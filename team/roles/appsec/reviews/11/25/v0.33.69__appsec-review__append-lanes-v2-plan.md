# Append Lanes v2: AppSec review of the implementation plan

**date** 25 Nov 2026 · **role** AppSec · **status** Review of a PROPOSED plan. Nothing reviewed here exists in code yet.
**inputs:** [the plan](../../../../dev/reviews/11/25/v0.33.69__dev-plan__append-lanes-v2-implementation.md), [the architect review](../../../../architect/reviews/11/25/v0.33.69__architect-review__append-lanes-v2-capacity-large-payloads-signed-lanes.md) (§1, §4, §9), and the code on `claude/vault-inbox-append-api-jj79bn`.
**evidence:** [executed] means an in-memory probe, or an offline botocore/cryptography run, in the review session. [code-read] means read but not run. No production service was contacted.
**re-checked by the planning session:** AS-4 (`configure` accepts a `NaN` limit and a plaintext `label` field: 200) and AS-11 (the token type accepts a trailing newline) were re-run and reproduce [executed]. The scope excludes the webhook, which the owner dropped on 25 Nov (no server-initiated outbound calls).

## Verdict

The direction is sound, and Phase 4's cryptographic core is well chosen. Names derived from content, not from the malleable signature, are correct. Grants bind both the vault and the lane. Verification is local. The plan is **not ready as written for Phases 2–4**. Two design flaws need to change before code:
- **AS-1:** replay protection covers only `pending/`, and client-chosen timestamps hide entries behind reader cursors.
- **AS-2:** the blob byte budget can be bypassed with a public token, and the check also gives writers a byte-precise oracle.

Most Medium items are about `configure`: it has no schema, it can downgrade a lane or lose a revocation silently, and Phase 4 rollback fails open. The others are the per-instance count cache, read keys that cover the whole vault, a retention-tag bug that deletes unread entries, presign pitfalls, and the app-bridge permission mapping.

**Phase 1 can start now**, with AS-11 and AS-16 folded in. Nothing in the plan adds server-initiated egress apart from the dropped webhook. Its leftover references should be removed (I-2).

## Detail

### AS-1 (High): replay and ordering
**Plan:** "The entry's file id is `<ts_ms>_<first 24 hex of sha256(grant_id | signed string)>.enc` … the write is create-only. A replay inside the window lands on the same name and changes nothing." It also tells agents to "mark entries after decoding instead of keeping local seen-id files".

**Problem:**
- "Create-only" means "absent from `pending/`". Once a reader marks the entry (or a purge removes it), a replay within ±300 s writes it again. Readers can rebuild the full signed request, because the writer seals the grant, signer and signature into the entry. So can anyone who saw the request. An agent then acts on the same entry twice, and the plan has just told agents to drop their dedupe files.
- The file id's time prefix comes from the client and may be up to 300 s old. A reader paging with `after_file_id` never sees such an entry. Honest clock skew does this too. Today the server assigns the time, so this window is only the PUT latency (milliseconds).
- No create-only storage primitive exists. `Storage_FS__S3.file__save` is a plain `put_object`, and Memory-FS overwrites.

**Evidence:** [executed] A simulation using today's `mark_processed` gave: first write stored, replay "duplicate", mark, then replay → **stored again** and listed as pending. An entry with ts = now − 200 s was **not visible** after the cursor. [code-read] `Storage_FS__S3.py:81-87`.

**Fix:**
1. Before storing, create-only write a zero-byte marker `bare/append/<token>/replay/<sha256(grant_id|signed string)>`, with `If-None-Match: *` and tag `sg-retention=1d`. If it already exists, return `{ok:true}` and do nothing. The marker holds only a hash.
2. Name the entry `<server_now_ms>_<first 24 hex of that hash>.enc`. This keeps the file-id pattern, and cursors stay monotonic.
3. Add `file__save__if_absent` to the storage layer: on S3, `put_object(IfNoneMatch='*')` (supported by botocore 1.44.11 [executed]); on memory/disk, an exists-check under a lock.
4. Keep the "drop seen-id files" advice off signed lanes until step 1 ships.

### AS-2 (High): blob budget race and oracle
**Plan:** "The server checks … `size ≤ max_blob_bytes`, and the lane's byte budget", with a 900 s URL. Decision 2 recommends "owner opt-in with a byte budget" for token lanes.

**Problem:**
- The budget counts only objects that already exist. With a public token, an attacker can request 1,000 URLs before uploading anything. Each one passes the check. Uploading all of them stores up to 1,000 × 256 MiB, limited only by the attacker's bandwidth. Orphan blobs also stay in the budget after readers drain entries, which locks the lane until retention or a purge. The owner cannot tell orphans from real attachments without decrypting every entry.
- The accept/refuse answer depends on the requested `size`, and costs no upload. About 28 binary-search requests reveal the lane's used bytes to the byte, and repeated polling shows reader activity. This breaks the blindness the plan promises ("A sender learns only … a 507 at the hard limit").

**Fix:**
- Decision 2 → **blobs on signed lanes only**.
- If token lanes keep blobs:
  - Each `blob-upload` create-only writes a reservation `blobs/.reserved/<sha256>`, with its size in metadata and a 1-day tag. The budget counts pending entries, blobs and reservations.
  - Refuse on a fixed condition, `used + max_blob_bytes > budget`, that does not depend on the requested size. The answer is then 1 bit, like today's 507.
  - Set the token-lane `max_blob_bytes` ceiling to 25 MiB.
  - Set PUT expiry to 300 s.

### AS-3 (Medium): count cache overshoot
**Plan:** "count is cached per instance for 5 s … concurrent instances can overshoot slightly". The risk table says "bounded to about 5 s of appends per instance".

**Problem:** The bound is per instance, and the attacker controls how many instances run. Lambda scales with in-flight requests. Total overshoot is roughly K instances × R accepts/s × 5 s.

**Evidence:** [executed] Model with an empty lane, hard = 5,000 and R = 30/s: K = 100 accepts about 15,000 (3× hard); K = 500 accepts about 75,000 (15×).

**Fix:**
- Trust the cache only while `cached + local_accepts < hard − margin`, with margin = max(100, 10% of hard).
- Inside the margin, count exactly on every append and every `unmark`. Overshoot is then bounded by in-flight requests, the same TOCTOU as today.
- DevOps: reserved concurrency on the user Lambda, and a WAF rate rule on `/api/vault/append/write*` and `/blob-upload*`.
- Correct the risk-table wording.

### AS-4 (Medium): `configure` has no schema
**Plan:** "`configure` refuses values above the server ceilings (400)". Config is free JSON.

**Problem and evidence:** [executed]
- Starlette parses bodies with `json.loads`, which accepts `NaN` and `Infinity`. `NaN > 5000` is False, so it passes the ceiling check, and `count >= NaN` is always False. Any SG/Send account can therefore make an **unlimited public lane**. Booleans are ints in Python.
- Today `configure` stores whatever it receives. A 13.6 MB `append_anchors` list was accepted (the route caps it at about 6 MB). With a TTL, every warm instance re-parses that config every 30 s.
- Without a whitelist, `lanes[*]` would store owner labels or a `webhook_url` in plaintext, which breaks ground rule 2.
- Interpolating `retention_days` into `x-amz-tagging` allows tag injection (`30&x=y`).

**Fix:**
- Model the config as Type_Safe classes (`Schema__Append__Config`, `Schema__Append__Lane`). Type_Safe `int` rejects NaN, bool, float and str [executed]; then range-check `1 ≤ v ≤ ceiling`.
- Reject unknown keys at every level with 400.
- Limits:
  - `lanes` keys must match `^[0-9a-f]{64}\Z` and be in `append_anchors`; at most 64 lanes.
  - At most 256 anchors, 16 `enum_key_hashes` and 1,024 `revoked_grants`.
  - `retention_days` ∈ {7, 30, 90, 365, null}.
  - `lane_key` validated as in AS-12.
  - Configure body at most 64 KiB.

### AS-5 (Medium): downgrade and lost updates
**Plan:** "`configure` sets `lanes[<sha256(token)>]` to `{mode: "signed", lane_key, revoked_grants: []}`".

**Problem:**
- If `lanes[h]` is replaced whole, a Phase-2-era client that sets only `retention_days` wipes `mode`, `lane_key` and `revoked_grants`. The lane silently becomes writable by its public token.
- `configure` is read-modify-write with no concurrency control [code-read `:109-118`]. Two owner devices, say a revoke and a retention change, lose one update, and a revocation can vanish.
- Writing `revoked_grants` as a whole list lets a stale client un-revoke grants.

**Fix:**
- Merge per lane and per field.
- A lane leaves `signed` only through an explicit `{set_mode:"token", confirm_downgrade:true}`.
- Change `revoked_grants` and `enum_key_hashes` only through `add_*` and `remove_*` operations.
- Write config.json with `IfMatch=<etag>` (PutObject IfMatch exists in botocore 1.44.11 [executed]) and retry on 412. The memory backend uses a lock.

### AS-6 (Medium): rollback fails open
**Plan:** "Old code ignores `mode: signed` … rotate the tokens … or tell their owners first."

**Fix:** Ship a fail-closed guard in Phase 2 (add it as item 2.7). Writes, `blob-upload` and `unmark` on any lane whose `mode` is neither absent nor `token` return 401 `lane_mode_unsupported`. Rolling back to any build at Phase 2 or later then locks signed lanes rather than opening them. Rule: never roll back below Phase 2 once any lane is signed.

### AS-7 (Medium): read keys cover the whole vault
**Plan:** "Each keeper (feedback, site, maestro) gets its own key, removable on its own".

**Problem:**
- Every key still lists, fetches, marks and unmarks every lane in the vault.
- `list` returns the raw token as `inbox` [executed], and tokens are the folder names. So read access gives write access to every token-mode lane, and revoking a key does not take back the tokens it has already seen.
- The derived enum key belongs to every holder of the vault read key (app-shell: "the read key IS the enum key" [code-read]).
- `sg-append.js configure()` always re-sends `enum_key_hash` (line 85). Any later anchor rotation from the vault UI therefore restores the legacy, read-key-derived key after the owner has moved to per-keeper keys.

**Fix:**
- Use `enum_keys: {<sha256(key)>: {lanes: [<sha256(token)>…] | "*"}}` (at most 16), and have every enum-key verb filter by that scope.
- Document that revoking a keeper means rotating the tokens of the token-mode lanes it could list.
- Once scoped keys exist, refuse a bare `enum_key_hash` unless `legacy_enum_key:true` is sent.
- Change `sg-append.js` so it sends `enum_key_hash` only when asked.

### AS-8 (Medium): retention deletes unread data
**Plan:** "the copy into `processed/` sets an object tag"; "unmark … by server-side copy"; "Blobs carry the lane's retention tag from upload"; DevOps rule "expiring `bare/append/*` objects by tag".

**Problem:**
- CopyObject's `TaggingDirective` defaults to COPY [executed: the parameter exists; default per the AWS docs]. An unmarked entry carries `sg-retention=30d` back into `pending/`, and lifecycle deletes it unread.
- A blob expires N days after upload whether or not its entry was read. A reader offline longer than retention loses attachments, in the phase called "Don't lose things".
- S3 lifecycle prefixes are literal, so `bare/append/*` cannot be expressed. DevOps would end up with a tag-only rule covering the whole bucket.

**Fix:**
- `unmark`: `copy_object(TaggingDirective='REPLACE', Tagging='')`.
- `mark`: `REPLACE` with `sg-retention=<n>d`. osbot `S3.file_copy` exposes neither option, so call through `S3.client()`. The Lambda role needs `s3:PutObjectTagging` and `s3:GetObjectTagging`.
- Blobs get a separate `blob_retention_days`, untagged by default, and the UI warns that unread attachments can expire.
- Lifecycle: one rule per retention class, using `And{Prefix:"<storage root>/vault/", Tags:[sg-retention=Nd]}`.

### AS-9 (Medium): presigned PUT pitfalls
**Plan:** "a presigned `PUT` with `Content-Length`, `x-amz-checksum-sha256`, `If-None-Match: *` and the retention tag signed into it".

**Evidence:** [executed] botocore 1.44.11 puts all of these in `X-Amz-SignedHeaders` when they are passed as `Params` (`content-length;content-type;host;if-none-match;x-amz-checksum-sha256;x-amz-tagging`). A client that omits a signed header fails SigV4. However, the existing `osbot_aws S3.create_pre_signed_url` passes only Bucket and Key, so it signs `host` only. The transfer `create_upload_url` is unpinned for that reason [code-read]. Separately, `Safe_Str__File__Path` silently rewrites characters outside `[A-Za-z0-9_\-./\\ ]` [executed]. A key built outside Storage_FS can therefore differ from one built through it unless inputs are strictly hex.

**Fix:**
- Call `S3.client().generate_presigned_url('put_object', Params={…ContentLength, ChecksumSHA256, IfNoneMatch:'*', Tagging, ContentType:'application/octet-stream'}, ExpiresIn=300)`, and return the exact header map to the client.
- Add `Safe_Str__Vault__Append__Blob_Id` matching `^[0-9a-f]{64}\Z`, used by `blob-upload`, `blob-url` and `purge folder:blobs`.
- The server derives the base64 checksum from the validated hex.
- The test asserts the exact `X-Amz-SignedHeaders` string above.

### AS-10 (Medium): bridge permissions
**Plan:** "bridge: stats and processed listing under `append.list`, unmark under `append.markProcessed`"; "lane settings and read keys in the vault UI".

**Problem:** Apps granted `markProcessed` would gain `unmark`, which changes capacity. `MountLanes.LANE_VERBS` = list/fetch/markProcessed [code-read], so `unmark` would also reach **mounted child vaults**. If owner-only settings ever go through `sg.append.configure`, an app frame could add a read key, replace `lane_key` or downgrade a lane.

**Fix:**
- Give `unmark`, `stats`, `blob-url` and `blob-upload` their own `permissions.append.*` grants.
- Keep `unmark` out of `LANE_VERBS`.
- Expose `lanes`, `lane_defaults`, `enum_key_hashes`, `mode`, `lane_key` and `revoked_grants` only in the vault UI. The bridge keeps forwarding only `append_anchors`.

### AS-11 (Low): validation details feeding new paths
**Evidence:** [executed]
- `Safe_Str__Vault__Append_Token` accepts `"abab…ab\n"`, because `re.match` with `$` matches before a trailing newline.
- `Safe_Str__Vault__Append__File_Id` accepts a trailing `\n` and Arabic-Indic digits (`\d` matches Unicode digits, and `int()` parses them).
- `list_entries(after_file_id=123)` raises TypeError, which surfaces as a 500 today.

**Fix:**
- New types and validators use `re.fullmatch`, or `\Z` with `[0-9]`.
- Validate `after_file_id` against `^[0-9]{1,13}(_[0-9a-f]{0,24}(\.enc)?)?\Z` before building `StartAfter`; anything else is a 400.
- Validate lane names from `CommonPrefixes` with the token type and skip failures. (A vault write-key holder can create arbitrary keys under `bare/append/` through `/api/vault/write/{id}/{file_id:path}` [code-read].)
- Validate `folder` as a strict enum in the service as well as the route.

### AS-12 (Low): Phase 4 input handling
**Evidence:** [executed]
- A compressed-point SPKI loads as the same key under a different SHA-256.
- P-384 and Ed25519 SPKIs load without error, so the caller must check the curve.
- An off-curve point is rejected. r=0, s=0 and r≥n are rejected.

**Fix:**
- The server builds both strings from typed fields and never verifies a string the client supplies.
- A grant splits into exactly 6 fields, each fullmatched (literal tag, vault-id, 64 hex ×2, `[1-9][0-9]{12}`, 16 hex).
- JSON numbers must satisfy `type(x) is int`.
- `signer` and `lane_key` decode to exactly 91 bytes beginning `3059301306072a8648ce3d020106082a8648ce3d03010703420004`, then load and are checked for secp256r1.
- Signatures are exactly 64 bytes. Any exception from verify returns 401 `sig_invalid`.
- Refuse grants with `not_after > now + 400 d` (`grant_too_long`). Store revocations as `{grant_id: not_after_ms}`, prune expired ones, and cap the list at 1,024.

### AS-13 (Low): domain separation
Today's design signs the same string for an inline write and a blob upload. Anyone holding the blob bytes can replay a blob-upload signature as an inline entry, and an entry signature can be used to obtain a blob URL.

**Fix:** sign `sg-append/v1|write|…` for writes and `sg-append/v1|blob|…` for blobs. Document that a pki.sgit.ai key used as the writer key may sign only fixed-prefix strings.

### AS-14 (Low): check order
**Evidence:** [executed] ECDSA verify takes 64 µs, SHA-256 of 4.4 MB takes 4.2 ms, and base64 decoding of 4.4 MB takes 16 ms. The route decodes the payload before the gate [code-read `Routes__Vault__Append.py:59`].

**Fix:** this order: field formats → anchor gate → mode → ts window → `not_after` → revoked → signer hash → grant verify → decode and hash → sig verify.

### AS-15 (Low): stats cost
Calling `stats` without `inbox` lists up to 100k processed keys per lane, which means hundreds of LIST calls and a likely Lambda timeout. Any vault reader can trigger it.

**Fix:** require `inbox`, cap the processed count at 10k, and cache results per lane for 30 s.

### AS-16 (Low): `fetch` ceiling
**Fix:**
- Stop reading once the ceiling is reached; deferred ids are never read.
- Measure the ceiling in encoded bytes: the sum of `4·⌈n/3⌉` must stay ≤ 5.5 MB.

### Info
- **I-1 Revocation horizon.** A 30 s TTL is acceptable (the access-token cache is 60 s). The real horizon is TTL plus the life of URLs already issued (900 s PUT, 300 s GET). Clamp `SGRAPH_SEND__APPEND_CONFIG_TTL` to at most 300. Apply the TTL to cached tombstones and manifests too. Do not cache negatives beyond the TTL.
- **I-2 Webhook leftovers.** Remove the webhook column from the at-a-glance and team tables (including DevOps "confirm Lambda egress to the internet"), `webhook_url (W)` from the API table, test item 5, the SSRF risk row and decision 5. `configure` must reject `webhook_url` (AS-4). Nothing else adds egress: presigning is local, S3 HEAD/LIST/Copy are existing AWS calls, and grants are verified locally [code-read]. The existing Admin token lookup and n8n early-access POST are not new.
- **I-3 Blob serving.**
  - `blob-url` should set `ResponseContentType=application/octet-stream` and `ResponseContentDisposition=attachment`; a public-token writer can upload any bytes, HTML included.
  - S3 CORS: exact vault origins, PUT and GET only, the exact headers, never `null`. CORS is bucket-wide.
  - Direct-to-S3 requests log raw client IPs in S3 access logs and CloudTrail, bypassing the `ip_hash` rule.
  - The 412 presence oracle needs the ciphertext. `blob-upload` must not HEAD the key, and clients must never reuse a blob ciphertext across lanes.
- **I-4 Identifiers at rest.**
  - The raw token is the folder name, and it also appears in blob keys and presigned URLs. The `Safe_Str__Vault__Append_Token` docstring says "token = H(recipient public key)". A token built that way is an identifier at rest, so require random tokens.
  - Grants carry sha256(writer SPKI), whose first 16 hex characters are the pki.sgit.ai fingerprint. Never log grants.
  - The file id is a grant-keyed tag: anyone holding the grant can attribute entries to it.
- **I-5 Status codes.** New enum-key endpoints (`unmark`, `stats`, `blob-url`) should return 401, per ground rule 5. "Error codes stay as today (400, 403…)" contradicts that rule.

**Auth matrix (today → plan):**
- `write` and `blob-upload`: append token, which is public (+ grant on signed lanes).
- `list`, `fetch`, `mark`, `unmark`, `stats`, `blob-url`: enum key, which every vault reader holds.
- `purge` and `configure`: write key + SG/Send access token.
- `limits`: no auth.

The plan keeps today's pattern. The gaps are scope (AS-7, AS-10), not missing gates.

## Security tests the plan must add
1. Replay after mark, after purge, and after `unmark` is a no-op. A ts 299 s old is still seen by a cursor reader (AS-1).
2. 50 blob URLs issued before any upload cannot exceed the budget. The refusal does not depend on `size` (AS-2).
3. Two instances with warm caches near the hard limit overshoot by at most in-flight requests (AS-3).
4. `configure` rejects NaN, Infinity, true, 5.5, "5000", unknown keys, oversized bodies, lane keys not in the anchors, and `webhook_url` (AS-4).
5. A lane-level partial update keeps `mode: signed`. Two concurrent revokes both persist (AS-5).
6. A Phase 2 build refuses writes to a lane with `mode: "signed"` (AS-6).
7. A scoped read key cannot list or fetch other lanes. The legacy key is not restored by `configure` (AS-7).
8. LocalStack: an unmarked entry has no tag; a marked entry has exactly the retention tag (AS-8).
9. Exact `X-Amz-SignedHeaders`. Blob ids with `/`, `..`, a trailing `\n`, uppercase or 63 characters return 400 on all three blob verbs (AS-9).
10. `after_file_id` given as int, list or `"\n"` returns 400, not 500 (AS-11).
11. Compressed, P-384 and Ed25519 SPKIs, a 63- or 65-byte signature, and a grant with 7 fields or a bool `ts` all return 401, never 500. A signed lane with no signature fields returns 401. A signed lane whose token was removed from the anchors is refused even with a valid grant (AS-12).
12. A blob-upload signature replayed as an inline write is refused (AS-13).

## Checked and sound
- botocore 1.44.11 signs every pinned header when they are passed as Params [executed]. With all of them signed, a leaked PUT URL is useless without the exact ciphertext.
- ECDSA malleability is real ((r, n−s) verifies [executed]), so naming from content rather than the signature is correct. Degenerate r and s values and off-curve points are rejected [executed].
- Grants bind `vault_id` and sha256(token), so they cannot be reused across lanes or vaults. Rotating the lane key revokes every grant at once.
- Lane prefixes end in `/<hex token>/pending/`, so there is no prefix confusion between lanes, and `StartAfter` cannot escape `Prefix` [code-read].
- CopyObject keys are built only from validated tokens and ids, and osbot uses a dict `CopySource` [code-read].
- `/limits` takes no vault or lane input, so it is not an oracle. Keep it that way.
- The FastAPI stack has no middleware that logs request headers or bodies [code-read].
- No keys or plaintext are added at rest. Lane and writer keys are generated on the client.
- A 30 s config TTL is adequate for revocation.
