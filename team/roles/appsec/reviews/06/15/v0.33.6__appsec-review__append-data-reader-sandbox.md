# AppSec Review — Append Data Reader sandbox (jail + key custody)

**Version:** v0.33.6
**Date:** 2026-06-15
**Reviewer:** AppSec (Explorer team)
**Target:** [`../../../../architect/reviews/06/09/v0.33.6__architect-spec__append-data-reader-sandbox.md`](../../../../architect/reviews/06/09/v0.33.6__architect-spec__append-data-reader-sandbox.md)
**Scope:** the design only (no code exists yet — D3 is the security-critical increment). This review is the gate that must clear before D3 merges.
**Verdict:** **Conditional approval.** The two-layer split (trusted parent unseals; untrusted reader jailed) is the right shape and materially safer than rendering vault-supplied code in the app realm. Approval is contingent on the **must-fix** controls in §3 being specified and test-covered before D3 merges.

---

## 1. Threat model (what we are defending)

| # | Threat | Actor | Asset |
|---|---|---|---|
| T1 | Vault-supplied `reader.js` exfiltrates decrypted message content | attacker who authored a vault you opened | plaintext bodies |
| T2 | `reader.js` reaches the vault **private key** or `read_key` | same | decrypt capability for the whole vault |
| T3 | `reader.js` escapes the frame → drives the parent kernel (vfs writes, key ops) | same | the whole vault app |
| T4 | `reader.js` reads append traffic the user did **not** open | same | other senders' messages |
| T5 | Forged/confused `type` tag → raw-byte or mis-typed render | sender (append_token holder) | XSS / content spoof |
| T6 | Malicious `summary`/intent floods or smuggles data back to parent | same | parent integrity / covert channel |

The design's posture: **T1 is partially accepted** (a reader you opened can render misleading content *to you*), but T1-as-exfiltration, plus T2/T3/T4, must be **prevented**. T5/T6 must be **contained**.

---

## 2. Assessment against the spec's six asks

### 2.1 Jail escape (T3) — **sound, with caveats**
`sandbox="allow-scripts"` **without** `allow-same-origin` yields an opaque (null) origin: no parent DOM, no same-origin storage/cookies, no `BroadcastChannel` to a named origin. This is the correct primitive. Caveats that become **must-fix**:
- **MF-1:** `allow-same-origin` must be absent *everywhere in the chain*. SGraph already nests sandboxed kernels (ViV). If this reader iframe is mounted **inside** an already-sandboxed kernel that itself was granted `allow-same-origin` for some reason, opacity can be subverted. Verify the reader frame is a direct, independently-sandboxed child and that no ancestor grants same-origin to it.
- **MF-2:** Do **not** also add `allow-popups`, `allow-top-navigation`, `allow-modals`, `allow-forms`, or `allow-downloads`. Each is an exfiltration or nuisance vector. The spec already omits them — pin this in a test that asserts the exact `sandbox` token set.

### 2.2 Egress / CSP (T1) — **sound, tighten the directives**
`default-src 'none'` with no `connect-src` blocks fetch/XHR/WebSocket/`sendBeacon`/EventSource. Required additions/confirmations:
- **MF-3:** Add **`connect-src 'none'`** explicitly (don't rely solely on `default-src` fallback — some engines have historically leaked WebSocket/`navigator.sendBeacon` past `default-src`; explicit is defense-in-depth).
- **MF-4:** Add **`frame-src 'none'`** / **`child-src 'none'`** and **`object-src 'none'`** so the reader can't nest its own iframe (a re-sandbox-with-same-origin trick) or embed plugins.
- **MF-5:** `img-src data:` is acceptable, but **`media-src 'none'`** and **no `font-src` remote** — a remote font/`<video>`/`<audio>` URL is a beacon. Confirm `style-src 'unsafe-inline'` does **not** imply remote `@import`/`url()` egress; pin `style-src 'unsafe-inline'` (no `https:`).
- **Note (accepted):** `script-src 'unsafe-inline'` is required to run the reader and is acceptable *because* there is no network to exfiltrate to. The CSP's value here is egress control, not script control.
- **MF-6:** Belt-and-braces — set the iframe **`allow` (Permissions-Policy)** to deny `camera; microphone; geolocation; clipboard-read; clipboard-write; usb; ...`. Clipboard in particular is a plausible covert/annoyance channel inside a frame the user interacts with.

### 2.3 Key custody (T2) — **the core control; make it auditable**
The whole model rests on "the key never enters the jail."
- **MF-7:** The parent must perform the X25519 unseal in the **parent realm only**, and the message posted into the jail must carry **only** the unsealed inner bytes for the specific opened message — never the private key, never `read_key`, never the ciphertext envelope (the envelope contains the `ephemeral_pubkey`; harmless, but send only what the reader needs).
- **MF-8:** Add an **invariant test**: scan every `postMessage` payload crossing parent→jail and assert it matches the `{ msgId, folder, innerBytes }` schema and contains no key-shaped material. This is the single highest-value test in D3.
- **MF-9:** Zeroize the private key buffer after unseal where the platform allows, and ensure it is never written to logs, the debug pane, or error messages that could surface in the jail.

### 2.4 Type confusion / fallback (T5) — **must be fail-safe**
- **MF-10:** Unknown, missing, or malformed `t` → the **built-in fallback reader** renders **metadata only** (size, received-time, the literal `t` string, escaped). It must **never** render raw inner bytes and must **never** guess a type.
- **MF-11:** `decode`/`render` exceptions are caught **per message**; one poisoned message cannot blank the list or wedge the harness. Each message renders in its own try/catch with an error placeholder.
- **MF-12:** `t` is attacker-controlled (it sits inside sender-sealed plaintext). Treat it as an untrusted string: length-cap it, character-allowlist it before using it as a registry key, and never use it to index anything but the reader map (no path/prototype lookups — guard against `__proto__`/`constructor` keys).

### 2.5 Intent channel (T6) — **parent must treat the jail as hostile**
- **MF-13:** Every jail→parent message is validated against a strict allowlist schema (`{ intent ∈ {markProcessed, purge, reply}, payload }`), size-capped, and **rate-limited**. No `eval`, no dynamic dispatch, no reflecting `payload` into a privileged call without re-validating ids against the set the parent actually fetched.
- **MF-14:** `markProcessed`/`purge` intents must be **re-authorized by the parent** against the currently-open vault and the file_ids the parent itself listed — the jail cannot name arbitrary file_ids or vaults. (Prevents a malicious reader from purging messages the user never saw.)
- **MF-15:** `summary` objects sent back for any in-jail list are bounded (field allowlist + per-field length cap) so they cannot be used as a high-bandwidth covert channel or to inject markup into a parent-rendered surface. **Preferred:** keep *all* human-readable rendering inside the jail (spec §4.1 already leans this way) so no reader-controlled string is ever rendered by the parent.

### 2.6 Rendering / sanitizer (T5) — **specify the allowlist before build**
- **MF-16:** `ctx.markdown` must be an **allowlist** sanitizer (tags + attributes), not a denylist: no `<script>`, no event-handler attributes, no `javascript:`/`vve:`/`data:` URLs in `href`, no `<iframe>/<object>/<embed>/<form>`, no `srcset`. CSP already blocks most egress; the sanitizer is defense-in-depth and the anti-spoof layer.
- **MF-17:** `ctx.h` must reject event-handler attribute names (`on*`) and scheme-bearing URL attributes that aren't `data:` images. Pin with a test.

## 3. Must-fix summary (gating D3 merge)

MF-1, MF-2 (sandbox token set) · MF-3, MF-4, MF-5, MF-6 (CSP/permissions egress) · MF-7, MF-8, MF-9 (key custody + invariant test) · MF-10, MF-11, MF-12 (fail-safe typing) · MF-13, MF-14, MF-15 (hostile-jail intent handling) · MF-16, MF-17 (allowlist rendering).

Each MF needs at least one assertion in the D3 test set. The two non-negotiables: **MF-8** (no key crosses the boundary — invariant test) and **MF-10** (no raw-byte render on unknown type).

## 4. Residual risk (accepted, to be documented for the owner)

- A reader in a vault **you chose to open** can display **misleading content to you** (phishing-style). It cannot exfiltrate, cannot reach keys, cannot escape. This is equivalent to opening any untrusted document and is acceptable — but the owner UI should make clear *whose* vault/reader is rendering (provenance line), and `from` must be shown as **sender-asserted, not verified** (TOFU — matches spec §11).
- Browser-engine CSP/sandbox bugs are out of our control; MF-3–MF-6 are the defense-in-depth margin. Pin a supported-browser matrix and re-test on engine updates.
