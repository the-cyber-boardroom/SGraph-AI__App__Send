## 1. Phase 3 Security Gate — SEC-VIV-001 CLOSED

**Finding (SEC-VIV-001, from SECURITY-same-origin-app-bypass.md):**
> Vault apps running in same-origin `allow-same-origin` iframes could bypass the sg.* bridge entirely, reading `localStorage` (vault keys, access tokens), walking `window.parent` DOM, and making direct `fetch()` calls to vault endpoints.

**Remediation shipped (commits f534b27 + 1b5b6b1 + probe fixes):**
- All 4 iframe mount sites in `app-shell.js` now use `sandbox="allow-scripts allow-forms"` (no `allow-same-origin`).
- Content delivered via `srcdoc`, not a parent-origin `blob:` URL (null-origin sandbox refuses `blob:` from another origin).
- The `blob:` URL / `_objectUrls` dance is removed from these sites.

**Verification evidence:**
- Phase 3 probe suite: 30 Playwright assertions, 0 failures.
- Probe P5 (body-hide self-check via `postMessage`) browser-locked.
- T1 + T2 (null-frame `parent.document`/`localStorage` access throws) require a real browser — these are the direct tests of the security property and should be run in the next browser E2E session.

**Residual note:**
- `sg-app-banner.js`'s `_tryInjectIframeErrorListener` is now dead for null-origin app-shell frames (same-origin `contentDocument` reach impossible). The Phase 4 error re-spec (in-frame `postMessage({type:"sg-app-error"})`) replaces this. Status: **addressed**.
- `allow-forms` retained across all 4 sites pending per-app inventory (ViV plan §5.7 item 2). If an app doesn't use forms, `allow-forms` is unnecessary. However, removing it could break existing apps. **Deferred to Phase 6 hardening (P-262).**

**Status: SEC-VIV-001 CLOSED.** The vulnerability class (same-origin bypass via allow-same-origin) is eliminated for all 4 app-frame contexts.

## 2. Credential Tier Gate (B5/B6) — Security Assessment

**Module:** `viv-credential-tiers.js`
**Gate point:** `kernel-parent.js relay()` — BEFORE mediation (broker entry only created for operations that pass the gate).

**Tier model:**
| Verb | Required Tier | Default Present | Pass? |
|------|--------------|----------------|-------|
| fs.read, vfs.read | NONE | yes | always |
| fs.write, vfs.write | STANDING | ambient | yes for normal ops |
| fs.delete, vault.delete | PER_REQUEST_RW | no | EUNDERPRIVILEGED unless perRequest credential present |
| Unknown verbs | PER_REQUEST_RW (fail-closed) | no | blocked |

**Security assessment:**
- Fail-closed on unknown verbs is correct.
- The gate running before mediation means a refused operation never enters the broker log — no audit trail. This is intentional (log only what was attempted within policy).
- **Gap (P-254 still PROPOSED):** The full credential tier feature (issuance, token format, revocation) is not yet built. Currently, standing credentials are always present and per-request credentials are never issued. This means the gate correctly blocks fs.delete/vault.delete, but there is no path to elevate to PER_REQUEST_RW legitimately. This is safe (conservative) but limits functionality.

**AppSec recommendation:** The gate as shipped is the correct security posture. Build the issuance UX (P-254) only with explicit AppSec review of the token format and revocation model.

## 3. Custody Gate (B10) — Security Assessment

**Module:** `viv-custody.js`
**Mechanism:** Fail-closed. Unknown custodians are rejected with EUNSAFE_CUSTODY before any channel operation begins.

**Security assessment:** Correct. Prevents "trusted by accident" — a kernel accepting operations from an unexpected source. The gate is at the channel level, so it runs before any application logic sees the message.

**Residual concern:** The custody model assumes the kernel knows its expected custodian set at spawn time. If a kernel is re-parented (spawned by one kernel, adopted by another), the custody check would fail. This is the correct behaviour — re-parenting should not be silently permitted. **No action needed.**

## 4. Vault Chat Attack Surface Assessment

Vault Chat is architecturally secure by design because it is a null-origin app iframe using the same sg.* bridge. The security properties of Phase 3 apply automatically.

**New surfaces introduced by Vault Chat:**

### 4.1 LLM API Key Exposure

The chat iframe makes direct LLM API calls (OpenRouter or similar). The API key must be accessible to the iframe. Options:
1. User pastes key into the app (stored in app's VFS, not in vault — no persistent exposure)
2. Key stored in vault encrypted (read via sg.vfs.read — goes through bridge, logged)
3. Injected by kernel via sg.* bridge at app startup

**AppSec recommendation:** Option 1 (user-managed in-session key) for the first version. The key never touches the server. If option 2 is used, the bridge's logging of the read operation creates a side-channel audit trail of key access frequency — acceptable.

**Do NOT use option 3** (kernel-injected LLM keys) without explicit AppSec review. LLM API keys injected via the bridge would be accessible to the app code — no different from option 1 in practice, but architecturally it sets a precedent for kernel-managed secrets that extends beyond vault crypto.

### 4.2 Prompt Injection via Vault Content

When Vault Chat reads vault files and includes them in LLM context, attacker-controlled vault content could include prompt injection payloads ("Ignore previous instructions and…"). 

**AppSec recommendation:** The sidecar LLM security checker (P-266) specifically addresses this — it inspects vault content for injection patterns before including in context. Until P-266 is built, document this risk in the Vault Chat user guide: "Do not connect Vault Chat to vaults containing content from untrusted sources."

### 4.3 VFS-Vault Sync Data Leakage

If VFS content (which may include raw LLM API keys or sensitive extracted facts) is synced to vault, it becomes part of the encrypted vault history. This is acceptable as long as:
1. VFS path prefix (`.vfs/`) is clearly documented as containing LLM session data
2. The user is informed that syncing creates a permanent record

**AppSec recommendation:** Display a notice ("VFS sync creates a versioned record in your vault") before enabling VFS-vault sync.

### 4.4 Phase 2 §7 CORS CDN Check (P-257)

The CORS code fix (`allow_credentials = False`, commit `434106dc`) is on dev. The operational verification — CDN cache invalidation, CloudFront `Origin` forwarding, `Vary: Origin` honoured — is still pending (OQ-cors-cdn-1). Until verified, null-origin fetch calls to the API may fail in a real browser. This is blocking Phase 2 §7 browser E2E (P-258).

**AppSec: this is a functionality issue, not a security regression.** The code change is conservative (removing credentials from CORS allows null-origin frames to make unauthenticated calls). No new attack surface is introduced; the change reduces one.
