## Executive Summary

The 24 May briefs introduce the most significant architectural security change to date: SG/Sentinel as the production enforcement surface for SG/Send's business model. This surfaces both new security capabilities and new attack surfaces that must be designed carefully before implementation.

**Critical security findings (design-time):**

1. **Identity-creation via fingerprinting can be gamed** — fingerprints must include entropy beyond IP
2. **The business-logic engine introduces a trust-level concern** — SG/Sentinel must not trust application state claims without authentication
3. **Vaults within vaults require clear security classification guidelines** — parent vault access implies child vault access
4. **Free/non-private mode's educational fingerprint display is itself a threat intelligence exposure risk** — must not expose more than can be legitimately disclosed
5. **OAuth vault-key derivation creates key-rotation failure modes** — must have a documented recovery path before launch

---

## Finding 1: Fingerprint Identity Gaming (P-224) — HIGH

**Design claim:** Every visitor, including bots, gets a fingerprint identity via SG/Sentinel's identity-creation rule. No cookies; local storage fair game.

**AppSec concern:** Browser fingerprints can be gamed. Sophisticated actors can:
- Clear localStorage (destroys the stable identifier)
- Rotate IP addresses (corporate NAT, residential proxies, Tor)
- Spoof browser characteristics (headless Chrome with manipulated `navigator` properties)
- Use multiple browser profiles/tabs

The fingerprint provides *soft* identity, not *hard* identity. This is acceptable for the free tier (it's educational and limits casual abuse) but **must not be used as a security-grade boundary**. The design correctly separates fingerprint identity from the zero-knowledge vault model.

**Recommendation:**
- Document explicitly: fingerprint identity is *abuse-deterrence*, not *security assurance*
- The hostile-to-bad-traffic goal (make attacking expensive) is achievable with fingerprints; deniable cryptographic identity is not
- Fingerprint evidence should feed the *anomaly score* (per the behavioural spec P-218) but not serve as the sole gate for high-value actions (payment, vault creation)

---

## Finding 2: Business-Logic Engine Trust Model (P-228) — HIGH

**Design claim:** Authn/authz/metrics moved into SG/Sentinel rules; app declares logic to Sentinel.

**AppSec concern:** If the application communicates its state to SG/Sentinel via headers (the "communication module" in P-239), and SG/Sentinel trusts those headers, an attacker who bypasses SG/Sentinel (e.g., via a direct Lambda URL call) can forge state and bypass business-logic controls.

**Required design invariants:**
1. SG/Sentinel must authenticate that headers come from a trusted source (PKI-signed, per P-238 per-deployment PKI)
2. The application Lambda URL must NOT be publicly accessible — traffic must only arrive via SG/Sentinel
3. The two-way conversation (SG/Sentinel → app) must use a shared secret or PKI, not just an IP allowlist (Lambda@Edge IPs are not fixed)

**Recommendation:** Before implementing the business-logic engine, design and test the traffic isolation model. Confirm: (a) Lambda URL has no public DNS alias, (b) SG/Sentinel signs its forwarded requests, (c) application validates the SG/Sentinel signature on every request.

## Finding 3: Vaults Within Vaults — Security Classification (P-231) — MEDIUM

**Design claim:** Parent vault holds child vault key; parent reads children it references.

**AppSec concern:** The parent vault's security classification implicitly applies to all child vaults it references. If the parent vault key is shared (e.g., as a share token for read-only access), the recipient can access all child vaults referenced in the parent.

**This is by design** — the vaults-within-vaults feature intentionally makes child vaults accessible to parent vault readers. However, it must be communicated clearly:

1. **User-facing:** "Sharing this vault shares access to all linked child vaults" must be shown in the vault browser UI before generating a share token
2. **Developer guidance:** Child vaults should not be used to store data that should be hidden from parent vault readers (e.g., do not store admin configuration in a child vault of a public-facing parent)

**Recommendation:** Add an explicit security warning in the vault browser's share flow: "This vault links to X child vaults. Sharing this vault also shares access to all linked child vaults."

## Finding 4: Educational Fingerprint Display — Threat Intelligence Exposure (P-223) — MEDIUM

**Design claim:** Free/non-private mode shows users "exactly what we can discover about them" from their IP.

**AppSec concern:** The educational fingerprint display reveals our threat detection capabilities to attackers. If we display "we detected you are using a residential proxy", "we detected your datacenter ASN", or "we detected inconsistency between your reported timezone and your IP geolocation" — we are teaching attackers what signals to suppress.

**Acceptable disclosures (low risk):**
- IP geolocation (country, city) — widely available via public IP databases
- Browser and OS (user-agent) — attacker already knows this
- Whether the IP appears in public threat intel lists (AbuseIPDB reputation)

**Avoid disclosing:**
- Specific behavioural anomaly scores or detection rules triggered
- Internal fingerprint hash values (could be used to pre-compute collisions)
- Which specific signals contributed to an anomaly detection

**Recommendation:** Design the educational display as a "here's what your IP reveals about your location" tool, not a "here's what our security system knows about you" tool. The former is educational and low-risk; the latter is a capability intelligence leak.

## Finding 5: OAuth Vault-Key Derivation — Key Rotation Failure Mode (P-230) — MEDIUM

**Design claim:** Client-side OAuth with vault-key derived from provider secret OR stored in Google appDataFolder.

**AppSec concern — derivation path:** If the vault key is *derived* from the OAuth secret (e.g., the refresh token), and the user revokes the OAuth grant or the provider rotates the underlying secret, the derived vault key changes and the vault becomes permanently inaccessible. There is no recovery path.

**The appDataFolder path is safer** — the vault key is stored independently of the OAuth session; losing OAuth access means the user needs to re-authenticate, but the vault key is still in appDataFolder.

**Recommendation:**
- Mandate the appDataFolder storage path (not derivation) for Google OAuth
- For other providers, design explicit key backup/escrow mechanisms before launch
- Document the "what happens if you lose OAuth access" recovery flow before any OAuth launch

---

## Finding 6: Free Mode's "Maximum Governance" — Zero-Knowledge Nuance (P-227) — LOW

**Design claim:** In free mode, activity is visible but file *content* is unseen (zero-knowledge preserved).

**AppSec assessment:** This is correct and the right design. The file content is AES-256-GCM encrypted client-side; the server (and SG/Sentinel) sees only ciphertext. Activity metadata (transfer sizes, timing patterns, access patterns) is visible, but this is normal and acceptable.

**However:** Access pattern analysis can sometimes infer content (e.g., a 4MB encrypted file is likely a PDF; a 12KB encrypted file is likely a document). This is a theoretical concern, not an actionable threat at this stage. The zero-knowledge nuance should be documented clearly in user-facing materials: "We can see that you transferred a file; we cannot see what it contained."

## Security Sequencing Recommendation

Implement in this security-conscious order:

1. **SG/Sentinel passive mode** — observe only, no changes, zero risk
2. **Vaults within vaults** — UI-only, no backend, add the sharing security warning
3. **Ephemeral-by-default** — reduces data retention risk immediately
4. **Fingerprint identity** — after agreeing on what fingerprint identity guarantees (abuse-deterrence only)
5. **Traffic isolation model** — before business-logic engine; confirm Lambda URL is not publicly accessible
6. **Business-logic engine** — after traffic isolation; after PKI-signed inter-layer communication is designed
7. **Client-side OAuth** — after appDataFolder key storage mechanism is designed and recovery flow is documented
8. **Free-tier fingerprint display** — after agreeing on what can be safely disclosed (see Finding 4)
