# AppSec Finding — `allow-popups-to-escape-sandbox` granted unconditionally to inner-vault content

**Date:** 2026-05-31
**Reviewer:** AppSec (Explorer)
**Severity:** Medium (capability over-grant / sandbox-escape primitive handed to untrusted content)
**Status:** OPEN — fix agreed, not yet implemented
**Affected branch:** `dev` (introduced `e80827f6`, preserved through Phase 4)
**Decision (Dinis, 05/31):** Gate popups to the **root vault only**. Inner / mounted
sub-vault content must NOT receive popup capability; an inner vault wanting popups
becomes a future *request + parent-consent* flow.

---

## Summary

The four app-frame render paths in `app-shell.js` set the iframe sandbox to:

```
allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox
```

unconditionally. Those same four methods are also the render surface for
**mounted sub-vault content** (via `CompositeDataSource`). The result: HTML/markdown/
page content from an *inner* vault — which never asked for it — inherits
`allow-popups-to-escape-sandbox`, i.e. the ability to open a **fully unsandboxed,
real-origin** browsing context that escapes the null-origin sandbox entirely.

This violates the intended model: **popups are the top vault's privilege**, with
inner vaults having to ask for (and be granted) that capability.

---

## Evidence (code-verified on `dev`)

### The four over-granted frames

`sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/_common/js/components/app-shell/app-shell.js`:

| Line | Method | Sandbox |
|---|---|---|
| 1215 | `_mountApp` | `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox` |
| 1290 | `_mountPageLayout` | same |
| 1344 | `_mountVaultFile` (HTML branch) | same |
| 1385 | `_mountVaultFile` (markdown branch) | same |

Introduced in `e80827f6` ("Also lands the external-link half of the deferred
Commit B work … sandbox: allow-popups + allow-popups-to-escape-sandbox at the four
app-frame mount sites"). Phase 4's `AppFrameBootstrap` refactor faithfully preserved
the string; it did not introduce or loosen it.

### The nested ViV kernel iframe is correctly clean

`app-shell.js:942` — `_spawnChildChannel` (the headless child-kernel frame,
`KERNEL_SHELL_HTML`):

```
iframe.sandbox = 'allow-scripts';            // null origin
```

No popups. `kernel-shell-bundle.js` contains **zero** `allow-popups`. The commit
author explicitly noted "The headless ViV kernel iframe is NOT touched." So the
gap is **not** in the kernel layer — it is in the four user-content render frames.

### Why inner-vault content lands in those frames

The four mount methods render through `this._dataSource`, which is wrapped in a
`CompositeDataSource` (`app-shell.js:1888`). The composite scans the root for
`*.link.json` mounts and **splices the child vault's tree in** under a
`mounts/<ref>/…` prefix (`composite-data-source.js:10-18`). Reads under a mounted
prefix are served through the same data source and resolved via `self._mounts`
(`app-shell.js:2035, 2077`). So opening an inner-vault `.html` / `.md` / `_page.json`
renders it in one of the four top-level frames — **with popups attached**.

The author's mental model appears to have been:
- *kernel iframe* = nested ViV kernel → left alone (correct), and
- *the 4 app frames* = "the user's own top vault" → given popups.

The missed fact: the 4 app frames are **also** the render surface for inner-vault
content via the composite. The inner vault inherits a capability it never requested.

---

## Risk

`allow-popups-to-escape-sandbox` lets framed content call `window.open(...)` and have
the new context launch as a **fully unsandboxed, real-origin** browsing context —
outside the null-origin sandbox. For *untrusted* inner-vault HTML this is:

- a **phishing / redirect vector** (open an attacker page in a real tab, styled to
  look like a trusted flow), and
- a **sandbox-escape primitive** (the escaped popup is not constrained by the
  iframe's sandbox at all).

The app frame document itself stays null-origin, so this is **not** a
vault-secret-exfiltration hole in the same class as same-origin would be — hence
Medium, not High. But it is a real capability over-grant to content that should be
treated as untrusted, and it contradicts the explicit design intent.

---

## Agreed fix — provenance gate (root-only popups)

Gate the popup tokens on **content provenance**, decided at mount time:

- **Root-vault content** (path does NOT resolve to a `mounts/<ref>/…` prefix) →
  keep `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox`.
- **Inner / mounted sub-vault content** (path resolves via `self._mounts.resolve(...)`
  / carries a `mounts/` prefix) → minimal `allow-scripts allow-forms` only.

The mount methods already have the signal needed to decide this:
`self._mounts && self._mounts.resolve(path)` (used at `app-shell.js:1987, 2020,
2070`). The decision should be centralised, not copy-pasted across the 4 sites —
candidates:

- Add a `sandbox` (or `allowPopups`) field to the `AppFrameBootstrap` **descriptor**
  contract and have each mount method compute provenance once and pass it, OR
- Add a tiny pure helper (e.g. `AppShellNavHelpers.sandboxFor({ isMounted })`)
  returning the correct token string — unit-testable in Node, matching the codebase's
  pure-logic-extraction pattern (cf. `decideMountStrategy`).

**Note:** `AppFrameBootstrap.build()` returns only the *HTML string*; the iframe's
`sandbox` attribute is set by the caller in `app-shell.js`. So the gate lives in the
4 mount methods (or a shared helper they call), not in the bootstrap builder.

### Future: inner-vault popup *request* flow (the slot this preserves)

Once popups are withheld from inner vaults by default, "an inner vault asks for
popups" becomes an explicit capability:

- declared in the inner vault's `app.json` (e.g. `permissions.ui.popups: true`),
- surfaced to the **parent/top** operator for consent (same shape as the existing
  fs grant / custody consent flows), and
- only then does that mount's frame get the popup tokens.

This is consistent with the deny-by-default permission model already shipped
(B-items / MIGRATING-TO-THE-PERMISSION-MODEL.md). Not in scope for the immediate
fix — but the provenance gate is the precondition that makes it expressible.

## Suggested tests (when implemented)

- **Unit** (pure helper): root provenance → token string includes `allow-popups`;
  mounted provenance → token string is exactly `allow-scripts allow-forms`.
- **E2E / probe** (real browser): a frame mounted for a `mounts/<ref>/…` path has a
  `sandbox` attribute **without** `allow-popups`; a root-path frame has it. Pin it so
  a future refactor can't silently re-flatten the grant (same spirit as the Phase 3
  null-origin probe locks).
- Keep the existing root-vault external-link-in-new-tab behaviour green.
