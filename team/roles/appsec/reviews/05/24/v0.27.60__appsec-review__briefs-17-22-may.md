## Part 1: SG/Sentinel Security Assessment

### Design Strengths

**1. No-invalid-request principle (critical property)**
Allowlist-not-denylist is architecturally superior to denylist-based WAFs because it fails safe. An unknown request is blocked by default. Generic WAF rules are a denylist that must be perpetually updated; our model requires an explicit permit. This is the correct security posture when we control both the client and server.

**Security value:** Eliminates entire classes of unknown-unknown attacks. An attacker exploring undocumented paths gets blocked by default, not logged for later analysis.

**2. Tabletop simulation discipline**
The tabletop found five security-critical gaps before any code was written (see Gap Assessment below). This is the AppSec ideal: threat modelling on paper, not in production. The discipline should be continued throughout the implementation phase (tabletop each new feature before coding).

**3. Time-as-security-dimension**
The detect-before-damage framing is correct: success is damage prevented, not requests blocked. The fingerprint allowlisting (good users go faster) inverts the usual security/usability tension. Security is a performance benefit for legitimate users, not a tax.

**4. Rules-as-vault with per-rule IAM**
Version-controlled rules with per-rule least-privilege IAM scoping is the right security model. A rule is a function with an IAM scope: it can only read what it needs. This limits blast radius of a compromised or malicious rule.

**5. Layer separation enforces correct use of LLM**
LLM interpretation is confined to Layer 3 (async, off-hot-path). LLM is explicitly forbidden inline in Layers 1/2. This is the correct posture: LLM in the hot path introduces latency and unpredictability; LLM in the async layer allows interpretation without performance degradation or blocking correctness.

### Gap Assessment (from Tabletop Simulations)

The tabletop found 25 gaps (11 in simulation 1, 14 in simulation 2). AppSec prioritisation of the nine major gaps:

| Gap | Severity | MVP? | Notes |
|-----|----------|------|-------|
| Fast-track bypasses authorisation (Tabletop 2, #1) | **CRITICAL** | Must fix | Fast-track as zero-trust acceleration (P-220) resolves this correctly. Verify the resolution is implemented, not just documented. |
| App must report auth outcomes (Tabletop 2, #4) | **HIGH** | Must fix | Without this, brute-force detection cannot work. Fire-and-forget async POST is the implementation path, but the API must exist and the app must call it. |
| Per-IP detection defeated by residential proxies (Tabletop 2, #2) | **HIGH** | Partial | Multi-dimensional keying is the solution. MVP can start with per-IP (catches a lot); must extend before production hardening. |
| In-profile exploits need content rules (Tabletop 2, #7) | **MEDIUM** | No | Sentinel is defence in depth, not sole defence. Honest limit correctly stated. Content rules are post-MVP; application-layer validation must exist independently. |
| Fingerprint storage at Layer 1 (Tabletop 1, #1) | **HIGH** | Must fix | Layer 1 has no I/O; fingerprint must be validated via signed token (tabletop resolution). The signed-token mechanism must be cryptographically sound (not just a session ID). |
| Symmetry blocks new deploys (Tabletop 1, #2) | **MEDIUM** | Must fix | New deploy temporarily has no known-good profile. Observe-mode on first deploy is the correct resolution. |

**AppSec verdict on the tabletop resolution:** The tabletop resolutions are sound. The critical concern is that they are **documented but not yet verified in implementation**. AppSec requests explicit acceptance criteria testing for each gap resolution before MVP is declared done.

### New Attack Surface: The Auth-Outcomes API

The app-must-report-auth-outcomes coupling introduces a new security surface:

**Threat:** If an attacker can POST fabricated auth-outcomes to Sentinel's API, they can manipulate the evidence graph (e.g., mark their own requests as "authenticated successfully" to build a fraudulent good-user fingerprint, or falsely flag legitimate users as brute-forcers).

**Mitigations required:**
1. The auth-outcomes endpoint must be API-key-protected (existing pattern)
2. Auth-outcome payloads must be signed by the application (not just submitted)
3. Rate limiting on the auth-outcomes endpoint itself
4. The evidence graph must validate that a claimed auth-outcome has a corresponding Layer 1/2 request log entry before accepting it

This threat should be modelled in a Tabletop 3 before the auth-outcomes API is implemented.

### New Attack Surface: The TUI API

The TUI API (Day 67, P-202, P-203) is a structured invocation surface. AppSec concerns:

**1. TUI API as command injection vector**
If the `invoke` surface is insufficiently validated, an attacker with TUI API access could invoke destructive operations. The native IAM least-privilege (P-203) addresses this: the IAM scope attached to the invocation context limits what can be called. **Required:** The IAM enforcement must be at the API layer, not just the tool layer.

**2. Memfs as exfiltration surface**
Skills.md and changelog loaded on demand are innocuous content. However, if the memfs scope is not precisely bounded, an attacker could request paths outside the intended orientation files. **Required:** The memfs virtual filesystem must serve only explicitly whitelisted paths.

**3. LLM-consumable output as prompt injection vector**
If the TUI API output is fed directly into an LLM context, the output could be crafted to inject into the LLM's context. **Required:** Treat TUI API output as untrusted input to LLMs; sanitise before including in agent contexts.

### SG/Sentinel and the Zero-Knowledge Boundary

The zero-knowledge boundary (Sentinel never performs file/malware scanning; no content inspection) is correctly stated in the research brief. AppSec endorses this constraint:
- Prevents Sentinel from becoming a GDPR liability (scanning encrypted content it should not access)
- Keeps the threat surface small and well-defined
- Ensures the project's core promise (server never sees plaintext) is not violated by the security layer

**Verification needed:** Confirm that the Layer 2 content rules (for in-profile exploits, post-MVP) do not violate the zero-knowledge boundary. Content rules should validate structure (is this a valid request shape?), not content (what data does this request contain?).

---

### The Honeytoken Resolution

The tabletop resolution for fast-track (honeytoken-touch-revokes-trust) is security-sound practice. Honeytokens are a proven deception mechanism for high-confidence compromise detection. AppSec notes:

1. **Honeytoken placement must be non-obvious to legitimate users.** If a legitimate user can accidentally touch a honeytoken (e.g., navigating to a plausible-looking URL), the false-positive rate will be unacceptably high.

2. **Trust revocation must be irreversible by the requestor.** The revoked fast-track fingerprint must not be recoverable by the same client; only an administrator can reinstate it.

3. **The minimal version (single honeytoken-touch-revokes-fast-track) is achievable in the MVP.** Do not defer all deception infrastructure to post-MVP; this one property can be in the MVP.

## Part 2: TUI API and Publishing (Day 67 AppSec)

### TUI API (P-202, P-203)
See above (TUI API as command injection vector, memfs bounds, LLM output). Also:
- The change-control surface must log all invocations with operator identity, timestamp, and outcome. Audit trail is a security requirement.
- The orientation endpoint ("now what?") must not leak sensitive information about internal system state.

### Publishing Architecture (P-197, P-198)
Articles-as-vaults and MyFeeds website. AppSec notes:
- Evidence graph in article vaults contains source materials that may be proprietary or regulated. Access controls must match the sensitivity of the content.
- Multilingual versions of articles in the same vault must have the same access controls as the primary version.
- The "email-style signoff inside article vaults" from the arch brief needs clarification: if this involves storing email addresses, GDPR retention constraints apply.

### Articles as Evidence Packs (P-193)
MyFeeds B2B research briefings as evidence packs. AppSec notes:
- Evidence packs for B2B clients may contain sensitive competitive intelligence. The vault's access model (encryption in browser, key with sender) is the right protection model. However, the sharing mechanism (who gets the decryption key?) must be part of the client onboarding workflow.

7. ✅ Fast-track = zero-trust acceleration (never skip authorisation)
