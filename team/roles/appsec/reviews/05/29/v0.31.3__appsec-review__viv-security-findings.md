## 1. Security Finding: Same-Origin App Bypass (Latent)

**Finding ID:** SEC-VIV-001  
**Severity:** Latent today; **Active the moment any non-first-party vault app code runs**  
**Status:** Documented; remedy designed; Phase 3 implementation PROPOSED (P-259)

### The Vulnerability

Vault app code runs in an iframe with `sandbox="allow-scripts allow-forms allow-same-origin"` — a real vault origin. Because the app frame shares the origin with the kernel, app code can bypass the `sg.*` bridge entirely:

- Read **vault key** and **access token** directly from `localStorage`
- Read/modify the kernel DOM and globals
- Reach `window.parent` / `window.top`

The permission model (Phases 1–4B: deny-by-default, EPROTECTED floor, grants, HUD consent) is enforced inside `sg.*`. Untrusted code simply reads bytes and sets commit headers without calling `sg.*`. The permission model is a real boundary only for cooperative code; for uncooperative code in the same origin, it is advisory and fully bypassable.

A sharp example: `.vault/app.json` is described as "always denied" via the EPROTECTED floor. The floor protects the file path through the bridge — it does **not** keep the secret away from same-origin app code, which can read the token from `localStorage` without ever calling `sg.vfs`.

### Why It's Latent (Not Active Today)

All vault app code is currently first-party. No adversary can place code in an app frame. The bypass is a design constraint, not an active hole, **as long as this remains true**.

### When It Becomes Active (Threat Model)

Any of the following makes this an active vulnerability:
1. A vault hosts **customer- or third-party-authored** HTML app code
2. A user can be induced to **open an untrusted shared vault** whose `app.json`/app code then runs
3. App templates or snippets from an untrusted source execute in a vault context

In those cases, app code can: exfiltrate vault key + access token, and (if a parent vault is open) reach `window.parent` to read **another vault's secrets** — defeating the entire permission model and any cross-vault isolation.

### The Remedy (PROPOSED — Phase 3)

The null-origin nested-kernel architecture from the ViV brief pack (version-2 §01) closes this:
- App frames run at `null` origin (`allow-scripts` only, no `allow-same-origin`)
- The app holds a `SecureChannel` port to the kernel — a capability, not credentials
- The kernel holds all secrets and enforces all policy
- App code cannot reach `localStorage` (SecurityError), cannot read `window.parent.document` (opaque origin), cannot reach `window.top` through the null-origin boundary

**Implementation:** Phase 3 of the ViV plan (P-259). Sub-step E (drop `allow-same-origin`) is the security gate flip.

### AppSec Directive

> **Do NOT enable any form of third-party, customer-authored, or shared-untrusted vault app code until Phase 3 sub-step E is complete and the T1/T2/T3 browser probe tests return BLOCKED.**

This directive must appear in AUTHORING.md and the reality/security/index.md trust assumption caveat (Phase 0 of the ViV plan).

## 2. ViV Architecture Security Assessment

### 2.1 Trust Direction — Correct

Parent→child only (D2). The child has no reference back — no port, no `window`, no upward reach. This is browser-enforced via port transfer at birth (the one `contentWindow.postMessage` + `[port]`). After that, everything is on MessagePorts — the child cannot initiate contact with the parent.

**Verified by:** M6 fix (cid check after unpack — rejects envelopes not addressed to this channel). Without this fix, a forged message from a grandchild addressed to a parent's cid would have been accepted.

### 2.2 Key Custody (D6) — Isolation is Default

The child generates its own non-extractable keypair from the one-use bootstrap key K1 (K1 mode). The parent never holds the child's private key after the handshake — K1 is immediately discarded. The parent can only read child traffic in monitoring mode (debug-build, off in prod), and monitoring mode must be visible in the vault-in-vaults page (PROPOSED, P-256).

**Risk: The trial credential model** (`_resolveChildCredentials` reading from `clinic.json` in the parent vault) is explicitly marked trial-only. The parent vault holds the child's write credentials. This is safe for synthetic data only. **It is the one combination that exposes child secrets to any same-origin code (because the parent app frame is still same-origin until Phase 3 lands).** The coupling rule from the brief pack must be enforced:

> **Do not ship ViV with real PHI until EITHER: (a) child-generated keys (not yet designed) OR (b) Phase 3 complete (so the parent app frame is null-origin and cannot exfiltrate the child's secrets).**

### 2.3 Anti-Replay — Correct

`ReplayGuard` in `secure-channel-envelope.js` rejects re-used nonces within the guard's lifetime. T6 (replay) is covered in the test suite (29 envelope assertions). This closes the replay attack vector on the inter-kernel edge.

### 2.4 Misrouting — Correct (after M6 fix)

The cid check after unpack (M6) ensures that a message correctly signed but addressed to a different channel ID is dropped unread and logged as EPROTO. T5 (tamper/wrong-key fail-closed) is covered in the test suite. **This was a real security gap before the fix** — a forged message could have been executed by the wrong kernel.

### 2.5 CORS (D5) — Code Fix Applied; Operational Verification PROPOSED

The code fix (`allow_credentials = False`, commit `434106dc`) is correct. The bug was that `allow_credentials=True` + `allow_origins=["*"]` caused Starlette to reflect the request Origin, emitting `Access-Control-Allow-Origin: null`, which browsers reject for null-origin frames. Setting `allow_credentials=False` gives a clean `ACAO: *`.

**Remaining risk (P-257):** CDN may have cached the old reflected-Origin header. Until CloudFront cache is invalidated and `Vary: Origin` is confirmed, cached responses could still block null-origin frames. This is the single operational gate for Phase 2 §7.

### 2.6 Phase 3 Parity List — Security Surface

The Phase 3 parity list (P1-P7 in ViV plan §5.4) includes items that have security implications:
- P7 (`sg-app-banner` iframe onerror capture, noted "same-origin only") — **will break under null**. The stub must absorb it or the feature is dropped. If dropped silently, it becomes an invisible regression that could surface as a bypass if the feature is re-added without null-origin consideration.
- P3 (in-app navigation / hash handling — top kernel owns the URL): app code in a null frame cannot manipulate the parent URL. Any feature relying on hash navigation from the app frame will break.

AppSec must be consulted before any parity item is marked "accepted regression" rather than "fixed."

## 3. Trust Assumption Documentation (Phase 0 — Not Yet Done)

**Required action:** The trust assumption must be explicitly documented before any external feature work proceeds. Text for AUTHORING.md and reality/security/index.md:

> "Vault apps are first-party and trusted. The permission model (Phases 1–4B) assumes cooperative app code. The permission model is NOT a boundary against untrusted code. Do NOT enable third-party, customer-authored, or shared-untrusted vault app code until Phase 3 sub-step E is complete (the `allow-same-origin` security gate)."

This is Phase 0 of the ViV implementation plan. It requires no code change — only a documentation commit. It should be the first commit in the Phase 3 work sequence.

## 4. Summary Verdict

The ViV architecture is sound and the security properties are correctly specified. The core risk is timing: the same-origin bypass is latent today and becomes active the moment the trust assumption is violated. The implementation plan has the right sequencing (Phase 3 as the security gate). The critical dependency is ensuring Phase 3 completes **before** any third-party app roadmap item is attempted.

The 10 bug fixes in this delivery (H1, M1–M6, L1, L3, L4) each had a real security or data-integrity consequence and were correctly identified and closed. The deferred L2 is a low-risk edge case.
