## 0 · The one correction that reorders everything

The revised brief's §3 says the app has exactly one working witness of a cross-mount write — the `state` on `sg.vault.mounts()` — and that it "reports the mount clean after a successful publish". It does not witness the write.

- `sg.vault.mounts()` returns `KernelParent.list()` rows; the `sync` object is `m._sync` (`kernel-parent.js:200`).
- `m._sync` is written in exactly two places: `status()` and `sync()` (`kernel-parent.js:169,177`).
- Those run only from `syncAll()`, which is called only by `app-shell._checkBehind()` (`app-shell.js:589`), scheduled by the tab-focus behind-check with a **30 s debounce** (`app-shell.js:576-582`).
- `sg.vfs.write` on a mount → relay → child `vfs.write` → `_safePush` → resolve. **It never updates `m._sync`.**

So the field reads `clean` before a successful write and `clean` after it (the write resolves only after the CAS push landed), and a failed publish rejects the write itself. The agent's check #3 is vacuous; its check #1 (read every written file back through the mount) is the only real one, and it is good — reads reconcile before serving. This also answers the brief's §5.3 timing question exactly: *the state is as of the last behind-check; the write does not settle it.*

Consequence: the receipt is not "nicer than the flag". It is the only per-write signal that can exist, and it is the first thing to build.

## 1 · SAFE — we will build these

No new information. | One shape for both paths (a mount-only shape is a mount oracle and an inconsistent API). ## 2 · NEEDS DESIGN — not in this cycle

| # | Item | Why not now |
|---|---|---|
| D1 | `sg.fs.delete` through a mount | `fs.delete` across a mount boundary is `PER_REQUEST_RW` (`viv-credential-tiers.js:48-49`); the relay classifies a request without a `credential` as `standing` → `EUNDERPRIVILEGED` **before** the broker (B5/B6). The per-request issuance model does not exist yet. Interim (safe): return `EUNDERPRIVILEGED` with a clear message instead of the composite's `EMOUNT_RO`, so callers stop trying. |
| D2 | `sg.history.*` across a mount | It is not "frozen" — it is **never routed**: `logCommits` takes `{limit, from}` only (`sg-vault--history.js:28`) and the bridge calls it on the parent unconditionally (`app-shell.js:3885`). Making it "live" is a new kernel verb, relay plumbing and a policy decision (it exposes the child's decrypted commit messages, including other writers', to the parent app). Defer; S1 removes the need for the agent's use case. |

## 3 · REFUSED — security

| # | Ask (as it could be implemented) | Refusal |
|---|---|---|
| N1 | Return **404** when the vault or lane behind `/api/vault/append/write/{vault_id}` does not exist | Today a bad token returns **403 whether or not the vault exists** — a missing manifest is `gate_failed` → 403 (`Service__Vault__Append.py:79-83`, `Routes__Vault__Append.py:68`), and has since 24 July. That uniformity is a deliberate absence of a vault-id existence oracle. The 404 HTML the agent sees comes from a layer above the route (the path matches `ROUTES_PATHS__VAULT_APPEND` exactly; routes are registered; dev deploys per push). **Nobody touches the gate until the response headers say where the 404 is generated.** |
| N2 | Lower `fs.delete` to `STANDING` so the relay "works" | The tier table is the control. Destructive verbs across a vault boundary need per-request elevation by design (architect pack §4.4). |
| N3 | Document (and thereby freeze) the **raw** mount row as the app contract, and add `vault_id` to it | The raw row carries `sync.head/named/serverHead` commit ids, `sync.lastError.message` (built from SGSend errors: `POST /api/vault/batch/<vaultId> failed (403): <detail>` — uncontrolled server text), `custody`, `ref`. `sg.vault.mounts()` has **no permission check** (`app-shell.js:4493`). The projection (S4) is the contract; `vault_id` stays out of it — the owner's `data.link.json` is where the app may read it, by the owner's choice. |
| N4 | `sg.fs.move` across a mount boundary (in↔out, mount↔mount) | A cross-vault copy+delete on two data sources; the current `fs` block acts on one. Partial state = duplication or loss. `EXDEV`. |
| N5 | Silent enum-key derivation on a **public-read** vault | `enum_key` is a pure function of the read key: publishing the read key publishes the lane's enumeration (ids, sizes, count). The agent's topology is safe by architecture (the lane sits on the private viewer vault), not by guard rail. Derive by default, refuse without explicit opt-in when the vault is public-read. |
| N6 | Adopt `declare-mount.mjs` as the worked example **before review** | It handles the highest-tier secrets in the system (child full key sealed with the parent write key; `ro-links.json`). Review gate, not a refusal: never prints a key (incl. `--dry-run`), never writes plaintext keys to disk, seals with the parent write key only, `ro-links` carries the read key only. Then adopt — it fills a real gap. |

## 4 · Corrections to the revised brief (so the next one starts from facts)

1. **§3 "the history is genuinely frozen"** — see D2. Both `log({path:'data/'})` and `log('data/')` return the *parent's* first-parent chain; the "25 vs 37" difference is not child-vs-parent. Build-order item 9's second option ("`sg.sync.refresh()` invalidates the snapshot") has nothing to act on.
2. **§3 "the mount state works"** — see §0. It is not a witness of the write.
3. **§3 / §5.3 "the only place the child's vault id survives"** — `list()` rows contain no vault id (`kernel-parent.js:188-201`). It survives in `data.link.json`, which the app can read.
4. **§1 "accidental read-only guard"** — `EMOUNT_RO` is explicit enforcement (`composite-data-source._refuseIfMounted`, 7 Sep) that replaced the silent-corruption case the 7 Sep brief predicted. The stripped prefix in `Folder not found: /poc` is the child's own view of the path (`hit.rest`) — by design.
5. **§5.1** — see N1: the code returns 403; the diagnosis "a gate failure rewritten into the 404 page" is not what the code can do.
6. **§2 "is the label attacker-controlled"** — it is owner-controlled and sanitised (S7).

What the brief got right and we adopt: the recoverable/irreversible split in the drain (goes into the guide, with the S1 durability caveat); the before/after commit-id diff instead of timestamps; the `path` parameter on append verbs as the interesting capability of the cycle.
