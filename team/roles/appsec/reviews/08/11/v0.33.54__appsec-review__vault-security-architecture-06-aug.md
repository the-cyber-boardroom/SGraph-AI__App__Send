## 1. Summary

The 6 August vault-authorisation thread (docs 928-931) describes a security architecture for the vault's agent execution surface. It is not a threat assessment of shipped code — it is a proposed design addressing a known attack class (prompt injection via ambient authority). This review assesses the design claims, confirms alignment with the shipped security properties, and flags gaps.

The design is sound. It addresses a real attack class with a named, studied pattern. The limitations are honestly stated in the briefs themselves. The main gaps are implementation: the kernel does not yet exist, the capability surface is not yet enumerated, and the ignore file blocking git+sgit coexistence has not been built.

---

## 2. The Attack Being Addressed

**Prompt injection via ambient authority.**

The vault today grants operations per-credential per-path. There is no notion of "this operation belongs to a declared flow". An instruction injected into content (e.g., a document the agent reads) can produce an action that is:
- Individually permitted (the credential has write access)
- Correctly authorised (the path is within scope)
- Entirely outside what was asked for

This is not a flaw in the vault's current design for its current use. It is the class of attack that becomes relevant when agents act autonomously using vault credentials.

**The ambient authority critique applies here:** the agent inherits read/write authority by virtue of where it runs. An attacker need not break anything — they only need to ask the confused deputy to use the authority it already holds.

## 3. Proposed Defences and Assessment

### 3.1 State machine in vault kernel (doc 928)

**Design:** Vault transitions from per-operation ("may this credential write here?") to per-transition ("is this the next legal step in the declared execution?"). The kernel holds the transition graph, tracks current state, permits or refuses the next step, and decrements a budget. It executes nothing itself.

**Assessment:** This is the plan-then-execute pattern documented in the agent security literature. It is a form of control-flow integrity. The design is correctly described, including its limits.

**Confirmed limit:** The state machine constrains which steps occur, not what those steps carry. An injected instruction causing a summary step to produce malicious content that then travels through the legitimate write step is NOT caught by sequence integrity. The brief states this explicitly and correctly. Mitigation is elsewhere (isolated processing, treating untrusted input as data not instruction, content-level constraints).

**AppSec position:** Build the kernel as described. Keep it minimal — the brief's verifiability constraint ("a reference monitor too large to analyse has failed on its own terms") is correct and should be the primary architectural rule. Every feature request that adds logic to the kernel should be reviewed with high scrutiny.

**Complete mediation:** The Architect's brief identifies "complete mediation" as the precondition for the security claim. Complete mediation means every access to every resource passes through the kernel. This is the hardest property to establish and the easiest to accidentally violate. It must be verified, not assumed. Recommend a formal audit of the kernel's call graph before claiming the property.

### 3.2 Plugins as capability grants (doc 930)

**Design:** A vault begins with no capabilities. Each capability (inference spend authority, storage path reach, network host reach) must be explicitly granted as a typed import. A plugin is not a code module — it is an authority grant. The reference is the permission.

**Assessment:** This is the object-capability discipline, correctly described. The critical rule — "the reference is the permission" — eliminates the confused-deputy failure by construction: a component that holds no reference to a resource cannot reach it, regardless of ambient authority.

**Component model alignment:** The brief notes that the WASM component model already implements this discipline: components begin with no filesystem, no network, no clock, and every capability must be declared as a typed import. If the vault workbench runs in a WASM component, this discipline is available today. If it does not, the discipline must be implemented at the vault layer.

**Migration path:** Instrument-before-enforce is the correct sequence. Implicit grants recorded silently → data reveals actual use → declare with warning → enforce. **AppSec must review the instrumentation data before enforcement begins.** The transition from "log what we grant" to "require what we grant" is a security boundary change, not a refactoring exercise.

**AppSec position:** Accept the design. Add one constraint: the instrumentation step must produce a capability surface document (the brief names this as the first deliverable of the plugin work). AppSec should co-own that document — it is the attack surface specification.

### 3.3 Engine outside vault (doc 929)

**Design:** The statechart execution engine that interprets declared flows lives outside the kernel. The kernel is a referee; the engine interprets the graph and decides which transition to attempt; the kernel permits or refuses it.

**Assessment:** Correct separation of concerns. The referee/player split is essential to the "small kernel" property. The engine can be complex; the kernel must not be.

**Formalism choice:** The brief recommends statecharts (XSTATE or equivalent) rather than inventing a new formalism. AppSec position: agree. A formal, testable, widely-deployed formalism has published tooling for verification. An invented formalism has none.

**Override boundary:** The brief introduces a vocabulary-and-override concept — a declared flow can be modified within declared bounds. AppSec flag: overrides must be authenticated. An unauthenticated override request is equivalent to a prompt injection at the flow level. The override mechanism must be included in the kernel's permission check, not handled at the engine layer.

### 3.4 Git + sgit coexistence and the ignore file (doc 931)

**Design:** A single directory holding both a git working tree and a sgit vault. The ignore file determines what git holds. What git holds determines the zero-knowledge status of the vault.

**AppSec position: this is a critical security property, not a convenience.**

If the vault's key material enters the git working tree (even transiently), the zero-knowledge property is violated for anyone with access to the git history. Git's history is not ephemeral — once committed, it persists in the reflog, the remote, any forks. The ignore file is not optional when using the coexistence pattern.

**The ignore feature has not been built (confirmed in doc 931).** The coexistence pattern MUST NOT be used until the ignore file is shipped and verified to exclude all vault key material from the git staging area.

**AppSec recommendation:** Add a pre-commit hook that verifies no vault key material is staged. The hook is a guard-of-last-resort; the ignore file is the primary control. Both are needed.

## 5. Vault Workbench Security Review (Docs 918-920)

The vault workbench (five-role review, doc 920) includes security findings verified against code. AppSec has not independently reviewed the workbench code — it lives in a vault, not the repo. The findings in doc 920 should be read by AppSec and compared against the proposed plugin architecture. If the workbench currently uses ambient vault authority, it will need to be refactored once plugin grants are enforced.

**Recommendation:** Obtain the vault workbench code and conduct an independent security review before the plugin enforcement step. The workbench is described as production-grade (13 replication recipes, multi-role review); it may accumulate downstream users before enforcement is in place.

## 7. AppSec Position Summary

The proposed vault security architecture is architecturally sound. It addresses a real, named attack class with the appropriate patterns. The design is honest about its limits. No shipped security property is threatened.

Three items require AppSec involvement before implementation:
1. **Capability surface enumeration** — AppSec co-owns this document
2. **Complete mediation verification** — required before claiming the kernel security property
3. **Ignore file** — must ship and be verified before the git+sgit coexistence pattern is used by any team
