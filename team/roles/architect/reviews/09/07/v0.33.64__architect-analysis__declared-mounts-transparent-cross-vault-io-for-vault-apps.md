## 0 · The answer in one paragraph

The goal stated by the project lead — *a vault app has no idea it is reading and writing files that
belong to another vault, with zero impact on today's `sg.vault.mount`* — is reachable **without**
P-279's shell unification, by adding one thing the platform lacks: **declared mounts**. The kernel
lane already gives an app *operation* transparency (once a mount exists, every `sg.vfs.*` under the
prefix relays invisibly through broker → gate → child kernel → push), but not *provenance*
transparency: the app must call `sg.vault.mount(prefix, ref)` itself, so it knows. The composite
lane gives provenance transparency (`<name>.link.json`, the app calls nothing) but only for reads,
and its write path is a silent-corruption bug. **Fuse the two halves that already work: let the top
kernel read the vault's existing link records at boot and register each as an ordinary
`KernelParent.mount()` before the app iframe exists.** Same mount table, same custody gate, same
tier gate, same relay, same child kernel — one more *caller* of `mount()`, not a new path. The app
then writes `/data/report.json` and never learns that `data/` is another vault.

Four corrections to the brief follow, one of which changes its build order.

## 1 · Verified: the brief's central finding holds, and it is worse than stated

The brief says the composite lane's read-only behaviour is an accident of path resolution with an
untested silent-corruption case. **Confirmed by execution** (stub root data source with a real folder
`acme/` *and* `acme.link.json`; composite mounted; `saveFile('/acme','report.md')`):

```
tree.children.acme._subvault     = undefined   ← the REAL folder overwrote the mount node in the tree
_mountForPath('acme/report.md')  = true        ← yet the adapter still believes the path is a mount
saveFile into mount              → NO ERROR
bytes landed in ROOT vault       = [{"folder":"/acme","name":"report.md","n":16}]
```

Three things the brief did not say:

1. **The tree lies too.** `_spliceNode` processes `files` (link → mount node) *before* `children`
   (real folders), so a real folder of the same name **replaces the mount node in the rendered
   tree** while `_mountForPath` still reports the path as mounted. The user browses the parent's
   folder believing it is the child.
2. **It is reachable from a vault app, not only from the tree.** `app-shell` swaps the bridge's data
   source for a `CompositeDataSource` whenever any `.link.json` exists (`dataSource = composite`,
   app-shell ~3378). A `.link.json` mount is **not** a kernel mount, so `_mounts.resolve()` misses,
   the write falls to the parent's `fs.write` grant and then to `composite.saveFile` → root. So the
   brief's "two lanes share no code" is only true of *writes*: for reads/lists the app lane already
   has **three** paths (kernel relay → composite splice → root), and the composite's blind write
   pass-through sits under the app lane as its fallback.
3. **The existing composite suite attempts zero writes** (grep: 0 `saveFile/deleteFile/renameFile`),
   confirming the brief.

**Fix regardless of anything else:** an explicit refusal in `CompositeDataSource` for any mutation
whose path resolves to a mount (`EMOUNT_RO`), a tree splice that refuses to let a real folder shadow
a mount (surface `_conflict`, never overwrite), and the two tests. Small, isolated, needed by both
lanes.

## 2 · Correction 1: the embedded-token hypothesis is wrong at the vault tier

The brief's step 3 proposes that a child kernel reading its own `.vault/access-token.json` would let
a parent holding only the child's **read key** obtain a **writable** child, dissolving decision D1
(a writable key at rest in the parent). It asks for two properties to be confirmed. Checked in code:

| Property | Result |
|---|---|
| Can a read-key-opened child decrypt `.vault/access-token.json`? | **Yes.** It is `read_key`-encrypted; `openReadOnly` imports `read_key` decrypt-only. |
| Does that token authorise writes on the child's connection? | **No.** Every vault write carries **two** credentials: the account-tier access token (`x-sgraph-access-token`) *and* the vault-tier write key (`x-sgraph-vault-write-key`, `sg-send.js:151/208/244`), and `Service__Vault__Pointer.write` refuses unless `SHA-256(write_key)` matches the vault manifest (`:65-87`). `openReadOnly` sets `_writeKey = null`; `vault.writable` is `!!_writeKey`. |

The embedded token only upgrades the **account** tier. The **vault** tier still needs `write_key`,
which is *by design* not derivable from `read_key` (independent PBKDF2 salts — the exact property
the read-key feature shipped this fortnight rests on). So a read-key mount can never be writable,
and **D1 stands**: a writable child needs the child's write key held somewhere on the parent side.

Porting the embedded-token read into the child kernel is still worth doing — it is what makes a
*full-key* child writable without the parent forwarding its own account token — but it does not
remove the decision.

## 3 · Correction 2: D1 was decided in practice on 8 June, and the brief did not notice

The 31 May scoping calls D1 "storing a writable key at rest in the parent as `rw-links.json`" and
marks it blocking. But **the owner-secret store shipped on 8 June already does exactly that**:
`sg.vault.create` seals each child's *full* key at `.vault/owner/secrets/<ref_id>`, encrypted under
a key derived from the **parent's write key** (`SGVaultOwnerSecrets`, `_ownerSecretPut`,
app-shell ~1622–1760). Read-only parent sessions cannot decrypt it; it lives beneath the `.vault/**`
floor so no app can reach it; `sg.vault.getKey(ref)` and `sg.vault.openApp(ref)` resolve child keys
from it today. That is `rw-links.json` under another name, with the "owner-only double-encryption"
the scoping asked for, and AppSec has been living with it for three months.

So the credential store for read-write declared mounts **is not a decision, it is a lookup**:
resolve `ref_id` against the owner-secret store (rw, custody `parent-held`), else against
`ro-links.json` (ro), else unmounted. Meanwhile the kernel lane's *actual* production resolver is a
trial stub that reads a **plaintext** `clinic.json` from the vault tree (`_resolveChildCredentials`),
and nothing ever injects `_resolveChildCredentialsImpl` in production. That stub is the weakest
link in the whole lane and should be replaced by the lookup above in the same change.

## 4 · Correction 3: two of the four "unspecified" properties are specified — by code

| Property | Brief | Code |
|---|---|---|
| Which branch a relayed write commits to | unspecified | The child kernel opens with `SGVault.open` → commits on the child's **`web-ui` clone ref**; `_safePush` pushes to the child's **named** ref, CAS-guarded. Specified, undocumented. |
| Mount cycles | "nothing terminates them" | **Cannot form today**: only an *app* can call `mount`, and child kernels run no app. They become possible only if child kernels also auto-mount — so the rule below (declared mounts are top-kernel-only) is what keeps this true. |
| Provenance in the child's history | none | Confirmed none. |
| One child mounted by two parents | never discussed | **A real hazard, and sharper than the brief says:** both parents' child kernels open with the same key and therefore derive the **same** `web-ui` clone ref (`deriveBranchRefFileId(hmac, vaultId, 'web-ui')`). Two headless kernels then share one clone branch; the CAS makes the loser fail closed, but a headless child that lands *diverged* has no shell to surface it and silently stops fast-forwarding. |

## 5 · The design: declared mounts

### 5.1 One declaration, two consumers

Do **not** invent a new manifest field. The vault owner already declares "this path is another
vault" with `<name>.link.json` (a dumb pointer, no secret) plus an owner record. Keep that as the
single declaration and give it a second consumer: the top kernel at boot. The tree view keeps
rendering it (composite, read-only, now with an honest refusal); the app kernel *mounts* it.
This is what the scoping's D6 demands anyway ("existing `.link.json` + `ro-links.json` must keep
working; rw purely additive").

### 5.2 Credential resolution (replaces the `clinic.json` stub)

```
resolveDeclared(ref_id):
  1. owner-secret store   .vault/owner/secrets/<ref_id>  (parent write-key tier)  → full key  → rw, custody 'parent-held'
  2. ro-links record      .vault/owner/ro-links.json     (parent read-key tier)   → read cred → ro, custody 'parent-held'
  3. localStorage child key ('save on this device')                              → per record → custody 'user-entered'
  4. none                                                                         → declared-but-locked (ENOENT under the prefix)
```

Step 2 needs the child kernel to accept a read credential: `kernel-bootstrap`'s `vaultFactory`
calls `SGVault.open` only. Add the one branch built this fortnight —
`SGVaultCrypto.parseReadOnlyCredential` → `SGVault.openReadOnly` — and port the shells'
`_readEmbeddedAccessToken` into the child for the account tier (§2). Both are small.

### 5.3 Where it happens

In `app-shell._mountAppFlow`, **before** `_mountApp` builds the app iframe:
`await this._mountDeclaredVaults()` → for each link mount →
`this._ensureKernelParent().mount({ prefix, ref, label, meta: { declared: true, linkPath, access } })`.
Nothing in `KernelParent.mount` changes: the B10 custody gate still runs (parent-held creds are
allowed because app frames are null-origin by default and refused if an app is granted
`allow-same-origin`), the channel is spawned the same way, the mount table is the same table.

**Spawn lazily, register eagerly.** Boot must not pay one child-kernel bring-up per link (the
scoping's D3). Register the mount entry at boot with a channel *promise*; `relay()` awaits it on
first use. Transparency is preserved (the path resolves from the first millisecond) and an app that
never touches a mount never pays for it.

### 5.4 Why this has zero impact on `sg.vault.mount`

| | Runtime mount (today) | Declared mount (proposed) |
|---|---|---|
| Caller | the app, via the bridge | the top kernel, at boot |
| Grant required | `permissions.vault.mount` | none — the **owner** declared it, the app is not asking for anything |
| `KernelParent.mount()` | unchanged | unchanged |
| Custody gate, tier gate, broker, relay, child kernel, `_safePush` | unchanged | identical objects |
| `sg.vault.mounts()` | lists it | lists it, with `declared: true` |
| `sg.vault.unmount()` | allowed | **refused (EPERM)** — see §6 |

Because `_mounts.resolve()` is consulted **first** in every bridge handler (write/read/list/download,
app-shell ~3516/3550/3600/4237), a declared mount shadows the composite for the same prefix in the
safe direction: kernel path wins, composite becomes the read-only fallback for links that could not
be mounted. No runtime-mount behaviour changes because no runtime-mount code changes.

### 5.5 What the app sees

`sg.vfs.write('/data/report.json')` → floor check → `_mounts.resolve('data/report.json')` hits →
`relay('write')` → tier `standing` (fine for write) → broker → child channel → child's own floor,
grant and writability checks → `addFile`/`updateFile` → `_safePush` → the **child's** server
connection. The reply is `{ size, mounted: true }` — the only trace, and only if the app looks.
`sg.vfs.list('/')` shows `data/` as a folder because the composite splice already renders the link
as one; `list('/data')` relays.

## 6 · Three rules the design needs that nothing states today

1. **Declared mounts are top-kernel-only.** A child kernel never auto-mounts its own links. This is
   what keeps cycles impossible (§4) and matches the non-transitive-reach invariant already pinned
   (`kernel relay — non-transitive reach (T4)`).
2. **An app cannot unmount a declared mount.** Otherwise an app could `unmount('data')` and its
   next `write('/data/x')` would land in the parent — a trivial route to the §1 corruption with the
   guard bypassed. `sg.vault.unmount` returns `EPERM` for `meta.declared`.
3. **Per-kernel clone branch for headless children** (or an explicit "single writer" declaration).
   Two parents mounting one child share a clone ref today (§4). Either derive the child kernel's
   clone branch from `kernelId` or refuse the second mount; both are decisions, neither is free.

## 7 · Provenance: put it in the commit, but not the parent's identity

The brief is right that a collector cannot be audited from an in-memory log in the *other* vault.
The child kernel already writes the commit; give relayed writes a commit message trailer. But do
**not** put the parent's `vault_id` in it — the brief itself names that disclosure as a tension. Use
the owner-chosen **mount label** (`meta.label`) plus `declared|runtime`: `Via-Mount: reports
(declared)`. The child's history then says *which door* a write came through, which is what an
audit needs, without naming the vault behind the door.

## 10 · What this does not decide

- Whether P-279 (tree view on the kernel path) is scheduled. This analysis makes it *optional* for
  the app-lane goal; it is still the right end state for the tree view.
- The commit-window setting per lane (brief §"Commits and batching"); orthogonal, agreed.
- §6.3 — the two-parents rule. Needs a decision; the analysis names the trade-off, not the answer.
- The popup-capability gate (P-280) — unchanged; a declared mount is a mounted sub-vault for its
  purposes, and the `meta.declared` flag is one more clean signal for the "is this an inner vault"
  test P-280 needs.

## Key claims (each checked in code at `0577c98d`)

1. The composite adapter's mutations are blind pass-throughs to the root (`composite-data-source.js:230-234`); a real folder at a mount path both replaces the mount in the tree and receives the write, silently — executed, not inferred.
2. The composite adapter is also the app bridge's fallback data source (`app-shell` ~3378), so the corruption case is reachable from a vault app.
3. Every vault write carries `x-sgraph-vault-write-key` and the server hash-checks it; a read-key session has `_writeKey = null`; therefore an embedded access token cannot make a read-key child writable.
4. The owner-secret store (`.vault/owner/secrets/`, sealed under the parent's write-key tier) already holds child write keys at rest in the parent — D1 is decided in practice.
5. The kernel lane's only production credential resolver is the plaintext `clinic.json` trial stub.
6. Relayed writes commit on the child's `web-ui` clone ref and push to its named ref; child kernels never auto-mount, so cycles cannot form today.
7. Two parents mounting one child share a single derived clone ref.
8. Declared mounts need no change to `KernelParent.mount`, the gates, the relay or the child kernel — they add a boot-time caller.
