## 0. Executive summary

The CLI team shipped four releases in four days and documented the contract they need from us in their repo (`team/humans/dinis_cruz/claude-code-web/10/07/*` and `10/08/*`). The headline: **the sgit.ai site now states publicly that the web UI cannot sign, cannot write 128-bit ids, overwrites the branch index and pushes blind.** All four statements are correct against our `v0.2.3` code. None of them is a bug in our code; they are the four places where the CLI moved first and we have not followed.

Good news, verified rather than assumed:

- **No library is needed.** ECDSA P-256 / SHA-256 with raw `r‖s`, the RFC 8785 canonical commit bytes, the HMAC-derived deterministic tree IV and the 32-hex object id all reproduce byte-for-byte with Web Crypto alone (15/15 vector checks pass in Node, which has the same `crypto.subtle` as the browser).
- **The server needs nothing.** `write-if-match` already answers the shape the CLI depends on (HTTP 200 + `results[i].status == "conflict"` + `current`), 44-character `file_id`s are accepted (the CLI proved it on the live dev Lambda; our route takes `file_id:path` untyped), and `list` is id-agnostic.
- **The CLI already tolerates us.** Everything the CLI writes today parses in our `loadCommit` / `loadTree` / `readBranchIndex`; the only thing we cannot *read* is a 32-hex id, and only because `computeObjectId` would recompute a 12-hex id when verifying, which we do not do.

The work splits into five items. The first two are small and unblock the rest; the third is the one the user asked about (signed commits) and is medium-sized; the last two are policy and should follow, not lead.

| # | Item | Size | Unblocks |
|---|---|---|---|
| 1 | **Read and honour the format gate; format-aware `computeObjectId`** | S (½ day) | raised vaults stay readable *and writable* by the web; `min_client` refusal by name |
| 2 | **Branch index as a shared document** (read → merge → CAS write, never a single-entry overwrite; keep `tags`, gate, unknown fields) | S–M (1 day) | gate and `signatures-required` stop being erased by every web push; keys and tags survive; the CLI stops "repairing" after us |
| 3 | **Per-device signing key + canonical signed commits + verification** | M (3–4 days) | web commits verify in `sgit check verify`; web can work under `signatures-required`; web can show verified / unsigned / bad in the SGit view |
| 4 | **Ref monotonicity + compare-and-swap push in the shells** | S–M (1–2 days) | the CLI stops reporting web saves as rewinds; two browsers can no longer drop each other's commits |
| 5 | **Deterministic tree encryption parity** | S, but a decision first | identical folder content gives identical tree ids in both clients (dedupe); CLI asked us to choose the plaintext rule |

Items 1 and 2 should ship together and first. Item 3 is the feature. Item 4 is required before any vault we write to is raised with `signatures-required` *and* rewind detection is meaningful. Item 5 waits for one decision (§6).

## 3. The contract, precisely (what the CLI will accept from us)

All of this is pinned by `tests/_fixtures/interop_vectors.json` in the CLI repo; this repo now carries a copy and a test that reproduces every value with Web Crypto.

### 3.1 Object ids
`hex = sha256(ciphertext)`; format 1 → `obj-cas-imm-` + `hex[:12]`; format 2 → `obj-cas-imm-` + `hex[:32]`. Vector: `sha256(b'sgit test vector 0001') = 1abfd21f1430…` → `obj-cas-imm-1abfd21f1430` / `obj-cas-imm-1abfd21f14308c611fe591dc4d6de285`. The format comes from the branch index; a vault with no `format` field is format 1. `content_hash` (tree entry, dedupe) **stays 12 hex** in both formats.

### 3.2 Format gate
```
format     : integer   1 | 2            (absent → 1)
min_client : "MAJOR.MINOR.PATCH"        (absent → no minimum; unparseable → no minimum, log it, never refuse)
features   : ["ids-128", "signatures-required", "signed-since-<24 hex of the head when switched on>", …]
```
Comparison is on the three integers. Refusal wording, agreed with the CLI (ours substitutes product name and "reload"):
`this vault needs SG/Vault >= 0.21.0 and this is 0.2.3: reload, then try again`.
**Decision needed:** what version string the web compares. `min_client` values are CLI versions (`0.21.0`); the web's own version is `v0.2.3`. Comparing a web version against a CLI floor is meaningless. Recommendation: the web treats `min_client` as *informational* and refuses only on things it actually cannot do: a `format` it does not know (> 2) or a feature it cannot satisfy for a **write** (`signatures-required` before item 3). Say so to the CLI team (the `min_client` field was designed for the CLI fleet; a `min_web` field could be added to `features` later if ever needed).

### 3.3 Branch index entries the CLI understands
```
{ branch_id: 'branch-(named|clone)-[0-9a-f]{8,64}', name, branch_type: 'named'|'clone',
  head_ref_id: 'ref-pid-(muw|snw)-…', public_key_id: 'key-rnd-imm-[0-9a-f]{8,64}', private_key_id: null,
  created_at: int ms | ISO string, creator_branch: branch_id | null, display_name }
```
`name` of the named branch MUST stay `current`. The CLI merges by `branch_id` (remote wins per field, local fills gaps), never loses an entry, keeps the **server's** gate unless the server copy has no gate fields at all, and carries `tags[]` entries it cannot read as exact JSON. We must at least: preserve every field we do not understand (`tags`, `format`, `min_client`, `features`, unknown keys) by merging into the **server's current JSON**, not rebuilding from scratch.

### 3.4 Signing key file
`bare/keys/key-rnd-imm-<16 hex>` = AES-GCM(read_key, `{"type":"public","pem":"-----BEGIN PUBLIC KEY-----…"}`) — SPKI PEM, P-256. Fingerprint (used by `sgit pki`, not by verification) = `sha256:` + `sha256(DER SPKI).hex[:16]`. Web Crypto exports SPKI DER directly (`exportKey('spki')`); PEM is base64 + headers.

### 3.5 Commit signing bytes
Stored JSON with **all ten** `commit_v1` members (`schema, tree_id, message_enc, branch_id, signature, author_key_id, author_signature, parents, timestamp_ms, attestations`), remove `signature`, sort keys by code point, no whitespace, UTF-8, non-ASCII unescaped. Sign SHA-256 / ECDSA P-256, encode raw `r‖s` (64 bytes) base64. `author_key_id` non-null marks the canonical form. Verified this session: `crypto.subtle.verify({name:'ECDSA', hash:'SHA-256'}, …)` accepts the CLI's vector signature, and a Web Crypto signature over the same bytes is 64 bytes and verifies under the vector public key.

Three consequences for our commit writer:

1. **`branch_id` must be CLI-conforming or `null`.** The CLI's `load_commit` rewrites a non-matching `branch_id` to `''` before re-serialising, which would change the signed bytes and make our signature **bad**, not merely unverifiable. Use `branch-clone-<16 hex>` per device (the CLI proposed exactly this on 10/07).
2. **`schema`.** The CLI's type accepts `commit_v2` (regex `^[a-z_]+_v\d+$`) and has read our `commit_v2` commits for months; the bytes include the string verbatim so either verifies. Recommendation: write **`commit_v1`** for signed commits. It *is* the same shape, our `loadCommit` already reads both, and it removes the one open naming question in the CLI's reply (§1 "Schema alignment").
3. **Integers only.** `timestamp_ms` must be an integer (`Date.now()` is). Never put a float in a commit.

### 3.6 Deterministic tree encryption
`IV = HMAC-SHA256(read_key, plaintext)[:12]`, `ciphertext = IV ‖ AES-256-GCM(read_key, IV, plaintext)` for the tree **and** each entry field. Vector reproduced (`obj-cas-imm-1b397bef28b6`). The plaintext rule today is Python's `json.dumps` default separators and the 7-field entry order `blob_id, tree_id, name_enc, size_enc, content_hash_enc, content_type_enc, large`. See §6 for the decision.

### 3.7 Rewind rule
`FORWARD` when the new head equals or descends from the last accepted head (or there is none); `REWOUND` when the new head is an ancestor of the last accepted head or a complete unrelated lineage; `UNKNOWN` when the walk hits its limit. Only a verified pull / merge / push moves the record.

## 4. The plan, in order

### Item 1 — format gate + format-aware ids (ship first, with item 2)

- `SGVault.open()` / `openReadOnly()`: keep the parsed index on the instance (already `_branchIndex`), expose `format` (default 1), `features`, `minClient`. Read the index in `openReadOnly` too (we already derive `branchIndexFileId` there and do not use it, `sg-vault-crypto.js:242`).
- `SGVaultObjectStore.computeObjectId(ciphertext)` → `'obj-cas-imm-' + hex.slice(0, this._idHexLen)` with `_idHexLen` = 12 or 32 set from the vault format at `_initManagers()` time and **re-set after any index refresh** (a vault can be raised while a tab is open; the CLI tells us `pull` refreshes the gate, we should do the same on every `_checkAndAutoSync` / reconcile).
- Refuse by name only for `format > 2` on open, and for `signatures-required` on **write** until item 3 (read stays allowed; the CLI's rule for `cat`/`ls` is the same).
- Tests: KAT for both id widths (added this session); open a fixture index with `format: 2` and check a stored object gets a 44-char id; unknown format refuses with the agreed wording.
- Regenerate the kernel bundle (`python3 scripts/build-kernel-shell-bundle.py`); `test__bundle_freshness.js` enforces it.

### Item 2 — branch index as a shared document

Replace `writeBranchIndex(idxId, refId)` with `upsertBranchIndex(idxId, ourEntry)`:

1. read `bare/indexes/<idx>` raw (keep the exact ciphertext for CAS; `readRef` already does this for refs via `_rememberRaw`);
2. parse; if absent, start from `{schema:'branch_index_v1', branches:[]}`;
3. ensure the named entry (`name:'current'`, `head_ref_id` = named ref) exists **without replacing** an existing one; upsert our clone entry by `branch_id` (item 3 adds `public_key_id`); touch nothing else — `format`, `min_client`, `features`, `tags`, unknown keys and other branches go back exactly as read;
4. `write-if-match` against the raw bytes read (plain `write` when absent); on `conflict`, take `current`, re-merge, retry up to 3 times, then give up **loudly** (the CLI raises; we should surface, not swallow with `catch (_) {}` as `push()` does now);
5. the write must leave the commit batch: today the index write is staged into the same `POST /batch` as objects and the ref (ordering rank 1). CAS needs a read first, and the server stops a batch at the first conflict, so a conflicting index op would abort the ref write that follows it. Do the index upsert as its own batch **after** the ref write succeeds (the CLI does the same: registration is a separate call).

Also stop writing the index on `create()` as a one-entry overwrite when a vault id collides (it cannot today, ids are random, but the code path is the same function).

Tests: index with 3 CLI branches + gate + tags → after our push it still has 3 + ours, the gate and the tags; conflict path retries and re-merges; the exact-bytes CAS uses the server's `current`.

### Item 3 — signing (the feature)

**Key custody.** One non-extractable P-256 `CryptoKey` pair per device per vault, generated with `crypto.subtle.generateKey({name:'ECDSA', namedCurve:'P-256'}, false, ['sign','verify'])` and stored as a `CryptoKey` object in IndexedDB (structured-clone of a non-extractable key is allowed; the private scalar never exists in JS). Keyed by `vault_id`. The public half is exported as SPKI, PEM-wrapped, encrypted under the read key and written to `bare/keys/key-rnd-imm-<16 random hex>` **on first push** (not on every commit), exactly where the CLI's `_register_pending_branch` writes it. The clone entry in the index gets `branch_id: 'branch-clone-<16 hex>'`, `branch_type:'clone'`, `head_ref_id: <our snw ref>`, `public_key_id`, `created_at`, `creator_branch: <named branch_id>`.

**Null-origin contexts.** Child kernels and embedded apps have no IndexedDB. Options: (a) the kernel commits unsigned (today's behaviour; fine until the vault requires signatures); (b) the parent shell holds the key and the kernel asks the parent to sign via the existing secure channel (`secure-channel.js`), which keeps one key per device and no key material in the sandbox. Recommend (b) as the design, (a) as the first ship. Read-only sessions never have a key.

**Commit writer** (`SGVaultCommit.createCommit`): build the ten-member object, `branch_id` = our clone branch id, `author_key_id` = our key id, `author_signature: null`, `attestations: []`, then `signature` = base64(raw r‖s) over JCS(object minus `signature`). JCS for our value types is: sort keys recursively, `JSON.stringify` each scalar, no whitespace (the test file carries a 6-line implementation that matches the vector). Unsigned fallback (no key, RO, null-origin) keeps `signature: null` and `author_key_id: null`.

**Verifier** (`SGVault.verifyCommit(id)` → `verified | bad | unsigned | no-key | missing`): key from `author_key_id`, else from the index's `branch_id → public_key_id`; fetch `bare/keys/<id>`, decrypt, import SPKI; verify over the canonical bytes; for `author_key_id == null` commits with a signature, also try the legacy bytes (Python default separators with `"signature": null` present) exactly as the CLI's `verify_commit_signature` does. Cache public keys per session.

**Where to use it.**
- SGit view: a status chip per commit (`verified` / `unsigned` / `no-key` / `bad`) replacing the raw signature dump; a per-vault summary like `fsck` prints. This is the visible deliverable.
- Sync: when `features` contains `signatures-required`, verify incoming commits after `signed-since-<anchor>` before merging (the CLI's `require_signatures`); refuse to **publish** an unsigned local commit with the CLI's wording so the user is not surprised when `sgit pull` refuses the vault.

**Tests.** KAT: sign the vector's stored commit with the vector private key, verify under the CLI's public key; verify the CLI's vector signature; a `branch_id` the CLI would rewrite is refused at write time; legacy bytes path; a commit with a changed `tree_id` reports `bad`. Live: `tests/integration/vault_ui/live/` already drives a real server; add "web commit → `sgit check verify` says verified" using the CLI in the venv (`team/explorer/dev/guides/03/14/python-3.12-venv-integration-testing.md` in the CLI repo describes the setup; the CLI's integration suite already runs against this repo's in-memory server).

### Item 4 — ref monotonicity + CAS push in the shells

- `SGVault` records `lastAcceptedNamedHead` per vault in `localStorage` (`sg-vault-last-head:<vault_id>`), moved only by a successful pull / merge / push. On every read of the named ref, classify with the §3.7 rule using the existing `_isAncestor` (wave BFS, all parents). `UNKNOWN` beyond the walk limit is not a refusal.
- Shells: replace the blind `push()` calls listed in §2 with `pushIfMatch()` + one reconcile-and-retry (the exact loop in `kernel-app-handlers.js:186-200`); keep `push()` only behind an explicit "force publish" affordance that the user clicks, which is our `push --force`. The three-way-merge auto-publish in `sg-vault--sync.js:218` must become CAS too.
- Rewind UX: the "Sync now" banner gains a third state: *"The published branch was rewound or rewritten (it pointed at X, now Y). If the owner force-pushed, accept; otherwise do not."* Accept = move the record and reload; nothing is written. Mirrors `sgit pull --accept-rewind` and uses the CLI's wording so a mixed team reads the same message in both tools.

### Item 5 — deterministic trees (after the decision in §6)

`SGVaultCommit.createTree` and `_encryptTreeEntry` switch to `encryptDeterministic` (HMAC-derived IV; a 10-line addition to `sg-send-crypto.js`); the entry gains `content_type_enc` (we have `file-type-detect.js`) and `large` (we already know when a blob went via presigned multipart); folder entries carry `size_enc` / `content_hash_enc` as `null` rather than omitted; plaintext serialised by whichever rule §6 decides. Blobs and commits keep random IVs. AppSec note: deterministic metadata encryption leaks equality of names and sizes across trees to the host (CLI threat model TM-R08 / KI-SEC-02); the CLI accepted that for dedupe, and we would be adopting the same accepted risk.

| Q1 44-char `file_id` on every surface | yes on write/read/batch/list/presigned; the route is `{file_id:path}`, the service is id-agnostic; they verified on dev; nothing to change |

| `list` continuation token | does not exist (`list_files` returns the whole prefix); when we add one the field will be `next_token` on the response and `?token=` on the request. Not scheduled; say so |
| `commit_v2` ↔ `commit_v1` | we will write `commit_v1` for signed commits; keep reading both |
| `branch_id` for web commits | `branch-clone-<16 hex>` per device, as they proposed |
| Tree plaintext rule | our preference in §6 |
| `min_client` for the web | the web does not compare a CLI floor against its own version (§3.2); it refuses on unknown `format` and on writes it cannot make policy-compliant |

## 6. Decisions needed

1. **Tree plaintext: match the CLI's Python bytes, or move both clients to JCS behind the gate?** Matching is cheaper for them (nothing changes) and costs us a 20-line serialiser that emits `", "` / `": "` and the CLI's field order. JCS is cleaner and what commits already use, but changes every tree id the CLI computes (a format bump). Recommendation: **match the CLI bytes now**; propose JCS-for-trees as the first format-3 item if the native-PKI design (their `10/09/design__native-pki-vault-mode.md`, `format: 3`) goes ahead, since that bump rewrites everything anyway.
2. **Key custody for sandboxed kernels:** parent-signs (recommended design) vs. unsigned-in-sandbox (first ship). See item 3.
3. **Should web verification be on by default** (chip in SGit view: yes; refusing to open or sync a vault over a bad signature: only under `signatures-required`, matching the CLI).
4. **Order of shipping:** 1+2 → 3 → 4 → 5 as above, or 4 before 3 if the immediate pain is CLI users seeing "REWOUND" after a browser save. Both are defensible; the sgit.ai page lists them in the order 1, 2, 3, 4.

## 7. What is further out (PROPOSED in the CLI repo, no action for us yet)

- **Writer-signed refs and index** (`10/09/design-analysis__read-write-keys-as-pki.md`): Ed25519 key derived from the passphrase along a third PBKDF2 path (`salt "sgit-sign:<vault_id>"`), signed `{commit_id, seq, ts, sig}` refs and a `writer_sig` on the index, sequence pinning per clone. Closes TM-R01 (any read-key holder + host can forge). Would need the same derivation and verification in the web, and Ed25519 in Web Crypto (available in current browsers). Phase 1 estimate on their side 1.5–2 weeks; ours would be similar.
- **Native PKI vault mode, `format: 3`** (`10/09/design__native-pki-vault-mode.md`): X25519 read pair + Ed25519 write pair, data key sealed to the read public key, write-only "deposit" capability, server-verified signed writes (that one is a server change for us: `Service__Vault__Pointer` would check an Ed25519 request signature instead of the bearer write key).
- **Sealed files** (`10/09/design__sealed-files-layer.md`): per-file envelope encryption to recipient P-256 keys over ECDH + HKDF + AES-GCM, opened in the browser with no WASM. Orthogonal to the above.
- **Things the CLI listed as "after 0.21"** that touch commit fields (stable change ids) are gated behind `min_client` because a new commit field breaks every 0.19+ verifier; the two safe fields are `attestations` and `author_signature`. We should never add a commit field either.

All of the above is **PROPOSED — does not exist yet**, on both sides.
