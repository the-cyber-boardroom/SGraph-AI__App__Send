### 1.2 Q1 — no sanctioned opt-out — CONFIRMED

There is no `data-*` attribute check, no class check, and no `e.defaultPrevented` check anywhere in the interceptor (`app-shell.js:2457-2473`) or in the pure-helper mirror `AppNavHelpers.shouldInterceptVaultHtmlHref` (`app-shell-nav-helpers.js:67-78`). The helper filters only on href string shape (`#`, `mailto:`, `javascript:`, `http://`, `https://`, `//`, extension). A capture-phase `window` listener in the app is currently the only way to keep an `.html`-href click.

### 1.3 Q2 — document-capture only; no window-level click listener — CONFIRMED

`grep window.addEventListener('click'|"click"` across the entire app-shell component directory returns **zero matches**. All other click listeners in the shell files are element- or shadow-root-scoped (e.g. `app-hud.js:119` shadow-root delegate; `app-hud.js:417,728` are `document`-level `{once:true}` popup-dismiss handlers that do not preventDefault navigation). The DOM event dispatch order (window-capture before document-capture, regardless of registration order) is spec behaviour, so the regulation-graph team's Attempt 4 (window-capture listener + `stopPropagation`) wins deterministically. **Attempt 4 is sound as claimed.**

The Attempt 3 root-cause (body-level bubble listener never fires because the shell's document-capture handler calls `preventDefault()` **and** `stopPropagation()` on `.html` hrefs) is confirmed at `app-shell.js:2470`.

### 1.4 Q3 — the `__sgVfsScrollToHash` flow — CONFIRMED, with one claim UNDERSTATED

Verified flow, matching the document's three-step description:

1. Bridge forwards the original href (fragment intact) — `app-shell.js:2471`.
2. Parent `_navigateToPath` (`app-shell.js:2119-2183`) delegates parsing to `AppNavHelpers.resolveNavigation` (`app-shell-nav-helpers.js:95-105`), which splits the fragment off via `splitHrefFragment` (`:52-57`); the file lookup runs on the fragment-free `resolved` (`app-shell.js:2150`); the srcdoc is swapped (`:2167-2168`); if a fragment was present the parent posts `{__sgVfsScrollToHash: fragment}` into the new frame on its `load` event (`app-shell.js:2173-2178`).
3. The injected listener (`app-shell.js:2479-2484`) applies on `DOMContentLoaded` (or immediately if past loading): `getElementById(frag)` → `scrollIntoView()`, **else `location.hash = "#" + frag`** — the fallback assignment is at `app-shell.js:2482`, exactly as the document quotes.

**The claimed live bug is real.** The fallback at `:2482` fires precisely when the anchor target does not exist yet (content rendered after load — the norm for data-driven apps), and in a null-origin srcdoc frame a `location.hash` assignment is not a safe fragment update (see 1.5). The shell's own miss-recovery path is the re-navigation vector.

**Query-string claim — UNDERSTATED; reality is worse.** The document says the interceptor forwards `?query` but "no parent-side code delivers the query to the new doc — treat `?query` as unsupported." Verified, and then some:

- `splitHrefFragment` splits on `#` only (`app-shell-nav-helpers.js:52-57`). A href like `page.html?node=42` produces `pathPart = "page.html?node=42"`.
- `resolveNavigation` returns that query-carrying string as `resolved` (`:100-104`).
- `_findEntry` (`app-shell.js:3435-3440`) matches on exact path or `endsWith('/' + norm)` — `"page.html?node=42"` matches **no vault file**.
- Result: `nav not found` → broken-link overlay (`app-shell.js:2151-2156`).

So a `?query` href does not merely lose its query — **it breaks navigation entirely** and lands the user on the host's "Page not found" overlay. Note the asymmetry: the bridge and `shouldInterceptVaultHtmlHref` deliberately strip `?query` for the *intercept decision* (pinned by tests HI2/HI3 in `tests/unit/vault_ui/loader/test__app_shell_nav_helpers.js:72-75`), but the *resolution path* never strips it. This is a latent bug in v0.2.3 independent of the HUD-addressing proposal.

### 1.5 Q4 — srcdoc semantics: bare-`#` clicks and `location.hash` — CONFIRMED

Code-level facts confirmed:

- App frames are `srcdoc` iframes (`app-shell.js:2166-2168`, comment cites the Phase 3 flip in ee6f4995) with sandbox `allow-scripts allow-forms` — **no `allow-same-origin`** — so they are null-origin (`app-shell.js:2295-2299`; pinned by `test__app_shell_bridge_build.js:61-62`).
- The interceptor exempts bare-`#` hrefs without `preventDefault` (`app-shell.js:2460`), so the browser default runs.

Spec-level reasoning confirmed: a srcdoc document's URL is `about:srcdoc` but its **fallback base URL is inherited from the container document** (HTML spec, "fallback base URL"). A clicked `<a href="#x">` therefore resolves against `https://…/en-gb/app/` → `https://…/en-gb/app/#x`, which is not same-document with `about:srcdoc` → real cross-document navigation of the iframe to the host app entry page → vault-key screen. **The Attempt 1 root-cause analysis is correct and spec-solid.**

For `location.hash` assignment (Attempt 2 and the shell's own fallback at `:2482`): the setter navigates via the Location-object navigate algorithm. Whether a given engine treats `about:srcdoc` → `about:srcdoc#x` as same-document is murky (Chromium restricts navigations to `about:srcdoc` URLs), and two independent app teams have now observed it re-navigating the frame to the host page. From an architecture standpoint the precise engine behaviour is moot: **`location.hash` in a null-origin srcdoc frame is at best engine-dependent and at worst a frame reload — it must be treated as banned**, and the shell must not use it itself. Verdict "fragment navigation banned app-wide" — confirmed as the right doctrine.

**AUTHORING.md is worse than the document claims.** The response says AUTHORING.md's "just use anchor tags" is "only true for `.html` and `page.html#frag` links." In fact `library/guides/vault-html/AUTHORING.md:345-346` affirmatively documents the broken behaviour as working:

> "**Pure-fragment links** (`<a href="#section">`) are passed through — the browser scrolls within the current page without the host being involved."

That sentence is **factually wrong** for srcdoc app frames — the browser does not scroll within the current page; it navigates the frame away. This is a documentation bug to fix regardless of which code proposals land (see §4).

### 1.6 Q5 — HUD addressing granularity — CONFIRMED with a nuance

History entries do carry fragments: `_navigateToPath` pushes `match.path + '#' + fragment` (`app-shell.js:2169-2170`), and the HUD mirrors that path in the address row and recent list (`app-hud.js:21-24, 598-609, 645-655`; the address bar is editable, `app-hud.js:134` / AUTHORING.md:360-364). So the HUD *can* distinguish `page.html#a` from `page.html#b` — **but only for navigations that went through `.html#frag` links**. An app whose articles are client-side state within one page (the regulation-graph case) gets exactly one history entry; and `?query` granularity does not exist anywhere (and currently breaks nav, per 1.4). The document's "cannot distinguish two articles" claim is correct for the reporting app's architecture.

### 1.7 Test-coverage baseline (for contract-impact assessment)

- `tests/unit/vault_ui/loader/test__app_shell_bridge_build.js` — asserts the bridge builds without throwing, exposes `window.sg`, and pins the external-link Option C/D flip (`__sgOpenExternal` vs `window.open`) and the sandbox tokens. **It does not pin the click-interceptor's exemption list, the `__sgVfsScrollToHash` listener, or the `location.hash` fallback.**
- `tests/unit/vault_ui/loader/test__app_shell_nav_helpers.js` — pins `shouldInterceptVaultHtmlHref` (including HI2/HI3: `?query` hrefs ARE intercepted) and `resolveNavigation` fragment/path-doubling rules. **No test asserts what `resolveNavigation` does with `?query` in the pathPart** — the current breakage in 1.4 is unpinned behaviour.
- `tests/integration/vault_ui/browser/` — `test__app_mode_deep_link.py`, `test__embed_handshake.py`, etc. contain **no coverage** of the click interceptor, scroll-to-hash, or bare-`#` behaviour (grep: zero hits for scroll/hash/NavReq/click).

Consequence: all five proposals below are unconstrained by existing tests except where noted; equally, none of this behaviour is regression-pinned today, so every adopted change must ship with new pins.

### 2.1 Proposal 1 — opt-out + defaultPrevented — ADOPT NOW

`if (e.defaultPrevented || a.hasAttribute("data-sg-native")) return;` as the first line after the `closest("a")` guard is correct and minimal.

- The `defaultPrevented` check formalises exactly the Attempt-4 pattern: only a **window-capture** handler runs before document-capture, so an app that intercepts there and calls `preventDefault()` gets a guaranteed pass-through even without `stopPropagation()`. App handlers at target/bubble phase run *after* the shell's document-capture handler and are not helped by this check — AUTHORING.md must say so explicitly (window-capture or `data-sg-native`, not "any preventDefault").
- `data-sg-native` is the better primitive for markup-driven apps: declarative, greppable, and testable in the pure helper if we later mirror it (`shouldInterceptVaultHtmlHref` is string-only today; the attribute check belongs in the bridge/DOM layer — acceptable divergence, but document it in the helper's header comment, which already acknowledges the bridge/helper copy at `app-shell-nav-helpers.js:9-13`).
- Apply the same two-guard bypass to the **external-link branch** as well, not just the `.html` branch — an app may legitimately want to own an `https://` anchor click (e.g. to render an in-app preview). The proposal as written only rescues `.html` hrefs.
- Ship with: a bridge-build regex pin (`data-sg-native` and `defaultPrevented` present in the built string), AUTHORING.md section, changelog entry classifying "no test should break".

### 2.2 Proposal 2 — claim bare-`#` clicks — ADOPT NOW, MODIFIED

Correct: the browser default for bare-`#` in a null-origin srcdoc frame is a cross-document navigation to the host entry page (1.5) — the exemption at `app-shell.js:2460` currently hands the click to guaranteed breakage. Claiming it with `preventDefault()` + `getElementById(h.slice(1))` + `scrollIntoView()` converts a footgun into the behaviour every author already expects.

Modifications:

- **`preventDefault` only — no `stopPropagation`** (the proposal's snippet already omits it; keep it that way) so app-level handlers still observe the event and can override the scroll.
- **Honour proposal 1's guards first** (`defaultPrevented` / `data-sg-native`) so an app that owns its `#` anchors (custom smooth-scroll, router) opts out cleanly.
- **`preventDefault` even on a miss.** If `getElementById` finds nothing, still swallow the click — falling through to the browser default is the vault-key-screen bug. A miss should be a no-op (optionally a console.warn).
- **Handle `href="#"` (empty fragment)** — common as a button-anchor idiom; must become a no-op, not a navigation.
- Do not push HUD history for in-page scrolls in this change — that belongs to proposal 5's design.
- AUTHORING.md:345-346 must be rewritten in the same commit (see §4).

### 2.3 Proposal 3 — remove the `location.hash` fallback — ADOPT NOW

The fallback at `app-shell.js:2482` is the shell using, on its own behalf, the exact primitive that is banned app-wide (1.5). It fires precisely in the common case (anchor target rendered after load) and can re-navigate the frame. No test pins it; no app can rely on it (its observable behaviour is a misnavigation).

- **Step 1 (now): delete `location.hash="#"+frag;` from the injected listener.** A miss becomes a silent no-op. Strictly better; trivial diff.
- **Step 2 (modified follow-up): bounded retry.** The right long-term shape is: on miss, retry `getElementById` on a short schedule (e.g. `requestAnimationFrame` poll or `MutationObserver`, capped at ~2-3 s) and/or re-apply when the app signals ready. Note the response document's "retry after `sg-app-ready`" names an event that **does not exist in the v0.2.3 bridge** (no such signal is emitted — PROPOSED); the shell does have a ~2.5 s blank-app probe (`app-shell.js`, AUTHORING.md:350-359) but that is host-side. If proposal 4's `sg.app.onDeepLink` lands, the retry becomes unnecessary for well-behaved apps — the app receives the fragment and applies it when its content exists — so do step 1 now and fold step 2 into proposal 4's design rather than inventing a ready-event just for this.

### 2.4 Proposal 4 — document `__sgVfsScrollToHash` / wrap as `sg.app.onDeepLink` — ADOPT MODIFIED

Do **not** document the raw `{__sgVfsScrollToHash}` postMessage as public API. It is a parent↔bridge wire detail; freezing it as a contract makes every future change to the message shape a breaking change, and apps listening for raw messages bypass the bridge's ordering guarantees (DOMContentLoaded gating at `app-shell.js:2483`).

Instead: the bridge (which already owns the listener) exposes `sg.app.onDeepLink(cb)`; on receipt of the internal message it calls `cb({ fragment })` — extended to `cb({ fragment, query })` when 5a lands. Default behaviour when no callback is registered stays as today's `getElementById`/`scrollIntoView` (post-proposal-3). If a callback is registered, the default scroll is suppressed — the app owns deep-link application. This is precisely the mechanism a data-driven app (regulation-graph) needs: it can defer applying the fragment until its content is rendered, which also retires the retry question in 2.3.

Contract impact: new `sg.app.*` surface — AUTHORING.md `window.sg` reference, reality doc, and a bridge-build pin. No existing test breaks.

### 2.5 Proposal 5 — query strings + HUD URL addressing — SPLIT

**5a — resolution bug fix + query delivery: adopt now.** Verified in 1.4: a `?query` href is intercepted (pinned by HI2/HI3) but then fails file lookup and lands on the broken-link overlay. This is an unshipped-feature *and* a live bug. Fix: add `splitHrefQuery` alongside `splitHrefFragment` in `AppNavHelpers`, resolve on the query-free path, carry `{resolved, query, fragment}` through `resolveNavigation`, and deliver the query into the new doc through the same channel as the fragment (the `__sgVfsScrollToHash` message generalised internally to a deep-link payload, surfaced only via `sg.app.query` / `onDeepLink`). New helper test cases are additive; RN1-RN9 are untouched. Changelog: "no existing test should break; new cases pin query handling."

**5b — HUD addressing (`sg.app.setQuery`, back/forward and recent-pages at `?node=` granularity): defer to a designed follow-up.** Endorsed as a direction — the response document's Q5 endorsement is architecturally sound (the HUD address bar is already editable and fragment-aware, `app-hud.js:598-609`; extending the entry format to `path?query#frag` is coherent). But it changes the history-entry format (`app-shell.js:2169`), the `app-nav:change` event payload, HUD dedup/display, and introduces the first *app→host* nav-state push (today nav state flows host→app only) — that reversal deserves its own architecture review covering: dedup semantics for rapid setQuery calls, history-length bounds, interaction with `alreadyResolved` entries, and whether `_findEntry` lookups must strip query on the history-replay path too (they must — history entries would now carry query). Do not fold this into the bug-fix batch.

## 3. Recommended implementation order

All are Explorer-track changes (behaviour changes in a shipped component; each needs a changelog entry under `team/comms/changelog/` classifying good vs bad test failures, plus reality-doc updates in the same commit).

1. **Proposal 3, step 1** — delete the `location.hash` fallback (`app-shell.js:2482`). Smallest diff, removes the shell's own live bug, unblocks nothing else.
2. **Proposal 1** — `defaultPrevented` + `data-sg-native` guards (both the `.html` branch and the external branch). Gives every downstream team a sanctioned opt-out and retires the window-capture workaround.
3. **Proposal 2** — claim bare-`#` clicks with in-frame scroll (with the 2.2 modifications). Removes the last default-broken anchor path.
4. **Proposal 5a** — query split in `AppNavHelpers` + fix the `_findEntry` miss + internal deep-link payload.
5. **Proposal 4** — `sg.app.onDeepLink(cb)` + `sg.app.query`, documented in AUTHORING.md's `window.sg` reference. (Depends on 5a's payload shape; supersedes any retry logic from 3 step 2.)
6. **Proposal 5b** — HUD state addressing: separate architecture review first.

Test additions per step: bridge-build regex pins for 1-3 (the built bridge string must contain the guards / the `#` branch / must NOT contain `location.hash`), helper unit cases for 5a, and one Playwright case in `tests/integration/vault_ui/browser/` covering: bare-`#` click stays in-frame; `.html#frag` scrolls; `data-sg-native` click reaches the app. Nothing in this area is browser-pinned today (1.7) — that gap is itself a finding.

## 4. AUTHORING.md guidance (to ship with steps 1-3)

Current text at `library/guides/vault-html/AUTHORING.md:311-364` ("Just use anchor tags…") needs three corrections:

1. **Delete/replace lines 345-346.** "Pure-fragment links are passed through — the browser scrolls within the current page" is factually wrong in a null-origin srcdoc frame: the href resolves against the inherited parent base URL, producing a cross-document navigation to the host app page (the vault-key screen). Until proposal 2 ships, the guidance must be: **"Do not use bare-`#` hrefs. For in-page anchors, `preventDefault()` in your own handler and call `element.scrollIntoView()`."** After proposal 2 ships: "Bare-`#` anchors are claimed by the host and scrolled in-frame; apps that want custom behaviour mark the anchor `data-sg-native` or preventDefault from a window-capture handler."
2. **Add an explicit `location.hash` ban.** New bullet: **"Never assign `location.hash` (or `location.href`) inside a vault app.** App frames are null-origin `srcdoc` documents; a hash assignment is a navigation, not a fragment update, and can reload the frame onto the host page. Keep in-app state in JS (and, once available, `sg.app.setQuery` — PROPOSED)."
3. **Document the opt-outs when proposal 1 ships:** `data-sg-native` on an anchor means "the host must not claim this click"; alternatively `preventDefault()` from a **window-capture** listener (document-/body-level bubble handlers run too late — the host intercepts at document-capture).

Also worth a line: `page.html?query` hrefs currently break navigation (1.4) — until 5a ships, AUTHORING.md should say "do not put `?query` on same-vault links."
