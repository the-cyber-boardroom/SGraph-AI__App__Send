## 1. Agent Authorization: Union of the Possible

### What Changed

The authorization model was previously framed as "what was granted". This brief reframes it as **the transitive closure of everything reachable from the grant**. This is not an additive change — it is a model correction. The blast radius and de-authorization machinery in the risk register graph must be recomputed over the closure, not over the stated permission.

### Architectural Impact

**Graph model revision required.** The `AuthorizationScope` entity (PROPOSED since June 22 mandate-graph brief) must become `AuthorizationClosure` — a computed subgraph, not a static list. The edges are:

```
Agent
  → hasClosure → AuthorizationClosure
  → hasNominalGrant → PermissionSet
  → hasDelta → PermissionSet   (unexpected = closure minus nominal)
  → hasCapabilityCertificate → CapabilityCertificate (if scoped)
```

**Closure computation is a graph traversal**, not a declaration. Every artifact within reach that grants further access (credential file, session cookie, token, reset-email link) is a node in the closure and must be edge-linked. The Architect must define:

1. The node types that are "permission-amplifying" artifacts (classified by type, not by name)
2. The traversal rule: what makes one node reachable from another in the authorization graph
3. The delta computation: `closure.minus(nominalGrant)` expressed as a graph query

**CapabilityCertificate** is the mechanism for bounding the closure. It must carry:
- A signed, named permission list (the grant)
- A block list (edges the agent is explicitly forbidden to traverse)
- A re-delegation flag (authorises or prohibits onward delegation)

### Key Concern: Re-delegation Consent

The two-gap model identifies a serious systemic hole: the original delegator never consented to re-delegation. This must enter the graph as an explicit edge. Any `MomentOfAuthorization` node must record whether re-delegation is permitted. Without this, the authorization graph is incomplete by construction.

### Open Architectural Questions

| Question | Notes |
|----------|-------|
| Closure computability vs completeness | The full transitive closure over a real enterprise is large. Define a practical approximation: depth-bound traversal, or type-based enumeration? |
| Credential/session node typing | How are credential files vs session cookies vs reset-email paths classified at the node type level? |
| Block list enforcement | At what layer is the capability certificate's block list enforced — graph query filter, runtime intercept, or both? |
| Re-delegation audit | When re-delegation occurs, who is notified? |

## 2. RAMM: Risk Acceptance Maturity Model

### What Changed

The corpus already has Node Type Formulas, ontologies-of-ontologies, risk appetite bands, and the acceptance lifecycle. The RAMM brief synthesises these into a **named, publishable standard** with five maturity levels expressed as testable graph predicates. This is architecturally significant because it:

1. Creates a new top-level entity class: `RAMMAssessment`
2. Formalises the acceptance node's required edges as a level-indexed predicate
3. Introduces the Agentic RAMM overlay as a typed extension of the base model

### RAMM Entity Model — Architectural Assessment

The ten entity classes map cleanly onto corpus concepts already built or PROPOSED:

| RAMM Entity | Corpus Status | Notes |
|------------|---------------|-------|
| RiskItem | EXISTS (risk node) | Standard corpus risk node |
| RiskAssessment | PROPOSED (scoring layer) | Needs OWASP Risk Rating mapping as method |
| RiskTreatmentDecision | PROPOSED | TAME options already named |
| RiskAcceptanceDecision | PROPOSED (acceptance node) | no-deny/accept-in-direction/for-interval already modelled |
| RiskOwner, DecisionAuthority | PROPOSED (underwriting chain) | Board propagation path already discussed |
| RiskAppetiteStatement, RiskToleranceThreshold | PROPOSED (appetite band) | Goldilocks zone brief (June 30) |
| CompensatingControl | PROPOSED | Standard control node |
| ReviewEvent, ExpiryEvent, ReassessmentTrigger | PROPOSED (interval mechanic) | Interval clock brief (June 30) |
| EvidenceArtifact | PROPOSED (grounding ladder) | Evidence→Measure→Twin→Reality chain |
| FrameworkReference | PROPOSED (bridge model) | Ontologies-of-ontologies brief |

The entity model requires no new invention — it is a formal assembly of what was already in the corpus.

### Five Maturity Levels — Graph Predicate Design

The levels must be implemented as graph queries. Level 3 ("Defined") is the practical target for an initial deployment:

```
Level 3 predicate:
  every RiskAcceptanceDecision node has:
    → ownedBy → RiskOwner          (required)
    → approvedBy → DecisionAuthority  (required)
    → expiresAt → ExpiryEvent       (required)
    → reviewedAt → ReviewEvent      (required)
    → justifiedBy → CompensatingControl  (required)
```

The query returns `true` if every acceptance node in the estate satisfies all five edges. This is directly implementable once the acceptance vault schema is defined.

### Agentic RAMM Overlay

Four new entity types required:

| Entity | Description |
|--------|-------------|
| `CapabilityCertificate` | Scoped, PKI-signed grant with block list (cross-links doc 1 above) |
| `AuthorizationClosure` | The computed subgraph of everything reachable (cross-links doc 1 above) |
| `MomentOfAuthorization` | Timestamped, signed record of the grant act |
| `AgentTwin` | Carries the agent's permissions, capabilities, and track record |

At Managed level, the delta (unexpected permissions) must be accepted explicitly. This creates a strong dependency on the CapabilityCertificate and AuthorizationClosure work from doc 1.

### Key Architectural Decision Needed

**Graph representation for RAMM:** The brief identifies four options (RDF/OWL, property graph, JSON-LD, dual-publish). Given the corpus already uses vault files as nodes and edges, the most consistent approach is **dual-publish**: a JSON-LD conceptual ontology (for external interoperability with OWASP/RIMS) plus vault-native path-pattern schema (for internal implementation). This avoids forking the implementation. Dinis should confirm.

## 3. Accountability Paradox of Gen AI

### Architectural Impact

This brief confirms and extends the existing direction: semantic knowledge graphs as the legibility layer for scaled accountability. It adds two architectural patterns that need formalisation:

**Pattern 1: Decision Scaffolding (not Decision Making)**
The LLM's role is to populate and connect the decision graph, not to traverse it and choose. Architecturally, this means the LLM writes nodes and edges; a deterministic graph query makes the acceptance decision. This pattern already exists implicitly in the corpus but needs to be stated explicitly in the architecture as a constraint.

**Pattern 2: Accountability-in-the-Loop Detection**
The brief identifies a failure mode: a human placed in the approval chain only as a blame target, not as a genuine decision-maker. The architecture needs a way to distinguish these. Suggested signal: if the approver lacks the `ownedBy` edge to the `RiskAcceptanceDecision`, they are accountability-in-the-loop, not an owner. The RAMM Level 3 predicate would fail on such an acceptance.

### No New Entities Required

This brief introduces no new entity types — it is a strategic framing that informs how existing entities are used.

## 4. Product Roadmap

### Architectural Assessment

The roadmap is architecturally disciplined: it builds everything on existing core, and the single engineering unlock (E1) is correctly identified as the vault-loader library extraction. The phase sequencing is sound from an architecture perspective.

**E1 dependency:** Every Phase 1 site is blocked by the vault-loader library. The roadmap is correct that this is the single piece of work that is "engineering on top of core rather than pure configuration." The vault-loader must be defined as a standalone library with a clear API before Phase 1 work begins on any site other than the already-shipped scenario MVP.

**Critical path:**
```
E1 (vault-loader library)
  → 1.1 Library mini-site
  → 1.2 Use-case mini-sites
  → 1.3 Dynamic scenario survey
  → 1.6 RAMM site
  → 2.1 Risk register vault graph
  → 2.3 Risk queue MVP
  → 2.4 Acceptance flow
  → 3.1 Demo app
  → 3.2 RAMM maturity queries
```

**Phase 2.1 dependency:** The risk register as a vault graph must be structured before 2.2 (graph viewer), 2.3 (risk queue), 2.4 (acceptance flow), and 2.5 (acceptance dashboard). The vault schema for risk nodes, acceptance nodes, and their edges must be defined first.

**Phase 4 pull-forward:** The roadmap correctly identifies billing and customer-owned deployment as commercial pull items. No architectural preparation is needed beyond what the S3-compatible vault container and on-demand metering already provide.
