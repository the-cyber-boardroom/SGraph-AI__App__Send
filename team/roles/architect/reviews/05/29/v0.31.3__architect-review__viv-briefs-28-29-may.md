## 1. Executive Assessment

The vault-in-vault (ViV) architect brief pack (version-2, v0.28.7) is the best-specified design brief the project has produced. The five-sentence design summary is normative and correct. The decision log (D1–D8) resolves every major architectural question cleanly. The implementation plan provides verified `file:line` targets and an adversarial test matrix. The pre-build architect review (v0.29.2) caught two real blocking defects before they were shipped.

**The core design is sound.** The "one primitive applied fractally" discipline is exactly the right constraint for a recursive cross-vault architecture — it prevents the natural drift toward ad-hoc cross-vault APIs. The broker placement (per-kernel, not global) is both the simplest and the most secure choice.

**The implementation is ahead of where I expected it to be.** Phases 1 + 2 + Phase 3 sub-step C prep are shipped in a single session. The 10 bugs fixed (including H1, the missing two-sided gate) are exactly the bugs a careful pre-build review would have predicted.

## 2. Design Evaluation

### 2.1 The Two-Edge Invariant

**Status: Correctly implemented.**

The design enforces two distinct edges:
- **Edge 1 (server edge):** Each kernel ↔ SG/API directly, with its own bearer token. The broker is NOT in the server path.
- **Edge 2 (inter-kernel edge):** Parent kernel → child kernel via SecureChannel (brokered, logged).

These must never be merged. The risk of merging would be: either a global network proxy (re-centralises the design, kills zero-knowledge) or a parent-as-relay (couples parent and child lifetimes, creates a single-point-of-failure). The per-kernel-direct-to-server model is correct.

**Concern:** The CORS code fix (`allow_credentials = False`) is shipped, but the operational verification (CDN cache invalidation + real-browser null-frame round-trip) is PROPOSED (P-257). Until P-257 is green, Edge 1 for nested kernels is unverified in production. **Phase 2 §7 browser end-to-end must not be claimed as done until P-257 is confirmed.**

### 2.2 Trust Direction (D2)

**Status: Correctly specified and implemented.**

Parent→child only. The child has no reference back (no port, no `window`). The v0.29.2 review defect B1 — imprecise directional rule — is resolved correctly: `request()` is restricted to initiators; `send()` works both ways (for events + replies). This is the right model. Upward reach (`window.parent`, `window.top`) is deliberately removed.

**The fractal recursion case** (grandchild C posting to ancestor A): correctly handled by the channel ID check in SecureChannel (M6 fix — checking `cid` after unpack). Without this fix, a forged message from C addressed to A's cid would have been accepted — a real security gap now closed.

### 2.3 The Null-Origin Origin Model (D3)

**Status: Conceptually correct; Phase 3 implementation PROPOSED.**

Only the top kernel has a real origin. Every nested frame is null-origin. This is browser-enforced once `allow-same-origin` is dropped from the 4 sandbox sites.

**Critical gap:** The sandbox sites still have `allow-same-origin` today (Phase 3 is PROPOSED as P-259). Until Phase 3 lands:
- App frames share origin with the kernel
- The same-origin bypass documented in `SECURITY-same-origin-app-bypass.md` is **still latent**
- The sg-app-stub.js (Phase 3C prep) is shipped but not yet injected into `_buildAppSrcdoc`

**The Phase 3 security gate should be the highest-priority next implementation step**, particularly if there is any plan to allow non-first-party vault app code. The trust assumption caveat must be explicitly documented (Phase 0 of the implementation plan).

### 2.4 PKI and SecureChannel

**Status: Implemented correctly; one deferred bug.**

The SecureChannel design (port-anchored, one `postMessage` at birth, everything on MessagePorts thereafter) is elegant and correct. The K1 one-use bootstrap key provides forward secrecy for secret delivery. The ECDSA signing + ECDH-AES-GCM encryption combination is appropriate for the threat model.

**Deferred bug L2:** `Envelope._canonicalParse` treats any `{__u8: "<string>"}` as bytes. A canonical JSON object shaped that way would round-trip incorrectly. The fix (add a tag byte: `{__u8b64: "..."}`) is small. Recommend scheduling before Phase 6 hardening.

### 2.5 Broker Architecture (D1)

**Status: Correctly implemented.**

Per-kernel broker is both the simple and secure choice — the parent provisions the child's key, and the broker (which knows that key) must be co-located with the provisioner. A global broker would be a centralised secret store.

`KernelBroker.mediate` returns an opaque `entryId`; `finalize(entryId, result)` closes the matching row regardless of concurrency (N3 resolved). The concurrent-safe design is correct.

**Gap (P-252):** The default policy for mutations is `ask`, but nothing wires the HUD prompt. Every test sets `autoAllow: true`. Until P-252 is implemented, the broker's `ask` policy is a dead prompt — the broker accepts but nothing surfaces the user-facing consent UI. This must be wired before any path where a user could be tricked into auto-allowing a cross-vault write.

### 2.6 Credential Model (D7)

**Status: Partially implemented.**

The per-request credential tier (standing-ro + perRequest-rw) is tested in the relay suite (T9 via `TestKernel._oneShotToken`) but is PROPOSED at the production level (P-254). The envelope passes a `credential` field through; the child kernel's policy adapter does not consume it; no issuance flow or token format exists.

**The current trial model** (`_resolveChildCredentials` reading `clinic.json` from the parent vault) is explicitly documented as a trial-only stub. **It must not be used with real PHI.** The coupling rule is clear: real PHI requires either child-generated keys (not yet designed) or Phase 3 complete (Phase 3 drops same-origin, so the parent can no longer exfiltrate the child's key). Until at least one of these is true, ViV is safe for synthetic data only.

## 4. What the Version-1 → Version-2 Evolution Shows

The version-1 briefing (`v0.27.79__architect-briefing__viv-isolated-kernel-spawn.md`) was a solid first attempt. The version-2 pack (`00–06`) is the result of one round of review and convergence. Two mechanisms changed:
- **B1:** The directional rule was imprecise ("initiator/responder" confused with `request()/send()`). Now precise.
- **B2:** Binary payloads were described as JSON-serialised. This would have silently zeroed all file-byte payloads. Now correct: `Uint8Array` in `payload` field, structured-clone for the wire.

Both are the kind of defect that would have been invisible in pure JSON tests but catastrophic for binary file reads/writes. The v0.29.2 pre-build review caught them before any code was written. **This is the model for how architect reviews should work.** The brief pack → pre-build review → implementation → post-build audit sequence worked as designed.
