## 1. Purpose

We need **evidence-driven optimisation**. Before touching the backend we need a way to:

1. Measure the current cost of every API path from the client's perspective.
2. Capture a baseline so we can prove any future change is a win, not a regression.
3. Run the same scenarios in production after each release as a QA smoke suite.
4. Do all of this **without polluting server storage** — no orphan transfers, no abandoned vaults.

This tool is a static page that talks only to the public API. It does not bundle any privileged credentials. It speaks the same `x-sgraph-access-token` header as every other client. Anything it creates server-side it tears down before reporting "done."

## 2. Scope (v0.1.0)

- A self-contained static page at `/dev/performance/v0/v0.1/v0.1.0/index.html`.
- A small set of test scenarios, runnable individually or as a batch.
- A timing engine that captures duration, bytes in/out, success/failure, and (where measurable) the inferred number of server-side S3 operations.
- A **client-side artefact tracker** in localStorage that records every transfer or vault the tool creates. Orphans (anything the cleanup step failed to remove) can be listed and purged on subsequent visits.
- A results table with copy-to-clipboard JSON export so runs can be diffed across releases.

Not in scope for v0.1.0: multi-region comparisons, automated regression detection, persistence of historic runs to S3, charts/graphs.

## 3. Why Static (No Build Step, No Framework)

The tool follows the IFD methodology already in use across the vault and admin pages:

- Vanilla JS + Web Components, zero framework dependencies.
- Versioned at `v0/v0.1/v0.1.0/` with surgical override at minor/patch levels (`library/guides/development/ifd/`).
- Uses `sg-layout` from the SG dev tools CDN to match the vault page's look.
- Reuses the existing `api-client.js` pattern for the `x-sgraph-access-token` header.

This means anyone with network access to `send.sgraph.ai` can open the URL and run a probe — no install, no auth beyond the access token the user already has.

## 4. The "No Side Effects" Contract

Every scenario falls into one of three classes:

| Class | Side effects | Examples |
|---|---|---|
| **Pure read** | None — server state unchanged | `GET /api/transfers/info/<nonexistent>`, `GET /api/openapi.json`, `GET /api/transfers/check-token/<name>` |
| **Round-trip with cleanup** | Creates a server-side artefact, then deletes it before the scenario completes | Transfer create→upload→complete→download→delete; Vault write→read→delete→destroy |
| **Metered consume** *(explicit user consent)* | Permanently consumes one or more uses from the access token's quota | `POST /api/transfers/validate-token/<name>` |

**A test scenario is only allowed to advertise itself as "no side effects" if, after a successful run, the server state matches the pre-run state.** Today there are two known exceptions; we accept and document them:

### 4.1 Transfer `delete` leaves the meta record

`DELETE /api/transfers/delete/{transfer_id}` removes the payload but updates `meta.json` to `status='deleted'` rather than purging it. The 1 KB metadata record stays. This is by design (prevents transfer-id reuse, supports audit) — but it means a clean run still leaves a tiny residue.

### 4.2 Vault `destroy` leaves a tombstone (`deleted.json`)

Confirmed in `sgraph_ai_app_send/lambda__user/service/Service__Vault__Pointer.py:225-226`:

```python
tombstone = dict(vault_id=vault_id, status='deleted', deleted_at=Timestamp_Now())
self.storage_fs.file__save(path__vault_tombstone(vault_id),
                           json.dumps(tombstone).encode())
```

The tombstone is intentional (prevents re-use of the same `vault_id` after destruction) but for performance testing it accumulates. Two recommended follow-ups, both small:

- **Option A (backend):** Add a `?purge=true` query flag to `DELETE /api/vault/destroy/{vault_id}` that omits the tombstone. Restrict to admin-token holders.
- **Option B (operational):** Use a dedicated `tokens=*` prefix for perf-test vault IDs so an offline sweep can identify and purge tombstones nightly.

Either option is out of scope for this tool's v0.1.0. The tool will surface the residue in the results.

## 5. Test Scenarios — Starter Catalogue

Each scenario records `duration_ms`, `bytes_sent`, `bytes_received`, `http_calls`, `inferred_s3_ops`, `success`, `error`. The S3-op count is derived from the mapping in `v0.27.34__storage-io-flows-and-optimisation.md`.

### A. Pure reads (zero state change)

| ID | Name | What it does | Why we care |
|---|---|---|---|
| `cheap.transfer-info-404` | Transfer info — unknown ID | `GET /api/transfers/info/zzzz-not-exists-zzzz` | Measures the cost of a single Memory-FS `exists` miss + Lambda overhead. Baseline for "cheapest possible gated path." |
| `cheap.vault-health-404` | Vault health — unknown ID | `GET /api/vault/health/zzzz-not-exists-zzzz` | Same primitive on the vault side. Used by warmup. |
| `cheap.openapi-json` | Fetch `/api/openapi.json` | Static JSON | Pure routing/serialisation cost. No storage hit. |
| `cheap.api-docs-html` | Fetch `/api/docs` | Static HTML | Sanity check the page even renders. |
| `token.check` | `GET /api/transfers/check-token/<token>` | Looks up token, returns `{valid,status,remaining}` | Measures cost of the inter-Lambda cache lookup. Does **not** consume a use. |

### B. Transfer round-trip (create + clean up)

| ID | Name | Payload size | Operations |
|---|---|---|---|
| `transfer.roundtrip.1kb` | Small transfer | 1 KB | create → upload → complete → info → download → delete |
| `transfer.roundtrip.100kb` | Medium transfer | 100 KB | same |
| `transfer.roundtrip.1mb` | Large transfer | 1 MB | same |

Each step is timed individually. Result also reports the *implied* S3-op cost from the storage-flows document so the user can compare measured wall-clock against theoretical minimum.

### C. Vault round-trip

| ID | Name | Payload | Operations |
|---|---|---|---|
| `vault.roundtrip.1kb` | Single-file vault | 1 KB | new vault_id → write → read → list → delete file → destroy vault |
| `vault.roundtrip.5files` | Multi-file vault | 5 × 10 KB | same with 5 writes, 5 reads, 5 deletes |
| `vault.roundtrip.20files` | Larger vault | 20 × 10 KB | same with 20 of each |

Tombstone caveat per §4.2 is shown in the result.

### D. Concurrency

| ID | Name | What |
|---|---|---|
| `concurrency.info-parallel-10` | 10× `GET /transfers/info` in parallel against one fixture | Measures Lambda concurrency scaling |
| `concurrency.info-parallel-100` | 100× same | Stress |
| `concurrency.vault-read-parallel-20` | 20× `GET /vault/read` on the same file | Tests how the read path scales (no caching today) |

The fixture is a single created-then-deleted-at-end transfer / vault file. Concurrent reads do not modify state, so cleanup is trivial.

### E. Lambda warmth probe

| ID | Name | What |
|---|---|---|
| `warmth.cold-after-30s` | Send one probe, wait 30 s, send another | Detects cold-start gap. Wait period configurable. |
| `warmth.burst-10` | 10 sequential probes back-to-back | Shows steady-state Lambda cost once warm. |

### F. Batch (vault)

| ID | Name | What |
|---|---|---|
| `batch.vault-read-10` | Write 10 files, batch-read all, cleanup | Measures `/api/vault/batch` read-only fan-out |
| `batch.vault-read-100` | 100 files | Stress test of the anonymous batch-read endpoint |

These are the most expensive scenarios per the storage-flows analysis (200 S3 ops for the 100-file variant).

### G. Optional — metered

| ID | Name | What |
|---|---|---|
| `metered.validate-token` | `POST /api/transfers/validate-token/<name>` | **Consumes 1 token use.** Requires an explicit confirmation checkbox. Useful for measuring the validate-token cost without confounding from other paths. |

## 6. Client-Side Artefact Tracker

Backed by `localStorage`. Keys:

| Key | Purpose | Format |
|---|---|---|
| `sg-perf:access-token` | The token the tool will send in `x-sgraph-access-token` | string |
| `sg-perf:artifacts:transfers` | Every transfer the tool has created | array of `{transfer_id, delete_auth, created_at, status, scenario_id}` |
| `sg-perf:artifacts:vaults` | Every vault the tool has created | array of `{vault_id, write_key, file_ids: [], created_at, status, scenario_id}` |
| `sg-perf:last-run` | Last results JSON | for diffing across sessions |
| `sg-perf:config` | User prefs (size choices, parallelism, etc.) | object |

**Lifecycle:**

1. Before a scenario calls `POST /transfers/create` it writes a record with `status='pending'`.
2. After the cleanup step succeeds it sets `status='cleaned'`.
3. On page load the tool scans both arrays and counts orphans (anything with `status` ≠ `cleaned`).
4. A "Clean Orphans" button iterates the orphans and calls the appropriate delete/destroy. Records that successfully clean are removed from the array. Records that fail (404 — already gone) are also pruned.

This satisfies the user's two motivations: **(a)** we will always be able to find and clean transfers/vaults left behind by a crashed run, and **(b)** we have a real list of artefact IDs that double as fixtures for testing the backend's various read paths.

## 7. Layout & UI Pattern

Follows the vault page's use of `sg-layout` for the panel structure. Three regions:

- **Top bar**: title, access-token input, "Save", "Clear", environment indicator.
- **Left panel** (scenarios): grouped tree of scenarios (A–G). Each has a "Run" button. Above the tree: "Run All Selected" and "Loop N times" controls.
- **Right panel** (results): table with one row per run, columns: timestamp, scenario, duration, http calls, status, error. A footer row shows aggregates.
- **Footer**: artefact-tracker summary ("3 transfers tracked, 0 orphans") + Clean Orphans button. Plus "Export Results" (copy JSON to clipboard).

All styling is local. No `<table>` is used for layout, just for results display.

## 8. What "Inferred S3 ops" Means

The tool does not have direct visibility into the Lambda's storage backend. We label each scenario with the expected `inferred_s3_ops` count from the storage-flows mapping. This gives a useful sanity check: if a scenario that should be 4 S3 ops is taking 200 ms, we know the cost is dominated by network/Lambda overhead and not by the storage backend. As we ship optimisations the inferred-cost column will update and we can compare measured ↔ inferred.

## 9. Reuse as a QA Suite

The same scenarios serve a second purpose: pre-release smoke testing. The QA team's start file (`team/comms/QA_START_HERE.md`) can be updated to instruct: "open `/dev/performance/` against the staging environment, run the full suite, paste the exported JSON into the QA brief." A failure on any scenario is a release blocker.

## 10. What's Deliberately Not Here

- **No backend changes.** This tool's whole point is to measure *before* we change anything.
- **No automated thresholds.** We need a baseline run first; thresholds come in a future minor version.
- **No history persistence to S3.** Results live in localStorage and clipboard for now.
- **No charts.** Numbers in a table beat pixels at this stage.
- **No CSS framework.** Same IFD rules as the rest of the project.

## 12. Surgical Versioning Plan

The pattern from `library/guides/development/ifd/`:

- `v0.1.0` — this initial drop. Complete files.
- `v0.1.1`, `v0.1.2` — surgical overrides. Only the changed file(s) appear. The patch references load v0.1.0 first, then the override file.
- `v0.2.0` — first consolidation. All v0.1.x patches are folded into complete files at this version.
- `v1.0.0` — release copy of the last v0.2.x snapshot, version strings updated.

When a scenario is added or modified, the change goes into a new patch under `v0/v0.1/v0.1.{n}/js/scenarios.js`. CSS tweaks go into a new `v0/v0.1/v0.1.{n}/css/perf.css`. The index.html in `v0.1.0` loads each surgical override after the base — for a fresh deploy, the deployed `index.html` lives at the latest patch version.

## 13. Followup Items After Baseline Capture

Once we have a baseline (a single full-suite run on production), the work order from the storage-flows document slots in:

1. Land the cheap wins (drop redundant hash lookup, etc.). Re-run the suite. Confirm token-related scenarios got cheaper.
2. Add the Lambda-lifetime token cache. Re-run. Confirm `complete` and `validate-token` got cheaper.
3. Stop rewriting `meta.json` on every download. Re-run the download-heavy scenarios.
4. Introduce the deferred event log. Wire vault writes/reads. Confirm hot-path cost did not go up.
5. Switch destroy to batch-delete. Re-run vault-multi-file scenarios.

Each iteration uses this tool's exported JSON as before/after evidence.

## 14. Risks & Open Questions

- **Token consumption from `transfer.roundtrip`.** Every transfer-roundtrip scenario consumes one token use (via the `complete` call), regardless of whether we then delete the transfer. The token's `usage_count` will increment. The tool surfaces this in the UI ("This run consumed N token uses") so an operator with a small quota does not exhaust their token by running the suite once. We could mitigate by issuing a "perf-test" token with a high quota and binding it to the tool's localStorage. Decision deferred.
- **CORS.** The tool is on the same origin as the API (`send.sgraph.ai`) when deployed, so no CORS headaches. If used cross-origin against a staging host the CORS allow-list already includes `x-sgraph-access-token`.
- **Lambda cold start contamination.** A scenario's first measurement may include a cold-start penalty. The tool always reports raw timings; consumers should look at the `warmth.*` scenarios to factor this out.
- **Browser network overhead.** Wall-clock includes DNS, TLS, and browser scheduling. For absolute Lambda timing, a second tool (curl-based, run from EC2) will eventually be useful. Out of scope here.
