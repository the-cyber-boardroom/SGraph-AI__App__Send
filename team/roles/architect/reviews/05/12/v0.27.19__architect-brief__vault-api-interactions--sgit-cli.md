# Architect Brief — Vault API Interactions & Call-Count Reduction

**Version:** v0.27.19 | **Date:** 12 May 2026
**From:** Architect (SGraph Send / Vault UI)
**To:** SGit CLI team (`SGit-AI__CLI`) — owners of the SG/Vault HTTP API and its canonical client semantics
**Scope:** Browser-side `sg-vault` client in SGraph Send + the SG/Vault server endpoints it consumes
**Status:** REVIEW REQUEST — please confirm the map below, then propose the reduction shape

---

## Why This Brief Exists

The Vault UI in SGraph Send (the browser-side `sg-vault` library) has grown a fairly complete set of vault operations: open, pull, push, commit, check, refresh, status, folder walk, blob read. Recently we added **auto-push on every `sg.vfs.write()` commit** (see "Recent change" below) which makes a SG/App in App Mode feel instant — but it also makes the per-keystroke-save API cost more visible.

Sitting on top of `sg-vault`, the SG/App author surface (`sg.git.*`, `sg.auth.*`, `sg.app.*`, `sg.ui.*`) is now stable enough (v0.27.19) that we want to step back and look at the round-trip count of "simple" operations like pull and commit before more SG/Apps start hammering them.

The feeling from the Vault UI side is that **we are still making too many calls to the SG/Vault APIs for operations that conceptually should be 1–2 round-trips**. We need your eye on this — the SGit CLI team owns the canonical client and the protocol shape, so optimisation decisions ultimately belong to you.

This brief gives you the SGraph Send–side map. We are asking for:

1. **Confirmation** that our map is correct (anything we missed? anything we duplicated?)
2. **A reduction proposal** for the worst offenders — ideally protocol-level (single endpoint that fuses two operations) so all clients benefit
3. **A "minimum number of HTTP requests" target** for each operation, so we know what good looks like

---

## Recent Change: Auto-Push on `sg.vfs.write()`

Until 12 May, an iframe write committed locally but the user had to click "Push" in the header to publish. Auto-push (`2ac1ec1`) eliminated that:

- After `saveFile()` resolves on the parent side, the bridge calls `_vault.push()` immediately
- Push failures are caught and logged as warnings — they do **not** fail the write reply to the iframe
- Source: `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.3/_common/js/components/send-download/send-browse--v0.3.2.js`

The behavioural intent: **we have yet to find a workflow where unpushed state actually helps the user**. We expect every commit to publish.

The cost: each `sg.vfs.write()` now does an extra ref write (the named ref) on top of the commit's clone-ref write. The commit-then-push pair is **two ref writes that always travel together** — a prime candidate for fusion at the protocol level.

Related surface added in the same wave (`220a5a3`, `6ec37ba`, `6790ae7`):

- `sg.git.{status, check, push, pull, refresh}` — author-facing
- ↻ "Check" button + visibility-change / vault-open auto-check (debounced 30s, no background polling)
- `sg.app.{vaultName, vaultId, fileCount, totalSize}` injected statically at iframe boot
- `sg.auth.{hasKey, setKey, check, clear}` — write-only key flow

The `sg.git.refresh()` known caveat: it tears down the calling iframe (full vault reload). `sg.git.pull()` is the iframe-state-preserving alternative.

## Current Vault Interaction Map (SGraph Send → SG/Vault)

The browser-side client is split across:

```
sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/_common/js/
  lib/sg-vault/sg-vault.js                  # entry point: open(), commit()
  lib/sg-vault/sg-vault--sync.js            # pull(), push(), merge(), divergence walk
  lib/sg-vault/sg-vault-ref-manager.js      # readRef(), writeRef()
  lib/sg-vault/sg-vault-object-store.js     # store(), load(), batchLoad(), loadLarge()
  lib/sg-vault/sg-vault--file-ops.js        # saveFile()
  lib/sg-vault/sg-vault--folder-ops.js      # loadSubTreeOnDemand()
  lib/sg-vault/sg-vault--branches.js
  components/vault-shell/vault-shell.js     # _checkBehindOnly(), _refreshSyncState(), _onRefresh()
  components/vault-header/vault-header.js
  adapters/vault-data-source.js
```

The endpoints (as the client sees them):

- `vaultRead(/bare/refs/ref-pid-muw-*)` — named ref pointer (one commit ID, encrypted)
- `vaultRead(/bare/refs/ref-pid-snw-*)` — clone ref pointer
- `vaultRead(/bare/indexes/{branchIndexFileId})` — branch index (optional)
- `vaultRead(/bare/data/obj-cas-imm-*)` — content-addressed objects (commits, trees, blobs, encrypted)
- `vaultReadLarge(/bare/data/obj-cas-imm-*)` — presigned-URL path for blobs > 4 MB
- `vaultBatch([objectIds])` — batched object fetch (50-object chunks)
- `vaultWrite(/bare/refs/...)` — ref pointer write
- `vaultWrite(/bare/data/obj-cas-imm-*)` — immutable object store

### Operation 1 — Vault Open / Initial Clone (`sg-vault.js:87–145`)

| # | Call | Notes |
|---|------|-------|
| 1a | `vaultRead /bare/indexes/{branchIndexFileId}` | Optional. 404-tolerant. |
| 1b | `vaultRead /bare/refs/ref-pid-muw-*` (named) | Required. Throws if missing. |
| 1c | `vaultRead /bare/refs/ref-pid-snw-*` (clone) | Optional. **Always 404 on first open.** Round-trip wasted. |
| 1d | `vaultRead /bare/data/obj-cas-imm-*` (HEAD commit) | Via object store. |
| 1e | `vaultRead /bare/data/obj-cas-imm-*` (root tree + non-lazy subtrees) | Recursive, lazy subtrees deferred. |

**Smell:** clone-ref read at 1c is structurally a 404 on first open. Could be elided by either creating the clone ref at vault-creation time, or by treating "no clone ref" as a derived state rather than a separate round-trip.

### Operation 2 — Pull (`vault--sync.js:118–135`)

| # | Call | Notes |
|---|------|-------|
| 2a | `vaultRead /bare/refs/ref-pid-muw-*` | Read named HEAD. |
| 2b | `vaultRead /bare/data/obj-cas-imm-*` (commit + tree) | Only if named HEAD moved; recursive. |
| 2c | `vaultWrite /bare/refs/ref-pid-snw-*` | Advance clone ref. |

**Smell:** the clone-ref write at 2c is unconditional once we've decided to pull. If we always pull-to-head, the clone-ref is just a mirror of the named ref — why does it exist as a separate object?

### Operation 3 — Check (lightweight ↻, `vault-shell.js:530–553`)

| # | Call | Notes |
|---|------|-------|
| 3a | `vaultRead /bare/refs/ref-pid-muw-*` | One cheap GET, no follow-on. |

If the ref pointer changed, the caller may immediately follow up with a full status refresh — see Operation 6. Within a debounced window the two reads are effectively duplicates of the same byte.

### Operation 4 — Commit + Auto-Push (single `sg.vfs.write()`)

Path: `send-browse.js` → bridge → `vaultShell._onTreeChanged()` → `_commit()` → `_vault.push()`.

| # | Call | Notes |
|---|------|-------|
| 4a | `vaultWrite /bare/data/obj-cas-imm-*` (blob) | 1 per file. |
| 4b | `vaultWrite /bare/data/obj-cas-imm-*` (tree) | 1 per modified tree level. |
| 4c | `vaultWrite /bare/data/obj-cas-imm-*` (commit) | 1. |
| 4d | `vaultWrite /bare/refs/ref-pid-snw-*` (clone ref) | Inside `_commit()` (`sg-vault.js:238`). |
| 4e | `vaultWrite /bare/refs/ref-pid-muw-*` (named ref) | Inside `_vault.push()` (`vault--sync.js:91`). |

**For a single-file save in a flat folder: 5 HTTP writes.**

**Top smell:** 4d and 4e are two ref writes that, post-auto-push, **always travel together**. They could be one server-side operation. Even a thin endpoint `POST /bare/refs/advance` that accepts `{ commit_id, advance_named: true, advance_clone: true }` would cut writes per save by 20%.

### Operation 5 — Refresh (`sg.git.refresh()` / `_onRefresh` `vault-shell.js:248–279`)

Re-runs Operation 1 from scratch (full re-open). If divergent, runs the merge / commit-DAG walk (`vault--sync.js:142–256`), which BFS-walks both parents using `batchLoad()` in 50-object waves. Worst case on a deep divergence: dozens of batches.

### Operation 6 — Status (`sg.git.status()` → `_refreshSyncState`)

| # | Call | Notes |
|---|------|-------|
| 6a | `vaultRead /bare/refs/ref-pid-muw-*` | Named HEAD. |
| 6b | `vaultRead /bare/refs/ref-pid-snw-*` | Clone HEAD. |
| 6c | `vaultBatch([commit ids])` × up to 4 waves | Only if diverged. |

**Smell:** 6a duplicates 3a if both fire inside the auto-check debounce window (e.g. ↻ click + immediate `sg.git.status()` from the iframe). No in-memory cache TTL on ref pointers.

### Operation 7 — Folder / File Browse Navigation

- Tree is fully loaded at open with lazy subtrees marked `_loaded: false`
- Expanding a folder triggers `loadSubTreeOnDemand()` → 1 `vaultRead /bare/data/obj-cas-imm-*` per subtree
- Opening a file blob → 1 `vaultRead` (or `vaultReadLarge` for > 4 MB)

No N+1 at the file level — blobs are only fetched on tab open, not on listing. Subtree expansion is 1-per-folder which is acceptable, but could benefit from a "fetch this subtree and its direct children" batched call for deep navigation.

### Operation 8 — Object Store

- Cache layer: browser Cache API, keyed by `https://sgvault/{vaultId}/bare/data/{objectId}` — hits skip the network entirely
- Batch reads: `vaultBatch()` in 50-object chunks (`sg-vault-object-store.js:122–156`)
- Result-cache populated after fetch

This layer looks healthy. The question is whether the 50-object chunk size is optimal — the SGit CLI team probably has real numbers.

## Identified Excess (Ranked)

| # | Issue | Where | Impact |
|---|-------|-------|--------|
| 1 | **Commit + auto-push = 2 ref writes that always travel together** | `sg-vault.js:238` + `vault--sync.js:91` | Every iframe write costs an extra round-trip post-auto-push. Highest frequency op. |
| 2 | Clone-ref read at open is structurally a 404 on first open | `sg-vault.js:139` | One wasted round-trip per cold open. |
| 3 | Named-ref read can fire twice within the auto-check window (Check button + status refresh) | `vault-shell.js:536, 572` | Duplicate GETs of the same 1-byte pointer. |
| 4 | Full commit-DAG walk on divergence check (BFS both parents, 50-per-batch) | `vault--sync.js:215–256` | Pathological case on deep histories. Rare today, will bite as vaults age. |
| 5 | No in-memory TTL on ref pointers | `sg-vault-ref-manager.js` | Every caller re-reads independently. |
| 6 | Branch-index read at open is always-attempted even with single-named-branch vaults | `sg-vault.js:122–131` | One avoidable read for the common case. |
| 7 | Subtree expansion is 1-per-folder, no "include immediate children" option | `vault--folder-ops.js:93–117` | Slow first navigation into a deep tree. |

## Questions for the SGit CLI Team

We do not want to prescribe protocol changes — you own the spec. We do want you to grade these:

1. **Is there a clean way to fuse commit + push into a single server-acknowledged operation?** Either:
   - A `POST /bare/refs/advance` that accepts `{ commit_id, advance_named, advance_clone }` and is atomic
   - Or rethinking the clone-ref entirely (is it adding value separate from the named ref when auto-push is the default?)
2. **What's the right way to make first-open faster?** Pre-create the clone ref at vault creation? Treat its absence as "use named HEAD" without a 404 round-trip? Something else?
3. **Should ref pointers be cacheable with a short TTL** (say, 2–5 seconds) on the client? The named ref changes on every push — but inside a single user interaction we read it 1–2 times redundantly. Would a `Cache-Control: max-age=2` on the response be appropriate, or should the client own the TTL?
4. **What's the optimal `vaultBatch` chunk size today?** We use 50. Is that still right for your S3 backend? Is there a "fetch tree + N levels of children" batched call that would speed up subtree expansion?
5. **For divergence resolution**, is there a server-side "find common ancestor" endpoint we should be calling instead of walking the DAG client-side? Doing it server-side could be O(1) round-trips even on deep histories.
6. **Auto-push semantics:** are there cases where you (the CLI team) would explicitly *not* want the named ref to advance on every commit? We have not found one in the browser context. If the CLI has them, we need to understand whether the auto-push model holds at the protocol level or is purely a browser-UX choice.

## What We're Asking For

A reply (in `team/comms/briefs/05/MM/` or in your own debrief location, your call) that contains:

1. **Confirmation or correction of the map above** — flag anything we got wrong
2. **A target HTTP-request count per operation**, e.g. "vault open = 2 reads minimum", "single-file save = 3 writes minimum", "pull when behind = 1 read + N tree reads"
3. **Your reduction priorities** — which of the 7 ranked items should we tackle first, and which need protocol-level changes vs. pure browser-client work
4. **For each protocol change**, the migration shape (backwards-compatibility path so today's vaults keep working)

We're happy to do the browser-client work once the protocol direction is clear. We're not happy to do it in a way that diverges from the CLI's behaviour — keeping browser-client and CLI semantically identical is non-negotiable.
