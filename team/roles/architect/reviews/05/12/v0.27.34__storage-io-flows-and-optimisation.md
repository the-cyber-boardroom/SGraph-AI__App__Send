# Architect Review — Storage I/O Flows & Optimisation Map

**Role:** Architect
**Team:** Explorer
**Version:** v0.27.34
**Date:** 2026-05-12
**Companion to:** `v0.27.34__access-key-architecture-review.md`
**Scope:** Every backend storage operation (Memory-FS / S3 / MGraph-AI Cache) that happens behind every endpoint at `send.sgraph.ai/api/docs`, drawn as ASCII flow diagrams, with annotated cost.
**Goal:** Identify where the current code is needlessly expensive, where we can defer / batch / cache, and where to add licensing + bandwidth-billing primitives with the smallest possible runtime tax.

---

## 1. Cost Model

Three classes of storage operations exist behind the API. Their costs differ by **orders of magnitude**.

| Class | Symbol | Mechanism | Cost per call | Latency |
|---|---|---|---|---|
| **In-process** | `[MEM]` | Lambda-lifetime in-memory cache (e.g. `_manifest_cache` dict) | ~0 (nanoseconds) | <0.001ms |
| **Memory-FS (dev)** | `[FS]` | Local file system — only in tests and local runs | very low (microseconds) | <1ms |
| **S3 (prod)** | `[S3]` | Storage_FS backed by S3. Each `file__exists`, `file__json`, `file__save`, `file__delete`, `folder__files__all` is an S3 API call | $-charged + 5–30ms RTT | 5–30ms |
| **MGraph-AI Cache** | `[CACHE]` | HTTP call to a separate Lambda/service, which itself does multiple S3 ops | inter-Lambda HTTP RTT + 1–N internal S3 ops | 30–80ms |
| **S3 multipart API** | `[S3-API]` | `create_multipart_upload`, `complete_multipart_upload`, `generate_presigned_url`. Not file I/O but billed S3 API calls. | $ + RTT | 30–80ms |

**Key facts that drive the optimisation strategy:**

- In production, `[FS]` calls *are* `[S3]` calls. Every `file__exists` is a `HeadObject`; every `file__json` is `GetObject` + JSON parse; every `file__save` is `PutObject`.
- `[CACHE]` calls fan out: a single `token_use` is 1 HTTP RTT to the cache service *which then does 3 S3 reads + 2 S3 writes internally*. So one "token use" is ~**5 S3 operations** plus a Lambda hop.
- **Reads of payloads are also bandwidth.** Reading a 100 MB transfer to stream it back through Lambda is not just a `GetObject` cost — it's 100 MB of Lambda egress.

  ▼
┌──────────────────────────────────┐
│ GET /vault/zip/{vault_id}        │

## 8. Optimisation Strategies

### 8.1 Cheap & immediate wins

**O-1. Remove the redundant hash lookup in `Service__Tokens.use()`.**
The flow `token__lookup()` → `token__lookup_cache_id()` re-reads the same hash twice (`Send__Cache__Client.py:99–109`). The first call already knows the `cache_id`; pass it through. Saves 1 S3 read per token use, applied to every `POST /transfers/complete` and `POST /transfers/validate-token`.

**O-2. Same redundancy in `update_limit`, `reactivate`, `revoke`.**
All re-look-up after the first lookup. Same fix.

**O-3. Coalesce `exists` + `json` into a single `GetObject`.**
`Service__Transfers` consistently does `file__exists()` *then* `file__json()`. In S3, `HeadObject` then `GetObject` is two API calls — but `GetObject` itself already returns a 404 if missing. Catching the 404 from the `GetObject` and treating it as "doesn't exist" halves the API count for most transfer/vault reads.

**O-4. Lambda-lifetime cache for token lookups.**
Mirror what `Service__Vault__Pointer` does with `_manifest_cache`: hold a small LRU keyed by `token_name` with a short TTL (10–30s). Most realistic traffic patterns (a user uploads, then within seconds visits the download page) re-hit the same token. Cuts inter-Lambda RTT on `check-token` + `validate-token` + `complete` sequences. Must support **explicit invalidation** on revoke — easy if the admin side publishes an invalidation event (or accept the TTL as the worst-case staleness window).

**O-5. Stop re-writing `meta.json` on every download.**
Right now `GET /transfers/download` re-writes `meta.json` to bump `download_count` and append a `download` event. For a popular transfer this is one `PutObject` per download against the *same* tiny object. Two options:

- **Defer:** record the download event into an in-Lambda buffer; flush every M downloads or on Lambda shutdown.
- **Out-of-band:** drop a per-download event marker into a sharded append-only path (`transfers/{id}/events/{ulid}`) and aggregate offline.

The same fix applies to `GET /presigned/download-url`.

**O-6. Batch-delete in `destroy_vault`.**
S3 supports `DeleteObjects` up to 1000 keys per call. Currently we issue one `DeleteObject` per file. For a 1000-file vault: 1 API call instead of 1000.

### 8.2 Skip-the-check wins (immutability boundaries)

The previous review identified that **transfer metadata and vault manifests are immutable in their core fields** after creation. We can exploit that:

**O-7. Skip the `exists(meta.json)` precheck on `complete`/`upload`.**
The route already needs `json(meta.json)`. If the parse succeeds, the file exists; if it 404s, the parse raises. The current `exists` precheck is a free `HeadObject` we don't need.

**O-8. Skip `exists(payload)` in `complete`.**
The flag exists in `meta.json` (the upload event is already written when payload landed). The HeadObject is paranoia. Trust the metadata.

**O-9. Cache vault `write_key_hash` Lambda-lifetime — already done.**
Recognise this exists (`_manifest_cache`) and lean harder on it: the manifest is immutable after first write, so the cache *never* needs to invalidate within a Lambda lifetime.

**O-10. Cache transfer metadata Lambda-lifetime for download paths.**
A popular transfer downloaded 50 times in quick succession is currently doing 50× (HeadObject + GetObject + PutObject). With a short Lambda-lifetime cache plus the deferred event buffer (O-5), it becomes 1× GetObject and an in-memory counter increment.

### 8.3 Deferred & out-of-band aggregation

This is the core idea behind enabling licensing/billing without a runtime tax.

**Pattern A — write-through buffer:**
Hot-path code increments an in-memory counter. A background flusher (Lambda extension, scheduled Lambda, or piggy-back on the next slow request) writes the aggregate every M seconds or M events, whichever first.

**Pattern B — append-only event log:**
Hot path drops a tiny event marker into `events/{date}/{ulid}.json` (single S3 PUT, no read). A nightly aggregator job (separate Lambda) folds them into the token's counters. Loses real-time precision but is essentially free per request.

**Pattern C — SQS fan-out:**
Hot path enqueues a usage event onto SQS (low cost, async). A consumer Lambda batches them and writes one aggregated S3 update per N events.

For SGraph Send specifically, **Pattern B** fits best: it's the most consistent with the existing Memory-FS abstraction (no new infrastructure), it works in dev mode trivially (a folder of files), and aggregation can be deferred indefinitely until the next admin-side stats request.

### 8.4 What we should *stop* doing

- **Anonymous `vault/batch` reads of 100 files.** This is a free bandwidth amplifier for any caller. Either rate-limit at the edge, or require a token for batch reads, or cap batch size to 10.
- **`download-base64` for non-trivial files.** It blows up Lambda memory and egress by 33%. Restrict to ≤ 1 MB or remove.
- **`token list-details`** as currently implemented. It does 2N reads. If admins need it, paginate; if a UI needs it, the result should itself be cached.

## 9. Licensing & Billing Roadmap (No-Drama Edition)

The user requirement: *"add licensing to the vault, minimise performance impact, start tracking & billing downloads and bandwidth."* The goal is to enable this without paying for it on every hot-path call.

### 9.1 What we want to capture (per token)

| Metric | Where it happens | Frequency | Aggregation key |
|---|---|---|---|
| Transfer create | `POST /transfers/create` | Per transfer | `token_name` |
| Transfer upload bytes | `POST /transfers/upload` *and* `POST /presigned/complete` | Per upload, with size | `token_name`, day |
| Transfer download count | `GET /transfers/download` *and* `GET /presigned/download-url` | Per download | `token_name`, `transfer_id` |
| Transfer download bytes | Same | Per download, with size | `token_name`, day |
| Vault writes (count + bytes) | `PUT /vault/write`, `POST /vault/batch` writes | Per write | `token_name`, `vault_id` |
| Vault reads (count + bytes) | `GET /vault/read`, `POST /vault/batch` reads | Per read | `vault_id`, day (no token on reads — see §9.4) |
| Vault zip generation | `GET /vault/zip` | Per build | `token_name`, `vault_id` |
| Storage occupied | Derived from manifest size + payload sizes | Periodic | `vault_id`, day |

The data model needs to grow from "one counter" to "a fact table keyed by (token, day, action)".

### 9.2 Granularity without runtime cost — recommended design

**Step 1 — Stop using `token_use` for billing-grade events.**
`token_use` does 5 S3 ops. Use it only for the existing rate-limit-style quota check on transfer completion. Do not call it for downloads or vault writes.

**Step 2 — Introduce a hot-path event sink.**
Define one new primitive: `usage_event__append(token_name, action, dimensions: dict)`. Implementation in v1:

```
storage_fs.file__save(
  path = f"usage_events/{date}/{token_name}/{ulid}.json",
  body = json({action, dimensions, ts, ip_hash})
)
```

One PutObject. No read. No counter update. The file path is sharded by date + token so listings later are scoped.

This becomes the bedrock for *all* fine-grained tracking: it's a write-only fire-and-forget that can later be relocated to SQS or Kinesis without changing call sites.

**Step 3 — Build a periodic aggregator (separate Lambda).**
Triggered by EventBridge every N minutes (or on demand from the admin UI). For each token, list `usage_events/{date}/{token_name}/` and roll the events into a daily aggregate at `usage_daily/{token_name}/{date}.json`. After successful aggregation, delete the source events (1 batch-delete call).

**Step 4 — Admin API reads the aggregate, not the event stream.**
`GET /tokens/usage/{token_name}` returns the daily aggregate (1 read). Real-time queries can optionally also list the unaggregated tail (`usage_events/{today}/{token_name}/`) for the last N minutes.

**Step 5 — Quota & licensing checks read the *daily aggregate*, not live counters.**
This is the most important property: a license check at the start of a request reads one cached object (probably already in the Lambda-lifetime cache). The check is approximate (lags by ≤ the aggregation interval), which is fine for monthly/daily billing — and for hard cut-offs we already have the existing `token_use` exhaustion mechanism as a backstop.

### 9.3 Where to hook each event

| Hook point | Event written |
|---|---|
| `Transfer__Service.create_transfer` end | `transfer.created` (+size limit attempted) |
| `Transfer__Service.upload_payload` end | `transfer.uploaded` (+bytes) |
| `Transfer__Service.complete_transfer` end | `transfer.completed` |
| `Transfer__Service.get_download_payload` end | `transfer.downloaded` (+bytes) |
| `Service__Presigned_Urls.create_download_url` end | `transfer.download_url_issued` (presigned downloads bypass Lambda for the actual bytes, so this is the only billing signal — fine, since we know the size from the metadata) |
| `Service__Vault__Pointer.write` end | `vault.write` (+bytes) |
| `Service__Vault__Pointer.read` end | `vault.read` (+bytes) — **anonymous, see §9.4** |
| `Service__Vault__Pointer.batch` per op | one event per op |
| `Service__Vault__Zip.get_or_create_zip` end | `vault.zip_build` (+bytes, +cache hit/miss) |

Each is **one S3 PutObject**, no read, no inter-Lambda call.

### 9.4 The anonymous-read problem

Vault reads (`GET /vault/read`) have **no token** in the request. To bill the vault owner for read bandwidth we need a binding from `vault_id` → `token_name` (the token that created the vault). Two options:

- **A:** Store the owning `token_name` inside `manifest.json` at vault creation. The manifest is already loaded on writes (cached) — but not on reads (intentionally, for the zero-knowledge model). For billing the read, we'd need to add a single cached lookup `vault_id → token_name`. Memoise it Lambda-lifetime: most reads of the same vault hit the cache.
- **B:** Don't bill anonymous reads — only bill the vault owner for the *storage size* of the vault (a periodic measurement). Simpler, preserves the zero-knowledge surface, but loses the bandwidth signal.

Recommendation: **A** in production with the manifest-lookup cached aggressively. The cost is one extra HeadObject per cold Lambda per vault, which is fine.

### 9.5 What this lets the business do

- Bill per upload bytes (existing data we already have).
- Bill per download count and bytes (new).
- Bill per vault storage size (new — measure once a day).
- Bill per vault read bandwidth (new — anonymous-read attribution above).
- License vault features (zip export, batch writes) by counter rather than by token-quota.
- Provide accurate usage dashboards without ever touching the hot path with a counter increment.

### 9.6 Cost of doing nothing

If we keep using `token_use` to track granular billing events:

- Every download = 5 S3 ops (instead of 1).
- Every vault write = 5 extra S3 ops + 1 inter-Lambda call.
- A bursty 1000-download transfer = 5000 cache S3 ops just for accounting.
- The Admin Lambda becomes the bottleneck of the whole system.

The deferred-event-log pattern keeps the hot path at **1 extra PutObject** while giving us strictly *more* granular data than `token_use` does today.

## 10. Migration Sequence (Recommended Order)

1. **Land the cheap wins first** (O-1 through O-3) — they touch only the Admin token service and are reviewable in isolation.
2. **Add the Lambda-lifetime token cache** (O-4) — small, well-bounded change to `Routes__Transfers.check_access_token` and `Routes__Vault__Pointer.check_access_token`. Extract the shared validator while doing this (the dedup recommendation from §7.4 of the previous review).
3. **Introduce `usage_event__append`** as a primitive (§9.2 step 2) without changing existing call sites. Pure addition.
4. **Wire it into all the hooks in §9.3** behind a feature flag. Existing `token_use` calls remain.
5. **Build the aggregator Lambda** (§9.2 step 3). Run it offline against the event stream until aggregates look right.
6. **Switch admin reads to consume aggregates** (§9.2 step 4).
7. **Stop calling `token_use` for billing-grade events** (§9.1 step 1). Keep it only for the hard quota cutoff at transfer completion.
8. **Apply the bandwidth fixes** (O-5, O-6) once events are flowing.
9. **Decide on anonymous-read attribution** (§9.4) and ship the manifest cache for the vault-read path.
10. **Schema work for licensing**: add the per-token feature flags / monthly allowances on the `Schema__Token__Metadata` once we know what we're actually billing.

Each step is independently shippable, reversible, and measurable.
