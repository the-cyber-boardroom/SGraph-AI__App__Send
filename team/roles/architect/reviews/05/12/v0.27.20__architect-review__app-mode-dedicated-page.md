# Architect Review: Current App Mode vs. Proposed `/en-gb/app` Dedicated Page

**Role:** Architect
**Date:** 2026-05-12
**Version:** v0.27.20
**Scope:** Architecture evaluation of App Mode delivery + proposal for a dedicated `/en-gb/app` page
**Status:** Proposal — no code changes yet
**Companion doc:** [`v0.27.20__architect-review__readonly-sharing-and-owner-secrets.md`](./v0.27.20__architect-review__readonly-sharing-and-owner-secrets.md) — the `/en-gb/app` entry page consumes the ro-token + owner-only-namespace features described there. Each doc is independently actionable.

---

## TL;DR

App Mode today is a "mode" of the full vault page, which means app users see vault chrome (entry form, header, nav, file browser) flash before the app takes over. The iframe also lives inside `send-browse`, a component designed for file browsing — leading to iframe-reuse bugs, an unsafe `sg.git.refresh()`, and full vault weight for users who never touch vault features.

This review proposes:

1. **Delete App Mode from the vault page entirely.** `sg-app-banner`, the `chrome.mode` detection in `send-browse`, and all panel-hijacking code are removed. The iframe-with-`window.sg.*`-bridge behavior (clicking any `.html` file in the vault) is **kept unchanged** — it's too powerful to touch.
2. **One app per vault, surfaced at vault level.** When `.vault/app.json` is present, the vault header shows a single prominent **Open App** button. The `chrome.mode`/`present` field is removed — it served only to tell the vault to maximise, which the new page makes unnecessary.
3. **New `/en-gb/app#[vault-key]` page** — lightweight `app-shell` (~250 LOC), no vault chrome, fresh iframe, `auto_load` respected, `resources.css/js` pre-injected before entry loads.
4. **Hashless `/en-gb/app` entry page** — single field that accepts a vault key OR a `ro-` token (token resolution + RO sharing detailed in the companion doc), plus an optional backend access key persisted to `localStorage`.
5. **Unified hash handling** — both `/en-gb/vault` and `/en-gb/app` parse credentials through one shared module (`vault-credentials.js`, defined in the companion doc). Credentials cached in `sessionStorage`, hash cleared immediately, free navigation between the two pages with no re-auth.

The `window.sg.*` bridge is identical in both the vault preview and the new app page. No SG/App code changes required. Estimated scope (this doc only): ~3 phases, ~565 LOC added + ~280 LOC of old App Mode code deleted, ~6–10 hours. The RO/owner-only/visual-cues work in the companion doc adds another ~650 LOC / 10–13 hours.

## Current Architecture: App Mode as a Vault "Mode"

App Mode today is an overlay on top of the full vault UI. The iframe lives deep inside a stack of components designed for vault file-browsing, not for app delivery:

```
Browser URL: /en-gb/vault#[vault-key]
│
└── index.html (full vault page)
    ├── vault-loader scripts × 6 (routing, storage, format, recent, ...)
    ├── sg-layout (fractal window manager — CDN)
    ├── sg-tool-api-* debug components (CDN ×3)
    ├── sg-llm-* components (CDN ×3)
    └── vault-shell (the entire vault orchestrator)
        ├── vault-entry
        │   └── [entry form visible during load — app users see this]
        │
        └── [after vault opens] vs-shell
            ├── vault-header
            │   └── vh-sync-section (↻ check / push / pull / refresh)
            ├── vault-auth
            ├── vault-nav (Files | SGit | Settings)
            └── vs-main
                └── vs-content
                    └── send-browse (full file browser)
                        ├── [file tabs, tree, download button, ...]
                        └── [App Mode: sg-app-banner activates]
                            └── iframe (vault-hosted HTML app)
                                └── window.sg.* bridge (injected)
```

### How App Mode activates today (step-by-step)

```
1.  URL loads
2.  vault-loader scripts run → routing decision made
3.  vault-shell renders → vault-entry form APPEARS (user sees this)
4.  User is already at the hash → auto-decrypt begins
5.  vault-shell calls _mountBrowse() → VaultDataSource + send-browse mount
6.  send-browse scans file list → detects app.json
7.  Reads app.json → detects chrome.mode = "maximised"
8.  sg-app-banner.activate() → banner replaces header chrome
9.  iframe element is created (or reused — see Problem 2) inside the panel
10. vfsBridgeScript is injected into iframe → window.sg.* available
11. app HTML loads inside iframe → app renders
```

### The core structural problems

**Problem 1 — User sees vault chrome during steps 1–8.**
The entry form, vault-nav tabs, and file browser all flash before the app takes over. Users who exclusively use App Mode see UI they'll never understand and that exists only for vault operators.

**Problem 2 — Iframe reuse.**
`send-browse` was never designed for App Mode — it reuses the same panel element when navigating between file tabs. App Mode "hijacked" this panel. This creates state leakage: double event listeners, stale `window.sg` injections, and undefined behaviour when `_mountBrowse()` is called after an already-active App Mode session.

**Problem 3 — Full vault weight for a simple app.**
`sg-layout`, `sg-llm-*`, `vault-nav`, `vault-sgit-view`, `vault-settings`, `vault-status-bar`, the debug sidebar, six vault-loader scripts — none of these are needed by an app user. They register listeners, consume memory, and fire requests that have nothing to do with the app.

**Problem 4 — `sg.git.refresh()` is unsafe to await.**
A "refresh" in vault context means `_mountBrowse()` re-runs, which destroys the iframe that sent the call. The promise never resolves. This is a direct consequence of App Mode living inside `send-browse` rather than owning its own lifecycle.

**Problem 5 — `app.json` has no resource declaration.**
Currently only `entry` and `chrome.mode` are used. An app that needs external CSS or JS must load them lazily via `sg.vfs.read()` + `<style>` injection — round-trips through the VFS bridge that happen after the iframe is already visible, causing flash-of-unstyled-content.

**Problem 6 — Multiple "apps" in a vault create conflicting activation.**
`chrome.mode: "maximised"` fires per-file, so a vault with two app-like HTML files produces undefined behaviour. One app per vault is the natural model — navigation between sub-views is handled inside the app's own router, not by the vault.

## Proposed Architecture: `/en-gb/app` as a First-Class Page

An SG/App needs exactly three things from the vault infrastructure:

```
1. Crypto layer   — open the vault from the URL hash key
2. VFS bridge     — read/write files (window.sg.*)
3. HUD            — minimal status + feedback surface (optional)
```

Everything else is for vault operators, not app users. The new page is built around this constraint:

```
Browser URL: /en-gb/app#[vault-key]
│
└── app.html (new lightweight page — no vault-loader scripts)
    ├── sg-send.js          (crypto + transfer layer — already exists)
    ├── sg-vault.js         (vault open/close — already exists)
    └── app-shell           (new minimal custom element, ~250 LOC)
        │
        ├── PHASE 1 — loading
        │   ├── Reads vault key from URL hash
        │   ├── SGVault.open() — same call vault-shell makes
        │   ├── Reads .vault/app.json from vault VFS
        │   ├── Parallel-fetches resources declared in app.json
        │   │   (CSS + JS, from vault VFS, injected into iframe <head>)
        │   └── Shows ONLY: spinner + vault name
        │       (no vault-nav, no vault-header, no sg-app-banner)
        │
        ├── PHASE 2 — ready
        │   ├── Creates a FRESH iframe (never reused, new every time)
        │   ├── Injects vfsBridgeScript (identical window.sg.* surface)
        │   ├── Injects pre-fetched CSS/JS from app.json resources
        │   ├── Loads entry file
        │   └── Optional minimal HUD bar (if app.json hud: true)
        │
        └── (no vault-shell, vault-nav, vault-settings, send-browse,
             vault-sgit-view, sg-layout, sg-llm-* — none of these load)
```

### Hashless entry page (`/en-gb/app` with no `#vault-key`)

The hashless variant is the **entry page** — a first-class auth surface. The user pastes a vault key (full read+write) or a `ro-` token (read-only — see [companion doc](./v0.27.20__architect-review__readonly-sharing-and-owner-secrets.md) for token format and resolution flow). Optional backend access key is collected in a collapsed sub-section.

```
  ┌──────────────────────────────────────────────────────────────┐
  │                                                               │
  │              ┌─────────────────────────────────────┐         │
  │              │   Open a vault                       │         │
  │              │                                       │         │
  │              │   ┌─────────────────────────────────┐ │         │
  │              │   │ Vault key or read-only token    │ │         │
  │              │   │ e.g. apple-river-1234           │ │         │
  │              │   │      ro-coral-stamp-1234        │ │         │
  │              │   └─────────────────────────────────┘ │         │
  │              │                                       │         │
  │              │   ▸ Backend access key (optional)     │         │
  │              │     ┌──────────────────────┐ ✓ saved  │         │
  │              │     │ ●●●●●●●●●●●●●●●●●●● │  locally  │         │
  │              │     └──────────────────────┘  □ remember         │
  │              │                                       │         │
  │              │   [  Open vault  ]                    │         │
  │              │                                       │         │
  │              └─────────────────────────────────────┘         │
  │                                                               │
  └──────────────────────────────────────────────────────────────┘
```

The vault-key vs ro-token discrimination happens in the shared `vault-credentials.js` module (defined in the companion doc) — same parser as for hash URLs. Once parsed, credentials land in `sessionStorage` and the rest of the flow is identical.

**Backend access key handling:**

The access key (write permission for the server, e.g. `apple-river-1234`) is **separate from the vault encryption keys** and changes far less often. The entry page should:

- Show the access key field as a collapsed section labelled "Backend access key (optional)"
- Persist it to **`localStorage`** (not `sessionStorage`) when "remember" is checked — the value is stable across sessions
- Auto-fill on next visit with a "✓ saved locally" indicator
- Validate via the existing `GET /api/transfers/check_token/{name}` endpoint before opening the vault (catches expired keys at entry, not mid-session)
- Expose a "clear saved key" action for shared devices

This collapses the current friction where users have to: open vault → see read-only badge → click badge → paste access key → wait for validation. The entry page handles it before the vault opens.

### Auth-required state with hash (`auth.required: true` in app.json)

When the vault is opened via `#[full-key]` but `app.json` declares `auth.required: true` and no access key is cached, the app-shell intercepts before mounting the iframe:

```
  ┌──────────────────────────────────────────────────────────────┐
  │                                                               │
  │              ┌─────────────────────────────┐                 │
  │              │  KneeScore                  │                 │
  │              │                             │                 │
  │              │  Enter your access key      │                 │
  │              │  to continue                │                 │
  │              │                             │                 │
  │              │  [ __________________ ]     │                 │
  │              │  □ Remember on this device  │                 │
  │              │                             │                 │
  │              │  [ Continue          ]      │                 │
  │              │                             │                 │
```

The app-shell handles this before the iframe even loads — no `sg.auth.setKey()` call needed from app code, no onboarding screen for the app author to build. "Remember on this device" persists to `localStorage`; unchecked goes to `sessionStorage` (current behaviour).

## Enhanced `app.json` Schema

**Location:** `.vault/app.json` (was `.app.json` at root — now inside the `.vault/` metadata namespace)

**Current (inferred from code):**
```json
{
  "entry": "app.html",
  "chrome": { "mode": "maximised" }
}
```

**Proposed:**
```json
{
  "entry":     "app.html",
  "title":     "KneeScore",
  "icon":      "icon.svg",
  "auto_load": true,
  "hud":       true,
  "resources": {
    "css": [
      "_common/reset.css",
      "_common/app.css",
      "themes/dark-health.css"
    ],
    "js": [
      "_common/lib/chart.min.js",
      "_common/utils.js"
    ]
  },
  "auth": {
    "required": true,
    "prompt":   "Enter your access key to continue"
  }
}
```

**Field changes from current schema:**

| Field | Status | Purpose |
|---|---|---|
| `entry` | kept | The HTML file the app-shell loads into the iframe |
| `auto_load` | kept | When `true`, the vault file preview auto-opens this file on vault open (current behaviour) — **this is about the in-vault preview, not the app page** |
| `chrome.mode` | **deleted** | Previously told the vault to maximise the panel; no longer needed — the URL itself is the discriminator now |
| `title` | new | Display name shown in HUD and vault "Open App" button |
| `icon` | new | Icon shown in the vault button and HUD |
| `hud` | new | Whether app-shell shows the minimal status bar at the top of `/en-gb/app` |
| `resources.css/js` | new | Vault-VFS files pre-fetched and injected into iframe `<head>` before `entry` runs — app author writes zero loader code |
| `auth.required` | new | app-shell intercepts before mounting iframe, collects access key |

`resources.css/js` files are fetched from the vault VFS in parallel before the iframe loads, then injected as `<style>` and `<script>` blocks. Zero loader code in the app.

`auth.required` intercepts before the iframe loads — no `sg.auth.setKey()` needed from app code, no onboarding screen to build.

## Population Separation

The two URLs serve two fundamentally different audiences from the same vault:

```
         same vault key ──────────────────────────┐
                                                   │
  /en-gb/vault#[key]              /en-gb/app#[key] │
  ─────────────────────           ───────────────────
  Vault operator                  App user
  Needs file browser              Never sees file browser
  Needs SGit view                 Never sees git controls
  Needs settings panel            Never sees settings
  Understands push/pull           Sees "Saving..." / "Up to date"
  Uses window.__tool (Playwright) Uses window.sg.* (in-iframe)
  Distributes to team members     Distributes to end users
```

The vault key is identical. The difference is only the HTML page that serves the shell. A KneeScore author keeps `/en-gb/vault#[their-key]` for their own management and distributes `/en-gb/app#[their-key]` to patients.

## What Stays, What Goes

**Stays unchanged:**
- `/en-gb/vault` — full vault page, all features, zero regressions
- `send-browse` iframe preview of HTML files — every `.html` file still renders in the file panel with the `window.sg.*` bridge injected
- `window.sg.*` bridge (vfsBridgeScript) — identical in both the vault preview and `/en-gb/app`
- `auto_load` field in `.vault/app.json` — still controls which file auto-opens in the vault preview

**Vault root structure (after migration):**
```
  /                              ← app content (all user-visible files)
  ├── app.html
  ├── _common/
  │   ├── reset.css
  │   └── utils.js
  └── .vault/                    ← vault metadata (hidden dir, replaces scattered root files)
      ├── app.json               ← was .app.json at root
      ├── settings.json          ← was .vault-settings.json at root
      └── owner/                 ← double-encrypted (HKDF from vault-key, write-only)
          ├── readonly-tokens.json
          ├── author-notes.md    (future)
          └── llm-api-keys.json  (future)
```

**Deleted:**
- `sg-app-banner` web component (~150 LOC) — entire component gone
- `chrome.mode: "maximised"` detection in `send-browse` (~80 LOC) — gone
- Panel-hijacking / iframe-reuse logic in `send-browse` (~50 LOC) — gone
- `chrome` key in `app.json` schema — ignored if present in old files, never written by new tooling

**Added to vault page (small):**
- Vault header shows **"▶ Open [app title]"** button when `app.json` exists at vault root — one `window.open('/en-gb/app#' + vaultKey, '_blank')` call (~15 LOC in vault-header)

**Migration for existing apps using `chrome.mode: "maximised"`:**
The vault page simply stops auto-activating. The iframe preview still loads the HTML file. The vault operator now uses the "Open App" button to get the full-screen experience. The `chrome.mode` field is silently ignored — no errors, no breakage, just a no-op until the app author removes it.
