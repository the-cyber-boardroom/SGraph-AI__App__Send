# Architect Review: Current App Mode vs. Proposed `/en-gb/app` Dedicated Page

**Role:** Architect
**Date:** 2026-05-12
**Version:** v0.27.20
**Scope:** Architecture evaluation of App Mode delivery + proposal for a dedicated `/en-gb/app` page
**Status:** Proposal — no code changes yet

---

## TL;DR

App Mode today is a "mode" of the full vault page, which means app users see vault chrome (entry form, header, nav, file browser) flash before the app takes over. The iframe also lives inside `send-browse`, a component designed for file browsing — leading to iframe-reuse bugs, an unsafe `sg.git.refresh()`, and full vault weight for users who never touch vault features.

This review proposes a new first-class page at `/en-gb/app#[vault-key]` that loads only the vault crypto layer + a minimal `app-shell` (~250 LOC), with an enhanced `app.json` that can declare CSS/JS resources to inject before the iframe boots. The `window.sg.*` bridge stays identical, so no SG/App code changes are required. Estimated scope: 5–7 hours total for Phase 1 + Phase 2.

---

## Current Architecture: App Mode as a Vault "Mode"

App Mode today is an overlay on top of the full vault UI. The iframe lives deep inside a stack of components designed for vault file-browsing, not for app delivery:

```
Browser URL: /en-gb/vault#[vault-key]
│
└── index.html (full vault page)
    ├── vault-loader scripts × 6 (routing, storage, format, recent, ...)
    ├── sg-layout (fractal window manager — CDN)
    ├── sg-tool-api-* debug components (CDN ×3)
    ├── sg-llm-* components (CDN ×3)
    └── vault-shell (the entire vault orchestrator)
        ├── vault-entry
        │   └── [entry form visible during load — app users see this]
        │
        └── [after vault opens] vs-shell
            ├── vault-header
            │   └── vh-sync-section (↻ check / push / pull / refresh)
            ├── vault-auth
            ├── vault-nav (Files | SGit | Settings)
            └── vs-main
                └── vs-content
                    └── send-browse (full file browser)
                        ├── [file tabs, tree, download button, ...]
                        └── [App Mode: sg-app-banner activates]
                            └── iframe (vault-hosted HTML app)
                                └── window.sg.* bridge (injected)
```

### How App Mode activates today (step-by-step)

```
1.  URL loads
2.  vault-loader scripts run → routing decision made
3.  vault-shell renders → vault-entry form APPEARS (user sees this)
4.  User is already at the hash → auto-decrypt begins
5.  vault-shell calls _mountBrowse() → VaultDataSource + send-browse mount
6.  send-browse scans file list → detects app.json
7.  Reads app.json → detects chrome.mode = "maximised"
8.  sg-app-banner.activate() → banner replaces header chrome
9.  iframe element is created (or reused — see Problem 2) inside the panel
10. vfsBridgeScript is injected into iframe → window.sg.* available
11. app HTML loads inside iframe → app renders
```

### The core structural problems

**Problem 1 — User sees vault chrome during steps 1–8.**
The entry form, vault-nav tabs, and file browser all flash before the app takes over. Users who exclusively use App Mode see UI they'll never understand and that exists only for vault operators.

**Problem 2 — Iframe reuse.**
`send-browse` was never designed for App Mode — it reuses the same panel element when navigating between file tabs. App Mode "hijacked" this panel. This creates state leakage: double event listeners, stale `window.sg` injections, and undefined behaviour when `_mountBrowse()` is called after an already-active App Mode session.

**Problem 3 — Full vault weight for a simple app.**
`sg-layout`, `sg-llm-*`, `vault-nav`, `vault-sgit-view`, `vault-settings`, `vault-status-bar`, the debug sidebar, six vault-loader scripts — none of these are needed by an app user. They register listeners, consume memory, and fire requests that have nothing to do with the app.

**Problem 4 — `sg.git.refresh()` is unsafe to await.**
A "refresh" in vault context means `_mountBrowse()` re-runs, which destroys the iframe that sent the call. The promise never resolves. This is a direct consequence of App Mode living inside `send-browse` rather than owning its own lifecycle.

**Problem 5 — `app.json` has no resource declaration.**
Currently only `entry` and `chrome.mode` are used. An app that needs external CSS or JS must load them lazily via `sg.vfs.read()` + `<style>` injection — round-trips through the VFS bridge that happen after the iframe is already visible, causing flash-of-unstyled-content.

## Proposed Architecture: `/en-gb/app` as a First-Class Page

An SG/App needs exactly three things from the vault infrastructure:

```
1. Crypto layer   — open the vault from the URL hash key
2. VFS bridge     — read/write files (window.sg.*)
3. HUD            — minimal status + feedback surface (optional)
```

Everything else is for vault operators, not app users. The new page is built around this constraint:

```
Browser URL: /en-gb/app#[vault-key]
│
└── app.html (new lightweight page — no vault-loader scripts)
    ├── sg-send.js          (crypto + transfer layer — already exists)
    ├── sg-vault.js         (vault open/close — already exists)
    └── app-shell           (new minimal custom element, ~250 LOC)
        │
        ├── PHASE 1 — loading
        │   ├── Reads vault key from URL hash
        │   ├── SGVault.open() — same call vault-shell makes
        │   ├── Reads /.app.json from vault VFS
        │   ├── Parallel-fetches resources declared in app.json
        │   │   (CSS + JS, from vault VFS, injected into iframe <head>)
        │   └── Shows ONLY: spinner + vault name
        │       (no vault-nav, no vault-header, no sg-app-banner)
        │
        ├── PHASE 2 — ready
        │   ├── Creates a FRESH iframe (never reused, new every time)
        │   ├── Injects vfsBridgeScript (identical window.sg.* surface)
        │   ├── Injects pre-fetched CSS/JS from app.json resources
        │   ├── Loads entry file
        │   └── Optional minimal HUD bar (if app.json hud: true)
        │
        └── (no vault-shell, vault-nav, vault-settings, send-browse,
             vault-sgit-view, sg-layout, sg-llm-* — none of these load)
```

## Enhanced `app.json` Schema

**Current (inferred from code):**
```json
{
  "entry": "app.html",
  "chrome": { "mode": "maximised" }
}
```

**Proposed for `/en-gb/app`:**
```json
{
  "entry":  "app.html",
  "title":  "KneeScore",
  "icon":   "icon.svg",
  "hud":    true,
  "resources": {
    "css": [
      "_common/reset.css",
      "_common/app.css",
      "themes/dark-health.css"
    ],
    "js": [
      "_common/lib/chart.min.js",
      "_common/utils.js"
    ]
  },
  "auth": {
    "required": true,
    "prompt":   "Enter your access key to continue"
  }
}
```

`resources.css` and `resources.js` are fetched from the vault VFS in parallel before the iframe loads, then injected as `<style>` and `<script>` blocks into the iframe `<head>` before `entry` runs. The app author writes no loader code — the shell handles it.

`auth.required` tells the shell to intercept the read-only case and collect the access key before mounting the iframe. The key is set via the same `vault-settings-access-key` event path that already exists — no new code paths to audit.

## Population Separation

The two URLs serve two fundamentally different audiences from the same vault:

```
         same vault key ──────────────────────────┐
                                                   │
  /en-gb/vault#[key]              /en-gb/app#[key] │
  ─────────────────────           ───────────────────
  Vault operator                  App user
  Needs file browser              Never sees file browser
  Needs SGit view                 Never sees git controls
  Needs settings panel            Never sees settings
  Understands push/pull           Sees "Saving..." / "Up to date"
  Uses window.__tool (Playwright) Uses window.sg.* (in-iframe)
  Distributes to team members     Distributes to end users
```

The vault key is identical. The difference is only the HTML page that serves the shell. A KneeScore author keeps `/en-gb/vault#[their-key]` for their own management and distributes `/en-gb/app#[their-key]` to patients.

## Migration Path and Compatibility

```
  1. /en-gb/vault continues exactly as today — zero regressions
  2. window.sg.* bridge is IDENTICAL in both pages — no app rewrites needed
  3. existing app.json works — entry + chrome.mode are ignored by app-shell
     (or chrome.mode could be the activation condition: "app" → use /en-gb/app routing)
  4. App Mode on vault page is preserved — same send-browse path unchanged
  5. No vault-shell changes required for Phase 1 of /en-gb/app
```

## Implementation Scope Estimate

**Phase 1 (happy path, no auth prompt, no resource loading):**
```
  app.html             ~30 LOC    new page, loads crypto libs + app-shell
  app-shell.js         ~200 LOC   vault open, app.json read, iframe lifecycle, HUD
  route registration   ~5 LOC     add /en-gb/app path to server routing
  ─────────────────────────────
  Total                ~235 LOC   3–4 hours
```

**Phase 2 (auth prompt + resource loading):**
```
  app-shell additions  ~100 LOC   auth intercept, parallel resource fetch + inject
  ─────────────────────────────
  Total                ~100 LOC   2–3 hours
```

**What is NOT needed:**
`vault-shell`, `vault-header`, `vault-nav`, `vault-auth`, `vault-settings`,
`vault-sgit-view`, `vault-status-bar`, `send-browse`, `vault-browse-edit`,
`sg-layout`, `sg-llm-*`, all six vault-loader scripts.

None of these load on `/en-gb/app`. The page weight drops by roughly 70%.

## Open Questions Before Implementation

1. **URL path:** `/en-gb/app` vs `/en-gb/vault/app` — the former is cleaner for distribution links; the latter is easier to route (shares the `/en-gb/vault` prefix). Preference?

2. **`app.json` location:** `/.app.json` (root, unambiguous) vs `app.json` (already used by App Mode today). Should these be the same file or separate?

3. **Activation condition:** Should the shell check for `chrome.mode` in app.json before mounting app-shell, or should the URL itself (`/en-gb/app` vs `/en-gb/vault`) be the only discriminator?

4. **Hh145 merge sequencing:** The `window.__tool` Phase 2 work (brief `v0.27.20__brief__merge-tool-api-phase-2-implementation.md`) and `/en-gb/app` are both pending on the same branch. Implement Hh145 first (3–4h) then `/en-gb/app` (6–7h), or start `/en-gb/app` now and merge Hh145 after?
