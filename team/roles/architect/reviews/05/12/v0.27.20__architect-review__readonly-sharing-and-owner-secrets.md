# Architect Review: Read-Only Sharing, Owner-Only Vault Secrets, and File-Access Visual Cues

**Role:** Architect
**Date:** 2026-05-12
**Version:** v0.27.20
**Scope:** Two new vault capabilities + the visual indicators required to make them safe and discoverable
**Status:** Proposal — no code changes yet
**Companion doc:** [`v0.27.20__architect-review__app-mode-dedicated-page.md`](./v0.27.20__architect-review__app-mode-dedicated-page.md) — the `/en-gb/app` entry page consumes these features but they are independently valuable.

---

## TL;DR

Today, sharing a vault is all-or-nothing: if you share the vault key, the recipient gets full read **and write** access. There is no UI surface for genuine read-only sharing, even though the backend's encryption model already supports it.

This review proposes three intertwined capabilities:

1. **Friendly `ro-` tokens for read-only sharing.** A vault author creates a short token (e.g. `ro-coral-stamp-1234`) and shares a URL like `send.sgraph.ai/en-gb/app#ro-coral-stamp-1234`. The token resolves via the existing SG/Send transfer API to `{ vault_id, read_key }`, granting decrypt-only access. The author controls expiry, use-count, and revocation per token. No new server endpoints required.

2. **`.vault/owner/*` — a write-key-only encrypted namespace.** Files under this path receive an inner encryption layer keyed by an HKDF derivation of the full vault-key. Read-only recipients see the file paths but cannot decrypt the bytes. The ro-token list lives here (preventing read-only peers from enumerating other tokens); future owner-only secrets land here for free.

3. **Visual access cues throughout the vault UI.** Every user — owner or read-only — knows at a glance who else can see what. Per-file badges, file-open banners, and a persistent access-level indicator in the header make the privacy boundary visible at the moment of viewing, editing, or sharing.

Total estimated scope: ~600 LOC + ~10–13 hours. No new server endpoints. No changes to the existing `window.sg.*` bridge.

---

## Current Limitations

```
  Today:  Share the vault key  →  recipient has full read + write
          That's the only mechanism.

  Result: vault authors cannot share with "view-only" audiences
          (patients, journalists, paper reviewers, preview users)
          without exposing the master key and granting them commit
          authorship.
```

Concrete gaps:

1. **No read-only sharing UI.** The backend's encryption layer supports decryption with a read-key alone, but no surface in the vault (or app) accepts that mode.
2. **No vault-private secrets.** Any file stored in the vault is visible to anyone who can open the vault. There is nowhere to put data that only the vault author should see — author notes, LLM API keys for the app, partner lists, draft content.
3. **Access state is invisible.** A user editing a file has no idea whether they're an owner or a read-only peer, whether the file they're editing is visible to others, or whether their changes will be shareable. The UI assumes "you have full access" everywhere.

## Capability 1 — Read-Only Tokens (`ro-...`)

### Resolution flow

```
  Vault author (in vault settings → "Read-only access links"):
  1. Click "Create new link"
  2. Set label, optional expiry, optional use-count
  3. Client constructs payload: { vault_id, read_key }
  4. Client encrypts payload — the friendly token IS (or derives) the encryption key
  5. POST /api/transfers — server stores encrypted blob with author-set TTL/uses
  6. Server returns short token: ro-coral-stamp-1234
  7. Client appends entry to .vault/owner/readonly-tokens.json
     (double-encrypted, see Capability 2; pushed to server)
  8. Author shares URL: /en-gb/app#ro-coral-stamp-1234

  Recipient browser (first visit):
  1. Hash parser sees `#ro-` prefix → resolve mode
  2. GET /api/transfers/coral-stamp-1234 → encrypted blob
  3. Client decrypts blob using token as key → { vault_id, read_key }
  4. Cache result in sessionStorage; clear hash from URL
  5. Open vault in read-only mode → normal flow from here

  Recipient browser (refresh / return in same tab):
  1. sessionStorage already has { vault_id, read_key }
  2. No API call — straight to opening the vault
```

### Why no new server endpoint

The existing `/api/transfers` already provides everything needed:

| Capability | Provided by |
|---|---|
| Store encrypted blob | `POST /api/transfers` |
| Resolve token → blob | `GET /api/transfers/{token}` |
| Author-controlled TTL | Existing `expires_at` field |
| Author-controlled use count | Existing `uses_max` / `uses_remaining` fields |
| Token revocation | `DELETE /api/transfers/{token}` |
| Validity check without consuming a use | `GET /api/transfers/check_token/{token}` |

The "file" being stored is just a ~60-byte JSON blob `{ vault_id, read_key }`. Same crypto, same store, same lifecycle as a regular file send. Author-controlled TTL/use-count are now features, not leakage.

### Three sharing tiers

```
  Tier 1: /en-gb/app#[full-vault-key]      or  /en-gb/vault#[full-vault-key]
          → read + write recipient (current model)

  Tier 2: /en-gb/app#ro-[friendly-token]   or  /en-gb/vault#ro-[friendly-token]
          → read-only recipient (NEW)
          → token resolves via SG/Send API → encrypted blob → { vault_id, read_key }
          → author controls expiry + use-count + revocation per token

  Tier 3: /en-gb/app  (no hash, hashless entry page)
          → recipient pastes credentials themselves
          → useful for credentials shared verbally / via password manager
          → useful for recovery / re-auth after clearing storage
```

### Edge cases

- **Token loss (vault-side list corrupted):** Author can no longer see issued tokens in the dashboard, but tokens continue to work until natural expiry. Authors who remember a token string can still revoke via direct API call. Worst case: tokens persist until the TTL set at creation time. Acceptable — this is recovery degradation, not a security failure.
- **Multi-device revocation sync:** The vault-side file is the convenience UI; the API is the source of truth. If author A revokes from device 1 and device 2 hasn't pulled yet, device 2 shows a stale "active" entry — but the actual `GET /api/transfers/{token}` returns 404, so any recipient using the link gets denied. The vault file converges on next pull.
- **Same token on both pages.** `/en-gb/vault#ro-...` opens read-only in vault mode; `/en-gb/app#ro-...` opens read-only in app mode. Author can pick which experience to deliver. The "Copy link" button could let the author choose, or default to `/en-gb/app` (most likely the intended recipient experience).

## Capability 2 — `.vault/owner/*` Owner-Only Namespace

### Why this is required

The readonly-tokens file (and any future owner-only metadata) cannot be encrypted with **only** the standard vault read-key. Any read-only recipient — anyone holding a `ro-` token — could decrypt it using the read-key they were given via the token resolution flow. They would see every other ro-token issued for the vault, plus labels, notes, and recipient hints. That's a privacy + token-enumeration leak.

The fix: a second layer of encryption keyed by something only the **full** vault-key holder can derive.

```
  .vault/owner/readonly-tokens.json
       │            │
       │            └─ inner encryption: AES-256-GCM with vault-secret-key
       │               (derived deterministically from full vault-key)
       │
       └─ outer encryption: standard vault read-key (applied on commit, like every file)
```

Read-only clients see the file exists in the listing but the bytes never decrypt.

### Deterministic key derivation

```js
vault_secret_key = HKDF-SHA256(
    input_key = vault_key_bytes,
    salt      = vault_id_bytes,             // vault-bound — same vault-key on a different vault
                                            //   produces a different secret-key
    info      = "sgraph-vault-secret-v1",   // domain-separation + version tag
    length    = 32                          // AES-256-GCM key length
)
```

- **Deterministic:** any device with the vault-key derives the same secret-key. No distribution, no out-of-band exchange.
- **Vault-bound (via salt):** the same vault-key cannot accidentally produce the same secret-key for a different vault.
- **Domain-separated (via info):** future derived keys (signing, other secret namespaces) won't collide.
- **Versioned (via "-v1"):** future crypto upgrades stay non-confusable.

Per-write AES-GCM IVs remain random (stored alongside the ciphertext).

### The namespace pattern

Every file under `.vault/owner/` receives the inner encryption layer on commit. The crypto layer detects the path prefix and applies it transparently. Read flow detects the prefix, attempts the inner decrypt, fails gracefully with a `secret-locked` marker when the user is read-only (don't even try to decrypt — show as opaque).

```
  .vault/owner/readonly-tokens.json    ← this proposal
  .vault/owner/author-notes.md         ← future: private vault-author notes
  .vault/owner/llm-api-keys.json       ← future: secrets the app needs at deploy time
  .vault/owner/collaborator-list.json  ← future: who has been granted access
```

### Schema (inner plaintext, after both layers are decrypted)

```json
{
  "tokens": [
    {
      "token":      "ro-coral-stamp-1234",
      "label":      "Patient preview link",
      "created_at": "2026-05-12T14:30:00Z",
      "expires_at": "2026-05-19T14:30:00Z",
      "uses_max":   100,
      "note":       "Shared with Dr. Smith's team"
    },
    {
      "token":      "ro-maple-leaf-9012",
      "label":      "Journalist embargo",
      "created_at": "2026-05-12T15:00:00Z",
      "expires_at": null,
      "uses_max":   null,
      "note":       "Permanent, for press team"
    }
  ]
}
```

### Server-side knowledge boundary

| Server knows | Vault knows (encrypted, only author can read) |
|---|---|
| Encrypted payload per ro-token | List of MY active ro-tokens |
| TTL + use-count metadata per token | Label / note / created-at for each |
| Cannot link tokens to a vault | Who I shared each one with |
| Cannot list "all tokens for vault X" | Full revocation control + audit trail |

The server never learns the relationship between any ro-token and any vault. A breach of the server reveals encrypted blobs, not vault membership.

## Capability 3 — File-Access Visual Cues

A vault with mixed access scopes is a privacy minefield without good UI. A user editing a file should know:

1. **What level of access do I have?** (RW owner vs RO viewer)
2. **What's the access scope of THIS file?** (visible to all, owner-only)
3. **Who else can see what I'm editing?** (other owners, RO peers, nobody)

Today none of this is surfaced. The proposed visual cues make it impossible to miss.

### Per-user persistent indicator (vault header)

The vault header always shows the current user's access level:

```
  Owner (full vault key):
  ┌─────────────────────────────────────────────────────────────────┐
  │  SG/Vault  HealthScore   🔓 Owner   ↻   [Open App]   Settings    │
  └─────────────────────────────────────────────────────────────────┘

  Read-only viewer (ro-token):
  ┌─────────────────────────────────────────────────────────────────┐
  │  SG/Vault  HealthScore   👁 Read-only — cannot modify             │
  └─────────────────────────────────────────────────────────────────┘
```

The read-only badge replaces the existing "Read-only" badge (used today for missing access-key) — but means a different, stronger thing: the vault was opened with a read-key, not just lacking a write token.

### Per-file badges in the file list

```
  Owner view of file list:
  ┌─────────────────────────────────────────────────────┐
  │ Files in HealthScore                                  │
  ├─────────────────────────────────────────────────────┤
  │ 📄 app.html                  🌐 Visible to all     │
  │ 📁 _common/                                         │
  │   📄 reset.css               🌐 Visible to all     │
  │   📄 utils.js                🌐 Visible to all     │
  │ 📁 .vault/                                          │
  │   📄 app.json                🌐 Visible to all     │
  │   📄 settings.json           🌐 Visible to all     │
  │   📁 owner/                  🔒 Owner-only         │
  │     📄 readonly-tokens.json  🔒 Owner-only         │
  │     📄 author-notes.md       🔒 Owner-only         │
  └─────────────────────────────────────────────────────┘

  Read-only viewer of the same vault:
  ┌─────────────────────────────────────────────────────┐
  │ Files in HealthScore        👁 Read-only access      │
  ├─────────────────────────────────────────────────────┤
  │ 📄 app.html                                         │
  │ 📁 _common/                                         │
  │   📄 reset.css                                      │
  │   📄 utils.js                                       │
  │ 📁 .vault/                                          │
  │   📄 app.json                                       │
  │   📄 settings.json                                  │
  │   📁 owner/                  🔒 Not accessible     │
  └─────────────────────────────────────────────────────┘
```

The owner sees green "Visible to all" badges as a constant reminder that those files are NOT private. The RO viewer sees `.vault/owner/` listed but marked inaccessible — transparency about what exists, even though contents are sealed.

(Alternative for RO viewer: hide `.vault/owner/` entirely. Trade-off: less transparency, but cleaner. **Recommendation:** show the directory but mark it as inaccessible — users notice if a directory "disappears" between two access levels, and that's confusing.)

### File-open banner (the moment-of-edit cue)

When a file is opened, a thin banner above the content shows its access scope. This is the most important cue — it's visible exactly when the user is about to read or modify content.

```
  Owner viewing owner-only file:
  ┌─────────────────────────────────────────────────────┐
  │ 🔒 author-notes.md                                   │
  │ Only visible to vault owners. Read-only viewers     │
  │ with an ro-token cannot see this content.           │
  ├─────────────────────────────────────────────────────┤
  │ [file content + edit controls]                      │
  └─────────────────────────────────────────────────────┘

  Owner viewing a normal file:
  ┌─────────────────────────────────────────────────────┐
  │ 🌐 app.html                                          │
  │ Visible to everyone with vault access, including    │
  │ read-only viewers with an ro-token.                 │
  ├─────────────────────────────────────────────────────┤
  │ [file content + edit controls]                      │
  └─────────────────────────────────────────────────────┘

  RO viewer reading any (accessible) file:
  ┌─────────────────────────────────────────────────────┐
  │ 👁 app.html — Read-only, you cannot modify          │
  ├─────────────────────────────────────────────────────┤
  │ [file content; edit controls disabled with tooltip] │
  └─────────────────────────────────────────────────────┘

  RO viewer clicks an .vault/owner/ file:
  ┌─────────────────────────────────────────────────────┐
  │ 🔒 readonly-tokens.json — Not accessible            │
  │ This file is encrypted with the vault owner's key.  │
  │ Your read-only token cannot decrypt it.             │
  ├─────────────────────────────────────────────────────┤
  │ [no content shown]                                  │
  └─────────────────────────────────────────────────────┘
```

The owner-only banner is the most important: it tells the owner that what they're typing **won't** leak to ro-token recipients, which is exactly the assurance they need to use the namespace confidently.

### Issue-time preview (in the "Create read-only link" flow)

When creating a new ro-token, show what the recipient will see:

```
  ┌─────────────────────────────────────────────────────────────────┐
  │  Create read-only link                                          │
  ├─────────────────────────────────────────────────────────────────┤
  │  Label:    [Patient preview link              ]                  │
  │  Expires:  [7 days  ▼]                                           │
  │  Max uses: [100      ]                                           │
  │  Note:     [Shared with Dr. Smith's team      ]                  │
  │                                                                  │
  │  Recipients with this link will see:                            │
  │  ✓ app.html, _common/*, .vault/app.json, .vault/settings.json   │
  │                                                                  │
  │  Recipients will NOT see:                                       │
  │  ✗ .vault/owner/readonly-tokens.json                            │
  │  ✗ .vault/owner/author-notes.md                                 │
  │                                                                  │
  │  [Create link]                              [Cancel]            │
  └─────────────────────────────────────────────────────────────────┘
```

The preview makes the access boundary visible at the moment the author commits to sharing — no surprises later.

### Implementation in `vault-shell` and friends

The cue rendering hooks into existing components:

- **`vault-header`** — adds an access-mode badge (owner / read-only) sourced from `sessionStorage.sgraphVault.credentials.mode`. Replaces the current "Read-only" badge meaning.
- **`send-browse`** — file-list renderer checks each path against `/^\.vault\/owner\//`; renders the appropriate badge. RO mode also gates "open" clicks for these files.
- **New `vault-file-banner` component** (~80 LOC) — rendered above the file content area in `send-browse`. Reads access mode + file path, renders one of the four banner variants.
- **`vault-settings-readonly-links`** — new section on the settings page wiring through `.vault/owner/readonly-tokens.json` (~150 LOC).

## Migration Path and Compatibility

1. **Existing vaults continue to work unchanged.** No data migration needed. Vaults without `.vault/owner/*` just don't have anything to inner-decrypt.
2. **First ro-token created → `.vault/owner/readonly-tokens.json` materialises.** Until then, the directory doesn't exist.
3. **Existing vault-shell users continue to default to read+write mode.** The access mode is determined by which credentials were supplied (full key vs ro-token), not by config.
4. **Visual cues degrade gracefully.** If `.vault/` doesn't exist yet, banners simply don't render. If owner-only badges aren't present, the existing UI continues.

## Open Questions

1. **Hide vs show `.vault/owner/` for read-only viewers.** Current proposal: show the directory but mark it as inaccessible. Trade-off: transparency vs noise. Alternative: hide entirely. **Recommendation:** show as inaccessible — but invertible later if user testing shows it's confusing.

2. **Token lifecycle: delete from vault-list immediately on revoke, or mark as revoked?** Marking as revoked preserves the audit trail (who you shared with, when, why) at the cost of an ever-growing list. Deleting is cleaner. **Recommendation:** delete on revoke; export "audit log" feature if/when needed.

3. **"Copy link" default URL: `/en-gb/app` or `/en-gb/vault`?** Author decides per token? Or fixed default? **Recommendation:** default to `/en-gb/app` (cleanest recipient UX); add a "Copy as vault URL" secondary action.

4. **Access-key (`localStorage`) scope: per-origin or per-vault?** A user managing tokens from multiple administrators benefits from per-vault keying (`accessKey:[vaultId]`). One token spanning many vaults benefits from per-origin. **Recommendation:** per-vault keying — safer default, more useful in multi-author scenarios.

5. **Visual cue colours and icons.** ASCII mockups use 🔒 / 🌐 / 👁 — should the production UI use these, or rely purely on text + colour (more accessible)? **Recommendation:** colour + icon + text label for max clarity; let user-testing prune.
