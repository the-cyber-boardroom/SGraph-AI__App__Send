# Architect Review — Access Key Architecture

**Role:** Architect
**Team:** Explorer
**Version:** v0.27.34
**Date:** 2026-05-12
**Scope:** API-only review of how the access key works at `send.sgraph.ai/api/docs` — what it captures, how it is validated, and how it gates the two consumption paths (file transfers and vault operations).
**Out of scope:** UI flows, sgit CLI, vault read/write key cryptography (covered by `team/roles/librarian/reality/vault/`).

---

## 1. Executive Summary

The "access key" in SGraph Send is a **named, server-side token** managed by the Admin Lambda and validated by the User Lambda on every gated request. It is not a cryptographic secret tied to a user identity; it is a **human-readable label** (e.g. `community-x`) backed by a metered record stored in the MGraph-AI Cache Service.

Its three responsibilities are:

1. **Authorise** specific write paths on the public API (transfer creation/upload/completion; vault writes; presigned multipart initiation).
2. **Meter** usage — every successful transfer completion (and every download-page "validate" call) consumes one unit and is recorded against an IP hash.
3. **Capture light analytics** — IP hash, action label, and associated `transfer_id` are stored as child events under the token record.

It is deliberately not used for:

- **Reads.** Transfer downloads, vault reads, vault list/health, and `check-token` are all public.
- **Cryptographic authorisation of vault writes.** Vault writes require the access token *plus* a separate `x-sgraph-vault-write-key` (cryptographic). The access token is the rate/quota gate; the write key is the authorisation gate.
- **User identity.** A token is shared across whoever holds it; there is no per-user provisioning, no rotation, no expiry.

The system is intentionally minimal: a single named-token primitive with a usage counter and a status. There is no scope, no expiry, no per-endpoint metering. This keeps the model simple but means the same token grants the same rights to every gated endpoint — transfers and vault writes alike.

## 2. What an Access Key Is (Data Model)

### 2.1 The token record

Defined by `Schema__Token__Metadata` at `sgraph_ai_app_send/lambda__admin/schemas/Schema__Token__Metadata.py:11`:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `token_name` | `Safe_Str__Id` | — | The literal value clients send in the header. Human-readable. Primary key. |
| `usage_limit` | `Safe_UInt` | `50` | Max uses before the token auto-exhausts. `0` = unlimited. |
| `usage_count` | `Safe_UInt` | `0` | Monotonically incrementing counter. |
| `status` | `Safe_Str__Id` | `'active'` | One of `active`, `exhausted`, `revoked`, `expired`. |
| `created_by` | `Safe_Str__Id` | — | Free-text admin identifier. |
| `metadata` | `dict` | `{}` | Untyped bag — typically `{batch_id, notes, community_name}`. |

### 2.2 Child events (`usage_events`)

Each successful or rejected use produces a child record under the token (`Send__Cache__Client.token__use`, `sgraph_ai_app_send/lambda__admin/service/Send__Cache__Client.py:99`):

| Field | Source | Meaning |
|---|---|---|
| `event_id` | 8-byte random hex | Event primary key. |
| `ip_hash` | SHA-256 of `request.client.host` | Caller's IP, hashed (no salt currently in the route — see §7). |
| `action` | Request body | Free-text label, e.g. `page_opened`, `upload_completed`. |
| `transfer_id` | Request body | Associated transfer when applicable; empty otherwise. |
| `success` | Server-derived | `False` if the use was rejected by limit/status. |
| `rejection_reason` | Server-derived | `not_found`, `revoked`, or `exhausted`. |

### 2.3 Persistence

- **Backend:** MGraph-AI Cache Service (`mgraph-ai-service-cache-client`), via `Send__Cache__Client`.
- **Namespace:** `'tokens'` (fixed).
- **Strategy:** `key_based` — the `token_name` is simultaneously the cache key, the `file_id`, and the `json_field_path` discriminator (`Send__Cache__Client.py:62`).
- **Logical layout:** `tokens/data/key-based/{token_name}/` with child path `usage_events/{event_id}`.
- **TTL:** None. The `expired` status exists in the enum but no code path sets it.

## 3. The Wire Contract (How a Caller Presents an Access Key)

### 3.1 Header (primary)

```
x-sgraph-access-token: <token_name>
```

Defined at `sgraph_ai_app_send/lambda__user/user__config.py:21`:

```python
HEADER__SGRAPH_SEND__ACCESS_TOKEN = 'x-sgraph-access-token'
```

> **Discrepancy noted.** The reality document `team/roles/librarian/reality/send-api/index.md` and `identity/index.md` refer to this header as `x-sgraph-send-access-token`. The actual code uses `x-sgraph-access-token`. Both Routes__Transfers and Routes__Vault__Pointer read the constant (not the literal string), so the code is internally consistent — but the reality doc is wrong and should be corrected. (See §8.)

### 3.2 Query parameter (fallback)

```
?access_token=<token_name>
```

Read in `Routes__Transfers.check_access_token` (`sgraph_ai_app_send/lambda__user/fast_api/routes/Routes__Transfers.py:37`). Useful for share-URL contexts where headers are inconvenient. **Beware:** this puts the token in URLs (browser history, logs, referrers). It is acceptable for the named-token model (low secrecy) but should not be reused if access keys ever become cryptographic.

### 3.3 MCP tool parameter

For MCP-exposed endpoints, the token may be passed as a function argument (`access_token: str = ''`) — see `Routes__Transfers.py:89` and the MCP wiring at `Fast_API__SGraph__App__Send__User.py:142`, which whitelists `x-sgraph-access-token` in `forward_headers`.

### 3.4 Env-var fallback (dev mode)

If no `admin_service_client` is configured *and* `SGRAPH_SEND__ACCESS_TOKEN` is set in the environment, the User Lambda accepts any token equal to that env-var value. If neither admin service nor env var is configured, every request is accepted (no enforcement). This is a development convenience and is *not* the production code path.

## 4. Validation Path

There is **no global FastAPI middleware** for access tokens. The User Lambda explicitly disables it (`Fast_API__SGraph__App__Send__User.py:54`):

```python
_.enable_api_key = False
```

Each gated route calls `self.check_access_token(request)` inline. The two implementations (`Routes__Transfers.py:37` and `Routes__Vault__Pointer.py:53`) are near-identical and follow this sequence:

```
1. Extract candidate token from:
   header  → query param → MCP arg → env var

2. If admin_service_client is configured:
   a. token_lookup(token)        → HTTP call to Admin Lambda
   b. 404 → raise 401 "Invalid access token"
   c. status != 'active' → raise 401 "Access token <status>"
   d. exception → raise 503 "Token validation service unavailable"
   e. otherwise → return token_name

3. Otherwise (dev mode):
   a. compare against SGRAPH_SEND__ACCESS_TOKEN env var
   b. mismatch → raise 401
   c. match (or unset) → return token_name (or None)
```

**Architectural consequences:**

- **Inter-Lambda dependency.** Every gated request on the User Lambda triggers an HTTP call to the Admin Lambda. If Admin is down, User returns 503 on all gated routes. There is no local caching of token state.
- **Per-route enforcement.** Adding a new gated endpoint requires the implementer to remember to call `check_access_token`. There is no decorator, no dependency-injection guard, no schema-driven enforcement. This is a foot-gun.
- **Two duplicated implementations.** `Routes__Transfers.check_access_token` and `Routes__Vault__Pointer.check_access_token` are independent copies. Drift between them is possible (and would be a security regression). Worth extracting to a shared utility.

## 5. How the Access Key Applies to File Uploads (Transfer Flow)

Routes are registered without an explicit prefix in `Routes__Transfers.py`; the reality doc shows them mounted under `/api/transfers/*`.

| Method | Path | Gated? | Consumes a use? | Notes |
|---|---|---|---|---|
| `POST` | `/api/transfers/create` | **Yes** | No | Validates only. Issues `transfer_id`. |
| `POST` | `/api/transfers/upload/{transfer_id}` | **Yes** | No | Validates only. Writes ciphertext. |
| `POST` | `/api/transfers/complete/{transfer_id}` | **Yes** | **Yes** — `action='upload_completed'` | Records a usage event with the caller's IP hash and the transfer ID. **Does not return `token_name` to the client** (security fix at `Routes__Transfers.py:137`). |
| `GET` | `/api/transfers/info/{transfer_id}` | No | No | Public metadata. |
| `GET` | `/api/transfers/download/{transfer_id}` | No | No | Public — ciphertext is opaque. |
| `GET` | `/api/transfers/download-base64/{transfer_id}` | No | No | Public. |
| `DELETE` | `/api/transfers/delete/{transfer_id}` | No (uses separate `x-sgraph-transfer-delete-auth`) | No | Out-of-band delete auth. |
| `GET` | `/api/transfers/check-token/{token_name}` | No | No | Read-only lookup. Returns `{valid, status, remaining}`. Used by the download page to display token state. |
| `POST` | `/api/transfers/validate-token/{token_name}` | No (token in path) | **Yes** — `action='page_opened'` | Used by the download page to record a visit. |

### What the access key actually gates (transfer side)

1. **Producer-side write paths only.** The sender needs the token to create, upload, and complete a transfer. The receiver does **not** need it to download — the decryption key (out-of-band) is sufficient.
2. **Metering is at completion, not at upload.** A producer can call `create` and `upload` repeatedly with the same valid token without consuming uses; the counter only increments on `complete`. Practically this means quota enforcement is at the "finished transfer" boundary, which is correct for billing-style models.
3. **A second use is consumed on the recipient's download page** via `validate-token`. This is a soft analytics signal, not an authorisation gate (download itself is public). It means a single transfer typically consumes **two** uses: one for the upload completion, one for the first visit to the download page.

### What it does *not* gate

- Download of ciphertext (intentional — zero-knowledge model).
- Download metadata via `/info` (public — leaks size, MIME, timestamps).
- Deletion (uses a separate cryptographic auth header — see §7).

## 6. How the Access Key Applies to Vault Usage

Routes registered under `/api/vault/*` (`Routes__Vault__Pointer.py`).

| Method | Path | Access token? | Write key? | Consumes a use? | Notes |
|---|---|---|---|---|---|
| `PUT` | `/api/vault/write/{vault_id}/{file_id}` | **Yes** | **Yes** | No | Writes encrypted blob. |
| `GET` | `/api/vault/read/{vault_id}/{file_id}` | No | No | No | Public — ciphertext. |
| `GET` | `/api/vault/read-base64/{vault_id}/{file_id}` | No | No | No | Public. |
| `DELETE` | `/api/vault/delete/{vault_id}/{file_id}` | **Yes** | **Yes** | No | |
| `POST` | `/api/vault/batch/{vault_id}` | **Conditional** | **Conditional** | No | Read-only batches bypass auth; any write op requires both headers. |
| `GET` | `/api/vault/list/{vault_id}` | No | No | No | Public listing (filenames are ciphertext-derived IDs). |
| `GET` | `/api/vault/health/{vault_id}` | No | No | No | Unauthenticated warmup. |
| `GET` | `/api/vault/public-info/{vault_id}` | No | No | No | Public-vault metadata. |
| `GET` | `/api/vault/zip/{vault_id}` | **Yes** | **Yes** | No | Bulk export. |
| `DELETE` | `/api/vault/destroy/{vault_id}` | **Yes** | **Yes** | No | Tear down whole vault. |

### What the access key actually gates (vault side)

1. **Vault writes require *two* credentials: an access token *and* a write key.** They have different semantics:
   - **`x-sgraph-access-token`** — server-side, named, metered (but *not* metered on vault ops), quota-bearing. Authority comes from "the admin minted you this token."
   - **`x-sgraph-vault-write-key`** — client-side, cryptographic, derived from the user's passphrase or vault token (see `team/roles/librarian/reality/vault/index.md`). Authority comes from "you know the secret that produces this key, and its hash matches what we stored."
   The access token is a *gatekeeper* (rate/quota/blocklist); the write key is the actual *authorisation*. Holding only one does not let you write.
2. **Reads are completely public.** This is the zero-knowledge property: blobs are opaque, vault IDs are sparse, so no auth is needed to read.
3. **Vault operations do not consume token uses.** The token is validated on every gated vault call but `token_use` is never invoked from `Routes__Vault__Pointer`. A token with `usage_limit=1` can therefore back unlimited vault writes for its lifetime, but only one transfer completion. (See §7 — this is a notable inconsistency.)

## 7. Findings and Concerns

### 7.1 The token is metered for transfers but not for vaults

`Routes__Transfers.complete_transfer` records a usage event (`Routes__Transfers.py:140`). No vault route does. Consequences:

- A token nearing exhaustion still permits unlimited vault writes — exhaustion only blocks transfer completion.
- Two products share one quota primitive with two semantics. Operators reading "remaining: 0" cannot tell whether the holder is locked out of vaults or not.
- Analytics on the token record show transfer activity only; vault usage by the same token is invisible.

**Recommendation:** Decide explicitly whether vault operations should count. If yes, add `token_use(action='vault_write', vault_id=...)` to the write/delete/zip/destroy/batch paths. If no, document the asymmetry and consider whether a different primitive (e.g. a vault-scoped allowance) is needed.

### 7.2 Token name in query parameter is a leakage risk

`access_token` as a query parameter (`Routes__Transfers.py:39`) ends up in browser history, server logs, and `Referer` headers. The security-fix comment at `Routes__Transfers.py:137` already shows awareness of token leakage in shareable URLs. The query-param fallback contradicts that fix.

**Recommendation:** Either remove the query-param path or restrict it to MCP-only contexts.

### 7.3 IP hash has no salt

The handler hashes `request.client.host` with bare SHA-256 before storing it. CLAUDE.md rule §12 mandates "SHA-256 with **daily salt**". The implementation in the transfer route applies hashing inline; no daily-salt rotation is visible.

**Recommendation:** Centralise IP hashing in a helper that applies the daily salt described in CLAUDE.md, and use that helper from every route that records a usage event.

### 7.4 Two copies of `check_access_token`

`Routes__Transfers.check_access_token` and `Routes__Vault__Pointer.check_access_token` are near-duplicates. Any future fix (rate limit, cache, audit log, stricter status semantics) has to be applied twice. This is a footgun and a likely source of future drift.

**Recommendation:** Extract to `sgraph_ai_app_send/lambda__user/middleware/Access_Token__Validator.py` (or similar) and call it from both routes. Consider exposing it as a FastAPI dependency (`Depends(...)`) rather than an inline method call, so missing-the-call defects become structural rather than reviewer-dependent.

### 7.5 No expiry, no rotation, no scope

The schema reserves `status='expired'` but no code path sets it. There is no API to rotate a token (must `revoke` + `create` a new name). There is no way to scope a token to "transfers only" or "one specific vault." Every token grants identical rights on every gated endpoint.

**Recommendation:** Either accept this consciously and document it, or extend the schema with `expires_at`, `scopes: List[Safe_Str__Id]`, and enforcement in `check_access_token`. The simplest first step is `expires_at` — a TTL is cheap and would let community tokens self-retire.

### 7.6 Inter-Lambda call on every gated request

Every transfer create/upload/complete and every vault write triggers an HTTP `token_lookup` to the Admin Lambda. Implications:

- **Latency.** Every gated call pays a cross-Lambda RTT.
- **Coupling.** Admin Lambda availability is a hard dependency for the User Lambda's write paths.
- **No deduplication.** Three sequential calls (create → upload → complete) for the same token do three separate lookups.

**Recommendation:** Add a small in-process LRU cache keyed by `token_name`, with a short TTL (10–30s) and explicit invalidation on revoke. The cache hit need not validate the counter; just the `status` and existence. This is a Villager-style hardening — record it but defer.

### 7.7 Header name mismatch with reality doc

The reality doc refers to `x-sgraph-send-access-token`; the code uses `x-sgraph-access-token`. The Librarian's reality document is meant to be code-verified. This is a small drift but worth fixing in the same commit family that lands this review.

**Recommendation:** Update `team/roles/librarian/reality/send-api/index.md` and `team/roles/librarian/reality/identity/index.md` to match the code constant.

### 7.8 No token usage recorded for `upload` or `create`, only `complete`

This is probably correct (avoids charging users for half-finished transfers), but it means:

- An attacker holding a valid token can call `create` + `upload` many times without consuming uses, filling storage with orphaned half-transfers.
- There is no per-token rate limit on the unmetered steps.

**Recommendation:** Add a separate rate-limit primitive on `create` and `upload` keyed by `token_name`, or accept the risk and rely on storage TTL + orphan cleanup.

### 7.9 Token validation failure mode is fail-closed for production but fail-open in dev

If `admin_service_client is None` and `SGRAPH_SEND__ACCESS_TOKEN` is unset, `check_access_token` returns the candidate token (or `None`) without rejecting. This is fine for local development but is a sharp edge: a misconfigured staging environment that fails to wire the admin client *and* forgets the env var becomes an open Lambda.

**Recommendation:** Add a startup-time assertion that, in non-dev environments, either `admin_service_client` is set or `SGRAPH_SEND__ACCESS_TOKEN` is set. Fail to boot otherwise.

## 8. Summary of What the Access Key Captures

In one paragraph: an access key is a **named, server-side, named-token primitive** with a `usage_limit` quota and a status (`active|exhausted|revoked|expired`). It captures, per use, the caller's IP hash, the action label (`upload_completed`, `page_opened`), and the associated `transfer_id`. It is presented via an HTTP header (or query param / MCP arg / env-var fallback), validated on every gated route by an inter-Lambda call to the Admin Lambda, and consumed (counter incremented) only on transfer completion and on download-page validation. It gates transfer producer-side endpoints, vault write endpoints, and presigned-upload endpoints. It does **not** gate any read path, does **not** carry user identity, has no expiry or scope, and — notably — does **not** consume a use on vault operations even though it is required for them.
