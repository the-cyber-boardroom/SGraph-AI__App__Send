## 1. Executive Summary

Container support for the **user lambda** (`sgraph_ai_app_send/lambda__user/`) **already exists and is in active CI**. The same FastAPI application that runs inside AWS Lambda runs unchanged inside a Docker container via a thin packaging layer (`sgraph_ai_app_send__docker/`). The container exposes the Send API on port `8080` under uvicorn, supports three storage backends (memory / disk / S3), and is built, smoke-tested, and pushed to ECR by the GitHub Actions pipeline on every successful main-branch build.

What this document covers:

- The packaging layer that turns the User Lambda into a container image
- Storage backend wiring (memory, disk/mounted-volume, S3) and how it is selected
- The CI pipeline that builds and publishes the image
- The test suite that verifies container behaviour
- What is **NOT** yet wired (gaps for follow-up)

This is a factual inventory of what is in the codebase at `v0.27.44`. Anything marked **PROPOSED** does not exist yet.

## 2. The Container Packaging Layer

The user lambda's FastAPI class — `Fast_API__SGraph__App__Send__User` — is reused unchanged. The container variant is a thin subclass plus a uvicorn factory.

### 2.1 Package layout

```
sgraph_ai_app_send__docker/
├── __init__.py
├── Dockerfile
├── app.py                                 # uvicorn factory entry point
├── Fast_API__SGraph__Send__Container.py   # subclass of the User Lambda FastAPI
└── provision_ec2.py                       # sg-send-ec2 CLI (EC2 host provisioning)
```

### 2.2 `Fast_API__SGraph__Send__Container`

File: `sgraph_ai_app_send__docker/Fast_API__SGraph__Send__Container.py`

- Extends `Fast_API__SGraph__App__Send__User` — **same routes, same storage, same schemas as the Lambda**.
- Adds two container-specific concerns:
  1. **Optional global auth middleware** (`enable_global_auth`, lines 22–31). When `SEND__ENABLE_AUTH=true` or `SGRAPH_SEND__ACCESS_TOKEN` is set, an `x-sgraph-access-token` header/cookie check is enforced via `Middleware__Check_API_Key` from `osbot-fast-api`.
  2. **Static UI mounting** (`setup_static_routes`, lines 44–58). Mounts the versioned user UI at `/console/v.../start.html` and redirects `/` to the latest version. Also wires `Routes__Set_Cookie` so an operator can set the access-token cookie from a form (excluded from auth enforcement).

### 2.3 Uvicorn factory

File: `sgraph_ai_app_send__docker/app.py`

```python
def create_app():
    with Fast_API__SGraph__Send__Container() as _:
        _.setup()
        return _.app()
```

This is invoked by uvicorn with the `--factory` flag — no module-level side effects, no Lambda Mangum handler. The same FastAPI instance can therefore be served by any ASGI host (uvicorn, hypercorn, gunicorn-with-uvicorn-workers).

### 2.4 The Dockerfile

File: `sgraph_ai_app_send__docker/Dockerfile` (25 lines)

| Aspect | Detail |
|---|---|
| Base image | `python:3.12-slim` |
| Workdir | `/app` |
| Copied in | `pyproject.toml`, `README.md`, `sgraph_ai_app_send/`, `sgraph_ai_app_send__docker/`, the three user UIs (`user`, `vault`, `workspace`). The admin UI is **stubbed** with an empty `__init__.py` (line 12) so the package imports cleanly without the admin assets. |
| Install | `pip install -e .` then `pip install uvicorn` |
| Volume | `/data` is created (line 17) as the disk-storage mount point |
| Port | `8080` (line 19) |
| Default env | `SEND__STORAGE_MODE=memory`, `SEND__DISK_PATH=/data` |
| CMD | `uvicorn sgraph_ai_app_send__docker.app:create_app --factory --host 0.0.0.0 --port 8080` |

**Default mode is `memory`.** To get persistence, the operator must override `SEND__STORAGE_MODE=disk` and mount a host directory at `/data` (or override `SEND__DISK_PATH`).

### 2.5 `.dockerignore`

Excludes `.git`, `.github`, `tests/`, `team/`, `library/`, `venv`, `pytest_cache`, and the admin UI assets — keeps the image small and free of repo metadata.

## 3. Storage Backend Wiring

The single most important architectural point about the container is that **storage selection is policy-driven, not code-driven**. The container image is identical regardless of backend; the runtime environment chooses one of three modes.

### 3.1 `Send__Config` — the auto-detector

File: `sgraph_ai_app_send/lambda__user/storage/Send__Config.py`

Auto-detection priority (`determine_storage_mode`, lines 37–47):

1. **Explicit override** — `SEND__STORAGE_MODE` env var (`memory` | `disk` | `s3`)
2. **AWS credentials present** → `S3` (via `aws_config.aws_configured()`)
3. **`SEND__DISK_PATH` set** → `DISK`
4. **Otherwise** → `MEMORY`

Factory (`create_storage_backend`, lines 68–77):

| Mode | Backend class | Source |
|---|---|---|
| `MEMORY` | `Storage_FS__Memory` | `memory-fs` |
| `DISK` | `Storage_FS__Local_Disk(root_path=disk_path)` | `memory-fs` (folder auto-created via `folder_create`) |
| `S3` | `Storage_FS__S3(s3_bucket=...).setup()` | local class, SnapStart-safe |

A second factory `create_public_vault_storage_backend` (lines 79–83) returns an S3 backend for the optional **public vault** bucket when `SEND__PUBLIC_VAULT__S3_BUCKET` is set, otherwise `None`.

### 3.2 Container-specific implications

**Memory mode** (in-container, ephemeral):
- No volume needed. Everything lives in process memory.
- Suitable for local dev, ephemeral demo containers, CI smoke tests.
- Container restart = total data loss.

**Disk mode** (in-container or mounted volume):
- Default path: `/data` (constant `SEND__DISK_PATH__DEFAULT`, line 20 of `Send__Config.py`)
- Path is overridable via `SEND__DISK_PATH`
- Folder is auto-created at startup (`folder_create` call in `create_storage_backend`, line 71)
- Operator pattern: `docker run -v /host/path:/data -e SEND__STORAGE_MODE=disk send:latest`
- Survives container restart as long as the host path persists

**S3 mode** (any container with AWS credentials):
- Triggered automatically if AWS credentials are available, or explicitly via `SEND__STORAGE_MODE=s3`
- Bucket name: explicit (`SEND__S3_BUCKET`) or derived as `{account_id}--sgraph-send-transfers--{region}`
- Used by Lambda, but also valid for Fargate / ECS / EC2 / GCP containers with IAM roles
- SnapStart-safe: the boto3 client is created lazily on first use, not at process init (see `Storage_FS__S3._s3()`, lines 23–26)

### 3.3 Environment-variable contract

| Variable | Purpose | Default |
|---|---|---|
| `SEND__STORAGE_MODE` | Force a backend (`memory` / `disk` / `s3`) | auto-detect |
| `SEND__DISK_PATH` | Root dir for disk mode | `/data` |
| `SEND__S3_BUCKET` | Override S3 bucket | `{account}--sgraph-send-transfers--{region}` |
| `SEND__PUBLIC_VAULT__S3_BUCKET` | Enables public vault routing | unset |
| `SEND__ENABLE_AUTH` | Force enable container global auth | `false` |
| `SGRAPH_SEND__ACCESS_TOKEN` | Access token value; if set, auth is enabled even without `SEND__ENABLE_AUTH` | unset |

## 4. CI Pipeline — Build, Push, Smoke

File: `.github/workflows/ci-pipeline.yml`, job **`docker-build-push`** (lines 181–233)

The job runs on `ubuntu-latest`, depends on `check-aws-credentials` and `increment-tag`, and is gated by `if: needs.check-aws-credentials.outputs.has-credentials == 'true'`. Steps:

1. Checkout + branch update (`OSBot-GitHub-Actions/git__update_branch`)
2. **Configure AWS credentials** from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` secrets
3. **Login to ECR** (`aws-actions/amazon-ecr-login@v2`)
4. **Ensure ECR repository exists** — auto-creates `${{ env.ECR_REPO_NAME }}` (`sg-send`) with `MUTABLE` tags if missing (lines 203–206)
5. **Read version** from `sgraph_ai_app_send/version`
6. **Build and push** via `docker/build-push-action@v5`, context `.`, file `sgraph_ai_app_send__docker/Dockerfile`, two tags: `:latest` and `:{version}`
7. **Smoke test** (lines 222–232) — `docker run -d -p 8080:8080 ...:latest`, sleep 5s, `curl /info/health`, stop container, fail the job if status ≠ 200

This means every published image has been confirmed to start, run uvicorn, and serve the FastAPI health endpoint before the tag is allowed to land.

## 6. Adjacent Tooling

- **`sg-send-ec2`** CLI (`sgraph_ai_app_send__docker/provision_ec2.py`, Typer) — provisions an EC2 host, attaches an IAM instance profile, opens security group rules, pulls the ECR image, and runs the container. Commands: `create`, `wait`, `health`, `connect`, `exec`, `forward`, `list`, `info`, `delete`. This is **adjacent** to container support, not part of it — it is how the container gets onto a long-running host.

## 8. Gaps and Recommended Follow-Ups

These are the gaps the Architect role observes — they are **not blockers** for the current container deployment, but they will matter as the container surface widens beyond local dev and EC2.

1. **No ECS / Fargate task definition in the repo.** The image is published; there is no infrastructure-as-code yet to run it as a service. Candidate location: `sgraph_ai_app_send__docker/ecs/` or a separate IaC repo.
2. **No GCP wiring.** Reality doc lists GCP as a target but the image has not been verified on Cloud Run. A `provision_cloud_run.py` companion to `provision_ec2.py` would be the natural shape.
3. **`Send__Config.__init__` reads env vars and creates folders.** Flagged in code comments (`Send__Config.py` line 29) — should move to a Service Registry pattern, particularly important once we want to construct the config in tests without env mutation.
4. **Disk-mode lifecycle.** `Storage_FS__Local_Disk` has no built-in retention / TTL story. For a long-running container with a mounted volume, the operator currently relies on the application-level cleanup paths (transfer expiry) and on the volume's host-level disk quota. A background reaper that walks `/data` would be valuable for Villager hardening.
5. **No container-level metrics endpoint.** Health is covered (`/info/health`); there is no `/metrics` (Prometheus) yet. Likely a Villager concern, but the Architect surface decision (path, format) belongs here.
6. **Admin UI is stubbed in the user-container image.** The Dockerfile creates an empty `sgraph_ai_app_send__ui__admin/__init__.py` to satisfy imports. This is fine for the user image but means a single combined image is **not** currently producible from this Dockerfile — by design, since admin is intended to ship as a separate Lambda. Worth documenting explicitly so nobody attempts to "fix" the stub.

## 9. Quick-Reference Run Commands

In-memory container (ephemeral):

```bash
docker run -p 8080:8080 <ecr>/sg-send:latest
```

Disk-backed container (mounted volume):

```bash
docker run -p 8080:8080 \
  -e SEND__STORAGE_MODE=disk \
  -v /var/lib/sgraph-send:/data \
  <ecr>/sg-send:latest
```

Authenticated container (header `x-sgraph-access-token` required):

```bash
docker run -p 8080:8080 \
  -e SGRAPH_SEND__ACCESS_TOKEN=<token> \
  <ecr>/sg-send:latest
```

S3-backed container (any AWS-credentialed host):

```bash
docker run -p 8080:8080 \
  -e AWS_ACCESS_KEY_ID=... -e AWS_SECRET_ACCESS_KEY=... -e AWS_DEFAULT_REGION=eu-west-2 \
  <ecr>/sg-send:latest
```

(The container will auto-select S3 when credentials are present; no `SEND__STORAGE_MODE` needed.)
