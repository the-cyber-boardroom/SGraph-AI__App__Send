## 0. Framing — Routine IFD Consolidation

This is **normal IFD hygiene**, not a rescue. The IFD methodology alternates between two modes:

1. **Surgical overlays** — each minor version (v0.3.1, v0.3.2) ships as a small set of patch files that monkey-patch the previous version. This keeps each release diff tiny and reviewable.
2. **Periodic consolidation** — every few minors, the overlays get inlined into a fresh self-contained snapshot. This keeps the patch surface from compounding indefinitely and resets the base for the next round of surgical work.

The Vault UI did exactly this at v0.2.3 (commit `56ce79d` — "full self-contained snapshot"). v0.3.3 is the equivalent moment for the user UI: v0.3.0 (base) + v0.3.1 (folder + browse patches) + v0.3.2 (secret-share overlay) collapse into one tree, and the next surgical overlay (v0.3.4+) starts from that clean base.

The two confirmed orchestrator-pattern bugs from the Dev briefing (duplicate Email Link button on Step 5; Back from secret Confirm misroutes) are absorbed naturally by the consolidation — they exist because two different `_render` / `_wireEvents` implementations are fighting each other at runtime, and a single inlined class makes that impossible.

## 1. Goal & Non-Goals

### Goal

Produce a single self-contained `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.3/` tree that:

- Contains the entire sender + recipient UI (file flow + secret flow + recipient view) with no runtime dependency on `v0.3.0` or `v0.3.2`.
- Eliminates the prototype-patch / capture-phase-handler / `_render` overlay class of bug by **inlining** the v0.3.2 patches into the components they patch.
- Fixes the three confirmed bugs from the Dev briefing (§6) at their natural sites in the consolidated tree, without changing any user-visible behaviour beyond those bug fixes.
- Mirrors the precedent set by the Vault UI v0.2.3 snapshot in commit `56ce79d` so the deploy and local-server stories are simplified.

### Non-Goals

- **No new features.** No QR codes, no save-links-as-file, no kill-link safekeeping affordance, no telemetry. Those are §12 follow-ups.
- **No behaviour changes** beyond the three bug fixes named in §6. The 5-step wizard, the secret tab, the recipient `<send-secret-view>`, the kill flow, the API contract — all stay byte-for-byte equivalent in observable behaviour.
- **No backend changes.** The `expires_at: int ms` migration already shipped in `cd90038`; this plan only deletes the stale frontend warning comments.
- **No i18n retro-fit.** Locale-aware strings for the secret elements are an open Explorer follow-up (§11 Q1, §12).
- **No version-file edits.** `sgraph_ai_app_send/version` stays untouched — CI owns it.
- **No deletion of v0.3.0 or v0.3.2** in this plan. Whether to retire v0.3.2 immediately or keep it parallel for a release is a Dinis decision (§11 Q3).

## 2. Vault Precedent Recap

Commit `56ce79d` ("Vault UI v0.2.3 — full self-contained snapshot", 2026-05-09) collapsed Vault `v0.2.0` (base), `v0.2.1` (Design 02 landing), and `v0.2.2` (App Mode shell) into a single tree at `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/`. The diff was **~13,361 insertions / 25 deletions across 65 files** (roughly the whole vault UI plus three CI/script lines). Two non-tree changes shipped in the same commit:

- `.github/workflows/deploy-ui-vault.yml` dropped `BASE_SOURCE_DIR` and the `en-gb/` seed step.
- `scripts/vault__run-locally.sh` reduced to a single base layer with an empty overlays list.

The commit message explicitly cites the failure mode that motivated the snapshot: "a small path-handling mistake made v0.2.2's vault shell clobber v0.2.1's landing page at /en-gb/." That is structurally the same class of bug the Dev briefing flags for v0.3.2 (the duplicate Email Link button, the Back-from-Confirm misroute) — symptoms of the overlay pattern itself.

### Lessons for v0.3.3

1. **Path handling is the silent killer.** The vault snapshot worked because the new tree was complete; v0.3.3 must include `404.html`, `manifest.json`, `robots.txt`, `sitemap.xml`, `_common/favicon.svg`, fonts, design tokens, all i18n JSONs, and every component asset — not just the JS modules. Anything left behind would force the local-server overlay loop to re-engage.
2. **Update CI and run-locally in the same change set.** The vault precedent edited `deploy-ui-vault.yml` and `vault__run-locally.sh` alongside the snapshot. v0.3.3 will need the equivalent change for `deploy-ui-user.yml` (the loop already iterates `v0.3.x` versions so it will keep working, but a clean v0.3.3-only deploy is preferable — see §9).
3. **Follow-ups are gentle, not catastrophic.** Inspecting commits after `56ce79d` (`1e3f916`, `28a2367`, `48bd735`, `e97b0fa`, `1dee4f3`) shows the vault tree absorbed Phase 1–3 of the VaultLoader work cleanly on the new base. No emergency reverts. That is the steady-state we want for v0.3.3.

### Bug 1 — Duplicate Email Link button on Step 5 (secret mode)

- **Lives now in:** `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.0/_common/js/components/send-upload/send-upload.js:147-148` (the `_render` injects `<button id="upload-email-btn">Email Link</button>` whenever `_state === 'complete'`). The v0.3.2 `_render` patch at `send-upload-options.js:124-142` only handles the `choosing-options` action slot — it does not suppress the header email button for `complete + isSecretMode`.
- **Lives after in:** `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.3/_common/js/components/send-upload/send-upload.js` — single `_render` method.
- **Change:** the header-action injection condition becomes `if (this._state === 'complete' && !this._isSecretMode)`. Because there are no longer two `_render` implementations fighting, there is exactly one place to enforce this. The existing `<upload-step-done-secret>` element keeps its in-panel Email Link button — that button stays; the header duplicate goes.

### Bug 2 — Back from Confirm in secret mode lands on Options

## 9. Migration / Rollout

The IFD deploy at `deploy-ui-user.yml:72-101` already iterates every `v0.3.x` directory in patch order and overlays each onto `latest/`. Three options for v0.3.3:

### Option A — v0.3.3 is the only v0.3.x directory (parallel removal)

Delete `v0.3.0`, `v0.3.1`, `v0.3.2` directories at the same commit as v0.3.3 ships. The CI loop discovers only `v0.3.3` and deploys it with `--clean-latest`. Mirrors the vault precedent most closely.

### Option B — keep v0.3.0/v0.3.1/v0.3.2 and add v0.3.3 (overlay-on-overlay)

CI keeps overlaying. v0.3.3 ends up "winning" because it is the last one alphabetically, so its files clobber the earlier ones. **This is fragile** — exactly the failure mode `56ce79d` was written to avoid (commit message: "the multi-layer merge dance"). PROPOSED: do not pick this option.

### Option C (RECOMMENDED) — v0.3.3 self-contained, retire v0.3.2 in a follow-up commit one release later

Keep `v0.3.0` and `v0.3.2` in the tree for one release as a safety net (so `clean_latest: false` rollbacks still work). Route `latest/` at `v0.3.3` exclusively by ordering — since `sort -t. -k3 -n` puts `v0.3.3` last, its files win. After one stable release, delete `v0.3.0`/`v0.3.1`/`v0.3.2` directories. This decouples the consolidation from the directory removal.

### Coordination

- **No DNS / CloudFront changes** — same distribution, same bucket.
- **`clean_latest: true`** on the cutover deploy (default on push-triggered).
- **`scripts/user__run-locally.sh`** — no edits required because the script already iterates `v0.3.x` and overlays in order. The vault precedent did edit `vault__run-locally.sh` because the vault overlay logic was more bespoke; the user script is already simpler.
- **`deploy-ui-user.yml`** — no edits required, but PROPOSED: simplify the loop to a single-version deploy in a follow-up commit once Option C reaches steady state.
- **i18n generator** — `scripts/generate_send_i18n_pages.py` runs per-version. Confirm it generates `en-gb/s/index.html` translations correctly. PROPOSED: read the script's locale-folder copying logic to confirm it picks up `en-gb/s/` (it loops `for route in download browse gallery v view`, which does NOT include `s/` — so the secret recipient page would not get locale-translated copies under `pt-pt/s/`, `de-de/s/`, etc. This is a side-issue but worth flagging as §12 follow-up).
