## 0. Framing — IFD Major Release

The IFD methodology has three release types:

1. **Minor (surgical overlay)** — e.g. v0.3.1, v0.3.2. A small set of patch files monkey-patches the previous version. Each release diff stays tiny and reviewable.
2. **Periodic minor (consolidation snapshot)** — e.g. the originally-planned v0.3.3 and the vault precedent v0.2.3 (`56ce79d`). The overlays are inlined into a fresh self-contained snapshot at the same minor, so the next round of surgical work has a clean base.
3. **Major (independent codebase)** — e.g. v0.4.0. A new top-level version folder, not a continuation of v0.3.x. Intentional UX changes, default changes, or architectural changes ride on the major bump. v0.4.1+ then resume the surgical-overlay pattern on the v0.4.0 base.

**v0.4.0 is type 3.** Dinis chose this over the type-2 consolidation because the work bundles (a) the same refactor the v0.3.3 plan covered, AND (b) intentional UX changes — unifying the Done screen across file and secret share, applying ephemeral-by-default semantics to file transfers, and dropping multi-locale page generation.

**Strategic framing.** Send is ephemeral-by-default: every transfer (file OR secret) has a view limit and a TTL. Vault is the durable-by-design cousin. The temporal/quantity element is the Send platform's defining property — not a feature of the secret tab. v0.4.0 makes that consistent across all blob types.

## 1. Goal & Non-Goals

### Goal

Produce a single self-contained `sgraph_ai_app_send__ui__user/v0/v0.4/v0.4.0/` tree that:

- Contains the entire sender + recipient UI (file flow + secret flow + recipient view) with no runtime dependency on `v0.3.x`.
- Unifies the Done screen: one `<upload-step-done>` component renders both file and secret completion screens.
- Unifies the wizard shape: both flows are 6 steps — Upload → Delivery → Share mode → Confirm → Encrypt & Upload → Done.
- Applies ephemeral-by-default semantics: defaults `max_views = 20`, `expires = 7d` for file mode; `max_views = 2`, `expires = 24h` for secret mode. Kill link visible on both.
- Drops multi-locale page generation: `/en-gb/` only ships in v0.4.x.
- Inlines v0.3.0 + v0.3.1 + v0.3.2 + v0.3.3 patch surface into the new tree — eliminates the prototype-patch / capture-phase / overlay-class of bugs at the same stroke.

### Non-Goals

- **No new features beyond the locked NEW list in §2.** No telemetry, no save-links-as-file, no transparency receipt on the secret Done.
- **No i18n retro-fit.** Multi-locale generation is explicitly dropped from v0.4.x. i18n returns in a future release.
- **No backend changes.** `expires_at: int ms` shipped in `cd90038`; the unified Done's view/expiry display continues to read from the existing API.
- **No version-file edits.** `sgraph_ai_app_send/version` stays untouched — CI owns it.
- **No immediate deletion of v0.3.x.** v0.3.0–v0.3.3 stay in the tree for one release as a rollback safety net, then a follow-up commit deletes them (§9).
- **No DNS / CloudFront topology changes.**

## 5. UX unification details — the merged Done

The single `<upload-step-done>` component renders both modes. The vast majority of the markup is shared.

### Always shown (both modes)

- Success banner — text differs by mode (file: "File ready to share"; secret: "Secret link created").
- Simple token / Full link share boxes with Copy buttons (v0.3.0 `_renderToken` already does this).
- QR code panel + "Open in new tab — test the recipient experience" panel (v0.3.0 `qr-open-row`).
- Ephemerality notice: `"N views remaining · expires {date}"`. Populated from `result.maxDownloads` and `result.expiresAt`, which the orchestrator now always provides.
- Kill-link section: `<label>Delete this now</label>` with kill URL `…/en-gb/s/kill/{id}#{deleteAuth}` and Copy Kill button.
- Action row: `[Email Link]` + `[Send another]`.
- Trust footer: "The server holds only encrypted ciphertext…".

### Secret-mode-only differences

- Heading text: "Secret link created" (vs "File ready to share").
- Email body template: "I've shared a secret with you via SG/Send..." (vs "I've shared an encrypted file via SG/Send...").
- Label on the primary share row: "Secret link" (vs "File link"). Whether the "Simple token" row is rendered for secrets is a §13 Q3 decision.

**No other content differences are required.** The shared markup template is the single source of truth; `_isSecretMode` controls labels/copy only.

## 6. Defaults & data-flow changes

### File mode defaults

Applied in the merged `send-upload.js` at submit time:

```text
if (!_isSecretMode) {
    _config = {
        max_downloads:    20,
        auto_delete:      true,
        expires_at:       Date.now() + 7 * 24 * 3600 * 1000,
        delete_auth_hash: sha256_hex(_deleteAuth)
    };
}
```

The v0.3.0 file flow currently does **not** pass `max_downloads` / `expires_at` / `delete_auth_hash` on file transfers. The merged `api-client.js.createTransfer` always accepts these fields; passing them is the v0.4.0 NEW behaviour.

### Secret mode defaults

```text
if (_isSecretMode) {
    _secretConfig = {
        max_downloads:    cfg.maxDownloads || 2,       // was 1 in v0.3.2
        auto_delete:      true,
        expires_at:       cfg.expiresInHours ? (Date.now() + cfg.expiresInHours * 3600 * 1000) : 0,
        delete_auth_hash: sha256_hex(_deleteAuth)
    };
}
```

The pill default in `<upload-step-select>`'s Secret tab moves from `1` to `2`.

### Always-on `deleteAuth`

`crypto.getRandomValues(new Uint8Array(32))` → hex → `_deleteAuth`. `sha256_hex(_deleteAuth)` → `delete_auth_hash` sent to backend. `_deleteAuth` retained on the orchestrator and passed to the Done component via `result.deleteAuth`. **Both modes**.

### Result extensions for the unified Done

`upload-engine.run()` populates these fields on `result` for both modes:

- `result.maxDownloads` — int
- `result.expiresAt`    — int ms (or 0 = never)
- `result.deleteAuth`   — hex string
- `result.isSecretMode` — bool

This replaces the v0.3.2 engine's secret-only `combinedUrl` rewrite + `deleteAuth` stash with a uniform contract.

## 7. Kill link for files

### Server side

**No changes.** The backend `delete_auth_hash` field on `POST /api/transfers/create` already accepts the hash for any transfer type. `DELETE /api/transfers/delete/{id}` with header `x-sgraph-transfer-delete-auth: <raw>` already supports authenticated deletion regardless of content type (verified via `send-secret-view.js:227-276` and `api-client-v032.js:38-46`).

### UI side

- `_deleteAuth` is always generated by the orchestrator (not gated on `_isSecretMode`).
- `result.deleteAuth` is always populated.
- `<upload-step-done>` always renders the "Delete this now" / kill-link section.
- The recipient page for files (`/en-gb/download/#…`) does NOT change — kill is a sender action.

### Always-on vs opt-in?

**RECOMMENDED — always create `deleteAuth`, always show kill link in Done for both modes.** Simplest. The sender can ignore it. The cost is 32 random bytes + one SHA-256 per upload — negligible. **Flag for Dinis** (§13 Q2) — alternative is an Options toggle "Generate kill link" defaulting to ON, which adds UI noise for almost no benefit.

## 13. Open decisions for Dinis

Genuinely open — needs a human call before Phase A starts:

1. **Secret-mode expiry default — 24h or longer?** Current v0.3.2 default is 24h. Tunable in one line of `upload-step-select.js`. Recommendation: keep 24h.
2. **Kill link always-on vs Options toggle for file mode?** Recommendation: always-on (simplest, no UI noise, backend already supports it). Alternative: Options checkbox "Allow me to delete this later" defaulting to ON.
3. **Hide the "Simple token" row from the unified Done for secret mode?** Secrets don't get a friendly-token form (engine rewrites `combinedUrl` to `/s/{id}#{key}`). Recommendation: when `_isSecretMode`, render only the "Secret link" row (no simple-token), keeping the QR + Open-in-new-tab panels.
4. **File-mode "Unlimited views" and "Never expires" still available?** Defaults are 20 / 7d. Recommendation: keep "Unlimited" and "Never" as opt-out pills on the Options/Confirm step for power users — otherwise the cap becomes a regression for the existing file-share user base.
5. **`i18n/en-gb.json` ship or drop?** PROPOSED: ship the single JSON; verify in Phase A whether the runtime fails without it.
6. **Split upload (sender) and download (receiver) into separate IFD trees inside v0.4.0?** Sender and receiver share no runtime state; only utility modules and chrome are shared. Three options:
   - **(A)** One tree, unified — current plan default. Simplest.
   - **(B) RECOMMENDED** — One tree, internally split: `v0.4.0/send/`, `v0.4.0/receive/`, shared `_common/`. Captures the air gap; lets receiver work versionable as `v0.4.1__receive` independently of `send`. Smaller receiver bundle (better security posture: less attack surface on the recipient page running with someone else's key in the URL fragment). `_common/` becomes the staging area for what eventually moves to `tools.sgraph.ai`.
   - **(C)** Two parallel IFD lines: `v0.4.0__send/` and `v0.4.0__receive/`. Maximum separation, more deploy complexity now.
   If (B) or (C) is chosen, §3 file tree and §12 phased work breakdown require a small revision; the §4–§7 merge actions remain the same (they're all on the send side).
