## 0. Framing — IFD Major Release

The IFD methodology has three release types:

1. **Minor (surgical overlay)** — e.g. v0.3.1, v0.3.2. A small set of patch files monkey-patches the previous version. Each release diff stays tiny and reviewable.
2. **Periodic minor (consolidation snapshot)** — e.g. the originally-planned v0.3.3 and the vault precedent v0.2.3 (`56ce79d`). The overlays are inlined into a fresh self-contained snapshot at the same minor, so the next round of surgical work has a clean base.
3. **Major (independent codebase)** — e.g. v0.4.0. A new top-level version folder, not a continuation of v0.3.x. Intentional UX changes, default changes, or architectural changes ride on the major bump. v0.4.1+ then resume the surgical-overlay pattern on the v0.4.0 base.

**v0.4.0 is type 3.** Dinis chose this over the type-2 consolidation because the work bundles (a) the same refactor the v0.3.3 plan covered, AND (b) intentional UX changes — unifying the Done screen across file and secret share, applying ephemeral-by-default semantics to file transfers, and dropping multi-locale page generation.

**Strategic framing.** Send is ephemeral-by-default: every transfer (file OR secret) has a view limit and a TTL. Vault is the durable-by-design cousin. The temporal/quantity element is the Send platform's defining property — not a feature of the secret tab. v0.4.0 makes that consistent across all blob types.

## 1. Goal & Non-Goals

### Goal

Produce two self-contained, independently-versioned IFD trees that together replace the v0.3.x `sgraph_ai_app_send__ui__user/` codebase:

1. **`sgraph_ai_app_send__ui__share/v0/v0.4/v0.4.0/`** — the sender. Contains the wizard (file + secret flows), the unified Done component, the kill-link UI, ephemeral-by-default defaults, and all NEW v0.4.0 UX work. URL: `send.sgraph.ai/en-gb/share/`.
2. **`sgraph_ai_app_send__ui__open/v0/v0.4/v0.4.0/`** — the receiver. Contains `send-browse`, `send-download`, `send-gallery`, `send-viewer`, `send-secret-view`, plus the recipient shells. URLs: `send.sgraph.ai/en-gb/open/{,browse,download,gallery,v,view,s}/`.

Both trees together must:

- Have no runtime dependency on `v0.3.x`.
- Unify the share-side Done screen: one `<upload-step-done>` component renders both file and secret completion screens.
- Unify the share-side wizard shape: both flows are 5 steps — **Upload → Options → Confirm → Encrypt & Upload → Done** — keeping the v0.3.2 Options consolidation (merged Delivery + Share-mode) for both modes.
- Apply ephemeral-by-default semantics: defaults `max_views = 20`, `expires = 7d` for file mode; `max_views = 2`, `expires = 24h` for secret mode. Kill link visible on both.
- Drop multi-locale page generation: only `en-gb/` ships in v0.4.x.
- Inline v0.3.0 + v0.3.1 + v0.3.2 + v0.3.3 patch surface into the new trees — eliminates the prototype-patch / capture-phase / overlay-class of bugs at the same stroke.
- Each tree carries its own duplicated `_common/` (deliberate trade-off; `tools.sgraph.ai` extraction is the next milestone, §14).

### Non-Goals

- **No new features beyond the locked NEW list in §2.** No telemetry, no save-links-as-file, no transparency receipt on the secret Done.
- **No i18n retro-fit.** Multi-locale generation is explicitly dropped from v0.4.x. i18n returns in a future release.
- **No backend changes.** `expires_at: int ms` shipped in `cd90038`; the unified Done's view/expiry display continues to read from the existing API.
- **No version-file edits.** `sgraph_ai_app_send/version` stays untouched — CI owns it.
- **No immediate deletion of v0.3.x.** v0.3.0–v0.3.3 stay in the tree for one release as a rollback safety net, then a follow-up commit deletes them (§9).
- **No DNS / CloudFront topology changes.**

- **`upload-step-done-secret/` is absent** — dissolved into `upload-step-done/` (Share tree).

They MUST be byte-identical at v0.4.0 launch — Phase A0 includes a checksum step. Drift is the cost; `tools.sgraph.ai` extraction (§14) is the long-term resolution.

## 6. Defaults & data-flow changes

### File mode defaults

Applied in the merged `send-upload.js` at submit time:

```text
if (!_isSecretMode) {
    _config = {
        max_downloads:    20,
        auto_delete:      true,
        expires_at:       Date.now() + 7 * 24 * 3600 * 1000,
        delete_auth_hash: sha256_hex(_deleteAuth)
    };
}
```

The v0.3.0 file flow currently does **not** pass `max_downloads` / `expires_at` / `delete_auth_hash` on file transfers. The merged `api-client.js.createTransfer` always accepts these fields; passing them is the v0.4.0 NEW behaviour.

### Secret mode defaults

```text
if (_isSecretMode) {
    _secretConfig = {
        max_downloads:    cfg.maxDownloads || 2,       // was 1 in v0.3.2
        auto_delete:      true,
        expires_at:       cfg.expiresInHours ? (Date.now() + cfg.expiresInHours * 3600 * 1000) : 0,
        delete_auth_hash: sha256_hex(_deleteAuth)
    };
}
```

The pill default in `<upload-step-select>`'s Secret tab moves from `1` to `2`.

### Always-on `deleteAuth`

`crypto.getRandomValues(new Uint8Array(32))` → hex → `_deleteAuth`. `sha256_hex(_deleteAuth)` → `delete_auth_hash` sent to backend. `_deleteAuth` retained on the orchestrator and passed to the Done component via `result.deleteAuth`. **Both modes**.

### Result extensions for the unified Done

`upload-engine.run()` populates these fields on `result` for both modes:

- `result.maxDownloads` — int
- `result.expiresAt`    — int ms (or 0 = never)
- `result.deleteAuth`   — hex string
- `result.isSecretMode` — bool

This replaces the v0.3.2 engine's secret-only `combinedUrl` rewrite + `deleteAuth` stash with a uniform contract.

## 7. Kill link for files

### Server side

**No changes.** The backend `delete_auth_hash` field on `POST /api/transfers/create` already accepts the hash for any transfer type. `DELETE /api/transfers/delete/{id}` with header `x-sgraph-transfer-delete-auth: <raw>` already supports authenticated deletion regardless of content type (verified via `send-secret-view.js:227-276` and `api-client-v032.js:38-46`).

### UI side

- `_deleteAuth` is always generated by the orchestrator (not gated on `_isSecretMode`).
- `result.deleteAuth` is always populated.
- `<upload-step-done>` always renders the "Delete this now" / kill-link section.
- The recipient page for files (`/en-gb/download/#…`) does NOT change — kill is a sender action.

### Always-on vs opt-in?

**RECOMMENDED — always create `deleteAuth`, always show kill link in Done for both modes.** Simplest. The sender can ignore it. The cost is 32 random bytes + one SHA-256 per upload — negligible. **Flag for Dinis** (§13 Q2) — alternative is an Options toggle "Generate kill link" defaulting to ON, which adds UI noise for almost no benefit.

## 9. Migration / Rollout

### Cutover deploy — twin pipelines

- Branch `dev` push triggers BOTH `deploy-ui-share.yml` and `deploy-ui-open.yml` independently (each filtered by its own `paths:` trigger).
- Each pipeline runs with `clean_latest: true` for the cutover (default for push-triggered deploys).

  - `s3://<bucket>/en-gb/open/`  ← from `__open/v0.4.0/en-gb/open/` + flattened `__open/v0.4.0/_common/` etc.
  - The previous v0.3.x `s3://<bucket>/en-gb/{,browse,gallery,download,view,v,s,welcome}/` content is left in place during the retention window — the new paths are additive.

### CloudFront — additive behaviours

- Same distribution, same bucket. No DNS change.
- Two new path-pattern behaviours are added BEFORE the existing default:
  - `/en-gb/share/*` → existing origin, no special transform (S3 already has the files at that prefix).
  - `/en-gb/open/*`  → existing origin, no special transform.
- Existing `/en-gb/`, `/en-gb/browse/`, `/en-gb/download/` etc. behaviours **stay live** during the retention window so v0.3.x users with bookmarked links keep working. After Phase F retirement they are removed.
- Each pipeline's last-version step issues an invalidation for its own prefix.

### `deploy-ui-share.yml` and `deploy-ui-open.yml` — what they look like

Both are forks of the existing `deploy-ui-user.yml` with these differences:

1. `UI_BASE_DIR` → `sgraph_ai_app_send__ui__{share,open}`.
2. `paths:` trigger → `sgraph_ai_app_send__ui__{share,open}/v0/v0.4/**`.

5. S3 destination prefix → `en-gb/share/` or `en-gb/open/` (deploy script copies the tree's `en-gb/{share,open}/` content + flattened `_common/` to that prefix).

### `_common/` byte-identical-across-trees check

Phase A0 adds a small CI step that hashes a defined set of `_common/js/*.js` files in both trees and fails the build if they diverge. PROPOSED files: `crypto.js`, `friendly-crypto.js`, `api-client.js`, `i18n.js`, `send-icons.js`, `base/send-component.js`, `base/send-helpers.js`. Drift is the cost of the duplicated `_common/`; this check makes drift visible.

- Rollback path: re-enable `deploy-ui-user.yml`, push a no-op commit; v0.3.x deploys back to the old paths. Switch CloudFront's default behaviour back if needed.

### `generate_send_i18n_pages.py`

- Not invoked for v0.4.x trees.
- The script itself is **not** deleted (other UIs may reuse it).
- If/when i18n returns for the share or open trees, a future release re-enables the deploy step.
