## 1. What This Pack Covers (the why, how, what)

Three human briefs ask for one coherent capability:

| Brief | Date | The ask |
|---|---|---|
| `vaults-within-vaults-nested-vault-access` (dev) | 24 May | A vault can **open and read other vaults** it references. Driving use case: a doctor's parent vault reading many per-patient vaults. No backend complexity. |
| `sg-send-sub-vaults-workflow-access-points` (arch) | 25 May | Implement nesting as a **convention** (Git-submodule model), built on the existing `.vault` folder + read-only-token double-encryption. **Web UI first**; **pre-initialise on access** (lazy). |
| `sg-send-vault-conventions-and-external-resources` (arch) | 25 May | Codify the references as **convention files** uniform with `app.json`/`_page.json`; extend the same pattern to **embed external resources** (video, link, external app) in a **controlled iframe** (default-deny; selectively grant). |

**The why.** A vault should be able to point at other vaults and at the outside world, with access governed by the keys the user holds, *without* new backend machinery or new vault primitives. This unlocks the doctor/admin "parent vault over many child vaults" workflow and a controlled plugin/embed model.

**The how.** A lightweight *link file* in the vault tree (a Git-submodule-style pointer that carries no key) plus key/detail records in `.vault/owner/`. The Vault Web UI reads them and either **splices the child vault inline** (so a sub-vault behaves exactly like a folder) or **embeds an external resource** in a locked-down iframe with no vault access by default.

**The what.** Mostly wiring existing parts together — read-only-open, lazy sub-tree loading, `.vault` double-encryption, the convention-file mechanism — behind one new file convention.

## 2. Principles (these govern every decision below)

1. **Transparency = invisibility for sub-vaults.** When this is right the user is *barely* aware they crossed into another vault: they just **expand a folder**. Sub-vaults nest and proliferate exactly like folders (`demos/`, `customers/`, `xyz/` may each *be* a sub-vault). There is **no separate "section" or divider** for them — that only adds friction. A subtle, honest indicator stays (a vault glyph + a tiny access chip) so the user is "a little bit aware."
2. **Access is governed by the key, not the relationship.** A read-only key gives read-only; a read-write key gives read-write; the UI does not change. A read-only parent can hold a child the user has read-write to, and vice-versa — access is per-key and independent at each level.
3. **v1: read-only inside sub-vaults.** Editing a child means commit/sync bookkeeping we have not built for the nested case, so **v1 always opens a sub-vault read-only, regardless of the key held.** Writing, recursive write, and create-child are a later phase. This makes traversal a simple walk down the tree.
4. **Keep the secrets in `.vault`; keep the tree file dumb.** The link file in the tree carries **no key** — only a public id + a cross-reference. Keys and richer details live in `.vault/owner/`. A link file is therefore safe to sit anywhere, be moved, even be reader-visible.
5. **Default-deny for the outside world; opt-in access is a first-class capability.** No external app/resource gets vault data by default. But because **in most app workflows the user never sees the raw vault** (a doctor sees a rendered app and steps into a vault *through the app*), an explicit, opt-in way to grant an app scoped access to vault data is a core v1 requirement. Granularity and per-file monitoring come later.
6. **Empower the app workflow.** Both the raw vault UI and the app-only workflow (user never sees the vault) are first-class; the app-only one is the larger requirement. "Transparent" includes occasionally entering a key, or saving the key — the user should never be fighting the machinery.

## 4. Architecture & Design

### 4.1 The link file — a dumb, movable pointer in the tree
A sub-vault (or external resource) is declared by a small JSON **link file that lives in the regular vault tree**, exactly like a Git submodule's gitlink. It is the convention twin of `app.json`.

- **Naming convention:** any filename ending in **`.link.json`**. The **prefix is a user-chosen label** (`acme-demo.link.json`, `.health-score.link.json`); the **`.link.json` suffix is the sole signal** that tells the UI to treat the file specially.
- **This is a feature, not just a name.** If the user renames a link file *away* from the suffix — e.g. `acme-demo.link.json` → `acme-demo.link-2.json` — the UI stops treating it specially and shows it as a **plain `.json` file**. Two consequences: (a) renaming is a trivial "disable this link" gesture; (b) it reinforces why **no confidential data may ever live in a link file** — it is just a normal vault file that happens to match a suffix, and could be viewed as raw JSON at any time.
- **Rendered by an icon, never as raw JSON** when the suffix matches. A `type:"vault"` link renders as an **expandable folder** (vault glyph); `type:"link|video|app"` renders as an embed launcher.
- **Carries NO secret key** — only public / non-sensitive fields:
```json
{
  "type": "vault",                 // vault | link | video | app
  "label": "Patient: Alice",       // optional; the filename prefix may serve as the label
  "vault_id": "abcd1234",          // public id — safe; used to fetch public info
  "ref_id": "lk-a1b2c3d4",         // cross-ref into .vault/owner/{ro,rw}-links (where the key lives)
  "pin": { "mode": "latest" },     // or { "mode":"commit", "commit":"<id>" } — submodule-style
  "description": "Right health-score record, post-op",
  "url": null                      // for type link/video/app: the external URL
}
```
- **Editable + movable.** Because it is a normal file: edit it (via the link card, §5.2), and **move a sub-vault between folders/vaults by moving or copying the link file**, then refresh. Moving a whole sub-tree of vaults = moving one small file.
- **Same vault, many places.** Several link files with the same `vault_id`, in several folders, surface the same vault several ways (by customer / by use case / by hex). They are independent pointers — no conflict.

### 4.2 Where the keys live — two files in `.vault/owner/`
The link file is dumb; the **keys and richer details live in `.vault/owner/`, split into two files by the power of the key they hold**:

| File | Encryption tier | Who can read it | Holds |
|---|---|---|---|
| `.vault/owner/ro-links.json` | `read_key` only (single layer) | any holder of **parent read** access | **read-only** references (`read_key` / ro-token + `ref_file_id`), description, public-info cache |
| `.vault/owner/rw-links.json` | double-encrypted (owner-secret) | **parent owner only** (full key) | **read-write** references (full child `vault_key`) |

- Cross-referenced by the link file's `ref_id`. The sensitivity of the stored key **matches** the file's tier: read-only keys may be reader-visible (`ro-links`), full keys never leave the owner tier (`rw-links`).
- A read-only holder of the parent can therefore **traverse into `ro-links` sub-vaults** but never sees `rw-links` — exactly the desired behaviour. (Everything in a vault is private; the `ro`/`rw` distinction is about the *power of the link*, not public-vs-private.)

### 4.3 How a key is resolved on open (stored, or entered)
When the user expands/opens a `type:vault` link file:
1. **Resolve `ref_id`** in `ro-links.json` (then `rw-links.json` if owner). Found → use that key.
2. **Also check browser `localStorage`** (the existing `sg-access-key:` pattern) for a locally-saved key.
3. **Nothing found** → show the **link card** (§5.2): fetch and show the vault's **public info first** (a capability from the per-vault public-info brief — accounted for here), then **prompt for the key**, offering three save choices: *save into `.vault` (`ro`/`rw`-links)*, *save on this device (`localStorage`)*, or *don't save — ask each time*. All three are supported.
4. **Open the child read-only** (v1, §4.4) via `openReadOnly` (read key) or `open` (full key, then wrapped read-only), honouring `pin` (§4.5).

### 4.4 Opening & traversing a sub-vault (inline, lazy, read-only in v1)
- On expand, the child vault is opened **lazily** and its tree is **spliced inline** beneath the link-file node — a *virtual folder* backed by a child `VaultDataSource`. Sub-folders within it expand normally. The experience is "folders all the way down."
- **v1: always read-only inside a sub-vault**, regardless of the key held — wrap the child in `new VaultDataSource(childVault, null)` so no write/upload/new-file controls appear. (Principle 3.)
- **Recursive sub-vaults are supported structurally** — a sub-vault may itself contain link files, opened the same lazy read-only way. (It is just a pointer; deep *write* is deferred.)
- **"Open in new window"** affordance on a sub-vault → the normal full vault workflow (`/en-gb/vault/#<key>` or `/en-gb/app#<key>`), which may be read-write. To avoid clobbering the parent in `localStorage`, a tracked **parent↔sub-vault relationship** is recorded so "back" returns to the parent.

### 4.5 Submodule-style pinning (default: latest)
- `pin.mode:"latest"` (default) → open the child's current named HEAD. **Users never have to "sync submodules"**; the common case just shows the latest.
- `pin.mode:"commit"` → open the child at a recorded commit id (via `_loadTreeFromCommit`) for reproducible/frozen views. Editable from the link card.

### 4.6 External resources (`type:link|video|app`)
Same link-file convention; `url` is set. Rendered as an embed launcher; opened in a **controlled iframe** (`<sg-embed-frame>`, §6) that by default **cannot reach the vault**. `type:app` additionally supports an explicit **opt-in access grant** (§6.3) — the one sanctioned way an external app reads vault data.

## 5. UX & Design

> Companion design review (wireframes, states, tokens, transparency analysis): [`../../../../designer/reviews/05/25/v0.27.62__designer-review__sub-vaults-and-external-resources-ux.md`](../../../../designer/reviews/05/25/v0.27.62__designer-review__sub-vaults-and-external-resources-ux.md).

### 5.1 Sub-vaults are inline, expandable folders (seamless)
```
┌─ SG/Vault ──────────────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ─────────────────┐ ┌── preview ───────────────────────────────┐ │
│ │ 📁 reports               │ │  health-score.json …                     │ │
│ │ ▼ 📁 subvaults           │ │                                          │ │
│ │   ▼ 📁 demos             │ │                                          │ │
│ │     ▾ 🗄 acme-demo  ·ro  │ │   ← a sub-vault: expands like a folder    │ │
│ │        📄 readme.md      │ │     (contents loaded on demand)          │ │
│ │        📁 assets         │ │                                          │ │
│ │   ▼ 📁 customers         │ │                                          │ │
│ │     ▸ 🗄 acme       ·ro  │ │   (acme appears here AND under demos —    │ │
│ │     ▸ 🔒 globex          │ │    same vault, two link files;           │ │
│ │   ▸ 🗄 acme        ·ro   │ │    globex is locked → opens link card)   │ │
│ └─────────────────────────┘ └──────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────────┘
```
- A sub-vault is a tree node that **expands inline** like a folder. The only difference from a plain folder is a **subtle vault glyph (`🗄`) + a tiny access chip (`·ro`/`·rw`)** — enough to be "a little bit aware," never a wall.
- A locked sub-vault (no key yet) shows `🔒`; clicking opens the link card (§5.2) rather than expanding.

### 5.2 The link card — a miniature "open vault" surface
Clicking a link file (or its `🔒`) shows a small graphical card (the convention's visual form, the way `app.json` drives App Mode):
```
┌ 🗄 Linked vault — acme-demo ───────────────────────────────┐
│ Status   🔒 Locked (no key on this device)                  │
│ Public   "ACME product demo · 12 files · updated 24 May"    │   ← public info, shown before any key
│ Key      [ ro-coral-stamp-5678                            ] │
│ Save     (•) In this vault (ro-links)  ( ) On this device   │
│          ( ) Don't save — ask each time                     │
│ Pin      (•) Latest   ( ) Commit [ ………… ]                   │
│ Notes    [ Right health-score record, post-op …          ] │
│      [ Open here (read-only) ]   [ Open in new window ↗ ]   │
└──────────────────────────────────────────────────────────────┘
```
- Shows **public info before any key**, then prompts. Save choice = the §4.3 three-way. "Open here" splices inline (read-only); "Open in new window" = full workflow with parent/sub-vault tracking.
- Owner sees editable fields (label, notes, pin, key store); a reader sees a read-only card for `ro-links` entries only.

### 5.3 External resources keep the strong boundary (default-deny)
For `type:link|video|app`, the embed loads in `<sg-embed-frame>` with a **sticky, non-dismissable** guarantee banner — two states; **amber appears only when data can leak**:
```
🔒 External window · youtube.com · CANNOT read this vault                 [Why?]
🟠 External window · mail.example.com · CAN READ /shared (12 files) · Granted by you · [Revoke]
```
Granting an app access is an explicit owner action behind an **Advanced disclosure + a risk-proportional confirm** that names the site, folder, and file count (never a one-click toggle).

### 5.4 The app-only workflow (user never sees the raw vault)
A doctor opens an **app** (e.g. `/en-gb/app#<key>`), sees the rendered page, and steps **into a specific sub-vault from inside the app** — never touching the tree UI. This requires (a) the link-file/sub-vault machinery to be reachable from the app/VFS layer, and (b) the app to be able to hold an opt-in grant (§6.3). The raw vault UI (§5.1–5.3) and this app-only path are both first-class.

## 6. Security Analysis (the boundary that must be right)

### 6.1 Two iframe paths, kept separate
| | App iframe (exists) | External-resource iframe (`<sg-embed-frame>`, new) |
|---|---|---|
| `src` | same-origin `blob:` of vault HTML | **cross-origin** external URL |
| `sandbox` | `allow-scripts allow-forms allow-same-origin` | `allow-scripts allow-popups allow-presentation` — **no `allow-same-origin`** |
| VFS bridge / `message` listener | yes (trusted vault content) | **none by default** |
| Vault access | full | **none (default-deny)** |

Cross-origin **and** no bridge **and** no listener **and** no `allow-same-origin` ⇒ the embed has no path to vault data.

### 6.2 Link-file & key confidentiality
- Link files carry **no keys** (only a public `vault_id` + `ref_id`) → safe to move/copy/place anywhere, even reader-visible. The `.link.json`-suffix rule means a link file is just a normal vault file; treat it as readable raw JSON at any moment, so it must never hold a secret.
- Read-only keys live in `ro-links` (read-tier); full keys live only in `rw-links` (owner-tier, double-encrypted). Reuses the audited `ownerEncrypt`/`ownerDecrypt`. **Never** put a key in a link file or a full key in `ro-links`. PKI-ready (encrypt references to recipient public keys when PKI lands).
- CLAUDE.md rule 14/33: keys are secrets — inside the encrypted vault only, never Git, never logs; mask in debug (`_maskKey` exists).

### 6.3 Opt-in app→vault access (first-class in v1)
Default-deny stays; the sanctioned exception is an **explicit owner opt-in** that lets a `type:app` embed read vault data, because the app-only workflow (user never sees the vault) is core.
- **v1 grant model (minimal):** the owner grants a **scoped, read-only** channel to a named folder (e.g. `/shared`) via the Advanced confirm (§5.3). The embed gets a **narrow, separate** channel — *not* the full `window.sg.*` bridge — exposing only `requestFile(path)` constrained to the granted prefix (the parent enforces the prefix). Recorded against the link file's grant and reflected in the amber banner with inline Revoke.
- **Explicitly later (not v1):** per-file access monitoring/audit, fine-grained capability sets, write grants, time-boxed grants. The lead flagged a future "monitoring and control of which files are accessed"; design the v1 channel so that layer can wrap it.
- **AppSec asks:** sign off the scoped channel before build; confirm `<sg-embed-frame>` shares no code with the app bridge; confirm no `message` listener for ungranted embeds; threat-model prefix enforcement and stale-grant fail-closed.

## 7. Implementation Plan (Web UI first)
All in `sgraph_ai_app_send__ui__vault/` (IFD; the next minor of v0.2.x). No backend changes for v1 (children reuse existing read endpoints; embeds are client-only). The CLI does not change in v1 — it will simply see `.link.json` and `ro/rw-links` as ordinary files and gain clone-within-clone behaviour in a later phase.

**Phase 1 — convention + crypto (no UI)**
- `_common/js/lib/links/vault-links.js` (new): recognise the `.link.json` suffix; parse/validate the schema; `loadRoLinks(vault)` / `loadRwLinks(vault)` (read `.vault/owner/ro-links.json` via `read_key`; `rw-links.json` via `ownerDecrypt`); `resolveKey(refId)` (incl. `localStorage`); `saveLink*` / `saveRoRwEntry`. Mirrors `vault-token-manager`.
- Move `vault-hkdf.js` → `_common/js/lib/crypto/` (shared by tokens + links).

**Phase 2 — read-side: inline sub-vaults**
- Teach the browse tree (`vault-data-source.js` / `send-browse` / `vault-shell.js`) to recognise `.link.json`, render it as a **virtual folder** (vault glyph + access chip), and on expand open the child **read-only** (lazy) and splice its tree in. Add the parent↔sub-vault `localStorage` relationship + "open in new window". Recursive expansion falls out of the same path.
- `<sg-link-card>` (new): the §5.2 card (public info → key prompt → save choice → pin → open).
- `<sg-embed-frame>` (new): the controlled external iframe + sticky banner (§6.1).

**Phase 3 — write-side (owner) + opt-in app grant**
- Owner "Add / Edit / Move" for link files (extend `vault-browse-edit.js`); write `ro-links` / `rw-links` via Phase 1.
- The minimal scoped app-grant channel (§6.3) + amber granted banner + Revoke.

**Phase 4 — follow-on (separate brief):** write-inside-sub-vault (commits across levels), recursive write, CLI clone-within-clone, per-file access monitoring / granular grants.

|---|---|
| ADD | `_common/js/lib/links/vault-links.js` |
| MOVE | `_common/js/lib/crypto/vault-hkdf.js` |
| ADD | `_common/js/components/sg-link-card/*`, `_common/js/components/sg-embed-frame/*` |

## 8. Testing / QA Plan
No mocks; in-memory stack; Playwright for E2E. A changelog entry + QA brief accompany the build.

- **Unit:** `.link.json` suffix recognition (a file renamed off the suffix is treated as a plain `.json`); link-file parse/validate (malformed dropped, not thrown); `ro-links`/`rw-links` round-trip; `ref_id` resolution incl. `localStorage`; pin latest vs commit.
- **Crypto:** `ro-links` decrypts with `read_key`; `rw-links` decrypts only owner-side; a read-only holder of the parent **can** resolve `ro-links` but **cannot** read `rw-links`.
- **Security (priority):** `<sg-embed-frame>` exposes no `window.sg` and registers no `message` listener; sandbox lacks `allow-same-origin`; the granted app channel is read-only, prefix-enforced, and **fails closed** on a stale/missing folder; an ungranted app gets nothing.
- **E2E:** inline expand of a sub-vault (read-only, lazy — assert the child is not fetched until expand); recursive sub-vault expands; same vault under two link files; move a link file → sub-vault relocates; rename off the suffix → shows as plain JSON; locked node → link card → enter key → each save choice; "open in new window" returns to the parent (relationship tracked); a `video` embed renders with the sticky banner; expired/unreachable child → friendly failure, never a dead node.
- **Changelog test-impact:** *Should break (good):* browse-tree snapshots (virtual folders), action-bar (Add link). *Should NOT break (bad):* `app.json`/`_page.json` flows, RO-token open, lazy-folder loading, the app VFS bridge.

## 9. Decisions (settled)
| Topic | Decision |
|---|---|
| Link-file name | Any filename ending **`.link.json`**; the prefix is a user label, the suffix is the UI signal. Renaming off the suffix → treated as a plain `.json` (a deliberate "disable" gesture and a reason link files hold no secrets). |
| Where child keys are stored | All three supported, chosen in the link card: `.vault/owner/{ro,rw}-links`, browser `localStorage`, or prompt-each-time. |
| ro vs rw link files | `ro-links.json` (read_key-encrypted) + `rw-links.json` (owner-only double-encrypted); the link file holds only `ref_id`. |
| Write inside a sub-vault | **No in v1** — read-only always. Deferred until nested commit/push management exists. |
| Recursive sub-vaults | Supported structurally (read-only walk); deep write deferred. |
| App→vault access grant | v1: scoped read-only `requestFile` channel; monitoring/granularity later. |
| CLI clone-within-clone | Phase 4 — get the UI right first; the CLI sees these as ordinary files until then. |

## 11. Risks
1. **Inline sub-vaults blur "am I in another vault?"** → subtle glyph + access chip + a slim context bar on deep entry (see design review).
2. **External embed reaching vault data** → the §6.1 boundary; the priority test suite enforces it.
3. **Opt-in grant is the deliberate hole** → scoped read-only, prefix-enforced, fail-closed, Revoke, amber banner; AppSec sign-off; monitoring later.
4. **A key placed in a link file by mistake** → schema forbids keys in link files; keys only in `ro`/`rw-links`; the `.link.json`-as-plain-JSON property makes the rule self-evident; lint/test guard.
5. **Write-inside-child scope creep** → explicitly excluded from v1.
