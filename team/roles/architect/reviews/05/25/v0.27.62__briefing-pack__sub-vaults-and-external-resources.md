## 1. What This Pack Covers (the why, how, what)

Three human briefs, read together, ask for one coherent capability:

| Brief | Date | The ask |
|---|---|---|
| `vaults-within-vaults-nested-vault-access` (dev) | 24 May | Make a vault able to **open and read other vaults** it references (operable nesting). Driving use case: a doctor's parent vault reading many per-patient vaults. No backend complexity. |
| `sg-send-sub-vaults-workflow-access-points` (arch) | 25 May | Implement nesting as a **convention** (Git-submodules model), not native vault support. Build on the existing `.vault` folder + read-only-token double-encryption. Three access points (CLI, Vault Web UI, iframe); **Web UI first**; **pre-initialise on access** (lazy). |
| `sg-send-vault-conventions-and-external-resources` (arch) | 25 May | Codify the references as **convention files** uniform with `app.json`/`_page.json`. Extend the same pattern to **embed external resources** (video, link, external app) in a **controlled iframe** (default-deny; selectively grant). |

**The why.** A vault should be able to point at (a) other vaults and (b) the outside world, with controlled access, *without* adding new backend machinery or new vault primitives. This unlocks the doctor/admin "parent vault over many child vaults" workflow and a controlled plugin/embed model — both as conventions layered on the vault we already have.

**The how.** A small, double-encrypted convention file inside the existing `.vault/` folder records typed "pointers." The Vault Web UI reads it (exactly as it already reads `app.json`), renders pointers in the file tree, and acts on them: open a sub-vault lazily on access (reusing the existing read-only-open path), or load an external resource in a locked-down iframe with **no** vault access by default.

**The what.** One convention file (`type`-discriminated), one new convention-reader module, two new UI surfaces (a "Linked / Resources" tree section and a controlled embed frame), and owner-side "Add" management — all reusing existing crypto, storage, and the existing vault-open machinery.

## 2. What Already Exists (code-verified foundations)

This feature is unusually cheap because **almost every primitive it needs is already built.** Citations are to `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/` unless noted.

### 2.1 The convention-file mechanism (`app.json` / `_page.json`)
- The UI already loads a convention file from **`.vault/app.json`** (preferred) with `app.json` legacy fallback — `_common/js/components/app-shell/app-shell.js:448` (`_readAppJson`), and the browse-page twin in `index.html` (`_applyAppJson`, ~lines 667–762).
- `app.json` fields in use: `entry`, `auto_open`, `present`, `title`, `resources.{css,js}`, `auth.{required,prompt}`.
- On finding the file, the UI emits events, reveals a header action, and may auto-open the entry — i.e., **"the UI knows there is something here and how to load it."** This is the exact pattern the briefs want extended.

### 2.2 The `.vault` folder + double-encryption (read-only tokens)
- Owner-only files live under **`.vault/owner/*`** and are **double-encrypted**: outer layer = vault `read_key` (the standard vault layer every object uses); inner layer = `vault_secret_key` derived via **HKDF-SHA256** — `en-gb/vault/token/vault-hkdf.js:25` (`deriveVaultSecretKey`, info `sgraph-vault-secret-v1`, salt = `vault_id`), with `ownerEncrypt`/`ownerDecrypt` at lines 61/79.
- Result: a file in `.vault/owner/` is readable **only by the holder of the full vault key** — a read-only-token holder cannot decrypt it. This is precisely the "store the reference reader-only" property the workflow brief asks for (its Risk 3).
- Read-only tokens already work end-to-end: `en-gb/vault/token/vault-token-manager.js` stores `.vault/owner/readonly-tokens.json` (double-encrypted) and the token payload is `{ vault_id, read_key (b64), ref_file_id }`, encrypted with the token as a PBKDF2 passphrase (salt `sgraph-ro-token-v1`, 100k iters) and parked in a transfer slot.

### 2.3 Opening a vault read-only from a reference (the heart of "clone on access")
- **`SGVault.openReadOnly(sgSend, vaultId, readKeyBase64, refFileId)`** already exists — `_common/js/lib/sg-vault/sg-vault.js:93`. It opens a vault with only a read key (no passphrase, no write key → `vault.writable === false`).
- **`VaultLoader.openROToken(roToken)`** already does the full resolve-and-open: GET `check-token` → decrypt payload → `SGVault.openReadOnly(...)` — `_common/js/vault-loader/vault-loader.js:122`.
- **A sub-vault "vault pointer" is, structurally, a stored RO-token payload.** Opening it is the *same code path* we already ship.

### 2.4 Lazy loading ("pre-initialise on access")
- Folders are already loaded lazily: `VaultDataSource.loadAllSubTrees()` / `_ensureLoaded()` / `vault.loadSubTreeOnDemand()` — `_common/js/adapters/vault-data-source.js:40,136`; `sg-vault.js:408`. The "open the sub-vault only when accessed" model is the same lazy pattern, one level up.

### 2.5 The iframe + VFS bridge (the thing external resources must NOT get)
- App iframes are mounted from a **same-origin `blob:` URL** with `sandbox="allow-scripts allow-forms allow-same-origin"` and a **full VFS bridge** injected (`window.sg.vfs.read/write/list`, `sg.sync.*`, `sg.auth.*`) — `app-shell.js:609,742,854`. Apps are trusted vault content and get full vault access by design.
- **There is no external-URL iframe anywhere in the codebase today** (verified: every `iframe.src` is a `blob:` of vault content or a same-origin vault frame). External embedding is genuinely new, and its security boundary is the central new design decision (§6).

### 2.6 Multi-vault navigation surface
- The landing page already tracks **recent vaults** (`VaultLoaderRecent`) and routes vault keys through `VaultLoader.open()` (`vault-loader.js:42`). Sub-vault traversal is "open another vault in the same session with a breadcrumb back" — the navigation primitives are present.

## 3. Architecture & Design Decisions

### 3.1 Decision: one convention file, `type`-discriminated (answers the open question)
The conventions brief asks (open question): *"Do resource-pointer and vault-pointer conventions share a format? Possibly a common pointer format with a type field."* **Recommendation: yes — one file, one array, a `type` field.** This is the simplest, most uniform choice, honours the "keep it simple, name it for what it is, avoid stacked extensions" principle, and reuses one read/write path for all pointer kinds.

**File:** `.vault/owner/pointers.json` (owner-only, double-encrypted — same tier and code path as `readonly-tokens.json`).

Naming rationale (settles the brief's deliberately-open naming question): the file sits *inside* `.vault/owner/`, so it needs no `.vault`-stacked extension; it is named for what it is (`pointers`); the kind is carried by `type`, not by the filename. This avoids the "dot vault dot vault dot json" awkwardness the brief flagged.

**Schema (v1):**
```json
{
  "version": 1,
  "pointers": [
    {
      "id": "ptr-a1b2c3d4",
      "type": "vault",
      "label": "Patient: Alice",
      "ref": { "mode": "readonly", "vault_id": "…", "read_key": "<b64>", "ref_file_id": "ref-pid-muw-…" }
    },
    {
      "id": "ptr-e5f6…",
      "type": "vault",
      "label": "Shared working vault",
      "ref": { "mode": "full", "vault_key": "apple-river-1234:abcd1234" }
    },
    { "id": "ptr-…", "type": "video", "label": "Intro video",   "url": "https://www.youtube.com/embed/XXXX", "provider": "youtube", "access": "none" },
    { "id": "ptr-…", "type": "link",  "label": "Clinic website", "url": "https://clinic.example.com",        "access": "none" },
    { "id": "ptr-…", "type": "app",   "label": "Email",          "url": "https://mail.example.com/embed",     "access": "none", "grants": [] }
  ]
}
```

- `type ∈ {vault, link, video, app}`.
- `vault` pointers carry either an RO triplet (`mode:"readonly"` — preferred; opens via `SGVault.openReadOnly`) or a full `vault_key` (`mode:"full"` — writable child; opens via `SGVault.open`). **The `vault_key` / `read_key` are secrets — this is why the file is owner-only/double-encrypted.**
- `link`/`video`/`app` carry a `url` and an **`access` field defaulting to `"none"`** (default-deny). `app` may carry an explicit `grants` allowlist (future; §6.3).

### 3.2 Decision: storage tier — owner-only by default (with a documented reader-visible option)
- **Default: `.vault/owner/pointers.json`** (double-encrypted). Only the parent **owner** (full vault key) sees and traverses pointers. This is correct and safe for the *driving* use case (the doctor holds the parent's full key) and satisfies the workflow brief's "references readable only by the entitled reader" + Risk 3.
- **Optional reader-visible tier (deferred): `.vault/pointers.json`** (encrypted with `read_key` only, no inner layer). Pointers here are visible to any read-only-token holder of the *parent* (useful for "published" sub-vault structures and non-sensitive embeds like a public video). v1 ships owner-only; the reader-visible tier is a one-line location/encryption switch added later if a use case needs it. *Vault pointers carrying a `full` key must never be placed in the reader-visible tier.*

### 3.3 Decision: opening sub-vaults reuses the existing open path, lazily
- On "access" (user clicks a `type:vault` pointer), the UI calls the **existing** machinery:
  - `mode:"readonly"` → `SGVault.openReadOnly(sgSend, ref.vault_id, ref.read_key, ref.ref_file_id)` (sg-vault.js:93).
  - `mode:"full"` → `SGVault.open(sgSend, ref.vault_key)` (sg-vault.js:118).
- Opening is **pre-initialise-on-access**: nothing about the child is fetched until the user navigates in (matches the lazy-folder model). Many child pointers cost only their (cheap) reference rows.
- Navigation model: a **vault back-stack** in the shell. Opening a child pushes `{ vault, dataSource, label }`; "Back to parent vault" pops. Each level reuses `VaultDataSource` unchanged. The child renders read-only (badge) when opened via `openReadOnly`.

### 3.4 Decision: external resources load in a controlled iframe with NO bridge (the security core)
This is the one place we deliberately diverge from the app-iframe path. See §6 for the full security analysis. In short: cross-origin `src`, locked-down `sandbox`, **no VFS bridge injected, no `postMessage` handler registered** → the embed is default-deny and *cannot* reach vault data.

### 3.5 Where this is uniform with existing conventions
- Same folder (`.vault/`), same JSON-convention idea, same "UI reads the file and knows what to do" behaviour as `app.json`/`_page.json`.
- Same double-encryption tier and crypto as `readonly-tokens.json`.
- Same lazy model as folders. Same open path as RO tokens. **The feature is mostly wiring existing parts together behind a new convention file.**

## 4. UX & Design (wireframes)

> The Designer reviewed these; see **§4.6** for the Designer's verdict and the refinements folded in. Full design review: `../../../../designer/reviews/05/25/v0.27.62__designer-review__sub-vaults-and-external-resources-ux.md`.

### 4.1 Vault browser — "BEYOND THIS VAULT" sections (three-bucket mental model)
The existing multi-pane browser gains a clearly fenced-off region below the vault's own files. Per the Designer, the user must hold a **three-bucket mental model — my files / other vaults / windows out** — and the cue is a hard divider plus **consistent trust chips** (not the ambiguous emoji-soup of the first draft). **Rule: amber is reserved exclusively for things that can leak data** (used in §4.3/§4.4), never for decoration.

```
┌─ SG/Vault ─────────────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ─────────────────┐ ┌── preview ───────────────────────────────┐ │
│ │ 📁 patients              │ │  # Clinic Vault                          │ │
│ │ 📁 reports               │ │  …                                       │ │
│ │ ═══ BEYOND THIS VAULT ═══│ │                                          │ │
│ │ ▼ Linked vaults     (2)  │ │                                          │ │
│ │    Patient: Alice [vault·RO]                                          │ │
│ │    Patient: Bob   [vault·RO]                                          │ │
│ │ ▼ Windows out       (3)  │ │                                          │ │
│ │    Intro video    [embed·none]                                        │ │
│ │    Clinic website [embed·none]                                        │ │
│ │    Email (app)    [embed·none]                                        │ │
│ │    🔒 owner-only — visible only to you (the vault owner)              │ │
│ └─────────────────────────┘ └──────────────────────────────────────────┘ │
│  [ + Add ▾ ]   ← owner only (writable vaults)                             │
└────────────────────────────────────────────────────────────────────────────┘
```
- **Trust chips** (one new design token): `[vault·RO]` / `[vault·✎]` for sub-vaults (access you'll get in the child); `[embed·none]` for default-deny embeds; `[embed·READS]` (amber) only when a grant is live (§4.3).
- The `🔒 owner-only` marker states honestly that this whole region is visible only to the owner (v1 owner-only tier) — the pointer **labels themselves are sensitive metadata** (e.g. patient names), so they are hidden from read-only viewers, not shown locked-but-readable.

### 4.2 Traversing into a sub-vault (lazy clone-on-access) + persistent boundary bar
Per the Designer, reuse the **App-Mode chrome pattern** (a persistent boundary bar) and the **8-second loading/timeout** treatment already used by `sg-app-banner`, so a sub-vault feels like a clearly-labelled context switch, not a silent jump. The bar names the access level and the **key provenance** (where the access came from), with a `[Why?]` explainer.
```
click "Patient: Alice"  →  [ Opening linked vault…  fetching on access · ⏱ ≤8s ]

┌─ SG/Vault ────────────────────────────────────────────────────────────────┐
│ 🗄 Linked vault · Patient: Alice · 👁 Read-only · via parent vault   [Why?] │  ← persistent boundary bar
│ ‹ Back to parent vault                                                      │
│  ┌── tree ──────────┐ ┌── preview ──────────────────────────────────────┐ │
│  │ 📄 knee.json      │ │  knee-score.json …                              │ │
│  │ 📄 notes.md       │ │  (Read-only inherited — no edit/upload controls)│ │
│  └──────────────────┘ └─────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────┘

Failure card (unreachable child / expired token) — never a dead click:
┌──────────────────────────────────────────────┐
│ ⚠ Linked vault unavailable                    │
│   "Patient: Alice" could not be opened.        │
│   The read-only token may have expired.        │
│            [ Back ]   [ Retry ]                │
└──────────────────────────────────────────────────┘
```
Read-only is **inherited at the file level** (edit/upload/new-file controls are absent, not just disabled) so the viewer is never offered an action that will fail.

### 4.3 External resource in a controlled iframe — sticky banner, two variants
Per the Designer (P0): **the banner carries no `✕`** and must stay pinned through scroll and full-screen — it is the only on-screen statement of the zero-knowledge guarantee and must not be swat-away-able. (Closing the embed is done from the tree / boundary bar, not by dismissing the guarantee.) Two variants:

**Default-deny (the common case) — neutral:**
```
┌──────────────────────────────────────────────────────────────────────────┐
│ 🔒 External window · youtube.com · CANNOT read this vault         [Why?]   │  ← sticky, no ✕
├──────────────────────────────────────────────────────────────────────────┤
│                        ▶  (sandboxed YouTube iframe)                       │
└──────────────────────────────────────────────────────────────────────────┘
```

**Granted (rare, owner opted in) — amber, the only place amber appears for embeds:**
```
┌──────────────────────────────────────────────────────────────────────────┐
│ 🟠 External window · mail.example.com · CAN READ /shared (12 files)        │  ← amber, sticky, no ✕

├──────────────────────────────────────────────────────────────────────────┤
│                       (sandboxed external app iframe)                      │

```
The granted banner **names the exact folder + file count**, **attributes the choice to the user** ("Granted by you"), and offers **inline Revoke**. "Why?" opens the `<send-transparency>`-voiced explainer.

### 4.5 States to design (not just the happy path)
- **Empty:** no pointers → the "BEYOND THIS VAULT" region is hidden entirely (no clutter for the common single-vault case).
- **Reader's view (v1):** owner-only tier → an RO-token holder of the parent sees **nothing** in this region (correct — the labels are sensitive metadata). Do **not** show a locked-but-listed state that leaks labels.
- **Granted-embed (live):** the amber variant in §4.3 — its own persistent state with folder name, user attribution, inline Revoke.
- **Errors:** unreachable child / expired RO token / broken iframe (still sealed!) → the failure card in §4.2; embeds that fail still show the sticky guarantee banner.
- **Stale grants:** a grant whose folder no longer exists must **not silently re-bind** to a different folder — it fails closed and prompts the owner.
- **Narrow/mobile:** sections collapse; both the sub-vault boundary bar and the embed guarantee banner stay pinned.

## 6. Security Analysis (the controlled-iframe boundary — the part that must be right)

The conventions brief is explicit: the iframe is the security mechanism; external embeds are **default-deny**, access granted **selectively and explicitly**. The single most important implementation rule:

> **App iframes and external-resource iframes are different paths and must stay different.** An external embed must NEVER receive the VFS bridge or a `postMessage` handler.

### 6.1 The contrast (enforced, not incidental)
| | App iframe (exists today) | External-resource iframe (`<sg-embed-frame>`, new) |
|---|---|---|
| `src` | same-origin `blob:` of vault HTML | **cross-origin** external URL (e.g. `youtube.com`) |
| `sandbox` | `allow-scripts allow-forms allow-same-origin` | `allow-scripts allow-popups allow-presentation` — **no `allow-same-origin`** |
| VFS bridge injected? | **Yes** (full `window.sg.*`) | **No — never** |
| `message` handler registered for it? | Yes | **No** |
| Vault access | full (by design; trusted content) | **none** (default-deny) |

Because the embed is cross-origin **and** gets no bridge **and** has no listener on the parent side, the same-origin policy plus the absence of any channel means the embedded page has no path to vault data. Dropping `allow-same-origin` further forces the embed into an opaque origin so it cannot even assert our origin.

### 6.2 Pointer-file confidentiality
- `vault`-type pointers carry child keys → the file is **owner-only/double-encrypted** (`.vault/owner/pointers.json`). A read-only-token holder of the parent cannot decrypt it. **Never** place a `full` vault key in the reader-visible tier.
- Reuses the audited `ownerEncrypt`/`ownerDecrypt` path; no new crypto is invented. PKI-ready: when PKI lands, the same references can be encrypted to recipient public keys (the briefs' stated direction).
- **CLAUDE.md rule 14/33:** pointer files contain secrets (child keys); they live *inside the encrypted vault*, never in Git, never in logs. Mask keys in any debug output (the codebase already has `_maskKey`).

### 6.3 Selective grant model (for `type:app`, deferred to Phase 4)
- Default `access:"none"`. A grant is an explicit owner action that records `grants:[{ scope:"/shared", mode:"read" }]`.
- When granted, the embed gets a **separate, narrow** channel — *not* the full VFS bridge — exposing only the whitelisted scope (e.g. a read-only `requestFile(path)` limited to `/shared`, with the parent enforcing the prefix). This is a new minimal protocol, not a reuse of `__sgVfs*`. Designed and security-reviewed before it ships.

### 6.4 AppSec asks
- Confirm the sandbox token set per resource type (generic web vs. YouTube vs. granted app).
- Confirm no `postMessage` listener is ever attached for an embed frame, and that `<sg-embed-frame>` shares no code path with `app-shell`'s bridge.
- Threat-model the Phase 4 grant channel before implementation.

## 7. Testing / QA Plan

Per CLAUDE.md: no mocks, in-memory stack; Playwright for E2E. A changelog entry + QA brief accompany the build.

### 7.1 Unit (pytest / JS harness)
- Pointer schema: parse valid file; **malformed entries dropped, not thrown**; unknown `type` ignored gracefully; empty/absent file → empty list (not error).
- Round-trip: `savePointers` → `loadPointers` returns identical set; survives `push`/reopen.

### 7.2 Crypto
- `ownerEncrypt`→`ownerDecrypt` round-trip for `pointers.json`.
- **Negative:** an RO-token holder of the parent **cannot** decrypt `.vault/owner/pointers.json` (owner-only tier holds).
- Reader-visible tier (when added): decrypts with `read_key`, no inner layer.

### 7.3 Security (the priority suite)
- `<sg-embed-frame>` exposes **no** `window.sg` / `window.sgVault` inside the embed; parent registers **no** `message` listener for it.
- Sandbox attribute asserts per type; `allow-same-origin` absent for generic embeds.
- Cross-origin embed cannot read parent DOM / vault (origin-isolation check).
- Default-deny: a fresh `app` pointer has `access:"none"`; granting is explicit and scope-limited.

### 7.4 E2E (Playwright)
- Owner adds a read-only sub-vault pointer → it appears under "Linked vaults" → click → child opens read-only → "Back" returns to parent.
- Owner adds a YouTube video → renders in `<sg-embed-frame>` with the transparency banner; "Why?" opens the explainer.
- Error states: expired RO token / unreachable child → inline "unavailable" + retry.
- Lazy: child contents are **not** fetched until the pointer is opened (assert network).
- Reader (RO token of parent) sees no owner-only pointers (v1).

### 7.5 Changelog test-impact classification
- **Should break (good):** snapshot tests of the browse tree (new sections), action-bar tests (new `[ + Add ]`).
- **Should NOT break (bad):** existing `app.json`/`_page.json` flows, RO-token open, lazy-folder loading, the app-iframe VFS bridge. Any breakage here is a regression.

## 10. Risks
1. **Convention-file proliferation / confusion** → one file, `type`-discriminated, documented next to `app.json`.
2. **External embed reaching vault data** → the §6 boundary (cross-origin + no bridge + no listener + no `allow-same-origin`); the priority test suite enforces it.
3. **Pointer file holds child keys** → owner-only double-encryption (existing, audited); never in the reader tier; never in Git/logs.

5. **CLI nested-clone complexity** → explicitly deferred (Phase 4); Web UI carries the driving use case meanwhile.
