## 1. What This Pack Covers (the why, how, what)

Three human briefs ask for one capability:

| Brief | Date | The ask |
|---|---|---|
| `vaults-within-vaults-nested-vault-access` (dev) | 24 May | A vault can **open and read other vaults**. Use case: a doctor's parent vault reading many per-patient vaults. No backend complexity. |
| `sg-send-sub-vaults-workflow-access-points` (arch) | 25 May | Nesting as a **convention** (Git-submodule model), built on `.vault` + read-only tokens. Web UI first; **pre-initialise on access** (lazy). |
| `sg-send-vault-conventions-and-external-resources` (arch) | 25 May | Codify references as **convention files** uniform with `app.json`/`_page.json`; extend to **external resources** in a **controlled iframe** (default-deny; selectively grant). |

**The why.** A vault should point at other vaults and at the outside world, with access controlled by keys, without new backend machinery. **The how.** A lightweight *link file* in the tree (a Git-submodule-style pointer) plus key/detail records in `.vault/owner/`; the Web UI reads them and either splices the child vault in inline, or embeds an external resource in a locked-down iframe. **The what.** Mostly wiring existing parts (read-only-open, lazy loading, `.vault` double-encryption, the convention-file mechanism) behind a new file convention.

## 2. Principles (Rev 2 — the project lead's framing)
These govern every decision below.

1. **Transparency = invisibility for sub-vaults.** When we get this right the user is *barely* aware they crossed into another vault: they just **expand a folder**. Sub-vaults nest like folders (`demos/`, `customers/`, `xyz/` may each *be* a sub-vault) and proliferate the way folders do. A separate "section" made it *more* complicated — we abandon that. (A subtle, honest indicator stays — "a little bit aware" — see §5.)
2. **Access is governed by the key, not the relationship.** Read-only key → read-only; read-write key → read-write; the UI does not change. A read-only parent can hold a child you have read-write to, and vice-versa — access is per-key and independent at each level.
3. **v1 simplification: read-only inside sub-vaults.** Editing a vault means commits/sync we have not finished for the nested case. So **v1 always opens a sub-vault read-only regardless of the key held.** Writing (and recursive write, and create-child) is a later phase. This makes traversal a simple walk down the tree.
4. **Keep the secrets in `.vault`; keep the tree file dumb.** The link file in the tree carries no key — only a public id + cross-reference. Keys and richer details live in `.vault/owner/`. So a link file is safe to sit anywhere, be moved, even be reader-visible.
5. **Default-deny for the outside world; opt-in access is a first-class capability.** No external app/resource gets vault data by default. But because **in most app workflows the user never sees the raw vault** (the doctor sees a rendered app and steps into a vault *through the app*), an explicit, opt-in way to grant an app access to vault data is a core requirement — not a nice-to-have. Granularity and monitoring (which files were read) come later.
6. **Empower the app workflow.** Both the raw vault UI and the app-only workflow must be fully supported; the app-only one (user never sees the vault) is the massive requirement. "Transparent" includes: occasionally enter a key, or save the key — the user should not be fighting the machinery.

## 3. What Already Exists (code-verified foundations)
Almost every primitive is already built. Citations are to `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/`.

- **Convention-file mechanism (`app.json`/`_page.json`)** — loaded from `.vault/app.json` (preferred) with legacy fallback; `app-shell.js:448` (`_readAppJson`) and `index.html` `_applyAppJson` (~667–762). The UI already "knows there's something here and how to load it." Fields: `entry, auto_open, present, title, resources.{css,js}, auth.{required,prompt}`.
- **`.vault/owner/*` double-encryption** — outer = vault `read_key`; inner = `vault_secret_key` (HKDF-SHA256, info `sgraph-vault-secret-v1`, salt `vault_id`) — `en-gb/vault/token/vault-hkdf.js:25/61/79` (`deriveVaultSecretKey`/`ownerEncrypt`/`ownerDecrypt`). Owner-only files are unreadable to read-only-token holders. `readonly-tokens.json` already uses this (`vault-token-manager.js`).
- **Read-only open from a reference** — `SGVault.openReadOnly(sgSend, vaultId, readKeyB64, refFileId)` (`sg-vault.js:93`); `VaultLoader.openROToken()` resolves+opens (`vault-loader.js:122`). **A sub-vault reference is structurally a stored RO-token payload** `{vault_id, read_key, ref_file_id}` → opening is the path we ship.
- **Open at a specific commit** — `SGVault._loadTreeFromCommit(commitId)` (`sg-vault.js:312`) loads any tree from a commit id → enables the submodule-style "pin to a commit" (§4.5).
- **Lazy loading** — `VaultDataSource.loadAllSubTrees()`/`_ensureLoaded()`/`vault.loadSubTreeOnDemand()` (`vault-data-source.js:40,136`; `sg-vault.js:408`). Sub-vault open is the same lazy model, one level up.
- **Read-only data source** — `new VaultDataSource(vault, /*accessKey*/ null)` ⇒ `writable=false` (`vault-data-source.js:23`). This is how we force read-only inside a sub-vault regardless of how the child was opened.
- **App iframe + VFS bridge (the thing external resources must NOT get)** — same-origin `blob:` URL, `sandbox="allow-scripts allow-forms allow-same-origin"`, full `window.sg.*` bridge (`app-shell.js:609,742,854`). **No external-URL iframe exists anywhere today** (verified) — external embedding and its boundary are genuinely new (§6).
- **Multi-vault navigation** — `VaultLoaderRecent` + `VaultLoader.open()` (`vault-loader.js:42`) already track and open multiple vaults; the "open another vault, keep a back-path" primitives exist.

## 4. Architecture & Design (Rev 2)

### 4.1 The link file — a dumb, movable pointer in the tree
A sub-vault (or external resource) is declared by a small JSON **link file that lives in the regular vault tree**, exactly like a Git submodule's gitlink. It is the convention twin of `app.json`.

- **Naming (recommended, settle-at-build):** a `*.link.json` suffix the UI recognises — e.g. `alice.link.json`, `demos.link.json`. (The lead floated `.vault.ui` / `link` / per-type; `*.link.json` keeps it simple, "named for what it is," no stacked extensions, and lets the *filename* be the label so the **same vault can appear in many places** under different names.)
- **Rendered by an icon**, not shown as raw JSON. A `type:"vault"` link renders as an **expandable folder** (a vault icon); `type:"link|video|app"` renders as an embed launcher.
- **Carries NO secret key.** Only public/non-sensitive fields:
```json
{
  "type": "vault",                 // vault | link | video | app
  "label": "Patient: Alice",       // (filename may also serve as label)
  "vault_id": "abcd1234",          // public id — safe; used to fetch public info
  "ref_id": "lk-a1b2c3d4",         // cross-ref into .vault/owner/{ro,rw}-links (where the key lives)
  "pin": { "mode": "latest" },     // or { "mode":"commit", "commit":"<id>" } — submodule-style
  "description": "Right knee, post-op",
  "url": null                      // for type link/video/app: the external URL
}
```
- **Editable + movable.** Because it is a normal file: edit it (the graphical card, §5.2), and **move a sub-vault between folders/vaults by moving or copying the link file**, then refresh. Moving a whole sub-tree of vaults = moving one small file.
- **Same vault, many places.** Five link files with the same `vault_id` in five folders = the same vault surfaced five ways (by customer / by use case / by hex). No conflict — they are independent pointers.

### 4.2 Where the keys live — two files in `.vault/owner/`
The link file is dumb; the **keys and richer details live in `.vault/owner/`, split into two files by the power of the key they hold** (the lead's `ro-links`/`rw-links`):

| File | Encryption tier | Who can read it | Holds |
|---|---|---|---|
| `.vault/owner/ro-links.json` | `read_key` only (single layer) | any holder of **parent read** access | **read-only** references (read_key / ro-token + `ref_file_id`), description, public-info cache |
| `.vault/owner/rw-links.json` | double-encrypted (owner-secret) | **parent owner only** (full key) | **read-write** references (full child `vault_key`) |

- Cross-referenced by the link file's `ref_id`. The sensitivity of the stored key **matches** the file's tier: read-only keys may be reader-visible (`ro-links`), full keys never leave the owner tier (`rw-links`).
- This answers the brief's open question and the lead's "public vs private links" idea, renamed honestly (everything in a vault is private; the distinction is *read-only* vs *read-write* link).
- A reader of the parent (RO-token holder) can therefore **traverse into `ro-links` sub-vaults** but never sees `rw-links` — exactly the desired behaviour.

### 4.3 How a key is resolved on open (stored, or entered)
When the user expands/opens a `type:vault` link file:
1. **Resolve `ref_id`** in `ro-links.json` (then `rw-links.json` if owner). Found → use that key.
2. **Not found / no stored key** → show the **link card** (§5.2): fetch and show the vault's **public info** (capability from the *next* brief — accounted for here), then **prompt for the key**, offering: *save to `.vault` (`ro`/`rw`-links)*, *save locally* (existing `sg-access-key:` localStorage pattern), or *don't save — ask each time*. (This is the lead's open question — we support all three.)
3. **Open the child read-only** (v1, §4.4) via `openReadOnly` (read key) or `open` (full key, then wrapped read-only), honouring `pin` (§4.5).

### 4.4 Opening & traversing a sub-vault (inline, lazy, read-only in v1)
- On expand, the child vault is opened **lazily** and its tree is **spliced inline** beneath the link-file node — a *virtual folder* backed by a child `VaultDataSource`. Sub-folders within it expand normally. The user experience is "folders all the way down."
- **v1: always read-only inside a sub-vault**, regardless of the key held — wrap the child in `new VaultDataSource(childVault, null)` so no write controls appear. (Per Principle 3; write/recursive-write is a later phase.)
- **"Open in new window"** affordance on a sub-vault → the normal full vault workflow (`/en-gb/vault/#<key>` or `/en-gb/app#<key>`), which may be read-write. To avoid clobbering the parent in `localStorage`, introduce a tracked **`sub-vaults` relationship** (parent key ↔ child key) so "back" returns to the parent. (Directly addresses the lead's localStorage concern.)
- Traversal is a simple walk because everything nested is read-only (no commit/merge bookkeeping across levels in v1).

### 4.5 Submodule-style pinning (default: latest)
- `pin.mode:"latest"` (default) → open the child's current named HEAD. **Users do not have to "sync submodules"** — the common case just shows the latest.
- `pin.mode:"commit"` → open the child at a recorded commit id (via `_loadTreeFromCommit`). Reproducible/frozen views for the future; editable from the link card.

### 4.6 External resources (`type:link|video|app`)
Same link-file convention; `url` set. Rendered as an embed launcher; opened in a **controlled iframe** (`<sg-embed-frame>`, §6) that by default **cannot reach the vault**. `type:app` additionally supports an explicit **opt-in access grant** (§6.3) — the one sanctioned way an external app reads vault data.

## 5. UX & Design (Rev 2)

> The Designer reviewed Rev 1 (`../../../../designer/reviews/05/25/v0.27.62__designer-review__sub-vaults-and-external-resources-ux.md`). Rev 2 **keeps** the Designer's transparency rules for everything that can leak data (external embeds, granted apps) but **reverses the separation model for sub-vaults** per Principle 1. This flip warrants a quick Designer re-pass (§5.5).

### 5.1 Sub-vaults are inline, expandable folders (seamless)
```
┌─ SG/Vault ──────────────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ─────────────────┐ ┌── preview ───────────────────────────────┐ │
│ │ 📁 reports               │ │  knee-score.json …                       │ │
│ │ ▼ 📁 subvaults           │ │                                          │ │
│ │   ▼ 📁 demos             │ │                                          │ │
│ │     ▾ 🗄 acme-demo  ·ro  │ │   ← a sub-vault: expands like a folder    │ │
│ │        📄 readme.md      │ │     (contents loaded on demand)          │ │
│ │        📁 assets         │ │                                          │ │
│ │   ▼ 📁 customers         │ │                                          │ │
│ │     ▸ 🗄 acme       ·ro  │ │                                          │ │
│ │     ▸ 🗄 globex     ·ro  │ │   (globex appears here AND under demos;   │ │
│ │   ▸ 🗄 acme        ·ro   │ │    same vault, two link files)           │ │
│ └─────────────────────────┘ └──────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────────┘
```
- A sub-vault is a tree node that **expands inline** like a folder. The only difference from a plain folder is a **subtle vault glyph (`🗄`) + a tiny access chip (`·ro`/`·rw`)** — enough to be "a little bit aware," never a wall. (Principle 1.)
- Locked sub-vault (no key yet) → the node shows a small `🔒`; clicking opens the link card (§5.2) rather than expanding.

### 5.2 The link card — a miniature "open vault" surface
Clicking a link file (or its `🔒`) shows a small graphical card (the convention's visual form, like `app.json` drives App Mode):
```
┌ 🗄 Linked vault — acme-demo ───────────────────────────────┐
│ Status   🔒 Locked (no key on this device)                  │
│ Public   "ACME product demo · 12 files · updated 24 May"    │   ← public info, no key needed (next brief)
│ Key      [ ro-coral-stamp-5678                            ] │
│ Save     (•) In this vault (ro-links)  ( ) On this device   │
│          ( ) Don't save — ask each time                     │
│ Pin      (•) Latest   ( ) Commit [ ………… ]                   │
│ Notes    [ Right knee post-op …                           ] │
│      [ Open here (read-only) ]   [ Open in new window ↗ ]   │
└──────────────────────────────────────────────────────────────┘
```
- Shows **public info before any key** (the next brief's capability), then prompts. Save choice = the §4.3 three-way. "Open here" splices inline (read-only); "Open in new window" = full workflow with parent/sub-vault tracking.
- Owner sees editable fields (label, notes, pin, key store); a reader sees a read-only card for `ro-links` entries only.

### 5.3 External resources keep the strong boundary (default-deny)
For `type:link|video|app`, the Designer's transparency treatment stays in full: a **sticky, non-dismissable** guarantee banner; two variants — neutral "CANNOT read this vault" and amber "CAN READ /shared (N files) · Granted by you · [Revoke]". This is where "amber = can leak data" lives.
```
🔒 External window · youtube.com · CANNOT read this vault            [Why?]
🟠 External window · mail.example.com · CAN READ /shared (12 files) · [Revoke]
```

### 5.4 The app-only workflow (user never sees the raw vault)
The doctor opens an **app** (e.g. via `/en-gb/app#<key>`), sees the rendered page, and steps **into a specific sub-vault from inside the app** — never touching the tree UI. This means: (a) the link-file/sub-vault machinery must be reachable from the app/VFS layer, and (b) the app must be able to hold an opt-in grant (§6.3). The raw vault UI (§5.1–5.3) and this app-only path are both first-class.

### 5.5 Designer reconciliation & re-pass
- **Kept from the Designer:** sticky/undismissable guarantee banner; amber reserved strictly for data-leak states; the granted-embed state (folder + file-count + user attribution + Revoke); the grant flow behind an Advanced + risk-proportional confirm; honest error/empty/expired/stale-grant states.
- **Reversed (Principle 1):** the "BEYOND THIS VAULT" divider and trust-chips-for-everything approach — sub-vaults are now inline folders with a subtle glyph. **Recommend a short Designer re-pass** on (a) the inline glyph/chip so it reads as "another vault" without breaking flow, and (b) the locked-node + link-card affordance.

## 6. Security Analysis (the boundary that must be right)

### 6.1 Two iframe paths, kept separate
| | App iframe (exists) | External-resource iframe (`<sg-embed-frame>`, new) |
|---|---|---|
| `src` | same-origin `blob:` of vault HTML | **cross-origin** external URL |
| `sandbox` | `allow-scripts allow-forms allow-same-origin` | `allow-scripts allow-popups allow-presentation` — **no `allow-same-origin`** |
| VFS bridge / `message` listener | yes (trusted vault content) | **none by default** |
| Vault access | full | **none (default-deny)** |

Cross-origin + no bridge + no listener + no `allow-same-origin` ⇒ the embed has no path to vault data.

### 6.2 Link-file & key confidentiality
- Link files carry **no keys** (only public `vault_id` + `ref_id`) → safe to move/copy/place anywhere, even reader-visible.
- Read-only keys live in `ro-links` (read-tier); full keys live only in `rw-links` (owner-tier, double-encrypted). Reuses the audited `ownerEncrypt`/`ownerDecrypt`. **Never** put a full key in a link file or in `ro-links`. PKI-ready (encrypt references to recipient public keys when PKI lands).
- CLAUDE.md rule 14/33: keys are secrets — inside the encrypted vault only, never Git, never logs; mask in debug (`_maskKey` exists).

### 6.3 Opt-in app→vault access (Rev 2: first-class v1, not deferred)
Default-deny stays; the sanctioned exception is an **explicit owner opt-in** that lets a `type:app` embed read vault data, because the app-only workflow (user never sees the vault) is core.
- **Grant model (v1, minimal):** owner grants a **scoped, read-only** channel to a named folder (e.g. `/shared`) via the Advanced confirm (§5.3). The embed gets a **narrow, separate** channel — *not* the full `window.sg.*` bridge — exposing only `requestFile(path)` constrained to the granted prefix (parent enforces the prefix). Recorded in the link file's grant + reflected in the amber banner with inline Revoke.
- **Explicitly NOT in v1 (later):** per-file access monitoring/audit, fine-grained capability sets, write grants, time-boxed grants. The lead flagged a future "monitoring and control system of which files are accessed" — design the v1 channel so that layer can wrap it.
- **AppSec asks:** sign off the scoped channel design before build; confirm `<sg-embed-frame>` shares no code with the app bridge; confirm no `message` listener for ungranted embeds; threat-model prefix enforcement and stale-grant fail-closed.

## 7. Implementation Plan (Web UI first)
All in `sgraph_ai_app_send__ui__vault/` (IFD; next minor of v0.2.x). No backend changes for v1 (children reuse existing read endpoints; embeds are client-only).

**Phase 1 — convention + crypto (no UI)**
- `_common/js/lib/links/vault-links.js` (new): parse/validate the `*.link.json` schema; `loadRoLinks(vault)` / `loadRwLinks(vault)` (read `.vault/owner/ro-links.json` via `read_key`; `rw-links.json` via `ownerDecrypt`); `resolveKey(refId)`; `saveLink*`/`saveRoRwEntry`. Mirrors `vault-token-manager`.
- Move `vault-hkdf.js` → `_common/js/lib/crypto/` (shared by tokens + links).

**Phase 2 — read-side: inline sub-vaults**
- Teach the browse tree (`vault-data-source.js` / `send-browse` / `vault-shell.js`) to recognise `*.link.json`, render it as a **virtual folder** (vault glyph + access chip), and on expand open the child **read-only** (lazy) and splice its tree in. Add the parent/sub-vault `localStorage` relationship + "open in new window".
- `<sg-link-card>` (new): the §5.2 card (public info → key prompt → save choice → pin → open).
- `<sg-embed-frame>` (new): the controlled external iframe + sticky banner (§6.1).

**Phase 3 — write-side (owner) + opt-in app grant**
- Owner "Add / Edit / Move" for link files (extend `vault-browse-edit.js`); write `ro-links`/`rw-links` via Phase 1.
- The minimal scoped app-grant channel (§6.3) + amber granted banner + Revoke.

**Phase 4 — follow-on (separate brief):** write-inside-sub-vault (commits across levels), recursive write, CLI clone-within-clone, per-file access monitoring/granular grants.

## 8. Testing / QA Plan
No mocks; in-memory stack; Playwright for E2E. Changelog entry + QA brief accompany the build.

- **Unit:** `*.link.json` parse/validate (malformed dropped, not thrown); `ro-links`/`rw-links` round-trip; `ref_id` resolution; pin latest vs commit.
- **Crypto:** `ro-links` decrypts with `read_key`; `rw-links` decrypts only owner-side; an RO-token holder of the parent **can** resolve `ro-links` but **cannot** read `rw-links`.
- **Security (priority):** `<sg-embed-frame>` exposes no `window.sg`/no listener; sandbox lacks `allow-same-origin`; granted app channel is read-only + prefix-enforced + **fails closed** on a stale/missing folder; ungranted app gets nothing.
- **E2E:** inline expand of a sub-vault (read-only, lazy — assert child not fetched until expand); same vault under two link files; move a link file → sub-vault relocates; lock → link-card → enter key → save choices; "open in new window" returns to parent (relationship tracked); YouTube embed renders with sticky banner; expired/unreachable child → failure card, never a dead node.
- **Changelog test-impact:** *Should break (good):* browse-tree snapshots (virtual folders), action-bar (Add link). *Should NOT break (bad):* `app.json`/`_page.json`, RO-token open, lazy-folder loading, the app VFS bridge.
