## 1. What This Pack Covers (the why, how, what)

Three human briefs ask for one coherent capability:

| Brief | Date | The ask |
|---|---|---|
| `vaults-within-vaults-nested-vault-access` (dev) | 24 May | A vault can **open and read other vaults** it references. Driving use case: a doctor's parent vault reading many per-patient vaults. No backend complexity. |
| `sg-send-sub-vaults-workflow-access-points` (arch) | 25 May | Implement nesting as a **convention** (Git-submodule model), built on the existing `.vault` folder + read-only-token double-encryption. **Web UI first**; **pre-initialise on access** (lazy). |
| `sg-send-vault-conventions-and-external-resources` (arch) | 25 May | Codify the references as **convention files** uniform with `app.json`/`_page.json`; extend the same pattern to **embed external resources** (video, link, external app) in a **controlled iframe** (default-deny; selectively grant). |

**The why.** A vault should be able to point at other vaults and at the outside world, with access governed by the keys the user holds, *without* new backend machinery or new vault primitives. This unlocks the doctor/admin "parent vault over many child vaults" workflow and a controlled plugin/embed model.

**The how.** A lightweight *link file* in the vault tree (a Git-submodule-style pointer that carries no key) plus key/detail records in `.vault/owner/`. The Vault Web UI reads them and either **splices the child vault inline** (so a sub-vault behaves exactly like a folder) or **embeds an external resource** in a locked-down iframe with no vault access by default.

**The what.** Mostly wiring existing parts together — read-only-open, lazy sub-tree loading, `.vault` double-encryption, the convention-file mechanism — behind one new file convention.

## 2. Principles (these govern every decision below)

1. **Transparency = invisibility for sub-vaults.** When this is right the user is *barely* aware they crossed into another vault: they just **expand a folder**. Sub-vaults nest and proliferate exactly like folders (`demos/`, `customers/`, `xyz/` may each *be* a sub-vault). There is **no separate "section" or divider** for them — that only adds friction. A subtle, honest indicator stays (a vault glyph + a tiny access chip) so the user is "a little bit aware."
2. **Access is governed by the key, not the relationship.** A read-only key gives read-only; a read-write key gives read-write; the UI does not change. A read-only parent can hold a child the user has read-write to, and vice-versa — access is per-key and independent at each level.
3. **v1: read-only inside sub-vaults.** Editing a child means commit/sync bookkeeping we have not built for the nested case, so **v1 always opens a sub-vault read-only, regardless of the key held.** Writing, recursive write, and create-child are a later phase. This makes traversal a simple walk down the tree.
4. **Keep the secrets in `.vault`; keep the tree file dumb.** The link file in the tree carries **no key** — only a public id + a cross-reference. Keys and richer details live in `.vault/owner/`. A link file is therefore safe to sit anywhere, be moved, even be reader-visible.
5. **Default-deny for the outside world; opt-in access is a first-class capability.** No external app/resource gets vault data by default. But because **in most app workflows the user never sees the raw vault** (a doctor sees a rendered app and steps into a vault *through the app*), an explicit, opt-in way to grant an app scoped access to vault data is a core v1 requirement. Granularity and per-file monitoring come later.
6. **Empower the app workflow.** Both the raw vault UI and the app-only workflow (user never sees the vault) are first-class; the app-only one is the larger requirement. "Transparent" includes occasionally entering a key, or saving the key — the user should never be fighting the machinery.

## 4. Architecture & Design

### 4.1 The link file — a dumb, movable pointer in the tree
A sub-vault (or external resource) is declared by a small JSON **link file that lives in the regular vault tree**, exactly like a Git submodule's gitlink. It is the convention twin of `app.json`.

- **Naming convention:** any filename ending in **`.link.json`**. The **prefix is a user-chosen label** (`acme-demo.link.json`, `.health-score.link.json`); the **`.link.json` suffix is the sole signal** that tells the UI to treat the file specially.
- **This is a feature, not just a name.** If the user renames a link file *away* from the suffix — e.g. `acme-demo.link.json` → `acme-demo.link-2.json` — the UI stops treating it specially and shows it as a **plain `.json` file**. Two consequences: (a) renaming is a trivial "disable this link" gesture; (b) it reinforces why **no confidential data may ever live in a link file** — it is just a normal vault file that happens to match a suffix, and could be viewed as raw JSON at any time.
- **Rendered by an icon, never as raw JSON** when the suffix matches. A vault link renders as an **expandable folder** (vault glyph); a link/video/app renders as an embed launcher. (The `type` used to pick the icon comes from the resolved owner record, §4.2 — optionally cached as an override hint, below.)
- **Deliberately minimal — only `vault_id` + `ref_id` are required.** All other metadata (`type`, `label`, `pin`, `description`, `url`) lives **once in the owner record** keyed by `ref_id` (§4.2); the link file may **override any of those fields** per location when needed. The common case is two fields:
```json
// minimal link file — the common case
{ "vault_id": "abcd1234", "ref_id": "lk-a1b2c3d4" }

// with optional per-location overrides of owner-record fields
{ "vault_id": "abcd1234", "ref_id": "lk-a1b2c3d4",
  "label": "Patient: Alice (post-op)",
  "pin":   { "mode": "commit", "commit": "<id>" } }
```
- **External resources** (`type` link/video/app) have no `vault_id` — the link file is just `{ "ref_id": "lk-…" }` (+ optional overrides); `type`/`url` come from the owner record.
- **Why centralise the metadata.** The canonical `type`/`label`/`pin`/`description`/`url` (and the key) live once in `.vault/owner/{ro,rw}-links.json`. **Many link files can share one `ref_id`** — edit the record once and every pointer updates; per-link overrides handle the exceptions. This is what makes "the same vault in five places" cheap to create and maintain, and keeps the in-tree file trivial to author by hand.
- **Carries NO secret key** — `vault_id`/`ref_id` and any overridden labels/pins are non-sensitive; the key never appears here (§4.2).
- **Editable + movable.** Because it is a normal file: edit it (via the link card, §5.2), and **move a sub-vault between folders/vaults by moving or copying the link file**, then refresh. Moving a whole sub-tree of vaults = moving one small file.
- **Same vault, many places.** Several link files with the same `vault_id`, in several folders, surface the same vault several ways (by customer / by use case / by hex). They are independent pointers — no conflict.

### 4.2 Where the keys + canonical metadata live — two files in `.vault/owner/`
The link file is dumb; the **key *and* the canonical metadata live in `.vault/owner/`, in a record keyed by `ref_id`**, split into two files by the power of the key they hold:

| File | Encryption tier | Who can read it | Holds (per `ref_id` record) |
|---|---|---|---|
| `.vault/owner/ro-links.json` | `read_key` only (single layer) | any holder of **parent read** access | `type`, `label`, `pin`, `description`, `url`, public-info cache, **+ read-only reference** (`read_key` / ro-token + `ref_file_id`) |
| `.vault/owner/rw-links.json` | double-encrypted (owner-secret) | **parent owner only** (full key) | same metadata fields **+ read-write reference** (full child `vault_key`) |

Each record looks like:
```json
{ "lk-a1b2c3d4": {
    "type": "vault", "label": "Patient: Alice", "pin": { "mode": "latest" },
    "description": "health-score record, post-op", "url": null,
    "read_key": "<b64>", "ref_file_id": "ref-pid-muw-…" } }
```
- A `ref_id` resolves to exactly one record (look in `ro-links` first, then `rw-links` if owner). The record carries both the **key** and the **default metadata**; a link file may override individual metadata fields.
- The sensitivity of the stored key **matches** the file's tier: read-only keys may be reader-visible (`ro-links`), full keys never leave the owner tier (`rw-links`).
- A read-only holder of the parent can therefore **resolve `ro-links` records** (and traverse those sub-vaults) but never sees `rw-links`. (Everything in a vault is private; the `ro`/`rw` distinction is the *power of the link*, not public-vs-private.)

### 4.3 How metadata + a key are resolved on open
The **effective value of any field is `link-file override ?? owner-record value`.** When the user expands/opens a link file:
1. **Resolve `ref_id`** in `ro-links.json` (then `rw-links.json` if owner) → the record's `type`, metadata, **and key**. Apply any link-file overrides on top.
2. **No key in the record** → also check browser `localStorage` (the existing `sg-access-key:` pattern) for a locally-saved key.
3. **Still nothing** → show the **link card** (§5.2): fetch + show the vault's **public info first** (a capability from the per-vault public-info brief — accounted for here), then **prompt for the key**, offering three save choices: *save into `.vault` (`ro`/`rw`-links record)*, *save on this device (`localStorage`)*, or *don't save — ask each time*. All three supported.
4. **Open the child read-only** (v1, §4.4) via `openReadOnly` (read key) or `open` (full key, then wrapped read-only), honouring the effective `pin` (§4.6).

(If a link file has a `ref_id` with no resolvable record — e.g. a reader hitting an `rw-links`-only ref — it renders as locked/unavailable; it cannot be opened, which is correct.)

### 4.4 Opening a sub-vault — two distinct modes
There are two ways to open a sub-vault, and they behave very differently. **Inline = read-only, same tab; new window = full session, independent tab.**

**(a) Inline expand (read-only, in the same tab) — the default.**
- On expand, the child vault is opened **lazily** and its tree is **spliced inline** beneath the link-file node — a *virtual folder* backed by a child `VaultDataSource`. Sub-folders expand normally; the experience is "folders all the way down."
- **v1: always read-only**, regardless of the key held — wrap the child in `new VaultDataSource(childVault, null)` so no write/upload/new-file controls appear. (Principle 3.)
- **Recursive sub-vaults** are supported structurally — a sub-vault may itself contain link files, opened the same lazy read-only way (it is just a pointer; deep *write* is deferred).
- **The tab's "current vault" never changes** — Vault A stays loaded; the child is only *read in* to render. Collapsing the node returns to A. So there is **no storage juggling and no "back" state** for this mode.

**(b) Open in new window (full, read-write, independent tab).**
- `window.open('/en-gb/vault/#' + childKey, '_blank', 'noopener')` — a normal full `/vault` session for the child (read-write if the key allows). The child's key comes from A's owner-only `rw-links` record; it travels in the URL **hash** (client-only, never sent to the server — the existing key-in-`#` pattern) and `noopener` keeps the new tab fully independent.
- **There is no "back" and no parent relationship** for this mode — it is a separate, standalone session (per your clarification). The requirements are instead **per-tab reload correctness** and **close = no-op**, which fall out of per-tab identity (§4.5).

### 4.5 Per-tab vault identity (makes multi-window correct)
Today the "current vault" lives in **`localStorage` (`sg-vault-key`, `vault-loader-storage.js:34`) — shared across all tabs**, so a second vault in a new tab would clobber the first. The fix: **the current-vault identity becomes per-tab (`sessionStorage`)**, with `localStorage` demoted to a "last-opened" convenience default for a brand-new tab.
- **Open-in-new-window** puts the child key in the new tab's hash; the `/vault` page **adopts the hash as this tab's identity** (write `sessionStorage`, then `history.replaceState` to strip the hash). This requires `runVault()` (`vault-loader-routing.js:94`, which today *discards* the token hash) to treat a token hash as a **per-tab inbox**.
- **Reload** of any tab reads its own `sessionStorage` → reopens its own vault (A reloads A; B reloads B). **Closing** a tab discards its `sessionStorage` → no-op for the others.
- **Resolution order on `/vault` load:** `hash token (adopt → sessionStorage → strip)` ▸ else `sessionStorage` current key ▸ else `localStorage sg-vault-key` (legacy default; copied into `sessionStorage` so the tab is then pinned).
- The read-write gate (`sg-vault-access-key`) is already per-tab `sessionStorage`, so independent write access needs no extra work. Use the hash, never the query string.

### 4.6 Submodule-style pinning (default: latest)
- `pin.mode:"latest"` (default) → open the child's current named HEAD. **Users never have to "sync submodules"**; the common case just shows the latest.
- `pin.mode:"commit"` → open the child at a recorded commit id (via `_loadTreeFromCommit`) for reproducible/frozen views. Editable from the link card.

### 4.7 External resources (`type` = `link | video | image | app`)
A link file with one of these types points at an external `url`. **Rendering and the security boundary differ by type — not everything is an iframe:**

| `type` | Rendered as | Boundary | Notes |
|---|---|---|---|
| `image` | `<img src>` (reuse the vault's image/gallery viewer) | media element — cannot reach parent DOM/vault | a `.png`/`.jpg`/`.webp`/`.svg` URL |
| `video` (file) | `<video src>` | media element | a direct `.mp4`/`.webm` URL |
| `video` (provider) | provider `<iframe>` (embed URL) | cross-origin iframe, no bridge/listener | `provider:"youtube"` etc. |
| `link` (web page / HTML) | sandboxed `<sg-embed-frame>` | cross-origin iframe, locked sandbox, no bridge (§6.1) | arbitrary external page |
| `app` | sandboxed `<sg-embed-frame>` | as `link`, **plus** optional opt-in grant (§6.3) | the plugin model |

- **Default-deny holds for every type** — none can read the vault. Media elements (`<img>`/`<video>`) inherently cannot reach the parent; web pages/apps are isolated by §6.1.
- **Click-to-load (the privacy default, §6.4).** Every external type renders as a **placeholder until the user clicks to load**, so opening a vault never auto-phones-home to a third party. After load, the sticky guarantee banner (§5.3) applies.
- **Add-UI enumeration + URL auto-detect (§5.3):** the owner chooses *Linked vault / Web page / Video / Image / External app*, but `type` is **auto-detected from the pasted URL** where possible (YouTube/Vimeo → `video`+`provider`; `.png/.jpg/.gif/.webp/.svg` → `image`; `.mp4/.webm` → `video` file; otherwise → `link`).

┌─ SG/Vault ──────────────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ─────────────────┐ ┌── preview ───────────────────────────────┐ │
│ │ 📁 reports               │ │  health-score.json …                     │ │
│ │ ▼ 📁 subvaults           │ │                                          │ │
│ │   ▼ 📁 demos             │ │                                          │ │
│ │     ▾ 🗄 acme-demo  ·ro  │ │   ← a sub-vault: expands like a folder    │ │
│ │        📄 readme.md      │ │     (contents loaded on demand)          │ │
│ │        📁 assets         │ │                                          │ │
│ │   ▼ 📁 customers         │ │                                          │ │
│ │     ▸ 🗄 acme       ·ro  │ │   (acme appears here AND under demos —    │ │

- A sub-vault is a tree node that **expands inline** like a folder. The only difference from a plain folder is a **subtle vault glyph (`🗄`) + a tiny access chip (`·ro`/`·rw`)** — enough to be "a little bit aware," never a wall.
- A locked sub-vault (no key yet) shows `🔒`; clicking opens the link card (§5.2) rather than expanding.

### 5.2 The link card — a miniature "open vault" surface
Clicking a link file (or its `🔒`) shows a small graphical card (the convention's visual form, the way `app.json` drives App Mode):
```
┌ 🗄 Linked vault — acme-demo ───────────────────────────────┐
│ Status   🔒 Locked (no key on this device)                  │
│ Public   "ACME product demo · 12 files · updated 24 May"    │   ← public info, shown before any key
│ Key      [ ro-coral-stamp-5678                            ] │
│ Save     (•) In this vault (ro-links)  ( ) On this device   │
│          ( ) Don't save — ask each time                     │
│ Pin      (•) Latest   ( ) Commit [ ………… ]                   │
│ Notes    [ Right health-score record, post-op …          ] │
│      [ Open here (read-only) ]   [ Open in new window ↗ ]   │
└──────────────────────────────────────────────────────────────┘
```
- Shows **public info before any key**, then prompts. Save choice = the §4.3 three-way. "Open here" splices inline (read-only); "Open in new window" = full workflow with parent/sub-vault tracking.
- Owner sees editable fields (label, notes, pin, key store); a reader sees a read-only card for `ro-links` entries only.

### 5.3 External resources keep the strong boundary (default-deny)
External resources of every type (`image`/`video`/`link`/`app`) render as a **click-to-load placeholder** first (privacy, §6.4): `[ ▶ Load external video from youtube.com — this will contact youtube.com ]`. After the user loads it, web pages/apps get the **sticky, non-dismissable** guarantee banner — two states; **amber appears only when data can leak**:
```
🔒 External window · youtube.com · CANNOT read this vault                 [Why?]
🟠 External window · mail.example.com · CAN READ /shared (12 files) · Granted by you · [Revoke]
```
Granting an app access is an explicit owner action behind an **Advanced disclosure + a risk-proportional confirm** that names the site, folder, and file count (never a one-click toggle).

**Owner Add menu** (writable vaults): *Linked vault · Web page · Video · Image · External app*. The type is **auto-detected from the pasted URL** (§4.7) so the user rarely picks manually; the chosen/detected `type` and `url` are stored in the owner record (§4.2).

### 5.4 The app-only workflow (user never sees the raw vault)
A doctor opens an **app** (e.g. `/en-gb/app#<key>`), sees the rendered page, and steps **into a specific sub-vault from inside the app** — never touching the tree UI. This requires (a) the link-file/sub-vault machinery to be reachable from the app/VFS layer, and (b) the app to be able to hold an opt-in grant (§6.3). The raw vault UI (§5.1–5.3) and this app-only path are both first-class.

## 6. Security Analysis (the boundary that must be right)

### 6.1 Two iframe paths, kept separate
| | App iframe (exists) | External-resource iframe (`<sg-embed-frame>`, new) |
|---|---|---|
| `src` | same-origin `blob:` of vault HTML | **cross-origin** external URL |
| `sandbox` | `allow-scripts allow-forms allow-same-origin` | `allow-scripts allow-popups allow-presentation` — **no `allow-same-origin`** |
| VFS bridge / `message` listener | yes (trusted vault content) | **none by default** |
| Vault access | full | **none (default-deny)** |

Cross-origin **and** no bridge **and** no listener **and** no `allow-same-origin` ⇒ the embed has no path to vault data.

### 6.2 Link-file & key confidentiality
- Link files carry **no keys** (only a public `vault_id` + `ref_id`) → safe to move/copy/place anywhere, even reader-visible. The `.link.json`-suffix rule means a link file is just a normal vault file; treat it as readable raw JSON at any moment, so it must never hold a secret.
- Read-only keys live in `ro-links` (read-tier); full keys live only in `rw-links` (owner-tier, double-encrypted). Reuses the audited `ownerEncrypt`/`ownerDecrypt`. **Never** put a key in a link file or a full key in `ro-links`. PKI-ready (encrypt references to recipient public keys when PKI lands).
- CLAUDE.md rule 14/33: keys are secrets — inside the encrypted vault only, never Git, never logs; mask in debug (`_maskKey` exists).

### 6.3 Opt-in app→vault access (first-class in v1)
Default-deny stays; the sanctioned exception is an **explicit owner opt-in** that lets a `type:app` embed read vault data, because the app-only workflow (user never sees the vault) is core.
- **v1 grant model (minimal):** the owner grants a **scoped, read-only** channel to a named folder (e.g. `/shared`) via the Advanced confirm (§5.3). The embed gets a **narrow, separate** channel — *not* the full `window.sg.*` bridge — exposing only `requestFile(path)` constrained to the granted prefix (the parent enforces the prefix). Recorded against the link file's grant and reflected in the amber banner with inline Revoke.
- **Explicitly later (not v1):** per-file access monitoring/audit, fine-grained capability sets, write grants, time-boxed grants. The lead flagged a future "monitoring and control of which files are accessed"; design the v1 channel so that layer can wrap it.
- **AppSec asks:** sign off the scoped channel before build; confirm `<sg-embed-frame>` shares no code with the app bridge; confirm no `message` listener for ungranted embeds; threat-model prefix enforcement and stale-grant fail-closed.

### 6.4 External fetch is observable (privacy) — hence click-to-load
Embedding *any* external resource — even an `<img>` — makes an outbound request that leaks the viewer's IP, referrer, and "someone is viewing this" to the third party (the classic tracking-pixel surface). The vault's *contents* stay secret, but the *act of viewing* becomes observable to the external host. For a zero-knowledge product this matters, so:
- **Click-to-load is the default for every external type** (§5.3): nothing is fetched from a third party until the user explicitly loads it. Opening a vault, or a folder full of resource links, phones home to nobody.
- This also defends against malicious/expired link files quietly beaconing on open.
- Media elements (`<img>`/`<video>`) cannot read the vault, but they *do* phone home — so the privacy treatment applies to them too, not just iframes.

## 7. Implementation Plan (Web UI first)
> Detailed hand-off spec (exact schemas, module signatures, the splice design, per-tab identity, component contracts, assertion-level tests, phase checklists): [`v0.27.62__implementation-plan__sub-vaults-and-external-resources.md`](../../../../dev/reviews/05/25/v0.27.62__implementation-plan__sub-vaults-and-external-resources.md). The summary below is the shape; that doc is what a coding session executes.

All in `sgraph_ai_app_send__ui__vault/` (IFD; the next minor of v0.2.x). No backend changes for v1 (children reuse existing read endpoints; embeds are client-only). The CLI does not change in v1 — it will simply see `.link.json` and `ro/rw-links` as ordinary files and gain clone-within-clone behaviour in a later phase.

**Phase 0 — the thinnest vertical slice (prove the loop end-to-end first).**
Before any owner-management or `.vault/owner` writing, ship the smallest path that opens one sub-vault inline, reusing only the **existing create-file plumbing**:
1. Author a `*.link.json` by hand using the existing **New File** button (`vault-browse-edit.js:769/829`) — or upload one. (No new "Add" UI yet.)
2. Recognise the `.link.json` suffix in the tree and render it as an expandable folder (vault glyph + chip).
3. On expand, resolve the key from **`localStorage` / a one-shot prompt** (the "ask each time" path — *no* `.vault/owner` reading yet), open the child **read-only** via `openReadOnly`, splice its tree inline.
This gives a working sub-vault with zero new persistence. It de-risks the hard part (the virtual-folder splice) on its own, and everything after it is additive.

## 8. Testing / QA Plan
No mocks; in-memory stack; Playwright for E2E. A changelog entry + QA brief accompany the build.

- **Unit:** `.link.json` suffix recognition (a file renamed off the suffix is treated as a plain `.json`); link-file parse/validate (malformed dropped, not thrown); `ro-links`/`rw-links` round-trip; `ref_id` resolution incl. `localStorage`; **metadata merge — `link-file override ?? owner-record value` (incl. two link files sharing one `ref_id`; an override changes only that pointer)**; pin latest vs commit.
- **Crypto:** `ro-links` decrypts with `read_key`; `rw-links` decrypts only owner-side; a read-only holder of the parent **can** resolve `ro-links` but **cannot** read `rw-links`.
- **Security (priority):** `<sg-embed-frame>` exposes no `window.sg` and registers no `message` listener; sandbox lacks `allow-same-origin`; the granted app channel is read-only, prefix-enforced, and **fails closed** on a stale/missing folder; an ungranted app gets nothing.
- **External-resource rendering + privacy:** `type:image` renders via `<img>` (not an iframe); URL auto-detection maps extensions/providers to the right `type`; **click-to-load — assert no third-party request fires until the user clicks Load** (covers image/video/link/app); the sticky banner appears after load.
- **E2E:** inline expand of a sub-vault (read-only, lazy — assert the child is not fetched until expand); recursive sub-vault expands; same vault under two link files; move a link file → sub-vault relocates; rename off the suffix → shows as plain JSON; locked node → link card → enter key → each save choice; **multi-window:** "open in new window" opens child B in its own tab; **reload A → A, reload B → B** (per-tab `sessionStorage`); **closing B is a no-op** for A; a `video` embed renders with the sticky banner; expired/unreachable child → friendly failure, never a dead node.
- **Changelog test-impact:** *Should break (good):* browse-tree snapshots (virtual folders), action-bar (Add link). *Should NOT break (bad):* `app.json`/`_page.json` flows, RO-token open, lazy-folder loading, the app VFS bridge.

## 9. Decisions (settled)
| Topic | Decision |
|---|---|
| Link-file name | Any filename ending **`.link.json`**; the prefix is a user label, the suffix is the UI signal. Renaming off the suffix → treated as a plain `.json` (a deliberate "disable" gesture and a reason link files hold no secrets). |
| Where child keys are stored | All three supported, chosen in the link card: `.vault/owner/{ro,rw}-links`, browser `localStorage`, or prompt-each-time. |
| Link-file contents vs owner records | Link file is minimal: `vault_id` + `ref_id` (+ optional per-location overrides). **Canonical metadata (`type`/`label`/`pin`/`description`/`url`) and the key live once in the owner record keyed by `ref_id`**; effective value = `link-file override ?? record`. Many link files can share one `ref_id`. |
| ro vs rw records | `ro-links.json` (read_key-encrypted, read-only refs) + `rw-links.json` (owner-only double-encrypted, full-key refs); each holds the metadata record + key for its `ref_id`s. |
| Write inside a sub-vault | **No in v1** — read-only always. Deferred until nested commit/push management exists. |
| Recursive sub-vaults | Supported structurally (read-only walk); deep write deferred. |
| External resource types | `link` (web page) · `video` (file or provider e.g. YouTube) · `image` · `app`. Rendering differs by type (media element vs sandboxed iframe, §4.7); Add UI auto-detects `type` from the URL. |
| External fetch privacy | **Click-to-load** by default for every external type — no third-party request until the user opts in (§6.4). |
| App→vault access grant | v1: scoped read-only `requestFile` channel; monitoring/granularity later. |
| CLI clone-within-clone | Phase 4 — get the UI right first; the CLI sees these as ordinary files until then. |

## 11. Risks
1. **Inline sub-vaults blur "am I in another vault?"** → subtle glyph + access chip + a slim context bar on deep entry (see design review).
2. **External embed reaching vault data** → the §6.1 boundary; the priority test suite enforces it.
3. **Opt-in grant is the deliberate hole** → scoped read-only, prefix-enforced, fail-closed, Revoke, amber banner; AppSec sign-off; monitoring later.
4. **A key placed in a link file by mistake** → schema forbids keys in link files; keys only in `ro`/`rw-links`; the `.link.json`-as-plain-JSON property makes the rule self-evident; lint/test guard.
5. **Write-inside-child scope creep** → explicitly excluded from v1.
