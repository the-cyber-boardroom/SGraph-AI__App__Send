## 1. Executive summary

`dev.send.sgraph.ai` returns the branded **404 "Page not found"** on the root and almost every page. This is **not a code bug in any UI tree** — it is a **deploy collision**.

Three independent GitHub Actions pipelines publish the user-facing site:

- `deploy-ui-user.yml`  → legacy v0.3.x tree (`/` redirect, `/en-gb/` landing + wizard, legacy receiver pages)
- `deploy-ui-share.yml` → v0.4.0 sender tree (`/en-gb/share/`)
- `deploy-ui-open.yml`  → v0.4.0 receiver tree (`/en-gb/open/`)

**All three deploy to the same S3 prefix** — `--site sgraph-send` → `s3://<bucket>/websites/sgraph-send/<env>/latest/` (`scripts/deploy_static_site.py:413`). Each one runs **`--clean-latest` on push**, and `--clean-latest` does `aws s3 rm --recursive` on the **entire** `latest/` prefix (`scripts/deploy_static_site.py:267-284`), not just its own slice. So every push that touches one tree **deletes the other two trees' files**. Whichever of user/share/open deployed last is the only slice that survives; everything else 404s.

The v0.4.0 share/open work merged to `dev` between `bda2d5ca` (Phase A0, 2026-05-12) and `cfb83e11` (Phase B sub-commit 7, 2026-05-14). Those deploys wiped the v0.3.x `__user` tree's root `index.html` and `/en-gb/` landing out of `latest/`, so `/` → no object → CloudFront serves the still-present `404.html` → the screenshot.

There are **two distinct collisions** on the shared prefix:

1. **`--clean-latest` mutual wipe** (the catastrophic, blocking one) — **FIXED in this branch** (§5).
2. **Shared `latest/_common/` across two majors** — v0.3.x and v0.4.0 ship **63 files at the same relative path** with different content; they overwrite each other on overlay. This is the deeper hazard and needs a design decision (§6).

## 2. The deploy topology (code-verified)

```
S3 bucket: <account>--static-sgraph-ai--eu-west-2

  websites/sgraph-send/<env>/
    releases/v0/v0.3/v0.3.x/   ← __user archive       (rollback source)
    releases/v0/v0.4/v0.4.0/   ← __share / __open archive
    latest/                    ← SERVED PREFIX (CloudFront origin path)
      index.html               ← __user        (root locale redirect)
      404.html                 ← any tree
      _common/                 ← __user + __share + __open  ⚠ SHARED
      en-gb/
        index.html             ← __user        (old wizard)
        welcome/               ← __user
        browse|download|gallery|v|view|s/  ← __user (legacy receiver)
        share/                 ← __share v0.4.0
        open/                  ← __open  v0.4.0
```

- CloudFront serves the domain from `…/latest/`. Relative `_common/` references therefore all resolve to `latest/_common/`:
  - v0.3.x `en-gb/index.html` uses `../_common/` → `latest/_common/`
  - v0.4.0 `en-gb/share/index.html` uses `../../_common/` → `latest/_common/` (`__share/.../en-gb/share/index.html:64`)
- `vault` (`--site sgraph-vault`) and `workspace` (`--site sgraph-workspace`) use **separate** site prefixes, so they are **not** part of this collision. (The vault routing work is blocked from merging only because `dev` itself is broken, not because vault shares the prefix.)

## 3. Collision A — `--clean-latest` mutual wipe (root cause of the 404)

All three workflows share this logic (e.g. `deploy-ui-share.yml`, pre-fix):

```bash
CLEAN_REQUESTED="${{ inputs.clean_latest }}"   # EMPTY on push events
...
if [ "$VERSION" == "$FIRST" ]; then
  if [ "$CLEAN_REQUESTED" != "false" ]; then   # "" != "false" → TRUE on every push
    EXTRA_FLAGS="--clean-latest"
  fi
fi
```

On a `push` trigger there is no `inputs.clean_latest`, so `CLEAN_REQUESTED` is empty, `"" != "false"` is **true**, and `--clean-latest` is applied. `--clean-latest` calls:

```python
# scripts/deploy_static_site.py:267
aws s3 rm --recursive s3://<bucket>/websites/sgraph-send/<env>/latest/
```

i.e. it deletes **the whole shared prefix**, including the sibling trees. The pipelines are mutually destructive. The `paths:` filters are tree-specific, so a normal merge that touches only `__share/v0/v0.4/**` triggers only the share pipeline — which wipes user + open and republishes only `/en-gb/share/`.

**This is the architectural defect behind the screenshot.**

---

## 4. Collision B — shared `latest/_common/` across two majors (the deeper hazard)

Even with Collision A fixed, the three trees still write `_common/` to the **same** `latest/_common/`. Evidence: **63 `_common/` files share the identical relative path** in `__user/v0.3.0/_common/` and `__share/v0.4.0/_common/`, including content-divergent files:

- `js/api-client.js` — v0.4.0 merged the v0.3.2 patch (added `downloadBase64`, `deleteTransfer`)
- `js/components/send-upload/send-upload.js` — v0.4.0 unified three overlays into one state machine
- `js/components/send-upload/upload-step-done/upload-step-done.js` — v0.4.0 unified file+secret Done
- `js/components/send-upload/upload-step-select/…`, `upload-constants.js`, etc.

The overlay sync (no `--delete`) means `latest/_common/` becomes the **union**, with same-name files resolved **last-writer-wins**. Consequences:

- If a v0.3.x deploy runs last, `latest/_common/api-client.js` reverts to the old version → the **live v0.4.0 share app breaks** (missing methods).
- If a v0.4.0 deploy runs last, the old `/en-gb/` wizard loads v0.4.0's `send-upload.js` (different state machine; references steps like `upload-step-delivery` that no longer exist) → the **legacy wizard breaks**.

**Two majors of the same app cannot safely share one `_common/`.** The v0.4.0 plan's §9 "additive behaviours" assumption (new paths are purely additive) overlooked both `_common/` and the `--clean-latest` wipe.

Note: `__share` and `__open` `_common/` are required to be byte-identical (the `check-common-checksums.yml` CI guard enforces this), so share↔open is consistent. The conflict is strictly **v0.3.x ↔ v0.4.0**.

## 5. Fix implemented in this branch — scoped clean

The blocking defect (Collision A) is fixed by making the clean **scoped to each tree's own URL slice** instead of nuking the whole shared prefix.

**`scripts/deploy_static_site.py`** — new `--clean-prefixes` option and `clean_prefixes()` helper. It `aws s3 rm`s only the named sub-paths under `latest/` (recursive for directory prefixes, single-key for paths with a file extension), and tolerates missing prefixes. `--clean-prefixes` takes precedence over `--clean-latest`; `--clean-latest` is left intact for the isolated single-tree sites (vault, workspace).

**Workflows** — each `sgraph-send` pipeline now cleans only what it owns:

| Workflow | Owns / cleans |
|---|---|
| `deploy-ui-user.yml`  | `index.html en-gb/index.html en-gb/welcome en-gb/browse en-gb/download en-gb/gallery en-gb/v en-gb/view en-gb/s` |
| `deploy-ui-share.yml` | `en-gb/share` |
| `deploy-ui-open.yml`  | `en-gb/open` |

None of them clean `_common/` (it is shared — see §6). After this fix, the three trees coexist in `latest/`; a deploy of one no longer deletes the others. Verified via `--dry-run`: a share deploy now reports `Would delete …/latest/en-gb/share` only, instead of all of `latest/`.

**This stops the bleeding** — root `/` and `/en-gb/share/` and `/en-gb/open/` all survive. It does **not** by itself resolve Collision B (see §6).

## 6. Decisions REQUIRED to present v0.4.0 cleanly

Scoped clean makes the site reachable again, but two architectural decisions remain. **Both touch routing/`_common`; neither should be made unilaterally by a dev/CI change.**

### Decision 1 — `_common/` isolation strategy (resolves Collision B)

Options, in increasing order of correctness:

- **(a) Accept last-writer, sequence deploys so v0.4.0 wins.** Cheapest. Fragile: any future v0.3.x push re-breaks the live app. Acceptable only as a stopgap while v0.3.x is frozen.
- **(b) Tree-local `_common/`.** Move each tree's `_common/` under its own served path (e.g. share references `_common/` at `latest/en-gb/share/_common/`) by changing the shells' `../../_common/` reference and the deploy layout. No CloudFront change. Contradicts the plan's root-level `_common/` layout, so it is a deliberate revision. **Recommended interim.**
- **(c) `tools.sgraph.ai` shared library** (plan §14). The truly-shared modules move to a versioned CDN; both trees load them via absolute URL. Resolves drift for vault/admin too. **Recommended end-state**, larger effort.
- **(d) Separate CloudFront origins/behaviours** per tree (plan §9 envisioned `/en-gb/share/*` and `/en-gb/open/*` behaviours). Needs CloudFront/IaC access (not in this repo). Cleanest isolation but out-of-band.

### Decision 2 — entry-point routing (`/` and `/en-gb/`)

Today `/` redirects to `/en-gb/`, which is the **legacy v0.3.x wizard**. The "latest stable release" is v0.4.0 at `/en-gb/share/` + `/en-gb/open/`. So a user landing on the site does **not** reach v0.4.0. The plan **deferred** migrating the landing page to v0.4.0 (§4 routing-summary). Options:

- Keep the legacy `/en-gb/` wizard during the retention window (status quo; collides on `_common`).
- Point `/en-gb/` (and `/`) at a lightweight landing that routes to `/en-gb/share/` and `/en-gb/open/` (self-contained, no `_common/` deps — matches the existing self-contained root `index.html`). **Recommended** — it makes v0.4.0 the front door and sidesteps the legacy `_common/` dependency. This is effectively bringing part of Phase F forward and needs product sign-off.

## 8. Redeploy runbook (to restore the site after this fix merges)

The CI fix only changes future deploy behaviour; `latest/` must be rebuilt once.

1. Merge this branch's CI changes to `dev`.
2. Trigger the three pipelines (push to the relevant paths, or `workflow_dispatch`) so each republishes its slice. Recommended order so v0.4.0 owns `_common/` until Decision 1 lands:
   1. `deploy-ui-user.yml`  (env=dev, `clean_latest=true`) — restores `/` + legacy pages
   2. `deploy-ui-share.yml` (env=dev, `clean_latest=true`) — restores `/en-gb/share/`
   3. `deploy-ui-open.yml`  (env=dev, `clean_latest=true`) — restores `/en-gb/open/`
3. Smoke-test: `GET /` (200, redirects), `/en-gb/share/` (200), `/en-gb/open/` (200), `/en-gb/open/s/` (200).
4. Apply the same sequence to `main`/`prod` only after dev verification.

Requires AWS deploy credentials (GitHub Actions secrets) — not available from the agent environment.
