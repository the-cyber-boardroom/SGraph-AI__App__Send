## Protocol Design Assessment

### What Email-FS-lite Gets Right

**1. Semantic fit for the current operational mode**

The SGraph Send team operates through Claude Code sessions and chat-driven workflows. Agents hand off context to fresh runtimes when sessions end. The key property Email-FS-lite provides — **stable agent identity across runtime restarts** — is precisely what this operating mode requires.

Full Email-FS's session-id (`architect.claude-ai.s-X7MRM4EM9X`) changes with every runtime. In a team where the same "architect" agent may be multiple sequential runtimes over days, that instability in the agent name forces out-of-band coordination for every handover. Lite's `architect.spec` stays constant across restarts; the handover is just a `notes.md` entry.

**2. Commit cadence as cognitive unit**

The "one commit per processing cycle" rule is architecturally sound. It aligns the commit boundary with the meaningful unit of agent cognition (pull → deliver → process → respond → commit), producing a history that reads as a log of agent activity rather than a wall of file moves. For audit and replay, this is the right granularity.

**3. Pull-diff as inbox notification**

Reusing sgit's pull diff output as the inbox check (rather than building a separate notification layer) is a clean architectural choice. The substrate already tracks exactly what changed; the protocol just reads it. No broker, no daemon, no API — fits the zero-infrastructure philosophy.

**4. Issues-FS-lite integration**

The decision to embed task tracking inside the same `mail/{agent}/issues/` structure, in the same commit as the email actions that triggered the tasks, is correct. Tasks and their triggering emails are causally linked; committing them atomically preserves that link in the audit trail. A separate issue-tracking tool would scatter what belongs in one commit.

**5. The mailroom as read-receipt mechanism**

The producer-consumer mailroom (`mail/mailroom/{recipient}/`) where the disappearance of a file signals delivery is elegant. It requires no explicit read-receipt mechanism, no polling, no broker. The read-receipt is implicit in the filesystem state, observable on any pull.

---

### Design Trade-offs and Limitations

**1. Singleton-per-(role, team) constraint**

Lite's most significant architectural constraint. The protocol assumes exactly one agent per `(role, team)` pair. This breaks if two agents simultaneously write to the same `mail/{role.team}/` folder.

For SGraph Send's current operating mode (sequential session-driven work, one active session per role), this is not a problem. If the team ever scales to truly parallel agents within the same team (e.g. two Explorer Dev instances running concurrently), the naming scheme would need to differentiate them — either via explicit role-name changes or by moving to full Email-FS.

**Risk level for current team:** Low. The constraint matches current operating reality.

**2. No per-message cryptographic integrity**

Lite uses sgit commit-level signing, not per-message signing. Messages moved from `mailroom/` to `inbox/` are no longer in the signed commit that originally placed them there — the move (`mv`) happens in a separate commit. An adversary with write access to the vault could theoretically replace a message in the mailroom before delivery.

**Threat model relevance:** sgit vaults use AES-256-GCM encryption with access-key gating. Vault write access already implies the vault key is compromised. The absence of per-message signing is acceptable given this threat model — the vault-level encryption is the primary security control.

**Risk level for current team:** Low. Not a practical concern given vault key access controls.

**3. No queryable session state**

Full Email-FS's `mail/sessions/active/` gives a single `ls` view of all active sessions. Lite has no equivalent — a coordinator must walk every agent's session folder. For the current team size (≤5 active roles), this is not operationally limiting. At larger scale, add a coordination convention (e.g. a shared `mail/sessions/index.md` updated per cycle).

## Integration with Existing SGraph Send Infrastructure

### Compatible with current vault infrastructure

Email-FS-lite runs entirely on sgit vaults — the same infrastructure already in use for cross-agent communication via `team/comms/`. No new infrastructure required to adopt the protocol.

### Where to host the mail/ folder structure

This is the key architectural decision (OQ-email-2): does `mail/` live in the SGraph Send git repo, or in a dedicated communication vault?

**Option A — Inside SGraph Send git repo** (`/mail/` at repo root)
- Pro: Single repo, no separate clone step for agents
- Pro: PR review workflow can include message history
- Con: Mixes communication artefacts with application code
- Con: git history becomes noisy (message commits interleaved with code commits)
- Con: Doesn't use sgit encryption — messages visible to anyone with repo access

**Option B — Dedicated communication vault** (separate sgit vault)
- Pro: Clean separation of concerns
- Pro: sgit encryption — messages encrypted at rest, access-key gated
- Pro: Vault history is the message history, not interleaved with code commits
- Con: Agents need to clone two things (repo + comms vault)
- Con: Coordination across vault and repo requires out-of-band alignment

**Option C — Hybrid** (existing `team/comms/` for structured outputs, dedicated vault for Email-FS mail/)
- The `team/comms/` structure (changelog, QA briefs, plans) is already in the repo and working
- Email-FS mail/ would go in a vault, preserving encryption and separation
- Structured deliverables continue to land in the repo where they belong

**Recommendation:** Option C. `team/comms/` is already the right home for structured cross-team deliverables (changelogs, QA briefs, inter-team plans). Email-FS is for the conversational/operational layer — messages, handoffs, questions. That layer should be in an encrypted vault. Start a `sgraph-send-comms` vault for the `mail/` structure.

## Adoption Path

**Immediate (no tooling required):**
1. Agree on team identifiers (OQ-email-3)
2. Agree on vault vs repo hosting (OQ-email-2)
3. Each active role writes their `mail/sessions/{agent-name}/brief.md` and `notes.md` as they begin sessions
4. Use Email-FS-lite for cross-agent handoffs and questions that don't fit the structured `team/comms/` model

**Near-term (low effort):**
- Add the `mail/` folder to a dedicated comms vault
- Document the team's adopted agent names in `team/comms/README.md`

**Future (requires tooling):**
- Evaluate full Email-FS when a programmatic `email-fs` CLI exists
- Per-message signing becomes meaningful when automated systems generate messages
