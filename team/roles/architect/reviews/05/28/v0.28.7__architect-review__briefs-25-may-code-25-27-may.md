## Brief Analysis

### Doc 490: Sub-Vaults Workflow (Arch Brief)

**Architectural decision: convention not native support.** Correct. Adding native vault-level nesting would have required a new object type, versioning the vault schema, and coordinating the CLI, server, and UI simultaneously. The Git-submodule analogy is apt: submodules work precisely because they are a convention layered on top (`.gitmodules` + tooling behaviour), not a change to the object store. This approach preserves the vault primitive's simplicity.

**`.vault` folder + read-only-token double-encryption.** Sound use of existing primitives. The double-encryption pattern (data readable only by holders of the full vault key, or a specific read-only token) is the right bridge to PKI. When PKI lands, references can be encrypted to recipient public keys; the convention files are PKI-ready without needing to be rebuilt.

**Three access points sequenced correctly.** Web UI first (the need), CLI second (more complex, clone-within-clone), iframe third (the external-resources use case). The CLI path introduces real complexity (nested clone resolution) and deferring it is appropriate.

**Concern: pre-initialise-on-access performance.** Many nested vaults could produce many parallel network calls on the first load of a parent vault. The lazy model is correct (fetch on access, not on load), but the UI should signal loading state clearly and not block the parent vault's display. This is a UX concern for the Villager, not a blocker.

### Doc 491: Vault Conventions and External Resources (Arch Brief)

**Convention-file pattern.** Extending `app.json`/`_page.json` to vault-pointer files and resource-pointer files is architecturally consistent. The UI already parses convention JSON; adding more convention types is additive, not a redesign.

**External resources in default-deny iframes.** The iframe sandbox as the security boundary is the correct choice. The key property (default-deny, selectively grant) must be enforced — not just declared. Verifying that the `sandbox` attribute is set correctly (without `allow-same-origin` for untrusted embeds) is an AppSec gate before this is considered production-grade.

**Naming deferred.** Acceptable at this stage. Code uses `.link.json` for vault-pointer files. Formalising the convention naming before the Web UI has more convention types will prevent proliferation. **Recommendation:** Architect to produce a simple naming decision doc (one page, not a spec) settling the pattern before the next session adds more convention types.

**Plugin/app model via convention files.** Not yet built; correctly marked PROPOSED. The architecture is sound (external app in controlled iframe, selectively grant vault access), but AppSec review of the grant mechanism is needed before shipping.

### Doc 492: Public Vault Previews (Arch Brief) — Confirmed EXISTS

**Deterministic slug → transfer ID + read-only key.** Architecturally novel and sound. The insight (the public ID *is* the key for the public layer) is clean: a system-generated or user-defined slug derives both the location (transfer ID) and the read-only decryption key for the public-preview JSON. Because the preview is deliberately public, the usual zero-knowledge constraints don't apply to it.

**Critical verification needed: slug-to-key derivation soundness.** The derivation must be:
1. One-way: knowing the read-only key must not let an attacker find the slug or work backwards to the vault's actual content key.
2. Scope-limited: the read-only key must be scoped to the public preview only, not the vault's real contents.
3. Collision-resistant: user-defined slugs must not collide or allow one user to over-write another's preview.

The brief flags this as an open question. **AppSec must verify the derivation before this is considered production-grade.** The UI code delivers the feature; the cryptographic soundness of the slug derivation needs a dedicated AppSec review.

**Two access modes.** Sound UX + security. Hash-fragment carries the vault key (not sent to server), consistent with the zero-knowledge model. Public preview renders on the server side (only the public metadata — correct). No objection.

**Bookkeeping in `.vault/owner/public-previews/`.** Correct placement. Owner-only data, consistent with the `.vault/owner/` convention established by the sub-vaults work. Clean.

**Expiry/timing status.** The brief describes timing/expiry controls; the code commits do not explicitly include an expiry implementation. **OQ-pvp-expiry-1: verify whether expiry is implemented or PROPOSED.** If PROPOSED, add to the reality document.

### Doc 493: Talk to the Vault (Dev Brief) — PROPOSED

**Components identified correctly.** The brief correctly identifies that the pieces exist (tools engine, tool-calling, visible execution, OpenRouter billing, vault awareness). This is genuinely a wiring-up exercise.

**Arch pack now exists (`vault-chat/` dev-pack).** The 05/26 commits include Track A+B implementation pack with UX diagrams and state mockups. The groundwork is done; the next session can proceed directly to implementation.

**Read-write access is appropriate.** The vault is self-contained; write access is bounded to one vault. The framing (the vault is the blast radius) is the right way to think about agent safety here. Combined with the app-mode permission system (Phase 4B), `vault.create`/`vault.unlink` via the chat agent is now possible.

**Version-control safety.** The brief mentions revertibility. The vault's CAS-based object model is inherently version-controlled (every commit is a snapshot). The chat's tool-calling modifications are reversible by reverting to a previous commit. This is a genuine safety property worth surfacing to users.

## Code Audit (25–27 May)

### App-Mode Permission System — Architecture Assessment

The `AppPermissions` module design is strong:
- DOM-free, bridge-free pure logic → separately testable, separately deployable
- `normalizePath` handles traversal attacks (`/../.vault/`) before the bridge's absolute-path branch is reached — closes the one obvious bypass
- `READ_DEFAULT = true` with a recorded decision to flip in Phase 6 is the right incremental approach
- The five-phase delivery (security floor → grants → HUD visibility → consent surface → vault ops) is a textbook capability-increment pattern

**Phase 5 deferral is correct.** The changelog explains: storing the child write key in `ro-links.json` (read-tier) would expose write capability to parent read-only-token holders — a vulnerability. The owner-secret-tier design is a non-trivial architectural addition that AppSec must review. Not shipping the insecure alternative is the right call.

**Phase 6 (reads default-deny) is the right eventual end-state.** Flipping `READ_DEFAULT` to `false` once apps declare `fs.read` in `app.json` is the correct capability-explicit model. The decision is recorded; the path is clear.

### Sub-Vaults — Architecture Alignment

The delivered code aligns with the brief's architectural decisions:
- Convention files (`*.link.json`) rather than native vault support ✓
- Build on the existing `.vault/` and ro-links pattern ✓
- Start with Web UI ✓
- Lazy load (preserve open folders on sub-vault load) ✓
- Portable ro-links (open on any device without re-entry) — **better than spec'd**: the brief discussed this as a future nice-to-have; it shipped in Phase 1.

**Remaining gap:** CLI access. The brief was explicit that clone-within-clone is complex and was deferred. This is P-248.

### Vault Header Redesign

The status pill design (`● Synced`, `↑N to push`, etc.) is a significant UX improvement with no architectural concerns. The access-key validation (`GET /api/transfers/check-token/{key}`) closes a silent-failure gap. The API surface (`setAheadCount`/`setBehindCount`/etc.) is unchanged — vault-shell needs no rewiring.
