# Architecture Spec — App-Iframe Capabilities & Permission Model (FS verbs, vault create/unlink/delete)

**Version:** v0.27.79
**Date:** 2026-05-27
**From:** Architect (Explorer team)
**To:** Vault team, Dev (lead), AppSec, QA, Designer, Product
**Type:** Architecture / API contract spec
**Status:** **PROPOSED — none of the capabilities below exist in code yet.** Foundations they build on are code-verified and cited `file:line`. Per `team/roles/librarian/reality/vault/index.md`, *nested vaults (vault-in-vault)* and *app write-back beyond `vfs.write`* are **DOES NOT EXIST / PROPOSED**.

**Builds on:** [`v0.27.62__briefing-pack__sub-vaults-and-external-resources.md`](../../05/25/v0.27.62__briefing-pack__sub-vaults-and-external-resources.md) — this spec is the **write/create/delete half** of that pack. The pack ships v1 sub-vaults as *read-only* and defers "create-child", "write inside child", and a "granular grant model" to a later phase. **This is that later phase.**

---

## 1. Why

The driving use case is the **Vault App UI** (and similar app workflows) where the user never touches the raw vault — they work entirely inside a rendered app (iframe). That app needs to:

1. **Create a new vault and wire it in** as a sub-vault placed in a chosen folder of the current vault (vault-in-vault), e.g. one child vault per container/run/patient.
2. **Unlink** a sub-vault (remove the pointer; the vault keeps existing on the server).
3. **Delete** a vault from the server (destroy the ciphertext — irreversible).
4. **Reorganise files** — move/rename/delete/mkdir — which the bridge does **not** expose today.

This is the **first feature that requires per-app privilege restrictions.** Until now the iframe was implicitly trusted to read everything and write anywhere (subject only to the server access token). Creating and *destroying* vaults is a different blast radius, so we introduce a **declared, enforced permission model** with a **non-grantable security floor**.

The sandboxed app can only `postMessage` to it — so it is the natural, un-spoofable place for consent prompts (§3.5).

## 3. The permission model (`app.json`)

### 3.1 Shape

A new optional `permissions` block in `app.json` (loaded from `.vault/app.json`, legacy `app.json` fallback):

```json
{
  "title": "Container Manager",
  "entry": "index.html",
  "permissions": {
    "fs": {
      "read":   true,
      "write":  ["data/", "runs/"],
      "move":   ["runs/"],
      "delete": ["runs/"],
      "mkdir":  ["runs/"]
    },
    "vault": {
      "create": ["runs/"],
      "unlink": ["runs/"],
      "delete": false
    }
  }
}
```

### 3.2 Each permission is `true | false | string[]`

| Value | Meaning |
|---|---|
| `true` | Allowed vault-wide (still subject to the §3.4 floor). |
| `false` / absent | Denied. |
| `["data/", "runs/result.json"]` | Allowed **only** for paths matching an entry. |

**Path-match semantics (after normalising the resolved path to vault-root-relative, no leading `/`):**
- Entry **ending in `/`** → **prefix match**: the folder and everything beneath it (`"runs/"` matches `runs/`, `runs/a.json`, `runs/x/y`).
- Entry **without trailing `/`** → **exact file match** (`"runs/result.json"`).
- `*` / `**` globs are a **future extension** — not in v1.

**Per-verb path rules:**
- `read` / `write` / `delete` / `mkdir` — match against the target path.
- `move` — **both** `from` and `to` must satisfy `move` (and neither may be in the floor).
- `vault.create` / `vault.unlink` — the array scopes the **parent folder** the link may be created/removed in.
- `vault.delete` — **boolean only** (no path scoping; always consent-gated, §3.5).

### 3.3 Defaults — read-allow, mutate-deny (no back-compat carve-outs)

We do **not** bend the model to preserve current iframe behaviour. Existing apps that mutate are expected to **declare a `permissions` block**; this is a small, easily-applied edit to each app's `app.json`, not a design constraint. The default is chosen on its own security merits:

- **Reads** (`fs.read` / `fs.list`, plus `history`) are **allowed by default for now**, because reading is the app's basic function and the §3.4 floor already hides every secret. **Agreed end-state (Dinis, 2026-05-27): reads also go default-deny** — apps must declare `fs.read`, uniform with mutations. Rolled out as a defined flip (§9) once apps declare reads, to avoid a flag-day. Set `"read": false` or a scoped array to tighten today.
- **Everything that changes state** — `fs.write` / `move` / `delete` / `mkdir`, all `vault.*`, and `git push`/`pull` — is **denied by default** and requires an explicit grant.

This single rule holds whether or not a `permissions` block is present (a block only adds grants and/or tightens reads). There is no separate "legacy mode."

### 3.4 The security floor — non-grantable, always enforced

These rules apply **regardless of any `permissions` block** and **cannot be overridden** by any grant (not even `write: true`). They exist to stop an untrusted iframe from escalating its own privileges or exfiltrating secrets:

| Floor rule | Scope | Why |
|---|---|---|
| **`app.json` is write-protected** from the bridge | `.vault/app.json` **and** legacy root `app.json` | The manifest *is* the permission grant. If the app could write it, it could grant itself any capability — defeating the whole model. |
| **`.vault/**` is write-protected** from the bridge | entire `.vault/` subtree | Owner records (`ro-links.json`), public-preview internals, future credential records must not be tampered with by app code. |
| **`.vault/**` is read-protected** from the bridge | entire `.vault/` subtree | `.vault/app.json` may carry an **embedded server access token** (`accessToken`, see v0.27.79 app-mode token spec) — single-encrypted under the read key, so an app that could read it would lift the write credential. Owner records, ro-link keys, preview internals are likewise off-limits to the app. |

**Important scope note:** the floor governs **only the iframe bridge**. The **owner in `/vault` mode** is unaffected — they continue to read/write `.vault/` and edit `app.json` through the host UI. The floor is the boundary between *host (trusted owner)* and *iframe (untrusted app code shipped inside the vault)*.

**Precedence (evaluate in order):**
1. Path in the floor for this verb → **DENY** (non-grantable).
2. A matching grant allows → **ALLOW**.
3. Otherwise → **DENY**.

### 3.5 Consent gates for powerful verbs

A grant in `app.json` is **necessary but not sufficient** for the two highest-blast-radius verbs, because `app.json` is itself authored by whoever has vault write (self-assertion):

| Verb | app.json grant | Host consent | Confirm every time |
|---|---|---|---|
| `fs.*`, `vault.unlink` | required | — | no |
| `vault.create` | required | **one-time per vault**, cached (`sg-app-grant:<vaultId>:vault.create`) | no (after first) |
| `vault.delete` | required | one-time per vault | **yes — always** (irreversible server destroy) |

**The consent surface is the HUD — host chrome, outside the iframe.** Consent is **not** a dialog the app can draw. It is rendered by `app-hud` (`_common/js/components/app-shell/app-hud.js`), the fixed 48px bar that *"Sits OUTSIDE sg-layout"* (`app-hud.js:5`) in the **parent page's shadow DOM**. The app is a sandboxed iframe that can only reach the HUD by `postMessage` — it already triggers host-rendered notices via `sg.ui.message` → `app-hud.showMessage` (`app-hud.js:8,91`). The app therefore **cannot draw, spoof, or auto-dismiss** a consent prompt; only a real user click in the HUD resolves the bridge call. (This is why a consent prompt must never be a verb the app renders inside its own iframe — the user could not tell a real grant from a fake one.)

Three HUD affordances make the model visible and interactive:

1. **Consent bar (per request).** When the app invokes a consent-gated verb, the host renders an inline prompt in the HUD centre — e.g. *"Container Manager wants to **create a vault** in `runs/`"* with **Allow** / **Deny** — and holds the bridge reply until the user clicks. `vault.delete` shows it **every** time (irreversible); `vault.create` shows it once, then caches (table above).
2. **Privileges chip (persistent).** A small always-visible HUD chip — sibling to the read-only badge (`app-hud.js:38`) — summarises what the app may currently do (e.g. `🔓 write · create`). It makes the otherwise-invisible `app.json` grants legible to the user *before* they trust the app, and is the entry point to…
3. **Permissions panel.** A host-rendered panel listing every declared grant and its state (granted / consent-pending / denied), where the user can **revoke** any capability or pre-grant a consent. Revoking clears the matching consent cache and immediately tightens `_can` (§5) — effective without a reload.

**Apps ask for an upgrade at runtime** via `sg.ui.requestPermission` (§4.3): the app *requests* a capability, the host shows the consent bar, the user decides. The app never escalates itself — it can only ask, and the answer is the user's click; a denial returns `ECONSENT`.

> **Cache/chip invariant.** The consent cache (`sg-app-grant:<vaultId>:<verb>`) is the single source of truth that the HUD chip, the consent bar, and `_can` all read. Granting (bar or panel) writes it; revoking (panel) clears it; `_can` consults it. They never drift.

> **`app.json` is a ceiling, not just a default.** `requestPermission` can only surface a click for verbs the manifest **already declares** (and that aren't in the §3.4 floor). An app cannot acquire — even with user consent — a capability its `app.json` never listed; that would make the manifest non-auditable. To gain a brand-new capability, the app must ship an updated manifest. *(Whether to allow true runtime grants beyond the manifest is an explicit open question — §10.)*

### 3.6 Two independent gates for writes (clean layering)

A write/mutation now requires **all** of:
1. **Server access token** — `dataSource.writable` (the existing gate; the *server's* write authority).
2. **App permission** — `_can(verb, path)` (the *app's* declared capability).
3. **Not in the floor** (§3.4).

These are orthogonal: an app holding the access token still cannot write a path it has no `fs.write` grant for; an app with a grant still cannot write without the token. This means `cmd auth setKey` (the app supplying a token) no longer implies write capability.

## 4. New bridge verbs

All replies use the existing `__sgCmdReply` envelope `{ ok, result, err }`. Denials return `ok:false` with a stable error code so apps can branch:

| Error code | Meaning |
|---|---|
| `EPERM` | no app.json grant for this verb/path |
| `EPROTECTED` | path is in the non-grantable floor |
| `ECONSENT` | host consent not granted (or declined) |
| `EREADONLY` | no server access token (`dataSource.writable` false) |
| `ENOENT` / `EEXIST` | target missing / already exists |

### 4.1 FS mutations — `__sgCmdType: 'fs'`

| Action | Message fields | Host action | Permission |
|---|---|---|---|
| `move` | `{ from, to }` | rename in place (`renameFile`) when same dir, else relocate (reuse the host drag-move path) | `fs.move` on **both** `from` & `to` |
| `delete` | `{ path }` | `dataSource.deleteFile` | `fs.delete` |
| `mkdir` | `{ path }` | `dataSource.createFolder` | `fs.mkdir` |

`rename` is **not** a separate verb — it is `move` where the parent folder is unchanged. (Cross-folder move that preserves the underlying blob may need a small `vault.moveFile(fromDir, name, toDir)` lib helper; the host drag implementation already does this and should be factored into the data source.)

### 4.2 Vault lifecycle — `__sgCmdType: 'vault'`

**`create`** — `{ action:'create', path, label, options? }`
- Gate: `vault.create` for parent `path` + consent (§3.5) + token.
- Host: `SGVault.create(sgSend, passphrase, options)` → write a keyless `<label>.link.json` into `path` → write the owner record (read_key + ref) into `.vault/owner/ro-links.json` (double-encrypted) → push the parent.
- **Key format (mandatory):** the child is created with a **proper vault key** `{passphrase}:{vault_id}` (`SGVault.create` + `vault.getVaultKey()`, strong PBKDF2-600k `deriveKeys`). **Never generate a simple token** (`word-word-NNNN`, `deriveKeysFromSimpleToken`) — that format is being **retired**. Concretely: generate a **high-entropy passphrase that does NOT match `^[a-z]+-[a-z]+-\d{4}$`**; a simple-token-shaped passphrase is mis-routed to the legacy derivation by `SGVault.open` (`sg-vault.js:119` / `:132`) and will not round-trip. *(PROPOSED helper: a canonical `generateVaultPassphrase()` so every call site is consistent.)* This rule applies to **all** new credential-producing code, not just `create`.
- Reply: `{ vault_id, ref_id, ref_file_id }`. **Does not** return `read_key`/`write_key` to the app — secrets stay host-side; the app reaches the child through the `CompositeDataSource`.
- **v1 limit:** the child is wired for **read-through** only (consistent with the pack's "v1 = read-only inside sub-vaults"). Writing *into* the child from the app is a later phase.

**`unlink`** — `{ action:'unlink', path }`
- Gate: `vault.unlink` for `path`.
- Host: delete the `.link.json` at `path` (and its owner record); push. **The vault remains on the server** and can be re-linked later with its key. Reversible. Reply `{ unlinked:true }`.

**`delete`** — `{ action:'delete', path }`
- Gate: `vault.delete` + consent + **always-confirm** + token.
- Host: resolve the child's **write credential** from an owner-tier record → call the server vault-delete endpoint → on success, also unlink (§unlink) → push. Reply `{ deleted:true, files_deleted:N }`. Irreversible.
- **Dependency:** server delete is gated by `write_key_hash` (appsec v0.22.6). The read-only owner record stores only `read_key`. **To support `vault.delete`, `vault.create` must additionally stash the child's write credential in an owner-only (double-encrypted) record.** Without it, an app can `unlink` but cannot server-`delete` a child it created. This is a required companion change, flagged for AppSec.

### 4.3 UI / consent — `__sgCmdType: 'ui'`

The consent surface is the **HUD** (§3.5), not the iframe.

| Action | Message fields | Host action | Notes |
|---|---|---|---|
| `requestPermission` | `{ verb, path? }` | render the HUD **consent bar** for `verb` (+ optional `path`); resolve on the user's click | Reply `{ granted: bool }`; a denial also returns `ECONSENT`. A grant is written to `sg-app-grant:<vaultId>:<verb>` and reflected in the privileges chip. **Only verbs already declared in `app.json` and outside the §3.4 floor** can be requested — otherwise `EPERM`. |
| `message` *(existing)* | `{ handle, text, type, ttl }` | `app-hud.showMessage` (`app-hud.js:91`) | already shipped as `sg.ui.message` |

This gives apps a graceful-degradation loop: attempt a verb → catch `EPERM`/`ECONSENT` → `sg.ui.requestPermission(verb, path)` → retry when `granted`. The user, not the app, is always the decider.

## 5. Enforcement architecture

Single choke point in `app-shell.js`, consulted by **every** bridge handler before any side effect:

```
_isFloor(verb, path)   // §3.4 — non-grantable deny; checked FIRST
_can(verb, path)       // §3.2/3.3 — grant lookup against this._appJson.permissions (+ consent cache)
_consent(verb, path)   // §3.5 — render HUD consent bar; resolve on user click; cache the grant
```

- Parse `permissions` once at open (alongside `_readAppJson`); normalise into a fast lookup.
- `vfs.read` / `vfs.list` / `vfs.write` (already deployed) gain a `_isFloor` + `_can('fs.read'|'fs.write', path)` check; **`vfs.list` must also filter `.vault/**` entries out of results** (not just block direct reads).
- New verbs are added to the `__sgCmdType` switch with their gate calls.
- **Consent runs on the HUD, not the iframe** (§3.5): `_consent` drives `app-hud` (the consent bar / privileges chip / permissions panel) and only resolves on a user click. The cache key `sg-app-grant:<vaultId>:<verb>` is the **single source of truth** that `_can`, the chip, and the panel all read — granting writes it, revoking clears it, so they never drift. `sg.ui.requestPermission` (§4.3) is just `_consent` invoked by the app instead of by a gated verb.
- All denials emit a bridge-debug event (`_emitBridgeCall`) so the existing Bridge debug tab shows `EPERM`/`EPROTECTED`/`ECONSENT` etc. for diagnosis.

## 6. Security analysis (AppSec)

**Threat model.** The iframe runs **untrusted app code that ships inside the vault** (`sandbox="allow-scripts allow-forms allow-same-origin"`, same-origin `blob:`). The trust boundary is the host `app-shell`. The owner (in `/vault` mode) is trusted; the app is not.

**Escalation paths closed:**
- *App rewrites its own permissions* → closed by the `app.json` write-floor (§3.4).
- *App reads the embedded access token to gain write authority it wasn't granted* → closed by the `.vault/**` read-floor, **and** by the orthogonal `_can('fs.write')` gate (§3.6): even with a token the app can't write outside its grant.
- *App tampers with owner records / ro-link keys* → closed by the `.vault/**` write-floor (owner records are also double-encrypted, defence-in-depth).
- *App draws a fake "Allow" dialog to trick the user into a destructive grant* → closed by rendering all consent on the **HUD** (host chrome outside the iframe, §3.5); the sandboxed app cannot draw, spoof, or auto-dismiss it, and only a real user click resolves the call.

**Residual risks (accept / mitigate, call for AppSec sign-off):**
1. **Owner self-grant.** Anyone with vault write can author `app.json` to grant the app anything. Accepted: the owner is trusted, and the floor + consent gates still bound the *destructive* verbs. The floor is what makes the model meaningful despite self-assertion.
2. **`accessToken` extractable by read-key holders** (incl. `ro-` share recipients) — pre-existing from the app-mode token spec; the read-floor stops the *app* but not a human with the read key. Document where embedding a token is appropriate.
3. **`vault.delete` blast radius** — irreversible server destruction; existence-oracle and write-key-handling findings from appsec v0.22.6 apply to the endpoint this verb calls. Mandatory confirm + consent + the write-credential-storage dependency (§4.2) must be reviewed before build.
4. **Quota / abuse.** `vault.create` consumes server resources and needs the access token; an automated app could create many vaults. Consider a server/host rate cap. Out of scope for this spec; flagged.

## 8. Migration

We are **not** preserving current iframe behaviour for back-compat — existing vaults/apps are few and easily fixed by editing their `app.json`.

- **Apps that mutate** (write/move/delete/mkdir, push/pull) must **add a `permissions` block** declaring those grants (§3.3). This is a deliberate, one-line-per-verb edit per app — not something the design works around.
- **Read-only apps** need no change beyond the floor.
- The **floor** (§3.4) ships **independently and first** — pure hardening, no app-facing API, safe to land ahead of the verbs.
- New verbs are additive; an app only gains them by declaring them.

## 9. Phasing (recommended build order)

1. **Floor only** (smallest, highest-value security win): block iframe write to `app.json`/`.vault/**`, block iframe read of `.vault/**`, filter `.vault/**` from `vfs.list`. No new API.
2. **`permissions` parsing + `_can` + the FS verbs** (`fs.move` / `fs.delete` / `fs.mkdir`) — answers "can the iframe move files" with *yes, when granted*.
3. **HUD privileges chip** (§3.5) — surface the parsed grants in the HUD (read-only, no consent yet). Pure visibility; small and independently shippable.
4. **`vault.create` + `vault.unlink`** + owner-record + the **HUD consent bar** + `_consent` + cache + `sg.ui.requestPermission` (§4.3) + the permissions panel's revoke.
5. **`vault.delete`** — **DEFERRED by decision (Dinis, 2026-05-27).** Needs an owner-secret-tier write-credential store (the read-tier `ro-links.json` would leak the write key to parent read-holders) + AppSec sign-off on the destructive endpoint. `vault.unlink` (reversible) covers current needs; the verb returns `ENOTIMPL` until built.
6. **Flip reads to default-deny** — change the `fs.read`/`fs.list` default from allow to deny once apps declare `fs.read`. One-line change in `AppPermissions.can` (a `READ_DEFAULT` switch), shipped after the apps in the wild have been updated. Uniform default-deny end-state.

## 10. Decisions (resolved with Dinis, 2026-05-27)

- ✅ **Consent UX:** **one-time host prompt per vault for `create`, plus always-confirm for `delete`.** Not fully silent. (Matches §3.5.)
- ✅ **`vault.delete` ⇒ `unlink`:** **yes** — a successful server destroy is followed by removing the `.link.json`. (`unlink` and `delete` remain separate verbs/permissions.)
- ✅ **Write-into-child:** **read-through-only is acceptable to start.** `vault.create` wires the child for reads; write-back is a later phase.
- ✅ **`app.json` is a hard ceiling** (§3.5): `sg.ui.requestPermission` can only surface a click for verbs the manifest already declares — no runtime escalation beyond the manifest. **The manifest is editable via the Vault (browse) UI but NOT via the App UI** — i.e. exactly the §3.4 floor (the iframe bridge cannot write `app.json`; the owner edits it in `/vault` mode). Re-grant requires a manifest edit by the owner.

- ✅ **Reads → default-deny (eventually):** **yes.** The end-state is a uniform default-deny model (reads included; apps declare `fs.read`). Ship read-default-allow first, then flip to default-deny as a defined step (§9) once apps declare reads. Only the §3.4 floor is ever unconditional.

*(No open questions remain.)*
