## 0. The one thing this enables

> **A parent vault's app must be able to create/edit a file inside a *child* vault** — without the
> parent writing across the boundary, and without losing the parent's own session.

Concretely (KneeScore MVP): a clinician **console** vault app appends a review to a patient (child)
vault's `data/reviews.json`. Reading across a read-only sub-vault mount already works; **writing does
not**, and every client-side write route fails today (§2).

The fix is to let the parent **spawn the child vault's own app in an isolated kernel**, hand that kernel
the child's secrets over an authenticated channel, and let the **child app write its own file under its
own permission grant**. The parent never holds a write path across the boundary; the child writes itself.

Everything else in this doc (the security hardening of §8, the three-iframe unification of §7) falls out
of the *same* mechanism — but the **driving use case is the spine, and it lands first** (§9).

## 1. The driving use case, precisely

```
Clinician console vault (parent)            Patient vault (child)
  app: roster + read-only links               app: knee check-in, data/reviews.json
        │
        │  wants to append a review to the patient's data/reviews.json
        ▼
  ── today: no working write route ──
```

The clean shape (zero-knowledge-respecting): **the child writes its own data.** The parent transiently
brings up the *patient app* in an isolated frame, fed the patient vault's key + token, and asks it (over
a message its own app already understands — the KneeScore patient app ships an `sgpoc:writeReview`
listener) to append the review and push. The write executes inside the child's authenticated session,
under the child's `app.json` grant (`fs.write:["data/"]`), using the child's **already-working** commit/
push/merge machinery. The parent's vault is untouched; the parent never gets a cross-vault write API.

What the platform must provide for this: **a way to run a second vault's app in an isolated context with
that vault's own key, reachable by `postMessage`, without changing the origin's active vault.** That is
the missing primitive.

## 2. Why every route fails today (code-verified)

**One active vault per browser origin.** App mode resolves its vault key from
`localStorage['sg-vault-key']` (`app-shell.js:82`), persisted on open (`:225`). Opening a second vault's
app rewrites that key — a **navigation** that switches the whole origin to the child and clobbers the
parent console. The `#hash` on `/en-gb/app` is a *file path*, not a key, so it can't select a vault.

**Same-origin app frames can't be isolated by storage.** The app iframe runs
`sandbox="allow-scripts allow-forms allow-same-origin"` (`app-shell.js:919, 1033, 1090, 1170`). Two
same-origin iframes **share both `localStorage` and `sessionStorage`**, so you cannot give a nested app a
*different* key via storage without clobbering the parent.

**The other routes (all tried live, all fail):**

| Route | Result | Why |
|---|---|---|
| `sg.vfs.write('subvaults/<child>/…')` | resolves OK **but never persists** | inner-vault mounts are read-only by design (a silent no-op) |
| `sg.auth.setKey(childKey)` then write | stays on parent | `setKey` sets creds on the *current* vault; doesn't switch which is open |
| `/en-gb/app#<childKey>` nested | opens the **parent** | hash is a file path, not a key |
| Open form → "Open as App" | brings child up **but switches the origin** | rewrites `sg-vault-key` → navigation, not spawn; parent is gone on reload |

**Bonus root-cause finding (security):** because the app frame is same-origin with the kernel, untrusted
app code can bypass `sg.*` entirely — read the vault key/token from `localStorage`, script the kernel
DOM, reach `window.parent`. So the permission model (Phases 1–4B) is **a real boundary only for
cooperative code** (`SECURITY-same-origin-app-bypass.md`). Same root cause; same fix.

## 3. The architecture — isolated kernels, capability over RPC

Two roles, strictly separated:

- **Kernel** — trusted platform code (`/en-gb/app` shell). Holds the vault's **two secrets** (vault key
  *and* server access token), runs the **permission checks**, performs privileged ops. The top kernel is
  the **only frame with a real origin** (browser-loaded).
- **App frame** — the vault's `app.json` code (untrusted-ish). Runs at **`null` origin** (`sandbox`
  without `allow-same-origin`). Gets a **capability** — the `sg.*` RPC channel — never the credentials.
  Cannot read storage, cannot read the kernel's DOM, cannot reach across origins.

**Spawn** is one kernel creating a *child kernel* for **another** vault:

```
Kernel-A  (real origin)   ── holds parent vault secrets, runs parent app
   └─ App-A   (null)      ── parent "console" app code
       └─ Kernel-B (null) ── SAME platform shell code, booted from a message (not storage);
                             fed the CHILD vault's key + token over a SecureChannel
            └─ App-B (null)── the child vault's app code; writes its own data/reviews.json
```

Principles:
1. **One real origin; everything nested is `null`** (sandbox flags inherit downward). Nested kernels are
   credential-less and storage-less *by construction* — which is exactly why the session-clobber bug
   becomes structurally impossible (a `null` frame can't touch `sg-vault-key`).
2. **Trust is per-level, not global.** Each kernel protects *its own* secrets from *its own* app child.
   A nested kernel's code is injected by its creator (`srcdoc`), so "trusted kernel" means "the platform
   shell the creator chose to run" — fine here because the creator already holds the child secrets it is
   feeding down. Do **not** over-read this as "all kernels are equally trusted."
3. **Kernel holds secrets; app holds a capability.** The app can do what it's *authorized* to (the kernel
   acts for it) but can never *possess* the means to bypass authorization. This is what upgrades the
   permission model from advisory (§8) to enforced.
4. **Two secrets, fed explicitly.** A `null` kernel has no ambient context, so the creator must hand it
   both the **vault key** (decrypt) and the **access token** (authenticate to the server).

## 4. SecureChannel — the reusable authenticated channel (PKI)

All cross-context messaging goes through **one** primitive — a `SecureChannel` — rather than ad-hoc
`postMessage`. This both secures the boot/secret-injection and becomes the standard message-auth layer
for the codebase (the scattered `postMessage` + `event.source` + reply-id correlation in `app-shell.js`
collapses into one channel object). **Scope: cross-context messages only** (frame↔frame / worker / tab);
same-document `CustomEvent`s have no trust boundary and stay as-is.

**Trust is anchored on the window reference, then PKI secures the wire.** Under `null` origins
`event.origin` is always `"null"`, so the unforgeable discriminator is the **`event.source`** window the
creator holds — *not* the origin. PKI cannot bootstrap its own trust; the anchor is "this message came
from the exact frame I just created, before any other code interposed."

**Handshake (one-use PKI, verified live — §4 test 3):**
```
1. Initiator (parent) mints one-use K1 (ECDSA P-256), keeps K1-pub, sends K1-priv to the child over the
   creation-time channel (authenticated by event.source). K1's only job: authenticate the child's reply.
2. Child mints K2 (ECDH P-256, NON-EXTRACTABLE), returns { K2-pub, sign(K2-pub, K1-priv) }.
3. Initiator verifies the signature with K1-pub → trusts K2-pub (it minted K1). K1 retired (single use).
4. Initiator ECDH-derives an AES-GCM key to K2-pub, encrypts { vaultKey, accessToken }, sends ciphertext.
   Child decrypts with K2-priv (which never left the child).
5. All later messages signed (+ encrypted when sensitive); each carries nonce + direction (anti-replay).
```
Net: two long-lived public keys exchanged, **neither private key ever crosses a frame boundary**; the two
vault secrets are ciphertext to everyone but the intended child kernel.

**Proposed API (build once, reuse everywhere):**
```js
// initiator (creator of the child frame)
const ch = await SecureChannel.connect(iframe.contentWindow, { role: 'initiator', anchor: iframe });
await ch.send('secrets', { vaultKey, accessToken });   // encrypted on the wire
const res = await ch.request('sg.vfs.write', { path, data });   // RPC, id-correlated

// responder (the child kernel)
const ch = await SecureChannel.accept(window.parent);  // anchors on the creator; completes the handshake
ch.on('secrets', ({ vaultKey, accessToken }) => kernel.boot(vaultKey, accessToken));
```
The module models `anchor → key-exchange → encrypted channel` explicitly. Standard pinned once: **P-256**
(verified, universal; X25519/Ed25519 are cleaner if runtime support is confirmed), non-extractable keys,
a fixed envelope `{ kernelId, dir, nonce, type, payload, sig }`.

> **Why PKI now (org decision):** not for this handshake's marginal in-tab security, but to (a) make
> `SecureChannel` the **standard** authenticated carrier for all cross-context messaging, (b) build the
> codebase competency, and (c) *subtract* code by centralizing message auth. The payoff is real **only if
> it's one abstraction** — scattered per-feature PKI would add ceremony, not remove it.

## 5. The driving use case, end-to-end

```
App-A (console)            Kernel-A (real origin)        Kernel-B (null)            App-B (patient app)
  │  sg.app.openVault(childKey/handle, {mode:'app'})                                     
  │ ───────────────────────▶ │                                                          
  │                          │  create iframe sandbox="allow-scripts" (null), srcdoc=shell
  │                          │ ────────────────────────────▶ Kernel-B boots (no storage)
  │                          │  SecureChannel.connect(...) ─ handshake (§4) ─▶ accept
  │                          │  send 'secrets' {childKey, childToken} (encrypted) ─▶ kernel.boot
  │                          │                               │  mounts child vault, runs App-B
  │                          │                               │ ─ injects App-B (null) ─▶ sgpoc listener
  │  child handle returned   │                               
  │ ◀─────────────────────── │                                                          
  │  ch.post('sgpoc:writeReview', review) ───────────────────────────────────────────▶ │
  │                          │                               │ ◀─ sg.vfs.write('data/reviews.json') ─ App-B
  │                          │  ◀─ server op (proxy, §6) ─ Kernel-B   (writes child's own branch, pushes)
  │  result ◀───────────────────────────────────────────────────────────────────────  │
  ▼  parent's active vault unchanged; reload still loads the clinician console
```

Key properties for the driving case:
- **The write executes in the child's session**, under **App-B's own** `app.json` grant — the parent never
  writes across. Custody of the child key (parent-held vs patient-generated) is a separate product call
  (§10), and does **not** change this mechanism.
- **The parent app (App-A) need not be `null`-origin yet** to deliver this — App-A can stay as it is today
  and still spawn a `null` Kernel-B (SecureChannel works cross-origin). Making App-A itself `null` is the
  *security* upgrade (§8), sequenced **after** the product unlock.
- The child reuses the **commit/publish/three-way-merge** logic already hardened in `sg-vault--sync.js`
  (the merge-publish fix) — no cross-mount re-implementation, which is the big cost the "writable child
  mount" alternative would incur.

## 6. The server path — the one open platform decision

A `null`-origin frame's `fetch` to the vault API is **CORS-blocked** (`Origin: null` → `Failed to fetch`,
verified — §4 test 4). So a nested kernel cannot hit the server directly as-is.

| | Option 1 — API accepts token-auth'd `Origin: null` | Option 2 — top (real-origin) kernel proxies |
|---|---|---|
| Change | server CORS + auth | client only (relay up the channel) |
| Topology | each kernel self-contained | one origin talks to the server |
| Risk | `Origin: null` is shared by *every* opaque/sandboxed context on the web → must gate **strictly on token**, never ambient; AppSec sign-off | relay must be capability-scoped per vault |

**Recommendation: ship Option 2 first** (no platform change; works with everything verified). For the
**driving use case it sidesteps Option 2's main wrinkle**: the relay carries the child's token up through
App-A, but App-A is the console that *already holds* the child key — so no new secret is exposed. (For the
general recursive case, route a kernel's proxied I/O straight to `window.top`, authenticated, rather than
through the intermediate app frame.) Adopt Option 1 later as a simplification iff AppSec approves. Note:
we are zero-knowledge — the server holds only ciphertext — so CORS was never the confidentiality boundary;
the encryption is.

## 7. Unifying the three iframe contexts (later phase, same machinery)

Today three different renderers embed vault HTML with three different sandbox postures:

| Context | Today | Under this architecture |
|---|---|---|
| Standalone `/app` | `app-shell.js`, `allow-same-origin`, full bridge | top kernel + `null` app frame |
| `/vault` HTML **view** | send-browse's renderer | `null` kernel, read-only capability |
| `/vault` **edit preview** | split pane, sandboxed **without** `allow-same-origin` (the `sessionStorage`/`SecurityError` the MVP hit) | `null` kernel, read-only, **dirty-buffer overlay** data source |

Collapsing them onto **one kernel + one SecureChannel** with a per-context **capability + data-source mask**
is a real consolidation, and it delivers a concrete win beyond tidiness: **the edit preview becomes
identical to the real run** (both `null`-origin, both fed via the same bridge), eliminating the
"in-editor testing ≠ runtime" mismatch. The only per-context specialisation is the data source: the
preview serves the *unsaved editor buffer* for the file being edited and the vault for everything else.

This is a genuine refactor (the vault browser's file preview becomes "spawn a kernel for this file"), so
it is **Phase 4**, after the product unlock and the standalone-app hardening.

## 8. Security: the permission model becomes enforced

Today (`SECURITY-same-origin-app-bypass.md`): the floor (`.vault/**`, root `app.json` → `EPROTECTED`) and
grants are enforced *inside* `sg.*`. Same-origin app code can ignore `sg.*` and read the bytes/token
directly. So the model is **advisory for cooperative code, bypassable for uncooperative code**.

Under this architecture the **only path to act on the vault is a message the kernel validates** — the app
frame is `null`-origin with no ambient secrets, and `sg.*` is a secret-less stub whose every call is a
permission-checked RPC to the secret-holding kernel. The model becomes a **real boundary**, even against
untrusted app code. Verified isolation (§4 test 2): a `null` child cannot read its parent's document
(`parentDocReadable:false`) nor `localStorage` (`localStorageReadable:false`); a grandchild never receives
the parent→child secret.

Guarantee boundaries: PKI secures the **wire**; frame isolation keeps keys **out of untrusted frames** —
both are needed. **Out of scope:** same-frame compromise (untrusted code in the *same* frame as a kernel's
key) — non-extractability stops key *exfiltration* but not key *use* while resident; the architecture's
premise is that untrusted app code is always a `null` frame *separate* from the kernel.

This hardening (making the standalone app frame `null` + the bridge split) is **the gate for any
third-party / bring-your-own vault-app roadmap**, but it does not block first-party work today.

## 9. Phasing — driving use case first

| Phase | Delivers | Gating check |
|---|---|---|
| **0** | **Document the trust assumption** ("vault apps are first-party; permission model assumes cooperative code") so nobody enables third-party apps before §8 lands. | — |
| **1** | **`SecureChannel` module** (the PKI primitive) — standalone, unit-tested, no UI change. The reusable foundation. | unit tests green |
| **2** | **Spawn + nested kernel for the driving use case.** Kernel can spawn a `null` child kernel bound to another vault (secrets via SecureChannel); child kernel **message-boots** (3rd boot source); child app writes its own file; server I/O via **Option 2 proxy**. App-A may stay as-is. **→ parent-edits-child-file works.** | **real kernel-in-kernel** runs in the actual shell (not just `srcdoc`) — §10 |
| **3** | **Standalone `/app` app-frame → `null` + bridge split** (secret-less `sg.*` stub + secret-holding kernel; enforcing checks in the kernel). Closes §8 for the main app. Verify in-shell features survive `null` origin (`loadCss/loadJs`, nav, markdown, `img.src`). | feature parity under `null` |
| **4** | **Unify `/vault` HTML view + edit preview** onto the same kernel+channel (dirty-buffer data source for preview). | preview == runtime |
| **5** | **Hardening/simplification:** roll `SecureChannel` out to remaining cross-context message paths; optionally adopt server **Option 1**. | AppSec sign-off |

The **driving use case lands at Phase 2**. Phases 3–5 are the security/consolidation programme and are
explicitly sequenced *after* the product need.

## 10. Breakage & migration — acceptable, with docs

**Per Dinis: it is OK to break a number of vaults with these changes.** The bet is that with good
documentation, the Claude agents working on vaults can repair them easily. So we optimise for a *clean*
design over backward-compatibility shims, and invest in the repair docs.

What can break and how an agent fixes it:
- **Writes already deny-by-default (Phases 1–4B).** Apps that write need a `permissions` block. Fix: add
  `{ "permissions": { "fs": { "read": true, "write": ["data/"] } } }` to the vault's `app.json` (via the
  Vault UI / `sgit`, never from the app), commit + push. (`MIGRATING-TO-THE-PERMISSION-MODEL.md`.)
- **App frame becomes `null`-origin (Phase 3).** Apps that relied on same-origin tricks (reading
  `localStorage`, touching `window.parent`, `fetch` of vault paths) break — they must use `sg.*` instead.
  Fix: rewrite those accesses to the bridge API (already the documented contract in `AUTHORING.md`).
- **Custody (product, not mechanism).** For the trial the console holds child write keys; before real
  data, move to patient-generated keys or server-minted-and-delivered (doesn't change §3/§5).

**Deliverable alongside the code:** update `AUTHORING.md` (the `null`-origin contract + `sg.app.openVault`)
and `MIGRATING-TO-THE-PERMISSION-MODEL.md` (a "repair a broken vault app" checklist) so repair is mechanical.

## 11. Open decisions / to verify

1. **Server path (§6):** Option 2 now; Option 1 later (needs AppSec for token-gated `Origin: null`).
2. **Real kernel-in-kernel (Phase 2 gate):** confirm a nested `/en-gb/app` is `null` (sandbox inheritance)
   and can load its own shell code there — the lab proved the `srcdoc` primitive, not the real shell.
3. **In-shell feature parity under `null` (Phase 3 gate):** `loadCss/loadJs` (go via bridge — fine), nav,
   markdown render, `img.src` interception, `blob:` mounting.
4. **Spawn API surface:** `sg.app.openVault(keyOrHandle, { mode, target })` returning a postMessage handle;
   gated by a capability (`permissions.vault.openApp`, or reuse the read/link capability the parent holds).
5. **Curve:** P-256 verified; confirm it's the standard (or X25519/Ed25519 if runtime support is solid).
6. **Grandchild `window.top` reachability** (lab caveat): confirm enforced vs incidental — doesn't affect
   the secret-isolation guarantee, but firm it up.

## Appendix — message reference (illustrative)

```
parent → child   { type:'init', secret, k1priv }                     // boot + PKI bootstrap (event.source-anchored)
child  → parent  { type:'ready', secret, k2pub, sig }                // PKI introduce
parent → child   { type:'secrets', iv, ct }                          // encrypted { vaultKey, accessToken }
app    → kernel  { type:'sg.vfs.write', id, path, data }             // capability RPC (secret-less stub)
kernel → app     { type:'result', id, result | error:'EPERM' }       // permission-checked in the kernel
child  → top     { type:'server', id, op, … }                        // Option 2: proxied server I/O (authenticated)
console→ childapp { type:'sgpoc:writeReview', review }               // driving use case: child writes its own file
```

### Capability + data-source matrix
| Frame | Origin | Secrets | `sg.*` | Writes | Data source |
|---|---|---|---|---|---|
| Top kernel (`/app`) | real | vault key + token | — (it *is* the broker) | per grants | vault |
| App-A (console) | `null` | none | RPC | per grants | via Kernel-A |
| Kernel-B (spawned) | `null` | child key + token | — (broker for B) | per child grants | child vault |
| App-B (child app) | `null` | none | RPC | per child grants | via Kernel-B |
| `/vault` HTML view | `null` | none | RPC (read) | — | vault (read) |
| `/vault` edit preview | `null` | none | RPC (read) | — | dirty buffer + vault |
