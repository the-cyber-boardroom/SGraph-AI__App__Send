## Executive Summary

The 25 May briefs extend the vault from a storage-and-transfer primitive into a richer product surface through four closely related capabilities: sub-vaults as a convention (workflow + reference files), external resource embedding, public vault previews, and in-vault chat with tool-calling. All are designed to compose without backend complexity. Three of the four have been implemented (Phase 0–3 of sub-vaults, public-vault-previews, app-iframe permissions) and are code-complete but browser-unverified. The fourth (vault chat, P-248) has a comprehensive code-grounded architecture dev pack (12 documents, v0.27.80) and awaits an implementation session.

The architectural decisions are mostly sound. One decision requires attention and one open question needs resolution before Phase 5 of the app-iframe work can proceed.

## 1. Sub-Vaults: Convention-Based Design Assessment

### Decision: Convention (Git Submodules Model) Over Native Vault Support — CORRECT

The choice to implement sub-vaults as a convention (`.link.json` pointer files + `.vault/owner/ro-links.json` owner records) rather than as a new primitive in the vault protocol is architecturally correct. The analogy to Git submodules is precise:

- The vault object model stays simple (blob/tree/commit/ref); sub-vault references are just files in the tree.
- The tooling (UI, CLI) interprets the convention; the vault protocol is unaware.
- Adding a sub-vault is editing a file, not operating bespoke machinery.

The split between `ro-links.json` (read-key tier — any parent reader can traverse read-only sub-vaults) and `rw-links.json` (owner-only double-encrypted — full child keys) is the right security model and mirrors the existing `readonly-tokens.json` pattern. The deferral of `rw-links` (write-inside-child) to Phase 4 is appropriate: the use cases are all read-only in the near term.

### Decision: Vault Web UI First, CLI Second — CORRECT

The `.vault` double-encryption pattern uses `vault-hkdf.js`, which is an ES module on the token page (`<script type="module">`) but a global on the browse page (`<script>`). Moving it to `_common/js/lib/crypto/` would require a cross-module refactor of the browse page. The Phase 4 deferral of `rw-links` and the `vault-hkdf` move avoids this risky refactor until writable sub-vaults are actually needed. AGREE.

### Risk: Phase 4 CLI Clone-Within-Clone Is Genuinely Complex

Nested cloning (a cloned vault whose sub-vaults must also be cloned) is the hard submodule-update problem. The brief acknowledges this. The mitigation (explicit reference files make resolution tractable; start with Web UI where the need is) is adequate for now. The CLI implementation will need its own architecture session when scheduled.

### Observation: Per-Tab Vault Identity (P-174) Was a Bug Fix, Not a Feature

Moving the vault key from shared `localStorage` to per-tab `sessionStorage` (with `localStorage` as a last-opened fallback) was necessary to prevent one tab's vault clobbering another's on reload. This is correctly implemented and tested (8/8). The access token remains shared across tabs as intended.

## 2. Vault Conventions and External Resources Assessment

### Decision: Extend `app.json`/`_page.json` Convention Pattern — CORRECT

Vault pointer files and resource pointer files as convention JSON (alongside `app.json`, `_page.json`) are consistent with the platform's existing approach. The UI already understands the convention pattern; adding new types follows the same mechanics. No protocol change.

### Decision: Controlled Iframe (Default-Deny) for External Resources — CORRECT AND CRITICAL

The `<sg-embed-frame>` implementation correctly:
- Uses `<img>`/`<video>` media elements (cannot read the page) for media resources.
- Uses provider iframes for YouTube/Vimeo.
- Uses sandboxed cross-origin iframes with **no `allow-same-origin`** and **no bridge/message listener** for `link`/`app` types.
- Implements click-to-load privacy (no third-party fetch until user opts in).
- Shows a sticky "External window · host · cannot read this vault" banner.

This is the right security model: embed freely, grant access narrowly. The deliberate absence of `allow-same-origin` in the sandboxed iframes closes the vault-read vector for untrusted external pages. AppSec should verify this in a browser (noted as a gap in the changelog).

### Open Question: App→Vault Access Grant (P-164) Architecture

P-164 (opt-in app→folder `requestFile` grant) is AppSec-gated and deferred. When it is designed:
- It must use the app-iframe permission model (Phase 2's `parsePermissions`/`_can()`) not a separate mechanism.
- The grant declaration in `app.json` should follow the Phase 2 `permissions` block pattern.
- The consent surface (Phase 4A's `sg.ui.requestPermission`) is the user-facing mechanism.
- AppSec must sign off on the exact grant scope before any file-level access is wired.

The app-iframe spec already records this relationship. No new architecture is needed; the gap is security review and implementation sequencing.

## 3. Public Vault Previews Assessment

### Decision: Deterministic Public-Vault-ID Derivation — SOUND WITH CAVEAT

The derivation (`SHA-256('pvp-transfer-v1:' + id)[:12]` for the transfer ID, PBKDF2 with salt `sgraph-public-preview-v1` for the read-only AES key) is sound:
- The public-preview key namespace is **separate** from Simple Tokens and vault keys (PBKDF2 salts differ).
- The read-only key cannot be reversed to the vault passphrase.
- The KAT (9/9 JS, 6/6 backend) confirms cross-language parity.

**Caveat:** The brief and the dev pack both correctly note that the `delete_auth` must be **random** (never derived from the public string). This defacement gate is implemented: the `delete_auth` is a random secret stored in the owner vault at `.vault/owner/public-previews/<id>.json`. This is the right design.

### Decision: Not a Simple Token — CORRECT

The public-vault-ID is explicitly not a Simple Token (`word-word-NNNN`). The brief is clear: a Simple Token is a vault-key-derivation mechanism; the public-vault-ID is a deterministic public-preview key. Keeping them conceptually and mechanically distinct avoids coupling a new feature to a mechanism under refactoring. AGREE.

### Dependency: CloudFront Path-Segment Routing (DevOps)

The `/en-gb/app/<public-id>` route requires CloudFront to route path segments to the app shell. This is a DevOps dependency. An interim `?p=` query-parameter encoding is documented. This should be tracked as a DevOps requirement before the public-preview feature can be surfaced in production.

### Open Question: Server-Side OG Render Performance

The brief flags server-side performance for the OG-render path (crawlers fetch meta-tags server-side). The implementation uses a route on the User Lambda. Lambda cold starts + PBKDF2 derivation + HTTPS fetch-decrypt chain need to be measured before traffic arrives. The DevOps team should add this to the smoke-test + performance-monitoring checklist.

## 4. App-iframe Capabilities (Phases 1–4B) Assessment

The app-iframe permission system is the most architecturally significant body of work in this period. It was initiated by Explorer sessions in response to product need (not from a human brief), and the architect spec (`v0.27.79__architect-spec__app-iframe-capabilities-and-permissions.md`) was produced during the session.

### Security Floor — CORRECT AND NECESSARY

The non-grantable security floor (`.vault/**` reads/writes/list/nav blocked at the bridge, path-normalised to prevent traversal) closes a real attack vector: a malicious app iframe could have read `.vault/app.json` (which may carry the server access token). The floor is:
1. Non-grantable (app.json cannot grant vault access).
2. Path-normalised before the check (collapses `.`/`..`/`//`).
3. Applied to the bridge only (the owner editing `.vault/` in vault-mode is unaffected).

This is the right design. The 39-assertion unit test suite (`test__app_permissions.js`) covers path normalisation, traversal, floor rules, and grant parsing. **AppSec should verify the floor holds in a real browser.**

### `vault.delete` Deferral — CORRECT

The deferral of `vault.delete` is correct and the reasoning is sound: authorising `DELETE` requires the child's write key; storing that in `ro-links.json` (read-key tier) would expose write capability to any parent read-only-token holder. An owner-secret-tier credential store is required. This is a security-correct decision; shipping an insecure alternative would be a vulnerability. The open question for Phase 5 is: build the owner-secret-tier now, or find another approach.

**Recommendation:** The owner-secret-tier (double-encrypted via `vault-hkdf` owner key) is architecturally straightforward (the owner key derivation already exists in `vault-hkdf.js`). The deferral is appropriate; scheduling a Phase 5 session to design the owner-secret tier is the right next step. AppSec should sign off.

### `appId = SHA-256(app.json)` — SOUND

Using a hash of `app.json` as the stable app identity for consent caching is pragmatic: no separate app registry, no cross-origin key, derives from what's in the vault. The consequence (a cached consent is reset when `app.json` changes) is the correct behaviour: if the app's declared permissions change, the user re-consents.

## 5. Talk to the Vault (P-248) Assessment

The vault-chat dev pack (v0.27.80, 12 documents) is a code-grounded architecture spec that re-grounds the prior contract against the real `app-shell`/VFS bridge code. The corrections are significant and important.

### Key Corrections from the Dev Pack

| Correction | Significance |
|------------|-------------|
| `sg-agentic-loop`, `sg-tool-runner`, `sg-tool-definition` already exist in `__Tools` JS | The execution centre does not need to be built — only the policy/budget/CONFIRM wrapper | 
| `window.sg` bridge surface is `sg.vfs`/`sg.sync`/`sg.auth`/`sg.ui` (`git` is deprecated) | The contract must use the real bridge surface |
| Every `sg.vfs.write` is its own commit | The flush controller must coalesce writes into one commit; this is a bridge extension |
| Two VFS concepts: `window.sg.vfs` (bridge→vault) and `sg-vfs` (in-context, pluggable) | LLM working set uses `sg-vfs` memory; vault reached only through `window.sg` |
| OpenRouter key: parent `localStorage` today; vault decision: `.vault/secrets/openrouter.key` | Key must be injected at iframe-boot via one-time handshake; `/.vault/**` excluded from iframe VFS |

### Topology Decision — CORRECT

Everything-in-iframe is the right choice: minimal new bridge surface, clean blast-radius (the chat's scope is the vault), and the security properties of blob-origin isolation are maintained. The key injection (parent reads `.vault/secrets/openrouter.key`, injects at boot) is the only new bridge surface and is documented with security constraints.

### Track B (Cognition) — Deferred, Correctly

Track B (sidecars, multi-LLM consensus, semantic knowledge graph) is designed now but built after Track A. This is the right sequencing: Track A provides the substrate; Track B adds value on a working system. No architectural concerns with the design.
