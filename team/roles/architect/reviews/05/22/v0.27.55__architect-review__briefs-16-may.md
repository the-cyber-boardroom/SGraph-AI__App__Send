## Executive Summary

Day 66 is architecturally significant because it connects the substrate-mapping work from Day 65 to concrete shipping decisions. Three architectural patterns crystallised explicitly:

1. **Vault-as-communication-medium** between agents (first named explicitly in the multi-cloud brief; then echoed in backup, admin interface, CI pipeline)
2. **SG/Compute as serverless specifically for agents** (not generic Lambda; the parallel-request problem is the decisive technical argument)

The session also surfaces a critical DNS architecture correction (CNAME-to-wildcard does not work as described) and proposes the first real public-key infrastructure for vaults (Ed25519 + X25519). Both are foundational decisions.

## Architectural Findings by Domain

### 1. Serverless for Agents — The Central Architectural Decision

**Brief:** `v0.27.45__strategy-brief__sg-compute-as-serverless-environment (1).md`

The synthesis brief makes the decisive technical argument the team has been circling for weeks: **Lambda penalises parallel requests because each concurrent request needs its own cold-started execution context**. An agent making 20 parallel tool calls to the same Lambda endpoint triggers 20 potential cold-starts if no warm instances are available. Containers do not have this problem — one container handles many parallel requests with one cold-start cost paid once.

**Architectural assessment: sound.** The comparison table (Lambda vs SG/Compute) is accurate. The framing as "for agents, not generic Lambda alternative" is the right scope discipline — it avoids chasing Lambda's strengths (sub-second cold-start, infinite auto-scale, zero ops) where Lambda is genuinely better, and plays to our differentiation.

**The cold-start budget table needs to become a first-class document:**

| Path | Target | Status |
|------|--------|--------|
| EC2 from cold | 30-60s | Confirmed working (50s per doc 428) |
| EC2 from warm pool | 5-15s | PROPOSED — pool infrastructure not built |
| Fargate from cold | 10-30s | Experimental — not confirmed in production |
| Container on running EC2 | 1-5s | PROPOSED — container hosts primitive |
| Cached container | <1s | PROPOSED |
| Firecracker snapshot | <50ms | PROPOSED — PoC not yet done |

Only the 50-second dedicated EC2 path is confirmed in production. All others are projected from research. **Marketing claims must not be made until at least Fargate and container-on-running-EC2 are measured against real workloads.**

**Architecture concern:** The edge router (P-161) is a critical piece that does not exist yet. A single Lambda + state machine that checks "is there a running instance for this address?" and routes accordingly must be extremely reliable — if it fails, no vault apps are reachable. Design this with appropriate redundancy from day one.

### 2. Vault Public Key Infrastructure — Foundational Decision

**Brief:** `v0.27.45__arch-brief__vault-discovery-and-public-keys.md`

The proposal to add Ed25519 + X25519 key pairs to vaults (P-151) is architecturally the right approach. Ed25519 for signing (small keys, fast verification, widely supported) and X25519 for key agreement (enables asymmetric encryption via X25519-based ECDH) follows industry standards (used in Signal Protocol, WireGuard, age).

**Key architectural decisions this requires:**

1. **Key generation timing:** At vault creation, or deferred until first need? Recommendation: generate at creation — every vault should have a key pair regardless of whether it uses discovery. Retrofitting keys to existing vaults is harder than generating them proactively.

2. **Key storage:** Private key must never leave the client's control. If vaults are hosted on our servers, the private key must be stored encrypted under the vault key — same model as the vault's content encryption. This is consistent with the zero-knowledge design.

3. **Key rotation:** Explicitly flagged as an open question (OQ-disc-1). The brief notes rotation needs "explicit rotation events with both old and new keys briefly active." This is correct; key rotation is a finite state machine: generate new key → announce both keys valid → rotate to new key → retire old key. This needs a spec before implementation.

4. **Identifier model:** The brief correctly recommends keeping human-readable vault IDs as primary identifiers, with public keys as auxiliary for cryptographic uses. Do not make the vault ID a hash of the public key — migration cost is too high for existing vaults, and key rotation would break identifiers.

**"Send to a vault" (P-152):** Architecturally elegant. The flow (sender encrypts to public key → POST to server → stored in inbox → owner decrypts) maps cleanly to existing vault storage. The inbox needs a defined schema. Key risk: a malicious sender can spam a vault's inbox with encrypted garbage. Rate limiting per vault + per IP is required from day one.

**TXT records for public keys (P-154):** Sound approach (DKIM pattern). One caution: TXT records at a slug must always accompany an A record at the same slug, or the slug becomes NOERROR/NODATA for A queries and browsers cannot reach it. The brief explicitly states this — ensure the sync process enforces the A + TXT pairing.

### 3. DNS Architecture Correction — Critical

**Brief:** `v0.27.45__arch-brief__vault-registry-via-dns-records.md`

The correction the brief makes is accurate and important. RFC 4592 is unambiguous: a wildcard record does not match a name once any concrete record exists at that name, regardless of record type. The CNAME-to-wildcard scheme in the voice memo would have produced subtly broken behaviour across DNS implementations.

The corrected scheme (A record at the slug pointing to the same IP as the wildcard) works correctly. Properties verified:
- DNSSEC compatibility: A records at slugs + wildcard A record work cleanly
- TLS: wildcard cert covers both; no SNI issues
- State transitions: changing A record from Lambda IP to instance IP is a single atomic DNS update

**Architecture recommendation:** Adopt the corrected scheme as the canonical implementation. The admin vault as registry-of-truth (P-188) with DNS as a projection (P-189) is the right architectural inversion — DNS should not be the source of truth because it has propagation delays and no audit history. The vault wins on both counts.

**Risk flagged:** State drift between admin vault and DNS (P-189). The reconciliation job that catches drift is essential and must run continuously — not as a scheduled job but as a process that monitors vault commits and applies DNS changes in near-real-time, with the hourly sweep as a safety net.

### 4. Vault Testing Framework — Architecture Assessment

**Brief:** `v0.27.45__arch-brief__vault-testing-framework.md`

The four-layer model is sound. The key insight — using the same JS API surface for tests as for production — is architecturally correct and avoids the common failure mode of tests that don't exercise real code paths.

**One architectural concern:** The test definition format (single file with `layer` option) creates an implicit contract between the test runner and the execution environments. As the framework grows, tests declared as `'browser'` will be run in Playwright, which has very different capabilities from Vitest. The `layer` routing must be treated as a first-class configuration interface, not an implementation detail — if it changes, all existing test files need updates.

**Recommendation on test runner:** Vitest is the right choice. It is ESM-native, fast, Playwright-compatible for browser layer, and has a strong ecosystem. Do not default to Jest — the CJS-to-ESM migration overhead is non-trivial.

**The fifth test layer (LLM-validated qualitative, P-143):** Architecturally interesting but must be treated as advisory-only in CI. LLM outputs are non-deterministic; a qualitative test that blocks a merge because the LLM returned a different opinion on the same code change is a false positive problem. Design the fifth layer as "informational by default, blocking only when explicitly configured."

### 5. Agent Communication via Vaults — Pattern Assessment

**Brief:** `v0.27.45__strategy-brief__multi-cloud-deployment-and-agent-communication.md`

The vault-as-communication-medium pattern (P-172) is architecturally sound for the stated use cases: asynchronous, eventually-consistent cross-agent workflows where audit trail is important.

**Constraints to document explicitly:**

1. **Not appropriate for synchronous request-response.** If SG/Deploy needs a credential synchronously from SG/Compute to complete a deployment, vault round-trip latency (write → poll → read) is 1-10 seconds — too slow for interactive workflows. Design these cases to use direct CLI invocation as a fallback.

2. **Vault contention.** If multiple agents write to the same shared vault concurrently, conflict resolution must be defined. The vault's CAS (content-addressable storage) model helps, but the request queue schema needs explicit append semantics or a locking protocol.

3. **Schema versioning.** Both SG/Compute and SG/Deploy must agree on the request/result format. When either evolves, the shared vault schema must be versioned. Define this schema spec before the first integration.

**The SG/Deploy split decision is correct.** Adding GCP and Akamai primitives to SG/Compute would balloon its scope. The split also forces the vault-communication pattern to be proven, not just designed.

### 6. Backup Architecture — Assessment

**Brief:** `v0.27.45__dev-brief__backup-and-restore-strategy-for-vaults.md`

The 7-tier storage strategy (P-178) and separate AWS backup account (P-179) are sound and follow well-established operational patterns. The ransomware isolation argument (write-only IAM from account A to account B) is technically accurate.

**Architectural concern:** The brief explicitly defers sequence backup (vault commit history) in favour of data backup (raw S3 bytes). This is the pragmatic v1 decision. **Flag for v2:** without sequence backup, point-in-time recovery is not possible — only restore-to-latest-backup. For vaults holding mission-critical workflow state (manager vaults, backup-operations vault itself), this may be insufficient.

**The backup-operations vault is itself a vault.** This recursive application of the pattern is correct and desirable (dogfooding), but the bootstrapping concern is real: the backup-operations vault must itself be backed up, and its restore process must be simpler than the general vault restore process, otherwise the backup system cannot bootstrap itself after a catastrophe.

**Restore drill schedule (P-181):** The daily lightweight, weekly full, monthly full-platform, quarterly cold-tier cadence is operationally right. The monthly full-platform drill (restore all vaults to a fresh AWS account) is the most expensive but most valuable — it is the only test that catches cross-vault dependencies and account-level configuration drift.

### 7. AppSec Mini-Tools — Architectural Positioning

**Brief:** `v0.27.45__strategy-brief__appsec-mini-tools-on-top-of-vaults.md`

The pattern (find strong open-source tool + host on our infra + vault integration + contribute back) is architecturally clean. The data-sharing problem framing is accurate: AppSec tool data is moderately sensitive, needs versioning and sharing with revocation, and needs offline portability — vaults check all three.

**Two-mode architecture (P-155: client-side vs ephemeral compute-backed) is correct.** These serve genuinely different audiences. The client-side mode must be designed so it can run with zero network access (local LLM option) — this is the air-gapped requirement for regulated environments.

**Key architectural question for StrideGPT integration:** StrideGPT is a Python/Streamlit application. Integrating it into our vault architecture requires a wrapper that:
1. Runs StrideGPT in an ephemeral container on our substrate
2. Reads inputs from the threat-model vault
3. Writes outputs back to the vault
4. Reports cost to the pre-auth metering substrate

This is not trivial — it is essentially a job runner that wraps an external Python application. The generic pattern (job runner wrapping any external tool) should be designed once and reused across all AppSec mini-tools.
