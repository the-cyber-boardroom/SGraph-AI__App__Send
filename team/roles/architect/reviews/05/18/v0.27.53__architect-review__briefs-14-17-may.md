## Architectural Assessments

### 1. Vault Collections and Container Hosting (Briefs 384, 385, 389, 391)

**Soundness: HIGH**

The vault-as-zip portability concept is architecturally clean. It extends the existing object CAS model naturally — a vault collection is simply a directory of encrypted object stores that can be bundled, transmitted, and mounted. The key insight is that encryption is already object-level (AES-256-GCM per object), so a zip of encrypted objects is inherently safe to move between substrates.

The three density modes (dedicated EC2, multi-container, multi-vault-per-app) map well to real workload shapes: regulated isolation-sensitive workloads → dedicated; moderate multi-tenancy → multi-container; lowest-cost batch → multi-vault. The routing layer in multi-container mode (hostname → container) is a standard nginx/Traefik pattern with no novel risk.

**Vault rendering without iframe (bare-metal mode)** is architecturally simpler than the current iframe approach for single-app published vaults. The trade-off is correct: iframe isolation is useful for multi-app composition (hosted mode) but adds unnecessary complexity for standalone published vaults. The `window.SG.vault` API surface abstraction is the right boundary — the vault app doesn't know which rendering mode it's in.

**Concern:** The Vault Synchronizer is referenced as the orchestrator for three new commands (`deploy container`, `deploy ephemeral`, `--density` flag). The Vault Synchronizer is not currently in this repo — it lives in the SG/Compute project. This needs clarity: are these commands being added to sgit, to a separate CLI, or to SG/Compute? The brief is ambiguous.

**Concern:** Warm pools at £1-3/day for 3-5 t3.small instances are always-on costs regardless of usage. This needs a pool drain policy for low-traffic periods and a cost circuit breaker.

### 2. Manager Vault Pattern and Credential Manager (Briefs 386, 387)

**Soundness: HIGH — with one critical clarification needed**

The manager vault pattern is architecturally elegant: it reuses the vault's existing encrypted storage, commit history, and access control model for operational state. No new persistence layer. The credential manager vault is the first concrete instantiation.

The Simple Token format (`tok_<random>`) is distinct from the existing vault Simple Token auth format (`word-word-NNNN`). **This naming collision is a risk.** The existing system uses word-word-NNNN tokens for vault key derivation. The proposed `tok_<random>` tokens are API credential proxies. These must be clearly distinguished in documentation, code, and UX to avoid confusion.

The proxy mode (API keys never leave the credential manager) vs direct mode (token resolved to actual key) is a sound separation. Proxy mode is more secure but adds a network hop; direct mode is simpler but exposes keys to the callers. The brief correctly positions this as a configuration choice per credential class.

**Concern (OQ-cred-1):** The credential manager vault describes scoped tokens for third-party API access (OpenRouter, Anthropic, AWS). The existing admin Lambda already has a token management system (Simple Tokens for vault access). These must not conflict. The architect needs to specify whether the credential manager sits above the existing token system or is a separate namespace entirely.

### 3. Dynamic Credential Delivery Service (Brief 397)

**Soundness: HIGH**

The STS AssumeRole pattern for just-in-time AWS credentials is the correct approach for scoped infrastructure access. The scope catalogue versioned in a vault gives auditability and version control on privilege definitions — this is a non-obvious but valuable property.

The six-phase rollout (local validation → deployed service → IAM graph evidence) is well-sequenced. Phase 6 (SG commands themselves migrate to use scoped credentials) is the terminal state where the system eats its own dog food.

**Architectural note:** This service needs to be in-band with the dynamic credential delivery service brief from 05/17 and the IAM graph brief (400). All three are parts of the same security posture system. The Architect should specify the integration points before any implementation begins.

**Dependency:** The dynamic credential delivery service depends on the IAM graph (brief 400) for the scope catalogue definitions. IAM graph discovery must precede scope catalogue publication.

### 4. Infrastructure CLI Expansion (Briefs 399, 401, 402, 403, 404, 405)

**Soundness: MEDIUM-HIGH — individual components sound, collective scope is large**

Each individual CLI extension (Fargate, S3, container hosts, Bedrock) follows the established pattern: abstract AWS service complexity behind clean command trees, vault-ground all state, credential-manager integration. The pattern is proven.

**Fargate experiment (399):** This is a measurement brief, not a feature brief. The output is a decision table (Fargate wins/loses by workload shape), not new user-facing functionality. This is exactly the right way to approach substrate selection. The 7-metric benchmark design is appropriate.

**S3 native CLI (402):** The ETag-based conflict detection for vim edit integration is a useful safety mechanism. The vault-aware wrappers (`vault-open`, `vault-sync`, `vault-diff`, `vault-ls`) correctly layer vault semantics on top of S3 primitives. **Concern:** The brief must specify whether these wrappers go through `osbot-aws` (required by project rules) or call boto3 directly (prohibited).

**Container hosts primitive (403):** This is effectively a lightweight Kubernetes substitute — Lambda placement + per-host REST API. The multi-region parallel execution feature (`--regions us-east-1,eu-west-1,ap-southeast-2 --count-per-region 10`) is powerful but introduces cross-region state management complexity. Clarification needed on whether this primitive lives in SG/Compute or this repo.

**Bedrock CLI (404):** The vault-grounded model for AI sessions (prompts, agent definitions, memory, costs in vault) is architecturally consistent with the vault-first strategy. MCP interop as a design constraint is correct — CLI tools exposed as MCP tools is the right integration point.

**Substrate strategy (405):** The substrate spectrum framework (laptop → Lambda → Fargate → EC2 container → dedicated EC2) is the correct unifying narrative. The one-flag substrate selection principle is achievable if the CLI primitives are implemented consistently. The brief honestly acknowledges that Lambda hidden costs (SnapStart) make it uncompetitive for many workloads — this validates the multi-substrate approach.

### 5. Unified Observability Session (Brief 398)

**Soundness: HIGH**

The interactive session REPL for cross-source log investigation is architecturally clean: reads from sources directly (no consolidated backend in v1), source abstraction contract (`connect`, `list`, `tail`, `query`, `stats`, `schema`), session state persistence. The `agent-trace` feature (Bedrock + S3 + vault commits + costs in one trace) is a high-value capability for debugging agentic workflows.

**No architectural concerns.** This is read-only aggregation over existing sources. The main implementation risk is the breadth of source adapters, not architectural unsoundness.

---

### 6. IAM Graph Visualisation and Lockdown (Brief 400)

**Soundness: HIGH**

Graph-based IAM discovery is the correct approach for a complex permission structure. The evidence-driven cleanup (CloudTrail-derived observed vs granted permissions) is the right way to avoid blind revocation. The six-phase rollout (discovery → visualisation → cleanup → evidence → expansion → SG command migration) is well-sequenced.

**Critical integration point:** Phase 6 (SG commands themselves migrate to scoped credentials) depends on the dynamic credential delivery service (brief 397). These two briefs form a dependency chain that must be planned together.

---

### 7. Platform Validation vs Kubernetes (Briefs 392, 393, 394, 395)

**Architectural verdict:** Research validates the platform choice.

The per-tenant VM model is correctly positioned for the actual workload profile (bursty, isolation-sensitive, low-duty-cycle). The honest acknowledgement of where Kubernetes wins (dense scheduling, large stable workloads, established ecosystem) is important — it prevents architectural overreach.

**No new architectural concerns from these briefs.** They are strategic positioning documents, not technical specifications. The infographics (brief 392) serve external communication.
