## Executive Summary

This batch represents a **coherent platform expansion** from a single-product (file sharing) to a multi-product platform with publishing, compute, package management, and vertical customer workflows. The briefs are architecturally interconnected: the Local Claude milestone unlocks the package manager; the package manager enables the entrepreneur stack; the entrepreneur stack drives the customer workflow briefs (healthcare, job search, publishing). The architectural cascade is clear and internally consistent.

**Verdict:** The direction is sound. The key architectural risks are sequencing (too many PROPOSED items competing for Dev time) and the vault encryption mode decision (which blocks encrypted video streaming). The 05/10 vault-web handover is a high-quality technical artefact — Dev should adopt it immediately.

## 1. Vault-Web Handover (05/10) — Architectural Assessment

**Documents:** field-guide, gotchas, debrief (docs 352–354)

The vault-web team has produced three high-quality technical documents covering the iframe integration architecture. All patterns described are **EXISTS** in the current codebase.

**Architectural observations:**

### 1a. The `sg` Global Object API (EXISTS, well-designed)
The `sg.*` API surface (loadCss, loadJs, vfs.read/write/list, app.selfPath) is clean and covers the primary needs of vault-hosted apps. The path asymmetry documented in gotcha #3 (`bare/` prefix in list results vs `path/to/file` in read calls) is a known bug — not a design flaw, but it will cause repeated confusion until resolved.

**Recommendation:** Add an API normalisation layer. `sg.vfs.read()` should accept either path format and normalise internally. This is a one-day fix that prevents repeated developer error.

### 1b. FOUC Pattern (EXISTS — well-documented)
The FOUC (Flash of Unstyled Content) prevention pattern (load CSS before render, use display:none until ready) is correctly documented. The solution is sound but requires discipline from every vault app author.

**Recommendation:** Bake FOUC prevention into the vault template. The default template should include the pattern so new apps start correctly. Otherwise every new author rediscovers this pain.

### 1c. Delete Not Implemented (Architectural Gap)
Gotcha #2 documents that `sg.vfs.delete()` is not yet implemented. This blocks several proposed workflows (cleanup after processing, ephemeral temp files, archive management).

**Recommendation:** Prioritise implementing `sg.vfs.delete()`. It is a missing primitive, not an enhancement. Until it exists, vault apps cannot manage their own state correctly.

### 1d. localStorage Blocked in Preview Mode (Architectural Constraint)
The preview iframe cannot use localStorage. This is a browser security constraint (opaque origin), not a bug. Vault apps that need persistence must use `sg.vfs.write()` exclusively.

**Recommendation:** Document this explicitly in the vault template CLAUDE.md and README. It is a constraint that developers will hit repeatedly without guidance.

## 2. SG/Compute Package Manager (05/11) — Architectural Assessment

**Document:** `v0.27.32__arch-brief__sg-compute-package-manager.md` (doc 357)

PROPOSED — does not exist yet.

The package manager brief is the most architecturally significant document in this batch. It defines a new infrastructure primitive with deep implications.

### 2a. 10 Principles — Assessment

| Principle | Assessment |
|-----------|------------|
| Graph-driven (dependency graph) | Sound. Standard package manager design. |
| Tests-as-contract | Excellent. Tests travel with packages — enables safe composition. |
| Reuse-not-reimplement | Sound. Requires robust discovery (search, tagging, ratings). |
| Offline-first | Critical for EC2 image builds. Requires pre-resolved dependency graphs. |
| Granular loading | Sound. Avoids monolith packages. Needs a module boundary definition. |
| Compute-agnostic | Ambitious. Implies an abstraction layer over Lambda, Docker, EC2, GCP. |
| OS-aware | Needed for ARM64 vs x86, Ubuntu vs Amazon Linux. |
| Vault sidecars | Novel. SKILL.md + USAGE.md as agent-readable package metadata. The key differentiator. |
| LLM-friendly | Follows from vault sidecars. Well-motivated. |
| Per-client customisation | Required for the commercial model. See strategy brief (doc 370). |

**Architectural concern:** "Fractal composition" (managers nesting inside managers) is powerful but risks combinatorial complexity. The dependency resolver must be cycle-safe and the version conflict resolution strategy must be defined before implementation starts.

### 2b. S3-First Loading (Critical Design Decision)
The brief proposes S3-first over AMI for image distribution (5× faster, per doc 358). This is a good call architecturally: S3 objects are immutable and composable in a way AMI snapshots are not.

**Key question (OQ-pkg-1):** Does the Local Claude milestone (open source LLM + sgit tool use on EC2) block or enable the package manager? The dependency order must be resolved before Dev can begin.

### 2c. SKILL.md + USAGE.md Sidecar Pattern (Novel — Recommend Standardising)
This is the most distinctive architectural contribution in the batch. A sidecar that teaches an LLM how to use a package, alongside code, is a genuinely new pattern with broad applicability.

**Recommendation:** Define SKILL.md and USAGE.md schemas immediately. They should be versioned alongside the package and validated by the package manager on publish. This is the asset that differentiates SGraph's package manager from npm/pip.

## 3. EC2 Image Build CLI (05/11) — Architectural Assessment

**Document:** `v0.27.32__dev-brief__ec2-image-build-cli-s3-first.md` (doc 358)

PROPOSED — does not exist yet.

The `sg-image` CLI (6-phase pipeline: capture → package → load → test → strip → measure) is a well-scoped first version. S3-first is the right call.

**Architectural concern:** GPU support adds significant complexity (CUDA drivers, NCCL, model weights). The brief correctly separates runtime from model weights — that is the right architectural decision. However, the test phase needs to define what "test" means for an image: does it run the LLM and assert a response? That is slow (minutes). Define the test contract precisely.

**Recommendation:** Phase 1 CPU-only; Phase 2 GPU. Do not try to solve GPU in the first CLI version.

## 4. Published Readonly Vaults / sgraph.app (05/11–05/12) — Architectural Assessment

**Documents:** docs 366, 375, 376

PROPOSED — does not exist yet.

Three documents converge on the same architectural direction: vaults becoming publishable to public URLs. This is the highest-priority new product capability in the batch.

### 4a. Three Modes

| Mode | Description | Complexity |
|------|-------------|------------|
| Live published vault | `*.sgraph.app/en-gb/#<share-token>` — server-rendered, SEO | Medium |
| Serverless static | `sgit publish-static` → offline HTML bundle | Medium |
| Custom domain | Bring your own domain — DNS delegation to SGraph | High |

**Recommendation:** Implement modes in order above. Custom domain is high complexity (wildcard cert + SNI routing) and should be Phase 2 or 3.

### 4b. sgraph.app Subdomain Registration (PROPOSED)
The slug-to-share-token lookup is architecturally clean: it reuses existing token infrastructure with a new slug index. The slug must be unique per user account.

**Key question (OQ-publish-1):** Is `sgraph.app` wildcard DNS and cert provisioned? This blocks all subdomain work.

### 4c. SEO Implications
Published vaults require server-side rendering for SEO. The current architecture (client-side decryption) is fundamentally incompatible with server-side rendering of encrypted content. The SEO layer must operate on unencrypted metadata only (title, description, sitemap entries). Content SEO is not possible without breaking the zero-knowledge property.

**Architectural constraint:** Published vault SEO = metadata only. Content is still client-side decrypted. This must be documented clearly in the product brief to avoid investor-level misrepresentation.

## 5. GitHub-as-Vault-Projection (05/11) — Architectural Assessment

**Document:** doc 359

PROPOSED — does not exist yet.

The two-layer VCS pattern (Git = developer surface, SGit = consumer distribution) is architecturally sound and solves a real problem: customers want their work in Git for versioning, but consumers should access it via encrypted vault.

**Three-phase rollout:**
1. Manual sync (human runs both)
2. GitHub Action (auto-sync on push)
3. Bidirectional sync (vault changes propagate back to Git)

**Architectural concern:** Phase 3 (bidirectional) is complex. Two-way sync between Git and SGit requires a merge strategy. Define the conflict resolution rules for Phase 3 before implementing it. Phases 1 and 2 are safe to ship without solving Phase 3.

**Recommendation:** Ship Phase 1 (manual) and Phase 2 (GitHub Action) in the next Dev sprint. Phase 3 requires an Architect Brief before Dev touches it.

## 10. Encrypted Video Streaming Research (05/12) — Assessment

**Document:** doc 377

PROPOSED (research, no recommendation yet).

Three approaches proposed:
1. Chunked encryption (client-side, sequential)
2. Streaming decryption (requires specific AES mode — may conflict with current AES-256-GCM)
3. HLS/DASH segments (industry standard, most complex)

**Critical architectural decision needed:** The current vault encryption uses AES-256-GCM. Approach 2 (streaming decryption) requires a streaming-compatible cipher (e.g. AES-CTR or ChaCha20). Changing the cipher affects all existing vault objects and is a breaking change.

**Recommendation:** Research brief is correct to flag this. An Architect decision is required before any video streaming implementation begins. The cipher mode research (OQ-video-1) must be owned by the Architect — this is not a Dev decision.
