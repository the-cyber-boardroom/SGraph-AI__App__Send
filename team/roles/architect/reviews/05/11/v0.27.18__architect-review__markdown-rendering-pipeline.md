# Architect review — Markdown rendering pipeline

**Date:** 2026-05-11
**Author:** Claude (Opus 4.7), prompted by Dinis
**Scope:** How SGraph Send currently renders and edits markdown inside the
Send share view, the Vault, and (transitively) App Mode. What's coupled,
what's brittle, and how to refactor toward an isolated, reusable module.

---

## 1. Executive summary

Two bugs surfaced this session pointed at the same underlying problem:
markdown handling is **scattered across four separately-versioned files**
that share global state by convention rather than interface.

| Bug | Symptom | Root cause |
|---|---|---|
| List continuation | `1. item\n   continuation` rendered as `<p>` after `<li>` | Parser only consumed one line per list item |
| Edit shows wrong text | Editing `*.md` opened the contents of the first code block | `vault-browse-edit.js` read `<pre>` from the rendered DOM instead of the source bytes |

Both are now fixed in this branch (commits `40e7236` and `d7a23b0`). The
list-continuation fix is **invisible in production** because the vault
loads `markdown-parser.js` from `https://dev.send.sgraph.ai/_common/js/`
— a deployed CDN. Until that CDN is rebuilt and republished, the local
patch has no effect on what the user sees.

The deeper finding: **the parser is the only piece that is genuinely
reusable**, and even it is consumed via in-place monkey-patching by a
separate overlay file. Every other moving part — the call into the
parser, the post-render image/link rewriter, the edit flow, the
"Source" toggle, the App Mode lift — is hard-coded against the
`send-browse` DOM structure.

A refactor that pulls the parser, its overlay, and a thin
"editable-source" contract into `_common/lib/markdown/` lets us delete
this whole class of bug and stop debugging the same pipeline three
times (once for Send, once for Vault, once for App Mode).

## 2. Current shape of the pipeline

### 2.1 Files involved

```
sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.0/_common/js/
├── markdown-parser.js                    (290 lines — pure parser, no DOM)
└── components/send-download/
    └── send-browse.js                    (~1200 lines — renders, intercepts links/images)

sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.1/_common/js/
└── markdown-parser-v031.js               (153 lines — monkey-patches MarkdownParser in place)

sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.2/_common/js/components/send-download/
└── send-browse--v0.3.2.js                (overlay — patches SendBrowse.prototype methods)

sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/
├── index.html                            (loads parser + overlay from CDN, see §2.3)
└── _common/js/components/
    ├── vault-browse-edit/vault-browse-edit.js  (adds Edit/Save buttons by patching SendBrowse)
    └── sg-app-banner/sg-app-banner.js          (lifts .sb-file__content for App Mode)
```

### 2.2 Render call chain (markdown file selected in Browse)

1. User clicks the file in the tree
2. `send-browse.js` → `_renderFileContent(container, bytes, fileName, type)`
3. `type === 'markdown'` branch decodes bytes → `MarkdownParser.parse(text)` →
   safe HTML
4. `content.innerHTML = '<div class="sb-file__markdown">' + html + '</div>'`
   (`send-browse.js:493-494`)
5. A hidden `<pre class="sb-file__md-source">` is also injected for the
   "Source" toggle button
6. Post-render: `BRW-005` walks `<img data-md-src="...">` nodes, resolves
   each `data-md-src` to a `blob:` URL from the loaded zip, sets `src`
7. `BRW-004` intercepts clicks on relative-path links to open them as
   new tabs in the browse view

### 2.3 The CDN coupling

The vault's `index.html` loads the parser by absolute URL:

```html
<script src="https://dev.send.sgraph.ai/_common/js/markdown-parser.js"></script>
<script src="https://dev.send.sgraph.ai/_common/js/markdown-parser-v031.js"></script>
```

This is **why the list-continuation fix did not visibly work this
afternoon.** The fix is in the repo, but the vault is fetching the
parser from the deployed Send service, not from its own version tree.
The same is true for the v0.3.1 overlay.

Consequences:
- The vault and Send are tied to the **same parser version at
  runtime**, regardless of which folder you edit
- A regression in the deployed Send parser silently breaks the vault
- Reverting a parser change in Send (e.g. via a hot-rollback) breaks
  the vault without any vault deploy event
- Local development on the vault cannot test a parser change without
  also redeploying Send

### 2.4 The overlay pattern

`markdown-parser-v031.js` does **in-place mutation** of the `MarkdownParser`
object:

```js
MarkdownParser._sanitizeUrl = function(url) { ... }   // line 54
MarkdownParser._renderInline = function(text) { ... } // line 89
```

It saves bound references to the original methods, then assigns new
implementations. This works because both files share a global, and
because the overlay is loaded with a second `<script>` tag after the
base.

What this pattern costs:
- The "behaviour of the parser" is the **union of two files** that
  must be read together to understand any feature (images, links,
  inline rendering)
- Adding any feature means deciding which file owns it; the answer
  has historically been "the latest overlay"
- The base parser's tests, if any, don't cover the overlay path
- Loading order is a hidden contract — if either file fails to load,
  the parser silently regresses

### 2.5 The edit path (where today's bug lived)

`vault-browse-edit.js` overlays `SendBrowse.prototype._renderFileContent`.
After the original runs, it inspects the rendered DOM to decide what
to put in the textarea when the user clicks Edit:

```js
var content   = container.querySelector('.sb-file__content');
var preEl     = content ? content.querySelector('pre') : null;
…
var currentText = preEl ? preEl.textContent : new TextDecoder().decode(bytes);
```

For plain text files, the render path is `content.innerHTML = '<pre>…</pre>'`
— so `preEl.textContent` happens to be the file content. For markdown,
the render path is `content.innerHTML = '<div class="sb-file__markdown">…</div>'`
which contains code blocks rendered as `<pre><code>…</code></pre>`.
`querySelector('pre')` returned the **first code block**, and the
textarea showed that code block's text.

The fix is one line — always decode `bytes` — but the structural
problem is that **edit has no contract with render**. It reverse-engineers
the DOM. Any change to how `_renderFileContent` lays out HTML can break
edit silently, in a way that only shows up when a user clicks the button.

## 3. Coupling map

| Consumer | What it depends on | How brittle |
|---|---|---|
| `send-browse.js` (markdown branch) | `MarkdownParser.parse()` returning safe HTML; output uses specific class names | Tight but local |
| `send-browse.js` (image rewriter, BRW-005) | Parser emits `<img data-md-src>` (overlay-only behaviour) | Requires overlay to be loaded |
| `send-browse.js` (link interceptor, BRW-004) | Parser emits relative `<a href>` (overlay-only) | Requires overlay to be loaded |
| `vault-browse-edit.js` (Edit button) | `.sb-file__content` exists; first `<pre>` is the source (FALSE for markdown) | **Now fixed**, but no contract |
| `vault-browse-edit.js` (Save → re-render) | `SendBrowse._renderFileContent` accepts new bytes and reproduces the same DOM | Implicit |
| `sg-app-banner.js` (App Mode lift) | `.sb-file__content` is the renderable element to lift to fixed position | Implicit |
| `send-browse.js` ("Source" toggle) | Keeps two parallel subtrees (`.sb-file__markdown` and `.sb-file__md-source`) and shows/hides them | Local |

**The pattern:** every consumer below the parser line either
- queries the DOM for a structure send-browse owns, or
- patches a `SendBrowse.prototype` method by reference

There is no `MarkdownView` object, no event the renderer emits when
content changes, and no documented "what HTML do you produce for a
markdown file" contract.

## 4. Reusability assessment

| Module | Reusable? | What blocks isolation |
|---|---|---|
| `MarkdownParser` | ✅ Already pure | Currently mutated in place by the v031 overlay |
| v031 overlay | ⚠️ Tied to base | Uses `_renderInline`/`_sanitizeUrl` internals, references `_escape` |
| send-browse markdown branch | ❌ Coupled | Owns DOM layout, image rewriting, link interception, source toggle |
| vault-browse-edit edit flow | ❌ Coupled | Reverse-engineers send-browse's DOM |
| App Mode lift | ❌ Coupled | Targets send-browse's `.sb-file__content` |

The good news is that the **only piece doing real work** that we care
about reusing (the parser) is already pure. The problem is everything
above it.

## 5. Refactor proposal

### 5.1 Goals

1. **One canonical source for the parser**, with no overlays, served
   from one location per app
2. **A documented contract** between markdown rendering and its
   consumers (edit, App Mode, print)
3. **No `querySelector` on rendered markdown** outside the
   rendering module
4. **No CDN-fetched JS for vault apps that have their own version
   tree** — vault should ship its own copy of the parser

### 5.2 Proposed shape

```
_common/lib/markdown/
├── markdown-parser.js     ← absorbs v031 overlay into base; no global mutation
├── markdown-renderer.js   ← takes (container, bytes, fileName, options) → markdown view
│                             owns class names, image/link rewriting, source toggle,
│                             and exposes getEditableSource() / refresh(bytes)
└── README.md              ← documents the contract
```

The renderer becomes the single entry point. It returns a small handle:

```js
const view = MarkdownRenderer.mount(container, bytes, {
    fileName,
    resolveBlobUrl,      // for relative images
    onLinkClick,         // for relative-path links
});

// Consumers use the handle instead of querying the DOM:
view.getSource()       // → string (always the original markdown)
view.refresh(newBytes) // → re-render in place
view.unmount()         // → cleanup
view.isSourceVisible() // → for the Source toggle
view.toggleSource()    // → show/hide raw source
```

`vault-browse-edit.js` then becomes:

```js
var currentText = view.getSource();   // explicit, never wrong
// …
self.dataSource.saveFile(folder, fName, newBytes.buffer).then(() => {
    view.refresh(newBytes);            // no DOM-shape assumptions
});
```

### 5.3 Absorbing the v031 overlay

The overlay's three features (image `<img>` with `data-md-src`, relative
links, Discourse alt syntax, `BRW-021` code-span fix) are now stable
and should be merged into the base parser. The overlay file would be
deleted. No production behaviour changes — the union is already what
runs.

### 5.4 Where the parser physically lives

Two acceptable end-states:

**A. Ship-in-each-app.** The user UI and the vault each get their own
copy under `_common/lib/markdown/`. Versioning is per-app. Cost: one
duplicate file. Benefit: vault no longer depends on the Send CDN at
runtime — it can be opened from a local file URL and still render
markdown.

**B. Shared package.** A single `sgraph-markdown` npm-style package
imported by both apps. Cost: a build step where there is currently
none. Benefit: one source of truth.

**Recommendation: A**, for now. Both apps are IFD — they already
duplicate fonts, design tokens, and shared CSS. Duplicating one 350-line
parser file is consistent with that model and removes a real runtime
dependency. Revisit B if/when a third app appears.

### 5.5 What this does not solve

- The "Source" button and Edit button overlap conceptually. They could
  be unified into one editor with a render/source toggle. Out of scope
  for this refactor — would change UX, not just code.
- App Mode's content-lifting is independent of markdown and is
  correctly factored as a separate concern. Leave it.
- Print preview is a separate path (`window.print()` on the iframe
  for HTML files, on the document for markdown). Not affected.

## 6. Sequencing

The refactor is independently valuable even if we never write a new
feature on top of it. Suggested order:

1. **(done this session)** Patch both bugs in place — short, surgical
2. Deploy the parser fix to `dev.send.sgraph.ai` so the vault picks up
   the list-continuation fix (no code work needed, just a redeploy)
3. Create `_common/lib/markdown/` in the user UI; copy parser, absorb
   overlay, delete `markdown-parser-v031.js` from the next version
4. Add `MarkdownRenderer.mount()` API; migrate `send-browse.js` markdown
   branch to use it
5. Migrate `vault-browse-edit.js` to use `view.getSource()` /
   `view.refresh()`
6. Copy `_common/lib/markdown/` into the vault tree; remove the
   CDN-fetched `<script src="https://dev.send.sgraph.ai/...">` lines
   from `vault/v0/v0.2/v0.2.x/index.html`
7. Add one Playwright assertion per consumer: Edit-on-markdown returns
   source, App Mode shows white background for tables, list
   continuation joins into one `<li>`

Steps 3–7 are roughly half a day of work and leave the codebase with
one parser, one renderer, and no shared global mutation.

## 7. Open questions for Dinis

1. **CDN coupling — is it intentional?** The vault loading the parser
   from `dev.send.sgraph.ai` was likely convenient during early
   development. Are we OK to break it and ship the parser inside the
   vault tree?
2. **Markdown editor UX.** Long term, do we want a single "Edit mode"
   that swaps between rendered preview and source, or is the current
   "Edit hides preview, shows textarea" the intended end state?
3. **Where to host the new `_common/lib/`?** I've assumed under each
   IFD app's tree. If there's an existing convention for cross-app
   shared code, tell me — I haven't seen one.
