## Executive Assessment

Day 66's fourteen documents are the most architecturally consequential batch since the vault-collections + vaults-of-vaults brief on 14 May. Three structural patterns crystallised that had been implicit for several weeks:

1. **The vault-as-communication-medium pattern** — agents communicate through shared vaults, not direct calls. Surfaced independently in the multi-cloud brief (SG/Compute ↔ SG/Deploy), the backup brief (backup-as-mini-app reading operational vault), and the DNS registry brief (admin vault as registry of truth). Three briefs converging on the same answer is not coincidence; it is architecture.

2. **The serverless framing for agents** — SG/Compute Serverless is not a Lambda alternative; it is a serverless environment specifically for agent workloads. The parallel-request observation sharpens the positioning: Lambda cold-starts each concurrent slot; containers serve N parallel requests with one cold-start. This is a real and important difference for agentic workloads that make many parallel tool calls.

3. **The JS API as both production surface and test surface** — the vault testing framework's core insight is that the same JS API used by normal vault operations is the right surface for all four test layers. This is an excellent design decision. It means there is one API to learn, one API to maintain, and tests that exercise real code paths.

## Architectural Soundness Assessment

### A. Vault Discovery + Public Keys (doc 422) — STRONG

**Assessment:** Architecturally sound. The `/.well-known/vaults` endpoint follows established patterns (RFC 8615 Well-Known URIs). The Ed25519/X25519 key pair per vault is the standard approach (same as Signal, WireGuard, and most modern cryptographic systems). The four-tier visibility model (public/unlisted/private/count-only) is pragmatic and correctly mirrors established UX (YouTube's video visibility). The "send content to a vault" via public-key encryption is the architectural equivalent of email — encrypted to recipient's public key, only they can decrypt. The offline-bundle story is a natural consequence and correctly uses Docker image as the portable format.

**Concerns:**
- Key rotation design is flagged as an open question and needs explicit design before implementation. The brief notes this correctly. Key rotation without a plan creates a permanent technical debt.
- The "public key as vault identifier" question is correctly deferred. Human-readable IDs + public key as auxiliary is the right v1 answer.
- The CNAME-to-wildcard correction in doc 429 is architecturally important and correctly identifies that A records are more portable across DNS implementations.

**Risks:** LOW. This is foundational work with a clear design. Implementation is mostly new code, not refactoring.

### B. Vault Testing Framework (doc 418) — STRONG

**Assessment:** The four-layer model (unit/integration/QA/browser-automation) is correct. The critical architectural decision — using the vault's JS API as the test surface — is exactly right. This avoids the "two parallel surfaces" problem that plagues most testing frameworks. The single test file format with `layer` option for routing is clean. Vitest + Playwright is a sensible tool choice (both modern, ESM-native, well-maintained).

**Concerns:**
- The test fixture question (where do they live?) needs a decision. "In the vault for portability" is the right answer but needs explicit design.
- QA test layer with state mutations raises the question of test isolation: how do you guarantee tests don't leave the vault in a bad state? The brief mentions "session-scoped mutations" for QA tests — needs to be explicit that each QA test gets a fresh session scope.
- The "fifth layer" (LLM qualitative review from doc 420) is the most interesting but also the most novel. Starting with the four structural layers and layering LLM validation on top is the right sequencing.

**Risks:** LOW-MEDIUM. The framework architecture is clear; the implementation risk is in the test fixture and QA isolation details.

### C. Serverless for Agents (doc 424) — STRONG

**Assessment:** The synthesis is accurate. The table comparing Lambda properties to SG/Compute Serverless is the clearest comparison I have seen. The parallel-request argument is the sharpest technical point: Lambda's per-concurrent-instance provisioning model is fundamentally expensive for agentic workloads. This is not a marketing claim; it is a structural observation about how Lambda handles concurrency versus how containers handle it.

**Concerns:**
- The request path in the brief (12 steps from user request to response) is correct but does not address what happens when the edge router and the orchestrator are separated across network boundaries. This needs an explicit design for how the edge router communicates with the orchestrator when the orchestrator is itself ephemeral.
- Cold-start budgets need to be measured, not estimated. The brief correctly calls for this as an acceptance criterion.
- "Serverless" is a positioning decision as much as an architectural one. The brief is honest about the marketing vs. technical distinction.

**Risks:** MEDIUM. The architecture is sound but the integration of the twelve pieces has non-trivial operational complexity. Start with one piece (container-on-existing-host path) and extend.

### D. Multi-Cloud + Agent Communication (doc 425) — STRONG with CAVEATS

**Assessment:** The SG/Deploy separation is architecturally correct. Absorbing GCP and Akamai primitives into SG/Compute would create a coherence problem — the mental model of what SG/Compute does would diffuse. The split is the right call.

The vault-as-communication-medium pattern for agent-to-agent handoffs is architecturally elegant. No direct calls, no shared DB, full audit trail, eventual-consistency by design. It correctly identifies the asynchronous nature of most agent-to-agent communication (the agents don't need synchronous response; they need correct and auditable).

**Concerns:**
- Synchronous request-response between agents over a vault is awkward. The brief acknowledges this and recommends async-first use cases. This is the right guidance. However, teams will encounter synchronous needs; a fallback pattern (direct CLI invocation with vault logging) should be documented before it is needed.
- The vault-as-communication-medium pattern is elegant for two agents. It needs explicit design for three-or-more-agent workflows (fan-out, fan-in, parallel branches). This is a v2 concern but worth flagging.
- SG/Deploy will need its own credential management, observability, and CI. The cost of the split is ongoing maintenance of two repos. Worth the trade-off, but not free.

**Risks:** MEDIUM. The architectural direction is sound. The implementation risk is in the vault-as-communication-medium pattern reaching production-grade reliability (versioning, conflict resolution if two agents write simultaneously, etc.).

### E. DNS Registry via A Records (doc 429) — IMPORTANT CORRECTION VALIDATED

**Assessment:** The CNAME-to-wildcard correction is important and correctly reasoned. RFC 4592 is unambiguous: a wildcard does not match a name if any record exists at that name, and CNAME-to-wildcard behavior is implementation-specific across resolvers. The A-record approach is the correct fix. The admin vault as registry of truth (DNS as projection) is the right architecture — DNS should be derived state, not source of truth. The TXT records as optional metadata (DKIM pattern for public key distribution) is correct and does not affect the primary routing concern.

**Concerns:**
- The DNS sync process (admin vault → Route 53) introduces a consistency window. If the sync is delayed, the admin vault says "lab X is registered" but DNS does not yet have the A record. The brief correctly identifies this and recommends hourly reconciliation. This is adequate but should be operationalised before going to production.
- Per the brief's own risk analysis: "Route 53 provider quirks break the scheme." This is real. The acceptance criterion should include testing against actual Route 53 behavior, not just against a local mock.

**Risks:** LOW. Mostly operational configuration; well-understood DNS mechanics.

### F. Backup and Restore (doc 427) — STRONG

**Assessment:** The "backups never restored are not backups" framing is operationally correct. The four drill cadences (daily/weekly/monthly/quarterly) are industry-standard. The separate AWS account for backup (write-only IAM from production account) is the right architecture for 2026 — this is the canonical defense against ransomware that hits the production account. The seven-tier storage strategy is more elaborate than needed for v1 but correctly scopes: demo vaults need fewer tiers than the email vault.

**Concerns:**
- The backup mini-app itself needs to be backed up. The brief acknowledges this recursion and correctly handles it: the backup-operations vault has the same Tier 1 backup applied, and the chain terminates at "multi-provider as ground truth."
- The GDPR right-to-erasure concern across backup tiers is flagged as an open question and needs explicit design. Deleting a customer's data when backup tiers are involved is non-trivial. This is a P1 design concern before the system goes to production with customer data.
- The agentic-first design (Claude Code sessions running scheduled health checks against the backup vault JS API) is novel and appropriate. It validates the platform's own capabilities in a high-stakes operational context.

**Risks:** MEDIUM. The architecture is sound; the operational risk is in the restore drill automation and the GDPR deletion workflows.

## Cross-Document Architectural Coherence

The 14 documents are unusually coherent. Several observations:

1. **The vault-as-mini-app pattern runs through almost every document.** Backup mini-app, email mini-app, AppSec mini-tools, demo server, admin interface — all follow the same pattern: a vault holds the operational state; a UI built on the JS API exposes it; the compute is ephemeral. This is not repetition; it is convergent evidence that the pattern is right.

2. **The JS API surface is becoming load-bearing.** It is the production interface, the test surface, the CI interface, the agentic interface, and the demo interface. Before the JS API surface proliferates further, it needs a formal specification document. The testing framework brief (doc 418) is the right moment to produce this.

3. **Two briefs sharply contradict naive assumptions:**
   - CNAME-to-wildcard doesn't work (doc 429) — this would have been a production bug
   - SG Mail is not email infrastructure (doc 426) — this scopes the project correctly

4. **The agent communication pattern (doc 425) resolves a long-standing implicit concern.** Previous briefs had agents calling each other's CLIs as subprocesses, importing code, or using ad-hoc mechanisms. The vault-as-communication-medium pattern is the first explicit, principled answer. It should be canonised in the architecture documentation.

1. **JS API surface specification** — write the formal spec before more consumers are added. Foundation for everything.
2. **Vault testing framework** — foundational; unlocks CI, quality gates, and the LLM review layer.
3. **Vault demo capabilities** (session-scoped changes + read-only polish) — unblocks demo push; short work.
4. **Vault discovery + public keys** — foundational primitive that many other features depend on (AppSec, "send to vault", multi-cloud).
5. **DNS pinning fix + address router** — already-working provisioning flow with one remaining production bug.
6. **CI pipeline** — turns testing from capability to guarantee.
7. **Backup and restore infrastructure** — operational critical path now that email vault is coming.
8. **SG Mail v1** (SES connector + email web app) — first production "always-on" workload.
9. **SG/Deploy + multi-cloud** — week-long experiment; parallelisable with above.
