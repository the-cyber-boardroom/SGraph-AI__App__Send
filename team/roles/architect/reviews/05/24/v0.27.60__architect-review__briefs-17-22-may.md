## Part 1: The TUI API (Day 67)

### What Was Decided

The TUI API is named and specified as a first-class architectural layer. The development sequence (capability → CLI → TUI → Web API → Web UI) is the project's canonical build progression. The TUI API sits between the CLI and the Web API as the composable, LLM-consumable operator surface.

### Architectural Assessment

**SOUND.** The TUI API design is architecturally coherent and consistent with the vault-of-vaults fractal pattern. Key observations:

| Decision | Assessment |
|----------|------------|
| TUI API as a layer parallel to JS API | Correct. The JS API made vault apps composable; the TUI API makes tools composable. The analogy holds. |
| Seven API surfaces | Well-scoped. Status, list, get, invoke, subscribe, stream, reflect cover the standard operational needs. |
| TUI-of-TUIs fractal | Follows naturally from the established platform pattern. No concerns. |
| LLM-consumable output format | Correct direction. The TUI API must produce structured output, not human-formatted text, to be useful to agents. |
| Memfs virtual filesystem | Architecturally clean. Rich context without polluting the window. Skills.md/changelog loaded on demand is the right model. |
| Granular IAM vs MCP all-or-nothing | Significant advantage. Per-action IAM scoping is the correct security posture for agentic tool consumption. |

**Integration concerns:**

1. **TUI API ↔ SG/Sentinel TUI** — Day 68 immediately applied the TUI API to SG/Sentinel's nine operator surfaces. This confirms the TUI API is not theoretical; it has a real immediate consumer. The SG/Sentinel TUI mockups (P-217) should be the first TUI API implementation.

2. **TUI API discovery** — How does an LLM or TUI-of-TUIs discover available TUI APIs? The orientation endpoint (P-203) addresses this partially but needs a concrete protocol spec.

3. **Change-control surface** — The first-class change-control surface is the right design for distributed team operations. Needs to define the canonical audit log format.

## Part 2: SG/Sentinel — Architectural Evaluation

### Design Coherence

The nineteen SG/Sentinel documents form a coherent, well-sequenced design corpus. The intellectual arc (principles → model → rules → lifecycle → standards → compliance → architecture → validation → consolidation) is the correct sequence for a security product. The tabletop simulation discipline — simulating the engine before building it — is architecturally sound practice and found real problems.

### Architectural Strengths

**1. App-coupled WAF is the right model given our constraint set.**
We control both the client and the server. The no-invalid-request principle (server never receives a structurally invalid request) is achievable because we control what valid looks like. Generic WAFs cannot do this; they operate blind. This is a genuine architectural advantage.

**2. Rules-as-vault is architecturally natural.**
Version-controlled, deploy-artefact, fractal (rules within rule-sets within packs) — this follows the project's core storage model. Rule retirement (the Sigma/DaC lesson) is a first-class operation, not an afterthought. No concerns.

**3. Python same-code-everywhere is a killer feature.**
Development environment = local Sentinel = live Sentinel. Deploy parity as a correctness requirement (not a nice-to-have) is the right stance. This eliminates a major class of bugs (it works locally but not in production) without needing elaborate mocking infrastructure.

**4. The three-layer model is correctly altitude-separated.**
Layer 1 (CloudFront Functions, sub-ms, no I/O) → Layer 2 (Lambda@Edge, capable) → Layer 3 (async, off-hot-path) maps perfectly to the horses-for-courses principle. LLM interpretation belongs exclusively in Layer 3 (never inline in Layer 1/2). This is correctly specified.

**5. Sentinel's logging job ends at S3.**
The boundary is clean. Sentinel captures and delivers; existing code consumes from S3. This avoids scope creep and reuses what exists. Architecturally ideal.

### Architectural Concerns

**Concern 1: The app-must-report-auth-outcomes coupling (High Priority)**

The tabletop simulation 2 surfaced this correctly: brute-force detection requires Sentinel to know when the application rejects authentication. Without this feedback, Sentinel cannot distinguish "100 bad passwords" from "100 different users logging in normally."

This creates a **new architectural coupling**: the application layer must call Sentinel's API after auth decisions. This is:
- A new runtime dependency (application → Sentinel)
- A latency addition (auth path now includes a Sentinel call)
- A failure mode question (what happens when Sentinel is unreachable on the auth call?)

**Required design work:** Define the auth-outcomes API surface before MVP coding. Recommended: a fire-and-forget async POST (don't block the auth response waiting for Sentinel acknowledgement; accept eventual consistency in the evidence graph).

**Concern 2: Fast-track reconception (High Priority, needs memo first)**

Fast-track as zero-trust acceleration (skip expensive identity establishment, never skip authorisation) is the right reconception. The honeytoken resolution (a fast-tracked user touching a honeytoken triggers immediate trust revocation) is elegant and proven.

However, the implementation of "skip expensive identity establishment" needs the project lead's own framing before the MVP commits to it. The signed-token mechanism is the right direction (tabletop resolution #106), but the exact token lifecycle (issue, validate, revoke, expiry, rotation) needs the fast-track redesign memo.

**Concern 3: Per-IP detection defeated by residential proxies (Medium Priority)**

The finding is correct: residential proxy pools mean IP-based reputation is context (not verdict). The multi-dimensional keying solution (source IP, target endpoint, behaviour pattern, timing) is the right direction. However, multi-dimensional keying is harder to implement correctly than per-IP keying.

**Recommendation:** Start the MVP with per-IP keying (easy to build, still catches a lot), then extend to multi-dimensional keying in the post-MVP phase. Don't block the MVP on solving the residential proxy problem.

**Concern 4: Layer 1 in JavaScript (Low-Medium Priority)**

CloudFront Functions constraint requires JavaScript at Layer 1. The rest of the stack is Python. This creates a dual-language maintenance burden for the rule engine. The Sigma-style compile-to-backend approach (write rules in a canonical format, compile to JS for Layer 1) is the correct long-term direction but is explicitly post-MVP.

**For the MVP:** Accept the dual-language reality. Write the easy-win Layer 1 rules in JS directly. Keep them simple (banned IPs, obvious paths). The complexity belongs in Layer 2 (Python).

**Concern 5: S3 log volume and cost (Low Priority for MVP)**

High log volume to S3 has rate and cost implications. The brief notes this as a risk. The design is leaner than Firehose by design (batch + compress). This is acceptable for the MVP; measure and tune. Not a blocker.

### The Three-Graphs-as-One Proposal

The addendum proposes that the evidence graph, compliance graph, rule graph, and attack tree are one typed semantic graph. This is architecturally appealing — a unified query model over security state. However:

1. The unified graph is explicitly parked (post-MVP per the path-to-MVP brief). Correct decision.
2. The MVP should **assume** the unified model (don't build storage schemas that would make unification hard later) without **building** it now. Design data models with the unified graph in mind.

**Recommendation:** Before MVP coding, define the entity types and relationships in the unified graph (a one-page data model sketch). This costs a day and prevents architectural regret.

## Part 3: Cross-Cutting Architectural Observations

### The Platform Fractal Extends Consistently

Day 67 (TUI API) and Day 68 (SG/Sentinel) both extend the platform's core patterns:
- **Vault-of-vaults** → **TUI-of-TUIs** (TUI API) → **rules-as-vault** (SG/Sentinel)
- **JS API** for apps → **TUI API** for tools → **rule-set-as-vault** for security policies
- **Evidence graph** (agent ai domain) → **evidence graph per-user/IP** (SG/Sentinel domain)

The consistency is a significant architectural strength. New engineers (and new agents) need to learn one pattern; they get the rest for free.

### SG/Sentinel as Platform Validation

SG/Sentinel uses the platform to build security infrastructure, not bespoke security infrastructure. Rules-as-vault means the rule management lifecycle (version, deploy, rollback, audit) is solved without building a custom system. This is the platform paying for itself. Document this explicitly in the SG/Sentinel brief series (it's implied but not stated).

### SG/Sentinel TUI as First TUI API Implementation

The SG/Sentinel TUI mockups (9 surfaces, all TUI-API-friendly) are the natural first implementation of the TUI API. Implementing them first:
1. Proves the TUI API works
2. Delivers immediate operational value (the real-time visibility the project lead wants now)
3. Is the forcing function for the TUI API protocol design

**Recommendation:** Sequence the TUI API implementation to land with (or slightly before) the SG/Sentinel TUI implementation.
