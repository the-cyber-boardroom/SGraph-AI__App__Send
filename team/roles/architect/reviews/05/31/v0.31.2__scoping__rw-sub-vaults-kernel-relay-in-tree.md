# Architecture + Dev Scoping — Read-Write Sub-Vaults in `/vault` (rw kernel mount in the tree)

**Status:** PROPOSED — does not exist yet. This document scopes the work; no rw sub-vault write path ships today.
**Role:** Architect + Dev (Explorer)
**Date:** 2026-05-31
**Anchored to:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/` (bundle current as of the v0.31.2 session)
**Origin requirement:** *"Kernel A's App writes to a file in Kernel B, where Kernel A has rw access to Kernel B, with both vaults visible in the main tree view."*

---

## 1. One-paragraph problem statement

The kernel-relay path **already writes end-to-end into a child vault** (Kernel A → broker →
SecureChannel → Kernel B → child's own server storage). But that path is wired **only on the
`/app` page** and is **not** what the main tree view (`/vault`) uses. The `/vault` tree mounts
sub-vaults through a **separate, read-only** adapter (`CompositeDataSource`) that hard-codes
`access:'ro'`, stores **only the child's read key**, and routes every write to the **root**
vault. So the capability exists; the tree view can't reach it. This is an **integration +
credential-storage** task, **not** a net-new write implementation.

---

## 2. The two mechanisms today (why they don't meet)

| | **Kernel relay (rw — exists)** | **Read-through composite (ro — what the tree uses)** |
|---|---|---|
| Orchestrator | `KernelParent` (`app-shell/kernel-parent.js`) | `CompositeDataSource` (`adapters/composite-data-source.js`) |
| Instantiated on | `/app` only — `app-shell.js:749 _ensureKernelParent()` | `/vault` only — `vault-shell.js:396 new CompositeDataSource(...)` |
| Child opened with | **full writable key** via `secrets` msg (`app-shell.js:~853`) | **read key only** (`_openMount` → `_vaultOpenerRO`, `composite-data-source.js:194-207`) |
| Write into child | ✅ `kernel-app-handlers.js:108-118` → `ds.saveFile` → `_safePush(vault)` (Edge 1) | ❌ `saveFile()` pass-through to root (`composite-data-source.js:225-231`) |
| Access mode | per-mount, gated by child policy + broker | hard-coded `access:'ro'` (`composite-data-source.js:70`) |
| Visible in main tree | ❌ no tree surface (console/REPL only) | ✅ `🔗 ro · connected` node + chip |

**The gap, precisely:** the tree (composite) has the **UI surface** but no rw; the relay has
**rw** but no tree surface. The requirement needs **both**: rw *and* in-tree.

## 4. Target architecture

**Decision: do NOT port `KernelParent` into `/vault`. Make `CompositeDataSource` a relay
*client* for writes under a mount.** Rationale: the relay (broker, custody gate, child policy,
push-on-write, audit log) is the security-critical part and is already tested. Re-homing it
risks divergence and a second copy of the B10 custody gate. Cheaper and safer to let the
composite adapter *delegate* mount-scoped writes to a relay instance.

```
/vault page (vault-shell)
        │ builds
        ▼
  CompositeDataSource(root, { keyProvider, relay })      ← NEW: optional relay dependency
        │  read  under mount → m.child.getFileBytes (unchanged, in-process ro)   [keep fast path]
        │  write under mount → relay.relay('write', {path, data, credential})    ← NEW delegation
        ▼
  KernelParent (relay)  ── reused as-is ──►  SecureChannel ──► Kernel B
        │                                                         │ vfs.write
        │ custody gate (B10), broker policy, audit                ▼
        │                                              ds.saveFile + _safePush (child server, Edge 1)
```

**Two viable wiring options — pick one (A recommended):**

- **(A) Composite delegates writes to a relay it is handed.** `vault-shell` constructs a
  `KernelParent` (headless — no `/app` UI) and passes it into `CompositeDataSource`. Writes
  whose path falls under an **rw** mount go `relay.relay('write', …)`; everything else stays
  root-pass-through. Reads stay in-process (fast) for ro mounts; rw mounts may also read via
  relay for consistency. **Smallest blast radius, reuses the security engine.**
- **(B) Unify pages on `app-shell`.** Make `/vault` use the same shell that already owns the
  relay. Larger refactor (page lifecycle, two custom elements), more regression surface.
  Better long-term, out of scope for a first rw cut.

## 5. Work breakdown (Option A)

### M1 — `rw-links.json` credential store (fulfil the existing stub)
- Implement the deferred owner record `.vault/owner/rw-links.json`: owner-only,
  **double-encrypted full key** (mirror the `ro-links.json` shape in `vault-links.js`, add
  the write half). Add `VaultLinks.getStoredRwKey(vault_id)` / writer.
- **Add-link flow** (`vault-browse-edit.js:937-1023`): when the pasted key is a **full**
  (writable) key, offer an explicit **"mount read-write"** choice. On rw: write `rw-links.json`
  (full key) **instead of / in addition to** `ro-links.json`. Today the full key's write half
  is silently discarded — M1 stops that.
- **Security:** rw-links holds a writable key → it is a **secret at rest** in the vault.
  Must be encrypted to the owner only, never to share tokens. CLAUDE.md §14/§33 apply.
  Cross-check with AppSec before merge.

### M2 — Mount registration learns `access:'rw'`
- `composite-data-source.js:51-88 scan()` + `_openMount` (194-219): when an `rw-links` record
  (or rw-tagged `.link.json`) exists for a mount, set `access:'rw'` and resolve the **full**
  key (not `_vaultOpenerRO`). Keep `'ro'` as default.
- The link descriptor likely needs an explicit `access` field in `.link.json`
  (`vault-browse-edit.js:1008`) so intent survives reload independent of which owner record exists.

### M3 — Composite write delegation (the core change)
- Replace the blanket pass-throughs (`composite-data-source.js:225-231`) with mount-aware logic:
  for `saveFile/renameFile/deleteFile/createFolder/deleteFolder/renameFolder/moveFile/moveFolder`,
  if `_mountForPath(path)` resolves to an **rw** mount → delegate to `relay.relay(op, {path:rel, data, credential})`;
  else → existing root pass-through.
- `moveFile`/`moveFolder` across the mount boundary (root↔child) need explicit handling
  (read-from-source + write-to-dest + delete-source) — **flag as a sub-case**, can be a
  follow-up; first cut may reject cross-boundary moves with a clear error.
- `get writable()` (`composite-data-source.js:45`) currently reflects root only — extend so a
  path under an rw mount reports writable.

### M4 — `vault-shell` builds & injects the relay
- `vault-shell.js:396`: construct a headless `KernelParent` (reuse `app-shell`'s
  `_ensureKernelParent` factory logic — extract to a shared helper to avoid a second copy) and
  pass it as `{ relay }` to `CompositeDataSource`. Mount happens on first rw access (lazy), same
  as ro `_openMount`.
- Ensure the ViV modules (`secure-channel`, `kernel-mounts`, `kernel-broker`, `kernel-parent`,
  `viv-custody`) are loaded on the `/vault` page (`index.html` bundle) — today they're an
  `/app` concern (`app-shell.js:757` throws `EUNREACH` if missing).

### M5 — Custody gate on the `/vault` path
- The B10 gate (`app-shell.js:757-769`) refuses parent-held creds + same-origin App-A. The
  `/vault` tree's "app" context differs from `/app`'s App-A iframe. **Decide the custody story
  for tree-initiated writes** (the tree UI itself is first-party; there may be no untrusted
  App-A). Likely: tree-initiated rw writes are *operator* actions, not app-iframe actions, so
  the same-origin-App-A concern may not apply — **but this must be explicitly classified**, not
  assumed. AppSec sign-off required.

### M6 — Tree chip + UX honesty
- Wire `access:'rw'` through to the chip — the label layer already maps it
  (`vault-subvaults-view.js:36`). Show `● rw · connected` (green) vs `● ro · connected`.
- **Fix the silent-downgrade trap** (separate, shippable now even without rw): at add-time, if a
  full key is mounted ro, tell the user it's read-only. With M1-M6, give the explicit rw choice.
- Edit controls (`vault-browse-edit`) must enable save/rename/delete for files under an rw mount
  (today disabled under any sub-vault path).

### M7 — Tests (no mocks; in-memory stack)
- Unit: composite delegates write to a stub relay for rw mounts, root for ro/unmounted.
- Unit: `rw-links.json` round-trip (write full key → reopen → resolve writable child).
- Integration (in-memory two-vault): write under rw mount lands in **child** storage, not root;
  ro mount write still refused/root-routed.
- Adversarial (reuse relay's existing coverage): child policy still gates (`EPERM`), floor
  still applies (`EPROTECTED`), push failure surfaces (`EUNREACH`), custody decision recorded.
- E2E (Playwright, follow-up): add rw sub-vault in tree → edit a child file → save → reload →
  change persisted in child vault.

## 6. Sequencing & sizing

1. **M6 honesty fix** (silent-downgrade warning) — shippable immediately, no rw needed.
2. **M1 + M2** (rw-links + access:'rw' resolution) — credential foundation.
3. **M3 + M4** (delegation + relay injection) — the core integration.
4. **M5** (custody classification) — gate decision, **AppSec sign-off blocks merge**.
5. **M7** tests throughout; E2E last.

**Size:** focused Explorer task across ~6 files (`composite-data-source.js`, `vault-shell.js`,
`vault-browse-edit.js`, `vault-links.js`, `vault-subvaults-view.js`, `index.html` bundle) +
tests. **Not** a research spike — the rw engine exists. Largest unknowns are **M5 (custody
semantics for tree-initiated writes)** and **cross-boundary moves (M3)**.

## 7. Risks / decisions to confirm before coding

- **D1 (security, blocking):** storing a **writable** key in `rw-links.json` at rest inside the
  vault. Owner-only double-encryption is mandatory; confirm threat model with AppSec/CISO.
  This is the single biggest reason rw was deferred originally.
- **D2:** custody model for tree-initiated rw (M5) — is the tree a trusted operator surface
  exempt from the App-A same-origin concern, or does it need its own gate?
- **D3:** read consistency for rw mounts — keep fast in-process ro reads, or route reads through
  the relay too (simpler mental model, slower)? Recommend: reads stay in-process; only writes
  relay.
- **D4:** real-data vs synthetic. Per the prior session, **real-data relayed writes remain
  gated**; this scoping does not lift that. rw sub-vaults ship behind the same gate until the
  credential-issuance decision is made.
- **D5:** Explorer vs Villager — this **adds functionality**, so it's **Explorer** work
  (Villagers don't add features, CLAUDE.md §1).

---

## 8. Bottom line for the requirement

*"Kernel A's App writes to a file in Kernel B (A has rw to B), both visible in the tree"* is
**~80% built**: the relay does the A→B rw write today, tested. The remaining 20% is (1) storing
A's **full** key for B (`rw-links.json` — the deferred stub), (2) letting the **tree's**
composite adapter **delegate** mount-scoped writes to that relay instead of the root, and (3) a
custody/AppSec decision on storing a writable key at rest. No new write machinery required.
