# Architecture + Dev Scoping — Unify Vault Access on One Kernel Path (rw sub-vaults in the tree)

**Status:** PROPOSED — does not exist yet. This document scopes the work; no rw sub-vault write path ships today.
**Role:** Architect + Dev (Explorer)
**Date:** 2026-05-31
**Anchored to:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/` (bundle current as of the v0.31.2 session)
**Origin requirement:** *"Kernel A's App writes to a file in Kernel B, where Kernel A has rw access to Kernel B, with both vaults visible in the main tree view."*

---

## 1. Decision up front: one path, not two

We will **converge all in-vault-and-sub-vault access onto the kernel path** (`KernelParent` +
relay), and **retire the read-only composite adapter** (`CompositeDataSource`) as a parallel
mechanism. The tree view (`/vault`) and the app view (`/app`) become **one shell** over **one**
data/access path.

**Why this, not a bridge between two adapters:** the security-critical logic — broker policy,
the B10 custody gate, child-side floor enforcement, push-on-write (Edge 1), and the audit log —
lives **only** in the kernel path and is already built and tested. Every day a second,
independent read path (`CompositeDataSource`) exists is a day that logic can **drift, diverge,
or be silently bypassed**. Two code paths for "mount a vault inside a vault" is a maintenance
and security liability. The relay is still the younger of the two callers; collapsing onto it
**now** — before more callers accrete — is the cheapest this refactor will ever be, and it
future-proofs every later capability (rw, nested mounts, monitored mode, owner-secret tiers) on
a single substrate.

This replaces the earlier "make CompositeDataSource a relay client" sketch. We are not bridging
two paths — we are deleting one.

## 2. Where we are today (two mechanisms, one to keep)

| | **Kernel path (KEEP — becomes the only path)** | **Composite path (RETIRE)** |
|---|---|---|
| Orchestrator | `KernelParent` (`app-shell/kernel-parent.js`) | `CompositeDataSource` (`adapters/composite-data-source.js`) |
| Lives on | `/app` shell (`app-shell.js:749 _ensureKernelParent`) | `/vault` shell (`vault-shell.js:396`) |
| Child opened with | **full writable key** via `secrets` (`app-shell.js:~853`) | **read key only** (`_openMount`→`_vaultOpenerRO`, `composite-data-source.js:194-207`) |
| Write into child | ✅ `kernel-app-handlers.js:108-118` → `ds.saveFile` → `_safePush` (Edge 1) | ❌ pass-through to root (`composite-data-source.js:225-231`) |
| Access mode | per-mount, gated by child policy + broker | hard-coded `access:'ro'` (`composite-data-source.js:70`) |
| Security stack | broker, B10 custody gate, floor, audit log | none (in-process read splice only) |
| Tree surface | `app-shell` already builds `VaultDataSource` + tree (`app-shell.js:241-245`) | `🔗 ro · connected` node + chip |

**Key realisation that makes unification cheap:** the two shells are **not** as divergent as
they look. `app-shell` **already**:
- builds a full `VaultDataSource` and loads the entire tree (`app-shell.js:241-245`),
- references the **same** `vault-browse-edit` tree/editor component that `vault-shell` uses
  (both appear in §grep; `index.html:192` loads it once for both),
- consumes the **same** data-source contract the tree needs
  (`getFileBytes / getFileList / saveFile / scan / writable`),
- distinguishes full-key vs ro-token already (`app-shell.js:267-268` flips `writable=true` and
  sets `_accessKey` on a full key).

And `index.html` already routes between them: `#token → /en-gb/app` and **app-shell redirects to
`/en-gb/vault` when no `app.json` is found** (`index.html:19-20`). So "vault mode" is, in
effect, *"app-shell with no app to run, showing the tree."* That is the seam we formalise.

## 3. Target architecture — one shell, one access path

```
                         ┌─────────────────────────────────────────────┐
   #vaultKey  ─────────► │  app-shell  (THE shell — app view + tree view)│
                         │   • opens vault, builds tree (already does)   │
                         │   • runs app.json app IF present (app view)   │
                         │   • shows vault-browse-edit tree (tree view)  │
                         │   • owns KernelParent + relay + broker + B10  │
                         └───────────────┬─────────────────────────────-┘
                                         │ ALL file ops (root + every mount)
                                         ▼
                              VaultAccess (single facade)
                                 read  → relay.relay('read'/'list', …)   (or in-proc for root)
                                 write → relay.relay('write'/…  , …)     → child kernel → _safePush
                                         │
                                         ▼
                          KernelParent ── SecureChannel ──► Kernel B (child)
                            broker policy · B10 custody · floor · audit · Edge-1 push
```

- **`app-shell` is the single shell.** `/app` and `/vault` become two **render modes** of it
  (app-present vs tree-only), not two components with two data paths. `vault-shell`'s
  responsibilities (tree-only chrome, browse-edit hosting, settings) fold into `app-shell` (or
  `app-shell` composes the existing `vault-browse-edit`/settings sub-components directly).
- **`CompositeDataSource` is deleted.** Sub-vault mounting is done by `KernelParent` for **every**
  sub-vault — ro mounts open a read-only child kernel, rw mounts open a writable one. Reads and
  writes both flow through the relay's uniform op interface (`read`/`list`/`write`/…).
- **The root vault itself** can stay an in-process `VaultDataSource` for speed (it's "kernel
  self"), but it is exposed through the **same** `VaultAccess` facade so callers never branch on
  "is this the root or a mount." Mounts are kernel-relayed; root is local; one interface.
- **The tree** renders root + every mount uniformly; the `access` (`ro`/`rw`) per node comes from
  the mount's resolved credential tier, surfaced in the existing chip.

## 5. Work breakdown

### M1 — `VaultAccess` facade (the single interface)
- Introduce one access facade that all UI consumes (tree, browse-edit, REPL, settings):
  `getTree / getFileList / getFileBytes / saveFile / renameFile / deleteFile / createFolder /
  deleteFolder / renameFolder / moveFile / moveFolder / writable / scan`.
- For a path under a **mount** → delegate to `KernelParent.relay(op, …)`. For the **root** →
  local `VaultDataSource` (fast path) behind the same interface. Callers never branch.
- This facade is what replaces `CompositeDataSource`'s role; it is relay-backed, not
  root-pass-through.

### M2 — Promote `app-shell` to the single shell (tree mode)
- Add a **tree-only render mode** to `app-shell` for the no-`app.json` case (today handled by a
  redirect to `vault-shell`). Compose the existing `vault-browse-edit` + settings sub-components
  inside `app-shell` over the `VaultAccess` facade.
- Fold `vault-shell`'s unique chrome (tree layout, settings tab, sgit view) into `app-shell` or
  mount those same sub-components from it. Goal: `vault-shell` becomes a thin alias or is removed.
- Update `index.html` routing (`:19-20`, `:79`, `:474/513/616`) so `/vault` renders `app-shell`
  in tree mode rather than `vault-shell`. **Keep URLs stable** (`/en-gb/vault#…` still works).

### M3 — Every sub-vault mounts through `KernelParent`
- Replace `CompositeDataSource` mount logic: `_mountForPath` / `_openMount` semantics move to
  `KernelParent` mounts. Adding a sub-vault link → registers a kernel mount (ro or rw). Expanding
  it in the tree → spawns/opens the child kernel (lazy, as today).
- Reads of mount paths go through the relay (`read`/`list`); the in-process read-splice in
  `composite-data-source.js:172-189` is deleted. (Perf note in D3.)
- **Delete `composite-data-source.js`** and its `vault-shell` wiring once M1/M2 land.

### M4 — `rw-links.json` credential store (fulfil the deferred stub)
- Implement `.vault/owner/rw-links.json`: owner-only, **double-encrypted full key** (mirror
  `ro-links.json`, add the write half). `VaultLinks.getStoredRwKey(vault_id)` + writer.
- **Add-link flow** (`vault-browse-edit.js:937-1023`): a full (writable) key offers an explicit
  **"mount read-write"** choice → writes `rw-links.json`. Today the write half of a full key is
  silently discarded; M4 stops that and is the credential the relay's `secrets` message needs.

### M5 — Mount credential tier → relay
- Mount resolution picks the tier: rw-link → full key (writable child kernel); ro-link → read key
  (read-only child kernel). The resolved key is handed to the relay's existing `secrets` path
  (`app-shell.js:~853`) — no new transport, just a real credential source for `/vault`-initiated
  mounts.

### M6 — Custody / AppSec gate on tree-initiated writes
- The B10 gate (`app-shell.js:757-769`) classifies App-A iframe origin. Tree-initiated writes are
  **operator** actions in the first-party shell, not untrusted-app-iframe actions — likely a
  distinct (and simpler) custody class, but this **must be explicitly classified, not assumed**.
- Storing a **writable** key at rest in `rw-links.json` is the core security decision (see D1).
  **AppSec/CISO sign-off blocks merge.**

### M7 — Tree chip + UX honesty
- Surface per-node `ro`/`rw` via the existing label layer (`vault-subvaults-view.js:36`):
  `● rw · connected` vs `● ro · connected`.
- **Silent-downgrade honesty fix** — shippable immediately, even ahead of the full refactor: at
  add-time, if a full key is mounted ro, say so; with rw available, offer the explicit choice.
- Enable save/rename/delete on files under an rw mount (`vault-browse-edit` currently disables
  edit controls under any sub-vault path).

### M8 — Tests (no mocks; in-memory stack)
- Unit: `VaultAccess` routes root→local, mount→relay; rw vs ro mount picks the right child kernel.
- Unit: `rw-links.json` round-trip (write full key → reopen → writable child).
- Integration (in-memory two-vault): write under rw mount lands in **child** storage, not root;
  ro mount write refused at child (`EREADONLY`/`EPERM`).
- Adversarial (relay's existing coverage now exercised from the tree): child policy gates
  (`EPERM`), floor applies (`EPROTECTED`), push failure surfaces (`EUNREACH`), custody recorded.
- Regression: `/vault` tree-only mode renders + reads identically to today (the composite
  read-through behaviour must be reproduced by the relay read path — this is the main regression
  surface of retiring composite).
- E2E (Playwright): add rw sub-vault → edit child file → save → reload → persisted in child.

## 6. Sequencing & sizing

1. **M7 honesty fix** — ship now, independent of the refactor.
2. **M1 `VaultAccess` facade** — introduce behind the scenes; root-only first (no behaviour change), proves the interface.
3. **M2 app-shell tree mode** — render `/vault` via app-shell; `vault-shell` still available as fallback during transition.
4. **M3 mounts→KernelParent** + **delete CompositeDataSource** — the convergence step.
5. **M4 + M5** — rw-links credential + tier resolution.
6. **M6** — custody classification; **AppSec sign-off gates merge.**
7. **M8** throughout; E2E + the read-parity regression suite last.

**Size — honestly larger than the bridge approach, deliberately.** Touches the shell topology:
`app-shell.js`, `vault-shell.js` (folded/removed), `index.html` routing, `composite-data-source.js`
(deleted), `vault-browse-edit.js`, `vault-links.js`, `vault-subvaults-view.js`, plus the new
`VaultAccess` facade and tests. This is a **structural refactor**, not a feature patch — but it
collapses two access paths into one and is the right time to do it (relay is young, callers are
few). Biggest unknowns: **read-parity when retiring the in-process composite splice (M3/D3)** and
**custody semantics for tree writes (M6/D1)**.

## 7. Risks / decisions to confirm before coding

- **D1 (security, blocking):** storing a **writable** key at rest in `rw-links.json`. Owner-only
  double-encryption mandatory; confirm threat model with AppSec/CISO. This is the original reason
  rw was deferred — it does not get easier under unification, it just gets a single home.
- **D2 (topology):** folding `vault-shell` into `app-shell` changes the page model. Confirm no
  external deep-links depend on `vault-shell` being the `/vault` element (`index.html:474/513/616`
  query it directly — those call sites move).
- **D3 (perf):** retiring the in-process read splice means mount reads go through the relay
  (postMessage round-trip) instead of in-process. Confirm acceptable for tree browsing; mitigate
  by keeping **root** reads in-process and/or caching child trees. Explorer doesn't optimise, but
  must not regress basic browse responsiveness.
- **D4 (gate):** real-data relayed writes **remain gated** (prior session). Unification does not
  lift that; rw sub-vaults ship behind the same gate until credential-issuance is decided.
- **D5 (team):** adds functionality + restructures → **Explorer** work (CLAUDE.md §1). Villagers
  don't add features; this is not a Villager task.
- **D6 (migration):** existing `.link.json` + `ro-links.json` records must keep working through
  the relay path (read-only mounts unchanged for users who never opt into rw). No data migration
  for ro; rw is purely additive.

## 8. Bottom line for the requirement

*"Kernel A's App writes a file in Kernel B (A has rw to B), both visible in the tree"* is
**~80% built** — the relay already performs the A→B rw write end-to-end and is tested. The work
is **not** new write machinery; it is **collapsing the two vault-access paths into one**: promote
`app-shell` to the single shell, route every sub-vault mount (root + children, ro + rw) through
`KernelParent` behind a `VaultAccess` facade, **delete `CompositeDataSource`**, and fulfil the
deferred `rw-links.json` credential store. More code than a bridge, by design — it removes the
parallel path instead of entrenching it, so every future vault-access capability lands on **one**
secure substrate. AppSec sign-off on storing a writable key at rest (D1) is the gating decision.
