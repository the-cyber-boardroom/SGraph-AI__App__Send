## Executive Assessment

The 29 May briefs continue the vault's outward expansion. They are technically sound overall, with one significant correction (the OAuth/no-origin blind spot) and one strategically important cross-product linkage (the shared compliance graph with SG/Sentinel). The connector framework fits cleanly onto the existing VIV/bridge/PKI machinery. The assessment series builds on Vault Chat (P-263) and the visualisation cornerstone is the right precursor to all assessments.

**One critical architectural correction identified:** The original connector framework (doc 513) assumed the no-origin app iframe could perform OAuth handshakes. Doc 516 correctly identifies this as impossible (no-origin frames have no URL for the OAuth redirect). The data broker model is the correct fix and fits the VIV architecture naturally. **All connector implementation must use the data broker model, not the original "app-in-iframe-holds-credentials-and-makes-calls" model.**

### Data Broker Correction (doc 516): Critical

**ASSESSMENT: CORRECT — SUPERSEDES DOC 513 MODEL**

The data broker brief (doc 516) identifies and fixes a genuine architectural gap:

**The gap:** The Phase 3 VIV security gate (commit `f534b27`) made ALL app iframes null-origin (no `allow-same-origin`). A null-origin iframe has no URL. OAuth redirects target a URL. Therefore a null-origin iframe CANNOT receive an OAuth redirect. The original connector model was wrong.

**The fix (data broker):**
```
Auth flow:
1. Top-level kernel (has an origin) receives the OAuth redirect
2. Kernel relays the token PKI-encrypted to the broker's public key
3. Broker decrypts (only it can) and stores the token
4. Broker becomes the sole credentialed component; all API calls go through it
5. UI app renders + asks the broker for data; never touches credentials
```

This is correct VIV architecture:
- The broker is a sidecar with one responsibility (like the VIV broker for inter-vault requests)
- Credentials are PKI-encrypted in transit (like PKI-on-every-message)
- The kernel routes but cannot read the credentials (kernel is relay, not reader)
- The UI and credentials are isolated (separate iframes / separation of trust)

**Extension points noted in doc 516:**
- Broker as web worker: tighter isolation (no DOM), natural evolution
- Off-machine broker/proxy: needed for providers that block browser CORS (Notion); the broker model accommodates this cleanly because the broker is already the single isolated network caller

**One design question to resolve:** relay through top-level kernel, or connector at top-level? The relay (PKI-encrypted) is architecturally cleaner (connector stays null-origin, broker gets the token securely). The top-level connector is simpler but breaks the null-origin isolation for the connector UI. **Recommendation: relay model.**

### Connector Landscape (doc 515): Correct Research

**ASSESSMENT: ACCURATE — USE AS BUILD PRIORITY**

The two-viability-test framework (browser CORS + OAuth) is the right filter. The tier-1/2/harder ranking is accurate:

| Tier | Connectors | Architectural Note |
|------|-----------|-------------------|
| Tier 1 | Google Drive, GitHub, OneDrive | All CORS-friendly + OAuth; fit the model cleanly |
| Tier 2 | Dropbox (CORS pattern), S3 (signed, not OAuth) | Workable with documented technique |
| Harder | Notion (CORS blocked), Airtable (unreliable CORS) | Need off-machine proxy |
| Harder | General AWS | SigV4 + no CORS; not the OAuth model |

**Architecture flag for S3:** S3 uses signed requests, not OAuth. If S3 is prioritised, the broker model still applies (broker holds the signing credentials), but the auth flow differs from OAuth connectors. Design this explicitly, not as an afterthought.

The CRUD abstraction is the clean interface to bring back. ## Body Two: Evidence-Driven Assessment Series — Architectural Assessment

### Visualisation Cornerstone (doc 520): The Right Foundation

**ASSESSMENT: CORRECT — BUILD THIS BEFORE THE ASSESSMENTS**

The three primitives are architecturally clean:

| Primitive | Implementation Path | Risk |
|-----------|---------------------|------|
| Semantic knowledge graph | LLM extracts elements; pure graph engine renders (Mermaid or similar) | Low — Mermaid already in use |
| Visualisation-of-visualisations | Multi-altitude board; graph engine, not LLM | Medium — multi-altitude navigation is new |
| Pure infographics | Image models (evaluate by capability/cost) | Medium — image model cost/quality variability |

**The LLM-creates/engine-renders separation is important.** The LLM should not be drawing graphs; it should be identifying nodes and edges. The graph engine renders deterministically, cheaply, consistently. This is a pattern the codebase already follows (infographic tool uses LLM for content, SVG for rendering).

**Per-round budget control is architecturally non-negotiable.** An unbounded LLM loop is a cost hazard. The budget must be enforced at the infrastructure level, not left to the LLM's self-discipline.

**Version-controlled rounds on the vault:** each round is a vault commit. This is natural given the commit queue (P-265) and the vault's version control. Replay is cheap (just check out the commit).

### GDPR Assessment Vault (doc 519): Correct Architecture

**ASSESSMENT: SOUND — DEPENDS ON P-263 (VAULT CHAT)**

The self-contained vault structure (assessment + user data in one vault) is the right model. The propose-and-confirm workflow fits the vault chat architecture (P-263) well: the LLM reads the GDPR graph and the user's data, proposes hypotheses, the user confirms or corrects.

**The graph-based GDPR** is the load-bearing new work. It needs to be carefully sourced and structured. Recommendation: start with a subset of GDPR (e.g. lawful bases, data categories, controller/processor obligations) and expand. The structure should be a directed graph (GDPR articles → obligations → data categories → lawful bases).

**OpenRouter in the iframe** is consistent with the existing LLM integration pattern. The key/credits model works. Cost measurement needs to be built in from day one (not retrofitted).

**CRITICAL DEPENDENCY:** The GDPR assessment vault (P-274) and the CV workflow (P-276) both require Vault Chat (P-263), which requires VFS (P-264) and optionally Commit Queue (P-265). These are ordered dependencies. **Vault Chat must be implemented before either assessment can proceed beyond the initial research phase.**

### Evidence-Driven CV (docs 521–522): Correct Application

**ASSESSMENT: SOUND — COMPOSITES EXISTING INFRASTRUCTURE**

The CV workflow composites existing capabilities: research agents (external), vault chat (P-263), vault version control, sub-vaults and tokens, the evidence feedback loop (P-275). The new work is:
1. The CV-specific workflow (research → confirm → weight → anchor)
2. Evidence archiving (HTML/screenshot inlining into vault)
3. Consistency analysis (flagging evidence-graph inconsistencies)
4. Packaging as a versioned, importable vault app

Sub-vault feedback harvesting (read-only/read-write tokens) already exists (Phase 1–3 sub-vaults are shipped). The CV workflow can use this immediately.

**The vault-app packaging** is the most architecturally interesting part: the CV workflow as a versioned, importable vault app (like a Git submodule). This requires the Vault App Store (P-277) or at least the importable-vault-app primitive. The VIV kernel model and `vault.create` (Phase 4B, shipped) provide the substrate.

### Consulting Assessments (doc 524): Strategic Architecture

**ASSESSMENT: SOUND — IMPORTANT CROSS-PRODUCT CAPTURE**

**The cross-product capture is significant:** the customised graph-based standards (GDPR/ISO 27000 as graphs) are the same machinery as SG/Sentinel's compliance-as-a-living-graph. Building this once and sharing it across both products is correct. It should be a shared library, not duplicated.

**Three delivery models** (self-service / send-to-consultant / consultant-driven) map onto the vault's existing sharing model:
- Self-service: user runs the workflow in their own vault (private or ephemeral)
- Send-to-consultant: user shares the assessment vault with a consultant (read-only token or read-write)
- Consultant-driven: consultant runs the workflow in the client's vault (write-key or sub-vault access)

All three delivery models work on existing infrastructure. No new backend required.

**Companies House lookup** is a practical scoping mechanism. A read from the Companies House API (CORS-accessible) fits the connector model. This is a natural first connector after Google Drive and GitHub.

### Vault App Store (doc 523): Tractable

**ASSESSMENT: TRACTABLE — LEVERAGE ZIP MODEL**

The zip model is the right insight: distribution is distributing zips. The store needs:
1. A catalogue/discovery surface (a static vault or a dedicated page)
2. Security analysis before import (static analysis of app.json: what agents, what grants, what scopes)
3. Agent mapping (list the tools, skills, and capabilities the vault app uses)
4. Billing (most complex; start with free tier + OpenRouter credits bundle)
5. Import/version/load flow (built on `vault.create` + VIV vault-of-vaults)

**The security analysis layer is the most architecturally interesting.** Before importing a vault app, the system should parse its `app.json` (grants, scopes, agents) and present a trust summary. This is similar to Android's install-time permission screen. It uses the `AppPermissions` module (already shipped) to classify what the app requests.
