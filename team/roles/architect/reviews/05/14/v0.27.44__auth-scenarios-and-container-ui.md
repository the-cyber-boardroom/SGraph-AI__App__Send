**Version:** v0.27.44
**Date:** 2026-05-14
**Role:** Architect
**Status:** Investigation + design options — no code changes in this document

This document answers four questions raised about the EC2-deployed vault container:

1. Why does the EC2 container show the "old" vault entry UI? — **§1 below; the original answer was a misdiagnosis and has been corrected: there is no build-script bug, the container matches production exactly.**

## 1. The "old UI" — root cause

> **CORRECTION (2026-05-14):** The original version of this section claimed the
> build script was serving a "stale" file and listed fix options A/B/C. **That
> was a misdiagnosis.** After checking `deploy-ui-vault.yml`, the build script is
> doing *exactly* what production does. The corrected analysis follows.

**It is not an old container, and it is not a build-script bug.** The EC2 instance
runs a v0.2.3-based image (footer `local-dev . UI v0.2.3 (IFD)` confirms it).

### What's actually happening

The root `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/index.html` `<body>` is just:

```html
<body>
    <vault-shell></vault-shell>
    ...
```

`<vault-shell>` is the **real, current vault app component**. It renders:

- the **entry form** (two-column "Simple Token \| Full Vault Key") when *no vault is loaded*
- the **file browser** (FILES / SGIT / SETTINGS) when *a vault is loaded*

The earlier "old UI" screenshot and pic1 are **the same `<vault-shell>` component in two
states** — pre-vault entry vs vault-loaded. Production at
`dev.vault.sgraph.ai/en-gb/vault/` shows the identical two-column entry form before a
vault is opened. There is no "old design" being served.

### The build script is correct — it matches production exactly

`scripts/build-vault-static.sh` generates `/en-gb/vault/index.html` from the root
`index.html`:

```bash
mkdir -p "$SERVE_DIR/en-gb/vault"
sed -e 's|href="_common/|href="/_common/|g' \
    -e 's|src="_common/|src="/_common/|g' \
    "$SERVE_DIR/index.html" > "$SERVE_DIR/en-gb/vault/index.html"
```

Production's `.github/workflows/deploy-ui-vault.yml` does the **byte-identical** thing:

```bash
mkdir -p ${SOURCE_DIR}/en-gb/vault
sed -e 's|href="_common/|href="/_common/|g' \
    -e 's|src="_common/|src="/_common/|g' \
    "${SOURCE_DIR}/index.html" > "${SOURCE_DIR}/en-gb/vault/index.html"
```

There is **no `en-gb/vault/index.html` source file** (confirmed on `dev` too — `en-gb/vault/`
contains only the `markdown/`, `peek/`, `sgit/`, `token/` harness sub-dirs). Both production
and the container *generate* it from the root `index.html`. The container's
`/en-gb/vault/index.html` is therefore **identical to what `dev.vault.sgraph.ai` serves.**

### URL map (corrected)

| URL | Served from | What it is |
|---|---|---|
| `/` | `v0.2.3/index.html` (the vault shell) | `<vault-shell>` — app; routing script redirects |
| `/en-gb/` | `v0.2.3/en-gb/index.html` | Standalone **landing page** ("Open a vault." hero) — different by design |
| `/en-gb/vault/` | sed-patched copy of root `index.html` | `<vault-shell>` — the vault app, same as production |

`/en-gb/` (landing) and `/en-gb/vault/` (app shell) are **intentionally different pages**
with different jobs — not two competing versions of one page.

### The only real (trivial) issue

The root `index.html` `<title>` says `SG/Vault (v0.2.2)` — a **stale `<title>` tag** in the
vault UI source. It is purely cosmetic (the `<body>` renders the current `<vault-shell>`),
it affects production identically, and it is an Explorer-domain one-line fix in the vault
UI source — **not** a container or build-script concern.

If the team wants the `<vault-shell>` *entry-state* design refreshed to match the nicer
`/en-gb/` landing hero, that is a legitimate vault-UI design task — but it would change
production too, and it is unrelated to the container packaging.

**Recommendation:** Option A or C, as an Explorer task on the vault UI. The container build script needs no change — it's correct.

## 2. Auth credential taxonomy

Before the scenarios make sense, here are the **three distinct credentials** in play. They are routinely confused because two of them are called some variant of "key" / "token" in the UI.

| # | Credential | Header | Scope | Where it comes from | Who checks it |
|---|---|---|---|---|---|
| 1 | **FastAPI access token** | `x-sgraph-access-token` | The whole container/API | Operator sets `SGRAPH_SEND__ACCESS_TOKEN` env var; user supplies it via cookie or header | `Middleware__Check_API_Key` (osbot-fast-api) — gates *every* request |
| 2 | **Vault write key** | `x-sgraph-vault-write-key` | One specific vault | Derived **cryptographically** from the vault key / passphrase in the browser — never typed | `Service__Vault__Pointer` write/delete/batch handlers |
| 3 | **Vault read key** | `x-vault-read-key` | One specific vault (read-only) | Part of a read-only share token | Vault read handlers (public-vault flow) |

### The critical confusion

In `vault-entry`, the **"Access Key (optional for browsing)"** field is wired to **credential #1** — the FastAPI access token:

```js
// vault-entry.js
_getSGSend() {
    const token = this._accessKeyInput.value.trim() || this.getAttribute('data-token') || ''
    return new SGSend({ endpoint, token })
}
// sg-send.js
_authHeaders() {
    if (this.token) headers['x-sgraph-access-token'] = this.token   // ← FastAPI token
    return headers
}
```

But the field's **hint text says** *"Only needed for uploading files. Browse and download without it."* — which describes credential #2 (the vault write key) behaviour, **not** credential #1.

The vault write key (#2) is **never entered in this field**. It is derived from the vault key by `SGVault` and passed per-call:

```js
// sg-send.js
async vaultWrite(vaultId, fileId, writeKey, data) {
    headers: { 'x-sgraph-vault-write-key': writeKey }   // ← derived, not the Access Key field
}
```

**So the "Access Key" field is mislabelled.** It is the container access token, and its real behaviour is:

- Container has **no** API key set → the field is **ignored entirely** (server doesn't check `x-sgraph-access-token`).
- Container **has** an API key set → the field is required for **every** operation (browse, download, *and* upload) — not "optional for browsing".

The hint is wrong in both directions.

## 3. Auth scenarios (the matrix)

There are two independent on/off switches, giving four scenarios:

- **Switch A — FastAPI API key:** `SGRAPH_SEND__ACCESS_TOKEN` (or `SEND__ENABLE_AUTH`) set on the container.
- **Switch B — Vault write key:** every vault always has one (cryptographically derived). It is never "off" — but a *reader* may not possess it.

| Scenario | Container API key | User has vault write key | Can browse/download | Can upload/commit | Notes |
|---|---|---|---|---|---|
| **S1 — Open container, full vault key** | off | yes | ✅ | ✅ | Current happy path on `localhost`. No FastAPI token needed; write key derived from vault key. |
| **S2 — Open container, read-only** | off | no (read key only) | ✅ | ❌ | Recipient of a read-only share. |
| **S3 — Locked container, full vault key** | **on** | yes | ✅ *(needs FastAPI token)* | ✅ *(needs FastAPI token + write key)* | EC2 / shared deployments. **This is the scenario that's currently awkward.** |
| **S4 — Locked container, read-only** | **on** | no | ✅ *(needs FastAPI token)* | ❌ | Read-only share against a locked container. |

### How the FastAPI token is delivered today (S3 / S4)

When Switch A is on, `Middleware__Check_API_Key` rejects **every** request that lacks a valid `x-sgraph-access-token` (header **or** cookie), with **one set of exceptions** — `AUTH__EXCLUDED_PATHS`:

```
/auth/set-cookie-form
/auth/set-auth-cookie
/docs
/openapi.json
/config/status
```

So the only way a browser gets in:

1. User hits any vault URL → **401 JSON** `{"status":"error","error":"Client API key is missing…"}` — the static UI itself won't even load.
2. User must manually navigate to **`/auth/set-cookie-form`**, paste the token, submit → it's stored as a cookie.
3. Now every subsequent request carries the cookie → the UI loads, the SDK calls succeed.

**The problem:** nothing tells the user step 2 exists. They get a raw 401 JSON blob and a blank page. There is no redirect, no friendly prompt.

## 4. Detecting "API key required" and redirecting (answer to Q2)

There is currently **no signal** the UI can use to know auth is on. Options, cheapest first:

### Option A — Frontend catches 401, redirects (no backend change)

The vault UI's bootstrap script does a probe fetch (e.g. `GET /info/status`). On `401`, `window.location` → `/auth/set-cookie-form?return=<current-url>`.

- **Pros:** zero backend change; works against any deployment.
- **Cons:** every cold load eats one guaranteed-401 round trip; the `/auth/set-cookie-form` page would need a "return URL" feature it doesn't have today; relies on the UI shipping this logic (Explorer change to the vault UI).

### Option B — Middleware redirects browsers instead of 401 (backend change)

`Middleware__Check_API_Key` (or a thin wrapper in `Fast_API__SGraph__Send__Container`) inspects the request: if `Accept: text/html` and the key is missing, return **`302 → /auth/set-cookie-form`** instead of `401 JSON`. API clients (sgit, fetch with `Accept: application/json`) still get the 401.

- **Pros:** seamless — a browser hitting any locked URL lands straight on the cookie form; no frontend change; API clients unaffected.
- **Cons:** the middleware lives in osbot-fast-api (upstream) — would need either a subclass/wrapper in this repo or an upstream change. Content-negotiation logic in auth middleware is slightly unusual.

### Option C — Public `/info/auth` endpoint (backend change, small)

Add an **unauthenticated** endpoint (add it to `AUTH__EXCLUDED_PATHS`) that returns `{"auth_required": true|false, "cookie_name": "x-sgraph-access-token", "cookie_form_url": "/auth/set-cookie-form"}`. The UI fetches it on load; if `auth_required` and no valid cookie, it shows an inline "enter access token" panel (no full-page redirect).

- **Pros:** explicit, no guessing, no guaranteed-401; the UI can render a *nice inline* prompt rather than bouncing to the bare-bones cookie form; API clients can use it too.
- **Cons:** new endpoint + new exclusion path; UI work to render the panel.

**Recommendation:** **Option C** for the clean long-term answer, with **Option B** as a strong alternative if we want zero frontend work. Option B + C combined is the best UX (browser auto-lands on a form *and* the UI can introspect), but that's two changes.

## 5. Improving "create vault" when the API key is set (answer to Q3)

Today, in scenario **S3** (locked container, creating a new vault):

1. The user opens the vault UI — but it's 401-blocked until they've set the cookie (see §4).
2. Assuming they got past that, they click "Create New Vault".
3. `vault-entry._getSGSend()` builds `SGSend({ endpoint, token })` where `token` = the "Access Key" field.
4. If they left "Access Key" empty (because the hint said *"optional for browsing"*), the create call goes out **without** `x-sgraph-access-token` … but the cookie is set, so it *might* still work — **unless** they're on a fresh session or the cookie expired, in which case create fails with a confusing 401.

### The problems

1. **Mislabelled field.** "Access Key (optional for browsing)" is the FastAPI container token and is **mandatory** (not optional) in S3/S4. The hint actively misleads.
2. **Two sources of truth.** The token can come from the cookie (set via `/auth/set-cookie-form`) *or* the "Access Key" field. They can disagree. The create flow silently prefers the field, then falls back to cookie.
3. **No feedback loop.** If the container API key is set and the user hasn't supplied a token anywhere, the failure is a generic 401 from deep in the SDK — not "you need to enter the server access token".

### Design options

**Option 1 — Make the field honest and conditional.**
When the UI knows auth is required (via §4 Option C), the vault-entry form:
- Renames the field to **"Server Access Token"** with hint *"Required — your deployment is access-controlled."*
- Marks it **required** (blocks Create/Open until filled).
- When auth is *not* required, hides the field entirely (it's genuinely unused).

**Option 2 — Single token entry, persisted.**
Drop the per-form "Access Key" field. When auth is required, the UI shows a one-time "Unlock this server" step (inline panel or the `/auth/set-cookie-form` page) that stores the token as the cookie. From then on, *all* SDK calls rely on the cookie — `SGSend` stops carrying a `token` at all for same-origin deployments. One credential, one place.

**Option 3 — Pre-flight check in the create flow.**
Before `SGVault.create(...)`, the UI does a cheap authenticated probe (e.g. `GET /info/status` with whatever token it has). If it 401s, surface a clear **"This server requires an access token"** message with a link/inline form — *before* doing the expensive key-derivation + create.

**Recommendation:** **Option 2** is the cleanest model — it matches how the container actually works (same-origin, cookie-based) and removes the confusing field entirely. **Option 3** is a low-cost safety net worth adding regardless. **Option 1** is the minimum viable fix if we want to keep the current form shape.

All three are **Explorer-domain changes to the vault UI** (`sgraph_ai_app_send__ui__vault/`), plus — for the detection part — a small backend addition (§4 Option C) in `Routes__Info` or similar.

## Appendix — quick reference

**Container env switches:**

| Env var | Effect |
|---|---|
| `SGRAPH_SEND__ACCESS_TOKEN` | Sets the FastAPI access token. If set, auth is enabled. |
| `SEND__ENABLE_AUTH` | Forces auth on even without a token value (test use). |

**Excluded paths (reachable without the token):** `/auth/set-cookie-form`, `/auth/set-auth-cookie`, `/docs`, `/openapi.json`, `/config/status`.

**Credential → header map:**

| Credential | Header | Set by |
|---|---|---|
| FastAPI access token | `x-sgraph-access-token` | user (cookie / header) |
| Vault write key | `x-sgraph-vault-write-key` | derived from vault key in-browser |
| Vault read key | `x-vault-read-key` | read-only share token |
