## Summary Assessment

Two bodies of work arrived together and they are deeply interdependent. The SG/Sentinel batch-2 develops the control layer; the SG/Send thread shows how that control layer *is the business model*. Together they represent the first coherent product architecture for SG/Send as a commercial product with tiers, identity, budgets, and a security-enabled business model. The architecture is ambitious but grounded: it builds on what EXISTS (the vault system, MCP, the Lambda dual-function model, the PKI, the existing token model) and extends through a layered PROPOSED surface.

**The two most architecturally significant additions:**
1. **Control-flow graphs for business logic** (P-237) — solves the WAF Achilles heel
2. **SG/Sentinel as business-logic execution engine** (P-228) — moves authn/authz/metrics into rules

Both require careful design before implementation.

## Part 1: SG/Send Product Architecture

### 1.1 The Tiered Deployment Model (P-223)

**What is proposed:** Three deployment modes — free/non-private (max visibility), paid/non-tracking (privacy via SG/Sentinel rules), ephemeral per-customer EC2 (confidential data).

**Architectural assessment:**
- This is a **clean three-tier model** but requires that SG/Sentinel is deployed and operational before any tier can be activated. The free tier and paid tier both depend on SG/Sentinel rules for their characteristic properties. This creates a hard architectural dependency: **SG/Sentinel must ship before SG/Send's commercial tiers**.
- The free tier's "educational fingerprint display" (show users what we know about their IP) is a genuinely interesting UX capability. It requires the SG/Sentinel evidence graph (P-212, from batch-1) to be queryable from the frontend. This is a data-flow concern: how does the frontend receive the per-request fingerprint data? Via a signed response header? Via a dedicated endpoint? **This data-flow is not yet designed — flag for the Architect team.**
- The ephemeral per-customer EC2 tier aligns with the existing EC2 infrastructure direction (SG/Compute). The "specific (not general) S3 buckets" requirement needs to be validated against the current `Storage_FS__S3` abstractions — the abstraction is pluggable (MEMORY/DISK/S3 per `Enum__Storage__Mode`) so bucket-per-customer isolation should be achievable.

**Open architectural question:** How does a request know which tier applies? Is this determined at the SG/Sentinel layer (fingerprint → tier lookup → rule set applied) or at the application layer? This is the central routing question for the tiered model.

### 1.2 Identity, Ephemeral By Default, Budgets (P-224, P-225, P-226)

**What is proposed:** No anonymous users (fingerprint via SG/Sentinel identity-creation rule); public shares expire 2-3 days; per-account ~£1 budget.

**Architectural assessment:**
- **No anonymous users** is architecturally elegant: the identity is created *by SG/Sentinel*, before the request reaches the application. The application receives a request with a fingerprint identity already attached. This is clean separation. The identity-creation rule (P-233) is a new SG/Sentinel rule type — it must be designed into the rules engine (P-207, batch-1) as a first-class primitive.
- **Ephemeral-by-default** maps cleanly to the existing `Transfer__Service` expiry mechanisms (EXISTS — `delete_after` field exists per the 05/25 dev pack). Implementing 2-3 day default expiry requires an S3 lifecycle policy or a cleanup Lambda. The cleanup Lambda pattern is already PROPOSED (S3 lifecycle cleanup in `reality/infra/proposed/index.md`). **This is a feasible, incremental addition.**
- **Per-account budgets** require a budget store. Where does the budget live? Options: (a) in the user vault (vault-per-user, P-227), (b) in a SG/Sentinel state store, (c) in a dedicated Lambda table. Option (a) aligns with the vault-per-user thesis and avoids new storage primitives. However, vault reads add latency to every request. This is a **performance vs. architecture alignment trade-off** that needs profiling before commitment.

### 1.3 Vault-Per-User + Business-Logic Engine (P-227, P-228)

**What is proposed:** One vault per user as SG/Send's storage substrate; SG/Sentinel writes activity to user vaults; authn/authz/metrics as rules.

**Architectural assessment:**
- **Vault-per-user** is the right direction. It dogfoods the vault system, removes a separate "user database" primitive, and aligns with the zero-knowledge model (activity visible, file content not). The key architectural question: who *creates* the user vault? At what point in the user journey? On first fingerprint identity assignment (at SG/Sentinel)? On first transfer? On first payment? **The vault creation trigger and lifecycle need specification.**
- **SG/Sentinel as business-logic execution engine** (P-228) is the most architecturally consequential proposal in the thread. Moving authn/authz/metrics into SG/Sentinel rules means the application layer becomes a thin execution surface; SG/Sentinel handles all business-logic decisions. This is powerful but creates tight coupling between SG/Sentinel's runtime and the application's state. The app must communicate its state to SG/Sentinel (via headers per P-479 design, the "communication module"). **This is a design commitment that affects every endpoint.** Do not implement incrementally without a coherent interface contract.

### 1.4 OAuth + User-Dedicated Mode (P-230)

**What is proposed:** Client-side OAuth (Google, GitHub); vault key derived from OAuth secret or stored in Google appDataFolder; user-dedicated mode with personal LLM key.

**Architectural assessment:**
- This is an extension of the partially-PROPOSED OAuth work (Google OAuth + app:data vault key storage, `identity/proposed/index.md`). The new element is the "user-dedicated mode" concept — a named, coherent mode rather than just OAuth login.
- The **vault key derived from OAuth secret** approach has a security concern: if the OAuth provider revokes the token, the user loses vault access. The **Google appDataFolder** approach is cleaner (the vault key is stored, not derived), but it creates a dependency on Google's per-app storage — this storage is app-specific and isolated by design, which is exactly what we want.
- **Open security question (flag for AppSec):** What happens when a user rotates their Google account credentials? Does the vault key become inaccessible? This is the key-rotation problem surfaced by open decision #15 (`sg1.` prefix) in the identity domain — it now has a concrete scenario attached.

### 1.5 Vaults Within Vaults (P-231)

**What is proposed:** Open + create child vaults from inside a parent vault; parent reads referenced children; no backend complexity.

**Architectural assessment:**
- This is a **clean feature** with no backend changes required (the child vault is just another vault with its own key). The parent vault stores the child vault key (or a reference to it). The vault browser (EXISTS — vault v0.2.3) already handles individual vault navigation; adding "open a child vault" is a UI addition, not an API addition.
- **Security consideration (flag for AppSec):** When the parent vault holds the child vault key, anyone with the parent vault read_key can also read the child vault. This is expected and correct — but it means the parent vault's security classification applies to all child vaults it references. The zero-knowledge boundary still holds (the server never sees the child vault key — it stays in the parent vault, which is encrypted).
- The "create child vault from inside a parent" flow requires the vault creation API (`POST /vault/create-pointer`, which EXISTS). This should work without changes.

## Part 2: SG/Sentinel Batch-2 Architecture

### 2.1 Control-Flow Graphs for Business Logic (P-237) — Most Significant Addition

**What is proposed:** Layer 2 (Lambda@Edge) shares state with the app and enforces valid request sequences via control-flow graphs; hyper-jump blocking; the WAF Achilles heel (business-logic blind spot) solved.

**Architectural assessment:**
- This is the **most architecturally innovative element of the entire batch**. Traditional WAFs are stateless — they evaluate each request independently. Control-flow graphs make SG/Sentinel stateful at Layer 2, which shares state with the application. This is the mechanism that lets SG/Sentinel know that `DELETE /api/transfers/delete/{id}` can only be called by a client that previously called `POST /api/transfers/create` with a matching transfer ID.
- **The state sharing mechanism is not yet designed.** Layer 2 (Lambda@Edge) and the application Lambda are separate execution environments. "Shared state" must mean shared external state (DynamoDB, ElastiCache, or S3). The latency budget for a state lookup at Layer 2 is sub-20ms (Lambda@Edge SLA). DynamoDB single-digit millisecond reads are compatible; Redis even faster. **This design decision is prerequisite to any implementation.**
- The phrase "Layer 2 shares state with the app" needs clarification: does it mean (a) both read from the same state store, (b) the app writes state that Layer 2 reads, or (c) Layer 2 reads from the app via a sidecar? Option (b) is most natural — app writes transaction state; Layer 2 reads it for sequence validation.

### 2.2 Passive Mode as First Deployment Milestone (P-238)

**Architectural assessment:**
- Passive mode (observe-only, no side effects, rule reverse-engineering from logs) is architecturally sound as a first milestone. It requires no changes to the application; it only needs CloudFront + Lambda@Edge logging configured to write to S3. The application code is not touched until blocking rules are deployed.
- This is the **recommended first implementation target** — it delivers immediate visibility (the founding value) with zero risk.

### 2.3 SGS as Portable Spec (P-239)

**Architectural assessment:**
- "A rule has no idea where it runs" is the key design invariant. If this invariant holds, rules written for one deployment can be exported to AWS WAF, Cloudflare Workers, or any other execution surface. This requires that rules have no I/O dependencies — they receive inputs (the request envelope) and return a decision, with no side effects.
- This is achievable for Layer 1 (CloudFront Functions) rules by design (no I/O allowed). Layer 2 rules can have I/O (state lookups, LLM calls), but could be designed with an abstraction layer that hides the I/O backend. **The abstraction layer for I/O-capable rules is the key design decision for portability.**

### 2.4 MVA + Feature Flags as Rules (P-243) — High-Value, Incremental

**Architectural assessment:**
- **Feature flags as rules** is architecturally elegant and high-value: toggling a feature flag IS deploying/disabling a rule. This means feature flag management, A/B testing, gradual rollouts, and incident response (disable a feature under attack) all use the same mechanism. The rule machinery already exists by design; feature flags ride on top.
- This is a **quick win** once the rule engine is implemented. Flag a rule as a `feature-flag`, mark its scope, and the UI surface for "feature flags" is just a filtered view of the rules console.

### 2.5 Agent Governance (P-245) — Strategically Significant

**Architectural assessment:**
- Agent governance (one substrate controlling outbound actions, sequences, blast radius, and communication authentication for production agents) is a distinct architectural surface from security. It requires SG/Sentinel to observe *outbound* traffic as well as inbound — a capability established by P-238 (outbound-traffic observation) from the deployment-modes brief.
- The key architectural primitive: SG/Sentinel acts as an outbound proxy for agent traffic, applying rules to what agents *send* (API calls to external services, LLM requests, tool invocations). This is architecturally similar to how an egress firewall works, but with the rich SG/Sentinel context (PKI-authenticated agent identities, control-flow graphs for valid action sequences, vault-per-agent activity logging).
- **This is a 2025+ capability** — it should not block the MVP, but the architecture must accommodate it from the start (outbound proxy mode in the reverse-proxy form factor, PKI agent identity already in the design).
