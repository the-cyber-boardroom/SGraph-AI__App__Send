## 1 · Course corrections

| Earlier proposal | Corrected design |
|---|---|
| `/` redirects to `/en-gb/vault` when LS has a key (auto-resume). | `/` redirects based **only on the presence of a hash**. With `#token` → save → `/en-gb/vault`. Without `#` → `/en-gb/` (landing, even if LS has a key). |
| `/#token` redirects to `/en-gb/`, the user picks from the list. | `/#token` saves the token to LS, then redirects to `/en-gb/vault`. Share-link recipients land directly on the opened vault. |
| Migration as IFD overlay v0.2.4. | All edits happen in v0.2.3. New files (loader module, peek page) live under v0.2.3. Routing patches happen in v0.2.3 too. |
| The landing page does not read `localStorage('sg-vault-key')`. | The landing page **does** read it — but only for **display** (highlight the current vault in the recent-vaults grid). It still does not redirect or auto-open. |

The five principles from the previous doc remain in force, with two clarifications:

> Principle 2 (clarified). The **content** of the hash never influences routing — `/#`
> is treated identically to `/#anything` for redirect-target purposes. But the **presence**
> of a hash on root *does* determine the target: with hash → `/en-gb/vault`, without →
> `/en-gb/`. This is not a "decision based on the # value" because the hash is not
> parsed for routing; it is a "decision based on whether a share-link arrived." The hash
> payload is consumed (saved to LS) regardless.

> Principle 5 (clarified). Current vault key is **set, loaded, and cleared via
> `localStorage('sg-vault-key')`, and the only page that *acts on* it is `/en-gb/vault`.**
> Other surfaces may **read** it (landing for highlight, peek for display) but never act —
> never redirect, never open a vault, never mutate. Note the routing redirect at root is
> driven by *hash presence*, not by reading LS, so it does not violate principle 5.

## 2 · The Routing Table (final)

| URL | Hash present? | Action |
|---|---|---|
| `/` | no | Redirect to `/en-gb/` |
| `/#token` | yes | Save token to `localStorage('sg-vault-key')` → redirect to `/en-gb/vault` |
| `/en-gb/` | n/a | Render landing. Highlight LS-current vault in recent grid. |
| `/en-gb/#anything` | yes | **Strip and discard** (do not save) → render landing |
| `/en-gb/vault` | no | Render vault shell. Auto-load from LS. |
| `/en-gb/vault#anything` | yes | **Strip and discard** → render vault shell. Auto-load from LS. |
| `/en-gb/vault/peek` | no | Render peek page. |
| `/en-gb/vault/peek#anything` | yes | **Strip and discard** → render peek page. |

**Two routing rules.** First, root is the only hash inbox; everywhere else strips. Second,
root has exactly two redirect targets driven by hash presence: with `#` → `/en-gb/vault`
(open the just-arrived share link), without `#` → `/en-gb/` (let the user pick from their
list). Hash *content* is never parsed for routing — only presence.

### 2.1 The five entry flows under the new routing

```
   FLOW                       NAVIGATION                                OUTCOME
   ────                       ──────────                                ───────

   1. Type token at /en-gb/   landing handler:                          /en-gb/vault
                                 LS.sg-vault-key = token                opens vault
                                 nav to /en-gb/vault

   2. Click recent vault at   landing handler:                          /en-gb/vault
      /en-gb/                    LS.sg-vault-key = chosen.key           opens vault
                                 nav to /en-gb/vault

   3. Create new vault from   landing handler:                          /en-gb/vault
      /en-gb/                    SS.sg-vault-creating = key             create branch fires
                                 SS.sg-vault-access-key = ak            new vault opens
                                 LS.sg-vault-key = key
                                 nav to /en-gb/vault

   4. Share link /#token      root inbox:                               /en-gb/vault
      (external)                 LS.sg-vault-key = token                opens directly
                                 redirect to /en-gb/vault               (one hop, no
                                 (because hash was present)             extra click)

   5. Direct visit to         /en-gb/vault head script:                 /en-gb/vault
      /en-gb/vault              strip any hash                          opens (or shows
      (refresh, bookmark)       <vault-shell> reads LS, auto-opens      entry form if LS empty)

   6. Direct visit to /       root: no hash, redirect to /en-gb/        /en-gb/ landing
      (no hash, no purpose)    (regardless of LS contents)              user picks from list

Note flow 4: a share link arrives **with intent** (the user clicked it to open that specific
vault). Routing honours that by going directly to `/en-gb/vault`. Direct visits to `/`
without a hash (flow 6) go to `/en-gb/` — the user is exploring, not opening a specific
vault. The two cases are distinguished only by hash presence, not by hash content.

## 3 · Vault key formats — the canonical catalogue

The vault UI accepts five distinct credential formats. The loader's first job is to
**recognise** the format from a pasted string.

| # | Format | Shape | Read | Write | Origin |
|---|---|---|---|---|---|
| 1 | **Simple token** | `<word>-<word>-<NNNN>` | ✅ | ✅ | `SGVault.create()`, `<vault-entry>` token field, `_navigateToBrowse`. Both passphrase and vault_id derive from this single string. |
| 2 | **Passphrase + hex vault_id** | `<passphrase>:<12-hex-chars>` | ✅ | ✅ | Generated by `sgit vault info` for vaults created via the standard `passphrase:vault_id` flow. Passphrase may be a simple token. |
| 3 | **Passphrase + alphanumeric vault_id** | `<passphrase>:<4–24 a-z0-9 chars>` | ✅ | ✅ | Older / server-generated vault_ids. Passphrase may itself be a longer alphanumeric string. |
| 4 | **Read-only credential** *(new)* | `<vault_id> <read_key_hex>` (whitespace separator) | ✅ | ❌ | Generated by `sgit vault info` (`Read key:` line) plus the `Vault ID:` line. The recipient pastes both as one block. |
| 5 | **Server access token** *(separate)* | opaque random string | n/a | n/a | Server licensing/billing/quota gate. Stored in `sessionStorage('sg-vault-access-key')`. **Not** a vault credential — orthogonal axis. |

### 3.1 Detection rules (in order)

The parser tries patterns in this precedence:

```
   Input s = trim(paste)

   1. /^[a-z]+-[a-z]+-\d{4}$/                           → Simple token             (#1)
   2. /^[^:\s]+:[a-f0-9]{12}$/                          → Passphrase + hex id      (#2)
   3. /^[^:\s]+:[a-z0-9]{4,24}$/  (and not #2)          → Passphrase + alnum id    (#3)
   4. /^[a-z0-9]{4,24}\s+[a-f0-9]{64}$/                 → Read-only credential     (#4) ← whitespace only (D1)
   5. else                                              → Error: unrecognised format
```

Format #1 is also accepted in the right-hand passphrase position of #2/#3 (a simple token
is itself a valid passphrase). The grammar is permissive; the failure path produces a
clear "this looks like X but Y is missing" error message.

### 3.2 Worked detection examples (with synthetic placeholders only)

| Pasted string (synthetic) | Detected as |
|---|---|
| `apple-river-1234` | Simple token (#1) |
| `apple-river-1234:abcdef012345` | Passphrase + hex id (#2) |
| `apple-river-1234:short01` | Passphrase + alnum id (#3) |
| `mylongpassphrase:mylongerservervaultid01` | Passphrase + alnum id (#3) |
| `abcdef012345 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef` | Read-only credential (#4) |
| `apple-river` | Error: unrecognised |

### 3.3 What each format derives

| Format | `passphrase` | `vault_id` | `read_key` | `write_key` | `structure_key` |
|---|---|---|---|---|---|
| #1 simple token | token itself | derived from token | PBKDF2/HKDF | PBKDF2/HKDF | HKDF(read_key) |
| #2/#3 passphrase + id | left-side string | right-side string | PBKDF2 | PBKDF2 | HKDF(read_key) |
| #4 read-only | (none) | left-side string | hex-decoded right side | (none — vault is read-only) | HKDF(read_key) |
| #5 access token | n/a | n/a | n/a | n/a | n/a |

The existing `SGVaultCrypto.parseVaultKey` already handles #1–#3 (file
`_common/js/lib/sg-vault/sg-vault-crypto.js`, lines 32–51). The loader refactor adds #4 to
the same parser with a new code path that bypasses passphrase-based derivation.

### 4.2 Constraints

- **Standalone HTML.** Inline CSS/JS. No `_common/` JS imports. Same defensive property as
  the landing page — survives `_common/` regressions.
- **Read-only by default.** Vault key, access key, and any 32-byte hex blob are masked
  unless the user explicitly clicks "show". Mutating buttons (Clear, Open vault, Clear all)
  require an explicit click.
- **No vault open from peek.** Even "Open vault" navigates to `/en-gb/vault`; never
  instantiates `SGVault.open` from this page. Preserves the principle 5 invariant.
- **Server probe is opt-in.** Page does no network calls until "Probe" is clicked. Visiting
  Peek is offline-safe.
- **Format detection is local-only.** Pasted-key inspection runs key derivation in the
  browser without any network or LS write.
- **Display-only of LS/SS** — Peek inspects all keys (including legacy `sg-vault-history`
  and `sg-vault-picker:credentials`) and labels legacy keys with a "migrate" badge.
- **No vault data leak in `<title>`.** Page title stays `SG/Vault — Peek`. The vault key
  is in the body, not the title or URL.

### 4.4 Discoverability (D4)

Peek is a power-user surface, not part of the everyday flow. Two low-visibility entry
points:

- **Landing page footer** — a small muted link next to the version stamp:
  `<a class="vp-debug-link" href="/en-gb/vault/peek">peek</a>`.
  Style: 11–12px, `color: var(--muted)`, `opacity: 0.6`, no underline by default.
- **Vault shell status bar** — a small "debug" link in the existing status-bar area,
  next to (or replacing) the current debug-panel toggle. Same low-visibility styling.

Direct URL `/en-gb/vault/peek` continues to work (and is the documented entry for support
sessions). No prominent navigation; no menu item; no popover; no modal.

### 4.3 The "show raw localStorage" pattern

Two display modes for each value:

| Type | Default | "Show" behaviour |
|---|---|---|
| `sg-vault-key` | masked (`apple-river-····`) | Reveal full value, click to copy |
| `sg-vault-access-key*` | masked (`●●●●●●●●●● (n chars)`) | Reveal value |
| `sg-vault-recent`, `sg-vault-history`, `sg-vault-picker:credentials` | "[N entries — expand]" | Expand list with each entry's vault key (masked) and metadata |

`Export JSON` writes the full snapshot (with secrets) to a `Blob` download. User explicitly

```

### 5.3 Public API (vault-loader.js)

```js
window.VaultLoader = {

    // --- Format detection -------------------------------------------------------
    detectFormat(input)              => { format: 1|2|3|4, kind: string,
                                          parts: { passphrase?, vaultId?, readKeyHex?, raw } }
                                       throws Error(unrecognised)

    // --- Open / create / lock ---------------------------------------------------
    open(input, { accessKey, endpoint })       => Promise<{ vault, format }>
    create(simpleToken, { accessKey, endpoint, name? }) => Promise<{ vault }>
    openReadOnly(vaultId, readKeyHex, { endpoint })     => Promise<{ vault }>
    lock()                                              => void  (clears LS + SS,
                                                                  emits vault-locked)

    // --- Storage (single source of truth) ---------------------------------------
    storage: {
        getCurrentKey()              => string | null
        setCurrentKey(key)           => void   (emits vault-key-set)
        clearCurrentKey()            => void   (emits vault-key-cleared)

        getAccessKey()               => string | null
        setAccessKey(key)            => void
        clearAccessKey()             => void

        getEndpoint()                => string  (default applied)
        setEndpoint(url)             => void

        getCreatingFlag()            => string | null
        setCreatingFlag(key)         => void
        clearCreatingFlag()          => void
    }

    // --- Recent vaults (unified list) ------------------------------------------
    // (D2) Each entry stores BOTH key and name. name defaults to key.
    //      add(key, name) is idempotent — replacing the entry updates name + lastOpened.
    //      isCurrent is computed at list() time by comparing key to LS.sg-vault-key.
    recent: {
        list()                       => [{ key, name, lastOpened, format, isCurrent }]
        add(key, name?)              => void   // upsert; name → key when omitted
        remove(key)                  => void
        clear()                      => void
        migrate()                    => { migrated: number }
            // One-shot migration: union of sg-vault-history +
            // sg-vault-picker:credentials → sg-vault-recent. When the same key exists
            // in both, sg-vault-history wins (it carries the friendlier name).
            // Removes the old keys after migration.
    }

    // --- Routing (called from inline head scripts) -----------------------------
    routing: {
        runRoot()                    => void  // /index.html head script
        runLanding()                 => void  // /en-gb/ head script
        runVault()                   => void  // /en-gb/vault/ head script
        runPeek()                    => void  // /en-gb/vault/peek/ head script
    }

    // --- Events emitted by the loader ------------------------------------------
    events: {
        VAULT_OPENED          // detail: { vault, format, vaultKey, accessKey }
        VAULT_CREATED         // detail: { vault, vaultKey }
        VAULT_OPEN_FAILED     // detail: { error, vaultKey }
        VAULT_CREATE_FAILED   // detail: { error, vaultKey }
        VAULT_LOCKED          // detail: {}
        VAULT_KEY_SET         // detail: { key }
        VAULT_KEY_CLEARED     // detail: {}
        VAULT_RECENT_CHANGED  // detail: { count }
    }
};
```

The module emits events on `window.sgraphVault.events` (the existing `EventBus`). All
existing listeners continue to work.

### 5.5 The migration (in-place on v0.2.3)

The refactor does NOT delete the existing methods on `<vault-entry>` etc. — it
**reimplements** them as thin wrappers over `VaultLoader`. Behaviour is preserved exactly;
the upgrade is observable only by looking at the code. Sequenced as:

1. **Phase 1 — Add the loader module.** Create the six new files. They contain the
   *same* logic that lives elsewhere, lifted into one place. Nothing else changes yet.
2. **Phase 2 — Add tests.** Unit-test format detection, parsing, storage, recent-list,
   key-derivation interop with the existing crypto. **No production code references the
   loader yet** — the tests verify it before any caller is migrated.
3. **Phase 3 — Migrate callers, one at a time.**
   - 3a. `<vault-entry>._isSimpleToken` → `VaultLoader.detectFormat`.
   - 3b. `<vault-entry>._openVault` → `VaultLoader.open`.
   - 3c. `<vault-shell>._onLock` → `VaultLoader.lock`.
   - 3d. `<vault-entry>._onCreate` and the create-from-token patch → `VaultLoader.create`.
   - 3e. Recent-vaults migration: call `VaultLoader.recent.migrate()` once on each surface
     load.
   - 3f. `en-gb/index.html` recent-vaults grid + token regen → `VaultLoader.recent.*` and
     `VaultLoader.create`.
   - 3g. `en-gb/index.html._navigateToBrowse` → direct LS write + nav (no hash bounce).
   - 3h. Routing head scripts on all four surfaces → `VaultLoader.routing.run*`.
4. **Phase 4 — Add the peek page.** It's a thin caller of `VaultLoader.storage` /
   `VaultLoader.recent` / `VaultLoader.detectFormat`, so it lands cleanly after phase 3.
5. **Phase 5 — Remove the legacy bodies.** Once all callers go through the loader, the
   bodies of the original methods are deleted; only the wrapper-call lines remain.

Each phase is independently shippable and testable. A regression in phase 3a is fixable
without rolling back phase 1 or 2. The loader module is **additive** until phase 3, so it
cannot break the live UI.

Harness shape (file: `helpers.js`):

```js
// Tiny zero-dep assert/suite runner. Run with: node helpers.js test__*.js
import { strict as assert } from 'node:assert';
import { JSDOM } from 'jsdom';

export function suite(name, fn) {
    console.log(`\n[suite] ${name}`);
    const tests = [];
    const ctx = {
        test: (label, body) => tests.push({ label, body }),
        before: (fn) => (ctx._before = fn),
        after:  (fn) => (ctx._after  = fn),
    };
    fn(ctx);
    let pass = 0, fail = 0;
    for (const { label, body } of tests) {
        try {
            ctx._before?.();
            body();
            ctx._after?.();
            console.log(`  ✓ ${label}`);  pass++;
        } catch (err) {
            console.log(`  ✗ ${label}\n      ${err.message}`);  fail++;
        }
    }
    console.log(`  ${pass} pass, ${fail} fail`);
    if (fail) process.exit(1);
}

export function withDom() {
    const dom = new JSDOM('<!doctype html><html><body></body></html>',
                          { url: 'https://dev.vault.sgraph.ai/' });
    Object.assign(globalThis, {
        window: dom.window, document: dom.window.document,
        localStorage: dom.window.localStorage, sessionStorage: dom.window.sessionStorage,
    });
    return dom;
}

export { assert };
```

Sample test (file: `test__format_detection.js`):

```js
import { suite, assert } from './helpers.js';
import './load-loader.js';   // sources VaultLoader into globalThis

suite('VaultLoader.detectFormat', ({ test }) => {
    test('detects simple token', () => {
        const r = VaultLoader.detectFormat('apple-river-1234');
        assert.equal(r.format, 1);
        assert.equal(r.parts.passphrase, 'apple-river-1234');
    });

    test('detects passphrase + hex id', () => {
        const r = VaultLoader.detectFormat('apple-river-1234:abcdef012345');
        assert.equal(r.format, 2);
        assert.equal(r.parts.vaultId, 'abcdef012345');
    });

    test('detects passphrase + alnum id', () => {
        const r = VaultLoader.detectFormat('foo:short01');
        assert.equal(r.format, 3);
    });

    test('detects read-only credential', () => {
        const id = 'abcdef012345';
        const hex = '0'.repeat(64);   // synthetic
        const r = VaultLoader.detectFormat(`${id} ${hex}`);
        assert.equal(r.format, 4);
        assert.equal(r.parts.vaultId,   id);
        assert.equal(r.parts.readKeyHex, hex);
    });

    test('rejects unrecognised', () => {
        assert.throws(() => VaultLoader.detectFormat('apple-river'));
        assert.throws(() => VaultLoader.detectFormat(''));
        assert.throws(() => VaultLoader.detectFormat('apple-river-1234:!!!'));
    });
});
```

The harness is ~80 lines, zero npm dependencies (uses built-in `node:assert` and `jsdom`
which the project can install just for testing). Tests run with
`node tests/unit/vault_ui/loader/test__format_detection.js`.

### 6.4 The "regression file" pattern

The user's pain point is that bugs come back. The pattern that prevents this:

1. When a bug is found, before fixing it, write a failing test:
   `tests/e2e/vault_ui/test__regression__BRW_NNN.spec.js` (using the issue ID).
2. Fix the bug. Test passes.
3. Test stays in the suite forever.

The naming convention makes it easy to grep ("show me every regression test"), and the
filename ties to a tracked issue. The v0.2.3 history has at least eight bugs that should
each have a regression test by the time the refactor lands:

## 9 · Decisions resolved + open questions

### 9.1 Decisions (locked in by Dinis, 09 May 2026)

| # | Question | Decision |
|---|---|---|
| D1 | Read-only credential pair separator | **Whitespace only** (`<vault_id> <read_key_hex>`). No two-field UX. The detection regex stays as `/^[a-z0-9]{4,24}\s+[a-f0-9]{64}$/` and the "paste both lines from `sgit vault info`" workflow is the single supported entry path. |
| D2 | Recent-vault list — name vs. key | **Store both.** Each entry is `{ key, name, lastOpened, format }`. `name` defaults to `key` when no friendly name has been assigned. Vault settings can update `name` later; that update writes back to the recent list via `VaultLoader.recent.add(key, newName)` (idempotent — replaces the entry). |
| D3 | Current-vault highlight click behaviour on `/en-gb/` | **Card click navigates to `/en-gb/vault`.** The current vault's card behaves identically to any other recent-vault card — clicking writes `LS.sg-vault-key = card.key` (idempotent for the current one) and `location.assign('/en-gb/vault')`. The highlight is a visual differentiator only; the action is the same. |
| D4 | `/en-gb/vault/peek` accessibility | **Add a subtle link** from the landing page footer, in the visual style of "for power users — debug page." Not prominent. Direct URL still works. The peek page is also linked from inside `<vault-shell>`'s status bar (small "debug" pill, equally low-visibility). |

### 9.2 Implications of D1–D4 for the implementation

- **D1** → `VaultLoader.detectFormat` ships with one read-only regex. The peek page's
  paste-to-inspect input accepts the same form.
- **D2** → `vault-loader-recent.js` schema is `{ key, name, lastOpened, format }`. The
  legacy migration (`recent.migrate()`) reads `sg-vault-history` (which has `name`) and
  `sg-vault-picker:credentials` (which uses `key` as `name`) and produces the unified
  shape. When both old keys have an entry for the same vault, the entry from
  `sg-vault-history` wins (it carries the better `name`).
- **D3** → The "current" highlight is purely a CSS class on the matching card. The click
  handler is the same one used for any other card. No special path. Reduces conditional
  code in the landing page.
- **D4** → Two surfaces link to peek:
  - Landing page footer: `<a class="vp-debug-link" href="/en-gb/vault/peek">peek</a>`
    or similar — small, muted, near the bottom of the page next to the version stamp.
  - Vault-shell status bar: a small "debug" link/badge, in the same position as the
    existing debug-panel toggle. Click navigates (does not open in same view).
