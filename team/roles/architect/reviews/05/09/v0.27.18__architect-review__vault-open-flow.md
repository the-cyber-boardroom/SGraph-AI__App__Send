**Date:** 09 May 2026
**Reviewer:** Architect (Explorer team)
**Branch:** `claude/vault-ui-architecture-review-6nTQZ`
**Scope:** Code-traced flow for opening an existing vault, from landing page to opened vault.

This document walks every URL, every script, every state mutation and every navigation that
participates in opening a vault. It is a companion to the architecture-and-guidance review and
the v0.2.3 consolidation debrief. **It also surfaces one observed gap** in the landing-page
flow where the URL ends at `/en-gb/` instead of `/en-gb/vault`. Section 6 documents that gap and
the four ways to close it.

**Three things to remember:**

1. The **landing page** at `/en-gb/` is a self-contained HTML file with **inline CSS and JS**.
   It loads no `_common/` JS, no Web Components, no vault library code. This is deliberate —
   it cannot be broken by a `_common/` regression.
2. The **vault shell** is one HTML file (`/index.html`) that gets deployed to **two URLs**: `/`
   and `/en-gb/vault`. The deploy workflow `sed`-rewrites `_common/` paths in the second copy
   so they resolve from the root.
3. The root URL `/` **never serves the vault shell live** — its head script always redirects
   to `/en-gb/` and the page is unloaded before the rest parses. Root is **a hash inbox + a
   localised redirector**, nothing more.

## 2 · Storage keys (the source of truth)

Vault state lives in the browser, not in URLs. Five keys are involved.

| Key | Where stored | Lifetime | Purpose |
|---|---|---|---|
| `sg-vault-key` | `localStorage` | persistent | **Source of truth** for "currently loaded vault." Read by `<vault-entry>` `onReady` to auto-open. Written by every entry path. Removed on Lock. |
| `sg-vault-history` | `localStorage` | persistent | Vault-entry's "Recent Vaults" list. Written by `_saveToHistory(vault, key)` after a successful open or create. |
| `sg-vault-picker:credentials` | `localStorage` | persistent | Landing page's "Recent Vaults" grid. **Different list** from `sg-vault-history`. Written by `_storeVault(key, name)` on the landing page. (Same key as `<sg-vault-picker>` in the user UI.) |
| `sg-vault-creating` | `sessionStorage` | tab-only | Set by the landing page's create modal. Tells the patched `_onSimpleTokenOpen` to **create** instead of **open**. Removed after handling. |
| `sg-vault-access-key` | `sessionStorage` | tab-only | Holds the access key for the session. Set by the create modal and by `<vault-settings>`. Read by `_getSGSend()` to authenticate write requests. |

**Two architectural notes** worth flagging:

- `sg-vault-history` and `sg-vault-picker:credentials` are **two separate recent-vault lists**.
  The landing page never sees `sg-vault-history` and `<vault-entry>` never sees
  `sg-vault-picker:credentials`. A vault opened on one screen does not appear in the recent
  list on the other.
- The vault key is intentionally **never** written into the URL. `vault-entry.js#_openVault`
  writes only to `localStorage`. The two `history.replaceState` calls that previously put
  `#token` back into the URL (commit `7876c8e`) were removed.

## 3 · The routing rules (root and everywhere else)

The head script in the **root vault shell** (`index.html` lines 16–43) is the single piece of
code that decides what happens to a `#token` in the URL. The same script is in
`/en-gb/vault/index.html` (because the deploy generates that file from this one), so it also
fires on direct visits to `/en-gb/vault#token`.

```js
var path     = window.location.pathname.replace(/\/$/, '');   // "" at root, "/en-gb/vault" otherwise
var hash     = window.location.hash;                           // "#token" or "#token|deepLink"
var hasHash  = hash && hash !== '#';
var isRoot   = (path === '' || path === '/index.html');

// 1) Save the token to localStorage (the source of truth)
if (hasHash) {
    var token = decodeURIComponent(hash.slice(1)).split('|')[0].toLowerCase();
    if (token) localStorage.setItem('sg-vault-key', token);
}

// 2) At root: redirect to /en-gb/ and abort. The vault shell never mounts at /.
if (isRoot) {
    window.location.replace('/en-gb/');
    return;
}

// 3) Anywhere else: strip the hash from the URL bar (it must not persist).
if (hasHash) {
    history.replaceState(null, '', window.location.pathname + window.location.search);
}
```

**The decision table:**

| URL the user lands on | hasHash | isRoot | Net effect |
|---|---|---|---|
| `/` | false | true | Redirect to `/en-gb/` |
| `/#token` | true | true | Save token → redirect to `/en-gb/` (hash dropped) |
| `/en-gb/` | n/a | n/a | Landing page (no head script — different file) |
| `/en-gb/vault` | false | false | Load vault shell, `<vault-entry>` reads localStorage |
| `/en-gb/vault#token` | true | false | Save token → strip hash → load vault shell → auto-open |

## 6 · Observed gaps and how to close them

### Gap #1 — `/#token` bounces to `/en-gb/`, vault never auto-opens

**Symptom:** A user pasting `https://dev.vault.sgraph.ai/#word-word-1234` (a canonical share
URL, exactly the form `_mountBrowse#downloadUrl` produces) ends up on the landing page with the
vault key in `localStorage` but the vault not opened. They have to click the (now-recent) vault
card to trigger the open — which itself just re-bounces them to landing.

**Root cause:** The root `index.html` head script always redirects to `/en-gb/` (the landing
page), but the landing page has no logic to read `localStorage('sg-vault-key')` and forward to
`/en-gb/vault`. Either the redirect target or the landing page has to change.

**Four ways to close it** — listed in increasing scope:

1. **Change the redirect target in root.** Replace
   `window.location.replace('/en-gb/')` with
   `window.location.replace(localStorage.getItem('sg-vault-key') ? '/en-gb/vault' : '/en-gb/')`.
   Tiny change, root keeps the routing decision.
2. **Add a head-script auto-redirect to the landing page.** When the landing page loads with
   `localStorage('sg-vault-key')` set, redirect to `/en-gb/vault`. Keeps the root → en-gb chain
   intact for users who explicitly want to see the landing.
3. **Have the landing page mount `<vault-entry>` directly when a key is present.** Avoids the
   second navigation but requires loading `_common/` from the standalone landing page —
   reverses a deliberate design decision (the landing page is intentionally
   `_common/`-independent).
4. **Have the landing page navigate to `/en-gb/vault#token` instead of `/#token`.** Bypasses
   the root bounce entirely. Cleanest from a flow point of view; requires defining what to do
   if a user does paste `/#token` directly (probably option 1 in addition).

**Recommendation:** Option 1 is the minimal fix. Option 2 is the cleanest user-visible fix.
Either is well-scoped for a single coding session.

### Gap #2 — `sg-vault-creating` orphaned on landing after create flow

**Symptom:** Clicking "Create vault & open" on the landing page sets
`sessionStorage('sg-vault-creating')` and navigates to `/#token`. The user lands back at
`/en-gb/` (Gap #1). The flag is never consumed because `<vault-entry>` is not on the landing
page. If the user then clicks the recent-vault card, the patched `_onSimpleTokenOpen` does
load on the next page — but only after another bounce.

**Root cause:** Same as Gap #1 — the routing redirect lands the user on a page that does not
host `<vault-entry>`.

**Closing Gap #1 (any of options 1/2/4) closes Gap #2** automatically, because the user ends
up on `/en-gb/vault` where `<vault-entry>` is mounted and the patch runs.

### Gap #3 — Two recent-vaults lists with overlapping content

**Symptom:** A vault opened via the vault shell (`<vault-entry>` flow) appears in
`localStorage('sg-vault-history')` but **not** in `localStorage('sg-vault-picker:credentials')`.
A vault opened via the landing-page input or recent-vaults grid appears in
`sg-vault-picker:credentials` but **not** in `sg-vault-history`.

**Root cause:** The landing page is standalone (uses `sg-vault-picker:credentials` — same key
as `<sg-vault-picker>` in the user UI). `<vault-entry>` was written before the landing page
existed and uses its own list (`sg-vault-history`).

**Impact:** "Recent vaults" lists shown on different surfaces are inconsistent. Users may not
see a vault they just opened on the page they next visit.

**Recommendation:** Lower-priority cleanup. When unifying, move both surfaces to
`sg-vault-picker:credentials` (the user-UI canonical) and migrate any existing
`sg-vault-history` entries on first read. Track separately from the open-flow fix.

```
              ┌──────────────────────────────────────┐
              │ /en-gb/vault loads vault shell       │
              │ <vault-entry> reads LS.sg-vault-key  │
              │ Detects sg-vault-creating?           │
              │   yes → SGVault.createFromToken      │
              │   no  → SGVault.open                  │
              └────────────────┬─────────────────────┘
                               ▼
              ┌──────────────────────────────────────┐
              │ <vault-shell> _onVaultOpened          │
              │ Vault is shown.                      │
              └──────────────────────────────────────┘
```

The minimal changes required to ship this happy path:

1. In root `index.html` head script: branch the redirect target on `localStorage('sg-vault-key')`.
2. (Optional) On the landing page: read `localStorage('sg-vault-key')` on load and redirect
   to `/en-gb/vault` if set. Catches users who navigate directly to `/en-gb/`.

No changes to `<vault-entry>`, no changes to the inline patches, no changes to the routing
contract beyond the redirect target.

## 8 · What this means for coding sessions

- **A coding session that touches "vault open flow" should fix Gap #1 first.** Most of the
  observed UX confusion ("clicked share link, nothing happened") will be fixed by that single
  change.
- **Do not move the routing decision out of the root head script.** That script is the only
  centralised place where `#token → localStorage` happens. Splitting it across multiple files
  increases the surface area for the loop-and-redirect bugs the v0.2.3 history already fixed.
- **Do not add a hash-listener on the landing page.** The hash is consumed and stripped at
  every page load; a `hashchange` handler will never fire after that. This was the source of
  several earlier bugs (commit `7876c8e`).
- **Keep the landing page `_common/`-independent.** Option 3 of Gap #1 (mount `<vault-entry>`
  on the landing page) is tempting but reverses a deliberate design property. The landing page
  is the only surface that survives a `_common/` regression — keep it that way.
