## 1 · Where the Vault UI Actually Lives

The vault UI is one IFD product (`sgraph_ai_app_send__ui__vault/`) with three rendering surfaces.
Two of them ship from this repo, the third is shared with the user UI and shipped from
`sgraph_ai_app_send__ui__user/` via CDN. Coding sessions that mistake which surface owns a feature
end up patching in the wrong place.

| Surface | Path in v0.2.3 | What it is | Owns |
|---|---|---|---|
| **Landing page** | `en-gb/index.html` | Standalone HTML, inline CSS+JS, **no `_common/` deps** | "Open a vault" hero, recent-vaults grid, create-vault modal |
| **Root vault shell** | `index.html` | Heavy patching layer + `<vault-shell>` mount | Routing rules, app.json App Mode wiring, error pages, vault-shell patches |
| **`<vault-shell>` web component** | `_common/js/components/vault-shell/vault-shell.js` | The live application | Vault lifecycle (entry → opened → lock), nav/views, mounting `<send-browse>` |
| **`<send-browse>`** | `dev.send.sgraph.ai/_common/js/components/send-download/send-browse--v0.3.2.js` (CDN) | **Lives in user UI** — file tree, tabs, file rendering, HTML iframe + VFS bridge | Tree, file tabs, file content rendering, iframe pipeline |
| **`vault-browse-edit.js` overlay** | `_common/js/components/vault-browse-edit/vault-browse-edit.js` | Patches `SendBrowse.prototype.{_renderFileContent,_build,_setupTreeListeners,_openFolderPage}` | Edit/Save/Cancel, Upload, New File, New Folder, Rename, Delete, drag-drop, App Mode button, conflict-resolve, SGit Data |
| **`<sg-app-banner>`** | `_common/js/components/sg-app-banner/sg-app-banner.js` | Web Component, fixed banner | App Mode (chrome hide + frame lift) |

**Implication for coding sessions:**

- "Make HTML files render with X" → almost always lives in `send-browse--v0.3.2.js` (user UI repo,
  loaded from CDN). The vault UI overlay can rarely fix it.
- "Add a new button next to Edit/Save/Delete" → `vault-browse-edit.js`.
- "Change the recent-vaults card layout" → `en-gb/index.html` (it's standalone).
- "Change how the vault opens / how the URL hash is consumed" → `index.html` (root shell) +
  `vault-entry.js`.
- "Change vault chrome (header / nav / status bar)" → the dedicated component file under
  `_common/js/components/vault-{header,nav,status-bar}/`.

## 2 · The Rendering Pipeline for Vault HTML Files

This is the most-reworked area in the v0.2.3 history (commits `85d3d16`, `8c1778b`, `c448bc9`,
`b50d822`, `2ccfe55`, `a26df38`, `8b94f52`, `b019560`). It now obeys a stable contract — any
session touching it must understand the contract before changing anything.

### 2.1 The contract — `window.sg.*`

Vault HTML files render inside a sandboxed iframe loaded from a `blob:` URL. Vault assets cannot
be loaded declaratively, because the browser HTML/CSS parser fetches them against the iframe's
opaque blob origin (404) before the bridge script runs. The contract is documented in
`library/guides/vault-html/AUTHORING.md`. Read it before writing or modifying vault HTML.

**The runtime API exposed inside the iframe:**

```js
window.sg = {
    vfs:     { write, read, readText, list },
    loadCss: (path) => Promise<HTMLStyleElement>,
    loadJs:  (path) => Promise<HTMLScriptElement>,
    app:     { selfPath, writable },
};
```

**What works:** `fetch(...)`, `<img src>` (initial + JS-set), `<a href>` clicks, `sg.vfs.*`,
`sg.loadCss('theme.css')`, `sg.loadJs('helper.js')`.

**What does not:** declarative `<link rel="stylesheet">`, `<script src>`, `<iframe src>`,
`<source src>`, `@import`, ES `import()`, `new Worker(...)`, `XMLHttpRequest`.

### 2.2 The architectural decision — why we do not data-URI inline

Earlier in the session (`85d3d16`, `8c1778b`, `2ccfe55`), the iframe pipeline parsed the HTML on
the parent side and rewrote `<script src>` / `<link href>` to base64 data URIs. This worked but
had an entire class of fragility (`</script>` / `</style>` early termination, regex sensitivity,
base64 inflation, `>`-text-node leaks via `$1` regex backreferences).

Commit `b019560` deliberately replaced that approach with the **calling-convention contract**
above. Authors load CSS/JS at runtime via `sg.loadCss`/`sg.loadJs`; the existing fetch override
serves the bytes; the parent never re-parses the HTML.

**Architectural implication:** the parent-side asset-rewrite path is intentionally dead. Future
sessions must not reintroduce data-URI rewriting as a "fix." If a vault HTML file has broken
imports, the answer is to **migrate the file** to the contract, not to re-add parsing.

### 2.3 Single-iframe invariant (view + edit)

`<send-browse>` creates **one** `.sb-file__html-frame` iframe per file tab. The HTML editor
(`vault-browse-edit.js`, `htmlEditBtn` handler) **reuses that iframe** rather than creating a
second one for the live preview. The textarea pane is prepended as a left sibling, the iframe's
parent is flipped to `flex-direction:row`, and `_loadHtmlIntoIframe(...)` is called with the
edited bytes on debounced `input`.

**Why this matters:** moving an iframe in the DOM forces a reload, losing parent-side bridge
state and any in-iframe JS state. Future sessions must not attempt to "simplify" by spinning
up a second iframe for the editor preview. Multiple regressions in this area trace back to
exactly that mistake.

### 2.4 Layout-collapse pitfall

The iframe is created with `height:0; min-height:0; flex:1` for the column-flex layout. When
edit mode flips the wrapper to row-flex, those declarations collapse the iframe to 0px on the
new cross-axis. The current code saves and overrides `height/min-height` on enter, restores on
exit (commit `8b94f52`). Future sessions touching the editor layout must preserve this
save/override/restore symmetry.

### 2.5 Bridge listener lifecycle

The parent-side VFS bridge listener (`window.addEventListener('message', …)`) is keyed by the
iframe's `contentWindow`. It survives a `src`/blob-URL reload because `contentWindow` is
re-evaluated per message. **Do not** call `_cleanupBridges()` on every keystroke during edit-mode
debounced re-render — that wipes the listener and breaks VFS reads/writes for the live preview.
Cleanup is correct on Save (full re-render rebuilds toolbar + iframe) and on Cancel (after
re-loading original bytes).

## 3 · Routing & Persistence Rules

Codified in `index.html` lines 9–43 and the patches lower in the same file. These rules emerged
from killing an infinite redirect loop (commit `353ef55`) and a chain of "crazy redirects" that
bounced the vault key back into the URL hash (commit `7876c8e`).

| Rule | Where enforced |
|---|---|
| Root `/` is **the only** path where `#vault-key` is allowed | `index.html` head script + `en-gb/index.html` `_navigateToBrowse` |
| At root, hash is consumed → saved to `localStorage('sg-vault-key')` → redirect to `/en-gb/` | `index.html` head script |
| Every other path **strips** any hash on entry | Same script |
| `localStorage('sg-vault-key')` is **the** source of truth for "currently loaded vault" | Read by `vault-entry.js#onReady`, the v0.2.2 splash check, `_onSimpleTokenOpen` patch |
| `sessionStorage('sg-vault-creating')` triggers create-vault flow | Set by `en-gb/index.html#recoveryConfirmBtn`, consumed by patched `_onSimpleTokenOpen` |
| `sessionStorage('sg-vault-access-key')` holds access key for the session | Set by `vault-settings`, consumed by vault open flow |
| Lock clears `sg-vault-key` and `sg-vault-session`, redirects to `/en-gb/` | `_onLock` patch in `index.html` |
| Share URLs always point at root: `origin + '/#' + token[ + '|' + path]` | `_mountBrowse` patch, `_plrSetHashPath` patch |

**Forbidden patterns** (these were all bugs at some point in the history):

- ❌ Writing the vault key back into the URL via `history.replaceState`. The address bar must
  stay clean. (`vault-entry.js` was patched in `7876c8e` to remove these calls.)
- ❌ Listening to `hashchange` to load vaults. Removed deliberately.
- ❌ Locale-detection redirects at any path. The site is en-gb only for now and the locale
  redirect at `/en-gb/` was the source of the v0.2.2 reload loop.
- ❌ Doing anything sensitive based on URL hash content **after** the entry script runs. By
  then the hash has been stripped.

**Coding session guidance:** if a session needs to add a new way to enter the vault, route it
through `localStorage('sg-vault-key')` + a navigation to `/en-gb/`. Do not invent new URL forms.

## 4 · App Mode Invariants (`<sg-app-banner>`)

App Mode is a deceptively-tricky feature — eight commits between `7233ea2` and `a26df38` chased
regressions here. The current shape works because of a small number of invariants. Future
sessions must preserve all of them.

### 4.1 Two layers, never one

- **Layer 1 (regular DOM CSS):** injected stylesheet `#sg-app-banner-max-css` hides
  `vault-header`, `vault-nav`, `vault-status-bar`, `.sb-header`, `.sb-file__actions`,
  `.sb-file__markdown` max-width.
- **Layer 2 (frame lift):** `position:fixed` applied to the **wrapper element**, not the iframe
  itself. The iframe stays in its DOM position so it does not reload.
- **Shadow CSS fallback:** `sgl-tab-bar`, `sgl-resize-handle`, `plr-source-bar` hidden via a
  stylesheet injected into `sg-layout`'s shadow root. Plus an explicit hide of the tree
  `.sgl-stack`.

### 4.2 No DOM moves

The lift mechanism (`_liftContentFrame`) overwrites `style.cssText` on the wrapper. It does not
reparent. Reparenting an iframe is a reload.

### 4.3 Save & restore exhaustively

`_savedLiftEl`, `_savedWrapperStyle`, `_savedIframeStyle` are captured on enter and replayed on
exit. Deactivate also re-shows the tree stack (`_restoreTreeStack`) and dispatches `resize`
twice (sg-layout caches panel dimensions; the second resize is needed because the first runs
before sg-layout has re-measured).

### 4.4 Auto-activate only when the entry exists

`index.html#_applyAppJson` checks that the entry file from `app.json` actually exists in the
file list before activating App Mode. Without this check, App Mode lifts whatever
`.sb-file__content` appears next — which is `app.json` itself if the entry is missing.

### 4.5 Re-lift is HTML-only

When a user navigates to a new file inside an active App Mode iframe, the patched
`_renderFileContent` re-lifts only when the new file is `.html`/`.htm`. Re-lifting on every file
type pulls non-HTML files into App Mode involuntarily (commit `b50d822` fixed this).

### 4.6 `_page.json` panels live in shadow DOM

The `_openFolderPage` patch dispatches `sg-page-layout-ready` with the panel element, and
`_waitForIframeAndLift` listens for it. This is the only path by which App Mode can lift a
panel that is not a direct light-DOM descendant of `body`.

### 4.7 Background colour

The HTML iframe has `background:#fff; color-scheme:light;` (commit `2ccfe55`, preserved in App
Mode by `a26df38`). Removing these declarations leaks vault chrome through transparent body
backgrounds.

## 5 · The `vault-browse-edit.js` Overlay Pattern

This 1,217-line file is the single biggest patching surface in the vault UI. It overrides four
`SendBrowse.prototype.*` methods. Each override has a specific contract.

| Method | What the override adds | Re-entry safety notes |
|---|---|---|
| `_renderFileContent` | All action-bar buttons (App Mode, Refresh, Edit/Save/Cancel, Copy, HTML editor, Full Screen, SGit Data, Rename, Delete, View Source, Resolve Conflict). Re-lift hook for HTML in App Mode. | **Re-entrant by design.** Refresh, Save, and Cancel all call `self._renderFileContent(container, …)` to re-render. Buttons are recreated each call — never accumulate listeners. |
| `_openFolderPage` | App Mode support for `_page.json` panels (sg-layout shadow DOM). | Captures the new panel ID by hot-patching `sgLayout.addTabToStack` for one call only. Restores immediately. |
| `_build` | Header buttons: New File, New Folder, Upload Files (writable only). | Called once per `<send-browse>` instance. |
| `_setupTreeListeners` | Refresh button on tree controls, folder rename/delete, drag-and-drop. | Called every time the tree re-renders. The refresh button check (`if (controls.querySelector('.sb-vault-refresh'))`) prevents duplicates; folder action injection has a similar guard. |

**Hard-won patterns coding sessions must follow:**

1. **All state lives at the `_renderFileContent` closure level.** `_htmlTextarea`, `_htmlEditing`,
   `_pvBridges` etc. are declared at the top of the function. A patch that put `_pvBridges`
   inside the Edit handler caused a `ReferenceError` in Save/Cancel (commit `b50d822` moved it).
2. **Always declare ext at the top.** `_ext0` is read by the App Mode re-lift check **before** the
   Edit handler runs; declaring it inside the Edit handler crashes the re-lift (`2ccfe55`).
3. **`insertBefore` defensively.** App Mode lift / page-layout overlays can wrap the iframe in
   intermediate elements. Insert into `iframe.parentNode`, not `content` (`a26df38`).
4. **Save & restore the split host's full `cssText`,** not just `flexDirection`. Layout state
   (display, flex-direction, etc.) must revert cleanly on Cancel/Save.
5. **Use the inline `_prompt`/`_confirm` dialogs**, not browser `prompt()`/`confirm()`. They
   block the iframe and are jarring.
6. **Toast all errors via `window.sgraphVault.messages.{success,warn,error,info}`.** Consistent
   user feedback across the file.

**Do not refactor this file casually.** It works, and the bugs it has accumulated — and
fixed — are not always obvious from the code alone. Prefer additive changes over restructuring.
A future structural pass should extract HTML-editor, drag-drop, and folder-actions into separate
files (the overlay is starting to feel like multiple components glued together), but that is its
own piece of architectural work.

## 6 · The Patches Inside `index.html`

`index.html` ends with ~500 lines of `<script>` patches that monkey-patch
`SGVault.createFromToken`, `VaultDataSource.prototype.{getTree,getFileList,getFileBytes,saveFile}`,
`VaultEntry.prototype._onSimpleTokenOpen`, and `VaultShell.prototype.{_mountBrowse,_onLock,_applyAppJson,_setupVaultLinkHandler}`.

This is mechanically convenient but architecturally unhealthy:

- The patches are not diffable as separate components.
- They run after `customElements.define` has fired, so script ordering is load-bearing.
- A coding session reading `vault-shell.js` to understand `_mountBrowse` will read the wrong
  thing — the overridden version in `index.html` is what actually executes.

**Guidance for coding sessions:**

- **For now**, keep additions inside the `index.html` patch IIFE — splitting it is its own
  refactor and beyond the scope of small features.
- **Always** comment the override with a clear "Patches X.Y because Z" header.
- **Never** remove `_origMount.call(this, deepLink)` (or analogous calls). The patches are
  delegating wrappers; bypassing the original breaks the whole vault-shell flow.
- A future structural pass should move these patches into `_common/js/components/vault-shell-patches/`
  loaded as a separate script. Track this as a follow-up but do not block feature work on it.

## 7 · IFD State and the v0.2.3 Snapshot

v0.2.3 is a **full snapshot** that consolidates v0.2.0 (base) + v0.2.1 (Design 02 landing) +
v0.2.2 (App Mode shell). The debrief at
`team/humans/dinis_cruz/debriefs/05/09/v0.27.18__debrief__vault-ui-v0.2.3-consolidation.md`
documents the consolidation logic and the deployment-script changes in detail.

**Consequences for future coding sessions:**

1. **All edits to "the latest vault UI" go into v0.2.3 first**, until a delta is created.
2. **The next change should create `v0.2.4/`** containing only the changed files, and re-introduce
   `BASE_SOURCE_DIR` in `deploy-ui-vault.yml` + `VAULT_IFD_OVERLAYS=("v0.2.4")` in
   `vault__run-locally.sh`. The debrief Part 5 has the exact patterns.
3. **Do not delete v0.2.0 / v0.2.1 / v0.2.2.** They are the historical IFD layers. Removing them
   breaks the audit trail and any external consumers pinned to those versions.
4. **A second consolidation snapshot is warranted** when overlays accumulate to ~3+ versions or
   when a major structural change makes the delta history unreadable. Until then, deltas.
5. **Inline patches in `index.html` should keep their version-marker comments** (e.g.
   `v0.2.1 patch:`, `v0.2.2 additions:`) so a reader can tell which delta introduced what.

## 9 · Per-Session Briefing Templates

Use these as the opening prompt for the corresponding coding session. Each one frames the
problem and points the session at the right files and invariants.

### 9.1 "Add a button to the file action bar"

- **File:** `_common/js/components/vault-browse-edit/vault-browse-edit.js`
- **Function:** `_renderFileContent` override
- **Pattern:** Use `_makeBtn(label)`, append to `bar` (which is
  `container.querySelector('.sb-file__actions')`). Conditional on `this.dataSource.writable`
  if the action mutates the vault.
- **Toasts:** `window.sgraphVault.messages.{success,error,warn,info}`.
- **After mutation:** call `_refreshBrowseTree(self)` if the file tree changed; re-render
  via `self._renderFileContent(container, newBytes, fileName, type)` if the file content
  changed.
- **Don't:** add the button at module scope, accumulate listeners, or use browser
  `confirm()`/`prompt()`. Use the inline `_confirm`/`_prompt` helpers in the same file.

### 9.2 "Change the landing page (Open a vault)"

- **File:** `en-gb/index.html` (standalone — no `_common/` deps).
- **All code is inline** in one IIFE. Recent vaults persisted in
  `localStorage('sg-vault-picker:credentials')`. Token regeneration uses the same word lists
  as `sg-vault-picker.js` in the user UI repo.
- **Navigation:** always via `_navigateToBrowse(key)` which writes
  `window.location.href = '/#' + encodeURIComponent(key)`. Root consumes the hash and
  redirects to `/en-gb/`.
- **Don't:** load anything from `_common/` here. The page is intentionally self-contained so
  it cannot be broken by a `_common/` regression.

### 9.3 "Fix something in HTML iframe rendering"

- **First:** read `library/guides/vault-html/AUTHORING.md` end-to-end.
- **Probable file:** `dev.send.sgraph.ai/_common/js/components/send-download/send-browse--v0.3.2.js`
  (user UI repo, not vault). The vault loads it from CDN and patches via
  `vault-browse-edit.js`.
- **Invariant 1:** single iframe across view + edit. Do not create a second iframe.
- **Invariant 2:** do not reintroduce parent-side `<link>`/`<script src>` data-URI rewriting.
  The fix is in the contract.
- **Invariant 3:** preserve the parent-side bridge listener across blob-src reloads. Only
  cleanup on Save/Cancel, never per-keystroke.
- **Invariant 4:** save/override/restore the iframe's `height`/`min-height` symmetrically
  during edit-mode flex-row.

### 9.4 "Change something about App Mode"

- **Files:** `_common/js/components/sg-app-banner/sg-app-banner.js` and the
  `_renderFileContent` re-lift block in `vault-browse-edit.js`, plus `_applyAppJson` in
  `index.html`.
- **Re-read §4 above** before changing anything.
- **Invariants:** two layers (CSS + position:fixed), no DOM moves, save/restore exhaustively,
  auto-activate only when entry exists, re-lift only for HTML, dispatch `resize` twice on
  deactivate.

### 9.5 "Add a new vault HTML demo (or fix one that's broken)"

- **File:** the demo's HTML, in whatever vault folder it belongs.
- **Read:** `library/guides/vault-html/AUTHORING.md` Quick Checklist (§ at the bottom).
- **Pattern:** if small, inline everything. If larger, split into `theme.css` + `app.js` and
  load via `Promise.all([sg.loadCss('theme.css'), sg.loadJs('app.js')])`.
- **Verify:** look for `[sg-vfs] window.sg ready` in the iframe console. If absent, the
  bridge didn't install — that's a `send-browse` bug, not your demo's bug.

### 9.6 "Move an inline patch out of `index.html`"

- This is structural work. Do it as a focused session, **not as part of a feature change**.
- **Approach:** create `_common/js/components/vault-shell-patches/vault-shell-patches.js`,
  loaded from `index.html` as a regular `<script>` tag after the components it patches.
  Move one IIFE at a time and verify each move with the local server.
- **Don't:** rewrite the patches while moving them. Move first, refactor later, in separate
  commits.

### 9.7 "Add an IFD delta on top of v0.2.3"

- **Create:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.4/` with **only** the changed files.
- **Update:** `.github/workflows/deploy-ui-vault.yml`:
  - `UI_VERSION: v0.2.4`
  - `SOURCE_DIR: …/v0.2.4`
  - **Re-introduce** `BASE_SOURCE_DIR: …/v0.2.3` if `v0.2.4` does not include `en-gb/`
    (i18n step seeds `en-gb/` from base).
  - Re-add the "Populate en-gb/" step accordingly. The debrief Part 3 has the exact YAML.
- **Update:** `scripts/vault__run-locally.sh`:
  - `UI_VERSION="v0.2.4"`, `IFD_PATH="v0/v0.2/$UI_VERSION"`
  - `VAULT_BASE_VERSION="v0.2.3"`, `VAULT_IFD_OVERLAYS=("v0.2.4")`
- **Verify:** run `scripts/vault__run-locally.sh`, browse to `http://localhost:.../en-gb/`,
  open a vault, exercise the changed surface.
- **Don't:** copy unchanged files into v0.2.4. The whole point of IFD is delta-only.

## 10 · Open Questions for Dinis (Optional)

These are areas where the architecture is functional but where a small product/architectural
decision could simplify future sessions. None are urgent.

1. **Should the `index.html` inline patches move into a dedicated `vault-shell-patches.js`?**
   Pro: diffability, separation of concerns, easier on coding sessions reading `vault-shell.js`.
   Con: another file to load, another script-order dependency.
2. **Should `vault-browse-edit.js` (1,217 lines) be split into 3–4 files** (HTML editor,
   drag-drop, folder actions, action-bar buttons)? It is starting to feel like multiple
   components.
3. **Should "Reload App" come back?** Removed in `fe2e071` "deferred to BRW-023". The current
   App Mode lacks an explicit reload button; users either exit App Mode or refresh the whole
   page. The CI pipeline + cover infra is already there in `_reloadAndLift` — just unwired.
4. **Should the vault deep-link `_plrGetHashPath`/`_plrSetHashPath` patches** in `index.html`
   become a public extension point on the page-layout renderer in the user UI repo? They
   monkey-patch what looks like a private API.
5. **When does v0.2.4 get cut?** The longer v0.2.3 stays the working tree, the more changes
   accumulate as snapshot edits rather than overlays. A delta gives us a clean diff for the
   next change.
