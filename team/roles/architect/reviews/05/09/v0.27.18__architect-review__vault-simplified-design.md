## 1 · Five Core Principles (ground truth)

> 1. **The only place where there is an auto-load of the vault is `/en-gb/vault`.**
> 2. **There are no redirects based on `#` values.** The hash is consumed (saved to
>    localStorage) but does not influence redirect target.
> 3. **The only place where `#{token}` is supported is the root `/`.** Root is the
>    single hash inbox.
> 4. **Any other place that has a `#` value in the URL — namely `/en-gb/`, `/en-gb/vault`,
>    `/en-gb/vault/peek` — strips and discards the hash immediately.** No reading, no saving.
> 5. **Current vault key is set, loaded, and cleared via `localStorage('sg-vault-key')`,
>    and the only page that reads it is `/en-gb/vault`.** Set by the root hash inbox and by
>    explicit user action; cleared by Lock.

These five principles together yield a much smaller architecture than the current code: one
inbox (root), one reader (`/en-gb/vault`), one source of truth (`localStorage`), and zero
hash-based routing decisions.

## 3 · The Single Routing Table

This replaces every routing branch in v0.2.3. Memorise this — it's everything.

| URL the user lands on | Has `#token`? | Auto-load vault? | Action(s) |
|---|---|---|---|
| `/` | no | n/a | Redirect: `LS.has_key ? '/en-gb/vault' : '/en-gb/'` |
| `/#token` | yes | n/a | Save token to LS → redirect to `'/en-gb/vault'` |
| `/en-gb/` | no | no | Render landing |
| `/en-gb/#anything` | yes | no | **Strip and discard** hash; render landing |
| `/en-gb/vault` | no | yes | Strip hash (none); load vault from LS |
| `/en-gb/vault#anything` | yes | yes | **Strip and discard** hash; load vault from LS |
| `/en-gb/vault/peek` | no | no | Render peek page |
| `/en-gb/vault/peek#anything` | yes | no | **Strip and discard** hash; render peek page |

**Two things this table makes explicit** that the v0.2.3 code does not:

1. Share links of the form `/en-gb/vault#token` are not honoured — the hash is silently
   discarded, the page loads whatever vault is in LS. **All share links must use root form
   `/#token`.** This is a deliberate simplification.
2. Root never blindly redirects to `/en-gb/`. After saving a hash token, root redirects to the
   shell because LS now has a key. With no hash and no key, root goes to landing. With no hash
   but an existing key in LS, root goes straight to the shell — automatic resume.

## 4 · The Storage Model (simplified)

### 4.1 The keys

| Key | Storage | Set by | Read by | Cleared by |
|---|---|---|---|---|
| `sg-vault-key` | `localStorage` | (a) Root hash-inbox script, (b) Landing page before navigation, (c) Peek page (manual paste) | **`/en-gb/vault` only.** Plus `/` (to choose redirect target) and `/peek` (to show what would open). Neither *acts* on it. | Lock; explicit "clear" on Peek |
| `sg-vault-recent` | `localStorage` | `/en-gb/vault` after successful open + `/en-gb/` after submit | `/en-gb/` (recent-vaults grid), `/en-gb/vault` (history), `/peek` (debug) | Manual "manage" / Lock with "clear history" |
| `sg-vault-access-key` | `sessionStorage` | Landing modal, vault settings | `/en-gb/vault` for write ops, `/peek` for display | Tab close, Lock |
| `sg-vault-creating` | `sessionStorage` | Landing create modal | `/en-gb/vault` (`<vault-entry>` create branch) | `<vault-entry>` after consume |
| `sg-vault-endpoint` | `sessionStorage` | `<vault-entry>` endpoint input | `<vault-entry>` and `/peek` | Tab close |

### 4.2 The recent-vaults consolidation

The current code maintains **two** lists:

- `sg-vault-history` (`<vault-entry>`)
- `sg-vault-picker:credentials` (landing page, same key as `<sg-vault-picker>` in user UI)

**Decision (per principle 5):** unify under a single key `sg-vault-recent`. Both surfaces
read and write the same list. Migration is one-shot: on first read, if the new key is missing
and either old key has data, copy the union into the new key and remove the old keys.

This is independent of the routing simplification but a natural consequence of "one source of
truth."

## 6 · `/en-gb/vault/peek` — debug / inspection page

A new top-level page at `/en-gb/vault/peek`. Its purpose is **to confirm what the browser
currently sees**, without opening a vault. Useful for:

- Debugging "why is my vault not loading?" — does LS actually have what I think it has?
- Verifying share links — paste a `/#token` URL, see what would be opened.
- Confirming vault format detection — is this token a simple-token, full-key, or read-only-key?
- Checking server reachability — does the configured endpoint respond? Does the vault exist?
- Diagnosing access-key issues — is one set in SS? Is it the right one?

### 6.2 Implementation constraints

- **Standalone HTML.** No `_common/` JS dependencies. Same property as the landing page —
  can't be broken by a `_common/` regression.
- **Inline CSS/JS.** Self-contained. Style consistent with the landing page.
- **Read-only by default.** Buttons that mutate state ("Clear", "Open vault") require an
  explicit click and a one-line confirm.
- **No vault open.** Even when the user clicks "Open vault", the action should redirect to
  `/en-gb/vault` (which auto-loads), not call `SGVault.open` from this page. Keeps the "only
  place that reads LS and acts on it" invariant.
- **Server probe is optional and explicit.** A "Probe" button issues `HEAD` or
  `GET /vault/...` against the endpoint. Without the click, the page does no network calls.
  This means visiting Peek is offline-safe.
- **Format detection is local-only crypto.** The "Inspect" path takes the pasted string and
  runs key derivation in-browser to display the derived `vault_id` and key format. **Does not
  touch localStorage.**

### 6.3 Where it fits in the IFD tree

Add as a single file at `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.4/en-gb/vault/peek/index.html`
in a new IFD overlay v0.2.4. The deploy workflow does not need any sed-rewrite step for it
(same reason the landing page doesn't — it has no `_common/` references).

## 7 · Read-only vault keys

### 7.1 The need

Today every vault key (simple token or full passphrase form) gives both **read** and **write**
capability. There is no way to share a vault read-only with someone, except by minting a share
token (`sgit share`) which is a frozen snapshot — read-only **and** ephemeral, not what we
want for "let this person follow my vault as it evolves."

### 7.2 The new format

A new credential pair: **`vault-key + read-only-key`**.

- **`vault-key`** — public-ish identifier of the vault. The `vault_id`, expressed as a friendly
  string. Suggested form: a 12-hex-char vault_id wrapped in a friendly word-pair label, e.g.
  `vault-apple-river` (the words are decorative; the ID is the canonical form).
  Alternative: just the bare `vault_id` (12 hex chars) without word decoration.
- **`read-only-key`** — the AES-256 `read_key` material itself, encoded for a human to
  paste. Suggested form: a 4-word + 4-digit + 4-word string (≈128 bits of friendly entropy)
  that decodes to the 32-byte read_key, OR a base32 encoding (52 chars) for full entropy.

The combination yields **only** the read-side keys. There is no derivation path from these
two strings to `write_key`.

### 7.3 Distinct from existing concepts

The existing model has **three** types of credential. The read-only key adds a fourth, with
clear separation:

| Credential | Form | What it gives | Where it travels |
|---|---|---|---|
| **Simple token** | `word-word-NNNN` | read + write keys | Browser memory; URL hash inbox; localStorage |
| **Full vault key** | `passphrase:vault_id` | read + write keys | Same as above |
| **Read-only credential** *(new)* | `vault-key + read-only-key` | read keys only | Same as above; cannot be used to write |
| **Access token** | random opaque string from server | server-side licensing/billing check (rate-limit, quota, identity) | sessionStorage `sg-vault-access-key`; `Authorization` header |

Crucial property: the **server cannot tell** the difference between a writable client and a
read-only client by looking at the access token. The capability is entirely cryptographic —
the server stores ciphertext indexed by `vault_id`, anyone who supplies the access token can
read or write the ciphertext, but only someone with the `write_key` can produce ciphertext
that decrypts to non-garbage with the `read_key`. (Read-only enforcement is "you cannot
encrypt valid content"; the server is not an authorisation point.)

### 7.4 Cryptographic shape

Existing derivation paths (per `team/roles/librarian/reality/vault/index.md`):

```
   Standard vault key (passphrase:vault_id):
     read_key      = PBKDF2(passphrase, salt='sg-vault-v1:{vault_id}',        600k)
     write_key     = PBKDF2(passphrase, salt='sg-vault-v1:write:{vault_id}',  600k)
     structure_key = HKDF(read_key, info=b'sg-vault-v1:structure-key')

   Simple token (word-word-NNNN):
     aes_key       = PBKDF2(token, salt=b'sgraph-send-v1', 600k)
     read_key      = HKDF(aes_key, info=b'vault-read-key')
     write_key     = HKDF(aes_key, info=b'vault-write-key')
     structure_key = HKDF(read_key, info=b'sg-vault-v1:structure-key')
```

`read_key` is already a 32-byte AES key. The new credential **is** that material.

```
   Read-only credential (NEW):
     vault-key     = friendly encoding of vault_id (12 bytes, base32 or word-decorated)
     read-only-key = friendly encoding of read_key (32 bytes, base32 or word-list)
     structure_key = HKDF(read_key, info=b'sg-vault-v1:structure-key')   ← derivable
     write_key     = (cannot be derived — that's the whole point)
```

A vault opened with this credential has `_writeKey = null` and `_passphrase = null`. The
existing `dataSource.writable` flag (already false in this case) gates all write UI in
`vault-browse-edit.js` — so most of the UI work is **already done**.

### 7.5 How the user produces a read-only credential

Two surfaces:

1. **`<vault-settings>` panel** — a new "Share read-only" button next to the existing share
   actions. Renders the current vault's `vault-key` + `read-only-key` pair, with copy buttons.
   The vault settings panel already has the `vault` instance with `_readKey` exposed.
2. **`sgit share-readonly` (CLI)** — emits the same pair. Out of scope for this UI session
   but worth noting; the CLI implementation goes in `SGit-AI/SGit-AI__CLI`, not here.

### 7.6 How the user opens a read-only credential

The landing page input field accepts pasted text. A new format check is added:

```
   Input parsing precedence (NEW order):
     1. /^[a-z]+-[a-z]+-\d{4}$/                → simple token        (read+write)
     2. /^[^:\s]+:[a-f0-9]{12}$/               → passphrase:vault_id (read+write)
     3. /^vault-[\w-]+\s+[a-z0-9-]{30,}$/      → vault-key read-only-key  (read-only) ← NEW
        (or whatever encoding lands)
     4. (else) try simple token interpretation as a fallback
```

The exact regex depends on the chosen encoding for `read-only-key`. Decide that first; the
UI work follows.

A new code path `SGVault.openReadOnly(sgSend, vaultKey, readOnlyKey)` constructs an `SGVault`
instance with `_readKey` populated from the credential, `_writeKey = null`, fetches the
encrypted ref + branch index + tree, and returns the vault. The existing `_loadTreeFromCommit`
and `_objectStore.read` paths already work with just `_readKey`.

### 7.7 UI state changes for read-only vaults

Most write UI is already gated by `dataSource.writable`. Audit the gate — anything not gated
must be:

| Surface | Read-only treatment |
|---|---|
| `<vault-header>` Push / Pull / Refresh / Upload buttons | Push hidden (write-only). Pull hidden (writes a new clone ref). Refresh visible. Upload hidden. |
| `<vault-header>` "Open or Create Vault" relabel | Visible (always). |
| `vault-browse-edit` Edit / Save / Cancel / Delete / Rename / New File / New Folder / Upload | All hidden (already gated by `dataSource.writable`). |
| `vault-browse-edit` HTML editor | Hidden. Full-Screen / App Mode / Copy / SGit Data remain. |
| `<vault-settings>` "Share read-only" | Hidden (you cannot re-share what you only read). |
| `<vault-settings>` Edit vault name | Hidden. |
| `<vault-auth>` access-key banner | Hidden — access key is for write licensing, irrelevant here. |
| `<vault-shell>` "Lock vault" | Visible — clears LS, returns to landing. |
| `<vault-shell>` sync notices ("ahead/behind/diverged") | Hidden — read-only clients don't have a clone ref. |
| `<vault-status-bar>` write counts | Hidden. |

Rule of thumb: **any UI that calls a method on `_writeKey` must be hidden.** Search
`_writeKey` in `_common/js/lib/sg-vault/` to enumerate exactly what's at risk.

### 7.8 What the vault-browser-edit gates already do

`vault-browse-edit.js#_renderFileContent` line 52:
`if (!this.dataSource || !this.dataSource.writable) return;`

This already returns before adding Edit / Save / Cancel / Copy. Good. The App Mode button,
Full Screen, SGit Data, and View Source render unconditionally above this line — those are
read-only-safe. Audit existing reads of `dataSource.writable` to confirm coverage.

### 8.2 v0.2.4/v0.2.5 — read-only keys

**Decide first**, in this order:

1. **Encoding** of the `read-only-key` (32 bytes). Candidates: base32 (52 chars), word-list
   chunks (e.g. 4 words + 4 digits + 4 words = ~120 bits friendly), or a hybrid. The simple
   token convention is "human-pasteable, not for hand-typing"; the read-only-key should be
   the same.
2. **Encoding** of the `vault-key` (12 bytes). Candidates: bare hex (12 chars), word-decorated
   hex (`vault-apple-river-a1b2c3d4e5f6`), or word-only (12 bytes ≈ 9 words).
3. **Pair separator**. Candidates: whitespace (`vault-key read-only-key`), slash
   (`vault-key/read-only-key`), pipe (already used for deep-link path — avoid). Whitespace
   feels safest because it also matches "paste both lines from an email."

**Files to change** for the open path:

- `_common/js/lib/sg-vault/sg-vault.js` — add `SGVault.openReadOnly(sgSend, vaultKey, roKey)`.
- `_common/js/lib/sg-vault/sg-vault-crypto.js` — add `decodeReadOnlyKey(roKey)` /
  `decodeVaultKey(vaultKey)` helpers.
- `_common/js/components/vault-entry/vault-entry.js` — accept the new format in the input,
  detect via the regex precedence in §7.6, route to `SGVault.openReadOnly`.
- `_common/js/components/vault-shell/vault-shell.js` — pass `writable: false` to
  `VaultDataSource` (already does, since `_accessKey` is empty).
- `_common/js/adapters/vault-data-source.js` — confirm `writable` is `false` when the vault's
  `_writeKey` is null. The current logic uses access-key presence; needs an additional check.

**Files to change** for the share path:

- `_common/js/components/vault-settings/vault-settings.js` — add "Share read-only" UI block
  that renders the current vault's `vault-key` and `read-only-key` (encoded from
  `vault._vaultId` and `vault._readKey`) with copy buttons.

**UI gating audit:** §7.7 lists everything to check. Most surfaces already gate on
`dataSource.writable`. The audit is to confirm — search for code that calls things like
`vault.push`, `vault.merge`, `vault.addFile`, `vault.deleteFile`, etc. and ensure they're all

## 12 · Open questions for Dinis

1. **Read-only-key encoding format.** Word-list, base32, or hybrid? Decision blocks the
   read-only feature.
2. **`vault-key` terminology.** "vault-key" for `vault_id` collides with current usage where
   "vault key" means the simple token. Should we rename current "vault key" → "vault token"
   and reserve "vault-key" for the new read-only credential's first half?
3. **Should `/en-gb/vault/peek` require the user to confirm before showing the current vault's
   token?** Anyone with access to the device can already see it via DevTools, but a "Show"
   click might be friendlier than displaying it by default.
4. **Should `/en-gb/` ALSO redirect to `/en-gb/vault` when LS has a key?** Under the strict
   reading of principle 5, no — `/en-gb/` doesn't read LS at all. But this means a user with
   a vault loaded who clicks the "Open Vault" link in the header arrives at landing, not vault.
   Is that the intended UX or should there be an exception?
5. **Read-only credential expiry.** Should the credential be revocable? Without a server-side
   authority, "revocation" means "rotate the read key, re-encrypt everything." Probably
   out-of-scope but worth flagging.
6. **`sg-vault-recent` migration.** Quietly union the two old lists on first read, or expose a
   one-time migration prompt?
