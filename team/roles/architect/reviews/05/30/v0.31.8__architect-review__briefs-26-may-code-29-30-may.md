## 1. Vault Chat Architecture Assessment (docs 505–506)

### Design Decision: Vault Chat = Standard App Iframe

The 05/26 brief confirms the key architectural decision: **Vault Chat is an app iframe over the same `window.sg` bridge**. This is not a new protocol — it is a different HTML payload running at null-origin, accessing the vault via the existing SecureChannel→kernel→VFS handlers path.

**Architectural soundness: HIGH.** This means:
- Phase 3 security gate (null-origin app frames) applies to Vault Chat automatically.
- Phase 4 AppFrameBootstrap builds the chat iframe the same way as any app iframe.
- The entire ViV B5/B6/B7/B10 invariant suite (credential tiers, monitor mode, custody gate) protects Vault Chat from day one.
- No new bridge verbs are needed for an initial version.

**Open design question:** Does the initial Vault Chat need `sg.vfs.*` only (read/write vault files for context) or does it also need `sg.llm.*` (a new LLM calling surface in the bridge)? The brief says the LLM call is made from inside the iframe (the app itself calls an LLM API). This means LLM calls are outbound network traffic from the iframe — the bridge does not intermediate them. This is simpler and avoids adding sensitive API keys to the kernel flow.

### The Two-Filesystem Model

| Filesystem | Owner | Persistence | Purpose |
|-----------|-------|-------------|---------|
| Vault FS | kernel (via SecureChannel) | Permanent (encrypted vault) | Source documents, history snapshots, published outputs |
| VFS | chat iframe (in-memory) | Ephemeral; optionally synced to vault | LLM working memory, context chunks, extracted facts |

**Concern:** The VFS sync-to-vault path needs a clear sync trigger. Options:
1. Explicit: user action ("Save VFS to vault")
2. Periodic: every N seconds
3. Event-driven: at end of each LLM response

The commit queue (doc 509) solves the explosion problem for option 3. The sync format (one file per context chunk vs one JSON blob) affects vault clutter and search. **Recommended:** one file per conceptual unit (message/fact/consolidation) under `.vfs/` path prefix; excluded from normal vault display but accessible via bridge.

### Sidecar LLMs (doc 506)

Running multiple LLMs in parallel for curation, security checks, and consolidation is architecturally viable. The concern is cost and latency. **Recommended approach:**
1. Start with a single LLM (main chat) and a self-pruning tool.
2. Add sidecar LLMs as configurable extensions, disabled by default.
3. Prompt-injection security check sidecar is the highest-priority one (given the vault contains attacker-controlled content).

## 2. Commit Queue Design Assessment (doc 509)

**Problem:** Vault Chat writing one file per LLM response (VFS sync) creates O(N_responses) commits. At 10s/response, that's ~360 commits/hour. Each commit triggers a full vault encrypt+push cycle.

**Solution:** Timer-windowed batch on the vault mothership.

**Architectural soundness: HIGH.** The queue correctly lives on vault-shell (the mothership), not in the app iframe. The iframe sends VFS writes via the sg.* bridge; vault-shell accumulates them and drains at window expiry. This is:
- **Transparent to the iframe:** the iframe's `sg.vfs.write()` calls succeed immediately (staged); the iframe doesn't know about batching.
- **Consistent with the existing commit model:** vault-shell already owns the commit/push cycle.
- **Configurable:** zero window = current behaviour (regression-safe).

**Open design question (OQ-commit-queue-placement-1):** Does the queue apply to CompositeDataSource child vault writes (sub-vaults) or only the root vault? Sub-vault writes go through a different path (child VaultDataSource). The queue should probably apply only to root vault writes in v1 — sub-vault commit cycles are independent.

**Staging area visibility:** The brief proposes a "staging" panel showing pending files. This aligns with the Sub-vaults pane concept (debug sidebar on /vault now exists as a right-side panel). The queue panel fits naturally as an additional tab in the vault debug sidebar.

## 3. ViV Kernel Model Brief Assessment (doc 507)

This brief reinforces the architecture already shipped in Phase 1–3. Key design decisions confirmed:
- **Directional trust** (parent grants down, child cannot reach up) — correct. Prevents escalation.
- **PKI on every inter-vault message** — correct. Provides tamper-detection for free and catches misrouting bugs.
- **Broker as sidecar** — correct. Keeps mediation code separate from the kernel's storage path.
- **Monitoring vs isolation** — VivMonitor.CLOSED is the safe default (B7, shipped). OPT_IN only when debugging.

One observation: the brief mentions a "vault-in-vaults visualization page" where vaults can be opened side by side with broker logs visible. This is **P-261 territory** — currently only the Audit tab in /app debug pane exists (Phase 5.1 shipped). A dedicated standalone page is still PROPOSED because broker logs are in-memory per-document and a cross-document page cannot read them. The correct implementation is to surface aggregation within the /app page (as done) rather than a separate URL.

## 4. Code Architecture Audit (v0.31.3 → v0.31.8)

### Phase 3: Security Gate Closed

The null-origin flip (`allow-same-origin` dropped from all 4 iframe mount sites) is the most architecturally significant change in this period. **SEC-VIV-001 is closed.** App code can no longer:
- Read `localStorage` containing vault keys
- Reach `window.parent` DOM
- Fetch vault paths directly

The only remaining vector for a malicious app to reach vault state is through the sg.* bridge — which is now the full enforcement surface (AppPermissions, credential tiers, custody gate, broker log).

**Residual architectural note:** The Phase 3 completion brief (commit 1b27f17, "docs(viv): brief for next session — Phases 4 & 5 + honest Phase 3 record") flags that `sg-app-banner.js`'s `onerror` capture is now dead for null-origin frames (same-origin reach impossible). The Phase 4 error re-spec (d9f20f3) replaces this with self-reporting from inside the null-origin frame. This is the correct fix — the frame self-reports via `postMessage`, the parent receives it as an `sg-app-error` event. Clean separation of concerns.

### Phase 4: AppFrameBootstrap (Option A)

AppFrameBootstrap unifies the four srcdoc templates into a single pure, DOM-free, testable builder. This is architectural housekeeping with no functional change — all four mount paths still use the postMessage `sg.*` bridge (not SecureChannel). Phase 4 "Option B" (promote app frames to SecureChannel) remains PROPOSED.

**Implication for Vault Chat:** Vault Chat will use `AppFrameBootstrap.build({kind: 'app', …})` like any other app iframe. No special casing needed.

### Phase 5.1: VivAuditView

The cross-kernel audit aggregation core is consent-honest by design:
- CLOSED children contribute mount rows but NO log rows (no fabricated audit data)
- Only `monitor=top|opt-in` sources expose a log
- Grandchildren are "unreachable by design" — this prevents a single collector from becoming a surveillance chokepoint

**Open architecture decision (OQ-viv-phase5-scheduling-1):** The standalone cross-document vault-in-vaults audit page CANNOT read in-memory broker logs from other documents. The Audit tab in /app works because app-shell has a reference to KernelParent. A dedicated vaults page would need to poll each open vault's app-shell via some mechanism. This is non-trivial and deferred.

## 5. Summary Assessment

| Item | Architectural Soundness | Key Flag |
|------|------------------------|----------|
| Vault Chat = app iframe | ✅ HIGH | No new protocols needed; builds on Phase 3 security |
| VFS as client-side memory | ✅ HIGH | Needs clear sync trigger and path convention |
| Commit queue on mothership | ✅ HIGH | Zero-window regression-safe; sub-vault placement needs decision |
| Sidecar LLMs | ⚠️ MEDIUM | Cost/latency risk; start disabled, enable incrementally |
| Phase 3 security gate | ✅ SHIPPED | SEC-VIV-001 closed |
| AppFrameBootstrap Option A | ✅ SHIPPED | Correct refactor; Option B (kernel promotion) deferred |
| VivAuditView core + Audit tab | ✅ SHIPPED | Consent-honest; standalone page path blocked by design |

**Most important open decision:** `OQ-vault-chat-arch-1` — confirm that the initial Vault Chat is a standard app iframe with no new bridge verbs. If yes, the implementation path is: write a self-contained HTML app that (a) calls an LLM API directly, (b) reads/writes vault files via existing `sg.vfs.*` verbs, (c) manages VFS in-memory. The commit queue and VFS-vault sync are then the only new pieces to build.
