## Executive Summary

This batch is primarily research and strategic analysis rather than new feature specifications.
It contains no new API contracts, no new data models, and no direct implementation requests.
Its architectural significance lies in three areas: (1) a substrate decision that changes the
Firecracker posture from "deferred" to "prototype now"; (2) a confidential-computing architecture
(Nitro Enclaves) that adds a fourth boundary to the zero-knowledge contract; and (3) a strategic
clarification of how AgentCore fits in the stack (substrate-not-competitor). Each carries
architectural implications for existing work in progress, noted below.

## Architectural Assessments

### 1. Firecracker on C8i — Substrate Decision (Briefs 408, 411, 412)

**Soundness: HIGH — with important implementation caveats**

The February 2026 nested-virt announcement on C8i/M8i/R8i is a genuine external fact that
changes the architecture. Prior to this, Firecracker required `.metal` EC2 ($3+/hr); now
c8i-flex.large is viable at ~$0.089/hr. The strategic brief correctly identifies this as a
"prototype selectively now" signal rather than a "ship to production" signal.

**Architecturally correct positions from these briefs:**

The performance research (brief 411) settles an important question: cold-start Docker is
measurably faster than cold-boot Firecracker on nested-virt C8i (~150ms vs ~125-200ms with
nested-virt overhead). The win for Firecracker is snapshot-restore, not cold-start. This
correctly limits the Firecracker use cases to:

- AI agent code execution sandboxes (isolation requirement, independent of startup speed)
- Snapshot-fast Playwright fleets (snapshot-restore dramatically beats container cold-start)
- Vault-attached compute with snapshots (sub-second restore from vault-ready state)

For the container hosts primitive (doc 403 from prior batch), the performance research clarifies
the default substrate: **Docker/Podman containers are the right default** for long-running
vault hosting workloads. Firecracker is an optional backend for the three use cases above.

**Podman as default container runtime:** The research is clear — Podman has no daemon (15-20%
less memory at scale), rootless-by-default security, and OCI compatibility. This should be
the default for the container hosts primitive. The Architect formally confirms this recommendation
pending the real benchmark (P-107).

**Nested-virt performance tax:** Important caveat for implementation. A ~10% CPU performance tax
applies to Firecracker microVMs on nested-virt C8i vs bare-metal Firecracker. For I/O-heavy
workloads the gap is larger. This is fine for experimentation and small-scale production; flag it
in the container hosts design document so it's not a surprise in benchmarks.

**Concern — orchestration gap:** The strategy brief calls for Firecracker as a "first-class
substrate option" in the container hosts primitive. The orchestration gap between "container
hosts running Docker" (what is proposed) and "container hosts optionally running Firecracker
microVMs" is non-trivial. The placement lambda (brief 403) needs a substrate-selection layer.
This is real engineering work beyond the PoC; scope it separately.

**Concern — fourth density mode:** Brief 411 introduces a fourth vault-hosting density mode
(multi-microVM per EC2) positioned between dedicated EC2 and multi-container per EC2 on the
isolation axis. This is architecturally sound and fills a real gap. However, it increases the
density mode surface from three to four, which has implications for the Vault Synchronizer's
`--density` flag and the routing layer design. Update the density modes brief (doc 385 from
prior batch) to include this mode before implementation.

### 2. Nitro Enclaves — Fourth ZK Boundary (Briefs 409, 414)

**Soundness: HIGH — significant new architectural layer**

The zero-knowledge contract currently has three boundaries: client browser (plaintext),
network (ciphertext only), S3 (ciphertext only). Nitro Enclaves add a legitimate fourth
boundary: plaintext can exist server-side but only inside an attested enclave running
code the customer can verify. This is architecturally defensible and is the standard AWS
pattern for confidential compute.

**The three-tier key architecture is sound:**

```
Tier 1: Customer vault key (client-side only) — unchanged from today
Tier 2: Vault decryption key inside enclave (customer encrypts to enclave's ephemeral pubkey)
Tier 3: Service keys via KMS + PCR-based policy (only verifiable enclave can use)
```

This composes cleanly with the existing architecture. No changes to the current encryption
model are required for Tier 1. Tiers 2 and 3 are additive layers.

**The seven use cases are architecturally plausible:**

All seven use cases (server-side search, vault AI inference, multi-party computation, verifiable
operations, server-side signing, confidential credential manager, async vault sharing) follow
the same core pattern: customer encrypts sensitive material to enclave's ephemeral public key
from a verified attestation document → enclave processes in memory → returns result encrypted
to customer → enclave terminates. This single pattern has many applications; the substrate
work (P-116 — the vault-enclave EIF) is the foundation that unlocks all seven.

**Prioritisation recommendation:**

Server-side vault search (P-109) is the highest-priority first use case because:
- It is the most-requested missing feature
- The pattern is CPU-bound, low-I/O (ideal for enclaves)
- It has a clear customer demand signal
- The engineering is contained: one EIF, one vsock API, one KMS policy

AI inference (P-110) is second — it unlocks LLM features for regulated customers but adds
a third-party trust boundary (the LLM provider sees plaintext), which requires careful
customer communication.

**Concern — EC2-only substrate:** Enclaves require a dedicated EC2 parent. This means
enclave-protected workloads cannot use Lambda, Fargate, or AgentCore Runtime as the hosting
substrate. For latency-sensitive or high-burst workloads, this is a design constraint. The
Architect must specify the connection between the enclave host EC2 and the rest of the
request flow (API Gateway / Lambda URL forwarding to the enclave host? Direct EC2 URL?).

**Concern — session recovery:** Enclaves have no persistent state. If the enclave dies
mid-session, the customer's vault key (held in enclave memory) is lost and the session must
re-attest. The design must include a graceful session recovery flow. The vault itself is safe
(encrypted in S3), but the session state is lost. This needs a clear customer-facing UX
(retry prompt) and a server-side keepalive / heartbeat model.

**Concern — open-source commitment:** The strategy brief correctly identifies that the
customer-facing position requires open-source enclave images. This means the build pipeline
(EIF → PCR measurements → published values) must be deterministic and auditable. This is
a real DevOps commitment (signed releases, published PCR values) that must be scoped before
making customer-facing claims.

**Concern — composability with AgentCore:** The brief notes that AgentCore Runtime uses
Firecracker internally (per-session microVM isolation, tenant-from-tenant) while Nitro
Enclaves provide customer-from-platform isolation. These are correctly positioned as
complementary, not competing. For high-trust agentic workflows, the architecture would be:
AgentCore Runtime hosts the agent (tenant isolation), plus a Nitro Enclave on the parent EC2
handles vault key operations (platform operator isolation). This composability needs to be
specified in the architecture design for vault AI inference (P-110).

### 3. AgentCore Layering — Build Burden Reduction (Briefs 410, 413)

**Soundness: HIGH — important strategic clarification**

The use/leverage/resell taxonomy is architecturally useful because it gives clear rules for
where to invest engineering effort. The "use directly" category reduces the build list:

- AgentCore Code Interpreter (sandboxed code execution — was on our build list)
- AgentCore Browser (cloud browser — was being evaluated as Neko replacement)
- AgentCore Memory short-term (in-session memory)
- AgentCore Identity (OAuth tokens and pre-authorised user consent)
- AgentCore Bidirectional streaming (voice agents)

**This is a significant scope reduction.** These are not trivial features to build; offloading
them to AgentCore saves months of engineering. The freed time should go to vault grounding,
the credential manager, and the manager vault patterns.

**The "leverage with a wrapper" category** identifies the right boundary: AgentCore capabilities
where SG distinctiveness comes from vault grounding (Memory → vault-grounded LTM, Gateway →
vault-stored tool manifests, Observability → unified session with vault histories, Evaluations
→ eval results as vault commits, Policy → Cedar policies in vault, Agent Registry → agents
as manager vault entries). This is consistent with the existing vault-as-system-of-record pattern.

**Architectural concern — pricing passthrough:** The AgentCore resell products (P-120 through
P-124) require the pre-auth micropayments substrate (docs 396 from prior batch) to handle
AgentCore's consumption-based billing passing through to customers. The architecture needs a
line item in the micropayment ledger for each AgentCore service consumed per customer session.
This must be designed before the first resell product is shipped.

**Architectural concern — region alignment:** AgentCore service availability varies by region.
The container hosts primitive (doc 403) is multi-region. The Architect must specify how region
mismatches are handled when an agent running in our container hosts needs to invoke an
AgentCore service only available in us-east-1.

**I/O-wait-free pricing:** The pricing model is the most distinctive AgentCore property — CPU
billed only for actual cycles consumed, not I/O-wait time. For our agent workloads (which spend
30-70% of session time waiting on LLM responses), this is meaningfully cheaper than pre-allocated
compute. The Architect should note this in cost modelling for any agent-workload pricing.

### 4. USDC / Agentic Commerce (Brief 415)

**Soundness: HIGH — clean three-scenario analysis**

The three-scenario framework is architecturally sound:

- Scenario 1 (customer pre-pay, internal accounting): no USDC needed, Stripe-fronted stays
- Scenario 2 (internal agent budgets): no USDC needed; internal ledger is sufficient; design
  for USDC-backability later (the ledger should treat "wallet" as an interface, not an
  implementation)
- Scenario 3 (cross-org transactions via x402): USDC is the right substrate

**Critical architectural note:** The brief correctly states that even with USDC, an internal
ledger is still required (user balances, provider budget tracking, usage metering, tax
reporting, reconciliation). USDC is a settlement rail for specific transaction patterns,
not a replacement for the application ledger.

**Per-agent-wallet pattern:** The brief describes per-agent wallets (each agent has real USDC)
as an eventual architecture, not an immediate one. This is correct. The Architect should
design the current internal-accounting agent-budget model (Scenario 2) with a clear
interface boundary between "what is an agent budget" and "how is it settled" so the
implementation can be USDC-backed later without architectural rework.

**Architectural note — the x402 receiver (P-126):** Exposing one of our services as an x402
micropayment receiver is a real protocol integration task. The service needs to:
(a) respond with HTTP 402 + payment request headers when accessed without payment,
(b) validate incoming x402 payment proofs,
(c) emit the transaction record to the observability session and internal ledger.
This is a well-defined integration but it is not trivial. It belongs in a separate dev brief.

### 5. Observability Addendum (Brief 407)

**Soundness: HIGH — important context, no new architecture**

The addendum confirms that two data pipelines are already running (CloudFront→Firehose→S3
and CloudTrail→S3) and producing data that is currently unread. The three-layer framing
(infra observability, product analytics, customer-facing reporting) is the right taxonomy.

**Architectural note — layer 2 boundary:** The addendum names product analytics (vault clones,
downloads, conversion funnels) as a distinct layer from infra observability. These are different
query shapes (aggregate behavioural queries vs operational diagnostic queries) but both sit
on the same S3/CloudWatch substrate. The Architect should specify: is the unified observability
session the query surface for both layers, or does layer 2 get a separate surface? The addendum
implies "same substrate, different queries" which is the right answer — but this needs to
be explicit in the architecture docs.

**Architectural note — SG billing as a source:** SG billing (pre-auth micropayments emitting
events, distinct from AWS billing) must be a first-class source in the observability session.
The source contract pattern from brief 398 (prior batch) needs a SG billing source defined
alongside the CloudWatch / CloudTrail / S3 sources.

## Cross-Brief Integration Notes

The briefs from 05/14–05/17 (prior batch) and 05/15 (this batch) form a coherent whole:

```
Substrate spectrum:
  Laptop → Lambda → AgentCore Runtime → Fargate → Container Hosts → Dedicated EC2
  (+ Firecracker option on C8i/M8i/R8i for specific use cases)
  (+ Nitro Enclaves tier for cryptographic isolation from platform operator)

Vault as system-of-record for all substrates:
  AgentCore Memory → vault-grounded LTM
  Bedrock sessions → vault-committed
  Eval results → vault-committed
  Cedar policies → vault-stored
  Agent definitions → vault-stored (manager vault)

Payments substrate across substrates:
  Customer-facing: Stripe pre-auth + micropayment ledger
  Inter-org: AgentCore Payments + x402 + USDC backend treasury
  Agent budgets: internal ledger (USDC-backable interface)
```

The architecture is now the most coherent it has been since the project began. No breaking
inconsistencies between the three batches (05/14, 05/17, 05/15). The main gap is the
Firecracker orchestration layer — it is named but not yet specified.
