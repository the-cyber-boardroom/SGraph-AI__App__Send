## Executive Summary

These 22 briefs represent a cohesive and significant architectural evolution in three layers:

1. **Artefact layer (05/30):** Vault-per-standard makes compliance documents into semantic graph artefacts — a convergence of the document-to-graph pipeline (P-281), public-preview-with-read-only-key (P-282), and the vulnerability threat-intel vault as the first demonstration (P-283).

2. **Content publishing engine (05/30–05/31):** The website becomes a living knowledge base controlled by agents via per-section vaults, a VIV parent, and a vault CI pipeline (P-284, P-285). Industry pages embed real vault examples (P-286). Every page serves a semantic graph for machines via Lambda@Edge (P-287).

3. **Partner ecosystem + skills creator economy (06/01):** Seven partner integrations map onto existing SG/Vault primitives (hosting, execution, live backend, harness interop, video, skills graph, channel). A vertically integrated skills creator economy (P-295–P-299) builds on top.

The architectural signal is strong: all partner integrations converge on skills/MCP/provenance — exactly the primitives SG/Vault has already committed to. This is external validation of the bet.

## Architectural Decisions Required

### 1. Document-to-Graph Pipeline Design (P-281) — Priority: HIGH

The 05/30 arch-brief specifies a universal pipeline:
```
document → structured version → visualisations → semantic graph (ontologies/taxonomies)
         → validate → feedback
```

**Key architectural questions:**

| Question | Implication |
|----------|-------------|
| Where does the pipeline run? | Client-side (browser WASM), SG/Compute backend, or Daytona sandbox (P-289)? |
| How does provenance attach? | Every transformation step must record model + version + timestamp in the vault — aligns with existing vault commit model |
| What is the fractal ontology format? | Section-level ontologies connect to a top-level one — needs a schema that supports cross-vault references |
| Intersection vaults (company-customised)? | VIV already supports this — the company vault holds a mounted section of the standard artefact vault |

**Recommendation:** Design the pipeline as a series of vault commits (each stage = one commit) so the transformation is auditable and replayable. This reuses the existing vault versioning model and is directly compatible with the Daytona stateful sandbox model (P-289).

### 2. Agent-Controlled Website — Vault CI Pipeline Architecture (P-285) — Priority: HIGH

The 05/31 arch-brief proposes:
- Per-agent section vaults (ambassador owns main site, alchemist owns /investors)
- One website vault (VIV parent) containing all section vaults
- Four environment vaults: dev / main / QA / prod
- Vault-to-vault promotion as the CI pipeline release

**This is a fully specified architecture. Key decisions:**

| Component | Decision Needed |
|-----------|----------------|
| VIV parent topology | Does the website vault hold sub-vault references for each section? Or does each section push to a namespace within the parent? Sub-vault references (P-159/P-160) via `ro-links.json`/`rw-links.json` seem appropriate |
| Environment vault promotion | How does promotion work? Options: (A) `sgit push` with environment tag, (B) explicit vault-to-vault copy step, (C) share token from QA env consumed by prod env |
| QA sign-off gate | Who/what approves a QA→prod promotion? Needs a vault-level audit record of the sign-off |
| Prod isolation | Prod vault is on a separate server — needs a network/auth boundary that the existing `SecureChannel` + relay model can provide |

**Critical dependency:** P-285 depends on P-279 (kernel path unification). The VIV parent must be able to read/write all section vaults through a single kernel relay path. Implementing P-285 before P-279 means building on `CompositeDataSource` — the code path being retired.

**Recommendation:** Do not start P-285 implementation until P-279 is complete, or scope P-285 Phase 1 to a subset that only uses the existing single-vault model (one vault, content deployed at publish time, no live VIV sub-vault traversal).

### 3. Lambda@Edge Semantic Graph Serving (P-287) — Priority: MEDIUM

Per-page semantic knowledge graphs + references served edge-side for LLMs/crawlers. Already has a foundation: the existing Lambda@Edge llms.txt/.md renderer for static vault content.

**Architecture:**

```
Human request → CloudFront → Normal CDN cache (HTML/CSS/JS)
Crawler/LLM → CloudFront → Lambda@Edge → Derive + fetch semantic graph from vault
                                        → Inject JSON-LD / Turtle / triples into response
```

**Key questions:**

| Question | Implication |
|----------|-------------|
| Graph format? | JSON-LD (web-native, LLM-parseable, SEO-compatible) is the natural choice |
| Cache strategy? | Graphs invalidate on vault commit — CloudFront cache TTL must align with publish cadence |
| Link graph maintenance? | Broken-link detection needs a crawler job or a build-time check against the reference graph |
| Context-problem detection? | Needs LLM-mediated quality signal — fits the skills/eval model |

**This reuses the existing Lambda@Edge architecture exactly.** No new infra required. Main work is the graph extraction component (P-281 pipeline output) and the edge renderer.

### 4. Partner Integration Stack — Architecture Boundary Map (P-288–P-293) — Priority: MEDIUM

Seven partners, each occupying a different layer. This is not seven independent integrations — it is a layered stack:

```
Channel (Tavon P-293)                — delivers to end customers via SG/Vault
  ↓
Video (HeyGen P-292)                 — consumption format for vault content
  ↓
Skills Graph / Foundation (P-294)   — enables discovery + trust across the stack
  ↓
Harness Interop (Pi P-291)          — cross-ecosystem skills distribution
  ↓
Live Backend (Convex P-290)         — multi-user live layer for vault apps
  ↓
Execution (Daytona P-289)           — secure sandboxes for skill/code execution
  ↓
Hosting (Netlify P-288)             — vault-as-zip deployed to CDN edge
```

**Architectural principle:** Each layer has a clean integration boundary with the vault. The vault is the durable artefact at the centre. Partners are not alternatives — they layer.

**MVP recommendation for first partner integration:** Netlify (P-288) — mostly connecting existing pieces:
- Vault is already a zip (`sgit push` produces a zip)
- Netlify Build API accepts a zip
- Edge functions already match vault edge-rendering
- llms.txt/.md serving is already aligned
- Netlify MCP server means an agent can trigger deploys directly from vault chat (P-263)

**Effort estimate:** 1–2 days for the MVP (one vault deployed and live on Netlify). No new architecture needed — primarily a CI/CD wiring job.

### 5. Data Broker Iframe Interaction with VIV (P-271 + P-291) — Note

The data broker iframe (P-271, existing PROPOSED) and the Pi harness (P-291) both need to receive credentials. The data broker cannot receive OAuth redirects in a null-origin iframe. The architectural pattern (broker receives via top-level kernel → relay PKI-encrypted to broker) is already documented in P-271.

**For P-291 (Pi integration):** The same pattern applies — a Pi agent running in a sandbox needs credentials relayed securely. The data broker pattern is the correct model.

### 6. OpenRouter Broker Architecture (P-299) — Note on Vault-as-Secret-Manager

The 06/01 strategy brief makes an important architectural observation: the gap in a real company's solution was that vault keys were stored server-side-only (not zero-knowledge). SG/Vault's zero-knowledge storage is the architectural moat.

**P-299 design constraints:**

| Constraint | Architectural requirement |
|-----------|--------------------------|
| Zero-knowledge key storage | OpenRouter key stored in vault, never on SG/Vault server |
| Identity | Google/GitHub OAuth for user identification — requires the OAuth identity work (P-221) |
| Payment brokering | New component; vault + auth already exist |
| Ecosystem integration | Billing substrate must be reachable from vault apps (via `window.sg` bridge or a dedicated broker iframe) |

**Critical dependency:** P-299 requires OAuth identity (P-221, currently PROPOSED). This must be scheduled before or in parallel with P-299.
