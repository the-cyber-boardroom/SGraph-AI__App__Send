# Architect — CloudFront Immutable Object Bypass

**Version:** v0.29.1 | **Date:** 2026-06-03 | **Status:** PROPOSED — does not exist yet
**Context:** sgraph.ai website reads read-only immutable vault objects via `send.sgraph.ai`

---

## Problem

The sgraph.ai website renders vault content by fetching objects from
`send.sgraph.ai`. Objects with the `obj-cas-imm-` prefix are
**content-addressed and immutable** — the ID is the content hash, so the
content can never change for a given ID.

Current request path:

```
Browser → CloudFront (send.sgraph.ai) → Lambda@Edge → S3 → return encrypted blob
```

For `obj-cas-imm-*` objects, Lambda@Edge is a pure pass-through with no
business logic. But it still cold-starts (500ms+), and every request — even
for the exact same immutable blob — hits the full origin chain. The vault
performance harness (`v0.27.20__brief__vault-sgit-performance-harness.md`)
shows these reads dominate the request trace for folder expansion and page
rendering.

---

## Proposed Fix: Two Independent Improvements

### 1. CloudFront Behavior Bypass (eliminate Lambda entirely)

Add a new CloudFront **cache behavior** that matches paths like
`*/obj-cas-imm-*` and routes them directly to the S3 origin, skipping the
Lambda@Edge function entirely.

**Why this is safe:** immutable objects are content-addressed. The ID is a hash
of the content. By definition they cannot change — Lambda has zero legitimate
work to do for them. There is no auth decision to make (the object ID itself
is the credential — knowing the hash means you have the vault key or a share
token that gave you the hash).

| Setting | Value | Rationale |
|---------|-------|-----------|
| Path pattern | `*/obj-cas-imm-*` or `/bare/data/obj-cas-imm-*` | Matches the Memory-FS content-addressed object naming convention |
| Origin | S3 (same origin as current default behavior) | Direct S3 fetch, no Lambda |
| Viewer protocol | HTTPS only | Same as current |
| Lambda@Edge | **None** | The entire point — skip it |

### 2. CloudFront Edge Caching (eliminate S3 roundtrip after first hit)

For the same behavior, set aggressive caching headers:

| Setting | Value |
|---------|-------|
| Default TTL | `31536000` (1 year) |
| Max TTL | `31536000` |
| Min TTL | `31536000` |
| `Cache-Control` | `public, max-age=31536000, immutable` |
| Origin response headers | S3 can return whatever — CF behavior overrides with cache policy |

After the first request per CloudFront edge PoP, every subsequent fetch for
the same object returns instantly from CF memory — 0ms origin time.

### Combined Result

| Request | Before | After |
|---------|--------|-------|
| First-ever to this edge PoP | Lambda cold-start + S3 (~600ms) | S3 only (~50ms) |
| Subsequent (same edge) | Lambda cold-start + S3 (~600ms) | CloudFront cache hit (~1ms) |
| Subsequent (warm Lambda) | Lambda + S3 (~100ms) | CloudFront cache hit (~1ms) |

Cold starts become irrelevant. For the sgraph.ai website use case (repeatedly
reading the same vault pages), the improvement is dramatic — most reads after
the first visit will be cache hits.

---

## Security Analysis

**This bypass does NOT weaken security.**

Content-addressed immutable objects in the vault system are encrypted
ciphertext blobs. The object ID (`obj-cas-imm-{hash}`) is derived from the
content hash. To request an object, you must already know its hash — which
means you either:

1. Have the vault key (and decrypted the tree/commit chain to discover the
   blob hashes), or
2. Have a share token that resolved to a snapshot containing those hashes

The hash itself is the authorization. There is no additional auth check that
Lambda@Edge performs on these requests — it simply proxies to S3. Bypassing
Lambda removes a no-op, not a security gate.

The objects are encrypted ciphertext. Even if an attacker guesses a hash
(computationally infeasible for SHA-256), they get encrypted bytes with no key.

## What's Needed to Implement

The CloudFront distribution configuration for `send.sgraph.ai`. Specifically:

1. **Where is the CF distribution managed?** CDK, Terraform, CloudFormation
   template, or manual console config?
2. **The distribution ID** for `send.sgraph.ai` (not the website distribution
   `E2YZA5CZTJE62H`, which is for `sgraph.ai`)
3. **The S3 origin ID** already configured in the distribution
4. **Whether OAC (Origin Access Control) is used** for S3 — this determines
   whether the direct behavior needs the same OAC policy

If managed as IaC, the change is ~20 lines of CloudFormation/CDK to add a new
cache behavior with a path pattern + cache policy.

## Implementation Sketch (CloudFormation)

```yaml
CacheBehaviors:
  - PathPattern: '/bare/data/obj-cas-imm-*'
    TargetOriginId: S3-send-vault-origin      # same S3 origin as default
    ViewerProtocolPolicy: https-only
    CachePolicyId: !Ref ImmutableCachePolicy
    Compress: true
    # NO LambdaFunctionAssociations — that's the point

ImmutableCachePolicy:
  Type: AWS::CloudFront::CachePolicy
  Properties:
    CachePolicyConfig:
      Name: immutable-vault-objects
      DefaultTTL: 31536000
      MaxTTL: 31536000
      MinTTL: 31536000
      ParametersInCacheKeyAndForwardedToOrigin:
        EnableAcceptEncodingGzip: true
        EnableAcceptEncodingBrotli: true
        HeadersConfig:
          HeaderBehavior: none
        CookiesConfig:
          CookieBehavior: none
        QueryStringsConfig:
          QueryStringBehavior: none
```

## Interaction with url-rewrite.js

The existing CloudFront Function (`url-rewrite.js` on distribution
`E2YZA5CZTJE62H`) handles the **website** distribution — adding trailing
slashes and rewriting to `index.html`. It is a Viewer Request function on the
**sgraph.ai** distribution, not `send.sgraph.ai`.

The `send.sgraph.ai` distribution has its own behaviors (Lambda URL origin for
`/api/*`, S3 for vault data). The new `obj-cas-imm-*` behavior would be added
to the **send** distribution, not the website distribution.

The website's url-rewrite function does not need modification — it never sees
vault object paths. The browser's vault JS client fetches `obj-cas-imm-*`
objects directly from `send.sgraph.ai`, not `sgraph.ai`.

---

## Rollback

If unexpected issues arise, remove the cache behavior — requests fall back to
the default behavior which routes through Lambda@Edge as before. The cache
policy can stay (unused policies have no effect). CloudFront invalidation
(`/*`) clears any cached objects if needed, though for immutable objects this
should never be necessary.
