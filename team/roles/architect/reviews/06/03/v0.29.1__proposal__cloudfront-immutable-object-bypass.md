# CloudFront Immutable Object Bypass — Implementation Briefing

**Version:** v0.29.1 | **Date:** 2026-06-03 | **Status:** DEPLOYED to send.sgraph.ai (2026-06-03)
**Audience:** DevOps / anyone applying the three CF changes
**CF Function code:** `sgraph_ai_app_send/cloudfront/imm-object-rewrite.js`

---

## Problem

The sgraph.ai website renders vault content by fetching objects from
`send.sgraph.ai`. Every vault read goes through Lambda, even for immutable
content-addressed objects that Lambda has no business logic to perform on.

Current request path:

```
Browser
  → GET /api/vault/read/{vault_id}/bare/data/obj-cas-imm-{hash}
  → CloudFront (send.sgraph.ai)
  → /api/* behavior
  → Lambda URL origin (f47ufrcmasn463xdm...)
  → Lambda resolves S3 key via Storage__Paths.path__vault_payload()
  → S3 GetObject
  → return encrypted ciphertext blob
```

Lambda cold-starts cost 500ms+. Even warm, the roundtrip through Lambda adds
~100ms. Every request for the same immutable object re-executes the full
chain. The vault performance harness shows these reads dominate the trace for
folder expansion and page rendering.

---

## Solution: Three Changes

Bypass Lambda for immutable vault object reads using a CloudFront Function
that rewrites the API path to the S3 key. Requires exactly three changes to
the `send.sgraph.ai` CloudFront distribution:

1. **New CF Function** — validates and rewrites the URI
2. **New S3 origin** — the transfers bucket, wired with OAC
3. **New behavior** — routes immutable object reads to the S3 origin via the CF Function

No client changes. No Lambda changes. The client keeps requesting
`/api/vault/read/{vault_id}/bare/data/obj-cas-imm-{hash}` exactly as before.

## Current Behavior Table (send.sgraph.ai)

| Prec | Path pattern | Origin | Cache policy | Purpose |
|------|-------------|--------|-------------|---------|
| 0 | `/api/*` | Lambda URL (`f47ufrcmasn...`) | CachingDisabled | API routes → Lambda |
| 1 | `/mcp` | Lambda URL (`f47ufrcmasn...`) | CachingDisabled | MCP endpoint → Lambda |
| 2 | Default `(*)` | S3 static (`745506449035--sta...`) | CachingDisabled | UI static assets |

## Target Behavior Table

| Prec | Path pattern | Origin | Cache policy | CF Function | Purpose |
|------|-------------|--------|-------------|-------------|---------|
| **0** | **`/api/vault/read/*/bare/data/obj-cas-imm-*`** | **S3 transfers bucket** | **Immutable 1-year** | **`imm-object-rewrite`** | **Immutable vault objects → S3 direct** |
| 1 | `/api/*` | Lambda URL | CachingDisabled | — | All other API → Lambda |
| 2 | `/mcp` | Lambda URL | CachingDisabled | — | MCP → Lambda |
| 3 | Default `(*)` | S3 static | CachingDisabled | — | UI static assets |

The new behavior at Prec 0 is more specific than `/api/*` at Prec 1.
CloudFront evaluates behaviors top-to-bottom by specificity — the immutable
pattern matches first for these requests, everything else falls through to
Lambda as before.

## How the Request Flows (After)

```
Browser
  → GET /api/vault/read/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7
  → CloudFront (send.sgraph.ai)
  → behavior match: /api/vault/read/*/bare/data/obj-cas-imm-*  →  Prec 0
  → CF Function: imm-object-rewrite (Viewer Request)
      validates strict regex:
        vault_id = "0js1r0uj"   (lowercase alphanumeric, 8-24 chars)
        hash     = "00184ac7e9d7" (exactly 12 hex chars)
      rewrites URI to:
        /sg-send__data/sg-send-api__v1.0/shared/vault/0j/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7/payload
  → CloudFront cache lookup (rewritten URI as key)
      HIT  → return cached response (~1ms)
      MISS → S3 GetObject via OAC (~50ms) → cache for 1 year → return
```

## Change 1: CloudFront Function

**Source:** `sgraph_ai_app_send/cloudfront/imm-object-rewrite.js`

**What it does:**
- Matches the URI against a strict regex
- Extracts `vault_id` and `object_id`
- Rewrites URI to the S3 key path (mirroring `Storage__Paths.path__vault_payload()`)
- Returns 403 for anything that doesn't match

**Strict regex:**
```
/^\/api\/vault\/read\/([a-z0-9]{8,24})\/bare\/data\/(obj-cas-imm-[a-f0-9]{12})$/
```

This enforces:
- `vault_id`: lowercase alphanumeric, 8-24 chars (matches `VAULT_ID_PATTERN` in
  `Service__Vault__Pointer.py`)
- `hash`: exactly 12 lowercase hex chars (matches `SGVaultObjectStore.computeObjectId`:
  `hex(SHA256(ciphertext))[:12]`)
- No path traversal possible (character classes reject `.`, `/`, `..`)

**S3 key construction** (mirrors `Storage__Paths.py` line 33-34):
```
/{STORAGE__BASE}/{STORAGE__VERSION}/{STORAGE__DEPLOYMENT}/vault/{vault_id[:2]}/{vault_id}/bare/data/{object_id}/payload
```

With defaults:
```
/sg-send__data/sg-send-api__v1.0/shared/vault/{vault_id[:2]}/{vault_id}/bare/data/obj-cas-imm-{hash}/payload
```

**Deploy:**
```bash
# Create
aws cloudfront create-function \
  --name imm-object-rewrite-for__send-sgraph-ai \
  --function-config '{"Comment":"Rewrite immutable vault object reads to S3 key","Runtime":"cloudfront-js-2.0"}' \
  --function-code fileb://sgraph_ai_app_send/cloudfront/imm-object-rewrite.js

# Test (see Verification section below)

# Publish
aws cloudfront publish-function \
  --name imm-object-rewrite-for__send-sgraph-ai \
  --if-match <ETag-from-create>
```

## Change 2: New S3 Origin

Add the transfers bucket as a new origin on the `send.sgraph.ai` distribution.

| Setting | Value |
|---------|-------|
| Origin domain | `745506449035--sgraph-send-transfers--eu-west-2.s3.eu-west-2.amazonaws.com` |
| Origin path | *(empty)* |
| Origin ID | `S3-sgraph-send-transfers` (descriptive name) |
| Origin access | **Origin Access Control (OAC)** — create new OAC or reuse existing |
| Protocol | HTTPS only |

**OAC configuration:**
| Setting | Value |
|---------|-------|
| Name | `OAC-sgraph-send-transfers-immutable` |
| Signing behavior | Always |
| Signing protocol | SigV4 |
| Origin type | S3 |

**S3 bucket policy** — add a statement allowing this CF distribution to
`GetObject` on the transfers bucket:

```json
{
    "Sid": "AllowCloudFrontImmutableReads",
    "Effect": "Allow",
    "Principal": {
        "Service": "cloudfront.amazonaws.com"
    },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::745506449035--sgraph-send-transfers--eu-west-2/sg-send__data/*/vault/*/bare/data/obj-cas-imm-*/payload",
    "Condition": {
        "StringEquals": {
            "AWS:SourceArn": "arn:aws:cloudfront::745506449035:distribution/<SEND_DISTRIBUTION_ID>"
        }
    }
}
```

The `Resource` pattern restricts S3-level access to only `obj-cas-imm-*/payload`
paths. Even if the CF Function had a bug, S3 itself would reject requests for
manifests, tombstones, transfers, or any other object type.

## Change 3: New Behavior

Add a new behavior at the **highest precedence** (Prec 0):

| Setting | Value |
|---------|-------|
| Path pattern | `/api/vault/read/*/bare/data/obj-cas-imm-*` |
| Origin | `S3-sgraph-send-transfers` (the new origin from Change 2) |
| Viewer protocol policy | Redirect HTTP to HTTPS |
| Allowed HTTP methods | GET, HEAD |
| Cache policy | Custom: `immutable-vault-objects` (see below) |
| Origin request policy | None (OAC handles auth) |
| Response headers policy | Custom: add `Cache-Control` (see below) |
| Function associations | Viewer Request → `imm-object-rewrite-for__send-sgraph-ai` |
| Compress | Yes (gzip + brotli) |

**Cache policy: `immutable-vault-objects`**

| Setting | Value |
|---------|-------|
| Name | `immutable-vault-objects` |
| Default TTL | `31536000` (1 year) |
| Max TTL | `31536000` |
| Min TTL | `31536000` |
| Headers in cache key | None |
| Cookies in cache key | None |
| Query strings in cache key | None |
| Enable gzip | Yes |
| Enable brotli | Yes |

**Response headers policy** (optional but recommended):

Add a custom response headers policy that stamps:
```
Cache-Control: public, max-age=31536000, immutable
```

This tells the **browser** to cache the response for a year too — eliminating
even the CloudFront roundtrip on repeat visits from the same browser.

## Security Model — Three Independent Gates

### Gate 1: Behavior Path Pattern (coarse filter)

Only requests matching `/api/vault/read/*/bare/data/obj-cas-imm-*` reach
the S3 origin. Everything else goes to Lambda or the static S3 bucket.

**Attack: direct S3-path request**
```
GET /sg-send__data/sg-send-api__v1.0/shared/vault/0j/0js1r0uj/bare/data/obj-cas-imm-xyz/payload
```
This does NOT match `/api/vault/read/*/bare/data/obj-cas-imm-*`.
It falls through to Default `(*)` → static S3 bucket → file doesn't exist → 404.

The transfers S3 bucket is **only reachable** via Prec 0, and Prec 0 has the
CF Function gating it.

**Why this works:** CloudFront matches behaviors on the **original request URI**,
before any CF Function runs. The CF Function rewrites the URI, but CF does
NOT re-match behaviors. The origin was selected at match time and is locked in.

### Gate 2: CF Function Strict Regex (fine filter)

The CF Function validates:
- `vault_id` is `[a-z0-9]{8,24}` — no slashes, no dots, no traversal
- `object_id` is `obj-cas-imm-[a-f0-9]{12}` — exactly 12 hex chars
- Anything else → 403

The function can only produce S3 keys of the form:
```
/sg-send__data/sg-send-api__v1.0/shared/vault/{2 alnum}/{8-24 alnum}/bare/data/obj-cas-imm-{12 hex}/payload
```

It is structurally impossible for the function to read manifests, tombstones,
transfers, or any non-immutable object.

### Gate 3: S3 Bucket Policy (defense in depth)

The bucket policy restricts the OAC to `s3:GetObject` on paths matching
`*/obj-cas-imm-*/payload` only. Even if Gates 1 and 2 failed, S3 would
reject the request.

### Content is Encrypted Ciphertext

Even with all three gates bypassed (hypothetically), an attacker gets
encrypted bytes. The object ID is `hex(SHA256(ciphertext))[:12]` — guessing
a valid hash requires brute-forcing truncated SHA-256. And the decryption key
is never stored server-side.

## Performance Impact

| Scenario | Before | After |
|----------|--------|-------|
| First request to this edge PoP for this object | Lambda cold-start + S3 (~600ms) | S3 only via OAC (~50ms) |
| Repeat request (same edge, CF cache hit) | Lambda + S3 (~100-600ms) | CF cache hit (~1ms) |
| Repeat request (same browser, browser cache hit) | Lambda + S3 (~100-600ms) | No network request (~0ms) |

For the sgraph.ai website use case — loading the same vault pages repeatedly —
nearly all reads after the first visit will be browser or CF cache hits.

### 3. Monitor

After deployment, check CloudFront access logs or real-time metrics for:
- Cache hit ratio on the new behavior (should climb rapidly)
- 403 responses from the CF Function (malformed requests being rejected)
- No 5xx errors from the S3 origin (OAC misconfiguration would show as 403 from S3)

## Rollback

1. **Delete the behavior** — immutable object requests fall back to `/api/*`
   → Lambda. Service restored to pre-change state.
2. **CloudFront invalidation** is NOT needed — cached immutable objects are
   correct (same content Lambda would return). But `/*` invalidation is
   available if needed.
3. **The S3 origin and CF Function can stay** — unused origins and unpublished
   functions have no effect.

## Maintenance Notes

### When Storage__Paths changes

The S3 prefix in the CF Function (`sg-send__data/sg-send-api__v1.0/shared`)
mirrors `Storage__Paths.py` lines 11-15. If these values change (via env vars
or code), the CF Function must be updated to match. This is a deploy-time
configuration that rarely changes — the comment in `Storage__Paths.py` warns:
"changing these values for an existing deployment makes prior data unreadable."

### When object ID format changes

The 12-hex-char hash length comes from `SGVaultObjectStore.computeObjectId`:
`hex(SHA256(ciphertext))[:12]`. If this changes, update the regex in the CF
Function. The behavior path pattern (`/api/vault/read/*/bare/data/obj-cas-imm-*`)
uses wildcards and doesn't need updating for hash length changes.

### When vault_id format changes

The 8-24 alphanumeric constraint comes from `VAULT_ID_PATTERN` in
`Service__Vault__Pointer.py`. If this changes, update the CF Function regex.
