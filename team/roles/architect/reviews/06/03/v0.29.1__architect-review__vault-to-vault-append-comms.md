## 1. API Contract Quality

### 1.1 Endpoint design is clean and well-separated
**Finding:** The five endpoints (append, inbox list, inbox fetch, mark-processed, purge) map
precisely to the four capability tiers. Each endpoint has exactly one gate and one purpose.
The `Type_Safe` schema declarations follow the existing pattern (see
`sgraph_ai_app_send/lambda__user/schemas/Schema__Transfer.py` and siblings).
**Verdict:** Praise | **Severity:** N/A

### 1.2 Manifest file naming mismatch — "vault_pointer.json" vs "manifest.json"
**Finding:** The brief consistently refers to the manifest as `vault_pointer.json` (01 section 2, multiple
references). The actual codebase uses `manifest.json` everywhere:
- `Storage__Paths.py:28` — `path__vault_manifest` returns `…/manifest.json`
- `Service__Vault__Pointer.py:4` — file header: "manifest.json is the sole auth record"
- `Service__Vault__Pointer.py:152` — skips `manifest.json` in listings

This is a documentation error in the brief, not a code issue, but it will confuse implementers
who read the brief and then look at the code. The term `vault_pointer.json` appears to come
from the vault_pointer *service* name, not the actual file name.
**Verdict:** Concern | **Severity:** Important — fix in the brief before handing to Dev

### 1.3 Schema field type `Safe_Str` does not exist in the codebase
**Finding:** The brief's schemas use `Safe_Str` as a field type (e.g., `inbox: Safe_Str`,
`file_id: Safe_Str`). The codebase uses `Safe_Str__Id` (from
`osbot_utils.type_safe.primitives.domains.identifiers.safe_str.Safe_Str__Id`). There is no
bare `Safe_Str` import anywhere in the `sgraph_ai_app_send` package. The implementer needs to
know the correct qualified type.
**Verdict:** Concern | **Severity:** Minor — clarify in the brief or note that the implementer
should use the appropriate `Safe_Str__*` subtype

### 1.4 Status codes are well-chosen
**Finding:** `200` for success, `403` for gate failure, `413` for size, `507` for capacity.
The separation of `403` (auth) from `507` (capacity) is correct: the appender should not
learn why a write failed (bad token vs. full), but honest clients do need to distinguish
"back off" from "wrong credentials." The brief acknowledges the tension and handles it
correctly: body is always `ok:false`; the status code differentiates.

One subtlety: `507 Insufficient Storage` is an HTTP/WebDAV code that some proxies may
interpret specially. CloudFront and Lambda URLs pass it through, so this works in the current
stack, but note it for any future API Gateway migration.
**Verdict:** Praise with note | **Severity:** Note

### 1.5 POST for listing breaks REST convention but is justified
**Finding:** `POST /vault/inbox/{vault_id}` for listing is unconventional (GET with query
params is more standard). The brief justifies this: it takes options, is gate-checked via
header, and must not be cached. This is consistent with the existing pattern — the codebase
already uses `POST /vault/batch/{vault_id}` for similar reasons.
**Verdict:** Praise | **Severity:** N/A

### 1.6 Missing: new header constant definition
**Finding:** The brief introduces `x-sgraph-enum-key` as a new header for enum-gated
endpoints. The existing `user__config.py` defines header constants centrally
(`HEADER__SGRAPH_SEND__ACCESS_TOKEN`, `HEADER__SGRAPH_VAULT__WRITE_KEY`, etc.). The brief
should state that `HEADER__SGRAPH_VAULT__ENUM_KEY = 'x-sgraph-enum-key'` must be added to
`user__config.py`.
**Verdict:** Question | **Severity:** Minor — standard pattern, Dev should pick it up

## 2. Storage Layout Compatibility

### 2.1 Inbox path fits the existing tree
**Finding:** The existing storage path is `{ROOT}/vault/{vault_id[:2]}/{vault_id}/…` (see
`Storage__Paths.py:27-35`). The brief proposes `inbox/{append_token}/…` and
`processed/{append_token}/…` as subdirectories within this tree. Since vault files are already
stored at `{vault_prefix}/{file_id}/payload`, and `file_id` can be an arbitrary path, the
inbox files at `inbox/{token}/{epoch_ms}_{rand}.enc` fit cleanly. No conflict.
**Verdict:** Praise | **Severity:** N/A

### 2.2 But existing list_files() will expose inbox files
**Finding:** `Service__Vault__Pointer.list_files()` (line 140-163) lists all files under
`path__vault_prefix(vault_id)`, filtering only for files ending in `/payload` and skipping
`manifest.json` and `deleted.json`. Inbox files end in `.enc`, not `/payload`, so they will
be excluded by the current filter. This is correct by accident — the inbox files will not
appear in vault listings. However, if the implementer follows the existing pattern and wraps
inbox files in `{file_id}/payload`, they would leak into list results.

The brief should explicitly specify that inbox files use a **different naming convention**
(`.enc` suffix, no `/payload` wrapper) and note that `list_files` naturally excludes them.
**Verdict:** Concern | **Severity:** Important — document the naming convention's interaction
with the existing list filter to avoid accidental exposure

### 2.3 No conflict with CAS paths
**Finding:** Existing CAS objects live at `bare/data/obj-cas-imm-*`, `bare/keys/key-rnd-imm-*`,
`bare/refs/`, and `bare/indexes/`. The proposed `inbox/` and `processed/` prefixes are new
top-level folders within the vault prefix, with no overlap.
**Verdict:** Praise | **Severity:** N/A

### 2.4 Storage__Paths.py needs new path functions
**Finding:** The brief does not mention adding path helper functions to `Storage__Paths.py`.
Following the existing pattern (`path__vault_manifest`, `path__vault_tombstone`,
`path__vault_payload`, etc.), the implementation should add:
- `path__vault_inbox(vault_id, append_token, file_name)`
- `path__vault_processed(vault_id, append_token, file_name)`
- `path__vault_inbox_prefix(vault_id, append_token)`
**Verdict:** Question | **Severity:** Minor — implied by the storage layout, but should be
stated for completeness

## 3. Manifest Evolution

### 3.1 Backward compatibility is preserved
**Finding:** Adding `append_anchors` (list) and `enum_key_hash` (string) to `manifest.json`
is backward-compatible. Existing vaults that lack these fields will have no inbox capability
— they simply cannot receive appends. The code reads the manifest via `_load_manifest()`
which returns a plain dict from JSON. Missing keys produce `None`/`KeyError` on `.get()`,
which is the standard failure path. The existing `_check_vault_write_key()` only checks
`write_key_hash` and `status`, so new fields are invisible to existing code paths.
**Verdict:** Praise | **Severity:** N/A

### 3.2 Manifest update path needs careful handling
**Finding:** The brief says manifest changes are "cold-path" and last-write-wins is fine
(01 section 2). This is true for the current single-Lambda deployment. But the manifest now
carries three independent concerns: `write_key_hash` (ownership), `append_anchors`
(communication), and `enum_key_hash` (enumeration). A vault owner rotating their
`write_key_hash` with a read-modify-write could clobber a concurrent `append_anchors` update.

Currently `_ensure_manifest()` only writes on first creation and never updates. There is no
"update manifest" path in the existing code — all manifest fields are set at creation time.
The brief needs to specify **how** `append_anchors` and `enum_key_hash` are set. Options:
(a) at vault creation time (requires knowing the PKI keys upfront), or (b) via a new
"update manifest" endpoint (does not exist today).
**Verdict:** Concern | **Severity:** Blocking — the brief describes fields in the manifest
but does not specify the endpoint or mechanism to set them. This is a gap.

### 3.3 Manifest cache invalidation
**Finding:** `Service__Vault__Pointer._manifest_cache` caches the manifest for the Lambda
instance lifetime. If a new endpoint updates the manifest (to add `append_anchors`), the
cache must be invalidated. The existing `_ensure_manifest()` updates the cache on creation
(line 81). Any new update path must do the same.
**Verdict:** Question | **Severity:** Minor — standard pattern, but must be mentioned in
the implementation plan

## 4. Consistency with Existing Patterns

### 4.1 Gate mechanism follows the write_key_hash precedent
**Finding:** The existing pattern: client sends `write_key` in header; server computes
`SHA-256(write_key)` and compares to `manifest['write_key_hash']`. The proposal extends this
identically: client sends `enum_key` in header; server computes `H(enum_key)` and compares
to `manifest['enum_key_hash']`. Same for append_token: `H(presented_token)` checked against
`append_anchors`. This is exactly right.
**Verdict:** Praise | **Severity:** N/A

### 4.2 Route naming convention mismatch
**Finding:** Existing routes use the pattern `/vault/{operation}/{vault_id}` (e.g.,
`/vault/write/{vault_id}/{file_id}`, `/vault/read/{vault_id}/{file_id}`,
`/vault/destroy/{vault_id}`). The brief proposes `/vault/append/{vault_id}/{append_token}`
(fits), `/vault/inbox/{vault_id}` (fits), but `/vault/inbox/fetch/{vault_id}` and
`/vault/inbox/mark-processed/{vault_id}` and `/vault/inbox/purge/{vault_id}` introduce a
**two-level operation prefix** (`inbox/fetch`, `inbox/mark-processed`, `inbox/purge`).

The existing codebase has one precedent for this: `/vault/presigned/initiate/{vault_id}`,
`/vault/presigned/complete/{vault_id}`, `/vault/presigned/cancel/{vault_id}`. So the
`/vault/inbox/*` family follows the established `vault/{namespace}/{operation}` pattern.
**Verdict:** Praise | **Severity:** N/A

### 4.3 Double-gate pattern on purge is correct
**Finding:** The brief gates purge with both `x-sgraph-send-access-token` and `write_key`,
matching the existing double-gate on `/vault/write` and `/vault/destroy`. All other
destructive operations in the codebase use this exact pattern (see
`Routes__Vault__Pointer.py` lines 96-98 for write, 277-287 for destroy).
**Verdict:** Praise | **Severity:** N/A

### 4.4 Routes file placement
**Finding:** The brief says new endpoints live "alongside" `Routes__Vault__Pointer.py`. It
should specify: will this be a new `Routes__Vault__Inbox.py` file (preferred — separation
of concerns) or additions to the existing file? The existing file is already 338 lines with
13 route methods. Adding 5 more endpoints to it would make it unwieldy.
**Verdict:** Question | **Severity:** Minor — recommend a separate `Routes__Vault__Inbox.py`

## 5. Topology Feasibility

### 5.1 Topology A (inbox-in-target) is sound
**Finding:** Simple, minimal moving parts. One vault, two roles (appender, owner/drainer).
The inbox lives inside the target vault's storage tree. The gate model is clean: append-token
gates write, enum_key gates list/fetch/mark-processed, write_key gates purge. The drain loop
is a straightforward cursor-based pagination.
**Verdict:** Praise | **Severity:** N/A

### 5.2 Topology B (three-vault blind relay) is architecturally coherent but underspecified
**Finding:** The topology is sound in principle: the relay holds enum_key (shared inbox) and
append_token (each target), but no private key. It routes by folder name and re-appends.
However, the brief does not specify:
- **Relay identity and deployment:** Is this a Lambda function? A cron job? A separate
  service? What triggers the drain loop?
- **Relay failure and retry:** If the relay crashes mid-batch (after fetching but before
  mark-processed), the server-side idempotency handles it, but the relay needs its own
  cursor persistence. Where?
- **Relay credential provisioning:** How does the relay receive its enum_key and
  append_tokens? Manual config? Vault-based? This is not a Phase 0 concern but needs
  a placeholder answer.

The brief (03 section 4) does say this is Phase 6 and "prove Topology A first." The
underspecification is acceptable at this stage but should be flagged for the P6 brief.
**Verdict:** Concern | **Severity:** Minor — acceptable for Explorer phase, but flag for P6

### 5.3 Email bridge is a proof, not a feature
**Finding:** The brief correctly positions the MTA bridge as a theoretical proof that the
transport is content-blind, not a production feature. The metadata risks (SMTP envelopes,
hop logging) are honestly disclosed. This is well-handled.
**Verdict:** Praise | **Severity:** N/A

## 6. Missing Pieces and Gaps

### 6.1 No manifest update mechanism specified (repeat of 3.2)
**Finding:** This is the most significant gap. The brief describes what the manifest should
contain but not how it gets there. There is no existing "update manifest" endpoint. The
`_ensure_manifest()` method only writes on vault creation. The implementation needs either:
(a) A new `POST /vault/configure/{vault_id}` endpoint (write_key-gated) to set/update
    `append_anchors` and `enum_key_hash`, or
(b) Extending the vault creation flow to accept these fields upfront, or
(c) Using the existing `write` endpoint to overwrite `manifest.json` directly (fragile,
    bypasses the service layer).
**Verdict:** Concern | **Severity:** Blocking

### 6.2 Rate limiting on append is mentioned but not designed
**Finding:** The brief mentions a "per-inbox cap" (01 section 5) on file count and total
bytes. It says "make both configurable per vault." But it does not specify:
- Default values for the caps
- How the server counts files efficiently (listing on every append is expensive)
- Whether the cap is tracked in memory, in the manifest, or derived from storage listing
- What happens when a cap is hit and then files are mark-processed (does capacity free up?)

For an Explorer phase this is acceptable as "implement the simplest version (count files
via storage listing on append)." But storage listing on every append is O(n) and will
degrade as inboxes grow. A counter in the manifest or a separate metadata file would be
better but adds concurrency concerns.
**Verdict:** Concern | **Severity:** Important — needs a design decision before P0 implementation

### 6.3 Concurrency on mark-processed (move operation)
**Finding:** `mark-processed` moves files from `inbox/` to `processed/`. In `Storage_FS`
(memory or S3 backends), a "move" is typically read + write + delete, which is not atomic.
If two drain loops (or a drain loop and a purge) run concurrently:
- Two drainers could both try to move the same file. The brief's idempotency model handles
  this (second move sees "missing"), but only if the implementation checks existence before
  moving.
- A purge running while a drain is active could delete files the drain is about to move.

The brief says to report missing files in the `missing` list, which is the correct approach.
But the implementation must be careful with the non-atomic move.
**Verdict:** Concern | **Severity:** Minor — manageable with the idempotency model, but
note in implementation guidance

### 6.4 Cross-region is out of scope and correctly so
**Finding:** The brief does not mention cross-region. The current stack is single-region
(Lambda + S3). Cross-region vault communication would be a Villager/infrastructure concern.
Not a gap for this brief.
**Verdict:** Note | **Severity:** N/A

### 6.5 Pagination cursor stability
**Finding:** The `after_file_id` cursor is the filename (`{epoch_ms}_{rand_hex}.enc`).
Because filenames are lexicographically ordered by timestamp, a new append that arrives
between two poll cycles will have a filename *after* the cursor, so it will be picked up
on the next poll. This is correct.

However, if `mark-processed` moves a file that the cursor pointed to, the cursor itself
becomes invalid — it refers to a file that no longer exists in `inbox/`. The lexicographic
comparison ("entries after this string") still works because it does not require the cursor
file to exist. This is fine but should be documented.
**Verdict:** Note | **Severity:** Note

### 6.6 No mention of the new Routes class registration
**Finding:** The existing app registers routes in a setup method (see
`Routes__Vault__Pointer.setup_routes()`). The brief should mention that the new
`Routes__Vault__Inbox` (or equivalent) must be registered in the FastAPI app's route
setup, alongside the existing pointer routes.
**Verdict:** Question | **Severity:** Minor

## 7. Risk Assessment

### 7.1 Highest risk: PKI implementation (P2)
**Rating:** High
**Rationale:** X25519 key generation, ECDH, sealed-box encryption, and cross-language
parity (Python + JavaScript) is the largest net-new crypto work. The brief correctly
identifies this as "the largest net-new piece" (04 section 4). Failure modes include
subtle interop bugs (endianness, serialization format, padding). The KAT requirement is
the right mitigation, but the work is still high-risk.

### 7.2 Manifest update gap (see 6.1)
**Rating:** High
**Rationale:** Without a mechanism to set `append_anchors` and `enum_key_hash`, the entire
feature cannot be activated. This needs resolution before P0 begins.

### 7.3 Storage performance at scale
**Rating:** Medium
**Rationale:** The capacity cap check (counting files via storage listing) is O(n) on each
append. At 100 children sending frequently, the parent's inbox could grow large. The brief
mentions "agent budget" as a second limiter but provides no design. For the Explorer phase,
a simple cap with periodic listing is adequate. The Villager will need a counter or index.

### 7.4 Cross-language crypto parity
**Rating:** Medium
**Rationale:** The `enum_key` HKDF derivation (P1) must produce identical bytes in Python
and JavaScript. The existing `structure_key` derivation provides a precedent and test
pattern, which reduces risk. But the `append_token = SHA-256(pubkey)` requires agreement
on public key serialization format (raw bytes? DER? PEM?). The brief says "pin the format
in the KAT" which is correct, but someone must decide the format first.

### 7.5 Complexity concentration
**Rating:** Low-Medium
**Rationale:** Complexity is concentrated in three areas: (1) the drain loop (client-side,
both Python and JS), (2) the encrypt-to-vault seal/open (client-side crypto), and (3) the
provisioning flow (template vault + reply-key bootstrap). The server side is relatively
simple — it is just storage with gates. This is the right shape: keep the server dumb.

## Summary Verdict

The briefing pack is **well-structured, honest about what exists vs. what is net-new, and
architecturally sound.** The four-tier capability model is clean. The gate mechanisms follow
existing patterns. The storage layout is compatible. The phased plan is sensible.

**One blocking issue must be resolved before implementation begins:**

1. **Manifest update mechanism (6.1/3.2):** There is no endpoint or mechanism to set
   `append_anchors` and `enum_key_hash` in the manifest. This must be designed and added to
   the brief.

**Three important issues should be addressed in the brief:**

2. **Manifest file naming (1.2/8.3):** Change `vault_pointer.json` to `manifest.json`
   throughout the brief. Also fix the reality document.
3. **Inbox file naming convention (2.2):** Explicitly document that inbox files use `.enc`
   suffix (not the `/payload` wrapper) and explain why this is compatible with
   `list_files()`.
4. **Capacity cap design (6.2):** Specify at least a default implementation (e.g., "list
   and count on each append for P0; replace with a counter for Villager hardening").

**Minor items (address in implementation, not the brief):**

5. Add `HEADER__SGRAPH_VAULT__ENUM_KEY` to `user__config.py`
6. Create `Routes__Vault__Inbox.py` as a separate routes file
7. Add `path__vault_inbox*` helpers to `Storage__Paths.py`
8. Pin the X25519 public key serialization format before P1
9. Document cursor behavior when the cursor file has been moved

**Overall assessment:** Approve with conditions. Resolve the blocking issue (manifest update
mechanism), address the three important items, then proceed to P0 implementation.
