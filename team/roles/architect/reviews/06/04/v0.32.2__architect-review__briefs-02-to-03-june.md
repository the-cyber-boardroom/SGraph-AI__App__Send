## Layer 1: Skills Creator Economy — Architecture Assessment (06/02)

### P-300: Skills as Business Knowledge Capture
**Assessment:** No new architecture required from P-295 (skill base vaults). The framing clarifies *what goes in* a skill vault — GDPR erasure workflow, finance approval chain, etc. This is content work, not infrastructure work. Important architectural consequence: the "keep-in-sync" challenge for multi-level cascades (P-303) requires a **sync-notification primitive** (parent update → notify child customisations). This is not yet specified.

**Dependency:** Requires P-295 (skill base vaults) as container + P-303 cascade sync.

### P-303: Finance Team Skills with Multi-Level Customisation Cascade
**Assessment:** The cascade architecture — corporate → group → cyber → ethics — introduces a **tree of vault customisations**. The key question: where does the canonical version live? Three options:
1. Parent vault holds the base; child vaults hold diffs (dependency graph)
2. Each level is a self-contained vault with an explicit `parent_vault_id` field
3. Customisation is a separate record alongside the base vault (composition, not inheritance)

**Option 2 is architecturally cleanest** given the vault's immutable-object model. An explicit `parent_vault_id` field in vault metadata + a `sync_pending` flag + a sync notification endpoint. Recommend architect specifies this before any implementation.

**New open question:** `OQ-cascade-sync-design-1` — define the parent_vault_id + sync notification model.

### P-304: Expert Brand Vaults (Anonymisation Path)
**Assessment:** The **anonymisation path** is architecturally non-trivial. The claim is: expert grades the skill class without seeing the confidential customer vault. This requires:
- A "comparison request" vault that redacts confidential fields before sharing with the expert
- OR the expert grades a non-confidential sample vault only, not the customer vault
The second is simpler and architecturally cleaner. No new infrastructure needed if grading is on sample vaults.

### P-305: Monetising Skills on Aggregators
**Assessment:** Aggregator integration (Tessl, Pi, Anthropic marketplace) requires the vault-as-zip interoperability format to be portable to those platforms. The existing vault is not yet packaged as a standard zip (P-295 specifies this; not yet built). No new architecture beyond P-295 + P-296. Confirm that vault zip format is compatible with agentskills.io.

## Layer 2: Vault Communications Infrastructure — Architecture Assessment (06/03)

### Vault Inbox Endpoints — NOW EXISTS ✅
**Classification:** P0 server primitive, now shipped. 6 endpoints confirmed in code. Four-tier capability model (append_token / enum_key / private_key / write_key) is solid. Important architectural properties confirmed:
- Write-blind: sender with `append_token` cannot read messages back
- Enum/read separation: listing does not require decryption capability
- Owner control: purge and configure gated behind `write_key`
- Storage path: follows `Storage__Paths` convention (confirmed in code)

**Architect notes:** The `inbox` field in list/fetch/mark-processed supports named inboxes within a vault. This is a good extension point but the naming convention for inboxes should be documented before external callers assume any pattern.

### P-313: Vault-to-Vault Comms via Append Token + PKI
**Assessment:** The inbox is the P0 primitive (now EXISTS). P-313 specifies the key-provisioning layer on top of it:
- Sender receives: parent vault's public key + parent vault's append_token (via template-vault provisioning)
- Sender encrypts payload with public key, appends via append_token
- Only parent (holding private_key) decrypts

**Architecture approval with two conditions:**
1. **Template-vault provisioning spec needed** — the mechanism by which a sender receives a parent's public key + append_token must be formally specified before building (who creates the template vault? how does the sender prove they are allowed to receive it?).
2. **Inbox naming convention** — the inbox name passed in list/fetch/mark-processed should follow a defined pattern (e.g. `<sender_vault_id>` or `<topic>`). Document this before demo.

### P-312: Three-Agent Comms Demo Vault
**Assessment:** This is a proof-of-concept (PoC), not a production feature. The browser-harness approach (3 iframes + internal API: ping/send/receive/mark-received) is appropriate for PoC. The key insight — "agents only share what they explicitly message, not full vault access" — is architecturally correct and should be preserved as a design principle.

**Recommend:** Build P-312 before P-313. The demo will expose the real friction points in inbox naming, key provisioning, and round-trip latency. Design decisions should flow from observed demo behaviour, not from spec alone.

### P-311: Publishing Mode via GitHub Actions
**Assessment:** Clean architecture: vault holds the editable source; GHA workflow reads vault via public read key and publishes static output. This is a **content-pipeline pattern** not a new server feature. The vault stays the source of truth; GitHub becomes the publish surface. No server-side changes needed. Works with existing vault read endpoints.

**Risk:** If the vault's public read key changes, the GHA workflow breaks silently. Recommend the GHA workflow validate the key on each run and fail loudly if read access is denied.

### P-314: PKI Not Secrets — Identity Envelopes + Identity-Provider Partnership
**Assessment:** This is the most significant architectural proposal in the period. The shift from "one vault key (a secret)" to "many granular keys per identity" touches the entire vault security model.

**Current model:** single write_key + append_token + enum_key per vault (as shipped in inbox)
**Proposed model:** per-identity keying (each actor gets scoped keys; supply-chain gated by key handoffs)

**Architect position:** P-313 + P-312 (append-token model) is correct at the P0 primitive level. P-314 is the **long-term evolution** of that model. There is no conflict, only sequencing:
- Phase 0: append_token model (NOW EXISTS in vault inbox) — simple, works today
- Phase 1: per-vault scoped keys with provisioning (P-313) — additive extension
- Phase 2: per-identity PKI with identity-provider integration (P-314) — long-term evolution

**Blocking architectural question for P-314:** What does key distribution look like? Three options:
1. Identity provider (IdP) issues keys → vault trusts IdP signature
2. Vault operator issues keys → identity is vault-scoped
3. Self-sovereign (user generates keys, vault verifies via known public key registry)

These are architecturally distinct paths. Option 1 requires the identity-provider partnership. Option 2 is buildable today. Option 3 is the most decentralised but requires key discovery infrastructure. Recommend an architect decision document before starting P-314 implementation.

**New open question:** `OQ-pki-key-distribution-model-1` — define the key distribution model for P-314 before implementation.

### P-316: SG/Vault as Platform of Primitives — Positioning
**Assessment:** Architecturally, the "platform of primitives" framing is consistent with what's been built. The three-layer model (vault primitives / heterogeneous middle / bespoke top) maps cleanly onto:
- Bottom: vault endpoints, inbox endpoints, MCP server (EXISTS)
- Middle: vault chat, connectors, skills library (PROPOSED)
- Top: specific UX apps (share/open/workspace UI, accountant demo, three-agent demo)

This is not an architecture change — it is a framing of existing architecture that is accurate and should be adopted across all design documentation.

## Skills Library Architecture (P-315)

### P-315: Skills Library as Platform Feature
**Assessment:** The skills library is architecturally a **vault + structured manifest + discovery layer**. Concretely:
- A library vault holds: SKILL.md files, provenance metadata, sync state, applicability scores
- Discovery: search by name/topic/provider, filter by score/source, browse by category
- "Talk to skill": instantiate an on-demand vault from a skill base vault (requires vault cloning endpoint P-295)
- Budget/billing per skill: requires OpenRouter broker (P-299) or equivalent

**Dependency chain:** P-315 → P-297 (marketplace scoring) → P-295 (base vaults) → P-294 (semantic graphs). The library can be built incrementally: start with a curated list + SKILL.md search, add scoring later.

**Minimum viable library:** One vault holding 5–10 skills from different sources, with SKILL.md viewing, basic search, and a "copy key to use this skill" UX. No scoring, no billing needed for MVP.
