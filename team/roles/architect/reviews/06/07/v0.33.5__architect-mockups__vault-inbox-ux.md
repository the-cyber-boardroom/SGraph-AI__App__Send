## 1. Where the Inbox lives in the left nav

### 1.1 Recommendation — **2nd item, between Files and SGit**

```
   ┌────────┐                                  ┌────────┐
   │ Files  │  ← primary content               │ Files  │  ← primary content
   │ SGit   │  ← version control               │ Inbox  │  ◀── NEW (active comms)
   │Settings│  ← config                        │ SGit   │  ← version control
   └────────┘                                  │Settings│  ← config
                                                └────────┘
        TODAY                                       PROPOSED
   ────────────                                ────────────────────────
   3 items, hardcoded                          4 items, Inbox at #2
   in vault-nav.js:25-30
```

### 1.2 Why position #2 (not between SGit and Settings)

| Concern | #2 (between Files and SGit) | #3 (between SGit and Settings) |
|---|---|---|
| **User mental model** | Inbox = active content the user receives — sits next to Files (active content the user holds) ✓ | Inbox treated as a developer/admin section like SGit ✗ |
| **Visual scan order** | First-class — third item below Files ✓ | Buried after SGit which most users rarely open ✗ |
| **Badge prominence** | Counter at #2 is hard to miss ✓ | Counter at #3 next to Settings looks like a config dot ✗ |
| **Implementation cost** | Identical (one DOM insertion in `vault-nav.js`) | Identical |
| **Future Reply UI** | Naturally adjacent to Files (drag-to-attach?) ✓ | Disconnected from content surface ✗ |

The dev brief said *"this is a main section on the left. The same way we have the other main sections."* Position #2 honours that — Inbox is **a content section**, not a config section.

## 5. The app's view of the inbox

The app is hosted in a sandboxed iframe at `/en-gb/app/#<vault-key>`. From the app's perspective, **the vault inbox layer is one event and six methods**.

### 5.1 What the app declares (`app.json`)

```json
{
  "title": "Inbox Reader (demo)",
  "permissions": {
    "inbox": {
      "list":          true,
      "read":          true,
      "markProcessed": true
    }
  },
  "host_events": {
    "inbox.new-messages": true
  }
}
```

### 5.2 What the app code looks like

```js
// In the app's main JS:
sg.on('inbox.new-messages', async (info) => {
  // info = { total, per_anchor, entries?, trigger, last_check }
  for (const [anchor, count] of Object.entries(info.per_anchor)) {
    console.log(`Anchor ${anchor} has ${count} new`);
  }

  // Fetch + decrypt only the new ones (vault doesn't decrypt for us)
  const { entries } = await sg.inbox.list({
    inbox: anchor, include_content: true
  });
  for (const e of entries) {
    const plaintext = await myAppDecrypt(atob(e.content));  // L2 concern
    renderMessage(plaintext);
  }

  // Mark them processed on the server
  await sg.inbox.markProcessed({
    inbox: anchor,
    file_ids: entries.map(e => e.file_id)
  });
});
```

**Six lines of meaningful logic.** Everything else (polling, debounce, headers, key plumbing, event registration) is the kernel's job.

## 7. Where this scales (future kernel→app pushes)

Once the event channel exists, the same UI shapes work for every future feature. Sketch:

```
   nav badge animations:           events the channel will carry:
                                   ──────────────────────────────
   ✉  ❹  inbox new messages       inbox.new-messages
   ⇅  ❷  commits behind           vault.commits-behind
   👤 ●  peer connected           peer.connected
   ⏳ ▓▓▓ task progress           task.progress
```

Each new feature ships an event name, a default-off `host_events` entry, and reuses **all** the same plumbing. UX cost per new feature: a nav icon + a status section.

## 8. Mobile / narrow-viewport considerations

The current vault UI nav is a 56 px fixed column. On narrow viewports, the existing pattern collapses Files/SGit/Settings to icons-only. The Inbox entry follows the same rule:

```
   Desktop          Tablet           Phone
   ─────────        ─────────        ───────
   📁 Files         📁               📁
   ✉  Inbox ❹       ✉  ❹             ✉ ❹       (icons + badge only;
   ⚙  SGit          ⚙                ⚙           tap title in header for
   ⚙ Settings       ⚙                ⚙           text labels)
```

Badge stays — it's the highest-signal element on the page when messages arrive.

## 9. UX acceptance criteria (mirrors brief #4 and #5)

| Criterion | Verification |
|---|---|
| Inbox is a main left-nav section | Position #2 between Files and SGit. |
| Counter updates on refresh-equivalents | Badge increments on `inbox.new-messages`; resets when the user opens the view. |
| Sender identity surfaced ("which key") | Anchor short-hex shown in the row; friendly labels are L2 app concern (app overlays its own). |
| Configuration surfaced | Two booleans (`enabled`, `auto_fetch`) in the status panel. Anchor list is observed (read-only — apps register, owner views). |
| Apps receive notifications | `sg.on('inbox.new-messages', cb)` — one line for the app author. |
| RO-token sessions work | View-only mode, toggles disabled, list available. |

---

## 10. What this is NOT — explicit non-goals

- **Not a mail reader.** No message list with bodies. No "Reply" composer in the vault layer. Those live in apps.
- **Not a sender directory.** Anchor short-hex is all the vault knows. Friendly names live in apps.
- **Not a notification centre.** Only the inbox icon's badge animates. No global toast queue from the vault layer. (Apps may show their own toasts.)
- **Not configurable cadence.** No "poll every 30 s / 60 s" picker. Events drive checks; the user has no knob.
