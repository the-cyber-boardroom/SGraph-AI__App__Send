## 0. What changed in revision 3

| | r2 | r3 |
|---|---|---|
| Detection model | Poll loop with `poll_interval_ms` (30 s default) | **No polling.** Kernel runs one cheap `list` on quasi-events (tab focus, refresh click, peer poke). Same triggers that already drive `_scheduleBehindCheck`. |
| App receive surface | Bespoke `sg.inbox.subscribe(cb)` | **General `sg.on(eventName, cb)`** — kernel→app event channel that works for *any* future feature. Inbox is its first consumer. |
| Event gating | None | **`app.json.host_events`** allowlist — apps declare which kernel events they accept. Default-deny. |
| Bridge methods | `configure, append, list, fetch, markProcessed, purge` + `subscribe, status, checkNow, setAutoPull` | **Six transport verbs only.** All notification flows through `sg.on`. |
| Cross-vault wake | Not addressed | `sg.vault.notify(mountId, eventName, payload?)` over existing SecureChannel. |
| Vault-level config | `enabled, auto_pull, poll_interval_ms, anchors[], labels{}` | **`enabled, auto_fetch`** — two booleans. Anchors live on the server; labels are app-state. |

Net: fewer moving parts, less app-side code, and the kernel→app event channel becomes a reusable substrate beyond inbox.

| Layer | Owner | Responsibility |
|---|---|---|

## 2. The kernel→app event channel (new substrate)

This is the bigger architectural addition in r3 and pays off well beyond inbox. The bridge today is request/response — apps call `sg.vfs.read(path)`, kernel responds. There is no kernel-initiated push to the iframe. r3 adds one.

### 2.1 The contract

```
kernel (app-shell.js)                     iframe app
  ───────────────────────                  ────────────────────────
  emit(eventName, payload)
    └─ check app.json.host_events[eventName] === true
    └─ postMessage({type:'sg-event', name, payload}, '*')
                                          window.addEventListener('message',
                                            on 'sg-event' → dispatch to
                                            sg.on(name, cb) registrations)
```

### 2.2 App-facing API (one method, three forms)

```js
sg.on('inbox.new-messages', (payload) => { ... });   // subscribe
sg.off('inbox.new-messages', handler);               // unsubscribe
sg.on('*', (name, payload) => { ... });              // wildcard (still gated per-event)
```

That's all an app writes. No subscribe boilerplate, no manual list-polling, no rebuilding event plumbing per feature.

### 2.3 The allowlist (`app.json.host_events`)

```json
{
  "permissions":  { "inbox": { "list": true, "read": true, "markProcessed": true } },
  "host_events":  {
    "inbox.new-messages":    true,
    "inbox.config-changed":  false,
    "vault.commits-behind":  false
  }
}
```

- **Default-deny.** An app that omits `host_events` receives **no** kernel pushes.
- The kernel filters every outgoing event through this map. An app cannot receive an event it didn't declare.
- Wildcards (`inbox.*`) are not supported in the allowlist — events must be enumerated by exact name. Keeps the audit surface explicit.
- Permission to subscribe via `sg.on` is implicit in the `host_events` allowlist; no separate capability key needed (subscribing without an allowlist entry is a silent no-op, not an EPERM — the app simply never sees the event).

### 2.4 Why this is general, not inbox-specific

Future features (commits-behind toast, peer-connected handshake, ephemeral-task progress, sub-vault link-resolved) all want the same shape. r3 spends the small extra to build the channel once. Inbox is the first user.

## 3. The check-on-events model (no polling)

### 3.1 Triggers

The kernel runs `_checkInbox()` on the **same triggers** that already drive `_scheduleBehindCheck`:

| Trigger | Source | Today | r3 addition |
|---|---|---|---|
| Tab gains focus | `document.visibilitychange` (`vault-shell.js:37`) | Fires `_scheduleBehindCheck(500)` | Also fires `_scheduleInboxCheck(500)` |
| User clicks Refresh | `vault-header` sync menu | Fires `_scheduleBehindCheck(0)` | Adds "Check inbox" menu item firing `_scheduleInboxCheck(0)` |
| Vault open | `_onVaultOpened` | Runs initial ref check | Adds initial inbox check |
| Peer poke arrives | `SecureChannel.on('inbox.new-messages')` from another vault | n/a | Fires `_scheduleInboxCheck(0)` |
| App calls `sg.inbox.list({})` directly | Bridge verb | n/a | The kernel runs the call but does NOT fire the event channel — that's a direct read, not a check |

Same debounce floor as `_scheduleBehindCheck` (no double-fires within ~1 s). **No standalone timer.** If the tab is backgrounded for an hour, no inbox check fires until the user comes back.

### 3.2 What `_checkInbox()` does

```
1. inbox.list({ include_content: false })   // cheap; server returns metadata only
2. Diff entries against last-seen set (sessionStorage, keyed by vault_id)
3. If counts unchanged: do nothing.
4. If counts changed:
   a. If config.auto_fetch === false: emit 'inbox.new-messages' with { total, per_anchor }.
   b. If config.auto_fetch === true:  inbox.fetch({...}) per anchor; cache locally;
                                       emit 'inbox.new-messages' with { total, per_anchor, entries }.
5. Update last-seen set.
```

When the **server doorbell** ships (the comms-MVP agent's §3.1 — `GET /api/vault/inbox/status/{vault_id}` returning counts + timestamps without enumerating shards), step 1 swaps to that. It's a transport-internal change in `sg-inbox.js`; no client code outside that module changes.

### 3.3 Cross-vault peer wake

When parent vault has just appended a message to child vault's inbox and wants the child to check **right now** (not on next focus), the parent app calls:

```js
sg.vault.notify(mountId, 'inbox.new-messages');
```

The kernel relays this over the existing `SecureChannel` (`secure-channel.js`, authenticated and replay-guarded). The child kernel's `ch.on('inbox.new-messages')` handler runs `_scheduleInboxCheck(0)`. The child's `_checkInbox()` then calls `list`, sees the new entry, and emits to any child apps subscribed via `sg.on('inbox.new-messages', cb)`.

The peer poke is a **trigger**, not a payload carrier — the child still does its own `list` to discover what arrived. This keeps the wire content-free (matches the comms-MVP agent's acceptance criterion #4).

Capability: `vault.notify` (new key in `AppPermissions`). Default-deny.

## 4. Vault-side persistent state (simplified)

`.vault/inbox/config.json`, encrypted with `read_key`, committed:

```json
{
  "enabled":    true,
  "auto_fetch": false
}
```

That's it. Two booleans.

| Field | Purpose |
|---|---|
| `enabled` | Master switch. If false, `_checkInbox()` is a no-op and the nav entry hides. |
| `auto_fetch` | If true, `_checkInbox()` calls `fetch` for new entries and includes ciphertext in the emitted `inbox.new-messages` payload. If false, only counts. |

Anchors live on the server (the `append_anchors` list passed to `configure`). The vault doesn't maintain a local mirror. The owner panel reads anchors from the kernel's most-recent `list` response.

Labels (friendly names per anchor) are **app state**. Apps that want to display "alice" instead of `abc12…def` store their own mapping in their own app-data area of the vault.

## 5. Vault-app bridge surface (locked)

### 5.1 Transport (six verbs, 1:1 with server endpoints)

```
sg.inbox.configure({ append_anchors })                  // vault adds enum_key_hash
sg.inbox.append({ vault_id, append_token, payload })    // outbound to remote vault
sg.inbox.list({ inbox?, after_file_id?, limit?, include_content? })
sg.inbox.fetch({ inbox, file_ids })
sg.inbox.markProcessed({ inbox, file_ids })
sg.inbox.purge({ inbox, file_ids?, folder })
```

| Verb | Kernel adds | App capability |
|---|---|---|
| `configure` | `x-sgraph-vault-write-key`, `x-sgraph-access-token`, computed `enum_key_hash` | `inbox.configure` |
| `append` | nothing | `inbox.append` |
| `list` | `x-sgraph-vault-enum-key` | `inbox.list` |
| `fetch` | `x-sgraph-vault-enum-key` | `inbox.read` |
| `markProcessed` | `x-sgraph-vault-enum-key` | `inbox.markProcessed` |
| `purge` | `x-sgraph-vault-write-key`, `x-sgraph-access-token` | `inbox.purge` |

### 5.2 Cross-vault peer wake

```
sg.vault.notify(mountId, eventName, payload?)
```

Single new verb. Permission: `vault.notify`. Default-deny.

### 5.3 Receive surface (the only event API)

```
sg.on(eventName, callback)
sg.off(eventName, callback)
```

Gated by `app.json.host_events` (§2.3). Not inbox-specific.

### 5.4 Standard events emitted by the inbox subsystem

| Event | When | Payload |
|---|---|---|
| `inbox.new-messages` | Check detected count delta | `{ total, per_anchor: {...}, entries?: [...] }` (entries present iff `auto_fetch:true`) |
| `inbox.config-changed` | `.vault/inbox/config.json` rewritten | `{ before, after }` |
| `inbox.error` | Check or fetch failed | `{ code, message, http? }` |

### 5.5 What's gone

No `sg.inbox.subscribe`, `onNotify`, `status`, `checkNow`, `setAutoPull`. All redundant once the general event channel exists.

## 7. `AppPermissions` extension

`app-permissions.js` gains two new groups:

```js
parsePermissions({
  inbox: { configure, append, list, read, markProcessed, purge },   // booleans, default false
  vault: { ..., notify }                                              // add 'notify' to existing vault group
})
```

`host_events` is **not** part of `permissions.parsePermissions` — it's a separate top-level field in `app.json`, parsed by a new helper `AppHostEvents.parse(appJson)` returning a `Set<string>` of allowed event names. Kept separate because permissions describe outbound capability (what the app can call), host_events describes inbound capability (what the host can push). Distinct concerns, distinct shapes.

Default-deny everywhere. Unknown events / verbs / keys are silently dropped.

## 9. Phase / sequencing plan

| Phase | Deliverable | LOC |
|---|---|---|
| **A** | `sg-inbox.js` transport (six endpoints + `enum_key` derivation). No UI. Console-drivable. | ~250 |
| **B** | `sg-inbox-checker.js` + hook into `vault-shell._visibilityHandler` and `vault-header` refresh menu. Emits `inbox.new-messages` on the existing vault bus. **No app delivery yet.** | ~200 |
| **C** | **General kernel→app event channel.** `app-host-events.js` + `app.json.host_events` schema + `sg.on/sg.off` bridge + post-message envelope. Pumps the inbox events from Phase B to subscribed apps. | ~250 |
| **D** | Inbox bridge transport (`sg.inbox.*` verbs + `inbox.*` permissions) + nav entry + `<vault-inbox-status>` + `<vault-inbox-badge>`. | ~350 |
| **E** | `sg.vault.notify(mountId, eventName)` + SecureChannel relay handler. Wakes peer kernel; peer fires `_scheduleInboxCheck(0)`. | ~150 |
| **F (deferred)** | sgit CLI port; per-anchor capability scoping; ephemeral-compute worker; server doorbell adoption (`GET /inbox/status` swap inside `sg-inbox.js`). | — |

Total: ~1200 LOC, sequenced so the general event channel (C) lands before any app actually depends on it. Phases B and C are split deliberately — B's events fire on the internal vault bus (`window.sgraphVault.events`), C adds the app-facing fan-out. This means the kernel's internal observability works in B even before any app subscribes.

## 11. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Apps abuse `sg.on` to enumerate event names | Allowlist gates delivery, but a malicious app could call `sg.on(name, cb)` for every plausible name to detect which fire. Mitigation: registration is purely client-side state; the kernel never confirms whether an event is "real" or "allowed" — handlers simply never fire if not allowed. Indistinguishable from "no events occurred". |
| Event flood (auto_fetch on, large drop arrives) | Cap `entries` in a single `inbox.new-messages` event at 100; emit multiple events if needed. |
| Peer-notify spam | `vault.notify` is rate-limited per (sender, target, eventName) tuple — e.g. ≤1/sec. Server-mediated notify (deferred — see API team's §3.1+§3.2) gets its own server-side rate limit. |
| App fails to declare `host_events` and wonders why nothing fires | Debug pane "Events" tab shows dropped pushes with reason "not in host_events". |
| `_checkInbox()` fires on focus and overlaps with `_scheduleBehindCheck` | Both already debounce; share visibility handler; sequential calls, not concurrent. |
| SecureChannel peer-notify and local-poll race (peer wakes us, we check, peer's append hasn't reached storage yet, we see nothing) | Acceptable — next quasi-event or next peer poke retries. Document as "eventually consistent". |
| `enum_key` derived from `read_key` widens key surface | AppSec sign-off Q1. |
