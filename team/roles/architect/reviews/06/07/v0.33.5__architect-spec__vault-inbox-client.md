## Front matter — what this is / what exists / what's proposed

- **What this is.** The client-side architecture that lands the inbox as a first-class section of the vault Web UI (`/en-gb/vault/`), with a notes-only design layer for sgit CLI parity, and a new `sg.inbox.*` bridge namespace exposed to apps running under `/en-gb/app/` (the app-shell sandbox).
- **What exists today (code-verified).** The six server endpoints in `sgraph_ai_app_send/lambda__user/fast_api/routes/Routes__Vault__Inbox.py` (append, list, fetch, mark-processed, purge, configure) and `Service__Vault__Inbox.py`. Three header constants (`HEADER__SGRAPH_VAULT__WRITE_KEY`, `HEADER__SGRAPH_VAULT__ENUM_KEY`, `HEADER__SGRAPH_SEND__ACCESS_TOKEN`). On the client side, **nothing inbox-shaped exists in the vault UI repo** — Grep for `inbox` in `sgraph_ai_app_send__ui__vault/` returns only the unrelated `inbox-saves` regression test name from the embed handshake (`test__regression__root_hash_inbox_saves.spec.js`). The vault-nav has three peers: Files / SGit / Settings (`vault-nav.js:22-30`); refresh cadence runs from `vault-shell._scheduleBehindCheck` / `_behindCheckTimer`; `AppPermissions` (`app-permissions.js`) governs an iframe capability set that does not yet include any `inbox.*` keys.
- **What's proposed.** A `sg-inbox` JS library tier (parallel to `sg-vault`), three new web components (`<vault-inbox-view>`, `<vault-inbox-settings>`, `<vault-inbox-badge>`), a fourth nav item, a new `inbox.md` reality document, an `inbox.{read,list,markProcessed}` capability set in `AppPermissions`, and the `sg.inbox.*` bridge surface. Owner-only verbs (configure, purge) stay in the host kernel and are **not** exposed to apps.

## 1. Scope and non-goals

### 1.1 In scope (this spec)

| Surface | Coverage |
|---|---|
| Vault Web UI | Primary deliverable: nav entry, list/decrypt/process flows, settings tab for accepted pubkeys, polling integration with the existing behind-check timer. |
| sgit CLI | Design-level only — capability mapping, key storage at rest, the same six endpoints, alignment with the Web UI's `sg-inbox` library shape. **Implementation deferred to the sgit-ai team.** |
| Vault-app bridge (`/en-gb/app`) | New `sg.inbox.*` namespace exposed to sandboxed iframes; new `AppPermissions` capability keys (`inbox.read`, `inbox.list`, `inbox.markProcessed`). Owner-only verbs stay in the host kernel. |
| Reality-document deltas | Listed for the Librarian to apply post-merge — this spec does NOT modify reality docs itself. |

### 1.2 Out of scope

- **Server-side work** — the SG API team has shipped it. The Service and Routes files exist and are tested.
- **Replacing the existing "mailbox-as-send"** flow used in some demo vaults — that lives elsewhere; the inbox is additive.
- **Sgit CLI implementation details** — owned by the sgit-ai team. This spec only fixes the contract.
- **Ephemeral-compute auto-processing** of inboxes — separate brief (`v0.32.4__ephemeral-compute-actions-on-vaults`). This spec leaves a hook (the inbox is processable headlessly by anything holding `enum_key`) but does not build that worker.
- **PKI Modes 2–4** — only Mode 1 (Web Crypto P-256, already in the vault token-test harness via `vault-hkdf.js`) is in scope. X25519 may be needed; see §6.
- **Sender-side UX** — there is no "send a message to a vault" UI in this spec. The receiving inbox is the only thing being built. (A separate brief addresses the comms harness's sender path; this spec is recipient-only.)

## 2. Capability model mapping

The API brief specifies four tiers. Mapped onto the existing vault credential layers:

| Brief tier | What it does | Derived from | Browser storage | Sent to server? | Maps to existing layer |
|---|---|---|---|---|---|
| **`append_token`** (hex, 16–128) | Append only (sender) | `SHA256(recipient_pubkey).hex()` (per accepted sender) | **Not stored at recipient** — it is the sender's credential. Recipient stores only `SHA256(append_token).hex()` (the anchor). | Yes, in append body | New tier — closest analogue is the existing per-vault `write_key` but scoped to one inbox shard. |
| **`enum_key`** (any string, sent as hex) | List / fetch / mark-processed | Owner secret; recommendation: HKDF over `read_key` with `info=b'sg-vault-v1:inbox-enum-key'` so a vault owner who has the passphrase can re-derive without a separate stash. | sessionStorage (per-tab), keyed by `vault_id`, mirroring how the vault key is stored (`VaultLoader.storage`). Never localStorage. | Yes, header `x-sgraph-vault-enum-key` | Sits between `read_key` and `write_key` — enum-only, no mutation, no append. |
| **`write_key`** (hex) | Configure / purge (owner) | The existing vault `write_key` derived by `SGVaultCrypto.deriveKeys` (`sg-vault-crypto.js`) — **reuse, do not derive a second one**. The brief's "configure must hit a pre-existing vault" matches this exactly. | sessionStorage (already there from `sg-vault.js`). | Yes, header `x-sgraph-vault-write-key` | Existing layer — reused unchanged. |
| **`private_key`** (X25519) | Decrypt ciphertext | The recipient's PKI key. Today: PKI Mode 1 (P-256). See §6 on whether to upgrade to X25519 or stay on P-256 with ECDH+HKDF. | **Never leaves the browser.** In-memory only after unlock; key material persisted in the vault's PKI registry under `read_key` (the existing PKI storage convention). | **No.** Server is decrypt-blind. | New flow on top of the existing PKI layer. |

Key derivation summary (proposed):

```
enum_key      = HKDF(read_key, info=b'sg-vault-v1:inbox-enum-key').hex()
append_anchor = SHA256(append_token).hex()    // recipient knows only the anchor
append_token  = SHA256(sender_pubkey).hex()   // sender derives at send time; recipient
                                              //   reproduces it to know which anchor matches
                                              //   a known sender pubkey
```

Rationale for HKDF-from-`read_key`:
- The owner already knows `read_key` whenever they have the vault open. No new credential to remember, store, or rotate.
- `read_key` → `enum_key` is one-way (HKDF) so leaking `enum_key` does not back out to `read_key`.
- An RO-token session does NOT hold `read_key`. Therefore an RO-token session can **list metadata** only if we also persist `enum_key` in the ro-record (we propose **not** to — see §11 open question on RO-token inbox visibility).

## 3. Module / component decomposition

### 3.1 New library tier: `sg-inbox`

| File | Purpose |
|---|---|
| `_common/js/lib/sg-inbox/sg-inbox.js` | Core class. Constructor takes `{ endpoint, vault_id, enum_key?, write_key?, access_token? }`. Exposes `list({ inbox?, after_file_id?, limit?, include_content? })`, `fetch({ inbox, file_ids })`, `markProcessed({ inbox, file_ids })`, `configure({ append_anchors, enum_key_hash })`, `purge({ inbox, file_ids?, folder })`. No DOM, no Shadow DOM — pure transport + base64 packing + retry/backoff. Mirrors the shape of `sg-vault.js`'s split into a thin lib. |
| `_common/js/lib/sg-inbox/sg-inbox-crypto.js` | Encryption module: derive `enum_key` from `read_key` via HKDF; derive `append_anchor` from an accepted sender pubkey; **decrypt** an inbox ciphertext payload using the recipient's private key (open the seal). For Phase A, the decrypt function is stubbed; for Phase B it is wired to Web Crypto or noble-curves (§6). |
| `_common/js/lib/sg-inbox/sg-inbox-pki.js` | Accepted-pubkey list helpers: read/write `.vault/owner/inbox/accepted-keys.json` under `read_key` encryption (mirrors the `public-previews/` convention, `ro-links.json` convention). One record per accepted sender: `{ alias, pubkey_b64, append_anchor, added_at }`. |
| `_common/js/lib/sg-inbox/sg-inbox-batcher.js` | Pure helper that splits a `file_ids[]` array into chunks of ≤100 (server cap) and serialises calls. DOM-free; unit-testable. |

The library is **storage-blind**: it does not commit anything to the vault tree. Persistence of accepted-pubkey records is delegated to the host (vault-shell) using existing `sg-vault` write paths.

## 4. Outside-version-control storage

The dev brief is emphatic: the inbox is **outside the commit tree**. We distinguish two storage concerns:

| Thing | Where it lives | Why |
|---|---|---|
| **Inbox messages (ciphertext)** | **Server only.** Never written to the vault `bare/` tree. After `markProcessed` they move to a server-side `processed/` folder; after `purge` they are gone. | The brief: "introduces something that is, by design, outside the normal traditional version control." The whole point of the public-key-controlled inbox is that it is independently arriving, independently retained. Committing messages into the tree would defeat the design. |
| **Accepted-pubkey configuration** (the list of keys the vault will receive from) | `.vault/owner/inbox/accepted-keys.json`, **encrypted with `read_key`**, committed to the vault. | Mirrors `.vault/owner/ro-links.json` (sub-vaults pack) and `.vault/owner/public-previews/` (PVP pack). The accepted-keys list IS owner state and IS version-controlled — it must survive vault clones, re-opens, and CLI/Web parity. The server holds only `SHA256(append_token)` anchors; the human-readable mapping (alias, pubkey, anchor) is the owner's. |
| **Optional read-cursor / "already seen" markers** | `localStorage`, keyed by `${vault_id}:inbox:seen` | Per-device convenience for the badge ("3 unread since you last looked"). Not authoritative; the authoritative state is the server's processed/not-processed flag. |

What we explicitly **do not** do:

- Do **not** commit ciphertext to `bare/data/obj-cas-imm-*`. Inbox messages never enter the CAS.
- Do **not** persist `enum_key` in `localStorage`. It is sessionStorage only (per-tab), and re-derived from `read_key` on vault open. (Matches the per-tab vault key isolation already in place — `vault-loader-storage.js` P-174.)
- Do **not** persist `append_token`s on the recipient. The recipient knows the **anchor** (the SHA-256). When a known sender's pubkey is added to the accepted list, the recipient can re-derive both the token (`SHA256(pubkey)`) and the anchor (`SHA256(token)`) on demand.

## 5. Polling / refresh integration

The vault shell already runs a behind-check timer keyed off visibility and a user-configurable cadence:

```
vault-shell.js:35-38
_lastBehindCheckTime, _behindCheckTimer, _visibilityHandler → _scheduleBehindCheck(...)
```

Fit the inbox into this **same** cadence; do not add a second poll loop:

| Phase | Action | Endpoint | Cost |
|---|---|---|---|
| **Refresh tick (cheap)** | `list({ include_content: false })` — no `inbox` field → scans all sender folders. Group results by `inbox` to produce per-sender counts. Update `<vault-inbox-badge>` total and per-sender badges. | `POST /api/vault/inbox/list/{vault_id}` | Zero payload reads (server-side); a single request per tick. |
| **User clicks Inbox nav** | Re-issue the metadata `list` immediately (don't wait for the next tick); render per-sender rows. | Same as above. | One request on click. |
| **User opens a sender** | `list({ inbox: <token>, include_content: true, limit: 50 })` to fetch ciphertext for that sender only. Decrypt client-side. | `POST /api/vault/inbox/list/{vault_id}` with content | One request per sender open; bounded by the 50 limit. |
| **User clicks "Mark processed"** | Single batch call with the file_ids of decrypted-and-handled messages. | `POST /api/vault/inbox/mark-processed/{vault_id}` | Single request; ≤100 file_ids. |
| **Owner clicks "Purge processed"** (in Settings) | Bulk purge for that sender. | `POST /api/vault/inbox/purge/{vault_id}` with `folder:"processed"` and no `file_ids` | Single request. |

**Auto-expand is OFF by default.** Refresh ticks read metadata only. Decryption only happens when the user opens a sender (or — phase C — when an app explicitly calls `sg.inbox.fetch`). This avoids paying the storage-read cost on every refresh.

**Cadence floor.** Reuse the existing `_lastBehindCheckTime` debounce so two adjacent triggers (visibility-change + user-click on the nav) don't double-fire.

## 6. Encryption contract

The API brief mandates "X25519 + AES-256-GCM" client-side. The reality:

- The vault repo today uses **P-256 (ECDSA + ECDH-AES-GCM)** via Web Crypto in `secure-channel-envelope.js` (used by the ViV kernel). Web Crypto in all evergreen browsers supports P-256 natively.
- **Web Crypto does not natively support X25519 in stable browsers as of 2026** (it is in draft/origin-trial). Polyfilling X25519 means shipping `@noble/curves` (already a vetted micro-lib) or libsodium-js.
- The PKI registry plan (`reality/vault/proposed/pki-modes.md`) lists Mode 1 = P-256 as existing. Modes 2–4 are PROPOSED.

**Recommendation:**

1. **Phase B starts on P-256** (ECDH with HKDF-SHA256 → AES-256-GCM). It aligns with existing PKI Mode 1, is supported natively by Web Crypto, and matches `secure-channel-envelope.js`'s curve choice — operators are already using P-256 keys in the ViV kernel and in the Comms Harness's `SecureChannel`. The API brief's "X25519" is descriptive of the seal model, not prescriptive of the curve; the seal property (ECDH-derive → AEAD) holds for P-256 too.
2. **Document an X25519 upgrade path** as a follow-up (PKI Mode 1.1 or PKI Mode 2), to be decided alongside the PKI registry proper. If the comms harness has already standardised on X25519 in code, we revisit and bring the vault UI inline; otherwise P-256 is the default.
3. **No new dependency in Phase B if we stay on P-256.** If the team decides X25519 is required, add `@noble/curves` (or the X25519 subset of libsodium-js) as a single vendored micro-library under `_common/vendor/`. No npm runtime; IFD discipline keeps the dependency surface frozen.

**Seal/open primitive (P-256 ECIES-style):**

```
seal(plaintext, recipient_pubkey):
  eph_kp     = generateKeyPair(P-256)
  shared     = ECDH(eph_kp.priv, recipient_pubkey)
  aes_key    = HKDF(shared, info=b'sg-vault-inbox-v1:aead')
  iv         = randomBytes(12)
  ciphertext = AES-256-GCM.encrypt(aes_key, iv, plaintext)
  return concat(eph_kp.pub.raw, iv, ciphertext)

open(envelope, recipient_privkey):
  parse eph_pub, iv, ciphertext = envelope
  shared     = ECDH(recipient_privkey, eph_pub)
  aes_key    = HKDF(shared, info=b'sg-vault-inbox-v1:aead')
  return AES-256-GCM.decrypt(aes_key, iv, ciphertext)
```

The library lives in `sg-inbox-crypto.js` and is unit-testable in Node via `runInThisContext` the same way `app-permissions.js` is.

## 7. Vault-app bridge surface — `sg.inbox.*`

### 7.1 The verbs

| Verb | What it does | Permission key | Owner-only? |
|---|---|---|---|
| `sg.inbox.list({ inbox?, after_file_id?, limit?, include_content? })` | Metadata or content listing. Identical to the server endpoint shape. | `inbox.list` | No — apps can request it. |
| `sg.inbox.fetch({ inbox, file_ids })` | Fetch specific ciphertext blobs. The decryption happens host-side; the app receives plaintext. | `inbox.read` | No — apps can request it. |
| `sg.inbox.markProcessed({ inbox, file_ids })` | Move messages to processed. State-changing but bounded (does not destroy data). | `inbox.markProcessed` | No — apps can request it, but the HUD consent prompt fires per the existing `requestPermission` pattern (Phase 4A app-perms). |
| `sg.inbox.acceptedKeys()` | Read-only listing of accepted-key aliases + fingerprints (NOT the anchors). | `inbox.list` (reuses) | No. |
| `sg.inbox.configure({...})` | Re-write the configure manifest. **Not exposed to apps.** | — | **YES — host kernel only.** |
| `sg.inbox.purge({...})` | Destroy server-side ciphertext. **Not exposed to apps.** | — | **YES — host kernel only.** |

### 7.2 Why owner-only verbs stay host-side

`configure` and `purge` require `write_key` in the header. `write_key` is the highest credential tier; per the existing model (`AppPermissions`'s `vault.delete` is bool-only, always consent-gated), the bridge **does not expose** any verb that would let an iframe escalate to write_key authority. The HUD does not surface a consent prompt for purge or configure because the verb itself is unreachable from the iframe side.

If an app needs to "clean up" processed messages on the user's behalf, the right pattern is the existing `sg.ui.requestPermission` flow but routed to a **host UI prompt** ("App X is asking you to purge N processed messages — Purge / Cancel"). That is a follow-up; v1 of this spec leaves purge owner-only via the Inbox Settings panel.

### 7.3 Wiring into `AppPermissions`

Extend `parsePermissions(appJson)` in `app-permissions.js` to recognise an `inbox` block:

```json
{
  "permissions": {
    "fs": { ... },
    "vault": { ... },
    "inbox": {
      "list":          true,
      "read":          ["agent-alice/", "agent-bob/"],
      "markProcessed": ["agent-alice/"]
    }
  }
}
```

- `inbox.list` — `true | false`. No path scoping (the list is global per vault).
- `inbox.read` / `inbox.markProcessed` — `true | false | string[]` where each string entry is a **sender alias prefix** (mapped via `accepted-keys.json` to the `inbox` token). Trailing `/` means "this alias", literal match means "this alias's specific anchor".
- Default-deny for all three (consistent with `fs.write` etc.).
- Floor: there is no floor concept analogous to `.vault/` for the inbox — every accepted sender is grantable. The non-grantable rule is simpler: **`configure` and `purge` are not in the capability schema at all**, so even `"inbox": { "configure": true }` parses to garbage and is ignored.

### 7.4 Wiring into the kernel handlers

Add an `inbox` capability mapping to `kernel-app-handlers.js` next to `fs` and `vault`. The handler resolves the alias to the `inbox` token via the vault's `accepted-keys.json` (which the kernel has via `dataSource.getFileBytes('.vault/owner/inbox/accepted-keys.json')` — gated by the existing read-key path, not the floor), then calls into the `sg-inbox` library with `enum_key` from the host context.

The iframe never holds `enum_key`. The host kernel does.

### 7.5 Debug pane tab

Add an `<app-debug-inbox>` tab to `<app-debug-pane>` (currently 7 tabs at `app-debug-pane.js:230-232`). It mirrors the Bridge Log tab but filtered to `sg.inbox.*` calls. Pure consumer of `window._appDebug.bridgeCalls`.

## 8. Cross-team interface contract — endpoint mapping

Locking the client to the API team's contract:

| Server endpoint | `sg-inbox.js` method | Notes / gotchas |
|---|---|---|
| `POST /api/vault/inbox/configure/{vault_id}` | `inbox.configure({ append_anchors, enum_key_hash })` | Vault must pre-exist (the brief's #1 gotcha). The client should detect 403 here and surface a "vault not initialised — open Files first" message rather than silently failing. |
| `POST /api/vault/inbox/append/{vault_id}` | `inbox.append({ append_token, payload_b64 })` | **Recipient does not call this method.** Senders call it. Included in the library shape because the same code is reused by the (future) sender path and the comms harness. No auth headers; the token IS the auth. |
| `POST /api/vault/inbox/list/{vault_id}` | `inbox.list({ inbox?, after_file_id?, limit, include_content })` | Metadata-only on refresh; with-content per-sender on click. Pagination via `after_file_id`. |
| `POST /api/vault/inbox/fetch/{vault_id}` | `inbox.fetch({ inbox, file_ids })` | Batch cap 100; `sg-inbox-batcher.js` splits. |
| `POST /api/vault/inbox/mark-processed/{vault_id}` | `inbox.markProcessed({ inbox, file_ids })` | Idempotent; `missing[]` is non-error. |
| `POST /api/vault/inbox/purge/{vault_id}` | `inbox.purge({ inbox, folder:'processed', file_ids? })` | Owner-only. `folder:'processed'` + no `file_ids` = bulk drop. |

**Header rules (locked):**
- `enum_key` goes in `x-sgraph-vault-enum-key` (not `x-sgraph-vault-write-key`).
- `write_key` goes in `x-sgraph-vault-write-key`.
- `access_token` goes in `x-sgraph-access-token`.
- `append` carries no headers (token-is-auth).
- All tokens are **raw hex** — no `tok_` / `enum_` prefixes; the path validator rejects prefixes with `400`, not `403`.

**Payload rules:**
- All `payload` / `content` fields are base64. Use `btoa(String.fromCharCode(...bytes))` or the cleaner `arrayBufferToBase64` helper already in `_common/`.
- `file_id` format `\d{13}_[0-9a-f]{24}\.enc` — never construct one client-side; only round-trip the server's exact strings.

**CORS:**
- `dev.send.sgraph.ai` already permits the three custom headers and accepts null-origin requests (per the brief's CORS notes). The sandboxed app-iframe (null origin) calls the same headers — verify in Phase C.

## 11. Open questions for the human

| # | Question | Why it matters |
|---|---|---|
| 1 | Should the recipient's inbox keypair be **the existing vault PKI key** (Mode 1, already published to the registry) or a **separate inbox-only identity**? | The brief says "a public key per agent working on the vault" — but does "agent" mean the human-owner or the iframe-app? Reusing the vault PKI key simplifies the model; a separate inbox identity decouples mail-routing from signing. |
| 2 | **Curve choice:** P-256 (Web Crypto native, aligns with `secure-channel-envelope.js`) or X25519 (no native Web Crypto, needs `@noble/curves`)? | The API brief documents X25519 in the encryption contract section, but the spec property (ECDH + HKDF + AES-GCM) holds for either. We default to P-256 unless the comms harness has hard-coded X25519. |
| 3 | **Accepted-keys UX:** paste-pubkey only (initial), import-from-PKI-registry, or QR-scan (mobile)? | Affects the `<vault-inbox-settings>` complexity. Phase B ships paste-only; the others queue as follow-ups. |
| 4 | **Does the Inbox section appear in RO-token sessions?** An RO-token session has no `read_key`, so it cannot re-derive `enum_key`. Options: (a) hide the section entirely in RO mode (simplest); (b) store `enum_key` alongside the RO-token in the owner's ro-record so RO-token sessions can read-only the inbox; (c) require the RO-recipient to enter `enum_key` separately. | Affects whether the inbox is "always a main section" or "a main section only when the vault is fully opened". The dev brief's "main section" phrasing suggests (a) — hide entirely under RO — is acceptable. |
| 5 | **Purge ergonomics:** the Settings panel should expose "Purge processed" per sender — but should it also auto-purge after N days, or always require an explicit click? | Default to explicit; revisit when ephemeral-compute lands. |
| 6 | **Decryption failures** (recipient privkey rotated, sender used wrong pubkey, payload corrupt): show as a red row with the file_id but no plaintext, mark-processable so the owner can clear it? Or refuse to mark-process anything that didn't decrypt? | Default to "show as un-decryptable, allow mark-process with confirmation" so a single bad message can't jam the inbox. |
| 7 | **App access on un-configured inboxes:** if an app calls `sg.inbox.list` on a vault whose inbox was never configured, do we (a) return empty + a flag `configured:false`, or (b) auto-configure (would need write_key — owner consent), or (c) error? | Default to (a). Auto-configure is risky from the iframe side. |
| 8 | **Per-anchor rate-limiting / abuse handling on the recipient side** — if a noisy sender fills the inbox (within the 1000-file ceiling), do we expose "remove this anchor" prominently? | Yes — the Settings panel's "Remove key" action also auto-purges that anchor's processed folder. |

## 12. Risks and mitigations

| Risk | Class | Mitigation |
|---|---|---|
| **Key-management UX confusion** — owners have a vault key, a PKI key, an enum_key (derived but felt opaque), and accepted-pubkey records | UX / safety | Surface only what owners need: the Settings tab shows accepted pubkeys with friendly aliases; `enum_key` derivation is automatic and silent; `write_key` is the same one they already use for Push. |
| **Base64 overhead on large payloads** — fetch+decrypt of a 5 MB ciphertext = ~6.7 MB on the wire, decoded once for AES-GCM | Performance | Default `limit:50` with `include_content:true` (per the API brief's 3 MB sum ceiling, the server will reject anything bigger). Only fetch on-demand per sender. Phase B includes a per-message lazy-fetch (click row → fetch one). |
| **Refresh polling cost** — adding a list call to every behind-check tick | Server load / browser cost | Share the existing timer; metadata-only is free server-side; debounce visibility-change + click double-fire (§5). |
| **App permission widening** — exposing inbox.read/list to apps is new attack surface | Security | (a) Floor: configure and purge never exposed. (b) Default-deny on `inbox.*` parses. (c) Consent prompt on first-use (mirrors `vault.delete` consent pattern). (d) `<app-debug-inbox>` makes calls auditable. |
| **Cross-team contract drift** — the API team modifies a header or token format | Coordination | The `sg-inbox.js` library is a single chokepoint. Any contract change has exactly one client-side touchpoint. Add a `sg-inbox.contract.md` line-locked summary in the lib folder mirroring this section. |
| **Outside-version-control surprise** — vault clones don't get inbox messages | Mental model | Document explicitly in the Inbox view header: "Inbox messages are not part of vault history. Clone this vault and the inbox starts empty on the new device." Mirror in the `proposed/inbox.md` reality doc. |
| **Vault-must-pre-exist on configure** — first-time owners hit a 403 | UX | The Inbox nav entry is disabled (with a tooltip "Open a vault file first") until `vault-shell._onVaultOpened` has completed an initial push so the manifest exists with `write_key_hash`. |
| **RO-token sessions lacking `enum_key`** — section appears broken | UX | Default to hiding the Inbox nav entry under RO mode (open question #4). |

## 13. Acceptance Criteria (mirrored from the dev brief)

| # | Criterion (from dev brief) | This spec's verification path |

| 1 | The SG CLI supports the inbox | Design contract here; implementation in sgit-ai (DEFERRED Phase D). The contract in §8 locks the CLI to the same six endpoints + headers + token format. |
