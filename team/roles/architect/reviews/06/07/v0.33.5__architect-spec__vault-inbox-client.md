## 0. The reframing (why this is revision 2)

Revision 1 of this spec baked PKI, X25519, "accepted public keys", and a mail-reader UI into the vault layer. That was wrong. The **server is PKI-blind** — it stores only opaque token-hashes and ciphertext bytes; it has no concept of "public key", "sender identity", or "encryption". The "`append_token = SHA256(pubkey)`" line in the API brief is a **client convention**, not a server rule.

The vault's native role is therefore narrower than r1 implied: it is a **transport-and-notification substrate** that holds the vault-owner credentials (`enum_key`, `write_key`), runs the poll loop, gates the bridge, and emits "new messages arrived" events — exactly the shape of the existing "new commits arrived → auto-pull" loop for sgit refs. **Apps own the semantics** (token derivation, encryption, sender identity, mail metaphor).

This revision deletes ~60% of r1 (the entire encryption/PKI/settings-UI stack) and adds the **auto-pull + subscribe** loop that the human asked for.

## 1. Layering (locked)

| Layer | Owner | Responsibility | This spec covers? |
|---|---|---|---|
| **L1 — Server (SG API)** | SG API team | Token-and-blob routing. Stores `SHA256(append_token)`, `SHA256(enum_key)`, `SHA256(write_key)`, and ciphertext bytes. **PKI-blind.** | No — already shipped. |
| **L1.5 — Vault Native** | Vault team (this work) | Holds `enum_key`/`write_key` for the owner. Forwards bridge calls. Runs poll loop. Emits events. Persists watch-list. **Also PKI-blind.** | **YES** — this is the whole spec. |
| **L2 — Vault App** | App authors | Chooses token-derivation recipe. Encrypts/decrypts. Manages sender identity. Maintains "who is alice" mappings. | No — app concern. |
| **L3 — App UX** | App authors | "Accepted public keys" UI, message reader, reply composer, the mail metaphor. | No — app concern. |

The dev brief's "main UI section / check on refresh / show how many messages and from which key" partly lives at L1.5 (count, anchor hash, last-checked, auto-pull toggle) and partly at L3 (which-key-is-alice, decrypted message list). **This spec covers only the L1.5 surface.** Anchors are displayed as opaque short hex (like commit SHAs); friendly labels are optional cosmetic strings the owner can attach without semantic meaning.

## 2. What the SG/API actually knows (and doesn't)

| The server stores | What it is | What the server knows |
|---|---|---|
| `write_key_hash` | `SHA256(write_key)` — opaque hex | Compared on `configure` / `purge` |
| `append_anchors[]` | `SHA256(append_token)` for each accepted slot | Compared on `append` |
| `enum_key_hash` | `SHA256(enum_key)` | Compared on `list` / `fetch` / `mark-processed` |
| Ciphertext blobs | Opaque bytes, base64 on the wire | Stored at `inbox/{matched_anchor}/{ts}_{rand}.enc`; never decoded |

**The server has no opinion** on whether `append_token` came from `SHA256(pubkey)`, a random invitation seed, or a coin toss. It just checks `SHA256(presented) == stored`. The same is true for `enum_key`. This is the property the vault layer inherits: **opaque tokens in, opaque blobs out**.

## 3. Vault-held credentials (L1.5)

The vault holds two credentials on the owner's behalf and uses them transparently when forwarding app bridge calls:

| Credential | Source | Used for | Persisted? |
|---|---|---|---|
| `enum_key` | Derived once from `read_key`: `enum_key = SHA256("sg-inbox-enum:" \|\| read_key_raw_bytes).hex()`. | Header `x-sgraph-vault-enum-key` on `list` / `fetch` / `mark-processed`. | Re-derived per session, in-memory only. Never sent to apps. |
| `write_key` | Existing vault `write_key_hex`. | Header `x-sgraph-vault-write-key` on `configure` / `purge`. | Already lives in `sg-vault.js`. Never sent to apps. |

Apps never see these keys. They call e.g. `sg.inbox.list({...})` and the vault attaches the header.

**Anchors and tokens are app-owned.** Apps call `sg.inbox.configure({ append_anchors: [...] })`; the vault adds `enum_key_hash` automatically. Apps call `sg.inbox.append({ vault_id, append_token, payload })` for outbound messages and the vault forwards verbatim (no auth header — the token is the auth).

Note that this maps the four-tier capability model from the API brief onto only **two layers** at the vault: vault-owner credentials (enum_key, write_key) and pass-through tokens (append_token, append_anchor). `private_key` doesn't appear at L1.5 at all — it's an L2 concern.

## 4. Vault-side persistent state

One file in the vault tree, encrypted with `read_key`, committed normally:

`.vault/inbox/config.json`:

```json
{
  "enabled":          true,
  "auto_pull":        false,
  "poll_interval_ms": 30000,
  "anchors":          ["abc...def", "55ee...aa99"],
  "labels":           { "abc...def": "alice", "55ee...aa99": "bob" }
}
```

| Field | Purpose |
|---|---|
| `enabled` | Master switch. If false, the nav entry hides and the poll loop is dormant. |
| `auto_pull` | If true, the poll tick also fetches ciphertext for new messages and emits `inbox-messages` with content. If false, the tick only emits `inbox-changed` with counts. |
| `poll_interval_ms` | Cadence floor (debounced). Default 30 s, matching `_scheduleBehindCheck`. |
| `anchors` | The watch-list. Apps update this via `sg.inbox.configure(...)`. The vault reflects updates here so a clone of the vault re-enables polling on the same anchors. |
| `labels` | Optional cosmetic strings. The vault has no semantic for them — pure display. Apps may write labels (e.g. "alice's pubkey fingerprint") if they wish; the vault just shows them. |

**No PKI here.** No pubkeys, no curves, no decrypted bodies. The `labels` field is the closest thing to identity and it is opaque to the vault.

In-memory inbox cache (sessionStorage, not committed): a small ring buffer of "messages arrived since this tab opened" so the status panel can show recency without re-polling. Capped at 200 entries; metadata-only by default; full ciphertext only when `auto_pull` is on.

## 5. Auto-pull / refresh integration

This is the headline new behaviour and the explicit ask: **mirror the existing "check for new commits → auto-pull" loop for inbox messages.**

| Loop | Existing (sgit refs) | New (inbox) |
|---|---|---|
| Trigger | `_scheduleBehindCheck` on visibility-change, on user click, on debounce | `_scheduleInboxCheck` on the same triggers |
| Cheap probe | `GET /api/vault/refs/...` returning current ref head | `POST /api/vault/inbox/list/{vault_id}` with `include_content: false` |
| Diff | Compare remote head to local | Diff entries by `file_id` against the in-memory "seen" set |
| Auto-action (if configured) | `sg-vault.pull()` | `sg.inbox.fetch(...)` per anchor + populate cache + emit |
| Surfacing | Status pill on `vault-header` ("↓N to pull") | Badge on `vault-nav` + count in `vault-status-bar` |

Implementation lives in `sg-inbox-poll.js` (pure, DOM-free, Node-testable). The vault shell registers it as a sibling to `_behindCheckTimer` so the existing visibility handler fires both probes. **One shared cadence, two probes.**

Emitted events on the existing `window.sgraphVault.events` bus:

| Event | When | Detail |
|---|---|---|
| `inbox-changed` | Metadata count differs from last tick | `{ total, per_anchor: { [anchor]: count } }` |
| `inbox-messages` | Auto-pull fetched new ciphertext | `{ entries: [{ inbox, file_id, received, content_b64 }] }` |
| `inbox-config-changed` | `config.json` rewritten (by an app or the owner UI) | `{ before, after }` |
| `inbox-error` | Poll or fetch failed | `{ code, message, http? }` |

Apps subscribe via `sg.inbox.subscribe(callback)` (bridge method, §6). The vault relays events into the app iframe.

## 6. Vault-app bridge surface — `sg.inbox.*`

All six server endpoints exposed, plus three vault-native helpers (`status`, `subscribe`, `checkNow`, `setAutoPull`). Each gated by a per-app `inbox.*` capability declared in `app.json`. Default-deny.

```
// Transport (1:1 with server endpoints; vault attaches the right headers)
sg.inbox.configure({ append_anchors })                            // vault adds enum_key_hash
sg.inbox.append({ vault_id, append_token, payload })              // outbound to remote vault
sg.inbox.list({ inbox?, after_file_id?, limit?, include_content? })
sg.inbox.fetch({ inbox, file_ids })
sg.inbox.markProcessed({ inbox, file_ids })
sg.inbox.purge({ inbox, file_ids?, folder })

// Vault-native (no server call — read local state / drive the loop)
sg.inbox.status()              // { enabled, auto_pull, total, per_anchor, last_checked_ms, error? }
sg.inbox.subscribe(callback)   // delivers inbox-changed / inbox-messages / inbox-config-changed
sg.inbox.checkNow()            // force one poll cycle; returns status when done
sg.inbox.setAutoPull(boolean)  // owner-grant required (writes config.json)
```

| Verb | Vault headers added | App capability key | Notes |
|---|---|---|---|
| `configure` | `x-sgraph-vault-write-key`, `x-sgraph-access-token` | `inbox.configure` | App supplies anchors; vault supplies `enum_key_hash`. |
| `append` | none (token is auth) | `inbox.append` | Outbound; remote vault_id required. Bridge forwards verbatim. |
| `list` | `x-sgraph-vault-enum-key` | `inbox.list` | Metadata-only default. |
| `fetch` | `x-sgraph-vault-enum-key` | `inbox.read` | Batch ≤100 enforced client-side. |
| `markProcessed` | `x-sgraph-vault-enum-key` | `inbox.markProcessed` | Idempotent. |
| `purge` | `x-sgraph-vault-write-key`, `x-sgraph-access-token` | `inbox.purge` | Owner-grant. |
| `status` | none | `inbox.list` (reuses) | Reads in-memory state. |
| `subscribe` | none | `inbox.list` (reuses) | Relays bus events. |
| `checkNow` | uses `list` header | `inbox.list` (reuses) | Force-debounce. |
| `setAutoPull` | none (writes `config.json` via vault) | `inbox.configure` (reuses) | Rewrites `.vault/inbox/config.json`. |

Example `app.json`:

```json
{
  "permissions": {
    "inbox": {
      "configure":     true,
      "append":        true,
      "list":          true,
      "read":          true,
      "markProcessed": true,
      "purge":         false
    }
  }
}
```

There is **no per-anchor scoping** in this revision. Anchor-scoped grants (e.g. "this app can only read messages on anchor `abc...def`") are a Phase D consideration; v1 grants are coarse (any-or-none per verb) to keep the bridge gate trivial. This is consistent with how `fs.write: true` works today.

**No `sg.inbox.open()` / decryption verb.** Decryption is an L2 concern. Apps receive base64 ciphertext from `fetch` / `inbox-messages` events and decrypt with their own primitives.

## 7. Vault UI surface (minimal)

The dev brief asks for a main left-nav section. This revision keeps it **observability-only** — no message reader, no settings tab for pubkeys (apps own that).

### 7.1 Nav entry

A 4th item in `vault-nav.js` between SGit and Settings:

```
Files / SGit / Inbox [3] / Settings
```

The badge shows total un-processed count from `sg.inbox.status().total`. Click → activates the `vs-view-inbox` slot.

### 7.2 `<vault-inbox-status>` panel

A single small component showing:

- Total message count + breakdown by anchor (anchor short-hex + optional label + count + last-received timestamp).
- Last-checked timestamp.
- Auto-pull toggle (writes `config.json`; requires owner — not behind app grant since this is the owner-side UI).
- "Check now" button.
- "Disable inbox" toggle (sets `enabled: false` in config).
- A read-only list of watched anchors (clickable to copy hex; no add/remove here — apps add anchors via `configure`).
- A link to the debug pane's Inbox tab for raw API logs.

**That's the whole section.** No message bodies, no "Mark processed" button, no per-message rows. If you want a mail reader, write a Vault App.

### 7.3 What's deliberately absent

- `<vault-inbox-view>` with a sender/message tree → app concern.
- `<vault-inbox-settings>` with pubkey CRUD → app concern.
- A decrypted message body pane → app concern.
- A "Reply" composer → app concern.

This pruning is the entire point of revision 2.

## 8. AppPermissions extension

`app-permissions.js` gains one new group:

```js
parsePermissions({ inbox: { configure, append, list, read, markProcessed, purge } })
  // each value: boolean (default false)
```

`can(perm, 'inbox.<action>', null)` — no path argument needed (no per-anchor scoping in v1). The dispatch in `can()` adds a `grp === 'inbox'` branch that returns the boolean from the parsed grant. Default-deny everywhere.

Floor: there is no floor concept. The schema is closed (six known verbs); unknown verbs return false. This sidesteps the path-scheme question from r1 entirely.

## 9. sgit CLI (hand-off, design-only)

The sgit CLI gets the same L1.5 surface in Python:

- A `sgit_inbox/client.py` module mirroring `sg-inbox.js` (6 endpoints, same headers, same batch caps).
- A `sgit inbox check` command that runs one poll cycle and prints counts per anchor.
- A `sgit inbox pull` command that runs check + fetch + writes raw ciphertext to stdout or files.
- `enum_key` derived the same way (`SHA256("sg-inbox-enum:" || read_key_bytes).hex()`) so a vault opened in either tool sees the same inbox.

That's the contract. Implementation lives in `SGit-AI/SGit-AI__CLI`; not this repo.

## 11. Open questions

| # | Question | Why it matters |
|---|---|---|
| Q1 | Is the deterministic `enum_key = SHA256("sg-inbox-enum:" \|\| read_key_bytes).hex()` derivation acceptable? Alternative: random per-vault, stored in `.vault/inbox/enum.enc`. Deterministic = zero UX cost; random = stricter compartmentalisation if `read_key` is ever exfiltrated. | AppSec sign-off required either way. |
| Q2 | Default `poll_interval_ms`: reuse the 30 s `_scheduleBehindCheck` cadence, or longer (60–300 s) given inbox isn't latency-critical for most flows? | Server load and UX feel. |
| Q3 | Per-anchor capability scoping in v1 (e.g. `inbox.read: ["abc...def"]`), or coarse boolean grants only? Coarse = simpler bridge; per-anchor = principle of least privilege. Recommendation: coarse for v1, scoping in a follow-up. | Bridge complexity. |
| Q4 | Should the inbox status panel be visible in RO-token sessions (which have `read_key` and therefore can re-derive `enum_key` and list metadata)? | UX consistency. Default: yes, view-only; `setAutoPull` and `purge` disabled. |
| Q5 | `sg.inbox.append({ vault_id, ... })` is an **outbound** call to a remote vault. Does the vault enforce any cross-origin policy (allowlist of target vaults), or trust the app entirely? | Abuse / exfiltration vector. Default: no allowlist in v1; revisit if abuse surfaces. |
| Q6 | When `auto_pull` is on and a fetch fails (network, 403, oversized), do we surface a persistent error toast in the owner UI, or just an `inbox-error` event? Recommendation: both — toast + event, with a "dismiss + retry next tick" pattern matching `_behindCheckError`. | Owner observability. |

Notice none of these are about cryptography, PKI, curves, or sender identity. That's the point.

## 12. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Auto-pull cache grows unbounded | Ring buffer capped at 200 entries; metadata-only fallback when capped; cache cleared on tab close. |
| Two tabs both fetch + mark-process the same `file_id` | Server `mark-processed` is idempotent (API brief gotcha #5). No client work needed. |
| Server reads on every refresh tick add cost | Metadata-only default; same cadence as the existing ref check; no new poll loop. |
| App with `inbox.configure` overwrites another app's anchors | `configure` accepts the full anchor list, so the LAST app wins. Mitigation: `sg.inbox.configure` semantics are "merge into current set" at the vault, not "replace" — apps can only ADD anchors; removal requires owner UI or `purge`. **NEW CONSTRAINT FROM R2.** |
| Coarse `inbox.read: true` lets one app read another's sender slots | Acceptable for v1 (we don't have per-anchor scoping yet); flagged as Q3 follow-up. |
| Outbound `sg.inbox.append` abused as a backchannel | Q5. Defer to follow-up unless abuse surfaces. |
| Vault clones don't see inbox messages on the new device | Document explicitly in the status panel: "Inbox messages live on the server only — clones start empty." |
