## 0. TL;DR — What Changed Since 05/12

1. **NEW (biggest finding): the S3 backend itself double-counts every read and delete.** `Storage_FS__S3.file__bytes()`, `file__delete()`, and `file__str()` each call `file__exists()` *internally* before doing the real op (`Storage_FS__S3.py:46, 53, 81`). The 05/12 audit costed `file__bytes` as **1 GetObject**; in reality it is **1 HeadObject + 1 GetObject**. When a service *also* prechecks existence (most do), a single logical "read" is **3 S3 calls** (Head + Head + Get), and a single "delete" is **3 S3 calls** (Head + Head + Delete). Every per-op count in the 05/12 review is therefore **under-stated by ~1.5–2×**.
2. **REGRESSION: `GET /vault/zip` now downloads the entire vault to compute its cache key.** `vault_content_hash()` reads **full payload bytes** of every file just to measure `len(payload)` (`Service__Vault__Zip.py:33–36`). This runs on **every** zip request, **including cache hits**. The 05/12 review said "the list runs even on cache hit" — it's now far worse: the whole vault is pulled into Lambda even when the zip is already cached.
3. **NEW surface: Vault Inbox** (`Service__Vault__Inbox.py`, landed since 05/12 — commits `9d727b5`, `e365c60`) was not in the 05/12 map. It is *carefully* built (list paths use metadata only, no per-file reads — see `I-1`/`I-2` comments) but still inherits the backend double-call tax on every `fetch`/`mark_processed`/`purge`.
4. **UNCHANGED: none of the 05/12 vault wins (O-3, O-6) shipped.** `delete_vault` still deletes one-by-one; reads still pre-Head; no batch-delete; no billing/usage-event primitive.

## 1. Corrected Cost Model (the backend tax)

`Storage_FS__S3` wraps the osbot-aws primitives. The osbot-aws `file_bytes()` does a raw `get_object` that **raises** on a missing key (`S3.py:219–224`); that is *why* the wrapper guards it with a `file__exists()` HeadObject. So the true per-primitive cost is:

| `Storage_FS__S3` method | S3 calls | Breakdown |
|---|---:|---|
| `file__exists` | 1 | HeadObject |
| `file__bytes` | **2** | HeadObject (`:46`) + GetObject |
| `file__json` | **2** | = `file__bytes` |
| `file__str` | **2** | HeadObject (`:81`) + GetObject |
| `file__save` | 1 | PutObject |
| `file__delete` | **2** | HeadObject (`:53`) + DeleteObject |
| `folder__files__all` | ⌈N/1000⌉ | paginated ListObjectsV2 (pagination OK — `S3.py:195–217`) |
| `folder__folders` | ⌈N/1000⌉ | same list, key-prefix folded client-side |

**Consequence:** a service that does the common `if file__exists(p): file__bytes(p)` pattern pays **3 calls** for one read. The single highest-leverage fix in the whole audit is to make `file__bytes`/`file__str`/`file__delete` **catch the 404 instead of pre-Heading**, and to stop services pre-checking existence around them.

## 3. The Zip Regression (highest single-op cost)

`Service__Vault__Zip.get_or_create_zip()` flow today:

```
get_or_create_zip(vault_id)
  ├─ _check_vault_write_key            manifest cache (0 warm)
  ├─ file__exists(manifest_path)  :64  1 Head   ❗ bypasses _load_manifest cache — redundant
  ├─ vault_content_hash()         :67
  │     ├─ list_files()                1 List
  │     └─ for f in N: read(f)         3N S3 calls + FULL payload egress of EVERY file  ❗❗
  ├─ zip_exists()                 :76  1 Head
  │     ├─ HIT  → (returns; but everything above already ran)
  │     └─ MISS → build_zip()     :79
  │                ├─ list_files()     1 List
  │                └─ for f in N: read(f)   3N + full egress AGAIN
  │            → file__save(zip)       1 Put
  └─ list_files()                 :82  1 List   ❗ third list, only to get len()
```

Two structural problems:

- **P-1: the cache key is computed by reading file bytes.** `vault_content_hash` only needs each file's **size**, but calls `read()` which downloads the whole object (`Zip.py:34`). On a cache *hit* this means the entire vault is streamed into Lambda just to confirm "the zip already exists." For a 500 MB vault that is 500 MB of pointless egress + Lambda memory per zip poll.
- **P-2: `list_files()` is called three times** and the manifest existence is checked outside the cache (`:64`).

This is the clearest "money on the table" item and it is strictly worse than the 05/12 description.

## 4. New Surface — Vault Inbox (not in 05/12 map)

Generally the most carefully-built vault code: `inbox_list` derives `received` timestamps from filenames (no reads — `:160`), enumerates folders via one `folder__folders` list, and reads bytes only for the paged window when `include_content` is set. Caps are in place (`INBOX_MAX_FILES`, `INBOX_BATCH_MAX_FILE_IDS`). Remaining S3-cost notes:

| Inbox op | S3 calls | Note |
|---|---:|---|
| `append` | 1 list + 1 Put | list is a count-only capacity guard (`:116`) — acceptable |
| `inbox_list` (all folders, F folders) | **1 + F lists** | one `folder__folders` + one `folder__files__all` per folder |
| `inbox_fetch` (K ids) | **3K** | each = Head (`:192`) + `file__bytes`(Head+Get) |
| `mark_processed` (K ids) | **~5K** | per id: Head + (Head+Get) + Put + (Head+Del) — S3 has no move; copy+delete unavoidable, but the prechecks add 2 Heads/id |
| `purge` processed (bulk) | **1 list + 2M** | each delete = Head+Del |

The inbox doesn't need redesign — it just inherits the backend double-call tax (§1). Fixing §1 fixes the inbox for free.

## 5. Memory-FS Caching Observations

- **`_manifest_cache` is correct and worth leaning on harder.** Manifests are immutable in their auth fields after first write, so the Lambda-lifetime cache never needs invalidation within an instance. Good.
- **But two services hold separate caches.** `Service__Vault__Pointer._manifest_cache` and `Service__Vault__Inbox._manifest_cache` are distinct dicts (`Pointer.py:26`, `Inbox.py:33`). A request that touches both reloads the same manifest twice (cold). Minor; a shared manifest-cache object passed to both would remove it.
- **Zip service bypasses the cache** for its manifest existence check (`Zip.py:64`) — should go through `_load_manifest`.

## 6. Prioritised Fix List (vault-scoped, refreshed)

Ordered by leverage / risk. All are behaviour-preserving (Explorer-safe — no feature change).

| # | Fix | Where | Saves | Risk |
|---|---|---|---|---|
| **V-1** | Make `file__bytes`/`file__str`/`file__delete` catch the 404 (`get_object`/`delete_object` ClientError) instead of pre-`file__exists`. | `Storage_FS__S3.py:44–55, 78–83` | ~1 Head on **every** read/delete, system-wide | Low — needs the `Storage_FS__Memory` backend to match semantics (return `None`/`False` on miss). Cover with tests. |
| **V-2** | Drop the service-level `file__exists` precheck before a `file__bytes` (rely on `None` return). | `Pointer.read:98`, `_batch_read:259`, `_cas_write:268`, `write_if_match:126` | another Head per read | Low |
| **V-3** | Zip cache key from **size metadata, not bytes**: add a `file__size`/stat primitive (HeadObject → `ContentLength`) and use it in `vault_content_hash`. | `Zip.py:33–36` | turns 3N + full egress into N Heads; **eliminates full-vault download on cache hit** | Medium — new primitive + tests |
| **V-4** | Compute `list_files()` **once** in `get_or_create_zip`; reuse for hash, build, and count. Use `_load_manifest` for the existence check. | `Zip.py:58–90` | 2 lists + 1 Head per zip | Low |
| **V-5** | Batch-delete in `delete_vault` and inbox bulk `purge` (S3 `DeleteObjects`, ≤1000/call). | `Pointer.delete_vault:217–220`, `Inbox.purge:234–238` | N delete calls → ⌈N/1000⌉ | Medium — needs a `files__delete(paths)` primitive |
| **V-6** | Cap / gate anonymous `POST /vault/batch` read-only. | `batch_read:249`, route | bandwidth-amplifier mitigation | Low (product call — confirm cap) |
| **V-7** | Share one manifest cache between Pointer + Inbox services. | `Pointer.py:26`, `Inbox.py:33` | 1 cold manifest reload when both touched | Low |

**Sequencing:** V-1 first (it silently improves every other number, including the inbox), then V-3/V-4 (kill the zip regression), then V-2, then V-5/V-6/V-7. Each is independently shippable and testable against the in-memory stack.

## 7. Carry-Over From 05/12 (still valid, billing track)

The billing/licensing half of the 05/12 review is **untouched** in code: there is still no `usage_event__append` hot-path primitive, and vault reads/writes remain unmetered. That track is out of scope for this refresh (the request was "S3 calls on vault ops only"), but the §1 fixes are a prerequisite — once `usage_event__append` lands it must be **one PutObject, no precheck**, which V-1 guarantees by making fire-and-forget writes actually fire-and-forget.
