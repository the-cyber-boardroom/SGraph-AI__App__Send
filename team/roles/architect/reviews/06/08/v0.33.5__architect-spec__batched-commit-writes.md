## 1. Architect review of the analysis

Both briefs are accurate. I verified every load-bearing claim against the code before designing:

| Claim | Verdict |
|---|---|
| Server `/api/vault/batch/{vault_id}` supports **write** ops | **TRUE** — `Service__Vault__Pointer.batch` handles `op:'write'` (`{op,file_id,data:b64}`), `write-if-match` (CAS) and `delete`; requires access-token + write-key for non-read batches. |
| Client `vaultBatch` already supports write ops | **TRUE** — `sg-send.js:199`, sends write-key header, routes through `_fetch` (adds the access token), auto-chunks at 50. |
| A commit = ~5 PUTs | **TRUE** — blob (`addFile→store`), tree + commit (`_commit→createTree/createCommit→store`), clone-ref (`_commit→writeRef`), named-ref + branch-index (`push`). |
| The per-write preflight is **uncacheable** | **TRUE** — content-addressed object URLs are unique each time; the batch URL `…/batch/{vid}` is fixed → its OPTIONS *does* cache under `Access-Control-Max-Age`. |

So the briefs' core recommendation — *batch the commit's writes into one POST* — is correct and needs **no backend change**.

### One design change vs the brief

The brief proposed a new `objectStore.storeMany(objects)` and rewiring `_commit`/`push` to collect-then-store. I chose a **transparent write-batch scope** instead:

- A batch buffer on the object store. While a batch is open, the **existing** `store()` and `writeRef()` calls *stage* the write instead of issuing a PUT; one `flushBatch()` sends them as a single ordered `POST /batch`.
- **Re-entrant** (`_withBatch`): nested scopes share the outermost batch, so `addFile`'s blob and the `_commit` it triggers collapse into one request.

**Why this is better:** zero changes to the many `store()`/`writeRef()`/`createTree`/`createCommit`/`addFile` call sites; it captures the **ref** writes too (not just objects); and it composes (file-write + commit + index in one batch). Smaller diff, lower blast radius on the core commit path.

## 2. What was implemented

### 2.1 Write-batch scope — `SGVaultObjectStore`
- `beginBatch()` / `flushBatch()` / `discardBatch()` / `get batching()` / `_stage(filePath, bytes)`.
- `store(ciphertext)`: when batching → compute the content id, **stage** `{filePath, bytes}`, return the id (no network); else → PUT as before. (The id is the ciphertext hash, so it's known without a round-trip.)
- `flushBatch()`:
  1. **Order** staged writes `bare/data/` → `bare/indexes/` → `bare/refs/` (a ref/index must never be written before the object it points at; the server processes batch ops in array order).
  2. One `vaultBatch(vaultId, writeKey, ops)` → `POST /batch` (auto-chunks at 50; a commit is ~5).
  3. On success, populate the imm in-memory cache for the data ops (so a read-back is free).
- `_abToB64` helper (bytes → base64 for the batch `data` field).

### 2.2 Ref/index writes join the batch — `SGVaultRefManager`
- Constructor now takes the `objectStore`. `writeRef` / `writeBranchIndex` call `_putOrStage(filePath, bytes)`: stage into the object store's batch if one is open, else PUT directly.

### 2.3 Re-entrant batch wrapping — `SGVault`
- `_initManagers` passes the object store to the ref manager.
- `_withBatch(fn)`: opens a batch (if none open), runs `fn`, flushes once; **re-entrant** — if a batch is already open it just runs inline and lets the outermost scope flush; on error, `discardBatch()` + rethrow.
- `_commit` body wrapped in `_withBatch` → tree + commit + clone-ref in one batch.
- `create` wraps initial-commit + named-ref + branch-index → a brand-new vault is **one** request.
- `push` wraps named-ref + branch-index → one request.
- `addFile` / `addFiles` / `updateFile` wrapped → the **blob** joins the commit's batch (the others — rename/move/remove, folder ops — store no blob, so `_commit`'s own batch already covers them).

### 2.4 What did NOT change
- The batch endpoint, protocol, commit content, object ids, and ref semantics are **identical** — only the *transport* changed (N PUTs → 1 POST). Inbox append and read paths are untouched. Non-batch callers behave exactly as before (the buffer is opt-in per scope).

## 3. Before / after (one message send)

| | Before | After |
|---|---|---|
| Commit object/ref writes | 3 objects + 1 clone-ref = **4 PUTs** | **1 POST** (addFile batch) |
| Push | named-ref + index = **2 PUTs** | **1 POST** |
| Write-side preflights | ~6 OPTIONS, **all uncacheable** (unique URLs) | 2 OPTIONS, **cacheable** (fixed batch URL) → ~0 after the first send |
| Vault creation | 5 writes | **1 POST** |

Per the brief's projection: one-message total drops ~20 → ~12 immediately, and the write side trends to ~1 request once the batch preflight caches. (Compounds with the imm-cache + reconcile work already shipped this branch.)

## 4. Correctness analysis

- **Ordering.** `flushBatch` sorts objects-before-refs, so within a batch every ref/index is written after its target object. The named-ref (in a later `push` batch) points at a commit already persisted by the commit batch. No dangling pointer is ever published.
- **Flush-failure rollback (REV 2 — fix for the SG/API team's blocking issue).** `_commit` advances `_headCommitId` (and clears `_settingsDirty` / sets `_currentSettingsEntry`) **inside** `fn`, but the writes only land at `flushBatch()`. The first cut left a regression: if the flush threw, `discardBatch()` dropped the staged writes yet the client was left **ahead** of the server, and the next commit would build on a phantom parent → a dangling pointer on the next push (self-healing only on reload). **Fixed:** `_withBatch` now snapshots `{_headCommitId, _namedHeadId, _settingsDirty, _currentSettingsEntry}` before `fn` and **restores them in the catch** before rethrowing. This reinstates the pre-batch semantics — head advances only on a durable write, so a retry re-stages from the correct parent and self-heals. (The in-memory tree mutation is intentionally not rolled back; that was already the pre-batch behaviour and self-corrects once head is restored.) `push` was already correct — it sets `_namedHeadId` *after* `_withBatch` returns.
- **Re-entrancy.** `_withBatch` only flushes (and snapshots/restores) at the outermost scope, so `addFile → _commit` is one batch, not two, and a failed `addFile` rolls back to its pre-call head. A direct `_commit` (e.g. `setName`) opens and flushes its own.
- **Cache truth.** The imm cache is populated **after** a successful flush, so it never holds bytes the server rejected.
- **`>50` ops caveat.** A normal commit is ~5 ops, so "one POST per commit" holds for the message-send case. `addFiles` bulk-add can stage `>50` → `vaultBatch` splits into sequential chunks (>1 POST). Ordering still protects the server (refs are in the last chunk; a chunk that throws stops the rest and rolls back the client head), but the multi-POST window means a bulk-add isn't a single atomic request. Acceptable — bulk-add is rare and the rollback keeps the client consistent.
- **Back-compat.** No batch is opened unless a wrapped method runs; every other path (`store`/`writeRef` called outside a scope) PUTs as before. The full loader suite (incl. branch-index, mem-cache, composite, kernel) is green.

## 6. Layered batching — where this sits

The briefs frame three stacking layers:

1. **App layer (commit less often — append, don't rewrite the transcript).** *App-team work (MVP A).* Not this change.
2. **Commit layer (batch a commit's writes).** ← **this change.** Client-library only.
3. **Read layer (batch reads; drop read-backs).** `batchLoad` already batches reads; trimming post-commit read-backs is a follow-up (would need batch-write responses to return the new HEAD).

This delivers layer 2 in full. Layers 1 and 3 remain available and compound.

## 7. Follow-ups (not in this change)

- **Drop post-commit read-backs** (waterfall #15/#16/#19) — the batch-write response already returns per-op `status:'ok'`; if we trust it, the reconcile read-backs can go. Needs a careful look at the reconcile-on-open interaction.
- **`Access-Control-Max-Age` on the batch endpoint** — confirm the server/CloudFront sends a generous max-age so the single batch preflight actually caches across sends (server/devops knob; the client change makes it *possible*).
- **Pause the embedded parent kernel's poll while a child is mounted** (waterfall #2/#20) — unrelated to batching; separate small fix.
