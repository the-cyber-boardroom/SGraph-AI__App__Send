## 0. Why this plan exists

Observed live: the **Comms Agent** vault app (an HTML app authored *inside* a writable vault) issues **~20 HTTP requests to send one chat message**, and those requests fan out into a comparable number of S3 calls and Admin-Lambda round-trips on the server.

This plan dissects the **send (write) path** specifically and splits the fix into three levers across two teams. It is the implementation spec for the two levers the **backend (Explorer) team owns** and a handoff brief for the one the **vault (UI library) team owns**.

### The send, measured

One message = an optimistic commit to the app's own vault **+** an inbox append to the peer. The commit alone produces **5 writes**: 3 content-addressed objects (blob + tree + commit) + clone ref + named ref. Client-side detail is in the storage-I/O refresh; this plan is about what each of those writes costs **on the server**.

### Per-write server cost (today, warm Lambda)

For each `PUT /api/vault/write/...` (`Routes__Vault__Pointer.py:91`):

| Step | Code | Cost |
|---|---|---|
| Access-token check | `check_access_token` → `admin_service_client.token_lookup` (`Routes__Vault__Pointer.py:52`, `Admin__Service__Client.py:23`) | **1 HTTP round-trip to the Admin Lambda, per write, uncached** |
| Write-key check | `_check_vault_write_key` → `_load_manifest` (`Service__Vault__Pointer.py:65`) | 0 S3 warm (manifest cached — already good) |
| Store object | `storage_fs.file__save` (`Service__Vault__Pointer.py:91`) | 1 S3 PutObject (irreducible) |

So an un-batched send = **5 PutObjects + 5 Admin round-trips + 5 Lambda invocations**. The PutObjects are irreducible (5 distinct objects); the auth round-trips and invocation count are pure overhead. Reads on the same path (refs, batch-read) additionally pay the backend double-call tax from the refresh (V-1): every `read`/`_batch_read` is `file__exists` **+** `file__bytes` = HeadObject + GetObject.

## 1. The three levers and who owns them

| # | Lever | Effect | Owner | Status |
|---|---|---|---|---|
| **#1** | **Token-validation cache** — memoise `token_lookup` results for the Lambda lifetime (TTL) | Collapses N per-write Admin round-trips → 1 | **Backend / Explorer (this session)** | This plan, §2 |
| **#2** | **Catch-404 reads** — stop pre-`HeadObject`-ing before every read (V-1 + V-2 from the refresh) | Drops every read/delete from 2–3 S3 calls → 1 | **Backend / Explorer (this session)** | This plan, §3 |
| **#3** | **Batch the commit** — client sends the 5 commit writes as one `POST /api/vault/batch` instead of 5 PUTs | 5 invocations/auth-checks/preflights → 1 | **Vault team (UI library)** | This plan, §4 (handoff) |

**Why the split:** #1 and #2 are backend service/storage changes in `sgraph_ai_app_send/lambda__user/`. #3 is purely in the browser library `sgraph_ai_app_send__ui__vault/.../sg-vault/` (object-store, ref-manager, commit flush) — owned by the vault team. The backend already exposes everything #3 needs (`POST /api/vault/batch` supports write ops today — `Service__Vault__Pointer.batch:165`), so the two tracks are independent and can land in any order.

**Convergence:** #3 multiplies the value of #1 and #2 — when the client batches, the server does **one** auth check (cached after #1) and **one** invocation for the whole commit. But none of the three blocks the others.

## 2. Lever #1 — Token-validation cache (NEW — call it **V-8**)

### Problem
`check_access_token` (`Routes__Vault__Pointer.py:52`, duplicated in `Routes__Vault__Inbox.py:37`) calls `admin_service_client.token_lookup(token)` on **every** authenticated write/batch/delete/configure/purge. `token_lookup` is an HTTP GET to `/tokens/lookup/{token}` on the Admin service (`Admin__Service__Client.py:23`) — in prod a remote Lambda URL via the service registry. There is **no caching**. The manifest path already proved the pattern (`_manifest_cache`, Lambda-lifetime) — the token path simply never adopted it.

### Design
Add a small TTL cache keyed by the **token string**, value = `(status, cached_at)`. Mirror `_manifest_cache`'s Lambda-lifetime model but with a short TTL (tokens can be revoked out-of-band, manifests can't).

- **Location:** a single shared helper so both `Routes__Vault__Pointer` and `Routes__Vault__Inbox` use it. Recommend a `Service__Access_Token` (Type_Safe) holding the cache + the `admin_service_client`, injected into both route classes — removes the copy-pasted `check_access_token` / `_check_access_token` (they are byte-identical today).
- **TTL:** default 60s, env-configurable (`SGRAPH_SEND__TOKEN_CACHE_TTL`). Cache **positive** validations only; never cache `401`/`404` (a freshly-created token must work on next request without waiting out a negative TTL).
- **Semantics preserved:** on cache miss or expiry → live `token_lookup`. On the Admin service being unreachable → keep today's behaviour (`503`), do **not** serve stale-positive past TTL.
- **Local-dev / env-var fallback path is unchanged** (no admin client → env compare → free).

```
validate(token) -> token | raise
  hit = cache.get(token)
  if hit and now - hit.cached_at < TTL and hit.status == 'active':
      return token                      # 0 network
  status = admin_service_client.token_lookup(token)   # live
  if active: cache[token] = (active, now); return token
  else: raise 401/404 (NOT cached)
```

### Files
| Change | File |
|---|---|
| New `Service__Access_Token` with TTL cache | `lambda__user/service/Service__Access_Token.py` (new) |
| Use it in route auth | `Routes__Vault__Pointer.py:52-84`, `Routes__Vault__Inbox.py:37-61` |
| Wire injection | `Fast_API__SGraph__App__Send__User.py` (where `admin_service_client` is set today, `:39`) |
| TTL env var | `user__config.py` |

### Saves
Repeat writes/batches in a warm instance go from **1 Admin round-trip each → 0**. For the 5-write send, 5 → 1. For any chatty app, approaches 1 per TTL window.

### Test impact (per CLAUDE.md §27)
- **SHOULD pass unchanged:** existing token-auth tests (`401` on bad token, `200` on good) — semantics identical.
- **NEW tests:** (a) second call within TTL performs **0** `token_lookup` (assert via an in-memory admin app call-counter — no mocks, real in-memory admin per house rules); (b) revoked token still rejected after TTL expiry; (c) negative result never cached.
- **Bad failure to watch:** any test asserting a `token_lookup` happens on *every* request would break — that would be a **good** break (it's the behaviour we're removing); update it.

## 3. Lever #2 — Catch-404 reads (V-1 + V-2 from the refresh)

This is exactly **V-1** and **V-2** from the storage-I/O refresh, pulled forward because the send/boot path hammers reads (every ref read, every batch-read).

### Problem
`Storage_FS__S3.file__bytes/file__str/file__delete` pre-call `file__exists()` internally (`Storage_FS__S3.py:46,53,81`) because the osbot-aws `get_object` raises on a missing key. On top of that, services pre-check existence again (`Service__Vault__Pointer.read:98`, `_batch_read:259`, `_cas_write:268`, `write_if_match:126`). Net: one logical read = **HeadObject + HeadObject + GetObject = 3 S3 calls**.

### Design (two parts)
- **V-1 (primitive):** make `file__bytes` / `file__str` / `file__delete` **attempt the op and catch the not-found `ClientError`** (`NoSuchKey` / `404`), returning `None` / `False` — instead of pre-Heading. **Parity requirement:** `Storage_FS__Memory` must return the same `None`/`False` on miss so tests stay backend-agnostic (they do today via existence checks — verify and lock with tests).
- **V-2 (service):** delete the now-redundant `file__exists` prechecks in the Pointer service; rely on the `None` return.

### Files
| Change | File | Lines |
|---|---|---|
| Catch-404 in primitives | `lambda__user/storage/Storage_FS__S3.py` | 44–55, 78–83 |
| Memory backend parity check | `Storage_FS__Memory` (osbot dependency — assert behaviour, add wrapper test) | — |
| Drop service prechecks | `Service__Vault__Pointer.py` | `read:96-100`, `_batch_read:257-264`, `_cas_write:266-277`, `write_if_match:117-138` |

### Saves
Every read/delete system-wide drops ~1 HeadObject; the read-only `POST /vault/batch` of 100 ops drops from ~300 → ~100 S3 calls. Inbox `fetch`/`mark_processed`/`purge` improve for free (they inherit the primitive).

### Test impact
- **SHOULD pass unchanged:** all read/write/delete behaviour tests — return values and statuses are identical.
- **NEW tests:** primitive returns `None`/`False` on missing key without raising; in-memory and (LocalStack) S3 backends agree.
- **Bad failure to watch:** any test asserting a specific S3 call **count** would shift — update counts; that's the point of the change.

> **Scope guard (Explorer rules):** both levers are strictly behaviour-preserving — no endpoint contract, status code, or payload changes. No new feature. Safe for Explorer; nothing here is a behaviour bug fix that belongs back with anyone.

## 4. Lever #3 — Batch the commit (HANDOFF to the vault team)

**Not done in this session.** Captured here so the dependency and the target shape are explicit; this section is the brief.

### What
The browser commit path (`sg-vault`) writes each object and ref with an individual `PUT /api/vault/write` (`sg-vault-object-store.js:81`, `sg-vault-ref-manager.js:27`). It should instead **buffer the commit's writes and flush them as one `POST /api/vault/batch/{vaultId}`**.

### Why it's a vault-team change
It lives entirely in `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/_common/js/lib/sg-vault/`. No backend change is required — `Service__Vault__Pointer.batch()` (`:165`) already executes a `write` op list under a **single** write-key check and a **single** `_ensure_manifest`, and the route does **one** access-token check for the whole batch (`Routes__Vault__Pointer.py:188-206`). The capability exists; only the client doesn't use it for writes.

### Target shape (suggested, vault team to design)
- Add `SGVaultObjectStore.storeMany(ciphertexts[]) -> objectId[]` that emits `{op:'write', file_id, data}` ops and posts one batch.
- Have `_commit` (`sg-vault.js:249`) collect the blob/tree/commit objects + the ref write into one buffer and flush once. The two-ref model (clone `snw` + named `muw`) can ride in the same batch.
- Client request count for the commit: **5 PUT + 5 CORS preflight (10) → 1 POST + 1 preflight (2)**. The batch URL is stable, so even that preflight caches via `Access-Control-Max-Age` (content-addressed PUTs cannot — each is a unique URL).

### Backend interaction with #1/#2
When #3 lands, the server-side win compounds automatically: one batch = **1 auth check** (cached after #1) + **1 manifest check** + 5 PutObjects in a loop, in **1 Lambda invocation**. The only thing that scales with message size is the irreducible PutObject count.

A standalone inter-team brief should be filed at `team/comms/briefs/06/08/` pointing here; this section is its source.

|---|---|---|---|
| baseline | — | — | 5 invocations · 5 Admin lookups · 5 Puts · reads at 2–3 S3/each |

| 2nd | **#2 catch-404 (V-1/V-2)** | this session | reads 2–3 → 1 S3/each |

Land #1 and #2 as **two independent commits** on `claude/eager-rubin-5ayb8e` so each one's effect is measurable in isolation on the network waterfall. #3 proceeds on the vault team's branch in parallel; no merge-order constraint.
