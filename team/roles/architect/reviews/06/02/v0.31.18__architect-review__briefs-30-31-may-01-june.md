## Executive Architectural Summary

Three days of briefs describe a coherent architectural ambition: **SG/Vault as the substrate for an agentic publishing and skills ecosystem.** The architecture spans three layers:

1. **Content layer** — vaults holding standards, vulnerability debriefs, skills, and assessments as graph artefacts
2. **Web layer** — vaults rendering websites (library, per-industry pages), agent-controlled, with vault-to-vault CI pipelines
3. **Ecosystem layer** — vault-based skills marketplace, creator economy, and billing broker, with Netlify/Daytona/Convex/Pi/HeyGen as partner primitives

Each layer is architecturally coherent and builds on confirmed foundations. The primary architectural concerns are integration seams (especially the Convex sync boundary and the Netlify edge-rendering path) and the sequencing of the skills stack (graph → base vaults → marketplace).

## Architectural Assessment by Theme

### 1. Vault-per-Standard Document-to-Graph Pipeline (P-281)

**Assessment:** Architecturally sound and well-scoped. The universal pipeline (document → structured form → semantic graph/ontologies → validation → feedback) reuses existing machinery: the evidence feedback loop, the semantic knowledge graph work, the vault as workshop. The new work is defining the pipeline schema once and running it for GDPR first.

**Key architectural concerns:**
- **Fractal ontology-of-ontologies:** Section-level ontologies connecting to a top-level ontology is the right design for large compliance documents. The architect should define the graph schema for this relationship before building GDPR — it must be reusable across all standards.
- **Beyond-face-value content:** GDPR rulings, guidance, and per-country variation must be modelled as first-class graph nodes with provenance edges to their sources (not embedded text). This requires the provenance model to distinguish between the standard text, a ruling, and a regulator's guidance.
- **The vault-as-workshop model:** Raw input, transformations, and model responses with provenance all in one vault is good for GDPR but will grow large for ISO 27000 (which is vast). Consider vault size budgeting.
- **Intersection vaults:** The mechanism for an intersection vault to draw on two parent per-standard vaults needs a design decision: is it a VIV sub-vault link (P-159/P-160) or a fresh vault that copies/references? The VIV path is cleaner and already partially implemented.

**Dependencies:** Semantic knowledge graph machinery (vault-chat Track B, P-249), VIV sub-vault links (P-159/P-160 partially implemented), document-to-graph pipeline (not yet specified in detail).

**Architectural decision needed:** Define the graph schema for the fractal ontology-of-ontologies before building GDPR. This schema should be reusable as the base for P-294 (skills graphs) and P-298 (comparison vaults).

### 2. Public Preview with Embedded Read-Only Key (P-282)

**Assessment:** Architecturally clean. It combines two existing mechanisms (public preview P-166/P-168 and RO token P-177) with a small new link. The critical constraint is that the public preview's `sgraph-public-preview/v1` convention JSON must not expose more than the read-only key — the field-name guard banning `write_key`/`read_key`/`passphrase` (from P-167) extends naturally.

**Key architectural concern:** The embedded read-only key travels with the public link. If the public link is indexed by a search engine, the read-only key is public. This is intentional (the vault is meant to be public-readable) but the architecture must enforce that only read-only access is possible via this path — the full vault key must never appear in the public preview convention JSON.

**Dependencies:** P-166 (public preview), P-177 (RO token resolution via deterministic transfer-id), P-168 (auto-load from hash). Branch `claude/gracious-mendel-ynkJj` has the public preview implementation (pending review/merge as of the reality doc).

**Small effort — good quick win.**

### 4. Agent-Controlled Websites + Vault CI Pipeline (P-285)

**Assessment:** Architecturally ambitious but well-grounded. The library rendering from vault is claimed as working foundation. The new architecture is:

1. **Per-agent section vaults** — three vaults (ambassador/alchemist/journalist) plus the existing content vault, each rendered as a website section via its public read key.
2. **Website vault as VIV parent** — uses the VIV (vault-in-vault) mechanism (P-159/P-160) to give one place to manage all section vaults.
3. **Dev/QA/Prod environment vaults** — each environment is a vault; promotion = push from one vault to the next.

**Key architectural concerns:**
- **Vault-to-vault promotion mechanism:** The "push from one vault to the next" as a CI step needs a concrete design. The commit-queue (P-commit-queue) and sgit push are the candidates. Is it a full vault clone, a patch, or a selective file-push? This needs a design decision.
- **Prod isolation on a separate server:** The brief is correct that prod should be on a separate server reachable only through the CI pipeline. This is standard but requires DevOps work (separate Lambda/container, separate vault instance).
- **VIV dependency:** P-285 depends on P-159/P-160 (VIV) being fully working in the browser. The reality doc notes P-159/P-160 are logic-verified by unit tests but browser-unverified (no browser in build env). P-285 cannot be fully implemented until VIV browser tests pass.
- **Per-agent read-write keys:** The security model is sound (agents write with read-write key, public site reads with read key). Ensure the read-write keys for the ambassador/alchemist/journalist agents never appear in public vault content or committed files.

**Critical dependency:** VIV browser verification (OQ-viv-phase2-browser-1) must complete before P-285 is viable.

### 5. Per-Page Semantic Graphs + Edge Rendering (P-286)

**Assessment:** Architecturally well-founded; builds on a claimed-existing foundation (Lambda@Edge for llms.txt/.md). The key architectural decision is the URL scheme for the per-page semantic graph endpoint.

**Key architectural concerns:**
- **Edge-side decryption security model:** The edge function that decrypts vault content for llms.txt already does this. Extending it to semantic graphs means more vault content is decrypted at the edge. The public read key model limits this to public vaults — private vault content must never be served edge-side.
- **Graph generation cost:** Generating a semantic graph per page costs (LLM invocation). Cache aggressively; generate on content change only (the vault's version control makes change detection available).
- **URL scheme:** The brief suggests `page.md` (existing) and a new URL for the semantic graph. The natural choice is `page.graph.json` or `page.ttl` (Turtle for triples). Define this before building.
- **Format:** Turtle, JSON-LD, or a proprietary format? JSON-LD is the most agent-friendly and aligns with the semantic web framing. This is an architectural decision.

**No blocker — can start after verifying the llms.txt edge function foundation.**

### 6. Partner Integration Stack: Architectural Assessment (P-288–P-293)

**Netlify AX (P-288):**
The vault-is-a-zip → Netlify-deploys-zips fit is genuinely clean. The main architectural question is: does the vault deploy its raw zip (the encrypted vault files) or a rendered output (the decrypted public content)? For public library sites, it should be the rendered output. For vault-native hosting, the raw zip with edge-rendering. These are two different deployment modes; both are valid but need distinct paths.

**Daytona (P-289):**
The execution model (vault holds code, Daytona runs it, results flow back with provenance) is clean. The architect must define the **result return interface** before building — what goes back to the vault (stdout? structured JSON? artefacts?), in what format, and via which sgit operation. The stateful-sandbox-for-multi-round-workflows pattern needs a session/state contract.

**Convex (P-290):**
This is the architecturally most complex partner integration because it introduces a **hosted server-side layer** into an otherwise zero-knowledge system. The sync boundary ("vault = source of truth, Convex = live layer") is the right design, but it needs a concrete specification: what triggers a commit from Convex state to vault? Who has the vault write key in a Convex-backed app? How is the zero-knowledge property maintained when Convex holds live working state? These must be resolved before building.

**Pi (P-291):**
The base-vault ↔ Pi-Package bidirectional mapping is clean architecturally. The open Skills standard is the shared interface. Pi is additive, not replacing anything. Use Pi where it adds value (agent harness, unified LLM API); don't duplicate the vault's storage model in Pi.

**HeyGen (P-292):**
Wrapping HeyGen as a skill/connector (MCP path) is the architecturally cleanest integration — it doesn't touch the vault's trust model. The key architectural decision is where the vault content → script conversion happens (edge-side or agent-side) and whether the generated video is stored back in the vault with provenance.

**Tavon (P-293):**
This is a channel/GTM decision, not an architecture decision. No architectural work required.

## Cross-Cutting Architectural Concerns

### A. The Graph Schema — Define Once, Use Everywhere

P-281 (compliance graphs), P-286 (per-page graphs), P-294 (skills graphs), and P-298 (comparison graphs) all use semantic knowledge graphs. **Define a single, unified graph schema** covering:
- Node types: document, section, skill, evidence, provenance, person, organisation, ruling, jurisdiction
- Edge types: prerequisite, composition, conflict, family, references, derivedFrom, validatedBy, conflictsWith
- Provenance model: who produced this node, from what source, at what time, with what confidence

Building four separate graph implementations will create inconsistency. One schema enables cross-graph reasoning (e.g. a comparison vault that queries the compliance graph and the skills graph simultaneously).

**Recommended action:** Write an Architect scoping document for the unified graph schema before building any of P-281, P-286, P-294, or P-298.

### B. The Edge-Rendering Model — Security Boundary

Three briefs (P-282, P-285, P-286) rely on the edge function decrypting vault content at the edge. The security constraint is identical in all three: **only public content (with a public read key) is decrypted at the edge; private vault content is never served edge-side.** This boundary must be enforced in the edge function itself, not assumed by callers.

### C. VIV as Foundation — Verify Browser First

P-285 (agent-controlled websites), P-287 (industry pages with embedded vaults), and P-288 (Netlify AX) all depend on VIV (vault-in-vault, P-159/P-160) working in the browser. The reality doc notes this is unit-tested but browser-unverified. **VIV browser verification must be the next immediate step before building any of these features.**

### D. Convex Zero-Knowledge Boundary — Unresolved

P-290 (Convex) introduces a hosted server-side layer. Until the sync boundary is specified in detail and the zero-knowledge model is confirmed to hold, **P-290 should remain PROPOSED and not be implemented.** It is architecturally the riskiest integration because it touches the platform's core trust model.
