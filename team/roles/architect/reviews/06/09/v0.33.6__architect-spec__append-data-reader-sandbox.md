## 0. Decision record (Dinis, 2026-06-09)

| Decision | Chosen | Consequence |
|---|---|---|
| **Where the private key lives vs the sandbox** | **Parent unseals** | The trusted kernel holds the vault X25519 private key and performs the outer unseal. The sandbox never receives keys. |
| **Reader trust level** | **Untrusted (shared vaults)** | A `reader.js` may be attacker-authored (you opened someone else's vault). Jail it hard: no keys, no network, no parent access; all output validated. |
| **Message depth** (carried from scope) | Decrypted content reader | Bodies render — but only inside the jail. |
| **UI scope** (carried from scope) | Full owner UI | Nav + badge + panel + current/processed reader. |

## 1. Why this design

Two requirements collide: we want to (a) render decrypted message **bodies of arbitrary, evolving types**, and (b) **not trust** the code that knows how to render them. The resolution is a **two-layer split with the trust boundary on the key**:

- **Layer A — outer transport seal (platform, trusted).** The append payload is a standard sealed-box `ephemeral_pubkey ‖ iv ‖ ciphertext ‖ tag` (dev-pack `02 §3`). Only the **vault private key** opens it. That key lives as a file *inside* the vault, encrypted under `read_key` (`02 §3`) — so the **parent kernel already holds it** in any read session. The parent unseals; **the key never moves**.
- **Layer B — inner per-type decode + render (vault-supplied, untrusted).** The unsealed inner bytes carry a type tag. A **vault-resident reader file** registers, per type, how to decode and render. This is the "supports multiple message types" surface — and the only code we don't trust.

By having the parent do Layer A and hand the sandbox only the **already-unsealed bytes for the messages currently being viewed**, the untrusted reader cannot reach keys, the network, the parent DOM, or any message the user didn't open. One canonical reader location; trusted built-in readers can later be promoted into the platform.

## 3. The gate model (4 tiers — confirms the migration guide)

| Tier | Who holds it | Grants | Where |
|---|---|---|---|
| `append_token` = `H(pubkey)` | any provisioned sender | **write** (append) | body / path |
| `enum_key` = HKDF(read_key, `inbox-enum-key`) | owner + delegated drainers | **list / fetch / mark-processed** | `x-sgraph-vault-enum-key` |
| `write_key` | owner only | **configure / purge** | `x-sgraph-vault-write-key` + access token |
| **`private_key`** (X25519, in-vault, read_key-encrypted) | owner (read session) | **decrypt** (Layer A unseal) | never sent to server; loaded client-side |

The server enforces the first three (stores hashes only) and **never** sees `private_key` — decryption is wholly client-side. This spec's reader concerns Layer A (`private_key`, parent) and Layer B (reader, sandbox).

## 4. Architecture

```
┌──────────────────────── PARENT  (kernel / vault app — TRUSTED) ───────────────────────┐
│                                                                                        │
│  SGAppend (transport)         SGVaultPKI (NEW: load privkey, X25519 unseal)            │
│    list/fetch/markProcessed     │  key from in-vault file (read_key-encrypted)          │
│    /purge  (+folder)            │  NEVER leaves this realm                              │
│        │ ciphertext             ▼                                                       │
│        └────────────▶  innerBytes = unseal(payload, privKey)   (Layer A)               │
│                                 │                                                       │
│        ┌────────────────────────┘ postMessage({msgId, innerBytes})  (transferable)     │
│        ▼                                                                                │
│   ┌──────────── <iframe sandbox="allow-scripts"> · null origin · CSP default-src 'none' ┐
│   │  APPEND READER JAIL  (UNTRUSTED)                                                     │
│   │    harness (platform, in srcdoc)  ── parses wrapper {t,d}, dispatches               │
│   │    built-in readers (platform)    ── sgraph/text@1, sgraph/log@1, …                 │
│   │    .vault/append/reader.js        ── vault-supplied, extends/overrides (Layer B)    │
│   │        decode(d,ctx) → model · render(model,el,ctx) → DOM (stays here)              │
│   │        emits user-intents (markProcessed/purge) back to parent — NEVER acts         │
│   └──────────── no keys · no network · no parent DOM · output validated ───────────────┘
│        ▲ counts only / validated intents                                                │
│  nav badge = pending file count (metadata; no decryption)                               │
└────────────────────────────────────────────────────────────────────────────────────────┘
        │ /api/vault/append/{list,fetch,mark-processed,purge}  (enum_key / write_key)
        ▼
   Service__Vault__Append   (pending/ ⇄ processed/, config.json)
```

### 4.1 Data flow (read one message)

1. Owner opens the **Append** view (or `append.new-messages` fires).
2. Parent → `SGAppend.list({ folder:'pending' })` and `{ folder:'processed' }` (enum-gated) → metadata (file_id, received, size). **Nav badge = pending count** — no crypto needed.
3. Parent → `SGAppend.fetch({ folder, file_ids })` → ciphertext blobs.
4. Parent loads the vault **private key** (in-vault, read_key-decrypted) and runs **Layer A unseal** → inner bytes. *Key and ciphertext never leave the parent realm.*
5. Parent `postMessage`s `{ msgId, folder, innerBytes }` into the jail (innerBytes as a Transferable `ArrayBuffer`).
6. **Jail harness** parses the canonical wrapper `{ t, d }`, looks up the reader for `t`, calls `decode` then `render` → DOM **inside the iframe** (this iframe *is* the reading pane).
7. User actions inside the jail (mark-processed, purge, reply) emit **intents** back to the parent; the parent validates and executes them via the Append API. **The jail has no transport and no keys.**

No human-readable content ever crosses back to the parent. The parent deals in counts, ids, and validated intents only.

## 5. The vault-resident reader file — JS API spec

### 5.1 Location & loading

- Canonical path: **`.vault/append/reader.js`** (the `.vault/**` floor is non-app-writable — owner/platform curated; still untrusted when it's *someone else's* vault).
- Optional override via append `config.json`: `{ "reader": ".vault/append/reader.js" }`.
- The parent reads the file (vault content → it has `read_key`), and injects it as an inline `<script>` into the jail's `srcdoc` **after** the platform harness + built-in readers. Absent file → built-in readers only.

### 5.2 Registration API (runs inside the jail)

The harness exposes one global, `sgAppend`:

```js
// .vault/append/reader.js   —  UNTRUSTED, runs in the null-origin sandbox
sgAppend.defineReader('sgraph/text@1', {

  // decode: type payload `d` (+ raw bytes) → a plain model object. No DOM, no I/O.
  decode(d, ctx) {
    return { from: d.from, ts: d.ts, subject: d.subject || '(no subject)', body: String(d.body || '') };
  },

  // render: model → DOM, into the harness-provided element. Sandbox-local only.
  // Use ctx helpers for anything that could be an injection vector.
  render(model, el, ctx) {
    el.append(ctx.h('div', { class: 'subj' }, model.subject));
    el.append(ctx.h('div', { class: 'meta' }, `${ctx.shortHex(model.from)} · ${ctx.time(model.ts)}`));
    el.append(ctx.markdown(model.body));            // sanitized; raw HTML stripped
  },

  // summarize (optional): model → tiny row model for the in-jail list. Pure.
  summarize(model) {
    return { from: model.from, subject: model.subject, ts: model.ts };
  },

  // actions (optional): which owner intents this type offers in its rendered view.
  actions: ['markProcessed', 'reply']               // 'reply' → emits an intent the parent may route to an app
});
```

### 5.3 `ctx` — the only capabilities a reader gets

`ctx` is the **complete** capability surface. A reader has nothing else (no `fetch`, no `crypto`, no keys, no parent handle).

| `ctx` member | Provides | Notes |
|---|---|---|
| `ctx.h(tag, attrs, ...children)` | safe element factory | rejects event-handler attrs, `javascript:` URLs |
| `ctx.markdown(str)` | sanitized markdown → DOM fragment | no raw HTML, no remote refs |
| `ctx.text(str)` | escaped text node | |
| `ctx.shortHex(s)`, `ctx.time(ms)` | display formatters | |
| `ctx.emit(intent, payload)` | request a parent-side action | validated + rate-limited by harness |
| `ctx.bytes` | the raw inner `Uint8Array` (for binary types) | for `d`-as-base64 / custom framing |

A reader **cannot**: open sockets, read other messages, persist anything, touch `window.parent`, or call any verb. It transforms `d`→model→DOM and may `ctx.emit` an intent.

### 5.4 Canonical inner wrapper (what Layer A yields)

After the parent unseals, inner bytes are UTF-8 JSON:

```json
{ "t": "sgraph/text@1", "d": { "from": "...", "ts": 1733740800000, "subject": "...", "body": "..." } }
```

- `t` = `"<namespace>/<name>@<major>"`. The harness dispatches on `t`. Unknown `t` → a built-in **fallback reader** shows safe metadata + "no reader for type `t`" (never raw bytes).
- `d` is type-defined; may be a JSON node or a base64 string for binary types (reader uses `ctx.bytes`).
- Binary-first types may instead use a 1-byte format marker + framing — the harness passes raw bytes through; only the wrapper's `t` lookup is mandatory. (JSON wrapper is the v1 default.)

### 5.5 Built-in readers (platform) + override

The harness ships trusted built-in readers for common types (`sgraph/text@1`, `sgraph/log@1`, `sgraph/signal@1`). `defineReader` with an existing `t` **overrides** the built-in for that vault. This is the "promote a reader into the main vault code" path: once a type is common, ship it as a built-in and vaults stop needing to carry it.

## 6. The sandbox — exact jail configuration

| Control | Setting | Stops |
|---|---|---|
| iframe `sandbox` | **`allow-scripts`** only (NO `allow-same-origin`) | null/opaque origin → no parent DOM, cookies, storage, no same-origin XHR |
| CSP (srcdoc `<meta>`) | `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; base-uri 'none'; form-action 'none'` | all network egress (fetch/XHR/WebSocket/beacon/remote img), key exfiltration |
| no `allow-popups` / `allow-top-navigation` | (omitted) | `window.open`, navigation-based exfiltration |
| keys | **never posted in** | reader can't leak what it never has |
| inbound from parent | only `{ msgId, innerBytes }` for messages the user opened | reader can't see un-opened traffic |
| outbound to parent | only `{ intent, payload }` and `{ summary }` — **schema-validated, size-capped, rate-limited** by parent | reader can't drive the parent or smuggle data via oversized summaries |

Residual risk accepted: a malicious reader can render misleading content **to the user who chose to open that vault**, and can lie in summaries — but it cannot exfiltrate, cannot reach keys, and cannot escape the frame. That is the contained blast radius the design targets.

## 9. Security review asks (AppSec)

1. **Jail escape:** confirm `sandbox="allow-scripts"` + srcdoc CSP `default-src 'none'` blocks all egress on target browsers; verify no `allow-same-origin` anywhere in the chain (incl. nested ViV mounts — null-origin inheritance).
2. **Intent channel:** parent must treat every inbound message as hostile — strict schema, size cap, rate limit, no `eval`, no reflection of intent payload into privileged calls without re-validation.
3. **Layer A custody:** private key loaded only in the parent realm, zeroized after unseal where feasible, never logged, never posted into the jail.
4. **Type confusion / fallback:** unknown/forged `t` must hit the safe fallback (metadata only), never raw-byte render; `decode` exceptions isolated per message (one bad message can't blank the list).
5. **Folds in the open C1 item:** `enum_key` derivation (Q1) + the new `private_key`/append KAT under one review.
6. **Rendering:** `ctx.markdown` sanitizer spec (allowlist), no `data:`-script, no `srcset`/remote img (CSP already blocks, defense-in-depth).

## 11. Non-goals

- Not a mail client (no threading/composer in the vault layer; reply = intent hand-off).
- Not sender-identity verification (`from` is sender-asserted, TOFU — `02`/comms-guide §9). UI must not present it as verified.
- The jail does **no** transport and holds **no** keys — by design, forever.
- Does not attempt to decrypt types with no registered reader — safe fallback only.
