## 2. The two hard problems

### 2.1 There is no canonical message format the vault can decrypt

The working reference (comms guide §5–6) seals messages with **`nacl.box` (X25519 + XSalsa20-Poly1305)**, layout `ephPub(32) ‖ nonce(24) ‖ ciphertext(+16 tag)`, body `{t, text, …}` JSON. Critically, the recipient **NaCl secret key lives in an app-authored `identity.json` inside the vault**, the salts are **app constants**, and the envelope is an **app convention** — none of it is a platform standard. A vault-layer reader cannot decrypt arbitrary app inbox traffic; it can only decrypt messages sealed in a **format the platform defines and to a key the platform custodies.**

**→ We must define a canonical SGraph Inbox Envelope v1 and a vault-layer inbox identity.** Apps (and the CLI, and future senders) that want their messages readable in the owner UI seal to that standard. App-private formats remain app-only (the reader shows them as "opaque / app-encrypted").

### 2.2 `list`/`fetch` cannot see the `processed/` folder

Seeing processed messages — explicitly required — is impossible with today's transport. `inbox_list`/`inbox_fetch` only read `inbox/`. This needs a `folder: 'inbox' | 'processed'` parameter threaded through **server → transport → bridge → UI**. Server changes are in scope (Explorer builds first versions).

## 3. Proposed architecture

```
   ┌─────────────────────────── vault layer (kernel) ────────────────────────────┐
   │                                                                              │
   │  <vault-inbox-status>  ── owner UI: status panel + current/processed reader  │
   │        │  renders                                                            │
   │        ▼                                                                     │
   │  SGInboxReader  ── decrypt + envelope-parse (NEW)                            │
   │        │  uses                  │ secret key from                            │
   │        ▼                        ▼                                            │
   │  SGInbox (transport)     SGVaultInboxIdentity (NEW)                          │
   │   list/fetch + folder     X25519 keypair, sk sealed in OwnerSecrets,         │
   │        │                  pk published to manifest for senders               │
   │        ▼                                                                     │
   └────────│─────────────────────────────────────────────────────────────────────┘
            ▼  POST /api/vault/inbox/{list,fetch}  (+ folder param — server change)
       Service__Vault__Inbox  (inbox/ ⇄ processed/)
```

### 3.1 Inbox identity & key custody (`SGVaultInboxIdentity` — NEW)

- A per-vault **X25519 keypair** dedicated to the inbox (separate from read/write keys).
- **Secret key** sealed into the **owner-secret store** (`SGVaultOwnerSecrets.seal`, keyed off `write_key`) → only writable (owner) sessions can decrypt messages; RO-token sessions get metadata only. This cleanly realises the mockups' RO-mode (§3.6).
- **Public key** published in the vault manifest / inbox config so senders can seal to it (mirrors the reference's `identity.json.pk`, but platform-owned, not app-owned).
- Generated lazily on first "Enable inbox" in the owner UI; survives clone because it is derived/stored deterministically in vault content.
- **Crypto primitive decision (open — see §7):** WebCrypto has no portable X25519 across all targets; the reference uses bundled `tweetnacl`. Recommend **bundling `tweetnacl` (audited, 4KB min)** as the inbox box primitive for parity with every existing sender, rather than betting on `crypto.subtle` X25519 availability. This is the one new third-party dep; IFD zero-dep rule needs an explicit waiver (§7-D1).

### 3.2 Canonical envelope (`SGraph Inbox Envelope v1`)

Wire (base64 of): `magic(4)="SGI1" ‖ ephPub(32) ‖ nonce(24) ‖ box(plaintext)`. Plaintext = UTF-8 JSON:

```json
{ "v": 1, "t": "msg", "from": "<sender vault id or anchor>",
  "subject": "optional", "body": "markdown/plaintext", "ts": 1733740800000 }
```

- `magic` lets the reader distinguish a canonical envelope from app-private/opaque payloads (show those as "🔒 app-encrypted — open in app").
- Decryption: `nacl.box.open(box, nonce, ephPub, inboxSecretKey)`; `null` → not-for-us/opaque.
- Forward-compatible: unknown `t`/`v` rendered as a generic record, never crash the list.

### 3.3 Backend change (`Service__Vault__Inbox.py`)

- Add optional `folder` (`'inbox'` default | `'processed'`) to `inbox_list` (`:126`) and `inbox_fetch` (`:181`); select prefix via `path__vault_inbox_prefix` vs `path__vault_processed_prefix` (both already imported, `:16-21`). No new gate — same `enum_key`.
- Keep caps/validation identical. Update `Routes__Vault__Inbox.py` + route tests.

### 3.4 Transport change (`sg-inbox.js`)

- `list({ folder, … })` and `fetch({ folder, … })` pass `folder` through (`:89`, `:98`). Default `'inbox'` preserves C1–C4 behaviour. Update the verb header doc-block.

### 3.5 Reader module (`SGInboxReader` — NEW, pure, Node-testable)

- Input: a `SGInbox`, the inbox secret key, a folder. Lists metadata, fetches ciphertext for the page, parses+decrypts each envelope, returns `{ entries: [{ file_id, received, from, subject, body, state, opaque }], truncated }`.
- No DOM. Constructor-injected crypto + transport → unit-tested with a fake fetch and a known keypair (no mocks, project rule 22).

### 3.6 UI (full C5 — `<vault-inbox-status>` + nav)

Per mockups, plus the **new reader surface**:
- **Nav** `vault-nav.js` — 4th item "Inbox" @ position #2; unread badge (counts via existing `inbox.new-messages` event); error/⚠ state.
- **Status panel** — enabled/auto-fetch toggles (owner-only; persisted to `.vault/inbox/config.json`), anchor table, last-check trigger, "Check now".
- **Message reader (NEW vs mockups)** — two views, **Current** (`inbox/`) and **Processed** (`processed/`), toggled by a tab/segment. Each row: `from` · subject · time · state; expand → decrypted `body`. Owner actions: **Mark processed** (current → moves row to Processed), **Purge** (processed). RO session: read/list only, actions hidden.
- **Header refresh menu** — "Check inbox" entry (`vault-header.js`).
- **Debug pane** — Events tab (mockups §6) — optional, low priority.

## 5. Security considerations

1. **Owner-only decryption** — inbox secret key sealed under `write_key` (OwnerSecrets); RO sessions structurally cannot decrypt. Verify the key is never written to a read-tier file or logged.
2. **Zero-knowledge preserved server-side** — server still sees only ciphertext + routing hashes; decryption is client-side in the owner's browser. No plaintext, key, or filename crosses to the server.
3. **Envelope authenticity** — `nacl.box` is authenticated (Poly1305); tamper/wrong-recipient → `null`, rendered as opaque, never as trusted content. `from` is **sender-asserted, unauthenticated** (TOFU, like the reference §9) — UI must not present it as verified identity. Flag for AppSec.
4. **Opaque payloads** — non-canonical or app-private messages must render as "🔒 app-encrypted" with no decrypt attempt; never surface raw ciphertext as a "body".
5. **Carries the open C1 item** — `enum_key` derivation (AppSec Q1) still lacks recorded sign-off; this scope adds a second key (inbox X25519) — fold both into one AppSec review.
6. **Markdown/HTML rendering** — decrypted `body` is untrusted; render as **escaped plaintext** (or sanitised markdown) — no raw HTML injection into the vault DOM.

## 6. Non-goals (unchanged from mockups §10, except decryption)

- Not a full mail client: no threading, no rich composer in the vault layer (a **Reply** affordance may hand off to an app — out of scope here).
- Not a sender directory / identity verification (TOFU only).
- Not a notification centre (badge only).
- Not configurable polling cadence (events drive checks).
- **Does NOT** attempt to decrypt app-private formats — only the canonical envelope.

## 8. Risks

| Sev | Risk | Mitigation |
|---|---|---|
| **High** | Decryption in the vault layer widens the trust boundary (new long-lived secret key, untrusted bodies in vault DOM). | OwnerSecrets custody + escaped rendering + AppSec review **before** merge. |
| **Med** | Canonical-envelope adoption — existing senders use app salts/format; they won't appear decrypted until they adopt v1. | Document the envelope; provide a sender helper; render legacy as opaque (no breakage). |
| **Med** | Forward-compat with the SecureChannel stub / ViV bundle (review R1/R2) — new modules must land in the bundle + stub, or the reader won't work in mounted vaults. | D8 includes bundle; add stub parity if reader is ever app-exposed (D3 = no for now). |
| **Low** | Processed folder can grow unbounded → list cost. | Existing caps + purge; surface count in panel. |
