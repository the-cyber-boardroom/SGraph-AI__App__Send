# Append lanes v2 — capacity, large payloads and signed lanes

**date** 25 November 2026
**role** Architect, with an AppSec lens
**status** **PROPOSED — none of the v2 features exist yet.** Every "today" statement was checked against `dev` @ `da293d4f` (`Service__Vault__Append.py`, `Routes__Vault__Append.py`, `Storage_FS__S3.py`). Each is marked **[executed]**, **[code-read]** or **[AWS limit]**.
**asked by** Dinis: (1) the 1,000-entry limit forces some writers onto five lanes, so allow higher limits or a burst; (2) payloads of 50–100 MB; (3) other features, now that lanes are used everywhere; (4) a PKI mode where holders of particular public keys can submit (see pki.sgit.ai).

---

## 0 · The recommendation on one screen

1. **Limits become per-lane settings**, set by the vault owner with the write key, inside fixed server ceilings. The default stays at today's 1,000. A lane gets a **soft** limit (the normal level) and a **hard** limit (the burst ceiling). The server refuses appends only at the hard limit.
2. **Cheap counting first.** Today every append lists the whole lane. That is fine at 1,000 entries and does not scale to 20,000. Phase 1 fixes it, and the lane-listing costs, with no change in behaviour. The ceilings are raised only after that.
3. **Large payloads go straight to S3, not through Lambda.** One presigned `PUT` pins the exact size and the SHA-256, and can only create the object, never overwrite it. The file-id format and the `pending/` folder are unchanged, so listing, marking processed and purging keep working.
4. **Signed lanes.** A lane can require every append to be signed by a P-256 key on the owner's allow-list, named by its **pki.sgit.ai fingerprint**, so a key from the register works as it is. Today, a pki.sgit.ai `inbox` statement publishes the append token. **A published token is a public write capability**, and the only limit on it is the entry cap.
5. **These three changes depend on each other.** Token-only lanes keep conservative ceilings. Signed lanes unlock the high ones: 50k entries and 100 MB+ payloads are safe once every writer is named and can be revoked.
6. **Two defects need fixing on the way, whatever is decided.** Revoking a token does not reach other Lambda instances (§1.2). A `fetch` of a few large entries exceeds Lambda's response limit (§1.1).

### 1.1 Defect: a `fetch` can exceed Lambda's 6 MB response

`fetch` returns every requested entry inline. Two 2.5 MB entries come to 6.7 MB of base64, and Lambda refuses the response, so the reader gets a non-JSON error. `list include_content` already has a ceiling (`INLINE_CONTENT_CEILING`, 3 MiB raw, about 4 MB as base64). `fetch` has none. **Fix:** return entries until the ceiling is reached, and list the rest under a new `deferred` field. The reader asks for those next.

### 1.2 Defect: revoking a token does not reach other warm Lambdas [executed]

Two `Service__Vault__Append` instances on one store stand in for two warm Lambdas:

```
B append before revoke : ok
A revokes the token    : configured
A append after revoke  : gate_failed
B append after revoke  : ok          ← instance B still accepts the revoked token
```

`configure` refreshes only the instance that served it. Every other warm instance keeps the old anchors, enum-key hash and (once v2 lands) limits and signers until AWS recycles it, which can take hours. **Fix:** a TTL on both caches (30 s by default, overridable from the environment), the same pattern as `Service__Access_Token`. This is required before signed lanes, because removing a signer has to take effect.

### 1.3 Why writers needed five lanes

The limit applies to **pending** entries in **one** lane, so five lanes give five times the capacity. A writer that bursts between two drains of a slow reader hits 507 on one lane and spills into the next. Using lanes as shards costs the reader five listings, five checkers and five `mark_processed` streams. That is the cost v2 removes.

## 2 · Capacity: per-lane limits with a burst ceiling

**Config.** New optional fields in `bare/append/config.json`. Per-lane settings are keyed by `sha256(token)`, the anchor the server already stores, so raw tokens never go into config.

```json
{ "append_anchors": ["…"], "enum_key_hash": "…",
  "lane_defaults": { "soft_pending": 1000 },
  "lanes": { "<sha256(token)>": { "soft_pending": 5000, "hard_pending": 20000,
                                   "max_pending_bytes": 2147483648,
                                   "max_payload": 104857600, "large": true,
                                   "mode": "signed", "signers": ["sha256:9f2c…16hex"] } } }
```

Absent fields mean today's behaviour: a soft and hard limit of 1,000, the inline payload only, token mode. **No existing lane changes.**

**Burst.** Appends are accepted up to `hard_pending`. `soft_pending` is the level the owner expects. Above it, the stats endpoint (§5) and the vault UI flag a backlog, so the reader can be alerted before the lane is refused. Senders still get the blind `{ok:true}`. A sender learns only what it learns today, a 507 at the hard limit.

**Server ceilings** (constants, overridable from the environment; the numbers are a decision for Dinis, §8):

| | token lane | signed lane |
|---|---|---|
| `hard_pending` | ≤ 5,000 | ≤ 50,000 |
| `max_pending_bytes` | ≤ 1 GiB | ≤ 20 GiB |
| `max_payload` | inline only (≈ 4 MB) unless the owner opts in | ≤ 256 MiB |

**Cheap counting.**
- `count_up_to(prefix, n)` stops listing once it has seen `n` keys. `ListObjectsV2` also returns each key's size, so the byte budget costs nothing extra.
- The count is cached per warm instance for about 5 s and incremented on each accepted append. Between refreshes, concurrent instances can admit a little over the limit. That overshoot is bounded and is exactly what a burst ceiling tolerates.
- The exact check runs at each refresh.

**Listing costs (Phase 1, same results, same order):**
- **Cursor pushdown:** `StartAfter = pending/<token>/<after_file_id>`, `MaxKeys = limit + 1`, per lane. File ids sort by time across all lanes (`<epoch_ms>_<rand>`), so merging the per-lane pages keeps today's global order.
- **Lane discovery** uses `Delimiter='/'` (`CommonPrefixes`). That is one call per thousand lanes, instead of listing every key ever written.

## 3 · Large payloads (50–100 MB and beyond)

> **Revised in §9:** attachments become content-addressed **blobs** referenced from small sealed entries. The presigned-`PUT` mechanics below still apply, keyed by `blobs/<sha256>`.

**Recommendation: always a limit, set per lane, with a server ceiling.** "No limit" would turn any published token into free storage. The physical ceiling of a single S3 `PUT` is 5 GB. Start the server ceiling at 256 MiB and raise it when there is a need.

**The flow:**

1. `POST /api/vault/append/write-large/{vault_id}` with `{append_token, size, sha256}` (plus the signature fields on a signed lane). The server checks the gate, the lane's `large` flag, `max_payload`, the entry and byte limits, then returns `{upload_url, headers, expires_in}`. That is a presigned `PUT` for `pending/<token>/<epoch_ms>_<rand>.enc` with **`Content-Length`, `x-amz-checksum-sha256` and `If-None-Match: *` signed into it**. botocore 1.44 supports all three on `PutObject` [executed].
2. The client `PUT`s the ciphertext straight to S3. S3 refuses a wrong size, a wrong hash, and any second write to that key. An S3 object becomes visible only when its `PUT` completes, so there is **no complete call**, and a half-written entry can never appear in a listing.
3. **Readers:**
   - `list` already returns each entry's `size` from the listing.
   - `include_content` skips entries above the inline ceiling and marks them `large: true`.
   - `fetch` returns a presigned `GET` `url` (5 min) instead of `content` for those entries.
4. **`mark_processed` and `purge` use S3 `CopyObject`** (server-side, no bytes through Lambda) for **all** entries. This also fixes the doubled transfer in §1. A copy primitive is added to our `Storage_FS__S3`, with a read-and-write fallback in the memory and disk backends.

**Why a single `PUT` and not multipart:**
- A single `PUT` handles 100 MB without trouble. Multipart only adds resumable uploads, which can come later through the existing `Service__Presigned_Urls`.
- 100 MB of AES-GCM in browser memory is fine.

**Blindness, a documented change:**
- A large-entry sender learns **its own** entry's file id, because the id is in the URL.
- That tells it nothing about other entries: not their ids, not the count. It cannot read anything without the enum key.
- Inline appends stay fully blind.

**What it needs outside this repo's Python:**
- **S3 bucket CORS** must allow `PUT` from the vault origins, with the `x-amz-checksum-sha256` and `If-None-Match` headers.
- The null-origin app frames cannot reach S3 (their CSP blocks it), so the **top kernel** performs the `PUT` for `sg.append.write` with a Blob. That is client work.
- **sgit CLI parity.**
- Memory and disk modes return 501 `presigned_not_available`, as vault presigned uploads already do. Unit tests cover the gates and validation in memory mode; the S3 path is tested on LocalStack (house rule 23).

## 4 · Signed lanes (the PKI mode)

> **Revised in §9:** a server-held allow-list of pki.sgit.ai fingerprints breaks the rule that the server holds no identifiers. Use **lane keys and grants** instead. The signing format, the replay-safe names and the 401s below still apply.

**Why.** A pki.sgit.ai `inbox` statement is `{endpoint, vault, token}` inside a **public** record. The site itself says to treat the token as public. So every lane advertised in the register can be written by anyone, and the 1,000 cap is the only defence. A signed lane makes the token just an address, and the **key** the capability.

**Match pki.sgit.ai exactly**, so that a key already in the register works with no conversion:

| | value |
|---|---|
| algorithm | ECDSA P-256 / SHA-256 (the register's signing key; the CLI's commit keys are also P-256) |
| signature | base64 of raw `r‖s`, 64 bytes, what WebCrypto produces |
| public key | base64 DER SubjectPublicKeyInfo |
| key id | `sha256:` + first 16 hex of `sha256(DER SPKI)`, the register's **signing fingerprint** |

**The request.** `write` and `write-large` gain `signer` (SPKI), `ts` (ms) and `sig`. The signed bytes are a **fixed pipe-delimited string, not JSON**:

```
sg-append/v1|<vault_id>|<sha256(append_token)>|<ts_ms>|<size>|<sha256 hex of ciphertext>
```

There are two reasons for that format:
- It avoids the canonicalisation trap we flagged in October for CLI commit signatures (`json.dumps` versus `JSON.stringify`).
- It follows the register's own invite string (`pki.sgit.ai/invite/v1|<fp>|<exp>|<nonce>`).

It carries the token's **hash**, so an attestation can be shown without revealing a private lane's token.

**Server checks:**
1. `fingerprint(signer) ∈ lane.signers`.
2. `|ts − now| ≤ 300 s`.
3. The ciphertext hash matches: computed for an inline entry, pinned in the presigned checksum for a large one.
4. The signature verifies.

A failure returns **401, not 403**. The CDN rewrites every API 403 into an HTML 404 (an open DevOps item), while 401 reaches the client as JSON.

**Replay protection with no nonce store:**
- The entry's file id is `<ts_ms>_<sha256(fingerprint | signed string)[:24]>.enc`. That fits today's file-id pattern `^\d{13}_[0-9a-f]{24}\.enc$`.
- The write is create-only.
- A replay inside the 300 s window maps to the same name and is a no-op (`duplicate`). Outside the window it fails the timestamp check.
- The name is derived from the signed **content**, not the signature. ECDSA signatures are malleable (`s` and `n − s` both verify), so a name built from the signature could be duplicated by flipping `s`.
- Side benefit: an honest client's retry is idempotent.

**Attestations readers can check themselves:**
- The server stores `{fingerprint, signer, ts, sha256, sig}` at `bare/append/<token>/sig/<file_id>.json`. That is **outside** `pending/` and `processed/`, so listings and old readers are unaffected.
- `list` and `fetch` return the attestation.
- A reader re-hashes the ciphertext and verifies the signature against its own trust decision, **without trusting the server**. The server's check is admission control; the reader's check is authenticity.

**Trust and revocation:**
- The server checks only the lane's own allow-list. It makes no network calls to pki.sgit.ai.
- The owner's tooling uses the register to decide which fingerprints to add, and applies revocation statements by removing them.
- Removal takes effect once the config TTL (§1.2) runs out.

**Library:** `cryptography` is in the dev venv only as a dependency of `pyjwt`. Declare it explicitly, and confirm it is in the Lambda package (arm64 wheels exist). One verification takes about **63 µs** [executed].

**Later (PROPOSED):**
- Per-signer quotas.
- Allow-lists by register relation (for example "any agent operated by X").
- Sealing to the register's RSA-OAEP encryption key (today the payload format is the client's choice).

## 6 · Side effects and compatibility

| Change | Existing lanes | Old web client / sgit | Note |
|---|---|---|---|
| Per-lane limits | none (absent = today) | none | — |
| Cheap count, cursor pushdown, delimiter discovery | none | none | tests must pin identical results **and order** against the current implementation |
| Copy-based `mark_processed` | none | none | moves the same bytes server-side |
| Config TTL | config changes now reach every instance within 30 s | none | an intended behaviour change: revocation starts working |
| `fetch` ceiling | a fetch that failed now returns partial + `deferred` | an old client that ignores `deferred` sees fewer files; it already re-lists, so nothing is lost, but it re-fetches | client update recommended |
| Large entries | only on lanes with `large: true` | an old reader gets `url` without `content` for those entries and fails on them | **owner opts in after upgrading readers**; document it |
| Signed lanes | only on lanes with `mode: signed` | an old writer gets 401; old readers work (attestation ignored) | opt-in |
| S3 CORS, Lambda package, CLI parity | — | — | DevOps + sgit team; cross-team brief needed |

The September CDN rewrite (API 403 → HTML 404) is still live, which is another reason every new auth error in v2 is a 401.

| **4** | signed lanes: P-256 verify, fingerprints, replay-safe names, attestations, 401s; client signing with the vault web's device key (the IndexedDB P-256 key from the unmerged sgit-0.21-parity branch); CLI brief | opt-in per lane | M server + M client |

Each phase ships on its own. Phases 3 and 4 do nothing until an owner turns them on for a lane.

## 8 · Decisions for Dinis

2. **Large payloads on token-only lanes:** allow them when the owner opts in with a byte budget, or reserve them for signed lanes?
3. **Order:** start Phase 1 now (it is also the bug-fix phase)?

Source: `SovereignWebsite/Site__Agent__Maestro` @ `dev`, `site/factory/dinis-cruz/account-a/notes/2026-11-25-append-lane-improvements.md`. It records what account A's agents hit using lanes every day. It also states a rule from Dinis that this design must follow: **the server holds no identifiers and no plaintext metadata.**

| Their item | Already exists? | Verdict and change to this design |
|---|---|---|
| **Soft drop, acknowledge without deleting** | **Mostly, yes.** `mark_processed` *moves* entries to `processed/`, where they stay until an owner purge [code-read]. Their readers keep local seen-id files instead, which a new container forgets | Add the missing parts: `list` of `processed/`, an `unmark` verb (processed → pending), and **retention** as a lane setting. Keep per-reader cursors **in the reader's own vault**, not on the server, which follows the no-data rule and survives containers. Readers should mark only entries that decoded |
| Overflow instead of 507 | — | Same as §2's soft/hard limits. "Reject the oldest read entries first" would free nothing: read entries do not count against the cap |
| `GET /limits`; a 413 that states the limit and the size received | no | **Add to Phase 1** (trivial) |
| Accept raw bytes | — | It removes **their** second base64 layer (1.8× → 1.33×), but **does not raise the ceiling**: a Lambda Function URL base64-encodes a binary body inside the 6 MB event. The fix for the double encoding is a documented client envelope |
| **Blobs referenced by hash** | no | **Adopted; replaces §3's "large entries".** Entries stay small; attachments are content-addressed blobs at `bare/append/<token>/blobs/<sha256>`, uploaded with a presigned `PUT` that pins `x-amz-checksum-sha256` (S3 itself verifies the hash) and is create-only. Readers fetch a blob only when they need it. Blobs count against the lane's byte budget and follow its retention |
| Names stay on the client | — | Agreed, and it is enforced by design: config is keyed by token hashes |
| **Signed appends, without the server holding identifying keys** | no | **Their trade-off is right, and §4 as written breaks the rule.** A pki.sgit.ai fingerprint names a person in a public register. **Revised §4: lane keys and grants.** Each lane gets its own random P-256 key, which identifies nothing. The owner gives each writer a signed, expiring **grant** bound to `sha256(writer SPKI)`. The server stores only the lane's public key and the hashes of revoked grants. It verifies grant → writer key → append signature. Writers can still use their pki.sgit.ai keys: the owner checks the register before issuing a grant. The writer key passes through the server only inside the request, and the attestation travels **inside the sealed entry**, not in a server sidecar |
| Per-IP and per-token rate limits | — | Per-IP at the edge (CloudFront/WAF rate rules), not in the app: IPs are identifiers. Per-token = §2 limits |
| Rotate or revoke tokens without recreating the lane | **yes** (`append_anchors` is a list) | **But broken by §1.2**: a revoked token keeps working on other warm instances. The Phase 1 TTL fixes it |
| **Webhook on append (bare signal)** | no | **Dropped on 25 Nov by Dinis: the server makes no outbound calls** (plan ground rule 7). The analysis is kept for the record. Worth building **generically** (n8n and similar accept plain POSTs). Guards: https only, public addresses only, no redirects (SSRF, incl. the Lambda runtime API on localhost); at most one signal per lane per N seconds (anyone holding the public token could otherwise make us hammer the owner's URL); the URL is the one piece of plaintext config, so it is owner opt-in. **Waking a Claude cloud session this way probably does not work:** a session's inbound webhook (`watch_url`) expects deliveries signed by Anthropic's artifact service, whose credential only that service can open, so an unsigned POST from SG/Send is likely refused. Not tested (the probe was blocked). Confirm before agents depend on it |
| One read call | **yes**: `list` with `include_content` (3 MiB a page) | Document it. The server's `fetch` takes 100 ids [code-read]; the 20-id limit is in their client |
