# Review — `sg.llm.*` as built, and what to do next

**Date:** 2026-08-13 · **Role:** Architect · **Branch:** `claude/zealous-thompson-yDjFX` (== `origin/dev`)
**Reviews:** the plan in `team/roles/architect/reviews/08/02/v0.33.43__architect-review__sg-llm-kernel-capability-plan.md`
against the code actually shipped between 2026-08-02 and 2026-08-06.
**Method:** agent-assisted audit of every `sg-llm*` source and test, with the two most serious
findings re-verified by hand before being written down here.

---

## 1. Verdict

**Phase 1 shipped, and then some.** The bridge exists with a wider surface than planned, the
accounting of Phase 2 largely landed with it, and the security property that mattered most is
not merely claimed but *pinned by tests*: **the key never reaches the app frame.**
`test__app_shell_llm_bridge.js` uses a sentinel key and asserts its absence from the injected
bridge string, from every delta frame, and from the terminal reply. The `.vault/**` floor holds
at both layers (`AppPermissions.isFloor` for the bridge, `SGLlmTools.isFloor` independently for
the host tools). 11 test files, ~641 assertions, full suite green.

**But the plan's central coupling was half-delivered, and that half is the dangerous half.**
§7 of the plan said: *ship key custody **with** egress lockdown, because moving the key into the
kernel is insufficient if the frame can still `fetch` anywhere.* Key custody shipped. Egress
lockdown did not. The result is the exact configuration the coupling existed to prevent: apps
now have a strong incentive to take the LLM grant, and taking it buys them nothing in
containment.

Two things make that worse than a missing feature, and both are why this review exists:

- **The code asserts the CSP as fact.** `app-permissions.js:174-178` documents `permissions.network`
  by stating that app frames *are* served with `connect-src blob: data:` so "the postMessage
  bridge is the only way out". Verified false: `_appSandbox()` returns
  `'allow-scripts allow-forms'` (+ popups under `externalLinks`) and nothing else; there are
  **zero** `http-equiv` occurrences in `app-shell.js` and no `connect-src` anywhere outside
  `team/` prose. A reader of our own source is actively misled about a security control.
- **`permissions.network` is a dead grant.** Parsed, exported, read by nothing. `true` and
  `false` are behaviourally identical because the default is already unrestricted.

## 3. Findings, ranked

### F1 — Egress containment missing; the source claims otherwise (**highest**)
T3 (exfiltration of decrypted vault content by direct `fetch` from the frame) is entirely
unmitigated. The false comment compounds it. **Fix in two moves:** correct the comment today
(minutes), ship the CSP as its own change (days).

CSP must be `connect-src blob: data:` — **not** `'none'`. The print RPC fetches `blob:` URLs to
inline images and stylesheets; `'none'` would silently break printing. `img.src`/`import()` are
governed by `img-src`/`script-src` and are unaffected, so CDN component imports keep working.

### F2 — Consent can be switched off by the party the model treats as untrusted
`_consent` (`app-shell.js:1527-1540`) reads `mode` from `app.json` `permissions.consent[verb]`,
and `'auto'` returns `true` with no prompt. Plan §5.2 is explicit that `app.json` is authored by
an untrusted party and *declares intent only*. So an app author can write
`"consent": {"llm.chat": "auto"}` and disable the gate on a capability that **spends the vault
owner's money**. That is a two-tier-permission inversion.

Worse for `llm.listen`: only `vault.delete`/`vault.createKey` are `defaultAlways`, so a
**microphone** capability defaults to `'once'` — cached in `localStorage` indefinitely. The code
comment at `3690-3692` says "consent EVERY time by default. A microphone is not a capability to
grant once and forget." The code does precisely what that sentence forbids.

### F3 — Per-app budget caps are unenforceable as written
`limitsFor(policy, appId)` resolves **per-app** caps (`3791`) but compares them against
`VaultLlmLog.totals()` — a **session-global** ledger the host-native vault chat also writes to
(`_llmTotals`, `1382-1385`). Consequences: the owner's own chat spend can trip an app's
`EBUDGET`; two apps in a session cannibalise each other's budget; and the ledger entry
(`3856`) carries no app identity, so there is no per-app accounting or audit trail. The
librarian doc frames the shared ledger as intentional ("one bill per session") — defensible as
*UX*, but it silently nullifies a documented *feature*.

### F4 — `permissions.network` is dead
Parsed at `app-permissions.js:179`, read by nothing. Either wire it (F1) or delete it; shipping
a grant that does nothing while its comment promises a HUD indicator is worse than not having it.

### F5 — Host-side tools are a new surface the plan never contemplated (**decision needed**)
`sg-llm-tools.js` + `vault-llm-chat` load on `/en-gb/app/index.html` — the app *host* page. A
user running a sandboxed app now has, in host chrome beside it, an LLM with `files.read` over
the whole vault (empty `allow` = everything minus the floor), at host authority, entirely
outside that app's `permissions.fs` scoping, with an 8-round loop.

Mitigations are real and were clearly thought about: default-off grants, the governing file
unreachable by the tools it governs (`sg-llm-tools.js:91-97`), a 16 000-char read cap, results
fenced as UNTRUSTED. But the fence is advisory, and the residual is concrete: **a poisoned
document in the vault can steer `read_file`, and the model call itself is the egress.** Plan §8's
letter ("no kernel-side tool dispatch") is honoured — nothing is exposed to app frames — but its
spirit now has a host-side exception. This is a product decision, not a bug; it needs an explicit
one rather than arriving by accretion.

### F6 — HUD surfacing is thin
A 6-second transient toast, once per session (`app-shell.js:1506`). The bridge-call activity
meter explicitly `return`s on anything that is not a file op (`app-hud.js:447`), so LLM calls are
invisible to it, and there is no cost pill anywhere in the app HUD. For a capability that spends
money on the user's behalf, "it flashed once, earlier" is not adequate.

## 4. Plan

Ordered by risk-reduction per unit of effort. P0 is hours; nothing here is a rewrite.

### P0 — Truth and consent (do first)
1. **Correct the false CSP comment** in `app-permissions.js`; mark `network` explicitly as
   *reserved, not yet enforced* until F1 lands. Removes an active source of misplaced trust.
2. **Make `llm.*` consent non-overridable by `app.json`.** Ignore `'auto'` for `llm.chat` /
   `llm.listen`; the manifest may only make consent *stricter*, never weaker. This restores the
   two-tier model for the spending capability.
3. **`llm.listen` → `defaultAlways`.** Make the code match its own comment; a microphone grant is
   not cacheable.
4. Tests: consent-policy matrix asserting `'auto'` cannot weaken an `llm.*` verb, and that
   `listen` never reads the consent cache.

### P1 — Close the boundary (the plan's original Phase 1, finished)
5. Inject `<meta http-equiv="Content-Security-Policy" content="connect-src blob: data:">` as the
   first child of `<head>` in every app srcdoc path (`2280 / 2358 / 2412 / 2453`), **omitted when
   `permissions.network` is true**. `blob:`/`data:` are required — `'none'` breaks print.
6. **Wire `permissions.network`** to that omission and add the standing HUD indicator its comment
   already promises. An app with direct egress must look different from one without.
7. Tests: bridge-build pins asserting the meta is present by default, absent under `network`,
   and that `blob:` survives; one browser case proving print still works under the CSP.
8. Update `AUTHORING.md` with the new default and the escape hatch.

### P2 — Make the accounting true
9. **Tag ledger entries with an app identity** (`self._appId`, already computed for consent).
10. **Scope budget checks to that identity** when a per-app block exists in
    `.vault/llm/config.json`; keep the session-global total as the *display* figure. Then
    per-app caps mean what the config says.
11. Tests: two apps in one session don't cannibalise; host-chat spend doesn't trip an app cap.

### P3 — Decide on the host-side tools (needs the human)
12. Options, in increasing restriction: (a) leave as-is, documenting the trust assumption
    plainly; (b) scope `files.read` grants to explicit path prefixes with no empty-means-all
    default; (c) require a per-session confirmation when tools are enabled on the `/app` page
    specifically, since that is where an untrusted app is co-resident.
    **Recommendation: (b) now, (c) if tools ever gain a write verb.**

### P4 — Surfacing
13. Standing HUD affordance for LLM activity + a session cost pill in the app HUD; make the
    activity meter stop filtering out non-file bridge calls.

---

## 5. What I would not change

- The wider-than-planned bridge surface (`listen`, `imagePart`, `usage`) — additive, tested,
  and `available()` remains the honest feature-detection entry point.
- The shared session ledger as the *displayed* total. One bill per session is the right UX; the
  fix is to add per-app attribution underneath it, not to split the display.
- `sg-llm.js` staying DOM-free and bridge-free. That is why the kernel could reuse it unchanged,
  and it is why the host-native chat and the bridge share one transport rather than two.
