# Architect spec — Release channels for vault apps ("pin a version")

**Date:** 2026-08-02 · **Version:** v0.33.47 · **Status:** PROPOSED — nothing below is built yet
**Source:** Dinis voice brief, 2026-08-02 (`Vault_Feature_Enhancement` Otter transcript)
**Grounded against:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3` (code-verified primitives)

---

## 1. The problem, in the brief's own terms

> *"I want to keep pushing new versions to the vault, but I want to be in a position where I
> don't break what exists… the user doing the demo might be comfortable with the previous
> version."*

Today a vault link is a **moving target**. `sgit push` changes what every existing holder of the
key sees, instantly and irreversibly-from-their-side. There is no way to hand someone a stable
thing while continuing to work.

The ask: a curated set of named versions, selectable from the **host chrome** (HUD), configured by
a file in `.vault/`, and **invisible to the app** — *"the vault app should not be aware of that."*

---

## 2. Verdict up front — yes, and it is cheap

This is a **selection layer over data that already exists**. Every version is already in the vault:
SGit keeps the full commit DAG, immutable and content-addressed. Nothing needs to be stored twice.

Everything needed is code-verified as already present:

| Primitive | Where | Note |
|---|---|---|
| `logCommits({limit, from})` | `sg-vault--history.js:28` | the release picker's source of commits |
| `listTreeAt(commitId, path)` | `sg-vault--history.js:52` | built on `_flattenCommitTree` |
| `readFileAt(commitId, path)` | `sg-vault--history.js:74` | bytes at a commit |
| `_flattenCommitTree(commitId)` | same file | **`Map<path,{blob_id,size,content_hash}>` for a whole commit, cached** — this is `getFileList()` in one call |
| Data-source contract | `vault-data-source.js` | only `getFileBytes(path)` + `getFileList()` + `writable` are load-bearing for a mount |
| `.vault/**` is app-invisible | `AppPermissions.isFloor` | gives us "the app should not be aware" **for free** |

So the whole feature is: **one ~40-line read-only data source + one config file + one HUD control.**
The app-shell mount path talks only to the data-source interface, so `_mountApp`, `app.json`
resolution, resource injection and every `sg.vfs.*` call work unchanged against a pinned commit.

### Why it matters more than it looks

1. **It turns a vault link into a product with releases.** The difference between handing someone
   your working directory and handing them `v1.2`.
2. **It composes with read-only sharing.** `ro-token` + pinned release = *"exactly this version,
   read-only, revocable"* — a distributable artefact with a version number. That is what a demo, a
   client deliverable, or a security report actually needs.
3. **Rollback is honest.** An old release is not a *copy* that might have drifted — it is the same
   content-addressed objects. You cannot accidentally ship a "restored" version that differs from
   what people saw.
4. **Zero-knowledge is preserved.** The release map is an ordinary encrypted vault file. The server
   cannot tell v1.0 from v1.2, or that releases exist at all.
5. **It unlocks evidence-grade use cases** — "the report as it stood on 2 Aug" is exactly what
   audit, legal disclosure and regulated reporting need (connects to P-267 security-report demo and
   the VC data-room work, P-268).

## 3. Configuration — `.vault/releases.json`

Inside the permission floor, so apps can neither read nor tamper with it, and only an owner
(writable) session can edit it.

```json
{
  "schema": "sg-releases/v1",
  "default": "v1.2",
  "allowLive": true,
  "releases": [
    { "name": "v1.2", "commit": "<commit-id>", "label": "Black Hat demo",
      "notes": "stable narration path", "created": "2026-08-02T10:00:00Z" },
    { "name": "v1.1", "commit": "<commit-id>", "label": "pre-demo" }
  ]
}
```

Design notes:

- **Ordered array, not a map.** Array order *is* display order; object key order is not a contract.
- **`default` is the load-bearing field.** It decides what a *freshly opened link* gets. Without it,
  "don't break the demo" only works if every viewer manually picks the right version. With it, the
  owner pins the **audience** to a known-good release while continuing to push to HEAD. Omit it →
  live HEAD (today's behaviour, so the file is additive and safe).
- **`allowLive`** — whether non-owners may select "Live (latest)". For a demo you may want *no*
  route to HEAD.
- Absent file → **nothing changes anywhere**, no HUD control. (The brief's own rule.)

### The subtle rule that makes it work

> **The release map is always read at HEAD. Only the app content is pinned.**

If `releases.json` were read at the pinned commit, pinning to v1.0 would freeze the release list to
whatever v1.0 knew about — you could never see, or return to, anything newer. The map is live; the
content is pinned. This is the one rule that is easy to get wrong and expensive to discover later.

## 4. Resolution order

For a given open, the effective release is the first that resolves:

1. **URL pin** — `#<key>|@v1.2` (see §6)
2. **User's stored choice** for this vault (`localStorage`, per vault id)
3. **`default`** in `releases.json`
4. **Live HEAD** (today's behaviour)

An unknown/removed release name must **fail visibly** ("release v1.4 is no longer published —
showing Live"), never silently fall through to HEAD. Silently serving different content than the
link asked for is the exact failure this feature exists to prevent.

## 5. Implementation

### 5.1 `PinnedVaultDataSource` (new, ~40 lines)

```js
class PinnedVaultDataSource {
    constructor(vault, commitId) { this._v = vault; this._c = commitId; this.writable = false; }
    async _map() { return this._files || (this._files = await this._v._flattenCommitTree(this._c)); }
    async getFileList() { /* Array.from(map) → [{path,name,dir,size}] */ }
    async getFileBytes(path) { return this._v.readFileAt(this._c, path); }
}
```

`writable` is **always false** — not a limitation, a safety rule: committing on top of an old tree
would diverge the branch. Pinned means read-only, full stop.

`getFileList()` is currently **synchronous** on `VaultDataSource`; the pinned one needs one async
warm-up. Resolve by pre-warming `_flattenCommitTree` during mount (before handing the source over),
so the sync contract is preserved. *Do not* make the interface async — every existing caller would
have to change.

### 5.2 app-shell wiring

- On mount: read `.vault/releases.json` **at HEAD** (walk lazy sub-trees — see the `_ensureSubtree`
  fix in `sg-llm-vault.js`; `.vault/` is lazy and one-level expansion is a known trap).
- Resolve the release (§4). If pinned → build `PinnedVaultDataSource` and use it as `_dataSource`
  for the whole mount, **including reading that commit's `app.json`** (so entry, permissions and
  `hud.*` are that version's).
- `sg.app.writable` becomes `crypto && auth && !pinned` — extending the existing two-tier rule so
  apps degrade correctly instead of getting surprise `EREADONLY` on write.
- Writes while pinned reject with a distinct code (`EPINNED`) and a real message, not a silent no-op.

### 5.3 HUD control

- Rendered **only** when `releases.json` exists.
- `<select>`: `Live (latest)` (if `allowLive`) + each release, current selected.
- A visible **pinned badge** (`⏱ v1.2`) whenever not on Live — pinned+read-only must be legible, the
  same principle as the existing read-only badge. A user who cannot save and cannot see why is a
  support ticket.
- Change → re-resolve + remount + persist + update the URL.

### 5.4 Publishing a release

Minimal viable: the SGit history view (`vault-sgit-view--history.js`) already lists commits with a
diff screen. Add **"Publish as release"** on a commit row → name/label prompt → write
`.vault/releases.json` → commit + push. Owner-only.

## 6. The URL — the part that makes it actually solve the demo problem

**This goes beyond the brief and I think it is essential.** The demo problem is fundamentally a
*sharing* problem. If the pin lives only in the demoer's `localStorage`, it is fragile: new laptop,
different browser, cleared storage, incognito — and they are on HEAD mid-demo, which is precisely
the failure being designed against.

The root hash inbox already parses `#<key>|app:<path>` (`vault-loader-routing.js` `runRoot`).
Extend the pipe grammar with a release selector:

```
https://dev.vault.sgraph.ai/#<key>|@v1.2                 → pinned, default entry
https://dev.vault.sgraph.ai/#<key>|@v1.2|app:index.html  → pinned + deep link
```

`@name` is unambiguous against existing segments (`app:` prefix, bare path). Then a pinned link is
**stable on any device, forever**, and the demoer needs no setup at all.

## 7. Traps (each will bite if unhandled)

| # | Trap | Handling |
|---|---|---|
| 1 | **Auto-sync un-pins you.** `_scheduleBehindCheck` → `_checkBehind` fast-forwards and calls `_remountCurrent()`. Mid-demo, that silently yanks the viewer to HEAD. | While pinned, **suppress the remount**. Keep the check, surface it passively: "a newer release is available". |
| 2 | Writes while pinned | `EPINNED`, `sg.app.writable === false`, HUD badge. Never a silent failure. |
| 3 | **Release map read at the wrong commit** | Always read at HEAD (§3). |
| 4 | Sub-vaults (`*.link.json`) | Link *records* pin naturally (they are files in the tree). The **child vault's own content does not** — it has its own HEAD. State this as a limitation; do not pretend otherwise. |
| 5 | **Garbage collection** | There is no GC today. Before anyone builds one, pinned commits must be roots. Write it down now — this is the kind of thing that silently breaks a year later. |
| 6 | Lazy `.vault` sub-tree | Walk **every** segment (the `ENOKEY` bug we just fixed was exactly this). |
| 7 | `sg.llm.*` ledger | Record the active release on each entry — cheap, and makes demo/cost forensics answerable. |

## 8. Phasing

| Phase | Scope | Value |
|---|---|---|
| **1** | `PinnedVaultDataSource` + read `releases.json` + resolve + mount pinned + `writable=false` + HUD badge | The capability exists; releases can be hand-authored |
| **2** | HUD dropdown + persist choice + `default` | The brief's actual ask, usable by non-authors |
| **3** | URL pin (`\|@name`) | Pinned links are shareable — the demo problem is genuinely solved |
| **4** | "Publish as release" from the SGit history view | Owners stop hand-editing JSON |
| **5** | Auto-sync notice while pinned; `allowLive:false`; release notes surfaced in the picker | Polish |

Phases 1–3 are the ones with real value; 1 and 2 are roughly a session's work given the primitives
already exist.

---

## 9. Open questions for the Product Owner

1. **Should `default` bind the owner too, or only other viewers?** Recommendation: only others —
   an owner opening their own vault should see Live unless they explicitly pin, otherwise "why
   aren't my pushes showing up" becomes a recurring confusion.
2. **Release names — free text or enforced semver-ish?** Recommendation: free text (`"Black Hat
   demo"` is more useful than `v1.2` for the audience), with uniqueness enforced.
3. **Should a pinned open be forced read-only even for the owner?** Recommendation: yes. The
   alternative (commit on top of an old tree) creates a diverged branch, which is a far worse
   experience than "switch to Live to edit".
