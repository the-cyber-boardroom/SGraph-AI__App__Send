# Architect review + plan — `sg.llm.*` as a kernel capability

**Date:** 2026-08-02 · **Role:** Architect · **Status:** PROPOSED — no code written yet
**Inputs:** the SG/Vault Workbench debrief set (Architecture, Developer, UX/five-role review,
`workbench.html` v0.6.8), cross-checked against this repo's shipped kernel
(`app-shell.js` / `app-permissions.js` / `app-hud.js`, v0.2.3).
**Ask:** let any vault app call OpenRouter models through the kernel, gated by our permission
model, with the key supplied by the vault admin and stored in `.vault/`.

---

## 1. Verdict up front

The Workbench's own migration thesis is right, and our kernel has moved far enough since it was
written that **most of the hard security work is already done**. Three of the five-role review's
highest-severity findings are structurally solved here today:

| Workbench finding | Status in this kernel |
|---|---|
| #6 app can rewrite its own `app.json` / entry (privilege escalation) | **Already impossible.** `AppPermissions.isFloor` denies all mutations to root `app.json`, and `normalizePath` collapses `..` so the floor can't be walked around (`app-permissions.js:56-66`). |
| #5 credential file readable by the agent (`vfs.read("key.json")`) | **Solved by construction if the key lives in `.vault/`.** `hasVaultSegment` makes every `.vault/**` path a non-grantable DENY for read *and* write. No deny-list needed — it's the floor. |
| #8 unrestricted frame egress | **Not solved, but now cheaply solvable** — and this proposal makes it a condition of the LLM grant (§7). |

So the work is genuinely additive: transport, custody, accounting, consent surface. The
Workbench app-side machinery it replaces (tool registry, parser, agent loop, composer, staging)
stays app-side — that split is correct and I am not proposing to move it.

**The single most important design decision** is where the key lives, and it follows from one
fact the Workbench docs never state plainly:

> **A vault is not a secret store from anyone who holds the vault key.** The vault is decrypted
> client-side; anyone who can open it can read every byte in it, including `.vault/`.
> The floor protects secrets from **apps**, not from **people**.

That gives a clean, honest threat model (§3) and it means "the admin puts a key in `.vault/`" is
sound for *self-hosted* use and **unsound as a distribution mechanism for keys we mint**. Both
are addressed below; the second is what Phase 4 exists for.

## 2. What we are building

```
        APP FRAME (null-origin srcdoc, allow-scripts allow-forms)
        ┌───────────────────────────────────────────────┐
        │  any vault app                                │
        │    await sg.llm.chat({messages, model}, onTok)│
        │    ▲ no key, no endpoint, no fetch            │
        └────┼──────────────────────────────────────────┘
             │ postMessage  {__sgCmdType:'llm'}   +  {__sgLlmDelta:id}
        ┌────▼──────────────────────────────────────────┐
        │  KERNEL / HOST (real origin)                  │
        │   1. permission:  app.json permissions.llm    │
        │   2. policy:      .vault/llm/config.json      │  ← admin-owned, floored
        │   3. consent:     HUD confirm (once|always)   │
        │   4. budget:      per-session / per-app caps  │
        │   5. transport:   SGLlm → fetch + SSE         │
        │   6. accounting:  invocations, cost recon     │
        │   7. surface:     HUD meter + Σ cost pill     │
        └────┬──────────────────────────────────────────┘
             │ HTTPS (key attached here, never in the frame)
        ┌────▼──────────────┐
        │ OpenRouter        │
        └───────────────────┘
```

The app never sees the key, never learns the endpoint, and — with the CSP in §7 — cannot reach
any network host directly. The bridge becomes the only way out of the frame, which is what
finally closes the trust boundary the Workbench deliberately left open.

## 3. Threat model (state this before any code)

| # | Adversary | Capability | Mitigation |
|---|---|---|---|
| T1 | **A malicious or buggy vault app** | Runs arbitrary JS in the frame; can call any granted verb | Floor (`.vault/**` unreadable) + `permissions.llm` grants + consent + budget caps |
| T2 | **Prompt-injected model output** flowing back into an app that acts on it | Can cause the app to emit further `sg.llm.chat` / `sg.fs.*` calls | Same as T1 — the kernel does not care *why* the app called; caps and grants bound the blast radius. Kernel never dispatches app callbacks (§8) |
| T3 | **Exfiltration of decrypted vault content** by app or injected code | Today: unrestricted `fetch` | **CSP `connect-src` lockdown coupled to the LLM grant** (§7) |
| T4 | **A person you shared the vault with (read-only)** | Holds the *read* key → can read every ordinary vault file | **Largely solvable after all — see §3.1.** The owner-secret tier seals the credential with a key derived from the **write** key, which an ro-token session does not have. Residual: a *full* vault-key holder can still extract it (that is what "owner" means) |
| T5 | **The vault owner themselves**, if the key was minted by us | Can extract their own key and spend it outside the product | Server-side caps/TTL at mint time. A commercial problem, not a crypto one — do not pretend otherwise |

T5 is the one the Workbench's business model rests on, and it is an honest limit of
"key in the vault". The architecture below is deliberately shaped so Phase 4 can swap the key
source without any app-visible API change.

### 3.1 Correction — the owner-secret tier changes T4 (added 2026-08-02)

My first draft asserted flatly that *"a vault is not a secret store from anyone holding the
vault key"*. That is **only true of ordinary vault files**. This repo already ships
`SGVaultOwnerSecrets` (`_common/js/lib/sg-vault/sg-vault-owner-secrets.js`), which seals a
record with an AES-GCM key derived by HKDF from the vault's **write key** — and
`SGVault.openReadOnly` sets `_writeKey = null`, so an ro-token session *cannot derive it*
(`sg-vault.js:94-102, 208-209`).

Consequence: **read-only sharing does not have to share the credential.** That materially
improves the design and pulls part of Phase 4's benefit forward to Phase 1. The config
therefore carries an explicit **key tier**:

| Tier | Where the key sits | Who can use `sg.llm.*` | Who can extract the key |
|---|---|---|---|
| **`owner`** (default) | sealed via `SGVaultOwnerSecrets` inside `.vault/llm/config.json` | write-key holders only | write-key holders only |
| **`shared`** (opt-in) | clear in the same file (still read_key-encrypted at rest) | anyone who can open the vault | anyone who can open the vault |

`shared` is a real choice, not a footgun to hide: a team vault where every reader should be
able to spend the owner's budget is a legitimate configuration — it just has to be *chosen*,
with the extraction consequence stated in the UI. Default is `owner`.

This also resolves **Q2** (below) more precisely than either of the two positions in the
original draft: we do not need a policy switch to decide whether read-only sessions may call
`sg.llm.*`, because the **key tier already decides it, cryptographically**. `owner` → an
ro-session gets `ENOKEY` because it genuinely cannot open the seal; `shared` → it works. No
security theatre, and no policy flag that pretends to protect something it cannot.

## 4. API surface — `sg.llm.*`

Injected into the bridge exactly like `sg.append.*` / `sg.vfs.*`. Verbs, deny-by-default:

```js
// Streaming chat. onToken is a FRAME-LOCAL function (never crosses postMessage);
// the bridge wires a delta listener keyed by request id.
const res = await sg.llm.chat({
    messages : [{role:'user', content:'summarise docs/report.md'}],
    model    : 'anthropic/claude-sonnet-4',   // optional → policy default
    stream   : true,                          // default true
    tools    : [...],                         // optional, passed through (see §8)
    maxTokens: 2000,
}, onToken);
// → { content, model, finishReason, usage:{promptTokens, completionTokens},
//     cost:{value, source:'openrouter'|'generation'|'estimate'}, id, toolCalls? }

await sg.llm.models();     // [{id, name, pricing, context, modalities}] — policy-filtered
await sg.llm.usage();      // {calls, promptTokens, completionTokens, cost, remaining}
sg.llm.cancel(id);         // abort an in-flight call (kernel aborts the fetch)
sg.llm.available();        // {ok:bool, reason?:'ENOKEY'|'EPERM'|'ESTATIC', models:n}
```

Design notes:

- **`available()` is not optional.** Every other `sg.*` namespace can be feature-detected by
  existence; LLM additionally depends on *runtime* state (is a key configured? is this a static
  host? has the budget run out?). Apps must be able to degrade before rendering a chat UI.
- **`models()` is policy-filtered**, so an app cannot enumerate models the admin disallowed, and
  the picker an app builds is automatically correct.
- **`usage()` returns `remaining`** so apps can show a budget bar without knowing the cap.
- Errors reuse our existing shape/codes: `EPERM` (no grant), `ECONSENT` (user declined),
  `ENOKEY` (no key configured), `EBUDGET` (cap reached), `EMODEL` (model not allowed),
  `ESTATIC` (static-host mode), `EPROTO` (upstream failure).

### 4.1 Streaming over postMessage

`sg.vfs.read` is one request → one reply. Chat is one request → N deltas → one terminal reply.
Wire format:

```
app  → host : {__sgCmdType:'llm', action:'chat', __sgCmdId:id, messages, model, stream}
host → app  : {__sgLlmDelta: id, delta:'…'}        ×N   (kernel-coalesced, ~50ms / ~256 chars)
host → app  : {__sgCmdReply: id, ok:true, result:{content, usage, cost, …}}
```

Three rules that matter:

1. **Coalesce in the kernel, not the app.** A token-per-postMessage flood is the obvious
   performance trap; the kernel batches on a ~50 ms timer (the same cadence the Workbench found
   optimal for its render throttle) and always flushes the tail before the terminal reply.
2. **Deltas carry only the increment**, not the accumulated string — O(n) total, not O(n²).
3. **The terminal reply is authoritative.** An app that ignores `onToken` entirely still gets
   the full `content`. Deltas are a UX affordance, never the source of truth.

Cancellation: `sg.llm.cancel(id)` posts `{__sgCmdType:'llm', action:'cancel', id}`; the kernel
aborts the underlying fetch and settles the original promise with the partial content plus
`finishReason:'aborted'` — the Workbench's hard-won lesson that discarding a partial makes Stop
feel like data loss, and that the aborted call must **still** be recorded and costed.

## 5. Key custody and admin policy

### 5.1 Where the key lives

`.vault/llm/config.json` — inside the floor, so **no app can read it under any grant**:

```json
{
  "schema"  : "sg-llm-config/v1",
  "provider": "openrouter",
  "key"     : "sk-or-v1-…",
  "endpoint": "https://openrouter.ai/api/v1",
  "models"  : { "allow": ["anthropic/*", "openai/gpt-4o-mini"],
                "default": "anthropic/claude-sonnet-4" },
  "limits"  : { "maxCostPerSession": 1.00, "maxCallsPerSession": 200,
                "maxTokensPerCall": 8000, "maxConcurrent": 2 },
  "apps"    : { "workbench.html": { "maxCostPerSession": 0.50 } },
  "observability": { "appendAnchor": null }
}
```

Written by the **vault admin through host UI** (real origin), never by an app — writes to
`.vault/**` are floored, so this is enforced, not merely conventional. Needs a small
"LLM settings" panel in the vault browser (`/en-gb/vault/`), following the existing
`.vault/access-token.json` precedent.

### 5.2 Two-tier permission — the important cut

There are **two authors with different trust levels**, and conflating them is how key-custody
designs go wrong:

| Layer | Authored by | Trust | Role |
|---|---|---|---|
| `app.json` `permissions.llm` | the **app author** (may be a third party, or an LLM that wrote the app) | untrusted | *declares intent* — a ceiling on what the app will ask for |
| `.vault/llm/config.json` | the **vault admin** (the human who owns the key) | trusted | *grants capability* — key, allowed models, budget |

**Effective capability = intersection.** An app declaring `"llm": {"chat": true}` in a vault
with no config gets `ENOKEY`; a permissive config grants nothing to an app that didn't declare
the verb. This mirrors how `fs.read` grants combine with the floor, and it means installing an
untrusted app can never widen spend.

`permissions.llm` parses like `permissions.append` — booleans, default-deny:

```json
{ "permissions": { "llm": { "chat": true, "models": true, "usage": true } } }
```

Deliberately **no budget numbers in `app.json`** — a limit an app author can set is not a limit.
Per-app caps live in the admin config's `apps` block.

### 5.3 Consent

Reuse the shipped machinery (`_consentPolicy` already supports `always` | `once` | `auto`).
Default for `llm.chat` is **`once` per (vault, app)** — a HUD bar naming the app, the model, and
the session cap: *"This app wants to use this vault's LLM key (anthropic/claude-sonnet-4, up to
$0.50 this session)."* Rationale: unlike `sg.ui.preview` (ephemeral display of readable content,
no consent), an LLM call **spends money and sends vault content to a third party** — it is an
effect that outlives the page, which is exactly the line we drew for downloads.

## 6. Cost accounting and observability

Lift the Workbench's two-source cost model into the kernel verbatim — it is the most rigorous
part of that codebase and every LLM app would otherwise reimplement it badly:

- Request with `usage:{include:true}`; if the stream carries `usage.cost`, that is real
  (`source:'openrouter'`).
- If not, schedule `GET /api/v1/generation?id=…` ~1.2 s later for the authoritative
  `total_cost` and native token counts (`source:'generation'`).
- Until then, estimate from `/models` pricing and **label it** (`source:'estimate'`); the HUD
  renders estimates with a `~` prefix. Never show an estimate as a bill.

Kernel-side because it is the **budget chokepoint**: `maxCostPerSession` can only be enforced
where the numbers are known. The HUD gains an LLM row (calls, Σ cost, remaining budget) reusing
the existing activity-meter pattern, and optionally appends invocation records to an
observability anchor via `sg.append.*` — the two capabilities compose naturally.

## 7. Egress lockdown — the coupling that closes the boundary

Moving the key into the kernel is **insufficient on its own**: a frame that can still `fetch`
anywhere can exfiltrate the decrypted vault content it legitimately holds (T3). The Architect
review of the Workbench says this plainly and it is right.

Proposal — **make the LLM grant conditional on giving up direct egress**:

> An app that declares `permissions.llm` gets a `<meta http-equiv="Content-Security-Policy"
> content="connect-src 'none'">` injected at the top of its `srcdoc` `<head>` (the bridge
> already injects there, before any app script runs).

The incentive is aligned: the app no longer *needs* egress, because the kernel does the calling.
Vault data can then leave the frame only through the bridge, where it is permission-checked.

Sequencing (this is why it is a coupling, not a blanket default):

- **Now:** CSP applied only when `permissions.llm` is present. Zero impact on existing apps.
- **Next:** opt-in `"csp": "strict"` for any app; encourage it in AUTHORING.md.
- **Later:** flip the default once the app corpus has migrated, with an explicit
  `permissions.network` escape hatch for the rare app that genuinely needs a third-party API.

Caveat to verify during implementation: `connect-src` governs `fetch`/XHR/WebSocket/SSE but not
`<img>`/`<script>` loads, and dynamic `import()` from a CDN is governed by `script-src` — apps
importing components from `dev.tools.sgraph.ai` (as the Workbench does for `sg-layout`) are
unaffected by `connect-src` alone. A stricter profile should be a separate, later decision.

## 8. What the kernel deliberately does **not** do

- **No kernel-side tool dispatch.** `sg.llm.tools.register()` — where the kernel calls back into
  app code — inverts the trust boundary in the dangerous direction. Instead: the app passes
  `tools` definitions, the kernel returns `toolCalls` in the result, and **the app executes them
  and calls `chat` again.** The kernel stays a transport; the agent loop stays app-owned.
- **No kernel agent loop, no kernel prompt.** Bounded loops, tool-call parsing, system prompts,
  memory and staging are app policy. The Workbench remains the reference implementation.
- **No native-vs-text tool-protocol opinion.** We pass `tools` through and surface the model's
  `supported_parameters` from `/models` so apps can capability-detect (the AI Engineer review's
  recommendation) without the kernel choosing for them.
- **No client-side budget claim dressed as security.** Kernel caps are UX and accident-prevention.
  The enforceable cap is the OpenRouter key's own credit limit, set at mint time. Say so in the
  docs.

## 9. Delivery plan

| Phase | Scope | Why this order |
|---|---|---|
| **1 — Custody + chat** | `.vault/llm/config.json` schema + host-side reader; `permissions.llm` parsing; `sg.llm.{available,models,chat,cancel}` with SSE streaming over postMessage; consent (`once`); CSP coupling; HUD "app is calling an LLM" indicator | The whole security thesis lands in one phase: key out of the frame **and** egress closed. Nothing after this changes the app-visible contract. |
| **2 — Accounting** | Invocation records, two-source cost reconciliation, `sg.llm.usage()`, budget enforcement (`maxCostPerSession`, `maxCallsPerSession`, `maxTokensPerCall`), HUD Σ pill | Needs Phase 1's chokepoint. Enables the "talk to your content" surfaces to be safe by default. |
| **3 — Admin UX** | LLM settings panel in `/en-gb/vault/` (paste key, choose allowed models, set caps, per-app overrides, "test connection"); redaction guarantees | Until this ships, configuring a vault means hand-editing a floored JSON file — fine for us, not for users. |
| **4 — Minted credentials** | Kernel exchanges the vault access token for a **short-lived, budget-capped** upstream token from SG-API; `.vault/llm/config.json` holds a *reference*, not a raw key | Removes T4/T5 entirely: the key is never in the vault, so sharing a vault no longer shares a credential. **This is the phase that makes the commercial model possible** — and Phase 1's API shape is unchanged by it. |
| **5 — Host-native "talk to this vault"** | A kernel-provided chat surface (HUD panel) that works in *any* vault with a configured key, no app code | The headline user value; deliberately last because it should sit on the finished capability, not race it. |

Phases 1–2 are the ones I'd start now. Phase 4 is the commercially load-bearing one and should
be scheduled as soon as 1–2 land — the Product Owner review's "everything gates on key
distribution" is correct.

## 10. Test strategy

Following the pattern that has been catching real regressions in this repo:

- **Pure unit (`test__app_permissions.js`)** — `permissions.llm` parse matrix: default-deny,
  non-boolean coercion, unknown verbs ignored.
- **New pure unit (`test__sg_llm_policy.js`)** — the intersection rule (app grant × admin
  config), model allow-list matching (incl. `*` globs), budget arithmetic and cap tripping,
  cost estimation vs reconciliation precedence. All pure functions in `sg-llm.js`, no network.
- **Bridge-build pins (`test__app_shell_bridge_build.js`)** — `sg.llm.*` exposed only with the
  grant; **the key never appears in the injected bridge string** (assert the config value is
  absent from `_buildVfsBridgeScript` output — this is the single most important regression pin
  in the whole feature); CSP meta present iff `permissions.llm` declared.
- **Transport unit** — SSE frame parsing against recorded fixtures, including the two bugs the
  Workdev doc found the hard way: **flush the decoder tail** (a final `usage` chunk with no
  trailing newline is otherwise lost) and **surface mid-stream `data:{"error":…}`** instead of
  returning an empty reply.
- **Browser integration** — one Playwright case: app calls `sg.llm.chat` against a stubbed
  endpoint, asserts deltas arrive, consent bar renders, budget cap rejects.

## 11. Decisions (answered 2026-08-02)

1. **Provider scope → OpenRouter only.** `provider` stays in the schema as a seam; no
   abstraction layer is built. *(Implemented: `SGLlmConfig.parse` pins `provider:'openrouter'`.)*
2. **Read-only opens → `sg.llm.*` works wherever the vault opens.** The original
   deny-by-default recommendation is **withdrawn**: a read-only token only stops *server-side
   writes*, so denying in-app use would block the legitimate path while leaving
   extract-the-key-and-use-it-elsewhere wide open — theatre. The **key tier** (§3.1) is the
   real control and it is cryptographic, not policy: `shared` works for every opener,
   `owner` is unopenable by an ro-session by construction.
3. **Static-host mode → `ESTATIC`.** Independent of this work; no kernel, no key, no
   credentialed call from a static page.
4. **CSP → default-on, with an escape hatch.** Stricter than the original phasing: the
   `connect-src` lockdown becomes the default for app frames, with a per-vault/per-app
   configuration option for the rare app that genuinely needs third-party egress. Sequencing
   note stands — ship it *with* Phase 1 so custody and containment land together, and give the
   escape hatch a visible HUD indicator so "this app can call the internet directly" is never
   silent.

## 12. Implementation status

**Shipped (2026-08-02)** — the admin surface, pulled forward from Phase 3 because the
capability is unusable without a way to configure it:

- `_common/js/lib/sg-llm/sg-llm-config.js` — pure policy module (parse / serialize /
  `modelAllowed` globs / per-app limits / key-shape check / redaction). Safe-by-default:
  junk or absent config collapses to `keyTier:'owner'`, allow-`*`, default limits.
  38 assertions in `tests/unit/vault_ui/loader/test__sg_llm_config.js`.
- **Vault Settings → "AI models (OpenRouter)"** — key entry (password field, cleared from the
  DOM after save), Test against `/models` from the real origin, Save, Clear; advanced block for
  key tier, default model, allow-list, and spend caps. Owner-tier saves seal the key with
  `SGVaultOwnerSecrets.deriveKey(vault.writeKeyHex)`.
- **Vault Settings → "Read-only access (share these together)"** — vault id, the combined
  `readkey:vaultid` value (the single form `sgit clone` accepts), and a ready-to-paste
  `sgit clone "…"` command, each with its own copy button.

**Also shipped (2026-08-02) — Phase 5 pulled forward ahead of Phase 1:**

- `_common/js/lib/sg-llm/sg-llm.js` — the **shared transport engine** (`SGLlm`): OpenRouter
  chat + SSE, abort-keeps-partial-and-costs-it, `models()`, `reconcileCost()`, and the pure
  helpers (framing, cost, file-context, redaction). 40 assertions.
- `_common/js/lib/sg-llm/sg-llm-vault.js` — `SGLlmVault.open(vault)`: config → unsealed
  credential → configured client, with `EREADONLY` arising cryptographically for ro-sessions.
- `<vault-llm-chat>` — native "Ask about this file" drawer in the vault UI, wired to the
  file being viewed via a `vault-file-viewing` event from `vault-browse-edit`. 19 assertions
  (jsdom mount smoke).

**Why the reordering was right.** The Vault UI is the *real origin*: no bridge, no
postMessage streaming, no CSP. Building the host-native surface first exercises the
transport, key-resolution and policy paths end-to-end at a fraction of the risk, and leaves
Phase 1 as *"expose the existing engine over postMessage + consent + CSP"* rather than
"build an engine and a bridge simultaneously". The engine is deliberately DOM-free and
bridge-free so the kernel can reuse it unchanged — that reuse is the point, not a bonus.

**Still PROPOSED** — the `sg.llm.*` bridge verbs and SSE-over-postMessage plumbing,
`permissions.llm` parsing, consent, kernel-side budget enforcement, the CSP coupling, and
Phase 4 (minted credentials).
