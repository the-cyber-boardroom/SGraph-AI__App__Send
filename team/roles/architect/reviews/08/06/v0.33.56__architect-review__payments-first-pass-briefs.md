## 1. Verdict

The three briefs are architecturally sound and — unusually for first-pass documents — already
converge on the patterns this codebase has *shipped and tested* in miniature. The
append-and-settle ledger is the Vault Append state machine; the budget-as-containment
chokepoint is the `sg.llm.*` bridge order (permission → consent → budget → policy → call);
the estimated-vs-billed discipline is `VaultLlmLog`; credential-not-address is the shipped
access-token system generalised. The design is buildable on primitives that exist.

Five things need correcting or deciding before implementation starts:

| # | Item | Severity |
|---|------|----------|
| 1 | The Token Gateway brief's assembled diagram and two of its closing sections still describe **RESERVE/RECONCILE**, which the Four Vaults brief (and its own §"The Ledger") explicitly removed in favour of append-and-settle. Stale internal contradiction — will confuse implementers. | High |
| 2 | "Write without read via public key" describes the **PROPOSED** append PKI layer, not the shipped mechanism (hash-gated capability tokens). The property claimed is real and shipped; the mechanism described is not. | High (accuracy) |
| 3 | Within one vault, **read access is all-or-nothing** (single `read_key`; the structure-key split is PROPOSED). The "gateway reads the snapshot but not the events" shape needs a second small store or an accepted gateway read-credential on the billing vault. | High (design) |
| 4 | The **streaming gateway does not fit the house Lambda pattern** (Mangum/Python — no response streaming). The gateway should be the first SGraph service on the container/long-running deployment pattern, which the repo already has. | High (build) |
| 5 | The OpenRouter-resale prohibition **invalidates two standing key decisions recorded in the reality tree** (2026-07-27 "OpenRouter carries both inference and billing"; the 27 July commercialisation kit). The Librarian must record the correction so future sessions don't build on it. | Process |

## 2. Review — Token Gateway brief (append-and-settle, forced in-line)

### 2.1 Validated against code and corpus

- **Resale prohibition → build the meter.** Consistent with P-299's own blocker
  ("payment brokering is regulated" — note P-299 was about brokering *payments*; metering
  *our own credential against our own ledger* is a different regulatory shape, but the open
  question at the end of brief 1 — regulatory position on rails — still applies and should
  be answered before anything customer-facing).
- **Never-in-line vs meter-in-line distinction.** Correct and consistent with the standing
  key decision (2026-07-23, "never-in-line" is the *governance product's* posture). The
  brief's requirement that the risk platform must not acquire an in-line dependency on the
  gateway should be promoted to a hard architectural rule in the new repo's CLAUDE.md.
- **Append-and-settle, no reservation, negative balances.** Strongly validated by shipped
  precedent: `VaultLlmLog` already records spend *after* the call (aborted calls still
  costed), keeps `estimatedCost` and `billedCost` in separate buckets, and reconciles
  against the provider statement by generation id. The brief's "cost is unknown until the
  call completes" is exactly why the LLM ledger works this way. Adopt the shipped
  invariants verbatim: **an estimate is never rendered as a bill; reconciliation moves,
  never double-counts; the join key to the upstream statement is stored on every event.**
- **Generic consumption meter (unit-typed events).** Right, and cheap now, expensive later.
  Tokens first; vault storage size second (the vault layer already computes
  `totalSize`/`fileCount` — surfaced in `sg.app` context today).
- **Fractal resale + "the meter must be authoritative somewhere".** Consistent with the ViV
  trust rules: authority flows parent→child, never transitive; usage events flowing upward
  mirrors the broker/audit pattern.
- **Privacy claim moves from architectural to operational.** Honest and correct. The
  structural mitigation the brief asks for ("a log that never contained content cannot leak
  it") matches the house pattern — gateway ledger events must be **metadata-only by
  construction** (model, unit type, quantity, rate, cost, timestamps, outcome, join key —
  a schema with no content field, enforced by Type_Safe).

### 2.2 Corrections

- **Stale reservation remnants (High).** The assembled architecture diagram shows
  `RESERVE → LEDGER (strong)` and `RECONCILE`; "What This Does Not Try To Be" says "the
  reservation must be strong"; two open questions ask about reservation estimates. The Four
  Vaults brief records that the reservation step was removed. The Token Gateway brief should
  be revised (or annotated) so the two documents agree: **hot path = read snapshot policy +
  forward + append event. Nothing reserved, nothing contended.**
- **Streaming compute shape (High).** The brief's Lambda analysis is right and understated
  for this codebase specifically: the house serverless stack is **Python + Mangum via
  `Serverless__Fast_API`**, and Lambda response streaming is managed-Node-runtimes only
  (custom runtime / web adapter otherwise). So the gateway is not just economically awkward
  on Lambda — it is *not buildable on the current house Lambda pattern at all* without
  abandoning either streaming or the stack. The repo already ships 7 deployment targets
  including Docker/Fargate/EC2; the gateway should be the first SGraph service deployed on
  the **container/long-running pattern** (which also fixes the pay-for-wall-clock economics
  and the disconnect-abandonment double-loss). The **billing plane**, by contrast, is
  bursty and fits the house Lambda pattern perfectly.
- **Concurrency/rate limiting is a new build.** The shipped access-token system has
  usageـlimits (decrement-per-use) but no rate limiting and no concurrency caps. The brief's
  "rate limit per credential" bound on credit exposure needs building; nothing exists to
  reuse beyond the token-lookup shape.

## 3. Review — Four Vaults brief (least privilege, derived balance, credential ≠ address)

### 3.1 Validated against code

- **Four-vault structure via vault-in-vault and links.** Buildable today from shipped
  primitives: `sg.vault.create({seedFrom, link, custody})` mints child vaults with keys
  sealed into the parent's owner-secrets; `*.link.json` + `CompositeDataSource` presents
  one unified tree; the `.vault/**` permission floor keeps config/custody material away
  from app code. The "customer master vault we hold, customer does not" inverts the usual
  direction (operator-held master) — that works, but note ViV production custody posture is
  *child-generated non-extractable keys* (D6); the operator-held master should follow the
  same discipline: per-customer child keys sealed under the operator master's owner-secrets,
  never a flat keyring.
- **Write-without-read as the ledger primitive.** The *property* is shipped and
  server-tested (133 tests): an `append_token` holder can write into `bare/append/` and
  cannot list, read back, count, alter, or delete — server-assigned filenames, no id leaked
  to the writer. A compromised gateway holding only an append token genuinely cannot
  exfiltrate or rewrite history. **Correction (High):** the brief describes the mechanism as
  "create a public key and a private key, and give the public key to the other vault" —
  that is the **PROPOSED** encrypt-on-write PKI layer (X25519 seal/open, dev pack
  `v0.32.1__vault-to-vault-append-comms/02`), not what is deployed. Today the gates are
  hash-compared capability tokens (`H(presented) == stored`), and confidentiality of the
  event payload rests on the *writer* encrypting before writing. For a billing ledger where
  the writer (gateway) is ours, that is acceptable at v1 — but the brief's stated properties
  ("cannot read the history it is appending to") hold via the token tiers, not via PKI, and
  the seal-to-recipient layer should be scheduled if third-party writers ever append.
- **Derived balance, nothing contended.** Sound, and better than the CAS-heavy alternative.
  Two shipped facts support it: (a) the vault batch API already exposes `write-if-match`
  CAS server-side for exactly the off-hot-path objects the brief nominates (snapshot,
  credential records) — no new storage capability needed; (b) unique-key appends into the
  append lane have no coordination requirement. The brief's S3-conditional-write citations
  are correct but partially unnecessary: **our own server already wraps that primitive.**
- **Credential ≠ address.** The strongest correction in the three briefs, and it resolves a
  *known shipped gap*: today "sharing a vault key shares spend authority" (the vault UI's
  Phase-4 "minted credentials" item, PROPOSED). The credential-record indirection
  (`credential → {account, scope, budget, expiry, status} → billing vault`) is the shipped
  access-token model generalised — `Schema__Token__Metadata` already carries
  `{token_name, usage_limit, usage_count, status, created_by, metadata}`. Extend that shape
  rather than inventing a new one, and note the deep synthesis in §5.3: **gateway
  credentials ARE the minted credentials the vault UI is waiting for.**
- **Deterministic paths leak equality — with one refinement.** True that a storage-level
  observer sees object counts, arrival rate, and timing per vault. One correction in the
  customer's favour: the deterministic file IDs are **HMAC-derived from the read key**, so
  an observer *without* the key cannot compute which path corresponds to which logical
  file — the leak is volume-and-timing per vault, not equality-of-content across vaults.
  The brief's conclusion stands: name it as an accepted risk with an owner.

### 3.2 Design gaps to resolve

- **Snapshot readability (High).** "The gateway reads a balance and appends events but
  cannot read the history" is not expressible *inside one vault* today: a vault has one
  `read_key` and the structure-key split is PROPOSED. Options, in order of preference:
  1. **Split the stores**: events live in the billing vault's append lane (gateway holds
     append token only); the **snapshot + policy live in a separate tiny "meter-state"
     store** the gateway can read — either a second small vault whose read credential the
     gateway holds, or (simpler, honest) operator-side state in the payments service's own
     `Storage_FS`, since the snapshot is operator-derived metadata anyway.
  2. Accept a gateway read credential on the billing vault and state it (weakens the
     least-privilege story: gateway could then read event history).
  Option 1 keeps the brief's least-privilege claim intact and costs nothing — recommend it.
- **Append-lane limits vs event volume.** Shipped caps: ≤5 MB per payload, **≤1000 files
  per append token**, list pagination ≤100. A per-request usage event stream will exhaust a
  single token's namespace quickly. Combine the brief's own batching recommendation (the
  2 Aug telemetry pattern: accumulate, flush on boundary, clear on confirmed write) with
  **time-sharded append tokens** (e.g. one per day) or lift the cap in the payments
  service's own storage tier. Since payments is a new repo with its own `Storage_FS`, the
  operator-authoritative ledger can use plain sharded `events/<ulid>` paths under
  `Storage__Paths`-style pure functions, with the *customer's provenance copy* delivered
  into their billing vault via append — two ledgers, one authoritative (operator, metadata-
  only), one sovereign (customer-readable). This also resolves the abuse-detection tension
  exactly as the brief recommends: metadata on our side, content nowhere.
- **"Cannot suppress an inconvenient event"** — a gateway can suppress by *not writing*.
  Detection is reconciliation: periodic cross-check of the operator ledger against upstream
  provider statements (the `VaultLlmLog` generation-id join pattern) and against the
  customer's copy. Cheap, but must be scheduled, not assumed.

## 4. Review — Not A Billing System brief (containment, provenance, rails, float)

- **Budget as containment control.** Validated by shipped precedent at small scale: the
  `sg.llm.*` chokepoint already enforces per-session cost/call caps host-side from a shared
  ledger with typed errors (`EBUDGET`), caps clamped not trusted. The gateway generalises
  this to per-credential/per-agent/per-action budgets server-side. "Revoking a metering
  credential is a plug with a small blast radius" — matches the shipped token revocation
  semantics (revoke stops server acceptance; note the 60 s positive-validation cache in
  `Service__Access_Token` — the gateway's revocation latency SLA must account for whatever
  cache it adds).
- **Provenance of inference.** The strongest product idea, and cheap because the gateway
  knows provider/model/policy/jurisdiction at routing time. Implementation note: this is a
  **unit-typed usage event with extra fields**, not a second system — put
  `{provider, model_version, jurisdiction, data_policy, routing_reason}` on the event
  schema from day one and the provenance product is a view over the customer's own billing
  vault. Delivery into the customer vault uses the shipped append lane; rendering uses the
  shipped vault browser / `_page.json` layouts — zero new UI platform needed for v1.
- **Master keys / multi-provider routing.** Sound. Custody: master provider keys are
  operator secrets and belong in the payments service's environment (env vars per house
  rule 14), with per-customer material sealed vault-side via owner-secrets. The four
  configurations table is right; note the customer-instance case aligns with the existing
  EC2/AMI deployment target and the ephemeral-compute work.
- **Sovereign rails, float inversion, grants-vs-purchases.** Commercially coherent;
  architecture implications adopted in §5: rail-agnostic `credits/` intake (the ledger does
  not care which rail credited the account), and **`origin ∈ {purchase, grant, adjustment}`
  on every credit event from v1** — the brief is right that separating them later means
  reconstructing history nobody kept. Unconsumed-credit-as-liability is an accounting
  posture the Alchemist should own.
- **Conflict of selling the control and the assessment.** Governance, not architecture, but
  it has one architectural consequence the brief names and the new repo should honour:
  **no shared dependency** — the risk/governance product must not depend on the payments
  service, and the payments repo must not import from it.

## 5. Build implications for the new repo (payments.sgraph.ai)

### 5.1 Repo shape — follow the house style, split the planes

```
SGraph-AI__App__Payments            (new repo, payments.sgraph.ai)
  sgraph_ai_app_payments/
    lambda__billing/                # BILLING PLANE — house Lambda pattern fits
      fast_api/Fast_API__SGraph__App__Payments__Billing.py   (Serverless__Fast_API)
      fast_api/routes/Routes__Accounts.py    ('accounts')
      fast_api/routes/Routes__Credentials.py ('credentials')   # mint/rotate/revoke/scope/budget
      fast_api/routes/Routes__Credits.py     ('credits')       # rail-agnostic intake + grants
      fast_api/routes/Routes__Webhooks.py    ('webhooks')      # per-rail, signature-verified, idempotent
      fast_api/routes/Routes__Ledger.py      ('ledger')        # snapshots, statements, reconciliation
      schemas/  (one Type_Safe class per file; Safe_* primitives on every boundary;
                 Schema__Usage__Event {credential_id, account_id, unit_type, quantity,
                 rate, cost, currency, origin, provider, model_version, jurisdiction,
                 data_policy, upstream_join_key, ts} — NO content field, by construction)
      service/  (Service__Accounts, Service__Credentials, Service__Ledger,
                 Service__Snapshots, Service__Reconciliation)
      storage/  (Storage__Paths pure functions; Storage_FS memory/disk/S3;
                 events/<shard>/<ulid> appends; snapshot + credential records via
                 write-if-match CAS)
    gateway/                        # GATEWAY PLANE — container/long-running, NOT Lambda
      (FastAPI app, same Type_Safe/OSBot style, deployed via the existing
       Docker/Fargate/EC2 patterns; hot path: authn credential → policy check against
       cached snapshot → forward+stream → append usage event (batched);
       reads meter-state, never the customer's vaults; holds append tokens only
       for customer billing vaults)
  tests/unit/   (no mocks; in-memory full stack via the Test_Objs singleton pattern;
                 upstream providers as real stub classes selected by config —
                 the CloudWatch__Client__Stub precedent — never patches)
```

Inter-service integration reuses the shipped `Admin__Service__Client` pattern: one client
class, `IN_MEMORY` transport in tests (the payments app booted in-process), `REMOTE` in
production — which is how SG/Send's User Lambda will validate gateway credentials without
mocks. From day one the new repo needs its own reality document, changelog discipline, and
`ROUTES_PATHS__*` route-drift tests.

### 5.3 The convergence worth designing for now

The vault UI's PROPOSED "Phase-4 minted credentials" (short-lived, budget-capped tokens so
sharing a vault does not share spend authority) and the gateway's credential records are
**the same object**. When SG/Send's `sg.llm.*` host swaps its raw OpenRouter key for a
gateway credential, every vault app instantly gets per-agent server-enforced budgets, the
provenance record lands in the vault automatically, and the known key-sharing gap closes —
with no change to any app, because the bridge contract stays identical. Design the
credential record so a vault-scoped, budget-capped, short-expiry credential is just a row,
and this convergence is a configuration change, not a project.

### 5.4 Suggested build order

1. **Ledger core + credential records** (billing plane, in-memory testable end-to-end):
   unit-typed events with `origin`, fold + snapshot, negative-threshold policy, CAS on
   snapshot/credential writes, grants vs purchases separated. No gateway yet.
2. **Rail intake**: one rail (Stripe checkout webhook — signature-verified, idempotent by
   event id via CAS create-only write), credits land in the ledger; the long-standing
   manual £5→tokens fulfilment gap closes as a side effect.
3. **Gateway v1** (container): one upstream provider, non-streaming first, metadata-only
   events, per-credential budget/rate policy, revocation latency stated; customer
   provenance copy appended into their billing vault (batched).
4. **Streaming + abandonment instrumentation**; curated model list; second provider.
5. **SG/Send convergence**: `sg.llm.*` host uses gateway credentials (5.3); voice tool
   moves onto the meter — the first product's billing becomes the platform's first tenant.
6. **Sovereignty options**: second rail (EU provider) behind the same `credits/` intake;
   customer-instance metering when a real customer asks.

### 5.5 Open decisions for the human (before Phase 1)

1. Snapshot/meter-state placement — separate meter-state store (recommended) vs gateway
   read-credential on the billing vault (§3.2).
2. Gateway compute — container-first (recommended) vs Lambda-with-custom-runtime.
3. Authoritative-ledger storage — payments-service `Storage_FS` (recommended) vs forcing
   all events through the vault append endpoints (caps, cost).
4. Regulatory review scope — P-299 was BLOCKED on "payment brokering is regulated";
   confirm the own-credential/own-ledger model's position before customer-facing launch.
5. Reality-tree corrections — record that the OpenRouter resale mechanism (27 Jul key
   decision) is invalidated, per the Token Gateway brief.
