This document is the "know how it all works" record requested before designing a payment
workflow on top of vaults. It covers: the Vault Web code (dev.vault.sgraph.ai), the SGit
protocol it rides on, the two Lambdas, the Type_Safe / OSBot house style, the Vault App and
Vault-in-Vault (ViV) architecture, and the shipped UX/workflow building blocks the Librarian
catalogued as most relevant to payments.

## 1. Vault Web (dev.vault.sgraph.ai) — what it actually is

- **Pure static assets on S3 + CloudFront, no Lambda serving.** Active tree:
  `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/` (~37k lines, IFD-versioned, vanilla JS
  Web Components, zero frameworks, classic scripts — load order is a contract). Deployed by
  `.github/workflows/deploy-ui-vault.yml`, gated by `_test-ui-vault.yml`.
- **The API is the User Lambda** (`dev.send.sgraph.ai`) under `/api/vault/*` —
  `Routes__Vault__Pointer` (write/read/read-base64/delete/batch/list/health/zip/destroy/
  public-info), `Routes__Vault__Append` (6 endpoints), `Routes__Vault__Presigned`.
- **Routing contract** (`_common/js/vault-loader/vault-loader-routing.js`): root `/` is the
  only hash inbox — `/#vault-key` saves the key to storage and redirects to `/en-gb/app`
  **with no hash** (keys never persist in URLs/history). `/en-gb/app` mounts the app if the
  vault has `app.json`, else forwards to the `/en-gb/vault` browser. `#key|@v1-2|app:path`
  carries release pins and deep links.
- **Two shells:**
  - `<vault-shell>` (`/en-gb/vault`) — the vault browser: file explorer (remote `SendBrowse`
    component + `vault-browse-edit.js` write affordances), `<vault-header>` sync pill
    (`● Synced / ↑N / ↓N / ⇅ Diverged / 🔒`), `<vault-sgit-view>` history/diff/repair,
    Settings (AI keys, releases editor), debug pane.
  - `<app-shell>` (`/en-gb/app`, 3,511 lines) — the SG/App host that runs vault apps (§4).
- **Client crypto pipeline:** PBKDF2 (600k iterations) derives independent `read_key` and
  `write_key`; HMAC over `read_key` derives even the *locations* of ref files; all objects
  are AES-256-GCM (12-byte IV + ciphertext + 16-byte tag). Open flow: branch index → named
  ref (live, `no-store`) → clone ref → reconcile-on-open → decrypt commit + tree
  (all metadata encrypted) → lazy sub-trees → blobs on demand.
- **Caching:** 3 tiers — module-level 64 MB LRU (the only tier that works in null-origin
  sandboxes), Cache API `sg-vault-blocks`, and browser HTTP cache (server sends
  `immutable, max-age=31536000` for `-imm-` objects). **No IndexedDB anywhere.**

## 2. SGit — the protocol layer

### 2.1 Keys and capabilities

| Credential | Derivation | Power |
|---|---|---|
| Vault key (`passphrase:vaultid` or simple token `word-word-NNNN`) | PBKDF2 ×2 (read salt / write salt) or PBKDF2+HKDF split | Full read + write capability |
| `read_key` | PBKDF2(passphrase, `sg-vault-v1:{vault_id}`) | Decrypt everything; derive file locations |
| `write_key` | PBKDF2(passphrase, `sg-vault-v1:write:{vault_id}`) | Sent as header on writes; server stores only `SHA-256(write_key)` in `manifest.json` |
| ro-token (`ro-word-word-NNNN`) | hash → transfer holding encrypted read credentials | Live read-only view |
| Share token (`sgit share`) | hash → transfer_id; PBKDF2 → AES key | One frozen zip snapshot; never the live vault |
| Access token (admin-minted) | opaque; `x-sgraph-access-token` | Account/quota gate on writes (usage_limit, decrement per use) |
| Append token / enum_key | four-tier append ladder (§2.4) | Blind write / drain capability |

Knowing `read_key` reveals nothing about `write_key` and vice versa — read-only capability
is cryptographic, not ACL-based. Reads are tokenless by design ("ciphertext is public").
Writes are **double-gated**: access token (account) AND write-key hash (capability).

### 2.2 Object model

Content-addressed store with self-describing 4-segment IDs
(`obj-cas-imm-{sha256(ciphertext)[:12]}`, `ref-pid-muw-*`, `ref-pid-snw-*`, `idx-pid-muw-*`)
under `bare/data|refs|indexes/`. Commits (`commit_v2`) are a Merkle DAG: commit → root tree
(`tree_v1`, names/sizes/content-hashes individually encrypted) → sub-trees → blobs. Commit
messages are double-encrypted. `signature: null` — **commits are not signed today**.

Server storage (`Service__Vault__Pointer` over Memory-FS):
`{ROOT}/vault/{id[:2]}/{id}/{file_id}/payload` — the server treats every file_id as an
opaque path; first authenticated write **claims** a fresh vault_id (self-registering, no
create endpoint). `write-if-match` CAS exists server-side (`{status:'conflict', current}`)
— the only optimistic-concurrency primitive, and important for payments (§6).

### 2.3 Sync model

Two-ref model: per-client **clone ref** (working head, advanced on every commit) + shared
**named ref** (published, advanced by `push`). Pull is fast-forward-only; the browser ships
a three-way file-level merge with `_conflict` copies; every logical write is **one**
`POST /api/vault/batch/{vault_id}` ordered `data → indexes → refs` so a ref never precedes
its target (write-batch = a transaction). The browser writes the branch index on every push
so `sgit clone` interops. Caveat: browser `push()` writes refs with plain `write`, not CAS —
concurrent pushers are last-writer-wins at the pointer (objects survive).

### 2.4 Vault Append — the cross-party rail (133 server tests)

One vault (or an account-less sender) writes into another **without being able to read it**:

- `append_token = H(...)` — blind write only; the sender cannot list, count, or read back
  its own write (server assigns filenames, leaks no ids).
- `enum_key` — list pending / fetch ciphertext / **mark-processed** (idempotent
  pending→processed move).
- `write_key` — configure/purge. `private_key` — decrypt, client-side only.
- Storage at `bare/append/{token}/pending|processed/` — **outside the commit DAG**; no
  access token required (account-less senders); ≤5 MB payloads.
- Client: `sg-append.js` + `sg-append-checker.js` (event-triggered checking, no timers) →
  `sg.append.*` bridge verbs + `sg.on('append.new-messages')` push into apps.
- The encrypt-on-write PKI layer (X25519 seal-to-recipient) is **PROPOSED** — today append
  confidentiality rests on the honest client encrypting before writing.

**This is a two-state workflow machine (request → pending → processed) with
capability-separated actors and push notification — the closest shipped thing to a payment
rail.**

### 2.5 sgit CLI (PyPI `sgit-ai`, repo `SGit-AI/SGit-AI__CLI`)

20+ working commands: init/commit/status/push (delta, re-encrypts clone-branch objects to
named-branch key)/pull/clone/log/diff/branches/switch/revert/stash/share/publish/export/
keygen/sign/verify/encrypt/decrypt/pki/inspect/fsck/uninit/vault-store. Offline-capable.
Two-layer branch model: one private clone branch per device/agent, push forwards to the
named branch — the documented multi-agent pattern (one clone branch per Claude session).
Claude-as-vault-peer is VERIFIED (clone → read SKILL.md → operate autonomously).

## 3. The Lambdas + Type_Safe / OSBot house style

- **Two apps**, both `Serverless__Fast_API` (osbot-fast-api-serverless → osbot-fast-api →
  Type_Safe): `Fast_API__SGraph__App__Send__User` (public; transfers, vault pointer, append,
  presigned, early-access; `enable_api_key=False` — per-route access-token checks) and
  `Fast_API__SGraph__App__Send__Admin` (tokens, keys, users, rooms, legacy vault CRUD;
  global API-key middleware + httponly cookie flow). Lambda Function URLs (no API Gateway),
  Mangum, SnapStart with content-addressed dependency zips, MCP mounted at `/mcp` on both.
- **Dependency injection, Type_Safe style:** every service is a nullable typed class
  attribute auto-created in `setup()` — which is why the whole stack starts in-memory in
  ~100 ms with zero mocks (`Storage_FS__Memory`; the Admin cache and inter-Lambda client run
  as real in-process FastAPI apps via the Service Registry's IN_MEMORY mode).
- **Type_Safe:** validation on every assignment; `Safe_Str` subtypes in REPLACE (sanitizing)
  or MATCH+strict (rejecting) modes — every path parameter is a `Safe_*` type so `../` never
  reaches storage; FastAPI integration auto-generates throwaway Pydantic models from
  Type_Safe classes (Pydantic exists only as an invisible adapter).
- **Routes convention:** `Routes__X(Fast_API__Routes)` with `tag`, method-name→path
  derivation (`def lookup__payment_id` → `GET /{tag}/lookup/{payment_id}`), and a mandatory
  `ROUTES_PATHS__X` constant asserted verbatim by the app-level route test.
- **Storage:** everything through `Storage_FS` (memory/disk/S3 via `Send__Config`
  auto-detection); paths from pure functions in `Storage__Paths.py`
  (`{ROOT}/{entity}/{id[:2]}/{id}/meta.json` sharding). AWS only via osbot-aws.
- The full "how to add a payments module in house style" sketch is in the plan document §7.

## 4. Vault Apps + the `window.sg` capability surface

A vault app = HTML/JS **stored inside the encrypted vault**, executed by `<app-shell>` in a
**null-origin sandboxed iframe** (`sandbox="allow-scripts allow-forms"`, srcdoc, no
`allow-same-origin` — SEC-VIV-001 closed). The app gets **capabilities, never credentials**:
`window.sg.*` RPCs over postMessage; the vault key and access token stay in the kernel.

Key facts for payments:

- **`app.json`** declares entry, resources (no `<link>`/`<script src>` — host-injected),
  `permissions` (mutations deny-by-default, path-scoped, e.g. `"write": ["data/"]`),
  `host_events`, `hud`. `appId = SHA-256(app.json bytes)`.
- **`.vault/**` is a non-grantable security floor** — invisible and unwritable from app
  frames. This is where releases.json, llm/config.json, owner secrets, access-token.json
  live — and where payment config/state must live.
- **Consent UX:** `sg.ui.requestPermission` → HUD consent bar (unsuppressable, Deny-focused,
  risk-tiered; `permissions.consent[verb] ∈ always|once|auto`); privileges chip (`🔒 N`),
  file-activity meter (`⇅ R N W N`). The approve step of a payment maps directly onto this.
- **`sg.llm.*` — the strongest shipped precedent for payments.** Full key-custody proxy:
  OpenRouter key never enters the app frame; ordered host chokepoint
  **permission → consent → budget → model policy → call** with typed errors
  (`EPERM/ECONSENT/EBUDGET/EMODEL/ENOKEY/EREADONLY/EABORT`); budget enforced host-side from
  the **shared** `VaultLlmLog` ledger (app spend + chat spend = one bill); caps clamped,
  never trusted; aborted calls still costed; `billedCost` vs `estimatedCost` kept separate
  (estimates rendered with `~`, never as bills); OpenRouter **generation id as the
  reconciliation join key** against the provider statement. Key tiers: `shared` (clear) vs
  `owner` (sealed via owner-secrets — a read-only session *structurally cannot spend*
  because no write key exists to derive the unseal key).
- **Owner-secrets** (`sg-vault-owner-secrets.js`): HKDF over write-key → AES-GCM seal/open
  at `.vault/owner/secrets/` — the custody mechanism for child-vault keys and owner-tier
  API keys; the exact pattern for a payment credential.
- **Child vaults:** `sg.vault.create({seedFrom, link, accessToken:'inherit', custody})`
  mints per-counterparty/per-transaction vaults from templates, keys sealed into
  owner-secrets, `getKey` behind always-confirm consent; `*.link.json` +
  `CompositeDataSource` composes them read-through into the tree.
- **Releases:** `.vault/releases.json` (floored) — named releases pin the whole app+data at
  ONE immutable commit (`PinnedVaultDataSource`, `EPINNED`, read-only for everyone incl.
  owner; resolution url > stored > default > live; `#key|@v1-2`). **Immutable receipts and
  terms-as-of-acceptance already exist as a mechanism.**
- **Embed protocol:** 3-message handshake (`vault-embed-ready → vault-open → vault-ready`),
  key in memory only; `sg.vault.embed()` refuses `allow-same-origin` even if requested — the
  checkout-widget model.

## 5. Vault-in-Vault (ViV) kernel

One primitive applied fractally: **mount = child kernel in a null-origin iframe**, secrets
delivered encrypted over `SecureChannel` (P-256 sign, ECDH→AES-GCM, replay guard, port-
anchored). Trust is parent→child only, never transitive. Every kernel talks to SG/API
directly (the broker is not a network proxy; the enabling server change was CORS
`allow_credentials=False` so `Origin: null` gets `*`). Per-kernel **`KernelBroker`**
mediates and logs every cross-mount op (default: reads auto, mutations ask; metadata-only
audit log; cross-kernel Audit tab). Hardening gates, all shipped with 335+ assertions:
credential tiers (fail-closed `EUNDERPRIVILEGED`; standing-ro vs per-request-rw — maps to
standing mandate vs per-transaction authorisation), custody gate (`EUNSAFE_CUSTODY`;
production posture = child-generated non-extractable keys), monitor mode (CLOSED by
default, consent-honest). Caveat: the assembled user-facing `sg.vault.mount()` is **P-250
PROPOSED** (pieces exist, ~80 lines of assembly), rw mounts are PROPOSED, and live app
frames still use the inline bridge (SecureChannel promotion is Phase 6).

## 7. What the platform guarantees a payment workflow — and what it does not

**Can rely on:** cryptographic integrity (GCM tags + content-addressing — a commit id
transitively pins the whole history); structural immutability (write-once CAS objects);
audit replay (log/diff/dump/fsck; pending→processed append state machine; metered token
usage with ip_hash events); zero-knowledge boundary (amounts/counterparties/invoices are
ciphertext to the server and to a subpoena); capability separation (read / write /
append-only / frozen snapshot); a server-side CAS primitive (`write-if-match`); atomic
multi-file write batches.

**Must NOT rely on (design must compensate):**
1. **Refs are mutable, last-writer-wins** — no server-enforced fast-forward; anchor payment
   heads with CAS writes and counterparty-held head receipts.
2. **No commit signatures** (`signature: null`) — write-key holders are indistinguishable;
   sgit PKI exists but is file-level. Receipts need explicit signing.
3. **Timestamps are client-asserted** — PSP/webhook timestamps must be the authoritative
   clock for money events.
4. **Deletion is possible** (delete/destroy+purge) — durable evidence needs exports,
   snapshots, or replication (multi-remote PROPOSED); no GC exists yet.
5. **Traffic shape is visible** (counts, sizes, cadence, IPs).
6. **Sharing a vault key shares spend authority** — until Phase-4 minted credentials
   (PROPOSED), owner-tier sealed custody is the only mitigation, and it is a good one.
7. **Key custody is absolute** — no reset/escrow; losing the vault key loses the ledger.
