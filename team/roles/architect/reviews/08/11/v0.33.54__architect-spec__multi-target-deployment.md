## 1. The Architectural Thesis

**One OCI image is the unit of deployment. Every runtime is an adapter around it.**

Today the project has two deployment mechanisms that share no artifact: the Lambda zip
(+ combined-deps S3 cache) and the Docker image. This spec collapses them: the existing
`sg-send-vault` image (EXISTS, multi-arch, published) becomes the single artifact, and each
target — Lambda, EC2, Cloud Run, Heroku — is a thin, declarative wrapper that runs it.

```
                          ┌──────────────────────────────┐
                          │   sg-send-vault OCI image     │
                          │   (EXISTS — one build, CI)    │
                          │   + LWA extension  (Phase A)  │
                          │   + $PORT contract (Phase A)  │
                          └──────────────┬───────────────┘
              ┌───────────────┬──────────┼──────────────┬───────────────┐
              ▼               ▼          ▼              ▼               ▼
        AWS Lambda        AWS EC2     GCP Cloud       Heroku        Docker
        (container fn,    (CFN:       Run             (container    local/EC2
         Function URL)     docker +   (Phase D1)      stack,        by hand
        [CFN: Phase B]     caddy)                     Phase D2)     (EXISTS)
                          [CFN: Phase B]
              │
              ▼
        Netlify is NOT an API runtime → serves the STATIC vault UI
        (SGSend.staticMode, EXISTS since 2026-06-30)   [Phase D3]
```

The Lambda **zip path stays untouched as the incumbent** until the container path has
run in dev long enough to trust — the same coexistence pattern used for the
combined-deps rollout and the append/config.json migration.

## 2. Decision Records

### ADR-1: Lambda Web Adapter over a second Mangum image — ACCEPTED (proposed)

Two ways to make the image Lambda-runnable:
- **(chosen) LWA extension**: `COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter … /opt/extensions/`.
  The adapter translates Function-URL events ↔ HTTP against `:8080`. It activates only when
  `AWS_LAMBDA_RUNTIME_API` is present — **inert on every other runtime**. One image, all targets.
- (rejected) A second image `FROM public.ecr.aws/lambda/python:3.13` with the existing Mangum
  handler as CMD. Two images to build/test/version; loses "one artifact" and the whole point.

Consequences: container-image Lambda has no SnapStart (irrelevant — SnapStart is deliberately
disabled today) and cold starts are governed by image pull (mitigated by Lambda's image cache
and our ~250 MB size). The bespoke S3-deps-at-cold-start mechanism is **not needed** on this
path and is eventually retired with the zip path.

### ADR-2: The port contract is `$PORT` with 8080 fallback — ACCEPTED (proposed)

`serve.py` binds `int(env PORT, default 8080)`. Cloud Run and Heroku inject `PORT`; Lambda/LWA
and Docker use the 8080 default (LWA's own default port is 8080 — no config needed). TLS mode
(`FAST_API__TLS__*`, EXISTS) keeps priority when enabled.

### ADR-3: CloudFormation AND Terraform — different consumers, both first-class — ACCEPTED (proposed, amended 08/11)

The repo has zero IaC today. Two formats, because they serve disjoint consumers:

- **CloudFormation** (`deploy/aws/`) — for the AWS Marketplace listing (Marketplace delivery
  is CFN-native — P-398 specifies "AMI + CloudFormation one-click"), for **Launch Stack
  buttons** (ADR-11), and for zero-tooling AWS customers. Plain YAML, `cfn-lint` gated.
- **Terraform** (`deploy/terraform/`) — for everything CFN cannot reach: it is the only IaC
  that spans **AWS + GCP + Heroku + Netlify with one tool**, it is what enterprise platform
  teams demand ("we don't run CFN — give us a module"), and it becomes the engine for our own
  non-AWS CI deploy jobs (replacing bespoke `gcloud`/`heroku` CLI sequences in Phase D).

**Drift rule:** for the two AWS targets the CFN template is **authoritative** and the
Terraform module mirrors it (a documented, deliberate duplication — the shared pytest smoke
suite is the equivalence check, since both must produce a stack that passes it). For non-AWS
targets Terraform is the only implementation — nothing to drift from. CDK stays rejected
(build step, language runtime, serves no consumer the other two don't).

### ADR-10: Terraform layout — root modules per target, git-sourced — ACCEPTED (proposed)

```
deploy/terraform/
  modules/
    aws-lambda/       # mirrors lambda.cfn.yml   (image fn, Function URL, buckets, optional CF+DNS)
    aws-ec2/          # mirrors ec2.cfn.yml      (instance, compose user-data, EBS, SSM token, DNS)
    gcp-cloud-run/    # google_cloud_run_v2_service + secrets + optional domain mapping
    heroku/           # heroku_app + container release + config vars
    netlify-static/   # netlify_site + deploy of the built static vault tree
  examples/           # one tfvars-driven example per module
```

Modules are consumed by git source (`source = "github.com/the-cyber-boardroom/SGraph-AI__App__Send//deploy/terraform/modules/aws-lambda"`).
Publishing to the public Terraform Registry requires one-module-per-repo naming
(`terraform-aws-sgsend`, …) — registered as a follow-on, not a blocker. State is the
consumer's problem (document local + S3 backend examples); our CI uses an S3 backend in the
deploy account. `terraform fmt -check` + `tflint` + `terraform validate` gated in CI beside
`cfn-lint`.

### ADR-11: One-click install delivery — hosted templates + provider-native buttons — ACCEPTED (proposed)

"One click" is a *distribution* concern with a per-provider native mechanism; the website's
job is to host the buttons and the 5-minute path around them:

| Provider | Mechanism | Repo artifact it needs |
|---|---|---|
| AWS Lambda / EC2 | **CloudFormation Launch Stack URL** — `…console.aws.amazon.com/cloudformation/home?region={r}#/stacks/create/review?templateURL={s3-url}&stackName=sg-send&param_MemorySize=1024…` (params prefillable) | templates published to a **public, versioned S3 bucket** (`…/templates/{version}/lambda.cfn.yml` + `latest/`) by the Phase C pipeline |
| GCP | **Cloud Run Button** (`deploy.cloud.run?git_repo=…&dir=sgraph_ai_app_send__docker`) — builds from the repo's Dockerfile in the customer's GCP project | none beyond the Dockerfile (EXISTS); optional `app.json` for env-var prompts |
| Heroku | **Heroku Button** (`heroku.com/deploy?template={repo-url}`) | `app.json` (stack `container`) + `heroku.yml` pointing at the Dockerfile, at repo root |
| Netlify | **Deploy to Netlify button** (`app.netlify.com/start/deploy?repository=…`) | `netlify.toml` whose build runs `build-vault-static.sh` |
| Docker | no button exists — a copy-paste one-liner IS the one-click | none (EXISTS) |

Security note: the hosted CFN templates are public-read by necessity; they contain **no
secrets by construction** (ADR-6 — tokens are generated at boot or passed as NoEcho
parameters). The template bucket is versioned and the pages pin `latest/` while docs link
immutable versions.

### ADR-4: Deploy tooling — `aws cloudformation deploy` in CI, not boto3-in-tests — ACCEPTED (proposed)

The "all AWS calls through osbot-aws" rule governs **application code**. Pipeline-side stack
deployment uses the AWS CLI's idempotent `cloudformation deploy` (create-or-update semantics,
changeset-based). A thin pytest smoke file per target validates the *deployed* stack (health,
auth, CORS) — tests verify, CFN deploys. This keeps the CFN path usable by customers who will
never run our pytest harness.

### ADR-5: EC2 TLS via caddy sidecar container — ACCEPTED (proposed), resolves P-398 open item 1

The EC2 CFN user-data runs **two containers via docker compose**: `sg-send-vault` (8080) and
`caddy` (80/443, auto-TLS via Let's Encrypt when `DomainName` is set, internal reverse-proxy
to 8080). This was the Architect's 06/23 recommendation (sidecar over ALB for single-instance);
this spec adopts it. When no domain is given, caddy serves a self-signed cert (browser warning,
still a secure context → Web Crypto works). The container's *native* TLS mode remains available
for users bringing their own certs.

### ADR-6: EC2 first-boot secrets — ACCEPTED (proposed), resolves P-398 open item 2

User-data generates `SGRAPH_SEND__ACCESS_TOKEN=$(openssl rand -hex 32)` on first boot and
stores it in **SSM Parameter Store** (SecureString, path `/sg-send/{stack}/access-token`) —
readable by the instance role and by the account owner, never baked into AMI or template.
CFN Outputs point at the SSM parameter name, not the value.

### ADR-7: EC2 data volume — ACCEPTED (proposed), resolves P-398 open item 3

Separate EBS data volume mounted at `/var/lib/sg-send` → container `/data`, with
`DeletionPolicy: Snapshot` + `UpdateReplacePolicy: Snapshot`. Stack deletion snapshots the
vaults instead of destroying them.

### ADR-8: Storage per target — ACCEPTED (proposed)

| Target | Default storage | Rationale |
|---|---|---|
| Lambda (CFN) | `s3` (buckets by existing convention, created by the stack) | stateless runtime |
| EC2 (CFN) | `disk` on the EBS volume; `s3` selectable via parameter → swaps the IAM policy (P-398's least-privilege-role-per-mode) | appliance semantics |
| Cloud Run | `s3` cross-cloud (AWS creds via Secret Manager) — Phase D1; a `Storage_FS__GCS` backend is the clean end-state (Phase D-future, well-shaped by Memory-FS) | no durable disk |
| Heroku | `s3` only (ephemeral filesystem — dyno restarts wipe disk) | platform constraint |
| Netlify | n/a — static host; vault UI in `SGSend.staticMode` (EXISTS) reads a static mirror; API calls go to an external endpoint if configured | no server runtime |

### ADR-9: Netlify is a UI target, not an API target — ACCEPTED (honest constraint)

Netlify has no container runtime; its functions model cannot host this FastAPI app. The
architecturally honest Netlify deployment is: **the static vault tree** (built by the existing
`scripts/build-vault-static.sh`) in one of two modes — (i) *static-mode read-only vault host*
(`window.SG_STATIC=true`, per `library/guides/vault-html/HOSTING-ON-STATIC-STORAGE.md`, EXISTS),
or (ii) *UI-on-Netlify, API-elsewhere* (`SG_ENDPOINT` pointing at a Lambda/Cloud Run deployment;
CORS is already permissive). Anyone asking for "the API on Netlify" gets redirected to Cloud Run
or Heroku.

## 3. Configuration Contract (all targets, one table)

The image's env contract (EXISTS today, unchanged) is the portable surface. CFN parameters,
Cloud Run flags, and Heroku config vars are all projections of this table:

| Env var | Lambda CFN | EC2 CFN | Cloud Run | Heroku |
|---|---|---|---|---|
| `SEND__STORAGE_MODE` | `s3` (fixed) | param `StorageMode` | `s3` | `s3` |
| `SEND__S3_BUCKET` | stack-created bucket | stack-created / convention | secret-fed | config var |
| `SEND__DISK_PATH` | — | `/data` (EBS) | — | — |
| `SGRAPH_SEND__ACCESS_TOKEN` | param (optional) | SSM first-boot (ADR-6) | secret | config var |
| `PORT` | — (LWA:8080) | — (compose:8080) | injected | injected |
| `FAST_API__TLS__*` | — (TLS at edge) | — (caddy sidecar) | — (platform TLS) | — (platform TLS) |

DNS/memory and friends are **stack parameters**, not image config: `MemorySize`, `Timeout`
(Lambda); `InstanceType`, `VolumeSize`, `AllowedCidr` (EC2); `DomainName`, `HostedZoneId`,
`CertificateArn` (both — see §4 caveat).

## 4. Known Constraints Called Out Now

1. **CloudFront certificates must live in us-east-1.** The Lambda template therefore takes
   `CertificateArn` as a *parameter* (pre-created) rather than minting one, OR skips CloudFront
   and Route53-ALIASes the bare Function URL domain (no custom domain on Function URLs without
   CloudFront — so custom DNS on Lambda ⇒ CloudFront ⇒ us-east-1 cert). EC2 has no such
   constraint (caddy gets its own certs).
2. **Admin Lambda.** Phase B templates deploy the **User** surface (the container = user API +
   vault UI). Token-validation against an Admin Lambda is optional by design (the container's
   `SGRAPH_SEND__ACCESS_TOKEN` mode, EXISTS). An Admin-included template is a later increment —
   tracked, not blocking.
3. **Heroku arch:** amd64 only — the multi-arch manifest already covers it.
4. **Cold-start regression risk (Lambda container vs zip):** measured, not assumed — the dev
   deployment runs both paths side by side and the smoke suite records init timings before any
   cutover decision.
5. **GCP/Heroku/Netlify credentials** are new CI secrets (Workload Identity Federation for GCP —
   no SA keys; `HEROKU_API_KEY`; `NETLIFY_AUTH_TOKEN` + site id). None exist in CI today.

## 5. What This Spec Deliberately Does NOT Do

- No Fargate/ECS task definition (image is ready for it; add when a consumer exists).
- No AMI baking (that is P-398/Marketplace scope; the EC2 CFN template is its direct precursor —
  the AMI is "this user-data, pre-executed").
- No change to the incumbent zip-Lambda pipeline until the container path earns the cutover.
- No `Storage_FS__GCS` implementation in Phase D1 (validated as follow-on work).
