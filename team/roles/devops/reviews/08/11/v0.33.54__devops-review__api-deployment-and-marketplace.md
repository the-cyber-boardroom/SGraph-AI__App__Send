## (a) How Deployment Currently Works — EXISTS, code-verified

### The shape of it

Two Lambda functions (User + Admin) × three stages (dev / main-qa / prod) = **6 functions**, all in **eu-west-2**, named `sgraph-ai-app-send--{user|admin}--{stage}`, each behind a **public Lambda Function URL** (no API Gateway), fronted by CloudFront for the custom domains (plus the deployed CloudFront Function that lets immutable `obj-cas-imm-*` vault objects bypass Lambda entirely and serve straight from S3). Deployment is **"deployment-as-pytest"**: the CI pipeline literally runs a pytest file whose test methods perform the deployment steps in order.

### Pipeline topology (`.github/workflows/`)

| Trigger | Workflow | Target | Version bump | Publishes |
|---|---|---|---|---|
| push to `dev` | `ci-pipeline__dev.yml` | `dev` stage | minor | — |
| push to `main` | `ci-pipeline__main.yml` | `main` stage | major | PyPI + Docker Hub |
| manual dispatch | `ci-pipeline__prod.yml` | `prod` stage | none | — |

All three call the shared `ci-pipeline.yml`, which runs: **unit tests → increment tag (CI owns the version file) → check AWS credentials → deploy Admin Lambda + deploy User Lambda (parallel) → optionally PyPI / Docker Hub**.

The UI static assets deploy separately (`deploy-ui-vault.yml`, `deploy-ui-user.yml`, …) to S3 under branch-prefixed paths (`websites/sgraph-vault/{dev,main,prod}/`) with CloudFront invalidation.

### The deploy action itself

`.github/actions/aws__deploy__lambda/action.yml` is tiny: install deps, then

```
pytest -rs ./tests/deploy/{User|Admin}__Lambda/deploy_aws/test_Deploy__{type}__Service__to__{target}.py
```

The test class (`test_Deploy__User__Service__base.py`) executes, in order:

1. **`test_2__upload_dependencies`** — legacy per-package zips to S3 (kept until combined zip fully validated)
2. **`test_2b__upload_combined_dependencies`** — `Lambda__Dependencies__Builder` pip-installs the whole dependency list targeting `manylinux2014_x86_64` / `cp313`, strips runtime-provided packages (boto3 etc.), zips once, uploads to `{account_id}--osbot-lambdas--{region}/lambdas-dependencies-combined/{name}-{hash12}.zip`. **Content-addressed by package-list hash → idempotent** (skip if exists).
3. **`test_4_create__lambda_function`** — `Deploy__Serverless__Fast_API` (osbot-fast-api-serverless) packages **app code only** (no site-packages), sets env vars (admin base URL + API key, `SEND__STORAGE_MODE=s3`, explicit bucket names), creates/updates the function and its **public Function URL**.
4. **`test_5__update_lambda_runtime__to_3_13`** — forces Python 3.13 runtime.
5. **`test_5b__disable_snapstart`** — SnapStart explicitly disabled (stale-socket timeouts).
6. **`test_6/7__invoke`** — smoke: direct invoke + `GET /api/info/health` over the Function URL.

### Cold-start dependency loading

`lambda_handler__user.py` detects Lambda (`AWS_REGION`), then `Lambda__Dependencies__Loader` downloads the **one combined zip** from S3 → extracts to `/tmp` → `sys.path.insert`. Warm containers reuse `/tmp`. One STS call, one S3 GET, one unzip — this replaced the per-package pattern (6 STS + 6 downloads).

### Storage and naming conventions

`Send__Config` auto-detects the backend: explicit `SEND__STORAGE_MODE` → AWS credentials present → `SEND__DISK_PATH` → memory. Buckets derive by convention:

```
{account_id}--sgraph-send-transfers--{region}     (main data)
{account_id}--sgraph-send-public--{region}        (public vaults)
{account_id}--osbot-lambdas--{region}             (dependency zips)
```

This convention is the quiet hero of the whole design: **nothing about storage is account- or region-specific in code**.

### The Docker container — EXISTS, published

`sgraph_ai_app_send__docker/Dockerfile` builds `diniscruz/sg-send-vault` (Docker Hub, multi-arch amd64+arm64 via per-platform digest builds + manifest assembly, smoke-tested in CI on every `main` publish). It is a genuinely self-contained appliance: user API + vault UI same-origin, disk storage at `/data` (memory/S3 switchable), optional token auth (`SGRAPH_SEND__ACCESS_TOKEN`), optional **native TLS** (`FAST_API__TLS__*` contract, fail-loud on missing certs). ~250 MB, `python:3.12-slim`, uvicorn, single process.

### Observations / gaps (current state)

| # | Observation | Severity |
|---|---|---|
| **A-0** | **The Admin Lambda only deploys to `dev` via CI.** `ci-pipeline.yml` line 134 skips the admin deploy job when `target_deploy` is `main` or `prod`. Main/prod admin updates are therefore manual/out-of-band — a new-account bootstrap must not inherit this asymmetry silently. | High |
| **A-1** | **The edge layer is hand-built.** CloudFront distributions, ACM certs, Route 53 records, UI S3 buckets, and the CI IAM user exist only as ~20 GitHub secrets pointing at console-created resources. There is no IaC in the repo — no Terraform, CDK, SAM, or CloudFormation anywhere (confirmed by the 04/18 handoff doc: "IaC: None — all Python-driven"). New account/region = re-clicking all of it. | High (for the goals of this review) |
| **A-2** | `ci-pipeline__prod.yml` passes `git_branch: 'dev'` — prod deploys the head of `dev` at dispatch time, not a tagged release ref. Works, but a prod deploy is not pinned to an immutable version. | Medium |
| **A-3** | Long-lived AWS access keys in GitHub secrets. GitHub OIDC → assume-role would remove them. | Medium |
| **A-4** | Dependencies zip is x86_64-only (`manylinux2014_x86_64`). Fine today (functions are x86_64), but blocks a Graviton/arm64 Lambda switch, and contradicts the CLAUDE.md stack table ("Python 3.12 / arm64") — the runtime is actually **Python 3.13 / x86_64**. Doc drift. | Low |
| **A-5** | The S3-deps-at-cold-start pattern means the Lambda's code identity is split across two artifacts (code zip + deps zip in S3). Clever and fast, but it is a bespoke mechanism a container-image Lambda would eliminate (see b). | Info |
| **A-6** | Deploy tests keep the legacy per-package upload alongside the combined zip — double upload work on every deploy until the legacy path is retired. | Low |
| **A-7** | **The "7 deployment targets" figure is aspirational, not deployed.** CLAUDE.md, `reality/index.md` quick-stats, the website, and investor materials all count *designed* targets. The honest table is `reality/infra/index.md`: **4 working targets** (Lambda, Docker Hub container, local container, sgit CLI); GCP and Fargate are PROPOSED, EC2/ECR were **built and then removed in v0.27.45** (moved to the separate SG/Compute project), and AMI has never existed. This review's recommendations are how the number becomes honest. | Medium (accuracy) |

## (b) One Docker Image for Lambda + GCP + Docker (local/EC2) — mostly PROPOSED

The container already covers **Docker local, EC2, Fargate/ECS, and (accidentally, almost) GCP Cloud Run**. The one target it cannot serve today is **Lambda** — the Lambda path uses the zip+S3-deps mechanism instead.

**Prior art to be aware of:** the 04/18 container plan (`v0.19.8__devops-plan__container-deployment.md`) proposed ECR push + a Packer AMI; neither shipped, and the ECR CI job plus the `sg-send-ec2` CLI that *did* exist were **removed in v0.27.45** (EC2 provisioning moved to the separate SG/Compute project). So the container-hardening work below is a restart with better foundations (the image now exists and is multi-arch), not a first attempt. EC2 *provisioning* remains SG/Compute territory; what belongs here is making the image itself runnable everywhere.

The unification move:

### B-1. Add the AWS Lambda Web Adapter (LWA) — PROPOSED, one line

```dockerfile
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:0.9.1 /lambda-adapter /opt/extensions/lambda-adapter
ENV AWS_LWA_PORT=8080
```

LWA is an official AWS Lambda extension that translates Function-URL/ALB events into plain HTTP against the container's port. With it, **the exact same image** runs:

| Target | How | Code change |
|---|---|---|
| **Lambda** (container image) | push to ECR, create function from image, Function URL in front | none — LWA translates events |
| **GCP Cloud Run** | `gcloud run deploy --image …` | honor `$PORT` (see B-2) |
| **Docker local / EC2 / Fargate** | as today | none |

The extension is inert outside Lambda — it does not affect the other targets. This removes the split-artifact problem (A-5): deps are baked into the image, cold-start behaviour is deterministic, image limit is 10 GB, and the deploy step becomes `docker push` + `update-function-code --image-uri`. The Mangum/zip path can remain as the incumbent until the container path is validated (same coexistence pattern the team used for the combined-deps zip).

### B-2. Container hardening for portability + marketplace readiness — PROPOSED

1. **Honor `$PORT`** in `serve.py` (`int(os.environ.get('PORT', 8080))`) — Cloud Run injects it; today it happens to default to 8080 so the image works, but honoring it is the contract.
2. **Non-root `USER`** — currently runs as root; AWS Marketplace container scans and most enterprise policies flag this.
3. **`HEALTHCHECK`** instruction pointing at `/api/info/health` (endpoint already exists) — ECS/EKS/Marketplace benefit.
4. **Multi-stage build** — build the vault static tree in a builder stage; final stage keeps only runtime. Trims image and drops build-only surface.
5. **OCI labels + SBOM** (`docker buildx --sbom=true`) — provenance metadata that Marketplace listing review and enterprise buyers expect.
6. **Pin the base image by digest**; refresh via automation (CVE hygiene — Marketplace rescans listings continuously).
7. **Publish to ECR Public** alongside Docker Hub — Marketplace container products must be served from Marketplace-managed ECR anyway, and AWS-side pulls avoid Docker Hub rate limits.

### B-3. GCP storage caveat — flagged honestly

`Storage_FS` has memory / disk / S3 backends. On Cloud Run the durable options today are: (i) point S3 mode at real AWS S3 cross-cloud (works, adds latency + egress), or (ii) GCS's S3-interoperability XML API with HMAC keys (works with S3 clients in most cases — needs a validation spike), or (iii) **PROPOSED**: a `Storage_FS__GCS` backend — the Memory-FS abstraction makes this a contained, well-shaped task. Disk mode on Cloud Run is ephemeral (in-memory filesystem) — demo only.

## (c) Deployment Automation for New AWS Accounts / Regions — PROPOSED

### What already works

Because buckets, Lambda names, and dependency zips all derive from `{account_id}` + `{region}` + stage, the **compute plane is already account-portable**: run the two deploy pytest files with credentials for any account and you get working Function URLs. That is genuinely rare and worth protecting.

### What's missing — the bootstrap and the edge

| # | Automation | What it does | Effort |
|---|---|---|---|
| **C-1** | **`Deploy__Full_Stack` bootstrap** (same deploy-as-pytest pattern, or a `sg-send-deploy` console script) | One entrypoint that: creates the three buckets, deploys Admin then User Lambda (wiring the admin URL env var automatically), creates Function URLs, runs the smoke suite, prints endpoints. ~90% of the code exists in `Deploy__Service`; this is sequencing + the admin→user URL handoff. | Small |
| **C-2** | **Edge-layer IaC** (CloudFormation or CDK, checked into the repo) | CloudFront distribution (+ the `imm-object-rewrite.js` CF function), ACM cert (DNS-validated), Route 53 records, UI S3 buckets + the `websites/…` prefix convention, origin wiring to the Function URLs. Parameterised by `DomainName` + stage. This is the entire A-1 gap as one template. | Medium |
| **C-3** | **GitHub OIDC role** created by the bootstrap (trust policy for the repo), replacing the four long-lived AWS secrets. GH Environments (dev/main/prod) instead of the flat secret pile; document the minimal required set. | Small |
| **C-4** | **Region/account matrix** — a `region` input on the base pipeline; secrets scoped per GH Environment. Multi-region = same pipeline, N environment entries. No code change needed in the deploy classes (convention handles it). | Small |
| **C-5** | **Post-deploy smoke suite** — extend the current invoke+health check to the documented smoke set (health, auth, CORS, no-plaintext). Exists partially in `tests/deploy`. | Small |

With C-1 + C-2, "new AWS account" becomes: create account → deploy edge template → run bootstrap → add GH environment. Target: **under one hour, no console**. The container-image Lambda from (b) simplifies C-1 further (no deps zip step at all).

## (d) AWS Marketplace Options — PROPOSED (facts verified Aug 2026)

### This work is already on the books: P-398

The marketplace question is not greenfield. **P-398 "SG/Vault AWS Marketplace standalone"** exists in `reality/infra/proposed/index.md`, sourced from the human brief of 21 June (`briefs/06/21/aws-marketplace-deployment/v0.33.31__dev-brief__…ami-cloudformation.md`) and assessed by the Architect on 23 June (`architect/reviews/06/23/v0.33.31__architect-review__briefs-21-june-2026.md`). Its shape: setup-mode boot, storage-mode selection with a **least-privilege IAM role per storage mode** (Marketplace policy prohibits credentials baked into an AMI), two-layer authorization, **AMI + CloudFormation one-click deploy**, free/BYOL/metered pricing. The Architect confirmed most components map to existing code (`Enum__Storage__Mode`, the token auth pattern) and left **three open pre-launch items**: TLS without Caddy (recommendation: nginx/caddy sidecar in the AMI rather than an ALB), admin-auth bootstrap (first-boot random token, never baked in), and EBS `DeletionPolicy: Snapshot`. The website already ships a `/pricing/aws-marketplace/` page whose CTA is "register your interest" — the listing itself does not exist.

This review's recommendations below are therefore sequenced to **land P-398**, not to propose a parallel plan.

### The product-type landscape

AWS Marketplace supports **SaaS, AMI, container, ML model, AI-agent, data, and professional-services** products. Two facts shape the strategy:

1. **There is no "Lambda function" product type in AWS Marketplace.** You cannot list a Lambda per se.
2. The serverless distribution channel is the **AWS Serverless Application Repository (SAR)** — publish a SAM template publicly, customers deploy it *into their own account* in one click. SAR is free and has **no billing integration** — it is distribution, not monetization. (Still active as of Aug 2026.)

### The four realistic plays, in recommended order

| # | Listing | Fit for SG/Send | Notes |
|---|---|---|---|
| **D-1** | **Container product (free)** | Immediate — `sg-send-vault` already exists, is multi-arch, smoke-tested | Images move to Marketplace-managed ECR; must pass vulnerability scan (→ B-2 non-root, digest-pinned base). Delivery: ECS/EKS/Fargate launch instructions. Note: Marketplace discontinued EKS Helm "Quick Launch" on 1 Mar 2026 — use plain container/Helm delivery. Free listing = distribution + credibility, zero billing plumbing. |
| **D-2** | **AMI product — "SG/Send Vault Appliance"** | Natural — the EC2 scenario is already documented in the container README | Build with **EC2 Image Builder**: Amazon Linux 2023 + docker + the container + caddy (auto-TLS) + systemd unit, cloud-init for token/domain config. Marketplace AMI requirements: no default passwords, no hardcoded credentials, SSH key-only login, must pass AMI self-service scanning. Pricing: start free/BYOL, add hourly/annual later. **AMI + CloudFormation delivery** lets the listing ship a template that launches instance + S3 bucket + IAM role together. |
| **D-3** | **SAR publication** of the Lambda form | The closest thing to "Lambda on the marketplace" | SAM template: both functions (container image or zip), Function URLs, buckets, IAM. Public "Launch Stack"-style deployment into the customer's account. Free by design — pairs with D-1/D-2 rather than replacing them. |
| **D-4** | **SaaS listing** (send.sgraph.ai itself) | Later — different business motion | Sell subscriptions to the hosted service with AWS billing/entitlement APIs. Note: from 1 Jun 2026 new SaaS products must support Concurrent Agreements. Only worth it when there is a paid tier to meter. |

**Seller mechanics** (once, account-level): register the AWS account as a Marketplace seller, tax/banking via Hyperwallet, then per-product listing review. Non-trivial but well-trodden; the technical prerequisites are exactly the B-2 hardening list.

### The honest "Lambda on Marketplace" answer

For a *commercial* Lambda-shaped product the Marketplace answer is: **list the container product, and make Lambda one of its documented launch modes** (via the LWA image from B-1 — the same image is the Lambda). For *free* distribution of the Lambda form, SAR + a public CloudFormation/SAM template is the right vehicle. Trying to force a paid pure-Lambda listing has no supported product type.

## (e) Using Marketplace Deployments Ourselves — the Vault-Sovereignty Play — PROPOSED

This is where (b)–(d) compound into something strategically interesting. The Architect's 28 July review already frames the deployment topology as three billing/sovereignty shapes — **SHAPE A** (serverless shared endpoint — today's send.sgraph.ai), **SHAPE B** (dedicated EC2 instance — a *new* provisioning primitive that does not exist yet), **SHAPE C** (AMI in the customer's account). Part (e) is the observation that SHAPE C's artifact and our own expansion tooling should be the **same artifact**.

### The core insight

An SG/Send deployment **is** the vault service — the vaults are just data under `Storage_FS`, and every piece of naming derives from account + region. So the marketplace artifacts (AMI, container, SAR/CFN template) are not merely a sales channel — **they are our own deployment automation, productised**:

1. **Customer-owned data plane.** A customer subscribes (or clicks Launch Stack) and gets SG/Send running in *their* AWS account, in *their* region. Zero-knowledge means we never held their keys anyway — now we don't even hold their ciphertext. "Your vaults, your account, our code" is a sovereignty story none of the SaaS-only competitors can tell, and it drops our compliance surface to ~zero for those customers.
2. **We dogfood the same artifacts.** New region for us = the same CFN template + pipeline environment entry (C-4). If the marketplace artifact can't stand up a region cleanly, our own expansion can't either — one tested path instead of two.
3. **The sgit CLI already supports it.** `sgit clone <key> --endpoint https://their-instance --token …` works today against any deployment (container README documents it). A customer-deployed instance is a first-class vault remote from day one.
4. **Federation via the append API.** Vault-append write is account-less by design (append_token is the only gate). Instances in different accounts/regions can therefore interoperate: org A's vault accepts appends from org B's clients with no shared AWS trust, no cross-account IAM. Marketplace deployment becomes **the onboarding path for a federated vault network** — each org runs its own node, nodes communicate through the gate-controlled append lanes.

### Caveats to engineer for

- **No phone-home.** Marketplace products must run without calling vendor infrastructure. The container already satisfies this (air-gapped mode is documented). Keep it true.
- **Update cadence.** Every release means republishing AMI/container versions — automate in the pipeline (D-1/D-2 publish jobs next to the existing Docker Hub job).
- **Admin Lambda.** The appliance form currently ships the user surface only; a customer-owned deployment that needs token management needs the Admin Lambda in the CFN/SAM template (D-3) or the token env-var mode the container already supports.
- **Support commitments.** Marketplace listings carry support expectations — even free ones need a support contact and a docs path.

## Recommended Sequence

1. **B-1 + B-2** — LWA line + container hardening (non-root, `$PORT`, HEALTHCHECK, labels). Small diffs, unlocks everything downstream, no behaviour change for existing targets.
2. **Validate container-image Lambda** in dev alongside the zip path (same coexistence pattern as the combined-deps rollout).
3. **C-1 + C-2** — bootstrap entrypoint + edge-layer CFN template. This is the highest-leverage item for "deploy anywhere in under an hour" regardless of whether Marketplace ever happens.
4. **C-3/C-4** — OIDC + environment matrix (quality-of-life, de-risks secrets).
5. **D-1** — free container listing (cheapest Marketplace entry, forces the hygiene work to completion).
6. **D-2 + D-3** — AMI appliance + SAR template.
7. **D-4 / federation (e)** — when the business motion calls for it.
