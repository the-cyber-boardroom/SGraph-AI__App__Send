# Code Review — Opening and Sharing a Vault with the Read-Only Key

**Version:** v0.33.44 | **Date:** 2026-07-24 | **Role:** Dev (code review)
**Scope:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/` (deployed to dev.vault.sgraph.ai), plus the User-Lambda transfers/vault-pointer endpoints it depends on.
**Question under review:** *"How can I open and share a vault using the read-only key?"* — i.e. share vault **content** with a wider audience without granting the ability to make changes.

Reference pattern (external): `sgraph.ai/en-gb/library/reference/vault-read-keys.md` — the website renders live vault content from a **raw 32-byte read key** (base64url) via `<sg-vault-content vault-id read-key content-object-id>`. That component lives in the website repo, not here; this review maps what this repo already has that is equivalent, and where the wiring stops short.

---

## 1. Executive Summary

**Almost everything needed already exists and is tested — but the last mile of wiring is broken or missing in three places.**

1. A complete **read-only token (ro-token) lifecycle** is implemented: mint, store, resolve, open, display, revoke. A vault owner can create `ro-word-word-NNNN` tokens today and a recipient can open the vault **live and read-only** at `https://dev.vault.sgraph.ai/#ro-<token>`.
2. **The share link the Token Manager copies is broken** (F1): it copies `/en-gb/vault/#ro-<token>`, but that page's routing strips and discards the hash before anything reads it. Recipients get an empty entry form (or their own last vault). The working URL shape is `/#ro-<token>`.
3. **The raw read-key open path (format 4) is stubbed out with an incorrect assumption** (F2): `VaultLoader.openReadOnly` throws *"requires further investigation for ref discovery"* — but ref discovery is fully derivable from the read key. This ~20-line gap is exactly the capability the sgraph.ai website pattern uses, and the Settings tab already displays the raw Read Key it would consume.
4. The **Token Manager is a developer harness page**, not a user-facing share flow — Settings links to it, but there is no one-click "create read-only link" in the vault UI proper.

Bottom line for the question: **the mechanism exists; the front door doesn't.** One 1-line bug fix makes today's flow usable; one small feature (format 4 open + a Share button in Settings) makes it first-class.

## 2. What Exists Today (Code-Verified Map)

### 2.1 Credential format catalogue — two read-only formats are already defined

`_common/js/vault-loader/vault-loader-format.js` recognises five formats; two are read-only:

| # | Format | Access | Open path today |
|---|--------|--------|-----------------|
| 1 | `word-word-NNNN` (simple token) | rw | `SGVault.open` ✅ |
| 2 | `passphrase:hex12_id` | rw | `SGVault.open` ✅ |
| 3 | `passphrase:alnum_id` | rw | `SGVault.open` ✅ |
| 4 | `<vault_id> <64-hex read_key>` | **ro** | ❌ **throws "not yet supported"** (`vault-loader.js:107-114`) |
| 5 | `ro-word-word-NNNN` (ro-token) | **ro** | `openROToken → SGVault.openReadOnly` ✅ |

### 2.2 The ro-token lifecycle (format 5) — fully implemented

| Stage | Where | Detail |
|-------|-------|--------|
| **Mint** | `en-gb/vault/token/vault-token-manager.js` `createTransferToken()` (line 120) | Encrypts `{vault_id, read_key (b64), ref_file_id}` with the token as PBKDF2 passphrase (100k iters, salt `sgraph-ro-token-v1`), uploads it as a transfer at a **deterministic transfer-id** = `SHA-256('ro-token-transfer-v1:' + token)[:12]`. Supports expiry (`expires_at`) and max uses (`max_downloads`; 0 = unlimited — verified in `Transfer__Service.py:59`). Server accepts client-chosen `transfer_id` (`Routes__Transfers.py:95`). Minting requires the owner's access token; a random `delete_auth` preimage is kept locally as the revocation key. |
| **Record-keeping** | same file, `saveTokenList()` | Token list stored owner-encrypted at `.vault/owner/readonly-tokens.json`, committed + pushed. |
| **Resolve + open** | `_common/js/vault-loader/vault-loader.js` `openROToken()` (line 122); `app-shell.js` `_resolveROToken()` (line 1003) | Recipient derives the same transfer-id from the bare token, `GET /api/transfers/download/{id}` (public — no access token needed for reads), decrypts with the token, then `SGVault.openReadOnly(sgSend, vaultId, readKeyB64, refFileId)` (`sg-vault.js:98`) — `_passphrase = null`, `_writeKey = null`, read key imported **non-extractable, decrypt-only**. Opens from the **named ref** → recipients always see the latest pushed state (live view, not a snapshot). |
| **Display** | `vault-shell.js:238`, `vault-header.js:124` | True RO mode detected (`!writable && _passphrase === null`) → `👁 Read-only` blue pill; Settings hides the share/preview owner sections (`vault-settings.js:156`); `app-shell` sets `sg.app.writable=false` so apps fail closed. |
| **Revoke** | `vault-token-manager.js` `revokeTransferToken()` | `DELETE /api/transfers/delete/{id}` with the delete_auth preimage. Stops **new** resolutions (see F7b for the limits). |
| **Tests** | `tests/unit/vault_ui/loader/test__ro_token_resolution.js`, `test__ro_record_derivation.js` | Round-trip: deterministic-id drift guard + encrypt→wire→decrypt with the exact salts/iterations both sides use. |

### 2.3 Entry points — which URLs work for a recipient

| URL | Behaviour | Works? |
|-----|-----------|--------|
| `dev.vault.sgraph.ai/#ro-<token>` | Root is the only hash inbox (`vault-loader-routing.js` `runRoot`): saves key to localStorage → `/en-gb/app` → app-shell detects the `ro-` prefix (`app-shell.js:347`) → RO open (falls back to `/en-gb/vault/` when no `app.json`). | ✅ **canonical share URL** |
| `dev.vault.sgraph.ai/en-gb/browse/#ro-<token>` | Redirects to `/#ro-<token>` (`en-gb/browse/index.html:27`). | ✅ |
| Landing page input (`/en-gb/`) | No format validation — stores the string and navigates to the vault shell, which opens via `VaultLoader.open` → format 5 dispatch. | ✅ |
| `dev.vault.sgraph.ai/en-gb/vault/#ro-<token>` | `runVault()` **strips and discards the hash** (`vault-loader-routing.js:96-99`) before anything reads it. | ❌ **this is the URL the Token Manager copies** |

### 2.4 The raw read key — displayed but not openable here

- **Settings → "Read Key"** (`vault-settings.js:57-63, 140-151`) exports the AES read key as 64-char hex with a Copy button, hint: *"Pass to `sgit clone` for read-only access without the vault passphrase."* (CLI-side support is **not** confirmed in `reality/cli/index.md` — see F6.)
- Format 4 (`<vault_id> <64-hex read_key>`) is detected everywhere (loader, peek page) but `VaultLoader.openReadOnly` **throws** (see F2 — the blocker cited in the comment does not actually exist).
- In RO sessions the Read Key row degrades gracefully to "(unavailable)" because `openReadOnly` imports the key non-extractable.

### 2.5 Adjacent read-only mechanisms already shipped (same triple, different wrappers)

All of these wrap the same `{vault_id, read_key, ref_file_id}` capability triple that `openReadOnly` consumes — the codebase has converged on this as *the* read-only credential; only the delivery envelope differs:

| Mechanism | Envelope | Live or snapshot | Where |
|-----------|----------|------------------|-------|
| **ro-token** (this review) | Encrypted transfer at token-derived id | **Live** (follows named ref) | vault UI |
| **Sub-vault ro-links** | `.vault/owner/ro-links.json` + `*.link.json` (read_key tier) — parent readers open children via `SGVault.openReadOnly` (`composite-data-source.js:254`) | Live | vault UI, portable across devices |
| **`sgit share` share token** | Read-only **snapshot** transfer, viewed at `send.sgraph.ai/en-gb/browse/#<share-token>` | Snapshot at share time | sgit CLI (⚠️ known 503 failure on vaults > ~4 MB from egress-controlled environments) |
| **Public vault previews** | `public-preview-crypto.js` derives a *separate* decrypt-only key from a public slug (salt `sgraph-public-preview-v1`) — deliberately **cannot** reach the real vault; preview payload only, then prompts for a real key | Preview + key prompt | vault UI `/en-gb/preview`, `/en-gb/app/<id>` (Mode A/B wiring still pending per reality doc) |
| **Static-host mode** | `SGSend.staticMode` — same vault app HTML against a plain static host; writes reject `EREADONLY` | Live (against static copy) | `sg-send.js` |
| **Website `<sg-vault-content>`** | Raw base64url read key in an HTML attribute | Live per-object | **external** — sgraph.ai website repo, not this one |

**Answer to "how do I share content-only today":** mint an ro-token (live view, revocable, expirable) *or* `sgit share` (frozen snapshot). The ro-token is the right fit for "a number of vaults shared with a wider audience" — provided the link bug below is fixed.

## 3. Findings

### F1 — BUG (high): Token Manager copies a share URL that discards the token

`vault-token-manager.js:408` and `:434`:

```js
const shareUrl = `${origin}/en-gb/vault/#ro-${t.token}`;
```

Every non-root page calls `VaultLoaderRouting.runVault()` from a synchronous `<head>` script (`index.html:32`), which strips the hash **without saving it** — by design ("root is the only hash inbox"). A recipient clicking the copied link lands on the vault shell with no credential: empty entry form, or silently their *own* last-opened vault. The one flow built for exactly this use case ships a dead link.

**Fix (one line, two occurrences):** `${origin}/#ro-${t.token}`.
**Test to add:** a routing-decision test asserting the share URL shape matches the hash-inbox contract (`test__routing_decisions.js` already covers `runRoot`; add a guard that nothing user-facing emits `/en-gb/vault/#`).

### F2 — GAP (high value, small effort): format 4 open is stubbed on a false premise

`vault-loader.js:103-114` throws:

> "Read-only vault open (format 4) is not yet supported. … Placeholder: format 4 requires further investigation for ref discovery."

And `vault-token-manager.js:162-163` claims RO recipients need `ref_file_id` in the payload because *"they can't derive it without the HMAC key, which only the owner has."*

**Both statements are wrong.** In `sg-vault-crypto.js:92-99` the HMAC key is imported **from the read-key bits themselves**:

```js
const hmacKey = await crypto.subtle.importKey('raw', readBits, { name: 'HMAC', ... })
refFileId = 'ref-pid-muw-' + HMAC(hmacKey, `sg-vault-v1:file-id:ref:${vaultId}`)[:12]
```

So any holder of `(vault_id, read_key)` can derive the named-ref file id. Implementation of format 4 is ~20 lines:

```js
async function openReadOnly(vaultId, readKeyHex, opts) {
    var readBits = hexToBytes(readKeyHex);
    var hmacKey  = await crypto.subtle.importKey('raw', readBits, { name:'HMAC', hash:'SHA-256' }, false, ['sign']);
    var refHex   = await SGVaultCrypto._deriveFileId(hmacKey, 'sg-vault-v1:file-id:ref:' + vaultId);
    var vault    = await SGVault.openReadOnly(_makeSGSend(opts), vaultId, bytesToBase64(readBits), 'ref-pid-muw-' + refHex);
    ...
}
```

This closes the loop with what Settings already displays (copy `vault_id` + Read Key hex → paste into any open box → read-only session, **no server-side artefact needed at all**), and is the in-repo equivalent of the sgraph.ai website read-key pattern. It also gives ro-token minting a fallback (a read-key credential works even if the creds transfer expires).

Note the derivation nuance: this works for standard vault keys and simple-token vaults alike (both derive ref ids via `HMAC(read_key_bits, …)` — `sg-vault-crypto.js:166-174`). The misleading comments should be corrected in the same change.

### F3 — STALE CODE: the Token Harness's own RO resolution path cannot succeed

`en-gb/vault/token/vault-credentials.js` `resolveCredential()` (line 85-112) resolves ro-tokens via `GET /api/transfers/check-token/{token}` and expects `vault_id`+`read_key` or a `ciphertext` field. The server's `check_token` (`Routes__Transfers.py:219-231`) returns only `{valid, status, remaining}` — never those fields — so this path always throws *"RO token resolved but server returned no vault_id or ciphertext payload."* It predates the deterministic-transfer-id design that `vault-loader.js` and `app-shell.js` use. Dead code on the harness page's loader; should be rewritten on top of `SGVaultCrypto.deriveRoTokenTransferId` + `/api/transfers/download/{id}` or deleted.

### F4 — DUPLICATION: three copies of the RO payload crypto

The PBKDF2(100k, `sgraph-ro-token-v1`) + AES-GCM(iv‖ct) decrypt exists in `vault-loader.js:163-178`, `app-shell.js:1011-1024`, and `vault-credentials.js:178-193` (plus the encrypt side in `vault-token-manager.js:199-216`). The drift-guard test only pins the derivation constants. Consolidate into `SGVaultCrypto` (e.g. `sealRoPayload`/`openRoPayload`) so the tested code is the shipped code — the same principle the repo already applies to `sg-embed-helpers.js`.

### F5 — UX GAP: no first-class "share read-only" flow

- The only mint UI is the **developer Token Test Harness** (`/en-gb/vault/token/` — reality doc classifies it as a dev page). Settings' "Read-only sharing" section (owner-mode only) opens it in a new tab; the handoff works via the shared `sg-vault-key` localStorage entry, i.e. same-browser only.
- Settings itself surfaces **no share URL** and no token list; the Vault URL + Vault Key rows share *write* capability, with only a hint-text warning distinguishing them. For an owner whose intent is "share content, not control", the safe artefact (ro link) is two pages away and the dangerous one (full key URL) has a Copy button front and centre.
- Recommended: lift `createTransferToken`/`saveTokenList`/`revokeTransferToken` out of the harness page into `_common/js/lib/` and give Settings a "Create read-only link" row that outputs `${origin}/#ro-<token>` directly (plus the existing expiry/max-uses options). The harness stays as the power-user surface.

### F6 — DOC DRIFT

- `vault-settings.js:62` claims the Read Key can be passed to `sgit clone` for read-only access. `reality/cli/index.md` documents no read-only clone mode — **unverified claim in shipped UI text**; either confirm against `SGit-AI/SGit-AI__CLI` and note it in the reality doc, or soften the hint.
- The ro-token feature as a whole is scattered across the reality doc (a Token-Harness bullet in `ui/index.md`, an RO-resolution row in the 05/25-26 table) — there is no single "read-only access" entry answering this review's question. Worth a dedicated subsection in `reality/vault/index.md`.
- `library/guides/vault-html/` has no guide for read-only sharing (SUB-VAULTS-AND-LINKS.md covers the ro-links variant only).

### F7 — SECURITY NOTES (for the "wider audience" use case)

a. **Token entropy:** `generateFriendlyToken()` = 87 adjectives × 116 nouns × 10⁴ ≈ **1.0 × 10⁸** combinations. The token is both the locator (transfer-id derivation) and the decryption passphrase (PBKDF2 100k). Online enumeration means guessing tokens against `GET /api/transfers/download/{derived-id}` — ~10⁸ space is thin for a determined attacker against a high-value vault, especially as a hit yields the ciphertext *and* the passphrase is the guess itself. Mitigations already available: expiry + max-uses. Consider widening the word lists or adding a second number group for owner-configurable "high entropy" tokens. (Same class of consideration as simple tokens; worth an explicit AppSec note.)
b. **Revocation is access-revocation, not crypto-revocation.** Deleting the creds transfer stops new resolutions, but anyone who already resolved holds `read_key` permanently; the vault cannot be re-keyed without re-encrypting. Inherent to the zero-knowledge design — must be stated in any user-facing share UI ("revoking stops new opens; people who already opened retain access to current content").
c. **`max_uses` counts resolutions, not people.** Each open (per device/session that re-resolves) consumes a download. Fine, but label it accurately in UI.
d. **Structure-key split is still inert** (`reality/vault/index.md`): everything — refs, commits, trees, full history — is encrypted with `read_key`. A read-key recipient therefore sees the entire commit history, not just current content. Acceptable for content-sharing, but owners should know a "read-only" share includes history (the SGit View diff screen works in any full-read-key session; RO-token sessions get the same read key, so it works there too).
e. **Recipient-side persistence:** the ro credential is stored in recipient localStorage (`VaultLoaderStorage.setCurrentKey('ro-…')`, recent-vaults list) — same treatment as full keys; consistent, no new exposure.
f. Reads are unauthenticated by design (`Routes__Vault__Pointer` gates only writes/batch) — an RO recipient needs no access token; nothing to hand out beyond the link. ✅

### F8 — MINOR

- `vault-token-manager.js` sends `expires_at: new Date(expiresAt).getTime()` and `max_downloads: 0` for "unlimited" — both semantics confirmed server-side (`Transfer__Service.py:59-61`). ✅ No issue; recorded here because the schema names differ (`max_uses` in UI, `max_downloads` on the wire).
- Peek page (`/en-gb/vault/peek`) correctly labels format 4 as "Read-only credential · read only" in its inspector — it will display a credential the shell then refuses to open (F2 makes this consistent).

## 5. How to Do It Today (works on dev.vault.sgraph.ai right now)

1. Open your vault with the full key; set your access key (Settings) so you can push.
2. Settings → **Read-only sharing** → *Manage read-only tokens* → **+ Create read-only token** (optionally set expiry / max uses).
3. **Do not use the Copy-link button** (F1). Hand out: `https://dev.vault.sgraph.ai/#ro-<token>`.
4. Recipient opens that URL — vault renders live, `👁 Read-only`, no access token needed, writes impossible (no write key exists client-side; server rejects unauthenticated writes anyway).
5. Alternative (snapshot semantics): `sgit share` → `https://send.sgraph.ai/en-gb/browse/#<share-token>`.

Per repo rule 33: vault keys, ro-tokens and share tokens are secrets — share out-of-band, never commit them.
