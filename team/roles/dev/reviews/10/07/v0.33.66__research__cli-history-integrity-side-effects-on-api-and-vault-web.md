# Research — side effects of the CLI team's history-integrity changes on the vault API and the vault web code

**date** 7 October 2026
**role** Dev (with an AppSec lens)
**input** CLI team brief *"history-integrity changes planned in sgit-ai, and three questions"* (7 Oct): verify commit signatures, a client-side ref-monotonicity check, 128-bit object ids as an opt-in per-vault "format 2", and a format gate (`format`, `min_client`, `features`) in the branch index.
**scope** The two areas Dinis flagged: (1) the API that vaults are committed through; (2) the vault web code. The CLI side was read from `SGit-AI/sgit-ai__cli` @ `bec996d` (read-only), because three of the side effects only become visible once both halves are read together.
**method** Server: the real user-Lambda routes were exercised in memory with 24- and 44-character object names. Web: code read, plus the web UI's own id function run on the CLI's test vector. CLI: schema and workflow code read. Each claim below is marked **[executed]** or **[code-read]**.
**short reply to the CLI team:** [`team/comms/briefs/10/07/…reply-to-cli-team…md`](../../../../../comms/briefs/10/07/v0.33.66__reply-to-cli-team__history-integrity-q1-q2-q3.md)

## 0 · The answers, first

| Area | Verdict |
|---|---|
| **Which API is this?** | Not `vault.sgraph.ai`. That host (and `dev.vault.sgraph.ai`) serves only the **web UI** (static, S3 + CloudFront). **Both clients commit to `https://dev.send.sgraph.ai/api/vault/*`**, the SG/Send user Lambda. It is the hard-coded default in the CLI (`Vault__API.DEFAULT_BASE_URL`) and in every endpoint fallback in the web UI, and the vault-UI deploy injects no per-environment endpoint. So production `vault.sgraph.ai` writes to the **dev** Lambda. [code-read] |
| **Q1 — server accepts 44-char object ids?** | **Yes, on every surface, with no server change.** [executed] The one real limit is `list`, which is unpaginated: it hits Lambda's 6 MB response cap at about **165k objects on format 1 and about 108k on format 2**. |
| **Q2 — web UI handles both id lengths?** | **It can read them today** (ids are opaque strings on the read path). **It cannot write them, and its branch-index writer would undo the format gate.** Four changes are needed; one of them fixes a latent bug that exists today. |
| **Q3 — web UI signs its commits?** | **Not today. It is feasible, but there are three blockers** — one on the CLI side (the signing input is not a canonical byte string), two on ours (no per-writer identity in the browser; the index writer). Size: L. The CLI's `warn` default is the right call until then. |

**On your two worries:** the **API has no side effects** — the server never parses ids, so the changes are transparent to it. The **vault web code has material side effects**, and the largest is not about id length at all.

## 1 · Which API vaults are committed through

| Client | Default API | Evidence |
|---|---|---|
| sgit CLI | `https://dev.send.sgraph.ai` | `sgit_ai/network/api/Vault__API.py:18` `DEFAULT_BASE_URL`; `CLI__Vault.py:632,645` |
| Vault web UI (`vault.sgraph.ai`, `dev.vault.sgraph.ai`) | `https://dev.send.sgraph.ai` | `vault-entry.js` `_getSGSend()` fallback; `app-shell.js` `_sendEndpoint()` and four more fallbacks — all `'https://dev.send.sgraph.ai'` |
| Per-environment override at deploy? | **none** | `deploy-ui-vault.yml` injects a build version and rewrites `_common/` paths, nothing else; no `data-endpoint` or `SG_ENDPOINT` in any page |

**Consequences for this work:**

- Any server-side change for format 2 — none is needed — or any server-side guard has to be deployed to the **`dev.send` Lambda**, because that is where vaults actually live.
- `send.sgraph.ai` (the prod Lambda) holds a **separate** store. A vault created there is invisible to clients on the default. Not a bug introduced by this brief, but the naming ("dev" is the de facto production vault store) should be a deliberate decision rather than an accident.

## 2 · The API (Q1) — verified per surface

Run against the real routes, in memory, with `obj-cas-imm-1abfd21f1430` (format 1, 24 chars) and `obj-cas-imm-1abfd21f14308c611fe591dc4d6de285` (format 2, 44 chars) under `bare/data/`. **[executed]**

| Surface | 24-char | 44-char | Notes |
|---|---|---|---|
| `PUT /api/vault/write/{vault_id}/{file_id}` | ✅ | ✅ | `file_id` is a plain `str` on `{file_id:path}`; no length or pattern check |
| `GET /api/vault/read/…` | ✅ | ✅ | `Cache-Control: public, max-age=31536000, immutable` still applies (it keys on the `-imm-` substring) |
| `GET /api/vault/read-base64/…` | ✅ | ✅ | |
| `GET /api/vault/list/{vault_id}?prefix=bare/data/` | ✅ | ✅ | both ids returned, byte-exact |
| `POST /api/vault/batch` — `read`, `write`, `write-if-match`, `delete` | ✅ | ✅ | all four `ok`; read-only batch needs no auth, as today |
| `DELETE /api/vault/delete/…` | ✅ | ✅ | |
| presigned `initiate` / `complete` / `cancel` schemas | ✅ | ✅ | `file_id: str`, kept verbatim (no `Safe_Str` rewriting) |
| presigned `read-url` route | ✅ | ✅ | route matches; the S3 call itself is S3-mode only, so it was **not executed** — but the key is built by the same `path__vault_payload()`, so its shape is identical [code-read] |
| S3 key length / charset | ✅ | ✅ | 121 bytes for a 44-char id (limit 1024); hex and `-` only |
| Test vector | — | — | `sha256(b'sgit test vector 0001')` = `1abfd21f…5479`, matching the brief |

**The server is id-agnostic by construction.** No server code parses `obj-cas-imm-` beyond the cache-header substring check. Zero-knowledge is unaffected.

### 2.1 The one real limit — `list` is unpaginated

`list` returns every key in one JSON response, and S3 listing itself does paginate internally (`ContinuationToken`), so correctness is fine. But Lambda caps a response at 6 MB:

| | Bytes per entry | List size @ 19,780 objects (today's largest) | 6 MB ceiling |
|---|---|---|---|
| format 1 | 38 | 0.75 MB | **≈ 165,500 objects** |
| format 2 | 58 | 1.15 MB (+396 KB, matching the brief's ~400 KB) | **≈ 108,500 objects** |

Format 2 brings the cliff **35% closer**. The largest vault today has 5.5× headroom, so this is not urgent. But past the cliff `list` fails, the CLI's clone sweep fails, and the vault becomes unclonable — and 100k+ objects also means 100+ S3 `ListObjectsV2` calls inside one Lambda invocation. **Recommendation:** add a continuation token to `list` before any vault approaches ~80k objects. This is independent of format 2.

### 2.2 A guard rail for our own backlog

The 26 Sep API review proposed validating vault `file_id` (S1, the disk-mode traversal fix). **That fix must not use an object-id regex.** It has to accept 24- *and* 44-character object names, plus the other path families (`bare/refs/ref-pid-*`, `bare/indexes/idx-pid-*`, `bare/keys/key-rnd-imm-*`). The right rule is a safe charset, no `..` segments, no leading `/`, and a bounded length. A `^obj-cas-imm-[0-9a-f]{12}$`-style rule would make S1 the thing that breaks format 2.

## 3 · The vault web code (Q2) — where the side effects are

### 3.1 🔴 The branch-index overwrite (fix first; a latent bug today)

`SGVaultRefManager.writeBranchIndex()` (`sg-vault-ref-manager.js:145`) writes a **fresh** object every time:

```js
const index = { schema: 'branch_index_v1', branches: [
    { branch_id: branchId, branch_type: 'named', head_ref_id: refFileId, name: 'current' }
]}
```

It does not read, merge or compare-and-swap. It is called on **`create()`, every `push()` and every `pushIfMatch()`** (`sg-vault.js:87`, `sg-vault--sync.js:94,110`), and through the generated kernel bundle it also runs in **child kernels**, so every write through a declared mount rewrites the *child* vault's index too. [code-read]

What the CLI keeps in that index (`Schema__Branch_Meta`): `branch_id`, `name`, `branch_type`, `head_ref_id`, **`public_key_id`**, `private_key_id`, `created_at`, `creator_branch`, `display_name` — one entry per clone branch. [code-read, CLI]

**Today:**

- CLI push uploads its local index when it registers a new clone branch (`Vault__Sync__Push.py` ~786–800). The remote index is therefore **last-writer-wins**: each CLI registration writes its own view, and **every web push resets it to one entry**.
- Existing CLI clones are **not** affected. `pull` never re-downloads the remote index (`Step__Pull__Load_Branch_Info` reads the local copy). Only `clone` reads it.
- The real loss today: a clone made after any web push never learns the other clone branches or their `public_key_id`s. That is silent, because nothing verifies signatures yet.

**Under the CLI's plan, this turns from silent to active:**

1. **The format gate is wiped by the next web push.** The gate lives in the branch index, and absent means format 1. Once an owner raises a vault to format 2, the first web push erases `format` / `min_client` / `features`. Every clone made afterwards sees format 1, writes 12-hex ids, and is never refused. Existing clones keep their local copy, so different clones disagree about the vault's format.
2. **Signature-key mapping is wiped.** The verifier maps a commit's branch to `public_key_id` through the index. After a web push, new clones cannot map any other branch's commits to a key. Under `warn` every commit becomes "unverifiable"; under `required` the vault becomes unusable.
3. **CLI index writes race web index writes.** Even after a merge fix, two writers updating the same index object need compare-and-swap.

**Fix (size S–M):** read-modify-write that preserves unknown top-level fields and all other branch entries, written with `write-if-match` (the server's batch already supports it), retrying on conflict. Keep the current single-branch write only for the **create** path, where no index exists yet. This must ship **before CLI 0.19**, or the format gate is unreliable from its first day.

### 3.2 🟠 Unconditional `push()` vs ref monotonicity

The shells call `push()`, which writes the named ref with no compare. Its own comment says it can re-point the ref *"even if another client published in between, silently dropping their commits"*. `pushIfMatch()` (compare-and-swap) exists, but only headless child kernels use it. [code-read]

Once the CLI checks that a new head descends from the last known one (0.20), every such web lost-update race will be reported as a **rollback**. The CLI will be right: those are real lost updates, happening today with no one noticing.

**Fix (size M):** move the shells to `pushIfMatch()` and give the user a reconcile path on `ECAS` (merge, then retry). The primitive is already built and tested; the work is the conflict UX. Ship **before CLI 0.20**, or the monotonicity check's first output will be a stream of web-caused alarms.

### 3.3 🟠 Random-IV trees vs the CLI's determinism (corrects the brief)

The brief says *"trees already use deterministic encryption (IV = HMAC-SHA256(key, plaintext)[:12]) so that the same folder content gives the same tree id in both clients."* **That is true of the CLI only.** The web UI encrypts trees with `SGSendCrypto.encrypt`, which takes a random IV (`sg-send-crypto.js:96–98`). [code-read]

Correctness is unaffected — ids are still content addresses over ciphertext. But three consequences follow:

- Identical folder content gets **different tree ids** depending on which client wrote it, so any CLI logic that reads "same tree id ⇒ no change" sees web-written trees as always changed.
- The CLI ships a migration, `tree-iv-determinism`. It is manual (`sgit migrate apply`), and `is_applied()` returns false whenever **any** random-IV tree exists. So after any web commit the vault reports "needs migration" **forever**.
- Running that migration **rewrites history** (trees, then commits and refs). Against the new monotonicity check that reads as a rollback, and rewritten commits no longer carry valid signatures.

**Fix (size M):** have the web UI encrypt trees with the CLI's deterministic IV — `IV = HMAC-SHA256(read_key, plaintext)[:12]`, as in `Vault__Crypto.encrypt_deterministic` — with a shared test vector. Independent of format 2, but it removes a standing conflict with the integrity plan.

### 3.4 🟡 The 12-hex id computation (the part the brief asked about)

**Where the web UI assumes an id length** — the brief's explicit question. [code-read]

| Location | What | Action |
|---|---|---|
| `sg-vault-object-store.js:223` | `computeObjectId`: `'obj-cas-imm-' + hex.slice(0, 12)` | **The one place ids are computed.** Make it format-aware (12 or 32). It already reproduces the format-1 vector: run on `b'sgit test vector 0001'` it returns **`obj-cas-imm-1abfd21f1430`** [executed]. Add both vectors as JS fixtures. |
| `sg-vault.js:163–172` | opening a vault reads the branch index to find the named ref | Extend it to read `format` / `min_client` / `features` and **refuse by name**, as the CLI will. |
| `sg-vault-commit.js:153` | `computeContentHash` → `sha256(plaintext)[:12]` | **Not an object id** (the tree entry's dedupe hash). The CLI uses the same 12 (`Schema__Cache_Value`). Leave it, and confirm the CLI is not widening it. |
| `vault-loader-format.js:36` | `RE_HEX_ID_PART = /^[a-f0-9]{12}$/` | **Not an object id** — the `vault_id` inside a pasted vault key. Unaffected. But see the naming note below. |
| `sg-vault-ref-manager.js:112,137` | `ref-pid-…{12}`, `branch-(named\|clone)-hex` | Refs and branch ids are unchanged per the brief. Unaffected. |
| `kernel-shell-bundle.js` | generated copy of all of the above | **Regenerate** after any change (the freshness test enforces it). Child kernels run this copy. |
| Read path (`load`, `batchLoad`, tree walks) | ids treated as opaque strings | **Already format-2-ready** — no validation, no fixed-width parsing. |
| Column widths or fixed-width display | none found | — |

**Naming collision:** the web UI already calls a *vault-key* format "Format 2" (`passphrase:12-hex-vault-id`, `vault-loader-format.js`). The CLI's "format 2" is an *object-id* format. Two different things share one name inside the same client — worth a distinct UI-facing label, such as "id format v2", before support tickets start.

**Size:** S (about a day with tests and the bundle regenerated). It is the easy part.

### 3.5 Other writers and readers

- **No other UI touches vault objects.** The user, open and share UIs have no `blob_id` / `tree_id` / `obj-cas-imm` handling. [code-read]
- **Old vault-UI releases stay reachable.** The deploy overlays onto `latest/` with no `--delete`, and release folders are kept for rollback. Old builds are gate-unaware, and the server cannot block them because the gate is encrypted. When the gate-aware build ships, delete or retire the older release folders deliberately.
- **Declared mounts / child kernels** use `pushIfMatch` (good for monotonicity) but still call `writeBranchIndex` (bad for the gate), and compute 12-hex ids. Both are fixed by the same changes, via the bundle.

## 4 · Web commit signing (Q3)

**What already exists:**

- ECDSA P-256 sign/verify via WebCrypto in `secure-channel-envelope.js` (`signBytes` / `verifyBytes`, used by the kernel SecureChannel).
- The CLI already emits **raw `r‖s` "for Web Crypto interop"** (`PKI__Crypto.py:64–75`), so the **signature encoding is compatible**. One classic interop trap is already avoided. [code-read]

**Three blockers:**

1. **The signing input is not a canonical byte string** (CLI side). The CLI signs `json.dumps(commit.json()).encode()` (`Vault__Commit.py`) — Python's `", "` / `": "` separators, Type_Safe's field order and defaults (`branch_id` → `''`; `author_key_id`, `author_signature` → `null`; `attestations` → `[]`). JavaScript's `JSON.stringify` produces different bytes. **Ask the CLI team** to specify the signing input exactly — for example RFC 8785 (JCS), or a fixed field list with compact separators — and to ship test vectors, as they did for ids.
2. **There is no per-writer identity in the browser** (our side). Every browser session holding the vault key commits on **one shared clone branch per vault** (`'web-ui'`, derived from the HMAC key + vault id + `'web-ui'`); child kernels use `viv:<parent>`. The CLI model is one key per branch in the index. A web signing key therefore needs:
   - **per-device clone branches** (e.g. `web-ui:<device id>`);
   - a **non-extractable P-256 key in IndexedDB** on the top-level `vault.sgraph.ai` origin (not inside the null-origin app frames, which have no IndexedDB);
   - its public key written to `bare/keys/key-rnd-imm-<id>` and **registered in the index — which depends on §3.1**.
3. **Schema alignment.** The web writes `schema: 'commit_v2'`, `branch_id: null` and no `author_key_id`. The CLI calls the same shape `commit_v1`, and its `Safe_Str__Branch_Id` pattern requires `branch-(named|clone)-hex`. Parsing is fine today (the CLI defaults the missing fields), but a `required` policy needs a rule for web commits, and the two schema names should be reconciled.

**The "server attests web commits" option:** technically the server could record which access token wrote which ref. But it would need a **server signing key** — a secret, against the zero-knowledge, no-secrets model — and access tokens are not personal identities (one token is often shared). **Not recommended.**

**Size:** L. The CLI's `warn` default is correct; `required` must wait for per-device web keys and a canonical signing input.

## 5 · Cross-checks for the CLI team (their side, found while reading both)

- **The format gate will not reach existing clones.** `pull` never re-reads the remote branch index (§3.1). An owner raising a vault to format 2 changes it only for **new** clones; existing clones keep their local index, keep writing 12-hex ids, and are never refused. If the gate is meant to apply to existing clones, pull has to refresh it.
- **Pre-gate CLIs crash rather than refuse.** `Safe_Str__Object_Id` is strict `^obj-cas-imm-[0-9a-f]{12}$` with max length 24. Any CLI up to 0.18 that meets a 32-hex id raises a validation error instead of "this vault needs sgit ≥ X". Worth a release note.
- **Migration × integrity.** Once signatures and monotonicity ship, `sgit migrate apply` (the tree-IV migration) rewrites history. It should either refuse on signed vaults or re-sign and record intent, as `push --force` will.

## 6 · Recommended order, matched to the CLI's ship order

| CLI ships | Web/server must have shipped first | Why |
|---|---|---|
| **0.19** — format gate, `author_key_id`, signatures in `warn` | **§3.1** index read-modify-write with compare-and-swap; **§3.4** read and honour the gate | Otherwise the first web push wipes the gate and the key mapping |
| **0.20** — ref monotonicity | **§3.2** shells on `pushIfMatch` plus conflict UX | Otherwise the check's first output is web-caused rollback alarms |
| **format 2** | **§3.4** format-aware `computeObjectId` with vectors; bundle regenerated; old release folders retired; `list` pagination if any vault nears ~80k objects | Correct ids; no gate-unaware writers left |
| **`required` signatures** | **§4** canonical signing input from the CLI; per-device web keys | Otherwise every web commit fails policy |
| any time | **§3.3** deterministic tree IV in the web UI | Removes the standing migrate-forever / history-rewrite conflict |

**Nothing on the server blocks any step.** The server work is optional hardening (`list` pagination) and a constraint on our own S1 fix (§2.2).
