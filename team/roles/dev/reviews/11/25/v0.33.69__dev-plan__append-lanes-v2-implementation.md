# Append Lanes v2 — Implementation Plan

**date** 25 November 2026 · **role** Dev (plan), from the Architect design · **status** PROPOSED — nothing here is built yet
**shared copy:** the same plan as a Claude Docs page (with the roadmap drawn), owned by Dinis. This file is the repo record.
**design:** [`team/roles/architect/reviews/11/25/v0.33.69__architect-review__append-lanes-v2-capacity-large-payloads-signed-lanes.md`](../../../../architect/reviews/11/25/v0.33.69__architect-review__append-lanes-v2-capacity-large-payloads-signed-lanes.md)

Append lanes v2 ships in four phases on the SG/Send API. Each phase is deployable on its own and opt-in per lane. Phase 1 fixes two live defects and changes nothing else. Phases 2–4 add retention and limits, blobs for attachments, and signed writes. The vault web client, the sgit CLI, the agents and DevOps each have follow-on work, listed per phase.

## At a glance

| | Phase 1 | Phase 2 | Phase 3 | Phase 4 | Webhook |
|---|---|---|---|---|---|
| **Theme** | Fixes + fast listing | Don't lose things | Blobs by hash | Signed lanes | optional, alongside Phases 2–4 |
| **Contents** | config cache TTL; `fetch` ceiling; `GET /limits`; cheap counting; paged listing; server-side copy | list processed; unmark; retention by tag; soft/hard limits; several read keys; lane stats | presigned S3 `PUT` with size and hash pinned, create-only; `blob-url` downloads; retention tags | random lane key; expiring grants; six server checks; replay-safe names; no identifiers at rest | bare signal to an owner-set URL |
| **Gate before it** | none: start now | decisions 1, 3, 4 | decision 2; S3 CORS | test vectors; `cryptography` in the Lambda | Phase 1's TTL |

Every phase ships API first. The vault web client, sgit CLI, agents and DevOps follow.

## Ground rules

Every item below follows these rules. A change that cannot is redesigned, not shipped.

1. **Zero-knowledge.** The server stores ciphertext and hashes, never keys or plaintext. All keys are generated on the client.
2. **No identifiers on the server** (Dinis, 25 Nov). No names, labels, aliases or identifying public keys at rest. Lane settings are keyed by `sha256(append_token)`, the anchor the server already stores.
3. **Opt-in per lane.** A lane with no new settings behaves exactly as today: 1,000 pending entries, inline payloads, token-only writes.
4. **No layout changes.** File ids keep the pattern `^\d{13}_[0-9a-f]{24}\.enc$`, and `pending/` and `processed/` keep their paths. New data goes in new sibling folders (`blobs/`).
5. **New auth errors are 401, not 403.** The CDN still rewrites every API 403 into an HTML 404 (open DevOps item), while a 401 reaches the client as JSON.
6. **House rules:** `Type_Safe` schemas, AWS calls through `osbot-aws`, storage through Memory-FS, and tests with no mocks (memory backend for units, LocalStack for the S3 paths). Every phase updates the reality doc and adds a changelog entry that classifies test impact.

All work lands on the user Lambda behind `https://dev.send.sgraph.ai`, the API both the CLI and the vault web client use.

## Phase 1 — fixes and cheap listing

Phase 1 is server-only. It fixes the two live defects and makes counting and listing cheap enough to raise limits later. Results, order and status codes stay identical, apart from the two fixes. Size: S–M, about 3 days with LocalStack tests.

## Phase 2 — don't lose things

Phase 2 turns `processed/` into the soft drop the agents asked for, and lets owners size each lane. The server already keeps processed entries until a purge; it just offers no way to see them, undo a mark or expire them. Size: M server (about 4 days), S client.

| # | Item | What changes | Access |
| --- | --- | --- | --- |
| 2.1 | **List processed entries** | `list` takes `folder: "pending" \| "processed"` (default `pending`); same paging and cursor | enum key |
| 2.2 | **Unmark** | new `POST /append/unmark/{vault_id}` with `{inbox, file_ids}` (up to 100) moves entries from `processed/` back to `pending/` by server-side copy. Ids the lane's hard limit cannot take come back in `refused` | enum key |
| 2.3 | **Retention** | lane setting `retention_days`: 7, 30, 90, 365 or none (none = kept until purged, today's behaviour). On S3, the copy into `processed/` sets an object tag (`sg-retention=30d`) and bucket lifecycle rules expire by tag, so no server job runs. Memory and disk run a bounded sweep on `list` and `mark_processed`. `purge` stays the explicit removal route | write key (configure) |
| 2.4 | **Soft and hard limits** | lane settings `soft_pending`, `hard_pending` and `max_pending_bytes`, plus `lane_defaults` for every lane. Appends are accepted up to the hard limit, and 507 starts there. Above the soft limit, stats raise `over_soft`. `configure` refuses values above the server ceilings (400). The count is cached per instance for 5 s and incremented on each accept, so concurrent instances can overshoot slightly: that is the burst | write key (configure) |
| 2.5 | **Several read keys** | config gains `enum_key_hashes` (up to 16); the legacy `enum_key_hash` is still honoured. Each keeper (feedback, site, maestro) gets its own key, removable on its own, effective within the 1.1 TTL | write key (configure) |
| 2.6 | **Lane stats** | new `POST /append/stats/{vault_id}`, optionally `{inbox}`, returns per lane: pending count and bytes, oldest and newest entry time, processed count (capped at 100k, with `processed_capped`), soft and hard limits, `over_soft` | enum key |

**Config shape** (all fields optional; lanes keyed by `sha256(append_token)`):

```json
{ "append_anchors": ["…"], "enum_key_hashes": ["…", "…"],
  "lane_defaults": { "soft_pending": 1000, "hard_pending": 1000 },
  "lanes": { "<sha256(token)>": { "soft_pending": 5000, "hard_pending": 5000,
                                   "max_pending_bytes": 1073741824, "retention_days": 30 } } }
```

**Proposed server ceilings** (constants, overridable from the environment). Token lanes: 5,000 entries and 1 GiB. Signed lanes (Phase 4): 50,000 entries and 20 GiB.

**Reader cursors stay on the client.** A keeper that needs its own position stores it in its own vault, which survives a new container. The server keeps no per-reader state. A keeper should mark an entry only after it has decoded; a failure stays pending.

## Phase 3 — blobs by hash

Entries stay small and inline. Attachments (PDFs, screenshots, images, archives up to the lane's limit) become **blobs**: ciphertext stored at `bare/append/<token>/blobs/<sha256>` and referenced by hash from inside the sealed entry. The bytes go straight to S3, never through Lambda. Size: M, about 4 days server with LocalStack tests, plus client work.

**Upload, in order** (blob first, so a reader never sees a reference to a missing blob):

1. The writer encrypts the attachment and computes the SHA-256 of the ciphertext.
2. `POST /append/blob-upload/{vault_id}` with `{append_token, size, sha256}`, plus the signature fields on a signed lane. The server checks the gate, that the lane has `blobs` on, `size ≤ max_blob_bytes`, and the lane's byte budget.
3. The server returns `{upload_url, headers, expires_in: 900}`: a presigned `PUT` with `Content-Length`, `x-amz-checksum-sha256`, `If-None-Match: *` and the retention tag signed into it.
4. The writer `PUT`s the ciphertext. S3 refuses a wrong size or hash. A **412** means that blob already exists: treat it as success.
5. The writer appends the small entry as today, with the blob's hash inside the sealed envelope.

**Read:**

1. The reader lists or fetches entries as today and opens the envelope.
2. `POST /append/blob-url/{vault_id}` with `{inbox, blob_ids}` (up to 100, enum key) returns a presigned `GET` per blob (5 minutes), plus `missing`.
3. The reader downloads, checks the hash and decrypts. A reader fetches only the blobs it needs.

**Lifecycle and limits.**
- Blobs carry the lane's retention tag from upload, and `purge` gains `folder: "blobs"` (write key).
- `mark_processed` never touches blobs: the server cannot see which entry references which.
- Lane settings: `blobs` (default off), `max_blob_bytes` (server ceiling proposed at 256 MiB), and the byte budget, which counts pending entries plus blobs.
- Memory and disk modes return 501 `presigned_not_available`, as vault presigned uploads already do.

**Nothing new leaks.** A blob's name is the hash of its own ciphertext. A 412 tells a writer only that this exact ciphertext is already there, which is meaningless without the ciphertext itself (every encryption uses a fresh IV).

**Outside the API:** S3 bucket CORS must allow `PUT` from the vault origins with those headers (DevOps). Null-origin vault apps cannot reach S3, so the top kernel performs the upload for them (vault web).

## Phase 4 — lane keys and grants

A signed lane accepts only writes from writers the owner has granted, and the server holds nothing that identifies them. The token stays the lane's address and can be public. Size: M server (about 4 days), M client, plus the CLI.

**Setup (owner, on the client).** The owner generates a random P-256 **lane key** for this lane only. The private half stays with the owner, sealed in their vault. `configure` sets `lanes[<sha256(token)>]` to `{mode: "signed", lane_key: <SPKI, base64>, revoked_grants: []}`.

**A grant (owner → writer).** The owner checks the writer (for example in pki.sgit.ai), then signs with the lane key:

```text
sg-append-grant/v1|<vault_id>|<sha256(token)>|<sha256 hex of writer SPKI DER>|<not_after_ms>|<nonce, 16 hex>
```

- `grant_sig` = ECDSA P-256 / SHA-256, base64 of raw `r‖s` (WebCrypto's format, the same as pki.sgit.ai and the CLI).
- `grant_id` = first 32 hex of `sha256(grant string)`.
- The writer key can be any P-256 key, including the writer's pki.sgit.ai signing key.

**A signed write.** `write`, `blob-upload` (and batch write, if built) add `grant`, `grant_sig`, `signer` (writer SPKI, base64), `ts` (ms) and `sig` over:

```text
sg-append/v1|<vault_id>|<sha256(token)>|<ts_ms>|<size>|<sha256 hex of ciphertext>|<grant_id>
```

**Server checks, in order.** Any failure returns 401 with a code.

1. The grant verifies under `lane_key`, and its vault and lane match the request (`grant_invalid`).
2. `now ≤ not_after` (`grant_expired`), and `grant_id` is not in `revoked_grants` (`grant_revoked`).
3. `sha256(signer)` equals the grant's writer hash (`signer_mismatch`).
4. `|ts − now| ≤ 300 s` (`ts_out_of_window`).
5. The ciphertext hash matches: computed for an inline entry, pinned in the presigned checksum for a blob (`hash_mismatch`).
6. `sig` verifies under `signer` (`sig_invalid`).

**Replays are free no-ops.** The entry's file id is `<ts_ms>_<first 24 hex of sha256(grant_id | signed string)>.enc`, which fits today's file-id pattern, and the write is create-only. A replay inside the window lands on the same name and changes nothing. Outside it, it fails check 4. The name comes from the signed *content*, not the signature, because ECDSA signatures are malleable. Honest retries are idempotent too.

**At rest, the server holds only** the lane's random public key and the revoked grant ids. The writer's key and grant pass through inside the request. For readers who want proof, the writer puts the grant, signer and signature inside the sealed entry, so they can verify without trusting the server.

**Revocation:** add the `grant_id` to `revoked_grants`, effective within the 1.1 TTL. Rotating the lane key revokes every grant at once.

**Implementation notes.**
- Declare `cryptography` explicitly: today it is in the venv only through `pyjwt`. A verification measured 63 µs.
- Ship fixed **test vectors** (lane key, writer key, grant, signed string, expected file id) as JSON fixtures for the CLI and the web client.
- Signed lanes unlock the high ceilings: 50,000 entries, 20 GiB, 256 MiB blobs.

## Webhook (optional track)

A lane can wake its reader with a bare signal on each accepted append, instead of the reader polling. It runs alongside the phases and needs only Phase 1's config TTL. Size: S–M.

**Contract.**
- The owner sets `webhook_url` on a lane (write key).
- After an append is stored, the server POSTs `{"v":1,"event":"sg-append"}`: no content, no ids, no counts. The URL itself tells the receiver which lane it is.
- The URL is the one plaintext value in the lane config, which is why the feature is opt-in.

**Guards** (each one has a test):

1. `https` only, no redirects followed, 1.5 s timeout.
2. The host must resolve only to public addresses. Loopback, private, link-local (`169.254.0.0/16`, the Lambda runtime API on `127.0.0.1:9001`) and their IPv6 forms are refused. The server connects to the address it checked, so DNS rebinding cannot swap it.
3. At most one signal per lane every 30 s per instance. Anyone holding a public token could otherwise make the server hammer the owner's URL.
4. A failed or slow delivery never fails the append.
5. Signals are unsigned, because the server holds no secret to sign with. Receivers must treat a signal as a hint to poll: a forged one costs a poll and nothing else.

**Delivery.** Inline, after the store, with the timeout above. If that latency matters, a second step moves delivery to an async self-invoke.

**Known limit: Claude cloud sessions.** A session's inbound webhook (`watch_url`) expects deliveries signed by Anthropic's artifact service, whose credential only that service can open. An unsigned POST from SG/Send is therefore likely refused. Plain receivers such as n8n work. **Test this once by hand before agents rely on it.** The test from the planning session was blocked by that session's permission settings.

## API changes

All paths are under `/api/vault/append/`. Five endpoints are new; the six existing ones keep their request shapes and gain only optional fields.

| Endpoint | Access | Phase | Change |
| --- | --- | --- | --- |
| `GET limits` | public | 1 | **new**: server limits and ceilings |
| `POST write/{vault_id}` | append token | 1, 2, 4 | 413 body `{error, limit, received}` (1); 507 at the lane's hard limit (2); grant and signature fields on signed lanes, 401 codes (4) |
| `POST list/{vault_id}` | enum key | 1, 2 | same results via cursor pushdown (1); optional `folder` (2) |
| `POST fetch/{vault_id}` | enum key | 1 | new `deferred` list for entries over the response ceiling |
| `POST mark-processed/{vault_id}` | enum key | 1, 2 | server-side copy (1); retention tag (2) |
| `POST unmark/{vault_id}` | enum key | 2 | **new**: processed → pending, `refused` when the lane is full |
| `POST stats/{vault_id}` | enum key | 2 | **new**: per-lane counts, bytes, times, `over_soft` |
| `POST blob-upload/{vault_id}` | append token (+ grant on signed lanes) | 3 | **new**: presigned `PUT` for one blob |
| `POST blob-url/{vault_id}` | enum key | 3 | **new**: presigned `GET`s for up to 100 blobs |
| `POST purge/{vault_id}` | write key + access token | 3 | `folder: "blobs"` |
| `POST configure/{vault_id}` | write key + access token | 2, 3, 4, W | `lane_defaults`, `lanes`, `enum_key_hashes` (2); `blobs`, `max_blob_bytes` (3); `mode`, `lane_key`, `revoked_grants` (4); `webhook_url` (W) |

## Tests and test impact

Today's suite has 85 append service tests and 48 route tests. Only two kinds of existing test should fail, and both are updated in the same PR. Any other failure is a regression.

**Should break (expected):**

| Test | Phase | Why |
| --- | --- | --- |
| `test_Fast_API__SGraph__App__Send__User` route list | 1, 2, 3 | `ROUTES_PATHS__VAULT_APPEND` gains the new endpoints |
| any test comparing a whole `fetch` result | 1 | the result gains `deferred: []` |

**Must not break:**
- gates, blindness (`test__append__blindness_no_file_id_returned`) and account-less writes;
- cursor paging, metadata-only listing and the incremental content ceiling;
- `mark_processed` idempotency and the 8 traversal negatives;
- the 100-id batch cap, the separate config file, and "`list_files` never returns append entries";
- the 413 and 507 route tests (they read the constants, so they follow any change of limit);
- `test_Storage_FS__S3` and the web loader suites for `sg-append`.

**New tests, per phase** (memory backend unless marked LocalStack; no mocks):
1. Phase 1: two service instances on one store for the TTL; the `fetch` ceiling and `deferred`; `/limits`; listing equivalence against today's implementation (many lanes, cursors and limits; same entries and order). LocalStack: early-stop counting, `StartAfter` paging, delimiter discovery, `CopyObject`.
2. Phase 2: processed listing; `unmark`, including `refused` at the hard limit; the hard-limit boundary (accept at hard − 1, 507 at hard); `configure` refusing values above the ceilings; several read keys, and a removed key refused after the TTL; stats figures. LocalStack: the retention tag set on copy. Memory: the retention sweep.
3. Phase 3: blob-upload validation (blobs off, size, budget); the presigned URL signs `content-length`, `x-amz-checksum-sha256` and `if-none-match`. LocalStack: a wrong size or hash is refused, a second `PUT` gets 412, `blob-url` downloads.
4. Phase 4: the shared test vectors; one failing test per check, each with its 401 code; a replay and a malleated signature (`s` → `n − s`) both land on the same file id; a revoked grant refused after the TTL; token-mode lanes ignore signature fields.
5. Webhook: refusal of loopback, private, link-local and IPv6-local targets and of redirects; coalescing; a failed delivery does not fail the append. Delivery is tested against a real local HTTP server through a test-only switch that allows loopback.

One LocalStack gap to check before Phase 3: support for `If-None-Match` and `x-amz-checksum-sha256` on presigned `PUT`s. If it is missing, those cases run against a dev bucket.

## Rollout, risks and rollback

**Merging to `dev` is a production change.** The vault web client at vault.sgraph.ai and the sgit CLI both talk to the `dev.send` Lambda, so a merge to `dev` reaches every lane in use.

**Rollout.**
1. One PR per phase, API first.
2. `/limits` also returns `features` (for example `["fetch-deferred", "unmark", "blobs", "signed-lanes"]`), so clients detect support at runtime instead of pinning an API version.
3. Phase 1 keeps the old listing code for one release behind `SGRAPH_SEND__APPEND_FAST_LISTING`, on by default, for an instant switch back.
4. After each deploy, smoke-test the deployed API: write, list, fetch, mark, plus that phase's new endpoints.

| Risk | Phase | Mitigation |
| --- | --- | --- |
| Faster listing returns different entries or order | 1 | equivalence tests; old path behind the switch for one release |
| The cached count overshoots the hard limit | 2 | bounded to about 5 s of appends per instance; exact check at each refresh; server ceilings |
| Public tokens used to fill storage | 2, 3 | low ceilings on token lanes; blobs off by default; byte budgets |
| A presigned URL leaks | 3 | 15-minute life, one object, exact size and hash, create-only |
| A signed-lane misconfiguration locks writers out | 4 | the owner can switch the lane back with `configure`; tooling warns before grants expire |
| Webhook used for SSRF or flooding | W | the five guards, each tested |
| An old client meets a lane using new features | 2–4 | owners opt a lane in after upgrading its readers and writers |

**Rollback.**
- **Phases 1–3 revert cleanly.** Old code ignores the new config fields, leaves `blobs/` folders alone (until a purge) and keeps working on the same layout. Retention tags on objects are harmless, and lifecycle rules can be removed.
- **Rolling back Phase 4 is a security regression.** Old code ignores `mode: signed`, so every signed lane becomes writable again by anyone holding its token. Before any Phase 4 rollback, rotate the tokens of signed lanes, or tell their owners first.
