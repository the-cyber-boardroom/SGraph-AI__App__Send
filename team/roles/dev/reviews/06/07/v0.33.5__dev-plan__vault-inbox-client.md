## Goal + scope

Implement the **client side** of the public-key-controlled vault inbox across:

1. **Vault Web UI (primary)** — a fourth main left-nav section "Inbox" with badge, polled on refresh, listing senders by accepted pubkey, opening into a per-sender message list, decrypting in-browser, with mark-processed / purge owner actions and an accepted-pubkey settings sub-panel.
2. **Vault App bridge (secondary)** — three new `sg.inbox.*` verbs (`list`, `fetch`, `markProcessed`) routed through the existing `app-shell.js` `__sgCmdType` switch, gated by a new `inbox.*` group in `app-permissions.js`, with paths normalised to `inbox://{sender_token}` so the existing `_match(grant, path)` machinery applies unchanged.
3. **sgit CLI hand-off (note only)** — out of scope for this plan; the recommendation is to extract `sg-inbox-derive.js`'s rules as the cross-tier source of truth and port the derivation logic to Python in `SGit-AI/SGit-AI__CLI`.

The server is **done**. Everything here is client-side: derivation, transport, view-model, components, bridge wiring, tests, debug pane, reality doc.

## A. Issues spotted (read this first)

Found while grounding the plan in the actual UI code. Severity is for *the design as written*; each has a resolution folded into a phase below.

| # | Issue | Severity | Resolution |
|---|---|---|---|

| **A2** | **`enum_key` and `write_key` aren't yet exposed where the inbox client needs them.** `sg-vault.js:27` holds `_writeKey` (hex string) and `sg-vault.js:187` exposes `get writable()` — but there is no `enum_key`. ## B. Shared infrastructure (build once, before Phase 1)

**Goal: Pure, Node-testable derivation + transport, mirroring the `app-permissions.js` / `viv-mounts-view.js` pattern.**

Three new modules in `_common/js/lib/sg-inbox/`. None touch the DOM, none reference `this` from a class instance, all attach their exports to `globalThis` so the existing jsdom-free Node test harness (`runInThisContext`) can load and assert against them.

### B1. `sg-inbox-derive.js` — pure derivation rules

```
globalThis.SGInboxDerive = {
  appendToken(pubkeyHex),         // SHA256(pubkey).hex(); validates 64 hex chars in/out
  appendAnchor(appendTokenHex),   // SHA256(append_token).hex() — server-side hash
  enumKey(readKeyRawBytes),       // SHA256("inbox-enum:" || readKey).hex()   — PROPOSED, see Q1
  enumKeyHash(enumKeyHex),        // SHA256(enum_key).hex()
  x25519Seed(readKeyRawBytes),    // HKDF over readKey with info="inbox-x25519-seed" — PROPOSED, see Q2
  isHexToken(s),                  // /^[0-9a-f]{16,128}$/.test(s)
  isInboxFileId(s),               // /^\d{13}_[0-9a-f]{24}\.enc$/.test(s)
};
```

Every derivation is **deterministic** (no randomness inside, all randomness coming from the seed bytes the caller already holds). This is what makes the same module portable to sgit Python (Open Question Q5).

### B2. `sg-inbox-crypto.js` — hex/base64/X25519 helpers

```
globalThis.SGInboxCrypto = {
  hexToBytes(hex), bytesToHex(bytes),
  b64encode(bytes), b64decode(b64),         // standard base64 (server uses no urlsafe)
  sha256Hex(stringOrBytes),                 // Web Crypto SHA-256
  generateKeypair(seedBytes),               // X25519 keypair from seed (deterministic)
  seal(plaintextBytes, recipientPubBytes),  // X25519 ECDH + AES-256-GCM → bytes
  open(ciphertextBytes, ownPrivBytes, senderPubBytes),
};
```

For X25519 + AES-256-GCM, reuse the **same primitives** the existing `sg-vault-crypto.js` and `sg-send-cli` use. **No new third-party library** — Web Crypto API only — to stay inside the IFD doctrine (zero framework deps).

### B3. `sg-inbox.js` — the public client (matches `sg-vault.js` shape)

```
class SGInbox {
  constructor(sgSend) { this._sgSend = sgSend; this._vault = null; ... }

  attach(vault) { this._vault = vault }  // pulls vaultId, writeKeyHex, derived enum_key

  // Owner-only (writable required, sends x-sgraph-vault-write-key header)
  async configure(acceptedPubkeysHex)             // POST /configure
  async purge({ folder='processed', sender, fileIds=null })  // POST /purge

  // Owner read/process (sends x-sgraph-vault-enum-key header)
  async list({ sender=null, afterFileId=null, limit=50, includeContent=false })
  async fetch({ sender, fileIds })
  async markProcessed({ sender, fileIds })

  // Sender side (no auth headers; for tests + future "Reply")
  async append({ appendToken, payloadB64 })       // POST /append
}
```

Constructor mirrors `SGVault` (`sg-vault.js:23`): no work in `new`, all state set by `attach(vault)`. Errors map to a single `SGInboxError` subclass (with `.code` = `'EREADONLY'|'EBADTOKEN'|'EFORBIDDEN'|'EPAYLOAD'|'ENOSPACE'|'ENETWORK'`).

**Load order** (add to `v0.2.3/index.html` after `sg-vault.js` and its companions, before `vault-shell.js`):
```html
<script src="_common/js/lib/sg-inbox/sg-inbox-derive.js"></script>
<script src="_common/js/lib/sg-inbox/sg-inbox-crypto.js"></script>
<script src="_common/js/lib/sg-inbox/sg-inbox.js"></script>
```

### B4. Error codes (single source)

| Code | When | HTTP | User-facing |
|---|---|---|---|
| `EBADTOKEN` | hex/file-id validation fails client-side or server returns 400 | 400 | "Inbox token format invalid" |
| `EFORBIDDEN` | enum_key / write_key / append_token hash mismatch | 403 | "Not authorised for this inbox" |
| `EPAYLOAD` | append payload > 5 MB | 413 | "Message too large (max 5 MB)" |
| `ENOSPACE` | > 1000 files per inbox | 507 | "Inbox full — purge processed first" |
| `EREADONLY` | `vault.writable` false on configure/purge | n/a | "Open the vault for writing to configure the inbox" |
| `ENETWORK` | fetch threw | n/a | "Network error contacting inbox" |

These mirror the `EPERM/EPROTECTED/ECONSENT` convention from app-permissions Phase 1.

## D. Each endpoint → client method (call signature, headers, errors)

| API | Client method | Headers | Body | Error mapping |
|---|---|---|---|---|
| `POST /configure/{vault_id}` | `SGInbox.configure(acceptedPubkeysHex: string[])` — derives `append_anchors[]` and `enum_key_hash` client-side. | `x-sgraph-vault-write-key: <writeKeyHex>` + `x-sgraph-access-token` (if vault has one) + `Content-Type: application/json` | `{ append_anchors: [sha256(append_token).hex()...], enum_key_hash: sha256(enum_key).hex() }` | 403 → `EFORBIDDEN`; 400 → `EBADTOKEN`. Pre-check: `if (!vault.writable) throw EREADONLY`. |
| `POST /append/{vault_id}` | `SGInbox.append({appendToken, payloadB64})` | `Content-Type: application/json` only | `{ append_token, payload }` | 400 → `EBADTOKEN`; 403 → `EFORBIDDEN`; 413 → `EPAYLOAD`; 507 → `ENOSPACE`. **No access token required.** |
| `POST /list/{vault_id}` | `SGInbox.list({sender, afterFileId, limit, includeContent})` | `x-sgraph-vault-enum-key: <enumKeyHex>` | `{ inbox: sender\|null, after_file_id, limit, include_content }` | 403 → `EFORBIDDEN`; 400 → `EBADTOKEN`; 413 → `EPAYLOAD` (>3 MB inline cap). Defaults: `limit=50`, `include_content=false`. |
| `POST /fetch/{vault_id}` | `SGInbox.fetch({sender, fileIds})` | `x-sgraph-vault-enum-key` | `{ inbox: sender, file_ids: [...] }` | Pre-check: `fileIds.length <= 100` else throw `EBADTOKEN` (A1 of API guide). 403 → `EFORBIDDEN`. |
| `POST /mark-processed/{vault_id}` | `SGInbox.markProcessed({sender, fileIds})` | `x-sgraph-vault-enum-key` | `{ inbox: sender, file_ids: [...] }` | Idempotent (A12). 400 → `EBADTOKEN` (batch >100); 403 → `EFORBIDDEN`. |
| `POST /purge/{vault_id}` | `SGInbox.purge({folder='processed', sender, fileIds=null})` | `x-sgraph-vault-write-key` + `x-sgraph-access-token` | `{ folder, inbox: sender, file_ids: fileIds }` | Pre-check: writable; 403 → `EFORBIDDEN`. |

Client-side validations before network (all derive from API guide token-format table):
- `appendToken` must match `^[0-9a-f]{16,128}$`.
- `fileId` must match `^\d{13}_[0-9a-f]{24}\.enc$`.
- `vault_id` must match the existing `VAULT_ID_PATTERN` (already used by `sg-vault.js`; reuse).
- `payload` must be base64 (decode-test) and ≤ 5 MB raw.
- `file_ids.length` ≤ 100 for fetch/mark/purge.

## E. Token / key plumbing (concrete call paths)

**Where the client gets its keys at runtime:**

| Key | Source | Lifecycle |
|---|---|---|
| `vault_id` | `window.sgraphVault.shell._vault._vaultId` (`sg-vault.js:30`) | Set at vault open. |
| `write_key` (hex) | `window.sgraphVault.shell._vault._writeKey` (`sg-vault.js:27`) — but `_writeKey` is **private**; access via `vault.writable` for presence check and a new public getter `vault.writeKeyHex` exposed for the inbox client. | Set after passphrase entry. |
| `enum_key` | Derived: `SGInboxDerive.enumKey(readKeyRaw)` where `readKeyRaw` = exported raw bytes of `vault._readKey` (the existing CryptoKey). **PROPOSED** — see Q1. | Derived once per session, held in `SGInbox` instance only, never persisted. |
| X25519 keypair | Derived: `SGInboxCrypto.generateKeypair(SGInboxDerive.x25519Seed(readKeyRaw))`. | Derived once per session in memory. |
| `append_token` for accepted senders | `SGInboxDerive.appendToken(pubkeyHex)` for each pubkey listed in the settings tab. | Computed on `configure()`. |

The host wires the inbox client up in `vault-shell.js` right after `_vault` is opened. Pseudocode:

```js
this._inbox = new SGInbox(this._vault._sgSend);
this._inbox.attach(this._vault);   // pulls vaultId, writeKeyHex, derives enum_key + keypair
window.sgraphVault.inbox = this._inbox;   // mirrors window.sgraphVault.shell._vault
```

The accepted-pubkey list itself is **owner-only state**. It lives in the vault tree under `.vault/inbox/accepted-pubkeys.json` so it is version-controlled, encrypted at rest, and protected by the `app-permissions.js` `.vault/` floor (so iframes can never read it). Reading/writing it goes through `vault._objectStore` — same path as `app.json` and `ro-links.json`.

## F. Phase plan (ordered)

### Phase 1 — Derivation + crypto + transport (no UI)

**Goal:** prove the protocol end-to-end against the real server without a single line of UI code.

**Files:** `sg-inbox-derive.js`, `sg-inbox-crypto.js`, `sg-inbox.js`; tests `test__sg_inbox_derive.js`, `test__sg_inbox_crypto.js`, `test__sg_inbox_client.js`.

**Wiring:** add the three `<script>` tags to `v0.2.3/index.html`. Nothing else changes.

**Manual smoke:** in the browser console:
```js
const inbox = new SGInbox(window.sgraphVault.shell._vault._sgSend);
inbox.attach(window.sgraphVault.shell._vault);
await inbox.configure(['<pubkey_hex>']);
await inbox.list({ includeContent: false });
```

**Tests pass criterion:** `node tests/unit/vault_ui/loader/test__sg_inbox_*.js` returns zero failures.

### Phase 2 — `<vault-inbox-view>` metadata-only listing

**Goal:** show "you have N messages from sender X, Y, Z" in the inbox view. No decryption yet.

**Files:** `vault-inbox-view.js`, `vault-inbox-view--store.js`; test `test__vault_inbox_view_store.js`.

**Wiring:** add the view to `vault-shell._render()`; route `_switchView('inbox')`; on view-enter, call `window.sgraphVault.inbox.list({includeContent:false})` and render via the store.

The store is **pure**: takes the raw `entries[]` shape from `/list`, returns `{ senders: [{ token, fingerprint, unread, lastReceived }], total }`. The component reads the store output and renders rows.

### Phase 3 — Nav + badge + refresh integration

**Goal:** the inbox is a first-class section, badge in the nav, polled on the same cadence as the ref check.

**Files modified:** `vault-nav.js` (4th item + badge), `vault-shell.js` (`_scheduleInboxCheck`, `_visibilityHandler` extension, refresh hook), `vault-header.js` ("Check inbox" menu entry), `vault-inbox-badge.js` (new).

### Phase 5 — `app-permissions.js` adds `inbox.*`; `app-shell.js` wires `sg.inbox.*`

**Goal:** apps inside vault iframes can read the inbox under explicit grants.

**Files modified:** `app-permissions.js`, `app-shell.js`, `kernel-app-handlers.js`.

#### F5.1 `app-permissions.js`

Extend `parsePermissions` to recognise `permissions.inbox = { list, read, markProcessed }`. Each value: `true | false | string[]` of `inbox://<sender_hex>` entries (matches the existing `_grant` shape; no new grammar). Extend `can()`:

```js
if (grp === 'inbox') {
    // Default-deny (unlike fs.read): no implicit grant.
    return _match(perm.inbox[act], path);
}
```

Path here is `inbox://<sender_token>` (or `inbox://*` for "any sender"). `_match` already handles exact and prefix matches; for the inbox we use **exact match only** — no prefix grants — and `inbox://*` becomes a special-cased `true`. This sidesteps A1 entirely.

#### F5.2 `app-shell.js`

Add `__sgCmdType === 'inbox'` branch (place right after the `vault` branch at line 2359). Three actions:

| action | gate | host call |
|---|---|---|
| `list` | `_can('inbox.list', 'inbox://' + (sender\|\|'*'))` | `self._inbox.list({sender, afterFileId, limit, includeContent})` |
| `fetch` | `_can('inbox.read', 'inbox://' + sender)` | `self._inbox.fetch({sender, fileIds})` |
| `markProcessed` | `_can('inbox.markProcessed', 'inbox://' + sender)` | `self._inbox.markProcessed({sender, fileIds})` |

`configure` / `purge` / `append` are **NOT exposed** to apps in v1. These are owner host actions. Document in the bridge spec.

In-iframe stub (added to `_buildVfsBridgeScript`):
```js

  fetch:          (opts) => __sgCmd('inbox', { action:'fetch',         ...opts }),
  markProcessed:  (opts) => __sgCmd('inbox', { action:'markProcessed', ...opts }),
};
```

## H. Vault-app bridge surface

| Verb | Args | Returns | Permission | Notes |
|---|---|---|---|---|
| `sg.inbox.list` | `{ sender?: hex, afterFileId?: string, limit?: number<=50, includeContent?: boolean }` | `{ entries: [...], truncated: boolean }` | `inbox.list` against `inbox://<sender\|*>` | Apps default to `includeContent: false`. |
| `sg.inbox.fetch` | `{ sender: hex, fileIds: string[<=100] }` | `{ files: [{file_id, size, content}], missing: [] }` | `inbox.read` against `inbox://<sender>` | Returns base64 ciphertext; the **app** does its own decrypt. |
| `sg.inbox.markProcessed` | `{ sender: hex, fileIds: string[<=100] }` | `{ moved: [], missing: [] }` | `inbox.markProcessed` against `inbox://<sender>` | Idempotent. |

**Not exposed:** `configure`, `purge`, `append`. These are owner-only host actions.

Example `app.json` permissions block:
```json
{
  "permissions": {
    "inbox": {
      "list":          ["inbox://abc123...def"],
      "read":          ["inbox://abc123...def"],
      "markProcessed": ["inbox://abc123...def"]
    }
  }
}
```

`inbox://*` means "any sender". Default-deny — absence of grant means the verb returns `EPERM`.

Decryption: in v1, the app receives ciphertext only. The host could expose a higher-level `sg.inbox.open()` that decrypts for the app, but that requires handing the X25519 private key into the bridge — flagged as a Phase 7 question, out of this plan.

## L. Risks + mitigations

| Risk | Mitigation |
|---|---|
| **Base64 overhead on large attachments.** A 5 MB payload becomes ~6.7 MB base64; pulling 50 messages at once would be ~335 MB on the wire. | Always poll metadata-only (`include_content: false`); fetch content only per-sender on open; cap `limit` at 50; rely on `truncated` for paging. |
| **CORS surprises dev → prod.** The CF managed `CORS-With-Preflight` policy strips custom headers (API guide gotcha #3). | Verify dev calls against `send.sgraph.ai` from local; if CF is in front of a future preview env, file with DevOps to drop the managed policy per the guide. |
| **Per-tab vault key isolation (`vault-loader-storage.js`).** `enum_key` derived per-tab: if a user opens two tabs, both derive the same value (deterministic) — no race. But if we ever switch to a random seed, two tabs would diverge. | Keep derivation deterministic (Q1). |
| **Double-mark race.** Two tabs both mark the same `file_id`. | Server's `mark-processed` is idempotent (API guide #5). The "duplicate" tab sees the file in `missing`. No client work needed; document in the inbox view as "this is fine". |
| **Vault must pre-exist before configure.** Hitting `configure` on an empty key returns 403 (API guide gotcha #1). | Pre-check `vault.writable` AND that the vault has at least one commit (via `vault._headCommitId !== null`) before calling `configure`; otherwise surface "Save the vault first" to the user. |
| **Token format gotcha (hex-only).** A developer adding `tok_` or `enum_` prefixes breaks (API guide gotcha #2). | `SGInboxDerive.isHexToken` guard before any network call; typed `EBADTOKEN` error. |
| **App reading inbox widens permission surface.** | Default-deny on `inbox.*`; no implicit grant; HUD privileges chip surfaces it; AppSec review (K) before C6 merges. |
| **PKI not in place yet.** No per-agent pubkey registry exists in the vault UI today — accepted pubkeys are entered manually in v1. | Settings tab accepts paste-in hex pubkeys; PROPOSED label on the reality doc; Q3 below confirms timing relative to PKI Mode 2. |

## M. Open questions for the human

| # | Question | Why it matters |
|---|---|---|
| **Q1** | **Is deriving `enum_key` deterministically from `readKey` acceptable?** Alternative: random per-vault, stored encrypted in `.vault/inbox/enum.json`. The deterministic approach has zero UX cost and no extra key-management surface; the random approach is more conservative cryptographically. | Affects every owner action. AppSec sign-off needed either way. |
| **Q2** | **Is deriving the X25519 keypair from `readKey` acceptable for v1?** Alternative: each agent supplies their own keypair. Deterministic is the only way v1 ships without PKI Mode 2 plumbing. | Without a decision, the senders can't seal messages to the recipient. |
| **Q3** | **Do we ship a manual "accepted pubkeys" UI before PKI Mode 2 lands?** Or wait? | Without it, configure is a code-only action. Manual UI in v1 is the lower-risk path. |
| **Q4** | **What's the default polling cadence?** Reuse the 30-second `_scheduleBehindCheck` debounce, or a different window? The brief says "checked regularly like a refresh" but doesn't quantify. | Affects server load and inbox responsiveness. |
| **Q5** | **Should the inbox section appear in RO-token-only sessions** (where `vault.writable === false`)? Reading the inbox needs `enum_key`, which we derive from `readKey` — so technically RO users **can** list. But should they? | Affects acceptance criterion #4 wording. Recommendation: yes, RO can list and decrypt (they have `readKey`), but cannot configure/purge. |
| **Q6** | **Should the host expose `sg.inbox.open()` (decrypted plaintext) in v1, or only `sg.inbox.fetch()` (ciphertext)?** | Decrypted version exposes private key indirectly; ciphertext means the app has to do its own X25519 — which it can't, because it doesn't have the private key. v1 ciphertext-only is a placeholder; needs a Phase 7 design. |
