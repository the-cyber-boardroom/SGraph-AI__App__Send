## 0. What changed in revision 3

| | r2 | r3 |
|---|---|---|
| Detection model | `SGInboxPoll` class with timers + `_scheduleInboxCheck` cadence | **`SGInboxChecker` — no timers.** Called from existing visibility/refresh hooks. |
| App receive surface | `sg.inbox.subscribe(cb)` | **`sg.on(name, cb)`** — general kernel→app event channel (works for any future feature). |
| Event gating | None | **`app.json.host_events`** allowlist — apps declare which kernel events they accept. Default-deny. |
| Bridge methods | 6 transport + `subscribe/status/checkNow/setAutoPull` (10 total) | **6 transport + `sg.on/sg.off` (generic)** + `sg.vault.notify(mountId, name)`. |
| Cross-vault wake | Not addressed | Phase E: SecureChannel relay. |
| Vault config | 5 fields | **2 booleans** (`enabled`, `auto_fetch`). |
| New foundation | n/a | **`app-host-events.js`** — pure host→app event channel infra (reusable beyond inbox). |

Net: app authors write less code, kernel exposes a smaller and cleaner surface, and the new event-channel infra pays off for future features (commits-behind, peer-connected, ephemeral-task progress, etc.).

## 3. The kernel→app event channel (the new foundation — read this first)

### 3.1 Module: `_common/js/components/app-shell/app-host-events.js`

Pure, DOM-free, Node-testable. Mirrors `AppPermissions`'s shape.

```js
globalThis.AppHostEvents = {
  parse(appJson) {
    // Returns Set<string> of allowed event names, or empty set.
    // Validates each entry is a string matching ^[a-z][a-z0-9.\-_]*$.
    // No wildcards (events must be enumerated by exact name).
  },
  allows(allowed, eventName) {
    return allowed.has(eventName);
  }
};
```

### 3.2 Bridge wiring (`app-shell.js`)

```js
class AppShell {
  // ... existing fields ...
  _hostEvents = null;           // Set<string> from app.json
  _appWindow = null;            // the iframe contentWindow

  _onAppMounted(appJson, appWindow) {
    this._hostEvents = AppHostEvents.parse(appJson);
    this._appWindow = appWindow;
  }

  // Generic emit — used by the inbox checker, future features, peer-notify, etc.
  pushEvent(eventName, payload) {
    if (!this._hostEvents || !this._hostEvents.has(eventName)) {
      this._debugDropped(eventName, payload, 'not in host_events');
      return;
    }
    this._appWindow.postMessage(
      { type: 'sg-event', name: eventName, payload },
      '*'
    );
    this._debugDelivered(eventName, payload);
  }
}
```

### 3.3 In-iframe receive (`sg-app-stub.js`)

```js
const _handlers = new Map();   // eventName → Set<callback>

window.addEventListener('message', (ev) => {
  if (!ev.data || ev.data.type !== 'sg-event') return;
  const set = _handlers.get(ev.data.name);
  if (set) for (const cb of set) cb(ev.data.payload);
  const star = _handlers.get('*');
  if (star) for (const cb of star) cb(ev.data.name, ev.data.payload);
});

window.sg = window.sg || {};
window.sg.on = (name, cb) => {
  if (!_handlers.has(name)) _handlers.set(name, new Set());
  _handlers.get(name).add(cb);
  return () => window.sg.off(name, cb);   // unsubscribe handle
};
window.sg.off = (name, cb) => {
  const set = _handlers.get(name);
  if (set) set.delete(cb);
};
```

### 3.4 `app.json` schema extension

```json
{
  "permissions": { "inbox": { "list": true, "read": true } },
  "host_events": {
    "inbox.new-messages":   true,
    "inbox.config-changed": false
  }
}
```

Apps that omit `host_events` receive **no** kernel pushes. Subscribing via `sg.on` for a name not in the allowlist silently never fires — no error (deliberately indistinguishable from "no events occurred", to avoid leak via probing).

### 3.5 The `kernel-app-handlers.js` mirror

The null-origin kernel path (used when the app is a ViV sibling) needs the same `pushEvent` surface. The kernel side already has access to `app.json` via the bootstrap; route events through the existing `SecureChannel` with envelope `{kind: 'sg-event', name, payload}`.

## 4. The check-on-events model

### 4.1 Module: `_common/js/lib/sg-inbox/sg-inbox-checker.js`

```js
class SGInboxChecker {
  constructor(inbox, bus, getConfig) {
    this._inbox = inbox;           // SGInbox instance
    this._bus = bus;               // window.sgraphVault.events
    this._getConfig = getConfig;   // () => { enabled, auto_fetch }
    this._seen = new Map();        // anchor → Set<file_id>
    this._lastTotal = 0;
  }

  async check(trigger) {
    const cfg = this._getConfig();
    if (!cfg.enabled) return;

    try {
      const res = await this._inbox.list({ include_content: false });
      const perAnchor = groupCounts(res.entries, 'inbox');
      const newEntries = this._diff(res.entries);

      if (newEntries.length === 0 && this._lastTotal === res.entries.length) return;
      this._lastTotal = res.entries.length;

      let entries = null;
      if (cfg.auto_fetch && newEntries.length > 0) {
        entries = [];
        for (const [anchor, anchorEntries] of groupBy(newEntries, 'inbox')) {
          const fileIds = anchorEntries.map(e => e.file_id);
          // Batch ≤100
          for (const chunk of chunked(fileIds, 100)) {
            const fr = await this._inbox.fetch({ inbox: anchor, file_ids: chunk });
            entries.push(...fr.files.map(f => ({ ...f, inbox: anchor })));
          }
        }
      }

      this._bus.emit('inbox.new-messages', {
        total: res.entries.length, per_anchor: perAnchor,
        entries, trigger, last_check: Date.now()
      });
      this._markSeen(res.entries);
    } catch (err) {
      this._bus.emit('inbox.error', { code: err.code || 'EUNKNOWN', message: String(err), trigger });
    }
  }

  _diff(entries) { /* return entries whose file_id not in this._seen[entry.inbox] */ }
  _markSeen(entries) { /* update this._seen */ }
}
```

**No timers.** No `start()`/`stop()`. The checker is dormant until `check(trigger)` is called.

### 4.2 Triggers (in `vault-shell.js`)

```js
// In the existing visibility handler:
this._visibilityHandler = () => {
  if (document.hidden) return;
  this._scheduleBehindCheck(500);     // existing
  this._scheduleInboxCheck(500);      // r3 addition
};

// New helper, mirrors _scheduleBehindCheck pattern exactly:
_scheduleInboxCheck(delayMs) {
  const since = Date.now() - this._lastInboxCheckTime;
  const wait = Math.max(delayMs, 1000 - since);   // 1s debounce floor
  clearTimeout(this._inboxCheckPendingTimer);
  this._inboxCheckPendingTimer = setTimeout(() => {
    this._lastInboxCheckTime = Date.now();
    this._inboxChecker.check('visibility');
  }, wait);
}
```

The 1-second debounce prevents focus-blur-focus thrash. No 30-second cadence. **No standalone timer.**

Triggers:

| Trigger | Source | Wiring |
|---|---|---|
| Tab focus | `_visibilityHandler` (existing) | Added: `_scheduleInboxCheck(500)` |
| Refresh menu "Check inbox" | New entry in `vault-header` sync menu | Dispatches `vault-header-check-inbox`; shell calls `_scheduleInboxCheck(0)` |
| Vault open | `_onVaultOpened` | Calls `_inboxChecker.check('vault-open')` once after the initial ref check |
| Peer poke | Phase E SecureChannel handler | Calls `_scheduleInboxCheck(0)` |
| Status panel "Check now" | `<vault-inbox-status>` button | Calls `_scheduleInboxCheck(0)` |

### 4.3 Bus → app fan-out (Phase C)

`app-shell.js` subscribes to the vault bus on app mount:

```js
_onAppMounted(appJson, appWindow) {
  this._hostEvents = AppHostEvents.parse(appJson);
  this._appWindow = appWindow;
  const bus = window.sgraphVault.events;
  this._busUnsubs = [
    bus.on('inbox.new-messages',   (p) => this.pushEvent('inbox.new-messages', p)),
    bus.on('inbox.config-changed', (p) => this.pushEvent('inbox.config-changed', p)),
    bus.on('inbox.error',          (p) => this.pushEvent('inbox.error', p)),
  ];
}
```

`pushEvent` filters through the allowlist (§3.2). One vault bus event → zero or more app pushes (one per running app whose allowlist contains the name).

## 8. Bridge surface

### 8.1 Transport — `app-shell.js` adds `__sgCmdType === 'inbox'`

Dispatch on `action`:

| action | gate | host call |
|---|---|---|
| `configure` | `inbox.configure` | `self._inbox.configure({ append_anchors })` |
| `append` | `inbox.append` | `self._inbox.append({...})` |
| `list` | `inbox.list` | `self._inbox.list({...})` |
| `fetch` | `inbox.read` | `self._inbox.fetch({...})` (batch guard) |
| `markProcessed` | `inbox.markProcessed` | `self._inbox.markProcessed({...})` |
| `purge` | `inbox.purge` | `self._inbox.purge({...})` |

### 8.2 Cross-vault wake — `__sgCmdType === 'vault'`, action `notify`

| action | gate | host call |
|---|---|---|
| `notify` | `vault.notify` | `self._kernel.channel.send('vault-notify', { name: eventName, payload })` to `mountId` |

The receiving kernel handles `ch.on('vault-notify', ...)` by:
1. Calling `_scheduleInboxCheck(0)` if `name === 'inbox.new-messages'` (and similar fast-paths for other relay-aware events).
2. Forwarding the bus event so it fans out to subscribed apps via `pushEvent`.

## 12. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Apps probe event names by registering for all plausible names | `sg.on` registration is purely client-side state; kernel never confirms allow/deny of `on()` calls. Handlers silently never fire if not in `host_events`. Indistinguishable from "no events occurred". |
| Auto-fetch flood | Cap entries per emit at 100; multiple emits if needed. |
| `vault.notify` spam | Per-(sender, target, name) rate-limit ≤ 1/sec at the kernel relay. |
| App declares `host_events` for an event the kernel doesn't emit | Debug pane Events tab shows "registered but never fired" so authors notice. |
| Focus thrash (focus-blur-focus) | 1-second debounce floor in `_scheduleInboxCheck`. |
| Two tabs check concurrently | `BroadcastChannel('sg-inbox-' + vaultId)` leader election; fallback: both check (idempotent). |
| Peer wakes us before append has reached storage | We do `list`, see no new entries, no event fires. Next trigger retries. Document as eventually consistent. |
| `read_key` raw-bytes for `enum_key` derivation widens key surface | AppSec sign-off Q1. |
| `host_events` allowlist evolves over time and breaks deployed apps | New event names default to off; existing apps keep working unless they explicitly subscribe. |

## 14. Sequencing summary

```
C1 transport → C2 checker(bus only) → C3 EVENT CHANNEL (host_events + sg.on) → C4 inbox bridge → C5 owner UI → C6 peer-notify → C7 reality
```

C3 is the architectural keystone. After C3, every future kernel→app push (commits-behind, peer-connected, ephemeral-task progress) reuses the same plumbing. C4–C6 are surgical additions on top.
