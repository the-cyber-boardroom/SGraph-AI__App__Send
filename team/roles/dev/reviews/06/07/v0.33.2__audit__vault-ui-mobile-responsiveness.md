# Vault UI — Mobile & Responsiveness Audit (Developer view)

**Version:** v0.33.2
**Date:** 2026-06-07
**Role:** Dev
**Scope:** `https://dev.vault.sgraph.ai/` and `https://vault.sgraph.ai/` — the `/vault` UI specifically (the `/app` UI is already full-screen and behaves acceptably per the brief).
**Status:** Audit only — no code changes in this commit.
**Companion review:** `../../designer/reviews/06/07/v0.33.2__audit__vault-ui-mobile-responsiveness.md`

---

## TL;DR

The `/vault` UI is built around a **CSS Grid shell with hardcoded pixel sizing** and **`<sg-layout>` (an external ES module from `dev.tools.sgraph.ai`) holding the tree + preview as fixed-percentage panes**. Neither has any `@media` breakpoints, no touch-resize support, no collapse-to-drawer pattern, and no minimum-width fallbacks. On a phone or narrow window:

1. The 20%/80% files-tree split inside `sg-layout` leaves ~75 px for the file list — unusable.
2. The header overflows: brand + vault-name + Upload + Debug + raw + Lock + version on one row, no wrap.
3. The inline auth banner (label + input + Set Key + ×) cannot fit on <500 px and pushes layout.
4. The sidebar nav (`--nav-width: 56px`) stays fixed even though a phone-width screen could use the room.
5. Settings, SGit, file preview tabs all assume a desktop preview pane; nothing falls back to a single-column view.
6. `sg-layout` resize handles are mouse-only — no pointer/touch event hooks were found in the loaded ES module reference, and we have no `touch-action` styling to opt into touch resize.

Net effect: the `/vault` UI is **desktop-only by construction**, not by accident. The screenshots Dinis described (resize doesn't work; large parts inaccessible) are exactly what we'd expect from the current architecture.

## Where the responsiveness fails

### 1. Shell grid uses hardcoded columns — no breakpoint

`vault-shell.js:1556-1572` defines the shell layout:

```css
.vs-shell {
    --nav-width: 56px;
    display: grid;
    grid-template-areas:
        "header  header"
        "auth    auth"
        "nav     content"
        "status  status";
    grid-template-columns: var(--nav-width) 1fr;
    grid-template-rows: 48px auto 1fr auto;
    height: 100vh;
    overflow: hidden;
}
```

There is **no `@media (max-width: …)` redefinition** of this grid anywhere in the 600-line style block. On a 360 px phone screen this still renders a 56 px rail + 304 px content; the content area then has `sg-layout` inside it splitting 20/80, so the files panel gets ~60 px (covering the row gutter + scrollbar) and the preview gets ~244 px. Most file rows clip immediately.

### 2. `<sg-layout>` is configured for desktop and never re-flowed

`vault-shell.js:212-222` initialises the layout with fixed pixel-fraction sizes:

```js
layoutEl.setLayout({
    type: 'row', id: 'root', sizes: [0.20, 0.80],
    children: [
        { type: 'stack', id: 's-files', activeTab: 0, tabs: [
            { type: 'tab', id: 't-files', title: 'Files', tag: 'vault-tree-view', state: {}, locked: true }
        ]},
        { type: 'stack', id: 's-preview', activeTab: 0, tabs: [] }
    ]
});
```

Problems:
- `0.20 / 0.80` is applied regardless of viewport width. There is no `if (window.innerWidth < 768) { … }` branch and no `matchMedia` listener.
- The Files stack is marked `locked: true` so the user cannot close it to reclaim the preview area on a small screen.
- `sg-layout` is loaded from an external CDN (`https://dev.tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js`) — its source isn't in this repo, so behavioural changes have to happen either upstream in `sg-layout` itself or by replacing it for narrow viewports.
- No `customElements.whenDefined('sg-layout').then(() => …)` resize observer; no `window.addEventListener('resize', …)` on the shell. The vault never re-balances when the user rotates a phone.

### 3. `<sg-layout>` resize handles appear to be mouse-only

Searches across `_common/` for `touchstart`, `touchmove`, `pointerdown`, `pointermove` returned **zero hits** in the vault UI. The drag handle for the pane split therefore depends on whatever `sg-layout` itself ships with. Even if it does fire pointer events upstream, we don't set `touch-action: none` on any container, so the browser will hijack the gesture for scroll/zoom before the handle ever sees it. This matches Dinis's report: *"the resize of the vault UI doesn't really work on mobile."*

### 4. Header packs 7 controls in one flex row with no wrap

`vault-shell.js:1431-1446`:

```html
<header class="vs-header">
    <div class="vs-header-title">
        <span class="vs-header-brand">SG/Vault</span>
        <span class="vs-header-vault-name"></span>
    </div>
    <div class="vs-header-right">
        <span class="vs-readonly-badge">Read-only</span>
        <button class="vs-upload-btn">Upload</button>
        <button class="vs-debug-toggle">Debug</button>
        <a class="vs-raw-vault-link">raw</a>
        <button class="vs-lock-btn">Lock</button>
        <span class="vs-header-version">v0.1.4</span>
    </div>
</header>
```

CSS uses `display: flex; justify-content: space-between` with no `flex-wrap: wrap`. On a phone, the vault-name truncation is fine but the right cluster forces horizontal overflow — buttons get clipped or pushed off-screen.

### 5. Inline auth banner is a horizontal row

`vault-shell.js:1864-1875` and `1449-1454`:

```html
<div class="vs-auth-banner">
    <span class="vs-auth-banner-msg">Access key needed for write operations</span>
    <input class="vs-auth-input" placeholder="Paste access key">
    <button class="vs-auth-submit">Set Key</button>
    <button class="vs-auth-cancel">×</button>
</div>
```

The message is `white-space: nowrap` (line 1881) and the input has `max-width: 320px`. On a 360 px phone the message alone overflows, hiding the input.

### 6. Settings panel is hardcoded to 640 px wide

`vault-shell.js:2028-2030`:

```css
.vs-settings-panel { max-width: 640px; }
```

640 px works on desktop. On phones it remains 640 px and overflows horizontally because there is no `width: 100%` fallback or breakpoint. The inputs inside (`.vs-settings-key-row` is a `display: flex`) don't wrap either, so the Save button is squeezed against the input.

### 7. Side nav stays 56 px on a phone — wastes 15% of the viewport

The icon+label vertical buttons (`.vs-nav-item`) read fine at 56 px on a desktop but on a 360 px phone they consume 15% of the width while the content is already cramped. A phone wants either a bottom tab bar, a top horizontal nav, or a hamburger drawer — none exist.

### 8. Per-file action bar is a `display:flex` row with 5+ buttons

`vault-shell.js:449-526` builds the in-tab toolbar inline (filename + raw + Edit + Save + Cancel + Rename + Download + Delete). It has `gap:0.5rem` and no `flex-wrap`. Even on desktop with a long filename this clips; on a phone half the buttons disappear.

### 9. Entry screen (vault unlock) is dialog-shaped

`vault-shell.js:1547-1554`:

```css
.vs-view-entry {
    display: flex;
    align-items: center;
    justify-content: center;
    min-height: 100vh;
    padding: var(--space-4);
}
```

The card inside is rendered by `<vault-entry>`. Its CSS (in `vault-entry.js`) uses a fixed-width card. On a narrow viewport the card width and the input fields don't shrink below their content size.

### 10. Debug panel adds a third pane

When Debug is toggled (`vault-shell.js:1342`), `sg-layout.addPanel(…)` adds a panel. There is no special-case for narrow viewports — Debug appears alongside Files + preview as a third column, further squeezing both. The 4 internal tabs (Msgs / Events / API / Storage) each fit only on desktop widths.

### 11. SGit view: no width handling

`vault-shell.js:2013-2018`:

```css
.vs-view-sgit { padding: var(--space-4); overflow-y: auto; height: 100%; box-sizing: border-box; }
```

The view delegates to `<vault-sgit-view>` which renders its own table of commits/branches/objects. No mobile rules; tables overflow horizontally.

### 12. Per-file action bar uses inline `style.cssText`

`vault-shell.js:449-450, 460-465, 547`, etc. apply layout via `el.style.cssText = '…'`. These bypass the stylesheet entirely, so even adding `@media` rules to the shell stylesheet won't override them — the JS will have to read `window.matchMedia` or every inline style needs to move to classes. **This is the single biggest tactical obstacle to a clean responsive pass.**

## What's already in our favour

1. **Design tokens** (`design-tokens.css`) cross Shadow DOM correctly. We can add `@media` rules that swap token values (e.g. `--space-4` to `--space-2` under 600 px) and the whole UI benefits.
2. **The `/app` route already has a `@media (max-width: 600px)` block** — same project, same conventions. The pattern is established; we just have to apply it to the `/vault` route.
3. **The shell is a single web component** — the entire layout/styles block lives in one place (`VaultShell.styles` static getter, lines 1545-2148). Any media-query addition is local.
4. **No framework lock-in** — vanilla JS + custom elements. We can swap `sg-layout` for a native CSS solution on mobile (e.g. show only Files OR preview, not both) without ripping out anything.
5. **The IFD methodology supports surgical versioning** — we can ship `v0.1.5` of the vault UI in parallel with `v0.1.4` and switch the route over once verified.

## Recommended engineering approach (proposed — not in scope of this audit)

Rough order of difficulty, lightest first. None of this is implemented yet.

### Phase A — Cheap wins (no `sg-layout` change)

1. Add `@media (max-width: 768px)` to `vault-shell.js` styles:
   - Collapse `--nav-width: 56px` → bottom-tab bar (or `0` + hamburger).
   - `flex-wrap: wrap` on `.vs-header-right`, `.vs-auth-banner`, all inline action bars.
   - `.vs-settings-panel { max-width: 100%; }` and stack `.vs-settings-key-row` vertically (input full width, Save below).
   - Shrink header buttons to icons under 600 px.
2. Move per-file action-bar inline `style.cssText` into stylesheet classes (`.vs-file-tab-actionbar`, `.vs-file-tab-btn`, etc.) so breakpoints can override them. Mechanical refactor; no logic changes.

### Phase B — `sg-layout` adaptation

3. After `customElements.whenDefined('sg-layout')`, register a `matchMedia('(max-width: 768px)')` listener that calls `setLayout()` with a **single-column stack** (Files becomes a tab, preview becomes a tab, debug becomes a tab) instead of a row split. The currently-locked Files tab must be made unlocked-on-mobile so the user can give the preview the whole screen.
4. Audit `sg-layout` upstream for `touch-action: none` on its drag handles and `pointerdown` / `pointermove` listeners. If absent, either patch upstream or hide the resize handle under 768 px (the single-column layout makes resize meaningless anyway).

### Phase C — Mobile-first refinements

5. New mobile-first chrome: a slim 44 px top bar (brand + vault-name only) and a bottom action bar with the 3-5 most-used controls (Upload, Files/Preview toggle, Debug). Lock button moves into a menu.
6. Replace the dense file action bar with a row of icons + an overflow ⋮ menu. On desktop, keep the current labelled buttons.
7. Inline auth banner: change to a stacked layout under 600 px (message on row 1, input + Set Key on row 2). Increase input height to 44 px tap target.
8. Settings panel: 100% width on mobile, vertical stacking of label/input/button.

### Phase D — Out-of-scope but worth flagging

9. The Web Components in this UI are mostly **light DOM** (the shell is light DOM). Touch event delegation, scroll-into-view on tab activation, and `inputmode="…"` hints on the access-key field are easy wins once we're in the file.
10. Worth confirming whether Dinis wants the *same* vault UI to scale down, or whether mobile should be a **deliberately reduced surface** (e.g. read-only browse + share-create only). The current code path makes every desktop affordance available on mobile, which is the root cause of the cramming.

## Risk and test-impact notes

- Most of the listed changes are **CSS-only** — they don't change behaviour, so unit/integration tests should not break. Any Playwright E2E that asserts viewport pixel positions will need updating; those should fail loudly (good failure) once the breakpoints land.
- The `sg-layout` reconfiguration in Phase B has a higher blast radius — it touches layout state persistence (`_savePreferences` / `localStorage` `sgraph-vault-prefs-v2`). We'll need a migration path or a separate key for mobile layout state to avoid resetting desktop users.
- `sg-layout` is on `https://dev.tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js`. If upstream changes are needed, that's a cross-repo dependency the Town Planner / Villager teams should be aware of.

## Open questions for Dinis

1. **Floor breakpoint** — what's the smallest viewport we commit to supporting? 320 px (small Android), 360 px (typical phone), or 600 px (tablet portrait)?
2. **Scope** — should mobile expose the full vault (read + write + share + debug + SGit) or a curated subset?
3. **Resize on touch** — is making the desktop split-pane drag work on touch important, or are we happy collapsing to a tabbed single-column on mobile (which removes the resize gesture entirely)?
4. **Timeline** — Phase A alone (1-2 days work) would already fix the "large parts are inaccessible" half of the brief. Should we ship that first as v0.1.5 and tackle Phases B-C separately?
