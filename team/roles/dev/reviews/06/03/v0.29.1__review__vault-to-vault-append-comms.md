## 2. Schema Mapping to Type_Safe — GOOD, 1 concern

Existing schemas (e.g. `Schema__Transfer__Upload_Request`) use `Type_Safe`
with `Safe_Str`, `Safe_UInt`, `Timestamp_Now` etc. The proposed schemas map
cleanly.

**Concern — `bytes` field in Type_Safe.** The brief specifies
`payload: bytes` in `Schema__Append_Request` and `content: bytes` in
`Schema__Inbox_Entry`. In the existing codebase, binary data is handled via
`Request.body()` (raw bytes from FastAPI) and `Response(content=payload,
media_type='application/octet-stream')` — NOT through Type_Safe schema fields.

See `Routes__Vault__Pointer.py:91-118`: the write endpoint reads `payload`
directly from the `Request` object, not from a schema.

**Recommendation:** Handle `payload` as raw request body (like existing
write), not as a schema field. The schema is for the metadata/response. The
append endpoint should mirror the existing write pattern:

```python
@route_path('/append/{vault_id}/{append_token}')
async def append(self, vault_id: Safe_Str__Id,
                       append_token: str,
                       request: Request) -> dict:
    payload = await request.body()
    # ... gate check, cap check, store ...
    return {'ok': True}
```

For `include_content:true` responses (inbox listing with inline ciphertext),
use base64 encoding like the existing `/read-base64/` endpoint, or return
binary in a `Response` object with content negotiation.

## 3. Storage Operations — BLOCKING finding

### 3a. `file__move` does NOT exist in Storage_FS

**This is blocking for the `mark-processed` endpoint.**

The `mark-processed` operation needs to move files from `inbox/{token}/` to
`processed/{token}/`. Verified that `Storage_FS` has NO `file__move` method:

```python
# Storage_FS public methods:
# file__bytes, file__delete, file__exists, file__json, file__save, file__str,
# files__paths, folder__files, folder__files__all, folder__folders
# → NO file__move, NO file__copy
```

**The raw `osbot-aws` S3 class DOES have `file_move` and `file_copy`:**
```python
s3.file_move(bucket, key_source, key_destination)  # copy + delete
s3.file_copy(bucket_source, key_source, bucket_destination, key_destination)
```

And there's a code example in `team/humans/dinis_cruz/code-example/` that
adds `file__move` and `file__copy` to an extended `Storage_FS__S3`. But this
is NOT in the production code.

**Three options:**
1. **Implement as copy+delete at the service layer** — `file__save(dest,
   file__bytes(source))` then `file__delete(source)`. Works with all backends
   but is NOT atomic (crash between save and delete = duplicated file).
2. **Add `file__move` to `Storage_FS__S3.py`** locally — wrap `S3.file_move`.
   Also add to `Storage_FS__Local_Disk.py` and memory backend.
3. **Contribute `file__move` upstream to `memory-fs`** — proper fix but
   slower.

**Recommendation:** Option 2 for now (local extension in this repo's
`Storage_FS__S3.py`), with a `# todo: contribute upstream` comment. The
existing `Storage_FS__Local_Disk.py` already patches upstream
(`Storage_FS__Local_Disk__Upstream`) for `folder__files__all` — same pattern.

### 3b. Listing / pagination

`folder__files__all(prefix)` returns ALL matching paths. There's no built-in
cursor or limit — the S3 implementation calls `s3.find_files()` which returns
a full list.

For the `after_file_id` cursor:
1. Call `folder__files__all(inbox_prefix)` to get all paths
2. Sort by filename (lexicographic = chronological due to zero-padded epoch_ms)
3. Filter to entries after `after_file_id`
4. Apply `limit`

This works for moderate inbox sizes (hundreds of files). At scale (thousands),
a paginated S3 list would be better, but that's a Storage_FS enhancement for
later. The capacity cap keeps inbox size bounded, so this is acceptable for P0.

### 3c. S3 atomicity

S3 doesn't have atomic move. The copy+delete pattern means a crash between
copy and delete leaves the file in both `inbox/` and `processed/`. This is
safe because:
- `mark-processed` is idempotent (already-moved → reported as `missing`)
- The drainer uses cursors, not counts
- `purge` (owner-only) can clean up duplicates

## 4. Gate Implementation — STRAIGHTFORWARD

Three gates, mapped to existing patterns:

```python
# Append gate (new)
def _check_append_token(self, vault_id, presented_token):
    manifest = self._load_manifest(vault_id)
    if not manifest:
        return False
    anchors = manifest.get('append_anchors', [])
    return hashlib.sha256(presented_token.encode()).hexdigest() in anchors

# Enum gate (new)
def _check_enum_key(self, vault_id, presented_key):
    manifest = self._load_manifest(vault_id)
    if not manifest:
        return False
    return hashlib.sha256(presented_key.encode()).hexdigest() == manifest.get('enum_key_hash')

# Write gate (existing) — reuse Service__Vault__Pointer._check_vault_write_key()
```

The manifest cache (`_manifest_cache`) is already Lambda-lifetime scoped.
Since appends don't modify the manifest, cache invalidation only matters
for anchor management (cold path).

## 5. Testing Strategy — GOOD

**Fully feasible with in-memory stack.** The existing test pattern works:
set up `Storage_FS__Memory`, create vault, write manifest, then test each
endpoint. No mocks needed.

**Test fixtures needed:**
- A vault with `append_anchors` + `enum_key_hash` in its manifest
- A helper to compute `H(token)` and `H(enum_key)` from test values
- Inbox files at known paths for testing list/fetch/mark-processed/purge

**Drain loop testing:** The drain loop is a client-side concept — test it as
a sequence of endpoint calls: append N files → inbox list → mark-processed →
verify inbox empty, processed non-empty → purge → verify processed empty.

**Negative tests (critical for security):**
- Append with wrong token → 403
- Inbox list without enum_key → 403
- Inbox list with append_token (wrong tier) → 403
- Purge without write_key → 403
- Mark-processed with wrong enum_key → 403

## 7. Practical Concerns

**7.0 — Manifest update endpoint (BLOCKING)**

The brief does not specify how `append_anchors` and `enum_key_hash` get into
`manifest.json`. The existing `_ensure_manifest()` only sets `write_key_hash`
at vault creation and never updates. Without a manifest update mechanism, no
inbox gates can be configured and no inbox endpoints function.

**Options:**
- `POST /api/vault/configure/{vault_id}` (write_key-gated) — new endpoint for
  manifest field updates
- Extend the existing batch endpoint to accept manifest updates
- Set fields at vault creation (requires knowing PKI keys upfront)

**Priority:** Blocking — must be designed before P0 begins.

**7.1 — 96-bit random hex in Python:**
```python
import secrets
rand_hex = secrets.token_hex(12)  # 12 bytes = 96 bits = 24 hex chars
```
Clean, `crypto`-grade, built-in.

**Epoch milliseconds (13-digit zero-padded):**
```python
import time
epoch_ms = f'{int(time.time() * 1000):013d}'
```

**Filename construction:**
```python
filename = f'{epoch_ms}_{rand_hex}.enc'
# e.g. "1717430400000_a1b2c3d4e5f6a7b8c9d0e1f2.enc"
```

**Capacity cap enforcement:** Check on each `append` call:
```python
files = self.storage_fs.folder__files__all(inbox_prefix)
if len(files) >= MAX_FILES or sum_sizes >= MAX_BYTES:
    return 507
```
This requires listing the folder on every append — acceptable for moderate
inbox sizes (the cap keeps them bounded). For high-throughput scenarios, a
counter file or a metadata index would be more efficient, but overkill for
P0.
