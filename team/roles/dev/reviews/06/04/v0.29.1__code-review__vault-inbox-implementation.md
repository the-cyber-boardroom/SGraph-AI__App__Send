## Verdict (original): SOLID FOUNDATION — 2 blocking, 3 important before this is production-safe

The structure is right: clean tier separation, gates mirror the existing
`write_key_hash` pattern, the drain cycle works end-to-end, and 101 tests pass
with no mocks. But the tests all run on the **memory** backend, and two of the
findings below are invisible on memory and only bite on **S3 (Lambda
production)** and **local-disk (container)**. That's the dangerous kind of bug.

---

## BLOCKING

### B-1 — `inbox_list(inbox=None)` silently returns empty on S3/Lambda

`Service__Vault__Inbox.py:135` calls `self.storage_fs.folder__folders(...)` to
enumerate inbox folders when no specific `inbox` is given.

- **Memory backend** implements `folder__folders` → works (so all tests pass).
- **Local-disk backend** overrides it (`Storage_FS__Local_Disk.py:22`) → works.
- **S3 backend** does NOT override it. It inherits the base
  `Storage_FS.folder__folders`, which is `return []` (verified). So on S3 it
  returns **zero folders, silently.**

**Impact:** The brief's canonical drain loop (`03 §2`) polls
`POST /vault/inbox { include_content:true, after_file_id:cursor }` with **no
`inbox` field**. On Lambda/S3 — the primary production target — that call
returns `entries: []` even when the inbox is full. A drainer would conclude
"nothing to process" and never drain. Messages pile up, undelivered, with no
error. This is worse than a crash because it fails silent.

**Why tests miss it:** every test runs on `Storage_FS__Memory`.

> **RESOLVED:** `Storage_FS__S3.folder__folders` implemented (derives immediate
> subfolder names from `find_files` keys, mirroring the local-disk patch).
> Regression test `test_Storage_FS__S3.py` asserts the method is overridden (not
> the base `return []` stub). Behavioural parity is exercised via the memory and
> local-disk backends the service runs on.

**Fix options:**
1. Add `folder__folders` to `Storage_FS__S3` (derive folder names from
   `find_files` keys by splitting on `/` after the inbox prefix). Mirrors the
   `Storage_FS__Local_Disk` patch precedent. **Recommended.**
2. Or: require `inbox` on the list endpoint and drop list-all. But that
   contradicts the brief's drain loop, so (1) is better.
3. Either way: **add an S3-backed (or LocalStack) test** so backend-specific
   gaps can't hide behind the memory backend again.

### B-2 — Path traversal via untrusted `file_id` / `inbox` / `append_token`

The token and file identifiers from the request are used **directly** as path
components with no format validation:

- `append`: `path__vault_inbox(vault_id, append_token, file_name)` — `Service:116`
- `inbox_fetch`: `path__vault_inbox(vault_id, inbox, file_id)` — `Service:173`
- `mark_processed`: src/dst from `inbox` + `file_id` — `Service:189-190`
- `purge`: `inbox` + `file_id` — `Service:218-220`

`Storage__Paths` is pure f-string interpolation — no normalization. A caller
who passes `file_id = '../../bare/data/obj-cas-imm-xxxx/payload'` builds a path
that escapes the `inbox/` subtree into the vault's real content tree.

- **S3 / memory:** keys are opaque, so `../` is literal and does *not* resolve
  — low real impact there.
- **Local-disk (container deployment):** `../` traverses the actual filesystem.
  An `enum_key` holder could **read, move, or delete files anywhere the process
  can reach** via `fetch` / `mark-processed`, and a `write_key` holder via
  `purge`.

This directly defeats the brief's core promise (`00`, principle 4): `enum_key`
is a *lower* tier than vault read — it must reach only the inbox namespace. With
traversal, `enum_key` becomes arbitrary vault read. That's the exact
capability-escalation the four-tier model exists to prevent.

**Fix:** validate before any path construction:
- `file_id` must match `^\d{13}_[0-9a-f]{24}\.enc$` (the server's own filename
  format). Reject anything else → `400`.
- `inbox` / `append_token` must match `^[0-9a-f]{16,128}$` (hashes are hex).
  Reject otherwise. (Even though the gate makes a malicious-but-matching token
  a SHA-256 preimage problem, validate anyway — defense in depth, and it closes
  the local-disk hole regardless of the gate.)

> **RESOLVED via Type_Safe (not manual regex):** two `Safe_Str__*` primitives
> now enforce the format at the type boundary —
> `Safe_Str__Vault__Append_Token` (`^[0-9a-f]{16,128}$`) and
> `Safe_Str__Vault__Inbox__File_Id` (`^\d{13}_[0-9a-f]{24}\.enc$`), both
> `strict_validation=True`, `regex_mode=MATCH`. The service coerces every
> path-component input through these before any path is built; bad input →
> `invalid_input` → `400`. Traversal negative tests added at both the service
> and HTTP layers (`test__*_rejects_traversal_*`,
> `test__enum_holder_cannot_escape_inbox_via_file_id`). Note: on S3/memory the
> keys are opaque so `../` was already literal — the real fix is for the
> local-disk (container) backend, plus correctness/defense-in-depth everywhere.

## IMPORTANT (performance — explicitly requested)

### I-1 — `inbox_list` downloads every file's full bytes, even metadata-only

`Service:146` reads `file__bytes(path_str)` for **every** file in scan, just to
compute `size` — *even when `include_content=False`*. On S3 that's a full
`GetObject` per file per list call. A 500-message inbox = 500 full downloads to
return a metadata listing. With messages up to 5 MB, a single "list" can pull
gigabytes.

There's no size-without-download in the `Storage_FS` abstraction (S3
`find_files` returns keys only). Options:
- For P0: when `include_content=False`, **omit `size`** (or return `0`/`null`)
  and skip the read entirely. The drain loop only needs `file_id` + ordering to
  page; it fetches content separately.
- Better (later): add a `folder__files__sizes` / head-object path to the S3
  backend so `size` is cheap.

> **RESOLVED:** metadata-only listing now reads **zero** payloads — entries
> carry `inbox` / `file_id` / `received` (the latter parsed from the filename).
> `size` + `content` are only produced when `include_content=True`, and only for
> the **paged window** (not all entries). Tests:
> `test__inbox_list__metadata_only_omits_size_and_content`,
> `test__inbox_list__content_includes_size`.

### I-2 — `append` capacity check downloads the whole folder on every append

`Service:107-110` sums sizes by reading `file__bytes` of every existing file in
the folder — on **every** append. O(n) full downloads per write; the hot path
is the most expensive one. This will dominate cost and latency under load and
partially negates the whole point of a cheap append surface.

**Fix for P0:** keep the **file-count** cap (cheap — it's just
`len(folder__files__all(...))`, one list call) and **drop the byte-sum** until
the backend can report sizes without a full read. The count cap already bounds
abuse; the brief calls the cap an availability guard, not a precise quota.

> **RESOLVED:** byte-sum removed. `append` now does one list call for the
> file-count cap and no per-file reads. `INBOX_MAX_BYTES` removed. (`per-message`
> size cap via `APPEND_MAX_PAYLOAD` is retained — that's a cheap `len()`.)

### I-3 — No cap on `file_ids` batch length (DoS)

`fetch`, `mark_processed`, `purge` iterate `file_ids` with no length limit
(`Service:172, 188, 216`). The existing pointer batch caps at
`BATCH_MAX_OPERATIONS = 100`. A caller (e.g. a compromised `enum_key`) can send
100k ids → 100k storage ops in one request → Lambda timeout. Add an equivalent
cap and return `400` over it.

> **RESOLVED:** `INBOX_BATCH_MAX_FILE_IDS = 100` enforced in fetch /
> mark-processed / purge → over cap returns `invalid_input` → `400`. Tests:
> `test__*_rejects_oversized_batch`, `test__fetch__accepts_max_batch`.

## What's good (keep it)

- Tier separation is clean and the negative tests for it are thorough
  (`test__tier__*` in both suites) — exactly the right security posture.
- Gates reuse the proven `H(key) == stored_hash` pattern; tombstone/deleted
  handling is correctly inherited.
- `mark-processed` copy+delete with idempotent `missing` reporting matches the
  brief's reversible-move design; non-atomicity is correctly offloaded to the
  client seq-number layer.
- `append` response is genuinely blind (`{ok:true}`, no id/count) — the test
  asserts this explicitly. 
- Status-code discipline (403 vs 413 vs 507) matches `01 §4`.

## Recommended order to land

1. **B-1**: add `folder__folders` to `Storage_FS__S3` + an S3/LocalStack test.
2. **B-2**: validate `file_id` / `inbox` / `append_token` formats; add traversal
   negative tests.
3. **I-2** then **I-1**: drop the byte-sum, make metadata listing read-free.
4. **I-3**: cap batch `file_ids`.
5. **M-***: cleanup pass.

None of these change the API shape or the data model — they're hardening of an
otherwise sound P0.
