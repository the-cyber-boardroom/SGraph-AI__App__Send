## Code Shipped This Period

### Vault Inbox — 6 Endpoints, 101 Tests ✅

The vault-to-vault communication server primitive is live. Key implementation notes for follow-on builders:

| Endpoint | Complexity | Notes |
|----------|-----------|-------|
| `POST /api/vault/inbox/append/{vault_id}` | Low | Body: `{append_token, payload (base64)}`. Returns `{ok: true}` or 403/413/507 |
| `POST /api/vault/inbox/list/{vault_id}` | Low | Header: `x-sgraph-vault-enum-key`. Body: `{inbox, after_file_id?, limit?, include_content?}` |
| `POST /api/vault/inbox/fetch/{vault_id}` | Low | Header: `x-sgraph-vault-enum-key`. Body: `{inbox, file_ids[]}` |
| `POST /api/vault/inbox/mark-processed/{vault_id}` | Low | Header: `x-sgraph-vault-enum-key`. Moves files inbox/ → processed/ |
| `POST /api/vault/inbox/purge/{vault_id}` | Low | Header: `x-sgraph-vault-write-key`. Irreversible delete |
| `POST /api/vault/inbox/configure/{vault_id}` | Medium | Header: `x-sgraph-vault-write-key`. Sets `append_anchors` + `enum_key_hash` |

**Test coverage:** `Service__Vault__Inbox` (62 tests), `Routes__Vault__Inbox` (39 tests). All in-memory, no mocks.

**Critical:** `inbox` is a named sub-folder within the vault. `mark-processed` is reversible (inbox/ → processed/). `purge` is not reversible.

## Implementation Analysis by Priority

### Stream 1: Three-Agent Comms Demo (P-312)

**Effort:** 3–5 days | **Blocks:** P-313 real design | **Depends on:** vault inbox (DONE)

The server is ready. The demo is browser-side work:
1. Build 3-pane iframe harness (each iframe = one agent, has a vault_id + append_token + enum_key)
2. Implement internal JS API: `ping()`, `send(to_vault_id, payload)`, `receive()`, `markReceived()`
3. Build step-by-step validation UI (not an automated test — a manual confirmation flow)
4. Manual round-trip: Agent A sends to Agent B's inbox; Agent B lists, fetches, marks processed
5. Phase 2: replace manual sends with OpenRouter API calls (agentic round-trip)

**Dev notes:**
- The `append_token`, `enum_key`, and `private_key` values per vault must be provisioned before the demo — hardcode them for the PoC; key provisioning UX is a separate concern
- Use `include_content: false` for `list` calls (avoid loading payloads in the demo list view)
- Keep the payload small for the demo (text only, no large blobs)

### Stream 2: Vault-to-Vault Comms PKI Layer (P-313)

**Effort:** 5–8 days (after demo) | **Depends on:** vault inbox (DONE) + architect provisioning spec

P-313 is the formalisation of what the demo (P-312) proves informally. The dev work after the demo:
1. Define the template-vault provisioning format (one vault holding `{public_key, append_token}`)
2. Build a provisioning endpoint (or document the manual provisioning flow)
3. Build the client-side key-encryption wrapper: `encryptForRecipient(message, recipientPublicKey)` → base64 payload
4. Wire into the demo to replace hardcoded keys with provisioned keys

**Blocked on:** Architect provisioning spec (`AD-provisioning-spec-1`). Do not start until spec exists.

### Stream 3: GitHub Actions Publishing Mode (P-311)

**Effort:** 1–2 days | **Depends on:** existing vault read endpoints (DONE)

This is almost entirely a GHA workflow file + a static-site generator script:
1. GHA workflow reads vault via public read key (calls `/api/vault/read/{vault_id}/{file_id}` or `/api/vault/read-base64/...`)
2. Decrypts in Node.js (reuse the sgit-ai JS crypto module if available)
3. Generates static output (markdown → HTML, or JSON → HTML)
4. Publishes to GitHub Pages

**Dev note:** The vault read endpoints are public (no auth required). The read-only key is the only credential needed. The GHA workflow MUST NOT commit the read-only key in plaintext — use a GitHub secret.

### Stream 4: Skills Library MVP (P-315)

**Effort:** 5–8 days | **Depends on:** existing vault (DONE) + basic search (low effort)

Minimum viable skills library:
1. A library vault (one vault holding all skills as encrypted files)
2. A SKILL.md schema with: name, description, source, version, tags, applicability_score
3. A search endpoint (or client-side search over the manifest)
4. A "view skill" page that decrypts and displays the SKILL.md
5. A "copy key to use" UX

**Not needed for MVP:** real-time sync from aggregators, evals, scoring, billing. Start with a manually curated list of 5–10 skills.

### Stream 5: Skill Base Vaults (P-295) — Foundation for P-300–P-305

**Effort:** 15–20 days total across sub-tasks | **Depends on:** vault zip format decision

This is the foundation for all Skills creator economy items (P-300–P-305, P-303, P-304). Before starting, the vault-zip portability format must be agreed with the architect. Sub-tasks:
1. Vault zip export (SKILL.md + code + docs + metadata) as a standard zip
2. Base vault schema (SKILL.md v2: adds `parent_vault_id`, `customisation_level`, `sync_state`)
3. Customised vault creation flow (fork base vault, record `parent_vault_id`)
4. Sync notification mechanism (parent updated → child receives sync_pending signal)

**Note:** Items P-300, P-301, P-303, P-304, P-305 are **content and commercial model work**, not code work. They do not generate dev tasks directly — they tell the Dev team what content the skill base vaults need to hold.

## Implementation Risk Flags

### Risk 1: Key provisioning is unspecified (P-313, HIGH)
The three-agent demo will hardcode keys (acceptable for PoC). But P-313 requires a real provisioning mechanism. This has not been specced. **Flag to Architect before P-313 implementation starts.**

### Risk 2: Vault zip portability not agreed (P-295, MEDIUM)
All skills creator economy work (P-300, P-303–P-305) depends on vault-as-zip being portable to aggregators (Tessl, Pi, Anthropic). This format is not yet agreed. Building skill base vaults without this agreement means rework. **Flag to Architect.**

### Risk 3: Cascade sync model not designed (P-303, MEDIUM)
The multi-level customisation cascade (corporate → group → cyber → ethics) requires a sync notification mechanism. No design exists. Building any customised vault without this will lead to orphaned customisations when the base updates. **Flag to Architect.**

### Risk 4: P-314 PKI scope creep (P-314, MEDIUM)
The PKI brief is architecturally large (touches the entire vault security model). Without a clear decision on which key distribution model to use (vault-scoped vs. IdP vs. self-sovereign), implementation could start down the wrong path. **Do not start P-314 until OQ-pki-key-distribution-model-1 is resolved.**

### Risk 5: GitHub Actions key management (P-311, LOW)
If the vault's public read key is rotated while the GHA workflow is using it, the workflow will break silently. The workflow should validate key access on each run and alert on failure. Easy to prevent if designed in from the start.
