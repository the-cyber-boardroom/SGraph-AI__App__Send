# Code Review — SG/API, Vault Inbox, and the Append Rename Proposal

**version** v0.32.7 | **date** 8 June 2026 | **reviewer** Dev (Opus 4.8, Explorer team)
**scope** SG/API User Lambda (broad) → Vault Inbox (deep) → `append` rename brief
**method** Source read, no mocks. Cross-checked against the reality document.

---

## Verdict

The inbox implementation is **solid and the security model holds** — the four-tier
gates are clean, traversal is closed at the type boundary, and the prior code-review
findings (B-1, B-2, I-1, I-2, I-3) are genuinely resolved. I found **one medium
availability bug** (memory blow-up on `include_content`), **two low-severity
hardening gaps**, and a few notes. The **`append` rename I agree with**, with three
corrections to the plan before it ships.

Nothing here blocks the rename — fold the fixes into the same pass.

---

## Part 1 — SG/API (broad pass)

I read the pointer service (the pattern the inbox mirrors), the storage backends,
the path layer, and the typed primitives. The architecture is coherent:

- **Write-key model is consistent.** `Service__Vault__Pointer` hashes the write key
  (SHA-256), stores only the hash in `manifest.json`, and first-write creates the
  manifest. Tombstones block re-creation. The inbox service reuses this exactly.
- **Read is unauthenticated by design** — payloads are ciphertext, so `read` /
  `batch_read` need no auth. This is the zero-knowledge contract and it's applied
  consistently.
- **`VAULT_ID_PATTERN`** (`^[a-z0-9]{8,24}$`) keeps vault IDs opaque so project names
  never leak into S3 keys or logs. Good.
- **Storage_FS__S3** correctly defers boto3 client creation to first request
  (SnapStart-safe), and `folder__folders` is properly overridden (the B-1 fix).

One broad note carried into the inbox review below: **the manifest cache is
per-service-instance and never invalidated.** That's fine for the pointer service's
write-key check (the hash is immutable for a vault's life), but the inbox `configure`
does a **read-modify-write on the same manifest**, which is a different access
pattern — see L-2.

## Part 2 — Vault Inbox (deep pass)

### What's right (keep it)

- **Tier separation is real.** `append_token` → write only; `enum_key` → list/fetch/
  mark-processed; `write_key` → configure/purge; `private_key` → never touches the
  server. An append-token holder **cannot** enumerate or fetch (no enum_key → 403),
  and an enum-key holder **cannot** purge or configure (no write_key → 403). I traced
  every gate; there is no path that crosses a tier.
- **Traversal is closed at the type boundary.** Every path-component input is coerced
  through `Safe_Str__Vault__Append_Token` (`^[0-9a-f]{16,128}$`) or
  `Safe_Str__Vault__Inbox__File_Id` (`^\d{13}_[0-9a-f]{24}\.enc$`) before any path is
  built. Bad input → `invalid_input` → 400, ahead of the gate. This is the right
  architecture (typed primitives, not ad-hoc regex in the handler).
- **Append is genuinely blind.** Response is `{ok:true}` — no file_id, no count. The
  sender learns nothing about inbox state. Confirmed against the route.
- **Metadata listing reads zero payloads** (the I-1 fix) and **append does one
  list-call, no per-file reads** (the I-2 fix). Both verified in source.
- **Secure default:** a vault with no `append_anchors` key rejects *all* appends
  (`manifest.get('append_anchors', [])` → `[]` → nothing matches). A vault created via
  the pointer API but never inbox-configured is closed, not open.

### FINDINGS

#### M-1 (MEDIUM, availability) — `inbox_list(include_content=True)` reads the whole page into memory *before* the ceiling check

`Service__Vault__Inbox.py:168-177`. The loop reads **every** entry's bytes and
base64-encodes them into the response dict, accumulating `total`, and only *after the
loop* checks `if total > INLINE_CONTENT_CEILING`. So the ceiling never bounds memory —
it bounds the *response*, after the cost is already paid.

Worst case: `limit` coerces up to `INBOX_MAX_LIMIT = 200`, each file up to
`APPEND_MAX_PAYLOAD = 5 MB` → **~1 GB read + ~1.3 GB base64 in memory** before the 3 MB
ceiling rejects it. On Lambda that's an OOM/timeout, not a clean 413.

**Blast radius:** the caller needs a valid `enum_key`, so it's not anonymous. But
`enum_key` is the *read/processing* capability — in the brief's model it can be handed
to an ephemeral compute agent, separate from the vault owner. A misbehaving or
compromised enum-key holder can OOM the function repeatedly, and Lambda OOMs consume
shared concurrency → **cross-tenant availability impact**, not just self-harm.

**Fix (cheap):** check the ceiling *inside* the loop and bail before reading more:

```python
if include_content:
    total = 0
    for entry in entries:
        file_path  = path__vault_inbox(vault_id, entry['inbox'], entry['file_id'])
        file_bytes = self.storage_fs.file__bytes(file_path) or b''
        total += len(file_bytes)
        if total > INLINE_CONTENT_CEILING:                 # bail BEFORE encoding more
            return dict(status='content_too_large', entries=[], truncated=True)
        entry['size']    = len(file_bytes)
        entry['content'] = base64.b64encode(file_bytes).decode('ascii')
```

Better still, clamp `limit` to a small value when `include_content=True` (e.g. 25), so
the page can't request 200 large blobs at once. The drain loop fetches content in
windows anyway.

#### L-1 (LOW, hardening) — `configure` stores `append_anchors` / `enum_key_hash` without format validation

`Service__Vault__Inbox.py:91-104`. The values from the request body are written to the
manifest as-is. They're only ever used in equality comparisons (`self._hash(x) in
anchors`, `== enum_key_hash`), so a malformed value simply never matches — **no
injection, no traversal** (they're JSON values, never path components). But everywhere
else in this service path-adjacent inputs are typed; these two are the exception.

**Fix (defense in depth):** validate each anchor and the enum hash as 64-char hex
before storing (`^[0-9a-f]{64}$`), reject otherwise. Cheap, and keeps the "no raw
primitives on stored security material" invariant consistent.

#### L-2 (LOW, correctness) — `configure` is a read-modify-write on a cached, shared manifest with no concurrency guard

`Service__Vault__Inbox.py:91-104`. `configure` loads the manifest (returned **by
reference** from `_manifest_cache`), mutates it in place, and saves. Two concerns:

1. **Lost update:** two concurrent `configure` calls (or a `configure` racing a
   pointer-service write that also touches the manifest) can clobber each other — last
   writer wins, no CAS. The pointer service avoids this because its manifest is
   write-once; the inbox makes the manifest mutable, which changes the assumption.
2. **Cross-service staleness:** the pointer service holds its **own** `_manifest_cache`
   in a **separate instance**. After inbox `configure` adds `append_anchors`, the
   pointer service's cached copy is stale. Harmless today (pointer never reads those
   keys), but it's a latent coupling — two services now co-own one JSON document with
   independent caches.

**Impact today:** low — configure is an owner-only, infrequent operation and there's no
production data. **Recommendation:** at minimum document that the manifest is now
co-owned and mutable; ideally move inbox config to its **own** file
(`inbox-config.json` / `append-config.json`) next to the manifest, gated by the same
write-key, so the two services don't share a mutable document. This also makes the
append feature self-contained for the sgit migration.

#### N-1 (NOTE, by-design but document it) — `append` / `list` / `fetch` / `mark-processed` require **no SGraph access token**

Only `configure` and `purge` call `_check_access_token`. `append` is therefore an
**account-less write surface**: anyone on the internet who learns a valid
`append_token` can write up to `INBOX_MAX_FILES` × `APPEND_MAX_PAYLOAD` (1000 × 5 MB =
**5 GB**) per token, with no SGraph Send account. That is the *intended* model (external
senders must be able to post without an account), and the per-token caps bound it — but
it should be **explicitly documented** as a deliberate trade-off, because it's the one
place the API accepts unauthenticated writes. Worth a line in the reality doc's security
section and in the cross-team brief.

#### N-2 (NOTE, minor) — fragile base-path derivation in `inbox_list`

`Service__Vault__Inbox.py:142`: `path__vault_inbox_prefix(vault_id, '')[:-1]` builds the
all-folders scan base by passing an empty token (yielding `.../inbox//`) then stripping
one char. It works, but it's brittle — a dedicated `path__vault_append_base(vault_id)`
helper (which the rename plan already proposes) is the clean replacement. Fold it in.

## Part 3 — The `append` rename proposal

**I agree with the rename and the move into `bare/`.** "Inbox" over-specifies one use
case; the server genuinely provides a generic, gate-controlled, append-only storage
lane, and the same primitive backs logs, signals, control flows, and Email-FS-lite. The
four-tier model and the verbs (`configure` / `write` / `list` / `fetch` /
`mark-processed` / `purge`) describe storage, not messaging — naming should too.

Three corrections before it ships:

### C-1 — The path prefix in the plan is wrong

The implementation plan (and my earlier cross-team brief) write the path as
`transfers/vault/{vid}/bare/append/...`. The **actual** layer (Storage__Paths.py:48-49)
is `{_ROOT}/vault/{vault_id[:2]}/{vault_id}/inbox/...` — prefix is `vault/`, **not
`transfers/vault/`**, and there's a `{vault_id[:2]}` shard segment. The correct new
path is:

```
{_ROOT}/vault/{vault_id[:2]}/{vault_id}/bare/append/{token}/pending/{file}
{_ROOT}/vault/{vault_id[:2]}/{vault_id}/bare/append/{token}/processed/{file}
```

Fix this in the plan and the brief, and double-check `path__vault_append_base` returns
the sharded form too.

### C-2 — Be explicit that `bare/append/` is NOT in the commit DAG

This is the subtle part. Today the inbox sits at `vault/xx/id/inbox/` — *outside*
`bare/`, so sgit never sees it. Moving it to `bare/append/` puts it in the same
namespace as `bare/data/` (sgit's object store). That's intentional (so sgit can
*manage* it), **but** the dev brief is emphatic that the inbox is *outside version
control by design*. Those reconcile only if we state the rule plainly:

> `bare/append/` is a **managed-but-unversioned** lane. sgit knows about it (clone/
> pull/push can sync it) but it is **not reachable from commits** and **not part of the
> object DAG**. Append entries are timestamp-named `.enc` files, not content-addressed
> CAS objects.

Verify the placement is safe against the pointer service: `list_files` skips anything
without a `/payload` suffix (append files end in `.enc`, so they're skipped ✓), and
`delete_vault` blanket-deletes the whole vault prefix (append files included ✓). Both
behave correctly, but add a regression test asserting `list_files` never returns append
entries.

### C-3 — Rename the typed primitives too, and fix M-1/L-1/L-2 in the same pass

The plan renames services/routes/constants but doesn't list the schema files. Include:

- `Safe_Str__Vault__Inbox__File_Id` → `Safe_Str__Vault__Append__File_Id`
- (`Safe_Str__Vault__Append_Token` already has the right name — keep it.)

And since the rename touches every line of this service anyway, land **M-1** (incremental
ceiling check), **L-1** (validate stored hashes), and **L-2** (split inbox config into
its own file) in the same commit — they're all in the files being rewritten, and L-2 in
particular makes the feature self-contained right when sgit is about to depend on it.

Everything else in the plan (8-phase order, alias bridge, verification grep, "no data
migration") is sound. The alias bridge in Phase 1 is the right call to keep tests green
mid-rename.

---

## Recommended order

1. **M-1** — incremental ceiling check (medium availability fix).
2. **C-1** — correct the path prefix in plan + brief.
3. Execute the rename per the 8-phase plan, folding in **C-2** (DAG note + regression
   test), **C-3** (schema renames), **L-1** (hash validation), **L-2** (own config file).
4. **N-1 / N-2** — document the account-less write surface; replace the fragile base-path
   derivation with `path__vault_append_base`.

None of these change the API shape or the four-tier model. They harden an already-sound
implementation and make the `append` primitive clean for the sgit handoff.
