## Feature: vault-embed postMessage Handshake

### Architecture Assessment

The embed flow is cleanly decomposed:
- **`embed-protocol.js`** — Pure, DOM-free module. Contains only message shape definitions and origin validation logic. No side effects. Globally available as `globalThis.EmbedProtocol` (following the existing loader module pattern). Loaded before `app-shell.js` in `en-gb/app/index.html`.
- **`app-shell.js`** — Minimal integration surface: `_initEmbed` (the embed boot path), `_initWithKey` (gated for embed mode to skip persistence).

The separation mirrors the existing pattern for `AppPermissions`, `AppHudConfig`, `AppNavHelpers`, and `AppFrameBootstrap` — pure modules tested in Node, wired into the shell for browser execution. Consistent.

### Protocol Correctness

The three-message handshake is sound:

1. **`vault-embed-ready`** — iframe signals it is listening. One-shot: removed once the parent responds.
2. **`vault-open`** — parent sends key + optional mode + optional deepLink. Parsed and validated by `parseOpenMessage`.
3. **`vault-ready`** — iframe signals the vault is interactive (vaultName, fileCount, hasApp).

The one-shot listener is the right design: a misbehaving parent cannot re-key mid-session. The `event.source === window.parent` check correctly rejects sibling iframes in a multi-iframe page.

### Security Surface

**Key isolation is verified:** The browser integration test explicitly checks that `sg-vault-key` is absent from both `localStorage` and `sessionStorage` of the iframe. This test caught a real storage leak in the initial implementation (`_initWithKey` was persisting key for reload recovery; the embed gate was missing). The fix is correct: `if (this._embedMode) return` before any storage writes in `_initWithKey`.

**deepLink storage leak** (fix `84ba117`): The initial implementation wrote `deepLink` to `sessionStorage` via a try/catch. In null-origin App Iframes, `sessionStorage` access throws `SecurityError` — the catch swallowed it, the subsequent read also threw, and the embed silently landed on `home/index.html` instead of the requested target. Fix: store `_embedDeepLink` on the instance; `_continue` prefers it. The instance-memory path is one-shot (cleared after read), which is correct behaviour.

**`_setCachedAccessKey` gap** (fix `159ec76`): An audit of all storage writes reachable from `_initEmbed` found one ungated write. The `sg-app-perm-ok:*` write (line 828) was also identified as theoretically reachable but unreachable in practice (consent prompt not auto-invoked by the open path). The audit is documented in the commit. The one unguarded-but-unreachable case is noted; a future authed-vault embed test would catch it.

### Origin Policy Assessment

The current default — accept any origin when `?parent=<origin>` is not specified — is reasonable for the primary use case (null-origin App Iframe embedders do not have a real origin to specify). The `event.source === window.parent` check prevents sibling-iframe confused-deputy attacks. The authoring note recommends using `targetOrigin=vault-origin` (not `'*'`) for real-origin parents; for null-origin parents `'*'` is technically unavoidable and safe given the source-window check. The open question OQ-embed-cross-origin-1 tracks updating the authoring note.

## Fix: `typeof caches` Sandbox Safety

### Root Cause

`typeof` in JavaScript only suppresses `ReferenceError` for genuinely undeclared identifiers. `window.caches` is a defined property accessor in all modern browsers. In sandboxed iframes without `allow-same-origin`, reading the `caches` accessor throws `SecurityError`. This is spec-correct behaviour (the spec explicitly states the accessor throws in non-secure contexts). The fix is minimal and correct: move the guard inside the `try`.

### Verification Quality

The regression test (`4b2a4bf`) is the right design: it sets up the exact failing condition (sandbox=`allow-scripts`, no `allow-same-origin`), waits for `vault-ready` (which would time out pre-fix), and also checks that `typeof caches` actually throws in the iframe (pinning the precondition — if a future browser changed sandbox behaviour, the test would fail loudly rather than passing vacuously).

The test author noted that the cross-origin iframe drill (`iframe.contentDocument` access) is intentionally skipped for sandboxed iframes because that access is itself blocked by the sandbox — the `vault-ready` signal is sufficient proof of vault-open success.

### Bundle Rebuild

The bundle freshness check failing in CI (`8bccfdc`) is a known footgun: editing any file in `build-kernel-shell-bundle.py`'s `SCRIPTS` list requires re-running the build script. The commit message notes this correctly and mentions a pre-commit hook as a future improvement. No action needed now.

## Mobile Audit (docs only)

The 06/07 audit documents (`bfb41e2`) are referenced here but not code. The 4-phase fix plan from the Dev review:

1. **Phase 1 (CSS-only wins):** Add `@media (max-width: 768px)` rules to `vault-shell.css`, `vault-tree.css`, `vault-preview.css`. Estimated: 1 session, low risk.
2. **Phase 2 (sg-layout reconfiguration):** Make `<sg-layout>` collapse to a single-panel view on narrow viewports; swipe or tab-switch between panels. Medium risk (touches the layout component shared with `/app`).
3. **Phase 3 (mobile chrome):** Floating action buttons, bottom nav bar, touch targets ≥44px.
4. **Phase 4 (scope reduction):** Consider whether `/vault` and `/app` should merge into a unified responsive shell.

Phases 1–2 are the recommended near-term focus. Phase 3 and 4 depend on UX decisions (OQ-mobile-vault-fix-sequence-1).
