## 1. sg.* convention conformance (the explicit ask)

Audited the existing `sg.*` surface (`app-shell.js:1857–1924`). The conventions, and how each new method conforms:

### 1.1 The conventions in force

| # | Convention | Evidence |
|---|---|---|
| **A — arg shape** | Fixed small arity → **positional**; optional/rich/extensible → **trailing `opts` object**; none → `()`. | `fs.move(from,to)`, `vault.unlink(path)`, `auth.setKey(key)` (positional); `vault.mount(opts)`, `ui.message(text,type,opts)` (trailing opts); `vault.mounts()`, `sync.push()` (none). |
| **B — action === grant act** | Bridge `action:'X'` ↔ `_can('vault.X')` ↔ `perm.vault.X`. | `action:'create'`→`_can('vault.create')`→`perm.vault.create` (L2305); `action:'mount'`→`vault.mount` (L2336). |
| **C — return shape** | Promise resolving to the `result` object from `cmdReply(true, result)`; rejects `new Error(err)`. | `_sgCmd` (L1848–1856). |
| **D — payload flattening** | The iframe stub **flattens** opts fields into the `_sgCmd` payload — it does not nest an `opts` object. | `mount:function(opts){return _sgCmd("vault",{action:"mount",prefix:opts&&opts.prefix,ref:opts&&opts.ref,label:opts&&opts.label});}` (L1872). |
| **E — naming** | lowerCamelCase methods; grouped namespaces (`vfs`/`fs`/`vault`/`history`/`sync`/`auth`/`ui`/`state`). | `setKey`, `readText`, `requestPermission`, `readBlob`. |

### 1.2 New methods, conformed

| New method | Arg shape (Conv A) | Grant act (Conv B) | Stub flattening (Conv D) | Notes |
|---|---|---|---|---|
| `sg.vault.create(opts)` | trailing opts (rich) — matches `mount(opts)` | `vault.create` / `vault.createKey` | flatten `label,link,returnKey,seedFrom,custody` | was `create(path,label)`; opts is correct for the extensible shape |
| `sg.vault.openApp(ref, opts)` | positional + trailing opts — matches `ui.message` | `vault.openApp` | flatten `deepLink,target` | **grant renamed** brief `open` → `openApp` to satisfy Conv B (action===act) |
| `sg.vault.getKey(ref)` | single positional — matches `unlink(path)` | `vault.createKey` (key-retrieval == key-power) | n/a | always-confirm consent |
| `sg.vault.list()` | none — matches `mounts()` | — (reads own tree) | n/a | |
| `sg.vault.delete(ref)` | single positional — matches current `delete(path)` | `vault.delete` | n/a | now **enabled** via owner-secret store (§6) |
| `sg.vault.unlink(path)` | unchanged | `vault.unlink` | n/a | kept |

**One naming fix vs the brief:** the brief proposed method `openApp` with grant `open`. That violates Conv B (every other vault verb's action name equals its grant act). I unify to **`openApp` for both** the method and the grant act. `app.json` uses `"openApp": true`, not `"open"`.

**One signature break (intentional, per "don't worry about backward compatibility"):** `create(path,label)` → `create(opts)`. Grep `sg.vault.create(` before merging C-create to migrate any in-tree consumer to `create({ link:{path}, label })`.

## 2. ⚠ Correctness catch — return `passphrase:vault_id`, not the bare passphrase

`SGVault.create` (`sg-vault.js:45`) takes a *passphrase* and **separately generates** the `vault_id` (L49–52). The openable artifact is the **full vault key** `{passphrase}:{vault_id}` parsed by `parseVaultKey` (`sg-vault-crypto.js:32`):

```
parseVaultKey('k3x9...')            → parts.length < 2 → THROWS
parseVaultKey('k3x9...:ab12cd34')   → { passphrase:'k3x9...', vaultId:'ab12cd34' } ✓
```

The bare `_genVaultPassphrase()` value has no colon and isn't a simple-token, so `SGVault.open(bare)` throws. **The returned/custodied key MUST be:**

```js
const key = child._passphrase + ':' + child._vaultId;
```

(`SGVault.create` stores `vault._passphrase = passphrase` at L47, so both halves are on the returned `child`.) Acceptance #1 only passes with the composed form — tests assert `SGVault.open(sgSend, key)` succeeds and `writable === true`.

## 3. Owner-secret store (build now — Q1)

A kernel-held credential tier for secrets only the **owner** (parent-vault write-key holder) can read — distinct from the read-tier `ro-links.json` (readable by any parent reader). This is where a managing Vault App's child write-keys are custodied, and it's the missing piece that also unblocks `vault.delete`.

### 3.1 Tier property

| Tier | Encrypted under | Who can read |
|---|---|---|
| read-tier (`ro-links.json`, exists) | `read_key` | anyone with the parent vault's `read_key` (incl. RO-token holders) |
| **owner-tier (`secrets/`, new)** | key derived from `write_key` | only parent-vault **write_key** holders — RO sessions (`write_key = null`) **cannot decrypt** |

This falls straight out of the verified key model: `write_key` is present only for writable sessions, so deriving the secret-store key from it gives owner-only custody for free.

### 3.2 Module: `_common/js/lib/sg-vault/sg-vault-owner-secrets.js` (new, pure)

```js
globalThis.SGVaultOwnerSecrets = {
  // derive the AES-GCM secret-store key from the parent vault's write_key (hex string)
  async deriveKey(writeKeyHex) {
    const material = await crypto.subtle.importKey('raw',
      new TextEncoder().encode(writeKeyHex), 'HKDF', false, ['deriveKey']);
    return crypto.subtle.deriveKey(
      { name:'HKDF', hash:'SHA-256', salt:new Uint8Array(0),
        info:new TextEncoder().encode('sg-vault-v1:owner-secret-key') },
      material, { name:'AES-GCM', length:256 }, false, ['encrypt','decrypt']);
  },
  async seal(key, obj)   { /* AES-GCM encrypt JSON → { iv, ct } (base64) */ },
  async open(key, rec)   { /* AES-GCM decrypt → obj */ }
};
```

Pure (Web Crypto only, no DOM), Node-testable like `app-permissions.js`.

### 3.3 Storage

`.vault/owner/secrets/<ref_id>.json` = `{ iv, ct }` where plaintext = `{ vault_id, key, label, created }`.

- Under `.vault/**` → **floored** from iframe bridge access (`isFloor`, `app-permissions.js:58`).
- Encrypted under the owner-tier key → unreadable even to RO-token holders.
- Committed to the parent tree → travels with the vault, survives clone (the owner re-derives the secret-store key from their write_key on open).

### 3.4 Kernel helpers (on `app-shell`, not exposed raw to apps)

```js
async _ownerSecretKey()              // cache: SGVaultOwnerSecrets.deriveKey(this._vault.writeKeyHex)
async _ownerSecretPut(refId, secret) // seal + saveFile('.vault/owner/secrets', refId+'.json', ...)
async _ownerSecretGet(refId)         // readFile + open → { vault_id, key, label }
async _ownerSecretList()             // list the secrets dir → [{ ref_id, vault_id, label }] (no keys)
async _ownerSecretRemove(refId)      // deleteFile
```

Requires a `writeKeyHex` getter on `SGVault` (the inbox plan adds the same getter — share it). In RO sessions `_ownerSecretKey()` throws `EREADONLY` → secret ops unavailable, as intended.

## 5. `_createChildVault(opts)` refactor + custody

```js
// opts = { label, link:{path}|false, returnKey:bool, custody:bool, standalone:bool, seedFrom }
async _createChildVault(opts) {
    var parentVault = this._vault, sgSend = parentVault && parentVault._sgSend;
    if (!sgSend || typeof SGVault === 'undefined') throw new Error('Cannot create vaults here');
    var label     = String(opts.label || 'vault');
    var wantsLink = !!(opts.link && opts.link.path != null);
    var wantsKey  = !!opts.returnKey;
    var custody   = opts.custody !== false;                 // default: kernel custodies the key
    if (!wantsLink && !wantsKey && !custody) { var e = new Error('unreachable vault'); e.code = 'EINVAL'; throw e; }

    var passphrase = this._genVaultPassphrase();            // unchanged generator (strong shape)
    var child      = await SGVault.create(sgSend, passphrase, { name: label });
    var vaultId    = child._vaultId;
    var key        = child._passphrase + ':' + child._vaultId;   // §2 composed openable key
    var refId      = this._genRefId();

    if (opts.seedFrom) await this._seedVaultTree(child, opts.seedFrom);

    var result = { vault_id: vaultId, ref_id: refId };

    if (custody) await this._ownerSecretPut(refId, { vault_id: vaultId, key: key, label: label, created: Date.now() });

    if (wantsLink) {
        // …existing read-through wiring: <slug>.link.json + VaultLinks.saveRoRecord (read-tier)…
        result.ref_file_id = child._refFileId;
    }
    if (wantsKey) result.key = key;                         // raw key returned only on demand
    return result;
}
```

- **`custody` defaults on** — the managing-app use case wants the kernel to hold the key (owner-tier). `returnKey` is *additional* (hand the raw key to the app to re-share). An app can do both, either, or — with `custody:false, returnKey:true` — take the key and decline kernel custody.
- **Standalone** = `wantsLink` false → skip the link/ro-record entirely; the parent tree is untouched **except** the owner-secret (which lives under `.vault/owner/secrets/`, owner-tier, and is the intended custody record). If an app wants a *truly* untouched parent, it passes `custody:false` too and takes the key via `returnKey`.
- The composed key escapes the kernel only via the owner-secret store (sealed) and the `returnKey` result.

## 6. `vault.delete` — now enabled (§3 unblocks it)

The previous `ENOTIMPL` (bridge L2321–2328) existed because *"there is no owner-secret tier to store the child WRITE key."* §3 builds exactly that tier.

```js
async _deleteChildVault(refId) {
    var secret = await this._ownerSecretGet(refId);        // { vault_id, key } — owner-tier
    if (!secret) { var e = new Error('no key on file for ' + refId); e.code = 'ENOKEY'; throw e; }
    var child = await SGVault.open(this._vault._sgSend, secret.key);   // writable (has write_key)
    await child.destroy();                                  // server destroy with write_key authorization
    await this._ownerSecretRemove(refId);
    // also remove any *.link.json in the tree carrying this ref_id (best-effort)
    return { deleted: true, vault_id: secret.vault_id };
}
```

- **Gated** by `vault.delete` (bool) + **always-confirm consent** (already the rule at `_consent` L824 for `vault.delete` — irreversible).
- Needs a `SGVault.destroy()` (server-side vault teardown with write_key). **Confirm this server endpoint exists**; if not, it is the one server dependency of this plan — flag to the SG API team. (Everything else is client-side.)
- AppSec sign-off on the destructive path, as the original deferral required.

## 7. `getKey` / `openApp` / `list`

```js
// Retrieve a custodied key to re-share. As powerful as createKey → same grant + always-confirm.
async _getVaultKey(refId) {
    var secret = await this._ownerSecretGet(refId);
    if (!secret) { var e = new Error('no key on file'); e.code = 'ENOKEY'; throw e; }
    return { key: secret.key };
}

// Launch a vault as an app. ref → resolve key from owner-secret store (key never crosses the
// iframe boundary); raw key → use directly (app already holds read+write authority by possession).
async _openAppVault(ref, opts) {
    opts = opts || {};
    var key = (ref && ref.indexOf(':') > -1) ? ref : (await this._ownerSecretGet(ref) || {}).key;
    if (!key) { var e = new Error('cannot resolve key for ' + ref); e.code = 'ENOKEY'; throw e; }
    var url = location.origin + '/en-gb/app/#' + encodeURIComponent(key) +
              (opts.deepLink ? ('/' + String(opts.deepLink).replace(/^\//, '')) : '');
    if (opts.target === 'replace') { location.href = url; return { opened:'replace' }; }
    if (opts.target === 'embed')   { var e = new Error('embed deferred'); e.code = 'ENOTIMPL'; throw e; }  // embed-loader brief
    window.open(url, '_blank'); return { opened:'tab' };
}

// Roster: custodied secrets (owner-tier) ∪ read-through links (read-tier).
async _listChildVaults() {
    var rows = await this._ownerSecretList();              // [{ ref_id, vault_id, label }] tier rw
    return rows.map(function (r){ return { ref_id:r.ref_id, vault_id:r.vault_id, label:r.label, tier:'rw' }; })
               .concat(this._collectReadLinks());          // *.link.json without a secret → tier ro
}
```

- `openApp` gated by `vault.openApp` (bool, Q3 — no per-call consent). `embed` target → `ENOTIMPL`, pending the [embed-loader brief](https://github.com/the-cyber-boardroom/sgraph-ai__app__send/blob/claude/zealous-thompson-yDjFX/team/comms/briefs/06/07/v0.33.5__brief__vault-embed-loader-relay-for-inbox-notify.md).
- `getKey` gated by `vault.createKey` + always-confirm consent (retrieving a key is as powerful as minting one with returnKey).

## 8. `seedFrom` (Q4 locked)

`_seedVaultTree(childVault, source)` copies a template tree into the freshly-created writable child.

- `source = 'self:<path>'` → read a folder in THIS vault. Gated by `_can('vault.seedFrom', '<path>')`.
- `source = '<ref_id>'` → resolve via owner-secret/ro-record. Gated by `_can('vault.seedFrom', '<ref_id>')`.
- `source = '<raw key>'` (has `:`) → open read-only and copy. **Possession sufficient — no grant check** (Q4: the app already has read authority by holding the key).
- **Floor:** `_collectTree` skips any path with a `.vault` segment (`AppPermissions.hasVaultSegment`) — a template copy can never exfiltrate owner secrets. **Hard requirement.**
- `app.json` copies like any other file. The root-`app.json` write floor guards *iframe input*, not kernel-mediated writes via `childVault.saveFile` — call this out to AppSec as intentional.

## 12. Security analysis

| Concern | Mitigation |
|---|---|
| App custodies keys in readable app-data | **Solved by §3** — kernel custodies them owner-tier (encrypted under write_key-derived key, floored from iframes). RO-token holders cannot decrypt. The app holds opaque refs, not keys, unless it explicitly `getKey`s. |
| Managing app *can still* request the raw key | Intended — it's the special-case app. `returnKey`/`getKey` gated by the stronger `createKey` grant + always-confirm consent. |
| Key logged in telemetry | Never — `returnedKey:bool` only (§9). Hard requirement. |
| seedFrom exfiltrates owner secrets | `_collectTree` skips `.vault/**` (§8). Hard requirement. |
| Kernel-mediated writes vs the iframe floor | Floor guards iframe input; kernel writes (seed, owner-secret) are trusted. Called out for AppSec. |
| `vault.delete` destructive endpoint | Always-confirm consent + AppSec sign-off + relies on `SGVault.destroy()` server path (confirm exists). |
| Simple-token weakness | Not reachable from any creation path (Q5). Verified property for AppSec. |
