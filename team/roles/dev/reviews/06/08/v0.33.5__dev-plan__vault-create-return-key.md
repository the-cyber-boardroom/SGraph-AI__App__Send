## 2. ⚠ Correctness catch — the returned key must be `passphrase:vault_id`, not the bare passphrase

The brief says (§3.1, §4): *"return the full high-entropy write key (the `_genVaultPassphrase` value)."* **Returning that bare value would not open the vault.**

`SGVault.create` (`sg-vault.js:45`) takes a *passphrase* and **separately generates** the `vault_id` (L49–52). The openable artifact is the **full vault key** `{passphrase}:{vault_id}`, parsed by `parseVaultKey` (`sg-vault-crypto.js:32`):

```
parseVaultKey('k3x9...'):           → parts.length < 2 → THROWS "Invalid vault key format"
parseVaultKey('k3x9...:ab12cd34'):  → { passphrase:'k3x9...', vaultId:'ab12cd34' } ✓
```

The bare `_genVaultPassphrase()` value has no colon and isn't a simple-token, so `SGVault.open(barePassphrase)` throws. **The returned `key` MUST be composed:**

```js
const key = child._passphrase + ':' + child._vaultId;   // the openable full vault key
```

This is the single most important correctness point in the whole change. Acceptance criterion #1 ("a valid high-entropy key that opens the new vault read+write") **only passes** if we return the composed form. Add a round-trip assertion in tests: `SGVault.open(sgSend, returnedKey)` succeeds and `vault.writable === true`.

(`SGVault.create` already stores `vault._passphrase = passphrase` at L47, so both halves are available on the returned `child` object.)

### 3.2 `can` — extend the vault branch

```js
if (grp === 'vault') {
    if (act === 'delete')     return perm.vault['delete'] === true;
    if (act === 'standalone') return perm.vault.standalone === true;
    if (act === 'open')       return perm.vault.open === true;
    return _match(perm.vault[act], path);   // create, createKey, seedFrom, unlink, mount

```

`createKey` and `seedFrom` are path-prefix grants (use existing `_match`). `standalone` and `open` are booleans (like `delete`). Default-deny throughout — absent grant → `_match(undefined, ...)` → `false`.

### 3.3 The grant relationship (brief §5, locked)

| App holds | `returnKey:true`, `link:{path}` | `returnKey:true`, no `link` (standalone) |
|---|---|---|
| `create` only | `EPERM` (create never yields a key) | `EPERM` |
| `create` + `createKey:[path]` | ✓ link + return key | `EPERM` (needs `standalone`) |
| `create` + `standalone` | `EPERM` (createKey covers linked path) | ✓ standalone + return key |
| `createKey:[path]` + `standalone` | ✓ | ✓ |

**`createKey` is strictly stronger than `create` and never implied by it.** A plain `create` grant must never return a key. `standalone` implies key-return (a keyless unlinked vault is unreachable — brief §4 table row 4 → `EINVAL`).

## 4. `_createChildVault` refactor (`app-shell.js:866`)

Change the signature from `(path, label)` to `(opts)` matching the brief's API. Keep a thin back-compat shim so existing callers (if any in-tree) don't break — though the only caller is the bridge, which we update in lockstep.

```js
// opts = { label, link: {path}|false, returnKey:bool, standalone:bool, seedFrom:string }
async _createChildVault(opts) {
    var parentVault = this._vault;
    var sgSend = parentVault && parentVault._sgSend;
    if (!sgSend || typeof SGVault === 'undefined') throw new Error('Cannot create vaults here');

    var label    = String(opts.label || 'vault');
    var wantsLink = !!(opts.link && opts.link.path != null);
    var wantsKey  = !!opts.returnKey;

    // brief §4 table row 4: keyless standalone is unreachable
    if (!wantsLink && !wantsKey) { var e = new Error('standalone create needs returnKey'); e.code = 'EINVAL'; throw e; }

    // 1. Mint the vault (always high-entropy; generator unchanged)
    var passphrase = this._genVaultPassphrase();
    var child      = await SGVault.create(sgSend, passphrase, { name: label });
    var vaultId    = child._vaultId;

    // 2. Optional seed (template copy) — BEFORE wiring the link so the link sees a populated tree
    if (opts.seedFrom) await this._seedVaultTree(child, opts.seedFrom);

    var result = { vault_id: vaultId };

    // 3. Optional parent-tree wiring (today's read-through link + ro-record)
    if (wantsLink) {
        var refId = this._genRefId();
        var dir   = opts.link.path ? ('/' + AppPermissions.normalizePath(opts.link.path)) : '/';
        if (dir !== '/' && !parentVault.listFolder(dir)) { try { await this._dataSource.createFolder(dir); } catch (_) {} }
        var fileName = this._slugify(label) + '.link.json';
        await this._dataSource.saveFile(dir, fileName,
            new TextEncoder().encode(JSON.stringify({ vault_id: vaultId, ref_id: refId, label: label }, null, 2)).buffer);
        var rawRk  = new Uint8Array(await crypto.subtle.exportKey('raw', child._readKey));
        await VaultLinks.saveRoRecord(parentVault, refId,
            { type: 'vault', label: label, pin: { mode: 'latest' }, vault_id: vaultId,
              read_key: btoa(String.fromCharCode.apply(null, rawRk)), ref_file_id: child._refFileId });
        if (this._dataSource.scan) { try { await this._dataSource.scan(); } catch (_) {} }
        result.ref_id = refId;
        result.ref_file_id = child._refFileId;
    }

    // 4. Optional key return (THE openable composed form — see §2)
    if (wantsKey) result.key = child._passphrase + ':' + child._vaultId;

    return result;
}
```

Notes:
- **Standalone = skip step 3 entirely.** No `.link.json`, no ro-record, no `scan()`. The vault exists on the server with its initial commit; the parent tree is untouched (brief §3.2, acceptance #2).
- The composed key (step 4) is the only place the passphrase escapes. Everywhere else it's discarded as before.
- `seedFrom` runs before linking so a linked+seeded vault shows its template immediately.

## 5. `_seedVaultTree(childVault, source)` — new helper

Copies a template tree into the freshly-created (writable) child. The kernel holds the child's write capability (the `child` object from `SGVault.create` has `_writeKey`), so it can write + commit.

```js
// source: 'self:<path>'  → a folder in THIS vault
//         '<ref_id>'      → a linked child the app may read (resolve via VaultLinks)
//         '<key>'         → a full vault key the app supplied (open read-only)
async _seedVaultTree(childVault, source) {
    var entries;   // [{ relPath, bytes }]
    if (source.indexOf('self:') === 0) {
        var srcDir = AppPermissions.normalizePath(source.slice(5));
        // floor: never copy out of .vault/** (isFloor guards each file)
        entries = await this._collectTree(this._dataSource, srcDir);   // skips .vault/**
    } else {
        var srcVault = await this._resolveReadableVault(source);       // ref_id or key → read-only SGVault
        entries = await this._collectTree(srcVault, '');
    }
    for (var i = 0; i < entries.length; i++) {
        var slash = entries[i].relPath.lastIndexOf('/');
        var dir   = slash > 0 ? '/' + entries[i].relPath.slice(0, slash) : '/';
        var name  = entries[i].relPath.slice(slash + 1);
        await childVault.saveFile(dir, name, entries[i].bytes);        // childVault is writable
    }
    await childVault.commit('Seed from ' + source);
}
```

- **Floor enforcement:** `_collectTree` must skip any path with a `.vault` segment (reuse `AppPermissions.hasVaultSegment`) so a template copy can never exfiltrate owner secrets. This is a **hard requirement** — add it to the AppSec review.
- `seedFrom` is gated by `_can('vault.seedFrom', sourcePathOrRef)` (brief §5). For `self:<path>`, the grant path is the `<path>`; for a ref/key, the grant must list that ref (path-grant against the ref string).
- `app.json` is part of the template (brief §4 `seedFrom` note + acceptance #5): copy it like any other file — but note the **root `app.json` write floor** (`isFloor('write','app.json')` → true at `app-permissions.js:62`). Since we're writing to the *child* vault via `childVault.saveFile` (not the bridge), the floor doesn't apply — the floor guards the *iframe bridge*, not the kernel's own writes. Confirm this distinction in the AppSec review: kernel-mediated seed writes are trusted; the floor is an iframe-input guard.

## 6. Supporting bridge primitives (brief §4)

### 6.1 `sg.vault.openApp(keyOrRef, opts)` — `_openAppVault`

The missing "open a vault as an app from inside an app" primitive. Gated by `vault.open` (bool).

```js
async _openAppVault(keyOrRef, opts) {
    opts = opts || {};
    var key = await this._resolveKey(keyOrRef);          // ref_id → stored key (if app holds it) | passthrough key
    var url = location.origin + '/en-gb/app/#' + encodeURIComponent(key) +
              (opts.deepLink ? ('/' + opts.deepLink.replace(/^\//, '')) : '');
    if (opts.target === 'replace') { location.href = url; return { opened: 'replace' }; }
    if (opts.target === 'embed')   { throw Object.assign(new Error('embed target deferred'), { code: 'ENOTIMPL' }); }
    window.open(url, '_blank');                            // default: 'tab'
    return { opened: 'tab' };
}
```

- **v1 ships `tab` and `replace`.** `embed` is **deferred** — it depends on the embed-loader relay in [`v0.33.5__brief__vault-embed-loader-relay-for-inbox-notify.md`](https://github.com/the-cyber-boardroom/sgraph-ai__app__send/blob/claude/zealous-thompson-yDjFX/team/comms/briefs/06/07/v0.33.5__brief__vault-embed-loader-relay-for-inbox-notify.md). Returning `ENOTIMPL` for `embed` keeps the API stable.
- `openApp` does **not** require consent per-call in v1 (it opens a vault the app already has a key/ref for — no new privilege escalation; it's navigation). Flag for AppSec: should opening a *new* tab/replacing the page be consent-gated? Recommend a one-time consent like `create`.

### 6.2 `sg.vault.list()` — `_listChildVaults`

Enumerate the `*.link.json` pointers in this vault's tree + their ro-records, for rebuilding a roster.

```js
async _listChildVaults() {
    var out = [], files = this._collectLinkFiles(this._vault);   // walk tree for *.link.json
    for (var i = 0; i < files.length; i++) {
        var rec = await VaultLinks.loadRoRecord(this._vault, files[i].ref_id).catch(function () { return null; });
        out.push({ ref_id: files[i].ref_id, vault_id: files[i].vault_id, label: files[i].label,
                   tier: rec && rec.write_key ? 'rw' : 'ro' });
    }
    return out;
}
```

No new grant needed — listing pointers the app can already read in the tree exposes nothing new. (Reads obey the existing floor; `.vault/**` is never walked.)

### 6.3 `sg.vault.mount({ key|ref, prefix, mode:'rw' })` — writable mount

The existing `_mountChildVault` (bridge L2331–2344) is **read-through only**. The brief asks for a writable mount by key. This is the **most involved** piece:

- A writable mount needs the child's *write key* threaded into the mount's data source (the current read mount uses only the read key from the ro-record).
- The app supplies the key (from a prior `returnKey` create). The kernel opens the child writable via `SGVault.open(sgSend, key)` and wraps it as a writable mount data source.
- Gated by `vault.mount` for the prefix **plus** possession of a valid key (the key is the write capability — no separate grant needed beyond `mount`).

**Recommendation: stage `mount:'rw'` as Phase D** (after the create/key/standalone/seedFrom core lands). It's orthogonal to the brief's primary ask (return-the-key) and carries the most risk. The doctor/patient MVP can use `returnKey` + `openApp` without rw-mount for the first iteration.

## 7. Bridge dispatch changes (`app-shell.js:2303`)

Replace the `create` branch and add the new actions. The key change: parse the full `opts` object and apply **the stronger consent** for key-return.

```js
if (vAct === 'create') {
    var cOpts = {
        label:      String(e.data.label || 'vault'),
        link:       e.data.link,                       // {path} | false | undefined
        returnKey:  e.data.returnKey === true,
        standalone: !(e.data.link && e.data.link.path != null),
        seedFrom:   e.data.seedFrom
    };
    var linkPath = (e.data.link && e.data.link.path != null) ? AppPermissions.normalizePath(e.data.link.path) : '';

    // ── permission gates ──────────────────────────────────────────
    // base create grant for linked creates; standalone grant for unlinked
    if (cOpts.link && cOpts.link.path != null) {
        if (!self._can('vault.create', linkPath)) return denyEPERM('vault.create', linkPath);
    } else {
        if (!self._can('vault.standalone', '')) return denyEPERM('vault.standalone', '');
    }
    // returnKey requires the stronger grant
    if (cOpts.returnKey) {
        var keyOk = (cOpts.link && cOpts.link.path != null)
            ? self._can('vault.createKey', linkPath)
            : self._can('vault.standalone', '');     // standalone implies key-return
        if (!keyOk) return denyEPERM('vault.createKey', linkPath);
    }
    // seedFrom requires its own grant
    if (cOpts.seedFrom && !self._can('vault.seedFrom', _seedGrantPath(cOpts.seedFrom))) {
        return denyEPERM('vault.seedFrom', cOpts.seedFrom);
    }

    // ── consent ───────────────────────────────────────────────────
    // key-return ALWAYS re-confirms (brief §3.5); plain create one-time cached.
    var consentVerb = cOpts.returnKey ? 'vault.createKey' : 'vault.create';
    self._consent(consentVerb, linkPath).then(function (ok) {
        if (!ok) { cmdReply(false, null, 'Consent declined'); return; }
        return self._createChildVault(cOpts).then(function (res) {
            cmdReply(true, res);
            // NEVER log the key in the bridge-call telemetry
            self._emitBridgeCall('vault.create', { path: linkPath, ok: true, vault_id: res.vault_id, returnedKey: !!res.key, standalone: !cOpts.link });
        });
    }).catch(function (err) { cmdReply(false, null, err.message); });
    return;
}
```

Add the always-confirm rule to `_consent` (L824):

```js

```

And the HUD consent string (brief §3.5): *"App ‹id› wants to create a vault and receive its full key."* — add a verb→message map in `_hudConsent` / `app-hud.requestConsent`.

New `openApp` / `list` / writable-`mount` branches slot in alongside the existing `mount`/`unmount`/`mounts` actions (L2331–2356).

**Telemetry hygiene (hard requirement):** `_emitBridgeCall` and the debug pane must **never** record the returned key. Emit `returnedKey: true/false`, never the value. Add to AppSec checklist.

## 10. Security analysis

| Concern | Status / mitigation |
|---|---|
| **App now holds a write key** | The app custodies it. Inherits the readable-vault caveat: anyone who can read the app's vault can read stored child keys. For a no-PII MVP this is acceptable; document loudly. **Beyond MVP:** keys belong in a kernel-held wrapped owner-secret tier (`sg.crypto.*`/`sg.identity.*` direction) — same blocker as `vault.delete`. **Recommend building the owner-secret store next** (unblocks both this and delete), but it is **out of scope for this plan.** |
| **Key never logged** | `_emitBridgeCall`, debug pane, and any telemetry emit `returnedKey:bool` only. Hard requirement (§7). |
| **seedFrom floor** | `_collectTree` skips `.vault/**` via `hasVaultSegment`. A template copy can never exfiltrate owner secrets. Hard requirement (§5). |
| **Kernel-mediated writes vs the bridge floor** | The floor (`isFloor`) guards *iframe input*, not the kernel's own writes. Seeding `app.json` into the child via `childVault.saveFile` is a trusted kernel write — correct, but call it out for AppSec so the distinction is intentional, not accidental. |
| **Simple-token weakness** | Creation path never produces simple-token keys (`_genVaultPassphrase` guarantees the strong shape; `SGVault.create` derives via `deriveKeys`, never `deriveKeysFromSimpleToken`). The brief asks to forbid simple-token *generation* platform-wide — **note: no code in the create path generates it today**, so we're compliant. A separate hardening task could remove `deriveKeysFromSimpleToken` from any creation surface, but `open` must keep accepting it (existing vaults). Out of scope; flag to AppSec. |
| **Standalone reachability** | Standalone vaults have no parent read link — readable only via a key the app stored. Intended ("doctor keeps patient keys"). |
| **openApp navigation** | Opens a vault the app already holds a key/ref for — no new data access. Recommend one-time consent anyway (Q3). |
