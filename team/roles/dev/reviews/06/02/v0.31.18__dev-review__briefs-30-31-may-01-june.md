## Executive Dev Summary

The 19 proposed items form five build streams. Most are synthesis (reusing existing machinery in new combinations) rather than net-new infrastructure. The heaviest new build is the unified graph schema + document-to-graph pipeline (P-281/P-286/P-294/P-298) — these share a substrate and must share implementation. Three items are unblocked quick wins today: P-282 (embedded RO key), P-284 (vulnerability debriefs as vault template), P-291 (Pi bidirectional mapping). VIV browser verification and the architect's graph schema definition must precede the rest of the work.

## Stream 1: Unified Graph Schema + Pipeline (P-281, P-286, P-294, P-298)

These four items are architecturally coupled. Build with one shared schema.

### P-281 — Vault-per-Standard Document-to-Graph Pipeline

**Effort:** HIGH (3–5 days net-new + schema design time)
**Depends on:** Architect graph schema document (not yet written), VIV (P-159/P-160) for intersection vaults
**Blocks:** P-286, P-298 indirectly via schema reuse

Implementation tasks:
1. Define `StandardDocument`, `Section`, `Ruling`, `Jurisdiction`, `Provenance` node types in graph schema (JSON-LD or RDF/Turtle — architect decision).
2. Build the four-stage pipeline: raw document → structured form → semantic graph → validation.
3. Store all pipeline artefacts in the vault (raw input, LLM responses, extracted ontologies) with provenance edges.
4. Run GDPR first as the pilot standard — one vault per standard.
5. Design the intersection vault mechanism: determine whether it is a VIV sub-vault link (P-159/P-160) or a fresh vault with references. The VIV path is preferred (architect assessment).

**Key risk:** Vault size for large standards (ISO 27000 is vast). Design vault-size budget before building.

### P-286 — Per-Page Semantic Graphs + Edge Rendering

**Effort:** MEDIUM-HIGH (2–3 days after foundations verified)
**Depends on:** llms.txt edge function verified in website repo (OQ-llmstxt-edge-verify-1), graph schema from P-281, URL scheme decision
**Blocks:** nothing directly

Implementation tasks:
1. Verify llms.txt Lambda@Edge function in the website repo (cross-ref: OQ-llmstxt-edge-verify-1). If not verified, this item cannot start.
2. Decide URL scheme (`page.graph.json` vs `page.ttl`). Recommend `page.graph.json` (JSON-LD) for agent-friendliness.
3. Extend the edge function to generate and cache per-page semantic graph.
4. Generate only on content change (use vault's version control for change detection to minimise LLM cost).
5. Security: edge function must only decrypt content from public vaults (read key present); private vault content must never be served edge-side.

**Key risk:** LLM cost per page. Cache aggressively. Budget the generation cost before shipping.

## Stream 3: Partner Integrations (P-288–P-293)

### P-288 — Netlify AX Integration

**Effort:** MEDIUM (2–3 days)
**Depends on:** VIV for vault-native hosting path; website repo verification for rendered-output path
**Blocks:** nothing

Two deployment modes need separate implementation paths:
- **Mode A (rendered output):** Vault produces rendered/decrypted public content as zip → Netlify deploys zip. For public library sites.
- **Mode B (raw zip + edge rendering):** Vault deploys its encrypted zip; Netlify edge functions decrypt at request time using public read key. For vault-native hosting.

Design these as distinct deploy targets before implementation. Mode A is simpler and can ship first.
