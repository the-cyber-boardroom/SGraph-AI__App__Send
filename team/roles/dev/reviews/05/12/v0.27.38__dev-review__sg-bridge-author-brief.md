## 2. Per-ask technical assessment

### Ask 1 — `sg.vfs.write` must reject on push failure

**Diagnosis plausible?** Yes, directly confirmed in code at lines 906–912 of
`send-browse--v0.3.2.js`:

```js
_writeReply(true, { size: wBytes.byteLength });            // resolves the iframe promise FIRST
var ds = self.dataSource;
if (ds && ds.writable && ds._vault && typeof ds._vault.push === 'function') {
    ds._vault.push().catch(function(err) {
        console.warn('[sg-vfs parent] auto-push failed (non-fatal):', err);
    });
}
```

So today: local `saveFile` resolves → `_writeReply(true)` fires → `push()` is
launched fire-and-forget and its failure is swallowed to `console.warn`. The
v0.27.19 comms brief calls this out explicitly ("Failures are caught and logged
as warnings — they do **not** fail the write reply to the iframe").

**Sketch of fix.** Restructure the write handler to await push before replying:

```js
self.dataSource.saveFile(wDir, wFile, wBytes.buffer)
  .then(function() {
      fileList = self.dataSource.getFileList();
      var ds = self.dataSource;
      if (ds && ds._vault && typeof ds._vault.push === 'function') {
          return ds._vault.push().then(function() {
              return { size: wBytes.byteLength };
          });
      }
      return { size: wBytes.byteLength };
  })
  .then(function(payload) { _writeReply(true, payload); })
  .catch(function(err)    { _writeReply(false, { err: err.message || 'Write failed' }); });
```

Open design question: do we want a third state ("local commit succeeded, push
failed")? Two reasonable options:

- **Option A (the author's expectation):** push failure → write rejects. Simple
  contract. Risk: short-lived network blips now surface as user-visible errors
  for a write the user perceived as having completed locally.
- **Option B:** resolve `{ size, synced: false, reason }` on push failure, with
  a `sg.sync.refresh()` to retry. Authors who care can inspect; authors who
  don't get the simple "it worked" path. More API surface.

Recommend Option A — matches "no silent partial success" and lets `sg.sync.refresh()`
be the recovery affordance.

**Risk / breaking change.** Medium. Existing authors who relied on
fire-and-forget writes when offline will now see rejections. Mitigation: ship
behind the same release as `sg.sync.refresh()` so authors have a retry primitive.
Document in the v0.28 changelog.

**Priority.** **P0** — this is the root cause of "phantom unpushed commits" (the
named ref drifts because the iframe believes the write succeeded). the author ranks
this #2 of his 5; from a correctness-vs-DX standpoint I'd put it joint #1 with
the `readText` cache.

### Ask 2 — `sg.vfs.readText` must invalidate after auto-sync, and error on missing paths

This is actually two distinct issues, both real, both fixable in this repo.

**2a. Cache invalidation.** The bridge's `_readText` is just
`fetch(path).then(r => r.text())` (line 662). The `fetch` is intercepted by the
service worker / vault iframe loader and ultimately served from the `fileList`
snapshot the parent captured at iframe-mount time. The parent-side handler's
`fileList` variable IS refreshed on write (line 903) but **is not refreshed when
the vault pulls/syncs from the named branch**. Auto-sync changes
`dataSource._vault` state but the per-iframe `fileList` closure variable holds
the old list.

**Sketch of fix.**

1. On every `sg.git.pull()`/refresh path in the parent handler, after
   `vault.pull()` resolves with `changed=true`, re-read `fileList =
   self.dataSource.getFileList();` (currently only `shell._mountBrowse()` is
   called — line 980 — which remounts UI but does not update *this* iframe's
   closure).
2. Subscribe the bridge to a "data refreshed" event from `dataSource` /
   `_vault` if one exists; if not, add one. Failing that, hook
   `dataSource.on('changed', …)` if available.
3. Optionally invalidate on visibility-change (the shell already auto-checks
   here per the v0.27.19 brief).

This needs a small protocol with the shell repo (an event the shell fires after
auto-sync), otherwise we are guessing when to refresh.

**2b. Fuzzy match on missing paths.** Directly confirmed at lines 1505–1532
(`_findEntry`). For an SG/App author API, `_findEntry` is wrong — it was designed
for HTML browsing where ambiguous `<img src="logo">` references should still
render. Two callers, two contracts:

| Caller | Today | Should |
|---|---|---|
| HTML asset resolution (lines 1241, 1264) — `<img src>`, `<a href>` | fuzzy ok | fuzzy ok (legacy HTML) |
| `sg.vfs.read*` / `sg.vfs.list` — author API (line 1067) | fuzzy | **strict** |

**Sketch of fix.** Split `_findEntry` into `_findEntryStrict` (exact path only,
slash-normalised) and `_findEntryFuzzy` (today's behaviour). Use strict for the
`__sgVfsReq` read path (line 1067) and for `__sgVfsListReq` (line 922). Return a
discriminated error: `{ __sgVfsReply: id, err: 'ENOENT', path: resolved }` so
the iframe-side `fetch`-shim can synthesise a 404 response that `_readText`
rejects on rather than returning empty/wrong content.

The iframe-side `_read`/`_readText` currently uses plain `fetch().then(r =>
r.text())` — it will need a status check (`if (!r.ok) throw new Error('No such
file: ' + path)`) and the parent must return a proper 404 envelope.

**Risk.** Low for the API. Medium ripple: any author code currently relying on
fuzzy `readText('config')` finding `config.json` will break — but that breakage
is *correct* (it's what the author is asking for).

**Priority.** **P0** for invalidation, **P1** for strict matching. Both small.

### Ask 3 — `sg.sync.status()` returning three booleans + version token

**Diagnosis plausible?** Yes — current status (lines 950–958) returns
`{ ahead, behind, diverged, headCommitId, namedHeadId, writable }`. Authors are
forced to translate raw `ahead/behind/diverged` into intent. Worse, the
sub-claim — that `sg.git.status()` and `sg.git.pull()` disagree about unsynced
commits (phantom-commits in Q5) — is **structurally plausible**: `status()`
reads `shell._syncState` (an in-memory cache last refreshed by some shell
trigger, lines 951–957), while `pull()` calls `vault.pull()` (the live SGit
client). They are different state stores. We can't fully verify here because
`_syncState` is set in the shell repo.

**Sketch of fix.**

- Add `sg.sync.status()` as the new canonical shape:

  ```js
  {
    current:          !ahead && !behind && !diverged,
    serverHasNewer:   behind > 0 || diverged,
    localHasUnsynced: ahead > 0,
    serverVersion:    namedHeadId,         // opaque token; equal → no change
    lastSyncedAt:     /* ISO from shell._syncState.lastCheckedAt */
  }
  ```

- Implement as a thin adapter on top of the existing `status` handler (line
  948), then keep `sg.git.status` as a back-compat alias returning the old
  shape with a deprecation `console.warn`.

- The contract the author demands — "if `status().localHasUnsynced` is `false`,
  `pull()` must not refuse with phantom unpushed commits" — requires a fix in
  the shell repo: `_syncState.ahead` must be sourced from the same place
  `vault.pull()` reads its precondition. Today they appear to diverge. Cross-
  team fix.

**Risk.** Low for the additive API. The "agree with pull" guarantee depends on
the shell-repo fix and is the real work.

**Priority.** **P1** — add the new shape immediately, then chase the shell-side
consistency fix.

### Ask 4 — Non-destructive in-place `sg.sync.refresh()`

**Diagnosis plausible?** Yes. Current `sg.git.refresh` (lines 985–991) calls
`shell._onRefresh()` which, per the v0.27.19 brief's "Known Caveats" section,
**destroys the calling iframe** — full vault remount, scroll loss, state loss.
Meanwhile `sg.git.pull` calls `vault.pull()` then `shell._mountBrowse()` which
remounts the *browse component* — also a destructive operation for the iframe.

So neither current option satisfies "iframe survives, cache is fresh, author
re-renders".

**Sketch of fix.** A new method `sg.sync.refresh()` that:

1. Calls `vault.pull()` — pulls upstream commits.
2. If there are unsynced local writes (the new `status().localHasUnsynced`
   path), calls `vault.push()`.
3. **Refreshes the parent-side `fileList` closure** (`fileList =
   self.dataSource.getFileList()`).
4. Posts a `{ __sgVfsCacheInvalidate: true, version: namedHeadId }` message to
   the iframe so the iframe-side bridge can dump any local memoisation.
5. Updates `shell._syncState` (calls `shell._refreshSyncState()`).
6. **Crucially: does NOT call `shell._mountBrowse()` or `shell._onRefresh()`.**
   The iframe element is left exactly where it is.
7. Resolves `{ from: prevHead, to: newHead, filesChanged: <int> }`.

The "filesChanged" count requires either a tree diff inside `vault.pull()` (the
sgit client must surface it) or a simple pre/post `getFileList()` set diff in
the parent handler — the latter is trivial.

**Risk.** Medium. We must be confident that not remounting `<send-browse>`
doesn't leave the surrounding *vault chrome* (file tree, header) showing stale
data. Mitigation: refresh chrome separately (header state from
`_refreshSyncState`, file tree from a lighter event) without touching the
active iframe. This needs design coordination with the shell repo owner.

**Priority.** **P1**, but blocked on agreement with shell repo. The author
ergonomics win here is large — it removes the entire "I called pull but my UI
still shows stale data" class of bug.

### Ask 5 — Symmetric TTL across `sg.ui.message` types + `sg.ui.dismiss`

**Diagnosis plausible?** Yes — both the iframe-side surface (line 738) and the
parent-side handler (lines 1037–1052) are short. Today:

- `success` → `banner.showStatus('✓', text, 3000)` — auto-dismisses.
- `info` / `warn` → `banner.showStatus('•', text /* no timeout */)` — persistent.
- `error` → `banner.showStatusError(text, '')` — persistent.

So the author's complaint is exactly right: `sg.ui.message('Checking…', 'info')`
sticks forever.

**Sketch of fix.**

1. **Iframe-side surface (lines 737–739):**

   ```js
   ui: {
     message: function(text, type, opts) {
       opts = opts || {};
       var handle = (Math.random()*1e9|0).toString(36) + Date.now().toString(36);
       window.parent.postMessage({
         __sgUiMsg: { handle: handle, text: String(text||""),
                      msgType: type || 'info',
                      ttl: opts.ttl === null ? null
                            : (typeof opts.ttl === 'number' ? opts.ttl : 3000) }
       }, "*");
       return handle;
     },
     dismiss: function(handle) {
       window.parent.postMessage({ __sgUiMsg: { handle: handle, dismiss: true } }, "*");
     }
   }
   ```

2. **Parent-side handler (lines 1037–1053):** Honour `ttl` uniformly for all
   types. For dismiss, look up the handle and call the banner / messages
   `dismiss(handle)` if exposed (this requires the banner / `sgraphVault.messages`
   to expose a handle-based dismiss; if they don't today, this is the only
   piece that needs an addition outside this repo).

**Risk.** Low. Default TTL = 3000ms across the board changes behaviour for
existing callers that fire `info`/`warn`/`error` and rely on persistence — but
those callers are inside our codebase (audit them) and most of them genuinely
want auto-dismiss. The `ttl: null` opt-in covers the legitimate persistence
cases (e.g. "Read-only — switch on write key to edit").

**Priority.** **P1**. Self-contained, small.

### Ask 6 — Rename `sg.git.*`

**Diagnosis plausible?** Yes, and it's a real ergonomic issue — the brief is
correct that we do not support most git semantics (no merge, no rebase, no
branching beyond the named ref). `sg.git.pull` invites `git pull` mental model
mismatch from the first read.

**Sketch of fix.** Add `sg.sync` as a sibling namespace on the same `_sgCmd`
backend in the injector (lines 724–730). Keep `sg.git` as an alias for ≥ 2
releases with a one-shot `console.warn` on first access in dev mode. The new
namespace also picks up `sync.status()` (Ask 3) and `sync.refresh()` (Ask 4)
naturally.

`sg.sgit` (suggestion from Question-1) is more brand-accurate but jargon-y;
`sg.sync` reads as the verb the author actually wants. Recommend `sg.sync`.

**Risk.** Trivial (additive + alias). Communication overhead is the real cost
— SKILL.md / AUTHORING.md / example author vaults need updating.

**Priority.** **P3**. Cosmetic; bundle into the same release as the substantive
fixes so authors see one coherent v0.28 surface.

## 3. Cross-cutting observations

- **Two contracts living in one file.** `_findEntry` and the read handler
  serve both legacy HTML asset resolution AND the strict author API. They need
  to split. This is the lowest-cost lever for several of the asks.
- **The "shell vs vault vs iframe" tri-party state.** The disagreement
  the author hits (status vs pull) is structural: `shell._syncState` is a UI
  cache, `vault._headCommitId` / `vault._namedHeadId` are SGit-client state,
  and the parent-side handler's `fileList` is a third closure. Each is
  refreshed on different triggers. Any durable fix to asks 2a/3/4 needs
  this trio to agree.
- **No iframe-side cache to invalidate, today.** `_readText` just calls
  `fetch`, so "invalidate the cache" really means "refresh the parent-side
  `fileList` closure and ensure the parent serves fresh bytes via
  `dataSource.getFileBytes`". Good news — no separate iframe cache to manage.
- **All five asks are realistic for v0.28.** Asks 1, 5, 6 are self-contained
  to this file plus minor shell additions. Asks 2a, 3, 4 need a coordinated
  change with the shell repo.

## 4. Open questions back to the author / Author teams

1. **Push-failure write semantics (Ask 1).** Option A (write rejects on push
   failure) vs Option B (write resolves with `{synced:false}`)? My recommendation
   is A; the author's brief is consistent with A. Confirm.
2. **What state does `sg.sync.refresh()` preserve, exactly?** The iframe
   survives — but does the author expect scroll position, focus, in-flight
   `XHR`, IndexedDB connections, all to be untouched? Setting expectations
   here drives whether we can ever fall back to a remount for edge cases.
3. **Should `sg.sync.status()` ever do a network round-trip?** Brief says no
   ("cheap to call, no required network"). That implies a separate
   `sg.sync.check()` for the explicit "go ask the server" case. Currently
   `sg.git.check()` exists and does this. Keep both, with `check()` being the
   explicit network call?
4. **`filesChanged` granularity in refresh result.** Count only? Or paths
   too? Paths is cheap given pre/post `getFileList()` diff and lets authors
   may do targeted re-renders.
5. **Read-only iframes calling `sg.sync.refresh()`.** Should they be able
   to? They have nothing to push, but pulling upstream changes is meaningful
   for read-only viewers. Recommend: yes, refresh is allowed read-only; only
   the implicit `push()` step is skipped.
6. **Are there real-world `sg.ui.message('info', …)` callers in shipped
   SG/Apps relying on persistence?** If yes, the default-TTL change is a
   breaking change for them and needs a migration note in the v0.28 release.
