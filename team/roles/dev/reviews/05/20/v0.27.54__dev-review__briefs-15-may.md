## Implementation Streams Assessment

### Stream 1: Firecracker Proof-of-Concept (P-099) — 1-2 days

**Priority: High | Effort: ~2 days | Blockers: None**

The brief is unusually concrete about scope: c8i-flex.large + `NestedVirtualization=enabled` +
Firecracker binary + one microVM running the vault app container image + measured startup +
snapshot save/restore + documented operating model. Cost: sub-$5 (or under $2 on spot).

This is the entry point for the entire Firecracker work stream. It should be done before
any of P-100 through P-106. The expected outcome is empirical data on:
- Cold-boot time on nested-virt C8i vs the 125-200ms published numbers
- Snapshot-restore time for our specific vault app image
- Actual memory consumption vs the "kernel adds 30-100 MiB" estimate
- Developer experience of the Firecracker API surface

**Acceptance criteria (from brief 412):**
1. Working Firecracker microVM running SG vault app's container image
2. Measured cold-start time
3. Snapshot save/restore demonstrated and timed
4. Documented operating model (what commands, what configuration)

This is a timebox — two days maximum. If it takes longer, something is wrong with the
approach, not the implementation.

### Stream 2: Observability and S3 CLI — Customer-Readiness (P-093 to P-098, relates to P-088, P-081)

**Priority: High | Effort: 2-3 weeks total | Blockers: None**

The addendum (brief 407) changes the framing of the observability and S3 CLI work from
"nice consolidation" to "operational readiness critical path." Two real data pipelines
are already producing data that sits unread:

- CloudFront → Firehose → S3 (traffic logs — every request, cache hit/miss, origin pull)
- CloudTrail → S3 (AWS API audit trail — all account activity)

The bottleneck is the tool to read them, not the pipeline to produce them. The S3 native
CLI (P-088, from prior batch) and unified observability session REPL (P-081, from prior
batch) unlock this data.

**Revised priority from the addendum:**

The addendum identifies observability as on the critical path for:
- CV/portfolio launch (customers need to see their own usage)
- Partner POCs moving to production
- Any paying-user workflows

This means the S3 CLI and observability REPL should be front-loaded in the backlog, ahead
of the Firecracker experiments which are useful but not on the customer-readiness path.

**New items from this batch:**

P-093 (CloudFront pipeline as named source) and P-094 (CloudTrail pipeline as named source)
are small additions to the observability session source contracts. Both pipelines already
exist; the work is writing the source contract implementation for each.

P-095 (CloudWatch dashboard screenshots) is small: `dashboard fetch`, `dashboard list`,
`dashboard screenshot`. Brief 407 says "add to v1 scope if cheap, v2 if not." This is
likely a v2 item.

P-096 (product analytics layer) and P-098 (per-customer reporting) are explicitly downstream
of the substrate (layer 2 and layer 3 after layer 1 is built). Do not start these before
the observability REPL (P-081) is working with real data.

P-097 (SG billing emission) depends on the pre-auth micropayments ledger (P-074 from prior
batch). These must be built in order.

**Recommended sequencing for this stream:**
1. S3 native CLI (P-088) — unlocks reading data from existing pipelines
2. Observability REPL with CloudFront and CloudTrail as sources (P-093, P-094, extends P-081)
3. SG billing as a source (P-097, after micropayments ledger exists)
4. Product analytics queries (P-096, after substrate working with real data)
5. Per-customer reporting surface (P-098, last — depends on P-096)

### Stream 3: Nitro Enclaves PoC — High Effort, High Value

**Priority: Medium-High | Effort: 2-3 months for first production primitive | Blockers: Architecture decision on first use case**

The brief correctly stages this as significant work. The PoC (enclave-protected vault
decryption primitive) is the foundation for all seven use cases. Before any specific use
case, the team needs working plumbing:

1. Build an EIF from the vault app Docker image (`nitro-cli build-enclave`)
2. PCR measurements recorded
3. KMS policy written using PCR0 condition key
4. Enclave launched on an EC2 instance with `enclave_options.enabled`
5. vsock proxy configured for KMS access
6. Customer vault key sent to enclave (via vsock) and used to decrypt vault content
7. Decrypted data returned over vsock

This is the SG-vault-enclave EIF (P-116). Everything else is an application of this primitive.

**Development sequencing:**

Phase 1 (plumbing, ~2 weeks): Build the basic EIF, get the vsock flow working, PCR-based
KMS policy working. This is exploratory — budget for iteration.

Phase 2 (first use case, ~3-4 weeks): Server-side vault search (P-109) is the recommended
first use case. It is CPU-bound (good for enclaves), contained scope (one EIF, one vsock
API), and directly addresses a known customer gap.

Phase 3 (open-source release, ~1 week): Publish PCR values, establish auditable build
pipeline, publish EIF source. Required for customer-facing credibility.

**Blockers and dependencies:**
- Architecture decision on enclave host → request flow (not yet specified)
- An EC2 parent instance with `enclave_options.enabled` must be provisioned
- The instance needs at least 4 vCPUs and enough RAM for both parent and enclave
- KMS key with PCR-based condition policy must be created

**Development risks:**
- vsock proxy configuration is operationally complex; no off-the-shelf solution for our
  use case — probably write a thin Python proxy initially
- Debug mode vs production mode: PCR-based KMS policies refuse debug-mode attestations,
  so dev/test requires a separate environment or a separate KMS key
- Session recovery (enclave dies mid-session) needs a defined flow before GA — do not
  GA without this

### Stream 4: AgentCore Integration — Build Burden Reduced

**Priority: Medium | Effort: Varies by service | Blockers: AgentCore enabled in AWS account**

The layering decision (use/leverage/resell) removes several items from the build backlog:

**Items removed from build backlog (consume AgentCore instead):**
- Sandboxed code execution sandbox → AgentCore Code Interpreter
- Cloud browser runtime → AgentCore Browser (replaces Neko evaluation)
- In-session agent memory → AgentCore Memory (short-term)
- OAuth tokens + pre-authorised consent → AgentCore Identity
- Bidirectional streaming → AgentCore Runtime (available out of the box)

**Items that still need building (the "leverage with wrapper" category):**
- Vault-grounded LTM wrapper for AgentCore Memory (P-120-related)
- Vault-stored tool manifests wrapper for AgentCore Gateway
- AgentCore trace integration into the unified observability session (P-095 extension)
- Cedar policies stored in vault (wrapping AgentCore Policy)
- Agent definitions as manager vault entries (wrapping AgentCore Agent Registry)

These wrappers are thin by design — they add vault grounding to AgentCore capabilities.
Each one is probably 2-4 days of work once the underlying AgentCore service is enabled.

**For the first resell product (recommended: Vault-Grounded Agent Hosting, P-120):**

The components needed:
1. AgentCore Runtime session for an agent (AWS side)
2. Vault-grounding hook that commits agent outputs to vault on each action
3. Pre-auth micropayments billing line item for AgentCore Runtime per-session cost
4. Customer-facing UI to show vault-bound agent state

This composes existing primitives cleanly. The new work is the vault-grounding hook and
the billing integration. Estimated 2-3 weeks for a working prototype.

**Dependency:** AgentCore must be enabled in the AWS account (OQ-bedrock-1 from prior
sessions). This is a DevOps prerequisite — check before scheduling this stream.

### Stream 5: USDC / x402 — Prototype Scope Only

**Priority: Low-Medium | Effort: 1-2 weeks for prototype | Blockers: Regulatory review, Circle Mint or Coinbase Business setup**

The brief is clear: scenarios 1 and 2 don't need USDC; scenario 3 does. The three
builds are:

P-125 (agent-buys-from-third-party via x402): Pick one concrete external service with
x402 support or a paid per-call API. Build the AgentCore Payments integration. This is
the clearest value demonstration.

P-126 (one SG service exposes x402 micropayment receiver): Pick the simplest SG service
to x402-enable. Per-vault-open is the most natural. HTTP 402 response + payment validation
+ access grant.

P-127 (USDC backend treasury): Depends on Circle Mint or Coinbase Business account being
set up. Do not start without the account. Low urgency.

**Pre-requisites:**
- Legal review of UK stablecoin regulations before any customer-facing use
- Circle Mint or Coinbase Business account for treasury operations
- Tax treatment clarification (stablecoin payments may have implications)

This stream should not start until the observability and Firecracker work is underway.
It is strategically important but has zero customer-facing urgency in May 2026.
