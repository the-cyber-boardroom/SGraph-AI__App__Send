## Stream 1: TUI API

### Implementation Scope

The TUI API is well-specified in two briefs (442, 443). The seven API surfaces:

| Surface | Description | Estimate |
|---------|-------------|----------|
| `status` | Current state of a tool (health, version, active tasks) | 0.5 day |
| `list` | Enumerate available capabilities within a tool | 0.5 day |
| `get` | Retrieve a specific resource or state | 1 day |
| `invoke` | Execute an operation | 1 day |
| `subscribe` | Watch for state changes (event stream) | 2 days |
| `stream` | Live output stream (logs, metrics) | 2 days |
| `reflect` | Orientation: what this tool does, what changed, what is coming | 1 day |

Total for core surfaces: ~8 days.

**Additional work:**
- Memfs virtual filesystem (skills.md, changelog on demand): 3 days
- Native IAM least-privilege scoping: 2 days
- Change-control surface: 2 days
- TUI-of-TUIs composition: 3 days (post first consumer)
- Documentation and protocol spec: 2 days

**Total TUI API stream: ~20 days (4 weeks)**

### First Consumer: SG/Sentinel TUI

The SG/Sentinel TUI mockups (9 surfaces, P-217) are the immediate first consumer of the TUI API. Build the TUI API to serve these nine surfaces; the generic protocol spec emerges from the concrete use case.

Sequencing: TUI API foundation (status, list, get, invoke, reflect) → SG/Sentinel TUI surfaces → subscribe/stream → memfs.

### Acceptance Criteria (TUI API)

1. Each of the 7 API surfaces is callable from a Python client
2. Output is structured (not human-formatted text)
3. IAM scoping enforced: a read-only scope cannot invoke destructive operations
4. `reflect` returns: current version, recent changes (changelog), upcoming changes (roadmap)
5. Orientation file (skills.md) loads on demand, not on startup
6. TUI-of-TUIs: one TUI can invoke another via the TUI API and aggregate state

## Stream 2: SG/Sentinel MVP

### Pre-Implementation Dependencies

**Resolve before coding:**

|---|-----------|-------|---------------|

**Assumption for planning:** 1 week for these pre-conditions.

### MVP Scope (from path-to-MVP brief, P-222)

The ten-step MVP sequence:

| Step | Component | Estimate |
|------|-----------|----------|
| 1 | Layer 1 (CloudFront Function): logging every hit, clean, to S3 | 3 days |
| 2 | Layer 1: easy-win blocks (banned IPs, /etc/passwd, /.env, PHP-scan, WordPress-on-static, obvious-bad patterns) | 2 days |
| 3 | S3 log delivery: batch, compress, structured format; Sentinel ends at S3 | 2 days |
| 4 | The fingerprint object: signed-token-based; per the tabletop resolution | 3 days |
| 5 | Layer 2 (Lambda@Edge): known-good-profile validation for 2-3 endpoints (observe-mode first) | 4 days |
| 6 | Rule engine core: tiny engine + deterministic rules; fractal rule graph; rules-as-vault | 5 days |
| 7 | TUI surface 1: live traffic (real-time hit stream from S3) | 2 days |
| 8 | TUI surface 2: blocks (recent blocks, with reasons) | 2 days |
| 9 | TUI surface 3: logs + S3 (S3 bucket state, recent log files) | 1 day |
| 10 | TUI surface 4: rules management (list, enable/disable, version) | 2 days |

**MVP total (excluding pre-conditions): ~26 days (~5-6 weeks)**

### Dev Environment

The dev environment specification is clear (same code as production, lambda-as-container). This extends the existing SG/Compute local-run infrastructure. Expected cost: 3-4 days to wire up the Sentinel-specific local environment. **Start this in parallel with Step 1.**

### Layer 1: JavaScript Constraint

CloudFront Functions require JavaScript. All other Sentinel code is Python. For the MVP:
- Write Layer 1 rules directly in JS (they are simple: banned IPs, path matching, obvious-bad patterns)
- Do NOT attempt to compile Python rules to JS in the MVP
- The Sigma-style compile-to-backend is explicitly post-MVP

Acceptance criteria for Layer 1 JS: test coverage with offline CloudFront Function test harness (no live deploy required for unit tests).

### Layer 2: Python with Type_Safe

Layer 2 runs as Lambda@Edge. Follow standard project patterns:
- All schemas use `Type_Safe` (never Pydantic)
- No mocks in tests; in-memory stack starts in ~100ms
- Extend `Serverless__Fast_API` for the Sentinel API surface

### Risk Register

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| Fast-track memo not ready before coding | Medium | High (blocks identity design) | Start with logging-only (no fast-track) in Steps 1-3; revisit when memo arrives |
| Layer 1 JS rules are brittle | Low | Medium | Keep them simple (pattern matching only); complex logic belongs in Layer 2 |
| S3 log volume cost higher than expected | Low | Medium | Batch + compress from Day 1; measure actual cost before MVP sign-off |
| Auth-outcomes coupling creates latency | Medium | Medium | Implement as fire-and-forget async POST; never block auth response |
| Deploy parity breaks in practice | Low | High | Run the full local environment in CI; any QA-vs-prod diff = failed build |

### What Is NOT In The MVP

The path-to-MVP brief (P-222) is explicit. Do NOT attempt:
- Unified semantic graph (full build)
- Compliance-as-living-graph feature
- Full LLM Layer 3 analysis (hook only)
- Multi-CDN (Cloudflare, Fastly)
- Full deception layer (honeytoken-touch-revokes-fast-track is the minimal version; that IS in MVP for the fingerprint)
- User-facing "what do you know about me?" privacy feature (dev-only debugging version only)
- Vault-per-user evidence at scale
- SSL termination
- Standards-as-vaults
- Rule retirement automation

## Testing Notes

SG/Sentinel introduces Layer 1 JavaScript that needs a test harness. For the existing Python layers:
- No mocks, no patches (existing rule)
- In-memory MemFS for rule-set storage tests
- Lambda-as-container for Layer 2 integration tests
- The `replay-from-S3` pattern (addendum, P-221) is the right approach for regression: production logs become the regression test corpus. Implement this from the start.

**New testing requirement:** CloudFront Functions offline test harness for Layer 1 JS. This is a single-file Jest or Node.js test harness that simulates the CloudFront event object. 1 day to set up.
