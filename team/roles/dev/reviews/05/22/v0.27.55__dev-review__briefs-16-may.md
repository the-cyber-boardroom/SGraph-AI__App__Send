No new infrastructure is required — everything builds on existing primitives (vault, JS API, email-fs, FastAPI pattern, SG/Compute CLI, container hosts, on-demand provisioning, pre-auth metering, DNS + TLS).

This review estimates effort, identifies streams, and flags risks. PROPOSED items are not code. All estimates assume 1-2 experienced developers per stream.

## Production Milestone (Confirmed)

**50-second end-to-end vault provisioning (doc 428)**

This is EXISTS, not PROPOSED. The brief documents a working production result:
- One command: EC2 instance up → vault created → TLS cert issued → DNS live
- ~50 seconds end-to-end
- Holding page during provisioning works (wildcard cert + Lambda)
- UI that polls and redirects on readiness works

This is a meaningful infrastructure milestone. The DNS pinning problem identified in the same brief is the next technical hurdle to resolve before this is production-reliable at scale.

### Stream 3: Vault Discovery and Public Keys (2-3 weeks)

**Brief:** 422 (vault discovery + public keys)
**Effort:** Medium-High
**Dependencies:** Vault format (key audit step required first)

**Week 1 (audit and design):**
- Audit current vault key infrastructure: what keys exist, which are encrypted vs plaintext, do any serve as signing or encryption keys?
- Design Ed25519 + X25519 key pair model (P-151): storage format, derivation or generation, private key encryption under vault key
- Design key rotation FSM (generate → announce both → rotate → retire)
- This is design work, not implementation. Output: a spec document.
- ~5 days

**Week 2 (implementation):**
- Implement key pair generation at vault creation
- Implement public key in vault metadata
- Implement `/.well-known/vaults` endpoint (P-149): return JSON listing
- Implement visibility model (P-150): public/unlisted/private/count-only in vault metadata

**Week 3 (send-to-vault):**
- Implement inbox endpoint (POST encrypted blob to vault)
- Rate limiting per vault + per IP
- Server-side: store encrypted blob in vault inbox path
- Client-side: encrypt to X25519 public key using Web Crypto API (already available in browser)
- TXT record public key export (P-154): add to DNS sync process

**Risk:** If the vault key audit reveals that existing vault format does not accommodate new key material without a migration, migration cost could be significant (hundreds of existing vaults). Migration must be backwards-compatible (old vaults without key pairs still work; new key pairs are added on next write or explicitly).

**Week 3 (vault client UI):**

**Risk:** email-fs audit may reveal significant gaps between what exists and what is needed for a working email client. If email-fs is incomplete, the vault client cannot be built on top of it — the audit must happen first before committing to the week 3 timeline.

### Stream 7: Backup and Restore (4-5 weeks)

**Effort:** High
**Dependencies:** AWS Organizations (or separate account setup), Backblaze B2 account, Glacier configuration

**Week 1 (account setup + design):**

**Weeks 2-3 (backup worker):**

- Implement backup loop: discover sources → compute hash → sync to Tier 1 (cross-account S3) → verify → write result
- Implement Tier 1 (cross-account S3) for first 3-5 vaults

- ~10 days

**Week 4 (restore drills):**
- Implement daily lightweight restore drill: pick sample vault, restore to scratch environment, hash compare, write result
- Implement weekly full-vault restore drill
- Alert on failed drills (P-176: alerts section in backup-operations vault)
- ~5 days

**Week 5 (multi-provider + agentic):**
- Set up Backblaze B2 account (P-180): create bucket; configure S3-compatible credentials via credential manager
- Implement Tier 4 (Glacier) for one vault: lifecycle policy + Glacier instant retrieval
- Implement Tier 5 (Backblaze B2) for one vault: sync to B2 bucket

- ~10 days

**Brief:** 428 (on-demand provisioning)
**Effort:** Low-Medium
**Dependencies:** Existing 50-second provisioning flow (confirmed working)

**Week 1:**
- Implement DNS pinning fix (P-183): extend holding-page Lambda to check provisioning state on each request; return 302 redirect to live instance when ready

- Test fix across major browsers and DNS resolvers (dig against 8.8.8.8, 1.1.1.1, Quad9)
- Implement randomised ephemeral address pattern (P-184): generate GUID-like slug on request; provision dedicated instance; return address to user

**Week 2:**

**Risk:** DNS TTL reduction to 30s on the wildcard record may cause a small number of additional DNS queries globally. Confirm with DevOps that this is acceptable at current traffic volume.
