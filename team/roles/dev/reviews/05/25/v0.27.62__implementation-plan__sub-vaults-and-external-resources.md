## 1. Data contracts (exact)

### 1.1 Link file — `*.link.json` (lives in the regular tree)
Recognised **only** by the `.link.json` filename suffix. Minimal; carries **no key**.
```jsonc
{
  "vault_id": "abcd1234",        // REQUIRED for type vault; OMITTED for external resources
  "ref_id":   "lk-a1b2c3d4",     // REQUIRED — key into the owner record (§1.2)
  // optional per-location overrides of any owner-record field:
  "type":     "vault",           // vault | link | video | image | app   (override/hint)
  "label":    "Patient: Alice",
  "pin":      { "mode": "latest" },          // or { "mode":"commit","commit":"<id>" }
  "description": "…",
  "url":      "https://…"        // external types only
}
```
- **Validation:** must parse as JSON and contain a non-empty `ref_id`. A `vault` resolution additionally needs a `vault_id` (from file or record). Malformed → **dropped with a `console.warn`, never thrown** (treat as a normal file).
- **Effective field value = `link-file value ?? owner-record value`** (override precedence).
- A file **not** ending in `.link.json` is a normal file (renaming off the suffix disables the link — see test T-U1).

### 1.2 Owner records — `.vault/owner/ro-links.json` and `.vault/owner/rw-links.json`
A map keyed by `ref_id`. Holds canonical metadata **+ the key**. Mirrors the storage pattern of `en-gb/vault/token/vault-token-manager.js` (`readonly-tokens.json`).
```jsonc
// .vault/owner/ro-links.json   — encrypted with the vault read_key ONLY (a normal vault file).
//   Readable by anyone with parent READ access. Only read-only references allowed here.
{ "lk-a1b2c3d4": {
    "type": "vault", "label": "Patient: Alice", "pin": { "mode": "latest" },
    "description": "…", "url": null,
    "read_key": "<base64-32B>", "ref_file_id": "ref-pid-muw-…"   // for vault type
} }

// .vault/owner/rw-links.json   — DOUBLE-encrypted: ownerEncrypt(...) THEN stored as a vault file.
//   Owner-only (full vault key). Full child vault_key may live here.
{ "lk-9f8e7d6c": {
    "type": "vault", "label": "Shared working vault", "pin": { "mode": "latest" },
    "vault_key": "apple-river-1234:wxyz5678"
} }
```
- **Encryption tiers (reuse existing crypto):**
  - `ro-links.json`: write as a **normal vault file** via `dataSource.saveFile('/.vault/owner','ro-links.json', bytes)` — the vault layer encrypts it with `read_key`. No inner layer.
  - `rw-links.json`: inner-encrypt the JSON with `ownerEncrypt(vault._passphrase, vault.vaultId, plainBytes)` (`en-gb/vault/token/vault-hkdf.js:61`) → store those bytes as a vault file (outer `read_key` layer added automatically). Decrypt with `ownerDecrypt(...)` (`vault-hkdf.js:79`). **Identical to `vault-token-manager.saveTokenList`/`loadTokenList`.**
- External-resource records (`link/video/image/app`) hold `type`,`label`,`url`,`description` (+ `provider` for video, + `grants[]` for app) and live in **ro-links** (urls aren't secret) unless they carry an app grant (then owner-tier rw-links).

## 2. New module — `_common/js/lib/links/vault-links.js`
Pure logic, no DOM. Mirrors `vault-token-manager.js`. Signatures:

```js
// suffix recognition
isLinkFile(path) -> boolean                     // /\.link\.json$/i.test(path)
mountLabel(path, link) -> string                // link.label ?? filename minus ".link.json"

// parse + validate a link file's bytes (ArrayBuffer/Uint8Array/string) -> object|null (null on malformed)
parseLinkFile(bytes) -> { vault_id?, ref_id, type?, label?, pin?, description?, url? } | null

// owner records (read)
async loadRoLinks(vault) -> Record<refId, LinkRecord>   // normal vault file read; {} if absent
async loadRwLinks(vault) -> Record<refId, LinkRecord>   // ownerDecrypt; {} if absent or not owner
async resolveRef(vault, refId) -> { record, tier } | null
    // ro-links first, then rw-links (only if vault.writable/owner). null if neither.

// effective view used by the UI: merge record + link-file overrides
effectiveLink(linkFileObj, record|null) -> { type, label, pin, description, url, vault_id, ...key fields }

// key resolution for opening (NO prompt here — returns what's available)
keyForVault(vault, refId, linkFileObj) -> { readKey, refFileId, vaultKey } | null
    // 1) record (ro: read_key+ref_file_id; rw: vault_key)  2) localStorage 'sg-access-key:'+vault_id  3) null

// owner records (write) — Phase 3, but define here
async saveRoRecord(vault, refId, record)   // saveFile('/.vault/owner','ro-links.json', …) + push
async saveRwRecord(vault, refId, record)   // ownerEncrypt → saveFile('/.vault/owner','rw-links.json', …) + push
```
Also: **move** `en-gb/vault/token/vault-hkdf.js` → `_common/js/lib/crypto/vault-hkdf.js` and update the two importers (token harness + this module). It is already self-contained ES exports.

## 3. The inline splice — `CompositeDataSource` (the hard part; Phase 0 proves it)
The browse component (`send-browse`) consumes the 3-method data-source contract: `getTree()`, `getFileList()`, `getFileBytes(path)` (see `_common/js/adapters/vault-data-source.js`). **Wrap** the root `VaultDataSource` in a `CompositeDataSource` that presents the same contract and splices sub-vaults in. `send-browse`/`vault-shell.js` then talk to the composite and stay almost unchanged.

**File:** `_common/js/adapters/composite-data-source.js` (new).

**Mount model.** A `vault` link file at tree path `P` (e.g. `subvaults/demos/acme-demo.link.json`) defines a mount at `mountPath = P without ".link.json"` (→ `subvaults/demos/acme-demo`).
```
mounts: Map<mountPath, {
  linkPath, link,            // the parsed link file + its path
  status: 'collapsed'|'opening'|'mounted'|'locked'|'error',
  child: VaultDataSource|null,   // read-only child (accessKey=null)
  vault: SGVault|null,
  error: string|null
}>
```

**Lifecycle:**
1. `await composite.scan()` — call `root.getFileList()`, find `isLinkFile(path)`; for each, `parseLinkFile(getFileBytes(path))`. `type:'vault'` (or vault_id present) → create a `collapsed` mount. External types → hand to `<sg-embed-frame>` rendering, not a mount.
2. `getTree()` / `getFileList()` (composite):
   - **hide** the raw `*.link.json` entries;
   - **insert** a folder node at each `mountPath` with `{ dir:true, _subvault:true, _access:'ro', _status }` (send-browse renders the glyph + `·ro` chip from these flags);
   - for `mounted` mounts, **splice** the child's entries with paths **prefixed** by `mountPath` (`readme.md` → `subvaults/demos/acme-demo/readme.md`).
3. **Expand** a mount node → `composite.openMount(mountPath, { keyProvider })`:
   - resolve key via `keyForVault(...)`; if null → status `locked`, surface the link card (Phase 2) / prompt (Phase 0);
   - `SGVault.openReadOnly(sgSend, vault_id, readKey, refFileId)` (`sg-vault.js:93`); if only a full `vaultKey` is available, `SGVault.open(...)` then wrap read-only;
   - `child = new VaultDataSource(childVault, null)` (read-only); `await child.loadAllSubTrees()` (or lazy per-folder); status `mounted`; fire `onTreeChanged`.
4. `getFileBytes(path)` (composite): if `path` starts with a mounted `mountPath + '/'`, strip the prefix and delegate to that mount's `child.getFileBytes(rel)`; else delegate to `root`.
5. Errors (unreachable child / expired token / decrypt fail) → status `error`, keep the node visible with a retry (no dead click).

**Recursion** falls out naturally: a mounted child is itself a `VaultDataSource`; wrap each child in its own composite (or make `CompositeDataSource` recursive) so a child's own `.link.json` files mount one level deeper. Phase 0 may stop at depth 1; Phase 2 enables recursion.

## 4. Per-tab vault identity (enables "open in new window")
Three small, surgical changes (briefing pack §4.5):

1. **`_common/js/vault-loader/vault-loader-storage.js`** — add a per-tab current key in `sessionStorage` and make it the source of truth:
   - `getCurrentKey()` → `sessionStorage['sg-vault-key']` ?? `localStorage['sg-vault-key']` (fallback).
   - `setCurrentKey(key)` → write **both** `sessionStorage` (per-tab truth) and `localStorage` (last-opened convenience).
   - `clearCurrentKey()` → clear both.
2. **`_common/js/vault-loader/vault-loader-routing.js`** — `runVault()` (line 94) currently *strips* the token hash. Change to: if the hash is a vault token (not the `/app#path` case), **adopt it** — `VaultLoaderStorage.setCurrentKey(token)` then strip. The vault page now opens from the adopted key.
3. **`app-shell.js`** reload recovery (line 70) — read `sessionStorage` first, then `localStorage` (keep current behaviour as fallback).

**"Open in new window"** (composite mount action / link card): `window.open('/en-gb/vault/#' + childVaultKey, '_blank', 'noopener')`. Hash only (never query). Result: each tab reloads its own vault; closing one is a no-op (briefing pack §4.5 / test T-E5).

## 5. Components

### 5.1 `<sg-link-card>` (`_common/js/components/sg-link-card/`)
Shown when a mount is `locked`, or when the user opens a link file to view/edit it.
- **Attributes/props (set by caller):** `vault-id`, `ref-id`, `status`, and an object with the effective link fields.
- **Renders:** status; **public info first** (label, file count, updated — from the per-vault public-info endpoint when it lands; until then, show what the record has); a key input; save choice (radio: *in this vault (ro/rw record)* · *on this device (`localStorage`)* · *don't save*); `pin` (Latest / Commit); editable `description` (owner only).
- **Events:** `sg-link-open` `{ key, save:'vault-ro'|'vault-rw'|'local'|'none', pin }` → caller runs `openMount`; `sg-link-open-new-window` → caller does the `window.open` above.
- Reuses tokens from the briefing pack/designer review (teal `#4ECDC4`, blue `👁 Read-only` pill).

### 5.2 `<sg-embed-frame>` (`_common/js/components/sg-embed-frame/`)
Per-type external renderer (briefing pack §4.7). **Shares no code with `app-shell`'s VFS bridge; registers no `message` listener; injects no `window.sg`.**
- **Attributes:** `type` (`link|video|image|app`), `url`, `provider`, `label`, optional `grant` (Phase 3).
- **Click-to-load:** initial render is a **placeholder** ("▶ Load external {type} from {host} — this contacts {host}"). No network until the user clicks (test T-S3).
- **After load, render by type:**
  - `image` → `<img src=url loading="lazy" referrerpolicy="no-referrer">`.
  - `video` (file) → `<video src=url controls>`.
  - `video` (provider) → `<iframe sandbox="allow-scripts allow-same-origin allow-presentation" src=providerEmbedUrl>` (provider needs same-origin for its own player; it is cross-origin to *us*).
  - `link`/`app` → `<iframe sandbox="allow-scripts allow-popups allow-presentation" src=url>` — **no `allow-same-origin`**, no bridge.
- **Sticky guarantee banner** above the frame for `link`/`app` (and full-screen toast fallback) per the designer review; `image`/`video` get a lighter "external · {host}" caption.

## 7. Test plan (assertion-level; no mocks)

**Unit (`vault-links`, composite):**
- T-U1 `isLinkFile('a.link.json')===true`; `isLinkFile('a.link-2.json')===false` (rename-off-suffix disables).
- T-U2 `parseLinkFile` returns object for valid; **returns null (no throw)** for malformed/empty.
- T-U3 `effectiveLink` applies `override ?? record`; two link files sharing one `ref_id` differ only by their overrides.
- T-U4 composite hides `*.link.json`, inserts a `_subvault` folder node at `mountPath`; `getFileBytes` routes a `mountPath/...` path to the child.

**Crypto (real, in-memory):**
- T-C1 `ro-links.json` round-trips as a normal vault file (read_key).
- T-C2 `rw-links.json` `ownerEncrypt`→store→load→`ownerDecrypt` round-trips; tamper → fails.
- T-C3 a read-only holder of the parent resolves `ro-links` but **cannot** decrypt `rw-links`.

**Security (priority):**
- T-S1 `<sg-embed-frame>` for `link` has sandbox without `allow-same-origin`, exposes no `window.sg`, and the host registers no `message` listener for it.
- T-S2 `type:image` renders an `<img>`, not an iframe.
- T-S3 **click-to-load:** no network request to the external host until the user clicks Load (spy on fetch/resource load).
- T-S4 (Phase 3) granted `requestFile` is read-only, prefix-enforced, fails closed on missing folder.

**E2E (Playwright):**
- T-E1 author `*.link.json` via New File → expand → child files inline (read-only) → open a child file.
- T-E2 same vault under two link files in different folders both work.
- T-E3 move the link file to another folder → sub-vault relocates after refresh.
- T-E4 recursive: a sub-vault containing its own link file expands one level deeper.
- T-E5 **multi-window:** "open in new window" → child B in its own tab; reload A→A, reload B→B; close B = no-op.
- T-E6 locked node → link card → enter key → each save choice behaves; expired/unreachable child → error card + retry, never a dead node.
- T-E7 YouTube `video` renders via click-to-load then provider iframe with sticky banner.
- T-E8 `image` link renders via `<img>` after click-to-load.

**Changelog test-impact:** *should break (good)* — browse-tree snapshots (new nodes), data-source contract tests (now composite). *should NOT break (bad)* — `app.json`/`_page.json` flows, RO-token open, lazy-folder loading, the app VFS bridge, single-vault reload (now sessionStorage-first).

## 9. Risks & sequencing
- **The composite splice is the only genuinely hard piece** — Phase 0 isolates and proves it before any persistence. If `send-browse`'s tree rendering resists a wrapped data source, fall back to teaching `VaultDataSource` itself about mounts (same mount model), but prefer the wrapper to keep `send-browse` unchanged.
- **Per-tab identity changes existing behaviour** (single-vault reload, `/app` recovery) — keep `localStorage` as the documented fallback and cover with regression tests; this is the one change that can break current flows.
- **Phase 3 grant channel is blocked on AppSec** — do not implement the `requestFile` channel until the protocol is signed off.
