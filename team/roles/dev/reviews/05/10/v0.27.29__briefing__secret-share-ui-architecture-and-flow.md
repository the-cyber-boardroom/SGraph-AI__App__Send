## 1. Executive Summary

The "Share a Secret" workflow is the 5-step encryption wizard that ends with the
"Secret link created" screen shown in the user-supplied screenshot. It is
implemented entirely as **IFD surgical overlays on top of v0.3.0** under
`sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.2/`. Eight v0.3.2 JS files patch the
v0.3.0 base orchestrator, engine, API client, constants and step-select element,
and add two new light-DOM Web Components (`<upload-step-options>`,
`<upload-step-done-secret>`) plus a standalone receive page
(`<send-secret-view>` at `/en-gb/s/`).

End-to-end the flow works in code: the user types a secret, picks views/expiry,
hits Review, lands on the standard Confirm step, hits "Encrypt & Upload" which
fast-paths through the same engine pipeline as a file (with a transient
`createTransfer` patch to inject `secretConfig`), and the Done step renders a
share URL of the form `…/en-gb/s/{transferId}#{keyHex}` and a kill URL of the
form `…/en-gb/s/kill/{transferId}#{deleteAuth}`. Both copy buttons and the
"Create Another Secret" reset are implemented.

**Top three issues found by reading the code:**

1. **Duplicate Email Link button** on the Done step in secret mode — the
   v0.3.0 header-action slot still renders `<button id="upload-email-btn">Email Link</button>`
   on `state==='complete'` and v0.3.2's `_render` patch never suppresses it,
   so the user sees an Email Link in the top-right header AND inside the
   `secret-done` panel; the header one builds a generic file-flow mailto.
2. **No i18n** — every visible string in `upload-step-done-secret.js`,
   `upload-step-options.js`, `upload-step-select-secret.js` and
   `send-secret-view.js` is a hard-coded English literal. The page sits under
   `/en-gb/` but the wizard is meant to be locale-aware.
3. **Backend contract drift on `expires_at`** — v0.3.2 sends an int
   millisecond timestamp (`Date.now() + dh*3600000`); per code comments the
   v0.3.0 `Schema__Transfer` declared it as ISO-8601 `str`. A backend fix
   (`cd90038 fix(transfer): change expires_at from ISO-8601 str to int ms since
   epoch`) appears to address this but the frontend code/comments still flag
   the mismatch as outstanding (see `send-upload-secret.js:15-19`,
   `api-client-v032.js:13-17`).

## 6. State Model

| State (in `_state`) | Step (1–5) | Active Component | Notes |
|---|---|---|---|
| `idle`, `file-ready`, `folder-options` | 1 | `select` (`<upload-step-select>`) | Includes both File and Secret tabs |
| `choosing-options` | 2 | `options` (`<upload-step-options>`) | New v0.3.2 state — replaces `choosing-delivery` and `choosing-share` |
| `confirming` | 3 | `confirm` (`<upload-step-confirm>`) | Re-used by secret flow as of `ff9c1f8` |
| `zipping`, `reading`, `encrypting`, `creating`, `uploading`, `completing` | 4 | `progress` | Same pipeline for file and secret |
| `complete` (`!isSecretMode`) | 5 | `done` (`<upload-step-done>`) | File flow only |
| `complete` (`isSecretMode`) | 5 | `done-secret` (`<upload-step-done-secret>`) | Secret flow Done screen — the screenshot |
| `error` | 1 | `error` | Plain `<div class="status status--error">` |

State storage:

| Where | What |
|---|---|
| `<send-upload>` instance properties | `_state`, `_isSecretMode`, `_secretConfig`, `_deleteAuth`, `selectedFile`, `result`, `_shareMode`, `_selectedDelivery`, `_stageTimestamps`, `_friendlyParts`, `_friendlyKey` |
| `UploadEngine` static (transient) | `_pendingSecretConfig`, `_pendingDeleteAuth` (cleared in `finally`) |
| `<upload-step-done-secret>` instance | `_result`, `_secretConfig` |
| URL fragment (`#…`) | Share link: AES key (base64url). Kill link: raw `deleteAuth` (hex). Never sent in HTTP. |
| `localStorage` | `sgraph-send-token` (access token; not secret-specific) |
| `window.SGRAPH_BUILD` | `appVersion`, `uiVersion`, optional `apiEndpoint` |
| Cookies | None (verified — `crypto.js:46`, `upload-step-select-secret.js:93` "Zero cookies" note; no `document.cookie` writes in any v0.3.2 secret file) |

State transitions for the secret flow (from `send-upload-secret.js`,
`send-upload-options.js`, `send-upload.js`):

```text
idle ──Secret tab + Review──▶ confirming ──Encrypt & Upload──▶ reading
                                                                  └─▶ encrypting
                                                                  └─▶ creating
                                                                  └─▶ uploading
                                                                  └─▶ completing
                                                                  └─▶ complete  (Step 5)
                                                                                  │
                                                                                  └─Create Another─▶ idle
```

(`send-upload-options.js:175-185`, capture-phase) — back from `confirming`
goes to `choosing-options` even in secret mode. **This is a bug** — see §10.

## 7. What is Implemented (verified by reading code)

- 5-step stepper with labels Upload / Options / Confirm / Encrypt & Upload / Done — `upload-constants-patch.js:11-12`.
- Stepper `Step N of 5` updates correctly because `stepForState` is overridden to read the public `STATE_TO_STEP` (the v0.3.0 closure-bound original could not be updated by patching the property alone) — `upload-constants-patch.js:34-36`, fixed in `ff9c1f8`.
- Secret tab renders alongside File tab — `upload-step-select-secret.js:36-48,131-144`.

## 8. What is Missing

- **No internationalisation in the new secret elements.** Every visible string is hard-coded English. The base UI uses `data-i18n` attributes and the `I18n` module (`v0.3.0/_common/js/i18n.js`); none of `upload-step-done-secret.js`, `upload-step-select-secret.js`, `upload-step-options.js`, `send-secret-view.js` reference `I18n` or `data-i18n`. Searches return zero matches.
- **No "Email Link" pre-population beyond a static body** — `upload-step-done-secret.js:120-126` builds a generic `mailto:` body with the share URL. There is no recipient field, no subject customisation, no warning if the user's mail client truncates long links.
- **No QR code** for the share link or kill link. The base UI loads `qr-code.js` for the file-flow `<upload-step-done>`, but the secret-done element does not consume it.
- **No "Save kill link to clipboard automatically" or download-as-file** — the kill link is shown once and can be lost forever.
- **No accessibility roles/aria** on the secret-done element — the share/kill inputs are `readonly` text inputs with no `aria-label`; the buttons rely on visible emoji labels only. The base wizard has some `aria-current="step"` on the indicator (`send-step-indicator.js:50`) but the new elements do not extend that pattern.
- **No telemetry / no transparency receipt display** in the secret done element. The file-flow done element renders `result.transparency`; the secret done element ignores it.
- **No "view as recipient would" preview** before the link is shared.
- **No protection against the user navigating away from the Done screen** — `_setBeforeUnload(false)` runs at the start of `complete` (`send-upload.js:520`), so the kill link can be lost on accidental refresh.
- **No analytics or "link visited" indicator** for the sender (out of scope for zero-knowledge design — but worth noting).
- **No bulk operations / no "download both links as .txt"** — no file export of the share + kill pair.
- **No share-mode variants for secrets.** Only Simple `token` is wired (`send-upload-secret.js:59`). The Options panel hides the pill row entirely in secret mode — Combined-link and Separate-key modes are not considered, which is fine but should be documented (see commit `e383472` message: "other share modes are not wired for secrets yet; can be added later").
- **No "max payload size" guard surfaced to the secret tab** — the textarea is unbounded and the size limit message ("Maximum upload: 5 MB") only appears on the File tab (`upload-step-select-secret.js:106-110`). A 6 MB pasted secret would fail at upload time with an opaque error.
- **No reality-doc entry for the kill link route in `send-api/index.md`** beyond the brief mention; the recipient view route is logged but the kill route's interaction with delete-auth-hash is not in the reality doc.

## 9. Bugs

### Confirmed (read-from-code)

1. **Duplicate "Email Link" button on the Done screen in secret mode** — confirmed by reading code.
   - Root cause: the v0.3.0 `_render` (`send-upload.js:147-148`) writes `<button id="upload-email-btn">Email Link</button>` into `.upload-header-row__action` whenever `_state === 'complete'`. The v0.3.2 `_render` patch (`send-upload-options.js:124-142`) only handles the `choosing-options` state for the action slot — it does not clear or replace the slot for the `complete + isSecretMode` case.
   - Effect: on Step 5 the user sees an Email Link button in the top-right header AND an Email Link button inside `<upload-step-done-secret>`. Both work but they build different mailto bodies — the header one ends up using `result.combinedUrl` (which has been rewritten to the secret URL by the engine patch), so functionally they are not catastrophic, but the body text differs ("encrypted file" vs "secret"). UX is broken.

2. **Back from Confirm in secret mode lands on the (delivery/share) Options screen** — confirmed by reading code.
   - Root cause: `send-upload-options.js:179-185` and `:236-238` both define a `step-back` capture-phase handler that, when `_state === 'confirming'`, sets `state = 'choosing-options'`. There is no `_isSecretMode` check. The secret flow never visited `choosing-options` (it jumps `idle → confirming` directly per `ff9c1f8`), but Back goes there anyway.
   - Effect: clicking Back on the secret Confirm step shows the Options screen (delivery cards) for a `secret.txt` blob, then the user has to click Back again to reach the Secret tab. The `_isSecretMode` flag is preserved but the file flow's Options screen is not the right back-target. (The screenshot does not exercise this — back is on Step 3, not Step 5 — but it's the closest UX bug to the screen.)

3. **`step-back` from Step 5 is not handled at all** — confirmed by reading code.
   - The done-secret element does not render any back affordance (correct — Step 5 is terminal in the stepper), but the stepper itself only marks step ≤ active as clickable. With `step=5`, all of 1-4 are "completed" and clickable. Clicking step 4 (Encrypt & Upload) re-fires `step-nav` with `step=4`. The v0.3.2 capture handler (`send-upload-options.js:188-206` and `:240-247`) only handles steps 1, 2, 3 — step 4 falls through with `stopImmediatePropagation()` already called, so clicking the "Encrypt & Upload" pill on a completed secret link is a silent no-op. Same applies for clicking step 5 once on it. Low severity; debatable whether this is a bug or by design.

4. **`secretConfig` setter on `<upload-step-done-secret>` does NOT call `_render()`** — confirmed by reading code.
   - `upload-step-done-secret.js:26` defines `set secretConfig(v) { this._secretConfig = v; }` (no render). `set result(v) { this._result = v; this._render(); }` does render, so the orchestrator's `_syncComponent('done-secret')` carefully sets `secretConfig` first then `result` second (`send-upload-options.js:114-115`) to avoid a blank notice. This is fragile — any future call site that sets these in the wrong order silently breaks the ephemerality notice. Bug 2 of `62d01df` was exactly this issue and the workaround was the ordering, not a fix to the setter. Suspect-but-likely.

5. **`expires_at` contract drift** — confirmed by reading code (status: probably resolved by commit `cd90038` but frontend comments still flag it).
   - Frontend sends `expires_at: int milliseconds since epoch` (`send-upload-secret.js:55-57`, `api-client-v032.js:32`). The frontend code/comments at `send-upload-secret.js:15-19` and `api-client-v032.js:13-17` still warn that backend `Schema__Transfer.expires_at` was a `str`. The git log shows `cd90038 fix(transfer): change expires_at from ISO-8601 str to int ms since epoch` — the backend has been updated to match. The stale frontend comments should be removed.

### Suspected (needs runtime verification)

6. **`UploadStepSelect` mode reset on resetForNew** — `_resetForNew` (`send-upload.js:574-587`) does NOT reset the Step 1 element's `_inputMode`. After "Create Another Secret", the orchestrator returns to `state='idle'` but the existing Shadow-DOM `<upload-step-select>` instance still has `_inputMode='secret'`. This is probably the desired behaviour (user wanted to make another secret, so keep the Secret tab open), but if the user wanted a file upload they would have to click [File] manually. Not strictly a bug.

7. **Share-link copy fallback uses `document.execCommand` which is deprecated** — works in current browsers but flagged for the future. `upload-step-done-secret.js:151`.

8. **No size guard on secret text** — see §8 missing item; will fail at upload with `Upload failed: 413` or similar with no graceful UI handling on the secret-done path because the orchestrator's error handling switches `state='error'`, leaving the user on the empty "error" element with whatever `errorMessage` was set.
