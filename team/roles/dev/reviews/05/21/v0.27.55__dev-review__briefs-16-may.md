## Overview

Day 66 is a large batch with a wide surface area. Fourteen documents, 72 new PROPOSED items, five distinct thematic clusters. Some pieces are buildable in a day; others are 2-3 week efforts. This review classifies work by effort, identifies dependencies, and flags which pieces unblock the most downstream work.

The good news: most of the new work is composition, not invention. The infrastructure primitives (DNS, TLS, Fargate, container hosts, credential manager, pre-auth metering, observability) are in place or in build. Day 66 uses those primitives to build demo experiences, testing frameworks, operational tooling, and product surfaces. The substrate is mostly done; the applications are the work.

## Work Classification by Effort and Priority

### Stream A: Demo + Testing + CI (4-6 weeks total; parallelisable)

**Priority: CRITICAL PATH — blocks demo push**

#### A1: Vault Demo Capabilities (P-128 to P-132)
**Effort:** 2-3 weeks

What actually needs building:
- **Read-only polish** (~3-5 days): visual indicator (badge/banner), mobile responsiveness audit, polished load experience, "make this your own" CTA. Mostly CSS + small JS changes. Buildable quickly.
- **Cross-vault navigation** (~1-2 days): decide and implement the new-tab default for cross-vault links. Small change. Does not require new infrastructure.
- **Session-scoped state shim** (~1 week): the big new feature. In-memory map keyed by vault path; overrides read operations for the session; writes land in the map instead of the vault. Survives in-vault navigation (same tab, different page); discarded on reload. The implementation is not complex but needs careful integration with every JS API read/write path. Risk: missing a code path that bypasses the shim. Mitigation: test each read/write operation systematically.

Dependencies: JS API surface spec (see Architect review). The shim needs to wrap the JS API; if the API changes, the shim changes.

#### A2: Vault Testing Framework (P-133 to P-137)
**Effort:** 2-3 weeks

What needs building:
- **Vitest setup for unit/integration layers**: a `vitest.config.js` that knows about vault contexts; probably a `@sgraph/vault-test` package that wraps Vitest with vault-aware helpers.
- **Playwright setup for browser layer**: a `playwright.config.ts` that knows about our vault URLs and share-token patterns; probably an `openVault` helper that sets up the browser session correctly.
- **Test definition format**: the unified format with `layer: 'unit' | 'integration' | 'qa' | 'browser'`. This is a thin orchestration layer on top of Vitest/Playwright.
- **Fixture vault support**: a decision on fixture location (recommendation: in the vault itself) plus helpers for loading fixtures.
- **Reference test suite** for the CV vault: 5-10 tests across all four layers to validate the framework works end-to-end.

Dependencies: vault demo capabilities (A1) must be done first — the QA and browser test layers use session-scoped changes.

#### A3: Vault App CI Pipeline (P-138 to P-141)
**Effort:** 1-2 weeks

What needs building:
- **GitHub Actions workflow file** for the vault app repo: triggers on commit, runs unit tests, iterates the vault registry, reports.
- **Vault test registry as manager vault**: a vault holding the list of registered vaults + per-vault test configuration. Small vault schema; needs a reader in the CI workflow.
- **sg-compute bridge in CI**: the CI workflow calls `sg-compute fargate run-task` or `sg-compute container run` to spin up isolated test environments. This is composing existing primitives, not new infrastructure.
- **Failure report format**: link to the failing vault's commit history + reproduction command.

Dependencies: vault testing framework (A2) must exist first. CI automates running tests that exist.

#### A4: Nova + AgentCore POC (P-142 to P-146)
**Effort:** 1 week

What needs building:
- **FastAPI service** with two endpoint groups (`/nova/invoke` and `/agentcore/invoke`).
- **Mini UI**: model selector, prompt textarea, result panel, session history. Same pattern as other mini UIs we have built.
- **sg-compute aws bedrock integration**: this is already done per previous briefs; wire it up.
- **Nova Act SDK**: `pip install nova-sdk` (or equivalent); wrap in the `/nova/act` endpoint.
- **Cost/token logging**: every invocation writes a log entry with model, tokens in, tokens out, cost estimate, latency.

Dependencies: none beyond existing SG/Compute bedrock CLI work. This is the most self-contained item in the batch.

### Stream B: Accountant Demo (3-4 weeks; depends on A1)

**Priority: HIGH — first major demo; template for others**

#### B1: Accountant Demo (P-147 to P-152)
**Effort:** 3-4 weeks

What needs building:
- **FastAPI orchestration service** (~1 week): 6 endpoints (sessions, setup, step/N, state, teardown). Holds AWS credentials and orchestration logic. Idempotent operations (creating a session twice is safe).
- **Accountant vault app** (~1 week): forms, client lists, report drafting interface, approval workflow. Role-aware routing at `/accountant`. Uses existing vault JS API + session-scoped changes from A1.
- **Client vault app** (~1 week): data entry forms, document upload interface, signature flow, confirmation views. Role-aware routing at `/client`.
- **12-step workflow content**: the starter data, each step's state transitions, narrative text per step. More content work than code work.
- **Infographic generator integration**: step 7 (report generation) calls the existing infographic tool.
- **Nova integration**: 3-4 steps that call the Nova POC from A4.
- **Auto-teardown**: idle timeout (15-20 min) that calls the teardown endpoint. Reuses the reset-on-activity pattern from container hosts.

Dependencies: vault demo capabilities (A1) for session-scoped changes and read-only opening; Nova + AgentCore POC (A4) for the LLM steps; on-demand provisioning (D1) for the infrastructure setup step.

Implementation note: "same vault, two apps" via role-based routes is the key design. The vault app SPA detects the role from the URL parameter and branches rendering. This is a new SG/App framework capability that needs to work correctly before the demo can be built. Plan for the framework extension first.

### Stream C: Vault Discovery + AppSec Mini-Tools (4-6 weeks; partially parallelisable)

**Priority: HIGH for vault discovery; MEDIUM for AppSec mini-tools**

#### C1: Vault Discovery + Public Keys (P-153 to P-158)
**Effort:** 2-3 weeks

What needs building:
- **Vault key audit**: read the current vault format code; document what keys exist today and what gaps the Ed25519/X25519 proposal fills. (~2 days)
- **Ed25519/X25519 key generation**: generate key pair at vault creation; store public key in vault metadata; store private key encrypted. (~3 days)
- **Discovery endpoint** at `/.well-known/vaults`: reads all vaults on the server; returns JSON filtered by visibility. (~3 days)
- **Visibility metadata**: add `visibility` field to vault metadata (default: `private`). (~1 day)
- **Public key in metadata**: serialize public key into vault metadata for the discovery endpoint to include. (~1 day)
- **"Send to vault" endpoint**: `POST /vault/{id}/inbox` — accepts encrypted content (encrypted by sender to vault's public key); stores in vault's inbox path. (~3 days)
- **Demo server catalogue UI**: simple HTML page that renders the discovery endpoint's output. (~2 days)

Note: the offline-bundle story (Docker image with bundled vaults) is a packaging exercise that should happen after the vault discovery endpoint works.

#### C2: AppSec Mini-Tools — StrideGPT (P-159 to P-164)
**Effort:** 4-6 weeks

Prerequisite: contact Matt Adams (StrideGPT maintainer) before building. Understanding his integration preferences avoids duplicating work or creating tension.

What needs building:
- **AppSec vault schema**: data structure for threat-modelling artefacts. JSON schema for system descriptions, threat lists, attack trees, mitigations, evidence. (~2 days)
- **StrideGPT wrapper**: a thin wrapper repo that runs StrideGPT as a service, with our vault integration layer on top. The wrapper handles: reading system description from vault, calling StrideGPT, writing results back to vault. (~1 week)
- **Client-side mode**: the vault app includes the StrideGPT wrapper as a WASM module or iframes a hosted version. (~1 week)
- **Ephemeral compute mode**: a Fargate task that runs the StrideGPT wrapper against a vault; triggered from the vault app UI. (~1 week)
- **Infographic integration**: attack tree visualisation via the existing infographic generator. (~3 days)
- **Nova integration**: use Nova Lite for routine analysis; Claude 4.5 for quality analysis. Route through the Nova POC from A4. (~3 days)
- **Per-invocation pricing**: wire through the pre-auth substrate. Each threat-model run is a metered transaction. (~2 days)

Estimated total: 4-6 weeks for a credible v1 with both modes.

### Stream D: Serverless + Multi-Cloud + SG Mail (5-7 weeks; sequential dependencies)

**Priority: HIGH for serverless framing + DNS fix; MEDIUM for multi-cloud; HIGH for SG Mail**

#### D1: DNS Pinning Fix + Address Router (P-190 to P-194)
**Effort:** 1-2 weeks

What needs building:
- **Holding-page-detects-readiness Lambda update**: extend the existing holding-page Lambda to check provisioning state per request (read from admin vault or DynamoDB); return HTTP 302 when the instance is ready. (~3 days)
- **Short TTL on wildcard DNS record**: configuration change in Route 53 (30s TTL). (~1 day)
- **Randomised ephemeral address generation**: function that generates `ephemeral-{random}.sgraph.app` names; registers them in the address router state. (~2 days)
- **"Found existing instance, want to join?" UX**: the holding-page Lambda checks for a running instance and serves the choice UX. (~2 days)
- **Multi-instance-per-user state**: the address router tracks multiple instances per user; the "choose which instance" UI lists them. (~2 days)

This is the most important near-term fix — it affects every demo and customer-facing provisioning flow.

#### D2: Admin Interface as Vault App + DNS Registry (P-195 to P-199)
**Effort:** 2-3 weeks

What needs building:
- **Admin vault schema** (labs, policies, state, audit): the data structure for the labs registry. (~2 days)
- **Admin vault app UI**: list/create/inspect/wake/sleep/teardown/cost panels. Follows the standard vault app pattern. (~1 week)
- **DNS sync process**: reads admin vault on commit; creates/updates/removes Route 53 A records to match. Can be a Lambda triggered on vault change or a scheduled reconciliation job. (~3 days)
- **Three lab state transitions**: cold→provisioning (trigger provision), provisioning→live (DNS A record flip from Lambda IP to instance IP), live→cold (DNS A record flip back, instance stop). (~3 days)
- **TXT records for public keys**: when a vault has a public key (from C1), write a TXT record. Extends the DNS sync process. (~1 day)

Dependencies: vault discovery + public keys (C1) for the TXT record feature; holding-page Lambda (D1) for the routing behaviour.

#### D3: SG/Compute Serverless Framing (P-165 to P-169)
**Effort:** 1-2 weeks (mostly documentation + measurement)

This is mostly a framing and measurement exercise, not new code:
- **Cold-start measurement**: run the existing container host and Fargate substrates against real workloads; capture numbers; document them. (~3 days)
- **Serverless reference example**: a minimal vault-app that demonstrates cold-start, warm-state, and teardown lifecycle. Probably just the CV demo vault in a clean deployment. (~2 days)
- **Documentation update**: canonise "serverless for agents" as the framing in key docs. (~1 day)
- **Pre-warmed pool implementation**: extend the container hosts primitive to support a warm pool of pre-started containers (the actual pool logic is the new work). (~1 week)

#### D4: SG/Deploy + Multi-Cloud (P-170 to P-174)
**Effort:** 1-2 weeks for the experiment

What needs building:
- **New SG/Deploy repo**: bare-bones repo with its own CLI entry point (`sg-deploy`). (~1 day)
- **GCP Cloud Run deployment**: `sg-deploy gcp cloud-run deploy` command; uses GCP credentials; pushes Docker image to GCR; deploys to Cloud Run; returns the URL. (~3 days)
- **Akamai Cloud deployment**: `sg-deploy akamai linode deploy` command; provisions a Linode; SSHs in; runs docker-compose or equivalent. (~3 days)
- **Shared manager vault for SG/Deploy ↔ SG/Compute communication**: create a vault; define the schema for agent-to-agent messages (request, response, error). (~2 days)
- **One working cross-agent operation**: SG/Deploy asks the credential manager vault for scoped credentials; SG/Compute processes the request; SG/Deploy receives the response. (~2 days)

This is a week of work, not a month. The experiment is about validating the architecture, not building a production multi-cloud platform.

#### D5: SG Mail v1 (P-175 to P-182)
**Effort:** 3-4 weeks

What needs building:
- **email-fs audit**: read the existing email-fs code; document what exists and what's missing. (~2 days)
- **Email vault schema**: mailboxes, threads, messages, attachments, contacts. Extends email-fs. (~2 days)
- **AWS SES inbound connector**: configure SES to receive mail → drop to S3 → S3 event trigger Lambda → read EML → write to vault via email-fs. (~3 days)
- **AWS SES outbound connector**: vault compose → call our outbound service → SES API → recipient. (~2 days)
- **Email web app UI** — the main work (~2 weeks): inbox, folders, thread view, compose, reply, forward, search, contacts, attachments, mobile-responsive. This is a full email client UI, built as a vault app. Standard UX patterns but non-trivial to do well.
- **WorkMail migration tool**: script that reads mbox/maildir export from AWS WorkMail; parses each message; commits to vault via email-fs. (~2 days)
- **Multi-provider backup for email vault**: extend backup infrastructure from E1 to cover the email vault across tiers 1 (cross-account S3) and 5 (Backblaze B2). (~3 days)
- **DNS configuration**: MX pointing to SES, SPF record, DKIM CNAME records from SES, DMARC policy. All configuration, no code. (~1 day)

The email web app UI is the critical path. Everything else is plumbing.

## Implementation Risk Assessment

| Risk | Severity | Mitigation |
|------|---------|-----------|
| Session-scoped state shim misses a JS API code path | HIGH | Systematic testing of every read/write path before shipping |
| QA test isolation breaks between test runs | MEDIUM | Explicit session-scope-per-test guarantee; document the contract |
| DNS pinning fix doesn't fully solve the issue across resolvers | MEDIUM | Test with 4+ resolver types; document known limitations |
| email-fs code is further from production-ready than expected | MEDIUM | Audit first (2 days); surface gaps before committing to timeline |
| StrideGPT maintainer is unresponsive or has concerns about integration | LOW | Start with a wrapper that doesn't fork; contribute upstream PRs to de-risk |
| SG/Deploy repo maintenance overhead grows | LOW | Keep the boundary clean; no shared code with SG/Compute |
| Multi-provider backup cost grows faster than expected | LOW | Monthly cost review; per-vault cost attribution |
