## 1. Mounting site decision

**Decision: Separate `vault-tool-api.js` module, loaded in `index.html`.**

Rationale: `vault-shell.js` is a non-module IIFE. `SgToolApi` ships as an ES module from `dev.tools.sgraph.ai`. Putting the import in a separate `vault-tool-api.js` (loaded with `type="module"`) keeps vault-shell.js clean and follows the `video-creator` pattern of separating the API surface from the component implementation.

The module listens for `shell-ready` on `window.sgraphVault.events` (emitted in `VaultShell.connectedCallback` immediately after `window.sgraphVault.shell = this`), then constructs and activates the `SgToolApi` instance. This ensures the shell reference is available before api registration.

Path: `_common/js/components/vault-tool-api/vault-tool-api.js`  
Constants: `_common/js/components/vault-tool-api/vault-events.js`

## 2. `waitForReady()` semantics

"Ready" means all three conditions are true simultaneously:
1. `window.sgraphVault.shell` is set (fires `shell-ready`)
2. `shell._vault` is a live `SGVault` instance (fires `vault-opened`)
3. `shell._dataSource` is a live `VaultDataSource` (set in `_mountBrowse()`, synchronous with `vault-opened`)

**Signal chain:**
- `vault-opened` on `window.sgraphVault.events` fires at line 194 of vault-shell.js, inside `_onVaultOpened`, after `_mountBrowse()` completes (which sets `this._dataSource` and `this._browse`).

**Edge cases handled:**
- If `waitForReady()` is called after vault is already open → resolves immediately
- If called before vault is open → waits for `vault-opened` event
- `timeout` (default 30 s) rejects with `TimeoutError`

## 3. `navigateTo(tab)` render-complete detection

`send-browse._openFileTab(path)` uses `requestAnimationFrame` + `await dataSource.getFileBytes()` + `_renderFileContent()`. There is no emitted signal when rendering completes.

**Proposed mechanism:** Polling with deadline.

After calling `browse._openFileTab(tab)`:
1. Wait 100ms for the `requestAnimationFrame` to fire and "Loading..." to appear
2. Poll every 50ms on `browse._sgLayout.getPanelElement(tabId)`
3. Resolve when the panel's textContent no longer includes `'Loading...'` and has meaningful length (> 50 chars)
4. Emit `vault:navigation-complete` after resolve

**`vault:section-rendered` enhancement (Phase 1.1):** Patch `send-browse._renderFileContent` to emit `vault:section-rendered` via `window.dispatchEvent`. This replaces polling with a cleaner event path. For Phase 1, polling is sufficient for Playwright screenshot use-cases.

## 4. `getState()` shape

```js
{
  vaultId:    string | null,   // shell._vault._vaultId
  title:      string | null,   // shell._vault._settings.vault_name || shell._vault.name
  decrypted:  boolean,         // !!shell._vault
  syncState:  { ahead: number, behind: number, diverged: boolean },
  activeView: 'files' | 'sgit' | 'settings',
  openTabs:   string[],        // Array.from(shell._browse._openTabs.keys())
}
```

All fields read synchronously from existing shell state. Never throws.

## 6. Phase 2 / Phase 3 deferral

Phase 1 ships first:
- 4 methods: `getState`, `waitForReady`, `navigateTo`, `getSkills`
- 3 SKILL files
- Event bridging: `vault:opened`, `vault:locked`, `vault:navigation-complete`

Phase 2 (file read ops) and Phase 3 (mutations + push/pull) are deferred until documentation agents and QA have exercised Phase 1 in real workflows. The data source methods (`getTree`, `getFileList`, `getFileBytes`, `saveFile`, etc.) are already fully implemented in `VaultDataSource` — Phase 2/3 is purely additive registration, not new logic.

---

## 7. Backward compatibility

`window.sgraphVault.events` listeners are untouched. The SgToolApi layer is purely additive:
- Existing `sgraphVault.events.emit('vault-opened', ...)` continues to fire
- The tool API bridges these events to `window` CustomEvents with `instanceId`
- No existing component code is modified; vault-tool-api.js only reads from shell internals

---

## 8. No vault-specific divergence from `sg-tool-api`

Confirmed:
- `slug: 'vault'` — no `window.__vault`
- Uses standard registry: `window.__tool`, `window.__tools`, `window.__tool_registry.find('vault')`
- `activate()` is called — publishes `window.__tool`, fires `tool:ready`
- No custom registry, no skipping the activation step
- Event names follow `tool:*` and `vault:*` namespace conventions
