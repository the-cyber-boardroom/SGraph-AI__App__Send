# Change 5 — Iframe Write API: Design Review

**Role:** Dev
**Version:** v0.2.2
**Date:** 2026-05-08
**Status:** Design — not yet implemented (planned for v0.2.3)

---

## Context

Changes 1–4 (v0.2.2) gave HTML files rendered inside the vault viewer a read path via the VFS bridge: `fetch()`, `img.src`, and anchor navigation all resolve against the vault. Change 5 adds a **write path**: an HTML page running inside the iframe can save content back to the vault — creating or updating files, triggering an encrypted commit.

This is the foundation for vault-hosted apps (forms, editors, generators) that need to persist state.

---

## 1. What the Iframe Can Already Do (Read Side, v0.2.2)

The VFS bridge injected into every HTML iframe handles:

| Mechanism | How | Message envelope |
|-----------|-----|-----------------|
| `fetch(relativeUrl)` | Intercepted in iframe, resolved via postMessage | `__sgVfsReq` / `__sgVfsReply` |
| `img.src = relativeUrl` | `HTMLImageElement.src` setter overridden | same |
| `<a href="relativeUrl">` click | Click event listener, preventDefault | `__sgVfsNavReq` |

The parent (send-browse) listens on `window.addEventListener('message', vfsBridge)` and routes all `__sgVfsReq` messages through `dataSource.getFileBytes(resolvedPath)`.

The iframe's `contentWindow` is the source-of-truth identity check: `e.source !== iframeEl.contentWindow` guards all bridge messages.

---

## 2. Write API Design

### 2.1 Iframe-side surface (`window.sgVault`)

The bridge script injected into the iframe exposes a minimal API object:

```javascript
window.sgVault = {
    // Write a file to the vault. path is relative to the HTML file's directory.
    // content: string | Uint8Array | ArrayBuffer
    // Returns Promise<{ path: string, size: number }>
    writeFile: async function(path, content) { ... },

    // Read the current text content of a vault file (same path resolution as fetch).
    // Returns Promise<string>
    readFile: async function(path) { ... },

    // List files visible to this iframe (same as getFileList, filtered to writable vault).
    // Returns Promise<[{ path, name, size }]>
    listFiles: async function() { ... },

    // True if the vault is writable (accessKey present).
    writable: true | false,

    // The vault-relative path of the HTML file currently being rendered.
    selfPath: 'path/to/current-page.html',
};
```

`readFile` and `listFiles` already exist on the read side via `fetch()` and the VFS bridge — they are convenience wrappers, not new network calls. Only `writeFile` requires a new message type.

### 2.2 New postMessage envelope: `__sgVfsWriteReq`

```javascript
// iframe → parent
window.parent.postMessage({
    __sgVfsWriteReq: requestId,   // random ID (same scheme as __sgVfsReq)
    path: 'relative/path.json',   // path relative to iframe's htmlDir
    data: base64String,           // base64-encoded file content
    encoding: 'base64',           // always 'base64' for now (handles binary cleanly)
}, '*');

// parent → iframe (reply)
iframe.contentWindow.postMessage({
    __sgVfsWriteReply: requestId,
    ok: true,
    size: 1234,                   // bytes written
    // or on failure:
    ok: false,
    err: 'Read-only vault'        // human-readable error message
}, '*');
```

Base64 is chosen for the wire format because `ArrayBuffer` transfer via postMessage works but requires care (the buffer becomes detached in the iframe after transfer). Base64 avoids that class of bug at the cost of ~33% size overhead — acceptable for file content that's going to be encrypted anyway.

### 2.3 Path resolution

The same `_resolvePath(htmlDir, relativePath)` function used for reads applies to writes. `htmlDir` is the directory of the currently-loaded HTML file:

```
htmlDir = 'reports/'          (for 'reports/index.html')
path    = '../data/out.json'
resolved → 'data/out.json'
```

Resolved paths are validated against the vault file list before write:

- The **folder** must exist (or be creatable — see section 2.4)
- Path traversal outside the vault root (`../../../etc`) is rejected
- The resolved path must not be `.vault-settings.json` (protected)

### 2.4 Folder creation policy

`VaultDataSource.saveFile(folderPath, fileName, bytes)` already handles the add-vs-update decision by checking `folder.children[fileName]`. It does **not** create the folder if it doesn't exist — it throws `Folder not found`.

For the write API, the parent-side handler needs to auto-create intermediate folders:

```javascript
// Before calling dataSource.saveFile():
async function _ensureFolderExists(dataSource, folderPath) {
    try {
        // vault.needsLoading checks if the node exists in-memory tree
        if (!self.dataSource._vault._findNode(folderPath)) {
            await self.dataSource.createFolder(folderPath);
        }
    } catch (_) {}
}
```

Each `createFolder` call commits to the vault. For an iframe writing to `data/results/output.json` where neither `data/` nor `data/results/` exist, that is **two extra commits** before the file write commit. This is acceptable for the initial implementation; a batched "create folder + add file" in a single commit is an optimisation for later.

## 3. Parent-Side Handler

Added inside the existing `vfsBridge` function in `send-browse--v0.3.2.js`, alongside the existing `__sgVfsNavReq` and `__sgVfsReq` handlers:

```javascript
// ── Change 5: vault write from iframe ──────────────────────────────────────
if (e.data.__sgVfsWriteReq) {
    var writeId   = e.data.__sgVfsWriteReq;
    var writePath = e.data.path;
    var writeData = e.data.data;     // base64 string

    // Guard: only writable vaults
    if (!self.dataSource || !self.dataSource.writable) {
        e.source.postMessage({ __sgVfsWriteReply: writeId, ok: false, err: 'Read-only vault' }, '*');
        return;
    }

    // Resolve path relative to iframe's current htmlDir
    var resolved = _resolvePath(htmlDir, writePath);

    // Security: reject path traversal outside vault root
    if (!resolved || resolved.startsWith('../') || resolved.includes('/../')) {
        e.source.postMessage({ __sgVfsWriteReply: writeId, ok: false, err: 'Invalid path' }, '*');
        return;
    }

    // Security: protect vault internals
    if (resolved === '.vault-settings.json' || resolved === '.vault-settings') {
        e.source.postMessage({ __sgVfsWriteReply: writeId, ok: false, err: 'Protected file' }, '*');
        return;
    }

    // Decode base64 → bytes
    var bytes;
    try {
        var bin = atob(writeData);
        bytes   = new Uint8Array(bin.length);
        for (var i = 0; i < bin.length; i++) bytes[i] = bin.charCodeAt(i);
    } catch (decodeErr) {
        e.source.postMessage({ __sgVfsWriteReply: writeId, ok: false, err: 'Bad encoding' }, '*');
        return;
    }

    // Split resolved path into folder + file
    var slashIdx   = resolved.lastIndexOf('/');
    var writeDir   = slashIdx > 0 ? '/' + resolved.slice(0, slashIdx) : '/';
    var writeFile  = resolved.slice(slashIdx + 1);

    // Ensure folder exists, then save
    _ensureVaultFolder(self.dataSource, writeDir)
        .then(function() {
            return self.dataSource.saveFile(writeDir, writeFile, bytes.buffer);
        })
        .then(function() {
            e.source.postMessage({
                __sgVfsWriteReply: writeId,
                ok: true,
                size: bytes.byteLength
            }, '*');
            console.log('[sg-vfs parent] wrote', resolved, bytes.byteLength, 'bytes');
        })
        .catch(function(err) {
            console.error('[sg-vfs parent] write failed:', resolved, err);
            e.source.postMessage({
                __sgVfsWriteReply: writeId,
                ok: false,
                err: err.message || 'Write failed'
            }, '*');
        });
    return;
}
```

`_ensureVaultFolder` is a module-level async function that walks the path components and calls `dataSource.createFolder()` for any missing node, suppressing errors on already-existing folders.

## 4. Iframe-Side Bridge Additions

The `window.sgVault` object is injected as part of the `vfsBridgeScript` string, appended after the existing `_vfsReq` helper. The write request uses the same request-ID + reply-listener pattern as `_vfsReq`:

```javascript
// Injected into iframe as part of vfsBridgeScript:
'window.sgVault = {' +
  'writable: ' + (self.dataSource && self.dataSource.writable ? 'true' : 'false') + ',' +
  'selfPath: ' + JSON.stringify(fileName) + ',' +

  'writeFile: function(path, content) {' +
    'return new Promise(function(res, rej) {' +
      // Encode content to base64
      'var bytes;' +
      'if (typeof content === "string") {' +
        'bytes = new TextEncoder().encode(content);' +
      '} else {' +
        'bytes = content instanceof Uint8Array ? content : new Uint8Array(content);' +
      '}' +
      'var b64 = btoa(String.fromCharCode.apply(null, bytes));' +
      // Send write request
      'var id = (Math.random()*1e9|0).toString(36) + Date.now().toString(36);' +
      'function h(e) {' +
        'if (!e.data || e.data.__sgVfsWriteReply !== id) return;' +
        'window.removeEventListener("message", h);' +
        'if (e.data.ok) res({ path: path, size: e.data.size });' +
        'else rej(new Error(e.data.err || "Write failed"));' +
      '}' +
      'window.addEventListener("message", h);' +
      'window.parent.postMessage({ __sgVfsWriteReq: id, path: path, data: b64, encoding: "base64" }, "*");' +
    '});' +
  '},' +

  'readFile: function(path) {' +
    'return fetch(path).then(function(r) { return r.text(); });' +
  '},' +

  'listFiles: function() {' +
    'return fetch("/__sg-vfs-list__").then(function(r) { return r.json(); }).catch(function() { return []; });' +
  '}' +
'};'
```

`readFile` re-uses the existing `fetch()` override — zero new machinery. `listFiles` uses a special sentinel URL `/__sg-vfs-list__` that the parent intercepts and returns the file list as JSON (one additional message type to add to the read bridge, trivial).

## 5. Commit Semantics

Each `writeFile` call results in exactly **one vault commit** (possibly preceded by folder-creation commits if the path is new). The commit message is auto-generated:

```
Add path/to/file.json          (new file)
Edit path/to/file.json         (existing file updated)
```

This mirrors the existing `addFile` / `updateFile` commit messages in `sg-vault--file-ops.js`.

**No batching of multiple writes** in the initial implementation. If an iframe calls `writeFile` twice in quick succession, that is two commits. Batching (collect writes over a debounce window, commit once) is a v0.2.3+ optimisation. The current vault commit path is fast enough (~200ms per commit including encryption + network) that the simple approach is acceptable for the first version.

**UI feedback:** `VaultDataSource.onTreeChanged()` is called by `saveFile()` after every successful write. This triggers a tree refresh in the vault shell — the new/updated file appears in the file list immediately without a manual refresh.

## 6. Failure Modes and Error Handling

| Failure | Detection | Response to iframe |
|---------|-----------|-------------------|
| Vault read-only (no write key) | `dataSource.writable === false` | `{ ok: false, err: 'Read-only vault' }` immediately |
| Path traversal attack | `resolved.startsWith('../')` check | `{ ok: false, err: 'Invalid path' }` immediately |
| Protected file | `resolved === '.vault-settings.json'` | `{ ok: false, err: 'Protected file' }` immediately |
| Bad base64 | `atob()` throws | `{ ok: false, err: 'Bad encoding' }` immediately |
| Network error (encrypt/store fails) | `saveFile()` rejects | `{ ok: false, err: err.message }` |
| Folder missing (and createFolder fails) | `_ensureVaultFolder()` rejects | `{ ok: false, err: err.message }` |
| Concurrent write collision (two iframes) | Last-writer-wins at vault level | No special handling in v0.2.2 |
| iframe navigates away during pending write | `e.source` no longer valid | `postMessage` silently fails (no crash) |

The iframe-side `writeFile()` Promise rejects on any `ok: false` reply. The app in the iframe is responsible for catching and displaying errors.

## 7. Security Model

### What the iframe CAN do with the write API

- Write any file to any path within the vault that the user has the write key for
- Create new folders
- Overwrite existing files (including other HTML pages in the same vault)

### What the iframe CANNOT do

- Write outside the vault (the `_resolvePath` + path-traversal check prevents this)
- Write `.vault-settings.json` (explicitly blocked)
- Write without the user having the write key (the `writable` check blocks it before any crypto)
- Bypass encryption — all writes go through `SGVaultCrypto` / `SGSendCrypto` in the parent
- Make direct HTTP calls to the vault API — the iframe is sandboxed with `allow-scripts` only, no `allow-same-origin`, so it cannot use `fetch()` against the server directly (the VFS bridge is the only path)

### Trust model

The iframe content is HTML that came from the vault itself. This means the user already trusted this content by putting it there. The write API does not expand the trust boundary — it just makes the already-trusted content actionable. An iframe loaded from an untrusted external URL would not have the VFS bridge injected (the bridge is only injected for vault-sourced HTML via the blob URL path).

### Kill-switch

The write API can be disabled per-dataSource by setting a flag:

```javascript
self.dataSource._iframeWriteDisabled = true;
```

If set, the parent-side handler returns `{ ok: false, err: 'Write API disabled' }` immediately. This flag can be set from the vault shell via a vault-settings toggle ("Allow HTML apps to write to vault"). Default: **enabled** when `writable` is true.

## 8. Re-render After Write

When `writeFile` completes, `onTreeChanged()` fires and the file tree refreshes. The iframe itself is not automatically reloaded — it's the app's responsibility to update its own UI.

The typical pattern for a vault app:

```javascript
await window.sgVault.writeFile('data/results.json', JSON.stringify(results));
// Update the app's own UI:
document.getElementById('status').textContent = 'Saved ✓';
```

If the app wants to reload the updated file into itself (e.g., a live preview), it uses `fetch('data/results.json')` which goes through the VFS bridge and returns the new ciphertext → decrypted bytes from the parent. This will return the **committed** content (the parent re-reads from vault after the commit), not a stale cache.

## 10. Example: Vault App Using the Write API

A minimal form app that saves user input to `responses.json`:

```html
<!DOCTYPE html>
<html>
<body>
  <form id="f">
    <input name="name" placeholder="Your name">
    <button type="submit">Save</button>
  </form>
  <div id="status"></div>
  <script>
    document.getElementById('f').addEventListener('submit', async function(e) {
      e.preventDefault();
      var data = { name: e.target.name.value, ts: Date.now() };
      try {
        await window.sgVault.writeFile('responses.json', JSON.stringify(data, null, 2));
        document.getElementById('status').textContent = 'Saved ✓';
      } catch (err) {
        document.getElementById('status').textContent = 'Error: ' + err.message;
      }
    });
  </script>
</body>
</html>
```

This file lives in the vault. When the user submits the form, the parent encrypts the JSON and commits it to the vault as `responses.json`. The commit appears in `sgit log` immediately.
