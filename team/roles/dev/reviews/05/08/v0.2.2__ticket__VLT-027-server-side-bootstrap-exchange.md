# Ticket VLT-027 — Server-Side Bootstrap Exchange (Option A)

**Date:** 2026-05-08
**Milestone:** v0.4
**Priority:** Medium
**Team:** Explorer → Architect + Dev

---

## Summary

Currently, the vault opens by deriving encryption keys from the vault token client-side, then performing individual object-store GET calls to load the vault tree. The first load requires:

1. GET ref (named head commit ID)
2. GET commit (tree ID)
3. GET tree (file entry list)
4. Lazy GET per sub-tree (on demand)

**Option A (this ticket):** A single server-side `/vault/bootstrap` endpoint returns the commit, tree, and first-level sub-trees in one response — reducing the initial vault-open round-trip from 3–4 serial GETs to **1 GET + client-side decrypt**.

---

## Background

This was discussed in the real-time vault viewer design doc (`team/humans/dinis_cruz/claude-code-web/05/08/v0.2.2__design__real-time-vault-viewer.md`, Section 5). The current two-ref model requires:

- 1 GET to read named ref
- 1 GET to read commit
- 1 GET to read root tree
- N GETs for sub-trees (lazy)

For a vault with 3 folder levels, opening takes ~4 serial round-trips × 150ms = ~600ms latency on a slow connection. The bootstrap exchange compresses this to 1 request.

---

## Proposed API

### Server: `GET /vault/{vault_id}/bootstrap`

Returns the named-head commit + all objects reachable within 2 tree levels (root + immediate subfolders):

```json
{
  "schema": "vault_bootstrap_v1",
  "named_head_ref": "<ref_file_id>",
  "named_head_commit_id": "<commit_id>",
  "objects": {
    "<commit_id>":  "<base64 encrypted commit>",
    "<tree_id>":    "<base64 encrypted tree>",
    "<subtree_id>": "<base64 encrypted subtree>",
    ...
  }
}
```

The client decrypts all objects locally. If an object is missing (deep sub-tree), it falls back to the existing individual GET path.

### Client: `VaultDataSource.bootstrap()` (new method)

Replaces the initial 3-step load sequence:

```javascript
async bootstrap(vaultId) {
    const resp    = await this._sgSend.vaultBootstrap(vaultId);
    const objects = resp.objects;
    // Populate object cache with all pre-fetched ciphertext
    for (const [id, cipher] of Object.entries(objects)) {
        this._vault._objectStore.cacheRaw(id, cipher);
    }
    // Set named-head ref directly
    this._vault._namedHeadId = resp.named_head_commit_id;
    // Load tree from the cached commit (no network calls)
    await this._vault._loadTreeFromCommit(resp.named_head_commit_id);
}
```

---

## Security Considerations

- The bootstrap response contains only **encrypted ciphertext** — no plaintext, no keys
- The vault ID is derived from the vault token (HMAC-based, not guessable)
- The server does not decrypt or inspect object contents
- The bootstrap endpoint requires no authentication (same as existing object GETs)
- Object IDs are 256-bit content-addressed hashes — not enumerable

---

## Relationship to Real-Time Vault Viewer

The real-time viewer (named-ref-only model, VLT-025 PROPOSED) benefits from a fast bootstrap: the stale-check (`GET named_ref`) can fold into the bootstrap on first load, returning the current named-head commit in a single request.

## Open Questions

1. Should the bootstrap depth be configurable (1 level vs 2 levels)?
2. Should the bootstrap include blob content for small files (< 4 KB) as well as tree objects?
3. Should the bootstrap be optional or replace the existing sequential load entirely?
