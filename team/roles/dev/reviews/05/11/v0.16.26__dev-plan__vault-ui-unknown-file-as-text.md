# Dev Plan: Show Unknown-Extension Files as Text in Vault UI
**Version:** v0.16.26 | **Date:** 2026-05-11 | **Role:** Dev (Explorer)

---

## 1. Root Cause

**File:** `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.0/_common/js/components/send-download/send-browse.js`
**Function:** `_renderFileContent(container, bytes, fileName, type)` — lines 456–528

The final `else` branch (lines 521–527) renders "No preview available for this file type." whenever `type` is `null`:

```js
} else {
    content.innerHTML = `
        <div style="padding: 2rem; text-align: center; color: var(--color-text-secondary);">
            <div style="font-size: 3rem; margin-bottom: 1rem;">📄</div>
            <p>No preview available for this file type.</p>
            ...
        </div>`;
}
```

**Why `.issues` files hit this path:**
`FileTypeDetect.detect(fileName, null)` is called in `_openFileTab` (line 434). `FileTypeDetect` uses a pure extension lookup (`_extMap`). The extension `.issues` is not in `_extMap`, and no `contentType` is available (it is `null` for vault files). `detect()` returns `null`. The `null` type falls through all named branches (`'image'`, `'markdown'`, `'pdf'`, `'code'`, `'text'`, `'audio'`, `'video'`) to the `else` block.

The same applies to `.log` (present in `_extMap` as `'text'` — actually safe), `.config`, `.env` (present as `'code'`), and any file with no extension or an unlisted extension.

**Exact trigger condition:** `type === null` in `_renderFileContent` in the base `send-browse.js`.

---

## 2. Detection Strategy

Two-stage approach — extension whitelist first, content-sniff fallback:

**Stage 1 — Extension whitelist (already handled)**
`FileTypeDetect._extMap` already covers `.txt`, `.log`, `.md`, `.js`, `.json`, `.yaml`, `.env`, etc. These never reach the unknown path. No change needed here.

**Stage 2 — Content sniff for `type === null` (new)**
When `FileTypeDetect.detect()` returns `null`, inspect the raw `ArrayBuffer` for binary indicators before giving up:

- Sample the first **4096 bytes** (or the whole file if smaller)
- Check for **null bytes** (`\x00`) — strong indicator of binary data
- Attempt **UTF-8 strict decode** — if it throws, the content is not valid UTF-8

If neither check fails → treat as plain text (`'text'` type).

This correctly handles: `.issues`, `.config`, no-extension files (e.g. `Makefile`, `Dockerfile`), custom log formats, dotfiles (`.gitignore`, `.env.local`).

It will also correctly reject: `.zip`, `.png`, `.pdf`, `.docx`, `.wasm` — all contain null bytes or invalid UTF-8 sequences near the start.

**Size guard:** If `bytes.byteLength > 2 MB` and the file has no recognized extension, skip content-sniff and stay with the "No preview" path. This avoids blocking the main thread on large unknowns.

## 3. IFD Approach

**Do NOT touch** any base version file (`send-browse.js`, `send-browse--v0.3.2.js`).

**Target overlay:** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/_common/js/components/vault-browse-edit/vault-browse-edit.js`

This file already patches `SendBrowse.prototype._renderFileContent` by saving `_origRender` and calling it first, then adding vault-specific controls. The patch for unknown-as-text must be applied in the same IIFE, in the same `_renderFileContent` override.

**Approach:** Add a second monkey-patch of `_renderFileContent` **before** the existing `_origRender` save, so that unknowns are upgraded to `'text'` before the original render runs, making the change transparent to all downstream code (including the `isEditable` guard in the overlay itself).

Alternatively — and cleanly — inject `_isLikelyText` and then intercept `type` in the existing overlay patch by checking `type === null` and the content, then calling `_origRender` with the upgraded type. This requires changing one line in the existing patch but keeps the logic co-located.

**Recommended: pre-patch approach** — wrap `_origRender` once more to upgrade `null` → `'text'` when content is decodable. This keeps the existing overlay's `isEditable` logic working correctly without any additional changes.

## 4. Exact Code to Implement

Add the following block to `vault-browse-edit.js` **immediately before** the line:

```js
var _origRender = SendBrowse.prototype._renderFileContent;
```

### 4a. `_isLikelyText` helper

```js
// --- Helper: sniff ArrayBuffer for text vs binary ---
function _isLikelyText(buffer) {
    // Size guard: skip content-sniff for files > 2 MB with no known extension
    if (buffer.byteLength > 2 * 1024 * 1024) return false;

    var bytes = new Uint8Array(buffer, 0, Math.min(buffer.byteLength, 4096));

    // Null bytes are a near-certain binary indicator
    for (var i = 0; i < bytes.length; i++) {
        if (bytes[i] === 0) return false;
    }

    // Strict UTF-8 decode — throws on invalid byte sequences
    try {
        new TextDecoder('utf-8', { fatal: true }).decode(bytes);
        return true;
    } catch (_) {
        return false;
    }
}
```

### 4b. Pre-patch of `_renderFileContent` to upgrade `null` → `'text'`

```js
// --- Pre-patch: upgrade unknown-type files to 'text' when content is decodable ---
var _preRender = SendBrowse.prototype._renderFileContent;

SendBrowse.prototype._renderFileContent = function(container, bytes, fileName, type) {
    var effectiveType = type;
    if (effectiveType === null && _isLikelyText(bytes)) {
        effectiveType = 'text';
    }
    _preRender.call(this, container, bytes, fileName, effectiveType);
};
```

This must be placed **before** the existing:
```js
var _origRender = SendBrowse.prototype._renderFileContent;
```

After this insertion, `_origRender` will capture the pre-patched version, and the vault overlay will then add Edit/Save/Cancel buttons as usual — because `isEditable` checks `type === 'text' || type === 'code' || type === 'markdown'` and the upgraded `effectiveType` will be `'text'`.

### 4c. No changes needed to Edit/Save/Cancel logic

The existing `isEditable` guard in the overlay (line 58 of v0.2.3's `vault-browse-edit.js`) already handles `type === 'text'`:

```js
var isEditable = (type === 'text' || type === 'code' || type === 'markdown') && _ext0 !== 'html' && _ext0 !== 'htm';
```

Because the pre-patch upgrades `type` before the overlay sees it, this guard fires automatically for all text-sniffed files. Edit, Save, Cancel, Copy, and Refresh all work without further changes.

### 4d. Loading order check

The pre-patch IIFE runs at parse time. Confirm that in the page's `<script>` load order, `vault-browse-edit.js` is loaded after `send-browse--v0.3.2.js`. This is already the case in all v0.2.x vault pages (the overlay is always last in the send-browse stack).

## 5. Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Large binary decoded as text | Low — null-byte check catches most binaries early | 2 MB size guard; null-byte scan of first 4096 bytes |
| Valid UTF-8 binary (e.g. gzipped data that happens to be valid UTF-8) | Very low | Null-byte scan still catches most; user can always use "Save" to download |
| Performance: `TextDecoder` on 4096 bytes per file click | Negligible | Synchronous, < 1 ms for 4096 bytes |
| `.env` or `.gitignore` already working | Already handled — these extensions are in `_extMap` | No change needed, pre-patch is a no-op for known types |
| Breaking existing "View Source" button | No risk — "View Source" is only added when `!isEditable && type !== 'image' && type !== 'pdf'`; after upgrade type is `'text'`, which sets `isEditable = true`, so "View Source" is not shown (correct behaviour) |
| Re-render loop (Save calls `_renderFileContent` again) | No risk — `type` is passed through from save handler, not re-derived from filename |
