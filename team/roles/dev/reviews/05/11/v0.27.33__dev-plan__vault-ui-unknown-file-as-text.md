# Dev Plan: Vault UI — Show Unknown-Extension Files as Plain Text

**Version:** v0.27.33  
**Date:** 2026-05-11  
**Role:** Dev (Explorer)  
**Branch:** `claude/vault-ui-file-display-Df4fE`

## 1. Root Cause

The "No preview available" message is rendered in `SendBrowse.prototype._renderFileContent` at:

**File:** `sgraph_ai_app_send__ui__user/v0/v0.3/v0.3.0/_common/js/components/send-download/send-browse.js`  
**Lines 520–527** — the final `else` branch:

```js
} else {
    content.innerHTML = `
        <div style="padding: 2rem; text-align: center; color: var(--color-text-secondary);">
            <div style="font-size: 3rem; margin-bottom: 1rem;">📄</div>
            <p>No preview available for this file type.</p>
            <p style="font-size: 0.8rem;">${SendHelpers.escapeHtml(fileName)} · ${SendHelpers.formatBytes(bytes.byteLength)}</p>
        </div>`;
}
```

This branch is reached when `type` is `null`. The `type` comes from `FileTypeDetect.detect(entry.name, null)` called in `_openFileTab` (line 434).

**Why `.issues` files hit this path:**  
`FileTypeDetect.detect` (in `sgraph_ai_app_send__ui__vault/v0/v0.1/v0.1.4/_common/js/shared/file-type-detect.js`) looks up the extension from `_extMap`. The method `_getExtension` returns `null` when:
- the filename has no dot at all (no-extension files), or
- the dot is at the end of the name (trailing dot).

For `partner-feedback.issues`, `_getExtension` returns `.issues` — but `.issues` is not in `_extMap`. The content type hint is `null` (vault files have no HTTP content-type). Result: `detect()` returns `null`. The `else` branch fires.

The same applies to: `.config`, `.log` (when named without the known `log` basename), `.env` (without leading dot), no-extension files like `Makefile`, `Dockerfile`, `README`, `.gitignore` (dot-prefixed, so `_getExtension` returns the whole thing).

**Note on `.log`:** `.log` IS in `_extMap` (returns `'text'`) — but only if the file is named `foo.log`. A file named just `logs` (no extension) returns `null`.

---

## 2. Detection Strategy

**Two-step approach (extension first, content-sniff second):**

1. **Extension whitelist** — already handled by `FileTypeDetect.detect`. If it returns a known type, use it. No change needed here.
2. **Content sniff for `null` type** — when `detect()` returns `null`, attempt UTF-8 decode of the first 4 KB. If it succeeds without replacement characters AND contains no null bytes (U+0000), treat the file as `'text'`.

This is the industry-standard "not binary" heuristic. It catches:
- `.issues`, `.config`, `.secrets`, `.gitignore`, `Makefile`, `Dockerfile`, `README`
- Any no-extension text file
- Any unknown-extension text file

It rejects binary files correctly because: compiled binaries, images (without magic bytes), and encrypted blobs all contain null bytes or non-UTF-8 sequences.

**Size limit:** Only sniff files ≤ 1 MB. Files larger than 1 MB that lack a known text extension are treated as binary. This avoids blocking on large blobs.

## 3. IFD Approach

**Do NOT modify any base file.** Add the logic as an additional patch inside a new overlay:

**Target file:** A new file added to the v0.2.3 overlay directory:

```
sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3/_common/js/components/vault-browse-edit/
    vault-browse-edit--text-fallback.js
```

This file must be loaded **after** `vault-browse-edit.js` in the `index.html` (or via the same loader that loads `vault-browse-edit.js`).

The v0.2.3 `vault-browse-edit.js` already patches `SendBrowse.prototype._renderFileContent` once (saving the original). A second patch is safe — it wraps the already-patched prototype method. The call chain becomes:

```
new vault-browse-edit--text-fallback.js patch
    → calls vault-browse-edit.js patch
        → calls send-browse v0.3.2 _renderFileContent (original)
```

**Why a separate file rather than modifying vault-browse-edit.js:**  
- IFD rule: do not modify existing overlay files after they are released.
- Keeping the fallback isolated makes it easy to revert or tune independently.
- The `vault-browse-edit.js` in v0.2.3 is already a near-copy of v0.2.2 with one bug fix. Adding more logic bloats it.

## 4. Exact Code to Implement

### 4a. New file: `vault-browse-edit--text-fallback.js`

```js
/* =================================================================================
   SGraph Vault -- Text Fallback for Unknown File Types
   v0.2.3 overlay — loaded AFTER vault-browse-edit.js

   Patches _renderFileContent: when FileTypeDetect returns null (unknown extension),
   sniffs the first 4 KB for UTF-8 validity. If decodable and no null bytes found,
   treats the file as 'text' so it renders in <pre> and gets Edit/Save/Cancel buttons.
   ================================================================================= */

(function() {
    'use strict';

    if (typeof SendBrowse === 'undefined') return;

    // Maximum bytes to sniff. Beyond this we give up and show "No preview".
    var SNIFF_LIMIT = 1024 * 1024; // 1 MB

    /**
     * _isLikelyText(buffer) → boolean
     *
     * Returns true when an ArrayBuffer's contents are almost certainly UTF-8 text:
     *   1. buffer.byteLength <= SNIFF_LIMIT
     *   2. UTF-8 decode of first 4096 bytes succeeds (no replacement chars U+FFFD)
     *   3. No null bytes (U+0000) in the sampled region
     *
     * This is a fast, synchronous heuristic — no async needed because the buffer
     * is already fully loaded in memory by the time _renderFileContent is called.
     */
    function _isLikelyText(buffer) {
        if (!buffer || buffer.byteLength === 0) return true;  // empty file → treat as text
        if (buffer.byteLength > SNIFF_LIMIT) return false;

        var sample = buffer.byteLength > 4096
            ? buffer.slice(0, 4096)
            : buffer;

        // Check for null bytes first (fast path — rejects most binaries immediately)
        var bytes = new Uint8Array(sample);
        for (var i = 0; i < bytes.length; i++) {
            if (bytes[i] === 0) return false;
        }

        // Attempt strict UTF-8 decode — fatal:true throws on any invalid sequence
        try {
            var decoded = new TextDecoder('utf-8', { fatal: true }).decode(sample);
            // Paranoia: check for replacement char even with fatal:true (some engines differ)
            if (decoded.indexOf('�') !== -1) return false;
            return true;
        } catch (_) {
            return false;
        }
    }

    // Wrap the current (already-patched) _renderFileContent
    var _prevRender = SendBrowse.prototype._renderFileContent;

    SendBrowse.prototype._renderFileContent = function(container, bytes, fileName, type) {
        // Only intercept when type is null (unknown extension)
        if (type === null && _isLikelyText(bytes)) {
            type = 'text';  // promote to text — base renderer shows <pre>, overlay adds Edit
        }
        _prevRender.call(this, container, bytes, fileName, type);
    };

})();
```

### 4b. Load order in `en-gb/browse/index.html`

Add one line immediately after the existing `vault-browse-edit.js` script tag:

```html
<script src="../../_common/js/components/vault-browse-edit/vault-browse-edit.js"></script>
<script src="../../_common/js/components/vault-browse-edit/vault-browse-edit--text-fallback.js"></script>
```

The same addition is needed in any other `index.html` that loads `vault-browse-edit.js` within the v0.2.3 tree.

### 4c. How Edit/Save/Cancel flow activates automatically

In `vault-browse-edit.js` (both v0.2.2 and v0.2.3), the `isEditable` guard is:

```js
var isEditable = (type === 'text' || type === 'code' || type === 'markdown')
    && _ext0 !== 'html' && _ext0 !== 'htm';
```

Because our patch promotes `type` to `'text'` **before** calling `_prevRender` (which includes the vault-browse-edit patch), by the time the vault-browse-edit code evaluates `isEditable`, `type === 'text'` is already set. The Edit/Save/Cancel/Copy buttons appear automatically — no further changes needed in `vault-browse-edit.js`.

## 5. Risk Assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Large text file (>1 MB) shown as "No preview" | Low — 1 MB text files are rare in vaults | Acceptable; user can rename with a known extension to force preview |
| Binary file with no null bytes in first 4 KB decoded as text | Very low — binaries almost always have null bytes; PE/ELF headers do | If it happens, the garbled text in `<pre>` is harmless; user can dismiss |
| Performance: 4 KB decode on every file open | Negligible — synchronous decode of 4 KB is <1 ms on any device | None needed |
| Encrypted vault objects decoded as text | Not applicable — vault objects are decrypted before `_renderFileContent` is called | — |
| UTF-8 with BOM (U+FEFF at start) | BOM is valid UTF-8; decoded correctly; no null bytes | Works correctly |
| Files with Windows line endings (CRLF) | CRLF contains no null bytes; decodes cleanly | Works correctly |
| Re-entrant call (`_renderFileContent` calls itself after save) | Handled — `type` is passed as `'text'` on re-render, sniff is not re-run | No loop |
