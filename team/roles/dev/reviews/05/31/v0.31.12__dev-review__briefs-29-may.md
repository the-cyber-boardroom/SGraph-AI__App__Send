## Executive Summary

The 05/29 briefs specify two parallel implementation tracks: external data connectors and evidence-driven assessments. Both tracks are well-specified, build on existing infrastructure, and have clear implementation paths. The key insight across both: almost everything can be proved/built in the browser first (tools repo for connectors, Vault Chat + vault for assessments), with minimal new backend required.

**The data broker correction (doc 516) is the most important implementation note:** the no-origin OAuth approach from doc 513 will not work (Phase 3 null-origin applies to all app frames). The broker model adds a modest implementation cost but is the correct approach and fits the existing VIV architecture.

#### Phase 2: GitHub + OneDrive (P-272)

**Effort:** Medium each (after Drive proves the pattern, each subsequent connector is cheaper).

**GitHub specifics:** CORS any origin, standard OAuth, hierarchical. The custom viewer can render a repo tree and file contents. No broker quirks — GitHub allows CORS from any origin.

**OneDrive specifics:** Use `@microsoft.graph.downloadUrl` instead of `/content` redirect (the `/content` endpoint returns a 302 that CORS blocks). With this workaround, it fits the standard pattern.

## Risk Register

| Risk | Severity | Mitigation |
|------|----------|-----------|
| No-origin OAuth (connectors): the data broker pattern adds implementation complexity | Medium | The broker is a known pattern (VIV broker is the precedent); doc 516 is clear; validate in tools repo first |
| Vault Chat (P-263) dependency: connectors' most interesting uses and ALL assessments block on it | High | Treat Vault Chat Phase 0 as the highest-priority next session; it's simple (an HTML app calling sg.* bridge) |
| LLM closed-loop cost (assessments): per-round budget control is critical | High | Enforce budget at infrastructure level (not LLM self-discipline); per-round budget is a hard requirement |
| Graph-based standards accuracy (GDPR/ISO 27000): wrong standard → wrong assessment | High | Source carefully; leverage existing graph versions; confirm with legal/compliance expert; caveat clearly as assessment aid not advice |
| SG/Sentinel coordination for standards graph | Medium | Don't build twice; coordinate before writing GDPR/ISO 27000 graphs |
| Tools repo vs vault divergence (connectors) | Medium | Simulate vault null-origin conditions in the tool; validate the bring-back carefully |
| Visualisation cornerstone (P-275): if the games don't work, assessments won't work | High | Build Akinator/Whodunit first; iterate on prompts/workflows; don't rush to GDPR |

## Recommended Implementation Order

1. **Vault Chat Phase 0** (P-263) — an HTML app using sg.* bridge; no new bridge verbs; fastest to start; unlocks everything downstream
2. **VFS** (P-264) — client-side in-memory Map; define `.vfs/` convention
3. **Akinator/Whodunit proving ground** (P-275) — the visualisation cornerstone; prove prompts/workflows on low-stakes games
4. **Connector prototype in tools repo** (P-269, Phase 0) — parallel track; validate data broker pattern + null-origin OAuth relay
5. **Commit Queue** (P-265) — vault-shell batching; needed for practical Vault Chat use
6. **Google Drive Connector** (P-270) — first connector in vault; after tool prototype validates
7. **GDPR Assessment Vault** (P-274) — first real assessment; after Vault Chat and Akinator/Whodunit

**Explicitly defer until Vault Chat ships:** P-274 (GDPR), P-276 (CV), P-278 (Consulting), P-277 (App Store — needs working apps to distribute).
