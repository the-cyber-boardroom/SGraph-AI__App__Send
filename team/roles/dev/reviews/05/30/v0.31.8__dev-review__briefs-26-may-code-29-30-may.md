## 1. Code Shipped Before Last Librarian Session (Not Previously Documented)

These modules were committed before the 05/29 librarian session but were not covered in the previous master index.

### B4 — Mounts Debug Tab

**Module:** `viv-mounts-view.js` + `app-debug-mounts.js`
**Purpose:** Operator visibility into the per-kernel mount table + broker log from the /app debug pane.
**Status:** EXISTS, 33 unit assertions (viv_mounts_view), DOM-free view-model, wired into app-debug-pane.js as 🔗 Mounts tab.
**What it shows:** Live mount table (mountId, path, access) + broker log (newest-first, outcomeClass, credTag). Re-renders on `app-debug:bridge-call` events + manual refresh.

### B5/B6 — VivCredentialTiers

**Module:** `viv-credential-tiers.js`
**Purpose:** Three-tier credential gate — NONE (reads), STANDING (writes), PER_REQUEST_RW (destructive verbs). The gate runs in `kernel-parent.js`'s `relay()` BEFORE mediation — no broker entry is created for refused operations. Unknown verbs default to highest tier (fail-closed).
**Status:** EXISTS, 28 unit assertions.
**Integration:** The tiers module gates relayed operations. But the full feature (credential issuance UI, token format, revocation) is still PROPOSED (P-254). Currently, only the gate mechanism exists.

### B7 — VivMonitor

**Module:** `viv-monitor.js`
**Purpose:** CLOSED (default) / OPT_IN monitor modes. `registerOnChannel(channel)` wires the monitor to a SecureChannel. CLOSED kernels provide mount rows to an audit aggregator but no log entries.
**Status:** EXISTS, 20 unit assertions.
**Integration:** Wired into Phase 5.1 VivAuditView via `sourceRows()` — consent-gated.

### B10 — EUNSAFE_CUSTODY

**Module:** `viv-custody.js`
**Purpose:** Fail-closed custody checker. Unknown custodians are rejected with EUNSAFE_CUSTODY before any channel operation. Prevents "trusted by accident" scenarios.
**Status:** EXISTS, 33 unit assertions.
**Integration:** Wired into `kernel-parent.js` relay path.

### KernelParent

**Module:** `kernel-parent.js`
**Purpose:** Parent-side peer to `kernel-bootstrap.js`. Manages the parent's view of a child kernel: spawn a child srcdoc, handshake via K1, relay `sg.*` operations to child. M5 fix: reads endpoint from secrets payload (not hardcoded to `dev.send.sgraph.ai`).
**Status:** EXISTS, 44 unit assertions.
**Integration:** `app-shell.js` calls `_ensureKernelParent` to set up a KernelParent for the mounted child vault; B7 monitorChild method used by Phase 5.1 Audit tab.

### Phase 3: Null-Origin App Frames (Security Gate Closed)

**Commits:** `f534b27` + `1b5b6b1` + fixes
**Change:** All 4 `app-shell.js` iframe mount sites (`_mountApp`, `_mountVaultFile` HTML, `_mountPageLayout`, `_mountVaultFile` markdown) now drop `allow-same-origin`; content delivered via `srcdoc` (not `blob:` URL). The blob/createObjectURL/_objectUrls dance is removed for these sites.
**Status:** EXISTS, browser-verified via Phase 3 probe suite (30 Playwright assertions, 0 failed).
**What this means in practice:** An app iframe that calls `localStorage.getItem('vaultKey')` or tries `window.parent.document` now gets `null`/throws. All vault access must go through the `sg.*` bridge. SEC-VIV-001 is closed.

## 2. Code Shipped After Last Librarian Session

### Phase 4: AppFrameBootstrap

**Module:** `app-frame-bootstrap.js` (`globalThis.AppFrameBootstrap`)
**Change:** Extracted a pure, DOM-free, `this`-free `build({kind, …})` function that assembles the srcdoc HTML for all 4 iframe contexts (app/html/page-layout/markdown). Previously, each of the 4 mount methods had its own inline template — copy-paste with subtle differences. Now they all call `AppFrameBootstrap.build()` and pass in deps/bytes.
**Status:** EXISTS, 32 unit assertions (Node-runnable).
**What changes for Vault Chat:** Building the Vault Chat srcdoc is `AppFrameBootstrap.build({kind: 'app', …})` — no special casing needed.

### Phase 4: App-Error Surfacing Re-Spec

**Change:** Under null-origin frames, `contentWindow.onerror` injection is impossible. The injected bridge (delivered via srcdoc) now self-reports: `window.onerror`, `unhandledrejection`, post-DOMContentLoaded body-hidden check → `postMessage({type:"sg-app-error"}, "*")`. The parent handles this and shows a persistent toast via `<app-hud>.showMessage()`.
**Status:** EXISTS. Browser-verified via probe P5 (Playwright).
**Dev note:** This is the correct pattern for any null-origin iframe that needs to communicate errors to its parent. Vault Chat iframes should use the same self-reporting mechanism.

### Phase 5.1: VivAuditView

**Module:** `viv-audit-view.js` + `app-debug-audit.js`
**Purpose:** Cross-kernel audit aggregation. `VivAuditView.aggregate(sources)` merges mount tables and broker logs from multiple kernels. `<app-debug-audit>` component wires this to the /app debug pane as an "Audit" tab.
**Status:** EXISTS, 37 unit assertions. Wired in `/app` debug pane.
**Important limitation:** Broker logs are in-memory per-document. A standalone cross-document page cannot read them. The Audit tab works because app-shell has a live KernelParent reference.

### Vault Debug Pane + Sub-vaults Pane

**Change:** /vault debug pane moved from bottom panel to right-side resizable sidebar (mirrors /app). Added `<vault-subvaults-panel>` showing CompositeDataSource `*.link.json` sub-vaults (name/path/access/status/file-count).
**Status:** EXISTS. Note: this shows CompositeDataSource mounts (sub-vaults), NOT ViV kernel broker log. P-253 (ViV broker log on /vault) is still PROPOSED.

## 3. New Work from 05/26 Briefs — Implementation Path

### Vault Chat (P-263)

**What needs building:**
1. A self-contained HTML chat app with `window.sg` bridge access (Vault Chat iframe)
2. The VFS layer (client-side in-memory FS within the chat iframe)
3. VFS-vault sync (write VFS files to vault at appropriate intervals)
4. Context layers inspector (visible prompt breakdown)

**Implementation path:**
1. Start with Phase 0: standalone shell — a pure HTML file that connects to vault via `sg.*`, reads a file, shows it. No LLM. Independently testable.
2. Add LLM call (direct OpenRouter API call from inside the iframe). Stream response.
3. Add VFS (in-memory Map keyed by path). Write each response to VFS.
4. Add VFS-vault sync (sg.vfs.write() for each VFS entry; commit queue handles batching).
5. Add context layers inspector.

**Effort estimate:** Phase 0+1 (working chat with basic vault read/write): 1-2 sessions. Full architecture (VFS, sidecar LLMs, context inspector, self-pruning): 3-4 sessions.

### VFS (P-264)

**Implementation:** Client-side in-memory `Map<path, bytes>`. NOT a new backend construct. The chat iframe manages its own VFS. Sync to vault via `sg.vfs.write(vfsPath, bytes)` calls. Path convention: `.vfs/<session-id>/<timestamp>-<type>.json`.

**Effort:** Low — it's a Map with serialisation. The interesting part is the VFS path conventions and the sync trigger logic.

### Commit Queue (P-265)

**Implementation:** In `vault-shell.js`. A `commitQueue` class with:
- `queue(path, bytes)` — adds to pending map, starts/resets timer
- `_drain()` — called at timer expiry; for each pending entry, calls `vault.write(path, bytes)` then `vault.commit()`; single batch commit
- `window` property (seconds, 0 = off)
- `pendingCount` getter for status panel

**Integration point:** `vault-shell._onVfsWrite` currently calls `vault.write()` then schedules a commit. Replace with `commitQueue.queue(path, bytes)`.

**Effort:** ~80-100 lines. 1 session.
