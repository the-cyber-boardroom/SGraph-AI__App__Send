## Implementation Streams by Priority

### Stream 1: Vault & UI (Buildable Now, High Value)

**Estimated effort: 3–5 days each**

#### 1A. Credential Manager Vault
**Brief:** 387 | **PROPOSED items:** P-062 through P-066

The credential manager vault is a standard vault with a defined directory structure (`keys/`, `tokens/`, `recipients/`, `usage/`, `policies/`). The vault layer already exists. What's new is:
- Simple Token issuance logic (`tok_<random>` format, quota enforcement, expiry)
- Resolution service (proxy mode: API call routed through manager; direct mode: token → actual key returned)
- Manager UI (key inventory, token issuer, usage charts, audit log)

**Dev notes:**
- Token format (`tok_<random>`) must be distinguished from existing vault word-word-NNNN tokens. Use a different namespace in all storage and lookup paths.
- Proxy mode requires an HTTP relay — the credential manager vault needs to be a running service (not just a static vault), or proxy is deferred to Phase 2.
- Start with direct mode (simpler) + vault audit trail. Proxy mode is a separate implementation.
- Follow `Type_Safe` for all schemas. No Pydantic.

#### 1B. Dynamic Social Previews for Public Vaults
**Brief:** 388 | **PROPOSED items:** P-068 through P-070

Crawler detection (user-agent matching for WhatsApp/Facebook/Twitter/LinkedIn/Slack) + OG meta tag injection + dynamic preview image generation.

**Dev notes:**
- The preview sidecar service can start as a Lambda function sitting in front of vault URLs.
- OG image generation: the infographic tool's SVG → PNG pipeline already exists (via `sg-llm-infographic.js`). Reuse it server-side with a headless Playwright render step.
- `og-config.json` in vault root → read at sidecar request time → override defaults.
- Cache invalidation: add vault version hash to preview image URL; browsers and CDN handle cache busting automatically.

#### 1C. Vault Rendering Without Iframe (Bare-Metal Mode)
**Brief:** 391 | **PROPOSED items:** P-072, P-073

Published vaults bypass the iframe wrapper. A bootstrap script (< 1KB) injects `window.SG.vault` API surface (get, put, list, commit, subscribe) as a same-origin shim.

**Dev notes:**
- The `window.SG.vault` API maps directly to existing User Lambda endpoints — no new backend work.
- The bootstrap script is the only new asset. It should be versioned and served from a stable URL.
- Backward compatibility: existing iframe-based vaults continue working (hosted mode remains available).
- CSP enforcement: bare-metal mode requires explicit CSP headers on vault responses. Needs a test.

#### 1D. Pre-Authorisation + Micropayments Model
**Brief:** 396 | **PROPOSED items:** P-074 through P-077

Stripe pre-auth hold (£5 default) + internal micropayment ledger + batched weekly settlement.

**Dev notes:**
- Requires Stripe API access (OQ-mono-1 — confirm this is available before starting).
- The internal ledger is a new data store. Recommend a vault-backed ledger (consistent with vault-first strategy) rather than a new database.
- Settlement scheduler: a Lambda function on a CloudWatch Events trigger (weekly or threshold).
- Phase 1 scope: hold placement + ledger write + cost visibility in UI. Settlement logic is Phase 2.
- Do NOT implement idle-handling or multi-feature unified ledger in Phase 1.

### Stream 2: Infrastructure Experiments (Requires AWS Provisioning)

**Estimated effort: 2–4 days per experiment (plus AWS setup time)**

#### 2A. EC2 Warm Pools for Boot Optimisation
**Brief:** 389 | **PROPOSED items:** P-057 through P-060

Measurement-driven: the goal is to reach 10-20s boot from current 2-4 minutes.

**Dev phases:**
1. Instrument current cold boot (phase-by-phase timing: API call → running → SSH → vault app ready)
2. Bake AMI with vault app preinstalled
3. Measure AMI boot time
4. Implement warm pool (3-5 t3.small pre-provisioned instances, rotate on assignment)
5. Measure warm pool boot time
6. Implement DNS TTL tuning
7. Record final numbers per phase

**Dev notes:**
- The warm pool introduces always-on cost (£1-3/day). Add a pool drain command from day one.
- Decryption key separation constraint must be maintained: instance boots without customer vault data; data arrives with the first user request.
- t4g.nano/micro (Graviton ARM) may be sufficient for the vault app — test both architectures.

#### 2B. Fargate Vault Hosting Experiment
**Brief:** 399 | **PROPOSED items:** P-083, P-084

Performance comparison: Fargate vs Lambda for vault workloads over multi-operation sessions.

**Dev phases (following brief's 3-phase structure):**
1. Add Fargate CLI commands (create-cluster, run-task, list-tasks, stop-task, logs)
2. Containerise vault app (already has Dockerfile — adapt for Fargate networking)
3. Run 7-metric benchmark (cold start, clone times, vault op sequences, cost/operation, cost/session, concurrency)

**Dev notes:**
- Confirm Fargate is provisioned in the project AWS account (OQ-fargate-1) before starting.
- Use `osbot-aws` for all ECS/Fargate API calls — never boto3 direct.
- TLS/DNS plumbing for Fargate is different from EC2 — ALB/NLB rather than direct TLS. Plan this before containerising.
- Output must be a decision table (Fargate wins/loses by workload duration). If the data is ambiguous, say so explicitly.

#### 2C. Instance Sizing Experiments
**Brief:** 401 | **PROPOSED items:** P-087

Measurement programme: which EC2 instance types optimise ephemeral vault workloads?

**Dev phases:**
1. Build startup measurement harness (API-to-running, running-to-SSH, SSH-to-container-ready)
2. Run matrix across t3/t4g, m7i/m8g, c7i/c8g
3. Run workload benchmarks (Playwright 30s, 5x parallel, cold/warm ECR pull, 5-min CPU)
4. Model break-even points by workload duration
5. Test burstable credit dynamics (sustain time, unlimited mode cost, replenishment)

**Dev notes:**
- This is pure measurement work. Write results to a vault for persistent reference.
- The decision table output feeds the container hosts primitive and warm pool configuration.
- Run Graviton (ARM) vs x86 comparison — Graviton is 20-40% cheaper per compute unit.

### Stream 3: CLI Surface Expansion (Large, Sequential)

**Estimated effort: 5–10 days per CLI module**

#### 3A. S3 Native CLI Support
**Brief:** 402 | **PROPOSED items:** P-088, P-089

S3 CLI primitives + vault-aware wrappers + vim edit with ETag conflict detection.

**Dev notes:**
- ALL S3 operations must go through `osbot-aws`. Confirm this constraint before starting (OQ-s3cli-1).
- Vim integration: `s3 edit <path>` → download to tmpdir → open `$EDITOR` → re-upload with ETag check → warn on conflict. Standard pattern.
- Format-aware rendering: detect Content-Type from S3 object metadata, not filename extension.
- Vault wrappers (`vault-open`, `vault-sync`, `vault-diff`, `vault-ls`) should be thin wrappers over existing sgit + s3 commands, not a new implementation.
- Start with core commands (ls, view, cat, cp, mv, rm) before adding sync and vim edit.

#### 3B. SG/Compute Container Hosts Primitive
**Brief:** 403 | **PROPOSED items:** P-090

EC2+Docker node-pool behaviour: container task submission → placement → idle teardown.

**Dev notes:**
- **Repo question (OQ-container-1):** Confirm this lives in SG/Compute, not this repo, before starting any implementation here.
- The per-host REST API (capacity, run, list, status, logs, delete) is straightforward to implement as a lightweight FastAPI app on each host.
- Placement logic (first host with capacity, or spin new) can live in a Lambda function — consistent with existing Lambda spinup pattern.
- Multi-region parallel execution (`--regions` + `--count-per-region`) adds significant orchestration complexity. Defer to Phase 2 unless the use case demands it.
- Mutual TLS (CLI cert from internal CA) needs a cert issuance workflow. Plan this before host bring-up.

#### 3C. Dynamic Credential Delivery Service
**Brief:** 397 | **PROPOSED items:** P-078 through P-080

STS AssumeRole pattern, just-in-time AWS credentials per operation.

**Dev notes:**
- Start with the local service (master credentials held locally, scope resolved locally) before adding the deployed version.
- Scope catalogue as a vault (versioned, auditable) is the right storage choice.
- The (caller, scope) credential cache needs a TTL slightly shorter than the STS credential lifetime (15 min − 2 min buffer = 13 min cache).
- Integration with IAM graph (brief 400) is the Phase 6 target — don't couple these implementations in Phase 1.

#### 3D. IAM Graph Visualisation and Lockdown
**Brief:** 400 | **PROPOSED items:** P-085, P-086

IAM discovery → graph → cleanup → CloudTrail evidence → permission tightening.

**Dev notes:**
- This is a 6-phase brief. Start with Phase 1 (discovery pass, write to vault as graph data) only.
- Graph data structure: adjacency list of (role, policy, resource, action) tuples. JSON in vault.
- CloudTrail evidence layer (Phase 4) is the most valuable part — it turns the graph from a static map into an evidence-based permission audit. But it also has the most AWS complexity (CloudTrail query latency, data transfer costs).
- Never delete roles in `--dry-run=false` without an explicit `--confirm` flag. Two-phase deletion is required.

#### 3E. Bedrock CLI Native Support
**Brief:** 404 | **PROPOSED items:** P-091, P-092

Command tree: chat, agent, tool, kb, guardrail, eval, observe, meta.

**Dev notes:**
- Confirm Bedrock is enabled in the project AWS account (OQ-bedrock-1) before starting.
- The command tree is large. Implement `chat` sub-commands first (claude, nova, llama) — this validates the vault-grounded session pattern before tackling agent/tool complexity.
- Model ID complexity (region, inference profile, account path): abstract behind a model alias registry. The alias registry should live in a vault.
- MCP interop constraint: ensure CLI tools are exposed via the existing MCP server endpoints, not a new transport.

#### 3F. Unified Observability Session
**Brief:** 398 | **PROPOSED items:** P-081, P-082

Interactive REPL across S3/CloudWatch/CloudTrail/billing/vault sources.

**Dev notes:**
- No consolidated backend in v1 — reads from sources directly. This is the right scoping decision.
- The source abstraction contract (connect, list, tail, query, stats, schema) is the key interface. Implement one source adapter (S3 log files) first to validate the contract, then add others.
- `agent-trace <agent> --session <id>` is the highest-value feature — it pulls Bedrock + S3 + vault commits + costs. Implement this before general-purpose query routing.
