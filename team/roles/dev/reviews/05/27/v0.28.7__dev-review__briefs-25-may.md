### Phase 5 Decision Pending

`vault.delete` is deferred (correctly) because authorising it requires the child's write key, and storing that in `ro-links.json` (read-key tier) would be a vulnerability. Phase 5 requires:
1. Design and implement the **owner-secret-tier** credential store (double-encrypted via `vault-hkdf` owner key, `write_key` tier).
2. AppSec sign-off on the destructive endpoint (existence-oracle / write-key findings noted in appsec v0.22.6).

This is not urgent (no current use case requires server-side vault destruction via the iframe bridge) but should be scheduled when the need arises.

### Verification Gap

The permission model needs browser verification:
- `vfs.read('.vault/app.json')` → `EPROTECTED`.
- `vfs.list('/')` omits `.vault`.
- A normal app with a `permissions` block: writes/deletes granted scope work; denied scope returns `EPERM`.
- HUD privileges chip shows correct verbs; consent bar appears and caches correctly.

## 5. Talk to the Vault (P-248): Implementation Estimate

### Architecture (Dev Pack v0.27.80)

The dev pack has done the hard work: it re-grounds the architecture against real `__Send` code and produces a build-ready specification. The 12 documents cover:

| Track | What | Complexity |
|-------|------|-----------|
| **Track A** (substrate) | VFS bridge extensions (batch-commit method); VaultFlushController (coalesces memory→vault writes); vault-chat app shell (new Vault App at `en-gb/vault/chat/`); tool policy layer (wrapper on sg-agentic-loop); vault-generate LLM bus integration | **Medium** — most components are REUSE/EXTEND |
| **Track B** (cognition) | Sidecars; multi-LLM consensus; semantic knowledge graph; facts/hypotheses/evidence | **High** — built after Track A; novel capability |

### REUSE vs BUILD-NEW

| Component | Source | Effort |
|-----------|--------|--------|
| `sg-agentic-loop` | REUSE — already in `__Tools` JS | 0 |
| `sg-tool-runner` + `sg-tool-definition` | REUSE | 0 |
| `sg-llm-request`, `sg-llm-events`, `sg-llm-infographic` | REUSE (pin to actual versions) | minimal |
| VFS bridge batch-commit method | EXTEND `app-shell.js` | Small |
| VaultFlushController | BUILD-NEW (thin coalescing layer) | Small–Medium |
| Vault chat app (`en-gb/vault/chat/` + `vault-chat/` components) | BUILD-NEW (new Vault App) | Medium |
| Tool policy / budget governor | BUILD-NEW (wrapper on sg-agentic-loop) | Medium |
| Track B cognition module | BUILD-NEW | High (post-Track-A) |

### Estimated Effort (Track A only)

Track A is principally a composition task. The dev pack estimates it as a single focused session (1–2 days) for the substrate + policy layer + basic chat UI. Track B is a separate session after Track A is working.

### Key Risk

The OpenRouter key injection at iframe-boot (D4: key at `.vault/secrets/openrouter.key`, parent reads + injects via one-time handshake, `/.vault/**` excluded from iframe VFS) is the novel security-sensitive piece. It must be implemented with the same security rigour as the app-iframe floor (Phase 1). The dev pack (doc 09) documents the threat model.
