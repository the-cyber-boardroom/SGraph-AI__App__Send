## A. Issues spotted (read this first)

Found while grounding the plan in the actual bridge code. Severity is for *the design as written*; each has a resolution folded into the plan.

| # | Issue | Severity | Resolution |
|---|---|---|---|
| **A1** | **Floor bypass via un-normalised absolute paths.** The bridge resolves writes/reads as `wPath.startsWith('/') ? wPath.slice(1) : _resolvePath(...)` (`app-shell.js:1322,1374`). The **absolute branch skips `_resolvePath`**, so `..` is *not* collapsed — `/x/../.vault/app.json` reaches the handler verbatim. `_resolvePath` also pushes empty segments (`:1522`), so `//` survives. | **Critical** | The floor must **normalise the path itself** (collapse `.`/`..`, strip leading `/`, drop empty segments) *before* matching — never trust the bridge's pre-resolution. One shared `normalizePath()` used by `_isFloor` **and** `_can`. |
| **A2** | **`.vault` only as a prefix misses nested vaults.** Sub-vaults mounted by `CompositeDataSource` have their *own* `.vault/` under a mount prefix (e.g. `customers/acme/.vault/app.json`). A prefix-only rule (`startsWith('.vault/')`) wouldn't protect those. | High | Floor matches if **any path segment === `.vault`** (case-insensitive), not just the root prefix. Plus the legacy root file `app.json` (exact) for the write floor. |
| **A3** | **`vfs.list` leaks `.vault/**`.** `__sgVfsListReq` returns `dataSource.getFileList()` unfiltered (`app-shell.js:1345-1361`); the composite merges mounts (`composite-data-source.js:148`). So the app can enumerate `.vault/owner/...` and learn structure even with the *read* floor on `vfs.read`. The injected page-layout `fileList` (`app-shell.js:882`) has the same exposure (metadata only, not bytes — but still leaks the tree). | High | Filter **every** `.vault`-segment entry out of: (a) `vfs.list` results, (b) the injected `fileList`. A direct `list('.vault')` / `list('.vault/owner')` returns `ENOENT` (no existence oracle). |
| **A4** | **Consent cache keyed only by vault → cross-app leakage.** `sg-app-grant:<vaultId>:<verb>` (spec §3.5) lets a *different* app later opened in the same vault inherit a prior app's consent. There is no stable app identity today. | High | Add an **app identity** to the key: `sg-app-grant:<vaultId>:<appId>:<verb>`, where `appId = SHA-256(canonical .vault/app.json bytes)` (or an explicit `app.id` field if we add one). Editing the manifest ⇒ new `appId` ⇒ consent re-asked. Decide in §F-Q1. |
| **A5** | **App can't read its own config under the read floor.** If any app fetches `.vault/app.json` at runtime, the floor breaks it. | Medium | Don't let the app read the raw file. Expose a **sanitised** `sg.app.config` host verb returning `app.json` **minus `accessToken`/secrets**. (Bonus: closes the embedded-token read vector regardless of floor.) |
| **A6** | **Floor must not block the host's own internal writes.** Servicing `vault.create` writes the owner record into `.vault/owner/ro-links.json` — which is *in the write floor*. | Medium | The floor gates **bridge verbs only** (`vfs.write`, `fs.*`). The host's internal writes while servicing `vault.create`/`delete` are not bridge verbs and bypass the floor by construction. Make this explicit; never route host-internal writes through the gated path. |
| **A7** | **New mutations need the token gate too.** Only `vfs.write` checks `dataSource.writable` today (`:1314`). `fs.move/delete/mkdir` and `vault.*` also mutate/publish. | Medium | Every mutating verb checks **`writable` (token) AND `_can` AND `!_isFloor`** — three gates (spec §3.6). Reads check floor + `_can('fs.read')` only. |
| **A8** | **`vault.delete` needs the child's write key.** The server delete endpoint is gated by `write_key_hash` (appsec v0.22.6); the read-only owner record stores only `read_key`. | Medium | `vault.create` must additionally stash the child **write credential** in an owner-tier (double-encrypted) record at creation time, else delete can `unlink` but never server-destroy. (Already flagged in spec §4.2; this plan implements the storage.) |
| **A9** | **Error-code reconciliation.** Existing replies use human strings (`'Read-only vault'`, `'ENOENT'`, `'Bad encoding'`, `app-shell.js:1314,1320,1352`). The spec introduces `EPERM/EPROTECTED/ECONSENT/EREADONLY`. | Low | New verbs use the coded errors. Keep the existing `vfs.*` human strings *and add* a `code` field (additive) so current apps that match on the string don't break. |
| **A10** | **Consent concurrency.** The HUD has one centre slot (`app-hud.js:33`). Two consent-gated calls in flight would collide. | Low | `_consent` serialises via a host-side promise queue; second request waits or returns `EBUSY`. |
| **A11** | **Malformed `permissions` block.** A bad block shouldn't crash `_initWithKey`. | Low | Parse defensively: on parse error, **deny all mutations**, keep reads (within floor), emit a bridge-debug warning. |

None of these are blockers — A1/A2/A3 are the must-get-right ones and all land in **Phase 1**.

## B. Shared infrastructure (build once, before Phase 1)

**New pure module** `_common/js/components/app-shell/app-permissions.js` — **no DOM, no bridge, no `this`** so it runs in the existing jsdom-free Node test harness (the loader tests pattern). Exposes:

```js
globalThis.AppPermissions = {
  normalizePath(raw),                 // A1: strip leading '/', split '/', drop '' and '.', apply '..', re-join
  hasVaultSegment(path),              // A2: normalize → any segment.toLowerCase() === '.vault'
  isFloor(verb, path),                // read/write/move/delete/mkdir vs the floor (A2 + legacy 'app.json' write)
  parsePermissions(appJson),          // A11: → { fs:{read,write,move,delete,mkdir}, vault:{create,unlink,delete} } normalized to true|false|string[]
  can(perm, verb, path),              // §3.2/3.3: read default-allow; mutate default-deny; array = prefix('/'-suffix) or exact
  appId(appJsonBytes),                // A4: SHA-256 hex of canonical bytes (async; crypto.subtle)
};
```

`app-shell` keeps the **stateful** glue (`this._perm` = parsed grants, `this._consent(verb,path)`, the HUD calls, the cache) and *delegates the logic* to `AppPermissions`. This is what makes the model unit-testable without a browser — the gap I've been flagging on every prior change.

**Error codes** (single source): `EPERM` (no grant), `EPROTECTED` (floor), `ECONSENT` (declined/needed), `EREADONLY` (no token), `ENOENT`/`EEXIST`, `EBUSY`. New verbs reply `{ ok:false, err:<msg>, code:<CODE> }`.

**Load order:** add `<script src=".../app-permissions.js">` to `en-gb/app/index.html` **before** `app-shell.js`.

## C. Phase 1 — Security floor (no new app API)

**Goal:** the iframe cannot read `.vault/**`, cannot write `.vault/**` or `app.json`, and cannot enumerate `.vault/**`. Pure hardening; ships alone.

**Files & edits (all in `app-shell.js`, the host `message` handler ~1280-1480):**

1. **`vfs.write`** (`:1308`): before `saveFile`, compute `wResolved` (already done), then `if (AppPermissions.isFloor('write', wResolved)) return wReply(false,{err:'Protected path',code:'EPROTECTED'})`. (Keeps the existing `writable` check.)
2. **`vfs.read`** (`:1367`): after `rResolved`, `if (AppPermissions.isFloor('read', rResolved)) return rReply(false,{err:'Protected path',code:'EPROTECTED'})`.
3. **`vfs.list`** (`:1341`): after building `listed`, drop entries where `AppPermissions.hasVaultSegment(f.path)`; if the requested `prefix` itself is a `.vault` segment → reply `ENOENT` (A3). 
4. **`vfs.nav`** (`:1285`): nav fetches HTML via `getFileBytes`; apply the read floor on `navResolved`.
5. **Injected `fileList`** (`_mountPageLayout`/`_mountVaultFile`, `:882`): filter `.vault`-segment paths out of the array before `JSON.stringify` (A3).

**No `permissions` parsing yet** — the floor is unconditional.

**Tests** (`tests/unit/vault_ui/loader/test__app_permissions_floor.js`, jsdom-free):
- `normalizePath`: `/x/../.vault/app.json` → `.vault/app.json`; `a//b` → `a/b`; `./a` → `a`.
- `isFloor('write','.vault/app.json')` / `('write','app.json')` / `('read','customers/acme/.vault/owner/ro-links.json')` → true (A2).
- `isFloor('write','data/app.json')` → false (only root `app.json`).
- `hasVaultSegment` true for nested, false for `vault-notes/x`.

## D. Phase 2 — `permissions` parsing + `_can` + FS verbs

**Goal:** answer "can the iframe move files?" → **yes, when granted.**

**Parse at open:** in `_initWithKey` right after `_readAppJson` (`app-shell.js:245`): `this._perm = AppPermissions.parsePermissions(appJson)`; `this._appId = await AppPermissions.appId(appJsonBytes)`.

**Gate helper:** `this._can(verb, path)` = `!AppPermissions.isFloor(verb,path) && AppPermissions.can(this._perm, verb, path)`.

**Retro-fit existing read/write verbs** with `_can` (Phase 1 added only the floor): `vfs.read`/`list` → `_can('fs.read', …)`; `vfs.write` → `_can('fs.write', …)` (plus existing `writable`).

**New data-source wrapper** (`adapters/vault-data-source.js`): add `async moveFile(fromDir, name, toDir)` → `this._vault.moveFile(...)` (lib method exists, `sg-vault--file-ops.js:129`); gate on `this.writable`. (Composite already delegates writes to root.)

**New bridge type `__sgCmdType:'fs'`** in the `__sgCmd` switch (alongside `history`/`git`/`auth`, `:1402+`):

| action | fields | gates | host call |
|---|---|---|---|
| `move` | `{from,to}` | `writable` + `_can('fs.move',from)` + `_can('fs.move',to)` | same dir → `renameFile`; else → `moveFile` |
| `delete` | `{path}` | `writable` + `_can('fs.delete',path)` | `deleteFile` |
| `mkdir` | `{path}` | `writable` + `_can('fs.mkdir',path)` | `createFolder` |

**In-iframe client** (`_buildVfsBridgeScript` + the page-layout bridge, `:846/1112`): add `sg.fs.move/delete/mkdir` returning promises over `__sgCmd`.

**Tests:** `can()` matrix — `write:true` allows any non-floor path; `write:["data/"]` allows `data/x` not `out/x`; `move` needs both ends; read default-allow when unset; mutate default-deny when unset.

**Tests:** none jsdom-free (pure DOM). Manual: open apps with various blocks, confirm chip text.

## F. Phase 4 — `vault.create` + `vault.unlink` + consent (HUD) + `requestPermission`

**Consent plumbing (`app-shell` ↔ `app-hud`):**
- `app-shell._consent(verb, path)` → returns a Promise. Checks cache `sg-app-grant:<vaultId>:<appId>:<verb>` (A4); if present (and verb not always-confirm) → resolve true. Else dispatch `app-hud:consent-request` (verb,path); the HUD renders the **consent bar** (Allow/Deny) and dispatches `app-hud:consent-response`; `_consent` resolves on it, caching on Allow. Serialised queue (A10).
- **`app-hud.js`:** consent bar UI in the centre slot; permissions panel (opened from the chip) listing grants with **revoke** (clears the cache key → `app-shell` re-reads live, A-§3.5 invariant).

**`__sgCmdType:'ui'` → `requestPermission`** `{verb,path?}`: if verb undeclared in `this._perm` or in floor → `EPERM`; if declared & non-consent → `{granted:true}` immediately; if consent-gated → `await this._consent(verb,path)`.

**`__sgCmdType:'vault'` → `create`** `{path,label,options?}`:
1. Gate: `_can('vault.create', path)` + `await _consent('vault.create', path)` + `writable`.
2. **Generate a proper vault key** (spec §4.2): random high-entropy passphrase **not** matching `^[a-z]+-[a-z]+-\d{4}$` (new `AppPermissions`/util `generateVaultPassphrase()`); `const child = await SGVault.create(sgSend, passphrase, options)`; `const childKey = child.getVaultKey()`.
3. Host-internal writes (bypass floor, A6): write `<label>.link.json` (keyless `{vault_id, ref_id}`) into `path`; write owner record into `.vault/owner/ro-links.json` (read_key **and** write credential, A8, double-encrypted); `await rootVault.push()` (auto-publishes — see the merge-publish fix already in `sg-vault--sync.js`).
4. Reply `{vault_id, ref_id, ref_file_id}` — **never** the keys (secrets stay host-side).
- Reuse the existing host link-creation logic (`vault-browse-edit.js _showAddLink`, ~887-1010) — factor its core into a shared helper so both the host UI and the bridge call it.

**`vault.unlink`** `{path}`: gate `_can('vault.unlink',path)` + `writable`; delete the `.link.json` (+ owner record); push. Vault stays on server.

**Tests:** `_consent` cache key includes `appId`; revoke clears it; `requestPermission` EPERM for undeclared. Create/unlink need browser/integration (full vault stack) — document the gap; cover the *gate decisions* with `AppPermissions` unit tests.

## G. Phase 5 — `vault.delete` (server destroy)

**`vault.delete`** `{path}`: gate `_can('vault.delete')` + `await _consent` (**always-confirm**, no cache short-circuit) + `writable`. Resolve the child **write credential** from the owner-tier record (A8) → call the server vault-delete endpoint via `SGSend` (osbot path; **never boto3**) → on success `unlink` → push. Reply `{deleted:true, files_deleted}`.

**Dependencies:** AppSec sign-off on the endpoint usage (existing findings in appsec v0.22.6 — existence oracle, write-key handling). Confirm the client endpoint wrapper exists in `sg-send.js`; if not, add it.

## I. Test strategy (and the honest gap)

- **Unit-testable now (no browser):** *everything in `app-permissions.js`* — `normalizePath`, `isFloor`, `hasVaultSegment`, `parsePermissions`, `can`, `appId`. This is the bulk of the security logic and the highest-risk surface (A1–A4). Put it under `tests/unit/vault_ui/loader/` like the existing jsdom-free suites.
- **Not unit-testable without a harness:** the bridge wiring, `SGVault.create`, push, consent UI — they need the full vault stack + DOM. These get **manual/Playwright** verification; each phase's changelog lists the exact checks (e.g. "app with `write:['data/']` can save `data/x` but gets `EPERM` on `out/x`"; "`vfs.read('.vault/app.json')` → `EPROTECTED`"; "`vault.create` shows the HUD consent bar and a denied click returns `ECONSENT`").
- **Regression guard:** confirm an app with **no** `permissions` block still reads/renders (read default-allow) and that the floor doesn't break legitimate reads/writes outside `.vault/`.

## J. Recommended order & smallest safe slice

`B → C` first (shared module + floor) is the highest-value, lowest-risk landing: it closes A1–A3 and the embedded-token read vector with **no app-facing API change**. Everything after is additive and gated. Suggest shipping **B+C as one PR**, then one PR per phase.

---

## K. Open decisions (need a steer)

1. **A4 app identity:** `appId = SHA-256(app.json bytes)` (re-asks consent on any manifest edit — safest) vs an explicit stable `app.id` field (survives edits — friendlier). Recommend the hash for v1.
2. **A9 error strings:** keep legacy `vfs.*` human strings + add `code` (additive, recommended) vs migrate fully to codes (cleaner, may break apps matching strings).
3. **A5 `sg.app.config`:** confirm apps need runtime config access at all — if none do, we can skip the accessor and rely purely on the floor.
4. Spec §10 items still open (consent friction, delete⇒unlink, write-into-child, app.json-as-ceiling).
