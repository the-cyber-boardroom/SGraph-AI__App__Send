# Code review, second pass — the append-lane changes of 6–7 Sep, reviewed adversarially

**date** 7 September 2026
**role** Dev (with an AppSec lens — the brief asked for security issues explicitly)
**scope** Everything this branch changed: `sg-append.js`, `app-shell.js`, the two test files, `AUTHORING.md`, the skill, the changelog, the response doc, the reality doc. Plus the two debriefs from the games-vault agent that drove them.
**method** Every finding below was confirmed by executing it — a probe, a built bridge, a test — not by reading. Where I could not execute, I say so.

**Bottom line.** The first pass shipped one genuine new defect, three overclaims in documentation, and one dead code path that its own test disguised. It also sat next to — and in one case copied — a pre-existing bug that kills every app in a vault with a quote in its name. All of that is fixed on this branch with tests that drive the real code paths. Nothing here changes server behaviour, a permission boundary, or the CSP default. Two design items remain deliberately unshipped.

---

## A. Defects introduced by the first pass — mine to own

### A1. `release.label` could close the bridge `<script>` — **fixed**

`sg.app.release` is built with `JSON.stringify(releaseInfo.release)` and spliced into the bridge script, which is injected into a **srcdoc document** inside `<script>…</script>`. `JSON.stringify` yields a valid JS literal but is not HTML-safe. Measured: a label of `</script><script>…</script>` produced **three** raw closers in the built bridge instead of one. The srcdoc parser closes the bridge early; `window.sg` never installs; every `sg.*` call in the app fails.

- **Trust boundary:** `.vault/releases.json` needs the write key — the same tier that authors the app HTML the frame already runs. So this is **robustness and defence-in-depth, not a privilege escalation.** I am recording it as a defect anyway, because I added a second owner-authored free-text input to a hole that already existed (A6/B1), and "the owner can already break their own app" is not a reason to add ways to do it.
- **Fix:** `_jsLit()` — `JSON.stringify` plus `</` → `<\/` (and U+2028/U+2029, which JSON leaves raw and older engines treat as line terminators). Applied to **all** seven runtime embeds in the builder, not just mine.
- **Tests:** hostile label, name and path each yield exactly one closer; the bridge still parses; the app still receives the original label verbatim.

### A2. `.status` on bridge errors was dead code, and the test hid it — **fixed**

The first pass documented "`.status` when an HTTP status is known", wired `_sgCmd` to copy `e.data.status`, and wrote a test asserting it. But `cmdReply` never sent a `status` field — the test **faked the host reply**, so it asserted behaviour the host never produced. Classic: a test that tests the test.

- **Fix:** `cmdReply(ok, result, errMsg, code, status)`; the append catch passes `err.http`. Every other caller passes ≤4 args, so the extra optional parameter is inert for them.
- **Test:** now drives the real `_vfsBridgeHandler` through the real `cmdReply` with a stubbed transport, and asserts `code: 'EEDGE', status: 404` on the captured reply, `status: null` (not fabricated) on a denial and on a client-side `EINVAL`.

### A3. "Fixes every `sg.*` namespace" was an overclaim — **fixed, and the claim made true**

Three documents said the `_sgCmd` change fixed error codes for every namespace. It fixed every namespace *routed through `_sgCmd`*. `sg.vfs.write`/`list` (`_vfsMsg`) and `sg.vfs.read` (`_read`) use separate reply channels that **also** dropped the code the host sends (`wReply(false, { err, code: 'EPERM' })`).

- **Fix:** both frame-side handlers now copy `e.data.code`; where the host sends the code *as* the message (`err: 'ENOENT'`), it becomes `.code` too. A plain message yields no fabricated code.
- **Also found:** the host's read-only write reply — `wReply(false, { err: 'Read-only vault' })` — sent **no code** while `AUTHORING.md` and the skill both promised `{code:'EREADONLY'}`. That is exactly the shape the games-vault agent measured. Now sends `EREADONLY`.
- **Docs:** wording corrected in `AUTHORING.md`, the changelog, and the response doc to name the namespaces precisely.

### A4. "Every 403 across the whole API surface" was more than I measured — **corrected**

I measured the edge rewrite (API 403 → static `404.html`) on the **append routes only**, then wrote "every 403 across the API" in three places. Trying to verify: every non-append route gates on an access token and returns **401** before any 403, so a non-append 403 is unreachable without a real token, which I do not have and would not use. New datapoints, both useful to DevOps: **401 passes through as JSON** (`purge` with a missing and a bogus token), so the custom-error rule is specific to 403; and CloudFront rules are per-status not per-path, so the same behaviour elsewhere is *likely but unverified*. All three docs now say exactly that.

### A5. Smaller items — all fixed

| Item | What was wrong | Fix |
|---|---|---|
| `EINVAL` echoed the caller's value unbounded | a token mis-passed as `vault_id` would be echoed whole into an error that reaches the frame and the bridge log | truncated to 40 chars |
| `EAPPEND` fallback code undocumented | apps could see a code not in the table | documented |
| Append denial message changed shape | `'Permission denied'` → `'Permission denied: app.json needs …'`; anything doing `=== 'Permission denied'` breaks. No test in this repo did; the other team's harness string-matched | `.code === 'EPERM'` is the supported check; noted as a compat change in the changelog |
| Advice in the response doc had an unstated side effect | "re-run `configure` with the bridge-derived hash" **replaces** the `enum_key_hash` their harness was configured with, breaking their direct-API listing; and `configure` needs an access token, not just the write key | both caveats added |

### A6. `write` is now stricter client-side — **behaviour change, verified safe, keep**

`SGAppend.write` now rejects a target `vault_id` that fails `^[a-z0-9]{8,24}$` before sending. Verified: that is byte-for-byte the server's `VAULT_ID_PATTERN`, and the web UI generates 8-char lowercase ids. The only way this regresses is the server widening its pattern without the client following — worth a comment, which it has. One test fixture (`vault_id: 'r'`) was changed to a valid id; that test asserts payload passthrough, not id leniency.

## B. Pre-existing bugs the review found — not introduced, fixed because they sat in the same lines

### B1. A `"` or a newline in a vault name killed every app in the vault — **fixed, high value**

The bridge's ready-line `console.log` spliced the vault name **raw** into a double-quoted JS literal, escaping only `'`. Measured before the fix:

| Vault name | Result |
|---|---|
| `He said "hi"` | **SyntaxError: missing ) after argument list** — bridge never runs |
| `multi\nline` | **SyntaxError: Invalid or unexpected token** |
| `back\slash` | parses (by luck) |

A user renames their vault `Q3 "final"` and every app in it dies on mount with an error that names nothing. This was the *second* embedding of the name that A1's count of "5 closers" had pointed at. Same fix (`_jsLit`), five regression names now in the suite.

### B2. `sg.vfs.*` dropped host error codes; the read-only reply had none — see A3.

### B3. Security consideration, not a bug: **the read key *is* the enum key** — **documented**

`enum_key = SHA256("sg-inbox-enum:" || read_key_bytes)` is a pure function of the read key. The web UI imports the key non-extractable on read-only opens, so the *host* cannot derive it — but that is a courtesy, not a boundary: anyone holding a vault's read key can compute its `enum_key` elsewhere and list, fetch and mark-processed that vault's lane. The sgit.ai brief's threat model ("a visitor who extracts the append token cannot list the lane") is true of the *token* and silent about the *read key*. In the telemetry design the receiving vault's read key stays private, so they are fine — but a "publish the read key" pattern on a vault that *receives* a lane would publish enumeration. Now stated plainly in `AUTHORING.md`: never publish the read key of a vault that receives a lane.

## C. Things I checked and found sound

- **`_sgCmd` copying `code`/`status` from a postMessage** — no new attack surface: the same listener already accepted `err` from the same channel; these are scalar properties on an Error, never evaluated. `sg.app.release.commit` exposes nothing an app cannot already read via `sg.history`.
- **`_setActiveManifest` warning** — exactly one caller, always root→folder, so "vault-root manifest" in the message is accurate. Spurious noise is possible when root declares only `fs.read` (default-allow anyway); acceptable.
- **`network` HUD chip** — I documented it; it is implemented (`app-hud.js:415`), not just a comment.
- **Checker** passes unknown codes (`EEDGE`) straight through to `append.error`.
- **Kernel bundle** unaffected (neither edited file is embedded); freshness test green.
- **Server** untouched; 133 append tests green.
