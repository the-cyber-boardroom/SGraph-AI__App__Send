# Code review — can a published vault app write to an append lane?

**date** 6 September 2026
**role** Dev
**scope** `Service__Vault__Append.py`, `Routes__Vault__Append.py`, `sg-append.js`, `sg-append-checker.js`, `app-permissions.js`, `app-shell.js` (bridge), `Storage__Paths.py`
**trigger** Debrief from the games-vault agent (`what-can-it-do` → telemetry vault `kqngdecz`), 6 Sep 2026, following the brief at `https://sgit.ai/briefs/vault-telemetry-append-lanes.html`

**Verdict on the headline claim — "a published vault app has no way to write to an append lane": NOT CONFIRMED.**
Both paths the brief allows are open in code. Path A (direct `fetch`) has an explicit, enforced
opt-in the agent did not find. Path B (`sg.append.write`) has no read-only gate at all — the
denial they hit is a manifest-resolution problem, not a capability ceiling. Two of their four
findings are real and should be fixed; two are misdiagnosed. Details below, all line-referenced.

---

## Part 1 — How the append API actually works

### 1.1 The four-tier gate model

The lane is deliberately **account-less**: write, list, fetch and mark-processed need no SGraph
access token. Only the two owner verbs do.

| Verb | Endpoint (`POST`) | Gate | Checked against |
|---|---|---|---|
| write | `/api/vault/append/write/{vault_id}` | `append_token` **in the body** | `sha256(token) ∈ config.append_anchors` |
| list | `/api/vault/append/list/{vault_id}` | `x-sgraph-vault-enum-key` | `sha256(enum_key) == config.enum_key_hash` |
| fetch | `/api/vault/append/fetch/{vault_id}` | `x-sgraph-vault-enum-key` | same |
| mark-processed | `/api/vault/append/mark-processed/{vault_id}` | `x-sgraph-vault-enum-key` | same |
| purge | `/api/vault/append/purge/{vault_id}` | `x-sgraph-vault-write-key` + `x-sgraph-access-token` | `manifest.write_key_hash` |
| configure | `/api/vault/append/configure/{vault_id}` | `x-sgraph-vault-write-key` + `x-sgraph-access-token` | `manifest.write_key_hash` |

`config.json` is **authoritative** for the append and enum gates (`_load_append_config`,
`Service__Vault__Append.py`); only `write_key_hash` still comes from the manifest, because it is
owned by `Service__Vault__Pointer`. This was the L-2 fix of 10 June 2026.

The write path is genuinely blind: `write__vault_id` returns `{ok: true}` and nothing else — no
file id, no count. A token holder cannot infer lane state from a successful write.

### 1.2 Storage layout

```
{_ROOT}/vault/{vault_id[:2]}/{vault_id}/bare/append/
    config.json                                    ← append_anchors[] + enum_key_hash
    {token}/pending/{epoch_ms}_{rand_hex}.enc      ← 13-digit epoch, 24 hex chars
    {token}/processed/{same filename}              ← after mark-processed
```

`bare/append/` sits outside the version-controlled commit tree, so appends never touch the
branch and never conflict with a push.

### 1.3 Limits (server constants)

| Constant | Value |
|---|---|
| `APPEND_MAX_PAYLOAD` | 5 MB per message |
| `APPEND_MAX_FILES` | 1000 pending files per token folder → HTTP 507 |
| `APPEND_BATCH_MAX_FILE_IDS` | 100 file_ids per fetch/mark/purge |
| `APPEND_DEFAULT_LIMIT` / `APPEND_MAX_LIMIT` | 50 / 200 entries |
| `INLINE_CONTENT_CEILING` | 3 MB cumulative for `include_content` → HTTP 413 |

### 1.4 Path-traversal defence is type-level

`Safe_Str__Vault__Append_Token` = `^[0-9a-f]{16,128}$`, `Safe_Str__Vault__Append__File_Id` =
`^\d{13}_[0-9a-f]{24}\.enc$`, both `strict_validation = True`. A `../` never reaches a storage
call — it fails construction first. This is the right place for that check.

### 1.5 The client stack, in three layers

1. **`SGAppend`** (`sg-append.js`) — the transport. One method per endpoint, attaches the right
   gate header per verb. Errors carry `.code` (`EINVAL`/`EPERM`/`E2BIG`/`ENOSPC`/`EUNREACH`/`EHTTP`)
   and `.http`.
   Key derivation, locked: `enum_key = SHA256("sg-inbox-enum:" || read_key_bytes)`,
   `enum_key_hash = SHA256(enum_key_utf8)`. The `sg-inbox-` prefix is a wire contract — it survived
   the inbox→append rename deliberately.
2. **`SGAppendChecker`** (`sg-append-checker.js`) — no timers. Dormant until the shell calls
   `check(trigger)` on tab focus / app open, diffs a metadata-only `list` against a seen-set.
3. **The bridge** (`app-shell.js:3185-3192` frame side, `3662-3684` host side) — exposes
   `sg.append.*` and maps each verb to a permission.

### 1.6 The bridge's permission map (`app-shell.js:3664`)

```js
{ configure: 'append.configure', write: 'append.write', list: 'append.list',
  fetch: 'append.read', markProcessed: 'append.markProcessed', purge: 'append.purge' }
```

Note `fetch` → **`append.read`**, not `append.fetch`. All six are plain booleans, default-deny,
not path-scoped (`app-permissions.js`, `can()`: `!!(perm.append && perm.append[act] === true)`).

### 1.7 The one structural constraint that matters here

`_getAppendClient()` (`app-shell.js:1224-1241`) builds **one** `SGAppend` bound to the
**currently open vault** — `vaultId: vault._vaultId`, `enumKey` derived from *that* vault's read
key. Therefore:

- `list` / `fetch` / `markProcessed` / `purge` / `configure` **always act on the open vault**.
  There is no way to address a remote vault with them from an app.
- **`write` is the sole exception**: it takes an explicit `vault_id` in its options and posts to
  `/write/{that_vault_id}` with no headers at all (`sg-append.js`, `write()`). This is exactly
  what the cross-vault telemetry case needs, and it is the only verb that supports it.

That asymmetry is correct and deliberate, but it is not written down anywhere — and it is the
direct cause of finding #3 below.

## Part 2 — The agent's four findings, assessed

### Finding 1 — CSP blocks direct `fetch` → **observation correct, conclusion wrong**

The CSP is real and their measurement is accurate. But it is **conditional**, not fixed:

```js
// app-shell.js:2903-2905
var csp = (this._perm && this._perm.network)
    ? ''                                   // explicit escape hatch — see permissions.network
    : '<meta http-equiv="Content-Security-Policy" content="connect-src blob: data:">';
```

`permissions.network: true` in `app.json` omits the meta entirely and reopens direct egress. It
is parsed in `app-permissions.js` and has been genuinely enforced since v0.33.47 (before that it
was parsed and read by nothing — see `architect-review__sg-llm-as-built-and-next-steps`, F4).

So the brief's "verify the CSP allows connect-src" check has an answer: it doesn't by default,
and `permissions.network` is how you change that.

**Their documentation complaint is nevertheless justified.** `permissions.network` appears
**zero times** in `library/guides/vault-html/AUTHORING.md`, and zero times in the sgit.ai brief.
It is discoverable only by reading `app-permissions.js`. That is a real docs gap and the single
highest-value fix on this list.

**Caveat worth giving them:** `network: true` is a blunt instrument — it removes the CSP for the
whole frame, not just the API host, in an app that legitimately holds decrypted vault content.
For a telemetry sender that is a poor trade. Their own suggestion — scope `connect-src` to the
vault's API host when an app declares a lane — is the better design, and I'd support it as a
proposal. Prefer the bridge path (below), which needs no CSP change at all.

### Finding 2 — `sg.append.write` → "Permission denied" → **misdiagnosed; it is not about `writable`**

Their hypothesis is that the gate is "this app is read-only". **The code says otherwise.** The
append branch checks exactly one thing:

```js
// app-shell.js:3667
if (!self._can(ibCap, '')) { cmdReply(false, null, 'Permission denied'); ... }
```

`_can` → `AppPermissions.can(this._perm, 'append.write', '')` → `perm.append.write === true`.
There is **no** `writable` check, **no** consent gate, and no read-only branch anywhere in the
append handler. Compare `vfs.write` (`app-shell.js:3522`), which checks `fs.write` and then hits a
separate `EREADONLY` throw at the data-source layer — a different code path with a different
error string. Their proposed probe (deny `sg.vfs.write` with the same message → gate is
read-only) would therefore have given them a **false positive**: both deny with
`'Permission denied'`, but for unrelated reasons.

`sg.app.writable: false` is computed at `app-shell.js:2867` as
`_writable && dataSource.writable` and is irrelevant to append.

**The `app.json` key they used is correct.** `permissions.append.write: true` is exactly right,
and is covered by `tests/unit/vault_ui/loader/test__app_permissions__append.js`. Since the grant
is right and the gate reads only that grant, the conclusion is forced: **`_perm` was not built
from the `app.json` they edited.** Four candidate causes, in the order I'd check them:

1. **A folder-level `app.json` is overriding the root one.** If the entry HTML is deep-linked
   inside a subfolder that has its own `app.json`, `_resolveFolderAppJson` →
   `_setActiveManifest(folderJson)` replaces `_perm` **wholesale** —
   `AppNavHelpers.resolveFolderManifest` does `Object.assign({}, folderJson)`, so nothing is
   inherited from the root manifest. Root-level grants are then silently ignored. This is the
   most common cause and the easiest to miss.
2. **The vault is pinned to a release.** With `.vault/releases.json` present, `app.json` is read
   from that **commit**, not HEAD (`_applyRelease`, resolved *before* `_readAppJson`) — so
   pushing a new manifest changes nothing until the pin moves. Note this also forces
   `this._writable = false` "for EVERYONE, owner included" (`app-shell.js:1332`), which would
   independently explain the `writable: false` they saw. Given both symptoms co-occur, **this is
   my leading hypothesis.**
3. **They opened a share token, not the vault key.** A share token is a read-only snapshot at a
   point in time; a later `sgit push` is simply not in it.
4. A stale cached tree in the browser.

**Answer to their direct question** ("is there a correct `app.json` key?"): yes —
`{"permissions": {"append": {"write": true}}}`. Nothing else is required, and a read-only
session does not block it.

### Finding 3 — `sg.append.list` returns the HTML 404 page → **real bug, wrong root cause**

The bridge route exists (`app-shell.js:3674` maps `list` → `inbox.list(...)`), so "the bridge's
route to it does not [exist]" is not the explanation.

The decisive clue is in their own evidence: `inbox` is a **body** field, not a path segment. It
cannot affect the URL. So four different `inbox` values producing an identical 404 proves **the
URL itself is wrong**, independently of `inbox`. The URL is built as:

```js
`${this.endpoint}/api/vault/append/list/${this.vaultId}`
```

Working back from the server, a 404 pins it down precisely:

- a malformed non-empty `vault_id` → **400** (`_validate_vault_id`)
- a well-formed but wrong `vault_id` → **403** (gate fails, no manifest)
- an **empty** `vaultId` → `/api/vault/append/list/` matches no route → **404 HTML page** ✔
- an `endpoint` carrying a path prefix (e.g. `…/en-gb`) → also **404 HTML page** ✔

So it is an empty `vaultId` or a path-bearing `endpoint` in `_getAppendClient()`. One line in
the frame settles it:

```js
try { await sg.append.list({ limit: 1 }) } catch (e) { console.log(e.message.slice(0, 120)) }
// then compare against the vault id shown in the HUD
```

**But the more important answer is design, not diagnosis:** even with a correct URL, `list`
would have enumerated the **games** vault's own lane, never `kqngdecz`. Per §1.7, only `write`
crosses vaults. Listing a remote lane from an app is not supported and should not be — the enum
key is the recipient's, and handing it to a published app would give every visitor read access
to the whole lane. Their draining tooling has to run where the enum key legitimately lives
(the telemetry vault's own dashboard, or `sgit`), which is what they are already doing.

**Both their asks are agreed and are genuine bugs:**
- `SGAppend._post` does `res.text()` and stuffs an entire HTML error page into `Error.message`.
  It should not; parse JSON `detail` when present and truncate otherwise.
- `SGAppend.list` should validate `this.vaultId`/`endpoint` and throw `EINVAL` before issuing a
  request that cannot succeed.

### Finding 4 — `inbox` == the append token, byte for byte → **CONFIRMED**

Verified end to end:

- `append()` folders by the **raw** token: `path__vault_append_pending_prefix(vault_id, token)`
  where `token = self._safe_token(append_token)`.
- `Storage__Paths.py` interpolates it directly: `…/bare/append/{token}/pending/{file_name}`.
- `list_entries()` sets `entry = dict(inbox = token_folder, …)` — the folder name, i.e. the raw
  token — and no test asserts anything about this value's relationship to the token.

Meanwhile `config.append_anchors` stores `sha256(token)`. So the design hashes the token in
config and then writes the plaintext token into the object key. The hashing in `append_anchors`
buys much less than it appears to.

**Severity is moderate, not critical**, for two reasons the debrief doesn't credit:

1. The append token is **designed to be a public lane address**. Per the schema's own docstring:
   *"The append token (= H(recipient public key)) which also names the append folder."* It is a
   write-only capability — an address, closer to an email address than a password. Anyone who
   knows the recipient's public key can already derive it.
2. `list` is gated by the **enum key**, so the disclosure is to the vault owner, who by
   construction already holds every credential in play. It is not a public leak.

The residual risk is real though, and it is about **storage**, not the API: the raw token becomes
an S3 object key, so it lands in access logs, inventory reports, bucket listings and any
backup — surfaces with a very different audience from the enum-key holder.

**Recommendation:** name the folder `sha256(token)` and return that as `inbox`. `write` still
receives the raw token and hashes it to derive the folder, so the wire contract for `write` is
unchanged; `list`/`fetch`/`mark`/`purge` would carry the hash, which is all they ever need. This
is a breaking change for existing lanes and needs a migration, so it is an issue to file, not a
drive-by fix. Either way, **document the current behaviour now** — an integrator should not have
to discover from a debrief that `inbox` is the token.

### Minor — error codes are lost at the bridge boundary → **agreed, and half-built already**

Their ask ("a stable `code` so an app can degrade deliberately") is closer than they think.
`SGAppend._err` already sets `.code` and `.http`, and `_emitBridgeCall` already records the code
for the HUD (`app-shell.js:3683`). The information is simply **dropped crossing postMessage**:
`cmdReply(false, null, 'Permission denied')` sends a bare string, so `Object.keys(e)` is `[]` in
the frame — exactly as they measured. Propagating `{err, code}` through `cmdReply` is a small,
well-scoped fix and would satisfy their `permission_denied` / `missing_inbox` / `no_route` ask
using codes that already exist.

### Their open question — what fires `append.new-messages`?

`_initAppendChecker` (`app-shell.js:663-682`) builds the checker **only** when all of:

1. the app declares `"host_events": ["append.new-messages"]` (or `append.error`) in `app.json` —
   default-deny, parsed by `AppHostEvents`;
2. `SGAppend` + `SGAppendChecker` are loaded (they are on `/en-gb/app`, not on the vault browser
   or the `browse/` surface);
3. `_getAppendClient()` returns a client — i.e. a vault is open with a derivable enum key.

It then fires on **tab focus and app open** (`_scheduleAppendCheck`, 1 s debounce) — never on a
timer. Payload: `{total, per_anchor, entries, new_count, trigger, last_check}`, with `entries`
null because the shell hard-codes `auto_fetch: false`; apps pull ciphertext with
`sg.append.fetch`.

**Why it never fired for them:** the checker calls `this._client.list(...)`, which — per §1.7 —
lists the **currently open vault**. In the games vault (which has no lane of its own) there is
nothing to report, so no event can ever fire, regardless of `host_events`. It would fire in the
telemetry vault's own dashboard app, provided that app declares the `host_events` entry.

## Part 3 — What I recommend we change

| # | Change | Where | Priority |
|---|---|---|---|
| 1 | Document `permissions.network` (what it does, that it is all-or-nothing, and that the bridge is preferred) | `AUTHORING.md` | **High** |
| 2 | Document that only `write` takes a `vault_id`; every other verb is bound to the open vault | `AUTHORING.md` §append | **High** |
| 3 | Document that `inbox` is the lane id returned by `list`, and that today it equals the append token | `AUTHORING.md`, reality doc | **High** |
| 4 | Propagate `{err, code}` through `cmdReply` for the append branch | `app-shell.js:3667,3683` | Medium |
| 5 | Stop putting HTML error pages in `Error.message`; validate `vaultId`/`endpoint` and throw `EINVAL` | `sg-append.js` `_post`, `list` | Medium |
| 6 | Warn (HUD + console) when a folder-level `app.json` replaces root permissions | `app-shell.js` `_setActiveManifest` | Medium |
| 7 | File an issue: fold the lane folder to `sha256(token)`; keep `write`'s wire contract, migrate existing lanes | `Service__Vault__Append.py`, `Storage__Paths.py` | Medium |
| 8 | Proposal: scope `connect-src` to the vault's API host for apps that declare a lane, instead of all-or-nothing `network` | `app-shell.js` CSP builder | Low (design) |

**Not recommended:** loosening the default CSP, or adding a read-only bypass for append. Neither
is the problem, and the first would weaken the containment that makes it safe to hand an app
decrypted vault content.

## Part 4 — What to tell the games-vault agent

1. **Your `app.json` key was right.** `permissions.append.write: true` is the correct and only
   grant. Read-only does not block it.
2. **Check for a release pin first.** If the vault has `.vault/releases.json`, your `app.json`
   is being read from a pinned commit and your push is not being seen — and that also explains
   `writable: false`. Then check whether the entry HTML sits in a subfolder with its own
   `app.json`, which replaces root permissions wholesale.
3. **`permissions.network: true` unblocks the direct `fetch`** — undocumented, our fault. Prefer
   the bridge path once #2 is resolved; `network` reopens *all* egress from a frame holding
   decrypted vault content.
4. **`sg.append.list` cannot see `kqngdecz` from the games vault** — by design; only `write`
   crosses vaults. Keep draining with the enum key where it legitimately lives. The 404 is a
   separate client-side URL bug we're fixing.
5. **`inbox` == the append token is real and intended-ish** — it's a public lane address
   (`H(pubkey)`), write-only, and `list` needs the enum key. We're still going to hash the folder
   name, because the raw token currently lands in storage keys and logs.
6. **`append.new-messages` will never fire in the games vault** — the checker only watches the
   open vault's lane. Declare `host_events` in the telemetry vault's dashboard app instead.

Their harness is good work and the measurements were accurate throughout; the two misdiagnoses
both came from testing against an app whose manifest wasn't the one being served. The 22-probe
suite should be kept and pointed at a live (unpinned) vault.
