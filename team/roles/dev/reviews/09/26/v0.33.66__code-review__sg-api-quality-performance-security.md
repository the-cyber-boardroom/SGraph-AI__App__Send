# Code review — SG/API (user Lambda): quality, performance, security

**date** 26 September 2026
**role** Dev (with an AppSec lens)
**scope** `sgraph_ai_app_send/lambda__user/**` — the transfer, vault-pointer, append, presigned, public-preview, early-access and info routes plus their services and storage backends. This is the API now serving `send.sgraph.ai` file sharing and vaults in production.
**method** Read every route and service; ran the user-Lambda unit suite (464 pass / 1 environivment-only fail / 9 skipped); executed targeted probes against the in-memory and disk backends. Findings are code-verified; each carries impact and a concrete fix. No production system was touched.

---

## 0 · Summary

The API is well-structured and the zero-knowledge contract holds: the server stores ciphertext under opaque IDs and every access decision is a hash comparison. The core transfer and vault flows are correct and covered by tests. The findings below are **hardening and robustness**, not a broken contract. One finding (S1) is a real input-validation gap that matters for the container/EC2 deployment targets; the rest are defence-in-depth, performance, and consistency.

Severity key: **S** security · **P** performance · **Q** quality/correctness. Ranked most-actionable first.

| # | Sev | One line | Fix size |
|---|-----|----------|----------|
| S1 | High (disk/container only) | Vault `file_id` reaches the storage path unvalidated | S |
| S2 | Med | No request-size guard in app layer; large-body reads build full bytes in memory | M |
| S3 | Med | Three copies of `check_access_token`; only one has the TTL cache and they can drift | S |
| S4 | Low | Public-preview endpoint runs 600k-iteration PBKDF2 per request, unauthenticated | M |
| P1 | Med | Vault zip cache-key reads every file's bytes to hash sizes | S |
| P2 | Low | `list_files` re-listed twice per zip build | S |
| Q1 | Med | `download_url` returned by `complete` is a dead route (`/d/{id}`) | S |
| Q2 | Low | `create_transfer` hardcodes `sender_ip=''`; transparency IP is always the hash of empty | S |
| Q3 | Low | Presigned "complete" marks payload present without verifying the S3 object exists | S |
| Q4 | Low | `validate_token`/`check_token` route names use `_` but the reality/site docs show `-` | S |

## 1 · Security

### S1 — Vault `file_id` is not validated before it becomes a storage key (High on disk mode)

`Routes__Vault__Pointer.write__vault_id__file_id` takes `file_id : str` (raw, not a `Safe_Str`) and passes `str(file_id)` to `Service__Vault__Pointer.write`, which builds the storage path as `…/{vault_id}/{file_id}/payload` with no normalisation. The `vault_id` **is** validated (`VAULT_ID_PATTERN`), but `file_id` is not, on any of write / read / read-base64 / delete / batch.

- **On S3 and Memory backends (production `send.sgraph.ai`): not exploitable for traversal.** S3 keys are a flat namespace — a `../` in the key is a literal key segment, not a directory move — and the Memory backend is a dict keyed by the full path string. The blast radius there is limited to writing/reading a weird-but-still-scoped key, gated by the vault write key.
- **On the Disk backend (`Storage_FS__Local_Disk`, used by the Docker / container / EC2 deployment targets): it is a path-traversal exposure.** A `file_id` containing `../` segments resolves outside the vault's directory when written to the real filesystem. I confirmed this against a throwaway disk root: a crafted `file_id` landed a file above the intended vault folder. The write still requires a valid vault write key, so this is not anonymous — but a caller with write access to *one* vault should not be able to place bytes outside it, and read/list are unauthenticated.

**Why it matters even with S3 in prod:** the appended-lane code already validates its path components with a strict `Safe_Str__Vault__Append_Token` / `Safe_Str__Vault__Append__File_Id` (`^\d{13}_[0-9a-f]{24}\.enc$`). The pointer path is the one privileged surface that does *not* apply the same discipline, so the codebase is inconsistent with its own established pattern, and any future move of a deployment to disk mode (or a bug that lets disk mode run in a shared context) silently becomes exploitable.

**Fix (small, matches existing pattern):** validate `file_id` at the route boundary with a `Safe_Str` that rejects `..`, leading `/`, and NUL — or normalise-and-reject in `Service__Vault__Pointer` the way `AppPermissions.normalizePath` does client-side. A regex like `^[A-Za-z0-9._\-/]+$` **plus** an explicit "no `..` segment" check (a bare character-class does not stop `a/../../b`). Add the traversal negative tests that the append service already has (8 of them) to the pointer suite.

### S2 — No request-size guard; whole-body reads materialise in memory

`upload__vault_id__file_id` and `write__vault_id__file_id` do `await request.body()` and hold the full payload in memory before the service writes it. Downloads do the same in reverse. There is a *response* guard (the `LAMBDA_RESPONSE_LIMIT` / `LAMBDA_BASE64_LIMIT` checks) but no *request* guard in the app layer.

- On Lambda the platform caps the request at 6 MB, so the ceiling is enforced by the runtime — acceptable there.
- On the container/EC2 targets there is no such cap, so a large POST is bounded only by available memory. For an unauthenticated-read + write-key-gated-write service this is a low-to-medium DoS surface.

**Fix:** add a `Content-Length` check at the write routes returning 413 above a configured ceiling (mirror the existing `MAX_FILE_SIZE_DIRECT = 5 MB` the browser client already respects), and document that large blobs must use the presigned/multipart path. This also makes the "use presigned instead" error reachable *before* the bytes are read, not after.

### S3 — `check_access_token` is copied three times; only one is cached, and they can drift

`check_access_token` exists as near-identical copies in `Routes__Transfers`, `Routes__Presigned`, and `Routes__Vault__Presigned`, while `Routes__Vault__Pointer` and `Routes__Vault__Append` use the newer cached `Service__Access_Token`. The three inline copies:

- do **not** use the TTL cache, so they hit the Admin Lambda on every call (see also P-note below);
- each re-implement the same status-code logic, so a change to the auth contract (e.g. adding a `suspended` status) has to be made in four places and will be missed in some.

**Fix:** route all five through `Service__Access_Token`. It already exists, is tested, and centralises the env-var fallback. This is a delete-code change, not new surface.

**Note on the cache's negative path (correct, worth keeping documented):** `Service__Access_Token` caches positives only, for `ttl_seconds` (default 60), and never caches negatives — so a freshly created token works on the next request and a revoked token stops within the TTL. That is the right trade-off; just make every route use it.

### S4 — Public-preview endpoint does 600k-iteration PBKDF2 on every unauthenticated request

`Public_Preview__Service.derive_read_key_bytes` runs `PBKDF2-HMAC-SHA256(id, 600000)` per call, and `GET /api/public-preview/info/{id}` and `/og/{id}` are anonymous. I measured ~420 ms of CPU per derivation on this box. Two anonymous routes each pay that cost per hit.

- This is deliberate (it matches the browser derivation, and the preview is *meant* to be public), so it is not a confidentiality issue.
- It is a **cheap asymmetric-cost lever**: an unauthenticated caller forces ~0.4 s of Lambda CPU per request with a trivial GET, and each is billed. At any volume this is a cost-amplification / soft-DoS vector.

**Fix:** the derivation is deterministic in `public_id`, so cache the derived `read_key`/`transfer_id` per `public_id` (in-Lambda LRU, same pattern as `_manifest_cache`) — the first hit pays PBKDF2, subsequent hits for the same id are free. Optionally front these routes with a short CloudFront TTL (the og-image already sets `max-age=300`; the info/og routes send no cache header). Consider a lower iteration count *for the preview salt only* if the browser side can match it — the preview key protects nothing secret.

### S-notes (no action beyond awareness)

- **CORS** is `allow_origins=["*"]`, `allow_credentials=False`. That is the correct pairing for a token-in-header API (wildcard origin with credentials would be rejected by browsers anyway). Fine.
- **Token in query param** (`?access_token=`) is accepted as a fallback in `check_access_token`. It works but lands tokens in access logs. The VoiceDebrief guide already tells integrators to use the header; worth a one-line deprecation note in the API docs, not a code change.
- **`_hash_write_key` is a bare SHA-256** of the write key (no salt). This is acceptable *because* the write key is a high-entropy random value, not a password — a rainbow table is infeasible against 256-bit random input. Documented here so it is not "fixed" into a slow KDF that would add latency to every write for no gain.

## 2 · Performance

### P1 — Vault zip cache-key reads every file's bytes just to hash sizes

`Service__Vault__Zip.vault_content_hash` iterates all files and calls `self.vault_service.read(vault_id, file_id)` **to take `len(payload)`** for the hash input. That is a full GET of every object in the vault to compute a cache key — before the cache is even consulted. For a large vault this is O(n) S3 reads on every zip request, cached or not.

**Fix:** the S3/Memory list already yields keys; use the object size from the listing (or a HEAD) instead of reading the bytes. Memory-FS's `folder__files__all` can be extended to return sizes, or hash the sorted `file_id` list plus each object's `ETag`/size from a metadata listing. Falls back cleanly to the current behaviour if sizes are unavailable.

### P2 — `list_files` computed twice per zip build

`get_or_create_zip` calls `vault_content_hash` (which calls `list_files`), then `build_zip` (which calls `list_files` again), then `list_files` a third time for `file_count`. Three listings per request. Collapse to one.

### P-note — Admin round-trip on the three uncached auth copies

Tied to S3: the three inline `check_access_token` copies call `token_lookup` (an inter-Lambda HTTP round-trip) on every authenticated presigned/transfer call. `Service__Access_Token` was written precisely to avoid this on the vault write path. Consolidating (S3) removes a network hop from the hot path of every large-file and multipart operation.

## 3 · Quality / correctness

### Q1 — `complete` returns a `download_url` that 404s

`complete_transfer` returns `download_url = f'/d/{transfer_id}'`. There is no `/d/{id}` route (verified: 404). The browser client ignores it and builds the real link (`/en-gb/download/#…`), and the VoiceDebrief guide tells integrators to ignore it too — but shipping a field named `download_url` that does not resolve is a trap for every new integrator. **Fix:** either drop the field, or return the real canonical link (`/en-gb/download/#{transfer_id}` — link-only, since the server must never see the key). Prefer returning the link-only form; it is honest and useful.

### Q2 — Transfer `sender_ip` is hardcoded empty

`Routes__Transfers.create` passes `sender_ip = ''` (with a `todo` already in place), so `sender_ip_hash` is always `sha256('')` and the transparency block's `ip` field is a constant. The download path *does* capture the downloader IP correctly; only the creator IP is dropped. **Fix:** extract `raw_request.client.host` in `create` as the download path already does. Small, and it makes the transparency record meaningful.

### Q3 — Presigned "complete" trusts the client's ETags without confirming the object

`Service__Presigned_Urls.complete_multipart_upload` calls S3 `complete_multipart_upload` and then appends an `upload` event to the metadata so the existing `complete_transfer` flow sees `has_payload == True`. It never HEADs the assembled object. If the S3 call is mocked/partial or the parts list is malformed, the transfer can be marked completable with no valid object. **Fix:** HEAD the key after assembly and only record the `upload` event if it exists and its size is plausible.

### Q4 — Route-name punctuation mismatch (`_` vs `-`)

The transfer token routes register as `check_token` / `validate_token` (underscores, via the method names) but the reality doc and the sgit.ai API pages describe them with hyphens (`check-token` / `validate-token`), and the `ROUTES_PATHS__TRANSFERS` constant lists the hyphen form. Whichever is live, the constant and the docs disagree with the registered path. **Fix:** confirm the actual registered path (osbot-fast-api derives it from the method name → underscores) and make the constant + docs match reality. This is exactly the class of drift that sent the VoiceDebrief integration to a wrong header name last time.

### Q-note — the one failing unit test is environmental, not a bug

`test_Send__Config.py::test__has_aws_credentials__false_by_default` fails **in this container only**, because the sandbox has `AWS_*` env vars set, so `aws_config.aws_configured()` returns True. The test asserts a clean-env default. It is a test-isolation gap (the test should clear the AWS env, or the container should not leak creds into the suite), not a code defect. Worth a `monkeypatch`/`delenv` in the test so CI on a credentialed runner stays green.

## 4 · What is done well (so it is not lost in a refactor)

- **The zero-knowledge contract is clean.** Server stores `SHA-256(key)`, compares hashes, never holds plaintext or keys. The transparency block honestly enumerates stored vs encrypted vs not-stored fields.
- **Immutable-object caching is correct.** `-imm-` content-addressed objects get `max-age=31536000, immutable`; mutable refs get `no-store`. This is the right call and is the only cache tier that survives a reload in the null-origin sandboxed iframe.
- **The append service is the model to copy.** Strict typed path components, blind write response, per-tier gates, traversal tests. S1's fix is "make the pointer path look like the append path."
- **SnapStart discipline.** The S3 client is created lazily on first request, not at snapshot time — the comments explain why, and that is a real cold-start correctness fix.
- **Tombstone-on-delete** prevents vault-ID re-registration by default, with an explicit `purge` opt-in. Good default.

---

## 5 · Recommended order

1. **S1** (validate `file_id`) and **Q4** (path-name drift) — same area, ship together, add the traversal tests.
2. **S3 + P-note** (consolidate auth onto `Service__Access_Token`) — deletes code, removes a network hop.
3. **P1/P2** (zip cache-key and double-listing) — one small service change.
4. **Q1/Q2/Q3** (dead `download_url`, creator IP, presigned HEAD) — small correctness fixes.
5. **S2/S4** (request-size guard, preview PBKDF2 cache) — hardening for the container targets and cost control.

None of these change the wire contract for existing clients except Q1 (which only makes a currently-dead field useful) and Q4 (which should be reconciled to whatever is *already* live, so no client breaks).
