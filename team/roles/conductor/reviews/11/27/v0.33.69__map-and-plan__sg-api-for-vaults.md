## 1 · The API as it exists (EXISTS, `dev`)

All paths are on the user Lambda. Headers: access token `x-sgraph-access-token` (not `x-sgraph-send-access-token`, which gives 401); vault write key `x-sgraph-vault-write-key`; append read key `x-sgraph-vault-enum-key`; public bucket switch `x-vault-public: true`, plus `x-vault-read-key` on the first public write. Constants are in `sgraph_ai_app_send/lambda__user/user__config.py`.

### 1.1 Pointer: an opaque blob store (`Routes__Vault__Pointer.py`, `Service__Vault__Pointer.py`)

| Method | Path | Gate | Request | Response |
|---|---|---|---|---|
| PUT | `/api/vault/write/{vault_id}/{file_id:path}` | token + write key | raw bytes | `{file_id, vault_id, status:"completed"}`; 400 missing key or empty body; 403 key mismatch |
| GET | `/api/vault/read/{vault_id}/{file_id:path}` | none | | raw bytes; `Cache-Control` immutable for ids containing `-imm-`, else `no-store`; 404 |
| GET | `/api/vault/read-base64/{vault_id}/{file_id:path}` | none | | `{vault_id, file_id, data, size}`; 413 above 3.75 MB |
| DELETE | `/api/vault/delete/{vault_id}/{file_id:path}` | token + write key | | `{file_id, vault_id, status:"deleted"}`; 403 mismatch or missing |
| POST | `/api/vault/batch/{vault_id}` | none if every op is `read`, else token + write key | `{operations:[{op, file_id, data?, match?}]}`, at most 100 | `{vault_id, results:[…]}` (see 1.2) |
| GET | `/api/vault/list/{vault_id}?prefix=` | none | | `{vault_id, prefix, files:[file_id…]}`, unpaginated |
| GET | `/api/vault/health/{vault_id}` | none | | `{status:"ok", vault_id}` or 404 |
| GET | `/api/vault/public-info/{vault_id}` | none | | `public-vault.json`; 501 if public vaults are not configured |
| GET | `/api/vault/zip/{vault_id}` | token + write key | | zip of the vault, cached by content hash |
| DELETE | `/api/vault/destroy/{vault_id}` | token + write key | `{vault_id, purge?}` | tombstone unless `purge: true` |
| PUT/GET/GET | `/api/vault/write|read|read-base64/{vault_id}` | | | catch-alls for a missing `file_id` |

**Batch, in detail.** Ops are `read`, `write`, `write-if-match`, `delete`. They run **in order, best effort**. A `write-if-match` conflict or an unknown op **stops** the batch, but ops before it are already applied. `write-if-match` compares `base64(match)` with the **full current bytes** (absent `match` means "must not exist"), and on conflict returns `current` (base64). The comparison is a read followed by a write in the Lambda, **not a storage conditional write**. A read-only batch reads in parallel (16 workers, first read on the request thread).

**Storage layout.** `{root}/vault/{vault_id[:2]}/{vault_id}/{file_id}/payload`. `manifest.json` holds `SHA-256(write_key)` (first write wins). `deleted.json` is the tombstone. `vault_id` is checked against `VAULT_ID_PATTERN`. **`file_id` is not validated** (26 Sep review S1).

### 1.2 How a vault maps onto those file ids (client side, EXISTS)

The server sees only `vault_id`, opaque file ids and ciphertext. The mapping is all in the clients:

| Vault thing | file_id | Mutable? |
|---|---|---|
| blob, tree, commit | `bare/data/obj-cas-imm-{sha256(ciphertext)[:12 or :32 hex by vault format]}` | no |
| PKI key | `bare/keys/key-rnd-imm-{hex}` | no |
| named HEAD ref | `bare/refs/ref-pid-muw-{HMAC(read_key, "sg-vault-v1:file-id:ref:{vault_id}")}` | yes, CAS |
| branch index | `bare/indexes/idx-pid-muw-{HMAC(read_key, "…:branch-index:{vault_id}")}` | yes, shared, CAS with merge |
| append lanes | `bare/append/…` (server-managed, never in `list`) | server |

Keys (from `sg-vault-crypto.js` and the vault reality doc): a vault key `passphrase:vault_id` gives `read_key = PBKDF2(passphrase, "sg-vault-v1:{vault_id}")` and `write_key = PBKDF2(passphrase, "sg-vault-v1:write:{vault_id}")`, 600k iterations. A simple token `word-word-NNNN` gives `vault_id = SHA-256(token)[:12 hex]`, and `read_key` and `write_key` by HKDF from `PBKDF2(token, "sgraph-send-v1")`. The server stores `SHA-256(write_key)` and compares it. The append enum key is `SHA-256("sg-inbox-enum:" ‖ read_key)`, so publishing a read key publishes lane enumeration.

### 1.3 Presigned large objects (`Routes__Vault__Presigned.py`)

`POST /api/vault/presigned/initiate|complete|cancel/{vault_id}` (token + write key) and `GET /api/vault/presigned/read-url/{vault_id}/{file_id}` (none). S3 only. This route class still has its own uncached copy of the token check (26 Sep review S3).

### 1.4 Append lanes, the vault inbox API (`Routes__Vault__Append.py`)

12 endpoints, listed in full with their gates in `team/roles/librarian/reality/send-api/index.md` (§ Vault Append): `GET limits`, and `POST configure | write | list | fetch | mark-processed | unmark | stats | blob-upload | blob-url | blob-delete | purge`, each with `/{vault_id}`. Four keys: `append_token` (write only, in the body), enum key (read, optionally scoped to lanes since v2 Phase 2), write key (configure, purge), private key (client only). Lanes v2 Phases 1 to 3 shipped on 25 Nov (debrief `team/humans/dinis_cruz/debriefs/11/25/v0.33.69__debrief__append-lanes-v2-phases-1-3.md`). New endpoints answer 401 JSON. Old ones answer 403, which the CDN rewrites to an HTML 404 (open since September). The lane folder, and the `inbox` field, is the **raw append token**.

|---|---|---|
| **Vault web UI** (`sg-send.js`, `sg-vault*.js`, `sg-append.js`) | pointer `write`, `read`, `delete`, `batch` (reads, commit writes, `write-if-match` for refs and the branch index), `list`, `health`, `destroy`, `presigned/read-url`; append `configure`, `write`, `list`, `fetch`, `mark-processed`, `unmark`, `stats`, `blob-upload`, `blob-url`, `blob-delete`, `purge`. **Not** `limits` and not `deferred` handling yet (open in the 25 Nov debrief). | **sgit CLI** (`sgit-ai 0.27.0`, PyPI) | pointer `write`, `read`, `delete`, `batch` (`read`, `write`, `write-if-match`, `delete`), `list`, `destroy`, all four presigned routes (with HTTP `Range` reads of presigned URLs), plus `/api/info` and `/api/auth/whoami`. **No append-lane calls at all.** Sends the token as both `x-sgraph-access-token` and `X-API-Key`. Default host `dev.send.sgraph.ai` | package source, `sgit_ai/network/api/Vault__API.py` |
| **Append-lane users** (a.maestro, crm.dev.a, sites-pages.a, router.a, the mail team, crm.ios) | append endpoints over HTTP | 25 Nov debrief and plan |
| **CMS proposal** (cl-6.onboarding, SovereignWebsite/Site__Agent__Onboarding) | **none today.** The prototype makes one same-origin `fetch('demo/content.json')` and keeps uploads in browser memory, named by SHA-256. | **Account B's GitHub browser tool** | **unknown here**, same reason | n/a |
| MCP clients (`/mcp`) | every route tagged `api/vault` and `api/vault/presigned` | `Fast_API__SGraph__App__Send__User.setup_mcp` |

**One drift to note in the CLI.** `Vault__API.batch`'s docstring says `match` is "SHA256 hash of current content" and that a failed `write-if-match` "rejects the entire batch". Its unused `Schema__Batch_Operation.match` is typed `Safe_Str__SHA256`. The code that actually sends it (`Vault__Index_Sync`, `Vault__Serve__Mirror`) sends base64 of the full current bytes, which is what the server expects. So the wire works. But the documentation on both sides disagrees with the server about atomicity: the server is best effort and ordered, not atomic.
