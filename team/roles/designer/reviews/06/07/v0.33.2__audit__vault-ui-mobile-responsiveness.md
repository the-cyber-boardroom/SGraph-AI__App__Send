# Vault UI — Mobile & Responsiveness Audit (Designer view)

**Version:** v0.33.2
**Date:** 2026-06-07
**Role:** Designer
**Scope:** `https://dev.vault.sgraph.ai/` and `https://vault.sgraph.ai/` — the `/vault` route. The `/app` route is out of scope (works acceptably per brief).
**Status:** Audit only — no code changes in this commit.
**Companion review:** `../../dev/reviews/06/07/v0.33.2__audit__vault-ui-mobile-responsiveness.md` (engineering counterpart with code-level detail)

---

## TL;DR

`/vault` was designed as a **desktop IDE-style three-pane workspace** (sidebar nav + file tree + tabbed preview, with an on-demand debug rail). That metaphor is the right one for power users on a laptop — and it's also the reason the UI breaks on mobile. There is no **mobile design** in the current product; the desktop layout is simply re-rendered into less space.

Two issues Dinis named directly:
- **Resize doesn't work on mobile** — the split-pane drag handle (`<sg-layout>` pane separator) is a desktop mouse affordance with no touch fallback. Even where it accepts the gesture, it competes with the page scroll/zoom, so it's effectively unusable.
- **Large parts are not accessible on a narrow viewport** — at ~360 px the file tree shrinks to ~60 px wide (filenames clip), the right column buttons overflow the header, the inline auth banner spans wider than the screen, and the Settings/SGit views overflow horizontally.

Both are symptoms of the same root cause: **the design contract is "desktop only"**, but it's deployed at a URL anyone may hit from a phone (especially via share-token deep-links pasted into chat).

## Where the design contract is missing

### 1. There is no defined mobile information architecture

A desktop user gets:
- Left nav: Files / SGit / Settings
- Centre: Files tree (locked 20% pane)
- Right: tabbed previews (clickable files become tabs), plus optional Debug rail
- Top: brand + vault-name + Read-only badge + Upload + Debug + raw + Lock + version
- Bottom: status bar (stats + message badge)

A mobile user **needs** something different — but the design doesn't say what. The current code just rerenders all of the above into a 360 px column, where it can't fit. **The first deliverable here is a mobile IA, not CSS tweaks.**

### 2. The split-pane metaphor doesn't translate to phones

`<sg-layout>` is a great desktop pattern (fractal panes, draggable splitters, dockable tabs). On a phone it should not be present at all — touch users want a **single screen at a time** (Files OR a file's preview), with a clear way to navigate between them. The current implementation locks the Files pane open and never gives the user a way to give the file preview the whole screen.

### 3. Chrome density is desktop-dense

- Header has 7 controls (brand, vault-name, badge, Upload, Debug, raw, Lock, version) in a `flex` row with no wrap.
- Per-file tab action bar (rendered inline at `vault-shell.js:449-526`) has filename + raw + Edit + Save + Cancel + Rename + Download + Delete in one row.
- Inline auth banner has message + input + Set Key + ×.
- Settings rows: label / input / button on one row each.

Tap targets are below the 44 × 44 px Apple HIG / WCAG 2.5.5 guideline (e.g. the "raw" link is `0.625rem` / 10 px font with `padding: 0.25rem 0.375rem` → roughly 18 × 18 px tappable). On mobile, ~half of these need to consolidate into an overflow menu or an icon-only row.

### 4. No touch affordances

- Drag handles assume mouse precision.
- No `touch-action: none` on the split-pane handle, so the OS swallows the gesture for scroll/zoom.
- Drag-and-drop on the tree view (folder reorder, drag-into-folder) is mouse-only; no long-press touch substitute.
- The drop-zone for file uploads relies on `dragover` events, which don't exist on phones. There's a file-picker fallback in `<vault-upload>` but no obvious mobile "tap to choose files" affordance in the empty state.

### 5. The "everything-is-a-tab" desktop pattern fails on narrow screens

`<sg-layout>` opens each file as a new tab in the preview stack. On a desktop this is great. On a phone:
- Tab strips don't scroll well in `<sg-layout>` (no swipe-between-tabs affordance, no overflow menu).
- Once two or three files are open the tab titles become ellipsised stubs.
- Closing a tab requires hitting a small ×; restoring a closed tab requires re-clicking the tree.

### 6. The entry (unlock) screen isn't optimised for mobile

`<vault-entry>` is a card with a passphrase / vault-key input, an "Open" CTA, and a collapsible "Create new vault" section. Cards default to a desktop width and the inputs don't grow to full width. The vault-key input is a long opaque string (`word-word-NNNN`) that users will paste from chat — the mobile flow should:
- Auto-focus the key input.
- Be `inputmode="text"` with `autocapitalize="none"`, `autocomplete="off"`, `autocorrect="off"` (currently `autocomplete="off"` is set on some inputs but not consistently).
- Have a paste-and-go button as well as Open, so a one-handed user doesn't have to scroll-tap.

### 7. Visual hierarchy collapses without breathing room

The Aurora dark palette (`#1A1A2E` / `#1E2A4A` / `#4ECDC4`) is well-defined in `design-tokens.css`. Token spacing (`--space-1` … `--space-16`) is consistent. But the **density** assumed by the design is desktop-only — at 320 px every surface is touching its neighbour. Reducing density needs to be coordinated, not done ad-hoc on individual components.

### 8. Read-only badge, version, branding compete for the same row

On a phone we need a clear priority order. Suggested:
1. Brand mark (always visible)
2. Vault name (truncates with ellipsis)
3. Primary action (Upload OR Lock — context-dependent)
4. Overflow menu (everything else)

Today there is no priority — it's all one row with `gap: var(--space-2)`.

## What's already in our favour

1. **Design tokens are clean and Shadow-DOM-friendly** — token values can be remapped per breakpoint without touching components.
2. **The `/app` route already establishes the responsive pattern** (`@media (max-width: 600px)` in `vault-app.css`). We can keep the same single-breakpoint conventions across both routes for consistency.
3. **Aurora palette has strong contrast** — text passes WCAG AA on the dark surface. No colour rework needed.
4. **Web Component architecture means each surface can move at its own pace** — the shell can ship a mobile chrome before the tree-view ships its mobile interactions, etc.
5. **`<vault-app>` already shows the team can ship a single-column mobile-friendly version of the product** — the design DNA exists, it just hasn't been applied to `/vault`.

## Proposed mobile design direction (not implemented — designer recommendation)

### Two breakpoints, one design system

- `≤ 600 px` — **Phone**: single column, top app-bar + bottom action-bar, full-screen views, drawer for nav.
- `601-1024 px` — **Tablet / narrow window**: two columns (collapsible files drawer + preview), retained tab strip.
- `≥ 1025 px` — **Desktop**: current three-pane IDE.

Single breakpoint is acceptable for an MVP (mirroring `/app`'s `600px` threshold) but the tablet middle-ground is what most laptop-with-side-panel users will hit, so designing for it explicitly is worth ~1 extra day.

### Phone layout (≤ 600 px)

```
┌─────────────────────────────────┐
│ ☰  SG/Vault   ⋮                 │  ← 44 px top bar: drawer toggle, brand, overflow
│ "demo-vault"                    │
├─────────────────────────────────┤
│                                 │
│   (Files view OR file preview   │
│    OR Settings — one at a time) │
│                                 │
│                                 │
│                                 │
├─────────────────────────────────┤
│ [Files] [Recent] [Upload]       │  ← 56 px bottom bar
└─────────────────────────────────┘
```

Drawer (slide-in from left, dismissible by tap-outside): Files / SGit / Settings / Debug / Lock / About.

Overflow menu (top-right ⋮): Read-only badge, raw view, version, share, secondary actions.

When a file is opened, the whole viewport becomes the preview. A back-chevron in the top bar returns to Files. **No tab strip on phones.**

### Tablet layout (601-1024 px)

- Optional left files-drawer (40% width when open, 0 when closed; toggled by a hamburger).
- Right side gets the preview tab strip — same as desktop but only one tab at a time visible, with a swipe gesture to move between them.
- Debug rail off by default; when toggled, it replaces the files drawer (mutually exclusive on tablets).

### Desktop layout (≥ 1025 px)

Today's three-pane IDE. No changes other than `flex-wrap: wrap` on the header to prevent overflow during window resize.

### Per-component mobile rules

- **Header buttons** → consolidate into one primary action (Upload) + ⋮ overflow.
- **Per-file action bar** → row of icons (Edit / Download / ⋮) with Rename / Delete / raw moved into ⋮. Save/Cancel only visible in edit mode.
- **Inline auth banner** → 2-row layout: message above, input + Set Key below. 44 px tap-height inputs.
- **Settings rows** → `flex-direction: column` so input is full width and Save sits below.
- **Tree view** → larger row height (44 px min), larger tap target on the chevron, long-press for context menu.
- **Entry screen** → card grows to 100% width minus padding; inputs are 44 px tall; "paste vault key" helper button.

### Visual changes

- No colour or palette changes proposed.
- One token addition: `--touch-target: 44px` to standardise tap-height for buttons / inputs on phone breakpoint.
- Spacing remap on phones: `--space-4` (16 px) → `--space-3` (12 px) in chrome paddings to claw back ~30 px of horizontal room.

## Accessibility notes

- Tap targets under 44 × 44 px today — the inline "raw" link, the × in the auth banner, the per-tab close affordance. These fail WCAG 2.5.5.
- The file action bar uses colour alone for the Delete hover state (red border). On mobile (no hover), we should add an icon and tooltip, not just rely on colour.
- Focus order on the entry screen is fine, but the autofocus jumps to whichever input has prior session storage — on mobile this is jarring with the soft keyboard. Recommend focusing the most-recently-used input only on desktop.
- The "Read-only" badge is a `<span>` with no role; a `role="status"` would announce it.
- No `prefers-reduced-motion` handling on the loading slide animation (`vs-loading-slide`). Trivial to add.

## Open questions for Dinis

1. **What's the floor we commit to?** — 320 px (iPhone SE), 360 px (Android typical), 390 px (modern iPhone)? Designing all the way down to 320 is a few extra hours; 360 px gets you 95%.
2. **Is the goal mobile-capable or mobile-first?** — i.e. should a phone user be able to do everything (upload, share, browse, settings, SGit, debug), or only the receive/browse/unlock flow that share-token recipients land in?
3. **Vault key entry on mobile** — should we add a QR code scan for the key, so chat senders can post a QR alongside the key text? (Out of scope for this audit but very natural fit for a mobile-first vault UI.)
4. **Tablet** — is a separate tablet layout worth the design and engineering cost, or do we go straight phone-vs-desktop?
5. **Visual identity** — should mobile feel the same as desktop (current Aurora chrome carried down), or a deliberately more "app-like" feel (rounded card stacks, hairline separators, sheet-style modals)?

---

## Recommended next steps

1. **This audit lands as-is.** Dev's companion review covers the engineering specifics.
2. **A mobile IA brief** — one page from Dinis (or me, in a follow-up) answering Q1, Q2, Q4, Q5 above, so we know the design contract before we cut CSS.
3. **A 2-3 screen mobile mock-up** (entry / files / file preview) — enough to align on the chrome and navigation pattern before implementation. Can be hand-sketches or Figma — doesn't need to be polished.
4. **A v0.1.5 IFD pass** — once the mock is approved, ship the phone breakpoint (single column, drawer nav, stacked forms) in one IFD release. Tablet pass can follow as v0.1.6.
