# Designer Review — Sub-Vaults & External Resources UX

**Version:** v0.27.62 | **Date:** 25 May 2026 | **Role:** Designer
**Scope:** UX design review of the Architect's proposed Vault Web UI for (a) sub-vaults / vaults-within-vaults, (b) external resources in controlled iframes
**Responds to:** Architect briefing pack (Wireframes A–D), human briefs v0.27.60–v0.27.62
**Grounded in:** `team/roles/librarian/reality/ui/index.md` (Vault Browser v0.2.3, `<sg-app-banner>`, `<app-hud>`, `<send-transparency>`)

---

## 1. Design Philosophy — The One Rule This Feature Lives or Dies By

The entire product promise is *"even we can't read it."* This feature deliberately introduces things that **can** read it (external apps with a granted folder) and things that **look like** they're inside the vault but are not (sandboxed embeds). That is a structural tension. The mental model we must protect:

> "Inside this vault there are three kinds of things: **my files** (only I can read), **other vaults** (separate locked boxes I have a key to), and **windows to the outside** (which can see nothing unless I open the blinds)."

Every wireframe must reinforce that three-bucket model and never let a user lose track of which bucket they are in. The single worst outcome for this product is a doctor who believes an embedded email app cannot see patient data when in fact she granted it `/shared` three weeks ago and forgot. **The transparency burden is on us, not the user.**

This is the same honesty discipline the existing UI already commits to: `<send-transparency>` says "Decryption key — never sent to server" not "we try not to store keys"; the vault-creation popover says "cannot be recovered… by design." We extend that voice, we do not soften it.

---

## 2. Verdict at a Glance

| Wireframe | Verdict | Headline issue |
|-----------|---------|----------------|
| A — tree with Linked vaults / Resources | **Revise** | Two new sections + files in one flat tree blur the three-bucket model. Iconography is ambiguous. No owner-only indicator. |
| B — traverse into sub-vault | **Revise** | Breadcrumb good; loading state under-specified; no error/expired-token state; read-only inheritance not shown. |
| C — external embed banner | **Strong, tighten** | Default-deny notice is the best part of the pack. Needs to survive scroll, name the grant explicitly, and not be dismissable into invisibility. |
| D — owner Add flow | **Revise — highest risk** | The access-grant dialog is where a user can hurt themselves. "Grant read" is one radio click away from "no access" with near-identical visual weight. Must be re-weighted. |

Nothing here is unshippable. But Wireframe D and the persistence of Wireframe C's banner are the two things that, if shipped as drawn, would let a user mislead themselves about who can see their data. Those are P0.

## 3. Wireframe A — The Vault Tree (Revise)

### 3.1 What works
- Putting linked vaults and resources *in the tree* (not a separate tab) keeps one navigation surface. Correct call — consistent with the v0.2.3 multi-pane explorer.
- Collapsible `▼` sections match the existing folder-tree affordance.

### 3.2 Problems

**P1 — Three buckets, but the tree only signals two.** Files, linked vaults, and resources are three trust categories, but "Linked vaults" and "Resources" read as just two more folders next to `patients/` and `reports/`. A doctor scanning the tree cannot tell at a glance that crossing into `🔗 Linked vaults` means *leaving this vault's trust boundary* while `📁 patients` does not.

**P2 — Icon overload.** 🗄, 👁, ▶, 🔗, 🧩, 🌐 — six glyphs, several doing double duty (🔗 is both the "Linked vaults" section header AND the "Clinic website" item). Users will not decode this. The 👁 here means "read-only" but the same eye means "read-only vault" in `<app-hud>` and "views remaining" in the share UI — we are overloading an already-loaded glyph.

**P3 — No owner-only signal.** Pointers are stored owner-only (double-encrypted). The reader of a shared read-only token may or may not see them depending on the access model. The tree gives no hint that these entries are a privileged layer. (See §7 on the read-only viewer — this is a real ambiguity, not cosmetic.)

**P4 — `[ + Add ▾ ]` floats with no scope.** It's not clear whether Add adds to the current folder, to Linked vaults, or to Resources.

### 3.3 Proposed redraw

Group the two trust-crossing categories under one visually distinct **"Beyond this vault"** zone, separated from in-vault files by a labelled divider — the same "section-label + border" device the page-layout nav uses (`__section-label`, uppercase micro-caps, `border-bottom`). Each item carries a single, consistent **trust chip** on the right (not a bare emoji): `vault · read-only`, `vault · writable`, `embed · no access`, `embed · reads /shared`.

```
┌─ SG/Vault ─────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ───────────────────────┐ ┌── preview ─────────────────┐ │
│ │ 📁 patients                    │ │  # Clinic Vault            │ │
│ │ 📁 reports                     │ │  ...                       │ │
│ │ 📄 readme.md                   │ │                            │ │
│ │                                │ │                            │ │
│ │ ── BEYOND THIS VAULT ──────🔒  │ │                            │ │
│ │ ▼ Linked vaults                │ │                            │ │
│ │    🗄 Patient: Alice  vault·RO │ │                            │ │
│ │    🗄 Patient: Bob    vault·RO │ │                            │ │
│ │ ▼ Embedded resources           │ │                            │ │
│ │    ▶ Intro video    embed·none │ │                            │ │
│ │    🔗 Clinic website embed·none│ │                            │ │
│ │    🧩 Email (app)   embed·READS│ │  ← amber chip when granted │ │
│ └────────────────────────────────┘ └────────────────────────────┘ │
│  Linked vaults ▸ [ + Add ▾ ]   ·   visible only to you 🔒          │
└──────────────────────────────────────────────────────────────────┘
```

Key moves:
- **"BEYOND THIS VAULT"** divider + a 🔒 marker = "this whole zone is the owner-only pointer layer." One lock, one place, not per-row noise.
- **Trust chips carry the message, icons just categorise.** `vault·RO`, `vault·RW`, `embed·none`, `embed·READS`. The chip that says an embed *reads* the vault renders in the **amber warning** treatment (`#d97706`, the existing `callout--warning` colour) — it should be the only warm-coloured thing on the screen. Everything safe is teal/grey; the one risky thing is amber. The eye scans straight to it.
- **Add is scoped**: the breadcrumb-style prefix (`Linked vaults ▸`) shows what you're adding to, and the standing `visible only to you 🔒` reminds the owner the whole layer is private.

## 4. Wireframe B — Traversing Into a Sub-Vault (Revise)

### 4.1 What works
- Breadcrumb `apple-river-1234 ▸ Patient: Alice` is the right model and matches the `<app-hud>` vault-badge + title pattern.
- `‹ Back to parent vault` is explicit. Good — never rely on browser back for a trust-boundary crossing.

### 4.2 Problems

**P1 — The crossing is invisible after it completes.** Once Alice's vault is open, the only thing telling you you've left the parent is a breadcrumb segment. Crossing a trust boundary deserves a persistent frame, not just a breadcrumb. Reuse the existing App-Mode device: when inside a child vault, the chrome should read **"You are inside a linked vault"** the same way `<sg-app-banner>` makes App Mode unmistakable.

**P2 — Loading state is a guess.** `[ Opening linked vault… cloning on access ]` — "cloning on access" is engineer-speak. A doctor doesn't clone. And there's no failure path. Reuse the App-Mode loading-overlay pattern (the one with the 8s timeout and explicit error in `sg-app-banner.js`): a spinner with honest copy, and a real error state.

**P3 — Read-only inheritance not shown.** If the parent holds only a read-only token for Alice's vault (the recommended default in Wireframe D), then *everything* inside Alice is read-only — but the child tree in B shows files with no read-only framing. The viewer will try to edit `notes.md` and hit a wall.

**P4 — No "where did this key come from" affordance.** Trust hygiene: a user should be able to ask "why do I have access to Alice's vault?" and get "because the parent vault apple-river-1234 holds a read-only token for it."

### 4.3 Proposed redraw

```
clicking "Patient: Alice" →
   ┌──────────────────────────────────────────────┐
   │  Opening Patient: Alice…                       │
   │  ◐ Connecting to the linked vault              │
   │  (this is a separate vault — your parent vault │
   │   holds a read-only key to it)                 │
   └──────────────────────────────────────────────┘
   on failure ↓
   ┌──────────────────────────────────────────────┐
   │  ⚠ Can't open Patient: Alice                   │
   │  The linked vault didn't respond, or its key   │
   │  is no longer valid (it may have been revoked  │
   │  or expired).                                  │
   │  [ Try again ]   [ ‹ Back to parent ]          │
   │  [ Fix link… ]  ← owner only                   │
   └──────────────────────────────────────────────┘

success ↓
┌─ SG/Vault ─ apple-river-1234 ▸ Patient: Alice ─────────────────────┐
│ ┌────────────────────────────────────────────────────────────────┐ │
│ │ 🔗 Inside a linked vault · read-only · key held by your parent  │ │  ← persistent
│ │    vault                                       [ ‹ Back ]  [Why?]│ │     boundary bar
│ └────────────────────────────────────────────────────────────────┘ │
│ ┌── tree ──────────┐ ┌── preview ─────────────────────────────────┐ │
│ │ 📄 knee.json      │ │  knee-score.json …                         │ │
│ │ 📄 notes.md  👁RO  │ │  (editing disabled — read-only link)       │ │
│ └──────────────────┘ └────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

- **Persistent boundary bar** = the App-Mode-style frame that does not go away while you're inside the child. It states three facts: you're in a linked vault, your access level, where the key comes from.
- **`[Why?]`** opens the provenance explanation (parent vault X holds this key).
- **Read-only is shown at the file level**, not just the header, so the disabled Edit/Save buttons make sense before the user clicks them.

## 5. Wireframe C — External Embed Banner (Strong — Tighten)

This is the best-designed part of the pack and the one closest to shippable. The default-deny notice is exactly the right instinct and exactly the right tone.

### 5.1 What works
- `🔒 External embed · youtube.com · cannot read this vault` — perfect honest framing, same register as `<send-transparency>`. Keep this sentence almost verbatim.
- The notice sits *above* the iframe, owning the top of the frame.

### 5.2 Problems

**P1 — `✕` is dangerous.** A dismiss button on a security banner trains users to swat it away, and then the most important standing fact on the screen is gone. **Remove the ✕.** The banner is not a notification; it is a permanent property label for the embed. It should persist as long as the embed is open, the same way the App-Mode chrome persists.

**P2 — Banner must survive scroll and full-screen.** YouTube embeds go full-screen; long web pages scroll. If the banner scrolls away, the "cannot read this vault" guarantee scrolls away with it. Make it sticky to the embed frame's top edge. On full-screen takeover (which we cannot overlay), show a brief toast on entry via `<app-hud>`'s message channel: "Full-screen — this embed still cannot read your vault."

**P3 — The granted case is undrawn.** Wireframe C only shows the safe (no-access) case. The dangerous case — an embed that *was* granted access — needs its own, visually louder banner. This is the single most important missing artwork in the pack.

### 5.3 Proposed redraw — both states

No-access (the default, the calm case):
```
┌─ SG/Vault ─ apple-river-1234 ▸ Embedded resources ▸ Intro video ───┐
│ ┌──────────────────────────────────────────────────────────────────┐│
│ │ 🔒 Embedded from youtube.com · cannot read this vault      [Why?] ││  ← teal/grey, sticky, no ✕
│ ├──────────────────────────────────────────────────────────────────┤│
│ │                  ▶ (sandboxed YouTube iframe)                      ││
│ └──────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

Granted (the loud case — amber, never dismissable):
```
┌─ SG/Vault ─ apple-river-1234 ▸ Embedded resources ▸ Email (app) ────┐
│ ┌──────────────────────────────────────────────────────────────────┐│
│ │ ⚠ Embedded from mail.example.com · CAN READ folder /shared        ││  ← amber #d97706, sticky
│ │   You granted this access.            [ What it sees ] [ Revoke ] ││
│ ├──────────────────────────────────────────────────────────────────┤│
│ │                  🧩 (external email app, granted /shared)          ││
│ └──────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

- The granted banner is **amber**, names the **exact folder**, attributes the decision back to the user ("You granted this access"), and offers **`[ Revoke ]` inline** — revocation must be reachable from the place the risk is visible, not buried in an edit dialog.
- **`[ What it sees ]`** opens a precise read-out: the folder, file count, and that the embed sees *plaintext* of those files in the user's browser. No hedging.

## 6. Wireframe D — Owner Add Flow (Revise — Highest Risk)

This is where a user can quietly hurt themselves. Treat it as a security surface, not a form.

### 6.1 "Add linked vault" dialog — minor revisions
Mostly good. The owner-only reassurance (`🔒 Stored owner-only (double-encrypted)`) is well placed and on-voice.

- **Default to "Read-only token (recommended)"** — already done, keep it. Good.
- **Add a one-line consequence under the Full-key option**: "Full key lets anyone you later share this parent vault with also write to Patient: Carol." Users underestimate transitive sharing.
- **Validate the token shape inline** (same as the vault-picker's "That doesn't look like a valid vault key" pattern) — distinguish a `ro-` read-only token from a full key, and warn if the user pastes a full key into the "Read-only token" field.

### 6.2 "Add external app (access grant)" dialog — P0 RED FLAG

As drawn, two radio options sit with **equal visual weight**:

```
Access (•) No access to this vault (default)
       ( ) Grant read to:  [ /shared ▾ ]
```

The difference between these two options is the difference between *"this product keeps its promise"* and *"a third-party website can read patient files in this browser."* They must not look like a routine radio pick. A distracted owner clicks the second radio to "see what folders are available," picks `/shared` from the dropdown to look, and ships it.

**Required changes:**

1. **Make granting a deliberate, multi-step act.** Default dialog shows only the safe path. Granting access is revealed by an explicit, clearly secondary control — not a co-equal radio.
2. **Confirmation friction proportional to risk.** When the owner does choose to grant, require an explicit confirm that *restates the consequence in plain language and names the folder*.
3. **Show what's in the folder before granting.** "You're about to let mail.example.com read 14 files in /shared, including their contents." Counts make it concrete.
4. **The grant is visible forever after** (Wireframe A amber chip + Wireframe C amber banner). Granting is not fire-and-forget.

### 6.3 Proposed redraw

```
┌ Add an external app ───────────────────────────────────┐
│ Label  [ Email                                        ] │
│ URL    [ https://mail.example.com/embed               ] │
│                                                         │
│ ┌─────────────────────────────────────────────────────┐│
│ │ 🔒 By default this app runs in a sealed window and    ││
│ │    cannot read anything in your vault.                ││
│ └─────────────────────────────────────────────────────┘│
│                                                         │
│ ▸ Advanced: give this app access to a folder            │  ← collapsed by default
│                                  [ Cancel ] [ Add app ] │
└─────────────────────────────────────────────────────────┘

expanding "Advanced" reveals ↓
│ ▾ Advanced: give this app access to a folder            │
│   ⚠ This is the one setting that lets an outside website │
│     read your files. Only use it if you trust this app   │
│     with the data in the folder you pick.                │
│   Folder to share:  [ /shared ▾ ]  (14 files)            │
│   [ ⚠ Grant mail.example.com read access to /shared ]    │  ← amber, full-width, the only
│                                                          │     amber control in the dialog
└──────────────────────────────────────────────────────────┘

clicking the amber grant button → confirm step ↓
┌ Confirm access grant ──────────────────────────────────┐
│ ⚠ mail.example.com will be able to read the contents of │
│   14 files in /shared, in this browser.                 │
│   This site is not part of SGraph and we cannot see what│
│   it does with the data.                                │
│                            [ Cancel ] [ Yes, grant it ] │
└─────────────────────────────────────────────────────────┘
```

- Safe path is the only thing visible at rest. Granting is behind an "Advanced" disclosure and a confirm.
- Every step names the **site**, the **folder**, and the **file count**.
- The single amber control is the only warm element — same discipline as the tree and the embed banner. Amber = "this is the thing that can leak data," consistently, everywhere.

## 7. The Read-Only Viewer's Experience (Missing from the Pack — must be designed)

Pointers are stored **owner-only**. So a person you share a **read-only token** with: do they see the Linked vaults / Resources zone at all?

There are two defensible models and the pack must pick one explicitly, because each has a transparency consequence:

- **Model A — pointers hidden from read-only viewers.** Cleaner promise (the owner-only layer is truly owner-only). But then a doctor sharing the *parent* vault read-only with a colleague gets a surprise: the colleague sees none of the patient vaults. The parent vault looks empty-ish. We must show the colleague an honest empty/locked state, not nothing: *"Some linked items in this vault are visible only to its owner."*
- **Model B — pointers visible, child access still gated by the child's own token.** The viewer sees that linked vaults exist but can only open the ones whose keys are reachable. More discoverable, but it leaks the *existence and labels* ("Patient: Alice", "Patient: Bob") to anyone with the read-only parent token — which for a medical use case is itself sensitive metadata.

**Designer recommendation: Model A by default**, with the honest locked-state message above, because for the doctor use case the *list of patient labels* is exactly the kind of metadata we should not leak. Make this a documented, deliberate choice — not an accident of implementation. Whichever is chosen, the read-only viewer must never be left guessing whether they're seeing everything.

## 8. Cross-Cutting Gaps (Empty / Error / Edge States)

| State | Status in pack | Required design |
|-------|---------------|-----------------|
| **Empty "Beyond this vault" zone** | Missing | If no linked vaults/resources, owner sees a quiet prompt: "Link another vault or embed a resource — only you will see these." Reader sees nothing (Model A). |
| **Child vault unreachable** | Missing | Covered in §4.3 — explicit error card with Try again / Back / (owner) Fix link. |
| **Read-only token expired/revoked** | Missing | Distinct copy from "unreachable" — name the likely cause. Owner gets `[ Update key… ]`. |
| **Broken external URL / iframe refuses to load** | Missing | The embed area shows: "This page can't be displayed here — the site may block embedding." Crucially, the 🔒 "cannot read this vault" banner still shows: a broken embed is still a sealed embed. |
| **Granted folder later deleted/renamed** | Missing | The grant must not silently point at nothing or, worse, re-bind to a new folder. Show "granted folder /shared no longer exists — access is effectively none" and prompt the owner. |
| **Nesting depth** | Missing | A sub-vault that itself has sub-vaults. Breadcrumb must truncate gracefully (`apple-river ▸ … ▸ Patient: Alice ▸ Knee MRI`) and the "Back to parent" must pop one level, with the boundary bar always reflecting current depth. |

## 9. Mobile / Narrow Layout

The v0.2.3 explorer is multi-pane (tree + preview). On narrow screens this collapses. For this feature:

- The **boundary bar (§4.3) and embed banner (§5.3) must never be sacrificed for space** — they are the transparency guarantee. They stay full-width and sticky even when the tree/preview stack.
- Trust chips that don't fit inline (`vault·RO`, `embed·READS`) must wrap to a second line, not truncate — truncating `embed·READS /shared` to `embed·READS…` would hide the most important word.
- The Add flow's "Advanced / Grant" disclosure works well on mobile as a full-screen step rather than an inline expander — but the confirm step (§6.3) is mandatory on every form factor.

## 10. Consistency Check Against Existing Vault UI

| Existing pattern | This feature should reuse |
|------------------|---------------------------|
| Teal accent `#4ECDC4`, Aurora dark theme | All safe/neutral chrome |
| `callout--warning` amber `#d97706` | The *one* risk colour — granted embeds, grant controls, error states. Used nowhere else. |
| `<send-transparency>` three-section honest read-out ("never sent to server") | The `[Why?]` / `[ What it sees ]` panels — same register, same no-hedge voice |
| `<app-hud>` read-only badge (`👁 Read-only`, blue pill) | Sub-vault read-only state — reuse the exact badge, do not invent a new one |
| `<sg-app-banner>` App-Mode persistent chrome + 8s-timeout loading overlay | The §4.3 boundary bar and the §4.3 child-vault loading/error states |
| `<app-hud>` toast message channel (`sg.ui.message`) | Full-screen embed reminder, copy-link confirmations |
| Vault-key truncation + "doesn't look like a valid key" inline error | Token validation in the Add-linked-vault dialog |
| Vault-creation popover honest copy ("cannot be recovered… by design") | Grant confirmation copy ("we cannot see what it does with the data") |

**One new token is justified:** a consistent **trust chip** style (`vault·RO`, `embed·none`, `embed·READS`). Define it once; it appears in the tree, the boundary bar, and the embed banners.

## 12. Red Flags (read these even if you read nothing else)

1. **The access-grant radio (Wireframe D) gives "grant a third party read access to your files" the same visual weight as "do nothing."** As drawn, this will leak data through ordinary user inattention. This is the highest-severity finding in the review.
2. **The embed banner's `✕` lets users dismiss the only on-screen statement of the zero-knowledge guarantee.** Remove it.
3. **The granted-embed state is undrawn entirely.** The pack shows the safe case and implies the dangerous one exists, but never draws what a *live grant* looks like — which is precisely the state that matters most.
4. **The read-only viewer's view of the pointer layer is undefined**, risking either a silently-empty vault (confusing) or a leak of sensitive labels like patient names (privacy breach). Pick a model on purpose.
