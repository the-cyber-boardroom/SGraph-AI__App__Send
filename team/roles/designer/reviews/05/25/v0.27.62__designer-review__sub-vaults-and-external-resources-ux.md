# Designer Review — Sub-Vaults & External Resources UX

**Version:** v0.27.62 | **Date:** 25 May 2026 | **Role:** Designer
**Scope:** UX design for two new vault capabilities — (a) **sub-vaults** (a vault that points at other vaults, presented as seamless inline folders), and (b) **external resources** (video / link / external app embedded in a controlled iframe behind a default-deny boundary).
**Grounded in:** `team/roles/librarian/reality/ui/index.md` — code-verified Vault Browser **v0.2.3**, `<sg-app-banner>` (App Mode chrome + 8s loading/timeout overlay), `<app-hud>` (read-only badge, toast channel), `<send-transparency>` (honest read-out voice).

> **Reality note.** Sub-vaults, external-resource embeds, link cards, and the public-info preview are all **PROPOSED — they do not exist yet**. What exists today is the Vault Browser v0.2.3 multi-pane explorer, the App-Mode banner/loading patterns, and the SG/App host (`<app-shell>`, `<app-hud>`). This review designs the new feature on top of those existing primitives so engineers reuse, not reinvent.

---

## 1. Design Philosophy — Three Kinds of Things, Two Deliberately Opposite Presentations

The product promise is *"even we can't read it."* This feature introduces things that **can** read it (an external app the owner explicitly grants a folder to) and things that **look adjacent to** the vault but cannot see inside it (sandboxed embeds). That is a structural tension, and the only way to hold it honestly is a clear mental model the user never loses:

> "There are three kinds of things here: **my files** (only I can read them), **other vaults I have a key to** (separate locked boxes that happen to open right where I'm standing), and **windows to the outside** (which see nothing unless I open the blinds)."

This is the **three-bucket honesty discipline**, and it drives every decision below. But note the critical refinement that separates this design from a naive one:

- **The first two buckets are presented the *same* way on purpose.** Sub-vaults are *not* corralled into a separate zone, tab, or divider. They appear **inline, as folders**, because the project lead's guiding principle is that *when we get this right the user is barely aware they crossed into another vault — they just expanded a folder.* Transparency here is achieved through **invisibility**: the boundary is real but almost frictionless. The user is "a little bit aware" (a subtle glyph, a tiny chip) and never walled off.
- **The third bucket is presented as the deliberate opposite.** An external embed gets an **unmissable, sticky, non-dismissable** guarantee banner. Transparency here is achieved through **visibility**: the boundary is loud because the consequences of misunderstanding it are severe.

So the discipline is not "make every boundary loud." It is **calibrate the loudness to the trust direction**: crossing *into another vault you hold a key to* is safe and should feel seamless; *letting an outside site read your files* is dangerous and should feel deliberate. The single worst outcome this design must prevent is a doctor who believes an embedded app cannot see patient data when in fact she granted it `/shared` three weeks ago and forgot. **The transparency burden is on us, not the user.**

We extend the existing honest voice; we never soften it. `<send-transparency>` says "Decryption key — never sent to server," not "we try not to." The vault-creation popover says "cannot be recovered… by design." Same register throughout.

## 2. Sub-Vaults — Seamless Inline Folders

### 2.1 The core rule: a sub-vault is a folder, with two whispers

A sub-vault **expands inline like any folder**. It nests and proliferates exactly like folders — `subvaults/demos/acme-demo`, `subvaults/customers/acme` — and each sub-vault can itself contain sub-vaults (recursive, no special depth handling beyond graceful breadcrumb truncation). On expand, it loads on demand and **splices its contents inline** beneath its own node, indented one level, exactly where a folder's children would appear.

The **only** two differences from a plain folder:

1. A **subtle vault glyph** (`◈`) in place of the folder glyph — enough to signal "this is another vault," never a wall.
2. A **tiny access chip** immediately after the label: `·ro` (read-only) or `·rw` (writable). In **v1 every sub-vault opens READ-ONLY regardless of the key held**, so v1 chips read `·ro` in practice; `·rw` is reserved and defined now so the chip is stable when child-editing ships later.

That is the entire visible delta. **No separate region. No zone. No divider. No "linked vaults" header.** A sub-vault sits among files and folders, sorted as a normal tree node.

### 2.2 How a sub-vault is declared

A sub-vault is declared by a tiny **pointer file** named `<anything>.link.json`. The UI recognises a tree node by the **`.link.json` suffix**; the prefix is a user-chosen label (e.g. `acme-demo.link.json`, `health-score-2024.link.json`). The pointer file **carries no keys** — it names the target vault and a label, nothing decryptable-into-the-vault.

Consequences the UI must honour:
- The **same target vault can appear in several places** in the tree under different link-file names. That is expected and fine — they are just multiple pointers.
- **Moving a sub-vault = moving the little `.link.json` file.** There is no separate "manage sub-vaults" surface; tree operations are the management surface.
- When the device **holds a usable key** for the target, the node behaves as a folder (expand → splice contents).
- When the device holds **no key yet** (a *locked* sub-vault), the node shows a small **lock** and clicking opens a **link card** (§3) instead of expanding.

### 2.3 Wireframe 1 — The inline tree (recursive + locked example)

`◈` = sub-vault glyph · `·ro`/`·rw` = access chip · `🔒` on a node = locked (no key yet on this device).

```
┌─ SG/Vault ──────────────────────────  apple-river-1234 · ✎ writable ─┐
│ ┌── tree ─────────────────────────────┐ ┌── preview ─────────────────┐ │
│ │ 📁 patients                          │ │  # Clinic Vault            │ │
│ │ 📄 readme.md                         │ │  ...                       │ │
│ │ 📄 health.json                       │ │                            │ │
│ │ 📁 subvaults                         │ │                            │ │
│ │   📁 customers                       │ │                            │ │
│ │     ▾ ◈ Acme         ·ro             │ │   ← expanded inline,       │ │
│ │         📄 health.json               │ │     just like a folder     │ │
│ │         📄 notes.md                  │ │                            │ │
│ │         ▸ ◈ Acme — EU site  ·ro      │ │   ← a sub-vault inside a   │ │
│ │     ▸ ◈ Globex       ·ro             │ │     sub-vault (recursive)  │ │
│ │   📁 demos                           │ │                            │ │
│ │     ▸ ◈ Acme demo    ·ro             │ │                            │ │
│ │     🔒 ◈ Partner demo               │ │   ← locked: click opens    │ │
│ │                                      │ │     the link card (§3)     │ │
│ └──────────────────────────────────────┘ └────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

Reading the example:
- `◈ Acme ·ro` is **expanded** (`▾`) and its files (`health.json`, `notes.md`) and its own child sub-vault (`◈ Acme — EU site ·ro`) sit inline beneath it at the next indent. A user scanning this sees a folder that opened. The only tell that Acme is a separate vault is the `◈` glyph and the `·ro` chip.
- `◈ Acme — EU site ·ro` demonstrates **recursion** — a sub-vault nested inside a sub-vault, collapsed here (`▸`).
- `🔒 ◈ Partner demo` is **locked** (no key on this device). It does not expand on click; it opens the link card.

**Design notes / decisions:**
- **Sort sub-vaults among files and folders, not after them.** Pulling them to the bottom would re-create the "separate zone" we are explicitly avoiding. They are folders; sort them as folders.
- **The access chip is `·ro` / `·rw` in lowercase, hugging the label.** It must read as a quiet annotation, not a button. It is the one new token (§8) and the only thing besides the glyph that distinguishes a sub-vault.
- **Do not stack a read-only pill onto sub-vault nodes in the tree.** The `·ro` chip is sufficient at the tree level. The blue `👁 Read-only` pill is reserved for the file-action context inside an opened read-only sub-vault (§4), where it explains why Edit/Save are absent.
- **No per-node "this is another vault" tooltip warning.** A subtle hover title (`Acme — a linked vault, read-only`) is enough provenance at this level. The loud provenance lives in the context bar once you open it (§4).

### 2.4 Locked-node interaction

Clicking `🔒 ◈ Partner demo` does **not** expand and does **not** error. It opens the **link card** (§3), which is the miniature "open a vault" surface. This keeps the rule clean: *a sub-vault you can open behaves like a folder; a sub-vault you can't open yet asks you to open it.* The lock is the only extra glyph, and it is self-explanatory.

## 3. The Link Card

The link card is what you get when you click a `.link.json` node you don't yet hold a key for (or its lock). It is a **miniature "open a vault" surface** — deliberately echoing the existing vault-card / vault-picker patterns so it feels familiar, not like a new modal genre.

A crucial honesty principle: **show the vault's public info BEFORE asking for a key.** A user should be able to see *what they're about to open* — label, file count, last-updated — without first surrendering or even possessing a key. (Public-info-before-key is a capability arriving in a separate brief; design for it now, and degrade gracefully when the info is not yet available — show the label and a quiet "details unavailable until opened" line rather than a blank.)

### 3.1 Wireframe 2 — The link card

```
┌ Open linked vault ───────────────────────────────────────┐
│  ◈ Partner demo                                            │
│                                                            │
│  ┌── about this vault ──────────────────────────────────┐ │
│  │  18 files · last updated 3 days ago                  │ │   ← public info, shown
│  │  (this preview comes from the vault itself, before   │ │     BEFORE asking for a key
│  │   any key is entered)                                │ │
│  └──────────────────────────────────────────────────────┘ │
│                                                            │
│  Description                                               │
│  [ Partner-shared demo build — health-score walkthrough  ] │   ← editable
│                                                            │
│  Key for this vault                                        │
│  [ paste vault key or read-only token …               ]   │
│                                                            │
│  When you enter the key, save it:                          │
│   (•) In this vault     — travels with this vault for      │
│                            anyone you share it with        │
│   ( ) On this device    — stays in this browser only       │
│   ( ) Don't save        — ask me each time                 │
│                                                            │
│  Version to open                                           │
│  [ Latest ▾ ]                                              │   ← commit "pin", default Latest
│                                                            │
│  [ Open here (read-only) ]        [ Open in new window ↗ ] │
│                              [ Cancel ]                     │
└────────────────────────────────────────────────────────────┘
```

**Design decisions:**
- **Public info sits at the top, above the key field.** This is the whole point: you decide whether to open *before* you commit a key. When the public-info capability is not yet wired, show the label and a muted "details unavailable until opened" line — never a blank box that implies "empty vault."
- **Three save choices, plain-language consequences inline.** *Save in this vault* must carry the honest warning that the key then **travels with the vault** to anyone the parent is shared with — this is exactly the transitive-trust trap, and the radio label must say so. *Save on this device* and *Don't save (ask each time)* are the more conservative choices. Default to *In this vault* only because that is the collaboration-friendly intent of sub-vaults, but the consequence text must be visible at the point of choice, not hidden in a tooltip.
- **Commit pin defaults to `Latest`.** Pinning to a specific commit is the power-user path; most users never touch it. Keep it a single dropdown, not a date-picker wall.
- **Editable description** persists on the pointer (the `.link.json`), so the owner can annotate why this link exists.
- **Two actions, clearly distinct:**
  - **`Open here (read-only)`** — splices the vault inline in place (the §4 read-only experience). v1: always read-only.
  - **`Open in new window ↗`** — opens the full vault workflow in a new window. The parent↔sub-vault relationship is **tracked**, so the new window's "back" returns to the parent vault, not to a blank landing. This mirrors the existing vault card's "↗ Open in new window" affordance (reality doc, v0.2.3), so reuse it.
- **Validate the key shape inline** using the existing vault-picker pattern ("That doesn't look like a valid vault key"). Distinguish a read-only token from a full key, and since v1 opens read-only regardless, do **not** imply that pasting a full key unlocks editing — say "Opens read-only in this version" near the action so expectations are honest.

## 4. Inside an Opened Sub-Vault — Read-Only, Seamless, but "A Little Bit Aware"

When a sub-vault opens **here** (inline, the common path), the user is now browsing another vault's contents. The design tension: the project lead wants them *barely aware* they crossed a boundary — but "barely aware" is not "unaware." We must not let a user believe they're still in the parent vault, and we must explain why Edit/Upload/New File are missing.

The answer is a **slim context bar**, reusing the existing App-Mode chrome (`<sg-app-banner>` / `<app-hud>` register), plus the existing **8s loading/timeout pattern** for the on-demand load. It is one thin line — not a wall, not a takeover.

### 4.1 Loading (reuse the App-Mode 8s overlay)

```
   ┌──────────────────────────────────────────────┐
   │  Opening Acme…                                 │
   │  ◐ Loading linked vault                        │
   │  (a separate vault — opens read-only)          │   ← honest, no "cloning" jargon
   └──────────────────────────────────────────────┘
```

Reuse `sg-app-banner.js`'s loading overlay directly: spinner + status copy, and the **8s timeout** that surfaces an explicit error (§7) rather than hanging. Copy is plain ("Loading linked vault"), never engineer-speak like "cloning on access."

### 4.2 Opened, read-only (the slim context bar)

```
┌─ SG/Vault ─ apple-river-1234 ▸ Acme ───────────────────────────────────┐
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │ ◈ Acme · read-only linked vault                    [ ‹ Back ] [Why?]│ │  ← slim context bar
│ └────────────────────────────────────────────────────────────────────┘ │     (App-Mode chrome)
│ ┌── tree ──────────────────┐ ┌── preview ─────────────────────────────┐ │
│ │ 📄 health.json            │ │  health.json                           │ │
│ │ 📄 notes.md   👁 Read-only │ │  { "health-score": 0.92, ... }         │ │
│ │ ▸ ◈ Acme — EU site  ·ro   │ │  (editing disabled — read-only link)   │ │
│ └──────────────────────────┘ └────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

**Design decisions:**
- **The context bar is slim and reuses App-Mode chrome** — the same persistent device that already makes App Mode unmistakable in v0.2.3. It states two facts in one line: *which vault you're in* (`◈ Acme`) and *your access* (`read-only linked vault`). It does **not** block content or stack multiple rows. This is the "a little bit aware" surface — present, quiet, persistent.
- **`[ ‹ Back ]`** returns to the parent (the spot in the tree you expanded from). Never rely on browser-back for a vault crossing; this is explicit. For recursion, Back pops **one** level, and the breadcrumb (`apple-river-1234 ▸ … ▸ Acme ▸ Acme — EU site`) truncates the middle gracefully.
- **`[Why?]`** opens provenance in the `<send-transparency>` register: "You can read this vault because the parent vault (apple-river-1234) holds a read-only key to it." This answers the trust-hygiene question "why do I have access?"
- **No edit/upload/new-file controls anywhere inside a sub-vault in v1.** Per the spec, v1 opens every sub-vault read-only regardless of the held key. The **blue `👁 Read-only` pill** (the existing `<app-hud>` token) appears at the **file-action level** so the absence of Save/Edit is explained *before* the user reaches for it — not invented anew, reused exactly.
- **Recursion is seamless:** the child's own sub-vaults (`◈ Acme — EU site ·ro`) appear in its tree as inline folders, and opening one updates the context bar and breadcrumb to the deeper level. The bar always reflects current depth.

## 5. External Resources — Strong Default-Deny Boundary

This is the deliberate opposite of sub-vaults. A `video` / `link` / `app` resource (also declared by a small link file) embeds an external URL in a **controlled iframe that by default cannot read the vault**. Transparency here means an **unmissable, sticky, non-dismissable guarantee banner** owning the top of the embed frame.

There are exactly **two banner states**:

- **Neutral** (the default, the calm case): the embed cannot read the vault.
- **Amber** (only when the owner has explicitly opted in): the embed *can* read a named folder. **Amber is reserved strictly for "can leak data" states and is used nowhere else in this entire feature** — not for errors, not for read-only, not for locked. If something is amber, it means *an outside party can read your files.*

### 5.1 Wireframe 4 — Neutral and amber banners

Neutral (sealed — teal/grey, sticky, **no dismiss control**):
```
┌─ SG/Vault ─ apple-river-1234 ▸ Intro video ────────────────────────┐
│ ┌──────────────────────────────────────────────────────────────────┐│
│ │ 🔒 External window · youtube.com · CANNOT read this vault   [Why?] ││  ← sticky, no ✕
│ ├──────────────────────────────────────────────────────────────────┤│
│ │                  ▶ (sandboxed YouTube iframe)                      ││
│ └──────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

Amber (granted — `#d97706`, sticky, non-dismissable, names the folder + count):
```
┌─ SG/Vault ─ apple-river-1234 ▸ Email (app) ────────────────────────┐
│ ┌──────────────────────────────────────────────────────────────────┐│
│ │ 🟠 External window · mail.example.com · CAN READ /shared (12 files)││  ← amber, sticky
│ │    Granted by you.                       [ What it sees ] [ Revoke ]││
│ ├──────────────────────────────────────────────────────────────────┤│
│ │                  🧩 (external app, granted /shared)                ││
│ └──────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

**Design decisions:**
- **No `✕` / dismiss on either banner.** The banner is a permanent property label for the embed, not a notification. Dismissing it would remove the only on-screen statement of the guarantee. It persists as long as the embed is open — the same way App-Mode chrome persists.
- **Sticky through scroll and full-screen.** Long pages scroll; YouTube goes full-screen. The banner must stay pinned to the embed frame's top edge. On a full-screen takeover we cannot overlay, so emit a one-time toast via the existing `<app-hud>` message channel: "Full-screen — this window still cannot read your vault."
- **Neutral copy verbatim from the spec:** `🔒 External window · youtube.com · CANNOT read this vault [Why?]`. It is the right honest register; keep it almost word-for-word.
- **Amber copy attributes the decision to the user** ("Granted by you"), names the **exact folder and file count** (`/shared (12 files)`), and puts **`[ Revoke ]` inline** — revocation must live where the risk is visible, not buried in an edit dialog. **`[ What it sees ]`** opens a precise read-out: the folder, the file count, and the fact that the app sees the *plaintext* of those files in the user's browser. No hedging.

## 6. Owner Add / Grant Flow — Highest-Risk Surface

Adding a sub-vault is low-risk (it's a read-only pointer). **Granting an external app access to vault data is the one place a user can quietly hurt themselves**, so it gets the strongest friction. Per the spec, a grant is an **explicit, opt-in owner action behind an Advanced disclosure plus a risk-proportional confirm** that names the site, the folder, and the file count. It must **never** be a one-click co-equal toggle.

This matters because in most app workflows the user *never sees the raw vault* — a doctor sees a rendered app and steps into a vault *through the app*. So the grant must be deliberate (the owner sets it up knowingly) and revocable (visible at the point of risk, forever — §5.1 amber banner).

### 6.1 Wireframe 5 — Add external app (Advanced + confirm)

At rest — only the safe path is visible; granting is collapsed behind Advanced:
```
┌ Add an external window ─────────────────────────────────┐
│ Label  [ Email                                        ] │
│ URL    [ https://mail.example.com/embed               ] │
│ Type   ( ) video   ( ) link   (•) app                   │
│                                                         │
│ ┌─────────────────────────────────────────────────────┐│
│ │ 🔒 By default this window runs sealed and cannot      ││
│ │    read anything in your vault.                       ││
│ └─────────────────────────────────────────────────────┘│
│                                                         │
│ ▸ Advanced: let this window read a folder               │   ← collapsed by default
│                                  [ Cancel ] [ Add ]     │
└─────────────────────────────────────────────────────────┘
```

Advanced expanded — the grant control is the **only amber element** and is full-width, not a co-equal radio:
```
│ ▾ Advanced: let this window read a folder                │
│   🟠 This is the one setting that lets an outside site   │
│      read your files. Only use it if you trust this      │
│      window with the data in the folder you pick.        │
│   Folder to share:  [ /shared ▾ ]   (12 files)           │
│   [ 🟠 Grant mail.example.com read access to /shared ]   │   ← amber, full-width
└──────────────────────────────────────────────────────────┘
```

Clicking the amber grant → a risk-proportional confirm that restates the consequence and names site + folder + count:
```
┌ Confirm access grant ───────────────────────────────────┐
│ 🟠 mail.example.com will be able to read the contents of │
│    12 files in /shared, in this browser.                 │
│    This site is not part of SGraph and we cannot see     │
│    what it does with the data.                           │
│                            [ Cancel ] [ Yes, grant it ]  │
└─────────────────────────────────────────────────────────┘
```

**Design decisions:**
- **The safe path is the only thing visible at rest.** No "No access (•) / Grant read ( )" co-equal radio pair. Granting is a deliberate disclosure + confirm, never an accidental radio flip.
- **Every grant step names the site, the folder, and the file count.** Counts make the abstraction concrete ("12 files," not "a folder").
- **Exactly one amber control per dialog**, matching the amber-banner discipline: amber = "this can leak data," everywhere, only.
- **The grant is visible forever after** via the §5.1 amber banner and is revocable from there. Granting is never fire-and-forget.
- **Adding a sub-vault** reuses the link-card fields (label, key/token, save choice, commit pin, description) with no amber anywhere — because a read-only pointer cannot leak the parent's data outward. Validate the token shape inline; note "Opens read-only in this version."

## 7. Empty / Locked / Error / Expired / Stale-Grant / Narrow-Mobile States

| State | Required design |
|-------|-----------------|
| **Empty (no sub-vaults / resources)** | No special empty zone — because there is no separate zone. The tree simply shows files and folders. The only "empty" surface is inside a freshly opened sub-vault with no files: show the standard empty-folder copy plus the §4 context bar so the user still knows they're in a linked vault. |
| **Locked sub-vault** | `🔒 ◈ Label` in the tree; click opens the **link card** (§3) rather than expanding. The lock is the only extra glyph; no error tone. |
| **Sub-vault unreachable** (open fails / 8s timeout) | Reuse the App-Mode timeout error: `⚠ Can't open Acme — the linked vault didn't respond.` Actions: `[ Try again ]`, `[ ‹ Back ]`, and (owner only) `[ Fix link… ]` to repair the pointer. Plain, not amber (this is a failure, not a leak). |
| **Read-only key expired / revoked** | Distinct copy from "unreachable" so the user knows the likely cause: `⚠ The key for Acme is no longer valid — it may have expired or been revoked.` Owner gets `[ Update key… ]` (re-opens the link card). |
| **Broken external URL / iframe refuses to embed** | Embed area: "This page can't be shown here — the site may block embedding." **Crucially, the neutral 🔒 banner still shows** — a broken embed is still a sealed embed. Never let a load failure remove the guarantee. |
| **Stale grant (granted folder deleted/renamed)** | The grant must not silently re-bind to a different folder. Show on the amber banner: `🟠 The granted folder /shared no longer exists — this window currently reads nothing.` Prompt the owner to re-point or revoke. The grant stays visible until the owner resolves it. |
| **Narrow / mobile** | The v0.2.3 explorer collapses tree+preview on narrow screens. For this feature: (1) the **§4 context bar and §5 embed banner are never sacrificed for space** — they stay full-width and sticky even when panes stack; (2) the `·ro`/`·rw` chip and the `CAN READ /shared (12 files)` text **wrap rather than truncate** — truncating "CAN READ /shared…" would hide the most important word; (3) the Add/Grant flow's Advanced disclosure becomes a full-screen step, but the **confirm step is mandatory on every form factor.** |

## 8. Design Tokens

Reuse the existing vault-UI palette and components wherever possible. Introduce **exactly one** new token.

| Token | Value / source | Use |
|-------|----------------|-----|
| Teal accent | `#4ECDC4` | All safe / neutral chrome: sub-vault glyph, context bar, neutral embed banner, brand. |
| Warning amber | `#d97706` | The **one** risk colour — reserved strictly for "an outside party can read your files": the amber embed banner and the single grant control + confirm. **Used nowhere else.** Never for errors, read-only, or locked. |
| Blue `👁 Read-only` pill | Existing `<app-hud>` read-only badge | File-action context inside an opened read-only sub-vault (§4). Reused exactly — not reinvented. |
| `<send-transparency>` voice | Existing component register | The `[Why?]` and `[ What it sees ]` read-outs — honest, no-hedge ("CANNOT read this vault," "we cannot see what it does with the data"). |
| App-Mode chrome + 8s loading/timeout | `<sg-app-banner>` / `<app-hud>` (v0.2.3) | §4 sub-vault context bar and sub-vault loading/error states. |
| `<app-hud>` toast channel (`sg.ui.message`) | Existing | Full-screen embed reminder; copy/save confirmations. |
| Vault-key inline validation | Existing vault-picker pattern | Key/token validation in the link card and Add-app dialog. |
| **Access chip `·ro` / `·rw`** | **NEW** | The tiny lowercase chip hugging a sub-vault label in the tree. |

**Justification for the one new token (access chip).** Sub-vaults are presented *as folders*, so they deliberately carry almost no distinguishing chrome. But the spec requires the user to be "a little bit aware" — and v1's read-only-everywhere behaviour must be legible *before* the user opens a sub-vault and discovers Edit is gone. The blue `👁 Read-only` pill is the wrong instrument here: it is a heavyweight, button-sized badge appropriate to a file action, and stamping it on every sub-vault tree node would re-introduce the visual "wall" we are explicitly avoiding. The `·ro` / `·rw` chip is the minimum viable signal — a quiet, lowercase annotation that reads as metadata, not interaction. It is also forward-compatible: when child-editing ships, the same chip flips to `·rw` with no new token. One new token, tightly scoped, and it directly serves the "barely aware / a little aware" principle.

## 9. Priorities

| # | Item | Priority | Why |
|---|------|----------|-----|
| 1 | Grant flow = Advanced disclosure + risk-proportional confirm naming site/folder/count; never a co-equal toggle (§6) | **P0** | The single place a user can mislead themselves about who reads their data. |
| 2 | Amber embed banner: non-dismissable, sticky, names folder + count, inline Revoke (§5) | **P0** | A standing grant must be visible at the point of risk, forever. |
| 3 | Neutral embed banner: no dismiss control, sticky through scroll/full-screen (§5) | **P0** | The "CANNOT read this vault" guarantee must not be swat-away-able. |
| 4 | Sub-vaults presented inline as folders — glyph + `·ro`/`·rw` chip only, no separate zone/divider (§2) | **P1** | This is the core "transparency through invisibility" principle; a separate zone would break it. |
| 5 | Link card shows public info **before** the key; three save choices with consequence text; commit pin; Open-here vs Open-in-new-window with parent tracking (§3) | **P1** | The honest "decide before you commit a key" surface; the save-in-vault transitive-trust warning is the subtle trap. |
| 6 | Slim context bar (App-Mode chrome) + file-level `👁 Read-only` pill + `[Why?]` provenance inside opened sub-vaults (§4) | **P1** | "A little bit aware" without a wall; explains why Edit is absent. |
| 7 | Error/empty/locked/expired/stale-grant states; broken embed still shows the sealed banner (§7) | **P1** | A broken embed is still sealed; a stale grant must not silently re-bind. |
| 8 | Protect banners + context bar on mobile; chips and "CAN READ /shared (N files)" wrap, never truncate (§7) | **P2** | Transparency cannot be the thing we drop for space. |

## 10. Red Flags — Trust & Transparency

Read these even if you read nothing else.

1. **The inline-folder presentation is a calculated trade: it lowers the felt boundary on purpose, so it must not lower the *factual* signals to zero.** The risk is a user who genuinely forgets they are inside a *different* vault and assumes a file lives in the parent. Mitigations are load-bearing, not decorative: the `◈` glyph in the tree, the `·ro` chip, the slim context bar while open, the breadcrumb, and `[Why?]` provenance. **Do not let an engineer "simplify" by dropping the context bar or the glyph** — that is the exact line between "barely aware" (good) and "unaware" (a trust failure). This is the highest-judgement call in the whole feature.

2. **"Save key in this vault" is a transitive-trust trap.** Saving a sub-vault's key *into the parent* means anyone the parent is later shared with inherits that key. The link card's save-choice radio **must** state this consequence in plain language at the point of choice. A silent default here could hand a downstream recipient a key the owner never meant to share.

3. **v1 is read-only for sub-vaults regardless of the held key — the UI must never imply otherwise.** Pasting a *full* (writable) key into the link card still opens read-only in v1. The card must say "Opens read-only in this version" so a user holding a writable key is not misled into thinking they can edit inside the child.

4. **Amber is the leak colour, and only the leak colour.** If amber ever appears on an error, a read-only state, or a locked node, it dilutes the one signal that means "an outside site can read your files." Police this strictly in implementation review.

5. **A broken or full-screen external embed must never drop its guarantee banner.** A load failure or a full-screen takeover is exactly when a user might assume "the sandbox is off" — the sealed banner (or its toast equivalent) must persist.
