## Thematic Summaries

### Theme One: Authorization and Maturity Model (docs 1–2)

**Doc 1 — Agent Authorization: Union of the Possible.**
An agent's real authorization is not the words of the grant but the transitive closure of everything reachable from it. Three worked examples demonstrate this: inbox access reaches every account resettable by email; desktop access reaches every stored credential and every logged-in session; code or container execution can escalate to admin through a weak environment. The key quantity is the delta between expected and unexpected permissions. Two awareness gaps keep the delta hidden: (1) the granter does not know the full scope of what it grants; (2) the original delegator never authorised re-delegation to an agent at all. This is the "hope-driven development" anti-pattern — hoping the agent won't misuse what it holds, and hoping it won't find more — while remaining accountable for both, up to the board. The control is scoping and acceptance, not optimism. A scoped capability certificate with a named block list is the mechanism for bounding the union.

**PROPOSED items introduced:**
- Authorization closure as a first-class graph entity (union of everything reachable, not the nominal grant)
- Expected-vs-unexpected delta surfacing mechanism (shown to the granter at moment of grant)
- Scoped capability certificate with a named block list (bounds the delta toward zero)
- Re-delegation consent model (capturing original delegator's authorisation for agent re-delegation)
- Authorization graph edges for credential/session/escalation artifacts (map files that give more permission)
- De-authorization computed over the transitive closure (not just the stated permission)

**Doc 2 — RAMM: Risk Acceptance Maturity Model.**
A first-pass Risk Acceptance Maturity Model designed graph-native. Five levels (Ad hoc, Repeatable, Defined, Managed, Optimized) expressed as Node Type Formulas — testable path-patterns a graph query can evaluate. Maturity is computed from the graph, not asserted in a questionnaire. The entity model covers ten classes: RiskItem, RiskAssessment, RiskTreatmentDecision, RiskAcceptanceDecision, RiskOwner/DecisionAuthority, RiskAppetiteStatement/Tolerance, CompensatingControl, ReviewEvent/ExpiryEvent/ReassessmentTrigger, EvidenceArtifact, and FrameworkReference. Bridges (not merges) connect to OWASP Risk Rating Methodology, SAMM, RIMS, and public-sector maturity models via the ontologies-of-ontologies model. An Agentic RAMM overlay adds CapabilityCertificate, AuthorizationClosure, MomentOfAuthorization, and AgentTwin entities. Adopting Risk Mandate inherently raises an organisation's RAMM level because the product produces exactly the owned, evidenced, interval-bound acceptance nodes the higher levels require.

**PROPOSED items introduced:**
- RAMM as a published standard (graph-native, overlay approach)
- Ten RAMM entity classes as a formal schema
- Five maturity levels as Node Type Formulas (computable from graph queries)
- Example maturity queries (expired acceptances, no-control acceptances, no-board-path acceptances)
- Agentic RAMM overlay (CapabilityCertificate, AuthorizationClosure, MomentOfAuthorization, AgentTwin)
- RAMM-to-OWASP bridge (crosswalk: do this in RAMM → satisfy that in SAMM/ASVS/etc.)
- RAMM-to-RIMS bridge (staged progression and appetite semantics)
- RAMM published site and public repo (planned Phase 1.6 in roadmap)
- OWASP Incubator project submission for RAMM
- Per-control crosswalk (super-detailed next pass, not yet authored)

### Theme Two: Accountability Paradox of Gen AI (doc 3)

**Doc 3 — The Accountability Paradox of Gen AI.**
Two forces pull accountability in opposing directions. Force One: delegating decisions to models we cannot follow produces fuzzy accountability. "The machine decided" hides behind a human-in-the-loop that is really accountability-in-the-loop — a person given blame without agency, time, or context, whose judgment decays under approval fatigue. LLMs also fail unlike humans: errors scattered evenly across the knowledge space, delivered confidently, without warning. Force Two (the focus): using LLMs to scale control flows, decision trees, facts, and evidence, so that mission-critical decisions return to explicit, traceable logic at a scale previously impossible. "Use LLMs not to use LLMs" — the model builds the scaffolding; explicit logic makes the decision. Semantic knowledge graphs are the structure that allows this legibility to scale without becoming opaque. The payoff is risk-based rather than hope-based decisions. The friction: visibility exposes inefficiency and is against the self-interest of those who benefit from unaccountability.

**PROPOSED items introduced:**
- Accountability-in-the-loop detection pattern (distinguishing genuine human-in-the-loop from blame absorption)
- Approval-fatigue metric (decay in judgment quality under repeated approvals without context)
- LLM-confidence bounding pattern (guarding against confident wrongness in multi-step reasoning)
- Scaled accountability architecture (LLMs as scaffolding builders, not decision-makers)
- Decision-graph population by LLM (using the model to build and connect logic, not to decide)

### Product Roadmap (doc 4)

**Doc 4 — RiskMandate.ai Product Roadmap: Shipping on the Core We Already Have.**
A roadmap deliberately constrained to items that run on core technology already built (SG/Send, SGit, SG/Compute, vault-powered mini-site model, S3-compatible vault container, semantic graph on vaults). The single engineering enabler is E1: finishing the publish-to-prod pipeline and extracting the vault-loader library. Everything else is customisation, vault structuring, content, LLM packaging, connectors, or deployment targets.

**Four phases:**
- **Phase 1 (Content and story):** The Library (vault mini-site + librarian agent), use-case mini-sites (2FA, OAuth, calendar), dynamic scenario survey, scenario packs, partner/consulting pages, RAMM published site and public repo
- **Phase 2 (Product surfaces):** Risk register as vault graph, graph viewer mini-app, risk queue MVP, acceptance flow (SGit-commit-as-audit), acceptance dashboard, capability certificate
- **Phase 3 (Demo and maturity):** Demo app (discovery to dashboard, anonymous intake, stakeholder-packaged outputs), RAMM maturity queries, agentic overlay (capability cert, auth closure, agent twin)
- **Phase 4 (Platform, billing, enterprise):** On-demand billing, customer-owned deployment, integrations/connectors

**PROPOSED items introduced (Phase 1):**
- Vault-loader library (extracted from SGraph web repo, read-side JS)
- Publish-to-prod pipeline completion (E1 — the one engineering item)
- Use-case mini-sites (2FA, OAuth, calendar) as vault + DNS + mapping row
- Dynamic scenario survey (gamified, vault-captured, extends shipped MVP)
- RAMM published site and public repo (Phase 1.6, feeds OWASP submission)

**PROPOSED items introduced (Phase 2):**

- Risk queue MVP (trifecta status, exposure clock, time-bound decision per item)
- Acceptance flow mini-app (accept-in-a-direction, for-an-interval, SGit commit = audit)

**PROPOSED items introduced (Phase 3):**
