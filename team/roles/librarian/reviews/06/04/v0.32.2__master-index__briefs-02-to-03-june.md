## Code Changes (Since v0.31.18)

### Vault Inbox Endpoints — NOW EXISTS (v0.32.x batch)

**Commit `9d727b5` — feat: implement vault inbox endpoints (P0 server primitive)**

| Endpoint | Method | Auth | What It Does |
|----------|--------|------|-------------|
| `/api/vault/inbox/append/{vault_id}` | POST | append_token in body | Write-blind, token-gated; append encrypted message to inbox |
| `/api/vault/inbox/list/{vault_id}` | POST | enum_key header | Paginated listing of inbox messages; optional content inline |
| `/api/vault/inbox/fetch/{vault_id}` | POST | enum_key header | Batch fetch messages by ID |
| `/api/vault/inbox/mark-processed/{vault_id}` | POST | enum_key header | Reversible move from inbox/ to processed/ |
| `/api/vault/inbox/purge/{vault_id}` | POST | write_key header | Irreversible delete, owner-only |
| `/api/vault/inbox/configure/{vault_id}` | POST | write_key header | Set append_anchors and enum_key_hash |

**101 new tests** (62 service-level + 39 HTTP route tests). All use real in-memory stack, no mocks.

**Classification:** EXISTS — vault inbox is a new capability, not a reorganisation. 6 endpoints now shipping.

**Four-tier capability model:**
- `append_token` — write-only (sender can only append, cannot read)
- `enum_key` — list/fetch/mark-processed (receiver reads)
- `private_key` — decrypt (client-side, never seen by server)
- `write_key` — purge + configure (owner only)
