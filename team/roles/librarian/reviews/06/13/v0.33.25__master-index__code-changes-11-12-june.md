### Fix 1 — Null-origin localStorage crash

**Symptom:** When a parent vault opened a child vault via the embed protocol, the child was
mounted in a sandboxed iframe (no `allow-same-origin`). `vault-entry.js:41` read `sessionStorage`
without try/catch. In a sandboxed context the accessor throws synchronously, crashing
`VaultEntry.onReady` before the saved-key auto-open could run — the user had to type the vault
key manually every time, despite it having been previously saved.

**Root cause:** Uncaught synchronous `SecurityError` on `sessionStorage` access in sandboxed iframes.

**Fix — three files:**
1. `vault-entry.js` — wraps the endpoint-storage read in try/catch.
2. `index.html` creating-splash IIFE — wraps `sessionStorage.getItem` in try/catch.
3. `vault-loader-storage.js` — adds `VaultLoaderStorage.available()`: a cached feature-detect
   (tests one read, caches the boolean result) so any UI branch that gates on storage (recents
   list, "remember me") can call `available()` once rather than re-implementing try/catch.

**Test coverage:** `test__storage.js` null-origin survival suite — substitutes a throwing
`localStorage` / `sessionStorage` on `globalThis`, then asserts: every getter returns `null`,
every setter is silent, `available()` returns `false`, and no thrown exception propagates.

### Fix 2 — EFBIG guard for `sg.vfs.write`

**Symptom:** An app calling `sg.vfs.write` with a blob > ~3 MB would get an opaque network error
mid-batch (Lambda URL Function hard cap: 6 MB per request). The EBADENC fix earlier today
(commit `2892b4be`) resolved the 8 KB base64 padding bug; the Lambda cap is a separate ceiling.

**Root cause:** No pre-flight size check in the bridge receiver. One `POST /api/vault/batch`
carries: new blob + tree object + commit object + ref update + index file, each base64-encoded in
JSON. Base64 inflates ~1.33×; the metadata overhead is ~10–50 KB. Conservative ceiling for the
actual blob: ~3 MB plaintext.

**Fix:** The bridge receiver now checks the byte length of the incoming write. If it exceeds the
ceiling it returns `EFBIG` with the exact limit and actual size, so the app author knows precisely
what to change rather than diagnosing a generic 413.

**AUTHORING.md additions:** Documented the ~3 MB write ceiling, the read/write asymmetry (reads
scale further via presigned-S3; writes do not yet), and a note that the "Bad encoding" 8 KB cap
was the separate chunking bug fixed in `2892b4be`.

**PROPOSED — P-269:** A presigned-PUT mirror endpoint is the only proper way to lift the 3 MB cap
past Lambda. Server: `POST /api/vault/presigned/write-url/{vaultId}/{filePath}`. Client:
`vaultWriteLarge()` in `sg-send.js` + `sg-vault-object-store.js`. Memory-FS fallback:
`presigned_unavailable`. Scoped brief at
`team/comms/briefs/06/11/v0.33.21__brief__vault-presigned-put-large-write.md`. Estimated
~half-day end-to-end; sgit CLI unaffected (already direct-PUTs).

### Fix 1 — `sg.app.writable` parity

**Symptom:** Opening a vault with a full key (crypto tier: writable) but without a write access
token (auth tier: read-only) reported `sg.app.writable=true` in `/en-gb/app/` but `=false` in the
Vault UI editor preview. Apps trusting the flag on init (e.g. an audit-log write in
`connectedCallback`) received `EREADONLY` from the bridge, causing cascading failures (the brief's
"canUseSecrets stays false → 'needs the doctor key'" symptom was the cascade from that rejected
write, not a separate permission bug).

**Root cause:** The `/en-gb/app/` path surfaced `sg.app.writable` based on `this._writable`
alone (crypto tier). The Vault UI preview surfaced it based on `dataSource.writable` (auth tier).
The two paths disagreed.

**Fix — three places so bridge, HUD, and debug pane all agree:**
1. `_buildVfsBridgeScript`: `var writable = this._writable && dataSource.writable` (AND of
   both tiers — what the bridge actually enforces).
2. `app-shell:ready` event: `isRO = isRO || !dataSource.writable` so the HUD shows the
   read-only badge whenever writes will fail (not just ro-token).
3. `getDebugState()`: `writable = effective`; also exposed `writableCrypto` + `writableAuth`
   separately so the debug pane can show both tiers.

**Scope:** Changes only what is *advertised* — bridge enforcement was already correct
(`dataSource.writable` was already gated server-side); the app just didn't know.

### Fix 2 — Copy contents button (send-browse v0.3.3)

**What:** `⎘ Copy` action added to send-browse's file viewer toolbar (next to Save / Locate).
Shown for textual file types only: code, text, markdown, CSV, HTML source. Binary types
(images, video, PDF, archives) deliberately excluded.

**Implementation:** Uses `navigator.clipboard` with a `textarea + execCommand` fallback for
insecure contexts. Flashes "✓ Copied" for 1.6 s. Lives in the v0.3.3 IFD overlay on top of the
existing `send-browse--v0.3.2.js` — vault-browse-edit picks it up everywhere it renders a file.

**Open item flagged:** The `_write` encoder in this file still uses chunk=8192 (same base64
padding bug fixed in `app-shell.js` at v0.33.21). Only affects editor writes from the preview
pane > 8 KB. Commit author flagged it for a separate follow-up commit.
