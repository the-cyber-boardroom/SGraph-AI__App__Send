### Fix 1 — VFS write bridge base64 chunking bug

**Symptom:** `sg.vfs.write` silently failed (returned "Bad encoding") for any file above ~8KB.
Files ≤ 8KB wrote successfully; files ≥ 10KB (empirically) failed.

**Root cause:** The `_write` bridge injected into the app iframe chunks byte arrays into N-byte slices
and base64-encodes each slice independently with `btoa()`, then concatenates the outputs. The chunk
size was **8192 bytes**. Since 8192 mod 3 = 2, every non-final slice is not a multiple of 3 bytes,
so `btoa()` appends `=` padding. The host's `atob()` rejects `=` anywhere except at the end of the
string, causing the concatenated result to throw "Bad encoding" on `atob()` for any multi-slice
write.

**Fix:** Chunk size changed **8192 → 8190** (= 3 × 2730). Every non-final slice is now a clean
multiple of 3 bytes → no embedded `=` padding → `atob()` accepts the concatenated base64 at any
size. Verified through 128KB.

**Diagnostic improvement:** Added `EBADENC` error on receive — reports the raw base64 length and
the `atob` exception message so future encoding failures are immediately identifiable rather than
producing a silent mystery.

**Impact:** `sg.vfs.write` is now reliable for file sizes beyond 8KB. This unblocks vault apps
that need to write files of any practical size.

### Fix 2 — Privileges chip colour semantics

**Symptom:** The standing-grants chip on the `<app-hud>` was rendered **red** whenever destructive
grants were held (e.g. `vault.delete`, `vault.unlink`, `move`, `delete`). Users reported this as
"something looks wrong" — the red was read as an error state, not a permission indicator.

**Root cause:** The chip used `--danger` CSS class, which mapped to the same red token used for the
active consent prompt and the activity-meter error pulse. A persistent status chip should not share
the same visual weight as a live-alert surface.

**Fix:** Chip colour semantics revised:
- **Default state** (no destructive grants): **slate** (calm, informational)
- **Destructive grants held**: **amber** (notable but not alarming)
- Active-prompt **red** (consent bar) and error-red (activity-meter `pulse-err`) unchanged

The rows inside the expanded privileges popover also lift from red → amber for destructive-verb
entries, consistent with the chip.
