## Thematic Groupings

### Theme A: Vault Chat — Full Architecture (docs 505–506)

**The framing decision:** Vault Chat is the exact same primitive as Vault App — both are iframe-based surfaces over the `window.sg` bridge. The distinction is the iframe content: Vault App runs arbitrary HTML; Vault Chat runs an LLM chat interface. Same kernel model, same capability surface. This is architecturally elegant — it means the entire ViV security work (Phase 3 null-origin, SecureChannel, broker) applies to Vault Chat for free.

**Two filesystems distinction:** Vault Chat operates over two distinct filesystems:
1. **Vault FS** — the real, encrypted, version-controlled vault
2. **VFS (Virtual File System)** — the LLM's curated working memory; ephemeral by default; optionally synced to vault

The VFS is NOT a new backend construct — it is a client-side abstraction that the chat manages. Files represent context chunks, history entries, extracted facts. The LLM self-prunes by writing consolidation files to the VFS and dropping stale context.

**Token management discipline:** Every token matters. The LLM manages its own memory budget (self-pruning tool, consolidation into VFS). Sidecar LLMs run in parallel for curation, extraction, security checks, consolidation. The Librarian's graph-native patterns are the design reference.

**Architectural assessment:** This is the cleanest way to add LLM capability to the vault — no new protocols, no new security surfaces. The iframe bridge already handles everything. The VFS and commit queue solve the two main engineering challenges (LLM memory vs vault commits).

### Theme B: Commit Queue — Solving Chatty Volume (doc 509)

**The problem:** Vault Chat with VFS sync generates many fine-grained file writes. One-write-per-commit creates an explosion of commits (every LLM response = commit + push). This is untenable for anything resembling real use.

**The solution:** A timer-windowed commit queue on the vault mothership (not inside the iframe). A change starts a timer (configurable: 0s = current behaviour, 10-15s suggested default). At timer expiry, all pending changes batch into a single commit. The queue has a staging area (visible pending files) and a debug window.

**Key design decision:** The queue lives on the mothership (vault-shell), not in the app iframe. This is correct — the vault mothership already owns the commit/push cycle. The iframe sends VFS-sync writes via the sg.* bridge; the mothership decides when to batch and commit.

### Theme C: ViV Kernel Model Brokered-PKI (doc 507)

This brief is the companion to the 05/27 vault-in-vault briefing pack (already processed in the 05/29 master index). It provides additional design rationale for the same architecture:
- Within-vault and across-vault access are the SAME primitive (simplification confirmed)
- Directional trust flows parent-to-child only
- PKI on every inter-vault message prevents misrouting bugs AND enforces confidentiality
- Monitoring-vs-isolation choice per child kernel

**Relationship to implementation:** All structural decisions in this brief are either already shipped (Phase 1–2, Phase 3, B5/B6/B7/B10) or tracked as PROPOSED (vault-in-vaults visualization page P-261, CLI/REPL P-261).

Evidence graph linking findings to payloads/screenshots. Positive scorecard (industry gap). This demonstrates: Vault App (custom HTML per audience), Vault Chat (authoring), version control, controlled distribution.
