## Thematic Groupings

### Theme A: The ViV Security Finding and Architectural Response

**The finding (doc 494):** Vault app code runs in a same-origin iframe (`allow-same-origin`). Any code in that frame can bypass the `sg.*` bridge entirely — reading vault keys and access tokens from `localStorage`, walking the DOM, reaching `window.parent`. The permission model (Phases 1–4B: deny-by-default, EPROTECTED floor, grants) is advisory-only for cooperative code and fully bypassable for uncooperative code.

**The architectural response (doc 495, doc 497):** Run all app code at `null` origin — no ambient secrets, no storage, no parent DOM access. Deliver capabilities (not credentials) over a port-anchored PKI-authenticated channel (SecureChannel). The kernel holds secrets and enforces policy; the app frame only gets the `sg.*` RPC stub. This one change simultaneously:
1. Closes the same-origin bypass security vulnerability.
2. Enables vault-in-vault (a parent app can spawn a child vault's kernel in an isolated null frame, feed it that vault's secrets over the channel, and relay `sg.vfs.*` operations to it).

**Design evolution (doc 496 → doc 498):** The version-1 briefing proposed two mechanisms that the version-2 review corrected (B1: directional `request()` restriction; B2: binary payloads as `Uint8Array` not JSON). Version-2 is the normative reference.

- M2: Parent applied its own fs.write grant before resolving the mount (relayed writes spuriously EPERM'd)
- M3: `__sgVfsListReq` had no mount-resolve+relay branch
- M4: Bootstrap was untested — relay used a hand-rolled TestKernel not sharing code with shipped child
- M5: Endpoint hardcoded to `https://dev.send.sgraph.ai` (now reads from secrets payload)
- M6: SecureChannel dispatched any signature-valid envelope without checking it was addressed to THIS cid
- L1: generateSignKeypair had a dead then/catch fallback (only catch ever ran)
- L3: No check that kernel-shell-bundle.js was current vs. its sources
- L4: _preHandshakeBuf grew unbounded for unknown pre-handshake message types
