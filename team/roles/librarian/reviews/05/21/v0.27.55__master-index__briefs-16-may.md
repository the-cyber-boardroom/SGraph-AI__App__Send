## Thematic Groupings

### Theme A: Vault-as-Testable-Software — Demo + Testing + CI + LLM Validation

**Briefs:** 417 (demo capabilities), 418 (testing framework), 419 (CI pipeline), 420 (Nova + AgentCore POC)

**Signal:** Four documents form a coherent whole: demo capabilities give the JS API surface; the testing framework defines four test layers using that surface; the CI pipeline automates running them; the Nova POC adds a fifth qualitative layer. The same JS API that the vault app uses for normal operations is the test surface — this is the critical architectural decision. It means tests exercise real code paths and vault authors who know the API can write tests without learning a parallel interface. The LLM cost economics are compelling: Nova Lite at ~$0.0003/CI review means continuous qualitative testing at negligible cost.

### Theme B: Side-by-Side Personas — The Demo Template

**Brief:** 421 (accountant demo)

**Signal:** The accountant demo introduces a reusable pattern: four-pane UI, same vault, two apps, real infrastructure provisioning and teardown, LLM and infographic generator integrated. The real architectural insight is "same vault, two apps with role-based routing" — this is the SG/App framework taken to a concrete use case. The template will be reused for recruitment, news, and risk demos. Cost per demo run is ~$0.01 (infrastructure + LLM + metering).

### Theme C: Vault Discovery + Public-Key Infrastructure

**Brief:** 422 (vault discovery and public keys)

**Signal:** The `/.well-known/vaults` endpoint is a foundational primitive. The four visibility levels (public/unlisted/private/count-only) mirror YouTube's video visibility model. The Ed25519/X25519 key infrastructure is the "do this properly now" decision before it becomes a retrofit. The "send to a vault" pattern via public-key encryption is the architectural equivalent of what email already does — and connects directly to the agent-to-agent communication pattern in Theme D. The offline-bundle story (portable demo server as Docker image) is a meaningful market scenario for air-gapped environments.

### Theme D: The Vault-as-Communication-Medium Pattern Crystallised

**Briefs:** 424 (serverless), 425 (multi-cloud + agent communication)

**Signal:** The two most architecturally important documents in the batch. Day 66 names the pattern that was implicit in many earlier briefs: agents communicate through shared vaults, not direct calls. This solves the agent coupling problem (no library imports, no subprocess calls, no shared DB) while providing an audit trail for free (every interaction is a vault commit). The serverless synthesis is the other major framing: not Lambda, not Kubernetes — a serverless environment specifically for agents, where containers handle parallel requests naturally, the substrate is customer-controlled, and Nitro Enclaves are available for high-trust compute. The parallel-request observation (Lambda cold-starts each concurrent slot; containers serve N concurrent requests with one cold-start) is the sharpest technical justification for the container-first substrate.

### Theme E: AppSec Mini-Tools — A New Product Surface

**Brief:** 423 (AppSec strategy)

**Signal:** The core insight: every AppSec tool has a data-sharing problem; vaults solve it once for all of them. The pattern (find strong open source → host on our infrastructure → vault integrate → contribute back) is a productisation template, not a one-off. Matt Adams' StrideGPT is the first target. Eight concrete tools are mapped. This opens an entire customer category (AppSec engineers juggling 8-15 tools with scattered data homes). The STRIDE/OWASP LLM Top 10 integration and MAESTRO-inspired pattern detection make StrideGPT current and credible.

### Theme F: SG Mail — Email as a Vault Client

**Brief:** 426 (SG Mail)

**Signal:** The framing correction is the most important contribution: we are not building email infrastructure (SMTP, deliverability, anti-abuse). We are building the vault client on top of EML files. Everything before the EML is a connector (SES, Cloudflare Email Service, Gmail API, IMAP). Everything after is the vault and the client UX. The email-fs work already exists. The client is the new work. Target: ≤£8/month as a WorkMail replacement — plausible given SES pricing and serverless compute costs. Cloudflare Email Service (April 2026 launch) is specifically positioned as agent-native.

### Theme G: Operational Reality — Backup, Provisioning, Admin Registry

**Briefs:** 427 (backup), 428 (on-demand provisioning), 429 (DNS registry)

**Signal:** Three operational pieces that turn "interesting demos" into "actually runnable." Backup brings the "backups never restored are not backups" discipline — four drill cadences, separate AWS account for ransomware isolation, multi-provider (Backblaze B2). On-demand provisioning documents the 50-second end-to-end milestone and fixes the DNS pinning problem via the holding-page-detects-readiness Lambda. The DNS registry corrects the CNAME-to-wildcard idea (RFC 4592 makes this unreliable across resolvers) and provides the cleaner A-records-plus-TXT approach where the admin vault is the registry of truth. All three use the vault-as-mini-app pattern from earlier this week.
