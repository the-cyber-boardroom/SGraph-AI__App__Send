## Thematic Groupings

### Theme A: External Data Connectors (docs 513–518)

The connector series (6 documents) forms a complete specification from framework to implementation:

**The framework (doc 513):** Expand the existing link concept (YouTube, Page, Image, Vault) into a new category of links that point at external data stores. A connector is: (1) a link-type in the vault, (2) a custom viewer calling the source's API, (3) an iframe holding OAuth credentials. The source data is NEVER stored in the vault. Two integration levels: the connector renders its own custom viewer, or the vault asks the iframe for structure/files and renders them in the vault tree. Strategic point: the more connectors, the more people use the vault without noticing (adoption by augmentation).

**The first connector (doc 514):** Google Drive — a button on the left, click it, see Drive in a custom viewer, data stays in Google Drive. Least-privilege via the `drive.file` scope + Google Picker API: the app sees only the folder the user selects, nothing else in Drive. Folder ID stored in the vault (not the data). The VC-session insight: VCs live in Google Drive; a connector meets them there.

**The survey (doc 515):** Tier 1 easy wins: Google Drive, GitHub (CORS any origin), OneDrive/MS Graph. Tier 2 workable: Dropbox (CORS pattern), S3 (per-bucket CORS). Honest harder flags: Notion (CORS blocked, needs proxy), Airtable (unreliable CORS), general AWS (SigV4, not OAuth). Priority sequence: Drive → GitHub → OneDrive → Dropbox → S3.

**The OAuth fix (doc 516):** Critical architectural correction — a no-origin iframe (all app-shell frames are null-origin per Phase 3) CANNOT receive an OAuth redirect because there is no URL to redirect to. The fix: a data broker iframe, separate from the UI, that holds tokens and makes all API calls. The UI renders and asks the broker; the broker alone is trusted with credentials. The top-level kernel (which has an origin) receives the OAuth redirect and relays it PKI-encrypted to the broker. This is the correct model; the earlier connector briefs assumed the app iframe could do OAuth, which was wrong.

**The methodology (doc 517):** Build connectors in the tools repo first (Google Photos and YouTube integrations already exist there). 90%+ can be proven in the browser without vault code. Simulate the tree view, all comms, monitoring, visualisation. Abstract to CRUD primitives (create/read/edit/delete) so the tree view doesn't know what's behind it. Only bring matured, minimal code to the vault.

**The reverse PoC (doc 518):** A demo from the company-being-reviewed's perspective, the flip of the VC demo (P-268). Shows: presenting, controlling exposure, tracking, organising, keeping materials current across multiple shares. Builds on solid single-vault capabilities; VIV framed as coming. Parked: single-source-of-truth-across-vaults (flagged for later).

**Architectural assessment:** The data-broker model (doc 516) is a significant and correct refinement of the connector framework (doc 513). The no-origin OAuth blind spot is real and would have blocked connector implementation. The broker model is consistent with the VIV architecture (the broker is a single-purpose sidecar, like the VIV broker; credentials are PKI-encrypted; the kernel routes). The tools-first methodology (doc 517) is sound and de-risks the hard questions.

### Theme B: Evidence-Driven Assessment Series (docs 519–524)

The assessment series (6 documents) forms a complete application platform specification, building on Vault Chat (P-263):

**The cornerstone (doc 520):** The evidence-driven feedback loop is THE foundational mechanism. Every assessment, every CV, every consulting engagement runs on this: ask → extract → connect into graph → refine → next question → round. Akinator and Whodunit are the proving ground (tangible, tunable, free of domain complexity). Three visualisation primitives: (1) semantic knowledge graph (LLM extracts elements, pure graph engine renders), (2) visualisation-of-visualisations (multi-graph, multi-altitude, Miro/whodunit board), (3) pure infographics (image models). Per-round budget control is not optional — the closed-loop cost danger is real and has caused real financial harm.

**The first assessment (doc 519):** GDPR assessment vault — the first concrete facts/hypotheses/evidence vault. Propose-and-confirm: the system makes claims about the company's GDPR posture backed by evidence; the user confirms or rebuts. This is the inversion that matters: the burden is on the system to discover, the burden on the user is only to validate. Vault chat as engine (a variation of P-263), OpenRouter in iframe. All tooling largely exists; the new work is the graph-based GDPR, the discovery-workflow logic, and the cost measurement.

**The CV workflow (docs 521–522):** Research-first (agents discover, user confirms). Every claim anchored to stored, dated evidence (HTML, screenshots) in the vault. Consistency enforces honesty — evidence graphs make exaggeration visible because a junior who claims 100-node Kubernetes has no supporting evidence. The key insight (doc 522): conventional CVs are uni-dimensional because personalisation didn't scale; now it does. The workflow is a versioned, importable vault app. Sub-vault feedback harvesting (read-only/read-write tokens for reviewers). Hiring signals to surface: thinking/values/problem-solving, whole person, non-linear paths, trespasser syndrome (under-labelled transferable skills), buried nuggets.

**The store (doc 523):** Vault App Store / Hub distributes the vault apps the assessment series produces. Key insight: a vault is a zip, so distribution is distributing zips. The new work is the catalogue, security analysis (trust layer before import), agent mapping, billing, and a clean import/version/load flow. OpenRouter credits can be bundled with a sale — buyer gets the app and an allowance to run it.

**The consulting model (doc 524):** Closes the series by returning to where it began (GDPR), now with the full machinery. Formal rounds/passes concept (user chooses number; each round: current evidence → next questions → user confirms → analyse → save; non-linear, branchable, replayable). Customised graph-based standards (GDPR, ISO 27000) shared with SG/Sentinel compliance graph — important cross-product capture. Three delivery models: self-service (private/ephemeral), send-to-consultant, consultant-driven. The thesis: augment the human, don't replace them. Cost-effective and scalable analysis increases demand for the expert's judgement.

**Common spine across all applications:** The evidence feedback loop on the vault. Discover → present → confirm → anchor → visualise → round by round → version-controlled → budgeted. The GDPR assessment is the first instance; consulting assessments are the general business model; the CV is the personal instance; the Vault App Store distributes them all.
