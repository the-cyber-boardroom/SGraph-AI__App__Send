## 4. Significant Finding

### M-1 (Medium): The L-2 "separate config file" fix is incomplete and its test is misleading

**What L-2 was meant to fix:** `configure` did a read-modify-write on the manifest, which
is **co-owned** with `Service__Vault__Pointer`. The fix was to move append config out of
the manifest into a dedicated `config.json`.

**What the code actually does (`configure`, lines 99–107):**
```python
if append_anchors is not None:
    config['append_anchors']   = append_anchors   # → config.json
    manifest['append_anchors'] = append_anchors   # → STILL written to manifest
if enum_key_hash is not None:
    config['enum_key_hash']    = enum_key_hash     # → config.json
    manifest['enum_key_hash']  = enum_key_hash     # → STILL written to manifest
self.storage_fs.file__save(config_path,   ...)
self.storage_fs.file__save(manifest_path, ...)     # manifest re-written every time
```

**And the gates read from the manifest, never `config.json`:**
```python
def _check_append_token(...): anchors = manifest.get('append_anchors', [])   # manifest
def _check_enum_key(...):     expected = manifest.get('enum_key_hash')        # manifest
```

**Consequences:**
1. **L-2 is not actually resolved.** The manifest is still co-owned and still re-written
   on every `configure`. The exact RMW-on-shared-manifest pattern L-2 flagged remains.
2. **`config.json` is write-only dead data.** The only reader is a subsequent `configure`
   (the untested G-1 path). Nothing else consults it.
3. **Drift risk.** Two stores now hold the same truth. If anything ever writes one without
   the other (e.g. a future sgit managing `bare/append/`, or a manifest rewrite), the gates
   silently follow the manifest and ignore `config.json`.
4. **The test gives false confidence.** `test__configure__writes_separate_config_file`
   asserts the file *exists* and contains the keys — it does **not** assert the gates read
   from it. A reader of the suite would reasonably conclude L-2 is done. It is not.

**Recommended resolution (pick one, explicitly):**
- **(A) Make `config.json` authoritative** — gates read append config from `config.json`;
  stop writing append fields into the manifest. This is the true L-2 fix. Requires a
  cache for config and updating the 3 gate readers + tests.
- **(B) Drop `config.json`, accept the manifest as the single source** — document that the
  manifest is the append authority and that pointer/append co-ownership is safe because
  `_ensure_manifest` only ever *creates*, never overwrites. This is less work and is
  arguably fine given pointer never touches append fields — but then L-2 should be marked
  "won't fix / not a real problem" rather than "fixed".

Either is defensible. The current hybrid is the one option that should **not** ship as
"L-2 fixed", because it carries the duplication cost without the separation benefit.

## 5. Minor Notes

- **N-1 (Nit):** `_safe_token` / `_safe_file_id` catch `(ValueError, Exception)`. `Exception`
  already covers `ValueError`; the tuple is redundant. Harmless, but tidy-up candidate.
- **N-2 (Nit):** The response field and body param are still named `inbox` throughout the
  append API. This is deliberate wire-compat, but for a feature whose thesis is "this is not
  an inbox", the lingering `inbox` JSON key is a small honesty gap. Consider `lane` or `token`
  in a future contract version (not now — would break the harness again).
- **Observation:** S3 behavioural parity for append remains **structurally** tested only
  (`test_Storage_FS__S3.py` asserts `folder__folders` is overridden). The LocalStack
  end-to-end drain is still a documented TODO. Acceptable for Explorer; **Villager must
  close this before production** since the whole list/drain path depends on `folder__folders`.
