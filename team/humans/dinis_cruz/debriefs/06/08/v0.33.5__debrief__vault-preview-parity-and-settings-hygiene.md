## 1. The parity bug — what was actually happening (and the fix)

### What you saw (pic 1 vs pic 2)

| | SG/App (`/en-gb/app/`) | SG/Vault editor preview |
|---|---|---|
| `sg.app.vaultId` | populated | **empty** → `my vault: ?` |
| `sg.vault.*` | present | **absent** |
| mount script | `app-shell.js` | `send-browse--v0.3.2.js` |

Both scripts live in **this** repo and both deploy to `dev.send.sgraph.ai`. Two scripts, two surfaces, no shared builder. They drift.

### Root cause for the empty `sg.app.vaultId`

`send-browse--v0.3.2.js` reads `self.dataSource._vault.vaultId`. When the editor wraps the root data source in `CompositeDataSource` (the `*.link.json` / sub-vault adapter that's the default in v0.2.3), the underlying source lives at `composite._root`, not `composite._vault`. So `dataSource._vault` was `undefined` and `vaultId` defaulted to `''`. Pure layering bug — the composite didn't delegate the identity getter.

### Fix shipped now

- **`CompositeDataSource` `_vault` getter** that delegates to `this._root._vault`. The composite is now transparent for the identity delegate. **Every other consumer** that historically read `dataSource._vault` (vault-shell, vault-browse-edit, app-shell) also benefits.
- **`sg.app.context`** stamped on both surfaces:
  - `context: 'app'` from `app-shell.js` (full surface).
  - `context: 'preview'` from `send-browse--v0.3.2.js` (reduced surface).

### What this means for your app

```js
// Reliable feature-detection from now on:
if (sg?.app?.context === 'preview') {
  // Editor inline preview — sg.vault.* and some others may be absent today.
  // Still works for VFS, sync, auth, ui, identity.
}

if (typeof sg.vault?.create === 'function') {
  // Capability check — independent of context. Use this rather than
  // checking context==='app' so you keep working when the parity work
  // lands and 'preview' gains sg.vault.*.
}

console.log('My vault id:', sg.app.vaultId);   // populated in BOTH contexts now
```

### What I did NOT do (intentional, documented as follow-up)

The full unification — extracting `_buildVfsBridgeScript` into a shared `SgGlobalBuilder` so capability additions land in **one** place — is filed as Plan §4 in `team/comms/briefs/06/08/v0.33.5__brief__vault-preview-app-parity.md`. Same for getting `sg.vault.*` dispatched in the editor preview host loop (Plan §5). The current state makes the parity gap **discoverable** (via `sg.app.context`) instead of silent, which unblocks your app today.

## 2. HUD consent — testability hooks shipped

The source brief claimed the consent prompt "blocks the triggering click." Checking the code: it doesn't. The consent UI is an **inline element in the HUD chrome** (`app-hud.js` L42), not a modal overlay with a click-capturing backdrop. The click already returns; the prompt is independently actionable.

What was actually missing — and what's shipped now — is **automation hooks**:

```html
<span class="hud-consent" role="alertdialog" aria-label="Vault permission request"
      aria-live="polite" data-testid="hud-consent">
  <span class="hud-consent-text" data-testid="hud-consent-text"></span>
  <button class="hud-consent-allow" data-testid="hud-consent-allow" aria-label="Approve">Allow</button>
  <button class="hud-consent-deny"  data-testid="hud-consent-deny"  aria-label="Deny">Deny</button>
</span>
```

Playwright can now target `[data-testid="hud-consent-allow"]` reliably. Also added a label for the v0.33.5 `vault.createKey` verb ("create a vault and receive its full key").

**Test pre-grant flag (auto-satisfy in non-prod) is NOT shipped** — it's security-sensitive and deserves its own AppSec brief. The data-testid hooks unblock automation in the meantime.

## 3. `.vault-settings.json` — orphan hygiene

### What was happening

Two independent things conspired to make this file appear in your editor:

1. **Kernel (`sg-vault.js`):** `_commit()` rewrote `.vault-settings.json` on **every** commit, whether settings changed or not.
2. **UI patch (`index.html` L413–467):** `VaultDataSource.getTree` / `getFileList` were monkey-patched to **push** `.vault-settings.json` into the file list of the editor's file browser — even though the kernel-level `_loadTreeFromCommit` already consumes that entry into `_settings` and does NOT add it to `_tree`. So the patch was the ONLY thing making it visible in the file browser.

That's why you saw it: the kernel guaranteed it was in every commit, and the UI patch made it show up.

### What's shipped now

**Kernel side (`sg-vault.js`):**
- `_commit` writes `.vault-settings.json` **only** on the initial commit, OR when `_settingsDirty` is true.
- `_loadTreeFromCommit` captures the existing settings entry into `_currentSettingsEntry`, so subsequent commits **forward-carry the same blob_id un-rewritten** when nothing changed.
- `setName` is a no-op if the name is unchanged; it sets `_settingsDirty` when it does change.
- `_settingsDirty` is cleared after a successful commit.

**UI side (`index.html`):**
- The `getTree`/`getFileList` patches that pushed `.vault-settings.json` into the listing are **removed**. The file no longer appears in the editor's file browser.
- The `getFileBytes`/`saveFile` hooks **stay** (so any code path that asks for the file by path — e.g. a Settings tab JSON round-trip — still works), but they're now read-only by name; the file isn't listed.

### What you'll see now

A vault created via `sg.vault.create({ seedFrom: 'self:templates/patient' })` opens in the SG/Vault editor with only the files **you** put in it (`index.html`, `app.json`, etc.) — no auto-orphan `.vault-settings.json`. The metadata is still encrypted into the initial commit (with the label you passed), it just isn't surfaced as a user-editable file.
