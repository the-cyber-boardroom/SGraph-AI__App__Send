# Technical Debrief — One-click *writable* patient links (vault key in the link, token in the vault)

**Version:** v0.33.5
**Date:** 2026-06-08
**Branch:** `claude/zealous-thompson-yDjFX` (not yet merged)
**Audience:** The doctor-console / vault-manager app team
**Status:** **Implemented + loader-suite green. Browser-unverified — run the §6 checklist on dev.**

Implements the brief: doctor creates a patient vault → hands the patient **one key-only link/QR** → patient clicks/scans and is in, **writable**, zero setup. The backend access token is embedded **in the vault**, never in the URL.

---

## 1. The model (as shipped)

```
LINK / QR  =  https://dev.vault.sgraph.ai/#<passphrase>:<vault_id>     ← vault key ONLY, never a token
VAULT      =  .vault/access-token.json  { token, created, source }      ← token lives here, added at create
```

On open, the loader: takes the vault key from the link → decrypts the vault (reads need only the vault key) → reads the embedded `.vault/access-token.json` → uses that token to authorise **writes**. A key-only link now opens **writable**.

The token file is:
- **Encrypted under the vault's `read_key`** — only someone with the vault key can decrypt it (which the link holder needs anyway).
- **Under the `.vault/**` floor** — a sandboxed app inside the vault **cannot** read the raw token via the bridge. Only the kernel reads it, to authorise writes. (This is why we used `.vault/access-token.json` rather than `app.json.accessToken`, which an app *can* read.)

A vault **without** this file still opens **read-only** from a key-only link — exactly today's behaviour (your read-only sharing flow is preserved).

---

## 2. `sg.vault.create` — the new `accessToken` option

```js
const { vault_id, ref_id, writable_link } = await sg.vault.create({
  label:     'Patient — Jane Doe',
  custody:   true,
  seedFrom:  'self:templates/patient',
  accessToken: 'inherit'      // embed the DOCTOR vault's current token → patient link opens writable
            // | '<token>'    //   or embed a specific token string you provide
            // | 'new'        //   ⚠ ENOTIMPL for now (see §5)
});
// writable_link === true  → a key-only link to this vault opens writable
```

| `accessToken` | Behaviour | Grant |
|---|---|---|
| omitted | No embed → vault opens **read-only** from a key-only link (unchanged) | — |
| `'inherit'` | Embeds the doctor/kernel vault's current access token | `vault.embedAccessToken` |
| `'<token>'` | Embeds the supplied token string | `vault.embedAccessToken` |
| `'new'` | **ENOTIMPL** — mint endpoint exists but uses a separate API-key workflow not wired here | n/a |

The token is written **into the new vault** and published with it — never returned in any link.

## 3. Getting the writable link (no new API)

Unchanged from before: build the link from `getKey(ref)` + the open base. Because the vault now carries the embedded token, that **same key-only link** opens writable.

```js
const { key } = await sg.vault.getKey(ref_id);              // always-confirm consent
const link    = 'https://dev.vault.sgraph.ai/#' + key;     // render as text + QR
// Label it "Sensitive: contains the vault key" — it IS a read+write credential.
```

---

## 4. Rotating / updating the token (Q4) — `sg.vault.setAccessToken`

```js
await sg.vault.setAccessToken(ref_id, 'inherit');   // re-embed the doctor's current token
await sg.vault.setAccessToken(ref_id, '<newToken>'); // embed a specific token
```

`ref` can be a custodied `ref_id` (resolved kernel-side via the owner-secret store — the key never crosses the iframe) or a raw key. This is the "update the token for one or many vaults" path you asked for — loop over your roster and call it per vault. Gated by `vault.embedAccessToken` + one-time consent.

---

## 5. `accessToken:'new'` — why it's deferred

Per your answer: the per-vault mint endpoint exists but uses a **different API key / workflow** we're not integrating now. So `'new'` returns `ENOTIMPL` with a clear message. For v1, use:
- `'inherit'` — all patients share the doctor's token (revoking it revokes all). Simplest, works today.
- `'<explicit>'` — you supply a token per patient (independently revocable) if your billing layer already mints them out-of-band.

When the mint workflow is wired, `'new'` becomes a one-line change in `_resolveEmbedToken`.

---

## 6. `app.json` for the doctor console

```json
"permissions": { "vault": {
  "standalone":       true,
  "seedFrom":         ["templates/patient/"],
  "openApp":          true,
  "embedAccessToken": true,
  "createKey":        ["patients/"]
}}
```

`embedAccessToken` is **default-deny** and **one-time consent** (not per-create) — embedding the doctor's own token adds no exposure beyond the link itself (whoever has the key already has the vault), and the multi-patient workflow shouldn't prompt on every create. The HUD asks once per (vault, app).

---

## 7. Security (matches the brief)

- **The link is the credential.** It carries the vault key = read+write to content. Surface it as sensitive in your UI (text + QR both).
- **The token is never in the link.** It's in `.vault/access-token.json`, floored from apps, readable only with the vault key. **No exposure beyond the link itself.**
- **`'inherit'` = shared token** (revoke affects all patients); **`'<explicit>'` = independently revocable** if you mint per-patient out-of-band. Per-vault minting via `'new'` is deferred (§5).
- **Token never logged** — bridge telemetry records `writableLink:true`, never the token value.

## 8. Verification checklist (run on dev — browser behaviours not covered by Node tests)

1. **Writable one-click:** doctor `create({accessToken:'inherit', seedFrom, custody:true})` → open the resulting **key-only** link in a fresh tab/incognito → expect the patient vault opens **writable** (you can save), with **no token in the URL**.
2. **Read-only preserved:** create a vault **without** `accessToken` → key-only link opens **read-only**.
3. **Embedded wins:** open a vault that has an embedded token in a browser that also has a stale cached token → the embedded one is used.
4. **Rotate:** `setAccessToken(ref, '<newToken>')` → re-open the link → writes authorise with the new token.
5. **Floor:** confirm an app inside the vault **cannot** read `.vault/access-token.json` via `sg.vfs.read` (should be EPROTECTED).
6. **Grant gate:** an app without `embedAccessToken` calling `create({accessToken:...})` → `EPERM`.

## TL;DR

`create({accessToken:'inherit'})` embeds the doctor's token in `.vault/access-token.json` (floored, encrypted) → the patient's **key-only** link/QR opens **writable**, zero setup, token never in the URL. `setAccessToken(ref, value)` rotates it across one or many vaults. `'new'` (per-vault mint) is deferred to the separate mint workflow. Read-only sharing (no embedded token) is unchanged. Please run the §8 checklist on dev — the Node suite is green but the open-time writable behaviour needs a real browser.
