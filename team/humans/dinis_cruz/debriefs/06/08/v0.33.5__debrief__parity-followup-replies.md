## 1. Closing the loop on §1 — what I did, what I deliberately didn't

### What I added (3 new green assertions)

The `_vault` delegation on `CompositeDataSource` now has a regression-guard unit test in `tests/unit/vault_ui/loader/test__composite_data_source.js`:

```
[suite] CompositeDataSource — identity delegation (`_vault` getter)
  ✓ delegates _vault to _root._vault
  ✓ delegated _vault carries _vaultId
  ✓ returns undefined when root has no _vault (no throw)
```

This is the closest thing to verification I can produce without a browser. The composite is transparent for the identity delegate; nobody else has to find this bug again.

### What I considered and rejected: `sg.app.capabilities`

I weighed adding a `sg.app.capabilities = { vfs:true, fs:true, vault:true, ... }` discovery object on both surfaces. I'm **not** going to ship it, and I want to be explicit about why so you know the recommendation in my review remains "use capability checks" — not "use the capabilities object."

- It would be a **third feature-detection convention** (after `sg.app.context` and `typeof sg.vault?.create === 'function'`). One more thing an app author has to learn and keep straight.
- It would have to be **kept in sync by hand** with the actual surface on both mount paths. Today's gap is two surfaces drifting; adding a capabilities map gives us three things to drift. Bureaucracy I don't want to introduce ahead of the `SgGlobalBuilder` extraction (which makes a capabilities map trivially correct because there's one source).
- The standard pattern works without it:

```js
if (typeof sg.vault?.create === 'function') { /* manager UI */ }
```

This is universally understood, requires zero new API, and stays correct forever — when the §5 follow-up lands and preview gets `sg.vault.*`, capability-checking apps light up automatically with **no code change**.

**Once `SgGlobalBuilder` lands (the §4 follow-up)**, a `capabilities` object becomes cheap and correct because both surfaces derive from one source. Until then, please prefer the capability check over `sg.app.context` for gating UI.

## 3. The recommended consumption pattern (please adopt before building more)

Your debrief noted "the console now keys off `sg.app.context`." Keep that for telemetry/labels if you like, but **gate your manager UI on capabilities**:

```js
// PREFER — forward-compatible, lights up automatically when §5 lands
const canManage = typeof sg.vault?.create === 'function';

// AVOID for gates — locks you into context, needs editing when §5 lands
const canManage = sg.app.context === 'app';
```

The difference becomes important the day the editor preview also gets `sg.vault.*`. Anything checking `context === 'app'` will need a manual edit. Anything checking `typeof sg.vault?.create === 'function'` just starts working.

Likewise for the user message you saw ("host does not expose sg.vault.* yet") — keep it, but key the text off the capability check, not the context. Same logic.
