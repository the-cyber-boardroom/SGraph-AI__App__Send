Two things from your screenshot: (1) the consent banner overflowed the HUD and overlapped the title; (2) the prompt fired on **every** "Open / Share". Both fixed.

---

## 1. HUD layout fix

**Cause:** the consent banner sits in `.hud-center` (`flex:1; justify-content:center`), but the long sentence had no width constraint and the center had no `min-width:0`/`overflow`. So the text overflowed both directions — left over the "Doctor Console — Vault Manager" title, right toward the buttons. That's also why the Allow/Deny buttons appeared shoved over near "Open Vault".

**Fix (`app-hud.js` CSS):**
- `.hud-center { min-width:0; overflow:hidden; }` — the center can now shrink and clips.
- `.hud-consent-text { min-width:0; flex:0 1 auto; overflow:hidden; text-overflow:ellipsis; white-space:nowrap; }` — the message ellipsizes instead of overflowing; Allow/Deny stay put (`flex:0 0 auto`).
- `.hud-right { flex:0 0 auto; }` — the action buttons never get squeezed/overlapped.
- Shortened the message and **dropped the noisy ref** — it used to read *"…receive its full key in 'lk-eff652c425bb'."*; the `lk-…` ref is meaningless to a human, so the location is now only shown for real folder paths (containing `/`). New text: *"This app wants to create a vault and receive its key."*

The banner now stays on one line, ellipsizes if still too long, and never collides with the brand/title or the right-hand buttons.

## 2. Disable / tune the consent prompt from `app.json` (your main ask)

**Why it fired every time:** "Open / Share" calls `sg.vault.getKey(ref)`, which is gated by `vault.createKey` — and `createKey` (like `delete`) is **always-confirm** by design (returning a key is high-privilege, so it never silently caches). For a console you trust, that's friction you don't want.

**New: a per-verb consent policy in `app.json`.** You (the manifest author) decide the friction level:

```json
{
  "permissions": {
    "vault": { "createKey": ["patients/"], "delete": true },
    "consent": {
      "vault.createKey": "auto",     // no prompt — trust the grant
      "vault.delete":    "once"      // prompt once, then remember
    }
  }
}
```

Three levels per verb:

| Value | Behaviour |
|---|---|
| `"always"` | Re-confirm **every time**. Default for `vault.createKey` and `vault.delete`. |
| `"once"` | Prompt **once** per (vault, app, verb), then remember (the default for `create` / `embedAccessToken`). |
| `"auto"` | **No prompt** — rely on the `app.json` grant alone. |

For your trusted console, set `"vault.createKey": "auto"` and the "Open / Share" prompt disappears entirely. If you'd rather keep a single confirmation as a record, use `"once"`.

### Important — what this means and doesn't

- **`consent` only tunes verbs you've already granted.** It does **not** grant anything. Default-deny still applies: an app with no `vault.createKey` grant can't `getKey` no matter what `consent` says.
- **It's the same trust boundary as the grants.** Whoever authors/installs the app's `app.json` is choosing the friction. In your case that's you (the doctor owns the console), so `"auto"` is a deliberate "I trust my own app" choice.
- **Defaults are unchanged.** Any app that doesn't declare `consent` behaves exactly as before — `createKey`/`delete` still always-confirm. This is purely opt-in; nothing else regresses.
- **`"auto"` on `vault.delete` is allowed but think twice** — that makes destructive deletes silent. `"once"` is the safer choice there.

### Recommended `app.json` for the doctor console

```json
{
  "title": "Doctor Console — Vault Manager",
  "permissions": {
    "vault": {
      "standalone":       true,
      "seedFrom":         ["templates/patient/"],
      "openApp":          true,
      "createKey":        ["patients/"],
      "embedAccessToken": true
    },
    "consent": {
      "vault.createKey":        "auto",
      "vault.embedAccessToken": "auto"
    }
  }
}
```

With this, your create + share + open flows run with **zero prompts** (you've pre-trusted them in the manifest), while `vault.delete` — which you didn't list — keeps its always-confirm default.

## 3. Verify on dev

1. **Layout:** trigger any consent (e.g. an app with `vault.createKey` set to `"always"`, then click Share). The banner should sit on one line, ellipsize if long, and not overlap the title or the right-hand buttons.
2. **Auto:** with `"vault.createKey": "auto"` in `app.json`, click "Open / Share" repeatedly → **no prompt**, the link/key is returned each time.
3. **Once:** with `"vault.createKey": "once"`, the first share prompts; subsequent shares in the same vault don't.
4. **Default unchanged:** remove the `consent` block → "Open / Share" prompts every time again (today's behaviour).
5. **No silent grant:** an app with `consent: { "vault.createKey": "auto" }` but **no** `createKey` grant → `getKey` still returns `EPERM`.
