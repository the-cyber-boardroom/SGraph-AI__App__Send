# Debrief — Immutable-block caching (and why it was broken in null-origin iframes)

**Version:** v0.33.5
**Date:** 2026-06-08
**Branch:** `claude/zealous-thompson-yDjFX` (not yet merged)
**Status:** Implemented + tested (JS loader suite + Python route tests). Browser-unverified (cache behaviour needs a real-browser look).

You were right on both points: caching for `-imm-` blocks **was** added before — and it **doesn't work in null-origin iframes**, exactly as you suspected.

---

## What existed (and why you saw re-fetches)

`SGVaultObjectStore` already had a **Cache API** tier (`sg-vault-blocks`) for `-imm-` blocks. But the team had already discovered (comment dated 2026-06-07) that **in a null-origin sandboxed iframe** (`sandbox="allow-scripts"`, no `allow-same-origin`):

> `window.caches` is a defined accessor that THROWS a SecurityError on read … the catch's network-fallback path is the correct sink.

So in the ViV kernel / embedded-app context — which is null-origin — the Cache API throws, the code falls through to the network, and **every imm read hits the server**. `localStorage` and `IndexedDB` are unavailable there too, for the same reason (origin-storage is blocked in a null origin). The cache was effectively a no-op in exactly the contexts vaults are increasingly driven from.

That's the gap behind the re-fetches in your waterfall.

---

## The fix — three tiers, so caching works *everywhere*

### Tier 1 (NEW) — in-memory cache. The one that works in null-origin.
A module-level `Map` in `SGVaultObjectStore` (64 MB byte-capped LRU), keyed `vaultId/filePath`. It needs **no storage API**, so it works in null-origin iframes, normal pages, the kernel — everywhere. Session-scoped (cleared on reload). Content-addressed-safe: an imm objectId is `SHA256(ciphertext)`, so a key can never map to stale bytes. It's checked first (fastest) and also absorbs Cache-API hits.

**Effect:** within a session, the same imm object is fetched **once**, even in the null-origin kernel. (Proven by the test: 3 loads → 1 network read; Node has no `caches`, so the test runs in the exact "sandbox" condition.)

### Tier 2 (unchanged) — Cache API (`sg-vault-blocks`).
Persistent across reloads where available (normal same-origin pages). Bypassed in sandboxes; now promotes its hits into Tier 1.

### Tier 3 (NEW) — browser HTTP cache, for cross-reload persistence in null-origin.
This is the subtle but important one. The **HTTP cache is browser-managed and NOT gated by origin-storage permissions** — it works in null-origin iframes, unlike Cache API/localStorage/IndexedDB. Two changes make it usable for imm objects:

- **Client:** `vaultRead` no longer sends `cache: 'no-store'` for `-imm-` GETs (it still does for mutable refs/indexes — a stale ref would render an old tree).
- **Server:** `GET /api/vault/read/.../<-imm->` now returns `Cache-Control: public, max-age=31536000, immutable`; refs return `Cache-Control: no-store`.

**Effect:** after this deploys, an imm object fetched once is served from the browser HTTP cache on subsequent reloads — **even inside a null-origin iframe**. This is the only tier that survives a reload there.

> Note: Tier 3 helps single-object GETs (`load`). Batch reads (`/api/vault/batch`, POST) aren't HTTP-cacheable — those rely on Tiers 1 & 2.

---

## Answers to your two questions

- **"Why aren't we caching the -imm- files?"** They *were* cached via the Cache API, but that tier is dead in null-origin iframes (and the underlying `vaultRead` sent `no-store`, blocking the HTTP cache too). Fixed with the in-memory tier + HTTP-cache cooperation + the server `immutable` header.
- **"Won't null-origin iframes lack localStorage/IndexedDB?"** Correct — and Cache API too. That's *the* reason the old cache was inert there. The new in-memory tier needs no storage API (works in null-origin), and the HTTP-cache tier is browser-managed (also works in null-origin). Between them, null-origin now caches within a session (Tier 1) and across reloads (Tier 3).

---

## Security / correctness notes

- **Only `-imm-` is cached.** Mutable refs/indexes (`ref-pid-*`, `idx-pid-*`) are never cached at any tier — `no-store` client-side and server-side. A reload always sees the live ref (so the recent reconcile-on-open / branch-index work isn't undermined).
- **Content-addressed = safe.** An imm key maps to exactly one ciphertext forever, so caching can't serve stale data. (Purge/delete of an imm object is the one edge: a force-cached entry could outlive a server delete. We use the browser *default* cache mode, not `force-cache`, so a 404/different response still reaches the client on revalidation; the in-memory tier is session-scoped so it clears on reload.)
- **Zero-knowledge intact.** Cached bytes are ciphertext; decryption still happens client-side. The HTTP cache stores the same encrypted blob the server already serves.

## TL;DR

The imm-block cache existed but was inert in null-origin iframes (Cache API throws there, like localStorage/IndexedDB). Added an in-memory tier (works everywhere, dedups within a session) plus HTTP-cache cooperation (client stops `no-store`-ing imm GETs; server sends `Cache-Control: immutable`) so imm blobs also persist across reloads in null-origin. Refs stay strictly uncached so freshness/reconcile is unaffected. Verify the Network-tab drop on dev.
