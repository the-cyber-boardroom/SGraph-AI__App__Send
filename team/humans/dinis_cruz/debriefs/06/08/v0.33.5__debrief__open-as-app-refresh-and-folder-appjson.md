# Debrief — "Open as App" auto-refresh + per-folder app.json

**Version:** v0.33.5
**Date:** 2026-06-08
**Branch:** `claude/zealous-thompson-yDjFX`
**Status:** Implemented; loader suite green. Browser-unverified (mount/timing path).
**Audience:** the doctor-console / vault-app team

Two connected bugs in the SG/App (`/en-gb/app/`) mount path, both fixed.

---

## Bug 1 — auto-refresh of an "opened-as-app" file breaks

**Repro:** open a non-default HTML "as an app" → it loads → a vault update triggers an auto-pull → the refresh fails (`Entry file not found: tools/release-tester/index.html`). Manually going back to the vault and re-opening "as an app" works again. The refresh works fine for the vault's *default* app.

**Two causes, both in the auto-pull path (`_checkBehind`):**

1. **The deep path was forgotten.** Auto-pull re-ran `_continue(this._appJson)`, but `this._appJson` is the **root** manifest (set once at open) and the deep-link (`sessionStorage['sg-vault-deep-link']` / `_embedDeepLink`) had already been *consumed* on first mount. So `decideMountStrategy` saw no deep path → remounted the **default** app's entry, not the file you opened. (It "worked" for the default app precisely because the default entry *is* the right answer there.)
2. **Sub-trees were left lazy.** `_syncViewToPublishedHead` reloads the tree with every sub-folder unexpanded (`_loaded: false`). The initial mount calls `loadAllSubTrees()`; the auto-pull path didn't. So even when the entry *was* right, `_mountApp`'s file lookup couldn't find `tools/release-tester/index.html` → "Entry file not found".

**Fix:** a new `_remountCurrent()` that the auto-pull calls instead of `_continue`:
- `await loadAllSubTrees()` first (expand the freshly-reloaded tree), then
- replay the **persisted** mount: `_mountStrategy` (`app`/`file`) + `_effectiveAppJson` (the manifest actually mounted) + `_mountedFilePath`. These are recorded in `_continue`/`_mountAppFlow` at mount time, so the refresh re-mounts exactly what you're looking at — the opened file, with its resources — not the root default.

## Bug 2 — "Open as App" used the root app.json, not the folder's

**You asked:** when opening an HTML "as an app" from a sub-folder (e.g. `tools/release-tester/index.html`), load the `app.json` *in that folder*, not the vault-root one.

**Before:** `_readAppJson` only ever read `.vault/app.json` or the root `app.json`. Opening a sub-folder HTML overrode only the *entry* on the **root** manifest — so the folder app ran with the **root's** resources, permissions, host_events, auth, and HUD config. (That's why the screenshot's HUD showed the doctor-console's `write · mkdir · delete-vault` while you were in the release-tester app — root permissions leaking into a different app.)

**Fix:** `_resolveFolderAppJson(deepPath)` — when the opened HTML lives in a folder that has its **own** `app.json`, that manifest takes over:
- **entry** = the file you opened (not `folderJson.entry`).
- **resources** (`css`/`js`) resolve **relative to the folder** (`app.css` → `tools/release-tester/app.css`); a leading-slash path is treated as vault-absolute.
- **permissions / host_events / auth / hud / title** are the folder app's own — via `_setActiveManifest`, which re-derives `_perm`, `_appId`, and `_hostEvents` from the folder manifest. So the folder app is gated by *its* declared policy, and the HUD chip reflects *its* permissions.

A sub-folder with **no** `app.json` falls back to the existing behaviour (root manifest, entry overridden) — unchanged.

The path-resolution is a pure helper, `AppNavHelpers.resolveFolderManifest(folderJson, folder, deepPath)`, unit-tested.

---

## What this means for app authors

- **Each sub-folder app is now a first-class app.** Drop an `app.json` next to your HTML and it governs that app — its own `permissions`, `host_events`, `resources` (folder-relative), `title`. You no longer inherit the root app's grants. **Action:** if a sub-folder app needs `fs.write` (etc.), declare it in *that folder's* `app.json` — it will no longer ride on the root's permissions.
- **Auto-refresh now keeps you on the same app.** A vault update while you're in an opened-as-app file fast-forwards and re-mounts *that* file, not the default app.

## Known limitation (out of scope, flagged)

The `app-shell:ready` event (which configures the HUD `hud.*` and runs the `auth.required` intercept) fires **before** `_continue` resolves the deep path / folder manifest. So a folder app's **`hud` config** and **`auth.required`** don't yet apply on first mount (they'd use the root's). Permissions/host_events/resources/entry/title *do* apply (set in `_setActiveManifest` before mount). Fixing the hud/auth ordering means resolving the folder manifest earlier in `_initWithKey` — a larger reorder, deferred. Not relevant to the two reported bugs.
