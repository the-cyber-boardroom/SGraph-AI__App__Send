# Technical Debrief — A Vault App that creates & manages other vaults (`sg.vault.*`)

**Version:** v0.33.5
**Date:** 2026-06-08
**Branch:** `claude/zealous-thompson-yDjFX` (not yet merged to `dev`)
**Audience:** the agent building the Vault App that creates/manages vaults (and anyone writing such an app)
**Status:** **Implemented + unit-tested (Node). Browser-unverified.** Ship to a test vault before production.

This debrief is self-contained: it tells you what the app can call, what to put in `app.json`, the exact return shapes, the security model, and the gotchas — without reading the source.

---

## 1. What you can now do from inside a Vault App

Your app runs in a sandboxed iframe at `https://send.sgraph.ai/en-gb/app/#<vault-key>`. The host vault's **kernel** makes all the real calls; your app just calls `sg.vault.*` and awaits a result. New/changed surface:

| Call | Returns | What it does |
|---|---|---|
| `sg.vault.create(opts)` | `{ vault_id, ref_id, key? }` | Mint a new vault. Optionally link it into your tree, return its key, and/or seed it from a template. |
| `sg.vault.getKey(ref)` | `{ key }` | Retrieve a previously-custodied vault key (to re-share). Always prompts the user. |
| `sg.vault.openApp(ref, opts)` | `{ opened }` | Launch a managed vault as its own app (new tab / replace page). |
| `sg.vault.list()` | `{ vaults: [...] }` | Roster of the vaults this app manages. |
| `sg.vault.delete(ref)` | `{ deleted, server_teardown }` | Remove a managed vault (see the delete caveat in §6). |
| `sg.vault.unlink(path)` | `{ unlinked }` | (unchanged) remove a `*.link.json` pointer. |

**Breaking change:** `sg.vault.create` no longer takes positional `(path, label)`. It takes a single **opts object** (matching `sg.vault.mount(opts)`). Migrate `create('patients', 'Jane')` → `create({ link:{path:'patients'}, label:'Jane' })`.

## 2. `app.json` — declare your grants (default-deny)

Nothing works unless your manifest grants it. Grants mirror the existing per-verb, path-prefix model.

```json
{
  "title": "Vault Manager",
  "permissions": {
    "vault": {
      "create":     ["patients/"],            // read-through create at these paths
      "createKey":  ["patients/"],            // create+RETURN key here (STRONGER than create)
      "standalone": true,                      // allow create with no parent link (key-return implied)
      "seedFrom":   ["templates/patient/"],    // paths/refs allowed as a seed source
      "openApp":    true,                      // allow sg.vault.openApp
      "delete":     true                       // allow sg.vault.delete
    }
  }
}
```

Rules to internalise:
- **`createKey` is strictly stronger than `create` and is never implied by it.** A plain `create` grant returns NO key. To get a key back you need `createKey` (for linked creates) or `standalone` (for unlinked creates).
- `standalone`, `openApp`, `delete` are **booleans**. `create`, `createKey`, `seedFrom` are **path-prefix lists** (trailing `/` = prefix) or `true` for "anywhere".
- Absent grant → the call rejects with `Permission denied` (`EPERM`).

## 3. `sg.vault.create(opts)` — the full contract

```js
const result = await sg.vault.create({
  label:     "Patient — Jane Doe",   // vault display name
  link:      { path: "patients" },    // wire a read-through link here; OMIT for standalone
  returnKey: false,                    // true → return the raw key (needs createKey/standalone)
  custody:   true,                     // true (default) → kernel stores the key owner-tier
  seedFrom:  "self:templates/patient"  // optional template copy (see §5)
});
```

Result by combination:

| `returnKey` | `link` | result | grant needed |
|---|---|---|---|
| `false` | `{path}` | `{ vault_id, ref_id, ref_file_id }` (read-through, no key) | `create` |
| `true`  | `{path}` | `{ vault_id, ref_id, ref_file_id, key }` | `create` + `createKey` |
| `true`  | omitted | `{ vault_id, ref_id, key }` (standalone) | `standalone` |
| `false` | omitted | rejects `EINVAL` **unless** `custody:true` (then `{ vault_id, ref_id }` with the key held kernel-side) | `standalone` |

### The returned `key` is the **composed, openable** form

`key` is `"<passphrase>:<vault_id>"` — e.g. `"k3x9q…:ab12cd34"`. This is exactly what `SGVault.open` / the `/en-gb/app/#<key>` route expects. **Do not** try to reconstruct a key from `vault_id` alone, and don't expect a `word-word-1234` simple token — created vaults are always high-entropy (the simple-token shape is never minted; it has a known brute-force weakness).

### `custody` — let the kernel hold the key for you

With `custody:true` (the default), the kernel seals the new vault's key into an **owner-tier secret store** (`.vault/owner/secrets/<ref_id>.json`) inside *your* vault. You then refer to the managed vault by its `ref_id` and never have to store the raw key yourself. Use `returnKey:true` **additionally** only when you need the raw string to hand to someone out-of-band.

## 4. The management lifecycle (recommended pattern)

```js
// 1. Create a writable, seeded vault; let the kernel custody the key.
const { vault_id, ref_id } = await sg.vault.create({
  label:    "Patient — Jane Doe",
  custody:  true,                       // key sealed kernel-side
  seedFrom: "self:templates/patient"    // pre-populate from your template folder
});                                      // grants: standalone (or create+createKey), seedFrom

// 2. Show your roster (rebuild UI after reload).
const { vaults } = await sg.vault.list();
//  vaults = [{ ref_id, vault_id, label, tier:'rw'|'ro' }, ...]

// 3. Open one as its own app (no key handling on your side).
await sg.vault.openApp(ref_id, { target: 'tab' });   // grant: openApp

// 4. Re-share it out-of-band (prompts the user every time).
const { key } = await sg.vault.getKey(ref_id);        // grant: createKey

// 5. Remove it.
await sg.vault.delete(ref_id);                         // grant: delete  (see §6 caveat)
```

`tier` in the roster: `rw` = the kernel holds the key (you can `getKey`/`openApp`/`delete` it); `ro` = a read-through link only (no key on file).

---

## 5. `seedFrom` — instantiate from a template

Copies a whole tree (files + `app.json`) into the new vault at create time.

- `seedFrom: "self:templates/patient"` — a folder in **your** vault. Needs `seedFrom:["templates/patient/"]`.
- `seedFrom: "<ref_id>"` — a vault you manage. Needs the ref in your `seedFrom` grant.
- `seedFrom: "<raw key>"` (contains `:`) — any vault key you hold. **No grant needed** — possession is authority.

The copy **never** includes `.vault/**` (owner secrets, link records) — that's a hard security floor. Templates live in normal folders.

---

## 6. Security model — read this

- **Owner tier vs read tier.** Managed-vault keys are sealed under a key derived from *your* vault's `write_key`. A read-only opener of your vault (RO token, `write_key = null`) **cannot** decrypt them — `getKey`/`list` will simply not surface the keys. Only a writable owner session can manage vaults.
- **You are a key-holding app, by design.** This is the special case: an app that manages other vaults necessarily can obtain their keys. With `custody`, keys stay sealed kernel-side rather than in your plaintext app-data — prefer that. Only `getKey`/`returnKey` expose the raw string, and both **always prompt the user** (no silent consent cache).
- **Keys are never logged.** The bridge telemetry / debug pane records `returnedKey:true`, never the value. Don't `console.log` keys in your own app either.
- **Consent.** Key-returning create, `getKey`, and `delete` re-confirm on the HUD every time. Plain (no-key) create prompts once and caches.

## 7. `delete` caveat — partial today

`sg.vault.delete(ref)` **works for custody cleanup** (removes the sealed key record + any link) and retrieves the key kernel-side to authorise teardown — **but the server-side vault destroy depends on a `SGVault.destroy()` endpoint that may not exist yet.** The result tells you:

```js
const { deleted, server_teardown } = await sg.vault.delete(ref_id);
// deleted: true             — local custody record + link removed
// server_teardown: false    — the server vault is RETAINED (endpoint pending)
```

Until `server_teardown:true`, treat `delete` as "stop managing this vault" rather than "destroy its data on the server". (Tracked in the dev plan §16 server dependency.)

## 8. Errors you'll see

| Code / message | Meaning | Fix |
|---|---|---|
| `Permission denied` (`EPERM`) | grant missing for the verb/path | add the grant to `app.json` |
| `Permission denied (createKey)` | you asked `returnKey:true` with only a `create` grant | add `createKey` (or `standalone`) |
| `Consent declined` (`ECONSENT`) | user clicked "deny" on the HUD prompt | re-ask / respect the choice |
| `Read-only vault` (`EREADONLY`) | the host vault was opened read-only | open it writable to manage vaults |
| `unreachable vault` (`EINVAL`) | create with no link, no returnKey, no custody | set at least one of them |
| `no key on file` (`ENOKEY`) | `getKey`/`delete` on a ref with no custodied key | the vault was created `custody:false` — you hold the key |
| `embed target deferred` (`ENOTIMPL`) | `openApp(..., {target:'embed'})` | use `'tab'` or `'replace'` for now |

## 9. What is NOT available yet

- **`sg.vault.mount({ mode:'rw' })`** — writable cross-vault mount. Not implemented; tracked in `team/comms/briefs/06/08/v0.33.5__brief__vault-writable-mount.md`. To populate another vault, use `seedFrom` at create time, or `openApp` + in-app writes.
- **`openApp(..., {target:'embed'})`** — embedding a managed vault as an inline iframe. Deferred (needs the embed-loader relay).
- **True server-side `delete`** — see §7.

## 10. Minimal copy-paste starting point

`app.json`:
```json
{ "title": "Vault Manager",
  "permissions": { "vault": {
    "standalone": true,
    "seedFrom":   ["templates/"],
    "openApp":    true,
    "delete":     true
  }}}
```

app code:
```js
async function newManagedVault(name) {
  const { ref_id } = await sg.vault.create({ label: name, custody: true, seedFrom: "self:templates/base" });
  return ref_id;                          // store the ref in your roster file
}
async function roster()      { return (await sg.vault.list()).vaults; }
async function open(ref)     { return sg.vault.openApp(ref, { target: 'tab' }); }
async function share(ref)    { return (await sg.vault.getKey(ref)).key; }   // prompts the user
```
