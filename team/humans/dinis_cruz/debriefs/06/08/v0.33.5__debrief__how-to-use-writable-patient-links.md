---

## 1. What you can do now

```
Doctor app          Patient (their phone, their browser, no setup)
  │
  ├─ sg.vault.create({ accessToken:'inherit', ... })
  │     ↓
  ├─ stores key kernel-side (owner-secret tier)
  ├─ embeds doctor's backend token IN the new vault (.vault/access-token.json)
  ├─ pushes the new vault
  │
  ├─ sg.vault.getKey(ref)  → { key }
  ├─ render link as text + QR:   https://dev.vault.sgraph.ai/#<key>
  │
  └─ ───── hand to patient out-of-band ─────→ click / scan
                                                ↓
                                              vault opens WRITABLE
                                              (key decrypts, embedded token authorises writes)
                                              token NEVER in the URL
```

**One link. One scan. Writable. Zero patient setup.**

A vault without an embedded token still opens **read-only** from a key-only link — your read-only sharing flow is unchanged.

## 2. The doctor console's `app.json`

```json
{
  "title": "Doctor Console — Vault Manager",
  "permissions": {
    "vault": {
      "standalone":       true,
      "seedFrom":         ["templates/patient/"],
      "openApp":          true,
      "createKey":        ["patients/"],
      "embedAccessToken": true
    }
  }
}
```

`embedAccessToken` is **default-deny** and **one-time consent**. You'll see the HUD prompt once per vault (per app id) — *"App ‹id› wants to use vault.embedAccessToken"* — then it's silent for the rest of your roster work.

## 3. The doctor-side flow — copy-paste

### 3.1 Create a patient vault with a writable link

```js
async function createPatient(label) {
  const res = await sg.vault.create({
    label,
    custody:     true,                              // kernel holds the patient's vault key
    seedFrom:    'self:templates/patient',          // copy your template files into the new vault
    accessToken: 'inherit'                           // embed YOUR (doctor's) current backend token
  });
  // res = { vault_id, ref_id, writable_link: true }
  return res;   // store res.ref_id in your roster file
}
```

Returned `writable_link: true` confirms the patient's key-only link will open writable. You'll see it set whenever `accessToken` was honoured.

### 3.2 Get the patient's link (text + QR)

```js
async function patientLink(refId) {
  const { key } = await sg.vault.getKey(refId);              // always-confirm consent
  const url     = 'https://dev.vault.sgraph.ai/#' + key;     // or your env's vault host
  return url;
}

// Render the link + a QR code:
const link = await patientLink(roster[i].ref_id);
linkEl.textContent = link;
linkEl.dataset.sensitive = 'true';                            // label it sensitive
// (use whatever QR lib you already have — e.g. qrcode.js — encode `link`)
```

The string is the **vault key**: `<passphrase>:<vault_id>`. Mark it sensitive in your UI — anyone with the link has read+write to the patient vault.

### 3.3 Open a patient vault in a new tab (no key handling on your side)

```js
async function openPatient(refId) {
  await sg.vault.openApp(refId, { target: 'tab' });
  // kernel resolves the key from the owner-secret store and navigates the new tab
  // to https://dev.vault.sgraph.ai/#<key>  — the same URL you'd hand the patient.
}
```

## 4. Rotating the token across your whole roster

When the doctor's backend token changes, every patient vault that has `accessToken:'inherit'` from the old token needs the new one written in.

```js
async function rotateAllPatients() {
  const { vaults } = await sg.vault.list();        // your custodied roster
  let updated = 0, failed = [];
  for (const v of vaults) {
    if (v.tier !== 'rw') continue;                  // skip read-through links (no key on file)
    try {
      await sg.vault.setAccessToken(v.ref_id, 'inherit');   // re-embed the doctor's CURRENT token
      updated++;
    } catch (e) {
      failed.push({ ref_id: v.ref_id, label: v.label, error: e.message });
    }
  }
  return { updated, failed };
}
```

You'll see the consent prompt for `vault.embedAccessToken` once per session (it's cached), then the loop runs quietly. If a patient's token is being mismanaged (e.g. expired), `setAccessToken(ref, '<newToken>')` lets you embed a specific value instead.

## 5. What the patient sees

1. Receives the link/QR (chat, email, in-person).
2. Clicks the link or scans the QR.
3. Vault opens. If you used `seedFrom:'self:templates/patient'`, they see the template you authored (e.g. patient app's `index.html`).
4. They can **write** — `sg.fs.write`/`sg.fs.delete` calls go through; the auto-push from the recent sync-parity commit pushes within ~2.5s.

No prompt for an access key. No setup. No localStorage juggling.

---

## 6. Error codes you'll see (and what they mean)

| Code | Where | Meaning | Fix |
|---|---|---|---|
| `EPERM` (`embedAccessToken`) | `create` / `setAccessToken` | `app.json` doesn't grant `vault.embedAccessToken` | Add the grant |
| `ECONSENT` | `create` / `setAccessToken` | User clicked Deny on the HUD consent | Re-request / respect |
| `ENOTOKEN` | `'inherit'` resolution | The doctor's own vault has no access token to inherit | Your session lacks an access token — open the doctor vault with a write key first |
| `ENOTIMPL` | `accessToken:'new'` | The per-vault mint endpoint uses a separate API-key workflow we haven't wired | Use `'inherit'` or pass an explicit token string |
| `ENOKEY` | `setAccessToken(ref, ...)` | No custodied key on file for that `ref` | The vault was created `custody:false`; you'll need the raw key |
| `EREADONLY` | `setAccessToken` writing | The target vault opened read-only | Make sure the key you're using carries write authority |
| `EINVAL` | `setAccessToken` | `value` is empty / null | Pass `'inherit'` or a non-empty token string |

## 7. Verification checklist — please run this on dev

These exercise the parts the Node tests can't cover. Each step is a 30-second click:

1. **Writable one-click.** From your doctor console: `create({accessToken:'inherit', seedFrom:'self:templates/patient', custody:true})`. Get the link via `getKey(ref)`. Open it in a **fresh tab or incognito window** (no doctor cookies). Expected: the patient vault opens, you can save a change to a file, and the URL contains **only** `passphrase:vault_id` — no token, no other query params.

2. **Read-only preserved.** Create a vault **without** `accessToken`. Open its key-only link. Expected: opens **read-only** (no write actions work).

3. **Embedded wins over cache.** In a tab that has a stale `localStorage['sg-access-key:<vaultId>']` from a previous session, open a patient vault whose `.vault/access-token.json` has a *different* token. Expected: the **embedded** token is what authorises writes (you can verify in the Network tab — `x-sgraph-access-token` header value should match the embedded one).

4. **Rotate.** Call `setAccessToken(ref, '<a-new-token>')`. Close and re-open the same patient link. Expected: writes now authorise with the new token (Network tab confirms).

5. **Floor enforced.** Inside a patient vault app, try `await sg.vfs.read('.vault/access-token.json')`. Expected: `EPROTECTED` error. The raw token must not be reachable from the app sandbox.

6. **Permission gate.** From an app whose `app.json` does **not** grant `vault.embedAccessToken`, call `sg.vault.create({accessToken:'inherit', ...})`. Expected: `EPERM`.

If 1, 2, 5, and 6 pass, the feature is doing what the brief asked for.

## 8. Common pitfalls

- **"My patient link opens read-only."** Check the create response — `res.writable_link` should be `true`. If false, either you didn't pass `accessToken`, or `'inherit'` failed (`ENOTOKEN`) because your own doctor session has no token wired (a vault opened with no access key). Make sure the doctor vault was opened with a token (check `sg.app.writable === true` in the doctor console iframe).
- **"Link is too long for QR."** Vault keys are ~30–40 chars; the full URL is ~70. Any common QR lib handles this at error-correction level M without trouble. If you generate it at the highest correction level (H) and a low pixel density, you may get oversized blocks — pick M for most cases.
- **"Why does the patient see template files but no doctor data?"** That's intentional — `seedFrom` copies a **template** at create time; it doesn't auto-share doctor content. The patient writes to **their own** vault. Cross-vault content sharing is a separate feature (mounts / openApp).
- **"What if the doctor's token gets revoked?"** All patient vaults using `'inherit'` lose write capability. Run §4's rotate loop with a new token. (If you want per-patient independence, mint your own tokens out-of-band and embed via `'<explicit>'` per patient — they're then independently revocable.)
- **"I want the patient to see the link work but NOT be able to share it onward."** You can't — the link is a credential. If they forward it, the recipient has full access. Treat the link the way you'd treat a password.

---

## 9. What's NOT in this round (so you don't go hunting)

- **`accessToken:'new'`** (per-vault mint) → `ENOTIMPL`. The mint endpoint exists but uses a separate API-key workflow we haven't integrated. Use `'inherit'` or `'<explicit>'`.
- **Embedding via `openApp(..., {target:'embed'})`** still returns `ENOTIMPL` (the two-hop embed loader work is tracked separately).
- **Server-side `vault.delete` teardown** still reports `server_teardown:false` until the `SGVault.destroy()` endpoint ships.
- **Per-vault token discovery from your roster.** You can't ask "which token is embedded in patient X's vault?" without opening it. If you need this, write a small "audit" routine that opens each, reads the file, closes — but consider whether you need it (the doctor knows what they embedded).

## 10. Minimal end-to-end demo

If you want to prove the whole loop in 60 seconds:

```js
// In your doctor console (with the app.json from §2):
const create = await sg.vault.create({
  label:       'Demo Patient',
  custody:     true,
  seedFrom:    'self:templates/patient',
  accessToken: 'inherit'
});
console.log('writable_link?', create.writable_link);          // should be true

const { key } = await sg.vault.getKey(create.ref_id);
const link    = 'https://dev.vault.sgraph.ai/#' + key;
console.log('PATIENT LINK:', link);

// Copy → paste into a fresh incognito tab → vault opens writable.
// In that tab, open devtools and try:  await sg.fs.write('test.txt', 'hello');
// Expected: succeeds, auto-pushes within ~3s.
```

If that flow works end-to-end, you're done. Build the QR around it.
