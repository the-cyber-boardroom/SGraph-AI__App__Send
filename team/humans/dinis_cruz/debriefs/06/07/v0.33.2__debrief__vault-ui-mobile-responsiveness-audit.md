## Headline findings

The `/vault` UI is, by construction, a **desktop-only IDE-style three-pane workspace**:

1. **No `@media` queries anywhere in the active `/vault` code.** The only responsive rules in the entire `_common/` tree are in `vault-app.css` (the `/app` route, which is the one that works) and the legacy `vault-browser.css` (not loaded by the current shell).
2. **`<sg-layout>` is configured with a fixed `0.20 / 0.80` row split** and the Files panel is `locked: true`. On a 360 px phone the file tree gets ~60 px wide and the user cannot reclaim that space.
3. **The resize drag handle is desktop-only.** No `touchstart` / `pointerdown` listeners in the vault UI, no `touch-action: none` on containers, and `<sg-layout>` itself is loaded from an external CDN (`https://dev.tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js`) so its touch story has to be confirmed upstream.
4. **The header packs 7 controls** (brand + vault-name + Read-only badge + Upload + Debug + raw + Lock + version) in a `flex` row with no `wrap`. On phones this overflows immediately.
5. **The inline auth banner, per-file action bar, settings panel, and SGit view all assume desktop widths** — `max-width: 640px`, `white-space: nowrap`, horizontally-stacked button rows, etc.
6. **The per-file action bar is built with inline `style.cssText`** — adding stylesheet `@media` rules alone won't fix it; this needs a mechanical refactor to classes first.

Both symptoms Dinis named are explained by the same root cause: there is currently **no mobile design contract** for `/vault`. The desktop layout is being re-rendered into less space, not redesigned for it.

## Open questions for you (collected from both reviews)

1. **Floor breakpoint** — smallest viewport we commit to? 320 px, 360 px, or 600 px?
2. **Scope** — should mobile have the full vault surface (upload + share + settings + SGit + debug) or a deliberately reduced one (browse + unlock + share-receive)?
3. **Resize-on-touch** — important to keep, or are we happy collapsing to single-column on phones (which removes the resize gesture entirely)?
4. **Tablet (601-1024 px)** — design a dedicated layout, or jump straight phone ↔ desktop?
5. **IFD timeline** — Phase A (CSS-only cheap wins, ~1-2 days) would close the "inaccessible parts" half of the brief. Ship as `v0.1.5` first, or wait until the full mobile pass is ready?
6. **Visual feel on mobile** — same Aurora desktop chrome carried down, or a more "app-like" treatment (sheets, rounded cards, hairline rules)?
