## 4 · Verified facts — do not re-derive these

Each was established by running code, not by reading it.

- **The auth header is `x-sgraph-access-token`.** `x-sgraph-send-access-token` returns 401. The constant is named `HEADER__SGRAPH_SEND__ACCESS_TOKEN`; its value has no `send`. The reality doc was corrected.
- **The CDN rewrites only 403.** API 403 → `404` + `text/html`. A genuine route miss → `404` + JSON. So an HTML body, not the status, is the tell. The client raises `EEDGE` for it.
- **`host_events` is an object allowlist with explicit `true`.** An array parses to an empty set with no error, so an app following the old docs never received an event. Docs and tests fixed.
- **`/d/{transfer_id}`, the `download_url` returned by `complete`, is a 404.** Build the share link yourself: `https://send.sgraph.ai/en-gb/download/#{id}/{key}`.
- **The `file_id` traversal is disk-mode only.** On S3 and memory, `../` is a literal key segment.
- **The enum key is a function of the read key**: `SHA256("sg-inbox-enum:" ‖ read_key)`. Publishing a vault's read key publishes its lane enumeration. Documented in `AUTHORING.md`.
- **The append `inbox` field is the raw append token**, not its hash, and the folder is named by the raw token.
- **Only `sg.append.write` crosses vaults.** `list`, `fetch` and `markProcessed` are bound to the open vault, or to a *declared* mount's child when given a `path`.
- **A single-use password share is friendly token + `max_downloads: 1` + `auto_delete: true`.** All shipped.
- **An OAuth gate cannot release the key**, because the server never has it. It can only gate the ciphertext.
- **One unit test fails only in credentialed containers:** `test_Send__Config::test__has_aws_credentials__false_by_default` (the container leaks `AWS_*` variables). Not a code defect.

## 6 · The original inputs

Full text is in the zip under `inputs/`. Summaries:

- **Games-vault agent, debrief 1 (6 Sep):** a published vault app could not write to an append lane; direct `fetch` was blocked by the frame's CSP and `sg.append.write` returned "Permission denied". Four findings plus "bridge errors have no code". Our review: two were misdiagnosed (the denial was a manifest problem, not a read-only gate; and `permissions.network` exists), two were real (`inbox` is the raw token; error codes were dropped crossing the bridge).
- **Games-vault agent, reply (7 Sep):** `permissions.network` was the one-line fix and both paths now work. Two items left: a wrong token answers 404 with an HTML page instead of 403, and `sg.append.list` 404s. Both turned out to be the CDN rewriting 403s, not the API.
- **Voice memo (26 Sep), verbatim:** "This is a quick proof, brief for the creation, and see if we can actually add support for the agents to easily create single-use password tokens, where we can basically use the shared functionality, which I believe already is working for SGT for the SG send, and we map that out, and also have a have a sprint where we do a research, which is can we add to SG send the feature of using OAuth as a protection mechanism? That'll be quite powerful. Where imagine I'll be able to say, I'm going to send this to somebody, and only if you've been authenticated in OAuth, and that's easy to do, right? Because it's just a simple authorization, and we already have a version of that, and we've done that before, so we can create an app for that, and then, you know, the user can only can decrypt that if it comes from that thing. So we need to think about what would be the way to implement that on the server side, especially because we don't have secrets. So we need to figure out a way to do that. But the logic would be to use OAuth Amazon authentication before you even see the secret."
- **CLI team, history-integrity brief (7 Oct):** proposes verifying commit signatures, a client-side ref monotonicity check, and 128-bit object ids as an opt-in per-vault "format 2". Asks the server and web UI three questions before designing the parts that touch them.
