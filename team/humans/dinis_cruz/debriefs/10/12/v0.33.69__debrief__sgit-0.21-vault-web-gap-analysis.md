## Executive summary (as written before the implementation)

The sgit CLI shipped 0.18.0 → 0.21.0 between 7 and 10 October and now carries a format gate, 128-bit object ids, a merged branch index, commit-signature verification with a `signatures-required` policy, rewind detection and signed tags. The sgit.ai site states publicly that the web UI cannot sign, cannot write 32-hex ids, overwrites the index and pushes blind. All four are true of our `v0.2.3` code.

The gap is closable with Web Crypto alone and with no server change: every interop vector the CLI published (object ids, deterministic tree IV, canonical JCS signing bytes, P-256 signatures) reproduces byte-for-byte against this repo's own `SGVaultObjectStore` and `SGSendCrypto`, which is now a test in the unit suite. The plan is five items in order: format gate + format-aware ids, index merge with compare-and-swap, per-device signing key + signed `commit_v1` + verification in the SGit view, ref monotonicity + CAS publish in the shells, deterministic trees. Items 1–2 are about a day and unblock the rest; item 3 (signed commits) is three to four days.

Nothing was shipped to the UI in this session; this is the assessment and the plan, plus the reality document brought up to date so nobody describes web signing as existing.

## Decisions (review §6) — taken as recommended, since the brief was "match the CLI 100%"

1. Tree plaintext: the CLI's Python bytes (done; byte parity proven). 2. Sandboxed kernels: unsigned for now, `options.signer` is the hook for a parent-held key. 3. Verification chips always on; refusals only under `signatures-required`. 4. Shipped in the order 1+2 → 3 → 4 → 5.

## Decisions needed from you (as originally written)

1. Tree plaintext: match the CLI's Python bytes now (recommended) or agree JCS-for-trees behind a format bump.
2. Signing in sandboxed child kernels: parent signs over the secure channel (recommended design) or unsigned in the sandbox for the first ship.
3. Verification on by default in the SGit view; refusals only under `signatures-required` (recommended).
4. Ship order 1+2 → 3 → 4 → 5, or pull item 4 (rewind detection, CAS publish) ahead of item 3 if CLI users seeing REWOUND after browser saves is the immediate pain.
