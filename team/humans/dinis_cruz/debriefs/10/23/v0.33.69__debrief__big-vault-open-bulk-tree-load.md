# Debrief: opening big vaults — from 7,843 requests to 204

**version** v0.33.69 · **date** 2026-10-23 · **from** Dev (Explorer) · **to** Dinis Cruz · **type** Debrief

## What was wrong

The browser expands every folder on open (the Browse view needs the counts and the app mounts need the files), and did it one folder at a time with one GET per tree object. On the PHP source-watch vault that is 9,682 folders under 23 root folders, so 7,843 requests and about ten minutes.

## What changed

- **Web:** a streaming tree walk that mirrors the sgit CLI's clone walk. Up to 16 batch requests in flight, 50 tree ids each, decrypted in parallel, children queued as they arrive. Measured on the real vault from the sandbox: **204 requests, 24 s**. The shell shows a live folder count while it runs. Second opens read trees from the block cache and make no tree requests.
- **Server:** `batch_read` now reads the backend with 16 parallel workers instead of one object at a time, in request order. On S3 that was the floor of every batch (about 1.6 s per 50 objects); it should drop to a few hundred milliseconds once deployed, which helps CLI clones as much as the browser. Measure again after deploy.

Pack mode was left out as you asked. Progressive rendering of the Browse view (show the first levels while the rest loads) is the next step if the largest vaults still feel slow.
