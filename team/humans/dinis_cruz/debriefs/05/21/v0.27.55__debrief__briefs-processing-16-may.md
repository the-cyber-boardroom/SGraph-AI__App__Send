## Executive Summary

Day 66 is the most architecturally consequential brief batch since the vault-collections + vaults-of-vaults batch on 14 May. Three structural patterns crystallised that had been implicit for weeks:

1. **The vault-as-communication-medium pattern** — agents communicate through shared vaults, not direct calls. Surfaced independently in three separate briefs (multi-cloud, backup, DNS registry). Three briefs converging on the same answer is not coincidence; it is architecture.

2. **The serverless framing for agents** — SG/Compute is not a Lambda alternative. It is a serverless environment specifically for agentic workloads. The parallel-request observation is the sharpest technical point: Lambda cold-starts each concurrent slot; containers handle N parallel requests with one cold-start. This matters for agentic workloads that make many parallel tool calls.

3. **The JS API as both production surface and test surface** — the vault testing framework's core insight is that the same JS API used by normal vault operations is the right surface for all four test layers. One API, no parallel surfaces, tests that exercise real code paths.

Two important **corrections** were documented:
- CNAME-to-wildcard DNS does not work reliably across resolvers (RFC 4592) — the DNS registry must use A records
- SG Mail is NOT email infrastructure — it is a vault client over EML files (this makes the project tractable)
