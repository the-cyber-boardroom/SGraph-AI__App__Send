## What Was Delivered

### The JS API Layer (Phase 1)

SG/Vault v0.2.3 adds a clean programmatic surface over the existing vault internals. Any
documentation agent or QA script can now drive the vault **deterministically** — opening,
navigating, and reading state — without fragile DOM automation.

**Before this work:** Driving the vault from outside required clicking through tabs, polling for
render-complete, and hoping the layout didn't change. Every CSS tweak could break automation.

**After this work:** One call to `await window.__tool.waitForReady()`, then `await
window.__tool.navigateTo({ tab: 'README.md' })`, and the agent knows with certainty that
content has rendered. Screenshot immediately. No guessing.

### API Surface (Phase 1)

```js
// Single-tool page
await window.__tool.waitForReady();         // waits for vault open + browse mounted
const state = window.__tool.getState();    // { vaultId, title, decrypted, syncState, activeView, openTabs }
await window.__tool.navigateTo({ tab: 'README.md' }); // resolves AFTER render (iframe-aware)
const skills = window.__tool.getSkills(); // { human, browser, api } paths

// Registry
window.__tool_registry.find('vault')       // always works, single or multi-tool page
```

Events on `window`: `tool:ready`, `tool:state-changed`, `vault:opened`, `vault:locked`,
`vault:navigation-complete`.

Dev panel: click **Debug** in vault header → **Tool API** tab → `<sg-tool-api-explorer>`,
`<sg-tool-api-console>`, `<sg-tool-api-manifest>`.

## Why It's Parked

The `dev` branch has landed a **vault-loader refactoring** (`vault-loader-routing.js` etc.) that
changes the routing architecture of the vault shell. This creates a conflict with our `index.html`
since v0.2.3 was built on the pre-refactor v0.2.2 base.

The JS API code itself (`vault-tool-api.js`, SKILL files, manifest) is **completely
independent** of the routing layer and will survive the refactoring unchanged. Only `index.html`
needs to be rebased on the new vault-loader base when that work is ready.

**Nothing is lost.** The code is on the branch, architect-approved, with a detailed reality doc
entry and this debrief. Picking it back up is a half-day rebase of `index.html`.

Half a day. Unblocks cross-tool agentic flows (`chat` reading vault files for grounding).

### Sync event wiring (Nit 5 from architect review)

`tool:state-changed` doesn't yet fire on push/pull sync transitions. Wire it when the
broadcast event bus (Ticket 08) lands — `vault:vault-pushed` and `vault:vault-pulled` events
will subsume this naturally.

### Vault-level `navigateTo` event signal (plan doc §3)

Current implementation uses polling. Phase 1.1: patch `send-browse._renderFileContent` to
`window.dispatchEvent(new CustomEvent('vault:section-rendered', ...))` so `navigateTo`
can resolve on the event rather than polling. Cleaner, more reliable, especially for
slow-loading large HTML apps.

## Key Decisions Made

| Decision | Rationale |
|----------|-----------|
| Separate `vault-tool-api.js` module (not embedded in vault-shell.js) | vault-shell.js is a non-module IIFE; SgToolApi ships as ES module. Clean separation, follows video-creator pattern. |
| `slug: 'vault'`, no `window.__vault` | Standard registry convention. Agents use `window.__tool` or `window.__tool_registry.find('vault')`. Dev panel auto-binds. |
| Polling for render-complete in `navigateTo` | No emit signal exists today. Iframe-aware (waits for `contentDocument.readyState === 'complete'`). Phase 1.1 to replace with `vault:section-rendered` event. |
| Phase 1 only (4 methods) | Document agents need `waitForReady` + `navigateTo` to take screenshots. Ship small, get real-world usage before Phase 2/3. |
| `window.sgraphVault.events` untouched | Backward compat. New SgToolApi layer is additive only. Existing internal listeners keep working. |
