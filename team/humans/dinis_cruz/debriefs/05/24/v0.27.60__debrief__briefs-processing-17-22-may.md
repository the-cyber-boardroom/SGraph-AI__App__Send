## Two Things That Matter Most

### 1. SG/Sentinel is ready to build — but needs three pre-conditions

The SG/Sentinel MVP has a scoped 10-step implementation sequence. Before coding starts, three items need to be resolved:

1. **Fast-track redesign memo** (voice memo from the project lead) — the most important memo. Fast-track was reconceived in the tabletop as zero-trust acceleration (skip expensive identity establishment, never skip authorisation). The implementation of "skip identity establishment" needs the project lead's own framing before the MVP commits to the fingerprint/signed-token design.

2. **Auth-outcomes API design** — the tabletop found that brute-force detection requires the application to report authentication decisions back to Sentinel. This is a new coupling (application → Sentinel) that needs an API spec before implementation.

3. **Unified graph data model sketch** — a one-page entity type list. The three-graphs-as-one architecture is the right direction; a sketch before coding prevents regret.

Once these three items exist (estimated 3-5 days), the MVP is a 5-6 week implementation.

### 2. The TUI API is the TUI API for SG/Sentinel too

The TUI API (Day 67) and SG/Sentinel's nine TUI operator surfaces (Day 68) arrive together. This is not a coincidence. The SG/Sentinel TUI mockups are the natural first implementation of the TUI API. Build them together; the nine surfaces prove the TUI API works and deliver the operational visibility the project lead wants now.
