# Debrief — Markdown rendering: bug fixes, refactor, and wire-up

**Date:** 2026-05-12
**Branch:** `claude/vault-ui-architecture-review-6nTQZ`
**Session focus:** Markdown rendering pipeline — fix two production bugs, build a refactored library in isolation, validate it with a harness, then wire it into the vault.

---

## Executive summary

Two markdown bugs were reported in the vault this session:

1. Numbered/bulleted lists with multi-line continuations split into an
   orphaned `<p>` instead of staying inside the `<li>`.
2. Clicking "Edit" on a `*.md` file populated the textarea with the
   contents of the first code block in the document, not the markdown
   source.

Both are fixed. To stop debugging the same pipeline a third time, the
markdown parser (plus the previously-overlay-only fixes) was lifted into
a standalone library at `_common/lib/markdown/`, exercised by a 40-test
harness page at `/en-gb/vault/markdown`, and then wired into the main
vault — cutting the runtime dependency on the `dev.send.sgraph.ai` CDN
for markdown rendering.

The architect review for the wider refactor is at
[v0.27.18__architect-review__markdown-rendering-pipeline.md](../../../../../roles/architect/reviews/05/11/v0.27.18__architect-review__markdown-rendering-pipeline.md);
this debrief is the operational record of what landed and what remains.

## Key decisions

1. **Standalone parser ships inside the vault tree.** The vault no
   longer fetches `markdown-parser.js` from `https://dev.send.sgraph.ai`.
   The list-continuation fix is visible without a CDN redeploy and the
   vault is one runtime dependency lighter.
2. **The v0.3.1 overlay is absorbed**, not preserved. The new parser
   ships BRW-007 (`<img>` not `[image: alt]`), BRW-008 (relative file
   links), BRW-018 (Discourse dimensions), BRW-020 (`data-md-src`) and
   BRW-021 (code-span guard) as base behaviour, with one file to read
   instead of two.
3. **Refactor first, wire later.** A test harness was built and the
   refactored module exercised by 40 unit tests before any production
   wiring. This was your suggestion — the value showed up immediately
   in catching one regression in the renderer's image rewrite logic
   before it reached production code paths.
4. **`MarkdownRenderer.mount()` is loaded but not yet called.** The
   thin DOM-layer module is shipped to the page so a future single-line
   change in `send-browse.js` and `vault-browse-edit.js` can switch
   to it. Production rendering still flows through the existing
   `send-browse.js → MarkdownParser.parse() → innerHTML` path. This is
   the lowest-risk path; the migration happens when we want to retire
   the DOM-querying patterns in `vault-browse-edit.js`.

### Concrete next sessions

**For an Explorer / dev session:**

- Migrate the Send UI parser to a local `_common/lib/markdown/` copy
  (steps 2–3 above) so the user-facing Send share view also stops
  fetching the parser from itself
- Replace the markdown branch of `send-browse.js` (the CDN-hosted v0.3.0
  base) with a call to `MarkdownRenderer.mount()`, exposing the view
  handle on the SendBrowse instance. After this, `vault-browse-edit.js`
  can call `browse._markdownView.getSource()` instead of `TextDecoder`-ing
  the bytes argument.

**For a QA session:**

- Author Playwright tests that load the harness and assert the
  pass count is the full suite (auto-detect via `.mh-summary--pass`).
  This converts the harness into a CI gate.
- Cover: Edit-on-markdown shows source not first code block; App Mode
  for `.md` files shows white background on table cells; list with
  continuation lines produces one `<li>` not `<li> + <p>`.

### Open questions still on the table (Section 7 of the architect review)

1. **CDN coupling for Send UI** — vault is now decoupled; should the
   Send UI also ship its own parser?
2. **Markdown editor UX** — "Edit" and "Source" buttons overlap.
   Unify into one editor with a render/source toggle, or leave as is?
3. **Cross-app shared code convention** — `_common/lib/` is fresh
   ground. If there's an existing convention for cross-app sharing
   between vault and user UI trees, tell me before the Send UI side
   gets its own copy.

## How to verify

1. **On a deployed vault**, open `/en-gb/vault/markdown` — the harness
   runs on page load. Expected: `All 40 tests passed`.
2. **In a writable vault**, open any `*.md` file with a multi-line
   list item or code block at the top, click Edit. Expected: textarea
   shows the original markdown, not the first code block.
3. **Open a `*.md` file** with a numbered list whose items span
   multiple lines (continuation indented ≥ 3 spaces). Expected: each
   item renders as a single `<li>`, no orphan `<p>` underneath.
4. **In DevTools Network tab**, filter for `markdown-parser`. Expected:
   one request to the local `_common/lib/markdown/markdown-parser.js`,
   no request to `dev.send.sgraph.ai/_common/js/markdown-parser*`.
