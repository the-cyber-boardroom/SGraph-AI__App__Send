## Your three corrections — status

1. **No new server-side public store.** ✅ Captured as authoritative. The design stores the preview as an ordinary **SG/Send transfer** (the existing `create`/`upload`/`complete`/`download` flow); the only exposure is the public-vault-about-key in the URL/logs, from which the transfer-id and read-only key are deterministically derived. Nothing new is stored server-side.

2. **Just API/HTTP calls leveraging what exists.** ✅ Confirmed by reading the backend. Publish = the 3-step transfer upload; read = the tokenless `download-base64`. No new endpoints for the happy path.

3. **The API may not support modifying a key → hold the delete key.** ✅ **Investigated and resolved.** `DELETE /api/transfers/delete/{id}` exists (`Routes__Transfers.py:249`) with a `delete_auth` model: the server stores only `SHA-256(delete_auth)`; the owner presents `delete_auth` to delete. So the update flow is **delete-then-recreate at the same transfer-id**, authorised by a **random `delete_auth` the owner generates at publish and stores in their own vault**. The share link never changes across edits. The one hard rule: `delete_auth` must NOT be derived from the public string (or anyone could deface the preview) — see the security review.

**The blocker you decided on:** delete used to leave a tombstone that blocked recreate. Per your call, I added the per-transfer **`allow_recreate`** flag (creator opts in; default keeps the tombstone) — so delete-then-recreate works and the **share link is unchanged across edits**.

## Honest verification gaps (not done in this session)

- **No browser/Playwright run** — the four UI surfaces are code-complete and syntax-checked, but not yet exercised in a real browser (this environment can't). The card's rendering + read path are logic-verified; the editor's publish/thumbnail flows are not browser-tested.
- **`/en-gb/app/<public-id>` app-shell wiring** — **Mode A now wired**: `app-shell._init()` detects the public-id path segment and, when there's no saved key, renders the preview card + key prompt (instead of the bare entry form); submitting the key hands off to the existing `_initWithKey` open flow. Saved-key opens are untouched. **Mode B** (preview-then-auto-load when a key is already saved) is a small follow-up — currently a saved key opens directly without the card flash. Note: this app-shell takes the vault key from **localStorage**, not the URL hash (hash-key is deprecated here), so the brief's `#<vault-key>` auto-load maps to the saved-key path. Not browser-tested.

- **jsdom** isn't installed, so the older vault loader tests can't run; my KAT doesn't need it and passes standalone.
