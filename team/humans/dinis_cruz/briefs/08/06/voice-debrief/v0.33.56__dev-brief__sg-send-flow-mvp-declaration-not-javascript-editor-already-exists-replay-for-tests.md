# The Flow MVP: The Declaration Must Be Data Rather Than JavaScript, The Editor Already Exists, And Replay And Local Models Are For Different Jobs

**version** v0.33.56
**date** 6 August 2026
**from** Human (project lead)
**to** The team implementing the transcription tool

**type** Dev brief

*Fourteenth of 6 August. Editor tooling is grounded and cited, and prior local-model work is cited from the project record. Offered to be built on and challenged.*

---

## What This Is

A build brief for the experimentation surface, with one contradiction in the request resolved and one piece of work that turns out already to exist: **the memo asks for JavaScript-based flows and, separately, for a visual editor that stays in sync with the declaration, and those two cannot both be had, because arbitrary code cannot be round-tripped to a diagram and back, so the flow structure must be data while JavaScript remains the runtime that executes it and the implementation of individual steps; the editor should not be built, since the formalism recommended this morning brings a mature visual editor with bidirectional synchronisation between the diagram and its object-notation representation, along with automatic test generation, and if a bespoke canvas is wanted instead there is a permissively licensed node-graph library that is the standard choice for exactly this class of tool, with workflow-editor templates including automatic layout and a runner; the two testing mechanisms in the memo serve different purposes and should not be conflated, because recorded and replayed responses are deterministic, free and instant and are what a workflow test needs, while a locally running model produces real and therefore variable output and is what a demonstration and a quality investigation need, so using the second for tests would reintroduce exactly the variability the first exists to remove; the local model work is already done and documented rather than needing research, using ahead-of-time compilation to browser compute shaders with quantised weights and both the weights and the compiled shaders cached so that second and subsequent loads take seconds rather than minutes; and one correction carries forward from this morning, because the consolidating step cannot hear the audio and therefore cannot adjudicate a disagreement, which means it should mark where the models differ rather than choosing the more plausible reading, since plausibility is precisely the wrong criterion for the words transcription most often gets wrong.** It is the fourteenth document of 6 August (cross-ref: the v0.33.56 workflow state machine brief, the v0.33.56 engine-outside-the-vault brief, the v0.33.56 billing-on-screen brief, the v0.33.52 voice-note architecture brief, and the v0.33.56 token-gateway brief). New contributions: **the resolution that the declaration must be data because the editor requirement demands it, the identification that the editor already exists in two forms, the separation of replay from local inference by purpose, and the observation that the dev surface is a prototype of a product feature.**

## The Declaration Must Be Data

The memo asks for two things that pull against each other. The project lead: **"the creation of a set of JavaScript-based flows that we can define, even with some support or markdown, that basically controls the flow of execution."** And later. The project lead: **"I would also like to add a visual editor, so a way to visualise this, so that we can also keep in sync the JSON with the visual representation."**

The second requirement settles the first. **Arbitrary code cannot be round-tripped to a diagram**, because a diagram cannot represent a conditional expression, a closure or a loop written in a general-purpose language, and generating code from a diagram then reparsing it back into the same diagram fails the moment anybody edits the code by hand.

The resolution keeps everything the memo wants:

| Layer | What it is |
|---|---|
| The flow structure | **Data**: steps, transitions, guards, budgets, declared in object notation |
| The runtime | JavaScript, walking the declaration |
| A step's implementation | JavaScript, called by the runtime |
| The editor | Renders and edits the data, never the code |

So flows are declared, not written. The memo's own instinct in the morning brief was already this, and this brief is the place to make the two consistent before two formats exist.

## The Editor Should Not Be Built

The memo is undecided. The project lead: **"I think there's a very simple open source module, or maybe we just build our own if it's not that hard."**

It is harder than it looks, and it does not need building. Two routes exist and the choice follows from a decision already made.

**If the formalism is statecharts**, which this morning's brief recommended on the grounds that hierarchy, guards, parallel regions and formal verification are all already defined, then the visual editor comes with it. The tooling around that formalism offers **bidirectional updates between code and visualisation**, with a reported practitioner experience of implementing business workflows as statecharts where externalising them as object-notation configuration made changes simple to roll out and automatic test-case generation improved confidence. That is precisely the synchronisation the memo asks for, plus test generation nobody asked for.

**If a bespoke canvas is wanted instead**, the standard choice is a permissively licensed node-graph library used for exactly this class of tool, including automation builders and pipeline visualisers, with workflow-editor templates that already include automatic layout, a drag-and-drop palette and a runner. Related projects publish an editor with object-notation serialisation described as version-control friendly and easy to diff.

**The recommendation is the first**, because it makes one decision serve three purposes: the semantics, the editor and the verification. Choosing the second means owning the semantics as well as the canvas.

## This Is The Third Flow Format Proposed Today

Worth flagging plainly, because the risk is real and cheap to avoid.

Three pieces of work today touch the same construct: the application-level declaration for this tool, the execution engine to be developed separately, and now this experimentation surface. If each defines its own format, the tool's flows will need migrating to the engine's format later, and the visual editor built for one will not open the other.

**So this MVP should either use the format the engine work is adopting, or be explicitly disposable.** Both are legitimate. What is not legitimate is producing a third format by default and discovering the divergence in a month.

## Replay And Local Models Are For Different Jobs

The memo asks for both and treats them as related. They are, but their purposes are opposite in the one respect that matters.

The memo's description of the first is exactly right. The project lead: **"the idea of the surrogate dependencies, where we basically replicate the exact calls from the network, so the website should not know the difference between one and the other, because what we're really testing here is the workflow, is the UX, is the design, is the connection, not necessarily the model responses."**

```
   RECORDED REPLAY                    LOCAL MODEL
   deterministic: same in, same out   real inference, varies run to run
   instant, free, works offline       slower, free, needs a capable device
   tests the workflow and interface   tests that real output flows through
   -> the right thing for TESTS       -> the right thing for DEMOS
                                         and for quality exploration
```

Using a locally running model in automated tests would reintroduce the variability that replay exists to eliminate, and a test that fails intermittently because a model phrased something differently is worse than no test.

So the rule is straightforward: **replay for tests and for interface development, local inference for demonstrations and for investigating output quality.**

On the recording itself, one design note. Key each recorded response by a hash of the request that produced it, so replay is automatic and no test needs to name a fixture. That also satisfies the memo's concern about realism. The project lead: **"it'd be good to have data that kind of is statistically and sort of works quite well."** Recorded real responses are realistic by construction, because they were real.

## The Local Model Work Already Exists

The memo suspects this and is right. The project lead: **"if you look at the tools project, I'm pretty sure that we already done a number of local inference models using some powerful techniques and powerful recent open source tools that we can run on a browser with some caching, so that we don't have to download the models all the time."**

The project record documents it in detail. The runtime compiles models ahead of time into optimised browser compute shaders, downloads quantised weights as sharded binaries on first load, and compiles the inference library on the fly. Critically for the memo's caching concern, **both the weights and the compiled shaders are cached in the browser, so subsequent loads take seconds rather than minutes.**

So the local-model page is wiring existing work rather than research, which changes its cost estimate considerably.

It is also worth noting why this matters beyond convenience. The token gateway work earlier today established that metering puts us in the request path, which converts the product's privacy claim from an architectural property into an operational promise. **The browser-local mode is the one tier where the claim remains architectural**, because nothing leaves the device at all, and the same record describes exactly that: a document decrypted in the browser, processed by a model in the same tab, and re-encrypted, with no plaintext crossing a network boundary. That makes this page more strategically valuable than a testing convenience.

## The Consolidator Marks, It Does Not Choose

A correction carried from this morning, restated because the team building this needs it in front of them.

The memo describes the consolidating step as deciding. The project lead: **"the module that consolidates the three, or five, or two of each one, and makes a decision on the best transcription that makes more sense."**

The difficulty is that the consolidating model **never hears the audio**. Where two transcripts agree it adds nothing; where they disagree it cannot check, so it selects on plausibility. That is precisely the wrong criterion for proper nouns, technical terms and numbers, which are the words transcription most often gets wrong, and the published evidence includes a case where a text-only corrector roughly doubled the error rate.

So the instruction is to **mark disagreement rather than resolve it**: let it settle punctuation, casing and filler freely, and require it to surface content-word differences rather than pick between them. The proportion of disagreeing spans is then a quality score for the file at no additional cost.

The same applies to the other primitives. Two summaries or two infographics should be **shown side by side** rather than silently merged, because a merged summary asserts something neither model produced, while two summaries let the reader see the spread. The memo already leans this way for infographics.

## The Dev Page Is A Prototype Of A Product Feature

The memo is right to keep this off the main interface. The project lead: **"so not on the main UI, this is a good example of adding a sort of a dev QA page."**

Worth noting what it becomes, though, because it affects how well it should be built. This morning's brief established that once flows carry declared models and budgets, the same job exists at several price points, which turns workflow definitions into something closer to a product line than a configuration file. A customer choosing between a quick transcript and a consensus run is choosing a flow.

**So the experimentation surface is the unstyled ancestor of a customer-facing chooser.** That is a reason to get the data model right and not to worry about the styling, which is the correct division of effort for a development page anyway.

## Build Order

1. **Fix the format question.** Data, not code, and either the engine's format or an explicitly disposable one.
2. **Recorded replay**, keyed by request hash, captured from real calls once.
3. **The dev page**, running a declared flow against replay, with the execution visible.
4. **Multiple models per primitive**, with the consolidator marking rather than choosing.
5. **The visual editor**, adopted rather than built, rendering and editing the declaration.
6. **The local-model page**, wiring the existing runtime, used for demonstrations.
7. **Two or three worked example flows**, connected and readable, which the memo asks for as the starting point.

The memo's own closing instruction is the right shape for the last step. The project lead: **"we should start with a number of good examples that are connected, and then we should also have the ability to create our own."**

## What This Does Not Try To Be

- **Not JavaScript flows.** Declared data, executed by JavaScript, with steps implemented in it.
- **Not a bespoke editor.** Adopted, because the formalism decision already supplies one.
- **Not a third format.** The engine's format, or explicitly disposable.
- **Not local models in tests.** Replay for determinism; local inference for demonstrations.
- **Not a silent merge.** Disagreements marked, alternatives shown side by side.

## Honest Tensions

| Tension | Note |
|---------|------|
| Declared flows versus expressiveness | Data is analysable, verifiable and editable visually, and it cannot express everything code can, which will chafe on the first awkward case |
| Adopting an editor versus fitting it | Mature tooling arrives with its own model of what a flow is, and bending it costs more than it looks |
| Replay realism | Recorded responses are real and they age, so a fixture set captured today describes today's models |
| Local models on arbitrary devices | The capability exists and requires a capable browser and machine, so it cannot be the only demonstration path |
| A dev page that becomes a product | Building it properly is right and invites scope that belongs to a later version |
| Three flow formats | The risk is cheap to avoid now and expensive to unpick, and avoiding it requires a decision the tool team does not own alone |

| Question | Notes |

| Where are recordings stored? | Committed alongside tests, or in a vault, and how they are refreshed |
| How often are fixtures re-recorded? | They describe the models of the day they were captured |
| Which editor route? | Statechart tooling with synchronisation and test generation, or a bespoke canvas on a node-graph library |
| What are the two or three worked examples? | Chosen to show genuinely different shapes rather than variations of one |
| Does the local page share code with the main app? | It should, or it stops being a test of the real path |
| How is the disagreement rate presented? | It is a free quality signal and needs a presentation that informs rather than alarms |
