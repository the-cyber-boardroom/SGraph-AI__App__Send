## What This Is

The next phase of the voice transcription product, and an answer to the question the memo asks about whether the payment workflow can be avoided: **it cannot, and the platform's own fulfilment documentation prescribes almost exactly the shape described, namely a function triggered by a webhook, with a redirect used only to give the customer immediate access rather than to trigger anything, because a person who closes the tab must still receive what they paid for; four requirements make that function reliable and one of them is financial rather than technical, since duplicate webhook delivery is normal and the documentation warns that fulfilment may be invoked more than once and concurrently for the same session, which in this design means issuing a second funded key against one payment, so deduplication on the event identifier is not hygiene here but the difference between a margin and a leak; the proposal to distribute the credential through the existing secure send capability rather than by emailing it is right and was already the plan, and it has properties worth naming, because the key never exists in a mailbox, access can be withdrawn by removing the send, and the same reference can carry the credential into the browser's local storage through a link; the three persistence options the memo lists are not alternatives but a ladder, and the middle rung is probably skippable, since a customer vault is not a new thing to build but the existing architecture instantiated per customer, whereas adopting a third-party identity and data store contradicts the sovereignty posture and adds a dependency for a stage that may never be needed; and the most consequential observation is one the memo makes in passing, that persistence turns this from a transcription tool into somewhere a person keeps things, which is a different business with different economics from the one the current agreement prices, and that should be decided rather than drifted into.** It is the first document of 6 August (cross-ref: the v0.33.52 voice-note architecture brief, the v0.33.52 first-product commercial brief, the v0.33.53 voice-note build brief, the v0.33.55 vaults-as-substrate brief, and the v0.33.50 tools-to-productise brief). New contributions: **the research answer that no shortcut exists and the function is required, deduplication identified as a financial control rather than a correctness one, the persistence options ordered as a ladder with the middle rung questioned, the observation that persistence changes the business the current contract prices, and a duration guard identified as necessary once arbitrary audio is accepted.**

## Where The Product Now Stands

Worth recording because it validates a claim made in July. The project lead: **"we added some of the code and some of the examples of the chat environment that we created in one of the vaults to the WhatsApp voice transcription, which is a great example of the synergies between the two worlds."**

The product now takes a file, produces a transcription, a summary and an infographic, and offers a chat window with access to all three that can also modify them. The project lead: **"you can have a conversation about the chat, and you can then manipulate it."**

This is the second transfer of capability between products in a week. Voice input moved from the transcription tool into the vault work on 2 August; the chat environment has now moved the other way. The commercial brief of 27 July argued that the real output of the first product was a reusable kit and that the honest test was whether the second product shipped faster. Capability now moving in both directions is a stronger result than the test asked for, and it is worth recording as evidence rather than as a pleasant surprise.

## The Research Answer: No Shortcut, And The Shape Is Prescribed

The memo asks the right question. The project lead: **"this is probably worth doing a little bit of research, just to see if there is a better solution, and if not, does Stripe already have a workflow that we can piggyback, or what other technologies can do this."**

**The answer is that no shortcut exists and the described design is the documented one.** The payment platform's own fulfilment guidance states that you create a function on your server which webhooks trigger, that webhooks are required to ensure fulfilment happens for every payment, and that redirects exist so customers can access what they bought immediately rather than to cause fulfilment. Payment links use the same checkout mechanism, so choosing the simplest payment surface does not remove the requirement. A separate integration guide confirms the same conclusion in a no-backend context: this approach requires server-side code, in the form of a serverless function.

So the mini function the memo proposes is not a shortcoming of the design. It is the design, and the only genuine decision is where it runs.

One correction to the mental model is worth making. The memo describes a hook that triggers a function which creates a token. The documented pattern uses **both** a webhook and a redirect, for different jobs:

```
   customer pays
        |
        +--> REDIRECT to the site      -> immediate access, no fulfilment
        |
        +--> WEBHOOK to the function   -> the fulfilment, guaranteed
                 |
                 +-- verify signature on the raw body
                 +-- acknowledge fast
                 +-- dedupe on the event id
                 +-- do the work asynchronously
```

Guidance published in July 2026 sets out those four moves as what makes a serverless webhook reliable, and adds a warning worth heeding: do not model the whole fulfilment as one long workflow pretending the request is still open, but keep the durable unit a plain job or a pipeline of short retryable steps.

## Deduplication Is A Financial Control Here

This is the specific item that deserves emphasis, because in this design a common mistake has an unusual consequence.

The platform's documentation states plainly that fulfilment must be performed only once per payment, because the function may be called multiple times and possibly concurrently for the same checkout session. That is normal behaviour, not an error condition: retries, replays and the redirect path can all invoke it.

In most products a duplicate fulfilment ships a second copy of something cheap or creates a confusing record. **Here it provisions a second funded credential against one payment.** The customer pays once and receives two keys, each carrying the full allowance, and the loss is exactly the value of the second key.

So the ordering matters and should be written into the function rather than left to the implementer:

| Step | Why |
|---|---|
| Verify the signature on the raw body | Anything else is an open endpoint that provisions credit |
| Look up the event identifier; stop if already processed | The financial control |
| Record the intent before provisioning | So a crash after provisioning is recoverable |
| Provision the key, with an idempotency key on the write | Prevents a retry inside the provider creating a second key |
| Record completion, then create the send and notify | Notification last, because it is the only irreversible step |

The provider's own key creation should carry an idempotency key derived from the payment identifier, which means even a genuinely duplicated call returns the original rather than minting another. Guidance on the payment side recommends idempotency keys on all write operations for the same reason.

There is also a way to test all of this without any real card traffic, which is worth knowing before Saturday-style deadlines recur: the platform's command line tool can forward live events to a local or deployed endpoint and can fabricate a realistic event, so the whole verify, dedupe, acknowledge and fulfil path can be exercised end to end.

## Distributing The Key Through Send

The memo's instinct here is right and it executes a plan already made. The project lead: **"instead of actually sharing the key, you basically just share the transfer ID, the decryption key that we create from SG Send."**

The 28 July build brief identified the existing send capability as the secret distribution mechanism, so this is wiring rather than invention. The properties are worth naming because they are better than the obvious alternative of emailing a key:

**The credential never exists in a mailbox.** An emailed key sits in the recipient's mail store indefinitely, searchable, forwardable, and readable by anything with access to the account. A transfer reference points at a secret held elsewhere.

**Access can be withdrawn.** Removing the send revokes retrieval, which an email cannot do.

**It can be single use or time limited**, so a reference that leaks after retrieval is inert.

**And the link does double duty.** The memo describes the second half. The project lead: **"we'll send them an email with it, and we'll also send them a link to the website that has the same token, so that the website can take that token and add that to local storage."** So one artefact serves both the human path and the machine path.

The retrieval reference inherits the sensitivity of what it points at, which argues for short expiry and single use rather than a durable link.

## The Persistence Options Are A Ladder

The memo lists three and treats them as parallel. They are better understood as stages, and one of them may be skippable.

| Rung | Gives | Costs |
|---|---|---|
| Local storage | Zero friction, no signup, works today | Lost on cache clear or a change of device; nothing recoverable |
| A third-party account | A familiar login and an identity | An identity system to maintain, and customer data in somebody else's store |
| A vault per customer | Keys, chats, sessions and their files, in one place | The most work, and it is work already done in another form |

The case for skipping the middle rung is stronger than it first appears. **A customer vault is not a new thing to build; it is the existing architecture instantiated per customer.** The product is already a vault application, the paradigm brief of 2 August established vaults as the substrate for exactly this kind of durable per-participant state, and the corpus has spent months arguing that customer data should sit inside a boundary the customer controls.

Adopting a third-party identity and data store would contradict that posture, introduce a dependency, and produce an identity system that has to be maintained after the rung it served has been climbed past. If vault-per-customer is the destination, the middle rung buys a few weeks and costs a permanent obligation.

The honest counter is that vault-per-customer is more work up front, and that local storage plus the send-delivered key is genuinely sufficient for the first paying cohort. That sequence, local storage now and customer vaults next, seems right.

## Persistence Changes What The Product Is

The memo says this and then moves on, and it deserves to be the item that gets decided rather than absorbed. The project lead: **"it becomes not just a simple voice transcript, but also starts to become a bit of a data management solution."** With the reason. The project lead: **"you need a bit of data persistence, because that's when it becomes useful, when you don't lose your sessions."**

That is a positioning change with a commercial consequence.

**A transcription is a purchase.** Somebody has a file, they want it processed, they pay for the processing. The price is metered, the relationship ends when the job does, and the 27 July commercial brief prices exactly this: a take of twenty-five percent of net receipts, a minimum top-up set by the payment fee, and a ninety-day revenue share on a per-use product.

**A place where your transcripts, summaries, infographics and conversations live is a subscription.** The value is in what has accumulated, the relationship is continuous, churn becomes the metric that matters, and the customer's willingness to pay attaches to what they would lose rather than to what they are about to consume.

Those are different businesses. The current agreement prices the first. Nothing prevents the product becoming the second, and the memo is right that it is the more useful thing, but the commercial terms were written on the assumption that they were selling processing rather than storage. That should be revisited deliberately, before persistence ships rather than after, because renegotiating a revenue share once a product has changed shape is materially harder than agreeing it in advance.

## The Three Categories, Populated

The memo asks for the split and it is a useful one. The project lead: **"what are features that we need to add to the app that I can add independently, what are features that we can add to the backend to make it usable, and what are the workflows that we need to integrate with Stripe."**

| Category | Items | Blocked by |
|---|---|---|
| **App only** | Design variations and comparison, expanded file type support, video audio extraction, the chat surface, interface polish | Nothing |
| **Backend** | The fulfilment function, key provisioning, send creation, notification | A decision on where it runs |
| **Integration** | Webhook registration, signature verification, the event contract, the failure and refund paths | The backend existing |

The sequencing point matters more than the categories. **The app work is entirely unblocked and the payment work is the critical path.** Everything a customer sees can proceed in parallel and none of it produces revenue until the fulfilment function exists. If effort has to be chosen between them this week, the function wins, because the design can improve after money is flowing and cannot produce money by improving.

## Accepting Any Audio Has A Cost Consequence

The memo proposes widening the input. The project lead: **"we probably should just allow the user to drop any kind of audio file to be transcribed."** And further. The project lead: **"we could even maybe allow a movie to be dropped, because we already have all the code that extracts the audio from a video."**

Both are good, and the second is reuse rather than build, since the video splitter was among the tools listed as mature on 23 July. Two consequences should be handled before the door is opened.

**The unit economics were set for voice notes.** The pricing established on 27 July assumed a transcription costing under twenty pence, which is a two-minute message. A three-hour recording is roughly ninety times that. With a credential carrying a fixed allowance, a single long file can consume an entire top-up, and the customer will experience that as the product taking their money. A duration guard, or a cost estimate shown before processing, is required rather than advisable. The live cost display already designed for the field demo is the obvious mechanism.

**Large files are a different browser problem.** Extracting audio from a video client-side is straightforward for a short clip and a genuinely different proposition for a large file on a tablet. Worth establishing a size ceiling from measurement rather than discovering it from a support message.

## Design Work In Parallel

The memo asks for it and it fits the unblocked category. The project lead: **"we need to now brush up on the design, let's create a lot of different designs and do A/B testing on this."**

That is the same principle reached twice in the last week, that several options run simultaneously is what makes a comparison informative rather than merely safe, and that variations should differ on decisions that would be expensive to reverse rather than on surface treatment. Worth carrying over rather than restating.

## What This Does Not Try To Be

- **Not a way to avoid the function.** The documented pattern requires it; the only decision is where it runs.
- **Not fulfilment on redirect.** The redirect gives immediate access; the webhook guarantees delivery.
- **Not three equivalent persistence options.** A ladder, with the middle rung probably skippable.
- **Not a neutral feature.** Persistence changes the business the current agreement prices.
- **Not an open door on file size.** Arbitrary audio needs a duration guard before it ships.

## Honest Tensions

| Tension | Note |
|---------|------|
| No backend versus the fulfilment function | The product's whole architecture is static and this is the second component that must run somewhere, so the no-backend claim needs restating precisely rather than quietly abandoned |
| Skipping the middle persistence rung | Vault-per-customer is right and slower, and there will be a moment where a familiar login would have converted somebody |
| Persistence versus the current agreement | The commercial terms price a per-use product, and the more useful product is a subscription, which is a conversation with a partner rather than a decision to take alone |
| Widening file support versus focus | The corpus argued in July that one complete job beats a general tool, and accepting any audio is a step toward the general tool |
| A duration guard versus the promise | A ceiling protects the margin and will feel like a limitation to the first person who hits it |
| Send-delivered credentials versus recovery | A revocable time-limited reference is right and means a customer who loses the link has nothing, so the recovery path needs designing alongside |

## Open Questions

| Question | Notes |
|----------|-------|
| Where does the function run? | The only real decision, given that it must exist |
| What is the idempotency key derived from? | The payment identifier is the obvious choice and it should be written down rather than assumed |
| What happens on refund or dispute? | The credential is already funded and the money is being returned, which needs a defined behaviour |
| What is the duration ceiling? | Set from measurement and from the top-up size, not from intuition |
| When do customer vaults arrive? | The stated destination, and the trigger for building it |
| Does the agreement need revisiting before persistence? | Almost certainly, and it is easier now than after the product has changed shape |
| What is the recovery path for a lost link? | A revocable reference is secure and unforgiving |
