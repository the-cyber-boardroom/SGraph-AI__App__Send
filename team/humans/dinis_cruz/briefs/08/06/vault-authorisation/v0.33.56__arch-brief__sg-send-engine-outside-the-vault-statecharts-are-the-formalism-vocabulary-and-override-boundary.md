# Build The Engine Outside The Vault, And Do Not Invent The Formalism: Statecharts Already Have The Hierarchy, The Guards And The Verification

**from** Human (project lead)
**to** Engineering, Architecture

*Tenth of 6 August, on how to build what the previous brief investigated. The formalism and its tooling are grounded and cited. Answers the terminology question directly. Offered to be built on and challenged.*

## What This Is

A build approach for the execution engine, and a recommendation not to design its semantics from scratch: **the instinct to develop it as a separate model that the vault happens to use is right, and it has a testable form, since the engine must have no knowledge of vaults at all and the vault must integrate by implementing an interface the engine defines, which means the honest check is whether it runs in a plain process against a filesystem with nothing vault-shaped imported; building it inside a vault to get a better iteration loop is a good idea and carries one trap, that vault assumptions creep in by proximity, which a standalone build running from the first day prevents entirely; the fractal property wanted here, where one workflow calls another with its own vocabulary, is hierarchy in the statechart formalism introduced in 1987, which extends finite state machines with nested states, concurrent regions and communication, has forty years of formal semantics behind it, was standardised by the web consortium in 2015, and comes with mature libraries, visual editors, simulators and diagram export; the conditional permissions described in the memo are guards on transitions, which the formalism already has, and the properties that matter most to the previous brief's reference-monitor argument come with it, because a finite state space is amenable to exhaustive analysis and existing tooling can verify absence of deadlock, eventual termination and safety invariants, which is exactly the verifiability the pattern requires; the terminology question asked twice has a clean answer once the formalism supplies most of it, needing only a distinction between the definition and a running instance; converting existing vault commands to workflows should be done by value rather than by principle, because a single-operation command gains overridability and a uniform permission point and gains nothing from sequence enforcement while paying indirection on the hottest path in the system; and the override capability that excites the memo is also the one that needs a boundary, since letting a vault redefine a primitive is letting a vault redefine the security model, which argues for composition and hooks rather than replacement.** It is the tenth document of 6 August (cross-ref: the v0.33.56 kernel state machine brief, the v0.33.56 workflow state machine brief, the v0.33.55 graph-canvas brief, the v0.33.55 vaults-as-substrate brief, and the v0.33.52 outbound maturity model). New contributions: **the independence test for the separate engine, the identification of statecharts as the formalism with hierarchy and guards already defined, formal verification as the answer to the reference monitor's verifiability requirement, a settled vocabulary, conversion by value rather than by principle, and the system-versus-vault workflow boundary.**

## Build It Outside, And Here Is The Test

The instinct. The project lead: **"the execution engine of the state machine is almost vault independent, and we've done a couple of things like this before, where we develop something in isolation first, get it right, and then just add it to the vault codebase."** With the intended relationship. The project lead: **"a complete separate model that the vault happens to use."**

That is right, and independence is easy to claim and easy to lose. The test is specific and should be enforced mechanically:

**The engine must not know what a vault is.** No vault types, no vault imports, no vault assumptions in its interfaces. It defines what it needs from a host, and the vault implements that. The dependency runs one way only, and the direction is the whole point.

The practical form: the engine builds and its tests pass in a plain process with a filesystem and nothing else. If that stops being true, independence has been lost, usually quietly and in a single convenience import.

## Building It In A Vault Is A Good Idea With One Trap

The suggestion is offered tentatively and deserves endorsing. The project lead: **"this might be a good example of even developing this inside a vault, so that we could iterate much better, and then once we've done with it, we can just export that code base out."**

Two reasons it is a good idea. The workbench debriefs catalogued on 2 August show vault applications are now capable enough to host real development, and the feedback loop established the same day, where an observation spoken in place becomes an issue the building agent reads, is exactly the loop an engine under rapid iteration wants. It is also a genuine test of the vault application story: if the engine cannot be built comfortably in one, that is worth knowing.

**The trap is proximity.** Developing inside a vault makes vault-shaped assumptions easy to absorb without noticing, and the export at the end then becomes an unpicking exercise rather than a copy.

The fix is cheap: run the standalone build from day one, not at the end. If the engine is continuously proven to build and pass outside the vault, it cannot acquire a dependency on it.

## Do Not Invent The Formalism

This is the recommendation with the largest saving attached.

The memo asks for hierarchy. The project lead: **"make it again fractal, where one workflow can call another workflow that has its own ontology and taxonomy."** And for conditional permissions. The project lead: **"permissions that should take into context what has happened before, what's happening after, particular state, particular capabilities, and be able to add logic to these conditions."**

Both are defined constructs in an established formalism. **Statecharts**, introduced by Harel in 1987, extend finite state machines with three mechanisms: hierarchy, where states nest inside other states so that being in a sub-state means implicitly being in its parent and unhandled events propagate upward; concurrency, in the form of parallel regions; and communication between them. The standard elements include basic, composite and orthogonal states, event-based and time-based transitions, entry and exit actions, history states, actions, and **guards**, which are conditions attached to transitions.

The formalism was standardised by the web consortium in 2015 as a serialisation, and one implementation puts the relevant point well: the markup is not the point, the semantics are. The same semantics underpin tooling across every major language, and the most mature library in the relevant ecosystem is compliant with the standard while expressing machines in ordinary object notation rather than markup.

So the mapping is direct:

| The memo wants | The formalism calls it | Status |
|---|---|---|
| A workflow calling a workflow | Hierarchy, or composite states | Defined 1987, semantics reconciled in the literature |
| Conditions on whether a step may proceed | Guards | Standard element |
| Parallel steps | Orthogonal regions | Standard element |
| Resuming where something left off | History states | Standard element |
| A designer | Visual editors | Existing tooling |
| Animating execution | Simulators and inspectors | Existing tooling |
| Diagram output | Export to common diagram formats | Existing tooling |
| Budget per step | Nothing | **The genuine addition** |

**Almost everything asked for is already specified, and the one thing that is not is the thing this corpus actually contributes.** That is a good position: adopt forty years of semantics and tooling, and add the resource control nobody else has bothered with.

## Verification Is The Part That Matters Most

A consequence worth pulling out, because it answers the hardest requirement in yesterday's investigation.

The previous brief argued that the kernel must satisfy the three reference-monitor properties, and that verifiability is the binding constraint: a monitor too large to analyse has failed on its own terms.

Because a finite state space can be enumerated exhaustively, statechart models are **amenable to formal verification**, and existing tooling makes it practical rather than theoretical. The properties reported as checkable are precisely the ones a security argument needs: that no state deadlocks, that every execution path terminates within bounded steps, and that certain state combinations are never reachable.

Applied here, that means a flow definition can be checked before it is ever run, and the checks can be the security ones: **this workflow cannot reach a write step without passing the validation step; it cannot loop unboundedly; it cannot occupy the executing state and the finalised state at once.** That converts the reference monitor's verifiability requirement from an aspiration into a tool that already exists.

It is also the strongest argument against a bespoke formalism, because a home-grown one would have no verifier and no path to one.

## The Terminology, Settled

The memo asks twice. The project lead: **"let's figure out again the terminology: is a flow, is a workflow, what do we call it, a task?"**

The formalism supplies most of it, and the missing distinction is the one causing the confusion: **the definition and a running instance need different words**, and neither flow nor workflow gives you both.

| Term | Meaning | Notes |
|---|---|---|
| **Workflow** | The definition. Declared, versioned, addressable, reusable | The machine, in formalism terms |
| **Run** | One execution of a workflow. Has current state, remaining budget, history | The instance, or actor |
| **Step** | A unit within a workflow | A state; may itself be a workflow, which is the hierarchy |
| **Transition** | Moving from one step to the next | What the kernel permits or refuses |
| **Guard** | A condition that must hold for a transition to be taken | Where the contextual permissions live |
| **Budget** | A bounded resource a step may consume | The domain addition |

**Task should be avoided.** It is overloaded by queues and runners, and it does not distinguish definition from instance, which is the distinction that was missing.

One consequence of the hierarchy is worth stating: because a step may be a workflow, the two are not separate types. A step is either a leaf operation or a nested workflow, which is the fractal property expressed in the type system rather than bolted on.

## Budget Is The Genuine Addition, And It Generalises

The memo's own favourite, and rightly. The project lead: **"start assigning budget, even giving budget to calls, and even if it's not financial, we can add a budget, and this will be a great way to control agents from going rogue."**

The generalisation is the useful part. **A budget is any bounded resource**, and money is only the most obvious one. The outbound maturity model of 27 July named autonomy, elapsed time and spend as the components of the freedom precondition, so time-boxing was already in the corpus. Extending it costs nothing:

- currency or tokens
- wall-clock time
- number of model calls
- number of external requests
- bytes written

A step declares its consumption; the run carries the remainder; the kernel refuses when exhausted. One mechanism, several units, and the same shape as the consumption ledger from this morning, which was also deliberately generic beyond tokens.

## Converting Existing Commands: By Value, Not By Principle

The memo makes a large claim. The project lead: **"if you actually look at the SG commands, probably all, or at least most, if not all, could be converted to a workflow."**

The benefits are real: one enforcement point, uniform permission evaluation, overridability, and a visible execution record. But the conversion should be selective, because the value is not uniform.

**A single-operation command gains some of it and not the part that matters most.** Expressing a file read as a one-step workflow makes it overridable and gives it a uniform permission point, and gains nothing at all from sequence enforcement, because there is no sequence. What it does acquire is indirection on the hottest path in the system, evaluated on every access.

So the criterion should be value:

| Convert first | Convert later or not at all |
|---|---|
| Multi-step flows where order matters | Single atomic operations |
| Anything that spends | Anything on the hot path, until measured |
| Anything worth overriding per vault | Anything a vault should not redefine |
| Anything worth animating or auditing | Internal bookkeeping |

The end state the memo imagines, where everything including settings is a workflow, may well be right. It is a destination rather than a first move, and the route to it is measured rather than assumed.

## Override Is The Exciting Feature And Needs A Boundary

The capability that clearly appeals. The project lead: **"if we had the read file as a particular workflow already defined, then a vault could override it and add some extra stuff, which would be quite powerful."**

It is powerful and it is also the sharpest risk in the proposal, because **letting a vault redefine a primitive is letting a vault redefine the security model.** The kernel enforces the declared flow; if the vault declared it, the vault chose what is enforced, and the reference monitor is monitoring a definition supplied by the thing it is meant to constrain.

The resolution is the operating system one. System calls are not replaceable; programs compose them. So:

**System workflows** are defined by the kernel, versioned with it, and not replaceable. They may expose declared extension points.

**Vault workflows** are defined by a vault, may compose system workflows, and are constrained by them.

**Extension is composition and hooks, not replacement.** A vault wanting extra behaviour around a file read wraps it in a workflow that calls the system one, rather than substituting its own definition of what reading a file means.

That preserves the customisation the memo wants while keeping the primitive trustworthy, and it makes the privileged act explicit: defining a system workflow is a kernel change, and defining a vault workflow is not.

## Animation Is Provenance, Rendered In Time

The memo is enthusiastic and the enthusiasm is justified for a reason beyond presentation. The project lead: **"animating the whole animation of a flow as it executes is ridiculously powerful, because it provides a much more visual element of what's going on, and reduces a lot of the magic."**

Reducing the magic is a trust argument, and it is the same argument the corpus made for the visible cost meter and for showing a visitor the raw structure of what is held about them.

But there is a structural point too. The workflow brief this morning established that a declared workflow plus an execution record is a complete account of how an output was produced, and that this is the provenance artefact. **The animation is that same artefact projected onto time rather than onto a page.** It is not a separate feature to build; it is a second renderer over data the engine necessarily has.

Which also means the existing tooling helps here, since statechart libraries ship inspectors and simulators, and the corpus already decided on 2 August that text-based diagrams are the right output format and an interactive library the right canvas.

## Staging

The memo asks for stages and the ordering follows from the above.

1. **The formalism decision.** Adopt statechart semantics; choose the serialisation; decide whether to use an existing library or implement the subset needed. This decision gates everything.
2. **The engine, standalone**, with hierarchy, guards, budgets and an execution record. Built outside, or inside a vault with a continuous standalone build.
3. **The host interface**, which the vault implements, with the dependency running one way.
4. **One real flow**, the transcription workflow, ported and running under the engine.
5. **A second unlike flow**, to test that the schema generalises, before anything is settled.
6. **System workflows**, defined and marked non-replaceable, then a vault workflow composing one.
7. **Verification in the build**, checking flow definitions for the safety properties before they can run.
8. **Renderers**, static first and animated second, over the record the engine already produces.

The memo's own reassurance holds through all of it. The project lead: **"it doesn't add a lot of complexity in the short term, because we can just do it incrementally."** That is true provided each stage delivers something usable and the standalone build never breaks.

## What This Does Not Try To Be

- **Not a new formalism.** Statechart semantics, with budget as the addition.
- **Not vault-coupled.** The engine does not know what a vault is; the vault implements a host interface.
- **Not a wholesale command conversion.** By value, measured, starting with multi-step flows.
- **Not unrestricted override.** System workflows are composed, not replaced.
- **Not an animation feature.** A second renderer over the provenance record the engine already produces.

## Honest Tensions

| Tension | Note |
|---------|------|
| Adopting a formalism versus fitting the domain | Statecharts were designed for reactive systems and a workflow is a task sequence, and the fit is good rather than exact |
| Existing library versus independence | Using a mature library saves enormous effort and makes the engine depend on it, which is a dependency chosen rather than avoided |
| Building inside a vault versus exporting cleanly | The iteration loop is better and the coupling risk is real, which only a continuous standalone build resolves |
| Converting everything versus the hot path | The uniform end state is attractive and a permission evaluation on every file read is a cost that must be measured before it is accepted |
| Override versus trustworthy primitives | The most exciting capability is the one that can undo the security argument, so the boundary matters more than the feature |
| Verification available versus verification used | Exhaustive checking is practical and only helps if it runs in the build rather than being possible in principle |

## Open Questions

| Question | Notes |
|----------|-------|
| Which serialisation? | The semantics are the point; object notation fits the corpus better than markup |
| Existing library or own implementation? | Maturity and tooling against a dependency in the engine meant to be independent |
| What does the host interface require? | The smallest surface a vault must implement, decided before the first port |
| Which safety properties are checked in the build? | No unbounded loops, no write before validation, no contradictory states, at minimum |
| What are the system workflows? | The set defined by the kernel and not replaceable, which is a security decision |
| How is a budget unit declared? | Several resource types with one mechanism, and how a run reports remaining |
