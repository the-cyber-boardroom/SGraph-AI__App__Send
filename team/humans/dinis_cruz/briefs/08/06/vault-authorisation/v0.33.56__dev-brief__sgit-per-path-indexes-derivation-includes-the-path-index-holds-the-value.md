# Per-Path Indexes For sgit: The Schema Already Has A Slot For This, The Derivation Should Include The Path, And For Small Records The Index Should Hold The Value

**version** v0.33.56
**date** 6 August 2026
**from** Human (project lead)
**to** The sgit team

**type** Dev brief

*Thirteenth of 6 August. A feature brief for the vault storage layer, written inside the existing sgit design rather than proposing a parallel one. Prior sgit architecture work is cited from the project record.*

---

## What This Is

A request for per-path indexes maintained on write, expressed inside the design sgit already has: **the naming schema defines every file as type, derivation, mutability and identifier, and it already contains an index type described as a denormalised cache, a pseudo-deterministic derivation computed as a keyed hash over the vault key and a domain string, and a mutability segment that tells the server whether to cache and whether concurrent writes need protection, so this feature is a new domain string rather than a new mechanism; the project lead's own suggestion is the right one and should be taken further than stated, because including the path in the domain string gives one index per file rather than one index per vault, which scales without any registry and makes the identifier computable by any client holding the read key without a single discovery call; the reason it is worth doing turns on a property of the batch read API, since batching collapses breadth and not depth, meaning a client can fetch many known objects in one round trip and still cannot fetch the next object in a tree walk until it has decrypted the current one, so reaching a known path costs as many round trips as the tree is deep while a per-path index costs one; and for the records this is actually wanted for, which are small and read constantly, the index should hold the value rather than a pointer to it, because the type is already defined as a denormalised cache and a pointer would spend a second round trip retrieving something smaller than the pointer's own overhead.** It is the thirteenth document of 6 August (cross-ref: the v0.16.3 deterministic IDs simulation, the v0.33.56 git-and-sgit co-existence brief, the v0.33.56 plugins brief, the v0.33.56 vault-architecture brief, and the v0.33.55 vaults-as-substrate brief). New contributions: **the path included in the domain string, the round-trip argument set out for an architecture that already has batch read, the index holding the value for small records, the mutability choice as a caching decision, and the delete, rename and repair cases.**

## What Already Exists

Establishing the baseline, because most of the mechanism is built and the gap is narrow.

sgit has **no staging area and no index**, by design: it takes snapshots of the whole folder. That is what makes this request necessary and also what makes it small, because the identifier scheme it already uses was built to allow exactly this kind of extension.

Every file identifier follows the pattern **type, derivation, mutability, hexadecimal identifier**, so a filename declares what the file is, how to find it, and whether concurrent writes need protection. Relevant values:

| Segment | Value | Meaning |
|---|---|---|
| Type | `idx` | Index file, described as a denormalised cache |
| Derivation | `pid` | Pseudo-deterministic, a keyed hash over the vault key and a domain string, computable by any client holding the secret |
| Mutability | `snw` | Single-writer mutable; server caches with a short lifetime |
| Mutability | `muw` | Multi-writer mutable; no caching, and writes require match-on-write |

Deterministic identifiers are already in use for the branch index, the named head reference, the clone branch reference, the head snapshot and the commit log, each derived from a domain string of the form `sg-vault-v1:file-id:{purpose}:{vault_id}`.

The batch endpoint already supports read alongside write, match-on-write and delete, returning many objects in one payload, with the server reading them internally at a few milliseconds each. Reads are unauthenticated by design, on the reasoning that the data is encrypted and knowing an identifier does not help without the vault key.

**So the request is a new domain string and a write-path obligation, not a new subsystem.**

## Why It Is Worth Doing: Batching Collapses Breadth, Not Depth

Batch read collapses **breadth**: a client that knows the identifiers of twenty objects fetches them in one round trip. It cannot collapse **depth**, because in a tree walk the identifier of the next object is inside the current one, and the current one is encrypted. So each level costs a round trip regardless of batching.

```
   TREE WALK to a known path            PER-PATH INDEX
   read ref            round trip 1     compute idx id      no request
   decrypt -> commit id                 read it             round trip 1
   read commit         round trip 2
   decrypt -> tree id                   depth is irrelevant
   read root tree      round trip 3
   decrypt -> subtree id
   read subtree        round trip 4
   decrypt -> blob id
   read blob           round trip 5
```

The project lead's framing is exactly this. The project lead: **"we've done this before, but it was actually required quite a number of reads because you have to navigate the tree."**

And the trade is the standard one for a read-optimised index, stated exactly in the memo. The project lead: **"it's always much more expensive to write than to read, and there's also a lot less writes than reads."**

## The Derivation Should Include The Path

The memo proposes the mechanism and then improves on its own proposal, and the improvement is the right one. The project lead: **"one nice way to create the deterministic index objects is to use the same technique we use for deterministic branch names, which uses a hash of the branch name and the read key."** Then the refinement. The project lead: **"it might be more effective and scalable to use the file name as part of the hash."**

That refinement is what makes the feature scale, and it should be taken as the design.

**Keyed on the vault alone**, there is one index per vault, so it must contain an entry for every tracked path, every write rewrites the whole object, and concurrent writes to unrelated files contend with each other.

**Keyed on the vault and the path**, there is one index per file. Each write touches only its own index, unrelated paths never contend, the object stays small, and no registry is needed because the identifier is computable from something the client already knows.

Following the existing convention, the domain string becomes:

```
   sg-vault-v1:file-id:path-index:{vault_id}:{path}
        |
        v  keyed hash with the vault key
   idx-pid-{snw|muw}-{hex}
```

A client that knows the path and holds the read key computes the identifier locally and issues one read. Nothing is listed, nothing is discovered, and no registry exists to be maintained or to leak.

The memo's note on exposure is correct and worth keeping on the record. The project lead: **"the user is consciously leaking that particular index, which is okay because we're still not leaking the data, which is the key point."** Precisely: an identifier locates an encrypted object. What it discloses is that an object exists at a derived location and how often it changes, which was recorded as an accepted property on 4 August.

## For Small Records, The Index Should Hold The Value

The most useful refinement available, and it follows from the type's own definition rather than from anything new.

The `idx` type is described as a **denormalised cache**, not as a pointer. That distinction matters for the records this is actually wanted for.

If the index holds an object identifier, a read costs two round trips: fetch the index, decrypt it, fetch the object it names. If the index holds the value, a read costs one.

The memo's own examples are small, hot records. The project lead: **"we need when we have the website that needs to find the index of a particular page, or to find the API keys that we need to know exactly to load a user page or load an API key page."**

An API key record with its status, limits and current credit snapshot is a few hundred bytes. An object identifier is thirty. **Spending an entire round trip to retrieve something barely larger than the pointer is the wrong trade.**

So the rule should be by size and access pattern rather than uniform:

| Case | Index contains | Reads |
|---|---|---|
| Small, hot record (key record, page metadata) | The value itself | One |
| Large file (document, media) | The object identifier | Two |
| Either | Also the commit position it reflects | For staleness and repair |

That also resolves the key vault design from earlier today cleanly. The client computes one identifier and issues one batch read, and the record it needs comes back whole.

## Mutability Is A Caching Decision

Worth choosing deliberately rather than defaulting, because the segment drives server behaviour.

The server caches `imm` forever, caches `snw` with a short lifetime, and does not cache `muw` at all, requiring match-on-write for it.

A per-path index is mutable, so the question is how many writers a given path has:

- **One writer**, which is the common case where a single service owns a path, means `snw` and short-lived server caching. For a hot record read constantly and written rarely, that caching is worth a great deal.
- **Several writers** means `muw`, no caching, and match-on-write.

So the mutability segment should be chosen per index rather than fixed, and the default for the records driving this request is probably `snw`, since the writing interface is the only thing that updates them.

## Write Order: Content First, Index Last

A rule about failure rather than about performance, and the one that decides what a reader sees when a write does not complete.

A write produces several objects. If the process fails partway, what a reader sees depends entirely on the order:

- **Index written first**: it may point at, or claim, content that was never stored. The reader gets something that does not exist. Unrecoverable from the reader's side.
- **Index written last**: it still reflects the previous version. The reader gets a complete, consistent, slightly old answer, and the next successful write corrects it.

**Content first, index last.** The index may lag; it must never point at nothing.

Where the index holds the value rather than a pointer, the same rule applies to the ordering of the object write and the index write, for the same reason: the object is the source of truth and the index is the cache, so the cache must never lead.

## What The Index Must Not Become

The rule that keeps this an index. **It must contain nothing that cannot be recomputed by walking the tree.**

If that holds, a lost or corrupted index is a performance problem with a slow recovery path, and the objects remain the only source of truth. If any field exists only in the index, the vault has two masters and no answer for which is right when they disagree. The corpus has flagged that shape repeatedly, most recently this morning in arguing that derived state stays strictly downstream.

Each entry should therefore also record the commit position it reflects, which makes staleness measurable rather than invisible and lets a repair pass confirm most entries without reading content.

## It Belongs In The Write Path

The memo is undecided. The project lead: **"something we can actually even just implement as a convention... or it needs to be an extension to the API, the actual API who writes it."**

It has to be the writing interface, because of the failure mode a convention produces. A writer that forgets does not fail, warn or log; it leaves an index that is permanently and silently wrong, and every subsequent reader gets an old version with nothing anywhere indicating why. **Silent, permanent and undetectable** is the worst available combination, and a convention produces exactly that under maintenance.

In the writing interface it becomes an invariant instead: the write succeeded, therefore the index moved, because the same code did both. That is the fifth time this session the same principle has applied, and it is worth stating for the team: **an invariant belongs where it cannot be skipped.**

On the suggestion that this could be a workflow, one caution. Index maintenance is a storage invariant, and anything expressible as a workflow step is by definition omissible from a workflow. Keep it below that layer.

## Three Cases To Specify Before Implementation

**Delete.** When a tracked file is removed, its index must be removed too. An index left pointing at the last version of a deleted file is worse than no index, because it returns content the vault no longer has.

**Rename.** A rename changes the path, therefore the derived identifier. The old index must be removed and a new one created, so a single file operation becomes two index operations. Whether a rename is even distinguishable from a delete plus a create in snapshot semantics is a question for the team.

**Repair.** A pass that walks the tree, compares against the indexes and reconciles, running on a schedule and on demand. The recorded commit position makes most comparisons cheap. This should exist in the first version rather than being added after the first divergence, because divergence is silent by nature.

## Scope Is Declared, Not Universal

Not every path needs an index. Every indexed path costs an extra write forever, and the memo's own examples are all lookup-by-known-name: a page, a user record, a key record. Most vault content is read by walking, not by name.

So **indexed should be a declared property of a path or a pattern**, which keeps the cost proportional to the benefit and makes the commitment visible.

## What The Team Needs To Decide

1. The domain string format, following the existing convention with the path included.
2. Whether an index holds a value or an identifier, and the size threshold between them.
3. The default mutability, and how a path with several writers is marked.
4. The write sequence, written down: objects, trees, commit, then index.
5. Behaviour on delete and rename.
6. The repair pass, scheduled and on demand, using recorded positions.
7. How indexed paths are declared.
8. Where in the writing interface this lives, so it cannot be bypassed.

## What This Does Not Try To Be

- **Not a new subsystem.** A new domain string and a write-path obligation inside the existing schema.
- **Not a staging area.** sgit has snapshot semantics and this does not change them.
- **Not authoritative.** Derived, rebuildable, and never the source of truth.
- **Not always a pointer.** For small hot records the index is the value.
- **Not universal.** Declared per path, because it is a permanent write cost.

## Honest Tensions

| Tension | Note |
|---------|------|
| Write amplification | Every indexed path costs more on every write, which is why scope must be declared |
| The index holding values | It halves the round trips and duplicates content, so the rebuild path and the size threshold both matter |
| Single-writer caching | Marking an index single-writer buys server caching and is wrong the moment a second writer appears |
| Stale reads | An index maintained on write can lag, which suits the platform's stated position and should still be stated |
| Repair designed late | Divergence is silent, so a repair pass added after the first incident will be added after a period of quiet wrongness |
| Deterministic identifiers | They are what make a single-request read possible and they disclose existence and update frequency at the storage layer |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the size threshold for holding the value? | Above it the index points; below it the index is the record |
| Is the default single-writer or multi-writer? | A caching decision as much as a correctness one |
| How is a rename handled under snapshot semantics? | It may not be distinguishable from a delete and a create |
| How often does repair run, and what does it cost? | Recorded positions make most comparisons cheap; the walk still has a cost |
| How are indexed paths declared, and by whom? | A permanent maintenance commitment, so the declaration should be deliberate |
| Does the batch endpoint need any change? | Probably not, since these are ordinary reads of computable identifiers |
| What is the rebuild time at realistic vault sizes? | It is the recovery path, so it should be measured rather than assumed |
