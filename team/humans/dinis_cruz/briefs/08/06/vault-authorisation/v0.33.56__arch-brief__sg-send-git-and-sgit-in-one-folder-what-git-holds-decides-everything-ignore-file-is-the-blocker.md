# Git And sgit In One Folder: What Git Holds Decides Whether The Vault Is Still Zero-Knowledge, And The Pattern Is Blocked On A Missing Ignore File

**version** v0.33.56
**date** 6 August 2026
**from** Human (project lead)
**to** Engineering, Architecture

**type** Architecture brief

*Twelfth of 6 August. Treats the dual-repository arrangement as a general pattern, with the key management vault as its first application. sgit behaviour is cited from the project record.*

---

## What This Is

A pattern the project lead wants to adopt widely, in which a single working folder is tracked by both the encrypted vault system and by ordinary version control, and two findings that shape how it should be adopted: **the pattern is worth generalising because the two systems have almost disjoint strengths, since the vault is zero-knowledge with server-side blindness, deterministic identifiers, browser-reachable objects and token-based sharing, while ordinary version control brings an ecosystem the vault will never replicate, meaning continuous integration triggers, review, blame over plaintext, and a scheduler with logs and history that costs nothing to run; the decision that determines everything is what the second system actually holds, because tracking the plaintext working files makes the hosting provider a reader of everything and dissolves the confidentiality the vault exists to provide, whereas tracking the encrypted object directory keeps the property intact and reduces the second system to a durable append-only mirror with no diff, no blame and no review, and for a store holding credentials and balances only the second is defensible; the immediate blocker is mechanical and worth knowing before the pattern spreads, since the vault takes snapshots of the whole folder and its ignore mechanism is recorded as planned rather than implemented, which means that today a folder containing both would have the vault swallowing the entire version control directory, so the ignore feature is a prerequisite rather than a nicety; three configurations follow from the fork and each suits a different case, with disjoint paths being the one most likely to serve the general use, ciphertext mirroring being right for high-confidentiality stores, and a plaintext repository holding a small encrypted vault being the inverse; the exclusion configuration on both sides is a security control rather than housekeeping, because one missing line puts credentials in a hosted repository and one missing line in the other direction puts a churning history directory inside an encrypted vault, which argues for generating both from a single declaration and verifying in the build that no path is claimed by both; and the credential design proposed for the key vault survives with one correction, that its stable half must come from the vault's own pseudo-deterministic derivation rather than from any content-addressed identifier, since those change by design whenever content changes.** It is the twelfth document of 6 August (cross-ref: the v0.33.56 sgit per-path index brief, the v0.33.56 vault-architecture brief, the v0.33.56 token-gateway brief, the v0.33.56 plugins brief, and the v0.16.3 deterministic IDs simulation). New contributions: **the dual-tracking pattern stated generally with three configurations, the plaintext-versus-ciphertext fork identified as the decision that matters, the missing ignore mechanism named as a prerequisite, exclusion configuration treated as a security control, and the cost of mirroring ciphertext into ordinary version control.**

## Why Both, And Not One

The instinct behind the memo is right, and it is worth setting out why rather than treating it as an experiment. The project lead: **"the logic is to have both git and sgit running at the same time."**

The two systems are close in shape and almost disjoint in what they are good at.

| | The vault | Ordinary version control |
|---|---|---|
| Confidentiality | Zero-knowledge; the server never sees plaintext | Access control at best, and the host can read |
| Object access | Deterministic identifiers, reachable over the network, browser-readable with a read key | Requires a client and a clone |
| Sharing outside the team | One-shot tokens, no installation needed by the recipient | Accounts, permissions, forks |
| Diff, blame, review | Within the tool, over plaintext locally | Native, universal, and the reason the ecosystem exists |
| Automation | None of its own | Scheduled actions with logs and history, at no cost |
| Merge | Not yet | Mature |

So the pattern is not redundancy. It is using each for what only it can do, and the memo's own summary of the division is the right one. The project lead: **"we are actually mainly using git for backup."**

## The Blocker: There Is No Ignore Mechanism Yet

The most immediately useful finding, because it gates adoption.

The vault system takes snapshots of the whole folder, with no staging area and no index, and its comparison documentation lists an ignore file as **planned rather than implemented**. Ordinary version control, meanwhile, keeps its entire object database and history inside a directory in that same folder.

The consequence is direct: **today, a folder tracked by both would have the vault snapshotting the version control directory on every commit.** That directory churns constantly, contains its own compressed object store, and would be encrypted object by object into the vault, growing it without bound and slowing every operation.

So the ignore feature is a prerequisite for the pattern rather than a refinement of it. Until it ships, co-existence works only where the vault is initialised in a subdirectory that does not contain the version control directory, which is a workaround rather than the pattern being described.

That is worth raising with the vault team alongside the per-path index request, because both are small features that unlock a pattern intended for wide use.

## The Fork: What Does The Second System Hold?

This is the decision everything else follows from, and the memo notices it without settling it. The project lead: **"in principle this is going to be on a private repository, unless we actually encrypt the API keys or encrypt some of the data, which is also not a bad idea, but we don't have a hundred percent good support for that yet, so let's start simpler."**

There are two things that could be tracked and they have opposite properties.

**The plaintext working files.** Diff, blame and review all work, the ecosystem is fully available, and **the hosting provider can read everything**. A private repository restricts who may clone it; it does not make the contents unreadable to the host. For a vault whose purpose is that the server never sees plaintext, mirroring the plaintext to a third party removes the property entirely.

**The encrypted object directory.** The host sees ciphertext, the confidentiality property survives, and almost every reason to use ordinary version control evaporates: no meaningful diff, no blame, no review, because every object is opaque.

```
   PLAINTEXT MIRROR                 CIPHERTEXT MIRROR
   full ecosystem                   durability and off-site copies
   diff, blame, review, PRs         no diff, no blame, no review
   host reads everything            host reads nothing
   zero-knowledge property GONE     property intact
```

**For the key vault the answer is not close.** A store holding credentials, spending limits and balances cannot have its plaintext pushed to a hosted repository, private or otherwise. The memo's instinct to encrypt was right and the conclusion should be firmer than the memo reaches: for this use, the second system tracks the encrypted object directory, and nothing else.

## Three Configurations

Given the fork, the general pattern is really three patterns. Naming them makes the choice explicit rather than accidental.

**A. Disjoint paths.** Source, documentation and automation tracked normally; configuration, credentials and customer data tracked by the vault. Neither system sees the other's paths. Both tools work natively and nothing is duplicated. **This is probably the configuration that serves most of the intended uses**, because it takes each system's strength without compromise.

**B. Vault primary, ciphertext mirror.** Everything lives in the vault; the second system tracks the encrypted objects for durability and off-site copies. This is the memo's case and the right one for the key vault. Expect to lose the ecosystem and to watch the repository grow.

**C. Repository primary, vault for the secret subset.** An ordinary project that keeps its few unpublishable things in a small vault alongside. The inverse of A, useful where the bulk is genuinely public.

The configuration should be a stated property of each repository rather than something a reader infers, because the security consequences differ completely between them.

## The Exclusion Configuration Is A Security Control

Following directly, and the most likely source of a real incident.

In configuration A, two exclusion lists must be complementary and correct. A path missing from one puts plaintext credentials into a hosted repository. A path missing from the other puts a churning history directory into an encrypted vault. **One of those errors is a leak and the other is a performance problem, and neither announces itself.**

The recommendation is to stop maintaining them by hand. **Declare once which paths belong to which system, generate both exclusion files from that declaration, and verify in the build that no path is claimed by both.** A test that fails when a vault-owned path becomes trackable by the other system is cheap and catches the only mistake in this pattern that matters.

That is the same principle applied twice already this week: an invariant belongs where it cannot be skipped, and enforcement belongs where it cannot be bypassed.

## What Mirroring Ciphertext Costs

Worth knowing before configuration B is adopted broadly, because the costs are structural rather than incidental.

Encrypted objects are indistinguishable from random data, which means they **do not compress and do not delta**. Ordinary version control depends on both to keep repositories manageable: it stores similar objects as differences and compresses aggressively. Neither works on ciphertext.

The consequence is that a mirrored vault grows roughly linearly with the total volume ever written, with no reclamation. For a store written to on every metered request, as this one will be, that is a repository that grows continuously and never shrinks.

Three mitigations are worth considering rather than discovering. Mirror on a schedule rather than on every commit, which the memo already proposes. Consider whether the mirror needs full history or only periodic snapshots, since the vault holds its own history already. And expect to rotate or truncate the mirror at some interval, which is a decision better made at the start than after the first repository becomes unwieldy.

## The Key Vault As The First Application

The pattern's first use, and the memo's actual subject.

**The lookup.** A client holding the credential computes the identifier of a per-path index and issues one read. That index is the request from the companion brief, and for a record this small it should hold the value rather than a pointer, so the lookup is a single round trip returning the key record, its limits and the current credit snapshot together.

**The write.** Usage events append to the vault's inbox: one write, no read, no coordination. The memo has this. The project lead: **"the requests that are made are saved to the inbox, and that will allow us to have a very quick write without having to process, without having to synchronise the files."**

**The normaliser.** A scheduled action drains the inbox, updates the ledger, rewrites the snapshot index, commits to the vault, and mirrors the encrypted objects to the second system. The memo proposes exactly this. The project lead: **"a scheduled action that runs regularly, and the job of that action is to do the normalisation of the requests, and basically align all the API keys."**

One constraint on that: **the normaliser is the only writer to the mirror.** Nothing else pushes, and nothing reads from the mirror on a request path. Otherwise the arrangement has two sources of truth and no answer for which is right when they differ, which the corpus has now flagged in three separate contexts.

Using a scheduled action for this is a genuine free win from the pattern, since it supplies a cron with logs, history and manual triggering without any infrastructure to run.

## The Credential Locator Must Be Stable

The memo's design question, and the one place a correction is needed. The project lead: **"how do we resolve an API key in an encrypted vault? My thinking is to actually use the object ID, probably for the tree, most likely for the commit."**

**A content-addressed identifier cannot serve as a locator**, because it is derived from content and changes whenever content changes. Object identifiers in this system are hashes computed over plaintext, so a commit or tree identifier moves on every write, and any credential built on one stops resolving immediately.

The system already provides what is needed. Its identifier scheme distinguishes content-addressed derivation from **pseudo-deterministic derivation**, computed as a keyed hash from the vault key and a domain string, which is stable by construction because it depends on nothing that changes. The vault identifier itself is likewise permanent, appearing in the vault key alongside the passphrase.

So the credential the memo arrives at works, with its first half drawn from a stable derivation rather than from the object graph. The project lead: **"we have the user ID first part, which is that static ID, and then you have the API key inside of it, so that supports multiple API keys per user, and that allows to rotate that."**

That structure is right and resolves an objection raised two days ago about credentials doubling as addresses, because the second half distinguishes many keys within one account and rotation operates on entries inside the vault rather than on its address.

## The Read Path Is Already Fast Enough

One point worth correcting, because it affects whether an optimisation is needed at all.

The system's own architecture work records that the server reads objects internally at roughly one to five milliseconds each and returns many of them in a single batched response, so the client pays one network round trip regardless of how many objects it needs. The published concern about slow object reads applies to clients fetching over the internet, not to a function reading in the same region.

**So a faster storage class is an optimisation rather than a requirement**, and there is a cheaper lever available first: the identifier scheme encodes mutability, and the server caches aggressively for immutable objects and briefly for single-writer mutable ones while never caching multi-writer objects. A key record written only by the normaliser is genuinely single-writer, so marking it as such buys server-side caching that matters more at this volume than the storage tier does.

## Eventual Consistency, As Stated

The memo's position is settled and consistent with the ledger design agreed yesterday. The project lead: **"our current business model here is not to prevent the edge case of somebody using too much credits."**

That is the right appetite for this stage. The exposure is the account's spend rate multiplied by the staleness of the snapshot, which is knowable, and the normaliser's schedule is the lever. Running it more aggressively for accounts near their threshold and slowly for everyone else concentrates the effort where the risk actually is, which is the memo's own buffer idea made specific.

## What This Does Not Try To Be

- **Not redundancy.** Two systems used for what only each can do.
- **Not a plaintext mirror.** For a credential store the second system holds ciphertext, or the confidentiality property is gone.
- **Not available today.** The vault's ignore mechanism is a prerequisite and is not yet implemented.
- **Not two writers.** The normaliser is the only thing that pushes to the mirror.
- **Not dependent on a faster storage tier.** In-region reads are already fast; caching by mutability is the cheaper lever.

## Honest Tensions

| Tension | Note |
|---------|------|
| Ciphertext mirror versus the reason to use the ecosystem | Keeping confidentiality removes diff, blame and review, which are most of what the second system is for |
| Repository growth | Encrypted objects neither compress nor delta, so the mirror grows linearly forever and will need a truncation policy |
| Two exclusion lists | They are a security control maintained as configuration, and the failure is silent in both directions |
| Waiting for the ignore feature | The pattern is wanted broadly and is not safely available until a small missing feature ships |
| Private repository as a control | It restricts who may clone and does not stop the host reading, which is easy to conflate |
| Eventual consistency | The appetite is stated and correct for now, and the exposure grows with volume rather than staying fixed |

## Open Questions

| Question | Notes |
|----------|-------|
| When does the ignore feature ship? | It gates the pattern, so its timing sets the timing of everything built on it |
| Which configuration for which repository? | Stated per repository rather than inferred, since the security consequences differ |
| Is the mirror full history or periodic snapshots? | The vault holds its own history, so full history in the mirror may be redundant |
| What is the truncation policy for the mirror? | Better decided before the repository becomes unwieldy |
| Is the key record single-writer? | If so it earns server-side caching, which is worth more here than a faster storage tier |
| How is the exclusion declaration verified? | A build check that no path is claimed by both systems |
| What is the normaliser's schedule, per account? | Aggressive near a threshold, relaxed elsewhere |
