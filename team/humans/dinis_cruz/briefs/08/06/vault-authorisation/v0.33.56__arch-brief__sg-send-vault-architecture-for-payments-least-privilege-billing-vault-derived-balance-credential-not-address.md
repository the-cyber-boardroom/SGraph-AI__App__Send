# The Vault Architecture For Payments: Four Vaults, Least Privilege On The Hot Path, And Nothing Contended

**version** v0.33.56
**date** 6 August 2026
**from** Human (project lead)
**to** Engineering, Architecture

**type** Architecture brief

*Fourth of 6 August, mapping the storage architecture. Written in response to an explicit invitation to correct it. Revised after the project lead removed the reservation step in favour of natively supported negative balances, which is the better design and is argued as such. Object storage behaviour is grounded and cited. Offered to be built on and challenged.*

---

## What This Is

The storage architecture for the metering platform, built on vaults rather than a database, together with one correction offered because the memo asks for it: **the structure proposed is a customer vault containing inner vaults for activity and for the customer's own data, with billing separated into its own vault, and the reason the memo gives last for that separation is the strongest one, because a component serving a request needs to check a balance and post a usage event and has no business holding payment details, stored documents or an activity history, so splitting billing out is what lets the hot path carry a credential scoped to one small vault; the write-without-read property is the primitive that makes the ledger work, since a component can be given a public key that lets it append usage events to a vault it cannot read, which is the third instance of an append-only channel designed in this corpus in a week and confirms it as the house pattern; the balance should be derived from an append-only event stream rather than held as a contended value, which removes the only contention in the design rather than solving it, and which supports negative balances so that settlement can run on a threshold and the cutoff becomes a per-customer credit decision; the correction concerns addressing, because making the credential the vault identifier is elegant and would block the feature that makes this platform a risk control, since budgets per agent and per action require many credentials resolving to one account, and a credential that is an address cannot be issued more than once, rotated cheaply, or scoped; and two properties deserve stating rather than discovering, that deterministic paths leak equality and therefore volume and timing to anyone with storage-level read access, and that logging everything into a vault we cannot read is a sovereignty gain that removes our ability to detect abuse of a service we are contractually responsible for.** It is the fourth document of 6 August (cross-ref: the v0.33.56 payments-not-a-billing-system brief, the v0.33.56 token-gateway brief, the v0.33.55 vaults-as-substrate brief, the v0.33.48 browser-local-databases brief, and the v0.33.51 distributed vault architecture brief). New contributions: **the four-vault structure with least privilege as the organising reason, the derived-balance ledger with nothing contended on the hot path, the argument against credential-as-address, deterministic path leakage named, and the abuse-detection tension in write-only logging.**

## The Structure, Mapped

The memo works this out while speaking and arrives somewhere good. The project lead: **"you have the main vault, which has the user information, some user data, that's where we store payment information, payment details, payment references, all sorts of confidential information we don't want normal users to access."** Then the inner vaults. The project lead: **"we can have an inner vault which is almost the user activity vault, and another vault which is the user data vault, which we can charge for in terms of size and even the activity."** Then the revision. The project lead: **"maybe even a third vault, which is just the billing element, I think that's a better way."**

```
   CUSTOMER VAULT  (master, we hold, customer does not)
     identity, payment references, contract terms
     |
     +-- ACTIVITY VAULT      every request, every action
     |                       customer readable, append-only from our side
     |
     +-- DATA VAULT          their transcriptions, documents, outputs
     |                       theirs entirely, charged by size
     |
     +-- BILLING VAULT       balance, reservations, usage events
                             the ONLY vault the gateway touches
                             shareable with the customer
```

Vault-in-vault and vault-as-link make this one addressable tree rather than four systems. The project lead: **"I can add another vault as a link to another vault, which looks like one unified file system but is actually spread across multiple vaults."**

## Why Billing Is Separate: Least Privilege

The memo gives three reasons for the third vault and the third is the one that matters. The project lead: **"that also means that we only need to give access to the agent that is actually running the request to the billing vault."**

That is the strongest argument and it should be the stated reason rather than the afterthought. Consider what the gateway does on the hot path: authenticate, check a balance, reserve, forward, reconcile, append a usage event. Consider what it therefore needs: a balance and a place to write events. Consider what it does not need: payment details, contract terms, stored documents, or the customer's history.

**Separating billing means the most exposed component in the estate holds a credential to the smallest and least sensitive vault.** If the gateway is compromised, the blast radius is one customer's balance and their usage counters, not their payment references or their documents. That is the plug-profile discipline from the risk work applied to our own architecture, and it is worth stating in those terms.

It also has the commercial property the memo names, that a billing vault shareable with the customer is the provenance record described yesterday, held by the person it describes.

## Write Without Read Is The Ledger Primitive

The memo identifies the mechanism and it is the right one. The project lead: **"there's a technique where you can write to a vault even without having privileges to read it, which is very important; we call it a messaging system that exists in vaults."** With the mechanics. The project lead: **"you create a public key and a private key, and then you give the public key to the other vault, so it can send a message signed with this key."**

Applied to usage events this is exactly correct. The gateway appends an event for every request; it cannot read the history it is appending to; the customer and the billing process can. Three properties follow: a compromised gateway cannot exfiltrate a usage history, cannot alter past events, and cannot suppress an inconvenient one.

**This is the third append-only channel designed in this corpus in a week**, after the write-only telemetry of 2 August and the staging folder of the same day. That brief named it as an emerging house pattern; three instances confirm it. The rule worth stating: **a component that must communicate should default to a channel it can write and cannot read**, and any component needing read access should have to justify it.

## The Balance Is Derived, Not Contended

The memo asks for correction and the first thing to say is that an earlier draft of this architecture proposed a reservation step, and that was wrong. The project lead: **"correct me if I'm wrong, but I think this already gives us most of the pieces of the puzzle."**

It does, and the missing piece is smaller than a reservation. **The balance should be derived from an append-only event stream rather than maintained as a contended value.** Every request appends a usage event under a unique key; nothing is read-modify-written on the hot path; the balance is a fold over events, cached in a periodic snapshot.

That removes the only contention in the design and it removes it entirely rather than solving it. There is no lost-update problem because there is no shared mutable object. There is no retry because there is nothing to lose a race against. And the decision to serve or refuse becomes a policy applied to a balance that may be a few seconds stale, with **negative balances supported natively**, which is what makes threshold settlement possible.

```
   events/<ulid>        one object per request, unique key, no contention
        |
        v  fold, periodically
   snapshot             balance as of an event position
        |
        v
   policy               serve while balance > threshold
                        threshold may be negative
```

Object storage suits this shape unusually well, because unique-key appends have no coordination requirement at all and the whole cost is one write per request.

**Where conditional writes still earn their place** is off the hot path, on the few objects that genuinely have more than one writer: the snapshot, if more than one process may produce it, and the credential record described below. Object storage supports this natively through precondition headers, using an existence check for create-only writes and an entity-tag match for compare-and-swap, returning a precondition failure the caller retries against fresh state. It has been available at no additional charge in all regions since November 2024, and the equivalent exists on other major object stores. Worth knowing it is there; worth not needing it on the path that runs a thousand times a minute.

## The Ledger Shape

| Object | Written by | Contention | Consistency |
|---|---|---|---|
| `events/<id>` | The gateway, one per request | None, unique keys | Append-only |
| `snapshot` | A periodic process | Low, one writer if arranged | Derived, rebuildable |
| `credential/<id>` | Administration, rarely | Low but real | Compare-and-swap where needed |

Events are the audit trail, the billing source and the provenance record at once, and they grow without bound, which is what the customer reads and what the size charge applies to. The snapshot keeps balance derivation cheap and is always rebuildable, because events are immutable. Nothing on the hot path is shared, which is the property worth protecting as volume grows.

## The Correction: The Credential Should Not Be The Address

The memo floats an elegant idea. The project lead: **"we could even have the vault ID be the API key, and then the access ID, and the access secret can be the actual secret that only exists inside the vault."**

It is elegant and I would not do it, for a reason that comes from yesterday's brief rather than from cryptography.

**The feature that makes this platform a risk control is budgets per agent, per action and per customer.** That was the whole reframing: the ability to bound what any individual agent can spend, which is the containment control the outbound maturity model said nobody implements. That requires **many credentials resolving to one account**, each with its own budget, its own scope and its own revocation.

A credential that is an address cannot do that. If the key is the vault identifier then there is one credential per vault, so per-agent budgets require a vault per agent, rotation means re-addressing, and revoking one agent's access means moving the data everybody else is using.

The alternative is a small indirection that costs one lookup:

```
   credential (access id + secret)
        |
        v
   CREDENTIAL RECORD     -> account, scope, budget, expiry, status
        |
        v
   BILLING VAULT         -> balance, events
```

That gives many credentials per account, per-credential budgets and limits, revocation without touching data, and rotation as an ordinary operation. It also preserves the property the memo is reaching for, since the lookup itself can be a deterministic vault path and therefore still a couple of storage reads rather than a database query.

The memo's own instinct about efficiency survives intact. The project lead: **"you're just reading two or three files from S3, so that scales spectacularly."** One extra read buys the entire per-agent budget capability.

## Deterministic Paths Leak Equality

Worth stating rather than discovering, because the memo relies on the property. The project lead: **"the vaults are designed with an architecture where a couple of elements are deterministic, although they're encrypted, which means it's very efficient to read data from a vault with a couple of requests."**

That is the right technique and it has a known consequence. Deterministic derivation means the same input always produces the same path, which is what makes lookup possible without an index. It also means **anyone with read access at the storage layer can see how many objects exist under a given derived path, how fast they arrive, and when**, without decrypting anything.

For a billing vault that discloses request volume and timing per customer. That is probably acceptable, and it should be an accepted risk with a named owner rather than an unexamined property, particularly since the platform's own pitch is that customers can verify what we can see.

## Logging Everything, And What It Costs Us

The memo proposes total logging and it is right for the product. The project lead: **"I think we should have a mode where we log everything by default, so every single request, every single action is logged, which the user can then access."**

That is the provenance-of-inference product from yesterday, and delivering it into a vault the customer can read is what makes it credible rather than promised.

**The tension is that a log we cannot read is a log we cannot police.** The gateway will be contractually responsible for what passes through it, upstream providers impose their own content restrictions, and the previous brief recorded that the incumbent router enforces exactly this with blocked requests. If every request is encrypted to a vault only the customer can open, then abuse detection has nothing to work with.

The available positions are worth choosing between explicitly rather than arriving at:

- **Metadata only on our side.** We retain model, token counts, cost, timestamps and outcome, never content. Abuse detection then works on volume, pattern and cost rather than on what was said, which is weaker and may be sufficient.
- **Customer-held content, provider-held enforcement.** We rely on the upstream provider's own filtering and pass its refusals through, which is honest and outsources the judgement.
- **A break-glass path.** Technically possible and, in a system whose selling point is that we cannot read, corrosive to the entire claim.

The first two combine well. The third should be declined, and declining it publicly is worth more than the capability.

## Cost And Rate At Scale

Two practical items the memo does not reach, both cheap to handle early.

**Object writes have a per-request cost and a per-prefix rate limit.** A usage event per request means a write per request. At modest volume this is irrelevant; at agent volume it is a line item and eventually a throttle. The batching and local buffering pattern designed for telemetry on 2 August applies directly: accumulate events, flush on a boundary, and clear only on confirmed write.

**Unbounded logging needs a retention position.** The memo charges by size, which is the right mechanism, and a customer who never deletes will accumulate indefinitely. A stated default, with the customer able to keep more by paying more, turns an operational problem into a pricing feature.

## What This Replaces

Worth naming because it is the strongest argument for the whole design. A conventional implementation of this platform would need a relational database for accounts and balances, a separate store for usage events, an object store for documents, a secrets manager for provider keys, a queue for asynchronous reconciliation, and an identity system.

This design has **one substrate**, addressed as a filesystem, encrypted client-side, readable from a browser with a read key, writable from a function, deployable on a laptop or an instance, and with the customer holding their own copy of everything that concerns them. The memo's summary is accurate. The project lead: **"this will run anywhere, from a laptop, from a SaaS service, from a Lambda function, from EC2."**

## What This Does Not Try To Be

- **Not a database replacement in general.** It is a good fit here because the access patterns are simple and the encryption requirement is hard.
- **Not a reservation system.** Nothing is reserved; usage is appended and the balance is derived.
- **Not addressed by credential.** The credential resolves to an account through an indirection, which is what makes per-agent budgets possible.
- **Not opaque to the storage layer.** Deterministic paths disclose volume and timing.
- **Not policeable if we log only to the customer.** That is a deliberate trade with two workable positions and one that should be refused.

## Honest Tensions

| Tension | Note |
|---------|------|
| No database versus operational familiarity | The design is genuinely simpler and unfamiliar, and the failure modes will be unfamiliar too |
| Derived balances versus credit exposure | Removing contention means serving against a slightly stale balance, so the worst case is spend rate multiplied by staleness, which should be measured rather than assumed |
| Customer-readable logs versus abuse detection | Sovereignty and policing pull directly against each other, and the honest answer keeps content out of our hands and accepts weaker detection |
| Deterministic paths versus metadata leakage | The efficiency is the point and the disclosure is real, and the platform's own transparency pitch makes it harder to leave unstated |
| Log everything versus storage growth | Charging by size aligns the incentive and does not bound the worst case |
| One substrate versus one dependency | Everything running on vaults means a vault defect is a total defect, with no fallback path anywhere in the estate |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the negative threshold, and who sets it? | A per-customer credit decision rather than a storage property, with an owner and a review interval |
| What does a credential record contain? | Account, scope, budget, rate limit, expiry, status, at minimum |
| Where does the credential lookup live? | A deterministic path preserves the two-reads property |
| Is the deterministic-path disclosure accepted? | It should be a named accepted risk rather than an unexamined property |
| Which abuse-detection position? | Metadata only, provider enforcement, or both, with break-glass declined |
| What is the default retention? | A stated default with paid extension turns growth into pricing |
| Are usage events batched? | The telemetry pattern applies, and per-request writes will eventually throttle |
