# The State Machine Belongs In The Kernel: The Vault Currently Sees Operations And Not Flows, Which Is Why It Cannot Tell An Injected Action From A Legitimate One

**version** v0.33.56
**date** 6 August 2026
**from** Human (project lead)
**to** Engineering, Architecture, AppSec

**type** Architecture brief (investigation)

*Ninth of 6 August. An investigation brief rather than a design: it frames the problem, names the established pattern, and sets out what needs establishing. Security research is grounded and cited, including the pattern's documented limitations. Offered to be built on and challenged.*

---

## What This Is

An investigation into moving the execution engine built for one project down into the vault itself, prompted by a security observation the memo makes and understates: **the vault today authorises operations one at a time, so the question it can answer is whether a credential may write a given path, and never whether that write is the next legitimate step in something somebody started, which means a read, an inference call and a write are three unrelated authorisations with no notion that they belong together, and an instruction injected into content can produce an action that is individually well-formed and correctly authorised while being entirely outside what was asked for; declaring the flow and having the vault hold it changes the authorisation question from per-operation to per-transition, and this is a named and studied pattern rather than an invention, since published work on securing agents identifies plan-then-execute as establishing control-flow integrity by determining the sequence of actions from trusted input so that untrusted data cannot inject new steps or divert execution, with a companion analysis describing an operating-system reference monitor as the closer analogy; the same literature names the residual weakness precisely, that untrusted data read during a plan can still influence the arguments passed to later steps within it, so this constrains which actions occur and not what they carry, and the corpus should claim the first and not the second; the argument for the kernel rather than the application is the classical one for a reference monitor, namely complete mediation, tamper-resistance and verifiability, and the third of those is the answer to the memo's own worry about complexity, because a reference monitor that is too large to analyse has failed on its own terms, which turns simplicity from a preference into a requirement of the pattern; the kernel should therefore be a referee rather than a player, holding the transition graph, tracking which state an execution occupies, permitting or refusing the next operation and decrementing a budget, while executing nothing itself; and the sharpest open question is how the kernel learns that a step performed outside it actually happened as declared, where the elegant answer is that an external step advances the machine only by depositing its output into the vault, so the write is the attestation rather than a claim about one.** It is the ninth document of 6 August (cross-ref: the v0.33.56 workflow state machine brief, the v0.33.55 vaults-as-substrate brief, the v0.33.48 fractal semantic graphs brief, the v0.33.49 distributed vault architecture brief, and the v0.33.56 payments-not-a-billing-system brief). New contributions: **the authorisation question reframed from per-operation to per-transition, the identification of the established pattern and its documented limit, verifiability as the constraint that bounds the complexity, the referee-not-player boundary, and the write-as-attestation answer to external steps.**

## The Problem: Operations, Not Flows

The memo's diagnosis is the important part and deserves stating more sharply than it states itself. The project lead: **"if you think about a flow that right now is read file, execute LLM, write file, do something else, all of those actions are already done outside the vault, but there's no context, there's no understanding, because every request is in isolation."** With the consequence. The project lead: **"even if there's a mistake or a prompt injection or something wrong, there's no way for the vault itself to know the difference when requests are being executed out of order, or a request that is doing stuff that is not supposed to do."**

Put precisely: the vault is a store with permissions, so the only question it can answer is a capability question.

```
   TODAY                                  WITH A FLOW IN THE KERNEL
   "may this credential write here?"      "is this the next legal step
                                           in the execution this
                                           credential is running?"

   answerable per operation               answerable per transition
   an injected action that is             an injected action is
   individually permitted passes          out of sequence, and fails
```

That is the same distinction as a packet filter and a stateful firewall. A filter can only ask whether a packet is allowed; a stateful inspector can ask whether it belongs to a connection somebody established. **The second catches things the first cannot see, not because the rules are stricter but because it has memory.**

## This Is A Named Pattern

Worth knowing before designing anything, because the pattern has been studied and its properties are documented.

Published work on securing agents against prompt injection sets out a guiding principle that matches the memo's instinct: once an agent has ingested untrusted input, it must be constrained so that the input cannot trigger consequential actions. The paper argues that general-purpose agents with broad capabilities are inherently hard to secure with current technology, because the available defences are heuristic, and that the tractable route is structural constraint.

Among the patterns it defines, **plan-then-execute** is the one being proposed here: an agent formulates a plan, meaning a fixed list of actions, and then executes it, and although the tool calls in that plan may read untrusted third-party data, that data cannot cause deviation from the plan. The paper describes this explicitly as **a form of control-flow integrity**, and analysis of it puts the mechanism plainly: the sequence of actions is determined from trusted input, which prevents untrusted data from injecting new steps or diverting execution.

A related line of work describes an approach functioning like a classical operating-system reference monitor, but for agent tools, which is the closer analogy for what a vault kernel would be.

So the investigation is not into whether the idea works. It is into how it fits this architecture.

## And The Pattern Names Its Own Limit

Important, because it determines what the corpus may claim.

The same analysis records the residual weakness: untrusted data read by tool calls within a plan **can still influence the arguments passed to later tool calls in that plan**. Control-flow integrity constrains which actions occur, not what those actions carry. Practitioner commentary makes the same point about data flow, noting that a locked-down control flow still permits a script to combine data from several sources and pass the result into a single privileged call.

Applied here: a flow declared as read, summarise, write is protected against an injected instruction adding a fourth step or reordering the three. It is **not** protected against an injected instruction causing the summary itself to contain something it should not, which then travels through the legitimate write.

That is a real limit and the corpus should state it rather than discover it. The mitigation is elsewhere and is already in the corpus: content-level constraints, isolated processing of untrusted material, and the position taken in July that untrusted input is treated as data and never as instruction. Sequence integrity is one layer of a defence in depth, and the follow-up literature says the same, recommending least privilege, task-scoped access and sandboxed execution alongside.

## Why The Kernel And Not The Application

The memo's instinct is right and the reason is classical. The project lead: **"we can then do it at the vault kernel level, not at the vault app level."**

A reference monitor has three required properties, and each maps onto why this cannot live in the application:

**Complete mediation.** Every access must pass through it. A control in the application is bypassed by not using the application, and the vault is reachable by other means, so an application-level state machine constrains only well-behaved callers, which are not the ones that matter.

**Tamper-resistance.** It must not be modifiable by what it governs. An engine running in the same context as the agent it constrains is not a constraint.

**Verifiability.** It must be small enough to be analysed and believed.

The corpus has now reached the same conclusion three times from different directions: privacy tiers became real when enforcement moved from client advice to key-level restriction on 28 July, and the billing brief earlier today concluded that a spending ceiling in the client is convenient and unenforceable. **The rule is worth stating once: enforcement belongs at the layer that cannot be bypassed**, and everything above it is a convenience.

## Verifiability Is The Answer To The Complexity Worry

The memo raises the right concern. The project lead: **"I don't want to add a lot more complexity, but I think this is a good example of actually this could simplify things."**

The reference monitor's third property turns that from a preference into a constraint. **A monitor too large to analyse has failed on its own terms**, so the size limit is not a matter of taste; it is what makes the pattern work.

Which yields a concrete design rule: if the kernel component cannot be read and understood in a sitting, it is the wrong component.

## The Kernel Is A Referee, Not A Player

The way to stay inside that bound. The kernel needs to do five things and nothing else:

| The kernel does | The kernel does not |
|---|---|
| Hold a flow definition, opaque except for its transition graph | Interpret what a step means |
| Track which state an execution occupies | Execute anything |
| Permit or refuse the next requested operation | Call models, read for you, orchestrate |
| Decrement a budget and refuse when exhausted | Decide what should happen next |
| Record what happened | Retry, schedule, or recover |

It says yes or no and keeps score. Everything else stays where it is today, which is why this can simplify rather than complicate: the application stops carrying enforcement it cannot enforce, and the kernel gains a small mechanism that makes the enforcement real.

That is the same discipline the workflow brief set for the application layer earlier today, which warned against building an orchestration platform and asked for a declaration format, a runner and a renderer. The kernel version is smaller still.

## Inside, Outside, And The Attestation Question

The memo proposes a split. The project lead: **"distinguish between execution code or methods that are outside the vault, which will be whitelisted, and methods that are inside the vault, which can be more dynamic."**

That is the right split and it exposes the hardest question in the investigation.

An operation performed **inside** the vault is verifiable by construction: the vault did it, so it knows it happened and what it produced. An operation performed **outside** is not: the caller returns and says a step completed, and the kernel has only that claim.

If the kernel advances on assertion, an attacker who can make calls can walk the machine forward without doing the work, which reintroduces exactly the problem being solved.

The elegant answer available in this architecture is that **an external step advances the machine only by depositing its output into the vault.** The write is the attestation. There is no separate proof to design, because the artefact is the evidence:

```
   step 2: summarise (external)
        |
   caller performs it, writes the result to the step's declared output path
        |
   kernel observes the write, validates it against the step's declared shape
        |
   machine advances to step 3
```

That has three properties worth having. Nothing advances without an artefact. The artefact is retained, so the execution record is complete rather than asserted. And it composes with the append-only channels the corpus adopted as its house pattern this week, where a component writes to a place it cannot read and the receiving side does the interpretation.

It also has a cost, which is that every external step must produce something writable, and some steps legitimately do not. Whether a null artefact is acceptable is one of the things to establish.

## Budget At The Kernel Level

The memo names this and it is the connection to the rest of the week's work. The project lead: **"even if you want to do stuff like budget limitations and other things, we can then do it at the vault kernel level."**

The workflow brief earlier today put a budget on each step in the declaration. This puts the enforcement where it cannot be bypassed, which is the difference between a declared budget and an enforced one, and it completes an argument the corpus has been assembling for two weeks: the maturity model of 27 July identified spend ceilings as the cheapest unimplemented containment control, this morning's brief made them a product, and the kernel is where they stop being advisory.

It also makes a workflow's cost bounded by something other than trust. A flow whose steps sum to a declared maximum cannot exceed it, whatever the calling code does.

## Define Once, Reuse

The final motivation and a good one. The project lead: **"we define the vault schema and the vault execution schema once, and then we reuse on other vaults."**

That is the same argument made on 31 July for a document-agnostic ontology: a schema describing flows in general serves the next vault without modification, whereas one encoding this project's steps will need rewriting for the second. The investigation should therefore test the schema against at least two unlike flows before it is settled, and the transcription flow plus something structurally different is the obvious pair.

## What The Investigation Needs To Establish

Framed as questions with a bias toward answering them cheaply.

**Does a minimal kernel state machine stay small?** Prototype the five responsibilities above against the existing transcription flow and measure the result. If it is large, the boundary is wrong.

**What is the mediation surface?** Every path by which a vault operation can occur, and whether the kernel genuinely sits across all of them. If any path bypasses it, complete mediation fails and the security claim goes with it.

**How is an external step attested?** The write-as-attestation proposal above, tested against a step that produces nothing.

**What is the performance cost?** A state check on every operation, on the hot path, at the scale the payments work anticipates.

**What happens to a stuck execution?** Timeouts, abandonment, and whether a half-completed flow holds a budget reservation indefinitely.

**Does the schema survive a second flow?** Tested rather than assumed.

**And what is the failure mode of the kernel itself?** Every vault would depend on it. A defect in a store loses data; a defect in an execution kernel refuses legitimate work across every application at once.

## What This Does Not Try To Be

- **Not a design.** An investigation brief, framing the problem and the pattern.
- **Not a novel pattern.** Plan-then-execute with kernel enforcement, both established.
- **Not a defence against everything.** It constrains which actions occur, not what they carry.
- **Not an orchestration engine.** A referee that permits, refuses and counts.
- **Not a replacement for the application-level engine.** That declares the flow; this enforces it.

## Honest Tensions

| Tension | Note |
|---------|------|
| Simplification versus a new kernel component | The memo hopes this simplifies, and it adds a component in the least forgiving place in the estate |
| Control-flow integrity versus what it does not cover | It genuinely prevents injected steps and does nothing about injected content within a legal step, and the claim must not drift |
| Kernel enforcement versus iteration speed | Flows become a kernel concern, which slows the application layer's ability to change them |
| Complete mediation versus existing access paths | The security property holds only if every route goes through the monitor, which may not currently be true |
| Write-as-attestation versus steps with no output | Elegant where an artefact exists and awkward where the step is a check or a notification |
| One kernel, every vault | Reuse is the point and it makes a single defect a total defect, with no fallback anywhere |
