# Vaults As The Substrate: Asynchronous Collaboration Between Agents With Different Responsibilities, Through Encrypted Folders

## What This Is

A paradigm rather than a feature, in which several agents with distinct responsibilities collaborate by writing to and reading from encrypted folders in a shared vault, without ever addressing each other directly: **the essential properties are that each participant has its own responsibility, capability and focus, that they communicate through documents and issues in a durable shared medium rather than through calls or sessions, and that the exchange is asynchronous, which is not an implementation convenience but the load-bearing property, because it is what allows the arrangement to scale and what produces attention to detail; on scale, no participant blocks on any other, none needs to know who else exists, and adding a participant costs nothing at the other end; on attention, an asynchronous message is written completely rather than incrementally, is read when the reader has capacity rather than mid-task, and for agents specifically means the reader brings its full context to the message instead of splitting it between a live exchange and the work in hand; this is the blackboard architecture, a pattern established in the nineteen-eighties and recently revived for language-model agents, where recent measured work reports substantial improvements over the more common arrangement in which a controller assigns tasks to sub-agents it must already understand; and what the vault adds is precisely what that literature names as unresolved, since persistent shared state is widely recognised as valuable while how it should be authorised, audited and updated during long collaborations is described as an open question, whereas an encrypted versioned vault answers all three by construction, with keys and paths determining who may write where, commit history providing the audit trail without anybody building one, and cryptographic authenticity meaning a message from another agent can be distinguished from text an agent merely read somewhere.** It is the sixth document of 2 August (cross-ref: the v0.33.55 monitoring-vault brief, the v0.33.54 vault-authors-repo-publishes brief, the v0.33.51 distributed vault architecture brief, the v0.33.48 fractal semantic graphs brief, and the v0.33.53 scaling-collaboration brief). New contributions: **the vault named as a communication substrate rather than a store, asynchrony argued as the source of both scale and care, the agent-specific context argument for asynchronous messaging, the identification that the vault answers the authorisation and audit gap the literature leaves open, and permissions restated as the interface contract between agents.**

## The Pattern, Stated Plainly

Strip away what was built this week and the arrangement is this:

```
   AGENT A                    THE VAULT                    AGENT B
   own responsibility     encrypted folders            own responsibility
   own capability         documents, issues            own capability
   own focus              versioned, permissioned      own focus
        |                                                    |
        +----------- writes where it may ------------------->|
        |<---------- reads when it chooses ------------------+

   neither addresses the other. neither waits for the other.
   the folder is the interface.
```

No participant calls another. No session exists. Nobody needs to be running at the same time. What passes between them is a document in a folder, and the folder's permissions define what each may do.

The project lead's own description names the essential asymmetry. The project lead: **"we now have two types of agents: one with kind of more agency, which is the main chat session, and then one which is basically just direct input and output from inside the vault app."** And the chain. The project lead: **"you basically have the Claude communicating to the outer vault, communicating to the vault app, communicating with the agent running inside the vault app, and vice versa."**

The important word in that last sentence is *through*. Nothing communicates *with* anything; everything communicates *through* the vault.

## This Is A Blackboard, And The Comparison Is Favourable

The pattern has a name and a long history, which is worth knowing because it means the design decisions have been argued before.

Blackboard architectures date to the nineteen-seventies and eighties and coordinate independent contributors through a shared structured workspace rather than direct communication. Agents observe the workspace, decide whether they can contribute, and post results back. The classical description is a room of experts sharing a board: one writes a partial result, another sees it and adds to it, and nobody holds a one-to-one conversation.

The pattern has been revived for language-model agents and the reported results are strong. One study contrasts it with the prevailing arrangement, in which a central controller assigns subtasks to specific agents, and reports relative improvements in end-to-end task success between thirteen and fifty-seven percent across proprietary and open models. The reason offered is instructive: a controller assigning work must already possess precise knowledge of every sub-agent's capabilities, and faces genuine ambiguity when several agents have overlapping expertise. A blackboard removes that requirement, because the contributor decides whether it can help rather than being told.

Recent analysis also observes that coordination failures, ambiguous handoffs and redundant communication remain central problems in multi-agent systems, and concludes that the communication substrate deserves to be treated as a first-class object in the design rather than as plumbing. That is precisely the shift the memo is describing.

## What The Vault Adds Is What The Literature Leaves Open

Here is the part worth stating loudly, because it identifies where this work sits relative to everybody else's.

The same literature that establishes the value of persistent shared state describes an unresolved question: **how that state should be updated, authorised and audited during long-horizon collaboration.** Shared memory is easy to propose and hard to govern. Who may write what, how a bad write is detected, how the history is reconstructed afterwards, and whether a participant can read what it should not, are all left as future work in the papers proposing the pattern.

An encrypted, versioned, permissioned vault answers all of them by construction rather than by addition:

| The open question | What the vault does |
|---|---|
| Who may write, and where | Keys and paths, enforced cryptographically rather than by convention |
| Who may read | The same, so a participant can be given a channel it can write to and cannot read |
| What happened, and when | Commit history, without anybody building an audit facility |
| How a change is attributed | The write is signed by whoever made it |
| How the state is recovered | Versioning, so any prior state is reachable |

**That is the contribution.** The blackboard pattern is not new and the measured advantages are already documented. What has not existed is a blackboard where authorisation, audit and confidentiality are properties of the medium rather than of an application built on top of it.

## Why Asynchrony Is Load-Bearing

The memo flags this as important and it deserves developing, because two distinct benefits are usually collapsed into one.

**It is what allows scale.** No participant blocks on another, so throughput is not limited by the slowest. No participant needs to know who else exists, so adding one costs nothing at the other end. Nobody needs to be running simultaneously, so a message written today can be acted on next week by something that did not exist when it was written. The blackboard literature makes the same point: agents need not all be active at the same time, and one can post something and go idle until something relevant appears.

**It is what produces attention to detail**, and this is the less obvious half. Three mechanisms:

A synchronous exchange demands a response at whatever quality is available in that moment. An asynchronous message is **composed completely before it is sent**, which is a different kind of artefact from a turn in a conversation. There is no half-formed thought that gets corrected two messages later.

The reader engages **when it has capacity**, not when the sender happens to speak. Nobody is interrupted mid-task, which is the same argument the corpus made on 28 July about coordination cost: the interruption is the expensive part, not the information.

And for language-model agents specifically there is a mechanism that does not apply to people. An agent interrupted during a task must hold both the task and the interruption in its context at once, and both suffer. **An agent that reads a queue between tasks brings its whole context to each item.** Asynchrony is therefore not merely more polite; it produces measurably better work from a participant whose attention is a hard, finite resource.

## Roles Are Defined By Responsibility, Capability And Focus

The memo's framing of the participants is better than a size distinction, and it should be adopted as the vocabulary. Agents differ by what they are responsible for, what they are able to do, and what they are attending to, and those three determine everything else about them.

| | Responsibility | Capability | Focus |
|---|---|---|---|
| A long-running builder | Changing the artefact correctly | Full read and write within its scope, long context, judgement | The whole body of work |
| An embedded narrow agent | Faithfully structuring what it is given | Append to one folder, no judgement | The single item in front of it |

The consequences follow directly. Different permissions, because responsibility differs. Different models, because capability differs and a narrow structuring task does not need an expensive one. Different failure modes, because a builder's mistake is an incorrect change and a narrow agent's mistake is a garbled record. And different trust, which is why the narrow agent must not be allowed to exercise judgement about what deserves to reach the builder: an embedded participant that filters is a gatekeeper nobody appointed.

The corpus already has a defined role ecosystem covering orchestration, execution, intelligence and governance, and this paradigm is what makes those roles operational rather than notional. Each role becomes an agent with its own folder permissions, and the ecosystem document becomes an interface specification.

## Permissions Are The Interface Contract

The single most important design decision in the arrangement is not which agents exist but who may write where.

The project lead describes the specific choice made. The project lead: **"normally we're not allowing the app to modify files from the vault because we've got a permission model, in this case we actually allow it, a specific file in a staging folder, like a workspace."**

That is the same split-by-path discipline settled on 31 July for publishing, where generated files flow one way, contributed files flow the other, and no file has two writers. Here it becomes general: **a path with a single writer and defined readers is an interface between two agents**, and the set of such paths is the system's architecture.

Stated that way, several things become clear. The permission model is the API. Adding a participant means granting a path, not changing anybody else's code. A compromised participant can only affect what it could write, which is the blast-radius reasoning the plug work applies to systems, applied here to components. And the arrangement is inspectable: you can read the permission map and know what can influence what, which is not true of a system where agents call each other.

## The Channel Is Human-Readable, Which Makes It Three-Way

A property that distinguishes this from a message queue and that the memo demonstrates without naming.

What passes between the agents is documents and issues, not serialised payloads. So a person can open the folder, read the exchange, add to it, and correct it, using the same mechanism the agents use. There is no separate human interface onto the machine conversation, because the machine conversation is already in a form people read.

That makes the substrate three-way rather than two-way, and it is why a person speaking an observation into the demo could enter the same channel the agents were already using. The corpus argued on 28 July that material must be readable by people and by agents alike, and on 31 July that agent-maintained coordination requires agent-readable storage. This is both conditions met by the same choice.

It also means the exchange is reviewable after the fact by somebody who was not present, which no synchronous arrangement offers.

## Cryptographic Authenticity Is Injection Defence

A security property that follows from the medium rather than from vigilance, and one the corpus specified earlier this year when defining agent-to-agent communication with sequencing enforced by keys and injection defence achieved cryptographically.

An agent reading arbitrary content faces a standing problem: text that instructs it may arrive inside data it was merely asked to process. When messages between agents are authenticated by the medium, that ambiguity narrows considerably. A message in a folder written by a known key is a message from that participant. Text encountered anywhere else is data, whatever it claims about itself.

This is the same structural defence the corpus described on 12 July for the graph, where untrusted input is treated as data and never as instruction so that injection fails at the validator rather than being caught by inspection. The substrate makes the distinction rather than requiring the agent to make it.

## The Instance That Demonstrated It

The workflow assembled this week is one instance of the pattern and is worth recording as such rather than as the subject.

A person exploring the running demo spoke an observation. A narrow agent inside the application structured it and wrote it as an issue into a staging folder it was permitted to append to. The agent editing the main vault read that issue in its own time and acted on it. Voice made the capture pleasant and is not the mechanism; the mechanism is that two agents with different responsibilities exchanged a document through a permissioned folder without either waiting for the other.

The observation itself was that one risk was appearing at several altitudes when each executive should hold their own, which happens to confirm the diagnosis made in yesterday's review that the registers are a chain rather than parallel lists. That is a pleasing coincidence and it is not what makes the day a milestone.

## What This Enables

Because the substrate is general, the same arrangement supports things nobody has built yet:

**More participants without more coordination.** A quality role, a security role and a librarian role can all read the same folders and write to their own, without the builder being told they exist.

**Participants that do not yet exist.** A message written today is readable by an agent configured next month, because the medium outlives the session.

**Cross-boundary collaboration.** The permission model is cryptographic, so a participant belonging to a different organisation can be given exactly one writable path, which is the shape the partner and freelance models have wanted since July.

**Human participants on equal terms.** A person is a participant that reads and writes the same folders, which is the corpus's own working method already, one layer up.

## What This Does Not Try To Be

- **Not a feature of the demo.** The demo is where it was first exercised.
- **Not direct agent-to-agent messaging.** Nothing addresses anything; everything writes and reads.
- **Not synchronous.** Asynchrony is the property that produces both the scale and the care.
- **Not a new pattern.** A blackboard, with authorisation, audit and confidentiality supplied by the medium.
- **Not dependent on voice.** Voice is a pleasant capture method for one participant.

## Honest Tensions

| Tension | Note |
|---------|------|
| Asynchrony versus responsiveness | The literature notes a blackboard may wait for somebody to notice a state, so nothing here is suitable where a fast answer is required |
| The shared medium as a bottleneck | Documented as the pattern's main weakness when many participants read and write at once, and unmeasured here |
| No central coordinator versus nothing happening | Contributors self-selecting is the pattern's strength and means a message can sit unread with nobody accountable for noticing |
| Human-readable messages versus precision | Documents are legible and looser than a schema, and ambiguity between agents is a documented cause of coordination failure |
| Permissions as the architecture | It is inspectable and only as good as its enforcement, which is a property of the implementation rather than the design |
| Roles multiplying | Adding participants is cheap, which is exactly how a system acquires more agents than anybody can reason about |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the message contract? | Documents are readable and loose; some minimum structure per channel would reduce ambiguity without losing legibility |
| How does a participant know something is waiting? | Polling, notification, or a convention, and the answer determines the latency of the whole system |
| Who notices when nothing happens? | A message nobody picks up is the pattern's characteristic failure and needs an owner |
| Is the permission split enforced or conventional? | The difference between an architecture and an agreement |
| How are messages acknowledged? | A sender that never learns its message landed will eventually stop sending |
| What is the map of paths? | The permission map is the architecture, so it should be a document rather than an emergent property |
| Does this extend across organisations? | The cryptographic model suggests yes, and it would change the partner model materially |
