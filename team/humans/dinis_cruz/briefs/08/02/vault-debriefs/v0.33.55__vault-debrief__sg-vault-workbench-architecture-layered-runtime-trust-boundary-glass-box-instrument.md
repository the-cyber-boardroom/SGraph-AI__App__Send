# SG/Vault Workbench — Technical Architecture

**Subject:** `workbench.html` v0.6.8 — a single-file, in-vault LLM agent workbench
**Audience:** engineers and agents replicating these patterns; contributors to the `sg.llm.*` kernel migration
**Companion doc:** `DEVELOPER.md` (code-level implementation guide with annotated source and replication recipes)

---

## 1. Executive summary

The Workbench is one self-contained HTML file (~138 KB, one inline ES module, zero build step, zero framework) that turns a zero-knowledge encrypted vault into an observable agent environment:

- An **LLM REPL** over any OpenRouter model, streaming, with a budget-capped API key read from a file *inside the vault*.
- A **typed, tiered, audited tool execution center** giving the model read/write access to vault files.
- A **glass-box instrument layer**: the exact prompt bytes (context composer), every LLM call with reconciled real cost, every vault I/O operation, every staged change — all visible, all the time.
- **Ephemeral multi-chat + file-based memory**: conversations are short-lived; durable context is a curated, selectable set of files.
- **Staging → commit** semantics over a vault that otherwise auto-commits every write.
- **Full-state sessions**: everything (chats, invocations, audit, staged edits, memory, layout) snapshots to a single JSON file in the vault and restores from it.
- A **preview engine** that can render any vault HTML app inside a sandboxed iframe, including apps that load their own CSS/JS at runtime, by injecting a faithful `window.sg` shim.

Design intent: the Workbench is an *instrument and a prototype* — a forcing function that discovered the real host contract empirically and distilled which capabilities belong in the kernel as `sg.llm.*`.

## 2. The layered runtime

```
┌────────────────────────────────────────────────────────────────────────────┐
│ BROWSER (user's device)                                                     │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │ HOST / KERNEL (top-level origin)                                      │  │
│  │  • decrypts the vault client-side (zero-knowledge; keys never leave)  │  │
│  │  • owns the VaultSession, data source, commit/push                    │  │
│  │  • renders app shell, HUD, navigation                                 │  │
│  │  • INJECTS window.sg into the app frame; brokers every vfs/fs call    │  │
│  │  • enforces app.json permissions on each bridged call                 │  │
│  │  ┌────────────────────────────────────────────────────────────────┐   │  │
│  │  │ APP IFRAME  sandbox="allow-scripts"  srcdoc=…  (NULL ORIGIN)   │   │  │
│  │  │  workbench.html — one file, one <script type="module">         │   │  │
│  │  │   ├─ sg-layout (tiling layout web component, from tools CDN)   │   │  │
│  │  │   ├─ Execution center (REG + execute + audit)                  │   │  │
│  │  │   ├─ Agent loop (sendChat)                                     │   │  │
│  │  │   ├─ Context composer / Memory / Skills                        │   │  │
│  │  │   ├─ Sessions / Staging / Commit                               │   │  │
│  │  │   └─ Preview engine (+ injected sg shim for sub-iframes)       │   │  │
│  │  │                                                                │   │  │
│  │  │  window.sg ── postMessage ──► host bridge (vault I/O, state)   │   │  │
│  │  └──────────────────────────┬─────────────────────────────────────┘   │  │
│  └─────────────────────────────┼─────────────────────────────────────────┘  │
│        (the app frame ALSO makes its own outbound fetch, NOT via the host) │
└────────────────────────────────┼───────────────────────────────────────────┘
                                 ▼ HTTPS from inside the iframe
                  OpenRouter  /api/v1/chat/completions (SSE)
                              /api/v1/models
                              /api/v1/generation?id=…
```

Two channels leave the app frame, and they are architecturally very different:

1. **The bridge** (`window.sg` → postMessage → host): everything that touches the vault. The host mediates and enforces permissions; the app never sees encryption keys or the raw store.
2. **Direct `fetch` to the LLM provider**: the app calls OpenRouter itself with a key it read from the vault. The host is *not* in this path. This is the deliberate prototype shortcut that the kernel migration removes (kernel holds the key; app calls `sg.llm.chat`).

### 2.1 Trust boundary

```
      UNTRUSTED                    │   SEMI-TRUSTED          │  EXTERNAL
 (model output, vault content      │   (host kernel)         │
  rendered into the DOM)           │                         │
                                   │                         │
 model tokens ─► parser ─► execute ┼─► sg.vfs (permission   ─┼─► vault store
                   │               │    gated by app.json)   │   (encrypted)
                   │               │                         │
 app holds the LLM API key ────────┼─────────────────────────┼─► OpenRouter
                                   │   (NOT brokered today)  │
```

Principles the code follows:

- **Model output is adversarial input.** It is parsed defensively; only a known action is ever dispatched; every dispatch is audited; writes only stage.
- **The host is the permission authority.** Each bridged mutation is checked against `app.json` `permissions.fs` before touching the store.
- **The key is confined by economics, not just code**: it is a budget-capped, rotatable key, so worst-case leak is bounded spend.

Known hardening gaps at this boundary (found in review — see `DEVELOPER.md` §14 for the fixes):

- `allow-scripts` + no CSP means the frame has **unrestricted network egress**; sandboxing protects the host origin, not the vault data the frame legitimately holds.
- The permission manifest should never include itself or the entry file in its own write grant (self-modification path).
- The HTML-escaping and parser gates need the specific tightenings listed in the developer doc before this pattern is reused on untrusted content.

### 2.2 Deployment shape

| Artifact | Lives | Role |
|---|---|---|
| `workbench.html` | vault | the entire application |
| `app.json` | vault | entry point + `permissions.fs` grants |
| `key.json` | vault | budget-capped OpenRouter key, read at runtime |
| `skills/`, `sessions/`, `docs/`, `pocs/` | vault | content the agent reads/writes |
| `sg-layout` | tools CDN | layout web component, imported at runtime |
| OpenRouter | external | LLM provider |

No server component. The page is itself a vault file: the agent can read and edit its own source, and copying the vault copies the working app.

## 3. The host bridge contract (`window.sg`)

The contract was established **empirically** (reading kernel source + Playwright tests against the live page), not assumed. The surface the Workbench relies on:

```
sg.vfs.readText(path)        → string          read a vault file (text)
sg.vfs.list("")              → [{path, dir, size}, …]   FLAT listing; dirs flagged by .dir
sg.vfs.writeText(path, c)    → (write; AUTO-COMMITS + pushes)   [feature-detected]
sg.vfs.mkdir(dir)            → create one folder level           [feature-detected]
sg.fs.write / sg.fs.delete / sg.fs.mkdir                          [feature-detected alt surface]
```

Contract facts that shaped the design (each one was a discovered bug first):

1. **`sg.vfs.list('')` returns a FLAT list** of `{path, dir, size}` with directories marked `dir: true` — not a tree, and not `type:"folder"`. Code that expects a tree silently sees nothing nested.
2. **A vault write auto-commits and pushes.** There is no host-side staging. Any "make several changes, review, commit once" workflow must be built app-side (hence `STAGE`/`TOMB`).
3. **Writers do not create parent folders.** Every write must be preceded by a recursive `mkdir` walk (`ensureVaultFolder`), one segment at a time, tolerating "already exists" errors.
4. **The bridge may not be there.** `window.sg` is injected asynchronously (poll for it at boot, ≤2.5 s) and may never appear (page opened outside the host). Every capability is feature-detected; every consumer degrades.
5. **The null-origin sandbox blocks `alert()`** and friends — in-app toasts replace them.
6. **Permission enforcement is path-prefix based** via `app.json`:

```json
{
  "entry": "workbench.html",
  "auto_open": true,
  "permissions": {
    "fs": {
      "read": true,
      "write": ["docs/", "sessions/", "skills/", "notes/", "…"],
      "mkdir": true
    }
  }
}
```

### 3.1 The writer cascade

Because different host versions expose different write surfaces, all writes go through one feature-detected resolver:

```
vaultWriter():
  sg.fs.write present            → {kind:"sg.fs",  write, del, mkdir}
  sg.vfs.writeText/.write present→ {kind:"sg.vfs", write, del, mkdir}
  writable VaultSession present  → {kind:"session"}   (older hosts; uses a
                                    vault-mutations module + session.push())
  none                           → null  → exportChangeSet()  (download a JSON
                                    change-set the user applies with the CLI)
```

The active backend is always shown to the user (`writes → vault (sg.vfs)` in the toolbar), so trust-relevant state is never hidden.

## 4. Subsystems

### 4.1 Execution center

Three parts: a declarative **registry**, one **dispatcher**, an **audit trail**.

```
REG = {
  "vfs.list"        READ_ONLY    path?           list known vault files
  "vfs.read"        READ_ONLY    path            read (staged shadows vault)
  "vfs.stat"        READ_ONLY    path            existence + size + source
  "vfs.write"       WRITE        path, content   stage a write
  "vfs.delete"      DESTRUCTIVE  path            stage a delete (tombstone)
  "vfs.commit"      WRITE        —               flush staged → vault
  "preview.markdown|section|iframe"  READ_ONLY   render into Preview panel
  "memory.add|list|remove"           WRITE/RO/DESTR   always-on context items
  "skills.list|search|load"          READ_ONLY   how-to graph discovery
  "tools.load|actions|describe"      READ_ONLY   external self-describing tools
}
```

Design properties:

- **Tiers drive the UI** (blue/amber/red chips) and make intent legible at a glance: has the agent only been reading, or has it staged destructive changes?
- **One gate.** Every path from "the model said something" to "something happened" goes through `execute()`. Unknown action → recorded error. Per-tool enable/disable (`TOOLS_OFF`): a disabled tool is dropped from the prompt's tool defs *and* refused at dispatch (unless invoked manually from the UI).
- **Everything audits.** Success or failure, each dispatch lands in the audit list with tier, action, params, result preview — and (v0.6.8) an invoke-again form prefilled for replay.
- **Two summaries by design**: ~240 chars for the human-facing audit row; up to ~8,000 chars for the TOOL RESULT fed back to the model. (An early bug fed the model the 240-char version — models can't act on truncated file content.)

### 4.2 Tool-call parsing pipeline

```
reply text
  │ extractToolSegments: scan ALL fenced blocks; each that parses to a
  │ known call becomes an ordered segment list [text|tool|text|tool…]
  ▼ (if no segments)
  parseToolCall: (a) JSON object w/ action  → dispatch
                 (a2) bare action token immediately before a params object
                 (b) function-call style action({...})
                 (c) bare action on its own line, optional JSON after
  ▼ (if null)  → it was prose; render as the reply
```

Rationale: models genuinely differ in how they emit tool calls even when told the exact format; the parser is liberal in *shape* but strict in *what it will dispatch* (known-action gate). See `DEVELOPER.md` §3 for the exact code and the required hardening (exact-registry membership, fence-tag anchoring) before reuse.

### 4.3 Agent loop

```
sendChat(q):
  guard busy/no-key; consume one-shot attachments (PENDING)
  convo = [system?] + memoryMessages() + bounded history + [user turn]
  for step in 0..5:                         # hard cap 6 LLM calls/turn
    stream reply (live markdown bubble, abortable)
    segs = extractToolSegments(text)
    if segs:  push assistant text; walk segments in order —
              prose → chat message; tool → execute (≤10/reply),
              result appended as user-role "TOOL RESULT [action]: …"
              any tool ran → continue loop, else break
    call = parseToolCall(text)
    if call:  same, single-call path; continue
    else:     plain prose → final answer; break
```

Sequence for a two-tool turn:

```
user      sendChat      llmRequest     OpenRouter     execute      sg.vfs
 │  q        │              │              │             │            │
 ├──────────►│──convo──────►│──POST(SSE)──►│             │            │
 │           │  live tokens ◄──deltas──────┤             │            │
 │           │◄─reply(tool A)              │             │            │
 │           ├──execute(A)────────────────────────────-─►│──readText─►│
 │           │◄─result A──────────────────────────────-──┤◄──content──┤
 │           ├──convo += TOOL RESULT A ──► llmRequest (step 2) …      │
 │           │◄─reply(prose)                                          │
 │◄──final───┤                                                        │
```

Properties: **bounded** (no runaway loops); **stoppable** (Stop aborts the in-flight fetch AND halts further tool execution; the partial reply is kept and its cost still recorded); **transparent** (each step's invocation, dispatch, and I/O visible in their panels); **model-agnostic** (tool results as plain messages work on every model, at the cost of not using native tool-role APIs — see the trade-off note in `DEVELOPER.md` §4).

### 4.4 LLM transport & cost accounting

Direct `fetch` to OpenRouter with `stream:true, usage:{include:true}`; hand-rolled SSE line parser; non-stream JSON fallback. Every call — including aborted ones — records an **invocation**:

```
inv = { ts, kind, model, latencyMs,
        promptTokens, completionTokens, promptChars,
        cost, costSource,        # "openrouter" | "generation" | null
        generationId, finish, outcome, usage,
        request: redactForLog(messages),   # images/binaries → size notes
        content }
```

**Two-source cost model** — the load-bearing idea:

```
effCost(inv) = inv.cost          (real; from usage.cost or /generation)  → "$0.0031"
             | estCost(inv)      (tokens × live unit price from /models) → "~$0.0034"
```

If the stream carried no `usage.cost`, a delayed `GET /api/v1/generation?id=…` fetches the **authoritative** `total_cost` + native token counts and upgrades the row (`costSource:"generation"`). Estimates always render visibly as estimates (`~` prefix). The toolbar Σ pill is the running session total.

### 4.5 Context composer, memory, skills

The next request is assembled from **inspectable, individually toggleable parts**:

```
composeContext() rows:
  ☑ system prompt (base)        ~tok   SYS_ON            (editable overlay)
  ☑ tool defs [full|lean|off]   ~tok   TOOLDEFS
  ☑ skills discovery hint       ~tok   SKILLS_ON
  ☑ <memory item …>             ~tok   per-item .on      (text or image)
  ☑ chat history (N of M msgs)  ~tok   CTX.history / histLimit
  ☑ <one-shot attachment>       ~tok   locked to this turn
  ────────────────────────────────────────────────────
  next request: ~X input tokens · ~$Y · k/n parts included
```

- Rows expand to the **exact text** they contribute — no mystery bytes.
- With base + tool defs + skills all off, **no system message is sent at all**.
- Token estimates are `chars/4` (`estTok`), images floor at 258 tokens; clearly labelled as estimates, with real counts appearing per-call afterward.

**Memory vs attachments:** `MEMORY` items ride *every* request (one system message concatenating text items; one user message with `image_url` parts for images), survive Clear/New, can be paused (keep but skip next request), locked (chat cannot modify), and managed by the agent itself via `memory.add/list/remove`. `PENDING` attachments ride exactly one turn.

**Skills** decouple competence from the system prompt: a ~70-token hint tells the model that `skills.list / skills.search(topic) / skills.load(name)` exist; full guidance lives in vault files (`skills/index.json` + per-skill `SKILL.md`, with `topics` and `related` graph edges). Improving the agent is a documentation edit, not a release.

### 4.6 Staging & the commit pipeline

```
STAGE = { path → content }   pending writes     TOMB = { path → true }  pending deletes

allFiles()  = (live listing ∪ STAGE keys) − TOMB keys
readFile(p) = STAGE[p] ?? sg.vfs.readText(p)          # staged shadows vault
                                                       # (previews see staged edits)
commitStaged(msg):
  writer = vaultWriter()                # the cascade from §3.1
  for each staged path: ensureVaultFolder(parent); writer.write(path, content)
  for each tombstone:   writer.del(path)
  optional sync.commit(msg) + sync.push if the host exposes them
  clear STAGE/TOMB only on full success
```

Auto-commit toggle: off → changes wait for the Commit dialog (list of files + editable message — a deliberate review step); on → each `vfs.write`/`vfs.delete` flushes immediately.

### 4.7 Sessions

A session is a **complete instrument snapshot**, not just chat history:

```
snapshot() = { v:2, savedAt, title, model, autocommit, totalCost,
               chats: [ {id, title, history} … ],  activeChat,
               invocations,        # every LLM call incl. redacted request + cost
               stage, tomb,        # pending vault edits
               audit,              # tool-dispatch trail
               memory,             # always-on context items
               layout }            # exact panel arrangement
```

- Written to `sessions/<sanitised-title>.sgsession.json` — **title-keyed**, so re-saving overwrites the same file (a new vault commit) instead of accumulating timestamped copies. Loading a session adopts its title, so the next Save naturally writes back to the same file.
- The Sessions tab lists every `sessions/*.sgsession.json` in the vault — across runs and devices — each restorable in place.
- The API key is **never** serialized; requests are stored through `redactForLog`. A session file is therefore safe to share for debugging.
- Restore rehydrates everything including all ephemeral chat tabs and the layout.

Because invocations carry full (redacted) request/response pairs, **session files double as regression-test fixtures** for replaying agent behaviour.

### 4.8 Preview subsystem

Three modes: markdown render; HTML **section** (inlined, all scripts stripped); HTML **iframe** (sandboxed `srcdoc`, scripts allowed).

Two problems solved:

1. **Tag inlining** (`inlineHtml`): a null-origin page cannot `<link href>`/`<script src>` vault files. Before rendering, those tags are rewritten by reading the referenced vault-or-staged file and inlining it (`<style>…</style>` / `<script>…</script>`). External (`http…`/`data:`) references pass through.
2. **Runtime loading** (`buildSgShim`): well-behaved vault apps don't use tags — they call `window.sg.loadCss("x.css")` at runtime. The preview iframe has no `window.sg`, so those calls would silently no-op. The fix: scan the HTML for `loadCss/loadJs/readText/read('…')` string literals, **pre-read** each referenced file into an embedded map, and inject a `window.sg` shim (first thing in `<head>`) that replays the host's exact loadCss/loadJs behaviour against that map. Write surfaces in the shim are no-ops — previews are read-only by construction.

Result: a vault app previews exactly as it runs under the host, including staged (uncommitted) edits.

### 4.9 Ephemeral chats

```
CHATS  = [ {id, title, history[]} … ]     ACTIVE = current id
history = alias of curChat().history       # all chat code reads one variable
```

Multiple short-lived conversations in a tab strip; each keeps its own history; **all share** memory, model, staged files, costs, and the vault. A chat auto-titles from its first message. `Clear` empties the active chat (memory survives); `New session` resets chats + invocations + audit (memory survives). Sessions capture all open chats.

This implements the memory inversion: *the chat is ephemeral; the memory is the curated files.* The specified-but-not-yet-implemented half is auto-compaction (distilling a closing chat into a summary memory file) — flagged as the top gap in review.

### 4.10 UI layer

Built on `sg-layout`, a draggable/resizable tiling web component. The page declares a default arrangement and scaffolds panel content on `LAYOUT_READY`:

```
LEFT 42%: Ephemeral chats (tab strip + REPL)
RIGHT 58%: top stack  — Preview · Files · Memory · Tools · Audit · Context
           bottom stack — LLM calls · Costs · Vault I/O · Sessions
Toolbar: model + faceted picker + pricing · Commit · auto-commit · writes-target
         · md toggle · key pill · Σ cost pill · version pill (release notes)
```

Visual language: blue = read, amber = write, red = destructive, green = vault/success; mono for tools/data, sans for prose. The tier palette is reused across every panel so the *nature* of an event is legible before its text.

## 5. Boot sequence

```
boot()
 ├─ poll ≤2.5 s for window.sg.vfs.readText     (host injects the bridge async)
 ├─ instrumentSg()                              wrap vfs/fs read/write/delete to
 │                                              log every call into Vault I/O
 ├─ listen for "vault:connected"                capture a late writable session
 ├─ read key.json → API_KEY                     key pill shows source; absent key
 │                                              degrades to read-only chat UI
 ├─ loadModels()                                /models → pricing map + picker
 ├─ create <sg-layout>; on LAYOUT_READY → mount()  scaffold panels, wire handlers
 └─ refreshFiles() (+ retry at 1.8 s)           live listing, else static seed
```

Every step degrades: no bridge → static file seed + free-text model field; no key → UI still renders; no writer → export-changeset path.

## 6. State model

| State | Kind | Persists via |
|---|---|---|
| `CHATS/ACTIVE/history` | per-chat conversations | session snapshot |
| `INVOCATIONS` | every LLM call + cost | session snapshot |
| `audit` | every tool dispatch | session snapshot |
| `STAGE` / `TOMB` | pending vault edits | session snapshot → commit |
| `MEMORY` | always-on context items | session snapshot |
| `PENDING` | one-shot attachments | consumed by next turn |
| `VAULTIO` | bridge I/O log (capped 300) | ephemeral |
| `SYS_ON / TOOLDEFS / SKILLS_ON / CTX` | composer toggles | ephemeral |
| `TOOLS_OFF` | per-tool agent disable set | ephemeral |
| `MODEL / AUTOCOMMIT / layout` | instrument config | session snapshot |
| `API_KEY` | credential | **never** serialized |

Single-writer discipline: `busy` serializes turns, which is what makes the module-global streaming-render state and the `history` alias safe.

## 7. Design principles (as actually followed)

| Principle | Where it shows up |
|---|---|
| **Glass-box over magic** | composer shows exact bytes; LLM panel shows raw exchange + authoritative cost; Vault I/O logs every bridge call; audit logs every dispatch |
| **Key never leaves the vault** | read via bridge; redacted from every log; never in sessions |
| **Tolerate the model, not vice versa** | 4-style parser; multi-call segmenting; per-model quirks absorbed at the boundary |
| **Stage, then commit** | app-side staging over an auto-committing store; review dialog; auto-commit opt-in |
| **Minimum tokens, made visible** | per-part toggles, history cap, lean tool defs, skills-on-demand, projected cost before send |
| **Self-contained page** | one file; no build; the app is a vault file the agent can edit |
| **Degrade, don't crash** | writer cascade; listing cascade; bridge polling; offline model fallback |

## 8. Migration: what moves into the kernel (`sg.llm.*`)

The split rule distilled from building everything app-side:

**Kernel-owned** (pure plumbing every LLM app re-implements): transport + SSE parsing (`sg.llm.chat({messages, model, stream, onToken})`), key custody (app never sees the key), usage/cost accounting + reconciliation, the tolerant tool-call parser, the standard vault tool set (`vfs.*`, previews), session snapshot helpers, and — per review — **budget enforcement server-side** and a **frame egress CSP** so removing key custody also removes the exfiltration channel.

**App-owned**: prompt design, domain-specific tools contributed to the registry, panel UI, workflow choices (staging policy, memory curation).

The endgame: any vault (and the host's own UI) gets "talk to your content" without any per-app agent code, with the Workbench remaining as the ceiling-tier instrument.
