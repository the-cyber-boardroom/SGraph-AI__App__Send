## Part 1 — What this thing is

The vault is a **self-contained agent workbench that lives inside a zero-knowledge encrypted vault**. One HTML file (`workbench.html`, an inline ES module, no build step, no framework) turns the vault into a fully observable LLM REPL:

- Talks to **any OpenRouter model** with a budget-capped key read from `key.json` *inside the vault* — the key never touches a server the app owns.
- Gives the model **read/write access to vault files** through a typed, audited tool sidecar (the "execution center").
- Is deliberately **glass-box**: the exact prompt bytes, every LLM call with real cost, every vault I/O operation, every staged-but-uncommitted change is visible in a panel.
- Runs inside the host's **null-origin sandboxed iframe** (`sandbox="allow-scripts"`, srcdoc), talking to the vault only via the injected `window.sg` postMessage bridge, permission-gated by `app.json`.
- Is **itself a vault file** — the agent can read and edit its own source, and the whole thing is portable: copy the vault, get the workbench.

The vault also carries an 11-document architecture set (`architecture/01..11`), a skills graph, session recordings, strategy/dev briefs, and three POCs — it's simultaneously an app, its own documentation, and its own commercial context.

### The stack in one diagram

```
Browser
└─ SGraph App/Send HOST (top-level origin)
   • decrypts vault, owns VaultSession + commit/push
   • injects window.sg, enforces app.json permissions per call
   └─ APP IFRAME (null origin, sandbox="allow-scripts")
      workbench.html
      ├─ sg-layout (tiling layout web component, from tools CDN)
      ├─ Execution center (REG + execute + audit)
      ├─ Agent loop (sendChat, ≤6 LLM calls/turn)
      ├─ Context composer / Memory / Skills
      ├─ Sessions / Staging / Commit
      └─ Preview engine (+ injected sg shim for sub-iframes)
      │
      ├── window.sg ──postMessage──► host bridge (vault I/O)
      └── direct fetch ────────────► OpenRouter (SSE streaming)
```

Two channels leave the frame and they are architecturally very different: vault I/O is host-brokered and permission-checked; the LLM call is a **direct fetch from the iframe** with the key in app memory. The docs are honest that this is the thing the planned `sg.llm.*` kernel migration removes.

## Part 2 — The chat UI, in depth

### Ephemeral multi-chat REPL (v0.5.9+)

The left panel is not "a chat" but a **tab strip of ephemeral chats** (＋ new, × close, ⌫ clear). All tabs share the same memory, model, costs, staged files and vault — but each keeps its own conversation, auto-titled from its first message. This implements the philosophy in `docs/v0.33.38-ephemeral-chat-file-based-memory.md`, which inverts the usual framing:

> "The chat is ephemeral; the memory is the files you attach. …the industry talks a lot about memory, but I have two modes. One is the chat, which we usually view as memory, and I am now saying it should be ephemeral."

Conversation surface details:

- **User bubbles** right (vault-green), **agent bubbles** left, Markdown-rendered (toggleable `md: on/off`).
- **Tool badges** inline in conversation order — monospace blue chips showing the exact `action({params})` dispatched. Causality reads as narrative.
- **Streaming bubble**: model name + elapsed-seconds counter + spinner, filling with *live-rendered Markdown* as SSE tokens arrive (throttled ~60 ms).
- **Stop button** (v0.6.0/0.6.1): Send becomes a red Stop mid-turn; abort keeps the partial reply as a message, appends "stopped by user", and *still records the LLM call with its generation id* so partial cost is reconciled.
- **Sample prompt chips** seed example commands and hide once a conversation starts.
- **Attachments**: drag-drop or paste a file/image onto the input → a one-shot chip that rides only the next turn (images sent as `image_url` vision parts).
- **Model line above the input** with IMG/TXT + cost badges; click to jump to the model field.

### The streaming Markdown renderer is real engineering

Two changelog entries stand out for a "prototype":

- **v0.6.4** — fixed an infinite loop: a streamed table header arriving before its separator row pinned the tab at 100% CPU. The renderer now always advances.
- **v0.6.5** — sealed-prefix caching: instead of re-parsing the whole accumulated reply on each throttled frame, completed blocks (before the last blank line, outside an open code fence) are cached as HTML and only the streaming tail is re-parsed. Byte-identical output, bounded per-frame cost. *(The Developer agent property-tested this against 600 random chunkings — zero mismatches.)*

### The model picker (v0.6.0 → v0.6.7)

A faceted, curated picker driven by the live OpenRouter `/models` list: provider cards in a grid, per-model badges for **IMG/TXT** (modality), **$/$$/$$$** (cost tier), **OSS** (open weights), **WEB** (search-capable). Faceted filtering is OR-within-group, AND-across-groups. Groups track the OpenRouter leaderboards (DeepSeek, Tencent, Xiaomi, MiniMax, Z.ai, plus the majors); free models are deliberately excluded ("no markup margin, volatile"). Live per-model pricing shows inline in the toolbar; quick-pick chips resolve to the newest matching model id.

## Part 3 — The workflow machinery, in depth

### The execution center: typed, audited, tolerant

Every tool is declared once in a registry (`REG`) with a **tier** classifying blast radius — READ_ONLY (blue) / WRITE (amber) / DESTRUCTIVE (red). ~18 tools across five namespaces: `vfs.*` (list/read/stat/write/delete/commit), `preview.*` (markdown/section/iframe), `memory.*`, `skills.*`, `tools.*` (self-describing external-tool manifests). One dispatcher, `execute(action, params)`, audits every dispatch — success or failure — with tier, action and a preview.

Two deliberate summary sizes: `summ()` (~240 chars) for the human-facing audit row, `summFull()` (~8,000 chars) fed back to the model — the model needs the file content, the human needs a glance.

Since **v0.6.8**, the Tools panel gained per-tool enable/disable checkboxes (disabled tools drop out of the prompt tool-defs and are refused if called), plus a **Swagger-style "try" form** to invoke any tool manually and see exactly what it returns — and the Audit panel carries the same invoke-again form prefilled, so you can tweak and re-run any past call.

### The tolerant parser — "tolerate the model, not the other way round"

Models don't reliably emit clean JSON. The parser accepts four emission styles — a JSON object `{"action":…,"params":…}`, a bare action token followed by a params object, function-call style `vfs.read({...})`, and a bare action on its own line — gated by a known-action check so prose never dispatches. `extractToolSegments` handles models that batch *prose + several tool blocks* in one reply, splitting into ordered segments the loop walks in order. This is why qwen/mistral/sonnet all work despite preferring different styles.

### The agent loop

`sendChat` is a bounded ReAct loop: build convo (system? + memory + bounded history + user turn) → stream a reply → split into prose/tool segments → execute tools → feed each result back as a `TOOL RESULT [action]:` message → continue. Hard caps: **6 LLM calls per turn, 10 tool executions per reply**. If every composer part is toggled off, no system message is sent at all — the loop adapts.

### The context composer — byte-level prompt transparency

Every contributor to the next request is a row with a token estimate: system base, tool defs (**full / lean / off** modes), skills hint, each memory item, chat history (cappable to last-N), one-shot attachments. Each row expands to show the *exact text* it contributes; each is toggleable; the projected input cost for the selected model shows before you send. This is the rarest feature in the whole product — very few agent UIs anywhere give byte-level prompt inspection.

### Memory vs attachments, and the skills graph

- **MEMORY**: always-on items (text or images) riding every request, surviving Clear/New; lockable so the chat can't change an item; agent-manageable via `memory.add/list/remove`; pause-vs-remove semantics.
- **PENDING**: one-shot attachments consumed by the next turn only.
- **Skills**: a graph of how-to documents (`skills/index.json` + per-skill `SKILL.md`, with topics and `related` edges) discovered via `skills.list/search/load`. A ~70-token discovery hint replaces stuffing every vault-specific rule into the system prompt. The canonical win: models confidently gave the wrong `<link href>` answer for loading CSS in a vault app until `vault-authoring` taught them the null-origin rules. The graph is *content, not code* — improving agent competence is a documentation edit, not a release.

### Staging, commit, sessions

- Writes **stage** by default (`STAGE`/`TOMB` tombstones); the Files panel shows the merged vault∪staged view; a Commit dialog lists staged files with an editable message. Auto-commit toggle for immediate flush. The writer is **feature-detected** (`sg.fs` → `sg.vfs` → writable session → export-a-changeset-for-sgit) with the live target shown in the toolbar (`writes → vault (sg.vfs)`).
- **Sessions** snapshot *everything*: all open ephemeral chats, invocations (full redacted request/response/cost), audit trail, staged edits, memory, model, layout. Saved to `sessions/<title>.sgsession.json` — title-keyed, so re-saving overwrites (a new commit) rather than piling up timestamped copies. The Sessions tab lists every session in the vault across runs and devices, each restorable in place. The key is never serialized (`redactForLog`).

### Cost accounting — estimated now, authoritative shortly after

Streaming responses carry `usage` when available; otherwise the workbench schedules `GET /api/v1/generation?id=…` for the **authoritative** `total_cost` and exact token counts, updating the row with `costSource:"generation"`. Estimated costs show with a `~` prefix; the Σ pill is the running session total; "refresh all costs" reconciles everything. This two-source, provenance-labeled cost model is more rigorous than most production teams'.

### The preview subsystem

Three modes: `preview.markdown`, `preview.section` (scripts stripped), `preview.iframe` (sandboxed, scripts allowed). The hard problem solved: vault apps load CSS/JS at runtime via `sg.loadCss()` — inside a preview iframe there's no `window.sg`, so pages rendered unstyled. The fix injects a **`window.sg` shim** into the preview iframe that pre-reads referenced files from the vault+staged layer and replays the host's exact `loadCss`/`loadJs` implementation. Staged edits are visible in preview *before commit* — iterate on a file and watch it render without touching the vault. The shim's write surface is no-ops: previews are read-only.

### Velocity note

The changelog runs **v0.2.0 → v0.6.8 in roughly two days** (16–17 June 2026), with the architecture doc set (v0.5.8) written mid-stream as the briefing base for migrating most of this code into a kernel-native `sg.llm.*` capability set — the explicit endgame being every vault getting "talk to your content" without any app code.

## 4.1 Architect's review — 7/10

### Layered architecture and trust boundary

The layering is conceptually clean and unusually well documented (`architecture/02`). Host kernel holds decryption keys and the VaultSession; the app runs in a null-origin `sandbox="allow-scripts"` srcdoc iframe; every vault touch crosses the `window.sg` postMessage bridge and is permission-checked host-side. The docs are honest about the one boundary violation: the app frame makes **direct `fetch` to OpenRouter** with a key it read into memory.

Two problems the docs understate:

- **Null-origin does not mean egress-contained.** `allow-scripts` iframes can fetch anywhere; there is no CSP on the srcdoc. Any code in the frame — including code the model writes — can exfiltrate decrypted vault content to arbitrary hosts. The sandbox protects the *host origin*, not the *vault data* the frame legitimately holds.
- **The app can widen its own authority.** `app.json`'s `permissions.fs.write` list includes `"workbench.html"` and `"app.json"` themselves. An LLM whose output is (correctly) treated as untrusted can stage writes to both, and after `commitStaged()` (auto-commit + push) the app has rewritten its own code *and its own permission manifest*. Prompt injection in any vault file → staged self-modification → next load runs attacker code with expanded grants. **This is the single biggest architectural defect.**

### The `window.sg` bridge contract

Strengths: empirically derived, precisely documented contract (auto-commit semantics, flat-list shape, mkdir parent-folder gotcha, null-origin silent failures). Feature detection everywhere (`vaultWriter()` cascade) makes the app degrade gracefully. `instrumentSg()` wrapping bridge methods into a Vault I/O log is good observability discipline, though monkey-patching an injected bridge is fragile against host hardening.

Gaps: (a) permission granularity is path-prefix only — no per-verb rate limits, size caps, or a "requires user confirmation" tier at the bridge; (b) `read: true` is total — any preview sub-iframe bug or injected code reads the whole vault including `key.json`; (c) the contract is verified behaviorally, not versioned — no negotiated bridge version; (d) auto-commit-on-write means the bridge has no host-side undo/review seam — the app's staging layer compensates in the wrong layer.

### The `sg.llm.*` proposal (doc 10)

The thesis is right and the split rule — transport, custody, accounting, parsing and the standard tool set kernel-side; prompt design, domain tools and UI app-side — is the correct cut. Mirroring `permissions.fs` with `permissions.llm` is elegant; the phasing (custody + streaming first) is sensible. Three changes:

1. **Budget enforcement must not be client-side.** The real cap must live at the key/proxy. State as a requirement, not an open question — otherwise "budget-capped" is advisory.
2. **Pair custody migration with egress lockdown.** Moving the key to the kernel is insufficient if the frame can still `fetch` anywhere. Phase 1 should include a CSP (`connect-src` allowlist) on app frames, making the bridge the *only* channel out — that completes the trust boundary.
3. **Define the app-registered-tool execution contract before Phase 2.** `sg.llm.tools.register()` implies the kernel dispatching back into app code — that callback crosses the trust boundary in the dangerous direction and needs an explicit sandboxed-execution and result-validation contract.

Plus: add a `confirm: ["vfs.delete","vfs.commit"]` field so DESTRUCTIVE-tier tools require host-rendered user approval, taking the human-in-the-loop out of app code.

### Key risks (ranked)

1. **Self-modification of `app.json`/`workbench.html` by untrusted model output** — persistence + privilege escalation.
2. **Key in app memory + unrestricted egress** — the key has a hard cap + rotation, but vault *content* exfiltration has no cap.
3. **Runtime CDN dependency** — `sg-layout` and `sg-vault-mutations` dynamically imported from `dev.tools.sgraph.ai` with no SRI; a CDN compromise injects code with full bridge access, and the portability claim is false offline.
4. **Model output as untrusted input** — handled well (known-action gate, tiers, audit, bounded loop), but auto-commit mode collapses stage→commit→push into one model-triggered action.
5. **Single-file scaling** — 138 KB, one module, no in-repo test harness; approaching the limit where the agent editing its own source becomes high-risk.

### Top 5 recommendations

1. Remove `app.json` from its own write grant; kernel invariant: permission manifests never writable via the bridge (or host-UI confirmation required). Same for `entry` files.
2. Ship `sg.llm` Phase 1 **with** frame egress restriction (CSP `connect-src` allowlist).
3. Move budget/allow-list enforcement server-side (key-minting proxy or kernel), with observability-vault append at the `sg.llm.chat` choke point.
4. Host-mediated confirmation tier for DESTRUCTIVE and commit actions; default auto-commit off, diff view at commit.
5. Vendor `sg-layout` into the vault or add SRI + local fallback, restoring self-containment.

**Score: 7/10.** Exceptional documentation-as-architecture, a genuinely well-designed execution center, honest trust-boundary analysis, correct and well-phased migration plan. Held back by two concrete boundary defects — the app-writable permission manifest and unconstrained egress alongside vault read access — both exploitable today via prompt injection, plus the unpinned CDN supply chain. The team knows where the bodies are buried; the score reflects that the highest-severity gap (self-modification) isn't yet named in their own risk register.

## 4.2 Developer's review — 6.5/10

*(All findings below were verified empirically against the actual code, not just the docs.)*

### Single-file organization

Disciplined for its genre: `"use strict"` module, clear section banners, tiered registry, and a real test seam (`window.__wb`) exporting the pure functions. The architecture docs match the code closely — `sendChat` and `llmRequest` are faithful to doc 05, including the caps and the empty-system-message behavior. Where it strains: ~25 top-level mutable globals (`history` aliasing `curChat().history` is a footgun, so far handled correctly); every render function builds `innerHTML` strings with three interleaved quoting styles — which is where the escaping bugs live; streaming-renderer state is module-global rather than per-message, safe only because `busy` serializes turns.

### The hard parts

- **Markdown renderer.** The v0.6.4 hang fix (progress guard) is correct — verified: a stray table header without a separator renders as prose instead of looping. The v0.6.5 sealed-prefix optimization is genuinely sound: **property-tested 600 random chunkings** of table/fence/quote documents against the full parse — **0 mismatches**. The fence-aware blank-line seal is the right invariant.
- **SSE reader.** Solid: buffered line splitting, tolerant JSON parse, non-stream fallback, abort captured as a recorded invocation, cost reconciliation. Gaps: leftover buffer discarded at stream end (a final `usage` chunk without trailing newline is lost); a mid-stream `data: {"error":…}` payload is silently ignored → empty bot bubble.
- **Tool-call parser.** `extractJson`'s string-and-escape-aware brace matcher is well done. But the design is over-eager (below).

### Real bugs (verified)

1. **XSS via markdown links.** `esc()` does not escape quotes; the link rule interpolates `href="$2"` raw. A model reply (or previewed vault file) containing `[click](https://x" onclick="...)` produces a live `onclick` attribute — **verified**. `javascript:` hrefs also pass. `API_KEY` is in scope of this page. The same root cause affects every `data-*="${esc(...)}"` attribute built from model-controlled strings.
2. **`knownAction` gate is much weaker than doc 04 claims.** The regex accepts `vfs.readText`, even `vfs.destroyEverything` (verified). Combined with `extractToolSegments` scanning **every** fenced block, an assistant reply that merely *explains* the API executes real tools — `memory.remove("x")` in a code sample actually deletes memory, and the code block vanishes from the chat, replaced by a tool badge. Doc 04's "a made-up verb never dispatches" is false.
3. **`buildSgShim`: script-tag injection.** `JSON.stringify(F)` doesn't escape `</script>` (verified) — previewing an app whose inlined JS/CSS contains that literal terminates the shim script early and breaks the preview.
4. **Silent step exhaustion.** Six consecutive tool calls exit the loop with no final message and no "step limit reached" notice; tool segments past the 10-cap are silently dropped with no feedback to the model.
5. **Minor:** `commitStaged` swallows delete failures yet still clears tombstones; `saveSession` triggers a browser download on every save; `restoreSession` can mint colliding chat IDs after closed chats; doc 04 lists `memory.remove` as WRITE, code says DESTRUCTIVE.

### Testing story

Nothing in the repo. Tests exist only as an external, ephemeral Playwright/python harness described in the session debrief. Doc 04's "all four shapes were unit-tested" is unreproducible from this vault. The `__wb` seam is 90% of a test harness already; a committed `tests.html` running golden cases in-browser would make the claims verifiable.

### Top 5 recommendations

1. **Fix escaping now**: `esc()` must cover `"`/`'`; sanitize link hrefs (allowlist `https?:`/relative); `<`-escape the shim JSON. Small diffs, closes bugs 1 and 3.
2. **Tighten the parser**: `knownAction` = exact `REG` membership only; restrict `extractToolSegments` to ```` ```tool ````/```` ```json ```` fences (the system prompt already mandates them).
3. **Commit a `tests.html`** exercising `__wb`: parser corpus, `md` golden cases, streaming-equivalence property test.
4. **Close the loop's silent edges**: surface step/tool-cap exhaustion to user and model; handle SSE `error` payloads; flush the decoder tail.
5. **Wall off `key.json`**: it's readable via `vfs.read`, so the agent can pull the OpenRouter key into the conversation and into vault-persisted session files. Deny-list it in `vfsRead`/`allFiles`.

**Score: 6.5/10.** Genuinely strong engineering instincts for a zero-dependency POC — staging/tombstones, audit trail, cost reconciliation, abort handling, and a verified-correct incremental renderer are above the bar for this class of artifact. But two verified injection bugs in a tool that renders adversarial content, a dispatcher that fires on example code, and a testing story that lives entirely outside the repo cap it. Fixing recommendations 1–3 moves this to 8.

## 4.3 AI Engineer's review — 6.5/10

### Agent loop vs current best practice

`sendChat` is a textbook bounded ReAct loop. The deliberate choice of **prompt-based JSON emission over native tool-calling APIs** is defensible given OpenRouter's model diversity — `tools`-parameter support is uneven across open-weight routes, so a lowest-common-denominator text protocol maximizes portability, and the session traces show it working with Gemma and Qwen. The tolerant 4-style parser with a known-action gate is a pragmatic mitigation for format drift.

Costs of that choice: (a) no parallel tool calls; (b) real false-positive risk — a model *discussing* `vfs.read("x")` in prose can trigger execution; (c) tool results as `user`-role messages degrade models trained on `tool`-role turns and blur provenance — a **prompt-injection amplifier**, since vault file content re-enters as user-authority text; (d) `summFull` truncates at 8,000 chars silently, mid-JSON. Best practice today: capability-detect per model (OpenRouter exposes `supported_parameters`) and use native tool calling where available, keeping the text protocol as fallback. `DEFAULT_SYSTEM` itself is good: compact (~250 tokens), one canonical format, a "fewest calls, then STOP" frugality rule, read-before-edit.

One safety gap: tiers are rendered in the UI and "arm-to-confirm" gates *manual* destructive buttons, but `execute()` applies **no confirmation gate to agent-initiated DESTRUCTIVE calls** — with auto-commit on, a model-emitted `vfs.delete` persists immediately. Tiers are currently metadata, not policy.

### Ephemeral chat + file-based memory as context engineering

The philosophy doc's inversion — chat ephemeral, memory as curated files, minimum tokens — is genuinely ahead of where most agent products were until recently, and converges independently on the same conclusions as the CLAUDE.md/memory-file pattern: durable knowledge belongs in inspectable files, not an accreting transcript. The context composer is the standout artifact — very few production agent UIs give byte-level prompt transparency.

But the pattern is **half-implemented**. Of the brief's seven asks: file memory ✓, context UI ✓, selective tool defs ✓. The two "session assets" are missing: the audit log isn't exported as a reusable memory file, and the **pre-generated work-so-far summary (compaction) is specified but absent** — no summarization code path exists. Worse, ephemerality itself is opt-in: `histLimit` defaults to 0 (= *all* history), so out of the box the chat accumulates exactly like the pattern it critiques. No automatic compaction on close or on token pressure.

### Skills graph vs system-prompt stuffing

The strongest design element. A ~70-token discovery hint + `skills.list/search/load` is progressive disclosure done right — the same shape as Agent Skills / MCP resource discovery, built independently in one HTML file. "The graph is content, not code" is the right operational model. Weaknesses: `skills.search` is substring-match only; nothing measures whether the model actually loads skills when it should; `related` edges are declared but nothing exploits them.

### Evaluation & observability

Strong on *observability*: per-invocation records with redacted full request/response, latency, tokens, two-tier cost provenance (stream `usage.cost` → authoritative `/generation` reconciliation) — more rigorous than most teams'; a tool audit with replay; and `.sgsession.json` snapshots that are effectively **complete traces**, ready-made regression fixtures.

Missing for an AI engineer: (1) **evals** — no golden tasks, no assertion harness over sessions (a lone `library/round-trip.sgcase.json` hints at test cases but there's no runner); (2) **prompt versioning** — `DEFAULT_SYSTEM` is an unversioned constant; invocations don't record which prompt version produced them; (3) per-model comparison views; (4) failure taxonomies — the parser's miss rate is unmeasured, though the traces contain all the data to compute it.

### Top 5 recommendations

1. **Enforce tiers in `execute()`**: user confirmation for agent-initiated DESTRUCTIVE calls, never auto-commit them; explicit provenance wrapper (or native `tool` role where supported) so tool output isn't user-authority text.
2. **Implement the specified compaction**: on chat close/Clear or at a token threshold, auto-generate the session log + work-so-far summary as memory files; default `histLimit` to a bounded value.
3. **Capability-based tool calling**: use native tool calls where `supported_parameters` allows, text protocol as fallback; anchor function-call-style parsing to line-start.
4. **Build an eval harness on `.sgsession.json`**: replay sessions against models/prompt variants, assert on tool-call sequences and skill loads, report parse-failure and loop-cap-hit rates.
5. **Version the prompt and skills**: hash `systemPrompt()` into each invocation record; keep `SYSTEM_TEXT` edits as vault files; add a skill-usage counter.

**Score: 6.5/10.** Context-transparency, cost provenance, skills-graph disclosure and complete session traces put this well above typical prototype agents — several ideas anticipate current best practice. It loses points for unenforced safety tiers, the specified-but-missing compaction (the philosophy's centerpiece), injection-prone user-role tool results, parser false positives, and the total absence of evals/prompt versioning. The gap between excellent observability and nonexistent *evaluation* is the defining maturity limitation.

## 4.4 Designer's review — 7.5/10

### Information architecture

The 11-panel tiling layout is a defensible shape *for this instrument*: the panels map 1:1 onto the system's architecture — the UI *is* the block diagram, which is the honest way to build a glass box. Saved layouts in sessions and a Reset escape hatch are the right pro-user affordances.

But the taxonomy blurs three panel species — **workspace** (Preview, Files, Memory), **telemetry** (LLM calls, Audit, Vault I/O, Costs), and **meta** (Context, Sessions) — and the top/bottom split doesn't follow that line. Worse, Audit, LLM calls and Vault I/O are three projections of *one causal chain* (turn → LLM call → tool dispatch → vault write) with no cross-linking; the user joins them mentally by timestamp. And because panels are stacked tabs, the glass box only shows the pane you're facing — if a write stages while you're on Preview, nothing signals it. Observability is high per-panel, low across panels. This is a debugger without a unified timeline.

### Visual language (from the actual screenshots)

A restrained, coherent light theme: white surfaces on `#eef1f8`, disciplined type split (JetBrains Mono for chrome/data, Inter for prose), and the tier palette genuinely reused everywhere — the "a glance tells you the nature of the event" claim holds.

Problems visible in the render: **flat toolbar hierarchy** (Commit has identical weight to Reset layout; the 10 quick-model chips consume the whole top row and are superseded by the v0.6.2 picker — the chip row should go); **green is overloaded** (brand, user bubble, Send, key-ok pill, success, links — the color meaning "safe/vault" also means "you" and "click me"); **contrast**: `--faint #9aa4bf` on white at 11.5px mono is ~2.9:1 — below WCAG AA, and it's the dominant color of every empty state and hint; **the initial state is mostly void** — the largest panel (Preview) holds one faint line; **suite fragmentation** — Audio Transcribe is a dark-theme "SG/Tools" language, the Workbench a light "SG/Vault" one.

### The chat/REPL

The strongest surface. Inline tool badges showing exact action + params *in conversation order* is the single best glass-box move — causality reads as narrative. The streaming bubble and the craft underneath it (sealed-prefix parsing, table-hang fix, Stop that keeps the partial and records cost) are real. Sample chips, one-shot attachments, model line above the input — all correct.

Weaknesses: tool badges show the *call* but not the *result* — the answer to "did it work?" lives a panel-hop away in Audit. The empty state teaches neither the tool tiers nor the stage/commit safety model. "Ephemeral chats" names the implementation, not the benefit, and the crucial shared-state fact (memory/costs/staging shared across tabs) is buried in microcopy.

### Glass-box UX debt & the disclosure ladder

When everything is visible, nothing is prioritized: cost appears in at least four places; trust-critical state (key pill, writes-target) renders in the same faint chrome as cosmetic toggles. For the "talk to this doc" future, the workbench should be the *ceiling* of a disclosure ladder, not the floor:

- **Level 0** — doc popover: chat + answer, a cost ticker, one "receipt" affordance per reply.
- **Level 1** — per-message disclosure: expand any reply into its context parts, tokens, cost, tool calls with results.
- **Level 2** — writes as a review moment: staged changes as a diff sheet with an explicit Commit review.
- **Level 3** — the full workbench, for instrument work.

The kernel migration is exactly the moment to design these layers once.

### Top 5 recommendations

1. **Cross-link the telemetry**: clicking an LLM call highlights its Audit dispatches and Vault I/O lines (shared turn ID); activity badges on background tabs so hidden panels can't silently change.
2. **Attach receipts to bubbles**: per-reply expandable cost/tokens/context/tool-results — chat becomes self-sufficient for 90% of inspection and seeds the Level-1 pattern.
3. **Make Commit a designed moment**: staged-count in the toolbar, diff review, arm-to-confirm; separate consequential actions from cosmetic chrome.
4. **Toolbar consolidation + accessibility pass**: drop the chip row, group status pills, raise `--faint` contrast and minimum type sizes.
5. **Teach through empty states**: first-run panels should show the tier legend, the stage→commit model, and two guided flows — the safety story is the differentiator and is currently invisible until something happens.

**Score: 7.5/10** (as a power-user instrument). Exceptional transparency-as-design, rigorous color semantics, genuinely polished streaming mechanics — rare craft for a single-file prototype. Loses points for un-joined telemetry, flat action hierarchy, sub-AA contrast in dominant microcopy, and undesigned first-run states. As a consumer surface it would score ~4 — which is precisely why the disclosure ladder matters before "talk to this doc" ships.

## 4.5 Product Owner's review — 3/10

### Instrument vs product

The vault is admirably honest about what it is: "not a multi-user product surface… an instrument and a prototype… most of it is destined to become `sg.llm.*`." Today it serves exactly two people: the project lead and the Claude sessions building it. The "forcing function for the kernel API" framing is the **right** prioritization — the Workbench discovered the real host contract, proved key-in-vault agentic loops, and distilled a credible kernel API. That is genuine product work done cheaply.

But the changelog betrays drift: 20+ releases in ~2 days, and the v0.6.x run is heavily **instrument polish** — three iterations of a model picker, render caching, curated provider groups — while the commercially load-bearing items (key minting, observability vault, the early-adopter key UI) sit in "Next →" columns, explicitly blocked on a key source. The instrument is finished enough. Stop polishing it.

### The commercial model

**Strengths.** Client-side markup on metered OpenRouter usage is coherent with the zero-knowledge thesis: no server cost, no lock-in, cost transparency as a *feature*. The flywheel (useful tool → usage → consumption → data in vaults) is sound design, and the ephemeral-chat/file-memory brief gives it a real cost-control story.

**Risks the docs themselves confirm.**
- **Margin.** A "small markup" on users spending "a few dollars" is near-zero revenue; the v0.6.7 note excluding a free model because "no markup margin" quietly concedes fragile unit economics. And there is **no purchase path** — spend currently lands on the user's own OpenRouter account, so today's model produces zero attributable revenue.
- **Key abuse.** The key is client-visible by design; rotation + caps are reasonable, but the brief's own open question — "the key-sharing crypto is not yet precise" — stands unresolved six weeks later.
- **OpenRouter dependency.** Single provider for transport, pricing, and cost reconciliation; nothing addresses OpenRouter's ToS on redistributing keys — an existential check no brief performs.
- **Demand.** The engineering evidence is strong; the demand evidence is **zero** — no external user has spent a dollar. The v0.33.26 brief names this honestly; it is still untested.

### Roadmap coherence

The brief-tracker is excellent hygiene. The `sg.llm.*` phasing is technically sensible but **commercially backwards**: Phase 5 (budget/enforcement at `sg.llm.chat`) is the revenue chokepoint and Phase 4 ("talk to the doc") the headline value — both should be pulled forward, with Phases 2–3 deferred. Cut the semantic-graph "mesh of lenses" GTM apparatus for now; fix the deploy-drift item (B1: `getItems()` returning `{}` on the deployed page across nine versions) — a CI gate asserting against the live page is table stakes before any external user touches this.

### Competitive position and early users

The differentiation — zero-knowledge, local-first, glass-box cost transparency, keys that never leave the vault — is real and durable, but only for audiences that *care* (health, legal, compliance; the PatientIQ/REDCap comparisons suggest the team knows this). The wedge tool is thin: WhatsApp-audio transcription is a papercut mainstream assistants are absorbing. The outreach brief is the weakest document strategically: building an ontology-of-ontologies lens mesh to find ~10 early users is a classic displacement activity — intellectually on-brand, but it defers actual outreach to "Future / not in scope." Twenty hand-written LinkedIn messages would generate the spend signal faster than any RDF graph.

### Top 5 recommendations (next-quarter priority order)

1. **Unblock key distribution.** Mint budgeted, TTL'd OpenRouter keys as SG-API secrets from the admin vault; pin the wrapping/rotation crypto; verify OpenRouter ToS permits it. Everything gates on this.
2. **Run the spend experiment manually.** 15–20 hand-picked users, concierge onboarding, provided keys; track dollars and days-to-spend. No graph mesh until this signal exists.
3. **Ship `sg.llm.*` Phases 1 + 5 together, then Phase 4** — key custody, budget/observability enforcement, then the first kernel-native user-facing feature.
4. **Freeze Workbench features** at v0.6.x; instrument-only fixes henceforth. Fix the deploy gate so served bundles are asserted, not local ones.
5. **Scope the revenue path**: buy-credits design + a margin model, decided by the experiment in #2.

**Score: 3/10 product-readiness.** Outstanding prototype and documentation discipline, working end-to-end technology, honest self-assessment — but zero external users, zero attributable revenue, the key-distribution mechanism (the heart of the business model) unbuilt and cryptographically unpinned, and a single-provider dependency unexamined. A high-quality **instrument** one decisive quarter away from being *testable* as a product; not yet one.

# Part 5 — Synthesis: where the five reviews converge

**1. The execution center + context composer + skills graph are the crown jewels.** All five roles independently single out the same trio: the tiered/audited tool registry, byte-level prompt transparency with cost projection, and on-demand skills loading. These are ahead of most production agent UIs and are exactly the right things to lift into the kernel.

**2. One security cluster, seen from four angles.** The Architect's self-modification path (`app.json` writable by the app it governs + unrestricted egress), the Developer's verified XSS and over-eager parser (tool calls firing from *example code*), and the AI Engineer's user-role tool results (prompt-injection amplifier) and unenforced DESTRUCTIVE tier are all facets of one issue: **model output and vault content are adversarial inputs, and the last inch of that boundary isn't closed.** The fixes are small and known: strict `esc()` + href allowlist, `knownAction` = exact `REG` membership, fence-restricted segment extraction, deny-list `key.json`, drop `app.json`/`workbench.html` from their own write grant, confirmation-gate DESTRUCTIVE calls, CSP egress allowlist with the `sg.llm.*` migration.

**3. The philosophy is ahead of the implementation in one specific place.** The ephemeral-chat/file-based-memory doc is genuinely forward-thinking, but the compaction/summary asset it centers on doesn't exist in code, and history is unbounded by default. Implementing auto-compaction on chat close would close the single biggest spec-vs-code gap.

**4. Observability ≠ evaluation, and telemetry ≠ a timeline.** The AI Engineer and Designer converge from different directions: the traces are complete (sessions are ready-made regression fixtures; the panels show everything) but nothing *joins* or *judges* them — no eval runner, no prompt versioning, no cross-panel causal linking, no per-reply receipts. The data model already supports all of it.

**5. The strategic tension is real and the vault admits it.** The PO's 3/10 isn't a contradiction of the technical 6.5–7.5s — it's the same fact viewed commercially: a brilliant instrument whose business mechanism (key distribution, enforcement, a purchase path, a demand signal) is still on paper. The changelog's velocity is impressive and slightly misdirected; the docs' own "Next" columns already know what should come first.
