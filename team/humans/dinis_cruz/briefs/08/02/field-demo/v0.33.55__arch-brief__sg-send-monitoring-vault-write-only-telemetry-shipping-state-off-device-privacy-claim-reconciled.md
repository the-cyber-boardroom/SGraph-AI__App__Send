# The Monitoring Vault: Write-Only Telemetry, Shipping The State Off The Device, And The Privacy Claim That Has To Be Reconciled Before Saturday

**version** v0.33.55
**date** 2 August 2026
**from** Human (project lead)
**to** Engineering, Product, Design, Legal

**type** Architecture brief

*First of 2 August. Browser telemetry behaviour is grounded and cited. Data protection points are factual and are not legal advice. Written two days before the field demo opens, and the timing shapes the recommendations. Offered to be built on and challenged.*

---

## What This Is

An instrumentation architecture for the field demo, using a vault-to-vault mechanism already proven elsewhere: **the technique is that one vault writes encrypted messages into a storage location whose contents are sealed to a public key held by another vault, so the sending side performs a single write and carries no ongoing cost, and because it holds only the public half it cannot read back anything it has sent, which makes the telemetry write-only from the device's perspective and means a lost or compromised iPad discloses nothing about earlier sessions; the architectural gain the memo identifies is larger than the metrics, because if interaction state ships to another vault then the device does not have to preserve it, which lets the demo device stay effectively stateless between conversations and is exactly the property you want in something handed to strangers all day; there is a conflict to settle before the event, since the field workflow's stated privacy position is that nothing a person enters leaves the device, and this proposal sends interaction data off it and contemplates recording who the person was for later follow-up, so the claim needs to become precise rather than being quietly weakened, and the audience at this particular event is the one most likely to ask; the batching instinct is right and the specific failure the memo names, losing data at page navigation, has a documented answer, because the events traditionally used for this are unreliable on mobile browsers and actively harmful to caching, the recommended combination reaches roughly ninety percent, and the remaining loss is best absorbed by treating local storage as a durable buffer that is only cleared on confirmed delivery and re-attempted on the next load, which works unusually well here because the same device is used repeatedly through the day; and the strongest move available is to turn the whole thing into part of the demonstration, by showing a visitor exactly what is being sent and by carrying the collection itself as an accepted entry in the register the product is there to show.** It is the first document of 2 August (cross-ref: the v0.33.53 hand-them-the-iPad brief, the v0.33.54 black-hat-pack dev brief, the v0.33.48 browser-local-databases brief, the v0.33.51 distributed vault architecture brief, and the v0.33.54 register-maintains-itself brief). New contributions: **write-only telemetry named as a security property rather than an implementation detail, state-shipping identified as the larger architectural gain, the conflict with the stated privacy position surfaced with three resolutions, the durable-buffer pattern that makes lossy beacons near-lossless on a repeatedly used device, and the proposal to make the collection itself a demonstrated register entry.**

## The Mechanism, And The Property Worth Naming

The technique is established rather than new. The project lead: **"one of the super powerful features that we already added, and we use this in the medical vault, is the ability for one vault to send messages and very efficient messages and logs to another vault."** With the mechanics. The project lead: **"the server side allows the vault to write messages to a particular storage folder that is encrypted using a public key that we have defined, which means the iPad vault can send messages to our monitoring vault without any major performance implications, because it's literally just one write, one API call."**

The performance argument is clear. The security property is not stated and is the more valuable half.

**The sending device holds only the public key.** It can seal messages and it cannot open them. So the telemetry is write-only and append-only from the device's side, and three consequences follow that ordinary analytics does not have:

- A stolen or inspected iPad reveals nothing about any previous session, because the ciphertext on the way out is unreadable to the thing that produced it.
- Nobody operating the device, including the partner carrying it, can read the accumulated record.
- The monitoring vault holds the only key, so access to the data is a deliberate act performed somewhere else.

At a security conference that is a stronger position than any privacy policy, and it should be stated in those terms rather than described as a logging pipeline.

## Shipping The State Is The Bigger Win

The memo notices this almost in passing and it is the most consequential architectural point. The project lead: **"it allows the main iPad vault to not have to worry about preserving state, because we can ship the state somewhere else."**

A device handed to a stranger, then to another stranger, forty times in a day, has a state problem. Whatever the previous person entered must not be visible to the next one, and whatever is worth keeping must survive the handover. Those two requirements pull against each other, and the usual answers are either a login, which kills the hand-over test, or clearing everything, which loses the record.

Shipping the state resolves it. The device keeps only what the current conversation needs, ships the rest, and can be reset between visitors without losing anything. **The device becomes ephemeral and the record becomes durable**, which is the same inversion the corpus already applies when it treats the browser database as a query engine and the vault as the source of truth.

## The Privacy Claim Has To Be Reconciled

This is the item that needs a decision before the business hall opens, and it is better decided now than in a hallway.

The field workflow brief written on 28 July committed to a specific position: nothing a visitor enters leaves the device unless they ask for a takeaway, and the privacy answer should be offered in the first fifteen seconds rather than defended on the third question. That was identified as the fastest available demonstration of the sovereignty argument to an audience that cares about it more than any other.

This memo proposes sending interaction data off the device, and goes further. The project lead: **"we can capture the timings, we can capture even the person who did it, if she wants, to come to that for follow-ups."**

Those two positions are not compatible as stated, and the audience is the worst possible one to discover that with. Three resolutions, which combine well:

**Make the claim precise rather than weaker.** There is a real and defensible distinction between the content a visitor enters about their own estate, which never leaves, and interaction telemetry such as which page was reached and how long a question took. The precise sentence is stronger than the vague one, and it is checkable. What must be avoided is the phrase about only sending metadata, which has a poor history with exactly this crowd.

**Make identity capture an explicit exchange.** Recording who someone was, for follow-up, is lead capture. It is entirely legitimate and it must be a deliberate, visible act that the person performs, in the way a business card is handed over, rather than something inferred or attached silently to a session. It is also personal data, which carries a requirement for a lawful basis and a notice regardless of where the conference is held, and that is worth confirming rather than assuming.

**Show them the telemetry.** This is the strongest of the three. A screen showing exactly what this device has sent, in plain terms, available to any visitor who asks, converts the whole subject from a liability into the most credible thing on the stand. At this event, transparency about your own instrumentation is a differentiator that costs almost nothing to build.

## Make The Collection Part Of The Demonstration

Following directly from the above, and the best idea available here.

The product exists to show an organisation its risks, who owns them, and on what interval they are reviewed. The monitoring vault creates a real risk: personal data collected at a conference, on a shared device, with a follow-up purpose. **That risk should be in the demo's own register**, with a named acceptor, a date, an interval, and a plug profile.

A visitor who asks what happens to their data can then be shown the answer inside the product rather than told it. That is the dogfooding standard the corpus already committed to when it concluded that a maturity model published by a party that has not run it against itself is marketing, and it turns the single most likely objection into the single best demonstration.

## What To Capture

The memo asks for the list. The project lead: **"we need to define metrics from page load to answer submissions to timings to observations to special types of information."** A starting set, organised by what each answers:

| Group | Events | The question it answers |
|---|---|---|
| Session | start, device, scenario chosen, reset | How many conversations, and which scenarios attract |
| Progress | page reached, question shown, answer submitted, time per question | Where attention holds and where it goes |
| **Abandonment** | last event before reset or idle | **Where the hand-over test fails** |
| Outcome | register generated, altitudes viewed, takeaway requested and type | Whether the interaction completed and what they left with |
| Cost | model spend per session | The live meter's figure, retained |
| Friction | back navigation, re-answers, skipped questions | Which questions people cannot answer from memory |

Two of those deserve emphasis. **Abandonment is the single most valuable metric**, because the workflow's own acceptance test is whether a stranger can be handed the device and get through it without narration, and the point at which they stop is the direct measurement of that. And **friction** answers a question the corpus has been guessing at, which is which of the plug questions people genuinely cannot answer, because a question nobody can answer is itself the finding the product is built to surface.

## Batching, Buffering, And The Flush Problem

The optimisation instinct is right. The project lead: **"you don't have to have a case where every single request or every single action is sent; we can batch them, this doesn't need to be in real time, because most of the data is only going to be processed once we open the admin monitoring vault."**

And the memo names the exact failure mode that batching introduces. The project lead: **"the key is to make sure that it's done before we navigate the pages, or before we move, or before we lose things."** With the right answer already half-formed. The project lead: **"maybe even store some of that data in local storage, and then sync it up at specific intervals."**

The web platform has a documented answer and some specific traps.

The events traditionally used to flush on exit are unreliable, particularly on mobile. Reporting on beacon reliability indicates that one of them does not fire at all on mobile Safari, that both of them disable the browser's back-forward cache, and that neither improves reliability enough to justify that cost. The recommended combination is the visibility-change event when the page becomes hidden, together with the page-hide event, which is benchmarked at around ninety-one percent delivery against roughly eighty-two percent for the older combination. Because more than one of these can fire for a single user action, the flush must be deduplicated so a departure is reported once. The dedicated beacon method exists precisely for this and survives page teardown, with a size limit imposed by the browser.

Even the best combination loses roughly one departure in ten, which brings the real answer:

```
   buffer in local storage, always
        |
        +-- flush on interval (idle, or every N events)
        +-- flush on visibilitychange -> hidden, and on pagehide, deduplicated
        |
        +-- CLEAR THE BUFFER ONLY ON CONFIRMED DELIVERY
        |
        +-- on next load: unsent events are still there -> send them first
```

**That last step is what makes a lossy transport near-lossless here**, and it works unusually well in this specific deployment because the same iPad is picked up again minutes later by the next visitor. A session whose final flush failed is recovered by the following session's opening flush. Which in turn means the buffer must not contain anything belonging to the previous visitor that the next one could see, so buffered events should be sealed at the point they enter the buffer rather than at the point they are sent.

## The Monitoring Vault Itself

The memo asks what the receiving side looks like. The project lead: **"what is the UI for the monitoring mode? What is the vault that is going to monitor it? What are the workflows?"**

Given the timing, the honest recommendation is that this is two artefacts rather than one. The **capture** side is required before the event, because data not collected on the fourth cannot be recovered afterwards. The **interface** side is not, because the memo has already established that the data is processed when the monitoring vault is opened, which can be on the seventh.

So the instruction for the build is to get the schema and the pipeline right now, keep the events well structured and self-describing, and accept a crude view of them until after the event. An hour spent on the event schema this week is worth more than a day spent on dashboards, because the schema is the part that cannot be fixed retrospectively.

## The Line Not To Cross

The memo floats an extension and it should be declined for now. The project lead: **"we could even capture things like mouse movements, if that's relevant with the iPad, but all sorts of interesting metrics that we can capture."**

On a tablet that means touch and gesture data, which is behavioural biometric material. Capturing it at a security conference, from people who did not expect it, on a device presented as privacy-preserving, would be a serious misstep and would undo everything the transparency position buys. It is also unnecessary: the abandonment point and the per-question timings answer the questions that actually matter.

If gesture data is ever wanted, it should arrive as a separate, disclosed, consented thing, and it should not arrive this week.

## Timing

The business hall opens on the fourth, which is two days from now. That is enough for a sealed write, a local buffer with a deduplicated flush, and a well-designed event schema. It is not enough for a monitoring interface, an identity-capture flow with a proper consent step, and a dashboard.

The dev brief written on 31 July recommended splitting the deliverable into what ships for the event and what follows, and this is the first concrete instance of that split. Capture now, interpret later, and decide the privacy wording today rather than on Saturday morning.

## What This Does Not Try To Be

- **Not real-time monitoring.** Batched delivery, processed when the monitoring vault is opened.
- **Not silent identity capture.** Recording who someone is must be an explicit exchange they perform.
- **Not behavioural biometrics.** Gesture capture is declined for this event.
- **Not a dashboard project.** The schema is what must be right before Saturday; the interface can wait.
- **Not a weakening of the privacy position.** It requires making that position more precise, and showing it.

## Honest Tensions

| Tension | Note |
|---------|------|
| The privacy claim versus the telemetry | Both are defensible and they are not compatible as currently stated, and this audience will notice before we do |
| Content versus metadata | The distinction is real and the phrase describing it is worn out, so the wording matters more than the architecture here |
| Write-only telemetry versus what it contains | Sealing the channel protects the data in transit and says nothing about whether collecting it was appropriate |
| Shipping state versus the stateless claim | A device that ships state is not stateless, it is state-shedding, and the demo language should not blur that |
| Buffered events versus the next visitor | A durable local buffer holds one person's events while another holds the device, which is why events must be sealed on entry rather than on send |
| Two days versus doing this properly | Capture is achievable and consent flows and interfaces are not, and pretending otherwise is how the privacy position gets broken by accident |
