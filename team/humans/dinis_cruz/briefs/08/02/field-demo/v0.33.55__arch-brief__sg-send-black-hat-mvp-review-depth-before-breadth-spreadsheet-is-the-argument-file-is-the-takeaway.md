# Review Of The First Demo Build: Depth Before Breadth, The Spreadsheet Is The Argument Rather Than The Fallback, And The File Is The Takeaway

**version** v0.33.55
**date** 2 August 2026
**from** Human (project lead)
**to** Engineering, Design, Product

**type** Architecture brief

*Second of 2 August, reviewing the first working build. Conventional risk register practice is grounded and cited. Written two days before the field demo opens. Offered to be built on and challenged.*

---

## What This Is

Feedback on the first working version, which is good, together with the changes that would make it better and one that answers a question parked since 28 July: **the strongest structural change is to ask far fewer questions before showing the whole chain, because the later questions genuinely add value and only to somebody who has already seen where the answers go, so the sequence should be one or three questions, then the complete path from that single fact to a risk somebody owns, and only then the rest, which matters because the workflow's own acceptance test is whether a stranger can be handed the device and get through it unaided and eight questions is a long time to hold someone in a corridor before any payoff arrives; the first answer is already the demonstration, since somebody confirming they run an agent that touches production has, in that moment, stated a fact that is itself a risk requiring an owner, so the product can show a complete chain from one answer without any further input; the request for a spreadsheet view is not a concession to unsophisticated users but the sharpest argument available, because a conventional register has a well-known set of columns and the ones most often left empty or stale are precisely the ones this system fills structurally, with published practice describing stale review dates as the single most common audit finding and the escalation column as the thing that makes a register a control rather than a spreadsheet; the risks should connect to each other and back to their evidence, which the graph already holds and the view does not yet show, and the canvas that fills up as answers arrive is the best demonstration device in the build because the visitor watches their own picture being assembled rather than being shown a stock one; the file separation proposed is a real modelling distinction between what exists and what is practised, and a third file should be added for the computed output so that inputs and derived results stay apart in the same way the consolidated Act is computed rather than stored; and the drag-and-drop viewer on a static site answers the question of what the takeaway actually is, provided the parsing happens entirely in the browser, because a file that uploads to see itself would break the privacy claim in the same way the telemetry nearly did.** It is the second document of 2 August (cross-ref: the v0.33.53 hand-them-the-iPad brief, the v0.33.55 monitoring-vault brief, the v0.33.54 change-psychology brief, the v0.33.53 cognitive-load brief, and the v0.33.54 canonical-Act brief). New contributions: **depth before breadth as the question sequence, the first answer identified as a complete demonstration in itself, the spreadsheet view reframed as a comparison argument with the specific columns named, the third file for computed output, the file as the answer to the parked takeaway question, and the client-side parsing requirement.**

## What Is Working

Worth recording because it constrains what should be changed. The project lead: **"the first version of the Black Hat demo app is looking really good."** With three specifics. The project lead: **"I really like the way the questions go."** The scenario framing. And the altitude flow. The project lead: **"I really like the three execs and the flow from one to the three."**

The altitude flow being the thing that lands is worth noting, because it was predicted on 28 July as the most likely element to work and the most likely to run out of time. It has survived, which suggests protecting it in any restructuring.

## Depth Before Breadth

The most important change. The project lead: **"leverage that scenario and also ask a small amount of questions, so in a way, even just one question, so maybe have one, three, five, and then eight."** With the reasoning. The project lead: **"the next batch of questions, they actually add value, but they add value to somebody who's already seen the full workflow."**

That is right and it is a stronger point than a preference about pacing. The corpus's own acceptance test for this workflow is that a stranger can be handed the device and reach the end without narration, and yesterday's instrumentation brief identified the abandonment point as the metric that measures it directly. Eight questions before any output is a long time to hold somebody in a corridor with no reward, and a person who stops at question five has seen a questionnaire rather than a product.

```
   NOW                              PROPOSED
   8 questions                      1 question
        |                                |
        v                                v
   3 registers                      the whole chain, end to end
                                          |
                                          v
                                     now 3 more, which land
                                     because you know where they go
                                          |
                                          v
                                     now 5 more, if they want them
```

The second and third batches are then not a longer questionnaire; they are the visitor choosing to go deeper on something they now understand. That is a different act entirely, and it is also a much better signal for the monitoring vault, because continuing past the first payoff is a genuine indication of interest in a way that finishing a form is not.

## The First Answer Is Already A Risk

The observation that makes the single-question version work. The project lead: **"when somebody says yes, I have one that touches production, that's already a risk, right? You already have a risk, which is you have an agent that touches production, which is a risk that is worth capturing and needs to be accepted."**

That is exactly right and it should be the demo's opening move. One factual answer produces a real risk, with an owner, an interval and a place in a register, with no further input required. It is the fastest possible demonstration that this system does something a questionnaire does not, and it uses a fact the visitor has just supplied about themselves rather than an illustration.

It also belongs to the meta-risk family named on 31 July, in the same shape: the existence of a thing is itself a rateable exposure before anything has gone wrong with it.

## The Spreadsheet Is The Argument

The request sounds like a concession and is the opposite. The project lead: **"we should have a version that looks like a spreadsheet, because that's what a lot of these registers do, and we should also try to replicate some of the normal common risk registers."**

Conventional practice has a well-documented shape. Registers typically carry a risk identifier and description, a category, likelihood and impact scores, an inherent score before controls, the existing controls and their effectiveness, a residual score, a treatment response drawn from accept, treat, transfer or avoid, a named risk owner, a treatment owner and deadline, a status, a trigger, and a review date. No standard prescribes the format; the shape is convention rather than requirement.

Two findings from that practice literature make the spreadsheet view into a demonstration rather than a rendering.

**Stale review dates are described as the single most common audit finding on a risk register.** In this system a review date cannot go stale, because the interval is the decision and an expired interval produces an unaccepted risk that escalates. The column that is conventionally the weakest is here structurally impossible to leave rotting.

**The escalation column is described as what makes a register a control rather than a spreadsheet.** In this system escalation is not a column somebody fills in; it is what the register does when nobody accepts.

So the right way to build this view is as a familiar register, correctly and fully populated, in which the columns that are usually blank or out of date are the ones that are unmistakably alive.

| Conventional column | Usually | Here |
|---|---|---|
| Risk owner | Often a team or blank | A named person, because acceptance requires one |
| Review date | Stale, the commonest audit finding | The interval, which cannot expire silently |
| Escalation path | Declared in a policy, rarely used | What happens automatically when nobody accepts |
| Treatment response | One of four, usually accept by default | Acceptance is universal, and the variable is how long |
| Evidence | A reference, if anything | A chain back to a fact and a source |

That table is the pitch, and it works precisely because it is drawn on the incumbent's own grid. The change-psychology brief of 31 July made the general form of this argument: the incumbent is the spreadsheet, familiarity is its main advantage, and a replacement must be visibly better on the first day. Showing the same grid filled properly is how you win on the incumbent's terms before offering anything unfamiliar.

The graph view then earns its place by showing what the grid cannot, which is the next section.

## Connect The Risks To Each Other

The gap in the current view. The project lead: **"we need to connect the risks to each other, because the risks connect to each other, each risk leads to another risk, and we already have this in the graph, so we should be displaying the sequence of events where you have the fact."**

This is where the graph does something a register cannot represent at all. A spreadsheet has rows; it cannot express that this risk exists because of that fact, which was established by this evidence, and that accepting it at this altitude leaves that other exposure unowned. The corpus's grounding ladder already models it, and the memo asks for the chain to be shown in both directions: forward from the agent to the risk at the top, and backward from a risk to the evidence supporting it.

The memo also names the shape. The project lead: **"we should even have a little visualisation where we go from agent all the way to the risk at the top, and each of the multiple stakeholders and the evidence around it."**

Two views of one thing, then: the grid for recognition, the chain for the argument. Neither replaces the other.

## The Canvas That Fills Up

The best demonstration idea in the memo. The project lead: **"what's interesting about this canvas, this graph, is probably something that we can be populating as we add more risks, so it starts empty or very little, maybe just the stakeholders, and then it starts to get populated as we grow."**

Watching a picture assemble from your own answers is qualitatively different from being shown a completed one. It makes the graph legibly *theirs*, and it removes the suspicion that the output was prepared in advance, which at this event is a real suspicion. It also gives the interaction a visible reward at every step, which is exactly what the depth-before-breadth restructuring needs to sustain attention through the later questions.

There is a mild psychological effect working in favour here too, of the kind grounded on 31 July: people value what they had a hand in building. A graph the visitor watched being constructed from their own facts is not a demo they were shown.

## Three Files, Not Two

The separation proposed is a genuine modelling distinction. The project lead: **"one is the whole do you have this, the other one is do you have the procedures, do you have the actions, have you done it."** With a good analogy. The project lead: **"it's almost like one is the network architecture diagram, and the other is actually what happens on top of that."**

That is the split between **what exists** and **what is practised**, and it is the right one. Existence facts describe the estate: there is an agent, it touches production, it holds these credentials. Practice facts describe capability: there is a procedure, somebody has run it, it was tested last quarter. They behave differently, they age differently, and they are gathered from different people, which is why they visualise differently.

**A third file should be added: the computed output.** The risks, the registers, the altitudes and the citations are all derived from the first two, and keeping them separate has the same benefit established for the canonical Act, where the consolidated text is computed rather than stored. If the model improves, the output regenerates from the same inputs. If output and input are mixed in one file, every improvement invalidates every artefact anyone is holding.

```
   estate.json      what exists          <- collected
   practice.json    what is done         <- collected
        |
        v  computed
   register.json    risks, owners, altitudes, citations
```

## The File Is The Takeaway

This answers a question the corpus has carried since 28 July as the single most important unresolved product decision. The project lead: **"if I can host that UI on a static website the same way that we already have a website that hosts the EU AI Act, then all somebody has to do to see the data again is drag and drop that JSON file, so that JSON file almost becomes what you move around."**

That is the takeaway, and it satisfies every constraint the corpus has previously set for one. It requires no account, which the cognitive load brief identified as the difference between a takeaway and a portal. It resolves to content rather than to a sign-in. It is theirs, it persists, and it can be forwarded to a colleague, which was named as the only reliable indication that the value travelled. And it costs nothing to produce because it is the artefact the application already has.

It also gives the demo a second life. The visitor who drags their file onto the site a week later gets the whole thing back, on their own machine, without anybody provisioning anything.

## Drag And Drop Only Works If It Never Uploads

The condition attached, and it matters for the same reason the telemetry did yesterday.

That file contains what the visitor said about their own estate. If dragging it onto a website transmits it to a server, the privacy position collapses, and this audience will check. A static site can parse and render the file entirely in the browser without it ever leaving the machine, which is the same client-side posture the corpus already takes for its query engines.

So the requirement is explicit: **the viewer parses locally, uploads nothing, and says so on the page.** Built that way it is another demonstration of the sovereignty argument rather than a hole in it, and it can be verified by anybody with developer tools open, which at this event some of them will have.

## Pre-Populated Demos And The Tree

Two related requests. The project lead: **"I would like us to have a bunch of pre-populated demos with answers that go straight away into that dashboard view."** And the more interesting one. The project lead: **"this is a tree, almost like a choose your own adventure, so it's also very powerful to show in one go all the different options, show the multiple tree that we have created."**

With an observation that is worth more than it appears. The project lead: **"what we're basically saying is that the whole thing becomes deterministic, because it becomes a tree view of what's happening."**

Determinism here is a safety property rather than only a demo feature. A device handed to strangers at a security conference that can only ever produce outputs from a known finite set cannot be induced to say something unexpected, which removes an entire category of risk that would otherwise need managing. It also means the whole space can be tested exhaustively before Saturday rather than sampled, and the pre-populated demos are simply saved positions in a tree that already exists.

Showing the tree itself is a strong move for a technical audience, because it demonstrates that nothing is being generated on the fly, and it lets a visitor see the paths they did not take.

## What This Does Not Try To Be

- **Not a longer questionnaire.** One question to a complete chain, then more by choice.
- **Not a spreadsheet as a lesser view.** It is the comparison that makes the argument on the incumbent's grid.
- **Not a graph replacing the grid.** Two views of one thing, doing different jobs.
- **Not a file that uploads.** The viewer parses in the browser and says so.
- **Not generated output.** A finite deterministic tree, which is a safety property at this event.

## Honest Tensions

| Tension | Note |
|---------|------|
| Fewer questions versus less data | A shorter path collects less about the visitor's estate, and the depth-before-breadth argument accepts that trade deliberately |
| Replicating a conventional register versus endorsing it | Drawing our output on the incumbent's grid invites the comparison and also legitimises a format the corpus argues is inadequate |
| The canvas filling up versus performance | Live assembly is the best moment in the demo and the most likely thing to stutter on a tablet in a hall with poor connectivity |
| Three files versus one artefact | Separation is architecturally right and gives the visitor three things to keep track of, which argues for one bundle containing three parts |
| Client-side parsing versus what people assume | Uploading nothing is only persuasive if stated, and most visitors will assume the opposite unless told |
| Showing the tree versus revealing the scaffolding | It proves nothing is generated and it also shows exactly how small the demo is |
| Two days | The question restructuring and the spreadsheet view are cheap; the canvas, the chain view and the viewer site are not, and they cannot all land by Saturday |

## Open Questions

| Question | Notes |
|----------|-------|
| Which single question opens? | The agent-touching-production one is the obvious candidate, since its answer is immediately a risk |
| What is in the first chain? | The end-to-end path shown after one answer, and how far up the altitudes it goes |
| Is the spreadsheet the default view? | It is the familiar one, and defaulting to it may bury the graph that differentiates |
| What is the file bundle? | Three parts in one file, or three files, and what the visitor is actually handed |
| Does the viewer site exist by Saturday? | If not, the file is still worth producing, because it can be viewed later |
| How is the tree rendered? | A visualisation of all paths is a different design problem from the walkthrough |
| What ships by Saturday? | The restructuring and the register view look achievable; the rest should be sequenced deliberately rather than attempted |
