## The Queue Was Specified On 26 May

The memo proposes a mechanism and asks whether it will scale. Both halves are in the repository.

`v0.27.64__dev-brief__sg-send-vault-commit-queue-batched-autosync.md`, 26 May, opens by recording that **commit-on-every-change was already the shipped behaviour**, describing it as the most aggressive possible auto-commit, and it exists because that behaviour was about to become a problem. It names three reasons, and they are precisely the concerns the memo raises three months later: race conditions from many rapid commits, a network-call explosion because every commit generates many unoptimised calls, and a chatty environment generating files in bursts.

So the memo's proposal is not a new design. **It is the current behaviour, and the corpus already decided to move off it.**

What May settled, and what should be inherited rather than re-derived:

| Settled on 26 May | The value |
|---|---|
| A change starts or extends a timer; the commit fires at the end | One commit per window rather than per file |
| The window is configurable | Zero preserves commit-per-change; 1, 5, 10, 30 and 60 seconds offered |
| A suggested default | Ten to fifteen seconds |
| Staging is visible | A pending set, a control pane, and a debug view of the drain |
| The drain is asynchronous | Accumulate, commit, repeat, while new changes queue for the next drain |
| A conflicted batch aborts | It reuses the existing conflict resolution rather than inventing one |
| One honest trade-off | Repeated edits to one file inside a window collapse into one commit, so intermediate states are not separately recorded |

That last row is the answer to a question the memo does not ask and should. **Batching is lossy by design**, and the loss is exactly the case where a file is being edited repeatedly, which is the common case for an agent iterating on one document. Setting the window to zero recovers it and reintroduces everything the window exists to prevent. That trade is the feature's central setting and it should be surfaced rather than defaulted quietly.

## What Is New Is The Event Source, Not The Queue

The May design has a scoping sentence that decides most of today's work: it is a feature of the main vault interface, explicitly not the embedded frame.

That matters because **a browser interface owns the change events.** The application knows a file changed because the application changed it. There is nothing to detect.

The memo asks for something else. The project lead: **"how can we do that inside A cloud environment, right? But every time a file is touched, we we preserve it."** A filesystem has no such channel. Nothing tells you a file changed; you either watch or you poll.

| | Vault interface, May | Filesystem drive, today |
|---|---|---|
| How a change is known | The application performed it | **Must be discovered** |
| Completeness | Total, by construction | **Best effort, with a documented loss mode** |
| What a save looks like | One logical operation | **Several events, often on a temporary path** |
| What the queue does | Batches known changes | Batches discovered changes, and covers for missed ones |

**So the queue transfers unchanged and the watcher is the new component.** That is a much smaller project than the memo implies and a less reliable one than it assumes, and the next section is why.

## The Cloud Environment Has Numbers, And They Were Measured Here

The memo asks the right question about the environment. It has an answer with figures, taken from a running agent container of the kind this feature targets rather than from documentation.

| Limit | Measured | Consequence |
|---|---|---|
| Watches per user | 64834 | Recursive watching costs one watch per directory, and a single dependency tree can exhaust it |
| Instances per user | 128 | Bounds how many independent watchers can coexist |
| Queued events | 16384 | A burst larger than this overflows |

Three properties of the mechanism decide the design, and all three are in the kernel documentation rather than being folklore.

**Monitoring is not recursive.** A watch covers one directory, and every subdirectory needs its own. So the watch count is the directory count, not the file count, and it grows as the agent works.

**Overflow loses events.** The documentation states plainly that the queue can overflow, that events are lost when it does, and that robust applications must handle that gracefully, with the suggested remedy being to tear the watcher down and rebuild it. The overflow is signalled, so it is detectable, and what follows it cannot be recovered from the event stream.

**A watch established on a directory does not cover what was already in it.** The documentation recommends scanning a subdirectory immediately after adding a watch, because anything created in the gap is missed.

Together these give one conclusion worth stating as a design rule rather than as a caveat: **a watcher alone cannot be the source of truth, so the drive needs a reconciling scan and needs it from the first version.** The scan is what runs on overflow, on watcher restart, and on a schedule as a backstop. A design that treats the scan as a recovery path bolted on later will ship a drive that silently misses files, which is the worst possible failure for a product whose claim is that nothing is lost.

There is a second, independent reason the window is not optional. **A single logical save emits several filesystem events**, because the common safe-write pattern is to write a temporary file and rename it over the target. An unbatched watcher therefore commits several times per save, some of them capturing a partial or temporary file. The timer window collapses them. **So the window is correctness, not performance**, which is a stronger justification than the May brief needed and it should be recorded as such.

## The Conflict Model Is Better Than The Memo Remembers

The memo is right and modest about this. The project lead: **"you should even have multiple agents working at the same time, where only if they edit the same file at the same time, we have conflicts. And even now, we already have a way to detect conflicts."**

Fetched today, the shipped model is four mechanisms rather than one:

| Mechanism | What it does |
|---|---|
| **Clone branches** | Every clone gets a private branch whose keys stay local and are never pushed, so each agent is isolated by default |
| **Three-way merge per file** | Common ancestor, ours and theirs, with conflicting paths written out as conflict files |
| **A resolve verdict** | Classifies genuine conflicts separately from one-sided and identical changes |
| **Compare-and-swap on push** | An atomic batch write, so a push that lost the race is rejected cleanly instead of clobbering, and the caller pulls, merges and pushes again |

Two things follow, one confirming the memo and one correcting it.

**The isolation the memo wants already exists and it is not a feature that needs building.** A per-agent clone branch is per-agent isolation, and promotion into a shared branch is a push that merges. That is the model.

**The correction is where the contention lives.** The memo says conflicts occur when two agents edit the same file. That is true of content and false of the push. **The contended object is the branch reference**, so two agents editing entirely disjoint files still collide on it, and the compare-and-swap is what makes that safe rather than silent. It is not a conflict in the merge sense and it will not produce a conflict file; it produces a rejected push and a retry.

Three consequences for a drive that pushes continuously.

**Push rate is bounded by one reference regardless of how many files changed**, so the timer window is doing double duty and its length should be chosen against the number of concurrent agents rather than against file volume alone.

**The retry loop is the thing to instrument**, because rejected pushes per minute is the metric that says whether the window is too short, and it is invisible unless somebody measures it. The corpus's own position applies: instrument before you enforce.

**And the resolve verdict is more valuable here than in normal use**, because a continuously syncing drive generates overwhelmingly one-sided changes, and a merge that can tell those apart from genuine conflicts is what makes automatic merging safe enough to run without a human.

## Minimal Permission Is Not A Permission Question

The memo asks for the permissions mapped. The project lead: **"one of them is a shared drive with minimal permissions for for agents."**

**It cannot be answered as permissions**, and the reason is settled in this corpus twice. Possession of a key is access, so granularity comes from the shape of what you store rather than from a policy on top of it, which is the position reached on 14 August. And the four shipped capabilities gate operations rather than content, which is the correction made on 19 August, so an append token, an enumeration key and a write key decide what you may do to a vault and never which file inside it you may touch.

So one shared vault with one write key handed to four agents grants every agent everything, including purge. In this morning's vocabulary that is a grant four times larger than any agent's mandate, and the excess is unaccepted by construction.

**Minimal permission therefore has to be delivered as topology.** Three vaults rather than one:

| Vault | Who holds what | What it bounds |
|---|---|---|
| **Shared corpus** | Read key with every agent; write key with the orchestrator only | Everybody reads, no agent can rewrite shared history |
| **Per-agent workspace** | One vault per agent, that agent holding its own write key | A compromised agent reaches its own workspace and nothing else |
| **Session record** | An append lane on the orchestrator's vault | Write-only, account-less, and a blind acknowledgement, so an agent cannot read what it reported |

Promotion from a workspace into the shared corpus is then a merge performed by whoever holds the shared write key, which is the serialised pull request the site already leads with rather than a new mechanism.

Three notes on provenance, because none of this is new.

The 16 August research on shared drives for agents reached the same conclusion from the opposite direction, finding that surveyed products all run on your identity and that the answer is segregation rather than scoping. **This is the build side of that finding.**

The corpus validated the principle in March in almost the memo's own terms, recording that instead of giving an agent privileges and access to all assets you give it credentials for its own identity and let the vault control what that identity can do.

And a fourth tier has been proposed since March that would change the shape if it shipped: a structure key derived alongside the read key, granting metadata without content. **That is the only proposal on the table that would give a shared drive a genuine middle permission**, and it should be checked for status before the topology above is treated as the only option.

## The Chat History Is Already A File, Which Solves One Problem And Creates A Worse One

The memo treats capture as an open question. The project lead: **"including the the chat history, which is going to be interesting to see how we could capture that too, but I think that is possible."**

**It is not interesting, it is a path.** Verified by looking inside a running agent container: the session transcript is a single line-delimited JSON file named for the session, sitting under a per-project directory, with a sibling directory holding persisted large tool outputs, alongside separate directories for session state, shell snapshots, task state and uploads. The whole of it came to twelve megabytes for a working session of a few hours.

So capture needs no mechanism. **It needs a path added to the watch set**, and the memory-preservation half of the memo is the cheapest part of the feature rather than the speculative part.

The consequence is the expensive part, and it is the most important finding in this brief.

**The transcript is a superset of every file the session touched.** Anything the session read is quoted inside it. So an ignore rule that excludes an environment file from the drive does not exclude its contents, because the transcript contains them the moment that file was read. Path-based exclusion, which is the only kind an ignore file offers, does not reach the transcript at all.

Set that beside the finding recorded this morning, that a secret committed inside vault ciphertext matches no scanning pattern and therefore fires nothing. Together:

> An auto-syncing drive that captures the session record is a mechanism for moving every secret a session ever saw into a store that no scanner can inspect, and the house rule is to supersede rather than delete, so it stays there.

That is not an argument against the feature. It is the cost side of the property the product sells, stated in advance rather than discovered, and there are three honest responses.

**Put the transcript in its own vault under its own key**, so that the blast radius of the work product and the blast radius of the record are different. This is the same topology argument one level down and it costs nothing to do at the start.

**Make transcript capture explicit per session rather than default**, because the person starting the session is the only party who knows whether it is about to read credentials.

**And do not promise redaction.** The transcript is the record, and a redacted record is not the thing being preserved. Saying so is better than shipping a filter that works on the patterns somebody thought of.

## The Ignore File Has Blocked This Since March

The precondition, and it is older than the memo assumes.

An ignore file was proposed on 19 March with its design already specified: glob patterns in the manner of the equivalent git file, a hard-coded default set applied regardless of user configuration, and the defaults named as the dependency directory, the git directory, environment files and the Python cache directory. It appears in the repository's own status tables as proposed rather than shipped. It was raised again on 6 August as the thing blocking the git and vault co-existence pattern from being safely available. **It does not appear anywhere in the site's published index today**, which is consistent with it not having shipped, and the team should confirm rather than take a missing index entry as proof.

Five months is worth stating plainly, and so is the change in its status. Until now it has been an inconvenience for a pattern people wanted. **For this feature it is a precondition**, because a watcher pointed at a working directory will commit the dependency tree, the git directory and every environment file within seconds of starting, and the corpus's own limits make that fail loudly as well as unsafely: a thousand files per token, and a flat object directory that breaches the recommended three thousand entries per directory well before a dependency tree is finished.

**So the ignore file is line one of the MVP**, and nothing else in this brief can be attempted before it exists.

## Drive Is The Word This Corpus Uses For The Incumbent

Raised at the strength it deserves, which is lower than a naming collision.

Three words in this corpus have been caught colliding in the last fortnight because each already carried a system meaning. **Drive does not.** It carries a positioning meaning instead: the messaging work of 17 April aims at professionals who have never used version control, names shared drives among the things they use today, and positions vaults as folders that remember everything, which is to say as the replacement for the shared drive.

So calling our own feature a shared drive adopts the word for the thing we position against. That is a tension rather than a defect, and the resolution used for the plugin and component question applies: **the external analogy is good and the internal term should be something else**, settled before it appears in documentation. This brief does not settle it, and uses the mechanism names, being the watcher, the queue and the topology.

One factual note on the publishing half. The project lead: **"we could even publish it on hub.so. hub. Skit. AI."** That host did not resolve from here today, which is recorded in the site access report written earlier and is an observation rather than a finding, since one request from a second vantage point settles it. The public version of the drive should not be planned against it until somebody confirms it is live.

## The MVP

Ordered by dependency rather than by interest, because the first item gates everything.

1. **The ignore file**, with the default patterns specified in March. Nothing below can start without it.
2. **A watcher with a reconciling scan**, where the scan runs at startup, on overflow, on restart and on a slow schedule, and is treated as a normal component rather than a recovery path.
3. **The May commit queue, unchanged**, with the window configurable and zero preserving today's behaviour, plus one metric the May brief did not need: rejected pushes per minute.
4. **One agent, one workspace vault, one session, end to end**, with the transcript captured into a second vault under a different key.
5. **Two agents, two clone branches, one named branch**, which exercises the compare-and-swap and the resolve verdict together and is the acceptance test for the concurrent claim.
6. **The public version**, once the host it would be published on is confirmed to exist.

The acceptance test, in the discipline settled on 16 August and reused on 19 August:

> Run one agent session for an hour in a watched directory. Afterwards, a second agent given only the vault key should be able to reconstruct what the first one did and why, from the vault alone. No file matching a default ignore pattern may appear in any commit, and the number of commits should be within an order of magnitude of the number of minutes rather than of the number of file events.

The last clause is the one that catches a watcher that is working and a queue that is not.

## What This Does Not Try To Be

- **Not a new batching design.** The queue is from 26 May and should be inherited with its trade-off intact.
- **Not a permission model.** Possession of a key is access, so minimal permission is delivered as three vaults.
- **Not a claim that a watcher is complete.** Events are lost on overflow, and the reconciling scan is a component rather than a fallback.
- **Not a redaction promise for the session record.** The transcript is the record, and filtering it destroys what is being preserved.
- **Not buildable yet.** The ignore file has been proposed since March and gates the first line.

## Honest Tensions

| Tension | Note |
|---------|------|
| Batching against the memory case | The window makes the drive practical and it collapses exactly the repeated edits to one file that a memory of the session would most want |
| A watcher as the source of truth | It is the only mechanism that sees a filesystem change, and it is documented to lose events, so the design needs a second mechanism that makes the first one optional |
| Topology instead of permissions | It has no bypass and it means the permission model is fixed at vault creation, when nobody yet knows how many agents there will be |
| Capturing the session record | It is the cheapest part to build and it is the part that carries every secret the session saw into a store nothing can scan |
| The ignore file as a gate | Naming it a precondition is honest and it means a feature the memo wants this week depends on an item that has not moved in five months |
| Continuous push under many agents | Compare-and-swap makes it safe and it makes one reference the bottleneck, so the drive gets slower as the collaboration it exists for gets busier |
