# One Vault Per Conversation: Vaults Replace The Thread Store And Not The Dedup Check, And They Buy Portability Rather Than Zero-Knowledge

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** Engineering, Architecture

**type** Architecture brief

*Sixth of 14 August. A companion to the two bridge documents. Written against the managed-gateway proposal rather than the current workflow. Contains one honesty correction that should be settled before the privacy story is written down. Offered to be built on and challenged.*

---

## What This Is

An assessment of where vaults improve the bridge and where they would make it worse, because the answer differs sharply by component: **the dedup check should stay exactly as proposed, since it is a tiny strongly-consistent conditional write on the hot path that must complete before any spend, which is what a key-value store is for, and routing it through a commit-based vault would add latency to the one operation whose entire value is being fast and certain; the conversation history is the opposite case and is the strongest fit in the whole design, because it is per-user, append-only, personal, and needs the last twenty turns rather than a query, which makes one vault per conversation the natural shape and turns three separate problems into properties of the storage rather than features to build, namely export, deletion and per-user blast radius; the derivation of a vault identifier from a phone number would leak, since numbers are enumerable and deterministic naming discloses existence, so the identifier must come from a keyed hash of a service secret and the number rather than the number itself; a capability split falls out for free, because the ingest function can be given a write-only channel into the user's vault while only the generation function holds the read key, which is the append-only pattern this corpus adopted four times and it means a compromised ingest path cannot read anybody's history; media should keep the direct-to-object-storage write that the managed gateway provides and be ingested into the vault afterwards if it is retained at all, rather than losing the single best feature of that platform to route bytes through compute; prompts and the rolling summary belong in a vault for the ordinary reason that they are versioned text somebody will want to change without a deploy; and the honesty correction is that none of this yields zero-knowledge, because a service that assembles a prompt reads the plaintext to do it, so what vaults buy here is encryption at rest, per-user blast radius, versioning, portability and a clean data-subject story, and claiming more would repeat a mistake the corpus already made once.** It is the sixth document of 14 August (cross-ref: the v0.33.56 vault-architecture brief, the v0.33.56 token-gateway brief, the v0.33.55 vaults-as-substrate brief, the v0.33.56 sgit per-path indexes brief, and the v0.33.58 hub assessment). New contributions: **the component-by-component split, one vault per conversation as the unit, the keyed-hash requirement for the identifier, the ingest and generate capability split, and the statement of what vaults do not buy here.**

## Where Vaults Fit, And Where They Do Not

The useful answer is not uniform, so this is the summary before the argument.

| Component | Recommendation | Why |
|---|---|---|
| Dedup on message id | **Keep the key-value store** | Hot path, needs strong consistency, must be certain before spend |
| Conversation history | **Vault per conversation** | Per-user, append-only, personal, portable, deletable |
| Thread summary | **Same vault** | Derived text, versioned, occasionally corrected by hand |
| Retained media | **Object storage first, vault after** | Do not lose the direct write; ingest only what is kept |
| Prompts and configuration | **Vault** | Versioned, diffable, changeable without a deploy |
| Delivery statuses | **Keep as metrics** | High volume, individually low value, no reason to store |

The rest of this brief argues the two that matter and states the one thing this does not buy.

## Leave The Dedup Check Alone

The proposal puts a conditional write on the message identifier ahead of everything else, returning immediately on a condition failure. That is right and should not be moved.

The operation has three properties that make it the wrong candidate for a vault. It is on the **hot path** of every inbound message. It requires **strong consistency**, because two concurrent deliveries of the same retry must not both proceed. And its whole value is being **certain and fast before any money is spent**.

A vault write is a commit: object writes, tree, commit, index update. That is the right shape for durable content and the wrong shape for a single-key existence test executed on every message.

Worth noting there is a simpler option than the proposal if the aim is fewer moving parts. **Object storage supplies conditional writes natively**, using a create-only precondition, which the corpus grounded on 4 August. A create-only put on a key derived from the message identifier gives the same guarantee without a second database, and it fails with a precondition error exactly where the proposal expects a conditional check failure. Whether that is simpler than the table already being provisioned is a judgement, but it is available and it removes a dependency.

## One Vault Per Conversation

This is the strongest fit in the design and it changes several things at once.

The thread has exactly the shape a vault is good at. It is **per-user**, so it partitions naturally. It is **append-only**, since turns are added and never edited. It is **read as a window** rather than queried, since the requirement is the last twenty turns and not an analytical query. And it is **personal data**, which is the case where encryption at rest earns its cost.

```
   VAULT: conv-<derived id>
     turns/2026-08-14T22-07-11Z-<wamid>      one object per turn
     turns/2026-08-14T22-07-19Z-<wamid>
     ...
     thread                                  last activity, summary, phone id
     media/<mediaId>                         retained assets, if any
```

Three things that are ordinarily separate features become properties of that arrangement.

**Export is the vault.** A data subject access request is answered by handing over a read key, or an archive. Not a query, an export job and a format decision, but the thing itself, complete and in order.

**Deletion is deleting the vault.** Erasure is one operation with no risk of a row surviving in an index, a replica or a backup table. The corpus made the same argument about the hub earlier today, where the inability to identify individual objects made the vault the unit of action; here that granularity is an advantage rather than a constraint.

**Blast radius is one conversation.** A compromised key exposes one person's messages rather than a table containing everybody's. That is a materially better position to be in and a materially better sentence to write in an incident report.

There is also a convergence worth recording. The transcription product's roadmap identified **customer vaults** as the destination for persistence on 6 August, and the bridge is that product's ingestion path. **One vault per conversation is the same mechanism arriving from the other end**, which means building it here is not a detour.

## Two Requirements That Make It Work

**The identifier must not be derived from the phone number.** Deterministic naming is what makes a vault reachable in one request, and the corpus recorded on 4 August that it discloses existence at the storage layer. Phone numbers are enumerable, so deriving a vault identifier directly from one would let anybody with a number test whether that person has used the service. The content stays encrypted and the fact of use does not.

The fix is standard: derive the identifier from a **keyed hash of a service secret and the number**, so it is deterministic for the service and unguessable for everybody else.

**And reads need the per-path index.** Loading twenty turns must not be a tree walk. The index feature briefed on 6 August gives a computable pointer per path, and the batch read endpoint returns many known objects in one round trip. Together those make a thread load one derivation plus one or two requests, which is the right cost for something on every inbound message.

That makes the index a dependency of this design rather than an optimisation, and it is worth saying so to whoever is sequencing that work.

## The Capability Split Falls Out For Free

A nice property that arrives without extra design, and it is the pattern this corpus has now adopted four times.

The vault messaging model lets a component be given a public key that permits **writing to a vault it cannot read**. Applied here:

| Function | Holds | Can |
|---|---|---|
| **Ingest** | Write key only | Append the user turn. **Cannot read any history** |
| **Generate** | Read and write | Load the window, call the model, append the reply |
| **Status** | Neither | Emits metrics only |

That is least authority applied to the two functions, and it matters because ingest is the component nearest the outside world. A compromise there yields the ability to add junk to one conversation, not to read anybody's messages.

It also matches the security posture the gateway proposal already argues for, where each function receives a narrowly scoped role. This extends the same discipline from the platform's own permissions into the data itself.

## Media: Keep The Direct Write

One thing not to give up. The managed gateway can fetch media from the upstream provider and write it **straight into object storage**, without the bytes passing through compute, and can return metadata only so oversized files can be rejected before paying to download them. That is the single best feature in that proposal and it removes a whole class of problems from the current workflow.

So the sequence should be: **write to a staging bucket, decide, then ingest into the vault only if the asset is being retained.** Transcription reads from staging, and a lifecycle rule expires it regardless of what happens next.

For most cases the asset is not worth keeping and the transcript is. Where audio is retained deliberately, putting it in the user's vault means it inherits the same deletion and export properties as the conversation, which is a cleaner story than a bucket prefix and a lifecycle rule that has to be reasoned about separately.

## Prompts And Summary

Both belong in a vault, for ordinary reasons.

The open decisions list asks whether prompts live in a parameter store or in the bundle, and notes that the answer determines whether tuning requires a deploy. A vault answers it well: versioned, diffable, editable by a person or an agent, and readable at runtime. It also means prompt changes carry history, which matters the first time somebody asks why replies changed character last Tuesday.

The rolling summary is derived text that will occasionally be wrong and occasionally be corrected by hand. Storing it alongside the turns keeps the correction in the same history as the material it summarises.

## What This Does Not Buy

The correction, and it should be settled before any privacy claim is written.

**This is not zero-knowledge, because the service reads the plaintext.** A function that loads twenty turns to build a prompt has decrypted twenty turns. Wherever the key comes from, the service holds it at that moment.

The corpus already made this mistake once and corrected it. The token gateway work of 6 August established that metering forces you into the request path, which moves a privacy claim **from architectural to operational**: not *we cannot see your content* but *we do not retain it*. The same applies here, and the same discipline follows.

So the honest list of what vaults buy in this design:

| Buys | Does not buy |
|---|---|
| Encryption at rest, with keys separate from the store | Inability of the service to read |
| Per-conversation blast radius | Protection against a compromised generation function |
| Versioned history by construction | Anything the model does not already see |
| Export and erasure as single operations | Freedom from a retention policy |
| Portability: the user can be given their own copy | A zero-knowledge marketing claim |

That last row is the one with real product value. **A user can be handed the read key to their own conversation history**, which is a genuinely unusual thing to offer and is defensible in a way the stronger claim is not.

## Statelessness

The brief was asked for something as serverless and stateless as possible, and it is worth being precise about which of those vaults help with.

**Stateless compute: yes.** Every function reads what it needs and holds nothing between invocations. The vault is the state and the functions are pure transformations over it, which is the same position the corpus reached on 2 August about agents collaborating through folders.

**Serverless operations: partly.** There is no database to provision, patch, scale or fail over, and object storage is the substrate. That is a real reduction in operational surface.

**But not fewer moving parts overall**, and the brief should not pretend otherwise. A vault client must be present in the function bundle, which affects cold start on the path where latency is visible to a person waiting for a reply. That is worth measuring early rather than discovering, and it is the main technical risk in this proposal.

## Sequencing

Fits alongside the migration plan in the companion document rather than replacing it.

1. **Keep the proposal's step zero and step one.** The live defects should be fixed regardless, and none of this changes that.
2. **Prompts in a vault first.** Lowest risk, immediate benefit, no hot path involvement, and it proves the client works inside a function.
3. **Thread history in a vault**, alongside the existing store rather than instead of it, with reads compared for latency before anything is switched.
4. **Then the capability split**, once the write and read paths are separate functions.
5. **Media into the vault last**, and only for assets actually being retained.
6. **Dedup never.** It stays where it is.

Steps two and three are reversible. That matters, because the honest position on cold start is that it is unknown until measured.

## What This Does Not Try To Be

- **Not a replacement for the dedup store.** That operation is correctly placed already.
- **Not a reason to route media through compute.** Keep the direct write to object storage.
- **Not zero-knowledge.** The generation function reads plaintext, and the claim must reflect that.
- **Not fewer components.** Fewer managed services, one more client library, and a cold start to measure.
- **Not a detour.** The same customer vault the transcription product already needs.

## Honest Tensions

| Tension | Note |
|---------|------|
| Vault on the read path | It removes a database and adds a client to a latency-sensitive function, and only measurement settles it |
| One vault per conversation | Export, deletion and blast radius all improve, and the number of vaults grows with users, which is untested at that shape |
| Encryption at rest without zero-knowledge | It is a real improvement and it is easy to overstate, and overstating it is worse than not having it |
| Keyed identifiers | They prevent enumeration and mean the service secret becomes the thing that maps users to storage |
| Prompts in a vault | Changing them without a deploy is the point, and it means a prompt change is not gated by whatever gates a deploy |
| The per-path index dependency | This design assumes a feature that is briefed and not yet built |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the cold start cost of the vault client? | The main technical risk, and it should be measured before step three |
| Where do vault keys live? | A key derived from a service secret means the service can read everything, which is the honest position anyway |
| Does the per-path index ship before this? | It is a dependency rather than an optimisation |
| Is retained audio kept at all? | The open decision in the companion document, and vaults change the deletion story rather than the answer |
| Does the user get their own read key? | The most valuable product property available here, and it needs a delivery mechanism |
| One vault per conversation or per user? | The same today, and different if the same person appears on a second number |
| What happens to a vault after retention expires? | Deleting it is clean and loses the audit trail, which needs a stated position |
