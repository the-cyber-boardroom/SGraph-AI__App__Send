# Site Changes: Build The Catalogue As A Submission Queue, Because The Bottleneck Is One Person Pasting Read Keys

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** The agent working on the sgit.ai site

**type** Dev brief

## What This Is

The changes needed to turn a site that demonstrates vaults into one that **indexes** them, and one design decision that determines whether it works: **the previous pack has largely landed, since the concatenated single file exists, the index now answers the common questions without a second request, the demos section carries three live examples with published read keys, the serialised diff has its own page with the disclosure grounding, and there are six maps starting from where git wins, so this brief is not a re-run but the layer above them; the driver is inventory rather than demonstration, because vaults are accumulating faster than they can be tracked and each currently lives in its own environment, so what is missing is a catalogue rather than more demonstrations; the design decision that decides success is that the bottleneck is one person with a backlog of vaults and limited time, which means the catalogue must be built as a submission queue whose per-entry cost is a read key and one line of description, with everything else derived by the agent opening the vault, since any design requiring a written page per vault will stall at the third entry; that derivation is the interesting part, because an agent holding a read key can open the vault and produce the file listing, the structure, the size, the commit count and a rendered preview without being told any of it, so the human supplies what only a human knows, meaning what it is for and whether it is production or a sketch; the catalogue needs four fields that cannot be derived and must be captured at submission, being the shape, the evidence status, whether it is a copy or a live reference, and the write-key status, the last of which matters because a vault whose write key is lost can never be corrected; and topic sections should be assembled from catalogue entries rather than authored separately, so that adding a vault to the catalogue is what makes it appear in a topic page, which keeps one canonical location per fact.** It is Part A of the site pack (cross-ref: the previous site briefing pack, the v0.33.58 topic sections brief, the v0.33.58 serialised pull request brief, and the v0.33.58 agent access report). New contributions: **the submission-queue framing, the derived-versus-supplied split, the four fields that cannot be derived, topic sections assembled from entries, and the placeholder structure.**

## The Bottleneck Is One Person, So Design For That

The honest constraint. There is a backlog of existing vaults worth publishing, spanning galleries, a penetration test report, a data protection analysis, a standards browser, mail and messaging systems, a healthcare collaboration case and semantic graph work. New ones appear weekly.

**A design that requires a written page per vault will stall at the third entry.** Not because anybody lacks discipline, but because the marginal cost of the fourth page exceeds the value of publishing it, and the backlog then sits where it currently sits.

So the catalogue should be built as a **submission queue** with the smallest possible per-entry cost:

```
   WHAT A HUMAN SUPPLIES              WHAT THE AGENT DERIVES
   read key                           file listing and structure
   one line: what it is for           object count, size, commit count
   shape tag                          last-updated date
   evidence status                    a rendered preview or screenshot
   copy or reference                  whether an app is present
   write-key status                   whether it renders in the browser
```

The left column is what only a person knows. The right column is everything an agent can establish by opening the vault with the key it was just given.

**That asymmetry is the design.** Getting a vault into the catalogue should take under a minute.

## The Four Fields That Cannot Be Derived

Three of the six on the left are obvious. These four need capturing explicitly because getting them later is much harder than getting them now.

**Shape**, not domain. A visitor is looking for a workflow resembling theirs, so gallery, report, structured analysis, multi-agent collaboration, record-keeping and application are the useful tags. Healthcare is an instance of a shape, not a shape.

**Evidence status**, which the use-case pages already do. Production, demonstration, or sketch. A reader who cannot tell will guess wrong in one direction or the other, and the site's existing honesty about this is one of its better properties.

**Copy or reference.** An archive diverges the moment it is downloaded; a sub-vault link stays live and changes underneath the reader. Both are legitimate and they serve opposite needs, and offering both without saying which is which will mislead.

**Write-key status**, and this is the one most likely to be skipped. A vault published with a read key whose write key is lost is **frozen**: readable forever, never updatable, never correctable, never revocable. The demo of the strategy maps already records exactly this class of problem, where the original vault could not publish its key because its own write credential was inside its content, and a republish was needed.

So the catalogue should record `escrowed` or `lost` per entry, and a frozen entry should say so publicly, because a reader deserves to know it will never be corrected.

## The Placeholder Structure

What to build so that a read key can be dropped in without ceremony.

**A queue file in the vault**, not a form. Something the project lead can append to from any session, in the shape of one entry per vault:

```
   pending/
     <slug>.md          read key, one line, four fields, nothing else
```

**A catalogue page generated from processed entries**, sorted by shape, with the derived material filled in.

**And a visible to-do list**, because the memo asks for one. Two lists rather than one:

| List | Contents | Who acts |
|---|---|---|
| **Awaiting a read key** | Vaults named in memos but not yet supplied | The project lead |
| **Awaiting processing** | Read keys supplied, not yet opened and catalogued | The agent |

Seeding the first list from the material already in the briefs is worth doing now, because a named gap gets filled and an unnamed one does not. The known candidates are the galleries, the penetration test report, the data protection graph analysis, the standards browsing view, the mail and messaging systems, the healthcare collaboration case, and the semantic graph vaults.

**Publish both lists.** A visible backlog is an honest signal about what the site is, and it is consistent with the existing willingness to publish limitations and failures.

## Topic Sections Are Assembled, Not Authored

The memo wants topic and industry sections. The mistake to avoid is writing them as separate pages that then have to be kept in agreement with the catalogue.

**A topic section should be a view over catalogue entries plus a small amount of topic-specific prose.** Adding a vault to the catalogue with a healthcare tag is what makes it appear on the healthcare page. Nothing is written twice, nothing drifts.

The topic-specific part is what the catalogue cannot supply:

- The problem in that domain, stated plainly
- What encryption does and does not change for it, with the existing discipline of making no compliance claims
- Deployment guidance where it exists, since one project already needs vaults deployed into a new cloud account by somebody else
- Any published security review or assessment

That gives a healthcare page assembled from a few paragraphs and every catalogued vault tagged healthcare, which stays correct without maintenance.

## Where The Catalogue Lives

**In a vault**, which makes the site's own claim recursive in a way worth doing rather than avoiding: a vault whose contents are an index of vaults, published with a read key, listed in itself.

Two practical reasons beyond the pleasing symmetry. It can be updated without a site deploy, which matters if entries arrive weekly. And it becomes the first instance of the machine-readable catalogue that a hub would need, so the schema is not wasted work.

## One Thing To Fix While You Are Here

The discoverability finding from the previous pack has not obviously moved, and it now blocks more than it did.

The site still needs to be reachable by a search engine. The likely cause remains that a page assembled client-side from a vault is what a crawler cannot see, and `/llms-full.txt` helps an agent that already knows the domain while doing nothing for one that does not.

**This matters more with a catalogue than without one**, because the point of the catalogue is that somebody, or some agent, can find the vault they need without asking a person. A catalogue nobody can find does not remove the cost it exists to remove.

Worth checking what a crawler actually receives for one page, and reporting the answer even if the fix is not immediate.

## Suggested Order

1. **The queue and the two to-do lists**, seeded from the briefs. Cheapest, and it unblocks the person supplying keys.
2. **The catalogue schema and the derivation**, proved on one existing demo vault whose key is already published.
3. **The catalogue page**, sorted by shape.
4. **One topic section assembled from it**, healthcare first, since there is a live requirement behind it.
5. **The crawler check**, in parallel, since it is diagnostic rather than construction.

## What This Does Not Try To Be

- **Not more demos.** The demonstration layer works; this is the index above it.
- **Not a page per vault.** A read key and one line, with the rest derived.
- **Not authored topic pages.** Views over catalogue entries plus a little prose.
- **Not silent about gaps.** Two published to-do lists, because a named gap gets filled.
- **Not a fresh schema.** The catalogue is the first instance of what a hub would need.
