## Do This First: Audit What Already Exists

The proposal reuses a substantial amount of existing code and behaviour from the vault web application. **Nobody writing the architecture currently knows exactly how much**, and a design written without that knowledge will be wrong in one of two expensive directions: rebuilding something that exists, or assuming something that does not.

So the first deliverable is not architecture. It is an **inventory**, and it should be short and factual.

For each capability below, record: present, partial, or absent; where it lives; and whether it is reachable from a page on the site.

| Capability | Why the forge needs it |
|---|---|
| Open a vault in the browser from a read key | The entry point for everything |
| Open from a full vault key | The private-vault case, which is what makes it a forge rather than a gallery |
| List a tree, navigate directories | Browsing |
| Fetch and decrypt a single object by path | Viewing a file |
| Render markdown, highlight code | The reading experience |
| Walk commit history | History views |
| Fetch two versions and compare | Diff |
| Sparse or partial fetch | The performance answer; the docs mention sparse clones |
| Local caching between sessions | Whether a second visit re-fetches everything |
| Sub-vault traversal and link files | Permissions by topology |
| The app runtime and its permission model | Whether forge views can be vault apps |
| Write and push from the browser | Whether the forge is read-only at first |
| Merge and conflict handling client-side | Change proposals |

**Report the gaps as plainly as the presences.** A capability that is partial is more dangerous to a plan than one that is absent, because it will be assumed complete.

This audit is itself worth publishing. It is the sort of document the site's cross-team brief section already exists for, and it will be useful to the vault web team independently of the forge.

## The Model, Which Is Settled

State this in the pack rather than re-deriving it, because it is the decision everything else follows from.

**A forge whose application layer runs in the browser.** The client holds the vault key or the read key. The server is object storage plus the existing interface: it authenticates, stores and serves opaque objects, and reads nothing. Every feature that a conventional forge implements server-side because the server can read plaintext is implemented client-side here because the client can decrypt.

Two consequences the pack should carry near the front.

**The reference class is the self-hostable forge**, not the largest code host. Those users already accept running the server; the claim is that the server can be storage rather than an application, with no database to run, back up or upgrade.

**And features follow the key.** Anything you hold a key to gets the full experience, public or private. Only **discovery across vaults you have no key to** requires a reading index, which is the one place a public tier is genuinely different.

## What The Pack Must Contain

Six parts. The order matters because each rests on the one before.

### 1. The capability audit

As above. Facts, not design.

### 2. Architecture

What runs where, drawn as a diagram. Minimum: the browser holding the key, the object store, the existing interface, and the boundary across which only ciphertext passes. It should be obvious from the diagram alone that the server cannot read.

Include the data path for a single file view, end to end, because that path is the whole system in miniature: derive, fetch, decrypt, render.

### 3. User flows

Written as flows rather than screens, and these five cover the product:

- **Arriving at a public vault** with the key already in the link
- **Opening a private vault**, which is where the key handling question lives
- **Browsing and reading**, including a diff
- **Proposing a change** without holding write access, which is the serialised diff already documented
- **Reviewing and merging** a proposed change

The second is the one that needs the most care and the pack should say so. **Pasting a vault key into a web page is the obvious wrong answer** and the pack should reach a considered position rather than defaulting.

### 4. Interface mock-ups

Enough to make the flows concrete. Forge conventions are worth following closely, because the argument is that this is a familiar thing on unfamiliar foundations, and every gratuitous difference costs a reader attention that should go to the substance.

**One screen matters more than the rest**: the one where a visitor can see that the server returned only ciphertext while they were reading a file. That is the demonstration, and it should be designed rather than added later as a panel.

### 5. Development guidance

What to build first, what is reused from the audit, and what is genuinely new. **Read-only over one vault, then the same view over a private vault**, is the recommended order, because the second is what makes it a forge rather than a public gallery.

### 6. Hosting

Where the objects live, how the site is served, and how a person would run their own. The self-hosting story is not an afterthought here: the whole claim is that the server is simple enough that anybody could run one.

## Four Absences To State Plainly

The pack is more credible for naming these, exactly as the limitations page makes the rest of the site credible.

| Absent | Why |
|---|---|
| **Search across vaults you hold no key to** | Requires a reading index; possible only for published-key vaults |
| **Continuous integration** | A build runner must read the content to build it |
| **Server-enforced granular permissions** | Possession of a key is access; there is nothing for a server to withhold |
| **Content-triggered notifications and webhooks** | The server cannot see what changed |

On the second, the pack should carry the interesting answer rather than the resigned one: a build scoped to a **sub-vault containing only what the build needs**, holding only that key. That is least authority applied to integration and it follows directly from the permissions model.

## Permissions Need Worked Examples

The part most likely to be misunderstood, because it inverts an assumption every forge user holds.

In a forge, permissions are a policy the server enforces. Here, **possession of a key is access**, so granularity comes from **shape**: separate vaults, sub-vaults with their own keys, read keys distinct from write keys.

The pack should carry two or three worked topologies, because nobody will derive them unaided. Something like: a public documentation vault, a private working vault, and a secrets sub-vault with a separate key, showing who holds what and what each person can therefore do.

And it must state the two hard limits:

**Revocation is not retroactive.** Anybody who held a read key and fetched the objects keeps a working copy. Rotation protects future commits and returns nothing already taken.

**Granularity costs structure.** Five permission levels means five vaults and five keys, decided in advance. A forge lets you add a rule; this requires the shape to have been designed.

## One Correction To Carry In

A prior brief listed blame among the features that work client-side. **The site's own quick answers list blame among the operations sgit does not have**, alongside bisect, rebase, cherry-pick, hooks, submodules and tags.

Both can be true, and the pack should be precise about which. A forge could compute blame client-side by walking history, but that would be **adding a capability the tool does not have**, not surfacing one it does.

So the feature list in the pack should distinguish three categories, and the distinction is worth applying to every item rather than only this one:

| Category | Example |
|---|---|
| **Surfacing** what sgit already does | Diff, history, branch, merge |
| **Adding** something computed client-side | Blame, within-vault search |
| **Absent**, with a reason | The four above |

That table is more useful to a reader than a flat feature list and it is more honest.

## Publish It Before It Is Built

The pack should go on the site in the existing cross-team brief form rather than being held privately, and the reason is more than transparency.

The site already documents its own working method: agents collaborating through vaults, briefs filed between teams, case studies of what went wrong. **A design published before the thing exists is that method demonstrated at the largest scale so far**, and it invites the criticism that would otherwise arrive after the build.

It also fits what the site has already shown it does well. The pages that carry the most credibility are the ones that publish a failure or a limitation, and a design with its absences stated is the same instinct applied forward rather than backward.

## What This Specification Does Not Do

- **Not the design.** It says what the pack must contain and what must be established first.
- **Not a relitigation of the model.** The browser holds the key; the server stores ciphertext.
- **Not a feature list.** Surfacing, adding and absent are three different things.
- **Not private.** The pack belongs on the site, before the build.
- **Not startable today.** The capability audit comes first.
