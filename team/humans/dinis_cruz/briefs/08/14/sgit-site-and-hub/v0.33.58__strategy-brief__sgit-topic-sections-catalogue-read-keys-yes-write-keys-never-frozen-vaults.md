# Topic Sections As The Index For Vault Sprawl: Publish Read Keys, Never Write Keys, And A Vault Whose Write Key Is Lost Is Frozen Rather Than Broken

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** The agent working on the sgit.ai site, Product

**type** Strategy brief

*Eighth of 14 August, and an addition to the site briefing pack. Contains one hard rule that should be settled before any catalogue exists, and one property of the lost-key case that is worse than it sounds. Diagram tooling is verified and cited.*

## What This Is

Topic and industry sections that do three jobs at once, and a catalogue underneath them, with one rule that must not be got wrong: **the honest driver here is inventory rather than marketing, since the stated problem is that vaults accumulate faster than they can be managed and each one stays in its own environment, so the site is being proposed as the index for that sprawl and the demonstration value is a by-product, which is the right way round because it means the pages are maintained by being used; a topic section doing triple duty as documentation, live demonstration and agent guidance is also the sustainability answer already reached, because a page an agent is pointed at weekly fails loudly the first time it is wrong while a marketing page rots invisibly; the mapping proposal checks out, since the diagram language gained a Wardley type in version 11.14.0 with the renderer described as production-stable at 11.15.0 and native rendering in markdown on the code platform, with one syntax trap worth publishing because coordinates are given as visibility then evolution, which is the reverse of the usual convention; using such a map to explain the difference from git is a good idea for a reason beyond illustration, because a map is a falsifiable claim about where components sit rather than a picture, which is the same property that makes the boundary framing credible; the hard rule concerns the proposed central list, because publishing read keys for public vaults is fine and is what publication already means, whereas a central list of vault keys would be a single artefact whose compromise hands over write access to everything, and this site already documents the time a key exposure happened to it; and the lost-write-key case needs stating precisely, because a vault that is readable and unwritable is not damaged but frozen, permanently readable by anybody holding the published key, never updatable, never revocable and never correctable, so the recovery is a migration that strands the original rather than repairing it, which makes escrowing the write key a precondition of publishing rather than good practice.** It is the eighth document of 14 August (cross-ref: the site briefing pack leading brief, the v0.33.58 serialised pull request brief, the v0.33.58 component registry brief, the v0.33.58 hub assessment, and the v0.33.58 agent access report). New contributions: **inventory named as the real driver, triple duty as the maintenance mechanism, the mapping tooling verified with its syntax trap, the read-key and write-key separation as a hard rule, and the frozen-vault property with escrow as a precondition.**

## The Driver Is Inventory, Not Marketing

Worth putting first because it should shape the design, and because it is the more honest reason. The project lead: **"the problem right now is it doesn't scale, because my vaults tend to stay in their own environment. So in a way, it's the curse of now I'm creating so many vaults that I don't have a good way to manage it."**

That is not a content strategy problem dressed up. It is an **inventory problem**, and the site is being proposed as the place that solves it.

Which is the right way round, and it explains why this will be maintained when a marketing section would not. The project lead: **"that means that I'll keep using this all the time, and every time I come up with a new use case or workflow, which basically happens every week, almost sometimes every day, I have a good place to put it."**

**A page you use is a page that cannot rot invisibly.** The briefing pack made that argument for the documentation section; this extends it, and it is the strongest reason to build topic sections rather than a flat gallery.

## Triple Duty

The memo's own specification, and each of the three has a different reader. The project lead: **"serve as documentation and explanation of what we can do with sgit and our vaults, provide a live demo of it, and document for other agents when they want to implement similar things."**

| Job | Reader | Artefact |
|---|---|---|
| Documentation | A person evaluating | Prose explaining the problem and the approach |
| Live demonstration | A person who wants to see it | An embedded read-only vault, browsable in the page |
| Agent guidance | An agent building something similar | A recipe and a pasteable reference |

The third is the one most sites omit and the one that removes the recurring cost identified earlier: currently a new build starts with explaining an existing vault to an agent so it can extract a pattern.

The concrete instance the memo gives is the sharpest illustration of the gap. The project lead: **"if I wanted to create a vault and then put on a website that has Wardley maps as an example, I don't have a good place to point to another vault that already has figured out how to use the latest Mermaid, how to document it, how to explain it."**

## A Topic Section, Worked

The healthcare example in the memo is unusually complete and worth using as the template, because it contains the four things a topic section needs.

| Element | The healthcare instance |
|---|---|
| **The problem** | The challenges of handling this class of data |
| **The security properties** | How vaults work, what encryption changes and what it does not, published security reviews and assessments |
| **The deployment path** | How to deploy vaults into a new cloud account, so somebody else can do it |
| **The demonstrations** | Existing vaults, embedded and browsable |

The third is the one that turns a section from an argument into something usable, and the memo notes it is already a live requirement on a real project rather than a hypothetical.

One caution carried from earlier today: the existing use-case page for this domain is described as stating what client-side encryption does and does not change **without compliance claims**. That discipline should extend to the topic section. Publishing security reviews and deployment guidance is useful; implying regulatory readiness that has not been established is the easiest way to create an obligation nobody has met.

## The Mapping Proposal Checks Out

Verified, because a section would be built on it.

The diagram language added a Wardley type in version 11.14.0, and reporting from June describes the renderer as stable enough for production as of 11.15.0, with native rendering in markdown files on the code platform. The syntax places components with a value-chain position and an evolution stage, and it was implemented to stay compatible with the existing community standard.

**One trap worth publishing prominently**, because it will catch everybody once: coordinates are given as **visibility first, then evolution**, which is the reverse of the usual convention and was a deliberate choice to match the community tool. A map with its axes transposed renders happily and says something entirely different.

Two smaller notes: the hand-drawn look is not supported for this diagram type because it uses a separate renderer, and the type is still marked beta.

**Why this is more than illustration.** A Wardley map is a **claim**, not a picture: it asserts where each component sits on the evolution axis and is therefore arguable. Using one to explain the difference between sgit and git means publishing a falsifiable position about which parts of the stack are commodity and which are not.

That is the same property that makes the boundary framing work. A page that says plainly where the incumbent wins is credible because it can be disagreed with, and a map that places components is credible for the same reason. It also invites argument, which for a project trying to establish a category is a feature rather than a cost.

## The Hard Rule: Read Keys Yes, Write Keys Never

The memo proposes a central list and the wording needs splitting before anybody builds it. The project lead: **"we need to have also a centralised place where we basically list every single vault key and every single vault that exists on sgit.ai."**

Those are two different artefacts with opposite risk profiles.

| | A catalogue of read keys | A list of vault keys |
|---|---|---|
| What it grants | Read access to already-public content | **Write access to everything** |
| What publication already implies | It is published; the key is in the page | Nothing; these were never meant to be shared |
| Compromise | No loss, since the content is public | **Total: every vault altered or destroyed** |
| Belongs on the site | Yes | **Never** |

**A public vault's read key is published by definition**, so cataloguing read keys adds convenience and no exposure. That catalogue is a good idea and should exist.

**A central list of vault keys is a single artefact whose compromise is unbounded.** It would be the highest-value target in the estate, it would be stored on the most exposed surface, and it would undo the property that a compromise of one vault is a compromise of one vault.

This site already carries the runbook for a leaked vault key, including a worked case study of the time it happened here. **That page is the argument against this list**, written by the same team, from experience.

Where write keys should live: a secret manager, or an administrative vault that is not published and is not reachable from the site. The corpus reached the same conclusion on a different problem this morning, where a registry was necessary and had to be deliberate, guarded, and never on the request path.

The catalogue should record **the existence and status** of a write key without carrying it: known and escrowed, or lost. Which the next section explains is not a bookkeeping detail.

## A Vault Whose Write Key Is Lost Is Frozen

The memo raises the case and it deserves stating precisely, because the intuitive reading is wrong. The project lead: **"if I have published something with the read key but I lost the write key, the vault key, we should also map out how to convert that and publish that into a new server."**

The intuitive reading is that the vault is damaged and can be recovered. It is not damaged. **It is frozen**, and the properties are unusual:

```
   READ KEY, NO VAULT KEY

   readable       yes, by anybody holding the published key, forever
   updatable      no
   correctable    no
   revocable      no
   deletable      the objects can be removed from a server you control;
                  the key you published can never be withdrawn
```

Three consequences follow that are easy to miss.

**The recovery is a migration, not a repair.** Read everything out, create a new vault, write it in, republish, and update every reference pointing at the old one. The original does not become fixed; it becomes an orphan that still works.

**Nothing published can be corrected.** If a frozen sample vault turns out to contain something it should not, there is no edit available. The only remedy is to remove the objects from any server under your control and accept that anyone who already fetched them retains a working copy.

**And the published read key cannot be withdrawn.** That is true of any published key, and it becomes permanent here because rotation requires the write key.

So the rule that follows is a precondition rather than a practice: **escrow the write key before publishing, not after.** A vault published without its write key secured is a permanent, uncorrectable artefact, and that is a decision that should be made deliberately rather than discovered a year later.

It also connects to something recorded this morning. The hub assessment concluded that for a public host the unit of moderation is the vault, because an individual object cannot be identified. A frozen vault is the same problem with the granularity reduced further: not even the vault can be acted on, only the copies you happen to hold.

## Moving Between Servers

The memo flags this as newly real. The project lead: **"we need to also include the ideas of how to move data between servers, because that's quite powerful. But I think we even have a memo on that. But now it starts to be quite real."**

It is real, and it matters more than portability convenience for two reasons already in the corpus.

**It is the answer to the counterparty question.** The hub assessment noted that a durability strategy resting on one third party is not a durability strategy, and recommended that mirroring be indifferent to its destination from the first version. Server portability is the customer-facing version of the same property: the honest answer to what happens if you disappear is a documented procedure rather than an assurance.

**And it is a sovereignty control.** The maturity model built in July scores portability and survivability rather than treating them as binary. A documented, tested server migration is a scored outcome, and publishing the procedure is stronger than claiming the property.

Worth noting the frozen-vault case interacts here: a vault can only be moved by somebody holding the write key, so the migration guidance and the escrow rule belong on the same page.

## What To Build First

1. **The read-key catalogue.** Every public vault, its shape, its evidence status, and its write-key status. This is the inventory the memo actually wants and it is useful from the first entry.
2. **One topic section, fully worked.** Healthcare, because the memo has the most material and a live requirement behind it.
3. **The mapping component.** It is the concrete instance of the gap, it is small, and it unblocks the maps everywhere else.
4. **A map explaining the boundary**, which serves the reframe of the why page at the same time.
5. **The migration procedure**, published alongside the escrow rule.

Note that one and two are ordered that way deliberately. **The catalogue is the thing that makes the sprawl manageable**, and it is worth having before the number of sections grows.

## What This Does Not Try To Be

- **Not a gallery.** An inventory that happens to demonstrate the product.
- **Not a list of vault keys.** Read keys catalogued, write keys never on the site.
- **Not compliance claims.** Security reviews and deployment guidance, with the existing discipline preserved.
- **Not a repair path for lost keys.** Migration that strands the original, with escrow as the actual answer.
- **Not decoration.** A map is a falsifiable claim about where components sit.

## Honest Tensions

| Tension | Note |
|---------|------|
| The site as inventory | It guarantees maintenance and means the public site is shaped by an internal need |
| Publishing security reviews | It is unusually transparent and it publishes your own weaknesses to an audience that includes people looking for them |
| Read-key catalogue | Convenient and correct, and it makes every listed vault permanently public in one place rather than scattered |
| Escrow before publishing | It is the right precondition and it adds a step to a process whose appeal is that it is quick |
| Maps as claims | Falsifiability is the point and it invites public disagreement about your own positioning |
| Topic sections | Each one is a maintenance commitment, and a stale industry page is worse than an absent one |

## Open Questions

| Question | Notes |
|----------|-------|
| Where does the catalogue itself live? | A vault is the obvious answer, and it is then a vault listing vaults, including itself |
| What does a catalogue entry contain? | Shape, evidence status, copy or reference, write-key status, last verified |
| Where are write keys escrowed? | A secret manager or an unpublished administrative vault, decided before the first publication |
| How is a frozen vault marked? | Publicly, since a reader should know it will never be corrected |
| Which topic sections, and in what order? | Where a live requirement exists, rather than where the market looks largest |
| Is the migration procedure tested? | Publishing an untested procedure is worse than publishing none |
