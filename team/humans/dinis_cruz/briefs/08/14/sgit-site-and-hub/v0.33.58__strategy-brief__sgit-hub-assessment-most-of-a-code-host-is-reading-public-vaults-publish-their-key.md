# Yes To The Mechanism, Careful With The Analogy: Most Of What A Code Host Does Requires Reading, And A Public Vault Publishes Its Read Key Anyway

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** Product, Engineering, Strategy

**type** Strategy brief

*Fifth of 14 August. An assessment of the hub proposal. Platform limits, acceptable use terms and hosting obligations are grounded and cited, and one of the findings is more favourable than expected. Offered to be built on and challenged.*

---

## What This Is

An assessment of whether a public vault host is close, and the answer is that the mechanism is closer than the product: **almost every component already exists, since the protocol supports the full set of version control operations, the read key and read-write key are already separated, addressing is deterministic, vault-in-vault and vault-as-link are built, browsing from a read key works, static hosting from a code platform is already documented, and the site itself is served from a vault, so a host is an assembly rather than a build; what is not close is the analogy, because a code host is mostly a set of reading features, and search, code navigation, rendered readmes, language detection, dependency graphs, blame and hosted diffs all require the server to read plaintext, which a zero-knowledge host cannot do by definition; the resolution is elegant and follows from something already true, namely that a public vault publishes its read key, so the host can read public vaults legitimately because the owner chose to publish rather than because the encryption failed, which yields a two-tier design in which public vaults get indexing, search and rendering while private vaults get storage, sync and nothing server-side, and that is a stronger privacy position than the incumbent, which can read private repositories; the backup plan needs three adjustments, because a flat object directory breaches the recommended three thousand entries per directory and should be sharded by name prefix as the incumbent does for its own loose objects, because recommended push and read rates make the mirror asynchronous rather than the live path, and because the platform reserves the right to delete repositories placing undue strain on its infrastructure after notice, which makes a hub-scale mirror a counterparty risk on the disaster recovery strategy rather than a free one; the moderation question is more favourable than expected, since hosting providers are not liable absent actual knowledge and there is no proactive obligation to seek out illegality, so being unable to read is not disqualifying, though the unit of action becomes the vault rather than the file because an offending object inside a vault cannot be identified; and the thing the word close hides is that operating a public host changes what the organisation is, since there is no password reset by design and at hub scale that becomes a support and reputation problem it is not today.** It is the fifth document of 14 August (cross-ref: the v0.33.58 component registry brief, the v0.33.58 serialised pull request brief, the v0.33.58 agent access report, the v0.33.56 git-and-sgit brief, and the v0.33.51 OSMM brief). New contributions: **the reading-features diagnosis, the two-tier design derived from published read keys, object sharding as the answer to directory width, the acceptable use clause identified as a counterparty risk on disaster recovery, the vault as the unit of moderation, and the operational commitments named.**

## The Short Answer

**On mechanism, yes, and closer than the memo claims.** On the analogy, no, and the gap is specific rather than a matter of effort.

The inventory is worth stating because it makes the first half of that concrete:

| Needed for a host | Status |
|---|---|
| Version control operations | Present: commit, push, pull, clone, branch, diff, merge |
| Public read without write | Present: the read key derives from the vault key |
| Stable addressing | Present: deterministic derivation, no directory listing required |
| Efficient fetch | Present: batch read returns many objects in one response |
| Composition across vaults | Present: vault-in-vault and vault-as-link |
| Browser rendering | Present: vault apps, and the site is served this way |
| Static hosting from third-party infrastructure | Present and documented |
| Self-hosting | Present and documented |
| Multi-party workflow without credentials | Present: the serialised diff pattern |

That is most of a host. **What is missing is not storage or protocol. It is everything a code host does that is not storage.**

## The Diagnosis: A Code Host Is Mostly Reading

This is the observation that shapes the whole design.

Consider what the incumbent actually provides beyond a place to push objects: full-text and code search, language detection, syntax highlighting, symbol navigation, rendered documentation, dependency and vulnerability analysis, hosted diffs and review interfaces, blame, and automation triggered by content.

**Every one of those requires the server to read plaintext.** They are not features that happen to be server-side; they are features that exist because the server can read.

```
   WHAT A CODE HOST DOES              CAN A ZERO-KNOWLEDGE HOST DO IT?
   store and serve objects            yes
   authenticate and authorise         yes
   record who pushed what and when    yes
   ---------------------------------------------------------------
   search across content              no
   render documentation               no
   detect language, highlight         no
   analyse dependencies               no
   show a diff in the interface       no
   scan for secrets or vulnerabilities no
```

So a host built strictly on the zero-knowledge property is a **storage, addressing and identity layer**, and calling it an equivalent of the incumbent sets an expectation that the architecture forbids. The corpus made the same point about a metering gateway on 6 August: being unable to read is the property being sold, and its costs should be stated rather than discovered.

## The Resolution: A Public Vault Already Publishes Its Read Key

Here is the part that makes the proposal work, and it follows from something already true rather than requiring a compromise.

**If a vault is public, its read key is published.** That is how the sample vaults discussed earlier today are meant to work: the read key goes in the page, and anybody can browse. Which means the host can read those vaults too, not because the encryption was weakened but because **the owner chose to make them readable.**

That yields a two-tier design where each tier is coherent:

| | Public vaults | Private vaults |
|---|---|---|
| Read key | Published | Held by the owner |
| Host can read | **Yes, by the owner's choice** | No |
| Search and discovery | Yes | No |
| Rendered previews and documentation | Yes | No |
| Storage, sync, versioning | Yes | Yes |
| Access control and audit | Yes | Yes |

Two things follow that are worth saying out loud.

**The public tier can genuinely resemble a code host**, because for that tier the reading constraint does not apply. Search, previews and discovery are all available.

**And the private tier is a stronger position than the incumbent's**, because the incumbent can read private repositories and this cannot. That is a real differentiator and it is the honest one: not that public hosting is more private, but that **private means private in a sense the incumbent cannot offer.**

The memo's own framing, a public host of vaults, is therefore exactly right, and the caution is only against implying that private vaults will get public-tier features.

## The Backup Plan Needs Three Adjustments

The proposal to mirror every vault into a repository on the incumbent platform is sound in principle and needs three specific changes.

**Shard the objects.** The platform recommends no more than **three thousand entries in a single directory**, noting that wide directories significantly increase maintenance cost and degrade basic operations. A vault's object store is a flat namespace of derived filenames and will breach that quickly. The fix is the one the incumbent's own tooling uses for its loose objects: **shard by name prefix**, so objects live under two-character directories rather than one flat folder. That keeps every directory small at any vault size and requires only a path convention.

Note this is a different answer from the one for sample distribution, where archives were right. Archives suit **distribution**, because they are one entry and a single download. Sharded loose objects suit **mirroring**, because you can push a delta to them and cannot push a delta into a zip. The two use cases want opposite formats, which is worth stating before somebody standardises on one.

**Make the mirror asynchronous.** Recommended limits are around **six pushes per minute and fifteen read operations per second per repository**, with automated processes named as a cause of degraded performance. A live path that writes to the mirror on every commit will hit those. So the mirror is a scheduled follower, never the write path, which is the same rule the corpus set on 6 August: the normaliser is the only writer, and nothing reads from the mirror while a user waits.

**And treat it as a counterparty risk, not free storage.** The platform's acceptable use terms reserve the right, after notice, to **delete repositories determined to be placing undue strain on its infrastructure**, and separately steer bulk binary content toward object storage rather than repositories. A hub mirroring every hosted vault is precisely the shape that attracts that attention, and repositories above about five gigabytes already draw contact.

That matters because of what the mirror is for. **A disaster recovery strategy that depends on a third party's tolerance for an unusual usage pattern is not a disaster recovery strategy.** The mitigation is straightforward and should be designed in from the start: make the mirror **one target among several**, with object storage as a peer rather than an afterthought, and keep the mirroring layer indifferent to which target it writes to.

There is a sovereignty dimension too, given the corpus already holds a maturity model for exactly this. Making the durability of a zero-knowledge product depend on a single United States platform is a scored outcome, not a neutral one, and the model built on 24 July exists to express it. **This is the natural first subject for running that model against ourselves**, which has been parked since July.

## Moderation Is More Workable Than Expected

This is the finding that came back better than anticipated, and it removes what could have been a blocker.

Hosting providers are **not liable for stored content absent actual knowledge** of illegality, and the framework imposes **no proactive obligation to seek out facts or circumstances indicating illegal activity**. Actual knowledge means clear, specific awareness; general knowledge that some content might be illegal is not sufficient.

So **being unable to read is not disqualifying.** A host that cannot inspect content is in a comparable position to any storage provider that does not review content, and the required apparatus is procedural rather than analytical:

- A notice mechanism that is easy to find and use, accepting substantiated reports
- Prompt, objective examination of reports received
- A statement of reasons to the affected user when anything is restricted
- Notification of authorities where a report indicates serious criminal offences threatening life or safety
- An established legal representative for European users if not established there
- Annual transparency reporting on moderation activity

**The one real design consequence is granularity.** On notice about a specific file, an ordinary host removes that file. This host cannot identify it, because the objects are opaque and the reporter's description does not map to an object identifier. So **the unit of action is the vault**, and the available responses are suspension or deletion of the whole thing.

That should be stated in the terms rather than discovered during an incident, because it is a materially blunter instrument than users will expect, and because a vault owner whose entire vault is suspended over one file will want to know that was the only option.

The public tier changes this slightly and in a manageable direction: for vaults whose read key is published, the content is inspectable, so a report can be verified and the response can be proportionate. **Most abuse reports will concern public content anyway**, since that is what people encounter.

## What The Word Close Hides

The mechanism is close. Becoming a host is a change in what the organisation is, and four commitments arrive with it that do not exist today.

**There is no password reset, by design.** The published documentation states it plainly. Today that is a property of a tool used by people who understand it. At hub scale it becomes a stream of users who have lost everything permanently, with no remedy available and no way to distinguish them from someone attempting to take over an account. That is a support burden and a reputational exposure, and it needs a stated position before launch rather than after the first thread about it.

**Storage becomes an operating cost with no natural ceiling.** Free public hosting attracts volume, encrypted objects do not compress, and there is no server-side deduplication available because the server cannot see that two objects are the same. **The usual economics of a code host do not apply**, because those depend on compression and deduplication the encryption forecloses. This should be modelled before opening, not after.

**Uptime becomes a promise.** A vault on a live service today is somewhat ephemeral, as the memo says. A hub is expected to be there, and the corpus has repeatedly argued that customers should ask what happens if a provider disappears. Publishing a host invites that question about us.

**And abuse handling becomes a function.** Notice, examination, statement of reasons, appeal and reporting are ongoing work requiring a named owner, not a page in the terms.

None of those is a reason not to do it. They are the difference between a mechanism being ready and a service being ready, and the gap between the two is where this kind of launch usually goes wrong.

## What To Build First

Ordered so each step is useful alone and none commits to the next.

1. **The public tier only.** Vaults with published read keys, hosted and browsable. It is the demonstration, it needs no moderation apparatus beyond notice handling, and it is where the sample vaults and component registry already point.
2. **Discovery for the public tier.** Indexing and search over readable content, which is the feature that makes it feel like a host rather than a file server, and which yesterday's access report says is currently missing even for the documentation site.
3. **Mirroring, with more than one target.** Sharded objects, asynchronous, and indifferent to destination from the first version.
4. **Then private hosting**, with the operational commitments above resolved first: key loss position, storage economics, abuse process and a stated availability posture.
5. **And a name that is not the incumbent's.** A public host of vaults is accurate. An equivalent of the incumbent invites a comparison on features the architecture forbids, and the corpus argued this morning that stating the boundary plainly is what makes the whole argument credible.

## What This Does Not Try To Be

- **Not an equivalent of the incumbent.** Most of what that does requires reading plaintext.
- **Not a compromise on encryption.** The public tier is readable because owners published their read keys.
- **Not free durability.** The mirror is a counterparty relationship with stated limits and an acceptable use clause.
- **Not blocked by moderation.** No proactive obligation exists; the constraint is that the unit of action is the vault.
- **Not a small step.** The mechanism is ready and the operational commitments are not yet defined.

## Honest Tensions

| Tension | Note |
|---------|------|
| The two-tier design | It is coherent and it means the flagship features exist only where the privacy property is not being exercised |
| Mirroring to a third party | It is durable, free and familiar, and it makes a zero-knowledge product's recovery depend on somebody's usage policy |
| Vault-level moderation | It is the only available granularity and it is far blunter than users will expect |
| No password reset | It is the correct security property and at scale it is a stream of unrecoverable losses with no remedy |
| Storage economics | Encrypted objects neither compress nor deduplicate, so the usual host economics do not transfer |
| Naming it after the incumbent | It communicates instantly and sets an expectation the architecture cannot meet |
