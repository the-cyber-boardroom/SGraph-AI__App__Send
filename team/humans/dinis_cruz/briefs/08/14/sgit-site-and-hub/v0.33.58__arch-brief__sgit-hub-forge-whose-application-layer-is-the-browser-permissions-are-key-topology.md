## What This Is

The feature-level mapping for a vault forge, and a correction to this morning's assessment: **that brief concluded that most of what a code host provides requires the server to read plaintext, and resolved it by observing that public vaults publish their read key so the host may index them legitimately, which is true and is the weaker half of the answer; that also fixes the reference class, because the comparison is not to the largest code host but to the self-hostable forges, which already assume you run the server, and the difference from those is that the server here is object storage and a small interface rather than an application, which is a sharper and more demonstrable claim; mapping each forge feature by where it runs produces a clean split in which browsing, diffing, history, merging, issues and change proposals all run client-side and work, while continuous integration, notifications, cross-repository search and server-enforced access control do not, and those four should be stated rather than discovered; the load-bearing consequence is that permissions stop being a policy the server enforces and become a shape you build out of vaults and keys, since possession of a key is access, which means granularity comes from sub-vault topology rather than from an access control list, and it also means read access already granted cannot be withdrawn from somebody who fetched the objects; ## Answering The Question First

**Partly mapped.** The assessment written this morning covered the two-tier design, the mirroring plan and its counterparty risk, the moderation position, and the operational commitments that come with becoming a host.

**Not mapped**, and covered here: what a forge actually does feature by feature, where each of those features would run, what happens to permissions when possession of a key is access, and what cannot be done at all.

## The Correction

This morning's brief said that most of what a code host provides requires the server to read plaintext, and resolved it by noting that a public vault publishes its read key anyway, so the host can index public vaults legitimately.

That is true and it is the narrower answer. **The proposal here is better**, and it generalises: if the **browser** holds the vault key or read key, then the browser can do everything a reading server could do, for **any** vault the user has a key to, public or private.

```
   THIS MORNING                     THE BETTER MODEL
   server reads public vaults       browser reads whatever you hold a key to
   because keys are published
                                    server never reads anything, ever
   -> features on the public tier   -> features wherever you have the key
      only
```

So the two-tier design still applies to **discovery**, meaning search across vaults you do not hold keys to, which genuinely requires a reading index and therefore only works for public ones. It does not apply to browsing, diffing, history or review, which work on any vault you can open.

That is a materially stronger position and it changes the pitch. Not *a limited host with a public tier*, but **a forge where the application layer moved to the client.**

## The Reference Class Is A Forge, Not The Incumbent

The comparison the memo reaches for is the right one, and it is worth adopting deliberately.

Comparing to the largest code host invites a feature comparison that includes an ecosystem nobody is trying to replicate. Comparing to the self-hostable forges is more honest and more useful, because their users **already accept running the server themselves**, and the question is only what that server has to be.

| | A self-hosted forge | A vault forge |
|---|---|---|
| What the server is | An application, plus a database | **Object storage and a small interface** |
| What the server can read | Everything | **Nothing** |
| Where the application runs | On the server | **In the browser** |
| Who can operate it | Somebody who can run a service | Anybody with a bucket |
| What a compromise yields | All repositories, in plaintext | Ciphertext, and no keys |

That last row is the pitch, and the fourth is underrated. The operational burden of running a forge is the reason most teams do not, and **a forge that requires no application server is a different proposition** from one that requires a database, backups and upgrades.

## Where Each Feature Runs

The map. This is the part that was missing.

**Works, client-side:**

| Feature | Why it works |
|---|---|
| Browse files and directories | Fetch objects, decrypt, render |
| Diff between commits or branches | Both sides are objects the client can fetch |
| History and log | Walk commits client-side |
| Blame | Walk history; expensive but possible |
| Render markdown, highlight code | Purely a rendering concern |
| Branch, merge | The protocol already supports it; the client does the work |
| Issues and discussion | Files in the vault, which the existing mail and messaging work already demonstrates |
| Change proposals | Branches plus the serialised diff, reviewed in the browser |
| Search **within** a vault you hold | Index client-side after fetching; bounded by vault size |

**Does not work, and should be stated:**

| Feature | Why not |
|---|---|
| **Search across vaults you have no key to** | Requires a reading index; only possible for published-key vaults |
| **Continuous integration** | A runner must read the content to build it |
| **Server-enforced granular permissions** | Possession of a key is access; see below |
| **Content-triggered notifications and webhooks** | The server cannot see what changed |
| **Secret scanning, dependency analysis** | Reading features with no client-side trigger point |

Four absences, each with a reason rather than a roadmap entry. Three of them are the price of the property being sold. One of them, continuous integration, is a genuine gap and is discussed below.

## Permissions Become Key Topology

This is the most consequential item in the map and it deserves to be the headline of any design work.

In a forge, permissions are a **policy the server enforces**: this user may read that repository, may write to this branch, may not see that one. The server is the referee because the server holds the plaintext.

Here, **possession of a key is access.** There is no referee, because there is nothing for a referee to withhold that the key does not already unlock. Which means granularity cannot come from an access control list and must come from somewhere else.

It comes from **shape**. The product already has the pieces: separate vaults, sub-vaults with their own keys, link files, and read keys distinct from write keys. So an access model is built by deciding what lives in which vault and who holds which key.

```
   FORGE                           VAULT FORGE
   one repository                  one vault, or several
   + an ACL table                  + a key distribution
   server checks on each request   the key opens it or it does not

   "read src/, not secrets/"       secrets/ is a sub-vault with its own key
   enforced by policy              enforced by cryptography
```

That is genuinely elegant, and it is stronger in one respect: **a cryptographic boundary does not have a bypass.** A misconfigured ACL grants access; a missing key does not decrypt.

It has two hard limits that must be published rather than discovered.

**Revocation is not retroactive.** Somebody who held a read key and fetched the objects keeps a working copy forever. Rotating the key protects future commits and does nothing about what was already taken. That is the same property recorded this morning for a published sample vault, and it applies to every access grant here.

**And granularity costs structure.** Wanting five permission levels means five vaults and five keys, decided in advance. A forge lets you add a rule; this requires you to have designed the shape. That is a real ergonomic cost and it should be presented honestly, alongside the observation that a shape you can see is easier to audit than a table of rules nobody has read.

## Continuous Integration Is The Real Hole

The one absence that is not simply the price of the property.

A build runner must read the source to build it. There are three options and none is free:

**Run it locally.** The developer already has the key, so builds run where the checkout is. Honest, works today, and gives up the shared visibility that makes hosted integration valuable.

**Grant a runner a key.** It works and the runner can now read everything in that vault, which makes it exactly the over-privileged agent problem documented earlier today, where a disclosure at Black Hat on 5 August showed continuous integration secrets reachable from an issue opened by an account with no repository privileges. A key-holding runner in a zero-knowledge system is the same shape with a worse blast radius, because the key opens the whole vault.

**Or scope it by shape**, which is the only version that fits the model: a build runs against a **sub-vault containing only what the build needs**, holding only that key. That is least authority applied to continuous integration, it follows directly from permissions being topology, and it is the interesting answer rather than the resigned one.

Worth noting the corpus already has the adjacent piece: the serialised diff pattern gives an agent no credential at all by having it work on a public clone and emit a reviewable artefact. **Builds are the inverse case**, because they genuinely must read, which is why they are the hard one.

## Performance Is A Real Constraint

Browser-side version control is proven rather than speculative, and it is slower.

A pure JavaScript implementation of the protocol has run in browsers, service workers and workers for years, doing all its operations against the same on-disk format. The documented weakness is exactly the relevant one: pure JavaScript is **slower than native, especially for large repositories**, and a published benchmark comparing it against a compiled build found order-of-magnitude differences between browser and server execution on a modest repository, with packfile expansion identified as the dominant cost.

Two things follow.

**Decryption is on top of that.** Every object fetched must be decrypted before it can be used, so the browser is doing more work than a browser-side git client, not less.

**Sparse and shallow fetching is the mitigation**, and the product already has it. The documented answer for large repositories is to limit history and to check out only the paths you need, and the site's own agent documentation already lists sparse clones. **That should be the default in a forge interface rather than an option**, since a browsing session needs a subtree and a few commits, not the whole history.

The honest framing for the site: **this scales with what you look at, not with the size of the vault**, provided the interface only fetches what is being viewed.

## Why This Is Worth Building: It Teaches The Distinction

The memo names the purpose and it is the best argument in it. The project lead: **"I think that would be a great way to show the differences between git and GitHub."**

That distinction is one most developers have never had to examine, because they have only ever encountered the two together. A forge where the server provably cannot read makes it concrete:

- **Version control was always the protocol.** Commit, branch, diff, merge, history: none of that ever needed a hosting platform.
- **Collaboration was mostly the protocol too**, with the platform supplying an interface to it.
- **What the platform genuinely added was reading**: search, analysis, scanning, and a place to run builds.

So a working forge on a blind server is not a feature demonstration. **It is an argument, made by existing.** A visitor can browse a repository, read a diff, review a change, and then observe that the server returned nothing but ciphertext throughout. That is far more persuasive than a page explaining zero knowledge.

It also gives the boundary framing recommended for the why page something concrete to point at, and it is the sort of thing that gets written about.

## What This Changes About Sequencing

The assessment this morning recommended shipping the public tier first, and that still holds for **discovery**. But the browser-as-application-layer model changes what the first build should demonstrate.

1. **A read-only forge view over one vault**, using a read key held by the browser. Browse, diff, history. No accounts, no server logic. This is the demonstration and it is achievable now.
2. **The same view over a private vault**, with the key supplied by the visitor. Same code, and it proves the model generalises rather than depending on published keys.
3. **Issues as vault files**, which the existing mail and messaging work already covers.
4. **Change proposals**, using the serialised diff with review in the browser.
5. **Discovery across public vaults**, which is the only part that needs a reading index, and which is where the two-tier design applies.
6. **Continuous integration by sub-vault scope**, last, because it is the hardest and the most interesting.

Step two is the one worth prioritising over the tier work, because it is what makes this a forge rather than a public gallery.

## What This Does Not Try To Be

- **Not a clone of the largest host.** The reference class is a self-hostable forge.
- **Not limited to public vaults.** The browser holds the key, so features follow the key.
- **Not permission-free.** Permissions exist as vault and key topology rather than as server policy.
- **Not a home for builds.** Continuous integration needs a reading runner, and the answer is scope rather than trust.
- **Not fast on everything.** Browser-side operations plus decryption, mitigated by fetching only what is viewed.

## Honest Tensions

| Tension | Note |
|---------|------|
| Permissions as topology | Cryptographic boundaries have no bypass and they must be designed in advance, where a forge lets you add a rule later |
| Revocation | Rotating a key protects the future and returns nothing already taken, which is true of every grant here |
| Browser as application layer | It removes the server entirely and puts the cost on the visitor's machine, which varies enormously |
| Continuous integration | The only honest answers are local builds or a scoped key, and both give up something hosted integration provides |
| No cross-vault search | It follows from the property being sold and it is the feature people will ask for first |
| The demonstration argument | Existing is more persuasive than explaining, and it means the demonstration has to be genuinely good rather than indicative |
