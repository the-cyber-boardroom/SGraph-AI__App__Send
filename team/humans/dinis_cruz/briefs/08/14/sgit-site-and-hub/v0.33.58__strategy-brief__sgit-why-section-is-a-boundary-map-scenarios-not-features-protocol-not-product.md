# The Why Section Is A Boundary Map: Say Where Git Wins, Because The Intersection Is The Only Place The Argument Has To Be Made

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** Product, Engineering, Marketing

**type** Strategy brief

*First of 14 August. Positioning for the sgit website's Why and How-To sections. Technical details are drawn from the memo and from the project record. Offered to be built on and challenged.*

## Lead With The Boundary

The memo's most useful sentence is one it does not dwell on. The project lead: **"sometimes you can't do it with git, and I think that intersection is exactly the sweet spot of value."**

That should be the organising principle for the entire section, and it is unusual enough to be worth arguing for.

Most tool pages describe what the tool does and leave the reader to work out whether it applies. **A page that says plainly where the incumbent already wins does something better**: it is falsifiable, which makes it credible, and it makes the remaining territory unambiguous.

The corpus already reached this from the other direction on 6 August, when the co-existence work concluded that the two systems have almost disjoint strengths and that using both is division of labour rather than redundancy. The website should say that out loud:

**The boundary is not where people will assume it is**, and the page should correct the assumption early. sgit supports commit, push, pull, clone, branch, diff and merge. The version control operations are not the gap.

| Not the difference | The actual difference |
|---|---|
| Version control operations. Commit, push, pull, clone, branch, diff and merge are all supported | **Everything is encrypted on disk.** The host stores ciphertext under opaque identifiers and never sees filenames, contents or commit messages |
| Client-side execution. Git is also a client-side system: a git client understands the structure and schemas of the `.git` folder | **The client is doing the same job against encrypted objects**, which is why every implementation must understand the format |
| Merge workflow. Supported | **Proposing reviewable changes without holding write access is present**, as a serialised diff. What is absent is the hosted review interface, which is a platform construct layered on merge rather than a version control primitive |

What genuinely sits on git's side of the line is the **ecosystem above the protocol**, not the protocol itself: hosted review interfaces, continuous integration triggers, issue tracking, and server-side operations such as search and delta compression that require a server able to read the content. Those are real and worth naming.

A reader who arrives already using git is not being asked to give up their workflow. **They are being told which layer changes**, which is a much easier thing to accept than a claim that a familiar operation is missing.

## Scenarios, Not Capabilities

The memo is explicit about form and it is right. The project lead: **"the why section, I think, should be about here's a bunch of scenarios; if you have this, this is for you, kind of like walk through, very practical."**

That form works because it lets a reader self-select rather than translate. It also has a natural discipline attached, which is worth stating as a rule for whoever writes them:

**Every scenario is a problem somebody actually had.** The memo's own justification for this is the strongest asset the page has. The project lead: **"I literally use it every day, and it really solved the problem that I have."** And more pointedly. The project lead: **"it's important to capture the workflows that I wanted to have that I couldn't have, or I was struggling to do without sgit, which is kind of the way I developed it."**

That is a genuinely unusual position. The tool exists because specific workflows were impossible, so each scenario has a real before and after, and the before is documented in the corpus rather than reconstructed for marketing.

A structure that keeps them honest and comparable:

```
   THE SITUATION       what you have, in a reader's own terms
   WHAT YOU TRIED      the git-shaped attempt, and where it stopped
   WHAT CHANGED        the sgit version
   HOW                 link into the how-to section
```

The second field is the one most such pages omit and the one that makes the rest believable.

## One Artefact, Three Audiences

The memo raises sustainability as the reason for connecting the sections. The project lead: **"I want this why section to actually be connected to the how-to section, because now that we have this publishing environment, I want to leverage the sgit website."** With the mechanism. The project lead: **"it also has a nice, powerful llms.txt and markdown, so it's quite LLM friendly."**

The requirement underneath is that a use case written once should serve three readers without being written three times:

| Reader | Wants | Gets |
|---|---|---|
| A person evaluating | Do I have this problem | The scenario |
| A person building | How do I do it | The how-to, with working samples |
| **An agent** | Both, as context | The same pages, as markdown |

The third is the one the memo is most interested in and it is the one most sites get wrong. The project lead: **"I want it to also be used next time I'm with an agent, and I want to say, hey, let's do this, let's do that; I want this why section to be the one that gets referenced."**

For that to work the pages have to be genuinely usable as instructions, which means **working code samples and, as the memo suggests, sample vaults**. The project lead: **"very detailed guidance, including source code samples, even maybe vault samples that we can point to an agent and say, here's how you do it."**

A sample vault is a stronger artefact than a code sample, because it is the thing itself rather than a description of it, and it can be opened rather than read.

## The Mapping Page Already Exists, And Should Be The Anchor

Checked rather than assumed, because it changes what the Why section has to carry.

The site's machine-readable index already lists **a page mapping every git command to its sgit equivalent**, described as a Rosetta stone and noting three deliberate differences. It also lists an explicit limitations page covering the edges and current roadmap gaps, a use-cases index with a recipe and a stated evidence status per case, and packaged skills for agents.

Two consequences.

**The Why section should link to the mapping page rather than restate it.** A reader who wants to know whether a familiar command exists should reach an authoritative list in one click, and duplicating that list into marketing prose creates exactly the drift problem the memo is trying to avoid.

**And the honest-limitations page is an asset, not a liability.** A site that already publishes where the tool does not fit has earned the right to make the boundary argument, because the boundary claim is only credible from somebody visibly willing to state the negative case.

The index is also strong evidence for the agent-readability goal: every page is available as markdown, links inside the markdown point at markdown, and the notes for agents already carry install instructions, the key format, the agent-facing command and a cross-session state pattern. **The infrastructure the memo wants is in place**, so the work is content rather than plumbing.

One caution worth carrying: the material is spread across a why page, a use-cases index, four audience pages, a documentation set and a skills section. The memo's instinct to consolidate is right, and consolidating should mean **one canonical location per fact with the others linking to it**, rather than a new page that repeats what four existing ones say.

## The Sustainability Answer Is Structural

The memo's worry about keeping it updated has an answer that follows from the above rather than from discipline.

**If the how-to pages are the documentation the team actually uses, they cannot go stale without somebody noticing.** A marketing page nobody uses rots invisibly. A page an agent is pointed at every week fails loudly the first time it is wrong.

That is an argument for the how-to section being the primary artefact and the Why section being a curated index into it, rather than two bodies of prose that must be kept in agreement.

## Lead With Protocol, Because It Changes What Is Being Adopted

The memo insists on this and it deserves to be prominent rather than a technical footnote. The project lead: **"sgit ultimately is a protocol, and I think this is very important; it's a way to store data in a file system in a scalable, client-encrypted, distributed, version-controlled solution."**

The reason to lead with it is not precision for its own sake. **It changes what a reader is being asked to adopt.** Adopting a product means depending on a vendor. Adopting a protocol means the data outlives any particular implementation, which is exactly the concern a security-conscious buyer brings.

And it is demonstrable rather than asserted, which matters:

- **Implementations in two languages already exist**, in Python and JavaScript.
- **A command line client and a browser operate on the same vault**, which is the memo's own daily workflow.
- **The file naming convention is documented**, so a third party could implement against it.
- **The read path is short enough to state on one page**, which is the next section.

The corpus's sovereignty work supplies the argument for why this matters commercially: a buyer's real question is what happens if you disappear, and a protocol with two implementations answers it in a way a product cannot.

## The Read Path Is The Proof

The memo describes it and it should appear on the site almost verbatim, because a protocol you can explain in five steps is a protocol somebody believes exists.

```
   1. branch name  ->  deterministic filename       (no lookup needed)
   2. that file    ->  the head index
   3. head         ->  the commit                   (encrypted)
   4. commit       ->  the tree                     (encrypted)
   5. tree         ->  the blob, or another tree
   6. decrypt the blob                              -> your file
```

Two properties of that are worth calling out on the page rather than leaving implicit.

**Determinism without disclosure.** The memo is careful about this and the site should be too. The project lead: **"when I say everything is deterministic, all the contents are still encrypted, so all you're getting is a bit of metadata, but you won't have any of the contents."** A reader who understands that a computable filename reveals existence and not content has understood the security model.

**Two keys, not one.** The project lead: **"there's the vault decryption key, and there's the vault read key, which is created from the vault key, which allows you to read all the files."** A key that reads but cannot write is what makes browser consumption and public publishing safe, and it is a concrete thing to show rather than a claim to make.

## The Server Sees Ciphertext, Which Is The Whole Point

The constraint that shapes the design, and the way to present it matters because the obvious framing overstates the cost. The memo puts it directly. The project lead: **"you cannot rely on the server to do anything; the server cannot query files, cannot optimise, cannot consolidate data. In fact, that's one of the advantages of git."**

The important qualifier is that **git is also a client-side system.** A git client is what understands the object model, walks the tree and resolves a path; the server is largely a place to exchange objects. So the architectures are closer than they first appear, and the honest statement of the difference is narrow:

```
   GIT                              SGIT
   client understands .git          client understands the vault format
   objects on disk, readable        objects on disk, ENCRYPTED
   server can read them             server sees opaque blobs
        |                                |
   so the server CAN                so the server CANNOT
   compress, delta, search,         do any of it, and cannot be
   and be asked to disclose         compelled to disclose
```

What is genuinely lost is what the server could have done **on top**:

| | git hosting | sgit |
|---|---|---|
| Server-side search and code navigation | Yes | No |
| Server-side compression and delta | Yes, which is why repositories stay small | No, ciphertext neither compresses nor deltas |
| Hosted review, pull requests, continuous integration | Yes, an ecosystem | Not present; merge itself is supported |
| Host can be compelled to disclose content | Yes | **Nothing readable to disclose** |

The last row is what is being bought and the three above it are what it costs. The compression consequence was documented in this corpus on 6 August, and a page that names it before a reader discovers it is more credible than one that does not.

The memo also notes what the client does to compensate, and that is worth showing because it turns a constraint into visible engineering: filenames carry enough structure that a client can decide to cache a file **without knowing what it is**, which is what makes browser consumption fast.

## The Lead Example

The memo saves its best scenario for last and it should go first on the page. The project lead: **"I start a Claude session, and we do work on something, and then I say, hey, can you create a vault and put this data on it, and then I can access it from the vault web."**

That example does more work than any feature list:

- It is **concrete**, and a reader can picture it without any vocabulary.
- It demonstrates the **protocol claim**, since a command line client wrote it and a browser read it.
- It demonstrates the **encryption claim**, since the service that stored it could not read it.
- It demonstrates **collaboration**, since two different tools touched the same vault.
- It needs **one secret**, and the memo is careful about what that secret is not. The project lead: **"that access token is just for API usage, to make sure that the vaults we have open are not abused; it's not doing any encryption, it's transparent to it."**

That last point should be explicit on the page. An access token that governs service usage rather than confidentiality is a materially different thing from a credential that could decrypt your data, and saying so pre-empts the obvious objection.

And the extension the memo mentions makes it stronger still. The project lead: **"I can get Claude to create any kind of website and files, which I can then read and access from the vault web."** An agent producing a working application into an encrypted vault that a person opens in a browser is a demonstration, not a description.

## Three Modes, Named Once

The memo distinguishes them and the site needs the same distinction, since almost every scenario is one of them. The project lead: **"you're just using sgit in a local system, you're using sgit with a server which is the REST API, and then you have the vault web which gives you the front end."**

| Mode | Who uses it | Typical scenario |
|---|---|---|
| **Local** | A person or agent on one machine | Working offline, or on data that never leaves |
| **API** | Agents and services | An agent pushing work to a shared vault |
| **Web** | People, with a read key | Opening what an agent produced, or sharing outward |

Worth adding the memo's own note on how the third came about, because it explains why the browser experience is more than a viewer. The project lead: **"the vault web started as a web version of sgit, but eventually became its own powerful thing because we added the vault apps."**

## Industry Pages Are A Second Axis

The memo proposes them and they are a different cut of the same material. The project lead: **"add per industry, because we already have good examples on healthcare, on CVs, on recruitment, on collaboration, on risk management."**

Two cautions, both cheap to observe.

**Do not duplicate.** An industry page should assemble existing scenarios with a domain framing, not restate them, or the sustainability problem returns doubled.

**Do not claim readiness that does not exist.** Some of those examples are working products and others are demonstrations, and a healthcare page implying compliance work that has not been done creates an obligation nobody has met. The corpus already flagged this shape on 31 July, in the observation that claims about coverage are exactly where regulators look first.

## What This Does Not Try To Be

- **Not a feature list.** Scenarios a reader can self-select from.
- **Not a claim to replace git.** The boundary is stated, and both is a legitimate answer.
- **Not silent about the trade.** The server can do nothing, and that is named before a reader finds it.
- **Not two bodies of prose.** The how-to is the primary artefact and the Why is a curated index into it.
- **Not marketing an agent cannot use.** Working samples and sample vaults, because the third reader is an agent.

## Honest Tensions

| Tension | Note |
|---------|------|
| Naming where git wins | It is what makes the page credible and it hands a reader reasons not to adopt, in writing |
| Protocol framing | It is the stronger position and protocols are harder to sell than products, because nobody buys a convention |
| One artefact for three audiences | It is the sustainability answer and marketing prose and agent instructions genuinely want different things |
| Scenarios from one person's practice | They are real and specific, and they describe workflows most readers do not yet have |
| Industry pages | They convert interest faster and they are the easiest place to imply readiness that does not exist |
| Publishing the read path | Explaining the protocol is what makes it credible and it also documents the attack surface for anybody interested |
