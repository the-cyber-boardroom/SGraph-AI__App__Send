# Talk To The Page, File To An Inbox: The Chat Is A Scribe Rather Than An Editor, And The Extension Should Hold A Write-Only Channel Instead Of A Key

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** Engineering, Product

**type** Architecture brief

*Tenth of 14 August. Two related builds. Extension platform constraints are grounded and cited, and one of them rules out an assumed approach. Offered to be built on and challenged.*

---

## What This Is

An in-page chat surface and a browser extension, which are the same pattern on two surfaces and share one architectural decision: **the driver is a context switch, since making a change to a page currently means leaving it and describing it elsewhere, and that is exactly the cost closed on 2 August for a different surface, where an observation captured in place became a structured issue the building agent read, so this is that pattern applied to a website rather than a new idea, and the roles transfer unchanged, with the chat as the scribe that structures and files and the site agent as the builder that decides and edits; the decision that matters is that the chat must file to an inbox rather than edit the vault directly, because a chat that reads page content and holds a write key is a confused deputy by construction, with the page as untrusted input and the write as the privileged action, which is the ambient authority problem this corpus has now traced three times, and filing to a staging area removes it entirely while preserving the loop; the measured finding from that earlier work should also transfer, since the reported gain in feedback quality came from asking one adaptive follow-up question before filing rather than from capture alone, and the current design would transcribe and send; on the extension, the permissions answer is cleaner than the memo hopes, because the active-tab permission combined with scripting grants access to the current page only on explicit user invocation, shows no install-time warning, requires no per-site prompt and avoids the broad-host review delay, which is precisely the dynamic model asked for; one assumed approach is ruled out, because the extension platform prohibits remotely hosted code entirely, so vault content may be rendered as data and vault application code cannot be fetched and executed inside the extension; and the strongest recommendation is that the extension should hold a write-only channel to a feedback vault rather than a vault key at all, which sidesteps the key management question for the primary use case, since a login does not solve key storage but only moves it.** It is the tenth document of 14 August (cross-ref: the v0.33.55 vaults-as-substrate brief, the v0.33.56 plugins brief, the v0.33.58 forge brief, the v0.33.58 site changes brief, and the v0.33.55 monitoring-vault brief). New contributions: **the scribe and builder roles mapped onto this surface, inbox-not-editor as the injection fix, the follow-up question carried across, the active-tab answer to the permissions ask, the remote code prohibition as a hard constraint, and the write-only channel as the answer to key management.**

## This Is A Pattern You Already Have

The memo's reason for wanting it is the valuable part. The project lead: **"to make changes I have to go and have a chat with Claude Code or Claude Web, but at that moment in time I'm not really interacting with the page, so I want to provide this guidance that is much more immediate."**

That is the same cost identified on 2 August, when a spoken observation about a running demo became a structured issue that the building agent read, and the conclusion then was that what closes is not a feature gap but a **context switch**: the conventional route requires leaving the thing, opening another tool, and reconstructing from memory what you saw.

So the roles transfer without redesign:

| 2 August | Here |
|---|---|
| A person using the running demo | A person reading a page |
| The **scribe**: structures and files, no judgement | The in-page chat |
| A staging folder it can append to and not read | The site's inbox vault |
| The **builder**: reads, decides, edits | The site agent |

**That is the whole architecture**, and it is already proven on another surface. What follows is the two things to get right and the one thing that must not be built.

## File To An Inbox, Never Edit Directly

The memo raises the tempting version. The project lead: **"all I need is the read key, or I guess if I even have the write key, I could even change it directly, make a change to that file."**

**Do not build that.** A chat that reads the page and holds a write key is a confused deputy by construction:

```
   page content  ------> chat context  ------> write to the vault
   (untrusted)                                 (privileged)
```

Page content is untrusted input. On a public site it includes anything embedded from a sub-vault, anything a visitor pastes into the chat, and anything a future contributor adds. An instruction placed in any of those reaches a privileged action, and the corpus has now traced this same shape three times: ambient authority as the documented root cause of prompt injection, the vault kernel unable to distinguish an injected action from a legitimate one, and an over-privileged agent holding repository write access.

**The fix is the pattern already in use**: the chat appends to an inbox it cannot read back, and the builder picks it up. That gives four properties for free.

Nothing the chat produces takes effect without the builder acting. A malicious instruction yields a junk issue rather than an edited page. The inbox is a record of what was asked, which is provenance rather than a side effect. And the chat needs no write key at all, which means there is no key on the page to steal.

The memo already describes this mechanism in the extension section, and it is the right one for both. The project lead: **"one of the things that the vaults already support is the idea of messaging, so I can send a message to a vault, which allows some workflows to exist."**

## Ask One Question Before Filing

The finding from 2 August that should carry over, because the current design would skip it.

Research on feedback quality found that users submit vague reports omitting essential context, and that the measured improvement in a model-mediated system came specifically from **adaptive follow-up questions** asked before submission, together with automatically attached context. A system that transcribes and files inherits the vagueness.

So the in-page chat should ask **one** question aimed at whatever the observation lacks, most often what was expected rather than what happened, or which part of the page is meant. Five seconds, and it is where the quality is.

**And it should attach context automatically**, which on this surface is trivial: the page path, the section, the site version, and the vault commit. The site already increments a version on every push and records the vault commit per release, so the issue can say exactly which build was being looked at. That is the difference between an observation and a reproducible one.

## Read Key And Write Key Enable Different Products

Worth separating, because the memo runs them together and they are different features with different risks.

| | With a read key | With a vault key |
|---|---|---|
| Talk to this page | Yes | Yes |
| Talk to the whole vault | Yes | Yes |
| File an observation | Via the inbox, no key needed | Same, and no reason to use the write key |
| Edit the page | No | Possible, and should not be built |

**The read key is enough for everything worth having on a public site**, and this site already publishes one. The write key adds only the capability that creates the injection path.

There is a narrower case worth keeping in mind: a private working vault, opened by its owner, where direct editing is legitimate because there is no untrusted content and one person holds the key. That is a different product from a chat on a public page, and conflating them is how the dangerous version gets built by accident.

## The Extension: The Permissions Answer Is Better Than Hoped

The memo's ask. The project lead: **"ideally I would like a mode where I don't have to ask permissions for every website, or it'd be even better if we can actually do this a bit more dynamically, because you shouldn't need to see the content of every website from a security point of view."**

**That mode exists and is the recommended pattern.** The active-tab permission, combined with scripting, grants access to the current page **only when the user explicitly invokes the extension**, and both are documented as safe to include with **no install-time warning shown to the user**. Published guidance is direct that this combination replaces broad host permissions for most use cases.

The alternative is what to avoid. Declaring access to all sites produces the warning text about reading and changing all your data on all websites, and the store dashboard warns that broad host permissions may require an in-depth review that delays publishing.

For anything genuinely needing more, **optional host permissions** are requested at runtime rather than at install, which is the dynamic model the memo describes.

So the recommended manifest shape is: active tab and scripting, storage, no host permissions at all, and optional host permissions only if a later feature proves it necessary. **That is both the least alarming to a user and the least likely to attract review delay**, and it happens to match the security posture the product argues for everywhere else: the extension sees a page when you point it at one, and not otherwise.

One consequence worth designing around: because access is granted on invocation, the extension cannot watch pages in the background. Everything it does is user-initiated. For a feedback and observation tool that is exactly right.

## One Approach Is Ruled Out

A hard constraint that would otherwise be discovered late.

**The extension platform prohibits remotely hosted code entirely.** All extension logic must be part of the package: no scripts fetched from a server, no libraries from a content delivery network, and no bundled library that dynamically fetches code. The content security policy for extension pages disallows the values that would permit it.

Applied here: the extension may fetch vault **content** and render it, because that is data. It may not fetch a vault **application** and execute it, because that is remotely hosted code. So the idea of reusing the vault app runtime by loading apps into the extension does not work as stated.

Two workable shapes remain. The extension can bundle its own client and treat vaults purely as data. Or it can open a vault app in a normal browser tab or a sandboxed frame pointing at a web origin, which is how the site itself already embeds apps, with the extension acting as the launcher rather than the host.

Worth deciding early, because it changes what code is shared with the vault web application and what has to be bundled separately.

## Key Management: A Login Moves The Problem

The memo's other ask, and the honest answer is narrower than hoped. The project lead: **"I think we need to look at where can we store the data when we have a vault extension, so we could actually store it on the vault itself, or we can even see if we can leverage the Google login."**

There are only three arrangements and each has a fixed cost:

**The user supplies the key each session.** Nothing is stored, nothing can be stolen at rest, and it is the most annoying. It is also the only one fully consistent with there being no password reset.

**The key is stored client-side.** Local extension storage persists to disk unencrypted and is readable by anything with access to the profile directory, which is the wrong home for a vault key. Session storage is held in memory and cleared when the browser closes, which is materially better and is what it exists for. The workable pattern is: passphrase at unlock, derive, hold in session storage, never persist the key itself.

**The key is stored server-side behind a login.** This is where the memo's instinct leads and it is the one to be careful about, because **a login does not solve key storage, it moves it.** If a server can return your key after you authenticate, that server can decrypt your vaults, and the zero-knowledge property is gone. A login is useful for identity and for gating access to non-secret configuration; it is not a key vault unless the thing it returns is itself encrypted with something only the user has, at which point the user is supplying a secret again and you are back to the first arrangement.

That is worth writing down plainly because it is the sort of thing that gets built as a convenience and quietly undoes the product's central claim.

## The Better Answer: Hold A Channel, Not A Key

Which leads to the strongest recommendation here, and it sidesteps the whole question for the primary use case.

The memo describes the mechanism without noticing it answers the problem. The project lead: **"I could even have my extension without having full access to a particular vault, that sends messages to another vault."**

**Do exactly that.** For sending observations, the extension needs to write and never to read. So give it a write-only channel to a feedback vault: it can append, it cannot read the vault back, and it cannot reach anything else.

| | If the extension holds a vault key | If it holds a write-only channel |
|---|---|---|
| Can read your vaults | Yes | **No** |
| Value to an attacker | High | **Junk in an inbox** |
| Key management problem | Real, and unsolved above | **Does not arise** |
| Store review exposure | A credential in an extension | Nothing sensitive |

That is the fifth instance of the write-only channel in this corpus and the cleanest application yet, because here it removes an entire subsystem rather than reducing a blast radius.

Reading a vault in the extension is then a **separate, later feature** with its own key handling, and the first version does not need it.

## Chat History Needs A Home That Is Not Local Storage

Both parts of the memo mention keeping chats locally. The project lead: **"on both chats we probably need a bit of local storage to capture the chats that we've been having."**

Reasonable, with one caution. Browser local storage on a public site is readable by any script on that origin, and a chat about a page may contain unpublished observations, draft criticism, or a pasted key.

Two better homes, matching the two surfaces. In the extension, **session storage** rather than local, for the same reason as keys. On the site, the durable copy belongs in the inbox vault anyway, since that is where the observation is going, with local storage holding only a pointer for continuity within the session.

That also gives something better than a scrollback: the conversation that produced an issue is filed alongside it, which is the raw-transcript discipline the corpus applies elsewhere.

## Sequencing

1. **In-page chat, read key only, filing to an inbox.** No write key anywhere, which is the whole safety argument.
2. **The one follow-up question and automatic context attachment.** Cheap, and it is where the quality is.
3. **The extension with active tab and scripting**, a write-only channel, no vault key. Shippable to the store without a broad-permission review.
4. **Vault reading in the extension**, with session-held keys, as a separate feature once the first is working.
5. **Direct editing**, only for private vaults opened by their owner, and never on a public page.

## What This Does Not Try To Be

- **Not a new pattern.** The scribe and builder split, on a new surface.
- **Not an editor.** The chat files to an inbox; the builder edits.
- **Not a key holder.** The extension holds a write-only channel for the first version.
- **Not a host for vault apps.** Remotely hosted code is prohibited; the extension launches rather than runs them.
- **Not solved by a login.** A login moves key storage rather than solving it.

## Honest Tensions

| Tension | Note |
|---------|------|
| Inbox rather than direct edit | It removes the injection path and it means an observation does not become a change without a second step |
| One follow-up question | The evidence says that is where the quality is, and it interrupts somebody mid-thought |
| Active tab only | No warnings and no background awareness, so the extension cannot notice anything you did not point it at |
| Write-only channel | It removes the key problem and it means the extension cannot show you what you previously filed |
| Chat history in the vault | Better provenance, and it makes every conversation durable whether or not you wanted it kept |
| A login for identity | Useful for non-secret configuration and easily mistaken for a solution to key storage |

## Open Questions

| Question | Notes |
|----------|-------|
| Which inbox does a public page write to? | One per site, or one per section, and who triages it |
| What context is attached automatically? | Page path, section, site version and vault commit are all available |
| Where does the extension send observations? | A single feedback vault, or one per target site, which changes the channel model |
| Does the extension ever read a vault? | A later feature with real key handling, deliberately not in version one |
| How is a private-vault editing mode kept separate? | It is legitimate and it must not be reachable from a public page |
| What happens to a filed conversation? | Kept alongside the issue, and for how long |
| Is the site agent the triager? | The inbox will fill, and nothing currently sorts it |
