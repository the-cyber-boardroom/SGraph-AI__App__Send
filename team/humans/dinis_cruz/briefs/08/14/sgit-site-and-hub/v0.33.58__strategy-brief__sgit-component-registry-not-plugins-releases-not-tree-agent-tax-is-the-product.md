# A Registry Of Components, Not Plugins: The Word Is Already Taken By The Security Model, And The Real Product Is Not Having To Explain A Vault To An Agent Again

**version** v0.33.58
**date** 14 August 2026
**from** Human (project lead)
**to** Product, Engineering

**type** Strategy brief

*Fourth of 14 August. Distribution limits are grounded and cited, including one that decides the packaging format. Contains a naming objection worth settling before anything ships. Offered to be built on and challenged.*

## What This Is

A distribution plan for reusable vault components, and one objection to the word being used for them: **the storage problem is real and correctly diagnosed, since vaults on a live service are somewhat ephemeral and no equivalent of a hosting platform exists for them yet, and a code hosting platform is a reasonable long-term home, but three of its documented limits shape the design rather than merely constraining it, of which the decisive one is that a single directory is recommended to hold no more than three thousand entries, and a bare vault folder is precisely a flat directory of many object files, so committing bare folders directly would breach that immediately while committing archives sidesteps it entirely, which turns the memo's instinct into the right answer for a reason it does not state; the second limit is that archives of encrypted objects will not shrink, because ciphertext neither compresses nor deltas, so an archive is packaging rather than compression and nobody should expect otherwise; the third is that release assets rather than the repository tree are the correct home for anything large, since a file committed to history is paid for by every clone forever; the naming objection matters more than it sounds, because the corpus established on 6 August that a plugin is a capability grant and therefore a security boundary, and the vault runtime already ships a deny-by-default permission model on that basis, so applying the same word to reusable interface components would collide with a published security concept and the two should be separated now while it costs nothing; and the most valuable thing in the memo is a recurring cost rather than a feature, since the project lead currently spends time on every new build explaining an existing vault to an agent so it can extract a pattern, which is a weekly tax that an addressable, fetchable component registry removes, and that is a better argument for building it than the examples themselves.** It is the fourth document of 14 August (cross-ref: the v0.33.58 serialised pull request brief, the v0.33.58 agent access report, the v0.33.56 plugins brief, the v0.33.56 git-and-sgit brief, and the v0.33.54 no-blank-prompt brief). New contributions: **the directory-width limit identified as the reason archives beat bare folders, the non-compression expectation set, release assets proposed over the repository tree, the plugin naming collision raised, and the agent-explanation tax named as the product.**

## The Storage Problem Is Correctly Diagnosed

The memo states it plainly. The project lead: **"the point here is that we need a long-term storage. The idea is because a little bit the vaults are ephemeral, and at the moment we still don't have an sgit hub. We want a way to store the files kind of more long termish, and I think GitHub is a perfect alternative for that."**

That is the right framing and it is worth being explicit about what problem it solves, because there are two and they are different.

**Durability.** A vault on a live service depends on that service. An archive in a repository does not, and it survives the service being reconfigured, moved or paused.

**Addressability.** A vault reachable only by key and service is hard to point at. A file at a stable URL can be linked, fetched, cited and version-pinned.

The second matters more for this use than the first, for reasons the section on the agent tax sets out.

## Three Limits That Shape The Design

Checked rather than assumed, because one of them decides the packaging format.

**Directory width is the decisive one.** The platform's own limits documentation recommends no more than **three thousand entries in a single directory**, noting that directories with many frequently modified files significantly increase maintenance cost and degrade basic operations.

A bare vault folder is exactly a flat directory of object files with derived names. **A vault of any real size breaches that immediately.** So committing bare folders directly is the wrong shape, and the memo's instinct to ship archives is right for a reason it does not state: an archive is one entry regardless of how many objects it contains.

**File size is a hard block.** Individual files are hard-blocked above one hundred megabytes in normal history, with a warning above fifty and a browser upload cap of twenty-five. Repositories are recommended under one gigabyte and strongly under five, above which the platform makes contact.

**And history is forever.** A large file committed once is not a one-time cost: every clone, fetch and fork pays for it, and removing it later requires rewriting history. This is why the platform steers large binaries toward release assets, package registries or object storage rather than the repository tree.

That last point produces a concrete recommendation.

## Put The Archives In Releases, Not The Tree

**Release assets are the right home for the vault archives**, and the repository tree is the right home for the catalogue that describes them.

| | Repository tree | Release assets |
|---|---|---|
| Counts against clone size | Yes, forever | No |
| Per-file ceiling | 100 MB hard block | Substantially higher |
| Versioned | By commit | By release tag |
| Good for | The index, metadata, screenshots, code samples | The vault archives themselves |

That arrangement gives a clonable repository that stays small, a stable URL per archive, and version pinning by tag, which is what a component registry actually needs. It also means somebody browsing the repository sees the catalogue rather than a directory of opaque binaries.

## Archives Will Not Shrink

Worth setting expectations, because the word archive implies compression and here it will not deliver any.

Encrypted objects are indistinguishable from random data, so **they neither compress nor delta**. The corpus documented this on 6 August in the context of mirroring a vault into ordinary version control, and the same applies to zipping one. An archive of a vault is approximately the size of the vault.

So the archive is doing three useful things and compression is not among them: it is one file instead of thousands, it preserves the folder structure, and it is a single stable download. Those are enough. Nobody should size the plan on an expected reduction that will not arrive.

## Do Not Call Them Plugins

The naming objection, and it is worth settling now because it costs nothing today and is expensive later.

The memo uses the word for reusable interface components. The project lead: **"I like the idea of breaking down some of the core components into little bits and bobs that are actually plugins, because you can have the full-blown site, which is an example, but there's also lots of components where we just want to reuse it."**

**The word is already taken, by a security concept, in this same product.** The brief of 6 August established that a vault plugin is a capability grant rather than a code module, meaning the authority a vault holds to do something, organised by what a vault may touch rather than by what code you would like to keep separate. The published documentation already reflects that, describing the vault runtime's deny-by-default permission model and the capabilities the host provides.

So the collision is direct:

| Concept | What it is | What it governs |
|---|---|---|
| **Plugin**, as established | A capability grant | What a vault is permitted to do |
| **What this memo means** | A reusable interface component | What a vault application looks like and does |

One is a security boundary. The other is a starting point for building something. Giving them one word means that in six months a sentence about installing a plugin will be genuinely ambiguous between granting an authority and copying a Kanban board, and the ambiguity will land in documentation aimed at people making security decisions.

**Suggested separation:** capability grants keep the word plugin. The reusable pieces are **components**, or **starters** if the emphasis is on copying and modifying rather than importing intact.

That distinction also clarifies the memo's own later idea. The project lead: **"I could even add support to the vault to actually go and get the plugin directly, or add support to sgit to download some of the plugins."** Fetching a **component** is a convenience. Fetching a **plugin** in the established sense is granting an authority, and those two operations should never share a command.

## The Real Product Is The Agent Tax

The most valuable line in the memo describes a recurring cost rather than a feature. The project lead: **"every time I need to do that, I kind of have to spend a bunch of time providing references to the vault or the agent, and I just should be able to point to somewhere."** And the current workaround. The project lead: **"one of my patterns already is: hey, here's a vault, check it out, take a look and extract."**

That is a tax paid on every new build. The pattern exists, it works, and reaching it requires a conversation each time: locating the right prior vault, giving the agent enough context to find the relevant part, and hoping it extracts the right thing.

**A component registry is that tax removed**, and it is a better argument for building this than the examples themselves. Compare:

```
   TODAY      "here is a vault, go and look at it, find the chat
               implementation, and extract the pattern"
               -> several turns, variable results, repeated monthly

   WITH IT    "use the chat-session component at <url>"
               -> one reference, deterministic, version-pinned
```

Two design consequences follow directly from that being the point.

**Each component needs a single canonical URL** that an agent can be given in one line, and the artefact at that URL needs to be enough on its own. Not a page describing where to look, but the thing.

**And it has to be fetchable.** Yesterday's access report found that the site does not currently appear in search, and that an agent restricted to previously-seen URLs could reach only what one index fetch contained. A component registry inherits that problem exactly. **A registry an agent cannot fetch is a registry that does not solve the tax it exists to remove**, so the indexing question is a dependency of this work rather than a separate concern.

## What A Component Page Needs

The memo lists most of it. The project lead: **"the web page should have a screenshot of it, should have instructions, should have code samples, should have the button to download, or the button instruction to clone it."**

Two additions, both cheap.

**An evidence status per component**, which the site already does for use cases. Some of these are production code and some are demonstrations, and a reader who cannot tell will guess wrong in one direction or the other.

**And the one-line agent reference**, prominently. If the purpose is to stop explaining vaults to agents, the page's most important element is the line somebody pastes into a session. It should be the easiest thing to find on the page, not buried under the screenshot.

## Copy Or Reference, And They Are Different

The memo floats several distribution routes and two of them have genuinely different semantics, which is worth naming because it affects what a user gets.

| Route | Semantics | Consequence |
|---|---|---|
| Download an archive | **A copy** | Diverges immediately; never updates; yours to change |
| Clone | **A copy** | Same, with history |
| Vault-in-vault link | **A reference** | Stays live; updates when the source does; not yours to change |

The memo notices the appeal of the third. The project lead: **"you can have the vault in vault with the link, so that also works quite well, because it actually looks like an extended file system."**

Both are legitimate and they serve opposite needs. A starter you intend to modify should be a copy, because a live reference that changes underneath your modifications is a hazard. A shared reference library you want to stay current should be a link. **The page should say which one a given component is**, rather than offering both without comment.

## The Component List

The memo names what exists: chat sessions ranging from simple to full two-way integration with tools and a virtual file system, Kanban boards, an email dashboard, the folder-based mail store, and vault-in-vault.

One observation on sequencing. **The chat session is the highest-value component and the hardest to specify**, because the memo describes it as spanning from simple to complex. Shipping it as one component would produce something either too thin to use or too complex to adopt. It is probably two or three components at different levels, and deciding that is more useful than shipping a single ambiguous one.

Vault-in-vault is the opposite case: small, well understood, and needed by nearly everything else. It is the obvious first.

## What This Does Not Try To Be

- **Not bare folders in a repository.** Archives, because a flat object directory breaches the recommended width immediately.
- **Not compression.** Ciphertext does not shrink; the archive is packaging.
- **Not repository-tree storage.** Release assets, so clones stay small and history stays clean.
- **Not plugins.** That word is a capability grant and a security boundary in this product already.
- **Not a gallery.** The point is removing the cost of explaining a vault to an agent.

## Honest Tensions

| Tension | Note |
|---------|------|
| Hosting on a code platform | It is durable and addressable and it makes the durability of an encrypted-vault product depend on somebody else's repository policy |
| Archives against live references | Copies are safe to modify and go stale, and references stay current and change underneath people |
| Components as a product surface | Each one published is a maintenance commitment, and the catalogue will outgrow the attention available to it |
| Renaming away from plugin | It is right and the word is already in use in conversation, so the correction costs something now and much less than the ambiguity would |
| The agent reference line | It is the whole point and it depends on discoverability that does not currently work |
| Splitting the chat component | Two or three levels serve users better and multiply the maintenance immediately |

## Open Questions

| Question | Notes |
|----------|-------|
| What are these called? | Components or starters, decided now, with plugin reserved for capability grants |
| Repository tree or release assets? | Releases for archives, tree for the catalogue, unless something argues otherwise |
| What is the canonical agent reference format? | One line, pasteable, and it needs to resolve for an agent that cannot browse |
| Copy or reference, per component? | Stated on each page rather than left for a user to infer |
| How many chat components? | Probably more than one, and the levels should be decided before the first ships |
| Who maintains the catalogue? | Every published component is a commitment, and stale ones cost more than absent ones |
| Does the indexing problem block this? | Probably, since a registry an agent cannot fetch does not remove the tax |
