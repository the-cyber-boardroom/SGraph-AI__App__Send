# Agent Access Report: The Markdown Is Excellent And I Could Not Reach It, Because The Site Is Not In The Search Index

**version** v0.33.58
**date** 14 August 2026
**from** An agent working from the sgit.ai site
**to** The sgit.ai site team

**type** Cross-team brief

*Second of 14 August. A field report from an agent that tried to use the site as documentation and partly failed. One finding is on the site's side and is actionable; one is a constraint of the agent's own tooling and is reported because it is a class of constraint worth designing around. Fits the existing cross-team brief pattern the site already publishes.*

---

## What This Is

A report on what happened when an agent tried to read the documentation as context: **the machine-readable index works, and it is better than almost anything comparable, since a single fetch returned a complete annotated map of the site with one-line descriptions per page, install instructions, the key format, the agent-facing command, a cross-session state pattern and a pointer to the honest-limitations page, which is a genuinely high standard; what then failed was following a link out of it, because the agent's fetch tool refuses any URL that has not previously appeared in a search result or a prior fetch, and links listed inside a fetched document did not satisfy that condition, which is a harness policy rather than a fault of the site; the recovery path the tool prescribes is to search for the page first, and that is where the finding that matters emerged, because a search for the exact title and topic of the mapping page returned no sgit.ai result at all, and a second search using the site's own distinctive positioning language returned the package registry page but still not the site; the practical consequence is that for any agent under this common restriction, the entire documentation set is reachable only through whatever a single index fetch contains, so llms.txt is not a convenience for such agents but the whole surface; three mitigations follow, of which getting indexed is the real fix, making key facts self-sufficient inside llms.txt is the cheap immediate one, and publishing a single-file concatenation is the one that removes the dependency on link-following altogether; and the sharpest way to see the gap is that the package registry page currently answers a question the documentation answers better, because the registry ranks and the site does not.** It is the second document of 14 August (cross-ref: the v0.33.58 Why-section brief).

## What Worked

Recorded first, because it is unusual and should not be lost in a report about a failure.

A single fetch of the machine-readable index returned a complete, annotated map of the site: every page with a one-line description of what it contains, grouped by purpose. It also carried, without being asked:

- The installation command and the Python version requirement
- The key format, and the fact that no password reset exists
- A warning about writing a vault key into a tracked file, with a link to the cost
- The agent-facing command, with its flags
- A cross-session state pattern in one line
- A pointer to an honest-limitations page, described as honest edges

**That is a higher standard than most documentation sites reach.** Two details in particular are worth keeping: every page is available as markdown at the same path with the extension swapped, and links inside the markdown point at markdown, so a traversing agent never has to parse HTML.

The one-line descriptions did real work. They let a specific question be answered from the index alone, which is exactly what an index is for. When the question was whether a page listing command equivalents existed, the index answered it without a second request.

## What Failed, And Whose Fault It Is

**The failure was mine, not the site's**, and it should be stated that way before anything else.

After reading the index, the obvious next step was to fetch the page it listed at `/docs/sgit-for-git-users.md`. That request was refused by the agent's own tooling, with the message that the URL had not appeared in any prior search or fetch result and that a search should be run first.

That is a **harness policy**, not an HTTP error and not a site misconfiguration. The site returned nothing wrong because it was never asked. The policy exists to stop an agent constructing arbitrary URLs, and it is common enough to be worth designing around: **many agents can only fetch URLs that a search engine has already returned to them.**

The relevant nuance for the site team is narrow and consequential. **A link listed inside a fetched document did not count as having been seen.** The index was fetched successfully, the link was in it, and the link was still not fetchable. So the index's own careful design, in which links point at markdown so the site can be traversed, does not help an agent under this restriction. It can read the map and cannot walk it.

## The Finding That Is Actionable

The tool prescribed a recovery path: search for the page, then fetch the result. That is where the real problem surfaced.

| Search | Result |
|---|---|
| The mapping page's exact title and topic, with the domain named | **No sgit.ai result.** Generic git tutorials from unrelated sites |
| The site's own distinctive positioning language: encrypted vault, git, client-side encryption, zero knowledge | **The package registry page ranked. The site did not appear** |

The second is the one to act on. A search using the product's own framing, in the product's own words, surfaced the package listing and not the documentation.

**For an agent under the restriction described above, that means the documentation is unreachable except through whatever a single index fetch contains.** Not slow to reach, not awkward to reach: unreachable. And the package registry page, which is a summary written for a different purpose, becomes the authoritative source by default because it is the only one that ranks.

There is an irony worth naming, since the site's stated intent is to be agent-readable. **The markdown is exemplary and the discovery layer is what stops agents using it.**

## Why This Is Worse Here Than It Would Be Elsewhere

Three reasons this matters more for this site than it would for most.

**The audience is disproportionately agents.** The index carries a section of notes for agents and a section of packaged skills for them. If agents are a primary audience, the failure mode is a primary failure mode.

**The onboarding path runs through agents.** The workflow the product is proudest of involves telling an agent to do something with a vault, which requires the agent to reach the guidance. A person who cannot find the docs will search harder; an agent that cannot fetch them will answer from whatever it already believes, which for a young project is usually nothing or something wrong.

**And the site is served from a vault**, which is a demonstration of the product. A demonstration nobody can reach demonstrates nothing.

## Three Mitigations

In order of how quickly they can be done.

**Make llms.txt self-sufficient for the commonest questions.** It already carries install, key format and the agent command. Adding the answer to *does sgit support the git operations I know* would have answered, from the index alone, the exact question that failed here. One or two lines: commit, push, pull, clone, branch, diff and merge are supported; pull requests are not, being a hosting-platform construct layered on merge. That is cheap, it is already true, and it removes the most likely reason an agent needs to follow a link at all.

**Publish a single-file concatenation.** A page containing the full documentation set in one document, linked from the index, means one fetch gets everything. Several projects do this precisely because link-following is unreliable for agents. It removes the dependency entirely rather than mitigating it, and it costs nothing to generate from pages that are already markdown.

**Get indexed.** This is the actual fix and the slowest. Whatever the cause, the effect is measurable: the package registry ranks for the site's own language and the site does not. Worth checking the obvious candidates, which are whether crawlers can render a page that is generated client-side from a vault, whether a sitemap is published, and whether anything is served that discourages indexing.

That third question is worth a specific look. A site whose pages are decrypted and assembled in the browser is exactly the shape a crawler struggles with, and if the HTML served to a crawler is a shell that fills in client-side, then the content is invisible to indexing regardless of how good the markdown is. **That would explain both observations at once**, and it would be a fixable rendering problem rather than a ranking one.

## A Smaller Note On llms.txt Itself

One structural observation, offered lightly because the file is already good.

The file is a map with descriptions. For an agent that can follow links, that is the right design. For an agent that cannot, **the descriptions are the only content it will ever see**, which changes what they should contain.

A description that says what a page covers helps a reader decide whether to open it. A description that also carries the page's single most important fact helps a reader who will never open it. The limitations entry already does this well by saying honest edges rather than merely limitations. The mapping page's entry could do the same by naming the three deliberate differences rather than referring to them.

That is not a criticism of the current file. It is an observation that the index is doing double duty for a class of reader it was probably not designed for, and that a small change in emphasis serves both.

## What This Report Is Not

- **Not a bug report against the site.** The blocked fetch was the agent's own policy.
- **Not a criticism of the markdown.** It is better than most, and the traversal design is right for agents that can traverse.
- **Not a ranking complaint.** The likely cause is a rendering question with a technical answer.
- **Not urgent for human readers.** People find the site and read it fine.

## Summary For The Team

| Finding | Whose | Action |
|---|---|---|
| The index is excellent and answered a real question in one fetch | Yours, and worth keeping | None |
| A link inside a fetched document could not be followed | The agent's harness | None available to you directly |
| **The site does not appear in search for its own positioning language** | **Yours** | **Investigate crawlability, likely client-side rendering** |
| The package registry ranks instead | Consequence of the above | Resolved by the above |
| Agents under the common restriction can reach only what one index fetch contains | Both | Self-sufficient index entries, plus a single-file concatenation |
