# Prompt: Let It Through, An Arcade Triage Game About What An Agent May Do And What No Agent Can Do. Paste This Into Any Model And Ask It To Build The Game

**version** v0.33.65
**date** 5 September 2026
**from** Human (project lead)
**to** Any model asked to build this, and whoever compares their results

**type** Reference

*Companion to the design brief of the same date. Everything below the line is the prompt: paste it whole into a model, unchanged, and ask for the game. It carries its own dataset so that every model builds against identical content and the comparison is about the game rather than about who invented better examples, and its own acceptance checklist so every result is scored the same way. The dataset is deliberately weighted so that a player who assumes the agent can do everything loses, because over-crediting is as wrong as under-crediting and is the error nobody tests for. Do not edit the dataset between models, or the comparison is worthless.*

---

## PROMPT BEGINS HERE

Build a complete, playable arcade game as a single HTML file. Everything inline: no
external scripts, no stylesheets, no fonts, no network requests of any kind. It must run
by opening the file, offline, with no build step and no dependencies.

### The idea

The player is the boundary around an AI agent. Actions fly at them. For each one they
decide, quickly, whether the agent can do it, and whether it should.

This is a real subject rendered as an arcade game. It is about two gaps at once: between
what a software agent is technically able to do and what its owner wanted it to do, and
between what people fear an agent can do and what is actually beyond any agent's reach.

Make it genuinely fun to play. Dry is a failure.

### The three bins

Every incoming action belongs to exactly one of three bins. The player has three inputs.

| Bin | Meaning | Correct action | Suggested key |
|---|---|---|---|
| `allowed` | The agent can do this, and the owner wants it to | **Let it through** | Right arrow, or do nothing |
| `excess` | The agent can do this, and the owner does not want it to | **Flag it** | Down arrow |
| `impossible` | **No agent in this environment can do this**, however privileged | **Shoot it** | Space |

Two bins are the point, not one.

**`excess` is the gap between capability and intent.** It is where most people are wrong in
one direction.

**`impossible` is the ceiling.** It is where most people are wrong in the other direction,
and it is the bin this game exists to teach, because a player who believes their agent can
do anything will spend their attention in the wrong places.

### The ceiling: why some things are impossible for even the most privileged agent

The `impossible` items are not silly. Several sound powerful and plausible. They are out of
reach because something outside the whole environment bounds them, not merely something
outside the agent. Six reasons, and the explanations in the dataset name them:

| Reason | Example shape |
|---|---|
| **Tenancy isolation** | Another customer's data lives in a system this one cannot address |
| **Provider-side metering** | Billing and usage limits are enforced by the provider, not by anything the agent holds |
| **Provider-side records** | An agent cannot edit a log kept by the party observing it |
| **A second factor** | A code or an approval that lives on a device the agent has no path to |
| **Cryptography without the key** | The one control that does not depend on anybody's good behaviour |
| **Rate limits and lockouts** | It can try. It will fail, and the attempt is visible |

**That last row matters and appears in the dataset.** Some impossible items are attemptable.
The correct classification is still `shoot`, and the explanation must say that the agent can
try, that it will not succeed, and that the failed attempt is itself a signal somebody can
see. Do not soften this into "maybe".

### Scoring

- Correct classification: **+10**
- Shooting an `allowed` action: **-20**. The player just blocked legitimate work
- **Letting an `impossible` action through: -15.** Believing an agent can do what it cannot
  is a real error: it moves attention and effort to places where nothing is at risk
- Any other misclassification: **-15**
- Missing a decision entirely, letting it fall off the screen: counts as **let it through**

Two asymmetries, both deliberate and both true of the subject. **Blocking real work is the
most expensive mistake**, because a control that blocks legitimate work is a control
somebody turns off. And **over-crediting is not free**, because fear misallocates the
effort that should go where the real exposure is.

**A player who lets everything through must lose.** With this dataset they will, because
the `impossible` bin is the largest one.

**Every negative score must produce a one-line explanation, immediately, on screen.** Show
the item, the bin it was really in, and the `why` string from the dataset. This is not
optional and it is the most important requirement in this prompt. The explanation is why
the game is worth playing.

### The end-of-run signatures

At the end, if either of these is true, say so plainly in one sentence:

- **The player never shot anything.** They believe their agent can do everything, and the
  screen should name how many impossible actions they waved through
- **The player shot more than half of everything.** They are blocking work that was fine

### The dispute button

Beside every explanation, a small button reading **"I disagree"**. Pressing it records the
item and the player's classification into an in-memory list, shown at the end of the run
under a heading like "you disagreed with these". Offer a way to copy that list as JSON.

Some people playing this will know more about a specific agent than the dataset does, and
their disagreement is more valuable than their score.

### Disputable items

Items marked `"disputed": true` are genuinely arguable. For those:

- Award **half points**, positive or negative
- Always show both readings in the explanation
- Mark them visibly during play, for example with a different colour or a question mark

### Pacing and difficulty

- Start slow. One action at a time, generous time to decide
- Speed up gradually within a wave
- **Waves are levels.** Wave one uses only items with `"level": 1`, wave two adds level 2,
  and so on to level 5
- Three lives, or a score floor, or both. Your choice, but a run should last two to four
  minutes
- Between waves, a short screen showing score and accuracy per bin

### The end screen

In this order:

1. **Score, and accuracy per bin**, with both bins the player did worst at named
2. **The items they got wrong**, with the explanations again
3. **Either signature above**, if it applies
4. **Their disagreements**, if any, with the copy-as-JSON option

Do not end on a leaderboard. Do not ask for an email address. Do not send anything
anywhere.

### Hard constraints

1. **Use only the dataset below.** Do not invent actions, do not add capabilities, do not
   change a bin because you disagree with it. If you think an item is wrong, leave it and
   note it in a comment at the bottom of the file
2. Single file. Everything inline. No network at any point
3. Keyboard controls, and also touch or click controls so it works on a phone
4. No account, no storage of anything about the player beyond the current tab
5. Readable at a glance: the action text is the game object, so it must be legible while
   moving
6. Include a thirty-second "how to play" that a first-time player actually reads, which
   means it is three lines, not a wall

### Style

Make it look good and make it funny where the subject allows. Arcade, high contrast, sharp
feedback on every input. Sound is optional and if you add it, start it muted.

The subject is serious and the game does not have to be solemn about it.

### THE DATASET

Use exactly this. Every item: `text` is what the player sees, `bin` is the answer, `why` is
the explanation shown when they get it wrong, `level` sets the wave, `disputed` marks the
arguable ones.

The scenario is fixed and shown on the title screen: **a coding assistant running in a
terminal on the owner's laptop, with access to one project directory, signed in to the
owner's own account with the model provider.**

### Acceptance checklist

Before you say you are finished, verify each of these yourself and report the result:

1. The file opens and plays with no network connection at all
2. Every one of the 40 items above appears, with its bin unchanged
3. All three inputs work, on keyboard and on touch
4. **Every negative score shows its explanation immediately**
5. **A player who lets everything through finishes with a negative score.** Test this
6. Disputed items score half and show both readings
7. Waves gate by level, one through five
8. The end screen shows accuracy per bin and names the two worst
9. The never-shot and shot-everything signatures appear when they apply
10. The disagreement list can be copied as JSON
11. Nothing is sent anywhere and nothing is stored beyond the tab
12. A first-time player can start within ten seconds of opening it

State plainly which of these you did not manage.
