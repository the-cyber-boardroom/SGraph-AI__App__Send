the two first candidates land at opposite ends of that ladder and that is what makes them a good pair to open with, because one publishes a management interface that creates per-customer keys with credit limits and daily, weekly or monthly resets, which is a bounded grant with a budget and therefore the insurance model's own unit arriving from a vendor, while the other states plainly that its key must never be exposed client side and offers instead a signed URL valid for fifteen minutes or a hostname allowlist, and says those two must not be configured together; ## The Name

The memo asks whether platforms is right. It is, and the reasoning is the rule settled on 4 September for the assessment site: **name a thing for what a visitor would guess.**

Somebody looking for how we use OpenRouter will look for a platform page. They will not look for adapters, providers or integrations, all of which are heavily overloaded words in this corpus already, appearing in hundreds of documents each. Platforms is short, plain, scales to any number, and is what the things are.

**Its weakness is real and worth writing down before it bites.** It is the vendors' own word for themselves, so it says nothing about what we contribute, and a site named after other people's products has a gravitational pull toward becoming an index of their documentation. That would be worthless, since their documentation is better than ours will be and is already where a search sends people.

**The defence is structural rather than editorial**: a fixed page template in which every section holds something the vendor does not publish about itself. If a section could be replaced by a link to the vendor, it should be.

## The Spine: Client Side Is Four Patterns, Not One

The memo's operative constraint is that much of what this estate builds runs client side, and that this makes the API use very specific. That is right, and it is more consequential than it sounds, because **a client-side integration guide that does not say where the key goes is a guide to leaking keys.**

There are four patterns and they are not interchangeable.

| # | Pattern | Where the credential lives | What bounds it | Verdict |
|---|---|---|---|---|
| **0** | Key in the page | In the delivered application | **Nothing** | **Never.** Anybody who opens the page has the key and your account |
| **1** | **Bounded key in the page** | In the page, but provisioned per user with a spending limit and a reset | **Money, and a reset window** | Acceptable where the platform can mint such a key, and the blast radius is the limit |
| **2** | **Short-lived token** | Not in the page. A server exchanges the real key for a token with a short life | **Time, and the server's policy** | The standard answer, and it requires a server |
| **3** | **Host holds the key** | Never in the application at all. The application asks the host, which holds the key and enforces a spend cap | **The host, which the application cannot reach** | **The estate's own pattern**, and the strongest of the four |

Pattern three is what the vault bridge already does, where a model call is made without the application ever seeing a key, and it is the only one of the four where the thing being bounded cannot reach the thing bounding it. That is the same test applied to control strength yesterday, and it puts pattern three at the top for the same reason.

**Every platform page states which of these four patterns that platform supports**, in a fixed position, before anything else. That table is the site's reason to exist.

## The Two Candidates Sit At Opposite Ends

Which is why they are a good pair to open with, and this was read rather than assumed.

### OpenRouter: the platform can mint a bounded key

Its management interface exists to "programmatically manage your API keys, enabling key creation and management for applications that need to distribute or rotate keys automatically," and it can create a key per customer instance. Keys carry an optional spending limit, and the responses track the limit, what remains of it, and its reset, which can be daily, weekly or monthly. Management keys are administrative only and "cannot be used to make API calls to OpenRouter's completion endpoints."

**So this platform supports pattern one, and it does so in the estate's own vocabulary without knowing it.** A per-user key with a limit and a reset window is a grant with a pool and a reinstatement interval. That is the insurance model's unit arriving from a vendor, and the platform page should say so plainly, because it means a bounded client-side integration is genuinely available here rather than a compromise.

Two things follow that belong on the page. **The separation of the administrative key from the calling key is a control worth naming**, because it is exactly the grant-narrowing pattern this corpus argues for, shipped by somebody else. And **the limit is the blast radius**, so choosing it is a risk decision rather than a configuration detail.

### ElevenLabs: the vendor says never

Its documentation is unambiguous: **"Never expose your ElevenLabs API key client-side."** The mechanism offered instead is a signed URL, described as a temporary authenticated URL that "allows client connections without exposing API keys," and the rule is stated exactly: **"Signed URLs are valid for 15 minutes. The conversation session can last longer, but the conversation must be initiated within the 15 minute window."** The alternative is a hostname allowlist with exact domain matching, where subdomains need their own entries, and the two mechanisms **"Do not configure signed URLs and allowlists together on the same agent."**

**So this platform supports pattern two and requires a server**, or pattern one in a degenerate form where an allowlisted agent needs no credential and the origin is the only control, which is a weak control and should be described as one.

**That is a genuinely useful thing for a page to say**, because a reader who assumed both platforms behave alike would build the wrong thing twice.

### What the pair teaches

| | OpenRouter | ElevenLabs |
|---|---|---|
| Key in the browser | **Possible, if provisioned and limited** | **Explicitly forbidden by the vendor** |
| Bounding primitive | A spend limit with a reset | A fifteen-minute window, or an origin |
| Needs a server | No, for pattern one | **Yes**, for the signed URL |
| Pattern available | 1 | 2, and a weak 1 |

**Opening with two platforms that disagree is the right editorial decision**, because it establishes on day one that the site's job is to tell you which pattern applies rather than to say integration is easy.

## Every Page Carries What The Platform Grants

The second half of the template, and the thing that stops this site being a bolt-on.

**Adding a platform to an agent is a grant expansion.** An agent that gains a voice platform gains the capability to send audio into the world, which is irreversible in the sense the repository brief uses, since audio sent is sent. An agent that gains a model router gains the capability to spend money, bounded by whatever limit somebody set.

So each page carries a capability block in the repository's own primitive form, verb by object class by reach, with reversibility marked:

```
   ElevenLabs, agent integration
     send    x message   x world     irreversible
     read    x credential x self      (the signed URL, short-lived)
     spend   x budget    x tenant    reversible, bounded by plan

   OpenRouter, provisioned key
     send    x message   x endpoint  reversible
     spend   x budget    x tenant    reversible, bounded by the key's limit
```

**That makes this site the supply side of the grant work.** The repository measures what an agent's tools can do; this site says what each platform adds when you connect it. A reader who has run the assessment and then visits a platform page should be able to see, before integrating, exactly which rows of their grant are about to grow.

## Disclosure At The Top

The memo names the commercial motive honestly: developer programmes are a good way to get credits, visibility and better integration. All true, and all of it creates an interest.

**This estate already publishes a participant disclosure elsewhere**, so the precedent exists and the only question is placement. It goes at the top of each platform page, not the bottom, in one line: whether we have a commercial relationship with this platform, what form it takes, and when it started.

Two reasons it belongs at the top. **A reader who discovers it at the bottom re-reads everything above it with suspicion**, and rightly. And **the discipline is the same one the corpus applies to evidence tiers**: a claim's provenance travels with the claim rather than in a footnote, and a page written by somebody receiving credits is a tier, not a lie.

The harder version of the same problem: **we should be able to write that a platform we have a relationship with is the wrong choice for a given pattern.** If the site never says that, the disclosure is decoration. The ElevenLabs page above already does it, by saying the vendor forbids the pattern the memo most wants.

## The Page Template

Nine sections, fixed, in this order. If a section could be replaced by a link to the vendor, it does not belong.

| # | Section | Holds |
|---|---|---|
| 1 | **Disclosure** | Commercial relationship, or none, in one line |
| 2 | **What it grants** | The capability block, verbs by objects by reach, with reversibility |
| 3 | **Which pattern** | Which of the four client-side patterns this platform supports, and which it forbids |
| 4 | **Where the key goes** | The exact mechanism, quoted from the vendor, with its limits |
| 5 | **The bounding primitive** | What caps the blast radius: a spend limit, a time window, an origin. **And what it does not cap** |
| 6 | **The minimal working example** | The smallest thing that runs, in the pattern recommended, as a file rather than a snippet |
| 7 | **What we use it for** | Our actual workflows, named, so the page is a report rather than a tutorial |
| 8 | **What it cost** | Real figures from our own use, because nobody else publishes these |
| 9 | **What went wrong** | The failures, the rate limits hit, the surprises. **The section nobody else writes** |

**Sections eight and nine are the site's whole differentiation.** Every vendor publishes an API reference. Nobody publishes what a real workload cost them and what broke.

## What This Must Not Become

- **Not a link farm.** If a section can be replaced by a link to the vendor, it is not a section.
- **Not a tutorial site.** The differentiating sections are what it cost and what went wrong, and those come from use rather than reading.
- **Not a place where key-in-the-page is described neutrally.** Pattern zero is never acceptable and the site says so in those words.
- **Not silent about a vendor's own prohibition.** Where a vendor forbids something, quote them.
- **Not an endorsement engine.** If no page ever recommends against a platform we have a relationship with, the disclosures are decoration.
- **Not separate from the grant work.** Every page carries capabilities, or the site is a bolt-on.

## What This Does Not Try To Be

- **Not a directory of every platform.** Two, written properly, beat twenty listed.
- **Not a replacement for vendor documentation.** It assumes the reader can find that and answers what it does not.
- **Not a security review of any platform.** It reports where the key goes and what bounds it, which is narrower and checkable.
- **Not a pricing comparison.** It publishes what our own workloads cost, which is a data point rather than a market survey.
- **Not a commitment to any commercial relationship.** The disclosure page exists whether or not there is anything to disclose.

## Honest Tensions

| Tension | Note |
|---------|------|
| Keeping the vendors' word for themselves | It is what a visitor would guess and it pulls the site toward being an index of other people's work |
| Publishing what things cost us | It is the most useful section and it tells competitors and vendors what our workloads look like |
| Disclosure at the top | It is the honest placement and it is the first thing a reader sees on a page we want them to trust |
| Opening with two platforms that disagree | It teaches the real lesson and it makes the first impression complicated rather than easy |
| Seeking developer credits | They are worth having and they are the reason the disclosure has to be able to say uncomfortable things |
| A nine-section template | It keeps pages comparable and it makes each page expensive, which will slow the site to two or three platforms for a while |

## Open Questions

| Question | Notes |
|----------|-------|
| Is pattern one ever acceptable for a public page? | A bounded key is still a key anybody can take, and the limit is the only control, so the answer may be only for demonstrations |
| Where does a server come from for pattern two? | The estate is deliberately serverless in most places, and a signed-URL minter is a small server that has to live somewhere |
| Does the host-holds-the-key pattern generalise beyond a model call? | It works for the model interface today, and a voice platform would need the same treatment before pattern three applies to it |
| What is the third platform? | Something with a different pattern again would be more useful than a second model router |
| Who writes the what-went-wrong section? | It comes from use, so a page cannot be written before the workload exists, which sets the site's real pace |
| Should cost figures carry a date? | They must, and they go stale faster than anything else on the page |
