# Treat Chrome's Sync Store As An Untrusted Transport, Because Its Own Documentation Steers Sensitive Data Away From It And It Is Not Stated To Be Encrypted: The Budget Is A Hundred Kilobytes Across Five Hundred Items, Which Makes This A Vault Key Manager First, And The Origin-Bound Idea Fails Its Own Enforcer Test

**version** v0.33.65
**date** 5 September 2026
**from** Human (project lead)
**to** Engineering, Product

**type** Dev brief

*Fourth of 5 September. The memo asks for a browser extension that manages secrets, stores them in the browser's own data so they synchronise across machines, asks for the smallest possible privileges, likes a right-hand panel, and proposes encrypting data per site so that only that site can reach it. The platform's documentation was read rather than recalled, and it changes two of those in ways worth knowing before any code: the sync store has a hard budget far smaller than most people assume, and the platform's own guidance points sensitive data somewhere else. The good news is that the estate has already solved the resulting problem once, in the product this extension would serve. Limitation: the storage and permission documentation was read on 5 September and no extension was built, so the quotas below are the platform's stated constants rather than measured behaviour.*

---

## What This Is

A design for a browser extension that manages vault keys and small secrets, with two corrections the platform imposes: **the memo's instinct to use the browser's synchronised store is right because it solves cross-machine synchronisation for free with no server of ours anywhere, and it comes with two constraints that decide the whole design, the first being a hard budget of a hundred and two thousand four hundred bytes in total across at most five hundred and twelve items with no item above eight thousand, plus write limits of a hundred and twenty a minute and eighteen hundred an hour, which is ample for vault keys and nowhere near enough for a general secrets manager holding certificates or long tokens, and the second being that the platform's own documentation does not state that this store is encrypted and explicitly recommends the session store instead when working with sensitive user data, which is the vendor steering us away from exactly the thing the memo wants to do; the resolution is not to argue with that guidance but to make it irrelevant, by treating the synchronised store as an untrusted transport that carries ciphertext and nothing else, which is precisely the position this estate already takes toward its own server, so the extension becomes the same architecture at a different altitude, with a passphrase that never leaves the device, a key derived from it, and a store that holds bytes nobody upstream can read; the memo's idea of binding a secret to a site so that only that site can reach it is attractive and fails its own test, because the thing enforcing the binding would be the extension, and the extension is the actor that holds every secret it manages, so an extension enforcing a rule about itself is the same weak shape this corpus rejected when an agent enforces its own mandate, and the honest version is that origin binding is a usability control that prevents mistakes rather than a security boundary that prevents attacks, and it should be labelled as one; what does hold is the permission discipline the memo asks for, since the platform provides permissions granted at runtime rather than at install, and its own guidance is to use them wherever the extension's functionality permits, which lets this ship with almost nothing at install and ask for one origin at the moment a user first uses it there; and the panel the memo likes is the right surface for one reason beyond taste, which is that a secrets manager should never be a page you navigate away from into the thing you are pasting into.** New contributions: **the budget stated as a design constraint rather than a footnote, the sync store as untrusted transport with the estate's own precedent, the origin-binding idea assessed against the enforcer test and downgraded honestly, the permission ladder from install to first use, and a build order that ships something useful before any of the hard parts.**

## The Two Constraints, Read Rather Than Recalled

### The budget is small and the design has to respect it

| Constant | Value |
|---|---|
| Total bytes in the synchronised area | **102,400** |
| Bytes per item | **8,192** |
| Maximum items | **512** |
| Writes per minute | **120** |
| Writes per hour | **1,800** |

**That is a hundred kilobytes, not a hundred megabytes.** For comparison, the same platform gives ten megabytes locally, and unlimited with a further permission, but the local area does not synchronise, which is the entire reason the memo wants the synchronised one.

What fits, and what does not:

| Content | Rough size | Verdict |
|---|---|---|
| A vault read key with a label and a note | 200 to 400 bytes | **Hundreds fit comfortably** |
| An API token | 100 to 2,000 bytes | Fits, dozens to hundreds |
| A certificate or a private key file | 2 to 8 kilobytes | **A handful, and then the budget is gone** |
| Anything larger | Over 8,192 | **Cannot be stored as one item at all** |

**So this is a vault key manager first and a general secrets manager second**, and saying so on the first screen is better than discovering it at item forty. A larger secret can be split across items, and that is a real technique with a real cost in write operations and complexity, so it belongs in a later increment rather than the first.

The write limits matter too: an autosave on every keystroke would exhaust a minute's budget in seconds, so writes are debounced and batched, and the extension must handle the quota error rather than assume it will not arrive.

### The platform steers sensitive data away from this store

The documentation does not state that the synchronised area is encrypted, and its guidance is explicit: **if you are working with sensitive user data, use the session store instead.** The session store is cleared when the extension is disabled, reloaded, updated, or the browser restarts, and it does not synchronise, so it is the opposite of what the memo needs.

**This is the vendor telling us not to do the thing we want to do**, and the response is not to argue with it. It is to make the guidance irrelevant.

## The Resolution: The Sync Store Is An Untrusted Transport

The estate has already solved this exact problem one level down. Its own object store holds encrypted objects and reads nothing; the client holds the key; the server is a place bytes go. **The browser's synchronised store becomes the same thing.**

```
   passphrase        entered by the user, never stored, never synchronised
        |
   key derivation    a slow function with a stored salt and stated parameters
        |
   vault of secrets  encrypted client-side, authenticated, one blob or a few
        |
   sync store        holds ciphertext. Sees nothing. Synchronises for free
```

Three properties follow, and they are the extension's whole security argument.

**Whether the store is encrypted upstream stops mattering.** The question the documentation refuses to answer becomes a question about somebody else's copy of ciphertext.

**The synchronisation is free and the trust is not extended.** Multiple machines, no server of ours, no account, and nothing upstream that is worth stealing.

**And the failure mode is honest and stated.** Lose the passphrase and the secrets are gone, because there is no recovery path that does not also create a party who could read them. That is the same trade the vault product already makes, and users of this extension are largely the same people.

One caveat that belongs on the page rather than in a footnote: **the extension itself, while unlocked, holds the plaintext.** A compromised extension, or a compromised browser profile, reads everything. Encryption at rest in a synchronised store protects against the store, not against the machine.

## The Origin-Binding Idea, Assessed Honestly

The memo proposes encrypting a secret against a specific site so that only that site can access it, and calls it a nicely decentralised approach. It is an attractive idea and it does not survive the test this corpus applies to every control.

> **A control bounds an actor only if it is enforced by something the actor does not include.**

Here the actor is the extension. It holds every secret it manages, it performs the decryption, and it decides which origin is asking. **So the extension enforcing an origin binding is the extension enforcing a rule about itself**, which is the same shape as an agent enforcing its own mandate, rejected repeatedly in this corpus and downgraded again in the maturity work two days ago.

What origin binding genuinely provides:

| Claim | Verdict |
|---|---|
| Only that site can access the data | **False.** The extension can, and the extension is the one enforcing it |
| A secret cannot be pasted into the wrong site by accident | **True, and valuable** |
| A compromised page cannot ask for another site's secret | **True, if the extension checks the requesting origin** |
| The blast radius of one bad page is one origin's secrets | **True, and this is the real benefit** |

**So it is a usability and blast-radius control rather than a cryptographic boundary**, and it should be described that way. Deriving a per-entry key from the origin and the master key is still worth doing, because it makes the accident impossible rather than merely unlikely, and because it means a future version that moves the decryption somewhere the extension cannot reach would already have the right shape.

**The honest sentence for the page: your secrets are bound to the sites they belong to, so this extension will not offer one site's secret to another. The extension itself can read all of them while unlocked.**

## Permissions: Almost Nothing At Install

The memo's instinct here is exactly right and the platform supports it. Permissions can be granted at runtime rather than at install, and the platform's own guidance is to use them "wherever the functionality of your extension permits, to provide users with informed control over access to resources and data."

| Stage | What is asked | When |
|---|---|---|
| **Install** | Storage, and the panel. **No host access, no tabs** | Nothing alarming on the install screen |
| **First use on a site** | That one origin, at runtime | When the user first asks for a secret there |
| **Never** | Broad host patterns, cookies, network interception | Not asked for, and the manifest shows that |

**The install screen is the extension's first and best security claim**, and one that asks for nothing is worth more than any amount of copy explaining why the broad request is safe.

There is a nice reflexive property here worth using in the product's own materials. **This extension is itself a subject for the grant work.** Its manifest is its grant, it is small by construction, and it can be probed and published as a profile in the repository like any other tool. An estate arguing that grants should be minimal should be able to point at its own.

## The Panel

The memo likes the right-hand panel and there is a reason beyond preference: **a secrets manager must not be a place you navigate away to.** The moment the user leaves the page they are working in, they have lost their context, and a popup that closes when it loses focus is worse still because paste flows involve focus changes.

The panel stays open beside the page, survives navigation, and is where the list, the search and the lock live.

## What It Does, In Order Of Value

| # | Capability | Why |
|---|---|---|
| 1 | Hold and synchronise **vault keys**, labelled, searchable, copy to clipboard | The memo's actual pain, and it fits the budget comfortably |
| 2 | **Lock and unlock** with a passphrase, with a timeout | Without this it is a plaintext list |
| 3 | **Origin binding**, as a mistake-preventer with honest wording | The memo's idea, correctly labelled |
| 4 | **Clipboard hygiene**: clear after a short interval, and say so | The most common leak from tools like this |
| 5 | Small secrets beyond vault keys, within the budget | The general case, bounded |
| 6 | **Budget display**: bytes used of the hundred kilobytes, items of five hundred and twelve | Because the ceiling is real and arrives suddenly |
| 7 | Export and import as an encrypted file | The recovery path that does not create a third party |
| 8 | Large secrets by chunking | A later increment, with its write-rate cost stated |

**Items one and two are the whole first version.** They solve the memo's stated problem and nothing else is needed to be useful.

## The Path To A User Area

The memo names this as preparation for people managing vaults, and a user area on the site. The extension is the right first step and it should not be built as if the user area is coming, because the two have different trust properties:

| | The extension | A hosted user area |
|---|---|---|
| Who holds ciphertext | The browser's sync, and the user's machines | A server of ours |
| Who could hold plaintext | The extension, unlocked | **Nobody, if the same discipline holds** |
| What is added | Nothing. It is a client | Sharing, teams, revocation, recovery conversations |
| What is risked | Little | **A great deal, and it must be designed with the same rule** |

**The one rule to carry across: whatever is built later must be able to say the same sentence, that the thing holding the bytes cannot read them.** The extension establishes that discipline cheaply, and a user area that quietly relaxes it would undo the argument the whole estate rests on.

## What This Must Not Do

- **Not put plaintext in the synchronised store.** The store is a transport and the documentation already says not to trust it with sensitive data.
- **Not claim that origin binding stops the extension reading a secret.** It does not, and saying so would be the exact overclaim this corpus keeps catching.
- **Not ask for broad host permissions at install.** One origin, at first use, or the install screen has given away the argument.
- **Not offer a recovery path that requires somebody else to hold a key.** Lost passphrase means lost secrets, stated plainly before the first secret is entered.
- **Not hide the budget.** A hundred kilobytes arrives without warning otherwise.
- **Not autosave on every keystroke.** The write limits are per minute and per hour and they are not generous.

## What This Does Not Try To Be

- **Not a password manager.** It holds vault keys and small secrets, and it competes with nothing.
- **Not a general secrets store.** Eight kilobytes per item and a hundred in total is the honest ceiling.
- **Not a security boundary against a compromised browser.** Encryption at rest protects against the store, not the machine.
- **Not a team product.** One person, their machines, their passphrase. Sharing is the user area's problem.
- **Not a claim about the platform's own encryption.** Its documentation does not say, and this design makes the answer not matter.

## Honest Tensions

| Tension | Note |
|---------|------|
| Using a store the vendor steers sensitive data away from | Encrypting first makes the guidance moot and a reader who knows the guidance will need the explanation |
| A hundred kilobyte ceiling | It is plenty for the real use case and it makes the product sound small |
| Origin binding as usability rather than security | It is the honest description and it is a weaker sentence than the one the memo hoped for |
| No recovery path | It is the only design without a third party who could read everything, and people will lose passphrases |
| The extension holds plaintext while unlocked | It is unavoidable in a client and it must be said rather than left for somebody to discover |
| Asking for nothing at install | It is the best security claim available and it means the first use has a permission prompt in it |

## Open Questions

| Question | Notes |
|----------|-------|
| One blob or many items? | One blob is simpler and rewrites everything on each change, which the write limits punish; many items leak structure through their keys |
| Does the item key leak anything? | A key named for an origin tells the store which sites a user has secrets for, even if the values are opaque |
| Which key derivation, with which parameters? | It has to be slow, stated, and stored with its salt, and the parameters age |
| How long is the unlock timeout? | Short is safe and annoying, and the annoyance is what makes people disable it |
| Should the extension publish its own manifest as a profile? | It should, and it is the estate's cleanest demonstration of a minimal grant |
| What happens when the quota error arrives? | It must be handled and shown, since a silent failure to save a secret is the worst possible bug here |
