# The Chat Shipped With Scoped Writes And A Detected Mode, The Host Refuses Any Other Path And The App Refuses First, The Model Interface Carries No Tool Field So The Loop Is Prompted Rather Than Protocol, And What Remains Is The Export As A Citation Artefact

**version** v0.33.64
**date** 4 September 2026
**from** Human (project lead)
**to** Engineering, Product

**type** Dev brief

*Third of 4 September, reissued. The chat now exists in the conformance vault: the manifest grants writes, directory creation and deletion under one path and nothing else, grants the model interface, and deliberately does not grant listening. The mode detection the specification asked for shipped, the scoped write shipped, and the export, pruning, publication and citation rendering did not, so this reissue describes what runs and specifies what is left. One thing the specification got wrong is corrected: the model interface carries no tool field at all, which changes how the tool surface is enforced and weakens one claim about it. Limitation: the chat's behaviour is read from the manifest, the chat directory's own readme and the app source in the vault, and was not exercised.*

---

## What This Is

A record of the chat as built and a specification for the three parts that remain: **the manifest is the design, because it grants file writes, directory creation and deletion under a single path and nothing else, grants the model interface for chat, models and usage, and pointedly does not grant listening, which is deny-by-default expressed as a document anybody can read before trusting the page; enforcement is doubled and the order matters, since the application refuses an unsafe path first, allowing only three extensions with no traversal under the one permitted directory, and the host refuses anything else regardless, which means the outer refusal sits outside the app's reach and is therefore a real boundary rather than a promise the app makes about itself; the mode detection shipped in the form the specification argued for, because a read-only clone cannot write to the vault at all and there the threads stay on the reader's device and the tab says so, which is a consequence stated rather than a menu offered, and it is the right shape because a mode picker would have offered choices that fail; the specification was wrong about one thing and the build found it, since the bridge's model interface forwards messages, a model, a token cap, temperature, top-p and a stream flag and nothing else, with no tool schema going out and no tool calls coming back, so the tool loop is not merely absent from the protocol, it cannot be expressed in it, and the loop the app runs is prompted and parsed rather than declared, which means the tool allow-list is enforced by application code for reads and by the host only for writes; that distinction matters for the claim this chat makes about the control it documents, because the write scoping is enforced from outside the app and is therefore a genuine boundary, while the read surface is enforced by the app about itself and is a weaker thing wearing the same word; and what remains is the half of the specification that carries the value, namely pruning, an export that is a citation artefact rather than a chat log, and a publication path with a reviewed diff, because a published vault's history is kept and a session written into it cannot be recalled from anybody who already holds the key.** New contributions in this reissue: **the manifest read as the design, the doubled enforcement with its order and its asymmetry, the correction that the model interface has no tool field, the consequence for the control claim, and the export specified as a citation artefact with its four parts.**

## What Shipped

| Element | As built |
|---|---|
| **Write grant** | Files, directory creation and deletion under one path. Nothing else |
| **Model grant** | Chat, models and usage. **Listening deliberately not granted** |
| **App-side refusal** | Only three extensions, no traversal, only under the permitted path, refused before the host is asked |
| **Host-side refusal** | Any other path refused outright, at a layer the app cannot reach |
| **Read surface** | Every file in the vault, both graphs, and the layer |
| **Mode** | A read-only clone cannot write at all, so threads stay on the reader's device and **the tab says so** |
| **Layout** | A thread index, one directory per thread with metadata and a transcript including tool calls and their results, and notes |

**The manifest is the document to read before trusting the page**, and it is short enough that anybody can. That is a security property, not a convenience: a page whose permissions fit on a screen can be judged, and one whose permissions are in code cannot.

### The doubled enforcement, and why its asymmetry matters

Two refusals, in order: the app refuses an unsafe path first, and the host refuses anything outside the grant regardless. The order is a courtesy and the outer refusal is the control, because **the app cannot turn off the host's refusal and can turn off its own.**

That produces an asymmetry worth stating plainly:

| Surface | Enforced by | Can the actor reach the enforcer? | Strength |
|---|---|---|---|
| **Writes** | The host, per the manifest | **No** | A boundary |
| **Reads** | The app, and the grant is the whole vault anyway | Yes, it is the app | An intention |

So when this chat claims to satisfy the control it documents, the claim is strong on writes and weak on reads, and it should be written that way rather than as one sentence.

## The Correction: There Is No Tool Field

The specification said the bridge runs no tool-calling loop, so the app must run its own. That was right about the conclusion and wrong about the mechanism, and the difference matters.

**The interface forwards messages, a model, a token cap, temperature, top-p and a stream flag. That is the whole surface.** No tool schema goes out and no tool calls come back. So the app cannot declare a tool list to the model in the protocol's own terms; it describes the tools in the prompt, reads the reply, and parses what looks like a call.

Three consequences.

**The allow-list is a parser, not a schema.** What the model may invoke is whatever the app's parser recognises and executes, which is a real allow-list and is enforced at a different layer from where a protocol would put it.

**A malformed or unrecognised call is a parse failure rather than a validation error**, which is a weaker signal and needs its own handling and its own log line.

**And the claim about tool authorization needs qualifying.** The specification claimed this chat satisfies the tool-authorization requirement non-vacuously because its tool list is graph queries rather than a shell. The list is still graph queries and that part holds. What does not hold is the implication that the surface is enforced the way a declared schema would be: **for reads it is the app enforcing a rule about itself, which is the same structure the corpus rejects when an agent enforces its own mandate.** The honest statement is that the tool surface is narrow by construction and enforced by application code, and that the write scoping is the part enforced from outside.

## What Remains

Three things, and they carry most of the value the memo asked for.

### 1. Pruning, with disclosure

A viewer removes turns before sharing. **A pruned transcript is an edited document**, so the artefact states how many turns of how many it shows. That is the same rule as marking a simulated acceptance indelibly distinct from a real one, and without it a prune is indistinguishable from a misrepresentation.

### 2. The export, as a citation artefact

The mechanism is a print view printed to PDF: no library, no external resource, which matters because the vault contract forbids external resources entirely, and it works from a read key with nothing written anywhere.

**A printed chat log is worth very little. A printed conversation in which every assertion points at a byte range in a hashed file at a named commit is worth a great deal**, and this vault is the one place that is possible, because the word graph addresses every requirement and the layer records every attestation with its tier.

| Part | Contents |
|---|---|
| **Header** | Title, vault name and id, the commit the app was reading, the standard's release, the date, and the mode the session ran in |
| **Body** | The turns, with every control, requirement or clause rendered as a citation, and every assertion drawn from vault data carrying the block id it came from |
| **Sources** | One row per cited artefact: identifier, source URL, commit, SHA-256, filtered to what this conversation touched |
| **Footer** | The pruning disclosure, the unofficial and derivative notice, and the licence |

### 3. Publication, behind a reviewed diff

Writing a session into a public vault is a one-way door. Revocation is not retroactive and history is kept, so a session published and later removed is still held by everybody who cloned the vault or holds the key.

**Therefore the control is a reviewed diff of the exact bytes, not a confirmation dialog**, because a dialog tests intent and the risk here is content: a name, a client, a pasted fragment.

```
   1. prune      the viewer removes turns; the app shows the count it will publish
   2. preview    the exact bytes of the file that will be written, rendered and scrollable
   3. redact     inline, on that preview, applied to the bytes
   4. confirm    one line stating the door: this becomes public and cannot be recalled
   5. write      one file, under the sessions path, and nowhere else
```

Step two is the control. Steps one and four are theatre, and useful theatre, but not the thing that prevents the harm.

## What This Must Not Do

- **Not publish without showing the bytes.** A confirmation dialog is not a control.
- **Not print a pruned session without saying so.**
- **Not claim the read surface is enforced from outside.** It is the app enforcing a rule about itself, and the write scoping is the part that is not.
- **Not present the model's account of its own tool use.** The app makes the calls and the app's record prints.
- **Not put a shell, an arbitrary fetch or a free-text query executor behind the parser.**
- **Not load an external resource.** The contract forbids all of them and the print view must work with nothing fetched.
- **Not write outside the one permitted directory**, which the host already enforces and the app should refuse first anyway.

## What This Does Not Try To Be

- **Not a general chat framework.** A handful of graph queries over one vault.
- **Not a replacement for the host's own panel**, which the sovereignty rail means a viewer can always restore.
- **Not a legal record.** A citable document with its provenance attached, derived from an unofficial catalogue.
- **Not a publishing workflow for anything but sessions.** One directory, one file type.
- **Not a claim that the prompted tool loop is as good as a declared one.** It is what the interface permits.

## Honest Tensions

| Tension | Note |
|---------|------|
| A prompted tool loop | It is the only loop the interface allows and it enforces the surface at a weaker layer than a schema would |
| Doubled enforcement | It gives a real boundary on writes and it invites the reader to assume the same strength on reads |
| A detected mode | It never offers a lie and it removes a control people expect to have |
| A reviewed diff before publishing | It is the honest control and it puts friction exactly where somebody is most eager to move fast |
| Pruning at all | It makes an export presentable and every prune is an edit of a record |
| Example sessions in a public vault | They are the best explanation available and each is permanently public from the moment it lands |

## Open Questions

| Question | Notes |
|----------|-------|
| Should a parse failure be shown to the viewer? | It is the prompted loop's version of a validation error and hiding it makes the surface look tighter than it is |
| Does the host's own panel keep a transcript the app could read? | If it does, some of this is simpler |
| What does a session cost, and who pays? | The model grant spends the vault owner's key, and a public vault with a chat has an economics question this brief does not touch |
| Can a viewer import an exported session? | Round-tripping would let people share sessions without publishing, which may be better than publication for most cases |
| Should the tool list carry a version? | It is an allow-list, allow-lists drift, and the export should print which one ran |
| Should redaction be recorded? | A redacted export that does not say so has the pruning problem in a worse form |
