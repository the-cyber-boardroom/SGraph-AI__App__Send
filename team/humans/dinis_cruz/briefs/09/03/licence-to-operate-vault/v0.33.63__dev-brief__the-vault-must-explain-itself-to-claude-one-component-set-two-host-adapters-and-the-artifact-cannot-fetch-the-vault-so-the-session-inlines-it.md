# The Vault Must Explain Itself To Claude: One Component Set With Two Host Adapters, A Kit With A Manifest So Components Can Be Picked Rather Than Rewritten, And The Load-Bearing Constraint That The Session Can Fetch The Vault While The Artifact It Publishes Cannot

**version** v0.33.63
**date** 3 September 2026
**from** Human (project lead)
**to** The agent that will build the vault, and Engineering

**type** Dev brief

*Third of 3 September, a memo conversion, and an addendum to the licence-to-operate brief written earlier today rather than a replacement for it. The memo asks whether a vault can carry, inside itself, the artefacts and the explanation a language model needs to rebuild the same environment in its own interface, and whether the vault can offer reusable interface components with instructions for their reuse. Both are yes, and the shape of the yes is decided by one constraint that was read from the artifact tool contract in force in this session rather than assumed. Limitation: that contract was read, not tested by publishing, and testing it is the first item on the acceptance script below, because a contract read is a weaker tier than a contract exercised.*

---

## What This Is

A specification for making the licence-to-operate vault self-describing, so that a person can paste one prompt into a session and end up with the same environment running in the model's own interface: **the memo's instinct is right and the mechanism is not a mount, because the two hosts sit in different network positions, since a session can fetch a published file and can be handed a vault through a read key or a zip, while an artifact the session publishes runs under a policy that blocks fetch to every host including the one the vault came from, so the session must read the vault into its context and emit a page with the data already inlined, which makes the workflow a transcription rather than a link and puts a size ceiling on it that the vault should respect by shipping a small bundle beside the full one; the two host contracts otherwise agree far more than they differ, since both demand a self-contained page with styles and scripts inline and no external resources, both forbid loading vault or artifact files declaratively, and both keep per-viewer state locally, which means one component set can serve both if the three real differences are pushed behind a thin adapter, namely how data arrives, where the run is persisted, and whether a small script allowlist exists; so the deliverable is a kit inside the vault, a folder of host-agnostic components with a machine-readable manifest naming each one's inputs, its outputs and the adapter calls it makes, two adapter implementations of about a page each, and a short document written for a model rather than for a person that says which adapter to use and why; the two-store design settled this morning turns out to have anticipated this exactly, because the vault holding the terms and the browser holding the run maps without modification onto an artifact holding inlined terms and localStorage holding the run, and a design that survives a host change unmodified is the graph work's own test for a fractal rather than a hierarchical structure; the prompt a person pastes lives in the vault as a file, in three variants for the three ways a model can be handed the vault, and each variant states what it needs and what it will do before it does it; and the honest problem is named rather than buried, because a prompt that instructs somebody's agent to fetch content the author controls and then build from it is the confused deputy this corpus has documented repeatedly, so the vault ships as data that a model reads rather than as instructions a model obeys, every component is inspectable, and the prompt asks the person to read what they are pasting.** New contributions: **the two network positions as the load-bearing constraint, transcription rather than mounting as the workflow, the three-difference adapter, the kit manifest so components are picked rather than rewritten, the small bundle for the context ceiling, the two-store design shown to survive a host change unmodified, and the confused-deputy problem stated with its mitigations.**

## The Constraint That Decides The Design

The memo asks whether the model can replicate the vault's environment in the panel on the right of its own interface. It can, but not by loading the vault, and the reason is worth stating precisely because it will surprise anybody who has not read the artifact contract.

**A session and the page it publishes occupy different network positions.**

| Actor | May fetch the vault | Evidence |
|---|---|---|
| The session | **Yes.** It has a fetch tool, and it read four sites while this brief was being written | Exercised, repeatedly, today |
| The page the session publishes | **No.** The publishing policy permits scripts from a short list of content delivery hosts and blocks everything else, naming fetch, requests and sockets among the blocked, with no visible error | Read from the tool contract in force in this session on 3 September. Not yet tested by publishing |

So there is no arrangement in which a published page reaches back to sgit.ai for a policy file. **The session must read the vault's files into its own context and write a page with those files already inlined.** The workflow is a transcription, and three consequences follow that the memo does not anticipate.

**There is a context ceiling and a page ceiling.** Everything the page shows must first fit in the session's context and then fit in the published page, which is capped at a size the contract states. The vault should therefore ship a **small bundle**, a single JSON file holding one agent, one scenario, one policy and the fixtures, sized so that a session can read it in one call and inline it without difficulty, beside the full data the vault app itself uses.

**A transcription is a snapshot.** The page carries the terms as they were on the day it was published. That is not a defect if it is labelled, and the bundle should carry the vault's commit reference so the page can print which version of the terms it is showing.

**The failure is silent.** The contract says blocked requests produce no visible error, so a component that tries to fetch will simply render empty. The adapter must never attempt a fetch in the artifact host, and the acceptance script must include a page that would have fetched, to confirm it does not.

## The Two Host Contracts, Compared

The comparison is the useful part, because the agreement is larger than the difference.

| Requirement | Vault app host | Artifact host | Same? |
|---|---|---|---|
| Self-contained page | Required. "No external resources at all, no CDNs, fonts, or analytics" | Required in practice; only a short script allowlist and one font host are reachable | **Yes** |
| Styles and scripts inline | Required | Required for everything not on the allowlist | **Yes** |
| Loading its own files declaratively | Forbidden. No stylesheet, script or image tag against vault paths | Not applicable; the page has no sibling files | **Yes, in effect** |
| Images and media | Inline, or through the bridge | Data URIs only; media hosts are blocked | **Yes** |
| Reading data | `sg.vfs.readText(path)`. "fetch() of vault paths does not work" | Inlined at authoring time. Fetch blocked to every host | **No.** Difference one |
| Per-viewer state | `sg.state`, device-local, no vault commit | `localStorage`, per artifact origin, per viewer | **No.** Difference two, and they behave alike |
| External script | Forbidden entirely | Four hosts allowed, exact versions pinned | **No.** Difference three |
| Readiness signal | Post `sg-app-ready` or the host overlay stays | Not required | Minor |
| Document skeleton | The page is a full document | The file is wrapped at publish time, so it carries no doctype, html, head or body tags of its own | Minor, and it bites |
| Theme | The host's chrome | Three states, with an explicit attribute and a system default, and a page must define both palettes | Minor, and it bites |

**Three real differences and two that bite.** The three are data arrival, persistence and the script allowlist. The two that bite are the document skeleton and the theme, because a component written for one host and pasted into the other will look wrong in a way that has nothing to do with its logic. Both are handled by the adapter owning the page shell and the palette, so components never write either.

## The Answer: One Component Set, Two Adapters

```
   components/           host-agnostic. no fetch, no sg.*, no localStorage
     board.js              the six panes
     grant-mandate.js      the delta, shaded
     policy.js             bands, limits, pool, reserve
     insurer.js            pool, premiums, payouts, the line
     ledger.js             checks, claims, verdicts
     workflow.js           the chain, lit one node at a time
     verdict.js            the amount check, ported from the pack
     scope.js              the mandate allow-list check
        |
        |  every one of them takes data in and returns markup and handlers.
        |  none of them knows where the data came from or where state goes.
        v
   host/
     host.vault.js         read: sg.vfs.readText     state: sg.state      shell: full document
     host.artifact.js      read: an inlined constant state: localStorage  shell: no doctype, palette tokens
```

The adapter surface is deliberately tiny, because a large one would leak the host into the components:

```
   host.readJson(path)        -> Promise<object>
   host.getState(key)         -> object | null
   host.setState(key, value)  -> void
   host.ready()               -> void          no-op in the artifact host
   host.env()                 -> { name, writable, commit, tier }
```

Five calls. **A component that needs a sixth is a component that has learned something about its host, and the fix is to move that knowledge into the adapter.** Both adapters wrap their reads and writes in a guard and return a usable empty value, because the storage in one host can be absent and in the other can throw.

**This is the two-store design from this morning, unchanged.** The vault holds the terms and the browser holds the run; in the artifact host the terms are a constant the session inlined and the run is in localStorage. Neither the verdict function nor any pane changes a line. A structure that survives a host change without a new format or a special case is what the graph work calls fractal rather than hierarchical, and the vault should say so in the kit's own documentation, because it is the clearest small demonstration of that test the estate has.

## The Kit, And Its Manifest

The memo's second question is whether the vault can offer components a model can reuse, with an explanation of how. The explanation must be machine-readable or it will not be read, so the kit carries a manifest.

```
kit/
  kit.json              the manifest
  components/*.js       as above
  host/*.js             the two adapters
  bundle-small.json     one agent, one scenario, one policy, the fixtures, plus the commit
  FOR-CLAUDE.md         written for a model, not a person
  examples/
    artifact-minimal.html   the smallest working page, already inlined
    vault-minimal.html      the same, for the vault host
```

`kit.json` names, for each component: its file, one line on what it renders, the data keys it requires, the adapter calls it makes, the state keys it owns, its approximate size, and which other components it needs. A session picks components against that manifest rather than reading every file, which is the difference between the kit being usable and being merely present.

`FOR-CLAUDE.md` is a short document addressed to a model, and its whole job is to answer four questions in order: which host am I building for; which adapter do I therefore use; which components do I need for what the person asked; and what must I inline. It should be readable in one pass and should not restate anything `kit.json` already says.

**Ship the two minimal examples as working files, not as snippets in prose.** A model that can copy a page that already works will produce a working page; a model assembling one from a description will produce a plausible one.

## The Three Routes In, And What Each Costs

The memo suggests downloading a zip or cloning from the site. There are three routes and they are not equivalent, so the prompt comes in three variants and each states its own requirement.

| Route | How | Needs | Cost |
|---|---|---|---|
| **Fetch the published bundle** | The session fetches one URL and gets `bundle-small.json` and the kit | Nothing but a fetch tool | Lowest. The likely default, and it works in a plain chat session |
| **Clone with a read key** | The session uses the sgit tooling and a published read key | The tooling installed, and a shell | Highest fidelity: the real vault, its history, every scenario |
| **Attach a zip** | The person downloads the vault export and attaches it | Nothing. Works with no network and no tooling | Manual, and the version is whatever was downloaded |

**Publish the kit and the small bundle at plain URLs alongside the vault**, because the cheapest route is the one most people will take and it should not require any installation. The read-key route stays the one that gives a session the whole vault including its history, and it is the route that matters for anybody who wants to change the terms rather than only view them.

## The Prompt

It lives in the vault as `for-claude/PROMPT-fetch.md`, `PROMPT-clone.md` and `PROMPT-zip.md`, and each is short enough to paste. The fetch variant, as a shape rather than as final wording:

> Read the kit manifest and the small bundle at these two URLs. They contain a set of interface components, two host adapters, and one agent's grant, mandate and policy with a scenario. Using the artifact adapter, build me a page that shows the board and lets me click through the scenario. Inline the bundle; do not fetch anything from the page you build, because the page cannot fetch. Tell me which components you used and which version of the terms you inlined.

Three properties of that shape matter and should survive any rewording. **It names what it will read.** **It states the constraint the model would otherwise discover by silent failure.** And **it asks for the version back**, so the person can tell a stale page from a current one.

## The Problem To Name Rather Than Bury

A prompt that instructs somebody's agent to fetch content the author controls and then build software from it is, structurally, the confused deputy this corpus has documented repeatedly, and it is the mechanism behind the Convincing Email in one of the games written last week. It would be poor form to specify this workflow without saying so.

Four mitigations, and they are design constraints rather than reassurances.

**The vault ships data, not instructions.** `bundle-small.json` is grants, mandates, policies, scenarios and fixtures. `FOR-CLAUDE.md` explains a contract. Neither should contain anything phrased as an instruction to the reading model about anything other than assembling a page, and a reviewer should check that before publication.

**Every component is inspectable and small.** A person who wants to know what they are about to run can read a file of a few hundred lines. Size is a security property here.

**The prompt tells the person what it does before they paste it.** The variants are short for that reason.

**The page has no capability worth stealing.** It fetches nothing, holds no key, and writes only to its own origin's local storage. The worst outcome of a compromised bundle is a wrong picture, which is a real harm for a teaching artefact and a small one for everything else.

There is one more, which is that this vault is about exactly this problem. A demonstration of grant, mandate and licence that arrived through an unexamined paste would be teaching the opposite of its content, and the kit's own documentation should make that joke before a reader does.

## The Acceptance Script

The kit is not done until this passes. The first step is the one that turns a contract read into a contract exercised.

| Step | Do | Expect |
|---|---|---|
| 1 | Publish a page that attempts a fetch of the vault and reports success or failure on screen | It reports failure, or renders empty with nothing in the console. **If it succeeds, this brief's central constraint is wrong and everything below changes** |
| 2 | Publish `examples/artifact-minimal.html` unchanged | The board renders with inlined data, in both themes |
| 3 | Open `examples/vault-minimal.html` in the vault host | The same board renders, reading through the bridge |
| 4 | Diff the two examples | They differ only in the adapter import and the page shell |
| 5 | Click the scenario through in the artifact, then reload | The run persists in local storage; the terms are unchanged |
| 6 | Paste the fetch prompt into a fresh session with no other context | It produces a working page and names the components and the commit it used |
| 7 | Paste the clone prompt into a session with the tooling | It produces the same board from the real vault |
| 8 | Run the fixtures in both hosts | The verdicts agree, case for case, and agree with the pack |
| 9 | Break the bundle deliberately, removing a required key | Both adapters render an honest empty state naming the missing key, rather than a blank pane |

Step 4 is the one that proves the adapter split is real rather than aspirational, and step 6 is the one the memo actually asked for.

## What This Does Not Try To Be

- **Not a replacement for the vault app.** The vault app is the full thing with every scenario and the history behind it; the artifact is one agent and one scenario, transcribed.
- **Not a live connection.** A published page is a snapshot of the terms, labelled with the commit it came from.
- **Not a general component library.** The kit serves this board. Generalising it before a second board exists would be inventing requirements.
- **Not a claim about every model's interface.** The contract read here is the one in force in this session; other tools that publish pages have their own, and the adapter is where those differences would go.
- **Not a security boundary.** The mitigations above reduce a real risk and do not remove it, and a person pasting a prompt is trusting the author.

## Honest Tensions

| Tension | Note |
|---------|------|
| Transcription rather than mounting | It is the only thing the contract permits, and it means every published page ages the moment the terms change |
| A small bundle beside the full data | It makes the artifact route work and it creates a second copy of the terms that can drift from the first |
| Two adapters | It keeps components honest and it doubles the surface where a host quirk can hide |
| Publishing a prompt for other people's agents | It is the point of the exercise and it is the confused deputy, and the second does not stop being true because the first is |
| The contract was read, not tested | It is the strongest evidence available without publishing, and step 1 exists because that is not strong enough |
| A kit before a second consumer | The manifest is worth writing now and the generalisation is not |

## Open Questions

| Question | Notes |
|----------|-------|
| How small is small enough for the bundle? | Small enough to read in one call and inline without crowding the page budget. A target should be measured rather than guessed |
| Does the artifact host allow the fixtures to run at all? | It should, since they are pure computation, and step 8 confirms it |
| Should the page be able to export its run? | An export as text the person can copy back into a session closes the loop without any network, and it is a short addition |
| Which components does the games' board need? | EXCESS and CAPTIVE want the same insurer and ledger panes, which is the first real test of whether the kit generalises |
| Do the three prompt variants stay in sync? | Three files that say almost the same thing drift. One file with three sections may be better |
| Should the commit reference be verifiable? | Printing it is easy and proving it is not, and the honest version says which of the two the page is doing |
