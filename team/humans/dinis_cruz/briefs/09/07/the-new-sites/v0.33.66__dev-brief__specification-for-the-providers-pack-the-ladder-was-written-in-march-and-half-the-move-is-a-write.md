## What This Is

The specification for the pack that will build the providers site, and the two findings that change what the pack should say: **the memo asks for a briefing pack for a site with one page per provider, OpenRouter first, whose content is largely refactored out of the tools site because the material there is powerful but hard to use and carries little context, and it states the pattern every provider page should follow as three tiers of consumption, being guidance and tools usable straight from the raw page, tools that become powerful with browser local storage, and tools that become very powerful with vaults; the first finding is that this ladder is not new, because a dev brief of 6 March specified an OpenRouter model manager with exactly two of those tiers named as standalone mode with no vault and no account where notes and ratings live in local storage, and vault mode where the same things live in an encrypted vault, and it went further than the memo does by listing what the tool holds at each tier, which makes this the fifteenth instance of the corpus proposing already-specified work and means the pack's first job is recovery rather than invention; the second is that the third tier is not a plan but a shipped mechanism whose organising sentence is that the key belongs to the vault rather than to the app or the page, with the app never holding a credential and the host holding the key, the model allow-list, the spend caps, the consent prompt and the cost reconciliation, and with the read-only case failing by construction rather than by a policy check because the key is sealed under something derived from the write key; the sharpest thing in that mechanism is a comment in its own source saying the built-in limits are bounds against accidents rather than security and that the enforceable cap is the upstream key's own credit limit set when the key is minted, which connects directly to the finding of 5 September that this first provider can mint a per-customer key with a spending limit and a reset, so the two halves of a real bound sit in two documents and have never been put in one sentence; the memo's complaint about the tools site is recorded four times over fourteen months in the project lead's own words, most precisely that the user has to know which page to go to, that each page has its own header and its own save flow, and that there is no shared state, no unified cost tracking and no common vault context, which means the pack is not being asked to fix a discoverability problem but a composition one; and because this is a move rather than a build, the pack must use the discipline the corpus already established for exactly that shape, where moving and deleting are separate steps in separate reversible commits, where anything found unused during the move is written down rather than removed, and where a section records the things that look retirable but are load-bearing along with what blocks each one.** New contributions: **the March specification recovered and mapped onto the memo's ladder, the three tiers grounded in what ships at each one with their documented failure modes, the accident-bound finding paired with the provisioned-key finding to give one enforceable cap, the naming decision revisited honestly with the rule left unchanged, the pack's file list and the contents of each numbered part, and the move-then-delete discipline applied to a cross-repository migration.**

## The Name Changed, And The Rule That Chose It Did Not

The memo corrects itself mid-sentence, from platforms to providers, and that correction supersedes the recommendation made on 5 September. **It should be recorded as a change rather than absorbed silently**, and the honest account is that the rule stayed the same while the set it was applied to narrowed.

The rule settled on 4 September is to name a thing for what a visitor would guess. On 5 September the set was described as the platforms this estate builds on, and platforms won. **The set here is narrower**: these are the services that serve models, and the word for that in this field is provider. A visitor looking for the OpenRouter page is looking among providers.

**The codebase already agrees.** The word appears as a term of art in exactly this sense: a constant named for providers holds two entries, one for OpenRouter and one for a local runner, and the vault's own configuration file carries a field recording the provider as OpenRouter with a comment noting it is the only one so far. **A site called providers whose first page is OpenRouter is consistent with the vocabulary the code already uses.**

**There is one real collision and it should be disarmed on the first page rather than argued about later.** The corpus's own narrative sense of provider is a customer who distributes capability to the people they serve, which is how the 7 June brief on distributing keys to child vaults uses it, and there is a heavily used compound in the identity sense as well. **So the site needs one sentence saying which provider it means**, and the disambiguation is cheap because the pages themselves are unambiguous.

**Platform was the weaker option for a second reason worth recording.** It appears far more often across the corpus but almost entirely as a generic noun, and it is not a class name or a schema field anywhere. **A word that means everything cannot name a site.**

## The Ladder Was Written For This Provider On 6 March

A dev brief of 6 March 2026 specifies an OpenRouter model manager as a standalone tool, and it contains the memo's ladder with the tiers named:

> **Standalone mode (no vault, no account)** with user notes and ratings saved in local storage, working as a pure static page. **Vault mode (with an SG/Send vault)** where notes, ratings and preferences are saved to an encrypted vault.

**And it is more specific than the memo about what the tool does**, listing a model catalogue with filtering by capability, price, provider and context window, a cost calculator answering what a given number of tokens in and out would cost, a comparison table, price history, a free-model spotlight, per-model notes and ratings and use-case tags, an A and B comparison across models, and a capability matrix.

**A second brief of 31 March** goes further again, specifying five components by name for usage, models, key management, logs and balance, assembled into a user dashboard, an admin console and a model comparison tool, with an explicit distribution argument that the comparison tool needs no account and therefore reaches the whole of that provider's user base.

**None of it was built.** The reality index lists four active tools on that site and none of these is among them; the recorded disposition from March is that the model manager is a separate product and not blocking. **So the pack's first section is a recovery exercise**, and the two March briefs plus the June key-acquisition brief are its input rather than its background.

## What Each Tier Actually Is

The memo states the ladder as a pattern. Each rung already has a settled meaning, a shipped mechanism or a documented failure mode, and the pack should inherit all three rather than restate the pattern.

### Tier one: the raw page, and it has a constitution

The tools site's own pack states the constraint as a rule with a named exception:

> **No local storage.** Browser storage is not available in all contexts. Use in-memory state. **Exception: tools that explicitly need persistence.**

**That rule is the tier one and tier two boundary, already ratified.** Alongside it sit vanilla JavaScript only, no build step, client-side only, and privacy by default. **The pack should adopt these unchanged**, because they are what make a tier-one tool embeddable anywhere, including inside a page that forbids storage.

**So a tier-one page is: guidance a person can act on, plus any tool that is a pure function.** A cost calculator is tier one. A model comparison is tier one. Anything that has to remember is not.

### Tier two: a shipped primitive, a documented convention, and four ways it breaks

**The primitive exists.** Device-local app state is namespaced per vault and per app entry path, capped at sixty-four kilobytes per key, needs no permission grant, and works on a read-only open. **And its documentation already contains the tier two and tier three test**, in a sentence the pack should quote rather than paraphrase: if losing it when the user switches browsers would be fine, use device state; **if losing it would be a bug, write it into the vault.**

**The naming convention exists by practice rather than by rule**, with a prefix, kebab case, and a colon for sub-namespacing, and there is a single file described as the source of truth for every storage key the loader uses, including the doctrine that the vault key is per tab while the access token is deliberately shared across tabs. **The pack should write the convention down**, since nobody has, and this site will add keys to a shared origin.

**Four failure modes are documented and every one of them will be met by a tools site.** A sandboxed or opaque-origin frame throws on access rather than returning nothing, which is why every accessor in the loader swallows the exception. A real shipped bug corrupted a stored token through an encoding fault. A real incident lost a user's token because they opened a second browser. And the quota is a few megabytes per origin **shared with every other tool on that domain**, which is a direct consequence of putting many tools on one site.

**One specified and unbuilt component belongs in the pack's scope discussion**: a component for viewing and managing what is cached locally, recommended in March as a first-class shared component rather than something owned by one tool. **If tier two is a pattern across many providers, that is the shared piece.**

### Tier three: the key belongs to the vault, and this ships

This is the strongest thing in the ladder and it is not a proposal. Its organising sentence, from the authoring documentation:

> **The key belongs to the vault, not to the app and not to the page.** It lives inside the permission floor, sealed to the vault owner. Apps send messages and get text back; they never hold a credential.

**What the host holds rather than the app:** the key, the list of models the app may use, the spend caps checked before the call rather than after, the consent prompt, the capability check against the live model catalogue, and the cost reconciliation. **What the app gets** is a small surface for asking what is available, listing models, reading usage, and holding a conversation, with typed error codes for every refusal.

**Two properties deserve to be quoted in the pack because they are the argument.** The read-only case fails **by construction rather than by a policy check**, because the key is sealed under something derived from the write key, so a session without one cannot decrypt it however the checks are written. And an app's own manifest can make consent stricter and never weaker, on the stated ground that **a limit the app author chooses is not a limit**, which is this estate's enforcer test appearing for the third time in a week.

**The honest limitation must travel with it**, and the pack should carry it in the same paragraph rather than a footnote: the key still lives in the vault, so sharing the vault key shares the credential with anybody who can open it, and a vault with a key configured should be treated as a vault that carries a secret. **The fix for that is specified and unbuilt**, being short-lived budget-capped tokens so the vault holds a reference rather than a key, and it is described in its own source notes as the commercially load-bearing piece.

## The Real Bound Comes From The Provider, And Two Documents Each Hold Half Of It

This is the finding worth putting on the first page of the OpenRouter section, because it exists nowhere as one statement.

**The vault's own limits are not security, and its source says so.** The defaults cap a session at one unit of currency, two hundred calls, eight thousand tokens per call and two concurrent requests, with a comment beside them recording that these are bounds against accidents rather than security, and that **the enforceable cap is the upstream key's own credit limit, set when the key is minted.**

**And this provider can mint exactly that.** The finding recorded on 5 September is that its management interface creates a key per customer instance carrying an optional spending limit whose remaining balance and reset interval are readable, on a daily, weekly or monthly cycle, with the administrative key unable to make model calls at all.

**Put together, that is one enforceable statement**: the vault bounds accidents and the provisioned key bounds loss, so a vault configured with a provisioned key rather than a personal one has a blast radius equal to that key's limit and a recovery interval equal to its reset. **That is the insurance model's own unit arriving from a vendor**, and it is the strongest thing this site can say about any provider. **It should be the template's headline field.**

## The Tools Site's Problem Is Composition, Not Discoverability

The memo says the material there is powerful but hard to use and lacks context. **That is recorded four times over fourteen months**, and the most precise statement is worth carrying into the pack because it names the fix:

> The user has to know which page to go to. They navigate between separate URLs. Each page has its own header, its own layout, its own save flow. **There is no shared state, no unified cost tracking, no common vault context.**

**So the pack is not being asked to make things easier to find.** It is being asked to give a set of tools one context, which is the same defect the sites report named on 20 August in a different place and the same one the games brief this morning had to design around. **A providers site that is a better-organised list of the same isolated tools has not fixed anything.**

**The unifying context here is obvious and should be stated as the site's spine**: a provider page's tools share a key, a spend ledger and a model catalogue. **That is the shared state whose absence is the complaint.**

## This Is A Move, So Move And Delete Are Separate Steps

The corpus has done exactly this shape once and the discipline it produced should be copied verbatim.

> **Step one, move**, with zero behaviour changes, verified by identical output. **Step two, delete**, in separate commits, each reversible, each with a reason.

with the instruction that matters most for a job like this: **if you find something unused during the move, write it down rather than deleting it.** The deletion candidates go in their own file as input to a later, separate series, and every entry carries positive evidence of non-use, the date that evidence was verified, and the exact action to take.

**And the inverse section is the one that saves the project**: a list of things that look retirable but are load-bearing, each with the named blocker that must be resolved first.

**Two facts make this harder than the precedent and the pack must open with both.** The site whose content is moving **lives in a different repository**, so the move crosses a boundary the earlier extraction did not. And everything currently shipped points at the development host rather than production, with a recorded note that unpinned third-party code from that host runs in the same context as an injected key, described as the most significant residual risk in its pack and a conscious decision. **A migration that quietly promotes those references to production is a change of risk posture, not a change of address.**

### What the acceptance tests should be

| # | Test | Why |
|---|---|---|
| 1 | A tier-one tool renders and works in a context where storage throws | It is the boundary rule, and the failure is silent otherwise |
| 2 | The same tool at tier two remembers across a reload and loses nothing important when it does not | The stated tier-two test, applied |
| 3 | At tier three the app never sees a key, verified by attempting to read it and requiring a refusal | The existing suite already probes this; the site should too |
| 4 | The page states the provisioned-key limit and reset as a field, not as prose | It is the enforceable bound and the site's best sentence |
| 5 | Every tool on a provider page shares one key, one ledger and one catalogue | The composition fix, checkable |
| 6 | Nothing was deleted from the origin site in the same commit as a move | The discipline, mechanically checkable |
| 7 | Every cross-link points at a page rather than a domain | The family's known defect, from 20 August |
| 8 | Every page is reachable as markdown at the same path | The convention this family has and does not advertise |

## What The OpenRouter Page Carries

The template from 5 September stands and the ladder is added to it, so the page has the nine sections already specified plus three tier bands and one recovered section.

**Inherited unchanged:** the disclosure at the top, the capability block saying what the provider grants, which client-side pattern it supports and which it forbids, where the key goes quoted from the vendor, the bounding primitive and what it does not bound, a minimal working example, what we use it for, what it cost us, and what went wrong.

**Added:** the three tiers, each with at least one working thing rather than a description.

**Recovered:** the four key-acquisition journeys already written in June, being bring your own, create one with links and screenshots, retrieve one from a password manager, and use one we provide, under the June brief's own success condition that the section ends when the user has a key in their browser. **That is tier-one content, already authored, and it is the natural first page of the site.**

## What This Does Not Try To Be

- **Not the pack.** It specifies what the pack must cover and hands the writing to the agent with the two repositories in front of it.
- **Not a redesign of the tools site.** It says what moves and insists that removal is a later, separate act.
- **Not a key-management design.** Provisioning, markup and billing are blocked elsewhere on questions this brief does not touch.
- **Not a second naming argument.** The name is decided; what is recorded is why the rule produced a different answer for a narrower set.
- **Not a claim that all three tiers suit every tool.** Some tools are honestly tier one forever, and the template should let a page say so.

| Tension | Note |
