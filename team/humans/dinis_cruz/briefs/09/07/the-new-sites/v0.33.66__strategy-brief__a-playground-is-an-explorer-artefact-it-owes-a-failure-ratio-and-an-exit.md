## A Playground Is A Role In This Organisation, And It Has An Exit Condition

The memo describes a phase. **The corpus defines it as a role, with a mission, a measure and a handover.**

The Explorer role, defined on 14 February, operates in the genesis and early custom-built stages: **discover, experiment, build first versions, figure out what works.** Its culture line is move fast, capture everything, hand over when ready, then move to the next frontier. **And it has a measure that matters for a public playground:**

> **Failed experiment ratio.** Some percentage of experiments should fail. If nothing fails, we are not exploring, we are building the obvious, which is not exploration.

**That has a direct design consequence.** A site that publishes only the things that worked is not a playground; it is a portfolio. **These sites should carry what was tried and rejected**, which the 17 May prototypes brief already asked for in its own terms, noting that negative results are as valuable as positive ones. **A page recording that a capability was tested and found not good enough for a named purpose is the most credible page on a provider site**, and no competitor's marketing will contain one.

**The exit condition is the part the memo does not state and the corpus is firm about.** From 4 June:

> The experimentation is a typical Explorer. They are where you discover the brief. **The mistake is to think that is the final product.** Anybody who spends a lot of money on tokens has an engineering problem. They are using Explorer-type code and solutions in a commodity environment.

with the progression that a capability starts in English and ends in code as its scope narrows. **So the success test for these sites has two halves rather than one.** The memo names the first, which is others using it. **The second is that things graduate off them**, and a playground where nothing ever moves to the product side has become the expensive habit the 4 June brief warns about.

**The cost curve is already written too**, in an article describing exactly the memo's rhythm: start expensive because you do not yet know which parts matter, understand the full picture, then curate, then compress. **Spending freely in this phase is correct and is supposed to end.**

## The Vendor Gap Argument Was Written On 6 March, And One Part Of The Memo Is New

The observation that the tool gets built because the provider's own offering does not fit the workflow is in the corpus, about this provider, in the brief recovered yesterday:

> Choosing the right model is currently guesswork. **There is no good way to** filter models by capability, compare prices, or track which models worked and which did not. **The human has handwritten notes in a physical notebook about model experiments. That should be in a tool.**

and its distribution argument is the memo's success measure stated first:

> **This is a tool that everyone who uses this provider needs, not just our own users.**

with acceptance criteria that include deploying it a second way to demonstrate it works independently of our infrastructure and to make it easy for others to fork, and running it locally from a downloaded file with no dependencies.

**The same complaint appears about a much larger vendor**, in a brief that turns it into a rule after counting the clicks it took to read a log file through the vendor's own console: **our tools should get from intent to answer in two clicks.** And in another observing that an access console shows lists rather than relationships, which is a statement about what a general-purpose interface cannot do rather than about how well it was built.

**What is new here is the explanation.** The corpus argues speed, focus and the impossibility of forking a team, and it argues that incumbents cannot serve every niche. **It has never argued that a vendor with millions of users is structurally prevented from shipping the sharp version.** That argument is worth keeping and worth stating precisely, because it predicts where gaps will be rather than only observing that they are there: a vendor's interface must serve the median of a very large population, must not break for anybody, and must be supportable by a team that cannot know every workflow. **A tool built for one workflow by the person who has it is a different object, and it is allowed to be wrong for everybody else.**

**That framing also sets the honest limit on these sites.** They are not better than the vendor's environment. **They are narrower**, and narrowness is the whole of the advantage.

## The Vault Runs Away From The Site, Read-Only, And Its Own AI Stops

The memo's strongest architectural claim is that a vault is by design something that runs outside the website. **That is true, it ships, and it is narrower than the sentence implies.**

**What ships**: a static mode in which the same vault-app HTML runs against the live backend or a plain static file host, transparently, because file identifiers are derived on the client so a read is a deterministic fetch with no listing call. The app never learns which it is talking to.

**What survives the trip**: opening, browsing, reading, listing, history and large reads, with batch reads becoming parallel fetches that return the same shape.

**What does not**: every write, every append, and vault creation, all refused as read-only. **And the one that matters most for these sites**: a vault app's own model calls fail on a static host when the key is sealed to the owner, because that seal is derived from the write key and a read-only session does not have one. **So the most impressive kind of demo, a vault that thinks, is precisely the kind that stops working when it travels**, unless the key is published alongside it, which is a decision with an obvious cost.

**Two further constraints belong on the page that makes this claim.** The static tree is a snapshot frozen at export, so the update check re-reads a frozen reference and honestly reports no change. And the exporter that produces the deployable tree **does not exist**; the runtime half shipped on 30 June and the packaging half is still proposed.

**The reason to keep making the claim anyway is the best sentence in the corpus about it**, from 12 May: a partner can publish their vault, host it anywhere, and never depend on us being online, so **if we disappear, their site keeps working.** That is worth stating with its limits attached rather than without them.

## Two Providers, Two Resale Prohibitions, And One Planning Rule

The memo wants a developer account and more credits so it can run more experiments. **That is the right ask and the framing around it needs one correction, which is cheap to make now and expensive later.**

**The first provider's terms already prohibit reselling access.** That was found on 6 August, with enforcement already visible as blocked requests, and **it invalidated a commercial mechanism designed on 27 July.** The project lead's own recorded reaction is the useful part: it is good that it happened before the thing was built.

**The second provider's grant is generous and asks the same question in its own terms.** It offers thirty-three million characters over twelve months, described as more than six hundred and eighty hours of agent audio and stated as over five and a half thousand dollars of value, covering the full platform including speech, transcription, cloning, sound effects, music and video. Its published questions include whether grants can be resold or exchanged for cash, and its terms after the twelve months are a separate matter.

**So the rule to plan on is one sentence: a grant is a research subsidy, not inventory.** It funds the art of the possible, the quality assessment and the demonstrations, and it cannot fund anything that looks like reselling capacity. **Anything built on these sites that would only work if credits could be passed on should be identified now**, because the last time that assumption went unexamined it cost a design.

**One consequence for the pages themselves.** The disclosure rule settled on 5 September, that a commercial relationship goes at the top of the page rather than the bottom, **now has something to disclose**, and a granted account is exactly the kind of interest that reads badly when discovered at the end.

## What The Second Provider Actually Offers

Read from its documentation today, because the memo asks what is possible.

| Area | What is there |
|---|---|
| **Speech from text** | Four current models. The newest supports more than seventy languages with a five thousand character limit; a conversational variant is quoted at roughly two hundred and eighty milliseconds; an older multilingual model covers twenty-nine languages at ten thousand characters; and a low-latency model is quoted at roughly seventy-five milliseconds across thirty-two languages with a forty thousand character limit |
| **Transcription** | A separate capability area |
| **Voices** | A library of more than three thousand shared voices, instant and high-fidelity cloning, and design of a voice from a text description |
| **Transformation** | Voice changing, voice isolation, voice remixing, dubbing |
| **Generation** | Sound effects, music, text to dialogue, image and video including avatars |
| **Agents** | A conversational agent product, which is what the grant's hours are denominated in |
| **Alignment** | **Forced alignment**, which returns timing for the words in an audio file |

**The last row is the one to build on first and it is the one nobody notices.** The memo wants programmatic video with a narrative workflow. **Alignment is what turns narration into a timeline**: it gives the moment each word is spoken, which is precisely what animation, captions and slide transitions need in order to be driven by the audio rather than guessed alongside it. **A narrated page whose text highlights in time with the voice is a small demonstration that is disproportionately convincing**, and it needs alignment rather than a better voice.

**The latency figures are the second thing to test rather than trust.** A quoted seventy-five milliseconds is a model claim and the number a user experiences includes the network and the browser. **Measuring it is exactly the kind of thing these sites exist to publish**, and no vendor page will carry a third-party measurement of its own latency.

## The Video Workflow Reverses An April Decision, And That Should Be Explicit

This corpus already specified document-to-video, on 8 April: extract the topics from a document, generate an image and a narration script for each, synthesise the audio, and assemble a short video, with every intermediate asset kept. **It names speech synthesis as the missing component.**

**And a week later a full client-side stack was chosen for it**, with a browser speech model, a browser avatar renderer, canvas animation and in-browser encoding, under an argument stated as plainly as it could be: all running in the browser, no server, no subscription, **zero marginal cost per video.**

**In that document, this provider appears only as a price comparison.** It is the sole mention in the entire repository.

**So using it for narration is a reversal, and it is a legitimate one that should be recorded rather than drifted into.** The trade is real in both directions: a hosted voice brings quality, languages, cloning and alignment that a small browser model does not have, and it brings a key, a per-character cost, a network dependency and a demo that stops working on a static host. **The honest resolution is probably both**, with the hosted voice for the pieces that are published and the browser model for anything that must run offline or inside a vault somebody else opens.

**And there is a symmetric gap worth naming.** The platform has a shipped call for listening, which records audio and returns text with the audio never entering the app frame. **There is no counterpart for speaking.** That is the obvious first integration, it fits the existing bridge exactly, and the same custody argument applies: the app asks for speech and receives audio, and never holds the key.

## What Success Should Mean

The memo says the measure is others using it. **The corpus has a sharper version of that test and a harder one.**

The sharper version, from a brief about a different product: the acid test is not that the thing is usable but that **other teams choose to use our primitives for their own purposes, beyond the one we built them for, because they are that good.** Applied here: the measure is not visits to a provider page but somebody forking a tool from it for a workflow we did not anticipate.

The harder one is the corpus's own test of whether an open-source claim is real: **can a motivated team take it and, without purchasing anything, solve a real problem end to end?** If not, the openness is marketing rather than product. **For these sites that is a demanding bar**, because the most useful tier needs a vault and the most impressive demonstrations need a key.

**And one smaller test, from a translation tool brief, is the one to put on the wall**: can we get a single external person to contribute? That is the bar.

## What This Does Not Try To Be

- **Not the pack.** The previous brief specifies what the pack must contain; this one says why the sites exist and what they must not become.
- **Not a quality assessment.** Every capability figure here is the vendor's own, and the point of the sites is to replace those with measurements.
- **Not a commercial plan.** It records a constraint that two providers now impose and leaves the model to the work already blocked elsewhere.
- **Not a criticism of the vendors.** The argument is that a general-purpose interface cannot be narrow, which is a structural claim rather than a complaint.
- **Not a decision on the video stack.** It names the April choice, the reversal implied here, and the case for keeping both.
