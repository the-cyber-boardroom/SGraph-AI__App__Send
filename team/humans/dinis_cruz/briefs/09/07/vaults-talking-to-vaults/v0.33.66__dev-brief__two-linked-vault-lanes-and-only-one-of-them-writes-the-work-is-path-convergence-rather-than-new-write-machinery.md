## What This Is

The feature the memo asks for, placed against the three separate places this corpus has already been, and the one correction that changes what should be built: **the memo describes vault-in-vault as read-only today and names the missing piece as the ability to write into a linked vault from the parent, and that is accurate about the tree view and wrong about the platform, because there are two entirely separate linked-vault implementations that share no code, one being the `.link.json` composite adapter that renders a virtual folder in the main vault tree and is read-only, the other being the kernel mount reached through `sg.vault.mount` which spawns the child in its own null-origin kernel, relays the operation over a signed channel, and has performed parent-to-child writes since 28 May with tier gates, broker mediation, byte-exact unit tests and a passing browser end-to-end; the memo's own architectural instinct, that there should be an abstraction layer identifying parent vault versus vault-in-vault with every write or batch of writes as one commit, is not a proposal but a description of what the kernel lane already does, so the work is convergence of two paths onto one rather than new write machinery, and this was recognised on 31 May in a scoping document whose stated origin requirement is the memo's requirement almost word for word, which sets out eight work items and six blocking decisions, concludes that the capability is roughly eighty per cent built, and is catalogued in the reality index as proposed feature P-279 with the composite adapter still present and still hardcoded read-only on the current head, making this the ninth instance of this corpus proposing work it has already specified; what the reading adds beyond locating the plan is three things the plan does not say, the first being that the composite lane's read-only behaviour is not enforced anywhere and is instead an accident of path resolution, since every mutation is passed straight through to the root vault with no mount check and no path rewriting and fails only because the virtual mount path does not exist as a real folder, which means a parent vault that happens to contain a real folder at the mount path will accept the write and land it silently in the parent instead of the child, a corruption case with no test covering it; the second being that the blocking security decision, whether to store a writable child key at rest in the parent as `rw-links.json`, may not need to be taken at all, because a mechanism shipped on 8 June puts a backend access token inside the child vault at `.vault/access-token.json`, encrypted under the child's own read key and beneath the protected floor so no app can reach it, which is already read by both shells on open and is not read by the child kernel, so teaching the child kernel the path both shells already run would make a child self-authorising and leave the parent holding only a read key; and the third being that four properties the memo's collector depends on are genuinely unspecified everywhere in the corpus, namely which branch a relayed write commits to, whether anything in the child's history records that a different vault authored the commit, what happens when a vault is mounted by two parents at once, and whether a mount cycle terminates.** New contributions: **the two lanes distinguished and the memo's claim resolved against each, the 31 May scoping located and its status verified as unbuilt on the current head, the read-only guard shown to be accidental with its silent-corruption case named, the embedded access token connected to the deferred credential decision, the four unspecified properties of a collector topology stated, and a test design in four layers with the adversarial cases the existing suites do not cover.**

## There Are Two Lanes And They Share No Code

This is the finding everything else depends on, so it belongs first.

| | **Composite lane** | **Kernel lane** |
|---|---|---|
| Reached from | The main vault tree view | A vault app, through `sg.vault.mount` |
| Orchestrator | `CompositeDataSource` | `KernelParent` and the relay |
| Link record | `<name>.link.json` plus `.vault/owner/ro-links.json` | A mount registered at runtime |
| Child opened with | The child's **read key only** | The child's **full writable key** |
| Write into the child | **No** | **Yes, and tested byte for byte** |
| Security stack | **None.** An in-process read splice | Broker policy, custody gate, protected floor, audit log |
| Access mode | Hardcoded `'ro'`, never set otherwise | Per mount, resolved from the credential tier |

**The memo is describing the first column and the platform's answer lives in the second.** Both are real, both ship, and a reader who knows only one of them will reach the wrong conclusion about how much work this is.

The kernel lane's write path is not a sketch. The parent resolves the path against its mount table, applies a credential tier in which read and list need nothing, write needs a standing credential and delete needs per-request elevation, passes the operation to the broker, and relays it to the child. The child then applies its **own** policy, refuses if its data source is not writable, writes the file, and pushes on its own connection to the server. **The parent never writes across the boundary**, which was the design goal stated in May, and the effective authority is the intersection of what the parent was granted and what the child permits, so a credential is necessary and not sufficient.

## The Requirement Was Scoped On 31 May And Catalogued As P-279

The scoping document states its origin requirement in a single line:

> "Kernel A's App writes to a file in Kernel B, where Kernel A has rw access to Kernel B, with both vaults visible in the main tree view."

That is the memo, recorded ninety-nine days earlier. The document's own status line reads **"PROPOSED, does not exist yet"**, and its bottom line is that the requirement is **"~80% built"**, because "the relay already performs the A to B rw write end-to-end and is tested" and "the work is not new write machinery; it is collapsing the two vault-access paths into one."

It resolves the design question the memo leaves open, and it resolves it against the obvious answer. The obvious move is to teach the composite adapter to write. The document rejects that explicitly: **"We are not bridging two paths, we are deleting one."** The reasoning is that every security-critical behaviour, meaning broker policy, the custody gate, floor enforcement, push on write and the audit log, exists only on the kernel path, so a second independent access path is a place that logic can drift or be bypassed, and the relay is the younger caller, which makes collapsing onto it cheapest now.

Its work breakdown is already written: a single access facade so callers never branch on root versus mount, promotion of the app shell to the only shell with the tree as a render mode, every mount moving to the kernel parent, the deleted adapter, the `rw-links.json` credential store, tier resolution, a custody classification for operator-initiated writes, the chip that tells the truth about access, and tests. Its blocking decision is the one named below.

**It is catalogued.** The reality index carries it as **P-279, Kernel Path Unification and CompositeDataSource Retirement**, with the scoping document cited. **It is still not built**: on the current head the adapter file is present, `access: 'ro'` is still at line 75, the read-only wrapper is still constructed at line 217, and no access facade exists.

**So the first action is not to design this. It is to decide whether P-279 is being done, and if so to sequence it.**

## The Read-Only Guard Is An Accident, And It Can Corrupt The Parent

This is the finding that is not in the plan, and it is the one to act on first because it is a present defect rather than a missing feature.

The composite adapter does not refuse writes inside a mount. It has no mount check on the write path at all. Every mutation is a blind pass-through to the **root** vault with the path unchanged, and the writable flag is delegated to the root, so with a writable parent the editor's save, rename and delete controls are **enabled** inside a linked vault.

What stops the write is that the mount path is virtual. A save into the mount asks the parent vault for a folder that does not exist there, the lookup returns nothing, and the operation throws a folder-not-found error. **It fails closed by coincidence rather than by design.**

The consequence is a case nobody has written down. **If the parent vault contains a real folder whose path matches the mount path, the lookup succeeds and the write lands in the parent, shadowing the child.** No error is raised, the editor reports success, and the file is in the wrong vault. Nothing in the adapter prevents a link file and a real folder of the same name from coexisting, and the test suite, which covers the composite lane in thirty-nine assertions across scan, splice, lazy expand, key prompting and read transparency, **never attempts a write through a mount**, so neither the intended failure nor the corruption case is pinned down.

**Three things follow, in this order.** Add a failing test that writes into a mount and asserts where the bytes land. Add an explicit mount check that refuses with a real error rather than relying on path resolution. Then tell the truth in the interface, because a disabled control is a better answer than an enabled control that throws.

## The Blocking Credential Decision May Already Be Solved

The scoping document's gating decision, D1, is whether to store a **writable** key at rest inside the parent vault as `rw-links.json`, described as the original reason read-write was deferred and as requiring sign-off before merge. The credential issuance question is deferred in two other places as well and is marked as a gate before any real-data pilot.

**A mechanism shipped on 8 June appears to dissolve it.** A vault can carry a backend access token at `.vault/access-token.json`, encrypted under that vault's own read key and placed beneath the protected floor specifically so that an app running inside the vault cannot read it through the bridge, while the trusted shell can. Its purpose at the time was that a link containing only a vault key opens **writable**, because the authority to write is carried by the vault rather than by the link.

Both shells already run this path on open. **The child kernel does not.** It receives its vault key, access token and endpoint by message from the parent, and has no embedded-token read of its own.

So the proposition is one change with a large consequence: **have the child kernel read its own embedded token, exactly as the two shells already do, before falling back to a token supplied by the parent.** If it holds one, a parent that possesses only the child's **read key** obtains a **writable** child, because the write authority never left the child. There is then no writable key at rest in the parent, `rw-links.json` is not needed for this case, and D1 is not a decision that has to be taken before the feature can ship.

**It should be checked rather than believed.** Two properties need confirming before this is relied on: that a child kernel opened with a read key can decrypt its own token file, which the read key is what encrypts it, and that the token so obtained authorises writes on the child's own connection. Both are testable in an afternoon and both are cheaper than the sign-off they would replace. **State it as a hypothesis in the work item, not as a settled design.**

## Mapping The Relationships

The memo asks for the relationships mapped. Here they are, with what is true of each edge today.

```
   VAULT A                     VAULT B                     VAULT C
   the source                  the collector               the processor,
                                                           holds the code
      |                            ^                            |
      |   EDGE 1                   |                            |  EDGE 2
      |   append lane              |                            |  linked mount
      |   works today              |                            |  read-only today
      +----------------------------+                            |
                                                                |
                                   ^                            |
                                   +----------------------------+
                                     relayed read and write:
                                     ships in the app lane,
                                     absent from the tree lane
```

**Edge 1, A into B, works and has an unusual property worth stating.** The append lane authorises on a bearer token whose hash the owner has anchored in the vault's configuration. The appender can write and can do nothing else: it cannot list, read, purge or configure, those verbs being gated by two different credentials. The write endpoint deliberately carries no platform access token at all, because the appender is an outside party with no account. **And the appender is blind.** The filename is assigned by the server, is never returned, and there is an explicit test asserting that no identifier comes back, so the writer cannot enumerate, confirm or address what it wrote. There is a naming trap here: the mechanism is described as write by signature and the token is conventionally derived from a public key, but **no signature is verified anywhere on that path**, and the server compares a hash of a bearer secret. Anything written about this feature should say bearer token, or the first reader who looks will think a signature check is missing.

**Edge 2, C into B, is the whole of the ask**, and its state is the two-lane split above: the operation exists on the app lane and the surface the memo wants it on is the tree lane.

**The separation the memo wants, code in one vault and data in others, is the corpus's own answer to a different question.** The 16 August finding, restated on 20 August, is that minimal permission cannot be expressed as a permission, because possession of a key is access, so it is delivered as **topology**, meaning more vaults rather than finer grants. The collector's shape is that principle applied to a pipeline, which is a reason to expect it to hold rather than a coincidence.

## Four Properties A Collector Needs That Nothing Specifies

These are absent from all of the prior art, and each one bites specifically in the memo's use case rather than in the original medical-console case the design was written for.

| Property | State | Why the collector makes it matter |
|---|---|---|
| **Which branch a relayed write commits to** | Unspecified. The child reuses the shipped sync machinery and pushes on its own connection, and nothing names a branch | A collector writing continuously into shared data vaults is exactly where an unnamed default branch becomes a contention point |
| **Whether the child's history records who wrote** | **No.** The only cross-vault provenance is an in-memory broker log **in the parent**, and its persistence is explicitly deferred | For a **log collector** this is the property that matters most. Vault B cannot show that vault C authored a commit, so the audit trail lives in the wrong vault and does not survive a page reload |
| **A vault mounted by two parents at once** | Never discussed anywhere. The corpus covers one parent with many children and states the inverse is prevented by construction | The collector's B is written by A through the append lane and by C through the mount, and a relayed write racing a local write in the child has no stated semantics |
| **Mount cycles** | No cycle detection, no depth limit, no hop counter | Unbounded recursion is the explicit design intent and a pipeline is exactly the shape that accidentally closes a loop |

**The second row is the one to fix inside this work rather than after it.** A commit trailer naming the originating vault and the mount is a small addition to a write the child is already performing, and it is what turns the parent's ephemeral broker log into evidence that lives with the data. Without it, the collector can be built and cannot be audited, which is the wrong way round for this estate.

**The first row has a settled answer to inherit rather than invent.** The contended object on a push is the branch reference and not the file, so two writers touching entirely different files still collide there, and compare-and-swap on push rejects the loser cleanly instead of clobbering. That is shipped behaviour and it makes concurrent collectors safe at the push, but it does not decide which branch they push to.

## Commits And Batching Are Already Decided

The memo's instinct that every write or batch of writes is one commit is the right one and it is also three months old. A commit queue with a configurable timer window was specified on 26 May, its brief opening with the observation that commit-per-change was already the shipped behaviour and already a problem, for the three reasons the memo is circling: race conditions, a network-call explosion, and a chatty environment producing bursts. The suggested window is ten to fifteen seconds, and **zero preserves commit-per-change**, which is what makes it a setting rather than a migration.

**One consequence should be surfaced rather than defaulted.** A window collapses repeated edits to the same file into one commit, which is desirable for an editor and lossy for a log collector, where each append may be the thing being recorded. **The collector's lanes should be able to choose a zero window while the editor keeps a non-zero one**, and if that is a per-vault rather than per-application setting today, it is a small change and should be made in this work.

## The Test Design

The memo asks for this explicitly and it is the right instinct, because the failure modes above are all reachable by a test that nobody has written. Four layers, and the adversarial cases are the point.

**Layer 1, unit, on the access facade.** A path under the root routes locally, a path under a mount routes to the relay, and the caller cannot tell. A read-write mount resolves a writable child kernel and a read-only mount resolves a read-only one. The mount table resolves longest prefix, and a path that is a prefix of a mount but not inside it does not resolve.

**Layer 2, unit, on the credential store.** A full key offered at link time writes the read-write record and can reopen a writable child. A read-only record still opens read-only, so existing links are untouched. And, if the embedded-token hypothesis holds, a child holding its own token opens writable from a read key alone, with the fallback to a parent-supplied token exercised separately.

**Layer 3, integration, two vaults in memory, and this is where the real assertions live.**

| # | Case | Assertion |
|---|---|---|
| 1 | Write under a read-write mount | The bytes are in the **child's** store and **absent from the parent's** |
| 2 | Write under a read-only mount | Refused at the child, not at the parent, with a read-only error |
| 3 | **A real parent folder shadowing a mount path** | **Refused. This is the corruption case and it must fail loudly** |
| 4 | Write outside the child's own granted paths | Refused by the child's policy even though the parent was granted the write |
| 5 | Any path containing a protected segment | Refused before mount resolution is even attempted |
| 6 | The child's push fails | The error surfaces to the caller rather than being swallowed |
| 7 | Two writers, one child, different files | Both land, and the loser of the push race retries rather than clobbering |
| 8 | The full pipeline: A appends to B, C mounts B, C reads and rewrites | The round trip completes and the append lane's blindness is preserved |
| 9 | **A mounts B, B mounts A** | **Terminates. No test exists and no behaviour is specified** |
| 10 | Read parity, every existing composite read reproduced through the relay | Identical results, this being the main regression risk of retiring the adapter |

**Layer 4, browser end-to-end.** Add a read-write link, edit a file inside it in the tree, save, reload, and confirm the change is in the child vault and not the parent. The prior art is blunt about why this layer is not optional: two commits in the May work claimed a phase complete when its probe had never run, and the note recorded then is that **tests passing on a synthetic harness do not make a feature exist for users.**

**Cases 3 and 9 are the two that should be written first**, because both describe behaviour nobody has ever observed and one of them is a live defect.

## Build Order

| # | Step | Why here |
|---|---|---|
| 1 | The mount-write test and an explicit refusal in the composite adapter | A present defect with a silent-corruption case, fixable in isolation, no refactor needed |
| 2 | Tell the truth in the interface about access, at link time and in the tree | Shippable immediately, and it stops a full key being silently downgraded without the user knowing |
| 3 | **Test the embedded-token hypothesis** | It is cheap, and if it holds it removes the decision that gates everything after step 5 |
| 4 | The access facade, root only at first | No behaviour change, and it proves the interface before anything moves |
| 5 | The tree as a render mode of the single shell | The structural step, and the read-parity suite is what makes it safe |
| 6 | Every mount through the kernel parent, and delete the adapter | The convergence, and the second read path stops existing |
| 7 | The credential store and tier resolution, in whichever form step 3 leaves standing | Either a read-only record plus a self-authorising child, or the read-write record and its sign-off |
| 8 | Commit attribution across the boundary, and the collector's commit window | The two additions this use case needs that the medical-console case did not |
| 9 | The custody classification for operator-initiated writes | An explicit decision, and the prior art is emphatic that it must be classified rather than assumed |

**Steps 1 to 3 are worth doing even if P-279 is not scheduled**, which is the argument for putting them first: two are defect fixes and the third is an experiment that changes what the rest costs.

## One Security Item This Feature Makes Worse

Worth naming because it is catalogued and it sits directly under this work. Inner and mounted sub-vault content currently inherits a sandbox capability allowing popups to escape the sandbox, which is recorded as a finding with a fix that requires distinguishing a root-vault render from a mounted one at four separate mount sites. **The index notes that the fix is easier after the path unification**, because unification is what makes that distinction clean. So the ordering is fortunate rather than a conflict, but a collector that mounts many data vaults multiplies the exposure while it stands, and it should be closed in the same programme rather than left.

## What This Does Not Try To Be

- **Not a design for the write path.** The write path exists and is tested; this describes reaching it from a different surface.
- **Not a substitute for the 31 May scoping.** That document holds the work breakdown and the decisions, and this one locates it, checks its status and adds what it does not cover.
- **Not a security review of the kernel lane.** Its invariants are stated elsewhere and are inherited here rather than re-derived.
- **Not a schema for the collector's data.** It maps the vault relationships and the operations across them, and says nothing about what a log record contains.
- **Not a claim about anything built in the last fortnight.** The published head is 25 August, and work newer than that is invisible to this reading.

## Honest Tensions

| Tension | Note |
|---------|------|
| Deleting a working read path | It removes a place security logic can be bypassed, and it puts a shipped, in-process fast path behind a message round trip |
| The embedded-token hypothesis | It would dissolve the blocking decision, and building on an unverified hypothesis is how a gate gets skipped rather than passed |
| Fixing the corruption case first | It is the right order for a defect, and it spends effort on an adapter the plan intends to delete |
| Commit attribution across the boundary | It is what makes a collector auditable, and it puts a fact about vault C into vault B's history, which is a small disclosure between vaults that were meant to be separate |
| A per-lane commit window | A collector needs every append, and an editor needs batching, so the setting has to be finer than the vault |
| Structural refactor before a demonstrable use case | The plan is right that the relay is young and callers are few, and the collector is the first caller that would prove the shape is correct |
