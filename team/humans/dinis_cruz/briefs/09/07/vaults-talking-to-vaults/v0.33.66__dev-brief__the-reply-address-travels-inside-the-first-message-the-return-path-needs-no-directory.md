## What This Is

The feedback and reply architecture the memo asks for, placed against a question this corpus has had open since 19 August and a design that answers it from 3 June: **the memo proposes reusing the telemetry channel from the game vault to the stats vault to carry feedback rather than only actions, meaning a rating per question, an opinion, a challenge to a question, and something closer to a conversation with the data, then observes that the channel is one way, that two-way would have to be broadcast so everybody receives the same thing, that addressing an individual would need an identifier for a user or a session, and concludes that the eventual answer is a vault per user; the last of those is already this corpus's own conclusion, reached on 3 June for a rollout of roughly a hundred users where the requirement was stated as each user needs a vault and formalised as a provisioning routine, which makes it the twelfth instance of proposing settled work, and the community feedback shape is the thirteenth, since a brief of 22 June already proposed a published vault per subject with a separate vault collecting comments and votes from people who prefer not to go on record; what the reading changes is the middle of the memo's argument, because the dilemma it sets up between broadcast and per-user addressing was dissolved in June by a mechanism that is better than either, namely that a sender's first message carries its own public key and its own append token inside the sealed payload, so the receiver acquires the reply address by decrypting rather than by looking anything up, the conversation is self-bootstrapping, no directory exists to be stolen, and the player's own generated keypair is already its lane address without asking anybody; the second correction is that broadcast is not the weak fallback the memo treats it as but the cheap and private option, since the game vault is a published vault every player already opens, a broadcast is one commit whose content objects are then served from the edge with a one-year immutable cache and no function invocation at all, and the argument for preferring it is one this corpus already made on 20 August about notaries, that publishing an answer to a place the reader fetches cannot meter and cannot surveil and that these turn out to be the same property rather than two, which means an addressed reply is the option that costs privacy rather than the option that gains capability; the third finding is that the feedback this memo wants to carry has a producer already specified, since the arcade brief of 5 September put a disagreement button beside every explanation precisely so that a player who knows more than the dataset becomes a contributor rather than somebody who quit annoyed, and this memo is the transport that button has been waiting for; and the blocker is neither the transport nor the topology but the client sealing layer, which is proposed rather than shipped and has sat in the parked list since 19 August, because without it nothing can be sealed to a recipient and the return path cannot be built at all.** New contributions: **the parked return-path question answered from the corpus's own June design, the broadcast case reframed as the private option with the notary argument imported, three reply tiers costed and compared by what each leaks rather than by what each can do, feedback distinguished from telemetry as a different record with different retention, the identity question shown to be the introduction of the platform's first client-side identifier rather than a small addition, and the static-hosting constraint that silently disables the whole channel.**

## This Answers A Parked Item

The memo's question is on the standing list, and it has been there a while. The day index of 19 August records it as new, in these words: **the return path for an issued certificate, with the note that a write-only lane covers ingress only.** It was carried unchanged into 20 August and has appeared in every parked list since.

The brief that raised it put the problem the way the memo puts it: **the return path is the one direction the write-only lane does not cover**, and its companion added the sharper statement that **the return path needs its own answer rather than inheriting the ingress design**.

So this is not a new question with a game attached. It is the same question arriving from a second domain, which is usually the point at which it gets answered.

## The Return Path Was Designed On 3 June

And the design removes the dilemma the memo sets up, because it needs neither a broadcast nor an assigned identifier.

The mechanism is one sentence: **a sender's first message carries, inside the encrypted payload, its own public key and its own append token.** The receiver decrypts, and now holds everything needed to reply, meaning it can encrypt to that key and append to that lane. The dev pack states the consequence plainly, that **the conversation is self-bootstrapping and fully vault-to-vault**.

**This is better than either option in the memo, for four reasons.**

It needs no directory, so there is no table mapping players to lanes, which means there is nothing of that kind to steal or to subpoena. It needs no identifier to be assigned, because a client that has generated a keypair **already knows its own lane address without asking anybody**, the address being derived from the key. It is symmetric, so the reply path is the same shipped mechanism as the send path rather than a new one. And it is per correspondent by construction, which makes revoking one player's lane a local act rather than a rotation.

**The 8 June record shows it working.** Two vaults exchanged messages in both directions using each other's public keys, described at the time as sending the equivalent of a text message from one vault to another and back.

**One decision was left open and this memo should close it.** The dev pack asks whether the receiving lane uses a shared append token or one per correspondent, with per correspondent as the stated default on the ground that it allows surgical revocation. **For a game open to the public, per correspondent is the only defensible answer**, because a shared token that any player holds is a token any player can use to flood the lane.

## Broadcast Is Nearly Free, And It Is The Private Option

The memo treats broadcast as the compromise you accept when you cannot address an individual. It is worth inverting that, because the economics and the privacy both point the other way.

**It is nearly free.** The game vault is already a published vault that every player opens, so the audience needs no provisioning and holds no new credential. A broadcast is one commit. Its content objects are immutable and are served from the edge with a one-year cache, **bypassing the function entirely**; the only per-reader cost is the small uncached read of the reference that says what is current.

**It is also the private option, and this corpus has already made the argument.** The observability brief of 20 August states that in this design **there is no push**, so a change propagates at exactly the rate at which parties check, and its companion draws the conclusion that a party which **publishes answers to a location the verifier fetches cannot meter and cannot surveil, and that those turn out to be the same property rather than two**.

Applied here: **an addressed reply requires knowing who to address**, which means the stats side learns which player asked which question and when it answered. **A broadcast learns nothing.** So the choice is not capability against convenience; it is capability against a new observation the operator did not previously have.

**Its one real limitation is latency, and it is absolute.** There is no push of any kind in the platform, no callback, no webhook, no socket and no notification service. The one thing named notify is a poke between two vaults open in the same browser, not a network path. A reader picks up a broadcast on the next open, focus or manual refresh, and **there is no way to make a player see it sooner**.

## Three Tiers, Compared By What They Leak

| Tier | Mechanism | Cost to publish | Reaches | What the operator learns |
|---|---|---|---|---|
| **1. Broadcast** | A file in the game vault every player already reads | One commit, then served from the edge | Everyone, on their next open | **Nothing about who** |
| **2. Cohort** | A file per bucket, where the bucket is a property rather than a person, such as everyone who disputed question 14 | One commit per bucket | A group, on next open | That the bucket exists and its size |
| **3. Addressed** | A reply sealed to the key that arrived in the first message | One append per recipient | One player, on next open | **That this key asked this thing** |

**Tier 2 is missing from the memo and it is the one that does most of the work.** Almost everything the memo wants to say back is about a question rather than about a person: this item was disputed by many of you and here is why it stands, or this one was wrong and has been corrected. **A reply keyed to the question rather than to the player reaches everyone who cares and identifies nobody**, and it is a broadcast in mechanism with none of the noise of a general announcement.

**So the design rule is to answer at the coarsest tier that carries the message**, and to treat tier 3 as the exception that has to earn itself.

## Feedback Is Not Telemetry, And Should Not Share A Retention Rule

The memo's instinct to reuse one mechanism is right at the transport layer and should stop there, because the two payloads differ in every respect that matters after the write.

| | **Telemetry** | **Feedback** |
|---|---|---|
| Volume | High, per action | Low, per deliberate act |
| Value of one record | Near zero | **High. One good objection is the point** |
| Consolidation | Folded and the raw discarded | **Never folded away. The text is the artefact** |
| Wants a reply | No | **Often, which is why this memo exists** |
| Retention | Short, by design | Long, because a contested item stays contested |

**Two consequences follow.** They should be separate lanes rather than one, because separate append tokens are free, they make the volume of one not a capacity problem for the other, and they let feedback survive a purge that clears telemetry. And **feedback is prose written by a person**, which makes it the only content in this pipeline that could carry something personal by accident, so it needs a retention answer that the counters do not.

## The Producer Already Exists

**The arcade brief of 5 September already specified where this content comes from.** Every negative score owes the player an explanation, and beside every explanation sits a button reading that they disagree, on the reasoning that a player who knows more than the dataset should become a contributor rather than somebody who quits annoyed. Four of the forty items are marked disputed and show both readings, precisely to invite this.

**So the disagreement button is the producer and this memo is the transport**, and the two were designed two days apart without being connected. Three things follow for the record shape.

A disagreement is already **anchored to an item**, so it carries the item's identifier for free, which is what makes the cohort tier possible. It arrives with **the player's classification and the dataset's**, which means the record is a disagreement rather than an opinion, and can be counted. And **the rating per question the memo asks for is the same record with a lighter payload**, so it should be the same schema with the argument omitted rather than a second mechanism.

**One thing the game already computes is the strongest possible reason to reply.** The corpus's own metric is the gap between what a player predicted and what was found, collected per capability throughout play. **A player who disagrees is asserting that the gap is on our side rather than theirs**, and a channel that never answers that is a measurement instrument that treats every disagreement as noise.

## There Is No Identity Today, And That Is A Feature To Spend Carefully

The memo's middle step, giving an identifier to a user or a session, is larger than it sounds.

**Nothing of the kind exists.** There is no session identifier, no player identifier, no device identifier and no visitor identifier anywhere in the shipped client. A visitor is distinguished on the server by a hash of an address in the site analytics and by nothing else, and the identity model is recorded as a resolved decision: **the vault key is the credential**, with no external identity provider.

**So introducing one is introducing the platform's first client-side identity**, and the rule for doing it is already written. The field-demo brief of 2 August, dealing with the same situation of a public-facing vault handed to strangers, states that recording who somebody is for follow-up is lead capture, and that it **must be a deliberate, visible act that the person performs, in the way a business card is handed over, rather than something inferred or attached silently to a session.** It also declines silent identity capture in terms.

**The reply-address-in-the-first-message design satisfies that rule and an assigned identifier does not.** A player who wants an answer generates a key and includes it, which is the deliberate act; a player who does not, does not, and their feedback still counts. **The identifier is chosen by the person rather than assigned to them**, which is the whole difference.

**The closest precedent in the corpus wanted exactly this and never built it.** A brief of 8 March describes sending a one-time message addressed to a hashed session so that a returning user sees that the bug they reported has been fixed, and calls it the zero-knowledge support model: fix the bug, notify the reporter, never learn their identity. **That is this memo, written six months earlier**, and it is filed under future.

One operational rule to inherit from the same 2 August brief, because the games will run on shared devices: **buffered events should be sealed as they enter the buffer rather than as they are sent**, so that one player's pending feedback is unreadable to the next person who picks up the machine.

## What Actually Blocks This

Not the transport, which ships. Not the topology, which was settled in June. **The client sealing layer**, which seals a payload to a recipient's key and derives the lane address from it, is **proposed rather than shipped**, with a note against it saying not to code against the derivation until the server side lands.

**It has been in this corpus's parked list since 19 August**, phrased as the client sealing layer end to end, and carried through every index since. **Everything in this document depends on it**, because a feedback record that is not sealed to the stats vault's key is a plaintext opinion in a lane, and a reply that cannot be sealed to a player's key cannot be sent at all.

**One deployment constraint is worth stating in the same breath**, because it would otherwise be discovered late. A vault served from static hosting is a read-only snapshot, and the append calls return a read-only error in that mode. **So a game published the cheap way cannot send anything**, which means the distribution decision and the feedback decision are the same decision.

## Build Order

| # | Step | Why here |
|---|---|---|
| 1 | The feedback record schema, on its own append token, separate from telemetry | Free to separate now, expensive later, and the retention rules differ |
| 2 | Wire the disagreement button to it, unsealed at first if necessary and clearly marked as such | It exists in a specification and produces nothing; this is the shortest path to real content |
| 3 | **The client sealing layer** | The blocker. Everything below this line waits on it, and it has been parked for three weeks |
| 4 | Per-correspondent tokens rather than one shared token | The open June decision, and the only defensible answer for a public game |
| 5 | The reply address carried in the first message, optional and player-initiated | Satisfies the deliberate-act rule, and needs no directory |
| 6 | Tier 1 and tier 2 replies, published in the game vault | Nearly free, private, and covers most of what there is to say |
| 7 | Tier 3 addressed replies | The exception, and only where a coarser tier genuinely cannot carry the message |
| 8 | A vault per player | The June conclusion, and the right shape once a player has state worth keeping rather than one objection to file |

**Step 8 is deliberately last.** The memo is right that it is where this ends up, and a vault per player is a heavy answer to the first question a player asks. **A keypair is enough to receive a reply; a vault is what you need when the player has something of their own to keep**, and the games do not yet.

## What This Does Not Try To Be

- **Not a transport design.** The append lane ships, and its costs and blindness are covered in the afternoon's brief rather than restated here.
- **Not an identity system.** It argues for the smallest thing that lets a player receive an answer, and explicitly against assigning identifiers to people who did not ask for one.
- **Not a moderation design.** It routes disagreements and says nothing about who adjudicates them, which is an open question from 5 September and still open.
- **Not a chat product.** The memo's conversation with the data is treated as a slow exchange of sealed messages, not a live session, because no push exists.
- **Not a specification for the feedback record's fields.** It states what the record must be anchored to and what it must not silently carry.

## Honest Tensions

| Tension | Note |
|---------|------|
| Reusing the telemetry channel | It is the same transport and it is free, and the two payloads want opposite retention, so one mechanism must not become one lane |
| Broadcast as the default | It is cheap and private, and it means the player who wrote the objection may never know it was theirs that was answered |
| Player-initiated reply addresses | It satisfies the deliberate-act rule, and it means the players who care most are the only ones you can reach |
| Per-correspondent tokens | Surgical revocation, and a token per player is state the stats vault must hold, which is a small registry arriving by the back door |
| Answering disagreements at all | It is what makes a contributor, and every answer is a position the project then has to defend |
| Feedback prose in an append lane | It is the highest-value content in the pipeline, and it is the only part that can carry something personal by accident |

## Open Questions

| Question | Notes |
|----------|-------|
| When does the client sealing layer ship? | **Parked since 19 August and blocking everything here.** It is the only item on this list that is not a design choice |
| Shared or per-correspondent append token? | Left open on 3 June. For a public game the answer looks forced, and it should be recorded rather than assumed |
| Who answers a disagreement? | Carried from 5 September and still open. A channel that delivers objections nobody answers is worse than no channel |
| Does a rating need a reply path at all? | Probably not, which is an argument for two record types on one lane rather than one |
| What is the retention rule for feedback prose? | It must differ from telemetry, and nobody has written either |
| Does a broadcast reply reference the objection that prompted it? | It is more useful if it does, and quoting a player's words back in a public file is a disclosure they did not choose |
| How does a player know a reply is waiting? | There is no push, so the honest answer today is that they find out by opening the game again |
