## The Same Vault Was Designed For A Band On 13 May

Before anything is specified, this should be read: a dev brief of 13 May proposes a demo vault for a fully AI-produced band, and it is this memo in a different medium.

It contains **a board**, described as Kanban-style tracking work in progress, ideas and retired ideas. It contains **a studio section** answering how a track is made, holding the prompts, the generations, the iterations and the final mix. It contains **logged decisions**. Its acceptance criteria include that the inner workings are present so the vault exposes the work in progress alongside the polished output. And it says in terms that it is **a reusable template that any musician, band, label or artist could clone and adapt.**

**Its governing principle is the one this memo needs most and states least:**

> Every piece of content should be paired with the **prompts and process** that produced it: the prompt that generated each image, the prompt and parameters that produced each track, the discussion of why one variant was kept and others were rejected, and the iteration history when something was refined.

**So the first action is not to design a pipeline.** It is to read that brief, change the medium, and record what changes. Nothing suggests it was ever built.

## The Clone Ships, And Not From Where The Memo Puts The Button

This is the finding that changes the flow, and it is a guard in the source rather than a design opinion.

**What ships is better than the memo assumes.** A single call creates a new vault seeded from a source, and the source may be a folder in the current vault, a linked reference, **or a raw vault key**, which is exactly the published-template case. It mints a **new random passphrase** for the child rather than a share token, so the clone is genuinely the cloner's own and is writable. It pushes the seeded tree immediately so anybody opening the new vault sees it. And it **refuses to copy the protected folder**, with a comment in the source saying so directly, which means a template can never carry the author's own secrets, tokens or link records into somebody else's copy.

**The constraint is that creating a vault requires the current session to be writable.** A published template is read-only by definition. **So a clone-me button inside the template cannot work**, and the memo's flow of arriving at the template and cloning from there does not run as described.

**Three ways round it, in order of preference.**

| # | Where the clone starts | Note |
|---|---|---|
| 1 | **From the provider site's own page**, which holds the template's read key and calls create with it | The memo already wants a prompt and a key on the page, so this costs nothing new |
| 2 | From a small writable starter vault the person gets first | An extra step, and it gives them somewhere to keep several productions |
| 3 | From the command line, by cloning read-only and re-initialising the folder | The primitives exist and **no document prescribes this as a workflow**, so it is an inference rather than a supported path |

**The first is the right answer and it also fixes the memo's other half**, because the page can hand the prompt and the seed together, which is what makes it one action rather than two.

**Two things to note for the template's own design.** Since the protected folder is never copied, **anything the pipeline needs must live outside it**, so the agent instructions, the placeholders and the board's initial state are ordinary vault files. And the clone is a copy at a moment, so **a template improved later does not reach the productions already started**, which is a property to state on the page rather than a bug to fix.

## Versions And The Final Cut Already Ship

The memo wants several versions of the video in the vault and eventually a final one. **That is a shipped feature and it is better than copying files.**

A configuration file inside the protected folder holds named releases, each pointing at a commit, with an optional label and notes, a default, and a switch controlling whether the live head remains available. A link carries a pin, so a shared address resolves to a named release. Resolution runs from the link, then a stored choice, then the default, then live, on the stated ground that **a shared link must show the same thing on every device.**

**Two properties make this the right mechanism for a video vault rather than merely an available one.**

**A release is the same objects, not a copy.** Because the store is content-addressed, an old release cannot have drifted from what it was, which turns the vault into evidence rather than an archive. The specification's own words are that this is exactly what audit and disclosure need.

**Publishing new work does not change what a link holder sees.** Which is precisely the memo's requirement that early cuts stay reachable while the final one becomes the default.

**And two traps to design around.**

**A pinned view is read-only for everybody, including the owner**, with its own distinct refusal code, because committing on top of an old tree would fork the branch. So a producer reviewing cut two cannot annotate while pinned to it, and the annotation flow has to be at head.

**There are no collection roots yet.** The specification says plainly that when garbage collection is built, pinned commits must be roots, **or a published release could be collected out from under a live link.** For a vault whose whole purpose is that early cuts remain reachable, that is worth recording as a dependency rather than a detail.

## The Board Is The Burst-Write Case, And One Application Already Solved It

Every write through the bridge becomes its own commit and push. **There is no host-side staging.** The afternoon's brief measured what that costs: the tree for the folder and every ancestor is rewritten on each write, so cost grows with how many files the folder already holds, and nothing is ever reclaimed.

**A board is the worst shape for this.** Dragging a card is a state change; a person moving five cards while thinking produces five commits, each rewriting the same file's folder tree. And the batching that would fix it was specified on 26 May and **has not shipped**, with only a debounce on the push rather than on the commit.

**The decision rule is not in doubt.** Device-local state is for things whose loss across browsers would be fine; anything whose loss would be a bug goes into the vault. **A board's contents are the second kind**, so they must be vault writes and the frequency has to be solved rather than avoided.

**A shipped application already solved it and the pattern should be copied rather than reinvented.** The vault workbench hit exactly this, recorded it as a finding, and answered with app-side staging plus a **single state file keyed by title, so re-saving overwrites the same file rather than accumulating timestamped copies.** That gives one commit per save and a stable path.

**So the board's rules are three.** Hold moves in memory and write on an explicit save or on leaving a column, never on each drag. Write one file, not one per card. And show the person when there are unsaved changes, because an app that silently defers a write has taken on the promise the platform used to keep.

**One smaller trap worth knowing.** Vault markdown does not render task lists, so a checklist cannot be a markdown file and has to be part of the page layout or the app.

## The Homepage And The Menu

The memo wants the finished vault's front page to be the video's page, with a menu to the history, the materials and the evidence. **Two shipped mechanisms do this and the obvious-sounding third does not exist.**

**The application route.** A configuration file names an entry page and asks the vault to open straight into it rather than the file browser, and it also configures the surrounding chrome, which supplies navigation, history, a path bar and a home button. **The guidance is explicit that an app should not build its own back button.**

**The page-layout route.** A layout file at the root renders immediately when the vault opens, with a component set covering heroes, sections, galleries, slides, embedded documents and markdown.

**And the menu is a card set rather than a navigation bar**, which is the detail most likely to be got wrong: the navigation field holds anchors within the same page, while links to sub-sections are cards whose target is a relative path to a file or a folder. **A hub page with cards leading to the history, the materials and the evidence is the shape**, and each of those folders carries its own layout file.

**The declarative folder narrative that would make this tidier was proposed on 29 March and never built**, so anyone designing against it will find nothing there.

## The Cast Is Half Present, And Handover Is Already Defined

The memo wants editors, copywriters, designers, producers and video editors working together. **This organisation already runs a documented multi-role workflow, and its central rule is the one to carry into the vault:**

> Agents do not talk to each other directly. They coordinate through **file-based artefacts**. An issue is not just a to-do item. It is a **contract** between roles.

with disposability as the second rule: an agent finishes a task, writes a handoff artefact, and exits, and the next role starts fresh and picks it up. **That maps onto a vault exactly**, and the 2 August argument makes the mapping explicit: a path with a single writer and defined readers is an interface between two agents, and the set of such paths is the architecture, so **adding a participant means granting a path rather than changing anybody's code.**

**Of the memo's cast, three exist and three do not.**

| Role | State |
|---|---|
| **Designer** | Defined, and explicitly not a user-interface role. Its own file says the designer owns how things work |
| **Journalist** | Defined, and already owns user-facing copy |
| **Historian** | Defined, and already keeps decision logs, which is the memo's record of what was tried |
| Copywriter, producer, video editor | **Absent from every role tree**, and genuinely new |

**The worked example to copy is from 23 March**: one brief produced six documents, one per role, in a single session, with an explicit dependency graph saying which document informs which and a phased plan naming an owner per phase. **That is a video pipeline's shape already**, and the index that sequences the passes is the artefact the board is a view of.

**The honest tension is recorded too**, and it is the one a production pipeline will meet first: a message can sit unread with nobody accountable for noticing. **A board helps with exactly that**, which is a good reason for it to exist beyond looking like project management.

## Show The Work, And Never Give A File Two Writers

The memo's last idea, that the menu leads to the history and the reference material and the evidence, is where this vault earns its keep, and two established rules should govern it.

**The single-writer rule, settled on 31 July**: generated files flow one way, contributed files flow the other, and **no file has two writers.** For this pipeline that means the script the copywriter produces and the corrections a reviewer files are different paths, and a correction is recorded beside the thing rather than as an edit to it.

**The attach-never-mutate rule**, from the evidence work: material added about an artefact may add and may never alter or delete what it attaches to, which makes it detachable, attributable and safe to accept.

**Together they give the evidence section its shape.** The sources, the prompts, the rejected variants and the reviewer's objections all sit beside the output, none of them overwrite it, and the history is already kept by the store rather than by a convention.

## Where The Code Lives

The memo settles something left open yesterday: as much as possible should be reused from the tools site, **which stays the canonical source.**

**That is the right split and it should be written down as the rule for this family.** The tools site holds the components and remains where they are versioned; the provider site holds the context, the guidance and the home; the template vault holds the pipeline and the working method. **Nothing is authored twice**, and the deletion-candidates discipline from yesterday's specification stays untouched, because on this reading almost nothing is being deleted at all.

## What This Does Not Try To Be

- **Not a video production method.** It specifies the vault that holds one, and the method itself is the content of step two.
- **Not a video toolchain.** The rendering, narration and assembly pieces remain unbuilt and are covered elsewhere.
- **Not a project management product.** The board exists to stop a handoff sitting unread, and that is the whole of its ambition.
- **Not a new coordination model.** It maps the existing file-artefact handover onto a vault and adds nothing to it.
- **Not a claim that the cast must be agents.** Every role here can be a person, and the artefacts are the same either way.

## Open Questions

| Question | Notes |
|----------|-------|
| Does a published release survive collection? | **No mechanism yet, and the specification says pinned commits must become roots.** A dependency rather than a detail |
| Where does a person review a pinned cut? | A pinned view is read-only for everyone, so annotating an old cut has to happen at head and reference it |
| One vault per video, or one per series? | The memo says per video, and a series shares a style, a voice and a template, so the second may want a parent |
| How large does a vault holding several video versions get? | The cost model is derived rather than measured, and this is the first workload that would find out |
| Do the three new roles get their own instruction files in the template, or in the role tree? | In the template they travel with the clone; in the role tree they stay canonical. **Probably both, with one canonical** |
| Does the finished vault carry the key material it used? | Narration needs a provider key, and a published production vault should not contain one |
| Who reviews a correction filed beside a script? | The single-writer rule says where it goes and not who acts on it |
