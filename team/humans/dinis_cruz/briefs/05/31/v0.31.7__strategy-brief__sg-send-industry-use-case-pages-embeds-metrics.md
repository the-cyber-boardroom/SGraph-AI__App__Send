## What This Is

A follow-up on the pages to add to the website (cross-ref: the v0.31.7 agent-controlled-websites brief), from the ambassador's point of view: **a series of industry-by-industry, use-case pages, each with a live vault example and a how-we-work example, embedding read-only vaults and tools, and measured by the core usage metrics.** The ambassador (and the Sherpa) own how partners and users see, manage, and consume the websites, so this brief is about giving each industry and use case its own page that shows, concretely, how the vaults work for them.

The project lead: **"the ambassador's job, and both the ambassador and the Sherpa, is to think about how the partners and users see the websites, how they manage and consume them."** This brief turns that into a concrete content plan: go industry by industry, use case by use case, each with a real vault example.

## The Lens: Ambassador And Sherpa

The framing: **the ambassador and the Sherpa think about how partners and users see, manage, and consume the websites.** These are the outward-facing roles (cross-ref: the agent-controlled-websites brief, where the ambassador owns the main website): the ambassador thinks about the site, the partners, and the outreach; the Sherpa about how users find their way through and consume it. So the pages below are designed from the consumer's and partner's point of view: what does a pen testing company, a healthcare partner, a risk manager see when they arrive, and how quickly do they understand how the vaults work for them.

The project lead: **"I want a whole series of pages on the library and on the site that link from the main site, all about use cases, all about industry. We need to go industry by industry. I want to literally go industry by industry."** The approach is systematic: each industry gets pages, and within an industry, each use case gets its own page.

### Other Industries And Risks

The project lead noted this generalises: **"the people I want to reach out to in cybersecurity, in other risks and other industries, healthcare, for example."** So the industry-by-industry plan extends beyond cybersecurity and healthcare to other risk domains and industries, each getting the same treatment: pages, use cases, vault examples.

## Each Page: A Vault Example And A How-We-Work Example

The key requirement for every page: **each should have a vault example and a how-we-actually-work example.**

The project lead: **"each of those should have a vault example, and each of those should have a how-we-actually-work example."**

| Per Page | What It Shows |
|----------|---------------|
| **A vault example** | A real, live vault for that use case (a pen-test vault, a vulnerability debrief, a healthcare vault) |
| **A how-we-work example** | How we actually work with that audience, concretely |

This is what makes the pages powerful rather than generic marketing: each shows a real vault (cross-ref: the security-report, vulnerability threat-intel, and assessment demos, which are exactly these vault examples) and a concrete account of how the work is done. A pen testing company sees a real pen-test vault and how an engagement works; a vulnerability manager sees a real vulnerability debrief vault. The demos built across the recent work are the vault examples these pages showcase.

## Embedding Read-Only Vaults And Tools In The Site

A feature the project lead wants, where the pieces mostly exist: **show read-only vaults nicely in the main website, and show the tools, by embedding the component pages.**

The project lead: **"we need to be able to show nicely the read-only vaults in our main website, and also show the tools we have. Most of the stuff we download is components, so we should be able to easily embed those pages."**

| To Embed | How |
|----------|-----|
| **Read-only vaults** | Show a read-only vault nicely in the main site (cross-ref: the public-preview-with-read-only-key brief) |
| **The tools** | Show the tools (cross-ref: the tools.sgraph.ai work and the connectors/vault-chat tools) |
| **Component pages** | Because most of what is downloaded is components, embed those component pages easily |

So an industry page does not just describe the vault example; it embeds the live read-only vault and the relevant tools directly, using the public-read-only rendering (cross-ref: the public-preview-with-read-only-key and agent-controlled-websites briefs) and the component-embedding. The project lead noted the piece of the puzzle mostly exists; the work is making the embedding clean and easy. And the agent-controlled-websites capability (cross-ref) is what makes iterating on this fast: **"the power of the agents being able to edit it is we could iterate quite fast on how to make that work."** The ambassador agent can edit the pages and iterate on the embedding quickly, so the presentation improves rapidly.

## The Core Metrics: Vaults Created, Accessed, Files Loaded

The brief closes on how success is measured, returning to the recurring-usage metrics: **daily and monthly recurring usage, measured as vaults created per day, vaults accessed per day, and files loaded per day.**

The project lead: **"we're going to go back to our daily recurring usage and monthly recurring usage and our metrics. Now it's about how many vaults get created a day, how many vaults get accessed per day, how many files get loaded. That's fundamentally our main metric. If that goes up, we have a business."**

| Metric | What It Measures |
|--------|------------------|
| **Vaults created per day** | New vault creation (the top of the funnel) |
| **Vaults accessed per day** | Vault usage (engagement) |
| **Files loaded per day** | Activity within vaults (depth of use) |
| **Daily / monthly recurring usage** | The recurring-usage trend over time |

These are the core business metrics (cross-ref: the v0.27.60 identity-persistence-budgets brief's budgets-and-usage and the open-evaluation funnel): vault creation, vault access, and files loaded, tracked daily and monthly. The project lead's bottom line is direct: if these go up, there is a business. So the industry pages are not an end in themselves; they are the outreach that drives the metrics. Each industry page that lands brings an audience that creates and accesses vaults and loads files, which is exactly what the metrics measure. The pages are the top of the funnel; the metrics are how you know they are working.

## What This Asks For

1. **Build industry-by-industry, use-case pages** on the library and main site (linked from the main site).
2. **Start with cybersecurity** (pen testing companies, threat modelling, vulnerability management, risk management), then healthcare (the kneescore.com partnership), then other industries and risks.
3. **Give each page a vault example and a how-we-work example** (real, live vaults from the demos).
4. **Embed read-only vaults and tools nicely** (using the public read-only rendering and component embedding).
5. **Let the ambassador iterate fast** (the agent edits the pages; rapid iteration on the embedding and presentation).
6. **Design from the consumer/partner lens** (the ambassador and Sherpa: how partners and users see, manage, and consume).
7. **Track the core metrics** (vaults created per day, vaults accessed per day, files loaded per day; daily and monthly recurring usage).
8. **Keep partner-specific confidential detail private** (the public healthcare pages show the partnership and how the vaults work, not the confidential MVP specifics).

Estimated effort: the pages compose existing pieces (the demos as vault examples, the public read-only rendering, the component embedding, the agent-controlled websites for fast iteration); the new work is the industry/use-case page series, the clean embedding, and the metrics tracking. The demos already built are the vault examples, so much of the content exists.

## What This Does Not Try To Be

- **Not generic marketing pages.** Each page has a real vault example and a concrete how-we-work example.
- **Not one page per industry.** Each use case within an industry gets its own page (pen testing, threat modelling, etc.).
- **Not static.** The ambassador agent edits and iterates fast.
- **Not exposing confidential partner detail.** The public pages show the partnership and the vaults working, not the private MVP specifics.

## Honest Risks

**Risk 1: Many pages to build and maintain.** Industry-by-industry, use-case-by-use-case is a lot of pages. Mitigation: the agent-controlled websites let the ambassador build and iterate fast; the demos provide the vault examples; start with cybersecurity and healthcare.

**Risk 2: Embedding read-only vaults and tools must be clean.** A clumsy embed undermines the page. Mitigation: the piece of the puzzle mostly exists (public read-only rendering, component embedding); iterate fast with the agent; make the embedding easy.

**Risk 3: Partner-specific confidentiality.** Healthcare and partner pages must respect what is private. Mitigation: the public pages show the partnership and how the vaults work; the confidential MVP specifics stay in the private brief; clear boundary.

**Risk 4: Metrics could be vanity rather than business.** Counting vaults could mislead if not tied to real use. Mitigation: the metrics (created, accessed, files loaded) measure real activity; daily/monthly recurring usage shows the trend; tie the pages to the metrics to know they work.
