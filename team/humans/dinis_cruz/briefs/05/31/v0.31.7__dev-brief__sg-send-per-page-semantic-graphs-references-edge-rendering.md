# Per-Page Artefacts: Serving Semantic Knowledge Graphs And References Alongside The Content

**version** v0.31.7
**date** 31 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Dev brief

## What This Is

A follow-up on a great piece of work done yesterday, and the next step: **for every page on the website, serve not just the content but the semantic knowledge graph of that content (and the references), alongside the LLM-friendly text.** Yesterday the library gained native support for `llms.txt` and `.md` files (LLM-friendly files), rendered through edge functions. This brief extends that: serve the semantic graph per page, the references (who links to whom), and other consumption artefacts, so every page has both its content and its machine-understandable, interconnected, semantic form.

The why, in the project lead's framing: this is about being able to work with the content programmatically and with LLMs, to manipulate and understand what is going on, and to detect problems like broken links and context issues.

## The Foundation: llms.txt And .md Via Edge Functions

What was built yesterday, and why the method matters: **the library now natively supports `llms.txt` and `.md` files, rendered through edge functions.**

The project lead: **"yesterday we added native support to the library for serving llms.txt and .md files, which are LLM-friendly files. The way it was done is important: it was done using edge functions. These are static files, the browser will not run any JavaScript on them, so we couldn't render encrypted data. What we did was add a little bit of JavaScript on the Lambda@Edge function that does the rendering of the file. It works quite nicely."**

The key technical insight:

| Constraint | The Solution |
|------------|--------------|
| The files are static (e.g. `llms.txt`, `.md`) | No browser JavaScript runs on them |
| So encrypted vault data cannot be rendered client-side | The usual client-side decryption is not available |
| Edge function (Lambda@Edge) does the rendering | A bit of JavaScript on the edge function renders the file, including decrypting the vault content |

So the edge function is what makes serving static, LLM-friendly files from an encrypted vault possible: the browser would not run the decryption JavaScript on a static file, so the edge function runs it instead, rendering the file at the edge. This is a clean solution and the foundation for serving more artefacts the same way.

## The Client-Side Versus Edge-Side Choice

A design choice the project lead flagged, which applies to all the per-page artefacts: **render client-side or edge-side, depending on who the consumer is.**

The project lead: **"we need to think about whether we do this purely on client-side encryption, or we do it static [edge-side]. It depends who the consumer is. We have two choices: client-side rendering, and edge-side rendering."**

| Rendering | When | For |
|-----------|------|-----|
| **Client-side** | The consumer's browser runs the decryption JavaScript | Interactive consumers (a browser, the vault UI) |
| **Edge-side** | The edge function renders (decrypts) and serves static output | Consumers that do not run JavaScript (LLMs fetching `.md`/`.txt`, crawlers, programmatic access) |

So the same artefact can be served either way, chosen by consumer: an interactive browser gets client-side rendering (the existing model), while an LLM or crawler fetching a static file gets edge-side rendering (the new model). This is a useful general capability (cross-ref: the public read-only rendering in the agent-controlled-websites and public-preview-with-read-only-key briefs): the vault content can be served client-side for humans and edge-side for machines, from the same encrypted source.

## The New Artefact: A Semantic Knowledge Graph Per Page

The main ask: **for every page, serve the semantic knowledge graph of that page, the same way the `.md` is served.**

The project lead: **"the same way we're serving the MD, I also want to serve the semantic knowledge graph. So now you go to a page and add .md and you get the text of the page (the raw text). I would also like the semantic part: the semantic graphs, created per page."**

| URL Pattern | What It Returns |
|-------------|------------------|
| `page.md` (existing) | The text of the page (the raw content, LLM-friendly) |
| `page` + the semantic artefact (new) | The semantic knowledge graph of the page |

So every page gains a semantic form: a knowledge graph of its content, served alongside the text. This is the document-to-graph pipeline (cross-ref: the v0.31.9 vault-per-standard brief's pipeline and the v0.27.64 prompt-context brief's semantic knowledge graphs) applied per page: each page's content is extracted into a semantic graph (triples, ontologies), and that graph is served. The project lead's framing: **"this gives us the beginning of having semantic web proper, and triples, per content that we have here."** It is the semantic web realised for the site's own content: every page has machine-readable semantics, not just text.

## What The Per-Page Graphs Enable

The project lead listed what the per-page semantic graphs open up:

| Artefact / Capability | What It Is |
|-----------------------|------------|
| **Semantic graphs (triples)** | The machine-readable semantics per page (semantic web proper) |
| **Interconnections** | How pages and concepts connect across the site |
| **Analysis and insights** | Analysis over the content and its connections |
| **Evidence packs** | Even evidence packs (cross-ref: the security-report and vulnerability threat-intel briefs) |
| **References (who links to whom)** | The link graph of the site |

The project lead: **"this gives us the interconnections, the analysis, the insights, even an evidence pack. And I also like the references, the pages who linked to who."** So beyond the per-page graph, the artefacts include the cross-page interconnections and the reference/link graph (which page links to which). Together these turn the site from a set of pages into a navigable, analysable knowledge graph: each page semantically described, the pages interconnected, the references mapped, and analysis and insights derivable over the whole.

## The Why: Work With LLMs, Programmatically, And Catch Problems

The motivation the project lead gave: **this is about being able to work with LLMs, to programmatically manipulate and understand the content, and to catch problems.**

The project lead: **"remember this is also about being able to work with LLMs and programmatically manipulate and understand what's going on. For example, detect broken links, or problems with context."**

| Use | How The Artefacts Help |
|-----|------------------------|
| **Work with LLMs** | LLM-friendly text plus semantic graphs give LLMs structured access to the content |
| **Programmatic manipulation and understanding** | The graphs and references make the site machine-processable |
| **Detect broken links** | The reference/link graph surfaces broken links |
| **Detect context problems** | The semantic graph surfaces gaps and inconsistencies |

So the per-page artefacts serve both consumption (LLMs and programs can consume the content semantically) and maintenance (the reference graph catches broken links; the semantic graph catches context problems). This is the practical payoff: the site becomes both more consumable by machines and more self-checking. It connects to the evidence and assessment work (cross-ref: the visualisation-cornerstone and vault-per-standard briefs): the same semantic-graph and provenance machinery that powers the assessments now describes the site's own content.

## What This Asks For

1. **Serve a semantic knowledge graph per page** (alongside the existing `.md` text), created per page.
2. **Serve the references per page** (who links to whom; the site's link graph).
3. **Build on the edge-function method** (the Lambda@Edge rendering that made `llms.txt`/`.md` work for encrypted vault content).
4. **Support both client-side and edge-side rendering** (chosen by consumer: humans client-side, machines/LLMs edge-side).
5. **Enable the derived artefacts** (interconnections, analysis, insights, evidence packs) over the per-page graphs.
6. **Use the graphs for maintenance** (detect broken links via the reference graph; context problems via the semantic graph).
7. **Reuse the document-to-graph pipeline** (cross-ref: the vault-per-standard brief; the same extraction per page).

Estimated effort: builds directly on yesterday's edge-function rendering and the existing semantic-graph pipeline. The new work is generating the per-page semantic graph and reference graph, serving them (client-side and edge-side), and the derived analysis/maintenance. The method is proven (the `llms.txt`/`.md` serving works); this extends it to more artefacts.

## What This Does Not Try To Be

- **Not text only.** Every page gains a semantic graph and references, not just `.md` text.
- **Not client-side only.** Edge-side rendering serves machines/LLMs that do not run JavaScript.
- **Not a separate system.** It reuses the edge-function method and the document-to-graph pipeline.
- **Not just consumption.** The graphs also catch broken links and context problems (maintenance).

## Honest Risks

**Risk 1: Per-page graph generation has a cost.** Generating a semantic graph per page costs (LLM/processing). Mitigation: reuse the existing pipeline; generate on change; the budget discipline (cross-ref: the prompt-context and assessment briefs); cache the artefacts.

**Risk 2: Edge-side rendering decrypts at the edge.** The edge function decrypts vault content. Mitigation: only for content meant to be public (the public read key; cross-ref: the public-preview briefs); the same controlled-exposure model; private content is not served edge-side.

**Risk 3: Graph accuracy.** A wrong semantic graph misleads consumers. Mitigation: the document-to-graph pipeline's validation and provenance (cross-ref: the vault-per-standard brief); the graphs are derived from the page content, traceable.

**Risk 4: Keeping artefacts in sync with content.** The graph and references must track content changes. Mitigation: regenerate on change (the multi-agent workflow and version control; cross-ref: the library-as-shop-front and commit-queue briefs); the artefacts are derived, so they can be rebuilt.
