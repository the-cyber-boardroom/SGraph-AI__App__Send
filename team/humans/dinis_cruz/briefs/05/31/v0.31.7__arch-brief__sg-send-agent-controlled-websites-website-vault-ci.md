## What This Is

A brief on the intersection of several features that are just about live, which together let **agents control parts of the main website**, each through its own vault, all managed by a single website vault, and released from dev to prod through a vault-based CI pipeline. It builds directly on the library-as-shop-front work (cross-ref: the v0.31.9 library-as-shop-front brief) and combines two capabilities: **rendering a website from a vault** (already working for the library) and **vault-in-vault** (cross-ref: the v0.27.64 VIV kernel-model brief).

The result the project lead is excited about: a Claude session is given the read-write key for the vault an agent works on, and it pushes directly into the websites, with the ambassador, alchemist, and probably the journalist agents each owning a part of the site, all under one website vault, with QA sign-off and a dev-to-prod release pipeline.

## How Library Rendering Works (The Foundation)

The foundation, already working: **the library website renders content from a vault.** The project lead: **"when you go to the library website, you are seeing content from a vault, content stored encrypted, where we put the read key in the website, because it's public. This is the content vault, a special vault we mark as public, where we are exposing the read key, which is fine, because that's the whole point."**

| Element | Detail |
|---------|--------|
| **The content vault** | A vault marked public, holding the library content |
| **Stored encrypted** | The content is encrypted in the vault, as always |
| **The read key in the website** | The read-only key is exposed in the public website, deliberately |
| **Public by design** | Exposing the read key is the point; the content is meant to be public |

This is the public-read-only model (cross-ref: the v0.31.9 public-preview-with-read-only-key brief and the v0.27.62 public-vault-previews brief): a vault marked public, with its read key exposed in the website, so the site renders the vault's content. The library proves it works. The rest of this brief extends it from one content vault to several agent-controlled vaults under one website vault.

## Per-Agent Website Sections

The new step: **create more vaults, one per agent, each controlling a part of the website.**

The project lead: **"we can create two more vaults: one for the alchemist, which is the investors part of the website (/investors, where we talk about the investment fund), and the main website, managed by the ambassador, because that's the agent that controls and thinks about the website, the partners, everything. And probably the journalist too."**

| Agent | Website Section | Its Vault |
|-------|-----------------|-----------|
| **The ambassador** | The main website (the site, the partners, everything) | The main website vault |
| **The alchemist** | The investors section (`/investors`, the investment fund) | The investors vault |
| **The journalist** (probably) | Likely a content/news section | Its own vault |
| **(The content vault)** | The library (already live) | The content vault |

So each agent owns a vault, and that vault renders to its section of the site. The ambassador owns the main site (it is the agent that thinks about the website, partners, and direction); the alchemist owns the investors section (the fund); the journalist probably owns a content section. This maps the agent roles onto website sections, each agent maintaining its vault, each vault rendering its part of the site. It is the multi-agent content workflow (cross-ref: the library-as-shop-front brief's dev/content/QA agents and FS email) extended so each agent owns a public-rendering vault.

## The Website Vault: Vault-In-Vault For Management

The second capability that makes this manageable: **a website vault that contains all the per-agent read-write vaults, using vault-in-vault.**

The project lead: **"the other intersection of technology helping to manage this is vault-in-vaults, because then we can have a website vault which inside it has all the read-write vaults of all these. That means we can much better manage which vaults exist, what's going on, provide access, and even do cross-vault stuff. Without vault-in-vaults, managing becomes quite complicated. With this, I have one vault that is the main website vault."**

| Without VIV | With The Website Vault (VIV) |
|-------------|------------------------------|
| Many separate vaults to track | One website vault containing them all |
| Managing which exist, access, cross-vault work is complicated | Managed from one place |

So the website vault is a VIV parent (cross-ref: the VIV kernel-model brief) containing all the per-agent section vaults as children. This gives one place to manage everything: which vaults exist, what is going on in each, providing access, and cross-vault operations. The project lead's point is that VIV is what makes the multi-vault website tractable: without it, coordinating the ambassador's, alchemist's, journalist's, and content vaults would be complicated; with it, there is one website vault, and the rest are its children. This is exactly the manage-vaults-of-vaults use case the VIV work was for (cross-ref: the sub-vaults and VIV briefs).

## The Agent Workflow: A Read-Write Key And Direct Push

How an agent works on its section: **give a Claude session the read-write key for the vault the agent works on, and it pushes directly into the websites.**

The project lead: **"the intersection of these capabilities is what lets me have a Claude session where all I have to do is give it the read-write key for the vault the agent is working on, and it can push directly into the multiple websites."** So the workflow is simple: the agent (a Claude session) gets the read-write key for its vault, makes its changes, and pushes; the website renders the updated vault. The read-write key is the grant of control over that section; the public read key is what the website uses to render it. This is the clean separation the vault model gives: the agent writes with the read-write key, the public site reads with the read key.

## Dev To Prod: Multiple Vaults As A CI Pipeline

The release model, which preserves quality control: **multiple vaults as environments (dev, main, prod), where pushing from one vault to the next is the CI pipeline release.**

The project lead: **"we will have probably the equivalent of dev, main, and prod, or at least dev and prod. You have two vaults, and you push from one to the other. That's the CI pipeline release. We still have QA control of everything happening, but now that's two vaults. Technically we can have QA, dev, main, and prod vaults. Each of those, especially prod, should be on a separate server, and prod probably should only be pushed through the CI pipeline, so we still have that control of the final step. That allows quality control, QA sign-off, all of that, even for content."**

| Environment Vault | Role |
|-------------------|------|
| **Dev** | Where changes are made (the agent works here) |
| **(Main)** | An intermediate stage |
| **QA** | Where quality is checked and signed off |
| **Prod** | The live site; on a separate server; pushed only through the CI pipeline |

So each environment is a vault, and promotion is a push from one vault to the next: dev to (main/QA) to prod. This is a CI pipeline built on vaults: the agent works in dev, changes are QA'd, and only a controlled CI push promotes to prod. Two properties matter:

- **QA sign-off, even for content**: because promotion is a controlled push (not a direct edit of prod), there is a QA gate, so content gets the same quality control as code (cross-ref: the QA agent in the library-as-shop-front workflow). This is notable: it brings software-style release discipline to website content.
- **Prod on a separate server, pushed only through CI**: prod is isolated and only reachable through the controlled pipeline, preserving the control of the final step. The agent never edits prod directly; it edits dev, and CI promotes.

This is the same controlled-promotion discipline as a normal software CI pipeline, realised with vaults as the environments and a vault-to-vault push as the release. It keeps the speed of agent-driven content (the agent works freely in dev) with the safety of a gated release (QA sign-off, CI-only prod).

## How The Capabilities Intersect

The brief is explicitly about an intersection, and it is worth stating which capabilities combine:

| Capability | Contribution |
|------------|--------------|
| **Rendering a website from a vault** | The site sections render from vaults (the library proves it; cross-ref: the library-as-shop-front brief) |
| **Public read key in the website** | The public sections expose a read key to render (cross-ref: the public-preview-with-read-only-key brief) |
| **Vault-in-vault** | The website vault contains and manages all the section vaults (cross-ref: the VIV kernel-model brief) |
| **Read-write keys** | Each agent gets the read-write key for its section vault |
| **Multiple vaults as environments** | Dev/main/QA/prod vaults with vault-to-vault promotion (the CI pipeline) |
| **The multi-agent workflow** | The ambassador, alchemist, journalist agents own their sections (cross-ref: the library-as-shop-front workflow) |

The project lead's point is that these are all just about live, and their intersection is what unlocks agent-controlled websites with proper management and release discipline. None is new on its own; the combination is the capability.

## What This Asks For

1. **Create per-agent section vaults** (the ambassador's main website vault, the alchemist's investors vault, probably the journalist's; alongside the existing content vault for the library).
2. **Render each section from its vault** (public read key in the website, as the library does).
3. **Create the website vault** (a VIV parent containing all the section vaults; manage which exist, access, and cross-vault work from one place).
4. **Give each agent the read-write key for its section vault** (the agent works and pushes directly).
5. **Set up dev/main/QA/prod environment vaults** (or at least dev and prod), with vault-to-vault promotion as the CI pipeline.
6. **Gate promotion with QA sign-off** (even for content; the controlled push is the gate).
7. **Isolate prod** (on a separate server; pushed only through the CI pipeline; never edited directly).
8. **Capture the pattern** (agent-owns-a-vault-renders-a-section, managed by a website vault, released by a vault CI pipeline) for reuse.

Estimated effort: moderate, and built on capabilities that are just about live (vault rendering, public read keys, VIV, the multi-agent workflow). The new work is the per-agent section vaults, the website vault (VIV parent), the read-write-key agent workflow, and the dev-to-prod vault CI pipeline with QA gating and prod isolation. The library already proves the rendering foundation.

## What This Does Not Try To Be

- **Not direct editing of prod.** The agent edits dev; CI promotes to prod through a QA gate.
- **Not many ungoverned vaults.** The website vault (VIV) manages them all from one place.
- **Not exposing write access publicly.** The public site uses the read key; the read-write key is the agent's grant.
- **Not content without QA.** Content gets the same QA sign-off as code, via the controlled promotion.

## Honest Risks

**Risk 1: Public read keys expose the section content.** Each public section exposes a read key. Mitigation: that is the point (the content is public); the controlled-exposure model applies (cross-ref: the public-preview briefs); only public sections expose read keys; private vaults do not.

**Risk 2: Multiple environment vaults add coordination.** Dev/main/QA/prod per section is several vaults. Mitigation: the website vault (VIV) manages them; the CI pipeline standardises promotion; start with dev and prod, add stages as needed.

**Risk 3: Agents with read-write keys can change a live-adjacent vault.** An agent's write access is real. Mitigation: agents work in dev, not prod; QA sign-off gates promotion; prod is isolated and CI-only; version control allows rollback (cross-ref: the commit-queue and version-control work).

**Risk 4: Prod isolation and the CI push must be secure.** The final promotion to a separate-server prod must be controlled. Mitigation: prod only reachable through the CI pipeline; the controlled final step; the same discipline as a normal software release.
