# Public Preview With An Embedded Read-Only Key: Share A Vault Publicly Without Sharing The Key

**version** v0.31.9
**date** 30 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Dev brief

---

## What This Is

A short feature that combines two things added recently: **public vault previews** (cross-ref: the v0.27.62 public-vault-previews brief) and **read-only tokens** (cross-ref: the v0.27.62 sub-vaults-workflow brief's read-only tokens). The idea: **a public preview that also carries a read-only key, so following the public link opens the preview and shows the vault straight away in pure read-only, without having to share the key in the link.**

The project lead: **"I would like the public preview loading up and containing a read-only key, so that whoever follows the public preview can also open the vault. I want to share a vault publicly, without having to share the key in the link. Somebody goes to a link, the preview opens, and they see the vault straight away in a pure read key."** It is a clean combination of two features that now work well, and it makes public read-only sharing effortless.

## The Two Features It Combines

| Feature | What It Provides (Existing) |
|---------|------------------------------|
| **Public vault previews** | A deterministic public ID that renders a preview (title, description, thumbnail) as a page and a social-share card (cross-ref: the public-vault-previews brief) |
| **Read-only tokens** | A read-only key/token that grants read access to a vault, distinct from the full vault key (cross-ref: the sub-vaults-workflow brief) |

Both work well on their own. This feature combines them: the public preview, instead of only showing the preview and then asking for a key, **also carries a read-only key**, so the same public link that shows the preview also opens the vault in read-only.

## What Changes: From Preview-Then-Ask To Preview-Then-Open

The public-previews brief established two access modes (cross-ref): the public link shows the preview and asks for the key, or the key is put in the URL hash to auto-load. This feature adds the cleaner public case:

| Mode | Behaviour |
|------|-----------|
| **Preview, then ask for the key** (existing) | The public link shows the preview; the user must supply the key to open the vault |
| **Key in the hash** (existing) | The full key is in the URL hash; the vault auto-loads |
| **Preview with an embedded read-only key** (this feature) | The public link shows the preview and opens the vault in read-only, automatically, no key to share separately |

The distinction from the key-in-the-hash mode matters: there, the *full* vault key is shared in the link (read-write access, the whole key). Here, the preview carries a **read-only** key, so following the public link grants read-only access only, and the owner has not had to share the full key or paste a key into the link at all. It is public read-only sharing by default, with the read-only key travelling with the preview rather than being handed over separately.

## The Experience

The project lead's described flow:

1. Someone follows the public link.
2. The preview opens (the title, description, thumbnail; the social-share card if shared on a platform).
3. The vault opens straight away, in pure read-only.

No separate key to send, no key to paste, no asking. The public link is self-sufficient for read-only access. This is exactly the effortless public-sharing experience the project lead wants: share one link, the recipient sees the preview and the vault contents immediately, read-only.

## Why This Is Safe And Clean

This sits comfortably within the controlled-exposure model (cross-ref: the public-vault-previews brief's deliberate, user-chosen exposure):

- **It is opt-in and read-only.** The owner chooses to make a vault publicly readable; the embedded key is read-only, so the public can read but not change.
- **It uses the existing read-only-token mechanism.** Nothing new in the trust model; it is the existing read-only token, carried with the public preview.
- **The full key is never shared.** The owner shares a public link, not the vault key; only read-only access travels with it.
- **The exposure is still controlled.** The public-previews controls apply (cross-ref): timing/expiry, the public ID, and the edit-on-settings can govern the public read-only access too.

So it is the deliberate-public-exposure model (cross-ref) extended from "the public can see the preview" to "the public can read the vault," still opt-in, still read-only, still controlled, with the read-only key carried by the preview rather than handed over.

## What This Asks For

1. **Build the map link** that combines the public preview with an embedded read-only key.
2. **Carry a read-only key with the public preview** (the existing read-only token, embedded), so the public link grants read-only access.
3. **Open the vault straight away in read-only** when the public link is followed (preview, then the vault, read-only).
4. **Do not require sharing the full key** (the public link is self-sufficient for read-only; the full key is never shared).
5. **Keep the controlled-exposure controls** (opt-in, timing/expiry, edit on settings; cross-ref: the public-vault-previews brief).

Estimated effort: small. It composes two existing, working features (public previews and read-only tokens); the work is the map link that carries the read-only key with the preview and auto-opens the vault read-only. The project lead expects it to be a nice, clean addition, an implementation of features-we-already-have combined.

## What This Does Not Try To Be

- **Not full-key sharing.** The embedded key is read-only; the full vault key is never shared.
- **Not a new trust mechanism.** It is the existing read-only token, carried with the preview.
- **Not uncontrolled exposure.** Opt-in, read-only, with the public-previews controls (timing, expiry, edit).
- **Not replacing the ask-for-key mode.** It adds the public read-only mode alongside the existing modes.

## Honest Risks

**Risk 1: A public read-only link exposes the vault contents to anyone with the link.** That is the point, but it must be a deliberate choice. Mitigation: opt-in per vault; read-only only; the controlled-exposure controls (timing, expiry); clear UX about what becomes publicly readable.

**Risk 2: Read-only must genuinely be read-only.** The embedded key must not grant more than read. Mitigation: use the existing, proven read-only token; verify it grants read only; security review of the embedded-key path.

**Risk 3: Confusion with the full-key hash mode.** Users might conflate read-only public sharing with full-key sharing. Mitigation: clear UX distinguishing public read-only (this feature) from sharing the full key; default public sharing to read-only.
