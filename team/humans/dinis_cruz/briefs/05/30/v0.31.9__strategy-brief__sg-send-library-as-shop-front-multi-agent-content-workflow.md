## What This Is

A content-strategy brief with two connected parts: **the library should become the shop front** (everything the project lead does ends up there as a page or a case study), and **the multi-agent content workflow** that produces and maintains it (content and communications vaults, a dev/content/QA agent collaborating via file-based email). The main point: get to a mode where everything done now ends up as content on the website, with the library as the single, up-to-date, public home for it all.

This builds on the publishing and single-source-of-content threads (cross-ref: the v0.27.62 public-vault-previews, the v0.31.9 public-preview-with-read-only-key, the v0.31.5 Vault App Store, and the parked single-source-of-truth idea from the reverse-PoC brief) and reflects a workflow that is now actually working: vaults are being created and shared for real use cases, and multiple agents are collaborating to build the site.

## The Context: It Is Working

The project lead opened with the evidence that this is real: **"yesterday I created three vaults and sent them to three different people, because now they have use cases, and I have a number of Claude sessions that know how to create vaults and are comfortable with it."** Vaults are being created and shared for genuine use cases, and the agent sessions are fluent at it. The strategy below is about capturing and scaling a workflow that already works, not proposing a hypothetical one.

### New Infrastructure: SG Compute And SG Playwright

A new piece of infrastructure makes the workflow easier: **SG Compute, which includes SG Playwright, a service to easily run Playwright sessions.** The project lead: **"we've added SG Compute, which has SG Playwright, a service to easily run Playwright sessions. The advantage is it makes it much easier for Claude Code sessions, even normal code, to just invoke Playwright functions and do browser automation."** So browser automation (Playwright) is now a service that agent sessions and ordinary code can invoke directly, which supports the content workflow (rendering, screenshots, browser-based checks; cross-ref: the Wardley-map rendering, which used Playwright Chromium, and the visualisation work). It is noted here as enabling infrastructure for the content workflow.

## Part One: The Multi-Agent Content Workflow

The workflow worth capturing: **multiple agents collaborating on the same vaults via file-based email.**

The project lead: **"we have two vaults, the content vault and the communications vault, and the idea is to create more content vaults. I have a dev agent, a content agent, and a QA agent, and they all have access to the same vault and collaborate via email, but it's file-based email. I created an email protocol, FS email, and they're sending messages to each other. It's working really well and has really good provenance."**

| Element | What It Is |
|---------|------------|
| **The content vault** | Holds the content (more content vaults to come) |
| **The communications vault** | Holds the agents' communications |
| **The dev agent** | The development work |
| **The content agent** | The content work |
| **The QA agent** | The quality assurance |
| **FS email (file-based email)** | The protocol the agents use to message each other (cross-ref: the FS email protocol discussed previously) |

The agents share the same vault and collaborate by sending each other file-based email (FS email, an email protocol over the filesystem/vault). The project lead noted two properties that make it work: it is collaborating well, and it has **really good provenance**, every message is a file, so who said what, when, and why is all recorded and version-controlled (cross-ref: the vault version-control and the provenance themes in the vault-per-standard and evidence briefs). This is a concrete, working instance of multi-agent collaboration on a vault, with the vault providing the shared substrate and the provenance, and FS email providing the coordination. It is a workflow pattern worth capturing and reusing (cross-ref: the agent-governance and sidecar themes).

The changes this workflow produces are already flowing: **"we've now made changes to the website, we're pushing changes by the content [agent]."** So the multi-agent workflow is already producing and pushing real website changes.

## Part Two: The Library As The Shop Front

The main ask: **everything the project lead does should end up as a page or information on the website, and the library should become the shop front.**

The project lead: **"I really want to get to the point where everything I do now ends up as a page or information on the website. Every time I send a link to somebody, especially public ones or examples I can talk about, we need a page on the site, in this case in the library, and eventually on the main site as case studies. I want this mode where everything I do goes there."**

The principle is **default-to-publish**:

| What The Project Lead Does | Where It Goes |
|----------------------------|---------------|
| Creates a vault (for a real use case) | A page in the library |
| Sends a public link or shareable example | A page in the library |
| Produces something public and talk-about-able | A case study (eventually on the main site) |
| Develops a skill | The library (so there is always up-to-date material) |

So the library becomes the up-to-date home for everything: every vault, every shareable example, every skill. The project lead: **"the library should become our shop front, the place where all the content goes, so we need to make sure it is up to date, and every time I create a vault, everything should be there. Even all the skills should be there, so there's always up-to-date stuff."** The library is the shop front (the public face that shows what the platform can do, through real examples and case studies) and the content home (the up-to-date, single place where everything lives).

This connects the publishing features (cross-ref: the public-vault-previews and public-preview-with-read-only-key briefs): a vault created and shared becomes a published, read-only, previewable page in the library. The default-to-publish mode is the habit; the publishing features are the mechanism; the library is the destination.

## Single Sources Of Content: Surface What Is Buried In GitHub

A specific problem the library should solve: **the single sources of content and materials are currently buried in GitHub, and the library should surface and link to them.**

The project lead: **"I start to create these single sources of content and materials that at the moment are quite buried inside GitHub, so we need to start linking to them. Even something like, where are the GitHub repos, where's information about sgit, where's information about SG/Vault, where's the detailed documentation, all that. The library acts as that."**

| Buried Material | Should Be Surfaced In The Library |
|-----------------|-----------------------------------|
| The GitHub repos | Linked from the library |
| Information about sgit | A clear home in the library |
| Information about SG/Vault | A clear home in the library |
| Detailed documentation | Linked and navigable from the library |

So the library is also the index to the single sources of truth: rather than leaving the repos, the sgit and SG/Vault information, and the documentation buried in GitHub, the library links to and surfaces them, becoming the navigable front door to everything. This picks up the single-source-of-content thread (cross-ref: the parked single-source-of-truth idea in the reverse-PoC brief): the library is where the single sources are made findable, even when the material itself lives in GitHub.

## Navigation And Presentation: Step Back And Explore

The project lead asked for deliberate thought on how the library works: **"take a step back, read the content, and see what is the best way to navigate it, the best way to access information, especially to present information. Really explore how this can work."** With everything flowing into the library, navigation and presentation become the key design questions:

| Question | Why It Matters |
|----------|----------------|
| **How to navigate it** | With everything there, navigation determines whether it is usable |
| **How to access information** | Finding the right content quickly |
| **How to present information** | The shop front must present well (it is the public face) |

This is where the visualisation and tree-view work applies (cross-ref: the visualisation-cornerstone brief's navigation, the VIV tree-view, and the connectors' tree-abstraction): the library needs good navigation and presentation over a growing body of content. The project lead wants this explored properly, because the library's value depends on it: a shop front that is hard to navigate fails as a shop front.

## The Library Is The Main Communication Medium

The framing the project lead closed on: **the library is now the main communication medium.** The project lead: **"the library, sgit/SG/Vault, is now our main communication medium."** So the library is not a side artefact; it is the primary channel through which the project communicates what it does, via real, up-to-date, navigable content and case studies. Everything the project lead and the agents produce flows there, and it is where people (collaborators, prospects, users) go to understand and engage with the platform. This is the culmination of the publishing, single-source, and content-vault threads: one up-to-date, public, navigable shop front, fed by the multi-agent workflow, as the project's main way of communicating.

## What This Asks For

1. **Capture and reuse the multi-agent content workflow** (content and communications vaults; dev/content/QA agents; FS email; the good provenance).
2. **Adopt default-to-publish** (everything done, every vault, every shareable example, every skill, ends up as a page in the library).
3. **Make the library the shop front** (the public face and the up-to-date content home).
4. **Keep it up to date** (every vault created flows there; the content stays current).
5. **Surface the single sources buried in GitHub** (link to the repos, sgit and SG/Vault information, and the documentation from the library).
6. **Explore navigation and presentation** (step back, read the content, find the best way to navigate, access, and present; apply the tree-view/visualisation work).
7. **Treat the library as the main communication medium** (the primary channel; case studies on the main site eventually).
8. **Leverage SG Compute / SG Playwright** (browser automation as a service for the content workflow).

Estimated effort: the workflow and the publishing mechanisms exist (the agents, FS email, the vaults, the public previews, SG Playwright); the new work is the default-to-publish habit and tooling (every vault flows to the library), the library's navigation and presentation, and surfacing the GitHub-buried single sources. The content vaults and the agent workflow are already producing and pushing changes, so this scales a working system.

## What This Does Not Try To Be

- **Not a hypothetical workflow.** The multi-agent workflow is already working and pushing changes; this captures and scales it.
- **Not content buried in GitHub.** The library surfaces and links the single sources.
- **Not a side artefact.** The library is the main communication medium and the shop front.
- **Not a publish-some mode.** Default-to-publish: everything flows to the library.
- **Not unnavigable.** Navigation and presentation are explored deliberately.

## Honest Risks

**Risk 1: Default-to-publish could expose things prematurely.** Everything-goes-to-the-library could publish something not meant to be public. Mitigation: the controlled-exposure model (cross-ref: the public-vault-previews brief); public is opt-in and read-only per vault; default-to-publish is the habit for the public/shareable things, not the private ones.

**Risk 2: The library could become an unnavigable dump.** Everything-there fails if it is not navigable. Mitigation: the deliberate navigation/presentation work (the project lead's explicit ask); the tree-view and visualisation machinery; curation as it grows.

**Risk 3: Keeping it up to date is ongoing work.** A stale shop front is worse than none. Mitigation: the multi-agent workflow and default-to-publish keep it current; every vault flows there automatically.

**Risk 4: FS email and multi-agent collaboration need governance.** Multiple agents on one vault need coordination. Mitigation: FS email gives provenance (who said what); the agent-governance and version-control themes apply (cross-ref); the workflow is already working well.
