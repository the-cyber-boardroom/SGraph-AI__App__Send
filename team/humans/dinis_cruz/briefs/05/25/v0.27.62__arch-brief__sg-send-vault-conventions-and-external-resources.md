## What This Is

The second of two briefs expanding the vaults-within-vaults idea (cross-ref: the sub-vaults-workflow brief, which covers the access mechanics). This one covers **codifying conventions through specific files, and using them to map external resources into a vault**: a pointer-file convention (alongside the existing `app.json` and `_page.json`) that tells the UI "there is a vault, or a resource, here, and here is how to load it," and the powerful extension that the same pattern can embed external resources (a YouTube video, a link, an external app) inside a controlled iframe.

The project lead asked explicitly to split the vault-of-vaults discussion into two: the workflow and access points (the companion brief), and this codifying-conventions-and-external-resources piece. The unifying idea here: a small set of convention files turns a vault into a place that can point at other vaults and at the outside world, with controlled access.

## Codifying Conventions Through Specific Files

The core mechanism: **codify the nesting and resource references as specific convention files, the same way the platform already uses `app.json` and `_page.json`.**

The voice memo: **"I like the idea of creating a convention the same way we already have the app dot json and the underscore page dot json. We can create as many more as we want. We could create one called vault dot json or dot vault dot json, which is a page that exists on disk, containing the reference for that page, which means the UI knows that at this moment I need to access that."**

The platform already has convention files that the UI understands (cross-ref: the create-vault-content conventions: `app.json`, `_page.json`). The proposal extends this: add more convention files, each telling the UI something about what lives at a location. A vault-pointer convention file would record the reference to a vault, so that when the UI encounters it, it knows to go and get (clone) that vault.

| Existing Convention | New Convention (Proposed) |
|---------------------|---------------------------|
| `app.json` (an app definition) | A vault-pointer file (a reference to a vault to clone) |
| `_page.json` (a page layout) | Resource-pointer files (references to external resources) |

What a vault-pointer file contains, per the voice memo: **"that is where the reference for the vaults is, where the IDs are, even where we have the decryption key, the access key, or the encrypted vault key."** So the pointer file holds what the UI needs to access the referenced vault: its ID, and its key (the decryption/access key, or the encrypted vault key, stored reader-only per the `.vault` double-encryption pattern from the companion brief). The voice memo's summary: **"we create a page like dot vault dot json, which tells the UI that there's a vault here, and whenever you access a file here or below, you should clone the vault and look at the files inside."**

This is the same submodule-pointer idea as the companion brief, expressed as a codified convention file: a small file on disk that says "a vault lives here; clone it on access." It makes the sub-vault workflow concrete and uniform with the platform's existing convention-file approach.

## The Naming Question (Deliberately Left Open)

The voice memo spent time on naming and deliberately left it open, with a clear preference for simplicity. The candidates floated: `vault.json`, `.vault.json`, `.action.vault.json`, and (for resources) patterns like `link.vault.json`, `url.youtube.json`, and for apps something like `.sgv.json` or `email.app.json`.

The voice memo's own conclusion was to keep it simple and name things for what they are: **"let's keep it simple. Maybe we just call them what it is. Because it's convention, right? So let's keep it simple."** The concern it flagged: avoid awkward stacked extensions (the worry about `dot vault dot vault dot json` and similar). The recommendation to carry forward: **pick simple, descriptive convention names that say what the file points at, and avoid stacked or redundant extensions.** The exact strings are a naming decision to settle when building; this brief records the candidates and the keep-it-simple principle rather than fixing a final name.

| Points At | Candidate Names (To Settle) |
|-----------|----------------------------|
| A vault | `vault.json` / `.vault.json` |
| A link or URL | `link.json` / a URL-pointer convention |
| A YouTube video | a YouTube-resource convention |
| An external app | `.sgv.json` / an app-pointer convention |

The principle (keep it simple, name it for what it is, avoid stacked extensions) matters more than the specific strings; settle the strings during implementation.

## Mapping External Resources Into The Vault

The powerful extension, and the part the project lead was most enthusiastic about: **the same convention pattern can map external resources into a vault, loading them in a controlled iframe.**

The voice memo: **"while we're here, let's think about adding other types of external resources. Say I want to add a video, embed a YouTube video, add a link, anything we can open in an iframe. We don't have to provide an app, we don't have to provide full access, so it gets controlled. Any external web page or resource we load here is loaded in an iframe that doesn't have access, or we can selectively choose to add access."**

So a resource-pointer convention file records an external resource, and the UI loads it in an iframe with controlled (by default, no) access to the vault. The control is the key property:

| Resource | Loaded As | Access |
|----------|-----------|--------|
| A YouTube video | An iframe | No vault access (it is just an embed) |
| A link / external web page | An iframe | No vault access by default; selectively grant if needed |
| An external app | An iframe | Controlled; selectively grant access to vault data if appropriate |

The voice memo's insight on why this is valuable: **"this allows me to load up other apps that are now hosted outside the vault."** Combined with the existing app-in-the-vault idea (cross-ref: the v0.27.60 Wardley apps-in-the-vault map, where a vault plus HTML becomes a mini app), this adds the complement: apps and resources hosted *outside* the vault, embedded *into* it via a controlled iframe. The vault becomes a place that can compose both its own content (vaults, files, in-vault apps) and external resources (videos, links, external apps), with the iframe boundary controlling what each embedded resource can access.

The voice memo gave a concrete example: an email system embedded as an app, referenced by a convention file (something like `email.app.json` or an `.sgv.json` app-pointer). The app is hosted outside, embedded in a controlled iframe, and the convention file is how the vault knows to load it. This is a controlled plugin/app model for the vault: external apps as embedded, access-controlled iframes, declared by convention files.

### Why The Controlled Iframe Matters

The iframe boundary is the security mechanism: an embedded external resource runs in an iframe that by default cannot reach the vault's data, and access is granted selectively and explicitly if needed. This means a vault can safely embed arbitrary external resources (a video, a third-party app) without exposing its contents, because the iframe sandbox is the default-deny boundary. This is consistent with the platform's least-privilege, controlled-access stance (cross-ref: the SG/Sentinel least-privilege and controlled-access principles, and the SG/Send authentication least-privilege storage): embed freely, grant access narrowly.

## What This Asks For

For the vault team and product:

1. **Add convention files for vault pointers** (alongside `app.json` and `_page.json`): a file that records a vault reference (ID and key, stored reader-only) and tells the UI to clone on access.
2. **Settle the naming** (keep it simple, name for what it is, avoid stacked extensions; candidates recorded above).
3. **Add convention files for external resources** (link, video, app pointers).
4. **Load external resources in controlled iframes** (default no vault access; selectively grant).
5. **Support the external-app (plugin) model** (external apps embedded via a convention file in a controlled iframe).
6. **Keep it uniform with the existing conventions** (the same approach as `app.json`/`_page.json`, which the UI already understands).

Estimated effort: the vault-pointer convention is light and reuses the existing convention-file approach; the external-resource iframe embedding is a UI capability (load in iframe, control access); the external-app plugin model builds on both and on the apps-in-the-vault direction. Naming is a quick decision to settle at build time.

## What This Does Not Try To Be

- **Not native vault functionality.** These are convention files plus UI behaviour (consistent with the companion brief's decision).
- **Not a fixed naming scheme.** The candidates are recorded; the strings are settled at build time, keeping it simple.
- **Not uncontrolled embedding.** External resources load in controlled iframes; access is default-deny, granted selectively.
- **Not the access-mechanics design.** That is the companion sub-vaults-workflow brief.

## Honest Risks

**Risk 1: Convention-file proliferation could get confusing.** Many `*.json` convention files could be hard to keep straight. Mitigation: keep names simple and descriptive; avoid stacked extensions; document the conventions (as `app.json`/`_page.json` are documented).

**Risk 2: Embedding external resources has security implications.** An embedded external page or app could try to reach vault data. Mitigation: the iframe is default-deny; access is granted selectively and explicitly; this is the core control property and must be enforced.

**Risk 3: A pointer file holds a vault key/reference.** The vault-pointer file contains sensitive references. Mitigation: store it reader-only via the `.vault` double-encryption pattern (cross-ref: the companion brief); PKI when it lands.

**Risk 4: Naming churn.** Leaving naming open risks inconsistency if not settled. Mitigation: settle the strings early at build time using the keep-it-simple principle; the candidates are recorded here.
