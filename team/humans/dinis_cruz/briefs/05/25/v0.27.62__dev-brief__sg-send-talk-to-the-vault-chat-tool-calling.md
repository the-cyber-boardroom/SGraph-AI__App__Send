# Talk To The Vault: Wiring Up Chat With Tool-Calling Inside The Vault

## What This Is

The brief (to create the brief, in the project lead's words) for adding **chat to the vault**: a chat window inside the vault UI, with tool-calling, that is aware of what is in the vault and can read and modify its files. The standout use case is doing inside the vault what the project lead currently does with Claude: modifying files, adding files, and creating infographics and abstracts from files. The key point is that the pieces already exist (in the tools), so this is largely a wiring-up exercise rather than a build from scratch.

This brief opens with a short confirmation that the previous capability (public vault previews) has shipped and is working, then maps the talk-to-the-vault feature.

## Public Vault Previews Shipped (Confirmation)

The public-vault-previews capability (cross-ref: the v0.27.62 public-vault-previews brief) is now built and working. The project lead confirmed it: **the ability to own a URL and create a public description, using the slug to recalculate the value retrieved from SG/Send file storage.** The payoff is exactly as the brief anticipated: **sharing a link on social media, WhatsApp, or LinkedIn becomes ridiculously more effective, because the link is no longer some random string, it is something you can design**, even a collage. The project lead has already used it for trip-photo pages (a recent trip to the Algarve, and a Porto conference trip), sharing the link directly while the vaults work behind the scenes.

This is a validation of the previous brief, not a new design. It is noted here because it is the immediate context for the next feature: now that a vault has a usable, shareable front, the natural next step is to make the vault interactive through chat.

## The Feature: Talk To The Vault

The new capability: **a chat window inside the vault, with tool-calling, that is aware of the vault's contents and can act on them.**

The voice memo: **"the feature I would like to add is the feature of talk to the vault. Leveraging the concept of tools, which we have done before. The idea that we can see the tools execution, making the chat aware of what's in the vault, and seeing the conversations that happen there. The key capabilities: a chat window, and especially the tools calling, that is very important."**

Three capabilities define it:

| Capability | What It Does |
|------------|--------------|
| **A chat window** | Converse about the vault, inside the vault UI |
| **Vault awareness** | The chat knows what is in the vault (its files and contents) |
| **Tool-calling** | The chat can call tools to act on the vault, with the tool execution visible |

The project lead stressed tool-calling as the most important part: a chat that can only talk is far less useful than one that can act (read files, add files, run tools), with the tool execution visible so the user sees what is happening.

## The Pieces Already Exist In The Tools

The crucial point the voice memo made: **we already have all the components we need in the tools, so this should just be wiring up.**

The voice memo: **"this is something we already have a lot of the pieces of the puzzle in place for, so we should just be able to wire it up. Something we explored in the past, but now we should have all the components in the tools website."**

This is accurate. The components exist (cross-ref: the tools work at tools.sgraph.ai and the agentic-tooling history):

| Existing Component | Where It Came From |
|--------------------|--------------------|
| The tools website | tools.sgraph.ai |
| Agentic LLM tool-calling (sandboxed execution) | The agentic tool-calling work |
| Tool-execution visibility | The tools concept, with visible execution |
| Infographic generation | The infographic tool (sub-10-cent cost) |
| Client-side LLM tools and chat | The LLM chat and client-side tools work |
| OpenRouter billing and per-user keys | The OpenRouter integration (cross-ref: the SG/Send authentication brief: the user's own OpenRouter key) |

So talk-to-the-vault is a composition of existing parts: the tools (with tool-calling and visible execution) pointed at the vault, with the chat made vault-aware. The voice memo's framing (wire it up, the components are there) is the right one: this is integration, not invention. The project lead has experience with the tools concept and has explored chat-with-the-vault before; now the components are mature enough to wire together.

## Read-Write Access (The Vault Is Self-Contained)

A decision the voice memo worked through in real time: **the chat needs read-write access to the vault, not just read-only.**

The voice memo: **"let's only give it read-only access. Well, actually, it needs to be able to add files, so we can give it read-write access to the vault, because the vault is self-contained."** The initial instinct (read-only, the safer default) gave way to the realisation that the marquee use cases require writing: adding files, modifying files, creating infographics into the vault. And the justification is sound: the vault is self-contained, so read-write access is scoped to that one vault. The blast radius of the chat's tool-calling is the vault itself, nothing wider, which makes read-write access acceptable.

This connects to the controlled-access and blast-radius thinking elsewhere (cross-ref: the SG/Sentinel agent-governance brief, the vault-conventions controlled-iframe stance): the chat is an agent acting with tools, and its scope is bounded to the self-contained vault.

## The Use Case: What The Project Lead Does With Claude, Inside The Vault

The motivating use case is concrete: **do inside the vault what the project lead currently does with Claude, namely modify files, add files, and create infographics and abstracts from files.**

The voice memo: **"the thing I like to do is modify files, add new files, and more importantly create infographics and abstracts from files, kind of like what I've been using Claude for in my stuff. I would like to start doing that from inside the vault."** The pattern is exactly this conversation: a chat that reads the files, acts on them with tools (modify, add, generate infographics, write abstracts), and shows the work. The project lead does this today in Claude; the feature brings it inside the vault, where the files live, so the loop is closed (the files, the chat, and the tool outputs are all in the one self-contained vault).

The infographic generation is called out as especially desirable, and it is an existing tool (the sub-10-cent infographic generator), so the wiring is: the in-vault chat can call the infographic tool on a file in the vault and write the result back into the vault.

## The UI: A Pane On The Right

The UI direction the voice memo gave: **open the chat in a pane on the right (or a separate window/side), to connect the dots and try it.**

The voice memo: **"we need to think about, from a UI point of view, where do we open it. Maybe a different window, a different side, a different pane on the right. A pane on the right, to connect the dots and to try it."** The chat sits alongside the vault contents (a right-hand pane), so the user sees the vault and converses with it at the same time. This is a starting point to try, not a fixed final design; the priority is to wire it up and try it.

## What This Asks For

1. **Wire up a chat window inside the vault UI** (using the existing tools/chat components).
2. **Make the chat vault-aware** (it knows the vault's files and contents).
3. **Enable tool-calling with visible execution** (the most important capability; the user sees the tools run).
4. **Give read-write access to the vault** (add and modify files; scoped to the self-contained vault).
5. **Wire in the existing tools** (especially the infographic generator; modify/add files; abstracts from files).
6. **Open it as a pane on the right** (a starting UI to try).
7. **Use the user's own OpenRouter key** (cross-ref: the authentication brief; the chat runs on the user's key).

Estimated effort: low-to-moderate, because the components exist (tools, tool-calling, visible execution, infographic generation, client-side chat, OpenRouter billing). The work is integration: pointing the tools at the vault, making the chat vault-aware, wiring read-write to the self-contained vault, and placing the pane. The voice memo's expectation (wire it up) is realistic.

## What This Does Not Try To Be

- **Not a new tools engine.** It composes the existing tools and tool-calling.
- **Not read-only.** Read-write is needed and acceptable (the vault is self-contained).
- **Not a finished UI.** The right-hand pane is a starting point to try.
- **Not unbounded.** The chat's scope is the one self-contained vault.

## Honest Risks

**Risk 1: Read-write tool-calling could modify the vault unexpectedly.** An agent with write access can change files. Mitigation: the vault is self-contained (bounded blast radius); the vault is version-controlled (changes are revertible, cross-ref: the vault version-control work); tool execution is visible so the user sees what happens; confirm destructive actions.

**Risk 2: Tool-calling cost.** LLM and tool calls cost money. Mitigation: the chat runs on the user's own OpenRouter key (cross-ref: the authentication brief and the budget model); the infographic tool is already low-cost; cost is attributed (cross-ref: the SG/Sentinel cost-attribution brief).

**Risk 3: Wiring up existing components may surface integration gaps.** Composing parts that were not built together can reveal mismatches. Mitigation: the components are mature and used; try it in the right-hand pane first; iterate.

**Risk 4: Vault awareness must respect the vault boundary.** The chat should see only this vault. Mitigation: scope the awareness and access to the self-contained vault; no cross-vault reach without explicit action.
