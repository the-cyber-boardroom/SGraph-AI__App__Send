## What This Is

The first of two briefs expanding the vaults-within-vaults idea (cross-ref: the v0.27.60 vaults-within-vaults dev brief). This one covers the **sub-vaults workflow**: how a vault references and opens other vaults, the decision to do it as a convention rather than native vault support, the existing `.vault` folder and read-only-token pattern it builds on, and the three places a sub-vault can be accessed (CLI, Vault Web UI, iframe). The companion brief covers codifying conventions and mapping external resources.

The guiding decision, in the project lead's words: **do we add native support to the vault, or does this become a UI thing, like submodules and remotes in Git? The logic is to do the second.** Sub-vaults are not a new primitive baked into the vault; they are a convention layered on top, exactly as Git submodules and remotes are conventions layered on Git rather than core object-store features. The only thing added is a couple of extra files that describe the nesting.

## The Decision: A Convention, Not Native Vault Support

The architectural choice that frames everything: **sub-vaults are implemented as a convention (a few files plus UI behaviour), not as native vault functionality.**

The voice memo: **"the question is, do we add native support to the vault, or does this become a UI thing, kind of like submodules and remotes that get added on top in Git? The logic is to do the second. The only thing we add is a couple of extra files that contain this."**

This is the Git submodules analogy, and it is apt: Git does not have nested repositories as a core concept; submodules are a convention (a `.gitmodules` file plus tooling behaviour) that records "another repo lives at this path." Sub-vaults follow the same pattern: a convention file records "another vault lives here," and the tooling (UI, CLI) knows how to act on it. The vault primitive itself stays simple and unchanged; the nesting is a layer above it.

The benefit is the same as Git's: the core stays simple and the capability is additive. It also fits the standing no-backend-complexity principle (cross-ref: the v0.27.60 vaults-within-vaults brief): the vault does not grow a new feature; a convention plus existing mechanisms carries the capability.

## Building On The Existing `.vault` Folder And Read-Only Tokens

The convention builds on machinery that already exists: **the `.vault` folder, and the read-only-token plus double-encryption pattern.**

The voice memo: **"there's already a folder which we started to add, which is called dot vault. We added the ability to create read-only tokens, and to create multiple read-only tokens, which also becomes a share capability. The key point is we added the pattern, and this is a convention, not codified in the vault itself, but a pattern we use on the vault web to put data inside the dot vault and double-encrypt it with the right key."**

Two existing pieces matter here:

| Existing Mechanism | What It Provides |
|--------------------|------------------|
| **The `.vault` folder** | A conventional place inside a vault to put metadata and special files (already used in a couple of situations) |
| **Read-only tokens (multiple, double-encrypted)** | The ability to create read-only tokens, which also serve as a share capability; data placed in `.vault` and double-encrypted with the right key so only the intended reader can see it |

The read-only-token pattern is an interesting combination of techniques (cross-ref: the layered-encryption and recipient-key work, and the read-key-vs-access-token distinction from the CLI work): data can be placed in the vault such that only the holder of the full vault key (or the right reader key) can open it. The voice memo: **"we now have files that only with the full vault key you can open, and that is the feature we should leverage here."** This is the foundation for sub-vaults: a place (`.vault`) to put secrets and references that only the intended reader can decrypt, which is exactly what a sub-vault reference needs (the child vault's key or reference, readable only by those entitled to it).

This is also explicitly **in preparation for PKI** (cross-ref: the SG/Sentinel deployment-modes PKI work): the voice memo noted PKI is coming soon, and the read-only-token-into-`.vault` pattern is the bridge. Once PKI lands, the sub-vault references and keys can be encrypted to specific recipients' public keys, but the convention works now with the double-encryption pattern.

## The Sub-Vaults Convention

The convention itself, following the Git-submodules shape: **if a vault has a `.vault` folder, the tooling looks inside it for a sub-vaults reference (a file, or a folder with a file per sub-vault), and uses it to access the referenced vaults.**

The voice memo: **"if you load up the dot vault, and if that exists, you can read a file in there that may be called sub-vaults, or we have a folder in there with a file per sub-vault. From a UI point of view you then have the concept of accessing, reading, and writing into that sub-vault."**

| Convention Element | Role |
|--------------------|------|
| **The `.vault` folder** | Where the sub-vault references live (in the double-encrypted, reader-only pattern) |
| **A sub-vaults file (or folder with a file per sub-vault)** | Records the referenced child vaults (their IDs, references, and keys) |
| **The tooling behaviour** | On encountering the convention, the tooling can access (read and write) the referenced sub-vaults |

The reference to each sub-vault is what the holder needs to clone and open it (its ID and key), placed so only the entitled reader can decrypt it. Adding a sub-vault is editing this file; the voice memo: **"every time I want to add a vault, you just edit that."** This is the simple, file-based management the project lead wanted: managing vaults-of-vaults becomes editing vault reference files, not operating bespoke machinery.

## The Three Places A Sub-Vault Is Accessed

The part that needs the most thought: **a sub-vault can be accessed from three places, each with different complexity, and they need not all be built at once.**

The voice memo: **"there are three places where you could access this vault, and each requires a bit of thinking. One is the CLI, one is the Vault Web UI, and one is the iframe that exists inside the vault UI or the app that needs access to that data."**

| Access Point | What It Is | The Complexity |
|--------------|------------|----------------|
| **CLI (sgit)** | Reading/cloning the sub-vault from the command line | Tracking where it is stored, where the file exists, and how to clone within clones (clone-within-clone) |
| **Vault Web UI** | Accessing the sub-vault from the web vault browser | The primary need; this is where the use case lives |
| **iframe** | An app or page inside the vault UI that needs access to the sub-vault data | Controlled access for embedded apps/resources (the companion brief develops this) |

The CLI case introduces real complexity, as the voice memo noted: **"it means we need to track where it is stored, where the file exists, and how to clone within clones."** Nested cloning (a clone that itself contains sub-vault references to clone) is the hard part, exactly the submodule-update problem in Git. This is why the convention approach helps: the references are explicit files, so the CLI can resolve them step by step.

The voice memo identified where to start: **"this is a good example that we might actually try to do this on the cloud, on the vault web, because that's where the need is."** The Vault Web UI is the first target, because the driving use case (the doctor accessing per-user vaults, cross-ref: the private knee-score MVP) lives there. The CLI and iframe access can follow.

### On-Demand Versus Pre-Loaded

A design question the voice memo raised: **how much is loaded up front versus accessed on demand, because there could be many nested vaults.**

The voice memo: **"how much of it do you enable, and how much is on demand versus loaded up, because you can have tons and tons of inner vaults. It could be one of those cases where you pre-initialise on access, the same way we do a folder."** With potentially many sub-vaults, loading them all eagerly would be wasteful. The model the voice memo preferred is pre-initialise-on-access: a sub-vault is cloned/opened when it is accessed, the same lazy pattern already used for folders. This keeps a vault-of-many-vaults tractable: the references are all present (cheap), but the actual sub-vault contents are fetched only when needed.

## The Driving Use Cases

The voice memo grounded this in two concrete needs:

- **The doctor accessing per-user vaults** (cross-ref: the private knee-score MVP): the main use case, where a parent/admin context needs to read many per-user vaults. The voice memo: **"the main use case is we want the doctor to be able to access the vaults."**
- **The project lead managing vaults of vaults**: an existing personal need. The voice memo: **"I now have a case where I need to manage vaults of vaults, so this will make it much simpler, because you just have vault files, and every time I want to add a vault, you edit that."**

Both are the same shape: a context that references and opens a set of other vaults, managed as simple reference files. The sub-vaults convention serves both.

## What This Asks For

For the vault team:

1. **Implement sub-vaults as a convention, not native vault support** (the Git-submodules model: a few files plus tooling behaviour).
2. **Build on the `.vault` folder and the read-only-token double-encryption pattern** (references stored so only the entitled reader decrypts them; in preparation for PKI).
3. **Define the sub-vaults reference convention** (a file, or a folder with a file per sub-vault, holding each child's reference and key).
4. **Start with the Vault Web UI access point** (that is where the need is), then add CLI and iframe.
5. **Handle the CLI clone-within-clone complexity** (track storage location and resolve nested clones) when building the CLI path.
6. **Use pre-initialise-on-access** (lazy clone sub-vaults on access, like folders, to handle many nested vaults).
7. **Support read and write** to sub-vaults (not just read), though not all access points need it at the start.

Estimated effort: the Vault Web UI path is the near-term build and the priority (the use case lives there); the CLI clone-within-clone is the more complex follow-on; the iframe path connects to the companion brief's external-resources work. The convention itself is light (a few files), reusing existing mechanisms.

## What This Does Not Try To Be

- **Not native vault functionality.** Sub-vaults are a convention on top, like Git submodules.
- **Not all three access points at once.** Start with the Vault Web UI; CLI and iframe follow.
- **Not eager loading.** Pre-initialise on access, given potentially many nested vaults.
- **Not the conventions/external-resources design.** That is the companion brief.

## Honest Risks

**Risk 1: Clone-within-clone (CLI) is genuinely complex.** Nested cloning and tracking storage locations is the submodule-update hard problem. Mitigation: start with the Web UI (no clone-within-clone); when building the CLI, resolve references step by step; the explicit reference files make resolution tractable.

**Risk 2: Many nested vaults could be heavy.** A vault of many vaults could be slow if mishandled. Mitigation: pre-initialise on access (lazy); references are cheap, contents fetched on demand.

**Risk 3: A convention is not enforced by the vault.** Because it is a convention not native support, nothing stops malformed references. Mitigation: the tooling validates the convention; this matches Git submodules (also a convention) which work well in practice.

**Risk 4: Reader-only access must hold.** Sub-vault references and keys must be readable only by the entitled reader. Mitigation: the existing double-encryption / read-only-token pattern; PKI when it lands; the `.vault` reader-only convention.
