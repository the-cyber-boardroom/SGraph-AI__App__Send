# Public Vault Previews: Controlled Exposure, Shareable Links, And A Friendlier Front Page

**version** v0.27.62
**date** 25 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, Security, @Dev
**type** Arch brief

---

## What This Is

A brief (drawn from two memos, the second a continuation of the first) on a single capability: **public vault previews.** The idea is to give a vault an optional, deliberately-public set of preview information (a title, description, and thumbnail/screenshot) that can be rendered as a web page, shown on the vault's own front page, and surfaced as the social-share preview when a vault link is posted to WhatsApp, LinkedIn, or anywhere that loads link previews. Accessing it works in two modes: with just the public ID you see the preview and are asked for the key; with the key in the URL the vault loads automatically.

The framing the project lead opened with is the heart of it: **this deliberately creates an exposure, but a controlled one.** Is it creating a vulnerability, or creating an exposure? It is an exposure, created in a controlled way, that the user chooses. This is a usability feature that trades a sliver of opacity for a large gain in shareability and clarity, with the user in control of the trade.

This builds on the vault conventions work (cross-ref: the v0.27.62 vault-conventions-and-external-resources brief: the pointer-file convention) and the vault-key-sharing model (cross-ref: the v0.27.60 authentication brief), and it uses the controlled-exposure, timing, and expiry ideas (cross-ref: the SG/Sentinel time brief and the SG/Send identity-persistence-budgets ephemeral-by-default model). The public-preview capability itself, the deterministic derivation, and the two-mode UX are new.

## The Problem: Vaults Are Too Opaque To Share Well

The motivating problem: **vaults are very opaque. If you do not have the key, all you have is a key, so they are hard to manage and hard to understand.**

The voice memo: **"the vaults are very opaque. If you don't know what's in the vault, all I have is a key, so they become very hard to manage, very hard to understand what's going on. You really need the decryption key or the read key to see what's in the vault, but that introduces a bunch of attrition."**

The attrition is real and the project lead feels it personally: **"even me, I now send a lot of links, but who's on what link? That's quite problematic."** When every vault link looks identical (an opaque ID, needing a key to reveal anything), even the sender loses track of which link is which. And the current workflow tends to send the share key in the same place as the link, which is its own problem.

There is also a legitimate-use argument: **not every vault's title or description is confidential.** The voice memo: **"you could have a vault where the title doesn't have confidential information. This is where we treat users as capable, as long as they're aware. We allow them to choose."** Some vaults are meant to be shared widely (demos, public materials); forcing them to be fully opaque serves no one. The principle (cross-ref: the SG/Send open-evaluation brief's treat-users-as-capable stance): let the user choose what, if anything, to expose, with awareness of the trade. The voice memo also noted that commercial environments have more protections (more isolation between users, dedicated instances), so the public-preview mode is a choice, appropriate for some vaults and not others.

## The Capability: A Deliberately-Public Preview

The capability: **an optional public set of information about a vault (a title, description, thumbnail/screenshot) that is deliberately exposed, so it can be rendered and shared.**

The voice memo: **"a mode to have a mini exposed set of information, almost like a public page of the vault, that we can use to share the data. It means you can do a much better preview thumbnail, screenshot, little description of what's in the vault when you share a link, because I've had that request."**

What being deliberately public unlocks (the voice memo was explicit that the public-ness is what makes these acceptable): **"the moment we say this is all public, it means we can save this data in a folder server-side, we can save the key in the logs, the URL can actually contain the key."** Because the preview information is chosen-to-be-public, the usual zero-knowledge constraints do not apply to it: it can be stored server-side, it can appear in logs, and the access key for it can live in the URL. This is the controlled exposure: a clearly-bounded, user-chosen public surface, separate from the vault's still-encrypted contents.

| Property | The Vault's Contents | The Public Preview |
|----------|---------------------|--------------------|
| Encryption | Encrypted, zero-knowledge | Deliberately public |
| Server-side storage | Not in clear | Can be stored server-side |
| In logs / URL | Never | The preview key can be in the URL and logs |
| Who chooses | n/a | The user chooses to expose it |

## How It Works: A Deterministic Public Vault ID

The mechanism, from the continuation memo: **a public vault ID (a string in the URL) from which the SG/Send transfer ID and a read-only decryption key are deterministically derived, used to fetch and render the public preview.**

The voice memo: **"have a deterministic way to create the send key. From whatever this text is, you calculate the transfer ID and the decryption key, and we go and get the data. We are going to leak, almost like, a deterministic vault key."**

The workflow:

1. The user visits a URL like `/en-gb/app/vault-demo-health-data` (the public vault ID is the last segment).
2. From that string, the system deterministically calculates the SG/Send transfer ID (where to download) and the read-only decryption key.
3. It fetches the data at that transfer ID and decrypts it with the derived read-only key.
4. Inside, by convention, is a JSON file with the public information: title, description, and a thumbnail or screenshot (pre-generated, renderable).
5. That public information is rendered (as the page, as a thumbnail, and as the social-share preview).

The deliberately-leaked deterministic read-only key is the crux: the public ID *is* the key (it derives the read-only decryption key), so anyone with the public ID can read the public preview, which is exactly the intent. This is a read-only key for public information only; the vault's real contents still require the proper vault key. The voice memo's insight that delighted the project lead: **"for vaults I want to share publicly, I could even use this as a way to share the read-only decryption key."** The public ID doubles as the read-only key for the public layer.

### The Convention File Inside

The public information inside the fetched data is a convention JSON (cross-ref: the v0.27.62 vault-conventions brief's pointer/convention files): the voice memo: **"inside it we can have a JSON file that contains the title, description, and maybe a thumbnail or screenshot we've pre-generated that can be rendered."** This is the same convention-file approach as the rest of the vault work: a known JSON file the UI understands, here holding the public preview. It can be rendered as a client-side thumbnail, generated on the page, and shown on the vault's own front page.

### User-Defined Or Random Public IDs

The public ID can be system-generated or user-chosen. The voice memo: **"this could be a random string, or we could allow the user to define its own, like mvp-demo-x, which makes it quite nice."** A user-defined ID (`vault-demo-health-data`, `mvp-demo-x`) makes the link readable and meaningful, which directly addresses the which-link-is-which problem.

A deliberate distinction the voice memo drew: **this is not a Simple Token.** The voice memo: **"I don't want to make it a Simple Token, because we're going to refactor those, and because this is different. This is literally not the normal decryption token."** The public ID is its own concept (a deterministic public-preview key), separate from the Simple Token mechanism (which is being refactored). Keeping them distinct avoids coupling this new capability to a mechanism in flux.

## The Two Access Modes

The UX, from the continuation memo: **two modes, depending on whether the vault key is in the URL.**

The voice memo: **"the workflow is /en-gb/app/ then the public ID. If you put a hash with the vault key, that will be transparent: we can load it automatically. If you don't put the decryption key, we show the rendering of that public information, and then ask the user for the decryption key."**

| URL | What Happens |
|-----|--------------|
| `/en-gb/app/<public-id>` | Show the public preview (title, description, thumbnail), then ask the user for the decryption key |
| `/en-gb/app/<public-id>#<vault-key>` | The key is in the hash fragment; load the vault automatically (show the preview quickly, then load the contents) |

The hash-fragment carries the vault key transparently (a hash fragment is not sent to the server, which suits a client-side decryption key). When present, the vault loads automatically; when absent, the user sees the public preview and is prompted for the key. The voice memo on the auto-load: **"if that happens we can load it automatically. Maybe we still show the preview quickly and pre-automatically load the other stuff as soon as you render."** So even in the auto-load case, the public preview renders first (fast), then the real contents load.

This is a much better UX than today: the link looks and feels like the right thing (a real preview, not an opaque ID), and the decryption key is shared separately (or carried in the hash). The voice memo: **"now I'm sharing a link that actually looks and feels like the right thing, and then I share the decryption key."**

## Social-Share Previews (The Meta-Tag Card)

A specific, valuable payoff from the continuation memo: **the public preview powers the link-preview card that platforms generate when a vault link is shared.**

The voice memo: **"when I share a vault link on WhatsApp, LinkedIn, or any place that does the behind-the-scenes preview loading, we can now make sure that little preview, that meta tag, that metadata, is implemented."** When a link is posted to a platform that fetches link previews, the platform reads the page's metadata (the Open Graph / meta tags) to build the preview card. Because the public preview is deliberately public and server-renderable, the page can expose those meta tags, so the shared link shows a proper title, description, and thumbnail, instead of nothing. This directly answers a request the project lead has had, and it makes shared vault links look legitimate and informative.

## Corporate-Friendliness: Disclaimers And Support Links

A benefit the continuation memo highlighted: **the public page is a place to add disclaimers and support links, which makes it corporate-friendly.**

The voice memo: **"from a corporate point of view, you could add disclaimers: this is confidential data, don't use unless authorised. Or support links: if you don't have the key, contact this person."** The public preview page, shown when someone has the link but not the key, is the natural place for:

- **Confidentiality disclaimers** (this is confidential; do not use unless authorised).
- **Support / contact links** (no key? contact this person).

This turns the no-key state from a dead end into a useful, professional page, which matters in corporate contexts where a recipient might receive a link before the key, or need to request access. It solves a pile of the workflow problems the opacity created.

## Controlled Exposure: Timing, Delays, And Expiry

The control the voice memo wanted on the exposure: **the public preview can be time-limited, so it only works for a few days or a few times.**

The voice memo: **"with the vault, we could introduce timing and delays, and make sure that public thing only works for a couple of days or a couple of times. We control the exposure."** This ties to the ephemeral-by-default model (cross-ref: the SG/Send identity-persistence-budgets brief) and the time-as-a-dimension work (cross-ref: the SG/Sentinel time brief): the public exposure is not necessarily permanent; it can expire by time or by access count, bounding the exposure. This keeps the controlled exposure genuinely controlled: public, but only as long and as much as chosen.

It also anticipates PKI (cross-ref: the SG/Sentinel deployment-modes PKI work): the voice memo noted that once PKI lands, this gets smoother, because **"we could even go and check if the user has access to it anyway."** With PKI, the public-preview-then-key flow could become a public-preview-then-automatic-access flow for entitled users.

## Editing The Public Information

The remaining piece, from the continuation memo: **a UX to edit the public information, on the vault settings page.**

The voice memo: **"the only piece of the puzzle we also need is a UX to edit this, which should be done on the settings page of the vault."** The user needs to set and edit the public title, description, and thumbnail, and choose the public ID (random or custom). The vault settings page (cross-ref: the settings-panel work from the vault UI improvements) is where this belongs.

## Server-Side And Performance Implications

The voice memo flagged two implementation considerations honestly:

- **Server-side storage is now acceptable for this data** (because it is public): the public preview can be saved server-side, which is a change from the all-client-side default, justified by the deliberate public-ness.
- **Performance implications to understand**: the voice memo: **"I'm quite keen to understand the performance implications of doing this on the server side."** Rendering the public preview server-side (for the meta-tag card, which platforms fetch server-side) has performance characteristics worth measuring before scaling.

## What This Asks For

1. **Add the public-preview capability** (an optional, deliberately-public title, description, and thumbnail per vault).
2. **Implement the deterministic public-vault-ID derivation** (string to transfer ID plus read-only decryption key).
3. **Store the public preview as a convention JSON** (title, description, thumbnail; cross-ref: the conventions brief).
4. **Support user-defined and random public IDs** (not Simple Tokens; a distinct concept).
5. **Build the two access modes** (`/app/<public-id>` shows preview and asks for key; `#<vault-key>` auto-loads).
6. **Expose meta tags for social-share previews** (the Open Graph card on WhatsApp, LinkedIn, etc.).
7. **Support corporate disclaimers and support links** on the public page.
8. **Add timing/expiry controls** (the public exposure works for a few days or a few accesses).
9. **Add the edit UX on the vault settings page.**
10. **Measure the server-side performance implications.**

Estimated effort: the deterministic derivation and the convention JSON are light; the two-mode UX and the meta-tag rendering are focused UI/server work; the timing/expiry reuses the ephemeral model; the settings-page edit UX builds on the existing settings panel. The server-side rendering for meta tags is the main new server consideration, hence the performance check.

## What This Does Not Try To Be

- **Not a breach of the vault's contents.** Only the chosen public preview is exposed; the vault's real contents stay encrypted and need the proper key.
- **Not mandatory.** It is opt-in per vault; the user chooses what (if anything) to expose.
- **Not a Simple Token.** It is a distinct deterministic public-preview key, separate from the Simple Token mechanism.
- **Not permanent exposure.** It can be time-limited or access-limited.

## Honest Risks

**Risk 1: It deliberately creates an exposure.** The public preview, the deterministic key, and the key-in-URL are real exposures. Mitigation: it is controlled and opt-in (the user chooses); only the chosen public information is exposed; the vault contents stay encrypted; timing/expiry bounds it; the voice memo's framing (exposure not vulnerability, controlled, user-chosen) is the governing principle.

**Risk 2: Users might expose more than they intend.** Someone could put sensitive information in the public preview by mistake. Mitigation: clear UX about what is public; the edit UX makes the public surface explicit; default to nothing public; treat-users-as-capable with awareness (cross-ref: the open-evaluation brief).

**Risk 3: The deterministic derivation must be sound.** A weak derivation could expose more than the public layer. Mitigation: the derived key is read-only and for the public preview only; it must not grant access to the vault's real contents; security review of the derivation.

**Risk 4: Server-side rendering has performance and exposure implications.** Storing and rendering server-side changes the all-client-side default. Mitigation: justified by the deliberate public-ness; measure performance; only the public preview is server-side, not vault contents.
