**from** Human (project lead)

## The Shift in Audience

When we talk to the medical partner about the next steps, we are not really talking to him. We are talking to his Lovable agent. He has done the jump to LLM-driven development; he is a vibe coder. He will paste our instructions into Lovable and let it execute.

This is increasingly true of every customer we interact with. The investor pasting our pitch deck into Claude. The lawyer asking ChatGPT to extract terms from our contract. The other entrepreneur asking Cursor to scaffold their integration.

The audience is shifting from human to agent. Our communication has to adapt. We cannot send the doctor a 20-page technical setup guide. We can send him a prompt that his Lovable will execute.

## What This Means Operationally

The instructions we send must be:

- **Self-installing.** "Install SG/AI in your environment" should trigger the agent to do whatever is needed, with our package manager or skill files providing the next steps.
- **Agent-shaped.** Phrased as instructions to an LLM, not prose to a human. Bullet points, explicit steps, exit conditions.
- **Vault-aware.** A vault is the right container for the instructions because the agent can read it, the agent can write back to it, and we can update it without re-sending anything.
- **Auditable.** Every step the agent takes leaves a trace in the vault, so the human can review what their agent did on their behalf.

The form is closer to a SKILL.md (from the package manager brief) than to traditional documentation.

## The Communication Vault

Each engagement gets a communication vault. The vault carries:

- The initial prompt (kicks off whatever the partner's agent needs to do)
- The standards and templates (assessment framework, deployment manifests, etc.)
- A messages folder for bidirectional comms (using the Email-FS-light pattern from the multi-agent collaboration brief)
- The partner's agent's outputs (what they built, what questions they have, what is broken)
- Our agent's responses (clarifications, corrections, next steps)

```
comms-vault-{partner-id}/
    |
    +--> initial-prompt.md          (paste this into Lovable to start)
    +--> SKILL.md                   (instructions for the partner's agent)
    +--> USAGE.md                   (common patterns and pitfalls)
    +--> templates/                 (whatever the agent should clone or copy)
    +--> messages/
    |       +--> from-platform/     (our agent → partner's agent)
    |       +--> from-partner/      (partner's agent → us)
    |       +--> threads.json       (conversation index)
    +--> outputs/
    |       +--> deployed/          (what their agent shipped)
    |       +--> questions/         (what they need answered)
    |       +--> errors/            (what broke)
    +--> _page.json                 (vault navigation)
```

The partner's agent reads from this vault and writes back to this vault. We do the same. The whole conversation, in both directions, is auditable.

## Per-Agent Communication Protocols

Different AI dev tools have different surfaces. We need a small protocol document for each, capturing the specifics:

| Agent | What We Need to Document |
|-------|--------------------------|
| **Lovable** | Initial prompt, how to add SG/Vault dependency, how to commit to GitHub, how to deploy |
| **Claude (web)** | Network port requirements (sgraph.ai endpoints to allowlist), prompt format, file upload limits |
| **Claude Code (terminal)** | Installation steps, CLAUDE.md template, recommended tools to allow |
| **Cursor** | Project setup, .cursor/rules content, recommended extensions |
| **ChatGPT** | Custom GPT configuration, action/tool setup, prompt format |
| **Windsurf / Aider / others** | TBD as we encounter them |

Each is a short page on sgraph.ai with the exact prompt to start, the gotchas, and a worked example. As we discover what works, we update.

## Start With Lovable (Immediate Priority)

The medical partner uses Lovable. Lovable is the first agent we need to support fully. The pack should contain:

### Initial Prompt for Lovable

A short, copy-paste prompt that bootstraps the engagement:

> Install SG/AI in this project. Clone the communication vault at [vault-id] using the read key [read-key]. Read SKILL.md in that vault to understand your role. Follow the instructions in initial-prompt.md to begin. Write all questions and progress updates to messages/from-partner/ in the vault.

That single prompt is the entire onboarding. The partner pastes it into Lovable. Lovable does the rest, guided by what is in the vault.

### What Lovable Needs to Know (SKILL.md inside the vault)

- This project is a vault-backed application
- Your role is to build/modify the partner-facing UI
- The vault structure is X, the deployment target is Y
- When you need clarification, write a question to messages/from-partner/
- When you ship a change, commit to GitHub on the dev branch (deploys to dev environment)

### What We Need to Know (Reading from the Vault)

We watch `messages/from-partner/` for questions, errors, and progress updates. Our agent (Claude on our side) reads them, formulates responses, and writes to `messages/from-platform/`. Asynchronous, auditable, scalable.

## Bidirectional Communication via Email-FS-Light

The existing Email-FS pattern (multi-agent collaboration brief, 30 Apr) is the right mechanism. Lightweight version:

- Messages are files in `messages/from-X/` directories
- Filenames carry timestamps and IDs
- Subject and body in markdown
- Attachments alongside in the same folder
- A threads.json indexes conversations

This is enough. We do not need a real messaging service. The vault is the messaging service.

## WhatsApp + Token as the Out-of-Band Channel

For the medical partner specifically, we have direct WhatsApp access. The right onboarding moment is:

1. We message the partner via WhatsApp: "Paste this into Lovable: [prompt with vault-id and read-key]"
2. The partner pastes it
3. Lovable connects to the comms vault and reads SKILL.md
4. Lovable starts working
5. We continue helping via the comms vault (and WhatsApp for human-to-human checkpoints)

WhatsApp is the human-to-human channel for "is this working?" and "should I look at this?" The vault is the agent-to-agent channel for the actual work.

## Why This Generalises

This is not just for the medical partner. Every customer interaction increasingly has the same shape:

1. The customer is using an AI dev tool
2. We need to give the customer's AI dev tool instructions
3. The customer cannot or should not translate our instructions manually
4. The output of our communication is whatever the customer's agent built

The communication vault pattern works for every such interaction. We build it once for Lovable, then once more for Claude Code, then once more for Cursor. After three agents, we have a template for the fourth.

This becomes a documented capability on sgraph.ai: "How to onboard your AI dev tool to SG/Send."
