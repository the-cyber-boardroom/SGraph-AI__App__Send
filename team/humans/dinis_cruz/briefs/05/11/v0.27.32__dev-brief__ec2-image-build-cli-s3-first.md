## The Problem

Creating an AMI from the Local Claude EC2 instance took approximately 30 minutes. Loading that AMI was even slower, to the point where building from scratch would have been faster. The root cause: AMI creation uses legacy EBS snapshot technology that writes to S3 and reconstructs on load. For large images (GPU instances with models, dependencies, and tooling), this is unusable.

The current build process is also opaque: everything installs in one go, there is no visibility into which step takes how long, and there is no way to test or replay individual phases.

## The Solution: S3-First, Step-Based, CLI-Driven Build Process

### The Core Principle

**Loading from S3 is fast. Loading from EBS snapshots is slow.** Therefore: start with the lightest possible base image and load everything else from S3 at boot time (or mount time). The AMI contains almost nothing. S3 contains everything.

This inverts the traditional AMI model. Instead of "bake everything into the AMI, launch fast," it is "bake nothing into the AMI, load fast from S3." The bet is that S3 download speed (which is high within the same region) beats EBS snapshot reconstruction time (which is terrible for large volumes).

### The Architecture

```
Minimal Base AMI (as small as possible)
    |
    v  (boot in seconds)
    |
S3 Bucket: sg-compute-images/
    |
    +--> ollama/
    |       +--> runtime.tar.gz       (Ollama binary + dependencies)
    |       +--> models/
    |               +--> gemma-4.tar.gz
    |               +--> qwen-3.tar.gz
    |
    +--> vllm/
    |       +--> runtime.tar.gz       (vLLM + CUDA dependencies)
    |       +--> models/
    |               +--> llama-3.tar.gz
    |
    +--> tools/
    |       +--> sgit.tar.gz          (SGit CLI + dependencies)
    |       +--> node.tar.gz          (Node.js runtime)
    |       +--> python-deps.tar.gz   (Python packages)
    |
    +--> system/
            +--> stripped-base.tar.gz (minimal system files)
    |
    v
Instance boots, downloads what it needs from S3, extracts to disk
    |
    v
Ready to serve (target: under 2 minutes total)
```

### Why the Model Does Not Care

The LLM model (Ollama, vLLM, etc.) does not care where its files come from. It cares that the model weights are on disk at a specific path when it starts. Whether those weights were baked into an AMI, downloaded from Hugging Face, or copied from S3 is invisible to the model.

This means we can:
- Store model weights as S3 objects (compressed)
- Download them to the instance at boot
- Symlink or mount them at the expected path
- Start the model as if nothing changed

The same applies to every other component: the SGit CLI, the Python environment, the Node.js runtime, the FastAPI control plane. None of them care about their origin. They care about files on disk.

## The CLI Tool: sg-image

A Python CLI that manages the entire build, test, optimise, and deploy lifecycle:

### Phase 1: Capture

Monitor an installation and record everything that changed on disk:

```bash
# Start monitoring
sg-image capture start

# Run an installation (e.g. install Ollama + download a model)
curl -fsSL https://ollama.com/install.sh | sh
ollama pull gemma:7b

# Stop monitoring, see what changed
sg-image capture stop

# Output: list of all files created/modified during the installation
#   /usr/local/bin/ollama (12MB)
#   /root/.ollama/models/gemma-7b/ (4.2GB)
#   /usr/lib/x86_64-linux-gnu/libcuda.so (...)
#   ... (full manifest)
```

### Phase 2: Package

Bundle the captured files into S3-loadable packages:

```bash
# Package the captured installation into a tar.gz and upload to S3
sg-image package --name ollama-gemma --upload s3://sg-compute-images/ollama/

# Output:
#   Created: ollama-gemma-runtime.tar.gz (12MB)
#   Created: ollama-gemma-model.tar.gz (4.2GB)
#   Uploaded to: s3://sg-compute-images/ollama/
```

Separate the runtime (small, changes with versions) from the model weights (large, changes rarely). This allows updating the runtime without re-uploading 4GB of model weights.

### Phase 3: Load

On a fresh instance, download and extract from S3:

```bash
# Load a packaged installation from S3
sg-image load --from s3://sg-compute-images/ollama/

# Output:
#   Downloading ollama-gemma-runtime.tar.gz (12MB) ... 0.8s
#   Downloading ollama-gemma-model.tar.gz (4.2GB) ... 18s
#   Extracting to /usr/local/bin/ and /root/.ollama/ ... 5s
#   Ready in 24 seconds
```

### Phase 4: Test

Verify the loaded installation works:

```bash
# Run tests against the loaded environment
sg-image test --suite ollama

# Output:
#   [PASS] ollama binary exists at /usr/local/bin/ollama
#   [PASS] model gemma:7b loadable
#   [PASS] inference endpoint responds (235ms first token)
#   [PASS] tool use working (SGit clone test)
#   All 4 tests passed
```

### Phase 5: Strip

Remove unnecessary files from the instance to reduce disk usage and attack surface:

```bash
# Analyse what can be removed
sg-image strip --analyse

# Output:
#   /usr/share/doc/ (45MB) - safe to remove
#   /usr/share/man/ (12MB) - safe to remove
#   /var/cache/apt/ (230MB) - safe to remove
#   /usr/lib/x86_64-linux-gnu/libicu* (28MB) - NOT NEEDED by current workload
#   Total removable: 315MB

# Execute the strip
sg-image strip --execute

# Verify nothing broke
sg-image test --suite ollama
```

This is both a performance optimisation (less disk to snapshot/load) and a security hardening step (less "living off the land" surface for attackers).

### Phase 6: Measure

Benchmark every step with timing data:

```bash
sg-image benchmark --from-scratch
# Output:
#   Fresh instance boot: 12s
#   S3 download (runtime): 0.8s
#   S3 download (model): 18s
#   Extract: 5s
#   Service start: 3s
#   First inference: 2.1s
#   Total: 41s

sg-image benchmark --from-ami
# Output:
#   AMI boot: 28s
#   EBS volume ready: 180s (!!!)
#   Service start: 3s
#   First inference: 2.1s
#   Total: 213s

# S3-first: 41 seconds. AMI: 213 seconds. Winner: S3-first by 5x.
```

## The Step-Based Installation Model

Every installation is decomposed into discrete, replayable steps:

```json
{
  "name": "local-claude",
  "steps": [
    {
      "name": "base-system",
      "description": "Minimal system packages",
      "s3_package": "s3://sg-compute-images/system/base.tar.gz",
      "test": "sg-image test --suite base-system",
      "size_mb": 45
    },
    {
      "name": "python-runtime",
      "description": "Python 3.12 + core packages",
      "s3_package": "s3://sg-compute-images/tools/python-runtime.tar.gz",
      "test": "sg-image test --suite python",
      "size_mb": 120
    },
    {
      "name": "ollama-runtime",
      "description": "Ollama binary and dependencies",
      "s3_package": "s3://sg-compute-images/ollama/runtime.tar.gz",
      "test": "sg-image test --suite ollama-runtime",
      "size_mb": 12
    },
    {
      "name": "model-gemma",
      "description": "Gemma 7B model weights",
      "s3_package": "s3://sg-compute-images/ollama/models/gemma-7b.tar.gz",
      "test": "sg-image test --suite ollama-inference",
      "size_mb": 4200
    },
    {
      "name": "sgit-tools",
      "description": "SGit CLI + vault tools",
      "s3_package": "s3://sg-compute-images/tools/sgit.tar.gz",
      "test": "sg-image test --suite sgit",
      "size_mb": 35
    },
    {
      "name": "control-plane",
      "description": "FastAPI control plane",
      "s3_package": "s3://sg-compute-images/tools/control-plane.tar.gz",
      "test": "sg-image test --suite control-plane",
      "size_mb": 8
    }
  ]
}
```

Each step is independently testable, independently cacheable (in S3), and independently replaceable. Update the model without touching the runtime. Update the tools without re-downloading the model. Swap Ollama for vLLM by changing one step.

## GPU-Specific Considerations

GPU instances add complexity:

- **CUDA libraries** are large (several GB) and must match the GPU driver version
- **GPU instance storage** (NVMe SSD on g5, p4, etc.) is fast but ephemeral, perfect for model weights
- **GPU driver** must be pre-installed or installed at boot (driver mismatch = no GPU)

The approach: base AMI has only the GPU driver (small, must match hardware). Everything else loads from S3 to the GPU instance's NVMe storage (fast local SSD). Model weights on NVMe are served faster than from EBS.

Start with CPU instances (simpler, cheaper, faster iteration). Move to GPU once the S3-first pattern is proven. The pattern is identical; only the CUDA step and the target storage path change.

## Two Target Workloads

| Target | Runtime | Model Size | Instance Type | Goal |
|--------|---------|-----------|--------------|------|
| Ollama (CPU) | Ollama | 4-8 GB | c7i.xlarge | Proof of pattern, fast iteration, cheap |
| vLLM (GPU) | vLLM | 4-15 GB | g5.xlarge | Production path, GPU inference, tool use |

Both follow the same S3-first build process. The steps differ (CUDA for GPU, no CUDA for CPU). The CLI handles both.

## Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|-------------|
| 1 | `sg-image capture` records all files changed during an installation | Install a package, capture shows complete file list with sizes |
| 2 | `sg-image package` creates tar.gz and uploads to S3 | Package created, uploaded, downloadable from S3 |
| 3 | `sg-image load` downloads from S3 and extracts to correct paths | Fresh instance, load from S3, files in correct locations |
| 4 | `sg-image test` validates the loaded installation works | Test suite passes after S3 load |
| 5 | `sg-image strip` identifies and removes unnecessary files | Strip removes 200MB+, test suite still passes |
| 6 | `sg-image benchmark` shows S3-first is faster than AMI-first | Side-by-side timing comparison documented |
| 7 | Step-based installation definition (JSON) is loadable | Define 5 steps, load all from S3, full environment working |
| 8 | Individual steps independently replaceable | Update one step (e.g. model weights), others unchanged, system works |
| 9 | Ollama (CPU) working via S3-first in under 60 seconds total load time | Benchmark confirms: boot + download + extract + ready under 60s |
| 10 | Full test suite runs after strip (nothing needed was removed) | Strip + test, all pass |
| 11 | CLI works for both CPU and GPU target workloads | Same CLI, different step definitions, both produce working environments |
