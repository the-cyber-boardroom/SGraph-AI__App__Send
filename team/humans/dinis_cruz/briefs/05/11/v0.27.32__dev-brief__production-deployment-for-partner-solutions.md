## The Gap We Need to Close

Today's vibe-coding entrepreneur (in the immediate case, the medical partner; more generally, anyone with a domain methodology and a Lovable account) can build a polished MVP in hours. What they cannot do is ship that MVP to production responsibly: real environments, real CI, real custom domain, real isolation between iterations.

This is the gap we close. We have been pushing our own stuff to production from day one. The patterns work. They need to be packaged so a non-DevOps entrepreneur can adopt them.

## The Target Architecture (Smallest Viable)

Everything the partner builds runs on three components and nothing else:

| Component | Role |
|-----------|------|
| **Serverless function (or one EC2 instance)** | The vault API |
| **Static storage (S3 or equivalent)** | Static website assets (HTML, JS, CSS) |
| **Object storage (S3 or equivalent)** | Encrypted vault data |

That is the whole architecture. No database. No auth server. No queue. No cache layer. No backend application code. Everything else is the vault, the SG/App runtime, and the partner's vibe-coded UI.

For the cleanest possible deployment (one button, no DevOps), the same setup runs on a single EC2 instance. The same code, the same workflow, just collapsed onto one machine.

## Three Environments, Same Workflow

| Environment | Purpose | Subdomain example | Trigger |
|-------------|---------|-------------------|---------|
| **dev** | Where the partner's Lovable agent commits | `dev.assessment.example.com` | Push to `dev` branch |
| **main** | Integration target, smoke tests, validation | `main.assessment.example.com` | Push to `main` branch |
| **prod** | Live users | `assessment.example.com` | Push to `prod` branch (or tag from main) |

Each environment is fully isolated. Same code, different storage, different vaults, different domain. A break in dev never touches prod. This is the same pattern we use for sgraph.ai today.

Optional QA branch sits between dev and main for additional smoke testing, screenshot diffs, and agent-driven validation.

## The Critical Property: No Dependencies on Our Infrastructure

When a partner deploys to prod, **none of their infrastructure depends on ours**.

- Their vault API runs in their account
- Their static assets sit in their S3 bucket
- Their vault data sits in their S3 bucket
- Their domain points at their CloudFront (or equivalent)
- Their CI runs on their GitHub Actions

We are not in the runtime path. If we go down, their users do not notice. If they leave us, they take everything and run.

This is the zero-lock-in principle from the Private Health Score workflow, expressed as infrastructure.

## GitHub Is the Master Data

The partner's GitHub repository is the canonical source of truth (this builds on the GitHub-as-Vault-Projection brief from earlier today):

- The partner's Lovable agent commits to their GitHub repo
- Push to `dev` branch deploys to dev environment
- Push to `main` deploys to main, push to `prod` deploys to production
- Vaults are projections of the repo content; the repo is the master

This means the partner can switch deployment targets (AWS to GCP, AWS to Cloudflare) without losing anything. The repo is portable; the deployment is replaceable.

## Multi-Cloud Targets (Pick One, Add More)

We start with AWS because we know it deeply and have the tooling. The same pattern maps cleanly to:

| Provider | Compute | Storage | Notes |
|----------|---------|---------|-------|
| **AWS** | Lambda + API Gateway, or one EC2 | S3 + CloudFront | Primary target. Most documented. |
| **GCP** | Cloud Functions, or one Compute Engine | Cloud Storage + CDN | Equivalent stack. |
| **Azure** | Functions, or one VM | Blob Storage + CDN | Equivalent stack. |
| **Cloudflare** | Workers | R2 | Cheaper, simpler, no AWS account needed. |
| **Netlify / Vercel** | Their compute | Their storage | Familiar to vibe-coders; easiest onboarding. |

The partner picks based on what they already use or what their DevOps person recommends. We provide deployment manifests for each. The application code is identical across all.

## The Empowerment Story

The partner (entrepreneur, doctor) pushes to prod every day. They vibe code in the morning, they ship by the afternoon. This is non-negotiable: if they cannot ship without our help, the model is broken.

They should be backed by a fractional team:

- A DevOps or SRE person (or company) who watches the prod environment, sets up alerts, handles incidents
- A security reviewer who checks the AppSec posture quarterly
- A designer who reviews the user-facing experience

But the daily push-to-prod is the entrepreneur's. The fractional team makes the foundation solid; they do not block the iteration.

## The Deployment Manifest

Each partner solution ships with a `deploy/` directory in the GitHub repo containing:

```
deploy/
    |
    +--> aws/
    |       +--> terraform/             (Terraform modules for the AWS setup)
    |       +--> github-actions.yml     (CI workflow)
    |       +--> README.md              (per-cloud setup steps)
    |
    +--> gcp/
    +--> cloudflare/
    +--> netlify/
    |
    +--> shared/
            +--> dns-mapping.md         (how to point your domain)
            +--> secrets.md             (what credentials you need)
            +--> validation.md          (how to confirm the deployment worked)
```

The partner copies the relevant directory, fills in their account credentials, runs `terraform apply` (or the equivalent), and they have their three environments stood up. From scratch to dev/main/prod in under one hour.

## Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|-------------|
| 1 | AWS Terraform module deploys dev/main/prod from a clean account | New AWS account, run terraform, three environments stand up |
| 2 | GitHub Actions workflow templates trigger correct environment | Push to dev branch deploys to dev only; same for main and prod |
| 3 | Single-EC2 alternative deployment works end-to-end | Launch one EC2 instance, full stack operational, no other infrastructure |
| 4 | Zero infrastructure dependency on our systems | Partner's prod still works if we are down |
| 5 | Multi-cloud manifests work for at least one alternative (Cloudflare or GCP) | Same application code, deployed on alternative provider, equivalent functionality |
| 6 | A non-DevOps entrepreneur can complete the deployment in under one hour | Walkthrough: someone unfamiliar with AWS goes from zero to three environments in under 60 minutes |
| 7 | Push-to-prod takes under five minutes from commit to live | Measure: commit to prod branch, observe time to live URL update |
| 8 | Private Health Score POC reference deployment exists publicly | Live URL accessible, all three environments visible |
