## The Success Story That Sets This Up

The medical POC has reached a meaningful milestone:

1. We built the medical POC on top of a vault with a new UI
2. Showed it to a potential healthcare partner
3. Partner sent back a mockup of his own specifically-focused workflow
4. We pointed our vault-Claude agent at the example vault + the mockup and said "create a new vault with this"
5. That worked. A new vault appeared with the partner's specific workflow rendered correctly
6. We sent the MVP to the partner. He saw it, he liked it, he is engaged

This is the agentic content/dev pattern (from day 50) applied to a customer engagement: the agent did the work that would have taken a dev team a week. The MVP exists. The partner is happy. Now we need the next phase.

## The Core Principle: We Do Not See Their Data

Going forward, this engagement must be structured so that we (the SG/Send team) never see:

- Confidential patient data
- Proprietary formulas
- Spreadsheets and analyses the partner has built up over years
- Any of the application-specific knowledge that is the partner's actual business value

This is non-negotiable. It is the same principle that "client-encrypted vaults" expresses in product terms, now applied to the engagement model.

Equally important: the partner must be empowered. They should not depend on us for every UI tweak, every bug fix, every iteration. They have access to AI development tools (in this case Lovable). Those tools should do the work, on their side, with their data.

We provide the platform and the initial template. They run with it.

## The Architecture: GitHub as a Projection of the Vault

The workflow uses GitHub as a developer-facing projection of the vault:

```
                    Customer's AI dev tool (Lovable, Claude Code, etc.)
                                        |
                                        v
                              clone, edit, push
                                        |
                                        v
+-----------------------+      +----------------------+
|  GitHub repo          |      |  Vault (sgit)        |
|  (developer surface)  | <==> |  (consumer surface)  |
|                       |      |                      |
|  Source files         |      |  Encrypted vault     |
|  HTML, JS, content    |      |  objects, commits    |
|  CLAUDE.md, README    |      |  Render-ready        |
|  Standard git tools   |      |  Browser-mountable   |
+-----------------------+      +----------------------+
                                        |
                                        v
                              End users open the vault
                              and see the rendered app
```

Two version control layers run side by side:

| Layer | Purpose | Audience |
|-------|---------|----------|
| **Git** (GitHub) | Developer-friendly source of truth | AI coding tools, developers, contributors |
| **SGit** (vault) | Consumer-facing distribution channel | End users opening the encrypted vault |

The same content lives in both. Changes flow from GitHub to vault. The vault remains the canonical thing users interact with.

## Why This Decomposition Works

### GitHub Speaks Fluent AI Development Tools

Lovable, Claude Code, Cursor, Aider, and every AI dev tool worth using assumes a Git repository. They clone, they edit, they commit, they push. They look for README, CLAUDE.md, package.json. They understand branches and pull requests. None of them know what a vault is.

A GitHub repository is the lingua franca. By projecting the vault into GitHub, we make the partner's setup compatible with every AI dev tool in existence, without writing integrations for any of them.

### The Vault Stays Where the Value Is

The vault remains the consumer-facing distribution channel. End users open the vault with a read key. They see the rendered application. They never touch GitHub.

The encryption, the version history, the selective sharing, the SG/App runtime: all of this is still in the vault. The vault is where the trust boundary lives. GitHub is just a developer's workbench.

### The Customer Owns the Loop

Once the GitHub repo exists, the partner controls the development loop:

- Their AI dev tool clones their repo
- They tell the tool what to change
- The tool makes the changes
- The tool pushes back to their repo
- A sync step pushes from GitHub to their vault
- End users see the update

We are not in this loop. We do not need to see their data. We do not need to fix their bugs. They own the iteration.

## The Repo Structure

The GitHub repo mirrors the vault's internal structure, plus developer-facing additions:

```
medical-poc-repo/
    |
    +--> vault/                       (mirrors the vault structure)
    |       +--> _page.json
    |       +--> content/
    |       +--> images/
    |       +--> apps/                (SG/Apps inside the vault)
    |               +--> form/
    |               +--> dashboard/
    |
    +--> CLAUDE.md                    (instructions for the customer's AI dev tool)
    +--> README.md                    (human-facing project description)
    +--> .sgit-remote.json            (vault sync configuration)
    +--> scripts/
    |       +--> sync-to-vault.sh     (push to vault)
    |       +--> sync-from-vault.sh   (pull from vault, if needed)
    +--> tests/                       (smoke tests the AI tool can run)
```

The `CLAUDE.md` is critical. It tells the customer's AI dev tool everything it needs to know:

- What this repo is (a vault projection)
- How the vault and the repo relate
- How to sync changes (run the sync script after pushing)
- Where to find the rendered preview (open the vault in their browser)
- Conventions for the content (markdown structure, JSON schemas)
- The list of known patterns and the common pitfalls

Following the package manager pattern: SKILL.md and USAGE.md make AI tools effective on the package. CLAUDE.md does the same for the repo itself.

## The Sync Mechanism

Phase 1 (immediate, clunky-but-working): Manual or scripted sync.

- A `sync-to-vault.sh` script runs `sgit add` / `sgit commit` / `sgit push` against the configured vault
- The script is committed to the repo so the AI tool can find and run it
- After a customer's AI tool pushes to GitHub, they (or a GitHub Action) run the sync script
- End users hit refresh on the vault and see the update

Phase 2 (later): GitHub Action that auto-syncs.

- Push to the GitHub repo's main branch
- GitHub Action runs `sgit push` to the configured vault
- Vault auto-updates
- End users see the update with no manual step

Phase 3 (eventual): Bidirectional sync with conflict resolution.

- Vault changes (made by other agents or other tools) flow back into GitHub
- Conflicts resolved using vault commit history
- Single coherent timeline across both

Phase 1 is enough to ship the workflow. Phases 2 and 3 are improvements once the partner is using the system in anger.

## Public vs Private

The repo can be public or private. That is the partner's choice. We do not decide.

- **Public:** Anyone can read. The vault still requires the read key. The repo serves as the developer source; the vault serves as the consumer distribution. Sensitive data lives in the vault only.
- **Private:** Only the partner and their authorised collaborators can read or push. Same vault arrangement. Tightest control.

Either way, the vault encryption is unchanged. The repo holds source files, not patient records or proprietary data. Patient data lives in the encrypted vault objects, not in markdown files.

## Local Development (Future)

The partner can eventually run the whole stack locally:

- Clone the GitHub repo
- Run a local Docker container (or Apple container) that hosts the SG/App runtime
- Mount the local files into the runtime
- Preview changes in a browser before pushing
- Push to GitHub when ready

This removes the cloud round-trip from the iteration loop. Useful but not required for Phase 1. The partner can ship without it; they just push to GitHub and check the vault for the result.

## Why This Pattern Matters Beyond This Engagement

The medical POC is the proving ground. The pattern is generalisable:

| Customer type | What they build | What they own | What we provide |
|---------------|----------------|---------------|-----------------|
| Healthcare partner | Patient workflow, evidence capture | Patient data, clinical methodology | Vault platform, initial template |
| Investor / consulting firm | Engagement vaults per client | Client deliverables, scoring | Vault platform, evaluation standard |
| Security consultancy | Assessment vaults | Findings, client recommendations | Vault platform, assessment framework |
| Education provider | Course content vaults | Curriculum, student work | Vault platform, course template |

In every case: we provide the platform and the initial scaffolding. They customise, iterate, and ship using their own AI dev tools. They never give us their data. We never become a bottleneck.

This is the operationalisation of "execution as moat" (from the moat article): customers move faster because their own AI tools work on their own data inside our platform. The platform compounds in value as more customers operate this way. Our team stays small because the customers iterate themselves.
