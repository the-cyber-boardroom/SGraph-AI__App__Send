## Open Source Stays Open Source

Before anything else: this commercial model does not close off knowledge. It does not pull docs behind paywalls. It does not encourage maintainers to hoard expertise. Open source maintainers (us included) will continue to publish generously: documentation, examples, SKILL.md, USAGE.md, SECURITY.md, hardening guides, even 100 example deployments. That generosity is a core principle of open source and it stays.

The commercial layer is something different. It is not "the knowledge that was hidden." It is the line where a generic package meets a specific application.

## The Commercial Line

A package can ship with 100 generic examples published openly. None of them are your application. Your application has its own data conventions, its own compliance regime, its own performance profile, its own integration points, its own historical decisions, its own users, its own threat model.

The maintainer's generic guidance cannot anticipate all of this. Even with 100 examples published openly, none of them are exactly your situation. The work of mapping the generic package to your specific reality is what the commercial line covers.

To put it sharply: **the commercial line is where the package touches the target app.**

The free part is the package itself, plus everything the maintainer publishes about how to use it in general. The paid part is the part that is specific to one customer's actual deployment. The two never overlap.

This framing matters because it resolves the apparent tension between "open source ethos" and "maintainer sustainability." There is no tension. The maintainer can publish more generously than before, knowing that the commercial layer captures value from the application-specific connection, not from the knowledge itself.

## The Two Main Benefits

When a customer pays for the commercial relationship, what do they get?

### Benefit 1: Customised Guidance Only the Maintainer Can Credibly Provide

Who better than the creator of the package to show how to use it correctly in your specific context? The maintainer has:

- Years of pattern recognition: "this configuration looks fine but I have seen it cause issues in production for exactly your kind of workload"
- The full architectural mental model: which paths are stable, which are deprecated, which are about to change
- Domain expertise from building the thing in the first place
- Visibility into the issue tracker, the contributor discussions, the design tensions
- Knowledge of what was tried and abandoned, and why

A consultancy can study the package. The maintainer **is** the package. The advice is qualitatively different. The consultancy reads what the maintainer wrote; the maintainer wrote it.

### Benefit 2: Forward Compatibility Guarantee

A long-running relationship with the maintainer protects against the most expensive failure mode: a future package version breaking your application.

With this relationship in place, the maintainer can:

- Test the next release against your specific use case before publishing
- Write migration guides tailored to your code paths
- Hold back breaking changes that would affect you
- Coordinate releases with your deployment windows
- Provide compatibility shims when needed
- Warn you about deprecations before they bite

This is the value proposition for any production deployment of any open source package. Companies pay heavily for "support contracts" today that provide a fraction of this value because they go through intermediaries who do not have direct access to the maintainer.

## Additional Revenue Streams the Platform Enables

Once the package manager provides communication workflows between customers and maintainers, the commercial layer expands well beyond sidecars:

| Revenue stream | What it covers |
|----------------|----------------|
| **Maintainer sidecar subscription** | Ongoing customised guidance (the primary tier) |
| **Feature implementation** | Customer pays the maintainer to build a feature they need |
| **Bug fix prioritisation** | Customer pays to escalate a fix into the next release |
| **Custom integrations** | Maintainer (or their community) builds the glue code for the customer's stack |
| **Training and onboarding** | Maintainer-led training for the customer's team |
| **Performance tuning** | Maintainer profiles the customer's deployment and tunes it |
| **Migration support** | Maintainer assists with upgrades and version transitions |
| **Audit and certification** | Maintainer signs off that the customer's usage meets a specific compliance framework |

All of these are often cheaper for the customer than the current alternatives: hiring an external consultancy who does not know the codebase, hiring in-house engineers to develop the expertise from scratch, or forking the package and maintaining a private version internally.

For the customer, paying the maintainer directly is the most efficient way to get the work done. For the maintainer, it is a sustainable income stream that funds continued open source contribution.

## Real-World Precedent

This pattern is not theoretical. It has been done at smaller scale, often informally, in many places:

- **The private repo maintenance pattern.** A company sells the service of maintaining a private fork of an open source solution, with all of one customer's customisations applied and kept in sync with upstream. The customer pays for the ongoing relationship, not the code. This has been done at small scale by individuals and consultancies for years; it has never had a proper platform.
- **Linux distribution vendors.** Red Hat (RHEL), SUSE, Canonical all sell support contracts around open source kernels and userland. The Linux kernel stays free; the relationship is paid.
- **Database vendors.** PostgreSQL service providers, MariaDB Corporation, Percona for MySQL: all sell support around fully open source databases.
- **Foundation memberships.** The Linux Foundation, OpenJS Foundation, Apache Software Foundation: corporate memberships that fund maintainer relationships.

What is new here is not the model. It is the infrastructure that makes the model accessible to **every** maintainer at every scale, not just the ones with venture funding to build a commercial operation alongside the open source one.

A solo maintainer publishing a Python package today has no realistic path to capture value from production users. The relationship is missing because the platform is missing. This brief is about providing the platform.

## Why This Has Not Happened Before (the Platform Gap)

Most open source maintainers cannot capture this commercial layer today because the platform infrastructure does not exist:

| Missing piece | Why it matters |
|---------------|---------------|
| Customer-maintainer communication workflow at scale | Email and Slack do not scale; maintainers cannot serve 50 customers individually |
| Standardised format for customised guidance | Without SKILL.md and the sidecar format, every engagement is bespoke and slow |
| Distribution infrastructure for paid artefacts | How does the maintainer ship the customised sidecar? How is access controlled across versions? |
| Billing, licensing, signature verification | Maintainers want to build software, not invoicing systems |
| Trust signals (verified maintainer identity) | The customer needs to know the sidecar genuinely came from the maintainer |
| Recursive composition (consultancies adding a layer) | Maintainers cannot serve every customer directly; intermediaries help, but need infrastructure too (this is the fractal package manager from the main arch brief) |
| Issue/feature workflows tied to the commercial channel | A paid customer's bug should reach the maintainer differently to an anonymous GitHub issue; that channel needs structure |

We provide all of this. The maintainer focuses on the relationship and the customisation. The platform handles everything else.

## The Pricing Tiers (Reframed)

Three tiers, framed by what they actually deliver:

### Tier 1: Free Sidecar (Generic, Open Source)

The maintainer's free SKILL.md, USAGE.md, SECURITY.md. Published openly. Good enough for most users. This is what the maintainer would write anyway as part of being a responsible open source citizen. No paywall on knowledge. Distributed with the package.

### Tier 2: Maintainer-Supported (Customised + Forward-Compat)

The customer enters into an ongoing relationship with the maintainer. They get:

- A customised sidecar tuned for their specific deployment
- Forward compatibility guarantee on the maintainer's roadmap
- Direct communication channel for questions
- Heads-up on breaking changes before they happen
- Access to feature/bug request workflows (separate from the public issue tracker)

Price: subscription. Typically per-customer, not per-seat, because the value is the relationship.

### Tier 3: Enterprise (Custom + SLAs + Compliance)

Everything in Tier 2 plus:

- Compliance-specific hardening (HIPAA, FedRAMP, etc.) signed off by the maintainer
- SLAs on response time
- Roadmap influence
- White-glove onboarding
- Custom integration work

Price: high, per-engagement. Comparable to or replacing traditional consultancy engagements, with the advantage that the engagement is with the maintainer, not a third party.

## How the Package Manager Enforces This

The sidecar vault has a read key. Free sidecars have public read keys. Paid sidecars have keys distributed via licensing.

When a user runs `sg-package install ollama --sidecar maintainer`, the package manager checks the user's licence, fetches the maintainer-signed sidecar via its specific vault read key, and installs it alongside the package. The package itself remains open source and free. The sidecar is the paid component.

If the licence expires, the package keeps working but the maintainer sidecar is no longer accessible. The customer falls back to the free community sidecar. No breaking change to the package itself. The relationship benefit is what lapses, not the software.

## Example: SGit as a Sellable Package

We are both an upstream maintainer (SGit) and the operator of the package manager. SGit is open source. The SGit code stays free. The free SGit sidecar (containing generic SKILL.md, USAGE.md, security advisories) is also free.

The maintainer-supported SGit sidecar (which we sell) contains:

- A customised sidecar built for the customer's specific deployment patterns
- Forward compatibility guarantee: we test new SGit versions against the customer's use case before release
- Direct communication for questions, edge cases, deployment issues
- First-class access to the issue tracker for feature requests and bug fixes
- Performance tuning for the customer's specific S3 setup, latency profile, and workload mix

This is real value. Customers using SGit at scale pay for this relationship because the alternative is either doing all this work themselves (expensive and slow) or hiring a consultancy who has read the SGit docs but did not write them (also expensive and worse).

We have already done the work; we package the relationship and sell access to it. The same model applies to any upstream maintainer who wants to monetise their position.

## Why Maintainers Will Participate

Open source maintainers face a structural problem: their work is given away free, while companies build billion-dollar businesses on top of it. Sponsorship platforms (GitHub Sponsors, Open Collective, Patreon) help, but they are donations. They do not align with the value created.

The fear that blocks many maintainers from commercial offerings: "if I charge for something, I will be seen as betraying the open source ethos." This fear is reasonable but misplaced when the commercial layer is structured correctly.

The package, the docs, the examples, the SKILL.md, the SECURITY.md all stay open. The maintainer continues to publish generously. The commercial layer is something different: the customer-specific relationship, the forward-compat guarantee, the customised guidance.

A maintainer can publish **more** generously than before, knowing that the commercial layer captures value from the application-specific connection, not from the knowledge itself. The two reinforce each other: more generous open publishing makes the maintainer more visible, which surfaces more potential commercial relationships.

## Marketplace Dynamics

### The Network Effect

Every maintainer who participates increases the value of the platform. More maintainers means more customers will find their relationships there, which surfaces more potential commercial engagements for other maintainers. Standardised formats (SKILL.md, USAGE.md, sidecar schemas) make participation easier over time.

### Trust as a Filter

Maintainer sidecars are signed. Buyers trust that the sidecar genuinely came from the maintainer. This is enforced cryptographically: the package manager verifies signatures against known maintainer keys.

### Discovery

The package manager surfaces available sidecars at install time:

```
$ sg-package install ollama

Available sidecars:
  [free]      Community sidecar (last updated 3 days ago)
  [$29/mo]    Maintainer-supported by ollama-team (verified signature)
  [$199/mo]   Enterprise by ollama-team (HIPAA hardening, SLAs)

Choose [free]: maintainer
```

The marketplace lives inside the install command. Discovery is automatic, friction-free, and tied directly to the work being done.

### Recursive Composition Across Levels

This commercial pattern is fractal in the same way the package manager is. A consultancy can publish their hardening overlay at Level 2 (referencing Level 1 maintainer packages), and customers consume it from their Level 3. The consultancy's revenue stream is independent from the maintainer's; both can coexist on the same package without conflict. Cross-references between layers are explicit and auditable.

## What We Need to Build

The architectural foundations are in the main arch brief. The commercial layer needs:

1. **Sidecar signing infrastructure** so maintainer-produced sidecars are cryptographically verifiable
2. **Licence management** so paid sidecars can be gated by subscription or perpetual licence
3. **Marketplace discovery** so customers see available sidecars at install time
4. **Revenue routing** so payments flow from customers to maintainers (with our cut)
5. **Maintainer onboarding** so a maintainer can publish a sidecar in under an hour
6. **Schema validation** so sidecars meet the standardised format
7. **Customer-maintainer communication workflows** (this is critical and currently missing): structured channels for questions, feature requests, bug reports, breaking-change announcements, scoped to paying customers
8. **Issue/feature ticket system** integrated with the sidecar so customer requests reach the maintainer with full context (which package version, which sidecar tier, which customer)
9. **Roadmap and breaking-change feeds** that maintainers publish privately to Tier 2 and Tier 3 customers before public release
