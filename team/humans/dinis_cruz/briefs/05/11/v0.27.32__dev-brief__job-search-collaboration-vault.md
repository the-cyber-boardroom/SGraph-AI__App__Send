## What This Brief Is

A follow-up to yesterday's `v0.27.32__dev-brief__job-search-website-use-case.md`. That brief defined the eventual product (the friend's job-search site itself). This brief defines the **collaboration vault** that gets us there: the container I will use to give my friend advice, show him multiple prototype directions, and iterate live with Claude Code without ever leaving the vault.

The collaboration vault is also a deliberate demonstration of a workflow that is about to become much more powerful: with the new SG/App routing (HTML pages loaded directly without the full vault chrome), running a vault-rendered prototype side-by-side with a Claude Code session that edits the vault becomes a real, fast loop.

## The New Capability That Makes This Work

We are about to ship a change to SG/App: the HTML page loads directly, on its own page, instead of inside an iframe wrapped by the vault UI. The vault is still under the hood (encryption, version control, file access, column rendering, everything), but the visible surface is just the app.

What that means for this workflow:

- I open the vault as a clean app page in one window
- I open a Claude Code session in another window
- Claude Code makes changes, pushes to the vault
- I refresh my window and see the new version

This is the live iteration loop, with the vault as the shared workspace. No deployment step. No build process. No waiting. Vibe-coded prototypes become immediately viewable.

## What the Collaboration Vault Contains

The vault is structured around four kinds of content:


The structure separates four concerns:

| Section | Purpose |
|---------|---------|
| `current/` | The starting point: his existing website, captured |
| `advice/` | My commentary, in whatever format suits the point |
| `prototypes/` | Multiple agent-built directions for him to compare |
| `infographics/` | Visual summaries that complement the prose |

## Why Multiple Prototypes, Not Just Advice

The traditional flow when giving someone CV/website advice:

1. I look at their site
2. I write up what I would change
3. I send them notes
4. They try to implement the notes
5. They send back the result
6. I comment on what landed and what did not
7. Repeat until either of us gives up

This is slow and inefficient because the bottleneck is them translating my advice into code. They are not as fast at that as Claude Code is.

The new flow:

1. I look at their site
2. I write up what I would change
3. **I have Claude Code build three to five different prototype directions reflecting the advice**
4. I send them all of it: the advice plus the working prototypes
5. They pick the direction(s) they like and iterate from there (with their own Claude Code or Lovable)

Implementation cost on my side dropped from "almost zero" to "still almost zero" because Claude Code does the work. But the value to my friend exploded: instead of trying to imagine what my advice would look like, they see five concrete versions. They pick. They iterate from a real starting point.

## The Live Iteration Loop

The key behavioural pattern this vault enables:

**Window 1:** The vault, rendered as a clean app page. I am looking at one of the prototype directions.

**Window 2:** Claude Code, with the vault cloned (or via the vault-projection GitHub repo). I am giving Claude Code instructions: "make the headline larger, change the colour scheme to warmer tones, add a 'now' page link to the nav."

Claude Code makes the changes, commits, pushes. I refresh Window 1. I see the result. I give the next instruction. The loop is seconds, not minutes.

This is what the new SG/App routing makes possible. The prototype is rendered as if it were a deployed website, because it effectively is one. The vault is the deployment. The CDN is irrelevant. The build pipeline is irrelevant.

When my friend opens this vault later, the same loop is available to him: he opens the prototype in one window, opens Claude Code with the vault in another, and iterates.

## Why the Vault Is Better Than Sending Files

I could send my friend a zip file with five HTML prototypes, a markdown file of advice, and an MP3 of commentary. That works. It would have worked five years ago.

The vault adds things the zip cannot:

- **Version control.** Every change I make is committed. He can see how my thinking evolved.
- **Live iteration.** He can run Claude Code against the vault directly, with no setup, no project structure to learn.
- **Selective sharing.** I can share just the prototypes with him for review, or include the advice, or include the raw voice memos. His own decision.
- **The vault becomes the starting point for his own site.** When he picks the direction he likes, he forks that prototype into his own vault and runs from there.
- **The collaboration is auditable.** Every comment, every iteration, every prototype is captured with timestamps and authorship.

The vault is the collaboration; the prototypes are just artefacts in the collaboration.

## How the Advice Section Should Be Structured

The `advice/` section is mine. I write it. Claude Code does not generate it. This is the human judgement layer.

Useful breakdown:

| File | What It Contains |
|------|------------------|
| `my-analysis.md` | An article: what I think about his current site, what works, what does not, what I would change and why |
| `voice-memo.mp3` | A recording where I talk through my reactions in real time |
| `video-walkthrough.mp4` | Optional: me clicking through his site and commenting |
| `what-i-like.md` | The positives, by name |
| `what-to-improve.md` | The specific changes, prioritised |
| `recommended-approach.md` | Which of the prototypes I would recommend, and why |

The mix of formats matters. Some advice is best as prose. Some is best as voice (tone, emphasis, the bits that are hard to write). Some is best as video (when I am pointing at specific elements). The vault holds all of it; he picks the formats that work for how he processes information.

## The Prototypes (What Claude Code Builds)

Five distinct directions, each meant to test a different hypothesis about what works for him:

### v1: Minimal

Clean, white space, one clear call to action. The "don't make them think" principle taken to the extreme. Six audience pages but no clutter. Tests: does extreme simplicity work for his audience?

### v2: Narrative

Long-form. His career as a story, told well. Less structure, more voice. Tests: do his readers want to know him as a person, or as a list of capabilities?

### v3: Now-Page First

The `/now` page is the landing. What he is doing right now, this week, is the headline. Past experience is below the fold. Tests: does live, current activity beat curated history?

### v4: Infographic

A visual-first homepage. A one-page graphic that summarises everything. Text supplements the visual. Tests: do people retain visuals better than prose for first impressions?

### v5: Interactive

Embedded demos, interactive timelines, hover-to-reveal sections. The site does things, not just shows things. Tests: does technical demonstration beat technical claim?

He picks the one (or two, or a hybrid) that resonates. Or he picks none and we go back to the drawing board with the data we now have about what does not work.

Each prototype includes a `notes.md` explaining what it is trying to do. That helps him evaluate; it also helps him explain his choice to me, which makes the next iteration faster.

## Infographics

The `/infographics/` section is parallel to the prototypes: it provides visual summaries that any of the prototypes can embed (or that can stand alone).

- **Career graph**: visual of his trajectory, with key inflection points
- **Value proposition**: one image that captures what he brings (the "what you would get" message from yesterday's article)
- **Audiences model**: the six-audience structure, visualised, so he can see why the prototypes are structured the way they are

These are created via the infographic skill (similar to how we created infographics for the OWASP pack). Claude Code calls the infographic-gen capability.

## Bring Your Own API Key

A future feature worth flagging: this vault can include the "Bring Your Own Key" pattern for when he wants to run his own Claude Code or Lovable iterations.

He provides his Anthropic or OpenRouter key. The vault uses it. He pays for his own usage. Or he uses one of my keys (with limits) while we are still in the early collaboration phase. Or he uses tokens we sell as a service (the future commercial layer).

The collaboration vault becomes the first concrete instance of the "vaults as paid services" model: someone uses the vault, the vault uses an LLM, the LLM costs money, someone pays for it. The infrastructure to do this is mostly in place; this is a good place to validate the flow.
