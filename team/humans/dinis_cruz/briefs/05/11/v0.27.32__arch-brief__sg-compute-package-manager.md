## The Realisation

What started as an "image builder CLI" is actually a package manager. Not a reimplementation of pip or apt. An opinionated package manager built on the assumption that: dependencies should be locked, stripped, documented, security-reviewed, graph-connected, offline-capable, and LLM-friendly. The packages are installable on bare metal EC2 or inside containers (Docker, Podman, any runtime). The metadata travels as a vault sidecar. The tests are the contract. The entire system runs without internet access; the package manager itself is a single zip file.

The question driving the architecture: if you were building a package manager today, with all the opinions you have about security, observability, and agent-friendliness, what would you do differently?

## Core Principles

### 1. Graph-Driven by Design

Everything is about connecting dots. Packages have semantic relationships, not just dependency relationships. A package knows what it depends on, what depends on it, what it provides, what threats it carries, what security reviews exist, what performance profile it has, which clients use which configurations, and which other packages have similar capabilities.

These connections are not buried in metadata. They are first-class graph edges, queryable and visualisable. An agent or a human can ask: "show me every package that uses cryptography," "which packages have unresolved CVEs," "what does this package replace," "which clients run a stripped variant of this," "what changed between v0.27.31 and v0.27.32."

This is the philosophical foundation that distinguishes SG/Compute Package Manager from existing package managers. pip and npm have dependency trees. This has a dependency graph, a security graph, a capability graph, a deployment graph, and a usage graph: all interconnected, all live, all browsable.

Connects directly to the ontologist work from day 52: the ontologist builds knowledge graphs for content; the package manager builds knowledge graphs for code, configuration, and operational data. Same pattern, different domain.

### 2. Tests Are the Contract

The tests define what the package must do. If the tests pass, the package works. If the tests pass after stripping 90% of the files, the package still works and is now 90% smaller.

This inverts the normal relationship: instead of "install everything, hope it works," it is "define what must work, remove everything that is not needed, verify the tests still pass." The more brutal the stripping, the better the tests need to be. The tests and the stripping co-evolve.

```
Install full package (4.2GB)
    |
    v
Run tests: all pass
    |
    v
Strip: remove /usr/share/doc, /usr/share/man, unused libs
    |
    v
Run tests: all pass (3.9GB saved, now 300MB)
    |
    v
Strip more: remove unused Python packages, unused binaries
    |
    v
Run tests: 1 failure (went too far, restore that file)
    |
    v
Final: 350MB, all tests pass, minimal attack surface
```

### 3. Reuse, Don't Reimplement

We do not replace pip, apt, npm, Hugging Face, or any existing package source. We use them. The original maintainers build the package. We consume the build artefact, the binaries, the installers. We do not rebuild what they built.

What we add on top is what they do not provide: locked versions, stripped builds, security reviews, threat models, usage guides, performance benchmarks, SKILL.md for agents, hardening configurations, and a vault sidecar that travels with the package.

This is a hard rule: if you find yourself reimplementing what an upstream package already does, stop. The right move is to wrap, lock, strip, and document. Not to rewrite. The upstream maintainers have already done that work.

### 4. Offline-First (Air-Gap Capable)

The entire package manager supports 100% offline deployments. No internet access required at runtime. No call-home, no licence server, no telemetry, no upstream registry access during operation.

This is a critical design constraint, not an optional feature. Many real-world deployments (defence, healthcare, finance, regulated industries, isolated networks) cannot rely on internet access. The package manager must work the same way in those environments as it does in connected ones.

**The package manager itself is just a zip file.** The CLI, the metadata schema, the validation logic, the build tools: all packaged as a single zip. To deploy the package manager into an air-gapped environment, you copy one zip file across the boundary. Extract, configure, run.

What this requires:

- Every package distributable as a self-contained zip (already true: packages are tar.gz/zip files)
- Every vault sidecar distributable as a zip (already true: vault = zip on disk)
- The package manager binary distributable as a zip (build target)
- No runtime dependencies on hosted services (cloud APIs are optimisations, not requirements)
- Local-first metadata: catalogue, version manifests, signatures all in local files

What this enables:

- Air-gapped deployments (defence, classified environments)
- Offline development (long flights, remote sites, restricted networks)
- Reproducible installs (same zip equals same install, anywhere, anytime)
- Supply chain audit (one zip to scan, no remote dependencies to verify)
- Disaster recovery (restore from a zip without external services)

The system is recursive: a package manager that manages zips is itself a zip. SGit (which underpins vaults) already works from zips. Container runtimes can import zips. Vaults are zips. The pattern composes all the way down.

Online operation (downloading from S3, fetching updates, syncing catalogues) is an optimisation. Offline operation is the baseline.

### 5. Runtime Granular Loading

Build-time stripping reduces the package size on disk. Runtime granular loading is the next step: even within an installed, stripped package, do not load everything into memory at startup. Load the core, then load additional features on demand.

This serves three goals:

| Goal | How Runtime Loading Helps |
|------|---------------------------|
| Performance | Smaller initial memory footprint, faster startup |
| Security | Smaller attack surface during normal operation; less code in memory at any given moment |
| Cost | More functions per GB of RAM, more concurrent processes per instance |

The package manager supports this by treating each loadable subset as a named module that can be requested at runtime. The core binary boots fast. Specialised features load when they are actually invoked. Inactive features never enter memory.

This is the equivalent at the binary level of what lazy module imports do at the language level, but enforced by the package manager and visible in the SKILL.md so agents know which features require explicit loading.

### 6. Compute-Agnostic (Bare Metal and Containers)

A package installs identically on:

- Bare metal EC2 instance
- Docker container
- Podman container
- (Eventually) Apple containers, Kubernetes pods

The package does not know which compute substrate it is on. The installer detects the environment and adapts (different paths, different permissions). But the package contents and the tests are the same.

Containers are the fast testing substrate: spin up a container, install the package, run tests, destroy. Seconds, not minutes. Bare metal is the production substrate: install on EC2, run the real workload.

### 7. Architecture and OS Aware

The package manifest declares which architectures (ARM, AMD/x86) and which operating systems (Ubuntu, Fedora, Red Hat, Windows, etc.) are supported. The installer checks the host and selects the correct variant. All variants can coexist in the same package definition, with separate S3 paths.

This is first-class, not an afterthought. A single SG package definition for `sgit` can ship:

```
sgit/v0.27.32/
    +--> ubuntu-arm64/    sgit-runtime.tar.gz
    +--> ubuntu-amd64/    sgit-runtime.tar.gz
    +--> fedora-amd64/    sgit-runtime.tar.gz
    +--> rhel-amd64/      sgit-runtime.tar.gz
    +--> windows-amd64/   sgit-runtime.zip
```

The vault sidecar may also have OS-specific notes (Ubuntu hardening differs from Windows hardening). The package manager handles routing transparently.

### 8. Each Package Gets a Vault Sidecar

Every package has an associated vault (or folder that could become a vault) containing metadata that does not exist in the original package:

```
sg-packages/
    |
    +--> sgit/
    |       +--> v0.27.32/
    |       |       +--> ubuntu-amd64/sgit-runtime.tar.gz
    |       |       +--> manifest.json
    |       |       +--> package.json
    |       |
    |       +--> vault/
    |               +--> SKILL.md             instructions for agents
    |               +--> USAGE.md             how to use correctly, common mistakes
    |               +--> SECURITY.md          threat model, CVEs, hardening
    |               +--> ARCHITECTURE.md      data flow, component map
    |               +--> tests/
    |               |       +--> unit/
    |               |       +--> integration/
    |               |       +--> end-to-end/
    |               +--> issues/              known issues, workarounds
    |               +--> performance/
    |                       +--> benchmarks.json
    |                       +--> experiments/
```

**On disk, the vault is a single zip file.** The directory tree above shows the logical structure inside the vault. In cloud storage (S3 or any other object store), the entire sidecar is stored as one zip object. SKILL.md, USAGE.md, SECURITY.md, the tests folder, the performance data, every file shown above: all of it lives inside that single zip. Tools mount or extract the zip locally to expose the structure shown.

This is what makes the "no thousands of small files" property work: one download, one object, one storage entry per sidecar version. It also means the vault is self-contained and portable; you can move a sidecar between storage backends by copying one file.

When efficient access to specific small files inside the vault is needed repeatedly, deploy an SG/Send Vault server. The server reads the vault contents and exposes individual files via HTTP endpoints. A client fetches SKILL.md, USAGE.md, or any single file with one or two GET requests, no need to download the full zip. The two patterns coexist: zip-per-vault for cold storage and portability, vault server for hot access patterns where the same files are read repeatedly.

The vault provides:

- **Version control:** Every metadata change is a commit. The security review for v1.2 is different from v1.3.
- **Encryption:** Proprietary hardening guides and internal threat models can be encrypted.
- **Selective sharing:** Share SKILL.md with an agent via a vault read key without exposing the full security review.
- **Independence from SG/Send:** The sidecar works as a plain folder. SGit works from zips. No dependency on hosted infrastructure.
- **Single-file storage efficiency:** Connects to the SGit commit bundling research from day 51. Whole sidecars download as one bundle. No "thousands of small files" problem.

### 9. LLM-Friendly by Design (USAGE.md Solves a Real Problem)

Every package includes SKILL.md and USAGE.md. These are not nice-to-have documentation niceties. They solve a widespread problem: **most packages are used wrongly because nobody documents how to use them correctly**.

Existing documentation tells you how to install a package. It rarely tells you what error messages actually mean, which patterns work in practice, which command combinations are safe, which configurations break things subtly, what to monitor, when to upgrade, or what the package was actually designed for.

USAGE.md captures this. The format is structured so agents can parse it and humans can read it:

```
# USAGE.md
## When to use this package
## When NOT to use this package
## Common patterns that work
## Common patterns that fail
## Error messages decoded
## Operational warnings
## Configuration that breaks things
## Recommended monitoring
```

SKILL.md is the same information rendered for an agent: declared inputs, outputs, capabilities, failure modes, retry policies.

An LLM agent that encounters an SG package can read SKILL.md and use it correctly without prior training. That is the test: a model with zero prior exposure to the package should be able to operate it correctly from SKILL.md alone.

### 10. Customised Per Client / Per Environment

The package manager is not global. Each client, each application, each environment can have its own package set:

```
Client A (healthcare):
    sgit v0.27.32 (stripped for HIPAA compliance, no debug tools)
    ollama v0.5.1 (medical model only, no general chat)
    python v3.12 (minimal, only HIPAA-audited packages)

Client B (security consulting):
    sgit v0.27.32 (full, all debug tools)
    playwright v1.44 (with MITM proxy)
    elastic v8.14 (security dashboards preconfigured)
```

Same upstream packages, different configurations, different stripping, different SKILL.md, different security profile. The package manager is fractal: a property developed fully in the next section.

## The Fractal Package Manager: Managers All the Way Down

A package manager can contain another package manager. That inner package manager can contain another. There is no architectural limit to the depth. Each level is a fully functional package manager with its own catalogue, its own sidecars, its own customisations, its own zip.

This is the most powerful structural property of the design.

### Concrete Example: Four Levels Deep

```
Level 1: SG/Compute Global Package Manager
    Canonical, hardened, stripped versions of common packages
    Maintained by us and by upstream maintainers (via the commercial sidecar marketplace)
    Distributed publicly
    Contents: ollama, sgit, playwright, elastic, openssl, python, ...
    |
    v
Level 2: Acme Security Consulting Package Manager
    Built on top of Level 1
    Adds Acme's hardening, threat models, and operational guidance
    Adds Acme's private tools (their custom assessment scripts)
    Customises stripping rules for typical Acme engagements
    Contents: references to Level 1 + Acme overlay + Acme private packages
    |
    v
Level 3: Acme Engagement for ClientX Package Manager
    Built on top of Level 2
    Configured for ClientX's specific environment and compliance regime
    ClientX-specific SKILL.md (agents understand ClientX's data conventions)
    ClientX compliance settings (HIPAA, FedRAMP, whatever applies)
    Contents: references to Level 2 + ClientX overlay
    |
    v
Level 4: One specific application within ClientX
    Built on top of Level 3
    A single application, a single configuration, fully locked
    Locked versions, locked SKILL.md, locked everything
    Contents: references to Level 3 + application-specific lock file
```

Each level is a zip. Each level is independently deployable. Each level is air-gap capable.

### Two Distribution Modes

**Reference mode (small):** Level N contains only its own overlay. Using it requires Levels 1 through N-1 to be present locally. Smallest distribution size; requires intact chain.

**Embedded mode (large, air-gap-friendly):** Level N contains everything flattened into one zip: its own overlay plus all relevant packages from Levels 1 through N-1. Larger size; fully self-contained. Cross the air-gap boundary once with one zip.

**Hybrid mode:** Cherry-pick. Embed the critical packages, reference the rest. Tune the trade-off per deployment.

### The Graph Spans Levels

A package at Level 3 has a graph edge to its source at Level 2, which has a graph edge to its source at Level 1. Full provenance is queryable from any point: "where did this ollama come from? what did each level modify? which security review applies to my version? what changed between Level 2's view and Level 3's view?"

This is the supply chain audit story made concrete: one query, full history across all levels.

### Vault Sidecars Are Fractal Too

At each level, the vault sidecar can reference the level above. The SECURITY.md at Level 3 can be: "use Level 2's SECURITY.md as the base, then add these three ClientX-specific clauses." The package manager renders the effective SECURITY.md by composing the levels.

This is how a consultancy ships value: publish a hardening overlay at Level 2 that customers consume by referencing the consultancy's package manager from their own at Level 3. The consultancy is selling Level 2 sidecars to anyone who builds Level 3 on top of them.

### Why This Works in the Real World

Real-world deployments are layered. A defence contractor's environment is not "the same as Linux." It is "Linux, with the defence contractor's hardening, with the specific programme's compliance, with the specific system's lock file." Four levels at minimum.

Existing package managers cannot express this cleanly. You end up with private mirrors, custom builds, and undocumented overlays maintained by tribal knowledge. The fractal package manager makes each level a first-class, browsable, auditable artefact.

## IFD Versioning (Ours, Not Upstream)

We maintain our own version numbers alongside the upstream version:

```json
{
  "name": "sgit",
  "sg_version": "0.27.32-sg.3",
  "upstream_version": "0.27.32",
  "upstream_source": "pypi:sgit-ai",
  "modifications": [
    "Stripped test fixtures (saved 45MB)",
    "Added SKILL.md for agent use",
    "Added security review (SECURITY.md)",
    "Removed debug logging in production build",
    "Defined runtime-loaded modules (core + plugins)"
  ]
}
```

The `sg.3` suffix indicates this is our third modification of the upstream v0.27.32. A global manifest maps our versions to upstream versions for traceability and supply chain audit.

## Performance Measurement: Three Canonical Moments

Every package operation captures metrics at three canonical moments. These are the named, comparable measurement points:

| Moment | What Is Measured | Why It Matters |
|--------|------------------|---------------|
| **First load** | Time from "package not present" to "package on disk" | Cold-start cost: download, extract, prepare |
| **Boot time** | Time from "package on disk" to "service ready" | Warm-start cost: process spawn, initialisation |
| **Execution** | Time per operation once running | Steady-state cost: actual work |

Three numbers per package, per environment, per workload. These become the comparison axes for every optimisation experiment: "did this change reduce first load? boot time? execution? at what cost to the others?"

All three are stored as JSON in the vault. Loadable into the ephemeral Elastic instance (boots in 80 seconds) for visualisation. Screenshotable via Playwright. The full pipeline already exists; the package manager just needs to produce structured metrics in the right place.

### Vault Location via Environment Variable

The runtime needs to know which vaults hold the performance data, the SKILL.md, the security reviews, and so on. This is configured by environment variable:

```bash
SG_PACKAGE_VAULT=vault://abc123/sg-packages
SG_METRICS_VAULT=vault://def456/performance
```

The package manager reads these at startup. They can point to local vaults, S3-backed vaults, or remote SG/Send vaults. The runtime does not care which.

## S3 Loading: Modes and Techniques

| Mode | How | When to Use |
|------|-----|-------------|
| **S3 to disk** | Download to EBS/local disk, read from disk | Default, works everywhere |
| **S3 to memory** | Download to memory, never write to disk | Fast, RAM-limited. Best for small packages. |
| **S3 to NVMe** | Download to instance NVMe SSD (GPU instances) | Best for large model weights on GPU instances |
| **S3 NIC-maxing** | Saturate network interface bandwidth with parallel ranged GETs | Maximises throughput for any of the above modes |

NIC-maxing is the technique many high-performance S3 loaders use: split the file into ranges, issue parallel GET requests, saturate the network card. Bandwidth from S3 in-region can reach NIC line rate (often 10-25 Gbps on modern instances). This is the implementation detail that turns "S3 download" from a network operation into a near-disk-speed operation.

Hypothesis: S3 to memory with NIC-maxing is fastest for packages under 1GB. S3 to NVMe with NIC-maxing is fastest for model weights. S3 to EBS is slowest but most compatible. Benchmark all four; let the data decide.

## Communication with EC2: SSH (Not SSM)

For the build process (running commands on the EC2 instance during package creation and testing), use SSH, not SSM:

- SSH key injected into the EC2 instance at launch
- Build process is a series of SSH commands
- osbot-aws already has an SSH API for this (built previously)
- SSH is simpler, faster, no AWS API call per command
- SSM is useful for emergency access but too heavyweight for build automation

The build CLI wraps SSH and presents it as typed Python commands.
