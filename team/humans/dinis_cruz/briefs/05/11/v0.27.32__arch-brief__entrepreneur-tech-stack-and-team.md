## The Players

A vibe-coding entrepreneur shipping a vault-backed application has a small set of recurring players. Naming them explicitly makes the rest of the structure cleaner.

| Player | Role | What They Bring |
|--------|------|----------------|
| **The Entrepreneur** | The domain expert with the methodology and customer access | Vision, business logic, customer relationships, ability to vibe code |
| **Their AI Dev Tools** | The vibe-coding agents (Lovable, Cursor, Claude, ChatGPT) | Code generation, UI iteration, rapid prototyping |
| **Their Staff or Assistant** | Operational support (logistics, email, customer follow-up) | Day-to-day execution; can be augmented by agents |
| **Fractional Developer (V/TP)** | Picks up the explorer code; hardens, secures, frameworks-it | Wardley villager-to-town-planner transitions |
| **Security Reviewer** | AppSec, threat model, compliance review | Quarterly or release-gated reviews; not full-time |
| **DevOps / SRE** | Production monitoring, incidents, deployment health | Often a fractional company, not an in-house hire |
| **Designer** | User experience polish, brand consistency | Reviews the entrepreneur's vibe-coded UI |
| **Customer Service / Sales** | Front line with the end users | Initially the entrepreneur; eventually delegated |
| **The Platform (us)** | Vaults, runtime, templates, deployment, documentation | Tech stack, consultancy, hosting (optionally) |

The entrepreneur is the prime mover. Everyone else is fractional, agent-augmented, or in-platform support.

## Wardley Maps Framing

The roles map cleanly to the Wardley evolution stages:

| Stage | Role | What They Do |
|-------|------|-------------|
| **Explorer** | The Entrepreneur (vibe coding) | Tries things; ships PoCs; explores what works with customers |
| **Villager** | Fractional developer who hardens what the entrepreneur built | Refactors, adds tests, separates concerns, adds framework |
| **Town Planner** | DevOps / SRE / platform engineering (us, partly) | Production-grade infrastructure, monitoring, compliance |

The entrepreneur stays as the explorer. They keep iterating on customer-facing features. The villager and town planner roles support them; they do not slow them down.

We (the platform) are predominantly town planners: we package the deployment pattern, the vault infrastructure, the production-grade runtime. We also provide villager-level templates and frameworks so the entrepreneur's explorer code becomes solid faster.

## The Tech Stack (Minimal)

| Component | Purpose | Why It Is Enough |
|-----------|---------|-----------------|
| **Storage** (cloud object storage) | Static assets, vault data | One bucket per environment, S3 or equivalent |
| **Compute** | Vault API runtime | Serverless function, OR a single EC2/VM instance |
| **DNS mapping** | Custom domain → CloudFront/CDN | Standard cloud DNS, three subdomains |
| **SG/Vault technology** | Encryption, version control, sharing, app runtime | The core platform we provide |
| **GitHub** (or GitLab) | Source code, CI pipeline, master data | Where the entrepreneur's vibe-coded output lives |
| **Secrets manager** | API keys, vault keys, deployment credentials | Cloud-native or HashiCorp Vault |
| **The entrepreneur's vibe-coded app** | The actual user experience | HTML, JS, CSS produced by Lovable/Claude/etc. |

That is the entire stack. Eight items. No backend code in the traditional sense. No database (the vault is the database). No auth service (the vault keys are the auth).

This minimalism is the platform's promise: the entrepreneur does not have to learn or operate a complex stack. They learn one thing (the vault model) and the rest is conventional cloud primitives.

## Key Principles for the Stack

### 1. The User Controls Their Data

The user's data lives in their vault. They hold the key. They can revoke access at any time by re-encrypting. We never see the data; the entrepreneur never sees it without explicit user grant.

What can be retrieved after revocation is what was already viewed. There is no protection against memory or screenshots after the fact. But going forward, revocation is real and immediate.

### 2. No Backend Data to Protect

Because the user holds everything, the entrepreneur has no database of patient records, no spreadsheets of customer data, no proprietary formulas hosted on their server. There is nothing to leak from their backend because there is no backend data.

This collapses the entrepreneur's risk surface dramatically. Most data-breach scenarios simply do not apply.

### 3. The Vault Is the Communication Channel

Email, files, messages, application state: all transit via vaults. The vault is a communication channel as much as a storage primitive. This is what makes the architecture so small: many of the things you would normally need (queues, messaging services, file storage, document management) are subsumed by vaults.

### 4. The Entrepreneur Vibe Codes; The Team Hardens

The entrepreneur is the explorer. They generate the volume. The fractional team comes in behind to harden, secure, frameworks-ize. Both move forward; the entrepreneur is not blocked.

## Our Business Model in This Stack

We make money in this ecosystem through:

| Stream | Source |
|--------|--------|
| **Usage fees** | Hosting vaults, serving traffic, providing compute |
| **Maintenance contracts** | The relationship layer from the package manager commercial model |
| **Customisation work** | Helping a partner build a new template or extend an existing one |
| **Support** | Direct expert help; relationship-based |
| **Optional percentage of partner revenue** | Where we make the partner massively successful; case by case |

We do not make money from:

- Locking the partner in (the platform is open source)
- Holding the partner's data (we cannot, by design)
- Reselling the partner's customer data (impossible)
- Per-seat licensing of the platform (open source)

The economic alignment is direct: when the partner ships and grows, our usage grows. When they fail, we lose nothing material. Our incentive is to make every partner succeed.

## How Many Partners Can This Support?

The platform compounds. Each new partner:

- Stress-tests the technology in a new domain
- Produces a template that other partners can copy
- Generates case studies for the library
- Increases vault traffic (revenue)
- Refines the deployment workflow

The marginal cost per partner trends to zero as the platform matures. The marginal revenue per partner stays positive. The team supporting all of this stays small because the partners run themselves.

If we have ten partners by end of year, the case studies and templates make partner eleven onwards effectively self-service. If we have one hundred partners by next year, the marketplace dynamics start to matter (recommendations, ratings, template sharing). The platform's value grows non-linearly with adoption.

## Documentation as a First-Class Deliverable

The entrepreneurs need documentation more than they need code. Every operational pattern we have shipped (the deployment workflow, the agent communication, the template cloning, the vault model) needs to be a navigable page on sgraph.ai with worked examples.

This becomes the responsibility of @content (the website agent). The deliverables:

- A library section organised by use case (medical, investor, legal, education, etc.)
- A library section organised by capability (deployment, templates, agent comms, etc.)
- A "Start Here" path for new entrepreneurs to follow
- A "Worked Examples" section showing real partners' implementations
- A "Templates" section with clonable starting points

Documentation is the moat in a sense different from execution: when partners can self-serve, the platform scales without us.
