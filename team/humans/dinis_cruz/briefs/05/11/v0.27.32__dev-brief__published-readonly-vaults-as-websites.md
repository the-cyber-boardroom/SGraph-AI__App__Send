## What We Are Building

A new capability for SG/Send vaults: **public readonly publishing.** A vault owner can publish their vault to a public URL. Anyone with the URL can view the rendered content (App Mode, HTML pages, navigation) without needing a read key. The vault remains version-controlled, the owner remains in control, and updates to the vault propagate to the published site automatically.

This is the equivalent of what Netlify, Vercel, GitHub Pages, and Cloudflare Pages do for traditional websites: a one-step path from "I have content" to "the world can see it at a nice URL."

In our case, the content is a vault. The renderer is App Mode (or the vault content viewer). The publishing infrastructure is what this brief defines.

## Why This Capability Is Needed Now

Three concrete drivers, all from briefs published today:

1. **The job-search website use case** needs a public URL for the friend to share. Vault read keys work but are awkward to share by phone, email, or LinkedIn message. A nice URL is the right primitive.
2. **The 2026 entrepreneur strategy** depends on partners being able to ship to a public URL. A doctor running a patient assessment needs the patient to click a clean link, not "open this vault with this key."
3. **sgraph.ai itself** is a vault-rendered site that needs to be publicly accessible. We are already operating an instance of this capability for ourselves. This brief formalises it for everyone.

The capability has been implicit. This brief makes it explicit, documented, and offerable to partners.

## What "Published" Means

A published vault has these properties:

| Property | What It Means |
|----------|---------------|
| **Publicly accessible** | No read key needed; anyone with the URL sees the content |
| **Readonly to visitors** | Visitors can read but never write back, regardless of the vault's write permissions |
| **Owner retains full control** | The owner has write access and can revoke publication at any time |
| **Version-controlled** | The published version is a specific commit; updates require re-publishing (or auto-publish on push) |
| **Custom domain capable** | The owner can map their own domain to the published vault |
| **Free tier available** | A `*.sgraph.app` subdomain (or similar) for any vault, no payment required |
| **Paid tier for custom domains** | The custom domain mapping and any premium features sit behind a subscription |

The technical readonly enforcement is critical: even if the underlying vault has write tokens floating around, the published surface ignores them and serves a frozen view. The publishing layer is a one-way projection from vault to web.

## URL Structure

### Default URLs (Free)

Every published vault gets a subdomain on a shared root domain (working name: `sgraph.app`):

```
https://<vault-handle>.sgraph.app/
```

The vault handle is chosen by the owner at publication time (subject to availability). Examples:

```
https://private-health-demo.sgraph.app/
https://sara-job-search.sgraph.app/
https://acme-investor-pack.sgraph.app/
```

### Custom Domains (Paid)

The owner points their own domain at the published vault via DNS:

```
https://www.privatehealth.example.com/
https://sara.example.com/
https://invest.acme-capital.example.com/
```

The custom domain mapping is configured through the publishing dashboard. We handle the certificate (Let's Encrypt or equivalent) and the DNS-to-vault routing.

### Path-Based Routing Inside the Vault

The published vault's internal navigation works as expected:

```
https://sara-job-search.sgraph.app/                 # landing page
https://sara-job-search.sgraph.app/audiences/recruiters
https://sara-job-search.sgraph.app/work/timeline
https://sara-job-search.sgraph.app/now
```

Deep links work. SPA routing inside the vault's App Mode handles the path. Bookmarks and shares of deep links work correctly.

## Architecture

```
+--------------------+
| Vault (S3 bucket)  |   Encrypted vault objects
| Owner's account    |   Owner has write key
+--------------------+
        |
        v
+--------------------+
| Publish action     |   Owner declares: "publish this vault publicly"
| (writes a public   |   Generates a public read key (or marks vault as fully public)
|  manifest)         |   Records the chosen vault handle
+--------------------+
        |
        v
+--------------------+
| Edge cache layer   |   CloudFront (or equivalent)
| (vault-handle.     |   Origin: serverless function that reads the vault
|  sgraph.app)       |   Serves the rendered content
+--------------------+
        |
        v
+--------------------+
| Visitor's browser  |   Sees the site at the nice URL
+--------------------+   No vault key needed; the publish layer handles it
```

The serverless function at the edge:

1. Receives the request for `https://<handle>.sgraph.app/<path>`
2. Looks up the vault associated with `<handle>` (in a small handle-to-vault routing table)
3. Reads the vault objects for `<path>` (using the public read key from the publish manifest)
4. Returns the rendered content
5. Cache headers ensure the edge cache serves subsequent requests fast

For static assets (images, CSS, JS) inside the vault, the function streams them through the same path. For the App Mode entry point, the function returns the bootstrap HTML and the browser-side runtime fetches additional vault content as needed.

## The Publish Action

A new CLI command and UI button:

```
sgit publish --vault <vault-id> --handle <chosen-handle>
```

What it does:

1. Validates the vault is in a publishable state (has an `app.js` or content that can render)
2. Generates a public read key for this published version (or confirms the vault is fully public)
3. Records the handle-to-vault mapping in the routing table
4. Sets cache headers and propagates to the edge
5. Returns the URL: `https://<handle>.sgraph.app/`

Unpublish:

```
sgit unpublish --vault <vault-id>
```

Removes the handle mapping. The URL stops serving the vault (returns 404 or a "this site has been taken down" page).

Update:

```
sgit publish --update --vault <vault-id>
```

Publishes the current vault state (latest commit). The cache is invalidated for that handle.

Auto-publish on commit (opt-in):

```
sgit config set auto-publish true --vault <vault-id>
```

When set, every commit to the vault triggers a republish. The edge cache invalidates and the new content is live within a minute or so.

## What This Replaces

For partners building vault-backed applications, this replaces:

- Standing up their own CloudFront distribution and origin
- Managing the certificate for their custom domain (we do it for them at the published-vault level)
- Setting up the routing function that reads the vault
- Cache invalidation logic
- Custom domain mapping infrastructure

They get all of this for free with the free tier (subdomain on `sgraph.app`) and for a small subscription with a custom domain. The infrastructure work that used to take a DevOps person a day is now zero work for them.

This is "deployment is the product" from OWASP Article 03 in operational form. We are productising the deployment.

## Privacy Considerations

A published vault is **public**. Anyone with the URL can read it. Anyone can find it via search engines (we should respect robots.txt directives the owner adds to their vault). This is intentional: the use case is public-facing sites.

For private content, the existing vault sharing model (read keys, one-time tokens) is the right answer. The publishing capability is a different surface entirely; it is for content that the owner explicitly wants to be public.

The publishing dashboard should make this distinction extremely clear at publish time:

> "You are about to publish this vault publicly. Anyone with the URL will be able to read all content in this vault. Are you sure?"

Followed by a checklist: "I confirm there is no sensitive data, no patient records, no private notes in this vault. Only public-facing content."

## SEO and Indexing

Published vaults should be search-engine-friendly by default:

- Server-side rendering of the initial HTML (so crawlers see content, not blank app shells)
- Proper meta tags from the vault's `_page.json` configuration
- Sitemap generated from the vault structure
- robots.txt and other directives honoured

For owners who do not want their site indexed (e.g. a job-search site they only want to share with specific people), they can include a robots.txt in their vault that blocks crawlers. Default is open.
