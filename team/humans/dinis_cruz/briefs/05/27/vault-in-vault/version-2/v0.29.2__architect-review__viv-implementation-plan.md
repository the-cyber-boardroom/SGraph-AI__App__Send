## 1. BLOCKING — B1: the `directional` rule and the K1 rationale point at a removed mechanism

### What the plan says
- `01-PHASE-1` §2 and §6: a responder's `channel.request(...)` throws `'directional: responder cannot initiate'`.
- `01-PHASE-1` §4 "Why K1 instead of just trusting the port": *"For Phase 1 this is belt-and-suspenders; it becomes load-bearing in Phase 5 (`Kernel-B ↔ window.top` direct channel, mediated by the spawning kernel at birth)."*
- `01-PHASE-1` §10 hand-off item 3: *"Future (Phase 5+): kernel→`window.top` direct channels for the broker UI."*

### Why it's wrong
1. **`window.top` reach does not exist in this design.** Architect pack §01 §12 explicitly **removed** direct-to-`window.top` ("illegal under no-`window`; replaced by hop-by-hop… no, by direct per-kernel server I/O"). And Phase 5a of *this very plan* correctly says the vaults page aggregates **by querying each kernel** (`sg.broker.log()`), with *no* central collector and *no* top channel. So the K1 rationale and the §10 hand-off note describe a Phase 5 that contradicts the plan's own Phase 5. An implementer who believes "K1 is load-bearing for a `window.top` channel" will build upward reach — the exact thing the security model forbids (§01 §4, invariant #10).
2. **The directional rule, stated as "responder cannot initiate," is too broad for what Phase 2 needs.** `bootFromMessage` (02 §4) calls `this._parent.send('ready', { kernelId })` — a responder→initiator message. Replies to requests are also responder→initiator. If the directional guard accidentally blocks `send()` (not just `request()`), Phase 2's spawn handshake **deadlocks** waiting for a `ready` that the guard suppressed.

### Required change (doc-level, before coding)
In `01-PHASE-1-securechannel.md`:
- **§4 "Why K1":** replace the load-bearing/`window.top` sentence with: *"K1's only job is to let the child sign its generated K2.pub so the initiator can pin the child's long-term key before any secret flows. There is no `window.top` channel anywhere in this design (see architect pack §01 §12); the vaults page aggregates by querying each kernel (Phase 5a)."*
- **§10 hand-off item 3:** delete the `window.top` bullet. Replace with: *"Future cross-context edges (if any) use the same `MessagePort`+SecureChannel pattern; no `window.top`/`window.parent` reach is ever introduced."*
- **§2 / §6:** keep `request()` throwing on a responder, but **state explicitly that `send()` (events + replies) is permitted in both directions.** The directional invariant is "a responder cannot *initiate a request*," not "a responder cannot speak."
- **§8 tests:** extend **C3** — currently only asserts `responder.request(...)` throws. Add: *responder `send('ready', …)` succeeds and the initiator's `on('ready', …)` fires.* This pins the handshake path that Phase 2 depends on.

## 2. BLOCKING — B2: binary payloads do not survive the JSON envelope

### What the plan says
- `01-PHASE-1` §3: wire format = *"JSON-serialised envelope as a `Uint8Array` (`TextEncoder().encode(JSON.stringify(env))`)… easy to log/inspect."* Payloads live in `env.payload`.
- `02-PHASE-2` §4 `handleVfs` local read: `if (op === 'read') return this._dataSource.getFileBytes(path);`
- `02-PHASE-2` §4 cross-mount relay: `hit.mount.channel.request('vfs.' + op, { path: hit.rest, data, credential }, { sensitive: !!data })` — and the result is returned straight up.

### Why it's wrong (verified against shipped code)
`getFileBytes(path)` returns an **`ArrayBuffer`** — confirmed at `_common/js/adapters/vault-data-source.js:90` (the `.vault-settings.json` branch literally returns `new TextEncoder().encode(json).buffer`). `saveFile(folderPath, fileName, bytes)` (`vault-data-source.js:170`) takes **bytes**. But `JSON.stringify({ payload: <ArrayBuffer> })` yields `"payload":{}` — an `ArrayBuffer`/`Uint8Array`/`Blob` has no JSON representation. So:
- **Cross-vault read** returns an empty object to the app instead of the file bytes.
- **Cross-vault write** sends `data:{}` to the child, which writes an empty file.

This passes a "does the promise resolve / does a file appear" smoke test and **fails on real content** — the worst kind of latent bug, and it sits squarely on the KneeScore driving path (writing `data/reviews.json`).

### Required change (doc-level, before coding)
Pick one and write it into `01-PHASE-1` §3 + `04` test matrix:
- **Option A (minimal, keeps JSON-for-logging):** binary payloads are base64-encoded at the envelope boundary. Add to the `Envelope` contract: *"`payload` MUST be JSON-serialisable. Binary values (file bytes) are carried as `{ __b64: <base64 string>, __bytes: true }` and decoded by the recipient. `vfs.read` results and `vfs.write` `data` use this encoding."* Provide `bytesToB64`/`b64ToBytes` helpers in `secure-channel-envelope.js`.
- **Option B (cleaner, loses easy logging of bodies):** carry the envelope as a structured-cloneable object over `postMessage` (no `JSON.stringify`), so `ArrayBuffer`/`Uint8Array` transfer natively. Keep a separate `summary` field (type/path/sizes) for logging. This is more efficient for large files (no base64 33% bloat) and avoids a copy.

I recommend **Option B** for the data path (it's what `MessageChannel` is good at) with the envelope *metadata* still JSON for the broker log — but either is acceptable if tested. **Mandatory test (add to `04` matrix and Phase 1 §8):** round-trip a non-UTF-8 byte sequence (e.g. the 8-byte PNG signature `89 50 4E 47 0D 0A 1A 0A`) through `pack`/`unpack` **and** through a live `MessageChannel` request, asserting byte-exact equality. Today no test would catch this.

> Note: B2 interacts with the PKI encryption step. When `enc:true`, the *encrypted* payload is already binary (`{iv, ct}`); confirm that whichever option you choose, the encrypt-then-serialise order is: encode bytes → encrypt → wrap ct as base64/clone. The current §3 `encryptPayload(jsonObj, …)` assumes a JSON object input, which won't hold for raw file bytes — make `encryptPayload` take bytes, not a JSON object, for the data path.

## 3. SHOULD-FIX (fold into the named phase)

### N1 — `vfs.list` across a mount: the `rest===''` root case isn't in the code path (Phase 2)
`02 §5` step 4 describes the mount-root listing in prose, but the `handleVfs` code in `02 §4` only shows the generic relay. Make `handleVfs` explicit:
- if `resolve(path)` returns a mount with `rest===''`, the kernel may either synthesise the mount as a folder entry **or** relay `list` with an empty path to the child; pick one and code it.
- if relaying with `rest===''`, confirm the child's `listFolder('/' + '')` === `listFolder('/')` returns the child root (it should; empty-string path handling is a classic off-by-one — add a `KernelMounts`/relay test for `resolve('mounts/p')` → `rest===''` → child root listing).

Also: `list` goes through `broker.mediate` with cap `fs.read` → default policy `auto`, so it won't prompt — that's correct and intended; just make sure the prose and code agree that **reads/lists are `auto`, writes/deletes are `ask`** by default.

### N2 — nested-kernel boot is hard-blocked on the live SG/API (Phase 2 precondition)
`02 §6`'s test note admits `SGVault.open` does a network `fetch`, i.e. Phase 2's `mountChild` cannot complete until the CORS fix is **deployed and CDN-clean on `dev`** (not merely merged). Hoist this into **Phase 2 preconditions** as a hard stop:

> **Do not run 02 §7 (the browser end-to-end) until pack §6.6 passes on `dev`:** a `sandbox="allow-scripts"` null-origin iframe on `dev.vault.sgraph.ai` completes a tokenless GET and a token PUT to `dev.send.sgraph.ai` with `Access-Control-Allow-Origin: *`. A `Failed to fetch` here is almost always a stale CDN cache of the old reflected-`Origin` header — invalidate before debugging code.

Phase 1 (SecureChannel, no network) is **not** blocked by this and can proceed in parallel.

### N3 — broker `finalize` matches by tuple; use an opaque entry id (Phase 2)
`02 §3 KernelBroker.finalize` scans backwards for the last `pending` entry matching `(mountId, op, path)`. Two concurrent ops on the same path (or a write + retry) close the wrong entry, corrupting the audit trail the vaults page renders. Change `mediate` to return an opaque `entryId` (push it onto the log entry) and have `finalize(entryId, result)` take it directly. Cheap now; annoying to retrofit once Phase 5 depends on log accuracy. (AppSec cares about this — see §5.)

### N4 — harness confirmed (no action)
Verified on `dev` @ v0.29.2: `tests/unit/vault_ui/loader/{run-all.sh,test__app_permissions.js,helpers.js}` exist; Node here has `MessageChannel: function` and `crypto.subtle: object`. The plan's claim that C1–C4 run jsdom-free via `runInThisContext` holds. Recorded for confidence; nothing to change.

## 4. What the plan gets right (preserve these)

- **`handleVfs` local-vs-cross-mount fork** is the correct realisation of "one primitive" (§01 §1). Keep it.
- **App-A stays same-origin in Phase 2; null-origin split deferred to Phase 3.** Correct decoupling — product unlock doesn't block on the security refactor (pack §5.2). Keep the sequencing.
- **Verbatim reuse of `SGVault` / `VaultDataSource` / `sg-vault--sync.js`** for the child's own write — the big win of "a mount is just an app." Do not invent cross-mount storage machinery.
- **`sg-embed-frame.js:147` cited as the null-origin precedent** — accurate; it already mounts untrusted embeds with no `allow-same-origin`, no bridge.
- **Phase 3 sub-steps A–F** with E as the single breaking flip and the probe page (§7) as the gate — exactly how to stage a boundary change.
- **The vault-repair checklist (04)** grounded in real error codes (`EPERM`/`EPROTECTED`/`ECONSENT`/`EUNREACH`) — this is what makes "breakage is acceptable" operationally true.
- **Per-kernel broker, Edge 2 only** — matches D1 and §01 §8; the plan never puts the broker on the server edge. Good.

## 5. AppSec items to pull in (do not block Phase 1)

Two findings touch the security/audit surface and want an AppSec co-sign before they ship — both are Phase 2/3, not Phase 1:

1. **B2 binary handling on the PHI path.** The cross-vault write payload (`data/reviews.json`) is clinical content. Whichever encoding (Option A/B) is chosen, confirm with AppSec that: (a) when `enc:true` the bytes are encrypted *before* serialisation and the recipient is the only holder of the decrypt key (pack §01 §10), and (b) the broker log records *metadata only* (op/path/sizes/decision), never the content bytes — otherwise the audit trail leaks PHI.
2. **N3 log integrity.** The audit trail is a security artefact; the `entryId` fix is what makes "every inter-vault access is logged accurately" true under concurrency. AppSec should sign off that the finalised log is tamper-evident enough for the trial's needs (it's in-memory per kernel today — confirm that's acceptable for the synthetic-data phase, and flag persistence as a later item).

Neither blocks starting Phase 1. Both block Phase 2 going to anything beyond synthetic data — consistent with the coupling rule (pack §5.6).
