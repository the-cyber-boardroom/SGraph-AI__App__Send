# SG/Send On Vaults: Vault-Per-User, SG/Sentinel As A Business-Logic Engine, And Trust Through Gamification

## What This Is

The third SG/Send brief, expanding on how vaults can carry the open-evaluation model while keeping the architecture simple. It follows the identity-persistence-budgets brief (every user gets a fingerprint identity and account) and develops what sits underneath: **vaults as the storage substrate for every user, SG/Sentinel rules writing to those vaults, and the possibility of moving business logic itself into SG/Sentinel rules so the application stays simple.**

Four linked ideas:

- **Vault-per-user**: every user, even anonymous, gets a vault where their actions and activity are saved; SG/Sentinel rules mainly write to vaults; vaults decompose and remove complexity from the platform.
- **SG/Sentinel as a business-logic execution engine**: because SG/Sentinel sees everything and is rule-based, business logic like authentication, authorisation, and upload/download metrics can move into rules, removing complexity from the app.
- **Trust through gamification**: users unlock features by demonstrating behaviour (you cannot create a vault until you have sent five files), which is increased trust as a security property.
- **Multi-account detection**: because every user is identified, creating multiple accounts becomes a detectable abuse signal.

The governing theme, in the project lead's words: **use vaults left, right, and centre, to decompose and remove complexity, and dogfood our own platform.** Nothing here redesigns the SG/Sentinel work; it applies it to SG/Send and surfaces one significant SG/Sentinel extension (SG/Sentinel as a business-logic engine).

## Vault-Per-User: The Storage Substrate

The foundational mechanism: **every user gets a vault (or a place to upload to), where their actions and activity are saved.** This is how SG/Send stores per-user data without building a large backend.

The voice memo: **"we should create a vault per user. Your actions and the stuff you do get saved to your vault. Every anonymous user gets a vault. Each user gets given a vault or a place we can upload stuff to, and that's how we communicate."**

The reasoning is architectural simplification. Rather than building bespoke backend storage and management for user data, SG/Send uses the platform's own vault primitive: each user has a vault, their activity is written to it, and the vault provides the storage, encryption, versioning, and movability for free. The voice memo: **"we should be using vaults to decompose, to remove complexity from this whole platform, and to store data in ways that can be managed and moved around."**

This is dogfooding in the strongest sense (cross-ref: the SG/Sentinel test-driving brief's dogfooding): SG/Send stores its own users' data in the platform's own vaults, exercising and proving the vault primitive on the platform itself. The voice memo: **"this is how we dogfood our stuff."**

### The Efficient-Write-To-Vault Concept

A mechanism the voice memo recalled for making per-user vault writes efficient: **write to a particular folder in a vault that can be decrypted with the key and processed later, rather than requiring heavy real-time processing.**

The voice memo: **"we need to make it very efficient to write to a vault. We had this concept of just writing to a particular folder in a vault that can be decrypted with the key and then processed later."** This connects to the not-everything-real-time principle (cross-ref: the SG/Sentinel execution-model brief: slow analysis, fast enforcement) and the asynchronous Layer 3 (cross-ref: the SG/Sentinel time brief). The voice memo was explicit: **"we don't have to make all this run real time to start with."** A rule can write the user's activity to their vault folder quickly, and heavier processing happens later, asynchronously. This keeps the hot path fast while still capturing everything to the vault.

### The Zero-Knowledge Nuance

An important property the voice memo stressed, which is central to the privacy stance: **even with access to all the logs, the platform still cannot see the data the user puts in their vault.**

The voice memo: **"even at this stage, although I have access to all the logs, I still don't have access to all the data they are putting in there. I still can't see the information that goes in there."** This is the zero-knowledge boundary (cross-ref: the SG/Sentinel research brief and developer-friendliness brief: zero-knowledge-bound) holding even in the maximum-visibility free mode: the platform sees the activity logs (what was done, when, by which fingerprint) but not the encrypted content of the user's vault. The voice memo called this an important metric. It is what lets the free/non-private mode have maximum visibility into behaviour while still not seeing the user's actual data: visibility of activity, not of content. This is a crucial distinction for the privacy story: even the most-tracked free user's actual files stay encrypted and unseen.

## SG/Sentinel Rules Write To Vaults

The mechanism connecting SG/Sentinel to the vaults: **the SG/Sentinel rules (the rule, the Lambda function, the Lambda@Edge that executes) mainly write to vaults.** This is how user activity gets captured into the per-user vaults.

The voice memo: **"the rule that is going to run, or the Lambda@Edge that executes this, is mainly writing stuff to vaults. The SG/Sentinel rules are mainly writing stuff to vaults."** Because SG/Sentinel sees every request (cross-ref: the SG/Sentinel architecture-and-data-flows brief), it is the natural place to capture user activity, and it captures it by writing to the user's vault. This connects to the vault-per-request supply-chain pattern (cross-ref: the SG/Sentinel vault-aware brief): there, each layer adds files to a request's vault; here, the rules write each user's activity to their user vault. The vault is again the substrate SG/Sentinel writes to.

This reinforces the architecture-simplification theme: SG/Sentinel is already in the path seeing everything, so having it write activity to vaults means no separate activity-capture system is needed. The rule that identifies the user (the identity-creation rule, cross-ref: the identity-persistence-budgets brief) and the rule that captures their activity both write to the user's vault.

## SG/Sentinel As A Business-Logic Execution Engine

The most significant new idea, and a genuine extension of the SG/Sentinel architecture: **because SG/Sentinel is rule-based and sees everything, business logic like authentication, authorisation, and metrics can move into SG/Sentinel rules, removing that complexity from the application.**

The voice memo: **"should we move some of the business logic into the SG/Sentinel rule? Why can't SG/Sentinel do authorisation and authentication? Why do I have the complexity of which user has access to what in my app, if I can just write that as a rule, and the rule enforces it, so I remove complexity? SG/Sentinel becomes an execution engine for business logic, because it's fundamentally a rules-based thing."**

This extends the control-flow-graphs brief (cross-ref: the SG/Sentinel control-flow-graphs brief, which established that SG/Sentinel *can make* business-logic decisions because Layer 2 shares state with the app). This brief goes further: SG/Sentinel does not just *inform* business-logic decisions, it can *execute* them. Authentication, authorisation, and access control move from app code into rules.

The candidate business logic to move into rules:

| Business Logic | As An SG/Sentinel Rule |
|----------------|------------------------|
| **Authentication** | A rule verifies the user (fingerprint, key) |
| **Authorisation** | A rule enforces which user has access to what |
| **Upload tracking** | A rule captures uploads (it sees them anyway) |
| **Download tracking** | A rule captures downloads |
| **Upload/download metrics** | Rules compute the metrics from what they see |

The voice memo's reasoning on why this works: **"we have the edge, we are Lambda@Edge, but we can also call other stuff. The enforcement of authentication and authorisation, maybe with some delay, can be done in there. The rules become the logic."** SG/Sentinel runs at the edge (Lambda@Edge) and can call other services, so it can enforce authn/authz, possibly with some delay (the not-everything-real-time principle again). The voice memo noted the metrics angle especially: **"things like upload tracking, download tracking, upload metrics, download metrics: SG/Sentinel is going to see all of that anyway. If we add a little bit of business logic to it, it becomes a rule execution engine."**

The architectural payoff is significant: **moving business logic into SG/Sentinel rules removes that complexity from the application.** The app no longer needs to implement which-user-can-access-what; that becomes a rule SG/Sentinel enforces. This is the rules-are-everything model (cross-ref: the SG/Sentinel rules-engine brief) extended from security rules to business-logic rules: the rule is the logic, and SG/Sentinel is the engine that runs it. It connects to the development-workflow brief's reframing (cross-ref: the SG/Sentinel development-workflow brief: the rules become the definition of the application): if business logic is in the rules, the rules define even more of the app.

The voice memo was appropriately measured: **"there's some merit here, I think we need to explore that, but let's keep it with the Sentinel for now."** So this is flagged as a promising direction to explore (SG/Sentinel as a business-logic execution engine), kept within the SG/Sentinel concept rather than spun out, and developed further when it becomes a focus. It is a significant idea: it would make SG/Sentinel not just a security and traffic layer but a business-logic execution layer, substantially simplifying the applications it protects. This should be captured in the SG/Sentinel corpus as a major architectural direction (alongside the identity-creation rule from the identity-persistence-budgets brief).

## Trust Through Gamification

A distinct new idea, and a powerful security property: **users earn increased trust by demonstrating behaviour, unlocking features as they go, which is gamification serving security.**

The voice memo: **"this idea of increased trust, almost like gamification. You come to the website, you get an account. If you haven't paid, you don't get access to everything. There are things you can only do once you unblock certain features. For example, you can't create a vault until you've sent five files."**

This is increased-trust-through-demonstrated-behaviour as a security mechanism:

| Trust Level | Unlocked By | Grants |
|-------------|-------------|--------|
| New account | Arriving | Basic capabilities |
| Demonstrated use | Sending five files (or similar) | More capabilities (e.g. creating a vault) |
| Paid | Payment | More still (cross-ref: the budget model in the identity-persistence-budgets brief) |
| Dedicated | Provisioning | Privacy and a dedicated profile |

The security value is real: a brand-new account (which could be a bot or an attacker) has limited capability; capability is earned by demonstrating legitimate behaviour over time. This is the detect-before-damage and progressive-trust thinking (cross-ref: the SG/Sentinel time brief, the zero-trust framing in the addendum) expressed as a user-facing gamification: trust is not granted at the door, it is earned, and capability follows trust. An attacker or bot that cannot or will not demonstrate legitimate behaviour never unlocks the higher-capability (and higher-cost-to-abuse) features.

This composes with the budget model (cross-ref: the identity-persistence-budgets brief): budget gates *how much* you can do; gamified trust gates *what* you can do; payment unlocks both. Together they form a graduated capability model where capability is earned through trust, payment, and demonstrated behaviour.

### Showing Users Their Activity And Offering Privacy

The voice memo tied gamification to the education-and-privacy theme (cross-ref: the first SG/Send briefing): **show users everything they have done and everything we have captured, then offer privacy as the upgrade.**

The voice memo: **"we should show the user everything they have done, everything we have from them, every request we captured. Remember this is for evaluation. Then we say, if you want privacy, you get a dedicated account, which we provision, and that has a very different profile and threat profile."** This is the free-mode-shows-you-everything, paid-mode-gives-you-privacy model (cross-ref: the first briefing) made concrete at the activity level: the free user sees their full captured activity (educational, transparent), and the upgrade to a dedicated, provisioned account changes the profile entirely. The dedicated account has a different threat profile (it is isolated, provisioned, private), connecting to the ephemeral-EC2 and confidential-data separation (cross-ref: the identity-persistence-budgets brief).

## Multi-Account Detection As An Abuse Signal

A security property that falls out of no-anonymous-users (cross-ref: the identity-persistence-budgets brief): **because every user is identified, someone creating multiple accounts becomes a detectable abuse signal.**

The voice memo framed it as a deliberate red-team target: **"from a security point of view, try to hack it, try to create multiple users, see if our defences detect it. If multiple people create multiple accounts, that's a good example of a signal we should have, because we should try to detect that."**

This connects to the agentic red-team (cross-ref: the SG/Sentinel test-driving brief): trying to create multiple accounts is exactly the kind of attack the red-team should attempt, and detecting it is exactly the kind of defence SG/Sentinel should provide. Because identity is fingerprint-based (cross-ref: the identity-persistence-budgets brief), multiple accounts from the same underlying fingerprint, or patterns of mass account creation, are detectable signals. This is a concrete instance of the make-the-site-hostile-to-bad-traffic goal (cross-ref: the SG/Sentinel principles brief): mass account creation is bad-traffic behaviour, and SG/Sentinel detects and resists it.

## What This Asks For

Concrete next steps:

1. **Give every user a vault** (even anonymous; the per-user storage substrate).
2. **Have SG/Sentinel rules write user activity to user vaults** (the rules are in the path; they capture to vaults).
3. **Use the efficient-write-to-vault pattern** (write to a folder, decrypt with key, process later; not all real-time).
4. **Preserve the zero-knowledge boundary** (activity visible, vault content unseen, even in free mode).
5. **Explore SG/Sentinel as a business-logic execution engine** (move authn, authz, upload/download tracking and metrics into rules; capture in the SG/Sentinel corpus as a major direction).
6. **Build trust through gamification** (unlock features by demonstrated behaviour: e.g. send five files to create a vault).
7. **Show users their full activity** and offer the dedicated-account privacy upgrade.
8. **Detect multi-account creation** (a fingerprint-based abuse signal; a red-team target).
9. **Dogfood the platform** (SG/Send stores its own users' data in the platform's vaults).

Estimated effort: vault-per-user and rules-write-to-vaults build directly on the vault primitive and SG/Sentinel's in-path position; the efficient-write pattern needs a small exploration; SG/Sentinel-as-a-business-logic-engine is a larger direction to explore (kept within SG/Sentinel for now); gamification and multi-account detection are rule-and-product work on top of the identity model.

## What This Does Not Try To Be

- **Not a redesign of the SG/Send identity or tier model.** It develops the vault substrate beneath them.
- **Not a commitment to move all business logic into rules.** SG/Sentinel-as-a-business-logic-engine is a direction to explore, kept within the SG/Sentinel concept.
- **Not a breach of zero-knowledge.** Activity is visible; vault content stays encrypted and unseen.
- **Not a heavy real-time system.** Efficient vault writes plus later processing; not everything real-time.

## Honest Risks

**Risk 1: Moving business logic into rules could overload SG/Sentinel or blur concerns.** Authn/authz in rules is powerful but could make SG/Sentinel a complex monolith. Mitigation: explore incrementally; keep the baseline simple (cross-ref: the MVA brief's robust baseline); the rich rule metadata distinguishes business-logic rules from security rules; keep it within SG/Sentinel for now, as the voice memo said.

**Risk 2: Vault-per-user at scale could be a lot of vaults.** Many users means many vaults. Mitigation: vaults are lightweight (cross-ref: the vault-aware brief); the efficient-write pattern and the ephemeral persistence policy (cross-ref: the identity-persistence-budgets brief) keep it manageable; prune anonymous vaults per the cleanup policy.

**Risk 3: Gamification could frustrate legitimate users who want capability immediately.** Earning trust takes interaction. Mitigation: the thresholds are low (send five files); payment is an immediate unlock path; the design (cross-ref: the SG/Sentinel UX brief) makes the progression feel rewarding, not obstructive.

**Risk 4: Authn/authz with delay could create windows.** Enforcing authorisation asynchronously could leave gaps. Mitigation: critical authz stays synchronous; the with-some-delay applies to non-critical enforcement; the detect-before-damage window (cross-ref: the time brief) bounds it.
