This one is the setup: what Wardley maps are, the new capability to render them directly in Mermaid (so they live in GitHub, web pages, and our documentation as code), how they apply to us, the use cases worth mapping, and the render-and-screenshot workflow. The companion brief holds the actual maps with descriptions.

The motivation, in the project lead's words: **create a series of maps that explain what we are doing, the value we add, and fundamentally the shift, what we are commoditising.** The classic Wardley move is to show someone a map of how something works today, then a map of what we enable, with an arrow saying "we are commoditising this bit." We are, in effect, commoditising privacy and security, because with our platform they just happen.

A note on currency: Wardley map support in Mermaid is recent (v11.14.0+), so this brief is grounded in the current official Mermaid syntax, verified against the Mermaid documentation, so the maps we write actually render.

## What Wardley Maps Are (Brief Context)

A Wardley map is a visual representation of a value chain positioned on two axes, used for strategic analysis. Unlike most diagrams, position has meaning (it is a map, not just a diagram):

- Visibility (the Y-axis): how visible or valuable a component is to users, from infrastructure at the bottom to user-facing at the top.
- Evolution (the X-axis): how evolved or mature a component is, from genesis or novel on the left to commodity or utility on the right.

This dual positioning enables strategic analysis of value-chain dependencies, the evolution of components over time, build-versus-buy decisions, and inertia or resistance to change. Components are connected in a value chain (an anchor, usually the user or customer, at the top, depending on components below), and the map shows where each sits and where it is heading.

The strategic power for us is the evolution axis: showing that something which is custom and painful today (privacy, security, version control) becomes a commodity in our solution, and that commoditising it enables higher-order businesses to be built on top. This is the genesis-to-commodity story, which is exactly what Wardley maps are built to tell.

## The New Capability: Wardley Maps In Mermaid

Until recently, Mermaid (the go-to text-to-diagram tool) did not support Wardley maps; you needed a separate tool like OnlineWardleyMaps. That changed: Wardley map support was contributed to Mermaid, so you can describe a complete strategic map in a few lines of plain text, ready to embed in documentation, share with stakeholders, or version control alongside code. The capability landed in Mermaid v11.14.0+ and Wardley maps now render in GitHub Markdown directly.

This matters to us for three reasons:

1. **Maps as code, version-controlled.** A Wardley map becomes a few lines of text, versioned alongside everything else (and storable in a vault, the articles-as-vaults pattern). This fits the diagramming-as-code discipline the project already uses for Mermaid flowcharts and sequence diagrams.
2. **Renders in GitHub and the web.** Because GitHub renders Mermaid (including Wardley now), the maps appear directly in our repos and documentation, and can be embedded in web pages and put on our website.
3. **Renderable and screenshot-able in our workflows.** A simple web page with the Mermaid map, plus Playwright to open it and take a screenshot, gives us images on demand. The voice memo: **"you can create a web page, slap Playwright on it, take a screenshot, and show it to me."** This also means Claude can create and render Wardley maps inside the Claude environment (a skill to create and render maps), so we can have a conversation about a map and see it.

## The Mermaid Wardley Syntax (Verified)

The current syntax, so the maps we write render correctly. Every map starts with the `wardley-beta` keyword.

### The Critical Coordinate Rule

The single most important thing to get right: **Mermaid uses the OnlineWardleyMaps format `[visibility, evolution]`, which is the opposite of typical (x, y) notation.**

- The first value is visibility (0.0 to 1.0, bottom to top, the Y-axis); the second value is evolution (0.0 to 1.0, left to right, the X-axis). This is opposite of typical (x, y) notation.

So `component Vault [0.5, 0.4]` means visibility 0.5 (middle height), evolution 0.4 (left-of-centre, still evolving). Getting this backwards puts every component in the wrong place, so it is the thing to check first.

### The Core Elements

| Element | Syntax | Meaning |
|---------|--------|---------|
| Diagram | `wardley-beta` | Required first line |
| Title | `title Text` | Optional title |
| Size | `size [width, height]` | Optional canvas (default `[1100, 600]`) |
| Anchor | `anchor Name [vis, evo]` | A user/customer (bold label) |
| Component | `component Name [vis, evo]` | A value-chain component |
| Link | `A -> B` | A depends on B |
| Flow | `A +> B` | A flow link |
| Evolve | `evolve Name targetEvo` | Red dashed arrow showing evolution toward a target evolution value |
| Note | `note "Text" [vis, evo]` | A note at a position (text quoted) |
| Inertia | `(inertia)` after a component | Marks resistance to change |
| Strategy | `(build\|buy\|outsource\|market)` | Build/buy/outsource/market decision symbol |

A note on names: component names may contain hyphens (like real-time processing or end-user) without quoting; quote a name only if it begins with a non-letter or contains a character the grammar does not otherwise accept.

### A Minimal Worked Example

The canonical tea-shop example shows the shape of a complete map:

```
wardley-beta
title Tea Shop Value Chain
anchor Business [0.95, 0.63]
component Cup of Tea [0.79, 0.61]
component Tea [0.63, 0.81]
component Hot Water [0.52, 0.80]
component Kettle [0.43, 0.35]
component Power [0.10, 0.70]
Business -> Cup of Tea
Cup of Tea -> Tea
Cup of Tea -> Hot Water
Hot Water -> Kettle
Kettle -> Power
evolve Kettle 0.62
evolve Power 0.89
note "Standardising power lets Kettles evolve faster" [0.30, 0.49]
```

This is the pattern every map in the companion brief follows: declare the anchor (the user), declare the components with `[visibility, evolution]` coordinates, link them into a value chain, add `evolve` arrows to show the strategic shift, and add notes to call out the insight.

### Additional Features (For Richer Maps)

- **Trend indicators** show a predicted future position. Note the caveat: trends use standard (x, y) order, not [visibility, evolution], so they are the exception to the coordinate rule.
- **Pipelines** group components that share visibility and vary by evolution: pipeline components share visibility and only vary by evolution, written as `pipeline Parent { ... }`.
- **Notes** must have quoted text: `note "text" [vis, evo]`.
- **Numbered annotations**: `annotation N,[x,y] "text"`, optionally with an `annotations [x, y]` position block.
- **Custom evolution stages**: `evolution Stage1 -> Stage2 -> ...` to relabel the X-axis.
- **Source strategy symbols**: `(build)` triangle, `(buy)` diamond, `(outsource)` square, `(market)` circle.

A current limitation worth knowing: hand-drawn/rough mode is not supported for Wardley maps, because the diagram uses a custom D3 renderer rather than the shared shape system.

## How Wardley Maps Apply To Us

The voice memo identified the maps worth creating, each telling a part of the strategy. These are the use cases the companion brief renders:

| Map | The Story It Tells |
|-----|--------------------|
| **Today vs SG/Send (file sharing)** | What sending files looks like today (WeTransfer, email) vs what SG/Send enables, including privacy |
| **The privacy story** | Even in the tracked free mode the data is still encrypted; we still cannot see the data; the privacy properties hold |
| **The vault for sensitive information** | An investor sharing confidential deal/board information: before (WeTransfer, email) vs after (a vault), the commoditisation arrow on privacy and security |
| **Version control** | Today version control is complex and badly done (folders, inconsistent naming, no branches/commits); our vaults make it a commodity |
| **Agentic communication and memory** | Agent-to-agent, agentic memory and knowledge, with control, evidence, traceability, explainability |
| **The overall strategy** | Lots of little features, open source, client-side encryption; what we commoditise (file sharing, and more importantly vaults); enabling higher-order businesses on top |
| **Apps in the vault** | A vault plus a bit of HTML becomes a mini app; commoditising the vault enables a whole new layer of apps and workflows |

The recurring strategic move in all of these is the commoditisation arrow: **show what is custom and painful today, then show our solution moving it to commodity, with the arrow that says "we commoditise this."** The voice memo: **"we are commoditising privacy, we are commoditising security, because it just happens."** And the higher-order consequence: **"once you commoditise something, you enable other businesses to be built on top,"** which is the apps-in-the-vault story (a vault plus HTML becomes a mini app, enabling workflows that were not possible before).

### The Privacy Nuance To Map Carefully

One nuance the voice memo stressed, which the maps must represent honestly: **even in the tracked (free) mode, the data is still encrypted; we still do not have access to the full data, so the privacy properties still hold.** The maps should not overclaim. In the free mode we track activity (cross-ref: the SG/Send identity-persistence-budgets brief), but the data stays encrypted and unseen (cross-ref: the SG/Send vaults brief's zero-knowledge nuance). The privacy map should show this precisely: tracked activity, but encrypted, unseen data, so the core privacy property is preserved across both modes.

## The Strategy The Maps Express

The voice memo framed the maps as how we map the strategy itself. The strategy, to be expressed visually:

- **Lots of little features** (the platform's accumulated primitives).
- **Open source.**
- **Client-side encryption.**
- **Commoditising file sharing, and more importantly the vault.**
- **Enabling higher-order businesses on top** (the once-you-commoditise-something-you-enable-what-sits-above move, the classic Wardley and innovate-leverage-commoditise pattern).

The apps-in-the-vault point is the keystone: because a vault can render a full-screen web page, **adding a bit of HTML on top of a vault (with the HTML talking to the vault) creates a mini app.** Once you have apps, a whole series of workflows and capabilities that were not possible before become possible. The map shows the vault evolving to commodity and the apps layer emerging on top of it, which is the genesis-evolution story Wardley maps capture best, and a great basis for articles (cross-ref: the articles-as-vaults and de-commoditising work).

## The Render-And-Screenshot Workflow

The practical workflow for producing and using the maps:

1. **Write the map as Mermaid `wardley-beta` text** (version-controlled, in a vault, in the repo).
2. **It renders in GitHub Markdown directly** (native Mermaid Wardley support).
3. **For images, render in a web page and screenshot with Playwright** (open the page, screenshot, get an image on demand).
4. **Embed in the website and documentation** (the maps go on our website, in articles, in stakeholder decks).
5. **Claude can create and render maps in-conversation** (a skill to create and render Wardley maps, so we can discuss a map and see it).

This is the diagramming-as-code workflow extended to strategy: the maps are text, versioned, rendered automatically, and usable everywhere, the same way the project already treats its other Mermaid diagrams.

## A Note On Rendering (Verified)

The maps in the companion brief have been rendered and visually verified, using the Mermaid CLI (which bundles Mermaid v11.14.0, the version with Wardley support) pointed at the Playwright-bundled Chromium as the headless browser. So the maps are not just syntactically plausible; they have been confirmed to render as correct Wardley maps (axes, anchors, components, dependency links, evolve arrows, and notes all placed correctly). The companion brief carries the corrected, verified source, and the rendered PNGs are provided alongside.

The toolchain that works: a Mermaid v11.14.0+ CLI, with a Puppeteer/Playwright config pointing `executablePath` at an installed Chromium (the Playwright browser at `/opt/pw-browsers/chromium-*/chrome-linux/chrome` works, with `--no-sandbox`). The same source also renders in GitHub Markdown and mermaid.live.

### A Practical Syntax Caveat Discovered While Rendering

Although the Mermaid docs say component names may contain hyphens without quoting, in practice (v11.14.0) **component and anchor names that contain a hyphen, an ampersand, or a slash cause a parse error when those names are referenced in links or `evolve` statements.** For example, `Client-Side Encryption`, `Zero-Knowledge Storage`, `SG/Send`, and `Folders & Naming` all failed to render when used in links. The robust fix is to **keep component and anchor names to letters and spaces** (for example, `Client Side Encryption`, `Zero Knowledge Storage`, `Use SG Send`, `Folders and Naming`). The companion brief's maps follow this rule, which is why they render cleanly. This is worth knowing for any future Wardley maps: avoid hyphens, ampersands, and slashes in node names.

## Honest Risks

**Risk 1: The coordinate order is easy to get wrong.** `[visibility, evolution]` is the opposite of (x, y). Mitigation: the rule is flagged prominently; check every component's placement against intent; the companion maps follow it.

**Risk 2: Wardley support is beta (`wardley-beta`).** Beta syntax can change. Mitigation: grounded in the current official docs; revisit if Mermaid updates the syntax; the maps are simple enough to adjust.

**Risk 3: Maps can overclaim strategically.** A map that overstates our commoditisation or privacy could mislead. Mitigation: the privacy nuance is mapped honestly; the maps show what is real (encrypted, unseen data) not aspiration.
