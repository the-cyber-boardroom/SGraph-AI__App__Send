# Vaults Within Vaults: Opening And Creating Nested Vaults From A Parent Vault

**version** v0.27.60
**date** 24 May 2026
**from** Human (project lead)
**to** Vault team, Architect, Developer (lead), @Dev
**type** Dev brief

---

## What This Is

A brief for the vault team to add a missing feature: **support for opening, and even creating, other vaults from inside a vault.** The motivating need is a workflow where one vault must read the contents of other vaults (a parent or admin vault that reviews a set of per-user vaults), which is not possible today without this feature. The capability is generic and applies broadly: any workflow where vaults need to manage, read, or create other vaults benefits from it.

This is a focused, generic vault-team feature. It connects to the fractal vault-of-vaults direction (cross-ref: the vaults-of-vaults fractal-architecture work) and to the vault-per-user substrate (cross-ref: the SG/Send vaults-business-logic brief), making the nesting actually operable: not just vaults conceptually containing vaults, but a vault able to open and create the vaults nested within or referenced by it.

## The Missing Feature

Today a vault is a unit; there is no first-class way for one vault to open another vault from within it, or to create a new vault from inside an existing one. The feature to add:

| Capability | What It Does |
|------------|--------------|
| **Open a vault inside a vault** | From a parent vault, open and read a referenced (child) vault |
| **Create a vault inside a vault** | From a parent vault, create a new child vault |
| **Manage vaults within vaults** | The general pattern: a vault that manages a set of other vaults |

The core requirement is the read path: **a parent (or admin) vault must be able to read the contents of the other vaults it references.** Without this, a workflow where one vault aggregates or reviews many other vaults cannot be done seamlessly, because there is no way for the parent vault to reach into the child vaults.

## Why It Is Needed: Managing Vaults Within Vaults Seamlessly

The driving principle is the project lead's standing constraint: **we do not want to add backend complexity.** The voice memo: **"without that it's not possible to do this in a seamless way, because remember that we don't want to add backend complexity."**

If a workflow needs one vault to read or coordinate many others, there are two ways to do it: build bespoke backend machinery to aggregate across vaults (complexity we want to avoid), or give vaults the native ability to open and create nested vaults (the vault primitive doing the work). The second is the SG approach: the vault primitive carries the capability, so the workflow is just vaults using vaults, with no extra backend.

This is the operable form of the fractal vault-of-vaults idea (cross-ref: the vaults-of-vaults fractal-architecture work and the SG/Sentinel rule-architecture brief's fractal nesting): vaults conceptually nest, and this feature makes the nesting actionable, a parent vault can open the child vaults it contains or references, and create new ones. It also complements the vault-per-user substrate (cross-ref: the SG/Send vaults-business-logic brief): if each user has a vault, an admin or parent vault that can open those user vaults is exactly how a coordinating view over many user vaults is built without backend complexity.

## How It Fits The Vault Model

The feature should follow the existing vault model (cross-ref: the vault and key model in the authentication brief and the vault-discovery-and-public-keys work):

- **Opening a child vault** uses the child vault's key. The parent vault holds (or can obtain) the keys to the child vaults it manages, and uses them to open and read the children. This is consistent with vault-sharing-as-key-sharing (cross-ref: the authentication brief): a parent vault holding child keys is the same mechanism applied to nesting.
- **Creating a child vault** from a parent creates a new vault and records its reference (and key) in the parent, so the parent can subsequently open it.
- **The zero-knowledge boundary** is respected: opening a child vault requires its key; a parent can only read children it has the keys for. This keeps the nesting consistent with the platform's encryption model (a vault is only readable with its key).

So the feature is largely about making the key-and-reference plumbing work for nesting: a parent vault that holds references and keys to child vaults, with operations to open (read) and create them.

## What This Asks For

For the vault team:

1. **Add open-a-vault-from-within-a-vault** (a parent vault opens and reads a referenced child vault, using the child's key).
2. **Add create-a-vault-from-within-a-vault** (a parent vault creates a new child vault and records its reference and key).
3. **Support the manage-vaults-within-vaults pattern** (a parent/admin vault coordinating a set of child vaults).
4. **Keep it within the vault primitive** (no new backend aggregation machinery; the vault carries the capability).
5. **Respect the key and zero-knowledge model** (a parent reads only children it has keys for).

Estimated effort: this builds on the existing vault, key, and discovery model; the work is the nesting operations (open/create child, hold references and keys) rather than new infrastructure. It is a focused vault-team feature.

## What This Does Not Try To Be

- **Not backend aggregation machinery.** The vault primitive carries the capability; no new backend.
- **Not a breach of zero-knowledge.** A parent reads only children it holds keys for.
- **Not a specific application.** It is the generic nesting capability; the workflows that use it are separate.

## Honest Risks

**Risk 1: Nested vault access could complicate the key model.** A parent holding many child keys is more key management. Mitigation: it reuses the existing key and sharing model; the parent holds child keys the same way any keyholder does; no new key concept.

**Risk 2: Deep nesting could have performance or complexity costs.** Vaults within vaults within vaults could get heavy. Mitigation: the fractal model is bounded in practice; open children on demand; measure if deep nesting is used.

**Risk 3: A parent reading children must stay within the zero-knowledge model.** Mitigation: opening a child strictly requires its key; no backdoor read; the boundary is the key, as everywhere else.
