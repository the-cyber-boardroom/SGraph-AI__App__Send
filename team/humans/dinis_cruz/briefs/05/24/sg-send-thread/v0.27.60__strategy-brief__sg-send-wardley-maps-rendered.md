## What This Is

The companion to the Wardley-maps setup brief. That brief covered what Wardley maps are, the Mermaid capability, and how they apply to us; this one contains the maps themselves, as render-ready Mermaid `wardley-beta` source, each with a description of the story it tells. They are written to render in GitHub Markdown, mermaid.live, and the web-page-plus-Playwright screenshot workflow.

Each map follows the verified syntax (cross-ref: the setup brief), including the critical coordinate rule: coordinates are `[visibility, evolution]`, where visibility is the Y-axis (0.0 infrastructure to 1.0 user-facing) and evolution is the X-axis (0.0 genesis to 1.0 commodity). The `evolve` arrows show the strategic shift (the commoditisation move), and notes call out the insight.

A reminder on status (cross-ref: the setup brief): these maps have been rendered and visually verified (Mermaid CLI v11.14.0 plus the Playwright-bundled Chromium), and the rendered PNGs are provided alongside this brief. The source below is the corrected, verified version (see the setup brief's naming caveat: node names avoid hyphens, ampersands, and slashes, which break link parsing). The same source renders in GitHub Markdown and mermaid.live.

## Map 1: File Sharing Today vs SG/Send

The story: how sending files works today (email attachments, WeTransfer-style services) versus what SG/Send enables. Today the user-facing act of sharing depends on commodity transfer services that see the data; with SG/Send, sharing depends on client-side encryption and vaults, so privacy and security come for free. The evolve arrows show encryption and the vault moving toward commodity, which is the commoditisation of privacy.

```
wardley-beta
title File Sharing: Today
anchor User [0.95, 0.55]
component Share a File [0.82, 0.62]
component Transfer Service [0.62, 0.80]
component Provider Sees Data [0.45, 0.78]
component Storage [0.25, 0.82]
User -> Share a File
Share a File -> Transfer Service
Transfer Service -> Provider Sees Data
Transfer Service -> Storage
note "Today the provider can see your data" [0.40, 0.55]
```

```
wardley-beta
title File Sharing: With SG/Send
anchor User [0.95, 0.55]
component Share a File [0.82, 0.62]
component Vault [0.60, 0.45]
component Client Side Encryption [0.42, 0.55]
component Zero Knowledge Storage [0.25, 0.78]
component Privacy [0.50, 0.30]
component Security [0.38, 0.30]
User -> Share a File
Share a File -> Vault
Vault -> Client Side Encryption
Vault -> Zero Knowledge Storage
Share a File -> Privacy
Share a File -> Security
evolve Vault 0.80
evolve Client Side Encryption 0.82
evolve Privacy 0.85
evolve Security 0.85
note "We commoditise privacy and security: they just happen" [0.30, 0.42]
```

The contrast is the point: in the second map, privacy and security are components in the value chain that evolve to commodity, whereas in the first they are absent (the provider sees the data). Showing the two side by side is the classic before/after Wardley move.

## Map 2: The Privacy Story (Honest, Both Modes)

The story: SG/Send has a tracked free mode and a non-tracking paid mode (cross-ref: the SG/Send open-evaluation and identity-persistence-budgets briefs), but the honest nuance is that **even in the tracked free mode the data is still encrypted and unseen.** This map shows that the core privacy property (encrypted, unseen data) holds across both modes; only the activity tracking differs. It deliberately does not overclaim.

```
wardley-beta
title Privacy: Tracked Activity, Unseen Data
anchor User [0.95, 0.55]
component Use SG Send [0.85, 0.55]
component Activity Tracking [0.68, 0.50]
component Encrypted Data [0.50, 0.75]
component Data Stays Unseen [0.32, 0.72]
component Client Side Encryption [0.40, 0.62]
User -> Use SG Send
Use SG Send -> Activity Tracking
Use SG Send -> Encrypted Data
Encrypted Data -> Client Side Encryption
Encrypted Data -> Data Stays Unseen
evolve Encrypted Data 0.85
evolve Data Stays Unseen 0.82
note "Free mode tracks activity, never the data" [0.60, 0.30]
note "Paid mode removes tracking too" [0.44, 0.20]
```

The map makes the honest claim visible: activity tracking exists in the free mode (a component at mid-visibility), but the encrypted data and the data-stays-unseen property are the strong, evolving components. The notes state the truth precisely: free mode tracks activity but never the data; paid mode removes the tracking too.

## Map 3: The Investor Vault For Sensitive Information

The story: an investor needs to share confidential information (deal data, board information). Today they use email or WeTransfer, where the provider can see the data and there is no real control. With an SG/Send vault, the confidential sharing depends on the vault, client-side encryption, and dedicated ephemeral infrastructure (cross-ref: the SG/Send identity-persistence-budgets brief's confidential-data separation). The commoditisation arrow is on secure confidential sharing.

```
wardley-beta

component Share Deal and Board Info [0.84, 0.55]
component Vault for Sensitive Info [0.64, 0.42]
component Dedicated Ephemeral Instance [0.40, 0.40]
component Client Side Encryption [0.46, 0.60]
component Access Control [0.55, 0.48]
component Confidentiality [0.30, 0.28]
Investor -> Share Deal and Board Info
Share Deal and Board Info -> Vault for Sensitive Info
Vault for Sensitive Info -> Dedicated Ephemeral Instance
Vault for Sensitive Info -> Client Side Encryption
Vault for Sensitive Info -> Access Control
Share Deal and Board Info -> Confidentiality
evolve Vault for Sensitive Info 0.78
evolve Confidentiality 0.85
note "vs email/WeTransfer: provider sees everything" [0.70, 0.78]
note "We commoditise confidential sharing" [0.26, 0.42]
```

This is the highest-value commercial story (cross-ref: the SG/Send open-evaluation brief): the investor use case is concrete, the pain of email/WeTransfer for confidential data is real, and the vault-plus-ephemeral-instance answer is differentiated. The note contrasts with the status quo (provider sees everything).

## Map 4: Version Control As A Commodity

The story: version control today is complex and badly done for files (folders, inconsistent naming, no branches, no commits, no change tracking), and even existing solutions are either too granular or not usable. Our vaults make version control a commodity property of storing anything, because the vault has commits, branches, and history built in. The evolve arrow moves usable version control to commodity.

```
wardley-beta
title Version Control: Today vs Vaults
anchor User [0.95, 0.55]
component Track Changes [0.82, 0.40]
component Folders and Naming [0.60, 0.30]
component Manual Versioning [0.45, 0.22]
component Vault Version Control [0.58, 0.55]
component Commits and Branches [0.40, 0.60]
component History and Diff [0.30, 0.58]
User -> Track Changes
Track Changes -> Folders and Naming
Folders and Naming -> Manual Versioning
Track Changes -> Vault Version Control
Vault Version Control -> Commits and Branches
Vault Version Control -> History and Diff
evolve Vault Version Control 0.82
evolve Commits and Branches 0.80
evolve History and Diff 0.80
note "Today: folders, inconsistent naming, no branches" [0.55, 0.18]
note "Vaults make usable version control a commodity" [0.30, 0.42]
```

The map shows two paths from the same need (track changes): the painful, low-evolution status quo (folders, manual versioning) and the vault path (commits, branches, history) evolving to commodity. The point is that we make good version control just happen, where today it is complex and badly done.

Lots of little features, built on open source and client-side encryption, commoditising file sharing and (more importantly) the vault, which enables higher-order businesses on top. This is the innovate-leverage-commoditise pattern: commoditising the vault is what enables the apps layer above it.

## Map 7: Apps In The Vault

The story: the keystone consequence, mapped on its own. Because a vault can render a full-screen web page, adding a bit of HTML on top of a vault (with the HTML talking to the vault) creates a mini app. Once you have apps, a whole series of workflows and capabilities that were not possible before become possible. This map shows the apps layer emerging on top of the commoditised vault.

```
wardley-beta
title Apps in the Vault
anchor User [0.95, 0.55]
component Mini App [0.85, 0.40]
component HTML on the Vault [0.68, 0.45]
component The Vault [0.50, 0.78]
component New Workflows [0.80, 0.25]
component New Capabilities [0.75, 0.20]
User -> Mini App
Mini App -> HTML on the Vault
HTML on the Vault -> The Vault
Mini App -> New Workflows
Mini App -> New Capabilities
evolve The Vault 0.85
note "A vault plus a bit of HTML becomes a mini app" [0.55, 0.55]
note "Commoditised vault enables apps, then workflows" [0.40, 0.30]
```

This map makes the apps-in-the-vault point concrete: the vault is commodity (far right), the HTML-on-the-vault is the thin layer that turns it into a mini app, and the mini app enables new workflows and capabilities at the top (user-facing, novel). It is the clearest expression of once-you-commoditise-something-you-enable-what-sits-above, and a strong basis for an article (cross-ref: the articles-as-vaults and de-commoditising work).

## Using These Maps

Per the setup brief's workflow: these `wardley-beta` blocks render in GitHub Markdown directly, in mermaid.live, and via the web-page-plus-Playwright screenshot path for images. They are intended for the website, for articles, and for stakeholder conversations. They are version-controlled as code (and storable in a vault). If Mermaid's beta Wardley syntax changes, the maps are simple enough to adjust; the coordinates follow the verified `[visibility, evolution]` rule throughout.

A suggestion for refinement: Wardley maps reward iteration. The coordinates here are a considered first pass expressing the intended strategic positions; rendering them and adjusting the exact positions (so labels do not collide and the value chains read cleanly) is the natural next step, ideally in the render-and-screenshot workflow where the visual result is immediately visible.

## What This Does Not Try To Be

- **Not pre-rendered images.** Verified render-ready source; images via the workflow.
- **Not final coordinates.** A considered first pass; iterate from the rendered result.
- **Not the setup or syntax reference.** That is the companion setup brief.
- **Not overclaiming.** The privacy map shows the honest position.

## Honest Risks

**Risk 1: Coordinates may need visual refinement.** First-pass positions can have label collisions or awkward value chains. Mitigation: iterate from the rendered output; the workflow makes this fast; the positions express intent and are easy to adjust.

**Risk 2: Beta syntax could change.** Mitigation: grounded in current official docs; maps are simple to update.

**Risk 3: A map could imply more than is built.** Some components (agentic memory, apps) are directions more than shipped features. Mitigation: the maps express strategy and direction (which is what Wardley maps are for); pair them with honest status when presenting.
