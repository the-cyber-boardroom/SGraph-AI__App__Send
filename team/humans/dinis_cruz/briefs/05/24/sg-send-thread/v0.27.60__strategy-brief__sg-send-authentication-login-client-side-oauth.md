## What This Is

The brief on authentication and user login for SG/Send, which the project lead identified as the missing piece of the puzzle: **once users can log in, you can connect and map out the full user journey.** It develops how login should work (client-side OAuth via provider apps), the key question it raises (can we derive a unique secret from the provider to use as the vault key), the user-dedicated mode it enables (where the user's keys live), and vault sharing between users.

The core principles: keep it client-side (it works really well and avoids the complexity of mapping state across), support multiple providers, and use login to convert a user into a dedicated mode where their keys and vault information live.

These authentication flows are generic: they apply across many use cases, not just one, so this brief is written as a general capability. It builds on the identity-persistence-budgets brief (which established that logging in with a key changes capabilities and privacy, and the anonymous-to-live transition) and is foundational: it turns the anonymous-fingerprint users into authenticated users with persistent, accessible vaults.

## Client-Side OAuth Via Provider Apps

The login approach, grounded in the project lead's prior experiments: **client-side OAuth integration with provider apps, which works really well because the page is on our side, avoiding the complexity of mapping state across.**

The voice memo: **"I've already done some experiments, and it works really well with mini apps and Google experiments. I created a Google app that added the ability to access Google Photos, another to access the data store, another to log in. The interesting thing is to do it all client-side, which works really well, because we created the page we get on the other side, so there was no complexity of mapping this across."**

The client-side approach fits SG/Send because it matches the zero-knowledge, client-side-encryption stance: authentication happens in the client, the page is ours, and there is no server-side state to map across. The prior experiments (a Google app for Photos access, one for the data store, one for login) prove the pattern works.

### Multiple Providers

The voice memo wanted breadth: **add a bunch of authentication providers to the website.** Google is the proven one; the voice memo also noted Cloudflare has authentication solutions worth trying. The principle is to offer several login options, each integrated client-side:

| Provider | Status |
|----------|--------|
| **Google** | Proven in prior experiments (login, Photos, data store) |
| **Cloudflare** | Noted as having authentication solutions worth adding |
| **Others** | The principle is multiple options; add over time |

The brief does not fix a final provider list; the direction is multiple client-side login options, starting with Google and adding others as they are evaluated.

## The Key Question: A Provider-Derived Vault Key

The most important technical question, which determines the architecture: **do we get a unique secret from the provider, unique to us, that we can use as the vault key? Or is there a place, unique per app, where we can store data at the least-controversial privilege?**

The voice memo: **"do we get any unique secret that is unique to us from them that we can use as the vault key? Or is there a place, like Google's app space, which is a space within the app to store, unique per app, that we can use to store data, the least-controversial privilege we can ask from Google?"**

Two related possibilities, materially different as designs.

### Option A: A Provider Secret As The Vault Key (Derivation)

Derive the vault key from a secret the provider gives us that is unique to our app for this user. On login, obtain the secret, derive the key, unlock the vault. The user manages no key; login reconstitutes it.

Considerations (why this is delicate):

- **Stability**: the secret must be identical across every login, forever. If the provider rotates it, the derived key changes and the user is locked out of their vault permanently. The dominant risk.
- **Uniqueness and secrecy**: unique per user, never exposed.
- **Zero-knowledge tension**: if we can see the secret, we can derive the key and could in principle decrypt the vault. Derivation must happen fully client-side, the secret never reaching our servers.
- **Provider-specific**: each provider exposes different identifiers; evaluate per provider before reliance.

### Option B: Per-App Least-Privilege Storage (Store The Keys), The Preferred Starting Point

Store the user's SG/Send keys in the provider's per-app storage at least privilege, rather than deriving them.

The verified Google mechanism is the Drive appDataFolder: a per-app configuration folder; only the app that created the data can access it; it uses the non-sensitive `drive.appdata` scope (the least-privilege, least-controversial request). We store the user's vault keys there; on login we read them back; the keys live in the user's own Google account.

Advantages over derivation:

- **No lock-out from secret rotation**: keys are stored, not derived from a changeable secret.
- **Zero-knowledge preserved more cleanly**: keys are in the user's account; read client-side; we do not hold them.
- **Least privilege**: the non-sensitive `drive.appdata` scope is the minimum, and only our app can read what we wrote.
- **User-controlled**: deleting the app data (or uninstalling the app) removes it, a clean revocation path.

The residual consideration: the keys sit in the user's Google account, so security depends on the user's account security and on our client-side handling never leaking the keys.

**Recommendation:** start with Option B (per-app least-privilege storage, Google appDataFolder), because it avoids the lock-out risk and preserves zero-knowledge more cleanly. Treat Option A (derivation) as a research question to evaluate per provider, not a v1 mechanism. Do not ship a derivation scheme until the secret's stability and the client-side-only handling are proven.

## The User-Dedicated Mode

What login enables: **a user-dedicated mode, where the logged-in user's keys and vault information are stored, and through which they access their vaults.**

The voice memo: **"the logic is you log in, and we convert the user to that mode. That could be one of the modes where we store the user's keys, the OpenRouter key, more information about the vaults they use. We need to add a user-dedicated mode, meaning when you log in, you can access the vaults in there."**

The user-dedicated mode is the authenticated counterpart to the anonymous-fingerprint identity (cross-ref: the identity-persistence-budgets brief). It is where the user's persistent state lives, stored in the provider per-app storage:

| Stored In The User-Dedicated Mode | Purpose |
|-----------------------------------|---------|
| **Vault keys** | The keys to the user's vaults (the most sensitive item) |
| **OpenRouter key** | The user's own LLM API key (their agentic/LLM usage runs on their key) |
| **Vault information** | Which vaults they use, metadata |

Because these include the vault keys and a billable LLM key, the storage and client-side handling must be hardened (no logging, no transit to our servers, client-side-only use).

This connects to the budget and capability model (cross-ref: the identity-persistence-budgets brief): logging in moves a user from the anonymous, fingerprint-identified, budgeted state into a dedicated state with persistent keys and vault access. It is the anonymous-to-live transition (the e-commerce pattern) made concrete.

The OpenRouter-key point is notable: storing the user's own LLM key means their agentic and LLM-powered usage runs on their key, which is both a cost model (they pay for their own LLM usage; cross-ref: the cost-attribution and budget work) and a privacy property (their LLM usage is theirs).

## Logging In Gives Access To Your Vaults

The payoff: **when you log in, you can access your vaults.** The keys stored in the dedicated mode (or derived from the provider) unlock the user's vaults, so logging in reconstitutes their access. This makes SG/Send usable as a persistent personal tool, not only an ephemeral transfer service (cross-ref: the identity-persistence-budgets brief's ephemeral-by-default public shares): a logged-in user has durable access to their own vaults, distinct from the ephemeral public free-tier shares.

This is where the persistence tiers connect (cross-ref: the identity-persistence-budgets brief): the public free shares are ephemeral, but a logged-in user with their own vaults (and, for the paid tiers, persistent or ephemeral-EC2 vaults) has the durable, accessible storage that login unlocks.

## Vault Sharing Between Users

A capability login makes tractable: **sharing vaults is a case of sharing or sending the user the vault key, which they enter in their system.**

The voice memo: **"we need to look at how to share vaults within users, but that should just be a case of sharing or sending the user the vault key, and then they can enter it in their system, so it probably cannot be that complicated."**

Because a vault is unlocked by its key, sharing a vault is sharing its key: send the recipient the vault key, they enter it, they have access. This fits the client-side, key-based architecture: no server-side access-control mapping, just the key. It connects to the per-deployment PKI and key-sharing work (cross-ref: the SG/Sentinel deployment-modes brief; the vault-discovery-and-public-keys work): the shared key should be encrypted to the recipient's public key so only they can use it, and revocation must be designed (sharing a raw key has no revocation). The v1 mechanism (share the key) is simple; secure delivery and revocation are follow-on.

## Why This Is The Missing Piece: Completing The User Journey

The voice memo framed authentication as the missing piece: **once you have login, you literally have a way to connect and map out the user journey, which would be really powerful.**

The user journey, now completable:

1. **Arrive** (anonymous, fingerprint identity, a budget; cross-ref: the identity-persistence-budgets brief).
2. **Try** (the free/non-private mode, ephemeral shares; cross-ref: the open-evaluation brief).
3. **Log in** (client-side OAuth) and convert to the user-dedicated mode.
4. **Access your vaults** (keys from provider per-app storage or derived from the provider secret).
5. **Persist and share** (durable vaults; share by sending the vault key).
6. **Upgrade** (paid/non-tracking, persistent or ephemeral-EC2 vaults; privacy as a feature; cross-ref: the open-evaluation and identity-persistence-budgets briefs).

Authentication is the hinge between the anonymous-evaluation experience and the persistent-authenticated experience: without it, users can only evaluate (ephemeral, anonymous); with it, they become persistent users with their own accessible, shareable vaults. This connects the open-evaluation funnel to a durable user relationship, completing the journey from anonymous trial to logged-in, paying, vault-owning user.

## What This Asks For

1. **Build client-side OAuth login** (the proven Google integration first; the page on our side; no cross-mapping complexity).
2. **Add multiple providers** (Google first; evaluate Cloudflare and others).
3. **Build Option B first** (Google appDataFolder, `drive.appdata` scope) as the key-storage mechanism.
4. **Evaluate Option A per provider** as research; do not ship until stability and client-side-only handling are proven.
5. **Build the user-dedicated mode** (store vault keys, the OpenRouter key, vault information; harden the handling).
6. **Make login give access to the user's vaults** (keys reconstitute access).
7. **Design secure vault-key sharing** (PKI-encrypted delivery, revocation) before exposing sharing.
8. **Map the complete user journey** (anonymous to logged-in to paying to vault-owning).
9. **Security review** of the whole client-side auth and key-handling flow before launch.

Estimated effort: the client-side Google OAuth and appDataFolder integration is proven in prior experiments and is the near-term build; the provider-derived-key evaluation is per-provider research; the user-dedicated mode builds on the identity and vault work; vault sharing has a clear mechanism with follow-on secure-delivery details.

## What This Does Not Try To Be

- **Not server-side auth.** Deliberately client-side, matching the zero-knowledge stance.
- **Not a single provider.** Multiple client-side login options, Google first.
- **Not a finished vault-sharing design.** The mechanism (share the key) is clear; secure delivery and revocation are follow-on.
- **Not a replacement for the anonymous identity.** It is the authenticated counterpart; anonymous fingerprint identity remains for evaluation.

## Honest Risks

**Risk 1: Deriving a vault key from a provider secret is delicate.** The secret must be stable, unique, not exposed, and appropriate as a key. Mitigation: evaluate per provider; the per-app-storage approach (Option B) is safer; do not ship a key-derivation that could lock users out if the secret changes.

**Risk 2: Provider dependency.** Relying on Google or Cloudflare creates a dependency. Mitigation: multiple providers; the keys are the user's (in their account); a path to not depend on any single provider; the client-side approach keeps us thin.

**Risk 3: Vault sharing by key has key-management implications.** Sharing a key means the recipient holds it indefinitely (no easy revocation). Mitigation: secure delivery via PKI; follow-on work on revocation and multi-user vaults; key-sharing is the v1 mechanism.

**Risk 4: Client-side OAuth and key handling must be secure.** Mitigation: least-privilege scopes (the non-sensitive appDataFolder scope); no logging or server transit of keys; the prior experiments inform secure implementation; security review before launch.
