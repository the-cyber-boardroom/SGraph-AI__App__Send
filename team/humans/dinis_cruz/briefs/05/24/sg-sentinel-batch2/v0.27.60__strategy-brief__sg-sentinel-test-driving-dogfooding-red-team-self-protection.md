## What This Is

The first brief of the SG/Sentinel implementation batch (batch 2), written as the build begins. It captures three ideas about **test-driving SG/Sentinel** that emerged once the design corpus was complete and attention turned to validating it in practice: dogfooding via deliberately locked-down development and QA environments, an agentic red-team and bug-bounty programme that actively tries to break it, and the concrete self-protection deployment topologies.

These build on the day-68 design corpus without repeating it. The design briefs established *what* SG/Sentinel is and *how* it should behave; this brief is about *how we exercise it hard in practice* as we implement, to generate the scenarios, organic traffic, and adversarial pressure that turn a design into a proven system.

Three threads, each genuinely new relative to the design corpus:

- **Dogfooding via locked-down environments**: our own dev and QA become aggressive test beds, with prod deliberately more relaxed than dev/QA.
- **Agentic red-teaming**: agents whose job is to break SG/Sentinel, plus a bug-bounty leaderboard with public stats.
- **Self-protection topologies**: the concrete deployment shapes where SG/Sentinel protects SG/Sentinel, SG/Edge, and bare-EC2 SG Vault instances.

A note on scope: where the day-68 corpus already covered something (Sentinel-protects-Sentinel as a principle, enable/disable rules, visibility-as-the-real-value), this brief does not restate it; it extends it into concrete implementation practice and flags the cross-reference.

## Thread 1: Dogfooding Via Locked-Down Environments

The first test-drive strategy: **use our own development and QA environments as aggressive SG/Sentinel test beds, locked down far harder than a normal environment would be.**

The insight is that our dev environment is the perfect place to run an aggressive rule set, because we control exactly who should reach it. The voice memo's examples: lock the dev environment down to only Europe, only the UK, only London, or even only the project lead's single IP address. The QA environment, similarly, might be reachable only by the QA scripts and nothing else.

This is dogfooding with teeth. Rather than testing SG/Sentinel against synthetic traffic, we run it in front of our real environments with rule sets so aggressive that any unexpected access is blocked, and we learn from what happens.

| Environment | Lock-Down Example | What It Tests |
|-------------|-------------------|---------------|
| **Dev** | Only the project lead's IP, or only London/UK/Europe | Geographic and IP allowlisting; aggressive rule sets; PKI experiments |
| **QA** | Only the QA scripts can reach it | Programmatic-only access; the no-invalid-request principle against a known, tiny valid set |
| **Multiple projects** | Per-project rule sets, enabled/disabled on demand | Rule-set variation; the enable/disable mechanism (cross-ref: the interactivity brief) at real scale |

The enable/disable-rules-on-demand mechanism (already designed in the day-68 interactivity brief) gets its first real workout here: we can flip rule sets on dev and QA quickly, experiment, and observe. This brief does not redesign that mechanism; it exercises it.

### The Deliberate Inversion: Prod More Relaxed Than Dev/QA

A genuinely counterintuitive point the voice memo made, and one worth stating clearly because it inverts the usual assumption: **prod may end up more relaxed than dev and QA, and that is fine.**

The usual assumption is that production is the most locked-down environment. But for test-driving, the inversion makes sense:

- **Dev and QA are where we test-drive aggressively.** We want them brutally locked down to exercise the rules, experiment with PKI, and generate scenarios.
- **Prod serves real, varied, legitimate users.** It cannot be locked to one IP or one region; it must be relatively open to its actual user base.

So during the test-drive phase, dev and QA carry the most aggressive rule sets (because we control exactly who should reach them), while prod carries the rule set appropriate to a real user base (necessarily more permissive on geography and IP). The voice memo: **"you can be in a situation where prod actually has more relaxed environments than dev and QA, which is okay, because the point is to test-drive the whole solution and have all these variations."**

This is a test-drive stance, not a permanent posture. It is how we exercise the full range of rule behaviours: the locked-down extremes on dev/QA, the realistic middle on prod.

### Dev Environments Deserve Protection Anyway

A secondary point that strengthens the case: **dev environments often run more vulnerable code than prod, so protecting them is valuable in its own right.**

The voice memo: **"dev environment might actually have more vulnerable code and code that is quite problematic, so it makes sense that it is also protected."** Dev code is work-in-progress: less hardened, more experimental, more likely to have the kind of bug (the runaway-redirect class from the principles brief) that SG/Sentinel guards against. Putting SG/Sentinel in front of dev is not just a test-drive; it protects genuinely riskier code.

This is also where PKI authorisation and other identification capabilities get their first experiments: a locked-down dev environment, reachable only by known parties, is the natural place to trial PKI and stronger identification before they reach prod.

## Thread 2: Agentic Red-Teaming And The Bug-Bounty Leaderboard

The second test-drive strategy, and the most distinctive: **fire up agents whose job is to break SG/Sentinel, run agentic pen-tests on demand, and run a bug-bounty programme with a public leaderboard.**

This is the adversarial complement to dogfooding. Dogfooding generates organic legitimate traffic; agentic red-teaming generates organic hostile traffic, from attackers we control and can learn from.

The voice memo: **"we should start to create an attack-minded, almost like pen-testing on demand and agentic pen-tests, and even for bug bounty. We should say, can you attack this? Fire up some agents whose job is to break this, so we create our own mini pen-testing team that is actually trying to break all this."**

The components:

| Component | What It Does |
|-----------|--------------|
| **Agentic pen-testing** | Agents whose objective is to break SG/Sentinel; on-demand red-team runs |
| **A mini pen-testing team** | A standing set of attack agents, continuously probing |
| **Bug bounty** | External researchers invited to break it |
| **A leaderboard** | Public stats: who got through, what they found, what is happening on the servers |

The leaderboard is the distinctive twist. The voice memo: **"on the bug bounty, we should have a leaderboard, and it would be cool to show some stats on what's happening with our servers and who has gone through and what."** A public leaderboard turns red-teaming into a visible, competitive, motivating exercise, and the stats themselves demonstrate the platform's visibility (Thread 3 below) in action.

### The Objective: Block Them As Fast As Possible

Critically, the red-team is not just to find holes; it is to exercise the core objective. The voice memo tied it back: **"the point here is that we should be blocking them as fast as possible, because part of our objective is to make the site as hostile as possible to bad traffic."**

So the agentic red-team serves two purposes at once:

1. **Find gaps** (the conventional pen-test value): where does SG/Sentinel fail to block what it should?
2. **Exercise the detect-before-damage and make-hostile objectives** (cross-ref: the time brief, the principles brief): how fast does SG/Sentinel block the red-team? Does it catch them before damage? Does the async detection (the time brief's window) work against real adversarial agents?

The agentic red-team is the live test of the detect-before-damage success metric (damage prevented, not requests blocked) from the time brief. The red-team agents are the simulated attackers from the tabletop, now made real and adversarial. Where the tabletop simulated attacks on paper, the red-team runs them against the implementation, and the gaps the tabletop surfaced (fast-track bypass, per-IP evasion, in-profile exploits) get tested for real.

This connects the implementation back to the validation: **the tabletop found gaps on paper; the agentic red-team finds them in running code.** It is the natural next step after the tabletop, and it should specifically probe the tabletop's known gaps.

### An Aggressive Rule Set As The Test Subject

Both threads share a requirement the voice memo named: **an aggressive rule set is what makes the test-drive meaningful.** We want aggressive rules on dev, QA, and across multiple projects, both to lock down the dogfood environments and to give the red-team something hard to break. The aggressive rule set is the test subject; dogfooding and red-teaming are how we exercise it.

## Thread 3: Self-Protection Topologies

The third thread makes concrete a principle the day-68 addendum named (Observation 3: Sentinel must guard its own control plane) and extends it into specific deployment shapes. This is implementation-concrete rather than principle-level, so it is new material.

The voice memo: **"I really like this concept of Sentinel protecting Sentinel and protecting Sentinels."** Three concrete topologies emerge.

### Topology 1: An Independent Sentinel Guards The Admin Interface

The admin interface (the two-way conversation API from the MVP brief) is a high-value target. The concrete topology: **an independent, lightweight SG/Sentinel instance guards the admin interface**, separate from the main Sentinel it administers.

The voice memo: **"the admin interface gets protected by an independent SG/Sentinel, because we should be able to have very lightweight implementations, especially for very specific rules."** The point about lightness matters: guarding an admin interface needs only very specific rules (a tiny known-good set: who may administer, from where, doing what), so **Layer 1 alone, or a light Layer 2, may be entirely sufficient**.

The voice memo: **"maybe even Layer 1, or the light Layer 2, might be very effective for an admin interface, because by then it's very specific rules, very specific things that we're locking down."** This is the art-of-the-possible reduction (cross-ref: the rule-architecture brief) at its strongest: an admin interface has a tiny valid space, so a tiny rule set guards it, so a lightweight Sentinel suffices. The independent instance means a compromise of the main Sentinel does not compromise its guard, and vice versa.

### Topology 2: Sentinel Protects SG/Edge

SG/Sentinel protecting SG/Edge is one implementation of the general pattern (SG/Edge is the compute layer; SG/Sentinel is the guard in front). This is the canonical deployment and is already implied by the day-68 architecture; the new emphasis is that **SG/Edge is just one of several things Sentinel protects, not the only one.**

### Topology 3: Sentinel Protects Bare-EC2 SG Vault (The Concrete New Risk)

The most important new point, because it identifies a concrete risk surface the design corpus had not addressed: **we already deploy ephemeral SG Vault instances on bare AWS EC2, not behind CloudFront.**

The voice memo flagged this directly: **"we already deploy ephemeral versions of SG Vault on bare AWS EC2 instances. We're going to be publishing raw EC2 instances that are not even behind CloudFront, and that can be quite problematic."**

This is a real gap between the design and the reality. The day-68 design assumed CloudFront-first (Layer 1 = CloudFront Functions, Layer 2 = Lambda@Edge). But the ephemeral-vault provisioning (from the day-66 on-demand-provisioning work) puts raw EC2 instances directly on the internet, with no CloudFront in front. Those instances need protection too, and the CloudFront-based layers do not apply to them.

The implication: **SG/Sentinel needs a deployment mode that runs directly on or in front of a bare EC2 instance, not via CloudFront.** This is exactly the substrate-independence principle (cross-ref: the principles brief) made urgent by a concrete deployment reality. The voice memo's framing: **"Sentinel protects SG/Edge, which is one implementation, but also protects SG Vault directly, and the other stuff we do."**

This is where the reverse-proxy form factor matters:

### The Reverse-Proxy Form Factor

The voice memo named a form factor that addresses the bare-EC2 case: **a lightweight reverse proxy you can put on top of any instance.**

The voice memo: **"if we get this right, this could be quite a cool little reverse proxy that you can put on top."** A reverse-proxy form factor is the substrate-independent answer: the same SG/Sentinel rule engine, packaged as a reverse proxy that runs on or in front of a bare EC2 instance, protecting it the way CloudFront Functions protect a CloudFront distribution.

This is substrate-independence (cross-ref: the principles brief, Principle 1) realised concretely: the rule engine is the same; the deployment form factor varies (CloudFront Function, Lambda@Edge, or a reverse proxy on bare EC2). The bare-EC2 reality makes the reverse-proxy form factor a near-term need, not a future nicety, because we are already publishing raw instances.

## Over-Indexing On Visibility (Extending, Not Repeating)

The voice memo returned to a theme the day-68 corpus already established (the MVP brief and developer-friendliness brief both make visibility central), but with a sharpened framing worth capturing as an emphasis for the implementation: **we should over-index on visibility, because the blocking of bad traffic is almost a side effect of the value visibility provides.**

The day-68 corpus established that visibility matters. The new emphasis for the implementation phase: **visibility is the primary value; blocking is the side effect.** The voice memo: **"the fact that this can protect bad traffic is a side effect of the fact that this adds a crazy amount of value and acceleration and understanding and even optimisation, about how many requests are hitting the server, what's been optimised, what's been cached, what the clients actually see."**

For the implementation, this is a prioritisation signal (it does not need a new design): **build and surface the visibility first and richly, because it delivers value immediately (debugging, optimisation, understanding) even before the blocking is mature.** The bug-finding value (cross-ref: the developer-friendliness brief, the debugging goals in the MVP brief) is the immediate payoff; the security value compounds over time. This reinforces the path-to-MVP sequencing (visibility first), so it is an emphasis, not a new direction.

## What This Asks For

Concrete next steps for the implementation:

1. **Lock down dev and QA aggressively** (IP/geo allowlists; QA reachable only by QA scripts) as the first dogfood test beds.
2. **Accept the prod-more-relaxed inversion** during test-driving; document it as a test-drive stance, not a permanent posture.
3. **Use the dev environment for PKI and identification experiments** (it is locked-down and runs riskier code).
4. **Build the agentic red-team** (agents whose job is to break SG/Sentinel; on-demand pen-tests).
5. **Specifically probe the tabletop's known gaps** with the red-team (fast-track bypass, per-IP evasion, in-profile exploits).
6. **Build the bug-bounty leaderboard** with public stats (who got through, what is happening on the servers).
7. **Build the independent lightweight Sentinel for the admin interface** (Layer 1 or light Layer 2; a tiny rule set).
8. **Build the reverse-proxy form factor** for bare-EC2 SG Vault protection (the substrate-independent deployment mode).
9. **Prioritise visibility in the MVP build** (it delivers value before blocking matures).

Estimated effort: the dogfooding lock-down is quick (rule sets on existing environments); the agentic red-team and leaderboard are a focused build; the reverse-proxy form factor is the most substantial (a new deployment mode), but it is needed because bare-EC2 instances are already live.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a redesign of the day-68 work.** It extends it into practice.
- **Not a permanent prod-relaxed posture.** The inversion is a test-drive stance.
- **Not a replacement for external pen-testing.** The agentic red-team complements, not replaces, real security review.
- **Not the full reverse-proxy product yet.** The form factor is needed for bare EC2; productising it is later.
- **Not a new visibility design.** It is an emphasis on the existing visibility work.

## Honest Risks

Three risks:

**Risk 1: The prod-more-relaxed inversion could be misread as prod being insecure.** Mitigation: it is a test-drive stance; prod's rule set is appropriate to its real user base, not absent; document the distinction clearly.

**Risk 2: The agentic red-team could cause real damage if it finds a real hole.** Mitigation: run it against dev/QA and dedicated targets first; the whole point is to find holes before real attackers; contain the red-team's blast radius.

**Risk 3: The bare-EC2 reverse proxy is a new deployment mode with its own attack surface.** Mitigation: it runs the same proven rule engine; start with the lightweight Layer-1-equivalent rules; the art-of-the-possible reduction keeps the bare-EC2 valid space small.
