## What This Is

The ninth brief of the SG/Sentinel implementation batch, capturing one of the project lead's favourite areas: **resilience and graceful degradation, expressed as the Minimal Viable Application.** The core idea is that you should never have to take a whole application offline because one part has a bug, a vulnerability, or a catastrophic failure; instead, you take off the affected parts and keep a working solution running. SG/Sentinel makes this possible because the application and SG/Sentinel can talk to each other, so the app can say "I'm overloaded," "this feature is down," "don't send me traffic right now," and SG/Sentinel can act on it.

Three linked ideas:

- **The Minimal Viable Application (MVA)**: what parts of the application can be taken off while still leaving a working solution, drilled regularly so we know how the system degrades.
- **SGS-in-sequence resilience**: a chain of SG/Sentinels, each doing one thing more carefully than the last, with a simple baseline that must never go down.
- **Feature flags as rules**: SG/Sentinel as the place to enforce feature flags, because a feature flag is fundamentally a rule that enables certain traffic or activities.

This is genuinely new relative to the corpus. The path-to-MVP brief flagged "failure modes and resilience" as a memo worth recording; this brief is that development, and it goes further into the MVA concept and feature flags. It builds on the two-way conversation (the MVP brief) and the Sentinel-protects-Sentinel idea (the test-driving brief and the addendum) without repeating them.

## The Minimal Viable Application

The central concept: **the Minimal Viable Application is the set of parts you can keep running while taking others off, so that a bug, vulnerability, or failure in one part does not require taking the whole app offline.**

The voice memo: **"what parts of the application can we still take off so that you still have a working solution? You could have bugs on particular parts, catastrophic failures, massive vulnerabilities on certain parts. The logic should be that I shouldn't have to take the whole app offline."**

This inverts the usual binary (the app is up, or the app is down). Instead, the app has a graceful-degradation spectrum: full functionality at the top, the minimal viable core at the bottom, and many intermediate states where some parts are off but a working solution remains. The MVA is the floor: the smallest set of parts that still constitutes a usable application.

The reasons a part might be taken off:

| Reason | Response |
|--------|----------|
| A bug in a part | Take that part off; keep the rest running |
| A vulnerability discovered in a part | Disable the vulnerable part; investigate; keep the rest |
| A catastrophic failure of a part | Degrade to the parts that still work |
| Malicious traffic reaching a part it should not | Shut that part down; require investigation |
| A part overloaded | Shed load from that part; protect the rest |

### Drill It Regularly

A practice the voice memo insisted on: **drill the degradation regularly, taking parts of the app offline (especially in dev and QA) to understand how the system reacts.**

The voice memo: **"this is a scenario we need to practise. We need to drill it. Every day we should take parts of the app offline, especially on dev and QA, because we need to understand how every system reacts to that, how every part handles it."**

This is chaos engineering applied to graceful degradation (cross-ref: the surrogate-dependencies brief, which provides the chaos-simulation mechanism). Regularly taking parts offline in dev and QA proves that the MVA actually works: that the system degrades gracefully rather than collapsing when a part is removed. You do not discover your degradation behaviour during a real incident; you drill it daily so you know it cold.

## The Two-Way Conversation Enables Graceful Degradation

The mechanism that makes the MVA possible: **the application and SG/Sentinel talk to each other, so the app can tell SG/Sentinel its current state, and SG/Sentinel can route accordingly.** This is the two-way conversation (cross-ref: the MVP brief's two-way conversation API, the embedded-model brief's communication module and header signalling) applied to resilience.

The voice memo: **"now we have a two-way way to talk from the application through the SGS, from one module to the other. It is going to be possible for an app to start saying things like 'hold on, I'm overloaded,' or 'this feature is now down,' or 'we just removed this feature toggle,' or 'we don't have this capability.'"**

The messages the app can send to SG/Sentinel:

| App Says | SG/Sentinel Does |
|----------|------------------|
| "I'm overloaded" | Shed or slow traffic to that part |
| "This feature is now down" | Stop routing requests for that feature |
| "We removed this feature toggle" | Block traffic that the toggle would have enabled |
| "I don't have this capability" | Return appropriately; do not forward |
| "Don't send me more traffic right now" | Hold or redirect traffic |

This makes SG/Sentinel an intelligent traffic manager that knows the real-time state of the application, not just a static router. The voice memo called this **"an intelligent ALB"** (application load balancer): **"the point is that we know what's going on with the application, so we can implement much more interesting workflows."** A normal load balancer routes blindly; an intelligent ALB that knows each part's real-time health and capability can route around failures, shed load intelligently, and degrade gracefully, because the app is telling it what is happening.

## Shutting Down Compromised Parts Automatically

A security application of the same mechanism, and a powerful one: **if SG/Sentinel detects malicious traffic reaching a part of the application it should not, it can shut that part down and require investigation.**

The voice memo: **"as we introduce more reactive behaviours, if we detect that malicious traffic has reached a part of the application that it shouldn't, we should shut that down and then require further investigation."**

This is the reactive complement to the MVA: not just degrading when a part fails, but proactively isolating a part when it shows signs of compromise. If malicious traffic reaches somewhere it should not (a strong signal something is wrong, cross-ref: the no-404s-at-the-API-layer signal in the delegation brief, and the control-flow-graph hyper-jump detection in the control-flow-graphs brief), SG/Sentinel takes that part offline and flags it for investigation, containing the blast radius while the rest of the app keeps running.

This depends on the two-way conversation (to shut the part down) and the detection (to know the part is compromised), and it delivers a containment capability most architectures lack: automatic, targeted isolation of a compromised component without taking the whole system down. **The MVA is what makes aggressive isolation safe: you can shut down a suspect part precisely because the app keeps working without it.**

## SGS-In-Sequence Resilience

The voice memo applied the same degradation thinking to SG/Sentinel itself, extending the Sentinel-protects-Sentinel idea (cross-ref: the test-driving brief, the addendum's Observation 3) into a resilience architecture: **a chain of SG/Sentinels in sequence, each doing one thing more carefully than the last, with a simple baseline that must never go down.**

The voice memo: **"I like the idea of SGS protecting SGS in more robust applications. You could have three or four SGS in sequence, each one does one thing harder or looks at things more carefully than the other. If there was a bug on this part here, we can turn it all off, but we can't turn off the main SGS."**

The model:

| SGS In Sequence | Role | Can It Be Turned Off? |
|-----------------|------|----------------------|
| **The baseline SGS** | The simplest, most robust; the minimum to be live | No: without this we should not be live |
| **Additional SGS layers** | Each adds more careful, harder analysis | Yes: if one has a bug, turn it off, keep the baseline |

This is the MVA applied to SG/Sentinel's own stack: the baseline SGS is SG/Sentinel's minimal viable core (the simple, robust layer that must always run), and the additional layers are the parts you can take off if they have a problem. The voice memo's framing: **"this is the baseline; without this baseline we should not be live."**

This is why simplicity matters so much for the core (cross-ref: the rules-engine brief's tiny high-privilege core, the portable-spec brief's smallest-possible implementation): **the baseline SGS must be simple enough to be trustworthy, because it is the one thing that cannot be turned off.** The voice memo accepted the residual risk honestly: **"if SGS is completely down, then the whole thing is down, and that's an okay risk, which is why it needs to be as simple as possible in some of its elements."** The baseline is the single point whose failure means the app is down, so it is kept minimal and robust; everything more sophisticated is degradable.

This connects to the layered execution model (cross-ref: the execution-model brief): the layers (1, 2, 3) already form a sequence of increasing capability. The SGS-in-sequence resilience model adds the degradation property: the more sophisticated layers can be shed under fault, falling back to the simple, robust baseline, without going fully offline.

## Feature Flags As Rules

The third linked idea, which the voice memo flagged as a potential killer feature: **SG/Sentinel as the place to enforce feature flags, because a feature flag is fundamentally a rule.**

The voice memo: **"feature flags could be a nice killer feature for SG/Sentinel, because SG/Sentinel could be the place to enforce feature flags. A feature flag fundamentally is the one that enables certain features, and how does enabling a feature look? It looks like a rule. A rule that allows certain traffic, certain activities, certain things to be invoked is a great place to put a feature flag."**

This is an elegant unification. A feature flag and a SG/Sentinel rule are mechanically the same thing: both enable or disable certain traffic, activities, or capabilities. So:

| Feature Flag Concept | SG/Sentinel Equivalent |
|----------------------|------------------------|
| A flag enabling a feature | A rule allowing that feature's traffic/activities |
| Turning a flag off | Disabling the rule |
| A gradual rollout | A rule scoped to a subset (fingerprint, region) |
| A kill switch | Disabling the rule immediately |

Because SG/Sentinel already has the rule machinery (the fractal rule graph, enable/disable on demand, per-rule scoping, version control), it is a natural feature-flag enforcement point. The voice memo's insight is that feature flags are not a separate system to build; they are an application of the rules SG/Sentinel already runs.

This ties directly back to the MVA and graceful degradation: **feature flags are how you take parts of the app off.** When the app says "we removed this feature toggle" (the two-way conversation), that is a feature-flag rule being disabled, which takes that feature's traffic off. The MVA degradation and the feature-flag enforcement are the same mechanism: enabling and disabling rules that govern what parts of the app are reachable. Feature flags are the controlled, intentional version of degradation; the reactive shutdowns (compromised parts) are the automatic version. Both are rules being toggled.

This is a strong product angle (a killer feature, per the voice memo): SG/Sentinel offers feature-flag management as a native capability, integrated with security, traffic management, and resilience, because all of them are the same rule machinery. A team adopting SG/Sentinel for feature flags is adopting it for security too, and vice versa: the acid test (cross-ref: the UX brief) reached through the feature-flag door.

## What This Asks For

Concrete next steps:

1. **Define the Minimal Viable Application** (the minimal set of parts that still constitutes a working solution).
2. **Build the app-to-SGS state conversation** (overloaded, feature down, don't-send-traffic), on the comms module.
3. **Make SG/Sentinel an intelligent ALB** (route on real-time app state, not blindly).
4. **Drill degradation regularly** (take parts offline daily in dev/QA via the chaos mechanism).
5. **Build automatic isolation of compromised parts** (detect malicious traffic where it should not be; shut down; require investigation).
6. **Build the SGS-in-sequence resilience model** (a simple robust baseline that never goes down; degradable layers above it).
7. **Keep the baseline SGS minimal and robust** (it is the one thing that cannot be turned off).
8. **Build feature flags as rules** (SG/Sentinel as the feature-flag enforcement point).
9. **Connect feature flags to MVA degradation** (toggling a feature flag is taking a part off).

Estimated effort: the MVA and intelligent-ALB build on the two-way conversation (so they follow the comms-module work); the SGS-in-sequence model builds on the self-protection topologies; feature-flags-as-rules is a relatively quick application of the existing rule machinery and is an attractive early product feature.

## What This Does Not Try To Be

- **Not a guarantee against total outage.** If the baseline SGS is down, the app is down; that residual risk is accepted and mitigated by keeping the baseline minimal and robust.
- **Not a replacement for app-level resilience.** It adds edge-coordinated degradation; the app still needs its own resilience.
- **Not a full feature-flag platform yet.** It enforces feature flags as rules; the management UX builds on the existing rule surfaces.

## Honest Risks

**Risk 1: The baseline SGS is a single point of failure.** If it goes down, the app is down. Mitigation: keep it minimal and robust (the simplest possible implementation); it is the one component engineered for maximum reliability; the residual risk is accepted as the voice memo stated.

**Risk 2: Automatic shutdown of compromised parts could cause false-positive outages.** Shutting down a part on a false detection degrades the app unnecessarily. Mitigation: the detection feeding shutdown must be high-confidence (the control-flow-graph hyper-jumps and no-404 signals are high-confidence); the MVA means a false shutdown degrades rather than breaks; require investigation before re-enabling.

**Risk 3: Feature-flags-as-rules could blur security and feature management confusingly.** Mitigation: they share the rule machinery but are clearly categorised (feature-flag rules vs security rules); the rich rule metadata (cross-ref: the rule-architecture brief) distinguishes them.
