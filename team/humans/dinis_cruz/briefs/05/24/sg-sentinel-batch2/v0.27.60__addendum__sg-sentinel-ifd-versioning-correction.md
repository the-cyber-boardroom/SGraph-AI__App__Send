## What This Is

A short correction addendum. The day-68 SG/Sentinel corpus (specifically the rules-engine brief) referred to the version-control scheme as **RFD (Request For Discussion)**. This was a hallucination and is wrong. The correct scheme is **IFD: Iterative Flow Development.** Because the day-68 documents are frozen, this addendum records the correction rather than editing them, and the correction has been applied to the batch-2 documents.

## The Correction

| Wrong (in the frozen day-68 corpus) | Correct |
|-------------------------------------|---------|
| RFD (Request For Discussion) | IFD (Iterative Flow Development) |

Anywhere the corpus says "RFD version control" or "RFD-reviewed," read it as the IFD scheme described below. The batch-2 documents have had the erroneous "RFD" references removed and reworded to "version-controlled and reviewed" (the vault review process), consistent with IFD.

## What IFD Actually Is

Iterative Flow Development is the versioning scheme used across the project. The version format is:

```
v{release}.{major}.{minor}
```

For example: `v0.27.60`, `v0.27.55`, `v0.14.x`.

The rules for how the version changes:

| Event | Version Effect |
|-------|----------------|
| **Every push to dev** | The **minor** number increments |
| **Merge to main** | The **major** number increments |
| **Release** | The **release** number is changed manually, when we choose to cut a release |

So the minor advances continuously with development pushes, the major advances when work merges to main, and the release is a deliberate, manually-chosen milestone. This is the scheme that has been producing the version numbers throughout the project (the `v0.27.x` series and the daily-index version headers).

## Why It Matters Here

This correction is relevant to the rule-packs and versioning work (cross-ref: the rule-packs-and-architecture-as-a-pack brief), because rule packs and architectures are versioned under IFD. Getting the scheme right matters now that we are introducing multiple versions and multiple packs: each pack is versioned with IFD, so the version of a pack tells you its development lineage (minor pushes on dev, major merges to main, manual releases).

It is also relevant to the rules-as-vault model (the day-68 rules-engine brief): rules and rule packs live in vaults, version-controlled under IFD, with changes reviewed (the vault review process). The "review" aspect (the AppSec agent reviewing rules as the attack surface, from the development-workflow brief) is the review discipline; IFD is the versioning discipline. They are distinct: IFD versions, the vault review process reviews. The original "RFD" erroneously conflated a review-sounding name with the versioning scheme.

## Scope Of The Correction

- **Day-68 frozen documents**: not edited; read "RFD" as IFD per this addendum.
- **Batch-2 documents**: the erroneous "RFD" references (in the development-workflow brief) have been removed and reworded.
- **Going forward**: use IFD (Iterative Flow Development) for the versioning scheme; use "the vault review process" for rule review.
