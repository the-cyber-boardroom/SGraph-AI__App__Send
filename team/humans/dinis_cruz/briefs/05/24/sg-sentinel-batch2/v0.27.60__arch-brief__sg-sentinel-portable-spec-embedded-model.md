# SG/Sentinel As A Portable Spec: The Embedded Model, Location-Agnostic Rules, And The Communication Module

**from** Human (project lead)

## What This Is

The eighth brief of the SG/Sentinel implementation batch, capturing what the project lead flagged as worth capturing separately: **SG/Sentinel as a simple, portable specification, the way sgit is a simple protocol.** This has two linked parts: the idea that SGS is a small set of primitives that can be embedded anywhere (a baked-in firewall inside any web service, with universally compatible rules), and the SGS communication module (how a service talks to the SGS stack, with headers as the inter-layer signalling channel).

The core insight: **the fundamental principles of SG/Sentinel are a very small set of primitives and workflows, the same way sgit is fundamentally just a set of rules for how you read and write files.** Because the primitive set is small, an SGS-compatible implementation can be built in any language, embedded in any web service, and the rules can be universally compatible, running anywhere and drawing on rules from other IDS/IPS/WAF systems and vice versa.

This is genuinely new and significant. The day-68 corpus established the substrate-independence principle (the principles brief) and the rules-as-everything model (the rules-engine brief), but never proposed SGS as a formal portable specification, an embeddable baked-in firewall, or location-agnostic universally-compatible rules. This brief does, and it is arguably the most strategically expansive idea in the batch.

## SGS As A Simple Protocol, Like sgit

The framing: **SGS, like sgit, is fundamentally a small, simple set of primitives, simple enough to specify and to reimplement in any language.**

The voice memo: **"the same way that sgit is actually a very simple protocol, because sgit is fundamentally a set of rules for how you write the files and how you write and read the file, the fundamental principles of SG/Sentinel are exactly the same: a very small set of primitives, a very small set of workflows."**

sgit's simplicity is why it is easy to implement in JavaScript, Python, or any language: it is just a defined way to read from and write to a file system. The claim is that SGS shares this property: its core is a small enough set of primitives (read the rules, run the rules, act on the decision) that it too can be reimplemented anywhere.

The voice memo proposed formalising this: **"it might even be worthwhile creating an RFC for this, the spec definition, or a spec, or what we call a standard."** Specifying SGS as a standard (an RFC-style document) would make it implementable by anyone, in any language, the way sgit's simplicity makes it portable. This connects to the substrate-independence principle (cross-ref: the principles brief) and the OPA/Sigma prior art (cross-ref: the addendum): Sigma is a portable rule spec compiled to many backends; an SGS spec would play the same role.

## The Smallest Possible SGS-Compatible Implementation

A concrete design question follows: **what is the smallest possible SGS-compatible implementation?** Because SGS is a small set of primitives and is open source, we should be able to define a minimal compatible implementation.

The voice memo: **"because it is open source, we should be able to say what is the smallest possible SGS-like compatible implementation that you can do."**

The pattern to map, in the voice memo's words: **"you have a very thin rule layer, and then everything else is rules, and then you need to be able to read the rules."** This is the rules-are-everything model (cross-ref: the rules-engine brief) restated as a portability spec: the engine is a thin layer (read the rules, run them, act); everything substantive is in the rules. A minimal SGS implementation is therefore small: it needs only to read rules, run them, and act on the result. **The minimal implementation is the thin rule-running layer; the rules carry the substance.**

This matters because a small, well-specified core is what makes SGS embeddable everywhere (below). If the core were large, embedding it in arbitrary services would be impractical. Because it is thin, it can go anywhere.

## The Baked-In Firewall: SGS Inside Any Web Service

The most expansive application: **SGS capabilities can run as a baked-in firewall inside a FastAPI service, inside any Python function, inside any web service.**

The voice memo: **"it should be possible to run SGS capabilities almost like a baked-in firewall inside the FastAPI service, in fact inside any Python function, in fact any web service could have an SGS implementation."**

This is a significant expansion of where SGS runs. The day-68 design placed SGS at the edge (CloudFront Functions, Lambda@Edge) and the batch-2 work added the reverse-proxy form factor. This brief adds the most intimate form factor: **SGS embedded inside the application itself**, as a firewall baked into the service code.

The voice memo named the specific value of running rules inside the app: **"there's going to be rules that we might want to run inside the FastAPI, because that's where you have access to the full context, which is going to be more efficient, again doing the right altitude."** This is the right-altitude principle (cross-ref: the codebase-extension brief) taken to its conclusion: some rules are most effective with the full application context, which only exists inside the app. An embedded SGS runs those rules where the context is richest.

So SGS now spans a full spectrum of form factors:

| Form Factor | Where It Runs | Context Available |
|-------------|---------------|-------------------|
| **CloudFront Function (Layer 1)** | The CDN edge | Minimal (request only) |
| **Lambda@Edge (Layer 2)** | The edge, with I/O | Request plus app state (cross-ref: control-flow-graphs brief) |
| **Reverse proxy** | In front of a service / bare EC2 | Inbound and outbound traffic |
| **Baked-in / embedded** | Inside the app (FastAPI, any Python, any web service) | Full application context |

The same SGS, the same rules, at every altitude from the CDN edge to inside the application code.

## The Dev-To-Prod Abstraction Path

The embedded model enables a natural development-to-production progression the voice memo described: **start by running rules inside the application; as you move to production and scale, abstract those rules out to the infrastructure.**

The voice memo: **"in development we run the rules inside the application, or when doing new stuff. Eventually, as you move into more production, as you move into more scale, you abstract some of those rules from the FastAPI application, because now we run them on the actual DevOps infrastructure, the Lambda functions, whatever compute deployment we have."**

The progression:

1. **Development**: run rules inside the app (embedded SGS; full context; easy to develop and iterate).
2. **Production / scale**: abstract rules out to the infrastructure (Lambda@Edge, CloudFront Functions; the rules move to the right altitude for scale).

This is powerful because the rules do not change as they move (see location-agnostic rules, below); only where they run changes. A rule developed and proven inside the app in development can be lifted to the edge in production, unchanged. The voice memo's "FastAPI is the only piece of the ecosystem actually running SGS" describes the starting point (a single embedded SGS, no edge infrastructure yet), which is also an excellent place to start: **the embedded baked-in firewall is the simplest possible first deployment, needing no edge infrastructure at all.**

This connects to the path-to-MVP (cross-ref: the path-to-MVP brief): the embedded model is arguably an even simpler MVP starting point than the CloudFront-first approach, because it needs no CloudFront, no Lambda@Edge, just an SGS module inside an existing FastAPI service.

## Location-Agnostic, Universally Compatible Rules

The principle that ties the form factors together, and a genuinely important one: **a rule should have no idea where it is running.** A rule cares only about whether it has the inputs it needs to make its decision, and what its decision (or transformation) is.

The voice memo: **"a rule should have no idea where it is running. A rule should just care: do I have what I need to make my decision, and here is my decision, or here is my transformation. A rule should have no idea that it is running inside an app, inside code, inside an EC2 instance, inside a cloud function, inside a serverless function."**

This is the principle that makes the dev-to-prod abstraction path work and makes rules portable across every form factor. A rule is a pure function: given its required inputs, it produces a decision or a transformation. It does not know or care whether it runs at the CDN edge, in a Lambda, in a reverse proxy, or baked into the app. The voice memo characterised what a rule does: **"is it transforming a header, a request? Is it not touching anything, read-only? Is it blocking? Whatever it does"**, but always without knowledge of its execution location.

The consequences are large:

| Because Rules Are Location-Agnostic | Consequence |
|-------------------------------------|-------------|
| A rule runs anywhere it has its inputs | The same rule works at every altitude |
| Rules move between form factors unchanged | The dev-to-prod abstraction path works |
| Rules are portable across implementations | The SGS spec enables cross-language rules |
| Rules can come from anywhere | Leverage rules from other IDS/IPS/WAF systems |

That last point is strategically significant: **SGS rules should be universally compatible, able to run on anything that can run rules, and able to leverage rules from other intrusion-detection, intrusion-prevention, and WAF systems, and vice versa.** The voice memo: **"we should be making SGS rules universally compatible, because they should be able to run on anything that can do that. We should be able to leverage rules from other intrusion detection and prevention and WAFs, and even vice versa."**

This connects directly to the Sigma/CRS prior art (cross-ref: the addendum, the research brief): Sigma rules compile to many backends; CRS rules are widely compatible. An SGS rule spec that is universally compatible could both consume rules from those ecosystems and contribute rules back, the way the research brief proposed being CRS-compatible. **Location-agnostic rules plus a portable spec equals a universally compatible rule ecosystem.**

## The SGS Communication Module

The second linked part: **the SGS communication module, which is how a service (a FastAPI app, or any service) talks to the SGS stack.** This is distinct from running an SGS engine inside the service; it is about how the service interacts with SGS solutions, on both the receiving and sending sides.

The voice memo: **"there is the SGS communication module: how this FastAPI can talk with an SGS stack, how it can send information, receive information, and how do you only allow requests that originate on SGS? This is less about having an SGS engine inside a FastAPI app, and more about how the FastAPI interacts with SGS solutions, on both receiving traffic and sending traffic, or as a reverse proxy."**

The communication module's responsibilities:

| Responsibility | Detail |
|----------------|--------|
| **Send information to SGS** | The service passes context/signals to the SGS stack |
| **Receive information from SGS** | The service receives decisions/signals from SGS |
| **Only-allow-SGS-originated requests** | The service can require that requests come through SGS (not bypassing it) |
| **Work on both sides** | Receiving traffic, and sending traffic (reverse proxy) |

The only-allow-SGS-originated-requests capability is notable: it lets a service insist that all its traffic has passed through SGS, closing the bypass risk (an attacker reaching the service directly, around the edge). Combined with the per-deployment PKI (cross-ref: the deployment-modes brief), the service can cryptographically verify that a request genuinely came through SGS.

### Headers As The Inter-Layer Signalling Channel

The concrete mechanism for the communication, and a neat one: **use HTTP headers to carry comms and signals from one layer to another.** Because rules execute in multiple places throughout the request lifecycle (Layer 1, Layer 2, embedded, reverse proxy), the layers need a way to signal each other, and headers are the natural channel because they flow through the whole HTTP path.

The voice memo: **"if we have rules being executed in multiple places throughout the request lifecycle, we can use headers, there are a lot of places where we can put comms and signals from one layer to the other. Headers are a good place, because they always fly through from one system to the other, because it is all going on HTTP."**

This gives the multi-layer execution a coordination channel: a rule at one layer can leave a signal in a header that a rule at another layer reads. This enables the two-way conversation through the request lifecycle (cross-ref: the MVP brief's two-way conversation API, the development-workflow brief) and supports a specific use the voice memo named: **compatibility signalling.**

### Compatibility Signalling

A specific capability the header channel enables: **signalling compatibility between rules, engines, and apps.** The voice memo: **"this allows us to determine issues, and even compatibility stuff: is a rule compatible with another rule, is this engine compatible, is this app compatible with other apps."**

Because rules run in many places and come from many sources (the universally-compatible-rules vision), compatibility matters: does this rule work with this engine? does this rule conflict with that one? is this app's SGS compatible with that app's? The header channel carries the signals that let the layers and services negotiate and verify compatibility. This is the connective tissue that makes the universally-compatible-rules ecosystem actually work in practice: rules and engines declare and check compatibility via the signalling channel.

## What This Asks For

Concrete next steps:

1. **Specify SGS as a portable standard** (an RFC-style spec, the way sgit is a simple protocol).
2. **Define the smallest possible SGS-compatible implementation** (the thin rule-running layer).
3. **Build the baked-in firewall** (SGS embedded inside a FastAPI service / any Python / any web service).
4. **Make rules location-agnostic** (a rule knows only its inputs and its decision, not where it runs).
5. **Make rules universally compatible** (run anywhere; leverage and contribute rules to other IDS/IPS/WAF ecosystems).
6. **Build the SGS communication module** (send/receive to the SGS stack; only-allow-SGS-originated requests).
7. **Use headers as the inter-layer signalling channel** (comms and signals through the request lifecycle).
8. **Build compatibility signalling** (rule-rule, engine, app compatibility via the header channel).
9. **Support the dev-to-prod abstraction path** (rules start embedded, abstract to infrastructure at scale).

Estimated effort: the embedded baked-in firewall is potentially a very simple and early deliverable (an SGS module in a FastAPI app, no edge infrastructure needed), making it an attractive MVP starting point; the portable spec and universal-compatibility work are larger, strategic efforts; the comms module and header signalling are focused builds.

## What This Does Not Try To Be

- **Not a replacement for the edge form factors.** The embedded model is one altitude among several; the spectrum from CDN edge to embedded all coexist.
- **Not a finished standard yet.** The RFC/spec is proposed, not written.
- **Not a claim that all rules run everywhere equally well.** Some rules need specific context (embedded for full app context; edge for speed); location-agnostic means a rule does not know where it runs, not that every rule is ideal at every altitude.

## Honest Risks

**Risk 1: A baked-in firewall inside the app shares the app's fate.** If the app is compromised, an embedded SGS may be too. Mitigation: the embedded model is one altitude; defence in depth means edge layers also protect; the embedded firewall is for context-rich rules and early/simple deployments, not the sole defence.

**Risk 2: Universal rule compatibility is ambitious and could be shallow.** Claiming compatibility with other IDS/IPS/WAF ecosystems is a large undertaking. Mitigation: start with CRS/Sigma compatibility (concrete, well-specified); the compatibility signalling channel surfaces incompatibilities rather than hiding them; grow the ecosystem incrementally.

**Risk 3: The portable spec could fragment if not well-governed.** An open spec with many implementations risks divergence. Mitigation: a clear, minimal spec (like sgit's simplicity); the smallest-possible-implementation as a reference; the compatibility signalling to detect divergence.
