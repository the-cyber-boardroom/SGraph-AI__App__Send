## What This Is

A consolidating brief that pulls together a theme which has surfaced repeatedly across the implementation batch but has not had a home of its own: **using SG/Sentinel to govern agents, controlling what they can do, in both development and production.** The deployment-modes brief called this "the most conceptually expansive idea" and flagged it as a major future surface; the development-workflow brief built on it for development agents; the surrogate-dependencies brief built on it for testing agents; the cost and commercial briefs assume it. It is large enough, and central enough to where agentic systems are going, to deserve its own consolidated treatment.

This brief does not introduce much that is new; it **synthesises** the agent-governance threads already present across the batch into one coherent picture, and cross-references each contributing brief rather than repeating it. The purpose is to make agent governance legible as a single capability, because read across five separate briefs it is easy to miss how big and coherent it is.

The core claim: **because SG/Sentinel sees both inbound and outbound traffic, can be deployed as a reverse proxy in front of anything, controls what passes via rules, and can make business-logic decisions, it is a natural substrate for governing agents, one of the central control problems in agentic systems.**

## Why Agent Governance Is The Right Frame

Agentic systems pose a control problem that traditional security tooling does not address well: **an agent's risk is in what it does, what it reaches out to, what tools it calls, what other agents it talks to, what actions it takes.** Controlling an agent means controlling its actions, which are largely outbound: the agent reaching out to the world.

SG/Sentinel is well-suited to this because of capabilities established across the batch:

| Capability | Contributing Brief | Why It Matters For Agents |
|------------|-------------------|---------------------------|
| **Sees outbound traffic, not just inbound** | Deployment-modes | An agent's actions are outbound; governing them means seeing outbound |
| **Reverse-proxy form factor** | Test-driving, deployment-modes | An agent can sit behind a Sentinel reverse proxy |
| **Rules control what passes** | Rules-engine (day-68), rule-architecture (day-68) | The agent's allowed actions are defined by analysable rules |
| **Business-logic decisions** | Control-flow-graphs | The agent's allowed sequences of actions can be enforced |
| **PKI trust** | Deployment-modes | Agent-to-agent communication can be mutually authenticated |
| **Blast-radius control** | Development-workflow | What an agent can do is bounded and analysable |

No single one of these is agent governance; together they are. This brief is the synthesis.

## Governing Agents In Production

The production picture, drawn from the deployment-modes brief: **every agent sits behind an SG/Sentinel (as a reverse proxy), so the agent's outbound actions go through SG/Sentinel, which protects and limits what the agent can do.**

The mechanism (cross-ref: the deployment-modes brief, Topic 1): when an agent reaches out to the internet, calls a tool, or talks to another agent, that outbound traffic flows through its SG/Sentinel reverse proxy. SG/Sentinel applies rules to the outbound action: is this an action the agent's workflow legitimately requires? If yes, allow and log; if no, block. This is the no-invalid-request principle (cross-ref: the execution-model brief, day-68) applied to outbound agent actions: an agent should only make the outbound calls its declared workflow needs; anything else is out of profile and suspect.

The control-flow-graph capability (cross-ref: the control-flow-graphs brief) sharpens this: an agent's actions have a legitimate sequence (the agent's workflow), and SG/Sentinel can enforce that sequence, blocking an agent that tries to act out of sequence (the hyper-jump pattern applied to agent behaviour). An agent that suddenly tries to reach a resource or call a tool its workflow never legitimately uses is making a detectable mistake.

| Agent Action | SG/Sentinel Governance |
|--------------|------------------------|
| Reaches out to the internet | Allowed only if the workflow requires it; logged |
| Calls a tool | Visible and limitable; out-of-profile tool calls blocked |
| Talks to another agent | Mutually authenticated (PKI); controlled; logged |
| Acts out of its workflow sequence | Blocked (control-flow-graph enforcement) |

## Agent-To-Agent Communication As The Controlled Channel

The agent-to-agent picture, drawing the deployment-modes and PKI threads together: **agent-to-agent communication goes through SG/Sentinel, mutually authenticated and confidential via per-deployment PKI.**

If every agent is behind an SG/Sentinel (above), and each SG/Sentinel has a keypair (cross-ref: the deployment-modes brief, Topic 4: per-deployment PKI), then agent-to-agent communication is mediated by SG/Sentinels that mutually authenticate by sharing public keys. The communication is authenticated (each agent knows it is talking to the right counterpart), confidential (only the intended recipient can read it), controlled (the rules govern what passes), and logged (the visibility applies). This connects to the broader agent-communication direction (cross-ref: the day-66 multi-cloud-deployment-and-agent-communication work): SG/Sentinel becomes the controlled, trusted channel through which agents communicate.

This is a strong position in agentic systems: the channel between agents is not an unguarded pipe but a governed conduit with authentication, authorisation, control, and visibility built in.

## Governing Agents In Development

The development picture, drawn from the development-workflow brief: **development agents talk to the SG/Sentinel protecting the app they are building, which controls their blast radius.**

The mechanism (cross-ref: the development-workflow brief): an agent building or fixing code can do significant damage if unconstrained. Putting SG/Sentinel between the agent's work and the world bounds what that work can do, and because the bound is expressed as a small, analysable set of rules (cross-ref: the rules-engine brief, day-68), it is far easier to reason about what a development agent can do by reading the rules than by trying to constrain the agent directly. **The rules are the blast-radius boundary, and they are analysable in a way agent behaviour is not.**

This is the same governance mechanism as production (the agent's actions go through SG/Sentinel; the rules bound them), applied to development agents. The continuity matters: an agent is governed the same way whether it is building the app or running in production, because in both cases SG/Sentinel mediates its actions.

## Testing And Developing Agents Against Surrogates

The testing picture, drawn from the surrogate-dependencies brief: **agents can be developed and tested against surrogate dependencies, served by the same SG/Sentinel reverse proxies that govern them in production.**

The mechanism (cross-ref: the surrogate-dependencies brief): agents are hard to develop and test against because their dependencies (APIs, tools, other agents) are expensive, non-deterministic, and side-effectful. SG/Sentinel reverse proxies can serve surrogates instead of forwarding to real dependencies, letting an entire agent workflow be developed and tested against a controlled reality, deterministically and without cost or side effects. **The reverse proxy that governs agent traffic in production is the same one that serves surrogates in development**, so governance and testing share one mechanism.

This closes a loop: the same reverse-proxy substrate governs agents in production, controls development agents' blast radius, mediates agent-to-agent communication, and serves surrogates for testing agent workflows. One mechanism, four governance roles.

## The Consolidated Picture

Agent governance via SG/Sentinel, as one capability:

```
                    ┌─────────────────────────────┐
                    │   SG/Sentinel (reverse       │
   Agent  ────────► │   proxy, sees inbound        │ ────► World / Tools /
                    │   AND outbound)              │       Other Agents
                    │                              │
                    │   - rules bound actions      │
                    │   - control-flow enforces    │
                    │     workflow sequence        │
                    │   - PKI authenticates        │
                    │     agent-to-agent           │
                    │   - blast radius analysable  │
                    │   - surrogates for testing   │
                    │   - full visibility + cost   │
                    └─────────────────────────────┘
```

The same SG/Sentinel substrate:

- **Governs production agents** (outbound actions controlled by rules; out-of-sequence actions blocked).
- **Controls development-agent blast radius** (the rules are the analysable boundary).
- **Mediates agent-to-agent communication** (authenticated, confidential, controlled, logged via PKI).
- **Serves surrogates for testing** (agent workflows developed against controlled realities).
- **Provides visibility and cost attribution** (cross-ref: the over-index-on-visibility emphasis; the cost-attribution brief: every agent action has an attributed cost).

## Why This Is Strategically Significant

Agent governance is one of the central unsolved problems in agentic systems: how do you control what autonomous agents do, bound their blast radius, authenticate their communication, and observe their behaviour? SG/Sentinel addresses all of these with one coherent substrate, because the capabilities it was built for (seeing traffic both ways, controlling it via rules, making business-logic decisions, PKI trust, visibility) are exactly what agent governance needs.

This connects to the commercial model (cross-ref: the commercial-model brief: agentic-native as a differentiator): SG/Sentinel is not just agent-friendly to build with, it is a governance layer for agents, which is a distinct and valuable position as agentic systems proliferate. It also connects to the interoperability principle (cross-ref: the interoperability brief): governing agents does not require replacing anything; SG/Sentinel sits in front of agents and makes their operation safer and more observable.

The voice memo that introduced the agent-to-agent idea was tentative about how much to capture ("I'm not sure if we should fully capture this"). This consolidating brief is the answer: it is significant enough to name as a coherent capability and a major future surface, while the detailed design is developed when agent governance becomes an active focus.

## What This Asks For

This is a consolidating brief, so it asks mainly for recognition and sequencing:

1. **Recognise agent governance as a coherent SG/Sentinel capability**, not a scattered set of sub-topics.
2. **Treat the reverse-proxy + outbound + rules + PKI + business-logic stack as the agent-governance substrate.**
3. **Sequence agent governance as a major future surface** (develop the detailed design when it becomes an active focus).
4. **Ensure the contributing capabilities are built agent-governance-aware** (outbound handling, PKI, control-flow enforcement, surrogate serving) so agent governance composes from them later.
5. **Position agent governance commercially** (cross-ref: the commercial-model brief) as a differentiated capability for agentic systems.

Estimated effort: the contributing capabilities are specified in their own briefs; this brief asks that they be built coherently so agent governance emerges from them, and that the detailed agent-governance design be developed when it becomes a focus. It is a synthesis and a sequencing recommendation, not a separate build.

## What This Does Not Try To Be

- **Not new design.** It synthesises threads from the contributing briefs.
- **Not a fully-specified agent-governance system.** It names the capability and the substrate; the detailed design is a future focus.
- **Not a replacement for the contributing briefs.** Each owns its mechanism; this connects them.

## Honest Risks

**Risk 1: Synthesising across briefs could imply more is built than is.** Mitigation: this is explicitly a consolidation and a future-surface flag; the contributing capabilities are at varying maturity; agent governance composes from them when they are ready.

**Risk 2: Agent governance is a large surface that could expand unbounded.** Mitigation: it is sequenced as a major future surface, developed when it becomes an active focus, not built speculatively now.

**Risk 3: An embedded or proxy Sentinel governing an agent shares the agent's trust context.** Mitigation: the same defence-in-depth and self-protection principles apply (cross-ref: the test-driving brief's self-protection topologies; the MVA brief's SGS-in-sequence); the governing Sentinel is independent of the agent it governs.
