# SG/Sentinel In The Development Workflow: Agents Talking To The Guard, Rules As The App Definition

**date** 24 May 2026
**from** Human (project lead)
**to** Developer (lead), Architect, AppSec, @Dev

## What This Is

The sixth brief of the SG/Sentinel implementation batch, capturing a specific development-workflow idea: **when an agent is building an app, let it talk to the SG/Sentinel instance protecting that app.** This makes SG/Sentinel a key part of the development workflow, controls the blast radius of development agents, and turns the rules into the explicit, reviewable definition of what the application can do.

The core insight: **the rules become the attack surface, and therefore the definition of the application.** The voice memo: **"the rules here become what is possible to do the application, so it's a great way to push quality, a great way to detect regressions, a great way to introduce things on the application, because fundamentally these rules are the definition of the application, the definition of what's possible or what's not possible."**

This extends two themes from the corpus without repeating them: the acid test (the UX brief: teams adopting Sentinel for their own purposes) and the agentic development model (the codebase-extension brief: AppSec/developer/QA agents). The new angle here is **development agents interacting with the live SG/Sentinel that protects the app they are building, as a way to control those agents and to make the rules the shared, reviewable contract.**

## Agents Talk To The SG/Sentinel Protecting Their App

The mechanism: **when an agent is working on an app, especially early in the app's life, it talks to the SG/Sentinel instance protecting that app.** We already have the pieces: a local SG/Sentinel, a deployed one, and the multiple deployments already in place.

The voice memo: **"when you are developing an app and using an agent to work, especially in the beginning of the app, it is really powerful to allow those agents to talk to the SG/Sentinel instance that is protecting the app. You have a local one, you have the deployed one, you have multiple deployments already in place. We already have a lot of the key pieces of the puzzle."**

This builds directly on the local-everywhere property (cross-ref: the interactivity brief): because SG/Sentinel runs locally identically to production, a development agent can talk to its local SG/Sentinel during development, then the same rules apply when deployed. The agent develops against the guard, not around it.

## Controlling The Blast Radius Of Development Agents

The primary value: **this is a great way to control development agents, because it controls their blast radius.** An agent building or fixing code can do a lot of damage if unconstrained; putting SG/Sentinel between the agent's work and the world bounds what that work can do.

The voice memo: **"this is a really cool way to control the agents, because it's a great way to control the blast radius. It's much easier to analyse a set of rules."**

The reasoning connects to the rules-are-everything model (cross-ref: the rules-engine brief): because the rules define what is possible, and the rules are a small, analysable set, it is far easier to reason about what a development agent can do by reading the rules than by trying to constrain the agent directly. **The rules are the constraint, and they are analysable in a way an agent's behaviour is not.**

This is a meaningful contribution to the agent-control problem (cross-ref: the deployment-modes brief's agent-to-agent direction). Where that brief controls agents in production via the reverse proxy, this brief controls development agents via the SG/Sentinel protecting the app they are building. Both use the same mechanism: the agent's actions go through SG/Sentinel, and the rules bound what is possible.

## Rules As The Attack Surface And The App Definition

The conceptual heart: **the rules become the attack surface, which means they become the definition of the application.** This reframes what the rules are.

The voice memo: **"the rules then become the attack surface. The rules become what is possible to do the application. Fundamentally, these rules are the definition of the application, the definition of what's possible or what's not possible."**

This is a powerful reframing with several consequences:

| Because The Rules Are The App Definition | Consequence |
|------------------------------------------|-------------|
| The rules define the attack surface | Reviewing the rules is reviewing the attack surface |
| The rules define what is possible | Quality is pushed by getting the rules right |
| The rules define valid behaviour | Regressions are detected when behaviour deviates from the rules |
| The rules are introduced as features are | Introducing a feature means introducing its rules |

This connects to the control-flow-graphs brief (the rules define what should happen next, the app's business logic) and the no-invalid-request principle (the rules define what valid traffic is). The rules are not just security filters; they are the executable specification of the application's allowed behaviour. **To know what the app can do, read its rules.**

## Reviewing The Rules: An AppSec Agent's Job

A concrete practice that follows: **because the rules are the attack surface, an AppSec agent (or other agents) can review the rules, and that review is a review of the application's security.**

The voice memo: **"it's easy to have an AppSec agent, or other agents, whose job is to review the rules, because the rules become the attack surface."**

This is the agentic development model (cross-ref: the codebase-extension brief) applied with a sharp focus: the AppSec agent reviews the rules, and because the rules are the app definition, that review covers the app's security comprehensively. Reviewing a small, analysable set of rules is far more tractable than reviewing the entire application's code for security issues. **The rules are the reviewable security surface, and the AppSec agent reviews them.**

This is also why the rules-as-vault, version-controlled and reviewed model (cross-ref: the rules-engine brief) matters: rule changes go through review, and because the rules are the attack surface, that review is the security review. Every rule change is an attack-surface change, reviewed as such.

## All Teams Interact With SG/Sentinel

The voice memo named the breadth of adoption: **every team already in the project should now interact with SG/Sentinel, because every one of them builds something that will be protected by it or talk to it.**

The voice memo: **"I already have a bunch of teams: the sgit team, the dev team, the team developing sgit, the team that developed the vault web, even the tools. Every one of those should now start to interact with this, because every one of those will be talking to a site or system or service that will be protected. Either they have an SG/Sentinel inside of them, or they're talking to an SG/Sentinel on the other side."**

This is the acid test (cross-ref: the UX brief) realised across the whole project: not one team adopting Sentinel, but every team, because every component either sits behind a Sentinel or talks to one. The teams named (sgit, the vault-web team, the tools teams) all interact with Sentinel as a natural part of their work.

The two modes of interaction:

| Mode | Example |
|------|---------|
| **Has an SG/Sentinel inside it** | A service with a baked-in Sentinel (cross-ref: the embedded-model brief) |
| **Talks to an SG/Sentinel on the other side** | A client talking to a Sentinel-protected service |

Either way, every team's work touches SG/Sentinel, which means every team contributes to and benefits from the rules (the app definitions). This is the virtuous cycle of the acid test at project scale: broad adoption makes the rules richer, which makes the protection better, which makes adoption more valuable.

## What This Asks For

Concrete next steps:

1. **Let development agents talk to the SG/Sentinel protecting their app** (local and deployed).
2. **Use SG/Sentinel to control development-agent blast radius** (the rules bound what the agent can do).
3. **Treat the rules as the attack surface and app definition** (reviewing rules reviews the app).
4. **Have an AppSec agent review the rules** (the security review is the rule review).
5. **Bring every team into interaction with SG/Sentinel** (sgit, vault-web, tools: all behind or talking to a Sentinel).
6. **Use rule changes as attack-surface changes** (reviewed via the vault review process).

Estimated effort: this is largely a workflow and practice change (agents talk to Sentinel; teams interact with it; the AppSec agent reviews rules) built on existing mechanisms (local-everywhere, rules-as-vault, the agentic model), rather than a new build.

## What This Does Not Try To Be

- **Not a new agent-control subsystem.** It uses the existing Sentinel-controls-agents mechanism for development agents.
- **Not a replacement for code review.** Rule review complements code review; it focuses the security review on the attack surface.
- **Not mandatory for every team at once.** Broad interaction is the goal; adoption is incremental.

## Honest Risks

**Risk 1: Development agents constrained by Sentinel could be slowed.** Mitigation: the rules bound the blast radius without micromanaging; in development, rules can be permissive (passive mode) and tightened as confidence grows.

**Risk 2: Treating rules as the complete app definition could overclaim.** Not everything about an app is in its Sentinel rules. Mitigation: the rules are the attack surface and the allowed-behaviour definition, not the entire implementation; be precise about what they define.

**Risk 3: Broad team interaction could create inconsistent rule practices.** Mitigation: the rules-as-vault, reviewed model and the architect agent maintain consistency across teams.
