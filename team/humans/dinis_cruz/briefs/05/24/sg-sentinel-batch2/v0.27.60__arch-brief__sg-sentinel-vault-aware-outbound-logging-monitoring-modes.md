## What This Is

The tenth brief of the SG/Sentinel implementation batch, capturing how SG/Sentinel uses vaults as its data substrate and how that enables a spectrum of monitoring and logging modes. Three linked ideas:

- **Outbound data validation and logging**: because SG/Sentinel sees outbound traffic (as a reverse proxy), it can validate and log what is sent to other modules, servers, and users.
- **Monitoring and logging modes**: a spectrum from logging nothing of the user (privacy) to logging everything (compliance and maximum governance), with what-we-capture becoming a business-logic decision.
- **Vault-aware SG/Sentinel**: native integration with our vaults as the place to store captured data and secrets, including the vault-per-request and pass-the-vault-around supply-chain pattern.

This is genuinely new relative to the corpus. The deployment-modes brief introduced that SG/Sentinel sees outbound traffic; this brief uses that for outbound validation and logging. The compliance brief mapped standards to deployment; this brief is about the logging and vault mechanism underneath, not the compliance mapping. The vault-per-request and supply-chain ideas are wholly new.

A note: the voice memo also sparked an idea about the free version of SG/Send using the maximum-governance mode, which the project lead explicitly parked for a separate memo. This brief notes it as parked and does not develop it.

## Outbound Data Validation And Logging

The first capability follows from the outbound-traffic insight (cross-ref: the deployment-modes brief): **because SG/Sentinel as a reverse proxy sees outbound traffic, it can validate and log the data being sent out, to other modules, to other servers, and to the user.**

The voice memo: **"when you look at outbound traffic, both from the normal request and response and from the reverse-proxy concept, one of the things that's very interesting is that we can now do a lot of outbound data validation and logging, because we can understand much better all the data that has been sent to the different modules and to the different servers, including to the user."**

This is a significant capability. Most security tooling focuses on inbound (what arrives); outbound validation and logging (what leaves) is less common and very valuable: it catches data exfiltration, validates that responses are well-formed and do not leak, and provides a complete picture of what the system sends to whom. SG/Sentinel, sitting on the outbound path, can do all of this.

The voice memo added an important caveat that ties to the platform's nature: **mind the encryption.** **"Take into account that some of the data is encrypted, so we can't log that, and it doesn't make a lot of sense to log that, but a lot of other things will make sense."** Because the platform is zero-knowledge, much outbound data is encrypted and cannot (and should not) be logged in clear. So outbound logging is selective: log what is meaningful and loggable (metadata, structure, destinations, unencrypted content), and respect that encrypted payloads stay opaque. What is watched and logged, including whether file content is captured, **becomes a business-logic decision** (the voice memo: "it's almost like that becomes a business-logic solution, what we watch and what we see, including the content of the files"), configured per deployment.

## Monitoring And Logging Modes: From Nothing To Everything

The second idea is a spectrum of logging modes, which the voice memo framed as ranging from logging nothing of the user to logging everything: **SG/Sentinel supports different monitoring and logging modes, and the right mode is a per-deployment decision.**

The voice memo: **"we will have different types of monitoring and logging. We will have modes where we log nothing of the user, and also modes where we log everything, especially for compliance."**

The spectrum:

| Mode | What It Logs | Use Case |
|------|--------------|----------|
| **Log nothing of the user** | No user data (the privacy/anonymity mode) | Maximum privacy; the anonymity modes from the developer-friendliness brief |
| **Selective** | Meaningful metadata, destinations, structure | Normal operation; the IP-escrow middle ground (cross-ref: the tabletop resolution) |
| **Log everything (maximum governance)** | Every request, every response, all IPs, all data | Compliance; maximum governance and observability |

The maximum-governance mode is the new extreme the voice memo developed: **"we can have a mode where we save everything, every request, every response, everything gets captured, all the IP addresses, all the data, for compliance purposes, and we can have maximum governance and maximum observability on what's happening."**

This connects to several earlier threads: the IP-escrow resolution (cross-ref: the tabletop part 1, GAP 3.1, where binary on/off was too crude and escrow was the middle ground); the anonymity modes (cross-ref: the developer-friendliness brief); and the compliance graph (cross-ref: the compliance brief, where the logging mode is one of the things that determines compliance posture). The logging mode is a dial, set per deployment, and where it is set is itself a compliance-relevant and business-logic decision. **The same SG/Sentinel can be maximally private for one deployment and maximally governed for another, by setting the logging mode.**

## Vault-Aware SG/Sentinel: Vaults As The Data Substrate

The third and most novel idea: **SG/Sentinel should be natively integrated with our vaults, because vaults are the natural place to store captured data and secrets.** The voice memo: **"we eventually need to add native integration with our vaults, left, right, and centre, because the vaults are a great place to store data and to manage secrets."**

This makes the platform's core primitive (the vault) the data substrate for SG/Sentinel's logging, capture, and secret management. The maximum-governance mode, for example, saves everything into a vault: every request, response, and IP captured into a vault that provides the encryption, versioning, and access control the platform's vaults already have. SG/Sentinel does not need to build its own storage; it uses vaults.

This is the platform's own patterns applied to SG/Sentinel (cross-ref: the day-68 daily index's observation that SG/Sentinel is the platform's patterns applied to security): the rules are a vault (rules-as-vault, the rules-engine brief), and now the captured data and secrets are vaults too. SG/Sentinel is vault-native through and through.

### Vault-Per-Request And Passing The Vault Around

The most inventive part, which the voice memo explored as the next evolution: **because vaults are lightweight, we can create a vault per request, or zip a vault and pass it around, which is the beginning of a supply-chain pattern where each layer adds files to the vault.**

The voice memo: **"the vaults are lightweight enough that we can create a vault per request, or even zip a vault and pass it around in some cases. It's almost like the beginning of that whole supply-chain idea, where each layer could be adding files to these vaults."**

The supply-chain pattern: a request gets a vault; as it flows through the layers (Layer 1, Layer 2, the app, the outbound path), each layer adds files to that vault (its decisions, its evidence, its signals). By the end, the vault is a complete record of everything that happened to that request, assembled incrementally by each layer that touched it. This is the IDs-everywhere traceability (cross-ref: the rule-architecture brief) realised as a vault: the request's vault is its complete, portable history.

The voice memo noted a neat mechanism for passing the vault around, leveraging the fact that we control the HTTP: **"because we control the HTTP requests and the headers, we could always append it to a page. There's nothing preventing us from adding to the end of a file the actual vault, a base64-encoded version of the vault, or just the IDs of where to get the vault from."**

So the vault can travel with the request in two ways:

| Mechanism | How | When |
|-----------|-----|------|
| **Serialised inline** | Base64-encoded vault appended to the response/file, or carried in headers | When self-contained portability matters |
| **By reference** | Just the IDs of where to fetch the vault from a central vault server | When servers share access to a central vault store |

The voice memo flagged this as a performance trade-off to evaluate: **"this depends on whether the multiple servers have access to the same vault server. This is going to be an interesting performance check: is it better to include the vault serialised in the request, or to have a central place where they go and put the data?"** Both are viable; which is better depends on the deployment (do the servers share a vault store? is the vault large?). This is exactly the kind of question the cost-attribution and Prometheus-metrics work (cross-ref: the cost-attribution and deployment-modes briefs) would inform with real data.

This vault-per-request supply-chain pattern connects to the header-signalling channel (cross-ref: the embedded-model brief): the headers can carry the vault (serialised or by reference) from layer to layer, so the inter-layer comms channel and the vault-passing mechanism are the same HTTP-based channel. Each layer reads the vault from the headers, adds its files, and passes it on.

## What This Asks For

Concrete next steps:

1. **Build outbound data validation and logging** (on the reverse-proxy outbound path; selective, respecting encryption).
2. **Make what-is-watched a business-logic decision** (configured per deployment, including file-content capture).
3. **Build the logging-mode spectrum** (log-nothing-of-user, selective, log-everything/max-governance).
4. **Integrate natively with vaults** (vaults as the substrate for captured data and secrets).
5. **Build the maximum-governance mode** (save every request/response/IP into a vault for compliance).
6. **Build vault-per-request** (a lightweight vault per request, added to by each layer: the supply-chain pattern).
7. **Build vault-passing** (serialised inline via headers/append, or by reference to a central vault store).
8. **Run the inline-vs-central-vault performance check** (which is better, informed by cost/metrics data).

Estimated effort: outbound logging and the logging-mode spectrum build on the outbound-traffic and existing logging work; native vault integration leverages the platform's vault primitive; the vault-per-request supply-chain pattern is the most novel and is a next-evolution capability rather than first-MVP.

## What This Does Not Try To Be

- **Not logging of encrypted content.** Encrypted payloads stay opaque; logging is selective and respects zero-knowledge.
- **Not the free-SG/Send max-governance feature.** That application is parked for a separate memo.
- **Not a new storage system.** It uses the platform's vaults.
- **Not the compliance mapping.** It is the logging/vault mechanism; the compliance-graph brief maps it to standards.

## Honest Risks

**Risk 1: Maximum-governance logging captures sensitive data.** Saving every request, response, and IP is a significant data-protection responsibility. Mitigation: the vault provides encryption and access control; the mode is a deliberate per-deployment choice (for compliance contexts); the privacy modes exist for contexts that need them.

**Risk 2: Vault-per-request could be expensive at scale.** A vault per request, passed around, has overhead. Mitigation: vaults are lightweight; the inline-vs-central performance check determines the efficient approach; it is a next-evolution capability, measured before scaling.

**Risk 3: Outbound logging could accidentally capture encrypted or sensitive content.** Mitigation: logging is selective and encryption-aware by design; what is captured is an explicit business-logic decision, not a blanket capture.
