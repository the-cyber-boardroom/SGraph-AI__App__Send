## What This Is

The fifth brief of the SG/Sentinel implementation batch, capturing four related deployment-and-integration ideas from the project lead's notebook. Each extends how SG/Sentinel is deployed and integrated, and they hang together as "the ways SG/Sentinel runs and connects" rather than warranting four separate briefs:

1. **Agent-to-agent workflows and outbound traffic**: SG/Sentinel sees outbound as well as inbound traffic, so it can protect, limit, and visualise agents and agent-to-agent communication, deployed as a reverse proxy.
2. **Passive mode**: an observe-only first deployment that adds value through logging alone and lets us reverse-engineer rules from observed traffic.
3. **Prometheus-style pull endpoints**: pull-based metrics endpoints that scale data collection better than pushing.
4. **Per-deployment PKI**: public/private keys per SG/Sentinel deployment, so entities can authenticate to each other by sharing public keys.

These are genuinely new relative to the day-68 corpus and the earlier batch-2 briefs. The reverse proxy was introduced in the test-driving brief for bare-EC2 protection; here it gains the outbound/agent-to-agent purpose. Observe-mode was mentioned across day-68; here passive mode gains the rule-reverse-engineering mechanism. Prometheus endpoints and per-deployment PKI are wholly new.

## Topic 1: Agent-To-Agent Workflows And Outbound Traffic

The most conceptually expansive idea: **SG/Sentinel can visualise, manage, and control agents and agent-to-agent workflows, because every agent can sit behind an SG/Sentinel, and because SG/Sentinel sees outbound traffic, not just inbound.**

The voice memo: **"we could use SG/Sentinel to visualise, manage, and control agents and agent-to-agent workflows, because if every agent is behind an SG/Sentinel, deployed as a reverse proxy, we can really protect and limit what the agents can do."**

### The Outbound Insight

The key realisation that makes this work, and one the entire corpus had not addressed: **SG/Sentinel sees outbound traffic, not just inbound.** The day-68 design was entirely about inbound traffic (requests arriving at the protected app). But the same engine sees traffic going the other way.

The voice memo: **"at the moment SG/Sentinel mainly talks about inbound traffic, but remember that SG/Sentinel also sees the outbound traffic. So the reverse proxy is just a small variation where the outbound traffic is the connection and the inbound is the response."**

This reframes the reverse-proxy form factor (introduced in the test-driving brief for bare-EC2 protection). As a reverse proxy, SG/Sentinel handles outbound connections: when something behind it reaches out to the internet, that outbound request goes through SG/Sentinel, and the response comes back through it. The same rule engine, the same control, applied to outbound as well as inbound.

### Why This Matters For Agents

The outbound capability is what makes agent control possible. An agent's risk is largely in what it *does*: what it reaches out to, what tools it calls, what other agents it talks to. By putting each agent behind an SG/Sentinel reverse proxy, **the agent's outbound actions go through SG/Sentinel, which can protect and limit what the agent can do.**

The voice memo: **"an agent needs to go to the internet, or an agent is talking to another agent, they should go to the SG/Sentinel, they should use the SG/Sentinel stack."**

| Agent Action | SG/Sentinel Control |
|--------------|---------------------|
| Agent reaches out to the internet | Outbound request goes through Sentinel; allowed/blocked/logged |
| Agent talks to another agent | Agent-to-agent traffic goes through Sentinel; controlled |
| Agent invokes a tool | The invocation is visible and limitable |
| Agent-to-agent workflow | The whole workflow is visualised and controlled |

This is a significant expansion of SG/Sentinel's role: from protecting apps against inbound attacks to **governing what agents do**, which is one of the central safety and control problems in agentic systems. The same control-flow-graph and no-invalid-request principles (cross-ref: the control-flow-graphs brief) apply to outbound agent actions: an agent should only make the outbound calls its workflow legitimately requires; anything else is out of profile.

This connects to the broader agent-communication direction (cross-ref: the day-66 multi-cloud-deployment-and-agent-communication work): SG/Sentinel becomes the controlled channel through which agents communicate, with all the visibility, rules, and evidence-graph capabilities applied to agent-to-agent traffic.

The voice memo was tentative about how much to capture now ("I'm not sure if we should fully capture this"), so this is flagged as a direction with significant potential rather than a fully-specified design: **the outbound/agent-control capability is a major future surface, enabled by the reverse-proxy form factor and the outbound-traffic insight, worth developing further when agent governance becomes a focus.**

## Topic 2: Passive Mode And Reverse-Engineering Rules From Logs

The second idea sharpens the observe-mode concept (mentioned across day-68) into a distinct, valuable deployment mode with a specific mechanism: **passive mode, where SG/Sentinel just observes and logs, adding value immediately and letting us reverse-engineer the rules from the observed traffic.**

The voice memo: **"use SG/Sentinel in passive mode, which is the first deployment, where you just observe. With the logging, this will add a lot of value, and it is also a way to reverse-engineer the rules."**

### Passive Mode As The First Milestone

Passive mode is the safest possible first deployment, and the voice memo named it as the first milestone: **put SG/Sentinel in front of an application and make sure it has no side effects.**

The voice memo: **"the first milestone is to actually put SG/Sentinel in front of an application and make sure it has no side effects. If we can do that with logging and rule creation, so that it becomes transparent, and then people can enable rules as they're comfortable, that is massive."**

This is the lowest-touch possible onboarding (cross-ref: the UX brief's complexity-removal principle): put Sentinel in front, in passive mode, where it only logs and has zero side effects, so there is zero risk to the protected app. Then, as the operator gains confidence, they enable rules incrementally. This is the progressive lock-down model (cross-ref: the delegation brief) applied as an onboarding experience: start at zero (passive, observe-only), enable rules as comfortable, tighten over time.

The value of passive mode even before any rule is enabled: **the logging alone provides visibility that does not currently exist** (cross-ref: the over-index-on-visibility emphasis). An operator gets value from passive mode immediately, just from seeing their traffic, before any blocking happens.

### Reverse-Engineering Rules From Observed Traffic

The distinctive mechanism: **passive mode captures everything, and from that captured traffic we reverse-engineer the rules, then simulate them to see which would have side effects before enabling them.**

The voice memo drew on the project lead's prior experience building rule-based products: **"I remember working on a static analysis tool where it was faster for me to delete all the rules in the database and create a static-analysis visualisation that showed me all the sources and sinks in all the main code paths. I was mapping the attack surface, the inputs and outputs, then just adding rules that defined how data propagated, and I would have much better results."**

The lesson applied to SG/Sentinel: rather than writing rules blind, **observe the real traffic (passive mode), visualise the attack surface (the sources and sinks, the inputs and outputs, the main paths), and derive the rules from what is actually there.** The voice memo connected this to the LLM accelerant: **"with the power of the LLMs these days, especially around rule creation, we can have a passive mode that has very little logic, just the logging rules, and we capture everything, then we start to create rules, and we simulate rules to see which rules could have a side effect on traffic."**

The workflow:

1. **Deploy in passive mode** (logging only, no side effects).
2. **Capture everything** (the real traffic, the real attack surface).
3. **Visualise the attack surface** (sources, sinks, inputs, outputs, main paths).
4. **Reverse-engineer rules** from the observed traffic (LLM-assisted).
5. **Simulate the rules** against the captured traffic (would they have side effects?).
6. **Enable rules incrementally** as confidence grows.

This is the replay-from-S3 idea (cross-ref: the addendum's Observation 2) realised as the rule-creation workflow: the captured passive-mode traffic in S3 is the corpus against which candidate rules are simulated. **A rule is only enabled once simulation against real captured traffic shows it has no unacceptable side effects.** This directly addresses the false-positive fear that runs through the corpus.

## Topic 3: Prometheus-Style Pull Endpoints

The third idea is a concrete, pragmatic addition for metrics and performance monitoring: **expose Prometheus-style endpoints that are pulled rather than pushed, which scales data collection better.**

The voice memo: **"we can add a couple of endpoints, on /admin, maybe a bit protected, that behave like a Prometheus endpoint. From a performance and statistics and what's-going-on point of view, we could have Prometheus endpoints which scale more, because you don't have to keep pushing the data out, you can pull the data."**

The advantage of pull over push for metrics:

| Push (the default assumption) | Pull (Prometheus-style) |
|-------------------------------|-------------------------|
| Sentinel pushes metrics out continuously | A collector pulls metrics on its schedule |
| Constant outbound data, even when unobserved | Data collected only when pulled |
| Scales poorly (every instance pushing) | Scales well (collector controls the rate) |
| Awkward for ephemeral instances | Works for ephemeral if collected within the window |

The voice memo noted the ephemeral fit: **"if this is for ephemeral things that hold for a little bit, as long as you collect it within five or ten or thirty seconds, it will still work quite well. It is a really nice way to scale data collection, especially for performance monitoring."**

This is well-suited to the ephemeral-instance reality (cross-ref: the test-driving brief's bare-EC2 instances, the day-66 ephemeral provisioning): an ephemeral instance that lives for minutes can expose a pull endpoint, and as long as the collector pulls within the window, the metrics are captured without the instance having to push. The endpoints sit behind /admin (protected), and they provide performance and statistics data in a standard, scalable, pull-based form.

This connects to the cost-attribution work (cross-ref: the cost-attribution brief): the per-action cost data and the performance metrics are exactly what the Prometheus endpoints would expose, in a form that standard monitoring tooling can consume. It is a pragmatic, standards-compatible way to surface the visibility and cost data the corpus emphasises.

## Topic 4: Per-Deployment PKI

The fourth idea introduces public-key infrastructure at the deployment level, concretely: **each SG/Sentinel deployment has a public/private keypair, and entities authenticate to each other by sharing public keys.**

PKI was mentioned in the day-68 corpus (the principles brief listed it as a capability; the MVP brief's two-way API needed auth), but never developed. This memo makes it concrete.

The voice memo: **"each SG/Sentinel deployment has a public key, and we share public keys from our admin, or certain users, or even the application. How does the SG/Sentinel know it is talking to the right application? It just becomes a case of sharing the public keys. If you share the public keys, you make sure you are talking to the right entity, and only the right entity can read what you send."**

The per-deployment PKI model:

| Entity | Has A Keypair | Used For |
|--------|---------------|----------|
| **Each SG/Sentinel deployment** | Public + private | Identifying itself; receiving encrypted messages |
| **Admin** | Public shared with Sentinel | Authenticating admin actions to Sentinel |
| **Certain users** | Public shared with Sentinel | Authenticating those users |
| **The protected application** | Public shared with Sentinel | Sentinel knowing it is talking to the right app |

The two capabilities PKI provides:

1. **Authentication: knowing you are talking to the right entity.** The voice memo's example: how does Sentinel know it is talking to the right application? By having the app's public key. Sharing public keys establishes mutual authentication between Sentinel and the entities it interacts with (the admin, the app, specific users).
2. **Confidentiality: only the right entity can read what you send.** With public keys shared, messages can be encrypted so only the intended recipient can read them.

The voice memo connected this to two things: the admin interface (PKI authenticates admin actions, strengthening the API-key-protected admin surface from the MVP brief) and agent-to-agent (Topic 1): **"this is quite an important topic when you talk about agent-to-agent, and we already have most of the plumbing for this, so it would not be hard to add."**

The agent-to-agent connection is the strongest: if every agent is behind an SG/Sentinel (Topic 1), and each SG/Sentinel has a keypair, then agent-to-agent communication is mutually authenticated and confidential by sharing public keys. PKI is the trust layer for the agent-to-agent control SG/Sentinel provides. And the corpus already has the PKI plumbing (cross-ref: the day-66 vault-discovery-and-public-keys work), so this leverages existing infrastructure rather than building new.

## What This Asks For

Concrete next steps:

1. **Build passive mode** (logging only, zero side effects) as the first-milestone deployment.
2. **Build rule reverse-engineering from passive-mode capture** (visualise the attack surface; LLM-derive rules; simulate against captured traffic before enabling).
3. **Extend the reverse proxy to outbound traffic** (the connection is outbound, the response inbound).
4. **Develop the agent-to-agent control capability** (agents behind SG/Sentinel; outbound actions controlled) as a major future surface.
5. **Add Prometheus-style pull endpoints** (on /admin, protected; performance and statistics; ephemeral-friendly).
6. **Add per-deployment PKI** (keypair per deployment; share public keys for authentication and confidentiality), leveraging existing PKI plumbing.
7. **Use PKI as the agent-to-agent trust layer** (mutually authenticated, confidential agent communication).

Estimated effort: passive mode is near-term and high-value (it is the safest first deployment and the first milestone); Prometheus endpoints and per-deployment PKI are focused additions leveraging existing patterns; the outbound/agent-to-agent capability is a larger future surface to develop when agent governance becomes a focus.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a full agent-governance product (yet).** The outbound/agent-to-agent capability is flagged as a major direction, not fully specified here.
- **Not a replacement for the inbound design.** Outbound is a variation on the same engine, not a different system.
- **Not a new metrics platform.** Prometheus endpoints expose data in a standard form for existing tooling.
- **Not a new PKI system.** It leverages the existing PKI plumbing.

## Honest Risks

Three risks:

**Risk 1: Outbound/agent control is a large surface flagged tentatively.** The voice memo was unsure how much to capture. Mitigation: it is documented as a direction, not a committed design; develop it when agent governance is a focus; the reverse-proxy and outbound insight are the foundation.

**Risk 2: Passive-mode rule reverse-engineering could derive rules that overfit the observed traffic.** Rules derived from a sample might miss legitimate variations not in the sample. Mitigation: simulate against a broad capture; observe-mode before enforce; enable incrementally as confidence grows.

**Risk 3: Per-deployment PKI adds key-management burden.** Keypairs and public-key sharing need management. Mitigation: leverage the existing PKI plumbing; automate key distribution; the burden is justified by the authentication and confidentiality it provides, especially for agent-to-agent.
