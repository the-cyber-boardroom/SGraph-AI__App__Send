## What This Is

The third brief of the SG/Sentinel implementation batch, doubling down on **usability and user experience across every part of the platform.** The day-68 corpus established developer-friendliness as a quality multiplier (the developer-friendliness brief); this brief takes that principle and develops it into the concrete, designed experience: usability across every distinct persona, the explicit introduction of a designer role, the add-Sentinel-to-an-app onboarding flow, and the acid test that tells us SG/Sentinel has truly succeeded.

The governing instruction: **over-index on usability, everywhere, for everyone.** The voice memo: **"the experience of a developer adding SG/Sentinel to an app, the ability of a QA agent, a tester, even a developer understanding the impact of SG/Sentinel, or a business user using it: you have to always over-index on usability. It should be transparent, easy, straightforward."**

This is genuinely new relative to the day-68 corpus. The developer-friendliness brief argued *why* developer-friendliness matters (it correlates with code quality). This brief is about *the designed experience itself*: who the users are, what each needs to see, who designs it, how onboarding works, and how we know it succeeded. Where day-68 named developer/AppSec/QA/architect/accountant agents, this brief adds the role that was missing: the designer.

## The Principle: Usability Removes Complexity, It Does Not Add It

The strongest framing in the memo, and the one that should govern every UX decision: **SG/Sentinel must remove complexity from operations, not add it.**

The voice memo: **"this cannot be a solution that has complexity. If anything, this should be a solution that removes complexity from an operation."** This inverts the usual relationship between security tooling and complexity. Most security tools add operational burden (configuration, tuning, false-positive triage, integration work). SG/Sentinel's UX goal is the opposite: adding it should make operating an app *simpler*, because it abstracts away the questions developers currently struggle with.

The mechanism is the checks-and-visualisation work already proven elsewhere in the project. The voice memo: **"tools like installation, deploy, check, like health checks, a lot of the stuff we've been doing with checks are really powerful, because they allow the abstraction of the complexity. Instead of the developer having to figure out 'what the hell is wrong with this thing, why isn't it working,' you visualise the multiple elements."**

So the UX principle is: **abstract the complexity behind detailed health checks and visualisation, so the user never has to debug the plumbing.** The checks tell them what is deployed, what is configured, what is working, and what is not, so they do not have to figure it out themselves. This connects to the day-66 demo-discipline and checks work, now applied as the UX foundation for SG/Sentinel.

## Usability Across Every Persona

The central new content: **SG/Sentinel has many distinct users, and each needs a different experience, different visualisations, and different data sets.** The voice memo named them explicitly, and the UX must serve all of them.

| Persona | What They Need From SG/Sentinel |
|---------|--------------------------------|
| **Developer (adding Sentinel)** | Easy onboarding; is it configured right? is my code correct? simulate traffic; understand the impact |
| **Developer (understanding impact)** | What is SG/Sentinel doing to my app? what is it blocking, allowing, seeing? |
| **QA agent / tester** | Use Sentinel to validate behaviour; write tests against it; confirm what reaches the app |
| **Security tester / pen tester** | Probe it; see what gets through; the red-team view (cross-ref: the test-driving brief) |
| **AppSec engineer** | Threat-model coverage; which attacks are blocked; the security posture |
| **Business owner** | The business advantage: is the app faster? more visible? what is the value? |

The voice memo: **"we always need to look at what is the business advantage of deploying this, and we already mapped that this makes the app faster, gives good users a fast track, and gives more visibility."** Each persona sees the value through a different lens, and the UX must present the right lens to each.

The key design implication: **different users need different visualisations and different data sets.** The voice memo: **"we have to think about what the visualisation looks like, and what the data sets that our generator produces look like, for the different users we have, from developers to QA to security testers to AppSec engineers to pen testers to business owners."** This is not one dashboard for everyone; it is a designed experience per persona, drawing on the same underlying data (the evidence graph, the logs, the rule state) but presenting the view each persona needs.

This extends the TUI mockups brief (which showed operator surfaces) into persona-specific experiences. The operator surfaces are one persona's view; the developer-adding-Sentinel, the business-owner, and the pen-tester each need their own.

## The Designer Role

The most important new addition: **bring a designer onto the project, to design the experience.** The voice memo was explicit that this has been missing: **"this is something we haven't really introduced a lot, but we need to bring the designer on. The designer should be designing the experience. We should be thinking about the multiple users. The developer is a key player here; we design their experience, which sometimes gets overlooked."**

The day-68 development model named several agent roles (developer, AppSec, QA, architect) and this batch added the accountant agent. The designer is the role that was missing, and it is essential precisely because the UX-across-personas work needs dedicated design ownership, not ad-hoc UI decisions made by developers.

The designer's responsibilities:

| Responsibility | Detail |
|----------------|--------|
| **Design the per-persona experience** | The developer's, QA's, pen-tester's, business-owner's distinct experiences |
| **Design the onboarding flow** | Adding SG/Sentinel to an app (see below) |
| **Design the visualisations** | What each persona sees; the data-set-to-visual mapping |
| **Champion the developer experience** | The developer is a key player whose experience is often overlooked |
| **Ensure complexity is removed, not added** | The UX north star |

The voice memo singled out the developer experience as the one that gets overlooked: **"the developer is a key player here; we design their experience, which sometimes gets overlooked."** The designer's first duty is to make the developer's experience of adding and understanding SG/Sentinel genuinely good, because the developer is the gateway: if adding Sentinel is hard, it does not get added.

## The Add-Sentinel-To-An-App Onboarding Flow

The voice memo described a concrete onboarding flow, which is the developer persona's primary experience and deserves explicit design. When a developer wants to add SG/Sentinel to an app:

| Step | What The Developer Checks / Does |
|------|----------------------------------|
| **Which mode?** | What mode is Sentinel in for this app? |
| **Is CloudFront configured?** | Is the infrastructure in place? |
| **Is the code correct?** | Is the deployed code right? |
| **Is the code locally correct?** | Does it work locally (the local-everywhere check)? |
| **Simulate traffic** | Run simulated traffic to see the behaviour |
| **Implement** | Wire it in, confident it works |

The voice memo: **"if I want to add SG/Sentinel to an app, can I check which mode it is, is CloudFront configured, is the code correct, is the code locally correct, and then simulate traffic and implement this?"**

This is the health-checks-abstract-complexity principle applied to onboarding: the developer does not manually verify each piece; the onboarding flow checks them and visualises the state. The developer sees green/amber/red across the pieces (mode, CloudFront, deployed code, local code, simulated traffic) and knows exactly what is and is not ready. This is app-specific (each app's onboarding differs), but the flow and the checks are consistent.

This connects to the local-everywhere and deploy-parity principles (cross-ref: the interactivity and delegation briefs): the "is the code locally correct?" check is the local-everywhere property surfaced as an onboarding step. The developer confirms local correctness, then deploys, with deploy-parity guaranteeing they match.

## The Logging And Visibility Value, Per Persona

The voice memo returned to the visibility theme (established in day-68) but with a UX framing: **providing visibility into what happens to an app in ways that currently do not exist is a primary value, and the UX must surface it per persona.**

The voice memo: **"the logging is also quite important. Being able to provide visibility to what happens to an app in ways that currently don't exist is very important, which is why the design element of all this matters."**

The new UX angle: the visibility is not just raw logs; it is designed insight per persona. For a developer, the visibility surfaces bugs and optimisation opportunities. For a business owner, it surfaces the business value (faster app, fast-tracked users). For an AppSec engineer, it surfaces the security posture. The same underlying visibility (cross-ref: the over-index-on-visibility emphasis in the test-driving brief), designed into the right view for each persona.

A specific UX capability the voice memo named: **proactive gap detection.** The voice memo: **"we can monitor traffic and say, by the way, there's a gap between here, the traffic is not hitting here."** SG/Sentinel can surface not just what is happening but what is *not* happening: traffic that should be flowing but is not, a gap in the expected flow. This is a designed insight (the system tells you about a gap) rather than raw data (you find the gap yourself). It is the complexity-removal principle in action: the system does the noticing.

## The Acid Test: Teams Write Their Own Tests With Sentinel Primitives

The most important new idea, and the clearest success signal: **we know SG/Sentinel has truly succeeded when dev and QA teams start using its primitives to write their own integration tests, for their own apps, outside of security.**

The voice memo: **"the ultimate acid test that we know this is working is if the dev teams and QA teams start using some of our primitives to write tests, to write integration tests for their own app. That means that when they add a new feature, they already use SG/Sentinel as a way to add capabilities and add testing to what they're doing."**

This is a profound success metric, and it is genuinely new. It says: SG/Sentinel has succeeded not when it blocks attacks, but when developers adopt its primitives for their own non-security purposes, because the primitives are good enough and usable enough that teams reach for them naturally.

The virtuous cycle this creates:

1. Teams use SG/Sentinel primitives to write integration tests for their features.
2. In doing so, they validate behaviour outside of security (their feature works as expected).
3. This means they are **providing context, metadata, and business-logic information to SG/Sentinel** as a side effect of writing their tests.
4. That context makes SG/Sentinel smarter about what valid traffic looks like (the known-good profile, cross-ref: the no-invalid-request principle).
5. The more teams use it, the better its understanding of the app, the better its protection.

The voice memo: **"that means they're already validating stuff even outside of security, which is a great way for them to start providing context and metadata and business logic information to SG/Sentinel."** This is the app-coupling principle (cross-ref: the MVP brief's app-coupled WAF) achieved through adoption: the coupling is not imposed; it emerges because teams use Sentinel's primitives and thereby tell it what their app does.

And the voice memo noted the LLM accelerant: **"this is where the LLMs can help, because they can help do a lot of this development and customisation."** The LLM-assisted development (cross-ref: the rules-engine brief) lowers the barrier: teams do not have to hand-write the test primitives; the LLM helps them, so adoption is easier, so the acid test is reached sooner.

The acid test reframes the whole UX effort: **the UX is not done when SG/Sentinel is usable; it is done when teams choose to use it for things beyond security, because it is that good.** That is the bar.

## What This Asks For

Concrete next steps:

1. **Bring a designer onto the project**, owning the per-persona experience.
2. **Make complexity-removal the UX north star** (adding Sentinel makes operating an app simpler, not harder).
3. **Design the per-persona experiences** (developer, QA, pen-tester, AppSec, business owner), each with the right visualisation and data set.
4. **Design the add-Sentinel-to-an-app onboarding flow** (mode, CloudFront, code, local code, simulate, implement), abstracting complexity behind checks.
5. **Champion the developer experience** specifically (the gateway persona, often overlooked).
6. **Build proactive gap detection** (the system tells you traffic is not hitting where it should).
7. **Surface visibility per persona** (the same data, designed into each persona's view).
8. **Target the acid test** (teams using Sentinel primitives for their own integration tests).
9. **Use LLMs to lower the adoption barrier** (help teams write the primitives, customise, adopt).

Estimated effort: the designer role is a hiring/assignment decision; the per-persona experiences and onboarding flow are a design-then-build effort; the acid test is a long-term success signal, not a build task.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a redesign of the day-68 work.** It adds the design discipline and personas.
- **Not one dashboard for everyone.** Each persona gets a designed experience.
- **Not a claim that UX is secondary to security.** The acid test makes UX the primary success signal.
- **Not a replacement for the operator TUIs.** Those are one persona's view; this adds the others.

## Honest Risks

Three risks:

**Risk 1: Designing for many personas could fragment the effort.** Mitigation: the personas share underlying data (evidence graph, logs, rule state); the designer ensures a coherent design language across views; start with the developer persona (the gateway).

**Risk 2: The acid test is a high, long-term bar that could feel discouraging early.** Mitigation: it is a north star, not a near-term gate; intermediate signals (developers adding Sentinel easily, finding the visibility useful) mark progress toward it.

**Risk 3: Removing complexity is hard; the abstraction could leak.** Mitigation: the health-checks-and-visualisation approach is proven elsewhere in the project; when the abstraction leaks, the checks surface exactly what is wrong, so the developer is never stuck.
