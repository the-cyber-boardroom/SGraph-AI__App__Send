## What This Is

The second brief of the SG/Sentinel implementation batch, developing a topic the day-68 corpus flagged but never built out: **cost.** Cost was the founding motivation for SG/Sentinel (CloudWatch/Firehose expensive, AWS WAF rent-like), and the path-to-MVP brief named "the concrete cost model" as a memo worth recording. This brief is that development, and it goes further than a cost model: it introduces **the accountant agent as the owner of cost attribution, billing as a fundamental structural piece, cost-as-benchmark, and the Wardley-mapping of control flows and cost flows together.**

The core principle: **every single action, request, stream, and end-to-end processing has a cost, and we should know it.** How much are bots costing us? How much does a valid request cost? How much does a given user cost? How much does each layer (1, 2, 3) cost, including LLM costs? Cost is not an afterthought to be estimated later; it is attributed per-action, structurally, from the start.

This is genuinely new relative to the day-68 corpus. The corpus established that SG/Sentinel is cheaper than the Firehose+WAF baseline (the de-commoditising and principles briefs) but never said how cost is attributed, measured, or turned into decisions. This brief assigns that work to the accountant agent and makes cost a first-class flow alongside control.

## The Accountant Agent Owns Cost

The day-68 development model named several agents (developer, AppSec, QA, architect). This brief adds another to the SG/Sentinel context: **the accountant agent, whose job is cost attribution and analysis.**

The voice memo: **"we need to involve the accountant agent on this. The accountant has a massive piece of work done here, so we can track every single cost, every single request, every single element."** Cost attribution is substantial, ongoing work, and it deserves a dedicated agent role the way security deserves the AppSec agent.

The accountant agent's responsibilities:

| Responsibility | Detail |
|----------------|--------|
| **Per-action cost attribution** | Assign a cost to every action, request, stream, and processing step |
| **Per-category cost analysis** | How much do bots cost? valid requests? a given user? |
| **Per-layer cost tracking** | Layer 1, Layer 2, Layer 3 costs separately |
| **LLM cost tracking** | Every model call (Nova, OpenRouter, open-source) carries a cost |
| **Cost benchmarking** | Our measured cost vs other WAFs and logging solutions |
| **Cost-driven decisions** | When is always-on cheaper than on-demand? (see below) |

This connects to the broader accountant-agent direction from earlier in the project (the next-generation-accountant work from day 67), now applied internally: the same agentic-accounting capability that serves customers serves our own cost attribution. We dogfood the accountant agent on SG/Sentinel's costs.

## Every Action Has A Cost

The foundational principle: **every single thing SG/Sentinel does has an attributable cost, tracked from the start.**

The voice memo: **"every single action, every request, every stream, every processing end-to-end should have a cost. We should know how much bots are costing us, how much valid requests are costing, how much the user is costing us."**

The cost attribution spans every dimension:

| Dimension | Cost Attributed |
|-----------|-----------------|
| **Per request** | The full cost of handling one request, end to end |
| **Per traffic type** | Bots vs valid requests vs malicious vs flagged |
| **Per user / fingerprint** | What a given user (or fingerprint) costs to serve |
| **Per layer** | Layer 1 (CloudFront Function), Layer 2 (Lambda@Edge), Layer 3 (async/compute) |
| **Per LLM call** | Every model invocation: Nova, OpenRouter, open-source, whatever we use |
| **Per stream / processing** | Logging delivery, evidence-graph building, async analysis |

The LLM-cost point is worth emphasising because it is easy to overlook: the voice memo was explicit that **every LLM call carries a cost, regardless of provider.** Whether it is Nova (cheap, fast), an OpenRouter call, or a self-hosted open-source model, each invocation has a cost, and the accountant agent tracks it. This matters because the day-68 design leans on LLMs for the async analysis (Layer 3, rule generation, evidence building); those LLM costs must be attributed, not hidden.

This connects to the time and rule-architecture briefs: each rule, at each layer, on each timeline, has a cost. The fractal rule graph (rule-architecture brief) traversal has a cost per rule traversed. The async analysis (time brief) has a cost per LLM call. The accountant agent attributes all of it.

## Billing As A Fundamental Piece

A structural point the voice memo made: **billing is a fundamental piece of the entire puzzle, and it always takes a cut wherever it runs.**

The voice memo: **"billing has to be a fundamental piece of the entire puzzle, and the billing always has to take a cut wherever you're running."** This is a strong framing: cost tracking is not a reporting layer added afterward; it is woven into the execution itself. Wherever SG/Sentinel runs (Layer 1, Layer 2, Layer 3, the reverse proxy on bare EC2), the cost is tracked at that point.

The implication for the architecture: **cost attribution is instrumented into every layer's execution, not computed after the fact from logs.** Each layer, as it processes a request, records the cost of that processing. The cost flows alongside the request (and into the log that lands in S3), so cost is known per-request in real time, not estimated later.

This connects to the IDs-everywhere principle (the rule-architecture brief): the request ID that traces a request through the layers also accumulates the request's cost. By the time the request's log lands in S3, it carries both its verdict and its cost. **The request ID ties together the lifecycle and the cost.**

## Cost-As-Benchmark

The most strategically interesting point: **our measured per-action cost becomes the benchmark against which we evaluate other WAFs, logging solutions, and our own infrastructure choices.**

The voice memo: **"especially when you look at mapping other WAFs and other logging solutions, this becomes our benchmark. We can have a situation where we say it's actually cheaper for us to run an EC2 instance all the time, or in certain periods, and that should have a particular cost."**

This is the founding cost argument (SG/Sentinel is cheaper than Firehose+WAF) made rigorous and data-driven. Once we attribute cost per-action precisely, we can:

- **Compare to alternatives with real numbers.** Not "we think Firehose is expensive" but "Firehose costs X per million events; SG/Sentinel costs Y; here is the difference." The de-commoditising argument (cross-ref: the de-commoditising article) becomes quantified.
- **Make infrastructure decisions on data.** The voice memo's example: is it cheaper to run an EC2 instance always-on, or on-demand (the ephemeral-provisioning model)? With per-action cost, we can answer precisely, per workload, per period. Some workloads may be cheaper always-on; others on-demand. The data decides.
- **Benchmark our own choices over time.** As we gain experience, we know exactly what it costs to run on EC2, on Lambda, on CloudFront, with each LLM. The accumulated cost data becomes a decision-making asset.

The voice memo's framing: **"with experience, we start to know exactly how much money it costs to run on EC2, how much on certain properties."** This experiential cost knowledge is a competitive advantage: we can make build-vs-buy and always-on-vs-on-demand decisions with precision that vendors using opaque pricing cannot match. **Cost-as-benchmark turns the founding cost intuition into a measured, decision-driving capability.**

This connects to the always-on-vs-on-demand tension from the ephemeral-provisioning work (day 66): the cost data tells us, per workload, which is cheaper. And it connects to the compliance-graph's per-deployment view (compliance brief): the per-deployment picture now includes per-deployment cost.

## Wardley-Mapping Control Flows And Cost Flows

The voice memo introduced a framing that ties cost to the broader architecture: **map the control flows and the cost flows together, as a Wardley map.**

The voice memo: **"cost and control flows, and cost flows. The graph is almost like the map of this, the Wardley map of this. We need to have a mapping of what the control flows are that we're executing and how we implement the whole flow."**

Two kinds of flow, mapped together:

| Flow | What It Maps |
|------|--------------|
| **Control flow** | How a request moves through the layers and rules; what decides what; the execution path |
| **Cost flow** | How cost accumulates along that path; what each step costs; where the money goes |

These are two views of the same journey. A request follows a control flow (Layer 1 rules to Layer 2 validation to the application, or blocked along the way); along that same path, cost accumulates (the Layer 1 execution cost, the Layer 2 cost, any LLM cost). **The cost flow is the control flow with money attached.**

The Wardley-map framing adds the evolutionary dimension: mapping the control and cost flows on a Wardley map shows not just what costs what, but how each component sits on the commodity-to-custom spectrum, and therefore where cost is genuine value (the custom shield) versus where it is commodity attrition (the rent-like services we are replacing). This connects directly to the de-commoditising article (day 67): the Wardley map of cost flows shows precisely where SG/Sentinel removes commodity attrition and where it adds custom value.

For the implementation, this means: **the control-flow map (the rule graph traversal, the layer sequence) and the cost-flow map (the cost accumulated at each step) are built together, as one mapping of how the whole flow works and what it costs.** The visibility surfaces (the TUI mockups) should show both: what is happening (control) and what it costs (cost), on the same view.

| The rule graph traversal | Per-rule cost (cost of each rule traversed) |
| The async LLM analysis (Layer 3) | Per-LLM-call cost (Nova, OpenRouter, open-source) |
| IDs everywhere | The ID accumulates cost alongside lifecycle |
| The S3 log | The log carries cost as well as verdict |
| The TUI surfaces | Show cost alongside traffic |
| The compliance per-deployment view | Now includes per-deployment cost |
| The ephemeral-provisioning always-on-vs-on-demand question | Decided by per-workload cost data |

Cost is a dimension added to the existing flows, owned by the accountant agent, not a new subsystem. The control flow is unchanged; the cost flow is instrumented onto it.

## What This Asks For

Concrete next steps:

1. **Introduce the accountant agent** into the SG/Sentinel development and operation, owning cost attribution.
2. **Instrument per-action cost** at every layer (cost recorded as the request is processed, not estimated later).
3. **Attribute cost per traffic type** (bots, valid, malicious, flagged) and per user/fingerprint.
4. **Track LLM costs per call** (Nova, OpenRouter, open-source), attributed to the rule/analysis that invoked them.
5. **Make billing structural** (cost tracked wherever SG/Sentinel runs, including the bare-EC2 reverse proxy).
6. **Tie cost to the request ID** (the ID accumulates cost; the S3 log carries it).
7. **Build cost-as-benchmark** (compare to Firehose/WAF with real numbers; quantify the de-commoditising argument).
8. **Build the always-on-vs-on-demand cost decision** (per-workload data decides).
9. **Map control flows and cost flows together** (the Wardley map of the whole flow and its cost).
10. **Surface cost in the TUI** (what is happening and what it costs, on the same view).

Estimated effort: the per-action cost instrumentation is woven into the layer implementation (so it is part of the MVP build, not a separate project); the accountant agent and cost-as-benchmark analysis build on the accumulated cost data; the Wardley mapping is an analysis layer.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a new subsystem.** Cost is a dimension instrumented onto the existing flows.
- **Not customer billing (yet).** This is internal cost attribution; customer billing (if SG/Sentinel becomes a product) builds on it.
- **Not a replacement for AWS billing.** It attributes our costs at finer granularity than AWS billing provides, using AWS costs as input.
- **Not a redesign of the control flow.** The cost flow is instrumented onto the unchanged control flow.

## Honest Risks

Three risks:

**Risk 1: Per-action cost instrumentation could itself add cost and latency.** Tracking cost at every step has overhead. Mitigation: the instrumentation must be lean (especially at Layer 1, sub-ms); record cost cheaply (a counter, not a computation); aggregate async where possible.

**Risk 2: Cost attribution could be approximate and misleading.** Attributing shared costs (an always-on instance serving many requests) per-request involves allocation choices. Mitigation: be honest about what is measured vs allocated; the accountant agent documents the attribution model; benchmark comparisons use like-for-like.

**Risk 3: LLM costs could surprise.** The async LLM analysis could run up costs if not bounded. Mitigation: per-LLM-call cost tracking surfaces this immediately; the LLM-minimal-in-prod principle (rules-engine brief) bounds it; Nova (cheap) for most analysis.
