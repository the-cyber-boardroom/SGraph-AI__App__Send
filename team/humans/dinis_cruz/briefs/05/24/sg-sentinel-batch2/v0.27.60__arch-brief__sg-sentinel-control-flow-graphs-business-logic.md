## What This Is

The fourth brief of the SG/Sentinel implementation batch, capturing a substantial architectural idea from the project lead's notebook: **shared state between Layer 2 and the application, used to build control-flow graphs that enforce business logic.** This solves what has always been the Achilles heel of WAFs: they can do technical checks but cannot make business-logic decisions. SG/Sentinel can, because Layer 2 shares state with the app it protects and understands what should happen next.

The core idea: **the universe of what is possible should be determined by the current state of the user's current action, not by all the possibilities the application technically allows.** Most vulnerabilities occur because actions are executed out of sequence, or capabilities are invoked when they should not be. If SG/Sentinel knows the control flow (this action can only follow that action), it dramatically reduces the universe of exploitability, removes much of what attackers can do, and detects attackers far better.

This is genuinely new relative to the corpus. The day-68 briefs touched sequence rules (the time brief noted "certain files should follow a particular sequence") and the no-invalid-request principle (the execution-model brief), but neither developed the Layer-2-shares-state-with-the-app mechanism, the control-flow-graph model, or the business-logic-enforcement claim. This brief does.

## Layer 2 Shares State With The Application

The foundational mechanism: **Layer 2 can read and write to disk and make network calls, so it can talk directly with the application it protects.** This is what makes everything else possible.

The voice memo distinguished the layers carefully: **"this is not Layer 1, because Layer 1 can only talk to Layer 2. This is Layer 2 and the main application. Layer 2 is still running in real time, but Layer 2 can read and write to disk and make network calls, so it can literally talk with the app that it is protecting."**

This is a capability the execution-model brief established (Layer 2 has network and file access) but did not exploit for this purpose. The new use: **Layer 2 maintains shared state with the application, so it knows not just what a request looks like, but where the user is in their journey through the app.**

The shared state enables control-flow graphs: a representation of the current state of a particular action, used to define and control what can and should happen next.

## Control-Flow Graphs: The Current State Determines The Possible

The central concept: **a control-flow graph represents the current state of a user's action, and it determines the universe of what is possible next, narrowing it from "everything the app technically allows" to "what should happen next given where the user is."**

The voice memo: **"the universe of what's possible should be determined by the current state of affairs, the current state of the current action of that particular user, not necessarily by all the possibilities that are possible on the application."**

This is a profound narrowing. A normal application exposes its full surface to every request: any endpoint, any action, in any order. The control-flow graph says: given that this user has done X, only Y and Z should be possible next; everything else is, by definition, out of sequence and suspect.

| Without Control-Flow Graphs | With Control-Flow Graphs |
|-----------------------------|--------------------------|
| Every action available to every request, any order | Only the actions valid from the current state |
| The full app surface is the attack surface | The attack surface is the current state's valid transitions |
| Out-of-sequence actions are allowed | Out-of-sequence actions are blocked |
| The WAF cannot know what should happen next | Sentinel knows, because it shares state with the app |

### Hyper-Jumps: The Vulnerability Pattern

The voice memo named the vulnerability pattern this defends against: **hyper-jumps, where an attacker executes an action out of sequence, or invokes a capability that should not be available at that moment.**

The voice memo: **"most vulnerabilities occur because of that, because you literally are executing stuff out of sequence, or you're invoking capabilities that should not be invoked at that moment in time. We call this hyper-jumps. If we say that this action can only be invoked after that action, you dramatically reduce the universe of exploitability."**

A hyper-jump is the attacker skipping the legitimate flow: jumping straight to a privileged action without the preceding steps, accessing a resource without the prior authorisation step, invoking an admin capability without the admin context. These are some of the most common and serious vulnerability classes (broken access control, insecure direct object references, business-logic flaws). The control-flow graph blocks them by construction: **if the action requires a preceding state the user does not have, it is blocked, regardless of how technically well-formed the request is.**

This connects to the no-invalid-request principle (cross-ref: the execution-model brief), but goes deeper. No-invalid-request blocks structurally invalid requests (wrong endpoint, malformed). The control-flow graph blocks *sequentially* invalid requests (right endpoint, right shape, wrong moment). Together they cover both structural and sequential validity. **A request must be valid in shape AND valid in sequence.**

## Detect When The Attacker Makes A Mistake (Extending, Not Repeating)

The voice memo restated an idea the day-68 corpus established (the time brief's detect-before-damage, the delegation brief's no-404s signal), so this brief references rather than repeats it, but adds a sharpening worth capturing.

The sharpening: **the more we know our control flows, the easier it is to detect attackers, because the control-flow graph turns every out-of-sequence action into a detectable mistake.** The voice memo: **"the more we understand how the app is supposed to work and how it is supposed to be used, the easier it will be to detect attackers and bugs."**

The voice memo also reframed the classic attacker-defender asymmetry sharply: **"this is the inverse of the idea that defenders have to defend everything and attackers only have to find one thing. The reality is that once attackers exploit something, there are ten things that failed, ten controls, ten monitoring points that should have picked it up."** The control-flow graph is several of those ten: every out-of-sequence step an attacker takes is a mistake the graph catches. The attacker does not have to make one mistake; the control-flow graph ensures they make many, each detectable.

This is the detect-when-the-attacker-makes-a-mistake principle (cross-ref: the time brief) given a concrete mechanism: the control-flow graph is what makes the attacker's out-of-sequence actions into detectable mistakes.

## The Application Defines What Should Happen Next

The mechanism for building the control-flow graph: **the application defines what should happen next, using predefined schemas and predefined workflows.** SG/Sentinel does not infer the control flow; the application declares it.

The voice memo: **"the application defines what should happen next, using predefined schemas and predefined workflows."** This is the app-coupling principle (cross-ref: the MVP brief's app-coupled WAF) applied to sequence: the app tells Sentinel not just what valid requests look like (the known-good profile) but what valid *sequences* look like (the control-flow graph). The app is the source of truth for its own business logic, and it codifies that logic as schemas and workflows Sentinel enforces.

This is also where the acid test (cross-ref: the UX brief) pays off: when teams write integration tests with Sentinel primitives, they are codifying their app's workflows, which is exactly the control-flow-graph information Sentinel needs. The control-flow graph is built as a side effect of teams describing their app's expected behaviour.

## Sentinel Can Make Business-Logic Decisions: The WAF Achilles Heel Solved

The headline claim, and a genuinely significant one: **SG/Sentinel can make business-logic decisions, which has always been the Achilles heel of WAFs.**

The voice memo: **"this means SG/Sentinel can actually make business-logic decisions, which has always been one of the Achilles heels of WAFs. They can do a lot of technical stuff, but they cannot do business logic. Now we can, because if we understand what should happen next, if we understand the business logic of the application, we can enforce and protect key paths that require specific valid state to be executed."**

This is the differentiator. Traditional WAFs operate at the technical level: they detect SQL injection, XSS, malformed requests, known-bad patterns. They cannot enforce business logic (you must complete step A before step B; only the account owner may perform this action; this transaction requires this prior authorisation) because they have no knowledge of the application's business logic. They are blind to it.

SG/Sentinel is not blind, because:

- Layer 2 shares state with the app (it knows where the user is).
- The app defines the control-flow graph (it knows what should happen next).
- So Sentinel can enforce business-logic rules (block the action that requires a state the user does not have).

The voice memo's framing of the payoff: **"we can enforce and protect key paths that require specific valid state to be executed. We can protect business-logic decisions because we can enforce and protect key paths that require specific valid states."**

This connects to the explainability and determinism themes (cross-ref: the rules-engine brief): the control-flow graph is deterministic and explainable. When Sentinel blocks a business-logic violation, the reason is clear and inspectable: "this action requires state X, which the user does not have." The voice memo: **"this plays really well into the whole deterministic and explainability of what is actually happening."** Business-logic enforcement is not a black-box judgement; it is a deterministic check against a declared control-flow graph, with a clear reason.

### Why This Matters Strategically

Business-logic enforcement is the capability that most distinguishes SG/Sentinel from every existing WAF. The technical checks (injection, XSS) are table stakes that the CRS rules (cross-ref: the research brief) already provide. The business-logic enforcement is the differentiation no commodity WAF can match, because no commodity WAF shares state with the app it protects. This is the de-commoditising shield (cross-ref: the de-commoditising article) at the business-logic layer: the custom value that the commodity cannot replicate.

## Used For Bugs, Not Just Security

The voice memo reinforced a theme that runs through the corpus (the developer-friendliness brief, the delegation brief's hostile-to-our-own-apps): **the control-flow graph is for bugs, regression tests, and normal development, not just security.**

The voice memo: **"it's very critical that we always have this thing where we can use this for bugs and for problems and for regression tests and for normal development workflow things, instead of security."** A control-flow graph that catches an attacker's hyper-jump also catches a bug that causes the app to execute actions out of sequence. The same mechanism serves both: it is a correctness check (the app is behaving in valid sequence) as much as a security check. This is the acid test (cross-ref: the UX brief) again: teams adopt the control-flow graph because it catches their bugs, and in doing so they give Sentinel the business-logic knowledge that makes it a better security tool.

## What This Asks For

Concrete next steps:

1. **Build Layer 2 shared state with the application** (read/write/network to maintain per-user-action state).
2. **Build the control-flow-graph model** (represent the current state of an action; define valid transitions).
3. **Let the application define the control flow** (predefined schemas and workflows declaring what should happen next).
4. **Enforce sequential validity** (block hyper-jumps: actions requiring a state the user does not have).
5. **Make business-logic blocks deterministic and explainable** (clear reasons: requires state X).
6. **Use the control-flow graph for bugs and regression** (correctness as well as security).
7. **Build the control-flow graph from the acid-test codification** (teams describing their app's workflows).

Estimated effort: the Layer 2 shared-state mechanism is foundational and substantial; the control-flow-graph model builds on it; business-logic enforcement is the payoff. This is post-MVP work (the MVP proves the core; this adds the business-logic layer), but the Layer 2 shared-state mechanism should be designed MVP-aware so it is not retrofitted.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a Layer 1 capability.** Layer 1 talks only to Layer 2; this is Layer 2 sharing state with the app.
- **Not inferred control flow.** The app declares the control flow; Sentinel does not guess it.
- **Not a replacement for app-level authorisation.** It enforces sequence at the edge as defence in depth; the app still enforces its own authorisation.
- **Not in the first MVP.** It is post-MVP, but the Layer 2 shared-state design should anticipate it.

## Honest Risks

Three risks:

**Risk 1: Maintaining shared state at Layer 2 adds latency and complexity.** Layer 2 runs in real time; shared state with the app could slow it. Mitigation: the state is cached and scoped; the control-flow check is a fast lookup against the current state, not a heavy computation; measure.

**Risk 2: The control-flow graph could become stale or wrong as the app evolves.** If the declared control flow diverges from the actual app behaviour, legitimate sequences get blocked. Mitigation: the app declares the control flow as a deploy artefact (cross-ref: the symmetry principle and the tabletop GAP 5.1 resolution); observe-mode first; the acid-test codification keeps it current.

**Risk 3: Business-logic enforcement at the edge could duplicate or conflict with app-level logic.** Mitigation: the edge enforces the declared control flow as defence in depth; the app remains the authority; the two are co-designed (the app declares, the edge enforces).
