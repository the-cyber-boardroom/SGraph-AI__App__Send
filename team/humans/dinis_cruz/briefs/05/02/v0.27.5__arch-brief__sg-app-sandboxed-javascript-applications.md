## Context for the Spec Team

This brief captures the project lead's vision and design intent from a voice memo recorded after reviewing the v0.1 SG/App spec (the `00__overview.md` document). The spec is on the right track. This brief adds strategic context, clarifies priorities, confirms design decisions, and expands on use cases that should inform the implementation.

The SG/App spec team should read this alongside their existing spec. Where this brief and the spec align, the spec has correctly interpreted the intent. Where this brief adds new considerations, those should be folded into the next spec revision.

## The Core Realisation

This started as "let me add write access to vault HTML pages." But as the spec took shape, three things became clear:

1. **This is not vault-specific.** The app framework is storage-agnostic. The vault is one storage backend. localStorage, IndexedDB, a remote API, even a Chrome extension's local storage could all serve the same role. The framework should not know or care what is underneath.

2. **This is not a feature. It is a platform.** What we are building is a runtime for sandboxed mini-applications that communicate with their host via a messaging protocol, with policy-controlled access to storage and capabilities. This is bigger than "vault write from an iframe."

3. **This solves the tool integration problem.** The tools ecosystem (infographic generator, LLM chat, video recorder, etc.) has always struggled with interconnection. If each tool is an SG/App with a defined capability surface and a messaging protocol, they can coexist on the same page, share data through the host, and be policy-controlled independently.

## The Name: SG/App (or JS App)

The voice memo explored "JS App" as a name (JavaScript Application). The spec team landed on "SG/App" which is better: it is branded, it does not conflict with the generic "JS app" that means anything, and it follows the SG/Send naming convention.

**Confirmed: SG/App is the name.**

## Design Decisions Confirmed

The following decisions from the spec are explicitly confirmed by the project lead:

### 1. The iframe is maximally locked down

The iframe cannot load anything, cannot access anything, cannot reach the network. It can run JavaScript. That is it. All capabilities come through the messaging protocol. The app asks the runtime for everything: files, data, network access (if ever permitted), storage. The runtime decides.

**This is the security model.** The iframe is user-mode. The runtime is kernel-mode. The separation is the entire story.

### 2. Storage-agnostic (vault is one provider, not THE provider)

The app calls `sg.vfs.read('data.json')`. It does not know whether the file comes from a vault, from localStorage, from IndexedDB, or from memory. The runtime decides which provider to use at mount time.

**Practical consequence confirmed:** Build and test everything against the in-memory provider first. The vault provider comes later. This is how the MVP ships before vault-write is fully implemented.

### 3. Manifest declares, runtime enforces

The `app.json` manifest is a contract. It declares exactly which files the app can read, which it can write, which capabilities it uses. The runtime enforces these declarations. An app that accesses a file not in its manifest gets a denial, and the denial is logged.

**The project lead's emphasis:** This is not just security. It is auditability. A reviewer reads `app.json` and knows exactly what the app can do without reading the source code. This is the trust primitive that makes SG/Apps safe to distribute.

### 4. Visibility is a first-class capability (not a debugging afterthought)

Every capability call generates a structured event. Every event flows through the bus. The user can open a panel and see exactly what the app is doing: files read, files written, denials, timing.

**The project lead's framing:** This is not a developer tool. It is a trust artefact. The user verifies, at runtime, that the app is behaving as the manifest claimed. This is how we solve the "do I trust this app?" problem without requiring the user to read code.

### 5. Multiple apps on the same page, mutually isolated

Each SG/App is an iframe. Multiple apps can coexist on one page. Each has its own sandbox, its own bridge, its own scoped VFS. They cannot see each other. If they need to communicate, they go through the host, which mediates, logs, and policy-checks.

**The project lead's vision:** A page with an LLM chat app, a data capture form app, and a visualisation app, all running side by side, each with different permissions, each isolated, all sharing data through the host's mediation layer.

## Use Cases That Should Inform the Spec

### Use Case 1: Slide Deck Viewer/Editor (The Original Trigger)

A vault contains presentation slides. An SG/App renders them as an interactive slide deck. The app has read access to the slide files and write access to save annotations or edits.

Manifest permissions: `read: slides/*.md, slides/*.svg`, `write: slides/annotations.json`

### Use Case 2: Healthcare Data Capture (The High-Value Case)

A medical data capture form running inside a vault. The patient fills in health data. The app writes the data to the vault. The patient sends the vault to their doctor. The doctor opens the same vault with a different app (a viewer, not an editor) that has read-only access.

Manifest permissions (patient app): `read: form-schema.json`, `write: patient-data.json`
Manifest permissions (doctor app): `read: patient-data.json, form-schema.json`, `write: none`

This is the healthcare MVP from 17 Apr, now implementable through the SG/App framework.

### Use Case 3: LLM Chat Inside a Vault

An SG/App that provides an LLM chat interface. The app can read documents from the vault (to provide context to the LLM) and write conversation logs back. The app needs network access to the LLM API (OpenRouter).

Manifest permissions: `read: documents/*`, `write: conversations/*.json`, `network: api.openrouter.ai`

This is the tools integration solved properly: the LLM app is sandboxed, its network access is declared and enforced, and the conversation data is saved to the vault.

### Use Case 4: Decision Capture (Risk Acceptance)

The risk acceptance workflow from 21 Apr, now as an SG/App. A form captures the decision, the reasoning, the approval. The app writes structured data (JSON) to the vault. The approval tree visualisation is another SG/App on the same page, reading the same data with read-only permissions.

### Use Case 5: Interactive Evidence Pack

An evidence pack vault where one of the files is an SG/App that provides interactive exploration of the evidence: filter, search, cross-reference, annotate. The app reads all evidence files and writes annotations. The annotations are saved to the vault and become part of the evidence pack.

## What the Spec Should Add (Recommendations)

Based on the voice memo, the following should be considered for the spec:

### 1. Event Types That Can Propagate Out

The spec mentions `sg.host` for two-way messages (out of scope for v0.1). The project lead wants this scoped but not deferred entirely. At minimum, define the event types that an app can emit to the host, even if v0.1 only supports a small set (e.g. `app.ready`, `app.error`, `app.requestFocus`, `app.dataChanged`).

### 2. Network Access as a Declared Capability

The spec correctly blocks all network access by default. The project lead agrees. But the manifest should have a `network` field that can declare allowed origins:

```json
{
  "capabilities": {
    "network": {
      "allowed_origins": ["api.openrouter.ai"]
    }
  }
}
```

For v0.1, this field exists in the schema but is not enforced (all network access remains blocked). This sets up the schema for v0.2 without implementing the proxy layer yet.

### 3. The Runtime as a Brokering Layer for Network

When network access is eventually enabled, the project lead prefers that the runtime brokers the request (the app sends a message to the runtime, the runtime makes the fetch, the runtime returns the response) rather than allowing the iframe's CSP to permit direct access. This keeps all network traffic visible in the event bus and loggable.

### 4. App Identity and Tokens

Each SG/App can optionally have an identity (an app ID, a version, and eventually a token). This enables: apps that authenticate to external services via the runtime (the app does not hold the secret, the runtime injects it, similar to the MITM proxy secret injection pattern from the VNC brief).

### 5. Auto-Commit as a Storage Provider Feature (Not an App Feature)

The voice memo noted that auto-commit (saving to vault on every write) should not be an app concern. The app calls `sg.vfs.write()`. Whether that triggers a vault commit is the provider's decision, not the app's. The vault provider can be configured to auto-commit, batch commits, or require explicit commits. The app does not know.
