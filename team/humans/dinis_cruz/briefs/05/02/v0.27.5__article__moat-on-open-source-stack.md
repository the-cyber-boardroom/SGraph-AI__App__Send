# So If You Open Source Your Code, What Is Your Moat?

Short answer: the same moat every good software company has. We ship faster, we compound knowledge, and we provide a service that people pay for because it solves their problem better than doing it themselves.

The code being open source does not change any of that. It never has for any company that understood what they were actually selling.

---

## The moat is not the code. It never was.

Redis is open source. MongoDB is open source. Elastic is open source. Terraform is open source. Every one of them built billion-dollar businesses. Not because they hid their code, but because they were better at running, improving, and supporting the thing than anyone else.

Our encryption is AES-256-GCM. It is a standard. Our key derivation is PBKDF2. Also a standard. The vault protocol, the CLI, the rendering components: all open source. Anyone can read them, fork them, deploy them.

What they cannot fork is the team that ships 10 features a week. They cannot fork the operational knowledge we have accumulated running this in production. They cannot fork the customer relationships, the trust, or the fact that we have already solved the next three problems they are about to discover.

---

## Execution velocity is the moat

Here is what a typical week looks like for us.

We have multiple AI agents collaborating on the product simultaneously. A content agent creates documentation and pushes it to a vault. A developer agent picks up the brief, implements the code, pushes to a QA branch, takes automated screenshots to verify the change, and notifies the content agent that the feature is live. A third agent monitors the communication and reports status. All of this happens through vaults, the same technology we sell.

The result: we move from voice memo to production feature in hours, not weeks. A single briefing session produces a dozen implementation-ready specifications. Those specifications go to developer agents who implement, test, and deploy them the same day.

This is not a theoretical workflow. The website you are reading right now was built this way. The content on this page was created by an agent, reviewed by another agent, rendered from an encrypted vault, and deployed through an automated pipeline. The agents communicated via file-based email inside a vault. The screenshots were taken by a Playwright automation container and committed to the same vault.

A competitor who forks our code gets a snapshot. We are already three sprints ahead by the time they finish reading the README.

## What compounds (and cannot be forked)

### Operational knowledge

We run vaults in production. We know which S3 configurations cause latency spikes. We know how to tune the Lambda cold start. We know that CloudFront cache invalidation takes 47 seconds, not the "up to 10 minutes" the docs say. We know that tree-only vault loading drops page render from 6 seconds to 1 second. We know that commit object bundling reduces clone time by an order of magnitude because the bottleneck is request count, not bandwidth.

None of this is in the source code. It is in our operational muscle memory. It accumulated through months of daily production use. It compounds every day we run the platform.

### The building block library

We have a growing library of self-contained building blocks: Playwright with MITM proxy for browser automation, Firefox with traffic capture, Elastic with Kibana for ephemeral observability, S3-compatible storage with vault backend, Ollama for local LLM inference, AWS billing analysis, EC2 security posture, IAM permission auditing.

Each block follows the same pattern (self-contained, API-first, runs anywhere, storage-agnostic, marketplace-ready). Each one took days to specify and implement because the pattern does the heavy lifting. A competitor starting from scratch does not have the pattern. They will spend months rediscovering what we learned in weeks.

### Customer-specific vault content

Every customer engagement produces a vault: an encrypted, versioned bundle of deliverables, evidence, analysis, and decisions. Over time, these vaults represent accumulated domain expertise. A security consultancy using our platform has two years of assessment vaults, each containing the scoring, the evidence, the recommendations, and the client feedback. That library of work is not reproducible by forking the tools.

## What we actually sell

We do not sell code. We sell three things:

### 1. A platform that works

Vaults that encrypt on the client, version-control every change, and render in the browser in 120 milliseconds. Ephemeral compute that spins up in 80 seconds and costs fractions of a cent. Agent workflows that produce, review, and deploy content without human intervention. A website architecture where content comes from encrypted vaults and design is completely independent.

The platform works because we run it, fix it, and improve it every day. A fork works until the first bug the forker does not know how to fix.

### 2. A service that saves time

The investor pack use case: an investor wants to evaluate a startup. We provide the methodology (a versioned standard in a vault), the templates (engagement vault with folder structure, prompts, scoring rubrics), and the agentic workflow that populates it. What used to take a consulting team two weeks takes an afternoon.

The security review use case: a startup needs a security assessment for a partner or investor. We provide the codified standard, the automated evidence gathering, and the vault-delivered report with full provenance. What used to require hiring a consultant and waiting three weeks is now a self-service workflow backed by agents and vaults.

Customers pay because the service saves them time and produces better output than they could create manually. The code being open source is irrelevant to this value proposition.

### 3. A deployment that customers do not want to run themselves

This is the oldest moat in software: managed services. Yes, you can run Elastic yourself. Most people pay Elastic to run it for them. Yes, you can deploy your own vault infrastructure. Most customers would rather pay us, especially when the infrastructure includes ephemeral compute, agent orchestration, MITM proxy sidecars, S3-compatible storage nodes, VPC isolation per customer, and a growing library of building blocks they do not want to maintain.

Open source makes this easier, not harder. The customer can audit the code. They can verify the encryption is real. They can confirm the zero-knowledge claims. That transparency builds trust, and trust converts to paying customers faster than proprietary lock-in does.

---

## The question, reframed

"What is your moat?" is the wrong framing. It implies that a moat is a wall you build once. In practice, a moat is a rate: how fast you ship, how quickly you learn, how efficiently you convert customer problems into product features.

Our rate is high because:

- We brief in voice memos, convert to specs with AI, and implement with agentic dev teams in the same day
- We use our own tools to build our own tools (the website is vault-rendered, the agents communicate via vaults, the content is managed by agents)
- Every building block we create makes the next one faster to build
- Every customer engagement produces knowledge that feeds back into the platform

A competitor who forks our code today gets our position as of today. They do not get our velocity. By the time they have deployed what we have now, we have shipped another hundred features.

The code is open source. The execution is not forkable.
