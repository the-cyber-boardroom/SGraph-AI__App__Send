# Container Import: Push Locally-Built Containers to Running Nodes

**version** v0.27.5
**date** 02 May 2026
**from** Human (project lead)
**to** Developer (lead)
**type** Dev brief

---

## What It Does

Build a Docker container locally, push it to a running EC2 node, and run it there. No Docker Hub. No container registry. No public image repository. The container goes directly from your machine to the ephemeral instance.

This is a new capability on the host control plane FastAPI (the sidecar that runs on every node and already provides container listing, image listing, log access, etc.).

## Why This Matters

### Sensitive Containers

Some containers have secrets baked in: API keys, configuration files, proprietary code, credentials. Pushing these to Docker Hub (even a private repo) means they exist on a third-party server. With container import, the image goes from your local Docker to the running node. It never touches a registry. It can also be pushed to a vault (encrypted, versioned) for storage.

### Ephemeral Development Loop

Build locally. Push to an ephemeral node. Test. Destroy the node. The container image exists only on your machine and (briefly) on the ephemeral instance. Nothing persists in between.

### No Registry Dependency

The node does not need internet access to a container registry. This is critical for air-gapped or VPC-isolated deployments where pulling from Docker Hub is not possible.

## The Workflow

```
Developer builds a container locally:
    docker build -t my-custom-app:v1 .
    |
    v
Developer saves the container as a tar file:
    docker save my-custom-app:v1 -o my-custom-app.tar
    |
    v
Developer pushes the tar to the running node via the control plane API:
    POST /containers/import  (multipart file upload: my-custom-app.tar)
    |
    v
Node control plane receives the tar, runs docker load:
    docker load -i my-custom-app.tar
    |
    v
Image is now available on the node:
    GET /images  ->  [..., "my-custom-app:v1"]
    |
    v
Developer starts the container on the node:
    POST /containers  { image: "my-custom-app:v1", ports: {"8000": 8000} }
    |
    v
Container running on the ephemeral node
```

## API Additions to Host Control Plane

Add to the existing host FastAPI sidecar:

```
POST   /images/import          -> Upload a docker save tar, run docker load
                                  Body: multipart file upload
                                  Response: { image: "my-custom-app:v1", size: "245MB", loaded: true }

GET    /images                 -> List all images (already exists, now includes imported ones)

POST   /images/export          -> Run docker save on a running image, return tar
                                  Body: { image: "my-custom-app:v1" }
                                  Response: binary tar file download

DELETE /images/{name}          -> Remove an image from the node
```

### CLI Commands

```bash
# Import a local container to a running node
sg-compute image import --node node-abc123 --file my-custom-app.tar

# List images on a node (already exists)
sg-compute image list --node node-abc123

# Export an image from a node to local
sg-compute image export --node node-abc123 --image my-custom-app:v1 --output ./exported.tar

# Start the imported container
sg-compute pod start --node node-abc123 --image my-custom-app:v1 --ports 8000:8000
```

## Vault Storage for Container Images

In addition to pushing directly to a node, container images can be stored in a vault:

```
Developer saves container:
    docker save my-custom-app:v1 -o my-custom-app.tar
    |
    v
Push to vault:
    sgit add my-custom-app.tar
    sgit commit -m "Custom app v1 container image"
    sgit push
    |
    v
Later, on any node:
    Pull from vault, docker load
```

This means container images are encrypted at rest (vault encryption), version-controlled (vault commits), and shareable (vault tokens). An image built with sensitive configuration can be stored in a vault and loaded onto any ephemeral node without ever touching a public registry.

## Security Considerations

The import endpoint accepts arbitrary container images. This is powerful but must be controlled:

- API key authentication (already on the host control plane) restricts who can import
- Only the control plane has Docker socket access (no other container can import images)
- Imported images should be logged in the transaction log (who imported what, when)
- Optionally: scan imported images for known vulnerabilities before running (future enhancement)
