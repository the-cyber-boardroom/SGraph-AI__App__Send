# Ontologist Agent: Semantic Knowledge Graphs for Every Page

## What It Does

A new agent role (@ontologist) that creates semantic knowledge graphs for every piece of content on the website. Every markdown file, every article, every page gets an attached knowledge graph that captures the entities, relationships, and taxonomy within it. These graphs power a search engine and enable cross-content navigation.

## The Role

The ontologist is responsible for:

- Defining the schema and taxonomy for the knowledge graphs
- Creating a semantic graph for every content file pushed to the content vault
- Maintaining the graph-of-graphs (how individual page graphs connect to each other)
- Providing the data layer for the search engine
- Providing the data layer for relationship visualisations on each page

The ontologist works alongside the librarian (which catalogues and groups content) and @content (which creates and reviews content). The ontologist does not create content. It creates the semantic layer on top of content.

## The Knowledge Graph Per Page

Every markdown file in the content vault gets a companion `.graph.json` file:

```
articles/
    how-vault-pages-work.md
    how-vault-pages-work.graph.json    <-- ontologist creates this
```

The graph file contains:

```json
{
  "source": "how-vault-pages-work.md",
  "entities": [
    { "id": "vault", "type": "concept", "label": "Vault" },
    { "id": "read-key", "type": "concept", "label": "Read Key" },
    { "id": "object-id", "type": "concept", "label": "Object ID" },
    { "id": "aes-256-gcm", "type": "technology", "label": "AES-256-GCM" },
    { "id": "web-crypto-api", "type": "technology", "label": "Web Crypto API" },
    { "id": "sgit", "type": "product", "label": "SGit" }
  ],
  "relationships": [
    { "from": "vault", "to": "read-key", "type": "requires" },
    { "from": "vault", "to": "object-id", "type": "contains" },
    { "from": "vault", "to": "aes-256-gcm", "type": "encrypted-with" },
    { "from": "aes-256-gcm", "to": "web-crypto-api", "type": "implemented-via" },
    { "from": "sgit", "to": "vault", "type": "manages" }
  ],
  "tags": ["encryption", "vaults", "web-components", "client-side"],
  "summary": "How vault content is rendered on web pages using read keys and object IDs with client-side decryption."
}
```

## The Graph of Graphs

A top-level graph that connects all individual page graphs:

```json
{
  "type": "meta-graph",
  "pages": [
    { "id": "how-vault-pages-work", "graph": "how-vault-pages-work.graph.json" },
    { "id": "encryption-explained", "graph": "encryption-explained.graph.json" },
    { "id": "agent-communication", "graph": "agent-communication.graph.json" }
  ],
  "cross_references": [
    { "entity": "vault", "appears_in": ["how-vault-pages-work", "encryption-explained", "agent-communication"] },
    { "entity": "aes-256-gcm", "appears_in": ["how-vault-pages-work", "encryption-explained"] },
    { "entity": "email-fs", "appears_in": ["agent-communication"] }
  ]
}
```

This enables: "vault" appears in 3 pages, click to see all of them. "AES-256-GCM" appears in 2 pages, click to see the relationship. This is the search engine's data layer.

## The Search Engine

The librarian and ontologist collaborate to produce the search engine:

- **Ontologist:** Creates the semantic graphs (entities, relationships, tags, summaries)
- **Librarian:** Creates the catalogue (page titles, categories, ordering, navigation structure)

The search engine loads both:

```
User searches: "encryption"
    |
    v
Search index (from ontologist's graphs):
    +--> Entity match: "aes-256-gcm" (type: technology)
    |       Appears in: how-vault-pages-work, encryption-explained
    +--> Tag match: "encryption"
    |       Appears in: how-vault-pages-work, encryption-explained, security-model
    +--> Summary match: "client-side decryption"
    |       Appears in: how-vault-pages-work
    |
    v
Results ranked by relevance, displayed with context
```

The search index can be loaded dynamically (fetch the graph files from the vault, build the index in the browser). No server-side search infrastructure needed. For small-to-medium content libraries (hundreds of pages), client-side search from graph data is fast enough.

## Per-Page Visualisation

Each page can optionally display its knowledge graph as an interactive visualisation:

- Entities as nodes, relationships as edges
- Click an entity to see which other pages reference it
- Colour-coded by entity type (concept, technology, product, person)

This uses existing graph visualisation libraries (D3, vis.js) rendered as a Web Component (`<sg-knowledge-graph>`).

## The Ontologist's Vault

The ontologist gets its own dedicated vault for:

- The taxonomy definition (entity types, relationship types, schema)
- The graph-of-graphs
- Working notes and iterations
- The search index

This keeps the ontologist's data separate from the content vault (which @content manages) and the collaboration vault (which agents use for email-FS). The ontologist reads from the content vault but writes to its own vault.

## Acceptance Criteria

| # | Criterion | Verification |
|---|-----------|-------------|
| 1 | Schema defined for knowledge graph entities and relationships | Taxonomy document in ontologist vault |
| 2 | At least 5 pages have companion .graph.json files | Graph files exist alongside markdown files in content vault |
| 3 | Graph-of-graphs connects individual page graphs | Meta-graph shows cross-references across pages |
| 4 | Search engine returns results from graph data | Search "vault," get relevant pages ranked by relevance |
| 5 | Per-page graph visualisation renders interactively | Open a page, see its knowledge graph, click entities to navigate |
| 6 | Ontologist vault exists separately from content vault | Separate vault with taxonomy, meta-graph, and search index |
| 7 | Client-side search works without server infrastructure | Search functions in browser from dynamically loaded graph data |
