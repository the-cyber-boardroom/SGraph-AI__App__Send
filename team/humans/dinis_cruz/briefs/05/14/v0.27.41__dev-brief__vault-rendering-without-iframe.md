# Vault Rendering Without Iframe: HTML Direct To The Backend

**version** v0.27.41
**date** 14 May 2026
**from** Human (project lead)
**to** Developer (lead), @Dev
**type** Dev brief

---

## What This Is

Currently, when a vault renders its content via App Mode, the structure is: the vault page loads in the browser, and inside that page an iframe loads the actual HTML content; the iframe's JavaScript talks back to the vault page (which has the API keys, the SGit access, the storage layer) via postMessage.

The iframe pattern works. It is a reasonable sandboxing model (the iframe is isolated from the parent), and it has served the multi-app-on-one-page case well. But it adds complexity: a postMessage bridge, two JavaScript contexts to debug, double-loaded resources where shared, the iframe's own quirks (X-Frame-Options interactions, scroll handling, deep-link sharing).

This brief asks: for the **single-app-rendering-an-entire-vault case** (which is the common case for published vaults, the friend's CV, the band site, the medical POC), can we **drop the iframe**? Run the vault's HTML directly in the page, and give it APIs to talk to the backend without an intermediate iframe boundary.

## Why Now

Two things make this worth doing in this version cycle:

1. **The new SG/App routing.** We are already in the middle of making published vaults serve as clean pages without the full vault UI chrome. The iframe-removal is the natural endpoint of that simplification.
2. **The ephemeral instances milestone.** With proper DNS, real certs, and the vault app running on per-instance hosts, the backend the HTML talks to is naturally the same origin as the page. Same-origin requests are simpler than postMessage to a different origin.

We are at the right moment in the architecture to make this change.

## The Current Shape

```
Browser
  └── Vault page (from vault.sgraph.ai or similar)
        ├── Vault chrome (nav, settings, etc.)
        ├── postMessage bridge
        └── <iframe> (sandboxed)
              └── Vault's HTML/JS content
                    ↑ postMessage ↓
                    (read vault objects, write vault objects, etc.)
                    ↓ goes through bridge to parent ↓
                    ↓ parent calls vault API ↓
                    Backend / vault API
```

The HTML content cannot talk to the backend directly. It talks to the parent. The parent talks to the backend.

## The Proposed Shape

```
Browser
  └── Vault page (HTML served from same-origin vault instance)
        ├── Optional minimal chrome (or none)
        └── Vault's HTML/JS content
              ↓ direct calls to vault API on same origin ↓
              Backend / vault API
```

The HTML loads as the page. It calls the API directly. No iframe, no postMessage, no parent-mediated bridge.

## What Makes This Safe

The natural objection: the iframe was providing isolation. What replaces that?

Several things, in combination:

| Mechanism | What It Protects |
|-----------|------------------|
| **Same-origin policy** | The HTML cannot reach off-vault origins it should not |
| **Vault-app API permissions** | The API only serves the vault the page is authorised for |
| **Content Security Policy (CSP)** | Tight CSP prevents the HTML from loading external scripts, opening windows, etc. |
| **The vault is a single trust boundary** | The HTML in the vault was authored by (or for) the vault owner; the iframe was not protecting against the vault's own HTML, it was protecting against multi-app composition |
| **No cross-vault access** | The API only allows operations on the current vault |

The iframe was useful for **multi-app composition** (rendering several SG/Apps on one page, each isolated from the others). It was not strictly necessary for **single-app rendering** (one vault's HTML rendering its own content).

For single-app rendering, dropping the iframe is a net simplification with no new attack surface.

For multi-app composition (which is still a valid use case), the iframe approach can stay. The two modes can coexist:

- **Bare-metal mode**: one vault, one HTML page, direct API access. Used by published vaults, single-purpose sites.
- **Hosted mode**: vault chrome + iframe(s). Used when the vault UI is part of the experience, or when multiple apps share a page.

The published-vault flow defaults to bare-metal mode.

## The API Surface The HTML Uses

The HTML in bare-metal mode needs to call the vault API. The API needs to be designed for this:

```javascript
// Available globally in the page (injected by the vault app's bootstrap)
window.SG.vault.get(path)         // read a vault object
window.SG.vault.put(path, content) // write a vault object (if writable)
window.SG.vault.list(prefix)       // list objects
window.SG.vault.commit(message)    // commit changes (if writable)
window.SG.vault.subscribe(path)    // get notified of changes
```

This is the same API that the iframe today calls via postMessage. We expose it directly in bare-metal mode.

The API is scoped to the current vault. The HTML cannot reach other vaults, even on the same origin. The vault app enforces this server-side.

## What Changes In The Bootstrap

The HTML page served for a vault contains:

1. The vault's `index.html` (or the relevant entry point)
2. A small bootstrap script that exposes `window.SG.vault` (and similar) APIs
3. The vault's own scripts (which call those APIs)

The bootstrap is tiny: under a kilobyte. It establishes the API surface and any session state needed (vault id, read key reference, current commit). It does not include the vault app UI; it just sets up the page to talk to the backend directly.

For developers writing vault HTML, the difference is: instead of `parent.postMessage(...)` to read a file, they write `await window.SG.vault.get(...)`. Cleaner, async, same-origin, debuggable in browser dev tools without bridge plumbing.

## Backwards Compatibility

Existing vaults that use the iframe pattern keep working. The vault app detects the mode (bare-metal vs hosted) and serves the right wrapper. Existing HTML that calls the postMessage bridge sees that bridge still exists (the bootstrap polyfills it onto the direct API).

Migration: vault authors can opt in to bare-metal mode by setting a flag in their vault config. New vaults default to bare-metal.

## Performance Implications

Bare-metal mode is faster:

- **Fewer HTTP requests**: no separate iframe document fetch
- **Lower memory**: one JS context instead of two
- **Faster API calls**: direct fetch instead of postMessage round trips
- **Faster first paint**: the page's HTML renders immediately; the API calls happen alongside, not after the iframe loads

For published vaults (where time-to-first-render matters for social-media unfurling, search engine indexing, and human first impressions), this is a meaningful win.

## What This Replaces

This replaces a layer of complexity that exists for historical reasons but is not needed for the most common rendering case. For multi-app composition (where it adds real value), the iframe approach remains available.
