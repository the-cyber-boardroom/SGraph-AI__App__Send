## What This Is

A naming, conceptual, and architectural brief about a new (or newly-named) primitive: **vault collections**. Plus the concrete realisation: hosting vault collections in **containers**, which can spin up in seconds, hold encrypted data for a bounded time, serve it to authorised callers, and tear down.

The voice memo flagged this as the natural next step after the ephemeral EC2 work: containers boot faster, are lighter, and open up patterns that EC2 makes possible but heavy. And the underlying concept (the collection of vaults; the vault-as-zip; the data-volume thinking) deserves a name and a place in the architecture, not just an implementation choice.

This is one of those moments where the architecture clarifies because we are looking at how the pieces actually fit together in production rather than designing in the abstract.

## The Naming Problem

We have been talking about "vaults" as the unit. A vault has a backend (the API service, the file store, the metadata) and a frontend (the JavaScript that renders content in the browser). The vault is a unit of:

- Data ownership (one vault has one owner)
- Encryption boundary (one read key, one write key)
- Versioning (one commit history)
- Rendering (one app surface)

But once you have many vaults, the next question is: what do you call a collection of them?

| Concept | Possible Names |
|---------|---------------|
| One vault | Vault (current term) |
| A collection of related vaults | Vault collection? Vault group? Vault fleet? Vault zip? |
| The underlying storage of all vaults in some scope | Vault store? Vault volume? Vault data layer? |

The voice memo flagged the same gap: "what do you call a collection of vaults?" The naming is not settled. The concept needs a clear name before the implementation goes too far.

Working name for this brief: **vault collection**. A vault collection is a bounded set of related vaults that can be packaged, moved, mounted, and operated on as a unit. A user, a partner, an engagement, a workflow can have its own vault collection. The collection is the natural distribution unit, not the individual vault.

## What A Vault Collection Looks Like

Concretely:

```
my-vault-collection/
    ├── metadata.json                  (collection-level config, list of vaults)
    ├── vaults/
    │     ├── vault-001/               (one vault)
    │     ├── vault-002/
    │     └── vault-003/
    ├── shared-config/                 (config that applies to all vaults in the collection)
    └── access-rules/                  (who can do what)
```

The collection is a directory. The directory can be zipped (the voice memo's instinct). The zip can be loaded into a container, an EC2 instance, or a local filesystem. The same zip works in all three.

## The Vault-As-Zip Concept

The voice memo's strongest framing: a vault collection can be **just a zip**. Load the zip into a container, the container has the data. Tear the container down, the data only persists if you save it back. The container is the lifecycle; the zip is the asset.

This is powerful for several reasons:

| Reason | Why It Matters |
|--------|---------------|
| **Portability** | A zip is moveable. Email it, upload it, store it, ship it. The collection goes where you want it. |
| **Atomicity** | A zip is one unit. Move it as a whole. No partial transfer states. |
| **Snapshotability** | A zip is a snapshot at a point in time. The history is in the underlying vault data. |
| **Air-gappable** | A zip can move across boundaries (USB, sneakernet) when network is not available or not desired. |
| **Composable** | A larger workflow can be a set of zips, each loaded into its own container. |
| **Inspectable** | A zip is openable with any tool. The structure is auditable. |
| **Versionable** | Zips can be content-addressed (hash of contents), making them deduplicable, cacheable, verifiable. |

Note: the contents inside the zip are still encrypted. Loading the zip into a container does not decrypt anything. The decryption key arrives separately, when the user or agent or workflow needs to operate on the data.

## Containers As The Natural Host

EC2 instances are great. They are also heavy. Booting one takes ~30-60 seconds even fully optimised. They are sized for "stay alive for a while." For workloads that are bounded in time and scope, containers are a better fit:

| Property | EC2 Instance | Container |
|----------|-------------|-----------|
| Boot time | 30 seconds to minutes | 1-10 seconds typical |
| Memory footprint | Sized for the instance type (often GBs) | Sized for the workload (often MBs to hundreds of MBs) |
| Cost per running unit | $0.005-0.10+ per hour | Effectively free for short bursts (depends on host) |
| Isolation | Strong, kernel-level | Strong, namespace-level (good enough for most cases) |
| Lifecycle | Hours to days | Seconds to minutes typical |
| Suitable for | Persistent services, demos, long sessions | Workloads, agents, ephemeral data operations |

A container that loads a vault collection zip can be:

- Spun up in seconds
- Used for some operation (analysis, agent action, processing)
- Torn down
- Replaced with a fresh container next time

This is closer to the unit-of-work granularity than EC2 instances are.

## The Agentic Workflow Connection

The voice memo's most important insight: **this is how you give data to agents**.

The pattern is:

1. An agent needs to operate on some data (a customer's vault, a partner's evidence pack, a workflow's working state)
2. The orchestrator packages the relevant vault collection as a zip
3. A container starts, the zip mounts as the agent's data volume
4. The agent runs in the container with full access (within its decryption-key scope) to the data
5. The agent produces output (another vault, an artefact, a decision)
6. The container tears down; results persist to wherever they should go (canonical vault, output vault, message back to the orchestrator)

This is qualitatively different from "the agent calls an API to read the data." It is "the agent runs **alongside** the data, in a bounded environment, for a bounded time."

Properties of this pattern:

| Property | What It Enables |
|----------|----------------|
| **Spatial locality** | The agent and the data are in the same address space; reads are fast |
| **Bounded scope** | The container only has what was put in the zip; the agent cannot reach beyond |
| **Auditable** | Container instantiation, lifetime, teardown all logged; the work happened in a specific scope |
| **Reproducible** | Same zip + same agent + same orchestrator = same result (mostly) |
| **Parallelisable** | Multiple agents on multiple containers can work on different vault collections simultaneously |
| **Compartmentalisable** | Sensitive workloads in their own container; no cross-contamination |

This is what the CLI-first agent architecture briefs from 13 May were pointing toward. The orchestrator strings together CLI commands; **the orchestrator also stands up the container** the CLIs run in. The container plus the zip plus the agent CLIs are the unit of work.

## The Read/Write Modes Matter

The voice memo flagged this: the value depends on what the workload does to the data.

| Workload Type | Container Pattern Fit |
|---------------|----------------------|
| **Read-only processing** | Excellent. The zip mounts, the work runs, the container tears down, nothing changes. |
| **Read-and-derive** (input data → new output data) | Excellent. The zip is input; the output goes to a separate output vault. |
| **Modify in place** | Harder. The modified zip needs to persist back somewhere. Requires explicit save. |
| **Long-running bidirectional sync** | Not the right pattern. Use EC2 instance or persistent service instead. |

The first two cover most agentic workflows. The third is doable with explicit persistence. The fourth is what the Vault Synchronizer (13 May brief) handles via persistent EC2 instances.

The architecture has space for all four. Pick the right substrate for the workload.

## The Signed-Data-Inside Property

A subtle but powerful point the voice memo raised: the data inside a vault collection can be **signed with different keys**, and even if the container has access to the vault, **the container may not have decryption keys for specific data within**.

Example: a vault collection holds evidence for a medical workflow. The patient's identifiable data is encrypted with one key (held only by the patient and the doctor). The aggregated metrics are encrypted with a different key (held by the patient, the doctor, and the workflow agent).

When the workflow agent runs in a container with the collection mounted, it can decrypt the aggregated metrics (it has the key) but cannot decrypt the identifiable data (it does not have the key). The data is **present** in the container but **not readable** to the agent.

This is a strong privacy property. It means containers can be given "more data than they need" with the assurance that the unauthorised data stays opaque. It also means the same vault collection can serve multiple agents at different trust levels; each agent sees what it has keys for.

## When EC2, When Container

Both substrates have a place. The decision tree:

| Use Case | Substrate |
|----------|-----------|
| Long-lived demo URL | EC2 (DNS-named, certed) |
| Partner-hosted persistent deployment | EC2 |
| Vault that serves browser traffic | EC2 (browser needs persistent endpoint) |
| Agent reading data and producing output | Container |
| Quick scan or analysis | Container |
| Per-song production run in the daily band experiment | Container |
| One-off processing of a vault collection | Container |
| Warm pool waiting for assignments | EC2 (DNS already assigned) |

The Vault Synchronizer should support both: `deploy ephemeral-ec2` for the EC2 path, `deploy container` for the container path. The user picks based on workload.

## Logging Data Example

The voice memo's specific example: capturing logging data, and being able to share "x number of days of logs with a particular user."

The vault collection model handles this elegantly:

1. Continuous logging writes to a long-lived vault (on EC2 or elsewhere)
2. When a user requests N days of logs, the system extracts the relevant slice into a new vault collection (a zip)
3. The user receives the zip (via vault token, direct download, or any other channel)
4. The user mounts the zip locally (or hands it to their own agent in their own container)
5. They have exactly the data they asked for, in an inspectable, auditable, time-bounded form

This is what makes "share my logs" feasible: a zip is a clean unit, the keys are scoped, the recipient has everything they need and nothing they do not.

## What This Asks For

The architecture work this brief opens up:

1. Settle the **naming**: vault, vault collection, vault zip, vault host, vault volume. Get the terms consistent.
2. Define the **vault collection format**: directory structure, metadata, packaging convention.
3. Build the **container vault host**: a container image that mounts a vault zip and runs the vault app, suitable for ephemeral workloads.
4. Add `deploy container` to the **Vault Synchronizer**.
5. Document the **agentic workflow pattern**: how an agent's CLI work runs in a container with a mounted collection.
6. Measure: container boot + zip load + agent start, end to end, vs the EC2 path.

This is multi-week work. The first step (naming) costs nothing and unblocks everything else.
