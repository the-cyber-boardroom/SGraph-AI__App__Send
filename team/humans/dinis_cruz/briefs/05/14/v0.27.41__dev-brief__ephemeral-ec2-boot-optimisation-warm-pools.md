# Ephemeral EC2 Boot Optimisation and Warm Pools

**version** v0.27.41
**date** 14 May 2026
**from** Human (project lead)
**to** Developer (lead), DevOps, @Dev
**type** Dev brief

---

## What This Is

We are in the final stages of figuring out dynamic EC2 provisioning for vault hosts. Yesterday's milestones (TLS at boot, then proper DNS via Route 53) proved the substrate works. Today's work is the next-order optimisation: **how fast can we make this loop?**

Three concrete questions to answer:

1. How fast can an EC2 instance go from "request" to "ready to serve a vault"?
2. How fast can a vault be loaded onto an already-ready instance?
3. Can we maintain a warm pool of pre-provisioned instances waiting for vault assignments?

The goal is to get from "minutes per ephemeral instance" to "seconds per ephemeral instance," and ideally to "near-instant" via warm pools.

## Why Now

Three reasons this matters now and not earlier:

| Reason | Why It Matters |
|--------|---------------|
| **Demo experience** | A demo that takes minutes to spin up loses the audience; seconds keeps them. The Vault Synchronizer's "deploy ephemeral" command is the natural test. |
| **Daily band experiment** | The daily unsupervised production experiment will spin up workloads; latency on each affects how many we can run cheaply. |
| **Agentic workflows** | When an agent needs an isolated execution environment to act on a vault, that environment needs to materialise fast or the agent stalls. |
| **Container path next** | The companion brief on containers needs an EC2 baseline to compare against; this brief establishes it. |

## The Current Baseline

After yesterday's work, the boot sequence is roughly:

| Phase | Approximate Time |
|-------|------------------|
| EC2 instance creation request → instance running | 30-60 seconds |
| User-data script execution, package installation, build steps | 60-180 seconds depending on what is installed |
| DNS record propagation | 30-90 seconds (often overlapping with build) |
| Let's Encrypt ACME challenge and cert installation | 30-60 seconds (after DNS propagates) |
| Vault app startup, ready to serve | A few seconds |
| **Total wall-clock with parallel orchestration** | **2-4 minutes typical** |

Two minutes is much better than the naive serialised five-plus minutes. It is still too slow for an interactive demo, and unnecessary for a workflow that has spent the last week being orchestrated.

## The Optimisations Available

In rough order of impact:

### 1. AMI Baking

Most of the build phase is repeatable. Bake an AMI with:

- The vault app preinstalled and configured
- Dependencies preloaded
- The ACME sidecar preconfigured
- Most of what currently runs in user-data already baked in

What remains at boot:

- Per-instance configuration (IP, hostname, cert provisioning)
- The specific vault data load (or, in some modes, deferred entirely)

Expected impact: build phase drops from 60-180 seconds to under 30 seconds.

### 2. DNS Provisioning Tuning

Current approach is to create the A record after the IP is known, then wait for propagation. Two optimisations:

- **Lower the TTL** on the wildcard record so propagation is faster
- **Pre-allocate the DNS record** in some cases (e.g. for known slug-to-IP assignments in a warm pool)

Expected impact: DNS phase drops from 30-90 seconds to under 10-20 seconds.

### 3. Cert Strategy

Let's Encrypt is great but per-cert provisioning is the bottleneck on first request. Options:

- **Wildcard cert at the load balancer level** (per the 12 May `sgraph-app-subdomain-registration-workflow` brief) so per-instance certs are not needed for vaults served through the routing layer
- **Per-instance certs only when truly needed** (an instance with its own dedicated DNS name)
- **Pre-issued certs for warm pool instances**

Expected impact: cert phase drops to near-zero for most cases.

### 4. Warm Pool

The biggest win: maintain a pool of N already-running EC2 instances that have completed boot, DNS, cert provisioning, and are sitting idle waiting for vault assignments.

When a vault is requested:

1. Pull an instance from the warm pool
2. Load the requested vault onto it (seconds, not minutes)
3. Return the instance URL
4. Replenish the pool asynchronously

The user experience: vault assignment in seconds.

Cost trade-off: warm instances cost money even when idle. A pool of 3-5 t3.small instances at ~$0.02/hour each is roughly $1-3/day. Acceptable for the demo and workflow benefits.

### 5. Lighter Base Image

The vault app is, as the voice memo flagged, increasingly lightweight: an API service that renders files to the browser, plus the UI delivered as JavaScript. The actual binary footprint is small. With AMI baking, the image could be quite slim.

A lighter image boots faster and uses less RAM (allowing smaller instance types, which boot faster, which costs less).

### 6. Instance Type Choice

Larger instances boot faster but cost more. There is a sweet spot. For the warm-pool case, very small instances (t4g.nano, t4g.micro) with the baked AMI may be ideal: each instance is cheap, plenty for a single vault, fast to boot.

## The Decryption Key Constraint

The voice memo flagged this explicitly: even if we are moving instance data around in the back end, **the decryption key is still required for the user to actually access the vault content**. The key is not part of the warm-pool setup; it arrives with the user request.

This is an important property. It means we can:

- Pre-warm instances without any of the customer's data
- Pre-load **encrypted** vault data into a warm instance speculatively (if we predict it will be used)
- Only complete the user-facing operation when the key arrives

The warm pool is not "vaults are pre-loaded into RAM." It is "the substrate is ready; the vault data and decryption are user-triggered." This is the right model for both performance and security.

## Modes Of Boot

The voice memo also hinted at multiple modes worth supporting:

| Mode | What Boots | Use Case |
|------|-----------|----------|
| **Cold** | Full provisioning from scratch | Long-lived deployments; the current default |
| **Warm pool** | Pull from pool; load vault on assignment | Interactive demos, agent workloads |
| **Pre-loaded warm** | Pool instances each pre-loaded with a likely vault | Predictable repeated workloads |
| **Speculative** | Start provisioning before the user finishes a request | UX-driven; mask provisioning behind user thinking time |

These are not all equally valuable. Cold and warm-pool are the immediate priorities. Pre-loaded warm and speculative are nice-to-have if measurement shows they pay off.

## Container Path Will Follow

The companion brief (vault collections and containerised vault hosts) takes this thinking one step further: instead of EC2 instances, use containers. Containers boot in single-digit seconds. The trade-offs are different (isolation, hosting model, AWS billing). EC2 is the path we have today; containers are the next step. This brief establishes the EC2 baseline; the companion brief sets out the container direction.

## Measurement

We cannot optimise what we do not measure. Instrument the boot sequence:

- Time from request to instance running
- Time from instance running to build complete
- Time from instance running to DNS resolving
- Time from DNS resolving to cert installed
- Time from cert installed to vault app responding
- Time from vault app responding to first vault data loaded

Each step gets a clear measurement. Improvements are visible in the metrics. Regressions are caught.

The metrics feed into the daily band experiment's cost tracking too: a song that costs more in EC2 time than in API calls is a different problem from one that costs more in API calls than in EC2 time.

## What This Asks For

Concrete next steps, in priority order:

1. Bake an AMI with the vault app preinstalled
2. Add boot instrumentation to capture phase-by-phase timings
3. Implement a warm pool of 3-5 t3.small (or similar) baked instances
4. Implement the warm-pool checkout API (request → instance assignment in seconds)
5. Tune DNS TTL on the wildcard record
6. Confirm wildcard cert handles the routing-layer cases (no per-instance Let's Encrypt for those)
7. Document the new boot times and target SLOs
8. Use the Vault Synchronizer's `deploy ephemeral` command as the canonical test

Estimated impact: from ~2-4 minutes cold-boot to ~10-20 seconds with warm pool.
