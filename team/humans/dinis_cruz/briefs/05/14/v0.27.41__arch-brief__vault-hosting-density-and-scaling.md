## What This Is

The vault-hosting architecture so far has been one-vault-per-EC2-instance. That works, but it does not scale economically or in latency terms. This brief explores the next-order question: **how many vaults can one node serve, and what does the routing look like?**

The architectural choices made here determine the cost curve for the platform as we onboard more vault collections, more partners, more daily-band-experiment workloads, and more agentic workflows. Getting it right early matters.

The brief sits between the EC2 boot-optimisation brief and the vault-collections / containerised-hosts brief. The boot-optimisation brief says "make individual instances faster." The container brief says "use containers for ephemeral workloads." This brief says "for both substrates, how do we host multiple vaults per host node?"

## The Current Routing Pattern

The flow we are about to land:

```
User visits user-a.sgcompute.sgraph.ai
    ↓
DNS check: does an A record exist for "user-a"?
    ↓
    ├── YES → return the IP address, user hits the EC2 instance directly
    │
    └── NO  → wildcard record for "*.sgcompute.sgraph.ai" hits a Lambda function
              ↓
              Lambda function spins up an EC2 instance
              ↓
              Lambda function creates the A record mapping user-a to the new IP
              ↓
              User is redirected (or polled until ready), then served
```

This is good: on-demand provisioning, no pre-existing instances burning cycles for users who never come back, eventual fast-path once provisioned.

It also assumes one vault per EC2 instance. Each user gets their own instance. Each instance holds one vault.

That assumption is the question this brief opens.

## The Core Question

**Can one node host multiple vaults?**

There are several ways to slice this. They are not mutually exclusive; they sit on a density spectrum:

| Approach | Density | Isolation | Routing |
|----------|---------|-----------|---------|
| **One vault app per EC2 instance** (current) | Lowest | Strongest (kernel-level) | DNS → IP → that vault |
| **Multiple vaults in one vault app on one instance** | Medium | Logical (app-level) | DNS → IP → vault app → vault ID from URL |
| **Multiple vault-app containers per instance** | Higher | Container-level | DNS → IP → routing layer → container → vault |
| **Containers on a Kubernetes-style scheduler across instances** | Highest | Container-level | DNS → cluster routing → container → vault |

The decision is not "pick one." It is "which patterns do we support, for which workload classes, with which routing?"

## The Three Architectural Questions

The voice memo asked three concrete sub-questions. Each deserves an answer.

### Q1: Can one vault app host multiple vaults?

Almost certainly yes. The vault app is structurally:

- A web server serving static assets (the vault UI)
- An API service answering vault-data requests
- A file backend (vault data on disk)

None of these is inherently single-vault. The API takes a vault identifier; the backend can hold many vaults' data; the static assets are shared. The current pattern is one-vault-per-vault-app because we have not yet routed differently; it is not because the architecture forbids more.

What changes if we go multi-vault-per-app:

| Change | Impact |
|--------|--------|
| URL must carry vault identity | The path or subdomain encodes which vault is being served |
| API must route requests to the right vault | The vault ID becomes part of every API call |
| Backend storage must support multiple vaults side-by-side | Already true; vaults are isolated directories |
| Auth scoping is per-vault, not per-app | Existing tokens are vault-scoped, so this works |

This is a small set of changes, mostly in the URL-handling layer.

### Q2: Can one EC2 instance host multiple vault-app containers?

Yes, with the addition of a routing layer on the instance. The pattern:

```
EC2 instance
    │
    ├── nginx or Traefik (or similar) listening on :443
    │       │
    │       ├── routes user-a.sgraph.ai → container-1 (port 8001)
    │       │
    │       ├── routes user-b.sgraph.ai → container-2 (port 8002)
    │       │
    │       └── routes user-c.sgraph.ai → container-3 (port 8003)
    │
    ├── container-1: vault app for user-a
    ├── container-2: vault app for user-b
    └── container-3: vault app for user-c
```

The routing layer reads the host header and dispatches to the right container. Each container holds its own vault data and serves its own vault app. They are isolated from each other at the container boundary.

This is the **Kubernetes-style mode** the voice memo flagged. We do not necessarily need Kubernetes (yet); a single EC2 instance running a small routing layer plus N containers is sufficient for moderate density and easier to operate.

### Q3: How does the routing table work?

The routing table is the critical piece. It needs to answer two questions:

1. Given a hostname (e.g. `user-a.sgcompute.sgraph.ai`), which EC2 instance serves it?
2. Once on the instance, which container/vault answers the request?

The first question is solved at DNS / load balancer level. The second is solved at the routing layer on the instance.

Concretely, a routing table entry looks something like:

```json
{
  "user-a.sgcompute.sgraph.ai": {
    "instance_id": "i-abc123",
    "instance_ip": "10.0.1.5",
    "container_port": 8001,
    "vault_id": "vault-xyz789"
  },
  "user-b.sgcompute.sgraph.ai": {
    "instance_id": "i-abc123",
    "instance_ip": "10.0.1.5",
    "container_port": 8002,
    "vault_id": "vault-def456"
  }
}
```

Both user-a and user-b resolve to the same instance, but to different containers (or to the same container with different vault IDs, if we are in the multi-vault-per-app mode).

The routing table is the new piece of state we add. The slug-to-share-token lookup from the sgraph.app subdomain brief is a precedent for this kind of small, fast key-value lookup. Same shape, different content.

## The Cost / Security Trade-Off

The voice memo correctly framed this as a cost-and-security question:

| Pattern | Cost | Security |
|---------|------|----------|
| One vault, one EC2 instance | Highest cost per vault | Strongest isolation; no shared kernel |
| One vault, one container, multiple containers per instance | Lower cost (sharing instance overhead) | Container isolation; shared kernel |
| Multiple vaults, one container, one instance | Lowest cost | Weakest isolation; vaults share app-level boundary only |

Different vault classes have different requirements:

| Vault Class | Suitable Density |
|------------|-----------------|
| Highly sensitive (e.g. medical, financial) | One vault per EC2 instance; strongest isolation |
| Customer-deployed but not regulated | One vault per container; multiple containers per instance |
| Demo / showcase / public | Multiple vaults per app; lowest cost |
| Ephemeral agentic workloads | Containers per workload; possibly multiple per instance |
| Personal projects (CV, portfolio, band) | Multiple containers per instance; lower cost |

The platform should support all three densities. The customer (or the workload's classification) picks. Pricing reflects the density.

## The Latency Argument

Beyond cost, the density question affects latency in interesting ways.

**Cold path (no instance yet provisioned)**: spin up an EC2 instance, configure, serve. Slow (minutes today; ~10-20 seconds with warm pools per the EC2 optimisation brief).

**Warm path with multiple containers per instance**: an EC2 instance is already running with capacity. A new vault arrives → spin up a container on that instance → route traffic. Seconds, not minutes. Containers boot fast; the instance is already there.

This is what the voice memo meant by "is there an EC2 instance running that we can slap the current vault in?" If the answer is yes, the cost-and-latency win is significant. The substrate is shared; only the container is new.

## The Three Modes Coexist

This brief is not advocating for one mode replacing another. It is advocating that we **support all three modes** and pick the right one for the workload:

| Mode | When To Use |
|------|------------|
| **Dedicated EC2** | Regulated workloads, high-sensitivity vaults, partners who want full isolation |
| **Multi-container per EC2** | Most workloads; default; best cost-latency-isolation balance |
| **Multi-vault per app** | Demos, public showcases, very cheap hosting tier |

The Vault Synchronizer's `deploy` command should accept a density flag:

```
vault-sync deploy ephemeral <vault-id> --density dedicated
vault-sync deploy ephemeral <vault-id> --density shared-container
vault-sync deploy ephemeral <vault-id> --density shared-app
```

Default to shared-container. Override for special cases.

## Where The Vault Data Lives In Each Mode

Worth being explicit because it affects the design:

| Mode | Where Vault Data Lives |
|------|----------------------|
| Dedicated EC2 | On the instance's local filesystem (or attached EBS) |
| Multi-container per EC2 | On the instance's shared filesystem, mounted into each container as that container's data volume |
| Multi-vault per app | All in the app's shared filesystem; segregated by vault ID |

The container case is the most interesting: a vault collection zip (from the vault-collections brief) mounts as the container's data volume; the container is ephemeral; the zip is the persistent layer. Containers come and go; the data persists in the form chosen for the workload.

## The Lambda-Spinup-Function Evolution

The current routing pattern uses Lambda to spin up new instances on demand. As density increases, this evolves:

| Era | What Lambda Does |
|-----|------------------|
| Current | Spin up a new EC2 instance for each new vault |
| Next | Check if an existing instance has capacity for another container; if so, spin up a container on it; if not, spin up a new instance |
| Future | Talk to a real scheduler (Kubernetes, ECS, Nomad) that handles container placement |

The Lambda becomes a placement decision-maker, not just a provisioner. It picks where each new vault goes based on current capacity, vault class, latency requirements, and cost.

This is the natural evolution. We do not jump to a full scheduler today; we evolve the Lambda incrementally.

## What This Asks For

| Item | Why |
|------|-----|
| Decide on the **density modes** to support officially | Three modes named in this brief; commit to all three |
| Implement the **routing layer** on EC2 instances (nginx, Traefik, or equivalent) | Enables multi-container per instance |
| Add the **routing table** as a new piece of state | Maps hostnames to instance + container + vault |
| Update the **vault app** to support multi-vault-per-app mode | Smallest change; biggest density win for low-stakes workloads |
| Extend the **Vault Synchronizer** `deploy` command with `--density` | Lets workloads pick their mode |
| Evolve the **Lambda spinup function** to become a placement decision-maker | Makes density automatic, not manual |
| Document the **mode-per-workload-class** policy | So customers and operators know what to expect |
| Measure **cost-per-vault** at each density | So pricing decisions are grounded |

## What This Does Not Do

This brief does not (yet) commit to Kubernetes. A simple routing layer plus container management on EC2 instances handles meaningful density without the operational complexity of a full scheduler. Kubernetes (or ECS) is a later step if and when the scale justifies it.

This brief also does not (yet) address cross-instance vault movement (live migration). A vault stays on its initially-provisioned instance / container until a workflow explicitly relocates it. Cross-host migration is a much harder problem and deferred.
