# Vaults of Vaults: Each Vault As A Self-Contained Mini-App

**version** v0.27.41
**date** 14 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), @Dev
**type** Arch brief

## What This Is

A naming and conceptual brief for a pattern that has been forming organically: **each vault has its own centre of gravity**. Its own tools, its own visualisations, its own apps, its own UI. The vault is not just data with a shared renderer; it is a self-contained workspace with workflows specific to its purpose.

The pattern extrapolates to a useful sub-case: vaults whose purpose is to **manage other vaults**. A vault of vaults. Some vaults hold content (a CV, a band, an article); some vaults hold the operational state of other vaults (a credential manager, a synchroniser dashboard, an audit log). Both are vaults; both fit the same architecture; both deserve their own tooling.

This is taking the mini-app idea to its natural conclusion: **almost every vault becomes a mini-app**, customised to its purpose.

## The Pattern Today (And Where It Falls Short)

Today, the vault app is one app that renders many vaults. The rendering varies (App Mode shows the vault's own HTML; raw mode shows files; etc.), but the operational tooling is the same. The user always gets the same set of vault-management controls regardless of what the vault contains.

This works for content vaults (a CV, a portfolio, an article) because the rendering is the variable part and the operational tooling is largely irrelevant to the visitor. The visitor sees the CV; the vault chrome is mostly out of the way.

It does not work as well for **operational vaults**: vaults whose entire purpose is to provide a specific workflow. A credential manager wants buttons for "generate new key", "revoke this key", "see usage stats". A synchroniser dashboard wants graph visualisations and sync controls. A QA dashboard wants run-history and replay buttons. Each one needs its own UI, not the generic vault chrome.

The pattern that captures this: **the vault carries its own app**. The app is part of the vault. When you open the vault, you get the vault's app, not the platform's default vault viewer.

## The Concept Named

**Vaults of Vaults** is the umbrella term for the pattern. It has two distinct meanings worth keeping separate:

| Meaning | What It Refers To |
|---------|-------------------|
| **Each vault is its own world** | Every vault is a self-contained mini-app with custom tooling for its specific purpose |
| **Some vaults manage other vaults** | A specific sub-case where a vault's content is metadata or operational state about other vaults |

Both meanings matter. The first is the general principle. The second is a particularly powerful application.

For clarity downstream, this brief uses:

- **Self-contained vault** for the general principle
- **Manager vault** for the specific case of a vault that operates on other vaults

## Why Self-Contained Vaults Are The Right Pattern

Three reasons.

### Reason 1: The Workflow Belongs With The Data

A credential manager has specific workflows (generate, distribute, revoke, audit). Those workflows are useless if the data lives somewhere else. Putting both in the same vault means the workflows are always available wherever the vault is, on whatever substrate.

This is the same principle as SKILL.md files for code skills: the procedure is co-located with the resources it needs. Move the vault, the procedure moves with it.

### Reason 2: Customisation Without Platform Bloat

If every workflow had to be a platform-level feature, the platform would become unmanageable. Different users want different things. A credential manager is useful for some users; a publication scheduler is useful for others; a song-production dashboard for others.

By putting the customisation in the vault, the platform stays focused on the substrate (storage, encryption, sync, rendering primitives). The customisation lives in the vault content. The platform serves; the vault decides.

### Reason 3: The Author Owns The Experience

The vault author chooses what tools are available. They are not constrained by what the platform shipped. A medical partner can build a clinician-facing vault with controls tuned to their workflow. A musician can build a fan-facing vault with controls tuned to discovery. A team can build an internal manager-vault with controls tuned to their operations.

This is the SG/App framework from 02 May applied at full strength: the vault's app is the experience; the platform is just the engine.

## What "Self-Contained" Looks Like Concretely

A self-contained vault carries:

| Element | What It Is |
|---------|-----------|
| **Its content** | The data the vault holds (files, structured records, media) |
| **Its app** | The HTML/JS/CSS that defines the user experience for this vault |
| **Its tools** | Buttons, forms, visualisations specific to this vault's purpose |
| **Its workflows** | The actions a user can take in this vault (with their consequences) |
| **Its visualisations** | The custom views (graphs, timelines, dashboards) that suit this vault |
| **Its agent CLIs** | Per the agent-CLI architecture, any agents that operate on this vault have CLIs scoped to it |

When you open the vault, you get all of this. The platform handles the substrate (decryption, file serving, API access); the vault handles the experience.

This is already partly true with App Mode. The brief is making it explicit and extending it.

## The Manager Vault Sub-Pattern

The voice memo's most useful new construct: a manager vault. A vault whose content is **metadata about other vaults**, with tools to operate on those other vaults.

Examples:

| Manager Vault | Manages |
|---------------|---------|
| Credential manager | API keys (OpenRouter, OpenAI, Stripe, etc.) and tokens distributed to others |
| Vault Synchronizer dashboard | The graph of vault locations and their sync state |
| Publication scheduler | Upcoming releases across multiple content vaults |
| Agent supervisor | Running agentic workflows across multiple vaults |
| Audit log | Aggregated activity across a set of vaults |
| Customer-engagement tracker | Status of multiple partner deployments |

Each manager vault has its own app, its own tools, its own visualisations. None of them is the same. The pattern is the same; the instances vary.

The manager vault holds:

- References to the vaults it manages (vault IDs, share tokens, last-known states)
- Operational state (recent actions, scheduled actions, alerts)
- Audit trail
- Configuration

It does **not** hold the underlying vaults' content. It holds the metadata and the workflows. The actual vaults stay separate. This is important: if the manager vault is compromised, only its metadata is exposed; the managed vaults remain encrypted with their own keys.

## The Key Architecture Of Manager Vaults

Manager vaults raise an interesting key-management question:

- The manager vault has its own read/write keys (like any vault)
- The managed vaults have their own read/write keys
- Does the manager vault hold the managed vaults' keys?

Three options:

| Option | Property |
|--------|----------|
| **Hold all keys** | Manager vault has full power; convenient; high-trust requirement |
| **Hold only references, never keys** | Manager tracks state but cannot read managed content; requires the user to provide keys when operating |
| **Hold scoped tokens** | Manager has share tokens that grant specific permissions; not the master keys |

For most cases, the **scoped tokens** option is the right one. The manager vault holds share tokens (perhaps with expiry, perhaps with limited scope), not master keys. It can do its specific job; it cannot exceed that scope; it minimises the blast radius if compromised.

The vault-collection model from earlier today fits this: a manager vault and its managed vaults can be packaged together, but the cryptographic boundaries between them remain. A manager vault is **about** other vaults; it is not **the same as** them.

## What Changes In The Vault App

To support this fully, the vault app changes in a few ways:

| Change | Description |
|--------|-------------|
| **The vault's app is the default experience** | Opening a vault loads its app, not the platform chrome |
| **Platform chrome is opt-in, not default** | If the vault wants the platform's vault-management chrome, it asks for it |
| **The vault app has access to vault-management APIs** | A scoped API surface for "operate on this vault's state" actions |
| **Manager vaults can call cross-vault APIs** | A separate scoped API for "operate on another vault you have a token for" actions |

Most of this is already true in pieces. The brief is making it explicit and ensuring the pieces compose.

## The Audit Trail

A self-contained vault, especially a manager vault, generates its own operational history. Every action taken in the manager vault commits to the vault's history (because vault state is always versioned). This means:

- Who issued a token, when, with what scope
- Who revoked a token, when
- Which managed vaults the manager touched, and when
- Configuration changes over time

The vault's commit history IS the audit log. This is the same property used for songs in the band production team (every step commits to the vault) and stories in the newsroom (every editorial transition commits).

This makes manager vaults inherently auditable without any separate audit infrastructure. The vault's normal version control handles it.

## What This Asks For

The work needed to support this pattern fully:

1. Decide on the terminology (self-contained vault / manager vault / vaults-of-vaults; keep one).
2. Document the pattern with examples.
3. Ensure the vault app supports vault-provided apps as the default opening experience.
4. Add the cross-vault API surface for manager vaults to operate on their managed vaults (using share tokens, never master keys).
5. Build the first concrete manager vault (the credential manager; companion brief).
6. Validate the pattern with a second use case (Vault Synchronizer dashboard, audit log, or similar).

This is mostly clarification of an already-emerging pattern, not new infrastructure. The framing is the contribution.
