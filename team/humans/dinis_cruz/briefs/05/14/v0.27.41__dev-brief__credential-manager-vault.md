## What This Is

The first concrete instance of the **manager vault** pattern from the companion architecture brief. A vault whose purpose is to manage credentials (OpenRouter keys initially, eventually any third-party API key) and distribute scoped access to them via **Simple Tokens** rather than by handing out the underlying keys.

The motivation is operational. I have been distributing OpenRouter keys to users (notably for the infographic generator). There is currently no good tool for this. The keys themselves are sensitive; distributing them via WhatsApp or email is unsatisfactory; managing their lifecycle (rotation, revocation, usage tracking) is manual and lossy.

This brief defines a tool that solves the problem properly while also serving as the canonical demonstration of the vaults-of-vaults pattern.

## The Pattern: Simple Tokens Instead Of Keys

Rather than hand out a real OpenRouter API key, hand out a **Simple Token**. The token is short, opaque, easy to share, and resolved by the credential manager to the underlying key only at the moment of use.

The flow:

```
User → uses Simple Token in their request
                    ↓
Their tool → calls the credential manager API with the token
                    ↓
Credential manager → looks up the token, checks scope/expiry/quota
                    ↓
                    ├── valid → returns the actual key (or makes the upstream call on the user's behalf)
                    │
                    └── invalid → returns an error
```

The user never sees the real key. The user has the Simple Token, which can be:

| Property | Value |
|----------|-------|
| **Time-limited** | Expires after a configured period |
| **Quota-limited** | Caps total cost or call count |
| **Scope-limited** | Only valid for specific models, endpoints, or operations |
| **Revocable** | Can be invalidated instantly from the credential manager |
| **Auditable** | Every use logged in the credential manager vault |
| **Per-user** | Each user has their own token; usage attributable |

This is the same shape as scoped OAuth tokens, or AWS IAM scoped credentials, applied to third-party API keys we already pay for and want to distribute thoughtfully.

## What The Vault Holds

The credential manager vault structure:

```
credential-manager-vault/
    ├── manifest.json                 (vault metadata, schema version)
    ├── app.js                        (the manager UI, served via App Mode)
    ├── keys/
    │     ├── openrouter-personal.encrypted     (encrypted with the vault key)
    │     ├── openrouter-team.encrypted
    │     ├── openai-trial.encrypted
    │     └── anthropic-prod.encrypted
    ├── tokens/
    │     ├── tok_abc123.json         (Simple Token, scope, expiry, usage)
    │     ├── tok_def456.json
    │     └── tok_xyz789.json
    ├── recipients/
    │     ├── recipient-001.json      (the human or system the token was issued to)
    │     └── recipient-002.json
    ├── usage/
    │     ├── 2026-05-14.json         (usage log per day)
    │     ├── 2026-05-13.json
    │     └── ...
    ├── policies/
    │     ├── default-token-policy.json
    │     └── ...
    └── alerts/
          └── (events that warrant operator attention)
```

The vault is encrypted as a whole. The keys inside it are doubly-protected (the vault encryption plus a per-key encryption layer if desired). Tokens are not the keys themselves; they reference the keys via internal lookup.

## The Manager UI

The vault opens with its own app. The app provides:

| Surface | Purpose |
|---------|---------|
| **Key inventory** | List of upstream keys with status, last-used, current quota |
| **Token issuer** | Form to create a new Simple Token with scope, expiry, quota, recipient |
| **Active tokens** | List of issued tokens with usage stats and revoke button |
| **Recipient view** | Per-recipient activity, total cost, current tokens |
| **Usage charts** | Daily/weekly cost trends, model breakdown, recipient breakdown |
| **Audit log** | Recent operations (token issued, token revoked, key rotated) |
| **Alerts** | Tokens approaching quota, keys nearing rate limits, suspicious patterns |

The UI is purpose-built for credential management. It does not pretend to be a general vault viewer.

## The Resolution Service

The Simple Token only works if there is a service that resolves it. Two implementation options:

**Option A: Credential manager hosts a resolution endpoint.** Users (or their tools) call the credential manager's API with their Simple Token; the credential manager returns the underlying key. Simple, but the underlying key ends up in the client's memory.

**Option B: Credential manager proxies the upstream API.** Users call the credential manager's proxy endpoint with their Simple Token; the credential manager translates and forwards the request to OpenRouter (or wherever) using the underlying key; returns the response. Slower, but the underlying key never leaves the credential manager.

Option B is the right one for sensitive keys. Option A is acceptable for cases where the underlying key is less sensitive or the user is highly trusted.

The credential manager should support both. Per-key policy decides which mode is used. For OpenRouter keys distributed to external users: Option B. For development keys distributed to my own tools: Option A is fine.

## The Token Format

A Simple Token is a short, opaque identifier. Format:

```
tok_<random>
```

Examples: `tok_a3f9c2d1e8b4`, `tok_x7m2p9q4r5n6`.

Inside the credential manager, the token resolves to:

```json
{
  "id": "tok_a3f9c2d1e8b4",
  "key_id": "openrouter-personal",
  "recipient_id": "recipient-001",
  "scope": {
    "models": ["claude-sonnet-4-7", "gpt-4o-mini"],
    "endpoints": ["chat/completions"],
    "max_tokens_per_call": 4000
  },
  "limits": {
    "expiry": "2026-08-14T00:00:00Z",
    "total_cost_cap_gbp": 10.00,
    "total_calls_cap": 1000
  },
  "usage": {
    "calls_made": 47,
    "cost_gbp": 1.23,
    "last_used": "2026-05-14T09:30:00Z"
  },
  "issued_at": "2026-05-14T08:00:00Z",
  "revoked": false
}
```

This is what the credential manager stores. The recipient just sees `tok_a3f9c2d1e8b4`.

## The Lifecycle Workflows

The manager vault provides specific workflows:

| Workflow | What It Does |
|----------|--------------|
| **Issue token** | Operator selects a key, sets scope and limits, picks a recipient, generates a token, hands the token to the recipient |
| **Revoke token** | Operator clicks revoke; token immediately stops working; existing in-flight requests fail |
| **Rotate key** | Operator replaces the upstream key (after rotating it at the provider); all tokens that reference it keep working transparently |
| **Adjust scope** | Operator can tighten or loosen a live token's scope without revoking and reissuing |
| **Audit recipient** | See everything a recipient has done with their tokens over time |
| **Set policy default** | Define a default token policy so issuing new tokens is fast and consistent |

Each workflow has a clear UI affordance. None of them are "edit a JSON file"; the manager is a real app.

## How This Plugs Into Other Tools

The infographic generator (and other tools that use upstream models) can integrate the credential manager:

```
User: "Hi, I want to use the infographic generator."
        ↓
Infographic generator: "Do you have a Simple Token, or want one issued?"
        ↓
User: "Issue me one with £5 of credit for two weeks."
        ↓
Credential manager: issues tok_xyz, expiry +14 days, cap £5
        ↓
User: uses tok_xyz with the infographic generator
        ↓
Infographic generator: passes tok_xyz to the credential manager's proxy
        ↓
Credential manager: validates, forwards to OpenRouter, returns response
        ↓
Usage logged in the credential manager vault
```

This is much better than the current "send me your OpenRouter key" pattern. Users do not have to set up an OpenRouter account. We can issue, monitor, and revoke their access cleanly.

## The Pre-Auth Payment Integration

Per the payments brief from earlier today, this gets even better. The credential manager can issue tokens that draw against a user's pre-auth balance:

1. User adds card, gets a £5 pre-auth hold
2. User asks for a Simple Token tied to their balance
3. Credential manager issues a token with effective cap = available pre-auth headroom
4. User's actions draw against both the token's quota AND the user's pre-auth hold
5. Settlement happens at the user level; the credential manager is the metering layer

The credential manager becomes the meter that connects the pre-auth model to the actual upstream costs. This is the operational substrate for charging for use of any LLM-backed feature.

## Sharing And Distribution

A Simple Token is shareable via any channel (WhatsApp, email, in a vault, in a config file). It is short, easy to type, easy to revoke. The flow when a token is compromised:

1. Operator notices anomaly in usage charts
2. Operator clicks "revoke" on the token
3. Token stops working immediately
4. Operator issues a new token to the legitimate recipient if needed

This is far better than the current "the OpenRouter key leaked, now I have to rotate it everywhere" pattern. Granular revocation, no platform-wide rotation needed.

## Security Properties

| Property | How Achieved |
|----------|--------------|
| Underlying keys never leave the credential manager (when using proxy mode) | Option B above |
| Compromised tokens have bounded blast radius | Scope, quota, expiry all limit damage |
| Every action attributable | Tokens are per-recipient |
| Revocation is instant | No cache; check on every request |
| Audit trail complete | Vault commit history captures everything |
| Operator authentication strong | The credential manager vault itself is protected by strong vault auth |

This is the "container of secrets" pattern done correctly. The credential manager vault is a smaller attack surface than a thousand keys distributed via chat apps.

## Second-Order Capabilities

Once the basic credential manager exists, several useful extensions follow naturally:

| Extension | What It Adds |
|-----------|-------------|
| **Multi-provider abstraction** | One Simple Token might map to OpenRouter for some models, Anthropic direct for others, OpenAI for others |
| **Auto-failover** | If OpenRouter is having a bad day, route through Anthropic direct using a different upstream key |
| **Cost optimisation** | Rules like "for sub-100-token calls, use the cheapest provider"; the credential manager picks |
| **Distributed quotas** | A team of users sharing a pool, with per-user fairness limits |
| **Embedded usage caps** | The token enforces caps the upstream provider does not |

None of these are needed for v1. They are the natural growth path.
