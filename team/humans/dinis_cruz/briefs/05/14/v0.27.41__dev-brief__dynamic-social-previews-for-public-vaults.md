# Dynamic Social Previews for Public Vaults

**version** v0.27.41
**date** 14 May 2026
**from** Human (project lead)
**to** Developer (lead), @Dev, @Content
**type** Dev brief

---

## What This Is

When someone shares a public-vault URL in WhatsApp, LinkedIn, Twitter, Slack, or any other surface that auto-generates a preview, the preview is currently weak: a generic title, no description, no image, or worse, a default that has nothing to do with the actual vault contents. The result is that the most powerful sharing channel we have (informal social sharing) under-sells what is on the other side of the link.

This brief defines how public vaults dynamically generate meaningful social previews. The preview becomes a real representation of the vault's contents, dynamically rendered, vault-author-controllable, and useful as a soft pitch even before the user clicks.

## The Problem In Concrete Terms

Today, sharing `https://demo-band.sgraph.app/` in WhatsApp produces (best case) the page title and (typical case) nothing useful. Compare to sharing a YouTube link, a Spotify track, or a Substack post: each generates a rich preview with image, title, description, sometimes inline playback. The bar for "good preview" is high; vaults currently sit below it.

This matters more for **public** vaults than for **private** ones. Private vaults are shared with a specific recipient via tokens; the link does not get pasted into Slack. Public vaults are the marketing surface; the link gets pasted everywhere. The preview is the first impression for everyone who sees the link but does not click it.

## The Standard Mechanism

Social previews are driven by Open Graph (OG) meta tags and Twitter Card meta tags in the served HTML:

```html
<meta property="og:title" content="..." />
<meta property="og:description" content="..." />
<meta property="og:image" content="..." />
<meta property="og:type" content="..." />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:image" content="..." />
```

Every social surface that produces a preview reads some subset of these tags. Getting the tags right is necessary but not sufficient. Getting the image right is what makes a preview compelling.

## What "Dynamic" Means Here

The published vault is dynamic content. The author updates it; the live URL serves the latest version. The preview should track the live content, not be a static asset baked at publish time.

Two things follow:

| Concern | What It Means |
|---------|--------------|
| **The OG image needs to be generated, not authored** | The author should not have to hand-craft a 1200x630 image for every update. A generator produces one from vault content. |
| **The OG image should reflect the current vault state** | If the vault is the band site and the author publishes a new track, the preview image should reflect that. Not a frozen image from launch. |

This is where vault-author control matters: the author should be able to specify what the preview shows (this section's content as the headline, this image as the visual, etc.), but the system should produce sensible defaults so authors who do not configure anything still get a decent preview.

## The Sidecar Approach

The simplest implementation: a **preview sidecar** that runs alongside the vault-serving infrastructure. When a social-platform crawler requests the URL with a known user-agent (e.g. WhatsApp's `WhatsApp/2.x`, Facebook's `facebookexternalhit`, Twitter's `Twitterbot`), the sidecar:

1. Reads the vault's preview configuration (what to use as title, description, image source)
2. Generates the OG image if one is not already cached for this vault version
3. Returns HTML with the OG/Twitter Card meta tags pointing at the right URLs

For non-crawler user-agents (real browsers), the request bypasses the preview sidecar and serves the vault app normally.

This is the same pattern that Vercel, Netlify, and others use for SSR-on-demand for SEO. We use it for OG metadata specifically.

## What Goes In The Image

Different vault types call for different image generation strategies:

| Vault Type | Image Strategy |
|------------|---------------|
| **CV / portfolio** | Headshot or avatar + name + one-line headline ("Senior AI engineer looking for X") |
| **Band / artist** | Cover art for the latest track or release, plus band name |
| **Article / publication** | Headline text + author + publication name, photographic background where applicable |
| **POC / demo** | Title + a screenshot of the most important page |
| **Investor pack** | Logo + tagline + key metric, photographic or geometric background |
| **Catch-all** | Vault name + tagline + author + a deterministic-but-pleasant visual element |

The author picks the strategy (or accepts the default). The image is generated by an image-generation pipeline (could be an LLM with image generation, could be a templated rendering, could be a screenshot of a specific vault page).

## What Goes In The Title And Description

These should be configurable by the vault author but produce sensible defaults:

- **Title**: vault title or first H1 in the rendered output
- **Description**: vault tagline if specified, or first paragraph of the rendered output, truncated to 200 characters

For the band vault: title = band name, description = current-release blurb.
For a CV vault: title = the person's name and role, description = the one-line ask.
For an article: title = article title, description = lede.

## Caching Strategy

OG images cost something to generate (especially if image generation is involved). Caching matters:

| Cache Layer | Purpose |
|------------|---------|
| Generate-once-per-vault-version | When the vault publishes a new version, invalidate the cached preview and regenerate on first crawler hit |
| Edge cache (CloudFront / Cloudflare) | Subsequent crawler hits for the same version serve from edge |
| Author-explicit refresh | The author can force regeneration if a particular preview is wrong |

This means most crawler hits are cheap (cache hit). The first hit per published version pays the generation cost. Acceptable.

## Vault Author Configuration

In the vault, an optional `og-config.json` (or similar) lets the author tune the preview:

```json
{
  "title": "Dinis Cruz - Senior AI Engineer",
  "description": "Building agentic systems for the 2026 enterprise. Looking for Series A-C, fintech, AI-native.",
  "image": {
    "source": "auto",
    "strategy": "cv-headshot",
    "background": "warm"
  },
  "twitter_handle": "@diniscruz"
}
```

If absent, the system generates everything from the vault's existing content and configuration.

## Tying To The "Read Key In The Routing Layer"

A subtle point: the crawler does not have a vault read key. The vault is public (the read key is held server-side in the published-vault routing layer), so the crawler does not need one. The preview sidecar uses the same server-side path as the regular page-rendering for crawlers, reading the vault with the public read key, generating the preview HTML, returning it.

This is consistent with the architecture from the 12 May `sgraph-app-subdomain-registration-workflow` brief: the slug resolves to a share token, the share token gives access to the vault, the rendering happens server-side for crawlers (and possibly some browsers, optionally).

## What This Replaces

For partner sites that currently embed YouTube for video (and pick up YouTube's preview as a side benefit), this removes the temptation. The partner can host their video natively in their vault (per the encrypted video streaming research) AND get a great social preview, without YouTube in the loop.

For our own marketing, this turns every `sgraph.app` URL into a real social asset. Every link shared in WhatsApp, LinkedIn, or Twitter becomes a soft demo of the platform, not just a URL.
