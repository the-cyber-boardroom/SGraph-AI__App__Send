# Vault Chat: Prompt, Context, And Token Management As A First-Class Discipline

**version** v0.27.64
**date** 26 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Designer, Product, @Dev
**type** Arch brief

## What This Is

A zoom-in on one layer of the vault chat architecture (cross-ref: the v0.27.64 vault-chat architecture brief): prompt, context, and token management. The governing thesis: **token and prompt management is not a sideshow, not a nice-to-have, it is something that must happen continuously and be baked into the solution.** The virtual file system (VFS) that the vault chat gives the LLM is the foundation for powerful indexing and memory management, and this brief develops how that memory is managed: by the LLM itself, by sidecar LLMs, and with the discipline of treating every token as carrying context that costs money and dilutes focus.

The project lead: **"every word that we send to an LLM matters, because every word contains context, every word contains information. We need to leverage this, because not only does it keep cost down, more importantly it keeps the focus of the chat."** Token management here serves two ends at once: cost (fewer wasted tokens) and quality (a focused, uncluttered context produces better answers).

This builds directly on the VFS and context-layers model from the architecture brief, and it prepares for vaults about news stories, documents, and information (the facts/hypotheses/evidence direction).

## The Principle: Continuous, Baked-In Token Management

The framing the brief insists on: **prompt and token management happen continuously, by design, not as an occasional cleanup.**

The project lead: **"token management and prompt management is not a sideshow, it's not something that is good to have, it's something that should happen continuously, and is literally something we need to bake into the solution."** The implication is that the vault chat is built around managing what the LLM sees at every turn, not around dumping ever-growing history into the prompt. Every message and response is a candidate for the VFS rather than the live prompt; the live prompt is curated to exactly what the current turn needs.

This is the controlled-universe idea (cross-ref: the architecture brief's VFS-as-the-LLM's-memory) made into a discipline: the VFS holds everything, the prompt holds only what matters now, and the gap between them is actively, continuously managed.

## Learn From The Librarian

The first concrete directive: **learn from the SG/Sentinel project's Librarian, which has already solved much of how to catalogue and serve large content on demand.**

The project lead: **"this is something we should learn from the Librarian of the SG/Sentinel project, because the Librarian has already done huge work on cataloguing large MD files, loading large JSON files, creating a graph-based file system structure that can hold large amounts of content specific to a particular context, but only available on demand."**

The Librarian (cross-ref: the Librarian role work) is directly applicable. Its proven patterns map onto vault chat memory management:

| Librarian Pattern | Vault Chat Application |
|-------------------|------------------------|
| **Cataloguing large MD/JSON** | Cataloguing the VFS contents (every message, file, fact) |
| **Graph-based / fractal structure** | The VFS as a navigable graph, not a flat dump |
| **Finding aids (curated subgraphs)** | Curated views of the VFS for a given task |
| **Context packages compressed to scale** | The prompt assembled at the right size (executive / working / full) |
| **On-demand availability** | Content loaded into the prompt only when needed |
| **Weeding (removing stale/superseded)** | Pruning the live context (without losing the VFS copy) |
| **Provenance** | Facts and evidence traceable to their source |

The lesson: do not reinvent context management; adopt the Librarian's graph-native, on-demand, compress-to-scale approach for the vault chat's VFS. The Librarian has learned how to hold large amounts of context-specific content and serve only what is relevant; vault chat needs exactly that.

## Making The LLM Aware It Should Manage Its Own Memory

The second concept: **the LLM should be told, in the system prompt, that it has tools and a file system and should manage its own memory, including its budget.**

The project lead: **"we need to make the prompt aware that it should be managing its own memory. The first system prompt is more about explaining what is available: you have these tools, you have this file system, you should start by checking what is in the file system. Or we brief it: this is the current structure. And budget management is very important, the LLM itself should be aware of it."**

So the system prompt establishes the rules of the game:

- **What is available**: the tools and the file system (the VFS).
- **How to start**: check what is in the file system, or be briefed with the current structure (which can be in the first prompt).
- **The expectation**: the LLM should manage its own memory (move things to the VFS, keep the live context focused).
- **The budget**: the LLM is told its budget and is expected to respect it.

This turns the LLM from a passive recipient of an ever-growing prompt into an active manager of its own context, operating against an explicit budget. The system prompt is less about the task and more about the environment and the rules.

## LLM-Managed Memory: Self-Pruning

The mechanism: **a tool that lets the LLM prune its own history, strategically, without losing anything.**

The project lead: **"we should have a tool that allows the LLM to prune its own history. The LLM could issue a command to create a file in its own memory (the VFS), and then say, now I don't need all this extra stuff. It's like the compress we tend to do, but strategic, and a compress where we don't lose anything, because everything is still saved on the VFS."**

The model:

1. **Everything is a file in the VFS**: every message, every response is a file. The project lead: **"every message, every response should be a file in the virtual file system."** Nothing is lost; the VFS is the complete record.
2. **The LLM writes a consolidation file**: it can write a file into its VFS memory that consolidates or summarises what it needs.
3. **The LLM drops the detail from the live context**: it then says it no longer needs all the extra detail in the live prompt, because the consolidation (and the originals) are in the VFS.

This is strategic, lossless compression: the live context shrinks to what matters, but everything remains retrievable in the VFS. It is the opposite of a blunt truncation; it is the LLM curating its own working set, with the full record preserved. This can be LLM-triggered (automatic) or user-triggered (manually, especially at first, until it runs reliably automatically), and the user can see and curate it.

## Sidecar LLMs

The third concept, and a powerful one: **a set of sidecar LLMs that maintain the VFS, running alongside the main chat.**

The project lead: **"I would like a set of sidecar LLMs that maintain the virtual file system. I've done this before, and now is the time to bring it in."** The sidecars run with requests and do the memory and analysis work that should not clutter the main chat:

| Sidecar Role | What It Does |
|--------------|--------------|
| **Curation** | Maintain and organise the VFS |
| **Extraction** | Extract facts, references, evidence, ideas, information |
| **History maintenance** | Maintain what actually gets sent to the main LLM |
| **Security checks** | Prompt-injection detection and other security checks |
| **Consolidation** | Compress and consolidate (the memory management) |

Each sidecar is enable/disable-able. The security sidecars are notable: prompt-injection detection and other checks run as sidecars (cross-ref: the SG/Sentinel slow-analysis-fast-enforcement and LLM-never-inline principles, here applied as sidecar analysis alongside the main chat). The sidecars are how the continuous memory management actually happens: rather than burdening the main LLM with all the curation, dedicated sidecars maintain the VFS, extract structure, and check safety, in parallel.

This connects to the main-LLM-stays-focused goal: the main chat does the user's task; the sidecars keep the VFS curated, the facts extracted, the history maintained, and the inputs safe.

## Multi-LLM Consensus

A related capability: **native support to ask the same question to several LLMs and consolidate one answer.**

The project lead: **"we should add native support to ask the same question to three LLMs, and then get one to consolidate the answer."** Asking multiple models and consolidating is a quality and robustness technique (different models, different strengths and failure modes; consolidation reduces single-model error). It fits the sidecar model: the consolidation is itself a sidecar task. It also feeds the graph work below: multiple answers, reconciled, become higher-confidence facts.

## Semantic Knowledge Graphs

Where this leads: **building semantic knowledge graphs of the chat information, stored in the VFS and into a vault.**

The project lead: **"we can start to create semantic knowledge graphs of the information we have in these chats, and that can go into the VFS and directly into a vault."** The extracted facts, references, and evidence (from the sidecars) form a semantic graph, not just flat files. This is the Librarian's graph-native approach (cross-ref above) realised for chat: the chat's information becomes a navigable knowledge graph, catalogued and cross-referenced, stored in the VFS and persisted to a vault. This is the densest, most useful form of the chat's memory, and it is what makes large context manageable (you navigate the graph on demand rather than loading everything).

## Persisting The VFS: Zip Into The Vault

A simple but important persistence mechanism: **when a chat completes, zip the VFS and store the zip in the vault.**

The project lead: **"once the chat is completed, we can take a zip of the virtual file system and add it to the vault, for the cases where we don't want to lose it."** This is the complement to the optional live sync (cross-ref: the architecture brief's VFS-vault sync): rather than syncing every change (many commits), a completed chat's VFS can be zipped and stored as a single artifact in the vault. So there are two persistence options: live sync (step-by-step version control) or end-of-chat zip (a single snapshot), chosen per need.

## Budget Awareness (Including The Cost Of Managing Memory)

A subtle but important point: **the LLM has a budget, is aware of it, and must not spend disproportionately on managing its own memory.**

The project lead: **"budget is very important. We should give a budget to the LLM, and the LLM should be aware of it. The LLM should not spend a disproportionate amount of calls and money on cleaning or pruning itself. There's an interesting balance, because you can go on loops."** The risk is real: an LLM told to manage its memory could spend more on the management than on the task, or loop on pruning. So the budget covers all activity, including the memory management, and the LLM must balance task work against memory work within it. This ties to the OpenRouter budget capabilities (cross-ref: the SG/Send identity-persistence-budgets brief's per-account budgets, and the authentication brief's user's-own-OpenRouter-key) and to cost attribution (cross-ref: the SG/Sentinel cost-attribution brief: every call has a cost).

## Keys In The Vault For Execution

A supporting mechanism the memo added: **store OpenRouter / API keys in the vault, to give to the LLM for execution (making calls, generating infographics).**

The project lead: **"we should store on the vault the OpenRouter keys or API keys that we can give to the LLM to execute, to make calls or to execute for the infographics."** The keys live in the vault (cross-ref: the SG/Send authentication brief's user-dedicated mode storing the OpenRouter key) and are provided to the LLM/tools for execution. This keeps the user's keys in their own vault, and the chat's LLM and tool calls run on them.

## Preparation For Facts, Hypotheses, And Evidence

The forward-looking frame: **this is preparation for vaults about news stories, documents, and information, where facts, hypotheses, and evidence matter.**

The project lead: **"the whole idea of facts, hypotheses, evidence is going to be very relevant once we start adding vaults about news stories. This is the preparation for that, and also vaults about documents and information."** The sidecar extraction (facts, references, evidence) and the semantic knowledge graphs are not just for memory management; they are the groundwork for vaults whose purpose is to hold and reason about facts, hypotheses, and evidence (news stories, documents, research). The vault chat's memory architecture is, in effect, an evidence-graph builder, which is exactly what those future vaults need. This connects to the evidence-graph work (cross-ref: the SG/Sentinel developer-friendliness-and-evidence-graph brief).

## How The Memory Management Is Triggered

Pulling the triggers together, the memo identified three (not mutually exclusive):

| Trigger | How |
|---------|-----|
| **User-triggered** | The user triggers and curates the management, and can see it (especially at first) |
| **Main-LLM-triggered** | The running LLM manages its own memory automatically (prune, consolidate, archive) within its budget |
| **Sidecar-triggered** | Sidecar LLMs maintain the VFS continuously, in parallel |

The project lead: **"it should either happen by the user trigger (for the user to see and curate), or automatically by the LLM's own chat call, or by a set of sidecar LLMs."** Start with user-triggered and manual, move to automatic (LLM and sidecars) as it proves reliable.

## What This Asks For

1. **Treat token/prompt management as a continuous, baked-in discipline** (not occasional cleanup).
2. **Adopt the Librarian's patterns** (graph-native cataloguing, finding aids, compress-to-scale, on-demand, weeding).
3. **Make the LLM aware of its environment and budget** (the system prompt explains tools, the VFS, start-by-checking, and the budget).
4. **Build the self-pruning tool** (the LLM writes a consolidation file to the VFS and drops detail from the live context; nothing lost).
5. **Store every message/response as a VFS file** (the complete record).
6. **Build sidecar LLMs** (curation, fact/evidence extraction, history maintenance, security/prompt-injection checks, consolidation; each enable/disable-able).
7. **Add multi-LLM consensus** (ask several, consolidate one answer).
8. **Build semantic knowledge graphs** (from extracted facts/evidence, into the VFS and a vault).
9. **Add end-of-chat zip-to-vault** (a single snapshot persistence option alongside live sync).
10. **Enforce budget awareness** (including the cost of memory management; avoid loops; via OpenRouter).
11. **Store execution keys in the vault** (OpenRouter/API keys for the LLM and tools).
12. **Support the three triggers** (user, main-LLM, sidecar), starting manual, moving automatic.

Estimated effort: the Librarian patterns are proven and adoptable; the self-pruning tool and every-message-as-a-file build on the VFS from the architecture brief; the sidecars are the larger new build (the project lead has done this before, which de-risks it); the semantic graphs build on the Librarian's graph approach; the budget enforcement uses the existing OpenRouter capabilities.

## What This Does Not Try To Be

- **Not occasional cleanup.** Token management is continuous and baked in.
- **Not lossy truncation.** Pruning is strategic and lossless (the VFS keeps everything).
- **Not main-LLM-only.** Sidecars do the curation and checks in parallel.
- **Not unbudgeted.** The LLM respects a budget, including for memory work.
- **Not a new context system from scratch.** It adopts the Librarian's proven patterns.

## Honest Risks

**Risk 1: The LLM spends its budget managing memory, not doing the task.** Mitigation: explicit budget awareness; balance task vs memory work; sidecars offload management from the main LLM; avoid loops (the memo's explicit concern).

**Risk 2: Sidecars add cost and complexity.** Several LLMs per request costs more. Mitigation: each sidecar is enable/disable-able; run only what is needed; cheaper models for sidecar tasks; cost attributed and budgeted.

**Risk 3: Self-pruning could drop something needed.** The LLM might consolidate away something it later needs. Mitigation: lossless (the VFS keeps everything; the LLM can retrieve); user visibility and curation; the Librarian's weeding (mark superseded, do not destroy).

**Risk 4: Aggressive context curation could bias the LLM.** Curating what the LLM sees shapes its answers. Mitigation: full visibility (the context-layers inspector from the architecture brief); user can see and curate; provenance kept for facts.
