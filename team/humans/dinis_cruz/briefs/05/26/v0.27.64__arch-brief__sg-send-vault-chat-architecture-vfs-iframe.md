# Vault Chat: The Architecture, The Virtual File System, And The Iframe Bridge

## What This Is

A detailed architecture brief for vault chat, continuing the talk-to-the-vault idea (cross-ref: the v0.27.62 talk-to-the-vault brief) and doing it properly: mapping the primitives, the control model, the file systems, the context layers, the fractal element, and the keystone framing. It includes ASCII-art UI mockups and a phased plan, to be agreed before any coding.

The keystone idea the brief builds toward: **Vault Chat is the equivalent of the Vault App.** The same way a vault can be a Vault App (an HTML UI loaded in a sandboxed iframe, talking to the vault through the `window.sg` bridge), a vault can be a Vault Chat (a chat experience loaded in a sandboxed iframe, talking to the vault behind the scenes, with tool-calling and a virtual file system). Vault App and Vault Chat are siblings, both built on the same iframe-bridge primitive.

## The Primitives We Are Leveraging

The brief's premise (and the project lead's agreement with the analysis): **we have multiple primitives already working, and vault chat should leverage them rather than build new ones.**

| Primitive | What It Provides | Status |
|-----------|------------------|--------|
| **The `window.sg` iframe bridge** | How an HTML page in a sandboxed iframe accesses the vault (get-file, read-file, write-file, check-status) | Exists (the Vault App mode) |
| **Tool-calling with visible execution** | The LLM calling tools, with the calls visible | Exists (the tools work) |
| **The virtual file system (VFS)** | A file system the LLM uses (memory), distinct from the vault | Exists (`sg-vfs-bus`, memory/indexeddb/vault providers) |
| **The vault** | The encrypted, version-controlled file store | Exists |

So vault chat is a composition of existing primitives, principally the `window.sg` bridge and the VFS, with the chat and tools layered in.

## Primitive 1: The `window.sg` Iframe Bridge

The access mechanism: **vault chat runs in a sandboxed iframe and accesses the vault through the existing `window.sg` bridge, the same bridge the Vault App mode uses.**

The project lead: **"we should be leveraging the window.sg bridge, the iframe bridge we already have for the Vault App mode. This is how the HTML pages load up access to the vault."** The bridge exposes vault commands (get-file, read-file, write-file, check-status) to the code inside the iframe, over the postMessage channel to the parent (cross-ref: the SG/App runtime: `window.sg`, the VFS bus, the bridge shim).

The big consequence: **vault chat can be developed as a separate, independent app, loaded in an iframe, and tested independently.** The project lead: **"this allows us to develop this whole chat stuff as almost a separate app that we can load up, that is independent, that we can test independently. We probably should do like we did for some of the other pages on the vault, even have a long test page with it, because there are a lot of properties we need to test independently that are not related to the vault."** Because the chat is an iframe app talking through the bridge, it is decoupled from the vault UI: it can be built, run, and tested standalone (with a long test page exercising its properties), then dropped into the vault. This is the same pattern used for other vault pages.

The iframe is also the control boundary: **every chat session is always an iframe, so we always control it.** The project lead: **"the key premise is that every chat session is always an iframe, so we always control it, especially because later we're going to add more restrictions to this, even on the iframe."** Keeping every chat in an iframe means restrictions (sandboxing, CSP, capability limits) can be applied and tightened over time at the iframe boundary.

## Primitive 2: Tools Execution Control

A principle the brief stresses: **tool execution must be controlled, monitored, and visualised, with per-task and per-activity control over which tools are available.**

The project lead: **"one of the very important principles we need to manage, monitor, and visualise is the tools execution. We need very good control, including auto-execute, ask-for-permission, or control the execution. Every time there's a tool execution we should get visibility, see exactly the commands that flow."**

The control model:

| Control | What It Does |
|---------|--------------|
| **Auto-execute** | The tool runs automatically |
| **Ask-for-permission** | The user is asked before the tool runs |
| **Controlled execution** | Finer control over how/whether the tool runs |
| **Visibility** | Every tool execution is visible: the exact commands that flow |
| **Per-task / per-activity availability** | Which tools are available is controlled per task/activity |

The per-task tool availability is important: **every capability is a tool that is available or not.** The project lead: **"we should control the tools per task, per activity. Multiple capabilities are available or not. Even the call to default is a tool, available or not. Create an infographic is a tool, available or not."** So the chat's capabilities are a configurable set of tools, scoped per task: a given chat session (or task within it) has exactly the tools it should, no more. This is the controlled-blast-radius principle (cross-ref: the SG/Sentinel agent-governance brief) applied to the chat: the agent gets exactly the tools the task needs.

## Primitive 3: The Virtual File System (Two File Systems)

The most architecturally significant part: **there are two file systems available to the chat, the vault and a virtual file system (VFS), and the VFS is the LLM's working memory.**

The project lead: **"there are actually two file systems available here. There is the virtual file system that the LLMs can use, that we could also use for memory. This goes back to the conversation about one-shot deployment and controlling the universe the LLM sees."**

| File System | Role |
|-------------|------|
| **The vault** | The real, encrypted, version-controlled file store |
| **The VFS** | A separate file system the LLM uses as working memory, scoped to the chat |

The VFS serves several purposes:

- **The LLM's memory and workspace**: a place the LLM can read and write, separate from the vault. This connects to the one-shot-deployment / control-the-universe idea (cross-ref: the one-shot feedback loops and controlling-the-LLM-context work): the VFS is the controlled universe the LLM sees.
- **Controlled vault access**: instead of giving the LLM full vault access, files are moved from the vault into the VFS for a chat. The project lead: **"we don't give the LLM full access to the vault. We move files from the vault into the virtual file system for this chat."** So the VFS is a curated subset: only what is moved in is visible to the LLM, bounding what it can see and do.
- **Visibility into the prompt**: the project lead: **"we should have very good visibility into what actually goes into that particular prompt and chat that we send to the LLM at any moment."** The VFS plus the context layers (below) make the LLM's input inspectable.
- **A place for interesting workflows**: compression and consolidation. The project lead: **"this is where we can get interesting workflows, like the compressing and consolidation stuff. This is the time to start thinking about that."**

### Optional VFS-Vault Sync (Version Control As A Feature)

The VFS and vault can optionally be synced. The project lead noted the tradeoff and turned it into a feature: **"we could have a mode where we synchronise both. It generates more commits, but that's not a bad thing, because it gives us version control: step-by-step, everything that happens, so we can recreate a lot more."** Syncing the VFS to the vault produces a commit per change, which is a step-by-step version-controlled record of everything the chat did, recreatable and auditable (cross-ref: the vault version-control work). So sync is optional, and when on, the extra commits are a feature (a full execution history), not a cost.

## The Context Layers: What The LLM Actually Sees

A clarifying model the brief establishes: **there are multiple layers that compose what the LLM sees, and all of them are controllable.**

The project lead: **"there are multiple layers: the vault layer that has files, the virtual file system that can have more files accessed during tool calls, the attachments we can include (the files that go into the chat), and the history itself, which we should be able to change, modify, compress, recreate, and manipulate."**

| Layer | What It Is | Control |
|-------|------------|---------|
| **The vault layer** | The vault's files | Accessed via the bridge; not all exposed |
| **The VFS layer** | More files the LLM uses, accessed via tool calls | Curated; moved in from the vault |
| **The attachments** | Files that go into the chat | We control what is attached |
| **The history** | The conversation history itself | Changeable, compressible, recreatable, manipulable |

The history being a manipulable layer is a powerful idea: the conversation history is not fixed; it can be edited, compressed, recreated, and manipulated, which is what enables the chat-about-the-next-chat workflow below. Every layer is inspectable and controllable, giving full visibility into and control over the LLM's input.

## The Fractal Element And Chatting About The Next Chat

Two advanced ideas the brief captures.

### Fractal: Chat About Any Scope

The project lead: **"there's a fractal element. I should be able to have a chat about a document, about a folder, about the whole vault."** The chat's scope is fractal: it can be focused on a single document, a folder, or the entire vault, the same nesting that runs through the vault work (cross-ref: the sub-vaults and fractal-architecture work). The scope determines what is moved into the VFS for the chat.

### Chat About The Next Chat's Context

The striking idea, enabled by history-as-manipulable-files: **store the chat history as JSON files in a vault folder, then have one chat edit the files that control what the next chat sees.**

The project lead: **"if we have a JSON file that contains the current chat history, the chat history is a bunch of files we store in a vault folder. Then I could have two chats side by side, one reading that as the next conversation. One chat session edits that file, which controls the experience and the universe the other chat sees."**

The workflow: the chat history is a set of files (synced to the vault, so version-controlled); one chat session edits those files; a second chat session reads them as its starting context. So you can have a chat *about* the prompts, conversation, and history that the next chat will use, curating the universe of the next conversation. This is controlling-the-LLM-context taken to its conclusion: the context is editable data, and editing it is itself a chat-able activity. It is a powerful basis for the compression/consolidation workflows and for deliberately shaping what an LLM session sees.

## The Keystone: Vault Chat Is The Equivalent Of Vault App

The framing the brief builds toward: **Vault Chat is to chat what Vault App is to HTML UIs, the same primitive, a different surface.**

The project lead: **"the same way we have the Vault App, we should have the Vault Chat. That's the direction of travel. The Vault Chat is the equivalent of the Vault App, but I'm talking to the vault behind the scenes, with access to all these capabilities, including the ability to view the apps and HTML created from the chat session."**

| Vault App (exists) | Vault Chat (this brief) |
|--------------------|--------------------------|
| An HTML UI in a sandboxed iframe | A chat experience in a sandboxed iframe |
| Talks to the vault via `window.sg` | Talks to the vault via `window.sg` |
| Renders a custom UI from vault files | Converses about and acts on vault files, with tools |
| Author drops in `index.html` + `app.json` | A chat session, simple to complex |

And they compose: the Vault Chat can view the apps and HTML it creates (the chat generates an HTML app, and the Vault App machinery renders it). The two are siblings on the same iframe-bridge primitive, and the chat can produce apps that the app machinery displays. This is the elegant unification: one iframe-bridge primitive, two surfaces (app and chat), that compose.

## The Plan (Before Any Coding)

A phased plan, as requested, to agree before coding.

| Phase | Scope | Deliverable |
|-------|-------|-------------|
| **0. Standalone shell** | A standalone chat app in an iframe, with a long test page, decoupled from the vault | The chat runs and is testable independently |
| **1. Bridge wiring** | Connect the chat to the vault via `window.sg` (read-file, write-file, check-status) | The chat reads and writes the vault through the bridge |
| **2. Tools + control** | Tool-calling with visible execution; auto/ask/controlled modes; per-task tool availability | Controlled, visible tool execution |
| **3. The VFS** | The virtual file system as the LLM's working memory; move files vault to VFS; the context layers inspector | The LLM sees a curated universe; full prompt visibility |
| **4. Sync + history** | Optional VFS-vault sync (version control); history as manipulable files | Step-by-step version-controlled execution; editable history |
| **5. Fractal + next-chat** | Chat scoped to document/folder/vault; chat-about-the-next-chat | Fractal scope; context curation across chats |
| **6. Vault Chat = Vault App sibling** | Vault Chat as a first-class vault surface; view created apps/HTML | The keystone: Vault Chat alongside Vault App |

Start with Phase 0 (the standalone shell), because the chat is decoupled and the properties to test are not vault-related. The project lead: **"we should start by creating literally a standalone, almost outside-the-vault chat experience, or a very simple vault UI."**

## What This Asks For

1. **Build vault chat as a standalone iframe app first** (decoupled, independently testable, with a long test page).
2. **Access the vault via the `window.sg` bridge** (read/write/status; the Vault App bridge).
3. **Keep every chat session in an iframe** (the control boundary; restrictions tightenable later).
4. **Build the tools control model** (auto/ask/controlled execution; visible commands; per-task tool availability).
5. **Build the VFS as the LLM's working memory** (curated subset moved in from the vault; full prompt visibility; compression/consolidation workflows).
6. **Make the context layers inspectable** (vault, VFS, attachments, history; all controllable).
7. **Add optional VFS-vault sync** (version-controlled, step-by-step execution history).
8. **Support fractal scope and chat-about-the-next-chat** (document/folder/vault; history-as-editable-files).
9. **Establish Vault Chat as the Vault App sibling** (a first-class vault surface; view created apps/HTML).
10. **Agree this plan and the UIs before coding.**

Estimated effort: Phases 0 to 2 are the near-term core (standalone shell, bridge, tools control) and reuse existing primitives; Phase 3 (VFS) builds on the existing `sg-vfs-bus`; Phases 4 to 6 are the richer capabilities. The decoupled iframe approach lets each phase be built and tested independently.

## What This Does Not Try To Be

- **Not new primitives.** It composes the `window.sg` bridge, the VFS, and the tools.
- **Not full vault access for the LLM.** The VFS is a curated subset; the LLM sees what is moved in.
- **Not coding yet.** This is the plan and the UIs to agree first.
- **Not a final UI.** The mockups are starting points to try.

## Honest Risks

**Risk 1: Scope is large.** This is a rich architecture. Mitigation: the phased plan; start with the standalone shell; each phase is independently testable; reuse existing primitives.

**Risk 2: Tool execution with write access is powerful.** Auto-executing write tools could change the vault unexpectedly. Mitigation: the auto/ask/controlled model; visible commands; per-task tool availability; VFS curation (the LLM acts on the VFS, synced deliberately); version control via sync.

**Risk 3: Context manipulation could mislead.** Editing history and curating the universe could produce confusing or misleading LLM behaviour. Mitigation: full visibility (the layers inspector, view-full-prompt); it is a deliberate, inspectable capability; version control records what was done.

**Risk 4: VFS-vault sync generates many commits.** Mitigation: sync is optional; the commits are a feature (execution history) when on; off by default for casual chats.
