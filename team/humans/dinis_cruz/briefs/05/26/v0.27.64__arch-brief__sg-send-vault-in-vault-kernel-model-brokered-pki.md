# Vault-In-Vault: The Kernel Model, Brokered Access, And PKI Between Vaults

**version** v0.27.64
**date** 26 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, Designer, @Dev
**type** Arch brief

---

## What This Is

A deepening of the vault-in-vault (VIV) design, which the project lead considers **probably one of the most important features to add after sgit, because it makes the vault usable in a lot of real-world capabilities.** It builds on the sub-vaults workflow and conventions (cross-ref: the v0.27.62 sub-vaults-workflow and vault-conventions briefs) and the vault-chat iframe architecture (cross-ref: the v0.27.64 vault-chat architecture brief), and it lands on a cleaner, unified model: **accessing data within a vault and accessing data across vaults are the same thing.**

The governing discipline the project lead stressed: **get the design right, and simplify it, because VIV is very easy to make complex** (the first implementation already shows this). This brief aims for the simplest model that works: one primitive, no-origin iframes, a kernel that can talk to its host, brokered and logged access, and PKI on every message.

## What We Already Got Right

The project lead noted several foundations already in place that this design leverages:

| Foundation | Status |
|------------|--------|
| The vault knows how to behave in an iframe / nested context | First pass done |
| Mapping privileges inside the app | First pass done |
| PKI | First pass done |
| The SG API for an app (iframe) to talk to the vault host | Done (the `window.sg` bridge) |

So this is a refinement of working foundations, not a fresh start. The brief adds the kernel-talks-to-host idea, the brokered/logged access, per-request credentials, the visualisation, and PKI on every message.

## The Unification: Within-Vault And Across-Vault Access Are The Same

The central simplification: **accessing data within a vault and accessing data in another vault are the same operation. The primitive is the same; what differs is what you can do, what you can get, and who is getting it.**

The project lead: **"we are unifying how you access data within the vault and across the vault, so it's the same thing. The primitive should be the same; it's just what you can do, what you can get, and who's getting it that is different."**

This is the key insight that keeps the design simple. Rather than a special mechanism for nested vaults, the same access primitive serves both: asking for a file is asking for a file, whether it is in this vault or a linked one. When a linked vault is involved, the request relays to it; if that vault links to another, the relay recurses. So the whole tree of vaults is accessed through one uniform primitive, with the differences captured in capabilities and identity, not in separate code paths.

## No-Origin Iframes: The Isolation Model

The isolation mechanism: **everything uses no-origin iframes, which protect both the host and the client. Only the top-level vault has an origin.**

The project lead: **"we're going to be using iframes with no origin for all of this, because it works quite well and gives a good level of isolation. It protects both the host and the client from a lot of things."**

The origin model is precise and important:

| Vault | Origin? | Why |
|-------|---------|-----|
| **The top-level (host) vault** | Has an origin (a URL) | It needs the URL to read the hash and read local storage |
| **Every nested vault** | No origin | Everything is given to it or controlled by it |

The project lead: **"the only difference with the host top-level vault is that it has an origin, because it literally has a URL. Every vault after that should not have that. The top-level host origin needs to exist because that's how it reads the hash and reads local storage, and that's literally it. Everything else should be either given to it or controlled by it."**

So the top-level vault's origin exists for exactly one purpose: to bootstrap from the URL (read the hash, read local storage). Every vault below it has no origin and receives everything it needs from its parent. This means **a vault must be able to receive secrets from a parent and know it can be embedded.** The project lead: **"the vault has to have a concept of receiving secrets from a parent, and a concept that it could be embedded in something else."** A vault is no longer assumed to be top-level; it must work as an embedded, no-origin, parent-provisioned component.

## The Kernel Model: A Kernel Can Talk To Its Host

The reframing that unlocks read-write across vaults: **call the vault the kernel. The kernel's app can talk to the kernel (the existing SG API). The new idea is to let the kernel talk to its host.**

The project lead: **"think about it like the vault, we should call it the kernel. The kernel's app can talk to the kernel. The idea is to allow the kernel to talk to its host. If we do that, we immediately solve the read and write problem."**

The existing model: an app (HTML in an iframe) talks to its vault (kernel) through the bridge, governed by a policy. The new model adds: a kernel, embedded in a parent kernel, can talk to that parent. And because an app could itself be another vault (an iframe hosting a kernel), you get nesting:

```
   Kernel A (host vault)
   |-- App A           (HTML in iframe, talks to Kernel A via SG API)
   `-- Kernel B        (another vault, in an iframe inside Kernel A)
         `-- App B     (HTML in iframe, talks to Kernel B)
```

The project lead: **"the vault inside its HTML code can open an iframe, which we call an app, and an app could be an HTML page, but could actually be another vault. So you can have a vault directly hosting a vault as an iframe. The difference is the capabilities."**

### The Directional Trust: A To B, Never B To A

The crucial security property: **traffic flows from the parent kernel to the child, never the reverse.**

The project lead: **"if Kernel A opens an iframe with Kernel B, and I give it a secret (read-only, read-write), now you can have traffic from Kernel A to Kernel B, never the other way around. Kernel A could ask for data and ask to write data to Kernel B."**

So Kernel A (the parent) can ask Kernel B (the child) for data and to write data, governed by the secret A gave B. But B cannot reach back into A. This directional trust is the backbone of the security model: a child gets exactly the capability its parent grants (via the secret), and can never escalate to its parent. It is the controlled-blast-radius principle (cross-ref: the SG/Sentinel agent-governance brief) realised structurally: capability flows down, never up.

## Per-Request Versus General Credentials

A flexible credential model: **credentials can be granted generally, or per single request, relying on the fact that data is not stored.**

The project lead: **"the credentials could be provided in general, or for one request. Say Kernel A has read-write credentials, opens Kernel B with only read-only, but we want to write something: we make one request where we pass the token, and it can then do that. Or we just give it the read-write token and ask for the file."**

| Grant | Use |
|-------|-----|
| **General** | The child holds a standing capability (e.g. read-only) for its lifetime |
| **Per-request** | A higher capability (e.g. read-write) passed for a single request, then gone |

This is least-privilege with elevation: grant the child the minimum standing capability (read-only), and pass a higher token only for the specific request that needs it (a one-off write). Because the data is not stored (cross-ref: the ephemeral and zero-knowledge stances), the per-request token does not persist. This gives fine-grained control: a child operates at low privilege by default, elevated only momentarily and only for what is needed.

## Who Has Credentials Versus Who Is Accessing

A subtle distinction the model makes explicit: **the method of access is the same; what differs is who holds the credentials versus who is accessing.**

The project lead worked through the cases: **"if Kernel A starts App A, and Kernel A has mounted another vault (Kernel B) as a link, then when App A asks for a file from Kernel B, it goes through Kernel A. But if Kernel A opens App A and App A has the credentials to open Kernel B inside App A, then it's App A who's calling. So it becomes about who actually has the credentials versus who's accessing it, but the method is the same."**

| Scenario | Who Holds B's Credentials | Who Calls B |
|----------|---------------------------|-------------|
| A mounts B; App A asks for a B file | Kernel A | The request relays through Kernel A |
| App A holds B's credentials directly | App A | App A calls B directly |

The method (ask for a file through the bridge) is identical; the difference is which party holds B's credentials and therefore who is really the caller. This keeps the implementation uniform (one method) while the trust analysis (who is authorised) varies by who holds the credentials. The design goal the project lead stressed: **make this as easy and smooth as possible**, which the single-method model achieves.

## Mounting A Vault As A Link Is Just An App

The unification in practice: **mounting a vault as a link is, behind the scenes, just an app. Asking for a file in a linked vault relays to it; if the link points to another vault, you recurse.**

The project lead: **"if we mount the vault as a link, the link is now just an app behind the scenes. When we ask for a particular file in a particular vault, it's a matter of relaying to it: can you go and get it. And if that's a link to another vault, you do the thing recursively."**

So a linked (mounted) vault is an app (a no-origin iframe hosting a kernel), and accessing its files is relaying the request to it. Nesting is recursion on this one primitive: a request descends the tree of linked vaults, relaying at each level, governed by the credentials at each hop. This is the unification made concrete and is why the design stays simple despite arbitrary nesting.

## The Broker: Side-By-Side Kernel That Logs Everything

A key new component: **a broker that mediates all requests between vaults, logs every request, and captures everything that happens between them. It runs inside the kernel as a side-by-side kernel.**

The project lead: **"we need a component that becomes the broker for all requests, logs every single request, and captures everything that happens in between the vaults, in between the multiple transactions. This runs inside the kernel as a side-by-side kernel, the same way we have for other messages."**

The broker is the control and visibility point for inter-vault access:

- **Mediates all requests** between vaults (every A-to-B request goes through it).
- **Logs every request** (a complete record of inter-vault access).
- **Captures everything** in between (the full inter-vault transaction history).
- **Can require authorisation per request**: the project lead: **"we could have a permission set, the ability to run it automatically, or to say: Vault A just asked for this, App A just asked for this from Vault B, do you want to authorise it?"** So inter-vault access can be auto-allowed (by policy) or prompt the user per request.

The broker is a sidecar (cross-ref: the prompt-context brief's sidecar LLMs, and the SG/Sentinel side-by-side analysis pattern): it runs alongside the kernel, not inline, brokering and logging. This gives VIV the same visibility-and-control discipline as the rest of the platform: every inter-vault access is brokered, logged, and (optionally) authorised.

## PKI On Every Message

The security foundation: **all inter-vault messages use public and private keys, encrypted and signed, so only the right recipient can read or execute them.**

The project lead: **"all of this should be done using public and private keys, so we encrypt all the messages and sign all the messages, which means only the right recipients can read it."**

Each vault, on start, has a public/private key pair. Messages between vaults are encrypted to the recipient and signed by the sender, so:

- Only the intended recipient can read a message (encryption).
- The recipient can verify the sender (signing).
- A message arriving in the wrong place cannot be read or executed.

The project lead noted a benefit beyond security: **"this picks up lots of bugs, because if the wrong message arrives in the wrong place, it can't be executed, it can't even be read."** PKI on every message is also a correctness mechanism: misrouted messages fail safely (unreadable) rather than executing in the wrong context. This is defence in depth and a debugging aid at once.

### Where The Keys Come From

The project lead identified two cases for how a vault gets its keys, and both are valid:

| Case | How |
|------|-----|
| **Given by the parent** | The parent provides the key pair; the child asks for it (the common case) |
| **Created and sent upward** | The child creates its own pair and sends the public key up |

The project lead: **"each vault, when it starts, needs a public and private key. Is it given to it from its parent, or created and given upwards? It can go both ways. In most cases it should be provided by the parent. But I like the one-use-only key idea: the parent gives a public/private key to the child, the child uses that to create its own pairs, then sends up the public key."** So the elegant bootstrap is: the parent gives the child a one-use key pair; the child uses it to generate its own real pair and sends its public key back up; thereafter they communicate securely. The open question the project lead flagged: **does the parent need to have the child's private key or not?** (a monitoring-versus-isolation tradeoff, below).

## Vaults Can Refuse: Policies Limiting Callers

A vital property: **a vault can have a policy that limits what its callers can do, and can refuse to respond or provide data regardless of what a caller says.**

The project lead: **"the vault has the ability to say I'm not going to respond, or I'm not going to provide some data to my callers. I'm not going to allow my callers, regardless of what they say. You can have a policy that limits what the callers to a vault can do."**

So capability is not only granted by the parent (downward); the child vault itself enforces a policy on what it will do for callers. This is two-sided control: the parent grants a capability, and the child can still refuse beyond its own policy. It matters because a vault may be opened by an app or another vault that holds credentials, and the vault must be able to enforce its own limits regardless of those credentials.

The project lead drew an important distinction for the policy: **distinguish a caller that provided a credential from a caller that did not.** A vault treats a credentialed caller differently from an uncredentialed one. This is the basis of the policy: what an uncredentialed caller can do (likely little or nothing), versus what a credentialed caller can do (per the credential), versus what the vault's own policy allows regardless. This also covers the case where **the user provides the credentials inside the vault** (the project lead: an app opens a kernel, and the user inside that vault provides the credentials), where only the iframe knows the credentials.

## Visualisation: The Vault-In-Vaults Page

A new UI the project lead wants: **a vault-in-vaults page that visualises the open vaults (iframes) side by side.**

The project lead: **"we need a new page, maybe call it vault/vaults or vaults-in-vaults, where we visualise the iframes we have open, so we can open them all side by side."** With potentially many nested vaults open, a dedicated page shows them together, with the broker's per-request authorisation surfaced here (the authorise-this-inter-vault-request prompts). This is the operator's view of the VIV tree: what is open, what is talking to what, what is being requested, and what to authorise.

```
+- VAULTS IN VAULTS -------------------------------------------------+
|  +- Kernel A (host) ------+   +- Kernel B (linked, read-only) ---+ |
|  | files: report, data    |   | files: results, notes           | |
|  | app: dashboard         |   | (no origin; provisioned by A)   | |
|  +------------------------+   +---------------------------------+ |
|  +- BROKER LOG ----------------------------------------------------+ |
|  | A -> B  read results.csv          [auto]  ok                   | |
|  | A -> B  write summary.md          [ask ]  authorise? [y] [n]   | |
|  | (all inter-vault requests logged, signed, encrypted)           | |
|  +-----------------------------------------------------------------+ |
+----------------------------------------------------------------------+
```

## Tree View Compatibility

A requirement: **the tree view (with links) is 100% compatible with this, using the iframe app to get the data.**

The project lead: **"all of this should be transparent to the tree view. The tree view with the links should be 100% compatible. The difference is the tree view uses the iframe app to get the data. If I expand the tree view of a linked vault, that should create the Vault app and implement the connection."**

So expanding a linked vault in the tree view is not a special operation; it creates the Vault app (the no-origin iframe hosting the linked kernel) and establishes the connection, then reads through it. The tree view is a consumer of the same unified primitive: a linked node expands by mounting the vault as an app and relaying. This keeps the familiar tree-view UX while it runs on the new VIV machinery underneath.

## A New CLI / REPL-Style UI

A capability the model suggests: **a new SG-API-style UI, almost a JavaScript/CLI/REPL, to communicate with vaults without opening the full UI.**

The project lead: **"we need a new UI for the vault, almost an SG-API-style UI, a JavaScript or even CLI UI, even a REPL. Because if Vault A opens an iframe of Vault B, you don't need the whole UI at that moment, you don't need everything."** When one vault accesses another programmatically, loading the full vault UI is wasteful; a CLI/REPL-style interface to the SG API is enough (run a command, get a file). But the full UI must still be supported for the cases that need it:

- **App opens the full UI of another vault** (for usability: the user interacts with the whole vault).
- **App opens a kernel, and the user inside that vault provides the credentials** (user-supplied auth inside the embedded vault).

So there is a spectrum: a lightweight CLI/REPL for programmatic access (the common inter-vault case), and the full UI when a human needs to interact. Both run on the same primitive.

## The Monitoring-Versus-Isolation Tradeoff

A recurring tradeoff the project lead flagged across the keys and the broker: **whether you want to see the messages or not.** In debug mode, you may want the broker (or the parent) to see inter-vault messages; in maximum-isolation mode, the messages are end-to-end encrypted so even the parent cannot read them (the child generates its own keys, the parent does not hold the private key). The project lead: **"it depends, from a monitoring point of view, if you want to see the messages or not. In debug mode we do some stuff, and we don't otherwise."** So the design supports both: full visibility for debugging, full isolation for sensitive cases, chosen per need. This is the same logging-mode spectrum seen elsewhere (cross-ref: the SG/Sentinel vault-aware logging brief).

## What This Asks For

1. **Unify within-vault and across-vault access as one primitive** (what differs is capability, what you get, and who is getting it).
2. **Use no-origin iframes for all nested vaults** (only the top-level vault has an origin, for the hash and local storage).
3. **Make a vault able to receive secrets from a parent and be embedded** (a vault is not assumed top-level).
4. **Implement the kernel-talks-to-host model** (a kernel can talk to its parent; capability flows down, never up).
5. **Support general and per-request credentials** (least-privilege standing capability; momentary elevation per request; data not stored).
6. **Mount a vault as a link (an app); relay and recurse** (one primitive for arbitrary nesting).
7. **Build the broker** (mediates, logs, and captures all inter-vault requests; a side-by-side kernel; optional per-request authorisation).
8. **Use PKI on every message** (encrypt and sign; only the right recipient reads/executes; the bug-catching benefit; keys given by parent or created-and-sent-up, with the one-use bootstrap key).
9. **Let vaults enforce their own policies** (refuse callers regardless of credentials; distinguish credentialed from uncredentialed callers; support user-supplied credentials inside the vault).
10. **Build the vault-in-vaults visualisation page** (open vaults side by side; the broker log and authorisation prompts).
11. **Keep the tree view 100% compatible** (expanding a linked vault creates the Vault app and connects).
12. **Add a CLI/REPL-style SG-API UI** (lightweight programmatic access; full UI still supported when a human interacts).
13. **Support the monitoring-versus-isolation choice** (see messages in debug; end-to-end isolation otherwise).
14. **Above all, keep the design simple** (one primitive; resist complexity).

Estimated effort: substantial but built on working foundations (the bridge, privileges, PKI first passes). The unification and the kernel-talks-to-host model are the core; the broker is a focused sidecar; PKI-on-every-message extends the PKI first pass; the visualisation, tree-view compatibility, and CLI/REPL are UI work. The project lead's priority framing (the most important feature after sgit) and simplicity discipline should guide sequencing.

## What This Does Not Try To Be

- **Not native nested-vault support.** It is the unified primitive plus no-origin iframes and the broker, kept simple.
- **Not upward capability.** Capability flows parent-to-child, never child-to-parent.
- **Not credentials-override-policy.** A vault enforces its own policy regardless of caller credentials.
- **Not full-UI-only.** A CLI/REPL serves programmatic access; the full UI is for human interaction.
- **Not a complex design.** The explicit goal is the simplest model that works.

## Honest Risks

**Risk 1: VIV is very easy to make complex.** The project lead's central caution. Mitigation: the unification (one primitive); no-origin iframes; the kernel model; resist special cases; get the design right before building.

**Risk 2: Inter-vault access is a powerful surface.** A vault reaching into another is significant. Mitigation: directional trust (down only); the broker logs and can authorise every request; PKI on every message; per-request least-privilege; vaults enforce their own policies.

**Risk 3: PKI on every message adds overhead.** Encrypting and signing every inter-vault message costs. Mitigation: the security and bug-catching benefits justify it; the monitoring-vs-isolation choice lets debug mode relax it; measure performance.

**Risk 4: The key-bootstrap and parent-holds-private-key question affects isolation.** Whether the parent can read child messages is a real tradeoff. Mitigation: support both (parent-provided keys for monitoring; child-generated keys for isolation); the one-use bootstrap key; choose per need.

**Risk 5: Many open vaults could be heavy.** Many no-origin iframes and brokered channels. Mitigation: the CLI/REPL avoids loading full UIs; pre-initialise on access (cross-ref: the sub-vaults brief); the visualisation page manages what is open.
