# The Commit Queue: Batched Auto-Sync And Staging For The Main Vault

**version** v0.27.64
**date** 26 May 2026
**from** Human (project lead)
**to** Vault team, Architect, Developer (lead), @Dev
**type** Dev brief

---

## What This Is

A focused performance feature for the main vault UI: **a commit queue that batches changes over a configurable time window into a single commit, instead of committing and pushing on every individual file change.** The driver is the vault chat work (cross-ref: the v0.27.64 vault-chat architecture and prompt-context briefs): once the chat is syncing a virtual file system to the vault, and generating many files in bursts, the current every-change-is-a-commit behaviour would produce a flood of commits and network calls. The commit queue solves that, and also fixes an existing problem (the drop-a-folder-as-one-commit hack).

This is a main-vault-UI feature (the vault mothership), not an iframe feature. It is largely invisible in normal use, with an optional staging view for visibility.

## The Problem: Every Change Is A Commit And A Push

The current behaviour is the most aggressive possible auto-commit: **every single file change generates a commit and a push.** The project lead: **"what we have right now is the most aggressive auto-commit, where every file change generates a commit and a push."**

This is about to become a problem, for three reasons:

| Concern | Why It Matters |
|---------|----------------|
| **Race conditions** | Many rapid commits can introduce race conditions |
| **Network-call explosion** | Every commit generates many network calls; these are not optimised yet, so they will slow down significantly under volume |
| **The chatty vault chat** | The vault chat (cross-ref: the architecture brief) generates lots of files, often in bursts, especially when syncing the VFS to the vault |

The project lead named the chat as the trigger: **"especially on the vault chat, where we now have a very chatty (pun intended) environment generating lots and lots of files, we don't want to generate one commit for everything."** A chat that writes many files per turn, each triggering a commit and push, would overwhelm the current unoptimised commit path.

There is also an existing problem this addresses: **the drop-a-folder case.** The project lead: **"this should solve a problem we already have: when you drop a folder, we tried to make it send only one commit, but that was a hack, and it didn't work very well."** Dropping a folder (many files at once) was hacked to produce one commit; the queue replaces that hack with a proper mechanism.

## The Solution: A Timer-Windowed Commit Queue

The mechanism: **a queue where a change starts a timer, and the commit happens only at the end of the timer, batching everything in the window into one commit.**

The project lead: **"as soon as a change occurs, you start a timer, count down that timer, and only do the commit at the end. The auto-commit only happens on that period."** The window is configurable:

| Setting | Behaviour |
|---------|-----------|
| **Zero** | The current behaviour (commit on every change) |
| **1s / 5s / 10s / 30s / 60s** | Batch all changes within the window into one commit |

So a change starts (or extends) the timer; further changes within the window join the batch; when the timer fires, one commit captures all of them and pushes once. The project lead: **"if you make five changes to a file and save it, within that window you still only commit once. You start sending batches of 1, 2, 3, 5, 10, 20 files in one go."**

The configurability matters: zero preserves today's behaviour (nothing breaks for those who want every-change commits), and a window of 10 to 15 seconds (the project lead's suggested range) batches the bursts. It is a setting, not a hardcoded behaviour.

### The One Trade-Off

The project lead identified the single side effect honestly: **if the same file is changed multiple times within the window, the intermediate states are not kept as separate history.** The project lead: **"the only side effect is if the same file gets changed in a way you want to keep a history, but that is very rare."** Batching means five rapid edits to one file in the window become one commit, not five, so the intermediate versions are not individually recorded. The project lead judged this rare and acceptable: most bursts are many different files (the chat case), not repeated edits to one file you want versioned. Setting the window to zero recovers per-change history where it is wanted.

## Staging: Making The Queue Visible

The project lead worked through whether this should be invisible and concluded it deserves a visible staging concept: **pending files that have not yet been committed or pushed, with a control pane to see the auto-add-and-drain.**

The project lead: **"this would be absolutely invisible. Actually, maybe not. We could add the concept of staging, so there are pending files that haven't been pushed or committed. We need a new control pane and a debug window to see this auto-adding and draining of the changes."**

So the queue is largely invisible in normal operation, but a staging view makes it inspectable:

- **Pending (staged) files**: files changed but not yet committed (waiting for the timer).
- **The auto-add-and-drain**: the control pane shows changes being added to the queue and then drained (committed) when the timer fires.
- **A debug window**: for visibility into the queue's operation.

This is a familiar concept (staging, as in Git's staging area), here showing what is queued for the next batched commit. It gives visibility and debuggability to a mechanism that would otherwise be opaque. The project lead noted it needs a little thinking on exactly how to present it, but the staging concept is the right model.

## Asynchronous Operation And Conflicts

The queue operates asynchronously: **changes accumulate, the timer drains them into a commit, and as more changes come they queue for the next drain.** The project lead: **"if a file is being changed all the time, you cut one moment in time and commit those, and as more files come through, you commit them. This works nicely asynchronously."**

On conflicts, the project lead noted the existing conflict-resolution capability and a simple policy: **if a batched commit hits a conflict, abort that batch.** The project lead: **"the only problem is if there are conflicts, but we already have a way to solve conflicts. Maybe if there's a conflict, abort this. In most cases it should work."** So the queue uses the existing conflict resolution (cross-ref: the vault version-control and conflict work), and the fallback for a conflicted batch is to abort/cancel it rather than force it. In most cases (especially the chat's many-different-files bursts) there is no conflict and the batch commits cleanly.

## Where It Lives: The Vault Mothership, Not The Iframe

An important scoping point: **this is a feature of the main vault UI (the mothership), not the iframe.** The project lead: **"this is the vault mothership, the vault main UI, not inside the iframe."**

The commit queue sits in the parent vault UI that owns the actual vault sync, below the chat. The vault chat (in the iframe, cross-ref: the architecture brief) generates file changes through the bridge; those changes flow to the main vault UI, which queues and batches them. So the chat does not manage commits; it just makes changes, and the mothership's commit queue batches them. This keeps the concern in the right place: the iframe app is decoupled from the commit mechanics, and the parent handles efficient persistence.

## Why This Matters Now

The timing is driven by the vault chat. Without the commit queue, the chat's VFS-vault sync (cross-ref: the prompt-context brief's optional sync, and the architecture brief's version-control-as-a-feature) would generate a commit per file, flooding the unoptimised commit path. With the queue, the chat's bursts of files batch into occasional commits, keeping the version-control benefit (a recorded history) without the per-file cost. So the commit queue is what makes the chat's sync practical: you still get step-by-step version control, but batched sensibly.

It also helps every other case (dropping folders, bulk edits, any burst of changes), so it is a general vault performance feature, not only a chat enabler.

## What This Asks For

For the vault team:

1. **Build a commit queue on the main vault UI** (the mothership, not the iframe).
2. **Batch changes over a configurable time window** (zero = current behaviour; 1/5/10/30/60s options; ~10 to 15s a sensible default).
3. **Start/extend a timer on change, commit-and-push once at the end** (batching all changes in the window).
4. **Replace the drop-a-folder hack** with the queue (one proper batched commit).
5. **Add a staging concept and control pane** (pending files; the auto-add-and-drain; a debug window).
6. **Operate asynchronously** (accumulate, drain, repeat).
7. **Use the existing conflict resolution; abort a conflicted batch** (the fallback).
8. **Make the window configurable in settings.**

Estimated effort: moderate and well-bounded. The queue-and-timer is a focused mechanism; the staging view needs some UX thinking (the project lead flagged this); conflict handling reuses the existing capability. It is a contained vault-team feature with clear value.

## What This Does Not Try To Be

- **Not an iframe feature.** It lives in the main vault UI (the mothership).
- **Not a replacement for per-change history when wanted.** Setting the window to zero recovers today's behaviour.
- **Not always invisible.** The staging view makes it inspectable and debuggable.
- **Not a new conflict mechanism.** It uses the existing conflict resolution; aborts a conflicted batch.

## Honest Risks

**Risk 1: Batching loses intermediate single-file history.** Multiple edits to one file in a window become one commit. Mitigation: judged rare (bursts are usually many files); the window is configurable (zero recovers per-change history); document the behaviour.

**Risk 2: A crash mid-window could lose queued changes.** Changes pending in the queue (not yet committed) are at risk if the UI crashes. Mitigation: the staging view shows pending state; consider persisting the queue; keep windows short enough to bound exposure.

**Risk 3: Conflicts on a batched commit.** A batch could conflict. Mitigation: the existing conflict resolution; abort the conflicted batch as the fallback; most bursts (different files) do not conflict.

**Risk 4: Staging UX could add complexity.** A new control pane and debug window add surface. Mitigation: invisible by default; the staging view is for visibility/debugging; keep it simple (the project lead flagged it needs thinking).
