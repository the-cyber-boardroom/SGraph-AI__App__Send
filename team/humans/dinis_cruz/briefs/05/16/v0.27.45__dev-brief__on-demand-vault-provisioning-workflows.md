## What This Is

A consolidation memo covering several related developments around **on-demand vault provisioning via DNS-pinned EC2 instances**. The voice memo reports on something that genuinely worked end-to-end (the first time we are saying that about this workflow), names the specific technical wrinkle we hit in practice (DNS pinning persisting from the wildcard-cert holding page), and proposes several UX patterns worth exploring next.

The headline result: **with one command, we can register the creation of a vault, the EC2 instance comes up with the right AMI, the vault is created, the cert is issued, and the URL becomes live, in roughly 50 seconds**. This is real working infrastructure, not a design document. The brief captures what works, what does not yet work cleanly, and what the next set of workflows should be.

Three threads run through it:

1. **The DNS pinning problem** that surfaced when transitioning from the wildcard-cert holding page to the live instance
2. **The randomised ephemeral address pattern** as an alternative addressing scheme worth piloting
3. **The "we found an existing instance, want to join it?" workflow** that emerged from the work and feels right

Not the "click and instant" pattern (Lambda does that fine); the "click and you have a dedicated environment" pattern (where 50s is a fair trade for the isolation).

## The DNS Pinning Problem

The technical wrinkle the voice memo flagged: **DNS pinning persists after the DNS record changes**, which breaks the transition from the wildcard-cert holding page to the live instance.

### The Setup

The current flow:

1. Wildcard DNS entry `*.user-domain.example` points to a holding-page Lambda
2. The wildcard cert covers all subdomains under `user-domain.example`
3. When the user requests `slug-1.user-domain.example`, before the EC2 instance is registered, traffic hits the Lambda which serves the holding page
4. As provisioning completes, a specific A-record is added for `slug-1.user-domain.example` pointing at the new EC2 instance's IP
5. The UI on the holding page polls for the transition; when it detects the live instance, it redirects the user
6. **In theory**, future requests to `slug-1.user-domain.example` now resolve to the new IP and bypass the Lambda

### The Wrinkle

In practice, **the user's browser (or upstream DNS resolver) has already cached the wildcard-mapping result**. Subsequent requests to `slug-1.user-domain.example` continue resolving to the Lambda for some time after the A-record is added.

This is standard DNS caching behaviour. TTLs are honoured by clients and intermediaries. The Lambda was the answer; the client cached that answer; the cache outlives the change.

The voice memo's observation: "we hit that DNS pinning, because as we make requests to the server, then it holds it back." The repeated polling from the UI **actively reinforces the pin**: each request keeps the resolved address in cache, refreshing the TTL on the wrong answer.

### Options For Fixing It

Several possible approaches, with different trade-offs:

| Approach | How It Works | Trade-offs |
|----------|--------------|------------|
| **Short TTL on the wildcard record** | Set the wildcard's TTL to something tiny (10-30s) so caches expire quickly | Simplest fix; some recursive resolvers ignore very short TTLs; slight performance penalty on all wildcard lookups |
| **Different DNS name per phase** | Holding page lives at `provisioning-{slug}.host`; live instance at `{slug}.host`; UI explicitly navigates between them | Cleaner; no DNS-cache fight; requires UI cooperation |
| **Holding page detects readiness server-side** | Lambda checks the provisioning state on each request; serves a redirect (HTTP 302) when ready | DNS cache irrelevant; the Lambda becomes the switching layer; one extra hop but only briefly |
| **Use a path on the same domain, not a subdomain** | `host/{slug}` instead of `{slug}.host`; routing is application-layer not DNS | Fundamentally changes the addressing model; lots of downstream implications |
| **Service Worker on the holding page** | Holding page registers a Service Worker; SW intercepts subsequent requests and routes intelligently | Browser-only; doesn't help curl/agent traffic; clever but limited |
| **Long-poll bridge** | Holding page Lambda keeps a long-lived HTTP connection; when ready, sends a redirect via the open connection | Avoids the cache problem entirely; needs Lambda to support long-running connections |

**For v1, the holding-page-detects-readiness approach (option 3) is probably right**. The Lambda already exists; we extend it to check provisioning state on each request and return a 302 redirect once the instance is ready. The DNS cache continues pointing at the Lambda; the Lambda returns "the answer is now over there" until the cache eventually flips on its own.

This is also nice operationally: the Lambda becomes a single source of truth for "is this provisioning complete?" and can implement clean state transitions, retry handling, and observability.

Option 1 (short TTL) is worth doing anyway as defence in depth. Option 2 (different DNS names per phase) is a v2 refactor if the path matters and the Lambda approach turns out limited.

## The Randomised Ephemeral Address Pattern

The voice memo proposed an alternative addressing pattern: **randomised ephemeral addresses, like GUID-based references**, instead of predictable user-scoped slugs.

```
Current (predictable): user-a.sgraph.app/vault-name
Proposed (random):     ephemeral-7g3kp9-x.sgraph.app
```

The randomised version has several useful properties:

| Property | Why It Matters |
|----------|----------------|
| **Implies ephemerality** | A user sees `ephemeral-7g3kp9-x` and intuits this is a temporary thing, not their stable address |
| **Avoids namespace collisions** | No question of whether `john.sgraph.app` is taken; the random one is unique by construction |
| **Cleaner sharing semantics** | Sharing the URL with someone else is clearly "share access to this specific instance" rather than "share my account" |
| **Better security model for sensitive use** | Random URLs are unguessable; you cannot enumerate users by trying `user-1`, `user-2` |
| **Different DNS-cache behaviour** | Each random URL is fresh in DNS caches; the pinning problem mostly doesn't apply because nobody has resolved this exact name before |
| **Privacy-friendly** | Doesn't expose the user identity in the URL |

This is a good pattern for the **per-session-ephemeral-instance** use case. The user opens a vault, gets a randomly-named instance for that session, uses it, the instance eventually tears down, the address is gone. Next session: new random address, new instance.

For the **persistent personal-instance** use case (the user's own long-lived environment), the predictable slug still makes sense. The two patterns coexist: ephemeral random for sessions, predictable for persistent.

The voice memo suggested both: "let's create another UI, another workflow where we actually create these randomised instance names, which we then open up and give the user the ability to load up."

## The "Found Existing Instance, Want To Join?" Workflow

The voice memo named another pattern: **when a user navigates to their predictable slug, the system checks if an instance is already running and offers to join it, rather than always spinning up a new one**.

Concretely:

1. User visits `user-a.sgraph.app`
2. System checks: is there a running EC2 instance for user-a?
3. If yes: "Found your existing instance. [Join] [Create new]"
4. If no: "Create a new instance? [Create] [Cancel]"

This is the right UX for the persistent-personal-instance case. The user expects continuity if they were here recently; they expect new if they want a fresh start. The choice is theirs.

It also opens the door to **multi-instance-per-user**: nothing stops user-a from having multiple instances running simultaneously, each with a different ephemeral slug or use case. The persistent slug is the front door; individual instances live behind it with their own random or named identifiers.

A related question the voice memo raised: **who can create instances?** Possibilities:

- Anyone with the URL can create one (open; demo-friendly; potentially abused)
- Only authenticated users can create (standard)
- Only users with a specific key (project lead initially; teammates later; gradual access widening)
- A pre-auth balance is required (the metering substrate from earlier this week)

For v1, **the pre-auth balance approach is the right fit**. A new instance is a metered operation; the user (or their pre-auth pool) covers the cost. No instance is created without funding. This composes with everything else we have built around metering.

## Container Vs EC2 Provisioning

The voice memo flagged that this work composes with the container-host primitive: "very soon not just EC2 instances, but also containers with vaults running inside of it."

The substrate spectrum from yesterday means: a vault provisioning request can land on the right substrate per workload:

| Substrate | Provisioning Time | Best For |
|-----------|-------------------|----------|
| Fargate task | 10-30s | One-shot session vaults; bursty workloads |
| Container on existing host | 1-5s | Many small vaults on a shared host; lowest cost |
| Container on shared host with warm pool | <1s | Highest-throughput; pre-warmed containers ready |
| Dedicated EC2 instance | 30-60s | Long-running per-user environments; full isolation |
| Firecracker microVM (future) | <50ms snapshot restore | Eventually replaces dedicated EC2 for ephemeral isolated workloads |

The on-demand provisioning workflow we just got working is **dedicated EC2** (30-60s, full isolation). The container-on-existing-host path is what enables fast provisioning for shared workloads.

Different vaults pick different substrates based on their isolation needs and provisioning-time tolerance. The same UI flow (URL → check if instance exists → join or create) works regardless of substrate; the substrate is an implementation detail of "create."

## Putting It Together: The Recommended Flow

Based on everything that worked and the patterns flagged, the recommended v1 flow:

```
User visits {addressing}.sgraph.app
    ↓
Address router (Lambda + holding page logic):
  - Is there a running instance for this address? → Yes: serve redirect to live instance
  - Is provisioning in progress? → Yes: serve holding page with status
  - No instance, no provisioning? → Show "Create new instance" UI
    ↓
"Create new instance" UI:
  - Show estimated time (~50s for EC2 dedicated; faster for container)
  - Show cost (deducted from pre-auth balance)
  - Show choice of substrate if appropriate
  - [Create] button
    ↓
Provisioning starts (one of the substrate-specific paths)
    ↓
Holding page polls; refreshes status; shows progress
    ↓
When ready: 302 redirect to the now-live URL
    ↓
User is in their instance
```

The address router pattern (one Lambda handling all `*.sgraph.app` traffic and deciding what to do per request) is the cleanest implementation. It owns the state transitions; it handles DNS pinning gracefully; it can do interesting things like "join existing" or "create new."

The two addressing schemes (predictable slug vs random ephemeral) both work through the same router. The router's logic is "look up this address; act accordingly." The slug-vs-random difference is just a configuration of how addresses get assigned.

## What This Means For Cost

A dedicated EC2 instance per session at 50-second provisioning is not free. Approximate cost model:

| Workload | Cost |
|----------|------|
| Provisioning (50 seconds of compute + S3 access + DNS update) | ~$0.001 |
| Session running (say 30 minutes on a t4g.small) | ~$0.008 |
| Teardown (idle timeout + EC2 stop) | ~$0.0001 |
| **Per session** | **~$0.01** |

At a penny per session, even thousands of sessions per day stay under $10. This is comfortably within the pre-auth metering pattern from earlier this week.

For workloads where 50s provisioning is too slow or 1¢/session is too much, the container substrate (1-5s, fractions of a cent per session) is the right choice. The cost spectrum maps to the substrate spectrum.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not multi-region for v1**. Single-region provisioning; multi-region is a future expansion when customer demand justifies it.
- **Not real-time collaboration between instances.** Each instance is a separate vault; collaboration via vault sharing, not real-time sync.
- **Not a Kubernetes-equivalent control plane.** We use the existing primitives (Lambda + DynamoDB or vault state); we do not build a scheduler.
- **Not multi-user per instance for v1.** One user, one instance, although the address router could support multi-user later.
- **Not full reset-and-restore for v1.** Idle teardown is hard delete; recovery means provisioning a fresh instance and restoring from backup (which is why today's backup brief matters).

## Honest Risks

Two risks to flag:

**Risk 1: The DNS pinning solution does not fully solve the issue in practice.** Some networks and resolvers have weird caching behaviour. Mitigation: test with multiple browsers, networks, and tools; document the limitations; possibly use both option 1 (short TTL) and option 3 (Lambda redirect) together.

**Risk 2: The 50-second provisioning time becomes a real bottleneck for some use cases.** Mitigation: the container substrate's 1-5s provisioning addresses this for most workloads; the question becomes which use cases really need dedicated EC2 vs which can run on containers.
