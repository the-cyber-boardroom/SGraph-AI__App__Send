## What This Is

The operational follow-through on the vault testing framework: **a CI pipeline that automatically runs vault tests whenever the vault app changes, plus the ability to trigger ephemeral compute (Fargate, container hosts, etc.) from the CI pipeline itself**.

The pipeline is what turns the testing framework from a capability into a guarantee. Without CI, tests exist but are run when someone remembers. With CI, every change to the vault app is verified against all vaults before merging; every demo vault is checked daily; failures are visible immediately.

The voice memo flagged this concretely: "we need to create a new CI pipeline for the Vault app repo that is going to fundamentally test the repo... make sure that the new vault, as part of the dev pipeline, doesn't break anything."

## What The Pipeline Does

Three classes of CI jobs:

| Job Class | Trigger | What It Runs |
|-----------|---------|--------------|
| **Vault app smoke tests** | Every commit to the vault app repo | Unit tests on vault app modules; quick regression checks |
| **Per-vault test runs** | Every commit; nightly schedule | The vault's own test suite (unit, integration, QA) for each registered vault |
| **Browser-automation runs** | Every release candidate; nightly | Playwright-driven tests of each vault deployed in a real browser |

The first runs in seconds. The second runs in minutes. The third runs in tens of minutes for a full vault inventory. Each is triggered differently and reports differently.

## The Pipeline Stages

A typical vault-app commit goes through these stages:

```
1. Commit pushed to vault app repo
   ↓
2. CI runs vault app unit tests
   ↓
3. CI fetches the inventory of registered vaults
   ↓
4. For each vault: run that vault's unit + integration tests against the new vault app
   ↓
5. If all green: build artifact (vault app bundle)
   ↓
6. CI triggers a deployment of the artifact to staging
   ↓
7. Run browser-automation tests against staging vaults
   ↓
8. If all green: promotion path to production opens; manual approval gate
```

The key new step is stage 4: testing each registered vault against the new vault app. This is what guarantees that **a vault app change does not break any vault that depends on it**.

## The "Vault Inventory" Concept

The pipeline needs to know which vaults to test. Two options:

| Option | How It Works |
|--------|--------------|
| **Explicit registration** | Vaults that want to be tested register themselves in a list; pipeline iterates the list |
| **Discovery** | Pipeline scans for vaults with test suites in known locations; iterates whatever it finds |

The right answer is probably **both**, with explicit registration as the default. Customers who care about CI for their vaults register; we discover via convention; the registry combines both sources. Manager vaults (from earlier this week) are a natural place to hold the registry.

A registered vault has:

- A vault identifier
- A pointer to its test suite (probably in the vault itself)
- A configuration (which test layers to run, how often, any fixtures to set up)
- Notification preferences (where to send results)

The registry itself is a manager vault (specifically, "Vault Test Registry" as one of the manager vault instances from yesterday). It is auditable and version-controlled like any other vault.

## Triggering Ephemeral Compute From CI

The voice memo named a specific capability that takes this further: **the CI pipeline should be able to trigger ephemeral compute (Fargate tasks, container hosts) for itself**. This means the CI doesn't just run tests in its own environment; it can spin up dedicated environments for specific tests, run those tests, collect results, and tear them down.

Concrete use cases:

| Use Case | Why Ephemeral Compute |
|----------|----------------------|
| **Browser-automation tests with isolated state** | Each test run gets a fresh container host with a fresh browser; no cross-test pollution |
| **Multi-region tests** | Spin up containers in different regions to verify regional behaviour |
| **Load tests** | Spin up many parallel runners; measure how the vault behaves under load |
| **Compatibility tests** | Different runtimes (Node 20, 22, 24; Chrome, Firefox, Safari) get their own ephemeral environments |
| **Long-running QA tests** | A test that takes 20 minutes runs on a dedicated Fargate task; doesn't tie up CI runners |

The CLI primitives we've been building (Fargate, container hosts, the placement layer) are exactly the substrate this needs. The CI pipeline calls `sg-compute fargate run-task` or `sg-compute container run` with the test workload as the container image; gets back results; tears down. This is the substrate spectrum in action: the CI picks the right substrate per test.

## The CI Substrate Choice

Three options for where the CI runner itself lives:

| Substrate | Trade-offs |
|-----------|-----------|
| **GitHub Actions / similar hosted CI** | Familiar; managed; per-minute cost; limited customisation |
| **Self-hosted GitHub Actions runner on our infrastructure** | More control; per-instance cost; we operate it |
| **CI on our own SG/Compute substrate** | Fully self-hosted; uses our container hosts primitive; consistent with the rest of the stack |

The pragmatic answer is probably **GitHub Actions for the orchestration layer, plus our SG/Compute substrate for the actual test execution**. The CI workflow file lives in the repo; the runner triggers `sg-compute` commands that spin up the test environments. This gives us the best of both: familiar orchestration plus our own substrate for the actual workload.

As the platform matures, we can replace GitHub Actions with our own orchestration if it becomes worthwhile. But day one, the hybrid is the right move.

## What Triggers The Pipeline

Multiple trigger types are needed:

| Trigger | Purpose |
|---------|---------|
| **Commit to vault app repo** | Verify the change before it merges |
| **Commit to a registered vault** | Verify the vault still works with the current vault app |
| **Nightly schedule** | Catch external regressions (third-party services broken, dependencies updated, etc.) |
| **Manual trigger** | A developer wants to verify something now |
| **Webhook from external services** | E.g., AgentCore evaluation completion triggers a re-run |
| **Pre-deploy gate** | A deployment must pass tests before proceeding |

Each trigger type configures the pipeline differently. A commit-trigger might only run the affected vault's tests; the nightly might run all vaults; the pre-deploy gate runs everything including browser-automation.

## Reporting And Notifications

What happens when something fails matters as much as the test mechanics.

Tier 1: **Pass/fail signals** in CI UI. The standard green check / red X.

Tier 2: **Detailed failure reports** showing which test, which assertion, what was expected, what was returned. These go to the developer or vault author who needs to fix it.

Tier 3: **Investigation entry points**. A failure links to:
- The vault history commit at which the test started failing
- The vault app commit that caused the regression
- The full logs from the failing test
- A reproduction command the developer can run locally

Tier 4: **Aggregate dashboards**. Trends over time: which vaults break most often? Which kinds of changes cause the most regressions? Where is the test surface weakest?

All four tiers commit to the observability session (from yesterday). The vault commit history captures the run. The pre-auth metering captures the cost.

## Cost Considerations

CI is operationally cheap but not free. Concrete cost model:

| Workload | Approximate Cost |
|----------|------------------|
| Unit tests (run in CI runner) | ~$0.01 per run |
| Integration tests (Node.js process; 30 sec) | ~$0.05 per run |
| QA tests (a vault setup + state changes; 1-2 min) | ~$0.10-$0.20 per run |
| Browser-automation tests (Playwright; 2-5 min) | ~$0.20-$0.50 per run |
| Full per-vault test run | ~$0.50-$1.00 per vault per full run |

For 20 registered vaults with full test runs nightly: ~$10-20/night, ~$300-600/month. Modest, manageable, with clear value.

These costs flow through the pre-auth metering substrate. CI runs for our own vaults are billed to our operations account; CI runs for customer vaults are billed to the customer's pre-auth balance.

## The Vault App Repo Specifics

Specific to the vault app's CI:

1. **The vault app repo is where the work happens**. Every commit triggers a pipeline.
2. **A change to the vault app must not break existing vaults**. The pipeline tests this.
3. **A change to a vault must not break the vault's behaviour**. The pipeline tests this too.
4. **Test outputs are artefacts of the build**, not separate flows.
5. **Failed builds cannot be deployed to production** without explicit override.

This means the vault app repo's CI is the canonical gate for vault app changes. Customer vaults can have their own CI configurations on top of this gate.

## What This Asks For

1. **Set up the vault app's CI pipeline** using GitHub Actions (or equivalent) for orchestration.
2. **Implement vault inventory / registration** as a manager vault.
3. **Build the "trigger ephemeral compute from CI" capability** so test workloads can run on Fargate or container hosts.
4. **Define the reporting tiers** and route to appropriate channels.
5. **Cost-meter the pipeline** through the pre-auth substrate.
6. **Integrate with the unified observability session** so CI results are queryable alongside other sources.
7. **Run the pipeline for the first time** against a real change to verify it works.

Estimated effort: 1-2 weeks for the initial pipeline, plus ongoing refinement.

## What This Does Not Try To Be

- **Not a general-purpose CI/CD platform**. We use existing tools (GitHub Actions or similar) for orchestration.
- **Not a replacement for tests themselves**. Without good tests in the vaults, the pipeline cannot help.
- **Not a deployment automation tool** beyond verification. Actual deployment goes through other mechanisms.
- **Not a manual override-prevention mechanism**. Sometimes a vault genuinely needs to deploy with known test failures (e.g., known external regressions). The pipeline supports overrides with audit.
