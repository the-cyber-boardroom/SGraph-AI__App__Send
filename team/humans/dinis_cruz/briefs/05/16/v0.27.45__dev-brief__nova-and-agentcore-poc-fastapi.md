## What This Is

A small, self-contained proof-of-concept: **a FastAPI service with a mini UI that exposes Nova model invocations and AgentCore agent invocations through a simple interface**. The goal is to start introducing LLM-based decision-making into our workflows, validate the cost economics of Nova models, and figure out concretely what AgentCore agents and tools can do for us.

The forcing function is concrete: we just added Bedrock model invocation to SG/Compute (yesterday's work made `sg-compute aws bedrock` real). The natural next step is to start using it for the decision-making problems that pure code cannot solve. Yesterday's vault CI pipeline brief named the canonical example: "is the vault okay?": a question that has both structural and qualitative components. The structural part is unit tests, integration tests, browser automation; the qualitative part is "does this vault actually look right, read right, work in a way that a human reviewer would approve?" That qualitative part is where LLM decision-making earns its keep.

This brief covers building the substrate to experiment with that decision-making, starting from cost economics that are genuinely attractive.

## Why Nova, Why Now

Three factors make this the right moment:

1. **Bedrock CLI native support is in place.** We can call any Bedrock-hosted model from the CLI today. Nova models are first-party AWS, so invocation is clean.
2. **Nova pricing is aggressively low for the kinds of tasks we have.** $0.035 per million input tokens for Nova Micro, $0.06 per million input for Nova Lite. For comparison: routine "is this output reasonable?" judgements at this price are roughly free at our scale.
3. **AgentCore composes the pieces.** Tools, browsers, code interpreters, memory, observability, all addressable from a single agent. We have been mapping this out conceptually for two weeks; time to put it through real work.

The Nova family in particular is worth investigating because it is **Bedrock-exclusive**, priced aggressively to drive adoption, and includes a specialised browser-automation model (Nova Act) that is directly relevant to the vault QA use case. We have OpenRouter and Anthropic direct as our existing LLM substrates; Nova adds an AWS-native option with its own price-performance characteristics worth measuring against our workloads.

## What Gets Built

A small FastAPI service with two endpoint groups and a mini UI that drives them:

| Endpoint Group | Purpose |
|----------------|---------|
| `/nova/invoke` | Direct Nova model invocation (Micro, Lite, Pro, Premier; text in, text out; configurable max-tokens, temperature) |
| `/agentcore/invoke` | AgentCore agent invocation with configurable tools (Browser, Code Interpreter, custom tools), session management, memory |

The UI is a single-page interface (same pattern as other small UIs we have built):

- Model selector dropdown (Nova Micro / Lite / Pro / Premier; AgentCore agent options)
- Prompt textarea
- Optional tool/parameter configuration panel
- "Invoke" button
- Result panel showing output, tokens used, cost, latency, raw API response (collapsed by default)
- Session history (last N invocations with their results)

This is a developer tool, not a polished product. The goal is **fast iteration on prompts and configurations** so we can understand cost and capability before committing to specific use cases.

## The Architecture

The service is intentionally tiny:

```
Browser → Mini UI (HTML/JS)
            ↓
        FastAPI service
            ↓
        sg-compute aws bedrock (for direct Nova calls)
        sg-compute aws agentcore (for AgentCore agents)
            ↓
        AWS Bedrock / AgentCore
```

Authentication uses the same API key pattern we already have (per the credential manager work). The FastAPI service holds the key; the UI never sees it. Every invocation is logged: prompt, model, response, cost, timing.

The service can run anywhere our compute substrate runs: locally for development, on a container host for shared team access, on Fargate for production use. Following the substrate-spectrum framing, this is genuinely substrate-agnostic.

## What We Will Use It For

Three concrete use cases drive the build, each one validating a different aspect:

### Use Case 1: CI Pipeline Go/No-Go Decisions

The voice memo's first example: "I want to start to add some logic to the CI pipeline to make decisions for go/no go."

Today's CI brief described automated test runs. Each test run produces structured output (passed, failed, errors, durations). The structural answer is straightforward: all passed = go; any failed = no-go.

But there are real cases where the structural answer is incomplete:

- A browser automation test passed, but a screenshot looks subtly wrong. Is it a regression?
- A vault test passed, but the LLM-generated content in the test output reads oddly. Is the vault actually working?
- A configuration change passed validation tests but introduces unusual values. Should a human review before deploy?
- A test failure happened, but the failure mode is a known flake. Should this block the merge?

For each, a Nova-powered "qualitative reviewer" can produce a recommendation: ship, hold for review, definitely block. The CI uses the recommendation as additional input; the final decision is still automated but better-informed.

Nova Lite at $0.06 per million input tokens means a 5000-token CI review prompt costs about $0.0003 per run. For 100 CI runs per day, that is $0.03 per day, operationally free.

### Use Case 2: Vault Analysis And QA

The voice memo named this: "do some analysis on vault, some analysis on what's going on."

Specific kinds of vault analysis a Nova-powered agent can perform:

| Analysis | Question Answered |
|----------|-------------------|
| Vault content review | Is the vault internally consistent? Do the links work? Is the structure logical? |
| CV vault quality check | Does the CV read professionally? Are there obvious issues a human reviewer would catch? |
| Medical vault completeness | Are required fields populated? Does the patient summary match the underlying data? |
| Configuration vault sanity | Do the configured values fall within reasonable ranges? Are there obvious inconsistencies? |
| Newsroom article readability | Does the article meet the publication's standards? Quality, style, structure? |
| Demo vault polish | Is this vault demo-ready or does it need work before going to a customer? |

For each kind, a Nova call with the vault's content as input and a structured prompt produces a qualitative review. Output is JSON: a score, a list of issues, recommendations. The vault test framework (today's other brief) can include these as a new test layer: **LLM-assisted qualitative tests** that complement unit/integration/QA/browser-automation layers.

### Use Case 3: Browser Automation Via Nova Act

Nova Act is AWS's browser-automation product line. Distinct from AgentCore Browser; Nova Act is a separate SDK and service specifically optimised for reliable web UI automation, with its own training and tooling. It hits >90% accuracy on internal benchmarks for actions that trip up other models (date pickers, dropdowns, popups). PGA TOUR uses it for cross-geography testing; Hertz uses it for QA acceleration.

For our vault demos and customer-facing workflows, Nova Act becomes interesting for:

- Automated cross-browser testing of vault demos (does the medical demo work on mobile Safari? on Firefox? in low-bandwidth conditions?)
- Visual regression detection (does the rendered vault still look the same after a change?)
- Customer journey simulation (open this demo link as a brand-new visitor; do you understand the value proposition within 30 seconds?)
- Multi-region availability testing (does the vault work from a Tokyo IP? from a Frankfurt IP?)

The proof-of-concept includes a Nova Act invocation endpoint so we can experiment with these use cases concretely.

## Cost Economics

The point of the brief is to get real numbers, but plausible economics for the planned experiments:

| Workload | Approximate Cost |
|----------|------------------|
| Nova Micro CI review (5K input + 500 output) | ~$0.0003 per review |
| Nova Lite vault QA analysis (20K input + 2K output) | ~$0.0017 per analysis |
| Nova Pro detailed vault audit (50K input + 5K output) | ~$0.056 per audit |
| Nova Act browser session (per-task pricing TBD; assume $0.10-$0.50 per session) | ~$0.10-0.50 per test |
| AgentCore Runtime for a 5-minute agent session | ~$0.01-0.02 (mostly model inference) |

For comparison: yesterday's pre-auth payment model could handle these at the customer-action level (each LLM-validated vault check is a metered transaction). At Nova Micro pricing, **a vault customer could afford continuous LLM-based monitoring for pennies per day**.

These numbers need to be measured against real workloads. The proof-of-concept's first job is to **produce real cost numbers for our actual use cases**, not to rely on per-token rates alone (because token counts depend on prompt structure, which we will iterate).

## What This Lets Us Learn

Building the proof-of-concept answers concrete questions:

1. **What is the real cost of LLM-validated QA at our scale?** Multiply prompt tokens × invocation count × Nova rate. Get actual numbers.
2. **What quality level does Nova Lite (vs Nova Pro vs Claude Haiku) deliver for vault QA?** Run the same prompts; compare results; pick the floor of acceptable quality.
3. **Where does AgentCore Browser succeed vs fail for our vault demo testing?** Real workflows; real failure modes.
4. **What does Nova Act add over AgentCore Browser?** Both can drive browsers; the proof-of-concept lets us compare in our actual use cases.
5. **What does the prompt structure look like for "is this vault okay?"** Iterate prompts; learn what works; build a library of validated prompt templates.
6. **What is the right cadence for LLM checks in CI?** Every commit? Every release? Nightly? Cost data informs this.
7. **Does the FastAPI/mini-UI pattern scale to other LLM experiments?** This is our seventh small interactive tool; the pattern keeps paying off.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a production service.** This is a developer-facing experimentation tool. Hardening for customer use comes later if results justify it.
- **Not a single-model-only tool.** Nova is the focus but the architecture supports other models. The point is the workflow, not the model.
- **Not a replacement for unit/integration/browser tests.** LLM-based review supplements; it does not replace.
- **Not a public-facing service in v1.** Internal access only; pre-auth payments integration comes later if we expose it externally.
- **Not a fine-tuning playground.** We use base Nova models with prompts; fine-tuning is a separate consideration.
