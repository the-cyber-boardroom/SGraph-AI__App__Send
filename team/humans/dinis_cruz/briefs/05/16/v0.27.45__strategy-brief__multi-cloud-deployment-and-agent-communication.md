## What This Is

The next experiment for the platform: **run our vaults on multiple cloud providers**, not just AWS. The memo names three concrete options: GCP (where we have credits), Akamai Cloud (formerly Linode, where the project lead just opened an account), and continuing on AWS. The Docker Hub container we just published is the wedge: if we have a public container, the question is where it can run, and the answer should be "anywhere a Linux container runs."

But the memo also names two adjacent decisions that need to travel with the multi-cloud work. **First**, this should not bloat SG/Compute; it deserves a separate deployment tool that leverages SG/Compute primitives rather than absorbing them. **Second**, the act of splitting tools cleanly forces us to confront the agent communication problem: how do separate agent codebases hand off, communicate, and reuse each other's capabilities without copying code or coupling tightly. The memo says this is a good place to start experimenting with that pattern.

Three themes; one brief, because the splitting decision IS the framing of the agent communication problem, and the multi-cloud work IS the forcing function that requires the split.

## Why Now

Three converging factors:

1. **We have a public Docker container.** The barrier to running our code on another cloud is just "find compute that takes a container," which every cloud has.
2. **We have non-AWS credits sitting unused.** GCP credits are perishable; using them is free experimentation. Akamai Cloud just got opened with the intention of trying it.
3. **The vault format is portable.** S3-compatible storage is widely available; the vault itself just needs an object store, encryption keys, and HTTP endpoints. Most clouds provide this. Specifically: Akamai Object Storage is S3-compatible; GCP Cloud Storage has an S3 interop mode; even Cloudflare R2 and Backblaze B2 work.

The combination means **we can run a vault on three clouds in a week of focused work**, with each one validating a different aspect (object storage compatibility, container runtime, networking, identity).

This is also strategically timed. The serverless brief from earlier today named the substrate spectrum as our architectural backbone. Multi-cloud is the natural extension: not just multiple substrates within AWS, but multiple clouds running the same workload.

## What Each Provider Brings

| Provider | Strengths | Cost At Our Scale | Notes |
|----------|-----------|-------------------|-------|
| **AWS** | Mature; we know it well; AgentCore + Bedrock + Nitro Enclaves only here | Per-piece varies | Home base; everything else is comparison |
| **GCP** | Cloud Run for serverless containers; good free credits; reasonable AWS parity | Cloud Run pay-per-invocation similar to Lambda but with container support | Worth testing as a container-host alternative |
| **Akamai Cloud (Linode)** | Cheap VPS ($5/month entry, $36/month Dedicated 4GB); included transfer; S3-compatible object storage; LKE for Kubernetes; global presence via Akamai's network | Far cheaper than AWS at low scale | Compelling for ephemeral compute and for users who want non-hyperscaler infrastructure |
| **Cloudflare Workers (future)** | Edge compute; Email Service integration; Workers binding to R2 object storage | Generous free tier; predictable pricing | Different model (V8 isolates rather than containers); separate engineering work; v2+ |
| **DigitalOcean / Hetzner / Vultr (future)** | Cheap commodity VPS | Cheapest tier; good for specific deployments | Worth surveying but not v1 |

For the immediate experiment, **GCP and Akamai Cloud are the two we should run our vault on this week**. Both offer container-friendly compute at trivial cost. Both have S3-compatible object storage we can use for vault data. Both give us non-AWS validation of the architecture.

## The Concrete Experiment

The minimum viable multi-cloud experiment:

1. **Pick a vault that runs end-to-end on AWS today**, ideally a demo vault from yesterday's accountant-demo brief or similar.
2. **Deploy the same Docker container to GCP Cloud Run** with appropriate environment variables. Vault data lives in GCP Cloud Storage (S3-compatible mode) or in Akamai Object Storage.
3. **Deploy the same Docker container to Akamai Cloud** (probably a Dedicated CPU 4GB Linode at ~$36/month, or a Shared CPU instance for lower cost). Vault data in Akamai Object Storage.
4. **Validate**: does the same vault load, render, and accept reads/writes from each deployment?
5. **Measure**: cost, cold-start, performance, integration friction.
6. **Document**: what works, what does not, what each cloud needs differently.

This is genuinely a week of work, possibly less. The goal is not a polished multi-cloud product; it is **structural validation that our architecture works on cloud-neutral terms**.

## The Critical Architectural Decision: Separate Deployment Tool

The memo names this directly: **we should not absorb multi-cloud deployment into SG/Compute. It deserves a separate tool**.

The reasoning is operational hygiene. SG/Compute is already substantial. It handles AWS CLI primitives (EC2, Lambda, Route 53, Fargate, S3, IAM, Bedrock), vault hosting orchestration, agent execution, observability, credential management, the pre-auth payment substrate, the container hosts primitive. Adding GCP-specific commands, Akamai-specific commands, Cloudflare-specific commands would balloon the codebase to the point where the agent's mental model of "what is SG/Compute?" stops being clear.

The cleaner pattern is **SG/Deploy** (or whatever name we settle on) as a separate codebase that:

- Reuses SG/Compute's primitives where they help (vault read/write, credential resolution, observability connection)
- Adds its own primitives for non-AWS clouds (`sg-deploy gcp cloud-run`, `sg-deploy akamai container`, etc.)
- Has its own agent CLI surface
- Has its own scope and lifecycle
- Hands off to SG/Compute or other agents for the parts it does not own

This is the **CLI-first agent architecture** pattern (from earlier this month) applied to a new use case: SG/Deploy is a new agent with its own command tree, not a new subsection of an existing one.

## The Agent Communication Problem

This is where the memo gets architecturally interesting. **Splitting tools cleanly forces us to confront a problem we have been deferring**: how do separate agents communicate, hand off, and reuse capability without copying code or coupling tightly?

The naive answers all have problems:

| Naive Approach | Problem |
|----------------|---------|
| Import each other's code as libraries | Coupling; every change in SG/Compute breaks SG/Deploy |
| Call each other's CLIs as subprocesses | Lossy; structured data goes through string serialisation; observability splits |
| Share a database | Shared mutable state; coordination problems; not vault-native |
| RPC or REST APIs between them | Heavy; requires keeping protocols in sync; service-meshy |

The platform's existing primitives suggest a better answer. We have already been moving toward **vault-as-communication-medium** in several places (manager vaults holding agent state; vault commits as the audit log; the pre-auth substrate using vault-stored metering). Extending this to agent-to-agent communication is natural.

The proposed pattern: **agents communicate through shared vaults, not direct calls**.

### Agent Communication Through Vaults

The pattern works like this:

1. **Each agent has its own scope.** SG/Compute owns AWS-substrate operations. SG/Deploy owns multi-cloud deployment. Each is a self-contained agent with its own CLI command tree.
2. **Shared work happens in a shared vault.** When SG/Deploy needs SG/Compute to do something (e.g., "resolve credentials for cloud X", "fetch vault content to deploy"), it writes a request to a shared vault.
3. **The other agent processes the request when it can.** SG/Compute reads its request queue from the shared vault, processes each request, writes results back to the same vault.
4. **The vault is the audit log.** Every request, every result, every error is committed to the vault. The full handover history is reproducible.
5. **Vault keys gate access.** The shared vault has explicit per-agent permissions; an agent that should not be able to issue a particular request type does not have write access to that part of the vault.

This is a structural pattern, not a new technology. It uses the vault we already have. It composes with the credential manager (Simple Tokens grant scoped vault access). It composes with the observability session (vault commits are queryable). It composes with the pre-auth metering (each cross-agent operation is a metered event).

### Why This Works

The vault-as-communication-medium pattern has properties that the alternatives lack:

- **Decoupling**: SG/Compute and SG/Deploy don't import each other; they don't even need to be running at the same time. SG/Deploy can write a request; SG/Compute processes it when it wakes up.
- **Audit-trail-for-free**: every interaction is a vault commit. No special logging required.
- **Eventual consistency is acceptable**: most agent-to-agent operations don't need sub-second response; they need correctness and traceability.
- **Idempotency naturally falls out**: a request written to the vault has a stable identifier; processing it twice produces the same result.
- **Multi-language**: agents in Python, TypeScript, Rust, anything can read and write vault content.
- **Existing primitive reuse**: no new infrastructure; this is what vaults already do.

### What Patterns This Replaces

The agent communication pattern replaces or supersedes several things we have been informally doing:

| Today's Pattern | Vault-Based Replacement |
|----------------|-------------------------|
| Agent A imports agent B's code | Agent A writes a request to a vault that agent B watches |
| Agent A calls agent B's CLI as subprocess | Same |
| Agent A reads agent B's logs to know what happened | Agent A reads agent B's vault commits |
| Agent A maintains a copy of agent B's state | Agent A reads agent B's state from the vault |
| Agent A and B share a database | Agent A and B share a vault |

This is also explicitly the pattern we want for **inter-organisation agent communication** (the USDC scenario-3 work). External agents talking to ours, ours talking to external; all of it can flow through vaults with appropriate public-key access controls (today's vault discovery brief).

## What Should Live In Which Tool

For the multi-cloud experiment specifically, here is the proposed split:

### SG/Compute Keeps

- AWS-specific CLI primitives (EC2, Lambda, Fargate, S3, IAM, Route 53, Bedrock, AgentCore, Nitro Enclaves)
- Vault read/write operations (general)
- Container host orchestration on AWS
- Pre-auth payment substrate
- Credential manager (cross-tool; cross-cloud)
- Unified observability session

### SG/Deploy (New) Owns

- GCP-specific commands (`sg-deploy gcp cloud-run deploy`, etc.)
- Akamai-specific commands
- Cloudflare Workers commands (when added)
- Multi-cloud orchestration (deploy this vault to N clouds with these constraints)
- Multi-cloud cost tracking and comparison
- Cross-cloud failover logic (if needed eventually)

### Shared Via Vault

- Credential resolution (SG/Deploy asks the credential manager vault; gets scoped credentials back)
- Deployment status (SG/Deploy writes deployment state to a manager vault; SG/Compute reads it for observability)
- Cost data (each tool writes its cost data to the unified observability vault)
- Vault image artifacts (the Docker container is itself in a vault; SG/Deploy pulls it)

The boundary is clean. SG/Compute does not need to know about GCP; SG/Deploy does not need to know about Bedrock. They interoperate through vaults.

## What's New Beyond The Experiment

The multi-cloud experiment is the wedge. The broader implications:

### Customer Pitch

"We run on AWS, GCP, Akamai, and others. Pick your cloud. Pick your isolation. Your vault is portable; your data is yours." This is a meaningful differentiation. Customers in regulated industries, customers with specific cloud preferences, customers who want to avoid hyperscaler lock-in: all of these get a credible answer.

### Cost Optimisation

Each cloud has cost sweet spots. Akamai Cloud at $5-36/month for VPS undercuts AWS at the low end. GCP Cloud Run handles spiky workloads well. Cloudflare Workers is cheap at the edge. **A workload that knows it can run anywhere can run wherever it is cheapest.** This is not v1; this is what becomes possible.

### Resilience

A workload deployed across two clouds survives one cloud's outage. This is operationally meaningful and very hard to do without a portable substrate.

### Offline And Air-Gapped

The same portability that enables multi-cloud also enables on-premise. The Docker container that runs on Akamai also runs on a customer's own server. Today's vault discovery brief flagged offline bundles as a meaningful customer scenario; multi-cloud validates the same architecture from the opposite direction.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a multi-cloud abstraction layer for arbitrary applications.** We are running our vault; we are not selling a portable-app-deployment platform.
- **Not full feature parity across clouds.** AWS will always be ahead because AgentCore, Bedrock, and Nitro Enclaves are AWS-only. Multi-cloud is for the core vault and compute; advanced features stay AWS-only.
- **Not Kubernetes everywhere.** We are not deploying LKE everywhere. The container host primitive plus per-cloud orchestration is enough.
- **Not multi-cloud failover for v1.** Deploy to multiple clouds; do not yet automatically fail traffic between them.
- **Not solving the agent communication problem comprehensively.** We are using vaults as the communication medium for the multi-cloud case; we will see how it generalises before claiming we have solved it.

## Honest Risks

Three risks worth flagging:

**Risk 1: Multi-cloud quickly becomes its own time sink.** Each cloud has its own quirks, its own auth model, its own DNS story, its own observability tooling. Doing N clouds well is N times the work of doing one cloud well. Mitigation: start with the two cheapest (Akamai, GCP); resist scope creep; defer Cloudflare Workers and others until the first two work.

**Risk 2: The agent communication pattern is harder than the brief implies.** Vault-based communication works well for asynchronous, eventually-consistent workflows. Synchronous request-response over a vault is awkward. Mitigation: pick async use cases first; design the pattern to gracefully fall back to direct CLI invocation for synchronous needs.

**Risk 3: SG/Deploy becomes a second-class citizen that lags SG/Compute.** Splitting introduces ongoing coordination cost. Mitigation: keep the boundary clean; don't share code; communicate via vault only; resist the temptation to "just import that one thing."
