# Vault Demo Capabilities: Read-Only Opening, Cross-Vault Links, Session-Scoped Changes

**version** v0.27.45
**date** 16 May 2026
**from** Human (project lead)
**to** Developer (lead), @Dev, Design
**type** Dev brief

---

## What This Is

A consolidation of three vault-app capabilities we need to ship together to unblock the demo push: **read-only vault opening, cross-vault navigation, and session-scoped client-side changes** that exist only in the browser tab and never commit back to the vault. Some of this is partly in place; this brief consolidates what we have, what is missing, and what to ship.

The forcing function is concrete: **we are getting close to the stage where we can really start to demo the vault**, which means tonnes of use cases and tonnes of examples need to work cleanly when an unfamiliar visitor opens a link. Medical demos, CV demos, industry vectors, partner POCs: all of them depend on a polished "open this link and see the vault working" experience.

## The Demo Reality

The demo experience is: a visitor receives a link, opens it, sees the vault, can navigate it, can play with it, eventually understands what we are showing them. Several capabilities have to work together for this to land:

| Capability | Status | What's Missing |
|------------|--------|----------------|
| Read-only vault opening from a link | Partly working | Polish; consistent UX; handles the no-vault-key case cleanly |
| Cross-vault navigation (links from one vault to another) | Works as normal web pages | Should it work? Probably yes. Need policy on link behaviour |
| Session-scoped client-side changes | Not working | The big new feature; lets the visitor experiment without commits |
| Smooth degradation when JS is disabled | Unknown | Probably not relevant for demos but worth checking |
| Mobile-friendly read-only viewing | Probably broken in places | Demo-blocker on mobile |

The first three are the core. The brief focuses on those.

## Capability 1: Read-Only Vault Opening

The pattern: a visitor opens a link like `https://send.sgraph.ai/vault/{share-token}` and the vault opens in read-only mode. The visitor does not need an account, does not need credentials, does not need to download anything. The vault renders, the visitor can navigate, the visitor can read.

This is partly working today via the share-token mechanism. What needs to be cleaned up:

- **Consistent visual indication** that the visitor is in read-only mode. Probably a small badge or banner.
- **Clear UX for actions the visitor cannot take** (no "edit" buttons, no commit options, or those buttons exist but explain what would happen with an account).
- **Polished load experience**: fast, no flash of unstyled content, no error messages flashing through.
- **Mobile responsive**: vaults need to look good on phone screens for the demo to land via link-sharing.
- **Clear "make this your own" call-to-action** somewhere: how does a visitor become a customer if they like what they see?

This is mostly polish work on an existing capability. Maybe 3-5 days of focused effort.

## Capability 2: Cross-Vault Navigation

A visitor reading vault A clicks a link that points to vault B. What should happen?

Normal web semantics suggest the link should open vault B in read-only mode (assuming it has a valid share-token or is public). This is largely how the web works; we just need to make sure it works **for our specific vault routing** without breaking the share-token model.

Concrete cases to handle:

| Source Vault | Destination Link | Expected Behaviour |
|--------------|------------------|---------------------|
| Read-only vault A | Public read-only vault B | Open vault B in read-only mode in a new tab (or replace? worth thinking about) |
| Read-only vault A | Private vault B requiring share token | Use the embedded share-token in the link if present; otherwise show an "access required" message |
| Read-only vault A | Same-vault internal anchor | Standard anchor navigation; no special handling |
| Read-only vault A | External web URL | Standard browser link; opens normally |

The decision per case is mostly straightforward. The main design choice is **default tab behaviour**: replace the current vault, or open in a new tab? Probably open in a new tab for cross-vault links so the visitor does not lose their place; same tab for in-vault anchors. Authors can override via `target` attributes.

This connects naturally to the manager vault pattern from earlier this week: a manager vault holds links to many managed vaults; clicking one navigates to it; the manager vault stays open in the original tab.

## Capability 3: Session-Scoped Client-Side Changes

This is the new capability and the most interesting one. The proposition: **a visitor opens a read-only vault, makes changes during their session, sees those changes reflected in the UI, but the changes do not commit back to the vault and do not survive a page refresh**.

The use case is demo-driven. The voice memo flagged the workflow concretely: "we're going to have a number of workflows where you open up the data from one page to another, and then another, but the data needs to come from the vault. The best case studies is to say, hey, enter from here, and now go to this page, and you see the answers."

This is multi-step demo UX. The visitor:

1. Opens the vault on page A
2. Sees a form or interactive element
3. Enters data, makes choices, tweaks parameters
4. Navigates to page B (still within the vault)
5. Sees results derived from what they entered on page A
6. The whole experience feels live and personal to them
7. Refresh the page, and everything resets to the original demo state

This is **deeply different from "edit a vault."** Nothing commits. The changes exist only in browser memory for the session. The vault's canonical state is unchanged. The next visitor sees the original vault.

### How To Implement It

The architectural pattern: **client-side state shim over the vault read API**.

The vault's normal read flow (simplified):

```
Vault UI → JS API call: "get value at path X" → reads from vault storage → returns value
```

The session-scoped change flow:

```
Vault UI → JS API call: "set value at path X to Y" → writes to in-memory session store
Vault UI → JS API call: "get value at path X" → checks session store first;
                                                  falls back to vault storage
```

The session store is just an in-memory map keyed by vault path. It overrides the canonical vault state for read operations within the session. A page refresh discards it (the map is not persisted). Multiple tabs each have their own session store (different memory spaces).

This is technically straightforward. The trick is making sure **all the right operations route through this shim**. Every read needs to check session first. Every write needs to land in session, not the vault. The vault's actual write APIs need to be inert in read-only mode.

### What Needs To Change

| Component | Change |
|-----------|--------|
| **JS API read paths** | Check session store before vault storage |
| **JS API write paths** | In read-only mode, write to session store only; explicitly do not call vault commit |
| **Vault state cache** | Invalidation logic needs to handle session-overridden paths |
| **Refresh / navigation** | Session store survives in-vault navigation (same tab, different page within the vault); discarded on page reload or tab close |
| **Reset capability** | Maybe expose a "reset to original" button so visitors can clear their session changes without reloading |
| **Indication of session state** | Subtle UI cue when session changes exist (e.g., a small "changes not saved" indicator) |

Estimated effort: 1 week of focused work for the core shim, plus polish.

## How These Three Compose

The three capabilities form a coherent demo experience:

1. **Visitor opens a link** → read-only opening works cleanly (Capability 1)
2. **Visitor clicks around within the vault** → cross-vault and intra-vault links work (Capability 2)
3. **Visitor enters data, sees results across pages** → session-scoped changes carry state across the vault pages without commits (Capability 3)
4. **Visitor closes tab or reloads** → everything resets; next visitor sees the original vault

This is the demo experience we want. Each capability supports the others. Shipping any one without the others leaves the experience incomplete.

## Specific Demo Use Cases This Enables

Concrete demos that need all three working:

| Demo | Use Of Each Capability |
|------|------------------------|
| **CV / portfolio walkthrough** | Read-only opening; cross-vault links between portfolio sections; session-scoped "what would you like to highlight?" interactions |
| **Medical case study** | Read-only opening of a patient-history vault; session-scoped "what if you changed this parameter?" simulations |
| **Investor pitch vault** | Read-only opening with cross-vault links to detailed sections; session-scoped "tell me about your sector" customization |
| **Newsroom article with interactive elements** | Read-only article; session-scoped "what does this look like in your region?" personalization |
| **Daily-band song catalogue** | Read-only browse; session-scoped "play these in your preferred order" |
| **Infographic tool output gallery** | Read-only browse; session-scoped "rate these / pick a favourite" without committing |
| **Configuration vault for partner POCs** | Read-only view of a system configuration; session-scoped "what if you tuned these parameters?" experimentation |

Each one of these benefits from the trio of capabilities. None of them work cleanly with just one.

## The Connection To Testing And QA

These capabilities also unlock testing workflows. A test can:

- Open a vault in read-only mode (production-equivalent)
- Make session-scoped changes (test inputs)
- Navigate the vault and check expected behaviour
- Reset between test runs (session state is discarded)
- Never affect canonical vault state

This is covered in the companion brief on vault testing frameworks today. The two work together: session-scoped changes are useful both for demos and for tests.

## What This Does Not Try To Be

Deliberate non-features for v1:

- **Not a fork-and-edit model.** Session changes are ephemeral; if a visitor wants to actually edit the vault, they need a writable copy (e.g., by cloning it to their own account).
- **Not collaborative.** Session changes are per-tab, per-visitor; nobody else sees them.
- **Not exportable.** A visitor cannot save their session-scoped changes as a new vault from within the read-only experience. They could re-create the changes in a writable vault later.
- **Not persisted across sessions.** Reload = reset. Tab close = reset. Cross-browser session continuation is not in scope.
- **Not multi-step undo within the session.** Maybe v2; v1 just supports the current state.

Each of these is a possible v2 feature. None are needed for the v1 demo experience.

## What This Asks For

1. Audit the current state of read-only vault opening; identify polish work.
2. Decide the cross-vault navigation defaults (new tab vs replace; how share-tokens are carried).
3. Implement the session-scoped change shim over the JS API.
4. Add the visual indications for read-only mode and session state.
5. Test the trio against 3-4 concrete demo vaults (CV, medical, investor, configuration).
6. Document the JS API surface for vault authors so they can use these capabilities in their own vault apps.

Estimated effort: 2-3 weeks for the full trio, plus the polish that comes from real demo usage.
