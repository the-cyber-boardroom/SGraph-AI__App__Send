## What This Is

A new direction worth being deliberate about: **building AppSec mini-tools as small apps on top of vaults, leveraging existing open source tools where they exist, and using our infrastructure primitives (vaults, ephemeral compute, DNS, infographic generator, LLM integration) to solve the data-sharing problem these tools all share**. The voice memo names this as a direction with strong commercial and community potential, and threat modelling specifically as the first concrete example.

The framing matters because the pattern is bigger than any single tool. Once we have the substrate to host AppSec mini-tools on top of vaults, we can keep adding them: threat modelling, then SBOM analysis, then dependency scanning, then secrets detection, then security policy management, then compliance evidence collection. Each one becomes a small, well-scoped, vault-grounded mini-app.

Threat modelling is the first because it has the highest demand, the most active open-source projects to leverage (especially Matt Adams' StrideGPT), and the cleanest fit with our vault-as-state-of-truth model.

## The Strategic Insight

The voice memo names the structural problem these tools all face: **once you have done the analysis, where do you put the data?** Threat models, SBOMs, dependency reports, audit logs (each is a moderately-sensitive artifact that needs to live somewhere). Today, most of these tools either:

- Generate output as a one-off file the user is responsible for
- Store data in their own server-side database (vendor lock-in; trust issues)
- Live in GitHub Issues or a wiki (ad-hoc; loses metadata)
- Get exported to Confluence / Notion / SharePoint (lossy; manual)

**The vault is a clean answer**: cryptographically secured storage with versioning, sharing, audit trail, and offline portability. Every AppSec mini-tool we build on top of vaults gets the data-sharing problem solved for free. This is genuinely differentiating because most AppSec tool vendors do not have a credible answer to "where does the data live, and how do I share it with auditors / colleagues / customers without losing control?"

The secondary insight is **leveraging open source rather than rebuilding**. Tools like StrideGPT have been iterating for over a year, have active communities, integrate the latest LLM providers and the OWASP LLM Top 10. Building our own from scratch would waste their work; wrapping theirs gives us the tool plus the community engagement plus a contribution path back upstream.

The pattern that emerges: **find a strong open-source tool, host it on our infrastructure, give it our UI and vault integration, and contribute back to the upstream**. This is not us competing with the tool's maintainer; this is us providing distribution and a better data home.

## Matt Adams' StrideGPT As The First Target

The voice memo named the open-source threat modeller, and a quick search confirms: **Matt Adams' StrideGPT (github.com/mrwadams/stride-gpt)** is an actively-developed AI-powered threat modelling tool. Key capabilities as of May 2026:

| Capability | Detail |
|------------|--------|
| **Methodology** | STRIDE-based threat modelling |
| **GenAI integration** | OWASP LLM Top 10 integration for GenAI application threat modelling |
| **MAESTRO-inspired pattern detection** | Auto-detects RAG, multi-agent, code-execution, tool ecosystems |
| **Multi-modal input** | Accepts architecture diagrams as input |
| **Attack trees** | Generates attack tree visualisations |
| **DREAD scoring** | Risk-scored threats |
| **Gherkin test cases** | Generates test cases from threats |
| **GitHub repo analysis** | Pulls context from repo for analysis |
| **LLM providers** | OpenAI GPT-5.2, Anthropic Claude 4.5, Google Gemini 3, Mistral Magistral, plus local models |
| **Licence** | Open source on GitHub |
| **Author** | Matt Adams (mrwadams), security professional with strong domain credibility |

This is genuinely good work. The author has been iterating for over a year; the community is engaged; the LLM integrations are current. Building threat modelling on our platform without leveraging this would be wasteful.

The integration model:

1. The threat modeller mini-app lives on our infrastructure
2. The tool itself is a fork or wrapper around StrideGPT
3. The vault holds the threat models: both inputs (system descriptions, architecture diagrams) and outputs (threats, mitigations, attack trees, test cases)
4. Our LLM substrate (Nova via Bedrock; OpenRouter for other models) powers the analysis
5. Our infographic generator visualises attack trees and threat summaries
6. We contribute meaningful upstream PRs back to StrideGPT
7. The vault format becomes a portable home for threat models that competitors do not offer

This is not theft; it is layered value. The upstream tool solves the AI-powered threat modelling problem. We solve the data-home and operationalisation problem on top.

## The Two Implementation Modes

The voice memo flagged two distinct architectural options worth exploring:

### Mode 1: Pure Client-Side

The threat modeller runs entirely in the vault's app, in the user's browser. No server-side compute beyond serving static files. LLM calls go directly from the browser to the LLM provider using the user's own API key (or a Simple Token from the credential manager).

**Advantages:**

- Zero per-user infrastructure cost on our side
- Strong privacy: the data never leaves the user's browser
- Offline-capable: works on a laptop with no connectivity (assuming local LLM)
- Easy to ship as a self-contained vault

**Disadvantages:**

- No shared compute resources
- Tied to the browser's capability (storage limits, performance)
- Multi-user collaboration is harder
- Cannot do server-side scheduling or background analysis

This mode is the right fit for **individual practitioners** doing threat modelling on their own projects. It is also the right fit for **air-gapped or highly-regulated environments** where data must not leave the local machine.

### Mode 2: Ephemeral Compute-Backed

The threat modeller has a backend that lives on our infrastructure (Fargate task, container host, or AgentCore Runtime), spun up per-session or per-user. The browser-based vault app talks to its backend; the backend talks to LLM providers; results land in the vault.

**Advantages:**

- Server-side processing for heavier workloads (multi-agent system analysis, large repos)
- Multi-user collaboration possible (shared compute)
- Background analysis (scheduled threat-model refreshes, regression detection)
- Custom analysis pipelines beyond what runs in a browser

**Disadvantages:**

- Per-user compute cost (mitigated by the substrate spectrum work; ephemeral compute is cheap)
- Higher operational complexity
- Less obvious privacy guarantee (though the vault-grounding keeps the data confidential)

This mode is the right fit for **teams** doing collaborative threat modelling, **organisations** running threat modelling at scale, and **regulated environments** that benefit from auditable compute provenance.

**Both modes should be supported**, with the user picking based on their workflow. The vault is identical either way; the compute is what varies.

## The GitHub-Driven Vault Pattern

The voice memo flagged a specific operational insight: **this might be a good example of a vault that is also driven by GitHub**. The pattern:

1. The mini-tool's source code lives on GitHub
2. A vault clones the relevant GitHub repos as input data
3. Threat modelling runs against the cloned code
4. Results commit back to the vault
5. Updates to the upstream repo trigger re-analysis

This is a useful pattern beyond threat modelling. Any AppSec tool that analyses source code benefits from GitHub-driven vaults. The vault becomes a source-of-truth wrapper around external content, with analysis results layered on top.

We have not built this pattern explicitly yet. It is worth a separate dev brief if it gets traction, but for v1 of the threat modelling mini-tool, manual upload of code or system descriptions is enough.

## The "Solving The Data Sharing Problem" Frame

The voice memo named this as the core insight: **every AppSec tool has a data-sharing problem; vaults solve it once for all of them**. Worth being explicit about what this means:

| Data-Sharing Problem | How Vaults Solve It |
|---------------------|---------------------|
| Where does the threat model live? | In a vault; versioned, owned, exportable |
| How do I share it with auditors? | Read-only vault link with time-limited access |
| How do I bring in new data? | Vault content can be appended; tools read from vault |
| How do I run offline? | Vault collections are portable; tools run on local SG/Compute |
| How do I correlate findings across tools? | All tools write to the same vault structure; findings cross-reference |
| How do I version control my security artifacts? | Vault commit history IS the version control |
| How do I prove what was reviewed when? | Vault commits are cryptographically signed; auditors can verify |
| How do I share results without losing control? | Vault sharing with revocation; recipient sees data only as long as we allow |

Each of these is a real friction in current AppSec workflows. Each is solved by the vault model. **The platform's pitch to an AppSec team is not "we have better threat modelling than X"; it is "we have a clean home for all your security artifacts, with tools that work directly on top of them."**

## The Vibe-Code Path

The voice memo mentioned this: "we can vibe code and use private LLMs to create some experiments on top of it." This is the parallel innovation pattern:

- Beyond integrating existing open-source tools, we can prototype our own mini-tools quickly using LLMs
- A simple vibe-coded threat-modelling-experiment vault can be built in an afternoon
- These experiments live alongside the production tools and let us test new patterns rapidly
- Successful experiments graduate to formal mini-tools

This is the AI-augmented development pattern applied to AppSec product development. It is consistent with the "vibe code with private LLMs" direction across the platform.

## Commercial Implications

A few honest considerations about the commercial angle:

**Compelling pitch.** "We host the open-source AppSec tools you already use, on infrastructure you control, with a vault format that solves your data-home problem." This is genuinely differentiated from the existing market.

**Pricing model.** Pre-auth per-tool-invocation aligns naturally. Customers pay for compute and LLM costs; we add a thin margin. No subscription gatekeeping; pay-per-use. This is the credential manager + pre-auth substrate from Tuesday in action.

**Community engagement.** Contributing back to open-source projects we depend on (especially StrideGPT) is both ethical and strategic. The community sees us as good citizens; we get distribution and credibility from the affiliation.

**Risk:** the tools we integrate may pivot, become commercial, or stop being maintained. Mitigation: pick tools with strong governance, contribute upstream, fork only when necessary, have fallback options.

**Adjacent commercial opportunity.** Once AppSec teams use the platform for tool integration, they may also want it as a vault hosting platform for their broader security artifact management. The mini-tools become the wedge; broader vault adoption is the expansion.

## What This Does Not Try To Be

Deliberate non-features for v1:

- **Not a replacement for enterprise AppSec platforms.** This is a complementary offering, not a competitor to Snyk / Veracode / Checkmarx.
- **Not a comprehensive security platform.** The goal is a clean home + great mini-tools, not all-in-one.
- **Not a managed-service offering with humans in the loop.** This is software; human services are a separate conversation.
- **Not commercially exclusive use of integrated open-source.** Anything we build on top of open-source contributes back; the upstream stays freely available.
- **Not a fork of StrideGPT or similar.** We wrap; we contribute; we do not fragment communities.
