# SG Mail: Email Client On Vaults With Multi-Provider Backup

**date** 16 May 2026
**from** Human (project lead)

## What This Is

Build an email client that runs on our infrastructure, where **the vault is the system of record for email content and the user experience is a vault-client built on top of a file-system view of email**. The forcing function is concrete and personal: replace AWS WorkMail for the project lead's own email (~£8/month) with something we control end-to-end and that demonstrates the platform's capabilities to a customer-relevant degree.

A critical framing point: **we are not building email infrastructure**. SMTP servers, deliverability, IP reputation, DKIM/SPF/DMARC, spam filtering for outbound, anti-abuse for inbound: these are someone else's job, and there are now strong options. The vault starts the moment we have an EML file. Everything before that is connectors to AWS SES, Gmail, Cloudflare Email Service (which launched in April 2026 specifically as agent-friendly email infrastructure), or SMTP/POP3/IMAP servers we point at. Everything after that is the vault, the file-system abstraction over it, and the client experience.

The build is therefore tightly scoped: **the UX is the work, and the vault-as-filesystem is the substrate**. The email-fs work we already have is the foundation; the client built on top is the differentiated product. The rest is integration.

This is the right time. Several capabilities have converged: email-fs (existing), the serverless environment synthesis (today's brief), vault-as-data-store, DNS + TLS, infographic generator integration, LLM access via Nova and Bedrock. The voice memo names the integration explicitly.

The brief covers the email client itself, the multi-provider backup story (essential), connector strategy (multiple providers, our choice per use case), and the multi-vault isolation approach for private email.

## Why Now

Three converging factors:

1. **The substrate is ready.** Today's serverless brief makes the case explicit: stable DNS, ephemeral compute, vault as state, pre-auth metering, credential manager. The pieces that would have made this premature six weeks ago are now in place.
2. **The cost target is achievable.** WorkMail is ~£8/month for what the voice memo describes as a fairly basic offering. Running our own email solution on a small ephemeral EC2 instance with smart idle-down is plausibly cheaper, even at our scale of one user. The math says yes; the implementation reveals whether reality agrees.
3. **The demonstration value is high.** "Look, the team uses their own platform for email" is a sales artifact. It also forces us to confront the operational reality of running something we depend on, which is the best way to find the rough edges.

The personal use case is the wedge. Once the project lead's email runs on SG Mail, the next obvious customers are the team, then customers who already use the platform for other things. Email is sticky once it works.

## The Substrate Question

Because **we are not running email infrastructure ourselves**, the substrate question is much simpler than the original framing suggested. There is no always-on SMTP receiver; there is no always-on mail handler. The connectors are typically:

- **Polling-based** (poll IMAP every N minutes; pull new mail to vault) → ephemeral compute, runs on a schedule
- **Webhook-based** (Cloudflare Email Service posts to our endpoint when mail arrives; SES drops to S3 and triggers a Lambda; etc) → ephemeral compute, runs on arrival
- **API-based** (Gmail API; query for new messages) → ephemeral compute, runs on a schedule or user trigger

None require always-on infrastructure. The vault web app is the user-facing piece, and it can be serverless on-demand (today's brief). The connectors are short-lived workloads that run when mail arrives or when polled.

This means **the full SG Mail stack fits the serverless framing cleanly**. Substrate choice per piece:

| Component | Substrate |
|-----------|-----------|
| Connector (SES inbound poll / Cloudflare webhook handler) | Lambda or Fargate task, triggered on event/schedule |
| Email web app | Serverless vault app on container host (warm pool); cold-starts on first access |
| Vault storage | Standard S3 in dedicated account |
| Backup vaults | Different S3 in different account, possibly different provider |
| Outbound queue | Lambda or Fargate, runs on send-from-UI trigger |

The cost target (~£8/month for a single-user replacement of WorkMail) is comfortably reachable. SES inbound is roughly free at low volume; SES outbound is $0.10 per 1000; storage in S3 is cents per GB; serverless compute is fractions of pennies per invocation.

Compared to the original framing (always-on EC2 instance for SMTP), this is **much cheaper, much simpler operationally, and aligned with the serverless story** the platform tells.

## The Architecture

The system splits cleanly into **email infrastructure** (someone else's problem) and **the vault-based client** (our work):

```
+---------------------------------------------------------------+
|                                                               |
|   EMAIL INFRASTRUCTURE LAYER (provided by external services)  |
|                                                               |
|   - AWS SES                                                   |
|   - Gmail / Google Workspace                                   |
|   - Cloudflare Email Service (Agents-Week launch, Apr 2026)   |
|   - Generic SMTP / POP3 / IMAP / JMAP                          |
|                                                               |
+----------------------+----------------------------------------+
                       |
                       | EML files in / out
                       | (via connectors we build)
                       ↓
+---------------------------------------------------------------+
|                                                               |
|   THE VAULT-BASED PART (our work starts here)                 |
|                                                               |
|   +--------------+   +-----------+   +----------------+      |
|   |              |   |           |   |                |      |
|   | Connectors   |→  | email-fs  |→  | Vault (S3)     |      |
|   | per provider |   | layer     |   | encrypted      |      |
|   |              |   |           |   |                |      |
|   +--------------+   +-----------+   +----------------+      |
|                                              ↓                |
|                                      +----------------+      |
|                                      |                |      |
|                                      | Email Web App  |<-- Browser |
|                                      | (vault client) |              |
|                                      |                |              |
|                                      +----------------+              |
|                                                                       |
+-----------------------------------------------------------------------+
```

| Component | What It Does | Status |
|-----------|--------------|--------|
| **SES / Gmail / Cloudflare / SMTP connector(s)** | Receive EML files from provider; submit EML files to provider for sending | New (per-provider) |
| **email-fs layer** | Vault-backed filesystem; treats email as files in a folder hierarchy | Existing; needs polish |
| **Vault** | Encrypted storage of mailboxes, threads, messages, attachments, contacts | Existing |
| **Email Web App** | The vault client; browser-based; reads/writes via vault JS API | New; the substantive work |

The boundary is sharp and important: **as far as we are concerned, an email is an EML file with metadata**. How it got delivered to us is the connector's job. How we display it, search it, organise it, compose new ones, and put them back into a connector for sending; that is the vault client and email-fs.

This is what makes the build tractable. Email infrastructure is operationally heavy (deliverability, abuse handling, reputation management). The vault client is a UX problem. We pick the work that plays to our strengths and let providers handle theirs.

## The Connector Strategy

Different connectors serve different use cases. The first goal is the project lead's WorkMail replacement, but the architecture should support multiple providers because customers will already have a mail relationship they want to keep.

| Connector | Use Case | Effort |
|-----------|----------|--------|
| **AWS SES (outbound)** | High-deliverability outbound from our infrastructure; SES is mature, well-priced (~$0.10 per 1000 sent) | Low; well-documented APIs |
| **AWS SES (inbound)** | SES can receive into S3; we read EML files from S3 and pull into the vault | Low; well-documented |
| **Cloudflare Email Service** | Recently-launched (Apr 2026) agent-native email; Email Routing → Worker → POST EML to us; reasonable pricing | Medium; relatively new product |
| **Gmail API** | For users who keep Gmail as their primary; we read mailboxes via OAuth and mirror to vault | Medium; OAuth flow, scope decisions |
| **IMAP / POP3 / JMAP** | Generic; works against any mail server | Medium; lots of edge cases |
| **Direct SMTP submission** | For users who want to send through their own SMTP server | Low |

For the project lead's WorkMail replacement, the connector path is probably **SES inbound (receive into S3) + SES outbound (send via SES API)**. WorkMail's MX records get changed to point to SES; SES drops EML files into S3; our connector reads them into the vault. Outbound mail goes from the web app through the connector through SES.

For broader customer support, **Cloudflare Email Service** is interesting because it is positioned as agent infrastructure and uses Workers as the routing layer, which composes naturally with our serverless framing. We should evaluate it for v2.

For users who want to keep Gmail, **a Gmail API connector** pulls their mail into a vault as a mirror, with optional bidirectional sync. This is the broadest customer-reach play.

The connectors are pluggable. v1 ships AWS SES; v2 adds Cloudflare Email Service and Gmail API; later adds IMAP/JMAP for completeness.

## The Vault Client: Where The Differentiation Lives

This is the work. The email web app reads from email-fs and the underlying vault, displays a familiar email-client UI, lets the user compose and send, manages threads, search, contacts. All standard email-client UX patterns, plus the vault-grounded properties that make us distinctive.

The standard UX patterns (table-stakes for v1):

| Feature | What It Looks Like |
|---------|---------------------|
| Inbox / folders / labels | Standard sidebar with mailbox tree |
| Thread view | Conversations grouped by subject/references |
| Compose | New message, reply, reply-all, forward |
| Search | Full-text across messages |
| Contacts | Address book derived from message history |
| Attachments | Drag-and-drop in, click to download |
| Mobile-responsive web | Works on phone screens |
| Drafts | Auto-save; persist across sessions |
| Signatures | Per-mailbox signature configuration |

The vault-grounded distinctive properties (what sets us apart):

| Distinctive Feature | What It Enables |
|---------------------|------------------|
| **Versioned mail history** | Vault commit history shows when each message arrived; never lose anything |
| **Cross-vault references** | An email linking to a vault renders inline; a vault discussion can reference messages |
| **Per-message audit trail** | Who saw what when is part of the vault's commit history |
| **Export to vault collection** | A folder of email becomes a portable vault collection |
| **Multi-provider source visibility** | UI shows "this message came via SES inbound" or "via Gmail mirror" |
| **Encrypted at rest with user-held keys** | Provider has plaintext briefly during transit; vault holds encrypted; client decrypts |
| **LLM-augmented features (v2)** | Summaries, semantic search, draft suggestions, agent-assisted triage |
| **Infographic-generator integration (v2)** | Weekly digests as visual summaries |

The voice memo's framing question is right: **if we were creating a new version of email in an agentic web environment, what would it look like?** Not just a clone. v1 ships familiar UX with the vault-grounded foundation; v2 adds the agentic features that make it genuinely new.

For v1, **the familiar look-and-feel matching what people expect from email is the priority**. The differentiation can be subtle in v1 (good search, reliable threading, fast load, vault-grounded export). The bigger differentiation lands in v2 as the agentic features stack up.

## The Multi-Provider Backup Story

The voice memo named this as essential: **email backups should be in different vaults, different EC2 instances, different S3 buckets, and possibly different providers**. The reasoning is operational and architectural.

Operational reasoning: email is critical data. A bug in our vault code, a credential leak, an EBS volume corruption, an AWS account suspension: any of these could in principle threaten the primary store. Backups must be genuinely independent.

Architectural reasoning: **this is a great test case for the platform's multi-provider story**. If SG Mail can back up to a different AWS account and to (say) Backblaze B2 or Cloudflare R2, then we have validated the multi-provider vault pattern that customers will eventually want for their own data.

The proposed backup architecture:

| Tier | Storage | Purpose |
|------|---------|---------|
| **Primary** | Our main S3 in account A | Live email; what the web app reads |
| **Hot backup** | Different S3 in account B | Near-realtime mirror; cross-account isolation |
| **Cold backup** | Different provider (B2 / R2 / similar) | Provider-level isolation; weekly snapshot |
| **Offline archive** | Local file (encrypted vault collection) | Catastrophic recovery; quarterly export |

Each tier protects against a different failure mode. Even if the worst-case happens (someone gets into account A and deletes everything), the cold backup at a different provider remains.

The vault format makes this clean: a vault is a versioned encrypted store; copying it to a different bucket or provider is "just sync the files." No special backup format; the vault itself is the backup format.

## Storing Private Data In Different Vaults

The voice memo flagged this specifically: "let's not put these emails in the same vault as my public ones."

The principle: **private high-sensitivity data lives in its own vault**, ideally with its own:

- Encryption key (separate from other vaults)
- Storage location (separate S3 bucket / account / provider)
- Access path (the email vault is not reachable from the same DNS or share-token namespace as public vaults)
- Lifecycle (different backup cadence, different retention policy)

This is the natural extension of the vault-as-isolation-unit principle. For users with multiple categories of data (public bio + private emails + financial documents), each category lives in its own vault, with the manager-vault pattern from yesterday holding the relationship between them.

For SG Mail v1, this is a single vault per user, dedicated to email. The user's other vaults (public bio, infographic gallery, whatever) live elsewhere. The manager vault (if used) holds metadata about each but does not bridge them.

## Workflow For Migrating From WorkMail

The voice memo named a concrete need: import data from WorkMail into the new vault. The migration path:

1. **Export from WorkMail.** Use AWS WorkMail's export tools to get the user's mail in a standard format (probably mbox or maildir).
2. **Import to email-fs in a vault.** Run an import tool that takes the mbox/maildir, parses each message, commits to the vault using the email-fs structure.
3. **Verify.** Cross-check message counts, sample messages, ensure attachments are intact.
4. **Switch MX records.** Update DNS to point to the new SMTP receiver. Existing email flows to the new system.
5. **Cut over the client.** User opens the new email web app; sees historical mail; sends new mail.
6. **Keep WorkMail receiving for a transition period.** Either forward to new or keep as a secondary inbox during the cutover.

The transition can be staged. The user starts using the new system in parallel with WorkMail (forwarding); once confidence is high, the MX records change and WorkMail becomes archival.

Total migration effort: probably a half-day to a day, depending on volume of historical email. Some of this is one-time; some becomes a reusable migration tool for future customers.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not email infrastructure.** We do not run SMTP servers, do not manage IP reputation, do not handle deliverability. SES, Cloudflare Email Service, Gmail, or any IMAP server is the email infrastructure; we are the vault client on top.
- **Not a Gmail alternative for the mass market.** This is a personal/team email service that demonstrates the platform.
- **Not a competitor to Fastmail or HEY.** Different positioning; we are not selling to email-first customers initially.
- **Not full Outlook/Exchange replacement.** No calendar, no contacts as a shared resource, no scheduling for v1. Calendar may come later as a separate vault.
- **Not mobile apps in v1.** Mobile-responsive web only. Native apps later if there is demand.
- **Not POP3/IMAP for external clients in v1.** Web-only access. v3 could expose the vault content via IMAP for compatibility with Apple Mail / Outlook / Thunderbird.

Each of these is a possible expansion. None are needed for v1 to deliver the cost-replacement and demonstrability outcomes.

The architecture we are building for general "submit to a vault" workflows is essentially what email is. The two converge naturally.
