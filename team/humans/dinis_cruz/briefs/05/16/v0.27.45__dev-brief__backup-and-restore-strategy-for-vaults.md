## What This Is

A backup and restore strategy for our vaults, designed for the reality that **we are starting to hold mission-critical data**: the project lead's email after the SG Mail cutover, customer demo vaults, vaults that hold company operational state (manager vaults), and increasingly the artefacts that flow through the AppSec mini-tools. The memo flags this directly and names the right framing: it is not a backup solution, it is a **backup-and-restore solution**, with the restore part treated as first-class rather than an assumed-to-work afterthought.

The brief covers four interlocking concerns: the backup-restore discipline (with regular restore drills), the architecture (backup as a self-contained mini-app with its own vault and EC2 instance), the storage strategy (multi-tier across accounts and providers), and the agentic-first design (Claude Code sessions run scheduled health checks against the backup status vault).

## The Core Principle: Backups That Are Never Restored Are Not Backups

The voice memo names this up front: "let's not make the mistake that most people do with backups, where they do the backups and never restore it, so you never know if it works."

This is a well-known operational failure mode. Teams accumulate years of backup tapes, S3 buckets full of compressed dumps, and "yes we have backups" reassurances, and then when the day comes to restore, the format has drifted, the keys have rotated, the encryption is broken, the restoration scripts no longer work, or the data is corrupt in ways nobody noticed because it was never read.

The discipline that prevents this is **regular restore drills**. Not "we tested the backup once when we set it up." Continuous, automated, observable restore tests that prove the backup chain still works. Specifically:

- **Daily**: lightweight restore of a sample vault to a scratch environment; verify content matches source
- **Weekly**: full restore of a single random vault; cross-check against source
- **Monthly**: restore the whole platform's vault inventory to a fresh AWS account; cross-check against source
- **Quarterly**: tabletop disaster recovery exercise; restore from cold-tier (Glacier) backup

Each drill commits its results to a backup health vault (more on this below). A drill that fails is a P0 incident even if production is fine, because production-is-fine is a state that does not survive its first failure if the backups do not work.

## The Architecture: Backup As A Self-Contained Mini-App

The memo names a structural insight that elevates this beyond "set up cron + S3 sync": **the backup system is itself a mini-app on the platform**, with its own vault, its own UI, its own EC2 instance, its own workflows. This is the same vault-as-mini-app pattern from the AppSec mini-tools brief earlier today, applied to the operational concern of backups.

The architecture:

```
+-----------------------------------------------------------+
|                                                           |
|   Backup Mini-App (vault: sg-backup-operations)           |
|                                                           |
|   - UI (browser-based dashboard)                          |
|   - Backup status data (per-source, per-target)           |
|   - Restore drill results                                 |
|   - Configuration (sources, targets, schedules, alerts)   |
|   - Audit log (vault commit history)                      |
|   - JS API for agentic use                                |
|                                                           |
+-------------------------+---------------------------------+
                          |
                          | (workflows)
                          ↓
+-----------------------------------------------------------+
|                                                           |
|   Backup Worker (EC2 instance, long-lived)                |
|                                                           |
|   - Discovers sources (vaults to back up)                  |
|   - Performs backup operations (S3 → tier-2/3/cold)        |
|   - Verifies backups (read-back, hash compare)             |
|   - Schedules and runs restore drills                      |
|   - Writes results to the backup-operations vault          |
|                                                           |
+-----------------------------------------------------------+
                          |
                          | (data flow)
                          ↓
+-----------------------------------------------------------+
|                                                           |
|   Storage Tiers (next section)                            |
|                                                           |
+-----------------------------------------------------------+
```

The backup mini-app's vault holds the **operational metadata**: which vaults are configured to be backed up, when the last backup of each completed, whether the last restore drill passed, where the data is stored, what the rotation policy is. The backup worker EC2 instance reads this configuration, performs the backups, writes results back to the vault.

This is the **meta-project** framing the memo named: the backup system uses the platform's own primitives. It is dogfooding at the operational layer. If our vault-as-mini-app pattern is right, the backup system using it for backup operations is evidence.

### The DNS-Pinning Connection

The memo flagged the connection to the serverless work explicitly: "this is where the feature that is just about working, which we're introducing of the DNS pinning serverless to EC2 instances, this is where we can then have again long-lived workflows."

The pattern: `backup.sgraph.operations` (or similar) resolves to the backup worker's EC2 instance. The URL is stable; the underlying compute can change; observers (UI, agents, alerting) always reach the right thing. The DNS+TLS work from earlier this week makes this clean.

This also means **the backup mini-app is itself accessible at a stable URL**, so it can be linked, embedded, monitored, and shared with operators. It is a real piece of operational tooling, not a hidden cron job.

## The Agentic-First Design

The memo named another critical insight: backups should be **agentic-first**, meaning every operation has an API surface (JS API on the vault), so that automated agents can drive backup operations, verify results, and act on failures.

Concrete agentic workflows:

| Workflow | What It Does |
|----------|--------------|
| **Scheduled backup-health Claude Code session** | Runs every hour (or every day); reads the backup health vault; checks for stale or failed backups; alerts if anything is off |
| **Restore drill orchestrator** | An agent that picks a vault, restores it to a scratch environment, verifies, reports |
| **Cross-account auditor** | An agent that confirms backup vaults in account B match source vaults in account A |
| **Glacier retrieval coordinator** | When a deep restore is needed, an agent that initiates Glacier retrieval, waits for it, and runs the restore |
| **Anomaly investigator** | When backup size or duration changes anomalously, an agent that investigates and reports |

The JS API on the backup-operations vault lets each of these agents read state and trigger workflows. The voice memo's specific example: "this could literally be something that runs quite regularly, which is fundamentally going to stress test our capability."

This is the **operational version of the vault-grounded testing framework** from earlier today. The same primitive (an agent can drive any vault operation via the JS API) becomes a continuous integration story for the backup system itself.

## The Two Modes Of Backup: Data Vs Sequence

The memo named a subtle but important distinction: **backup of the data is separate from backup of the sequence**.

What this means concretely:

| Mode | Backed Up | Purpose |
|------|-----------|---------|
| **Data backup** | The S3 contents of vaults (raw encrypted bytes) | Restore the bytes; reconstruct the vault from S3 |
| **Sequence backup** | The vault's commit history, app state, metadata | Restore the vault to a specific point in time |

The data backup is **simpler and more important**: if we have the raw S3 contents and the vault's encryption key, we can reconstruct any vault. The sequence backup is **richer but optional**: it gives point-in-time recovery and detailed history, but a data-only restore still recovers the vault.

For v1, **focus on data backup**. Get the S3 contents copied to multiple tiers, multiple accounts, multiple providers, with verifiable integrity. The sequence backup story can be layered on later if the data backup proves the architecture works.

This also has an important property: **the backup system does not need to understand vault format**. It backs up bytes. The vault's encryption keys live elsewhere (with the user, in the credential manager). The backup is meaningless without the key, which is exactly the right property.

## The Storage Tier Strategy

Multiple storage tiers across multiple isolation boundaries. The voice memo flagged this directly: "one of the big mistakes you always do with backups is you put the backups in the same account that the data exists, which, of course, ransomware blows up everything, including your backups."

Proposed tiers:

| Tier | Storage | Purpose | Cost Profile |
|------|---------|---------|--------------|
| **Tier 0** | Same-account S3 (source) | The vault itself (not a backup, the original) | Standard S3 |
| **Tier 1** | Different-account S3 (account B) | Hot near-realtime mirror | Standard S3; cross-account write only |
| **Tier 2** | Different-account S3 (account C) | Daily snapshot copies | Standard S3 with retention |
| **Tier 3** | S3 Intelligent-Tiering or S3 Standard-IA (in account C) | Older snapshots; access infrequent | Cheaper per-GB; retrieval cost |
| **Tier 4** | S3 Glacier Instant Retrieval or Flexible Retrieval | Long-term archive | $0.004/GB-mo Instant or $0.0036/GB-mo Flexible; minutes-to-hours retrieval |
| **Tier 5** | Different-provider object storage (Akamai, Backblaze B2, Cloudflare R2) | Provider-level isolation | Variable per-provider; egress matters |
| **Tier 6** | Offline / cold (local encrypted archive) | Catastrophic recovery | Manual; quarterly |

Not every vault needs every tier. The vault's risk profile determines tier coverage:

- **Demo vaults**: Tier 0 + Tier 2 (we can rebuild the demo from scratch)
- **Customer-facing public vaults**: Tier 0 + Tier 1 + Tier 2 + Tier 4
- **Email vault**: All tiers including Tier 5 and Tier 6
- **Manager vaults (operational state)**: All tiers; especially important to preserve
- **AppSec data vaults (threat models, security findings)**: All tiers; regulatory implications

### The Backup Account As A Separate AWS Account

The memo flagged this specifically: "I really like this idea of having a backup account, which is a separate account that's almost read-only, and we provide, for example, a token to write into it in some cases."

The architecture: AWS account A is the production account where vaults live. AWS account B is the backup account where backups land. Account B has:

- Strict IAM that allows the source account's backup worker to write but not delete
- No interactive console access for normal operations (humans don't poke around)
- No outbound network access except for restoration
- Different root credentials; different recovery contact
- Optional: organisational SCP that prevents deletion of backup buckets without explicit override

This means **a compromise of account A cannot delete backups in account B**. Ransomware that reaches account A still cannot affect the recovery path because the credentials to delete in B do not exist in A.

This is a meaningful security property and is the right way to set up backup architecture in 2026. AWS Organizations support makes it relatively easy to set up; the operational discipline is the harder part.

### Multi-Provider For Provider-Level Isolation

Beyond multi-account-AWS, **multi-provider** protects against AWS-level events: account suspension, AWS-wide outages, account compromise via AWS support social engineering, regional disasters. Specific providers worth pursuing:

| Provider | Why |
|----------|-----|
| **Akamai Object Storage (Linode)** | S3-compatible; $0.02/GB-mo; reasonable retrieval cost; non-AWS infrastructure |
| **Backblaze B2** | S3-compatible; $6/TB-mo; very cheap egress; well-respected for backup-specific workloads |
| **Cloudflare R2** | S3-compatible; zero egress fees; pairs naturally with Workers |
| **Wasabi Hot Cloud Storage** | S3-compatible; predictable pricing; backup-focused vendor |

Different providers have different trade-offs. **For our initial multi-provider tier, Backblaze B2 is probably the right first target**: cheapest for the workload, backup-focused vendor reputation, S3-compatible API. Akamai Object Storage is a natural second because we already have an account.

The memo also flagged a strategic dimension: "this could be a nice way for us to start creating relationships with some other providers, including the ones that provide storage only." Multi-provider backup forces us to engage with non-AWS providers operationally. That experience compounds: every time we work with another provider, we learn what works, what does not, and what the integration boundary should look like. This is dual-purpose work: backup resilience AND multi-provider validation, the same direction as the multi-cloud brief from earlier today.

## What The Backup Worker Actually Does

A specific sketch of the backup worker's operational loop:

```
Every backup-window-start:
  1. Read backup-operations vault for configuration (which vaults; which tiers; which schedule)
  2. For each vault marked for backup:
     a. Read source S3 bucket; compute current state hash
     b. Check Tier 1 (different-account S3): is this state already there?
        - If yes: skip (deduplication)
        - If no: sync to Tier 1
     c. Verify: read back from Tier 1; compare hash
     d. Per the vault's policy, propagate to Tier 2, Tier 4, Tier 5 as appropriate
     e. Write backup result to backup-operations vault
  3. Schedule next backup window

Continuously (every N hours):
  1. Pick a random vault from the inventory
  2. Restore its most recent Tier 1 backup to a scratch environment
  3. Compare restored data to source data
  4. Write drill result to backup-operations vault
  5. Alert if drill fails

Weekly:
  1. Run full restore of one random vault
  2. Compare against source
  3. Document time-to-restore for the operational record

Monthly:
  1. Restore all vaults to a fresh AWS account
  2. Verify each
  3. Tear down the fresh account
  4. Write monthly DR drill report to backup-operations vault
```

This is the loop. It runs on a small EC2 instance (the same shape as the SG Mail receiver from this morning). Cost is low; coverage is comprehensive.

## The Backup-Operations Vault: What It Holds

Specifically, the structure:

```
sg-backup-operations/
├── configuration/
│   ├── sources.json           # Which vaults to back up
│   ├── targets.json           # Which storage tiers exist
│   ├── policies.json          # Per-vault policies
│   └── schedules.json         # Cron specifications
├── status/
│   ├── current.json           # Current state of every backup
│   └── by-vault/{vault-id}/  # Per-vault detailed status
├── drills/
│   ├── daily/                 # Daily restore drill results
│   ├── weekly/                # Weekly drill results
│   └── monthly/               # Monthly DR drill results
├── alerts/
│   └── active.json            # Currently active alerts
├── audit/
│   └── (commit history)       # Every backup, every drill, every change committed here
└── app/
    ├── index.html             # The UI
    └── api.js                 # The JS API
```

This is itself a vault. It has its own encryption key (Tier 1 backup applies here too, the backup vault gets backed up). It has its own UI showing dashboards and history. It has its own JS API for agentic access. **It is the platform applied to itself.**

## What This Asks For

Concrete next steps:

1. **Set up the separate AWS backup account** (account B). Configure IAM for write-only access from the source account's backup worker.
2. **Create the backup-operations vault** with the structure above.
3. **Build the backup worker** (small EC2 instance running the operational loop).
4. **Configure DNS for `backup.sgraph.operations`** (or chosen name).
5. **Define backup policies for the initial vault inventory** (which vaults; which tiers).
6. **Set up Tier 1 (cross-account S3) for all production vaults**.
7. **Set up Tier 4 (Glacier) for vaults that need long-term retention**.
8. **Set up Tier 5 (Backblaze B2 or similar) for one vault as a first multi-provider validation**.
9. **Implement the restore drill loop**: daily, weekly, monthly.
10. **Build the backup-operations vault UI** (dashboard, drill history, manual triggers).
11. **Configure scheduled Claude Code sessions** that run health checks against the vault.
12. **Run the first quarterly DR drill** within 60 days of backup system going live.
13. **Document the restore runbook**: what an operator does when "we need to restore X."

Estimated effort: 2-3 weeks for the backup worker, vault, and Tier 1/Tier 2 storage. Additional 2 weeks for Tier 4 (Glacier) and Tier 5 (multi-provider). Ongoing: restore drills are continuous operational work.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a customer-facing backup product (v1)**. This is for our own vaults. Customer backup as a service is a v3 conversation.
- **Not a point-in-time recovery system (v1)**. Data backup only; sequence backup is later if needed.
- **Not global failover.** Backups exist for restoration; they do not yet serve traffic.
- **Not a substitute for vault key management discipline**. Backups protect against data loss; key loss is a different problem requiring key escrow or similar.
- **Not zero-recovery-time-objective.** Tier 4 Glacier restores take hours; we are accepting that for cost reasons. Tier 1 restores are minutes.
- **Not snapshot consistency across vaults.** Each vault is backed up independently; consistent snapshots across many vaults at a single point in time is a separate concern.

## Honest Risks

Three risks to flag:

**Risk 1: Restore drills fail silently because nobody reads the results.** Mitigation: every drill failure creates an alert that requires acknowledgement; if alerts pile up unacknowledged, escalation kicks in.

**Risk 2: Backup costs grow faster than anticipated.** Each tier has a cost; multiple providers add cost; long retention adds cost. Mitigation: monthly cost review of backup spend; per-vault cost attribution so we can see which vaults are expensive to back up.

**Risk 3: The backup system becomes complex enough to need its own backups.** Recursive concern. Mitigation: keep the backup-operations vault simple; its own backup is just "same Tier 1 pattern, different account." The recursion terminates at "we trust the cross-provider tier as ultimate ground truth."
