## What This Is

A specific demo build, but also a template for a class of demos we want to ship: **a side-by-side two-personas demo environment showing accountant and client interacting through a shared vault**, with end-to-end orchestration (setup, vault loading, simulated workflow, teardown) controlled from a single UI. The accountant use case joins the demos we have planned (recruitment, news, risk) and adds an industry vector with strong customer pull.

The structural insight from the voice memo is the more interesting contribution than the use case itself: **a demo environment where the visitor can see two personas operating on the same vault simultaneously, with the orchestration of the underlying infrastructure visible to them as part of the demonstration**. This is more powerful than a single-pane demo because it shows the multi-actor reality of how the vault works.

Everything in this brief is buildable with technology we already have. No new primitives needed; just the right composition of existing pieces.

## The UI Structure

The visitor opens the demo and sees a four-pane layout:

```
+---------+----------------------+----------------------+----------+
|         |                      |                      |          |
| Actions | Accountant view      | Client view          | Demo     |
|         | (iframe → vault app) | (iframe → vault app) | text /   |
|         |                      |                      | narrative|
|         |                      |                      |          |
+---------+----------------------+----------------------+----------+
```

| Pane | Purpose |
|------|---------|
| **Actions (left)** | Demo control buttons: Setup, Load Vault, Run Step 1, Run Step 2, ..., Teardown |
| **Accountant view (centre-left)** | iframe showing the vault app from the accountant's perspective |
| **Client view (centre-right)** | iframe showing the vault app from the client's perspective |
| **Demo text (right)** | Narrative for the current step, explanatory copy, controls for advancing through the demo |

The visitor clicks through the action buttons sequentially. Each click triggers an underlying operation and updates the visible state.

This is the same FastAPI-mini-UI pattern we have used elsewhere (the infographic tool, the Nova POC from this morning). Familiar shape; well-trodden implementation path.

## The Same Vault, Two Apps

The architectural insight that makes this work: **the same vault can have different apps depending on who is opening it**. The accountant sees the accountant's app; the client sees the client's app; both apps are reading from and writing to the same underlying vault.

This is the SG/App framework taken to a concrete use case. The vault holds the data (contacts, invoices, transactions, reports, signatures). Each app is a different user-interface presentation tuned for a specific role.

How the two iframes load different apps from the same vault:

| Approach | Trade-offs |
|----------|-----------|
| **Different routes for different roles** | The vault app supports `/accountant` and `/client` routes; iframes load each accordingly |
| **Different apps mounted in the same vault** | The vault has `accountant.html` and `client.html` as separate apps; iframes load each |
| **Role-aware single app** | One app reads a role parameter and renders accordingly |

For v1, **different routes for different roles** is probably the cleanest. The vault app is a single SPA with role-based routing. Iframes load `/accountant?session=X` and `/client?session=X`. The same JS code runs in both; the rendering branches based on the role.

This raises a question worth flagging: **how do we open different pages for different users from the same vault?** This is partly a feature request on the SG/App framework. We probably need first-class support for "role-aware vault apps" beyond just route-based switching. For v1 of this demo, route-based switching is enough; longer-term, we may want richer role-based capabilities.

## The Workflow Steps

The demo walks the visitor through a sequence of business-logical steps. Each one is initiated by a button click in the Actions pane:

| Step | What Happens | Accountant View Shows | Client View Shows |
|------|--------------|----------------------|-------------------|
| 1. Setup | Provision the EC2 instance and DNS for this demo session | Banner: "Provisioning your demo environment..." | Same |
| 2. Load Vault | Vault is created with starter data; apps are loaded | Welcome to accountant package: "Click here to see accountant view" | Welcome to client package: "Click here to see client view" |
| 3. Accountant primes initial information | Accountant logs in; sets up the client's account | Form for setting up new client | "Waiting for accountant" |
| 4. Client enters data | Client logs in; provides initial details | Notification: "Client has filled in details" | Form for entering personal/business details |
| 5. Accountant requests documents | Accountant requests specific tax documents | Form for requesting documents | Notification: "Accountant needs your invoices" |
| 6. Client uploads invoices | Client uploads invoices, transactions | Sees invoices come in real-time | Drag-and-drop or simulated upload |
| 7. Accountant creates report | Accountant generates a tax return / financial report | Report drafting interface | "Accountant is preparing your tax return" |
| 8. Accountant submits for approval | Approval workflow triggered; client receives request | "Awaiting client approval" | Approval interface: "Click to review and sign" |
| 9. Client approves and signs | DocuSign-style sign flow | "Client has signed" | Signed confirmation |
| 10. Accountant submits to authorities | Simulated submission to local tax authority | Confirmation of submission; tracking ID | "Your return has been submitted on your behalf" |
| 11. Receipt and confirmation | Authority returns a confirmation document | Confirmation document received | Notification: "Tax return accepted" |
| 12. Teardown | Vault and EC2 instance are destroyed | Banner: "Demo complete; tearing down..." | Same |

The narrative text pane updates as each step runs, explaining what is happening, why it matters, and what the visitor is seeing.

Each step is an explicit action so the visitor can pause, examine state, take screenshots, and reflect before continuing. There is also a "play all" mode for visitors who just want to see the whole thing run.

## The Orchestration: FastAPI Behind The UI

The visitor's clicks need to actually do things. Most can be implemented entirely in the browser, but several require server-side action (creating EC2 instances, provisioning DNS, managing credentials, etc.). The same FastAPI pattern we are using elsewhere fits:

```
Browser → Mini UI (HTML/JS)
            ↓ (API calls per button click)
        FastAPI service
            ↓
        sg-compute commands (Setup, Load, Teardown)
        Direct vault state mutations (workflow steps)
            ↓
        Real infrastructure (EC2 instance, DNS, vault, etc.)
```

The FastAPI service holds credentials and the orchestration logic. The UI does not directly call AWS or our compute substrate; the FastAPI does. This is a critical separation because some of these operations create real cloud resources that cost real money; the orchestration layer enforces idempotency, rate limits, and authorisation.

### What The FastAPI Endpoints Look Like

| Endpoint | Action |
|----------|--------|
| `POST /demo/sessions` | Create a new demo session: returns a session ID |
| `POST /demo/sessions/{id}/setup` | Provision EC2 + DNS for this session; takes 30-60 seconds |
| `POST /demo/sessions/{id}/load` | Create vault with starter data; load both apps |
| `POST /demo/sessions/{id}/step/{n}` | Execute step N of the workflow |
| `GET /demo/sessions/{id}/state` | Return current state for the UI to render |
| `POST /demo/sessions/{id}/teardown` | Destroy the session; teardown infrastructure |

Each endpoint logs its action for observability and cost tracking (this is the kind of workload the pre-auth payment substrate is designed to meter).

## The Setup Phase: Real Infrastructure

The setup phase actually provisions real infrastructure:

1. Generate a fresh EC2 instance for this demo session (or pull one from the warm pool per the day 64 brief)
2. Set up DNS routing for the demo's subdomain (`demo-accountant-{id}.sgraph.app` or similar)
3. Issue a TLS certificate (via the Let's Encrypt automation)
4. Deploy the vault app
5. Create the demo vault with starter data
6. Return the session ID

This takes 30-60 seconds. The UI shows a clear progress indicator during this phase ("Provisioning your environment..." with rotating sub-steps).

Cost: a small EC2 instance for the duration of the demo (probably 10-20 minutes for a typical demo session) costs cents. The pre-auth substrate handles this transparently.

## The Teardown Phase: Cost Discipline

Teardown is as important as setup. The voice memo flagged this: "we wrap everything down, and then the EC2 instance is destroyed."

For a demo system that anyone can fire up, **automatic teardown is essential**. Two mechanisms:

1. **Explicit teardown** when the visitor clicks the Teardown button at the end of the demo
2. **Automatic teardown** after N minutes of inactivity (probably 15-20 minutes; reuses the reset-on-activity timeout pattern from the container hosts brief)

A demo that runs unattended for hours would burn unnecessary cost. The teardown logic guarantees we never leak resources.

There is also an "already-set-up" version the voice memo mentioned: a pre-provisioned demo environment that visitors can just dive into without waiting for setup. This is essentially a longer-running shared demo with multiple session slots. Worth offering both modes:

| Mode | Trade-offs |
|------|-----------|
| **Full setup-to-teardown experience** | Slower start; shows the infrastructure-provisioning capability; visitor's own session; cost per visit |
| **Pre-provisioned shared demo** | Instant start; less infrastructure visibility; shared environment; cost only when used |

For a public demo, the pre-provisioned mode is probably the default. For partner conversations and serious customer evaluations, the full setup mode is more impressive because it shows the real architecture working.

## What The Vault Holds

Demo-specific content in the vault:

| Path | Content |
|------|---------|
| `/clients/{client-id}/profile.json` | Client basic information |
| `/clients/{client-id}/transactions/{year}/` | Annual transaction data |
| `/clients/{client-id}/invoices/` | Uploaded invoice files |
| `/clients/{client-id}/reports/{year}/draft.pdf` | Drafted tax return |
| `/clients/{client-id}/reports/{year}/signed.pdf` | Signed version |
| `/clients/{client-id}/correspondence/` | Letters/emails from authority |
| `/accountant/clients-list.json` | Accountant's view of all clients |

The vault structure is intentionally realistic: this is what an actual accountant-client relationship might look like, mapped onto a vault. The demo's value depends on this feeling like a real workflow, not a contrived showcase.

## Workflow State And Demo State

A subtle but important distinction:

| State Layer | What It Holds |
|-------------|---------------|
| **Vault state** | The actual data (invoices, reports, signatures); persisted in the vault |
| **Demo session state** | Which step is current; what banner is showing; whether teardown is pending; held in the FastAPI service |

Stepping through the workflow advances both layers. The vault state mutates as expected (real invoices uploaded, real reports created). The demo state tracks where the visitor is in the narrative.

Resetting the demo (going back to step 1) does **not** roll back the vault; by step 7, the vault contains the work from steps 1-6. To start fresh, the visitor clicks Teardown and Setup. This keeps the model simple.

## What This Composes With

This brief is the third demo we have lined up (recruitment and risk were named earlier; news has been built; accountant is this one). The pattern that emerges:

- Each demo has a side-by-side persona view (the architecturally interesting bit)
- Each demo has a workflow with 10-12 steps
- Each demo provisions and tears down real infrastructure
- Each demo uses the platform's integrated capabilities (vault, apps, LLM, infographic generator)
- Each demo is self-contained, controllable, recordable

This means the work for the accountant demo is **mostly the demo content and the orchestration; not new infrastructure**. The infrastructure already exists. We are showcasing it.

A follow-up brief will likely propose a **demo framework** that captures these patterns so building the recruitment, risk, and news demos becomes mostly content work. Worth flagging now; not building today.

## The Recording And Self-Service Dimension

A demo built this way has two natural distribution channels:

1. **Live demos**: a salesperson or customer success person walks a prospect through the demo in real time, controlling the steps and explaining
2. **Recorded demos**: a 5-minute video of the full workflow with voiceover, shared as marketing content
3. **Self-service exploration**: a visitor clicks through at their own pace, reading the narrative text and pausing where curious

All three uses leverage the same demo build. The video recording is essentially the demo running with someone speaking over it.

For the public-facing version (self-service), the pre-provisioned shared environment is the right mode. For the live-demo version (with a salesperson), the full setup-to-teardown experience is more impressive.

## What This Does Not Try To Be

Deliberate non-features for v1:

- **Not a real accounting product.** This is a demo; the workflow is realistic but not production-grade accounting software.
- **Not multi-currency or multi-jurisdiction.** Pick one country's tax authority as the example; v2 can broaden.
- **Not actually submitting to a real authority.** The submission is simulated; we are not integrating with HMRC's actual systems.
- **Not a long-running customer-facing version.** This is a demo; if accountants want to actually use the platform, that is a separate productisation conversation.
- **Not the full vaults-of-vaults pattern.** One vault per demo session, not a manager vault holding many client vaults. The manager-vault pattern is what an accountant-platform product would look like at scale; the demo just shows one client.

Each of these is a possible later expansion. None are needed for the demo to land.

| Which country's tax workflow to simulate first? | Probably UK (HMRC self-assessment) for familiarity; US 1040 is the obvious alternative |
