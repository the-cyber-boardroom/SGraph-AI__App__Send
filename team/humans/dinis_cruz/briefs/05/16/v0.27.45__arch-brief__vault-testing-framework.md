## What This Is

A proposal for a layered testing framework for vaults: **unit tests, integration tests, QA tests, and browser-automation tests**, all accessible via the same JS API surface that the vault app uses for its normal operations. The premise is that a vault is not just content; it is a small application with its own tools, workflows, and behaviour, and any application worth shipping is worth testing.

This brief is the architectural piece. The companion dev brief covers the CI pipeline that runs these tests automatically.

The motivation is concrete: as we accumulate demo vaults (CV, medical, investor, newsroom, band, infographic gallery), and as customers start to build vaults that they expect to work reliably, **we need to answer the question "is this vault okay?" programmatically**. Without testing, the answer is "open it manually and see," which is slow and unreliable. With testing, the answer is a CI green check or a specific failure message pointing to what broke.

## The Four Layers Of Testing

Each layer answers a different question:

| Layer | Question Answered | Substrate |
|-------|-------------------|-----------|
| **Unit tests** | Does this specific function or component of the vault work as expected? | Pure JavaScript in the vault app context |
| **Integration tests** | Do multiple parts of the vault work together correctly with real data? | JavaScript with vault state access; possibly with some live data |
| **QA tests** | Does the vault behave correctly through the user-visible workflows, including writes? | JavaScript plus state mutations; results compared against expected outcomes |
| **Browser-automation tests** | Does the rendered vault work correctly in a real browser, from a real user's perspective? | Playwright (or equivalent) driving a real browser session |

The four layers compose naturally. A vault's test suite includes some of each, depending on what aspects of the vault matter most.

## The JS API As The Test Surface

A key architectural insight: **the same JS API surface that the vault app uses for normal operations is the right surface for testing**. The voice memo flagged this: "the same API that we made available in the iframe is the same API that we could make available to the entity opening up the page in Playwright."

This is a strong design decision. It means:

- Tests use the same primitives as the app, so they exercise real code paths
- A vault author who knows the JS API can write tests for their vault
- Tests are portable across testing environments (unit, integration, browser automation all use the same API)
- The API itself gets battle-tested by the test suite; if it is missing capabilities for testing, those gaps are visible
- We do not maintain two parallel surfaces (a "production API" and a "testing API")

The JS API is partly implemented today; this brief frames its completion as both a feature and the foundation for testing.

## Layer 1: Unit Tests

Pure JavaScript, no browser, no rendering, no vault state mutation. A unit test verifies a specific function or component in isolation.

Example unit tests for a CV vault:

```javascript
test('formatPhoneNumber handles UK numbers', () => {
  expect(formatPhoneNumber('+447900123456')).toBe('+44 7900 123 456');
});

test('skillsFilter returns only relevant skills', () => {
  const skills = [{ name: 'Python', relevant: true }, { name: 'Brainfuck', relevant: false }];
  expect(skillsFilter(skills)).toEqual([{ name: 'Python', relevant: true }]);
});
```

These run in a JavaScript test runner (Vitest, Jest, or whatever fits our stack). Sub-second execution per test. Hundreds can run on every commit.

The vault's own JavaScript modules are unit-testable like any other code. The test runner runs against the modules directly; no vault context needed.

## Layer 2: Integration Tests

JavaScript with access to vault state. An integration test verifies that components work correctly together when reading and processing real vault data.

Example:

```javascript
test('CV vault renders all experience entries', async () => {
  const vault = await openTestVault('test-vaults/cv-example');
  const renderer = createRenderer(vault);
  const html = await renderer.render('/experience');
  expect(html).toContain('Engineer at Anthropic');
  expect(html).toContain('Engineer at Google');
});

test('medical vault patient summary matches expected schema', async () => {
  const vault = await openTestVault('test-vaults/medical-example');
  const summary = await vault.getPatientSummary('patient-001');
  expect(summary).toMatchSchema(patientSummarySchema);
});
```

These run against a fixture vault (a real vault in a known state) and verify behaviour. They use real vault APIs but operate against test fixtures rather than production data.

The fixture vaults are themselves committed to the repo as test data. Tests reference them by path. The same fixtures can be used across many test runs.

## Layer 3: QA Tests

Like integration tests, but exercise read-then-write-then-verify workflows. A QA test might:

1. Open a writable test vault
2. Make a specific change
3. Verify the change is reflected correctly
4. Reset state for the next test

This is where the **read-only-with-session-scoped-changes** capability from the companion brief becomes useful for testing too. A QA test can:

- Open a vault in a writable test mode
- Make session-scoped or committed changes
- Verify the expected state
- Reset between tests via clean session boundaries

The QA tests verify the parts of the vault that depend on state mutations: forms, workflows, transformations.

Example:

```javascript
test('invoice creator produces valid output', async () => {
  const vault = await openTestVault('test-vaults/invoice-creator', { mode: 'session' });
  await vault.app.fillInvoiceForm({
    customer: 'Acme Corp',
    items: [{ description: 'Consulting', amount: 1000 }]
  });
  const invoice = await vault.app.generateInvoice();
  expect(invoice).toContain('Acme Corp');
  expect(invoice).toContain('£1,000.00');
});
```

QA tests are slower than unit and integration tests (vault state setup takes time) but verify the end-to-end behaviour that matters most for customer-facing functionality.

## Layer 4: Browser-Automation Tests

Playwright (or similar) drives a real browser, opens the vault as a real user would, interacts with the rendered UI, and verifies behaviour.

This is the slowest tier but the most realistic. It catches rendering bugs, JavaScript runtime issues, CSS problems, browser-compatibility quirks, accessibility issues that the lower tiers miss.

Example:

```javascript
test('CV vault is readable on mobile', async ({ page }) => {
  await page.setViewportSize({ width: 375, height: 812 }); // iPhone size
  await page.goto('https://send.sgraph.ai/vault/test-cv-token');
  
  await expect(page.locator('h1')).toBeVisible();
  await expect(page.locator('.experience')).toBeVisible();
  
  const emailLink = page.locator('a[href^="mailto:"]');
  await expect(emailLink).toBeVisible();
});

test('session-scoped form changes persist within navigation', async ({ page }) => {
  await page.goto('https://send.sgraph.ai/vault/test-investor-token');
  
  await page.locator('input[name="sector"]').fill('SaaS');
  await page.click('text=Next');
  
  await expect(page.locator('.results')).toContainText('SaaS-specific data');
});
```

Browser-automation tests are typically run less frequently than unit and integration tests (the cost is higher), but they are the only layer that genuinely tests the vault as users experience it. CI should run them at least on every release candidate; ideally on every merge to main.

## How The Layers Compose Per Vault

A typical vault's test suite mixes layers:

| Vault Type | Typical Test Mix |
|------------|------------------|
| CV / portfolio | Heavy unit (formatting, filtering); some integration (rendering); some browser-automation (mobile responsiveness) |
| Medical case study | Heavy integration (data correctness); some QA (interactive scenarios); some browser-automation (visual checks) |
| Investor pitch | Some unit; heavy integration (calculations); some browser-automation (multi-step flows) |
| Configuration vault | Heavy unit (validation); heavy integration (rule application); some QA (configuration changes); some browser-automation |
| Newsroom article | Some unit; heavy integration (rendering); browser-automation (mobile, accessibility) |
| Generic SG/App | Whatever the author writes; we provide the framework, they choose the mix |

The framework lets vault authors pick the test mix that matches their vault's risk profile.

## The Test Runner: Where Does It Live?

A specific design choice: **where does the test runner execute?**

Three options, each suitable for different layers:

| Option | Best For | Notes |
|--------|----------|-------|
| **In-vault (same JavaScript context as the vault app)** | Unit tests | Cheapest; fastest; vault author can run them in their dev environment |
| **In a separate Node.js process** | Integration and QA tests | Can simulate the vault context without a browser; faster than browser automation |
| **In a real browser via Playwright/equivalent** | Browser-automation tests | Most realistic; slowest |

V1 supports all three with a unified test definition format. The same test file can declare tests in different layers; the test runner routes each to the right execution environment.

## The Test Definition Format

A test file is JavaScript that declares tests using a standard format. Sketch:

```javascript
// tests/cv.test.js

import { describe, test, expect } from '@sgraph/vault-test';

describe('CV vault', () => {
  
  test('formats phone numbers correctly', { layer: 'unit' }, () => {
    // pure JS test, runs in unit context
  });
  
  test('renders all experience entries', { layer: 'integration' }, async ({ vault }) => {
    // runs in integration context with vault state access
  });
  
  test('form submission updates UI', { layer: 'qa' }, async ({ vault, session }) => {
    // runs in QA context with session-scoped mutations
  });
  
  test('mobile view shows all sections', { layer: 'browser' }, async ({ page }) => {
    // runs in browser-automation context
  });
  
});
```

The `layer` option tells the runner which execution environment to use. Test authors do not need to manage that themselves; they declare what they want to test and the framework handles the rest.

## The "Is The Vault Okay?" Question

The voice memo named this as the canonical use case: a way to programmatically answer "is the vault okay?" The answer:

1. Run the vault's test suite
2. Each test passes or fails
3. The overall status is the conjunction
4. Failed tests point to specific problems

This becomes the vault-equivalent of CI for traditional software. The pipeline (companion brief) runs this whenever the vault changes, whenever the vault app updates, on a schedule for monitoring purposes.

## What This Asks For

1. **Complete the JS API** so all four layers can use it consistently. This is the foundation.
2. **Pick a test runner / framework** that supports the layered model. Probably Vitest for unit/integration; Playwright for browser; a thin orchestration layer to unify.
3. **Define the test file format** so vault authors can write tests once and have them run in the appropriate environment.
4. **Build the integration / QA contexts**: ways to spin up a vault in a test environment, including with session-scoped mutability.
5. **Build a small reference test suite** for one of our demo vaults (CV is a good first target).
6. **Document the testing patterns** for vault authors.
7. **Connect to CI** (companion brief).

Estimated effort: 2-3 weeks for the framework foundation, plus ongoing work as we use it.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a general-purpose JavaScript test framework**. We use existing tools (Vitest, Playwright) and wrap them for the vault context.
- **Not a formal verification system**. We are testing behaviour, not proving correctness.
- **Not a load testing or performance benchmarking framework**. Those are separate concerns (covered separately).
- **Not opinion-enforcing**. The framework supports many test styles; we do not mandate a particular philosophy.

## How This Connects To Other Briefs

The testing framework sits at a junction:

- **Demo capabilities** (companion brief today): the read-only and session-scoped capabilities are reused by QA and browser tests
- **CI pipeline** (companion brief today): runs these tests automatically on vault changes

- **The Bedrock CLI work from yesterday**: agents that write vault code can run tests against the result before considering the work complete
- **The pre-auth payment metering**: test runs have cost (compute, browser-automation time); the metering handles it

The testing framework becomes part of the platform's connective tissue.
