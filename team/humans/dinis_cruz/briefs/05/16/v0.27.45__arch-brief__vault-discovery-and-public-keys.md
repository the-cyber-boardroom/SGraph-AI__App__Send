## What This Is

A new vault capability: **a server hosting multiple vaults should be able to answer "what vaults exist here?" in a controlled, useful way**. This sits at the intersection of three concerns the voice memo named: vault discovery (the structural question), public/private keys for vaults (the mechanism that makes secure discovery possible), and offline-deployable demo collections (a concrete application).

The motivation is operational. When a server hosts a self-contained collection of vaults (especially the manager-vault scenarios we have been describing, or a demo bundle, or an offline deployment) the question "which vaults are here?" is genuinely useful. A user lands on the server; the user wants to see what is available; the user picks one. Today, we have no answer to that question that does not require the user already to know what they are looking for.

This brief proposes the discovery primitive, the key infrastructure that supports it, and the concrete applications.

## The Discovery Question

"Which vaults exist on this server?" sounds simple but breaks into several distinct sub-questions depending on context:

| Context | Question | Who Should Answer? |
|---------|----------|--------------------|
| Public-facing vault server | What public vaults are here? | The server, freely |
| Public-facing vault server | How many private vaults are here? | Maybe count only, no identifying details |
| Self-contained demo bundle | What demos can I run? | The server, freely |
| Manager-vault collection | What vaults does this manager hold? | The manager vault itself |
| Multi-tenant hosting | What vaults exist on this host? | Should not answer; tenants do not see each other |
| Offline deployment | What vaults are bundled? | The bundle itself, like a table of contents |

Each context has a different right answer. The brief is about giving the platform the building blocks to support each context appropriately, not imposing a one-size-fits-all answer.

## The Public/Private Key Insight

The voice memo flagged a useful structural observation: **vaults already have keys, and some of the encryption is partial**. We have key material in the vault format that might already support a public/private split. Worth investigating concretely before designing new primitives:

1. What keys do vaults have today, and which are encrypted vs in plaintext?
2. Does the existing format support a public key that can be safely exposed?
3. If yes, what is the minimum change to make it useful for discovery?
4. If no, what is the minimum new key infrastructure to add?

The probably-right answer: **vaults gain a clearly-named public key (the one safe to expose) and a private key (the one that must stay protected)**. The public key supports:

- Verifying that the server is talking about a real vault (signed metadata)
- Cryptographic addressing (vault identifiers based on the public key)
- Receiving content from outsiders (anyone can encrypt to the public key; only the holder of the private key can decrypt)
- Discovery: a server can list public keys without exposing private content

This is the standard public-key cryptography pattern applied to vaults. Worth doing properly now rather than retrofitting later.

## The Server Discovery Primitive

The proposed structural addition: **a deterministic endpoint per server that lists vaults the server is willing to expose**.

```
GET https://server.sgraph.app/.well-known/vaults
```

or similar. The endpoint returns a structured response:

```json
{
  "server": "demos.sgraph.app",
  "vaults": [
    {
      "id": "demo-cv",
      "title": "CV / Portfolio Demo",
      "description": "A self-contained CV demo",
      "public_key": "...",
      "visibility": "public",
      "thumbnail": "data:..."
    },
    {
      "id": "demo-accountant",
      "title": "Accountant Workflow Demo",
      "description": "Side-by-side personas demo",
      "public_key": "...",
      "visibility": "public",
      "thumbnail": "data:..."
    }
  ],
  "private_count": 3
}
```

Key design choices:

| Choice | Default |
|--------|---------|
| Endpoint path | `/.well-known/vaults` (matches the well-known URI pattern) |
| Per-vault visibility | Each vault declares whether it appears in the listing |
| Public vault details | Title, description, public key, optional thumbnail, optional screenshot |
| Private vault details | Count only (or nothing, depending on server policy); no titles, no keys |
| Caching | Standard HTTP caching; servers can set TTLs |
| Format | JSON for v1; possibly RSS/Atom too for content aggregation later |

The server's policy decides what to expose. A public demo server lists everything. A multi-tenant private hosting server lists nothing (or returns 404 to discovery requests). A self-contained bundle for offline use lists all bundled vaults.

## The Vault Visibility Model

Each vault declares its discovery posture in its metadata:

| Visibility | What This Means |
|------------|-----------------|
| `public` | Vault appears in server listings; readable by anyone with the URL |
| `unlisted` | Vault is accessible by URL but does not appear in listings |
| `private` | Vault is not listed; not accessible without proper credentials |
| `count-only` | Vault is private but its existence (count) is visible in listings |

This is similar to YouTube's video visibility model. The defaults probably should be:

- New vault: `private` by default (least surprise)
- Demo vault: `public` (explicit choice by the author)
- Customer-uploaded vault: configurable, with `unlisted` as the recommended default for shareable but not discoverable

## The Self-Contained Demo Server

The voice memo named this concrete use case: **a server you deploy with a bundled collection of demos**. Visitor lands on the server, sees a "pick a demo to run" interface, clicks one, the demo loads. Same orchestration pattern as today's accountant-demo brief, but extended to a catalogue.

The architecture:

```
Server (single EC2 instance or container host)
    ↓ 
Discovery endpoint at /.well-known/vaults
    ↓ 
List of bundled demo vaults:
    - CV demo
    - Accountant demo
    - Newsroom demo
    - Recruitment demo
    - Risk demo
    - Band demo
    - Medical demo
    ↓
User clicks one → demo's vault loads → workflow runs → teardown when done
```

The whole server is essentially a manager vault, with its child vaults being the demos. The manager vault has its own app that presents the demo catalogue. Clicking a demo opens it in the same UI pattern as the accountant brief from earlier today.

**Cost is lower than per-demo setup** because the server stays running across many visitors. Each demo session is just a vault load, not an EC2 provision. The cost model becomes "one server hosting many demos" rather than "one EC2 per demo session." For a heavily-trafficked demo server, this is the right pattern.

## The Offline Deployment Story

This is where it gets interesting. The voice memo named it: "this could even be the vault that has all the demos, which could also be something you can ship locally for people who do offline deployments."

A self-contained server with a vault catalogue is **a portable artefact**. Properties:

| Property | Value |
|----------|-------|
| Format | Single container image or VM image |
| Content | Server runtime + bundled vault collection + apps |
| Connectivity | Optional: works fully offline; LLM features require network |
| Distribution | Docker image, VM image, USB stick, downloadable zip |
| Target users | Air-gapped environments, conferences, customer site visits, regulated industries |

**Why this matters**: some customers and prospects cannot or will not connect to the internet for evaluation. Defence, financial services in certain jurisdictions, healthcare in certain jurisdictions, customers behind strict corporate firewalls. For these, the ability to ship a complete demo collection that runs entirely on a laptop or air-gapped server is a meaningful differentiator.

It also serves a less exotic case: **a salesperson visiting a customer can bring a USB stick with the latest demo bundle and run it locally without depending on conference WiFi**. This is genuinely useful.

The offline bundle is essentially the same architecture as the online demo server, just shipped as a portable artefact. The container hosts primitive from earlier this week is the substrate either way.

## How This Composes With Manager Vaults

The vaults-of-vaults pattern from yesterday named manager vaults as a specific sub-category: vaults whose content is metadata about other vaults. The discovery primitive fits cleanly:

| Pattern | How Discovery Works |
|---------|---------------------|
| Standalone manager vault | The manager vault's own app lists its child vaults via the discovery endpoint |
| Demo server | The whole server is essentially a manager vault; discovery lists the demos |
| Customer collection | A customer's manager vault holds many private vaults; discovery lists them with appropriate visibility per the customer's policy |
| Self-contained mini-app | A standalone vault might list nothing (it is just itself) |

The pattern composes. The discovery primitive is a general capability that manager vaults specifically benefit from.

## The Public Key As Vault Identifier

A specific question worth being deliberate about: **should the vault's public key (or a hash of it) become its canonical identifier?**

Pros:

- Cryptographic addressing: an identifier that proves provenance
- Self-verifying: anyone with the identifier can verify the vault's authenticity
- Portable: the same vault on different servers is identifiable as the same vault
- Decentralisation-friendly: not tied to a particular server's namespace

Cons:

- Long identifiers (public-key hashes are not human-readable)
- Migration cost: existing vault IDs would need a mapping or replacement
- Key rotation becomes harder if the identifier IS the key

For v1, probably the right answer is: **keep human-readable vault IDs as the primary identifier, but also expose the public key in metadata for cryptographic uses**. Both identifiers coexist. The public key identifier is for machines; the readable ID is for humans.

## Sending Content To A Vault

The voice memo flagged a related question: "if I want to write something that I want to give a vote or want to send to a vote, how do I do it?"

This is where public-key infrastructure pays off in a second way: **anyone can encrypt content to a vault's public key, even without authorisation to read the vault**. The flow:

1. Sender knows the vault's public key (from discovery, or out of band)
2. Sender encrypts content under the public key
3. Sender sends the encrypted content to the server (POST to a vault-specific endpoint)
4. Server stores the encrypted content in the vault's inbox
5. Vault owner (who has the private key) reads the inbox and decrypts

This is essentially "submit to a vault" without "read from a vault": the cryptographic version of a one-way door. Useful for:

| Use Case | Example |
|----------|---------|
| Anonymous tip-line | A whistleblower submits an encrypted document; recipient decrypts |
| Customer-uploaded content | A client uploads files to an accountant's vault without seeing other clients' files |
| Form submissions | A web form submits encrypted data to a vault; vault owner reads later |
| Inter-vault messaging | Vault A sends a message to vault B by encrypting to vault B's public key |
| Anonymous voting / surveys | Submitters encrypt to the survey vault; vault owner counts |

Each one is a useful capability that becomes possible with public keys.

## What Already Exists Vs What Needs To Be Built

Before building anything, the audit step:

1. **What keys do vaults have today?** Check the current vault format; identify what is encrypted, what is plaintext, what serves what purpose.
2. **Is there an existing public key we can reuse?** If yes, the brief is mostly about discovery; if no, we need new key infrastructure.
3. **Are vault IDs derivable from keys today?** If so, we already have cryptographic addressing implicitly.
4. **What is the migration cost for existing vaults if we change anything?** A few hundred vaults exist; backwards compatibility matters.

Probable findings (based on what we have built so far):

- Vaults have an encryption key (the symmetric key used for content encryption)
- There may or may not be a separate signing key
- The encryption key is private; should never be exposed
- A public-key infrastructure layered on top is probably new work, not a reuse

The brief errs on the side of "do this properly" rather than "fudge it with existing material." Public/private keys for vaults is a small piece of foundational work that pays off many ways.

## What This Asks For

The concrete work:

1. **Audit the current vault key infrastructure** to understand what we have today.
2. **Design the public/private key model** for vaults (probably Ed25519 signing keys + X25519 encryption keys per industry-standard practice).
3. **Implement the discovery endpoint** at `/.well-known/vaults` on each server.
4. **Add visibility settings to vault metadata** (public / unlisted / private / count-only).
5. **Implement "send to a vault" capability** using the public key.
6. **Build the self-contained demo server** as the first real consumer of the discovery primitive.
7. **Plan the offline-bundle artefact** (single Docker image or VM image with bundled vaults).
8. **Decide on identifier model** (human-readable ID with public key as auxiliary, probably).
9. **Document the public-key infrastructure** for vault authors who want to use it.

Estimated effort: 2-3 weeks for the foundation. The demo server is mostly composition once the substrate exists.

## What This Does Not Try To Be

Deliberate non-features for v1:

- **Not a decentralised identity system.** Public keys are vault-level, not platform-level identity.
- **Not a public vault marketplace.** We are giving servers the ability to advertise their contents; not building a global directory.
- **Not blockchain-anchored.** Public keys are just keys; no chain commitment.
- **Not a forced visibility default.** Vault authors choose; we provide good defaults.
- **Not the same as our existing share-token mechanism.** Share tokens grant access; public keys enable discovery and one-way submission. Different primitives, both useful.

## Open Questions

| Question | Notes |
|----------|-------|
| Ed25519 + X25519 or a simpler model? | Industry standard; probably right |
| How do we handle vault key rotation? | Important; needs design; probably explicit rotation events with both old and new keys briefly active |
| Are vault public keys self-certifying or chained to a server's identity? | Probably self-certifying for v1; CA-style chaining if needed later |
| Should the discovery endpoint require any authentication? | Probably no for the public listing; yes for any deeper queries |
| How do we handle malicious servers listing vaults that are not really there? | The vault's public key is the cryptographic proof; servers cannot fake it |
| Is there an attack where a server claims many fake vaults to inflate counts? | Possibly; rate limits and key verification mitigate |
| What format for the offline bundle? | Probably Docker image (most portable for our team) or a simple zip |
| How does the offline bundle handle LLM-dependent features? | Either skip them, ship a local model, or document the connectivity requirement |
| Should there be a server-level catalogue UI bundled with the discovery endpoint? | Yes; a simple HTML page that renders the discovery output for browsers |
