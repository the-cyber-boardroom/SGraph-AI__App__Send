## What This Is

A synthesis observation: **the primitives we have been building over the last three weeks are now close enough to compose into a genuine new serverless compute environment, specifically built for agents**. Not "generic Lambda alternative"; Lambda is fine for what it does, and we are not chasing that market. **A serverless environment for agents, with the isolation, observability, and substrate control that agent workloads actually need**.

The observation is structural. Several recent briefs each named a piece of the puzzle. None of them framed the resulting whole. This brief names it: **a stable URL backed by ephemeral compute, per-use-case isolation, parallel-request handling that does not punish you for traffic spikes, and full control over the lifecycle in ways Lambda never let us**.

Once we connect the pieces explicitly, the question shifts from "can we build this?" to "should we ship it as a distinct product surface for agentic workloads, or is it implicit in the rest of the platform?" The brief argues for explicit naming, with the agent-focused framing as the differentiator.

## What Serverless Actually Means

Worth being precise about the property that makes serverless interesting:

> **Serverless = no servers running when there is no traffic, with a defined cost to start serving traffic and ongoing per-invocation cost while traffic is served.**

The cost shape is what matters. Capacity scales to zero when nothing is happening. The platform handles the cold-start when traffic arrives. Users pay only for what they use.

The voice memo flagged the operational complaint that has been latent in our conversations for weeks: **Lambda has serverless cost shape but limited control**. Functions are scoped narrowly; cold-starts are AWS-managed; you cannot inspect a running function; you cannot easily change runtime behaviour; you cannot stop a function that is misbehaving without modifying code and redeploying.

Our composition can deliver the cost shape **with full control**:

| Property | Lambda | SG/Compute Serverless |
|----------|--------|------------------------|
| Cost when idle | Near zero (small connection-warm overhead) | Zero (DNS only; no servers) |
| Cost during traffic | Per-invocation + per-ms compute | Per-second EC2 + per-invocation metering |
| Parallel request handling | Pay per-instance for concurrency; cold-start each new parallel slot | Container handles many parallel requests; cold-start paid once |
| Cold start time | 100ms-6s (depends on runtime, package size, SnapStart) | 30-60s for setup; 5ms-1s for subsequent if container warm |
| Maximum execution time | 15 minutes | Unbounded (workload's own timeout) |
| Maximum memory | 10 GB | Whatever the underlying EC2/Fargate provides |
| Control over running instance | None | Full (SSH, inspect, modify) |
| Substrate visibility | Hidden | Explicit (substrate spectrum) |
| Custom runtimes | Limited | Anything containerised |
| Stopping a misbehaving function | Hard | Stop the container or instance |
| Confidential compute option | None | Nitro Enclaves available |
| Custom networking | Limited | Full (VPC, custom routes, our DNS) |
| Per-request billing | Yes | Yes (via pre-auth metering) |

The trade-off Lambda makes is "less control, smaller startup tax, fully managed." Our composition makes a different trade: **more control, slightly longer first-call cold-start, broader workload range, and per-substrate optimisation**.

For some workloads Lambda is genuinely the better answer. For many of our use cases (vault apps, agents, AppSec mini-tools, demo environments, CI workloads, multi-region testing) the SG/Compute serverless shape is what we actually want.

## The Cold-Start Question

The voice memo named this as the gating concern: "assuming the cold boot problem, right, and let's say that that's within acceptable formats."

What is acceptable depends on the workload. Reasonable targets:

| Cold-Start Path | Target | How |
|-----------------|--------|-----|
| **EC2 instance from cold, no warm pool** | 30-60s | Standard EC2 boot + container start |
| **EC2 instance from warm pool** | 5-15s | Pre-warmed instances per the container hosts primitive |
| **Fargate task from cold** | 10-30s | Standard Fargate cold-start |
| **Container start on already-running EC2** | 1-5s | Image pull + container start |
| **Fast restart on already-running EC2** | 100-500ms | Image cached locally; just spin a new container |
| **Firecracker snapshot restore (future)** | <50ms | Snapshot-based restore from yesterday's research |

The cold-start improves dramatically as we move down the table. The right substrate for any given workload depends on the latency tolerance.

For most of our planned use cases (agents, mini-apps, CI workloads, demos), **a warm-pool approach combined with the reset-on-activity timeout from earlier briefs gives us 5-15s cold-starts**. For latency-sensitive workloads, **the warm-container-on-existing-EC2 path gives us sub-second**.

This is good enough for the workloads we actually have. Lambda's 100ms cold-start is impressive but irrelevant for most agentic workloads (which run for seconds or minutes anyway).

## The Parallel-Request Problem That Lambda Has

A second Lambda problem worth being explicit about, which the original framing missed: **parallel-request handling on Lambda is genuinely awkward**, and we hit this in practice every time we do an sgit clone.

The pattern: a client kicks off N concurrent requests against the same logical function (say N=20 git fetches as part of a parallel clone). Each request needs its own execution context. Lambda's answer is to **provision N concurrent Lambda instances**, each of which pays the cold-start cost independently if a warm instance isn't available. This means:

- The 21st simultaneous request creates a new cold-start
- Provisioned concurrency (Lambda's "keep N instances warm") gets expensive fast: you pay for the warmth whether traffic exists or not
- Bursty workloads with high parallelism are exactly where Lambda's pricing model becomes painful

Specifically for sgit: when we clone a repo with many objects in parallel, Lambda either:

- Cold-starts on each new parallel request (slow, jagged latency profile)
- Costs significantly more because we keep many functions hot (expensive idle)
- Limits parallelism to avoid the above (slow clones)

None of these are good answers for a workload that genuinely is parallel.

**Containers do not have this problem.** A single container can serve hundreds of parallel requests trivially. The cold-start is paid once per container, not once per request. A request handler that takes 200ms to handle one request handles 50 in parallel at roughly the same speed, bounded by the container's CPU and memory rather than by per-request provisioning.

This means **the agentic-workload sweet spot (many parallel operations from a single agent, often against the same logical service) fits containers much better than Lambda**. Agents fetch many URLs in parallel. Agents make many tool calls. Agents process batches. Lambda penalises all of these; containers handle them naturally.

The implication for SG/Compute Serverless: **the workhorse substrate is a container**, not a function. Cold-start cost is paid once per container; parallel requests are handled by the container's runtime; tear-down happens after idle. This is fundamentally a better fit for agentic work than Lambda's per-invocation provisioning model.

This is also why the Firecracker performance research from yesterday matters specifically here. For very-parallel workloads, container-density-per-host (favoured by Podman, slightly favoured by containers over Firecracker microVMs) means we can host more concurrent work on a given EC2 instance. For workloads with strong isolation requirements (one tenant per microVM), Firecracker's snapshot-restore gets us back to fast spin-up. The substrate choice depends on the parallelism shape and the isolation requirement.

## The "Once Compute Exists, Everything Spins Up" Property

The voice memo named a structural insight: "once you have one compute, we offer the races, right? Once we have that, we can spin up everything else."

This is the bootstrap property. Once a single piece of compute is running (the initial container host or Fargate task), it can spin up everything else: more containers, more EC2 instances, Fargate tasks, Firecracker microVMs, Nitro Enclaves. The first piece is the bootstrap; the rest is orchestrated by that first piece.

The architectural implication: **we do not need a serverless "control plane" running 24/7**. The control plane is one specific role that can spin up itself on demand, do its work, and shut down. The DNS layer is the always-on piece (cheap; effectively free); everything else is on-demand.

This is significantly cheaper than running an always-on Kubernetes-style control plane. And it composes well with our existing pre-auth metering: the user is paying for compute when their requests are being served; we are not subsidising idle infrastructure.

## How The Pieces Compose Into A Serverless Request Path

Walking through a typical serverless invocation flow:

```
1. User sends HTTP request to vault-app-id.sgraph.app (some-vault-app)
   ↓ (DNS resolves to our infrastructure)
2. Edge router checks: is there a running container for this vault app?
   ↓ NO (cold path)
   
3. Edge router triggers SG/Compute orchestrator:
   "Wake up vault-app-id"
   ↓
4. Orchestrator looks up vault-app-id:
   - What substrate does it want? (Fargate / container host / Lambda)
   - What image? (from vault metadata)
   - What environment? (from credential manager: scoped secrets, API keys)
   ↓
5. Orchestrator triggers the right substrate primitive:
   - sg-compute fargate run-task (or)
   - sg-compute container run (or)
   - sg-compute lambda invoke (or)
   - sg-compute firecracker run (future)
   ↓
6. Substrate starts; container/instance boots; vault app loads; signals ready
   ↓ (5-60s depending on substrate and warm-state)
   
7. Edge router routes the request to the running instance
   ↓
8. Vault app processes; returns response
   ↓
9. Edge router caches the running-instance pointer for subsequent requests
   ↓
10. Next request: edge router sees running instance; routes directly (5ms)
   ↓
11. After idle timeout: orchestrator tears down (back to step 1 for next traffic)
```

This is the full path. Each piece exists or is in design. **The integration is the work**; the pieces are not.

## The Product Surface Question

A specific question worth answering: **do we present this as a distinct serverless product surface, or is it implicit in the rest of the platform?**

Arguments for distinct framing:

- Customers understand "serverless." A new platform claiming serverless properties is legible.
- Pricing model maps cleanly: pre-auth pay-per-use is the canonical serverless billing pattern.
- Marketing positioning is clearer. "Run your agents serverlessly on our infrastructure" is easier to sell than "use our compute substrate with these properties."
- The substrate spectrum is internally useful but customer-confusing. A "serverless" product surface abstracts it.
- It opens a developer-platform pitch: "deploy your code; we handle the rest."

Arguments against distinct framing:

- We are not Lambda. Trying to compete head-on is a losing game; better to focus on differentiated capabilities.
- Customers who care about serverless cost shape are already using Lambda; switching has friction.
- The vault model is more distinctive than the serverless model; leading with vaults is stronger.
- We risk overpromising on serverless properties that depend on cold-start tuning we have not yet measured.

The balanced answer: **yes, frame it as serverless, but specifically as a serverless environment for agents, not a generic Lambda alternative**. The pitch is "the right serverless substrate for AI agents that handles their parallelism, isolation per use case, vault-grounded state, and full lifecycle control."

This means:

- We are not competing for the generic developer-platform market (Vercel, Cloudflare Workers, Lambda)
- We are competing for the agent-deployment market (where AgentCore Runtime is the obvious comparison and our differentiation is vault-grounding + customer-controlled substrate + confidential compute option)
- The serverless framing serves our existing direction (vault apps, agents, demos, mini-tools, AppSec mini-tools) rather than chasing developer-platform customers
- The "for agents" framing matches what agents actually need: parallelism, isolation per use case, observability, control

## What This Means For The Roadmap

If we adopt this framing explicitly, several things follow:

1. **The container hosts primitive becomes the workhorse substrate** for serverless workloads. Fargate is the auto-scale alternative for spiky workloads.
2. **The reset-on-activity timeout becomes the default behaviour** for all vault-app and mini-app hosting. No workload runs longer than needed.
3. **Cold-start optimization becomes a real engineering focus**. Pre-warmed pools, image caching, snapshot-based restore (Firecracker future).
4. **The substrate spectrum gets a serverless lane**: workloads that should never persist between requests, always tear down, always pay-per-use.
5. **Pricing presentation simplifies**: usage-based, pre-auth-funded, per-invocation visible to the user.
6. **Documentation needs updating**: the serverless mental model becomes a first-class part of the platform story.
7. **The Firecracker prototyping work (yesterday) becomes more important**: snapshot-restore is the path to sub-second cold-starts in the future.

These are not new initiatives; they are framing changes that affect priorities.

## Where Nitro Enclaves Fit

The voice memo flagged this specifically: "with the Nitro ones, the secure enclave ones, that's also very interesting to run compute at that level."

The natural composition: **serverless compute that runs inside a Nitro Enclave for sensitive workloads**. Same on-demand lifecycle (start on request, run, tear down); same pay-per-use billing; same vault-app or agent shape; with the added property that the compute happens inside an attested enclave whose code is verifiable.

This unlocks a specific customer scenario: **a security scanner that someone can invoke from anywhere, running inside a verified enclave, processing sensitive code without us having access**. The voice memo flagged this: "the idea that you can run this scanner from anywhere, it's super powerful." Right.

The customer's pitch becomes: "Run your security scan against your private repository. The scanner code is open source. The enclave's attestation proves it is the exact code you can inspect. We cannot see your code, even though it ran on our infrastructure." This is genuinely differentiating; few competitors offer it.

The integration cost: design the enclave-aware serverless path (same as the regular serverless path, plus enclave provisioning, attestation, vsock communication). The substrate spectrum gains an "enclave serverless" tier.

## The Bigger Strategic Implication

The composition we are close to making explicit has a name that the industry recognises. **Serverless** is a known category with known cost shape, known developer experience, and known limitations. Positioning SG/Compute's vault-app and agent hosting as serverless lets us speak the industry's language.

But the differentiator is what we add to standard serverless:

| Standard Serverless (Lambda) | SG/Compute Serverless For Agents |
|------------------------------|----------------------------------|
| Per-function deployment | Per-vault-app or per-agent deployment |
| Function source code is the unit | Vault + app is the unit |
| Parallel requests cold-start each slot | Container handles parallel requests naturally |
| Output goes to a database or storage | Output stays in the vault (zero-knowledge) |
| State is in external services | State is in the vault |
| Limited execution time and resource bounds | Substrate-dependent (often unbounded) |
| Vendor-managed runtime | Customer-selectable substrate; full control |
| No confidential compute option | Nitro Enclaves available |
| Custom domains require extra services | DNS + cert built-in |
| Cold-start opaque | Cold-start observable and tunable |
| Isolation per tenant | Isolation per use case |

The combination "serverless cost shape + agent-friendly parallelism + vault-grounded state + customer-controlled substrate + optional confidential compute + isolation per use case" is a genuinely new product surface for agentic workloads. We are not trying to be Lambda; we are using the serverless framing to make our distinctive offering legible to customers who already understand serverless cost shape.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a Lambda competitor for generic developer workloads.** We are not selling a function-as-a-service to web developers running their own code. We are selling an agent-friendly serverless environment with vault grounding, isolation per use case, and optional confidential compute.
- **Not a managed Kubernetes alternative.** Kubernetes is for teams with operational maturity; this is for teams who want compute without the platform-engineering burden.
- **Not promising sub-100ms cold-starts in v1.** Achievable with Firecracker snapshots eventually; not v1.
- **Not removing the option of long-running services.** Some customers want always-on. Both modes coexist.
- **Not introducing a new control-plane technology.** We use the substrates and orchestration we have.

## Honest Risks

Two risks worth being explicit about:

**Risk 1: Cold-start budget creep.** As we add features (vault loading, credential resolution, audit logging, observability tagging), each adds milliseconds to cold-start. Lambda's optimization of cold-starts has been a continuous engineering programme for years. We need to track our cold-start times as a first-class metric and resist features that bloat them.

**Risk 2: Serverless framing overpromises on control properties we have not validated.** Saying "we give you full control of your serverless containers" needs to be true in practice, not just in theory. The CLI primitives that expose container lifecycle need to actually work for customers, not just for our internal team. Documentation and DX matter.

Both risks are mitigated by being honest about cold-start times and explicit about the substrate choices. Customers want truthful framing more than they want maximum-impressive marketing.
