## What This Is

A proposed solution to the operational catch-22 we have today: **we cannot let anyone hitting `anything.sg-labs.app` get a new vault on demand (not scalable, not safe)**, but **we do want to create a controlled set of named labs and have them work via the wildcard-cert + on-demand provisioning machinery we just got working**. The voice memo proposes an admin interface plus a DNS-based registry mechanism using CNAMEs as the signalling layer.

This brief covers two things: **the admin interface as a meaningful new primitive** (a web UI for the on-demand provisioning workflow we have only had on the CLI until now), and **the DNS-as-registry idea**, where I have done the requested research and the answer is **mostly yes, with one important correction to the specific mechanism**. The corrected version still gives you exactly what you want operationally, but uses a slightly different DNS record arrangement than the voice memo described.

The correction matters because it determines whether the solution actually works. The good news is the core idea is sound and the fix is small.

## The Admin Interface

This is overdue and worth doing properly. We have been building the on-demand provisioning workflow via CLI commands like `sg-compute provision`, DNS update commands, etc. The voice memo names the right next step: **a web UI that wraps those CLI capabilities**.

Concrete capabilities the admin UI needs:

| Capability | What It Does |
|------------|--------------|
| **List labs** | Show all registered labs with status (live, provisioning, idle, torn down) |
| **Create lab** | Register a new lab: choose name, choose template/AMI, set TTL, optionally set scheduled teardown |
| **Inspect lab** | Drill into one lab: see its instance, vault, DNS state, cost, recent activity |
| **Wake / sleep** | Manually trigger provisioning or teardown of an existing registration |
| **Cost view** | Per-lab cost and aggregate cost; flows into the pre-auth metering substrate |
| **Schedule / TTL** | Set lifetime policy: max session length, idle timeout, scheduled scheduled-shutdown |
| **Activity log** | Recent events for each lab; vault commits, instance starts, errors |
| **Access control** | Which users or tokens can create which lab classes |

This is the on-demand provisioning workflow turned into a web UI. It uses the JS API surface from the vault testing brief earlier today. It runs as a vault app (the SG/App pattern). Probably called `sg-labs-admin` or similar. The admin vault is itself a manager vault: it holds the registry of labs, their state, their policies.

This composes with everything else from the week. It is mostly UI work over existing CLI primitives, not new infrastructure.

The first concrete v1: **a UI that lets the project lead manage 5-20 named labs** (`demo-cv-1`, `accountant-john`, `medical-acme`, etc.), each backed by either a permanent registration entry or a wildcard-fallback ephemeral. This is the operational reality the voice memo describes.

## The DNS-As-Registry Idea (And The Important Correction)

The voice memo proposes: use CNAME records as the registry of valid labs. When a request comes in:

- If the slug has a CNAME registered, the request is for a valid lab; spin up the instance if needed
- If the slug has no CNAME, the request is for an unregistered name; serve a clear "not found" response

**My assumption check**: does a CNAME pointing to a wildcard actually do what the voice memo expects? I have done the research, and the answer needs a correction.

### What The Voice Memo Got Right

The intuition is correct: **DNS records at a name can be used as a registry signal**. The presence or absence of a record at `john-cv.sg-labs.app` can be the answer to "is this a valid lab?". This is a real and useful pattern.

The intuition that **a Lambda function at the wildcard can detect whether the request was for a registered or unregistered name** is also right, with one nuance: the Lambda detects this from the request itself (the Host header), not from how DNS resolved it. The Lambda sees `john-cv.sg-labs.app` in the request and can look up "is john-cv registered?" in the admin vault.

### Where The Correction Is Needed

The specific mechanism ("CNAME at the slug points to the wildcard") does not work as described. The DNS spec (RFC 4592) has two relevant constraints:

**Constraint 1: A wildcard does not match a name once a concrete record exists at that name.**

> "Wildcard synthesis applies only when the name does not exist. The concrete record prevents wildcard matching."

If you create `john-cv.sg-labs.app CNAME *.sg-labs.app`, then a query for `john-cv.sg-labs.app` will resolve via the CNAME (which itself resolves), not via wildcard expansion of the asterisk. The wildcard only matches names that have no record at all.

**Constraint 2: CNAMEs to wildcards have undefined or implementation-specific behaviour.**

Multiple authoritative sources (UltraDNS, Microsoft Azure DNS docs, RFC 4592 itself) flag that wildcards and CNAMEs interact in ways that **are not consistent across DNS implementations**. Some resolvers do follow the CNAME and then attempt wildcard synthesis on the target; others do not. Some name servers refuse to even let you configure it.

**The combination means: do not rely on CNAME-to-wildcard as a load-bearing mechanism**. It might work in some configurations and break in others, and the failure modes are subtle.

### The Fix That Actually Works

The good news: **the core idea still works, with a small change to the DNS arrangement**. Instead of CNAMEs as the registry, use **any concrete DNS record at the slug**. The choice that works most cleanly is **an A record at the slug pointing to the same IP as the wildcard**.

```
*.sg-labs.app            A      198.51.100.10    (the Lambda's IP / ALB)
john-cv.sg-labs.app      A      198.51.100.10    (same IP; registered slug)
demo-acct.sg-labs.app    A      198.51.100.10    (same IP; registered slug)
random-xyz.sg-labs.app   (no record)              (unregistered; falls through to wildcard)
```

What happens at request time:

| Request | DNS Resolution | What The Lambda Sees |
|---------|----------------|----------------------|
| `john-cv.sg-labs.app` | A record exists; resolves to Lambda IP | Host header `john-cv.sg-labs.app`; Lambda looks up in registry; finds it; provisions/serves |
| `random-xyz.sg-labs.app` | No record; wildcard matches; resolves to Lambda IP | Host header `random-xyz.sg-labs.app`; Lambda looks up in registry; not found; serves "no such lab" |

**Both paths land at the Lambda**, but the Lambda can distinguish via the admin-vault registry (not via the DNS resolution path). The DNS records exist primarily to give DNSSEC-friendly behaviour and to enable future moves (e.g., once a lab's EC2 instance is up, the A record can be changed to point at the instance instead of the Lambda).

The registry-as-DNS-records intuition the voice memo described **survives**, just with A records instead of CNAMEs. The semantic role is the same: presence of a concrete record = registered lab.

### Why This Is Actually Better

The correction turns out to deliver something cleaner than the original:

1. **No CNAME-to-wildcard interactions** to worry about across resolver implementations
2. **DNSSEC works correctly** (CNAMEs to wildcards complicate DNSSEC; A records do not)
3. **TLS certs work cleanly** with the wildcard cert covering everything
4. **The transition from "Lambda is serving" to "real instance is serving"** is just changing the A record to point at the instance, same record type, just different IP
5. **The registry can be the admin vault**, not the DNS zone, meaning we change a vault entry to register/deregister a lab, and the DNS records are derived from the registry, not the source of truth

The last point is significant. **The admin vault is the registry**; DNS records are a projection of it. When you add a lab via the admin UI, the admin vault commits the addition; a process syncs that to DNS (creates the A record); the lab is now resolvable.

## The Three States Of A Registered Lab

With the corrected scheme, a lab can be in one of three states:

| State | DNS Record | Lambda Behaviour | Cost |
|-------|------------|------------------|------|
| **Registered but cold** | A → Lambda IP | Provisioning UI; offers to create instance | Effectively zero |
| **Provisioning** | A → Lambda IP | Provisioning UI with progress; polls readiness | Compute cost during the 50s window |
| **Live** | A → instance IP | Bypass Lambda; user reaches instance directly | EC2 cost while running |

State transitions are clean:

- Cold → Provisioning: user requests via UI; provisioning starts; DNS unchanged
- Provisioning → Live: instance comes up; DNS record updated to point at instance IP; user redirected
- Live → Cold: instance is torn down (idle timeout, explicit teardown, scheduled shutdown); DNS record reverted to Lambda IP

The admin UI shows current state for each lab; admin can force transitions; the user-visible UX is the same flow we already have.

## Unregistered Slugs: What The Lambda Returns

The voice memo proposed: when an unregistered slug is hit, serve a clear "no such lab" response rather than auto-provisioning.

This is the right answer for the lab-as-controlled-resource model. Options for the response:

| Response | When To Use |
|----------|-------------|
| **404 "No such lab"** | The strictest; lab-management is explicit; unregistered = doesn't exist |
| **Branded "this lab is not configured; would you like to create one?"** | Friendly; offers signup path; appropriate for trial-style flows |
| **Redirect to a list-of-labs page** | If the visitor seems lost; useful for exploration |
| **Lookup in a public-labs directory** | For "public-visible" categories of labs |

For v1, **404 with a branded landing page** is right. Strict enough to prevent accidental provisioning; friendly enough to not feel like a bug.

## Addendum: Could We Use TXT Records Instead Of A Records?

A follow-up question worth addressing: **could TXT records be used as the registry mechanism, instead of (or alongside) A records?** The short answer is that TXT records have a legitimate role in this scheme, but not as a replacement for A records. The detail matters because it determines what gets stored where.

### What TXT Records Do To Wildcards

The DNS spec rule from RFC 4592 is consistent: **the wildcard does not match a name if any record exists at that name, regardless of record type**. A TXT record at a name has exactly the same wildcard-blocking effect as an A record at that name.

The Microsoft Azure DNS case from earlier in this brief is the canonical example: a wildcard CNAME at `*.example.com` is broken for `api.example.com` because a `dummy.api.example.com TXT` record exists. The TXT record creates an empty non-terminal at `api.example.com`, which makes the name "exist," which means the wildcard no longer applies.

So in principle, you could signal "this name is registered" by putting a TXT record at the slug. The wildcard would no longer cover it; the Lambda would need to read the registry to decide what to do.

### Why TXT Alone Does Not Work

The trap: **a TXT-only registration leaves the name resolvable as NOERROR/NODATA rather than reaching your Lambda**. If you have:

```
*.sg-labs.app                A      198.51.100.10    (wildcard)
john-cv.sg-labs.app          TXT    "registered=true"
                             (no A record)
```

A client asking for `john-cv.sg-labs.app`'s A record gets:

- The name exists (TXT is there); wildcard does not apply
- No A record exists at this name
- Response: NOERROR with an empty answer section

The browser shows "this site can't be reached." The user never reaches your Lambda. **TXT alone breaks the user experience for registered slugs**, which is exactly the opposite of what you want.

You always need a record that resolves to an IP. For our scheme, that means an A record (or AAAA for IPv6, or an ALIAS for AWS endpoints).

### Where TXT Records Are Genuinely Useful

TXT records have a real role alongside A records, for carrying small amounts of public metadata that benefits from DNS-level distribution. Specifically:

| Purpose | TXT record value example |
|---------|---------------------------|
| Vault's public key for cryptographic addressing (from yesterday's discovery brief) | `"sg-pubkey=ed25519:Mxe7..."` |
| Domain-ownership verification for third-party services | `"sg-verify=abc123def456"` |
| Public lab metadata for discovery | `"type=demo;industry=accounting;public=true"` |
| Cache-busting / freshness hint | `"changed=1747345200"` |
| Version hint | `"version=v0.27.45;updated=2026-05-16"` |

**The vault public key case is the most interesting.** Yesterday's vault discovery brief proposed `/.well-known/vaults` as an HTTP-based discovery endpoint. TXT records give us a DNS-based alternative that does not require an HTTP roundtrip and works for tools that have not yet decided whether they trust the server's HTTP infrastructure.

This is exactly the DKIM pattern: email signing public keys are published as TXT records, so verifiers can fetch the key over DNS without trusting the sender's web infrastructure. The same approach works for vault public keys.

### The Recommended Arrangement

Combining everything from this brief plus the addendum, the recommended DNS arrangement for a registered lab is:

```
*.sg-labs.app                A      198.51.100.10                 (wildcard catch-all)
john-cv.sg-labs.app          A      198.51.100.10                 (route to Lambda; changes to instance IP when live)
john-cv.sg-labs.app          TXT    "sg-pubkey=ed25519:Mxe...;ver=v0.27.45"  (optional; public metadata)
```

Each record type does what it is best at:

| Concern | Mechanism |
|---------|-----------|
| Does this name reach our service? | A record |
| Which labs are registered, with what metadata? | Admin vault |
| Public metadata that benefits from DNS-level distribution | TXT record (optional) |
| Cryptographic addressing (public key per vault) | TXT record (DKIM pattern) |
| Domain-ownership proofs for third-party services | TXT record |

The admin vault remains the registry of truth. A records route traffic. TXT records carry public metadata that other systems benefit from being able to fetch via DNS rather than HTTP.

### The Trap To Avoid

The single trap worth being explicit about: **do not use TXT records as the only mechanism to signal "this is a registered lab"**. The wildcard-blocking behaviour means a TXT-only registration leaves the name as NOERROR/NODATA rather than reaching the Lambda. Always pair a TXT record at a registered slug with an A record.

The DNS spec rule is consistent: a name exists when it has any record. But "exists" and "is reachable as a web service" are different things. A records (or equivalent IP-providing records) deliver the second; TXT records deliver structured metadata around it.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not customer-facing lab self-service in v1.** Project lead manages the registry; customers do not yet add their own labs.
- **Not multi-region.** Single Route 53 zone; single region; multi-region is a v2 expansion.
- **Not lab templates beyond what we have.** Each lab uses an existing AMI/configuration; lab templates as a separate concept comes later.
- **Not collaboration between labs.** Each lab is its own instance/vault; cross-lab features are separate work.
- **Not automatic lab scaling.** One lab = one instance; horizontal scaling is a future expansion.

## Honest Risks

Three risks worth flagging:

**Risk 1: DNS provider quirks break the scheme.** Not all DNS providers handle wildcards consistently with explicit records. Mitigation: test thoroughly on Route 53 (our chosen provider); document fall-back behaviour; consider explicit A records for every registered slug to avoid wildcard interactions entirely.

**Risk 2: The admin vault becomes a bottleneck.** As labs grow, lookups against the vault need to be fast. Mitigation: cache the registry in the Lambda's memory with a short TTL; refresh on each cold start; reload on demand if the vault changes.

**Risk 3: State drift between admin vault and DNS.** If the sync process fails, the admin vault says "lab X is registered" but DNS does not have the record. Mitigation: reconciliation job runs hourly; alerts on drift; treat the vault as source of truth and re-sync DNS to match.
