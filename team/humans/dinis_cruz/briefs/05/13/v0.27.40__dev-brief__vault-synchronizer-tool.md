## What This Is

A tool we have needed for a while, made urgent by today's DNS-and-cert milestone. Now that we can spin up SG/Compute instances with proper DNS names, the natural next question becomes: **how do we manage the vaults that flow between these instances?**

The Vault Synchronizer is a CLI-first tool that:

- Synchronises vaults between locations (canonical API, ephemeral EC2 instances, local clones, partner deployments)
- Visualises the graph of vault locations and their relationships
- Surfaces health: which vaults are out of sync, which are at which commit, which need attention
- Provides hooks for events (GitHub webhook, schedule, manual trigger)
- Deploys ephemeral EC2 instances with a specific vault preinstalled

This is also an opportunity to **practice ephemeral provisioning more deliberately**. The tool itself runs on SG/Compute, on an EC2 instance, spun up on demand. The tool's existence forces us to get better at fast boot, ephemeral lifecycle, and on-demand resource shape.

## Why CLI-First

Two reasons.

**Robustness.** A CLI does not have to deal with browser quirks, session expiry, CORS, or HTTPS handshakes for cross-origin calls. It runs in a known environment. When something goes wrong, the failure is in one well-understood layer.

**Composability.** Vault synchronisation needs to be triggered from many places: webhooks, schedulers, agent workflows, human terminals, deployment pipelines. A CLI plugs into every one of these. A web UI plugs into none of them well.

The CLI is the first-class interface. A UI can sit on top of it later for the visualisation and exploration use cases. The underlying capability is CLI.

## What Good Looks Like

Two end-to-end scenarios define success:

### Scenario 1: Claude push to live instance

```
1. I am in Claude
2. I push a change to a vault
3. That triggers a sequence of events
4. Eventually, an EC2 instance has that same vault, current
5. The DNS name for the instance serves the updated vault
```

The trigger could be a GitHub webhook (if the canonical vault is GitHub-projected per the 11 May brief), a direct call, or a scheduled poll. The result is the same: the EC2 instance picks up the change.

### Scenario 2: Deploy this vault to a fresh instance

```
1. I have a vault
2. I issue one command: "deploy this vault to a new EC2 instance"
3. The synchronizer:
   - Spins up an EC2 instance via SG/Compute
   - Provisions DNS and cert
   - Installs the vault on the new instance
   - Returns the URL
4. Visit the URL, see the vault rendered
```

This is the second scenario the voice memo described as "what good looks like." A one-command path from "I have a vault" to "I have a live, certed, properly-named instance hosting it."

## The Command Surface

Following the agent-specific CLI architecture (this morning's earlier brief), the synchronizer is structured by function:

```
vault-sync
    ├── push        (push a vault to a remote)
    │     ├── to <target>
    │     └── all                     (push to all known targets)
    ├── pull        (pull a vault from a remote)
    │     └── from <source>
    ├── sync        (bidirectional align)
    │     ├── pair <a> <b>
    │     └── all                     (align all known vault locations)
    ├── deploy      (spin up an instance preloaded with a vault)
    │     ├── ephemeral <vault-id>
    │     └── persistent <vault-id> --domain <name>
    ├── status      (health, commits, drift)
    │     ├── vault <vault-id>
    │     ├── instance <instance-id>
    │     └── graph                   (cross-vault relationships)
    ├── hooks       (event-driven triggers)
    │     ├── register
    │     ├── list
    │     └── test
    └── meta
          ├── version
          └── targets                 (list known sync targets)
```

Each command is JSON in, JSON out, debuggable, scriptable. The structure mirrors the agent CLIs from earlier today: predictable surface, function-categorised, well-documented.

## The Visualisation Surface

Once the underlying CLI works, a visualisation layer becomes valuable. What you want to see:

| View | What It Shows |
|------|---------------|
| **Vault graph** | Every vault we manage; their canonical location, their derivative locations |
| **Sync edges** | Which vaults sync to which; direction of sync; last sync time |
| **Drift indicators** | Where the source is ahead of a destination; how many commits behind |
| **Instance health** | Which EC2 instances are live, which vaults they hold, their DNS status |
| **Hook activity** | Recent events, what they triggered, results |

This is the dashboard for the vault fleet. It runs on SG/Compute itself (eat our own dog food); the dashboard's data layer is the same CLI we use from the terminal.

The visualisation is **read-only** at first. Actions are taken through the CLI; the dashboard observes. Later, the dashboard can offer one-click actions that call the CLI underneath.

## Hooks

The hooks system is what makes the synchronizer useful for unattended operation:

| Hook Type | What Triggers It | What It Does |
|-----------|-----------------|-------------|
| **GitHub webhook** | A push to a vault's GitHub projection | Pull the change, push to mapped EC2 instances |
| **Schedule** | Cron-like timing | Periodic sync, periodic health checks |
| **Manual** | CLI invocation | Direct action, useful for orchestration scripts |
| **API call** | HTTP POST to a defined endpoint | Programmatic triggering from other tools |
| **Agent invocation** | One agent CLI calling the synchronizer CLI | Composable with the agentic workflows |

Each hook is registered via `vault-sync hooks register`. The registration includes the triggering condition, the action to take, the targets affected. The list is queryable via `vault-sync hooks list`.

## Why The Tool Runs on EC2

Two reasons.

**It can talk to all the vaults.** A tool running on EC2 in our VPC can reach the canonical SG/Send API, our other ephemeral EC2 instances, and (with appropriate network setup) partner instances. A tool running on someone's laptop cannot reach the EC2 instances reliably; a tool running in Lambda is constrained on duration and connectivity.

**It exercises ephemeral provisioning.** Every time the synchronizer runs, we are spinning up an instance, doing work, possibly tearing down. This is the practice we want to get better at. The tool itself is the exercise.

Eventually the synchronizer might run as a long-lived service. For now, ephemeral on-demand is fine and instructive.

## The Vault Graph Concept

The "vault graph" mentioned in the voice memo deserves its own paragraph. As the platform grows, we will have many vaults in many places:

- Canonical vaults on the SG/Send API
- Local clones on developer machines
- Ephemeral copies on demo EC2 instances
- Persistent partner deployments
- Static projections on GitHub Pages, S3, Cloudflare Pages
- Read-only published copies on `*.sgraph.app`

Each vault may exist in multiple of these forms simultaneously. They may be at different commits. They may have diverged. They may need bidirectional sync.

A graph view of this lets us reason about the fleet. Nodes are vault locations; edges are sync relationships. The graph view exposes:

- Where the canonical "truth" is for each vault
- Which derivatives need updating
- Where drift exists
- Where loops might be forming (vault A syncs to B which syncs to A)
- Which vaults are orphaned (nobody is updating them)

This is the same idea as Git's branch and remote model, applied at the vault-fleet level. Familiar shape, new domain.

## What This Replaces

Some current pain points this addresses directly:

| Current Pain | How The Synchronizer Solves It |
|--------------|-------------------------------|
| Manually changing remotes and pushing | One command sync |
| Forgetting which instance has which vault | The status command shows it |
| Spinning up demo instances by hand | `deploy ephemeral` does it |
| Webhook plumbing for vault updates | Hooks are first-class |
| "Is this vault current?" being hard to answer | Status drift indicators answer it |

## Phasing

The tool is meaningful in pieces. Phase order:

| Phase | Capability | Why First |
|-------|-----------|----------|
| Phase 1 | `vault-sync push/pull` between local, canonical, and one EC2 instance | The minimum that improves on manual remote-changing |
| Phase 2 | `vault-sync deploy ephemeral` for one-command instance creation | Highest demo value |
| Phase 3 | `vault-sync status graph` with basic visualisation | Operational visibility |
| Phase 4 | Hooks system (GitHub webhook first) | Unattended operation |
| Phase 5 | Multi-instance, multi-vault fleet management | Scale |

Phase 1 ships in days. Phases 2-3 ship in a week or two. Phases 4-5 mature over the following weeks.
