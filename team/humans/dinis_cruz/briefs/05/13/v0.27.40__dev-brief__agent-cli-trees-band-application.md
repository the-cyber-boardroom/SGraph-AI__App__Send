## What This Is

The applied counterpart to the agent-specific CLI architecture brief. That brief gave the structure: each agent gets its own folder, its own CLI tree with publish/consume/internal/meta function categories, its own prompts and schemas. This brief works through what that means concretely for the 13 roles in the band production team.

This is also the worked example that any subsequent team (newsroom, content workflows, medical workflows) can use as a template. Replace the role names; the structure stays the same.

## The Band Team CLIs at a Glance

Each role in the band production team becomes a CLI with its own command tree:

```
sg-agents
    ├── artistic-director
    ├── composer
    ├── writer
    ├── producer
    ├── musician
    ├── visual-director
    ├── visual-artist
    ├── video-artist
    ├── critic
    ├── editor
    ├── archivist
    ├── accountant
    └── publisher
```

Each of these is a full CLI tree, not a single command. The detail follows.

## Artistic Director

Sets the creative direction for each song. Picks the source piece and the target style.

```
agent-artistic-director
    ├── publish/
    │     ├── brief        (produce a brief for a new song)
    │     └── rationale    (explain why this brief, this week)
    ├── consume/
    │     └── ideas        (pull ideas from the inspiration inbox: news, requests, themes)
    ├── internal/
    │     ├── set-pool     (configure the source-piece pool)
    │     └── set-styles   (configure the target style range)
    └── meta/
          ├── status       (current direction, recent choices)
          └── cost-estimate
```

Example invocation:

```
agent-artistic-director publish brief \
    --pool /vault/sources/classical-pool.json \
    --style-rotation /vault/styles/rotation.json \
    --output /vault/songs/{id}/brief.json
```

## Composer

Takes a brief and proposes the arrangement: which themes survive, which are transformed, where the breakdowns and climaxes land.

```
agent-composer
    ├── publish/
    │     ├── arrangement     (full arrangement from a brief)
    │     ├── variant         (alternate arrangement for the same brief)
    │     └── analysis        (analysis of the source piece)
    ├── consume/
    │     └── brief           (read a brief from the queue)
    ├── internal/
    │     ├── review-prompt   (inspect the prompt that will be used)
    │     └── set-rules       (configure compositional rules)
    └── meta/
          ├── status
          └── cost-estimate --input brief.json
```

The cost-estimate sub-command is critical: it tells the orchestrator what the next step will cost before the orchestrator commits to it.

## Writer

If the song has lyrics, vocal lines, or a title and concept blurb, the writer produces them.

```
agent-writer
    ├── publish/
    │     ├── title           (song title for a composition)
    │     ├── concept         (the one-paragraph "what this song is")
    │     ├── lyrics          (full lyrics if vocal)
    │     └── liner-notes     (the album-page text)
    ├── consume/
    │     ├── composition     (read a composition to write for)
    │     └── style-guide     (read the writing style configuration)
    └── meta/
          ├── status
          └── cost-estimate
```

## Producer

Translates a composition into prompts for the music generation model.

```
agent-producer
    ├── publish/
    │     ├── prompts         (Suno-or-equivalent prompt set)
    │     ├── parameters      (model parameters: temperature, duration, structure tags)
    │     └── alternates      (alternate prompt variants for diversity)
    ├── consume/
    │     └── composition     (read the composition to translate)
    ├── internal/
    │     └── tune            (adjust prompt patterns based on past results)
    └── meta/
          ├── status
          └── cost-estimate
```

## Musician

The actual audio generation. Calls Suno (or Udio, or current best-in-class) and produces candidate tracks.

```
agent-musician
    ├── publish/
    │     ├── candidates      (N generated audio tracks)
    │     └── metadata        (parameters used per generation)
    ├── consume/
    │     └── prompts         (the prompts to run)
    ├── internal/
    │     ├── set-model       (which music model to use)
    │     └── set-quality     (quality tier configuration)
    └── meta/
          ├── status
          ├── credits-remaining  (how much Suno/Udio budget is left)
          └── cost-estimate --input prompts.json
```

This is where significant external API spend happens. The meta cost-estimate is especially important here; budget enforcement happens at the orchestrator using these estimates.

## Visual Director

Conceives the visual treatment: cover art direction, atmosphere, video direction if applicable.

```
agent-visual-director
    ├── publish/
    │     ├── art-brief       (cover-art direction)
    │     ├── video-brief     (clip or full video direction)
    │     └── palette         (colour and texture palette)
    ├── consume/
    │     ├── song-package    (read the song's brief, composition, concept)
    │     └── theme           (current visual theme of the band)
    └── meta/
          ├── status
          └── cost-estimate
```

## Visual Artist

Generates the actual images via GPT-Image-2, Midjourney, or current best-in-class.

```
agent-visual-artist
    ├── publish/
    │     ├── images          (generated images, with parameters)
    │     └── variants        (alternates for selection)
    ├── consume/
    │     └── art-brief       (read the art brief)
    ├── internal/
    │     └── set-model       (which image model)
    └── meta/
          ├── status
          ├── credits-remaining
          └── cost-estimate
```

## Video Artist

Generates clips or full music videos when applicable. Same shape as visual artist; different model.

```
agent-video-artist
    ├── publish/
    │     ├── clips
    │     └── full-video
    ├── consume/
    │     └── video-brief
    ├── internal/
    │     └── set-model
    └── meta/
          ├── status
          └── cost-estimate
```

## Critic

Reviews generated outputs and provides feedback. The strongest signal for "should we iterate or accept."

```
agent-critic
    ├── publish/
    │     ├── reviews         (per-candidate scores and notes)
    │     └── recommendations (which to keep, which to iterate, which to discard)
    ├── consume/
    │     ├── candidates      (audio, image, or video candidates to review)
    │     └── criteria        (review criteria for this kind of work)
    ├── internal/
    │     ├── set-strictness  (calibrate how harsh the reviews are)
    │     └── calibrate       (review against known-good examples)
    └── meta/
          ├── status
          └── cost-estimate
```

## Editor

Final sign-off on what gets published. Different from the Critic: the Editor decides whether to publish, the Critic decides what is good or bad.

```
agent-editor
    ├── publish/
    │     ├── decision        (publish, iterate-more, or abandon)
    │     └── notes           (reasoning and required follow-ups)
    ├── consume/
    │     ├── package         (the candidate plus reviews)
    │     └── policy          (publication policy: minimum quality, brand guidelines)
    ├── internal/
    │     └── set-policy
    └── meta/
          ├── status
          └── cost-estimate
```

## Archivist

Captures everything into the vault. Mostly programmatic; less LLM-driven than others.

```
agent-archivist
    ├── publish/
    │     ├── record          (full production record for the vault)
    │     └── timeline        (chronological summary)
    ├── consume/
    │     └── workflow-state  (the running workflow's current state)
    └── meta/
          └── status
```

## Accountant

Tracks the budget and reports actual spend per workflow. Mostly programmatic.

```
agent-accountant
    ├── publish/
    │     ├── budget-status   (where we are vs budget for this workflow)
    │     ├── daily-report
    │     └── alerts          (budget warnings)
    ├── consume/
    │     ├── spend-events    (incoming cost records from other agents)
    │     └── policy          (per-workflow and per-day caps)
    ├── internal/
    │     └── set-policy
    └── meta/
          └── status
```

The Accountant is one of the simplest agents but one of the most important. Without it, budget controls do not exist.

## Publisher

Pushes the approved output to the live band site and the vault publishing layer.

```
agent-publisher
    ├── publish/
    │     ├── go              (publish a song to the live site)
    │     └── schedule        (queue for a specific publish time)
    ├── consume/
    │     └── editor-decision (read the approval)
    ├── internal/
    │     └── set-destination
    └── meta/
          └── status
```

## The Orchestrator Script

These CLIs are composed by an orchestration script. The previous brief showed the basic pattern; with the per-agent CLI trees, it becomes:

```bash
SONG_ID=$(uuid)

agent-artistic-director publish brief \
    --output /vault/songs/$SONG_ID/brief.json

agent-composer publish arrangement \
    --input /vault/songs/$SONG_ID/brief.json \
    --output /vault/songs/$SONG_ID/composition.json

agent-writer publish title --input /vault/songs/$SONG_ID/composition.json --output /vault/songs/$SONG_ID/title.json &
agent-writer publish concept --input /vault/songs/$SONG_ID/composition.json --output /vault/songs/$SONG_ID/concept.json &
wait

agent-producer publish prompts \
    --input /vault/songs/$SONG_ID/composition.json \
    --output /vault/songs/$SONG_ID/prompts.json

# Cost check before expensive operations
ESTIMATE=$(agent-musician meta cost-estimate --input /vault/songs/$SONG_ID/prompts.json)
agent-accountant consume spend-events --estimate "$ESTIMATE"

agent-musician publish candidates \
    --input /vault/songs/$SONG_ID/prompts.json \
    --output /vault/songs/$SONG_ID/candidates.json \
    --budget 2.50

agent-critic publish reviews \
    --input /vault/songs/$SONG_ID/candidates.json \
    --output /vault/songs/$SONG_ID/reviews.json

# Iteration loop if reviews are insufficient
# (omitted for brevity; mechanically straightforward)

agent-editor publish decision \
    --input /vault/songs/$SONG_ID/candidates.json \
    --reviews /vault/songs/$SONG_ID/reviews.json \
    --output /vault/songs/$SONG_ID/decision.json

# Visual treatment in parallel with the audio iteration
agent-visual-director publish art-brief --song-package /vault/songs/$SONG_ID/ --output /vault/songs/$SONG_ID/art-brief.json
agent-visual-artist publish images --input /vault/songs/$SONG_ID/art-brief.json --output /vault/songs/$SONG_ID/images.json --budget 1.00

agent-archivist publish record --workflow-state /vault/songs/$SONG_ID/ --output /vault/songs/$SONG_ID/record.json

DECISION=$(jq -r '.action' /vault/songs/$SONG_ID/decision.json)
if [ "$DECISION" = "publish" ]; then
    agent-publisher publish go --song-id $SONG_ID
fi

agent-accountant publish daily-report --output /vault/reports/$(date +%Y-%m-%d)-cost.json
```

This is the daily run, expressed as plain shell. Each step is independently debuggable. Each cost is tracked. Each output is auditable. The vault carries the whole history.

## What Gets Tested First

The full team is 13 agents. Implementing all of them at once is unwise. Suggested phasing:

| Phase | Agents Implemented | Goal |
|-------|-------------------|------|
| Phase 1 | Composer, Producer, Musician, Critic | The minimal audio pipeline |
| Phase 2 | + Artistic Director, Writer, Editor | The brief-to-publish core flow |
| Phase 3 | + Visual Director, Visual Artist | Visual treatment |
| Phase 4 | + Archivist, Accountant, Publisher | The operational layer |
| Phase 5 | + Video Artist | The optional cherry-on-top |

Phase 1 produces music. Phase 2 produces publishable songs. Phases 3-5 polish.
