# Milestone: Ephemeral Vault App Instances on SG/Compute with TLS

## What Was Achieved

A clean, deployable SG/Compute spec that spins up an EC2 instance containing the full Vault App (SG API + Vault UI + SG/App rendering) on a public IP, with a valid TLS certificate provisioned during boot, and with the Playwright sidecar attached for browser-based work. From a single command, an ephemeral, fully-functional, properly-certified vault server is running and reachable.

This sounds simpler than it was, and that is part of the point: the complexity is now hidden inside the spec, not exposed to the user.

## Why This Is a Major Milestone

For the first time, all of the core technologies work together in a single ephemeral deployment:

| Capability | Status |
|------------|--------|
| EC2 instance provisioning via SG/Compute | Working |
| Vault API service (SG API powering SGit) | Working in the instance |
| Vault UI (load vaults, create vaults, render apps) | Working in the instance |
| Public IP and DNS assignment at boot | Working |
| TLS certificate provisioned during boot | Working |
| Web Crypto API (which requires HTTPS) | Now functional |
| Playwright sidecar | Attached and working |
| SGit pushes from elsewhere into this instance | Working |
| App Mode rendering of pushed vaults | Working |

The combination is what matters. Each piece existed before; getting them all in one ephemeral boot was the unblock.

## The Web Crypto / TLS Discovery

The certificate provisioning was the harder-than-expected piece. The Vault UI loaded fine over plain HTTP, but creating or opening vaults failed silently because the browser's Web Crypto API refuses to operate in non-secure contexts. Correctly so, on the browser's part; mysterious, until you spot it.

The solution involves an ACME-based sidecar (Let's Encrypt) provisioning a cert during the boot sequence. Once that lands, the cert is in place, the browser trusts the origin, Web Crypto operates, and the full vault experience works.

The architectural lesson worth recording: **any client-side encryption product depends on TLS not as a transport security layer but as a feature-enablement gate.** Without the cert, Web Crypto refuses to run, and the entire premise of client-side encryption breaks. This is the right behaviour from browsers, but it means TLS provisioning is non-optional in our deployment automation. Every SG/Compute spec that runs vault-side code in a browser must have a valid cert from the moment it serves its first request.

## What This Unblocks

The ephemeral instance is now a real platform surface. Several things become possible immediately:

### A Disposable Working Surface

Anyone can spin up a fresh vault server, push vaults into it, work in them, then destroy the instance. Useful for:

- Demos that need a clean state every time
- Throw-away development sandboxes
- One-time client engagements where the infrastructure should not persist
- Testing new vault features against a fresh substrate

### A Pre-baked AMI Path

The current setup boots and configures from scratch. The next step is to bake an AMI with most of the setup pre-applied, so boot time drops from minutes to under a minute. The cert still has to be provisioned per instance (since the IP and domain are per-instance), but everything else can be in the image.

### Demos That Look Real

The website, the partner POCs, the marketing surfaces previously demoed by walking someone through a local environment or our own infrastructure. Now we can spin up an isolated instance, demo a real vault rendered on a real domain with a real cert, and tear it down. The demo and the production are the same code path.

### The Whole-Stack Test

This is the smallest, most complete reproduction of our platform: API, UI, vault format, app rendering, certificates, automation, browser tooling. If something breaks in the ephemeral instance, it would break in production. The instance becomes a continuous integration target for the whole stack.

## What Comes Next

Two immediate directions:

**Bake the AMI.** Most of what the boot script does today is repeatable. Bake the configured base into an AMI; only the per-instance steps (IP assignment, cert provisioning, vault data sync) happen at boot. Time to ready should drop below 60 seconds. This is the next AMI work for the package manager / image builder workflow.

**Build demo content on top of it.** Now that we have the substrate, fill it with examples. The first one is the music band demo (companion brief). More follow: the friend's CV site, the medical partner POC re-deployed on ephemeral, sgraph.ai itself running on this substrate.
