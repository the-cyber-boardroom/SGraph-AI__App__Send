## The Core Idea

Every agent operation should be a CLI command. Not "the agent has access to CLI tools" but "**invoking an agent is invoking a CLI command**". Each command takes structured input (JSON), produces structured output (JSON), and is independently testable, debuggable, and runnable.

The agentic team is then nothing more than a set of CLI commands strung together. Same as Unix philosophy: small composable tools, structured pipes between them, each tool does one thing well.

This brief generalises the pattern beyond the immediate use case (the band production team). The same architecture should govern the newsroom agents, the content agents on sgraph.ai, the medical partner workflow agents, the investor pack engagement workflows, and every future agentic team we build.

## Why CLI-First

| Reason | Why It Matters |
|--------|---------------|
| **Debuggability** | When something goes wrong, you can re-run a single step with the same inputs and see what it produced. Black-box agent flows are hard to debug; CLI steps are not. |
| **Composition** | CLI commands chain. The output of one command is the input to the next. New workflows are new orchestrations of existing commands. |
| **Substitutability** | Any step can be replaced (a different model, a human, a faster heuristic) without touching the rest of the workflow. The CLI contract is the boundary. |
| **Testability** | Every command has a stable input/output schema. Tests are JSON in, JSON out. Regression is detectable. |
| **Productisation** | A workflow written as CLI commands can be sold, packaged, distributed. The same commands run on the partner's infrastructure or ours. |
| **Human-agent interop** | Any step that an agent can do, a human can do (and vice versa) because the contract is the same. The team flexes between fully agentic, fully human, and hybrid without architectural change. |

The last point is the strategic one. The team is the same team whether agents or humans do the work; only the implementations differ.

## The Command Contract

Every command follows the same shape:

```
agent-{role} {verb} --input <json-file-or-stdin> [--output <path>] [--budget <amount>]
```

Examples:

```
agent-artistic-director create-brief --input source.json --output brief.json
agent-composer propose-arrangement --input brief.json --output composition.json
agent-producer write-prompts --input composition.json --output prompts.json
agent-musician generate --input prompts.json --output candidates.json --budget 0.50
agent-critic review --input candidates.json --output reviews.json
agent-editor sign-off --input candidates.json --reviews reviews.json --output decision.json
```

For the newsroom:

```
agent-research investigate --input topic.json --output background.json
agent-reporter draft --input background.json --output article.json
agent-fact-checker verify --input article.json --output verification.json
agent-translator translate --input article.json --target-lang pt --output translated.json
agent-editor approve --input article.json --verification verification.json --output decision.json
```

Same shape, different verbs and inputs. Every command is discoverable (`agent-{role} --help`), well-documented, and stable.

## JSON In, JSON Out

The contract between commands is structured JSON. No prose, no implicit context, no "agent state". Each command:

- Reads structured input (typically a JSON file or stdin)
- Performs its operation (which may include calling models, calling other CLIs, doing local computation)
- Writes structured output

This makes the data flow visible. You can pipe one command into another:

```
agent-research investigate --input topic.json | \
  agent-reporter draft --output article.json
```

You can inspect intermediate states. You can replay from any point.

The schemas for input and output are part of each command's documentation. They evolve carefully (additive changes only, deprecation cycles for removals) so downstream commands do not break.

## Each Agent Has a CLI

The pattern is:

| Agent Role | CLI Binary |
|-----------|-----------|
| Composer | `agent-composer` |
| Reporter | `agent-reporter` |
| Critic | `agent-critic` |
| Editor | `agent-editor` |
| Fact-checker | `agent-fact-checker` |
| Translator | `agent-translator` |

Each binary is a small program. Inside, it might call an LLM API, or run local logic, or invoke a sub-tool. The implementation is hidden behind the CLI contract.

When an agent role has multiple operations, they are subcommands:

```
agent-research investigate ...
agent-research enrich ...
agent-research source-check ...
```

This is the same pattern as `git commit`, `git push`, `git status`. Familiar and well-understood.

## The Orchestration Layer

The orchestration layer (the thing that strings commands together) is itself a CLI or a script that calls CLIs. For a band song:

```bash
#!/bin/bash
SONG_ID=$(uuid)
agent-artistic-director create-brief --input source-mozart-40.json --output brief-${SONG_ID}.json
agent-composer propose-arrangement --input brief-${SONG_ID}.json --output composition-${SONG_ID}.json
agent-producer write-prompts --input composition-${SONG_ID}.json --output prompts-${SONG_ID}.json
agent-musician generate --input prompts-${SONG_ID}.json --output candidates-${SONG_ID}.json --budget 0.50
agent-critic review --input candidates-${SONG_ID}.json --output reviews-${SONG_ID}.json
agent-editor sign-off --input candidates-${SONG_ID}.json --reviews reviews-${SONG_ID}.json --output decision-${SONG_ID}.json
agent-publisher publish --decision decision-${SONG_ID}.json
```

That is the workflow. Plain shell. Each step debuggable. Each output inspectable.

More sophisticated orchestration adds error handling, retries, parallel execution where possible. Still a CLI script (or a small program that calls CLIs).

The orchestration layer can be human, agent, or scheduled. A cron job can run this workflow nightly. A human can step through it manually. An agent can decide which workflow to run based on incoming events.

## Budget as a First-Class Parameter

The voice memo flagged this: as we use more expensive models, budget control matters. Every command accepts a budget parameter:

```
agent-musician generate --input prompts.json --output candidates.json --budget 0.50
```

The command respects the budget: chooses a cheaper model if expensive ones would exceed, limits the number of generations, falls back to alternatives when over budget. If even the cheapest path exceeds budget, the command exits with a clear error and the orchestrator decides what to do.

Budget tracking is itself a command:

```
agent-accountant track --workflow-id ${SONG_ID} --spent 0.42
agent-accountant report --workflow-id ${SONG_ID}
```

Every command that spends money reports it. The Accountant rolls up. Per-workflow budgets are enforced. Per-day budgets cap total spend.

## Where the Vault Fits

CLIs read from and write to the vault. The vault is the structured filesystem that all commands share. Concretely:

- Input files are paths inside a vault
- Output files are paths inside a vault
- The orchestrator commits the vault after each successful command
- The full workflow history is the vault's commit history

This makes the vault the "tape" the workflow runs on. Every state is recorded. Every step is reproducible. The vault's commit history IS the workflow execution log.

## Productisation: Sell the CLIs

This is the strategic angle. The CLIs are sellable artefacts:

- Other organisations want their own production teams (newsrooms, agencies, studios)
- They can buy the CLIs as a package: `npm install -g @sgraph/band-team` (or equivalent)
- The CLIs run on their infrastructure or ours
- Updates are package updates
- The same CLIs that produce our content produce theirs

This is the package manager commercial model (11 May) applied to agentic workflows. The CLI is the unit. The vault is the storage. The orchestration is the service.

A musician who wants to operate this way installs the band-team CLIs and runs them against their own vaults. A news organisation installs the newsroom CLIs and runs their own publication. The expertise is in the CLIs (prompts, schemas, orchestration patterns); the customer's infrastructure runs them.

## Connection to SG Compute

## Open Questions

| # | Question | Approach |
|---|----------|----------|
| 1 | Should CLIs be Python or Node, or polyglot? | Probably both; pick per agent based on what the agent's tools need |
| 2 | How to version CLIs and maintain backward compatibility? | Standard semver + schema versioning |
| 3 | What happens when an LLM API breaks the world? | Each CLI is small enough to update without cascading changes |
| 4 | How to handle long-running operations (video generation taking 10 minutes)? | Async patterns: command returns a job ID, separate command polls status |
| 5 | Should there be a meta-CLI that orchestrates without shell scripts? | Probably, eventually. For now, shell is enough. |
