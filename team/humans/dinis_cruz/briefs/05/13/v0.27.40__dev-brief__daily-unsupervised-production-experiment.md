# Daily Unsupervised Production Experiment: One Song A Day

**version** v0.27.40
**date** 13 May 2026
**from** Human (project lead)
**to** Agent (Claude), @Dev, @Content
**type** Dev brief

## What This Is

The operational practice that runs on top of the band production team and the CLI-first agent architecture. Every day, the team produces a new song. End to end. Unsupervised. Budget controlled. Published to the band's website. I wake up the next morning and find out what the team made overnight.

This is the first concrete experiment in **running an agentic creative team in production**, unsupervised, with real outputs that are publicly visible. It tests not just the technical pieces (which exist) but the operational practices: budget control, quality gates, error recovery, daily cadence, the "wake up and see what happened" experience.

## The Daily Cadence

The workflow runs once per day, in a window when nobody is watching. The team:

1. Picks a classical source piece (from a curated pool, weighted by what has not been done yet)
2. Picks a fusion target style (rotates through the band's range)
3. Runs the full song-creation pipeline from the production team brief
4. Generates the visual treatment
5. Publishes the result to the band's website
6. Records the full provenance in the vault

The next morning, I open the band site and see what was made. The "today's track" slot has new content. The studio page shows the production record. The accountant page shows the cost.

If something failed during the night, the failure is logged, the orchestrator handles retry or skip, and the morning view explains what happened (no song today because X, here is the failure trace, the budget was not spent).

## Budget Control

Each song has a fixed budget. Working number: **£5 per song**. The accountant CLI enforces this:

- The orchestrator declares the budget at the start of the workflow
- Each step that costs money reports its spend to the accountant
- If a step's cost would exceed the budget, the step gracefully degrades (cheaper model, fewer iterations, lower quality threshold) or stops
- If no acceptable path exists within budget, the workflow aborts and the morning view shows why

The £5 figure is a starting point. The experiment will reveal:

- What quality is achievable at £5
- What the cost distribution actually looks like (mean, P90, outliers)
- Where the biggest spend is (music generation, image generation, model API calls for review)
- Whether £5 is too tight, too loose, or about right

After a week of runs, the budget can be tuned based on data.

## Bootstrap: Claude Dispatch

The voice memo flagged the bootstrap correctly: while we work toward fully API-driven automation, the initial trigger is **Claude Dispatch** (or equivalent) firing the workflow once a day on a schedule. Dispatch invokes the orchestration script; the script runs the CLIs; everything else happens automatically.

This is a deliberate compromise. Going fully API-only would be better in steady state, but requires a few extra plumbing pieces (scheduler, retry queue, alerting) that are not the point of this experiment. Dispatch handles the trigger; the rest is the actual work.

Once the workflow is stable, the trigger can migrate:

- Phase 1 (now): Claude Dispatch fires daily
- Phase 2: A cron job on an SG/Compute instance fires daily, runs the CLIs locally
- Phase 3: A scheduler service triggers via API, with retry and alerting
- Phase 4: An adaptive scheduler that decides when to run based on day of week, social patterns, what is happening in classical music news

Each phase has a clear migration path; none are blocking the experiment.

## The Quality Question

This is where it gets interesting. Songs vary in quality. Some will be great. Some will be embarrassing. Some will be middling.

The experiment must decide how to handle this. Two options:

**Option A: Publish everything.** The honest path. Every song goes live regardless of quality. The vault's provenance pages explain how each was made. Visitors see the range; they can like or dislike. This treats the project as an exploration, not a curated brand.

**Option B: Publish only what the Critic and Editor approve.** Quality gate. Only good songs go up. Songs that fail review are archived in the vault but not surfaced. The brand stays clean.

For the first weeks: **Option A.** Maximum learning, complete transparency, the experiment is partly about understanding what AI music sounds like across many tries.

Once patterns emerge: **shift toward Option B.** Tune the Critic and Editor to filter out the worst, surface the best. The brand evolves from "interesting experiment" to "curated AI band."

The decision point is around 2-4 weeks in, with data to inform it.

## The Morning View

The most important user experience for this experiment is mine, every morning. Open the site, see what happened. The morning view should show:

| Element | Content |
|---------|---------|
| **Today's track** | New song with cover art, playable inline |
| **Production summary** | "Mozart 40th → Zeppelin style, produced overnight, £4.30, 3 iterations" |
| **Studio link** | "How this song was made" with full provenance |
| **Yesterday's stats** | Plays so far, any feedback, comparison points |
| **Failures (if any)** | "No song today because X" with reasoning |
| **Pipeline status** | "Tomorrow's track is queued: Bach Cello Suite 1 → indie rock fusion" |

This page is the daily product. It is also the surface that any human producer running this kind of team would want.

## What This Experiment Will Teach Us

Beyond the obvious (does it work?), this experiment will surface:

| Question | What We Will Learn |
|----------|-------------------|
| **What does unsupervised agentic production look like in steady state?** | Failure rates, quality variance, cost variance over weeks |
| **Where do the agents get stuck?** | Decision points where they make poor choices, calibration needed |
| **What is the right budget?** | Cost-quality trade-off curve, sweet spot |
| **How does daily output compare to deliberate output?** | Is one good song per week better than seven mediocre ones per week? |
| **What is the audience response?** | Listeners, social engagement, feedback patterns |
| **What is the maintenance burden?** | How much of my time does an "unsupervised" team actually take? |
| **Where do humans still have to intervene?** | The specific edge cases that need human judgement |

These insights become directly applicable to the newsroom workflow, the content workflows, future agentic team work. The band is the cheapest place to learn lessons that apply everywhere.

## What Makes This A Good First Experiment

| Property | Why It Matters |
|----------|---------------|
| **Low stakes** | A bad AI song is not catastrophic; nobody is harmed |
| **Visible outputs** | Public, listenable; failure is observable and instructive |
| **Multi-modal** | Stresses audio, visual, text production simultaneously |
| **Bounded budget** | Cost is predictable per cycle |
| **Daily cadence** | Fast feedback loop; lessons apply within days |
| **Creative domain** | Quality is partially subjective; tests the Critic and Editor roles harder than fact-based content would |
| **No regulatory exposure** | Unlike the medical use case, no compliance risk |

The combination is rare. Most experiments either have higher stakes (and slower iteration) or lower stakes (and less informative outputs). The band hits both targets at once.

## The "Wake Up and See What The Team Made" Experience

The voice memo flagged this as the experiential goal: wake up in the morning, check the site, see what the team did overnight. This is the experience we want to validate.

If it works, it generalises beyond music. Imagine:

- Wake up and see what new content the newsroom produced
- Wake up and see what new analyses the investor pack team prepared
- Wake up and see what new evidence packs the medical workflow produced
- Wake up and see what new research the ontologist surfaced

The band is the first instance of a much broader pattern: **agentic teams that run while you sleep, accountable through provenance, controllable through budgets, observable through daily summary surfaces.**

If the daily-song experiment works, the daily-anything-else pattern follows.

## Failure Modes To Watch For

A few things that could go wrong, worth naming explicitly:

| Failure Mode | Mitigation |
|-------------|-----------|
| **All songs converge to the same sound** | Critic enforces diversity criteria; rotation of source-style pairs is broad |
| **Budget exhausted partway through, leaving partial work** | Accountant aborts cleanly with rollback; vault state is consistent |
| **API outage stops the whole workflow** | Orchestrator detects, logs, the morning view explains, no retry storm |
| **Quality degrades unnoticed** | Periodic human spot-checks; baseline tracks for comparison |
| **The Critic and Editor become rubber stamps** | Their disagreement is logged; if everything passes, the prompts need retuning |
| **Costs creep up over time** | Daily budget hard-cap; weekly total budget hard-cap |
| **The vault gets noisy with failed attempts** | Separate "successes" branch from "all attempts" branch; visitors see successes by default |

These are not blockers. They are predictable issues with known mitigations. Plan for them; do not be surprised by them.

| # | Criterion | Verification |
|---|-----------|-------------|
| 1 | One full song produced unsupervised in a single workflow run | End-to-end execution from trigger to published song without manual intervention |
| 2 | Per-song budget enforced (initial £5 cap) | Workflow respects budget; reports actual spend |
