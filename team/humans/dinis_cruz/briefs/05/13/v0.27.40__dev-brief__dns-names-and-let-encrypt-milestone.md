## What Was Achieved

Yesterday's milestone delivered ephemeral SG/Compute instances with valid TLS certs on raw IP addresses. Today's milestone closes the remaining gap: **proper DNS names**. An SG/Compute instance now boots with a valid DNS name (under our controlled domain), a valid Let's Encrypt certificate for that name, and the full vault app stack running.

In product terms: nobody wants to share a raw IP address. Browsers warn on them. Users distrust them. The instance was working but unshareable. Today it became shareable.

## The Catch-22 and How We Solved It

The interesting engineering puzzle of the day. The dependency chain looked impossible at first:

- We need the EC2 instance to exist before we know the public IP
- We need the public IP before we can create the DNS A record
- We need the DNS A record to propagate before Let's Encrypt can validate
- We need the cert to be in place before the vault app can serve over HTTPS
- We need the vault app to be up before the instance is useful

Naively serialised, this takes minutes to complete, mostly waiting on DNS propagation.

The solution: **parallel orchestration with rendezvous timing**. Three things happen in parallel:

```
Start EC2 instance ──┬─────────────────────────────────► instance ready
                     │
Build steps run on the instance ──┬────────────────────► app stack ready
                                  │
Create DNS record (after IP is known) ──┬──────────────► DNS propagates
                                        │
                       (rendezvous: all three converge)
                                        │
                                        ▼
                       Let's Encrypt ACME challenge runs
                                        │
                                        ▼
                                  Cert installed
                                        │
                                        ▼
                                  Vault app serves over HTTPS
```

The build and the DNS provisioning happen at roughly the same pace, so by the time the build finishes and the ACME sidecar is ready to request the cert, the DNS record has propagated. The wait is hidden inside work that needed to happen anyway. The whole sequence completes smoothly.

This worked first time after the design was right. Worth recording because it is a transferable pattern: **for boot sequences with circular dependencies, find work you can do in parallel to hide the wait.**

## The Cloud Reachability Mystery (Unresolved)

Side note worth recording. We can hit Claude's API from local environments and from production deployments, but we hit a `503` error from the ephemeral SG/Compute instances. We initially suspected the IP-address-only configuration was the cause; today's DNS work confirmed it is not. The error reproduces with the proper DNS name.

The current best hypothesis: **something about Claude's egress proxy is rejecting the request**, possibly related to IP reputation or freshly-created DNS records being scored as suspicious. We could not confirm this through perplexity research or Claude's own debugging.

For now: the instances work end-to-end except they cannot call Claude directly. Workarounds exist (route via a relay, use a different model). Documenting it here so we revisit when we have more time.

## The Full Workflow Demonstrated Today

To capture what is now possible end-to-end:

1. Open Claude
2. Ask Claude to create a vault with specific content (a band demo, a CV, a POC)
3. Push from Claude to the canonical SG/Send API (`send.sgraph.ai`)
4. Clone the vault locally
5. Change the remote to the ephemeral EC2 instance
6. Push to the new remote (notably **way faster than the Lambda function path**)
7. Visit the instance's proper DNS name in a browser
8. See the vault app rendering the content with a valid cert

That is the full loop: Claude → canonical API → local → ephemeral instance → live URL with cert. The whole thing now works smoothly. It would have been a research project a week ago.

## Performance Note

The push from the local clone to the EC2 instance is **way faster than the equivalent push to the Lambda function**. Worth recording for the architectural backlog: at some point the Lambda path needs investigation. For workflows that need speed, the EC2 path is now the preferred substrate.
