## What This Is

An extension of the CLI-first agent architecture brief from earlier today. That brief established the principle: every agent operation is a CLI command, JSON in, JSON out. This brief takes it further: each agent gets its **own full command tree**, with sub-commands organised by function, its **own folder** in the repository (with its own code, prompts, skills, interfaces), and a clear taxonomy of what each kind of command does.

This is the Wardley-maps next phase: moving up an order of abstraction. We are no longer talking about individual CLI invocations; we are talking about the structure that organises CLI invocations into coherent agent surfaces.

## The Higher-Order Abstraction

The earlier brief gave us: `agent-{role} {verb} --input <json> --output <json>`.

What we need now is the recognition that each `agent-{role}` is itself a **full CLI with its own sub-command tree**, not a single binary with a single verb. The shape becomes:

```
agent-{role}
    ├── internal/
    │     └── (commands the agent uses on itself, or that an orchestrator uses to drive it)
    ├── publish/
    │     └── (commands that produce output for other agents to consume)
    ├── consume/
    │     └── (commands that ingest input from other agents)
    └── meta/
          └── (status, configuration, introspection)
```

Each branch contains the sub-commands relevant to that function. The agent is a structured surface, not a flat list of verbs.

## The SGit Precedent

The reason this works is that SGit already proves the pattern. SGit is agent-friendly: an agent can use SGit commands (`commit`, `push`, `pull`, `status`, `branch`) to interact with vaults. The command structure is intuitive, well-bounded, predictable. An agent reads the help text, understands the operations available, picks the right one, and proceeds.

We need this same property for every agent. Not as a side-effect of how an agent happens to be wrapped, but as a deliberate design choice. Each agent presents itself to other agents (and to orchestrators, and to humans) through a CLI surface that mirrors what makes SGit work.

This is what scales agent collaboration. Without it, every agent-to-agent interaction is bespoke. With it, the interaction model is uniform: read the CLI, pick the command, run it, parse the output.

## The Three Function Categories

Every agent CLI breaks down into three function categories. The taxonomy matters because different categories have different operational properties.

### Publish

Commands that produce output for consumption by other agents (or humans, or systems).

```
agent-composer publish arrangement --output arrangement.json
agent-research publish findings --topic mozart-40 --output findings.json
agent-translator publish translation --source article-en.md --target pt --output article-pt.md
```

Publish commands write to vaults. Vaults hold structured output. Other agents read from vaults to consume.

Properties:
- Idempotent when re-run with the same input
- Output is auditable and reviewable
- Cost is bounded (the work is concrete)

### Consume

Commands that read input from other agents and process it. The receiving side of the email-FS-light pattern.

```
agent-critic consume queue --inbox /vault/critic/inbox --output processed.json
agent-editor consume submissions --inbox /vault/editor/queue --output decisions.json
agent-fact-checker consume claims --inbox /vault/fact-checker/inbox --output verified.json
```

Consume commands pull from inboxes (vault locations). They process whatever is there. They produce output (decisions, validations, new work items) that other agents then consume.

Properties:
- Often runs on a schedule (check inbox every N minutes/hours)
- Output may trigger new work elsewhere
- The inbox is the queue; the vault is the persistence layer

### Internal

Commands the agent runs on itself, or that orchestrators use to drive the agent's behaviour without going through publish/consume cycles.

```
agent-critic internal configure --strictness high
agent-composer internal review-prompt --version v3
agent-musician internal calibrate --target-style "led-zeppelin-heavier-moments"
```

Internal commands change the agent's behaviour, inspect its state, or run housekeeping. They do not typically touch the vault.

Properties:
- Used during development, debugging, configuration
- Used by orchestrators that want fine-grained control
- Not part of the standard agent-to-agent flow

### Meta

Status, introspection, version information.

```
agent-composer meta status
agent-composer meta version
agent-composer meta capabilities
agent-composer meta cost-estimate --input brief.json
```

Meta commands let the orchestrator (or a monitoring system, or a human) understand the agent without invoking it for real work. The cost-estimate sub-command is particularly important: it lets the budget layer make decisions before money is spent.

## What Each Command Type Actually Does

Within each function category, individual commands may differ in their nature:

| Command Nature | What It Does |
|---------------|--------------|
| **Purely programmatic** | Runs deterministic logic (data transformation, validation, file management). No LLM call. Cheap, fast, predictable. |
| **Prompt-driven** | Builds a prompt from the input, returns the prompt for an external agent to execute. The CLI does not call an LLM itself; it produces material for a wrapping agent. |
| **LLM-executed** | Calls an LLM internally. The CLI is a wrapper around a model invocation with structured input and output. |
| **Mixed** | Combines programmatic preparation, LLM execution, programmatic post-processing. Most production CLIs are this. |
| **Network calls** | Talks to external services (Suno, GPT-Image-2, web search). Cost-tracked, error-handled. |
| **Vault operations** | Reads from or writes to vaults. Uses SGit underneath. Commits become workflow history. |
| **Triggers other CLIs** | Invokes other agent CLIs as part of its work. The composition layer. |

A single agent's CLI tree mixes these. Some sub-commands are pure programmatic helpers; some are full LLM invocations; some return prompts for an outer agent to run. The taxonomy is documentation, not constraint.

## Per-Agent Folder Structure

Each agent gets its own folder in the repository. The structure is consistent across agents:

```
agents/
    ├── composer/
    │     ├── README.md              (what this agent does)
    │     ├── cli/                   (the CLI implementation)
    │     │     ├── publish/
    │     │     ├── consume/
    │     │     ├── internal/
    │     │     └── meta/
    │     ├── prompts/               (the prompts this agent uses)
    │     │     ├── arrangement.md
    │     │     ├── style-guide.md
    │     │     └── ...
    │     ├── skills/                (SKILL.md-style files for specific tasks)
    │     ├── schemas/               (input/output JSON schemas)
    │     ├── tests/                 (unit and integration tests)
    │     └── package.json           (or pyproject.toml; deps, version)
    ├── critic/
    ├── editor/
    ├── musician/
    └── ...
```

This structure achieves several things at once:

- Each agent is independently versionable
- Each agent is independently testable
- Each agent is independently distributable (the packaging unit for the package manager)
- Prompts live next to the code that uses them (no global prompt soup)
- Schemas are the contract; downstream agents read them to know what to expect
- A developer (human or agent) working on one agent does not have to read the whole project

This is the same principle as microservices applied to agents. Bounded, autonomous, contract-bound.

## The Fractal Uber-CLI

On top of the individual agent CLIs, an Uber-CLI composes them:

```
sg-agents <agent-name> <function> <command> [args...]
```

For example:

```
sg-agents composer publish arrangement --input brief.json
sg-agents critic consume queue
sg-agents publisher meta status
```

The Uber-CLI is a thin wrapper that dispatches to the underlying agent CLIs. It exists for convenience (single binary, consistent invocation pattern, easy tab-completion) but the underlying agent CLIs are still independently runnable.

This is the fractal property: at the bottom, individual sub-commands. Above them, per-agent CLIs. Above those, the Uber-CLI. Each level has the same shape; each level composes from the level below. Same idea as the package manager fractal composition from 11 May.

## Why This Scales

Three reasons this design scales agentic systems where flatter designs do not:

| Reason | Why It Matters |
|--------|---------------|
| **Bounded surfaces** | Each agent has a clearly-defined CLI. Other agents do not need to understand the agent's internals; they only need to read the CLI surface. Cognitive load is constant as the system grows. |
| **Substitutability** | If the composer agent is upgraded, the new version exposes the same CLI. Callers do not change. The contract is the boundary. |
| **Containability** | A weaker model can run a simple sub-command competently. A stronger model is reserved for the sub-commands that need it. Containment makes mixed-model systems possible. |
| **Determinism** | Tight CLI contracts produce more deterministic agent behaviour. The agent knows exactly what it can do, what input is valid, what output is expected. Open-ended prompts produce open-ended behaviour. |

This last point matters most. The earlier CLI-first brief made this argument generally; this brief reinforces it specifically. The reason to invest in CLI infrastructure is that **agents become more deterministic when their action space is structured.** A composer agent told "compose something" is unpredictable. A composer agent that exposes `publish arrangement`, `publish variant`, `consume brief`, `internal review-prompt` has bounded behaviour. Determinism follows from structure.

## Containment for Less-Capable Models

The voice memo flagged this explicitly: some agents will run on weaker models (open source, smaller, cheaper). The CLI-per-agent design makes this practical:

- The CLI defines exactly what the agent can do
- The prompts inside the CLI are tight, well-scoped, unambiguous
- The schemas validate input and output, so model wandering is caught
- A weaker model running a structured sub-command often performs comparably to a stronger model running an open prompt

This is how we deploy expensive models where they add value (creative composition, complex review) and cheaper models where they suffice (translation, formatting, classification). The CLI contract makes the split possible.

| # | Criterion | Verification |
|---|-----------|-------------|
| 1 | Per-agent folder structure specification documented | A canonical layout exists; any new agent uses it |
