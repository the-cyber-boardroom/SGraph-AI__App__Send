## What This Is

A methodology brief codifying a technique that works in practice but has not been written down. When designing a new agentic workflow, before writing any code, you spin up an agent (or several agents) to **role-play** the workflow on paper. Literally produce the documents that would flow between agents, the decisions each agent would make, the artefacts each step would produce.

The output is a set of documents that walk through the workflow as if it had already run. The benefit: you find tonnes of gaps, bottlenecks, missing schemas, ambiguous handoffs, places where two agents need information they would not have. You find these on paper, before any code is written, when the cost of fixing them is hours of writing rather than days of refactoring.

This is also called "dry running" or "tabletop exercise" in other disciplines. In this brief, it is the **paper test**.

## Why This Works

Agentic workflows have a property that makes the paper test unusually valuable: the work the agents do is **already documents**. A composer agent produces a composition document. A critic agent produces a review document. An editor agent produces a decision document. The artefacts at runtime are documents; the artefacts on paper are the same documents.

This means role-playing the workflow is not a poor approximation of running it. It is an actual rehearsal that produces actual artefacts in the right shape.

Three concrete benefits:

| Benefit | What It Catches |
|---------|----------------|
| **Schema gaps** | The composer's output does not have a field the producer needs |
| **Decision gaps** | Two paths in the workflow but no agent is positioned to make the choice |
| **Information gaps** | An agent late in the workflow needs context that no earlier agent published |
| **Ambiguity** | A brief is too open and produces wildly different outputs in different role-plays |
| **Cost surprises** | A step that looked simple actually needs many model calls to do well |
| **Sequencing problems** | Step B needs the output of Step A in a form Step A does not produce |
| **Bounce-back patterns** | Where iteration loops actually need to live (not where you initially planned them) |

All of these are vastly cheaper to fix in a paper rehearsal than after the implementation is half-built.

## The Methodology

The technique is straightforward but requires discipline:

### Step 1: Specify the workflow at a high level

Write down the agents involved, their roles, the high-level sequence. This is what we already produce in dev briefs and arch briefs. The paper test starts here, with a brief in hand.

### Step 2: Pick a concrete example

The role-play needs a concrete input. For the band: "Mozart's Symphony 40, first movement, rendered in Led Zeppelin's heavier style." For the newsroom: "EU AI Act implementation in Portugal, focus on funding mechanisms." For a medical workflow: "Patient with type-2 diabetes, age 58, requesting a Private Health Score assessment."

Concrete examples force concrete artefacts. Abstract examples produce abstract artefacts that hide problems.

### Step 3: Have an agent (or several) produce each step

For each step in the workflow, have an agent produce what that step would produce, in the correct shape, for the concrete example. The output is a document (or several). Save it.

For some steps, the agent role-plays a specific agent. The Composer agent in the rehearsal is Claude acting as Composer for one rehearsal run. The Critic agent is Claude (or a different model, or a different prompt) acting as Critic for one rehearsal run.

### Step 4: Pass documents between agents

Step N's output becomes Step N+1's input. If the rehearsal Critic's review references information not present in the rehearsal Musician's output, that is a gap. Write it down. Fix the schema. Continue.

### Step 5: Run multiple variations

The same workflow with three different concrete examples reveals different problems. A pop-style remix exposes different issues than a heavy-metal remix. A short news article exposes different issues than a long investigation. Variations are essential; one rehearsal is rarely enough.

### Step 6: Document the findings

Every gap, ambiguity, decision point, and surprise gets written into a "findings" document. This becomes the change set for the design before code is written.

### Step 7: Iterate the design

Update the briefs based on findings. Re-run paper tests on the updated design. Loop until the rehearsal is clean.

### Step 8: Then write code

Implementation follows. With the paper tests in hand, the implementation is largely mechanical; the hard design decisions are already made.

## What Makes This A Brief Rather Than An Article

This methodology is worth a brief because it produces tangible output (the paper-test documents themselves) that lives in the vault alongside the design documents. The paper-test artefacts are valuable in their own right:

- They are the canonical example inputs and outputs for each agent
- They are the test fixtures for the implementation (run the real agent, compare output to the paper-test output)
- They are the demo content for the "How this team works" pages on the website
- They are the documentation for what each agent should produce
- They are the calibration material for the Critic and Editor agents

The paper-test outputs do not get thrown away once the code is written. They become part of the project's substrate.

## When To Use This Methodology

Not every project needs paper tests. The cost is meaningful (it takes time to do properly). The technique is worth it when:

| Use When | Why |
|----------|-----|
| The workflow has 4+ agents | Cognitive complexity benefits most from rehearsal |
| Agents will run unsupervised | Errors caught at runtime are expensive when nobody is watching |
| Less-capable models will run some steps | Tight contracts matter more; paper tests reveal looseness |
| The workflow runs in production | Production failures are expensive; rehearsal is cheap |
| The workflow is novel | First-of-a-kind designs benefit most from rehearsal |
| Multiple variations exist | Different example inputs reveal different problems |

Skip paper tests when:

- The workflow is simple (1-2 agents, 1-2 steps)
- The workflow is throw-away (will run once or twice)
- The cost of failure is low and recovery is trivial
- The design is a direct copy of an already-tested workflow

The band team is exactly the right shape for paper tests: many agents, unsupervised, multi-modal, novel. The newsroom team is the same. Both warrant the investment.

## Why This Makes Agents Deterministic

The voice memo's closing line is the key principle: **how do you scale and make agents deterministic, and how do you contain them**. The paper test is one of the strongest tools for this.

By producing the expected artefacts on paper first, you create:

- Reference outputs that the implementation must match (or beat)
- Concrete schemas refined against real examples
- Documented decision criteria that the agents can be calibrated against
- A regression test bed: re-run the rehearsal periodically, compare to the original, detect drift

A weaker model running a CLI sub-command becomes more deterministic when the CLI is calibrated against paper-test outputs. The model knows what good looks like. The schemas catch deviations. The Critic and Editor have reference examples to compare against.

This is the practical answer to "how do we trust unsupervised agentic workflows?" You rehearse first. You codify the rehearsal. You measure the running system against the rehearsal. You catch drift before it becomes incidents.

## Generalisation Beyond The Band

The methodology applies wherever multi-agent workflows are designed. After the band team, the obvious next targets:

| Workflow | Paper-Test Value |
|----------|-----------------|
| Newsroom team (15 departments) | High; many agents, high stakes for accuracy |
| Medical workflow (Private Health Score) | Very high; mistakes have real-world impact |
| Investor pack engagement | High; deliverables go to clients |
| CV/portfolio production | Medium; failures are visible but recoverable |
| Content publishing on sgraph.ai | Medium; ongoing operational practice |

The pattern is: any workflow that will run in production with limited supervision benefits from paper tests during design.

## What This Asks For

To execute the methodology for the band team:

1. Pick three concrete song examples spanning the band's stylistic range
2. Run a paper test for each, producing all intermediate documents
3. Document findings (gaps, issues, surprises)
4. Update the agent CLI tree designs based on findings
5. Re-run paper tests on the updated design until clean
6. Use the final paper-test documents as fixtures for implementation
7. Publish the paper-test documents themselves to the band vault (under `/rehearsals/`) as part of the "how this team works" content

Estimated effort: 1-2 days of careful work for the band team. The output saves an order of magnitude more time during implementation.
