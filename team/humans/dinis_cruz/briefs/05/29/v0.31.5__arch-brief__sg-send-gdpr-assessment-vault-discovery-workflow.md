# The GDPR Assessment Vault: A Self-Contained Assessment Driven By A Discovery Workflow

## What This Is

The first of what will likely be several briefs on a powerful new kind of vault: **a GDPR assessment vault.** It is a self-contained vault that holds two things, the assessment itself and the data provided by the user, and it runs an interactive workflow that asks the user a series of questions, extracts facts, decisions, hypotheses, and next questions, and visualises the result (including with infographics). The project lead has wanted to build this for a long time but **did not have the tech for it before**; the recent vault chat, OpenRouter, and graph work now make it possible.

This is the first concrete instance of the facts/hypotheses/evidence vaults that the vault-chat token-management work anticipated (cross-ref: the v0.27.64 prompt-context-token-management brief, which named this preparation explicitly). It is foundational: it establishes the assessment-vault concept, the discovery workflow, and the tooling, with more detail (the GDPR graph, the question design, the visualisations) to come in follow-on memos.

## What The Assessment Vault Is

The structure: **a self-contained vault holding the assessment and the user's data.** The project lead: **"we want to create a GDPR assessment for a company, put it in the vault, and this is a self-contained vault that has two things: the assessment, and the data provided by the user."**

| The Vault Holds | What It Is |
|-----------------|------------|
| **The assessment** | The GDPR assessment: the framework, the questions, the analysis, the findings |
| **The user's data** | The facts, decisions, and answers the user provides during the workflow |

Self-contained (cross-ref: the v0.27.62 talk-to-the-vault brief's self-contained vault) is important: everything the assessment needs and produces lives in one vault, which is what makes it portable, shareable, and complete. The vault is both the tool (the assessment workflow) and the record (the user's data and the result).

## The Three Things It Needs

The project lead set out three components:

| Component | What It Is |
|-----------|------------|
| **A graph-based version of GDPR** | GDPR represented as a graph (the regulation/framework as structured, navigable knowledge) |
| **A set of questions and answers** | The questions to ask the user (designed for the discovery workflow below) |
| **A way to visualise the answers** | Many views of the answers, including infographics of what is happening |

The graph-based GDPR is notable: rather than GDPR as a flat checklist, it is a graph (its principles, obligations, lawful bases, data categories, and their relationships), which fits the semantic-knowledge-graph approach (cross-ref: the prompt-context brief's semantic knowledge graphs, and the Librarian's graph-native cataloguing). The questions and the visualisations are developed further in follow-on briefs; this brief establishes that they are needed and how they fit.

## The Key Principle: A Discovery Workflow, Not A Questionnaire

The heart of the brief, and the principle that makes it different: **minimise the user's work; the user should mostly confirm what we discover, not answer questions from scratch.**

The project lead: **"the key principle is creating a workflow where we ask the user a series of questions and extract a set of data: the facts, the decisions, the hypotheses, and the next questions. The idea is to minimise the work, minimise the input, almost like the user doesn't have to answer questions. The user should almost confirm what we discover. This is where I want an interactive workflow."**

This is the inversion that matters. A traditional GDPR assessment is a long questionnaire the user slogs through. This workflow is the opposite:

| Traditional Questionnaire | The Discovery Workflow |
|---------------------------|------------------------|
| The user answers every question from scratch | The system discovers and proposes; the user confirms |
| High input burden | Minimal input burden |
| Static form | Interactive, adaptive |
| The user does the work | The system does the work; the user validates |

The workflow extracts four things as it goes:

| Extracted | What It Is |
|-----------|------------|
| **Facts** | What is true about the company's data handling |
| **Decisions** | What the company has decided (lawful bases, retention, etc.) |
| **Hypotheses** | What the system infers or proposes, for the user to confirm |
| **Next questions** | What to ask next, driven by what has been discovered |

The facts/decisions/hypotheses/next-questions structure is exactly the facts/hypotheses/evidence vocabulary the prompt-context brief prepared for (cross-ref). The system proposes hypotheses; the user confirms or corrects; confirmed hypotheses become facts; the gaps generate the next questions. The user's job shrinks to validation and correction, which is far less work than answering a blank questionnaire, and it is what the LLM and the GDPR graph make possible (the system can infer and propose, rather than just ask).

## The Tooling (Already Mostly In Place)

The project lead noted the tools needed are largely already built, and wants to measure the cost per assessment.

### The LLM, Via The Vault Chat

The assessment needs an LLM, and the vault chat provides it: **"we need to add an LLM to this, but we already did the LLM chat. This is a variation of that."** The assessment workflow is a variation of the vault chat (cross-ref: the v0.27.64 vault-chat architecture brief): the same iframe app, the same `window.sg` bridge, the same tool-calling, applied to the GDPR discovery workflow rather than general chat. So the assessment vault is a specialised vault chat: the LLM reads the GDPR graph and the user's data, proposes hypotheses, asks the next questions, and the user confirms.

### OpenRouter In The Iframe, With A Key

The LLM access is via OpenRouter, exposed in the iframe: **"we are going to expose in the main app inside our iframe a way to talk to OpenRouter, because we need some models from there, and we pass in a key that has a certain amount of credits the user can use, or the key can provide its own API key."**

| Key Model | How It Works |
|-----------|--------------|
| **A provided key with credits** | A key with a certain amount of credits the user can use (a budgeted allowance) |
| **The user's own API key** | The user provides their own OpenRouter/API key |

This is the OpenRouter-key model from the auth and token-management briefs (cross-ref: the v0.27.60 authentication brief's user-OpenRouter-key, and the v0.27.64 prompt-context brief's keys-in-the-vault-for-execution): the assessment runs on either a provided, credit-limited key or the user's own. The provided-key-with-credits option is notable for assessments: it lets a user run an assessment on a budgeted allowance without bringing their own key (useful for a trial or a paid assessment), while the own-key option suits users who have one.

### Cost Per Assessment

The project lead wants to measure this: **"let's see how much these actually cost per assessment."** Because the workflow is LLM-driven (proposing hypotheses, generating questions, producing infographics), each assessment has an LLM cost, and knowing the per-assessment cost matters for the budgeted-key allowance and for any commercial model. This ties to cost attribution (cross-ref: the SG/Sentinel cost-attribution brief) and the budget discipline (cross-ref: the prompt-context brief's budget awareness): the assessment should run within a known, measured cost, and the discovery-workflow's minimise-the-input principle also helps minimise the cost (fewer, smarter LLM turns).

## Visualising The Result (Including Infographics)

The output side: **visualise the answers in many ways, including infographics of what is happening.** The project lead: **"we need a way to visualise the answers in all sorts of different ways, including using infographics of what's happening, and then we'll show infographics to the user on what has been created."** The infographic generation is an existing tool (cross-ref: the talk-to-the-vault brief's infographic use case, and the existing low-cost infographic generator): the assessment produces infographics of the company's GDPR posture (what data is held, the lawful bases, the gaps, the risks), shown to the user as the assessment progresses. The visualisations are both a result (the assessment's output) and part of the workflow (showing the user what has been discovered, to confirm). The detail of the visualisations is follow-on; this brief establishes that infographics of the assessment are a core output.

## Why This Matters

The assessment vault is a significant new direction for three reasons:

- **It is a concrete, valuable use case.** GDPR assessments are a real, recurring need for many companies; delivering one as an interactive, self-contained vault is materially better than a static questionnaire or a consultant's PDF.
- **It proves the facts/hypotheses/evidence vault.** It is the first concrete instance of the evidence-graph vault direction (cross-ref: the prompt-context brief), validating that the vault chat, the graph approach, and the discovery workflow compose into a real assessment tool.
- **It is a template.** GDPR is the first assessment; the same pattern (a graph of a framework, a discovery workflow, confirm-not-answer, visualisations) applies to many other assessments (security, compliance, risk), so this establishes a reusable assessment-vault model.

## What This Does Not Try To Be

- **Not a static questionnaire.** The user confirms discoveries; the system does the work.
- **Not a new chat engine.** It is a variation of the existing vault chat.
- **Not legal advice.** It is an assessment tool; the GDPR graph and the analysis support the user, who remains responsible (a caveat to carry into the product).
- **Not GDPR-only forever.** GDPR is the first assessment; the pattern is reusable.

## Honest Risks

**Risk 1: GDPR is complex; a graph and an LLM could mislead.** An assessment that proposes wrong hypotheses or misreads GDPR could give false assurance. Mitigation: the user confirms (the human stays in the loop); the GDPR graph should be carefully built and sourced; be clear it is an assessment aid, not legal advice; cite the basis for each hypothesis.

**Risk 2: Cost per assessment could be high or variable.** LLM-driven workflows cost money per run. Mitigation: measure it (the project lead's explicit ask); the minimise-the-input principle reduces turns; the budgeted-key allowance bounds it; cost attribution.

**Risk 3: The discovery workflow is the hard, novel part.** Propose-and-confirm is more sophisticated than a questionnaire. Mitigation: it builds on the vault chat and the graph; start simple (propose, confirm, next question) and refine; follow-on memos will detail it.

**Risk 4: Sensitive data in the assessment.** A GDPR assessment necessarily handles information about the company's data practices. Mitigation: the self-contained vault and zero-knowledge encryption; the user's data stays in their vault; the OpenRouter calls should be handled per the privacy stance.
