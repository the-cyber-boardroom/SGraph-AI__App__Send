# Connector OAuth In Practice: The Data Broker Iframe (And The No-Origin Blind Spot)

**version** v0.31.5
**date** 29 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, @Dev
**type** Dev brief

---

## What This Is

A practical implementation brief for the connector OAuth (Google Drive and the other connectors), which corrects a gap in the earlier connector analysis and proposes a cleaner model: **a data broker iframe.** The earlier connector briefs (cross-ref: the v0.31.5 external-data-connectors framework and Google Drive connector briefs) assumed the connector iframe, running with no origin, could perform the OAuth handshake. The project lead identified that this is a blind spot: **OAuth redirects cannot redirect to a no-origin (null) frame, because there is nothing to redirect to.** This brief works through the problem and lands on the data-broker model, which is both the fix and a stronger security design.

The project lead's instinct, which the brief follows: the UI the user interacts with should not be the thing that makes the network calls; a dedicated, isolated, token-holding broker should, and all the comms between the parts should be PKI-encrypted.

## The Blind Spot: OAuth Redirects And No-Origin Iframes

The correction: **the earlier analysis assumed the no-origin connector iframe could perform the OAuth handshake, but it cannot, because OAuth redirects (the 302 redirect back with the token) cannot target a null/no-origin frame.**

The project lead: **"there's a mistake we're making in the analysis, a gap: we're assuming the iframe running inside our environment, which runs with no origin, will be able to perform the OAuth handshakes. The blind spot is that, especially for OAuth redirects, you can't redirect to a null frame, because there's nothing to redirect to."**

This is a real constraint. The no-origin iframe model (cross-ref: the v0.27.64 VIV kernel-model brief, where only the top-level vault has an origin and every nested iframe has none) is excellent for isolation, but OAuth's redirect flow needs a real origin/URL to redirect back to. A null-origin frame has no URL for the OAuth provider to redirect to with the token, so the handshake cannot complete in the no-origin iframe as the earlier briefs assumed. The connector model needs adjusting to account for this.

## The Two Choices For The OAuth Redirect

The project lead identified two ways to handle the redirect problem:

| Choice | How It Works |
|--------|--------------|
| **1. The connector at the top level** | The connector (the part doing OAuth) runs in the top-level code (which has an origin), not in the no-origin app iframe, above the kernel |
| **2. Relay the request** | The parent kernel is told: if you receive a call on this URL (the OAuth token redirect), send it to this iframe (or send a message here); encrypted to the connector's public key |

The project lead: **"we have two choices: either the connector has to be on the top-level code, not on the app iframe (above the top-level kernel), or we relay the request. We have a mode where we tell the parent kernel: if you ever receive calls on this URL (the OAuth request tokens), send it to this event, send a message here. And if we give it a public key, we say: encrypt with this public key, so only the correct one gets those credentials. That's quite an interesting security model."**

The relay option (choice 2) is the more elegant, and it builds directly on the VIV kernel model (cross-ref: the VIV brief's kernel-talks-to-host and the broker): because only the top-level kernel has an origin, the OAuth redirect lands there, and the kernel relays it to the connector. The relay carries the credentials encrypted to the connector's public key (every iframe has a PKI, cross-ref: the VIV brief's PKI-on-every-message), so even though the credentials pass through the kernel, only the connector iframe can read them. This is the fix and a security property at once: the kernel routes but cannot read the credentials.

## The Data Broker Iframe

The model the project lead landed on and likes: **introduce a data broker, an iframe with one specific responsibility, to broker all requests with a specific connector. It holds the tokens and is the only thing that makes the network calls.**

The project lead: **"I quite like the scenario where for these connectors we introduce the concept of a data broker, which could be an iframe. I like the isolation the iframe provides, but it's an iframe that runs a specific codebase with a specific responsibility: to broker all requests with that specific connector. It holds the tokens and is the one that actually makes the requests to the server. That allows us to introduce a lot of security, controls, checks, policies, in a centralised place."**

| Property Of The Data Broker | Detail |
|-----------------------------|--------|
| **One responsibility** | Broker all requests with one specific connector |
| **Holds the tokens** | The OAuth tokens live here, nowhere else |
| **The only network caller** | The only component that makes network calls to the connector's API |
| **Isolated** | An iframe (the isolation the project lead values) |
| **A centralised control point** | Security, controls, checks, and policies all in one place |

The trust model is the striking part: **"we don't trust the vault, we don't trust anybody else, apart from that little iframe."** The data broker is the single trusted component for a connector: it holds the tokens and makes the calls, and nothing else (not the vault, not the UI, not the app) is trusted with the credentials or the network access. Concentrating the trust in one small, single-purpose, isolated, auditable component is a strong security posture: the attack surface for the credentials is one tiny iframe with one job, where all the controls and policies live.

## Separate The Network Connector From The UI

The conceptual distinction the brief draws out: **separate the network connector (the part that makes the calls) from the UI (the part the user interacts with).**

The project lead: **"the more I think about it, the more I like that the UI we create to support Google Docs or whatever should not be the one that makes the network calls, because that's where the user is interacting. I like the idea that there's a safe broker, even in the browser, that is the only one that can make the network calls."**

| Component | Responsibility | Trust |
|-----------|----------------|-------|
| **The connector UI** | What the user interacts with (the custom viewer; cross-ref: the connectors framework brief) | Not trusted with credentials or network access |
| **The data broker (the network connector)** | Holds the tokens; makes the network calls | The single trusted component |

This is a clean separation of concerns and a security boundary: the UI (where the user, and any untrusted rendered content, lives) is kept away from the credentials and the network, which live only in the broker. So the custom viewer renders, but it asks the broker for data; the broker holds the tokens and makes the calls. This corrects the earlier framework brief's "the app-in-iframe holds the credentials and makes the calls" into a more precise two-part model: the UI app, and a separate broker that is the only credentialed network caller.

## It Could Run As A Worker, Or Even Off-Machine

Two extensions the project lead noted, both following naturally from the broker model:

### A Worker

The broker could run as a worker: **"a safe broker, even in the browser, and eventually could be running as a worker, which gives us a couple more protections."** A web worker is even more isolated than an iframe (no DOM, a separate execution context), so running the broker as a worker tightens the isolation further. This is a natural evolution of the broker: start as an isolated iframe, move to a worker for more protection.

### Off-Machine (A Proxy Or Third-Party Service)

The broker need not even be in the browser: **"in the future that could be removed from here completely, sent to a specific other third-party service. Some providers actually need a proxy, so that iframe or set might not even be in the current browser. Most of the time we want it in the browser, but it could be that we don't, and the requests can be done by somebody else."** This connects to the connector-landscape research (cross-ref: the v0.31.5 connector-landscape-and-easy-wins brief, which flagged that some providers, like Notion, need a proxy because they block browser CORS): the broker model accommodates this cleanly, because the broker is already the isolated, single-purpose network caller, so moving it off-machine (to a proxy or service) for providers that need it is a natural variation, not a redesign. The default stays in-browser; the proxy case is supported when a provider requires it.

## The Elegant End State: The Caller Does Not Know Where The Data Is

The conceptual payoff the project lead articulated: **the nested app or kernel requesting an asset should have no idea where the data is, or even whether the request was made on that machine at all.**

The project lead: **"the nested app versus kernel that is making the request to access that piece of data should have no idea where it is, and no idea if that request to access that particular asset was even made on that machine."** This is the abstraction the broker model achieves: the component asking for data just asks (through the bridge, cross-ref: the VIV kernel brief); the broker resolves it, wherever the broker is and wherever the data lives (Google Drive, GitHub, a proxy, another machine). The requester is fully decoupled from the how and where of access. This is both elegant (clean separation) and secure (the requester never touches credentials, never knows the location, cannot leak what it does not have), and it unifies the in-browser and off-machine cases under one model: ask the broker; the broker handles it.

## How This Corrects And Extends The Connector Framework

This brief refines the connectors framework (cross-ref: the framework and Google Drive briefs) in three ways:

| Earlier Framework | This Brief's Refinement |
|-------------------|--------------------------|
| The app-in-iframe holds credentials and makes the calls | A separate data broker holds the tokens and makes the calls; the UI app does not |
| The no-origin iframe performs OAuth | OAuth redirect needs an origin; the top-level kernel receives it and relays (PKI-encrypted) to the broker, or the connector runs top-level |
| The viewer is the connector | The viewer (UI) and the broker (network connector) are separated; only the broker is trusted with credentials and network |

The broker model is consistent with, and builds on, the VIV kernel design (cross-ref: the VIV kernel-model brief): the broker is a side-by-side, single-purpose component (like the VIV broker that logs inter-vault requests); credentials are PKI-encrypted to it (like PKI-on-every-message); and the relay uses the kernel-talks-to-host routing. So this is not a new architecture; it is the connector OAuth done correctly within the VIV model.

## What This Asks For

1. **Correct the no-origin OAuth assumption** (a no-origin iframe cannot receive the OAuth redirect).
2. **Introduce the data broker iframe** (one responsibility per connector; holds the tokens; the only network caller; the single trusted component).
3. **Separate the network connector from the UI** (the UI renders and asks; the broker holds credentials and makes calls).
4. **Handle the OAuth redirect** via the top-level kernel receiving it and relaying (PKI-encrypted to the broker), or running the connector top-level.
5. **PKI-encrypt the credentials** to the broker's public key (only the broker can read them, even in transit through the kernel).
6. **Support running the broker as a worker** (more isolation) and **off-machine as a proxy/service** (for providers that need it; cross-ref: the connector-landscape brief).
7. **Decouple the requester from location** (the caller asks; the broker resolves; the caller does not know where or how).
8. **Centralise connector security in the broker** (controls, checks, policies in one auditable place).

Estimated effort: this is a design correction plus a focused component (the broker), built on the VIV kernel, PKI, and bridge that already exist. The relay (kernel receives the OAuth redirect, forwards PKI-encrypted to the broker) is the main new flow; the broker is a single-purpose iframe (then a worker); the off-machine/proxy mode is a supported variation. It refines the connector framework rather than replacing it.

## What This Does Not Try To Be

- **Not the no-origin-iframe-does-OAuth model.** That was the blind spot; OAuth redirect needs an origin.
- **Not the UI making network calls.** The UI renders and asks; the broker makes the calls.
- **Not trusting the vault or the app with credentials.** Only the broker holds the tokens.
- **Not always off-machine.** In-browser by default; off-machine (proxy) only where a provider requires it.
- **Not a new architecture.** It is the connector OAuth done correctly within the VIV kernel/broker/PKI model.

## Honest Risks

**Risk 1: The OAuth-redirect constraint could affect more than connectors.** Other flows assuming no-origin iframes could hit the same wall. Mitigation: this brief surfaces it; audit other flows for the same assumption; the relay model is a general fix.

**Risk 2: The broker is a concentrated trust point.** All the credentials and network access in one component. Mitigation: that concentration is the point (one small, auditable, single-purpose component); isolate it (iframe, then worker); PKI-encrypt comms; centralise the controls and policies there.

**Risk 3: Off-machine brokers add infrastructure.** A proxy/service for some providers is against the no-backend preference. Mitigation: in-browser by default; off-machine only where a provider requires it (cross-ref: the connector-landscape brief's proxy-needing providers); a deliberate, per-provider choice.

**Risk 4: The relay routes credentials through the kernel.** The OAuth credentials pass through the top-level kernel. Mitigation: PKI-encrypt them to the broker's public key, so the kernel routes but cannot read them; the kernel is a relay, not a reader.

| Which providers need an off-machine proxy? | Per the connector-landscape brief (e.g. Notion); decide per provider |
