# External Data Connectors: Virtual Files, Custom Viewers, And The Connector Model

**version** v0.31.5
**date** 29 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Arch / strategy brief

---

## What This Is

The general idea behind adding Google Drive support, generalised: **external data connectors.** Rather than a one-off Google Drive integration, the bigger opportunity is a model where a vault can present data that lives in other systems (Google Drive, GitHub, and many more) as virtual files, navigated and viewed inside the vault, without the data being stored in the vault. The Google Drive connector (cross-ref: the v0.31.5 Google Drive connector brief) is the first concrete instance; this brief is the framework.

The strategic reason this matters, in the project lead's framing: **the more of these connectors we have, the more people start to use SG/Vaults without noticing.** A connector meets people in the systems they already use; each one is a low-friction on-ramp to the vault. This is the same meet-them-where-they-are insight that drove the Google Drive idea (the VC session showed how much VC work happens in Google Drive), generalised into a strategy.

## The Core Idea: Expand The Link Concept Into Virtual Files

The starting point: **we already have the concept of a link, and it works well. Expand it.**

The project lead: **"the same way we created the vault within vaults, which is fundamentally just a convention, a UI thing, we already have the concept of link. Let's map out how to expand the concept of the link, because we already have this link structure, which works quite well: you can move them around, it's managed in the vault."**

The existing vault links already cover several resource types:

| Existing Link Type | What It Points At |
|--------------------|-------------------|
| **YouTube** | A video |
| **Page** | A web page |
| **Image** | An image |
| **Vault** | Another vault (the navigable vault-in-vault link) |

These work well, and the vault-link in particular gives the sense of navigating into the linked thing. The proposal: **add more link types that point at external data stores**, so a link can point at a Google Drive folder, a GitHub repo, or any other data store with an accessible API. The infrastructure already exists (links are created, moved, and managed in the vault); connectors are new link types on that infrastructure.

So a connector is, at its simplest, a new kind of link: a managed reference in the vault to data that lives elsewhere, with a viewer that knows how to render it.

## The Key Requirements

The project lead set out the requirements precisely, and they define what makes a connector viable:

| Requirement | Detail |
|-------------|--------|
| **API access from the browser** | The data store must be reachable via an API from the browser (the fundamental requirement) |
| **OAuth** | Authentication via OAuth, which the platform already supports |
| **No data stored in the vault** | The vault stores the reference and the credentials/config, not the data; the data stays in the source system |
| **Read-only or read-write** | Distinguish the access level and the privileges required per connector |
| **Hierarchical / folder view** | Anything with a hierarchical structure can be presented as a navigable tree |

The project lead: **"the key requirement is that we need to access it from an API on the browser. OAuth should work, because we already support OAuth. But the key point is we're not storing any data in the vault, we're just accessing data. We're leveraging our editors, our environment."**

The no-storage point is central: a connector does not copy data into the vault. It accesses the source on demand, renders it, and the data stays where it lives. The vault contributes the reference, the credentials/config, the viewer, and the navigation, not the storage. This keeps the connector lightweight, avoids duplicating (and having to secure) the source data, and respects the source system as the system of record.

## Custom Viewers, Not Framing

A crucial design decision: **we show our own custom viewers for each connector, not an iframe of the third-party site.**

The project lead: **"I'm pretty sure Google Drive will not allow framing. So instead of framing it, we actually show our own views: our customised viewer for GitHub, our customised viewer for Google Drive."** This is correct and important. Most major services prevent being embedded in an iframe (via X-Frame-Options or frame-ancestors CSP), so framing the third-party UI mostly does not work. The right model is the opposite: **a custom viewer (our own HTML) that calls the source's API (with OAuth) and renders the data in our UI.**

| Approach | Viability |
|----------|-----------|
| **Frame the third-party site** | Mostly blocked (X-Frame-Options / CSP); not viable for major services |
| **Custom viewer calling the API** | Viable; our HTML, the source's API, our rendering |

This is why the connector model is built on API access plus a custom viewer: we are not embedding Google Drive's UI, we are building a Google Drive viewer that talks to the Drive API. The viewer is just a web page (cross-ref: the Vault App model), so it fits the platform naturally. The project lead: **"remember that this just looks like a web page, so in principle it shouldn't be that hard, because we already have that."**

## The App-In-Iframe-Has-The-Credentials Model

The architecture that makes connectors safe and composable, building on the vault chat and Vault App work (cross-ref: the v0.27.64 vault-chat architecture brief): **the connector is an app in an iframe; the app holds the credentials and makes the API calls; the vault talks to the app, not to the source.**

The project lead: **"you're basically seeing an app in the page, and the app is the one that has the credentials to do it. We still open the system inside the app iframe, so you still need to get permissions for that, and we don't cache them. You get the OAuth permission inside the iframe, but you can ask questions to that app from the vault."**

The flow:

1. The connector is an app (HTML) in an iframe.
2. The app obtains the OAuth permission (inside the iframe) and holds the credentials.
3. The app makes the API calls to the source (Google Drive, GitHub, etc.).
4. The vault talks to the app (asks it what files exist, what the structure is, to fetch a file), not directly to the source.

This is the `window.sg` bridge pattern (cross-ref: the vault-chat architecture and the VIV kernel brief) applied to connectors: the iframe app is the credentialed boundary, and the vault communicates with it through the bridge. The credentials stay in the iframe (not cached, not in the vault); the vault gets answers, not the raw credentials. The project lead: **"once you click on it, it's whatever HTML, so it becomes a case of getting a JSON from the source and having a viewer, basically a mini app."** Get JSON from the source, render it in a viewer, that is the connector.

## Exposing Primitives To The Vault

The deeper integration the project lead wants: **expose connector primitives to the vault, so the vault can ask the connector app what exists and render it natively.**

The project lead: **"how hard would it be to expose some of those primitives to the vault, where we can say: if you embed this file inside the vault and authenticate, we can ask through that particular iframe what files exist, what structure exists, and then show it either in the UI, or abstract the whole thing and just use the iframe as the communication layer."**

Two levels of integration:

| Level | What It Means |
|-------|---------------|
| **Show in the connector's own viewer** | The connector app renders its own view (the Google Drive viewer, the GitHub viewer) |
| **Abstract the iframe as a communication layer** | The vault asks the iframe what files/structure exist and renders them in the vault's own UI (e.g. the tree view) |

The second level is the powerful one: the iframe becomes a communication layer (a credentialed API proxy), and the vault's own UI (the tree view, cross-ref: the VIV brief's tree-view compatibility) renders the external data as if it were vault content. The project lead's question, **"can I also make it look like it's part of a tree?"**, is exactly this: the external folder structure appears as a branch in the vault tree, navigable like any vault folder, with the iframe quietly supplying the data behind it.

So there are two elements, as the project lead summarised: **"the element of what a vanilla Google Drive (or GitHub) in these permissions looks like, where you use OAuth and normal flows to represent that, but instead of framing it we show our own views; and the element of making it look like it's part of a tree."** A connector can be a standalone custom viewer, or it can be abstracted into the vault tree. Both run on the same app-in-iframe-with-credentials primitive.

## Read-Only Versus Read-Write

The project lead noted connectors should distinguish access levels: **read-only versus read-write, and the privileges (and OAuth scopes) each requires.** A connector might offer only browsing (read-only) or also editing (read-write), depending on the source's API and the OAuth scopes granted. This maps onto the least-privilege stance (cross-ref: the Google Drive connector brief's least-privilege scopes, and the authentication brief): request the narrowest scope that serves the connector's purpose, and offer read-only where that is enough. The access level is a property of each connector (and each connection), set by the scopes the user grants.

## Why This Is Strategic: Adoption Without Noticing

The project lead's strategic framing deserves its own statement: **each connector is a low-friction on-ramp, so the more connectors, the more people use the vault without noticing.** A VC who lives in Google Drive, a developer who lives in GitHub, an analyst who lives in a particular data store: a connector lets each of them work in the vault while their data stays in the system they already use. They get the vault's benefits (the unified UI, the navigation, eventually the chat and the controlled sharing) layered on top of their existing data, with no migration and no noticing. This is adoption by augmentation rather than replacement, and it compounds: each connector widens the set of people for whom the vault is immediately useful.

This connects to the interoperability principle (cross-ref: the SG/Sentinel interoperability-collaborators-not-competitors brief): the vault feeds on and works with the systems people already use, rather than demanding they move. Connectors are that principle made into a product surface.

## What This Asks For

1. **Build the external-data-connector model** as an expansion of the link concept (new link types pointing at external data stores).
2. **Require API-access-from-the-browser plus OAuth** (the two viability requirements; OAuth is already supported).
3. **Store no source data in the vault** (only the reference, credentials/config, and the viewer).
4. **Build custom viewers, not framing** (our HTML calling the source API; framing is blocked for most services).
5. **Use the app-in-iframe-with-credentials model** (the iframe holds the credentials and makes the calls; the vault talks to the iframe via the bridge; credentials not cached).
6. **Expose primitives to the vault** (ask the iframe what files/structure exist; render in the connector viewer or abstract into the vault tree).
7. **Support read-only and read-write** (per connector, per the OAuth scopes granted; least privilege).
8. **Prioritise connectors by easy wins** (cross-ref: the v0.31.5 connector-landscape-and-easy-wins research brief).

Estimated effort: the model builds on existing infrastructure (links, the `window.sg` bridge, Vault App, OAuth), so the framework is largely composition; each connector is then a custom viewer plus the source's API integration; the tree-abstraction is the deeper (and higher-value) integration. The first connector (Google Drive) proves the pattern; subsequent connectors get cheaper as the model matures.

## What This Does Not Try To Be

- **Not data storage.** Connectors access source data; they do not copy it into the vault.
- **Not framing the third-party UI.** Custom viewers calling APIs; framing is blocked for most services.
- **Not a single integration.** It is a general model; Google Drive is the first instance.
- **Not unbounded access.** Read-only or read-write per the least-privilege OAuth scopes granted.

## Honest Risks

**Risk 1: Not every API is browser-accessible.** Some sources block CORS or do not offer browser-friendly APIs (cross-ref: the connector-landscape research brief). Mitigation: prioritise CORS-friendly, OAuth-supporting APIs (the easy wins); be honest about which sources need a proxy or are not viable browser-side.

**Risk 2: Custom viewers are per-connector work.** Each connector needs a viewer and an API integration. Mitigation: a shared connector framework (the app-in-iframe model, the bridge primitives) so each viewer is mostly rendering; reuse across connectors; prioritise by value and ease.

**Risk 3: Credentials in the iframe must be handled safely.** The iframe holds OAuth credentials. Mitigation: credentials stay in the iframe, not cached, not in the vault; the bridge passes answers, not credentials; least-privilege scopes; the no-origin-iframe isolation (cross-ref: the VIV brief).

**Risk 4: Source APIs change.** A connector depends on an external API that can change. Mitigation: connectors are isolated viewers (a broken one does not break the vault); version and monitor; the no-storage model means a broken connector loses access, not data.

## Open Questions

| Question | Notes |
|----------|-------|
| What is the connector link-type schema? | Extend the existing link convention; type, source, scope, config |
| How are credentials held and refreshed in the iframe? | Not cached; OAuth refresh; define the lifecycle |
| What primitives does the vault ask the iframe for? | List files, get structure, fetch a file, write a file (if read-write) |
| When to render in the connector viewer vs abstract into the tree? | Both; the tree-abstraction is the deeper integration |
| How is read-write exposed and confirmed? | Per OAuth scope; confirm writes; least privilege |
| Which connectors first? | Per the easy-wins research (Google Drive first) |
