## What This Is

The research the project lead asked for: the art of the possible for external data connectors (cross-ref: the v0.31.5 external-data-connectors framework brief), and the good and easy wins, so connectors can be prioritised. The strategic reason for caring, in the project lead's words: **the more of these connectors we have, the more people start to use SG/Vaults without noticing.** Each connector is a low-friction on-ramp, so picking the easy, high-value ones first compounds adoption.

The research is grounded in two viability tests from the connector model: **(1) is the source's API accessible from the browser (CORS-friendly), and (2) does it support OAuth?** A connector is an easy win when both are true, the data is hierarchical (so it renders as a navigable tree), and the audience is large. This brief surveys candidate connectors against those tests and ranks them, honestly flagging the ones that are harder than they first appear.

A note on what makes a connector viable, from the model: the connector is a custom viewer (our HTML) calling the source API with OAuth, in an iframe that holds the credentials, not a frame of the third-party site (most sites block framing). So the question is always: can our browser-side code call this API, and authenticate cleanly?

## The Two Viability Tests

| Test | Why It Matters |
|------|----------------|
| **Browser-accessible API (CORS)** | The connector calls the API from the browser; if the API does not send CORS headers, the browser blocks the call, and a server-side proxy is needed (more infrastructure, against the no-backend stance) |
| **OAuth support** | The connector authenticates via OAuth (already supported); without it, the connector needs API keys or another flow (more friction, less safe) |

A third, softer test is **hierarchical data**: the model shines when the source has a folder/tree structure to render and navigate. A fourth is **audience size**: a connector is more valuable the more people use the source.

## The Easy Wins (CORS-Friendly And OAuth)

These sources pass both viability tests: their APIs support CORS (callable from the browser) and they support OAuth. They are the connectors to build first.

### Google Drive (The First Connector)

Google Drive is the natural first connector (it drove this whole line of work, cross-ref: the Google Drive connector brief). Client-side OAuth is well supported (Google explicitly supports JavaScript browser apps), the data is hierarchical (folders), the audience is huge, and crucially the least-privilege path exists: the non-sensitive `drive.file` scope plus the Google Picker API give per-folder access (the app sees only what the user picks). It is the strongest easy win: high audience, clean least-privilege, hierarchical, browser-friendly.

### GitHub

GitHub is an excellent easy win. Its REST API explicitly supports CORS for requests from any origin, it supports OAuth, the data is hierarchical (orgs, repos, folders, files), and the audience (developers) is large and exactly the kind that adopts tools by augmentation. The project lead named a GitHub viewer specifically. A GitHub connector (browse repos, view files, render READMEs and code) is low-friction and high-value, and the custom-viewer model fits it well (GitHub's own pages are not the point; our viewer rendering the repo tree and files is).

### OneDrive / Microsoft Graph

OneDrive (via Microsoft Graph) documents CORS support and provides a JavaScript OneDrive-explorer sample, supports OAuth, and is hierarchical (folders). The audience (Microsoft 365 users, especially enterprise) is large. One honest caveat from the research: file download via the `/content` endpoint returns a 302 redirect, which CORS prohibits, so the connector uses the `@microsoft.graph.downloadUrl` property instead of the `/content` redirect. With that known workaround, OneDrive is a solid easy win, and it pairs naturally with Google Drive to cover both major consumer/enterprise file stores.

### Cloud Object Storage (S3, Google Cloud Storage)

Amazon S3 and Google Cloud Storage both support CORS (configurable per bucket). These are more technical audiences, but for developer and data use cases a bucket-browser connector is straightforward and useful. Note S3 uses its own auth (signed requests) rather than OAuth in the typical case, so the auth flow differs from the OAuth connectors; for buckets the user controls, this is workable.

### Media And Social (Spotify, SoundCloud, YouTube, Flickr)

Several media and social APIs support CORS and OAuth (Spotify, SoundCloud, YouTube, Flickr, the Facebook Graph API). These are lower-priority for the vault's likely audience (less about confidential documents), but they are genuinely easy and could power lightweight connectors or demos. YouTube is already a link type (cross-ref: the conventions brief), so it is partly done.

## The Workable-With-A-Quirk Tier

These support OAuth and are browser-reachable, but with a known quirk to handle.

### Dropbox

Dropbox supports OAuth and browser use, and is hierarchical (folders), with a large audience. The known quirk from the research: Dropbox's API triggers CORS preflight requests on calls unless you use its specific pattern (pass `arg` and `authorization` as URL parameters, set the `Content-Type` to the Dropbox CORS-hack value, and set `reject_cors_preflight=true`). With that pattern, browser calls work efficiently. So Dropbox is a workable win with a documented technique, and it is a strong file-store complement to Google Drive and OneDrive.

## The Harder Ones (Honest Flags)

These were mentioned or are tempting, but the research shows they are harder than they look. Flagging them honestly avoids wasted effort.

### Notion

Notion is appealing (hierarchical pages, large audience), but its API **blocks CORS in the browser**: browser-direct calls are rejected, and a server-side proxy is required. That is against the no-backend, browser-API stance of the connector model. A Notion connector is possible but needs a proxy, so it is not an easy win; defer it or accept the proxy cost deliberately.

### Airtable

Airtable supports OAuth and offers a browser client, but its CORS behaviour is **inconsistent and unreliable** (community reports of CORS being blocked, and a common need for a CORS proxy). So while it sometimes works browser-direct, it cannot be relied on without a proxy. Treat Airtable as caution-tier: attractive data (structured bases), but the browser-access test is shaky.

### AWS (EC2 And Most Services)

The project lead floated AWS specifically (**"I could even do AWS, see EC2 instances"**). This is the honest hard case. Most AWS service APIs (EC2, etc.) use **SigV4 request signing, not OAuth**, and are **not designed for browser CORS access**. So a general AWS connector does not fit the OAuth-plus-browser-API model: it would need signed requests (and exposing AWS credentials in the browser is a security problem). The exception is **S3**, which supports CORS (above). So: an S3 bucket connector is viable; a general AWS-console-style connector (EC2 instances and other services) is not an easy win and would need a different approach (a backend, or a narrow signed-request design). Worth saying plainly so it is not mistaken for a quick add.

## The Ranking

Pulling it together, a suggested priority order by ease and value:

| Tier | Connector | Browser API (CORS) | OAuth | Hierarchical | Audience | Verdict |
|------|-----------|--------------------|-------|--------------|----------|---------|
| **1 (build first)** | Google Drive | Yes (client-side OAuth) | Yes (`drive.file` + Picker, least-privilege) | Yes (folders) | Huge | The first connector; cleanest least-privilege |
| **1** | GitHub | Yes (CORS any origin) | Yes | Yes (repos/files) | Large (devs) | Excellent, named by the project lead |
| **1** | OneDrive / MS Graph | Yes (with downloadUrl caveat) | Yes | Yes (folders) | Large (enterprise) | Solid; pairs with Drive |
| **2 (workable)** | Dropbox | Yes (with preflight technique) | Yes | Yes (folders) | Large | Workable with the documented CORS pattern |
| **2** | S3 / Cloud Storage | Yes (per-bucket CORS) | Signed/keys (not OAuth) | Yes (prefixes) | Technical | Good for dev/data use cases |
| **3 (lower priority)** | Spotify / YouTube / SoundCloud / Flickr | Yes | Yes | Partly | Varies | Easy but less aligned to confidential-docs audience |
| **Caution** | Airtable | Unreliable (often needs proxy) | Yes | Yes (bases) | Medium | Attractive data, shaky browser access |
| **Harder** | Notion | No (CORS blocked) | Yes | Yes (pages) | Large | Needs a proxy; not an easy win |
| **Harder** | AWS (EC2/general) | No (not CORS; SigV4) | No (signed requests) | Yes | Technical | Not the OAuth/browser model; S3 is the exception |

## What Makes The Easy Wins Easy (The Pattern)

The tier-1 connectors share a profile worth naming, because it is the template for evaluating future connectors:

- **The API sends CORS headers**, so our browser-side viewer can call it directly (no proxy, no backend).
- **OAuth is supported**, so we reuse the platform's OAuth and request least-privilege scopes.
- **The data is hierarchical**, so it renders as a navigable tree (the vault's strength).
- **A least-privilege path exists** (like Drive's `drive.file` plus Picker), so we access only what is shared.
- **The audience is large and tool-adopting**, so the connector compounds adoption.

When evaluating any new connector, run it against this profile; the more it matches, the easier the win.

## The Strategic Sequence

A suggested sequence that builds momentum:

1. **Google Drive** (the first; proves the model; the VC-driven, high-audience, clean-least-privilege win).
2. **GitHub** (the developer win; named; excellent CORS/OAuth; a different audience to broaden reach).
3. **OneDrive** (the enterprise file-store win; pairs with Drive to cover the major file stores).
4. **Dropbox** (the third file store; workable with the known technique).
5. **S3 / Cloud Storage** (the developer/data win).
6. **Reassess** Notion, Airtable, and a possible AWS-S3-only or proxied approach, deciding deliberately whether the proxy cost is worth the audience.

The first three (Drive, GitHub, OneDrive) are all clean easy wins across three distinct audiences (general/VC, developer, enterprise), which is the fastest way to make the vault immediately useful to many people without them noticing they have adopted it.

## What This Asks For

1. **Adopt the two viability tests** (browser-API/CORS and OAuth) plus the softer tests (hierarchical, audience) to evaluate connectors.
2. **Build the tier-1 easy wins first** (Google Drive, GitHub, OneDrive).
3. **Use the documented techniques for tier-2** (Dropbox's CORS pattern; S3 per-bucket CORS).
4. **Flag the harder ones honestly** (Notion needs a proxy; Airtable's CORS is unreliable; general AWS is not the OAuth/browser model).
5. **Sequence for audience breadth** (Drive, GitHub, OneDrive cover three distinct audiences).
6. **Re-run the easy-win profile** on any new candidate connector.

Estimated effort: this is a prioritisation, not a build; the builds are per the framework and Google Drive briefs. The value here is avoiding wasted effort on the harder ones and sequencing the easy wins for maximum adoption.

## What This Does Not Try To Be

- **Not a commitment to build all of these.** It is a ranked survey to prioritise.
- **Not a claim every API is browser-friendly.** The harder ones are flagged honestly.
- **Not a static list.** APIs and CORS policies change; re-verify before building each connector.
- **Not the framework or the Drive design.** Those are separate briefs.

## Honest Risks

**Risk 1: CORS and API policies change.** A source that is CORS-friendly today may change. Mitigation: re-verify at build time; isolate connectors (a break loses access, not data); monitor.

**Risk 2: The harder ones are tempting.** Notion and a full AWS connector are attractive but need a proxy or a different model. Mitigation: flag them clearly (this brief); decide the proxy cost deliberately, do not stumble into it.

**Risk 3: OAuth scope and review burden vary.** Some sources have heavier OAuth review (especially broad scopes). Mitigation: prefer non-sensitive, least-privilege scopes (like Drive's `drive.file`); this also eases user consent.

**Risk 4: Browser credential handling.** Each connector holds OAuth credentials in the iframe. Mitigation: the app-in-iframe model (cross-ref: the framework brief); not cached; least privilege; no-origin isolation.
