# The Vault App Store: Sharing, Distributing, And Billing For Vaults

**version** v0.31.5
**date** 29 May 2026
**from** Human (project lead)
**to** Product, Strategy, Architect, @Dev
**type** Strategy brief

---

## What This Is

A short brief on the **Vault App Store** (or Vault App Hub, the name is to be settled): a place to share, distribute, describe, secure, and bill for vaults. The need is now clear because vault-of-vaults makes importing a vault as easy as a Git submodule (cross-ref: the v0.27.64 VIV kernel-model brief and the v0.31.5 evidence-CV brief's workflow-as-an-importable-app), so there should be an easy way to find, share, and distribute the vaults people build. This is the marketplace layer on top of the importable-vault-app capability.

The project lead's framing: a plug-in/module app store, like other app stores, including billing, and (helpfully) easy to implement because **a vault is just a zip**.

## Why Now

The project lead: **"especially with vault-of-vaults and the ability to import them easily, we need to start to have this alternative, easy way to share and distribute these vaults, describe what they do, analyse them for security, and map all the agents."** The capability to import vault apps (the CV workflow, the infographic generator, the graph generator, an assessment) exists; what is missing is the distribution surface. The store is that surface: a catalogue of vaults you can find, understand, trust, and import.

## What The Store Does

| Function | Detail |
|----------|--------|
| **Share and distribute** | Publish a vault for others to find and import |
| **Describe** | What the vault does (its purpose, its workflow) |
| **Security analysis** | Analyse the vault for security before importing (cross-ref: the SG/Sentinel and security-report work) |
| **Map the agents** | Show the agents, tools, and skills the vault uses |
| **Billing** | Sell vaults; pay the developers |

It is, the project lead said, **"a plug-in module, an app store, like other stores."** The familiar app-store model applies: a catalogue, descriptions, trust signals (the security analysis and the agent map), import, and billing. The security analysis and agent-mapping are notable trust features: before you import a vault (which may carry agents and tool access), you can see what it does and that it is safe, which matters more for an executable vault app than for a passive file.

## The Billing Model: Pay The Developers, Bundle Credits

The commercial model the project lead sketched: **sell a vault for a little money to the benefit of the developer who made it, and optionally bundle OpenRouter credits.**

The project lead: **"you could sell one of these vaults for a little bit of money to the person who developed it, but also with maybe five [dollars/grid] of credits on OpenRouter. That could be a nice way of doing this."** So a vault app can be sold, the developer is paid, and the purchase can include a bundle of OpenRouter credits (cross-ref: the v0.27.60 authentication brief's OpenRouter-key model and the v0.31.5 GDPR brief's provided-key-with-credits). The credits bundle is a clean idea for vaults that run LLM workflows (a CV workflow, an assessment): the buyer gets the app and an allowance of credits to run it, so it works out of the box without bringing their own key. This rewards developers and lowers the buyer's friction in one move.

This sits within the broader commercial direction (cross-ref: the open-evaluation and SG/Sentinel commercial-model briefs): the store is a way for an ecosystem of vault-app developers to be paid, with the platform taking the usual store role.

## Multi-Language And Multi-Culture

The project lead noted this can serve many audiences: **"this can now be done in multiple languages, multiple cultures."** A vault app (a CV workflow, a GDPR assessment) can be published in multiple languages and adapted to multiple cultures and jurisdictions, which widens the market and is especially relevant for assessments that are jurisdiction-specific (GDPR for one region, a different regime for another). The store can host localised and culturally-adapted versions, published by developers who know those markets.

## Why It Is Simple: A Vault Is Just A Zip

The implementation insight that makes this tractable: **a vault is just a zip, so distribution is releasing zip files.**

The project lead: **"it shouldn't be that complicated, because ultimately the vault is just a zip, so we can just release the zip files that contain the vault. We just need a nice way to import them, version-control them, load them up, do all that locally."** Because a vault is a self-contained zip (cross-ref: the v0.27.64 prompt-context brief's zip-the-VFS-to-vault, and the self-contained-vault model), distributing a vault app is distributing a zip. So the store's core is straightforward:

| Need | Detail |
|------|--------|
| **Release zips** | A vault app is a zip to publish |
| **Import** | A nice way to import a published vault |
| **Version control** | Versioned releases (grab the latest; cross-ref: the workflow-as-an-app versioning) |
| **Load locally** | Load and run the imported vault locally |

The store does not need heavy infrastructure to move the vaults themselves (they are zips); it needs the catalogue, the descriptions, the security analysis, the agent map, the billing, and a clean import/version/load flow. The heavy lifting (the import, the version control, the local load) builds on the vault-of-vaults and self-contained-vault capabilities already designed.

## What This Asks For

1. **Build the Vault App Store / Hub** (settle the name): a catalogue to share, distribute, and discover vault apps.
2. **Describe each vault** (what it does, its workflow).
3. **Analyse vaults for security and map their agents** before import (the trust layer, especially important for executable vault apps).
4. **Add billing** (sell vaults; pay the developers; optionally bundle OpenRouter credits).
5. **Support multiple languages and cultures** (localised and jurisdiction-adapted vault apps).
6. **Implement on the zip model** (release zips; a clean import, version-control, and local-load flow).

Estimated effort: modest, because the hard parts already exist (importable vault apps, vault-of-vaults, the self-contained zip, versioning, OpenRouter credits). The new work is the catalogue/store front, the descriptions, the security-analysis and agent-mapping trust layer, and the billing. The project lead expects it to be relatively simple, given the vault-is-a-zip foundation.

## What This Does Not Try To Be

- **Not heavy distribution infrastructure.** A vault is a zip; the store is the catalogue, trust, and billing around it.
- **Not an unvetted free-for-all.** Security analysis and agent-mapping are part of the trust layer.
- **Not a replacement for vault-of-vaults importing.** It is the marketplace on top of that capability.
- **Not a finished commercial model.** The billing and revenue split are sketched; details are follow-on.

## Honest Risks

**Risk 1: Executable vault apps carry security risk.** A vault app with agents and tool access could be malicious. Mitigation: the security-analysis and agent-mapping trust layer (cross-ref: the SG/Sentinel and security-report work); show what a vault does before import; sandbox on import (cross-ref: the no-origin-iframe and broker model).

**Risk 2: Billing and revenue split need care.** Paying developers fairly and handling payments is non-trivial. Mitigation: the usual store model; start simple; the OpenRouter-credits bundle is a clean first commercial shape.

**Risk 3: Multi-language/culture adds maintenance.** Many localised versions to maintain. Mitigation: developers publish and maintain their own localised versions; versioning handles updates.

**Risk 4: Quality and trust in a marketplace.** A store can fill with low-quality or unsafe vaults. Mitigation: the descriptions, security analysis, agent map, and versioning as trust signals; curation as the store matures.
