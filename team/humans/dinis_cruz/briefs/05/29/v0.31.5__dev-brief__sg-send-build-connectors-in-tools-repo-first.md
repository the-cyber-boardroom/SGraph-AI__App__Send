# Build Connectors In The Tools Repo First: Experiment, Mature, Then Bring Minimal Code To The Vault

**version** v0.31.5
**date** 29 May 2026
**from** Human (project lead)
**to** Developer (lead), Architect, @Dev
**type** Dev brief

---

## What This Is

The implementation methodology for the connectors (Google Drive and the others): **build them as a tool in the tools repo first, experiment and mature them there, and only then bring minimal code back to the vault.** The project lead's strong claim: 90% or more of what is needed can be built and validated in the tool, in the browser, before any vault code is written. This closes the connector series (cross-ref: the v0.31.5 external-data-connectors framework, Google Drive connector, connector-landscape, and connector-OAuth-data-broker briefs) with how to actually build it.

The principle, which runs through the project lead's approach: do not build a lot of code in the vault. Prototype where the plumbing already exists, prove it works, and bring back only the matured, minimal result.

## The Methodology: Tools Repo First

The core: **build the connector as a tool that goes into the tools repo, because the plumbing already exists there and it is the right place to experiment.**

The project lead: **"the way we should implement Google Drive and the others is we should build a tool. Building a tool that goes into the tools repo is the best way to do this, because we already have a lot of plumbing in it. We already have a number of tools integrations, for example accessing Google Photos, uploading to YouTube. There's a whole bunch of properties we already have, so we can put it there and develop it there, and go to town on experiments."**

The tools repo (cross-ref: the tools.sgraph.ai work and the existing integrations) already has:

| Existing Plumbing | Relevance |
|-------------------|-----------|
| Google Photos access | A proven Google integration pattern (OAuth, API) |
| YouTube upload | Another proven integration |
| Other tool integrations | The broader integration plumbing |

So the tools repo is where the connector work belongs first: the OAuth, API, and integration plumbing exists, and it is built for exactly this kind of component. Building the Google Drive connector there reuses that plumbing and produces a usable, testable component, rather than starting cold in the vault.

## Go To Town On Experiments

The reason this matters most: **the tool is where the open questions get answered through experiment, before any vault commitment.** The connector-OAuth and no-origin questions (cross-ref: the v0.31.5 connector-OAuth-data-broker brief, which surfaced the no-origin OAuth blind spot) are exactly the kind of thing to validate experimentally first.

The project lead's list of experiments to run in the tool:

| Experiment | Question |
|------------|----------|
| **Connect to Google Drive** | Can we connect to Drive from the tool? (Almost certainly yes) |
| **Privileges** | What privilege do we need? What do we actually get from each privilege we request? |
| **The iframe** | Can we put an iframe? Can the iframe code access it? |
| **Loading data** | Can we load the data into the iframe? Where does the iframe data come from? |
| **Null origin** | What happens with the null origin? How does that whole thing work? |
| **The connectors and messages** | All the connectors, all the messages back and forth |

The project lead: **"we can do all sorts of assessments, validations, hypotheses: can we connect to Google Drive from the tool, what privilege we need, what we actually get from each privilege, can we put an iframe, can the iframe code access it, can we load the data into the iframe, where does the iframe data come from, what's with the null origin, how does that whole thing work, all those connectors, all the messages back and forth."** These are precisely the questions the data-broker brief raised (the no-origin OAuth issue, where credentials live, how the iframe communicates); the tool is where they get answered with working code rather than analysis. Only when the tool is mature do you bring code to the vault: **"it's only when you have the tool matured that we then look at what we're going to bring and actually add code to the vault."**

## Simulate Everything In The Browser (90%+ In The Tool)

The project lead's strong claim about how much can be done in the tool: **90% or more, including simulating everything, purely in the browser.**

The project lead: **"we don't build a lot of code. In this case, we should be able to create 90% of what we need in the tool, or even more, because we should simulate everything: including a tree view to navigate it, the outer edge talking internally, the internal talking outwards, all those communications, all the monitoring, all the visualisation. All that should happen purely on the browser, on the tool side, where we can make all those experiments, analysis, and validations."**

What gets simulated and validated in the tool, before any vault code:

| Simulated In The Tool | What It Proves |
|-----------------------|----------------|
| **The tree view to navigate it** | The navigation UX over the connector data (cross-ref: the framework brief's tree-abstraction) |
| **The outer edge talking internally** | The connector receiving external data and passing it inward |
| **The internal talking outwards** | The vault-side asking the connector for data outward |
| **All the communications** | The full message flow (cross-ref: the data-broker and bridge briefs) |
| **All the monitoring** | Observing the requests and flows |
| **All the visualisation** | Rendering the connector data |

All of this runs purely in the browser, tool-side. So the entire connector behaviour, the navigation, the inward/outward communication, the monitoring, the visualisation, is built and proven in the tool, and only the matured, minimal result is brought to the vault. This is the do-not-build-a-lot-of-code-in-the-vault principle taken to its limit: the vault gets a small, proven integration, not a large experimental build.

## The Standard Primitives: CRUD As The Abstraction

The key design point that makes this clean: **abstract the connector to a standard set of primitives (create, read, edit, delete/write), so that as you navigate the tree view, the vault does not even need to know what is behind it.**

The project lead: **"the whole point is to abstract this. You need a very standard set of primitives, so as you navigate the tree view, we don't even know what's there. We just need crude mappings from create, read, edit, and delete/write capabilities, because that's what we need to do with the files. And that becomes permissions that get asked or get allowed."**

| Primitive | The File Operation |
|-----------|--------------------|
| **Create** | Create a file |
| **Read** | Read a file |
| **Edit** | Edit a file |
| **Delete / Write** | Delete or write a file |

This CRUD abstraction is what makes connectors uniform: every connector (Google Drive, GitHub, OneDrive) exposes the same create/read/edit/delete primitives, so the tree view navigates any of them without knowing what is behind it. The project lead's point, **"we don't even know what's there,"** is the abstraction working: the vault-side just navigates and issues CRUD operations; the connector (and its broker) translates them to the specific source API. And the primitives map to permissions: each capability (read, write, etc.) is a permission that gets asked or allowed (cross-ref: the connectors framework's read-only/read-write and the data-broker's controls), so the abstraction carries the access control too.

This connects to the data-broker model (cross-ref: the v0.31.5 connector-OAuth-data-broker brief): the iframe that makes the communication, holds the tokens, and has the PKI is what sits behind the CRUD primitives. The project lead: **"including the idea that we have an iframe that makes the communication, and then we talk to the iframe, and it has a PKI and all that jazz. We should be able to do all of this in the tools first, then bring it back to the vault codebase."** So the broker, the CRUD primitives, and the PKI comms are all prototyped and proven in the tool, then brought back.

## Why This Methodology Is Right

The tools-first methodology is right for connectors specifically because:

- **The plumbing exists** (OAuth, API integrations, Google Photos, YouTube) in the tools repo, so prototyping is fast.
- **The open questions are experimental** (the no-origin OAuth, where credentials live, the iframe communication), best answered with working code, not analysis.
- **Almost everything can be simulated in the browser** (the tree view, the comms, the monitoring, the visualisation), so the risk is retired before any vault commitment.
- **It keeps the vault code minimal** (the standing principle), bringing back only the matured, abstracted result.
- **The CRUD abstraction is reusable** across all connectors, so the tool work amortises.

This is the same prototype-where-the-plumbing-is, then-bring-back-minimal-code discipline the project lead applies throughout (cross-ref: the connectors framework's compose-existing-infrastructure and the do-not-add-backend-complexity stance). For connectors it is especially apt, because the experiments are browser-side and the tools repo is built for exactly this.

## What This Asks For

1. **Build the Google Drive connector (and others) as a tool in the tools repo first** (reuse the existing OAuth/API plumbing).
2. **Run the experiments in the tool** (connect to Drive, the privileges, the iframe access, loading data, the null-origin behaviour, the messages).
3. **Simulate everything in the browser** (the tree view, outer-talking-in, internal-talking-out, the comms, the monitoring, the visualisation).
4. **Aim for 90%+ in the tool** (bring only matured, minimal code to the vault).
5. **Abstract to standard CRUD primitives** (create, read, edit, delete/write), so the tree view navigates any connector without knowing what is behind it.
6. **Map the primitives to permissions** (each capability asked or allowed).
7. **Prototype the broker, the iframe comms, and the PKI in the tool** (cross-ref: the data-broker brief), then bring back.
8. **Only bring code to the vault once the tool is mature** (validate first, integrate second).

Estimated effort: low risk and efficient, because it reuses the tools repo's existing plumbing and retires the hard questions experimentally before any vault code. The bulk of the work happens in the tool (where it is cheap to experiment); the vault gets a small, proven, abstracted integration.

## What This Does Not Try To Be

- **Not building in the vault first.** Build in the tools repo; bring back minimal, matured code.
- **Not a lot of vault code.** 90%+ in the tool; the vault gets the small, proven result.
- **Not connector-specific vault logic.** The CRUD abstraction makes connectors uniform; the vault does not know what is behind the tree.
- **Not analysis instead of experiment.** The open questions get answered with working code in the tool.

## Honest Risks

**Risk 1: The tool environment differs from the vault environment.** What works in the tool may behave differently in the vault (especially the null-origin and iframe specifics). Mitigation: simulate the vault's conditions in the tool (the null origin, the iframe comms); the data-broker brief's findings inform this; validate the bring-back.

**Risk 2: The 90%-in-the-tool claim could slip.** Some things may only surface in the vault. Mitigation: simulate as much as possible (the project lead's list); accept that the last 10% (the real vault integration) needs care; the abstraction keeps it small.

**Risk 3: The CRUD abstraction may not fit every source.** Some sources have operations beyond CRUD. Mitigation: CRUD covers the file operations needed; source-specific operations (cross-ref: the Google Drive brief's Picker-vs-API note) are handled in the connector/broker behind the abstraction.

**Risk 4: Tool-built code must be brought back cleanly.** The hand-off from tool to vault could introduce issues. Mitigation: mature the tool first; the abstraction (CRUD, the broker, PKI) is the clean interface to bring back; keep the vault code minimal.
