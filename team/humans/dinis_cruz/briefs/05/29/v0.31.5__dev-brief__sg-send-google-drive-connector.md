# The Google Drive Connector: Drive Inside The Vault, At Least Privilege

**version** v0.31.5
**date** 29 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Dev brief

---

## What This Is

The first concrete external data connector (cross-ref: the v0.31.5 external-data-connectors framework brief): **Google Drive inside the vault.** A button on the left says Google Drive; clicking it shows the user's Drive (or, ideally, just a shared folder) in a custom viewer, navigable like the rest of the vault; the data stays in Google Drive, not the vault. The goal is a better UI on top of Google Drive, with the least-privilege access the project lead wants (ideally just one folder), reachable through the vault.

The driver is direct user feedback: a VC session showed that **a lot of VC sharing and communication happens through Google Drive**, so meeting users there is high-value. The project lead's framing of the platform's strength: **the power is not that we have every feature ready, it is that we move fast and add the bits, so we can go to the environment the user already uses.**

This brief covers the Google Drive connector specifically; the general model is in the connectors framework brief, and the broader connector survey is in the connector-landscape research brief.

## The Vision: Google Drive Inside The Vault, Transparently

The project lead's target experience: **Google Drive appears inside the vault, transparently, the same way vault-in-vault works.**

The project lead: **"I would like the equivalent of what we've done with the vault-in-vaults. It's almost like Google Drive inside Vault. How can we make it transparent, so when I'm browsing Google Drive I just get a little button on the left that says Google Drive? And the data is not stored in the vault, the data is stored in Google Drive. Can we create a better UI to manage Google Drive?"**

So the experience is:

- **A Google Drive button on the left** (alongside the vault's own navigation).
- **Click it and see Drive** (in a custom viewer, navigable like vault content).
- **The data stays in Google Drive** (the vault accesses it, does not store it).
- **A better UI on top of Drive** (the vault's UI, the eventual chat, the navigation, layered on the user's Drive).

This is the connector model (cross-ref: the framework brief) for Google Drive: a custom viewer (not a frame of Drive, which Drive blocks), an app-in-iframe holding the OAuth credentials, the vault talking to it through the bridge, and the Drive data rendered in the vault's UI, ideally abstracted into the tree.

## Least Privilege: Can We Ask For Just One Folder?

The most important question the project lead raised, and the one needing research: **can we access only the specific folder shared, rather than the whole Drive?**

The project lead: **"my ideal situation is that we almost don't access, the only privilege we ask for is literally just the files we're supposed to see. Is it possible to just ask for a particular folder? Is it possible to say all we need is a particular folder? We can store that folder ID in the vault itself."**

The research answer is yes, and it is the recommended Google approach.

### The Finding: drive.file Plus The Google Picker API

Google explicitly recommends narrow, per-file access over broad Drive access, and provides two non-sensitive mechanisms that give exactly the least-privilege model the project lead wants:

| Mechanism | What It Grants | Sensitivity |
|-----------|----------------|-------------|
| **`drive.file` scope** | Per-file access: only files the user opens with the app or shares with the app via a picker | Non-sensitive (recommended) |
| **The Google Picker API** | A JavaScript file/folder picker (a modal with the Drive look and feel) that lets the user select specific files or folders, granting the app access to only those | Used with `drive.file` |
| **`drive.appdata` / `drive.appfolder`** | The app's own hidden config folder (not the user's files) | Non-sensitive |

Google's own guidance is that an app whose features are limited to specific files the user picks **should not request a broad-access Drive scope**; it should use `drive.file` (and the Picker API), which is non-sensitive and grants per-file access. This is precisely the project lead's ideal: the app sees only what the user selects, not the whole Drive.

So the least-privilege model for the Google Drive connector is:

1. The user authenticates with the **`drive.file`** scope (non-sensitive, per-file).
2. The user selects the folder (or files) to share via the **Google Picker** (the Drive-like modal).
3. The app gets access to only the selected folder/files, nothing else in the Drive.
4. The vault **stores the folder ID** (the reference) so it can return to that folder, exactly as the project lead proposed.

This means the connector never requests broad Drive access; it asks for nothing until the user picks a folder, and then sees only that. It is the cleanest possible answer to the project lead's least-privilege goal, and it is the Google-recommended path (narrow scopes get readier user consent and avoid the broad-access review burden).

### A Caveat To Note

One honest caveat from the research: the Google Picker is for selecting and granting access; it does not itself let the app organise, move, or copy files between folders (those operations need the Drive API or the Drive UI). For the connector's browse-and-view purpose this is fine; for read-write management operations, the connector uses the Drive API on the files the user has granted via the picker. Also, client-side OAuth for Drive is well supported (Google explicitly supports JavaScript browser apps), which fits the browser-API requirement of the connector model.

## Storing The Reference In The Vault

Per the project lead, **the vault stores the folder ID (and the connector config), not the Drive data.** The project lead: **"we can store that folder ID in the vault itself."** So the vault holds:

| Stored In The Vault | Not Stored In The Vault |
|---------------------|-------------------------|
| The folder ID (the reference) | The Drive files themselves |
| The connector config (scope, access level) | The file contents |
| Possibly the OAuth token reference (handled per the auth model) | |

This is the no-storage principle of the connector model (cross-ref: the framework brief): the vault remembers which folder to show and how to access it, and the data stays in Drive. The folder ID stored in the vault is what lets the connector return to the right folder on each visit.

## The Sharing Question

The project lead raised the sharing workflow as needing thought: **how does sharing work, and could we give a particular Google account access?**

The project lead: **"the logic is that user A shares a folder with user B. How do we do this from a sharing point of view? How can we maybe give a particular Google account access to it?"** Two sharing dimensions are in play:

| Sharing Dimension | Detail |
|-------------------|--------|
| **Drive-side sharing** | The folder owner shares the Drive folder (Drive's own sharing); the connector then accesses it via the picker/scope |
| **Vault-side sharing** | The connector reference (the folder ID and config) is shared via the vault's own sharing (cross-ref: the authentication brief's vault-key sharing) |

The interaction between the two needs mapping: when a vault with a Drive connector is shared, the recipient needs both the vault reference and their own Drive access to the folder (or the folder must be shared with them in Drive). The project lead flagged this as something to understand better; the brief records it as an open question rather than fixing a design. The clean model is likely: the vault shares the reference; each user authenticates their own Drive access (least-privilege, via the picker) to the shared folder, so no Drive credentials are shared, only the reference.

## How Much Workflow In Drive Versus The Vault

A scoping question the project lead raised: **how much of the workflow happens in Drive versus in the vault, and what we actually ask for.** The project lead: **"it depends how much of the workflow we actually do in Google Drive and how much we do in the vault, and what we ask for in terms of access."** The least-privilege answer shapes this: because the connector asks only for the picked folder, the heavy workflow (organising, broad management) can stay in Drive, while the vault provides the better UI for viewing, navigating, and (eventually) chatting about the folder's contents. The connector does not need to replicate Drive's full management; it needs to view and work with the shared folder well.

## What This Asks For

1. **Build the Google Drive connector** as the first connector (cross-ref: the framework brief's model).
2. **Use the least-privilege approach**: the `drive.file` scope plus the Google Picker API, so the app sees only the folder/files the user picks.
3. **Store the folder ID and config in the vault** (the reference, not the data).
4. **Build a custom Google Drive viewer** (not a frame; Drive blocks framing), rendering the folder in the vault UI, ideally abstracted into the tree.
5. **Use the app-in-iframe-with-credentials model** (the iframe holds the Drive OAuth; the vault talks to it via the bridge; not cached).
6. **Add the Google Drive button on the left** (the transparent entry point).
7. **Map the sharing workflow** (Drive-side sharing plus vault-side reference sharing; each user authenticates their own least-privilege Drive access).
8. **Keep heavy management in Drive** (the connector views and works with the shared folder; it does not replicate Drive).

Estimated effort: moderate, and de-risked by the research. The least-privilege path (`drive.file` plus Picker) is the Google-recommended, well-supported, client-side-friendly approach; the custom viewer is rendering plus the Drive API; the app-in-iframe and bridge already exist. The sharing workflow is the main design question to settle.

## What This Does Not Try To Be

- **Not broad Drive access.** Least privilege via `drive.file` plus the Picker; only the picked folder.
- **Not Drive storage in the vault.** The folder ID is stored; the data stays in Drive.
- **Not a frame of Drive.** A custom viewer (Drive blocks framing).
- **Not a full Drive replacement.** Heavy management stays in Drive; the connector views and works with the shared folder.

## Honest Risks

**Risk 1: Sharing across Drive and the vault is the tricky part.** Reconciling Drive-side sharing with vault-side reference sharing needs care. Mitigation: each user authenticates their own least-privilege Drive access to the shared folder; the vault shares only the reference; map the workflow before building.

**Risk 2: The Picker grants access on selection, which is a per-user step.** Each user must pick the folder to grant access. Mitigation: this is the least-privilege cost and is acceptable (it is one selection); store the folder ID so it is a one-time step per user.

**Risk 3: Read-write management is limited via the Picker alone.** The Picker selects; management uses the Drive API. Mitigation: use the Drive API (on the granted files) for read-write; the connector's core purpose (view/navigate) needs only read.

**Risk 4: Dependence on Google's API and policies.** The connector depends on Drive's API and scope policies. Mitigation: the non-sensitive `drive.file` path avoids the broad-access review burden; isolated viewer (a break loses access, not data); monitor API changes.

## Open Questions

| Question | Notes |
|----------|-------|
| Exact sharing model (Drive-side plus vault-side)? | Likely: share the reference; each user authenticates their own least-privilege access |
| Read-only first, or read-write from the start? | Read (view/navigate) first; read-write via the Drive API later |
| How is the folder ID and config stored and refreshed? | In the vault (the reference); OAuth refresh in the iframe |
| Tree-abstracted, or its own viewer first? | Its own viewer first; tree-abstraction as the deeper integration |
| How does the Picker step fit the UX? | A one-time folder selection per user; store the ID after |
