## What This Is

A strategic analysis: where do AWS Nitro Enclaves fit in the SG/Send, SG/Vault, and SG/Compute ecosystem, and specifically: **can we put our most confidential data (vault keys, possibly decrypted vault content) inside an enclave to open up use cases that currently require trusting our infrastructure?**

The companion research brief describes what Nitro Enclaves are technically. This brief reads them against our current zero-knowledge architecture and identifies the seams where they extend our story into new product surfaces.

The core insight is direct: we currently hold customer data in zero-knowledge encrypted vaults, which is good but limiting. Customers do everything client-side because the alternative (trusting our servers with plaintext) is unacceptable for the high-trust use cases we care about. Nitro Enclaves offer a third path: **we can process data server-side without ever being able to see it ourselves**, because the enclave is cryptographically sealed against even root on our parent EC2 instance. This expands what we can offer without breaking the zero-knowledge contract.

## The Current Zero-Knowledge Story

Today's architecture:

| Boundary | What Crosses It |
|----------|----------------|
| **Client browser** | Plaintext content; keys derived from the user's vault key |
| **Network** | Encrypted content only; we never see plaintext |
| **Our S3** | Encrypted content only; we hold ciphertext |
| **Our compute** | Encrypted content; the metadata around it; never the plaintext |

This is genuinely zero-knowledge: even if our entire AWS account is compromised, customer plaintext is not exposed. The vault key never leaves the client.

The cost of this design: **anything that benefits from server-side processing is impossible or awkward**. Server-side search over encrypted content, server-side AI inference on customer data, server-side transformations, server-side validation; all require either client-side computation (often slow or impractical) or breaking the zero-knowledge contract (unacceptable for high-trust use cases).

Nitro Enclaves change the calculus.

## The Enclave-Enabled Position

With enclaves, we can introduce a fourth boundary:

| Boundary | What Crosses It |
|----------|----------------|
| **Client browser** | Plaintext content; keys derived from the user's vault key |
| **Network** | Encrypted content only |
| **Our S3** | Encrypted content only |
| **Our compute (parent EC2)** | Encrypted content; never plaintext |
| **Our enclaves** | Plaintext content **but only inside an attested enclave running code the customer can verify** |

The new property: **plaintext can exist server-side, but only inside a cryptographically sealed environment running code whose hash is published and auditable**. We extend the zero-knowledge contract from "we cannot see your plaintext" to "we cannot see your plaintext, and we can prove cryptographically what server-side code did process it."

This is a stronger story than just "we cannot see your data." It is "here is the exact code that processed your data, here is the cryptographic proof it was that code, and here is the integration with KMS that ensures only that code could access the keys."

## The Three-Tier Vault Key Architecture

The most useful concrete pattern: a three-tier key architecture that lets us do server-side work without holding the underlying secrets.

### Tier 1: Customer's Vault Key (Client-Side Only)

The root key derived from the customer's password or other client-side material. Never leaves the client. Used to decrypt the customer's master vault key.

This is unchanged from today.

### Tier 2: Vault Decryption Inside Enclave

When the customer wants server-side work performed on their vault, they:

1. Send their vault encryption key to the enclave (over an attested channel)
2. The enclave proves its identity to the customer via attestation (PCR values verifiable against the open-source enclave image)
3. The customer encrypts the vault key under the enclave's ephemeral public key (from the attestation document)
4. Only the enclave can decrypt; the parent never sees the vault key

The customer's vault key now lives in enclave memory for the duration of the session. The parent EC2 instance cannot read it. We cannot read it. The enclave can use it to decrypt vault content.

### Tier 3: KMS-Wrapped Service Keys

For service-level keys that we manage (the keys used by SG/Compute itself, the credential manager's keys, the platform's own signing keys), KMS-attested policies ensure:

- Only specific enclave images (verified by PCR0) can decrypt these keys
- Even if the parent EC2 is fully compromised, the keys cannot be unwrapped
- Key rotation does not require re-attestation if the enclave image is signed (PCR8-based policies)

This is the standard Nitro Enclaves + KMS pattern, applied to our service keys.

The architecture means **even we cannot decrypt our own most-sensitive service keys without running an enclave with the right measurements**. This is a clean compliance story.

## What Enclaves Unlock: New Product Surfaces

Now to the substantive question: what new use cases become possible with enclaves in our stack?

### Use Case 1: Server-Side Vault Search

**The problem today:** Searching encrypted vault content requires either client-side search (download everything, search locally) or breaking encryption (server sees plaintext). Both are bad.

**With enclaves:** Customer sends their vault key to an attested enclave; the enclave decrypts the customer's vault content, builds a search index, holds it in memory, accepts encrypted query requests. The search index never persists; the plaintext never leaves the enclave.

**Why this is valuable:** It is the missing feature most customers ask about. Server-side search over encrypted data without trust compromise.

**Pricing implication:** Per-session enclave time. Customers pay for the time their vault is decrypted in the enclave. Falls neatly into the pre-auth + micropayments substrate.

### Use Case 2: Server-Side AI Inference Over Vault Content

**The problem today:** Customers who want LLM-powered features (summarisation, semantic search, generation grounded in their content) either upload to a third-party LLM (privacy compromise) or do it client-side (slow, limited).

**With enclaves:** An enclave decrypts the customer's vault content, sends it to an LLM provider via the parent (but using attested-server-mediated calls), returns the result. Even better: with AgentCore Browser or Code Interpreter integration via vsock proxy, the enclave can run agentic workflows over the decrypted vault.

**The key trick:** the LLM provider sees plaintext (it has to, to do inference), but they see it briefly, without persistence (provider-side commitment), and the rest of our infrastructure does not. The trust boundary expands by exactly one (the LLM) and only for the inference window.

**Why this is valuable:** Unlocks LLM features for high-trust customers (legal, medical, financial) who would never accept us seeing their plaintext. The enclave guarantees that we (the platform) do not; the LLM trust boundary is one the customer can audit separately.

**Pricing implication:** Enclave-hour + LLM-token cost, both metered through pre-auth.

### Use Case 3: Multi-Party Vault Computations

**The problem today:** Two parties (e.g., two doctors collaborating on a case, two firms doing diligence) cannot jointly process their combined data without one of them seeing the other's. End-to-end encryption protects each one's data from us but not from each other.

**With enclaves:** Both parties encrypt their data to the enclave's ephemeral public key. The enclave decrypts both inputs, computes the result, returns it to both parties (encrypted under their respective keys). Neither party sees the other's input; we never see either input.

This is the "multi-party computation" use case AWS specifically cites for Nitro Enclaves. We can productise it.

**Why this is valuable:** Opens an entire category of collaborative-but-private workflows: due diligence, medical second opinions, joint analyses, contract negotiations, supplier comparisons.

**Pricing implication:** Per-computation enclave time, possibly with a coordination fee for the multi-party setup.

### Use Case 4: Verifiable Vault Operations (Audit Trail With Code Identity)

**The problem today:** When a customer asks "what did your platform do to my data?", we can show vault commit history but cannot cryptographically prove which exact code touched the data.

**With enclaves:** Every sensitive operation runs inside a signed enclave with known PCR values. The vault commit records the PCR0 of the enclave that performed each operation. Auditors can verify: "This commit was made by enclave-image-version-X, here is its source, here is the build that produces PCR0 = Y, here is the AWS attestation log confirming that PCR0 ran."

This is a step beyond vault audit trails: not just "what happened" but "what specific verified code made it happen."

**Why this is valuable:** Regulated industries that need to prove not just what was done but by what code. Insurance, banking, certain government workflows. The compliance posture is meaningfully different.

**Pricing implication:** Premium tier for verifiable-operation vaults; same substrate.

### Use Case 5: Server-Side Signing With Customer-Held Keys

**The problem today:** If we want to sign things on a customer's behalf, they have to either give us their private key (compromise) or sign client-side (limits use cases like server-initiated workflows).

**With enclaves:** Customer's signing key is sealed inside an enclave under their control (attestation document available to the customer; they encrypt the key to the enclave's ephemeral public key). The enclave performs signing operations; the parent forwards requests and responses; the key never leaves the enclave.

Critically, **the customer can verify which code is signing**. They check the enclave's PCR values against published values; they trust the signing because they trust the code.

**Why this is valuable:** Enables server-initiated workflows (scheduled signings, automated approvals, webhook-triggered signatures) without compromise. Unlocks classes of workflow we cannot currently offer.

**Pricing implication:** Per-signature, with the enclave-time amortised across signatures within a session.

### Use Case 6: Confidential Credential Manager

**The problem today:** Yesterday's credential manager vault stores API keys encrypted, but at some point those keys exist in plaintext when used (proxy-mode requests still decrypt before forwarding). If our parent EC2 is compromised, in-flight credentials are exposed.

**With enclaves:** The credential manager's proxy mode runs inside an enclave. Decryption happens in the enclave; the upstream call is made via vsock proxy to the upstream provider. The key never exists in plaintext on the parent.

This significantly hardens the credential manager. Combined with PCR-based KMS policies, the master keys for the credential vault are themselves only usable by the credential manager enclave.

**Why this is valuable:** Compliance posture for the credential manager goes from "we hold encrypted keys" to "we hold encrypted keys that even we cannot decrypt without a specific verified enclave running." Major for security-sensitive customers.

**Pricing implication:** Folds into existing credential manager pricing; minor incremental cost.

### Use Case 7: Vault Encryption Operations On Customer's Behalf

**The problem today:** When a customer wants to share a vault snapshot with another user, the re-encryption (re-wrapping the data keys under the recipient's public key) happens client-side. This is fine but limits async workflows.

**With enclaves:** The customer's vault decryption key is briefly held in an enclave; the enclave re-wraps the data keys under the recipient's public key (which the customer provided); returns the re-wrapped vault. The customer can be offline during this process.

**Why this is valuable:** Enables vault sharing workflows that are async (background processing, scheduled delivery, multi-recipient broadcasts) without compromising the zero-knowledge property.

**Pricing implication:** Per-operation, minor.

## The Architectural Pattern That Recurs

Across these use cases, a single pattern recurs:

```
1. Customer encrypts something (vault key, signing key, payload) to the enclave's
   ephemeral public key from a verified attestation document.
2. The enclave processes the plaintext in memory only.
3. The enclave returns results to the customer encrypted under the customer's key.
4. The parent EC2 instance never sees plaintext; we never see plaintext.
5. The enclave terminates; in-memory state vanishes.
```

This is a single pattern with many applications. The work to support it is shared across all use cases above; the productisation is differentiating each one.

## What Lives Inside The Enclave, And What Doesn't

A clear separation matters:

### Inside The Enclave

- Customer vault keys during a processing session
- Decrypted vault content during processing
- Service signing keys when used
- Credential manager master keys when used
- In-memory search indexes over decrypted content
- Multi-party computation inputs

### On The Parent EC2 (Not Inside Enclave)

- Encrypted vault content
- The metadata and routing layer
- The vsock proxy
- API request handling
- Pre-auth payment metering (the events, not the key material)
- Audit log writing (the commits, not the plaintext)

### In S3 / Storage

- Encrypted vaults
- Audit logs
- Configuration

The pattern: **the enclave holds the minimum sensitive working set; everything else stays in our usual stack**. This minimises both the enclave attack surface and the operational footprint.

## How This Composes With Other 2026 Pieces

### With AgentCore (Today's Other Research)

AgentCore Runtime is microVM-isolated but not enclave-grade. They serve different threat models:

- **AgentCore** isolates customers from each other; AWS can still see the data; the threat model is "other tenants."
- **Nitro Enclaves** isolate the customer from us; AWS cannot see the data; the threat model is "the platform operator."

These compose well. **AgentCore Runtime can run inside an enclave-protected workflow**: the enclave holds the decryption key and the orchestration; AgentCore Runtime handles specific tool invocations on the parent. For most agents, AgentCore alone is enough. For high-trust agents (medical agents, financial agents, legal agents), the enclave adds the platform-operator threat-model layer.

### With Pre-Auth Payments

Enclave time is a meterable resource. Pre-auth payments (yesterday's brief) charges per enclave-hour. Customers see exactly how much enclave-time they used. This is the same metering pattern as the rest of the platform; enclaves are just another substrate billed through the same rail.

### With Vault Collections

Vault collections (the zip-as-vault primitive) can include enclave image identifiers in their manifest: "this vault must only be opened by enclave image PCR0 = Y." The vault carries its own access policy expressed as enclave attestation requirements.

### With The Density Modes

The fourth density mode emerges: **enclave-protected dedicated EC2**. Higher cost (dedicated EC2 + the operational complexity of enclaves) but cryptographic isolation from the platform operator. The tier above "dedicated EC2" in the density spectrum.

### With Container Hosts

Container hosts (today's brief) provide our own EC2 substrate for ephemeral workloads. They can be enclave-enabled. The host that runs untrusted-from-platform-operator workloads runs them inside enclaves; the host that runs trusted workloads runs them as regular containers. Same primitive, different security tier.

## The Customer-Facing Position

The position becomes:

> "On SG/Send, your data is end-to-end encrypted with zero-knowledge: we cannot see your plaintext, full stop. When server-side processing is useful (search, AI, signing, collaboration), it happens inside Nitro Enclaves whose code is open source, signed, and cryptographically verified before they can access your keys. We can prove which code processed your data, and so can you."

This is a meaningfully stronger position than the current one, and a meaningfully stronger position than the typical "we encrypt at rest and in transit" SaaS pitch. It is also a position competitors with bigger engineering teams have not built.

## Operational And Cost Realities

A few honest constraints:

### EC2 Cost, Not Serverless

Enclaves require a dedicated EC2 parent. This is the substrate-cost trade-off: cheaper than Kubernetes overhead but more expensive than serverless. Enclave-using workloads are best when sessions are long enough to amortise startup, or when multiple operations share an enclave session.

### Operational Complexity

Building and deploying enclaves is more involved than running plain Lambda or Fargate. Signed EIFs, PCR-based KMS policies, vsock proxies, attestation flows. The CLI primitives we have been building (today's `sg-compute aws X` pattern) can hide most of this, but it is real work.

### Recovery And State

Enclaves have no persistent state. If an enclave dies, its in-memory keys vanish (which is the security property, but operationally means the customer's session needs to re-establish trust). Need to plan for graceful recovery and for the customer experience of "your enclave session ended, please re-attest."

### Performance For I/O-Heavy Workloads

Streaming gigabytes through an enclave is expensive due to vsock overhead. The pattern works best for high-CPU low-I/O workloads (crypto, signing, in-memory search). For high-I/O workloads (bulk transformations), the architecture needs care.

### The Open-Source Commitment

The strongest version of the customer-facing position requires that **our enclave images are open source**. Customers need to be able to verify what code we are running. This is a commitment that has implementation cost (auditable build pipelines, published PCR values, signed releases) but a meaningful competitive moat once made.

## What This Asks For

Concrete next steps:

1. **Validate the threat model and use-case prioritisation.** Which of the seven use cases above is the first to build?
2. **Prototype the "enclave-protected vault decryption" primitive.** This is the foundation; everything else builds on it.
3. **Establish the open-source enclave image release process.** PCR values published; build pipeline auditable; signing certificate managed.
4. **Update the density mode framework** to include enclave-protected as a fourth tier.
5. **Add enclave CLI commands to SG/Compute** (`sg-compute aws nitro-enclaves run --eif ...` etc.) following the established pattern.
6. **Bake an SG-vault-enclave EIF** as the first reusable image: takes a vault encryption key, decrypts content from S3, exposes a vsock API for read/write/search operations.
7. **Write a customer-facing position paper** that explains the architecture and what it unlocks.
8. **Decide pricing tier** for enclave-protected workloads vs standard zero-knowledge workloads.

This is significant work: probably 2-3 months for the first production-usable primitive plus one prioritised use case. But it is a moat that few competitors will replicate.
