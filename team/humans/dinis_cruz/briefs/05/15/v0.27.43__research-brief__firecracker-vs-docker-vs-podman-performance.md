## What This Is

A focused research brief on the question: **assuming Firecracker works on our nested-virt EC2 instances, would it actually start faster and use fewer resources than Docker or Podman containers running on the same Linux VM?**

The short answer is more interesting than "yes" or "no": **it depends on the comparison, and the intuition most people start with is wrong**. This brief sorts out what is actually true, with measured numbers from the 2025-2026 published benchmarks.

The headline findings up front:

1. **Cold-start Docker containers are faster than cold-boot Firecracker microVMs**, not slower. Containers start in tens of milliseconds; Firecracker boots a kernel in ~125ms. The container-is-slower intuition is backwards.
2. **Snapshot-restored Firecracker is faster than cold Docker**, often by an order of magnitude. This is where Firecracker actually wins on startup time.
3. **Memory overhead is roughly comparable** for the runtime overhead itself, but the comparison is more subtle than it appears because the Firecracker microVM has to include a kernel.
4. **Podman is the most resource-efficient container runtime** in 2026, with no daemon and a smaller idle footprint than Docker.
5. **For our use cases**, the right comparison is not Firecracker vs containers in isolation; it is Firecracker-with-snapshots vs containers-with-something-pre-warmed, where the answer depends on what specifically we are optimising for.

## Why The Question Is Worth Asking Carefully

The Firecracker community's marketing emphasises "125ms boot time" and "less than 5 MiB memory overhead per microVM." Read quickly, those numbers sound dramatically better than containers.

But containers are not slow. A Docker container starts in **tens of milliseconds** (typically 50-200ms depending on image size and warm-state). A Podman container is comparable or slightly faster on memory-constrained hosts. The relevant comparison for us is not "VM vs container at all" but "what does each give us for the workloads we actually run?"

The question matters because of what we are considering: running our SG vault app and other workloads in our own container hosts primitive (today's brief), possibly with Firecracker as the substrate. The answer determines whether Firecracker is a faster or slower runtime than Docker/Podman for what we do.

## Startup Time: The Cold-Start Numbers

Published benchmarks from 2025-2026:

| Runtime | Cold-Start Time | Source |
|---------|----------------|--------|
| **Docker container** | ~150ms typical (~50-200ms range) | Multiple 2025-2026 benchmarks; Northflank, Uptrace, Morph |
| **Podman container** | ~180ms typical (~12-15% slower than Docker for individual operations) | Uptrace 2025 |
| **Firecracker microVM cold boot** | ~125ms to user-space code | Firecracker GitHub, multiple sources |
| **Firecracker microVM with optimal minimal kernel** | ~100ms achievable | Oblien sub-200ms breakdown |
| **Firecracker snapshot restore (L1 cache)** | ~1ms per 512KB chunk | AWS Lambda SnapStart documentation |
| **Firecracker snapshot restore (L2 cache)** | ~single-digit ms per 512KB chunk | AWS SnapStart |
| **Lambda SnapStart total cold start (Java)** | ~150-700ms (vs 6+ seconds without) | AWS production data |
| **Lambda SnapStart total cold start (.NET)** | ~700ms P90 (vs 1,680ms without SnapStart) | AWS .NET benchmark |
| **Kata Containers (VM-isolated container)** | ~150-300ms | Onidel 2025 |
| **gVisor (user-space kernel)** | ~50-100ms | Onidel 2025 |

The non-obvious takeaways:

- **Docker and Firecracker are in the same order of magnitude on cold start.** Firecracker is slightly slower than Docker; this is widely confirmed.
- **Snapshot-restore Firecracker is 10-100x faster than cold Firecracker.** This is where the headline "millisecond" numbers come from.
- **Snapshot-restore is currently the strongest argument for Firecracker over containers.** It is not the cold-boot path that wins; it is the warm-pool path.
- **Lambda SnapStart numbers are real-world Firecracker snapshot data.** AWS achieves single-digit-millisecond chunk restores in production; total cold starts drop by 90%+.

If our workload is "one shot, no pre-warming, plain image," **Docker wins on startup**. If our workload is "many instances of the same base image, can pre-snapshot once and restore many times," **Firecracker wins by an order of magnitude**.

## Memory: The Resource Picture

The classic Firecracker number is "<5 MiB memory overhead per microVM." This is the VMM process overhead, not the total memory cost. The total picture for a running workload:

| Component | Firecracker microVM | Docker Container | Podman Container |
|-----------|---------------------|------------------|------------------|
| **VMM/runtime overhead** | ~5 MiB | ~10-50 MiB (Docker daemon shared) | ~0 MiB (no daemon) |
| **Guest kernel (microVM only)** | ~30-80 MiB depending on config | N/A (uses host kernel) | N/A (uses host kernel) |
| **Init system / minimal user space** | ~5-30 MiB depending on what's in the image | Minimal beyond container's own processes | Minimal beyond container's own processes |
| **Application memory** | Whatever the app uses | Whatever the app uses | Whatever the app uses |

So for a workload that needs (say) 256 MiB of application memory:

- **Firecracker microVM**: ~290-340 MiB total (5 VMM + 30-80 kernel + minimal init + 256 app)
- **Docker container**: ~280-310 MiB total (~25-50 MiB shared daemon amortised across containers + 256 app)
- **Podman container**: ~260-280 MiB total (~0 daemon + minimal overhead + 256 app)

For a single workload, the differences are small. The picture shifts at scale:

- **Many containers (Docker)**: The daemon overhead is shared across all containers. At 50 concurrent nginx containers, Docker uses ~15-20% more total memory than Podman per published benchmarks (Morph 2026).
- **Many containers (Podman)**: No daemon. Each container is just its own processes. Linear memory scaling.
- **Many microVMs (Firecracker)**: Each microVM has its own kernel. Kernel-deduplication via KSM (Kernel Same-page Merging) helps but does not eliminate the per-VM kernel cost. Still, the overhead is bounded and predictable.

The headline "5 MiB per microVM" is correct **for the VMM process**, but the realistic per-microVM memory cost when including the kernel is more like **30-100 MiB depending on configuration**. This is still excellent but not the fairy-tale number the marketing implies.

**Podman is the lightest at idle** (no daemon). Firecracker is in the middle. Docker is heaviest at idle but the gap is small per-container at scale.

## CPU: The Runtime Picture

CPU overhead is harder to measure cleanly because it depends on the workload mix. Published findings:

| Comparison | Finding |
|-----------|---------|
| Docker vs Podman | Within 2-4% of each other for compute-bound work; Docker slightly faster on individual operations; Podman more efficient at idle. |
| Containers vs Firecracker for CPU-bound work | Near-equivalent. Firecracker adds ~1-3% virtualization overhead. |
| Containers vs Firecracker for I/O-bound work | Containers faster. Firecracker's vsock and virtio-net introduce noticeable overhead vs container networking. |
| Memory-bound workloads on virtualized vs bare-metal Firecracker | Nested virtualization (C8i etc.) adds another 10%+ overhead vs bare-metal Firecracker. |

**For our nested-virt scenario specifically**, the layering is:

```
L0: AWS Nitro Hypervisor (on physical hardware) → AWS handles
L1: Our C8i EC2 instance (KVM) → we run this
L2: Firecracker microVMs inside the EC2 instance → we run these
```

The L2 microVMs pay the full nested-virt tax. Containers in L1 do not. This means **for raw CPU performance on C8i/M8i/R8i, containers will be measurably faster than Firecracker microVMs** running on the same EC2 instance.

This is a non-trivial point that the Perplexity research hinted at ("AWS still recommends bare metal for performance-sensitive workloads") and the Firecracker community has measured: ~10%+ slowdown for nested-virt Firecracker vs bare-metal Firecracker for CPU-bound work. Bigger for I/O-heavy work.

## The Nuanced Picture For Our Workloads

For each of our likely workload types, the comparison comes out differently:

### Workload 1: SG Vault App Hosting (Long-Running, Single-Vault)

- **Container (Docker/Podman)**: Starts in ~150ms; runs at native speed; ~280 MiB for a typical vault app.
- **Firecracker microVM**: Cold-boots in ~125-200ms (slightly slower on nested-virt); runs at ~95% of container speed (nested-virt tax); ~310-340 MiB for the same vault app (kernel overhead).
- **Snapshot Firecracker**: Restore in single-digit ms; runs at same ~95% steady-state.

**Verdict**: For long-running vault hosting, **containers are slightly faster and use slightly less memory**. Firecracker offers no startup advantage (the workload is long-running) and pays a small steady-state tax. **Containers win for this workload class.**

### Workload 2: Ephemeral Per-Request Vault Operations (Short-Lived, Many Instances)

- **Container (Docker/Podman)**: Each request spins up a fresh container in ~150ms; tears down; ~280 MiB while running. Per-request overhead: low.
- **Firecracker microVM (cold boot)**: Each request boots a fresh microVM in ~125-200ms (nested-virt tax included); tears down; ~310-340 MiB while running. Per-request overhead: slightly higher.
- **Firecracker microVM (snapshot restore)**: Restore from a snapshot in single-digit ms; runs the request; tears down. Per-request overhead: **dramatically lower**.

**Verdict**: For ephemeral per-request workloads, **Firecracker with snapshots is the fastest path** if we can engineer the snapshot lifecycle correctly. **Firecracker wins for this workload class, but only with snapshots in play.**

### Workload 3: AI Agent Code Execution Sandbox (Untrusted Code Per Execution)

- **Container (Docker/Podman)**: Shares host kernel. A kernel exploit from inside the container compromises the host. NIST SP 800-190 explicitly identifies container escapes as a major risk.
- **Firecracker microVM**: Hardware-level isolation. Kernel exploits inside the microVM stay inside the microVM. This is the standard substrate for AI sandboxes in 2026 (Morph's "sbx", Northflank's sandboxes, etc.).

**Verdict**: For untrusted code execution, **containers are unsafe and Firecracker is the right substrate**. The startup-time question is secondary; the isolation question dominates. **Firecracker wins for this workload class on security grounds, regardless of startup-time comparison.**

### Workload 4: Multi-Region Playwright Test Fleet (Parallel Browser Sessions)

- **Container (Docker/Podman)**: Each Playwright session in a container. Cold start ~150ms plus Playwright initialization (~2-3 seconds typically). Resources ~500-700 MiB per browser.
- **Firecracker microVM (cold boot)**: Each session in a microVM. Cold boot ~150ms plus Playwright init. Comparable total time.
- **Firecracker microVM (snapshot restore from "Playwright ready" state)**: Restore from a snapshot where Playwright is pre-initialized. Single-digit ms plus first-request time. **Dramatically faster.**

**Verdict**: For Playwright fleets, **Firecracker with snapshots is dramatically faster** if we can snapshot a "Playwright ready" state and restore many times. Containers cannot match this; container snapshots exist (CRIU and similar) but are not as integrated. **Firecracker with snapshots wins for this workload class.**

### Workload 5: Multi-Tenant Vault Hosting (Many Customers' Vaults On Shared Infrastructure)

- **Container (Docker/Podman)**: Multiple vaults per host share a kernel. Container escape would compromise multiple vaults. Acceptable for non-regulated workloads; risky for regulated.
- **Firecracker microVM**: Each vault in its own microVM with its own kernel. Hardware-level isolation. Standard pattern for multi-tenant SaaS.

**Verdict**: For multi-tenant hosting, the answer depends on the trust model. **Containers are sufficient for trusted-customer workloads; Firecracker is the right answer for regulated or hostile-tenant workloads**. This maps to our existing density modes (multi-vault per app is containers; isolation-sensitive is Firecracker-shaped).

## The "It Depends" Summary Table

Plain comparison across the dimensions that matter:

| Property | Docker Containers | Podman Containers | Firecracker (cold boot) | Firecracker (snapshot) |
|----------|-------------------|-------------------|--------------------------|--------------------------|
| **Cold-start time** | ~150ms | ~180ms | ~125-200ms (nested-virt) | **~single-digit ms** |
| **Memory overhead per workload** | ~25-50 MiB amortised + app | **~0 daemon + app** | ~30-100 MiB (kernel) + app | ~30-100 MiB + app |
| **Idle resource footprint** | Daemon always runs | **None** | None per microVM | None per microVM |
| **CPU speed (steady state)** | ~native | ~native | ~95-97% native on nested-virt | Same as cold boot |
| **Isolation strength** | Shared kernel | Shared kernel | **Hardware-level (KVM)** | Hardware-level |
| **Multi-tenant safety** | Risky for untrusted | Risky for untrusted | **Safe** | Safe |
| **Image ecosystem** | **Massive (OCI)** | Massive (OCI compatible) | EIF (rebuildable from container images via firecracker-containerd) | Same |
| **Operational complexity** | Low | **Low** | High (build orchestration) | Higher (manage snapshots too) |
| **Cost on C8i-flex.large** | ~$0.09/hr | ~$0.09/hr | ~$0.09/hr + engineering | Same |
| **At-scale memory efficiency** | Daemon overhead amortised | **Best (no daemon)** | Kernel overhead per VM | Same |

No single runtime wins on all dimensions. The answer for any given workload depends on which dimensions matter most.

## What Snapshot Restore Actually Buys Us

Snapshot restore is the single most important Firecracker capability for our purposes, so worth a focused look.

**Without snapshots**, every Firecracker microVM startup pays the full cost: VMM init, kernel boot, init system, application startup. ~125-200ms minimum, plus whatever the application itself adds.

**With snapshots**, the picture changes:

1. Pre-init a microVM in production-ready state (app running, dependencies loaded, caches warmed)
2. Take a snapshot
3. Restore from snapshot when a new instance is needed
4. The new instance is ready in single-digit milliseconds

This means a "Playwright sandbox" snapshot, once created, can be restored 1000 times per second per host, each restore taking <10ms. The cold-boot cost is paid once at snapshot creation; restores are nearly free.

**Containers cannot match this** without significant engineering (CRIU-based checkpoint/restore is possible but operationally complex). Firecracker's snapshot system is first-class and production-tested at AWS scale (trillions of Lambda invocations per month).

**For our use cases involving repeated identical starts** (AI sandboxes, Playwright fleets, ephemeral test environments), snapshot restore is genuinely transformative.

## The Resource Math For Our C8i Scenario

Concrete: a c8i-flex.large at ~$0.089/hour gives us 2 vCPUs and 4 GiB RAM. How many microVMs vs containers can it run?

Approximate capacity (purely indicative; real numbers depend on workload):

| Workload | Container Capacity | Firecracker Capacity (cold) | Firecracker Capacity (snapshot pool) |
|----------|--------------------|-----------------------------|-------------------------------------|
| 256 MiB app workloads | ~10-12 concurrent | ~8-10 concurrent | ~10-12 concurrent (after first snapshot) |
| 512 MiB app workloads | ~5-6 concurrent | ~4-5 concurrent | ~5-6 concurrent |
| Lightweight 128 MiB workloads | ~20-25 concurrent | ~15-20 concurrent | ~20-25 concurrent |

**Container density is slightly higher** for the same instance size because containers do not pay the per-VM kernel overhead. The gap is in the 15-25% range for typical workloads.

For most of our scenarios, **a c8i-flex.large running Docker or Podman containers gives us slightly more capacity than the same instance running Firecracker microVMs**. The exception is workloads that benefit from snapshot pre-warming, where Firecracker's snapshot capacity (warming a snapshot once and restoring many times) creates effective density that containers cannot match.

## What This Means For Our Direction

Reading this against the strategy briefs from earlier today:

### Reinforces The Container Hosts Primitive (Today's Brief)

For our default container hosts substrate (running Docker/Podman containers on our own EC2 fleet), **the performance and resource picture favours containers over Firecracker** for the typical long-running vault-hosting workload. The container hosts primitive should ship as a container-first substrate. Firecracker becomes one of several optional backends.

### Sharpens The Firecracker Case

The earlier strategy brief recommended prototyping Firecracker for specific workloads. This research clarifies which ones:

1. **AI agent code execution sandboxes**: Containers are unsafe; Firecracker is the right substrate regardless of startup-time comparison.
2. **Snapshot-fast Playwright fleets**: This is where Firecracker's snapshot restore is dramatically better than container alternatives.
3. **Vault-attached compute with snapshots**: If a vault has a snapshot of "ready to serve this vault" state, Firecracker restore is sub-second; containers cannot match.

The earlier recommendation stands: **prototype Firecracker for specific use cases where it materially outperforms**. Not for general-purpose workloads.

### Refines The Density Modes

The vault-hosting density modes brief (14 May) named three: dedicated EC2, multi-container per EC2, multi-vault per app. The Firecracker investigation adds a fourth: **multi-microVM per EC2**, sitting between dedicated EC2 and multi-container per EC2 on the isolation axis, and approximately equal on cost. This is the right tier for moderately-sensitive multi-tenant workloads where container kernel-sharing is not acceptable but dedicated EC2 is too expensive.

### Adds A Caveat To The Nested-Virt Pricing Win

The nested-virt research from earlier today celebrated cheap Firecracker hosts on C8i ($0.09/hr vs $3+/hr bare-metal). The performance research adds a caveat: **nested-virt Firecracker pays a ~10% performance tax** vs bare-metal Firecracker. For our experimentation and small-scale workloads, this is fine. For high-throughput production, bare-metal still wins on per-cycle cost despite higher hourly cost.

This does not change the conclusion (start prototyping on C8i; revisit bare-metal if scale justifies). It just means the "Firecracker on C8i" path has its own trade-offs.

## What This Brief Does Not Try To Answer

Deliberate scope limits:

- **Not benchmarking specific workload performance.** That requires running the experiments on our actual workloads with our actual code. The Fargate experiment brief and the instance sizing brief (both today) are the right vehicles for that.
- **Not picking a winner.** The question is not which runtime is best; it is which runtime fits which workload.
- **Not covering Kata Containers or gVisor in depth.** These are mid-points between containers and Firecracker; covered briefly but not the focus. Both worth knowing about: Kata for VM-isolation with OCI compatibility, gVisor for user-space kernel interception at lower isolation cost.
- **Not covering AWS bare-metal performance comparisons.** Bare-metal Firecracker is faster than nested-virt Firecracker, but our entry point is nested-virt.
