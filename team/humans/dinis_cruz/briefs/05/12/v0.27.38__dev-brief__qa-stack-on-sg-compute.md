## What We Are Building

A QA stack that combines the vault model (as the storage and UI development environment), SG/Compute (as the standalone execution environment), and the existing browser automation infrastructure (Playwright, MITM proxy). The result: a self-contained, deployable test environment that we can run on a schedule, drive from a vault-backed UI, and use to generate real traffic against our own and partner sites.

This builds on the traffic simulation brief from 01 May, the SG/Compute building blocks architecture, and the SG/App framework. The pieces exist. This brief assembles them into a coherent QA platform.

## The Two Parts

### Part 1: The Vault-Driven QA UI

A vault that contains the QA control surface. This is where the human (or another agent) defines test scenarios, watches them run, and inspects results. The UI is built using the App Mode pattern, with the vault as both the storage layer and the development environment.

Two execution modes for the tests:

**Mode A: Iframe injection.**

The UI opens target pages inside an iframe and triggers user interactions via JavaScript. Fast, lightweight, runs inside the QA UI itself. Limitations: many sites block iframe embedding via `X-Frame-Options` or CSP. Useful for our own sites (sgraph.ai, partner sites we host) where we control the headers.

**Mode B: Real browser automation (Playwright).**

The UI talks to a Playwright service running in the SG/Compute environment. Playwright opens real browser windows, runs full user journeys (clicks, scrolls, form fills), captures screenshots, and reports results. Works against any site regardless of iframe restrictions.

The UI lets the operator pick the mode per test scenario. Some checks are cheap and fast in iframe mode; some require real browser automation. The same UI surfaces both.

### Part 2: The Standalone SG/Compute Stack

A SG/Compute instance containing all the moving parts needed to run the QA workflows independently:

```
SG/Compute QA Stack
    |
    +--> Vault server (sgit + storage)
    +--> Static website front end (renders the QA control vault as an app)
    +--> Playwright service (browser automation)
    +--> MITM proxy (traffic capture, request logging)
    +--> Scheduling layer (cron-like, fires test runs on intervals)
```

This is one stack, deployable as a unit. Spin it up, point a browser at it, run tests. Spin it down when you are done. Costs are tied to runtime; nothing persists between sessions unless explicitly committed to the vault.

The stack runs the same QA UI that the operator uses locally. Same vault. Same scenarios. Same results format. The only difference is that the SG/Compute version runs on a schedule, generates traffic continuously, and stores results back into the vault.

## Why Both Parts Matter

**The vault-driven UI** gives a fast, interactive surface for defining and debugging tests. The operator writes a scenario, runs it immediately, sees the result, iterates. No deployment cycle. The vault is the development environment, exactly like for any other SG/App.

**The SG/Compute stack** automates the same scenarios on a schedule. Every few hours, the stack wakes up, pulls the latest scenarios from the vault, runs them, commits the results back. The operator looks at the vault next morning and sees the history of runs.

The first part is human-driven (build and tune scenarios). The second part is agent-driven (execute on schedule, store evidence). Both use the same vault and the same scenario format. The promotion path is: define a scenario interactively, mark it as "scheduled," it picks up in the next automated run.

## What Goes in the QA Vault

```
qa-vault/
    |
    +--> _page.json                 (vault navigation, App Mode config)
    +--> app.js                     (entry point for the UI)
    |
    +--> scenarios/
    |       +--> {scenario-id}/
    |               +--> definition.json      (steps, target URL, expected outcomes)
    |               +--> mode.json            (iframe or playwright)
    |               +--> schedule.json        (frequency, if scheduled)
    |               +--> notes.md             (why this scenario exists)
    |
    +--> runs/
    |       +--> 2026-05-12/
    |               +--> {run-id}/
    |                       +--> scenario-id.json
    |                       +--> screenshots/
    |                       +--> network-log.json
    |                       +--> result.json   (pass/fail, timings, errors)
    |
    +--> environments/
    |       +--> dev.json           (target URLs for the dev environment)
    |       +--> main.json
    |       +--> prod.json
    |
    +--> reports/
            +--> daily-summary.md
            +--> trends.json
            +--> incidents.md
```

The structure separates intent (`scenarios/`), execution evidence (`runs/`), configuration (`environments/`), and analysis (`reports/`). The vault becomes the system of record for what has been tested, when, what passed, what failed, and what changed.

## How the Two Execution Modes Coexist

A scenario declares its mode:

```json
{
  "id": "login-flow-basic",
  "target": "https://sgraph.ai/login",
  "mode": "iframe",
  "steps": [
    { "action": "wait", "for": "selector", "selector": "#email" },
    { "action": "fill", "selector": "#email", "value": "test@example.com" },
    { "action": "click", "selector": "button[type='submit']" },
    { "action": "screenshot", "name": "after-submit" }
  ],
  "assertions": [
    { "type": "url-contains", "value": "/dashboard" }
  ]
}
```

The same scenario definition can run in iframe mode (inside the QA UI) or Playwright mode (via the browser service). The runtime is different; the scenario is identical.

For scenarios that require third-party site access (testing against a partner deployment, testing against production), Playwright mode is forced because iframe injection will not work. The UI surfaces this constraint when the operator picks mode.

## The Scheduling Layer

Inside the SG/Compute stack, a small scheduler runs every N minutes:

```
Every 5 minutes:
    Read scenarios/ from the QA vault
    For each scenario with schedule.json:
        If the schedule says "due now":
            Execute the scenario (via Playwright service)
            Capture screenshots, timings, results
            Write to runs/{date}/{run-id}/ in the vault
            Commit
    Sleep
```

This produces continuous traffic against the targets. CloudFront logs show realistic visit patterns. The observability pipeline (LETS) ingests the QA traffic and reports trends. If a scenario starts failing, the daily summary surfaces it.

The schedule definitions live in the vault, so they are version-controlled and editable through the UI. No separate config file in the SG/Compute stack.

## Connection to the Traffic Simulation Brief

The 01 May traffic simulation brief defined the same architecture (coordination engine + execution engine, human-speed simulated users). This QA brief is a closely related but distinct use case:

| Brief | Purpose |
|-------|---------|
| Traffic simulation (01 May) | Generate realistic-looking traffic for performance and observability testing |
| QA stack (this brief) | Functional testing: did the login flow work? Did the page render correctly? |

The infrastructure is largely shared. The Playwright service, the MITM proxy, the SG/Compute deployment, the scheduling: all reusable. What differs is the assertion model. Traffic simulation does not care about correctness; it cares about volume and shape. QA cares about correctness; volume is a side effect.

Both can run in the same SG/Compute stack, sharing the Playwright service and the MITM proxy. Different vaults, different scenarios, same underlying execution layer.

## The Standalone Stack

The SG/Compute QA stack is a building block in the sense of the building blocks architecture brief (01 May). It is self-contained:

| Property | How It Applies |
|----------|---------------|
| Self-contained | One stack, all dependencies inside |
| API-first | The QA UI is a thin client over the underlying APIs |
| LETS-native | Test runs produce structured JSON consumable by the LETS pipeline |
| Runs anywhere | Bare metal EC2, Docker, Kubernetes; same scenarios run identically |
| Composable | Pair with Elastic for trend dashboards; pair with the vault publishing layer for shareable reports |
| Storage-agnostic | The QA vault can be hosted on S3, on local disk, or via the vault publishing layer |

The stack is one of our internal building blocks. Eventually, it can be packaged for partner deployments who want their own QA infrastructure rather than relying on shared tooling.

## Why This Matters Now

Three drivers:

**The partner deployments need continuous QA.** As we onboard medical partners, investor pack engagements, and other 2026 entrepreneurs, each deployment needs ongoing validation. A QA stack pointed at each partner's environment catches regressions before the partner notices.

**Vault-backed app development needs vault-backed app testing.** The pattern we are promoting (vibe-coded HTML in a vault, rendered via App Mode) needs an equivalent QA pattern. This brief defines it.

**The SG/Compute stack needs more validated workloads.** Each new stack we build (Local Claude, the package manager, the AWS billing analyser, the IAM visualiser) is a node in the ecosystem. QA is the meta-stack: it tests all the others. Building it forces us to validate the building block pattern itself.
