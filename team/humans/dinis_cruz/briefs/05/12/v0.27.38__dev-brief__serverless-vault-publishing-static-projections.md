# Serverless Vault Publishing: Read-Only Vault Projections to Any Static Host

**version** v0.27.38
**date** 12 May 2026
**from** Human (project lead)
**to** Developer (lead), @Dev, DevOps
**type** Dev brief

## The Insight

Strip writing, strip authentication, strip licensing, and what is a vault on disk? Just a folder of files. The vault format already lives on S3 as plain encrypted objects. The structure is just files in a deterministic layout.

That means a vault can be projected into a fully serverless read-only artefact: a folder of files that any static host (GitHub Pages, S3, Cloudflare Pages, Netlify, even a USB stick) can serve. The browser-side runtime decrypts and renders. No server needed at all. No vault API running. Nothing but static files.

This is meaningfully different from what we shipped yesterday (the published readonly vaults at `sgraph.app`). That model still runs a serverless function at the edge to route requests, look up the share token, and read from the vault store. It is "serverless" in the lambda sense but still needs our infrastructure.

What this brief proposes is **fully serverless**: a static-file projection of a vault that runs anywhere static files run, with zero runtime dependency on SG/Send infrastructure.

## The Two Modes Now Coexist

| Mode | Yesterday's Brief | This Brief |
|------|------------------|-----------|
| Architecture | Vault store + edge function + slug lookup + CDN | Static files only |
| Infrastructure required | Our vault hosting | Anywhere static files can live |
| Updates | Push to vault, propagates automatically | Re-publish to create new projection |
| Hosting options | sgraph.app subdomains or custom domains pointed at us | GitHub Pages, S3, Cloudflare Pages, Netlify, anywhere |
| Cost to us | Bandwidth + edge function execution | Zero |
| Cost to publisher | Free tier or subscription | Whatever the static host charges (often free) |
| Use case | Live, frequently-updated sites | Frozen, distributed, archive-quality snapshots |

These are not competing approaches. They are different points on a spectrum, each appropriate for different scenarios.

## Why This Matters

### True Independence From Our Infrastructure

A partner can publish their vault as a static projection, host it anywhere, and never depend on us being online. If we disappear, their site keeps working. This is the strongest possible expression of the "zero lock-in" principle from the 2026 entrepreneur strategy brief.

### Distribution Anywhere

The same projection can be:

- Uploaded to GitHub Pages (free, version-controlled hosting)
- Dropped on S3 (cheap, owned by the publisher)
- Served from Cloudflare Pages (fast, free, global)
- Burned to a USB stick (truly offline, air-gapped distribution)
- Bundled in a Docker image (deployable inside enterprises)
- Mirrored across multiple regions for resilience
- Archived on the Internet Archive

Any place that can serve static files can serve a vault projection. That is a much larger set than "places that can run our edge function."

### The Static Site as the Final Artefact

For published content (an article, a portfolio, a public engagement record, a finished evaluation), the static projection is the canonical output. It is what gets cited, indexed by search engines, shared on social media, and archived.

The live vault is the working surface where the author iterates. The static projection is what the world sees.

This is exactly the build-publish workflow developers expect: a development environment where you iterate, and a publish step that produces an artefact you deploy.

## How It Works (the Mechanics)

A vault is structurally:

```
vault/
    +--> manifest.json              (vault metadata, version, app entry point)
    +--> objects/
    |       +--> {hash}.enc          (each vault object as an encrypted file)
    +--> commits/
    |       +--> {commit-id}.json    (commit history)
    +--> _page.json                  (navigation, if present)
    +--> app.js                      (entry point for App Mode, if present)
```

These are all already static files. SGit already manages them as such (it works from zips, after all).

The projection step:

1. Read the current vault state (latest commit, or a chosen commit)
2. Copy all the encrypted objects, manifest, navigation, and app entry into a clean output directory
3. Include the runtime: a small JS bundle that decrypts vault objects and renders content
4. Generate an `index.html` that bootstraps the runtime with the vault's read key embedded (or read from URL hash)
5. Output is a folder ready to upload anywhere

```bash
sgit publish-static --vault <vault-id> --output ./dist
# Produces a folder:
#   dist/
#       index.html         (bootstrap)
#       runtime.js         (decryption + rendering)
#       manifest.json
#       objects/
#       _page.json
#       app.js
```

The publisher uploads `./dist/` to wherever they want. Done.

## The Read Key Question (Same as Before)

Three options for delivering the read key to the runtime:

1. **Embedded in the static HTML.** Simplest. Anyone with the URL can decrypt. The vault is fully public; the read key is not a secret. Same logic as the published readonly vaults brief.

2. **Hash fragment in the URL.** The read key lives in `index.html#read-key=xyz`. Never sent to the server. The static host never sees it in logs. This is the technique from the 01 May website object viewer brief; it works identically here.

3. **Provided at runtime.** The visitor enters the key (for vaults intended for a specific recipient). The static projection is more "encrypted archive" than "public website" in this mode.

For public sites (the most common case), Option 1 or 2 is right. The brief lets the publisher choose at projection time.

## How This Composes With the Published Vault Layer

The yesterday's brief and this brief are complementary, not competing:

**Active development phase:** The publisher iterates on their vault using the live published-vault layer (yesterday's brief). They commit, the slug at `their-name.sgraph.app` updates automatically. Their AI dev tool can keep editing.

**Publication phase:** When the publisher is happy with a version and wants to freeze it, they run `sgit publish-static`. The output is a snapshot they can host anywhere. The live version can keep evolving; the static snapshot represents a specific commit forever.

This maps cleanly to the engineering workflow: development branch and tagged releases. Yesterday's brief was the development branch. This brief is the tagged release.

## Compatibility With GitHub Pages

GitHub Pages is the obvious first target. It is free, version-controlled, and ubiquitous. The publisher:

1. Runs `sgit publish-static --vault <id> --output ./docs`
2. Pushes `./docs/` to their GitHub repo
3. Enables GitHub Pages on the `/docs` folder
4. Visits `https://username.github.io/repo-name/`
5. The vault renders

That whole flow is achievable today with one command, a git push, and a click in GitHub's settings UI. No coordination with us required.

This is also a natural extension of the GitHub-as-Vault-Projection brief from 11 May. That brief described the development workflow (GitHub repo as developer surface, vault as consumer surface). This brief adds: when the developer is ready to publish, GitHub Pages can serve the vault directly. The same GitHub repo holds both.

## The Runtime Bundle

The static projection ships with a small JavaScript runtime that:

- Loads the manifest
- Reads the read key (from embedded config, URL hash, or user input)
- Fetches encrypted objects on demand (lazy load)
- Decrypts client-side via Web Crypto API
- Renders content (markdown, HTML, images, App Mode)
- Handles SPA routing for deep links

This runtime is one of our Web Components (the same ones already serving sgraph.ai). The static projection bundles it; no CDN dependency for the runtime either.

Bundle size matters here. The runtime should be small (target: under 50KB compressed) because every static deployment carries its own copy. We will not load it from a shared CDN; that would reintroduce a runtime dependency on us.

## What This Replaces

This replaces a few painful patterns:

- **"Export your vault to a static site" hand-coded workflows.** Anyone who needs a frozen version of their vault content today has to write custom code. This makes it a one-liner.
- **Dual-publishing workflows.** Currently a publisher who wants both a live editing surface and a frozen public archive maintains both manually. This makes the static archive a derivative of the live vault.
- **Lock-in concerns about hosting.** A partner worried about depending on our infrastructure can now publish their frozen version anywhere. They use us for the live working surface only, by choice, not necessity.

## What This Does Not Replace

The live published-vault layer (yesterday's brief) is still the right answer when:

- The site updates frequently
- Visitors should see changes within minutes
- The author keeps iterating after publication
- The vault has interactive features that need ongoing infrastructure

The static projection is for snapshots. The live layer is for ongoing work. Both ship; publishers pick.

| 2 | The output folder serves correctly when uploaded to S3 with static hosting | Upload to S3, open URL, vault renders fully |
| 3 | The output folder serves correctly on GitHub Pages | Push to GitHub, enable Pages, vault renders at the GitHub URL |
| 4 | The output folder serves correctly from Cloudflare Pages | Deploy to Cloudflare Pages, vault renders |
| 5 | The output folder works when served from `python -m http.server` locally | Run locally, vault renders correctly |
| 6 | The runtime bundle is under 50KB compressed | Measure the size; if larger, refactor |
| 7 | The static projection works without any internet access to sgraph.ai or our APIs | Block network access to our domains, vault still renders |
| 8 | Deep links work in the static projection (SPA routing) | Open a deep URL directly, correct page renders |
| 9 | Read key embedding mode works (Option 1) | Static projection with embedded key serves to anyone with the URL |
| 10 | Hash-fragment read key mode works (Option 2) | URL with `#read-key=xyz` works; key never appears in server logs |
| 11 | The static projection represents a specific commit and never changes | Commit, publish, change the vault, the static projection unchanged until republished |
| 12 | The runtime decrypts and renders the same content as the live vault | Same vault, side-by-side: live and static, identical rendered output |
