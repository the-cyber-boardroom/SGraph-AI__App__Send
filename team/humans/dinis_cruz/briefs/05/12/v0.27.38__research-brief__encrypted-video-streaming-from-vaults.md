## The Problem

I am starting to create and publish videos. I want to put them on the website (sgraph.ai, library content, use case demos). I have two hard constraints:

1. **No YouTube embeds.** YouTube comes with tracking, third-party cookies, recommendation algorithms pulling viewers away, and a hosted dependency. Not acceptable for the SG/Send brand or for the partner sites we power.
2. **No "download the whole video first."** A 20MB video should start playing in seconds, not after the whole file arrives. Standard streaming behaviour, except the file is in an encrypted vault.

The standard solutions assume neither of these constraints. YouTube/Vimeo break (1). Plain S3-hosted MP4 breaks (2) for large files unless you implement HTTP range requests, which assume the file is readable in chunks.

Vaults encrypt the whole object. That is the conflict to resolve.

## The Question

**Can we stream encrypted video from a vault, with the first frames playing within a few seconds, without requiring the entire file to be downloaded and decrypted first?**

This brief is a research scope. The implementation depends on what the research finds.

## Three Approaches to Investigate

### Approach 1: Chunked Encryption (Break the Video Into Many Encrypted Pieces)

Instead of encrypting one 20MB video file as one ciphertext, encrypt 20 chunks of 1MB each (or 40 chunks of 500KB, or however we tune it). Each chunk is independently encrypted. Each chunk can be downloaded and decrypted independently.

The video player consumes chunks in order:

```
Chunk 1 (first second of video)    → download, decrypt, start playing
Chunk 2 (next second)              → download in parallel while chunk 1 plays
Chunk 3 (next second)              → download in parallel
...
```

The player starts after chunk 1 arrives. The rest streams in the background.

**Advantages:**
- Each chunk uses standard AES-GCM encryption (no new crypto primitives)
- Chunks can be downloaded in parallel (NIC-maxing from the package manager brief)
- The first chunk is small, so startup latency is minimal
- Works with any video format (MP4, WebM, etc.)
- Compatible with HTTP range requests at the chunk level

**Concerns:**
- Need an index file that maps chunk position to chunk file (and the index needs to be downloaded first)
- Re-keying between chunks (or using the same key with different nonces) needs care
- More files in the vault (mitigated by SGit commit bundling from day 51)

**Variation: variable chunk sizes.** The first few seconds of a video are more critical to start playback fast. Make those chunks smaller (256KB) so they arrive quickly. Make later chunks larger (1-2MB) for efficient bulk transfer. The index file describes which chunk is which size.

### Approach 2: Streaming Decryption of a Single Encrypted File

Some encryption modes (AES-CTR, AES-GCM with careful framing) can be decrypted in a streaming way: you do not need the entire ciphertext before you can start producing plaintext. You decrypt the first N bytes as soon as you have them.

**Question for research:** What encryption mode do vaults currently use? AES-GCM as a single block, or AES-GCM in a streaming-friendly framing?

If it is the latter, we can ask the browser to download with HTTP range requests, decrypt the bytes as they arrive, and feed them to the video player. The video player itself handles the rest (most modern players support partial MP4 playback via the moov atom at the start of the file).

**Advantages:**
- No chunking required; one encrypted file
- Standard HTTP range request mechanics
- Simpler vault structure
- The video file format already has the "play while downloading" property; we just need to not block it

**Concerns:**
- Depends on the encryption mode being streaming-friendly (or being changeable to one)
- The video file must be "fast start" (moov atom at the beginning, not the end)
- Integrity verification: AES-GCM authenticates the whole ciphertext at the end; streaming playback might play unauthenticated bytes that later fail authentication

### Approach 3: HLS or DASH Inside the Vault

HTTP Live Streaming (HLS) and MPEG-DASH are the industry standards for adaptive video streaming. They are already chunked: a master playlist references segments (typically 2-10 seconds each), and the player downloads segments as needed.

If we generate HLS or DASH output for our videos (transcode the source MP4 into HLS segments), each segment becomes a vault object. The player asks for the playlist, gets it, then asks for segments in order. We encrypt each segment as a vault object.

**Advantages:**
- Solves an already-solved problem; HLS players are mature
- Adaptive bitrate possible (multiple qualities, player picks based on bandwidth)
- Standard tooling (FFmpeg, MediaConvert) for the transcoding step
- The vault holds the same kind of file structure HLS expects (playlist + segments)

**Concerns:**
- More processing on our side (transcoding)
- More storage (multiple qualities multiply the file count)
- The HLS playlist needs to be reachable; the segments are encrypted vault objects, which is unusual for HLS players

This is essentially Approach 1 with a standardised format. Worth comparing the two directly.

## My Initial Intuition

Approach 1 (chunked encryption) feels right for these reasons:

- It is the simplest model; chunks are just files
- It works with the existing crypto layer without modification
- It leverages SGit commit bundling for storage efficiency
- It supports variable chunk sizes (small first chunks, larger later ones)
- It is the same pattern as the package manager (decompose into manageable units, load progressively)
- It composes with the new SG/App routing: the player runs as an SG/App and asks the runtime for chunks via VFS API

But the research should validate this against the alternatives, not just assume it.

## The Player Surface (Common to All Approaches)

Whatever approach we pick, the consumer-facing surface is:

```html
<sg-video src="vault://abc123/video.media" autoplay></sg-video>
```

A Web Component that:

1. Reads the video manifest (or single-file metadata) from the vault
2. Requests chunks (or ranges) as needed
3. Decrypts each chunk
4. Feeds bytes to a native `<video>` element via MediaSource Extensions (MSE)
5. Shows a loading indicator until the first frames arrive
6. Manages buffering, seeking, and playback state

This component lives in the tools repo (with the other vault-aware Web Components). It works on any page that loads it, including pages outside our infrastructure.

## Privacy and Tracking Property

Worth making explicit: video served from a vault has the same privacy property as everything else in the vault. No third-party tracking. No analytics fingerprinting from a video host. The vault read key controls access; the playback infrastructure does not log who viewed what to any external service.

For the partner sites where the whole point is "we do not see your data," using YouTube for the videos would be a contradiction. Vault-native video is consistent with the rest of the platform's privacy posture.
