## The Win Already in Hand

Yesterday's brief on published readonly vaults mentioned `*.sgraph.app` as the working domain for free-tier vault hosting. **The domain is now registered.** We own `sgraph.app`.

This brief defines the workflow to make subdomain registration on that domain self-service: a vault owner picks a slug, the system maps it to their vault, the DNS provisions, the certificate provisions, and within minutes their vault is live at `https://<slug>.sgraph.app/`.

This is the operational implementation of decision 45 from yesterday's open decisions list (which domain to use for published vaults). Decided: `sgraph.app`. Now we build.

## What We Are Building

The capability looks simple from the user's perspective:

1. Vault owner has a vault they want to publish
2. They run `sgit publish --slug my-vault-name`
3. The CLI checks slug availability, registers it, propagates DNS, requests certificate
4. Within minutes, `https://my-vault-name.sgraph.app/` serves the vault content
5. Updates to the vault propagate automatically to the live URL

Behind the scenes, this orchestrates DNS, certificate management, vault-to-slug routing, and edge caching. The vault owner sees one command and a URL.

## The Slug Acts Like a Share Token

The cleanest part of this design: we do not need a new mapping table. SG/Send already has a mechanism for resolving an opaque identifier to a transfer ID and read key (the share token system). We reuse it.

A slug is a share token, just with a friendlier alphabet.

When a request arrives at `https://my-vault-name.sgraph.app/`, the edge function:

1. Extracts the slug from the host header (`my-vault-name`)
2. Resolves the slug through the existing share-token resolution (deriving or looking up the transfer ID and read key by the same mechanism we already use for read-only tokens)
3. Fetches and decrypts the vault content
4. Returns rendered HTML to the browser

No new persistence layer. No new schema. No new operational concern. The same mechanism that produces a working share-token URL produces a working slug URL; only the alphabet and the surface differ.

The browser never sees the read key. It stays inside the resolution layer that already exists for share tokens. The URL is clean and professional: `demo.sgraph.app`, `sara-cv.sgraph.app`, `private-health.sgraph.app`.

This is the right model because **the vault is intentionally public.** The read key would not need to be secret anyway. Keeping it inside the resolution layer gives us a cleaner URL and the option to revoke access (revoke the underlying share token) without rotating anything in places we cannot reach.

### What the Slug Is, Concretely

A slug is a human-chosen alias that maps to a share token. The share token is what actually carries (or resolves to) the vault transfer ID and read key. The mapping from slug to share token is the only new piece of state we need, and it is trivial: a small key-value lookup of slug to share-token reference.

Everything downstream (resolving the share token to vault transfer ID + read key, fetching encrypted vault objects, decrypting, rendering) is the existing share-token plumbing. No new code paths.

## The DNS and Cert Story

The technical pieces, in the AWS context (other clouds map similarly):

### Wildcard DNS

`*.sgraph.app` resolves to our CloudFront distribution. Every subdomain hits the same edge. No DNS provisioning per slug needed; the wildcard handles it.

Route 53 (or Cloudflare DNS) hosts `sgraph.app`. One wildcard A or CNAME record points all subdomains to CloudFront. Done once.

### Wildcard Certificate

ACM (or Let's Encrypt for non-AWS deployments) issues a wildcard cert for `*.sgraph.app`. One certificate covers every subdomain. No per-slug cert provisioning.

This is the cleanest path. The alternative (per-subdomain certs via Let's Encrypt) works but adds complexity and provisioning latency. Wildcard cert removes both.

### Edge Function Routing

CloudFront receives every request. A Lambda@Edge function (or CloudFront Function for simpler cases) extracts the host header, queries the slug-to-vault mapping, and routes to the right vault.

For non-AWS deployments, the equivalent: Cloudflare Workers, Netlify Edge Functions, or Fastly Compute. The same logic; different runtime.

### Slug-to-Token Lookup

The only new state: a small key-value lookup from slug to share-token reference. Single-key lookups, read-heavy, low write volume. Any of these work: DynamoDB on AWS, Cloudflare KV, Redis, or even a JSON file in S3 with edge caching.

The schema is minimal: slug as primary key, the share-token reference as value, owner ID for access control, timestamps for audit. That is the whole table. Everything else (vault transfer ID, read key, vault objects) flows through the existing share-token resolution and is not duplicated here.

## The CLI Command

```bash
sgit publish --slug my-vault-name [--vault <vault-id>]
```

Flow:

1. CLI authenticates the user
2. CLI checks slug availability via the slug lookup
3. If available, CLI registers the slug pointing at a share token for the vault (generating one if needed)
4. CLI confirms DNS propagation (usually instant with wildcard)
5. CLI confirms certificate coverage (instant with wildcard)
6. CLI returns the live URL

```bash
$ sgit publish --slug demo-health-score
✓ Slug "demo-health-score" available
✓ Vault vault-abc123 registered
✓ Mapping created
✓ DNS resolves: demo-health-score.sgraph.app
✓ HTTPS active
→ https://demo-health-score.sgraph.app/
```

Unpublish removes the mapping:

```bash
sgit unpublish --slug my-vault-name
```

Update is implicit (changes to the vault propagate automatically; no republish needed for content updates).

## Slug Naming Rules

To keep things sensible:

- 3-40 characters
- Lowercase letters, numbers, hyphens only
- Cannot start or end with a hyphen
- No double hyphens
- Reserved slugs blocked: `www`, `api`, `admin`, `docs`, `app`, `mail`, common service names
- Profanity filter applied (basic)
- Trademark-sensitive names (e.g. major company names) reserved for verified claims

These rules mirror what GitHub, Vercel, and Netlify do for similar subdomain features. Standard pattern.

## Why This Matters Beyond Convenience

A subdomain on `sgraph.app` does three things at once:

**It makes vault-backed sites feel professional.** Sharing `https://demo-health-score.sgraph.app/` reads as a real product. Sharing a long URL with a query string and a read key reads as a developer's debug artefact.

**It demonstrates the platform.** Every `sgraph.app` URL someone sees in the wild becomes a soft pitch. People click. They see a polished site. They notice the URL. Some of them ask "what is this?" and we have new candidates for the platform.

**It removes a deployment step.** A vibe-coding entrepreneur can publish their site at `https://their-name.sgraph.app/` without buying a domain, without configuring DNS, without provisioning a certificate. The path from "I have a vault" to "I have a live website" is one command. This is the Netlify-equivalent productisation working as designed.

## Future Capabilities Worth Flagging (Not For Now)

These are deferred but worth noting:

- **Custom domains.** Already in yesterday's brief. The owner brings their own domain and we map it to their vault. Same routing mechanism, different host. Paid tier.
- **Slug ownership transfer.** When an owner wants to give up a slug (or sell it). Standard transfer flow with confirmation from both parties.
- **Slug expiry.** Free-tier slugs released after a long period of inactivity, with grace period and reminder emails. Paid-tier slugs reserved indefinitely.
- **Premium slugs.** Short, memorable slugs (one-character or common words) reserved for paid tiers. Standard pattern from URL shorteners and subdomain hosts.
- **Analytics per slug.** Visitor counts, referrers, top pages. Paid feature. Aggregated from edge logs.

The MVP this brief defines is: register slug, route to vault, serve content. The rest follows when there is demand.

## Research Required Before Implementation

A couple of things to validate in AWS specifically:

1. **Wildcard cert + Lambda@Edge routing performance.** Confirm latency is acceptable when every request hits the Lambda@Edge function for slug lookup. Caching the slug mapping at the edge should make this trivial, but worth measuring.

2. **Storage backend for the slug-to-share-token lookup.** DynamoDB is the obvious choice but its read latency from Lambda@Edge regions can be unpredictable. Cloudflare KV is faster for this pattern but requires running the routing outside AWS. Worth a benchmark before committing.

3. **CloudFormation vs Terraform for the one-time wildcard setup.** Most of this is provisioned once and forgotten. Pick the simpler option for our team and document the setup.

4. **ACM wildcard cert auto-renewal.** Confirm the renewal is automatic and reliable. We do not want to discover a certificate expiry the hard way.

These are not blockers. The implementation can start with the obvious choices and refine later if needed. But they are worth a couple of hours of research before we commit to the architecture.

## What This Replaces

For the friend's job search site (yesterday's brief), this replaces:

- The friend buying a domain
- The friend setting up DNS
- The friend provisioning HTTPS
- The friend wiring it to their vault

Instead: `sgit publish --slug sara-job-search` and they are live at `https://sara-job-search.sgraph.app/`. If they want a custom domain later, they buy it and point it at us. We handle the rest.

For the medical partner, this is even more important. The doctor publishing the Private Health Score POC does not want to learn AWS. They want a URL. We give them `https://private-health-score.sgraph.app/` in one command.

For sgraph.ai itself: we migrate to using our own infrastructure. `sgraph.ai` becomes a custom-domain pointing at our published-vault layer. We eat our own dog food.
