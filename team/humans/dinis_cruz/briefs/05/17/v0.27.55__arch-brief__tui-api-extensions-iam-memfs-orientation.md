# TUI API Extensions: Granular IAM, Virtual Filesystem, And The "Now What?" Problem

**date** 17 May 2026
**from** Human (project lead)

## What This Is

The architectural extension of yesterday's TUI API brief, capturing five substantial mechanics that emerged as the work crystallised:

1. **Multiple TUI APIs per tool**: each tool can expose several APIs covering different components and capabilities
2. **Native IAM with least privilege**: granular access control over which TUI APIs an agent (or operator) can see and invoke
3. **The "now what?" problem**: when arriving at a tool, the LLM (or human) needs to orient quickly: status, available actions, recent changes, what is coming
4. **Change control as a first-class TUI API surface**: tools communicate their own change log, current state, and upcoming features through the API
5. **Virtual filesystem (memfs-based)** for rich context: skills.md, changelogs, guidance loaded on demand without polluting the context window upfront

Together these mechanics turn the TUI API from "structured surface for one tool" into **a system for tools to talk to each other and to LLM agents at scale, with security, freshness, and discoverability built in**.

The core architectural insight: **the TUI API stops being a passive surface and becomes the medium through which tools actively communicate**.

## Multiple TUI APIs Per Tool

Yesterday's framing implicitly treated each tool as having one TUI API. The voice memo corrects this: **each tool can have multiple TUI APIs, one per component or capability cluster**.

Concretely, for SG/Edge the relevant TUI APIs might be:

| TUI API | Scope |
|---------|-------|
| `sg-edge.deployment` | Deployment reality, what is wired, what is live |
| `sg-edge.topology` | The component graph and its current state |
| `sg-edge.slugs` | Per-slug detail, wake, terminate, status |
| `sg-edge.events` | Live activity stream, throughput, errors |
| `sg-edge.config` | Configuration view and edit (high-privilege) |
| `sg-edge.admin` | Administrative actions, danger zone |

Each API has its own:
- Surface description (what it does)
- Capabilities (what actions it exposes)
- IAM requirements (who can use it and how)
- Documentation (its skills.md, its changelog)
- Change history (what changed recently)

This is structurally similar to the difference between a single web service and a microservice cluster. A monolithic TUI API exposes everything; a properly-decomposed TUI API surface lets each capability stand on its own, with appropriate privileges per capability.

The decomposition makes a lot of subsequent work cleaner: you can give an agent access to `sg-edge.deployment` (read-only deployment view) without giving them access to `sg-edge.admin` (destructive actions). The MCP equivalent would typically be "give the agent the whole sg-edge tool or nothing"; this approach is finer-grained.

## Native IAM And Least Privilege

The voice memo named this directly: **"the best way to control damage limitation at all is to not give enough privileges."** The TUI API design needs IAM as a first-class concept.

Specifically, every TUI API exposes:

| Aspect | What It Means |
|--------|---------------|
| **Required scopes** | What capability tokens are needed to use this API (e.g., `sg-edge:deployment:read`, `sg-edge:slugs:write`, `sg-edge:admin:destructive`) |
| **Action-level granularity** | Different actions within the same API may require different scopes |
| **Audit logging** | Every API call records who called it, with what scopes, what happened |
| **Time-bounded grants** | Scopes can be granted for a session, an hour, a workflow |
| **Conditional gating** | Some actions only available after others (sequencing) |

The credential manager from earlier this week is the natural substrate. Simple Tokens are scoped to specific TUI APIs and specific capabilities within them. An agent doing operational work gets a token for exactly the capabilities it needs, no more.

This is **deliberately different from how MCP servers typically work**. MCP tends toward all-or-nothing exposure: connect the tool, the agent can do whatever the tool allows. That works for sandbox workflows; it does not work for production operational tools where a misaligned agent (or a confused one) could do real damage.

The voice memo's framing was sharp: **"how can we expose the right tools at the right type for the agents at the right situation, right? And how can we provide that?"** The answer is granular IAM at the TUI API level, with programmatic assembly of the toolkit per agent per task.

### Sequencing And Conditional Gating

A specific elaboration worth being explicit about. The voice memo named it: **"there's a sequence of events and you can only run this tool after that tool, and then after that tool, and after that tool."**

Some workflows have intrinsic ordering. You cannot terminate an instance before it exists. You cannot apply a configuration before it has been validated. You cannot publish an article before it has been signed off. The TUI API can encode these dependencies:

- Action `wake-slug` requires the slug to be in state `registered` or `idle`
- Action `terminate-instance` requires the slug to be in state `live`
- Action `publish-article` requires the article to be in state `signed-off`

This is not just convenience; it is safety. **The TUI API enforces sequencing the LLM might otherwise violate.** This makes the operational surface dramatically safer to expose to autonomous agents.

The conditional gating also feeds back into discovery. When the agent asks "what can I do here?", the answer includes only the actions currently available given current state. **Capabilities not in the answer are not available; the LLM cannot accidentally invoke them.**

## Programmatic Tool Assembly

A related mechanic the voice memo named: **"the key concept here is not to have black magic, not to have the agent designing what tools to use; we should be providing that."**

The pattern: for any given workflow, the system assembles the set of TUI APIs and scoped capabilities the agent needs. The agent does not choose its toolkit; the toolkit is curated for the task.

Concretely:

```
Workflow: "diagnose-edge-issue"
  Assembled toolkit:
    - sg-edge.deployment      (read scope: see what is deployed)
    - sg-edge.slugs           (read scope: inspect specific slugs)
    - sg-edge.events          (read scope: see recent events)
    - sg-edge.topology        (read scope: see relationships)
  Excluded:
    - sg-edge.admin           (no destructive actions during diagnosis)
    - sg-edge.config          (no configuration changes during diagnosis)
```

```
Workflow: "fix-edge-issue"
  Assembled toolkit:
    - sg-edge.deployment      (read scope)
    - sg-edge.slugs           (read + wake scope, no terminate)
    - sg-edge.events          (read scope)
    - sg-edge.config          (read scope; specific edit scopes case by case)
  Excluded:
    - sg-edge.admin           (still excluded for normal fixes)
```

The workflow definition is the source of truth for what the agent sees. The LLM does not browse for tools; it operates on the curated set.

This is the JS API equivalent: when a vault app loads another vault app, it does not get full access to that app's internals; it gets the specific surface the host has exposed. The same principle applied to operational tools.

## The "Now What?" Problem

The voice memo named a real cognitive load problem: **"you arrive at a tool and you go, now what?"** Both humans and LLMs face this. A tool that has been recently developed, or one the user has not touched in weeks, or a new component in the stack, the user lands there and needs to orient.

The TUI API should answer this question directly. When an agent (or human) connects to a TUI API, they get:

| Information | Why It Matters |
|-------------|----------------|
| **Current status** | Is the tool healthy? What is it doing right now? |
| **Available actions** | What can I do given current state and my scopes? |
| **Recent changes** | What changed in this tool since I last visited? |
| **Coming soon** | What is in active development that I should know about? |
| **Skills documentation** | How do I use this tool well? (Skills.md style) |
| **Common workflows** | What do most users do here? |
| **Known issues** | What is currently broken or limited? |

This is the **orientation surface**. Every TUI API exposes it via a standard endpoint (`describe`, `status`, `whatsnew`, or similar). The LLM calling it gets enough context to operate without prior knowledge of the tool.

Critically, **this orientation information lives inside the tool, alongside the code**. It is updated when the code is updated. The tool talks to its users (human and LLM) about itself.

## Change Control As A First-Class Surface

A natural extension: **every change to a tool produces an update to its change-log surface**. The voice memo named the practical mechanism: when an LLM is creating workflows, when a developer is pushing features, when a bug is fixed, the change description gets captured and exposed via the TUI API.

The pattern:

| Event | Captured As |
|-------|-------------|
| New feature added | Entry in `changelog`, summary in `whatsnew` |
| Bug fix shipped | Entry in `changelog`, optional alert in `known-issues` cleared |
| Capability deprecated | Entry in `changelog`, warning in `coming-soon` |
| Breaking change | Entry in `changelog`, prominent flag in `status` |
| Configuration change | Entry in `audit`, summary in `status` if material |

These are not human-written prose dropped into a wiki. They are **structured artefacts captured at the moment of change**, exposed through the TUI API so consumers (LLMs, humans, other tools) can see what is current.

This solves a real problem. Today, when a tool finishes a feature, there is no clean way for it to communicate that to its users. People discover changes when they hit them. With this pattern, **the tool announces its changes through its own surface**, and any agent or human connecting can see what is new without external documentation hunting.

For LLM agents specifically, this matters a lot. An LLM that "knew" how a tool worked six months ago may operate against stale assumptions. **A self-describing tool whose change log is part of its API surface lets the LLM stay current automatically.**

## The Virtual Filesystem: Context Without Pollution

The most architecturally interesting mechanic in the voice memo. The catch-22 it names:

- **You want rich tool documentation** (skills.md, changelogs, guidance, examples) for the LLM
- **You do not want to pollute the context window** with 50,000 tokens before the LLM even invokes anything

Today's typical MCP-style approaches either dump everything into the context (expensive, hits limits fast) or expose nothing useful upfront (LLM has to discover via trial and error). Neither works at scale.

The proposal: **a virtual filesystem (memfs-based) attached to every tool execution and chat session**, where rich documentation lives as files. The LLM does not see the documentation upfront; it sees that the filesystem exists. When it needs context, it reads the relevant files on demand.

The virtual filesystem properties:

| Property | What It Means |
|----------|---------------|
| **In-memory by default** | No disk IO; instant access |
| **Persistable** | Can be saved as zip, MySQL row, or eventually S3 |
| **Per-execution scoped** | Each chat or agent session has its own filesystem |
| **Tool-populated** | Tools write their docs, changelogs, schemas into the FS |
| **LLM-readable** | The agent reads files via standard `read-file` operations |
| **Structured** | Conventions for where things live (`skills.md`, `changelog.md`, `current-state.json`) |

The result is a context-window-friendly way to give the LLM access to arbitrarily rich tool documentation. **The LLM sees a directory of relevant files; it reads what it needs; the context stays small.**

For SG/Edge, the virtual filesystem at the start of a session might look like:

```
/tools/sg-edge/
├── skills.md              # How to use this tool well
├── changelog.md           # Recent changes
├── whatsnew.md            # Highlights since last week
├── coming-soon.md         # In-development capabilities
├── known-issues.md        # Current limitations
├── current-state.json     # Deployment state snapshot
├── workflows/
│   ├── diagnose.md        # Common diagnosis workflow
│   ├── fix-issue.md       # How to fix common issues
│   └── deploy.md          # Deployment workflow
└── api/
    ├── deployment.json    # API surface description
    ├── slugs.json         # API surface description
    └── ...
```

The LLM agent sees this tree. It reads `skills.md` first (small, always relevant). It reads `current-state.json` to understand what is happening now. It reads specific workflow files when asked to do specific things. **Context grows on demand, bounded by what is actually needed for the task.**

### Composition With Memfs

The voice memo named the specific implementation: **memfs**, which we have already built as part of earlier work. This is the right substrate. Memfs gives us:

- In-memory file operations with standard FS semantics (`open`, `read`, `write`, `unlink`)
- The ability to serialise the entire FS to a zip, MySQL blob, or S3 object
- Compatibility with anything that expects a filesystem (LLM tool calls, agent harnesses, debugging)

The TUI API virtual filesystem is essentially **memfs configured for tool-documentation conventions**, with population happening as tools start up and changes get committed.

## How These Mechanics Compose

The five mechanics reinforce each other. A practical example showing them together:

```
1. Agent connects to SG/Edge with workflow "diagnose-edge-issue"
   ↓
2. System assembles the toolkit:
   - sg-edge.deployment (read)
   - sg-edge.slugs (read)
   - sg-edge.events (read)
   - sg-edge.topology (read)
   ↓
3. Virtual filesystem populates:
   /tools/sg-edge/skills.md
   /tools/sg-edge/changelog.md
   /tools/sg-edge/whatsnew.md
   /tools/sg-edge/workflows/diagnose.md
   /tools/sg-edge/api/<each-api>.json
   ↓
4. Agent reads skills.md (small, oriented)
   ↓
5. Agent reads whatsnew.md (small, knows what changed recently)
   ↓
6. Agent reads workflows/diagnose.md (specific to task)
   ↓
7. Agent calls sg-edge.deployment.describe (gets API surface)
   ↓
8. Agent reads current-state.json (deployment snapshot)
   ↓
9. Agent operates: read events, inspect slugs, draw conclusions
   ↓
10. Audit log captures every call, every scope used
```

Compare against an MCP-style integration where the agent dumps the whole tool capability into context, then operates without scope limits. The proposed pattern is more secure, more focused, more current, and far more efficient on context tokens.

## The Bigger Pattern

Pulling back, what these mechanics together create is something specific: **a system where tools actively communicate with their users (human and LLM) about themselves**, with appropriate security and minimal context pollution.

Today, tools are mostly passive surfaces. You read documentation about them, you remember how they work, you operate them. The proposed pattern flips this: **the tool tells you about itself**. Status, capabilities, recent changes, current limitations, common workflows, all surfaced through the TUI API, scoped by IAM, loaded on demand from the virtual filesystem.

This is what the voice memo was reaching for with the phrase **"two-way conversation system where each tool can control the files you create and control the things."** Tools become agents in their own right, with their own surfaces for self-description, self-advertisement, and operational dialogue.

The architectural significance is comparable to the JS API for vault apps. The JS API made vaults composable; the TUI API with these extensions makes tools composable in the same way. **Vault of vaults via JS API; tool of tools via TUI API; the fractal extends one layer up.**

Estimated effort: 2-3 weeks for the SG/Edge implementation, including the IAM, virtual filesystem, and orientation endpoints. Ongoing as we add the pattern to other tools.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not an MCP replacement.** The TUI API with extensions interoperates with MCP where useful; it does not try to displace it.
- **Not a full IAM rebuild.** The credential manager from earlier this week provides the substrate; this brief uses it.
- **Not a documentation system.** Tools generate their own documentation through the change-capture pattern; we do not build a separate docs platform.
- **Not infinitely flexible.** The orientation conventions are deliberately opinionated; tools follow them or they do not get the benefits.
- **Not v2 work.** These extensions ship as part of the v1 TUI API; building the API without them means redoing it.

## Honest Risks

Three risks:

**Risk 1: The granular IAM model is more complex to reason about than all-or-nothing access.** Mitigation: provide good defaults (read-only access for most workflows); make the toolkit-assembly logic explicit; lint workflows for inappropriate scopes.

**Risk 2: The virtual filesystem becomes a dumping ground.** If every tool writes everything to the FS, the LLM may face the same context-pollution problem inside the FS. Mitigation: conventions for what goes where; size limits per file; relevance flags so the LLM reads small high-signal files first.

**Risk 3: Change capture is hard to enforce.** If developers do not write changelog entries when they ship, the surface becomes stale. Mitigation: make change capture part of CI; refuse to ship if the changelog is empty for a feature; lean on LLM-assisted changelog generation when possible.

## Open Questions

| Question | Notes |
|----------|-------|
| Standard filename for the orientation file: `skills.md` or `README.md` or `ORIENT.md`? | Probably `skills.md` for continuity with the vault-app convention |
| How granular should IAM scopes be? Per-action, per-API, per-resource? | Probably per-API by default; per-action where the action is destructive |
| What format for the API surface description? | Probably JSON for machine readability; with optional Markdown for human reading |
| Should the virtual filesystem persist across sessions? | Optional; default ephemeral; persistent for debugging/replay |
| How do we handle versioning of the API surface? | Each TUI API has its own version; clients can target specific versions |
| Do we expose internal tools (like SG/Compute primitives) via TUI APIs? | Yes, by default; this is how internal-vs-external surfaces are unified |
| When does the virtual filesystem get loaded into context? | On demand; never automatically; agent reads files via standard tool calls |
| Should change-capture be optional or mandatory? | Mandatory for shipped features; warning if absent |
| How do we handle long-lived workflows where the toolkit might need to evolve? | Re-assemble per task; do not pin a toolkit across multiple tasks |
| What about delegation: an agent allowing a sub-agent to inherit a subset of its scopes? | Yes, via Simple Token derivation; first-class feature |
