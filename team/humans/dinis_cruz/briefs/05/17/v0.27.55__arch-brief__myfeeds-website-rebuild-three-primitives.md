## What This Is

The architectural follow-through on yesterday's MyFeeds repositioning piece. That brief named the business: B2B research briefings as vault-delivered evidence packs, with the journalism layer alongside. This brief addresses **the website rebuild that supports both layers**, structured around publishing vaults as the unit of content.

The voice memo crystallised three primitives that need to be treated as distinct architectural concerns, not collapsed together: **the vault itself (the thing being published), the storage substrate (where the vault lives), and the management layer (the vault-of-vaults that controls publishing operations)**. Most current website architecture treats these as one thing; the MyFeeds rebuild treats them as three, which makes a number of things simpler that were getting awkward.

The brief covers the three primitives, the website itself (which has several architectural options worth thinking through), the publishing workflow, the data-flow question (where does source material live versus the article versus the agent's working state), and what gets built in what order.

## The Three Primitives

The architectural insight from the voice memo. These are conceptually distinct and need to stay distinct:

### Primitive 1: The Vault

The vault is the thing being published. An article is a vault. A research briefing is a vault. A multi-part investigation is a vault (possibly a vault-of-vaults if the parts have their own structure). The vault is identified by its vault key, holds its content as files, carries its commit history, has its own app surface for presentation, and is the unit that gets shared, archived, and updated.

This is the canonical vault definition from the rest of the platform. Nothing new here; the new bit is committing to **the vault as the canonical unit of publishable content**, rather than treating articles as a special case.

### Primitive 2: The Storage Substrate

A vault has to live somewhere. The voice memo named several options worth being explicit about:

| Storage Option | Use Case |
|----------------|----------|
| **Always-on vault server** | High-traffic vaults that need consistent availability (the front page, latest article) |
| **Ephemeral vault server** | Vaults that get woken on demand (older archives accessed occasionally) |
| **S3 static serving** | Read-only published vaults that do not need server-side compute (probably most articles) |
| **Vault zip / archive file** | Portable distribution; offline reading; long-term cold storage |
| **Multiple vault servers** | Geographic distribution; cost optimisation; provider diversity |

The substrate choice is per-vault, picked from the spectrum based on traffic, freshness, and cost requirements. **A vault is not tied to one substrate.** The same vault can be served from S3 today, moved to an ephemeral vault server tomorrow if traffic justifies it, archived as a zip next month for long-term storage, and republished on demand from any of those forms.

This composition with the substrate spectrum from earlier this week is intentional. The publishing world gets the same flexibility the rest of the platform has.

### Primitive 3: The Management Layer

The third primitive is what makes the system tractable to operate. **A vault-of-vaults that holds the keys, the metadata, the operational status, and the publishing workflow state for every published artefact**.

The voice memo named this directly: "the master management of all this, the management console for the whole publishing workflow." It is the management vault for the publishing operation. Specifically, it holds:

- The vault read keys (so we can serve content from vaults whose keys we manage)
- Optionally the vault write keys (for vaults we control end-to-end)
- The public/private key per vault if we use the DKIM-style pattern from this week's discovery brief
- Metadata: which vault corresponds to which article, when published, on what substrate, last-updated, traffic stats
- Workflow state: which articles are in draft, review, signed-off, published, archived
- Audit log: who did what when, via the vault's own commit history

This is the manager vault pattern from earlier this week, applied to publishing. **The publishing operation has its own vault that manages the rest of the publishing operation.** Recursive, in the comfortable way the platform pattern is built around.

## Why Separating These Three Matters

Several things become cleaner once the three are distinct:

| Operation | Without Separation | With Separation |
|-----------|--------------------|----- |
| Move a vault from one server to another | Re-publish; URLs change; SEO breaks | Update management layer's pointer; vault key unchanged |
| Archive an old article | Delete from server; lose it | Move vault to cold storage; management layer remembers |
| Republish an article that was archived | Manual re-deploy | Management layer wakes the substrate |
| Rotate a vault key (sensitive material) | Replace everywhere | Update management layer; reissue references |
| Migrate to a new storage provider | Manual migration; URLs break | Management layer redirects; vaults move underneath |
| Add a new substrate type (e.g., Cloudflare R2) | Custom integration per content type | Substrate is just another option in the management layer |

The pattern is that **operational flexibility lives in the management layer; the vault itself is portable; the substrate is interchangeable**. This separation is what makes the publishing system maintainable as it grows.

## The Website's Own Architecture Options

The MyFeeds website itself needs to be served somehow. The voice memo named the right options worth thinking through:

### Option A: Vault Server (Always-On)

The website is a vault app served from an always-on EC2 instance with a stable DNS name. Standard pattern; works today; uses the substrate spectrum's persistent-EC2 lane.

| Pros | Cons |
|------|------|
| Real-time updates (publish an article, it appears immediately) | Always-on cost (~£3-4/month for a t4g.nano) |
| Dynamic features (search, comments, real-time updates) | Single point of failure unless replicated |
| Standard architecture; familiar | Performance limited by single instance |

### Option B: S3 Static Site

The website is rendered to static HTML and served from S3 (or Akamai Object Storage, or Cloudflare R2) with a CDN in front.

| Pros | Cons |
|------|------|
| Cheap (cents per month at typical traffic) | Updates require regeneration |
| Globally distributed via CDN | No dynamic features without separate API |
| No server to manage | Search has to be client-side or via API |
| Excellent performance | Real-time updates need a workaround |

### Option C: Hybrid Static Plus Ephemeral

The bulk of the site is S3 static (articles, archives, navigation). Specific pages or workflows that need dynamic state spin up ephemeral compute on demand. The front page might be static and regenerate every 10 minutes; a search page might be a vault app that wakes on demand.

| Pros | Cons |
|------|------|
| Best cost profile (mostly static; ephemeral only when needed) | More complex to operate |
| Performance of static for most traffic | Cold-start visible on dynamic pages |
| Dynamic capability when needed | Requires the on-demand provisioning machinery from earlier this week |

### Recommendation

**Option C, the hybrid, is the right v1 target**, with the static portion as the primary delivery path. The cost economics are favourable; the performance is excellent; the publishing workflow naturally maps to "regenerate the static site when content changes." The dynamic portion uses the same on-demand provisioning machinery from earlier this week, which is now working at 50-second cold-start with the holding-page-detects-readiness fix.

For specific use cases:

- **The front page**: static, regenerated every 10 minutes (or on-publish)
- **Articles**: static, regenerated on-publish; cache-headered for long-term browser caching
- **Archive pages**: static, regenerated when new articles are added
- **Search**: client-side via pre-built index, or ephemeral compute for full-text
- **Subscriber-only B2B research vaults**: ephemeral compute, gated by Simple Tokens from the credential manager
- **Admin / publishing UI**: ephemeral compute, accessed via management vault credentials

This is a workable architecture. It does require us to build the static-regeneration pipeline, which is a piece of work; but the rest is composition of existing primitives.

## The Publishing Workflow

How an article actually gets from idea to public:

```
1. Article vault is created (draft state in management vault)
   ↓
2. Content is drafted; agents may assist; vault commits accumulate
   ↓
3. Review state: editor reviews; email-fs threads inside the vault track signoff
   ↓
4. Email-style signoff system inside the vault (voice memo's specific request)
   ↓
5. Approval committed; management vault state moves to "ready to publish"
   ↓
6. Publishing trigger:
   - Vault is copied to publishing storage (S3 static OR vault server)
   - Static site regeneration runs
   - DNS records updated if new vault URL
   - Management vault state moves to "published"
   ↓
7. Discovery / propagation:
   - Vault appears in `/.well-known/vaults`
   - RSS / Atom feed updates
   - Newsletter subscribers notified (if applicable)
   - Social posts queued (if applicable)
   ↓
8. Live state: article is publicly readable; analytics tracked
   ↓
9. Eventually: archive trigger moves vault from hot storage to cold storage
   - URL still works; management layer points to cold storage
   - First access may have a cold-start delay; subsequent are cached
```

Each step is observable and audit-trailable through the management vault. The workflow can be paused at any state; re-attempted on failure; manually overridden when needed.

## The Email-Style Signoff Pattern

The voice memo specifically flagged this: **the email system inside the article itself as the email-fs likes that are implemented as the signoff and the issues etc**.

This is genuinely useful and worth implementing well. The pattern:

- The article vault contains an inbox folder
- Reviewers send EML-formatted messages (signoff, questions, issues, suggested edits) to the inbox
- The vault app surface presents these as a threaded conversation alongside the article
- Approvals are first-class messages with a recognised structure
- The audit trail is the inbox plus the article's commit history

This composes with the email-fs work the project has been doing. Each article gets its own micro-email-channel, scoped to the article, with the editorial process visible inside the artefact itself. **The article carries its own provenance as part of its content.**

For external review (clients of B2B research, external editors, expert reviewers), the inbox supports public-key-based submission per yesterday's vault discovery brief. A reviewer outside the publishing organisation can submit a signed signoff that the management vault verifies.

## The Data-Flow Question

The voice memo named a subtle architectural question that needs explicit treatment: **where does each kind of data actually live during the publishing process?**

Three categories of data with different homes:

| Data Category | Where It Lives | Why |
|---------------|----------------|-----|
| **The article itself (final content)** | The article vault | This is what gets published |
| **Source materials (raw evidence)** | A separate sources vault | Linked to from the article; not necessarily published with it |
| **Agent's working state (intermediate analysis)** | A separate working vault (or a private folder within the article vault) | Not part of the public article; useful for traceability, regeneration, audit |

The separation matters for several reasons:

- **Publishing scope**: the article vault is what goes public; source vaults may be partially private; working vaults are operational
- **Vault key access**: agents work on different vaults with different permission scopes
- **Update lifecycle**: source vaults can update on their own cadence; the article vault is point-in-time
- **Backup posture**: agent working state may not need the same backup discipline as published articles

The voice memo flagged the specific access question: what does Claude (or any agent working on the article) have access to? The answer is **scope-limited via Simple Tokens**: the agent has read access to the sources vault, read-write to its working vault, and append-only commit access to the article vault (changes need editorial approval before becoming part of the published version).

This is the credential manager from earlier this week doing real work. Different scopes per agent; revocable; auditable via management vault commits.

## The Multiple-Vault-Servers Pattern

The voice memo flagged the broader pattern explicitly: **multiple basically vault servers in our SG APIs open up, including some that we load up on demand**. This is the substrate spectrum applied to a publishing context.

Concrete instantiation for MyFeeds:

| Server | Role | Substrate |
|--------|------|-----------|
| **`myfeeds.ai`** | Main website (static + ephemeral hybrid) | CDN + S3 + on-demand compute |
| **`vault-1.myfeeds.ai`** | Live vault server for active articles | Always-on EC2 |
| **`archive.myfeeds.ai`** | Older articles, woken on demand | Ephemeral container hosts |
| **`research.myfeeds.ai`** | B2B research vaults, client-specific | Per-client ephemeral with Simple Token gating |
| **`admin.myfeeds.ai`** | Publishing management UI | Ephemeral, project-lead-only access |

Each server runs the same vault-app code; the difference is access policy, traffic profile, and substrate choice. The management vault knows where each vault currently lives and routes requests appropriately.

This is meaningfully different from running one big server. **Each substrate is optimised for its workload; failure isolation is real; the cost profile fits the traffic profile per role.**

Yesterday's brief positioned MyFeeds commercially: B2B research briefings as vault-delivered evidence packs, with the journalism layer alongside. This brief describes the technical substrate that supports both.

The mapping:

| Yesterday's Concept | Today's Implementation |
|---------------------|------------------------|
| Evidence pack as the deliverable | Article vault with sources vault attached |
| Tiered pricing (starter / standard / deep / ongoing) | Different vault depth and refresh cadence; same architecture |

The architecture in this brief makes the business model in yesterday's brief practical. Without the three-primitive separation, the operational complexity of running both layers becomes punishing.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a CMS in the traditional sense.** No WYSIWYG editor; no per-user accounts in the WordPress style. The publishing flow is git-shaped, not editor-shaped.
- **Not a real-time collaboration platform.** Multiple authors work via vault commits and the email-style threads; not via simultaneous typing.
- **Not multi-tenant for external authors.** v1 is for MyFeeds' own authors. External submissions come via public-key inbox (covered above), not via shared authoring.
- **Not auto-scaling beyond the substrate spectrum.** Each server type has its own scaling story; the platform does not auto-shift between substrates without explicit configuration changes.
- **Not a competitor to Substack or similar.** The architecture supports newsletter-style delivery, but the positioning is different (B2B research briefings, not consumer subscriptions).

## Honest Risks

Three risks:

**Risk 1: The three-primitive separation adds operational complexity that does not pay off at small scale.** The architecture is justified by the operations it enables at scale; at very small scale, simpler approaches work too. Mitigation: build it because we are operating at growing scale, not because it is conceptually clean; revisit if the management overhead becomes painful relative to the value.

**Risk 2: The hybrid static/dynamic architecture introduces edge cases.** Cache invalidation when content updates; cold-start visibility on dynamic pages; dual debugging surface. Mitigation: standard hybrid-CDN patterns exist; we lean on them; document the edge cases explicitly.

**Risk 3: The management vault becomes a single point of failure.** If the management vault is lost or corrupted, the entire publishing operation is in trouble. Mitigation: the backup discipline from earlier this week applies here in spades; multi-tier, multi-provider backup is mandatory; restore drills are non-optional.
