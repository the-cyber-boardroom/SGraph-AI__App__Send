# First Five TUI Screens For SG/Edge: Exploring The Art Of The Possible

**version** v0.27.55
**date** 17 May 2026
**from** Human (project lead)
**to** Developer (lead), Design, @Dev
**type** Dev brief

## What This Is

The concrete follow-up to the earlier TUI brief from today. That one named the framework, the framing, the deployment chain. This one names **the first specific TUI screens to build**, framed as exploration rather than final design.

The voice memo set the brief frame clearly: **"can you create four or five TUI visualisations, kind of pages that have a certain degree of interactivity, some might be dynamic, some might not, where you basically have a mode where we explore the side effects of how this thing can work and how everything fits together."** The goal is not to ship the final SG/Edge dashboard; it is to **explore the art of the possible** and learn what shapes work, what does not, and how the flow eventually wants to be.

The motivation is concrete and operational: today, when the project lead wants to know what is deployed, what is wired, what is real, the answer comes from asking Claude or running CLI commands and reading walls of text. The voice memo names this directly: **"a visual sort of wall of text, which is not that easy to spot."** TUI screens that just show the reality, visually, are a substantial UX improvement even before we get to interactivity.

This brief proposes five specific screens to prototype, what each one shows, what we expect to learn from each, and how they fit together as a learning exercise rather than a finished product.

## The Framing: Exploration, Not Production

Worth being explicit about this because it shapes how the work should be approached. The voice memo named it: **"explore the art of the possible, see what works, what doesn't work, play around with a lot of these ones, and then eventually understand the flow."**

This means:

- **Five prototypes are the goal, not five polished products.** Each one is a learning artefact.
- **Some will be kept; some will be discarded; some will inform a different design that absorbs the best of several.** That is the expected outcome.
- **The screens do not need to compose into a single coherent app yet.** They can be standalone explorations.
- **Effort per screen is bounded.** A day or two each, not a week. The goal is breadth of exploration, not depth of polish.
- **Aesthetic quality matters as part of the exploration.** A clean-looking prototype teaches more than an ugly one with more features.

Once the five have been built and used, a sixth conversation happens: which of these patterns deserves promotion to the canonical SG/Edge TUI proposed in the earlier brief.

## What The Five Together Teach

Each screen answers a different question:

| Screen | Question | Interactivity | Update Rate |
|--------|----------|---------------|-------------|
| 1. Deployment reality | What is deployed? | Low | 5-10s |
| 2. Topology | What is wired to what? | Medium (focus, drill-in) | 5-10s |
| 3. Local vs Edge vs Deployed | What is different across environments? | Low (refresh) | On demand |
| 4. Slug detail | What is happening with X? | High (multiple actions) | 1-2s |
| 5. Live activity stream | What is happening right now? | Medium (filter, pause) | Real-time |

By building all five, we learn:

- Which visual idioms work (topology art vs flat lists vs comparison tables vs streaming feeds)
- Which information density is right
- Which level of interactivity matches which use case
- Which colour and indicator conventions stick
- Which keyboard patterns feel natural
- Which screens get used vs which are pretty but unused

The **sixth conversation** (which the voice memo set up implicitly) is whether these five become tabs of a single TUI, separate commands, or get reduced to a smaller set that absorbs the best of each. That conversation happens after the five exist, not before.

## What Each Screen Asks Of The Implementing Agent

The voice memo named the agent brief simply: **"can you create four or five TUI visualisations, kind of pages that have a certain degree of interactivity."** Translating to concrete asks per screen:

| Screen | Approximate Effort | Specific Asks |
|--------|--------|------------|
| 1. Deployment reality | 1 day | Read state from existing SG/Edge CLI commands; render as structured panes; status indicators per category |
| 2. Topology | 1-2 days | ASCII-art rendering of the component graph; keyboard focus moves between nodes; this is the most visually-experimental |
| 3. Local vs Edge vs Deployed | 1 day | Three-column comparison; drift detection logic; per-row status indicator |
| 4. Slug detail | 1 day | Drill-in target; many sections; sparkline rendering for activity over time |
| 5. Live event stream | 1-2 days | Streaming feed with filter shortcuts; sparklines below for context; pause/resume |

Total: 5-7 days of focused work for all five. The agent producing these should be free to deviate from the sketches above; they are starting points, not specifications. **The voice memo's framing of "explore the art of the possible" is the brief, not these specific layouts.**

The agent should also document what they tried and rejected. Negative results (the topology view did not work well because of X, the local-vs-edge comparison should have been a different shape because of Y) are as valuable as positive ones.

## Specific Constraints From The Deployment Chain

Per the addendum to the earlier TUI brief, these screens all need to work over SSM + docker exec. Concrete implications:

- **Update rates throttled to 5-10 Hz at most**, not 60 FPS. The network bandwidth between operator and container does not need 60-Hz updates and bursty terminal output over a saturated network feels worse than slower-but-consistent updates.
- **First frame under 100ms on launch.** The operator is waiting through three hops; the TUI should render visible state immediately on launch, even if some panes show "loading" briefly.
- **Reset on resize.** Terminal resize events should re-layout cleanly; no broken frames.
- **No mouse-required interactions.** Every action reachable via keyboard.

## What Frameworks Each Screen Exercises

A side benefit of building all five: they exercise different aspects of the chosen framework (probably Textual + Rich per the earlier brief), which builds team familiarity with the breadth of the library.

| Screen | Framework Features Exercised |
|--------|------------------------------|
| 1 | Static layout, periodic refresh, tables, status indicators |
| 2 | Custom ASCII-art rendering, focus management, navigation tree |
| 3 | DataTable, diff-style rendering, multi-column comparison |
| 4 | Drill-in pattern, sparklines, multiple action handlers |
| 5 | Streaming list, real-time updates, filter state, pause control |

By the end of building five, the team has touched every major Textual + Rich capability. The implementation knowledge transfers to whatever the final SG/Edge TUI looks like.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not the final SG/Edge TUI.** These are explorations; the canonical TUI proposed in the earlier brief comes after.
- **Not customer-facing.** All five are operator tools for internal use.
- **Not exhaustive.** There are other useful screens (cost analytics, multi-tenant views, configuration editor); these five are the starting set.
- **Not a UX competition.** The goal is learning, not best-of-show; ugly-but-illuminating is better than pretty-but-uninformative.
- **Not a feature checklist.** If a screen turns out to be unhelpful, do not force it; document what went wrong.

## Open Questions

| Question | Notes |

| Should the five screens be commands (`sg-edge tui-deployment`) or tabs of one app? | Probably commands for exploration; a unified tab interface comes if the patterns earn it |
| What is the minimum viable refresh mechanism, polling the SG/Edge CLI, or a watch API? | Polling for v1; watch API as a future enhancement |
| Should screen 5 (event stream) consume from the unified observability session or directly from SG/Edge? | Probably observability session for consistency |
| Theme: light or dark for the first prototypes? | Dark; matches expected operator preference |
| Should the screens be runnable side-by-side (one per pane in tmux)? | Yes; they are independent commands, so this works for free |
| When do we decide which of the five to keep? | After a week of operational use; gather opinions then decide |
