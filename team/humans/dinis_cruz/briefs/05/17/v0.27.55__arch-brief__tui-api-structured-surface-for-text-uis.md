# The TUI API: A Structured Surface For Composing And Consuming Text UIs

**version** v0.27.55
**date** 17 May 2026
**from** Human (project lead)
**to** Architect, Developer (lead), @Dev
**type** Arch brief

---

## What This Is

A conceptual contribution that has been crystallising through the TUI work this week and now needs explicit naming: **the TUI API**. A structured surface (parallel to the JS API for vault apps) that makes TUIs composable, agent-friendly, and the natural unit of LLM-consumable interface in our stack.

Two related ideas travel together here. **First**, the development sequence the voice memo named explicitly: **capability → class → CLI → TUI → Web API → Web UI**. The TUI is the missing middle step that turns the rest of the sequence from "expensive parallel tracks" into "natural progression." **Second**, the TUI API itself: the structured surface that makes TUIs as consumable from agents and other tools as the JS API made vault apps consumable from other vault apps.

The brief covers both because they reinforce each other. The sequence explains why the TUI deserves first-class treatment in our stack. The API explains how to make TUIs scale into the "TUI of TUIs" pattern that follows naturally from the substrate we have been building.

## The Friction Point That Surfaced This Idea

Worth being explicit about the operational reality the voice memo named: **CLI-only workflows have a discoverability problem, but web UIs have an attrition problem so high that creating one for every capability is unsustainable**.

The CLI is excellent at:
- Executing specific actions with precision
- Composing into pipelines
- Being driven by agents and scripts
- Being remoted via SSH/SSM (the deployment chain from the earlier TUI brief)

The CLI is poor at:
- Showing what is there (discoverability)
- Surfacing relationships between things
- Communicating system state at a glance
- Multi-step workflows that span several commands
- Onboarding new users (and new agents) to what a tool can do

Web UIs solve some of these problems but introduce their own attrition: each web UI needs a backend, an API, a live server, an HTML/CSS/JS frontend, deployment infrastructure, and ongoing maintenance. **The cost of creating a web UI for every capability we build has been outpacing our ability to build the capabilities themselves.** Web UIs are valuable; they are also expensive; the maths becomes prohibitive at the rate we are now creating capabilities.

**TUIs sit exactly where the friction is least.** They run anywhere a CLI runs (including through SSH/SSM/docker exec). They give us discoverability, structure, and at-a-glance state. They cost far less to build than web UIs. And, the key insight from the voice memo, **they can serve as the first iteration of a UI before a web UI is justified**.

## The Development Sequence

The voice memo named this clearly. The right sequence of events when creating a new capability:

```
1. Capability  →  what the thing does (a class, a function, an algorithm)
2. CLI         →  raw invocation surface (every action exposed; agent-friendly)
3. TUI         →  rich text-based UI (use-case focused; human-friendly; composable)
4. Web API     →  HTTP surface (mostly automated from the CLI/TUI definitions)
5. Web UI      →  graphical interface (only when truly needed; expensive)
```

Each layer builds on the previous one and adds something specific:

| Layer | What It Adds | Cost Profile |
|-------|--------------|--------------|
| Capability | The actual functionality | Variable (the real engineering) |
| CLI | Granular invocation; agent surface; pipeline composition | Low (mostly argument parsing over the capability) |
| **TUI** | **Discoverability; structure; at-a-glance state; multi-step workflows; use-case packaging** | **Low (Textual/Bubble Tea make it cheap)** |
| Web API | HTTP surface; remote access; web-app integration | Low if generated from CLI; medium if hand-written |
| Web UI | Graphical interface; non-technical user access; visual polish | High (frontend stack, design work, deployment) |

The voice memo's key insight: **today, most projects skip the TUI step and go straight from CLI to web UI**. This is exactly backward. The web UI is the most expensive layer; skipping the TUI means paying the highest cost first, often for capabilities that could have been adequately served by a TUI alone.

The proposed sequence makes the TUI the natural next step after the CLI, not an afterthought. **In many cases, the TUI is the final UI layer; the web UI is never needed**. In other cases, the TUI's existence makes the web UI cheaper to build because the layout, workflow, and information design have already been validated in the text version.

## Why The TUI Slots In Between CLI And Web API

A subtle point worth being explicit about. The TUI does not replace the CLI; it sits between the CLI and the user (or LLM) for use-case-focused interactions. The web API does not replace the CLI either; it adds a different invocation surface for remote consumption.

The three layers serve different consumers:

| Layer | Primary Consumer | Why |
|-------|------------------|-----|
| CLI | Agents, scripts, pipelines, individual commands | Each action atomic; composable in pipes; minimal startup cost |
| TUI | Humans doing operational work; LLMs reasoning about state | Rich state visualisation; use-case packaging; multi-step workflows |
| Web API | Remote applications, web frontends, third-party integrations | HTTP semantics; standard auth; cross-language access |

The voice memo named the distinction precisely: **the CLI is already an API in some sense, but the TUI tends to be use-case focused and packages information in ways that the raw CLI does not**. A CLI exposes every action with maximum granularity. A TUI selects, combines, and presents actions for specific workflows. **The TUI is a use-case-focused projection of the CLI**.

This shapes what the TUI API needs to provide.

## What The TUI API Is

The TUI API is the structured surface that makes a TUI machine-readable, composable, and consumable by other tools (including LLMs, other TUIs, and automation pipelines).

The pattern is directly parallel to the JS API for vault apps (which made vault apps composable from other vault apps). The JS API let one vault app read and operate on another's state through a well-defined interface. The TUI API does the same thing for TUIs: it lets one tool inspect, drive, and compose with another's TUI through a structured interface.

Concretely, the TUI API should expose:

| Surface | What It Does |
|---------|--------------|
| **Discovery** | List what the TUI can do (its screens, actions, queries) in structured form |
| **State queries** | Read current TUI state (selected item, current screen, displayed data) as structured data |
| **Action invocation** | Trigger TUI actions programmatically (the same actions a keyboard shortcut would trigger) |
| **Event subscription** | Subscribe to events the TUI emits (state changes, user actions, errors) |
| **Screen navigation** | Move between TUI screens / panes via the API |
| **Data export** | Pull what the TUI is showing as structured data (for downstream consumption) |
| **Composition** | Allow one TUI to embed or call into another TUI's surface |

This is what the JS API does for vault apps. The TUI API is the same shape, applied one level up.

## Why The TUI API Specifically

A reasonable question: **does the TUI need its own API, or is the underlying CLI API sufficient?**

The voice memo answered this directly: **the CLI is already an API, but it does not capture what makes the TUI valuable**. Specifically:

- The TUI packages information for use cases (the deployment-reality screen combines five CLI commands' worth of data into one view)
- The TUI carries state (current selection, current screen, current filter, current view mode)
- The TUI exposes workflows that span multiple CLI commands (drilling from topology to slug detail involves several underlying calls)
- The TUI surfaces relationships that the raw CLI does not (which proxy is currently serving which slug)

An agent or composable tool consuming the **CLI** has to reconstruct all of this from primitives. An agent consuming the **TUI API** gets it pre-packaged. The TUI API is the JS API moment for command-line tools: a way to interact with the use-case-focused projection, not just the raw primitives.

For LLMs specifically, this matters even more. An LLM trying to operate a CLI has to remember every command, every flag, every option. An LLM consuming a TUI API can ask "what can I do here?" and get a structured answer. The TUI API turns the use-case packaging into a self-describing surface that an LLM can navigate without prior knowledge.

## What "TUI API" Looks Like Concretely

Sketch of what the TUI API surface might be for the SG/Edge TUI from the earlier briefs today:

```
# Discovery
sg-edge-tui-api describe
  → returns JSON describing screens, actions, state shape

# State queries
sg-edge-tui-api state
  → returns current state (selected slug, current screen, recent events)

sg-edge-tui-api state --screen topology
  → returns the topology pane's current state

# Action invocation
sg-edge-tui-api invoke wake --slug john-cv
  → triggers the wake action; same as pressing 'w' on the selected slug

sg-edge-tui-api invoke filter --type errors
  → applies an error filter to the live event stream

# Event subscription
sg-edge-tui-api watch
  → streams events as they occur (NDJSON over stdout)

# Data export
sg-edge-tui-api export --screen deployment-reality --format json
  → returns the current deployment-reality state as structured data
```

The same commands work whether the TUI is currently running or not; invoking a TUI API action on a stopped TUI either starts it (if it has state worth showing) or executes the action without rendering (if the action does not need a display).

This is the JS API pattern: the underlying capability exists; the TUI is one expression of it; the TUI API is another expression that gives programmatic access.

## The Composition Pattern: TUI Of TUIs

The voice memo named this directly: **"the same way that we did the JS API, and now working on the TUI API, which is the same thing, but for these tools."** The composition pattern that fell out of the JS API (vaults of vaults) has its TUI parallel: **TUIs of TUIs**, where one TUI can host or call into another TUI's surface.

Concrete examples:

| Pattern | Example |
|---------|---------|
| **TUI embedding another TUI** | The SG/Compute TUI shows a panel that is the SG/Edge TUI's deployment-reality screen, embedded |
| **TUI delegating to another TUI** | The labs admin TUI calls into the SG/Edge TUI when an operator wants edge-level detail |
| **TUI composing several TUIs** | A platform-wide dashboard TUI shows panels from SG/Edge, SG/Compute, the labs admin TUI, the backup TUI |
| **Cross-TUI navigation** | Pressing a key in the SG/Compute TUI jumps to the SG/Edge TUI focused on the relevant slug |
| **TUI driving another TUI programmatically** | An automation script uses TUI API to inspect state across multiple TUIs and act based on the combined picture |

This is the fractal property the voice memo named explicitly: **"you can have a tool of tool and components of components, and they each have one of these."** Every tool exposes a TUI; every tool exposes a TUI API; tools compose by invoking each other's APIs.

The result is a stack where each capability gets its own TUI (cheap to build), each TUI gets its own API (cheap to expose), and composite TUIs emerge from combining the leaf TUIs. **The same fractal that made the vault-app ecosystem viable makes the TUI ecosystem viable, one layer up.**

## How LLMs Consume The TUI API

A specific consideration that justifies the API as a distinct layer. The voice memo named it: **"how do we make the CLI kind of easy to consume from an LLM."** The answer is the TUI API, because:

- The CLI exposes maximum granularity (every command, every flag); the LLM has to reason about combinations
- The TUI exposes use-case-focused capabilities; the LLM gets pre-packaged workflows
- The TUI API is self-describing (`describe` returns the surface); the LLM can introspect rather than memorise
- The TUI API exposes state in structured form; the LLM can reason about the current situation
- The TUI API surfaces actions in machine-readable form; the LLM can invoke them precisely

This makes the TUI API the natural surface for LLM-driven operations of our tools. An LLM agent doing operational work calls the TUI API to read state, invoke actions, and reason about what to do next. **The TUI is the human interface; the TUI API is the LLM interface; they share the same underlying capability**.

This is the same principle as web accessibility: the screen reader and the visual presentation are two views of the same content. Here, the TUI is the visual presentation; the TUI API is the structured view. Both are first-class.

## The Naming Question

A small but important point. The voice memo named the question explicitly: **"why TUI API and not CLI API?"**

The answer is that **the CLI is already an API** (every CLI is a structured action invocation surface) but the CLI is at the wrong level of granularity for the kind of composition we want. The CLI exposes individual atomic actions. The TUI API exposes use-case-focused workflows that combine multiple atomic actions and carry state across them.

You can build a "CLI API" trivially (it is just the CLI). You cannot trivially build the equivalent for the TUI; it needs deliberate construction. That deliberate construction is what makes the TUI API a distinct concept worth naming.

Two consequences:

- The TUI API is **not just the CLI repackaged**. It is a higher-level abstraction with state, workflows, and screens as first-class concepts.
- The CLI remains the right tool for agents doing atomic operations. The TUI API is the right tool for agents doing use-case-level operations.

Both layers serve agents. They serve different agent needs.

## What This Means For How We Build

If we adopt this framing, several things follow:

1. **Every new tool we build should have a TUI from the start**, not as an afterthought. The capability/CLI/TUI sequence becomes the default; the web UI is the optional later step.
2. **Every TUI should expose its TUI API alongside its visual surface**. Same investment; both surfaces benefit.
3. **The TUI API design should mirror the JS API design** where reasonable, so the patterns transfer.
4. **Documentation focuses on TUI workflows** rather than CLI command catalogues. The use-case-focused projection is what users (human and LLM) need to learn.
5. **Cross-TUI composition becomes a first-class feature**, not an unusual edge case. Tools talk to each other through their TUI APIs.

For the active development this week (the SG/Edge TUI), this means the TUI API is not a v2 feature; it is part of v1. The screens being built carry their state in a queryable form; the actions are invocable programmatically; the events are subscribable. Building the visual TUI without the API would mean redoing the work later.

## How This Connects To The Broader Platform Direction

The TUI API completes a pattern that the platform has been converging on:

| Layer | API |
|-------|-----|
| Vault content | JS API (composable vault apps) |
| Tool surfaces | **TUI API (composable TUIs)** |
| Inter-agent communication | Vault-as-communication-medium (from earlier this week) |
| Cross-cloud orchestration | Separate codebase with shared vault interfaces |

Each layer has its own API surface, but they all share the same architectural principle: **structured, machine-readable, agent-consumable, composable**. The TUI API is the same idea applied to a layer that was missing it.

Combined with the vault-as-communication-medium pattern from yesterday, the substrate spectrum from earlier this week, and the manager-vault pattern from last week, we have a coherent stack where every layer is automatable, composable, and observable. **The TUI API is the missing piece that makes the operational layer match the architectural elegance of the data and compute layers.**

## What This Asks For

Concrete next steps:

1. **Define the TUI API specification** for the SG/Edge TUI work that is in active development. This is the canonical first instance.
2. **Implement the TUI API alongside the visual TUI** for the five screens from the earlier brief. Each screen exposes state, accepts action invocations, and emits events.
3. **Document the TUI API surface** with the same care as we document the JS API.
4. **Build at least one composite TUI** that consumes another TUI's API (proves the composition pattern works).
5. **Build at least one LLM-driven operational workflow** that uses the TUI API for reasoning and action (proves the LLM-consumability is real).
6. **Establish TUI + TUI API as the default for new tools** from this point forward.
7. **Plan the migration of existing tools** that have CLI-only surfaces toward adding TUI + TUI API surfaces.
8. **Write the TUI API conventions document** so future tools follow consistent patterns.

Estimated effort: 1-2 weeks for the SG/Edge TUI API alongside the visual TUI build. Ongoing as we add the pattern to other tools.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a replacement for the CLI**. CLI remains the primary surface for atomic operations and pipelines.
- **Not a replacement for web APIs**. Web APIs serve different consumers (remote applications, third-party integrations).
- **Not a UI framework**. The TUI API describes the surface; the TUI itself is built with Textual/Bubble Tea/whatever.
- **Not universal**. Some tools genuinely do not need a TUI; the pattern is the default, not a mandate.
- **Not v2 work**. The TUI API is part of v1 for new tools because adding it later means redoing work.

## Honest Risks

Three risks:

**Risk 1: Building the TUI API alongside the TUI doubles the work.** Mitigation: design them together from the start; the TUI's internal state is the API surface; they share a single source of truth.

**Risk 2: TUI APIs proliferate inconsistently across tools.** Mitigation: TUI API conventions document; lint or audit conformance; treat the convention as we treat the JS API conventions.

**Risk 3: LLMs may not navigate the TUI API as fluently as we hope.** Mitigation: design for self-description; include examples in the `describe` output; provide a small reference set of common workflows.

## Open Questions

| Question | Notes |
|----------|-------|
| Should the TUI API be a separate binary or built into the TUI? | Probably built in; same binary, different invocation mode |
| What is the data format for `describe` output? | Probably JSON; possibly OpenAPI-like for familiarity |
| Should TUI APIs support cross-TUI subscriptions natively, or via a broker? | Direct for v1; broker if it becomes painful |
| How do we handle authentication for TUI APIs? | Inherit from the underlying tool's auth model; Simple Tokens via credential manager |
| Do we standardise on a TUI API "shape" or let each tool define its own? | Shared conventions; per-tool details |
| What about backward compatibility as TUI APIs evolve? | Versioned APIs; deprecation cycles |
| Should the TUI API enable recording and replay of TUI sessions? | Yes, eventually; valuable for testing and debugging |
