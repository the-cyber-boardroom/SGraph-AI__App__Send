## What This Is

A proposal to take the CLI work we have been doing further in a specific direction: **build a visually-rich, text-based UI for SG/Edge that goes well beyond standard CLI output**. Colours, real-time data, interactive commands, visualisations, sparklines, gauges, ASCII-art status displays, animations where they help. The goal is not to make the CLI prettier; it is to **make the CLI dramatically more usable for the SG/Edge case specifically**, which involves real-time data, multiple wired-up components, and the kind of operational state that benefits from being seen at a glance rather than read line-by-line.

Two threads converge in this brief. **First**, the CLI as a feedback loop has proven itself across our work this month. The REPL pattern we built into SG/Compute (`sg> ...`) is genuinely productive, both for humans and for agents. **Second**, SG/Edge has a structural shape that begs for visual representation: it is a simulated ALB with multiple components (DNS proxy, CloudFront, Edge Waker, edge proxies, vault servers, slug mappings, wake state). Listing this state as plain text loses the structural relationships; visualising it as a real-time TUI surfaces them.

This brief covers what the SG/Edge CLI should become, grounds the design in current best-in-class examples (research summarised below), names the build trade-offs, and proposes a separate module so this work does not bloat SG/Edge proper.

## The State Of The Art In 2026

Before diving into design, worth grounding in what exists today. The TUI ecosystem has matured significantly; "text-based UI" no longer means "ugly green-on-black with menu structures." Modern TUIs deliver visually-rich, interactive, real-time experiences that often rival GUI tools for specific workflows.

### The Frameworks That Matter

| Framework | Language | What It Provides |
|-----------|----------|------------------|
| **Ratatui** | Rust | Charts, sparklines, tables, gauges, scrollable lists, progress bars; constraint-based responsive layouts; 60+ FPS even with complex layouts |
| **Bubble Tea + Lipgloss + Bubbles** | Go | The Charm Bracelet ecosystem; declarative styles like CSS-for-terminals; rich widget library |
| **Textual + Rich** | Python | TUI framework built on Rich; 16.7M colours, mouse support, smooth flicker-free animation; benchmark numbers reach 120 FPS via segment-tree diffing |
| **blessed-contrib** | JavaScript | Dashboards with gauges, donuts, sparklines, tables, trees; pure ASCII/ANSI art |
| **OpenTUI** | TypeScript | TypeScript library for building TUIs; newer entrant |
| **PHP-TUI, Nimwave, nocterm** | Various | Showing the breadth of the ecosystem; the pattern crosses every language |

The frameworks share a common architectural shape: declarative widgets, responsive layouts (think Flexbox-for-terminals), event-driven updates, partial rerendering for efficiency. They differ mainly in language and ecosystem.

### The Reference Applications

A handful of tools demonstrate what excellent TUI design looks like in 2026. Each is worth installing and trying for an hour:

| Tool | What It Does | What To Learn From It |
|------|--------------|-----------------------|
| **k9s** | Kubernetes cluster management TUI | Real-time data refresh; keyboard-first navigation; resource-type drill-down; the canonical example of "TUI for managing live infrastructure" |
| **lazygit** | Git wrapper TUI | Multi-pane layout; staging area visible; complex operations made one-keypress; zero memorisation goal |
| **btop / btop++** | System monitor | Unicode block characters for live graphs; per-core CPU bars; the gold standard for "ugly htop reborn beautifully" |
| **lazydocker** | Docker management | Same shape as lazygit, applied to containers; clear precedent for "lazy* tools" pattern |
| **sampler** | Visualisation for any shell command | YAML config; live updates; gauges, runcharts, sparklines, ASCII boxes; the most relevant precedent for our case |
| **gping** | Ping, but with a graph | Tiny scope; huge usability improvement over plain ping; shows how minimal changes can transform a tool |
| **picomon** | GPU monitoring TUI | Sparkline history; shareable ASCII art summaries (press `r` to generate a card); visually-rich without being decorative |
| **below** | Time-travelling resource monitor | From Meta; records system state continuously, replays the past; the most ambitious in terms of state model |
| **Grafterm** | Metrics dashboards in terminal | Grafana-inspired; charts and gauges; explicit dashboard-in-terminal positioning |
| **gum** | Toolkit for interactive shell scripts | From Charm; not a single app but components (choose, confirm, input, spin); useful pattern for adding UI to scripts |

**The pattern across all of these**: the visual richness is in service of operational clarity. None of them are visually rich for the sake of it. The graphs, sparklines, colours, and structures all encode information that would be slower to extract from plain text.

### What Makes A TUI Visually Rich Without Being Gratuitous

A few principles emerge from studying the reference applications:

1. **Layout structure encodes information.** Multi-pane layouts (lazygit, k9s) put related state next to each other; the spatial relationship is part of the meaning.
2. **Colour is semantic, not decorative.** Red means problem; green means good; the same colour means the same thing across the app.
3. **Real-time updates are partial, not full-screen redraws.** Modern TUI frameworks diff and patch; this is what makes 120 FPS possible in pure text.
4. **Unicode block characters do enormous lifting.** █▓▒░ ▁▂▃▄▅▆▇ ╭╮╰╯ ━┃ all encode information cheaply. The full Unicode block-and-box space is the TUI's drawing surface.
5. **Sparklines and gauges compress time.** A series of `▁▂▄▆█▅▃▂` shows a trend at a glance; ten lines of timestamped numbers would take a paragraph.
6. **Keyboard-first, mouse-supported.** The serious TUIs are keyboard-driven (because power users prefer it), but support mouse for casual use.
7. **Help is one keypress away.** `?` shows the keybindings. The shortcuts are not memorisation tax; they are discovery surface.
8. **State changes are visible and explicit.** When something changes (a new pod, a new connection, an error), the UI shows it clearly, ideally with subtle animation that draws the eye without distracting.
9. **Animations are functional, not decorative.** Spinners during loading; subtle pulses on changing values; never "look at me" effects.
10. **Status is everywhere.** The screen always shows current state of what matters; you do not have to ask.

These are the principles we should adopt for the SG/Edge CLI.

## Why SG/Edge Specifically Benefits

Most CLIs do not need this treatment. A tool that takes flags and prints output is fine as a tool that takes flags and prints output. The case for SG/Edge is specific:

**SG/Edge has structural state.** Multiple components (DNS proxy, CloudFront, Edge Waker, edge proxies, vault servers) interact in defined ways. Showing this as a topology with live status is dramatically more useful than listing each component's state separately.

**SG/Edge has real-time data.** Wake events, request routing, slug-to-instance mappings, instance health, traffic patterns. All of this changes continuously; the user needs to see the current state, not a snapshot from when they last ran a command.

**SG/Edge is operationally critical.** Mistakes have real cost. A clear, immediately-readable view of state reduces the chance of operator error.

**SG/Edge has a learnable internal model.** The user benefits from understanding the flow (CloudFront → edge proxy → Edge Waker → EC2 instance → vault). A visual representation teaches the model implicitly.

**SG/Edge is used both by humans and by agents.** A rich TUI helps humans; the CLI primitives underneath help agents. Both audiences get served by the same module if designed well.

Compare against a regular CLI: typing `sg edge status`, getting twenty lines of text, parsing it mentally, asking for more detail on one slug, repeating. A TUI shows everything at once, updates live, lets the user dive in with arrow keys.

This is one possible shape. Notice the properties:

- **Topology pane** shows the SG/Edge flow visually; live status indicators (`●` healthy, `◐` provisioning, `○` idle, `✗` error)
- **Live activity pane** streams events as they happen; sparklines show throughput and wake-event trends over time
- **Slugs pane** lists all registered slugs with their current state; the selected one is highlighted
- **Detail pane** drills into the selected slug; shows instance, uptime, request pattern, vault binding, cost
- **Keyboard bindings** at the bottom; everything reachable with one or two keys
- The whole thing updates in real time without redrawing

Compared to typing `sg edge status` repeatedly, this is a different category of tool.

## The Module Question

The voice memo flagged this directly: **this should be a separate module, because it will be quite a bit of code**. That instinct is right and worth following deliberately.

The proposal: **SG/Edge keeps its CLI primitives as they are**. A new module (call it `sg-edge-tui` or `sg-edge-dashboard`) wraps those primitives in a TUI. The primitives remain CLI-shaped, agent-friendly, scriptable, composable. The TUI is the human-facing dashboard layered on top.

This split has several good properties:

1. **The CLI primitives stay simple.** They take flags, return output, exit. Agents and scripts use them happily.
2. **The TUI can be replaced or upgraded** without touching the primitives. If we decide Ratatui was the wrong framework choice, the primitives are unaffected.
3. **Both audiences are served.** The agent wants `sg edge slug-status john-cv` returning JSON. The human wants the dashboard. Both run on top of the same source of truth.
4. **The TUI itself is testable.** Standard CLI primitives are easier to unit-test than a TUI; keeping them separate lets the TUI be tested against the primitives' outputs rather than against the world.
5. **The de-commoditising-the-commodity pattern applies.** SG/Edge primitives are our "commodity"; the TUI is the custom layer that absorbs attrition (raw CLI output is hard to interpret quickly) and produces a commodity-feeling experience (the dashboard).

## Framework Choice

The substrate spectrum applies here too. Each major framework has trade-offs:

| Framework | Best For Our Case |
|-----------|--------------------|
| **Ratatui (Rust)** | Best raw performance; cleanest declarative API; the modern Rust default; high learning curve if team is not Rust-fluent |
| **Bubble Tea + Lipgloss (Go)** | Excellent design language (Charm Bracelet aesthetic); cross-platform; declarative styling; Go is approachable; many reference applications |
| **Textual + Rich (Python)** | Easiest to prototype in; mature ecosystem; some of the most beautiful TUIs in the wild; slight overhead vs Rust/Go |
| **blessed-contrib (Node)** | Already-rich widget library (gauges, sparklines, donuts, charts); but the library is older and less actively maintained |

For our case, **Textual + Rich (Python)** is probably the right starting point. Reasons:

- Python is already in our stack
- Textual + Rich is the most productive for rapid iteration on visual design
- 120 FPS via segment-tree diffing is more than enough for our needs
- The library ships with mature widgets (DataTable, Tree, ProgressBar, Sparkline)
- If we need to optimise, we can rewrite specific hot paths in Rust later

The Charm Bracelet ecosystem (Bubble Tea + Lipgloss) is the second choice and would be the right pick if we wanted to ship a single-binary TUI. Worth revisiting if the Python version validates the design and we want to harden it for distribution.

## What This Module Should Contain

Concrete v1 scope:

1. **Topology view**: visual representation of SG/Edge components with live status
2. **Slug inventory**: list of all registered slugs with state, with keyboard navigation
3. **Detail view**: per-slug deep-dive showing instance, vault binding, cost, recent activity
4. **Live activity feed**: streaming events as they occur
5. **Sparkline panels**: throughput, wake events, error rates over time
6. **Keyboard navigation**: Tab to switch panes, arrow keys within panes, single-letter shortcuts for actions
7. **Action triggers**: wake a slug, terminate an instance, refresh state; all from within the TUI
8. **Help overlay**: `?` shows all keybindings; context-aware
9. **Theme support**: dark/light, possibly per-user preference
10. **Static-image export**: press `r` to generate an ASCII-art summary of current state (picomon-style); useful for sharing or pasting into incident reports

These are the v1 features. v2 might add time-travel (replay state from N minutes ago), advanced filtering, custom dashboards per workflow.

## Animation, Where It Helps

The voice memo specifically named animations. Worth being deliberate about where animation adds value versus where it is gratuitous:

**Animations that help:**
- Spinners during async operations (provisioning, wake) so the user knows the system is working
- Subtle pulse on a value when it changes (draws the eye without distraction)
- Smooth transitions when state changes (slug moves from "provisioning" to "live")
- Loading bars with estimated completion time during multi-step operations
- Sparklines that shift left as new data arrives (rather than full redraws)

**Animations that hurt:**
- Continuous "alive" animations that draw the eye away from real changes
- Bouncing logos or branded effects in the main view
- Particle effects for the sake of it (the `ascii-splash` style is fun but distracting in operational tools)
- Anything that competes with status indicators for attention

The rule is: animation conveys information. If it does not, it does not belong in an operational tool.

A possible exception is the startup screen. A brief, branded ASCII-art splash on launch (under one second) sets the tone and aesthetic; it does not interfere with operations because it appears before any real work. This is the "MS-DOS Clipper" feel the voice memo nostalgically named, used sparingly.

## Addendum: The Deployment Chain (SSH/SSM + Docker Exec)

A practical reality worth treating explicitly because it materially shapes the design. The SG/Edge TUI runs inside a container, accessed from the operator's laptop through a chain of three hops:

```
Laptop terminal (iTerm2 / Wezterm / Windows Terminal)
    ↓ SSH or AWS SSM Session Manager
EC2 instance
    ↓ docker exec -it <container>
Container running the SG/Edge TUI
```

Each hop preserves the modern TUI experience well, but only if a few things are configured correctly. This addendum covers what survives the chain, what to watch out for, and what design implications follow.

### What Survives The Chain

The encouraging answer first: **the modern TUI experience survives this chain very well**, as long as configuration is right. SSH was designed for this exact case; tools like k9s and lazygit are routinely run inside containers accessed via SSH or SSM and work properly.

What passes through cleanly:

- ANSI colours (16, 256, and 24-bit truecolor)
- Unicode characters (block-drawing, sparklines, emojis) when the locale is set right
- Mouse events when both endpoints support them
- Window resize events (SIGWINCH propagated by SSH and docker exec)
- Keyboard input including arrow keys, function keys, modifiers
- Real-time refresh and partial redraws (SSH is just a byte stream)
- The visual richness of the TUI in full

### What Needs To Be Right At Each Layer

**The laptop terminal**. Use a modern terminal that supports 24-bit truecolor and ships with a font that has comprehensive Unicode coverage (box-drawing characters, powerline glyphs). Good choices: iTerm2 (macOS), Wezterm (cross-platform), Kitty (Linux/macOS), Windows Terminal (Windows), Alacritty (cross-platform). The default Terminal.app on macOS is workable but limited; the default Windows command prompt is not great. Set `$TERM` correctly, typically `xterm-256color` or terminal-specific (`wezterm`, `xterm-kitty`).

**The SSH / SSM hop**. SSH passes the byte stream through transparently. SSM Session Manager works similarly but has two specifics worth knowing:

1. SSM does not propagate `$TERM` automatically; set it inside the session: `export TERM=xterm-256color`
2. SSM has a default 20-minute idle timeout; for long-running TUI sessions, bump this in the SSM document

When using `ssh -t user@host docker exec ...` as a one-liner, the `-t` flag is mandatory for TTY allocation; without it the TUI will not work.

**The docker exec hop**. This is where most issues arise. The correct invocation:

```bash
docker exec -it <container> <command>
```

Both `-i` (keep stdin open) and `-t` (allocate pseudo-TTY) are required. Without `-t`, the TUI library detects no TTY and either refuses to start or falls back to dumb output.

Inside the container, three things matter:

| Requirement | Why | Dockerfile Snippet |
|-------------|-----|---------------------|
| UTF-8 locale | Without it, Unicode characters render as `?` or boxes | `ENV LANG=C.UTF-8 LC_ALL=C.UTF-8` |
| `$TERM` matching laptop terminal | Determines colour profile and capability detection | `ENV TERM=xterm-256color` (or pass via `docker exec -e`) |
| Terminfo database | Minimal images often ship without it; some TUI libraries fail without it | `RUN apt-get install -y ncurses-term locales && locale-gen C.UTF-8` |

A clean Dockerfile snippet for TUI-friendly containers:

```dockerfile
ENV LANG=C.UTF-8 \
    LC_ALL=C.UTF-8 \
    TERM=xterm-256color
RUN apt-get install -y ncurses-term locales && \
    locale-gen C.UTF-8
```

### Design Implications

Six things worth being deliberate about in the SG/Edge TUI design because of the deployment chain:

| Implication | What To Do |
|-------------|------------|
| Cold-start latency matters more than usual | First frame should render under 100ms; user is already waiting through three hops |
| Static-image export becomes more valuable | Pressing `r` to copy a snapshot is useful before disconnecting or for sharing with a colleague not currently SSM'd in |
| Mouse support is optional, not assumed | Different SSH/SSM clients handle mouse events differently; keyboard primary, mouse as enhancement |
| Throttle high-frequency updates | Bytes go over the network on every redraw; 5-10 Hz is plenty for operational data, kinder to flaky connections than 60 FPS |
| Connection drops should be graceful | Run the TUI as a foreground process inside the container; underlying SG/Edge services run as separate processes that survive the TUI's death |
| Locale and `$TERM` should be set at the container level | Do not rely on environment inheritance through three hops; set it explicitly in the Dockerfile and confirm with diagnostics |

### Diagnostics For When Something Breaks

A small set of commands worth knowing for when the chain produces broken output:

```bash
# Inside the container, confirm the environment looks right
echo $TERM        # expect xterm-256color or terminal-specific
echo $LANG        # expect C.UTF-8 or similar UTF-8 locale
locale            # confirm UTF-8 is active

# Test colour support
tput colors       # expect 256

# Test Unicode rendering
echo "█▓▒░ ▁▂▃▄▅▆▇█ ╭─╮ │ │ ╰─╯"
# If you see boxes or question marks, locale or font is wrong

# Test 24-bit truecolor
printf '\x1b[38;2;255;100;0mTRUECOLOR\x1b[0m\n'
# If this renders orange, 24-bit colour works; if not, fall back to 256
```

These should ship as a `sg-edge-tui-diagnose` subcommand that operators can run before reporting issues.

### Why This Matters For The Brief

The TUI is built once but accessed through this chain by every operator. Getting the deployment chain right at the Dockerfile and SSM document level is a small piece of work that pays off across every TUI session forever. Treating it as an implementation detail rather than a design constraint is the common mistake; treating it as part of the design surface makes the experience consistent.

This also reinforces the framework recommendation in the main brief. Textual + Rich (Python) is well-tested in containerised remote deployments; Bubble Tea + Lipgloss (Go) ships as single binaries which can be even simpler in containers (no Python runtime required). Both work; the deployment chain does not push the choice strongly either way.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not a replacement for the SG/Edge CLI primitives.** Both coexist; the TUI sits on top.
- **Not a web dashboard.** This is specifically a terminal experience. A web dashboard might come later but is a separate piece of work.
- **Not multi-cluster yet.** v1 shows one SG/Edge deployment. Multi-deployment view is a future expansion.
- **Not a deep monitoring system.** Real-time observability lives in the unified observability session; this TUI is operator-focused.
- **Not commercial v1.** This is internal tooling; the moment it becomes a customer-facing surface, the requirements change.

## Honest Risks

Three risks worth flagging:

**Risk 1: Visual richness eats engineering time.** The difference between "functional TUI" and "delightful TUI" is non-trivial. Mitigation: ship v1 functional; iterate on delight. Do not block initial release on perfect aesthetics.

**Risk 2: Terminal compatibility issues.** Different terminals support different Unicode subsets, colour profiles, and mouse behaviour. Mitigation: target a modern terminal (iTerm2, Wezterm, Kitty, Windows Terminal) for the rich experience; ensure graceful degradation on older terminals.

**Risk 3: The TUI becomes a maintenance burden separate from the primitives.** If the primitives evolve faster than the TUI keeps up, the TUI shows stale state. Mitigation: keep the TUI thin over the primitives; treat primitives as the source of truth; update TUI views via subscription to primitive output rather than parallel state.
