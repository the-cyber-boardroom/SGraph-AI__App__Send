## What This Is

The admin and management surface for the labs scheme we settled yesterday. The DNS mechanism is decided (TXT records as the registry signal, A records for routing, per yesterday's vault registry brief and its addendum); this brief covers **the operational reality of running and managing predetermined labs**: who can create them, what their lifecycle looks like, what the admin UI shows, how policies are enforced, how recovery and audit work.

The forcing function from the voice memo is concrete and urgent: **we cannot let anyone hitting `anything.sg-labs.app` get a new vault** (not scalable, not safe), but **we do want to create a controlled set of 5-20 predetermined labs** that work via the on-demand provisioning machinery. The DNS question is solved; the admin question is what this brief addresses.

Two things the brief deliberately does not redo:

- The DNS mechanism (settled: TXT records signal "registered", A records do routing; see yesterday's brief plus addendum)
- The on-demand provisioning workflow itself (the 50-second EC2 spin-up; see yesterday's on-demand provisioning brief)

What it does cover: **the admin interface, the lifecycle policies, the access control, the operational discipline that turns the DNS-plus-provisioning primitives into something a small team can actually manage**.

## What The Admin Interface Manages

The admin interface manages labs across their full lifecycle. A lab is a registered slug (`john-cv.sg-labs.app`, `demo-accountant.sg-labs.app`, etc) with a known purpose, an owner, a template, a lifecycle policy, and observable state.

The core managed object:

```yaml
lab:
  slug: demo-accountant-1
  domain: sg-labs.app
  owner: project-lead
  template: accountant-demo-v2
  status: idle | provisioning | live | error | torn-down
  policy:
    max-session-duration: 30m
    idle-timeout: 15m
    scheduled-teardown: optional cron expression
    cost-cap-per-session: £0.05
    max-sessions-per-day: optional
  access:
    create-by: [list of identities or tokens]
    wake-by: [list of identities or tokens]
    can-be-public: bool
  current-instance:
    id: i-xxx (if live)
    started-at: timestamp
    ip: address
  history:
    - vault commits showing every state transition
```

Each field maps to operational decisions: who can create new instances, how long they stay alive, what the cost cap is, where activity is logged. The admin vault holds these objects; the admin UI manipulates them; everything else (DNS sync, lifecycle enforcement, observability) is downstream.

## What The Admin UI Does

A reasonable v1 UI has six surfaces:

| Surface | Purpose |
|---------|---------|
| **Lab inventory** | List of all registered labs with status badge (idle / provisioning / live / error / torn-down) |
| **Lab detail** | Per-lab view: current state, recent activity, cost-to-date, manual controls |
| **Create lab** | Form for registering a new lab: slug, template, owner, policy |
| **Templates** | Catalogue of available lab templates (accountant demo, CV demo, etc.); upload or modify |
| **Activity log** | Cross-lab feed of recent events; filterable by lab, type, time |
| **Cost dashboard** | Per-lab and aggregate cost; flows into the pre-auth metering substrate |

The UI runs as a vault app on the platform itself (the SG/App pattern from earlier this month). The admin vault holds the registry; the UI reads/writes the vault; the platform's own primitives provide everything else.

This is the structural pattern from the AppSec mini-tools brief earlier this week, applied to the operational concern of managing labs. We are dogfooding at the management layer.

## The Lifecycle In Operational Terms

A lab moves through observable states. The voice memo named three; the operational reality has more:

| State | What It Means | Typical Duration |
|-------|---------------|------------------|
| **Registered (idle)** | Lab exists in registry; no instance running; TXT record present; A record points at Lambda | Indefinite |
| **Waking** | Someone has triggered provisioning; EC2 is booting | 30-60 seconds |
| **Live** | Instance is running; A record points at instance IP; users can access | Bounded by policy |
| **Cooling** | Idle timeout approaching; no activity for N minutes | 5-15 minutes before teardown |
| **Tearing down** | Instance being destroyed; A record reverting to Lambda | 10-30 seconds |
| **Error** | Something went wrong; admin attention required | Until acknowledged |
| **Suspended** | Admin has paused this lab; can be resumed | Indefinite |
| **Retired** | Lab is removed from active inventory; history retained | Indefinite |

State transitions are auditable (every transition commits to the admin vault). The UI shows current state in real time. Most transitions are automatic (policy-driven); admins can force any transition manually.

This is more detailed than "create / running / destroyed" because the operational reality is more nuanced. A lab can be live but cooling (about to tear down). A lab can be suspended (registered but explicitly paused). A lab can be in error (acknowledgement required). The state model needs to match what operators actually deal with.

## Policy Decisions That Need Defaults

For 5-20 labs run by a small team, sensible defaults matter more than infinite flexibility. The brief proposes specific defaults:

| Policy | Default | Why |
|--------|---------|-----|
| Max session duration | 30 minutes | Long enough for meaningful demos; short enough to cap accidental cost |
| Idle timeout | 15 minutes | Standard pattern from the container hosts brief |
| Cost cap per session | £0.05 | At ~$0.01 per session base cost, this is 5x headroom |
| Max concurrent live instances per lab | 1 | Simple; multi-user same instance is fine |
| Max sessions per day per lab | 50 | Caps accidental abuse |
| Reset on activity | Yes | Sessions extend if activity is happening |
| Require pre-auth balance | Yes | Composes with the metering substrate |
| Public discoverability | No (per-lab opt-in) | Conservative default; explicit opt-in needed |
| Scheduled teardown | None by default | Add per-lab if a known nightly window exists |
| Provisioning retry on failure | 2 retries | Cover transient AWS issues; fail hard after that |

These are starting defaults. The admin UI lets per-lab override; observability shows where defaults are hit so we can tune.

## Access Control: Who Does What

This is the part the voice memo asked to think through. Several distinct concerns:

| Concern | Question |
|---------|----------|
| **Who can create labs?** | Today: project lead only. Eventually: team members; later: customer partners managing their own labs |
| **Who can wake an existing lab?** | Depends on the lab. Some are public (anyone can wake); some are gated (specific tokens) |
| **Who can manage a lab once created?** | The owner. Eventually delegation to teams |
| **Who can see usage and costs?** | The lab owner. Aggregate for the platform admin |
| **Who can change policies?** | The lab owner (within platform limits). Some hard limits set platform-side |
| **Who can retire/delete a lab?** | Owner only. Two-step confirmation (the admin vault retains history regardless) |

For v1 with 5-20 labs, the model is simple: **the project lead is the platform admin; lab owners are explicitly assigned per lab**. Most labs initially have the project lead as owner. A few might be owned by trusted team members or partner accountants.

The access model lives in the admin vault. Each lab has an `access` block (sketched above) listing identities or tokens that can do specific actions. Identity here can be:

- A Simple Token from the credential manager (the cleanest option; revocable; scoped)
- An OAuth identity (if we wire up GitHub/Google login for admin access)
- An API key (for programmatic admin operations)
- Project lead's master credential (override for emergency)

Composability with the credential manager from earlier this week matters: an admin UI session presents Simple Tokens; the labs scheme verifies them; the credential manager handles revocation and rotation.

## The Templates Question

A lab is provisioned from a template. The template defines: the AMI to boot, the vault contents to load, the apps to install, the workflows to enable, the cost shape.

Reasonable v1 templates:

| Template | What It Creates |
|----------|-----------------|
| **Demo: Accountant** | The full side-by-side personas demo from yesterday's brief |
| **Demo: Recruitment** | Recruitment-vertical demo (planned) |
| **Demo: News** | Newsroom workflow demo (planned) |
| **Demo: Risk** | Risk-vertical demo (planned) |
| **Demo: CV / Portfolio** | The CV demo for the portfolio market |
| **Generic Vault** | Empty vault with the standard app; for ad-hoc experimentation |
| **Empty (Sandbox)** | Minimal vault for testing platform changes |

Templates live as their own thing, probably as **template vaults** (each template is a vault collection that gets cloned when a lab is provisioned). This composes with the vault collection pattern from earlier this week and the offline-bundle direction from yesterday's vault discovery brief.

The admin UI lets you:

- Browse the template catalogue
- See per-template usage statistics
- Edit a template (changes apply to new lab provisions, not existing instances)
- Promote a successful experiment vault into a reusable template

This template-as-vault approach means **a template is itself a managed object**. It gets backed up (today's backup brief covers this), versioned (vault commits), and shared (the discovery primitives from yesterday).

## Observability And Audit

The admin UI surfaces what operators need to see. Three observability layers:

| Layer | What It Shows | Where |
|-------|---------------|-------|
| **Real-time state** | Current state of every lab; current cost; current users | Lab detail page |
| **Historical activity** | Every state transition; every cost event; every error | Activity log + per-lab history |
| **Aggregate analytics** | Trends across all labs; cost breakdown; usage patterns; error rates | Cost dashboard + analytics page |

This flows into the unified observability session from earlier this week. Lab events are queryable alongside other platform events. The admin UI is a focused view on the lab-relevant subset.

Critically, **every administrative action commits to the admin vault**. The vault is the audit log. If a lab was created, the commit shows who created it. If a policy was changed, the commit shows what changed. If a lab was retired, the commit shows when and by whom. This is audit-trail-for-free, courtesy of the vault model.

## Error And Recovery Scenarios

A lab can fail in several ways; the admin UI needs to handle each.

| Failure | What Happens | Admin Action |
|---------|--------------|--------------|
| **Provisioning fails** (EC2 won't start, AMI bad, etc.) | State → Error; alert raised | Admin investigates; retry or fix template |
| **DNS sync fails** | State → Error; lab not reachable | Admin reconciles DNS state with admin vault |
| **TXT record exists but vault has no entry** | Drift detected by reconciliation job | Admin decides: register lab or remove TXT |
| **Pre-auth balance insufficient** | Wake refused; user shown clear message | User tops up; or admin grants override |
| **Instance crashed mid-session** | State → Error; auto-restart attempt | Admin reviews logs; may retire lab if recurring |
| **Idle teardown but state not updated** | Reconciliation job catches it; state updated | None usually; logged for review |
| **Stuck in provisioning state** | After 5 minutes, marked Error | Admin investigates AWS state |

Most of these are handled automatically with reasonable defaults; admin intervention is the exception. But the UI needs to make the exception case clear.

A reconciliation job runs hourly to catch drift between the admin vault (truth) and the actual world (DNS records, EC2 instances, lab state). Drift is alerted; the admin can investigate or trigger automatic resync.

## What This Does Not Try To Be

Deliberate scope limits:

- **Not customer-facing self-service lab creation in v1.** Project lead approves labs; customers do not create their own yet.
- **Not multi-tenant in v1.** All labs share the platform's infrastructure account; multi-tenant isolation is a v2 question.
- **Not lab analytics for business intelligence.** Cost and usage tracking, yes; product-analytics dashboards, later.
- **Not template marketplace.** Templates are internal initially; sharing across organisations is a v2 question.
- **Not automatic template generation from existing vaults.** Manual template creation; auto-detection of "this could be a template" is later.

## Honest Risks

Three risks worth flagging:

**Risk 1: The admin UI becomes complex enough to need its own admin.** Avoid this by ruthlessly keeping the UI simple. Six surfaces; clear defaults; minimal options. If a feature requires a "training session" for the project lead to use, it has not been designed right.

**Risk 2: Templates drift from what works in production.** A template that worked at creation may not work three months later as the platform evolves. Mitigation: CI from earlier this week runs against templates regularly; failed templates are flagged.

**Risk 3: Reconciliation between admin vault and actual world surfaces edge cases.** Drift will happen; the question is whether reconciliation handles it cleanly. Mitigation: start with strict reconciliation (vault is truth; force re-sync); relax to softer reconciliation as edge cases are understood.

## Open Questions

| Question | Notes |
|----------|-------|
| Single admin UI for all environments, or per-environment? | Single for v1 (we have one production environment); split if/when we have staging |
| How do we surface "lab is unhealthy" without spamming admin? | Aggregate alerts; per-lab thresholds; standard ops patterns |
| Should partner accountants get a read-only view of their own lab? | Yes, eventually; v2 work |
| Template versioning: when a template changes, what happens to existing instances? | Probably: existing instances keep running on the old template version; new provisions use new; explicit version-pinning |
| How granular should cost attribution be? | Per-lab-per-session for v1; per-action within a session if useful later |
| Do we need a separate "approve new lab" gate, or trust the project lead to self-approve? | Self-approve for v1; gating for v2 if multi-admin |
| What happens to retired labs' data? | Retained in vault for audit; not provisioned; can be unretrieved manually if needed |
| Should admin actions require 2FA / second-person confirmation for destructive ops? | Two-step confirmation in the UI; full 2FA when we add more admins |
