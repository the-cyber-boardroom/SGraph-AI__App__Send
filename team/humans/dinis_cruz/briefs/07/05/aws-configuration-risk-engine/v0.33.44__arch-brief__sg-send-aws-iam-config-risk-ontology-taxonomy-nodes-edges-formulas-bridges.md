## What This Is

A first-pass ontology and taxonomy for the AWS IAM configuration risk engine: **one Node Type Formula set that bridges into the existing risk ontology rather than replacing it, laid out in layers from Reality and the Twin at the floor, up through the AWS structural nodes that model the account, its principals, policies, statements, actions, and resources, up through the grounding rungs the corpus already owns, Measure, Evidence, Fact, Vulnerability, and Risk, up to the reach-and-consequence nodes that carry the AWS-specific risk semantics, the Grant, the AuthorizationClosure that is the agentic union of everything transitively reachable, the Capability, the BlastRadius, and the per-region CostCeiling, and finally the acceptance and accountability nodes that drive the sign-off; every edge is directed with a named inverse, so the graph has an inward grounding path and an outward reach path; every type is a path-pattern a query computes rather than a label a person assigns, so a public bucket is a Fact and becomes a Vulnerability only when an upward path to a real Risk exists, which is the context-not-configuration principle from part one made structural; and the whole set is designed to be maintained programmatically as Type_Safe classes and to bridge, at declared points, to OWASP, the CIS AWS Foundations Benchmark, AWS-native signals, and the RAMM.** It is the third brief of 5 July (cross-ref: the v0.33.44 engine dev-brief and rating arch-brief, the v0.33.36 grounding-ladder, node-type-formulas, and ontologies-of-ontologies briefs, and the v0.33.40 agent-authorization brief). New contributions: **the layered AWS IAM node taxonomy, the directed edge set with named inverses, the AWS Node Type Formulas including the authorization closure and cost blast radius, and the programmatic Type_Safe shape.**

## Design Principles, Inherited Not Invented

The ontology follows five rules the corpus already established, so it is an application of the ontology core rather than a new model. It bridges into the existing risk ontology at the grounding rungs, keeping AWS as its own owned sub-ontology connected at declared points rather than merged. Types are computed: a node's class is the path-pattern it satisfies, run as a query, not a stored label. Edges are directed and each has a named inverse, giving every node an inward grounding path and an outward reach path. Everything grounds down through a Twin to Reality, where the twin is the live AWS object and its connectedness to the account is itself a measure. And a configuration is only ever a Fact until it earns an upward path to a Risk, so the ontology cannot express a bare setting as a finding.

## The Layered Taxonomy

The node types sit in six layers. The lower three are grounding and are largely reused; the upper three carry the AWS risk semantics.

**Layer 0, grounding floor (reused).**

| Type | Meaning |
|------|---------|
| Reality | The live AWS account and the real resource being reasoned about |
| Twin | The digital twin of an AWS object (a policy, a bucket, a principal); connectedness to reality is measurable |

**Layer 1, AWS structural model.**

| Type | Meaning |
|------|---------|
| Account, Region, OrgUnit | The account boundary, the regional scope, the organisation tree |
| Principal | Abstract identity; subtypes IAMUser, IAMRole, ServiceRole, FederatedIdentity, RootUser, Agent |
| Policy | Abstract policy document; subtypes IdentityPolicy, ResourcePolicy, PermissionsBoundary, SCP |
| Statement | A single policy statement: Effect, Action set, Resource set, Condition |
| Action | An IAM action, for example `s3:GetObject` or `ec2:RunInstances` |
| Resource | Abstract target; subtypes S3Bucket, EC2Capacity, KMSKey, RDSInstance, LambdaFunction, and others |
| ConfigurationSetting | A specific setting on a resource, for example BlockPublicAccess or bucket ACL |
| Condition | A constraint on a grant (source IP, MFA, tag, principal org) |

**Layer 2, grounding rungs (reused from the grounding ladder).**

| Type | Meaning |
|------|---------|
| Measure | An observation on a twin: public-access is true, access-logging records is zero, region vCPU quota is N |
| Evidence | Supports or challenges a claim, grounded by a downward path to a Measure |
| Fact | Carries the evidential burden, grounded by a downward path to Evidence |
| Vulnerability | A Fact with an upward path to a Risk; nothing more, nothing less |
| Risk | A judgment with a downward path to a Vulnerability and an upward path toward a top risk |

**Layer 3, reach and consequence (AWS-specific).**

| Type | Meaning |
|------|---------|
| Grant | An effective permission: a Principal can perform an Action on a Resource under Conditions, net of denies |
| AuthorizationClosure | The transitive union of every Grant reachable from a Principal over assume-role, pass-role, and wildcard edges |
| Capability | An effect a Grant enables: read-data, write-data, delete-data, spawn-compute, exfiltrate, escalate-privilege |
| BlastRadius | The unit of consequence a Capability can affect, expanded through confidentiality, integrity, and availability |
| CostCeiling | The maximum spend a spawn-compute Capability can incur, bounded per region by the account's service quotas |
| DamageWindow | The time a consequence runs before detection, derived from the monitoring and billing-lag posture |

**Layer 4, controls and context.**

| Type | Meaning |
|------|---------|
| PreventiveControl | Blocks reach: SCP, PermissionsBoundary, BlockPublicAccess, deny statement |
| DetectiveControl | Sees consequence: CloudTrail, GuardDuty, access logging, Cost Anomaly Detection |
| DataClassification | What the resource holds: none, public, internal, confidential, regulated |
| BusinessContext | Owner, environment (prod or dev), criticality, the account's asset weight |

**Layer 5, agentic overlay and acceptance.**

| Type | Meaning |
|------|---------|
| Agent | A Principal that is a non-human identity, an agent twin carrying permissions, capabilities, and track record |
| Invocation | The moment a Grant can be invoked, by a human or an agent |
| CapabilityCertificate | A scoped, PKI-signed grant with a block list that bounds the closure |
| LethalTrifectaStatus | Whether untrusted input, ability to act, and an exfiltration path co-occur |
| AcceptanceDecision | No-deny, accept-in-a-direction, for-an-interval, owned, signed |
| Owner, DecisionAuthority | Technical owner, business owner, and the underwriting authority chain |

## The Edge Types, Directed With Named Inverses

Every edge is stored once and read both ways. The outward direction is reach (what this opens); the inward direction is grounding or authorisation (what backs or authorised it).

| Outward (reach) | Inward (inverse) | Typical from, to |
|-----------------|------------------|------------------|
| has_policy | attached_to | Principal, Policy |
| allows | permitted_by | Policy, Statement |
| grants | granted_by | Statement, Action |
| can_assume | assumable_by | Principal, IAMRole |
| acts_on | acted_on_by | Grant, Resource |
| reaches | reachable_from | Principal, AuthorizationClosure |
| enables | enabled_by | Grant, Capability |
| exposes | exposed_by | Capability, BlastRadius |
| bounded_by | bounds | CostCeiling, Region quota |
| can_invoke | invocable_by | Principal or Agent, Grant |
| protected_by | protects | Resource or ConfigurationSetting, PreventiveControl |
| monitored_by | monitors | Resource, DetectiveControl |
| contains | contained_in | Resource, DataClassification |
| gives_rise_to | arises_from | Vulnerability, Risk |
| backed_by | backs | Fact, Evidence; Evidence, Measure |
| observed_on | observes | Measure, Twin |
| connected_to | tracks | Twin, Reality |
| owned_by | owns | Risk or AcceptanceDecision, Owner |
| accepted_by | accepts | Risk, AcceptanceDecision |
| certified_by | certifies | Grant, CapabilityCertificate |

## The AWS Node Type Formulas

Each type is the path-pattern a query tests, with each edge test binary, so classification is computed and the ontology's choices are visible and arguable.

- `Grant := a Principal with an outward allow-path through a Statement to an Action AND an acts_on path to a Resource, net of any deny reachable via SCP, PermissionsBoundary, or explicit deny.`
- `AuthorizationClosure(P) := the transitive union of every Grant reachable from Principal P over can_assume, pass-role, and wildcard-action edges. This is the agentic union: for an Agent, the closure is the rating floor, not the nominal grant.`
- `PublicExposure := a ConfigurationSetting on a Resource with a reach-path from an anonymous or wildcard Principal AND no protected_by preventive control on that path. It is still a Fact.`
- `Fact := a node with a downward backed_by path to Evidence.`
- `Vulnerability := a Fact with an upward gives_rise_to path to a Risk. A PublicExposure becomes a Vulnerability only once contains reaches a DataClassification above public and exposes reaches a real BlastRadius.`
- `CostBlastRadius := a Capability of type spawn-compute with a bounded_by path to a per-region CostCeiling AND an associated DamageWindow.`
- `AcceptableForInterval := a Risk with an accepted_by path to an AcceptanceDecision carrying an owner, a direction, an interval, and a sign-off.`

## The Graph, Rendered On Two Axes

```
             TOP RISK (register: "loss of regulated data", "uncontrolled cloud spend")
                  ^  gives_rise_to (up) = why it matters
               RISK
                  |  arises_from (down)
          VULNERABILITY   = a config Fact WITH an up-path to a Risk
                  |  backed_by (down)
               FACT        "bucket is publicly readable" / "role can RunInstances"
                  |  backed_by (down)
            EVIDENCE       bucket policy doc, CloudTrail, quota reading
                  |  measured_by (down)
             MEASURE       public=true; logging records=0; vCPU quota=N
                  |  observed_on (down)
               TWIN        digital twin of the policy / bucket / principal
                  |  connected_to (down)
             REALITY       the live AWS account and resource

   REACH axis (outward, from the Grant):
     PRINCIPAL --grants--> GRANT --acts_on--> RESOURCE --contains--> DATA CLASS
         |                   |--enables--> CAPABILITY --exposes--> BLAST RADIUS
         |--reaches--> AUTHORIZATION CLOSURE  (union of all transitively reachable grants)
         |--can_invoke--> INVOCATION (human | agent)
     CAPABILITY(spawn-compute) --bounded_by--> COST CEILING (per region) + DAMAGE WINDOW
```

## The Programmatic Shape

The ontology is maintained in code, as part one requires, so the taxonomy is a set of Type_Safe classes over a shared node base, in the style of the corpus semantic-graph library. A sketch, not the implementation:

```python
class AWS_Config_Node(Semantic_Node):                 # extends the corpus node base
    account_id  : Account_Id                          # structural scope
    region      : Region        = None                # None for global resources
    twin_id     : Twin_Id       = None                # grounding: the live-object twin
    # id, label, node_type, provenance, confidence inherited from Semantic_Node

class IAM_Principal(AWS_Config_Node):
    principal_kind : Principal_Kind                    # user | role | service | agent | root
    is_agent       : bool        = False

class Grant(AWS_Config_Node):
    principal_id : Node_Id                             # granted_by inverse target
    action       : IAM_Action
    resource_id  : Node_Id
    conditions   : List__Condition
    effect       : Effect        = Effect.allow        # net of denies at build time

class Authorization_Closure(AWS_Config_Node):
    principal_id : Node_Id
    grants       : List__Node_Id                       # the transitive union
    delta        : List__Node_Id                       # closure minus nominal grant

class Capability(AWS_Config_Node):
    kind         : Capability_Kind                     # read | write | delete | spawn_compute | exfiltrate | escalate

class Cost_Ceiling(AWS_Config_Node):
    max_spend_per_hour : Decimal                        # bounded_by region vCPU quota
    quota_basis        : Str__Quota_Code                # e.g. L-1216C47A
    damage_window_hrs  : Decimal                        # detection lag

class Schema__AWS_Risk_Graph(Schema__Semantic_Graph):  # ontology_id + rule_set_id as FKs
    pass                                               # nodes: Dict__Nodes__By_Id, edges: List__Edges
```

Classification (`is this a Vulnerability?`) is a query over `edges`, not a field on the node, so promotion and demotion are edge events exactly as the node-type-formulas brief requires.

## Bridges To Existing Frameworks

The AWS ontology stays its own and connects at declared points, bridges not merges. The CIS AWS Foundations Benchmark and AWS-native signals such as IAM Access Analyzer and AWS Config supply findings and reachability that attach as Evidence and Measure. OWASP feeds the risk vocabulary and, through the RAMM, the maturity overlay. NIST and control catalogues attach at the Control nodes. Each bridge is a crosswalk: satisfy a control here, and the corresponding external requirement is marked satisfied there, without either side adopting the other's schema.

## What This Does Not Try To Be

- **Not a merge of AWS into the risk ontology.** AWS is an owned sub-ontology bridged at declared points.
- **Not a config linter.** A setting is a Fact; it is never expressed as a finding without an upward path to a Risk.
- **Not the full permission model.** The first pass is IAM-centred; other services attach as Resource subtypes later.
- **Not the final schema.** The Type_Safe shape is a sketch to be reconciled with the semantic-graph library.

## Honest Tensions

| Tension | Note |
|---------|------|
| Closure completeness versus tractability | The authorization closure is the honest reach but is expensive to compute fully over assume-role and wildcard chains |
| Deny resolution timing | Pre-computing net-of-deny grants keeps the graph clean but bakes an evaluation the live account can change under you |
| Reuse versus AWS sharpness | Bridging to the corpus rungs is economical, but IAM's edge cases may need AWS-only node kinds |
| Ontology in code versus AWS drift | A programmatic ontology is testable but must track AWS as actions, services, and quota mechanics change |

## Open Questions

| Question | Notes |

| What is the canonical Action-to-Capability table? | The mapping from IAM actions to read, write, spawn, exfiltrate, escalate |
| How deep is the closure computed by default? | Bounding assume-role and pass-role traversal without missing reach |
