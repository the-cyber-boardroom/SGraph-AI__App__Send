# The AWS Configuration Risk Engine: Context, Not Configuration (Part One, the Python Engine)

**version** v0.33.44
**date** 5 July 2026
**from** Human (project lead)
**to** @Dev, Architect, Product, Strategy
**type** Dev brief (semantic graph)

*Part one of a two-part brief. This is the deterministic Python engine; the companion v0.33.44 arch-brief is the browser rating layer it feeds.*

---

## What This Is

The build spec for an AWS configuration risk engine, IAM first: **an engine that treats a cloud configuration as a set of facts to be classified rather than a verdict to be pronounced, because the existence of a configuration is never itself a risk, only context makes it one, so a public S3 bucket is a fact and not a problem until you know what it holds, what mitigations and monitoring surround it, and what the account can reach; the engine is a Python codebase that builds the ontology and taxonomy programmatically rather than by hand, runs the deterministic analysis, the calculations, and the formulas, reuses the existing Python codebase and the digital twins already built, is covered by unit tests, and emits a set of JSON objects as its only output; it grounds each AWS object as a twin, an IAM policy, an S3 bucket, an EC2 permission, connected to reality the way the grounding ladder requires, and it deliberately does not decide how risky anything is, it produces the evidenced, typed objects that the browser rating layer then rates; and it runs anywhere, on ephemeral compute or in the browser, so the same engine serves a headless job and a client-side UI, with AWS first because we own the code and the twins, generalising to any other cloud after.** It is the first brief of 5 July (cross-ref: the v0.33.36 grounding-ladder and node-type-formulas briefs, the v0.33.35 digital-twins brief, and the v0.33.38 black-box handover brief). New contributions: **the context-not-configuration principle as the engine's core, the programmatically-maintained ontology and taxonomy, and the JSON-object handover to the rating layer.**

## The Question This Answers

The engine answers a single, sharp question. The project lead: **"what are the risks that we have with a specific AWS configuration?"** The scope is deliberately narrowed for the first pass to IAM, Identity and Access Management, because IAM is where the reach of a configuration is decided and where the corpus already has the twins to model it. The project lead: **"we might even make it IAM specific, an AWS IAM policy risk acceptance."** Other services attach later; IAM is the spine because it governs what everything else can do.

## The Core Principle: A Configuration Is Not a Risk

The heart of the engine, and the place the project lead thinks most similar attempts go wrong, is that a configuration existing is not a problem in itself. The project lead: **"the fact that a particular configuration exists doesn't mean that there's any risk immediately."** The worked example is the one everyone reaches for and almost everyone mis-handles. The project lead: **"an S3 bucket that is public, that in itself is not enough to create a problem."** Public is a fact, not a finding. Whether it is a risk depends entirely on context. The project lead: **"you need to have context, you need to see what's on the S3 bucket, what other security mitigations are in place, what monitoring is in place."** An empty public bucket in an account with no assets is close to harmless; a public bucket holding regulated data with read-write access in an account with wide reach is a serious exposure. The engine's job is to hold the fact and gather the context, not to fire an alert on the fact alone. This is the grounding ladder applied to cloud: the public-bucket setting is a Fact, and it becomes a Vulnerability only when an upward path to a real business Risk exists.

## A Semantic-Graph Engine, Not a Rules List

The engine is built as a semantic graph, so the model is nodes, edges, and evidence rather than a flat list of checks. The project lead: **"we take a semantic graph approach, we create the ontology and a taxonomy and see how much we can reuse."** The reuse point is load-bearing. The ontology of AWS objects, their permissions, and their relationships should lean on what the corpus already defines rather than inventing a parallel model, so the AWS ontology bridges into the existing risk ontology rather than sitting beside it.

## The Ontology and Taxonomy Are Maintained in Code

The decision that shapes the whole build is that the ontology and taxonomy are programmatic artifacts, not documents someone edits. The project lead: **"what we produce is a set of JSON, a set of objects, the ontology and taxonomy maintained programmatically."** The types, the permission model, the mappings from IAM actions to reachable effects, all of it lives in code and is produced by executing the code, which is what makes it testable, versionable, and reproducible. Node Type Formulas fit this exactly: a node's classification is a path-pattern the code can compute, so promotion of a fact to a vulnerability is a query result, not a hand-applied label.

## The Deterministic Layer: Formulas and Calculations in Python

Part one is deterministic on purpose. It is the layer that calculates what can be calculated from the configuration and the data, without reaching for judgment. The project lead: **"this should be a Python based code base that does the analysis and the calculations and has the formulas."** It reuses what is already built. The project lead: **"we leverage our existing Python code base, but also the digital twins that we already have."** And it is held to the standard the rest of the codebase is held to. The project lead: **"this should be supported by unit tests, very testable code."** Deterministic, tested, and reproducible is the contract for this layer; the uncertainty and the judgment live in part two.

## Digital Twins Connect the Configuration to Reality

Each AWS object the engine reasons about is a twin, the same construct the corpus uses everywhere. An IAM policy is a twin with its statements, principals, and reachable actions as properties; an S3 bucket is a twin with its policy, its contents descriptor, and its monitoring as properties; an EC2 permission is a twin whose behaviour is the compute and cost it can bring into existence. The twins are what let the engine connect the dots between a configuration and its real effect, and the discipline of reality applies unchanged: a twin's connectedness to the real AWS account is itself a measurable property, and a gap between the twin and the live configuration is named and tracked rather than hidden.

## JSON Is the Only Output, and It Is the Handover

The engine does not render anything and does not decide risk. Its single output is a set of JSON objects, the typed, evidenced nodes and edges that describe the configuration and everything the engine could determine deterministically about it. The project lead is explicit that the risk rating happens elsewhere: **"the actual calculation of the risk is done on the browser, on the UI that we're building for Risk Mandate."** That boundary is the black-box handover the corpus already defined: the engine owns inputs to outputs, the rating layer consumes the outputs, and where you touch it you own it. The JSON contract is therefore the most important interface in this brief, because it is the seam between the two parts.

## Run It Anywhere

Because the engine is pure Python with a JSON output and no UI, it runs in more than one place. The project lead: **"we can run this on ephemeral compute, or we can even run it in a browser."** A headless job on ephemeral compute can analyse an account on a schedule; the same logic compiled to run client-side can analyse a configuration inside the browser with nothing leaving the client, which fits the zero-knowledge, sovereignty-first posture. The engine is written once and hosted wherever the deployment needs it.

## AWS First, Any Cloud After

The choice of AWS is pragmatic, not exclusive. The project lead: **"this can be done for any other cloud provider, but I know AWS, and we have a lot of the code and digital twins, so let's start there."** The ontology, the twins, and the formulas are cloud-shaped, so the same engine generalises to other providers once the AWS pass proves the model; starting where the code and the domain knowledge already exist is the fastest route to a working first version.

## What This Does Not Try To Be

- **Not a risk verdict.** The engine classifies and grounds facts; the rating layer decides how risky they are.
- **Not an alert-on-configuration scanner.** A configuration is a fact, not a finding; context is required before it is a risk.
- **Not a hand-authored ontology.** The ontology and taxonomy are produced and maintained in code.
- **Not AWS-only by design.** AWS is first because the code and twins exist; the model generalises.

## Honest Tensions

| Tension | Note |
|---------|------|
| Deterministic scope | Some risk genuinely cannot be settled deterministically; the engine must hand that uncertainty to part two rather than guess |
| Programmatic ontology versus drift | An ontology maintained in code is testable but must track AWS as IAM and services evolve |
| Reuse versus AWS specificity | Leaning on the existing ontology speeds the build but the AWS permission model has sharp edges the general model may not have |
| Twin fidelity | A twin is only as useful as its connectedness to the live account; stale twins produce confident nonsense |

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | The engine ingests an AWS IAM configuration and emits a set of JSON objects, and nothing else |
| 2 | A configuration on its own is never emitted as a risk; it is emitted as a fact with its context |
| 3 | A public S3 bucket resolves to a fact that becomes a vulnerability only via an upward path to a real risk |
| 4 | The ontology and taxonomy are produced and maintained in code, not hand-authored |
| 5 | Classification is computed as a Node Type Formula path-pattern, not stored as a static label |
| 6 | Each AWS object is modelled as a twin whose connectedness to the live account is a tracked property |
| 7 | The engine reuses the existing Python codebase and the existing digital twins |
| 8 | The engine is covered by unit tests and is deterministic and reproducible |
| 9 | The same engine runs headless on ephemeral compute and client-side in the browser |
| 10 | The JSON object schema is documented as the handover contract to the rating layer |
