# The Paragraph Is A Folder: Filesystem As The Data Source, Hashes As Change Detection, And A Stopping Rule For The Rabbit Hole

**version** v0.33.54
**date** 31 July 2026
**from** Human (project lead)
**to** Engineering, Architecture, the implementing agent

**type** Architecture brief

*Third of 31 July, refining the storage and annotation model for the canonical Act. Prior corpus work is cited by brief rather than reconstructed. Offered to be built on and challenged.*

---

## What This Is

The storage model underneath the paragraph-level graph, which turns out to be an upgrade on the position taken yesterday rather than a restatement of it: **yesterday's brief resolved the granularity question against the corpus's own February position that each paragraph is a file, and this memo goes one better, because a paragraph does not merely hold text, it accretes, gathering metadata, references, dependencies, research, subgraphs, mappings, comments and issues over time, none of which fits in a file and all of which fits in a folder, so the unit becomes a directory with the provision's text inside it alongside everything anyone ever attaches to that provision; the filesystem is then the storage and the graph is built from it rather than the other way round, which keeps the most granular representation as the master record and lets every other view be a transformation of it, and because the structure of a legal instrument is already nested, the folder hierarchy mirrors the instrument without anyone designing a schema for it; the hashes the memo mentions almost in passing are the load-bearing part, because the corpus established in March that hashing every content unit and caching derived analysis per hash reduces language model calls by an order of magnitude, which means the cost of maintaining this graph scales with change rather than with size, and applied to an amended instrument it means re-deriving hashes tells you exactly which provisions moved and only those need reanalysis, so the same mechanism is simultaneously the cost control that makes deep annotation affordable and the detector that makes amendment cheap; the ambition to annotate at word level, capturing verbs, actions and nouns in the manner of a syntax tree, is right and needs a stopping rule, and the natural one is that a word earns annotation if removing it would change who must do what, by when, or to what standard, which reduces an unbounded task to five identifiable classes; and the folder is also where participation lands, since comments and issues attach to a provision rather than to a document, which is what turns a published artefact into something people can argue with.** It is the third document of 31 July (cross-ref: the v0.33.54 canonical-Act implementation brief, the v0.6.14 fractal document signing brief, the v0.11.1 hash-caching brief, the v0.33.53 every-paragraph-is-a-graph brief, and the v0.33.48 browser-local-databases brief). New contributions: **the upgrade from paragraph-as-file to paragraph-as-folder, the filesystem as master record with the graph derived from it, the identification of hashing as simultaneously cost control and amendment detection, a stopping rule for word-level annotation reducing it to five operative classes, and the folder as the anchor for comments and issues.**

## From File To Folder

Yesterday's brief resolved the granularity question by citing the corpus's own February architecture, which held that a document is a collection of paragraphs, clauses, amendments and signatures and that the document behaves as a data room in which each paragraph is a file. That was right about the unit and understated about its shape, and this memo corrects it. The project lead: **"imagine if every paragraph becomes a folder, then we can put inside that paragraph basically all the information required, all the research, all the references, all the dependencies, all the subgraphs, all the mappings."**

The reason the folder is better is that a provision accretes. On day one it holds its text. Within a month it holds the definitions it depends on, the provisions it cross-references, the risks derived from it, the amendment history, an analysis of its operative words, a mapping from an external framework, two comments and an open question. A file holds the first of those. A folder holds all of them and stays addressable while doing it.

The project lead is explicit that this is the atom. The project lead: **"what is the smallest unit that we can do here? I think the smallest unit is the bullet point, is the paragraph."** And that the atom already carries structure. The project lead: **"that already has a nested structure."** A legal instrument is a tree before anyone models it, so the directory hierarchy is not a design decision so much as a transcription of what the instrument already is.

## The Filesystem Is The Master Record

The architectural inversion is worth stating plainly because it decides everything downstream. The project lead: **"we're using the file system as storage, and then the graph builds from there."** And the status of that store. The project lead: **"this folder is our data source, is our core, most granular database, because then it can scale."**

So the graph is derived, not primary. That has three consequences the corpus already values. It is diffable, because the store is files and directories under version control. It is inspectable without any tooling, since a human can open a folder and read what is in it. And it is portable, which the memo anticipates as the eventual distribution form. The project lead: **"eventually the argument would be that this should be a schema and a zip file that should be shared."**

It also keeps the derived views honest. The project lead: **"we can then do transformations out of this, so it doesn't actually mean that this is all the data that everybody will consume."** Everything anyone reads is a projection of the folder tree, which is the same discipline as computing the consolidated text rather than storing it.

## The Hashes Are Not Decoration

The memo mentions hashing briefly. The project lead: **"we capture the hashes of the text."** The corpus established in March why that matters, and it is more consequential here than the memo suggests.

That earlier work observed that most document edits change a small fraction of the content, and concluded that hashing every content unit, caching the analysis results per hash, and sending only uncached units for processing reduces language model calls by an order of magnitude or more.

Applied to this build, the same mechanism does two jobs at once.

**It makes deep annotation affordable.** The ambition here is to analyse every paragraph, in some cases every operative word, across a long instrument in many language versions. Done naively that is an enormous and repeated cost. Done with content-addressed caching, each distinct paragraph is analysed once and the result is reused wherever that exact text appears, including across language versions where structure repeats and across the many provisions that share boilerplate.

**It detects the amendment.** Re-derive the hashes after an amending instrument is applied and the changed provisions light up automatically. Nothing needs to parse the amending instructions to know that Article 10 paragraph 5 moved and Article 9 did not. This is the mechanism that makes yesterday's amendment-as-native-operation practical rather than aspirational, and it means the cost of staying current scales with what actually changed.

```
   paragraph folder
     +-- text          -> hash
     +-- analysis      -> cached against that hash
     +-- annotations   -> cached against that hash
     +-- references, comments, issues, mappings

   amendment arrives -> re-hash -> only changed paragraphs reprocess
   cost scales with CHANGE, not with SIZE
```

## The Index Makes It A Tree

The memo describes an indexing pattern drawn from prior work. The project lead: **"if the folder has a hash, then we have a master index, and each folder has an index of the items that it has itself, which is kind of like the approach I've been taking in other projects."**

A folder whose index records the hashes of its contents, contained by a parent whose index records the hashes of its children, is a hash tree. That structure gives three properties without further work. Integrity, since the root hash changes if anything anywhere changes. Localisation, since comparing indexes descends directly to what differs rather than scanning. And addressability, since any provision can be referred to by content rather than only by position, which matters for an instrument whose numbering is not stable under amendment.

The memo also captures why the index has to be readable rather than internal. The project lead: **"that can be all read and maintained by the other end, but also by code."** Both audiences matter, and it is the same argument made on 28 July about material that agents and people must both be able to read.

## Every Word Matters, But Not Equally

The most ambitious part of the memo is word-level structure. The project lead: **"even the text inside of it, almost every word, every verb, every word needs to have a mapping, and I think maybe we should go back and introduce that AST style structure, so we capture what's a verb, what's an action, what's a noun."** And the justification, which is exactly right. The project lead: **"that simple word acceptable is then massive, because that is a massive concept that then has its own permutation."**

That example proves the case rather than illustrating it. The work of 28 July established that the instrument requires residual risk to be judged acceptable and never defines the word anywhere in its definitions. A word-level annotation would surface that automatically: a term carrying operative weight, appearing in an obligation, resolving to no definition. That is a computable finding rather than a lucky reading.

The memo also supplies its own guard. The project lead: **"we have to follow this rabbit hole until we hit minimums of diminishing returns."** That instinct is right and needs teeth, because annotating every word of a long instrument is unbounded and most of the words are prose.

**The proposed stopping rule: annotate a word if removing it would change who must do what, by when, or to what standard.** That reduces the task to five identifiable classes.

| Class | Examples | Why it carries weight |
|---|---|---|
| Deontic operators | shall, shall not, may, must, is prohibited | They create the obligation; without one the sentence is descriptive |
| Defined terms | the instrument's own vocabulary | Each either resolves to a definition or does not, and the second case is a finding |
| Cross-references | referred to in paragraph 2, point (d) | These are edges, and they are what makes navigation possible |
| Qualifiers and thresholds | strictly necessary, as far as technically feasible, where appropriate, reasonably | They set the standard, and they are where interpretation actually lives |
| Actors | provider, deployer, importer, distributor | They determine who is bound |

Everything outside those five is text to be preserved and not annotated. That makes the rabbit hole finite, gives a defensible answer to when a provision is finished, and targets the annotation at precisely the material a risk or an obligation would need to cite.

## The Folder Is Where Participation Lands

A consequence the memo draws out and that is worth building for early. The project lead: **"if people have comments on that particular paragraph, that's where the comments will be, and we could even have issues that are directly mapped just to that folder."**

Comments and issues attached to a provision rather than to a document change what the artefact is. A published instrument that a reader can only consume is a reference. One where a reader can raise an issue against Article 10 paragraph 5, and where that issue lives permanently beside the provision, is something people participate in. That is the mechanism by which a public resource earns the attention the corpus has hoped for from it, and it costs almost nothing given the folder already exists.

It also has an internal use. An organisation applying the customised standard will produce exactly this kind of material, notes on why a provision does or does not apply to them, and it lands in the same structure.

## One Article, To The Maximum

The build discipline is stated clearly and should be enforced. The project lead: **"a pass where we focus on maybe just one article or one section, and we map it to the maximum, and we basically implement it how we would like it to do, and then we do it for the rest, so we don't have to process the whole thing in one go."**

This is stronger than yesterday's start-small instruction because it specifies the shape: not a thin pass over everything, but one article taken to completion so that the pattern is proved before it is replicated. Everything about the folder layout, the index format, the annotation classes and the caching becomes concrete on a real provision, and the mistakes are made once.

## What This Does Not Try To Be

- **Not a database.** The filesystem is the store and the graph is derived from it.
- **Not paragraph-as-file.** The unit is a folder, because a provision accretes more than text.
- **Not an annotation of every word.** Five operative classes, with a stated stopping rule.
- **Not the consumable artefact.** This is the master record; everything a reader sees is a transformation of it.
- **Not a whole-instrument first pass.** One article to the maximum, then replicate.

## Honest Tensions

| Tension | Note |
|---------|------|
| Folder per paragraph versus sheer count | A long instrument produces a very large number of small directories, and navigability has to be engineered rather than assumed |
| Filesystem as master versus query performance | Files are diffable and inspectable and are not a query engine, which is why the browser database work exists, and the sync between them is real work |
| Five annotation classes versus what gets missed | The stopping rule is defensible and will exclude words that turn out to matter, and the rule should be revisited after the first article |
| Content-addressed caching versus context | Analysis cached against a paragraph hash assumes the analysis does not depend on surrounding provisions, which for legal text is not always true |
| Comments and issues versus moderation | Participation attached to provisions is valuable and creates a public surface somebody has to look after |
| One article to the maximum versus knowing what maximum means | Completeness on a single provision is only definable once the schema exists, so the first article defines the standard it is measured against |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the folder layout and the index file format? | The concrete convention, readable by people and by code, decided once on the first article |
| What is hashed, exactly? | The raw text, the normalised text, or the text plus structure, since the choice determines what counts as a change |
| Does cached analysis survive context changes? | Whether an annotation cached against a paragraph hash is still valid when a provision it references is amended |
| Which article goes first? | Article 10 demonstrates amendment; Article 9 is already in corpus use and contains the acceptable finding |
| How are the five annotation classes detected? | Deterministically by pattern, by a model, or by a model proposing and a person confirming |
| How do comments and issues stay attached under amendment? | An issue raised against a provision that is subsequently substituted needs a defined behaviour |
| What is in the shareable zip? | The full folder tree, or a projection, and under what licence |
