# The Brief To Create The Pack: Use The Team That Already Exists, Make The Variations The Experiment, And Budget For The Review

**version** v0.33.54
**date** 31 July 2026
**from** Human (project lead)
**to** Engineering, Design, Product, the authoring session

**type** Dev brief

*Twenty-fifth of 31 July. A specification for producing a design pack rather than the pack itself. Role definitions are cited from the corpus repository rather than invented. Offered to be built on and challenged.*

---

## What This Is

The instruction for an agentic authoring session that produces a complete design pack for the field workflow, reviewed and signed off before implementation begins: **the request is for a comprehensive pack assembled by multiple agents working in parallel, covering the strategic view, the architecture, a designer mapping every page with mockups, and a developer writing enough of the code that its structure and quality can be assessed, together with quality assurance and a governance persona, so that when the work reaches a developer for real there is almost no ambiguity left and it can be built in one pass; the most useful correction is that the team does not need assembling, because the corpus already carries a documented ten-role ecosystem with a defined structure of orchestration, execution, intelligence and governance, plus a separately defined designer role, which means the session should instantiate existing roles rather than invent session-specific ones and the outputs will then land in the corpus's own vocabulary and inherit each role's stated quality bar; the governance persona is a different kind of participant from the rest, since a compliance agent reviewing the pack is a reviewer while a compliance agent walking through the workflow as a user is a simulation, and the second is far more valuable because it tests the thing the pack describes rather than the pack itself; producing several design variations is the right instinct and is better understood as an experiment run at the cheapest possible moment, which is the same principle arrived at twice already today, once about deciding budgets before committing resources and once about keeping several doors open at the same time; two constraints should be stated before the session starts, a size budget because a pack too large to read defeats its own purpose of letting one person connect the dots, and an explicit marking of which code has actually been executed, since agent-written code that has never run is a proposal rather than a verified artefact; and the reviewing sequence of vault first and repository afterwards is consistent with the publishing architecture settled earlier today, in which the vault is where things are authored and reviewed and the repository is where they are published for others to check.** It is the twenty-fifth document of 31 July (cross-ref: the v0.33.53 hand-them-the-iPad brief, the v0.33.54 vault-authors-repo-publishes brief, the v0.33.54 pre-approve-the-ladder brief, the v0.33.54 change-psychology brief, and the v0.33.50 freelance-next-steps brief). New contributions: **the instruction to instantiate the existing role ecosystem rather than invent one, the distinction between a governance reviewer and a governance persona simulation, design variations framed as an experiment at the cheapest moment, a stated review budget as a first-class constraint, and the requirement to mark executed code separately from written code.**

## What Is Being Asked For

The memo is clear about the shape. The project lead: **"a cloud session where we spin up multiple subagents that each will do an analysis and a mapping of the whole workflow."** Producing a familiar artefact. The project lead: **"an uber brief pack, and we've done this before, so this is just a variation of those."**

And the purpose is a single sign-off moment rather than a document. The project lead: **"the idea here is to clarify and leverage as much as we can the features of the vault that we're going to use, so that when we actually give this to a developer to implement it, there is very little ambiguity, and you probably should be able to do it all in one go."**

## The Team Already Exists

This is the correction worth making before the session starts. The memo describes assembling a team. The project lead: **"we need the developer, designer, the whole shebang of the team."**

That team is already defined in the corpus, in detail, with a documented structure. A role ecosystem guide sets out ten roles arranged in four groups: a **Conductor** orchestrating, an **execution** group of Dev, QA and DevOps, an **intelligence** group of Journalist, Librarian, Cartographer and Historian, and a **governance** group of Architect and AppSec. Each carries a stated primary output. A **Designer** role is separately defined, and the wider corpus adds further roles including Advocate, Sherpa, Ambassador, Translator, Ontologist and a data protection role.

Instantiating those rather than inventing session-specific agents buys three things. The outputs arrive in the corpus's own vocabulary, so the pack is legible to anybody who has read the role definitions. Each role has a stated primary output, which is a ready-made specification for what that agent must produce. And the pack becomes comparable with previous packs rather than a one-off.

There is also a strategic reason. The engagement criterion set out on 23 July was that a partner should arrive with their own agentic team defined in their brief. Running this session on the corpus's own documented roles is that standard applied inward, and a pack visibly produced by a defined team is itself a demonstration of the working practice being sold.

## Mapping The Request To The Ecosystem

The memo's list maps cleanly, with one addition and one distinction.

| The memo asks for | Existing role | Primary output for this pack |
|---|---|---|
| Strategic view | Cartographer, with the Conductor framing | Where this sits, and the map of what it replaces |
| Description | Journalist or Conductor | The narrative a reader starts with |
| Architecture view | Architect | Decisions, boundaries, and the vault interface contract |
| Every page mapped, mockups, ASCII art | Designer | Page inventory, flows, and several visual variations |
| Code written and reviewable | Dev | Structure, key modules, and the vault interaction code |
| How we test it | QA | Test strategy, and what must be true before the field |
| Simulate and test it out | Governance persona, see below | A walkthrough as a real user would experience it |
| Connectivity and cross-references | Librarian | The pack's own index and its edges into the corpus |

The Librarian is the addition and is not optional. A pack produced by seven agents in parallel needs somebody responsible for its coherence, its navigation and its connection back to the briefs it depends on, or it becomes seven documents rather than one pack.

## The Governance Agent Is A Persona, Not A Reviewer

Worth separating because the memo's phrasing contains two different jobs. The project lead: **"maybe even have a GRC agent that can go and simulate it and test it out."**

A governance agent could review the pack for compliance quality, which is a reviewing function and largely duplicates AppSec and Architect. Or it could **walk the workflow as the persona would**, answering the questionnaire as a compliance officer, receiving the register, and reporting where the experience fails.

The second is far more valuable, and it tests the right thing. The workflow's stated design goal is that the device can be handed to a stranger without narration, and the corpus specified on 28 July that a compliance function is one of the altitudes the register must translate for, and that validation is a distinct predicate from confirmation and acceptance. A simulated walkthrough is the cheapest available test of whether that translation actually works.

It also has a dogfooding property the corpus has already committed to elsewhere: the sovereignty work concluded that a maturity model published by a party that has not run it against itself is marketing. The same applies here.

## The Variations Are The Experiment

The memo asks for several design options. The project lead: **"we probably could then have two or three or four design mockups there and variations, so we can pick the one we like from the point of view of the architecture, the flows, the UX."**

This is right, and it is worth naming what it is rather than treating it as thoroughness. Two other briefs written today reach the same principle from different directions. The pre-approval brief argued that decisions should be taken at the moment they are cheapest, before resources are committed. The change brief argued that reversibility makes experiments safe and running several options at the same time is what makes them informative.

**Producing four mockups before any code exists is an experiment with four arms at the lowest cost it will ever have.** That framing matters for how the variations are built: they should differ on decisions that would be expensive to reverse later, rather than on surface treatment. Genuinely different flows, genuinely different information architecture, genuinely different answers to how the altitudes are navigated. Four versions of the same design in different colours is not an experiment.

## Budget The Review

A constraint the memo implies and does not state. The stated purpose is a single human review. The project lead: **"by reviewing that set of documents, I should be able to basically connect the dots."**

Parallel agents each instructed to be comprehensive will produce more than one person can read, and a pack that cannot be reviewed in one sitting has failed at the thing it exists for. So the session should carry an explicit size budget, a required single entry point that a reader starts from, and a rule that detail lives in appendices rather than in the path through the pack.

This is the same argument made on 28 July about cognitive load: extraneous effort displaces the attention available for the material itself, and a reviewer who has spent their capacity navigating has none left for judgement.

## Mark What Has Actually Been Run

An honesty requirement specific to agent-authored packs. The memo wants real code. The project lead: **"we should have the developer also propose and write down most of the code in terms of the way it's going to be structured, so we can look at code quality, we can look at the interactions with the vault."**

Code in a document that has never been executed is a proposal. It may be structurally sound and still not run, and the failure will surface at the worst moment. The pack should therefore distinguish plainly between code that was written, code that was executed, and code that was executed against the real vault interface. The same applies to the QA output: a test plan is not a test run.

This is not a reason to write less code in the pack. It is a reason to be exact about its status, and the distinction is cheap to record and expensive to discover later.

## Vault First, Repository Afterwards

The memo settles the sequence. The project lead: **"I push the pack to GitHub, which is an option, but I think in this case it's probably better to first put it in a vault so that we can review it, to get the approval and the sign-offs from me and from the business partner, before we implement it all."**

That is consistent with the publishing architecture settled earlier today rather than a departure from it: the vault is where things are authored and reviewed, and the repository is where they are published for others to check. A pack under review is authoring; a pack published for verification is the later step, and it may never need to be taken for this artefact.

## What The Pack Must Cover

The memo enumerates the moving parts and they should be the pack's contents list. The project lead: **"there's the user, the first interaction, the questionnaire form, there's the multiple risk registers, there's the multiple altitudes that we are mapping, there's also visualisations and graphs, there is the connection with the EU AI Act, which needs a section of its own, and there's the connection of these things end to end."**

Two of those deserve emphasis because earlier work identified them as the hardest. The **altitude navigation** is where the fractal register becomes tangible and is the most likely thing to land in a corridor conversation, and the 28 July brief warned that its value is in the translation rather than the number of views. And the **regulation connection** carries the copy decision flagged as the single most important in the demo: whether the output informs or accuses. Both should be designed rather than assembled.

## The Timing

Worth stating because it is the constraint everything else sits inside. The event runs from the first of August, with the business hall from the fourth. That leaves a small number of days for a comprehensive pack, a review cycle, two sign-offs and an implementation.

That is not a reason to abandon the approach, but it probably requires splitting the deliverable: a deliberately narrow specification for what can be built and tested before the event, and the full pack for the version that follows it. Choosing which is which now is considerably better than discovering it on the third of August, and the 28 July brief made the same point in different words when it observed that something will be thin and that choosing what in advance beats finding out in a hallway.

## What This Does Not Try To Be

- **Not the pack.** This specifies how the pack is produced.
- **Not a new team.** The roles exist and should be instantiated rather than invented.
- **Not a waterfall specification.** The variations are the experimentation, run where it is cheapest.
- **Not a claim that written code works.** Executed and unexecuted code must be marked differently.
- **Not a publication step.** Vault for review; the repository comes later if at all.

## Honest Tensions

| Tension | Note |
|---------|------|
| Comprehensive design before code versus fast iteration | The corpus's ethos is experiment and adjust, and a large upfront pack pulls the other way; the defence is that the architecture is settled and the variations carry the exploration |
| Parallel agents versus coherence | Seven agents working simultaneously produce volume quickly and coherence slowly, which is why the Librarian role is not optional |
| Agent-written code versus verified code | A pack can look complete and contain nothing that has run, and the reviewer cannot easily tell without being told |
| The size budget versus the ambition | The memo asks for as much detail as possible and the review requires the opposite, and something has to give |
| Four variations versus four times the work | Genuine alternatives cost real effort, and shallow variations cost effort while producing no information |
| The timeline | A comprehensive pack, two sign-offs and an implementation in a handful of days is very tight, and the honest response is to scope rather than to compress |

## Open Questions

| Question | Notes |
|----------|-------|
| Which roles run, and in what order? | Some outputs depend on others, so full parallelism is not available and the Conductor needs a sequence |
| What is the size budget? | Stated as a number before the session starts, since it cannot be imposed afterwards |
| What are the four variations varying? | The decisions that would be expensive to reverse, chosen deliberately rather than emerging |
| Where do the mockups come from? | Whether generated directly or through the design tooling, and whether they need to be interactive |
| What must be executed rather than written? | The minimum that has to actually run for the pack to be trustworthy, especially the vault interface |
| What ships before the event, and what after? | The split that the timeline requires, decided now |
| Who signs off, and against what? | Two named sign-offs are specified; the criteria they are signing against are not |
