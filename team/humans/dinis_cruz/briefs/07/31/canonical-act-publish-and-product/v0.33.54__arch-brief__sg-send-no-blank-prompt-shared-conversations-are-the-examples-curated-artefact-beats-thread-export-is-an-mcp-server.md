## What This Is

The design decisions that make a conversational layer worth using rather than merely present, and one convergence that solves two problems with a single mechanism: **the failure mode to avoid is the blank prompt, because a reader arriving at an empty box on a regulatory site does not know what is worth asking and leaves, so the interface should open with worked examples of the tool doing something genuinely useful rather than with an invitation to think of something; the model of conversation matters as much as the examples, and the memo's preference is for a curated artefact plus ephemeral chats over long accumulating threads, which is right for a reason beyond cost, since a transcript records how somebody got somewhere while a curated artefact records what they concluded, and only the second is useful to anybody else; those two ideas turn out to be one idea, because the examples that solve the cold-start problem are precisely the curated conversations other people already paid for, so a shared analysis is simultaneously the thing that teaches a new reader what to ask and the thing that makes the earlier reader's spend a public good, which is the produce-once-consume-many principle applied to conversation rather than to evidence; cost stays visible throughout, and it matters more here than for a discrete job because a conversation has no natural unit; on export, the instinct to let users take the work to their own environment is right and the implementation should not be a download, because the protocol for exactly this became the industry standard over the past year with nearly ten thousand published servers, its specification was revised three days ago to be stateless so a server scales like an ordinary web service, and both major clients now consume remote servers over HTTPS, which means the right artefact is a server that any client reads rather than a file that every client rebuilds; users building small applications over the data is feasible because the query engine already runs client-side, so a mini application is a query plus a rendering; and the sharpest thing in the memo is a question nobody has asked, which is how this compares to what an expert already has, since consultants working on this instrument have spreadsheets, prompts and workflows that took years to develop, and the honest test is whether the interface, the import and the export beat theirs.** It is the thirteenth document of 31 July (cross-ref: the v0.33.54 talk-to-the-Act brief, the v0.33.54 registrar-of-evidence brief, the v0.33.54 customised-standard brief, the v0.33.50 tools-to-productise brief, and the v0.33.48 compete-against-the-burden brief). New contributions: **the identification that shared conversations and worked examples are the same artefact, the argument that a curated artefact beats a thread because conclusions travel and transcripts do not, the recommendation that export be a protocol server rather than a file, mini applications framed as a query plus a rendering on the existing client-side engine, and the expert-workflow comparison proposed as a research task with a method.**

## The Blank Prompt Is The Failure

The memo is emphatic and correct. The project lead: **"the key thing is to not present people a sort of blank prompt; actually give them lots of examples of it working, and especially interesting analysis."**

An empty box asks the reader to already know what the tool can do. On a regulatory site the problem is worse than usual, because the visitor arrived with a vague worry rather than a formed question, and the honest version of their query is something like whether any of this matters to them. Faced with a blank prompt, most people type nothing and leave, and the ones who do type something ask a lookup question the site could already answer without a model.

The memo names the questions worth seeding with. The project lead: **"especially things like, is this relevant to me? Is this something I should care about?"** Those are exactly the queries a graph answers well and a search box does not.

## The Curated Artefact Beats The Thread

The conversational model the memo prefers is a departure from the norm and worth stating precisely. The project lead: **"it's not about massive chat threads; it's about keeping state on the conversation and capturing information, and then having ephemeral chats on top of documents and memory."**

This was flagged as a powerful concept once before, in the July tool inventory, where the chat tool was noted for its single-execution prompt and prompt-curation workflow. It deserves elevating now because it decides the architecture.

```
   LONG THREAD                        CURATED ARTEFACT + EPHEMERAL CHAT
   state lives in the transcript      state lives in an edited document
   grows with every turn              stays the size it deserves
   records how you got there          records what you concluded
   only useful to its author          useful to anyone
   cannot be meaningfully shared      is the thing worth sharing
```

There is a cost argument and a better one.

**The cost argument** is that a long thread resends its accumulated history on every turn, so spend per turn rises as the conversation continues. Prompt caching mitigates this substantially and does not eliminate the underlying shape, and on a metered public product where the user watches the number, a model that stays flat is easier to defend than one that climbs.

**The better argument** is about what the artefact is for. A transcript is a record of a search, full of false starts and clarifications that mattered only to the person having them. A curated artefact is the conclusion, edited, and it is the only one of the two a second person can use. That distinction is what makes the next section work.

## Shared Conversations Are The Examples

Here are two ideas that turn out to be one. The memo raises them separately.

First, sharing. The project lead: **"if somebody already paid for some conversation, somebody else should be able to follow it up, and I think we should think about how can we allow this to go a little bit social by allowing people to share publicly some of the conversations that they had."**

Second, examples. The project lead: **"give them lots of examples of it working."**

**The examples should be the shared conversations.** A curated analysis somebody paid for, published, becomes simultaneously the thing that teaches the next visitor what to ask, the demonstration that the tool produces something worth paying for, and a public good the original spender did not have to fund alone.

That is the produce-once-consume-many principle from the registrar brief, applied to conversation instead of evidence. And it only works because of the previous section: a shared forty-turn transcript is close to useless to a stranger, while a shared curated analysis is immediately valuable. The conversational model and the sharing model are the same design decision.

It also generates the seed corpus. The site launches with a handful of analyses produced in-house, and every user who publishes one adds to the library without being asked to write documentation.

## Cost At The Centre

The memo puts it plainly. The project lead: **"the other thing is absolutely critical: to put at the centre of this the cost of it."**

This has been argued twice this week, for the field demo and for the chat layer, and it is more necessary here than in either. A transcription job has a knowable price before it runs. A conversation does not, and a curious reader can spend without noticing. Showing the running cost is what makes an unbounded activity feel bounded, and on a public site it is also the fastest way to establish that the pricing is honest, because the number accrues in front of the person paying it.

The sharing model interacts with this well: a reader who follows a published analysis pays nothing for the work already done and pays only for their own follow-up questions, which is a visibly fair arrangement and a good reason to publish.

## Do Not Build An Export, Build A Server

The instinct is right and the implementation should be different from what the memo describes. The project lead: **"we should always have a download button or instructions for how to bring this to Claude, how to bring this to ChatGPT, how to bring this to other providers."** With the reasoning. The project lead: **"they can use their own tokens, and they can use that themselves there, because what we want is to drive adoption."**

Giving users the data to take elsewhere is consistent with the corpus's open-source position and removes lock-in as an objection, which the burden-not-features argument already established as the right competitive posture. The question is the mechanism, and file export is the weaker one.

The state of the ecosystem answers it. The Model Context Protocol has become the standard connector between models and external systems, with the official registry counting more than nine and a half thousand published servers as of May 2026 and protocol libraries passing ninety-seven million monthly downloads in March. Both major assistants consume remote servers over HTTPS, with one supporting local and remote natively and the other accepting remote HTTPS endpoints through its connector settings. And the specification was revised on **28 July 2026, three days ago**, to make the protocol stateless, removing the initialisation handshake and session identifier so that every request is self-contained, which means a server can sit behind an ordinary load balancer with no sticky sessions and scales like any web service.

Against that, the file route is documented as painful: there is no shared format between the major assistants, knowledge and instructions must be rebuilt per tool at something like half an hour each, chat history does not transfer at all, and any later update requires redoing the migration. The diagnosis in that reporting is one the corpus already holds in different words, that every migration is a rebuild because each assistant keeps memory inside itself, and the fix is to put the memory outside any one of them.

**That is precisely the vault-as-source-of-truth position.** So the export should be a stateless remote server exposing the instrument, its provisions, its amendments and the shared analyses, which any compatible client reads directly. Both assistants consume the same source, nothing is rebuilt, updates propagate, and the user brings their own tokens exactly as the memo intends.

A download button should still exist, because some people want a file and it costs nothing to provide. It should not be the primary route.

## Mini Applications Are A Query Plus A Rendering

The memo raises this and it is more feasible than it sounds. The project lead: **"the other thing we should allow them is to create mini apps to visualise the data."**

The customised-standard brief established that graph and analytical queries run entirely client-side in the browser through compiled query engines, with the database shipped alongside a static site. Given that, a mini application is a query and a rendering, with no backend and no permission required. A user who wants a view of the obligations touching a particular actor writes a query and draws the result.

The natural first step is to publish the query interface and one or two worked applications, and let the same sharing mechanism carry user-built ones. It is the same pattern as the shared analyses, applied to code rather than to prose.

## The Question Nobody Has Asked

This is the most valuable thing in the memo and it is framed as an aside. The project lead: **"as we start talking with the consultants and the experts on the EU Act, everybody has their own workflows, everybody will have their own spreadsheets, their own tools, their own prompts; what we need to understand is how do we rate against them."** And the test. The project lead: **"what can we do to give them a better UI and experience and import and export of data than they have?"**

The corpus has spent two weeks building capability and has not once asked whether the result beats what a competent practitioner already uses. That is the same discipline as asking whether the second product ships faster than the first: an honest, externally measurable test that the team cannot pass by agreeing with itself.

It is answerable with a small piece of fieldwork rather than a study. Find five or ten people who work with this instrument professionally. Watch what they actually do, rather than asking what they would like. Record the artefacts they maintain, the questions they answer repeatedly, and the part of the job they find tedious. Then identify which of those the graph does better and which it does worse, and be willing to record the second.

Three outcomes are all useful. If the graph plainly beats their workflow on a task they repeat, that task is the product. If it does not beat anything, the assumption that structure wins needs revisiting before more is built on it. And if what they actually want is import and export rather than an interface, then the protocol server above matters more than the site does, which is a cheap thing to learn early.

## Quality Control On What Gets Published

The memo anticipates the obvious risk. The project lead: **"maybe just do a bit of quality control on it, from a security point of view."**

Two distinct risks sit behind that. Published conversations may contain material a user did not intend to make public, since somebody asking whether a provision applies to them is describing their own systems, so publication must be an explicit, informed act rather than a default. And a published analysis carries apparent authority, so an incorrect one on a regulatory site damages the site rather than its author, which argues for a review step before anything appears in the seeded examples even if user-published items are labelled differently.

The informing-not-advising boundary applies with more force to a shared analysis than to a private one, because the second reader did not ask the question and cannot see the assumptions behind it.

## What This Does Not Try To Be

- **Not a blank chat box.** The interface opens with worked examples, not an invitation.
- **Not a thread-based assistant.** A curated artefact with ephemeral chats over it.
- **Not a file export.** A stateless protocol server that any client reads, with a download as a convenience.
- **Not an unmoderated forum.** Publication is explicit, and seeded examples are reviewed.
- **Not a claim to beat expert workflows.** That is a question to answer with fieldwork, and the answer may be no.

## Honest Tensions

| Tension | Note |
|---------|------|
| Sharing analyses versus disclosing estates | The most valuable conversations are the ones where a user describes their own systems, which are exactly the ones that should not be published casually |
| Curated artefacts versus how people actually chat | Everyone has learned the thread from other assistants, and a different model is better and will need explaining |
| Export as a server versus giving the value away | Making the data trivially consumable elsewhere is the right posture and forfeits the token revenue for those sessions, which has to be accepted rather than hedged |
| A protocol server versus the no-backend position | The corpus prefers static hosting, and a remote server is a server, although a stateless one is close to the cheapest possible form |
| Published examples versus apparent authority | A shared analysis on a regulatory site reads as endorsed however it is labelled, and the review burden grows with the library |
| Asking how we rate against experts | It is the right question and the answer may be that a practitioner's spreadsheet is better for what they do, which would be uncomfortable and worth knowing |
