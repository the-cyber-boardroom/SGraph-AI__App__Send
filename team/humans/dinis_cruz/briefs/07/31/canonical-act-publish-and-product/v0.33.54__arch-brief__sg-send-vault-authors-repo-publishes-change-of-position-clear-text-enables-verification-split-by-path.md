# Vault Authors, Repo Publishes: A Deliberate Change Of Position, And Why Clear Text In A Public Repo Is What Makes Verification Possible

**version** v0.33.54
**date** 31 July 2026
**from** Human (project lead)
**to** Engineering, Architecture, Product

**type** Architecture brief

*Sixth of 31 July. Records a change from the previously stated publishing plan, at the project lead's own flag. Prior corpus positions are cited by brief rather than reconstructed. Offered to be built on and challenged.*

---

## What This Is

A revised architecture for publishing the canonical Act, which the project lead correctly flags as contradicting an earlier plan and which is better for a reason larger than the one he gives: **the arrangement is that the vault remains the place content is created and edited, while a public repository holds the published material in clear text and the live site is built from that repository, with a pipeline moving content from the first to the second on release; the stated motivation is deployment cost, since cloning entire vaults on every run means that the larger a vault grows the slower every deployment becomes, when what the job actually needs is a delta, and the proposed remedy is an archive used as a build cache so that only changed content moves; the flow has two passes, a first job triggered on release, possibly from the vault itself, holding a vault key or better a read-only key, which fetches what has changed since the last run, copies those files into the repository and commits, and a second job triggered by that commit which publishes to the live site, so the whole site including its structure and content comes from the repository while being managed from the vault; the delta this needs already exists, because the folder indexes carrying content hashes specified earlier today form a hash tree, so the pipeline compares published hashes against current ones and moves only what moved, which is the same mechanism as amendment detection and as the analysis caching, three uses of one structure; the observation that not cloning the whole vault is already corpus doctrine, established for the browser file system where the vault provider was told to open lazily rather than clone on construction, makes this consistency rather than novelty; but the reason to adopt it is bigger than deployment speed, because yesterday's publishing brief made independent verification the differentiator and you cannot ask the public to check, fork or diff an encrypted vault they cannot read, so committing the published material as clear text into a public repository is the enabling condition for the thing that was already chosen as the product's distinguishing claim; and the risk it introduces is two stores holding the same content, which the memo acknowledges as needing a way to bring pull requests back, and which is best answered not by bidirectional synchronisation but by splitting ownership by path, so that generated files flow one way and contributed files flow the other and no file ever has two writers.** It is the sixth document of 31 July (cross-ref: the v0.33.54 publishing brief, the v0.33.54 paragraph-is-a-folder brief, the v0.33.48 browser-local-databases brief, the v0.33.54 canonical-Act implementation brief, and the v0.33.53 cognitive-load brief). New contributions: **the change of position recorded explicitly, the identification that the clear-text repository is what makes the verification differentiator executable rather than aspirational, the mapping of the required delta onto the hash tree already specified, the split-by-path answer to the two-store problem, and the observation that this deliberately places a copy outside the sovereignty boundary for a reason that should not be cited as precedent.**

## What This Changes

The project lead flags it himself, which is the right instinct and worth honouring rather than smoothing over. The project lead: **"I think this contradicts some of the past plans, but I feel this might actually work better."**

The corpus position has been that the vault is the source of truth, that browser databases are an ephemeral query engine loaded from it and synced by commit identifier, and that a site is a projection of vault content. Yesterday's publishing brief followed that line, describing a repository that leverages the content of the vault, with files hosted via a read key on the public environment.

The revision keeps the vault as the authoring environment and moves the *published* copy into a public repository as ordinary files.

| | Previous plan | This proposal |
|---|---|---|
| Where content is created | The vault | The vault, unchanged |
| What the site reads from | The vault, via a read key | A public git repository |
| What the public can do with it | Read, if given a key | Read, fork, diff, comment, propose changes |
| Deployment unit | Whole vault | Changed files only |
| Sovereignty boundary | Content stays inside it | Published copy deliberately outside it |

Stated that way, only the last two rows are what the memo argues for, and the third row is the one that matters most.

## The Stated Motivation, And The Larger One

The reason given is operational. The project lead: **"the trick that I want to use is to avoid having to clone all of the repos, all of the vaults all the time, because that's one of the challenges I had in the past, and that creates this flow where the bigger the vaults are, the longer the deployment is, and it's crazy because you should just be able to do deployment based on a delta."**

That is a real problem and it is worth fixing. But it is not the strongest argument for this design, and the strongest argument is worth making explicitly because it changes how the work should be prioritised.

Yesterday's publishing brief concluded that **verification is the differentiator**, on the reasoning that no competing consolidation has been independently checked, and it specified three mechanisms to make checking tractable: publishing the derivation per provision, accepting issues against provisions, and publishing content hashes.

None of that works against an encrypted vault. A member of the public cannot fork it, cannot diff it, cannot open a pull request against it, and cannot see a history. Handing out a read key gives them reading and nothing else, and it is a one-way action that yesterday's brief already flagged as irrevocable.

**Clear text in a public repository is what turns the verification claim from an aspiration into a workflow.** Fork, branch, diff, issue, pull request, blame and history are exactly the affordances the checking process needs, they are free, and every potential verifier already knows how to use them. So this is not a deployment optimisation that incidentally helps. It is the enabling condition for the property already chosen as the product's distinguishing claim, and it should be argued on that basis.

## The Two-Pass Flow

The mechanics as described, which are conventional and should stay that way.

```
   VAULT (authoring)
     |  release triggered, possibly from the vault itself
     v
   JOB 1  holds vault key, or better a read-only key
          fetches what changed since last run (delta)
          copies changed files into the repo
          commits, then stops
     |
     v  on-commit trigger
   JOB 2  builds and publishes to the live site
     |
     v
   LIVE SITE  structure and content both from the repo
```

The project lead: **"whenever we want to do a release or a push to production, we run a CI pipeline that could be triggered programmatically, even from the vault; the pipeline has access to the vault key, or even the vault read-only key, goes to the vault, grabs the latest version, has a diff of the last time we did it, copies those files to the GitHub repo, commits that and stops the action."** And then the second stage. The project lead: **"we have an on-commit action, triggered by the previous one, that will then push those content files to the live website."**

Two details are worth fixing in the specification rather than leaving to implementation. The pipeline should hold **the read-only key, not the full key**, because a publishing job has no reason to be able to write to the authoring store, and a credential in a CI environment is the most exposed credential in the system. And the two-job split is correct, because it separates the privileged step that touches the vault from the unprivileged step that builds a site, so only the first needs any secret at all.

## The Delta Already Exists

The memo reaches for a cache. The project lead: **"if we add support for creating a zip file, almost like an archive, sort of a cache, which I believe GitHub supports quite nicely."**

That is a reasonable mechanism and it does not need to compute the delta itself, because the delta was specified this afternoon. The paragraph-as-folder brief established that each folder carries an index recording the content hashes of its items, with parent indexes recording their children, which forms a hash tree.

So the pipeline compares the hash tree it last published against the current one and copies only the subtrees whose hashes differ. No separate diffing, no timestamps, no state to keep beyond the last published root hash. The archive cache then serves its proper purpose, which is avoiding refetching unchanged content, rather than being the mechanism that decides what changed.

This is the third use of the same structure, which is a good sign that it is the right structure: it detects amendments, it caches analysis so cost scales with change, and it now drives deployment.

## Not Cloning The Vault Is Already Doctrine

The frustration in the memo has a precedent that resolves it in the same direction. Prior corpus work on the browser file system concluded that the vault provider should not clone the vault on construction, and should instead open lazily and let the cache handle performance, with the layered provider stack applying to write-through buffering rather than to preloading.

That is the same principle the memo is reaching for, in a different environment. The browser answer was lazy opening plus a cache API; the pipeline answer is a delta plus a build cache. So this is the established position applied consistently rather than a new idea, which is worth knowing because it means the vault tooling may already expose what the pipeline needs.

## Two Stores, One Truth

This is the real risk in the design and the memo names it without solving it. The project lead: **"we just need to have a way to bring back any pull requests back into the vault, but that's okay because we could always clone the repo from the Vault UI."**

Cloning back works mechanically and leaves the question of authority open, which is where architectures of this shape usually fail. Three options exist and only one avoids conflict.

**Vault authoritative, repository as a mirror.** Simple and one-directional, and it overwrites contributor commits on the next publish, which is both rude and confusing to anyone who submitted a correction.

**Repository authoritative for published content.** Also coherent, and it demotes the vault to a client and abandons the authoring model the rest of the corpus rests on.

**Split ownership by path**, which is the recommendation. No file is written by both sides, so there is nothing to reconcile.

That split maps cleanly onto the folder model already specified, because a provision folder naturally contains two kinds of thing:

```
   provisions/article-10/paragraph-5/
     text.md            generated   vault -> repo
     index.json         generated   vault -> repo   (hashes)
     derivation.json    generated   vault -> repo   (original + instruction + result)
     analysis/          generated   vault -> repo
     ----------------------------------------------------
     issues/            contributed repo -> vault
     comments/          contributed repo -> vault
     corrections/       contributed repo -> vault   (proposals, not applied text)
```

Generated files flow one way, contributed files flow the other, and a correction is a *proposal* recorded beside the provision rather than an edit to the published text. A maintainer reviews it in the vault and, if accepted, the next publish regenerates the text. That preserves a single writer per file, keeps the vault authoritative for content, and still gives contributors a real mechanism with a permanent record of what they raised.

## Clear Text In A Public Repository Is A One-Way Door

The memo touches the confidentiality question. The project lead: **"we want to make sure that there's no secrets stored, unless we encrypt it too, which is one interesting option, to do it encrypted."**

Two things should be settled rather than left as options.

**Git history is permanent.** Yesterday's brief noted that a read key cannot be recalled once handed out. This is stronger: content committed to a public repository remains in its history even after deletion, and anyone may have cloned it. The sub-vault recommendation from yesterday therefore moves from preferable to required, and it should contain only material intended to be public forever.

**Encrypted files in this repository are a contradiction.** The entire purpose of the repository is to invite strangers to check the work. A blob they cannot read cannot be verified, and its presence signals that something is being withheld from a process whose value is that nothing is. The rule should be that the published sub-vault contains nothing requiring encryption, rather than that secrets are encrypted before publication.

## The Sovereignty Boundary Moves, On Purpose

Worth recording because the corpus argues sovereignty hard and this is the first deliberate publication of vault content into an unencrypted third-party store.

It is the right call here, and the reasoning is specific: this artefact's value lies in being checkable rather than in being controlled. A public consolidation of a public law, published so that the public can verify it, has nothing to protect and everything to gain from being copied.

That reasoning does not generalise. It applies because the content is public law and the goal is scrutiny. It should not be cited as precedent for customer registers, personal vaults or anything where the sovereignty argument was made on the customer's behalf, and this brief records that limit deliberately so the distinction is on file before somebody needs it.

## What This Does Not Try To Be

- **Not an abandonment of the vault.** It remains where content is created, edited and held authoritatively.
- **Not bidirectional synchronisation.** Ownership splits by path so no file has two writers.
- **Not a deployment optimisation.** The delta is welcome; the verification unlock is the reason.
- **Not a general sovereignty change.** It applies to a public artefact whose value is being checkable.
- **Not a place for anything private.** The published sub-vault holds only what is intended to be public permanently.

## Honest Tensions

| Tension | Note |
|---------|------|
| Recording a change of position versus drift | The project lead flagged the contradiction himself, which is the right practice, and the previous plan is one day old, so the corpus should be able to show why it moved |
| Split by path versus contributor expectations | It avoids conflict cleanly and means a contributor's pull request never directly edits the published text, which will feel like a rejection unless the mechanism is explained on the site |
| Clear text for verification versus the sovereignty argument | Both are correct in their own domain, and the boundary between them is now something the corpus has to state rather than assume |
| A read-only key in a pipeline versus any key in a pipeline | Least privilege is right and a read key that can pull the whole published sub-vault is still a credential worth protecting |
| Hash-tree delta versus first run | The mechanism is elegant once a published baseline exists, and the first publish is a full copy regardless |
| Two stores versus one story | However clean the split, contributors and colleagues will ask which one is real, and the answer needs to be sayable in a sentence |
