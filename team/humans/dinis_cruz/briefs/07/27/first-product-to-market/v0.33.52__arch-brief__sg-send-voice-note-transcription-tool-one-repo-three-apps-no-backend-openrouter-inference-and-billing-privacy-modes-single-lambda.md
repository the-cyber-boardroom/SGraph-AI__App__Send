# The Voice Note Transcription Tool: One Repo To Web, iOS And Android, No Backend, OpenRouter For Both Inference And Billing, And A Single Lambda For Keys

**version** v0.33.52
**date** 27 July 2026
**from** Human (project lead)
**to** Engineering, Architecture, Product, Partners

**type** Architecture brief

*First of 27 July. The architecture for the first SGraph product going to market. The commercial model is a companion brief. External formats, APIs, and platform capabilities are grounded and cited. Offered to be built on and challenged.*

---

## What This Is

The architecture for a WhatsApp voice memo transcription tool, the first SGraph product being taken to market: **the product exists because the job is genuinely awkward today, and testing shows the reason is not the format but availability, since a mainstream assistant reads a WhatsApp voice note perfectly and still cannot transcribe it when the capability is absent from that session, which the user cannot predict in advance, and every existing route demanded extra steps, so the design goal is one smooth motion, drop in the audio file and get back a transcript, an analysis, and a short debrief in a single pass, with an infographic if the user asks for one, and nothing else; the shape is a shared repository publishing three targets, a web app and an iOS app and an Android app, which is a path already walked once for SGraph including the Apple and Android signing keys, with a Chrome extension as a likely fourth but deliberately after the first three; a CI pipeline mirrors two branches, dev building and pushing the dev estate and main building and pushing production, so every target ships from one place; there is no backend, which is the load-bearing decision, because everything runs in the front end and the hosting is therefore static, GitHub Pages with S3 and CloudFront where anything more is needed; inference goes through OpenRouter, which buys access to many models at once and, more importantly, carries the billing as well, since a key can be issued per user with a spend cap and OpenRouter meters and deducts against it, which removes the need to build a billing system at all; the cost of that choice is a privacy exposure, because a router gives no guarantee about which provider processes a given request, so the design answers with modes rather than disclaimers alone, a default routed mode, a restricted mode pinned to chosen providers, and a browser-local model mode that sends nothing anywhere and may be free; the only server-side component in the whole system is a single Lambda that provisions keys, and even that is deferred for the first beta users, whose key can simply be embedded in the client; and accounts are handled either by Google social login, already implemented and working, or by storing the session and the issued key in the browser's local storage, which keeps the no-backend property intact.** It is the first brief of 27 July (cross-ref: the v0.33.50 tools-to-productise brief, the v0.33.51 browser-automation brief, the v0.33.48 browser-local-databases brief, the v0.33.49 open-source-as-strategy brief, and the companion commercial-model brief of today). New contributions: **the one-pass pipeline from audio to transcript, analysis, debrief and optional infographic, the single repository publishing three app targets with a two-branch CI, the no-backend constraint held across the whole product, OpenRouter carrying inference and billing together, privacy expressed as selectable processing modes including a browser-local option, and the single key-provisioning Lambda as the only server-side code.**

## The Job, And Why It Is Awkward Today

The tool started as something the project lead built for himself and uses regularly, assembled from pieces already published on the SGraph tools site. The project lead: **"one of the tools I use regularly is a tool that I've created, actually has a combination of a couple of other tools on SGraph, that being published, that basically allowed the easy transcription of a WhatsApp voice memo."** The reason it needed building is that the obvious routes all failed in different ways. The project lead: **"I tried to do this with a couple of existing LLMs, and for example, Claude doesn't support audio transcriptions; ChatGPT, at the time, now does, but at the time didn't support the format that WhatsApp has, and Gemini sometimes worked, sometimes didn't, but every one of those required extra steps."**

The aside that one of those tools now handles it has been overtaken by two direct tests, and the tests correct the diagnosis as well as the claim.

**Test one, 25 July 2026.** Two voice memos of one minute forty-nine seconds each were uploaded and a transcript requested. They arrived as `.m4a`, identified as Apple MPEG-4 audio. After twenty seconds the assistant replied that it can transcribe WhatsApp voice memos, then stated that it did not have a speech-to-text engine available in that chat, deferred to whether transcription is enabled in the user's app or account, and offered instead to tidy or summarise a transcript produced somewhere else.

**Test two, the same memo as a genuine `.opus` file.** Dropped into the current version of the same assistant, the file was recognised immediately and correctly, reported as Opus inside an Ogg container, one minute forty-nine seconds, forty-eight kilohertz, mono. The assistant then said plainly that the format was not the problem: it could read and inspect the file but had no speech recognition engine available in that chat to turn the spoken audio into text. It added that the `.opus` file should work as well as the `.m4a` in a session where transcription is enabled, and suggested running a local speech-to-text tool such as Whisper and pasting the result back.

The second test is the more useful one, because it removes the explanation the memo originally offered. The barrier is not the format. The tool parses Opus in Ogg without difficulty and says so explicitly. The barrier is that transcription capability is conditionally available, scoped to the session or the account, and the user cannot tell in advance whether an attempt will work. Stated fairly, the claim is not that a competitor cannot transcribe audio, which would be too strong and probably wrong, but that two real attempts with a real WhatsApp memo did not complete, that the reason given was capability availability rather than any property of the file, and that the user had no way to predict either outcome. That unpredictability is the better thing to sell against, and it is more durable than a format gap, which any vendor can close in a single release.

There is also a quiet endorsement buried in the fallback advice. Told that the hosted path was unavailable, the assistant recommended running a local speech-to-text model and bringing the text back. That is precisely the browser-local mode described later in this brief, arrived at independently by a competitor's own troubleshooting.

**On the format, corrected.** WhatsApp voice notes are Opus audio inside an Ogg container, a choice the platform made in 2016 and which its own business messaging documentation still requires, specifying that voice messages must be Ogg files encoded with the Opus codec. Downloading a memo from WhatsApp on a laptop returns exactly that, and the inspected file above confirms it at forty-eight kilohertz, mono. The `.m4a` in the first test was not the general iOS case: it came from forwarding a file out of another iPhone app into the WhatsApp iPhone app, a path that re-encodes into Apple's container. Opus in Ogg is therefore the norm, and the AAC case is a real but narrower path rather than the default for every iOS user, as this brief first recorded it.

```
   laptop download (macOS)    ->  .opus        Opus in Ogg     <- the norm
   Android / chat export      ->  .opus/.ogg   Opus in Ogg
   iPhone app-to-app forward  ->  .m4a         AAC in MPEG-4   <- narrower path

   accept both, and detect by content rather than by extension
```

Three consequences follow for this architecture. The first is that the product's reason to exist is not a format gap but an availability gap, which is the stronger position, because a format gap closes with one vendor release while unpredictable capability is a standing user problem. The second is that the client should still accept both codec families and detect by content rather than by extension, since the AAC path is real even though it is not the default. The third is the useful one: modern browsers decode both Opus and AAC natively, so a front-end-only design is not fighting either format, which is part of why the no-backend constraint is affordable here.

On the capability claim, the honest and dated position is that Anthropic's documented Files API content-block types cover documents and images rather than audio, and its voice features are live-speech capabilities rather than file transcription. Supported inputs change, so this should be re-checked before the claim is published anywhere customer-facing.

## The Pipeline Is One Motion

The entire user-facing behaviour fits in a sentence, and keeping it there is a design constraint rather than an accident. The project lead: **"you basically take the audio file, and in one go you create a transcript, an analysis, a quick debrief of it, and if the user chooses an infographic, and that's it, literally that's it."**

```
   drop in the audio (.opus / .ogg / .m4a)
            |
            v
   ONE PASS  ->  transcript
             ->  analysis
             ->  short debrief
             ->  infographic (only if asked)
            |
            v
   done. no accounts to configure, no steps to chain.
```

This is the 23 July principle about complete jobs, applied. That brief observed that "upload a thing and get a transcript" is a complete user-facing job while "split the audio out of a video" is a step inside someone else's workflow. It also named audio transcription and the infographics generator as two separate items on the productisation list. This product folds both into one job, which is why it is a better first product than either would be alone.

## One Repository, Three Targets, Two Branches

The delivery shape is a single shared repository that both parties can access, publishing several applications from one place. The project lead: **"we're going to have a shared GitHub repo that we can use to publish the multiple applications, so we basically have a web app, we'll then have an iOS app and an Android app."** The risk that would normally sit here has already been retired. The project lead: **"the good news is I've already created this, there's already an open source project where for the SGraph I actually created and deployed, including with the Apple developer key and the Android key, so I already done that, and that worked quite well in terms of the deployment."** A fourth target is anticipated and explicitly deferred. The project lead: **"it's probably worth creating a Chrome extension app, but let's do with these two or three first."**

The pipeline mirrors two branches onto two estates. The project lead: **"we have a CI pipeline that has both dev and main, so dev is aligned with the dev branch, main is aligned with the main branch, and with every one of those, we build the apps there, and we push."**

```
   ONE REPO
     |
     +-- dev branch  --CI-->  build all targets  -->  dev estate
     +-- main branch --CI-->  build all targets  -->  production
                                   |
                    web app  +  iOS app  +  Android app   (Chrome extension later)
```

## No Backend, And What That Buys

The constraint that shapes everything else is stated plainly and treated as important rather than incidental. The project lead: **"the power of this is that there's no back end, so it's very important because everything is provided on the front end."** Hosting follows from it. The project lead: **"we're going to host a lot of it on GitHub Pages, and if we need any sites, anything hosted, we'll just host it on S3 with CloudFront, and that's it, so it's nothing too complicated."**

The gains are the ones the corpus has argued for elsewhere: nothing server-side to secure, patch, scale, or pay for when idle; the client holds the data and the key; and the cost base stays near zero, which is what makes the profit-share arrangement in the companion brief viable at small volumes. This is the browser-local-databases posture from 12 July carried into a consumer product, and it is the same reason the earlier vault work put the query engine in the browser rather than behind an API.

## OpenRouter Carries Inference And Billing Together

The choice of OpenRouter starts as model access. The project lead: **"we can use OpenRouter for this, so that gives us access to a lot of the models."** It becomes something more interesting when it also removes the need to build billing. The project lead: **"instead of developing a billing for this, what we'll do is we'll use OpenRouter for the billing, and basically what happens is when somebody buys credits, we give them an OpenRouter key that has an amount of credits that is 80% of what they purchased."**

That mechanism exists and works as described, which is worth confirming because the entire commercial model rests on it. OpenRouter provides management or provisioning keys that can only administer other keys and cannot themselves make inference calls, with key endpoints to create, list, retrieve, update and delete. A created key can carry a credit limit and an optional daily, weekly or monthly reset, and OpenRouter meters each request and deducts against both the key's limit and the account balance, so the operator does not maintain a model pricing table. Issuing one key per customer is one of the documented intended uses.

One property of that design has a working-capital consequence the memo does not mention. All issued keys draw from a single shared account balance, and the per-key limit is a cap rather than a wallet. The operator therefore pre-funds consumption and must keep the pooled balance topped up to cover every active key, holding the float between a user buying credits and spending them. At the volumes described this is small, but it is a real obligation rather than a pass-through, and it should be understood before the model is scaled.

## Privacy Is A Mode, Not A Disclaimer

The cost of routing is that the operator cannot say who processed a given request, and the memo identifies this without flinching. The project lead: **"we do need to have some disclaimers in terms of privacy because in OpenRouter we don't have a guarantee of who's going to process it."** The design response goes further than a notice, and this is the most product-relevant idea in the memo. The project lead: **"we can have multiple modes on this in terms of the models used, and we could have a mode of using the different providers, and in fact we could even have a mode that uses the browser itself, which maybe is an option, and that might even be free, because that only uses a local model."**

```
   MODE               WHERE IT RUNS            PRIVACY              PRICE
   routed (default)   any OpenRouter provider  no guarantee         cheapest
   restricted         chosen providers only    named processors     higher
   browser-local      the user's own device    nothing leaves       possibly free
```

Two things make this worth building rather than filing as a nice-to-have. It turns a weakness into a priced axis, since the privacy tier and the billing tier become the same selector, which is exactly the isolation-and-privacy billable unit named on 17 July, appearing here in a consumer product rather than an enterprise one. And the browser-local mode is the only tier that can honestly be marketed as private, which is a genuine differentiator against every hosted transcription service, at the cost of quality and device capability.

## The Only Server-Side Code Is One Lambda

The no-backend claim needs one honest qualification, and the memo makes it. The project lead: **"we're not saying there's no server side for the main functionality, but for the provision of the keys, I think we will need to have at least one Lambda function that provisions this."** And even that is deferred past the first users. The project lead: **"we can start without that, especially for the first beta users, because we can just give them the key, we can hardcode the key on the browser."**

Hardcoding a key in a client is acceptable only under conditions that should be written down rather than assumed: the key must carry a hard spend cap, it must be treated as public from the moment it ships, and it must be revocable and short-lived. The provisioning API supports exactly this, since a key can be created with a limit and disabled or deleted later. Beta users get a capped, disposable key; the Lambda arrives when strangers do.

Accounts sit alongside it with two options. The project lead: **"we can implement social login, especially with Google, because I've already implemented that, and that works quite well."** Or no accounts at all. The project lead: **"we could also do a local storage, which means we'll store the key in the user's browser, so we'll have the session stored and the OpenRouter key that we generate stored there."** Local storage preserves the no-backend property and gives the user custody of their own key, at the cost of losing everything when they clear their browser or change device, which is a trade to make deliberately.

## What This Does Not Try To Be

- **Not a backend service.** Everything runs client-side; the single key-provisioning Lambda is the only exception, and it is deferred.
- **Not a billing system.** OpenRouter meters and deducts; the markup is expressed as the issued key's limit.
- **Not a private service by default.** The routed mode gives no processor guarantee; privacy is a selectable mode with a price.
- **Not four targets at once.** Web, iOS and Android first; the Chrome extension is deliberately later.
- **Not a general transcription platform.** One job done in one pass, for one awkward format.

## Honest Tensions

| Tension | Note |
|---------|------|
| No backend versus the key problem | The architecture is clean until keys must be issued to strangers, which forces the one Lambda and a real auth story; the beta hardcoded key defers this rather than solving it |
| Hardcoded beta key versus abuse | A key shipped in a client is public; only a hard cap, short life and easy revocation make it safe, and those conditions need to be explicit rather than assumed |
| Routed inference versus the privacy promise | The cheapest mode is the one with no processor guarantee, so the default mode is the least private, which needs to be surfaced honestly in the interface rather than buried |
| Browser-local mode versus quality | The only genuinely private tier is also the weakest and most device-dependent, and marketing it as equivalent would be dishonest |
| Local storage versus losing everything | Custody of the key in the browser is the purest no-backend answer and also the one where a cleared cache costs the user their credits |
| Pre-funding the pool versus pass-through | All keys draw on one balance, so the operator carries float and must keep it funded; this is not the pure pass-through the framing suggests |
| Three targets versus a two-person team | Web, iOS and Android each carry store review, signing and release overhead, and the deployment being proven once is not the same as it being cheap to maintain |
| One-pass simplicity versus what users ask for next | Speaker labels, timestamps, long files and languages are the obvious requests, and each one erodes the single-motion design that is the product's advantage |

## Open Questions

| Question | Notes |
|----------|-------|
| Does the client convert, or does the model accept each format directly? | Whether the browser normalises Opus and AAC before sending, what that costs in time and fidelity, and how format is detected by content rather than assumed from the extension |
| What is the file length ceiling? | Model and cost limits on a long voice note, and how the interface communicates them |
| Which model per mode, and who chooses? | The default routing policy, and whether the user picks the model or only the privacy tier |
| What runs in the browser-local mode? | Which on-device model, at what quality, on what class of hardware, and whether it is genuinely free |
| When does the Lambda land? | The trigger for moving from hardcoded beta keys to real provisioning, and the auth that goes with it |
| What is the abuse model for a public key? | Cap size, key lifetime, rotation, and what happens when a beta key is scraped |
| Social login or local storage, or both? | Whether accounts are optional, and how a user recovers credits after clearing their browser |
| Where does the infographic come from? | Whether it reuses the existing infographics generator directly, and whether that is one call or two |
