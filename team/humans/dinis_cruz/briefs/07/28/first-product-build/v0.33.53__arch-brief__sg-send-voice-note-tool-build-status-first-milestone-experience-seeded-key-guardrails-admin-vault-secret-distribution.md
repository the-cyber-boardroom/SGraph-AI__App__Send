## What This Is

The current status of the voice note transcription tool and the clarifications the build session needs in order to proceed: **terms with the partner are agreed, everything is open source, publishing has begun and the first traction is arriving through professional networks, a repository exists, and an agent-driven build session is running, so this document exists to align that session rather than to argue a position; the shape of the first milestone is a branded site published from a repository on static hosting behind a proper domain, where a user drops a file and gets everything back in one motion, and the experience is the deliverable, meaning a visible indication that work is happening followed by the transcript, then the summary document, then the infographic, which is the part that does not exist yet and the part worth building first; the initial user batch will be served by a key deliberately seeded into the browser rather than by any provisioning flow, which is the right call for a first cohort and only safe under conditions that should be written down, and it turns out the platform supports more restriction than the memo assumed, because guardrails can constrain a key not only by spend but by which models and which providers it may reach and by what data policy applies, which means the privacy tiers designed into the architecture can be enforced on the key server-side rather than merely offered in the client; the build also needs a second vault, separate from anything user-facing, holding the administrative logic, the key management and the secrets, and the important discipline there is that an encrypted vault may live in a public repository while the key that opens it may not, a distinction that has to be explicit because it is exactly where this kind of arrangement fails; secret distribution can reuse the existing send capability rather than being invented, either by sending a secret directly or by handing the user a URL that retrieves and installs it; and a customer record system can be built on the same vault substrate, which closes the loop on managing the workflows around all of this.** It is the fourth document of 28 July (cross-ref: the v0.33.52 voice-note architecture brief, the v0.33.52 commercial-model brief, the v0.33.52 contract draft, the v0.33.50 tools-to-productise brief, and the v0.33.48 browser-local-databases brief). New contributions: **the build status and the alignment points for the session, the first milestone defined as the end-to-end experience rather than a feature set, the finding that platform guardrails can restrict a key by model, provider and data policy and therefore enforce the privacy tiers, the conditions under which a deliberately leaked key is acceptable, the separation of the product vault from an administrative vault with an explicit rule about what may sit in a public repository, and the reuse of the existing send capability for secret distribution.**

## The First Milestone Is An Experience, Not A Feature Set

The thing to build first is the whole path, thinly. The project lead: **"the first milestone is sort of that end-to-end experience of the website nicely branded, and where you can basically go drop a file and get in one go."** And the reason it comes first is that it is the missing piece rather than the obvious one. The project lead: **"just map that experience which we don't have yet, that nice experience, that simple experience."**

The sequence he describes is not one atomic result but three arriving in order, and that ordering should be preserved in the implementation rather than collapsed. The project lead: **"from a UI point of view, you just get the file, and then you get the visualisation that something is happening, then you get the infographic, so the transcription, and then the summary document, and then the infographic."**

```
   drop the file
        |
        v   something is visibly happening        <- load-bearing, not decoration
   TRANSCRIPT        arrives first, longest wait
        |
        v
   SUMMARY DOCUMENT  arrives second
        |
        v
   INFOGRAPHIC       arrives last, the delight
```

Two design consequences follow. The first is that progress indication is a functional requirement rather than polish, because a single pass over a two-minute voice note through transcription, analysis and image generation is measured in tens of seconds, and an interface that shows nothing during it will feel broken. The second is that results should stream as they complete rather than waiting for the whole pipeline, since the transcript is useful on its own and holding it back until the infographic renders makes the fastest artefact wait for the slowest.

## Hosting

Static publishing behind a real domain. The project lead: **"the idea is to publish a dedicated site using GitHub Pages and using then an AWS Route 53 link to it."** This is consistent with the no-backend architecture and needs no further argument. The only points worth settling in the session are the apex versus subdomain choice and the certificate path, both of which are routine and both of which are easier decided once than migrated later.

## The Seeded Key, And The Conditions That Make It Acceptable

The first cohort will be served by a key placed in the client on purpose. The project lead: **"probably we'll seed it with a token that we'll leak to the browser, so we can say, oh, this is for our first batch of users, so we'll kind of leak that key."**

This is the right decision for a first batch and it defers rather than solves the provisioning problem, exactly as the architecture brief anticipated. What makes it safe is not secrecy, because there is none, but the properties of the key itself. A key shipped in a browser should be treated as published from the moment it ships, and therefore should carry a hard spend cap, a short life, an easy revocation path, and the narrowest possible reach. The first three were already established. The fourth is where the memo points, and the platform supports it better than expected.

## Guardrails: The Key Can Be Narrowed By Model, Provider And Data Policy

The project lead's instinct here is correct and worth acting on. The project lead: **"the open router already allows the limitation of the tokens to some models, so we should be exploring that to see how that gets created."**

The platform documents a guardrails capability that lets an account or organisation control how its members and keys may be used, covering spending limits, restrictions on which models and which providers are available, and enforcement of data privacy policies, configured under the privacy settings in the dashboard and, on organisation accounts, requiring administrator rights. Budget limits are described as a spending cap that resets daily, weekly or monthly, with requests rejected once reached.

Three consequences matter for this build.

**The leaked key stops being a general-purpose credential.** Restricted to the two or three models the application actually calls, a key found by someone else cannot be spent on the most expensive model in the catalogue. That converts the worst case from an unbounded abuse surface into a bounded one, on top of the spend cap.

**The privacy tiers become enforceable rather than advisory.** The architecture brief proposed three modes: routed, provider-restricted, and browser-local. The provider-restricted tier was described there as a product selector, which in a client-side application is advisory, since a user holding the key can call whatever the key permits. Implemented as a guardrail on the issued key, provider restriction and data policy are enforced by the platform before the request is served. That is a materially stronger claim to make to a customer, and it means the middle privacy tier is a key configuration rather than application logic.

**There is a setup dependency.** Guardrails are configured in the dashboard under privacy settings and, for organisation accounts, by an administrator. The session should establish early whether the account is personal or organisational, because it changes who can create the restrictions and how they are automated.

The existing administrative console should be reused rather than rebuilt. The project lead: **"we should be leveraging the fact that we already have an OpenRouter admin console."**

## Two Vaults, And One Rule About The Repository

The build needs a second vault distinct from anything the user touches. The project lead: **"we should be doing also a vault that we can use for the admin logic and to hold some of the secrets, we need a new vault that we can use for the stuff that we can put on GitHub, like for example the management of the keys."**

The separation is right and the phrasing conceals a distinction that must be made explicit in the session, because it is precisely where arrangements like this fail. An encrypted vault is ciphertext, and ciphertext can sit in a public repository without harm. The key that decrypts it cannot. So the rule is simple and should be written into the repository's own documentation rather than assumed:

```
   MAY live in the public repo        MUST NOT
   the encrypted vault                the vault key
   key management logic and code      any plaintext secret
   the provisioning workflow          the management API key
   configuration and schemas          anything that decrypts the above
```

The distinction between the product vault, which is published as a static site and holds nothing sensitive, and the administrative vault, which holds the secrets and is operated rather than published, should be reflected in separate repositories or at minimum separate directories with different handling rules.

## Distributing Secrets Reuses What Exists

No new mechanism is needed. The project lead: **"we already have a way to distribute secrets quite nicely because on SGraph we already have a send capability which is well documented, so we can use it to distribute secrets, or even maybe give the user a URL that is going to basically go and grab the secret and then push it there."**

Two patterns are described and they suit different moments. Sending a secret directly fits a small first cohort contacted individually. A URL that retrieves and installs the secret into the browser fits the moment the cohort grows beyond hand-holding, and is the natural bridge between the hardcoded key and the provisioning function the architecture brief deferred. Whichever is used, the retrieval link inherits the properties of the secret behind it, so a single-use or short-lived link is worth more than a durable one.

## The Customer Record System

The last piece closes the operational loop. The project lead: **"we also going to need the CRM that we can build, we can build that on top of the vault, we need a way to manage those workflows."** This follows the position already taken in the corpus that vaults are a reasonable substrate for project management and customer records, and it has the useful property that the same encryption, versioning and provenance apply to commercial records as to everything else. It is not first-milestone work, and naming it now is enough.

## What The Session Should Settle First

In rough order of how much they constrain everything downstream:

| # | Decision | Why it comes first |
|---|----------|--------------------|
| 1 | Personal or organisation account on the model platform | Determines who can set guardrails and whether they can be automated |
| 2 | Which models the application actually calls | The guardrail allowlist cannot be written until this is fixed |
| 3 | Seeded key parameters | Cap, reset period, lifetime, revocation path, written down before the key ships |
| 4 | Repository split and the ciphertext rule | Cheap now, painful to unpick after secrets have been committed |
| 5 | Streaming versus atomic results | Shapes the client architecture and the perceived speed of the whole product |
| 6 | Domain and certificate path | Routine, and easier decided once |

## What This Does Not Try To Be

- **Not a new architecture.** The design is settled; this aligns the build against it.
- **Not a provisioning solution.** The seeded key defers that deliberately, under stated conditions.
- **Not a security model for strangers.** It covers a known first cohort; the model changes when the audience does.
- **Not first-milestone scope for the customer record system.** Named, not built.
- **Not a claim that the key is secret.** It is published by design, and made safe by its limits.

## Honest Tensions

| Tension | Note |
|---------|------|
| A deliberately leaked key versus any notion of a secret | This is defensible for a known cohort and stops being defensible the moment the site is public and indexed, and the transition point should be decided now rather than noticed later |
| Guardrails as enforcement versus a single account | Restrictions on the issued key are strong, and every key still draws on one funded balance, so a compromised key spends real money until it is revoked |
| Vault in a public repository versus operational reality | The ciphertext rule is simple and is broken by one careless commit; it needs a pre-commit control, not just documentation |
| Streaming results versus one clean reveal | Progressive arrival is better for perceived speed and worse for the single-motion promise the product is built around |
| Reusing send for secrets versus a provisioning flow | It works now and it is a manual step, so growth in the cohort is what forces the deferred function into existence |
| Naming the partner | The corpus convention is not to name individuals in published briefs, and this document follows it; if the partner is content to be named in public material, that is a decision to take deliberately |
