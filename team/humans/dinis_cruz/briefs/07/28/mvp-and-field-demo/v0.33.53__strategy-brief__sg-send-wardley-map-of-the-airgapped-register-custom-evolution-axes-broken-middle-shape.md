## What This Is

The specification for a Wardley map of the same workflow the press release describes, built to make one thing visually undeniable: **the map begins where mapping always begins, with the user and their need, and the scenario it depicts is the ordinary one rather than a worst case, an organisation that already knows its agents exist, already knows a good deal about what they can do, and in many cases has already bought tooling that discovers and monitors them, so the problem is not ignorance but disconnection, because the findings sit in one place, the register sits in another, and the board has never accepted anything; the component that carries that problem is the air-gapped register, and the mapping question the memo poses is how to render air-gappiness so that the missing service becomes obvious on sight, to which the answer is that a gap cannot be drawn as a component and should instead be drawn as the thing that actually occupies it, namely bespoke manual integration sitting at the far left of the evolution axis, which is honest because that labour genuinely exists and genuinely is custom every time; the shape that results is the argument, because the detection and discovery components sit far to the right where the market has already solved them, the executive need sits at the top where it is well understood, and everything between the two is stuck at the left, which produces a map whose ends are evolved and whose middle is manual, and in mapping doctrine an unevolved component that everything above depends on is exactly where opportunity is located; and the memo's proposal to use custom evolution scales rather than the standard four stages turns out to be explicitly sanctioned, with the caveat that the progression has to remain an evolution rather than becoming a quality score, which cleanly separates the scales that belong on this map from the ones that belong in the maturity models the corpus already has.** It is the twelfth document of 28 July (cross-ref: the v0.33.53 working-backwards PR-FAQ, the v0.33.53 scenarios-are-the-MVP brief, the v0.33.51 plug-profile series plan, the v0.33.50 governance-layer positioning, and the v0.33.49 fractal-registers brief). New contributions: **the air gap rendered as bespoke manual integration rather than as an absence, the ends-evolved-middle-manual shape as the visual form of the value proposition, a grounded verdict on custom evolution axes and the line between an evolution scale and a maturity scale, and the specification of three related maps rather than one.**

## The Anchor And The Scenario

Mapping starts with the user and the need, and the discipline is to be specific about both. The anchor here is the person accountable for agents already running in production, and the need is to be able to say what the organisation is carrying and to have somebody with standing sign it.

The scenario is deliberately not a disaster. The project lead: **"we can define a couple of scenarios where they already know their risk, they already know the agents exist, they already know what's happening; what they don't have is the connection, and the boards have not, for example, done the risk acceptance."**

That framing matters because it determines who the map is aimed at. It is not for an organisation that has lost control. It is for a competent one that has invested in the right things and cannot join them up, which is both a larger population and a more receptive one.

## The Component That Carries The Problem

The project lead: **"this is where we then have a flow of risks, which are on risk registers that are airgapped."** And the mapping question follows immediately. The project lead: **"how can we capture the air-gappiness of the risk register in these maps, so that it is very obvious the service that we provide and the knowledge that we provide."**

The answer worth adopting is that **you cannot map a gap, because a gap has no evolution.** An absence sits nowhere on the horizontal axis and therefore says nothing. What you can map is the thing that actually occupies the space, and in every organisation with this problem that space is occupied by people: somebody reads the findings, somebody retypes them into a register, somebody prepares a summary for a committee, somebody chases the owner.

So the honest rendering is a component called something like manual integration or human transcription, sitting at the far left of the evolution axis, with dependencies running up from the detection tooling into it and onward into the register. That is truthful, it is immediately recognisable to anyone who does it, and it has the property the memo wants: it makes the missing service obvious, because a component sitting in genesis that everything above depends on is the standard place a map tells you to look.

## The Shape Is The Argument

The memo predicts the shape before drawing it, and the prediction is the valuable part. The project lead: **"this will be a very interesting shape where you can have the top working quite efficiently, and then the middle bit those lines all the way to the left because they're manual, but then they can go all the way to the right to the detection element, because you could actually have already the detection problem well done."**

```
   VISIBLE
   TO USER
     ^
     |  accountable executive (the anchor)
     |  a signed, owned risk position .............. [ mostly understood ]
     |
     |  translation to each altitude .... X                    <- genesis
     |  board acceptance ............... X                     <- genesis
     |  the risk register ................. X                  <- custom
     |
     |  MANUAL INTEGRATION ........ X                          <- genesis
     |         ^  the air gap, drawn as the labour that fills it
     |         |
     |  agent discovery / detection ......................... X  <- product
     |  telemetry and posture data .......................... X  <- commodity
     |  compute, storage ..................................... X <- utility
     |
     +--------------------------------------------------------> EVOLUTION
        genesis        custom built        product        commodity

   the ends are solved. the middle is people.
```

Two things about that shape do work no argument does.

**It shows the customer their own investment failing to connect.** The detection tooling on the right is something they bought, chose, and can point at. The need at the top is something they are accountable for. The map says both are fine and the line between them is a person retyping. That is a more persuasive statement of the value proposition than any description of the product, and it is the memo's stated intent. The project lead: **"this is where we also start to show the value and the value proposition with other tools, because you could have a tool that automates the discovery of the vulnerabilities or the agents that are using, but then it connects to an air gap that then needs to manually be integrated with existing solutions."**

**It locates the opportunity where doctrine says to look.** In mapping practice, components in genesis and custom built are where differentiation is possible, while product and commodity components are where you optimise or buy. An unevolved component that a well-understood need depends on is the textbook position for a new entrant, and the standard move is to industrialise it. That is the product thesis, arrived at from the map rather than asserted.

It also restates the corpus position on where the product sits: consume findings from the layer that is already evolved, do not compete with it, and supply the governance the evolved layer cannot reach. The map makes that a picture rather than a claim.

## Custom Evolution Axes: The Verdict

The memo proposes departing from the standard axis, and the question deserves a straight answer because it affects whether the artefact is a Wardley map or a diagram that resembles one. The project lead: **"the evolution scale doesn't necessarily need to be Genesis, custom-built, product and commodity; you can go from air gap to file to API to event-driven."**

**This is sanctioned.** Mapping guidance states plainly that the four stages are usually labelled Genesis, Custom Built, Product and Commodity, that it is acceptable to change the labels, and that what matters is that the progression should be similar. Established tooling documents different terminologies for different component types, giving novel to custom to product to commodity for technology, unmodelled to divergent to convergent to modelled for data, and concept to hypothesis to theory to accepted for knowledge. So relabelling is orthodox practice, not a liberty.

**The caveat is that the progression must remain an evolution.** The underlying axis is derived from ubiquity and certainty: things move from rare and uncertain toward widespread and well defined. A relabelled scale is valid when it preserves that direction and invalid when it becomes a quality score.

Tested against the memo's two proposals, they land differently:

| Proposed scale | Verdict |
|---|---|
| Air gap, then file, then API, then event-driven | **Valid.** This is a genuine evolution of an integration practice from absent, through bespoke exchange, to standardised interfaces available from many providers, to utility-grade streaming. Ubiquity and certainty both increase left to right |
| Air gap, then spreadsheet, then networked, then API | **Valid**, same reasoning, and probably the more legible of the two for a business audience |
| Can pull the plug, time to understand, observability | **Not an evolution axis.** These measure how good a capability is, not how ubiquitous and certain the component has become. This is a maturity scale |

That last row is worth acting on rather than arguing with, because the corpus already has the right home for it. Plug capability, detection latency and observability quality are exactly what the maturity models are for, and there are now several. Putting them on the horizontal axis of a map would make the map say something it is not built to say, whereas expressing them as maturity levels keeps both instruments honest and lets the map reference the model rather than absorb it.

The practical rule: **relabel the axis when the thing genuinely evolves; use a maturity model when the thing merely improves.**

## Three Maps, Not One

The memo names more than one thing worth mapping, and they are better as separate maps than as one crowded diagram.

**The air gap map**, described above. The core sales artefact.

**The translation map.** The project lead: **"the current translation and delivering the message in context to the right stakeholder, which is where we excel by having customised risk registers per stakeholder, and we connect the dots from one stakeholder to the other to make sure that the business is actually not putting responsibility where you're not supposed to, but also that that line exists."** This maps the chain of stakeholders as the value chain and shows that translation between altitudes sits in genesis everywhere, which is a different and equally strong argument.

**The evidence chain map.** The project lead: **"we can show graphs and connections all the way from the top level risk, all the way to the regulation, and all the way to the actual event where an agent is actually being materialised; so the evidence, all the way to the regulation, all the way to the current context, all the way to the risk and business context, and then driving decisions."** This is the full chain from a running agent to a board decision, and it is the one that demonstrates the regulation graph earning its place.

The purpose behind all three is stated plainly and should be the caption on each. The project lead: **"we want to drive decisions, we want to drive risk reductions, we want to drive understanding, and that's the value that we provide to the business."**

## What This Does Not Try To Be

- **Not a map of a failing organisation.** The scenario is a competent one whose investments do not connect.
- **Not a critique of the detection market.** That layer is evolved, which is the premise rather than the complaint.
- **Not an unorthodox map.** Relabelled axes are sanctioned practice; the discipline is preserved deliberately.
- **Not a maturity model.** Capability quality belongs in the existing models, and the map references them.
- **Not one diagram.** Three related maps, each making a different argument.

## Honest Tensions

| Tension | Note |
|---------|------|
| Drawing the air gap as manual labour versus flattering the customer | It is accurate and it tells a competent professional that a chunk of their week is an unevolved component, which needs care in how it is presented |
| Relabelled axes versus audience familiarity | Sanctioned practice, and a reader who knows the standard four stages will still need the substitution explained, which costs time in a short conversation |
| The map as a sales artefact versus as analysis | A map drawn to show a gap we happen to fill is a map with a conclusion built in, and honest mapping should be able to show us in an unflattering position too |
| Three maps versus attention | Each makes a distinct argument, and a prospect will look at one |
| Middle-is-manual versus organisations that have automated it | Some have built the connection internally, and for them the map is wrong and the pitch is different |
| Doctrine says industrialise the gap versus never being in line | Mapping doctrine points at commoditising the unevolved component, and the corpus has already ruled out doing that inside the request path |
