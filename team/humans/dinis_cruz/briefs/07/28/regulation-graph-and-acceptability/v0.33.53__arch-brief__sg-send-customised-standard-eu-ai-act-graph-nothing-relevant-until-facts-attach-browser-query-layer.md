*Fifth of 28 July, and the concrete build behind the regulation graph proposed earlier today. Browser query engines and their capabilities are grounded and cited. Legal points are factual and are not legal advice. Offered to be built on and challenged.*

## What This Is

The design for a public graph of the European AI Act, held in a vault and projected as a website, whose central feature is not the graph but a subtraction: **the research is done and the finding removes the largest piece of anticipated work, because good sources of the raw material already exist and the original document does not need parsing, which turns the build into modelling and projection rather than extraction; the artefact is a vault with a website projection carrying a hyperlinked graph of the instrument, with ontologies and taxonomies layered on top, shipped as JSON and database files loaded and queried entirely in the browser using the same technique the existing prototypes already use, which is now well supported since graph and analytical engines compile to WebAssembly and run client-side with no server behind them; the idea that makes it worth building is the customised standard, meaning the ability to produce the version of the instrument that applies to a particular scenario, and the inversion inside it is the important part, because you start from nothing being relevant if you have no AI system at all and the standard accretes only as facts about your situation make articles attach, which is the opposite of every compliance tool that hands over the whole text and asks you to mark what does not apply; the resource is useful even where the instrument does not legally bite, because a great deal of careful thinking has already gone into exactly the areas the risk work cares about, human oversight and the ability to stop a system among them, so the Act functions as a source of well-reasoned risk content and not only as a set of obligations; it is built in two parts, first navigate and customise, then extract the risks directly, with five scenarios running from a simple agent to one clearly in scope so that an ordinary visitor gets value and can explore; everything stays connected to its source, which gives real provenance and makes the graph the evidence base beneath the risks that travel up to the board; and the visualisation is meant to be ambitious rather than adequate, using the full range of browser technology to render the whole standard at once, because the resource is also intended as a public artefact that earns attention on its own merits.** It is the fifth document of 28 July (cross-ref: the v0.33.53 regulation-graph brief, the v0.33.53 scenarios-are-the-MVP brief, the v0.33.51 plug-profile series plan, the v0.33.49 fractal-registers brief, and the v0.33.48 browser-local-databases brief). New contributions: **the customised standard as the core feature and the inversion that starts from nothing being relevant, the finding that raw material exists so parsing is not required, the confirmation that graph and analytical query engines run client-side in WebAssembly, the two-part build of navigate-and-customise then extract-the-risks, and the instrument treated as a source of risk content independent of whether it legally applies.**

## The Research Removed The Hard Part

The open question from this morning's regulation brief was whether structured material actually exists per instrument, because the answer decides the build cost. It does. The project lead: **"we've done the research, we found that there's already a lot of good places that we can get the raw data, which is great because it means we don't have to worry about parsing the original document."**

That matters more than it sounds. Parsing legislation from published text is the part of this kind of project that consumes months and produces brittle results. Removing it turns the work into modelling, projection and visualisation, which are the parts where the corpus already has capability and where the differentiation actually sits.

## The Artefact

A vault with a website projection of it, carrying a hyperlinked graph. The project lead: **"the ultimate goal here is to create a hyperlinked graph using a vault and the website projection of that vault."** With semantic structure layered over the instrument itself. The project lead: **"we want to have a graph-based representation of the act in ways that then has semantic graphs connected to it, and ontologies and taxonomies that we can create."**

The delivery format follows the existing pattern. The project lead: **"all of this is then JSON files and SQLite files that we can then load in the browser, the same technique that we already used for some of our MVPs of the risk mandate."**

## The Core Idea: Nothing Applies Until Something Makes It Apply

This is the feature the whole build exists for, and it is worth stating carefully because the inversion inside it is easy to miss. The project lead: **"the key point here and the key idea here is to allow the creation of a customised version of the standard based on a particular set of requirements."** It is a long-standing want. The project lead: **"this is something that I've always wanted to have, which is, what are the bits of the standard that are not relevant to a particular scenario."** And then the move that makes it different. The project lead: **"in a way, you should start with nothing is relevant if you don't have any AI solution."**

Every compliance tool in existence works the other way. It presents the whole instrument and asks the reader to mark what does not apply, which places the burden of exclusion on the person least equipped to carry it, and which produces the familiar outcome where everything looks potentially relevant, nothing is confidently excluded, and the document goes unread.

Starting from empty reverses the burden. The instrument accretes only as facts about the situation attach articles to it. No AI system means an empty standard, which is both correct and impossible to say in any existing tool. One agent that can change something means a small set of provisions arrive with a reason attached. A system that meets a high-risk definition means considerably more arrives, and the reader can see exactly which fact caused each arrival.

```
   CONVENTIONAL                        THIS
   here is the whole standard          here is nothing
   mark what does not apply            state a fact
   burden of exclusion on the reader   an article attaches, with its reason
   everything looks relevant           the standard grows as your facts do
   nothing is confidently excluded     absence is a defensible position
```

Two properties follow that the corpus already values. The customised standard is **computed rather than claimed**, in exactly the sense the maturity models use: the subset is derived from stated facts and can be recomputed when the facts change. And it is the **relevance fade** from the fractal register work applied to an instrument rather than to a register, where what a role sees is filtered to what bears on them, converging upward.

## It Is Useful Even When It Does Not Apply

The reason to build this before knowing whether a given customer is in scope is that the instrument is a good source of risk thinking regardless. The project lead: **"we're going to use it as one of our foundational facts and evidence for the risks that exist, regardless if the particular AI solution is in scope or not, because what they've done already is put a lot of good thinking on a lot of the areas that are important, for example the pull the plug element."**

That is a distinct and stronger claim than compliance mapping. Human oversight provisions, and the requirement that a system can be interrupted or overridden by a person, are the closest thing in any published instrument to the plug profile the corpus has been developing independently. Citing them gives the plug work an external anchor written by people who thought hard about it, and it does so whether or not the reader is legally bound. This also connects directly to this morning's finding that obligation and liability start on different dates: an organisation outside the enforcement perimeter can still use the instrument as a well-reasoned checklist, and would be wise to.

## The Query Layer Runs In The Browser

The technical claim is that graph queries can run client-side, and it holds. The project lead: **"we have even SQLite on the browser or a SQL version, I think we could even run SPARQL or Cypher queries on the browser, which is pretty cool, so basically graph database queries."**

All three paths are real and shipping:

**SPARQL**, for an RDF or ontology representation, runs client-side through a Rust engine compiled to WebAssembly and distributed as an npm package, offering an in-memory store with SPARQL 1.1 query and update and loading the standard RDF serialisations including Turtle, N-Triples and JSON-LD. A separate JavaScript querying framework is browser-ready via a content delivery network, can query local RDF files and in-memory sources, and has optional reasoning support.

**Cypher**, for a property graph representation, runs in the browser through an embedded graph database compiled to WebAssembly, with a published demonstration of a fully in-browser graph pipeline that loads a personal data export, queries it, and renders a node-link visualisation with no server involved.

**SQL**, for the analytical and tabular parts, runs through an embedded analytical database compiled to WebAssembly, with the specific pattern of shipping the database file alongside a static site and querying it from JavaScript without a round trip.

Two practical notes for the build. The choice between SPARQL and Cypher is not a preference but a consequence of the representation chosen this morning, since the identifier and ontology stack points toward RDF while the published research on converting legislative XML points toward property graphs, and the sensible move is to pick the representation first and let the query language follow. And browser resources are constrained, which the graph engine's own documentation notes, so the size of what ships to the client is a design parameter rather than an afterthought, which fits the earlier conclusion that the graph only needs to cover what is actually cited.

## Two Parts, And Five Scenarios

The build divides cleanly. The project lead: **"we need to navigate the app but also create customised versions of it, which we can then extract the risks from it, so that's part one; part two is let's extract the risks directly."** So part one is the public resource, navigable and customisable, and part two is the bridge into the product, where a customised standard yields a set of risks.

The scenario set is specified. The project lead: **"that's why I think it's important to then have five or six or even ten different scenarios, let's start with five, of simple agents to agents that are clearly in scope."** That ladder needs reconciling with the three or four scenarios named in this morning's MVP brief, and the likely answer is that they are the same ladder seen from two ends: the MVP walks a user from an agent to a register, and this walks a user from an agent to the part of the instrument that attaches to it. If so, one scenario set should serve both, and it should be designed once.

## Provenance Is What Makes It Evidence

The chain back to the source is what distinguishes this from a summary of the Act. The project lead: **"remember that all of this is connected to the source, so we have real provenance on all this, all of this is then the evidence base for our risk mandate risks and facts and evidence that we will connect all the way to the board."**

That is the same force-of-proof property the corpus has argued throughout, now with the advantage that the authority being cited is external and universally recognised. A board member who will not take a vendor's risk rating on trust will take an article of a regulation, and the graph makes the step between them inspectable.

## Ambition In The Visualisation, And A Naming Decision

The visualisation is explicitly not meant to be merely adequate. The project lead: **"let's really go to town in visualisation, maybe even some 3D animations and 3D and flat versions and customised versions, because we basically have all the power of JS frameworks and WASM, so we can actually do some really cool stuff, even visualising the whole graph in one go, the whole standard in one go."** With a commercial reason attached. The project lead: **"this could be a really good resource, and it could be a really good viral marketing."**

On naming, several options were floated, spanning a standalone domain and various subdomains of the product domain. The trade is worth stating rather than resolving here. A subdomain inherits the product's authority and ties the resource visibly to it, which serves the stated purpose that the product needs this artefact. A standalone domain travels further as a neutral public resource and is more likely to be linked by people who would not link a vendor page, at the cost of doing less direct work for the brand. Since both the resource value and the marketing value are named as goals, the decision is a real one and should be taken deliberately.

## What This Does Not Try To Be

- **Not a parsing project.** The raw material exists; the work is modelling, projection and visualisation.
- **Not a compliance verdict.** It shows which provisions attach to stated facts; whether an organisation complies is a person's judgement.
- **Not the whole instrument by default.** The default state is empty, and content arrives only as facts attach it.
- **Not scope-dependent.** It is useful as risk content whether or not the instrument legally applies.
- **Not a server application.** The graph, the queries and the state all run in the browser.

## Honest Tensions

| Tension | Note |
|---------|------|
| Starting from empty versus giving false comfort | An empty standard is an honest answer to no AI system and reads like a clean bill of health, so the interface has to make clear that it reflects what was stated rather than what is true |
| Customised standard versus interpretation | Deciding that an article attaches to a scenario is an interpretive act, and doing it automatically edges toward advice the product should not give; the compliance validator role from this morning is the intended answer |
| Ambitious visualisation versus the first milestone | Rendering the whole standard at once is the thing most likely to earn attention and the thing most likely to consume the schedule |
| Two query languages versus one representation | The choice is a consequence of the data model, and building for both would double the work while proving nothing |
| Viral resource versus product funnel | A neutral public artefact and a lead generator pull the naming, the tone and the calls to action in different directions |
| One instrument versus the plural requirement | This morning's brief argued the regulation layer must be multi-jurisdictional from the start, and this is a single-instrument build, which is defensible as a first move and should not become the architecture |
| Browser resource limits versus the whole graph in one go | The engines are constrained client-side, and the most ambitious visualisation is also the heaviest payload |

## Open Questions

| Question | Notes |
|----------|-------|
| Which representation, and therefore which query language? | RDF with SPARQL or a property graph with Cypher; pick the model first and let the language follow |
| Are these the same five scenarios as the MVP? | Almost certainly one ladder seen from two ends, and it should be designed once rather than twice |
| What attaches an article to a fact? | The rule or edge that causes a provision to arrive in a customised standard, and whether it is deterministic or interpreted |
| Which sources are the raw material? | Naming them, and confirming licence terms for republication in a derived graph |
| Standalone domain or product subdomain? | A real trade between reach as a neutral resource and value as a funnel |
| How large is the client payload? | Browser engines are resource-constrained, so what ships is a design parameter |
| When do incidents, fines and news attach? | Named as a later layer, and each is a different provenance problem from the instrument itself |
| How does the customised standard stay current? | The instrument's dates have already moved once, and a shared customised version is a snapshot |
