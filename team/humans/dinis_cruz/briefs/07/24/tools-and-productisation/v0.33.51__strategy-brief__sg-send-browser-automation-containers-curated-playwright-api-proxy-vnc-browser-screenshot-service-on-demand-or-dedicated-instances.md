## What This Is

The next set of mature tools that can be commercialised, all of them Docker containers built around browser automation: **there are a number of containers already running, explored serverless but also on EC2 instances and as AMIs, and that deployment spread is itself how they get personalised for a customer; the principal one runs Playwright headless inside a container with an API that executes commands and is wired to a man-in-the-middle proxy, and its real value is a curated JSON API that abstracts away the complexity of Playwright behind a set of commands, including taking screenshots and recording video, which makes it a powerful helper for anybody wanting to use browser commands inside an agent, something already in daily use when an agent is asked to create a vault, take a screenshot of one thing and then another, and capture information from a page, because at that point it is simply an API call, which is both simpler and faster than spinning up a browser and Playwright locally through Python code written for the occasion; a second variant runs a full browser rather than a headless one, fronted by VNC so the browser can actually be watched in action, and carries the same commercial shape; and a third, much simpler service does nothing but take a screenshot of a URL or grab the HTML from a page, which is useful on its own even though services already exist that do exactly this, on the argument that it can be provided very cheaply and still find a place in that market; across all three the billing intent is the established one, cheap and on demand, with the addition of dedicated instances for customers who want them.** It is the first brief of 24 July (cross-ref: the v0.33.50 tools-to-productise brief, the v0.33.50 freelance-next-steps brief, the v0.33.50 core-primitives brief, the v0.33.49 commercialising-the-primitives brief, and the v0.33.44 evidence-packs brief). New contributions: **the browser automation containers named as commercialisation candidates, the deployment spread across serverless, EC2, and AMI as the personalisation mechanism, the curated JSON API over Playwright as the actual product rather than the browser itself, the man-in-the-middle proxy as a wired-in capability, the speed argument that a remote API call beats a local browser spin-up, the VNC variant as a watchable browser, the simple screenshot and HTML tier as a deliberate commodity play, and dedicated instances added as a third billing shape alongside on-demand consumption.**

## The Deployment Surface Is The Personalisation

Before the individual tools, the memo sets out where they run. The project lead: **"there is a number of Docker containers that we have, and we start to explore running them serverless, but also on EC2 instances and also on AMIs, although that is how they can be personalised."** That last clause is the commercially interesting one, because it means the same container is the product in three different shapes: a shared serverless endpoint for cheap on-demand use, a dedicated EC2 instance for a customer who wants isolation, and an AMI for a customer who wants it inside their own account entirely. This is the deploy-everywhere argument from 17 July made concrete, and it maps directly onto the billable units named the same day, since isolation, privacy, and deployment into the customer's own environment are exactly what the second and third shapes sell.

## The Headless Playwright Container

The main candidate is described in terms of what sits around the browser rather than the browser itself. The project lead: **"we have a Docker container that is running Playwright headless, and that basically has an API that can run commands, that is also wired to a man-in-the-middle proxy."** The product is the abstraction layer. The project lead: **"there is a whole JSON-based, already curated API, where instead of dealing with the complexity of Playwright, I actually abstracted a whole bunch of stuff and a whole bunch of commands, which is what we use, including to take screenshots, record videos."** And the intended user is explicitly an agent operator rather than a developer writing test suites. The project lead: **"this is a really powerful helper for anybody who wants to easily use this kind of commands inside an agent."** It is already load-bearing in daily work. The project lead: **"when I say to an agent, can you create a vault on this, can you take a screenshot of this and take a screenshot of that, and can you capture this information."**

## Why A Remote API Call Beats A Local Browser

The value argument is not only convenience, it is latency, and this is worth stating plainly because it is the part a buyer can verify in a minute. The project lead: **"it is basically just an API call, which is way more simple than, and faster actually than, to spin up and to write Python code that then gets executed, that spins up the browser and Playwright locally."** An agent that needs a screenshot otherwise pays for a browser launch on every invocation, in code it had to write first. Against that, a warm remote endpoint returning structured JSON is both a smaller prompt and a shorter wall-clock path, which matters more the more often an agent does it.

## The VNC Variant: A Browser You Can Watch

The second container trades headlessness for visibility. The project lead: **"there is a variation of this, which actually runs a browser; the other version is headless, this is now a full-blown browser that runs with a VNC frontend, so you can actually see the browser in action."** The commercial treatment is the same. The project lead: **"the idea would again be to do something similar."** The distinct value here is debugging and trust: watching what an agent's browser actually did is a different product from receiving the artifacts it produced, and it is the natural companion to the proxy for anyone trying to understand agent behaviour rather than just collect its output.

## The Simple Tier: A Screenshot Or The HTML

The third is deliberately minimal. The project lead: **"one that is actually a simpler version of this is just one to take a screenshot, or just to grab HTML from a particular page."** Its usefulness is asserted modestly and its market is acknowledged. The project lead: **"even just take a screenshot of a URL, or to grab information from a URL, that itself is already quite useful, and there are already some services that do this."** With the commercial bet stated. The project lead: **"we can provide this quite cheaply, and we can be a player in this."**

## What The Existing Service Documentation Already Shows

The memo undersells the tool, and this matters for a productisation decision, so it is worth recording what the working service already does. The operating documentation for the running service describes six route families rather than a single command endpoint, covering individual browser actions, a linear sequence executor, a probe-many-reads-from-one-page inspector, a one-shot render, and stateful sessions that hold a page open across calls with a time-to-live so that navigation and vault decryption are paid once rather than per request. It exposes twenty-four step verbs, spanning navigation and interaction, text, HTML, DOM tree and accessibility tree extraction, PDF rendering, console and network-failure capture, and video start and stop. It has eight distinct wait predicates, including network idle, visible text, selector attachment and detachment, URL pattern, and load state. It returns a structured response carrying a trace identifier, per-step status, and a timing breakdown separating browser launch from step execution. It ships a Prometheus metrics endpoint, a capabilities endpoint, and live Swagger documentation. And it gates arbitrary JavaScript evaluation behind an allowlist that is empty by default.

Three of those details are commercially significant rather than merely technical. The metrics endpoint and the per-call timing breakdown mean the metering half of the shared productisation gap identified on 23 July is already substantially built for this tool, which is not true of the other nine. The empty-by-default JavaScript allowlist is a real security control already in place, which matters because running browsers on behalf of strangers is an abuse surface. And the stateful session with vault decryption amortised across probes is the piece that ties this container to the vault platform rather than leaving it a generic browser service.

## Three Billing Shapes Now

Yesterday's inventory produced two shapes, per token and per use. This adds a third. The project lead: **"this is the same model that we can charge on demand; we can charge for dedicated instances."** Dedicated instances are a different business from metered calls, because they trade the cheapness and elasticity of a shared endpoint for isolation, predictable capacity, and a much higher price point, and they are the shape that suits a customer who cannot send their URLs, their session state, or their credentials through somebody else's shared browser.

## The Competitive Picture

The memo's claim that services already exist is correct, and the shape of the market differs sharply between the simple tier and the agent-facing one.

At the simple end the market is a crowded commodity race. Comparison write-ups published in 2026 list nine or more screenshot API providers competing largely on price, with entry plans in the range of five to nine dollars a month for one to two and a half thousand screenshots, and per-screenshot costs at higher volumes measured in tenths of a cent. Most of these comparisons are published by vendors in the market and should be read as their own claims rather than as neutral research. One recurring point across them is worth attention anyway: a cited benchmark reports failure rates well above half for several established providers when tested against JavaScript-rendered single-page applications, full-page captures, and geolocation-specific rendering. Another is that pre-built agent integrations, particularly MCP alongside the common agent frameworks, are becoming the differentiator rather than raw price.

At the agent-facing end the market is consolidating around a well-funded incumbent. Browserbase provides cloud-hosted headless browser sessions for AI agents, compatible with Playwright, Puppeteer, and Selenium, with proxy networks, CAPTCHA handling, session isolation and session recording, an MCP server, and its own open-source agent automation framework. It raised a forty million dollar Series B in June 2025 at a three hundred million dollar valuation, reports tens of millions of browser sessions, and names large technology customers. Steel, Deck, and Anchor Browser occupy adjacent positions. One review of the category makes the defensibility argument bluntly and it applies to any entrant: the coordination problem of running isolated, fingerprint-managed, CAPTCHA-handling sessions at scale is genuinely hard, but Playwright, Puppeteer, and self-hosted Chromium are free and every cloud provider is one launch away from a managed offering, so an agent-integration advantage buys time rather than permanence.

## Where The Differentiation Actually Is

Read against that picture, competing on being a cheaper screenshot API is not credible, and competing on being a better browser fleet means competing with a funded specialist on its own ground. The differentiators that are actually ours are the two the market is not addressing.

The first is the man-in-the-middle proxy. Every provider above returns what the browser produced; a proxy wired into the session records what the browser did at the network level. For a corpus whose central concern is evidence, provenance, and reverse-engineering what an agent can actually do from what it actually did, a browser service that emits network-level evidence is a different category of artifact from a screenshot. It is also the natural feed for the mapping-error loop described on 23 July, since an agent reaching a system nobody modelled is precisely the kind of gap that proxy would see.

The second is the vault. The stateful session that amortises vault decryption, and the reverse-proxy path that authenticates through the vault, make this browser automation that runs inside a sovereign, encrypted, customer-controlled boundary. Combined with the AMI and dedicated-instance shapes, that is a defensible answer to the one question the commodity providers cannot answer: what happens to the URLs, the page contents, the session state, and the credentials that pass through the browser. That is the isolation and privacy billable unit from 17 July, and this container is the clearest instance of it in the portfolio.

## What This Does Not Try To Be

- **Not a cheaper screenshot API.** The commodity tier is a crowded price race, and price alone is not a position.
- **Not a general browser fleet.** No stealth network, no CAPTCHA solving, no fingerprint management, and competing there means competing with funded specialists.
- **Not three separate products necessarily.** One container family at three levels of capability, and whether they are packaged as one product or three is not decided here.
- **Not a build project.** The containers run today, and the working service is further along than the memo describes.
- **Not a single billing model.** On demand for shared use, per use for the simple tier, and dedicated instances for customers who need isolation.

## Honest Tensions

| Tension | Note |
|---------|------|
| We can be a player versus a commodity price race | At five to nine dollars a month for thousands of screenshots, the simple tier has no margin to win on price; the only credible openings are reliability on hard pages and agent-native packaging |
| Agent-facing infrastructure versus a funded incumbent | The category has a well-capitalised leader with proxy, CAPTCHA, and stealth capabilities we do not have; entering head-on is the same mistake the 23 July response warned against elsewhere |
| The defensibility argument applies to us too | Playwright is free and a cloud provider could launch a managed offering; the curated API and agent integration buy time rather than permanence, so the vault and proxy angles have to carry the weight |
| Dedicated instances versus the no-backend posture | Running EC2 instances for customers is an operational commitment that sits awkwardly with the sovereign, customer-runs-it architecture argued elsewhere in the corpus |
| Running browsers for strangers is an abuse surface | The allowlist gate is a real control, but scraping, request forgery against internal addresses, and malicious automation are risks the memo does not address |
| Three tiers versus yesterday's focus problem | These add to the nine named on 23 July, making twelve candidates, and the engagement model signs off one time-bound project at a time |
| The proxy as differentiator versus the proxy as liability | A service that intercepts and records traffic is exactly the service that must have an unimpeachable security and retention story before an enterprise will use it |
