## The Decision Being Rated

There are two designs, and the choice between them is a risk-acceptance decision, not an IT preference.

**Option A, in the user's browser.** The agent runs inside the user's browser profile, on the user's desktop, using the sessions the user is already logged into. This is the default, because it is the easiest to build and the most immediately useful: the agent can do anything the user can do, with no setup.

**Option B, in an isolated browser.** The agent runs in a separate, managed browser environment with an identity of its own, scoped to the task, with the user's desktop out of reach and a policy boundary around what it may visit, download, and send.

## The Assets At Stake

What Option A actually places within reach.

| Asset | Why it matters |
|-------|----------------|
| Authenticated sessions | Mail, finance, the customer system, admin consoles, cloud storage, all live and already past multifactor |
| Saved credentials and passkeys | The browser's own store, reachable from the profile the agent runs in |
| The desktop and its files | Downloads, local documents, and whatever else the user's account can open |
| The device's network position | A trusted endpoint inside the corporate network, which is a foothold, not just a browser |
| Attribution and non-repudiation | The ability to say who did what, which is a governance asset in its own right |

## The Facts

- **F1.** An agentic browser performs tasks by reading web pages and acting on them.
- **F2.** Web content is written by strangers, and the agent cannot reliably tell an instruction from content.
- **F3.** In Option A the agent runs in the user's profile, on the user's desktop, with the user's live sessions.
- **F4.** Those sessions are already authenticated, so the session is the credential and no step-up challenge fires.
- **F5.** The agent therefore holds the user's full authorization closure, plus the desktop and the network position.
- **F6.** Actions taken in the user's session are indistinguishable from the user's own actions.
- **F7.** Model-level injection defences have improved substantially and do not reach zero.
- **F8.** The agent acts at machine speed, so a hijacked task completes before a human can intervene.

## The Evidence

- **E1.** Published security research demonstrating indirect prompt injection against a production agentic browser, where hidden instructions in ordinary page content steered the agent.
- **E2.** A major vendor shipping a lockdown mode for its AI browser while stating publicly that prompt injection may never be fully patched, and another describing the problem as demanding a rethink from the ground up.
- **E3.** Independent enterprise testing in 2026 finding that leading AI browsers blocked only a small share of malicious test pages.
- **E4.** An analyst recommendation that enterprises block AI browsers for the time being, with many organisations restricting them to approved tools and keeping sensitive workflows off them.
- **E5.** Vendor system cards reporting browser prompt-injection attack success rates falling from roughly half to about one percent across a single model generation, which is a large real improvement and still not zero.
- **E6.** Academic research on browsing agents documenting credential exfiltration and unauthorised task execution, and recommending architectural isolation between planning and execution.
- **E7.** Identity-industry analysis describing the browser as an identity execution layer, where untrusted content becomes an identity input and the agent acts with the same privileges as the logged-in employee.
- **E8.** Survey data showing few organisations feel prepared for agentic AI while most security leaders say identity management must fundamentally change.

## The Vulnerabilities

A fact becomes a vulnerability once it has an upward path to a risk.

- **V1, indirect prompt injection.** From F1 and F2: any page the agent reads can issue it instructions.
- **V2, session inheritance.** From F3 and F5: the agent's authorization closure is the user's closure, entire and unscoped.
- **V3, multifactor bypass by design.** From F4: the session token is the authentication, so the strongest control the enterprise owns never fires.
- **V4, attribution collapse.** From F6: there is no separation between what the agent did and what the human did, so there is no audit trail and no non-repudiation.
- **V5, desktop and network reach.** From F3: the agent sits on a trusted device inside the network, so the exposure is not confined to the browser.
- **V6, no circuit breaker.** From F8: a hijacked task completes at machine speed, before detection is possible.

## The Risks

- **R1.** A hostile page hijacks the agent, which then acts with the user's full identity.
- **R2.** Mass exfiltration from any authenticated session the user holds.
- **R3.** Unauthorised transactions or record changes made in the user's name.
- **R4.** The enterprise cannot determine what the agent did versus what the person did.
- **R5.** Lateral movement from the trusted desktop into the corporate network.

## What Isolation Actually Changes

This is the heart of the case, and it is a comparison of computed reach, not a contest of adjectives.

| Dimension | Option A, the user's browser | Option B, an isolated browser |
|-----------|------------------------------|-------------------------------|
| Identity the agent holds | The user's own, with every live session | A scoped, task-specific identity |
| Authorization closure | Everything the user can reach | Only what the task's credential reaches |
| Multifactor | Already satisfied; no step-up ever fires | A fresh, scoped, time-bound credential per task |
| Desktop reach | Full: files, downloads, local applications | None: the agent is not on the desktop |
| Network position | A trusted device inside the corporate network | The isolation platform's egress |
| Attribution | Collapsed: the agent is the user | A separate agent identity, per task |
| Audit | The user's own history, indistinguishable | A policy-enforced log of what the agent did |
| Injection | Lands, with the user's full reach | Lands, with the task's reach only |
| Blast radius | Bounded only by the user's identity | Bounded by the task scope |

The row that matters is the last one, and the row that keeps it honest is the one above it. Injection lands in both designs. What changes is what it reaches. That is why this is a scope move and not a policing move: it does not add a fallible arbiter that must catch every attack, it removes variables from the closure, and a branch that is absent cannot be mis-adjudicated. The business case is therefore computable, the user's closure versus the task's closure, from grants rather than from fear.

## The Honest Case: Isolation Has Its Own Risks

A business case that only lists benefits is FUD, so here is the other side, and it is what makes the case credible to a CISO rather than a slide.

Injection is not prevented, only bounded, so the agent still gets hijacked and simply does less damage. Isolation without scoping is theatre: hand the isolated browser the user's single sign-on and every advantage above evaporates, because the closure is what mattered, not the container. The platform becomes a concentrated dependency, the single thing standing between the agent and everything, which is the swallowing risk in its familiar shape. The platform now sees the content, which is a new third-party data risk to own. Container escape is a real if unlikely path. And cost, latency, and friction are not free: a design people route around protects nothing, and some tasks genuinely need the user's identity, so isolation relocates the credential question rather than answering it. Every one of these belongs on the register as a risk of the mitigation, because every action has risks, including the good ones.

Read the closure comparison: `grant-session` grants `closure-user` which exposes `br-a` reaching the sessions, the desktop, and the network, whereas `grant-task` grants `closure-task` which exposes only `br-b`. That difference is computed from the grants, not asserted. The `impairs` edge, for a vulnerability that degrades an asset rather than exposing it, is proposed here alongside `conditional_on` and `emits`.

## Why This Is How This Industry Should Sell

The instinct in this category is to lead with the demo and the fear, and it underperforms because a CISO exhausted by vendors discounts fear automatically. The stronger move is the one this brief models. Lead with the closure comparison, because it is arithmetic rather than adjectives, and a buyer can check it. Concede the residual openly, since injection still lands and isolation without scoping is theatre, which buys the credibility that makes the rest land. Put the mitigation's own risks on the register, because a vendor who models the risks their product introduces is telling the truth. And hand the buyer a graph with names at every altitude rather than a slide, so the question stops being do you believe us and becomes who signs this, which is a question a board can actually answer. That is also the accept-first sequence from this morning: the organisation almost certainly has agentic browsing happening already, so the honest first step is to accept the current in-browser exposure now, explicitly and owned, and then let the isolation project be the funded adjustment that re-rates it down.

## What This Does Not Try To Be

- **Not a claim that isolation prevents injection.** It bounds the blast radius; the injection still lands.
- **Not a level assertion.** The case is a computed closure comparison; the residual level depends on the controls in place.
- **Not FUD.** The evidence includes the large improvement in model-level defences, not only the failures.
- **Not free.** The platform is a concentrated dependency that sees the content, and friction routes users around it.
- **Not legal advice.** The governance points are factual, not determinations.

## Honest Tensions

| Tension | Note |
|---------|------|
| Utility versus scope | The agent is useful because it can act as you; that is exactly what makes Option A dangerous |
| Isolation versus scoping | An isolated browser holding the user's single sign-on has recreated the problem inside a nicer box |
| Bounded blast radius versus prevented attack | Injection lands either way, which is the honest limit of the entire category |
| Improving models versus residual | Attack success rates have fallen sharply, and a small non-zero rate at machine speed is still material |
| Friction versus adoption | A design people route around protects nothing, so usability is a security property here |
