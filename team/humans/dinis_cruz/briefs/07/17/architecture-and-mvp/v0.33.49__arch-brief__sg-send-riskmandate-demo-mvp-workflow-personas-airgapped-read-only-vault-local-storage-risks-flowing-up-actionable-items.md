**date** 17 July 2026
**from** Human (project lead)
**to** Product, Engineering, Design, Commercial

*Sixth of 17 July, a memo pinning down the concrete input, output, and mechanism of the demo and the MVP. Offered to be built on and challenged.*

## What This Is

The concrete demo and MVP workflow for RiskMandate, built around an input and an output that the product controls end to end: **the thing being produced is a personalised risk mandate, which is the individual's own risk dashboard, and the demo begins with pre-populated personas and use cases loaded on the core platform, with the core scenario saved in the vault and then customised on top, so the same act that builds the example also defines a deliverable, because a deliverable here is exactly a defined use case, a defined set of scenarios, and something the recipient can follow up on; the first phase is deliberately airgapped and not integrated with the customer's systems, which turns the whole bet into a single question, whether the product adds value by raising enough real questions, concerns, and risks that the recipient changes behaviour and asks the right questions, rather than by doing heavy integration, and the scenarios worth leading with are the ones where people are adding agents to existing workflows, because that is the flow that is actually problematic; the power of the demo is that the potential partner goes through the application themselves and experiments, which is made possible by a specific mechanism, sharing a read-only copy of the vault that lives on the website and using local storage so the user's changes are saved locally with no backend and no risk to the source; the flow is simple by design, the user picks a persona, answers a couple of yes and no questions about the agents they run through a very simple form and UI, and the product generates that user's risks, and because it matters who the user is, it shows not only that user's register but the registers above them, their boss and upward toward the CEO as far as their line of sight reaches, so the demo's key moment is the visible flow of risks upward; and the engagement ends by delivering a set of actionable items, more information, a report of the risks that have been accepted, or follow-ups to the other executives, with each individual holding their own register while also seeing the dynamic registers of the other players involved.** It is the sixth brief of 17 July (cross-ref: the v0.33.46 MVP-build-architecture brief, the v0.33.44 experience-workflow-map brief, the v0.33.48 browser-local-databases brief, the v0.33.49 fractal-registers brief, and the v0.33.49 risk-mandate brief). New contributions: **the MVP defined as a fully controlled input and output, pre-populated personas customised on top of a core scenario in the vault, the airgapped-first bet that value comes from raising the right questions rather than from integration, the read-only-vault-plus-local-storage mechanism that lets a partner experiment on the website with no backend, the persona-to-risks-flowing-up demo flow, and the actionable-items deliverable with each individual seeing their own register and the dynamic registers above them.**

## The Input And The Output, And We Control Both

The clarifying move in this memo is to stop describing the product in the abstract and pin it to an input and an output that the team owns completely. In phase one there is no integration to complicate either end, so the demo is a closed loop the team can make good on its own terms. The output is the personalised risk mandate. The project lead: **"the creation of these personalised risk mandates, which are fundamentally the risk dashboards for the individuals."** The mandate is what is sold and the dashboard is how the individual sees it, which keeps this consistent with the sibling strategy brief that demotes the dashboard as the thing being sold while the individual still has one to look at.

```
   INPUT (we control it)                         OUTPUT (we control it)
   pick a persona   -->  a few yes/no about  --> generate this user's risks
   (pre-populated)       the agents you run      |
                         (very simple form)      v
                                            show registers, flowing UP:
                                              you -> your boss -> ... -> CEO
                                                    (as far as you can see)
                                                       |
                                                       v
                                            actionable items:
                                              more info / accepted-risk report /
                                              follow-ups to the other execs
```

## Pre-Populated Personas On The Core Platform

The demo is seeded, not blank. The project lead: **"we need to start with the personas and the use case that we can pre-populate."** The build method is itself a demonstration of the platform, because the core scenario is held in the vault and the specifics are layered on top. The project lead: **"having the core scenario saved in the vault, and then customising it on top."** That layering is why the example is not throwaway; the same structure that makes a convincing demo is the structure of a real deliverable. The project lead: **"you define the use case, you define the scenarios, and then you give them something that they can follow up."** So the demo and the first deliverable are the same artifact seen at two moments, which is what makes this a credible beginning for the MVP rather than a throwaway sales asset.

## Airgapped First: Does It Add Value Without Integration?

The strongest discipline in the memo is the refusal to lean on integration in phase one. The project lead: **"in the beginning we will assume that it is all airgapped and not integrated with the existing systems."** That constraint is not a limitation to apologise for; it is the test. The project lead: **"the question is, do we add value, do we raise enough questions, enough concerns and risks that allow the recipient to then go and do something about it, change behaviours, ask the right questions."** If the product can move behaviour with no data pipe into the customer, the value is in the thinking, not the plumbing. The project lead is explicit that heavy integration is not the phase-one job. The project lead: **"this is not about doing massive integrations on the other side."** And the scenarios that earn their place are the ones that are actually dangerous. The project lead: **"it is worth focusing on existing agentic workflows when people are adding agents to the mix, because that is the flow that is problematic."**

## The User Drives It Themselves

The demo is not a walkthrough performed at the partner; it is handed to them. The project lead: **"the potential partner going through the application themselves, because that is the power."** The design goal is experimentation. The project lead: **"how can I allow the user to experiment with the platform."** A partner who has clicked through their own scenario and watched their own risks appear has a different conviction than one who watched a slide, which is the whole reason the mechanism below matters.

## The Mechanism: Read-Only Vault Plus Local Storage

Letting an unknown partner drive a live application, on the website, with no backend to protect, is solved by one specific arrangement. The project lead: **"we share the read-only copy of the vault, and they use local storage to make and save any changes locally."** The source vault is never written to; every change the user makes lives only in their browser. The project lead is clear about where this belongs. The project lead: **"in fact, this should be on the website."** This is the browser-local-databases pattern from the v0.33.48 work put to direct use: the vault is the read-only source of truth, the query and edit happen client-side, and local storage holds the session, so there is nothing server-side to stand up, secure, or reset between visitors.

```
   WEBSITE
   read-only copy of the vault   (source of truth, unchanged)
            |
            |  user experiments
            v
   LOCAL STORAGE (in the browser)   <-- all the user's changes live here
            |
            x   no backend, nothing written back to the source vault
```

## The Flow: Persona To Risks Flowing Up

The interaction is deliberately minimal at the front and rich at the back. The project lead: **"the user chooses the persona, then there are a couple of scenarios where he provides information about maybe the agents they have, a couple of yes and no, very simple forms, very simple UI."** From that thin input the product does the work. The project lead: **"we are creating the risks for that user."** The identity of the user is not incidental, it is the pivot, because the register a person sees depends on where they sit. The project lead: **"it is important who the user is, because the logic is that we are showing the multiple dashboards for that user."** And what is shown is not one register but a stack of them. The project lead: **"we are showing the risk register for the user, the risk register for its boss, and all the way up to the CEO, depends how high you are, depends how high you can see."** That upward stack is the payload of the whole demo. The project lead: **"we need to show that flow of risks flowing up, and that is fundamentally the key point of the demo and the MVP."**

## The Deliverable: Actionable Items

The loop closes on something the recipient can act on rather than a dashboard they admire. The project lead: **"in the end we need to deliver them a set of actionable items, and this could be more information, could be a report of the risks that have been accepted, could be the follow-ups to the other execs."** The structural requirement underneath the deliverable is dual visibility. The project lead: **"each individual needs to have its own register, but also needs to be able to see the dynamic registers of the other execs."** So the deliverable is not a static PDF but a position in a live set of registers: your own to own, and the others' to watch as they move, which is what makes the follow-ups to other executives meaningful rather than cosmetic.

## What This Does Not Try To Be

- **Not an integrated product in phase one.** It is airgapped, with no connection to the customer's systems, by design.
- **Not a heavy-input experience.** A couple of yes and no questions, very simple forms, very simple UI.
- **Not a backend-hosted demo.** A read-only vault on the website plus local storage for local-only changes, nothing server-side.
- **Not a single-register view.** Each individual sees their own register and the dynamic registers above them.
- **Not a passive demo.** The potential partner drives the application themselves and experiments.

## Honest Tensions

| Tension | Note |
|---------|------|
| Airgapped versus real risks | With no integration and self-reported yes/no input, the risks are only as good as the persona and scenario mapping; the value bet is real but unproven until a partner reacts |
| Local-only changes versus continuity | Local storage protects the source and privacy, but the user can lose their work, and there is no defined path from a local experiment to an owned, persistent vault |
| Upward visibility in a demo versus in production | Showing a junior their boss's and the CEO's registers is the compelling moment, yet that upward line of sight is exactly the sensitive, permissioned thing a real deployment must govern |
| Chosen persona versus the real user | A partner walking a pre-built persona experiences a curated path; the leap to this is my risk needs a broad, honest persona library or the demo over-promises |
| Trivial input versus rich output | Generating a credible personalised register from a couple of booleans is a strong claim; the input-to-risks mapping is where the value must be real rather than scripted |
| Demo as deliverable versus depth | Reusing the example as the deliverable is elegant, but risks the deliverable being only as deep as an airgapped, self-reported demo when a paying client expects more |

## Open Questions

| Question | Notes |
|----------|-------|
| What is the persona library, and how wide must it be? | How many personas cover enough of the market for a partner to see themselves in one |
| How does a local experiment convert to an owned vault? | The handoff from a read-only, local-storage session to a persistent, real engagement |
| What governs upward register visibility in production? | Who is allowed to see whose register, versus the open visibility shown in the demo |
| What is the minimal input set, and how is the mapping produced? | Which yes/no questions yield a credible register, and whether input maps to risks deterministically or via an LLM |
| What are the standard deliverable formats? | Whether the accepted-risk report and exec follow-ups are generated or templated, and in what form |
| Which scenarios seed the launch? | How many agentic-workflow scenarios are needed at launch, and which existing ones carry over |
