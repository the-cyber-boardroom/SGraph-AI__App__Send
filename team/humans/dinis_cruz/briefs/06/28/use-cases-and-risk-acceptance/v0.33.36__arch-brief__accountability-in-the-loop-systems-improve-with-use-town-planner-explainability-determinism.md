# The 2:17am Problem, Part Two: Why the System Should Improve With Use

**version** v0.33.36
**date** 28 June 2026
**from** Human (project lead)
**to** Architect, @Dev, Product, Strategy
**type** Arch brief

---

## What This Is

The second of the paired reflections on the 2:17am problem, the system-design lens: **the deeper failure is that the system was built to degrade with use rather than improve, because the more it ran the less attention it received and the more dangerous it became, working well for the first weeks and then drifting into bad behaviours and edge cases; this happened because the team stopped optimising and never handed the system over to the town planners, leaving it stuck in an early, experimental phase, when a system like this should get better the more it is used, as more real use cases, more data, and less ambiguity flow in; the way to earn that is the town-planner approach, reducing scope, defining state flows and state machines, adding authorization tokens and fine-grained actions, and above all optimising for explainability, evidence collection, and visual representations of the decisions, which is how you reach determinism, make the clear decisions automatically, and route the unclear or higher-risk decisions to a separate pipeline.** It pairs with the risk-acceptance reflection (cross-ref: the v0.33.36 part-one strategy brief, the v0.33.32 explaining-the-why briefs, and the v0.33.35 risk-register brief). New contributions: **improve-with-use as a design property, the town-planner handover, and the two-pipeline determinism model.**

## The Deeper Failure: A System Built to Degrade

The incident in part one was a symptom; the disease is the shape of the system over time. The project lead: **"the system degrades with usage, the more usage, the more you are paying, the less attention you pay, the more dangerous it becomes."** And the decay has a profile. The project lead: **"it works great in weeks two to eight, but after week six you start to see these other behaviours and edge cases."** A system whose risk rises with its mileage, while the humans around it relax, is built to fail at exactly the moment it is most trusted.

## The Property It Should Have Had: Improve With Use

The right design has the opposite slope. The project lead: **"systems like this should get better the more you use them, more use cases, more data, less ambiguity, but only if you do the town planner approach."** Every real interaction is information, about the happy cases, the edge cases, the genuine ambiguities, and a well-built system folds that information back in so that uncertainty shrinks and reliability grows. Improving with use is not automatic; it is a property you have to engineer, and it is the property this system lacked.

## Why It Degraded: No Handover to the Town Planners

The reason is an evolution failure. In the Explorer, Villager, and Town Planner model, a system begins as an experiment, is built into something solid, and is finally hardened and stewarded for the long term. This credit system, in the project lead's reading, never left the early phase, it was never handed over to the town planners, so no one took on the work of reducing scope, hardening the flows, and making it dependable. It kept running on experimental foundations while being treated as production, which is precisely how a thing degrades with use.

## The Town-Planner Work

What the handover would have involved is concrete. The project lead: **"reducing scope, creating state flows and state machines, authorization tokens, and granularity of actions."** Narrowing what the agent may do, expressing its behaviour as explicit state machines rather than open-ended latitude, gating actions behind authorization tokens, and making the actions fine-grained, together turn an unbounded agent into a bounded, inspectable one. And as the system stays in place, the happy cases become known, so the common paths can be made safe and routine while the unusual ones are surfaced rather than waved through.

## Optimise for Explainability, Evidence, and Determinism

The missing optimisation target is the heart of it. The project lead: **"they are not optimising for explainability, for evidence collection, for creating visual and digital representations of the decisions, the trees, the flows."** A system that records why it decided, that collects the evidence behind each decision, and that can render the decision as a tree or a flow is a system you can reason about. And that is the route to determinism. The project lead: **"that is how you get determinism, how you make a number of decisions automatically, and the decisions that are not automatic, or have a higher risk profile, go to a separate pipeline."** Explainability is not a reporting nicety; it is what lets you separate the decisions that are safe to automate from the ones that need more thought.

## The Two-Pipeline Model

The design that falls out is two pipelines. The first is for decisions that are clear, low-risk, and well-understood, which run deterministically and automatically, fast and unattended because they have earned that trust through evidence. The second is for decisions that are ambiguous, novel, or carry a higher risk profile, which are routed away from the automatic path into a pipeline with more scrutiny, more context, and genuine human judgement, the real human-in-the-loop that part one found missing. The boundary between the pipelines is not fixed; as the system improves with use, more decisions earn their way into the automatic path, and the system gets both faster and safer over time.

## Why This Is the Right Fix

Part one showed that narrowing the agent's scope, the team's actual response, throws away the value. This is the alternative: not less capability, but more control, earned through explainability, state machines, fine-grained authorization, and the two-pipeline split. It keeps the power of the agent while making its decisions inspectable, deterministic where they can be, and escalated where they must be, and it turns the system from one that degrades with use into one that improves with it.

## What This Does Not Try To Be

- **Not anti-automation.** The clear decisions should run automatically and fast.
- **Not anti-agent.** The fix is more control, not less capability.
- **Not a one-time hardening.** Improving with use is continuous.
- **Not separate from acceptance.** The risks it surfaces are accepted as in part one.

## Honest Tensions

| Tension | Note |
|---------|------|
| Automation versus scrutiny | The pipeline boundary must move as trust is earned, not be set once |
| Explainability cost | Recording evidence and rendering decisions has overhead; it is the price of determinism |
| Town-planner timing | Handover too early kills exploration; too late bakes in decay |
| Improve-with-use is a claim | It must be measured, not assumed, as decisions move to the automatic path |
