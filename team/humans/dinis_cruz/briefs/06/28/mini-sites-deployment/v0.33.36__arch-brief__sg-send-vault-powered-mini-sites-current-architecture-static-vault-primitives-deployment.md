# Vault-Powered Mini-Sites: The Current Architecture and What a New One Takes

**version** v0.33.36
**date** 28 June 2026
**from** Human (project lead)
**to** Architect, @Dev, Product
**type** Arch brief

## What This Is

A map of the current architecture for the vault-powered websites and what it takes to deploy a new one, ahead of simplifying it: **the goal is to create many mini-sites, one per use case for Risk Mandate.ai and for other projects, each with its own home and structure, so the deployment needs to get much smoother; the current architecture, proven on the SGraph-AI library, has two primitives, a static site of HTML files in S3 served through CloudFront, and a vault whose files live in S3 and are written through a Lambda function that wraps the vault APIs behind an API key, with the website given the vault's read key so it can read the pages directly; a CI pipeline writes the static files, and the initial configuration can live as secrets or config on the main SG/Send APIs, reachable from a single original key; and today, standing up a new site means a new Lambda, a new CI pipeline and repo, and two S3 structures, one static and one vault, with a CloudFront distribution over the static one, which is more setup than it should be for something we want to do many times.** This is the current-state map, and the next memo will propose the simplification (cross-ref: the v0.33.33 S3-compatible vault container, the v0.33.34 vaults-and-healthcare-mvp debrief, and the v0.33.36 use-case-driven-shipping brief). New contributions: **the two-primitive framing and the new-site deployment checklist.**

## The Goal

The driver is volume. The project lead: **"I want to create lots of these mini websites, and each kind of needs its own home and its own structure, so we need to simplify the deployment."** The use cases for Risk Mandate.ai each want their own site, and so do other efforts, the doctor wants several sites, other projects need their own sites and vaults. The pieces of the puzzle already exist and work, but standing up each new site is not yet as smooth as it needs to be.

## The Current Architecture

The architecture is the one already proven on the SGraph-AI library, and it works well. It has two halves.

**The vault side.** A Lambda function hosts the vault APIs. The project lead: **"we have a Lambda function that hosts the vault APIs, and it is fundamentally just a nice wrapper, an easy way to write to S3, protected with an API key."** The Lambda guards writes behind an API key, and the vault files themselves are stored in S3.

**The site side.** The project lead: **"we have a static set of files served via CloudFront that provide the HTML pages, and we leak into that website the read key of the vault, so the website can read the pages."** So the website is a set of static HTML files in S3, served through CloudFront, and the vault's read key is injected into the site so the page can read the vault's content directly in the browser.

**The pipeline and the config.** A CI pipeline writes the static files into S3, where CloudFront serves them, while the vault files are written through the Lambda API. And the configuration has a natural home. The project lead: **"we have the ability to store secrets or configuration on the main SG/Send APIs, which is a great place to store the initial config, where all you need is the original key, and from that key you can do everything."** From a single original key, the rest can be reached.

## The Current Architecture, Rendered

```
  CI pipeline ──writes──▶ S3 (static HTML) ──served by──▶ CloudFront ──▶  Website
                                                                            │
                                                                reads vault via
                                                                injected READ KEY
                                                                            ▼
  Vault environment ──writes via──▶ Lambda (vault API, API-key guarded) ──▶ S3 (vault files)

  Initial config and secrets ── stored on the main SG/Send APIs ── reachable from one original key
```

## The Two Key Primitives

The architecture resolves to two primitives, and seeing them separately is what points at the simplification.

**The static site.** This should be as stable as possible and, ideally, reusable. The project lead: **"if I am making multiple Risk Mandate websites, I should be able to just reuse the HTML part, and just the vault changes."** In other words, the same site shell should serve many deployments, and what differs between them is only the vault, which becomes little more than a configuration value handed to the shell.

**The vault.** This is the per-site data, the part that genuinely changes from one site to the next. It is written from the vault environment through the Lambda and read by the site through the read key.

## What a New Site Takes Today

Standing up a new site at the moment is the friction the next memo will address. The project lead: **"to set up a new website I need a new Lambda function, a new CI pipeline and repo, and two S3 structures, one for the static files served by CloudFront, and one for the vault files written from the vault environment and read by the website via the read key."** As a checklist, a new site today needs:

1. A new Lambda function for the vault API.
2. A new CI pipeline, in its own repo.
3. An S3 structure for the static files, with a CloudFront distribution over it, deployed via CloudFormation.
4. A second S3 structure for the vault files, writable from the vault environment and readable by the site via the read key.

For something meant to be done many times, that is more standing infrastructure than it should require.

## The Insight Toward Simplification

The map already suggests where the simplification lies, which the next memo will develop. Because the static site should be reusable and stable, the same shell ought to be deployable once and pointed at different vaults, with the vault reduced to a configuration value rather than a fresh stack. And because the configuration can live on the SG/Send APIs behind a single original key, a new site could in principle be defined by that key and its config rather than by a new Lambda, a new pipeline, and two new buckets each time.

## What This Does Not Try To Be

- **Not the simplification proposal.** That is the next memo; this is the current-state map.
- **Not a rewrite of the vault.** The vault technology is unchanged and works.
- **Not a critique.** The architecture is sound; it just needs streamlining for many sites.
- **Not the only deployment.** This describes the proven library pattern, not every option.

## Honest Notes

- **It works.** The current architecture is proven and good; the issue is repetition cost, not correctness.
- **Two primitives, two lifecycles.** The static shell should be stable and shared; the vault is per-site and changes.
- **One key as the seam.** Storing config on the SG/Send APIs behind one original key is the natural simplification point.
