# Vault-Powered Mini-Sites: The Publishing Workflow and the Static Vault

**version** v0.33.36
**date** 28 June 2026
**from** Human (project lead)
**to** Architect, @Dev, Product
**type** Arch brief

---

## What This Is

Refinements to the simplified deployment, captured as a separate document ahead of a consolidated one: **the missing piece is the publish-to-prod workflow, a way to push a vault's files to the live bucket, where QA holds the live vault and live Lambda for editing and collaboration and prod is only static files; the whole system should be built local-first, on the file system, then in Docker, then on live environments; prod should be pure static hosting, CloudFront over S3 or even GitHub Pages as a first experiment; the key requirement is that the published files form a static vault, a projection compatible with the SG/Send read API, so the JavaScript reading the content cannot tell a live vault from a static one, which is straightforward because SGit has a predefined file structure; each site is published from one simple GitHub repo carrying the read token and vault ID, which may be leaked because they are public in the site anyway, with the deployment code shipped as a PyPI package; and it resolves the two earlier open questions, the two vaults are a public content vault and a private internal vault, and the vault-in-git idea is pencilled pending vault-commit support.** It refines the part-two proposal and feeds a consolidated brief to come (cross-ref: the v0.33.36 part-one and part-two mini-site briefs). New contributions: **the publishing workflow, the static vault, local-first, the deployment repo, and the resolved two-vaults and vault-in-git questions.**

## The Missing Piece: Publish to Prod

The part-two design described QA and prod but not the bridge between them. The project lead: **"the workflow that's missing is the publish to prod, we need a way to publish the files from a vault to the actual bucket."** QA is the live, editable side, with a live vault and a live Lambda; prod is only static files. The publish is the act of pushing the vault's content out to the live bucket, and it is the piece that completes the pipeline.

## Build It Local-First

Before any of this touches the cloud, it should run on a laptop. The project lead: **"we should first build this entire system on the local file system and local execution of the lambda functions, even Docker, so we can run it on the file system, then off Docker, then on the live environments."** The progression is deliberate: file system first, then Docker, then the live environment, so the whole system is portable and testable end to end before it depends on any provider.

## Prod Is Pure Static Hosting

Prod should carry no runtime of its own. The project lead: **"the live version is only static files, it should be just pure CloudFront to S3, pure static files hosting, and in principle it could even run off GitHub Pages, which might be a good first experiment."** GitHub Pages is worth trying first, with one caveat the project lead notes, that GitHub Pages tends to upload everything, whereas a commit-based push knows exactly which files changed per version and could copy more efficiently, though that is a minor concern and arguably GitHub Pages' problem rather than ours.

## The Static Vault

This is the key requirement, and the heart of the refinement. The publish is essentially a push. The project lead: **"we are using the vaults as an editing workflow and a real-time development and collaboration environment, because they are version controlled, but the publish is basically a push, it should be all static."** What the push produces is a static vault, and it must be indistinguishable from a live one to the reader. The project lead: **"the published files need to be compatible with the SG/Send default API, so that the JavaScript reading the content, especially in read-only mode, does not know the difference between a live vault and a static vault, which is just the projection of the files."** This is achievable cheaply. The project lead: **"this is straightforward because SGit has a very predefined file structure."** So the static vault is just the SGit file structure laid out as static files, and the read-side JavaScript treats it identically to a live vault.

## Two Modes: Vault Mode and Publishing

The architecture now has two clean modes. Vault mode runs against any live vault that exists. The publishing workflow projects a vault into a static vault on a bucket or GitHub Pages, and it has two parts, the projection itself and the read-side that consumes it. The read-side code needs refactoring out of the existing codebase. The project lead: **"the JavaScript API needs to be refactored from the current SGraph web repo into this static-vault environment, consumed by the specific content vault."** And there is one compatibility check. The project lead: **"I need to check whether GitHub Pages allows CORS, because if it does not, you have to post to S3."** If GitHub Pages does not permit the cross-origin reads, the static vault is served from S3 instead.

## The Publishing Flow, Rendered

```
  EDIT (QA):   live vault + live Lambda  <- edited by agent / Claude UI / vault
                     |
                     |  publish (a push)
                     v
  PUBLISH:     CI pipeline projects the vault -> STATIC VAULT (SGit file structure)
                     |                                   -> S3, or GitHub Pages (if CORS allows)
                     v
  PROD (live): pure static hosting (CloudFront over S3, or GitHub Pages)
                     |
                     |  read via the SG/Send read API; JS cannot tell live vault from static vault
                     v
               client loads and decrypts -> the site is built from the (static) vault
```

## The Deployment Repo

Each site publishes from one small GitHub repo, which exists mainly to carry the CI pipeline. The project lead: **"publishing a site requires one GitHub repo for the CI pipeline, and we give it the read token, which we can even leak in the code base because it is leaked in the main website anyway, along with the vault ID."** The trigger is a tiny configuration. The project lead: **"that small configuration, the vault ID, the read token, maybe the transfer ID and the decryption keys, is what triggers the CI pipeline deployment."** And the repo should stay thin. The project lead: **"keep the repo as simple as possible, and the deployment code we will probably put on a PyPI package so we can just import it as part of the CI pipeline."** The repo might also hold a little documentation or onboarding, but most of the site comes from the vault, so the repo's real job is to trigger deployment. It starts as one, and grows into the place where many sites, with many URLs and deployments, are managed.

## The Two Vaults, Resolved

This answers the earlier open question about the two vaults. The project lead: **"for risk mandate we should have a public vault, which is only the content on the website, and a more internal vault, which we also use to capture some secrets and the strategy and admin stuff we collaborate on, kept as private as little as possible."** So a public content vault feeds the site, and a private internal vault holds secrets, strategy, documentation, and coordination, with the bias toward keeping as little private as possible while accepting that some admin and coordination genuinely needs to be.

## Vault-in-Git, Pencilled

This answers the earlier open question about the git escape. The project lead: **"the other idea is that we could store the vault inside the git repo, with git holding the raw files and SGit used for the flow, but that would need support for committing on vault changes, which is planned but not fully supported, so for now let's pencil it."** It raises a real question of ownership. The project lead: **"then you think about who owns the master data, the vault or git, but for now let's keep it simple with the technology we have."** So the idea is recorded and deferred, because the vault UI does not yet support it cleanly.

## What This Does Not Try To Be

- **Not the consolidated brief.** That is the next step; this captures the new ideas.
- **Not a change to the vault.** The vault and SGit are unchanged; this projects from them.
- **Not server-side decryption.** Reading stays client-side, live or static.
- **Not vault-in-git yet.** That idea is pencilled, pending vault-commit support.

## Honest Tensions

| Tension | Note |
|---------|------|
| Live versus static parity | The static vault must match the SG/Send read API exactly, or the JS will diverge |
| GitHub Pages versus S3 | Depends on the CORS check; S3 is the fallback |
| Leaking the read token | Acceptable because it is public in the site, but only the read token, never write |
| Repo simplicity versus customisation | The repo should stay thin; customisation should come from the vault or the PyPI package |
| Vault or git as master | Deferred; vault-in-git needs vault-commit support before the question is live |

## Open Questions

| Question | Notes |
|----------|-------|
| Does GitHub Pages allow the needed CORS? | If not, serve the static vault from S3 |
| What exactly does the projection emit? | The static-vault file layout matching SGit |
| What goes in the deployment config? | Vault ID, read token, transfer ID, decryption keys |
| When does vault-commit support land? | The prerequisite for vault-in-git |

## What This Asks For

1. Build the publish-to-prod workflow: project a vault to a static vault on a bucket.
2. Build it local-first: file system, then Docker, then live.
3. Make prod pure static hosting; try GitHub Pages first, fall back to S3.
4. Make the static vault byte-compatible with the SG/Send read API, using the SGit layout.
5. Refactor the read-side JavaScript out of the SGraph web repo.
6. Give each site one thin deployment repo with the read token and vault ID.
7. Ship the deployment code as a PyPI package.
8. Use a public content vault and a private internal vault per site.
9. Pencil vault-in-git until vault-commit support lands.
10. Then create the consolidated mini-site deployment brief.
