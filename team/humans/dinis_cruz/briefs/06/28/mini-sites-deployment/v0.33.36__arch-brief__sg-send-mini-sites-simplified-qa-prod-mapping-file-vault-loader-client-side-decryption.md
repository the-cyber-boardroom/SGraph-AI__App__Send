# Vault-Powered Mini-Sites: The Simplified Deployment

**version** v0.33.36
**date** 28 June 2026
**from** Human (project lead)
**to** Architect, @Dev, Product
**type** Arch brief

---

## What This Is

The proposed simplification of the mini-site deployment, the part-two to the current-architecture map: **it introduces a QA-and-prod split, where QA stays the fully editable mode running on a Lambda and writable by the agent, the Claude UI, or the vault, with all the dynamism and risk that implies, and prod becomes a static, S3-served, client-side-decrypted site with no full Lambda API, air-gapped from QA and updated only through a CI pipeline; prod aims to run on nothing more than a CloudFront distribution, a CloudFront Function, and files, so it can host anywhere there is a little compute and storage, including Cloudflare or Google; a single exposed mapping file in S3 maps each DNS name to its SG/Send vault ID and read key plus its configuration, and is maintained by a CI pipeline that reads the DNS TXT records, since the browser cannot read DNS directly; and a small versioned JS vault loader reads that mapping, fetches and decrypts the vault data, and builds the entire site, UI, functionality, and content, from the vault, so a new site is spun up by changing one file.** It is the simplification promised at the end of part one (cross-ref: the v0.33.36 part-one current-architecture map, the v0.33.33 S3-compatible vault container, and the graph.ai client-side decryption). New contributions: **the QA-and-prod split, the exposed mapping file, and the JS vault loader.** Note: this memo was exploratory, so several points below are marked as open rather than settled.

## The New Variable: QA and Prod

The simplification introduces the deployment pipeline. The project lead: **"we need to introduce the concept of QA, dev, main, and prod, but to start with let's shorten it to at least two, QA and prod."** The full pipeline is QA, where the agent writes, then dev, then main which equals prod, then prod, but for now two environments are enough, a place to author and verify, and a place that is live.

## QA: The Editable Mode

QA is where content is made and checked. The project lead: **"QA is the mode where we can verify and create content, and we allow the agent to edit, and it can be changed directly by the Claude UI or by the agent in the vault itself."** It is essentially the current model, and it runs on a Lambda, with the costs that implies. The project lead: **"the QA runs off Lambda functions, which have scalability and cold-start problems, and it is a security vulnerability, because you are one prompt, one mistake away from something being in prod that should not be."** So QA is powerful and dynamic but unsuited to being the live surface, and it lacks quality control by design.

## Prod: Static, Served From S3, Client-Side Decrypted

Prod is the opposite: stable, static, and safe. The project lead: **"the prod is the one that serves the files directly from S3, and we already have a formula for this that almost worked, where the GET requests were compatible with the API."** The data is still decrypted in the browser. The project lead: **"the data is decrypted on the client side using the same technique we have on graph.ai, and for now let's keep the structure where it is the client that goes and gets and decrypts the file, because it is also a cool demo of the technology."** Keeping client-side decryption is deliberate, both to prove the technology and to surface the real performance questions. And prod is separated from QA. The project lead: **"we have an air gap between the QA, which can be edited by a vault, and the live website, which is edited by a CI pipeline."**

## The Goal: No Full Lambda, Run Anywhere

The point of prod is to shed the heavy runtime. The project lead: **"this static website now works as before but with no Lambda function, so it should be hostable anywhere we have a cloud function or cloud edge."** It should not need the full SG/Send vault API, the FastAPI service with its cold-start problem, only a little compute and a little storage. The project lead: **"ideally this could run from Cloudflare, or even Google, so it would be cool to make it compatible with multiple providers, because all you need is a bit of compute and a bit of storage."** The one piece that still needs a layer is SSL termination, which is why some minimal compute, rather than pure storage, is likely required.

## The Edge Logic: CloudFront Functions, Not Lambda@Edge

The domain points to a CloudFront distribution, and a little logic resolves the domain to its vault. There are two edge options, with a clear preference. The project lead: **"the CloudFront function is super fast and runs efficiently but cannot make network requests out, it can only see the input and the output, whereas Lambda@Edge can have logic, and I really do not want Lambda@Edge because it adds complexity."** So the design works within the CloudFront Function's no-network-out constraint, which is exactly what the mapping file is for, the resolution does not need a network call out because the mapping is a file the browser fetches.

## The Mapping File

The heart of the simplification is a single mapping file. It maps each DNS name to its vault and key. The project lead: **"we have a mapping between the URL and the vault ID and the decryption key, and the question is whether we expose it, and I think we would, because the mapping is just the DNS name to the SG/Send vault ID and the read key."** Exposing it is acceptable precisely because, in the client-side-decryption model, the read key is meant to be in the browser anyway. The file lives at a deterministic location in S3, and it is the single lever for new sites. The project lead: **"the beauty of this is we can spin up a new site or a new capability just by changing this one file."**

The reason it is a file rather than DNS is that the browser cannot read DNS. The project lead: **"we are doing this with a file because DNS records are not exposed to the browser, otherwise I would just do it via the DNS TXT entry."** So the bridge is a CI job. The project lead: **"a script reads the DNS TXT records, loads them, and updates the mappings file in the S3 bucket, and that is its sole job."** The mappings can therefore be authored as DNS TXT records and compiled into the exposed S3 file.

## The Vault Loader

On top of the mapping sits a small loader that does everything else. The project lead: **"the loader is actually quite simple, because all the key UI, functionality, and even content come from the vault."** Its only real job is to load and decrypt vault data. The project lead: **"once you can load a file from a vault and decrypt it, we can build anything."** The vault app UI is already downloaded programmatically from vault data, so the same approach serves a whole site. The mapping entry is really a configuration object. The project lead: **"it is a JSON file we control that contains the server the vault is hosted on, the URLs to build, the accesses needed, the vault ID and the read key, the load message, and properties for how much of the backend to expose."** And the loader itself is shipped as a library. The project lead: **"we version-control this and ship it as a JS library that can be imported into a site, so it becomes a static JS file or set of modules loaded on the page."**

## Serving the Mapping File: Two Choices

How the loader and mapping file are served is left open, with two candidates. The project lead: **"either a Lambda that gets the file from S3 with access only to that file, or a typical CloudFront loading a file from S3, making it obvious what is public versus private."** A scoped Lambda buys a little logic and tight access; plain CloudFront over S3 is simpler and provider-portable. The choice is a deliberate open question.

## The Prod Deployment, Rendered

```
  DNS (e.g. 2fa.demo.riskregister.ai) ──▶ CloudFront distribution
                                                │  CloudFront Function (sees the domain; no network out)
                                                ▼
                        serve from S3:   loader.js  (versioned JS library)
                                         mappings.json  (DNS name -> vault ID + read key + config)
                                                │
                                      browser runs loader.js
                                                │
                       loader reads mappings.json ──▶ finds vault ID + read key for this domain
                                                │
                       loader fetches vault data (immutable objects) and DECRYPTS client-side
                                                ▼
                       site built entirely from the vault: UI + functionality + content

  CI pipeline ── reads DNS TXT records ──▶ compiles mappings.json into S3   (its sole job)
  QA (separate): Lambda vault API + vault, editable by agent / Claude UI / vault, AIR-GAPPED from prod
```

## Why This Simplifies Things

A new prod site stops being a new stack. Instead of a new Lambda, a new pipeline and repo, and two S3 structures, a new site is a DNS entry, a row in the mapping file, and a vault, with one reusable loader serving them all. Because prod needs only a little compute and storage and uses client-side decryption, the same site can run on AWS, Cloudflare, or Google, and the read key living in the browser is the model working as intended rather than a leak.

## What This Does Not Try To Be

- **Not a change to QA.** QA stays the editable, Lambda-backed, agent-writable mode.
- **Not server-side decryption.** Prod keeps decryption in the browser, by design.
- **Not Lambda@Edge.** The edge logic stays in a CloudFront Function.
- **Not finished.** Several points are open; this is the architecture to define and MVP.

## Honest Tensions

| Tension | Note |
|---------|------|
| QA power versus safety | QA's dynamism is its value and its risk; the air gap to prod is the safeguard |
| Exposing the mapping | Acceptable in the client-decryption model, but it must carry only the read key, never write or private keys |
| No-network-out edge | The CloudFront Function cannot fetch; resolution must come from the served mapping file |
| SSL termination | The one reason pure storage is probably not enough; some minimal compute remains |
| Provider portability versus AWS logic | A scoped Lambda adds logic but ties to AWS; plain CloudFront over S3 is more portable |

## What This Asks For

1. Define the QA-and-prod split, starting with just the two environments.
2. Keep QA as the editable, Lambda-backed, vault-writable mode.
3. Build prod as static, S3-served, client-side-decrypted, with no full Lambda API.
4. Resolve the edge with a CloudFront Function, not Lambda@Edge.
5. Define the exposed mapping file: DNS name to vault ID, read key, and config.
6. Maintain the mapping file with a CI job that reads DNS TXT records.
7. Ship the vault loader as a versioned JS library.
8. Create MVPs and tests, and map the multiple flows, then implement.
