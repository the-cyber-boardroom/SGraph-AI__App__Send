# Setting Up The Agentic Team: Agents Inside The LinkedIn Vault, Via OpenRouter

**version** v0.33.26
**date** 13 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, @Dev, Strategy
**type** Dev brief

## What This Is

The environment setup for the next phase of the LinkedIn intelligence work: **spin up an agentic team that runs inside the LinkedIn vault, using OpenRouter for the in-vault LLM, with two kinds of agent (the external Claude session and the in-vault LLM), a roster of role-defined agents reused from the Send repo structure, email-FS-Lite as the rules of engagement, manual triggering now and automation later, OpenRouter token management as both a control surface and the commercialisation model, and read-only instruction vaults delivered through the website's read-only tokens, all kept within LinkedIn's terms by working from the data dumps rather than scrapers.** It follows the LinkedIn memos (cross-ref: the v0.33.16 linkedin-export-analysis, linkedin-semantic-knowledge-graph-crm-outreach, company-intelligence-vault, and data-source-mapping-agentic-research briefs) and builds on the key-management and compute work (cross-ref: the v0.32.7 central-key-management-openrouter-keys and v0.32.4 ephemeral-compute briefs). The companion UI brief is separate (cross-ref: the v0.33.26 linkedin-intelligence-ui-kanban-visualisations brief). New contributions: **the two-agent-types model, the in-vault OpenRouter agent, the agent roster, and the read-only instruction-vault delivery via the website.**

## The Milestone And The Terms-Of-Service Stance

The context: the visualisation now works across both LinkedIn dumps, and the approach stays strictly within LinkedIn's terms.

The project lead: **"with both LinkedIn dumps, we now create a really nice visualisation of the data and the messages. There are limitations and data issues, but already a lot of great stuff, especially the inbox, the likes, the comments, who I communicate with most, and spam gets detected very easily. I want to keep this within the SLAs and terms of LinkedIn, so we are not going to add scrapers, even though we could. The logic is to do all of this with the data, which means it will be a little behind and out of date, but that is okay, because a lot of this is about consistency, doing it every day."** So the design constraint is firm: work from the exported data, no scrapers, accept some staleness, and win on daily consistency (cross-ref: the linkedin-export-analysis brief).

## The Two Types Of Agent

The core architectural point: **there are two kinds of agent, the external Claude session and the LLM running inside the vault.**

The project lead: **"there are two types of agents involved. There is the Claude session I have now, which I gave the vault and it operates. And there is the LLM usage from within the vault itself, which is what we are going to add, leveraging the tools APIs and the tools JavaScript components that already exist. I want to start interacting with the vault and the files in the vault directly, not via the Claude loop, because it is going to be a lot more interesting."**

| Agent Type | What It Is |
|------------|------------|
| The external Claude session | The session the project lead drives now, given the vault, operating on it from outside |
| The in-vault LLM (new) | An LLM running inside the vault via OpenRouter, using the existing tools APIs and JavaScript components |

This is the first real example of wiring an agent inside the vault with OpenRouter, so the workflows and agents spin up from within the vault itself.

## The Agentic Team Structure

Reuse what already exists: **the Send repo has the team structure, so adopt it.**

The project lead: **"if you look at the Send project repo, there are a lot of great definitions, role MDs, an agentic team folder, a humans folder, and each agent has its own folder containing the role definitions. There is also the master CLAUDE.md that explains everything, so someone can clone the vault and understand it."**

| Element | Role |
|---------|------|
| The agentic-team folder | Holds the agents |
| The humans folder | Holds the human roles |
| Per-agent folders | Each agent's role definition |
| The master CLAUDE.md | Explains the whole vault so anyone cloning it understands it |

## The Agent Roster

The agents to define, each with roles, responsibilities, run conditions, outcomes, self-maintenance, and a way to communicate:

| Agent | Responsibility |
|-------|----------------|
| Architect | The structure and design of the system |
| Designer | The design work |
| Developer | The development work |
| Content | To be scoped; the project lead wants a conversation about it |
| LinkedIn analyst | Analyses the LinkedIn data; the exact name to be decided |
| Data scientist | The quantitative analysis |
| Ontologist (important) | Builds the intelligent taxonomy, especially for companies and the things to operate next |
| Librarian | Curates and finds across the corpus |

The project lead: **"we need the architect, designer, developer, the content agent, the agent that analyses LinkedIn, the data scientist, the ontologist which is very important, and the librarian. Each has specific roles and responsibilities, and we define when they run, the outcomes, how each maintains itself, and how they communicate. The ontologist is the one that creates the intelligent taxonomy, especially for the companies and the things we are going to operate next."** (Cross-ref: the nhi-2.0-semantic-knowledge-graphs brief for the ontology work.)

## The Rules Of Engagement: Email-FS-Lite

How the agents talk: **reuse the email-FS-Lite inbox protocol so agents can message each other.**

The project lead: **"we should add the inbox, the email-FS-Lite protocol we created, and define the rules of engagement, so the agents can email each other and send messages to each other."** So the inbox protocol becomes the inter-agent communication layer, with explicit rules of engagement.

## Triggering: Manual Now, Automation Later

The phasing: **trigger the agents manually first, then add automation, which raises an open question.**

The project lead: **"for now we trigger them manually, and eventually start to add automation, which is an interesting question of how we trigger automations to happen on vaults, probably one of the next steps."** So manual triggering ships first; automated triggering of agents on vaults is a named next step and an open design question (cross-ref: the ephemeral-compute-actions-on-vaults brief).

## Token Management And OpenRouter (The Commercialisation Model)

Why OpenRouter matters beyond convenience: **token management is both a control surface and the commercialisation model.**

The project lead: **"this is a good example of token management, controlling the prompts, making sure the prompts only have exactly what they need, and thinking about which tool usage we wire up or not. And once we have OpenRouter, giving OpenRouter keys to this is the commercialisation model."**

| Aspect | Detail |
|--------|--------|
| Prompt control | Each agent's prompt carries exactly what it needs, nothing more |
| Tool control | Decide per agent which tools are wired up |
| OpenRouter keys | The commercialisation model: keys distributed to vaults (cross-ref: central-key-management-openrouter-keys) |

## Read-Only Instruction Vaults, Delivered Via The Website

How to distribute the setup: **a read-only vault holds the setup instructions, delivered through the website's read-only tokens, which lets one vault serve both the website and the user's sub-vault.**

The project lead: **"it might be worth creating read-only vaults that contain the instructions for this. We can do it via the website too, and there is an interesting flow that kills two birds, because the SGraph website supports adding read-only tokens, so we could grab it from the website. The vault people use and add to their sub-vault is the same vault we use on the website, so it is the same thing."** So the instruction vault is read-only, distributed via the website's existing read-only-token support, and the same vault serves the website and the user's sub-vault (cross-ref: the recipient-created-disposable-vault and the read-only-token sharing model).

## What This Asks For

1. **Spin up the agentic team inside the LinkedIn vault** (reusing the Send repo structure).
2. **Add the in-vault LLM via OpenRouter** (the second agent type, using the existing tools APIs and JavaScript components).
3. **Define the agent roster** (architect, designer, developer, content, LinkedIn analyst, data scientist, ontologist, librarian).
4. **Adopt email-FS-Lite as the rules of engagement** (inter-agent messaging).
5. **Trigger manually now, scope automation later** (the trigger-on-vaults question).
6. **Build token management on OpenRouter** (prompt and tool control; keys as the commercialisation model).
7. **Create read-only instruction vaults via the website** (one vault serving the website and the sub-vault).

Estimated effort: moderate to large; the team structure, the tools components, OpenRouter, the inbox protocol, and read-only tokens all exist; the contribution is wiring the in-vault agent and the roster together.

## What This Does Not Try To Be

- **Not a scraper.** Strictly the exported data, within LinkedIn's terms.
- **Not real-time.** Some staleness is accepted; consistency is the goal.
- **Not automated yet.** Manual triggering first.
- **Not only the external Claude session.** The in-vault LLM is the new piece.

## Honest Risks

**Risk 1: terms-of-service compliance.** Mitigation: no scrapers; work from the dumps; accept staleness.

**Risk 2: token cost and control.** In-vault LLM usage costs tokens. Mitigation: tight prompt and tool control; OpenRouter key management (cross-ref: central-key-management).

**Risk 3: automation on vaults is unsolved.** Mitigation: manual first; treat triggering as a named next step.

**Risk 4: agent sprawl.** Many agents can become hard to maintain. Mitigation: each agent self-maintains; clear run conditions and outcomes.

**Risk 5: the in-vault agent is new ground.** Mitigation: it is the first real example; document it thoroughly in the master CLAUDE.md.
