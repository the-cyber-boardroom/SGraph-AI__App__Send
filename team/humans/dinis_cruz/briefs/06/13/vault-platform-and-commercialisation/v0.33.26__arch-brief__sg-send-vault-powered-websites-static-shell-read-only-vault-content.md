# Vault-Powered Websites: A Named Pattern For Vault-Managed Static Sites

**version** v0.33.26
**date** 13 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Arch brief

---

## What This Is

The formalisation and naming of a generic pattern the project lead now needs in several places: **a static HTML site, with a small JavaScript loader, a theme, and a layout, that renders content managed in read-only vaults, where the loader is given the vault server, the vault ID, and a read-only token, and resolves the content git-style through head, commit, tree, and files, with multiple content vaults each maintained by its own agent, built and shipped through a GitHub repository and a CI pipeline that pushes the static shell to S3, and a path to hosting it fully from vaults later.** This is already how the SGraph AI library works. The key insight the project lead stresses is that the encrypted content matters less than the workflow used to manage it. It composes SGit's object model, read-only tokens, and the agentic team (cross-ref: the v0.33.21 sgit-mapping-to-encrypted-spaces brief for head-commit-tree-files, the v0.33.26 linkedin-agentic-team and selling-llm-usage briefs for read-only tokens and static pages, and the v0.31.9 webify brief). New contributions: **the named pattern, the loader-and-resolution architecture, the multi-vault agent-maintained content model, and the proposed name.**

## The Name

The project lead asked for a name, since this is now needed in multiple places. A recommendation, with alternatives, for the project lead to choose:

| Option | Note |
|--------|------|
| SG/Sites (recommended) | Fits the SG family (SG/Send, SG/Vault, SG/Compute, SG/Sentinel); short and clear |
| SG/Pages | Evokes static pages; familiar to anyone who knows GitHub Pages |
| SG/Web | Broadest; perhaps too generic |
| Vault-Powered Sites | The descriptive term the project lead used; good as the explainer, long as a product name |

This brief uses vault-powered websites as the descriptive term and leaves the product name to the project lead; SG/Sites is the recommendation.

## The Core Primitive

The heart of the pattern, in the project lead's framing: **the site renders content from a vault, but the workflow to manage that content is what matters.**

The project lead: **"fundamentally these are websites managed and hosted by vault content, almost SG/Vault-powered websites. The website renders encrypted content, but the encrypted content matters less than the workflow used to manage it. You have a vault that has the content, you create a read-only vault key from it, and you give that read-only key to the HTML page."** So the primitive is: content lives in a vault, a read-only key is minted, and the page is handed that key. The value is the managed-content workflow (versioned, content-addressed, agent-maintained, ownable), not secrecy (see the note below).

## A Note On What The Encryption Is For

Worth stating plainly, because it changes how to think about it: **for a public site, the read-only token is effectively public, so this is about content management and integrity, not confidentiality.** The HTML page is handed the read-only token, so anyone viewing a public site can read the content; the encryption and the vault are not hiding the content from visitors. What they provide is the workflow: versioned, content-addressed, agent-maintained, portable, ownable content (which is exactly the project lead's point that the workflow matters more than the encryption). For a private site, the same pattern works with the read-only token gated behind access control. This is the sovereignty and ownability thesis applied to websites (cross-ref: the sovereignty-requires-open-source thesis), more than the zero-knowledge confidentiality story.

## The Static-Site Architecture

What the site is made of: **a static HTML shell, a JavaScript loader, a theme, and a layout.**

The project lead: **"it is a static HTML site, all of it static, with a bit of JavaScript, the loader, a theme, and a layout. The loader is given, in its code or deterministically, the server hosting the vault, the vault ID, and the vault read-only token, and a starting point."**

| Component | Role |
|-----------|------|
| Static HTML shell | The page; fully static |
| JavaScript loader | Fetches and renders the vault content |
| Theme | The visual style |
| Layout | The arrangement |
| Loader inputs | The vault server, the vault ID, the read-only token, and a starting object |

## The Content-Addressed Resolution

How the loader finds the content: **from the head, through the commit and the tree, to the files.**

The project lead: **"the loader is given a starting object, which is the head. From the head it determines everything else: the head file contains the link to the commit, the commit contains the link to the tree, and the tree lets you find the files and the objects you then go and get."** This is exactly SGit's content-addressed object model (cross-ref: the sgit-mapping-to-encrypted-spaces brief):

```
  head  ->  commit  ->  tree  ->  files / objects
   (the loader walks this chain to render the page)
```

So the loader resolves the head to a commit, the commit to a tree, and the tree to the files, then fetches and renders them. Because it is content-addressed, the same primitives that version a vault version the website.

## Multiple Content Vaults, Each Maintained By An Agent

How the SGraph AI library already works, and the powerful part: **the content is split across several vaults, each maintained by its own agent.**

The project lead: **"this is how the SGraph AI library already works, where the content is managed by three to four different vaults, each with a different agent managing it. That is very powerful, because the agents are now empowered to maintain different parts of the website."** So a single site is composed from multiple content vaults, and the agentic team maintains them in parallel (cross-ref: the linkedin-agentic-team brief, where the content and other agents are defined). This is the agentic team applied to a live website.

## The Build And CI Model

How it is shipped today: **a GitHub repository and a CI pipeline that pushes the static shell to S3, with code agents and content agents.**

The project lead: **"the way I do the SGraph AI website is a GitHub repo connected to a CI pipeline that pushes the files to S3. Two agents work on this: the agent for layout, design, and new features, the code agent, and the content agents that manage the content. The repo is used for the content, the design, everything, even to determine which vaults we use and what the root IDs are."**

| Element | Role |
|---------|------|
| GitHub repository | The static shell, the design, and the configuration (which vaults, which root IDs) |
| CI pipeline | Pushes the static files to S3 |
| Code agents | Layout, design, new features |
| Content agents | Manage the content in the vaults |

```
  GitHub repo (shell, theme, layout, config: vault IDs + root IDs)
        |  CI pipeline
        v
  Static files on S3  ->  served as the site
        |
        |  JS loader reads: server + vault ID + read-only token + head
        v
  Content vault(s)  ->  head -> commit -> tree -> files  ->  rendered
        ^
        |  maintained by per-vault agents (content agents)
```

## The Future And The Options

Where it goes, and the choices: **host fully from vaults later, use Docker for many sites, and add edge functions for SEO only if needed.**

The project lead: **"we could host all of it from a vault, although we still need to figure out the initial public pages, so for now we keep the GitHub repo, which is fine and can host some static assets and infrastructure. From a Docker point of view we want this for multiple workflows and websites. For SEO we could use Lambda at edge, but let us see if that is actually needed."**

| Option | Status |
|--------|--------|
| Full vault hosting | Future; the initial public pages need solving first |
| GitHub repo plus CI | The model for now; also hosts static assets |
| Docker for many sites | Wanted; the pattern is meant to be reused across websites |
| Lambda at edge for SEO | Only if needed; client-side rendering may otherwise hurt SEO |

## What This Asks For

1. **Name the pattern** (recommendation: SG/Sites).
2. **Capture the architecture so sites can be set up quickly** (the static shell, the loader, the resolution chain, the content vaults).
3. **Standardise the loader** (given server, vault ID, read-only token, head; walks head to commit to tree to files).
4. **Use multiple content vaults with per-vault agents** (as the library does).
5. **Keep the GitHub plus CI build for now** (pushing to S3; code and content agents).
6. **Make it reusable across sites with Docker** (the multi-site goal).
7. **Defer full-vault hosting and edge SEO** (until the public-pages and SEO needs are clear).

Estimated effort: low to moderate to formalise, since the SGraph AI library already runs this way; the work is naming it, documenting it, and templating it for fast reuse.

## What This Does Not Try To Be

- **Not confidential for public sites.** The read-only token is effectively public; the value is the workflow.
- **Not dynamic server-rendered.** It is static plus a client-side loader.
- **Not free of GitHub for now.** The repo and CI remain, by choice.
- **Not a single-vault site.** Content is split across vaults, agent-maintained.

## Honest Risks

**Risk 1: client-side rendering can hurt SEO.** Mitigation: Lambda at edge if needed; evaluate before building it.

**Risk 2: the initial public pages need bootstrapping.** Mitigation: keep the GitHub plus CI model until full-vault hosting solves the public-page bootstrap.

**Risk 3: confusion about confidentiality.** Mitigation: be explicit that public sites expose the read-only token; the encryption is for the workflow, not secrecy.

**Risk 4: multi-vault and multi-agent coordination.** Mitigation: clear per-vault ownership by agents, as the library already does.

**Risk 5: GitHub dependency.** Mitigation: acceptable for now; full-vault hosting is the path to remove it (which also strengthens the sovereignty story; cross-ref: the sovereignty thesis).
