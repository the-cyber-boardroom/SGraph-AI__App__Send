# Selling LLM Usage Through Vaults: The OpenRouter-Key Commercialisation Workflow

**version** v0.33.26
**date** 13 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Product, Strategy, @Dev
**type** Dev brief

## What This Is

The concrete commercialisation workflow that has been referenced as the model: **sell LLM usage by provisioning OpenRouter keys with a small markup through vaults, kick-started by a simple, genuinely useful tool (Audio Transcribe), where a read-only vault shares a budgeted, rotating OpenRouter key with selected users, shows them the cost and remaining budget, and eventually lets them buy more credits with Stripe, all client-side, with a separate admin vault for managing keys and visualising traffic and users, hosted as static pages on the SGraph website.** It is the concrete instance of the commercialisation model named elsewhere (cross-ref: the v0.33.26 linkedin-agentic-team-vault-agents commercialisation note, the v0.32.7 central-key-management-openrouter-keys brief, and the v0.33.26 open-source-success-paradox and sovereignty theses, which call for value-driven rather than rent-driven models). New contributions: **the sell-usage-via-vault workflow, the Audio Transcribe kick-start, the budgeted rotating-key sharing model, the admin vault, and static-page hosting.**

## The Model: Sell Usage With A Markup, Client-Side

The commercial idea, stated plainly: **provision and sell LLM usage with a small markup, entirely client-side.**

The project lead: **"this is the idea of getting users into a workflow where we are basically selling OpenRouter keys. It is a valid and profitable use case, because we do a little markup on it, and all of this is client-side. Like everything, we just need to ship it and understand it, find a couple of valid use cases, and connect the dots."** So the model is a usage markup on OpenRouter, which is value-driven (the user pays for what they use, with no lock-in) rather than rent-extracting, consistent with the open-source commercialisation thesis (cross-ref: the open-source-success-paradox brief).

## The Kick-Start Tool: Audio Transcribe

The first concrete tool, chosen because it is simple and genuinely useful: **Audio Transcribe.**

The project lead: **"I created a tool called Audio Transcribe, because there was not a simple way to do it. It records audio and processes the OPUS and OGG files you get from WhatsApp, which were not easy to transcribe or open, converts the audio format, and uses a selection of audio models from OpenRouter to do the transcription. I tried it and it worked quite well."**

| Aspect | Detail |
|--------|--------|
| What it does | Records audio, and ingests WhatsApp OPUS and OGG voice notes |
| The hard part it solves | Those formats were not easy to transcribe; it converts the format first |
| The models | A selection of OpenRouter audio models |
| Where it runs | Client-side |
| Status | Built and tested; worked well |

This is the template: a simple tool that does something people want, that consumes LLM usage.

## The First Milestone: Do We Have Something People Will Pay For

The honest first test: **do we have a tool that drives usage people actually want and will pay for.**

The project lead: **"the brutal thing is, do we have tools that drive usage people want. That is always the question. The first milestone is the audio workflows, the infographic workflows, the chat LLMs, even what you do once you get a transcript. We can think about those sequences of events and mini-tools that help people and drive usage, which drives consumption, which drives vaults, because then we put the data they create in a vault. It comes down to creating solutions and assets that people want to put in a vault, and until we have that, we do not have a workflow."**

| Candidate Workflow | Note |
|--------------------|------|
| Audio transcription | The kick-start tool |
| Infographic generation | An existing workflow (cross-ref: the storytelling-infographics work) |
| Chat with LLMs | Direct usage |
| Post-transcript workflows | What you do once you have a transcript |

The chain is: useful tool, drives usage, drives consumption (and revenue via the markup), drives data that lands in a vault.

## The Vault Mechanism

How the usage is provisioned: **a read-only vault, shared with selected users, holding a budgeted OpenRouter key, with the cost and remaining budget shown.**

The project lead: **"we use a vault for this. We already have a way to put secrets in a vault, the same technique we use for the uploads. We create a vault we can share with selected users, and they need the read-only key, because we do not want them to write to the vault. The vault contains a budget, even a daily or weekly budget, say two or three pounds, that can be used for transcripts, and we show the value, how much budget is available, how much you have spent, and how much it costs per transcript."**

| Element | Detail |
|---------|--------|
| Read-only access | Users get the read-only key; they cannot write the vault |
| The budgeted key | The vault holds an OpenRouter key with a daily or weekly budget |
| Cost visibility | Budget available, amount spent, cost per transcript |
| Secrets technique | The existing put-secrets-in-a-vault method (cross-ref: the central-key-management brief) |

## The Two Access Modes

A design choice worth exploring: **access the vault directly, or access it through the tools, and it could even be a static page.**

The project lead: **"the user gets a link to a read-only vault. This could even be a static page on a website. It is not a bad idea to explore the two modes, where you can access the vault directly, or access it via the tools, which is a more integrated workflow, using the vault to share the OpenRouter key."** So the same vault can be reached directly or through the tool UI, and can be served as a static page (cross-ref: the linkedin-agentic-team read-only-token-from-website flow).

## The Key-Sharing Mechanism

The crux, and the part that needs pinning down: **share a read-only decryption capability that unlocks the active, rotating OpenRouter key, so the user can spend the budget without ever holding write access or a long-lived secret.**

The project lead: **"we share a key with them that decrypts the key that is active for that day, so they can see how many credits they have and use a transcript. We need a separate admin vault that I can use to manage the keys and visualise the traffic and the users."** The intent is clear: the vault holds the OpenRouter key encrypted, the user is given a read-only capability that decrypts the currently-active (for example daily) key, and the key rotates so exposure is bounded. The precise public-and-private-key mechanics (which key wraps which, and how rotation is enforced) were described loosely and should be pinned down (see the open question). The security rationale is sound: a rotating daily key plus a capped daily budget bounds the blast radius even though the key is used client-side.

## The End-To-End Tool Flow

What the user does: **drop audio or video, transcribe it with a model, then see, copy, and download the result.**

The project lead: **"they can drop a voice note, or a video, because we already have a video splitter tool, or some audio, do the transcript, call one of the models, see the transcript, copy and paste it, and download it. That is the functionality we already have on the tool, we just need to wrap it on a vault and share that vault."** So the tool already exists; the work is wrapping it in the vault and sharing the vault (cross-ref: the video-splitter tool and the tools components).

```
  Read-only vault (budgeted, rotating OpenRouter key)
        |  user opens via link (direct, or via the tool, or a static page)
        v
  User drops audio or video  ->  format converted  ->  OpenRouter model
        |
        v
  Transcript shown  ->  copy / download
        |
        +--> usage and cost metered against the budget
        +--> activity visible to the admin vault
```

## The Admin Vault

The control side: **a separate admin vault to manage the keys and see the traffic and users.**

The admin vault is where the project lead manages the OpenRouter keys, sets and rotates budgets, and visualises traffic and users (cross-ref: the shipping-vault monitor vault and the end-to-end-milestone admin vault). It is the operator counterpart to the read-only user vaults.

## The Buy Workflow (Later)

The next step, deferred: **let users buy more credits with Stripe.**

The project lead: **"eventually you should be able to buy tokens or credits, for example using Stripe, which then get provisioned and used by the user, but let us take this a step at a time."** So a Stripe buy-credits flow that tops up the user's budget is the planned extension, after the basic provisioning workflow is proven.

## Hosting: Static Pages On The SGraph Website

Where it lives, and the key idea: **host these as static pages on the SGraph website.**

The project lead: **"the vault should go on the SGraph website, because we already have all those workflows done. The power of this is that we can now host these static pages on our SGraph website, and that is the key idea."** So the deliverable is served from sgraph.ai, reusing the existing website and read-only-token workflows.

## What This Asks For

1. **Wrap Audio Transcribe in a read-only vault and share it** (the kick-start).
2. **Provision a budgeted, rotating OpenRouter key in the vault** (daily or weekly budget; cost visibility).
3. **Pin down the key-sharing mechanism** (the read-only decryption capability and rotation).
4. **Build the admin vault** (manage keys; visualise traffic and users).
5. **Support the two access modes** (direct, via the tool, or as a static page).
6. **Host it on the SGraph website** (static pages).
7. **Plan the Stripe buy-credits flow** (later).

Estimated effort: moderate; the tool, the secrets-in-vault technique, read-only vaults, and the website workflows exist; the contribution is wiring the budgeted key, the metering and cost display, and the admin vault.

## What This Does Not Try To Be

- **Not server-side.** Usage is client-side; the markup is the model.
- **Not write-access for users.** Read-only vaults only.
- **Not the buy flow yet.** Stripe comes after the provisioning workflow is proven.
- **Not lock-in.** Pay for usage; value-driven, not rent (cross-ref: the open-source-success-paradox brief).

## Honest Risks

**Risk 1: the key is used client-side, so the user can see the active key.** Mitigation: rotate the key (daily) and cap the budget, bounding the blast radius; pin down the rotation mechanism.

**Risk 2: the key-sharing crypto is not yet precise.** Mitigation: pin down which key wraps which and how rotation is enforced (the open question).

**Risk 3: budget abuse or runaway spend.** Mitigation: daily or weekly caps; cost visibility; admin-vault monitoring.

**Risk 4: the do-people-want-it question is unproven.** Mitigation: the kick-start with real users and feedback is exactly to test this.

**Risk 5: markup economics.** Mitigation: a small markup on metered usage; validate with real consumption.
