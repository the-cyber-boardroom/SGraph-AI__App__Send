# The Shipping Provider Vault: Signed-Message Updates, A Product UI, Analytics, And A CRM

## What This Is

A milestone and the next MVP for the provider-and-recipient vault product (the use case in mind, rendered neutrally as a provider creating vaults for the people it serves, around a customer scoring tool): **the first MVP works (a recipient vault created from a provider vault, two chat systems, and vault updates delivered as PKI-signed messages), and the next step is a complete, shippable product vault with professional navigation, a clinician and admin console, analytics, resumable multi-visit sessions, multi-vault maintenance, a base CRM, and deployment to the customer's AWS account.** It builds directly on the release-and-event-capture workflow, the append capability, and central key management (cross-ref: the v0.33.2 vault-release-manifest, v0.33.2 vault-append-capability, and v0.32.7 central-key-management briefs). New contributions: **the signed-message update mechanism, the shippable product UI, the clinician and admin console, IP and analytics capture, resumable sessions, multi-vault maintenance, a base CRM, and the AWS-account deployment.**

## The Milestone: A Working MVP, With Signed-Message Updates

What just worked, and it is significant: **the first MVP successfully created a recipient vault from a provider vault, ran two chat systems, and, most notably, updated a vault through a PKI-signed message that only the parent admin key can send.**

The project lead: **"we just had the first MVP working. We were able to create the recipient vault from the provider vault, it had the workflow, it used the new messaging system with two chat systems, a normal chat and a send-reviews-back-to-the-user system, and that worked well. We also have a first working MVP of updating the vault using a message. This is a good example of leveraging our technology, security, and PKI, because we can now send a message to a vault that is signed with the parent admin key, and that is the only way to update it."**

| Milestone Piece | What It Demonstrates |
|-----------------|----------------------|
| Recipient vault created from the provider vault | Vault-from-vault creation works (cross-ref: central key management) |
| Two chat systems | Normal chat, plus send-reviews-back-to-the-user |
| Signed-message vault update | A message signed with the parent admin key updates the vault |
| Only the signed key can update | The signed message is the only update path |

So the signed-message update is the headline: a vault is updated by sending it a message signed with the parent admin key, and that is the only way to update it. This is PKI-controlled mutation (cross-ref: the v0.33.2 vault-append-capability and v0.32.4 PKI-foundations briefs): updates are authorised by signature, accountable to the signing key, and impossible without it. It is a clean realisation of the platform's security model.

## The Next MVP: A Shippable Product Vault

The next phase, and the goal: **create a complete new vault that is the one that ships, without the experimental debug parameters, looking and navigating like a proper product.**

The project lead: **"now I want to create the brief for a complete new vault, the one that is actually going to ship, because that is the one that does not have all the experimental debug parameters. It is going to look like a proper product, with proper navigation."** So the next MVP is a clean, shippable build: the experimental and debug parameters are removed, and it presents as a real product. The features below define it.

## A Professional UI With Navigation

The first requirement: **a professional UI with side and top navigation, a single versioned app rather than multiple app entry points, that feels like a full application.**

The project lead: **"we need a UI that looks professional, with navigation, maybe side navigation and top navigation. I should not have to open multiple app entry points across pages. I should have one that gets updated and versioned, that feels like a full-blown app, and lets me navigate to do multiple things, from communication to viewing results to talking to the recipient, all sorts of interfaces."**

| UI Element | Purpose |
|------------|---------|
| Side and top navigation | Move around a full app |
| One versioned app entry point | Not multiple app indexes across pages |
| Communication view | Chat and messaging |
| Results view | Viewing the captured results |
| Recipient chat | Talking to the recipient |

So the shippable vault is a single, versioned application with proper navigation, replacing the multiple app entry points of the MVP, and giving one coherent interface for communication, results, and recipient chat.

## The Clinician And Admin Console

Restore an existing piece: **bring back the clinician and admin console pages that were in the earlier MVP.**

The project lead: **"there was already a page on the MVP, given to me by the provider, that contained some of the pages for the admin site, the clinician site. We should put this back."** So the shippable vault includes the clinician and admin console (the provider-side pages from the earlier MVP), restored and integrated into the new navigation. This is the provider's side of the product (cross-ref: the release-and-event-capture brief's provider workflow).

## IP And Analytics Capture

A visibility feature, enable or disable: **capture the IP address of viewers and present a Google-Analytics-style view of who is using the product and how.**

The project lead: **"I want to capture the IP address of who is viewing this and map it out, to get a better sense of who is using it and how. It would be cool to have a Google-Analytics-style page showing who is coming, where they come from, and what they are using. We can choose to enable or disable it."** So the product can capture viewer IP addresses and present analytics (who, where from, what they use), in a Google-Analytics-style page, toggleable on or off. This extends the event-capture work (cross-ref: the release-and-event-capture brief's full event capture), and it is a real privacy-sensitive feature that must be handled carefully (see risks), especially given the sensitive domain.

## Resumable, Multi-Visit Sessions

A workflow improvement: **multiple visits retain the data, so a user can see what they provided and continue, stop, and start.**

The project lead: **"we need to improve the user workflow: make sure multiple visits retain the data, that they can see the data they provided, and they can continue, stop, and start."** So the product supports resumable sessions: a returning user sees their previous data and can pick up where they left off, rather than starting over. This pairs with the full event capture (the data is already captured per event) and matters for any multi-step workflow.

## Multi-Vault Maintenance And A Base CRM

Two operational additions: **maintain the multiple vaults (test and customer), and add a base CRM for customer contact and outreach state.**

The project lead: **"we need the maintenance of the multiple vaults, test vaults and customer vaults, and we need to add a base CRM, where we put customer email addresses and state, have we reached them or not, contact messages, emails sent, notes, and so on."**

| Addition | What It Holds |
|----------|---------------|
| Multi-vault maintenance | Test vaults and customer vaults, managed together |
| Base CRM | Customer email addresses, outreach state, contact messages, emails sent, notes |

So the product gains operational tooling: maintenance across the test and customer vaults (cross-ref: the release-manifest brief's Uber vault and supported-releases), and a base CRM tracking customers and outreach (reached or not, messages, notes). The CRM is lightweight but enough to run the go-to-market.

## Deployment: The Customer's AWS Account, A Lambda, And The Domain

How it ships: **deploy to the customer's AWS account so the data is already there, map it to the domain, and in principle it is just a Lambda function for the API.**

The project lead: **"we need to deploy this to the customer's AWS account, so all the data would already be there. I can map this to my domain name, and in principle it should just be a case of deploying a Lambda function, which is the API, and after that everything should be the same."** So deployment puts the product in the customer's own AWS account (their data stays in their account, consistent with the run-everywhere and sovereignty principles; cross-ref: the access-not-security and blast-radius briefs), mapped to a domain, with the API as a Lambda function. The rest of the stack stays the same, so deployment is principally the Lambda plus the account and domain configuration.

The MVP is the shippable product vault deployed to the customer's AWS account, with professional navigation, the clinician console, resumable sessions, analytics, and a base CRM, updated only by signed messages.

## What This Does Not Try To Be

- **Not the experimental MVP.** The shippable product has no debug parameters and proper navigation.
- **Not updatable without a signature.** Updates come only via a parent-admin-key-signed message.
- **Not multiple app entry points.** One versioned app with navigation.
- **Not for confidential data without care.** Analytics and IP capture are privacy-sensitive and toggleable.
- **Not hosted away from the customer.** Deployed to the customer's own AWS account.

## Honest Risks

**Risk 1: IP and analytics capture is privacy-sensitive.** Capturing viewer IPs, especially in a sensitive domain, carries real privacy weight. Mitigation: make it enable or disable; capture only what is needed; combine with the do-not-enter-confidential-data posture (cross-ref: the release-and-event-capture brief); review before any confidential use.

**Risk 2: Signed-message updates depend on key handling.** The parent admin key is powerful. Mitigation: PKI signing is the control; scope and protect the admin key; provenance on updates (cross-ref: the PKI-foundations brief).

**Risk 3: The CRM holds personal contact data.** Emails, state, and notes are personal data. Mitigation: minimal data; the customer's own AWS account; handle per the data posture.

**Risk 4: Shippable means production expectations.** A product raises the bar over an MVP. Mitigation: build on the working milestone; the release-manifest quality gate (cross-ref: that brief); ship deliberately.

**Risk 5: Deployment to a customer account adds variables.** Their account, their domain, the Lambda. Mitigation: the data-stays-there benefit; keep the rest of the stack the same; the Lambda is the main moving part.
