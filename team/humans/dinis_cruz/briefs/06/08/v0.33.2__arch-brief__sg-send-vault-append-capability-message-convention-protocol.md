# The Vault Append Capability: A Message Convention And The Three-Moment Processing Model

**version** v0.33.2
**date** 8 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), SG API team, Vault team, @Dev
**type** Arch brief

## What This Is

The next step after the working vault-to-vault comms MVP: **define a convention for the types of messages and events that vaults send each other over the append capability (the renamed inbox), and the three-moment model for collecting, classifying, and handling them.** The MVP succeeded: two vaults exchanged PKI-encrypted messages both ways. Now the task is to map the message types and the protocol, decide how much lives in the vault versus in vault apps, and build an MVP. It builds directly on the inbox feature and the comms milestone (cross-ref: the v0.32.7 vault-inbox brief and the vault-to-vault-comms reference guide), and reuses the Email-FS thinking (cross-ref: the v0.31.12 FAQ-protocol-harness-or-workflow brief). New contributions: **the rename to append capability, the append box decoupled from the vault, the message-type convention, the three-moment processing model, and the bake-in-versus-app question.**

## The Milestone: Two Vaults Communicating Via PKI

What was just achieved, and it worked well: **a working MVP where two vaults exchange encrypted messages both ways using PKI.**

The project lead: **"we just did a really cool MVP where, with modifications to the vault web and a couple of vaults, two vaults communicate through encrypted messages using PKI. Each vault has a public and private key, we gave each one's public key to the other, and then we used our SG API to send messages. We successfully sent the equivalent of a text message from one vault to another, and vice versa, and that worked really well."** So the foundation is proven (cross-ref: the vault-to-vault-comms reference guide): each vault has a keypair, the public keys are exchanged, and PKI-sealed messages flow both ways through the SG API. The equivalent of a text message works in both directions. This brief is about what to build on top of that.

## The Rename: Inbox Becomes The Append Capability

A terminology shift that reflects what it really is: **what was called the inbox is being renamed the append capability, with an append key that grants the ability to send messages from one vault to another.**

The project lead: **"it is called inbox, but we are going to rename it to append capability, the ability to send messages to each other. We gave it the PKI key and the append key, which is the ability to have messages sent from one vault to the other."** So the inbox (cross-ref: the vault-inbox brief) is more accurately an append capability: the right to append messages to another vault's stream, gated by an append key (cross-ref: the v0.31.12 vault-to-vault-comms-append-token-pki brief's append token). The rename matters because it frames the mechanism correctly: it is an append channel, not a mailbox, and the next sections build on that framing.

## The Append Box Is Decoupled From The Vault

A key architectural property: **the append box is independent of the vault itself, a stream of messages and signals added from one vault to another.**

The project lead: **"we have decoupled what we can call the inbox or the append box, and it is independent from the vault itself. What it is is a whole bunch of messages or signals added from one to the other."** So the append box is not part of the vault's version-controlled content; it is a separate, decoupled stream of inbound messages and signals (cross-ref: the vault-inbox brief's outside-version-control point and the deterministic-value-indexes brief's separate-layer model). This decoupling is what makes the convention a layer on top, and it is why the bake-in-versus-app question (below) is open.

## The Next Step: A Convention For Message Types

What this brief is really for: **start defining the types of messages and events that can be sent between vaults, and the protocol for where they are placed.**

The project lead: **"we need to start mapping the multiple types of events, the multiple types of data that can be sent from one vault to the other, and the protocol for where they are going to be placed. The logic is we need something like text messages, very simple messages, send and receive."**

| Message Type | Handling |
|--------------|----------|
| Text message | Simple send and receive (the starting point) |
| File | Routed by file type |
| Email | A file type routed to the email workflow |
| Image | A file type routed to where images go |
| JSON | Structured data routed to its handler (the structured-data use case) |

So the convention defines the message types (starting with simple text messages, then files of various kinds: email, image, JSON) and the protocol for where each type is placed. The structured-data (JSON) case is exactly the use case the team has in mind for a provider-to-end-user workflow, rendered here neutrally. Defining the types and their placement is the core of the convention.

## The Three-Moment Processing Model

The processing model, and it has three distinct moments: **collect new messages, classify them by type, then handle each according to its type.**

The project lead: **"there are three moments. There is the moment where you go and see if there is a new message and you collect them. Then there is the moment where you process the message and see: is this a text message, is this a file, what type of file, an email, an image, a JSON file? Something needs to go to a different place. And then there is the processing of that, what you do with it."**

| Moment | What Happens |
|--------|--------------|
| 1. Collect | The vault checks for new commits and messages and retrieves them |
| 2. Classify | Determine the type (text, file, email, image, JSON) and where it should go |
| 3. Handle | Process it according to its type; do what the type requires |

So message handling is cleanly separated into three moments: collection (check for and retrieve new messages), classification (determine the type and destination), and handling (act on it). Separating them keeps the design clean: the collection mechanism is generic, the classification is the convention, and the handling is per-type. This maps directly onto the working comms (which already does collection) plus the new convention (classification) plus the handlers (handling).

## Reuse The Email-FS Workflow

Where the handling can come from: **the Email-FS workflow is a strong fit for the handling stage, and a lot of it can be reused.**

The project lead: **"this is where our Email-FS workflow is quite interesting, because we could literally reuse a lot of it."** So the third moment (handling) does not start from scratch: the Email-FS workflow (cross-ref: the FAQ-protocol-harness-or-workflow brief's Email-FS-lite case study) already models how typed messages and files are routed and handled, and much of it can be reused for handling the message types defined here. This keeps the build small: the convention and classification are the new work, and the handling reuses Email-FS.

## The Open Question: Bake Into The Vault, Or Vault Apps

A deliberately open design question, echoing an earlier one: **should this logic be baked into the vault, or added on top as vault apps? Experiment first, and maybe eventually move some into the vault.**

The project lead: **"it is an interesting question whether this is logic we bake into the vault or logic we add on top of it. I think we need to experiment and maybe eventually add it to the vault. Let's map it out, create a convention, create an MVP, and then see how much of it we push to the vault versus just vault apps."** So the convention and processing can live either in the vault itself or on top as vault apps, and the decision is deliberately deferred. This is the same protocol-versus-workflow, in-the-vault-versus-on-top question raised before (cross-ref: the FAQ-protocol-harness-or-workflow brief): start on top (vault apps), experiment, and migrate into the vault only what proves it belongs there. The plan is explicit: map it out, create the convention, build the MVP, then decide the split.

## What This Asks For

1. **Adopt the append-capability framing** (the inbox is an append channel; the append key grants the right to append; rename accordingly).
2. **Treat the append box as decoupled** (a separate stream of messages and signals, independent of the vault content).
3. **Define the message-type convention** (text first, then files: email, image, JSON; the protocol for where each is placed).
4. **Implement the three-moment model** (collect, classify, handle, kept as distinct stages).
5. **Reuse the Email-FS workflow for handling** (the per-type handlers; do not rebuild them).
6. **Keep the bake-in-versus-app question open** (start as vault apps; experiment; migrate into the vault what belongs there).
7. **Map, conventionalise, MVP, then decide the split** (the explicit plan).

Estimated effort: moderate; the comms milestone, the append mechanism, and the Email-FS workflow exist; the contribution is the message-type convention and the three-moment processing. The MVP is two vaults exchanging typed messages (text, then a JSON and a file), with collection, classification, and Email-FS-based handling, built first as vault apps.

## What This Does Not Try To Be

- **Not a mailbox.** An append capability; a decoupled stream of messages and signals.
- **Not part of the vault content.** The append box is independent of the version-controlled vault.
- **Not text-only.** Text first, then files: email, image, JSON, by convention.
- **Not one big handler.** Three distinct moments: collect, classify, handle.
- **Not committed to the vault or to apps.** The split is deferred; experiment first.

## Honest Risks

**Risk 1: The convention could sprawl.** Too many message types early. Mitigation: start with text, add files and JSON deliberately; extend the convention as needed.

**Risk 2: Classification and handling can entangle.** Mixing the three moments creates a mess. Mitigation: keep collect, classify, and handle distinct; generic collection, conventional classification, per-type handling.

**Risk 3: The bake-in decision made too early.** Committing to the vault or to apps prematurely. Mitigation: start as vault apps; experiment; migrate only what proves it belongs in the vault.

**Risk 4: Reusing Email-FS may not fit every type.** Not all handling matches Email-FS. Mitigation: reuse where it fits; add per-type handlers where it does not.

**Risk 5: The append box is decoupled and outside version control.** It needs its own consistency. Mitigation: the comms milestone already handles collection; treat the append box as the separate layer it is (cross-ref: the vault-inbox brief).
