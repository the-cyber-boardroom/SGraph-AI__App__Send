# Rethinking Tests: Define Them By Properties, Not Unit Or Integration, And Treat Them As The Asset

**version** v0.33.2
**date** 8 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, Strategy, @Dev
**type** Strategy brief

---

## What This Is

The promised document on testing, prompted by the question of where tests run from inside a vault: **stop classifying tests as unit, integration, or end-to-end, and instead define every test by its properties (where it runs, who runs it, what resources and data it uses, how destructive and how realistic, how fast), treat tests as more important than the code, make tests accountable, and align coverage with the attack surface.** It delivers the concept parked in the release-manifest brief (cross-ref: the v0.33.2 vault-release-manifest brief) and extends the coding-as-abstraction thinking (cross-ref: the v0.32.4 coding-as-abstraction-layers brief). New contributions: **rejecting the unit-or-integration taxonomy, ephemerality as the real variable, tests-defined-by-properties, tests-over-code in the LLM era, mutation testing for blind spots, test accountability, bugs-and-vulnerabilities-as-features, and coverage aligned with the attack surface.**

## Against The Unit-Or-Integration Taxonomy

The starting objection: **the unit, integration, and end-to-end labels are unhelpful, because every test is a test of a unit, regardless of the unit's size.**

The project lead: **"I never liked the idea of a unit test, because most people imply you are testing a very small piece of code. But for me every one of those is a unit test, because everything is a unit, it just does not matter how big the unit is."** So the word unit describes what you are testing, not how small it is: a function, a module, a whole application are all units. Calling one test a unit test and another an integration test classifies them by size, which is the wrong axis. The useful distinctions are the properties below.

## Everyone Tests All The Time; The Variable Is Ephemerality

A reframe that parallels the coding-as-abstraction argument: **testing happens constantly, by everyone, and the real variable is how ephemeral the test is.**

The project lead: **"people are doing tests all the time, including users, developers, QA, managers. It is just a question of how ephemeral. How much do we capture the test, how long, how fast can we spin up a test environment to run it, how much mocking are we doing, and how much reality?"** So just as everyone programs but mostly ephemerally (cross-ref: the coding-as-abstraction-layers brief), everyone tests but mostly ephemerally: a user clicking through a flow is testing; the difference is whether the test is captured, repeatable, and how fast its environment spins up. Reality matters too, and a lot of the real effort goes into the test harness and environment.

## Redefine Tests By Their Properties

The core proposal: **define a test by a combination of properties, where it runs, who runs it, what it can access, what data it uses, how destructive and how realistic it is, and how fast, plus qualitative metrics.**

The project lead: **"we should not be defining the term unit or integration. We should define where the test is running, who is running it, what resources it has access to, is it synthetic data, lab data, or production data, how destructive are the tests, or how close to the real world, and how fast. Then there are qualitative and performance metrics: how fast can you spin up the environment, how realistic it is, how much data represents the real data, and how effective it is."**

| Property | The Question |
|----------|--------------|
| Where it runs | Inside the vault, the parent, the browser, elsewhere |
| Who runs it | The developer, QA, a user, an agent |
| Resources | What the test can access |
| Data | Synthetic, lab, or production |
| Destructiveness | How destructive, or how close to the real world |
| Speed | How fast it runs |
| Spin-up | How fast the environment comes up |
| Realism | How well the data and environment represent reality |
| Effectiveness | How much it actually catches |

So a test is described by this property set rather than a category label. This answers the where-do-tests-run-from question from the release-manifest brief directly: the location is one property among several, and the meaningful classification is the combination.

## Tests Are More Important Than Code

A long-held view, now acute with LLMs: **tests matter more than code, because in the LLM era code is disposable and can be rewritten freely as long as the tests pass.**

The project lead: **"tests are more important than code, something I have always said. With LLMs, code becomes more disposable, we should be rewriting it all the time, as long as the tests pass. If you refactor and the tests pass, go live. If something broke and no test caught it, your test is bad, so go fix your tests."** So if code can be regenerated cheaply (cross-ref: the coding-as-abstraction-layers and open-source-not-free briefs), the durable asset is the test suite: it defines correct behaviour, and code is just one passing implementation of it. A break that no test catches is a defect in the tests, not just the code.

And mutation testing is the tool for the blind spots. The project lead: **"I like mutation tests, which detect when stuff changes that you should pick up. If it is possible to change a line of code that has impact on the system and no test fails, you have a blind spot. That is why mutation is powerful."** So mutation testing (changing the code and checking that some test fails) finds the blind spots: any impactful change that breaks no test reveals untested behaviour.

## Test Accountability

A missing, measurable property: **make tests accountable, because every bug not caught by a test is a measurable, binary gap in the test environment.**

The project lead: **"we should be making the tests accountable. Every bug that happens that was not captured by a test shows a gap in the test environment, and that is measurable, it is binary."** So test quality is measurable: each bug (and vulnerability) that reaches reality without a test having caught it is, by definition, a gap in the tests, and that is a binary, countable signal. This turns test quality from a feeling into a metric: how many escapes, where, and what gap each one exposes.

## Bugs And Vulnerabilities Are Features Until Fixed

A sharp principle: **write passing tests for bugs and vulnerabilities, because until they are fixed they are features, behaviours that exist.**

The project lead: **"your tests should include passing tests for the bugs and passing tests for the vulnerabilities, because until they are fixed they are features. They are behaviours that exist. Whether you want to address that feature is a different conversation."** So a known bug or vulnerability should have a test that passes against the current (broken) behaviour, documenting that the behaviour exists. This makes the real state of the system explicit and measurable, and separates the description (this behaviour exists) from the decision (whether and when to change it). It also means a fix is visible as a test that flips.

## Coverage Aligned With The Attack Surface

A critical refinement to code coverage: **coverage should be measured against the variations a use case can take and aligned with the attack surface, and code that is never invoked should be deleted, not tested.**

The project lead: **"measure code coverage: how much the test covers, and more importantly, of the use case the test triggers, how much coverage of all the possible variations that could occur. And the coverage should be aligned with the attack surface, the exposed methods. There is no point having unit tests for code that is never invoked. In fact, we should delete that code, because if it is never invoked it should not be there."**

| Coverage Question | Why It Matters |
|-------------------|----------------|
| How much of the use case's variations are covered? | Coverage of paths, not just lines |
| Is coverage aligned with the attack surface? | Test what is exposed and reachable |
| Is there code that is never invoked? | Delete it; do not test dead code |

So coverage is not a single line-percentage; it is how many of the variations a use case can take are exercised, and it should track the attack surface and exposed methods (cross-ref: the SG/Sentinel and blast-radius security work). Testing dead code is wasted effort; never-invoked code should be removed entirely.

## Tests Are What You Keep

The philosophy, with two memorable framings: **if you could save only the code or the tests, you keep the tests, and in a code review you start with the tests, because the tests tell you the intent.**

The project lead: **"tests are the most important thing to keep. If there were two hard drives and you could save only one, one with all the code and one with all the tests, which do you take? And when I did code reviews as a security reviewer, I always started with the tests if they existed, because the tests told me the intent, and then I expected the code to match what I saw in the tests, for good or bad."** So the tests encode intent and correct behaviour; the code is a replaceable implementation of them. Keeping the tests lets you regenerate the code; keeping only the code loses the intent. And reviewing the tests first reveals what the system is supposed to do, against which the code can be judged.

## Naming

An open naming question, with a steer: **these should not be called unit tests; a name like execution test may fit better, because the classification is the properties, not the size.**

The project lead: **"what should we call this? Maybe execution test, some name. They are definitely not unit, because for me the unit is what you are testing, big or small. It is about all the other properties."** So the taxonomy should be replaced by names that reflect the properties (where, who, data, realism, speed), not the size of the unit. Execution test is one candidate; the point is that the name should not be unit or integration.

## What This Asks For

1. **Drop the unit-or-integration taxonomy** (the unit is what you test, any size; classify by properties).
2. **Treat testing as constant and ephemeral** (everyone tests; the variable is capture, repeatability, and spin-up speed).
3. **Define tests by their properties** (where, who, resources, data type, destructiveness, realism, speed; plus spin-up, realism, effectiveness metrics).
4. **Treat tests as the asset, not the code** (disposable code; rewrite freely if tests pass; a missed break is a test defect).
5. **Use mutation testing** (find blind spots: impactful changes that break no test).
6. **Make tests accountable** (every uncaught bug is a measurable, binary test gap).
7. **Write passing tests for bugs and vulnerabilities** (they are features until fixed; document and measure them).
8. **Align coverage with the attack surface** (cover the variations; track exposed methods; delete never-invoked code).
9. **Keep the tests** (they are what you save; start reviews with them; they encode intent).
10. **Rename** (not unit; a property-based name such as execution test).
11. **Write and visualise the document** (this brief; a visualisation of the property space).

Estimated effort: a concept and methodology brief, not a build; it informs how the team tests, especially the in-vault and release-manifest tests. The contribution is the property-based definition, test accountability, bugs-as-features, and attack-surface-aligned coverage.

## What This Does Not Try To Be

- **Not the unit/integration taxonomy.** Classification by properties, not size.
- **Not code-first.** Tests are the asset; code is a replaceable implementation.
- **Not line-percentage coverage.** Coverage of variations, aligned with the attack surface.
- **Not silent about known bugs.** Bugs and vulnerabilities get passing tests until fixed.
- **Not a test for dead code.** Never-invoked code is deleted, not tested.

## Honest Risks

**Risk 1: A property-based scheme is less familiar.** Teams know unit and integration. Mitigation: the properties map onto what people already do; name them clearly; visualise the space.

**Risk 2: Tests-over-code can be misread as no design.** Disposable code still needs good design. Mitigation: tests encode intent; design still matters; the code must match the tests' intent (cross-ref: the coding-as-abstraction-layers brief).

**Risk 3: Passing tests for bugs can confuse.** A passing test for broken behaviour looks wrong. Mitigation: label them as documenting current behaviour; a fix flips the test; it makes the real state explicit.

**Risk 4: Attack-surface alignment needs the attack surface mapped.** Coverage alignment depends on knowing what is exposed. Mitigation: reuse the security and blast-radius mapping (cross-ref: the SG/Sentinel and blast-radius briefs); delete dead code.

**Risk 5: Accountability metrics can be gamed.** Counting escapes can be skewed. Mitigation: the escape-to-gap mapping is binary; pair with mutation testing and coverage of variations.
