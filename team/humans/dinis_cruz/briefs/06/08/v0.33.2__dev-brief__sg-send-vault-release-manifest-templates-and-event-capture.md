# The Provider Vault Workflow: Release Manifests, Templated Vaults, And Full Event Capture

**version** v0.33.2
**date** 8 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, @Dev
**type** Dev brief

## What This Is

The workflow MVP for the provider-and-recipient vaults (the use case in mind, rendered neutrally as a provider creating vaults for the people it serves): **two capabilities together, a release-manifest system for creating versioned vaults from templates with tests and schemas, and a two-way communication channel that captures every event back to the provider, plus an observability vault that receives events from the provider vaults.** It builds on vaults-within-vaults, the append capability, and central key management (cross-ref: the v0.27.62 vault-in-vault-kernel-model, v0.33.2 vault-append-capability, and v0.32.7 central-key-management briefs). New contributions: **embedded access keys, the release manifest and supported-releases convention, update strategies, a tests-and-schema quality gate, two code bases per release, the Uber vault, full event capture, and the observability meta-layer.** A related concept, where tests run from, is flagged for its own document.

## Context: Vaults Within Vaults, With Embedded Access Keys

The capability this builds on: **a provider can create a vault and embed an access key in another vault, so a vault can write files and access vaults.**

The project lead: **"now that we have the ability to create vaults within a vault, the provider can create a vault and embed the access key in the other vault, which means we can create a vault that is able to write files and access vaults with an access key."** So vaults-within-vaults (cross-ref: the vault-in-vault-kernel-model brief) plus an embedded access key gives a vault the ability to act on other vaults. This is the foundation for both the release system (a vault that creates and writes other vaults) and the event capture (a vault that writes events to another vault).

## Part 1: Create Vaults From Templates Via A Release Manifest

The first capability, and the core convention: **create a vault from a template by copying a release, defined in a release manifest, so versioning is clean rather than copying things all over the place.**

The project lead: **"we need the ability to create a vault based on a template. What is powerful is you have version one, two, three, four of a vault. For each vault we create we should pick the vault ID and the commit we copy. The best way is to create a manifest, or else it gets messier, you get this weird copy all over the place. We add a release manifest, and that release is what we copy to the new vault."**

### The Release Manifest Convention

Releases live as folders inside the code folder, each self-contained:

| In A Release Folder | Contents |
|---------------------|----------|
| The release manifest | What defines and is copied for this release |
| The source code | All the source required, in the vault |
| Secrets choice | Whether to add secrets, and which ones |
| Tests | Unit, integration, end-to-end, and evals |
| The schema | Version-controlled (below) |

The project lead: **"in the same vault I can have multiple folders, each with the code. We call it release, each release is a folder inside the code folder, so I can have release one, two, three. Inside is the release manifest, all the source code required, whether to add secrets and which, and this is also a perfect place to include tests."** So a vault can hold several releases as folders, each a self-contained, copyable unit defined by its manifest.

### The Supported-Releases File And The Pointers

A single file lists which releases are live, with the pointers to recover them:

The project lead: **"we need a supported-releases file, maybe at the root, and when we open the vault that file is read and contains the releases currently alive, because we can remove and retire them, and it contains the commit. When you create a release, you add a file to the new vault with the vault ID created, the release ID, the hash of the commit, and the object ID, so we can always go back to where we were."**

| The Release Record Holds | Why |
|--------------------------|-----|
| The created vault ID | Which vault this release made |
| The release ID | Which release it is |
| The commit hash | The head it was created from |
| The object ID | So you can always go back |

So a supported-releases file declares the live releases (retirable over time), and creating a release writes a record (vault ID, release ID, commit hash, object ID) so any release is recoverable.

### Update Strategies

The project lead: **"if I want to update a vault with a new version, I could copy a new one, or just update those files, copy the commits on top of the others. It becomes a lot more scalable, because we do not have to worry about stuff leaking into the vault."** So updating a vault is either a fresh copy or an in-place update of the release files, and the manifest convention keeps it clean and scalable (no stray copying, nothing leaking in).

### The Tests-And-Schema Quality Gate

The project lead: **"what I like is it also lets us include tests, unit, integration, end-to-end validation, and evals, which gives us a quality gate: is the vault well deployed, is it configured correctly? The agent creating the vault can maintain this."** And on the schema: **"this should also define the schema we use, because we need to version-control the schema."** So each release carries tests and a version-controlled schema, giving a quality gate (is this vault correctly deployed and configured?) that the creating agent maintains (cross-ref: the v0.32.4 coding-as-abstraction-layers brief's scaffolding-and-validations-as-the-new-unit-tests).

### Two Code Bases Per Release, And The Uber Vault

The project lead: **"the release should have two code bases: the code we push to the server (the provider), and the client code base, or better, it should point to the provider's release, because even the provider vault needs the same things. The provider vault also needs version control of releases, so we can have an Uber vault that manages the multiple provider vaults, especially from a release point of view."** So a release covers both the server (provider) and client code (or the client points to the provider release), and because the provider vault itself needs release versioning, an Uber vault manages many provider vaults from a release standpoint, a fractal, vault-of-vaults release-management structure (cross-ref: the vault-in-vault and PKI-registry briefs).

### Flagged For Its Own Document: Where Do The Tests Run From?

The project lead explicitly parks this: **"an interesting property is where the tests run from. Do they run inside the vault, from the parent, from a browser? Is it pure unit test, assurance, browser automation? What resources do the tests need? I need to write a document about the concept itself."** So the question of where tests execute (inside the vault, the parent, the browser), what kind they are (unit, assurance, browser automation), and what resources they need is noted as a property of the release manifest but reserved for a dedicated brief.

## Part 2: Two-Way Communication And Full Event Capture

The second capability: **a two-way channel that carries any type of message, capturing every event the recipient generates and sending it back to the provider.**

The project lead: **"we need a two-way communication channel. The message we send back and forth is not necessarily just an email, it can be anything, which is why we are moving the API from inbox to append. We can have a whole set of events sent back to the provider with information about that client or vault."** So the channel is the append capability (cross-ref: the v0.33.2 vault-append-capability brief), carrying any message type, and it streams events from the recipient vault to the provider.

### Capture Every Event

The project lead: **"the workflow is the recipient gets a link, opens it, sees the page, clicks to start the form, goes through it providing answers, submits, maybe gets a report. As soon as the recipient opens the vault we see it, as soon as they click start, every submission, I would argue every single submission, we should send a message. So even if the last step failed or had a bug, we already have all the data."**

| Event | Captured |
|-------|----------|
| Opens the vault | Yes, immediately |
| Clicks start | Yes |
| Each step or submission | Yes, every one |
| Submit, report, view | Yes |

So every interaction (open, start, each submission) is sent as a message as it happens, so the provider has the data even if a later step fails. It scales because it is a pure write (below).

### The Visibility And Privacy Posture

An explicit MVP-stage posture, stated honestly: **visibility is turned up to maximum, with an explicit disclaimer not to enter confidential data.**

The project lead: **"we should have a disclaimer to say do not put any confidential data here, and in this version we have visibility tilted to 10 or 11. Just capture that information."** So for this MVP, logging and event capture are at maximum, and because of that the workflow carries an explicit do-not-enter-confidential-data disclaimer. This is a deliberate, stated MVP choice (cross-ref: the v0.32.7 large-file brief's maximum-visibility approach), and it is a real privacy posture that must be tightened before any confidential data is involved (see risks), which matters especially given the sensitive nature of the eventual use case.

### Two-Way Messaging And Help

The project lead: **"there is a whole inbox on and off, and we can now create a two-way messaging system. We could even say, do you need help, anything we can do, and that could be a person behind the scenes, which is cool, and eventually an LLM, but now it could just be us."** So the channel also supports live two-way messaging (a help conversation), staffed by a person now and possibly an LLM later (cross-ref: the central-key-management brief's in-vault LLM capabilities).

### It Scales Because It Is A Pure Write

The project lead: **"this should scale because it is just a simple write, a pure write, so we should not have to care too much about it."** So event capture is cheap: each event is a pure append/write to the channel, which is why capturing everything is feasible.

## Part 3: The Observability Meta-Layer

A meta-layer for the project lead, not the provider: **a vault that receives all the events from the provider vaults, so the team can see usage, bugs, results, and performance.**

The project lead: **"I should do the same for my own provider-release workflow: have a vault that receives all the events from the provider vault, so when I send this to the provider and the admin helping, I can see them opening it, see bugs, see results. We should have a mode where any bug, request, or stats, even performance stats like the timings, get sent over. We added a really cool timings observation, a Jaeger-like workflow, so we could send that too."** So the same event-capture pattern is applied one level up: an observability vault receives events from the provider vaults, giving the team visibility into adoption, bugs, results, and performance (including the Jaeger-like distributed-timing traces). It is the fractal pattern again (cross-ref: the Uber vault above): events flow recipient to provider, and provider to the observability vault.

## Go Live Soon

The urgency, and the payoff: **doing this gives a strong MVP, and there is already a lineup of users wanting to try it.**

The project lead: **"we really want to go live with this as soon as possible, because there is already a lineup of users that want to try this. If we do this, we will have a really good MVP."** So the goal is to ship: the release system plus the event-capture channel plus the observability vault is the MVP, and there is real, waiting demand.

## What This Asks For

1. **Use embedded access keys** (a vault that can write files and act on other vaults).
2. **Build the release-manifest system** (releases as folders; the manifest is what is copied; templated, versioned vaults).
3. **Add the supported-releases file and records** (which releases are alive; vault ID, release ID, commit hash, object ID; recoverable).
4. **Support both update strategies** (a fresh copy, or an in-place file update; clean and scalable).
5. **Include tests and a version-controlled schema** (unit, integration, end-to-end, evals; a quality gate the agent maintains).
6. **Carry two code bases per release** (server and client, or the client points to the provider release; the Uber vault manages many provider vaults).
7. **Build the two-way append channel** (any message type; live two-way messaging and help).
8. **Capture every event** (open, start, each submission; the provider has the data even if a step fails).
9. **State the visibility and privacy posture** (maximum visibility for the MVP; the explicit do-not-enter-confidential-data disclaimer; tighten before confidential data).
10. **Build the observability vault** (it receives events, bugs, results, and Jaeger-like timings from the provider vaults).
11. **Ship the MVP** (there is waiting demand).
12. **Write the where-do-tests-run-from brief** (the parked concept).

Estimated effort: substantial but well-supported; vaults-within-vaults, the append capability, central key management, and the timings tracing exist; the contribution is the release-manifest system and the full event-capture channel. The MVP is a provider creating versioned recipient vaults from a release manifest with tests and a schema, recipient interactions captured event by event to the provider, and an observability vault receiving events and timings.

## What This Does Not Try To Be

- **Not copy-all-over-the-place versioning.** A release manifest convention; clean and recoverable.
- **Not untested deployment.** Tests, a schema, and a quality gate per release.
- **Not email-only messaging.** The append channel carries any message type, both ways.
- **Not partial capture.** Every event is captured, even if a later step fails.
- **Not for confidential data, in this MVP.** Maximum visibility with an explicit disclaimer; tighten before confidential data.

## Honest Risks

**Risk 1: Maximum visibility plus full event capture is a real privacy exposure.** Capturing everything, especially in a sensitive domain, is sensitive. Mitigation: the explicit do-not-enter-confidential-data disclaimer for the MVP; capture only what is needed; tighten and scope before any confidential data; this posture is MVP-only and must change for production (cross-ref: the accountability briefs).

**Risk 2: The release manifest can grow complex.** Many releases, codebases, secrets, tests. Mitigation: the manifest convention; releases as self-contained folders; the supported-releases file; retire old releases.

**Risk 3: Embedded access keys concentrate capability.** A vault that can write other vaults is powerful. Mitigation: scope the access key; the permission mapping (cross-ref: the permission-granularity brief); the accountability discipline.

**Risk 4: The Uber vault and observability vault centralise a lot.** Managing many provider vaults and all their events in one place. Mitigation: the fractal pattern keeps it structured; scope what each vault can see; treat events as pure writes.

**Risk 5: Where tests run from is unresolved.** Test execution location and resources are open. Mitigation: the parked dedicated brief; for the MVP, choose the simplest location that works.
