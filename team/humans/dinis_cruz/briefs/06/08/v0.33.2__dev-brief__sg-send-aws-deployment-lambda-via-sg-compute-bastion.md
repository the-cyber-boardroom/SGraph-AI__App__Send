# Deploying The SG Send Lambda: AWS Commands Run Through An SG Compute Bastion, With Low-Privilege Tokens

## What This Is

A brief for the DevOps agent of the SG API: **capture every AWS command needed to install the SG Send Lambda function on a pristine AWS environment, run them through an SG compute bastion (an ephemeral EC2 spun up in the target account and driven from a vault app over bash), and scope the permissions tightly with low-privilege, impersonated tokens.** AWS commands now, replicated in code later. It is the how for the shippable product's deployment to the customer's AWS account (cross-ref: the v0.33.2 shipping-vault brief), uses the ephemeral-compute pattern (cross-ref: the v0.32.4 ephemeral-compute-actions-on-vaults brief), and applies the least-privilege discipline (cross-ref: the v0.32.3 NHI-2.0-permission-granularity and the accountability briefs). New contributions: **the command-capture approach, the SG compute bastion, vault-app-over-bash control, and low-privilege scoped tokens for deployment.**

## The Task: Capture Every AWS Command To Deploy The Lambda

The deliverable, deliberately concrete: **capture every single AWS command needed to install the SG Send Lambda on a pristine AWS environment, using plain AWS commands now and replicating them in code later.**

The project lead: **"this is a brief for the DevOps agent of the SG API to create a set of AWS scripts. We could do this with deployment tooling, but for now I would like to do it with just AWS commands, capturing every single command that needs to run to install the SG Send Lambda function on a pristine AWS environment, which is the one we are going to use for the customer. List all the commands required to deploy the Lambda, like what we do now in code, but as a series of AWS commands that we will then replicate in code."**

| Now | Later |
|-----|-------|
| Every AWS command, captured explicitly | Replicated in code (deployment tooling such as CDK) |
| A series of commands to deploy the Lambda | The same, abstracted into code |
| A pristine target AWS environment | The customer's account |

So the first step is to list, explicitly, every AWS command that installs the SG Send Lambda on a clean AWS account (the customer's), as a concrete command series rather than starting with deployment tooling. This is the explorer-phase approach (cross-ref: the v0.32.4 coding-as-abstraction-layers brief): get the exact commands working first, then move up the abstraction stack to code.

## SG Compute As A Bastion

The mechanism, and a neat one: **use SG compute as a bastion, spinning up a quick EC2 instance in the target environment and executing the commands there, driven from a vault app over bash.**

The project lead: **"the way we should do this is use SG compute as a bastion. SG compute spins up a quick EC2 instance on the target environment and uses that to execute the commands, which means we can do this from a vault app, because the vault app can communicate directly via bash, since we added bash support to the bastion host API."**

| Step | What Happens |
|------|--------------|
| SG compute as bastion | The control point for deployment |
| Spin up an EC2 in the target | A bastion instance inside the customer's account |
| Execute the commands there | The deployment runs from inside the target environment |
| Driven from a vault app over bash | The vault app talks to the bastion host via the bash API |

So deployment is driven by SG compute (cross-ref: the ephemeral-compute brief): it spins up an ephemeral EC2 bastion inside the target account, and runs the captured commands from there, controlled from a vault app over the bash support added to the bastion-host API. Running from inside the target account is the right place to execute account-scoped AWS commands, and the vault-app-over-bash control means the whole deployment is driven from the platform itself.

## Reduce The Attack Surface: Low-Privilege, Scoped Tokens

The security discipline, applied from the start: **work out the exact key permissions and reduce the attack surface, using low privilege and impersonation, with scoped tokens sent to the bastion to execute.**

The project lead: **"figure out the exact key permissions, and start to think about how to reduce the attack surface of the permissions used to execute the commands, so we start using low privilege and impersonating. What would be interesting is to create the tokens that we then send to the bastion host to execute."**

| Concern | Discipline |
|---------|-----------|
| What permissions the deployment needs | The exact key permissions, worked out |
| Over-broad deployment credentials | Reduce the attack surface; low privilege |
| Standing power | Scoped tokens sent to the bastion to execute |
| Acting as a broad identity | Impersonation, scoped to the task |

So the deployment credentials are scoped from the start: determine the exact permissions the commands need, reduce the attack surface to that minimum, use low-privilege and impersonation, and send scoped tokens to the bastion to execute. This is the accountability-at-provisioning and scoped-secret discipline (cross-ref: the v0.32.4 ephemeral-compute brief and the hope-driven-development and second-story articles) applied to deployment: the bastion gets the one scoped token for the one deployment, not standing broad access. It is also the per-application and per-API permission-mapping work in practice (cross-ref: the permission-granularity and cloud-permissions briefs).

## The Plan: List Commands, Map The Architecture, Then Code

The sequence: **list all the commands, map the architecture, and then replicate it in code.**

The project lead: **"start by listing all the commands, then map the architecture, and what we need is all the commands required to deploy the Lambda, and then start to replicate in code. Let's map this out."** So the plan is: enumerate every command, map the deployment architecture (the bastion, the vault app, the tokens, the target account), and then, once it works as commands, replicate it in code. Commands first for clarity and control; code second for repeatability.

## What This Asks For

1. **Capture every AWS command** (to install the SG Send Lambda on a pristine AWS environment; the customer's account).
2. **Use SG compute as a bastion** (spin up an ephemeral EC2 in the target account; execute the commands there).
3. **Drive it from a vault app over bash** (the bash support on the bastion-host API).
4. **Work out the exact key permissions** (what the deployment actually needs).
5. **Reduce the attack surface** (low privilege; impersonation; the minimum permissions).
6. **Send scoped tokens to the bastion** (the one scoped token for the deployment; not standing access).
7. **Map the architecture, then replicate in code** (commands first, code second).

Estimated effort: moderate; the existing code-based deployment, SG compute, the bash bastion support, and the permission-mapping work exist; the contribution is the explicit command capture, the bastion-driven deployment, and the scoped-token permissions. The deliverable is every AWS command to deploy the SG Send Lambda to the customer's pristine account, runnable through an SG compute bastion from a vault app, with low-privilege scoped tokens, then replicated in code.

## What This Does Not Try To Be

- **Not deployment tooling first.** Plain AWS commands now; code later.
- **Not deployed from outside the account.** An ephemeral EC2 bastion inside the target account.
- **Not broad deployment credentials.** Low privilege, impersonation, scoped tokens.
- **Not standing access.** The bastion gets a scoped token for the deployment, then goes away.
- **Not a one-off.** The commands are mapped to be replicated in code.

## Honest Risks

**Risk 1: Deployment permissions are powerful.** Installing a Lambda needs real AWS rights. Mitigation: the exact key permissions only; low privilege and impersonation; scoped tokens; the ephemeral bastion is torn down (cross-ref: the ephemeral-compute brief).

**Risk 2: A bastion in the customer's account is sensitive.** An EC2 with deployment rights is a target. Mitigation: ephemeral, scoped, destroyed after; the scoped token bounds what it can do.

**Risk 3: Scoped tokens must be handled safely.** Sending tokens to the bastion is itself sensitive. Mitigation: scope to the deployment, short-lived, sent over the controlled bash API; rotate.

**Risk 4: Commands can drift from the code version.** Two representations can diverge. Mitigation: capture commands first, then replicate in code as the source of truth; keep them aligned.

**Risk 5: A pristine environment has unknowns.** A clean account may differ from expectations. Mitigation: capture every command explicitly; test on the pristine target; the commands document the full setup.
