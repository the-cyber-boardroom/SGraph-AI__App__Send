# Artefact-Driven Security Assessments: Capture The Intermediate Representations, Scan The Delta, And Invert The Economics

## What This Is

A thesis on a gap in security-assessment workflows and how vaults close it: **capture, version-control, and reuse every intermediate artefact a security assessment produces, so that each rescan is a delta rather than a fresh start, the cost of rescanning falls the more you scan, and LLMs are used to build the analysis code rather than do the heavy lifting inline.** It builds directly on the blast-radius thesis, the testing-and-ephemerality reframe, and the coding-as-abstraction argument (cross-ref: the v0.31.9 blast-radius, v0.33.2 tests-as-properties, and v0.32.4 coding-as-abstraction-layers briefs), and on the security graph (cross-ref: the v0.27.58 SG-Sentinel compliance-as-living-graph brief). New contributions: **the broken cost-per-vulnerability economics, the lose-99-percent flat-report problem, artefact-driven assessment via the LETS workflow, delta scanning, the did-the-risk-change decision, LLMs-build-the-code, and the skill of a function.**

## The Gap And The Broken Economics

The motivating problem, from a sharp observation: **security tooling never keeps state between assessments and is not version controlled, so every scan starts from scratch, and the cost per vulnerability discovered keeps rising.**

The project lead: **"someone observed: you do a scan and find a hundred vulnerabilities, another and find ten, you fix them all, another and find zero, but every scan costs the same. So do you keep scanning? The cost per vulnerability discovered keeps going up. Security tooling traditionally had two key problems, beyond false positives and negatives: we never kept the state between assessments, so every security review starts from scratch, and it is not version controlled. They go hand in hand, because if you cannot version control the whole thing, capturing state becomes very problematic, you do not know which phase you are in."**

| Traditional Scanning | The Consequence |
|----------------------|-----------------|
| No state kept between assessments | Every review starts from scratch |
| Not version controlled | You do not know which phase you are in |
| Same cost every scan | Cost per vulnerability discovered rises as you fix them |

So the economics are broken: as you fix vulnerabilities, each scan finds fewer, but costs the same, so the cost per finding climbs and rescanning stops making sense. The root cause is that no state is kept and nothing is version controlled.

## The Flat-Report Problem: You Lose 99 Percent Of What You Create

The deeper waste, with an analogy: **an assessment generates enormous intermediate knowledge, then collapses it into a flat report, losing almost everything that was created.**

The project lead: **"it is like you go in, do the sensing, interview tons of people, create gigabytes and graphs, model the application, make all these connections, find all these clues, and in the end you produce a PDF, a flat file, a bunch of findings. You lose 99.9 percent of what you created. That is the problem, that is what does not scale, because every time you start from scratch."** So the assessment's real output (the models, graphs, connections, and clues) is discarded, and only a flat report survives. Starting the next assessment from that flat report means rebuilding all of it, which is why it does not scale.

## Artefact-Driven Assessment: Capture Every Intermediate Representation

The reframe, and it connects to testing and ephemerality: **drive the assessment by artefacts, capturing every intermediate representation and version-controlling the code that creates them, which every security engine already does internally but never exposes.**

The project lead: **"with LLMs we can create a security scanning flow driven by artefacts, an artefact-driven security assessment. Every security engine does this, they just do not expose it. It goes back to the whole thing of testing and ephemerality: the point is not that we are doing something different, it is that in the past most of that knowledge was thrown away. What is powerful is using LLMs to create mini tools, mini transformations, mini verifications, mini analysis, so you capture every intermediate representation, and version-control the code that creates them. This is the LETS workflow, load, extract, transform, and save, going from transformation to transformation."**

| The LETS Workflow | What It Does |
|-------------------|--------------|
| Load | Bring in the source, config, and environment |
| Extract | Pull out the representations |
| Transform | Apply mini tools and analyses, transformation to transformation |
| Save | Capture every intermediate representation, version controlled |

So the assessment becomes a chain of small, version-controlled transformations (the LETS workflow), each producing an intermediate representation that is kept, not discarded (cross-ref: the tests-as-properties brief's ephemerality and the coding-as-abstraction brief's mini-tools). The point is not novelty: engines already compute these internals; the change is exposing, capturing, and version-controlling them.

## The Next Scan Is A Delta

The payoff, and the inversion: **if every intermediate representation is captured and version controlled, the next scan is a delta, so you rarely start from scratch and the cost of rescanning falls the more you scan.**

The project lead: **"if we capture all the intermediate representations and only process data on intermediate representations, and build mini tools on top of them, then the next scan is fundamentally a delta. You should never, or very rarely, start from scratch, you just look at the delta from one version to the other. This needs access to source code, configuration files, the environment, everything that impacts the application, because without that you are starting blind. If you get this right, the cost of rescan goes down the more scans you do. If the code has not changed, the cost of rescanning should be minimal."**

| Traditional | Artefact-Driven |
|-------------|-----------------|
| Every scan from scratch | Each scan is a delta |
| Cost per finding rises | Cost of rescanning falls |
| Same work each time | Minimal work if nothing changed |
| Findings only | Reusable, version-controlled artefacts |

So the quality lives in the transformation blocks (their maturity is the assessment), and once they exist, a rescan compares versions rather than rebuilding. The cost of rescanning falls as the artefacts accumulate, the opposite of the broken economics, and it requires the whole chain (source, config, environment), because without it you cannot know what changed.

## If Nothing Changed, The Process Should Not Change: Feed In The Variables

The governing primitive, and where it goes upstream: **if nothing changed, the security process should not change, so what matters is feeding in the variables that can change, the whole upstream context, and asking, did the risk change?**

The project lead: **"if nothing changed, the security process should not change. What is important is the variables that could change, and this is where you go much upstream, the blast-radius context: the environment, the landscape, the risk profile, the threat environment, the type of attacker, the whole ecosystem. The code may not have changed, but the threat landscape changed, or the configuration, the deployment, the attacker's toolkit. With a holistic view of the entire chain, we make a risk-based decision: did the risk change?"**

| Even If The Code Is Unchanged | The Risk Can Change Because |
|-------------------------------|------------------------------|
| Same source | The threat landscape changed |
| Same logic | The configuration or deployment changed |
| Same vulnerabilities | The attacker's toolkit changed |
| Same artefacts | The risk profile or ecosystem changed |

So the delta is not only code: it is the whole upstream context (cross-ref: the blast-radius brief's context, threat landscape, attacker, and ecosystem). The decision a rescan answers is whether the risk changed, which can happen even with unchanged code, and which a holistic view of the entire chain makes possible.

## LLMs Build The Code, They Do Not Do The Heavy Lifting Inline

A crucial discipline, and a cost signal: **the LLM is used to create the parsing and analysis code, which matures over time, and only connects the dots at the end on new data, so token use should not keep growing.**

The project lead: **"the point is not to have the LLMs inline doing the heavy lifting. The LLM should create the code that does the parsing and analysis, which then evolves to a mature stage in the Wardley sense. Only at the end, in event-driven architectures and on new data, should the LLM connect the dots and run investigations on top of the artefacts. The use of LLMs and tokens should not grow big. It is a bad signal if the cost of LLMs keeps going higher and you are not reusing what was created before."**

So the LLM builds the transformation code (which then runs deterministically and matures, the Wardley evolution; cross-ref: the coding-as-abstraction-layers and skill-lifecycle briefs), and only does direct reasoning at the edges, on genuinely new data, to connect dots and run investigations on the artefacts. The consequence is a cost signal: if LLM and token costs keep rising, you are not reusing prior artefacts, which is a sign the approach is wrong.

## Vaults Make It Scale

Why the vault is the substrate: **vaults version-control everything and, with append mode, let this scale, capturing data, deltas, source, configurations, and the connections between them.**

The project lead: **"the vaults allow this to happen, because the vault gives version control anyway, everything you put in a vault is version controlled, and especially now that we have an append mode, we can scale capturing the data, capturing the delta, connecting the source code, the configurations, connecting everything together."** So the vault is the natural home (cross-ref: the v0.33.2 vault-append-capability and the publishing and commit-queue briefs): it version-controls every artefact for free, and append mode lets the capture scale, the deltas, the source, the configs, and the connections, all in one versioned store.

## Architecture, State, And Control Flows, And The Skill Of A Function

What the captured artefacts include, bottom-up: **architectural, state, and control flows, and for every function an analysis of its inputs, outputs, and intent, the skill of the function.**

The project lead: **"with vaults we can have architectural flows, state flows, control flows. Every function should have an analysis of inputs and outputs, everything we can grab about the function, and we also connect its intent. It is almost like, what is the skill of a function? What does it do, what is the point of it, what is the logic behind it. If you build these architectures bottom-up, you have that."** So the artefacts are not just findings: they are a structured model of the application, architectural, state, and control flows, and per-function analysis of inputs, outputs, and intent (the skill of a function; cross-ref: the v0.32.3 semantic-knowledge-graphs and skill-as-projection briefs, and the SG-Sentinel living graph). Built bottom-up, this is a living model of the application that each scan enriches.

## The Positive Model: Every Scan Builds Understanding

The reframe of value, and a pointed insight: **every scan now builds understanding of the application rather than being consumed, and the artefacts are often more valuable than the report.**

The project lead: **"you have a positive model, because every time you do a security scan you gain an understanding of the application, you are not wasting the scan, you are creating artefacts that tell you what the scan discovered. A lot of pen-testing and security companies do not realise that the artefacts they create during an assessment are sometimes more valuable than the report, because they have learned how to extract that information."** So the model is positive-sum: each scan adds to a growing, reusable model of the application, so no scan is wasted. And the strategic insight is that the intermediate artefacts (the extracted understanding) are frequently worth more than the final report, a value most security firms discard.

## What This Asks For

1. **Make assessments artefact-driven** (capture every intermediate representation; do not collapse to a flat report).
2. **Use the LETS workflow** (load, extract, transform, save; version-control the code that creates the artefacts).
3. **Make each rescan a delta** (rarely start from scratch; the cost of rescanning falls as artefacts accumulate).
4. **Connect the whole chain** (source code, configuration, environment; without it you are blind).
5. **Decide by did-the-risk-change** (feed in the upstream variables; the blast-radius context; even unchanged code can carry changed risk).
6. **Use LLMs to build the code, not inline** (mature transformation blocks; LLM reasoning only at the edges on new data; rising token cost is a bad signal).
7. **Store it in vaults** (version control plus append mode; capture data, deltas, source, configs, and connections).
8. **Build the application model bottom-up** (architectural, state, and control flows; per-function inputs, outputs, and intent, the skill of a function).
9. **Treat the artefacts as the asset** (each scan builds understanding; the artefacts can be worth more than the report).

Estimated effort: substantial but well-grounded; the vault version control and append mode, the LLM-builds-code approach, the blast-radius context, and the security graph exist; the contribution is the artefact-driven, delta-scanning model and its economics. The proof is two scans of one application where the second is a delta costing a fraction of the first, with every intermediate artefact captured and version controlled in a vault.

## What This Does Not Try To Be

- **Not scan-from-scratch.** Each rescan is a delta against captured artefacts.
- **Not a flat report.** Every intermediate representation is captured and reused.
- **Not LLM-inline heavy lifting.** LLMs build the code; reasoning only at the edges on new data.
- **Not code-only delta.** The risk delta includes the whole upstream context.
- **Not rising cost.** Done right, rescanning gets cheaper, and rising token cost is a bad signal.

## Honest Risks

**Risk 1: The transformation blocks must be high quality.** The assessment is only as good as the mini tools. Mitigation: maturity of the transformation blocks is the goal (the Wardley evolution); build and validate them well (cross-ref: the tests-as-properties brief).

**Risk 2: It needs deep access (source, config, environment).** Holistic analysis requires a lot of access. Mitigation: that access is the point, and the vault and scoped access manage it (cross-ref: the access and permission briefs); without it you are blind anyway.

**Risk 3: Capturing everything is a large data and provenance task.** Many artefacts and versions. Mitigation: the vault with append mode is built for this; deltas keep growth bounded; version control gives provenance.

**Risk 4: The did-the-risk-change decision needs the upstream context.** Risk deltas depend on good context. Mitigation: the blast-radius model (cross-ref: that brief); feed in threat landscape, config, deployment, attacker toolkit.

**Risk 5: Over-using the LLM inline.** It is tempting to let the LLM do the analysis directly. Mitigation: LLM builds the code; the rising-cost signal flags drift; reasoning only at the edges.
