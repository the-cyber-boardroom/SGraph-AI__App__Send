## What This Is

A brief for a personal vault that turns a LinkedIn data export into something useful: **load the LinkedIn export into a vault, script the analysis and transformation as a Load-Extract-Transform-Save chain across versioned folders, keep it current from weekly dumps, and build visualisations and filters on top, using the vault as a database and a store of visualisations powered by scripts and LLMs.** It is the personal-data sibling of the artefact-driven security thesis (cross-ref: the v0.33.16 artefact-driven-security-assessments brief), it serves the partner-outreach work directly (cross-ref: the v0.33.16 partner-briefing brief), and it builds on the vault-as-database and search work (cross-ref: the v0.31.9 webify-ai-fi-your-spreadsheets and v0.32.4 search-engine briefs). It also includes, as requested, a section on the SG/Vault capabilities the implementing agent should be aware of. New contributions: **the LinkedIn-export use case, the network-as-database approach, and the implementing-agent capability map.**

## The Problem

The motivation is concrete and felt: **LinkedIn holds a rich network, but its interface cannot filter, connect, process, or analyse it, so the data is stuck.**

The project lead: **"I have a really nice LinkedIn network, including comments I have made, people I have reached, people we swap messages with, all that. But right now it sucks, because the LinkedIn interface has no good way to filter the data, connect the data, process them, or do analysis and manipulations. In the past I took LinkedIn data, loaded a spreadsheet, added some metadata, processed it, but it was all manual or a bit of scripts."** So the data is valuable but trapped: the platform exposes it but does not let you work with it, and past attempts were manual one-offs. The export changes that, and the tech stack now exists to do it properly.

## The Use Case: Network Intelligence For Outreach

Why this matters right now: **the immediate use is answering outreach questions like who in my network works in a given field or company, which directly serves the partner search.**

The project lead: **"even from the previous thing, who do I know that works in password managers, who do I know that works in specific companies, how can I reach out to people?"** So the first payoff is network intelligence (cross-ref: the partner-briefing brief): querying the network by field, company, and relationship to find the right people to approach. The export contains the raw material, connections, comments, reaches, and messages, and the vault makes it queryable.

## The Approach: The Export In A Vault, Transformed Through LETS

The core method, and it is the artefact-driven pattern applied to personal data: **put the export in a vault and process it through a Load-Extract-Transform-Save chain, with multiple folders each holding a transformation and its analysis.**

The project lead: **"I already requested and got a zip from LinkedIn. Create a vault, put my LinkedIn data inside, then create the scripts to analyse and transform the data, our good old load, extract, transform, and save. Create multiple folders with multiple transformations, each containing a set of analyses."**

| Stage | What Happens |
|-------|--------------|
| Load | The LinkedIn export (the zip) goes into the vault |
| Extract | Pull out connections, comments, messages, reaches |
| Transform | Scripts derive analyses, enrichments, and metadata across folders |
| Save | Every intermediate representation is captured and version controlled |

So the export becomes the input to a chain of small, version-controlled transformations (cross-ref: the artefact-driven-security-assessments brief's LETS workflow), each folder a transformation and its analysis. The transformations are code, kept and versioned, not manual one-offs.

## Keeping It Current: Weekly Dumps And Version Control

How it stays useful over time: **as new weekly exports arrive, add them to the vault and version-control everything, so the network history accumulates as deltas.**

The project lead: **"as I get a weekly dump, a weekly download, we keep it up to date, so we version control everything we do."** So the vault ingests periodic exports (cross-ref: the v0.33.2 append-capability brief) and version-controls each, so the analysis updates as a delta over the previous version (cross-ref: the artefact-driven-security-assessments brief's delta model) and the network's history is preserved, not overwritten.

## Visualisation, Filtering, And The Vault As A Database

The output, and the demonstration: **go to town on visualisations and filters, using the vault as a database and a store of visualisations and data, a mix of scripts and LLMs behind the scenes.**

The project lead: **"very importantly, we look at visualisations. Let's go to town on how to visualise the data and filter the data. Let's show how we can use the vault fundamentally as a database, a store of visualisations and data stores, a mix of scripts powered by LLMs behind the scenes that helps put everything together."** So the vault is shown as a working database and visualisation store (cross-ref: the webify-ai-fi-your-spreadsheets and search-engine briefs): filterable network data, rich visualisations, and derived data stores, built from versioned scripts with LLMs assembling and assisting behind the scenes (cross-ref: the central-key-management and coding-as-abstraction briefs). This is also a public demonstration of the vault as more than storage.

## Questions To Confirm Before Building

Because several of the capabilities above are designs or MVPs in the corpus rather than confirmed-shipped, the implementing agent should confirm the following before starting, and the project lead should fill any gaps:

1. **Which capabilities are shipped today?** Specifically the append mode, ephemeral compute, the search engine, deterministic value indexes, and vault apps, the agent needs the current state, not the design intent.
2. **What is the LinkedIn export's structure?** The export is a set of CSV files (connections, messages, comments, reactions, and so on); confirm the exact files and fields in this export so the extract step is accurate.
3. **How does compute run against the vault?** Inside the vault, from a parent, or from a browser, and with what resources (cross-ref: the where-do-tests-run-from question in the tests-as-properties brief).
4. **What is the privacy boundary for visualisations?** The export contains personal data about other people; confirm what may be shared publicly versus kept private (see risks).
5. **Should this be built from a template?** If a release-manifest template exists, the agent could create the vault from it (cross-ref: the v0.33.2 vault-release-manifest brief).

The output is a working vault that answers network questions, refreshes from weekly dumps, and shows the vault as a database and visualisation store.

## What This Does Not Try To Be

- **Not a manual spreadsheet.** A scripted, version-controlled, repeatable pipeline.
- **Not a one-off.** It refreshes from weekly dumps as deltas.
- **Not just storage.** The vault is the database, the runtime, and the visualisation store.
- **Not a LinkedIn scraper.** It uses the user's own official export.
- **Not a public dump of others' data.** The privacy boundary is set deliberately.

## Honest Risks

**Risk 1: The export contains other people's personal data.** Connections, messages, and contacts include third parties. Mitigation: it stays in the user's zero-knowledge vault, which is the right home; do not publish third-party personal data in shared visualisations; set the privacy boundary explicitly (the question above).

**Risk 2: LinkedIn's terms and export format.** Use the official export and respect the terms; the format can change. Mitigation: the user's own official export; confirm the structure; do not scrape.

**Risk 3: Capability assumptions may be wrong.** Some referenced capabilities are designs, not shipped. Mitigation: the confirm-before-building questions; the status column.

**Risk 4: Analysis can sprawl.** Many transformations and visualisations. Mitigation: the LETS folders keep it organised; deltas keep refreshes cheap; start with the outreach questions.

**Risk 5: LLM cost if overused inline.** Letting the LLM do the heavy lifting each run. Mitigation: LLMs build and assemble the scripts, which then run deterministically (cross-ref: the artefact-driven-security-assessments brief's LLMs-build-the-code discipline).
