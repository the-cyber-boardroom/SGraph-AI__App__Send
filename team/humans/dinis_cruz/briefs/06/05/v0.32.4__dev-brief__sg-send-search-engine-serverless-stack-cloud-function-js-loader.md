# The Serverless Stack For The Vault Search Engine: A Cloud Function That Loads JavaScript

**version** v0.32.4
**date** 5 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, @Dev
**type** Dev brief

---

## What This Is

The implementation stack and MVP for the vault search engine: **a file-based, no-database, serverless semantic search, targeting the website, built on a cloud function whose only job is to load a JavaScript file that does the real work, with an inline-LLM option and a client-side alternative.** It is the concrete build for the architecture set out in the search-engine brief (cross-ref: the v0.32.4 search-engine-on-encrypted-vaults brief), and it reuses the website's existing cloud-function pattern (cross-ref: the v0.32.4 public-data-in-vaults brief). New contributions: **the cloud-function-loads-JavaScript pattern, the agent maintaining each file's semantic graph, the read-key-in-the-function data flow, the cloud-function versus Lambda-at-Edge split, the inline-LLM question-answering option, the paid client-side alternative, and the serverless function as the secret-holding enclave.**

## The Premise And Target

The plan, and where it points first: **build the search engine as an MVP, targeting the website, as a file-based, no-database, serverless semantic search.**

The project lead: **"this follows up on the search engine idea, and I have a plan that might actually work, which would be pretty insane if it worked. Let's create an MVP. The target is the website. We already tried to add search to the website and it did not work very well, but we started thinking in these terms. The primitives: a file-based semantic search, with no database and serverless. No constraints."**

| Primitive | Choice |
|-----------|--------|
| Search type | Semantic |
| Storage | File-based, in a vault |
| Database | None |
| Compute | Serverless |
| First target | The website |

So the MVP is deliberately constraint-free in the conventional sense: no database, no servers, just files in a vault and serverless compute. The website is the first target because search there was attempted before and the groundwork exists.

## The Primitives: Semantic Search The Agent Maintains

What feeds the engine: **ontologies and taxonomies for all the content, processed into a per-file semantic knowledge graph that the agent writing the file creates and maintains.**

The project lead: **"it is a semantic search. You create ontologies and taxonomies for all the articles and content, and that is what we feed the search engine, and it lives in a vault. We process the content into a semantic knowledge graph, on a schedule or on updates, it does not matter. The idea should be that this is created and maintained by the agent that creates and updates the file: every time you update a markdown file, you create or update a semantic graph of the file."** So search is grounded in semantic graphs (cross-ref: the v0.32.3 NHI-2.0-semantic-knowledge-graphs brief), and crucially the graph is maintained at write time by the agent that edits the file: edit a markdown file, update its semantic graph. The index is never stale and never a separate batch job, because building it is part of writing the content (cross-ref: the skills-as-graph and skill-as-projection briefs' built-in maintenance).

## The Key Move: A Cloud Function That Loads JavaScript

The architectural insight, and a clean one: **a very light cloud function whose sole job is to load a JavaScript file, which then runs all the search logic, so the function rarely changes and the logic iterates independently.**

The project lead: **"use the same cloud-function logic the website has. To be clear, this is not a Lambda@Edge, it is a cloud function, a pure, very light, very fast JavaScript function. What it does is download the JavaScript to execute from the website. The function's sole job is to load the JavaScript, because the JavaScript has a runtime, so we can run code. The reason is that we do not update the function very often: once it is on, it is on. The website has a JavaScript file, loaded by the cloud function, that executes the search engine logic."**

| Component | Role | Changes |
|-----------|------|---------|
| The cloud function | Loads the JavaScript file; nothing else | Rarely; once it is on, it is on |
| The JavaScript file | Runs all the search logic | Often; iterated independently |
| Where the JS lives | The website or a vault | Maintained by whoever owns the target |

So the deploy-once function is a thin loader, and all the changing logic lives in a JavaScript file deployed normally from the GitHub repo. The project lead: **"you have a bit of JavaScript we control from our GitHub repo, deployed as normal, and the JavaScript knows how to access the search engine, which means we can run, develop, and test it independently from the site. We minimise the function code, make it much easier to deploy and maintain, and we run it at edge, so you have the speed of the edge."** This is the power of the pattern: minimal, stable edge function; fast iteration on the real logic; edge-speed execution.

## The Data Flow: The JavaScript Has The Read Key

How it reaches the content: **the JavaScript is given the read key, fetches the encrypted files directly from S3, decrypts them (caching the immutable ones), and builds the search indexes from the semantic graph.**

The project lead: **"the JavaScript is given the read key, so it can get the encrypted files directly from S3, decrypt them, and since a lot of these are immutable you can cache them. It loads the files required to map the search engine so you can navigate it. With a semantic knowledge graph and the ability to run logic, we can create all sorts of indexes, from keywords to all sorts of searches."**

| Step | What Happens |
|------|--------------|
| The JS gets the read key | So it can decrypt |
| Fetch from S3 directly | The encrypted files, via the existing setup |
| Decrypt and cache | Immutable files cache well |
| Build indexes | Keyword and semantic indexes from the graph |
| Navigate | The loaded indexes drive the search |

So the JavaScript, holding the read key, pulls encrypted files straight from S3, decrypts them, caches the immutable ones, and builds whatever indexes the search needs from the semantic graph. The read key in the function is the sensitive part, and it is exactly where the serverless-as-enclave idea below matters: the goal is for the function (not the client) to hold the key.

## Cloud Function Versus Lambda At Edge

A deliberate split, by capability: **the light cloud function suffices for the JS-loader and the search, but calling an LLM such as Bedrock requires Lambda@Edge.**

The project lead: **"the inline LLM would only work if it is Lambda@Edge, which is okay, we can still do that. For this one we need Lambda@Edge, because we will need to call Bedrock."** So the architecture uses the lightest tool that works: the pure, fast cloud function for loading the JS and running the file-based search, and Lambda@Edge only when the engine needs to call out to an LLM (Bedrock), which the lighter function cannot do. Choose per feature.

## The Inline-LLM Option: Asking Questions Of The Content

An enhancement worth measuring: **add an inline LLM whose job is to build the semantic knowledge graph, enabling not just fuzzy matching but actually asking questions of the content.**

The project lead: **"it would be cool to add an LLM inline. The LLM's job is to create the semantic knowledge graph we use for the search. It would be interesting to see the performance hit, but this would allow not just much more fuzzy words, but actually asking questions about the content and getting responses."** So an inline LLM (on Lambda@Edge, calling Bedrock) can build or enrich the semantic graph and turn the search into question-answering over the content, not just keyword or fuzzy matching. The open question is the performance cost, which the MVP should measure.

## The Client-Side Alternative

A genuine fork in the design, with a monetisation twist: **alternatively, do the work client-side, where the client builds the semantic graph and the user pays for their own search and question-answering.**

The project lead: **"the alternative is to do this on the client, which might be a better way. It is paid, so that is cool, because then you pay for search, and you pay to talk to the content. The client code's job is to create a semantic knowledge graph, so our search works from both keywords and, more interestingly, from semantic knowledge graphs. This could be created client-side, and there are a lot of other use cases."**

| Server-Side (Serverless) | Client-Side |
|--------------------------|-------------|
| The function holds the read key and secrets | The client builds the graph and searches |
| We run the compute | The user pays for their own compute and LLM |
| The secret-holding enclave | Many other use cases; pay for search and to talk to content |

So the client-side route pushes the semantic-graph building and search to the user's own machine, which is naturally paid (the user pays for their own search and LLM calls) and opens other use cases. Search then works from both keywords and semantic graphs regardless of where it runs.

## The Serverless Concept Is The Enclave

Why the serverless route is still worth building even if client-side wins: **the serverless function is the secure enclave, the thing that can hold secrets the client never sees.**

The project lead: **"it is worth exploring the serverless concept, because it becomes that enclave we can use to do stuff. For example, the enclave can be the one that only has access to some secrets, so the client side never sees them."** So the serverless function is not just an alternative to the client; it is the secure enclave from the search-engine architecture (cross-ref: the search-engine-on-encrypted-vaults brief's secure enclaves, and the v0.32.4 ephemeral-compute brief's scoped secrets). It can hold the read key and other secrets so the client never has to, which is precisely the read-key-handling concern from the data flow above and the public-data brief (cross-ref: the public-data-in-vaults brief's leak-the-read-key versus serve-directly choice). Both routes are worth the MVP: client-side for reach and paid usage, serverless for the secret-holding enclave.

## What This Asks For

1. **Build the search MVP on the website** (file-based, no database, serverless semantic search).
2. **Maintain a per-file semantic graph at write time** (the agent updating the file updates its graph; ontologies and taxonomies).
3. **Use the cloud-function-loads-JavaScript pattern** (a thin, rarely-changed loader; the logic in a JS file iterated from GitHub; edge speed).
4. **Flow data through the JS with the read key** (fetch encrypted files from S3 directly, decrypt, cache immutable ones, build indexes from the graph).
5. **Split cloud function versus Lambda@Edge by capability** (light function for loading and search; Lambda@Edge when calling Bedrock).
6. **Prototype the inline-LLM option** (the LLM builds the graph; question-answering over content; measure the performance hit).
7. **Prototype the client-side alternative** (the client builds the graph; the user pays for search and to talk to content).
8. **Build the serverless route as the enclave** (it holds the read key and secrets the client never sees).

Estimated effort: moderate; the website cloud-function pattern, the vault, the read-key flow, and the semantic graph exist; the contribution is the JS-loader search engine and the two routes. The MVP is website search powered by a per-file semantic graph, served by the cloud-function-plus-JavaScript pattern, with a measured comparison of the serverless and client-side routes and an inline-LLM question-answering trial.

## What This Does Not Try To Be

- **Not database-backed.** File-based, no database, serverless.
- **Not a heavy edge function.** A thin loader; the logic lives in an independently-iterated JS file.
- **Not a stale batch index.** The semantic graph is maintained at write time by the agent.
- **Not committed to one route.** Serverless (the enclave) and client-side (paid) are both prototyped.
- **Not careless with the read key.** The serverless enclave exists so the client need not hold it.

## Honest Risks

**Risk 1: The read key in the function or client is sensitive.** Whoever holds it can decrypt. Mitigation: prefer the serverless enclave so the client never sees it (cross-ref: the ephemeral-compute and public-data briefs); scope the key to what the search needs.

**Risk 2: The inline LLM may be slow or costly.** Calling Bedrock at edge has a performance and cost hit. Mitigation: measure it in the MVP; make the LLM optional; consider client-side and paid usage.

**Risk 3: The JS-loader pattern adds an indirection.** Loading JS to run JS is unusual. Mitigation: it is the source of the benefit (stable function, fast iteration, edge speed); test and document it.

**Risk 4: Per-file graph maintenance must stay correct.** If the agent fails to update a graph, search drifts. Mitigation: make graph update part of the write workflow; schedule or on-update reprocessing as a backstop.

**Risk 5: Client-side exposes more to the user's environment.** The client sees what it processes. Mitigation: the serverless enclave for anything secret; client-side only for what the user is entitled to.
