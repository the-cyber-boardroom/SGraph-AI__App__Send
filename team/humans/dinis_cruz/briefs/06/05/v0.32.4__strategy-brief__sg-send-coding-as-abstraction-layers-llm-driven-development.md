# Coding Is An Abstraction Layer: What Programming Actually Is In The Age Of LLM-Driven Development

**version** v0.32.4
**date** 5 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Strategy, @Dev
**type** Strategy brief

## What This Is

A reflection on what programming actually is, prompted by the confusion behind the claim that we will not need developers any more. The argument: **coding is not giving instructions to a computer; it is creating an abstraction and communication layer between the person and the machine, and LLM-driven development does not remove the coding, it moves the coder up the abstraction stack.** It is the first-person, coding-practice complement to the skill-lifecycle brief (cross-ref: the v0.32.3 skill-lifecycle-explorer-to-town-planner brief, which framed the English-to-code evolution). New contributions: **coding as an abstraction and communication layer, everyone programming but ephemerally, the repeatability-versus-ephemerality distinction, LLM-driven coding moving you up the stack, programming the architecture and design directly, the architect parallel now connected to execution, and recreating your own libraries instead of relying on third-party bloat.**

## The Confusion: "We Will Not Need Developers"

The starting point: **the claim that we will no longer need developers rests on a confusion about what programming actually is.**

The project lead: **"I want to write about what I am experiencing in how I program and how coding actually works, and the confusions that exist, especially with this whole thing of we are not going to need any more developers and coders. I think this is to do with the confusion of what programming actually is."** So the brief sets out to correct a category error. The people predicting the end of developers are imagining programming as the manual typing of low-level instructions, the part LLMs now do well, and concluding the activity disappears. The argument below is that this misunderstands what programming is.

## Coding Is An Abstraction And Communication Layer

The core reframe: **coding is fundamentally the creation of an abstraction layer, a communication layer between the person giving instructions and the computer, not merely the instructions themselves.**

The project lead: **"programming and coding is giving instructions to a computer, a way to codify a bit of logic. But here is an interesting definition: coding is not giving instructions to computers. Coding is creating an abstraction layer, and the communication layer between the human giving instructions and the computer."**

| The Common View | The Reframe |
|-----------------|-------------|
| Coding is giving instructions to a computer | Coding is creating an abstraction and communication layer |
| The output is the instructions | The output is a layer between human intent and machine execution |
| Typing the logic is the work | Codifying logic in a captured, repeatable form is the work |

So coding is not the typing; it is the act of building the layer through which human intent is codified and communicated to the machine in a captured, repeatable way. This reframe is what makes the rest of the argument work: if coding is the abstraction layer, then the part LLMs automate (the manual typing at the bottom) is not the essence of it.

## Everyone Programs, But Ephemerally

A striking observation: **almost everyone already programs, through tools and craft, but ephemerally, because their instructions are not captured or repeated.**

The project lead: **"I always saw people using tools like Excel, Photoshop, Illustrator, a music production studio, and the complexity of what they do is crazy. You could even argue a surgeon, or craftspeople, all of them are programming. The difference is they are doing ephemeral programming, because their instructions are not captured, not repeated. What we do with programming is we are able to do that."**

| Ephemeral Programming | Captured Programming |
|-----------------------|----------------------|
| Excel, Photoshop, a DAW, surgery, craft | Code |
| Enormous complexity, performed live | The same logic, captured |
| Not repeatable; gone when done | Repeatable; runs again |

So the spreadsheet power-user, the designer, the surgeon, the craftsperson are all programming in the sense that they are executing complex, logical sequences of instructions, but ephemerally: the instructions live in the doing and vanish afterwards. What conventional programming adds is capture and repeatability. This recasts programming as a spectrum that most knowledge work already sits on, not a separate priesthood.

## The Distinction Is Repeatability, Not Level

The line that matters, and a sharp one: **the real distinction is not the level of the language but whether the instructions are captured and repeatable, and encoding a workflow is itself programming.**

The project lead: **"you have the lower-level languages, from machine code to assembly to libraries to higher languages, then frameworks, then business rules, then UIs. The confusion is to think one level is the real programming. A user using a UI is still programming. The real question is, where is the line between repeatability and ephemerality? When we simplify things or encode certain workflows, we are programming those actions. I have these primitives, but now I can do them in five steps, so I give you a button to do that."**

So the abstraction stack runs from machine code up through assembly, libraries, higher-level languages, frameworks, business rules, and UIs, and the mistake is to anoint one level as the real programming. Even a person clicking through a UI is programming. The meaningful line is not high versus low; it is captured-and-repeatable versus ephemeral. And encoding a workflow (taking primitives and wrapping them into a button, a five-step shortcut) is programming, because it captures and makes repeatable a sequence that was previously performed by hand. You are always writing on top of other abstractions and other code; the stack is abstractions all the way down.

## LLM-Driven Coding Moves You Up The Stack

The central personal observation, and the answer to the confusion: **LLM-driven development does not remove coding; the coder keeps coding, but higher up the abstraction stack and on several layers at once.**

The project lead: **"the more you get into this new age of LLM-driven coding, where the LLMs write a lot of the manual code, what I found is I am still coding. I am still creating, but I am working at high abstraction layers. What I am not doing is the simple do-this, do-this, do-that, which is what a lot of people are confusing. I am working on multiple layers at the same time."**

| What People Assume LLM Coding Means | What It Actually Is |
|-------------------------------------|---------------------|
| The LLM codes, so the developer disappears | The developer keeps coding, higher up |
| Manual do-this-do-that, automated away | The manual bottom layer automated; the work moves up |
| One layer | Multiple high layers at once |

So the LLM automates the lowest, most manual layer (the do-this-do-that typing), and the result is not that the coder stops coding but that the coder moves up the abstraction stack and works across several high layers simultaneously. This is exactly the skill-lifecycle progression (cross-ref: the skill-lifecycle brief's English-to-code and high-LLM-to-low-LLM) seen from the practitioner's chair: the human operates in intent and abstraction, the LLM fills in the manual code beneath. The activity does not vanish; it relocates upward.

## Programming The Architecture And The Design

A genuinely new capability the project lead reports: **you can now capture and program the architecture and the design directly, with scaffolding, experiments, and validations acting as a new kind of unit test that validates assumptions.**

The project lead: **"I am able to capture, in much more detail than ever before, the architecture decisions. I am able to program the architecture, program the design. I create lots of scaffolding technology, lots of experiments and validations, almost like my unit tests now, meaning full integrations and applications where I can validate a lot of the assumptions. So I am coding high up the stack, but it is not that I am not dealing with technology."**

So a new thing becomes possible: the architecture and design decisions, which used to live in documents and diagrams, can now be captured and programmed directly. And validating them changes shape too: instead of (or alongside) small unit tests, you build scaffolding, experiments, and even full integrations and applications that validate the architectural assumptions. The coder working high up the stack is still very much dealing with technology; they are programming the design itself and testing whether it holds. This is the explorer phase from the skill-lifecycle brief applied to architecture (cross-ref: the skill-lifecycle brief): use the LLM to build and validate the design cheaply.

## The Architect Parallel, Now Connected To Execution

The framing that ties it together: **this is what architects always did, but for the first time the design is directly connected to what gets executed.**

The project lead: **"the big difference is I am programming a couple of levels higher, which is what an architect would always do. Architects in the past were doing this, it is just that there was no direct connection between what they were designing and what actually got executed. So this new paradigm of coding closes that."** So the senior practitioner has always worked at this level, the architect designing the system rather than typing the leaf-level code. What is new is that the gap between design and execution has closed: the architecture you program is directly connected to what runs, rather than being a diagram handed to other people to implement (and reinterpret). The architect can now execute their design directly, which is a qualitative change in what the role can do.

## Recreate Your Own Libraries, Escape The Bloat

The practical payoff, and a power move: **instead of depending on third-party libraries you do not control and that bring bloat, you can use the LLM to recreate and simplify the components you need, and own them.**

The project lead: **"the big difference now is that instead of relying on third-party developers to write libraries that I then use, which I have no control over, which bring a lot of bloat and a lot of stuff I do not want or need, I can recreate them. I use the LLM to recreate that, keep simplifying, and create those libraries and components ourselves, which is a massive power."**

| Third-Party Dependency | Recreated Component |
|------------------------|---------------------|
| No control over it | You own and control it |
| Bloat and unwanted features | Only what you need |
| Someone else's roadmap | Your roadmap |
| A supply-chain and trust burden | A simpler, owned component |

So a concrete consequence of coding at high abstraction with an LLM is that dependencies become a choice rather than a necessity: rather than pulling in a bloated third-party library you do not control, you can have the LLM recreate a simpler, purpose-built version you own. This is the have-your-own-implementations principle from elsewhere in the corpus (cross-ref: the v0.31.9 blast-radius and v0.32.3 living-off-the-land and open-source-not-free briefs) realised in everyday coding: own your components, escape the bloat, control your own stack.

## What This Asks For

1. **Correct the confusion** (programming is not the manual typing the LLM automates; it is the abstraction and communication layer).
2. **Treat coding as the abstraction layer** (between human intent and machine execution; captured and repeatable).
3. **Recognise ephemeral programming everywhere** (tools and craft; the distinction is repeatability, not level).
4. **Work up the abstraction stack with LLMs** (the coder keeps coding, higher up, across multiple layers at once).
5. **Program the architecture and design directly** (capture architecture decisions; scaffolding, experiments, and validations as the new unit tests).
6. **Connect design to execution** (the architect's level, now directly executable; close the design-to-execution gap).
7. **Recreate and own your components** (use the LLM to replace bloated third-party dependencies with simpler owned ones).
8. **Apply this to how the team builds** (the practice that produces the platform: high-abstraction, LLM-driven, owned-component development).

Estimated effort: this is a framing and practice brief, not a build; it informs how the team thinks about and does development. The contribution is the reframe (coding as the abstraction layer) and its consequences (move up the stack, program the architecture, own your components).

## What This Does Not Try To Be

- **Not the end of developers.** The activity relocates up the abstraction stack; it does not vanish.
- **Not just instructions.** Coding is the abstraction and communication layer.
- **Not a claim that one level is the real programming.** The distinction is repeatability versus ephemerality.
- **Not LLMs replacing the coder.** The LLM fills the manual layer; the coder works higher up.
- **Not dependency on third-party bloat.** Recreate and own the components you need.

## Honest Risks

**Risk 1: High-abstraction coding still needs deep technical judgement.** Working up the stack is not easier; it requires more architectural skill. Mitigation: this is a senior-practitioner activity; pair high-abstraction work with the validation scaffolding that proves the assumptions.

**Risk 2: Recreating libraries can reintroduce work and bugs.** Owning components means maintaining them. Mitigation: recreate only what bloat or lack of control justifies; LLMs make recreation and simplification cheap; the owned component is simpler and purpose-built.

**Risk 3: The confusion is widespread and persistent.** Many will keep believing programming is going away. Mitigation: the abstraction-layer framing and the ephemeral-programming observation are clear, teachable counters.

**Risk 4: Programming the architecture can outrun validation.** Designing fast without validating assumptions is risky. Mitigation: the scaffolding, experiments, and full-integration validations are the new unit tests; validate the assumptions, not just the leaf code.
