# Public Data In Vaults: Serving Unencrypted Content And A Front End To A Vault

**version** v0.32.4
**date** 5 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, @Dev
**type** Dev brief

---

## What This Is

A building block that deliberately and explicitly breaks the default security model for a scoped purpose: **letting a vault hold and serve public, unencrypted data through a new GS API endpoint, so a vault can have a front end and serve public pages and objects directly, without the decryption loop.** It generalises something already built (the Lambda@Edge function that serves decrypted page content for LLMs, and the public page that drives link-preview cards) into an official capability, and it pairs naturally with the public key register, whose data is already public (cross-ref: the v0.32.4 PKI-public-key-registry-on-vaults brief). New contributions: **the explicit public-data exception, a GS API endpoint for editing and serving public data with the write key but no read key, the leak-the-read-key versus serve-directly choice, and a front end to a vault without exposing everything.**

## Breaking The Security Model On Purpose

The framing, stated plainly and deliberately: **there is a case for public data in a vault, meaning unencrypted data, and we should make that exception explicit rather than implicit.**

The project lead: **"this is an interesting example of we are going to break the security model here, but on purpose, and I am going to make it very explicit. There is a case where there is going to be some public data in the vault, and by this I mean there is unencrypted data."**

| The Default Model | The Explicit Public-Data Exception |
|-------------------|-------------------------------------|
| Zero-knowledge; everything encrypted | Specific data deliberately designated public |
| Read requires the read key to decrypt | Public data needs no decryption to read |
| Nothing served in the clear | Public pages and objects served directly |

So this is a conscious, scoped exception, not a weakening of the default. The zero-knowledge model stays the default for everything private; certain data is explicitly marked public (unencrypted), and the value is that it can be served directly. Making the exception explicit is the whole point: you always know exactly what is public and what is not.

## The Precedent: Serving Decrypted Content Without The Full Loop

This is not new ground; a variation already runs: **a Lambda@Edge function already serves decrypted page content (llms.txt, .md, .json) directly, and a public page already drives link-preview cards.**

The project lead: **"we did a variation of this. There is a public thing we added to the GS API that allows those cards to occur on LinkedIn and other places. And on the SGraph website, we wanted to add llms.txt and the ability to get .md and .json content from the pages, because they are much easier for LLMs to process. So we created a simple Lambda@Edge function that decrypts the content and sends it back as static. It is a way to send the decrypted content back to the client without a full encryption loop, which is exactly what we want in that case."**

| Existing Capability | What It Does |
|---------------------|--------------|
| Public link-preview cards | A public endpoint so LinkedIn and others can render cards |
| Lambda@Edge for llms.txt, .md, .json | Serves decrypted page content directly for LLM consumption |
| The pattern | Send decrypted or public content back without the full encryption loop |

So the team already serves content without the round-trip decryption loop, for good reasons (LLM-friendly formats, social cards). This brief makes that an official, general capability rather than a set of one-off functions.

## The Proposal: A GS API Endpoint For Public Data

The concrete ask: **add a new GS API endpoint that edits and serves public data in the vault, gated by the write key, but needing no read key because there is nothing to decrypt.**

The project lead: **"add a new endpoint to the GS API, and what this endpoint allows is the edit of public data in the vault, also using the right key. You still need the right key, but this is data that will be publicly available, so you do not need the read key, because you do not need to decrypt it."**

| Operation | Key Required |
|-----------|--------------|
| Edit public data | Yes, the write key (still gated) |
| Read public data | No read key (nothing to decrypt) |

So writing public data is still authorised by the write key (you cannot just publish into someone's vault), but reading it requires no key at all, because it is already in the clear. This keeps control over what becomes public (only the key holder can publish it) while making the published result openly fetchable.

## Two Approaches: Leak The Read Key, Or Serve Directly

A design choice the project lead draws out: **you could simply leak the read key on a public page, or, better, serve the public content directly without leaking any key.**

The project lead: **"why do not we have some public pages that contain that logic, where we can leak on purpose the read key. But this would be a way to do that without leaking the read key, which lets us serve those pages directly without the complexity, and have a bit more UI. So maybe we just add an API to support it, and we just leak the read key, but this would be a way to do it without leaking the read key. This would be a way to add a front end to a vault without leaking everything."**

| Approach | Trade-off |
|----------|-----------|
| Public page that leaks the read key | Simple, but exposes a key and risks more than intended |
| Serve public content directly (no key leak) | The public data is unencrypted and served as-is; no key exposed; the preferred route |

So the cleaner approach is to store the genuinely-public data unencrypted and serve it directly, rather than handing out a read key that might unlock more than intended. The endpoint serves only what is explicitly public, so adding a front end to a vault does not leak everything else in it.

## Use Cases

Where this is needed (cross-ref: the PKI registry and publishing briefs):

| Use Case | Why Public Data Fits |
|----------|----------------------|
| **The public key register** | Its data is already all public; serve its pages directly (cross-ref: the PKI registry brief) |
| **The SGraph website** | Public website content served from a vault |
| **A front end to a vault** | Public HTML pages and UI without exposing the private contents |
| **Public objects** | Fetchable directly from a browser without decryption |

The project lead: **"the public key register, when I said all the data is available, then I am okay to share all the data. Or the data from the SGraph website. I could have a set of public pages. There is a need to have public HTML pages, public stuff that can be fetched, public objects fetched directly from a browser without the decryption bit, and a front end to a vault without leaking everything."** So the public key register is the cleanest fit (it is public by design), and the same capability gives any vault a public face: a website, a front end, fetchable public objects, served directly.

## Public Content Stored In The Vault, Cloned And Mapped

A property worth keeping: **the public content lives inside the vault and is cloned and mapped like the rest of it.**

The project lead: **"there is a need to have a public set of content for a vault that is stored in the vault inside of it, and something that gets cloned and gets mapped."** So public data is not a separate system; it sits inside the vault alongside the encrypted data, clearly marked as public, and inherits the vault's distribution (cloned and mapped, run anywhere; cross-ref: the publishing-mode and platform-of-primitives briefs). One vault holds both its private encrypted content and its explicitly-public content, and the new endpoint serves the public part.

## What This Asks For

1. **Make the public-data exception explicit** (some vault data is deliberately unencrypted and public; the default stays zero-knowledge).
2. **Add a GS API endpoint for public data** (edit gated by the write key; read needs no key).
3. **Generalise the existing functions** (the Lambda@Edge decrypted-content server and the cards page become one official capability).
4. **Prefer serving directly over leaking the read key** (store public data unencrypted; do not hand out a key that unlocks more than intended).
5. **Serve the public key register's pages directly** (its data is already public; the cleanest first use case; cross-ref: the PKI registry brief).
6. **Enable a front end to a vault** (public HTML, UI, and objects fetchable from a browser, without exposing the private contents).
7. **Keep public content inside the vault** (marked public; cloned and mapped like the rest).
8. **Map the security explicitly** (what is public, who can publish it, what is never served in the clear).

Estimated effort: small-to-moderate, the pattern already runs as one-off functions; the work is the official endpoint, the public-data marking, and the security mapping. The MVP is the public key register served directly through the new endpoint, plus a simple public front end for one vault, with the private contents untouched.

## What This Does Not Try To Be

- **Not a weakening of the default.** The zero-knowledge model stays the default; this is an explicit, scoped exception.
- **Not for private data.** Only data deliberately designated public is served unencrypted.
- **Not a read-key handout.** The preferred route serves public content directly, leaking no key.
- **Not ungated writing.** Publishing public data still requires the write key.
- **Not a separate system.** Public content lives inside the vault, cloned and mapped.

## Honest Risks

**Risk 1: Public data is, by definition, exposed.** Anything marked public is readable by anyone. Mitigation: the exception is explicit and scoped; only deliberately-public data is served; map the security clearly.

**Risk 2: The leak-the-read-key option can over-expose.** A leaked read key may unlock more than intended. Mitigation: prefer serving public content directly; if a key is ever exposed, scope it to only public content.

**Risk 3: Mislabelling private data as public.** A mistake here exposes private content. Mitigation: explicit marking, write-key gating, and review of what is published; clear separation of public and private within the vault.

**Risk 4: A public face widens the attack surface.** A front end and public endpoint are reachable by anyone. Mitigation: the endpoint serves only public data and never decrypts; writing stays key-gated; standard web hardening.
