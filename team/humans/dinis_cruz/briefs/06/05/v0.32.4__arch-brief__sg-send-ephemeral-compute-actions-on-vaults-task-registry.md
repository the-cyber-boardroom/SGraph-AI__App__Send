# Ephemeral Compute For Actions On Vaults: A Task Registry And The Secret Problem

**date** 5 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, @Dev

## What This Is

A need surfaced by the public key register and the wider vault work: **some actions need to be performed on a vault by a trusted party, which calls for compute that acts on vaults, ideally ephemeral compute, plus a place to register the tasks to be executed.** It is the compute counterpart to the PKI registry building block (cross-ref: the v0.32.4 PKI-public-key-registry-on-vaults brief) and generalises something already in the corpus (cross-ref: the v0.31.12 publishing-mode-via-GitHub-Actions brief, where ephemeral CI compute already acts on a vault). This is a mapping brief: the pieces largely exist, and the ask is to design the architecture and run a couple of MVPs and experiments. New contributions: **the need for compute that acts on vaults, the ephemeral start-run-destroy pattern, the secret-handling problem and its mitigation, and a task registry for vault actions.**

## The Need: Compute That Acts On Vaults

The starting point: **now that there are many vaults and a public key register, some actions need a trusted party with compute to perform them on a vault.**

The project lead: **"an interesting need has appeared from the idea that we have vaults, and the public register or PKI register: we now need some compute to do some actions on vaults. There are cases where you need a trusted party that does some actions on the vault. A good example is vault registrations and maintenance, and inbox processing, for example how do we regularly get a vault to process its inbox?"**

| Action On A Vault | Why It Needs Compute |
|-------------------|----------------------|
| Vault registration | Registering a key or vault into the public register (cross-ref: the PKI registry brief) |
| Maintenance | Regular upkeep on a vault |
| Inbox processing | Regularly getting a vault to process its inbox (cross-ref: the vault-to-vault-comms brief) |

So the vaults and the register are largely passive stores; some operations (registering, maintaining, processing an inbox) require something to actively run and act on the vault. That something is compute, performed by a trusted party. This brief is about how that compute should work.

## The Ephemeral Compute Pattern

The proposed approach: **start ephemeral compute, run the task in a container, and destroy it, a disposable, live-off-the-land pattern.**

The project lead: **"this could be done using our ephemeral compute. One interesting way is to start ephemeral compute, have a container that runs the thing, and it gets destroyed. That is not a bad way."** So the pattern is disposable compute: spin up a container, run the task against the vault, tear it down. Nothing persistent holds standing access. This is the same shape as the existing publishing flow (cross-ref: the publishing-mode-via-GitHub-Actions brief, where an ephemeral CI runner acts on a vault and disappears) and fits the live-off-the-land and run-anywhere principles (cross-ref: the v0.32.3 NHI-2.0-living-off-the-land and v0.31.12 vault-as-platform-of-primitives briefs). The ephemerality is not incidental; it is the main security property, because the compute exists only for the task and then is gone.

## The Secret Problem, And Why Ephemerality Mitigates It

The honest hard part, and a direct link to the accountability work: **the compute needs a secret or key to act on the vault, there will always be a big secret, but ephemeral, scoped provisioning mitigates it.**

The project lead: **"it is just a case of giving secrets. We might need an Uber key, a key or public key or private key that allows the decryption of some things, so we need to think about that. There is always going to have to be a big secret, but we can mitigate it."** (The transcript's Uber key reads as the over-privileged master key, the Uber identity concept; cross-ref: the living-off-the-land brief.)

This is the provisioning problem from the articles, in miniature: to act on a vault, the ephemeral compute must be given a secret, and concentrating decryption power in one place is exactly the over-privileging that the accountability-at-provisioning argument warns about (cross-ref: the v0.32.4 hope-driven-development and second-story articles, and the v0.32.3 NHI-2.0-PKI-foundations brief). The mitigation is the same as the prescription in those pieces:

| The Risk | The Mitigation |
|----------|----------------|
| A big, standing secret with broad decryption power | Make it ephemeral: created for the task, destroyed after |
| One Uber key for everything | Scope the key to the specific vault and action |
| Persistent privileged compute | Per-task, just-in-time, time-bounded compute |
| Unaccountable access | Provenance on what the compute did and with what |

So the secret is unavoidable, but its danger is a function of scope and lifetime. Give the ephemeral compute the one key for the one task, briefly, scoped to the specific vault and action, and destroy both the compute and (where possible) the credential afterwards. The big secret becomes a small, short-lived one. This is the one-key-for-one-task principle applied to compute acting on vaults.

## A Task Registry For Vault Actions

The piece to build: **a place to register a task that will be executed on a vault to perform a particular action.**

The project lead: **"the idea is that we need a place where we can register a kind of task that will be executed in a vault to do a particular action on that vault. That is the bit we need to catch up on."** So alongside the compute pattern, there is a registry of tasks: a declared task says, in effect, run this action on this vault, under these conditions. The ephemeral compute picks up a registered task, provisions the scoped secret for it, runs it, and is destroyed. The task registry is the control point: it is where what-runs-on-which-vault is declared, scheduled, and made auditable, and it pairs naturally with the public key register (cross-ref: the PKI registry brief) as the place that knows which keys and identities a task may use.

## We Have The Pieces: Architecture, MVPs, Experiments

The framing of the work: **most of the pieces exist; the task is to design the architecture and prove it with a couple of MVPs and experiments.**

The project lead: **"we already have a bunch of needs for this, so let's map how this is going to work. We have a lot of the pieces of the puzzle, we just need to create the architecture and do a couple of MVPs and experiments to see how it could work in practice."** So this is not a from-scratch build: ephemeral compute exists, the vault and register exist, the publishing flow already demonstrates ephemeral compute acting on a vault. The work is to design the architecture that ties them together (the task registry, the scoped-secret provisioning, the ephemeral runner) and to validate it with small MVPs and experiments before committing, exactly the explorer-phase, scaffolding-and-experiments approach (cross-ref: the v0.32.4 coding-as-abstraction-layers brief).

## What This Asks For

1. **Design compute that acts on vaults** (a trusted party performing registration, maintenance, inbox processing).
2. **Use the ephemeral start-run-destroy pattern** (a container that runs the task and is destroyed; live-off-the-land; the publishing-flow shape).
3. **Scope and shorten the secret** (the unavoidable big secret made small and short-lived; one key for one task; just-in-time; destroyed after).
4. **Provision per the accountability principle** (scoped to the vault and action; provenance on what ran with what; cross-ref: the articles and foundations brief).
5. **Build a task registry** (a place to register the task to be executed on a vault; the control and audit point).
6. **Pair it with the public key register** (which keys and identities a task may use; cross-ref: the PKI registry brief).
7. **Architect, then MVP and experiment** (assemble the existing pieces; validate in practice before committing).

Estimated effort: moderate and exploratory; the compute, the vault, the register, and a working ephemeral-compute-on-vault example all exist; the contribution is the architecture that connects them and the task registry. The MVP is one registered task (for example, process a vault's inbox) executed by an ephemeral container with a scoped, short-lived secret, then destroyed, with provenance.

## What This Does Not Try To Be

- **Not persistent privileged compute.** Ephemeral: started, run, destroyed.
- **Not one Uber key for everything.** Scoped, short-lived secrets, one task at a time.
- **Not a finished design.** A mapping brief; the architecture and MVPs come next.
- **Not the vault's own job.** A trusted party with compute acts on the vault.
- **Not unaccountable.** The task registry and provenance record what ran, on what, with what.

## Honest Risks

**Risk 1: The secret is a real concentration of privilege.** Compute that can decrypt vault data is powerful. Mitigation: scope to the vault and action, make it ephemeral and just-in-time, destroy after, keep provenance (cross-ref: the accountability articles and foundations brief).

**Risk 2: Ephemeral compute can still be compromised while running.** The window is short but not zero. Mitigation: minimal scope, short lifetime, isolation, and the dangerous-trifecta discipline (limit what the runner can reach; cross-ref: the multiple-identities-chain brief).

**Risk 3: A task registry becomes a high-value target.** It controls what runs on vaults. Mitigation: the registry declares tasks but does not hold standing secrets; secrets are provisioned per run; pair with the key register's trust model.

**Risk 4: This is under-specified today.** The design is not yet settled. Mitigation: that is the point; architect, then MVP and experiment before committing.
