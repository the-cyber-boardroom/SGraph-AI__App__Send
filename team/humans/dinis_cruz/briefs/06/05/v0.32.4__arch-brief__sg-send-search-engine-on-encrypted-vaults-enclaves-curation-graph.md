# A Search Engine For Encrypted Vaults: Secure Enclaves, Three Parts, And A Curation Graph

**version** v0.32.4
**date** 5 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, @Dev
**type** Arch brief

## What This Is

A plan and architecture for adding search to vaults, where the data is encrypted: **search over confidential data, run in secure enclaves on ephemeral compute, built in three parts (an indexer, an index store and responder, and a curation graph that defines what may be searched at all).** It turns the limitation of searching encrypted data into an advantage through fractal search services and explicit curation. It builds directly on the ephemeral compute building block (cross-ref: the v0.32.4 ephemeral-compute-actions-on-vaults brief) and the semantic-graph foundation (cross-ref: the v0.32.3 NHI-2.0-semantic-knowledge-graphs brief). New contributions: **searching encrypted data via secure enclaves, the three-part architecture, the curation graph as the universe of searchable data, search-of-searches, and curation as the answer to agentic over-access.**

## The Challenge: Searching Encrypted Data

The problem, and the reframe: **encrypted data stores are hard to search, but that limitation can be turned into an advantage with a fractal set of search services.**

The project lead: **"one of the challenges when you have encrypted data and encrypted data stores is how do you search. But I think we can turn this limitation into an advantage by creating a fractal element of search services."** So rather than treating encryption as an obstacle to search, the architecture makes search a set of fractal, composable services that run where the data can be safely decrypted, and that are explicitly scoped by curation (below). The constraint forces a design that is more controlled and more auditable than a conventional search index over plaintext.

## Secure Enclaves On Ephemeral Compute

Where the search runs: **in secure enclaves, on the ephemeral compute the project already has, using technology such as AWS Nitro Enclaves.**

The project lead: **"this goes into creating secure enclaves, which we already have a place to do, because we have OSG compute that lets us spin that up, even ephemeral, and these days AWS has technology like AWS Nitro and others."** So the indexing and search compute runs in secure enclaves spun up on the ephemeral compute (cross-ref: the ephemeral-compute brief), torn down after use, with enclave technology (AWS Nitro Enclaves and similar) providing isolation for the moment the data is in the clear. This is the ephemeral, scoped-secret pattern from the compute brief applied to search: the enclave gets access for the task and is destroyed, so there is no standing service sitting on decrypted data.

## The Three Parts

The architecture has three distinct components, with deliberately different access:

### Part 1: The Indexer

**Compute that catalogues and indexes everything, and therefore needs access to the most data.**

The project lead: **"we need the compute that is going to index everything, catalogue everything, and this is the one that needs to have access to most of the data."** So the indexer is the most privileged component: to build an index it must read the content. This is exactly why it runs in an ephemeral secure enclave, scoped to the curated universe (Part 3), and destroyed after indexing, so the broadest access exists only briefly and in isolation.

### Part 2: The Index Store And Responder

**A real-time service that stores, manages, and responds to the indexes, and is itself sensitive.**

The project lead: **"there is the one that stores the indexes, manages the index, responds to the indexes. This is a service used in real time that also has access to quite a bit of sensitive data, because it has indexes. It might not have the whole document, but the more we move into semantic knowledge graphs, which is what search should be based on, the more we fundamentally have all the content."** So the index store is a live service, and it is sensitive even though it holds indexes rather than whole documents, because a rich enough index (especially a semantic-graph index; cross-ref: the semantic-knowledge-graphs brief) effectively contains the content. It must therefore be treated as sensitive and scoped by the same curation.

### Part 3: The Curation Graph

**The component that selects what data is searched at all, defining the universe the other two operate on, and this is the most important and most novel part.**

The project lead: **"then you have the bit where you select the data that is being searched, and this is where it is interesting. A lot of the agentic memory and copilot products, and the horror stories of agents having access to far more data than they are supposed to, is because they never curated. The universe and the graph that the first two operate on is defined by this. There is a data-collection node where you define what you want to search on."**

| Without Curation | With The Curation Graph |
|------------------|--------------------------|
| The index covers whatever it can reach | The index covers only the curated universe |
| Agents access far more than intended | Access is scoped to what was deliberately selected |
| No record of why something is searchable | Provenance on what is indexed and why |

So the curation graph is the control point: it defines, explicitly, the universe of data that the indexer and the index store are allowed to operate on. This is the direct answer to the agentic over-access problem (the copilots and memory systems that quietly index everything and then surface data they should never have touched), which is the data-access cousin of the over-provisioning problem (cross-ref: the v0.32.4 accountability articles and the v0.32.3 NHI-2.0-permission-granularity brief): you do not let the indexer reach everything; you curate what it may reach.

## Search-Of-Searches: The Search Index Is Itself A Graph

The structural insight: **the curation, the search mapping itself, is a graph, and searches can compound other searches, so the search index is a graph in its own right.**

The project lead: **"even the search mapping should be a graph. You can have search of searches, searches that compound other search blocks, so even the search index becomes a graph in itself, and that is what allows a lot of provenance and control of what is actually indexed and searched."**

| Property | What It Gives |
|----------|---------------|
| The search mapping is a graph | The searchable universe is explicit and navigable |
| Search of searches (compound search blocks) | Searches built from other searches; fractal and composable |
| Provenance | A record of what is indexed and searched, and why |
| Control | Precise scoping of the searchable universe |

So the curation graph is not a flat allowlist; it is a graph in which searches compose other searches (search of searches), making the searchable universe fractal and composable, and making provenance and control first-class. You can see exactly what a given search can reach and why, because it is all in the graph. This is the same everything-is-a-graph principle the corpus keeps returning to (cross-ref: the semantic-knowledge-graphs and PKI-registry briefs), now applied to search itself.

## The Payoff: A Proper Search Engine On Confidential Data

What it adds up to: **a proper search engine over confidential data, served by a simple service or serverless function once the curation, indexing, and store are in place.**

The project lead: **"from there we have the ability to search based on this, and all you need is a service running, or serverless, that has this data, and then we can implement a proper search engine on top of confidential data."** So once the curation graph defines the universe, the enclave indexer builds the index, and the index store responds, the actual search interface is a simple service or serverless function. The hard and valuable parts are the secure-enclave indexing and the curation graph; the search endpoint on top is straightforward. The result is real search over encrypted, confidential data, with provenance and curation built in, which is something most systems cannot offer safely.

## What This Asks For

1. **Build search for encrypted vaults** (turn the limitation into an advantage; fractal search services).
2. **Run indexing and search in secure enclaves** (on ephemeral compute; AWS Nitro Enclaves and similar; destroyed after; cross-ref: the ephemeral-compute brief).
3. **Build the indexer** (catalogues and indexes; the most data access; ephemeral and scoped).
4. **Build the index store and responder** (real-time; treat as sensitive; semantic-graph indexes effectively hold the content).
5. **Build the curation graph** (select what may be searched; the universe the other parts operate on; the answer to over-access).
6. **Make the search mapping a graph** (search of searches; compound blocks; provenance and control).
7. **Serve search with a simple service** (a service or serverless function on top, once curation, indexing, and store exist).
8. **MVP and experiment** (prove enclave indexing and the curation graph on one vault).

Estimated effort: substantial but well-grounded, the ephemeral compute, the secure-enclave capability, and the semantic graph exist; the contribution is the three-part architecture and the curation graph. The MVP is one vault's curated universe, indexed in an ephemeral enclave, with a simple search endpoint, and provenance on what was indexed.

## What This Does Not Try To Be

- **Not plaintext search.** The data is encrypted; search runs in secure enclaves.
- **Not a standing service on decrypted data.** Ephemeral enclaves, destroyed after indexing.
- **Not index-everything.** The curation graph defines the universe; over-access is the failure mode it prevents.
- **Not a flat allowlist.** The search mapping is a graph; search of searches; provenance and control.
- **Not a finished design.** A plan and architecture; MVPs and experiments come next.

## Honest Risks

**Risk 1: The indexer is the most privileged component.** It reads the content to index it. Mitigation: run it in an ephemeral secure enclave, scoped to the curated universe, destroyed after; the curation graph bounds what it touches.

**Risk 2: Rich indexes effectively hold the content.** A semantic-graph index is sensitive. Mitigation: treat the index store as sensitive as the data; scope by curation; isolate and control the responder.

**Risk 3: Curation can be set too wide.** Over-broad curation reintroduces over-access. Mitigation: explicit, reviewable curation graph; provenance on what is searchable and why; start narrow.

**Risk 4: Enclaves are not magic.** Enclave technology has its own assumptions and limits. Mitigation: ephemerality and scoping reduce exposure; treat the enclave as one layer, not the whole answer.

**Risk 5: Under-specified today.** The design needs proving. Mitigation: MVP the enclave indexer and the curation graph on one vault before scaling.
