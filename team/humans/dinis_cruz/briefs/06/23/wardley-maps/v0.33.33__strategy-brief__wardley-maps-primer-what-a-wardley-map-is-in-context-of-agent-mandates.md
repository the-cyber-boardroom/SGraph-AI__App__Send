# A Primer: What A Wardley Map Is, In The Context Of Agent Mandates

**version** v0.33.33
**date** 23 June 2026
**from** Human (project lead)
**to** All readers new to Wardley maps
**type** Strategy brief (primer)

---

## What This Is

A short primer for readers who do not know Wardley maps, so the agent mandate map series can be read by everyone: **a Wardley map plots the chain of things needed to meet a user need against how evolved each of those things is, with the user need at the top, the components it depends on arranged below by how visible they are to the user, and every component positioned left to right by its evolution from genesis through custom-built and product to commodity; you read it from the top down to see what the user sees and what it rests on, and from left to right to see what is still novel and custom versus what is mature enough to consume as a commodity, and because components drift rightward over time you can also read movement; in the context of agent mandates it is anchored at a need such as the exec's need to use AI safely or the agent's need to act, with components like authorization, controls, evidence, and execution placed by maturity, and it is most useful for showing where something feels like a product but is actually weak and custom-built behind the scenes.** It is the companion to the Wardley maps brief (cross-ref: the v0.33.33 Wardley-maps brief and the v0.33.32 agent-mandate-graph brief).

## Why A Map, Not Just A Diagram

A diagram shows boxes and lines. A map adds two things a diagram lacks: an anchor in a real user need, and a position for every component that says how evolved it is. Those two additions are what let a map tell you not just what exists, but what to do about it.

## The Two Axes

- **The vertical axis is the value chain, by visibility to the user.** The user need sits at the top. Below it sit the things it depends on, and below those the things those depend on, down to the foundations the user never sees.
- **The horizontal axis is evolution.** Every component is placed along: genesis, the novel and uncertain; custom-built, made by hand for the case; product or rental, repeatable and bought; and commodity or utility, standardised and taken for granted.

```
  visible to user
        ^
        |  [user need]
        |     |
        |  [component]      [component]
        |        |              |
        |  [component]   [component]   [component]
        |
        +-------------------------------------------> evolution
          genesis    custom-built    product    commodity
```

## How To Read It

Read top to bottom to see what the user needs and what it rests on. Read left to right to see maturity: components on the left are still being figured out and are usually custom and fragile, while components on the right are standardised and are usually better consumed than built. The same component tends to move rightward over time as it matures, so a map is also a picture of motion.

## Why It Helps

A map shows where to focus. It tells you what to build, because it is genuinely novel, and what to buy, because it is already a commodity. Most usefully, it exposes the gap between how something feels and what it is: a capability can feel like a finished product to the user while being, behind the scenes, custom-built and weak. In the agent mandate landscape the clearest example is hope-driven authorization, which presents as a working capability but is genesis or custom-built underneath.

## A Little Doctrine

Wardley mapping comes with a few universal principles worth stating: start with user needs, be pragmatic, challenge assumptions, manage inertia, the pull of the way things have always been done, and use common language so everyone reads the same map. The first of these, start with user needs, is the rule the whole map series follows.

## The Agent Mandate Reading

For our purposes a map is anchored at a need such as the exec's need to use AI safely, or the agent's own need to ask for, receive, and check permissions, make decisions, validate controls, and execute. The supporting components, the mandate, the authorization, the controls, the evidence, and the execution, are placed by maturity, and the map is drawn twice, once as reality today and once as the picture with our service, so the gap between them is visible.

## A Note On Drawing Them

A Wardley map is a graph with position: every component is a node, every dependency is an edge, and the two extra facts per node are evolution position and visibility. So we author these maps text-first in the vault, in the same graph as the agent mandate ontology, and then visualise them, which means a map query is just a graph query (cross-ref: the agent-mandate-graph brief).
