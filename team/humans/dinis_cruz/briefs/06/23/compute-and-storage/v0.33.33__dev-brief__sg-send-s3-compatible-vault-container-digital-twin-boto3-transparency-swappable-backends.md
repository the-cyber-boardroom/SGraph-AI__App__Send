# The S3-Compatible Vault Container: A Digital Twin That Serves Vault Files as S3

**version** v0.33.33
**date** 23 June 2026
**from** Human (project lead)
**to** @Dev, Architect, SG Compute
**type** Dev brief

---

## What This Is

A Docker container for the SG compute service that lets an existing service keep talking to S3 while the files actually come from a vault: **the container is a digital twin of S3, presenting the same S3-compatible API, so that code using boto3, the AWS CLI, or any S3 SDK believes it is talking to real S3, while the files are served from a vault, from local disk, or from memory, chosen as a swappable backend; the service's own code does not change, the redirection is transparent, achieved by pointing the S3 endpoint at the container; the AWS credential fields are reused to carry the container's header name and value for compatibility; and most of the code exists already.** It packages, for SG compute, the existing S3-compatible API with full boto3 transparency (cross-ref: the v0.27.2 S3-compatible-API brief, the v0.27.43 SG-compute container-hosts brief, and the v0.33.32 potential-mandate brief on transparent, out-of-band redirection). New contributions: **the Docker-for-SG-compute packaging, the swappable vault, disk, and memory backends, and the credential-to-header mapping.**

## The Situation

The problem to solve: **change where the files come from, without changing the code.**

The project lead: **"I have a service that uses an S3 bucket to retrieve some files, and I want to change the location, to serve the files from local disk, or in this case from a vault, eventually from a vault, without changing the code of the service."** So the goal is to keep an existing, working service exactly as it is, and only change where its files actually come from.

## The Digital Twin

How it works: **it looks like S3, and the code cannot tell.**

The project lead: **"we have a digital twin already built for S3, which has the same S3-compatible API, that is going to look like S3 to code that thinks it is accessing S3 via boto3, but it returns those files from the vault. The point is that the code should not know it is actually not talking to S3."** So the container is a digital twin of S3: a boto3 client, the AWS CLI, or any S3 SDK pointed at it behaves exactly as it would against real S3, and the non-negotiable requirement is that the calling code has no idea it is not talking to AWS.

## The Swappable Backends

What sits behind the twin: **vault, disk, or memory.**

The project lead: **"by getting it from the vault, we should also support just getting from disk, or getting from memory, so we should support multiple workflows."** So the same S3-compatible front presents a choice of backends: the vault, which is the eventual point of the exercise; local disk; and memory. The S3 interface stays identical while the source of the bytes is selected behind it.

## The Transparency Mechanism

How the redirection is made invisible: **repoint the endpoint, reuse the credentials.**

The service keeps using boto3 unchanged; only the S3 endpoint is pointed at the container instead of AWS. For compatibility and auth, the AWS credential fields are reused: the project lead notes that **"we could probably use the AWS API key and value as, in our case, the header name and the header value."** So the AWS access key becomes the container's header name and the secret becomes its header value, which keeps the standard S3 client happy while carrying whatever the container needs to authenticate and route the request. This is transparent, out-of-band redirection: no code cooperation is required from the service, in the same spirit as distributing a credential rather than asking the code to change (cross-ref: the potential-mandate brief).

## Packaging For SG Compute

What ships: **a container, mostly already built.**

The project lead: **"this is to add a Docker container to the SG compute service, and I believe I already have most of the code for this."** So the deliverable is a Docker container added to the SG compute service, packaging the existing S3-compatible API and the backend selection into a service that SG compute can run.

## Why This Matters

The payoff: **the vault becomes a drop-in S3 backend.**

Any service that already speaks S3, and almost everything does, can be served from a vault with no code change at all: point its endpoint at the container, choose the vault backend, and the service runs unchanged while its files now come from, and can be governed in, the vault. This turns the vault into a transparent storage backend for the entire S3 ecosystem, and it does so out of band, without touching the consuming code, which is exactly the property that makes it easy to adopt.

## Acceptance Criteria

1. A Docker container runs in the SG compute service and presents an S3-compatible API.
2. A boto3 client, the AWS CLI, or any S3 SDK works against it without modification.
3. The container serves files from a selectable backend: vault, local disk, or memory.
4. The existing service's code does not change; only the S3 endpoint is repointed.
5. The AWS API key and value are reused as the container's header name and header value.
6. The vault backend serves vault files transparently as S3 objects.
7. The calling code cannot tell it is not talking to real S3.

## What This Does Not Try To Be

- **Not a code change.** The consuming service is untouched.
- **Not S3-only behind the scenes.** The backend is vault, disk, or memory.
- **Not a new client.** It works with the standard S3 SDKs.
- **Not in-line in the agent sense.** It transparently redirects storage, out of band.

## Honest Tensions

**Tension 1: the S3 API surface is large.** Full transparency means covering the operations clients actually use. Mitigation: the S3-compatible API already exists and targets boto3 transparency; extend coverage as needed.

**Tension 2: performance from a vault backend.** A vault read may differ from an S3 read in latency. Mitigation: the memory and disk backends exist for hot paths, and caching can sit behind the twin.

**Tension 3: the auth mapping is a reuse, not a standard.** Carrying header name and value in the AWS credential fields is pragmatic. Mitigation: document it clearly, and keep the standard client behaviour intact.
