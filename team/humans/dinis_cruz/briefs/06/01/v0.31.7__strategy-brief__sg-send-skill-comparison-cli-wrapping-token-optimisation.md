## What This Is

A further expansion of the skills work (cross-ref: the v0.31.7 skill-base-vaults, skills-marketplace, skills-graph, and skills-as-opinionated-expertise briefs), adding three genuinely new points: **(1) the "which skill is best?" comparison problem and the comparison vault that answers it; (2) the pain point of wrapping a CLI or tool so an agent can use it, easily and with tests, in a sandbox; and (3) token optimisation as a distinct dimension of skill customisation.** The marketplace, scoring, semantic graph, and customisation are already documented; this brief concentrates on what is new.

## The Problem: Skills Are Everywhere, So Which One Is Best?

The sharp new framing: **there are many skills repositories, the same skill exists in many places, and the unanswered question is which one is best, best-suited for me, and what is the evidence.**

The project lead: **"there are a bunch of skills repositories. You have multiple skills in multiple places. The interesting question is which one is the best, and what's the evidence? There's ten of these, which one is better, which is better suited for me, how do you solve that problem?"** This is more specific than the marketplace's general scoring (cross-ref: the marketplace brief): it is the **comparison** problem. A user does not just want a score per skill; they want to know, among the ten implementations of the skill they need, which one is best *for them*, with the evidence.

This is a strong use case for the capabilities already built:

| Capability | Role In The Comparison |
|------------|------------------------|
| **A quick LLM to talk to** | The user asks questions about the candidates (cross-ref: the vault-chat brief); the project lead noted this is a good example of a vault that benefits from a quick LLM to talk to |
| **Semantic knowledge graphs** | Map the skills, their capabilities, and how they relate (cross-ref: the skills-graph brief) |
| **A logic / formula / framework** | Apply a specific framework to determine the correct skill/capability for the need |
| **Spin up environments** | Run the candidates to gather evidence (cross-ref: the Daytona brief) |
| **Provenance and explainability** | Show why this skill is the right one, with evidence (cross-ref: the marketplace and base-vault briefs) |

The project lead: **"by using semantic knowledge graphs, by applying a logic, a formula, a specific framework, that's how you map out what is the correct skill, the correct capability, the correct thing I need. We know how to talk to multiple skills, spin up multiple environments, collect the data, and expose that to the user."** So the comparison is the evidence-driven discovery loop (cross-ref: the visualisation-cornerstone brief) applied to choosing a skill: talk to the candidates, run them in environments, collect evidence, map it in a graph, apply a framework, and show the user which is best and why.

## The Comparison Vault: A Published, Cloneable Artefact

The product form: **the comparison itself is a vault, published publicly so people can clone it.**

The project lead: **"I can publish this as a vault, a public vault, so people can clone it. It's a good example of how do you access the right skill, how to rate it, how to pick the right one, and how you create one based on those, with provenance and explainability of why."** So a comparison of N skills for a given need becomes a self-contained, published, cloneable vault (cross-ref: the public-preview-with-read-only-key and library-as-shop-front briefs) that captures: the candidates, the evidence gathered (from running them), the framework applied, the ranking, and the explainability of why the winner won. This is a genuinely useful public artefact (cross-ref: the vault-per-standard brief's viral artefacts): anyone facing the same choice can clone the comparison rather than redo it.

And it closes a loop: the comparison can lead to **creating a new skill based on the best of the candidates** (the project lead: **"how you create one based on those"**), which feeds back into the base-vault and creator-economy model (cross-ref: the base-vault brief). So the comparison vault is both a buyer's decision aid and a creator's starting point.

## Wrapping A CLI So An Agent Can Use It

A concrete pain point the project lead hit, and a genuinely new capability: **easily wrapping a CLI or tool, in a sandbox, with tests, so an agent can use it.**

The project lead's example: he wanted to use a particular CLI (a Tesla CLI), but the agents could not drive it directly, when all he wanted was to run it in a container. The project lead: **"I just want to run that in a container. There's value in personalising and making this easy and buildable, the whole thing of spinning up a new CLI with tests, and then you allow an agent to talk to it. Just making that process easy, a simple process, so we can access everything."**

So the capability is: **take an arbitrary CLI or tool, wrap it (in a sandbox/container), add tests, and expose it so an agent can use it.** This is a recurring friction point, agents often cannot directly drive a given CLI, but they could if it were wrapped and runnable in a container with a clean interface. The pieces exist:

| Piece | Source |
|-------|--------|
| **A sandbox/container to run the CLI** | Daytona or SG Compute (cross-ref: the Daytona brief and the library-as-shop-front brief's SG Compute) |
| **Tests for the wrapped CLI** | Part of the base vault (cross-ref: the base-vault brief's tests and evals) |
| **An agent-usable interface** | The CLI wrapped as a skill / tool the agent can call (cross-ref: the skills and connector briefs) |
| **Packaged as a vault** | The wrapped CLI plus tests becomes a base vault / skill |

So wrapping a CLI is a specific, valuable instance of skill creation: the wrapped, tested, sandboxed, agent-usable CLI is itself a skill (a base vault), shareable and sellable (cross-ref: the base-vault and marketplace briefs). This also serves automation: the project lead noted **"it's about having things that can run automatically; if I run something on a schedule, you need to spin these things up."** A scheduled task needs to spin up the wrapped tool in a sandbox on demand, which is exactly the sandbox-plus-wrapped-CLI model (cross-ref: the Daytona brief). So wrapping CLIs for agents serves both interactive use and scheduled automation.

This is a clean, concrete addition to the skills work: a category of skill that wraps an existing CLI/tool so agents (interactive or scheduled) can use it, built on the sandbox and tests the platform already has.

## Token Optimisation As A Dimension Of Customisation

The third new point, a different angle on customisation: **a skill can be customised not just for personalisation, but for token optimisation, and for the context and license of where it runs.**

The project lead: **"it's also about token. We can optimise this. Instead of giving you the full skill, I can give you this skill broken down, much more optimised, a three-prompt version. So the angle could also be token management. It's not just personalisation, it's also taking into context where it's going to run, the license of where it's going to run, and minimising the token usage."**

So customisation (cross-ref: the base-vault and opinionated-expertise briefs' branded/certified/customised versions) has multiple dimensions, and token optimisation is a new one:

| Customisation Dimension | What It Tailors |
|-------------------------|------------------|
| **Personalisation** | The skill for a specific user/use case (already documented) |
| **Context of where it runs** | The skill for the environment it will run in |
| **License of where it runs** | The skill respecting the licensing of the target environment |
| **Token optimisation** | A broken-down, optimised (e.g. minimal "three-prompt") version instead of the full skill, minimising token usage |

The token-optimisation angle is genuinely additive: rather than always shipping the full skill, the platform can produce an optimised, broken-down version that uses fewer tokens, tailored to where and how it will run. This connects to the token-management and compression work (cross-ref: the v0.27.64 prompt-context-token-management brief's self-pruning and compression, and the visualisation-cornerstone brief's strategic compression): a skill is not a fixed blob; it can be delivered in an optimised form sized to the consumer and the budget. So a customised version might be optimised for the buyer's token budget and runtime context, not just their use case, which adds a concrete, measurable value (lower cost) to customisation.

## What This Asks For

1. **Build the comparison capability** (talk to candidate skills, run them in environments, collect evidence, map in a graph, apply a framework, rank with explainability).
2. **Publish comparisons as cloneable public vaults** (the candidates, evidence, framework, ranking, and the why; a useful public artefact).
3. **Close the loop to creation** (a comparison can produce a new skill based on the best candidates; feed the base-vault model).
4. **Build the wrap-a-CLI capability** (wrap an arbitrary CLI/tool in a sandbox, add tests, expose it as an agent-usable skill; a base vault).
5. **Serve scheduled automation** (spin up the wrapped tool in a sandbox on demand for scheduled tasks).
6. **Add token optimisation as a customisation dimension** (deliver an optimised, broken-down skill version; tailor for tokens, context, and license).
7. **Reuse the existing machinery** (the vault chat, the semantic graph, the sandboxes, the base vault, the marketplace; extend, do not rebuild).
8. **Produce the library page and example vaults** (a comparison vault, and a wrapped-CLI skill vault, as the MVPs).

Estimated effort: moderate, mostly composition. The comparison reuses the vault chat, the semantic graph, the sandboxes, and the evidence loop; the CLI-wrapping reuses the sandbox (Daytona/SG Compute), tests, and the base-vault model; token optimisation reuses the compression/token-management work. The new work is the comparison-and-ranking framework, the CLI-wrapping flow, and the token-optimised skill delivery. The MVPs are a published comparison vault and a wrapped-CLI skill vault.

## What This Does Not Try To Be

- **Not just per-skill scoring.** It is comparison for a specific need, with evidence (the marketplace scoring feeds it).
- **Not a static skill blob.** A skill can be delivered token-optimised, context-fitted, and license-aware.
- **Not manual CLI integration.** Wrapping a CLI for agents is made easy, sandboxed, and tested.
- **Not a rebuild.** It extends the marketplace, graph, base-vault, and sandbox work.

## Honest Risks

**Risk 1: Comparison requires running candidate skills safely.** Running multiple third-party skills to compare them is an execution risk. Mitigation: sandboxes (cross-ref: the Daytona brief); provenance and the marketplace's security analysis (cross-ref: the marketplace brief); the comparison is evidence-gathering, isolated.

**Risk 2: A comparison can be contested or go stale.** "Best" is contextual and changes. Mitigation: explainability (why this won, for this need); provenance and dated evidence; the comparison vault is version-controlled and re-runnable; "best for me" is scoped, not absolute.

**Risk 3: Wrapping arbitrary CLIs has security and licensing implications.** Running and wrapping third-party CLIs needs care. Mitigation: sandboxed execution; respect the CLI's license (the license-of-where-it-runs dimension); tests; provenance.

**Risk 4: Token-optimised versions could lose fidelity.** A broken-down skill might omit something important. Mitigation: the optimisation is validated (tests/evals; cross-ref: the base-vault brief); the full version remains available; the optimisation is a delivered form, not a replacement of the canonical skill.
