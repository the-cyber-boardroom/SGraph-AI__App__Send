## What This Is

A research brief on Convex (convex.dev): what it is, how SG/Send could use and integrate with it, and how it could help businesses be created around it. It is one of a set of partner-integration briefs aimed at producing library pages and example vaults.

The short version: **Convex is an open-source reactive database and backend, all in TypeScript, designed for both human and LLM developers, with built-in components for AI agents.** Where SG/Vault is the encrypted, self-contained, portable store of record (and a zip), Convex is a complement for the **dynamic, live, multi-user, server-side** side of vault applications, the parts that need real-time reactivity, shared mutable state, scheduled functions, and vector search.

## What Convex Is

The research picture, current as of this brief:

- Convex is the open-source reactive database for app developers, where queries are TypeScript code running in the database; just as React components react to state changes, Convex queries react to database changes, keeping apps live-updating without manually managing websockets or cache invalidation.
- It provides a database, a place to write server functions, and client libraries; schemas, queries, mutations, auth logic, and API endpoints are all expressed in pure TypeScript with end-to-end type safety.
- It is explicitly designed for both human and LLM developers, and positions itself as a strong target for AI-generated backends (AI can generate database/backend code in TypeScript rather than switching to SQL), with published evals and leaderboards for AI coding.
- It offers components for AI agents, including an AI Agent component with persistent message threads, automatic conversation context, vector search, file storage integration, long-running workflows (durable execution), and usage tracking, kept reactive to database changes.

So Convex is a reactive, TypeScript-native backend that is particularly agent-friendly (both for being generated by agents and for hosting agentic features).

## Why This Matters To SG/Send (And The Honest Distinction)

SG/Vault and Convex are different kinds of thing, and the integration is about using each for what it is best at. It is worth being precise about the distinction:

| Concern | SG/Vault | Convex |
|---------|----------|--------|
| **Model** | Encrypted, self-contained, portable store (a zip); zero-knowledge | Reactive, hosted, server-side database and functions |
| **Strength** | Provenance, version control, privacy, portability, shareability | Real-time reactivity, shared mutable state, scheduling, vector search |
| **Best for** | The record, the artefact, the curated body of work | The live, multi-user, dynamic application behaviour |
| **Trust model** | Client-side, zero-knowledge | Hosted backend |

So Convex is not a replacement for the vault; it is a complement for the parts of a vault application that are inherently dynamic and server-side. A vault is excellent at being the curated, provable, portable store of record; it is not, by design, a real-time multi-user reactive backend. Some vault applications want both: the vault for the record and the artefact, and a reactive backend for the live behaviour.

A clear example is the persistent-storage-for-artifacts pattern: some vault apps need live, shared, queryable state (a leaderboard, a collaborative tracker, a live multi-user view). The vault holds the canonical artefact; Convex could provide the reactive, shared, live state layer, kept in sync. The two compose: the vault is the source of truth and the shareable artefact; Convex is the live working surface.

## How SG/Send Could Use And Integrate With Convex

| Use | How |
|-----|-----|
| **Live, multi-user vault apps** | Convex provides the reactive shared state for collaborative or live vault apps; the vault holds the record |
| **Vector search over vault content** | Convex's vector search could index vault-derived content for retrieval (complementing the semantic graphs) |
| **Agentic features in vault apps** | Convex's AI Agent component (threads, context, long-running workflows) for vault apps that need live agentic behaviour |
| **Generated backends for vault apps** | Because Convex is agent-friendly and TypeScript-native, agents can generate the backend for a vault app |
| **Scheduling and durable workflows** | Convex's scheduled functions and durable execution for vault workflows that run over time |

The agent-friendliness is the strongest strategic alignment. SG/Vault is building an agent-native world (cross-ref: the v0.31.7 agent-controlled-websites and skills briefs); Convex is explicitly designed so agents can generate the backend in TypeScript. So an agent building a vault application could generate the Convex backend for its live side, while the vault holds the artefact and the provenance. The two fit the same agent-native, generated-software future.

A natural integration boundary: **the vault is the durable, portable, provable record; Convex is the live, reactive working layer; the two sync, with the vault as the source of truth.** A vault app's live state runs on Convex; on save/checkpoint, the canonical state is committed to the vault (with provenance and version control); the vault remains the shareable, portable artefact. This respects the vault's zero-knowledge model (the canonical, sensitive record stays in the vault) while using Convex for the live behaviour that the vault is not designed for.

## How It Helps Businesses Be Created Around It

The combination supports businesses building **live, collaborative, agentic applications that also need a portable, provable record.** A business could build a vault app where Convex powers the real-time, multi-user experience and the vault provides the durable artefact, the provenance, the privacy, and the shareability. For example: a collaborative assessment (cross-ref: the consulting brief) where multiple participants work live (Convex) and the result is a self-contained, provable assessment vault (SG/Vault); or a live evidence-gathering session (cross-ref: the visualisation brief) where the rounds are live and reactive (Convex) and every round is version-controlled in the vault.

It also supports the agent-builder ecosystem: a creator or agent building a vault app gets a generated, reactive backend (Convex) and a curated, sellable artefact (the vault), which fits the base-vault and marketplace model (cross-ref: the base-vault and marketplace briefs), the app's live backend on Convex, the app itself a sellable base vault.

## What This Asks For (The MVP)

1. **Use Convex for the live, reactive side of vault apps** (real-time, multi-user, shared state), with the vault as the record.
2. **Define the sync boundary** (the vault is the source of truth and the artefact; Convex is the live working layer; canonical state commits to the vault with provenance).
3. **Respect the zero-knowledge model** (the sensitive, canonical record stays in the vault; Convex holds the live working state).
4. **Use Convex's AI Agent component** for vault apps needing live agentic behaviour (threads, context, durable workflows).
5. **Consider Convex's vector search** as a complement to the semantic graphs for retrieval over vault-derived content.
6. **Leverage agent-generated backends** (agents generate the Convex backend for a vault app's live side).
7. **Produce the library page and example vault** (the page explains the SG/Vault-plus-Convex model; an example live vault app with a Convex backend and a vault record is the MVP).

Estimated effort: moderate; Convex is open-source, TypeScript-native, and agent-friendly, so integration is via its client libraries and functions. The new work is defining the sync boundary (vault as source of truth, Convex as live layer) in a way that respects zero-knowledge, and the example live vault app. The MVP is a collaborative/live vault app with a Convex backend and a vault record.

## What This Does Not Try To Be

- **Not a replacement for the vault.** The vault is the record and the artefact; Convex is the live layer.
- **Not breaking zero-knowledge.** The sensitive, canonical record stays in the vault; Convex holds live working state.
- **Not for static artefacts.** Convex is for the dynamic, live, multi-user side; many vaults need no backend at all.
- **Not Convex-only.** Convex is one reactive-backend option; the vault is portable and independent.

## Honest Risks

**Risk 1: It blurs the zero-knowledge model.** A hosted reactive backend is a different trust model from the encrypted vault. Mitigation: a clear boundary (sensitive canonical record in the vault; live working state in Convex); use Convex only for the live layer that genuinely needs it; the vault stays the source of truth.

**Risk 2: Two systems to keep in sync.** Vault-as-record plus Convex-as-live-layer needs syncing. Mitigation: the vault is the source of truth; Convex is the working layer; commit canonical state to the vault with provenance; define the sync clearly.

**Risk 3: Dependence on a hosted backend.** Relying on Convex for the live layer. Mitigation: Convex is open-source (self-hostable); the vault and artefact are independent and portable; Convex is one option.

**Risk 4: Not every vault needs it.** Adding a backend where none is needed is overhead. Mitigation: use Convex only for genuinely live, multi-user, dynamic apps; most vaults remain self-contained with no backend.
