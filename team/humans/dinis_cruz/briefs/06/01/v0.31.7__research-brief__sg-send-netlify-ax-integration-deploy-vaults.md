## What This Is

A research brief on a closer integration with Netlify and their Agent Experience (AX) work, focused on **making it really easy to deploy solutions, in particular how to push and host SG/Vaults on Netlify.** It is research-led (grounded in the current state of Netlify's AX, deploy APIs, edge functions, MCP server, and Agent Runners) and aimed at producing a library page and an example vault: a worked MVP of a vault hosted and deployed on Netlify.

The headline finding is that the fit is unusually clean, because the things Netlify has built for the agent era are exactly the things SG/Vault already does: deploy by zip (a vault is a zip), edge functions (the library already uses them to render encrypted vault content), the llms.txt convention (already adopted), and an MCP server plus Agent Runners for agent-driven deployment.

## Background: What Netlify AX Is

Netlify coined Agent Experience (AX), the holistic experience AI agents have as the user of a product or platform, framed as the next era alongside developer experience (DX). The research picture, current as of this brief:

- Netlify's framing has four pillars: Access (can the agent authenticate?), Context (does the agent understand the product?), Tools (are capabilities machine-readable?), and Orchestration (can agents be triggered and passed context?). These are the reason standards like MCP and llms.txt exist.
- Netlify proposes an "Agent Web", a purpose-built view of the web that prioritises AX while coexisting with human-centric experiences, serving the distinct needs of AI agents as first-class users.
- They have shipped concrete AX infrastructure: an MCP server (so agents can create, build, deploy, and manage Netlify projects via natural language), Agent Runners (AI coding agents inside the Netlify dashboard, with every change generating a deploy preview and being tracked, reversible, and auditable), prerendering that serves fully rendered HTML to crawlers and AI agents, and an AI Gateway with built-in model credentials.

This matters because SG/Vault is building for exactly this world (cross-ref: the v0.31.7 agent-controlled-websites and per-page-semantic-graphs briefs, and the v0.31.9 library-as-shop-front brief): agents controlling websites, content served to LLMs, llms.txt and edge rendering. Netlify is building the hosting layer for that world, so a close integration is natural.

## The Core Fit: A Vault Is A Zip, And Netlify Deploys Zips

The central technical finding: **Netlify deploys sites from a zip file, and a vault is a zip, so deploying a vault to Netlify is a direct fit.**

The research is clear on the deploy path:

- Netlify's API can create deploys from a ZIP file: you send the zip and Netlify unzips and deploys it. There is a Build API where you POST the zip to a builds endpoint to trigger a production build and deploy.
- Netlify explicitly positions this for the agent era: there is an "APIs for code agents" path for deploying sites at scale, such as building an AI code agent and using Netlify as a deploy target, and a CLI command (netlify create) that generates, deploys, and downloads a project from a natural-language description, with the ability to create a temporary project with a live URL without requiring credentials up front.

Because a vault is a self-contained zip (cross-ref: the v0.31.5 Vault App Store brief's vault-is-a-zip and the v0.27.64 prompt-context brief's zip-the-VFS-to-vault), the path from vault to live site is short: take the vault's zip (or the rendered output of the vault), deploy it via Netlify's zip/Build API, and it is live. This is the "make it really easy to deploy solutions" the project lead wants, and it requires almost no new concept on the SG/Vault side, the vault is already the deployable artefact.

## Edge Functions: Already How The Library Renders

The second clean fit: **Netlify edge functions are exactly what SG/Vault already uses to render encrypted vault content for static files.** The library already renders llms.txt and .md from an encrypted vault using edge functions, because static files run no browser JavaScript so the edge function does the decryption and rendering (cross-ref: the v0.31.7 per-page-semantic-graphs brief).

Netlify is a natural host for this pattern: it supports edge functions as a first-class primitive, and its zip/Build API deploy explicitly supports edge functions, redirects, and headers. So the edge-rendering approach SG/Vault already built maps directly onto Netlify's edge functions. Hosting a vault on Netlify means the same decrypt-and-render-at-the-edge model runs on Netlify's edge, with the read key exposed for public content (cross-ref: the public-preview-with-read-only-key and agent-controlled-websites briefs). This is not a new design; it is the existing SG/Vault edge-rendering running on Netlify's edge.

## llms.txt And The Agent Web: Already Aligned

The third fit is conceptual and already in place: **SG/Vault already serves llms.txt and machine-readable content, which is exactly what Netlify's AX and Agent Web call for.** Netlify uses llms.txt itself (its docs are served with an llms.txt index and .md versions of pages) and treats serving machine-readable, agent-consumable content as core to AX.

SG/Vault already does this (cross-ref: the per-page-semantic-graphs brief: llms.txt, .md, and now per-page semantic graphs and references). So an SG/Vault site hosted on Netlify is already an AX-friendly, Agent-Web-aligned site: it serves the human view and the machine view (llms.txt, .md, semantic graphs) from the same encrypted vault. The per-page semantic graphs (cross-ref) go beyond what most AX sites offer, so an SG/Vault-on-Netlify site is a strong AX exemplar, not just a hosted site.

## Agent-Driven Deployment: MCP Server And Agent Runners

The fourth fit serves the agent-controlled-websites direction: **Netlify's MCP server and Agent Runners let agents deploy and manage sites, which aligns with SG/Vault's agent-controlled websites.**

The research:

- Netlify's MCP server (built on the Model Context Protocol) lets code agents use the Netlify API and CLI to create projects, build, deploy, and manage resources via natural-language prompts, and works with MCP-compatible agents (Claude, Cursor, Windsurf, Copilot, and others).
- Agent Runners bring AI coding agents into the Netlify dashboard, where every change generates a deploy preview, and changes are tracked, reversible, and auditable, with role-based access controlling who can run agents.

This maps onto SG/Vault's agent-controlled websites (cross-ref: the v0.31.7 agent-controlled-websites brief, where per-agent vaults render sections, with a dev-to-prod CI pipeline, QA sign-off, and audit). The two models are complementary: SG/Vault's agents author and manage content in vaults; Netlify's MCP server and Agent Runners deploy and manage the hosting; and both share the audit-and-review discipline (SG/Vault's QA sign-off and version control; Netlify's tracked, reversible, auditable agent changes). So an integration could let an SG/Vault agent deploy its vault to Netlify via the Netlify MCP server, with both sides' audit trails recording it.

## The Integration, In Layers

Pulling the fits together, the integration has clear layers:

| Layer | SG/Vault Side | Netlify Side |
|-------|---------------|--------------|
| **Artefact** | The vault is a zip | Deploy from a zip (Build API) |
| **Rendering** | Edge-render encrypted content | Edge functions |
| **Machine view** | llms.txt, .md, per-page semantic graphs | llms.txt convention, Agent Web, prerendering for agents |
| **Agent deploy** | The agent authors in the vault | MCP server and Agent Runners deploy |
| **Audit** | QA sign-off, version control | Tracked, reversible, auditable agent changes |
| **Public exposure** | Public read key | Public hosting with edge rendering |

Each layer is a direct fit, and most reuse what SG/Vault already has. The integration is less a build and more a connection: point the existing vault-zip and edge-rendering at Netlify's deploy and edge, serve the machine view SG/Vault already produces, and let agents deploy via Netlify's MCP server.

## Why This Is A Good Partner Integration And Demo

The combination makes a compelling, buildable MVP:

- **Deploy a vault to Netlify with one step.** Take a vault's zip, deploy via the Build API, get a live URL.
- **Edge-render the encrypted content on Netlify.** The existing edge-rendering on Netlify's edge functions, with the public read key.
- **Serve the AX machine view.** llms.txt, .md, and per-page semantic graphs, making it an AX exemplar.
- **Let an agent deploy it.** Via the Netlify MCP server, with audit on both sides.
- **The library page and example vault.** A page explaining the integration; a vault that is itself deployed on Netlify as the worked example.

It is also a genuine partnership story: Netlify is evangelising AX and looking for partners building AX-native tools (they explicitly invite partners to build AI tools that work with Netlify), and SG/Vault is an AX-native artefact (a self-contained, zip-deployable, edge-renderable, machine-readable, agent-authored vault). The integration is mutually reinforcing: SG/Vault gets easy, scalable, agent-friendly hosting; Netlify gets a strong AX exemplar and a novel artefact (the encrypted, self-contained vault) on its platform.

## What This Asks For (The MVP)

1. **Deploy a vault to Netlify via the zip/Build API** (the vault's zip or its rendered output, deployed to a live URL).
2. **Run the edge-rendering on Netlify edge functions** (the existing decrypt-and-render-at-the-edge, with the public read key).
3. **Serve the AX machine view** (llms.txt, .md, per-page semantic graphs; an AX exemplar).
4. **Integrate the Netlify MCP server** (so an SG/Vault agent can deploy and manage the site via natural language).
5. **Preserve the audit on both sides** (SG/Vault's QA sign-off and version control; Netlify's tracked, reversible, auditable changes).
6. **Map onto the agent-controlled-websites CI pipeline** (the dev-to-prod vault promotion deploying to Netlify environments).
7. **Produce the library page and example vault** (the page explains the integration; the example vault is deployed on Netlify as the MVP).
8. **Explore the partnership** (Netlify invites AX partners; SG/Vault is an AX-native artefact).

Estimated effort: low to moderate, because most of it reuses what SG/Vault has (the vault-zip, the edge-rendering, the llms.txt/.md/semantic-graph serving) and what Netlify provides (zip deploy, edge functions, the MCP server). The new work is wiring the vault-zip to Netlify's Build API, running the edge-rendering on Netlify's edge, and the MCP-server deploy path. The MVP is a vault deployed and live on Netlify, serving both the human and machine views.

## What This Does Not Try To Be

- **Not a rebuild.** It connects the existing vault-zip and edge-rendering to Netlify's deploy and edge.
- **Not Netlify-only.** The vault remains portable; Netlify is one (excellent-fitting) host.
- **Not abandoning zero-knowledge.** The vault stays encrypted; only the public read key is exposed, as today.
- **Not just hosting.** It is an AX-native integration (machine view, agent deploy, audit).

## Honest Risks

**Risk 1: Edge-rendering decrypts at Netlify's edge.** The read key and decryption run on Netlify's edge. Mitigation: only public content (the public read key); the same controlled-exposure model as today (cross-ref: the public-preview briefs); private content is not deployed publicly.

**Risk 2: Dependence on Netlify's APIs and AX features.** The integration depends on Netlify's deploy API, edge functions, and MCP server. Mitigation: the vault stays portable (Netlify is one host); the core (vault-zip, edge-rendering) is not Netlify-specific; re-verify the APIs at build time.

**Risk 3: Agent-driven deploy needs guardrails.** Agents deploying to production needs control. Mitigation: both sides provide audit (SG/Vault's QA sign-off and version control; Netlify's tracked, reversible, auditable changes and role-based access); the dev-to-prod CI pipeline (cross-ref: the agent-controlled-websites brief).

**Risk 4: The AX space is moving fast.** Netlify's AX features are recent and evolving. Mitigation: build on the stable primitives (zip deploy, edge functions, MCP); the fit is structural (vault-is-a-zip), not feature-specific; re-verify as AX evolves.
