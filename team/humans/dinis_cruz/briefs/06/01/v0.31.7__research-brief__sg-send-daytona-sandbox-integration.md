## What This Is

A research brief on Daytona (daytona.io): what it is, how SG/Send could use and integrate with it, and how it could help businesses be created around it. It is one of a set of partner-integration briefs aimed at producing library pages and example vaults.

The short version: **Daytona is secure, elastic sandbox infrastructure for running AI-generated code, and it is the natural execution layer for the parts of SG/Vault that need to run untrusted or agent-authored code, the skills, the connectors, the assessment workflows, the agent-controlled deployments.** SG/Vault holds and curates; Daytona safely executes.

## What Daytona Is

The research picture, current as of this brief:

- Daytona is an open-source, secure and elastic infrastructure runtime for AI-generated code execution and agent workflows. It provides sandboxes: full composable computers with complete isolation (a dedicated kernel, filesystem, network stack, and allocated vCPU, RAM, and disk).
- Sandboxes spin up very fast (sub-90ms from code to execution), run code in Python, TypeScript, and JavaScript, are built on OCI/Docker compatibility, support massive parallelisation, and have persistent (stateful) sandboxes that preserve filesystem, environment variables, and process memory across interactions.
- Agents and developers interact with sandboxes programmatically through SDKs, an API, and a CLI, spanning sandbox lifecycle, filesystem operations, process and code execution, and runtime configuration.
- Daytona pivoted in early 2025 from development environments to running AI-generated code, and positions itself as agent-native infrastructure for a world where (in their framing) trillions of sandbox environments are created and destroyed dynamically.

The core problem it solves is the one everyone hits the moment agents leave the demo stage: **you have to run code you did not write, cannot predict, and should not trust (LLM-generated or user-submitted), safely and at scale**, which requires strong isolation, persistence, and programmatic control. That is exactly Daytona.

## Why This Matters To SG/Send

SG/Vault increasingly involves running code: skills include code in multiple languages (cross-ref: the v0.31.7 skill-base-vaults brief), connectors run code (cross-ref: the v0.31.5 connector briefs), assessment and discovery workflows execute LLM-driven loops (cross-ref: the v0.31.5 GDPR and visualisation briefs), and agent-controlled websites run build/deploy pipelines (cross-ref: the v0.31.7 agent-controlled-websites brief). The platform already has SG Compute / SG Playwright (cross-ref: the v0.31.9 library-as-shop-front brief) as a browser-automation service. Daytona is the general execution layer underneath all of this: a safe place to run vault-held code.

The fit is strong because the security concern is shared and central. The skills security research (cross-ref: the v0.31.7 skills-marketplace brief) is stark that skills execute locally with user privileges and are a serious supply-chain risk; a sandbox is the standard mitigation. Daytona provides exactly the isolation a skills-and-connectors platform needs to run third-party or agent-authored code without risk to the host.

## How SG/Send Could Use And Integrate With Daytona

| Use | How |
|-----|-----|
| **Run skill code safely** | A base vault's code (cross-ref: the base-vault brief) runs in a Daytona sandbox, isolated from the host and the user's environment |
| **Run connector code** | Connector logic and the data-broker (cross-ref: the connector-OAuth-data-broker brief) could run in a sandbox, especially the off-machine/proxy case |
| **Run assessment and discovery workflows** | The LLM-driven loops (cross-ref: the GDPR and visualisation briefs) execute in stateful sandboxes that persist across rounds |
| **Build and deploy pipelines** | The agent-controlled-websites CI (cross-ref: the agent-controlled-websites brief) runs builds in sandboxes |
| **Execute evals** | A skill's tests and evals (cross-ref: the base-vault and marketplace briefs) run in a sandbox to produce the eval score |
| **Underlie SG Compute** | Daytona could be (or complement) the runtime under SG Compute / SG Playwright |

Two properties make it an especially clean fit:

- **Stateful sandboxes match the vault's iterative, multi-round workflows.** The assessment and discovery loops run in rounds, persisting state (cross-ref: the consulting and visualisation briefs); Daytona's stateful sandboxes preserve filesystem and process state across interactions, which is exactly what those rounds need (rather than stateless execution that resets each time).
- **Programmatic, agent-native control matches the agent-controlled model.** Daytona exposes everything (lifecycle, filesystem, process, code execution) through an API the agent calls, which matches SG/Vault's agent-controlled websites and agent workflows: the agent drives the sandbox the way it drives the vault.

The integration is conceptually clean: a vault is the curated source of truth (the code, the skill, the connector); Daytona is where that code runs; the results flow back to the vault (with provenance). The vault holds and explains; the sandbox executes and isolates.

## How It Helps Businesses Be Created Around It

The combination supports a clear value proposition for businesses built on SG/Vault plus Daytona: **a skill or workflow can be safely sold and run.** A creator's base vault (cross-ref: the base-vault and marketplace briefs) includes code; a buyer needs to run it safely; Daytona is where it runs. So the creator economy (cross-ref: the base-vault brief) is underpinned by safe execution: a customer buys a skill (a vault) and runs it in a sandbox, isolated from their environment, with the marketplace's provenance and the sandbox's isolation together making third-party code safe to use. This is the missing execution-and-safety layer for the skills marketplace.

It also supports the assessment and consulting businesses (cross-ref: the consulting brief): a consulting assessment that runs LLM loops and code does so in a sandbox, isolated and stateful, with cost and behaviour controllable, which matters for the budget discipline (cross-ref: the visualisation brief's per-round budget) and the safety of running a customer's data through a workflow.

## What This Asks For (The MVP)

1. **Integrate Daytona as an execution layer** for vault-held code (skills, connectors, workflows, evals).
2. **Run skill and connector code in sandboxes** (isolated from the host; the safety the skills research demands).
3. **Use stateful sandboxes for multi-round workflows** (the assessment and discovery loops persist state across rounds).
4. **Drive sandboxes programmatically from agents** (matching the agent-controlled model).
5. **Run evals in sandboxes** (producing the marketplace eval score; cross-ref: the marketplace brief).
6. **Consider Daytona under SG Compute** (as the runtime or a complement).
7. **Flow results back to the vault with provenance** (the vault holds and explains; the sandbox executes).
8. **Produce the library page and example vault** (the page explains the SG/Vault-plus-Daytona model; an example vault whose code runs in a Daytona sandbox is the MVP).

Estimated effort: moderate; Daytona exposes SDKs, an API, and a CLI, and is Docker-compatible and open-source, so integration is via its programmatic interface. The new work is wiring vault-held code to Daytona sandboxes, flowing results back with provenance, and the stateful-multi-round pattern. The MVP is a vault whose skill/workflow runs in a sandbox.

## What This Does Not Try To Be

- **Not a replacement for the vault.** The vault holds, curates, and explains; Daytona executes.
- **Not running untrusted code on the host.** Isolation is the point; the sandbox protects the host.
- **Not stateless execution.** Stateful sandboxes match the iterative, multi-round workflows.
- **Not Daytona-only.** Daytona is one execution layer; the vault and the workflows are portable.

## Honest Risks

**Risk 1: Running third-party/agent code is inherently risky.** Even sandboxed, code execution carries risk. Mitigation: Daytona's isolation (dedicated kernel, filesystem, network); the marketplace's provenance and security analysis (cross-ref: the marketplace brief); least-privilege; behavioural monitoring.

**Risk 2: Dependence on a third-party runtime.** Relying on Daytona for execution. Mitigation: Daytona is open-source and Docker-compatible (portable, not locked-in); the vault and workflows are independent of the runtime; SG Compute could use Daytona or alternatives.

**Risk 3: Cost and concurrency at scale.** Sandbox usage can grow fast. Mitigation: the budget discipline (cross-ref: the visualisation brief); usage metrics (cross-ref: the industry-pages brief); Daytona is designed for agent-economics scaling.

**Risk 4: Data handling in sandboxes.** Customer data may pass through a sandbox. Mitigation: isolation; the data stays governed by the vault; customer-managed/on-prem compute options where needed; provenance.
