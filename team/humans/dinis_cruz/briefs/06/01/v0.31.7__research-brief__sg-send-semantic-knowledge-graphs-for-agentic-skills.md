## What This Is

A research brief on two connected ideas the project lead wants to explore, build examples of, and turn into a library page and an example vault: **(a) using semantic knowledge graphs for Agentic Skills, and (b) using SG/Vaults to hold all of that, the graphs, relations, provenance, visualisation, and explainability.** The first is the concept; the second is why the vault is the natural home for it. Together they point at a concrete integration and demo: a vault that holds a graph of skills, with provenance and visualisation, that an agent can reason over.

This brief is research-led (grounded in the current state of Agent Skills and of knowledge graphs for agentic AI) and is meant to produce an MVP: a library page explaining the idea, and a vault (or vaults) with worked examples.

## Background: What Agent Skills Are

Agent Skills are a recent, and now widely adopted, way to extend an agent's capabilities. The research picture, current as of this brief:

- A skill is a folder containing a SKILL.md file with metadata (name and description, at minimum) and instructions that tell an agent how to perform a specific task, optionally bundling scripts, reference materials, templates, and other resources.
- Skills were originally created by Anthropic and are now an open standard at agentskills.io, adopted by many platforms including Claude, OpenAI Codex, Gemini CLI, GitHub Copilot, Cursor, and VS Code.
- They work by progressive disclosure in three stages: discovery (at startup, agents load only the name and description of each skill, just enough to know when it might be relevant), activation (when a task matches a skill's description, the agent reads the full SKILL.md into context), and execution (the agent follows the instructions, optionally executing bundled code or loading referenced files as needed).

This matters to SG/Vault directly, because the platform already uses SKILL.md-style skills (cross-ref: the v0.31.5 evidence-CV brief's skills-from-a-vault idea) and the vault is itself a folder/zip, which is exactly the shape of a skill.

## The Gap: Skills Are Discovered By Description, Not By Relationship

The key insight that motivates using a graph: **skills are discovered by matching a task to a skill's description, but there are no explicit relationships between skills.** In the progressive-disclosure model, the agent sees a flat list of skill names and descriptions and picks by relevance. There is no structure expressing that skill A is a prerequisite for skill B, that skill C supersedes skill D, that two skills conflict, or that a skill belongs to a family. As the number of skills grows (and the ecosystem is growing fast), a flat description-matched list becomes harder to reason over.

This is precisely the gap a semantic knowledge graph fills. The research on knowledge graphs for agentic AI is consistent on what they add:

- Knowledge graphs provide agents a structure to reason with and a map to plan with: by following edges an agent can logically combine pieces of knowledge, and by reading subgraphs that represent processes or dependencies it can determine what to do next.
- For planning specifically, dependency relationships can be modelled in a graph (nodes for tasks, an edge "A is a prerequisite for B"), and the agent's planner can query the graph to find the order of steps or discover what resources are needed for a given task.
- And crucially for trust, a knowledge graph encodes meaning explicitly, relationships create context that raw data does not provide, new relationships can be added without rebuilding the system, and every connection can be tracked and justified (explainability by design).

So a semantic graph of skills turns a flat, description-matched list into a structured, navigable, reasoned-over map.

## Part A: Semantic Knowledge Graphs For Agentic Skills

The concept: **represent skills, and the relationships between them, as a semantic knowledge graph, so an agent can discover, select, sequence, and combine skills by reasoning over the graph rather than matching descriptions in a flat list.**

What the graph would model:

| Graph Element | Example |
|---------------|---------|
| **Skill nodes** | Each skill (its name, description, capabilities) |
| **Prerequisite edges** | Skill A must run before skill B |
| **Composition edges** | Skill C is built from skills D and E |
| **Conflict edges** | Skill F and skill G should not be combined |
| **Family / taxonomy edges** | Skill belongs to a category (e.g. document-processing, assessment) |
| **Capability ontology** | What each skill can do, in a shared vocabulary |
| **Provenance edges** | Who authored a skill, from what source, validated by whom |

With this graph, the agent's skill use improves at each progressive-disclosure stage:

| Stage | Flat List (Today) | With The Graph |
|-------|-------------------|----------------|
| **Discovery** | Match the task to skill descriptions | Traverse the graph to find relevant skills and their related skills |
| **Activation** | Load the matched SKILL.md | Load the skill and understand its prerequisites, conflicts, and compositions |
| **Execution / planning** | Run the skill | Sequence skills by their dependency edges; combine composable skills; avoid conflicts |

This aligns with the research consensus that shared and connected semantics let agents plan multi-step actions confidently, infer new relationships from trusted data, and explain their reasoning through auditable paths, and that without shared connected semantics agents risk duplication, inconsistent decisions, and opaque behaviour. A skills graph is that shared, connected semantics for the skills an agent has available.

It also fits the platform's existing direction exactly: the document-to-graph pipeline (cross-ref: the v0.31.9 vault-per-standard brief) already turns documents into semantic graphs; a SKILL.md is a document; so the same pipeline can extract a skill's capabilities and relationships into the graph. The skills graph is the document-to-graph pipeline applied to skills.

## Part B: SG/Vaults As The Substrate For The Graph

The second idea, and the natural fit: **the vault is the right place to hold the skills graph, the relations, the provenance, the visualisation, and the explainability.** Each of these maps onto a capability the vault already has.

| What Needs Holding | Why The Vault Fits |
|--------------------|--------------------|
| **The skills themselves** | A skill is a folder/zip; a vault is a folder/zip (cross-ref: the Vault App Store brief's vault-is-a-zip; skills as vault apps) |
| **The graph and the relations** | The vault holds the semantic knowledge graph (cross-ref: the vault-per-standard and prompt-context briefs) |
| **Provenance** | The vault stores raw, transformations, and model responses with provenance (cross-ref: the vault-per-standard brief's vault-as-workshop); version-controlled (cross-ref: the commit-queue brief) |
| **Visualisation** | The vault renders the graph (cross-ref: the visualisation-cornerstone brief's three primitives) |
| **Explainability** | The graph's auditable paths plus the vault's provenance give explainability by design |

This is a strong, specific argument, because the research says explainability and provenance are exactly what production agentic graphs need: trustworthy AI requires accurate, grounded, and explainable actions, and an enterprise knowledge graph that explicitly defines relationships and business logic lets agents demonstrate why and how they make decisions, supported by a rich audit trail back to the source. And the buyer's-guide research is blunt that explainability, auditability, and provenance tracking are non-negotiable in regulated industries. The vault provides exactly this: it already stores provenance, is version-controlled, is zero-knowledge encrypted, and renders visualisations, so a skills graph held in a vault is auditable, explainable, and shareable by construction.

So the pairing is natural: the graph gives the skills structure and reasoning; the vault gives the graph a home with provenance, visualisation, explainability, encryption, versioning, and shareability. Neither is a stretch for the platform; both reuse capabilities already built.

## Why This Is A Good Integration And Demo

The two ideas combine into a compelling, buildable MVP:

- **A vault holding a skills graph.** Skills (as documents/SKILL.md files) extracted into a semantic graph via the document-to-graph pipeline, with prerequisite, composition, conflict, and family edges.
- **Provenance for every skill and edge.** Who authored it, from what source, validated by whom, version-controlled.
- **Visualisation of the skills graph.** The graph rendered (cross-ref: the visualisation-cornerstone brief), navigable by altitude (the families, then the skills, then the detail).
- **Explainability.** When an agent selects or sequences skills, the graph path explains why (these prerequisites, these compositions, avoiding these conflicts).
- **An agent reasoning over it.** A vault-chat agent (cross-ref: the vault-chat architecture brief) that uses the graph to discover, sequence, and combine skills, rather than matching a flat list.

This is also a natural extension of the Vault App Store (cross-ref: the v0.31.5 Vault App Store brief): the store already distributes vault apps and could distribute skills; a skills graph is how the store's skills relate to each other, with the security-analysis and agent-mapping (cross-ref) feeding the provenance and the conflict edges.

## A Note On Skill Safety (Where The Graph Helps)

The research flags a real risk worth designing for: skills introduce power and risk, a malicious skill could exploit the environment, exfiltrate data, or execute harmful actions, so one should install only from trusted sources and audit all files. The skills graph plus the vault's provenance is a direct mitigation: provenance edges record where a skill came from and who validated it, conflict edges record known-bad combinations, and the vault's security analysis (cross-ref: the Vault App Store brief's security-analysis-and-agent-mapping) populates the graph with trust signals. So the graph is not only a reasoning aid; it is a safety surface, the place where a skill's provenance and trust are recorded and reasoned over before it is used.

## What This Asks For (The MVP)

1. **Build a skills graph** representing skills and their relationships (prerequisite, composition, conflict, family, capability ontology, provenance), using the document-to-graph pipeline on SKILL.md files.
2. **Hold it in a vault** (the skills, the graph, the relations, the provenance, version-controlled).
3. **Visualise the graph** (rendered, navigable by altitude; the families, the skills, the detail).
4. **Make it explainable** (the graph path explains why a skill was selected or sequenced).
5. **Have an agent reason over it** (a vault-chat agent that discovers, sequences, and combines skills via the graph).
6. **Record trust and safety in the graph** (provenance, validation, conflict edges; the security-analysis trust signals).
7. **Produce the library page and example vault** (the page explains the idea; the vault is the worked MVP with a real set of skills).
8. **Connect to the Vault App Store** (skills distributed and related through the store; the graph as the relationship layer).

Estimated effort: the building blocks exist (the document-to-graph pipeline, the vault's provenance and version control, the visualisation primitives, the vault-chat agent, the skills-from-a-vault idea, the store). The new work is the skills-specific graph schema (the edge types), extracting skill relationships, the explainability surface, and the agent that reasons over the graph. The MVP is a vault with a real skills graph, visualised and reasoned over.

## What This Does Not Try To Be

- **Not a replacement for the Agent Skills standard.** It enriches the standard with a relationship graph; skills remain SKILL.md folders.
- **Not a flat skill list.** It adds explicit relationships and reasoning over them.
- **Not a graph without a home.** The vault holds it, with provenance, visualisation, and explainability.
- **Not unaudited skills.** The graph records provenance and trust; safety is a design goal.

## Honest Risks

**Risk 1: Extracting reliable relationships between skills is hard.** Inferring prerequisites, compositions, and conflicts is non-trivial. Mitigation: the document-to-graph pipeline plus human/agent validation (cross-ref: the assessment briefs' confirm-not-assert); start with explicit, declared relationships, then infer.

**Risk 2: A wrong skills graph misleads the agent.** A bad edge causes bad sequencing. Mitigation: provenance and validation; the explainability surface lets a human see why; version control allows correction.

**Risk 3: Skill safety is a real risk.** Per the research, malicious skills exist. Mitigation: the graph records provenance and conflict edges; the vault's security analysis; install from trusted sources; the graph as a safety surface.

**Risk 4: The standard and ecosystem are moving fast.** Agent Skills is young and evolving. Mitigation: build on the open standard (agentskills.io); the graph is additive (it does not change the standard); re-verify as the standard evolves.
