# Skills Are Software Packages: Manage Them Like Dependencies, And Why Intent Beats Capability

## What This Is

A foundational concept the project lead wants captured clearly: **skills are code, must be version-controlled, and should be treated like software, specifically like a software package, a dependency, managed the way npm and pip manage dependencies.** It reinforces the treat-skills-like-software thread (cross-ref: the v0.31.9 ownership-of-delegated-processes and skills-as-business-knowledge briefs) and adds two sharp framings that are genuinely new: **skills are a dependency with the full software-package lifecycle, and skills are the evolution of code packages because they describe intent, in English, not just capability.**

The project lead notes that skills also finally give a business a scalable way to capture how it works, and flags that as the next, separate memo; this brief does not develop it.

This is the second in the 4 June skills series (cross-ref: the v0.32.3 consulting-firms-to-product brief).

## The Core Concept: Skills Are A Software Package

The central claim, stated plainly: **skills are code, need version control, and are best understood as a software package, in fact as a dependency.**

The project lead: **"skills are code and need to be version-controlled, and need to be treated like software. Skills are a software package, that is the best analogy. Skills are not just a bit of code; skills are like a dependency, and need to be managed just like a dependency. The same way we have npm and pip for managing dependencies, we need a way to manage skills like that."** So the right mental model is not "a skill is some code" but "a skill is a package, a dependency, with everything that implies." Some people are starting to do this (cross-ref: the v0.31.9 Tessl brief, a package manager and registry for skills), and the key principle is that everything you do with code, you must do with skills.

## The Full Software Lifecycle Applies

The consequence: **every practice that applies to code applies to skills.**

The project lead: **"treat skills the same way you treat code, the same way you version-control it, with vulnerabilities management, documentation, integration, wrappers, code reviews, deployment, CI pipelines, distribution reviews, every analogy we have with code, we need with skills."**

| Software Practice | Applied To Skills |
|-------------------|-------------------|
| **Version control** | Skills are versioned, with history (cross-ref: the commit-queue brief) |
| **Vulnerability management** | Skills are scanned and patched like dependencies (cross-ref: the skills-marketplace security findings) |
| **Documentation** | Skills carry their docs (cross-ref: the base-vault and skills-library briefs) |
| **Integration and wrappers** | Skills are integrated and wrapped like libraries (cross-ref: the skill-comparison CLI-wrapping brief) |
| **Code reviews** | Skills are reviewed before use |
| **Deployment and CI pipelines** | Skills are deployed and tested through CI (cross-ref: the agent-controlled-websites CI brief) |
| **Distribution and registries** | Skills are distributed and reviewed (cross-ref: the marketplace and library briefs) |

So a skill is managed, distributed, secured, and consolidated exactly as a software dependency is. This matters especially because **skills can contain code**: the project lead notes skills these days can have anything in them, and often do have scripts, so treating them as software is not a metaphor, it is literally accurate, a skill is a package that may contain executable code, with all the lifecycle and security that demands (cross-ref: the marketplace security findings and the Daytona sandbox brief).

## The Sharp Distinction: Skills Describe Intent, Not Just Capability

The genuinely new framing, and the most interesting one: **skills are the evolution of code packages, because a skill describes intent, in English, where a package describes capability.**

The project lead: **"skills are the evolution of code packages, because what skills do is describe the intent. A package has a capability, it does not tend to have an intent. Skills are much closer to what the user wants to do, and because they are written in English, they are not limited to the flow. They tend to be more context-specific and more relevant, because they leverage the fact that LLMs understand English, so we can describe what we want in instructions. The problem with APIs is that they do not describe how they are used, they describe a raw capability, and there are a lot of combinations of what you can do with them."**

| A Code Package / API | A Skill |
|----------------------|---------|
| Describes a capability | Describes an intent |
| What it *can* do | What the user *wants* to do |
| Raw functions, many combinations | Instructions, in English, toward a goal |
| Limited to the flow / the call surface | Context-specific, relevant, goal-oriented |
| You must know how to combine it | The intent and the how are described together |

This is the sharp point. A package or an API gives you a capability but not the intent: it tells you what is possible, not what to do or how it is meant to be used, and the many combinations are left to you. A skill, written in English and leveraging the fact that LLMs understand English, describes the intent, what the user wants to do, with the instructions for doing it. So a skill sits much closer to the user's goal than a package does, and it is more context-specific and relevant because it is expressed as intent rather than as a call surface. This is why skills are the *evolution* of packages: they carry the missing layer (intent and instruction) that a package or API never had.

A practical corollary the project lead notes: **because skills are written in English, they are easier to refactor and to write.** Expressing intent in English is more tractable than wiring API calls, so the skill is not only closer to the user's goal but cheaper to author and change. The intent layer is both more useful and more malleable than the capability layer beneath it.

## Why This Matters

Holding the two framings together:

- **Skills are software packages**, so the entire mature discipline of software management (version control, vulnerability management, documentation, review, CI, distribution) applies, and must, especially since skills can contain code. This is the rigour side: skills are not loose text, they are managed, secured, versioned artifacts (cross-ref: the ownership and marketplace briefs).
- **Skills describe intent, not just capability**, so they are the evolution of packages: closer to the user's goal, context-specific, expressed in English, easier to author and refactor. This is the power side: skills add the intent-and-instruction layer that packages and APIs lack.

Together these say what a skill *is*: a software package that carries intent. It demands the discipline of code and delivers more than code, because it describes what the user wants, not only what is possible. That is the foundation under the whole skills economy (cross-ref: the base-vault, marketplace, and consulting-firms briefs): the thing being created, sold, customised, and maintained is a managed software package whose distinctive value is that it captures intent.

## What This Asks For

1. **Adopt skills-are-software-packages as a foundational principle** (skills are code, version-controlled, treated like a dependency; the npm/pip analogy).
2. **Apply the full software lifecycle** (version control, vulnerability management, documentation, integration, wrappers, reviews, deployment, CI, distribution).
3. **Manage skills that contain code accordingly** (skills can and do contain scripts; the security and lifecycle are literal, not metaphorical; cross-ref: the marketplace and Daytona briefs).
4. **Adopt intent-over-capability as the distinguishing property** (a skill describes intent in English; a package describes capability; skills are the evolution of packages).
5. **Leverage the English-language intent layer** (closer to the user's goal, context-specific, easier to author and refactor).
6. **Build the management apparatus** (manage, distribute, secure, consolidate skills like dependencies; cross-ref: the skills-library and marketplace briefs).
7. **Carry the through-line to the next memo** (skills as the scalable way to capture how a business works).
8. **Produce the library page and example** (the page explains skills-as-software-packages and intent-over-capability; an example skill managed with the full lifecycle is the MVP).

Estimated effort: this is a foundational framing, not a new build; the management apparatus is largely the existing version-control, marketplace, library, and CI work. The contribution is the dependency model and the intent-over-capability distinction. The example is a skill managed exactly as a software dependency.

## What This Does Not Try To Be

- **Not loose text.** Skills are managed, versioned, secured software packages.
- **Not just code.** Skills describe intent in English, the layer packages and APIs lack.
- **Not a metaphor when skills contain code.** The software lifecycle is literally required.
- **Not the business-knowledge-capture memo.** That is the next, separate piece; only flagged here.

## Honest Risks

**Risk 1: Skills that contain code carry real security risk.** Executable skills are a supply-chain risk (cross-ref: the marketplace security findings). Mitigation: the full software lifecycle (vulnerability management, review, CI); provenance and scoring (cross-ref: the marketplace brief); sandboxed execution (cross-ref: the Daytona brief).

**Risk 2: The discipline is heavy.** Applying the full software lifecycle to skills is effort. Mitigation: reuse the existing apparatus (version control, marketplace, library, CI); the discipline is what makes skills trustworthy and sellable (cross-ref: the ownership brief).

**Risk 3: Intent expressed in English can be ambiguous.** English instructions are less precise than code. Mitigation: skills can contain code where precision is needed; tests and evals (cross-ref: the base-vault brief); the intent layer sits above, not instead of, precise execution.

**Risk 4: The dependency model needs real tooling.** Managing skills like npm/pip needs infrastructure. Mitigation: aggregators exist (cross-ref: the Tessl brief); the library and marketplace provide it (cross-ref: the skills-library and marketplace briefs).
