## What This Is

A variation of the permission-granularity brief, captured independently because it is a project and almost a business model in itself: **cloud permissions, why authorizing an agent to act inside a hyperscaler is so hard, and the project of giving every cloud API method its own permission graph.** It is the cloud-specific case of the general thesis (cross-ref: the v0.32.3 NHI-2.0-permission-granularity brief) and rests on the semantic graph (cross-ref: the v0.32.3 NHI-2.0-semantic-knowledge-graphs-of-identity brief) and per-action, time-bounded permissions (cross-ref: the v0.32.3 NHI-2.0-time brief). New contributions: **the hyperscaler-scale project as a business model, the cross-cloud primitive-divergence problem, the action-versus-resource mismatch, per-API-method permission graphs, the eventual-consistency whack-a-mole, per-action just-in-time permission sets, the reframe that AWS already has the granularity (the missing piece is the business reason), and the community-validation flywheel.** The project lead flags OAuth-not-fit-for-purpose as the next memo; this brief sets it aside.

## A Project And A Business Model In Itself

Why this deserves its own brief: **everybody needs cloud-permission mapping, the skills to do it are rare, and doing it open source, even sponsored by the hyperscalers, is a valid business model.**

The project lead: **"this is a variation of the previous one, but I want to capture it independently, because it is a project by itself, and almost a business model in itself, because everybody needs this. There are tons of applications, including the hyperscalers. Doing this open source, even sponsored by those organisations, would be a valid business model, because the skills required to pull off what I am about to describe are not that easy to come by."** So cloud-permission mapping is not just a feature of the platform; it is a standalone project with its own business model, because the need is universal (everyone on a cloud has it) and the skill is scarce. The hyperscalers themselves could fund or sponsor it (it makes their platforms safer and more usable), and open source is the natural model (the community-validation point below).

## The Cross-Cloud Divergence Problem

The first practical difficulty: **the hyperscalers' permission primitives are similar but different enough that expertise does not transfer, though LLMs now help bridge.**

The project lead: **"you want an agent to do an action inside one of the hyperscalers, AWS, Azure, GCP, Rackspace, DigitalOcean, Alibaba, whatever. The challenge is that although the primitives are very similar, annoyingly they are different enough that it is not straightforward for an AWS expert to move to Azure or GCP. Every time I look at the other platforms I think, how does this thing work? Of course, LLMs help a lot now, because they understand them."** So even an expert in one cloud struggles to move to another, because the primitives, while similar, diverge in the details. This is part of why the project is hard and the skills rare, and part of why LLMs are an enabler: they can understand and bridge the divergent models, making the mapping feasible where it was not before.

## The Core Insight: The Action-Versus-Resource Mismatch

The central technical insight: **cloud permissions are scoped to resources and primitives, but what you want to authorize is a higher-level action, and bridging that requires a graph of resources.**

The project lead: **"the action is not determined by the resources; the action is an abstraction layer. Say I want to start an EC2 instance connected to a particular network, that receives data from a particular place, sends logs to a particular location, and has a particular configuration. The cloud providers have very rich, powerful permissions, but they tend to be mapped to the primitive: a permission to add a DNS record, start an instance, create a VPC, connect this, assign an identity, create the identity required. The primitives are connected to the resource, not the action you have. So to start an instance you need a graph of resources, the AWS API, and boto3, which provides a bit of abstraction on the action."**

| The Action You Want | The Permissions You Get |
|---------------------|--------------------------|
| Start an EC2 instance, networked, logging, configured | Add DNS record, start instance, create VPC, assign identity, create identity |
| One higher-level intent | Many resource-scoped primitive permissions |
| An abstraction layer | Mapped to resources, not the action |

So there is a mismatch between the action (the abstraction layer: what you actually want to do) and the permissions (scoped to individual resources and primitives). A single action decomposes into a graph of resource permissions, and nothing in the cloud provider connects that graph back to the action. This is the cloud-specific form of the authorization-matrix complexity (cross-ref: the semantic-knowledge-graphs and permission-granularity briefs): the permissions are real and rich, but they are organised by resource, not by intent.

## The Big Ask: Every API Method Should Declare Its Permission Graph

The defining requirement: **every public cloud API method should contain a permission graph and identity graph, declaring the exact permission set needed to execute that action.**

The project lead: **"AWS today, as far as I can tell, still does not give you a graph per API method. Every public API method that exists should contain a permission graph, an identity graph, and that is why we go back to semantic graphs, because the semantic graph defines the ontology and understands all the bits. Every method should provide the exact permission set I need to execute that action at that moment in time. We do not have that today."** So the ask is precise: each public API method should declare, as a graph, exactly the permissions and identities required to call it, derived and understood through the semantic graph (cross-ref: the semantic-knowledge-graphs brief's ontology). With that, authorizing an action becomes exact (the method tells you precisely what it needs); without it, you are guessing (below). This is the project: build, for every method, the permission graph the providers do not give you.

## Why It Is Broken Today: Guessing, Eventual Consistency, And Whack-A-Mole

The honest state, and a concrete cloud-specific cause of over-provisioning: **without per-method permission graphs, developers guess, and eventual consistency plus inconsistent errors turn it into whack-a-mole, so nearly every role is over-provisioned.**

The project lead: **"what ends up happening is developers have to guess. You do research, you look at documentation that has some stuff, but it is not easy to understand. And most cloud providers have eventual consistency, which is a problem, because a permission change might take seconds or more to stabilise, which makes it much harder to test and understand the exact permissions and failures. Some error messages help, others do not, and they are not consistent. So it becomes a whack-a-mole exercise, which is why, with very few exceptions, every AWS account or role has more permissions than it should."**

| The Obstacle | The Effect |
|--------------|------------|
| No per-method permission graph | Developers guess from incomplete docs |
| Eventual consistency | Changes take time to stabilise; hard to test |
| Inconsistent error messages | Failures are hard to diagnose |
| The result | Whack-a-mole, so roles are over-provisioned to make it work |

So the over-provisioning endemic to cloud is not laziness; it is the rational response to a system where the exact permissions are unknown (no per-method graph), changes are slow to stabilise (eventual consistency), and failures are hard to read (inconsistent errors). Faced with whack-a-mole, developers grant broad permissions to make things work. The per-method permission graph removes the guessing, which removes the reason to over-provision.

## The Right Question: Per-Action, Just-In-Time Permission Sets

The reframe of the question itself: **the question is not what single privilege I need for all my actions, but a different permission set for every action, granted only when that action runs.**

The project lead: **"even at this level I am asking the wrong question. The question is not, I want to do all these actions, what privilege do I need. The question is, for every action, for every API, I should have a different permission set. Because I am going to make a bunch of calls, create EC2, assign DNS, assign IP, connect VPC, add to CloudTrail, create the identity, and each of those is a privileged action. Why should my code, when it is doing the ten or twenty things it is supposed to do, have access to all of them all the time? There is no point mapping a bunch of identities if I do not have this level of granularity, because I am just adding complexity."**

So the correct model is per-action, just-in-time permissions: each of the many privileged calls a piece of code makes gets exactly the permission set for that call, at the moment of that call, not a single aggregate privilege held throughout. Holding all the permissions all the time (the union; cross-ref: the foundations brief's union-of-privileges and the time brief's duration-bounded permissions) is the problem; per-action, time-scoped grants are the answer. And without this granularity, the elaborate identity model just adds complexity (cross-ref: the permission-granularity brief's identity-pointless-without-permission-granularity).

## The Reframe: AWS Already Has The Granularity

An important and clarifying point: **the granularity already exists in AWS (custom roles, conditions, granular permission sets); what is missing is the means to use it well and the business reason to bother.**

The project lead: **"in AWS, to set up a secure deployment, a CI pipeline, or a particular environment, you should create custom rules, custom roles, and custom permission sets, and that ability is one of the most powerful in AWS. AWS already has the granularity, you can do a huge amount of conditions and very granular requirements. The challenge is to make that work, and identities are what will make it work, because identities become the business reason why we need that granularity."** So this is not a missing-capability problem; AWS already supports highly granular custom roles, conditions, and permission sets. The problem is twofold: it is hard to use well (the guessing and whack-a-mole above), and there has been no compelling business reason to invest in using it. The NHI 2.0 identity model supplies the business reason: many granular, on-demand identities are exactly what make the existing granularity worth using, and they are what give the permission sets their teeth. The project, then, is to make the existing granularity usable and to connect it to identities.

## From Negative Cycle To Positive Cycle, And Community Validation

The flywheel, cloud-specific (cross-ref: the blast-radius and permission-granularity briefs): **today's negative cycle (no visibility leads to over-provisioning leads to giving up on multiple identities) can become a positive cycle, rewarded and validated by an open-source community.**

The project lead: **"the same way we could have a negative cycle, where we do not have good visibility or understanding of permissions, so we over-provision, so we end up with big identities, and then people say it does not matter to have multiple identities anyway, because I have to give the one with maximum power, the aggregation of all privileges, which caused the problem. I think it is the other way around: now we can create a positive model where we reward this. We do not need to do everything all the time, we can start slowly, with a couple of specific use cases. Open source is good here because it allows a much wider model: anybody using AWS, any script, is actually validating and confirming the mappings are correct."**

So the negative cycle (no visibility, over-provision, conclude multiple identities are pointless, grant the aggregate-of-all-privileges) flips to a positive one once per-method permission graphs exist and granular identities give the business reason. Crucially, open source enables a community-validation flywheel: every AWS user and every script that runs against the mappings validates and confirms them, so the mappings improve with use (cross-ref: the open-source-not-free brief). Start slowly, a few specific use cases, and let community usage harden the graphs.

## Permission Strictness By Wardley Stage, And Over-Privileged Keys

The business-decision framing (cross-ref: the time and skill-lifecycle briefs): **how strict the permissions are is a business decision driven by the Wardley evolutionary stage, and this connects to the problem of over-privileged keys in production.**

The project lead: **"without this granularity you really struggle to make a big difference; you shift the needle a little, he is not running from admin, not running as a user, but the user still has far too much privilege, or it is granular to access the application, but the application still has crazy privileges. So we need this granularity, and then it becomes a business decision, depending on the use case and the Wardley map evolutionary stage. There is nothing wrong with a vibe-coded app that has no access to real customer data, just exploring; that is very different from an app running in production, mission-critical, that people depend on. They have very different properties and should have very different permission mappings. This also connects to running keys in production, or having access to production, or keys that are way over-privileged."**

| Wardley Stage | Permission Strictness |
|---------------|------------------------|
| Explorer (a vibe-coded app, no real data) | Loose is fine; just exploring |
| Production, mission-critical, depended-on | Strict, granular, locked down |

So permission strictness is not one-size-fits-all; it is a business decision keyed to the Wardley stage (cross-ref: the time and skill-lifecycle briefs): an exploratory vibe-coded app with no real data can be loose, while a production, mission-critical application must be tightly, granularly permissioned. And this is the same problem as over-privileged keys in production (cross-ref: the foundations brief's secrets-at-the-edge): the granularity, and the discipline of matching it to the stage, is what stops production from running on over-privileged keys.

## What This Asks For

1. **Treat cloud-permission mapping as a project and business model** (universal need, rare skills, hyperscaler-fundable, open source).
2. **Bridge the cross-cloud divergence** (similar-but-different primitives; LLMs to understand and map them).
3. **Close the action-versus-resource gap** (map the graph of resource permissions a higher-level action needs).
4. **Give every API method a permission graph** (the exact permission set per method, via the semantic graph).
5. **Remove the guessing** (per-method graphs against eventual consistency and inconsistent errors; end the whack-a-mole).
6. **Grant per-action, just-in-time permissions** (a different permission set per call, when it runs; not the held union).
7. **Use the granularity that already exists** (AWS custom roles and conditions; identities as the business reason to use them).
8. **Flip to the positive cycle with community validation** (start with specific use cases; let open-source usage harden the mappings).
9. **Match strictness to the Wardley stage** (loose for explorer, strict for production; fix over-privileged production keys).

Estimated effort: large in aggregate (per-method permission graphs across the hyperscalers), but incremental and community-validated, and LLMs make the mapping feasible; the granularity already exists in the platforms. The contribution is the project framing, the per-method permission graph, and the connection to identities. The MVP is one action (start a networked, logging, configured EC2 instance) mapped to its exact per-method permission graph, granted just-in-time, validated by usage.

## What This Does Not Try To Be

- **Not a new permission capability for AWS.** The granularity exists; the project makes it usable and connects it to identities.
- **Not resource-scoped thinking.** Bridge resources to the higher-level action.
- **Not guess-and-over-provision.** Per-method permission graphs remove the guessing.
- **Not one aggregate privilege.** Per-action, just-in-time permission sets.
- **Not the OAuth memo.** OAuth-not-fit-for-purpose is the next brief.

## Honest Risks

**Risk 1: Per-method graphs across hyperscalers is huge.** Many methods, many clouds. Mitigation: open source and community validation; LLMs to map; start with specific high-value actions; incremental.

**Risk 2: Eventual consistency complicates enforcement and testing.** Changes are slow to stabilise. Mitigation: model it explicitly in the graphs; the middle layer (cross-ref: the permission-granularity brief) can enforce; account for stabilisation in testing.

**Risk 3: Cross-cloud divergence resists a single model.** Each cloud differs. Mitigation: the semantic graph and ontology reconcile (cross-ref: the semantic-knowledge-graphs brief); LLMs bridge; map per cloud, share the structure.

**Risk 4: The hyperscalers may or may not engage.** Sponsorship is not guaranteed. Mitigation: open source proceeds regardless; community validation; it makes their platforms safer, so the incentive aligns.

**Risk 5: Just-in-time per-action permissions add runtime complexity.** Granting per call is work. Mitigation: the granularity exists (AWS conditions, custom roles); ephemeral, on-demand grants (cross-ref: the foundations brief); the middle layer enforces where needed.
