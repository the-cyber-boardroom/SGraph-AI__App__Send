# NHI 2.0, Living Off The Land: Leveraging Existing Identity, Anchors, Sub-Identities, And Where The Keys Live

## What This Is

The second in the NHI 2.0 series (cross-ref: the v0.32.3 NHI-2.0-PKI-foundations brief and the NHI-2.0-startup-thesis brief): **how a startup built on this should live off the land for identity, leveraging what already exists in an organisation rather than building a core identity solution, and building the sub-identity and key layer on top.** It applies the live-off-the-land principle from the blast-radius work (cross-ref: the v0.31.9 blast-radius brief, where it meant consuming an organisation's existing data) specifically to identity: consume and anchor on the organisation's existing identity infrastructure. This is the first practical phase: understanding what exists, what must be provided, and where the keys live. New contributions: **identity-as-provenance, the anchor model, unique-versus-sub-identity, the Uber identity and hope-driven development, the private-key storage question, and the leverage-but-have-your-own-compatible-version commercialisation principle.**

## The Principle: Do Not Reinvent The Core Identity Solution

The starting logic: **do not build a core identity solution; there is already enough; live off the land.**

The project lead: **"the logic here is you do not reinvent the wheel. The logic is not to create a core identity solution, there is already enough. So the question becomes: what identities are currently available in the organisation? Can new identities be created, or do you have to connect on top of them? And what is the cost?"** So the NHI 2.0 startup is not an identity provider; it leverages the organisation's existing identity infrastructure (the directory, Google Auth, Active Directory, OAuth, Cognito) and builds the agent sub-identity and key layer on top. This is the live-off-the-land judo move (cross-ref: the blast-radius brief) applied to identity: consume what exists, do not rebuild it.

## Identity Is Provenance: Chain Links, Not Blockchain

The simplifying definition, and an important reframe: **an identity is a way to connect A with B, to say this was created by this, so an identity is provenance, and provenance is chain links, not blockchain.**

The project lead: **"ultimately an identity is a way to connect A with B, a way to look at an agent, or an agent action, and say this was created by this. So the identity is provenance. And provenance is about links, this is not about blockchain, it is about chain links, chains of trust."** So identity, at root, is provenance: the answer to "who or what created this action." This aligns identity directly with the chain-of-authenticity model (cross-ref: the NHI-2.0-foundations brief): identities are chain links (signatures linking an action to its origin), chains of trust, not blockchain. Framing identity as provenance is useful because it makes the goal concrete: every agent action should link back, through identities, to who authorised and performed it.

## The First Phase: Map What Exists, What Can Be Created, And The Cost

The first practical task: **map the organisation's existing identities, its ability to create new ones, and the cost of both, because the objective is many identities per agent, hundreds and thousands of them.**

The project lead: **"the first key principle is: what exists in the organisation in terms of identities, what exists in terms of the ability to create identities, and what we have available to connect the identities we create. Because the objective is not just an identity per agent, but multiple identities per agent. And the cost matters, because we need to create hundreds and thousands of new identities."**

| Mapping Question | Why It Matters |
|------------------|----------------|
| **What identities exist?** | The directory, Google Auth, Active Directory, OAuth, Cognito; what is already there to anchor on |
| **Can new identities be created (or only connected on top)?** | Determines whether you provision fresh identities or sub-identity from existing ones |
| **What is the cost (existing and new)?** | You need hundreds and thousands of identities; cost governs feasibility |

So the first phase is reconnaissance: catalogue the existing identities, determine whether new ones can be created and how, and price both, because the model needs many identities per agent at scale, and cheap creation changes everything (below).

## Anchors Of Identity

The structural concept: **anchors of identity are what exists to root on, and they are usually connected to a privileged action.**

The project lead: **"my key question is, what anchors of identity exist in an organisation? Usually the anchors are connected with an action that needs to be made, the privileged action, whether it is an individual account, a cloud account, a cloud role, all these things. We need to map what exists and how expensive it is to create new ones."** So an anchor is an existing identity (an individual account, a cloud account, a cloud role) that is tied to the ability to perform a privileged action, and it is what a new agent identity roots on. Single sign-on is double-edged here: the project lead notes the more SSO exists, the more dangerous it can be, but also the easier, because you can anchor agent identities in the SSO workflows and inherit the permissions on the target entity. The throughline: it is always about someone (or something) doing something, and the point of the identity is to know who, under what privilege, so the action has provenance.

## Unique Identity Versus Sub-Identity Under A Parent

The choice for each agent: **give the agent its own unique anchor identity (always best), or create a sub-identity anchored in a parent identity, and in the worst case the parent is an administrator or super-privileged account, which always makes it work.**

The project lead: **"can we give the agent a unique identity, an anchor of identity, which is always the best thing, or do we need to connect it under another one, a sub-identity anchored in a parent identity? At the end of the day you can always make this work, because the parent identity could be the administrator of everything, or an account with super privileges. That is the worst-case scenario, but it is still possible."**

| Option | Trade-off |
|--------|-----------|
| **Unique anchor identity per agent** | Best: maximum granularity and least privilege |
| **Sub-identity under a parent** | Works by inheriting from a parent; less granular |
| **Worst case: parent is admin / super-privileged** | Always possible, but the over-privileged fallback |

So the preferred path is a unique, cheaply-created identity per agent (granular, low-privilege), and the fallback is a sub-identity anchored under a parent, down to the worst case of anchoring under an administrator. This is why cheap creation matters: the project lead notes that if you can create identities cheaply and assign privileges, that is always best, because you get far more granularity, the same reason you want least privilege (cross-ref: the NHI-2.0-foundations brief). Cheap, granular identity creation is the difference between true least privilege and falling back to over-privileged parents.

## The Uber Identity And Hope-Driven Development

A sharp observation and a memorable coinage: **Uber identities have more privileges by design, the classic case being an agent on a user's desktop acting as the user, and relying on that is hope-driven development.**

The project lead: **"once you find these Uber identities, which by design always have more privileges, a perfect example is when an agent runs on somebody's desktop: they act on the user's account, the user's identity, and have access to everything the user has access to. Which is why I call this hope-driven development, because you hope the agent is not going to do something bad, because it does have access to it."**

So an Uber identity (an over-privileged anchor, the prime example being an agent running under a user's own desktop session) inherits everything the user can do, and operating an agent that way is **hope-driven development**: you are simply hoping it does not misuse the access it plainly has. This is the over-provisioning problem from the foundations brief (cross-ref: the NHI-2.0-foundations brief's accountability-at-provisioning) named vividly. The answer is to break the Uber identity down:

The project lead: **"once we have this identity, we want to create sub-identities, dozens, hundreds, linked to that, each for a specific use case, specific privileges, some even ephemeral, created when the agent turns up and destroyed when the agent is destroyed."** So you take the Uber identity and decompose it into many narrow sub-identities, each scoped to a use case and privilege, some ephemeral (created when an agent starts, destroyed when it ends). This turns hope-driven development into governed, least-privilege, provenanced identity, the core NHI 2.0 move.

## The Storage Question: Where Do The Sub-Identities And, Crucially, The Private Keys Live?

The practical crux: **once you have the anchor identities, where do the sub-identities, the public keys (with attributes), and above all the private keys actually get stored, can the existing platform hold them, or is infrastructure needed on top?**

The project lead: **"once you have OAuth, Gmail, Active Directory, the next question is: do we have a storage location in that identity to store the sub-identities? Say I have someone's Gmail and I want to break it apart into multiple identities, one can read, one can write. With a Cognito or OAuth login I can log in, but depending on setup I may or may not be able to put data on it. Where can we store the private keys? The private keys should be stored in a place connected with the identity. How does that work, and what does it cost, and what are the limits?"**

| What Must Be Stored | The Question |
|---------------------|--------------|
| **Sub-identities** | Does the existing platform have a place to store them? |
| **Public keys (with attributes)** | Is there a good place to put and distribute them? |
| **Private keys** | The most important: where, connected to the identity, retrievable by the authenticated user? |

This is the make-or-break practical question, and the private keys are the heart of it: they must be stored somewhere connected to the identity and retrievable by the authenticated user, and the existing platform (Cognito, OAuth, a directory) may or may not allow storing that data. A concrete gap the project lead cites: GitHub does not let you create identities for agents, so any GitHub action needs a super-privileged account or app, not the granularity NHI 2.0 wants. Where the existing platform cannot store the sub-identities and keys, the vault fills the gap (cross-ref: the NHI-2.0-foundations brief's vault-as-keyring): the vaults manage the information, the secrets, the public keys, and the private keys. So the key question for the phase is: how much can we leverage what already exists to store and distribute keys, and where must we put a vault layer on top?

## The Commercialisation Principle: Leverage What Exists, But Have Your Own Compatible Version

A principle the project lead calls central: **always leverage what exists, but always have an open-source or customised (usually simpler) compatible version you can deploy, which LLMs now make feasible and which unblocks early MVPs.**

The project lead: **"this is one of the key principles: you always leverage what exists, but you always have either an open-source or customised, usually simpler, version of something compatible that you can deploy, especially now that we can use LLMs to create most of these components. It also helps with early MVPs and integrations: if you are going to put data into Google or Microsoft OAuth but during the MVP you do not have access, these days you can recreate their platform, their APIs, their environment, make it compatible, and then flicking to the real one is just a case of some authentication tokens."**

| The Principle | The Payoff |
|---------------|------------|
| **Leverage what exists** | Do not rebuild the core identity infrastructure |
| **Have your own compatible version** | Open-source or simpler; deployable where the real one is not available |
| **LLMs make it feasible** | Recreating compatible components is now cheap |
| **Unblocks MVPs** | Recreate a provider's API for the MVP; flick to the real one with just auth tokens |

So the model is leverage-plus-fallback: anchor on the organisation's real identity platforms, but always have a compatible (open-source, simpler) version you can deploy, both for resilience and lock-in avoidance (cross-ref: the blast-radius brief's have-your-own-implementations and the open-evaluation brief) and, importantly, for MVPs, recreate the provider's API and environment so the demo works without access to the real platform, then switch to the real one with a token change. This is how the startup leverages existing infrastructure without being blocked by it.

## The First Phase, Summarised

The questions this phase must answer:

- **How can we create identities, and how much do they cost?** (Cheap creation enables granular least privilege.)
- **How can we assign identities to agents, people, code, and things?** (The assignment mechanic.)
- **How does the distribution work, of private keys to the authorised container running the agent, and of public keys to those who need to access it?**
- **How much do we get for free, or at what cost, from the existing platform at the company (or the division) we are working with?**

The project lead: **"this first phase is about understanding what exists, what we need to provide, and the key pieces of the puzzle: how can we create identities, how much they cost, how can we assign identities, how the distribution of private keys and public keys works, and how much we get for free or at a cost from the existing platform."**

## What This Asks For

1. **Live off the land for identity** (do not build a core identity solution; leverage what exists).
2. **Treat identity as provenance** (chain links, chains of trust, not blockchain; every action links to its origin).
3. **Map the first phase** (what identities exist, whether new ones can be created, and the cost of both).
4. **Anchor on existing identities** (individual accounts, cloud accounts and roles, SSO; tied to privileged actions).
5. **Prefer unique identities; fall back to sub-identities under a parent** (cheap creation enables granular least privilege; the admin parent is the worst case).
6. **Break down Uber identities** (decompose the over-privileged anchor into many narrow, often ephemeral sub-identities; end hope-driven development).
7. **Solve the storage question** (where sub-identities, public keys with attributes, and above all private keys live; the vault fills the gap where the platform cannot).
8. **Leverage but keep a compatible fallback** (an open-source or simpler compatible version, LLM-built; for resilience and for MVPs via recreated APIs).
9. **Carry the phase into the series** (the use cases and workflows build on this identity foundation).

Estimated effort: this is the first practical phase of the NHI 2.0 build, mostly reconnaissance and the leverage-plus-fallback design; the vault provides the key and sub-identity storage where the platform cannot. The proof is mapping one organisation's identities, anchoring agent identities (unique or sub), decomposing an Uber identity into ephemeral sub-identities, and storing the private keys in a vault connected to the identity.

## What This Does Not Try To Be

- **Not a core identity provider.** It leverages and anchors on what exists.
- **Not blockchain.** Identity as provenance via chain links and chains of trust.
- **Not hope-driven development.** Uber identities are decomposed into narrow, governed sub-identities.
- **Not blocked by missing infrastructure.** A compatible open-source or simpler fallback, and the vault, fill the gaps.
- **Not the whole series.** The first practical phase; the use cases and workflows follow.

## Honest Risks

**Risk 1: Existing platforms may not store sub-identities or keys.** The crux question may answer "no." Mitigation: the vault fills the gap (cross-ref: the NHI-2.0-foundations brief's vault-as-keyring); the compatible fallback; map this per platform.

**Risk 2: Cheap, granular identity creation is not always available.** Some platforms (e.g. GitHub for agents) do not allow it. Mitigation: sub-identity under a parent; the vault layer; flag the gaps as product opportunities.

**Risk 3: Anchoring on SSO concentrates risk.** SSO is easier but more dangerous to anchor on. Mitigation: decompose into narrow sub-identities; least privilege; the containment thesis (cross-ref: the blast-radius brief).

**Risk 4: Private-key storage is sensitive.** Where private keys live is the heart of the security model. Mitigation: the vault, connected to the identity, retrievable by the authenticated user; secure enclaves at the edge (cross-ref: the foundations and vault-in-vault briefs).

**Risk 5: The compatible fallback must stay genuinely compatible.** A recreated API can drift. Mitigation: keep it a thin, compatible shim; flick to the real platform with a token change; LLMs make maintenance cheap.
