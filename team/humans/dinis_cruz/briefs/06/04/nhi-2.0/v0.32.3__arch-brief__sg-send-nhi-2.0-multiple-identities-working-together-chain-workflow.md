## What This Is

The third in the NHI 2.0 series (cross-ref: the v0.32.3 NHI-2.0-PKI-foundations and NHI-2.0-living-off-the-land briefs): **how multiple identities actually work together in practice, a worked agentic pipeline (an agent reads an inbox, hands to a research agent, hands to an agent that sends an email) implemented with per-agent identities, keys, vaults, and a signed, encrypted chain.** It is the identity-and-capability implementation of the comms the three-agent demo proved (cross-ref: the v0.31.12 three-agent-comms-demo and vault-to-vault-comms briefs). New contributions: **generate-and-register a key versus being given one, secretless agent bootstrapping, capability limited by the code in the agent (and the dangerous trifecta), code-hash attestation of agent state, strongly-typed schemas as prompt-injection defence, the provenance-preserving signed and encrypted chain, and saving every LLM call for full provenance and accounting.**

## Vaults First, Identity Where Access Is Needed

A framing point that bridges from the living-off-the-land brief: **much of this could be done with vaults alone (it is all a graph of graphs), and you only need a core identity where the agent must actually access something, with some agents necessarily more privileged.** The project lead: **"you could do all of this just with vaults; you do not need core identities. Well, ultimately you will need an identity that gives you access to something, and some agents are going to be more privileged."** So vaults carry most of the structure (the keys, the memory, the messages), and a real, anchored identity (cross-ref: the NHI-2.0-living-off-the-land brief) is introduced precisely where the agent needs access to a real asset, with the more privileged agents being the ones that hold those access-granting identities.

## The Worked Example And The Identity Per Agent

The pipeline: **an agent reads an inbox; if research is needed it hands to a research agent; the research agent hands to an agent that sends an email.** Each agent is split out, named, and given its own identity, and that identity is tied to what the agent does.

The project lead: **"the identity for an agent should be connected with what the agent is actually doing, who the agent owner is, and the role of the agent. You split the agents in multiple ways, each agent has a name."** So identity is not generic; it encodes the agent's owner, role, and function. The core primitive under each agent is the vault (cross-ref: the NHI-2.0-foundations brief's vault-as-keyring): **"our vaults allow an easy way for each agent to receive information and store information, to receive secrets, memory, information, and write the output, write what they created."** The vault is how an agent receives its secrets, memory, and inputs, and writes its outputs.

## Generate-And-Register Versus Be-Given A Key

A sharp and important distinction: **whether the agent generates its own keypair and registers its public key, or is given a private key, has real security consequences.**

The project lead: **"the difference between the agent creating a public and private key and registering its public key is interesting: if the agent registers its public key, we know for sure that only that agent has the private key. If we give the private key to the agent, whoever controls the private key can pretend to be the agent too, and can read everything sent to the agent. This might be exactly what we want, or exactly what we do not want."**

| Approach | Consequence |
|----------|-------------|
| **Agent generates keypair, registers its public key** | Only the agent holds the private key; no impersonation, no eavesdropping by others |
| **Agent is given a private key** | Whoever controls that key can impersonate the agent and read everything sent to it |

So generate-and-register is the stronger default (the private key never leaves the agent), while being given a private key is sometimes deliberately wanted (for oversight or recovery) and sometimes a serious weakness (impersonation and eavesdropping). The choice is explicit and per-case. Web Crypto makes the generate path easy: the project lead notes it now runs well in browsers and Node, so creating keypairs without complexity is straightforward.

## Secretless Bootstrapping And Registering As A Capability Agent

A clean provisioning workflow: **an agent can start secretless, create its own vault and keypair, and register its public key as a capability agent.**

The project lead: **"we could allow the agent to start secretless, create a vault it is going to use to communicate, create a public and private key it might or might not show, and then register itself with a repository. The agent creates its own keys and registers the public key as a capability agent: I am an agent that can read email, browse the web, access certain assets."** So rather than handing an agent secrets up front, it bootstraps: generates its keys, sets up its communication vault, and registers what it is and can do. This avoids distributing secrets unnecessarily (the secretless start) and produces a registry of capability agents, each declaring its capabilities, anchored to a public key only it can prove control of.

## Limiting Capability By Code, And The Dangerous Trifecta

A powerful control, and genuinely sharp: **limit what an agent can do by the code it contains, and avoid the dangerous trifecta of accessing data, running code, and connecting to the outside world all at once.**

The project lead: **"we can limit the capability of the agent with the code that is in the agent. If an agent is going to read email, not write, or read one or five emails, we make sure the agent does not have the code required to do more. If the agent sends an email, it should not have the power to read email. There is an interesting trifecta: you do not want agents that can access data, run code, and connect to the outside world all three together."**

| Control | Effect |
|---------|--------|
| **Capability by code** | The agent simply lacks the code to do more than its task |
| **Read-only agent has no write code** | It cannot write even if manipulated |
| **The dangerous trifecta** | Avoid an agent that can access data, execute code, and reach the outside world at once |

So capability is enforced not only by keys but by the code the agent contains: a read-only agent has no writing code, a sending agent has no reading code, so even a manipulated agent cannot exceed its function. And the dangerous trifecta (data access plus code execution plus external communication in one agent, a widely-recognised agent-security risk) is avoided by construction, because each agent is built with only the code its narrow role needs. This is a second, independent layer of containment alongside the keys.

## Code-Hash Attestation Of Agent State

Taking it further: **the agent can attest its hashed code and version at registration, so its pristine state is known before it runs.**

The project lead: **"you can have the code hashed, and the agent can say, here is my code, here is my version, this is what I have inside me right now, a pristine environment before running anything. So you know the state of the agent before running anything, and when the agent registers it can say, here is my current status."** So at registration an agent attests a hash of its code and its version, establishing a known, pristine state before any execution. This means the system knows exactly what the agent is (and that it has only the code its role permits) before trusting it, attestation of agent integrity, which complements the capability-by-code control (you can verify the agent really has only the code it should).

## The Chain Workflow: Signed, Encrypted, Provenance-Preserving

The heart of the brief, the full pipeline implemented with keys and vaults:

```
   AGENT 1  (reads the inbox)
     - receives inbox credentials via its vault
     - does NOT just read: builds a semantic graph of what it read
     - encodes a research request in a STRONGLY-TYPED schema
       (company name, core keywords, objectives)
     - SIGNS with its own key, ENCRYPTS with AGENT 2's public key
     - writes to the vault, triggers Agent 2
                 |
                 v
   AGENT 2  (researcher) - the only one who can decrypt it
     - reads the strongly-typed research request
     - researches (browses, gathers), produces strongly-typed materials
       (markdown, verification, schemas, an ontology/taxonomy, a report,
        evidence, semantic graphs, infographics, screenshots of references)
     - includes Agent 1's original request
     - SIGNS, ENCRYPTS with AGENT 3's public key, writes to the vault
                 |
                 v
   AGENT 3  (sends the email) - the only one who can decrypt it
     - decrypts; because it holds AGENT 1's public key, it can CONFIRM
       the request originated from Agent 1 (provenance preserved
       cryptographically through the chain)
     - sends the email
```

The project lead: **"each agent only receives the data it is supposed to receive, in nice structured form. If you trigger the wrong agent, every other agent cannot read the message, because it does not have the private key the public key was used for. The third agent can decrypt it, and because it has the public key of the first agent, it can confirm the message was originally sent by the first agent. So you still have the provenance of the first one, cryptographically signed."**

Key properties of the chain:
- **Each hop is signed by the sender and encrypted to the next agent's public key**, so only the intended next agent can read it (cross-ref: the vault-to-vault-comms and PKI-not-secrets briefs).
- **A wrong or accidental trigger fails safely**: any agent without the matching private key simply cannot read the message.
- **Provenance is preserved through the chain**: by carrying the original request and the signatures, a later agent (Agent 3) can cryptographically confirm the chain back to Agent 1, decrypt-and-re-encrypt preserves the signed origin.
- **The vault carries the accumulating materials**: research, evidence, semantic graphs, infographics, screenshots of references, easy to add and remove (cross-ref: the blast-radius and evidence briefs).

## Strongly-Typed Schemas As Prompt-Injection Defence

A sharp security contribution within the chain: **tight, strongly-typed inter-agent messages dramatically reduce the prompt-injection surface.**

The project lead: **"the tighter that schema is, the less injection probability exists. If the schema is just the company name, some core keywords, and some objectives, strongly typed, we dramatically reduce prompt injection, because at most you could trick the agent to research another company, but you could not get the email agent to do a bunch of other stuff, and you cannot trick the next agent down."** So because Agent 1 passes Agent 2 a strongly-typed request (not free text), the worst a compromised input can do is alter the typed fields (research a different company), not inject arbitrary instructions, and the downstream agents receive only typed data, not prompts. Strong typing of the inter-agent messages is therefore a structural prompt-injection defence, the tighter the schema, the smaller the attack surface, which combines with capability-by-code and the keys for defence in depth.

## Provenance, Saving Every LLM Call, And Accounting

The provenance and accounting payoff: **saving the vaults gives complete provenance, and saving every LLM call gives maximum provenance plus full token accounting.**

The project lead: **"by saving these vaults, we have complete provenance, and I would argue every single LLM call made should be saved, so you have maximum provenance, and you can go back and understand the token cost. You can price all of this, which is important from an accounting point of view, so we have the accountant agent mapping and tracking everything."** So every step (each vault write, each LLM call) is saved, giving a complete, auditable record of what each agent did and what it cost. This enables token accounting and pricing of the whole workflow, tracked by the accountant agent (cross-ref: the three-agent-demo brief's accountant-agent experiment and the OpenRouter-broker brief), and it is the action-level audit trail NHI 2.0 needs (cross-ref: the NHI-2.0-thesis brief).

## Multiple Identities: Graph Of Graphs, Vault Of Vaults, Identities Of Identities

The structural result: **multiple identities, each connected to the right account, compose into a graph of graphs, a vault of vaults, and identities of identities.**

The project lead: **"this is only possible because we have multiple identities, each connected to the correct inbox. The inbox received from could differ from the inbox sent to, and the account used for research could be a different, parent identity. So you create a graph of graphs, a vault of vaults, and identities of identities, and you can visualise all this."** So each agent in the chain has its own identity tied to its own account (the reading inbox, the sending inbox, the research account, possibly a parent identity), and the whole composes into the nested structure the corpus keeps arriving at (cross-ref: the skill-as-projection-of-graph and vault-in-vault briefs): graphs of graphs, vaults of vaults, identities of identities, visualisable as one connected whole.

## The Reframe: This Is Already Happening, Just Without The Rigour

The crucial framing, and a reassuring one: **this is not more complex than what is happening today; it is what is already happening, but with the attention to detail, version control, testing, and control that is currently missing.**

The project lead: **"if you think this is complex, I would argue it is not. What is happening right now is exactly this, but without this attention to detail, without version control, without testing, without control, which is when things go wrong. The power of this workflow is you can now write tests, integration tests, unit tests, specs, you can code all this, and eventually reduce the amount of LLMs used inline, because ideally you want to create code and flows, just like Claude is doing with their workflows, where the more that runs in code, the better."** So the chain is not added complexity; it is the same multi-agent work organisations are already doing, made rigorous: versioned, tested, specified, and controlled, which is exactly what is missing today and why things go wrong. And it sets up the maturity path (cross-ref: the skill-lifecycle brief): with tests and specs in place, the inline LLMs can be progressively reduced and replaced with code and flows, the explorer-to-code evolution applied to the agentic identity workflow.

## What This Asks For

1. **Tie each agent's identity to its owner, role, and action** (named, split agents; identity encodes function).
2. **Default to generate-and-register** (the agent holds its own private key; give a private key only when impersonation/eavesdropping is acceptable or wanted).
3. **Support secretless bootstrapping** (the agent creates its keys and vault and registers as a capability agent).
4. **Limit capability by code, and avoid the trifecta** (the agent has only the code its role needs; never data access, code execution, and external comms together).
5. **Attest agent state** (hash the code and version at registration; a known pristine state before running).
6. **Implement the signed, encrypted, provenance-preserving chain** (each hop signed and encrypted to the next; wrong agents cannot decrypt; the origin is verifiable downstream).
7. **Use strongly-typed schemas between agents** (tight typed messages as a structural prompt-injection defence).
8. **Save the vaults and every LLM call** (complete provenance; token accounting; the accountant agent).
9. **Compose into the nested structure** (graph of graphs, vault of vaults, identities of identities; visualisable).
10. **Make it rigorous, then reduce the LLMs** (tests, specs, version control, then evolve inline LLMs toward code and flows; cross-ref: the skill-lifecycle brief).
11. **Produce the example** (the read-inbox, research, send-email pipeline implemented end to end with identities, keys, vaults, and the chain).

Estimated effort: substantial but built on documented primitives (vault-to-vault comms, PKI, the vault keyring, provenance, strong typing); the new build is the per-agent identity-and-capability model (generate-and-register, capability-by-code, attestation) and the provenance-preserving chain. The example is the three-agent pipeline implemented with real identities, keys, schemas, and the signed/encrypted chain, with every call saved.

## What This Does Not Try To Be

- **Not generic agent identity.** Identity is tied to owner, role, and action.
- **Not give-the-agent-a-private-key by default.** Generate-and-register unless impersonation/eavesdropping is wanted.
- **Not capability by keys alone.** Capability is also limited by the code the agent contains, and by avoiding the trifecta.
- **Not free-text between agents.** Strongly-typed schemas, for injection resistance.
- **Not more complex than today.** The same work, made rigorous and version-controlled.
- **Not the whole series.** The in-practice implementation; more use cases follow.

## Honest Risks

**Risk 1: Key generation and registration must be sound.** Generate-and-register relies on correct crypto. Mitigation: Web Crypto in browsers and Node; proven mechanisms; the registry of capability agents.

**Risk 2: Capability-by-code requires disciplined agent construction.** Agents must genuinely lack the extra code. Mitigation: code-hash attestation verifies it; build agents minimally; the trifecta rule as a design check.

**Risk 3: Schema design is security-critical.** A loose schema reopens injection. Mitigation: strongly typed, minimal fields; the tighter the schema, the smaller the surface; combine with keys and capability-by-code.

**Risk 4: Saving every LLM call is heavy.** Full provenance has a storage cost. Mitigation: the vault stores it; the accounting payoff justifies it; prune or summarise where appropriate.

**Risk 5: The nested structure can get complex to manage.** Graph of graphs, vault of vaults, identities of identities. Mitigation: visualisation (cross-ref: the visualisation briefs); the reframe (this is already happening, now made rigorous) keeps it grounded.
