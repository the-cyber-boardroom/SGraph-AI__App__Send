## What This Is

The memo flagged at the end of the skill-as-projection brief (cross-ref: the v0.32.3 skill-as-projection-of-graph brief): **the software development lifecycle seen through Wardley maps, applied to skills, where a skill evolves from an explorer (LLM-heavy, English, token-hungry) to a town planner (code, schemas, commodity).** It develops the Wardley characters that the skills-as-graph and skill-as-projection briefs only flagged (cross-ref: the v0.32.3 skills-as-graph and skill-as-projection briefs), and it deepens the token-optimisation thread (cross-ref: the v0.31.7 skill-comparison-CLI-wrapping-token-optimisation brief) into a full maturity model. The genuinely new contributions: **the explorer-to-town-planner evolution of a skill, the English-to-code progression, the sharp insight that high token spend is an engineering problem, the brief-discovery value of the explorer phase, the refactor-with-a-test-harness path (where the test harness can stay LLM-powered while the skill becomes code), and the full skill lifecycle ending in commoditisation or absorption.**

This is the fifth in the 4 June skills series.

## The Explorer: Where You Discover The Brief

The starting point, in Wardley terms: **an LLM-driven or LLM-powered solution is a typical explorer, a Genesis, custom-build thing, and its real value is that it discovers the brief.**

The project lead: **"the experimentation, an LLM-driven or LLM-powered solution, written heavily by an LLM or with LLMs inline, is a typical explorer. They are where you discover the brief. They are Genesis, the custom-build world, and they let us define the brief better. In the past this used to take weeks, months, or years; now you can do it in hours, and you can iterate, so you have the ability to create better briefs."** So the explorer phase, an LLM doing most or all of the work, often with little or no code, is enormously valuable, but for a specific reason: it is how you discover and define the brief, fast. What used to take months of analysis now takes hours of iterating with an LLM, producing a far better brief. The explorer's value is brief-discovery and iteration, not the artifact it produces.

## The Mistake: Thinking The Explorer Is The Final Product

The central warning, and a sharp, quotable insight: **the mistake is to think the explorer version is the final product, and high token spend is the symptom of that mistake, an engineering problem.**

The project lead: **"the mistake is to think that is the final product. You see it with skills: people think, I have this cool skill, I can do all this stuff, but then it requires lots of tokens, and people are seeing massive token usage. That is because they are not engineering their practices. Anybody who spends a lot of money on tokens has an engineering problem. They are using explorer-type code and solutions in a commodity environment."**

| The Symptom | The Diagnosis |
|-------------|---------------|
| A skill works but burns massive tokens | It is still in explorer form, being used as a product |
| High token spend | An engineering problem, not a usage problem |
| LLM doing everything, every time | Explorer-type solution running in a commodity context |

This is the key insight of the brief: **high token spend is an engineering problem.** A skill that works but consumes huge token volumes is an explorer-stage solution being run as if it were a finished product, in a commodity context where it does not belong. The fix is not to accept the token cost; it is to evolve the skill along the maturity curve (below). Token spend is a signal that the skill has not been engineered down from explorer to product to commodity.

## The Natural Progression: English To Code

The direction of evolution: **a skill naturally progresses from English to code, narrowing scope and variability as it matures toward reliability and repeatability.**

The project lead: **"the natural progression of a skill is to start in English and end up in code. As you refine the skill, you reduce the scope, you reduce the variability. You want reliability, you want the skill to do that thing once, effectively, repeatedly. You want explainability, repeatability, you want to make sure it does not go off piste. It does one thing really, really well."**

| Early (Explorer) | Late (Town Planner) |
|------------------|---------------------|
| English, LLM-driven | Code |
| Broad scope, high variability | Narrow scope, low variability |
| Flexible, exploratory | Reliable, repeatable, explainable |
| Does many things, variably | Does one thing really well |
| Token-hungry | Cheap, deterministic |

So maturity is the movement from English (flexible, exploratory, expensive) toward code (narrow, reliable, cheap). As a skill matures you deliberately reduce its scope and variability, because what you now want is reliability, repeatability, and explainability, the skill doing one thing really well, every time, not going off-piste. The English-to-code progression is the mechanism of that maturing.

## The Refactor Path: Drive Down The LLM With A Test Harness

The how, and a sharp nuance about testing: **once you have the brief and a good test harness, you ask how far down you can drive the LLM, and the test harness itself can stay LLM-powered even as the skill becomes code.**

The project lead: **"once I have the brief, that is where you create the specs, the tests, the acceptance criteria, the ability to say, is this correct? And the testing can be more in explorer mode, because the testing can have the subjectivity and power of an LLM, so we can ask much better questions of testing. Then, once the skill is defined and we have a good test harness and test suite, we can start asking: what is the smallest LLM we can use? Can we remove context? Can we remove text? Can we simplify? Can we refactor? You keep doing that."**

| Step | What Happens |
|------|--------------|
| Have the brief (from the explorer phase) | The skill is defined |
| Create specs, tests, acceptance criteria | The ability to say "is this correct?" |
| Keep the test harness LLM-powered | Tests can use the LLM's subjectivity and power to ask better questions |
| Drive down the skill | What is the smallest LLM? Remove context? Remove text? Simplify? Refactor? |
| Repeat | Keep refactoring toward code |

The nuance is valuable: **the test harness can stay in explorer mode (LLM-powered) while the skill itself is driven down to code.** Testing benefits from the LLM's subjectivity and power (it can ask richer, more human questions of correctness), so you keep the tests LLM-powered even as you make the skill deterministic. With that harness in place, you iteratively ask how far you can simplify, the smallest model, less context, less text, more code, refactoring repeatedly. This is the engineering discipline that drives the token cost down: a good (LLM-powered) test harness lets you safely refactor the skill from LLM-heavy toward code.

## The Product Phase: Used, Maintained, Sold

The middle stage (the settler, in Wardley terms): **the refactored skill becomes a product, used by others, maintained, and charged for.**

The project lead: **"you keep doing that, and that is what you do in a product, where you get others to use it, it gets maintainable, it gets sold, it gets charged. There is a business model here."** So as the skill is refactored from explorer toward reliability, it reaches product maturity: others use it, it is maintained, and it is sold and charged for, the business model (cross-ref: the consulting-firms-to-product and ownership briefs). This is the stage where the skill economy lives: a skill engineered enough to be reliable and maintainable is a product, and the product is what is monetised.

## The Town Planner: Drive It To Code And Commodity

The mature stage: **hand the product to the town planners, who remove inline LLMs, add strong schemas, and turn it into solid code built on commoditised primitives.**

The project lead: **"when you have product maturity, you should do another round, hand over to the town planners, and they really go to town on removing any inline LLMs, making sure there are strong schemas, the code is solid. You transform it into code, probably using other primitives that have now been commoditised."**

| The Town Planner's Job | Result |
|------------------------|--------|
| Remove any inline LLMs | Deterministic, no per-run LLM cost |
| Add strong schemas | Reliable, validated |
| Make the code solid | Production-grade |
| Use commoditised primitives | Built on what is now commodity |

So the final engineering pass is the town-planner pass: take the product and industrialise it, remove the inline LLMs entirely, enforce strong schemas, solidify the code, and build on primitives that have themselves been commoditised. The skill that began as pure English and LLM ends as solid, schema-validated code, a commodity.

## The Full Lifecycle Of A Skill

Putting the stages together, the project lead's lifecycle:

```
   EXPLORER          ->   PRODUCT            ->   TOWN PLANNER       ->   (ABSORBED)
   massive LLM            others use it           remove inline LLMs       commoditised
   English, no code       maintainable            strong schemas           eventually
   very expensive         sold, charged           solid code               absorbed by
   lots of tokens         (the business model)    commodity primitives     something else
   discovers the brief                            English -> code          and disappears
```

The project lead: **"the lifecycle of a skill is to start as massive LLM, held together with string and gum, very expensive, lots of tokens, all the way to a product, all the way to code, and it almost becomes a commodity, eventually disappearing, because maybe it is absorbed by something else. That is the lifecycle of a skill."** So a skill is born as an expensive, token-hungry, LLM-driven explorer that discovers the brief; it matures into a maintained, sold product; it is industrialised by town planners into solid, schema-backed code; and eventually it commoditises and may be absorbed into something else and disappear. This is the full Wardley evolution applied to a skill, and it closes the lifecycle thread (cross-ref: the skills-as-graph brief's creation-to-retirement lifecycle): retirement here is commoditisation and absorption.

## Why This Matters

This reframes how to think about skills and their cost:

- **The explorer phase is for discovering the brief, fast**, not for shipping the final product; its value is the better brief in hours.
- **High token spend is an engineering signal**, the skill is stuck in explorer form; the response is to evolve it, not to pay the tokens.
- **Maturity means English to code**, narrowing scope and variability toward reliability, with an LLM-powered test harness enabling the refactor.
- **The product phase is where the money is**, a reliable, maintained, sold skill (cross-ref: the consulting-firms and ownership briefs).
- **The town-planner phase commoditises it**, code, schemas, commodity primitives, and eventually absorption.

Together this gives the skill economy its engineering and economic discipline: know which stage a skill is in, do not mistake an explorer for a product, and evolve skills down the maturity curve so they become reliable, cheap, and eventually commodity.

## What This Asks For

1. **Use the explorer phase to discover the brief** (LLM-driven, fast, iterative; the value is the brief, not the artifact).
2. **Do not mistake the explorer for the product** (high token spend is an engineering problem, not a cost to accept).
3. **Progress skills from English to code** (reduce scope and variability; reliability, repeatability, explainability; do one thing well).
4. **Build an LLM-powered test harness** (specs, tests, acceptance criteria; keep the tests LLM-powered for better questions while the skill becomes code).
5. **Refactor down the LLM** (smallest model, remove context, remove text, simplify; repeat).
6. **Reach the product phase** (used, maintained, sold, charged; the business model).
7. **Hand to the town planners** (remove inline LLMs, strong schemas, solid code, commoditised primitives).
8. **Recognise the full lifecycle** (explorer to product to code to commodity to absorption; retirement as commoditisation).
9. **Produce the library page and example** (the page explains the skill lifecycle and the token-spend-is-engineering insight; an example skill evolved from explorer to code, with its test harness, is the MVP).

Estimated effort: this is an engineering-discipline and lifecycle framing; the test-harness, refactoring, and token-optimisation practices exist (cross-ref: the token-optimisation brief); the contribution is the explorer-to-town-planner model and the discipline of evolving skills down it. The example is one skill taken from an LLM-heavy explorer to refactored code, with the LLM-powered test harness that enabled it.

## What This Does Not Try To Be

- **Not anti-LLM.** The explorer phase (LLM-heavy) is essential, for discovering the brief.
- **Not accepting high token cost.** High tokens signal an unevolved skill; evolve it.
- **Not English-forever.** Skills progress from English to code as they mature.
- **Not deterministic testing only.** The test harness can stay LLM-powered even as the skill becomes code.
- **Not the end of the series' graph thread.** This is the maturity/lifecycle view; the graph briefs are the structure view.

## Honest Risks

**Risk 1: Evolving every skill to code is effort.** Not all skills justify the town-planner pass. Mitigation: evolve based on use and cost (high token spend signals which to evolve); leave low-use skills in explorer form; the lifecycle includes retirement.

**Risk 2: Premature optimisation.** Driving to code too early loses the explorer's flexibility. Mitigation: discover the brief first; only refactor once the brief and test harness are solid; the stages are ordered for a reason.

**Risk 3: The test harness is critical and non-trivial.** Refactoring safely needs good tests. Mitigation: build the LLM-powered harness first; it is the thing that makes the refactor safe; tests can use the LLM's subjectivity.

**Risk 4: Losing explainability when driving to code.** Mitigation: explainability is an explicit goal of the progression (one thing well, repeatable); schemas and solid code aid, not hinder, explainability.
