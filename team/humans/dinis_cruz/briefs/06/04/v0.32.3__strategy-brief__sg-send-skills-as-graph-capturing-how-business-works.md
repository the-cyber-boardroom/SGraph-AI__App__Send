## What This Is

The memo flagged at the end of the skills-are-software-packages brief (cross-ref: the v0.32.3 skills-are-software-packages brief): **why skills are the first scalable way for a business to capture how it actually works.** It deepens the 2 June knowledge-capture thesis (cross-ref: the v0.31.9 skills-as-business-knowledge-capture brief), which already established that the real power of skills is capturing how a business works, that past attempts (Confluence, SharePoint, wikis) were static and died, and that the breakthrough is skills being living and maintained. This brief does not re-derive that; it adds the genuinely new layers: **the Wardley-evolution reason this is possible now, a sharper diagnosis of why the old model failed, the central idea that a skill is a graph of skills (not a static document), the taxonomy and ontology this requires, the small-versus-large-company handover insight, and the built-in error-correction that comes from a skill being used every day.**

This is the third in the 4 June skills series.

## Why Now: The Wardley Evolution Of The Map

The grounding the project lead gives for the timing: **skills are an example of evolution on a Wardley map, possible only because of what LLMs can now do.**

The project lead: **"skills are a good example of the Wardley map's evolution scale, where a number of things evolve, new orders appear, implementations appear above. Skills could only be possible with the level of LLMs we have right now, with the ability to execute things, to consume and execute code, and the mini-agents. All that is now allowing this skills ecosystem to emerge."** So skills are not a fashion; they are an evolution-of-the-map step that became possible when the components beneath them (LLMs that understand English, execute, run code, and the mini-agents) matured. This is the why-now: the substrate evolved, and skills are the new order that appears above it. It also sets up the context-specificity point later (the same skill differs by Wardley character).

## A Sharper Diagnosis Of Why The Old Model Failed

The 2 June brief established that the old documentation model died; this memo sharpens *why*, through the asymmetric forces at play.

The project lead: **"in security we had run books and playbooks and documentation practices. The effort was to put this in Confluence, SharePoint, GitHub, wikis. They were popular because they are a way to capture knowledge, which is fundamental, but it never really worked, because of asymmetric forces."**

| The Force | Why It Killed The Old Model |
|-----------|------------------------------|
| **The experts will not write it** | The people best able to document had no time or inclination; they did not need it themselves, so there was no benefit, only cost |
| **Pure cost behaves like a tax** | When something is pure cost, it is like a tax, so it does not happen |
| **Juniors cannot fill the gap** | Pushing it to juniors helps a little, but they lack the knowledge, and experts still must review, so it stays a drag |
| **It never got used** | The fundamental problem: pre-LLM documentation never scaled because it never got used |

The project lead: **"the people who could best write the documentation did not have the time or inclination, because for them it was a waste of time, a pure cost, and when things are pure cost, it is like a tax, so it does not happen. You try to push it to junior people, but they do not have the knowledge, and you still need the experts to review it, so you have a massive drag. The fundamental problem is that pre-LLM, these analogue skills never scaled because they never got used."** The sharp formulation is "pure cost behaves like a tax, so it does not happen," and the root cause is non-use: documentation that is not used is not maintained, and dies. This is the asymmetry skills break, because (per the knowledge-capture brief and the error-correction section below) a skill that is used is maintained by being used.

## The Central New Idea: A Skill Is A Graph Of Skills

The most important addition: **a skill is not a static document captured once; it is a graph of skills, with context, usage, and situational awareness.**

The project lead: **"the skill is not static, or captured once. You actually have skills of skills. Skills have context. Skills have a whole tree of skills that need to be managed as a graph, because you have to have context. A skill is a graph of multiple skills combined with context, combined with how it is supposed to be used, combined with situational awareness, and now we can scale this."**

| A Static Document (Old) | A Graph Of Skills (New) |
|-------------------------|--------------------------|
| Captured once | Composed of skills of skills |
| No context | Carries context |
| A flat page | A tree/graph, managed as a graph |
| Read as-is | Includes how it is supposed to be used |
| Context-free | Includes situational awareness |

So the unit is not a skill-as-document but a skill-as-graph: skills compose into other skills, each carrying its context, its intended use, and situational awareness, and the whole is managed as a graph (cross-ref: the semantic-knowledge-graphs-for-skills brief and the vault-per-standard graph machinery). This is why skills can capture how a business *actually* works: a business is not a flat document, it is an interconnected graph of practices, contexts, and situations, and only a graph of skills can represent that. It is also why skills must be software packages (cross-ref: the skills-are-software-packages brief): a graph of composable, versioned, customisable units is a software-management problem.

## Taxonomy, Ontology, And The Functions Companies Never Funded

A requirement that follows from the graph: **to scale skills you need taxonomy and ontology, which means the librarian and journalist functions companies historically never invested in.**

The project lead: **"companies never hired librarians, never hired journalists, so they never invested in the taxonomy and ontology, which is what is needed. To scale skills you need ontology, taxonomies, references, customisation capabilities, and you need to abstract the skill itself from all the references and implications of how it operates."**

| What Scaling Skills Requires | Why |
|------------------------------|-----|
| **Taxonomy and ontology** | To organise and relate the graph of skills |
| **References** | To connect skills to their sources and context |
| **Customisation capabilities** | To adapt skills per context (cross-ref: the finance-team and ownership briefs) |
| **Abstraction of the skill from its references** | So the skill is reusable, separate from the specifics of how it operates |
| **Librarian and journalist functions** | The roles that build and maintain taxonomy, ontology, and clear capture, which companies never funded |

This explains a gap: companies spent millions on capturing knowledge but never funded the library science (taxonomy, ontology) or the editorial craft (journalism, clear capture) that the graph needs, so it never cohered. The platform's own agent team includes exactly these roles (the @Librarian, @Ontologist, and @Journalist agents; cross-ref: the protocol-harness-workflow FAQ's Email-FS-lite roster), which is how the graph of skills is built and kept coherent now: the functions that were too expensive to staff as humans are viable as part of an agentic team.

## The Handover Insight: Capturing The Intersections, Not Just The Functions

A sharp observation about organisations: **small companies are faster not because of resources but because their handovers and inter-departmental attrition are smaller, and a graph of skills captures those intersections.**

The project lead: **"the main reason smaller companies are leaner, faster, and more efficient than bigger companies is not resources. It is that the communications, the handovers, the department interactions, the attrition between departments become massive. In a small team or company, a lot of those roles get merged, people interact more and help each other, because they can connect the dots. That does not mean the functions are not important, they are, it is just that those handovers and touch points were very inefficient in the past."**

So the inefficiency of large organisations lives in the *intersections*: the handovers, the touch points, the attrition between departments, not in the functions themselves (which remain important). This is the deeper reason a graph of skills matters: it captures not just how each function works but **how the functions intersect, hand over, and interact**, which is exactly where large organisations lose speed. The project lead: **"a graph of skills is now fundamental, because you have a way to capture how the business is working, how the functions are working, how the intersections are working, and how the multiple parts operate, and how they evolve, version-controlled."** Capturing the intersections (the handovers) is what could let a large organisation regain some of the small-company speed, because the touch points become explicit, maintained, and improvable rather than tacit and lossy.

## Context-Specificity: The Same Skill Differs By Character

Tying back to Wardley: **the same skill is very different depending on the context and character it serves.**

The project lead: **"a skill, the same skill for a town planner, is very different for an explorer, for a villager. It is all about context-specific, but now we can do this, and we can scale."** So a skill is not one-size-fits-all: the same nominal skill must differ for an explorer (a pioneer, doing the new and uncertain), a villager, and a town planner (industrialising the known), the Wardley characters. This is the customisation thesis (cross-ref: the finance-team and opinionated-expertise briefs) grounded in Wardley: context determines the right form of a skill, and the graph plus customisation is what lets the same skill be rendered correctly for each character, at scale.

## The Other New Idea: Built-In Error Correction

The second major addition, and a powerful one: **a skill that defines a practice people use every day is verified and refined every day, so graph-based skills have built-in error correction.**

The project lead: **"the power is that you should be verifying the quality of a skill every day, because if you have a skill that defines a practice, every day people are using that skill. So you capture and refine the touch points, every day you are refining and improving all these little touch points, making the skill better and the workflow better. Skills have a built-in error-correction system, refinement, and retirement."**

| Static Document (Old) | Used Skill (New) |
|-----------------------|-------------------|
| Written once, decays | Used every day, so verified every day |
| No feedback | Every use is a touch point that can be refined |
| Quality unknown and falling | Quality checkable daily; improving |
| Lives forever, stale | Has a retirement step in its lifecycle |

This is the resolution of the old model's fatal flaw (non-use): because a skill is *used* to do the work, every use is an opportunity to verify and refine it, so the skill and the workflow improve continuously. Graph-based skills therefore have a built-in error-correction and refinement mechanism, and, importantly, a retirement step, the full lifecycle. The project lead: **"you have to have the whole life cycle, from creation to publishing to releasing to distributing to maintaining to retiring."** This is the living-not-static principle (cross-ref: the knowledge-capture brief) made mechanical: not just that skills *can* be maintained, but that being used *is* the maintenance, daily verification and refinement built into the act of doing the work, with retirement closing the loop.

## Why This Matters

The 2 June brief said skills capture how a business works and can be living. This memo says *how and why that scales now*: because skills are a graph (composable, contextual, situational), because the substrate (LLMs) evolved to make it possible, because the taxonomy and ontology functions are now viable as agents, because the graph captures the intersections where large organisations lose speed, and because using a skill verifies and refines it daily. Together these are why the project lead believes skills will be massive: for the first time there is a scalable way to capture how a business works, dynamic and version-controlled, replacing static Confluence-style sources, with the practices and tooling still to be figured out but the direction clear and the investment coming.

## What This Does Not Try To Be

- **Not a re-derivation of the 2 June thesis.** That brief established capture-how-the-business-works and living-not-static; this adds the graph, the why-now, and the error correction.
- **Not a static document.** A graph of skills with context, usage, and situational awareness.
- **Not one-size-fits-all.** Context-specific by Wardley character; customised.
- **Not captured-once.** Used daily, verified daily, refined daily, retired when due.

## Honest Risks

**Risk 1: The graph of skills is complex to build and manage.** A graph with context, usage, and situational awareness is hard. Mitigation: the semantic-graph machinery (cross-ref: the skills-graph and vault-per-standard briefs); the agent roles (librarian, ontologist, journalist); start with one function.

**Risk 2: Taxonomy and ontology are real, skilled work.** These functions were never funded for a reason. Mitigation: they are now viable as agents (cross-ref: the FAQ's Email-FS-lite roster); start small; the graph grows incrementally.

**Risk 3: Daily verification needs the skill to actually be used.** Error correction depends on use. Mitigation: that is the design (using is the maintenance); skills that are not used should be retired (the lifecycle); non-use is the signal, not a failure.

**Risk 4: Capturing intersections touches organisational politics.** Handovers and attrition are sensitive. Mitigation: capture how things work, not blame; the graph is a tool for improving touch points; provenance and version control keep it factual.
