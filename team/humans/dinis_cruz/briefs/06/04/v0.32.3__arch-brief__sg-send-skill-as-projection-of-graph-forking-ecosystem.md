## What This Is

The intersection of several threads: **skills need semantic and knowledge graphs, because a skill is a projection of a graph, decomposes into typed primitives, and lives in a forking ecosystem held together by connectivity.** It extends the graph thinking from the 1 June semantic-graphs brief (cross-ref: the v0.31.7 semantic-knowledge-graphs-for-agentic-skills brief) and today's skills-as-graph brief (cross-ref: the v0.32.3 skills-as-graph-capturing-how-business-works brief), which established that a skill is a graph of skills managed as a graph. This brief adds the genuinely new layers: **the projection paradigm (a skill is a projection of a semantic knowledge graph, where today's skills are static photographs), the decomposition of a skill into typed primitives (principles, concepts, facts, knowledge, actions), meaning through connectivity, the multiple graph types a skill connects, and the forking-and-open-source-tax ecosystem that lets edge customisation stay compatible.**

The project lead flags the next memo: the skill as a Wardley-map evolution (explorer, village, town planner, a maturity level, eventually high-LLM to low-LLM). This brief does not develop that; it is noted as the lead-in.

This is the fourth in the 4 June skills series.

## The Projection Paradigm: A Skill Is A Projection Of A Graph

The anchor idea, and a paradigm shift the project lead draws by analogy to documents: **the same way a document is a projection of a graph, a skill is a projection of a semantic knowledge graph, and today's skills are merely static photographs of what they should be.**

The project lead: **"there is another big paradigm shift here. The same way I talk about documents being projections of graphs, the skill is a projection of a graph, a projection of a semantic knowledge graph. Because the skill is describing actions, intent, facts, situations, environments, requirements, code, all of that. The skills we have today are just a photograph of what it should be, because it is static. It is a better photograph than before, but it is still a static document. What we want is for that to be abstracted, and then we have a projection created in the context of how the skill is going to be used."**

| Today's Skill (A Photograph) | A Skill As A Projection |
|------------------------------|--------------------------|
| Static document | A projection of an underlying graph |
| Captured once, fixed | Generated in the context of use |
| Better than before, but still a snapshot | Abstracted, then projected per context |
| One form for all | Multilingual, cultural, situational projections from one graph |

This is the sharp reframe: a skill should not *be* the document; it should be a *projection* of an underlying semantic knowledge graph, generated in the context of how it will be used. Today's skills, even good ones, are static photographs of that graph. Once the skill is abstracted to its graph, you can project it into the right form for the context, including (the project lead notes) different languages, cultures, and situations, because the abstraction layer sits beneath the projection. This is the documents-are-projections-of-graphs principle (a recurring SGraph idea; cross-ref: the vault-per-standard document-to-graph brief) applied to skills: the graph is the truth, the skill is a view of it.

## A Skill Decomposes Into Typed Primitives

What the graph is made of: **a skill is a graph of graphs of graphs, decomposing into typed primitives, principles, concepts, facts, knowledge, and actions.**

The project lead: **"a skill fundamentally is a graph of graphs of graphs, because you do not just have one skill. You have principles, concepts, facts, knowledge, and actions. You can start to abstract the skill into this set of primitives, and then you define the standards, and that is how you scale."**

| Primitive | What It Is |
|-----------|-----------|
| **Principles** | The guiding rules |
| **Concepts** | The ideas and definitions |
| **Facts** | The known truths |
| **Knowledge** | The accumulated understanding |
| **Actions** | What is actually done (the value; see below) |

So a skill is not atomic; it abstracts into a set of typed primitives, and because each primitive is itself a graph (and connects to others), the whole is a graph of graphs of graphs. Defining the standards for these primitives is what lets skills scale: once principles, concepts, facts, knowledge, and actions are typed and standardised, skills can be composed, compared, and connected reliably (cross-ref: the skills-are-software-packages brief's lifecycle, and the skills-as-graph brief's graph-of-skills). This decomposition is what makes the projection possible: you project the graph of primitives into a skill for a given context.

## Meaning Through Connectivity

The principle underlying the graph: **the more connected things are, the more you understand what they are, meaning comes through connectivity.**

The project lead: **"this is where you have the graphs-of-graphs architecture, where you have meaning through connectivity, where the more connected things are, the more you understand what they are."** So a primitive or a skill is not fully meaningful in isolation; its meaning emerges from how it connects to others (its principles, the concepts it draws on, the facts it relies on, the other skills it composes with). This is why everything must connect, and why the graph (not the document) is the unit of truth: connectivity is what carries meaning, and a static photograph loses it.

## A Skill Connects Multiple Graph Types

A precise architectural point: **a skill connects not only to semantic knowledge graphs but to control-flow graphs, permission maps, authentication maps, and identity graphs.**

The project lead: **"a coding standard is a skill like this, a GDPR standard, a requirement, a way of working, a practice, how to do X, all of those become skills that need to be version-controlled, integrated, and connected. That is why they all have to be graphs, semantic knowledge graphs and control-flow graphs, and also permission maps, authentication maps, identity graphs, all those are very important because they need to connect to each other."**

| Graph Type | What It Captures |
|------------|------------------|
| **Semantic knowledge graph** | Meaning, concepts, facts, relationships |
| **Control-flow graph** | How the actions sequence and execute |
| **Permission map** | What is allowed |
| **Authentication map** | Who is authenticated |
| **Identity graph** | Identities and their relationships (cross-ref: the PKI-not-secrets brief) |

So a skill is the meeting point of several graph types, and they must interconnect: the semantic graph gives meaning, the control-flow graph gives execution, and the permission, authentication, and identity graphs gate it (cross-ref: the PKI-not-secrets brief, where keys gate the workflow). A standard, a practice, a requirement, a way of working, all become skills, all are graphs, and all connect. This is why the graph thinking is not optional decoration: skills carry execution and security semantics that only graphs can connect coherently.

## The Forking Ecosystem And The Open-Source Tax

The major new contribution on ecosystem health: **the explosion of skills comes from customisation, forking a skill is good, and the graph plus a contribute-back discipline (the open-source tax) keeps edge customisation compatible with the top.**

The project lead explains why skills proliferate: **"a top-level skill applies only up to a point that is not exactly matched to the requirement, which is why companies will have ten skills, especially now that the cost of creating a new skill is much lower. People will customise it. But you want to customise on top of the previous one, and that is why you need graphs, this interconnection of skills, to make sure they are compatible."** So skills explode because a generic top-level skill never exactly fits, and customisation is now cheap, so everyone makes their own variant. The risk is fragmentation; the answer is the open-source forking model.

The project lead: **"we already have this concept in open source: it is called forks. Forking a skill is not a bad thing, it is a massive way to leverage what exists. And you have the open-source tax: if you fork something open source and do not contribute back, the problem is you have to maintain it yourself. So you fork a skill, make changes, and give back with pull-request equivalents, and that management structure. Then you have a much healthier ecosystem, because you are not disallowing the people at the edge from creating customised versions, but you make sure they synchronise to the top."**

| Concept | Applied To Skills |
|---------|-------------------|
| **Fork** | Customise a skill from an existing one; leverage what exists (forking is good) |
| **Open-source tax** | If you fork and do not contribute back, you must maintain the divergence yourself |
| **Contribute back** | Give changes back via pull-request-equivalents |
| **Synchronise to the top** | Edge customisations stay compatible with the upstream skill |
| **The graph** | What makes compatibility checkable across forks |

This is a genuinely healthy ecosystem model: the edge is free to create customised versions (forks), which is encouraged, but the open-source tax (you maintain what you do not contribute back) creates the incentive to give changes upstream, and the graph makes it possible to check that a fork stays compatible with the top. This resolves the customisation-versus-coherence tension (cross-ref: the finance-team brief's kept-in-sync cascade and the ownership brief's you-touch-it-you-own-it): customise freely, but synchronise to the top, with forking, pull-requests, and the open-source tax as the management structure. The graph is what lets all the forks remain a coherent ecosystem rather than fragmenting.

## The Power: Focus On The Action That Adds Value

The payoff the project lead emphasises (reinforcing the intent point; cross-ref: the skills-are-software-packages brief): **skills let us focus on intent and on the particular action that adds value, boiled down to the actual value-adding action.**

The project lead: **"the power of skills is that they allow us to focus on intent, on a particular action that adds value, and that is massive, because you boil it down to the actual action that adds value."** So among the typed primitives, the actions are where the value is, and skills let you focus on the value-adding action specifically, with the principles, concepts, facts, and knowledge connected around it as context. Skills focus on intent and the action that adds value, which is why the projection-of-a-graph is so useful: it can present exactly the value-adding action, in context, drawn from the full graph beneath.

## What This Does Not Try To Be

- **Not a static document.** A projection of a graph, generated in context.
- **Not atomic.** A skill decomposes into typed primitives; a graph of graphs of graphs.
- **Not only a semantic graph.** Also control-flow, permission, authentication, and identity graphs, interconnected.
- **Not fragmentation.** Forking with the open-source tax and synchronise-to-the-top keeps the ecosystem coherent.
- **Not the Wardley-maturity memo.** That is next; only flagged here.

## Honest Risks

**Risk 1: The projection architecture is ambitious.** Abstracting skills to graphs and projecting in context is hard. Mitigation: the document-to-graph machinery (cross-ref: the vault-per-standard brief); start with one skill abstracted to its primitives and projected.

**Risk 2: Typed primitives and standards are real design work.** Principles, concepts, facts, knowledge, actions must be typed and standardised. Mitigation: define the standards incrementally; the agent roles (ontologist, librarian; cross-ref: the FAQ's Email-FS-lite roster) build the taxonomy.

**Risk 3: The forking ecosystem needs tooling and culture.** Forks, pull-requests, sync-to-the-top need infrastructure and norms. Mitigation: the open-source model is proven; the graph checks compatibility; the open-source tax provides the incentive; reuse version-control machinery (cross-ref: the commit-queue and skills-are-software-packages briefs).

**Risk 4: Connecting multiple graph types is complex.** Semantic, control-flow, permission, authentication, identity graphs must interconnect. Mitigation: connect incrementally; the identity and permission graphs align with the PKI work (cross-ref: the PKI-not-secrets brief).
