## What This Is

How the tools-execution control flow integrates into the vault: **tools live at the vault top level and the vault kernel, not the vault app, manages, blocks, and limits them, the apps just use SG-star access the way they access the file system, a tool must never have more power than the vault app that contains it, the code is developed on the tools site and imported rather than written in the vault, the killer workflow is a two-pane chat-edits-the-vault (chat on the left, the vault page on the right, with the tools able to read and write files, refresh, and open panes), the vault app self-registers its own domain tools (contact management, forms, calculations) and exposes them to the chat UI, and the first MVP is a vault app that exposes read and write via tools, so the imported code can be validated end to end before it moves into the kernel.** It is Part Two; the standalone control flow is Part One (cross-ref: the v0.33.38 tools-execution-control-flow brief). It is the capture the project lead will hand to the agent to turn into an implementation brief. It builds on the kernel model and the editing workflow (cross-ref: the v0.27.62 vault-in-vault-kernel-model and v0.33.21 provider-self-service-vault-editing briefs). New contributions: **the kernel-manages-tools placement, the tool-not-more-powerful-than-the-app containment, the chat-edits-the-vault workflow, the self-registering vault tools, and the MVP-as-a-vault-app approach.**

## The Placement: Tools At The Vault Top Level, Managed By The Kernel

The architectural decision: **tools belong to the vault, not the vault app, and the kernel manages them.**

The project lead: **"the way to do this is to remove it from the vault app and put it at the vault top level. When you go into a vault, the vault can access a number of tools and capabilities, and the apps running inside just use SG-star access, the same way they access the file system. It is not the vault app's responsibility to manage, block, limit, or control what a tool does, it is the vault's responsibility. The vault kernel is the one that manages this."**

| Layer | Responsibility |
|-------|----------------|
| Vault kernel | Manages, blocks, limits, and controls the tools |
| Vault app | Just uses SG-star access to invoke tools, like the file system |

So tool governance is a kernel concern, and apps consume tools as a capability without owning their control, exactly the vault-in-vault kernel model (cross-ref: the vault-in-vault-kernel-model brief).

## The Containment: A Tool Must Not Exceed The App

The critical security property: **a tool can never have more power than the vault app that contains it.**

The project lead: **"the tool should not have more power than the vault app. Even if we give a tool write permissions or write capability, it should still be contained by the vault app. When we integrate this into the vault, we should take that into account."** So the vault app is the ceiling on a tool's power: a tool with write capability is still bounded by what the app itself is allowed to do. This is the containment principle from Part One made into a hard rule at integration (cross-ref: the tools-execution-control-flow brief and the blast-radius thinking in the access-not-security brief).

## The Code Comes From The Tools Site

Where the code lives: **developed on the tools site and imported, not written in the vault.**

The project lead: **"all the code should not come from the vault. Develop it on the tools site, because it can be reused in other places including a website. The vault should only add the vault-specific codebase and the vault-specific changes."** So the heavy lifting is the reusable control flow from Part One, and the vault contributes only its specific integration code, which keeps the control flow general and the vault thin (cross-ref: Part One).

## The Killer Workflow: Chat Edits The Vault From Inside

The motivating use case: **bring the Claude-edits-a-vault workflow inside the vault, as a two-pane chat and page.**

The project lead: **"the ultimate workflow is that at the moment, I have a powerful workflow with Claude where I say, here is a vault, can you make changes to it, and Claude iterates, makes changes, and pushes to the vault. But I would like to do this from inside the vault. Imagine two panes, the chat on the left and the vault page on the right, and I say, can you change the HTML, the CSS, the JavaScript, and reload the page. Which means the chat and the tools need to read the file, write the file, refresh, and open panes."**

```
  +-------------------+-------------------+
  |   Chat (left)     |  Vault page (right)|
  |                   |                    |
  |  "change the      |   <renders the      |
  |   HTML / CSS / JS |    vault page>      |
  |   and reload"     |                     |
  +-------------------+-------------------+
        |  tools: read file, write file, refresh, open panes
        v
  The vault content changes and the page reloads, live
```

This takes the external provider-self-service editing workflow and moves it inside the vault, so editing happens in place (cross-ref: the provider-self-service-vault-editing brief, where the provider edited a vault via an external agent).

## Self-Registering Vault Tools

The second mode, and the powerful part: **the vault app registers its own capabilities and domain tools, exposed to the chat UI.**

The project lead: **"we also need the vault itself to register some tools and capabilities. If you want the capability to open a page inside a vault app, that is a capability the vault app provides. And the vault app has specific domain activities, contact management, performing a form, doing a calculation. What is powerful is exposing those tools to the chat UI, because then from the chat I can see what actions I can execute."**

| Source | Example Tools |
|--------|---------------|
| Vault-app capabilities | Open a page inside the app |
| Vault-app domain activities | Contact management, fill a form, do a calculation, make a change |

When these self-registered tools are surfaced in the chat UI, the user sees exactly what actions are available, turning the chat into a control surface for the app's own functions.

## The Two Modes

Putting it together: **browser tool execution, and self-registering vault-app tools.**

| Mode | What It Is |
|------|------------|
| Tool execution (from Part One) | The control flow running tools, including reading and writing vault files |
| Self-registering vault tools | The vault app exposing its own capabilities and domain activities to the chat |

Both demand the same standard: maximum provenance, understanding, traceability, and control over when tools execute, when they do not, how they flow, and how they are exposed.

## The MVP Approach

The clever first step: **the first MVP is a vault app that exposes read and write via tools.**

The project lead: **"if you think about self-registering tools, the first MVP of using the tools code in the vault can be a vault app that exposes the read and write methods via a tool. That is the best way, because it lets me test the end-to-end flow and see that the code we are importing from the tools site is good enough to move into a vault. So we write a lot of the code that eventually goes into the vault kernel inside a vault app, in JavaScript, and once it works we move it."**

```
  MVP: a vault app exposes read + write as self-registered tools
        |  validate the end-to-end flow with the imported tools-site code
        v
  Confirm the imported code is good enough
        |
        v
  Move that code into the vault kernel
```

So the kernel-bound code is prototyped inside a vault app first (where it is easy to iterate), validated end to end, and only then promoted into the kernel.

## What This Asks For

1. **Place tools at the vault top level, managed by the kernel** (apps use SG-star access).
2. **Enforce the containment rule** (a tool never exceeds the vault app's power).
3. **Import the control-flow code from the tools site** (the vault adds only vault-specific code).
4. **Build the chat-edits-the-vault workflow** (two panes; read, write, refresh, open panes).
5. **Support self-registering vault tools** (capabilities and domain activities exposed to the chat UI).
6. **Start with the MVP-as-a-vault-app** (read and write via tools; validate, then move to the kernel).
7. **Hold maximum provenance and control** (across both modes).

Estimated effort: moderate; Part One provides the control flow and the kernel model exists; the work is the kernel placement, the containment enforcement, the two-pane workflow, the self-registration, and the MVP.

## What This Does Not Try To Be

- **Not app-managed tools.** The kernel governs tools, not the app.
- **Not a tool more powerful than its app.** Containment is absolute.
- **Not vault-developed code.** The control flow comes from the tools site.
- **Not kernel-first.** The MVP lives in a vault app, then moves to the kernel.

## Honest Risks

**Risk 1: containment is the critical security property.** If a tool can exceed its app, the model breaks. Mitigation: enforce the ceiling at the kernel; test it explicitly.

**Risk 2: chat-edits-the-vault is powerful and needs guardrails.** Writing files and reloading from chat is potent. Mitigation: provenance on every change; the containment rule; the vault's version control to undo.

**Risk 3: the MVP-to-kernel migration.** Code prototyped in a vault app must move cleanly into the kernel. Mitigation: write it as kernel-bound code from the start, in JavaScript, and validate before moving.

**Risk 4: self-registered tools widen the surface.** Exposing domain tools to the chat increases what can be invoked. Mitigation: least privilege, the containment rule, and clear exposure in the chat UI.
