## What This Is

The standalone tools-execution control flow, built on the tools site and reusable beyond vaults: **the LLM tool-calling loop (present the available tools, let the model choose, execute in a protected engine, return the result, continue), wrapped in a broker with tools registration and tools permissions, full provenance of every tool's input and output, security checks, a per-tool virtual file system that is the beginning of memory, graph and fractal tools where a tool can have tools, and the principle of exposing only the required tools to the required call, because the more contained the tools are, the more powerful they become.** It is Part One of two; Part Two covers integrating this into the vault (cross-ref: the v0.33.38 tools-in-vault-kernel-integration brief). It continues an agent's inventory of the existing tool work and is the capture the project lead will hand to that agent to turn into a detailed implementation brief. It builds on the kernel model and the compute work (cross-ref: the v0.27.62 vault-in-vault-kernel-model brief, the v0.32.4 ephemeral-compute brief, and the v0.33.26 vault-powered-websites and audio-transcribe-experience briefs). New contributions: **the tools-execution control flow, the broker-registration-permissions model, the virtual-file-system-as-memory, and the expose-only-required-tools principle.**

## The Context: Tools Are The Linchpin

Why this matters now: **the chat inside a vault is only useful if it can do something, and tools are what let it act.**

The project lead: **"we now have a really nice way to create vault apps, a really nice way to consume tools from inside a vault app, like the audio transcript, and now the ability to have a chat inside a vault using the OpenRouter environment, which is massive. The tools are the linchpin of everything, because the tools are what allow the LLM or the chat to actually do something, to interact, or else the chat is just a normal chat."** So tools turn a chat into an agent that can act on the vault and the world; without them it is just conversation (cross-ref: the audio-transcribe-experience brief, where the self-describing API made the tool usable by agents).

## What Tool-Use Means

A precise definition, to avoid confusion: **present the tools, let the model choose, execute in a protected engine, return the result.**

The project lead: **"by tools I mean the workflow of telling an LLM here are the available tools, then letting the LLM choose what tool to execute, then executing that in an execution engine, which needs to be protected and sandboxed, and giving the response back to the LLM so it can continue. This is not to be confused with the fact that this runs on the tools site, which is our shared environment."** So the control flow is the standard tool-calling loop, with the crucial requirement that execution happens in a protected, sandboxed engine.

```
  LLM  <--- here are the available tools
   |
   |  chooses a tool and arguments
   v
  Protected / sandboxed execution engine  --- runs the tool
   |
   |  result (with full provenance of input and output)
   v
  LLM  --- continues
```

## The Broker, Registration, And Permissions

What already exists, from the compute work: **a broker, tools registration, and tools permissions.**

The project lead: **"on SG Playwright, which is our SG Compute, we did a lot of powerful tools definition, where we expanded the idea of a broker, tools registration, and tools permission, which is very important. We need a very clear set of graphs and mappings on how everything fits together, or else tools are ridiculously dangerous."**

| Element | Role |
|---------|------|
| Broker | Mediates between the model and the tools |
| Registration | How a tool becomes available |
| Permissions | What a tool is allowed to do |

These need clear graphs and mappings, because uncontrolled tools are dangerous (cross-ref: the SG Playwright and ephemeral-compute work).

## The Control Flow To Build

What to tie together: **permissions mappings, auto-execute, full provenance, and security checks.**

The project lead: **"we need a full standalone workflow of permissions mappings, auto-execute with full provenance of the input and the output of the tools, and the ability to do security checks on the tools. Basically we are building a tools execution control flow, and we have a lot of the pieces, but now is the time to tie it all together."**

| Capability | Detail |
|------------|--------|
| Permissions mappings | Which tool may do what, mapped clearly |
| Auto-execute | When a tool runs without a prompt, and when it does not |
| Full provenance | Every tool's input and output recorded |
| Security checks | Checks on the tools before and during execution |

## The Containment Principle

The recurring SGraph principle, applied to tools: **the more we contain the tools, the more powerful they become.**

The project lead: **"this is another good example of the more we contain the tools, the more powerful they become, because the more we can actually use them. Or else tools are ridiculously dangerous."** Containment is not a limit on power but the enabler of it: a tool that is well-bounded can be used freely, where an unbounded one cannot be trusted at all. This is restrict-to-unleash applied to tool execution (cross-ref: the access-not-security brief).

## The Tool Design Primitives

How a tool is shaped: **a virtual file system that is the start of memory, graph and fractal structure, and only the required tools exposed per call.**

The project lead: **"a tool should have a virtual file system, which is the beginning of the idea of memory, where you can read, write, and CRUD files. Tools should have a graph element and a fractal element, a tool can have a tool can have a tool. And one of the core principles is that you only want to expose the required tools at the moment in time to the required app and the required LLM call, which means we could even change the tools on every call, because we are curating the use of the LLMs and creating the workflows."**

| Primitive | Meaning |
|-----------|---------|
| Virtual file system | A per-tool in-memory file system; the beginning of memory (read, write, CRUD) |
| Graph and fractal | A tool can contain tools, recursively; tools form a graph |
| Expose only the required tools | Per call, even changing the tool set on every call, to curate the workflow |

The expose-only-the-required-tools principle is both a safety control (least privilege per call) and a curation mechanism (shaping what the model can do at each step).

## The Test Scenarios

How to prove it end to end: **a good set of components and scenarios that grant an LLM specific capabilities.**

The project lead: **"we need a good set of components and core elements and tools to test all of this end to end. Say to an LLM, you only have access to the virtual file system, so you can read, write, and CRUD files. Now you have access to making network calls, so we can trigger a call, with the CORS limitations. Or you can make further LLM calls. Or you can access a vault file, because a lot of the tools we want to provide are tools to access a file in a vault."**

| Scenario | Capability Granted |
|----------|--------------------|
| Virtual file system only | Read, write, CRUD in the in-memory file system |
| Network calls | Make web requests (within CORS limits) |
| Further LLM calls | Call an LLM as a tool |
| Vault file access | Read and write a file in a vault |

Vault-file access as a tool is the bridge to Part Two (the vault integration).

## Reusable Beyond Vaults

Why build it standalone: **on the tools site, so a website or any caller can use it, not only agents.**

The project lead: **"all of this code should not come from the vault. Develop it in the tools site, because it can be reused in a bunch of other places, including a website. A web page could leverage it, and it does not necessarily need to be an agent, because tool execution is like, I want to do this, can you execute it, give me back the result."** So the control flow is a general capability that any caller can use, which is why it lives on the tools site and not inside a vault (cross-ref: the vault-powered-websites brief).

## Maximum Provenance, Traceability, And Control

The standard to hold: **maximum provenance, understanding, traceability, and control over tool execution.**

The project lead: **"we need maximum provenance, maximum understanding, maximum traceability, maximum control on the tools execution: when they execute, when they do not, how they flow, how they do not flow, and how we expose them."** Every execution is recorded with its input and output, and the conditions of execution are explicit and controllable, which is what makes powerful tools safe to use (cross-ref: the artefact-driven-security-assessments brief for provenance).

## What This Asks For

1. **Build the tools execution control flow** (the tool-calling loop in a protected engine).
2. **Implement the broker, registration, and permissions** (with clear graphs and mappings).
3. **Record full provenance** (every tool's input and output).
4. **Add security checks and auto-execute rules** (when tools run and when they do not).
5. **Give each tool a virtual file system** (the start of memory).
6. **Support graph and fractal tools** (tools containing tools).
7. **Expose only the required tools per call** (least privilege and curation).
8. **Build the test scenarios** (file system, network, LLM calls, vault-file access).

Estimated effort: moderate; many pieces exist (the browser tool-execution MVP, the SG Playwright broker and permissions); the work is tying them into one control flow with provenance and the virtual file system.

## What This Does Not Try To Be

- **Not vault-specific.** It is standalone on the tools site, reusable.
- **Not unsandboxed.** Execution is in a protected engine.
- **Not all tools at once.** Only the required tools per call.
- **Not opaque.** Full provenance and traceability.

## Honest Risks

**Risk 1: tools are dangerous if uncontained.** Mitigation: the broker, permissions, sandboxed engine, security checks, and least-privilege exposure; containment is the enabler of power.

**Risk 2: the execution engine must be genuinely sandboxed.** Mitigation: protected execution; security checks; this is non-negotiable.

**Risk 3: CORS and browser limits.** Network-call tools face CORS limits. Mitigation: design within them; route through compute where needed.

**Risk 4: provenance overhead.** Recording every input and output has a cost. Mitigation: it is the price of safe, powerful tools, and it is the standard to hold.
