## What This Is

A memory pattern emerging from the vault-chat MVP, which consolidates a lot of prior ideas: **split the conversation into an ephemeral chat session (the back-and-forth with the model, preserved only briefly so context and token cost do not explode) and a file-based memory (selectable attachment files shared per request, such as tool definitions, reference documents, project context, and images), add two kinds of session assets (auto-generated logs of the tool calls, and a pre-generated summary of the work so far), visualise the cost and tokens being sent, and aim always to send only the minimum tokens needed at each moment.** It inverts the usual framing, where the chat log is treated as memory; here the chat is ephemeral and the memory is the curated files. It develops the virtual-file-system-as-memory seed from this morning (cross-ref: the v0.33.38 tools-execution-control-flow and tools-in-vault briefs) and realises the curated-prompts idea in practice (cross-ref: the v0.33.26 selling-llm-usage brief for cost visibility). New contributions: **the ephemeral-chat-versus-file-memory split, the two session assets, and the minimum-tokens curation goal.**

## The Pattern: Ephemeral Chat, File-Based Memory

The core distinction, and the inversion: **the chat is ephemeral; the memory is the files you attach.**

The project lead: **"the industry talks a lot about memory, but I have two modes. One is the chat, which we usually view as memory, and I am now saying it should be ephemeral. The other is the memory, which is the attachment files we give to that chat session."** So rather than treating the accumulating chat log as memory, the chat is deliberately short-lived, and memory is the deliberate, selectable set of files shared with the session.

## Mode One: The Ephemeral Chat Session

What it is, and why it is ephemeral: **the back-and-forth commands, preserved briefly but not for long.**

The project lead: **"the ephemeral chat session is the commands we execute, the hello, the can you do this, can you do that, which needs to be preserved during that period of time, but we do not want to preserve it too long, because that is how you get an explosion of context and tokens."** So the session keeps just enough recent exchange to function, and is intentionally not allowed to grow without bound, because unbounded chat history is the source of context bloat and runaway cost.

## Mode Two: File-Based Memory

What memory actually is here: **selectable files shared with the session per request.**

The project lead: **"the memory is files we choose to share at the moment with that prompt: the tool definitions, reference documents like coding guidelines, what project you are working on, files or context or images we want to send with every request, but selectable, so I can choose, and they are part of what we share with that particular session."**

| Memory File | Example |
|-------------|---------|
| Tool definitions | What tools are available this call |
| Reference documents | Coding guidelines, the project being worked on |
| Context and images | Material to send with the request |

The defining property is selectability: memory is chosen, not accumulated, and scoped to the session.

## The Chat-Session Primitives

The building blocks the pattern sits on: **model execution, tools, the ephemeral session, and the memory.**

| Primitive | Detail |
|-----------|--------|
| Model execution | What is sent to the model; has tokens and cost |
| Tools | Tool executions chosen by the model, managed by the control flow (cross-ref: Part One) |
| Ephemeral chat session | The recent commands, preserved briefly |
| Memory | The selectable files shared with the session |

## The Two Session Assets

To preserve what happened without keeping the whole chat: **auto-generated logs and a pre-generated summary.**

The project lead: **"we probably have two sets of mini-files. One is auto-generated, the tool calls, not necessarily the inputs and outputs, just the execution commands or the titles, because that already gives a good sense of what is happening, or each tool has a summary of what it is doing, create file, list files. And we can have a pre-generated summary, call it compression, where we say this is the work we have done so far, so the agent in that call has a good sense of what is going on."**

| Asset | What It Captures |
|-------|------------------|
| Auto-generated session log | The tool calls, as execution commands, titles, or per-tool summaries (create file, list files) |
| Pre-generated summary | A compression of the work so far, so the next call has context |

This is the compaction idea: rather than carrying the full chat, the session is distilled into a compact log and a summary that can be shared as memory files. The project lead notes the word, summary or compression, is still being settled.

## Curating Context: Send The Minimum Tokens

The optimisation goal, which generalises the expose-only-required-tools principle: **send only the exact tokens needed at each moment.**

The project lead: **"the ultimate goal is to send the minimum, only the exact tokens needed at any point in time. We should not be sending all the tool definitions all the time, maybe only some tools, or even just a tool to discover the tools. There is a lot of optimisation we can do."** So context is curated per call: the tool definitions, the memory files, and the session summary are each included only when needed, which is the per-call least-privilege principle from Part One applied to the whole context window, not just the tools (cross-ref: the tools-execution-control-flow brief).

| Optimisation | Example |
|--------------|---------|
| Do not always send all tool definitions | Send some, or a tool to discover tools |
| Share memory files selectively | Only the relevant ones this call |
| Use the summary instead of the full chat | A compression, not the whole history |

## The Cost And Token UI

What the user sees: **the cost and tokens being sent, on one page.**

The project lead: **"visualise for the user the cost and the number of tokens being sent, because each of these has a token cost. We need a nice UI to see in one page all of the context, and some statistics of all the context we are sending."** So every contributor to the context (the session, the memory files, the tool definitions, the summary) shows its token cost, and a single page shows the whole context and its statistics, making the curation visible and tunable (cross-ref: the selling-llm-usage cost-visibility model).

## The Synthesis: Curated Prompts In Practice

What this consolidates, in the project lead's words: **the single and curated prompts idea, now working.**

The project lead: **"this is a consolidation of a lot of ideas we talked about before, single prompts or curated prompts to LLMs, now starting to work in practice."** So the pattern is the concrete realisation of the long-held idea that a prompt should be a deliberately assembled, minimal set of context, rather than an ever-growing log.

## What This Asks For

1. **Make the chat session ephemeral** (preserve briefly; avoid context explosion).
2. **Implement file-based memory** (selectable files shared per request).
3. **Auto-generate the session log** (tool-call commands, titles, or summaries).
4. **Pre-generate the work-so-far summary** (the compression).
5. **Curate context to the minimum tokens** (selective tool definitions, memory, and summary).
6. **Visualise cost and tokens** (one page; all context and statistics).
7. **Realise the curated-prompt idea** (a deliberately assembled, minimal prompt).

Estimated effort: moderate; the vault chat, tools, and vault file store exist; the work is the ephemeral-session handling, the selectable memory, the two session assets, and the context UI.

## What This Does Not Try To Be

- **Not chat-as-memory.** The chat is ephemeral; memory is the files.
- **Not unbounded context.** The minimum tokens needed, per call.
- **Not all tools always.** Selective tool definitions, or a discovery tool.
- **Not opaque.** The cost and context are shown.

## Honest Risks

**Risk 1: ephemeral chat can lose useful history.** Mitigation: the auto-generated log and the summary preserve what matters as memory files.

**Risk 2: the summary must be faithful.** A poor compression misleads the next call. Mitigation: auto-generate carefully; let the user inspect it.

**Risk 3: token optimisation versus completeness.** Trimming too much starves the model of context. Mitigation: the context UI makes the trade-off visible and tunable.

**Risk 4: selectable-memory UX.** Choosing files per session must be easy. Mitigation: the one-page context UI with statistics.
