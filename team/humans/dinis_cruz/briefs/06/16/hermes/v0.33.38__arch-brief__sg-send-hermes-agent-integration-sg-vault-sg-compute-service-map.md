# Integrating Hermes Agent With SG/Vault And SG/Compute: A Service Map

**version** v0.33.38
**date** 16 June 2026
**from** Human (project lead) and Research
**to** Architect, Developer (lead), Security, Strategy, @Dev
**type** Arch brief (service map)

## What This Is

A service that takes Hermes Agent, the open-source Nous Research agent, and gives it the two things it lacks by backing it with SG/Vault and SG/Compute: **Hermes keeps its memory and skills locally and unencrypted and runs on persistent infrastructure, so the integration makes its memory and skills live in encrypted, portable, shareable, provenance-bearing vaults, and runs its execution on disposable per-task ephemeral compute that is destroyed after each run, while SGraph's own services (URL-to-image threat analysis, audio transcription, image generation) are exposed to Hermes as SKILL.md skills, since both already use the open skill format.** It builds directly on the Hermes briefing (cross-ref: the v0.33.38 hermes-agent-briefing brief) and composes SGraph's memory, tools, compute, and service work (cross-ref: the v0.33.38 ephemeral-chat-and-file-based-memory, tools-execution-control-flow, and url-to-image-threat-analysis briefs, and the v0.32.4 ephemeral-compute brief). New contributions: **the integration mapping, the vault-backed-memory-and-skills design, the ephemeral-execution backend, and the SGraph-services-as-Hermes-skills idea.**

## The Thesis

In one line: **Hermes is a great agent runtime; SG/Vault and SG/Compute give it encrypted portable memory and disposable execution.**

Hermes already does the hard agent work: the closed learning loop, the skills, the multi-platform reach, the browser control, the model-agnostic LLM layer. What it does not do is keep its memory and skills in an encrypted, portable, shareable, provenance-bearing form, or run on disposable per-task compute. SG/Vault and SG/Compute are precisely those two capabilities, and both projects share the same MIT, self-hosted, no-tracking values, so the integration is natural rather than forced (cross-ref: the hermes-agent-briefing brief's overlap-and-gap analysis).

## The Integration Points

The mapping, Hermes component by component:

| Hermes Component | SGraph Integration |
|------------------|--------------------|
| Persistent memory (local) | Back it with SG/Vault: encrypted, portable, shareable, versioned, provenance-bearing memory, following the file-based-memory model (cross-ref: the ephemeral-chat-and-file-based-memory brief) |
| SKILL.md skills (local) | Store skills in SG/Vault: an encrypted, shareable, provenance-bearing skill library, interoperable with the open skill standard |
| Execution backends (Docker, SSH, Modal) | Add SG/Compute as a backend: disposable per-task ephemeral compute, destroyed after each run (cross-ref: the ephemeral-compute and url-to-image briefs) |
| LLM providers (OpenRouter, vLLM) | Use the OpenRouter-keys usage model, or the dedicated ephemeral sidecar LLM for privacy (cross-ref: the selling-llm-usage and url-to-image briefs) |
| Tool-calling | Run tools through the SGraph tools-execution control flow, with the broker, permissions, provenance, and containment (cross-ref: the tools-execution-control-flow brief) |
| Multi-platform gateway, voice transcription | Reuse or interoperate with the audio-transcribe tool (cross-ref: the audio-transcribe-experience brief) |
| Parallel sub-agents | Map onto the agentic team, with agents in vaults (cross-ref: the linkedin-agentic-team brief) |
| Cron automations | Use automation triggering on vaults (cross-ref: the archiver-cataloguer brief) |

## The Architecture

How it fits together:

```
                       Hermes Agent runtime (Nous Research, MIT)
                         |  closed learning loop, gateway, browser, sub-agents
        +----------------+----------------+-----------------------+
        |                |                |                       |
   SG/Vault          SG/Compute        Tools control flow     LLM layer
   - memory          - disposable       - broker /            - OpenRouter keys
     (encrypted,       per-task           permissions /        - or ephemeral
      portable,        ephemeral          provenance /           sidecar LLM
      shareable)       execution,         containment
   - skills            destroyed after
     (SKILL.md,        each run
      provenance)
        ^
        |  SGraph services exposed back to Hermes as SKILL.md skills:
        +--- URL-to-image threat analysis, audio transcription, image generation
```

So Hermes drives, SG/Vault holds its memory and skills encrypted and portable, SG/Compute runs its tasks in disposable ephemeral compute, the SGraph tools control flow governs tool execution, and the LLM layer is metered or isolated.

## SGraph Services As Hermes Skills

The two-way part, and the neat one: **expose SGraph's own services to Hermes as SKILL.md skills.**

Because Hermes uses the open SKILL.md format and SGraph already builds skill-shaped tools, SGraph's services can be packaged as Hermes skills: the URL-to-image threat-analysis service, the audio transcription tool, and the image-generation tool all become skills a Hermes agent can install and call (cross-ref: the url-to-image-threat-analysis, audio-transcribe-experience, and image-generation-opportunity briefs). So the integration flows both ways: Hermes gains vault-backed memory and ephemeral execution, and SGraph's services gain a popular open-source agent runtime as a distribution channel.

## What The Integration Adds

The value of doing this, beyond either project alone:

| Added Capability | From |
|------------------|------|
| Encrypted, portable memory and skills | SG/Vault (versus Hermes's local plain storage) |
| Shareable, multi-party memory and skills | SG/Vault PKI and authorised keys |
| Provenance on memory, skills, and actions | SG/Vault and the tools control flow |
| Disposable per-task execution | SG/Compute (versus persistent infrastructure) |
| Safe handling of risky tasks | SG/Compute ephemeral, destroyed after (cross-ref: the url-to-image brief) |
| Metered or isolated LLM usage | The OpenRouter-keys model and the sidecar LLM |
| Distribution for SGraph services | Hermes as a runtime that installs SGraph skills |

## The MVP

Where to start, smallest first: **back Hermes memory with a vault, run one task on SG/Compute, expose one SGraph service as a skill.**

1. **Vault-backed memory and skills.** Point Hermes's memory and skill storage at an SG/Vault, so its memory and skills become encrypted and portable.
2. **One task on SG/Compute.** Run a single Hermes task on disposable ephemeral compute, destroyed after, to validate the backend.
3. **One SGraph service as a Hermes skill.** Package the URL-to-image threat-analysis service as a SKILL.md skill and have a Hermes agent call it.

Each step is independently useful and validates one integration point.

## What This Asks For

1. **Back Hermes memory and skills with SG/Vault** (encrypted, portable, shareable, provenance-bearing).
2. **Add SG/Compute as an execution backend** (disposable per-task ephemeral compute).
3. **Route tools through the SGraph control flow** (broker, permissions, provenance, containment).
4. **Meter or isolate the LLM layer** (OpenRouter keys or the sidecar LLM).
5. **Expose SGraph services as Hermes skills** (URL-to-image, audio, image generation).
6. **Decide integrate-versus-fork** (build alongside upstream, or fork; the MIT licence allows both).
7. **Ship the three-step MVP** (vault memory, one ephemeral task, one service-as-skill).

Estimated effort: moderate; both projects exist and share values and formats; the work is the vault-storage adapter, the SG/Compute backend, and the skill packaging.

## What This Does Not Try To Be

- **Not a rewrite of Hermes.** It backs and extends Hermes, not replaces it.
- **Not local plain storage.** Memory and skills move into encrypted vaults.
- **Not persistent infrastructure.** Execution becomes disposable and ephemeral.
- **Not one-way.** SGraph services flow back to Hermes as skills.

## Honest Risks

**Risk 1: Hermes is fast-moving and post-cutoff.** Its APIs and internals change quickly. Mitigation: verify against the current repository; track upstream; prefer adapter layers over deep forks.

**Risk 2: integrate versus fork.** Deep integration risks drift from upstream; a fork risks maintenance burden. Mitigation: favour an adapter and contribute upstream where possible (the MIT licence allows either).

**Risk 3: the memory and skill format mapping.** Hermes's local memory and SKILL.md format must map cleanly to vault storage. Mitigation: a storage adapter that preserves the SKILL.md open format.

**Risk 4: the execution-backend surface.** Adding SG/Compute as a backend touches Hermes's execution layer. Mitigation: implement it as one more backend alongside Docker, SSH, and Modal, which Hermes already abstracts.
