# SG/Hermes: A Fully Ephemeral, Vault-Native Agent With NHI 2.0 And PKI

**version** v0.33.38
**date** 16 June 2026
**from** Human (project lead) and Research
**to** Architect, Developer (lead), Security, Strategy, @Dev
**type** Arch brief (vision and architecture)

## What This Is

The full vision behind the Hermes integration: SG/Hermes, a version of Hermes that runs entirely on ephemeral infrastructure, with vaults as its whole world. **It runs 100 percent on ephemeral compute, spun up on demand or by events and destroyed after each run, with SG/Vault as the only persistent layer and as the agentic memory itself (a topology of multiple vaults, vaults-in-vaults, and vaults-to-vaults), governed by NHI 2.0 graph-based identities and fine-grained permissions, and secured end to end by PKI for communication, authentication, and authorisation, so the result is an agent with no persistent attack surface, fully sovereign and portable state, hierarchical and shareable memory, least-privilege identity, and zero-trust communication.** It is the ambitious destination for which the previous integration map is the stepping stone (cross-ref: the v0.33.38 hermes-agent-briefing and hermes-agent-integration briefs), and it composes the ephemeral-compute, vault-in-vault, NHI 2.0, PKI, and memory work (cross-ref: the v0.32.4 ephemeral-compute and pki-public-key-registry briefs, the v0.27.62 vault-in-vault-kernel-model brief, the v0.32.3 nhi-2.0 briefs, and the v0.33.38 ephemeral-chat-and-file-based-memory brief). New contributions: **the SG/Hermes vision, the vault-topology-as-memory, and the ephemeral-plus-NHI-plus-PKI security model.**

## Why This Is Powerful

The payoff, and why the properties reinforce each other:

| Property | Payoff |
|----------|--------|
| No persistent compute | No persistent attack surface; the agent is rebuilt every run, so a compromise cannot persist (a structural answer to the agentic-compromise problem; cross-ref: the agentic-compromise-cleanup brief) |
| Vault-only persistence | Sovereign, portable, ownable state; no lock-in (cross-ref: the sovereignty thesis) |
| Memory as a vault topology | Hierarchical, shareable, provenance-bearing agentic memory |
| NHI 2.0 identity | Least-privilege, graph-based, auditable permissions per agent and per instance |
| PKI for comms | Zero-trust: every message encrypted, signed, and authorised |
| Event-driven and on-demand | Cost-efficient and reactive; compute exists only while needed |

The combination is the point: ephemeral compute alone loses state, but with the vault as the persistent layer it does not; a persistent agent is a standing target, but an ephemeral one rebuilt from a vault is not; and NHI 2.0 plus PKI ensure that the many short-lived instances can be trusted, identified, and contained.

## Pillar One: 100 Percent Ephemeral Infrastructure

The first pillar: **no persistent compute; spin up on demand or by events, then destroy.**

Every agent run, sub-agent, and tool execution happens on ephemeral compute that is spun up when needed (on demand, or triggered by an event) and destroyed afterwards, so nothing of the agent persists in compute between runs. This is the SG/Compute model already proven in the URL-to-image threat-analysis service, where fresh infrastructure is spun up per analysis and torn down (cross-ref: the url-to-image-threat-analysis and ephemeral-compute briefs), and the event-driven triggering is the debounced-trigger pattern from the archiver (cross-ref: the archiver-cataloguer brief). The spin-up-latency question is real and is addressed in the honest tensions.

## Pillar Two: SG/Vault As The Persistent Layer And The Agentic Memory

The second pillar, and the heart of it: **the vault is the only persistent layer, and the memory is a topology of vaults.**

All memory, skills, state, and identity live in vaults, not on disk in compute. And the agentic memory is not one vault but a topology:

| Vault Relationship | Role In Memory |
|--------------------|----------------|
| Multiple vaults | Separation: per project, per domain, per agent, no single uber-vault |
| Vaults-in-vaults | Hierarchy: kernel-managed sub-structures, nested memory and scopes (cross-ref: the vault-in-vault-kernel-model brief) |
| Vaults-to-vaults | Inter-agent memory and communication, via the two-key encrypt-and-sign send (cross-ref: the archiver-cataloguer and pki-public-key-registry briefs) |

This is the file-based-memory model at scale: memory is selectable, curated, versioned, and provenance-bearing vault content, and the closed learning loop's skills are vault-stored too (cross-ref: the ephemeral-chat-and-file-based-memory brief). Because the vault is the persistent layer, a destroyed instance loses nothing that matters.

## Pillar Three: NHI 2.0 Identity And PKI For Comms, Auth, And Authz

The third pillar: **graph-based identities, and PKI for everything between instances.**

Each agent, sub-agent, and ephemeral instance has an NHI 2.0 non-human identity with fine-grained, graph-based permissions, so what each can touch is governed by the identity graph rather than bolted-on security (access-not-security; cross-ref: the nhi-2.0 briefs). PKI secures the rest:

| PKI Function | How |
|--------------|-----|
| Communication | Vault-to-vault messages encrypted with the recipient vault's public key, signed with the sender's |
| Authentication | An instance proves who it is with its key |
| Authorisation | Authorised keys and the permission graph decide what it may do |

So the many short-lived instances are each identified, least-privileged, and able to communicate only in encrypted, signed, authorised ways, which is what makes a swarm of ephemeral agents trustworthy (cross-ref: the pki-public-key-registry and nhi-2.0 briefs).

## The Lifecycle

How a single run flows:

```
  Event or demand
        |
        v
  Spin up ephemeral instance  (nothing persisted yet)
        |  authenticate via PKI / NHI 2.0 identity
        v
  Read memory + skills from vault(s)  (multiple / vaults-in-vaults)
        |
        v
  Execute  (tools via the control flow; least privilege per NHI graph)
        |  communicate vault-to-vault (PKI: encrypt + sign + authorise)
        v
  Write memory + skills + provenance back to vault(s)
        |
        v
  Destroy the instance  (no persistent compute, no persistent attack surface)
```

Everything durable is in the vaults; the compute is disposable.

## The Security Payoff: Popped-Resistant By Design

Worth stating on its own: **SG/Hermes largely dissolves the agentic-compromise problem by design.**

The 15 June cleanup-service brief described privileged personal agents being compromised rootkit-style and the difficulty of cleaning up. SG/Hermes answers that structurally: because the agent runs on ephemeral compute rebuilt from a vault every run and destroyed after, there is no persistent foothold to gain; NHI 2.0 least-privilege limits what any instance can reach; and PKI ensures communications cannot be forged or replayed. The agent is, in effect, rebuilt and reset continuously, which is the very remediation that brief said users cannot do for themselves (cross-ref: the agentic-compromise-cleanup brief). This does not eliminate all risk, but it removes the persistent-foothold class of it.

## Relation To The Integration Map

How this differs from the previous brief: **the integration map is the incremental step; SG/Hermes is the destination.**

The integration map backs Hermes's memory with a vault and adds SG/Compute as one backend among several, which is shippable now. SG/Hermes goes all the way: vault-native (the vault is the only persistent layer), fully ephemeral (no persistent compute at all), and NHI-2.0-plus-PKI-governed. The integration map is therefore the MVP path toward SG/Hermes, and SG/Hermes is the architecture the steps converge on (cross-ref: the hermes-agent-integration brief).

## What This Asks For

1. **Run the agent fully on ephemeral compute** (on demand or event-driven; destroyed after).
2. **Make SG/Vault the only persistent layer** (memory, skills, state, identity).
3. **Build the memory as a vault topology** (multiple, vaults-in-vaults, vaults-to-vaults).
4. **Give every instance an NHI 2.0 identity** (graph-based, least-privilege permissions).
5. **Secure all comms, auth, and authz with PKI** (encrypt, sign, authorise).
6. **Govern tools through the control flow** (broker, permissions, provenance, containment).
7. **Phase it from the integration MVP** (the stepping stone to the full vision).

Estimated effort: high; this is an ambitious architecture, but every pillar exists in some form (ephemeral compute, vaults, vault-in-vault, NHI 2.0, PKI, the memory model), so the work is composition, the vault topology, and the performance engineering.

## What This Does Not Try To Be

- **Not persistent.** No standing compute; the vault is the only persistence.
- **Not one vault.** A topology of vaults for memory and comms.
- **Not bolt-on security.** NHI 2.0 access-not-security and PKI by design.
- **Not a fork-and-forget.** It composes Hermes with the SGraph substrate; phased from the integration MVP.

## Honest Tensions

**Tension 1: spin-up latency versus responsiveness.** Fully ephemeral compute adds startup cost, which fights agent responsiveness. Mitigation: warm pools and the immediacy tiers from the URL service (always-on first tier, on-demand deeper tiers), so the first response is fast and heavy work spins up behind it (cross-ref: the url-to-image-threat-analysis brief).

**Tension 2: the vault as hot agentic memory.** Reading and writing memory from vaults at agent speed is demanding. Mitigation: the deterministic value indexes and caching the read-only memory, accepting that this is real performance engineering (cross-ref: the deterministic-value-indexes brief).

**Tension 3: the vault topology is complex.** Orchestrating multiple vaults, vaults-in-vaults, and vaults-to-vaults is intricate. Mitigation: start with one vault, add the topology as the memory model demands it; the kernel manages the nesting.

**Tension 4: identity and key management at scale.** Many short-lived instances mean many identities and keys. Mitigation: the PKI public-key registry and NHI 2.0 graph must scale to ephemeral identities; issue and retire keys with the instances.

**Tension 5: permission-graph overhead per call.** Graph-based authorisation on every action has a cost. Mitigation: cache the resolved permissions for the life of the instance.

**Tension 6: it is ambitious.** This is a large architecture. Mitigation: phase it from the integration MVP; do not build it all at once.
