# Creating The Audio And Chat Vaults: Read-Only, Website-Integrated, Agent-Maintained

**version** v0.33.38
**date** 16 June 2026
**from** Human (project lead)
**to** The audio-and-chat agent, Developer (lead), Architect, @Dev
**type** Dev brief (execution)

---

## What This Is

An execution brief for the agent that built the audio transcript tool and then the chat UI, to split the work into two separate read-only vaults served from the main website: **an audio vault that does transcription, real-time transcription, synthetic audio, and launching the chat, and a chat vault that reuses the current code (much of which will move to the tools later), both run read-only from the main website (read from the vault, no writes, so sessions cannot persist, with the user bringing their own OpenRouter key or an optional included key), everything public, with the code, artefacts, and initial UI put in place and documented so that new agents can be spun up to maintain each vault.** It executes the prior release brief (cross-ref: the v0.33.27 audio-transcript-tool-release and audio-transcribe-experience briefs) on the vault-powered-website pattern (cross-ref: the v0.33.26 vault-powered-websites brief), reusing the tools and memory work (cross-ref: the v0.33.38 tools-in-vault and ephemeral-chat-and-file-based-memory briefs). New contributions: **the two-vault split, the read-only-mode constraint, and the documented-for-maintenance requirement.**

## The Purpose: Execution, Not Design

What this brief is for: **the design exists; now create the vaults and put the code in place.**

The project lead: **"this is a memo for the agent I have been working with on the audio transcript tool, which then moved into the chat UI. I want that agent to split this and create two separate vaults. I already have a brief from the agent that worked on the tool, with all the capabilities, so now we start to execute it. This is about putting all the code and the bits in place."** So this is the execution step: the audio brief is done, and the job now is to build the two vaults and assemble the artefacts.

## The Two Vaults

The split: **an audio vault and a chat vault.**

| Vault | Capabilities |
|-------|--------------|
| Audio | Audio transcription, real-time transcription, synthetic audio generation, and launching the chat |
| Chat | The chat UI, reusing the current code (much of which moves to the tools later) |

The project lead: **"there are two vaults to create. The audio vault, where we do the audio transcript, the real-time stuff, generate synthetic audio, and generate the chat from there. And the chat, where we reuse a lot of the code, remembering that a lot of it will move to the tools anyway, but let us use the code we have for this version."** (Cross-ref: the audio-transcribe-experience brief for the real-time and synthetic-audio features, and the tools-in-vault brief for the code that migrates to the tools.)

## Read-Only From The Main Website

How they are served: **a read-only key shared on the live website, loading the assets from the vault, rendered as a component.**

The project lead: **"these are the vaults we use as read-only from the main website. We share the read-only key on the live website and load the assets from there. The page is rendered on the main website as a component, so we may need to improve that a little."** So the vaults are served via the vault-powered-website pattern: a read-only key, assets loaded from the vault, the page embedded as a component on the main site (cross-ref: the vault-powered-websites brief).

## The Read-Only-Mode Constraint

The important technical point: **read-only means no writes, so sessions cannot persist, but everything else works.**

The project lead: **"when this runs off the main website it runs in read-only mode, so you can read from the vault but cannot write to it, which means we cannot use the sessions. But most of the other features should work from the site, except the sessions."** So in the website-served read-only mode, the chat and tools work, but session state cannot be written back to the vault, since sessions require writes. This ties directly to the ephemeral-chat-and-file-based-memory model: the ephemeral chat runs, but persisting it as memory needs write access the read-only mode does not have (cross-ref: the ephemeral-chat-and-file-based-memory brief).

## The OpenRouter Key

How the LLM is paid for: **the user brings their own key, or an optional key is included, at the project lead's discretion.**

The project lead: **"on the live website we will not have the OpenRouter key, so the user will need to provide their own. But whether the key is there or not should be my decision, so we could support both modes. Because it will not be discovered that much yet, I could put five dollars on a key and see if it gets used, for feedback."** So the build should support both bring-your-own-key and an optionally-included key, with the inclusion being a deployment-time choice, and a small funded key as an early feedback experiment (cross-ref: the openrouter-key-acquisition and audio-transcript-tool-release briefs).

## Everything Is Public

A constraint to design around: **everything in these vaults is public, and that is fine.**

The project lead: **"we need to take into account that everything there is public, but that is okay, we can have that information and those documents there."** So the audio and chat vaults hold no secrets, and the code, artefacts, and documentation can all live in them openly (cross-ref: the vault-powered-websites brief on public vaults).

## Documented For Maintenance Agents

A key requirement: **document it so a new agent can maintain each vault.**

The project lead: **"this is about putting all the code and the bits in place so that when I spin up a new agent to maintain this part of the website, the agent understands what is going on and how it works. It should have a good explanation."** So each vault must include the code, the artefacts, the initial UI, and a clear explanation of how it works, written for the maintenance agent that will be spun up to look after it (cross-ref: the provider-self-service-vault-editing and linkedin-agentic-team briefs for agent-maintained vaults).

## The Orchestration

How it fits into the wider plan: **this agent creates the vaults, then separate agents manage them, then the website agent wires them in.**

The project lead: **"this is the brief for the agent that creates the two vaults, which I can then spin up two separate agents to manage. Then I go to the agent that manages the main website to figure out where to wire it in, which domains, and how everything fits together."**

```
  This brief
     |
     v
  The audio-and-chat agent  ->  creates the two vaults (audio, chat)
     |
     v
  Two maintenance agents  ->  one per vault
     |
     v
  The main-website agent  ->  wires them in (domains, integration)
```

## What This Asks For

1. **Create the two vaults** (audio and chat).
2. **Build the audio vault capabilities** (transcription, real-time, synthetic audio, launch chat).
3. **Build the chat vault** (reuse the current code; note what moves to the tools later).
4. **Serve them read-only from the main website** (read-only key, assets loaded, rendered as a component).
5. **Handle the read-only constraint** (no session persistence; everything else works).
6. **Support both key modes** (bring-your-own, or an optionally-included key).
7. **Keep everything public** (no secrets in these vaults).
8. **Document each vault for a maintenance agent** (code, artefacts, UI, and a clear explanation).

Estimated effort: low to moderate; the tool, the chat, the release brief, and the website pattern exist; the work is splitting into two vaults, assembling the artefacts, the read-only handling, and the documentation.

## What This Does Not Try To Be

- **Not a new design.** The design exists; this is execution.
- **Not writable from the website.** Read-only; no session persistence there.
- **Not key-bearing by default.** Bring-your-own, or an optional included key.
- **Not secret.** Everything in these vaults is public.

## Honest Risks

**Risk 1: read-only means no sessions on the website.** Mitigation: accept it; the chat and tools work, and session persistence is simply not available in the read-only mode (cross-ref: the ephemeral-chat-and-file-based-memory brief).

**Risk 2: the key decision.** Including a key exposes it client-side. Mitigation: support both modes; the small funded key is a bounded feedback experiment.

**Risk 3: the UI-as-component needs improvement.** Mitigation: the project lead flagged it; improve the component rendering on the main site.

**Risk 4: documentation quality for the maintenance agents.** Poor docs mean the maintenance agent flounders. Mitigation: a clear explanation in each vault, written for the agent.
