# The Image Transformation Service: A Public Examples Vault With Remix

**version** v0.33.38
**date** 16 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Product, @Dev
**type** Arch brief (service architecture)

---

## What This Is

A simple image transformation service and the public examples gallery at its heart: **the user uploads an image, chooses a model, pays with credits, gets the result, and can save it to a vault, built on the vault-powered-website pattern with two vaults (one for website content and one public examples vault), where the examples vault is the centre of the design, a public gallery in which every example stores the source photo, the prompt, the cost, the request and response, and the result, with a remix button that reopens the same prompt and source photo, organised both by use case and by model-and-platform, and tagged and rated.** It turns the earlier market signal into an architecture (cross-ref: the v0.33.38 image-generation-opportunity brief) and reuses the credits model, the website pattern, and the indexes (cross-ref: the v0.33.26 selling-llm-usage and vault-powered-websites briefs, the v0.32.4 deterministic-value-indexes brief). New contributions: **the two-vault design, the public examples gallery, the remix button, and the dual use-case-and-model organisation.**

## The Core Service

The simple flow, to start: **upload, choose a model, pay with credits, get the image, save it.**

The project lead: **"this is a very simple image transformation service where you upload an image, you choose a model, you choose the payment, which could be credits, and you get the image to start with, and then we add the ability to save that into a vault."**

| Step | Action |
|------|--------|
| 1 | Upload an image |
| 2 | Choose a model |
| 3 | Choose the payment (credits) |
| 4 | Get the transformed image |
| 5 | Save it to a vault (added next) |

This is the usage-credits model applied to image transformation (cross-ref: the selling-llm-usage and image-generation-opportunity briefs).

## The Two Vaults

The structure: **a website-content vault, and a public examples vault.**

The project lead: **"you have a vault that gets the website content, which is the UI and the text, and then we need another vault, which is going to have examples."**

| Vault | Contents |
|-------|----------|
| Website content | The UI and the text (the vault-powered-website pattern; cross-ref: the vault-powered-websites brief) |
| Examples | The public gallery of example transformations |

## The Examples Vault: A Public Gallery

The heart of the design: **a populated gallery showing, for each example, the prompt, the cost, and the result.**

The project lead: **"we need a workflow to populate that vault with samples, so we can show examples of how much it cost, what the prompt was, and what was created. The idea is to take a particular model, like Google's or OpenAI's, and show very visually what prompt was used, what the cost was, and the result. The vault should have everything: the source photo, the transformation, or the multiple transformations."**

So each example is a complete, visible record: source photo, prompt, cost, result (and possibly several transformations), populated by a workflow that generates the samples (the archiver-style populate pattern; cross-ref: the archiver-cataloguer brief).

## The Remix Button

The clever interaction: **reopen the same prompt and source photo so the user can replicate and tweak.**

The project lead: **"add a button to almost remix, where you can open in the UI the same prompt with the same source photo. The trick is to use public photos, ones that can easily be replicated."** So remix turns every example into a starting point: one click reopens the prompt and source image in the UI, and because the source photos are public and replicable, anyone can reproduce or vary the example.

## The Centre Of Gravity: Use Case And Model

The organising question, and the answer: **organise the examples vault both by use case and by model-and-platform.**

The project lead: **"the interesting question is, what is the centre of gravity of the vault? I think we want two core sections. One is the use case, which could be photos, infographics, all sorts of stuff. The other is the actual models, indexed by platform, because you can go directly or by OpenRouter."**

| Axis | Organised By |
|------|--------------|
| Use case | Photos, infographics, and other transformation types |
| Model and platform | The model used, indexed by platform (direct, or via OpenRouter) |

Indexing by platform matters because the same model can be reached directly or through OpenRouter, and the gallery should make that visible (cross-ref: the deterministic-value-indexes and openrouter-key-acquisition briefs).

## Everything Is Public, So Store The Request And Response

A design consequence: **the examples vault has no secrets, so store the full request and response.**

The project lead: **"all the data in the vault is public, so we should also store the request and the response, because everything is public, the vault does not have any secrets."** So the examples vault is fully public, which means the complete request and response can be stored as part of the example, making each one fully transparent and reproducible (cross-ref: the vault-powered-websites brief, on public vaults where the value is the content and workflow, not confidentiality).

## Good And Bad Examples, Tagged And Rated

A nice extension: **keep good and bad examples, tagged and rated.**

The project lead: **"we can also store good and bad examples, or eventually allow user voting and ratings, but for now I can tag it and provide a rating, like best examples, or misses, or funny misses."** So the gallery is curated: the project lead tags and rates examples now (best, misses, funny misses), with user voting and ratings as a later addition.

## What This Asks For

1. **Build the simple service** (upload, choose model, pay with credits, get image).
2. **Add save-to-vault** (the result into a vault).
3. **Use two vaults** (website content, and the public examples vault).
4. **Populate the examples gallery** (source photo, prompt, cost, request and response, result).
5. **Add the remix button** (reopen the same prompt and source photo; public, replicable photos).
6. **Organise by use case and by model-and-platform** (the dual centre of gravity).
7. **Tag and rate examples** (best, misses, funny misses; user voting later).

Estimated effort: low to moderate; the credits model, the website pattern, and the vaults exist; the work is the transformation service, the examples gallery, the remix button, and the populate workflow.

## What This Does Not Try To Be

- **Not secret.** The examples vault is fully public, including requests and responses.
- **Not one vault.** Website content and examples are separate.
- **Not complex to start.** Upload, model, pay, result; save and gallery follow.
- **Not user-voted yet.** Tagging and rating by the project lead first.

## Honest Risks

**Risk 1: everything in the examples vault is public.** By design, but it must hold no secrets (no keys in requests). Mitigation: the vault has no secrets; store only public photos and reproducible prompts.

**Risk 2: the public-photo replicability requirement.** Remix only works if the source photos are public and replicable. Mitigation: use public, replicable photos, as the project lead specifies.

**Risk 3: cost-display accuracy.** Showing the cost per example must be accurate. Mitigation: store the actual request and response, from which the cost is derived.

**Risk 4: rating subjectivity.** Best and misses are subjective. Mitigation: the project lead curates now; user voting adds breadth later.
