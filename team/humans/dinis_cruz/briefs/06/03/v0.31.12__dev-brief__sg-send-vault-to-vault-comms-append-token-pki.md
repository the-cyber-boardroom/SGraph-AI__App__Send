# Vault-To-Vault Communication: The Append-Only Token And Encrypt-On-Write

**version** v0.31.12
**date** 3 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, Product, @Dev
**type** Dev brief

---

## What This Is

A concrete, buildable proposal for **vaults communicating with each other**, prompted by a real deployment need: a first rollout takes a batch of roughly 100 friendly users, scaling to hundreds and eventually thousands, where each user needs a vault, a way to send and receive messages, and a workflow, which requires separate vaults to talk to one another. This is the practical, zoomed-in instance of the PKI-not-secrets paradigm (cross-ref: the v0.31.12 PKI-not-secrets brief): here it becomes a specific primitive, an **append-only token**, combined with public and private keys and encrypt-on-write, in a parent-and-child vault topology.

This brief covers only the communication architecture: the primitive, the keys, and the message flow. Any domain-specific or confidential content carried over the channel is out of scope here and is governed separately; nothing about a particular use case's sensitive data is added.

## The Problem: Separate Vaults Need To Communicate

The deployment need is specific: **each of about 100 users (scaling to hundreds and eventually thousands) gets a vault, and those user vaults need to communicate with an admin vault, in both directions.**

The project lead: **"we are going for the first batch of 100-ish friendly users, so we need a very simple link people can use. The challenge is that each user needs a vault, and we need a way to communicate, send messages, and implement a workflow, based on the idea that vaults need to be able to communicate with each other. That is an instant challenge: how can that happen?"**

The topology is parent-and-child:

| Vault | Role |
|-------|------|
| **The admin / comms vault (parent)** | Receives messages from the child vaults; sends messages to them |
| **The user vaults (children)** | Each user's vault; talks up to the parent and receives from it |

So the requirement is bidirectional vault-to-vault messaging: child vaults write up to the parent, and the parent writes down to the children. This is a primitive the platform has discussed before (cross-ref: the vault-in-vault brief and the PKI-not-secrets brief), now made concrete by a real rollout that needs it.

## The Proposed Primitive: An Append-Only Token

The core proposal: **alongside the existing read token, add an append-only token that lets one vault write (append) to another.**

The project lead: **"the same way we have the read token, what about if we create an append-only token, which means we allow a vault to just append to another vault. This is probably a very good example of where we should use public and private keys, so let's go full on it, because once you have that, everything becomes simple."**

There are two parts to the mechanism:

| Part | What It Does |
|------|--------------|
| **Append** | A vault can write (append only) to another vault, via the append token |
| **Read** | The appended content must be readable by the right party (the existing read capability) |

The append token is analogous to the read-only token already used for public previews (cross-ref: the v0.31.9 public-preview-with-read-only-key brief): just as a read token grants read access, an append token grants append access. And like the read token, it is not really a secret in the dangerous sense, the project lead notes the append token can sit on a server, because you still need the actual token to use it, and the real protection comes from the PKI layer below. The dev ask is explicit: **add support in SG/Send for this capability, the ability to just append-write to a vault.**

## Why Public And Private Keys: Encrypt-On-Write Is The Point

The reason to do this with PKI rather than a bare token: **the appended data must be encrypted, and with public/private keys you cannot write unencrypted, which is exactly the property you want.**

The project lead: **"this is where public and private key works really well, because you cannot write data unencrypted. The data needs to be encrypted. If the data is appended encrypted with the public key of the communication vault, it means only that entity can decrypt it. That works quite well, and it works the same the other way around."**

So the mechanism is encrypt-on-write:

| Step | What Happens |
|------|--------------|
| A child wants to message the parent | It encrypts the message with the parent comms vault's **public key** |
| It appends the encrypted message | Using the parent's **append token** |
| Only the parent can read it | Only the holder of the parent's **private key** can decrypt it |
| The reverse works identically | The parent encrypts to the child's public key and appends via the child's append token |

This is the elegant part: because writes must be encrypted to a public key, an append token on its own cannot leak readable data, anything written is already encrypted to the recipient who holds the matching private key. The append token controls *who can write*; the public-key encryption controls *who can read*. Together they validate both sides (the project lead: **"you can use this to validate both sides"**): the writer needs the append token, and only the intended recipient can decrypt. The token adds abuse-resistance and assurance; the encryption provides the actual confidentiality.

## The Provisioning Flow: A Template Vault Per User

The onboarding mechanism: **each user gets a template vault, pre-loaded with what it needs to communicate with the parent.**

The project lead: **"we can have a template vault that gets created for a user. When the user comes in, they get a template vault, and that template vault is given the public key of the parent communication vault, and it also creates its own public and private key. So it needs to be given two things: the public key of the parent comms vault, and the append key (the append token) of that vault."**

So a freshly provisioned user vault is given:

| The User Vault Receives | Purpose |
|-------------------------|---------|
| **The parent comms vault's public key** | To encrypt messages so only the parent can read them |
| **The parent's append token** | To append those encrypted messages to the parent |
| **Its own newly created public/private key pair** | So the parent can encrypt back to it, and it can decrypt replies |

This makes onboarding a simple, repeatable flow: provision a template vault, hand it the parent's public key and append token, and have it generate its own key pair. That is the "very simple link" the project lead wants for the 100 users, behind it, a template vault wired for communication.

## Bidirectional Communication

Putting it together, messaging works both ways with the same primitive:

```
   CHILD  ->  PARENT
     encrypt message with PARENT's public key
     append to PARENT using PARENT's append token
     only PARENT (its private key) can decrypt

   PARENT ->  CHILD
     the child's message included the CHILD's public key (and its append token)
     encrypt reply with CHILD's public key
     append to CHILD using CHILD's append token
     only CHILD (its private key) can decrypt
```

The project lead: **"if in that message you have the public key of the receiver, and the append key, then the append key allows the parent to write back."** So a child's first message can carry its own public key and append token, giving the parent everything it needs to reply, encrypted to the child and appended to the child's vault. The conversation is fully vault-to-vault, encrypted end to end, with append tokens gating writes in each direction.

## What We Want To Prove

The project lead is clear about the milestone: **prove that two vaults (or five) can communicate purely by this method.**

The project lead: **"the workflow we want to prove is, can we have two vaults, or five vaults, communicating just using this method? If we have that, then we have a really powerful solution."** So the first deliverable is not the full rollout; it is the proof that N vaults can hold a bidirectional, encrypted, append-token-gated conversation. Once that works, the scaled rollout (and the general vault-to-vault capability) follows.

This is also the concrete, buildable proof of the broader thesis (cross-ref: the PKI-not-secrets brief and the protocol-harness-workflow FAQ): vaults coordinating through encrypted, gated writes, with no message broker, is the same substrate idea as the Email-FS-lite team coordination (cross-ref: the FAQ's case study), except across *separate* vaults rather than within one shared vault. The append token plus encrypt-on-write is what makes cross-vault communication work.

## What This Asks For

1. **Add append-only token support in SG/Send** (a vault can append-write to another vault; analogous to the read token).
2. **Require encrypt-on-write** (appended data must be encrypted to the recipient's public key; you cannot write unencrypted).
3. **Use public/private keys to validate both sides** (the append token gates who writes; the public-key encryption gates who reads).
4. **Build the template-vault provisioning flow** (each user gets a template vault given the parent's public key and append token, and generates its own key pair).
5. **Support bidirectional messaging** (child to parent and parent to child, via each other's public keys and append tokens).
6. **Prove N-vault communication first** (two, then five vaults communicating by this method, before the full rollout).
7. **Deploy on the first rollout** (the batch of ~100 users, scaling to hundreds and eventually thousands; a very simple link; comms architecture only).
8. **Position as the concrete instance of the PKI thesis** (cross-ref: the PKI-not-secrets brief; cross-vault analogue of the Email-FS-lite coordination).

Estimated effort: moderate; the read-token and public-key machinery exist (cross-ref: the public-preview and PKI briefs), so the new build is the append-only token, the encrypt-on-write enforcement, and the template-vault provisioning. The first milestone (two to five vaults communicating) is small and decisive; the scaled rollout follows.

## What This Does Not Try To Be

- **Not a message broker.** Vaults communicate directly via append-and-encrypt; no server-side message logic.
- **Not plaintext writes.** Encrypt-on-write is mandatory; the append token alone cannot leak readable data.
- **Not a shared single vault.** This is separate vaults communicating (contrast the Email-FS-lite single shared vault; cross-ref: the FAQ).
- **Not the content layer.** Comms architecture only; whatever sensitive content travels over the channel is governed separately.

## Honest Risks

**Risk 1: Append tokens could be abused if leaked.** A leaked append token lets someone write (encrypted) to a vault. Mitigation: the encryption means they cannot write *readable* data; rate-limiting and abuse-resistance; rotate tokens; the token is assurance, the encryption is the protection.

**Risk 2: Key generation and handling on the client.** Each user vault generates a key pair. Mitigation: build on the existing client-side crypto (cross-ref: the vault architecture and PKI briefs); the identity-provider partnership could manage keys at scale (cross-ref: the PKI-not-secrets brief).

**Risk 3: Scale to 100 (and beyond) vaults.** Many child vaults messaging one parent. Mitigation: prove two-to-five first; the parent append surface is the one shared write point, design it to scale (cross-ref: the Email-FS-lite mailroom pattern in the FAQ).

**Risk 4: Append-only semantics and ordering.** Many appenders to one vault need ordering and conflict-freedom. Mitigation: append-only avoids edit conflicts; version control orders writes (cross-ref: the commit-queue brief); the single-writer-per-zone discipline (cross-ref: the FAQ's Email-FS-lite).

**Risk 5: Confidentiality of the content carried.** Sensitive data may travel over the channel. Mitigation: comms architecture only; encrypt-on-write keeps content confidential (only the intended recipient can decrypt); any domain-specific confidentiality is governed separately by the content owner.
