# The Three-Agent Comms Demo: A Browser Harness To Prove Vault-To-Vault Messaging

**version** v0.31.12
**date** 3 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Product, @Dev
**type** Dev brief

---

## What This Is

A concrete demo to prove the vault-to-vault communication capability (cross-ref: the v0.31.12 vault-to-vault-comms append-token brief): **a demo vault with three agents (then five, then scaling to hundreds and eventually thousands), each agent an embedded iframe showing its inbox, with a step-by-step browser harness that validates every assumption, and a small internal API so actions can be triggered for testing.** It assumes the append-token plus public/private-key messaging from the comms brief exists, and exercises it across separate vaults. Start with three; scale after.

The headline architectural point that emerges: this message-passing model is a **better** solution than giving one party full access to another's vault, because it controls exactly what data crosses, and that is worth building the demo to prove.

## The Approach: A Step-By-Step Browser Harness

The project lead wants the proven validation pattern the team has used before: **a mini step-by-step harness, almost like a unit test in the browser, that double-checks every little step and validates every assumption.**

The project lead: **"create this mini step-by-step, almost like a unit test on the browser, that lets us really double-check everything and validate every little step is working, all the assumptions, this one can communicate with that one, this one can do this, that one can do that."** So the demo is not just a working flow; it is an explicit, observable validation harness: each capability (agent A can write to agent B, agent B can read it, agent B can reply, agent A can read the reply) is a checkable step. This is the same browser-based, assumption-by-assumption validation approach used for earlier vault demos (cross-ref: the vault-in-vault and vault-chat demos), applied to cross-vault messaging.

## The Structure: An App With Three Inbox Iframes

The UI: **an agent app (itself an iframe) containing three iframes, each one an agent's inbox, making an email system between agents across separate vaults.**

The project lead: **"the UI I am looking for has three iframes embedded. You have the agent app, which is the iframe, and inside it you can have three iframes. Each iframe is the inbox of an agent. So we are going to have an email system between agents, which is what we already implemented. This is just taking that idea of the inbox to multiple vaults."**

```
   +---------------------------------------------------------+
   |  Agent App  (iframe)                                    |
   |                                                         |
   |  +-------------+  +-------------+  +-------------+       |
   |  | Agent 1     |  | Agent 2     |  | Agent 3     |       |
   |  | (iframe)    |  | (iframe)    |  | (iframe)    |       |
   |  |             |  |             |  |             |       |
   |  | INBOX       |  | INBOX       |  | INBOX       |       |
   |  |  - msg ...  |  |  - msg ...  |  |  - msg ...  |       |
   |  +-------------+  +-------------+  +-------------+       |
   |                                                         |
   |  each agent = its own vault; the inbox is the vault     |
   +---------------------------------------------------------+
```

This is the Email-FS-lite inbox idea (cross-ref: the v0.31.12 protocol-harness-workflow FAQ's case study) generalised from one shared vault to multiple separate vaults: each agent has its own vault, the iframe shows that vault's inbox, and messages move between vaults via the append-token plus encrypt-on-write mechanism (cross-ref: the comms brief). The three iframes let you watch all three inboxes at once and see a message leave one and arrive in another.

## The Internal API

A small API is needed, and it has to be internal: **because each agent is a sandboxed iframe with no shared origin, the API must be created internally (the broker model), and it exposes methods to drive and test the messaging.**

The project lead: **"I like the idea of a mini Swagger kind of API, with methods like ping, send, receive, mark-as-received. Can we do this at API level? Because each of these is a sandboxed iframe, the API will need to be created internally. The reason we need this is I want a nice way to tell the agent to check emails, and to trigger from outside each agent's vault actions like refresh email, and pre-set tests like send email."**

| Method (illustrative) | Does |
|------------------------|------|
| **ping** | Check an agent/vault is reachable |
| **send** | Write an (encrypted) message to another agent's vault (via append token) |
| **receive / refresh** | Pull and deliver new messages into the inbox |
| **mark-received (ack)** | Acknowledge or move a handled message |

Because the iframes are sandboxed (the no-origin model; cross-ref: the v0.27.62 vault-in-vault kernel-model brief), cross-iframe calls go through an internally-created API rather than direct cross-origin calls, which is exactly the broker pattern the vault-in-vault model already uses. The API matters for the harness because it lets the test driver trigger actions from outside (refresh an inbox, send a pre-set message), so each validation step can be invoked and observed rather than only done by hand.

## The Manual Proof (First)

Before any automation, the whole loop should work by hand, which is the first validation: **go to Agent A's vault, send to Agent B, refresh Agent B, see it arrive, reply, refresh Agent A, see the reply.**

The project lead: **"in principle this should work manually. If everything is working and everyone has the right keys, credentials, and public keys, I should be able to go to the first agent's vault and say message the second agent, and that writes a message. Then I go to the second agent and refresh, and it sees the message. It can then reply, and so on."**

```
   1. Agent A vault: "message Agent B"    -> writes encrypted msg, appends to B
   2. Agent B vault: refresh              -> delivers msg into B's inbox
   3. Agent B vault: reply                -> writes encrypted reply, appends to A
   4. Agent A vault: refresh              -> delivers reply into A's inbox

   Each step is an observable assertion in the harness.
```

This manual loop is the minimum proof: if a human can drive a full round trip between two separate vaults with the keys and append tokens in place, the capability works. The API and any automation come after.

## The Key Insight: Messaging Beats Full Vault Access

The architectural realisation, and the reason this matters beyond the demo: **controlled message-passing is a better solution than giving one party full access to another's vault.**

The project lead: **"this will actually be a much better solution than giving one party full access to the other's vault, because we then control specifically what data gets sent from one to the other, and we never have a situation where either side has access to more data than what was sent. It just becomes a protocol of what you message, what you handle, and what APIs and actions you allow. This would be a much better solution than what I had before."**

| Full Vault Access (Before) | Controlled Messaging (This) |
|----------------------------|-----------------------------|
| One party sees the whole of the other's vault | Only the specific data that is sent crosses |
| Over-sharing in both directions | Neither side gets more of the other's data than was sent |
| Access is the unit | The message is the unit |
| Hard to bound | A protocol of allowed messages, actions, and APIs |

So the comms model is not just a convenience; it is a privacy and least-data improvement. Instead of granting access (broad, hard to bound), you exchange specific messages (narrow, explicit, controllable). What crosses is exactly what is messaged, and the relationship becomes a defined protocol of allowed messages and actions, which is far easier to reason about and to contain (cross-ref: the blast-radius and PKI-not-secrets briefs: this is least-data made concrete). This is the deeper reason to build the demo: it proves a better trust model, not just a working mailbox.

## The Phases

There is a clear phasing, and the project lead is explicit about what to do first and what to hold:

1. **Phase 1 (now): the pure proof of concept.** Three agents, three inbox iframes, the internal API, the manual round-trip proof, validating agent-to-agent vault-to-vault communication. This is the priority: prove the comms first.
2. **Phase 2: agentic workflows.** Tie the demo to the ability to run agents via the OpenRouter capability (cross-ref: the v0.31.7 OpenRouter-broker brief), so the agents in the iframes can actually run, opening the existing OpenRouter tool inside.
3. **Phase 3 (later experiment, hold for now): the SG accountant agent.** A fourth agent, an SG accountant, that requests tokens. The project lead: **"maybe don't do this straight away, but it would be interesting,"** so it is noted as a follow-on experiment, not part of the first build. Its appeal: short-lived tokens instead of tokens for everybody, and a comms channel between an SG vault account, admin, manager, and customer-service functions.

Then scale the vault count: three first, then five, then hundreds, and eventually thousands of vaults, which is the level the real deployments need.

## Downstream Use Cases (Noted, Not Built Yet)

The project lead sees many use cases once the comms works, captured here as direction, not as part of this build: short-lived OpenRouter tokens instead of provisioning tokens for everybody; internal comms between SG vault account, admin, customer-service, and other functions; and a help system where a vault holds the knowledge and users ask it questions. These reinforce why the demo matters, but the first deliverable is strictly the three-agent comms proof.

1. **Build the three-agent demo vault** (three agents, scalable to five, then to hundreds and eventually thousands of vaults), each agent its own vault.
2. **Build the UI** (an agent app iframe containing three inbox iframes; an email system across separate vaults).
3. **Build the internal API** (ping, send, receive/refresh, mark-received; internal because the iframes are sandboxed/no-origin; the broker model).
4. **Make it a step-by-step browser harness** (validate every assumption; each capability a checkable step).
5. **Prove the manual round trip first** (Agent A sends, Agent B refreshes and replies, Agent A refreshes; the minimum proof).
6. **Use the comms capability** (the append-token plus encrypt-on-write from the comms brief).
7. **Demonstrate messaging-beats-access** (only the messaged data crosses; a protocol of allowed messages and actions).
8. **Phase it** (PoC first; then agentic via OpenRouter; the SG accountant agent held as a later experiment).
9. **Design for the real scale from the start** (the demo starts at three, but the target is hundreds and eventually thousands of vaults communicating; the parent append surface must handle high fan-in).

Estimated effort: moderate; the iframe/broker model, the inbox pattern, and the append-token comms exist or are specified (cross-ref: the vault-in-vault, FAQ, and comms briefs). The new work is the three-iframe demo app, the internal API, and the validation harness. The first milestone is the manual round trip between two vaults; the harness and the scale-up follow.

## What This Does Not Try To Be

- **Not full vault access.** Controlled messaging; only what is sent crosses.
- **Not one shared vault.** Separate vaults communicating (contrast Email-FS-lite's single vault; cross-ref: the FAQ).
- **Not the SG accountant agent yet.** That is a held, later experiment.
- **Not the production rollout.** A PoC to prove the comms; the scaled rollout to hundreds and thousands of vaults follows (cross-ref: the comms brief).

## Honest Risks

**Risk 1: Sandboxed-iframe messaging is fiddly.** The internal API across no-origin iframes needs care. Mitigation: reuse the vault-in-vault broker model (cross-ref: the vault-in-vault brief); the step-by-step harness surfaces failures early.

**Risk 2: Manual-first might hide automation gaps.** A manual loop working does not prove the API. Mitigation: the API and harness are explicit deliverables; validate each step both manually and via the API.

**Risk 3: Scaling to hundreds and thousands of vaults.** Many vaults stress the model, and that scale is the real target, not an afterthought. Mitigation: prove three, then five, then scale up; watch the shared append surfaces (cross-ref: the comms and FAQ briefs); design the parent append surface for high fan-in.

**Risk 4: Scope creep into phases two and three.** Agentic workflows and the accountant agent could pull focus. Mitigation: phase 1 (the comms PoC) is the priority; phase 3 is explicitly held.

**Risk 5: High fan-in at scale.** When hundreds or thousands of vaults message a single parent, the parent's append surface becomes the bottleneck. Mitigation: design the append surface for high fan-in from the start; partition or shard the parent if needed; the mailroom-style transit zone and version-controlled ordering (cross-ref: the comms and FAQ briefs) keep concurrent appends conflict-free.
