## What This Is

A follow-up to the skills memos, going one level up: **a skills library, a vault that holds skills gathered from different sources, with the links back to those sources, provenance, synchronisation, applicability, evidence (including screenshots of the source), and crucially the documented knowledge of how to actually deploy and run each skill.** The project lead is deliberately calling it a library rather than a marketplace for now (cross-ref: the v0.31.7 skills-marketplace brief), because the immediate insight is that the platform already amounts to a really nice library-management solution, and the skills library is the worked example of that.

This builds on the base-vault, marketplace, and library-as-shop-front work (cross-ref: the v0.31.7 skill-base-vaults and skills-marketplace briefs and the v0.31.9 library-as-shop-front brief) and adds two genuinely new contributions: **the platform as a library-management solution with the skills library as its first instance, and the how-to-deploy-and-run knowledge as a first-class part of a catalogued skill.**

A second idea raised in the same memo, the publishing mode (hosting a vault through GitHub Actions), is captured separately at the project lead's explicit request (cross-ref: the v0.31.12 publishing-mode-vault-via-github-actions brief).

## The Framing: A Library, And A Library-Management Solution

The project lead is choosing the framing carefully: **"I'm not sure I'm going to call it a marketplace right now, but maybe a skills library."** The reason is an insight about what the platform already is: **"if you put it all together, we have a really nice library-management solution."** So the skills library is not only a catalogue of skills; it is the first worked example of the platform functioning as a general library-management solution (cross-ref: the library-as-shop-front brief). The skills are the content; the vault is the library system that manages, sources, provenances, synchronises, and presents them.

This is a useful step back: the marketplace (with scoring, billing, and selling; cross-ref: the marketplace brief) is a destination, but the library (gathering, sourcing, provenancing, documenting, presenting) is the foundation, and the platform already provides it. Start with the library; the marketplace is the evolution.

## The Library Is A Vault Of Skills From Different Sources

The structure: **a vault that holds a collection of skills gathered from different sources, with the platform itself as one of those sources.**

The project lead: **"I'd like to start by creating a vault that is going to have a bunch of skills coming from different sources, and one of the sources is going to be our website."** And the platform is already a source, which is the dogfooding point:

The project lead: **"we are in the final stages of publishing to the main SG/Send website, an agent is already working on it, where we publish the skills I use every day: the skill to talk to the agents, the skill to do Playwright (which is becoming a popular thing), the skills for infographics. So we already are a source of skills."** So the platform is not just building a library of others' skills; it is publishing its own daily-use skills (talk-to-the-agents, Playwright, infographics) and is itself a source. The project lead notes he should add more, but the ones already in daily use are the start. Other sources named are Tessl and possibly Anthropic, among others (cross-ref: the v0.31.9 monetising-on-aggregators-Tessl brief).

| Source | Examples |
|--------|----------|
| **The SG/Send website (own skills)** | Talk-to-the-agents, Playwright, infographics, the daily-use skills |
| **Tessl** | The aggregator's registry (cross-ref: the Tessl brief) |
| **Anthropic and others** | Published skills from other places |

## Provenance, Synchronisation, Applicability, And Evidence (With Screenshots)

The library is not a flat list of copied skills; it carries the full provenance apparatus the platform is built for: **link to the sources, and track provenance, synchronisation, applicability, and evidence, including screenshots of the source.**

The project lead: **"what's interesting about our skills library, which is fundamentally a vault, is that we can link to the sources, and then we do the thing where we think about provenance, synchronisation, applicability, and evidence. I really like the idea of even taking a screenshot of the source, which is what we do with GDPR, and works quite well."**

| Library Apparatus | What It Does |
|-------------------|--------------|
| **Link to the source** | Each skill points back to where it came from |
| **Provenance** | Where it came from, who authored it, version (cross-ref: the base-vault and marketplace briefs) |
| **Synchronisation** | Keep the catalogued skill in sync with its source as the source changes |
| **Applicability** | Where and when the skill applies |
| **Evidence (with screenshots)** | A screenshot of the source as evidence, the GDPR-evidence pattern (cross-ref: the GDPR-assessment brief) |

The screenshot-of-the-source idea reuses the GDPR evidence-capture pattern (cross-ref: the v0.31.5 GDPR-assessment brief), which the project lead notes works well: capturing a screenshot of the source as evidence and putting it in the library, so the catalogue entry is provably anchored to its real source. Synchronisation is the live-not-static principle again (cross-ref: the v0.31.9 knowledge-capture brief): the library keeps each skill in sync with its source, rather than holding a stale copy.

## The Sharp Insight: How To Deploy And Run The Skill

The genuinely new and sharp contribution: **the library captures the knowledge of how to actually deploy and run a skill in a particular environment, which is a real gap that even capable agents hit.**

The project lead's example is the proof: **"the other day I tried the Anthropic legal skill, and it wasn't straightforward. I gave the link to Claude, and Claude said it wasn't sure how to run this."** So a published skill is not self-evidently runnable: having the SKILL.md and the link is not the same as knowing how to deploy it into a specific environment and make it run, and that gap stops even a capable agent. The library fills exactly this gap:

The project lead: **"our skills library can have all the knowledge of how to deploy that into a particular environment, how to make it run, copy and paste if you need it, and eventually even talking online to it."**

| What A Library Entry Captures (Beyond The Skill) | Why |
|--------------------------------------------------|-----|
| **How to deploy it into a particular environment** | The skill alone does not say how |
| **How to make it run** | The runnable steps, not just the definition |
| **Copy-and-paste if needed** | The concrete, do-this-now instructions |
| **How to talk to it online** | Run and interact with it directly (below) |

This is a sharp extension of the base-vault idea (cross-ref: the base-vault brief, which already holds docs, code, and guidance): here the emphasis is specifically on the *deployment and run* knowledge, the thing that turns a published-but-opaque skill into one you can actually use. It is the how-to-use-it documentation as a first-class catalogue field, prompted by the real experience that even Claude could not run the Anthropic legal skill from the link alone. The library is where that know-how lives.

## Talking Online To A Skill, On-Demand Instances, And Billing

The capability that makes the library powerful: **talking online to a skill, connected to on-demand instances and budgets, with the billing mechanism as a real differentiator.**

The project lead: **"talking online to a skill becomes a really powerful thing, especially if you connect with on-demand instances, and then talk to the budgets. Adding the billing mechanism to our workflow will be quite powerful, because I don't think other people have solved it, so others can piggyback on top of us, which goes back to selling other skills with attribution."**

| Element | Role |
|---------|------|
| **Talk online to the skill** | Run and interact with the catalogued skill directly (cross-ref: the vault-chat brief) |
| **On-demand instances** | Spin up to run the skill (cross-ref: the Daytona sandbox brief) |
| **Budgets** | Talk to and manage the cost (cross-ref: the visualisation budget and OpenRouter-broker briefs) |
| **Billing mechanism** | The differentiator, others have not solved it; they can piggyback; sell skills with attribution |

So the library is not just a catalogue; it is a place where a skill can be run and talked to online, on on-demand instances, with budgets and billing handled, and the billing mechanism (cross-ref: the v0.31.7 OpenRouter-broker brief) is the differentiator the project lead believes others have not solved. Because of that, others can piggyback on the platform's billing, which ties back to selling skills with attribution (cross-ref: the v0.31.9 monetising-on-aggregators-Tessl brief): the library can host and run others' skills, with attribution and billing, and the billing is the moat.

## What This Asks For

1. **Build the skills library as a vault** (skills from different sources, including the platform's own).
2. **Position the platform as a library-management solution** (the skills library as its first instance; the library as foundation, marketplace as evolution).
3. **Publish the platform's own skills** (talk-to-agents, Playwright, infographics, the daily-use ones; add more over time).
4. **Carry the full provenance apparatus** (link to source, provenance, synchronisation, applicability, evidence with screenshots; the GDPR pattern).
5. **Capture how-to-deploy-and-run knowledge** (per environment, how to make it run, copy-and-paste; the gap even capable agents hit).
6. **Enable talking online to a skill** (on-demand instances, budgets, billing; the vault chat).
7. **Make billing the differentiator** (others piggyback; sell skills with attribution).
8. **Produce the library page and example vault** (the page is the skills library; the example vault holds the real skills with their provenance and how-to-run knowledge).

Estimated effort: moderate; the vault, the provenance machinery, the screenshot-evidence pattern, the chat, the sandboxes, and the billing substrate exist. The new work is the library structure, the synchronisation to sources, the how-to-deploy-and-run field, and publishing the platform's own skills. The MVP is a real skills-library vault with a handful of skills (the platform's own plus a couple from Tessl or Anthropic), each with provenance, a source screenshot, and how-to-run knowledge.

## What This Does Not Try To Be

- **Not a marketplace yet.** A library first (gather, source, provenance, document, present); the marketplace is the evolution.
- **Not a flat list of copied skills.** Linked to sources, provenanced, synchronised, evidenced.
- **Not just the SKILL.md.** It captures how to deploy and run the skill, the real gap.
- **Not static.** Synchronised with the sources; the live-not-static principle.

## Honest Risks

**Risk 1: Synchronisation with external sources is non-trivial.** Keeping catalogued skills in sync with changing sources is work. Mitigation: links and provenance; the synchronisation machinery; flag staleness; the live-not-static discipline (cross-ref: the knowledge-capture brief).

**Risk 2: Licensing of catalogued skills.** Hosting and running others' skills raises licensing (cross-ref: the Tessl brief). Mitigation: verify per source; attribution; link to source; the library can be reference-where-not-resellable.

**Risk 3: Running skills online has execution and cost risk.** On-demand instances and billing carry risk. Mitigation: sandboxes (cross-ref: the Daytona brief); budgets (cross-ref: the visualisation and OpenRouter-broker briefs); the billing substrate handles cost.

**Risk 4: How-to-run knowledge can go stale.** Deployment steps change. Mitigation: synchronisation and provenance; version control; the knowledge is maintained like the skill (cross-ref: the ownership brief).
