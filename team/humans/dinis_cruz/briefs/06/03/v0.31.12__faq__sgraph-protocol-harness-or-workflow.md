# SGraph: Is It A Coordination Protocol, An Agent Harness, Or A Workflow?

**version** v0.31.12
**date** 3 June 2026
**type** FAQ / explainer (site content)

---

## What This Answers

A question that comes up once a technical person has understood SGraph, usually after seeing it in use: is it an agent coordination protocol, an agent harness specification, or a workflow? It is a sharp question, and the honest answer is that it is none of those three as a primitive, and that this is the point. This document explains why the question arises, why the instinct behind it is correct, takes each of the three in turn, and gives the model that resolves it, with diagrams.

## Why The Question Arises (And Why The Instinct Is Right)

The question almost always comes from someone who saw the vault first, and saw it *through usage*: a clinical workflow, a pen-testing delivery, a blast-radius viewer, a risk-management tool writing back to the vault. Seeing the vault as the thing under all of those, it is entirely reasonable to conclude that it must be a coordination protocol, or a harness, or a workflow, and to suspect it might be all three at once.

That instinct is correct, and it should not be corrected so much as completed. A vault genuinely does enable all three. The reason is not that it is a blend of them, but that it sits one layer beneath them. Coordination protocols, agent harnesses, and workflows are things built *on top of* a vault, not things a vault *is*. Those three are about behaviour (how agents talk, how one runs, what steps happen). SGraph is about state (where the work lives, how it is shared, how you prove what happened). It is the noun, not the verbs. Someone arrives at three possible answers because, from whichever layer they are standing on, the vault looks like the thing that makes their layer work, and that is the signal that it sits beneath all of them.

## The Two Views

The reason the vault can feel like all three is that it is normally experienced from the top, where it is invisible, and only revealed from the side, where its structure shows.

```
   THE SHIPPED EXPERIENCE                THE PLATFORM VIEW
   (what the user sees)                  (what a builder sees)

   +-----------------------+             +-------------------------+
   |                       |             | top:  bespoke UX        |
   |  a knee-doctor app    |             +-------------------------+
   |  a blast-radius viewer|             | middle: agents,         |
   |  a pen-test delivery  |    <==>      |   harnesses, workflows, |
   |  a risk tool          |             |   protocols, manual steps|
   |                       |             +-------------------------+
   |  (no vault in sight)  |             | bottom: SGraph VAULT     |
   +-----------------------+             |   shared state + content |
                                         |   + provenance + access  |
   the vault is invisible;              +-------------------------+
   the experience is the product         the vault is the substrate
```

This is deliberate. The top line, the experience, is commoditised down to something simple, focused, and bespoke, precisely so that any kind of machinery can live underneath it without the user ever seeing it. Some of that machinery is agentic, some is conventional workflow, and some is manual. The vault is what lets the top be simple because the middle is free to be whatever the use case needs.

## Q1. Is SGraph An Agent Coordination Protocol?

No, not as such. A protocol defines *how* agents communicate: message formats, handoffs, wire conventions (MCP, or the agent-to-agent protocols emerging now).

But agents coordinate *through* a vault without needing a direct protocol at all. They read and write shared state, and because every change is versioned and attributed, the coordination is auditable by construction. It is closer to how a team coordinates through a shared git repository than to a wire protocol: the shared medium is the coordination.

The cleanest proof is that we run exactly this, in production. The SGraph agent team (@Content, @Dev, @Journalist, @Observer, @AppSec, @Comms, @Ontologist) coordinates entirely through a protocol called **Email-FS-lite**, with no broker, no daemon, no API, and no server. The full case study is below. The point for this question: Email-FS-lite *is* a coordination protocol, and it is built entirely out of files, folders, and commits in a vault. The vault is not the protocol; it is the substrate the protocol is built on, and you can build others (or run MCP) on the same substrate.

## Q2. Is SGraph An Agent Harness Specification?

No, and it is deliberately harness-agnostic. A harness is the runtime an individual agent executes in: the loop, the tool interface, the context management (Claude Code is a harness; Pi is a harness).

SGraph specifies none of that. What it provides is the persistent context, memory, state, and tools that a harness plugs into and reads from and writes back to. Different harnesses can work with the same vault, and the vault outlives any one of them. If anything, SGraph is what stops an agent's memory and state from being trapped inside one harness.

```
   [ Pi ]      [ Claude Code ]     [ a custom harness ]
      \              |                     /
       \      plug in: read context,      /
        \     write results, use tools   /
         v           v                  v
       +-----------------------------------+
       |          SGraph VAULT             |
       |  persistent state + context +     |
       |  tools the harness consumes       |
       +-----------------------------------+
     swap the harness; the vault and its history remain
```

## Q3. Is SGraph A Workflow?

No, but this is the closest of the three, and probably why it can feel like all of them. SGraph is not a workflow engine and prescribes no sequence of steps.

But a workflow is a series of steps, and that series can be codified, versioned, and run against a vault. The vault holds the workflow as content (this is essentially a "skill"), holds the code that drives it where there is code, and holds the workflow's evolving state and the provenance of every step. So the vault is where a workflow lives, runs, and leaves its trail, not the thing that drives it, and it is what turns a workflow into something shippable.

## Q4. So Can It Be All Three?

Yes, in the sense that matters: a vault can underpin all three. But it does so by sitting at a different layer. It is the substrate; protocols, harnesses, and workflows are the layers above, and each sees the vault as the thing that makes it work. That is exactly why it can feel like any of them.

A useful detail on where the backend lives. The vault and the assets it holds (such as Vault Apps) have no backend: that part is client-side and as simple as file storage. But the vault freely *enables* workflows that call out to systems that do have backends, an LLM, a security product such as a blast-radius service, any API or SaaS, through calls made from the vault experience. So the vault is a backend-less client-side surface that reaches whatever backend a use case needs. That is what keeps the substrate simple while the workflows on top can be arbitrarily powerful.

And there is a property worth stating plainly, because it is counterintuitive: the more tightly an agent is scoped in a vault, the more freedom it can safely be given. With least-privilege boundaries, vault-to-vault permissions, and constrained write zones, the blast radius of any agent is contained, which is exactly what makes it safe to let it act. Restriction is what enables capability, not the opposite.

## The Mental Model

The model we use internally: a vault is like **git plus a filesystem plus PKI, for humans and agents to share state.** A place to put the work, version it, branch it, prove it, and control who sees what, with everything else layered above.

## Case Study: How The SGraph Agent Team Coordinates

The clearest demonstration that "agents coordinating through an encrypted, versioned object store" is practical, not theoretical, is that the SGraph team runs on it. The agents that built the public library (@Content, @Dev, @Journalist, @Observer, @AppSec, @Comms, @Ontologist) coordinate entirely through a collaboration vault, using a protocol called **Email-FS-lite**. The library is the evidence: it was produced by the very protocol it documents.

**The mailbox is a folder.** Agents communicate by exchanging RFC 2822 `.eml` messages as files. There is no mail server; the vault is the mail server.

```
   mail/
     mailroom/{recipient}/     <- the one shared write surface (transit)
     {agent}/
       inbox/                  <- delivered, open work
       done/                   <- handled
       outbox/{recipient}/     <- the sender's tracking copy
       issues/                 <- OPEN / BLOCK / UNBLOCK / CLOSE
     sessions/{agent}/         <- brief.md (once) + notes.md (append-only)
```

**A message has a lifecycle, and it is just moving files.**

```
   SEND        sender writes a .eml to mail/mailroom/{recipient}/
               and a copy to its own outbox/{recipient}/
                      |
   DELIVER     recipient moves it from the mailroom into its inbox/
               (only the recipient touches its inbox)
                      |
   WORK OPEN   while it sits in inbox/, the work is open
               (replying does not close it)
                      |
   DONE        recipient moves it to done/ when the work is complete

   Messages are immutable: you only move them, never edit them.
   The read receipt is implicit: when the mailroom copy disappears,
   the message was delivered.
```

**Single-writer ownership keeps it conflict-free.** Each agent writes only inside its own folder, plus the mailroom when sending. Everywhere else is read-only. If an agent spots a problem in another agent's area, it does not fix it; it sends mail flagging it, and the owner fixes it. Conflicts within an agent's zone become structurally impossible, and every change is attributable to exactly one agent.

**One commit per cycle.** Each working session ends with a single `sgit` commit capturing everything done in that cycle: mail delivered, replies sent, issues updated, notes appended. The commit is one unit of agent cognition, and the commit history is therefore the complete, ordered, immutable audit trail. There is no separate audit system; the audit trail is the medium. The vault is also the team's durable memory: sessions start and stop, but a new session pulls the vault and knows exactly where things stand.

What this demonstrates, in one line: a multi-agent team coordinating with no message queue, no shared database, and no coordinator service, on the same encrypted, versioned vault technology that stores the content, getting ordering and audit for free from the version history and confidentiality from the encryption. It is the substrate thesis, running in production.

## In One Line

SGraph is not a coordination protocol, an agent harness, or a workflow. It is the shared, versioned, provenanced, encrypted state layer that all three are built on. The medium, not the mechanism.
