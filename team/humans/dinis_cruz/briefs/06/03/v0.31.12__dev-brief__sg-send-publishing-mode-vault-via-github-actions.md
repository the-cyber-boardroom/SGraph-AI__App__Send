## What This Is

A separate memo (the project lead explicitly asked for this to be captured on its own) on a **publishing mode**: a vault that is used to edit information and that has a public element, a published website, where the published static files are generated and hosted through GitHub Actions, while the live data stays encrypted. It is the companion to the skills-library brief from the same memo (cross-ref: the v0.31.12 skills-library brief) and a sibling to the existing publishing approaches: the static-page-that-exposes-a-read-only-key (cross-ref: the v0.31.9 public-preview-with-embedded-read-only-key brief) and the Netlify deploy-via-zip integration (cross-ref: the v0.31.7 Netlify-AX brief). Here the host is GitHub, via GitHub Actions.

A related thread the project lead raised, exploring more of the GitHub agentic capabilities, is explicitly parked at his request ("don't add that yet") and is noted only as a future topic at the end.

## The Existing Approach This Builds On

The starting point is the publishing approach already used on the main SGraph website: **a static page that exposes the read-only token and directly accesses the encrypted files.**

The project lead: **"there's another way of hosting a vault, which is what we do on the main SGraph website, where we create a static page that leaks the read-only token and exposes and directly accesses the encrypted files. For some of these vaults, that would be a really good way of doing it."** This is the public-preview-with-embedded-read-only-key model (cross-ref: the public-preview brief): a public, static page carries the read-only key and renders the encrypted vault content client-side or at the edge. The project lead's point is that this approach suits some of the library vaults and content well, and the new idea extends how that static publishing is hosted and generated.

## The Idea: Publishing Mode

The concept the project lead is describing: **a vault used to edit the information, with a public element (the published website), where the publishing is automated.**

The project lead: **"what I'm describing is a publishing mode, where you have a vault that is used to edit the information, and the vault has a public element, the website that is published. We need to think about how that works."**

| Element | Role |
|---------|------|
| **The vault (private/editable)** | Where the information is edited and managed; the source of truth |
| **The public element** | The published website, generated from the vault |
| **The publishing step** | Automated generation of the public static site from the vault |

So the vault is the editable source of truth, and the published website is its public face, generated from it. This is the agent-controlled-websites and library-as-shop-front pattern (cross-ref: the v0.31.7 agent-controlled-websites and v0.31.9 library-as-shop-front briefs), here framed specifically as a publishing mode with an automated publish step.

## The Mechanism: GitHub Actions

The specific mechanism the project lead proposes: **publish the data inside the vault, then use a GitHub Action to publish all the files statically.**

The project lead: **"a simple thing we could do is publish the data to be published inside the vault, and then in a GitHub Action we publish all the files statically. So the interesting question is how to host a vault in a GitHub Action. Could we have a vault hosted in GitHub, and use the publishing of the vault through GitHub Actions, where you just publish this data, and the live data is still all encrypted, same standard processes."**

| Step | What Happens |
|------|--------------|
| **1. Edit in the vault** | The information is edited and managed in the vault |
| **2. Mark data to be published** | The data to be published is identified inside the vault |
| **3. Vault hosted in GitHub** | The vault (encrypted) lives in a GitHub repository |
| **4. GitHub Action publishes** | A GitHub Action generates and publishes the static files |
| **5. Live data stays encrypted** | The published site uses the same standard read-only-key process; the data remains encrypted |

So the flow is: edit in the vault, host the (encrypted) vault in GitHub, and trigger a GitHub Action that statically publishes the public files, with the live data still encrypted via the same read-only-key approach. This is the GitHub analogue of the Netlify deploy-via-zip integration (cross-ref: the Netlify-AX brief): the same vault-to-static-published-site pattern, with GitHub Actions as the build-and-publish mechanism and GitHub (Pages or similar) as the host.

## The Sharper Question: Keep It Encrypted Even On GitHub

A sharper extension the project lead raised: **could the whole data stay encrypted even on GitHub, so that even on GitHub it is not readable?**

The project lead: **"what is interesting is that you could even have the whole data encrypted in GitHub, so even on GitHub it wouldn't be readable."** This preserves the zero-knowledge property all the way into the host: the vault's data sits encrypted in the GitHub repository, and only the published, intended-public output (via the read-only key) is exposed, so GitHub itself (and anyone with repository access) cannot read the underlying vault. This is consistent with the platform's zero-knowledge model (cross-ref: the public-preview and vault architecture briefs): hosting in GitHub does not mean trusting GitHub with the cleartext; the data stays encrypted at rest in the repo, and only the deliberately-published surface is readable.

## The Dev Ask: An Extension To Publish A Vault To GitHub

The concrete development question the project lead poses: **could there be an extension to publish a vault to GitHub, or to trigger a GitHub Action to do it?**

The project lead: **"could we have an extension to publish a vault to GitHub, or to trigger a GitHub Action to do that? There are some interesting integrations here with GitHub."** So the dev ask is an extension (or integration) that, from a vault, publishes it to GitHub and/or triggers the GitHub Action that generates and publishes the static public site, with the encrypted data in the repo and the read-only-key process exposing only the public surface. This sits alongside the Netlify integration (cross-ref: the Netlify-AX brief) as a second host-and-publish path, GitHub via Actions, giving the platform more than one way to publish a vault as a public site.

Don't add that yet."** It is noted here only as a future topic and is not developed in this brief.

## What This Asks For

1. **Define the publishing mode** (a vault edits the information; a public element, the published website, is generated from it; an automated publish step).
2. **Build the GitHub Actions publish path** (host the encrypted vault in GitHub; a GitHub Action generates and publishes the static files; the read-only-key process exposes only the public surface).
3. **Keep the data encrypted even on GitHub** (the vault's data sits encrypted in the repo; GitHub itself cannot read it; zero-knowledge preserved into the host).
4. **Build the extension/integration** (publish a vault to GitHub, or trigger a GitHub Action to do it).
5. **Position it alongside Netlify** (a second vault-to-static-published-site host-and-publish path; cross-ref: the Netlify-AX brief).
6. **Reuse the existing publishing model** (the static-page-with-read-only-key approach; cross-ref: the public-preview brief).
7. **Park the GitHub agentic exploration** (noted as a future topic; not developed now, per the project lead).
8. **Produce the example** (a vault published to GitHub via a GitHub Action, with the data encrypted in the repo and the public site live).

Estimated effort: moderate; the static-publishing and read-only-key model exists (cross-ref: the public-preview brief), and the pattern mirrors the Netlify integration. The new work is the GitHub Actions publish flow, the encrypted-in-the-repo handling, and the extension to publish or trigger from a vault. The MVP is a vault hosted (encrypted) in GitHub, publishing its public site via a GitHub Action.

## What This Does Not Try To Be

- **Not a new publishing model.** It reuses the static-page-with-read-only-key approach, hosted via GitHub Actions.
- **Not trusting GitHub with cleartext.** The data stays encrypted in the repo; only the public surface is exposed.
- **Not GitHub-only.** It sits alongside Netlify as one of several host-and-publish paths.
- **Not the GitHub agentic exploration.** That is parked, per the project lead.

## Honest Risks

**Risk 1: The read-only key on a public static page exposes the public content.** Mitigation: only public content is published; the same controlled-exposure model as today (cross-ref: the public-preview brief); the rest stays encrypted.

**Risk 2: Encrypted-in-the-repo must be done correctly.** Keeping the vault encrypted in GitHub needs care. Mitigation: the same standard vault encryption processes; only the published surface is decrypted; validate the approach.

**Risk 3: Dependence on GitHub Actions.** The publish path depends on GitHub. Mitigation: it is one of several paths (Netlify too; cross-ref: the Netlify brief); the vault and content are portable.

**Risk 4: Scope creep into GitHub agentic features.** Mitigation: that thread is explicitly parked; this brief is only the publish path.
