## What This Is

The use cases and user journeys, written as user stories that drive everything we build: **a set of Gherkin-style stories across the three roles from the first-cohort brief, the power user granting permissions, the adopter of an AI-powered service, and the LLM-service vendor, plus the back-end and platform stories, adding mappings for a new endpoint, capturing the data when a user talks to an LLM, and handling user submissions and custom requirements, with each story carrying its Gherkin scenario, a user and UX flow, the success criteria, and the billable units, the free part, and the paid part with the value it provides.** It follows directly from the first-cohort brief and turns the cohort into buildable journeys (cross-ref: the v0.33.28 first-cohort, assessment-template, WhatsApp-case-study, and need-to-ship briefs, and the v0.33.40 commercial-model brief). New contributions: **the user stories, their Gherkin and UX flows, and the per-story billing.**

## The Framing

What this is: **everything driven by a user story.**

The project lead: **"this is a follow-up from the users one. I want a document that focuses on use cases and user journeys, as user stories: as a user I want to do this, I want to know this, I want to pay this, I want this experience. Define five to ten user stories, and for each one the Gherkin workflows, the user flows, the mock-up UX, the success criteria, the experience, the billable units, and the prediction on payment and value, what is free and what is not. And think about the back-end stories too, like adding mappings for a new endpoint, or capturing the data when a user talks to an LLM. Everything we do should be driven by a user story."** So this is the buildable, journey-level layer the rest of the work feeds.

## Front-End Stories: The Power User

**Story 1: Assess an integration before granting**

As a user running agents, I want to see what an integration can do before I grant it, so that I am never surprised.

```gherkin
Given I am about to connect an MCP server or a connector
When I run an assessment on it
Then I see the blast radius, the data in reach, and what I am authorising
And I can accept for a window, narrow it, or walk away
```

```
[ connect ] -> [ assessment runs ] -> [ blast-radius card ] -> [ accept / narrow / stop ]
```

Success: the user sees the authorised universe before granting, and no surprise action is possible without having appeared in the assessment.
Billing: free basic assessment; paid deeper analysis. Value: avoided incidents and confident decisions.

**Story 2: Monitor my agents' blast radius over time**

As a power user, I want to track the blast radius of all my agents, so that I am alerted when it changes.

```gherkin
Given I have connected several agents and integrations
When the permissions or reach of any of them changes
Then I am alerted with what changed and the new blast radius
And the change is recorded in the vault with provenance
```

Success: every material change surfaces within the monitoring window.
Billing: paid monitoring, by usage. Value: continuous no-surprises assurance.

## Front-End Stories: The Service Adopter

**Story 3: Understand what I am accepting**

As someone adopting an AI-powered service, I want to know exactly what permissions and terms I am accepting, so that I can make a good decision.

```gherkin
Given I am evaluating a third-party AI service
When I ask for its permission and data footprint
Then I see what it requires, what it can reach, and what I would be accepting
```

```
[ paste / pick service ] -> [ footprint report ] -> [ plain-language terms ] -> [ decide ]
```

Success: the adopter can state what they are accepting in plain language before they buy.
Billing: free quick check; paid full assessment. Value: a good acquisition decision.

**Story 4: Compare two services on safety**

As a buyer, I want to compare the permission footprints of two services, so that I can choose the safer one.

```gherkin
Given two candidate AI services
When I compare them
Then I see which requires fewer permissions, has guardrails, and carries less blast radius
```

Success: a clear, evidenced side-by-side.
Billing: paid comparison. Value: a defensible procurement choice.

## Front-End Stories: The LLM-Service Vendor

**Story 5: See my own reality, internally**

As an LLM-service vendor, I want to see what my product is authorised to do in customer environments, so that I can fix over-privilege before it becomes an incident.

```gherkin
Given my product integrates into customer environments
When I run the assessment against my own integration
Then I see my product's blast radius and the permissions I could drop
```

Success: the vendor gets an honest internal picture and a list of reducible permissions.
Billing: paid posture tooling. Value: fewer incidents, less lost trust.

**Story 6: Prove we are more secure**

As a vendor, I want to publish evidence that I require fewer permissions and have guardrails, so that I win on trust.

```gherkin
Given I have reduced my product's blast radius
When I publish the evidence as a read-only vault
Then customers and regulators can verify my posture
```

Success: a verifiable, published posture a customer can check.
Billing: paid proof and attestation tooling. Value: a competitive advantage on trust.

## Back-End And Platform Stories

**Story 7: Add mappings for a new endpoint (and user submissions)**

As a user with specific requirements, I want to submit or request mappings for a new endpoint or connector, so that assessments cover it.

```gherkin
Given an endpoint or connector not yet mapped
When I submit it or request a mapping
Then the platform maps its permissions and blast radius
And future assessments include it
```

Success: a submitted endpoint becomes assessable, with provenance on who added it.
Billing: free to submit; paid for priority or custom mappings. Value: coverage of the user's real stack.

**Story 8: Capture the interaction when a user talks to an LLM**

As the platform, when a user talks to an LLM, I want to capture that interaction with consent, so that I can map permissions and blast radius in context.

```gherkin
Given a user is interacting with an LLM through a captured path
And the user has consented to capture
When the interaction touches data or actions
Then the platform records it and maps the in-context blast radius
```

Success: in-context assessments reflect real interactions, with consent recorded.
Billing: usage-based capture and analysis. Value: assessments grounded in reality, not theory.

Every story has a free entry and a paid path that maps to the billable units, with a low-friction way to connect (cross-ref: the commercial-model and first-cohort briefs).

## What This Asks For

1. **Drive everything from a user story** (use case first).
2. **Cover the three roles** (power user, adopter, vendor).
3. **Cover the platform stories** (endpoints, capture, submissions).
4. **Give each a Gherkin scenario, a flow, and UX** (buildable).
5. **Set success criteria per story** (the acceptance test).
6. **Attach billing to each** (free entry, paid path, value).

Estimated effort: these are the first journeys to build and ship; each is small enough to ship and learn from.

## What This Does Not Try To Be

- **Not a feature list.** It is journeys driven by user needs.
- **Not front-end only.** Platform stories are first-class.
- **Not free or paid only.** Each has both, by design.
- **Not final.** It is the first set, to ship and refine.

## Honest Tensions

**Tension 1: scope.** Ten stories is a lot to ship at once. Mitigation: ship the highest-value ones first, learn, then add.

**Tension 2: capture and consent.** Story 8 touches sensitive data. Mitigation: consent is part of the scenario, recorded in the vault.

**Tension 3: free-to-paid balance.** Too much free, no revenue; too little, no adoption. Mitigation: the billable-units table is the place to tune it.
