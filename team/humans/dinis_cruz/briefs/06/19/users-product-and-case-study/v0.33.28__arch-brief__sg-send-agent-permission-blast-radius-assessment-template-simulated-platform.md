## What This Is

The generic template for an agent permission and blast-radius assessment, written as if the platform already exists: **the information we capture, the bits of the puzzle and the materials, an intake that starts from how are you using this and how are you integrated, ASCII architecture, user, and permission flows, a blast-radius view of what the agent can do, a risk-acceptance flow that names who must accept and lets them narrow or remove, an evidence vault that holds it all with provenance, and the multi-stakeholder experience so each party sees its own lens; it is the reusable template that the WhatsApp case study then instantiates.** It answers the project lead's request to simulate what an assessment looks like on paper and on screen before building it (cross-ref: the v0.33.40 agent-authorisation-blast-radius, risk-acceptance, side-effects, and proactive-evidence-database briefs, and the vault-in-vault model). New contributions: **the assessment template, the flows, and the simulated assessment output.**

## The Framing

What was asked: **assume the platform exists, and show what it looks like.**

The project lead: **"create first a generic template: this is the information we want, the bits of the puzzle, the materials. Assume the platform exists. What would it look like on paper, and from a visual point of view, maybe even some UX mock-ups, taking everything we talked about, the vaults and all. Connect ASCII art diagrams, architecture flows, user flows, and then map the permissions."** So this is a simulation of the product's output, used to make the idea concrete and to drive the case study.

## The Intake: How Are You Using This?

Where every assessment starts: **the two questions that frame the risk.**

The project lead: **"it is a good example of those initial questions: how are you using this, how are you integrated? You have a WhatsApp integration, you can talk to an agent using your phone, great, here is the risk, here is everyone who should accept it, and here is what it actually means."** So the intake captures the integration, the identity behind it, and the mode of connection, because the mode is what decides the blast radius.

## The Information We Capture

The bits of the puzzle:

| Field | What it captures |
|-------|------------------|
| Integration | The system the agent connects to |
| Mode | How it connects (the access path, the most decisive field) |
| Identity | The non-human identity and the human behind it |
| Granted permissions | What the integration was authorised to do |
| Data in reach | What the permissions expose |
| Actions possible | What the agent can do, not what it did |
| Other parties | Who else is implicated, including non-consenting ones |
| Environment | Where it runs, and what that environment can reach |
| Duration | How long the authorisation stands |

```
+--------+     +-----------+     +-----------------+     +-------------+
     |                                   |                      |
     | grants                            | determines           | exposes
     v                                   v                      v
  authorisation                    blast radius            second parties

```

## User Flow

The assessment journey the user is taken through:

```
[1] Connect / declare      [2] Declare mode        [3] Map permissions
    the integration    -->     (how integrated)  -->  (what was granted)
                                                            |
                                                            v
[6] Accept, narrow,    <--  [5] See who must    <--  [4] See blast radius
    or remove now           accept (flows up)        (what it CAN do)
```

## The Permission Map

Granted permissions become a graph of what they enable:

```
 Granted permission        Enables (the reach)         Blast radius
 ------------------        -------------------         ------------
 read messages       -->   full chat history     -->   exposure of all
                                                        conversations
 send messages       -->   act as the account    -->   impersonation,
                                                        spam, contact harm
 read contacts       -->   the social graph      -->   third-party data,
                                                        non-consenting people
 media access        -->   photos, voice, files  -->   sensitive content
```

## The Blast-Radius View

The plot-twist screen: **what the agent is authorised to do, scored, not what it has done.** Each enabled capability is rated by reach, reversibility, and the parties it touches, so the universe of the possible is visible at a glance, with the worst-case clearly marked and the certain facts (an open path) separated from the hypotheses.

## The Risk-Acceptance Flow

Who must accept, and what they can do about it:

```
  Owner accepts (the click = accountability)
        |
        v   if not comfortable: narrow the permission, or remove now
  Boss underwrites
        |
        v
  Exec / Risk owner underwrites
        |
        v
  Consolidated report: N integrations, M agents that could do X; or zero
```

The only variables are how narrow the permission is and how long it is accepted; discomfort alone changes nothing (cross-ref: the risk-acceptance brief).

## The Evidence Vault

Where the assessment lives:

```
integration-vault/
  assessment.md            (the current assessment and score)
  intake.md                (how used, how integrated, identity)
  permission-map/          (the graph of granted permissions)
  blast-radius/            (what the agent can do, per capability)
  risk-acceptance/         (who accepted, when, for how long, narrowed)
  evidence/                (real-world incidents, sources)
  history/                 (the commit log, provenance over time)
```

Each integration is a git-compatible vault with full provenance, and vaults compose into a portfolio vault for the consolidated report (cross-ref: the vault-in-vault model and the proactive-evidence-database brief).

## The Multi-Stakeholder Experience

Each party sees its own lens onto the same graph: the user sees what they are about to authorise and what it means; the asset owner sees the reach into their system; the risk owner sees the consolidated, upward-flowing acceptance; and a regulator or affected third party sees the parties implicated. The same evidence, read in each party's language (cross-ref: the side-effects recipient-language brief).

## What This Asks For

1. **Capture the bits of the puzzle** (the intake fields).
2. **Start from how you are using and integrated** (the mode decides the risk).
3. **Map permissions to what they enable** (the permission graph).
4. **Show the blast radius** (what the agent can do, scored).
5. **Run the risk-acceptance flow** (who accepts, narrow or remove).
6. **Hold it in an evidence vault** (with provenance).
7. **Render each stakeholder's lens** (the multi-party views).

Estimated effort: moderate to prototype the template and flows; this is the simulation that precedes the build.

## What This Does Not Try To Be

- **Not the finished UI.** It is a paper-and-ASCII simulation to react to.
- **Not a behaviour log.** It shows the authorised universe, not history.
- **Not single-party.** It serves every implicated stakeholder.
- **Not generic forever.** The WhatsApp case study instantiates it.

## Honest Tensions

**Tension 1: simulating before building.** A mock can flatter the real thing. Mitigation: keep it honest about what is hard, especially the permission mapping.

**Tension 2: completeness versus clarity.** The assessment can drown in fields. Mitigation: the blast-radius and accept screens lead; detail sits in the vault.

**Tension 3: stakeholder views multiply work.** Each lens is effort. Mitigation: one graph, many reads, not many graphs.
