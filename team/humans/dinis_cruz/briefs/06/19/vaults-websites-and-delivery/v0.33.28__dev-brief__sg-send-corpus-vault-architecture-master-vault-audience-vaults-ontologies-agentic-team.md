**version** v0.33.28
**date** 19 June 2026

**to** Architect agent, Librarian, Ambassador, Product, @Dev
**type** Dev brief (a brief for the vault-creating agent)

## What This Is

A brief for the agent now creating the vaults, organizing the whole corpus into multiple interconnecting vaults: **it takes the memos and the new infographics and structures them into a master admin vault that links to and manages all the others, audience vaults for investors and customers, public data vaults for anything made public, and separate vaults for specific websites or content such as the WhatsApp reviews; it builds multiple ontologies for the multiple content areas and maps the audiences of the documents so the content can be adjusted to them; it leverages the chat-within-the-vault capability so you can talk to the content; it sets up the agentic team, the librarian, the architect, the ambassador, and a fourth role, each talkable on the website; and it distinguishes read-only from read-write access, starting with read-only; it is itself a demo of how multiple vaults interconnect.** It is the practical, self-referential task of organising this body of work (cross-ref: the vault-in-vault model, the v0.33.26 linkedin-agentic-team-vault-agents brief, the v0.33.27 archiver-cataloguer-librarian brief, the v0.33.38 chat-edits-the-vault brief, and the v0.33.26 vault-powered-websites brief). New contributions: **the corpus vault structure, the multiple-ontologies-and-audiences mapping, and the website agentic team.**

## The Framing

What this is: **a brief for the agent creating the vaults, as a live demo.**

The project lead: **"this is a brief for the agent that is now creating the vaults for the different permissions. It is a big example for us, because it shows how vaults work and how they interconnect in these environments."** So organising the corpus doubles as a demonstration of the multiple-vault model.

## The Setup

What the agent already has: **architect access to the project and the infographics.**

The project lead: **"I gave that agent access. It starts as an architect for the SG/Send project, which has access to all the memos we have written. I also uploaded three zip files containing all the infographics, one per document, created with ChatGPT deep research and ChatGPT images, which came out really well."** So the agent has the full memo corpus and the matching infographics to organise.

## The Need To Navigate

The first problem to solve: **there is now a lot to find.**

The project lead: **"we need a really good way to navigate the content. There are now around twenty-eight documents, plus the graphics, so we need to capture what is going on and capture the information."** So navigation and capture come first, because the corpus has grown past the point where a flat list works (cross-ref: the librarian and cataloguer brief).

## Multiple Ontologies And Audience Mapping

How to structure it: **many ontologies, mapped to audiences.**

The project lead: **"this is a perfect example of creating an ontology, multiple ontologies for the multiple contents, because there are multiple areas. Map the audiences of the documents, then adjust the content to them."** So the structure is not one taxonomy but several ontologies for the several content areas, each tied to an audience, so the same material can be presented in each audience's language (cross-ref: the graphs-of-graphs and side-effects recipient-language briefs).

## The Vault Structure

The vaults to create: **a master, public, audience, and topic vaults.**

The project lead: **"there is the master vault, which contains the links to all the vaults; it is the one we use for admin, where we create and manage vaults, and it should have a description. We have public data vaults for anything we make public straight away. Anything we can map as a specific website or specific content, like the WhatsApp reviews or other agents, should be separate vaults. We should have one for investors that maps all the documentation from the investor point of view, and one for customers mapped from the customer point of view."**

```
master-vault/            (admin: links to and manages all vaults, with a description)
  public-data-vault/     (anything made public straight away)
  investor-vault/        (the corpus from the investor point of view)
  customer-vault/        (the corpus from the customer point of view)
  whatsapp-reviews-vault/(a specific website or content area)
  <topic>-vault/         (further specific websites or content)
```

So the master vault is the admin and index, and the rest are public, audience, and topic vaults that interconnect through it (cross-ref: the vault-in-vault model and the vault-powered-websites brief).

## Chat Within The Vault

A capability to use: **talk to the content.**

The project lead: **"we should leverage the new capability of having the chat within the vault, so we could talk to this content."** So each vault should expose the chat-within-the-vault capability, letting a visitor or the team converse with the content rather than only read it (cross-ref: the chat-edits-the-vault brief).

## The Agentic Team

The team to set up, talkable on the website: **librarian, architect, ambassador, and a fourth.**

The project lead: **"set up the agentic team, very important. We have the librarian, the architect, the ambassador, and a fourth role that reuses the job description of the main one. You should be able to talk to each of these on the website."** So the website carries a team of agents, the librarian for navigation and cataloguing, the architect for structure, the ambassador for outward-facing explanation, and a fourth role reusing the primary agent's job description, each available to converse with on the site (cross-ref: the agentic-team vault-agents brief). The fourth role's exact name should be confirmed.

## Read-Only And Read-Write Access

The access modes: **read-only first.**

The project lead: **"we should have the read-only access and the read-write access, and first of all, read-only access."** So the vaults launch in read-only mode for safe public exposure, with read-write reserved and added deliberately (cross-ref: the read-only-vaults brief).

## What This Asks For

1. **Give the agent the corpus and infographics** (architect access, the three zips).
2. **Build navigation and capture first** (the corpus is large).
3. **Create multiple ontologies, mapped to audiences** (not one taxonomy).
4. **Create the master vault** (admin, links, description).
5. **Create public, investor, customer, and topic vaults** (interconnected).
6. **Expose chat within each vault** (talk to the content).
7. **Set up the agentic team** (librarian, architect, ambassador, and the fourth, talkable on the site).
8. **Launch read-only first** (read-write added deliberately).

Estimated effort: moderate; the structure and ontologies are the work; the vault, chat, and agent capabilities already exist.

## What This Does Not Try To Be

- **Not one flat vault.** It is many interconnecting vaults.
- **Not one taxonomy.** Multiple ontologies, mapped to audiences.
- **Not read-write by default.** Read-only first.
- **Not static.** Chat and the agentic team make it conversational.

## Honest Tensions

**Tension 1: the fourth role is unclear.** The memo names it loosely. Mitigation: confirm the fourth role and its job description before wiring it.

**Tension 2: navigation and ontology are the hard parts.** A large corpus resists clean structure. Mitigation: the librarian and the ontologies are exactly for this; iterate.

**Tension 3: public exposure risk.** Some content is not for public view. Mitigation: read-only first, and only the public-data and topic vaults are exposed.

**Tension 4: keeping vaults in sync.** Many vaults reference the same memos. Mitigation: the master vault is the single index; the others link to it.
