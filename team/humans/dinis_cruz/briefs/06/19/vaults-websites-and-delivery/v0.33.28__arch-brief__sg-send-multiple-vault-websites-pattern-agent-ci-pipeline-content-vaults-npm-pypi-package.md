# Multiple Vault-Powered Websites: The Pattern, And Refactoring It Into A Package

**version** v0.33.28
**date** 19 June 2026
**from** Human (project lead)
**to** Architect, Product, @Dev
**type** Arch brief (in the series)

---

## What This Is

The pattern for creating many vault-powered websites: **with a real need now to spin up multiple websites using vaults, the pattern is an agent-maintained CI pipeline that builds the HTML with a normal set of workflows, plus a set of vaults that hold the content and a bit of the JavaScript; to make adding a new website as small and smooth as possible, refactor the shared machinery out of the SGraph AI codebase into a reusable package, an npm package or a PyPI package, so the only per-site work is the customised bits; it is a variation of the single-file generator because each site is static, and the elegant concept is that it is a static site with a vault where the vault is also static content that can be hosted directly on the site, so the vault needs no separate hosting.** It follows from the multiple-vault and first-pull needs (cross-ref: the v0.33.26 vault-powered-websites brief, the v0.33.28 run-everywhere, need-to-ship, and corpus-vault-architecture briefs). New contributions: **the CI-plus-content-vaults pattern, the refactor-into-a-package move, and the static-vault-on-site concept.**

## The Framing

What this is: **a nice problem to have.**

The project lead: **"here is a nice problem to have. I now have the need to create multiple websites using vaults, and the interesting question is the pattern that can arrive at."** So the demand for many sites is the forcing function for a clean, repeatable pattern.

## The Pattern

The shape: **an agent-maintained pipeline, plus content vaults.**

The project lead: **"the pattern is one where there is a CI pipeline that an agent maintains, which produces the HTML with a normal set of workflows, and then a set of vaults that control the content, and a bit of the JavaScript too, but mainly the content."** So the build machinery and the content are cleanly separated: the agent-maintained CI pipeline owns the HTML and workflows, and the vaults own the content (cross-ref: the need-to-ship CI-pipeline-as-asset point and the agentic-content-website work).

```
agent-maintained CI pipeline  ->  builds HTML (normal workflows)
            +
        content vaults         ->  hold the content (and some JavaScript)
            =
        a vault-powered website
```

## Refactor Into A Package

The move that makes it repeatable: **extract the shared machinery.**

The project lead: **"we need to refactor out from the SGraph AI codebase into a package, an npm package or a PyPI package, so the code required to add a new website is as small and as smooth as possible, so we can focus on the bits that are customised."** So the shared site-building machinery becomes a reusable package, and adding a new website becomes a thin layer of customisation on top, which is what makes many sites cheap to create (cross-ref: the run-everywhere portability and the mini-apps pattern).

## A Variation Of The Single-File Generator

Where it comes from: **each site is static.**

The project lead: **"it is a variation of the single-file generator, because this is a static site."** So the pattern inherits the simplicity of the single-file generator: each site is static, built once, and served without a running backend (cross-ref: the no-databases, serverless constraint).

## The Static-Vault-On-Site Concept

The elegant part: **the vault is static content, hosted on the site.**

The project lead: **"it is an interesting concept, because it is a static site with a vault, but the vault is also static content, and the vault can be hosted directly on there, so the vault does not need to be hosted separately."** So the vault, being static content, can live on the same static site, removing the need for any separate vault hosting and keeping the whole site a single, portable, static artefact (cross-ref: the vault-powered-websites and read-only-vaults briefs).

## What This Asks For

1. **Separate the pipeline from the content** (agent-maintained CI builds HTML; vaults hold content).
2. **Refactor the shared machinery into a package** (npm or PyPI).
3. **Make adding a site a thin customisation layer** (minimal per-site code).
4. **Keep each site static** (the single-file-generator lineage).
5. **Host the vault on the site** (static vault, no separate hosting).
6. **Use it for the multiple sites already needed** (the real pull).

Estimated effort: moderate; the refactor into a package is the main work; the pattern and the static-vault concept are already proven in parts.

## What This Does Not Try To Be

- **Not a bespoke build per site.** It is a package plus customisation.
- **Not a dynamic backend.** Each site is static.
- **Not separate vault hosting.** The vault is static content on the site.
- **Not pipeline-owned content.** The vaults own the content.

## Honest Tensions

**Tension 1: the package boundary.** Deciding what is shared versus customised is the hard call. Mitigation: refactor iteratively, moving the proven shared parts first.

**Tension 2: static simplicity versus dynamic needs.** Some sites may want interactivity. Mitigation: the bit of JavaScript in the vaults covers light interactivity; keep the default static.

**Tension 3: npm or PyPI, or both.** The codebase may span both. Mitigation: pick the one matching the build, and add the other if needed.

**Tension 4: public exposure.** Static vaults on a site are public. Mitigation: only public content goes on public sites; read-only by default.
