## What This Is

The practical, build-it follow-through on the search architecture from yesterday: **how to build semantic search on top of per-file semantic knowledge graphs in concrete terms (the ontology, the schemas, the file structure, the flows, and the maintenance), proven by an MVP that is itself a vault, ideally with no backend at all.** It takes the search-engine architecture and stack (cross-ref: the v0.32.4 search-engine-on-encrypted-vaults and search-engine-serverless-stack briefs) and the per-file semantic graphs (cross-ref: the v0.31.7 per-page-semantic-graphs brief) and asks the practical questions. New contributions (beyond the 5 June search briefs): **the concrete data model, the website as the live use case, CI-pipeline and agent maintenance, the MVP built as a vault for visualisation, and the no-backend aspiration.**

## The Use Case: The Website

A concrete, live target: **the website already holds a body of content, and the plan is to build a semantic knowledge graph for each file, page, and document, then search on top of it.**

The project lead: **"the website is a good example. It contains a bunch of data we have, so we are going to start creating semantic knowledge graphs for each file, each page, each document. The question is how to create semantic knowledge graphs on top of this, and we have the use case, we have the data, we have the files."** So the website is the practical proving ground: real content, real files, a real reason to search them. Each page or document gets a semantic graph (cross-ref: the per-page-semantic-graphs brief), and the MVP builds search over those graphs. Having the data and files already means the work is the modelling and the mechanics, not gathering content.

## The Practical Questions: Ontology, Schemas, File Structure, Flows

The shift this brief makes, and the point of it: **move from architecture to practice, what the ontology, taxonomy, schemas, file structure, and flows actually look like in our tech stack.**

The project lead: **"let's think in practical terms. What would the ontology look like, what would the taxonomy look like, what would the files look like, what would the file structure look like, what would the schemas look like, what are the flows, who reads and writes? Going back to what we talked about yesterday on search, but now in practical terms: what would the schemas look like, how would the components actually work, what does it look like in our tech stack, and how can we build it?"**

| Practical Question | What To Define |
|--------------------|----------------|
| Ontology | The concepts and relationships the graph captures |
| Taxonomy | How content is classified |
| Schemas | The shape of the graph and index files |
| File structure | How the graph and index files are laid out in the vault |
| Flows | How content becomes a graph becomes an index becomes search |
| Who reads and writes | The agent, the CI pipeline, the search client |

So the deliverable of the thinking is the concrete data model: the ontology and taxonomy for the content, the schemas for the graph and index files, the file structure in the vault, and the read and write flows. This is the practical layer the 5 June architecture briefs deliberately left open, and it is what the MVP forces you to make real.

## Maintenance: Ephemeral Compute And The CI Pipeline

The honest practical constraint: **this is a database-driven approach that needs some compute to maintain, very plausibly ephemeral compute run as part of the CI pipeline, updating the indexes as content changes.**

The project lead: **"this is a database-driven approach, so this is one of those where we are going to need some compute, maybe ephemeral compute that maintains this, and maybe that is done as part of the CI pipeline as we go, so we update the indexes. The question is how we maintain, create, and manage it, and who maintains it."**

| Maintenance Option | How It Works |
|--------------------|--------------|
| Ephemeral compute | Spin up, build or update the graph and indexes, tear down (cross-ref: the ephemeral-compute brief) |
| The CI pipeline | Update the indexes as part of the build, as content changes (cross-ref: the publishing-mode brief) |
| The agent at write time | The agent updating a file updates its graph (cross-ref: the serverless-stack brief) |
| Scripts | A couple of scripts to maintain the whole thing |

So maintenance is the crux, and the brief names concrete options: ephemeral compute (cross-ref: the v0.32.4 ephemeral-compute brief), the CI pipeline updating indexes as content changes (cross-ref: the v0.31.12 publishing-mode brief), the agent maintaining a file's graph at write time, or a few maintenance scripts. The open question the project lead keeps returning to is who maintains it, in a way that does not generate constant writes (cross-ref: the v0.32.7 deterministic-value-indexes brief's overwrite-on-change and shared-responsibility model).

## The MVP Is A Vault

How to build it, and a telling instinct: **build the MVP not as a separate tool but as a vault, a proof-of-concept UI that visualises, simulates, and experiments, because that is how we build now.**

The project lead: **"let's build an MVP, a mini tool that allows us to visualise this. Let's create a tool, a proof of concept, a UI that allows us to visualise it. In fact, let's create a vault to visualise this, because that is how we start to build this stuff these days. In fact, it is not even a tool, it is a vault. Let's create a vault that allows us to simulate this and experiment."** So the MVP is a vault: a self-contained proof of concept that visualises the semantic graphs and the search, and lets the team simulate and experiment with the ontology, schemas, and flows. Building the experiment as a vault is itself the dogfooding pattern the corpus keeps using (cross-ref: the v0.31.12 vault-as-platform-of-primitives and v0.31.9 webify-spreadsheets briefs): the thing you build the tool in is the thing you are building.

## The No-Backend Aspiration

The thing the project lead most wants to prove: **can the whole thing be built with no backend, purely on vaults, files, and indexes maintained by the vault and the updating agent, aided by a serverless function to aggregate?**

The project lead: **"the ideal situation, and I would like to see this experiment, especially if we can aid it with a serverless function that aggregates some of it, is can we build all of this without the backend? That would be the coolest thing. Can we build it purely on top of vaults, purely on files and indexes maintained by the vault, giving the agent that makes the updates the responsibility to do that, or running a couple of scripts to maintain it?"**

| With A Backend | The No-Backend Aspiration |
|----------------|----------------------------|
| A server maintains the index | The vault, files, and indexes are the system |
| A service answers queries | A serverless function aggregates; the client searches |
| The backend owns maintenance | The updating agent (or scripts) maintains the indexes |

So the aspiration is to eliminate the backend entirely: the semantic graphs, the indexes, and the search all live as files in vaults, maintained by the agent that updates the content (or by a few scripts), with a serverless function only to aggregate where helpful (cross-ref: the serverless-stack brief's serverless-as-enclave and client-side routes, and the deterministic-value-indexes brief). If it works, the search engine is just vaults and files, which is the coolest version of the design and the one the MVP should try to prove.

## What This Asks For

1. **Build semantic search on per-file semantic graphs, in practice** (the website as the use case; the data and files already exist).
2. **Define the concrete data model** (ontology, taxonomy, schemas, file structure, flows, readers and writers).
3. **Decide the maintenance model** (ephemeral compute, the CI pipeline updating indexes, the agent at write time, or scripts; avoid constant writes).
4. **Build the MVP as a vault** (a proof-of-concept UI that visualises, simulates, and experiments).
5. **Try to build it with no backend** (vaults, files, and agent-maintained indexes, aided by a serverless function to aggregate).
6. **Reuse the 5 June architecture** (the enclaves, the cloud-function stack, the curation graph; do not rebuild them).
7. **Visualise the graphs and the search** (the MVP's main job is to make this visible and explorable).

Estimated effort: moderate and experiment-led; the architecture, the per-file graphs, ephemeral compute, the CI pipeline, and the vault-as-app pattern all exist; the contribution is the concrete data model, the maintenance decision, and the no-backend MVP. The MVP is a vault that builds a semantic graph for each website page, maintains indexes (ideally agent or CI maintained, no backend), and visualises the graphs and search.

## What This Does Not Try To Be

- **Not a re-do of the architecture.** It builds on the 5 June enclaves, stack, and curation graph.
- **Not architecture-only.** It defines the concrete ontology, schemas, file structure, and flows.
- **Not necessarily backend-driven.** The aspiration is no backend; vaults, files, and indexes.
- **Not a separate tool.** The MVP is a vault, built the way we build now.
- **Not constant writes.** Maintenance is on change, by the agent, CI, or scripts.

## Honest Risks

**Risk 1: The no-backend goal may not fully hold.** Some aggregation or compute may be unavoidable. Mitigation: a serverless function to aggregate; ephemeral compute or CI for maintenance; treat no-backend as the target, not a guarantee.

**Risk 2: Ontology and schema design is the hard part.** A poor data model undermines everything. Mitigation: the MVP forces it; iterate on the website's real content; visualise to validate.

**Risk 3: Index maintenance can generate constant writes.** Keeping indexes current is costly. Mitigation: overwrite on change; agent or CI maintenance; the deterministic-value-indexes model (cross-ref: that brief).

**Risk 4: Database-driven thinking can creep back to a server.** It is tempting to add a backend. Mitigation: hold the no-backend line in the MVP; only add a serverless aggregator if needed.

**Risk 5: Visualisation can become the product instead of the proof.** The UI is a means, not the end. Mitigation: the vault MVP is to prove the model and maintenance, not to ship a polished UI yet.
