# Deterministic Value Indexes: Finding Things In An Encrypted Version-Controlled Store

**version** v0.32.7
**date** 7 June 2026
**from** Human (project lead)
**to** Architect, Developer (lead), Security, @Dev
**type** Arch brief

---

## What This Is

A long-standing problem the PKI work brings into focus: **how do you find things in an encrypted, server-less, version-controlled data store, without maintaining large directories?** The proposed answer is a new primitive: **deterministic indexes whose filename is the hash of the value you are looking for (an email, an asset, a name), so that simply requesting the file tells you whether it exists and where it is, while the data behind it stays encrypted.** It builds directly on the public key register (cross-ref: the v0.32.4 PKI-public-key-registry-on-vaults brief) and complements the semantic search engine (cross-ref: the v0.32.4 search-engine-on-encrypted-vaults brief). New contributions: **deterministic indexes derived from the value rather than the key, discovery without decryption, the index as a special version-controlled branch or tree, anchors and shared maintenance, and the convention-on-a-vault framing.**

## The Problem: Finding Things In An Encrypted Store

The core challenge, faced many times and now sharpened by the PKI: **SG is fundamentally an encrypted, version-controlled data store with no server side, so how do you find things optimally without maintaining large directories?**

The project lead: **"if we have an encrypted version-controlled data store, which is fundamentally what SG is, how do we find things, and find them optimally? We do not have a server side, and that is part of the point. So how do you allow objects to be found without maintaining large directories, which is what I am trying to avoid?"** So the constraint is real: the store is encrypted and server-less, and the project lead deliberately wants to avoid large directories (which would be slow, leak structure, and need maintenance). The question is how to find a known thing quickly anyway.

## What Already Works: Direct Encrypted-File Access

The foundation this builds on, and it is dogfooded: **directly accessing individual encrypted files works very well, loaded dynamically and cached aggressively, helped by immutable files.**

The project lead: **"what is working quite well is directly accessing the individual encrypted files. We use it on the library website, which is a good example of dogfooding the solution. We load the files dynamically and cache them aggressively, and the fact that we have immutable files works quite well."** So the access pattern is proven: fetch an individual encrypted file by name, dynamically, with aggressive caching of immutable files (cross-ref: the v0.32.4 public-data-in-vaults and search-engine-serverless-stack briefs' direct file access). The missing piece is not access; it is knowing which file to fetch.

## The Missing Piece: Global Indexes

What the PKI exposes: **the register stores and manages data well, but there is no set of global indexes, so you cannot ask whether a given email or mapping is present.**

The project lead: **"the PKI structure gives a nice way to store and manage data, especially with the upstream and downstream ideas and graphs on demand. What we are missing is a set of global indexes. If I have a PKI data registry on a vault, how do I find that a particular email address is there? A particular key is easy, because that is a hash. But all the data is encrypted, so how do you find that?"** So a key is findable because it is itself a hash, but arbitrary values (an email, a mapping) are not, because the data is encrypted. The register needs a way to answer presence and location questions about values, not just keys.

## The Core Idea: Deterministic Indexes From The Value

The proposed primitive, extending the deterministic-branch mechanism: **just as a branch name is deterministic from its hash, create deterministic index files whose name is the hash of the value, so that requesting the file answers whether the value exists and where it is.**

The project lead: **"the same way we have branches and head, and the branch name is deterministic from its hash, I think we could add deterministic indexes in deterministic files you can quickly open. If I know an email address, I could answer: do we have it, and where is it? My idea is, if I calculate a hash of the value, and the hash is the name of the file, then just making a request for that file tells me if the index exists. From that file I get the encrypted index, or the object ID, plus some metadata."**

| Step | What Happens |
|------|--------------|
| Take the value | An email, an asset, a name |
| Hash it | The hash becomes the index filename |
| Request that file | If it exists, the value is present (question A: do we have it?) |
| Read the file | Get the object ID or encrypted index and metadata (question B: where is it?) |

So the index is a file named by the hash of the value. A single request answers do we have it (the file exists or it does not), and the file's contents answer where is it (an object ID or encrypted pointer, probably encrypted because it is JSON, plus metadata). No large directory, no server, just a deterministic file lookup, reusing the proven direct-access pattern.

## The Key Distinction: Derived From The Value, Not The Key

The genuinely new element, stated precisely: **today all deterministic IDs are derived from the key; this introduces deterministic IDs derived from the value the user is looking for, by convention.**

The project lead: **"the unique part I am introducing is creating a set of deterministic IDs based on the value the user has, not based on the key. All our deterministic IDs right now are created from the key. We are saying, let's create some that are not created by the key, they are created by whatever name or value, by convention, of whatever you want to find. The branch does something like this, but the branch still uses the key."**

| Existing Deterministic IDs | The New Value Indexes |
|----------------------------|------------------------|
| Derived from the key | Derived from the value (by convention) |
| Branches and head | Index files named by the hash of a value |
| You need the key to compute them | Anyone with the value can compute the index name |

So the novelty is computing an index name from the value itself (the email, the name) rather than from the key. Anyone who knows the value can compute where its index would be and check for it, which is exactly what makes lookup possible without a directory or a server. The branch mechanism is the closest existing analogue, but branches are still key-derived; these are value-derived.

## Security Preserved: Discovery Is Not Decryption

The safety argument, and it holds: **deriving index names from values does not compromise security, because the data is still encrypted, so finding that something exists does not let you read it.**

The project lead: **"I do not think we compromise our security, because the data will still be encrypted. So even if you could find it, you still get encrypted data back. That is still a good compromise."**

| What The Value Index Reveals | What It Does Not |
|------------------------------|------------------|
| Whether a value is present (existence) | The contents (still encrypted) |
| A pointer or object ID (probably encrypted) | The decrypted data |

So discovery and decryption are cleanly separated: a value index lets someone who knows the value confirm presence and get a pointer, but the data behind it remains encrypted, readable only with the right key (cross-ref: the foundations and public-data briefs). This is the same discovery-without-decryption posture the public-data brief drew: you can deliberately allow finding without allowing reading. There is a privacy nuance (existence itself is a signal), noted in the risks.

## The Index As A Special Version-Controlled Branch

What kind of object this is: **the index is like a special branch, an index to a file, branch, or tree, version-controlled, part of a commit, and overwritten whenever the indexed object changes, but managed separately from the normal tree and branch structure.**

The project lead: **"it is kind of a new concept of branch, a special branch, because it is a version, an index to a file, a branch, or a tree. You start to have specific trees that are version controlled. But this should be managed separately, it falls a little outside the current tree and branch structure, because these are indexes, pointers to specific places in the tree. This needs to be part of a commit, the index needs to be version controlled as much as everything else, so the logic is that this file is overwritten every time the index or the object changes, maybe linked to a particular object."**

| Property | The Value Index |
|----------|-----------------|
| Nature | A pointer to a file, branch, or tree (a special branch) |
| Version control | Yes; part of a commit, like everything else |
| Update rule | Overwritten when the indexed object changes |
| Management | Separate from the normal tree and branch structure |
| Linkage | Possibly linked to a particular object |

So the index is version-controlled (it commits and travels with the data, so it is never out of sync), but it is managed as a distinct layer of pointers rather than mixed into the normal tree and branch structure. It is overwritten when its object changes, which keeps it current and bounds the writes to actual changes.

## Anchors, Integrity, And Who Maintains Them

The shape of the real use, and the maintenance question: **for the PKI there are four or five anchors (email, GitHub, name) you want to look up, plus custom indexes, and the open question is who maintains them without causing constant writes, helped by graph logic and integrity.**

The project lead: **"the core concept is that with this encrypted data store, in the PKI example, we have a series of four or five anchors we want to know if we have: email, GitHub, name. And maybe indexes we create on top. How does that work, and who maintains it, so we do not end up with massive writes all the time? Because this is graph logic, it can be verified, you can have integrity flying around, and we can put some of this responsibility on the user of it."**

| Anchor | Lookup |
|--------|--------|
| Email | Is this email present, and where? |
| GitHub | Is this GitHub identity present? |
| Name | Is this name present? |
| Custom indexes | Whatever the user defines |

So the PKI has a handful of anchor types (the identity anchors; cross-ref: the v0.32.3 NHI-2.0-living-off-the-land brief) plus user-defined indexes, and because this is graph logic (cross-ref: the semantic-knowledge-graphs and PKI-registry briefs) the indexes can carry integrity and be verified, and some of the maintenance can be pushed onto the user of the data. The design challenge the project lead flags is maintaining the indexes as trees change without generating constant writes, which the overwrite-on-change rule and shared responsibility are meant to address.

## A Convention On A Vault, Maybe Not At The sgit Level

A scoping question worth keeping open: **this may not need to live at the sgit level; it could be a convention built on top of a vault, or a specific type of vault.**

The project lead: **"the interesting question is, do we even need to do this on top of sgit? This could just be a convention built on top of a vault, or a specific type of vault."** So the value-index primitive might be a convention layered on the vault rather than a change to sgit's core tree and branch model. That keeps the core simple and lets indexes be an opt-in capability of certain vaults (such as a PKI register vault), consistent with the clues-not-storage and platform-of-primitives framing (cross-ref: the PKI-registry and platform-of-primitives briefs).

## Relationship To The Search Engine

How this differs from the search work (cross-ref: the search-engine briefs): **the search engine is for semantic, fuzzy search over content; value indexes are for exact existence-and-location lookup of known anchors, and the two are complementary.**

| Value Indexes (This Brief) | The Search Engine |
|----------------------------|-------------------|
| Exact: do we have this email, and where? | Semantic and fuzzy: what is relevant to this? |
| A deterministic file named by the value's hash | An index built in a secure enclave from a curation graph |
| No compute; a single direct request | Compute in enclaves; a curation graph |
| Discovery without decryption | Search over decrypted, curated content |

So value indexes answer a precise question (presence and location of a known value) with a single cheap request and no compute, while the search engine answers open, semantic questions over curated content. The register can use both: deterministic value indexes for anchor lookups, and the search engine for richer queries.

## What This Asks For

1. **Introduce value-derived deterministic indexes** (filename is the hash of the value; request it to learn existence and location).
2. **Keep them distinct from key-derived IDs** (the new element: IDs from the value, by convention, not from the key).
3. **Preserve security** (discovery is not decryption; the data behind the index stays encrypted).
4. **Make indexes version-controlled but separate** (part of a commit; overwritten on change; managed apart from the normal tree and branch structure).
5. **Support the PKI anchors and custom indexes** (email, GitHub, name, plus user-defined; graph logic and integrity).
6. **Solve maintenance without massive writes** (overwrite on change; push some responsibility to the user; verify via the graph).
7. **Consider a convention on a vault, not sgit core** (an opt-in capability of certain vault types).
8. **Use alongside the search engine** (exact anchor lookup plus semantic search).

Estimated effort: moderate; the direct-access pattern, deterministic branches, and version control exist; the contribution is the value-derived index convention and its maintenance model. The MVP is a PKI register vault where requesting the hash of an email returns whether it is present and an encrypted pointer to where, version-controlled and overwritten on change.

## What This Does Not Try To Be

- **Not a large directory.** A deterministic file per value; no directory to maintain or scan.
- **Not server-side.** A single direct request to a hash-named file.
- **Not key-derived.** The index name comes from the value, by convention.
- **Not a security compromise.** Discovery without decryption; the data stays encrypted.
- **Not mixed into the core tree.** Managed as a separate layer of pointers; possibly a vault convention.
- **Not the semantic search engine.** Exact existence-and-location lookup; complementary to search.

## Honest Risks

**Risk 1: Existence itself is a signal.** Confirming a value is present leaks that fact to anyone who can guess the value. Mitigation: the data stays encrypted; consider salting or scoping index names; treat presence as a deliberate, bounded disclosure (cross-ref: the public-data brief).

**Risk 2: Maintenance as trees change.** Keeping indexes current without constant writes is hard. Mitigation: overwrite on change only; link to the object; push some responsibility to the user; verify via the graph.

**Risk 3: Guessable values enable enumeration.** Hash-named indexes can be probed. Mitigation: salting or keyed hashing where needed; rate and scope the lookup; accept that some anchors are meant to be discoverable.

**Risk 4: A separate index layer adds complexity.** Another versioned structure to manage. Mitigation: keep it a thin convention on the vault; overwrite-on-change; clear separation from the core tree.

**Risk 5: Scope of what becomes an anchor.** Too many anchors means too many indexes. Mitigation: start with the four or five PKI anchors; add custom indexes deliberately.
