# The Vault Inbox: A Public-Key-Controlled Mailbox In The CLI, The UI, And The App

**version** v0.32.7
**date** 7 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, SG API team, Vault team, @Dev
**type** Dev brief

---

## What This Is

A core feature for vaults: **add the concept of an inbox to the SG CLI, the vault UI, and the vault app, where the inbox is controlled by the public keys a vault has accepted to receive from, sits outside traditional version control by design, and appears as a main section the user checks regularly.** It is the receiving side of the vault-to-vault communication work and a concrete step toward Email-FS-lite (cross-ref: the v0.31.12 vault-to-vault-comms-append-token-pki, three-agent-comms-demo, and FAQ-protocol-harness-or-workflow briefs). New contributions: **the inbox as a first-class vault feature across CLI, UI, and app, the public-key-controlled receive model, the inbox as a main UI section checked on refresh, vault-app methods with permission mapping to read the inbox, and the cross-team handoff from the SG API team to the vault team.**

## The Inbox Is Outside Traditional Version Control, By Design

The first thing to understand, and it shapes the design: **the inbox introduces something that sits outside the normal version-control model by design, so it has to be managed a little differently.**

The project lead: **"we need to add the concept of inbox to the SG CLI, because the inbox introduces an interesting variable that you need to manage a bit better: it introduces something that is, by design, outside the normal traditional version control. So we need to add support for the CLI to get it, and support in the vault UI to do it."** So unlike the vault's content, which lives in the version-controlled tree, the inbox is inbound messages that arrive independently of commits. It is a distinct layer to manage, much like the value indexes that are also kept outside the core tree (cross-ref: the v0.32.7 deterministic-value-indexes brief). The CLI and the UI both need to understand and surface it.

## Public-Key-Controlled Inboxes

The model, and why it is better than what is used today: **a vault controls which public keys it accepts messages from, with a public key per agent working on the vault, and that is how the vault knows which messages exist.**

The project lead: **"at the moment in one of the vaults we use the mailbox as a way to send messages, but I reckon this will be better, because the inboxes are managed by the public key that the vault has accepted to receive. Each vault can control which public keys it receives from, and the public key, in our example, could be a public key per agent working on the vault. That is how we know which messages exist."**

| Today (Mailbox As Send) | The Inbox (Public-Key-Controlled) |
|-------------------------|------------------------------------|
| The mailbox is used to send | The inbox is for accepted inbound messages |
| Less control over who sends | The vault accepts specific public keys |
| No per-agent identity | A public key per agent working on the vault |
| Hard to know what is there | The accepted keys define which messages exist |

So the inbox is gated by accepted public keys (cross-ref: the v0.32.4 PKI-public-key-registry and v0.32.3 NHI-2.0-trust-and-identity briefs): a vault decides which public keys it will receive from, and messages are organised by the sending key, which can be a key per agent. This is a better model than using the mailbox to send, because it gives the vault control over what it receives and a clear identity for each sender.

## Email-FS-Lite

The shape this points to: **this is an interesting way to explore the Email-FS-lite idea.**

The project lead: **"it is quite an interesting way to explore, like the Email-FS-lite."** So the inbox is a step toward Email-FS-lite (cross-ref: the FAQ-protocol-harness-or-workflow brief, which used Email-FS-lite as a case study): a lightweight, file-and-vault-based messaging model where messages arrive into a vault's inbox, gated by accepted keys, rather than through a conventional mail server. The inbox feature is the concrete primitive that makes Email-FS-lite real.

## The Inbox As A Main UI Section

The UI requirement, and it is prominent: **the inbox should be a main section in the vault UI, checked regularly like a refresh, showing how many messages there are and which key they are from, along with the configuration.**

The project lead: **"this is a main section on the left. The same way we have the other main sections, we should also have the inbox, and it is something we should check regularly, the same way we do a refresh: just check the inbox and show the user how many messages are there, and which key. And the configuration, we should check the configuration."**

| UI Element | Behaviour |
|------------|-----------|
| A main left-hand section | The inbox is first-class, alongside the other sections |
| Checked on refresh | Regularly polled, like the existing refresh |
| Message count | Show how many messages are waiting |
| Which key | Show which accepted key each message is from |
| Configuration | Surface and check the inbox configuration (accepted keys) |

So the inbox is not a buried feature; it is a main section the UI checks regularly (on the same refresh cadence as the rest), showing the message count, the sending key, and the configuration of accepted keys. The user sees at a glance what has arrived and from whom.

## The Vault App Needs Inbox Access, With Permission Mapping

A key capability, so messaging can be built inside the app: **the vault app needs methods to access the inbox, governed by the permission mapping, so a mailbox structure can be built from inside the app.**

The project lead: **"we need to add methods so the vault app can access the inbox. Add the permission mapping, so we control the permissions of it, but the vault app should be able to access it, because we need to build a mailbox kind of structure from inside the vault app. If I am inside the vault app, I should be able to not just read and write the vault contents, but also read its inbox."**

| The Vault App Can | Governed By |
|-------------------|-------------|
| Read and write the vault contents | The existing permissions |
| Read the inbox | The permission mapping (cross-ref: the permission-granularity brief) |
| Build a mailbox structure inside the app | The inbox access methods |

So the vault app gets methods to read the inbox, gated by the permission mapping (cross-ref: the v0.32.3 NHI-2.0-permission-granularity brief), exactly as content access is. This lets a mailbox-style structure be built inside the vault app itself: an app running in a vault can read that vault's contents and its inbox, which is where the messaging logic and functionality belong.

## The Cross-Team Handoff

How to get it right, organisationally: **the SG API team needs to brief the vault team on the best way to implement the inbox.**

The project lead: **"we need a brief from the team that is creating the inbox: the SG Send and SG API team needs to brief the vault team on the best way to do this, and then you have the UI built."** So this is a coordinated build: the SG API team, who own the inbox mechanism on the API side, brief the vault team on the best way to consume it, and the vault team builds the CLI support, the UI section, and the app methods. The brief between teams is an explicit, named step.

## Processing The Inbox

How the inbox is serviced connects to existing work: **regularly processing a vault's inbox is exactly the ephemeral-compute-on-vaults use case already identified.**

The ephemeral-compute brief named inbox processing as a primary example (cross-ref: the v0.32.4 ephemeral-compute-actions-on-vaults brief: how do we regularly get a vault to process its inbox?). So the inbox feature and the ephemeral-compute task registry fit together: the inbox is the receiving structure, gated by accepted keys and surfaced in the UI and app, and an ephemeral, scoped task can be registered to process a vault's inbox regularly. The UI refresh checks the inbox for the user; the ephemeral compute can process it for the vault.

## What This Asks For

1. **Add the inbox to the SG CLI** (the CLI can get and manage the inbox).
2. **Treat the inbox as outside version control** (a distinct layer, managed separately from the commit tree).
3. **Control the inbox by accepted public keys** (the vault accepts specific keys; a key per agent; messages organised by sending key).
4. **Build toward Email-FS-lite** (the inbox is the primitive that makes it real).
5. **Make the inbox a main UI section** (left-hand, checked on refresh, showing message count, sending key, and configuration).
6. **Add vault-app inbox methods with permission mapping** (read the inbox from inside the app; build a mailbox structure there).
7. **Run the cross-team brief** (the SG API team briefs the vault team on the best implementation).
8. **Connect to inbox processing** (an ephemeral, scoped task can process a vault's inbox regularly; cross-ref: the ephemeral-compute brief).

Estimated effort: moderate; the vault-to-vault comms, the PKI keys, the permission mapping, and the ephemeral-compute pattern exist; the contribution is the inbox layer across CLI, UI, and app, and the public-key-controlled receive model. The MVP is a vault with an inbox section in the UI, gated by accepted public keys, checked on refresh, with the vault app able to read it under the permission mapping.

## What This Does Not Try To Be

- **Not part of the commit tree.** The inbox is outside version control by design, managed separately.
- **Not the mailbox-as-send model.** A public-key-controlled inbox for accepted inbound messages.
- **Not open to anyone.** The vault accepts specific public keys; messages are organised by sending key.
- **Not a buried feature.** A main UI section, checked on refresh.
- **Not app-inaccessible.** The vault app reads the inbox under the permission mapping.

## Honest Risks

**Risk 1: The inbox sits outside version control.** It needs its own consistency and management. Mitigation: manage it as a distinct layer (like the value indexes); clear handling in the CLI and UI; the SG API team's brief.

**Risk 2: Accepted-key management adds configuration.** Each vault must manage which keys it accepts. Mitigation: surface the configuration in the UI; a key per agent; reuse the PKI register and trust model.

**Risk 3: App access to the inbox widens the permission surface.** The app reading the inbox is new access. Mitigation: govern it by the permission mapping, exactly as content access is.

**Risk 4: Cross-team dependency.** The vault team depends on the SG API team's brief. Mitigation: the brief is a named, explicit step; agree the interface early.

**Risk 5: Polling on refresh has a cost.** Checking the inbox regularly adds load. Mitigation: align with the existing refresh cadence; ephemeral compute for heavier processing.
