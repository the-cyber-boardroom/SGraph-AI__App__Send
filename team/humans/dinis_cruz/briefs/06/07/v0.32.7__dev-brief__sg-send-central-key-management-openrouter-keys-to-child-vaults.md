# Central Key Management: Distributing OpenRouter Keys To Child Vaults For In-Vault LLM Capabilities

**version** v0.32.7
**date** 7 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, @Dev
**type** Dev brief

---

## What This Is

A workflow demo, now that the inbox over vault-to-vault comms is nearly working: **a parent vault manages keys centrally and distributes a shared OpenRouter key to each of its child vaults, so a child vault can use LLM capabilities (create an infographic, hold a chat) and return the result by message back to the parent.** The use case in mind is a provider distributing capability to the people it serves, rendered here neutrally as a parent-and-child-vault relationship. It depends on the inbox and vault-to-vault comms milestone (cross-ref: the v0.32.7 vault-inbox brief and the vault-to-vault-comms reference guide in today's pack). New contributions: **central key management with distribution to child vaults, the monitored shared-OpenRouter-key model, per-child billing and credits, and the parent-plus-children MVP.**

## The Context: Inbox-Over-Comms Is Nearly Working, And Vaults Want Chat

The starting point, and it is a milestone: **the inbox over vault-to-vault comms is nearly working, and the next step is letting some vaults hold chat and other LLM-powered capabilities.**

The project lead: **"we are now getting very close to having the inbox working with the vault-to-vault, which is a key requirement, and also a feature where some vaults can have chat situations. When you open a vault, say a parent and a child vault, we want the child to be able to create infographics, chat conversations, different capabilities."** So with the comms and inbox milestone (cross-ref: the vault-to-vault-comms guide in today's pack, and the v0.32.7 vault-inbox brief), vaults can now message; the next capability is in-vault LLM features (infographics, chat). For that, a vault needs access to an LLM, which means a key.

## The Need: A Key To The Vault For LLM Access

The requirement, plainly: **for a vault to use LLM capabilities it needs an OpenRouter key, which has to be given to the vault.**

The project lead: **"for that to work the user needs access to an OpenRouter key. The OpenRouter key needs to be given, so we need a key to the vault."** So enabling in-vault LLM features requires getting an OpenRouter key into the vault. The question this brief answers is how to do that safely and manageably across many vaults, which is a key-distribution and key-management problem (and a provisioning problem; cross-ref: the v0.32.4 ephemeral-compute and accountability briefs).

## The Model: A Monitored, Shared OpenRouter Key

The proposed approach for this stage, with its assumptions stated: **give child vaults a shared OpenRouter key that we monitor, accepting that at this stage we are not controlling where requests go, on the assumption that these users are neither sophisticated nor malicious.**

The project lead: **"a lot of this assumes no abuse, and a lot of the users are not very sophisticated and not potentially malicious. So we can have a shared OpenRouter key that we monitor. At this stage we are not controlling where it goes to, which is important. The coolest thing with OpenRouter is we do not get the data, we just see the usage. So we can share, basically leak to the vault, an OpenRouter key, even send it by email or internal messaging, and monitor usage."**

| Property | This Stage |
|----------|-----------|
| Key type | A shared OpenRouter key, distributed to child vaults |
| Delivery | Given to the vault, even by email or internal messaging |
| Monitoring | We see usage, because OpenRouter exposes usage, not the data |
| Control of destination | Not controlled at this stage (an explicit, accepted limitation) |
| Assumption | Users are non-sophisticated and non-malicious |

So the MVP model is a shared OpenRouter key distributed to child vaults and monitored centrally. A useful property of OpenRouter is that the provider sees usage but not the content of requests, so monitoring usage does not expose the data. The limitations are stated honestly: at this stage the destination of requests is not controlled, and the model leans on an assumption of non-abuse. This is a deliberate, bounded compromise for the MVP, to be tightened later (see risks).

## Trust Levels, Billing, And Credits

How it is managed and paid for: **different vaults can have different trust levels, and billing is separate per child, including a number of credits to use.**

The project lead: **"you can have these as different levels of trust, or different levels of vaults. The billing should be separate, and should include a certain number of credits they can use, and you manage through that."** So keys and access can be graded by trust level per vault, and billing is per child vault, each with an allocation of credits. Credits and per-child billing are the practical control: usage is bounded by credits and attributed per child, which is how the shared-key model is kept manageable even before fine-grained destination control exists.

## The Workflow: Manage Centrally, Distribute To Inner Vaults

The shape of it, and the MVP: **manage keys centrally in the parent vault, distribute a key to each child vault, and have a child create an infographic and return it by message to the parent (the mothership).**

The project lead: **"the idea is a workflow where we manage keys centrally, then distribute keys to the inner vaults. The MVP is the parent vault with a number of child vaults, each child vault receives an OpenRouter key, and the child vault is able to create an infographic and return the infographic by email back to the mothership. That would be a cool workflow."**

| Step | What Happens |
|------|--------------|
| Central management | The parent vault manages the keys |
| Distribution | Each child vault receives an OpenRouter key |
| In-vault capability | A child creates an infographic (or chats) using the key |
| Return | The child returns the infographic by message to the parent |

So the MVP is a parent vault with several child vaults (cross-ref: the vault-in-vault and investor-vaults briefs' vaults-in-vaults): the parent manages and distributes keys, each child uses its key for an LLM capability such as generating an infographic (cross-ref: the infographic generation tooling), and the result is sent back to the parent over the inbox and comms (cross-ref: the vault-inbox brief and the comms guide). It is a clean, end-to-end demonstration of central key management plus in-vault LLM capability plus vault-to-vault return.

## What This Asks For

1. **Build central key management in the parent vault** (manage the OpenRouter keys centrally).
2. **Distribute keys to child vaults** (each child receives a key; delivery can be by message).
3. **Use a monitored shared key for this stage** (we see usage, not data; assume non-abuse; state the limitations).
4. **Grade by trust level and bill per child** (different trust levels; separate billing; credit allocations).
5. **Enable in-vault LLM capabilities** (a child creates an infographic or holds a chat using its key).
6. **Return results over the comms and inbox** (the child sends the infographic back to the parent).
7. **Build the parent-plus-children MVP** (parent manages, children receive keys, a child returns an infographic to the mothership).
8. **Plan to tighten control later** (destination control and scoping beyond the shared-key stage).

Estimated effort: moderate; the comms, inbox, vaults-in-vaults, and infographic tooling exist, and the milestone comms are nearly done; the contribution is central key management and distribution plus the in-vault LLM capability. The MVP is one parent vault with a few child vaults, each given a monitored OpenRouter key with a credit allocation, one child generating an infographic and returning it to the parent.

## What This Does Not Try To Be

- **Not fine-grained key control, yet.** A monitored shared key for this stage; tightening comes later.
- **Not data exposure.** OpenRouter shows usage, not request content.
- **Not unbounded usage.** Per-child billing and credit allocations bound it.
- **Not a clinical or sensitive-domain detail.** The use case is rendered neutrally as parent and child vaults.
- **Not standalone.** It depends on the comms and inbox milestone.

## Honest Risks

**Risk 1: A shared key with uncontrolled destination is a real exposure.** At this stage requests are not destination-controlled, and a shared key can be misused. Mitigation: monitor usage; bound with per-child credits; assume non-abuse only for this MVP; tighten with scoped or per-child keys and destination control later (cross-ref: the v0.32.4 ephemeral-compute and accountability briefs).

**Risk 2: Leaking a key to a vault concentrates trust.** Distributing keys widely spreads exposure. Mitigation: trust levels per vault; credit limits; monitoring; revoke and rotate.

**Risk 3: The non-abuse assumption may not hold.** Some users may be sophisticated or malicious. Mitigation: treat this as an MVP-stage assumption; monitor; cap with credits; move to scoped keys.

**Risk 4: Billing and credit tracking must be accurate.** Per-child billing depends on attribution. Mitigation: OpenRouter usage per key; per-child allocation; reconcile.

**Risk 5: Key delivery by message is itself sensitive.** Sending a key by email or messaging has risk. Mitigation: use the confidential vault-to-vault comms; rotate; scope.
