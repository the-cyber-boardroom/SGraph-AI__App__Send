# The 2FA Digital-Twins Demo: Bottom Up, Twins as Actors

**date** 26 June 2026
**from** Human (project lead)
**to** Architect, @Dev, Product, Strategy
**type** Arch brief

## What This Is

The approach to building the two-factor-authentication scenario as a digital-twins demo, bottom up: **start from the digital twin and build the organisation first, with fractal twins that stack from the bottom and carry natural abstraction layers mirroring the handovers between real systems, developing the core technology on top of the use case so it both builds the product and explains it; the organisation, the HR system, the people, the roles, the actors, is created and stored with IssueFS, where each folder holds a set of issues and each issue holds a definition, giving a graph visualisation stored as files that an agent can manage directly through the CLI without running JSON all the time; once the organisation exists as twins, the risk movement runs through the twins, and the key concept is that every action that updates the graph, including accepting a risk, is performed by a twin, so the acceptor is the twin acting as the CEO or the CFO, connected either to a human or to an agent acting on that human's behalf, with the agent creating the actions, documenting its reasoning and why it chose one option over another, and carrying a persona; and because the graph is ultimately a set of changes, there is a pipeline for changes, which are fundamentally graph transformations, IssueFS transformations and actions.** It is the companion demo to the digital-twin model (cross-ref: the v0.33.35 digital-twins, risk-register, and learning-from-games briefs). New contributions: **the bottom-up fractal build, twins as actors connected to humans or agents, and the change pipeline.**

## The Framing

This is the memo on doing the digital-twins demo on the two-factor-authentication angle, and given the recent twin work, the interesting move is to approach it from a particular direction. The project lead: **"approach this from the angle of starting bottom up, from the point of view of the digital twin."** Rather than starting from the risk and reaching down, the demo starts from the twins and builds up.

## Bottom Up and Fractal

The twins are not flat; they nest. The project lead: **"we have digital twins that are fractal and can go from the bottom up, little twins, digital twins of digital twins, with natural abstraction layers, where in reality there are handovers or movements between two different systems."** So the abstraction layers in the model are not arbitrary; they correspond to the real boundaries between systems, the points where, in the real organisation, one system hands over to another. The demo is designed along those seams.

## Build the Technology on the Use Case

The use case is not just an illustration; it is the scaffold for the build. The project lead: **"develop the core pieces of technology on top of these use cases, which are both a good way to build the technology and a good way to explain how it works."** The 2FA case earns its place here because it is concrete and already rich: the vulnerability exists, it was accepted by the wrong person, and the consequences fan out, so building it exercises the technology and demonstrates it at the same time.

## Build the Organisation First, with IssueFS

The first thing built is the company, not the risk. You create the HR system, the people, the roles, the multiple actors, the organisation itself, and you store all of it with IssueFS. The project lead: **"each folder contains a set of issues, each issue contains a definition, so we have a graph visualisation, and that is what the data is stored on."** IssueFS keeps the graph as folders and files, with each issue a file that holds its information, which fits the vault's no-database model exactly. And it is operable by an agent. The project lead: **"the agent that manages this can use IssueFS directly through the CLI, you do not need it running JSON all the time."** So the managing agent works through the IssueFS command line rather than constantly parsing structured payloads.

## Risk Movement Occurs Via the Twins

This is the principle that falls out of building the organisation first. The project lead: **"we build the organisation first, and the risk movement should then occur via the digital twins."** Once the company exists as a graph of twins, the solution is implemented on top of it, and every risk that moves, every acceptance, every propagation, travels through the twins rather than around them.

## The Key Concept: Every Action Is Performed by a Twin

This is the centre of the brief. Setting aside creation and maintenance, which especially early on will involve a lot of manual assembly, the question of who and what updates the graph, and what actions occur, has a single answer. The project lead: **"who and what and how the graph is being updated, and what actions happen, they should all be done by the little twins, including the entity that is accepting the risk."** The actors in the system are themselves twins.

## Twins as Actors, Connected to Humans or Agents

This resolves a question the earlier work left open: when a risk is accepted, who accepts it? The project lead: **"in the beginning we will not have any humans, or the humans will be connected to a digital twin, so if a risk has been accepted, it has been accepted by the digital twin that is acting like the CEO, or the CFO, and we connect that twin either to a human or to an agent that acts on behalf of that human."** So the CEO in the demo is a twin playing the CEO, and that twin is bound either to a real person or to an agent standing in for them. The same slot accepts a human or an agent without changing the model.

## The Agent Creates the Actions

When the actor is an agent, it does real work in the simulation. The project lead: **"the agent is the one creating the actions, and we get the agent to document its reasoning, why it chose one option over another, and we can give a persona to that agent."** The agent does not just tick a box; it records why it accepted a risk, why it chose one path over another, and it does so in the voice of a persona, which makes the simulation both believable and auditable.

## The Graph Is a Set of Changes: The Change Pipeline

Underneath all of this is a simple truth about the data. The project lead: **"the graph is ultimately made of a set of changes, so we need a pipeline for changes to be made, and the changes are fundamentally graph transformations, IssueFS transformations and actions."** So the system needs a defined workflow through which changes flow, and each change is a transformation of the graph expressed as an IssueFS action. The history of the graph is the sequence of these transformations, which is also what the narrative engine from the register replays.

## Why This Matters

This memo turns the digital-twin idea into something buildable. It says: build the organisation first as a graph of twins in IssueFS; run every risk movement through those twins; make the actors twins that bind to a human or an agent; have the agents create and document the actions in persona; and route every change through a pipeline of graph transformations. That is at once the demo and the core technology, which is exactly the efficiency the project lead is after.

## A Possible Separate Document

One thread here may deserve its own brief: the risk-creation and maintainability view, who can impact the system, and which changes are made automatically versus by hand. That is a distinct concern from the action view above, and it can be expanded separately when the time comes.

## What This Does Not Try To Be

- **Not top down.** It starts from the twins and builds the organisation up.
- **Not database-backed.** The organisation lives in IssueFS, as folders and files.
- **Not human-only or agent-only.** A twin actor binds to either, interchangeably.
- **Not a literal step-by-step walkthrough.** It is the architecture for the demo, on which a walkthrough can be built.

## Honest Tensions

**Tension 1: agents acting as executives.** Letting an agent accept risk in persona is powerful and sensitive. Mitigation: the agent documents its reasoning, and the twin records whether it is backed by a human or an agent.

**Tension 2: manual assembly early on.** The first organisations will be built largely by hand. Mitigation: accept this for the creation phase; the action phase is what runs through twins.

**Tension 3: IssueFS as the store.** Leaning on IssueFS ties the demo to that mechanism. Mitigation: it fits the vault's folders-and-files, no-database model, and is operable from the CLI.

## Acceptance Criteria

1. The organisation is built first as a graph of twins: HR system, people, roles, actors, company.
2. The graph is stored in IssueFS, as folders of issues, each issue a file with a definition.
3. A managing agent can operate IssueFS through the CLI, without constant JSON.
4. Twins are fractal, with abstraction layers aligned to real system boundaries.
5. Risk movement runs through the twins, not around them.
6. Every graph-updating action, including risk acceptance, is performed by a twin.
7. A twin actor binds to either a human or an agent acting on the human's behalf.
8. Agent actors create actions and document their reasoning, choices, and persona.
9. Changes flow through a pipeline and are expressed as IssueFS graph transformations.
10. The change history can be replayed as the register's narrative.
