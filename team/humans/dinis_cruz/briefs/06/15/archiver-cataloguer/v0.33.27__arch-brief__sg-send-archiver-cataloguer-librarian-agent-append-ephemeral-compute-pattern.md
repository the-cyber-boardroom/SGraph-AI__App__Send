## What This Is

A frequently-requested generic pattern, the archiver and cataloguer, a librarian agent mode: **an authorised entity appends a file to a vault using the append-public-key capability, a debounced trigger spins up an ephemeral compute that is given the vault key, an agent reads and processes the appended data (cataloguing it, copying files, appending information, acting on it), places the result back in a vault, and then the ephemeral compute disappears, with the option to chain two or three vaults in sequence so a middle vault only processes and catalogues for the next, which isolates the cataloguer from the destination data and protects against prompt injection while enabling multiple recipients.** It is built almost entirely from established primitives (cross-ref: the v0.33.2 vault-append-capability brief, the v0.32.4 ephemeral-compute and pki-public-key-registry briefs, and the v0.33.26 linkedin-agentic-team brief for the librarian agent). This is Part One, the generic workflow; Part Two covers the specific use cases (cross-ref: the v0.33.27 archiver-cataloguer-use-cases brief). New contributions: **the archiver-cataloguer pattern, the two-key-plus-authorised-keys gating, the debounced ephemeral-compute processing, and the multi-vault chaining for prompt-injection protection.**

## The Concept: A Librarian Agent

What it is, in the project lead's words: **an archiver and cataloguer that combines the existing workflows with the librarian agent.**

The project lead: **"the idea is a workflow of an archiver and a cataloguer, an interesting combination of my workflows plus the librarian, almost a librarian agent mode. You drop a folder, a zip, an image, something, and it gets added to a vault using our append-public-key capability, and then we trigger a process."** So a user or agent drops content, it is appended to a vault, and a process catalogues and files it, the way a librarian would.

## The Primitives: Two Public Keys And Authorised Keys

The cryptographic primitives, all already in place: **the vault's public key encrypts, the sender's public key signs and authorises, and only authorised keys may submit.**

The project lead: **"an entity needs to add a file to a vault. This is the typical example of sending data from one vault or website to another by having two public keys: the public key of the vault, which we use to encrypt the data so only that vault can read it, and the public key of the sender, which we use to sign and if needed encrypt the data, and to be pre-approved. In principle you should be pre-approved to upload to the vault, so not anybody can submit, only entities the vault has approved by accepting their public key into what we call the authorised keys."**

| Key | Role |
|-----|------|
| The vault public key | Encrypts the data, so only the destination vault can read it |
| The sender public key | Signs (and optionally encrypts) the data, and identifies the sender |
| Authorised keys | The vault's allow-list of pre-approved sender public keys; only these may submit |

This is the key-gated supply-chain pattern applied to ingestion: submission is gated by the vault accepting the sender's public key, not open to anyone (cross-ref: the pki-public-key-registry and access-not-security briefs).

## The Workflow

The pattern itself: **append, debounce, spin up an ephemeral compute, process and catalogue, place back, disappear.**

The project lead: **"an entity, which could be a user, an agent, a drag and drop, an API call, or a log, adds a file to a vault. Then at regular intervals, or triggered from that with a debounce so we do not get multiple invocations from multiple uploads, we start an ephemeral compute instance, which is given the vault key. That ephemeral compute reads the messages, and this is where an agent processes them, and depending on the data it catalogues them, copies the files over, appends information, and acts on the data. Then the result is placed back in a vault, the ephemeral compute ends, and it all disappears. That is the workflow and the pattern."**

```
  Entity (user / agent / drag-drop / API / log)
        |  appends a file (vault PK encrypts; sender PK signs; authorised-keys gated)
        v
  Vault (append-only inbox)
        |  debounced trigger (interval or on-append, debounced)
        v
  Ephemeral compute (given the vault or comms key)
        |  agent reads, catalogues, copies, appends, acts (rules per use case)
        v
  Result placed back in a vault
        |
        v
  Ephemeral compute ends -> everything disappears
```

This is a LETS pipeline (Load the appended data, Extract, Transform and catalogue, Save to a vault) running in ephemeral compute (cross-ref: the artefact-driven-security-assessments brief for LETS, and the ephemeral-compute brief).

## Why The Vault Makes This Powerful

The reason to do it on vaults: **version control, provenance, explainability, and detection.**

The project lead: **"this is where it gets interesting, because the vaults provide version control, provenance, explainability, and a way to detect stuff."** Every catalogued item carries its history and provenance, which makes the archive auditable and the processing explainable, rather than an opaque dump (cross-ref: the artefact-driven-security-assessments brief).

## Semantic Graphs For Prompt-Injection Protection

An implementation lean the project lead flags: **process in terms of semantic graphs to defend against prompt injection.**

The project lead: **"I would argue this should all be done in terms of semantic graphs, because you want to prevent against prompt injections, but that is more of an implementation workflow."** Since the ingested data is untrusted and an agent processes it, prompt injection is a real risk; structuring the processing around semantic graphs is the project lead's preferred defence, alongside the chaining below (cross-ref: the nhi-2.0-semantic-knowledge-graphs and agentic-content-website briefs).

## The Multi-Vault Chaining

The structural protection, and the most interesting part: **chain vaults so the cataloguer only processes and never holds the destination data, enabling multiple recipients.**

The project lead: **"we can have two or three of these in sequence, where the vault in the middle is only able to process, filter, index, and catalogue it, and put it for the next vault. This adds a lot of protections against prompt injection, because the cataloguing server does not have access to all the data, it is just processing it, and only the receiving vault actually processes it. Which means we could have multiple recipients, so you do not have one big uber-vault, you can have multiple ones."**

```
  Source vault  ->  Cataloguing vault (process / filter / index only)  ->  Destination vault(s)
                     (no access to the full data; just transforms)         (the real processing)
```

| Benefit | How |
|---------|-----|
| Prompt-injection protection | The cataloguer is isolated; it does not hold the destination data |
| Least privilege | The middle vault only transforms; it cannot read everything |
| Multiple recipients | No single uber-vault; routing to many destination vaults |

This is the vault-in-vault and blast-radius thinking applied to ingestion: the cataloguing stage is a sandbox that cannot become a single point of compromise (cross-ref: the vault-in-vault-kernel-model and content-transformation-proxy briefs).

## What This Asks For

1. **Build the archiver-cataloguer workflow** (append, debounce, ephemeral compute, agent processing, place back, disappear).
2. **Gate ingestion with authorised keys** (two-key encrypt-and-sign; only pre-approved senders).
3. **Debounce the trigger** (avoid multiple invocations from multiple uploads).
4. **Process in ephemeral compute with an agent** (catalogue, copy, append, act; rules per use case).
5. **Lean on semantic graphs for prompt-injection defence** (the implementation choice).
6. **Support multi-vault chaining** (a cataloguer isolated from the destination; multiple recipients).
7. **Use the vault's provenance and version control** (auditable, explainable archive).

Estimated effort: low to moderate; the append capability, ephemeral compute, the two-key model, and authorised keys all exist; the work is the cataloguing agent, the debounce, and the chaining.

## What This Does Not Try To Be

- **Not open ingestion.** Only authorised keys may submit.
- **Not a persistent processor.** The ephemeral compute disappears after each run.
- **Not one big uber-vault.** Chaining and multiple recipients are preferred.
- **Not trusting the ingested data.** Semantic graphs and chaining defend against injection.

## Honest Risks

**Risk 1: prompt injection from untrusted ingested data.** Mitigation: semantic-graph processing and the chaining that isolates the cataloguer from the destination data.

**Risk 2: the ephemeral compute holds the vault key.** Mitigation: it is ephemeral and disappears; chaining limits what any one stage can read.

**Risk 3: debounce tuning.** Too tight and uploads are missed; too loose and it runs too often. Mitigation: tune the interval and the debounce per use case.

**Risk 4: authorised-keys management.** The allow-list must be maintained. Mitigation: the authorised-keys mechanism and the registry (cross-ref: the pki-public-key-registry brief).
