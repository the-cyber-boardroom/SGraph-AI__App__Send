## What This Is

Operational and release notes for the Audio Transcribe tool, advancing yesterday's commercialisation workflow into something shippable: **distribute daily OpenRouter keys to test users as SG API secrets with a time-to-live and a usage count, minted from an admin vault, offer a bring-your-own-key-or-early-adopter-key choice in the UI, host the tool on the main website through the vault-powered-websites pattern (the tools site provides the components, a vault embeds them with themes and layouts, and the SGraph site serves it from a path), add a separate observability vault that captures append-mode usage logs, and validate the whole thing against a simple metric, getting users to spend a few dollars.** It resolves the key-sharing question left open yesterday (cross-ref: the v0.33.26 selling-llm-usage brief), applies the vault-powered-websites pattern (cross-ref: the v0.33.26 vault-powered-websites brief), and reuses the append-mode logging from the provider-recipient workflow (cross-ref: the v0.33.2 vault-append-capability brief). New contributions: **the SG-API-secret key distribution, the bring-your-own-or-early-adopter-key choice, the three-component hosting, and the two-vault admin-and-observability split.**

## The Status

Where the tool is: **the first MVP is published, and the work now is the access vault and the website.**

The project lead: **"the audio transcript tool is coming out nicely. I created it, published the first MVP, and now we are iterating the workflows. We are working on creating the vault to access it, and then we need to create the website."** So the tool exists and works; this brief is about wrapping it for distribution and release.

## The Validation Metric

The honest test, operationalised: **can we get users to spend a few dollars.**

The project lead: **"the objective is that if I cannot get users to spend two, three, four, or five dollars on the technology, then it is not there yet."** This is yesterday's will-people-pay question made concrete and measurable: a handful of real dollars of usage is the signal that the tool is wanted (cross-ref: the selling-llm-usage brief's first milestone).

## The Key-Distribution Mechanism

This resolves the open question from yesterday: **distribute the daily OpenRouter keys as SG API secrets with a time-to-live and a usage count, minted as simple tokens from an admin vault.**

The project lead: **"we have a secret to give to our test users, the logic being a daily budget, a daily OpenRouter key. The same way we have vault keys, we should create simple tokens via an admin panel, an admin vault. Let us use the SG API capability to store secrets, which already exists, to manage this. They are secrets that can last a couple of days or hours, and they have a usage count, so we can try it out. That is also a good example of testing that capability."**

| Element | Detail |
|---------|--------|
| The secret | A daily OpenRouter key, distributed as an SG API secret |
| Time-to-live | A couple of hours or days |
| Usage count | A cap on how many times it can be used |
| Minted from | An admin vault and panel (simple tokens, like vault keys) |
| Side benefit | Exercises the SG API secrets capability |

This is exactly the bounded-exposure control flagged yesterday: a short-lived, usage-capped secret bounds the blast radius even though usage is client-side (cross-ref: the selling-llm-usage brief's key-sharing risk, now resolved).

## The UI Choice: Bring Your Own Key, Or An Early-Adopter Key

What the user sees: **a choice between their own key and a shared early-adopter key.**

The project lead: **"you go to the website and get a choice, either bring your own key, or enter an evaluation key, a preview key, or an early-adopter key, which is the one I can share. So I can go to my community and say, here is the key for today, try it out."**

| Option | Who It Is For |
|--------|---------------|
| Bring your own key | Users who already have an OpenRouter key |
| Early-adopter key (shared) | The community; the project lead shares today's key |

The early-adopter key is the SG API secret from above, so sharing today's key with the community is a low-friction way to drive the trial usage the validation metric needs.

## Distribution And Reach

Who gets it: **existing customers, beta users, others, and website visitors with restrictions.**

The project lead: **"we make it super easy, and I reach out to existing customers, which is a different thread, but also other beta users and other people, and even people who hit the website, with some restrictions."** So the reach widens from known contacts to public website visitors, with the secret's time-to-live and usage count as the restriction mechanism.

## The Three Components And The Hosting

The architecture is the vault-powered-websites pattern applied: **the tools site provides the components, a vault embeds them, and the main website serves it from a path.**

The project lead: **"there are three key components. The tool itself, hosted on the tools site, the standalone multi-integration UI we use to develop the components. Then a vault that embeds those components and creates websites, where we can explore multiple designs, layouts, themes, and languages, because the components have a JS API that provides the execution flows. That vault still needs a vault key. Then we provide the read key and the vault ID to the SGraph UI, where an agent controls it, so we can host it from a path like the tools audio-transcriber page on the main site, not just the raw tools list."**

```
  tools.sgraph.ai (raw component dev UI, JS API)
        |  components
        v
  Vault (embeds components; themes, layouts, languages)   <- needs a vault key
        |  read key + vault ID provided to the SGraph UI (agent-controlled)
        v
  sgraph.ai/en-gb/tools/audio-transcriber  (the main website hosts it)
```

| Component | Role |
|-----------|------|
| The tools site | The raw, multi-integration UI where components are developed |
| The vault | Embeds the components; the place to explore themes, layouts, and languages |
| The SGraph website | Serves the polished tool from a path, given the read key and vault ID |

(Cross-ref: the vault-powered-websites brief, which is exactly this pattern.)

## The Release Phase

What releasing means here: **documentation, use cases, and observability, with the website as the place for rich content.**

The project lead: **"the website is the one we can really create and explore, with multiple content that needs descriptions. We now need to go all the way into releasing this, the release phase, where we need documentation, use cases, and observability."** So the release is not just the tool working; it is the documented, described, observable product on the website.

## The Two Vaults: Admin And Observability

A deliberate split: **keep the admin vault and the observability vault separate.**

The project lead: **"there are two vaults here. The vault we use to manage the keys, both the early-access OpenRouter key and the visibility, and the observability vault, where we leverage our logging capability. They should probably be separate. We provide the public key of the observability vault, and the same append-mode approach we use in the provider-recipient workflow, we send logs when somebody opens the page and when somebody does an execution."**

| Vault | Purpose |
|-------|---------|
| Admin vault | Manage the keys (the early-access OpenRouter keys) and visibility |
| Observability vault | Receive append-mode usage logs |

## The Observability Posture

What to capture, and what not to: **capture useful usage stats in append mode, but nothing sensitive.**

The project lead: **"we want good observability. We send logs in append mode, when somebody opens the page, when they do an execution. We do not leak anything sensitive, but we capture who is accessing what, who is viewing what, the workflows, even which country they come from. I am not sure we want the IP address, but we can capture other things, for better control of who is using it and how much. And we say do not put anything confidential there, but it is good to get stats."**

| Capture | Do Not Capture |
|---------|----------------|
| Page opens and executions | Confidential content |
| Who accesses and views what | Sensitive data |
| Workflows used | The IP address (undecided; lean against) |
| Country of origin | Personally identifying details |

The posture is privacy-respecting analytics: append-mode logs to a separate observability vault, useful aggregate stats, no sensitive or confidential data, and the do-not-enter-confidential-data disclaimer (cross-ref: the recipient-vault-experience-improvements disclaimer and the provider-recipient append-mode logging).

## What This Asks For

1. **Distribute keys as SG API secrets** (daily OpenRouter keys with time-to-live and usage count, from an admin vault).
2. **Build the bring-your-own-or-early-adopter-key choice** (the shared early-adopter key is the SG API secret).
3. **Host via the three components** (tools site, embedding vault, served from the main website path).
4. **Do the release phase** (documentation, use cases, descriptions, observability).
5. **Run two separate vaults** (admin for keys, observability for logs).
6. **Add append-mode observability** (page opens and executions; useful stats, nothing sensitive).
7. **Validate against the spend metric** (get users to spend a few dollars).

Estimated effort: moderate; the tool, the SG API secrets, the vault-powered-websites pattern, and the append-mode logging all exist; the work is wiring the key distribution, the hosting path, and the two vaults.

## What This Does Not Try To Be

- **Not server-side.** Usage is client-side; the secret bounds it.
- **Not unrestricted.** The secret's time-to-live and usage count are the restriction.
- **Not a confidential-data tool.** The disclaimer says so.
- **Not capturing PII.** Stats, country, and usage, not sensitive identifiers.

## Honest Risks

**Risk 1: the validation metric might fail.** Users may not spend. Mitigation: that is the point; a few dollars of usage is the honest signal, and failing it tells us the tool is not there yet.

**Risk 2: client-side key exposure.** Mitigation: the SG API secret's time-to-live and usage count bound the exposure (this resolves yesterday's open risk).

**Risk 3: observability privacy.** Capturing usage can stray into PII. Mitigation: append-mode stats only, no sensitive data, lean against the IP address, and the do-not-enter-confidential-data disclaimer.

**Risk 4: two-vault coordination.** Mitigation: keep admin and observability separate with clear roles.
