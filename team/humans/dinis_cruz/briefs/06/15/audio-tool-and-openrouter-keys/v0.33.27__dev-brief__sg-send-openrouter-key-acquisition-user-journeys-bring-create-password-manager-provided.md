## What This Is

The use cases and user stories for getting a valid OpenRouter key into the user's browser, the step that ends when the key is present: **enter your own key, create one with guided agent-generated documentation, retrieve it from a password manager, or use a key we provide (which resolves through SG/Send), plus a couple more, mapped as a semantic graph of options and visualised as user-experience flows.** It expands the bring-your-own-or-given choice from the release brief into the full set of journeys (cross-ref: the v0.33.27 audio-transcript-tool-release brief), uses the semantic-graph framing from the user-finding work (cross-ref: the v0.33.27 finding-early-users brief), and continues the commercialisation thread (cross-ref: the v0.33.26 selling-llm-usage brief). New contributions: **the option graph, the four-plus key-acquisition journeys, and the guided agent-generated create-a-key flow.**

## The Goal

The boundary of this step, stated by the project lead: **everything here ends when the user has an OpenRouter key in their browser.**

The project lead: **"this whole section ends when the user has an OpenRouter key in their browser. Let's map out, again as a semantic graph, the multiple elements, and visualise this in graphs, ASCII art, user mock-ups, and user-experience flows: what are the multiple ways the user can get an OpenRouter key."** So the brief enumerates and visualises the acquisition journeys, each terminating in a key in the browser, and frames the set as a semantic graph of options.

## Use Case 1: Enter Your Own Key

The simplest journey: **the user already has a key and pastes it.**

The project lead: **"the simplest workflow is the user goes to a page that says enter your key, or click here to get one. The first option is enter your key: the user already has an OpenRouter key, copy and paste it, and Bob's your uncle, that is done."** One step: paste the key, and the section is complete.

## Use Case 2: Create An OpenRouter Key (Guided)

For users without a key: **guide them through creating one, with in-UI documentation that is as simple as possible, generated by the agent.**

The project lead: **"the user needs to create an OpenRouter key, so we have the documentation in the UI, as simple as possible. Open guidance on the same page: go to OpenRouter, here is the link, create an account, go to keys, create key, as many links as we can, and screenshots. Then create key, set budget, copy key, put it here. Remember this is all done by our agent, who creates these pages, because the website is rendering the content."**

```
  Explain  ->  Go to OpenRouter (link)  ->  Create account  ->  Keys (link)
       ->  Create key  ->  Set budget  ->  Copy key  ->  Paste here
```

The guidance is agent-generated and rendered as website content (cross-ref: the vault-powered-websites and audio-transcribe-experience briefs, where the agent writes the documentation), with links and screenshots at every step.

## Use Case 3: Retrieve From A Password Manager

For users who keep keys in a manager: **show how to retrieve it, with screenshots per manager.**

The project lead: **"another case is using a password manager, so we add screenshots for specific password managers, LastPass and others, or AWS Secrets, or Google password manager, with multiple examples of how that works."**

## Use Case 4: Use A Key We Provide

The shared-key journey, which the project lead places near the top of the list: **provide a key, on-screen or given, that resolves through SG/Send.**

The project lead: **"one of the first, second, or third on the list should be when we provide a key, either a key on the screen for them to click and copy, or you are given a key that you paste, and what that does is it goes to SG/Send, grabs the SG key from it, and uses it."**

```
  Provided key (on-screen or given)  ->  paste it
       ->  the app resolves it via SG/Send  ->  retrieves the OpenRouter key  ->  in the browser
```

So the provided key is an SG/Send reference, not the raw OpenRouter key: pasting it makes the app fetch from SG/Send and resolve the actual key. This is the early-adopter and shared-key flow, backed by the SG API secret with a time-to-live and usage count (cross-ref: the audio-transcript-tool-release brief, where this is the early-adopter key).

## The Semantic-Graph Framing

Why map it as a graph: **the ways to get a key are elements in a graph, connected to the capability and the user.**

Treating the acquisition journeys as a semantic graph (the options, the managers, the providers, the cohorts) connects them to the capability lens and the user-finding mesh (cross-ref: the finding-early-users brief), so the same graph that describes the tool also describes how a given user is most likely to obtain a key.

## What This Asks For

1. **Build the entry page with the option set** (enter, create, password manager, provided, plus more).
2. **Implement enter-your-own-key** (paste and done).
3. **Build the guided create-a-key flow** (agent-generated docs, links, screenshots, budget step).
4. **Add password-manager guidance** (LastPass, Google, AWS Secrets, others, with screenshots).
5. **Implement the provided-key flow** (resolves through SG/Send to the OpenRouter key).
6. **Add the evaluation-key and buy-credits journeys** (the cohort and purchase variants).
7. **Map it as a semantic graph and visualise the flows** (graphs, ASCII, mock-ups).

Estimated effort: low to moderate; the key handling, SG/Send, and agent-generated docs exist; the work is the entry page, the guided flow, and the per-manager guidance.

## What This Does Not Try To Be

- **Not a single path.** Several journeys to the same end.
- **Not raw provided keys.** Provided keys resolve through SG/Send.
- **Not unguided.** Creating a key is fully walked through.
- **Not the end of the tool.** This step ends when the key is in the browser; the tool takes over from there.

## Honest Risks

**Risk 1: the key is client-side in every journey.** Mitigation: for provided keys, the SG/Send resolution plus the secret's time-to-live and usage count bound the exposure (cross-ref: the release brief).

**Risk 2: password-manager guidance must be accurate per tool.** Mitigation: per-manager screenshots, kept current; agent-generated and reviewed.

**Risk 3: users may paste keys insecurely.** Mitigation: clear guidance; the provided-key path avoids exposing a raw long-lived key.

**Risk 4: too many options can confuse.** Mitigation: lead with the simplest (enter or provided), reveal the rest progressively.
