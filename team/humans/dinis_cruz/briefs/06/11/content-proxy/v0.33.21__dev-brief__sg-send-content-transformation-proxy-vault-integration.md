## What This Is

Part two of the three-part description of the as-built content-transformation proxy: **where the vaults come into play, in three roles, managing the version-controlled injected scripts, capturing the server logs via the append feature into an S3-backed vault that a whole auto-scaling fleet shares, and providing vault apps for testing tools and a user-experience launcher.** Part one covered the architecture and the transformation flow; part three covers the components, the docker-compose, and the scaling. The vault is what makes the solution manageable and distributed. It uses the append capability, the public-data and webify work, and the vault-app model (cross-ref: the v0.33.2 vault-append-capability, v0.32.4 public-data-in-vaults, and v0.31.9 webify-spreadsheets briefs). New contributions: **the script-management vault, the S3-backed distributed logging vault, and the UX-launcher vault app.**

## Why The Vault Is Central

The framing the project lead gives: **the vaults provide a key piece of the puzzle, because they handle the data communication for the whole solution.**

The project lead: **"where do vaults come into play? The vaults are going to provide a very key piece of the puzzle, because they help with the data communication."** So the vault is not an add-on: it is how scripts get to the server, how logs get off the server, and how the user experience is delivered. The three roles below each use the vault for a different kind of data movement.

## Role One: Script Management

The first role, and it ties straight to part one's script-as-formula model: **the vault holds the latest version of the injected scripts, which gives version control and customisation, and the scripts are shipped to the server in a vault.**

The project lead: **"the way we manage the scripts that are injected via the FastAPI service is via a vault. The vault contains the latest version of the scripts, which means we have version control, it can be customisable, and that is the first element. We ship the vault there."** So the transformation scripts (the formulas from part one) live in a vault: versioned, customisable per deployment, and delivered to the server by shipping the vault to it. The FastAPI MITM service injects the latest script from that vault, so updating the filtering is a vault update, not a redeploy (cross-ref: the part-one script-as-formula section and the v0.33.2 release-manifest-templates brief).

```
  Vault (scripts)              EC2 instance
  . version-controlled    -->  . FastAPI MITM service reads the latest script
  . customisable per           . injects it into the page (part one, step 5)
    deployment
  . shipped to the server
```

## Role Two: Logging Into An S3-Backed Distributed Vault

The second role, and the most architecturally interesting: **the server pushes its logs into a vault using the append feature, and because the vault writes to S3, a whole auto-scaling fleet of instances can feed the same vault, which makes it highly distributed and reopenable anywhere.**

The project lead: **"the second mode is you can use vaults to push, using our new append feature, the logs that happen on the server. One of the nicest things is that the vault allows a full ephemeral capability: everything that happens on an EC2 instance stays on that instance or has to be pushed out, and it can be using S3, which means they can all use the same vault. In a weird way the vault is then highly distributed, because they are all feeding from S3. You can have multiple instances in a load-balancer, auto-scaling format, two, five, ten, a hundred, and they all feed from the same vault, because the data comes from S3."**

```
   EC2 #1 --+
   EC2 #2 --+  append logs  -->  Vault (append)  --writes-->  S3 bucket (shared)
   EC2 #N --+  (local write)                                      |
                                          the same S3 files-------+
                                                                  v
                          Open the vault from ANY environment
                          (an analysis box, a laptop, another region)
```

So logging uses the append capability (cross-ref: the v0.33.2 vault-append-capability brief): each instance appends its logs to a vault, the vault persists to S3, and because the backing store is shared S3, the fleet behaves as one distributed vault. The instances stay ephemeral (nothing important stays local; it is pushed out), and the same S3 files can be opened as the vault from a completely different environment for analysis (cross-ref: the v0.32.4 ephemeral-compute and public-data-in-vaults briefs). The project lead: **"the local instance just writes to a vault, but that is actually writing to S3, and we can open that up from a different, even completely different, environment, and you still have the same S3 files."**

## Role Three: Vault Apps For Testing And The UX Launcher

The third role: **vault apps provide capabilities, including the testing tools already in use and a user-experience launcher that lists the supported sites and opens each in an iframe or a VNC viewer.**

The project lead: **"we can use vault apps to provide a bunch of different stuff. We already create testing tools using vault apps, but I really like the idea of user-experience vault apps. You have a web page that contains the icons of the multiple sites we support, and when you click on one it opens in an iframe or a VNC viewer inside the page, so we can create a great experience, because it is fundamentally just a web app."**

A UX-launcher mock-up (ASCII):

```
 +-------------------------------------------------------------+
 |  Supported sites                                  [ ? ] [ * ]|
 +-------------------------------------------------------------+
 |                                                             |
 |   +--------+   +--------+   +--------+   +--------+          |
 |   | [ A ]  |   | [ B ]  |   | [ C ]  |   | [ D ]  |          |
 |   | Site A |   | Site B |   | Site C |   | Site D |          |
 |   +--------+   +--------+   +--------+   +--------+          |
 |                                                             |
 |   click an icon  >  opens in an iframe / VNC viewer below   |
 |  +-------------------------------------------------------+  |
 |  |  (iframe / VNC viewer)                                |  |
 |  |   the transformed page renders here                   |  |
 |  |                                                       |  |
 |  |                                                       |  |
 |  +-------------------------------------------------------+  |
 +-------------------------------------------------------------+
```

So the launcher is itself a vault app (a web app served from a vault; cross-ref: the v0.31.9 webify-spreadsheets and v0.32.7 investor-vaults-curated-experience briefs): a page of supported-site icons, each of which opens the transformed site in an embedded iframe or a streamed VNC viewer (mode two from part one). The same vault-app mechanism also hosts the testing tools, which are already built. This is what turns the solution from a proxy into a product the user simply opens.

## How The Roles Fit Together

| Role | Vault Carries | Direction | Effect |
|------|---------------|-----------|--------|
| Script management | The versioned transformation scripts | Vault to server | Update filtering by updating the vault |
| Logging | The server logs (via append) | Server to vault to S3 | One distributed, reopenable log store for the fleet |
| Vault apps | Testing tools and the UX launcher | Vault to user | The user experience and the test harness |

So the vault is the data-communication backbone of the whole solution: it ships the policy in, carries the logs out to a shared store, and delivers the experience to the user, exactly the key piece of the puzzle the project lead described.
