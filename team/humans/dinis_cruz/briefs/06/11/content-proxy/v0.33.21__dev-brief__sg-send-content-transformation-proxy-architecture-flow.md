## What This Is

Part one of a three-part technical description of a solution that has been built: **a website-transformation-via-content-proxy, where a request passes through mitmproxy, which hands the page to a FastAPI service that decides whether to inject a transformation script, and that script runs client-side to blur or remove content before the user sees the page, so the user sees only what their policy allows.** This part covers the architecture and the request-and-transform flow; part two covers the vault integration; part three covers the components, the docker-compose, and the scaling. The pack documents an as-built solution and is described generically (no specific site or customer). It uses the iframe and browser-automation work (cross-ref: the v0.27.62 vault-in-vault-kernel-model and v0.33.21 vault-update-workflow-qa briefs) and the LLM-builds-the-artefact pattern (cross-ref: the v0.33.16 artefact-driven-security-assessments brief). New contributions: **the content-proxy architecture, the inject-and-transform flow, the script-as-formula model, and the two deployment modes.**

## The Premise

What the solution does, in one line: **transform a web page via a content proxy, changing parts of the page based on criteria, so the user sees only the content their policy allows.**

The project lead: **"the key premise is to create a solution that does website transformation via a proxy of content, where based on the criteria we can change some parts of the page. One use case is content filtering: change the content, blur some stuff on the page based on a particular criteria, so you only see content in clear that you have a particular formula for."** So the solution sits between the user and a website and rewrites the page before the user sees it: content that the policy permits is shown, and content it does not permit is blurred or removed. Content filtering is the lead use case, but the mechanism is general, any criteria-driven transformation of a page.

## The Request-And-Transform Flow

The core mechanism, end to end: **the browser requests through mitmproxy, mitmproxy fetches the origin page and hands it to the FastAPI service, the service decides whether to activate and injects a transformation script, and the script runs client-side to transform the page before render.**

```
  Browser (configured to use the proxy)
        |  (1) request
        v
  mitmproxy  --(2) fetch-->  Origin website
   (on EC2)  <-(3) page------+
        |
        |  (4) hand the page to the MITM service
        v
  FastAPI "MITM service"  (same EC2 instance)
        |   . decide: activate?  (currently via cookie)
        |   . if active: inject the transformation <script>
        |  (5) return page + injected script
        v
  mitmproxy
        |  (6) deliver the transformed page
        v
  Browser
        |  (7) the injected script runs CLIENT-SIDE
        v       blurs / removes content BEFORE the user sees it
  User sees only the content their policy ("formula") allows
```

The project lead: **"the user makes a request, the proxy goes and gets the content, we send the page to the service we call the MITM service, and the service decides, and at the moment we use cookies to decide. When activated it injects a bit of script, the script is rendered on the client, and the logic is that before the user even sees the page we do the transformations. The transformations are done on the client."** So the decision to transform happens server-side in the FastAPI service (currently keyed on a cookie), but the transformation itself happens client-side, in the injected script, before the page is shown. That keeps the proxy light (it injects, it does not rewrite the whole page itself) and puts the transformation where the rendered DOM actually exists.

## The Script Is The Formula

How the transformation is defined and changed: **the injected script contains all the detail and the formula, so updating the filtering means updating the script.**

The project lead: **"the script that is created contains all the details, all the formula, which means that if you want to update the filtering, we update the script."** So the script is the unit of policy: it carries the rules for what to blur or remove on a given page, and changing behaviour is a matter of shipping a new script. This is why the vault matters (part two): the scripts are versioned and managed in a vault and served from there.

## How The Script Is Built, And Where It Is Going

The current and future shape of the transformation logic: **today the script is largely a regex-and-graph structure built with the help of LLMs offline, and the direction of travel is more semantic-graph and more dynamic.**

The project lead: **"we use LLMs to create the script and to help us with the policy, which is a different process. Right now it is more of a graphy, regex kind of structure, where based on the content on the page defined in the script the changes are made. In the future it will be more semantic graphs, more dynamic, but it works quite well."** So the LLM work is offline (building the script and the policy), separate from the request path, which keeps the runtime simple and deterministic: at request time the script just applies its rules. The current rules are regex-and-graph; the planned direction is semantic-graph-driven and more dynamic (cross-ref: the v0.33.16 semantic-graph-visualisation and company-intelligence briefs), but the regex-and-graph approach is working today.

## The Two Deployment Modes

How a user reaches the solution: **mode one configures the user's browser to use the proxy; mode two streams a remote browser to the user via VNC, a browser inside a browser.**

```
MODE 1 - Proxy-configured browser
  [user's browser, proxy set] --> [mitmproxy on EC2] --> ... --> transformed page
  . the user's own browser renders the page
  . more complex to set up (the browser must be configured)
  . needs a Network Load Balancer for direct proxy access (see part three)

MODE 2 - Streamed remote browser (VNC)        [the VNC server is out of scope here]
  [user's browser] --(VNC stream)--> [remote browser in a container] --> [mitmproxy] --> ...
  . a browser inside a browser; nothing runs on the user's machine
  . the remote browser does the proxying and rendering
  . all the user needs is a browser
  . needs an Application Load Balancer (see part three)
```

The project lead on mode one: **"the main way is to access this via a proxy that is configured, so a browser configured to use the proxy. The proxy contacts mitmproxy, which contacts the FastAPI service, which injects the JavaScript, and the client renders the differences."** And on mode two: **"the second mode is when we render something like VNC. We provide a container, the container has the browser, and you browse the website on that browser, a browser in a browser. We stream via VNC. The power is that the browser runs remotely, not on the user's computer, which makes it much easier to deploy, because all you need is a browser to access the solution."** So mode one is the direct proxy (more setup, the user's browser renders) and mode two is the streamed remote browser (nothing on the user's machine, easiest to reach). The two modes drive the load-balancer choice in part three, and mode two is where the vault apps shine (part two). The VNC server itself is out of scope for this pack because it needs a container per user (part three).
