## What This Is

Part three of the three-part description of the as-built content-transformation proxy: **the four components on the EC2 image, the full docker-compose that runs them, the auto-scaling group with the load-balancer choice (a Network Load Balancer for the direct-proxy mode and an Application Load Balancer for the vault and web mode), and the deploy model of spinning up a server and copying the vaults in.** Part one covered the architecture and the transformation flow; part two covered the vault integration. The VNC server is out of scope here because it needs a container per user. It builds on the AWS deployment and ephemeral-compute work (cross-ref: the v0.33.2 aws-deployment-lambda-via-sg-compute-bastion and v0.32.4 ephemeral-compute briefs). New contributions: **the four-component image, the docker-compose layout, and the per-mode load-balancer and scaling design.**

## The Four Components On The Instance

What runs on the compute image: **mitmproxy, the FastAPI MITM service, sg-playwright, and the vault app (the SG API, the vault, and the vault UI).**

The project lead: **"the four main things the EC2 image, the compute, will have are mitmproxy, the FastAPI man-in-the-middle, sg-playwright, and the vault app, which is the SG API and the vault and the build-to-render vaults, the vault UI. That means we can deploy vaults to that server."**

| Component | Role | Reference |
|-----------|------|-----------|
| mitmproxy | The proxy: fetches the origin page and hands it to the MITM service (part one) | The mitmproxy open-source tool |
| FastAPI MITM service | Decides activation (currently via cookie) and injects the transformation script | A FastAPI microservice, Python 3.12, on the OSBot-Utils, OSBot-Fast-API, and OSBot-AWS stack, API-key auth via an x-api-key header, port 10011, Apache-2.0, AWS-Lambda-deployable, with a multi-stage dev, QA, and prod pipeline, an admin UI, a console, and a mitm-scripts CLI (github.com/the-cyber-boardroom/MGraph-AI__Service__Mitmproxy) |
| sg-playwright | Browser automation over HTTP: navigate, screenshot, PDF, extract DOM and text, run sequences, hold sessions; auth via x-sgraph-access-token through the vault /pw proxy or X-API-Key direct | The sg-playwright service (hub.docker.com/r/diniscruz/sg-playwright) |
| Vault app | The SG API plus the vault plus the vault UI (build-to-render vaults); lets vaults be deployed to and served from the server | The SGraph vault stack |

So the instance is self-contained: it proxies, it transforms, it can drive a browser, and it serves vaults. The FastAPI MITM service and sg-playwright are the two externally-referenced components, and the vault app is the SGraph stack that delivers the script-management, logging, and UX-launcher roles from part two.

## Out Of Scope: The VNC Server

A deliberate boundary: **the VNC server (the remote browser) is out of scope for this image because it needs a container per user, so it can sit on this instance or on a separate one.**

Because mode two (part one) streams a remote browser to each user, the VNC server needs a container per user, a different scaling and isolation profile from the four shared components above. It can run on this EC2 instance or on a separate instance or fleet; either way it is treated as a separate concern here.

```
 OUT OF SCOPE (separate concern):  VNC server / remote browser
   . one container PER USER
   . its own EC2 instance, or its own container fleet
   . different isolation and scaling profile from the shared components
```

## The Docker-Compose Layout

How the components run together: **a full docker-compose brings up the four components on the instance, with the vault app reading and writing vaults backed by S3.**

```
 EC2 instance  (one image, docker-compose)
 +----------------------------------------------------------+
 |  +------------+     +----------------------+              |
 |  | mitmproxy   | --> | FastAPI MITM service |  :10011      |
 |  | (proxy)     |     | (script injection)   |  x-api-key   |
 |  +------------+     +----------------------+              |
 |                                                          |
 |  +-------------+    +----------------------+              |
 |  | sg-playwright|    | vault app            |              |
 |  | (browser     |    | (SG API + vault      |              |
 |  |  automation) |    |  + vault UI)         |              |
 |  +-------------+    +----------------------+              |
 +----------------------------------------------------------+
        |  vault app reads/writes vaults
        v
     S3  (shared vault store; see part two)
```

So the docker-compose is the unit of deployment: it stands up mitmproxy, the FastAPI MITM service, sg-playwright, and the vault app together, and the vault app connects to the shared S3-backed vault store described in part two. A full docker-compose is a required deliverable so the whole instance comes up reproducibly.

## Scaling And The Load-Balancer Choice

How it scales, and the one real decision: **an auto-scaling group fronted by a load balancer, where the type depends on the mode, a Network Load Balancer for the direct mitmproxy, an Application Load Balancer for the vault app and web traffic.**

The project lead: **"the architecture is an auto-scaling group and a load balancer. It would be an application load balancer for the web apps, but you need a network load balancer if the customer needs to use the mitmproxy directly, or an application load balancer if it is going through the vault or hitting the web page. So the two modes have two different deployment modes, and because it is a scaling group, you scale quite nicely."**

```
   MODE 1: direct proxy           +------------------------------+
   -----------------------------> | Network Load Balancer (NLB)  |  L4, for direct mitmproxy
                                  +------------------------------+
                                                |
   MODE 2: vault / web            +------------------------------+
   -----------------------------> | Application Load Balancer    |  L7, for the vault app and web
                                  +------------------------------+
                                                |
                          +---------------------+---------------------+
                          v                     v                     v
                      [ EC2 #1 ]            [ EC2 #2 ]   ...       [ EC2 #N ]    Auto Scaling Group
                          +---------------------+---------------------+
                                                |  all feed from
                                                v
                                          S3  (shared vaults)
```

So the mode (part one) chooses the load balancer: mode one (the user's browser talks to mitmproxy directly) needs a Network Load Balancer (layer four), and mode two (the user hits the vault app or a web page) needs an Application Load Balancer (layer seven). Behind either, the auto-scaling group of instances all feed from the same S3-backed vault (part two), so scaling out to many instances is straightforward because no instance holds unique state.

## The Deploy Model

How a server is brought up: **deploy by spinning the server up and copying the vaults that belong on it, and that is it.**

The project lead: **"the deployment of a server fundamentally becomes a case of spinning this up, and then copying into the server all the vaults that should be on that server, and that is it. The architecture scales quite nicely, because it is an auto-scaling group and a load balancer."** So deployment is two steps: stand up the instance (the docker-compose with the four components), then copy in the vaults it should serve (the scripts, and any UX-launcher and testing vaults from part two). Because the instances are stateless beyond their vaults and the vaults are S3-backed, the auto-scaling group can grow and shrink freely (cross-ref: the v0.33.2 aws-deployment and v0.32.4 ephemeral-compute briefs).
