## What This Is

A comparison requested by the project lead: **how Eclipse Biscuit (biscuitsec.org) relates to SGit and SG/Vault.** The headline finding is that they sit at different layers and are largely complementary: Biscuit is an authorization-token standard (who may do what, verifiable by anyone, attenuable offline), while SGit and SG/Vault are a zero-knowledge encrypted data platform (confidentiality, versioning, comms). Biscuit is therefore a strong candidate authorization-and-capability layer that SG/Vault could adopt or learn from, especially its offline attenuation and Datalog policies, rather than a competitor. It touches the PKI, append-capability, and key-management work (cross-ref: the v0.32.4 pki-public-key-registry, v0.33.2 vault-append-capability, v0.32.7 central-key-management, and v0.33.16 recipient-key-management-options briefs). Biscuit facts are paraphrased from the sources at the end; the SGit and SG/Vault facts are from the project's own tooling and corpus.

## What Eclipse Biscuit Is

Biscuit is an open authorization-token specification, an Eclipse Foundation project under the Apache-2.0 licence, with these properties:

| Property | What It Means |
|----------|---------------|
| Authorization token | It carries rights, who may do what, for distributed systems where centralized authorization is not possible |
| Decentralized verification | Signed with public-key cryptography (Ed25519); any node holding the public key can verify it, with no call to the issuer |
| Offline attenuation | A holder of a valid token can derive a new, more restricted valid token (less access, an expiry) without contacting anyone |
| Datalog policies | Authorization rules are written in a logic language, carried by the token or supplied by the verifier; they model expiry, hierarchical roles, and delegation |
| Capabilities or ACLs | Naturally capability-based (the token carries the rights), but verifier-side ACLs in Datalog are also supported |
| Revocation | Each token has a unique revocation identifier; revoking a token also rejects everything attenuated from it, but the revocation state must be managed externally |
| Portable and small | Implementations in Rust, Go, Java, JS, WebAssembly, C, Python, and more; small enough to fit in a cookie; a new implementation needs only Protobuf and Ed25519 |

Its stated non-goals matter: **Biscuit is not an authentication protocol** (it can be an opaque token issued by something like OAuth, and can carry authentication data, but it does not define authentication), and **revocation requires external state** outside the specification.

## What SGit And SG/Vault Are

For grounding, the two SGraph pieces:

**SGit** is a CLI for zero-knowledge encrypted vaults, git for encrypted files: the server never sees plaintext (AES-256-GCM, keys derived locally via PBKDF2), commits snapshot the whole folder, objects are content-addressable (SHA-256 of plaintext, deduplicated), branches use a two-layer clone-and-named model, and sharing is via a Simple Token (a one-shot snapshot the recipient opens with only the token) or a multi-layer publish. It also has a PKI subsystem for signing, verifying, and encrypting files to recipients.

**SG/Vault** (with SG/Send) is the platform around that store: per-vault key pairs, vault-to-vault sealed-message comms, the append capability (an append key granting the right to add to a vault), signed updates (a message signed with the parent admin key is the only way to update a vault), a public-key registry with federation, and key-gated capabilities throughout (cross-ref: the pki-public-key-registry, vault-append-capability, shipping-vault-signed-message, and central-key-management briefs).

## The Fundamental Distinction

The cleanest way to see the relationship: **Biscuit secures authorization (who may do what), while SGit and SG/Vault secure the data itself (confidentiality, versioning, and communication).** Biscuit is a token format with no storage, no encryption of payload data, no versioning, and no comms. SGit and SG/Vault are a data platform that encrypts, versions, stores, and moves data, and that today expresses authorization through bespoke key-gated mechanisms (the vault key, the Simple Token, the append key, the signed-update admin key). They are different layers of the same stack, not alternatives.

## The Comparison

| Dimension | Eclipse Biscuit | SGit | SG/Vault |
|-----------|-----------------|------|----------|
| Primary purpose | Authorization tokens | Encrypted versioned sync (CLI) | Encrypted vault platform |
| What it secures | Who may do what | The data (confidentiality) plus access | The data plus access and comms |
| Cryptography | Ed25519 token signatures | AES-256-GCM data, plus a PKI for files | Per-vault key pairs, signed updates |
| Authorization model | Capability tokens and Datalog policies | Vault key, Simple Token, publish | Append key, signed updates, key-gated capabilities |
| Offline attenuation | Yes, holder-derived | No | No (capabilities are key-issued) |
| Policy language | Datalog | None (key possession) | None (key possession and signed messages) |
| Decentralized verification | Yes (public key) | Via PKI for files | Yes (the public-key registry, federation) |
| Revocation | Revocation IDs, external state | Version control, key change | Version control, key rotation, registry |
| Data storage and encryption | None | Zero-knowledge store | Zero-knowledge store |
| Versioning | None | Git-like commits and branches | Built on the SGit store |
| Communication | None | Share and publish | Vault-to-vault sealed messages |
| Authentication | Explicitly not in scope | Token or vault key | The identity layer being sought (cross-ref: partner-briefing) |
| Standardization | Open Eclipse spec, many languages | SGraph implementation | SGraph implementation |

## Where They Overlap

Three real conceptual overlaps explain why the comparison is worth making. Both rely on **public-key verification** (Biscuit verifies tokens with a public key; SG/Vault verifies signed updates and resolves identity through its public-key registry). Both are **capability-minded** (Biscuit carries rights in the token; SG/Vault gates capabilities with keys such as the append key). And both assume a **decentralized, no-central-authority** setting (Biscuit for microservices without centralized authorization; SG/Vault for federated, no-lock-in vaults). The overlap is in the authorization thinking, which is exactly where Biscuit could plug in.

## What Biscuit Has That SG/Vault Does Not

Three Biscuit capabilities are genuinely absent from SG/Vault today:

**Offline attenuation.** A Biscuit holder can derive a weaker token (less access, an expiry) with no call to anyone. SG/Vault's capabilities are issued by key possession and cannot be attenuated by the holder; to give someone narrower access today you mint a new scoped credential.

**A Datalog policy language.** Biscuit expresses expiry, hierarchical roles, and delegation as logic rules. SG/Vault expresses authorization as key possession plus signed messages, with no policy language.

**A portable, governed standard.** Biscuit is an Eclipse Foundation specification with implementations in many languages (including JS, WebAssembly, and browser), maintained by an established community. SG/Vault's token mechanisms are bespoke to the project.

## What SG/Vault Has That Biscuit Does Not

The converse is just as clear, and it is most of what SG/Vault is:

**Zero-knowledge data encryption.** Biscuit secures authorization, not payload confidentiality. SG/Vault encrypts the data so the server never sees plaintext. This is SG/Vault's core and is entirely outside Biscuit's scope.

**Versioning, storage, and comms.** SGit provides git-like versioning and a content-addressable encrypted store, and SG/Vault provides vault-to-vault sealed messaging. Biscuit has none of these.

**An identity and data home.** Biscuit is explicitly not authentication and holds no data. SG/Vault is where the data, the identity registry, and the relationships live (cross-ref: the partner-briefing identity work).

## The Finding: Complementary, And A Candidate Layer

So Biscuit is not a competitor to SGit or SG/Vault; it is a candidate **authorization and capability layer** for them. SG/Vault already reaches repeatedly for capability tokens: the Simple Token, the append key, the scoped tokens sent to the deployment bastion, the keys distributed to child vaults, and the signed-update admin key (cross-ref: the vault-append-capability, aws-deployment, and central-key-management briefs). Each of these is a bespoke capability mechanism that Biscuit could express in a principled, publicly-verifiable, attenuable, standard form. The biggest wins from adopting Biscuit, or a Biscuit-like pattern, would be offline attenuation and Datalog policies, with the portability and governance of an Eclipse standard as a bonus that fits the run-everywhere, no-lock-in, browser-interop ethos (cross-ref: the access-not-security and tool-replacement briefs).

## Where Adopting Biscuit Would Help SG/Vault Most

The offline-attenuation property maps directly onto several SG/Vault use cases that currently need a bespoke answer:

| SG/Vault Use Case | How Biscuit Attenuation Helps |
|-------------------|-------------------------------|
| Recipient restricted access (cross-ref: recipient-key-management) | A recipient could hold a capability and derive a narrower one for a delegate, offline |
| Partner-outreach restricted views (cross-ref: partner-outreach-vault) | Send a capability that the holder can further restrict before forwarding |
| Child-vault key distribution (cross-ref: central-key-management) | A parent issues a capability; a child attenuates it for its own callers |
| The append capability (cross-ref: vault-append-capability) | An append key could be attenuated to restrict what may be appended, or add an expiry |
| Deployment bastion tokens (cross-ref: aws-deployment) | The low-privilege, scoped token is exactly an attenuated capability |

The pattern SG/Vault keeps describing, restrict to unleash, scoped tokens, low privilege, is precisely what Biscuit's offline attenuation provides as a standard mechanism.

## Honest Trade-Offs

**Adopting Biscuit adds a dependency and a Datalog engine.** That is real complexity; the current key-possession model is simpler for today's use cases. Biscuit earns its place when attenuation, delegation, and policies become central, which the outreach, recipient-access, and child-vault work suggests they will.

**Biscuit revocation needs external state, which SG/Vault can supply.** Revocation lists are out of Biscuit's scope, but SG/Vault's version-controlled store and key registry are a natural home for revocation state (cross-ref: the deterministic-value-indexes and pki-public-key-registry briefs).

**Biscuit is authorization only.** It does not reduce what SG/Vault must own: encryption, storage, versioning, comms, and authentication. It slots in beside them, it does not replace them.

**Building bespoke remains an option.** SG/Vault could implement attenuation and policies itself rather than adopt Biscuit; the trade-off is standardisation and a proven, multi-language, browser-ready implementation against a dependency and a learning curve.

## Recommendations

1. **Treat Biscuit as a candidate capability-token layer, not a competitor** (it sits below SG/Vault's data, above nothing it conflicts with).
2. **Prototype offline attenuation on one use case** (the append capability or the recipient restricted-access case are the best first tests).
3. **Evaluate Datalog policies for vault access** (expiry, roles, delegation) against the current key-possession model.
4. **Use SG/Vault as the revocation-state home** (the version-controlled store and registry supply what Biscuit leaves external).
5. **Keep the encryption, versioning, comms, and identity layers as SG/Vault's own** (Biscuit does not touch them).
6. **Decide build-versus-adopt deliberately** (a standard with browser implementations fits the ethos; weigh it against the dependency).
