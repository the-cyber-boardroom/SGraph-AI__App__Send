## What This Is

A focused mapping of SGit specifically onto the Encrypted Collaboration Spaces paper, and an honest read of how much of what the paper describes SGit already implements: **SGit has already built the paper's substrate, an encrypted, content-addressed, append-only store on a server that holds no keys, with client-side verification by hash and a git-style catch-up, and the paper adds a verifiability superstructure (zero-knowledge tracer and fast-forward proofs) and a dynamic-group-key layer (ratchet, retention, rekey) on top of a substrate that looks a great deal like SGit.** It is the SGit-specific companion to the overall paper mapping (cross-ref: the v0.33.21 encrypted-spaces-paper-mapping-to-sgraph brief), and it draws on the SGit tooling and the post-quantum work (cross-ref: the v0.33.21 post-quantum-cryptography brief). The paper is paraphrased; the source is listed at the end. New contributions: **the SGit-to-paper substrate mapping, the implemented-versus-missing read, and the SGit-as-storage-layer observation.**

## SGit In One Paragraph

SGit is a command-line tool for zero-knowledge encrypted vaults, git for encrypted files: data is encrypted with AES-256-GCM and the server never sees plaintext or the passphrase (keys are derived locally with PBKDF2 from a passphrase-and-vault-id), commits snapshot the whole folder, objects are content-addressable by the SHA-256 of their plaintext and deduplicated across commits, branches use a two-layer clone-and-named-key model, push and pull move deltas, sharing is via a one-shot Simple Token (the recipient needs only the token, no vault key and no install) or a multi-layer publish, and a PKI subsystem signs, verifies, and encrypts files to recipients. The cross-session pattern is to commit and push at the end of a session and pull at the start of the next.

## The Substrate SGit Has Already Built

The important finding first: **the parts of the paper that are hardest to retrofit are exactly the parts SGit already has right.**

| Paper Substrate Concept | SGit Reality | Status |
|-------------------------|--------------|--------|
| Server holds no cryptographic keys | The server never sees the passphrase or plaintext; keys derived locally | Implemented |
| Confidentiality (encrypted, unreadable by the server) | AES-256-GCM, zero-knowledge | Implemented |
| Integrity-protected data | Authenticated encryption plus content-addressing by plaintext hash | Implemented (per-object) |
| Hash commitments to data | Content-addressable object IDs are SHA-256 of plaintext (a Merkle-DAG store) | Implemented |
| Changelog (append-only operation history) | The commit log is an append-only, content-addressed history | Implemented |
| Changelog commitment | Commit hashes fix the ordered history | Implemented |
| Client cache or copy as a local verifier | A clone is a full local copy; content is verified by hash | Implemented (by hash) |
| Fast-forward (catch up from a known point) | Pull applies the missing commits since the last known state | Implemented (git-style, not a proof) |
| Quantum-sound hashing | SHA-256 content-addressing and AES-256 are quantum-appropriate | Implemented |
| Deduplication via structural hashing | Objects deduplicate across commits by content hash | Implemented |
| Sharing access without the recipient holding the vault key | The Simple Token gives one-shot access with only the token | Implemented (token-derived, not public-key-wrapped) |
| A signing primitive over content | The PKI subsystem signs and verifies files | Implemented (primitive) |

So the substrate the paper assumes, an encrypted, integrity-protected, content-addressed, append-only store on a keyless server, with clients that hold copies and verify by hash, and a catch-up mechanism, is largely what SGit already is. These are also the properties that are painful to bolt on to a system that did not start with them, and SGit started with them.

## What The Paper Adds On Top Of An SGit-Like Substrate

The gaps are real, and they are the paper's research contribution rather than its substrate: **a verifiable-computation layer and a dynamic-group-key layer that SGit does not have.**

| Paper Superstructure | SGit Reality | Status |
|----------------------|--------------|--------|
| Transition system: apply(state, signed change) verified across server, prover, and client | SGit advances state by snapshot commits, with a PKI signing primitive, but no shared verified apply function | Partial (signing yes, verified apply no) |
| Tracer proofs (verifiable per-operation reads and writes) | SGit does not emit Merkle inclusion or tracer proofs to clients | Missing |
| Fast-forward proofs (zero-knowledge rollup of a batch) | SGit catches up by applying commits, with no zero-knowledge proof of correct application | Missing (the operation exists, the proof does not) |
| zkVM execution and recursive proof composition | Not present | Missing |
| Authorization policy verified inside apply | SGit relies on key possession and signatures, not verified policy | Missing |
| Ratcheting (forward access control) | SGit branch and vault keys are not ratcheted; new holders are not cryptographically blocked from old data | Missing |
| Retention system (cryptographic deletion, selective history) | SGit deletes by new commits; no key-tree retention or cryptographic deletion | Missing |
| Rekey to remaining members on removal | Sharing is token-and-key-based, not dynamic-group rekey | Missing |
| Two-tiered key tree | Not present | Missing |
| Multi-recipient verifiable encryption | Not present | Missing |
| Relational tables, typed schema, proven Select | SGit stores files and objects, not a typed queryable database | Missing (SG/Vault indexes are the closer analog) |

So SGit is git for encrypted files, the substrate, and the paper is git for encrypted files plus a verifiable database plus dynamic group cryptography. The verifiability and dynamic-group layers are what SGit would need to add to reach the paper's full model.

## The Key Observation: SGit Is The Natural Storage Layer

A point worth dwelling on: **the paper forks the merk Merkle AVL tree library and runs its proofs in the RISC Zero zkVM, and a content-addressed store like SGit is exactly the substrate those sit on.** The paper's data commitment is a Merkle root over an ordered key-value store; SGit's content-addressed object graph is a Merkle DAG over encrypted objects. The paper's changelog commitment is a hash chain over operations; SGit's commit log is a hash chain over snapshots. The verifiability layer (tracer proofs over the data commitment, fast-forward proofs over the changelog) is something that could, in principle, be built over an SGit-shaped store rather than instead of it. SGit has the keyless, encrypted, append-only, content-addressed foundation; the paper shows what a verifiability layer over such a foundation looks like.

## Honest Assessment

**SGit has the foundation right, which is the hard part.** No server keys, content-addressing, append-only history, and client-side hash verification are difficult to retrofit and easy to get wrong; SGit has them.

**SGit lacks the verifiability superstructure, which is the paper's point.** Proving that the server applied operations correctly, rather than trusting signatures and version control, is the gap, and it is expensive (the paper's prototype spends real GPU time per change).

**SGit lacks dynamic group cryptography, which SG/Vault partly covers.** Ratchet, retention, and rekey live more naturally in SG/Vault's key management than in SGit itself (cross-ref: the central-key-management and recipient-key-management briefs), but neither has the paper's full machinery yet.

**SGit is the storage layer, not the database.** The paper's relational and query model maps to SG/Vault's deterministic value indexes and the vault-as-database direction, not to SGit's file-and-object model (cross-ref: the deterministic-value-indexes and webify briefs).

## Recommendations

1. **Recognise SGit as the paper's substrate** (the keyless, encrypted, content-addressed, append-only foundation is built).
2. **Consider exposing inclusion proofs from the content-addressed store** (the cheapest step toward the paper's tracer proofs, since the Merkle structure already exists).
3. **Formalise the transition-system apply over SGit state** (a shared verified apply function is the bridge to the paper's verifiability model).
4. **Locate ratchet, retention, and rekey in SG/Vault key management, anchored to SGit** (the dynamic-group layer over the SGit substrate; cross-ref: the central-key-management brief).
5. **Treat the zero-knowledge fast-forward and tracer proofs as a research track over SGit** (a verifiability layer on the existing store, not a rewrite).
