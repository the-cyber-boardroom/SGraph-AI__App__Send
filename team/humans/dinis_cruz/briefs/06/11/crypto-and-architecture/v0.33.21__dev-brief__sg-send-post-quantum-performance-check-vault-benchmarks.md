# A Performance-Check Vault For Post-Quantum Crypto In The Vault Workflows And Data Flows

**version** v0.33.21
**date** 11 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, QA, @Dev
**type** Dev brief

---

## What This Is

A brief for a dedicated vault that measures the performance and size impact of post-quantum cryptography on SG/Vault's real workflows and data flows: **benchmark the classical, hybrid, and post-quantum-only variants of every cryptographic operation in the create, comms, signed-update, key-wrapping, and large-file flows, across both the server and the browser, capture every measurement as a version-controlled artefact, visualise the comparison, and set the thresholds that decide whether the migration is acceptable.** It operationalises the post-quantum research (cross-ref: the v0.33.21 post-quantum-cryptography brief), follows the isolated-experiment pattern of the update QA vault (cross-ref: the v0.33.21 vault-update-workflow-qa-test-vault brief), and applies the testing and capture discipline (cross-ref: the v0.33.2 tests-as-properties and v0.33.16 artefact-driven-security-assessments briefs). New contributions: **the post-quantum benchmark matrix, the workflow and data-flow coverage, the server-versus-browser comparison, and the acceptance thresholds.**

## Why This Is Needed

The post-quantum research established that SG/Vault's symmetric core (AES-256) is fine and the work is the asymmetric layer, but it also flagged two performance-relevant facts: **post-quantum keys and signatures are kilobytes rather than tens of bytes, and the operations have different speed and resource profiles, with the browser the likely pain point because the Web Crypto API has no native post-quantum support.** Before committing the migration, the team needs measured evidence of what hybrid and post-quantum cryptography cost in SG/Vault's actual workflows and data flows, not estimates. This vault produces that evidence.

## The Approach: A Dedicated, Isolated Performance Vault

The method mirrors the update QA vault: **an isolated vault that exercises the real workflows with instrumented cryptography, so the team can benchmark without touching production.** It uses the same code paths as production but swaps the cryptographic primitives between classical, hybrid, and post-quantum-only, measures each, and captures the results. Isolation keeps the benchmarking clean and repeatable, and the captured results feed back into the migration plan.

## The Benchmark Matrix

The core is a matrix of every asymmetric operation against the three crypto variants:

| Operation | Classical | Hybrid | Post-Quantum-Only |
|-----------|-----------|--------|-------------------|
| Key generation | Ed25519, X25519 | Plus ML-KEM, ML-DSA | ML-KEM, ML-DSA |
| Key encapsulation and exchange (sealed messages) | X25519 | X25519 plus ML-KEM | ML-KEM |
| Decapsulation | X25519 | X25519 plus ML-KEM | ML-KEM |
| Signing (updates) | Ed25519 | Ed25519 plus ML-DSA | ML-DSA |
| Verification (accept) | Ed25519 | Ed25519 plus ML-DSA | ML-DSA |
| Key wrapping (hierarchy) | X25519 | X25519 plus ML-KEM | ML-KEM |

The symmetric operations (AES-256-GCM bulk encryption, hashing) are included as an unchanged baseline, so the report shows clearly that the bulk data path is unaffected and the cost is concentrated in the asymmetric operations.

## The Workflows And Data Flows To Cover

The benchmarks run inside the real workflows, not in isolation, so the end-to-end impact is measured:

| Workflow Or Data Flow | What It Stresses |
|-----------------------|------------------|
| Vault create | Keypair generation |
| Sealed message and vault-to-vault comms | Encapsulation and decapsulation per message |
| Signed update and accept | Signing and verification, plus signature size in the message |
| Key wrapping in the parent-child hierarchy | Wrapping cost across the hierarchy (cross-ref: central-key-management) |
| The PKI registry | Storing and looking up larger public keys (cross-ref: pki-public-key-registry) |
| Large-file and chunked upload | Per-chunk and per-message key operations against the 15 GB load (cross-ref: large-file-sharing) |
| Deterministic value indexes | Hashing cost if moving to a 384-bit hash (cross-ref: deterministic-value-indexes) |
| The append capability | Signing and sealing per appended message (cross-ref: vault-append-capability) |
| The update QA loop | The full create-update-accept-verify-rollback loop with post-quantum crypto (cross-ref: vault-update QA brief) |

## The Metrics

Each run captures a consistent set of metrics so the variants are comparable:

| Metric | Why |
|--------|-----|
| Operation latency | Time per keygen, encapsulate, decapsulate, sign, verify, wrap |
| Throughput | Operations per second under load |
| Size | Key, signature, ciphertext, and message sizes; storage and bandwidth impact |
| End-to-end latency | The full workflow time, not just the primitive |
| CPU and memory | Resource cost, especially in the browser and ephemeral compute |
| Delta over time | Whether captured baselines drift across versions |

The size metric matters as much as speed: larger keys and signatures inflate messages, the capability tokens (cross-ref: the biscuit-comparison brief), the registry, and storage, so the report must quantify both the time and the space cost.

## Server Versus Browser

A distinction the report must make explicit: **measure both the server or native path and the browser or WebAssembly path, because the browser is where post-quantum is hardest.** Native libraries are fast; the browser has no native post-quantum support, so application-layer post-quantum needs a WebAssembly library whose overhead is unknown until measured. The vault benchmarks both, with Playwright driving the browser runs (cross-ref: the vault-update QA and beta-cohort briefs), so the report shows where the browser cost is acceptable and where it is not. Hybrid TLS, which the browser already supports, is noted separately as the transport baseline.

## Capture And Visualise

Consistent with the artefact-driven approach: **every measurement is captured as a version-controlled artefact in the vault, and the comparisons are visualised.** The vault stores each run (the variant, the workflow, the metrics, the environment) so results are reproducible and comparable over time, reusing the timings observability already built (the Jaeger-like timing traces; cross-ref: the release-manifest-and-event-capture brief). The visualisations show classical against hybrid against post-quantum-only, per operation and per workflow, in latency and in size, so the cost is legible at a glance.

## Thresholds And The Decision

The point of the exercise: **set acceptance thresholds and let the measured results decide where the migration is fine and where it needs care.** Define what slowdown and what size increase are acceptable per workflow (a vault create can be slower than a per-message sign), and use the report to confirm the migration is acceptable overall, to find the workflows where post-quantum is too costly (likely the browser path and the highest-frequency per-message operations), and to choose hybrid versus post-quantum-only per workflow. The output feeds straight back into the post-quantum migration plan (cross-ref: that brief).

## What This Asks For

1. **Build the isolated performance-check vault** (real workflows, instrumented crypto, no production impact).
2. **Run the benchmark matrix** (classical, hybrid, post-quantum-only for keygen, encapsulation, signing, wrapping).
3. **Cover the real workflows and data flows** (create, comms, signed update, wrapping, registry, large-file, indexes, append, the QA loop).
4. **Capture the full metric set** (latency, throughput, size, end-to-end, CPU and memory, delta).
5. **Measure server and browser separately** (the WebAssembly path; Playwright-driven).
6. **Capture every measurement as a versioned artefact and visualise it** (reproducible; the timings observability; clear charts).
7. **Set thresholds and make the per-workflow decision** (hybrid versus post-quantum-only; where it is too costly).
8. **Feed the results back into the migration plan** (the post-quantum brief).

Estimated effort: moderate; the workflows, the timings observability, the Playwright automation, and the post-quantum algorithms exist; the contribution is the benchmark matrix, the workflow coverage, and the server-versus-browser comparison. The output is a captured, visualised performance report that says, per workflow, what hybrid and post-quantum cryptography cost and whether it is acceptable.

## What This Does Not Try To Be

- **Not a production change.** An isolated measurement vault feeding the migration.
- **Not primitive micro-benchmarks alone.** End-to-end workflow measurement, not just raw operations.
- **Not speed-only.** Size and resource cost matter as much as latency.
- **Not server-only.** The browser and WebAssembly path is measured explicitly.
- **Not a one-off.** Captured, versioned, and comparable over time.

## Honest Risks

**Risk 1: Benchmarks can mislead if not end-to-end.** Raw primitive speed can hide real-workflow cost. Mitigation: measure inside the real workflows and data flows, not just the primitives.

**Risk 2: The browser cost may be the blocker.** WebAssembly post-quantum may be slow. Mitigation: measure it explicitly; the report decides per workflow; hybrid TLS covers transport regardless.

**Risk 3: Size impact is easy to underweight.** Focusing on latency can miss the storage and bandwidth cost of larger keys and signatures. Mitigation: size is a first-class metric; quantify token, message, registry, and storage impact.

**Risk 4: Results drift across versions.** Algorithms and libraries change. Mitigation: capture every run as a versioned artefact; track the delta over time.

**Risk 5: The vault could diverge from production.** A benchmark sandbox can drift. Mitigation: use the production code paths; swap only the primitives; feed results back into the migration.
