# Proposed Improvements To The Recipient Vault Experience

**version** v0.33.21
**date** 11 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Product, Design, @Dev
**type** Dev brief

---

## What This Is

The companion to the self-service editing guide: a menu of concrete improvements to the recipient assessment vault (the patient vault, rendered neutrally), captured as ideas the provider can choose from when editing their own vault, and at the same time a capture of what is possible with the vault (knowledge the provider and the provider's Claude session do not have, but the team does): **a friendly beta disclaimer and pervasive feedback, a clearer always-visible chat that separates the assessment conversation from general questions, persistence and bookmarking, the three UI primitives of theme, layout, and language plus feature toggles as a fourth, client and server feature toggles with capability negotiation, and a much richer scoring and answer-delta experience.** It is the proposed-changes document promised in the self-service editing brief (cross-ref: the v0.33.21 provider-self-service-vault-editing brief), set in the beta-testing context (cross-ref: the v0.33.2 beta-cohort-agent-testers and shipping-vault-signed-message briefs), and it draws the language matrix from SG/Send. New contributions: **the improvement menu, the three-UI-primitives model, the client and server feature-toggle and capability-negotiation concept, and the scoring and feedback experience.**

## The Framing: Ideas For The Provider, Capturing What Is Possible

The purpose of this document, stated by the project lead: **a set of ideas to hand to the provider, that also captures what the vault can do, because the provider and their Claude session do not know what is possible.**

The project lead: **"this is a document I should give to the provider and say, here are some ideas for you to use when you are making changes to your vault. From a design point of view it helps that I can provide guidance on what is possible with the vault, because neither the provider nor the provider's Claude session knows the details of what is possible, which is something we know."** So the document is both a menu of improvements and a capability map. The provider picks what they like and implements it with the cloning guide; the document tells them what the vault is capable of (cross-ref: the provider-self-service-vault-editing brief). The workflow remains: the provider works on the vault, gives the project lead access, and the project lead packages it as a release with tests and workflows.

## Cluster A: Beta Framing And Pervasive Feedback

The first cluster is about the beta posture and getting feedback, because the early cohort exists to test the system.

The project lead: **"we should show the disclaimer not in a red way, but in a messenger kind of way, to say this is beta, do not put in any confidential data, just use it to try out the vault. What we are looking for is feedback on the experience, on how they felt, on the questions. Our first fifty to a hundred are literally workflows to let us test the system, validate the workflows, the server side, the assessments, because we have already picked up a couple of bugs."**

| Idea | Detail |
|------|--------|
| Friendly beta disclaimer | A messenger-style, not red, note: this is beta, do not enter confidential data, just try the vault (cross-ref: the recipient-created-disposable-vault and shipping-vault privacy posture) |
| Pervasive feedback | Ask for feedback on every page, or at least at the end |
| Feedback on the experience | How it felt, how the flow worked |
| The testing goal | The first fifty to a hundred recipients validate the workflows, the server, the assessments, and deployment (cross-ref: the beta-cohort-agent-testers brief) |

The deployment note: the system will eventually move to the final production infrastructure (the target domain to confirm), so these early runs also validate deployment.

## Cluster B: A Clearer, Always-Visible Chat

The chat is currently too hidden, and it conflates two different conversations.

The project lead: **"the chat interface is not very obvious, you need to click on it. We need to separate the assessment conversation from the normal chat with the back end. The chat should always be visible, chat here, ask questions. We need a caveat that this is not real time for now, there is no bot and no human, so answers come when one of us, or the provider, or the admin is online."**

| Idea | Detail |
|------|--------|
| Always-visible chat | A persistent chat here, ask questions affordance, not hidden behind a click |
| Separate the two conversations | The assessment conversation versus general questions to the back end, kept distinct |
| A not-real-time caveat | No bot, no human on the other side; answers arrive when the team, provider, or admin is online |
| Screenshots | Copy and paste a screenshot to report something wrong, for better support |
| Dated and mapped | Each chat session properly dated and mapped to the assessment and conversation it belongs to |

## Cluster C: Persistence And Bookmarking

The current local mode raises a return-visit question.

The project lead: **"at the moment the vault is only stored on that computer, from the current tab. It is interesting to see if we can add a tab or a link or a bookmark to help with that. Remember we removed the hash from the top, so if you bookmark it you might risk the next session not having the data, but we will see."**

| Idea | Detail |
|------|--------|
| The current mode | The vault lives on that computer, in the current tab, from the link (cross-ref: the recipient-created-disposable-vault brief) |
| Bookmark or link to return | A way to come back to the same vault in a later session |
| The hash caveat | The URL hash was removed; a bookmark may not restore the data next session; to investigate |

## Cluster D: The Three UI Primitives (Plus Feature Toggle)

The central design idea, drawn from previous work: **the client UI should be driven by three primitives, theme, layout, and language, with feature toggles as a fourth.** Not all are exposed to every user; some sit behind an admin or configuration panel.

The project lead: **"we should see the client UI in three primitives. Theme: font, colours, light, dark, high contrast. Layout: literally different layouts, where things move to different places, the same premises but different arrangements, which gets into cultural and user differences, how a Portuguese versus an American versus an English versus a Chinese user experiences it. And language, which like we did with SG/Send should be language and country, Portugal from Portugal, Portugal from Brazil, English from the UK, English from America, different French, a matrix of languages."**

| Primitive | What It Controls |
|-----------|------------------|
| Theme | Font, colours, light, dark, high contrast |
| Layout | Different arrangements of the same elements; cultural and user variation |
| Language | A language-and-country matrix (for example Portugal-Portugal, Portugal-Brazil, English-UK, English-US), as in SG/Send |
| Feature toggle (the fourth) | Covered in Cluster E |

The enabling change: **move all content out of the HTML into standard translatable files, in multiple parts, separating the UI strings from the assessment questions, so each is maintained independently across languages.**

The project lead: **"all the content should move from being inside the HTML to standard files that can be easily translated, in multiple parts, separating the UI from the questions, because those need to be maintained independently across multiple languages."** This is the same content-externalisation the vault-as-app direction needs (cross-ref: the webify-spreadsheets brief).

## Cluster E: Feature Toggles And Capability Negotiation

How to ship all of this safely, and coordinate client and server.

The project lead: **"add the concept of feature toggles, so I can push every change I describe here to go live without impacting any current workflows. I can deploy a new version to all users, the UI looks exactly the same, but the feature is now available. We should also control the feature toggles from the server, push a message from the server to the client that changes settings, maybe even the theme. And we should be able to say a feature needs version x of the admin interface, and if that does not exist, the feature is not enabled."**

| Idea | Detail |
|------|--------|
| Client feature toggles | Ship changes dark; deploy to all users; the UI is unchanged until a feature is enabled |
| Server-controlled toggles | The server pushes settings, and even theme, changes to the client |
| Capability negotiation | A feature can require version x of the server or admin interface; if absent, the feature stays disabled (cross-ref: the release-manifest-templates and shipping-vault signed-update briefs) |

This is the client side of the signed-update and release-channel work: the client negotiates with the server about what it may show.

## Cluster F: A Richer Scoring And Answer-Delta Experience

The assessment results should explain themselves.

The project lead: **"I really like being able to continue and modify your responses and see the delta of your answers. We can do a much better job visualising what happens, providing more detail about the score, how it is calculated, what the impact of each answer was on the score. And the ability to provide feedback, because when I took the questions there were some that felt not relevant to me, or not the right question to ask."**

| Idea | Detail |
|------|--------|
| Modify responses and see deltas | Continue and change answers, and see how the answers and the result change |
| Explain the score | More detail on how the score is calculated |
| Per-answer impact | Show what each answer contributed to the score |
| Feedback on questions | Let the recipient flag a question as not relevant or not well-posed |

## What This Asks For

1. **Deliver the improvement menu to the provider** (the ideas in this brief, as a document they choose from; presented alongside).
2. **Add the beta disclaimer and pervasive feedback** (friendly, not red; feedback on every page or at the end).
3. **Make the chat always visible and split the two conversations** (assessment versus general; not real time; screenshots; dated and mapped).
4. **Investigate persistence and bookmarking** (the hash caveat).
5. **Build the three UI primitives plus feature toggles** (theme, layout, language; content out of HTML; UI separated from questions).
6. **Add client and server feature toggles with capability negotiation** (ship dark; server-pushed settings; version gating).
7. **Enrich the scoring experience** (answer deltas, score explanation, per-answer impact, question feedback).

Estimated effort: large in aggregate, but a menu, so it can be sequenced; several items (the disclaimer, the chat, feedback) are quick wins, while the UI primitives and feature toggles are foundational and larger.

## What This Does Not Try To Be

- **Not a rigid spec.** It is a menu the provider chooses from.
- **Not all at once.** Quick wins first; the primitives and toggles are foundational.
- **Not real-time chat yet.** The caveat is explicit.
- **Not confidential-data-ready.** The beta disclaimer says so.

## Honest Risks

**Risk 1: the menu is large.** Doing everything at once would stall. Mitigation: sequence; quick wins (disclaimer, chat, feedback) first.

**Risk 2: persistence is unresolved.** The hash removal may break bookmarks. Mitigation: investigate; the disposable mode is the safe default (cross-ref: the recipient-created-disposable-vault brief).

**Risk 3: feature toggles add coordination complexity.** Client and server must agree on capabilities. Mitigation: capability negotiation and version gating, built on the release-channel work.

**Risk 4: internationalisation is a real lift.** Externalising content and a language-country matrix is substantial. Mitigation: start by separating content from HTML; add locales incrementally.

**Risk 5: the sensitive domain still applies.** Mitigation: the friendly disclaimer and the do-not-enter-confidential-data message; data stays on the recipient's machine (cross-ref: the recipient-created-disposable-vault privacy posture).
