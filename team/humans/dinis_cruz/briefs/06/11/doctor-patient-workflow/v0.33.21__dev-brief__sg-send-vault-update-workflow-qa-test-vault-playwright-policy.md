# A QA Vault For The Update Workflow: Automate, Debug, And Harden Vault Create-And-Update

## What This Is

A brief for a dedicated experiment and QA test vault that isolates and hardens the vault create-and-update workflow already in the provider-and-recipient product (the doctor-and-patient use case, rendered neutrally as a parent provider vault and child recipient vaults): **build an automated loop that creates a vault, opens it in an iframe, triggers an update by sending a signed vault message, accepts it from the other side, verifies it, and tests rollback, while fixing the known bugs, debugging the logging and comms visually, adding Playwright support, and putting instrumentation under policy, so the workflow can be matured and refactored before going back into the production vault.** It hardens the shipping-vault update model (cross-ref: the v0.33.2 shipping-vault-signed-message-updates brief), uses the iframe and append work (cross-ref: the v0.27.62 vault-in-vault-kernel-model and v0.33.2 vault-append-capability briefs), the agent-tester automation (cross-ref: the v0.33.2 beta-cohort brief), and the policy thinking from the Biscuit comparison (cross-ref: the v0.33.21 biscuit-comparison brief). New contributions: **the QA test vault, the automated update loop, the file-count and message-size fixes, Playwright support, policy-controlled instrumentation, and the auto-install mode.**

## The Context: Isolate The Update Workflow

Why a separate vault: **the production parent-child update workflow works but has nagging bugs and needs cleanup, so a focused QA vault can zoom in on vault updates without touching production.**

The project lead: **"we already created a nice workflow between the provider vault and the recipient vaults, the parent and child vaults, but we still have a couple of nagging bugs and the code needs a cleanup. I would like to create an experiment, almost a QA test vault, that focuses purely on these vault updates. It is a continuation of the original vaults where we exposed the whole thing over MCP, leveraging the code we already created, but really testing it."** So this is a sandbox: the same code and workflow as production, isolated so the team can test, debug, and refactor vault updates without risk, then re-implement the matured result into the production provider-and-recipient vault.

## The Automated Update Loop

The core of the QA vault: **an automated loop that creates a vault, opens it in an iframe, triggers an update via a signed message, accepts it from the other side, verifies it, and tests rollback.**

The project lead: **"we need an automated way to create a vault, open the vault inside an iframe, trigger the vault update action, send a message to the vault, trigger accept the vault update from the other side, and make sure the update has gone through. We should also try rollbacks, which are important."**

| Step | Action |
|------|--------|
| 1. Create | Automatically create a vault |
| 2. Open | Open the vault inside an iframe |
| 3. Update | Trigger the update action: send a signed vault message |
| 4. Accept | Trigger accept of the update from the other side |
| 5. Verify | Confirm the update went through |
| 6. Rollback | Test rolling the update back |

So the loop exercises the full update path end to end (cross-ref: the shipping-vault-signed-message-updates and vault-append-capability briefs): create, open in an iframe (the vault-in-vault model; cross-ref: the vault-in-vault-kernel-model brief), send the signed update message, accept it, verify, and crucially test rollback, which the production flow needs and which is easiest to harden in isolation.

## The Bugs And Limitations To Fix

Concrete defects to address: **the update uses far too many files, and the message file-size limit is too low and should allow at least five megabytes server-side.**

The project lead: **"there is a bug where we are updating using far too many files, so we need to fix that. There is also a limitation on the file size of the message, which we should fix, because the server-side size should be at least five megabytes, so that should not be an issue. And all the logging, all the comms, all the visualisation, we need to debug visually and automated."**

| Issue | Fix |
|-------|-----|
| Update uses too many files | Reduce the file count an update touches |
| Message file-size limit too low | Raise the server-side limit to at least 5 MB |
| Logging, comms, visualisation | Debug them visually and in an automated way |

So the QA vault fixes the file-count inefficiency and the message-size cap (5 MB server-side as the floor), and makes the logging, comms, and visualisation debuggable both visually and automatically, which is exactly what an isolated test harness is for.

## Playwright Support

Automation for the vaults: **add a good way to support Playwright for these vaults.**

The project lead: **"we need to find a good way to add support for Playwright to these vaults."** So the QA vault gains Playwright browser automation (cross-ref: the beta-cohort brief's agent testers, which already use Playwright), driving the create-open-update-accept-verify-rollback loop automatically and repeatably. This is what makes the QA vault a real test harness rather than a manual exercise.

## Policy-Controlled Instrumentation

A clean way to gate the automation: **let a parent instrument a child vault from the iframe or not, controlled by policy, which is low-risk because updates are already cryptographically signed.**

The project lead: **"some of these should be controlled by policy. We could allow our vaults to be instrumented or not from their parent, from the iframe, for example to do an update or other actions. But remember the updates are already cryptographically signed by the caller, so even that is not a big issue."** So whether a parent may instrument a child vault (trigger updates and actions from the iframe) is a policy decision, not a hard-coded one (cross-ref: the v0.33.21 biscuit-comparison brief's policy and capability thinking, and the shipping-vault signed-update model). The security risk is low because updates are already signed by the caller (cross-ref: the shipping-vault-signed-message-updates brief), so the signature, not the instrumentation channel, is what authorises the change.

## The Auto-Install Mode

A convenience mode worth adding: **a mode where updates install automatically.**

The project lead: **"we could also add the mode where we install the updates automatically."** So alongside the trigger-and-accept loop, the QA vault can test an auto-install mode where accepted (signed) updates apply without a manual accept step, useful where the policy and signatures make it safe.

## Configuration Mappings, Visualisation, And Re-Implementation

The output of the QA work: **a sequence of configuration mappings, workflows, and visualisations, so the matured, refactored workflow can be re-implemented into the production vault.**

The project lead: **"create a whole workflow, ideally a sequence of configuration mappings and configuration workflows and visualisation, so that when we re-implement these back into the official provider-and-recipient vault, it is a lot more mature and refactored."** So the QA vault does not just fix bugs: it produces configuration mappings, workflows, and visualisations (cross-ref: the release-manifest configuration and the semantic-graph-visualisation briefs) that capture the hardened workflow, which is then re-implemented into production in a more mature, refactored form.

## Native Versus App Features

A design decision to make along the way: **decide which features belong natively in the vault versus in an app, noting that creating a new vault already works natively.**

The project lead: **"we should look at what features of these we can add natively to the vault versus not, because the vault already supports creating a new vault, that already works, so we should look at the code of that and optimise it."** So the QA work also informs the bake-into-the-vault-versus-app question (cross-ref: the vault-append-capability and release-manifest briefs): create-new-vault is already native and works, so its code is a place to optimise, and each hardened feature is assessed for whether it belongs natively in the vault or in a vault app.

## The First Pass: Map The Whole Workflow

Where to start: **a full mapping of how the entire create-and-update workflow happens, as the first research, before improving it.**

The project lead: **"the first pass is to do a full-blown mapping on how this entire workflow is happening, so we can figure out ways to improve it. That is the first research."** So before fixing or automating anything, the first step is to capture the current workflow end to end (cross-ref: the artefact-driven-security-assessments brief's capture-everything and the semantic-graph-visualisation brief): map every step, file, message, and signature in the create-and-update path, so the improvements are grounded in how it actually works.

## What This Does Not Try To Be

- **Not a change to production yet.** An isolated QA vault; re-implement into production once matured.
- **Not manual testing.** An automated, Playwright-driven loop.
- **Not many-file updates.** The file-count bug is fixed.
- **Not a small message cap.** At least 5 MB server-side.
- **Not hard-coded instrumentation.** Instrumentation is under policy; signatures authorise.

## Honest Risks

**Risk 1: The QA vault could drift from production.** A sandbox can diverge from the real code. Mitigation: it uses the same code and workflow; the output is re-implemented into production; keep them aligned.

**Risk 2: Instrumentation from a parent is a capability.** Letting a parent drive a child is power. Mitigation: it is under policy, and updates are cryptographically signed by the caller, so the signature authorises the change (cross-ref: the shipping-vault-signed-message-updates and biscuit-comparison briefs).

**Risk 3: Auto-install reduces a human checkpoint.** Automatic application removes the accept step. Mitigation: gate it by policy and by signature; use it only where safe; keep manual accept as the default.

**Risk 4: Raising the message size has cost implications.** Larger messages cost more to move and store. Mitigation: 5 MB is a reasonable floor; the file-count fix reduces waste; the content-addressed store deduplicates (cross-ref: the large-file and deterministic-value-indexes briefs).

**Risk 5: The sensitive domain raises the bar.** This hardens a workflow used in a sensitive product. Mitigation: that is the point of isolating and testing it; the privacy posture still applies (cross-ref: the shipping-vault brief).
