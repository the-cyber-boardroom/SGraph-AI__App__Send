# The Next Phase: Recipient-Created Disposable Vaults, Opened Via Iframe

**version** v0.33.21
**date** 11 June 2026
**from** Human (project lead)
**to** Developer (lead), Architect, Security, Product, @Dev
**type** Dev brief

---

## What This Is

The next phase of the provider-and-recipient workflow (the doctor-and-patient use case, rendered neutrally), after a successful first run: **stop having the provider create a vault for every recipient, because that is both a bottleneck and a security gap (it means holding everyone's private keys), and instead let the recipient create their own disposable vault, opened from a parent vault via the iframe technique, and send the results back, starting with a browser-local disposable vault and deferring login and persistence.** It builds on the shipped vault and the update workflow (cross-ref: the v0.33.2 shipping-vault-signed-message and v0.33.21 vault-update-workflow-qa briefs), resolves a tension from the key-management options (cross-ref: the v0.33.16 recipient-key-management-options brief), and uses the iframe model (cross-ref: the v0.27.62 vault-in-vault-kernel-model brief). New contributions: **the stop-holding-recipient-keys shift, the recipient-created disposable vault, the parent-opens-child-via-iframe pattern, and the assessment workflow with its login question.**

## The First Successful Run

The good news that sets up this phase: **the first run worked, the admin created five vaults and sent them over with no major issues, and the admin monitoring vault works well.**

The project lead: **"we had a first successful run. The admin created five vaults, sent them over, no major issues, a couple of minor things. The friction was almost on the creation of the vaults, which takes a couple of minutes, and some of the workflow can be improved, but the admin vault used to monitor and visualise worked quite nicely."** So the core works: vaults were created, delivered, and monitored through an admin vault. The main friction was the latency of creating the vaults (a couple of minutes), and small workflow improvements remain (cross-ref: the vault-update-workflow-qa brief, which hardens exactly this).

## The Problem: The Provider Creating Every Vault

The bottleneck and the security gap, stated plainly: **creating a vault for everybody does not scale and means the provider holds everyone's private keys, which is something to avoid.**

The project lead: **"the need to create vaults for everybody is a massive bottleneck, and also an interesting security gap, because it means we have the private keys to all those vaults, which is something we probably do not want to have, except in some situations."** So provider-created vaults have two problems: they do not scale (the creation latency, multiplied by everyone), and they concentrate custody of every recipient's private key in the provider, which is a real security liability (cross-ref: the recipient-key-management-options brief, which laid out exactly this custody question). The headline of this phase is removing that liability.

## The Shift: The Recipient Creates Their Own Vault

The new model: **the recipient creates their own vault and sends the results back, and can hold more in their vault than they share.**

The project lead: **"I quite like the idea of just the user creating the vaults, and then the user sends the results, or the user logs in and checks in with us and sends the data via messages. That is a much more interesting workflow, because it also goes into the idea that the user could have more data in a vault than they share."** So the recipient becomes the vault creator and key holder: they create the vault, keep their data, and send back only the results (via signed messages; cross-ref: the shipping-vault-signed-message and vault-append-capability briefs). Two wins follow: the provider no longer holds anyone's private keys (the security gap closes), and the recipient can hold more than they share (selective disclosure; cross-ref: the recipient-key-management and the encrypted-spaces retention idea in the paper-mapping brief).

## The Pattern: A Parent Vault Opens Child Vaults Via Iframe

The reusable mechanism, and the project lead notes it generalises: **a parent vault opens other vaults in an iframe, a powerful pattern that works for many situations.**

The project lead: **"this actually will work for a bunch of different places, so it is a really powerful pattern. There is a parent vault that you can use to open up other vaults in the iframe technique that we use."** So the architecture is a parent vault that launches child vaults inside iframes (cross-ref: the vault-in-vault-kernel-model brief): the parent orchestrates and monitors, the child is the recipient's own vault. This is the same pattern the update QA vault exercises (cross-ref: the vault-update-workflow-qa brief), and it generalises well beyond this use case.

## Build First: The Disposable Vault

The concrete first step, deliberately minimal: **a disposable, browser-local vault that just sends the results back, with its vault ID captured so it can be deleted later.**

The project lead: **"it might be a one-off disposable vault, only available on that browser, which is not a bad thing. We probably should build that one, a complete disposable vault. I want to make sure we get the vault ID, because I might want to delete it later. So let's do a disposable vault first, where we just get sent the results. For now, because we use local storage, we can use local storage on that computer, like we do now, to save the vault."** So the first build is a disposable vault: created in the recipient's browser, saved in local storage (as the product already does), used to run the assessment and send the results back, and discarded after. Capturing the vault ID matters so it can be deleted later. This sidesteps the whole persistence-and-login question for the one-off case while delivering the security win immediately.

## Persistence And Login

The deferred but necessary question: **how to persist the vault and log the recipient in, with options including local storage, Google OAuth, and Cognito, but the iframe vault creation comes first.**

The project lead: **"there is the question of persistence. We need to figure out how to persist and how to log in the user, and what login workflow to add. We could use Cognito, Google Auth, or other things, so we need an authentication layer. But the first thing, let's just experiment with creating a vault in an iframe."**

| Persistence or Login Option | Note |
|-----------------------------|------|
| Local storage (browser-local) | The disposable case; what the product already uses; build first |
| Google OAuth | The parent-vault login; depends on the Google OAuth approval being in place (to confirm) |
| AWS Cognito | An alternative authentication layer |
| Other authentication | Open |

So persistence and login are a real next step (where the secret, the key, lives), but they are deferred behind the disposable, local-storage case. One dependency to confirm: the Google OAuth approval, which the project lead flagged as possibly not yet in place (cross-ref: the long-standing OAuth question, still owed its own brief).

## The Assessment Workflow

How it looks to the recipient: **a Start assessment action that creates and registers the vault, optionally explains that the data stays on their computer, and sends the results back while the session is open.**

The project lead: **"you go to the vault, and it has Create or Start assessment. Maybe we explain: we are creating a vault on your computer, the data stays on your computer. For users who want more detail, that creates the vault, registers the vault, and then the data is sent to us, and we can communicate as long as that tab or session is open. We do need a place to put the secret, which we need to figure out."** So the flow is: the recipient clicks Start assessment, optionally sees a plain explanation that the data is created and kept on their own computer, the vault is created and registered, and results flow back to the provider while the session stays open. The styling and how much to explain are a presentation choice; the open piece remains where the secret lives (the login question above).

## The Provider's Role

A deliberate deferral: **whether the provider is in the loop in this first phase is open, and it may be all disposable assessments to start.**

The project lead: **"this is a conversation about how the actual provider fits, and they might be there in this first phase, or we do not do that and it is just all disposable assessments."** So the provider's live involvement is deferred: the first phase may be purely disposable, recipient-created assessments, with the provider brought into the loop in a later phase.

## What This Asks For

1. **Move vault creation to the recipient** (stop the provider creating a vault for everyone; close the key-custody gap).
2. **Let the recipient hold more than they share** (selective disclosure; send back only the results).
3. **Use the parent-opens-child-via-iframe pattern** (the parent orchestrates and monitors; the child is the recipient's vault).
4. **Build the disposable vault first** (browser-local, local-storage, one-off; capture the vault ID for later deletion).
5. **Defer persistence and login** (local storage now; Google OAuth or Cognito later; confirm the OAuth approval).
6. **Build the assessment workflow** (Start assessment, optional data-stays-local explanation, create and register, send results while the session is open).
7. **Defer the provider-in-the-loop decision** (disposable assessments may be the whole first phase).

Estimated effort: moderate, and a clear security improvement; the vault, the iframe model, local storage, the signed-message results, and the admin monitoring vault exist; the contribution is the recipient-created disposable vault and the parent-child iframe orchestration. The output is a workflow where the recipient creates a disposable vault, runs an assessment, and sends results back, with the provider no longer holding their keys.

## What This Does Not Try To Be

- **Not provider-created vaults for everyone.** The recipient creates their own.
- **Not provider custody of recipient keys.** The provider stops holding them.
- **Not durable yet.** The first build is disposable and browser-local.
- **Not blocked on login.** Local storage first; authentication later.
- **Not provider-in-the-loop yet.** Disposable assessments may be the whole first phase.

## Honest Risks

**Risk 1 (and the headline win): not holding recipient keys is the goal, and it shifts custody to the recipient.** That is the security improvement. The disposable, browser-local vault sidesteps long-term recipient custody for one-off assessments; durable cases need the login and persistence work (cross-ref: the recipient-key-management-options brief).

**Risk 2: disposable plus local storage means data can be lost.** Clearing the browser loses the vault. Mitigation: it is intentionally disposable; the results are already sent back; capture the vault ID; anything durable needs persistence.

**Risk 3: the Google OAuth approval is a dependency.** The parent-vault login needs it, and it may not be in place. Mitigation: confirm the approval; local storage is the fallback; this feeds the owed OAuth brief.

**Risk 4: the sensitive domain still applies.** This is a sensitive workflow. Mitigation: keeping data on the recipient's own computer and not holding their keys actually improves the privacy posture; it is a step toward tightening the healthcare MVP (cross-ref: the shipping-vault privacy posture).

**Risk 5: vault-creation latency.** Creation takes a couple of minutes today. Mitigation: the workflow improvements and the update QA vault address this (cross-ref: the vault-update-workflow-qa brief).
