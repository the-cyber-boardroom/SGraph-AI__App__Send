## What This Is

A generic platform pattern, built on SG/Vault, that delivers data aggregation and analytics, the kind of capability usually associated with a central database, without ever creating a central unencrypted database: **the data stays in sovereign, owner-held encrypted vaults; the compute moves to the data as ephemeral SG/Compute enclaves running under on-demand PKI permissions; a semantic knowledge graph federates queries over plaintext structure rather than values; every computation is a versioned, provenance-bearing LETS pipeline; and only aggregates ever leave, so aggregation and analysis happen openly, distributively, sovereignly, scalably, and safely.** This is a generic solution applicable to many domains (clinical outcomes, research consortia, financial data, supply chains, any multi-party data collaboration); the clinical provider-and-recipient case is one neutral example. It composes the NHI 2.0, LETS, semantic-graph, ephemeral-compute, and indexing work (cross-ref: the v0.32.3 NHI-2.0-permission-granularity and access-not-security, v0.33.16 artefact-driven-security-assessments and semantic-graph-visualisation, v0.32.4 ephemeral-compute and deterministic-value-indexes, v0.33.21 recipient-created-disposable-vault and biscuit-comparison briefs, and the encrypted-spaces-paper-mapping brief). New contributions: **the compute-to-the-data aggregation pattern, the federated-benchmark flow, the two key design decisions, and the business models.**

## The Thesis: Compute Moves To The Data

The core idea, stated once: **instead of moving the data into a central database to analyse it, move the computation to the data, run it transiently under permission, and let only the result leave.** A central unencrypted database is the thing every breach, every legal compulsion, and every misuse depends on; this pattern never builds one. The data remains encrypted in vaults the owners control; aggregation happens inside ephemeral, scoped, consented compute; and the platform itself never holds a readable corpus. This is the untrusted-server model (cross-ref: the encrypted-spaces-paper-mapping brief) extended from storage to analytics.

## The Four Building Blocks

| Block | Role In The Platform |
|-------|----------------------|
| Semantic knowledge graph (the library-search solution) | The federated schema, query, and index layer. It knows what exists across vaults via plaintext structural fields (the structure-versus-value split), so a cohort or benchmark query is planned and routed across many vaults without reading any values (cross-ref: semantic-graph-visualisation and deterministic-value-indexes) |
| On-demand PKI permissions (NHI 2.0) | Replaces standing access. Each computation requests a scoped, time-boxed, revocable capability to read specific vaults for one declared purpose; nothing has standing access; every grant is consented and auditable (cross-ref: NHI-2.0-permission-granularity and biscuit-comparison attenuation) |
| SG/Compute ephemeral enclaves | The compute-to-the-data engine. Spin up an isolated, ephemeral compute, grant it the scoped permission, run the pipeline, emit the aggregate, destroy it; scale out horizontally with no central bottleneck (cross-ref: ephemeral-compute and the content-proxy auto-scaling pattern) |
| LETS (Load, Extract, Transform, Save) | Every analysis is a pipeline: Load (decrypt inside the enclave under permission), Extract (only the needed fields), Transform (compute the aggregate, de-identify, statistic), Save (write the result, not the raw data, to a result vault, version-controlled with full provenance) (cross-ref: artefact-driven-security-assessments) |

So the semantic graph says what to query and where, the permission says who may compute what for how long, the enclave does the computing next to the data, and LETS records the whole thing as a reproducible, provenance-bearing artefact whose only durable output is the result.

## The Capabilities Delivered

| Capability | How The Platform Delivers It |
|------------|------------------------------|
| Within-organisation analytics | LETS pipelines run over the organisation's own vaults; results to a result vault |
| Cross-organisation benchmarking | A federated query; each participating owner grants an on-demand permission; an enclave computes the benchmark; only the aggregate is shared |
| Consented data participation (the evidence capability) | A data owner grants a scoped computation; the result, not the raw data, is produced; the owner participates and is credited, the platform never holds the data |

The third row is the important one: the capability usually built by a platform holding a dataset and selling extracts from it is delivered here by the owner granting a scoped, consented computation and only the result leaving. The inversion is covered below.

## Flow 1: The LETS Analysis Pipeline

```
  Owner-held encrypted vault(s)
        |
        |  (on-demand, scoped, time-boxed permission granted)
        v
  +-------------------------------------------------+
  |  Ephemeral SG/Compute enclave (transient)        |
  |                                                  |
  |  L  Load:      decrypt the permitted data inside |
  |  E  Extract:   take only the needed fields       |
  |  T  Transform: compute aggregate / de-identify   |
  |  S  Save:      write the RESULT (not raw data)   |
  +-------------------------------------------------+
        |  only the aggregate leaves
        v
  Result vault (version-controlled, full provenance)
        |
        v
  Enclave destroyed; permission expires
```

The raw data never leaves the owner's control in readable form; only the computed result is saved, and it carries provenance back to the inputs and the pipeline that produced it (cross-ref: the artefact-driven-security-assessments brief).

## Flow 2: The Federated Benchmark (Cross-Organisation)

```
                          Query planner (semantic knowledge graph)
                          knows WHAT exists across vaults via plaintext
                          structure, not values
                                     |
            +------------------------+------------------------+
            |  push scoped permission requests to N owners    |
            v                        v                        v
     Owner A vault            Owner B vault            Owner N vault
     grant (scoped,           grant (scoped,           grant (scoped,
     time-boxed)              time-boxed)              time-boxed)
            |                        |                        |
            v                        v                        v
     ephemeral enclave        ephemeral enclave        ephemeral enclave
     local aggregate          local aggregate          local aggregate
            |                        |                        |
            +------------------------+------------------------+
                                     |  only partial aggregates combine
                                     v
                          Combined benchmark (aggregate only)
                          written to a result vault, with provenance
```

Each owner consents per query and can revoke; no raw data is centralised; the planner routes over structure, not content; and the only durable artefact is the aggregate. This is the benchmarking capability without the central dataset.

## Flow 3: On-Demand Permission And Consent

The orchestration that makes the federated case work: **a computation pushes a permission request stating its purpose, scope, and lifetime; each owner grants (or declines); the grant is a scoped, revocable capability; the enclave runs only within it; the grant expires.** Nothing has standing access to anyone's data; every computation is a fresh, consented, auditable grant (cross-ref: the NHI-2.0-permission-granularity and biscuit-comparison briefs, where offline attenuation and scoped tokens are the mechanism). Keeping this low-friction (a clear request, a one-tap grant, sensible defaults and standing policies for trusted requesters) is what determines whether the cross-organisation case is usable.

## Key Design Decision 1: The Privacy Guarantee On Aggregation

A decision to make, not assume, because it sets the strength of the safety claim: **how much the aggregation is allowed to see and leak.** There is a spectrum:

| Option | Guarantee | Cost |
|--------|-----------|------|
| (a) Transient plaintext in the enclave | The enclave sees plaintext briefly to compute the aggregate; only the result leaves | Lowest cost; relies on enclave isolation and the result not leaking individuals |
| (b) Plus differential privacy, k-anonymity, secure aggregation | Even the aggregate leaks little about any individual | Moderate cost; stronger guarantee; some accuracy trade |
| (c) Multi-party computation or homomorphic encryption | Plaintext never exists, even transiently | Highest cost today; strongest guarantee |

The decision can vary by capability: within-organisation analytics may sit at (a); cross-organisation benchmarking and consented participation likely warrant (b); the strongest claims need (c). This choice is the spine of the safety story and should be made deliberately per capability.

## Key Design Decision 2: The Enclave Trust Model

The second decision, and an honest one: **the enclave is a transient, scoped, consented trust boundary, and how much to harden it is a choice.** The storage stays zero-knowledge regardless; the question is the compute. Options:

| Option | Trust Boundary |
|--------|----------------|
| Plain ephemeral isolated compute | Trust the isolation and the short lifetime; simplest |
| Hardware-attested enclaves (for example Nitro, SEV, SGX) | Attested isolation; but adds trust in a hardware vendor |
| Enclaves as a stepping stone to (c) above | Use enclaves now, move to multi-party or homomorphic computation as it matures |

A caveat worth stating plainly: the recent literature is sceptical of trusted execution environments for the storage trust model, because it means trusting a hardware vendor (cross-ref: the encrypted-spaces-paper-mapping brief). This platform's use is different and more defensible, transient, scoped, and consented compute, with storage staying zero-knowledge, but it is still a real, time-boxed trust boundary, and the honest framing is that enclaves are a pragmatic step toward plaintext-never-exists computation, not the end state.

| Axis | How The Platform Delivers It |

| Open | An open-source, auditable substrate; the security model is inspectable, not only certified |
| Distributed | Compute scales out across ephemeral enclaves; no central honeypot; no single bottleneck |

| Safe | No central plaintext database to breach, compel, or misuse; cryptographic provenance on every aggregation, which is stronger than trust-the-vendor |

## The Business-Model Inversion

The commercial heart of the pattern: **the data owner participates in and is credited for analytics over their data, while the platform never holds the data.** Where the usual model is a platform holding a dataset and selling extracts, here a data owner grants a scoped, consented computation and only the result is produced. The owner participates on their own terms and can revoke; the platform facilitates rather than holds; and there is no conflict of interest between the platform and the data subject. This also opens the privacy-sensitive owners and jurisdictions that a hold-the-data model structurally cannot serve, so the addressable market is arguably larger, not smaller.

## Honest Risks

**Risk 1: the privacy guarantee is a real choice with real consequences.** Transient plaintext in an enclave is weaker than multi-party computation. Mitigation: decide per capability (Key Design Decision 1); be precise in claims; do not overstate.

**Risk 2: the enclave is a trust boundary.** Even transient, scoped compute is a boundary. Mitigation: Key Design Decision 2; storage stays zero-knowledge; treat enclaves as a step toward plaintext-never-exists.

**Risk 3: cross-organisation consent has friction.** Asking N owners to grant per query can be slow. Mitigation: low-friction requests, standing policies for trusted requesters, sensible defaults; this determines usability.

**Risk 4: the semantic graph leaks structure.** Plaintext structural fields and query patterns are visible. Mitigation: minimise plaintext structure; the same leakage trade the literature names (cross-ref: deterministic-value-indexes and encrypted-spaces-paper-mapping).

**Risk 5: maturity.** This is an architecture, not a shipped platform; the building blocks exist but the composition is new. Mitigation: sequence the capabilities (within-organisation first, then federated, then the marketplace).
