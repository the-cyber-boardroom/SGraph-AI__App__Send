## What This Is

A milestone and the workflow it unlocks: **the assessment vault was vibe-coded by the provider themselves, using Claude or Lovable, which means the provider can own the design and changes to their own vault, so the next step is to give them a self-contained guide that they (or their Claude session) can use to clone, edit, and update that vault without the project lead being the bottleneck.** This brief captures the milestone, the empowerment principle, and the plan; the accompanying deliverable is the self-service editing guide (a plain-slug document, presented alongside, designed to be dropped into a Claude session or run from the command line). It builds on the recipient-created and update workflows (cross-ref: the v0.33.21 recipient-created-disposable-vault and vault-update-workflow-qa briefs, the v0.33.2 shipping-vault-signed-message brief, and the v0.27.62 vault-in-vault-kernel-model brief) and realises the empowerment thesis (cross-ref: the v0.32.3 access-not-security brief). New contributions: **the provider-vibe-coded-the-vault milestone, the self-service editing guide as a droppable agent prompt, and the vault-as-its-own-example pattern.**

## The Milestone

The thing worth marking: **a domain expert, not a developer, built their own vault by vibe-coding it.**

The project lead: **"the assessment vault was actually developed by the provider, vibe-coding it. The provider used Claude or Lovable to do this."** This is the empowerment thesis made real: a clinician with no software-development background built their own vault application with an AI coding assistant. It validates the whole direction of restrict-to-unleash, mini-apps, and the vault as something a domain owner shapes themselves (cross-ref: the access-not-security and webify briefs). The job now is to make that repeatable and self-service.

## The Principle: The Provider Owns The Vault, The Project Lead Is Not The Bottleneck

The reason this matters: **the provider should own the design, the experience, and the changes to their vault, so the project lead does not become the bottleneck.**

The project lead: **"what I don't want is for me to be the bottleneck. The provider should own the design, the experience, the changes to the vault, so they can experiment."** So the goal is provider self-sufficiency: the provider experiments with and evolves their own vault, with the project lead providing the guidance and the tools rather than doing the work. The deliverable is a guide that gives the provider that sense of empowerment.

## The Vault Is Its Own Example

A neat property the project lead noted: **any vault the project lead has access to can serve as the worked example for editing a vault.**

The project lead: **"I already have a release on my side, which is fundamentally a vault that we copy over and that can be created by another vault. The cool thing is we just take any vault that I have access to, for example one of the assessment vaults, and use it as an example of editing a vault."** So the existing release (a vault that is copied over, and can be created by another vault) doubles as a case study: a real vault is shared with the agent, which reads it, clones it, and sees how it works (cross-ref: the vault-in-vault-kernel-model and release-manifest-templates briefs). The guide teaches against a real vault, not an abstraction.

## What The Guide Must Include

The design constraints for the deliverable, from the memo:

| Requirement | Detail |
|-------------|--------|
| Self-contained from zero | The agent has no idea what sgit is, how vaults work, or how to make changes; the guide teaches all of it |
| Preconditions stated | Network access to the sgit domains (the memo names star.sgit.ai), and the ability to install and run sgit |
| The vault key or ID | The one piece the provider supplies; the guide is otherwise ready to run |
| Droppable as a prompt | The provider attaches the guide and says, in effect, read this and go for it |
| Works from the CLI too | The same steps run directly from a terminal |
| A real vault as the case study | An example vault is shared so the agent can read, clone, and see it |

The project lead: **"the Claude session the provider uses is able to install sgit, and I have already worked with it. Just make a reference that you also need network access to star dot sgit dot ai. The main preconditions are access to sgit and allowing that network access, and then the other requirement is the vault ID. Then it should literally be a case of the prompt being read the attached markdown or PDF and go for it, because the agent has no idea what sgit is or how vaults work."** The accompanying guide meets these constraints.

## What This Asks For

1. **Deliver the self-service editing guide** (how to clone, edit, and update a vault; self-contained; droppable into Claude or runnable from the CLI; presented alongside).
2. **State the preconditions clearly** (sgit install, network access to the sgit domains, the vault key or ID).
3. **Teach from zero** (the agent knows nothing about sgit or vaults).
4. **Use a real vault as the case study** (an example vault shared with the agent).
5. **Keep document two for the next memo** (the actual proposed changes, as a simulation).

Estimated effort: the guide is ready now; the building blocks (sgit, the vault model, the example vault) exist. The output is a provider who can clone, edit, and update their own vault without the project lead in the loop.

## What This Does Not Try To Be

- **Not the actual changes.** Those are document two, the next memo.
- **Not project-lead-driven.** The provider owns the editing.
- **Not abstract.** It teaches against a real vault.
- **Not assuming prior knowledge.** The agent starts from zero.

## Honest Risks

**Risk 1: the agent starts with no knowledge.** It must be taught sgit and vaults from scratch. Mitigation: the guide is self-contained and uses a real vault as a case study.

**Risk 2: the network precondition can block it.** Without access to the sgit domains, nothing works. Mitigation: the guide states the precondition first; from the CLI with access it should just work.

**Risk 3: the vault key is unrecoverable if lost.** There is no password reset. Mitigation: the guide warns to save the vault key.

**Risk 4: a self-editing provider can break their vault.** Experimentation carries risk. Mitigation: sgit is versioned; changes are committed and can be reverted; the guide covers status and revert.

**Risk 5: the sensitive domain still applies.** Mitigation: the guide is generic about editing; clinical content stays in the provider's own vault and on their own machine (cross-ref: the recipient-created-disposable-vault privacy posture).
