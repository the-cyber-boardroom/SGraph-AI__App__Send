## What This Is

The data-protection pattern for an open-source medical environment, written as a description paper for a 50-minute presentation to a medical partner and as the basis for a LinkedIn article: **it is deliberately not a product pitch but an explanation of the principles any data-protection solution in a medical setting should have, written for a non-technical audience and carried by medical analogies, covering encryption, symmetric and asymmetric keys and the public-key infrastructure that together give confidentiality, integrity, and attribution; client-side encryption, so that only the device creating, editing, or reading the data ever sees it in the clear and every system in between is blind; sovereignty from the keys rather than the data, so that where the data is stored matters far less than who holds the decryption key; version control, so that every change is a signed, chained record with full provenance; key custody in three modes, patient-held, shared, or clinician-held; authorization by the ability to decrypt, with data shared to a recipient's public key; an entirely open-source stack with no lock-in that runs anywhere, including offline; a live patient-and-doctor vault workflow; and a closing note that the whole pattern is agentic-friendly.** It is structured so it can become both the slides and the article. New contributions: **the medical framing, the analogy set, and the principles checklist.**

## The Setup

The talk is not about a particular product. It is about a pattern, an approach to protecting data that a medical organisation can adopt and, just as importantly, can use to judge any solution put in front of it. The audience is largely non-technical, so the goal is to make a small number of powerful ideas land clearly, using medical analogies wherever they help, and to make the ideas visual. The structure moves through definitions first, so nothing is assumed, then to the pattern in action, then to a closing note on AI.

## Concept 1: Encryption

Encryption is a mathematical way to scramble information so that it can be reassembled only by the intended party. You start with a piece of information, you scramble it into something unreadable, and on the other end the holder of the right key turns it back into exactly the original.

The medical analogy is the blinded clinical trial. In a blind trial, the treatment each patient receives is replaced by a code, and the link between the code and the real treatment is held separately. Anyone looking at the trial data sees only the codes; the truth is revealed only by the unblinding key, held by the few people entitled to it. Encryption works the same way: the data is the coded trial, and the key is the unblinding key.

## Concept 2: Symmetric and Asymmetric Keys

There are two kinds of encryption, and the pattern uses both.

Symmetric encryption uses the same key to scramble and to unscramble. It is fast and simple, and both sides hold the same key. Its limit is attribution: because anyone holding the key could have produced the message, you get confidentiality but you cannot prove who created it. The analogy is a shared key to a drug cabinet that two people hold; it keeps others out, but the register cannot tell which of the two opened it.

Asymmetric encryption uses a pair of keys that belong together: a public key, which can be shared freely, and a private key, which is kept secret. What one key locks, only the other can unlock. Anything encrypted to someone's public key can be opened only with their private key, and anything signed with someone's private key can be verified by anyone with their public key. The analogy is a specimen drop-box: anyone can post a sample through the public slot, but only the holder of the key can open the box and take the samples out.

## Concept 3: Public-Key Infrastructure, Sealed and Signed

Putting the two together gives a solution with three properties at once: confidentiality, integrity, and attribution.

To send a record to a specific person and be sure only they can read it, you encrypt it to their public key. Only their private key can open it, so you have confidentiality. To also prove who sent it, you first sign it with your own private key, which anyone can verify with your public key, so you have attribution and integrity. Done together, sign then encrypt, the result can be read only by the intended recipient and could only have come from you. All of this uses public keys, which are meant to be shared, so there is no risk in distributing them.

The medical analogy is a controlled-drugs prescription: it is sealed so that only the dispensing pharmacy can open it, and it is signed so that only the authorised prescriber could have issued it. Sealed and signed.

## Concept 4: Client-Side Encryption

In this pattern the only system that ever sees the data in the clear is the one that creates, edits, or reads it. The data is encrypted before it leaves that device, and every system in between, every server, network, and store, only ever handles the scrambled form. Data at rest, and even its metadata, stays encrypted.

The analogy is a sealed pathology specimen. It travels through couriers and sorting hubs and storage rooms, but none of them can open it; only the originating clinic and the destination laboratory can. The carriers in the middle move it blind.

## Concept 5: Sovereignty Comes From the Keys, Not the Data

Once the data is only ever clear text at its endpoints, a profound shift follows: it no longer matters very much where the data is stored. It can sit in many places, including places with sovereignty concerns or exposure to subpoenas, because what protects it is not its location but the key. Whoever holds the decryption key holds the data. So sovereignty comes from protecting the keys, not the data.

The analogy is a safe-deposit box. The bank stores the box and guards the room, but only you hold the key. Which branch the box sits in does not change who can open it.

## Concept 6: Everyone in the Middle Is Blind

This does not protect only the server. It changes who can see the data across the entire system. In an ordinary solution a surprising number of people can read the data: system administrators, database administrators, DevOps engineers, and the equivalent staff at every provider in the chain, many of whom are not really meant to see it. In this pattern they cannot, because they never hold the key. Only the people with the decryption key can read the data.

The analogy is the porters and filing clerks who move sealed records around a hospital. They carry the folders, but they cannot read them.

## Concept 7: Version Control and Provenance

Every change to the data is saved as a new version, a delta on what came before, and there are efficient ways to do this. Because each change is recorded and signed, and chained to the previous one, you get provenance and explainability: who changed what, and when. Combined with strong identities, this means data cannot be quietly altered in a database without it being visible. Encrypted and version-controlled together is a far stronger position than either alone.

The analogy is the controlled-drugs register or the tamper-evident lab notebook: every entry is dated, signed, and follows the one before, so nothing can be changed after the fact without it showing.

## Concept 8: Who Holds the Keys, the Three Modes

Key custody, who physically holds the keys, is a design choice, and the pattern supports three modes:

- The **patient holds the key**: the patient creates and manages the vault and shares specific data with the clinician.
- **Both hold the key**: patient and clinician both have access.
- The **clinician holds the key**: the clinician creates the patient's vault and holds its key.

Two points matter here. Holding many smaller keys avoids catastrophic failure, because a single breach exposes only what one key unlocks, not everything; a small set of keys is far easier to protect than an enormous dataset. And key management is well understood when the number of keys is small, with good key-management and identity systems available to connect to. The analogy is not keeping every sample in one freezer: distributing them limits the damage if any one fails.

## Concept 9: Sharing by Decryption, Not Secrets

Because of the public and private key design, data can be shared simply by encrypting it to the recipient's public key, so that only they can read it. Authorization becomes the ability to decrypt, not the possession of a password or a shared secret. This makes collaboration between institutions, between patient and clinician, and among different clinicians straightforward.

A good case study is a single vault that many people work with, administrators, secretaries, different specialists, and the patient's own GP, where each piece of data is encrypted so that each person can open only the parts they are meant to see. The analogy is addressing a sealed sample to a named specialist: it is sealed so that only that specialist can open it.

## Concept 10: Open Source and No Lock-In

The whole stack should be open source, under a licence that keeps the code freely available and does not lock the customer, the users, the students, the universities, or anyone else to the data or the supplier. This matters most for sovereignty: a system can claim to be sovereign while the means to access its data are controlled by a third party, and open source removes that trap. It also makes the solution far easier to integrate, to run in many places, and to run offline, and it yields a better architecture overall.

The analogy is the open formulary: open standards and generics mean no single supplier controls access, and care can continue even when one supplier cannot. In the agentic era especially, the value is not the software or a particular feature; it is the ability to build the experience and the workflow, letting patients enter and manage their data and clinicians access it over time.

## The Pattern in Action

The talk then shows it working. A patient sees a simple interface: they open a link, enter their data, and it is saved and shared. Behind that interface is a vault, but the patient never has to see it; the vault is created for them. In the demonstrated workflow the clinician creates the patient's vault, sends the patient a link, the patient fills in their data, and the vaults then talk to each other, so the data moves securely from one vault to another. The patient retains access to their own vault, and the clinician has an admin view to receive, consolidate, process, and analyse the data. Self-provisioning, where the patient creates their own vault, is also supported, but here the clinician-created flow is shown.

## Agentic-Friendly

A closing note: the whole pattern is agentic-friendly. Depending on the setup, the vaults can be accessed by private LLMs, by Claude, or by ChatGPT, according to the workflow you choose. Interfaces can be built with agents, and an agent can sit in the web interface so the patient can talk to their data and be helped to maintain it. This is a final comment rather than the core of the talk, but it shows the pattern is ready for what comes next.

## The Principles Checklist

The practical takeaway is a short list a medical organisation can use to judge any solution put in front of it. A good solution should:

1. Encrypt data on the client, so only the endpoints ever see it in the clear.
2. Use public-key cryptography to give confidentiality, integrity, and attribution together.
3. Derive sovereignty from key custody, not from where the data is stored.
4. Ensure administrators and intermediaries cannot read the data.
5. Version every change as a signed, chained record with full provenance.
6. Let key custody sit with the patient, the clinician, or both, by design.
7. Authorize by the ability to decrypt, not by shared secrets.
8. Keep keys few and well managed, so no single failure is catastrophic.
9. Be entirely open source, with no lock-in, and run anywhere, including offline.
10. Be ready for agents, so data can be used by AI under the same controls.

## What This Does Not Try To Be

- **Not a product pitch.** It is the pattern, and a way to judge any solution.
- **Not a deep technical talk.** It is for a non-technical medical audience.
- **Not storage-centric.** The keys, not the storage, carry the protection.
- **Not closed or proprietary.** The stack is open source by design.

## Honest Notes

- **Analogies simplify.** Each medical analogy captures one idea, not the full cryptography; say so.
- **Key management is the hard part.** The pattern is only as strong as how keys are held and recovered; address loss and recovery.
- **Open source is necessary, not sufficient.** It removes lock-in, but the implementation still has to be sound.
