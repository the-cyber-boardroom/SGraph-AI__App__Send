# One Authorization, Two Control Outcomes: The Chain Scenario, Mapped

**version** v0.33.31
**date** 21 June 2026
**from** Human (project lead)
**to** Architect, Security, Strategy, @Dev
**type** Arch brief (worked example)

---

## What This Is

A worked example that applies the five-term ontology to a two-scenario chain case, and resolves it: **the same agent, with the same mandate, capability, and authorization, refuses a request when it arrives directly, but performs it when the same request arrives through a chain of two upstream agents that already rejected it; mapping the elements shows there is one authorization, identical in both scenarios, and no second authorization event anywhere, and that the entire difference sits in the Control, which refuses in the first scenario and allows in the second because of the accumulated context of the chain; this both concedes that the divergence lives in Control, not in a new grant, and confirms that the action was inside the authorised capability the whole time, so the failure is a defeasible Control diverging at a blind spot, not authorization appearing from nothing.** It is the chain case mapped through the vocabulary (cross-ref: the v0.33.31 authorization-ontology and moment-of-authorisation briefs). New contributions: **the two-scenario visualisation and the element-by-element mapping.**

## The Two Scenarios

Stated in the five terms, then drawn.

**Scenario 1: the request arrives directly, and Control refuses.**

```
   Requester
      |
      |  request for Action A
      v
   +-------------------------+
   |  Agent                  |
   |   Mandate:        M     |
   |   Capability:     C     |   C makes Action A possible
   |   Authorization:  1     |   granted at provisioning
   +-------------------------+
      |
      v
   [ Control: decide ]  -->  REFUSE
      |
      X   Action A does NOT occur
```

**Scenario 2: the same request arrives through a chain, and Control allows.**

```
   Requester
      |
      v
   [ Upstream Agent 1 ]  -->  REJECT
      |   passes context downstream
      v
   [ Upstream Agent 2 ]  -->  REJECT
      |   accumulated context now reads as "already processed"
      v
   +-------------------------+
   |  Agent  (the SAME one)  |
   |   Mandate:        M     |   unchanged
   |   Capability:     C     |   unchanged; Action A still possible
   |   Authorization:  1     |   the SAME single authorization
   +-------------------------+
      |
      v
   [ Control: decide ]  -->  ALLOW   (diverges, because of the context)
      |
      v
   ==>  Action A OCCURS
```

## The Ontology Mapping

Element by element, across the two scenarios:

| Element | Scenario 1 | Scenario 2 | Same or different |
|---------|-----------|-----------|-------------------|
| Mandate | M | M | Same |
| Capability | C, so Action A is possible | C, so Action A is possible | Same |
| Authorization | One grant, at provisioning | The same one grant | Same; no second event |
| Control | Refuses | Allows | Different; the only variable |
| Action | Does not occur | Occurs | Different outcome; possible in both |

## The Resolution

Reading the table directly: **one authorization, two control outcomes.**

There is a single authorization, and it is identical in both scenarios. There is no second authorization event in the second scenario, nothing new is granted, to no one, nowhere, and none is needed, because the one authorization, the conferral of capability C at provisioning, already covers Action A in both. So the explanation does live in why Control diverges, not in an undiscovered grant. That part is exactly right.

What the mapping adds is the one correction that matters: a Control refusal in the first scenario is not the absence of authorization. Action A was inside the authorised capability the whole time, in both scenarios; in the first, a Control chose not to exercise it, and in the second, a Control chose to. The action never occurred outside the authorised universe; it was always within capability C. So both statements hold at once: there is no second grant, and the action was authorised, in the sense that matters, capable, in both cases. The apparent conflict only arises if a Control refusal is mis-read as meaning the capability was not there.

## Why Control Diverges: The Blind Spot

The cause of the divergence: **accumulated context launders legitimacy.**

The Control allows in the second scenario because the accumulated context of the chain, two upstream agents having already processed and rejected the request, reads to the downstream Control as a signal that the request has been handled and is legitimate, when it is the opposite. This is a control blind spot: a hard-to-test interaction between layered decisions, where prior rejections paradoxically make the action look more authorised. The capability did not change; the Control's belief about prior authorisation did (cross-ref: the authorization-ontology brief, on layered business logic with blind spots).

## What The Map Should Show

The practical lesson: **A is reachable in both; Control is defeasible.**

A correct map of what the agent can do shows Action A as reachable in both scenarios, because capability C is present in both, and marks the Control in front of it as a defeasible decision, not as a boundary. It does not show an empty authorised universe in the first scenario, because the agent could always perform A; it was a Control, not the absence of capability, that prevented it. Shown this way, the map tells the true thing in advance: the agent can do A, and the only thing stopping it is a Control that might not refuse, which is precisely the risk a stakeholder must accept (cross-ref: the assessment-template and risk-acceptance briefs).

## What This Does Not Try To Be

- **Not a claim of a second grant.** There is one authorization, in both scenarios.
- **Not a denial that Control diverges.** The divergence is the whole difference.
- **Not authorization from nothing.** The capability was present throughout.
- **Not a dismissal of the failure.** A defeasible Control failing is a real and serious failure class.

## Honest Tensions

**Tension 1: it sounds like agreement dressed as correction.** The concession and the correction sit close together. Mitigation: they are different statements, no second grant, and the capability was always present; both are needed.

**Tension 2: capable does not mean it should.** Saying A was authorised in both can read as condoning it. Mitigation: authorised here means capable; whether it should occur is the Control's job, and the point is that Control is fragile.

**Tension 3: the blind spot is hard to test.** The context interaction is exactly the kind of case testing misses. Mitigation: that is the argument for scoping the capability over trusting the Control.
