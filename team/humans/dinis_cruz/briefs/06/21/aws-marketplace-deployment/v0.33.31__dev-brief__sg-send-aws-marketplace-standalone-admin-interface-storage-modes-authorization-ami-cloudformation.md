# SG/Vault Standalone On AWS Marketplace: Admin Interface, Boot Modes, And Packaging

**version** v0.33.31
**date** 21 June 2026
**from** Human (project lead)
**to** @Dev, Architect, Product
**type** Dev brief (executed research included)

## What This Is

The build map for the standalone SG/Vault on AWS Marketplace: **a separate admin interface and FastAPI that manages the deployment; an application that boots into a setup mode when it needs configuring; a storage-mode property of memory, disk, or S3, with the permissions each needs supplied through a least-privilege IAM role rather than keys; a two-layer authorization model of FastAPI access and usage API keys; and AWS Marketplace packaging as an AMI with a CloudFormation template for one-click deploy, a marketplace-branded vault page rather than the default, and a pricing model that is free, bring-your-own-licence, or metered, since pay-what-you-want is not a native option; Playwright and Caddy are out of scope for this first cut, with the admin interface's own routing carrying the workflows for now.** It turns the AWS Marketplace pull into a concrete deployment (cross-ref: the v0.33.28 first-customer-pull AWS Marketplace brief, the v0.33.28 run-everywhere brief, and the v0.32.7 central-key-management brief). AWS Marketplace mechanics were researched and are sourced. New contributions: **the component map, the storage and authorization models, and the marketplace packaging.**

## The Framing

What was asked: **push SG/Vault to AWS Marketplace, standalone, and map the admin interface and the components.**

The project lead: **"now that we are going to push SG/Vault to AWS Marketplace as a standalone version, we need to re-add the admin interface we had, to manage the deployment. The application starts in a mode where it needs to be configured, so there is an install mode, and the admin panel should be a separate website and a separate FastAPI to the server. It is worth revisiting the admin API we already created, it was good, it just has a lot we do not need. Let us map it out and take it from there."**

## The Admin Interface

The shape: **a separate website and FastAPI that manages the deployment.**

The admin interface is a separate site and a separate FastAPI from the vault server, responsible for managing the deployment. The existing admin API is the starting point: keep what is needed, drop the rest. The application boots into a setup mode when configuration is required, and the admin interface is where that configuration is done.

## Boot And Auto Behaviour

What happens on boot: **check for required configuration, then enter setup mode.**

The project lead: **"we need to map the auto behaviour when it boots up. Some of these actions are currently done by SG/Compute, though we should double-check, probably not, so we need to define them."** On boot the instance checks whether configuration is required and, if so, enters setup mode for the admin interface to complete. One marketplace constraint shapes this: for the launch-from-website experience, the AMI must boot and function without requiring user data at creation, so the defaults must bring it up cleanly into setup mode rather than depending on inputs.

## Storage Mode

The first boot property: **memory, disk, or S3.**

The project lead: **"we need to define whether we are running in memory, on disk, or in S3. In memory means it reboots and you lose everything. On disk means it survives reboots, and you can attach an EBS volume and use it as the file storage. S3 means we use an S3 bucket. We then need to see what permissions are needed for each."**

| Mode | Behaviour | Persistence | AWS resource | Permissions |
|------|-----------|-------------|--------------|-------------|
| Memory | Everything held in memory | Lost on reboot | None | None beyond compute |
| Disk | Files on an attached disk | Survives reboot | An attached EBS volume | Volume attach and mount; lifecycle managed by the stack |
| S3 | Files in an S3 bucket | Durable and external | An S3 bucket | Least-privilege IAM role scoped to that bucket |

The permissions point has a fixed answer from marketplace policy: the AMI must not request AWS credentials, so disk and S3 access are granted through a minimally privileged IAM role attached to the instance, provisioned by the CloudFormation template, not through keys.

## The Authorization Model

The second property: **two layers, FastAPI access and usage API keys.**

The project lead: **"there are two authorizations. One is access to the FastAPI, to be able to connect to it, which we usually enable by default. The other is the usage API keys, to actually invoke things. The user should be able to control both, because it depends on the exposure. Most likely the workflow for somebody using SG/Vault on an EC2 instance is to create a vault to send to somebody else, so the recipient's use can be anonymous, because the access token is at the API layer, but you need the API key to invoke."**

| FastAPI access | Usage API key | Result |
|----------------|---------------|--------|
| Open (default) | Not required | Anyone who reaches the API can invoke; lowest friction, highest exposure |
| Open (default) | Required | Anyone can reach the API, invoking needs a key; the natural send-to-someone default |
| Restricted | Required | Both reaching the API and invoking are gated; lowest exposure |

The send-a-vault-to-someone workflow maps to the middle row: the recipient can reach the API anonymously to receive, while creating or invoking needs the usage API key (cross-ref: the central-key-management brief).

## The AWS Marketplace Components

The packaging: **an AMI, a CloudFormation template, a product code, and a pricing model.**

- **Delivery.** A single AMI, optionally with a CloudFormation template for one-click deploy. CloudFormation lets buyers deploy without manual configuration, and can carry the IAM role, VPC, security groups, and S3 bucket the storage modes need.
- **Parameters and bootstrap.** Group and order inputs with the CloudFormation interface metadata, and use the UserData section, with comments, to bootstrap; do not hardcode AMI IDs, reference them by parameter.
- **Tracking.** A product code is assigned to the product and tracks usage and billing through the AMI.
- **Pricing.** The options are hourly, monthly, yearly, metered, BYOL, or free; metered uses the AWS Marketplace Metering Service to charge per unit. Pay-what-you-want is not a native model, so it maps to free or a low fixed price, with metered usage if charging is wanted (cross-ref: the first-customer-pull brief, where this was flagged).
- **Branding.** A marketplace-branded AMI, and a specific marketplace vault page rather than the default vault page.

## Scope For The First Cut

What is deliberately out: **no Playwright, no Caddy.**

The project lead: **"it gets confused if you add Playwright, so for now we should not. It should just be the vault, the API, and the admin interface. This one does not have Caddy, so for now we can use the admin's extra routing for the workflows."** So the first cut is vault plus API plus admin interface, with the admin's routing carrying the workflows, and Playwright and Caddy deferred.

## Blind Spots To Close

Some the project lead invited spotting:

- **TLS without Caddy.** Caddy handled HTTPS; without it, define TLS, an ACM certificate with a load balancer, or a reverse proxy, since exposing the API in the clear is not acceptable.
- **Admin auth bootstrap.** Define how the admin interface is first secured, an initial credential or token generated at setup, since the setup mode is an open door until it is.
- **Disk-mode volume lifecycle.** Define what happens to the EBS volume on stack delete, snapshot or retain, or data is lost when the stack is torn down.
- **Data durability across modes.** Memory loses everything on reboot; make that explicit to the user at setup so the choice is informed.

## Acceptance Criteria

1. The admin interface is a separate site and FastAPI that manages the deployment.
2. The application boots into setup mode when configuration is required, with no required user data at launch.
3. The storage mode is selectable as memory, disk, or S3, with the right IAM role per mode.
4. The authorization model exposes both FastAPI access and usage API keys as user-controlled options.
5. The send-to-someone workflow works with anonymous access and a key required to invoke.
6. The product ships as an AMI with a CloudFormation template for one-click deploy.
7. A marketplace-branded vault page replaces the default.
8. TLS, admin bootstrap, and volume lifecycle are defined before launch.

## What This Does Not Try To Be

- **Not the full feature set.** Playwright and Caddy are deferred.
- **Not pay-what-you-want.** Pricing maps to free, BYOL, or metered.
- **Not credential-based storage access.** Storage uses an IAM role.
- **Not the default vault page.** A marketplace page is used.
