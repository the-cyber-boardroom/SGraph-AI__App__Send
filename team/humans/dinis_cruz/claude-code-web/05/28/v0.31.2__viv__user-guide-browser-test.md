# ViV (Vault-in-Vault) — Browser Test Guide

**Audience:** you, sitting at a browser, wanting to confirm that the Phase 2 ViV plumbing actually works end-to-end with a real `SGVault` over the network.

**Why this guide exists:** the Node unit-test suite proves the relay machinery and the policy gates against *synthetic* data sources. The browser is the only place that exercises the real `SGSend` → `SGVault.open()` → server edge path. None of that is mocked; this guide walks you through driving it manually.

> Status: PROPOSED browser walkthrough. The /app and /vault pages exist (see `team/roles/librarian/reality/`). The ViV mount UI (the parent-side "Mount vault" button) is itself PROPOSED — does not exist yet. Until that ships, the steps below use the JS console to simulate the mount.

---

## 0. Prerequisites

1. Two vault keys you can both write to. Easiest: `sgit init` twice in different folders.
2. The dev environment up to date: `git pull origin dev` and visit `https://dev.send.sgraph.ai`.
3. Optional: a freshly-built local bundle if you've made changes — run `python3 scripts/build-kernel-shell-bundle.py` and serve `sgraph_ai_app_send__ui__vault/v0/...` locally.

---

## 1. Open both vaults

In two browser tabs:

```
Tab A (parent):  https://dev.send.sgraph.ai/en-gb/app#<vaultKey_A>
Tab B (child):   https://dev.send.sgraph.ai/en-gb/app#<vaultKey_B>
```

Tab A is the **parent kernel**. Tab B is just there so you have a vault that exists; the actual child kernel for Tab A will be spawned inside Tab A as a `null`-origin `srcdoc` iframe.

**Sanity check (Tab A console):**

```js
window.sgVault          // → object (the legacy facade — still there)
window.sg               // → object (the new sg.* stub on /app)
sg.app.vaultName        // → "vaultKey_A" or your label
KernelMounts            // → class (loaded by the page)
KernelBroker            // → class
KERNEL_SHELL_HTML       // → long string starting with "<!DOCTYPE html>"
```

If any of those are `undefined`, the bundle isn't loaded — check the network tab for `kernel-shell-bundle.js`.

---

## 2. Add a child vault to the parent's app.json

Edit the parent vault's `app.json` (via the /app page's app-state debug tab, or by writing the file directly through `sgVault.saveFile`) to grant the `vault.mount` capability:

```json
{
  "permissions": {
    "fs":    { "read": true, "write": ["mounts/"] },
    "vault": { "mount": ["mounts/"] }
  }
}
```

Reload Tab A. The new permissions are picked up by `AppPermissions.parsePermissions`.

> Note: the parent app does NOT need `fs.write: ["mounts/"]` per architect §4.4 — the M2 fix in v0.31.2 moved mount resolution BEFORE the parent's own `fs.write` grant check. Listed here for completeness; you can omit it.

---

## 3. Spawn the child kernel from the parent

There is no UI button for this yet (PROPOSED). From Tab A's console:

```js
// 3.1 — Build the srcdoc iframe with the KERNEL_SHELL_HTML bundle.
const iframe = document.createElement('iframe');
iframe.sandbox = 'allow-scripts';                      // null origin
iframe.srcdoc  = KERNEL_SHELL_HTML;
iframe.style   = 'display:none';
document.body.appendChild(iframe);

// 3.2 — Wait for it to load, then do the ONE window.postMessage with a port transfer.
await new Promise(r => iframe.addEventListener('load', r, { once: true }));
const cid = 'ch-test-' + Math.random().toString(36).slice(2,6);
const ch  = await SecureChannel.create(iframe, { sensitiveKey: true, cid });

// 3.3 — Send the child's secrets (vault key + token + endpoint). NEVER log these.
await ch.send('secrets', {
    vaultKey:    'vaultKey_B',
    accessToken: localStorage.getItem('sg.accessToken') || null,
    endpoint:    location.origin           // M5 fix: endpoint comes from secrets payload
}, { sensitive: true });
```

**What to look for in DevTools:**

- The `Network` tab should NOT show any request directly attributable to the iframe under Tab A's tab — but you WILL see the child making its own server calls (Edge 1, D4). This is correct: every kernel hits the server directly.
- The `Console` tab should show a `ready` event arriving back. Listen with:
  ```js
  ch.on('ready', (p) => console.log('[parent] child ready:', p));
  ```

## 4. Wire the mount and broker

```js
// 4.1 — Register the mount in the parent's mount table.
const mount = { mountId: 'm-test', prefix: 'mounts/b/', ref: 'vaultKey_B', channel: ch };
// The parent kernel's _mounts is private; for testing, push through the debug surface:
window.__app_shell._mounts.add(mount);

// 4.2 — Set broker policy to 'auto' so writes don't prompt (production default is 'ask').
window.__app_shell._broker.setPolicy('m-test', 'fs.read',  'auto');
window.__app_shell._broker.setPolicy('m-test', 'fs.write', 'auto');
```

> `window.__app_shell` is a debug handle the page exposes; if it isn't there, the page didn't expose it. PROPOSED: a `sg.vault.mount(ref)` user-facing call that does the spawn+wire+grant in one step. Until then, this manual sequence is the only path.

## 5. Run the driving case (architect pack §6)

The clinician scenario: the parent app writes a JSON file into the child vault, lists it back, reads it back.

In **Tab A** console:

```js
// 5.1 — Write into the child vault THROUGH the parent.
const data = new TextEncoder().encode(JSON.stringify({ note: 'hello from parent' }));
const w = await sg.vfs.write('mounts/b/data/reviews.json', data);
console.log('write:', w);                  // → { ok: true, size: 39, mounted: true }

// 5.2 — List the child's mounted folder.
const ls = await sg.vfs.list('mounts/b/data/');
console.log('list:', ls);                  // → entries from the child's vault

// 5.3 — Read it back.
const buf = await sg.vfs.read('mounts/b/data/reviews.json');
console.log('read:', new TextDecoder().decode(buf));
```

**What to confirm:**

- `mounted: true` on the result of write — proves it crossed the relay (M3 ensures list reports it too).
- Server tab: the **child** vault's server traffic shows the write. The **parent** vault is untouched. That's D4 in the architect pack.
- Broker log: `window.__app_shell._broker.log({ mountId: 'm-test' })` shows one entry per relayed op with `decision: 'allow'`, `result: 'ok'`.

## 6. Adversarial spot-checks

These are the ones you'll want to eyeball — the unit tests cover them, but seeing them fail in the browser is the proof:

### 6.1 — Floor still applies after relay (T6 / H1)
```js
await sg.vfs.write('mounts/b/.vault/owner.json', new Uint8Array(8)).catch(e => console.log(e.code));
// → 'EPROTECTED' from the CHILD side (this is the H1 fix — child's AppPermissions.isFloor runs)
```

### 6.2 — Child policy refuses outside its scope (T8 / two-sided gate)
Set the child vault's `app.json` to `{ permissions: { fs: { read: true, write: ['data/'] } } }`, reload, re-mount, then:
```js
await sg.vfs.write('mounts/b/elsewhere/x', new Uint8Array(8)).catch(e => console.log(e.code));
// → 'EPERM' (the child enforced its own policy — the parent's broker said 'allow', the child said 'no')
```

### 6.3 — Push failure surfaces (M1)
Kill your network (DevTools → Network → Offline), then:
```js
await sg.vfs.write('mounts/b/data/will-fail.bin', new Uint8Array(8)).catch(e => console.log(e.code));
// → 'EUNREACH' (NOT silent ok — M1 was the silent-success bug)
```

### 6.4 — Signature/cid mismatch fails closed (M6 / T11)
Open Tab C with a third vault, spawn a kernel there with the same `cid` but its own keys, and try forwarding a message between channels. The receiver's `_dispatch` drops it on the floor (you'll see `[secure-channel] dropped envelope` in the console). The `cid` check (M6 fix) catches the cross-wire case after `unpack`.

### 6.5 — Replay nonce (T11)
Capture a message in the bridge debug tab, re-deliver it via `iframe.contentWindow.postMessage(...)` (you can't easily replay over the port; this is more of a unit-test concern but the bridge tab will show the drop).

## 7. What you can NOT yet test in the browser

These are PROPOSED — do not exist:

- `sg.vault.mount(ref)` as a user-facing call (Phase 3 sub-step D)
- `sg.vault.unmount(id)` (Phase 3 sub-step E)
- The /vault page's mount list and broker log viewer (Phase 4)
- Nested mounts (a child kernel mounting a grandchild) — should work mechanically because the bootstrap is the same code, but no UI surface yet
- HUD prompt for `ask` policy — the broker currently has the policy enum but no HUD prompt wired (Phase 3 sub-step B)
- Standing-RO / Owner-secret credential tiers (Phase 5)
- Monitored-mode visibility into the child's broker (Phase 6)

## 8. Cleanup

```js
ch.close();
window.__app_shell._mounts.remove('m-test');
iframe.remove();
```

If you've been writing to a shared vault and want to roll back, `sgit log` and `sgit revert` from the CLI.

---

## 9. If something goes wrong

| Symptom | First thing to check |
|---|---|
| `EPROTO` on `ch.send('secrets', …)` | the handshake didn't complete — open the bridge debug tab and check for envelope-drop warnings |
| `ECONSENT` on a relayed write | broker policy is still `ask`; `setPolicy('m-test', 'fs.write', 'auto')` |
| `EPERM` on a write that should work | child's `app.json` doesn't grant `fs.write` for that path; OR your parent app.json's `vault.mount` doesn't cover `mounts/` |
| `EUNREACH` on a relayed op | the child's channel is down (handshake never finished, or you closed it) |
| `[secure-channel] dropped envelope EPROTO` | signature failed — usually because you reloaded one side without reloading the other (key rotation) |
| Nothing happens at all | reload Tab A; reload the iframe; check `KERNEL_SHELL_HTML` is the latest by running `test__bundle_freshness.js` |
