## A-bis. CORRECTION (v0.31.2 follow-up commit)

An earlier draft of this doc listed B1/B2/B3 as missing. **That was wrong** — closer
reading of `app-shell.js` showed they ship. This section corrects the record; the
follow-up commit also extracted the parent orchestration into a testable module and
finished the M5 fix on the parent side.

| Item | Earlier (wrong) status | Actual status |
|---|---|---|
| **B1 mount** | "not assembled" | **SHIPS** — `__sgCmdType==='vault'` → `_mountChildVault` (app-shell.js) |
| **B2 unmount** | "no implementation" | **SHIPS** — `vault.unmount` → `_unmountChildVault` |
| **B3 HUD `ask`** | "nothing wires the HUD" | **SHIPS** — `KernelBroker.mediate` → `ui.prompt` → `_brokerPromptOnHud` → `app-hud.js requestConsent` |

What WAS genuinely wrong and is now fixed in the follow-up commit:

- **M5 was half-done.** The parent's `_spawnChildChannel` now passes `endpoint:
  this._sendEndpoint()` in the `secrets` payload. Before, the child always fell back
  to the hardcoded dev URL no matter where the parent ran.
- **Parent orchestration was untested.** Extracted into `kernel-parent.js`
  (`KernelParent`: mount table + broker + relay). app-shell delegates to it and
  supplies only the DOM-coupled `spawnChannel`. `test__kernel_parent.js` (21) drives
  a real `KernelParent` against a real child kernel (`bootKernelOnPort` + synthetic
  vault) — covering relay, the two-sided gate enforced by the *real* child, the
  floor surviving the relay, and broker `auto`/`ask`/`never` policies. The only
  untested remainder is the ~15-line iframe spawn (irreducibly DOM).

So B1-B3 move from "PROPOSED" to "SHIPS, now tested." The remaining genuine gaps are
the credential model (B5 below, the real one), the audit UI (B4), and the recorded
browser end-to-end (B9).

## B. What's MISSING (PROPOSED — not in code)

### B4 — Mounts list / broker log UI — ✅ SHIPPED (follow-up commit)

**Plan:** a "Mounts" panel listing each `BrokerEntry` with edge label, op, path, credential class, decision, result.

**Shipped as:** the **🔗 Mounts** tab in the /app debug pane. `viv-mounts-view.js`
(pure view-model, 25 unit tests) + `app-debug-mounts.js` (the pane component) +
app-shell installs `window._appDebug.vivProvider` = `() => ({ mounts: kp.list(),
entries: kp.broker.log() })`. Refreshes on each relayed op (`app-debug:bridge-call`).
Browser-verified by `test__viv_browser_e2e.spec.js` (B4 case).

**Why /app, not /vault:** the broker lives in the parent kernel on /app — that's where
the data is. A /vault surface would need cross-page persistence of the log (a separate
architectural decision); deferred. The pure `VivMountsView` is page-agnostic, so a
/vault embedding later is a small follow-on.

### B5 — Per-request elevation (Phase 5 — credential tiers)

**Plan:** three tiers — `none`, `standing-ro`, `perRequest-rw`. The relay carries `credential` in payload; the child can grant one-shot writes (matches the `TestKernel._oneShotToken` in `test__kernel_relay.js`).

**Reality today:** the **envelope** passes a `credential` field through (proven in T9 of the relay test). The **parent and child kernels** don't have a policy adapter that consumes it (it's purely a synthetic in the test). No issuance UI; no token format; no token revocation.

**Effort:** large. Needs a credential schema + issuance flow + child-side consumer + the broker's `credentialClass` mapping to enforce something.

### B6 — `vault.delete` owner-secret tier

**Plan:** §4.4 lists `vault.delete` as consent-gated boolean only. Plan 03 sub-pack discusses an owner-secret tier.

**Reality today:** `AppPermissions.parsePermissions` already accepts `vault.delete: true`. No bootstrap path triggers a destructive delete; no consent flow exists.

**Effort:** medium, but mostly UX (the destructive prompt). The capability lookup is already there.

### B7 — Monitored-mode child visibility (Phase 6)

**Plan:** parent can request a read-only view of child's broker log (only for child kernels it spawned). Matrix row D in §4.7.

**Reality today:** broker log is purely local per kernel. No cross-channel exposure. No protocol message for it.

**Effort:** small protocol addition (`broker.log` as a request type on the parent→child channel) plus child-side handler that exposes its own broker log.

### B8 — Phase 0.5 operational verification

**Plan:** before nesting, prove that the existing app-shell still works under `null`-origin + parity check of `window.sgVault` facade.

**Reality today:** the parity rewrite was not done. Today the /app page loads both `window.sgVault` (legacy) and `window.sg` (stub) — both work, but the stub is bypassed for /app's first-party iframes (which still use the legacy `__sgVfs*` postMessage protocol with mount-aware routing — M2/M3 fixes in v0.31.2).

**Effort:** medium. The plan called for re-expressing `window.sgVault` over the stub; today they coexist. Coexistence is fine for now, but the cleanup is owed.

### B9 — Phase 2 §7 browser end-to-end

**Plan:** a full SGVault-backed browser walkthrough of the driving case (clinician).

**Reality today:** synthetic unit tests pass; the browser walk has only been done by hand against the new bundle (no recorded run). The user guide in `v0.31.2__viv__user-guide-browser-test.md` is the step-by-step; a recorded Playwright run is still PROPOSED.

**Effort:** small if scripted via Playwright; needs two reachable dev vaults.

### B10 — Real credential model (the security-critical one)

**Plan:** architect pack §3 "cleaner future variant" — Kernel-A holds the child's
credentials and delivers them to the spawning parent via `MessagePort` transfer; the
parent never persists child vault keys at rest.

**Reality today:** `_resolveChildCredentials` (app-shell.js) is a **trial stub that
reads child vault keys from a plaintext `clinic.json` file inside the *parent*
vault**. That stores one vault's keys as a readable file in another vault — exactly
the kind of key-at-rest the zero-knowledge model is supposed to avoid. Functional for
a demo; not acceptable for production. The `KernelParent` seam now isolates this:
`resolveCredentials` is injected, so swapping the stub for the port-transfer model is
a contained change that the parent test can cover.

**Effort:** medium-large. Needs the Kernel-A holder, the port-transfer handshake, and
removal of the plaintext file path. **This is the highest-risk remaining gap** — flag
to AppSec before any real-data pilot.

## C. Bugs identified and FIXED in v0.31.2

For completeness — these were holes between the v2 plan and the shipped code, surfaced by the audit at the start of this session, fixed in this commit:

| Tag | Issue | File(s) fixed |
|---|---|---|
| **H1** | Child kernel `vfs.*` handlers skipped `AppPermissions.isFloor` / `can` — the entire "two-sided gate" was missing in production code | `kernel-app-handlers.js` (new), `scripts/build-kernel-shell-bundle.py` |
| **M1** | `vault.push()` errors silently swallowed in the child kernel — silent data-loss on relayed write | `kernel-app-handlers.js` `_safePush` raises EUNREACH |
| **M2** | Parent applied its own `fs.write` grant to the `mounts/*` path BEFORE resolving the mount — relayed writes spuriously EPERM'd | `app-shell.js` (reorder mount-resolve before grant check) |
| **M3** | `__sgVfsListReq` had no mount-resolve+relay branch (read and write did) | `app-shell.js` (list relay added) |
| **M4** | Bootstrap (`KERNEL_BOOTSTRAP_JS`) was untested — relay test used a hand-rolled TestKernel that did NOT share code with the shipped child | `kernel-bootstrap.js` (new, testable) |
| **M5** | Endpoint hardcoded to `https://dev.send.sgraph.ai` | `kernel-bootstrap.js` reads endpoint from secrets payload |
| **M6** | `SecureChannel._dispatch` accepted any signature-valid envelope without checking it was addressed to THIS cid | `secure-channel.js` (cid check after unpack) |
| **L1** | `generateSignKeypair` had a dead then/catch fallback chain (only the catch branch ever ran) | `secure-channel-envelope.js` (simplified) |
| **L3** | Nothing checked `kernel-shell-bundle.js` was current vs. its sources — could ship stale bundle silently | `test__bundle_freshness.js` (new), `--stdout` flag on build script |
| **L4** | `_preHandshakeBuf` grew unbounded for unknown pre-handshake message types | `secure-channel.js` (bounded to 8 types × 8 entries) |

**Not fixed (L2):** `Envelope._canonicalParse` treats any `{__u8: "<string>"}` object as bytes. A legitimate JSON shaped that way would round-trip incorrectly. Edge case; deferred. The fix would be to add a tag byte (`{__u8b64: "..."}`) or a per-side marker.
