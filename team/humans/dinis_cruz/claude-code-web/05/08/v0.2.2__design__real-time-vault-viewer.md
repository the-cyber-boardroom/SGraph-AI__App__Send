# Real-Time Vault Viewer — Design Document

**Audience:** SGit team (Developer + Architect)
**Vault UI version:** v0.2.2
**Date:** 2026-05-08
**Status:** Design proposal — not yet implemented

---

## 1. Why This Exists: The Problem With the Current Model

### What "Push ↑7" actually means

The current vault UI implements a **two-ref git model**:

| Ref | File ID derivation | Meaning |
|-----|-------------------|---------|
| Named ref (`ref-pid-muw-*`) | `sg-vault-v1:file-id:ref-id:named:${vaultId}` | Published HEAD — what the world sees |
| Clone ref (`ref-pid-snw-*`) | `sg-vault-v1:file-id:branch-id:clone:web-ui:${vaultId}` | Working HEAD — local browser state |

On page open, `SGVault.open()` reads both refs. `_headCommitId` tracks the clone ref; `_namedHeadId` tracks the named ref. Every `_commit()` advances only the clone ref. `push()` advances the named ref to match clone.

**Result:** The browser maintains its own independent working branch. Every file edit (rename, upload, save) is a commit to the clone ref that is NOT on the named ref — hence "Push ↑7" after you just pulled. The seven commits were made during the current session (file edits, vault-settings changes, etc.) and have never been pushed. The `sgit pull` from CLI only advanced the named ref on the server; the browser's clone ref had already diverged from it.

### The architectural mismatch

This two-ref model is designed for **offline-capable collaborative editing**: you accumulate local commits, then push/pull/merge. That's the right model for the CLI (`sgit`), which genuinely needs a working branch.

The web vault viewer is a different use case. Users open the vault to **view and lightly edit files**, not to stage a batch of commits before publishing. The right mental model is a **live read/write view of the named branch**, not a local checkout.

Specific problems with the current design:
- Every rename or file save creates a clone-ref commit that needs manual pushing
- "Push ↑7" is confusing and misleading when the user hasn't consciously made 7 changes
- `sgit pull` from CLI does not advance the browser's clone ref — the browser is always "ahead" or "behind" by default
- `getBehindCount()` makes a live API call (`GET named-ref`) on every sync-state refresh, but it's the only liveness signal — file reads are otherwise fully stale from the open-time snapshot
- The clone ref is a source of truth that competes with the named ref for no real benefit in the web viewer case

---

## 2. Proposed Model: Named-Ref-Only Viewer

### Core principle

The web vault viewer should operate entirely on the **named ref**. There is no separate working branch:

- **Read** = named HEAD at open time, refreshed on demand
- **Write** = commit directly to named ref (named HEAD advances atomically)
- **Stale check** = one GET to named ref, compare with in-memory `_namedHeadId`

The clone ref (`ref-pid-snw-*`) is not read, not written, not counted. It remains on the server as-is for CLI use.

### State model

```
_namedHeadId     — the commit ID currently in memory (named ref at last sync)
_headCommitId    — removed (or aliased to _namedHeadId — same thing now)
_lastRefCheck    — timestamp of last named-ref GET (for staleness budget)
_refCheckBudgetMs — 120_000 (2 min default — time between passive ref checks)
```

`ahead` and `behind` counters are removed from the UI. There is nothing to push or pull as a manual operation — it happens automatically.

## 3. API Request Inventory

All requests use the SG/Send REST API. Base URL: `https://send.sgraph.ai` (or configured endpoint).

### Auth headers

| Header | When required |
|--------|--------------|
| `x-sgraph-vault-write-key` | Any PUT/DELETE/batch-write |
| `x-sgraph-access-token` | Optional; not required for vault object reads |

### Object ID scheme

- Content-addressed blob: `obj-cas-imm-{SHA256(ciphertext)[:12]}`
- Ref file: `bare/refs/ref-pid-muw-{HMAC[:12]}` (named), `bare/refs/ref-pid-snw-{HMAC[:12]}` (clone)
- Index: `bare/indexes/idx-pid-muw-{HMAC[:12]}`
- Data objects: `bare/data/{objectId}`

## 4. Operation-by-Operation Request Breakdown

### 4.1 Page Open ("headless clone")

**Goal:** Get the tree from the current named HEAD, fast.

Equivalent to `sgit clone` in headless mode — read the minimum set of objects to render the root file list.

#### Step 1 — Resolve named HEAD

```
GET /api/vault/read/{vaultId}/bare/refs/ref-pid-muw-{HMAC[:12]}
← encrypted JSON: { "commit_id": "obj-cas-imm-..." }
```

Decrypt → `_namedHeadId = commitId`. Record `_lastRefCheck = Date.now()`.

**No clone ref read.** We don't care about `ref-pid-snw-*`.

#### Step 2 — Load commit object

```
GET /api/vault/read/{vaultId}/bare/data/obj-cas-imm-{commitId}
← encrypted commit_v2 JSON
```

Decrypt → `{ schema, parents, tree_id, timestamp_ms, message_enc }`.

**Cache:** Immutable objects (`-imm-`) are cached in the browser Cache API (`sg-vault-blocks`). Subsequent opens of the same vault skip this request if the commit is already cached.

#### Step 3 — Load root tree object

```
GET /api/vault/read/{vaultId}/bare/data/obj-cas-imm-{tree_id}
← encrypted tree_v1 JSON
```

Decrypt → `{ schema, entries: [ { name_enc, size_enc, content_hash_enc, blob_id?, tree_id? } ] }`.

For each entry: decrypt `name_enc` → file name. Decrypt `size_enc` → size. Sub-folder entries have `tree_id` set and `blob_id: null` — **not loaded yet** (lazy).

**Cache:** Same Cache API. Already-seen tree objects load instantly.

#### Step 4 — (Optional) Load branch index

```
GET /api/vault/read/{vaultId}/bare/indexes/idx-pid-muw-{HMAC[:12]}
← encrypted branch_index_v1 JSON
```

Only needed if the UI wants to display branch metadata. For the real-time viewer this can be skipped entirely on open.

**Summary — page open (cold, no cache):**

| # | Method | Path | What |
|---|--------|------|------|
| 1 | GET | `.../bare/refs/ref-pid-muw-{HMAC}` | Resolve named HEAD |
| 2 | GET | `.../bare/data/{commitId}` | Load commit object |
| 3 | GET | `.../bare/data/{rootTreeId}` | Load root tree entries |

**3 sequential GETs.** With cache hits on commit+tree (common for repeated opens), it reduces to **1 GET** (just the ref, which is intentionally not cached as it changes).

---

### 4.2 Load Subtree (on-demand folder expand)

**Goal:** Expand a lazy folder node without loading any sibling folders.

The root tree gave us `tree_id` for each sub-folder. On first expand:

```
GET /api/vault/read/{vaultId}/bare/data/obj-cas-imm-{subTree_id}
← encrypted tree_v1 JSON
```

Decrypt → entries for this folder level. Mark the node `_loaded: true`. Cache hit likely if the same commit was previously browsed.

**1 GET per unexpanded folder.** Folders that were already loaded (expanded in this session or cached from a previous open) cost 0 additional requests.

For deep trees, multiple folders can be expanded in one round if the client knows the `tree_id`s in advance:

```
POST /api/vault/batch/{vaultId}
Body: [
  { "op": "read", "file_id": "bare/data/{treeId1}" },
  { "op": "read", "file_id": "bare/data/{treeId2}" },
  ...
]
← array of encrypted objects
```

**1 POST (batch) per set of folders being expanded simultaneously** — e.g., when opening a deep-link path.

---

### 4.3 Load File Content (user clicks a file)

**Goal:** Decrypt and display the file bytes.

The tree entry has `blob_id` (content-addressed). The file bytes are encrypted as a single blob:

#### Option A — Direct read (small files, most common)

```
GET /api/vault/read/{vaultId}/bare/data/obj-cas-imm-{blob_id}
← encrypted raw bytes (AES-256-GCM)
```

Decrypt with `_readKey` → raw file bytes.

**1 GET.** Cache hit likely for previously-opened files in the same session.

#### Option B — Presigned URL (large files, server redirects)

For objects above a threshold the server may return a presigned S3 redirect instead of inline bytes. The client hits the same endpoint and follows the redirect transparently.

#### Stale check (if file was last accessed > `_refCheckBudgetMs` ago)

Before decrypting, optionally check if the named ref has advanced since last check (see section 4.5). If it has, refresh the tree first, then load the file from the new tree.

**Summary — load file:**

| # | Method | Path | What |
|---|--------|------|------|
| 1 | GET | `.../bare/data/{blob_id}` | File ciphertext |

**1 GET** (or 0 if cached from earlier in session).

---

### 4.4 Create File + Commit

**Goal:** Store a new file and advance the named HEAD atomically.

This is the key difference from the current model: commit goes directly to the named ref in one operation, with no separate push step.

#### Step 1 — Encrypt file content

Client-side only. `AES-256-GCM encrypt(fileBytes, _readKey)` → `ciphertext`.

#### Step 2 — Derive object ID

`SHA256(ciphertext)[:12]` → `obj-cas-imm-{hash}`. **No API call.**

#### Step 3 — Store blob

```
PUT /api/vault/write/{vaultId}/bare/data/obj-cas-imm-{hash}
Headers: x-sgraph-vault-write-key: {_writeKey}
Body: raw ciphertext bytes
```

Content-addressed = safe to retry; idempotent if object already exists.

#### Step 4 — Build and store tree objects

For each dirty folder (the folder receiving the new file + all ancestors):

- Encrypt each entry field (`name_enc`, `size_enc`, `content_hash_enc`)
- Assemble `tree_v1` JSON
- Encrypt the tree JSON
- Derive tree object ID from `SHA256(ciphertext)[:12]`

All tree objects can be batched:

```
POST /api/vault/batch/{vaultId}
Body: [
  { "op": "write", "file_id": "bare/data/{treeObjId1}", "data": "base64..." },
  { "op": "write", "file_id": "bare/data/{treeObjId2}", "data": "base64..." },
  ...up to 50 ops per request
]
```

#### Step 5 — Create and store commit object

Encrypt `commit_v2` JSON `{ parents: [_namedHeadId], tree_id, timestamp_ms, message_enc }` → derive commit ID from SHA256.

```
PUT /api/vault/write/{vaultId}/bare/data/obj-cas-imm-{commitId}
Headers: x-sgraph-vault-write-key: {_writeKey}
Body: encrypted commit JSON
```

Or include in the Step 4 batch if within the 50-op limit.

#### Step 6 — Advance named ref

```
PUT /api/vault/write/{vaultId}/bare/refs/ref-pid-muw-{HMAC}
Headers: x-sgraph-vault-write-key: {_writeKey}
Body: encrypted JSON: { "commit_id": "{newCommitId}" }
```

Update `_namedHeadId = newCommitId`. Record `_lastRefCheck = Date.now()`.

**No clone ref write.** No push step. The commit is immediately "published".

**Summary — create file + commit (typical 1-level deep file):**

| # | Method | Path | What |
|---|--------|------|------|
| 1 | PUT | `.../bare/data/{blob_id}` | File ciphertext |
| 2 | POST (batch) | `.../batch/{vaultId}` | Tree objects (2–5 typically) + commit object |
| 3 | PUT | `.../bare/refs/ref-pid-muw-{HMAC}` | Advance named HEAD |

**3 requests** (the batch collapses all object writes into one). For deep trees with many dirty ancestors, more tree objects batch into Step 2 but it remains 3 network round-trips.

---

### 4.5 Rename Vault (update .vault-settings + commit)

**Goal:** Update `vault_name` in `.vault-settings.json`, create a new commit.

`.vault-settings.json` is stored as a blob in every commit tree (not a separate ref file).

#### Step 1 — Encrypt new settings

`JSON.stringify(newSettings)` → encrypt → derive blob ID. No API call.

#### Step 2 — Batch write: settings blob + updated root tree + commit

```
POST /api/vault/batch/{vaultId}
Body: [
  { "op": "write", "file_id": "bare/data/{settingsBlobId}", "data": "..." },
  { "op": "write", "file_id": "bare/data/{newRootTreeId}",  "data": "..." },
  { "op": "write", "file_id": "bare/data/{newCommitId}",    "data": "..." }
]
```

#### Step 3 — Advance named ref

```
PUT /api/vault/write/{vaultId}/bare/refs/ref-pid-muw-{HMAC}
```

**Summary:** 2 requests (1 batch + 1 ref write). Identical pattern to any other commit.

---

### 4.6 Delete File + Commit

**Goal:** Remove a file from the tree and create a commit recording the deletion.

File blobs are content-addressed and immutable — they are **never explicitly deleted** from the object store (doing so would invalidate history). The commit simply omits the entry.

#### Step 1 — Update in-memory tree

Remove the entry. Mark the folder and all ancestors dirty. No API call.

#### Step 2 — Batch write: updated tree objects + commit

```
POST /api/vault/batch/{vaultId}
Body: [
  { "op": "write", "file_id": "bare/data/{updatedFolderTreeId}", "data": "..." },
  { "op": "write", "file_id": "bare/data/{updatedRootTreeId}",   "data": "..." },
  { "op": "write", "file_id": "bare/data/{newCommitId}",         "data": "..." }
]
```

#### Step 3 — Advance named ref

```
PUT /api/vault/write/{vaultId}/bare/refs/ref-pid-muw-{HMAC}
```

**Summary:** 2 requests. No blob deletion request — deleted files remain in the object store (accessible via history). If the storage policy requires physical deletion, a separate `DELETE /api/vault/delete/{vaultId}/{blob_id}` can be issued asynchronously, but this should not be in the commit path.

---

### 4.7 Passive Stale Check ("is my tree current?")

**Goal:** Detect that a collaborator (or CLI) pushed commits since we last loaded, without polling.

The strategy is **demand-driven staleness**, not polling:

1. Record `_lastRefCheck = Date.now()` whenever we successfully read or write the named ref.
2. When the user **clicks a file** (or expands a folder), check if `Date.now() - _lastRefCheck > _refCheckBudgetMs` (default: 2 minutes).
3. If over budget:
   ```
   GET /api/vault/read/{vaultId}/bare/refs/ref-pid-muw-{HMAC}
   ```
   Compare decrypted `commit_id` with `_namedHeadId`.
   - **Same:** Update `_lastRefCheck`. Serve the file from existing in-memory tree.
   - **Different:** Reload tree from new commit (see 4.2 pull flow below), then serve the file.

This is **1 GET per 2 minutes of activity**, not a constant poll. The check is transparent to the user — the file click triggers it, and the file opens after the check completes (typically < 200ms).

**Summary — stale check:**

| Case | Requests |
|------|---------|
| Within budget | 0 |
| Over budget, no change | 1 GET (ref only) |
| Over budget, changed | 1 GET (ref) + N GETs (new commit + tree objects, mostly cached) |

---

### 4.8 Pull / Refresh (explicit user action or auto-triggered)

**Goal:** Advance `_namedHeadId` to the current server named HEAD and reload the in-memory tree.

In the real-time viewer model, "pull" is just "reload from named HEAD". There is no merge step because there is no divergent working branch.

#### Step 1 — Read named ref

```
GET /api/vault/read/{vaultId}/bare/refs/ref-pid-muw-{HMAC}
← { "commit_id": "..." }
```

If commit_id === `_namedHeadId`: already current, done (0 further requests).

#### Step 2 — Load new commit

```
GET /api/vault/read/{vaultId}/bare/data/{newCommitId}
← encrypted commit_v2
```

Likely cached if a collaborator pushed this commit recently and the client has previously seen it via the stale check. In the worst case (cold cache): 1 additional GET.

#### Step 3 — Load root tree

```
GET /api/vault/read/{vaultId}/bare/data/{newRootTreeId}
```

Again, likely cached for files that haven't changed.

#### Step 4 — Reconcile lazy tree

Sub-folder nodes that have not changed (same `tree_id` as before) remain lazy. Only the new or changed folder nodes need new GETs — and those will be lazy until expanded.

**The tree diff is implicit:** the content-addressed IDs tell us what changed without diffing. Any sub-tree whose `tree_id` changed needs to be reloaded on next expand; unchanged sub-trees serve from cache immediately.

**Summary — pull/refresh:**

| # | Method | Path | What |
|---|--------|------|------|
| 1 | GET | `.../bare/refs/ref-pid-muw-{HMAC}` | Check named HEAD |
| 2 | GET | `.../bare/data/{newCommitId}` | New commit (often cached) |
| 3 | GET | `.../bare/data/{newRootTreeId}` | New root tree (often cached) |

**1–3 GETs**, typically 1 for in-session refreshes where objects are cached.

## 5. What Changes in the Implementation

### Remove (or ignore)

| Current thing | Why removed |
|--------------|-------------|
| `_headCommitId` (as separate ref) | Replaced by `_namedHeadId` — they are the same |
| Clone ref (`ref-pid-snw-*`) | Not written by web viewer in real-time mode |
| `push()` in the web UI flow | Commits go directly to named ref |
| `pull()` refusal when ahead | No separate ahead state; pull is always safe |
| `getAheadCount()` in UI | No unpushed commits; UI shows nothing |
| `getBehindCount()` on a timer | Replaced by demand-driven stale check |
| "Push ↑N" button | Removed — redundant in real-time mode |
| `_refreshSyncState()` on open | Replaced by `_lastRefCheck` timestamp |

### Keep unchanged

| Component | Notes |
|-----------|-------|
| `_commit()` internals | Same object creation/batching logic; just writes to named ref directly |
| `_objectStore.batchLoad()` | Same batch GET behaviour |
| Browser Cache API (`sg-vault-blocks`) | Same immutable object caching |
| Lazy folder loading | Same `_tree_id` tracking, same on-demand expand |
| `_buildTreeEntries()` / `_createTree()` | Same tree serialisation |
| Encryption / decryption | Unchanged |
| `sgit` CLI refs | CLI continues to use `ref-pid-snw-*` for its working branch |

### Minimal change surface

The key change is in `_commit()`: instead of writing to `_cloneRefFileId`, it writes to `_refFileId` (named ref). The `push()` step is eliminated. `_namedHeadId` is updated in-place after each commit.

```javascript
// Current (two-ref model):
async _commit(message) {
    ...
    await this._refManager.writeRef(this._cloneRefFileId, commitId);  // clone ref only
    this._headCommitId = commitId;
    // named ref still behind — requires explicit push()
}

// Real-time model:
async _commit(message) {
    ...
    await this._refManager.writeRef(this._refFileId, commitId);  // named ref directly
    this._namedHeadId = commitId;
    this._lastRefCheck = Date.now();
}
```

## 6. Concurrency and Multi-Client Safety

The named ref is a **last-writer-wins** store. Two browser sessions or a CLI + browser making concurrent commits will result in one overwriting the other's named ref.

This is **acceptable for the web viewer use case** because:

1. The web viewer is typically single-user (one person has the write key in their browser session)
2. CLI (`sgit`) operations still use the clone ref — they don't advance the named ref unless the user explicitly runs `sgit push`
3. The stale check (section 4.7) will detect any external advance to the named ref before the user makes their next write

If concurrent writes are a concern (e.g., two browser tabs), the stale check should be triggered immediately before every commit (not just on file access). This adds 1 GET per commit but prevents blind overwrites:

```
Before commit:
  GET named ref → if changed since _namedHeadId → reload tree → then proceed
```

This is still only 1 extra GET per write operation, not a polling loop.

## 7. UI Changes

### Remove
- **Push ↑N button** — gone entirely in real-time mode
- **Pull / Sync button** — replaced by a subtle "Refresh" that triggers an explicit stale check + tree reload
- **Ahead/behind counter** — no longer meaningful

### Add
- **"Saved ✓" indicator** — brief flash after every commit succeeds (replaces the push workflow)
- **"Refreshed from cloud" toast** — when stale check detects a new commit and the tree reloads
- **(Optional) Last-synced timestamp** — "Last checked 2 min ago" in the header or status bar

### Keep
- **Upload Files** — unchanged
- **Debug** — unchanged
- **Settings** — unchanged (vault rename still triggers a commit, just directly to named ref now)

---

## 8. Backward Compatibility With CLI

The `ref-pid-snw-*` clone ref is **not touched** by the real-time web viewer. The CLI (`sgit`) continues to use it as before. The only change is that the web viewer no longer reads or writes it.

When the CLI does `sgit push`, it advances the named ref. The browser detects this on the next stale check and reloads. No protocol change on the CLI side.

If the CLI has unpushed commits (clone ref ahead of named ref), the web viewer is unaware of them — it only sees the named ref. This is correct behaviour for the "live view of the published branch" model.

## 9. Request Count Summary

| Operation | Current model (GETs + writes) | Real-time model (GETs + writes) |
|-----------|-------------------------------|----------------------------------|
| Page open (cold) | 3 GETs (named ref + clone ref + commit + tree) | 3 GETs (named ref + commit + tree) |
| Page open (warm cache) | 2 GETs (both refs — not cached) | 1 GET (named ref only) |
| Load file (cached) | 0 GETs | 0 GETs |
| Load file (first access) | 1 GET | 1 GET |
| Load file (stale check due) | 1 GET (ref only, no change) | 1 GET (ref only) |
| Create file + commit | 3 requests (blob + batch + clone-ref) + push later (named-ref) | 3 requests (blob + batch + named-ref) |
| Delete file + commit | 2 requests + push later | 2 requests |
| Rename vault + commit | 2 requests + push later | 2 requests |
| Explicit refresh | 1–3 GETs | 1–3 GETs |
| Passive sync check | 1 GET / 2 min (getBehindCount polls named ref) | 1 GET / 2 min (demand-driven, same) |
| **Push** | 1 PUT (after manual click) | **eliminated** |
| Ahead count | N GETs (BFS commit walk) | **eliminated** |
| Behind count | 1 GET (named ref) + N GETs (commit walk) | folded into stale check |

The real-time model is **strictly fewer requests** across every operation. The biggest win is eliminating the clone ref read on page open and the entire push/ahead-count machinery.
