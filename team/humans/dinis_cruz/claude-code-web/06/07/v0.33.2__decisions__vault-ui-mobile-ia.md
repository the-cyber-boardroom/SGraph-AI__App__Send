## The "zoom-out reveals desktop" principle (NEW — critical)

Dinis's direction:

> *"The user is able to scale out (i.e. zoom out) on the mobile, where the smaller it gets the more is exposed, until the full desktop mode is visible (ok if very small fonts). Basically we need to support the 'desktop model' by zooming out."*

Applied to both phone and tablet:
- **Phone (≤ 390 px wide CSS layout):** show phone chrome.
- **Phone, zoomed out:** progressively reveal tablet then desktop layout — even if fonts get unreadably small at the extreme. The user controls the trade-off.
- **Tablet (391-1024 px):** show tablet chrome.
- **Tablet, zoomed out:** reveal desktop layout.
- **Desktop (≥ 1025 px):** show desktop chrome.

### What this means technically (for Dev to confirm in implementation)

Pinch-zoom on mobile changes the **visual viewport** but not the **layout viewport** — so CSS `@media (max-width: 390px)` rules normally **don't** fire when the user zooms out. To make zoom-out actually reveal desktop, we have options:

1. **Wider layout viewport + initial-scale<1** — set `<meta name="viewport" content="width=1280, initial-scale=…">` so the page always lays out at 1280 px and the phone starts zoomed out. Phone chrome then becomes a `@media (max-width: 390px)` overlay that hides itself as the user zooms out. (Closest to "desktop is the truth, mobile is a skin".)
2. **Manual "desktop view" toggle** — keep `width=device-width` by default but expose a button that swaps the viewport meta tag to a wider value. Cheap, but it's a toggle not a continuous gesture.
3. **`visualViewport` + JS-driven layout** — observe `window.visualViewport.scale` and dynamically swap stylesheets / classes as the user pinches. Most flexible, most fragile.
4. **Container queries** — use `@container` instead of `@media` so each section reflows based on its own width. Doesn't fully solve zoom-out, but composes well with option 1.

**Recommendation for Phase A:** pick option 1. It's the cleanest mapping to Dinis's mental model ("desktop is the canonical model, mobile is a skin you can shed by zooming out"), and Phase A is mostly CSS so we can experiment quickly.

**Verify with Dinis before locking in.** This is a non-obvious choice and the wrong one will undo all the Phase A work.

## Phase A — what to ship as v0.1.5

CSS-only / mechanical refactor. No `<sg-layout>` change yet. No new components.

### Files to touch

- `sgraph_ai_app_send__ui__vault/v0/v0.1/v0.1.5/_common/js/components/vault-shell/vault-shell.js` (clone from v0.1.4, edit the `static get styles()` block lines 1545-2148)
- `sgraph_ai_app_send__ui__vault/v0/v0.1/v0.1.5/en-gb/index.html` (viewport meta change if option 1 above is chosen)
- `sgraph_ai_app_send__ui__vault/v0/v0.1/v0.1.5/_common/css/design-tokens.css` (add `--touch-target: 44px`, possibly add a mobile-spacing remap)

### Concrete changes

1. **Viewport meta** — switch from `width=device-width, initial-scale=1` to a strategy that supports zoom-out-to-desktop. Confirm choice with Dinis before changing.
2. **Header** — `flex-wrap: wrap` on `.vs-header-right`; consolidate the "raw", version, Read-only badge into an overflow `⋮` menu under 600 px.
3. **Auth banner** — under 600 px, stack vertically (message row, then input + Set Key row); remove `white-space: nowrap`; bump input height to `var(--touch-target)`.
4. **Settings panel** — under 600 px: `max-width: 100%`, `.vs-settings-key-row { flex-direction: column; }` so input is full-width and button sits below.
5. **Per-file action bar** (`vault-shell.js:449-526`) — **move inline `style.cssText` into named classes first** (mechanical refactor, no behaviour change), then under 600 px collapse Rename / Delete / raw into a `⋮` overflow.
6. **Sidebar nav** — under 600 px: hide `.vs-nav`, render a hamburger button in the header that slides the nav in as a drawer. (Keep nav DOM intact so zooming out exposes the original layout.)
7. **Tap targets** — every button/link in the shell gets `min-height: var(--touch-target)` and `min-width: var(--touch-target)` under 600 px.
8. **Inline action bars (rename / confirm)** — under 600 px: wrap to two rows.
9. **SGit and Settings views** — `padding: var(--space-2)` instead of `--space-4`; tables get `overflow-x: auto` with `-webkit-overflow-scrolling: touch`.

### Out of scope for Phase A (deferred to Phase B / v0.1.6)

- `<sg-layout>` mobile reconfiguration (single-column tab stack).
- Bottom-tab bar / new mobile chrome.
- Sheet-style modals / app-like visual treatment.
- QR-code vault-key entry on `<vault-entry>`.
- Touch drag-and-drop for the tree view.

### Acceptance criteria for Phase A

- At 390 px wide (iPhone): header doesn't horizontally overflow; auth banner fits; settings inputs aren't clipped; every tap target ≥ 44 px.
- At 390 px zoomed-out to ~50%: desktop layout is visible (modulo small fonts) without horizontal scroll past the natural desktop width.
- At 1280 px+: no visual regression vs v0.1.4.
- No new failing unit/integration tests. E2E tests that assert pixel positions may need updating — that's expected and a "good failure".

## Phase B+ — what's deferred to v0.1.6 and later

Listed for context, not for this session:

- `<sg-layout>` reconfiguration: on `matchMedia('(max-width: 600px)')`, call `setLayout()` with a single-column tab stack instead of a 0.20/0.80 row split. Unlock the Files tab so users can give the preview the whole screen.
- New mobile chrome: 44 px top app-bar (drawer toggle + brand + ⋮) + 56 px bottom tab bar (Files / Recent / Upload).
- App-like visual treatment: sheet-style modals (auth, share, settings) sliding up from bottom; rounded cards; hairline rules.
- **QR-code vault-key entry** on the entry screen. Camera permission flow needed. May want a small `<vault-qr>` component that wraps the BarcodeDetector API + a polyfill (e.g. jsQR) for Safari.
- Tablet layout (391-1024 px): collapsible files drawer + preview + swipeable tabs.
- Touch DnD for tree view (long-press → drag).
- Touch resize handles on `<sg-layout>` if we decide to allow split-pane on tablet (upstream `dev.tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js`).

## Design system additions needed

- `--touch-target: 44px` token.
- Optional mobile spacing remap: `--space-mobile-3: 8px`, `--space-mobile-4: 12px` so phone chrome can systematically claw back ~30 px of horizontal room.
- An `app-like` modifier on `.vs-settings-section` and friends (rounded corners + drop shadow) for the v0.1.6 visual pass.
