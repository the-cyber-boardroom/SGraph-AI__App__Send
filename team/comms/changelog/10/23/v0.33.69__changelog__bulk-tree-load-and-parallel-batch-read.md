# Changelog: opening a big vault — bulk sub-tree loading (web) and parallel batch reads (server)

**version** v0.33.69 · **date** 2026-10-23 · **from** Dev (Explorer) · **surfaces** `sgraph_ai_app_send__ui__vault/v0/v0.2/v0.2.3` (sg-vault library, data source, vault shell, kernel bundle) and `Service__Vault__Pointer.batch_read` (user Lambda)

## The problem

Opening the PHP source-watch vault (23 root folders, 9,682 folders, 24,866 files) in the browser made 7,843 requests and took about ten minutes: the shells expand every sub-tree on open, and `VaultDataSource.loadAllSubTrees` did that one folder at a time with one `GET /api/vault/read/…` per tree object. The sgit CLI solved the same walk in 0.18.0 (batch reads per level, 16 parallel chunks); this brings the browser to the same technique.

## What changed

| Layer | Before | After |
|---|---|---|
| `SGVault.loadAllSubTrees()` (new, `sg-vault--folder-ops.js`) | — (recursive per-folder GETs in the data source) | a streaming tree walk: a pool of workers keeps up to 16 batch POSTs in flight; each takes up to 50 pending tree ids, fetches them in one `POST /api/vault/batch`, decrypts in parallel, inserts the children and queues the folders it found; a shared tree id is fetched once; progress callback per chunk |
| `SGVaultObjectStore.batchLoad()` | sequential 50-id chunks | bounded fan-out (16), a refused chunk split in two down to a single GET (the CLI's 502 rule), results matched by `file_id` |
| `VaultDataSource.loadAllSubTrees()` | recursive walk | delegates to the vault's bulk loader (recursive walk kept as fallback for fakes) |
| `SGVault._loadAllSubTreesInMemory()` (merge) | recursive | bulk loader |
| vault shell | "Loading vault files…" | live count: "Loading vault files… 3,366 folders (2,819 more)" |
| `Service__Vault__Pointer.batch_read` | read the backend one object at a time | `ThreadPoolExecutor(16)` over the operations, results in request order |

## Measured on the real vault (dev API, from the sandbox)

| Open + load all sub-trees | requests | time |
|---|---|---|
| before (one GET per folder) | 7,843 in the browser | ~650 s (screenshot); the sandbox run had not finished after 25 min |
| bulk, level by level, 8 in flight | 196 POSTs | 56 s |
| bulk, streaming, 16 in flight, 50 per POST | 204 POSTs | **24 s** |
| same with 100 per POST | 103 POSTs | 27 s (no gain: the server's per-object read was the floor) |

A 50-object batch took about 1.6 s on the server because objects were read from S3 one at a time. With the parallel `batch_read` that floor drops to a few hundred milliseconds per batch, which is the next measurement to take once the Lambda is deployed. Second opens of the same vault read trees from the immutable block cache and make no tree requests at all.

## Test impact

**Should break if reverted:** `tests/unit/vault_ui/loader/test__bulk_subtree_load.js` (14: batching, 16 in flight, split-on-refusal, equivalence with the serial walk, streaming keeps workers alive), `test__batch_read__many_files__parallel_keeps_order` in `tests/unit/lambda__user/service/test_Service__Vault__Pointer.py`, `test__bundle_freshness.js`.

**Should not break:** every other vault unit suite (`npm run test:vault-unit`, all passing), the Playwright e2e suite, `tests/integration/vault_ui/cli/test__sgit_cli_parity.py` (passes against the parallel batch read). Note: `tests/unit/lambda__user/fast_api/routes/test_Routes__Vault__Pointer.py` has 46 failures in this sandbox with and without these changes (environmental, pre-existing).

## Not done (deliberately)

- **Pack mode** (sgit-ai 0.24.0, zip per push): out of scope per Dinis; the browser does not read packs.
- **Progressive rendering**: the Browse view still waits for the full walk. Rendering the first two levels and filling in the rest in the background is the next UX step if 24 s is still too long for the largest vaults.
