# Changelog — append lanes over declared mounts; `sg.vault.notify` implemented

**date** 7 September 2026
**from** Dev (Explorer)
**builds on** `c579217c` declared mounts + `97aff102` composite write refusal (vault-web branch, merged here)
**affects** vault UI bridge (`app-shell.js`), new `mount-lanes.js`, `en-gb/app/index.html`, `AUTHORING.md`
**server/API changes** none

---

## Why

The monitoring pattern — a parent vault that declares data vaults as `*.link.json` mounts, where
each data vault *receives* append messages from other vaults — had no way for the parent's app to
see those lanes: the parent's `sg.append.*` was bound to the parent, child kernels carry no append
transport, and `sg.vault.notify` (the documented "peer wake") had no host handler at all.

## What changed

1. **`sg.append.list/fetch/markProcessed({ path })`** — a path under a **declared** mount binds
   the transport to that child (vault id + enum key derived in the top kernel from the credential
   the parent already resolved for the mount; the child is never opened; no write key carried).
   `purge`/`configure` with a path → `EPERM`. Runtime `sg.vault.mount` → `ENOLANE`. No mount →
   `ENOENT`. Same boolean grants as before.
2. **One checker per declared mount** — `append.new-messages` / `append.error` now also fire for
   each data vault's lane, tagged with `mount` + `mountId`; runs with the root checker on focus /
   app open. A mount with no derivable lane is skipped (`append-lane-skipped` vault event).
3. **`sg.vault.notify(mountId)`** — implemented: runs that mount's lane check now.
4. **`mount-lanes.js`** (new, pure, top-kernel only — not a bundle source): credential →
   `{vaultId, readKeyBytes, tier}` via the same derivation `SGVault.open` uses; refuses a
   credential for a different vault than the link declares.

## Security posture

Nothing new reaches the app. The parent already holds each child's credential (that is what
makes the mount work), and the child's `enum_key` is a pure function of its read key — the same
fact recorded as a security note in `AUTHORING.md`. Only the read verbs cross; the owner verbs
need the child's write key, which the lane binding never carries. Only the owner's declaration
is honoured as a trust anchor — an app-chosen runtime mount is refused.

## Test impact

**Should break (good):** anything asserting `sg.vault.notify` returns "Unsupported vault action".
**Should not break:** all declared-mount / kernel suites (unchanged and green post-merge); all
Python (no server change); bundle freshness (`mount-lanes.js` is not a bundle source).
**New:** `test__mount_lanes.js` (20, real Web Crypto, no mocks); 3 suites in
`test__app_shell_bridge_build.js` (lane routing, lane client, per-mount checkers + notify).

## Not changed, deliberately

- `sg.append.write` — already took an explicit `vault_id`; untouched.
- Child kernels still carry no append transport. Recorded in the reality doc as the same shape as
  the `sg.llm.*` parity gap. If a child-side lane is ever wanted, it needs the transport in the
  bundle, handlers in `kernel-app-handlers.js`, and the child to retain read-key bytes (it opens
  read credentials non-extractable today).
