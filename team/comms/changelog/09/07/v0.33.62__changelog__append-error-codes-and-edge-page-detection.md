# Changelog — append client hardening, bridge error codes, `sg.app.pinned`

**date** 7 September 2026
**from** Dev (Explorer)
**affects** vault UI bridge (`app-shell.js`), append transport (`sg-append.js`), `AUTHORING.md`
**server/API changes** none — no endpoint, schema or gate behaviour changed

---

## What changed

### 1. `sg-append.js` — never issue a doomed request; never paste an HTML page into an error

- **Vault-id validation.** `list` / `fetch` / `markProcessed` / `purge` / `configure` now build
  their path through `_vaultPath()`, which throws `EINVAL` when the client has no vault id or a
  malformed one, **before** any request goes out. Previously an unset `vaultId` produced
  `/api/vault/append/list/` — no route match, a 404, and a debugging session aimed at the server.
  `write` validates its caller-supplied target the same way.
- **`_errorForResponse()` replaces the inline error path.** A JSON body now yields the API's
  `detail`; any other body is truncated to 300 chars. An **HTML** body (by content-type or by
  sniffing the first bytes) yields a new code, **`EEDGE`**, and a message that says the status
  cannot be trusted and points at the credential rather than the URL.

### 2. `app-shell.js` — bridge errors carry a stable `code`

- `_sgCmd` used to rebuild every rejection as `new Error(e.data.err)`, discarding the `code`
  that `cmdReply` had always been able to send. `Object.keys(err)` was `[]` in the frame and
  apps had to string-match `message`. It now copies `code` and `status` onto the Error.
  **This fixes every `sg.*` namespace, not just append.**
- The append branch now sends codes: `EPERM` (and the denial message now names the exact
  `app.json` key to add), `ENOSYS` for an unknown action, `ENOTRANSPORT` when no vault is open,
  and the transport's own code otherwise.

### 3. `app-shell.js` — a folder `app.json` no longer drops root permissions silently

`AppNavHelpers.resolveFolderManifest` replaces the root manifest wholesale, so grants declared
at the vault root stop applying. `_setActiveManifest` now diffs the two and warns — console,
vault event (`app-json-permissions-dropped`) and a HUD message — naming the dropped groups.

### 4. `app-shell.js` — `sg.app.pinned` / `sg.app.release`

`.vault/releases.json` is inside the permission floor, so an app could not learn it was mounted
from a pinned commit rather than HEAD — the fact that explains "I pushed a new `app.json` and
nothing changed", and which also forces `writable: false`. Both fields are read-only mirrors.

## Test impact

**SHOULD break (good failure) — update these:**

| Test | Why |
|---|---|
| Any test calling a vault-bound `SGAppend` verb with a missing/short `vaultId` | Now throws `EINVAL` before fetching, by design. Use a realistic id (8–24 lowercase alphanumerics). One fixture in `test__sg_append_client.js` (`vault_id: 'r'`) was updated for this; it asserts payload passthrough, not id leniency. |
| Any test asserting an append error `message` contains a response body verbatim | Bodies are now parsed (`detail`) or truncated; HTML is never included. |
| Any assertion that `sg.*` bridge errors have no enumerable properties | They now carry `.code` (and `.status`). |

**Should NOT break (bad failure) — investigate if they do:**

- All 133 Python tests for `Service__Vault__Append` / `Routes__Vault__Append` — no server change.
- `test__app_permissions__append.js` — the grant model is untouched.
- `test__bundle_freshness.js` — neither edited file is in the kernel bundle; verified still fresh.
- Any test asserting the default frame CSP — unchanged.

**Verified green:** full `tests/unit/vault_ui/loader/run-all.sh` (exit 0), and
`test_Service__Vault__Append.py` + `test_Routes__Vault__Append.py` (133 passed).
New coverage: 14 assertions in `test__sg_append_client.js`, 11 in `test__app_shell_bridge_build.js`.

## For the QA team

The `EEDGE` case is worth a dedicated probe, because it is a **live production behaviour, not a
hypothetical**: `send.sgraph.ai`'s static-site custom error response maps `403 → /404.html` and
that mapping also applies to `/api/*`. Measured against dev on 7 Sep 2026:

| Request | API returns | Client sees |
|---|---|---|
| `write` with an unregistered `append_token` | 403 | **404 + `text/html`** |
| `list` with a wrong or missing `enum_key` | 403 | **404 + `text/html`** |
| `list` with an empty `vault_id` (real route miss) | 404 | 404 + `application/json` |
| `list` with a malformed `vault_id` | 400 | 400 + `application/json` |
| `write` with no `append_token` | 400 | 400 + `application/json` |

Only 403 is rewritten. **This is an infrastructure fix, not an application one** — see the
DevOps handoff in `team/roles/dev/reviews/09/07/`. Until it lands, every gate failure on the
append lane is indistinguishable from a wrong URL to anyone not checking the content-type.
