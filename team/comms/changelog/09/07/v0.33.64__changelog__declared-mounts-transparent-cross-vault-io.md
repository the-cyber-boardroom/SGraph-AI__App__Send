## What a vault app experiences

Nothing. The owner puts `data.link.json` in the vault (as they already do for the tree view);
the app writes `/data/report.json`; the write lands in the *other* vault through the same
broker → custody gate → tier gate → relay → child kernel → push chain that `sg.vault.mount`
uses. The app never calls `mount`, needs no `vault.mount` grant, and the only trace is
`{ mounted: true }` in the write reply.

## Changes

### Step 1 — child kernel: read credential + embedded token (`kernel-bootstrap.js`, `sg-vault.js`)
- Default `vaultFactory` strips sgit key prefixes and opens a **read credential**
  (`<64-hex>:<vault_id>`) via `SGVault.openReadOnly`, deriving the ref id itself — so a parent
  holding only a child's **read key** (an ro-links record) can mount it.
- `SGVault.readEmbeddedAccessToken()` — **one** implementation of the `.vault/access-token.json`
  read; `/app` and `/vault` shells now delegate to it (inline copies kept only as fallback for
  vault-likes without the method). The child kernel uses it so a **full-key** child is writable
  without the parent forwarding *its* token.
- A read-credential child is **never marked writable**, embedded token or not: it has
  `_writeKey = null` and every write also carries `x-sgraph-vault-write-key`, which the server
  hash-checks (analysis §2). The data source says read-only instead of failing at push.

### Step 2 — production credential resolver (`app-shell.js`, `declared-mounts.js`)
`_resolveChildCredentials` order, pure and unit-tested in `DeclaredMounts.resolveCredentials`:
1. owner-secret store `.vault/owner/secrets/<ref>` (parent **write-key** tier) → full key → **rw**
2. `ro-links.json` record (parent **read-key** tier) → read credential → **ro**
3. device-saved key (VaultLinks localStorage) → full key → rw, custody `user-entered`
4. the `clinic.json` trial stub — **now the last fallback**, kept only for the synthetic trial

A read-only parent cannot decrypt (1) and falls through to (2) — never throws, never rw.

### Step 3 — declared mounts (`app-shell.js`, `kernel-parent.js`, `kernel-mounts.js`)
- `_mountDeclaredVaults()` scans `*.link.json` (`DeclaredMounts.scan`) and registers each via
  the ordinary `KernelParent.mount({ lazy: true, meta: { declared: true } })` at the **four
  app-frame sites** (`_mountApp`, `_mountPageLayout`, `_mountVaultFile` HTML + markdown) —
  after the sandbox is final, before the frame exists. Idempotent; never fatal.
- **Register eager, spawn lazy** — `KernelParent.mount({lazy})` stores a spawner; `relay` /
  `monitorChild` call `_ensureChannel` on first use; concurrent first callers share one spawn.
- **Custody gate origin is now a function** evaluated at gate time (`_appSandbox()` before the
  frame exists, the live element after) — declared mounts are gated against the sandbox the
  frame is about to get, not a stale snapshot.
- Rule §6.1 (top-kernel-only, no cycles) holds by construction: child kernels run
  `kernel-bootstrap`, which has no mount path (pinned by a static test).
- Rule §6.2: `KernelParent.unmount(id, { byApp })` refuses a declared mount with `EPERM`; the
  bridge passes `byApp: true`; shell teardown may `force`.
- Rule §6.3: the child opens on a **per-parent clone branch** `viv:<parent vault id>`
  (`SGVault.open(…, { cloneBranch })`, HMAC-derived — never on the server in clear), so two
  parents mounting one child never share a clone ref. Decision made here, reversible.
- `KernelMounts.add` now keeps `custody` (it was silently dropped, so `list()` always said
  parent-held); `list()` gains `access`, `declared`, `spawned`.

### Step 4 — provenance (`sg-vault.js`, `kernel-bootstrap.js`)
`vault._commitTrailer` is appended to every commit message the child makes:
`Via-Mount: <owner label> (declared|runtime)` — the child's history records *which door* a
write came through without naming the vault behind it (analysis §7).

## Test impact

**New:** `test__declared_mounts.js` (15) — scan + resolver ordering incl. the read-only-parent
fall-through; `test__kernel_declared_mounts.js` (28) — real KernelParent + real child kernel:
lazy spawn shared by concurrent callers, declared-unmount EPERM vs runtime unmount OK (test B,
the **no-impact proof**), ro credential → `EREADONLY` from the child, default factory
(prefix strip, `openReadOnly` with the derived ref id, `cloneBranch`, embedded token,
**test G**: read-credential child never writable), Via-Mount trailer, function-valued gate
origin, and the static "child never auto-mounts" guard.

**Should NOT break (and did not):** `test__kernel_parent.js`, `test__kernel_relay.js`,
`test__kernel_app_handlers.js`, `test__kernel_bootstrap.js` — the runtime `sg.vault.mount`
path is unchanged; every existing suite is green on the merged tree.
