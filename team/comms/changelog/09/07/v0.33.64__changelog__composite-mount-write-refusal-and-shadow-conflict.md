## The defect

`CompositeDataSource` (the `.link.json` sub-vault splice) claims sub-vaults are read-only but never
enforced it. Every mutation was a blind pass-through to the **root** data source with the path
unchanged; it "failed" only because the virtual mount folder does not exist in the root. When the
parent held a **real** folder at the mount path, the write **succeeded silently in the parent**,
and — worse — the tree splice let that real folder *replace* the mount node, so the user browsed
the parent's folder believing it was the child while reads still routed to the child.

Reachable from **both** surfaces: the tree view (`vault-shell`) and any **vault app**, because
`app-shell` swaps the bridge's data source for the composite whenever a link file exists
(`.link.json` mounts are not kernel mounts, so `_mounts.resolve()` misses and the write falls to
the composite). Executed, not inferred.

## The fix (`_common/js/adapters/composite-data-source.js`)

| Change | Detail |
|---|---|
| **`_refuseIfMounted`** | Every mutation (`saveFile`, `renameFile`, `deleteFile`, `createFolder`, `deleteFolder`, `renameFolder`, `moveFile`, `moveFolder`) refuses with `err.code = 'EMOUNT_RO'` (+ `err.mountPath`) when **any** involved path — folder, joined file path, move **source or destination**, the mount root itself — is at/under a mount. Runs before anything reaches the root; does **not** require the mount to be open (a locked mount is still not the parent's folder). Editing the `*.link.json` file itself remains a root op. |
| **`_spliceNode` conflict guard** | A real folder sharing a mount's name no longer overwrites the mount node; the mount is kept and flagged `_conflict: 'shadowed-by-folder'` for the UI. |
| **`getFileList`** | Root entries at/under a mount path (the shadowed folder's contents) are hidden — reads route to the child anyway, so listing the parent's copy would be a lie. |
| `kernel-shell-bundle.js` | regenerated (the adapter is a bundle source) |

No behaviour change for mutations outside mounts, for reads, or for the kernel-lane
(`sg.vault.mount`) path — this adapter is only ever the *fallback* behind `_mounts.resolve()`.

## Test impact

**New** (in `tests/unit/vault_ui/loader/test__composite_data_source.js`, 20 assertions, suite now 64):
- every mutation verb at/under a mount → `EMOUNT_RO`, root recorder sees **nothing**; locked mount still refuses; ordinary paths (and the link file) still pass through
- the corruption case: real folder + link of the same name → tree keeps the mount node with `_conflict`, shadowed entries hidden from `getFileList`, write refused, **nothing lands in the parent**

**Should NOT break:** all existing composite/read/splice assertions (unchanged and green);
`test__bundle_freshness.js` (bundle regenerated in the same commit); kernel relay/parent suites
(untouched code path).

**UI follow-up (not in this change):** `send-browse` / `vault-browse-edit` should read `_conflict`
to show a warning on the node, and surface `EMOUNT_RO` as "this is a read-only sub-vault" instead
of a generic save error. Today the editor's controls are still *enabled* inside a mount and now
fail loudly instead of silently — an honest interim state (analysis §1 "tell the truth in the
interface" is the next step).
