# Changelog — M5-wiring: rw sub-vault credential layer made live + unit-pinned

**Date:** 2026-06-01
**Author:** Architect/Dev (Explorer)
**Scope:** `/en-gb/app/` app-shell — rw sub-vault credential resolution (M5-wiring, no-browser half)
**Version line:** v0.31.2 (rw-sub-vaults feature series)

## What changed

Completing the **no-browser half of M5-wiring** from the rw-sub-vaults scoping doc
(`team/roles/architect/reviews/05/31/v0.31.2__scoping__rw-sub-vaults-kernel-relay-in-tree.md` §6a).
The rw credential code already existed in `app-shell.js` (`_createChildVault({rw})` → `_saveRwLink`,
and `_resolveChildCredentials` → `_resolveRwCredentials`), but two things were wrong/missing:

### 1. Integration gap — the rw path was dead in its own context (FIX)

`vault-rw-seal.js` was loaded in the top-level `index.html` but **not** in `en-gb/app/index.html`,
where `app-shell` actually runs. So in the app context `VaultRwSeal` was `undefined`:
`_saveRwLink` threw "rw sealing unavailable" and `_resolveRwCredentials` returned `null`. The whole
rw path was unreachable code in the only context that uses it.

- **`en-gb/app/index.html`** — now loads `vault-rw-seal.js` (before `app-shell.js`).

No unit test caught this because it was a script-wiring gap, not a logic gap.

### 2. Glue extracted to a pure, importable helper + unit-pinned

The decision-bearing credential glue was inline in `app-shell.js` and only ever *reimplemented*
(not imported) by the loop test — so a regression in the assembly/shape/guard would have gone
unnoticed. Following the team's `app-shell-nav-helpers.js` precedent:

- **`app-shell-rw-creds.js`** (new) — pure, DOM/crypto-free `AppRwCreds` with:
  - `buildChildFullKey(passphrase, vaultId)` → `<passphrase>:<vaultId>` (the format `SGVault.open` parses).
  - `writeSecretOf(vault)` → parent `_writeKey` or `null` (the read-only-parent **guard**).
  - `credsFromChildKey(childKey)` → `{ vaultKey, accessToken:null, custody:'parent-held', access:'rw' }` (relay-consumed shape).
  - `rwRecordBody(meta, sealedKey)` → owner-record body; requires `sealed_key`, never a plaintext key field.
- **`app-shell.js`** — `_createChildVault` / `_saveRwLink` / `_resolveRwCredentials` now delegate to `AppRwCreds`.
- **`en-gb/app/index.html`** — loads `app-shell-rw-creds.js` before `app-shell.js`.

## Reality notes (no over-claiming)

- **No UI triggers rw yet.** The only `_createChildVault` caller does not pass `{rw:true}`, and mounts
  still render through the read-only `CompositeDataSource`. The credential layer is now live and
  substrate-complete, but a **writable mount in the tree** stays gated on M3 + a UI affordance.
- **Consistent with the M7 add-link honesty fix** — the add-link flow still correctly tells users the
  write key is not stored, because no writable mount exists in the tree yet.
- `app-shell.js` is **not** in the kernel bundle, so these edits require **no** bundle rebuild
  (verified: `kernel-shell-bundle.js` unchanged; `test__bundle_freshness.js` still green).

## Test impact

**SHOULD break if reverted / regressed (good failures):**

- `tests/unit/vault_ui/loader/test__app_shell_rw_creds.js` (new, 17 assertions) — key format, the
  read-only-parent guard, the relay creds shape, and the rw-record body (sealed_key required, no
  plaintext key).
- `tests/unit/vault_ui/loader/test__rw_credential_loop.js` (12) — now **delegates to the real
  `AppRwCreds`** instead of a private copy, so the seal→store→resolve→unseal loop fails on a glue
  regression, not just a substrate one.

**Should NOT break (bad failures if they do):**

- `test__vault_rw_seal*`, `test__vault_links*`, `test__vault_access*` — unchanged substrate.
- `test__bundle_freshness.js` — passes (no bundled source changed; new file is parent-context only).
- `test__app_shell_nav_helpers.js`, `test__app_hud_config.js` — unaffected.

**Verification:** full `npm run test:vault-unit` sweep green (exit 0); `kernel-shell-bundle.js` unchanged.
