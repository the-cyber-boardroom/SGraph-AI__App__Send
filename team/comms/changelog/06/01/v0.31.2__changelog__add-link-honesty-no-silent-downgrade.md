# Changelog — Add-link honesty: no silent read-only downgrade (M7)

**Date:** 2026-06-01
**Author:** Architect/Dev (Explorer)
**Scope:** `/vault` — "Add a link" → Linked vault flow
**Version line:** v0.31.2 (rw-sub-vaults feature series)

---

## What changed

The "Add a link → Linked vault" flow accepts a **full, write-capable** vault key,
but only ever mounts the sub-vault **read-only** (it derives and stores the read key;
the composite/tree splice is read-only today, and rw-in-tree is gated on M2/M3). Until
now this downgrade was **silent**: the form said a flat "Opens read-only" and the success
toast said nothing about the write capability being dropped — so pasting a full key looked
like it linked a writable vault when it did not.

This is the M7 honesty fix from the rw-sub-vaults scoping doc (`team/roles/architect/reviews/05/31/v0.31.2__scoping__rw-sub-vaults-kernel-relay-in-tree.md`). Shippable now, independent of M2/M3.

### Code

- **`vault-links.js`** — new **pure** helper `VaultLinks.addLinkDisclosure({ writable, portable, label })`
  → `{ mode: 'read-only', writeKeyStored: false, hint, result }`. No DOM; browser + node export.
  `hint` is the form caption, `result` the success line. When `writable` is truthy it explicitly
  states a write-capable key was provided and the write key is **not** stored.
- **`vault-browse-edit.js`** `_showAddLink` —
  - static form hint changed from "Validated + saved on this device. Opens read-only." to a clear
    statement that it opens **read-only** and a write-capable key's write key is **not stored**.
  - success toast now uses `addLinkDisclosure(...)` driven by the opened child's `.writable`, so a
    full key reports "…read-only (…) — write key not stored" instead of a bare "Linked vault".
- **`kernel-shell-bundle.js`** — rebuilt (both edited sources are bundled).

No behavioural change to what is stored or mounted — the sub-vault still mounts read-only and only
the read key is persisted. **Only the user-facing disclosure changed.** No API change.

### Docs

- Scoping doc §6a updated to fold the OPEN AppSec popup-over-grant finding
  (`team/roles/appsec/reviews/05/31/v0.31.12__...`) into the M3 milestone + verification gate, so
  inner/mounted sub-vault frames drop `allow-popups*` when M3 reroutes rendering through `VaultAccess`.
