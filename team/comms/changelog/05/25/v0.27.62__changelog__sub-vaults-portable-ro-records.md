## Summary

The "🔗 Add link → Linked vault" flow now writes a **portable, in-vault read-only record** instead
of only saving the key on this device — so a linked vault opens **silently on any device** that has
the parent vault.

On Add (linked vault): after validating the key by opening the child (`SGVault.open`), the flow
exports the child's **read key** (`crypto.subtle.exportKey('raw', child._readKey)` — the same
extractable-read-key pattern the read-only-token manager uses) plus its `_refFileId`, and writes a
`{ type:'vault', label, pin, vault_id, read_key, ref_file_id }` record into
`.vault/owner/ro-links.json` via `VaultLinks.saveRoRecord` (which commits **and pushes**, so the
record travels with the parent vault). The composite's `_openMount` already resolves that record and
opens the child via `SGVault.openReadOnly` with no prompt — now on any device.

- **Only read access is persisted** — the record holds the child's read key + ref, never its write
  key. (`ro-links` is the parent's read-tier, so parent readers can also traverse — by design.)
- **Fallback:** if the record can't be written (e.g. export fails), it falls back to saving the key
  on this device (`setStoredChildKey`) and warns.
- **ro-token input** in the Add dialog is a follow-on — full key / simple token are supported now
  (an `ro-…` paste shows a friendly "use the full key" message).

## Security note

The Add flow persists **read-only** capability for the child (read key + ref), encrypted inside the
parent vault at the read tier. The child's write key is never stored in the record. Worth an AppSec
glance that storing a child read key in the parent's read-tier `ro-links` matches the intended
"parent readers may traverse read-only sub-vaults" model.
