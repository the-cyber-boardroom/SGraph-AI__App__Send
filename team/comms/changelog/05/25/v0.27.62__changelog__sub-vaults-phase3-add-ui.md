## Summary

Owners can now create link files from the UI instead of hand-authoring JSON.

- **🔗 Add link** button (in `vault-browse-edit.js`, shown only on writable vaults) opens a small
  modal (`_showAddLink`):
  - **Linked vault** — label + the child's key (full key / simple token / `ro-…`). On Add, the key
    is **validated by opening the child** (`SGVault.open`, which also yields the real `vault_id` +
    name), the key is **saved on this device** (`VaultLinks.setStoredChildKey`), and a
    `<slug>.link.json` (`{ vault_id, ref_id, label }`) is written into the vault. The sub-vault then
    appears as a folder and opens read-only with no prompt on this device.
  - **Web page / Video / Image / External app** — label + URL; type is auto-detected
    (`VaultLinks.detectResourceType`); a `<slug>.link.json` (`{ ref_id, type, url, label }`) is
    written and shows as an embed leaf.
  - After writing, the composite is re-`scan()`ed and the tree refreshed so the new link appears.
- The dialog reuses the existing modal styling; the vault-key path requires `SGVault` + a transport
  (resolved from the composite's root vault).

## Test impact

- **No new logic tests** — the Add UI is a DOM modal; its helpers lean on already-tested pieces

  still pass: vault-links 45/45, composite 36/36, storage-pertab 8/8, pvp KAT 9/9; file syntax-clean.

## Notes / still open

- Today the linked-vault key is saved **on this device** (localStorage). A portable in-vault
  `ro-links` record (silent open on other devices too) is a small follow-on — it needs exporting the
  opened child's read key + ref. Behaviour is correct on the device that added the link.
- Links are written to the vault **root** (`/`); the owner can move the `*.link.json` afterwards.
- The opt-in **app→folder access grant** remains **AppSec-gated** and unbuilt.
