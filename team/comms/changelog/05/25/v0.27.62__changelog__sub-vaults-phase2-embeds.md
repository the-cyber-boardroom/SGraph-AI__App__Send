## Summary

A `*.link.json` can now point at an **external resource** (video / web page / image / app), shown
in the tree as a resource leaf and opened in a **controlled, default-deny embed**.

- **`<sg-embed-frame>`** (NEW) — per-type renderer with a hard security boundary:
  - `image` → `<img referrerpolicy=no-referrer>`, `video` (file) → `<video controls>` (media
    elements — cannot read the page);
  - `video` (provider, e.g. YouTube) → provider `<iframe>`; `link`/`app` → **sandboxed iframe with
    NO `allow-same-origin`, NO VFS bridge, and NO `message` listener registered for it**.
  - **Click-to-load:** a placeholder until the user clicks Load — nothing contacts the third party
    on open (privacy). Sticky "External window · host · cannot read this vault" banner + "Why?".
- **`VaultLinks`**: `detectResourceType(url)` (YouTube/Vimeo→video, image/video extensions, else
  link) + `isResourceLink(link)`.
- **`CompositeDataSource`**: `scan()` registers external-resource links into a `_resources` map and
  `getTree()` presents each as a `_resource` leaf (`_resourceType`/`_url`/`_provider`/`_label`); raw
  `.link.json` files stay hidden from `getFileList`.
- **`send-browse--v0.3.2.js`** (user v0.3.3): renders `_resource` leaves (icon + `↗`) and, on click,
  opens them via a new `_openResourceTab` → mounts `<sg-embed-frame>` in the preview stack (plain
  external-link fallback if the component isn't loaded).
- **`index.html`**: `<script>` include for `sg-embed-frame.js`.

## Security note (for AppSec)

The embed deliberately gives external content **no path to the vault**: cross-origin `src`, locked
sandbox (no `allow-same-origin` for `link`/`app`), and `<sg-embed-frame>` shares no code with
app-shell's VFS bridge and registers no `message` listener. Please verify in a browser. The opt-in
"grant an app access to a folder" capability is **not** built (Phase 3, AppSec-gated).
