## Summary

Adds the **`.vault/owner/ro-links.json` owner record** layer so a sub-vault opens **silently,
read-only, with no prompt** when its key is recorded in the parent vault.

- **`vault-links.js`** gains: `loadRoLinks(vault)`, `resolveRef(vault, refId)`,
  `effectiveLink(linkObj, record)` (effective value = link-file override ?? owner-record value),
  and `saveRoRecord(vault, refId, record)` (writable-only; ensures `.vault/owner/`, writes via
  `addFile`/`updateFile`, then `push()`). `ro-links.json` is a **read_key-tier vault file**
  (readable by any holder of parent read access) — mirrors `vault-token-manager`'s
  `readonly-tokens.json`. No owner-crypto needed.
- **`composite-data-source.js`**: `_openMount` now resolves the link's `ref_id` against the parent's
  `ro-links` first → opens the child via **`SGVault.openReadOnly(vault_id, read_key, ref_file_id)`**
  (silent, no prompt). Falls back to a localStorage key, then the `keyProvider` prompt. New
  `vaultOpenerRO` option (default `SGVault.openReadOnly`).

## Deferred (deliberate)

- **`rw-links.json` (full child keys, owner-only double-encrypted)** and the **`vault-hkdf.js` move
  to `_common/js/lib/crypto/`** — only needed for **writable** sub-vaults, which are out of scope in
  v1 (children open read-only). `vault-hkdf` is an ES module used by the token page; the browse page
  uses plain `<script>` globals, so moving/rewiring it is deferred to Phase 4 to avoid a risky
  cross-module refactor. ro-links needs none of it.
