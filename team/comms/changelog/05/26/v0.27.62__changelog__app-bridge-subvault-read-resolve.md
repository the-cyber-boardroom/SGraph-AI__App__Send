# Changelog — App bridge: resolve sub-vault reads/lists (auto-open on access)

**Version:** v0.27.62
**Date:** 2026-05-26
**Author:** Dev (Claude Code session, branch `claude/exciting-brown-G2P9Z`)
**Trigger:** Bug report (Bug 2) — from inside an App-Mode iframe, `sg.vfs.readText('subvaults/<child>/<file>')`
returned "No such file" and `sg.vfs.list('subvaults/<child>')` returned "No such path", even though the
**UI file browser** reads the same linked sub-vault fine. (Bug 1 / the write-401 is already fixed.)

---

## Summary

The app-side VFS bridge could not read or list a linked sub-vault, while the UI could. Keys, the
`ro-links.json` records, and the child data were all correct — the gap was purely that the UI's mount
was invisible to the bridge.

**Root cause.** `_setupVfsBridgeHandlers` already wraps the data source in a `CompositeDataSource`
(which splices sub-vaults and **auto-opens a mount on access**). But the bridge's **read** and **list**
handlers consulted a *static* `getFileList()` snapshot and short-circuited:

- **read:** `_findEntryStrict(fileList, path)` → if the path wasn't already in the flat list, it replied
  `ENOENT` immediately — **before** `getFileBytes()` (the method that auto-opens the mount) ever ran.
- **list:** filtered the same snapshot → empty → `ENOENT`.

A *collapsed* (not-yet-opened) sub-vault contributes only its mount-dir entry to `getFileList()`; its
inner files appear only after the mount is opened. The UI opens it via `loadFolder` on folder-expand;
the app has no expand gesture, so the mount stayed collapsed and every inner read/list ENOENT'd. The
fire-and-forget `scan()` also left a startup race.

**Fix (reads/lists only — inner-vault writes are unchanged, see below).** Both handlers now:

1. `await` the composite's `scan()` (captured as `compositeReady`) so mounts are registered, then
2. `ensureMountOpen(path)` — if `_mountForPath(path)` identifies a covering sub-vault, call
   `loadFolder(path)` to open it read-only (silent, via the stored ro-record — no prompt), then
3. re-read `getFileList()` and serve. Once a mount is open its inner files are listable and readable;
   `getFileBytes()` routes them to the child. No-op for ordinary paths and vaults without sub-vaults.

So `sg.vfs.readText('subvaults/patient-alex/submissions.json')` now resolves the link → ro-record →
opens the child read-only → returns the bytes, with no user prompt — matching the AUTHORING guide.

**Out of scope (per Dinis):** inner-vault **writes** (Bug 3) — child vaults stay read-only for now.
`sg.vfs.write` to a `subvaults/<child>/...` path still rejects by design; not changed in this fix.
