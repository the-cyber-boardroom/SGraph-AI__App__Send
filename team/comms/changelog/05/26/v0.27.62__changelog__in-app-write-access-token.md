# Changelog — In-app writes: thread the access token onto the write transport

**Version:** v0.27.62
**Date:** 2026-05-26
**Author:** Dev (Claude Code session, branch `claude/exciting-brown-G2P9Z`)
**Trigger:** Dinis — a Playwright session could read inside the vault app iframe and run
`sg.*` methods, but `sg.vfs.write` / `sg.sync.push` returned **401 "Access token required"**.

---

## Summary

Writes triggered from **inside** the vault app iframe (`window.sg.vfs.write`, `sg.sync.push`)
failed with **401**, even though the same vault was opened with a valid access token (the token
validated server-side — the check call returned a live `remaining` quota).

**Root cause.** When the vault opened, the access token was passed only to
`new VaultDataSource(vault, accessKey)`. That argument **only flips the `writable` flag**; it does
**not** authorise the network requests. The actual write `PUT` authorises via
`vault._sgSend.token`, which `SGSend._authHeaders()` reads **at request time** to add the
`x-sgraph-access-token` header. Because the token was never assigned to `vault._sgSend.token`, the
in-iframe write `PUT` went out **with no access-token header → 401**.

(Reads were unaffected: reads are tokenless by design.)

**Fix.** Thread the token onto the transport at every spot where the app shell obtains one:

- `_applyAccessToken(token)` — sets `vault._sgSend.token = token` (guarded).
- `_resolveAccessToken(vaultId)` — per-vault cached key → generic backend key fallback.
- Applied on: initial open (preset / cached / backend token), the `auth.required` cached-key path,
  the auth-prompt submit, and the bridge `setKey` command (which now also caches the token).

`SGSend._authHeaders()` reads `this.token` at request time, so assigning the token **after** the
vault is open (as the bridge does on `setKey`) is honoured by the next write — that is exactly the
property the new regression test guards.
