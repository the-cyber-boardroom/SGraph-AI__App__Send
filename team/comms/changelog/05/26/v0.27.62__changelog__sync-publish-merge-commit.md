# Changelog — Sync: publish the merge commit so clone and named branches converge

**Version:** v0.27.62
**Date:** 2026-05-26
**Author:** Dev (Claude Code session, branch `claude/exciting-brown-G2P9Z`)
**Trigger:** Dinis — SGit graph showed "HEAD (Merged)", "Working HEAD", and "Published HEAD" on
**three different commits** after an auto-synced merge. Requirement: a freshly-synced browser session's
HEAD must match `sgit pull` HEAD (Vault Web and the published branch must be the same state).

---

## Summary

The web UI always works on a per-working-copy **clone branch** (`ref-pid-snw-…web-ui`), separate from
the **published/named branch** (`ref-pid-muw-*`) that `sgit pull` reads. They converge only on `push()`.

A three-way `merge()` wrote the merge commit to the **clone** ref only, set `_namedHeadId` to the *old*
published tip, and **never published the merge**. None of the merge call-sites (`_syncToNamedHead`,
manual Sync, repair) pushed afterward. The activity-triggered auto-push would eventually publish it (the
clone is cleanly *ahead* post-merge), but only on a later nav-switch — so right after a merge, and
permanently if no further activity occurred, **Working HEAD = merge commit while Published HEAD lagged**.
A fresh session bootstrapped from the named ref (or `sgit pull`) then landed on a different commit.

**Fix.** After a successful three-way `merge()`, immediately `push()` (best-effort). Because the old
published tip is a parent of the merge commit, this is a fast-forward on the server — no published-only
commits are lost; they are all folded into the merge. Result: **Working HEAD == Published HEAD == merge
commit**, and a freshly-synced session matches `sgit pull`. If the push fails (offline/race) the merge
still stands locally and the next sync's ahead-path auto-push retries it.

Fast-forward merges and pull are unchanged — they already leave clone and named converged.

  commit manager, object store, crypto). Existing jsdom-free suites are unaffected and stay green.
  Syntax clean.
- **Verification gap (must test in browser / integration):** with concurrent edits on both the browser
  clone branch and the published branch, perform a sync; afterwards the SGit graph should show **a single
  converged tip** (Working HEAD == Published HEAD == the merge commit), and a fresh session / `sgit pull`
  should land on that same commit. Also confirm fast-forward syncs (browser-only or published-only edits)
  still produce no merge commit.
