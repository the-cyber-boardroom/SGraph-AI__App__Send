# Changelog — App Mode (/app): resolve the write access token from three sources

**Version:** v0.27.62
**Date:** 2026-05-26
**Author:** Dev (Claude Code session, branch `claude/exciting-brown-G2P9Z`)
**Trigger:** Dinis — saving a file works in `/vault` mode but fails in `/app` mode with
"Could not save: Read-only vault". Requirement: support three ways for `/app` to obtain the
server write token — (1) a token embedded in the vault, (2) a token set in this browser tab,
(3) parity so that whatever authorises writes in `/vault` also authorises them in `/app`.

---

## Root cause

Writability is gated by the **server access token**, not the crypto vault key
(`vault-data-source.js:26` → `writable = !!accessKey`). The vault key (`sg-vault-key`) is shared
across both modes, so the app opens and renders in `/app` — only the write gate was missing.

The two modes resolved the access token from **non-overlapping storage keys**:

| | session slot | durable slot |
|---|---|---|
| `/vault` (`VaultLoaderStorage`) | `sg-vault-access-key` | `sg-vault-access-key-saved` |
| `/app` (`app-shell._resolveAccessToken`) | `sg-access-key:<vaultId>` | `sg-access-key:<vaultId>`, `sg-backend-access-key` |

A token established in `/vault` mode lands under `sg-vault-access-key-saved`; `/app` never looked
there, so `accessKey` was `null` → `VaultDataSource.writable = false` → every bridge write returned
`'Read-only vault'`. An app opened straight from its vault key (root-inbox deep link) carries no
token at all in `/app`, so it was always read-only.

## Fix

`app-shell.js` now resolves the write token from three sources, in priority order:

1. **This browser/tab** — `_resolveAccessToken` checks its own per-vault cache
   (`sg-access-key:<vaultId>`), then **the `/vault`-mode shared keys**
   (`sg-vault-access-key` / `sg-vault-access-key-saved`), then the generic `sg-backend-access-key`.
   The shared-key step gives **`/vault`↔`/app` parity** on the same origin. (`VaultLoaderStorage`
   isn't loaded on the `/app` page, so the raw keys are read directly.)
2. **Embedded in the vault** — after `app.json` is read, if no browser-side token was found, adopt
   `appJson.accessToken` (or `appJson.auth.token`). Full-key opens only; a read-only (`ro-`) open
   never gains write capability via this path.

When a token is adopted post-construction, both the data source (`writable` + `_accessKey`) and the
transport (`vault._sgSend.token`, via `_applyAccessToken`) are updated, mirroring the `/vault`-mode
pattern in `vault-shell.js:161-162`.

## Security note (by design, flagged for awareness)

Embedding the write token in the vault (`app.json`) means **anyone with the vault read key can
decrypt it** — including a recipient of a read-only (`ro-`) share, who holds the read key and could
extract the token to write directly via the API. The UI's `isRO` guard prevents the *app* from
writing on an `ro-` open, but it cannot prevent manual extraction. Use the embedded token only where
"can read the vault ⇒ may write to it" is the intended trust model. The browser-tab / `/vault`-parity
sources (1) do not have this property.

## Test impact

- **No jsdom-free unit harness** exists for app-shell's open flow (needs SGVault, SGSend, the
  bridge, and storage). Existing jsdom-free suites are unaffected; syntax is clean.
- **Verification gap (must test in browser):**
  1. **Parity** — set the access token in `/vault` mode, open the same vault in `/app` (via vault
     key / deep link), confirm a file save succeeds (no "Read-only vault").
  2. **Embedded** — put `"accessToken": "<token>"` in the vault's `.vault/app.json`, open in `/app`
     with no browser token set, confirm save succeeds.
  3. **Read-only** — open with an `ro-` token and confirm writes are still blocked even when the
     vault carries an embedded `accessToken`.
  4. **Regression** — `/app` with no token anywhere still reads/renders and reports read-only on save.
