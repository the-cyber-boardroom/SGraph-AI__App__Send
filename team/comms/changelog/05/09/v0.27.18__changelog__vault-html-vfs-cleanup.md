# Changelog: Vault HTML iframe — replace data-URI inlining with `sg.loadCss` / `sg.loadJs` contract

**UI versions touched:** vault `v0.2.2`, send-browse `v0.3.2-vfs-5` and `v0.3.3-vfs-5`
**Date:** 9 May 2026
**Author:** Explorer team — Dev role
**Branch:** `claude/vault-web-bugs-ZQh10`
**Supersedes:** the data-URI inlining approach introduced earlier in [`v0.27.18__changelog__vault-html-iframe-bugs.md`](./v0.27.18__changelog__vault-html-iframe-bugs.md) (Bug 1)

---

## Summary

The data-URI rewrite of `<link rel="stylesheet">` and `<script src>` (Bug 1's previous fix) was a regex-based workaround. After discussion, replaced with a calling-convention contract for vault HTML authors:

> **Vault HTML must not use declarative `<link rel="stylesheet">` or `<script src>` against vault-relative paths. Instead, call `sg.loadCss(path)` or `sg.loadJs(path)` at runtime.**

This deletes ~150 lines of regex-and-base64 markup mangling and the entire class of bugs around `</script>` / `</style>` early-termination, base64 inflation, and unhandled grammar variants (`@import`, `<iframe src>`, `<source>`, ESM, workers).

A future architectural upgrade (Service Worker) is documented separately and will make declarative tags work again — see [`library/guides/vault-html/service-worker-future.md`](../../../../../library/guides/vault-html/service-worker-future.md).

## API surface added

```js
window.sg.loadCss(path) → Promise<HTMLStyleElement>
window.sg.loadJs(path)  → Promise<HTMLScriptElement>
```

Both fetch the vault file via the existing `fetch` override and inject a fresh `<style>` / `<script>` element into `document.head` with `data-sg-loaded="<path>"`. Bytes never enter the HTML body, so `</script>` / `</style>` collisions are physically impossible.

The pre-existing bridge surface (`sg.vfs.*`, `sgVault.*`, `sg.app.*`) is unchanged.

## Test impact classification

### Tests that SHOULD break (good failures — semantic shift)

- Any test asserting that `_inlineHtmlAssets` / `_inlineVaultAssets` / `_bytesToBase64` / `_replaceAsync` are exported or callable. They no longer exist.
- Any snapshot test that captured iframe blob HTML containing `data:application/javascript;base64,...` or `data:text/css;base64,...` substrings. The blob HTML now passes through unchanged.

### Tests that SHOULD NOT break (regression signal if they do)

- All tests for `window.sg.vfs.{read,readText,write,list}` — surface unchanged.
- All tests for the parent-side VFS message bridge — same listener, same protocol.
- Tests for `<a href>` same-vault navigation, `<img src>` rewriting, `fetch()` interception — all unchanged (independent code paths).
- Vault edit-mode tests for layout-flip + height save/restore + iframe reuse — independent of this change.

### New tests recommended

- Demo HTML containing `<link rel="stylesheet" href="theme.css">` (vault-relative): assert that `theme.css` is **not** auto-inlined and that the page console logs a 404 for it. Documents the contract.
- Demo HTML containing `<script>sg.loadCss('theme.css').then(...)</script>`: assert that `<style data-sg-loaded="theme.css">` appears in the iframe DOM after the load resolves.
- Same for `sg.loadJs`.

## What gets simpler downstream

- **Bridge script** is now the single seam between vault and iframe. No HTML-mangling regex anywhere in the codebase.
- **Live edit-mode preview** runs through the same path as the static viewer (already true after the earlier refactor); now both paths are simpler — no inlining await on either side.
- **Future Service Worker upgrade** is a clean swap: rip out the bridge fetch override + the `sg.loadCss`/`loadJs` loaders, leave the `sg.vfs.{write,list}` postMessage protocol. Documented in the service-worker-future doc.

---

## What vault content authors need to know

If you have existing vault HTML demos that use declarative `<link>` or `<script src>` against vault-relative paths, they'll break — fix by replacing with `sg.loadCss` / `sg.loadJs` per the [authoring guide](../../../../../library/guides/vault-html/AUTHORING.md). Most hand-written demos are small and just inline `<style>` / `<script>` directly; those are unaffected.
