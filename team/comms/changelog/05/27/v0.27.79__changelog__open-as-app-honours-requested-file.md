# Changelog — Fix: "Open as App" honours the requested file; links route through the root inbox

**Version:** v0.27.79
**Date:** 2026-05-27
**Author:** Dev (Claude Code session, branch `claude/exciting-brown-G2P9Z`)
**Trigger:** Dinis — "Open as App" always opened the vault's **default** app (it redirected to `/en-gb/app`
and ran the app.json entry), instead of opening the file/page the link pointed at.

---

## Root cause

`app-shell._continue(appJson)` read the `sg-vault-deep-link` (the `app:<path>` set by an "Open as App"
link) **only inside the no-app.json branch**. When the vault had an `app.json`, it skipped straight to
`_mountApp(appJson)` and the requested path was silently dropped (and never cleared). So any vault with a
default app always opened that default app.

Secondary: the routing contract changed earlier — `/en-gb/app#…` now means a **file path**, not a vault
key (`vault-loader-routing.js:13,22`) — but two link builders were never updated:
- the header **▶ Open App** button still navigated to `/en-gb/app#<key>` (`vault-header.js`), so the key
  was misread as a file-path deep-link and the vault opened only if the key happened to be cached;
- the per-file **↗ Open as App** links used `/en-gb/app#<path>`, which relies on the key already being in
  localStorage (not self-contained / shareable).

## Fix

1. **`app-shell._continue`** — evaluate the `app:` deep-link **first**, before the default app. If a file
   was requested, `_mountVaultFile(path)` runs it as an app (full VFS bridge). Guard: if the requested
   path **is** the `app.json` entry, fall through to `_mountApp` so its declared resources load.
2. **Header ▶ Open App** (`vault-header.js`) → `/#<key>` (root hash inbox), which saves the key and
   redirects to `/en-gb/app` to auto-mount the default app. **Required** alongside (1): now that any
   `app:` deep-link wins, the old `/en-gb/app#<key>` would have injected a bogus `app:<key>` file path.
3. **Per-file/page ↗ Open as App** (`vault-browse-edit.js`, both the file-tab and page-layout buttons) →
   self-contained `/#<key>|app:<path>` via the existing root-inbox `|` convention
   (`vault-loader-routing.js:77-79`). Key sourced from `VaultLoaderStorage.getCurrentKey()`; falls back
   to the legacy `/en-gb/app#<path>` when the current key is unavailable. Only the path is
   `encodeURIComponent`-d (runRoot decodes the hash once).

## Files Modified

```
.../app-shell/app-shell.js          — _continue: deep-link honoured before default app (+ entry guard)
.../vault-header/vault-header.js     — _openApp: /#<key> via root inbox (was /en-gb/app#<key>)
.../vault-browse-edit/vault-browse-edit.js — both "Open as App" links → /#<key>|app:<path> (+ fallback)
```

## Test impact

- **No jsdom-free unit harness** for the app-shell open flow / send-browse patches; existing suites
  unaffected; all three files syntax-clean.
- **Verification gap (browser):**
  1. Vault **with** an app.json: "Open as App" on a *different* file opens **that file** as an app (not
     the default app). "Open as App" on the entry file opens the full default app (resources load).
  2. Header **▶ Open App** opens the default app, and the link works in a fresh tab (key carried via `/#`).
  3. Per-file link opened in a fresh tab / shared opens the right file (key carried via `/#key|app:path`).
  4. Vault **without** app.json: "Open as App" still renders the file; bare `/en-gb/app` still falls back
     to the vault UI.
- **Known limitation:** a filename containing a literal `|` is unsupported by the `|` deep-link convention
  (runRoot decodes before splitting). Pathological; not handled.
