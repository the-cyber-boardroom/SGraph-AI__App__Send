# Changelog — App-iframe capabilities Phase 4A: consent surface + requestPermission

**Version:** v0.27.79 · **Date:** 2026-05-27 · **Author:** Dev (branch `claude/exciting-brown-G2P9Z`)

## Summary

The consent machinery that the vault lifecycle verbs (Phase 4B/5) will use, rendered on the HUD
(host chrome — un-spoofable by the iframe).

- **HUD consent bar** (`app-hud.requestConsent(verb, path, cb)`): inline Allow/Deny in the HUD centre;
  resolves only on a real user click. `app-hud._consentLabel` builds the prompt text.
- **`app-shell._consent(verb, path)`**: one-time per **(vault, appId, verb)** cached in localStorage
  (`sg-app-grant:<vaultId>:<appId>:<verb>`); `vault.delete` always re-confirms. Serialised queue so
  concurrent prompts don't collide. `appId = SHA-256(app.json)` computed at open (A4).
- **Privileges chip is now clickable** → minimal permissions panel: `window.confirm` to **reset** this
  app's cached consents (`app-shell._resetConsents` via the `app-hud:reset-consents` event). Manifest
  grants themselves are a fixed ceiling and not editable here.
- **`sg.ui.requestPermission(verb, path)`** (`__sgCmdType:'ui'`): app asks for a declared-but-consent-
  gated verb; host shows the consent bar; resolves `{granted}`. Undeclared verb → `EPERM` (the manifest
  ceiling); floored path → rejected.
