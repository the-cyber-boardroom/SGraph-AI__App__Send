# Changelog — App-iframe capabilities Phase 4B: vault.create + vault.unlink

**Version:** v0.27.79 · **Date:** 2026-05-27 · **Author:** Dev (branch `claude/exciting-brown-G2P9Z`)

## Summary

The iframe can now create a child vault wired into a folder, and unlink one — both consent/grant-gated.

- **`vault.create` (`__sgCmdType:'vault'`)**: gate `vault.create` grant + HUD consent + token, then
  `SGVault.create` with a **proper vault key** (high-entropy passphrase, never the `word-word-NNNN`
  simple-token shape), write a keyless `<slug>.link.json` into the target folder, and a portable
  read-only owner record via `VaultLinks.saveRoRecord` (read_key tier). Read-through child (agreed v1
  scope). Reuses the host "Add link" pattern (`vault-browse-edit _showAddLink`). Reply
  `{vault_id, ref_id, ref_file_id}` — keys stay host-side.
- **`vault.unlink`**: gate `vault.unlink` grant + token; deletes the `.link.json` (child stays on the
  server — reversible).
- **`vault.delete`**: **deferred** — returns `ENOTIMPL`. Secure server-destroy needs the child WRITE
  key, but there is no owner-secret tier to store it (`ro-links.json` is read-tier, readable by parent
  read-holders). See "Blocked" below.
- In-iframe API: `sg.vault.create(path,label)` / `sg.vault.unlink(path)` / `sg.vault.delete(path)`.

## Blocked — needs a decision (Phase 5, vault.delete)

`SGSend.vaultDelete(vaultId, fileId, writeKey)` exists, but authorising it needs the child's **write
key**. Storing that in the read-tier `ro-links.json` would expose write capability to any parent
read-only-token holder — a vulnerability. A secure `vault.delete` requires:
1. a new **owner-secret-tier** credential store (double-encrypted via `vault-hkdf` owner key), written at
   `vault.create` time, and
2. AppSec sign-off on the destructive endpoint (existence-oracle / write-key findings, appsec v0.22.6).

Not shipping the insecure alternative. Awaiting a decision on building the owner-secret store.
