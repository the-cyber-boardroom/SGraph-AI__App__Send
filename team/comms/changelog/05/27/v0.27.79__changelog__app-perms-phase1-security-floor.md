## Summary

First slice of the app-iframe permission model: a **non-grantable security floor** plus the pure
logic module both depend on. No app-facing API yet; pure hardening.

- **New module `app-permissions.js`** (`_common/js/components/app-shell/`) — DOM-free, bridge-free,
  `globalThis.AppPermissions`: `normalizePath`, `hasVaultSegment`, `isFloor`, `parsePermissions`,
  `can`, `appId`. Loaded on `/en-gb/app` before `app-shell.js`. Unit-tested in the jsdom-free harness.
- **Floor wired into the VFS bridge** (`app-shell.js`): the iframe now
  - cannot **write** `.vault/**` or the legacy root `app.json` → `EPROTECTED`;
  - cannot **read** `.vault/**` → `EPROTECTED` (closes the embedded-token read vector — `.vault/app.json`
    may carry the server access token);
  - cannot **nav** into `.vault/**`;
  - cannot **list** `.vault/**` — entries are filtered from `vfs.list` results and from the injected
    page-layout `fileList`; a direct `list('.vault…')` returns `ENOENT` (no existence oracle).
- The floor **normalises the path itself** (collapses `.` / `..` / `//`), so the bridge's absolute-path
  branch (`wPath.slice(1)`, which skips `_resolvePath`) cannot be used to slip `/x/../.vault/app.json`
  past it.

The floor governs the **iframe bridge only** — the owner editing `.vault/`/`app.json` in `/vault` mode is
unaffected, and the host's own reads of `.vault/app.json` (e.g. token resolution) are not bridge calls.

## Test impact

- **39 jsdom-free unit assertions pass** (`node tests/unit/vault_ui/loader/test__app_permissions.js`):
  path normalisation incl. traversal, `.vault` segment detection (root + nested + case), floor
  read/write rules, grant parsing (true/false/array, prefix vs exact), `can` defaults (read-allow,
  mutate-deny), scoping, and defensive parse of malformed blocks. All three edited JS files syntax-clean.
- **Should break (good):** any app that was writing/reading `.vault/**` or root `app.json` via the bridge
  — none should exist; that was never a supported app operation.
- **Should NOT break (bad if it does):** ordinary reads/writes outside `.vault/`; reads of root
  `app.json` are still allowed (only `.vault/**` reads are floored).
- **Browser verification (gap):** confirm `vfs.read('.vault/app.json')` → `EPROTECTED`; `vfs.list('/')`
  omits `.vault`; a normal app still reads/writes its own files.

## Notes

- `READ_DEFAULT = true` in `app-permissions.js` — Phase 6 flips it to default-deny once apps declare

- `parsePermissions`/`can`/`appId` are built now (shared infra) but only `isFloor`/`normalizePath`/
  `hasVaultSegment` are wired into the bridge in this phase; the grant gates land in Phase 2.
