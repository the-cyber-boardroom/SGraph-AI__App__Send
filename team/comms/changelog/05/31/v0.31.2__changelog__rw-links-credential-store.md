## Change

`VaultLinks` gains the owner-secret tier alongside the existing `ro-links.json` tier:

- `RW_LINKS_FILE = 'rw-links.json'` + `loadRwLinks` / `resolveRwRef` / `saveRwRecord` / `deleteRwRecord`,
  mirroring the ro-record trio (same on-disk map shape, same merge-on-save, same push-to-server).
- The rw record stores the child's FULL key as an opaque `sealed_key` — sealed by the **caller**
  (app-shell) with the parent owner's **write** secret. `vault-links.js` is **key-blind**: it persists
  and returns the opaque blob and never seals/unseals.
- `saveRwRecord` **fails closed** on misuse: throws if `sealed_key` is absent, and **refuses** any
  record carrying a plaintext key field (`key` / `full_key` / `vault_key`) so a raw key can never land
  here by mistake. Read-only parent vault → throws (cannot write owner records).

**Security shape (D1 accepted by Dinis 2026-05-31):** the file is a normal vault file, so the parent's
`read_key` already encrypts it at rest; the per-record key is *additionally* sealed with the parent's
write secret. Net: a parent **reader** can open the file but still cannot recover a child full key —
only a parent **owner** (write-secret holder) can unseal. Holding the child's writable key in the parent
is the accepted, intended mechanism for managing sub-vaults from the parent.
