# Changelog — an app can now end the recording it started

**Date:** 2026-08-03 · **Area:** Vault UI — `app-shell.js` (`sg.llm.*` bridge)
**Source:** Dinis, from a working PoC — *"it doesn't seem to be able to stop the recording from inside the Vault App … once the user has privs to call the llm audio mode, then the full workflow should be controllable from inside"*

## Whose bug it was

**The vault's.** The app rendered a Stop button, called the host, printed *"asked the host to
stop"* — and the host's bar kept counting. That app was written correctly against an API that
did not exist.

`sg.llm.listen()` started a take that only the **host's** Stop/Cancel buttons or `maxMs` could
end. `sg.llm.cancel(id)` is the chat-streaming cancel and operates on stream ids — a different
mechanism entirely, so an app-side button had nothing real to call. An app that may open a
microphone must be able to close it; that was simply missing.

## What was added

```js
const p = sg.llm.listen({ maxMs: 120000 });        // don't await yet — you need the stop path
myStop.onclick   = () => sg.llm.listenStop();      // → p resolves with the transcript
myCancel.onclick = () => sg.llm.listenCancel();    // → p rejects EABORT, microphone released
const { text } = await p;
```

| Verb | Behaviour |
|---|---|
| `sg.llm.listenStop()` | Ends the take as *Stop & send* does — transcribe, and resolve the **original** `listen()` promise. Stopping does not open a second channel to read the result from. |
| `sg.llm.listenCancel()` | Ends it as *Cancel* does — release the device, reject the original promise with `EABORT`. |
| `sg.llm.listening()` | `{recording}`, so an app can render its own button state. |

All three sit behind the **same `llm.listen` grant** and raise **no consent prompt**. Ending a
take you already started is strictly less authority than starting one, and nobody should have
to approve stopping. An app with no microphone grant still gets `EPERM` on all three.

Both stop verbs resolve `{stopped:false}` when nothing is recording, so calling stop defensively
— on unmount, on a route change — is safe and needs no error handling.

**The host's own Stop/Cancel stay on the bar.** An app gaining a stop button must not cost the
user theirs; that bar is the reason a microphone cannot be opened invisibly.

## Bug found while implementing

A second `listen()` while one was in flight would have opened a **second recorder over the
first** — two live microphones, two bars, and the first take's stop handle overwritten and
unreachable. Now refused with `EBUSY`. Nobody hit this yet; it became reachable the moment apps
started driving takes themselves.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__app_shell_llm_bridge.js` (63 → **79**) — two new suites driving the real host handler
  with real postMessage frames: stop/cancel are distinguishable (`finish(false)` vs
  `finish(true)`), stopping when idle succeeds with `{stopped:false}`, `listening()` reports
  state, all three are refused `EPERM` without the `llm.listen` grant, an unknown `listen*`
  action is still refused (the capability map is the allow-list, not a prefix match), and a
  second `listen()` is `EBUSY` **without opening a second microphone**.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- The HUD bar, its buttons, consent, budget, model policy and the ledger are untouched.
- Apps that only `await sg.llm.listen()` and let the host bar end the take behave exactly as
  before.
