# Changelog — release channels for vault apps ("pin a version")

**Date:** 2026-08-03 · **Area:** Vault UI — `/en-gb/app/` (app-shell + app-hud) + root routing
**Spec:** `team/roles/architect/reviews/08/02/v0.33.47__architect-spec__vault-release-channels.md`
**Source:** Dinis voice brief 2026-08-02 · **Decisions:** answered by Dinis 2026-08-03

## What changed

A vault can now publish **named releases**, and a viewer can pin to one. Pushing new work no
longer changes what an existing holder of the link sees.

Nothing is copied: SGit objects are immutable and content-addressed, so a release **is** the same
objects, not a restored duplicate that might have drifted.

### `.vault/releases.json` (new, optional)

```json
{ "schema": "sg-releases/v1",
  "default": "v1.1",
  "allowLive": true,
  "releases": [
    { "name": "v1.2", "commit": "<id>", "label": "Black Hat demo", "notes": "…" },
    { "name": "Old Pilot", "commit": "<id>" } ] }
```

Inside the permission floor → an app can neither read nor tamper with it. **Absent file ⇒ nothing
changes anywhere** (no HUD chrome, live HEAD as today).

### Resolution order — `url > stored > default > live`

| Source | Rule |
|---|---|
| **URL pin** (`#key\|@v1-2`) | Beats everything. A shared link must show the same thing on every device. |
| **Stored choice** | Only ever written by an **explicit** selection, so a vault nobody pinned reloads to the latest version. Device-local (same tier as `sg.state.*`). |
| **`default`** | Binds *other viewers*, **not the owner** — otherwise "why aren't my pushes showing up?" becomes permanent. |
| **Live HEAD** | Today's behaviour. |

A URL pin naming a release that no longer exists resolves to live **with a visible warning** —
silently serving different content than the link asked for is the exact failure this prevents. A
stale *stored* pin falls through quietly (it is not worth nagging about on every open).

### Names — free text **and** semver-ish (both supported)

Names are free text (`"Black Hat demo"` reads better to an audience than `v1.2`), uniqueness
enforced case-insensitively, and every name is **also** addressable by its slug — so
`#key|@black-hat-demo` and `#key|@v1-2` both work.

### Pinned = read-only, for everyone including the owner

`PinnedVaultDataSource.writable` is always `false`; mutations reject with **`EPINNED`** (distinct
from `EREADONLY` — different problem, different fix: "switch to Live to edit"). Committing on top
of an old tree would fork the branch.

### HUD

A `<select>` (Live + each release) plus an **amber `⏱ <name>` pill** whenever the view is not the
latest — the "gentle visual clue". Both render **only** when the vault publishes releases.

## The traps that were handled (each would have bitten)

1. **Auto-sync un-pinning a viewer mid-demo.** `_checkBehind` fast-forwards and remounts. While
   pinned it now **suppresses the remount** and surfaces "a newer version has been published"
   passively instead. This was the single most dangerous interaction.
2. **Reading the release map at the pinned commit.** It is read at **HEAD**, always — otherwise
   pinning to v1.0 freezes the release list to whatever v1.0 knew about, with no way back.
3. **Lazy `.vault` sub-tree** — walked before listing (same trap as the LLM `ENOKEY` bug).
4. **`getFileList()` is synchronous** on the live source; the pinned one pre-warms in `warm()` so
   the contract is preserved rather than rippling an async change through every caller.
5. **Flat commit maps carry no folder rows** — intermediate folders are synthesised so tree views
   behave as they do live.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__sg_releases.js` (**new**, 47) — the precedence table, owner-vs-other `default`, explicit
  `"live"`, visible failure for an unknown URL pin, quiet fall-through for a stale stored pin,
  free-text **and** slug addressing, and "no releases ⇒ behaves exactly as today".
- `test__pinned_data_source.js` (**new**, 27) — serves the OLD commit's bytes (incl. its
  `app.json`), sync `getFileList()` after `warm()`, synthesised folder rows, `EPINNED` on every
  mutation, and two pins of one vault staying independent.
- `test__routing_decisions.js` (+9) — `@name` extraction, composition with `app:` deep links in
  either order, bare `@` ignored, redirect target unchanged.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- **A vault without `releases.json` is untouched** — no HUD chrome, no behaviour change. Pinned by
  the "behaves exactly as today" suite.
- `test__bundle_freshness.js` — none of the changed files are in the kernel bundle.
- Existing deep links (`#key|app:path`, `#key|path`) parse unchanged.

## Not built yet

- **"Publish as release" UI.** Releases are authored by editing `.vault/releases.json` in the vault
  editor today. The SGit history view already lists commits with a diff screen, so a
  "publish this commit as a release" action there is the natural next step (spec §5.4).
- `/vault` browser parity — the picker is `/en-gb/app/` (where demos run) only.
- Sub-vault children are **not** pinned (a linked child vault has its own HEAD). Stated, not hidden.
- **GC roots:** there is no garbage collection today; when one is built, pinned commits must be
  roots or a published release could be collected out from under a live link.
