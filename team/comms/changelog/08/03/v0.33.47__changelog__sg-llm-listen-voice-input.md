# Changelog — `sg.llm.listen()`: voice input for vault apps

**Date:** 2026-08-03 · **Area:** Vault UI — `/en-gb/app/` (app-shell + app-hud)
**Source:** Dinis — "voice support so a user showing a vault from an iPad can interact by voice"
**Reuses:** SG/Tools `core/sg-audio` + `core/sg-audio-decode` (see "What we did not build")

## What changed

One call, and an app gets speech as text:

```js
const { text } = await sg.llm.listen();     // opts: {maxMs, model, prompt}
```

The **host** opens the microphone, shows a red recording bar with Stop/Cancel, converts the
audio to a format OpenRouter accepts, transcribes it with the vault's key, and returns text.

## What we did **not** build (and why that matters)

The SG/Tools team already solved the two genuinely nasty parts, versioned and CORS-open, so
`sg-voice.js` lazily `import()`s them rather than reimplementing:

| Module | Used for | The problem it solves |
|---|---|---|
| `core/sg-audio` v0.1.0 | `getBestMimeType`, `startRecording`, `stopRecording` | iOS Safari records `audio/mp4` (AAC); Chrome records `audio/webm` (Opus) |
| `core/sg-audio-decode` v0.1.0 | `blobToWav`, `OR_SUPPORTED` | **`webm` is not on OpenRouter's accepted list.** Three-tier never-fail decode → WAV |

Consequence: **iPad is the zero-conversion path** (m4a goes straight through); desktop Chrome
transcodes to WAV automatically. Callers never see the difference.

## Why capture lives in the host, not the app

A vault app frame is `sandbox="allow-scripts allow-forms"` with a **null origin**, where
`navigator.mediaDevices` is `undefined`. The SG/Tools integration guide documents the identical
constraint and assigns capture to the embedder.

That constraint produces the right design anyway: **recording happens on host chrome, so an app
cannot open a microphone without the user seeing it.** The red bar is a full-width sibling of the
chrome row — the same structural slot as the consent bar — so it appears in every `hud.mode`,
including `hidden` and `none`. Audio never enters the app frame; the app receives text.

## Security shape

| Gate | Behaviour |
|---|---|
| `permissions.llm.listen` | **Its own grant, never implied by `llm.chat`.** Recording a room is categorically different from sending text. |
| Consent | **Per use by default** (not once-and-cached like other verbs). `permissions.consent["llm.listen"]` can relax it for a kiosk. |
| Budget | Transcription is an ordinary paid call — same `SGLlm` client, model allow-list, spend caps and `VaultLlmLog` entry. Voice spend is not a separate untracked bill. |
| Cancel | Releases the microphone, not just the bar. A tab silently holding the mic open would be worse than the original problem. |
| No-HUD hosts | If there is no HUD to render a Stop button, recording falls back to a short fixed take rather than an open-ended microphone. |

New codes: `ENOMIC` (sandboxed / no device / browser refused), `EINSECURE` (not HTTPS),
`EABORT` (cancelled).

## Bug fixed in passing

`SGLlm.redactMessages` stripped `image_url` parts for log safety but knew nothing about
`input_audio` — a recording would have dumped tens of thousands of base64 characters into the
provenance log users are invited to read and paste into bug reports. Now redacted to a size note,
keeping the `format` for diagnosis.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__sg_voice.js` (**new**, 43) — the mime→format table (iOS `audio/mp4;codecs=…` → `m4a`),
  `isSendable` deciding when the decode runs, and **base64 chunked at 8190 not 8192** (8192 % 3 = 2
  would emit `=` padding mid-string; this repo shipped that exact bug once at v0.33.21). Also that
  `available()` never throws when `navigator` itself throws — the null-origin frame case.
- `test__app_shell_llm_bridge.js` (+18, now 63) — `listen` refused without its own grant *even
  when `chat` is granted*; `ENOMIC` when the mic is unavailable; declined consent never opens the
  microphone; and **no audio payload is returned to the frame**. Plus the redaction guard.
- `test__app_permissions.js` (+4) — `chat` does not imply `listen` and vice versa.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- `test__bundle_freshness.js` — the bundle was regenerated after the `app-permissions.js` change.
- Apps without `permissions.llm.listen` behave exactly as before.
- **`test__app_permissions.js` "llm block exposes only the declared verbs"** was updated from
  `chat,models,usage` to `chat,listen,models,usage` — an intended contract change. Its actual
  intent (no app-set spend limits leak into the manifest) is unchanged and still asserted.

## Known limits

- **Not verified on a real iPad.** The format logic is unit-tested and the module choice is the
  one SG/Tools ships for this exact case, but no device run has happened. Worth 5 minutes on the
  actual demo iPad before Black Hat.
- **Runtime dependency on `dev.tools.sgraph.ai`** for the two audio modules (consistent with the
  vault already loading `sg-layout` and `sg-llm-*` from there). Voice therefore does not work in
  `SGSend.staticMode`, which has no network by design. Override the base with
  `window.SG_TOOLS_BASE` if the modules move.
- No streaming/partial transcript — one take, one result. The SG/Tools `live-transcribe` tool
  does VAD-segmented near-realtime if that is ever wanted.
