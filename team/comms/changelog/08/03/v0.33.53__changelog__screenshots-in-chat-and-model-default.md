# Changelog — screenshots in the chat, images via `sg.llm.*`, and a better default model

**Date:** 2026-08-03 · **Area:** Vault UI — new `sg-vision.js`, `vault-llm-chat`, `sg.llm.*` bridge, `SGLlmConfig`
**Source:** Dinis — *"does our current chat llm capabilities support the sending of a screenshot (provided via copy and paste)"* → *"yes can you build this on both the current vault chat and the sg.llm.*"* → *"can you make the default model to be claude-sonnet-5"*

## 1. Paste a screenshot into the chat

Paste or drop an image into the composer. It attaches as a thumbnail chip and is sent with the
**next message only**, then clears.

That lifetime is deliberate and is **stated in the UI**, because it differs from files: a file
stays attached on purpose, but an image left attached would silently re-send — and re-bill — on
every subsequent turn. The transcript shows the image that was sent, so the log does not
misrepresent the conversation or what the call was billed for.

Two details that are easy to get wrong:

- **The paste handler only claims the event when the clipboard holds image FILES.** Most copies
  also carry `text/plain`; claiming those would have broken pasting text into a chat box.
- Big images are downscaled to 1568px on the longest edge — which is what the major vision
  models do server-side anyway, so sending more costs tokens and buys nothing. PNG, not JPEG:
  screenshots are flat colour and small type, exactly where JPEG ringing hurts.

## 2. Images from a vault app

```js
const part = await sg.llm.imagePart(blobOrBytes);      // Blob/File, bytes, or a data: URL
await sg.llm.chat({ messages: [{ role: 'user', content: [
    { type: 'text', text: 'What is wrong here?' }, part ] }] });
```

No new grant — an image is an ordinary `llm.chat` call. `imagePart()` runs **in the frame** (the
bytes are already the app's; a host round trip would buy nothing) and chunks base64 at **8190**.
`8192 % 3 === 2` puts `=` padding mid-string and `atob()` rejects it — a bug this repo has
shipped three times, so the helper exists specifically so nobody writes it a fourth.

Two things stay **host-side**, because neither is the app's to decide:

| Check | Why the host |
|---|---|
| Can this model read images? | A provider error names nothing. `EMODEL` here names the model. |
| Total image payload | It is spending the vault's key, so the ceiling is not the app's to raise (`EIMGSIZE`). |

## 3. Capability is read live, not hard-coded

OpenRouter's `/models` carries `architecture.modality` (`text+image->text`) and newer entries
`architecture.input_modalities`. `SGLlm.models()` already returned those objects verbatim, so
the truth was available for free — **this is better than how the audio model list was done**,
which is a curated list that has to be maintained.

The trap a naive `includes('image')` falls into: **`text->image` is a generator, not a reader.**
Only the input side of the modality counts, or a screenshot goes to somewhere it is never
looked at. When images are present and no catalogue is cached, the host **fetches one** rather
than fall back to the short offline list — refusing a model that *can* see is the worse error.

## 4. Ledger bug fixed

`promptChars` counted `typeof content === 'string'`, so a message carrying a 300 KB screenshot
logged **zero** prompt chars: the most expensive calls in the request pane reading as the
cheapest. Images are now their own count (`VaultLlmLog.images`), shown in the pane, and never
folded into the char total — a picture and a paragraph cost nothing alike.

## 5. A better default model

With no `models.default` configured, the panel auto-picks. It matched only on a **vendor
prefix** against an **alphabetically sorted** id list — so `anthropic/` matched
`anthropic/claude-3-haiku`, the oldest and weakest model on the key. Worse, haiku is not a
vision model, so a vault with no configured default could not read a pasted screenshot at all.

Named models are now tried first: `anthropic/claude-sonnet-5`, then opus-5, sonnet-4,
`google/gemini-3.5-flash`, `openai/gpt-5`. They are exact ids, so a rename drops through to the
vendor fallback rather than pinning something that no longer exists. **An explicit
`models.default` and the `models.allow` list still win** — otherwise the Settings page would
become advisory.

Also fixed: changing the model in the picker left the "Using anthropic/claude-3-haiku (no
default set…)" notice up, contradicting the control directly above it.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__sg_vision.js` (**new**, 62) — mime→format, the modality parser (including
  `text->image` being refused as a reader, and `input_modalities` winning over a stale
  `modality` string), 8190 chunking boundaries, `promptChars` not inflating on base64, and
  `imagesFromEvent` **not** claiming a text-only paste.
- `test__vault_llm_chat.js` (93 → **122**) — attach/remove/cap, the stated one-message
  lifetime, the multimodal message shape (and that a text-only turn stays a plain string),
  the transcript strip, the pre-send model warning, and the ledger counts.
- `test__app_shell_llm_bridge.js` (79 → **96**) — host-side vision refusal naming the model,
  the catalogue fetch happening once and only when images are present, `EIMGSIZE`, and the
  `imagePart` chunk constant.
- `test__sg_llm_config.js` (+9, now **53**) — sonnet-5 over alphabetically-first haiku, a named
  model from another vendor beating a weak same-vendor one, and the explicit default/allow-list
  still winning.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- Text-only chat is byte-for-byte unchanged — no gratuitous one-element content arrays.
- No new permission; `permissions.llm.chat` covers images.
