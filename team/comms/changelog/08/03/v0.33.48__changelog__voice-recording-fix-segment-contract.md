# Changelog — voice recording never started: SGVoice used the wrong `core/sg-audio` contract

**Date:** 2026-08-03 · **Area:** Vault UI — `_common/js/lib/sg-voice/sg-voice.js`
**Reported by:** Dinis — *"the error we also get when clicking on the record option: 'Could not start recording: onSegment callback is required'"*

## What was broken

Voice input shipped at v0.33.47 **could not record at all**. Tapping 🎤 in the vault chat
panel always failed with:

> Could not start recording: onSegment callback is required

## Root cause — an assumed API shape, never read

SG/Tools `core/sg-audio` is a **segment recorder**, built for long captures that must survive
device loss. Its actual contract:

```js
export async function startRecording(opts = {}) {
    ...
    if (!onSegment) throw new Error('onSegment callback is required');   // ← hard requirement
}

export async function stopRecording(session) { ... }                     // ← Promise<void>
```

Audio is delivered **only** through `onSegment`. `stopRecording()` resolves to nothing.

`SGVoice` was written against a one-shot recorder that does not exist:

```js
return m.audio.startRecording(opts || {});          // no onSegment  → always threw
var rec = await m.audio.stopRecording(session);     // undefined
var blob = rec && (rec.blob || rec);                // undefined → blobToWav(undefined)
```

So there were **two** bugs stacked: recording could never start, and had it started, stopping
would have failed on the next line. Only the first was reachable, which is why only the first
was reported.

The honest note: the export *names* were checked, the *signatures* were not.

## The fix — adapt, don't fork

A voice memo wants one take, one blob, transcribed immediately — the opposite shape to
segmented durable capture. `SGVoice.start/stop` now adapts:

| | Behaviour |
|---|---|
| `start()` | Passes the required `onSegment`, collecting each blob into a buffer **hung off the session** (two panels can hold two microphones; neither may collect the other's audio). Timeslice is long (10 min) so a normal take produces exactly one segment and there is no reassembly to get wrong. |
| `stop()` | Awaits `stopRecording()` (which resolves only after the final segment), joins the collected blobs into one `Blob` in arrival order, then converts only if the container is not OpenRouter-accepted. |
| `cancel()` **(new)** | Releases the microphone and discards the audio. It stops the tracks itself, because `sg-audio.stopRecording()` early-returns for an already-stopped session **without touching them** — the exact path a cancel-after-stop takes. |
| Silent take | Throws `ENOAUDIO` instead of billing a transcription call on zero bytes. |

Both cancel paths — `vault-llm-chat._stopVoice(true)` and `app-shell._recordAndTranscribe`'s
Cancel button — now call `cancel()` rather than `stop()`. They were calling `stop()`, which
assembles and returns audio nobody wanted.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__sg_voice.js` (43 → **67**) — new runtime suites for `start`/`stop`/`cancel`. They run
  against a stand-in **copied from the real module's source, guard included**, because that is
  the only way to catch a signature mismatch in Node: the real module arrives via
  `import()` of a CDN URL. A `__setModules()` seam exists solely for this. Covered: `start()`
  passes `onSegment`; `stop()` reads audio from the segments and **not** from
  `stopRecording()`'s return value; iPad `m4a` skips conversion while Chrome `webm` forces
  exactly one; multi-segment joins preserve order; `ENOAUDIO` never reaches the decoder;
  `cancel()` releases the device including after a stop.
- `test__vault_llm_chat.js` (92 → **93**) — cancel goes through `cancel()`, and `stop()` is
  **not** called for a cancelled take.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- `transcribeWith`, the budget/model/ledger chokepoint, and the pure helpers
  (`formatFor`/`isSendable`/`bytesToBase64`/`audioPart`) are untouched.
- `sg.llm.listen` permission, consent and HUD behaviour are unchanged.

## Still true

**Not verified on a real iPad.** This fix removes a certain failure on every device; it does
not substitute for a device run. The `m4a` pass-through path in particular has still never
executed against a real recorder.
