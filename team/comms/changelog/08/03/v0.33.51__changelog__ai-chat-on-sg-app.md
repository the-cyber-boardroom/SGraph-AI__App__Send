# Changelog — AI Chat (with voice) on `/en-gb/app/`

**Date:** 2026-08-03 · **Area:** Vault UI — `/en-gb/app/`, `app-hud`, `app-shell`, new `LlmPanels`
**Source:** Dinis — *"how can we make this also available from inside a vault?"* (answer: SG/App chrome)

## What changed

A `✨ AI` button in the SG/App HUD opens **the same** `<vault-llm-chat>` and
`<vault-llm-requests>` panels the vault file browser has — multi-file context, cost ledger,
mic button, all of it — beside the running app.

## Why host chrome and not an app API

The panel runs at the **real origin** (the `/app` page), not in the app's frame. That means:

- it holds the vault key and the microphone **directly** — no bridge, no `sg.llm.*` round trip;
- **the app frame is never involved and sees neither**;
- **no app changes and no new permission.** Every existing vault app gets this the moment the
  page ships. An app cannot read the conversation, and cannot suppress the button beyond the
  ordinary `hud.show.llm` preference.

`sg.llm.chat()` / `sg.llm.listen()` remain the path for AI *inside* an app's own UI — those
still need grants. This is AI *beside* the app.

## `LlmPanels` — one implementation, two pages

Both pages mount panels into an sg-layout, and the bookkeeping has a trap that already shipped
once: **sg-layout detaches a panel's element before it emits `panel:closed`**, so a handler
that re-queries the DOM finds nothing, parks nothing, and orphans the element — after which
the button that reopens the panel is dead (fixed at v0.33.50).

Rather than copy that, `_common/js/lib/sg-llm/llm-panels.js` now owns it and **`vault-shell`
delegates to it**. The 28 assertions in `test__vault_shell_llm_panels.js` were written before
the refactor and pass unchanged after it, which is what makes the delegation safe to claim.

## The trap specific to `/app`

`layout.setLayout(_layoutCfg)` **rebuilds the tree and unmounts everything not in the config**.
The AI panels are added with `addPanel()`, so they are not in `_layoutCfg` — toggling the debug
pane would have destroyed the transcript. The page now parks them first and re-shows whichever
were open. Asserted from source, because the symptom (a lost conversation) only appears to a
user mid-conversation.

## Author control

`hud.show.llm` — **on** in `full`, **off** in `minimal` (host chrome, same reasoning as the
activity meter). `"llm": true` forces it on in a stripped HUD; `"llm": false` turns it off in
`full` if a chat button would clash with the app's own UI.

## One contract change

`app-shell:ready` now carries the open `vault` so host chrome can resolve `.vault/llm` without
reaching into `app-shell` internals. The embed forwarder still copies **named fields only**
into its cross-origin `postMessage` — the vault object does not leave the page, and there is a
test asserting the forwarder never starts posting the whole detail.

## Files

**New:** `_common/js/lib/sg-llm/llm-panels.js`
**Changed:** `en-gb/app/index.html` (loads the components + `#llm-host` parking bay + wiring +
fallback CSS), `app-hud.js` (`.hud-llm-btn` → `app-hud:llm`), `app-hud-config.js` (`llm` flag),
`app-shell.js` (`vault` on ready), `vault-shell.js` (delegates to `LlmPanels`),
`index.html` + `en-gb/browse/index.html` (load `llm-panels.js`), `AUTHORING.md`

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__app_page_llm_panels.js` (**new**, 46) — `LlmPanels` in the `/app` host shape (where
  the parking bay *is* the host element), close→reopen with the element preserved,
  focus-don't-remount, `detachAll()` surviving a destructive `setLayout()`, and a missing
  fallback container degrading rather than throwing. Plus source guards: the page loads all
  three files in the right order, the debug toggle parks **before** `setLayout`, the HUD button
  exists and is flag-gated, and the embed forwarder still copies named fields only.
- `test__vault_shell_llm_panels.js` (28, unchanged) — now also the regression net for the
  `LlmPanels` extraction.

**Should NOT break (bad failures — investigate if they do):**
- Full vault unit suite green at commit time.
- `/vault` behaviour is byte-for-byte the same feature; only the implementation moved.
- `test__bundle_freshness.js` — nothing bundled changed.
- Apps with `hud.mode: "minimal"`, `"hidden"` or `"none"` see no new button.

## Not verified

**Not opened in a browser.** The panel logic is unit-tested and the page wiring is asserted
from source, but no one has clicked the `✨ AI` button on a real vault app yet. The two things
most worth checking there: the panel splitter with `--sgl-panel-header-height: 0px` (the app
page hides stack headers, so the chat's own `✕` is the way to close it), and whether the vault
arrives on `app-shell:ready` before the first open on a slow vault.
