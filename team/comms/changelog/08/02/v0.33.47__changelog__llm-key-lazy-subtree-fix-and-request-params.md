# Changelog — LLM key resolution fix, request params, inline confirm

**Date:** 2026-08-02 · **Area:** Vault UI (`/en-gb/vault/`, `/en-gb/browse/`)
**Follows:** `v0.33.47__changelog__vault-llm-chat-multi-file-and-cost-ledger.md`
**Reported by:** Dinis (3 items + 1 question)

## 1. BUG FIX — a configured AI key reported "No AI key configured"

**Symptom:** a vault with a valid `.vault/llm/config.json` (key sealed, `keyTier:"owner"`)
showed *"No AI key configured for this vault — add one in Settings → AI models"* in the chat.

**Root cause:** `SGVault.loadSubTreeOnDemand(path)` expands **exactly one level**
(`sg-vault--folder-ops.js:93`). `SGLlmVault.readConfig` expanded `/.vault`, which inserts `llm`
as *another* `_loaded:false` folder — so `listFolder('/.vault/llm')` returned `[]`, the config
read as absent, and `open()` returned `ENOKEY`.

**Why it looked intermittent:** in the session where Settings had just *written* the config, the
tree node was already materialised in memory and everything worked. It only broke on a **fresh
vault open**, i.e. after a reload — which is why the earlier screenshot showed a working chat
with a model selected and the later one did not.

**Fix:** `_ensureSubtree(vault, path)` now walks **every** path segment, expanding each lazy
level in turn. Same class of bug as the embedded-access-token one noted in the reality doc; this
is the nested-folder case of it.

**Second-order fix:** availability was resolved once, at vault open, and never revisited — so
even after configuring a key in Settings the panel kept insisting there was none until a full
page reload. `open()` now re-resolves when the current session is not `ok` (and does *not*
re-resolve when it is, so there is no wasted work).

## 2. No popups — the ledger's Clear confirms inline

`window.confirm()` in `<vault-llm-requests>` replaced with an inline confirm bar inside the
panel (Clear → bar with Clear/Cancel; Cancel focused by default). A native dialog steals focus
from the page, cannot be styled to match, and reads as a browser-level alarm for what is a
local, non-destructive act. The wording still states plainly that clearing the record does not
undo spend.

## 3. Request parameters are controllable again — and now actually plumbed

A `⚙` params bar in the chat header (collapsed by default): **temperature**, **top-p**, and
**max tokens**.

- Blank means *the provider's own default* — deliberately not a hard-coded `0.7`, because
  silently pinning a sampling parameter makes two vaults answer differently for no stated reason.
- **max tokens is clamped to the vault policy** (`limits.maxTokensPerCall` from Settings) and the
  clamp is *stated*, not silent: a per-session control must not be a way around the vault ceiling.
- The bar summarises what will actually be sent, including the policy default when unset.

**Transport gap closed:** `SGLlm.chat` previously supported `temperature` and `maxTokens` but had
no `top_p` at all, and nothing in the UI set any of them — the chat only ever passed the policy's
`maxTokensPerCall`. `topP` is now supported and all three are pinned by a test that captures the
outgoing body. Omitted params are **absent** from the request rather than sent as `null` (a null
temperature is a real value to some providers).

**On "did we lose this?"** — no control was removed in the multi-file change. The model picker
had disappeared because `_refreshModels()` returns early when the session is `ENOKEY`, i.e. it
was a *symptom of bug 1*. Fixing that restores the picker; the params bar is genuinely new.

## Test impact

**SHOULD break (good failures) if reverted:**
- `test__sg_llm_vault.js` (**new**, 17) — models lazy loading *faithfully* (one level per call)
  so the bug reproduces: verified failing against the pre-fix file with `reason=ENOKEY` and
  `loads=["/.vault"]`. Also pins that a genuinely absent config still says `ENOKEY`, an
  owner-sealed key in an ro-session still says `EREADONLY` (not `ENOKEY`), and a corrupt config
  never throws.
- `test__sg_llm.js` (+7) — the params reach the wire; omitted params are absent, not null.
- `test__vault_llm_chat.js` (+18) — params defaults/clamping/reset, and the re-resolve-on-open
  behaviour (including that an available session is *not* re-resolved).
- `test__vault_llm_requests.js` (+10) — clearing confirms inline; the test replaces
  `window.confirm` with a throwing stub, so any regression to a native dialog fails the suite.

**Should NOT break (bad failures — investigate if they do):**

- `SGLlmVault.readConfig` on an already-loaded tree does no extra expansion (pinned).
- Read-only sessions: unchanged — `EREADONLY` still arises cryptographically, not by policy check.

## 4. Answer — what is still missing from the `sg.llm.*` brief

Plan: `team/roles/architect/reviews/08/02/v0.33.43__architect-review__sg-llm-kernel-capability-plan.md`

| Phase | Scope | Status |
|---|---|---|
| **3 — Admin UX** | Settings panel: key, models, caps, test connection | **SHIPPED** (pulled forward) |
| **5 — Host-native chat** | Chat surface in any vault with a key, no app code | **SHIPPED** (pulled forward, + multi-file/ledger/params since) |
| **1 — Custody + chat over the bridge** | `sg.llm.{available,models,chat,cancel}`, SSE-over-postMessage, consent, CSP coupling, HUD indicator | **NOT BUILT** |
| **2 — Accounting (kernel-side)** | `sg.llm.usage()`, kernel budget enforcement, HUD Σ pill | **PARTIAL** — the two-source cost model and per-session caps exist *host-side*; nothing enforces them at a bridge chokepoint |
| **4 — Minted credentials** | Short-lived budget-capped token from SG-API; vault holds a *reference*, not a raw key | **NOT BUILT** — the commercially load-bearing phase |

**Concretely missing for `sg.llm.*` (the app-facing capability):**

1. **Bridge verbs** — no `__sgCmdType:'llm'` handler exists in `app-shell.js`. `permissions.llm`
   *is* parsed (`app-permissions.js:164`, `{chat, models, usage}`, default-deny) and
   `permissions.network` too, but nothing consumes them.
2. **SSE over postMessage** — the `{__sgLlmDelta: id, delta}` frame protocol, kernel-side
   coalescing (~50 ms), tail-flush before the terminal reply, and `sg.llm.cancel(id)`.
3. **`sg.llm.available()`** — apps must be able to degrade *before* rendering a chat UI.
4. **Consent + HUD** — the "this app is calling an LLM" indicator and the `once` consent grant.
5. **CSP coupling (§7 egress lockdown)** — the security thesis only closes when app frames
   cannot reach the network directly; without it the bridge is a convenience, not a boundary.
6. **Kernel-side budget enforcement** — caps are currently enforced by the chat panel on itself.
   An app calling through the bridge would be unbudgeted.
7. **Phase 4 minted credentials** — until this lands, sharing a vault still shares a key
   (threats T4/T5 in the plan).

The engine (`SGLlm`) and the resolver (`SGLlmVault`) were built DOM-free and bridge-free
precisely so the kernel can reuse them unchanged — Phase 1 remains *"expose the existing engine
over postMessage + consent + CSP"*, not "build an engine and a bridge at once".
