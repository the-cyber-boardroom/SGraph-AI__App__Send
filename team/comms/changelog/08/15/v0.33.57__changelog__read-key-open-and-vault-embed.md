## sgit.ai integration (the driving use case)

```html
<script src="https://dev.vault.sgraph.ai/_common/js/lib/sg-embed/sg-vault-embed.js"></script>
<!-- main vault UI (files + SGit history) -->
<sg-vault-embed surface="vault" key="sgit_rk1_<64-hex>:<vault_id>" style="height:600px"></sg-vault-embed>
<!-- App UI (kernel + HUD, hosting the inner vault-app iframe) -->
<sg-vault-embed surface="app"   key="sgit_rk1_<64-hex>:<vault_id>" style="height:600px"></sg-vault-embed>
```

Direct links also work now: `https://dev.vault.sgraph.ai/#<64-hex>:<vault_id>` (root hash
inbox → App UI → falls back to the vault UI when the vault has no app.json).

## Review fixes (same day — post-implementation code review, 7 findings, all fixed)

A clean-room review of the branch diff surfaced 7 findings; all are fixed in the follow-up commit:

1. **`vault-error` was never sent** — a failed embed open left the parent's `mount()` hanging
   to its generic 14s timeout. Added `EmbedProtocol.vaultErrorMessage` +
   `EmbedReceiver.notifyError`; both shells' open-failure paths now post the real reason.
2. **Embed-mode entry form was still live** — the recent-vaults buttons and manual form could
   open (and PERSIST) a credential inside the iframe, contradicting the no-persist invariant.
   `vault-shell._initEmbed` now replaces the entry card with a waiting/error state;
   `_onRefresh` falls back to the open vault's transport since the entry component is gone.
3. **App UI rejected format 4** — `_initWithKey` only matched the colon form. Replaced the
   two hand-copied regexes (dispatch + badge) with a NEW shared
   `SGVaultCrypto.parseReadOnlyCredential` accepting both forms; both surfaces now agree.
4. **Embed teardown lost in the refactor** — `disconnectedCallback` cleaned the now-dead
   `_embedOpenHandler` and never stopped the receiver. Both shells now call
   `_embedReceiver.stop()` (and vault-shell also unsubscribes its mounted handler).
5. **`?embed=1` failed OPEN on deploy skew** — gating `_initEmbed` on
   `typeof EmbedReceiver !== 'undefined'` fell through to the storage auto-open when the
   script was missing. Gate reverted to embed-mode-only; a missing receiver now fails
   CLOSED with an explicit error inside `_initEmbed`.
6. **`SgVaultEmbed._ensureHelpers` cached a rejected promise forever** — one transient
   script-load failure bricked every later `mount()`. The cache now clears on rejection.
7. **Format-6 regex hand-copied ×3** — consolidated to `parseReadOnlyCredential` (app-shell
   sites) + a drift-guard test asserting it agrees with `VaultLoaderFormat` on both read
   formats and all the near-misses.

New/extended tests: `notifyError` wire shape; `parseReadOnlyCredential` suite (9); the
cross-module drift guard (8). Kernel bundle regenerated again (crypto lib changed).

## Review round 2 (verification pass on the fixed state — 5 findings, all fixed)

1. **Fail-open moved one script down** — the round-1 fix still gated `?embed=1` on

   the storage auto-open. All three gates (app-shell, vault-shell, vault-entry) now use a
   DEP-FREE inline `URLSearchParams` check; missing embed modules fail CLOSED with an

## Review round 3 (live-testing feedback — Settings page in a read-key session)

Live use on dev.vault.sgraph.ai surfaced three Settings-panel bugs in RO sessions; fixed in
`vault-settings.js` (+ new `test__vault_settings_readonly.js`, 14 assertions):

1. **"Read Key: (unavailable)" in a session opened WITH the read key** — the imported
   CryptoKey is non-extractable by design, so `exportKey` threw; the hex is now recovered
   from the vaultKey string via `parseReadOnlyCredential`. This also fixes the cascaded
   "(unavailable)" in the Copy-both field and the `sgit clone` command. ro-token sessions
   (hex never retained) legitimately still show unavailable.
2. **The RO credential was labelled "Vault Key"** with the owner warning ("access all
   files") — RO sessions now relabel the section "Read-only key (this session's
   credential)" and scope the warning to read (cannot write, cannot become the vault key).
3. **The rename Save button was live in RO sessions** — now disabled with a tooltip.

## Review round 4 (live-testing feedback — hidden settings file + Untitled fallback)

1. **`.vault-settings.json` is now VISIBLE in the Files tree.** The file that names the
   vault lives in `vault._settings` (parsed out of the commit tree at load), so it never
   appeared in root.children and the tree never showed it. `VaultDataSource` now lists it
   synthetically in `getTree`/`getFileList` (reads/writes already round-tripped through the
   existing special cases); delete/rename are refused with descriptive errors; a legacy
   real entry produces no duplicate. Test: `test__vault_settings_file_listing.js` (9).
2. **Filter inventory (requested review).** Name-based filtering in the vault web UI:
   `.vault-settings.json` / legacy `.vault-settings` (intercepted at tree load — now
   re-listed synthetically) was the ONLY file hidden from the vault UI's own tree.
   Related but different surfaces: `.vault/**` is hidden from *vault apps* by the bridge
   permission floor (the vault UI itself shows it); `seedFrom` skips `.vault/**` when
   copying templates; `*.link.json` files are transformed into sub-vault mounts by
   `composite-data-source` (visible, rendered as link cards); `bare/*` objects are
   storage-level and never in any tree.
3. **'Untitled Vault' now falls back to the app's title.** New `SGVault.hasCustomName`
   (false when settings were synthesized with the placeholder; set false by setName /
   settings-file edits). When a never-named vault hosts an app with a `title`:
   the App UI suppresses the placeholder chip (the adjacent app title IS the identity,
   duplicating it would be noise), and the main vault UI header adopts the app title
   (`_applyAppJson`). Vaults with a real name are unchanged.

## Security notes (for AppSec review)

- Read keys cannot escalate to write — independent PBKDF2 derivations (pre-existing property;
  the feature rests on it).
- `SGVault.openReadOnly` fails closed (`_passphrase=null`, `_writeKey=null`, key imported
  non-extractable/decrypt-only) — unchanged, now reachable from two more credential shapes.
- Embed mode: credential never persisted (noPersist on open + refresh; entry auto-open
  suppressed); one-shot re-key-proof listener; sandbox sanitiser still refuses
  `allow-same-origin` / `allow-popups-to-escape-sandbox`.
- The `<sg-vault-embed key>` HTML attribute is documented as publishable-credentials-only.
- Open question for AppSec (brief §7.4): should any vault-shell surface (settings, token
  manager, SGit view) be suppressed in embed mode? Not done in this change — the RO tier
  already hides owner sections; embed currently shows exactly what a read-key holder sees.
