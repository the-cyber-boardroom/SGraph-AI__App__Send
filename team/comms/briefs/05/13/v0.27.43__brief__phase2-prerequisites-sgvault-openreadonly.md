# Brief — Phase 2 Prerequisites: SGVault.openReadOnly()

**Version:** v0.27.43
**Date:** 2026-05-13
**Author:** Explorer (Claude Code session claude/sgraph-send-test-harness-L7tPF)

## Context

Phase 1 of the vault/token harness ships a working RO token creation flow. Each token's encrypted
payload contains:

```json
{ "vault_id": "<12-hex-char vaultId>", "read_key": "<base64-encoded 32-byte AES-256-GCM key>" }
```

The `read_key` is the raw vault read key exported via `crypto.subtle.exportKey('raw', vault._readKey)`
and base64-encoded (standard `btoa`). It is 44 characters long (32 bytes → 44 base64 chars).

Phase 2 (wiring `#ro-[token]` URLs to actually open a vault in read-only mode) **cannot proceed**
until `SGVault` gains a way to open a vault from a raw key rather than a passphrase.

---

## Blocker: SGVault.openReadOnly() Does Not Exist

`_common/js/lib/sg-vault/sg-vault.js` only has `SGVault.open(sgSend, fullVaultKey)` which
derives keys from a passphrase string. There is no way to supply a raw CryptoKey or its bytes.

The Phase 2 brief (`v0.27.20__brief__readonly-sharing-and-owner-secrets-implementation.md §3`)
says to add `#ro-[token]` hash support to `vault-shell.js`. That requires calling something like:

```js
const vault = await SGVault.openReadOnly(sgSend, vaultId, readKeyBase64);
```

This call does not exist. Adding it to `_common/` is **out of scope for the vault/token harness**
(Phase 1 constraint: no changes to `_common/`), so it is a prerequisite for Phase 2.

---

## Required API Surface

The new static method on SGVault:

```js
static async openReadOnly(sgSend, vaultId, readKeyBase64) {
    const vault = new SGVault(sgSend);
    vault._vaultId     = vaultId;
    vault._passphrase  = null;  // no passphrase in RO mode
    vault._writeKey    = null;  // no write access — vault.writable returns false
    vault._readKey     = await crypto.subtle.importKey(
        'raw',
        Uint8Array.from(atob(readKeyBase64), c => c.charCodeAt(0)),
        { name: 'AES-GCM' },
        false,
        ['decrypt']
    );
    vault._initManagers?.();
    // Load tree from vaultId (no clone ref needed for read-only)
    await vault._loadTree(vaultId);
    return vault;
}
```

Key invariants:
- `vault.writable` → `false` (already gated on `_writeKey !== null` in sg-vault.js)
- `vault.vaultId` → the 12-hex-char id passed in
- No write operations may succeed — all vault.addFile/updateFile/push calls should throw
- `vault.loadSubTreeOnDemand(path)` must still work (read-only fetch)
- `vault.getFile(path, name)` must still work

## read_key Format Reference

| Property | Value |
|---|---|
| Algorithm | AES-256-GCM |
| Length | 32 bytes |
| Encoding | base64 (standard `btoa`), 44 characters |
| Extractable | false when imported for RO use |
| Usages | `['decrypt']` only |

The base64 string is safe for JSON transport and URL inclusion (no URL-encoding needed beyond
standard JSON string rules — no `+`, `/`, or `=` cause issues inside a JSON string).

## Security Notes

- The raw read key in the token payload is encrypted with the friendly token (`word-word-NNNN`)
  as PBKDF2 passphrase (100,000 iterations, SHA-256, AES-256-GCM). Intercepting the ciphertext
  without the token is computationally infeasible.
- The token itself is shared out-of-band (URL fragment: `#ro-word-word-NNNN`) and never sent
  to the server — only the encrypted payload blob is stored server-side.
- **NEVER commit vault keys, access tokens, or share tokens to Git.** The token is a secret.
