## Why this brief set exists

You are about to build one or more **FastAPI Lambda functions** that must reuse two
things SG-Send already does well:

1. **Optimised dependency management** — dependencies are pip-installed once,
   stripped, zipped, and uploaded to S3 as a single content-addressable archive;
   the Lambda downloads + extracts that one zip at cold start (single STS + single
   S3 GET), and reuses the `/tmp` extraction on warm containers.
2. **The `Serverless__Fast_API` + `Fast_API__Routes` coding patterns** — a
   batteries-included base class (routing, MCP, CORS, OpenAPI, Mangum adapter,
   SnapStart-friendly init) plus a convention-driven route-class pattern with
   Type_Safe schemas and per-route auth.

The canonical, working reference implementation is the **User Lambda** at
`sgraph_ai_app_send/lambda__user/`. Everything in these briefs is taken from that
code, not from aspiration. When in doubt, read the User Lambda.

## Assumed environment (these briefs are self-contained)

These briefs are written so a fresh session can build a FastAPI Lambda **without
access to the SG-Send repo**. You only need the published `osbot-*` packages:

| You need (pip) | Provides | Used in |
|---|---|---|
| `osbot-fast-api-serverless` | `Serverless__Fast_API`, `Deploy__Serverless__Fast_API` | the app class + deploy |
| `osbot-fast-api` | `Fast_API__Routes` | the route classes |
| `osbot-utils` | `Type_Safe` (+ `Safe_Str__Id` etc.) | schemas, identifiers |
| `boto3` (stdlib + this) | S3 / STS for the dependency loader | the Builder/Loader |

**One thing is NOT in any `osbot-*` package:** the combined-zip
`Lambda__Dependencies__Builder` and `Lambda__Dependencies__Loader`. They live only
in the SG-Send repo (`_for_osbot_aws/`, pending upstreaming into `osbot_aws`).
`osbot_aws` ships only the *older* per-package loader. **Their complete source is
embedded in Appendix A of the dependency-packaging brief** — recreate the two
files verbatim and you have the full optimisation; no repo access required.

Everything else in the briefs is either (a) an inline code skeleton you copy, or
(b) a reference to the SG-Send User Lambda as an *example* you can introspect if
you happen to have it — never a hard dependency. Repo file paths are given for
provenance, not because you must open them.

## Non-negotiable project rules (from `.claude/CLAUDE.md`)

1. **Type_Safe, never Pydantic** for all schemas (`from osbot_utils.type_safe.Type_Safe import Type_Safe`).
2. **osbot-aws, never boto3 directly** in application code. (The dependency
   Builder/Loader use raw boto3 intentionally — they are infra plumbing destined
   for osbot-aws itself, see brief 1's caveat.)
3. **All storage through Memory-FS (`Storage_FS`)** — never touch S3 or the
   filesystem directly from app code.
4. **All FastAPI apps extend `Serverless__Fast_API`**.
5. **No mocks/patches in tests** — the full stack starts in-memory in ~100 ms.
6. **Never read or write `sgraph_ai_app_send/version`** — CI owns it.

## One important reality check before you start

The dependency Builder is currently pinned to **Python 3.13 / `manylinux2014_x86_64`**
(`Lambda__Dependencies__Builder.LAMBDA_PYTHON = '3.13'`, `LAMBDA_PLATFORM =
'manylinux2014_x86_64'`, `LAMBDA_ABI = 'cp313'`). Note this **differs** from the
"Python 3.12 / arm64" line in `.claude/CLAUDE.md`. The *code* is the source of
truth: your new Lambda's runtime + architecture must match whatever the Builder
targets, or native wheels (e.g. pydantic-core) will fail to import at cold start.
Brief 1 explains how to change these if your function needs a different target.
