## Bug 1 — write 401 (FIXED)

**Was:** writes (`sg.vfs.write`, `sg.sync.push`) 401'd even after `setKey` returned `{valid:true}`.
The validated token was assigned to the `VaultDataSource` (which only flips the `writable` flag) but
never to `vault._sgSend.token`, which `_authHeaders()` reads to attach `x-sgraph-access-token`.

**Fix:** the shell threads the token onto `vault._sgSend.token` at every point it obtains one (open,
cached-auth, auth-prompt, and the `setKey` bridge command). `_authHeaders()` reads it lazily, so a
token set after open is honoured by the next write.

## Bug 2 — app-side sub-vault reads (FIXED)

**Was:** from inside the app, `sg.vfs.readText('subvaults/<child>/<file>')` → "No such file" and
`sg.vfs.list('subvaults/<child>')` → "No such path", while the UI file browser read the same files
fine. (Your derivation of the `ro-links` records was correct — that was never the problem.)

**Root cause.** The bridge already wraps the data source in a `CompositeDataSource` that auto-opens a
sub-vault mount on access. But the bridge's **read** and **list** handlers consulted a *static* file-list
snapshot and short-circuited: a collapsed (not-yet-opened) sub-vault's inner files aren't in that
snapshot, so the strict pre-check returned `ENOENT` **before** the auto-opening `getFileBytes()` ran.
The UI worked only because expanding the folder calls `loadFolder` first; the app has no expand
gesture. (A fire-and-forget `scan()` added a startup race too.)

**Fix.** Both handlers now `await` the mount scan, then open the sub-vault covering the requested path
(`_mountForPath` → `loadFolder`, read-only and silent — no prompt) before consulting the list. After
that the inner files are listable and readable.

**This answers your open questions:**
1. App-side auto-open-on-read is **now wired on the bridge**, not only when a user expands the folder
   in the UI. The AUTHORING guide's "no prompt fires during a read" now holds for the app path.
2. The app-side resolver now uses the **same composite mount table** the UI file browser uses.
3. Mount path is `subvaults/<linkname-without-suffix>/` — exactly what you had. No special form needed.

**Verify (after deploy, cache-busted):**
```js
await frame.evaluate(() => window.sg.vfs.list('subvaults/patient-alex'))
// → child entries (app.json, patient.json, submissions.json, …)
await frame.evaluate(() => window.sg.vfs.readText('subvaults/patient-alex/submissions.json'))
// → the JSON bytes, no prompt
```
Your dashboard should then read each child's data and render scores/bands with **no code change**.

## Bug 3 — inner (child) vault writes (NOT changing for now)

Per the owner: child vaults **stay read-only** in this version. `sg.vfs.write` to a
`subvaults/<child>/...` path still rejects by design. Your dashboard's "comments back to the record"
step can't write straight into a child vault through the parent's read-only mount yet.

**Recommended pattern until inner-writes land:** have the dashboard open the *child* vault **writable
with that child's own write key** (a separate `sg.auth.setKey` against the child), do the write there,
then return to the parent view — rather than writing through the parent mount. Alternatively, stage the
review in the parent vault and reconcile out-of-band. Flag if you want this designed properly; it's a
real feature (inner-vault write support), not a quick toggle.
