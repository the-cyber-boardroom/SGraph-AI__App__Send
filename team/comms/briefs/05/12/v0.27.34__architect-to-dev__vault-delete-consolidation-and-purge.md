## TL;DR

Two small changes to the User Lambda's vault API:

1. **Add an opt-in `purge` parameter** to `DELETE /api/vault/destroy/{vault_id}` so callers can request a "no-tombstone" hard delete.
2. **Remove the catch-route at `DELETE /api/vault/delete/{vault_id}`** (no `{file_id}`). It is a 400-returning stub that is not actually deleting anything but appears alongside the real `destroy` endpoint in the OpenAPI docs at `send.sgraph.ai/api/docs`, making it look like there are two ways to delete a vault. It is API noise.

The motivation for both: cleaner API surface, and the ability to clean up after performance test runs without leaving `deleted.json` residue on S3.

## 1. Current State of Play (code-verified)

### 1.1 `DELETE /api/vault/destroy/{vault_id}` — the real whole-vault delete

File: `sgraph_ai_app_send/lambda__user/fast_api/routes/Routes__Vault__Pointer.py:278-307`
Service: `sgraph_ai_app_send/lambda__user/service/Service__Vault__Pointer.py:209-231`

**Contract:**
- Headers: `x-sgraph-access-token`, `x-sgraph-vault-write-key`
- Body: JSON `{"vault_id": "<must-match-URL>"}`
- Behaviour:
  1. Loads the vault manifest, verifies `write_key` hash.
  2. Lists every file under the vault prefix (`storage_fs.folder__files__all`).
  3. Deletes each file individually (`storage_fs.file__delete` per file).
  4. Writes a tombstone at `path__vault_tombstone(vault_id)` → `vault/{id[:2]}/{id}/deleted.json` containing `{vault_id, status: 'deleted', deleted_at: <iso8601>}`.
  5. Caches the tombstone in `_manifest_cache` so subsequent writes to the same vault_id are rejected.
  6. Cleans up any cached zip archives.
- Response: `{status: 'deleted', vault_id, files_deleted: N}`

### 1.2 `DELETE /api/vault/delete/{vault_id}` — a 400-returning catch route

File: `sgraph_ai_app_send/lambda__user/fast_api/routes/Routes__Vault__Pointer.py:323-325`

```python
@route_path('/delete/{vault_id}')
async def delete__vault_id(self, vault_id: str):  # DELETE /vault/delete/{vault_id} — missing file_id
    raise HTTPException(status_code=400, detail='Missing file_id in path')
```

This exists so a client that calls `DELETE /api/vault/delete/{vault_id}` (forgetting the `{file_id}` segment) gets a clean `400 Missing file_id in path` instead of a redirect loop or routing error. It does **not** delete anything. It does, however, appear in the OpenAPI docs as a top-level `DELETE` entry — which is what makes it look like a sibling of `destroy`.

### 1.3 `DELETE /api/vault/delete/{vault_id}/{file_id}` — single-file delete

File: `Routes__Vault__Pointer.py:156-174`. Working as expected. Deletes one file from a vault. Not in scope for this brief.

## 2. Why the Tombstone is a Problem (Now)

The tombstone is **intentional**: it prevents re-using a `vault_id` after destruction. This is correct for the public API — a re-used `vault_id` would let a new vault collide with the historical one in caches, indexes, and any client-side state.

It is **also a cost** that is becoming visible:

- **Performance testing.** The new `/dev/performance/` tool creates and destroys hundreds of vaults across a full run. Every destroy leaves one tombstone object on S3. Over a CI cycle this is thousands of small objects that nothing ever reads again.
- **Internal automation.** As we add automated QA suites, smoke tests, and cache-warmup probes, every disposable vault is now a permanent footprint.
- **Bandwidth-billing rollout** (see storage-flows review §9). When we start metering per-vault storage size, tombstone-only vault folders become a billable phantom unless we explicitly exclude them.

A clean delete path — used only by trusted contexts that *know* the `vault_id` is disposable — solves all three.

## 3. Requested Changes

### 3.1 Add an opt-in `purge` parameter to whole-vault delete

Two acceptable shapes; we have no preference between them, but only pick one.

**Option A — body flag (preferred for consistency with the existing `{vault_id}` body field):**

```json
{
  "vault_id": "<must-match-URL>",
  "purge":    true
}
```

**Option B — query parameter:**

```
DELETE /api/vault/delete/<vault_id>?purge=true
```

**Semantics:**

- `purge` absent or `false` → existing behaviour, including writing `deleted.json`.
- `purge: true` → after deleting all vault files, do **not** write the tombstone; also delete the manifest entry from `_manifest_cache` rather than replacing it with the tombstone. The vault_id becomes fully reusable.

**Authorisation:** `purge: true` should be available to any caller that already passes the existing `x-sgraph-access-token` + `x-sgraph-vault-write-key` checks. Holding the write key is already proof of authority over the vault's existence. *If* we want to be strict, restrict `purge` to tokens with a `dev` or `perf-test` flag in the access-token metadata (`Schema__Token__Metadata.metadata`) — but this is optional and can be added later without breaking the API.

**Response addition:** include `tombstone_written: bool` in the response so clients can verify the request was honoured.

### 3.2 Remove the `DELETE /api/vault/delete/{vault_id}` catch route

**What to remove:**

```python
# sgraph_ai_app_send/lambda__user/fast_api/routes/Routes__Vault__Pointer.py:323-325
@route_path('/delete/{vault_id}')
async def delete__vault_id(self, vault_id: str):  # DELETE /vault/delete/{vault_id} — missing file_id
    raise HTTPException(status_code=400, detail='Missing file_id in path')
```

…plus the corresponding registration at line 341:

```python
self.add_route_delete(self.delete__vault_id)              # Catch: missing file_id
```

**Why:** This route exists only so that clients who forget the `{file_id}` segment of the *real* single-file delete (`DELETE /api/vault/delete/{vault_id}/{file_id}`) get a clean 400 instead of a 404 or a redirect loop. It does not delete any vault. It appears in the OpenAPI docs as a top-level `DELETE /api/vault/delete/{vault_id}` entry — looking, at first glance, like a sibling of `destroy/{vault_id}`. Users (and tool authors) get confused.

**What happens after removal:** A request to `DELETE /api/vault/delete/{vault_id}` (no file_id) will return a normal FastAPI `404 Not Found` because no route matches. That is the correct shape — there is no resource to delete at that path; the caller has used the wrong URL. Anyone wanting to destroy a whole vault uses `DELETE /api/vault/destroy/{vault_id}`.

**Optional symmetry cleanup:** The same file has three other "missing file_id" catch routes:

```python
@route_path('/write/{vault_id}')        # PUT 400
@route_path('/read/{vault_id}')         # GET 400
@route_path('/read-base64/{vault_id}')  # GET 400
```

Same reasoning applies — they pollute the OpenAPI surface. Removing them is **out of scope** for this brief because they don't look like a sibling of any other destructive endpoint, but the team may want to remove them in the same PR for consistency. Up to you.

### 3.3 OpenAPI / docs after the change

After §3.2 lands, vault delete-style entries at `/api/docs` will be:

- `DELETE /api/vault/destroy/{vault_id}` — destroy whole vault, with optional `purge`
- `DELETE /api/vault/delete/{vault_id}/{file_id}` — delete one file

Two endpoints, two clearly distinct semantics. The deceptive third entry is gone.

## 5. Open Questions for Backend Dev

1. **Should `purge: true` be gated on a special token scope?** Our recommendation is "no, write key is sufficient" — but if you'd prefer a soft gate (token metadata flag), shout.
2. **Reusing a purged vault_id immediately — any in-Lambda caches besides `_manifest_cache`?** Worth a grep for any other place that holds vault_id state.
3. **Public-vault bucket:** does the public vault service (`public_vault_service`) need the same treatment? It uses the same `Service__Vault__Pointer` class. Probably yes; please confirm.
4. **MCP exposure:** the MCP setup includes `api/vault` in `include_tags` (`Fast_API__SGraph__App__Send__User.py:142`). Once consolidated, the MCP tool surface drops one duplicate-looking tool. No action needed beyond the OpenAPI cleanup, but worth flagging.

## 6. Out of Scope

- Changes to `delete/{vault_id}/{file_id}` (single-file delete) — works as expected.
- Changes to `destroy`-like cleanup of cached zip archives — already handled inline.
- The transfer-side `DELETE /api/transfers/delete/{transfer_id}` which leaves a `meta.json` with `status='deleted'`. That residue is smaller and has different semantics (audit trail of completed transfers). A separate brief if/when needed.

## 7. Suggested Sequence for Delivery

Both changes are additive/subtractive and can ship in either order. The simplest path:

1. **Land §3.2 first** (remove the `delete/{vault_id}` catch route) — pure cleanup, one route + one registration to remove. Update or delete any test that asserted the 400 response. Done.
2. **Land §3.1** (add `purge` to `destroy/{vault_id}`) — additive parameter, no breaking change.
3. Update the `/dev/performance/` tool's `vaultDestroy` client call to pass `purge: true`. Re-run the perf suite — tombstones should stop appearing on test runs.

Both steps independently shippable and reversible.
