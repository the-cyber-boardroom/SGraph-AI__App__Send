## TL;DR

**The protocol is already shaped to do what you want — the browser client isn't using it the same way the CLI does.** The two top-ranked smells (`commit + push = 2 ref writes` and `clone-ref 404 on open`) **don't exist in the CLI today.** The fix for both is client-side: adopt the existing `execute_batch()` write path, and treat the clone ref as derived local state. No new endpoints needed for the highest-impact items.

## Map vs reality

| Op | Web map | CLI reality |
|---|---|---|
| Single-file save | 5 writes (1 blob + 1 tree + 1 commit + 2 refs) | **1 write** — `Vault__Batch.execute_batch()` packs all four into one HTTP call (`sgit_ai/core/actions/push/Vault__Sync__Push.py:263`) |
| Cold open clone-ref read | 404 round-trip | **0 round-trips** — clone ref is created locally at clone time (`sgit_ai/workflow/clone/Step__Clone__Create_Clone_Branch.py:59`); never read from server |
| Status | Multiple ref reads | **0 network calls** — `Vault__Sync__Status` reads only local files |
| Divergence ancestor walk | Client-side DAG walk | Same — `Vault__Fetch.find_lca` walks locally. No server merge-base endpoint exists or is planned. |
| Push batching | Not modelled | 50-op chunks via `Vault__API.execute_batch`, presigned S3 fallback on 502/503 |
| Ref pointer caching | Implied (Q3) | None — CLI reads are local-file, so caching is unnecessary on CLI |

## Quick wins / bugs (browser-side, no protocol change)

1. **Stop writing the named ref in `_vault.push()` as a separate HTTP call.** Include it in the same `execute_batch` as the commit/tree/blob writes. **Expected reduction: 5 writes → 1 write per save.**
2. **Stop reading the clone ref on open.** Create it locally at clone-time (matching the CLI). Treating clone ref as server-side is the root cause of the 404 read.
3. **Skip branch-index read for single-named-branch vaults.** Flag in vault metadata (e.g. `has_multi_branch: bool`) injected at `sg.app.*` boot lets the browser skip the read.
4. **Client-side ref-pointer TTL cache (2–5s).** Keep it in the JS layer keyed by `(vault_id, ref_id)`. Invalidate on any ref-write op from the same client. **Do NOT use `Cache-Control: max-age=2`** — refs are write-after-read sensitive; stale CDN/proxy cache is hard to debug.

## Bigger architecture / resilience changes

5. **`execute_batch()` IS the protocol-level fusion endpoint.** You don't need `POST /bare/refs/advance`. The atomicity guarantee comes from putting both ops in the same batch call. See `sgit_ai/network/api/Vault__API.py:65-96` (`MAX_BATCH_OPS = 50`, presigned S3 fallback on 502/503).
6. **Server-side merge-base (your Q5) — defer.** Deep DAG walks are pathological only on genuinely deep histories; CLI's 50-batch BFS keeps wall-clock low. Adding server LCA increases protocol surface and trust assumptions. **Better lever:** cache LCA result client-side keyed by `(local_head, remote_head)` — deterministic.
7. **Subtree expansion batching (your Issue #7).** CLI also expands one-at-a-time. Worth adding `read_subtree_with_children(tree_id, depth=1)` to the protocol — **both clients would benefit.** Migration: additive (new endpoint, old path stays).
8. **Resilience win for both clients.** Mirror CLI's presigned-URL fallback on 502/503 — make sure it exists on **writes too**, not only reads.

## Target HTTP-request counts

| Operation | Target | CLI today | Browser today |
|---|---|---|---|
| Vault open (cold, 1-commit vault) | **2** (branch_meta batch + tree+blob batch) | 4–5 | 5+ (with 404 on clone-ref) |
| Pull when up-to-date | **1** (named ref read) | 1 ✓ | 1 |
| Pull when behind | **2** (ref read + 1 batch for missing objects) | 2–3 | 3+ (unconditional clone-ref write) |
| Status | **0** | 0 ✓ (local-only) | 2 (both ref reads) |
| Single-file save (auto-push) | **1** (atomic batch: blob+tree+commit+ref) | **1 ✓** | **5** |
| Check button | **1** (named ref read) | n/a | 1 |
| Subtree expansion | **1** per depth-N tree | 1 per single subtree | Same |

## Answers to the 6 questions

- **Q1 Fuse commit + push?** Already done at protocol level — `execute_batch()`. Browser needs to adopt. No new endpoint required.
- **Q2 Faster first-open?** Treat clone ref as locally-derived. Zero protocol change.
- **Q3 Ref TTL cache?** Yes, 2–5s, client-owned, not HTTP `Cache-Control`. Invalidate on any ref-write op from the same client.
- **Q4 Optimal batch size?** 50 is correct. Throughput plateaus around 30–60. Don't change.
- **Q5 Server merge-base?** Defer. Cache LCA client-side instead.
- **Q6 Auto-push semantics?** CLI workflow batches commits manually; iframe `sg.vfs.write()` auto-push is the right default. Protocol does not care — pure client-UX choice.

---

## Migration shape

- **Items 1–4 (quick wins):** pure browser-client work, no server changes, no vault format changes, no backwards-compatibility concerns.
- **Item 7 (subtree-with-children):** new endpoint, additive. Old path stays. Old vaults keep working.
- **Item 8 (presigned fallback on writes):** transparent — clients try `execute_batch` first, fall back to presigned on 502/503.

## Prioritisation

| # | Change | Type | Impact | Effort |
|---|---|---|---|---|
| 1 | Move ref-advance into `execute_batch` on browser-side push | Browser-only | **5× fewer writes per save** | Medium |
| 2 | Stop reading clone ref on open | Browser-only | 1 round-trip per cold open | Low |
| 3 | Inject `has_multi_branch` flag to skip branch-index read | Browser + CLI | 1 round-trip per cold open (single-branch) | Low |
| 4 | Client-side ref-pointer TTL cache | Browser-only | Removes duplicate ref reads in Check + status | Low |
| 5 | Add `read_subtree_with_children` endpoint | Protocol | Faster first navigation into deep trees | Medium |
| 6 | Don't add server LCA | (Deferred) | n/a | n/a |
| 7 | Presigned fallback on writes (browser-side) | Browser-only | Resilience under transient S3 errors | Low |
