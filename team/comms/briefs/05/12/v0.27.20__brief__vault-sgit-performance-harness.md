## 1. Goal

Create a new internal debug page at `/en-gb/vault/sgit` that runs **today's vault client and an optimised client side-by-side against the same vault**, measuring the HTTP request count, payload bytes, and wall-clock time for each scenario. The page lets a developer (or QA agent) toggle each optimisation on or off individually to isolate its effect, and validates the SGit CLI team's recommendations before they ship into the shared client.

### Background

A 12 May architect brief mapped the browser-side vault API call patterns and identified 7 excess-call smells. The SGit CLI team's reply confirmed:

- **Today**: a single `sg.vfs.write()` save costs **5 HTTP writes** (blob + tree + commit + clone-ref + named-ref)
- **Target**: **1 HTTP write** (an atomic `execute_batch` that bundles all four ops)
- Most wins are **browser-client-only** — no protocol changes; the CLI already uses the optimal shape

The harness is the page that proves it, in numbers, side-by-side.

### Why a separate page (not benchmarks in-place)

- The production vault client is mid-flight; we cannot afford regressions on the main `/en-gb/vault/` UX while we experiment
- Toggling optimisations per-page makes A/B comparisons trivial (no rebuilds, no flags in shipped code)
- The page is the artefact a QA agent or human can demo when reviewing each optimisation's impact
- When Phase 2 lands, this page becomes the regression dashboard that proves the wins held

### 3.1 Reusing the tools.sgraph.ai vault-embed family

The tools team publishes a versioned set of CDN-served read-only vault components at `https://tools.sgraph.ai/components/vault-embed/*` (see `library/catalogue/v0.1.92__vault__quick-start.md`). Two of them save us significant work:

| Component | Use in this harness |
|---|---|
| `<sg-vault-trace>` (`vault-embed/sg-vault-trace/v0/v0.1/v0.1.0/`) | **Drop-in replacement for the from-scratch request log.** It auto-captures every `sg-vault-*:*` event in document order, sanitises non-serialisable values (CryptoKey etc.), and exposes `getLog()` / `clearLog()`. We use it as the foundation of `<vs-request-trace>` and add only the two-client colour-coding shim on top. |
| `<sg-content-markdown>` / `<sg-content-json>` / `<sg-content-image>` (`content/sg-content-*`) | Optional — use inside `<vs-vault-setup>` for "show me the decrypted bytes" inspector views after a scenario runs. Cosmetic, not required for measurements. |

The other vault-embed components (`<sg-vault-key>`, `<sg-vault-fetch>`, `<sg-vault-content>`, `<sg-vault-manifest>`) are **read-only by design** (no write keys, no mutations) and cover only the object-fetch sub-path. The harness needs the full `SGVault` state machine — commits, refs, push, pull — which those components don't address. **Do not** try to replace `SGVault` with them.

What we **do** adopt from those components is their **event taxonomy** — see §8.2. Our instrumentation dispatches events with the same names and detail shape so `<sg-vault-trace>` captures them without modification, and any future tooling listening for the vault-embed event family works against this harness too.

**Pin to exact versions** when importing from `tools.sgraph.ai`. The guidance is explicit: rolling paths can change underneath you.

## 5. Custom Elements to Build

### 5.1 `<vs-vault-loader>` — credential entry (reuse the token harness pattern)

Same UX as the token-harness loader (§5.1 of the token-harness brief), but it does NOT route to iframes. Once a vault key is loaded the harness creates **two** `SGVault` instances (one baseline, one optimised) and stores them on the page singleton (`window.__vsHarness.baseline` and `.optimised`).

**Important:** both instances **share the same vault key** and write to the **same server-side vault**. Coordinate carefully — see §7.

### 5.2 `<vs-opt-toggles>` — per-optimisation switches

One row per optimisation, with a checkbox and a one-line description. Default is **all off** (so the "optimised" client behaves identically to the baseline until something is toggled — sanity check baseline).

```
[☐] Batch push (commit + ref-advance in one HTTP call)
[☐] Local clone-ref (skip the 404 read on open)
[☐] Single-branch flag (skip branch-index read)
[☐] Ref TTL cache (2–5 s in-memory)
[☐] Subtree fan-out (simulate read_subtree_with_children)
[☐] Presigned fallback on writes (retry 502/503)
[☐] LCA cache (deterministic divergence resolution)
```

Toggles are stored in `sessionStorage['vs-opts']` and applied to the optimised client on next operation. Changing a toggle does NOT reload the vault — the optimised client picks up the change on its next call.

### 5.3 `<vs-scenario-picker>` — choose what to run

A list of scenarios (see §7). Each row has a "Run" button. There is also a "Run all" button at the bottom that runs scenarios sequentially. Each run produces one entry in `<vs-run-history>` and one card in `<vs-metrics-card>`.

### 5.4 `<vs-metrics-card>` — side-by-side comparison

The headline component. For the most recently run scenario, shows two columns:

## 6. Optimisations to Implement (one toggle each)

Each optimisation lives in `sgit-optimisations.js` as an independently togglable module. The optimised client (§5.1) reads the current toggle set from `sessionStorage` before each operation and applies only the enabled ones.

### 6.1 Batch push (`batchPush`) — the headline win

**Today:** `_commit()` writes the clone ref (`vault--sync.js:91`) and `_vault.push()` writes the named ref. Two separate `vaultWrite` calls on top of three object writes (blob + tree + commit). Total = 5 HTTP writes per save.

**Optimised:** build one batch payload that fuses all 5 ops into a single `POST /bare/batch` call. Reference shape (port from CLI `Vault__Batch.build_push_operations`):

```js
{
  operations: [
    { op: 'put_object', id: 'obj-cas-imm-<blob-hash>', body: <ciphertext> },
    { op: 'put_object', id: 'obj-cas-imm-<tree-hash>', body: <ciphertext> },
    { op: 'put_object', id: 'obj-cas-imm-<commit-hash>', body: <ciphertext> },
    { op: 'put_ref',    id: 'ref-pid-snw-<clone-id>',  commit_id: '<commit-hash>' },
    { op: 'put_ref',    id: 'ref-pid-muw-<named-id>', commit_id: '<commit-hash>' }
  ]
}
```

The endpoint to use is whatever the existing `SGSend` already exposes for batches — if no public batch endpoint exists in the browser yet, document the gap and emulate by issuing the 5 calls in `Promise.all()` (same number of round-trips, but at least same-tick). When the protocol-level batch lands, swap in.

**Target reduction:** 5 → 1 HTTP request per save.

### 6.2 Local clone-ref (`localCloneRef`)

**Today:** `SGVault.open()` reads `/bare/refs/ref-pid-snw-*` (`sg-vault.js:139`) which is structurally a 404 on first open.

**Optimised:** treat the clone ref as a **purely local** pointer. Skip the read entirely. Initialise the clone ref from the named ref in memory. On commit, the optimised client still writes the clone ref to the server (so the production client can read it back on re-open — backwards compatible) but it does NOT read it during its own open path.

**Target reduction:** 1 HTTP request per cold open.

### 6.3 Single-branch flag (`singleBranch`)

**Today:** `SGVault.open()` attempts to read `/bare/indexes/{branchIndexFileId}` (`sg-vault.js:122`) unconditionally.

**Optimised:** check a sessionStorage hint `vs-vault-{id}-multi-branch` (default: `false`). If `false`, skip the branch-index read and derive the ref-file-id directly from the vault key (existing fallback path).

If a user expects multi-branch support, they toggle a small checkbox in `<vs-vault-setup>` that flips the hint to `true`.

**Target reduction:** 1 HTTP request per cold open in the common case.

### 6.4 Ref TTL cache (`refTTLCache`)

**Today:** every ref read goes to the network. The new `Check` button and `_refreshSyncState` can both read the named ref within the same debounce window (see `vault-shell.js:536, 572`).

**Optimised:** wrap the ref-manager with an in-memory TTL cache:

```js
class RefPointerCache {
  constructor({ ttlMs = 3000 } = {})
  async read(refId, fetcher)        // returns cached if fresh; otherwise fetcher()
  invalidate(refId)                 // called on any local write to that ref
  invalidateAll()                   // called on refresh / vault re-open
}
```

Key: `(vaultId, refId)`. TTL: 3 seconds default, slider in the panel to vary 1–10 s for experiments. Invalidate on every local `writeRef` call. Do NOT use HTTP `Cache-Control` (per SGit team).

**Target reduction:** duplicate ref reads inside the TTL window → 0.

### 6.5 Subtree fan-out (`subtreeFanout`) — protocol-deferred simulation

**Today:** expanding a folder triggers one `vaultRead /bare/data/obj-cas-imm-*` (`vault--folder-ops.js:93`). For deep navigation this is N serial calls.

**Optimised (browser-only simulation):** when a subtree is expanded, **pre-fetch its direct children's tree objects in parallel** using the existing `vaultBatch()` path. Total wall-clock drops even though request count is unchanged or slightly higher — we trade one extra round-trip for parallelism on the children.

Mark the metrics card clearly: this optimisation **does not reduce request count** in Phase 1 — it reduces wall-clock. The true protocol-level win (`read_subtree_with_children`) needs server work.

### 6.6 Presigned fallback on writes (`presignedFallbackWrites`)

**Today:** `vaultWrite` for large blobs uses `vaultWriteLarge` (presigned). For small writes, no fallback if S3 returns 502/503.

**Optimised:** wrap every `vaultWrite` so that on a 502/503 response it retries through the presigned URL path. Inject synthetic failures in the panel ("Force 502 on next write") so the optimisation can be exercised without waiting for real S3 hiccups.

**Target:** resilience under transient errors (zero impact on the happy path).

### 6.7 LCA cache (`lcaCache`)

**Today:** `vault--sync.js:215–256` walks the commit DAG client-side on every divergence check.

**Optimised:** cache the result keyed by `(localHeadId, remoteHeadId)` (both are content-addressed, so the key is deterministic). Cache lives in `sessionStorage['vs-lca-cache']`. Invalidate any entry that mentions a head that has since moved.

**Target:** repeated divergence checks on the same head pair → 1 walk total.

## 8. Instrumentation Layer

### 8.1 Approach

`sgit-instrumentation.js` wraps the `SGSend` (or the underlying `fetch` calls inside `SGVault`'s I/O methods) and **dispatches CustomEvents on `document` matching the tools-team `sg-vault-*:*` taxonomy** (see §3.1). `<sg-vault-trace>` picks them up automatically; our `<vs-metrics-card>` and `<vs-run-history>` also subscribe.

Two separate `SGSend` instances (one per client) is the cleanest shape. Instrumentation lives in a thin subclass / wrapper:

```js
class InstrumentedSGSend extends SGSend {
  constructor(opts, { client /* 'baseline' | 'optimised' */ }) { ... }
  async vaultRead(path, opts) {
    const objectId = extractObjectId(path)
    this._fire('sg-vault-fetch:fetch-started', { client: this._client, vaultId: this._vaultId, objectId, url: maskPath(path) })
    const t0 = performance.now()
    const res = await super.vaultRead(path, opts)
    this._fire('sg-vault-fetch:fetch-completed', {
      client: this._client, vaultId: this._vaultId, objectId,
      bytesReceived: byteLengthOf(res), fetchMs: performance.now() - t0, cacheHit: false
    })
    return res
  }
  // mirror for vaultWrite (sg-vault-write:write-started/completed),
  //            vaultBatch (sg-vault-batch:batch-started/completed with opCount),
  //            vaultRead on refs (sg-vault-ref:read-started/completed),
  //            vaultWrite on refs (sg-vault-ref:write-started/completed)
}
```

If you can't subclass cleanly, wrap the underlying `fetch` at the bottom of the stack. **Do not modify `SGSend` itself.** Subclassing or composition only.

### 8.2 Event taxonomy (adopt the tools-team shape)

The tools team's vault-embed components define a stable event shape. We **mirror it for reads** and **extend it for writes / refs / batches** (which they don't cover, being read-only):

| Event (CustomEvent name) | Source | Detail fields |
|---|---|---|
| `sg-vault-fetch:fetch-started` | tools-team & ours | `client, vaultId, objectId, url` |
| `sg-vault-fetch:fetch-completed` | tools-team & ours | `client, vaultId, objectId, bytesReceived, fetchMs, cacheHit` |
| `sg-vault-fetch:decrypt-started` | tools-team & ours | `client, objectId, ciphertextBytes` |
| `sg-vault-fetch:decrypt-completed` | tools-team & ours | `client, objectId, plaintextBytes, decryptMs` |
| `sg-vault-fetch:content-ready` | tools-team & ours | `client, objectId, bytes, contentType, text` |
| `sg-vault-fetch:fetch-error` | tools-team & ours | `client, stage, objectId, error` |
| `sg-vault-write:write-started` | **harness-only** | `client, vaultId, objectId, url, reqBytes` |
| `sg-vault-write:write-completed` | **harness-only** | `client, vaultId, objectId, status, writeMs` |
| `sg-vault-write:write-error` | **harness-only** | `client, objectId, status, error` (used by `presignedFallbackWrites` to log the 502 + retry) |
| `sg-vault-ref:read-started` | **harness-only** | `client, vaultId, refId` |
| `sg-vault-ref:read-completed` | **harness-only** | `client, vaultId, refId, status, readMs, cacheHit` |
| `sg-vault-ref:write-started` | **harness-only** | `client, vaultId, refId, commitId` |
| `sg-vault-ref:write-completed` | **harness-only** | `client, vaultId, refId, status, writeMs` |
| `sg-vault-batch:batch-started` | **harness-only** | `client, vaultId, opCount, reqBytes` |
| `sg-vault-batch:batch-completed` | **harness-only** | `client, vaultId, opCount, status, batchMs, resBytes` |
| `vs:scenario-started` | harness | `{ scenario, client }` |
| `vs:scenario-completed` | harness | `{ scenario, client, metrics }` |
| `vs:run-completed` | harness | `{ scenario, baseline, optimised, deltas }` |

The `client` field is **the** signal that lets `<vs-request-trace>` colour-code two-client runs from a single event stream. Every event MUST carry it.

All events `bubble: true, composed: true` so they cross shadow-DOM boundaries (matching the tools-team convention).

### 8.3 Bytes measurement

For `Request`: `JSON.stringify(body).length` is fine as an approximation when body is JSON; for `Uint8Array` bodies use `.byteLength`. For `Response`: clone, `arrayBuffer()`, `.byteLength`. Don't worry about header bytes — body-only is the SGit CLI team's measure too.

### 8.4 Where the tools-team components stop

The vault-embed family is **read-only by contract**. They cover individual object reads via `<sg-vault-fetch>`. They do not cover:

- Writes of any kind (objects, refs, batches)
- Ref reads (refs are a different path from `/bare/data/obj-cas-imm-*`)
- Batch reads / writes
- The full `SGVault` open / commit / push / pull state machine

For all of those, the harness produces its own events using the `sg-vault-write:*`, `sg-vault-ref:*`, `sg-vault-batch:*` namespaces above. The naming matches the tools-team verb conventions (`-started`, `-completed`, `-error`) so the trace UI handles them uniformly.

## 9. Acceptance Workflows

A QA agent or developer must be able to execute each workflow end-to-end on this page:

### W3 — Local clone-ref removes the 404 on cold open

1. Load a vault (W1).
2. Toggle ON: `localCloneRef`.
3. Run `cold-open` scenario (the harness internally constructs a fresh client).
4. Metrics card shows optimised's HTTP request count drops by exactly 1.
5. Request trace shows the baseline column contains a `GET /bare/refs/ref-pid-snw-* → 404`; optimised column does not.

### W4 — Ref TTL cache collapses status to 0 network calls

1. Load a vault (W1).
2. Toggle ON: `refTTLCache`.
3. Run `status-check` scenario.
4. Metrics card shows baseline = 2 ref reads, optimised = 0 (after the first read, second is cache hit).
5. Δ HTTP delta badge shows `−100 %` in green.

### W5 — Run All produces the full picture

1. Load a vault (W1).
2. Toggle ON: all optimisations.
3. Click "Run all".
4. All scenarios run sequentially, each producing one row in Run History.
5. Summary row at the bottom of Run History shows totals: e.g. baseline = 23 HTTP requests across 9 scenarios; optimised = 8 HTTP requests; net reduction = 65 %.
6. Export-to-Markdown button produces a clean table suitable for a debrief.

### W6 — Toggling an optimisation off mid-session works

1. After W5, toggle OFF: `batchPush`.
2. Re-run `single-save`.
3. Optimised column reverts to 5 HTTP writes (matches baseline).
4. No page reload required.

### W7 — Discrepancy badge fires when actuals diverge from targets

1. With all toggles ON, run `single-save`.
2. If optimised actually does 1 request (target met), no badge.
3. Force a regression: temporarily set `batchPush` to emit 2 requests in dev mode.
4. Discrepancy badge appears next to the metric: "Expected 1, got 2".

### W8 — Request trace never leaks vault key or ref IDs in full

1. Inspect the request trace after any scenario.
2. URL column shows `/bare/refs/ref-pid-muw-…` (truncated) not the full ID.
3. The vault key is never printed anywhere.
4. The "Copy trace" / "Export" buttons emit the same masked form.

### W9 — Resilience scenario passes

1. Toggle ON: `presignedFallbackWrites`.
2. Run `resilience-502` (which injects one 502 on the first blob write).
3. Request trace shows the baseline path failing on the 502; optimised path retries via presigned and succeeds.
4. Optimised wall-clock is higher than the happy path (retry overhead) — surface that honestly; the win is "succeeded under failure" not "faster".

### W10 — Layout persistence

1. Drag panels to a new arrangement.
2. Reload the page.
3. Layout is restored from `localStorage['vs-layout']`.

### W11 — `<sg-vault-trace>` captures the full event stream

1. Run any scenario.
2. Open DevTools and call `document.querySelector('sg-vault-trace').getLog()`.
3. The returned array contains both baseline and optimised events, each with a `client` field, ordered by dispatch time.
4. Sanitisation: no `CryptoKey` object appears anywhere in the log; ref/object IDs are masked.

## 10. Working Constraints

### 10.1 Allowed reuse boundary

Same as the token harness, with additions for the tools.sgraph.ai CDN:

- You may `<script>`-load anything under `_common/js/lib/`, `_common/js/services/`, `_common/js/adapters/`
- You may NOT **modify** those files
- You may subclass / wrap their exports in your own files
- You may NOT add methods to `SGVault.prototype` or `SGSend.prototype` from harness code

If you find yourself wanting to override a private method (`_loadCommit`, `_commit`, etc.), do it by **composition**: build a thin wrapper class in `sgit-fast-client.js` that delegates to a baseline `SGVault` for unchanged work and replaces only the methods being optimised.

**Allowed external imports (pin to exact versions):**

```html
<!-- sg-layout for the panel arrangement -->
<script type="module" src="https://tools.sgraph.ai/core/sg-layout/v0.1.0/sg-layout.js"></script>

<!-- sg-vault-trace for the request log foundation (§5.5) -->
<script type="module"
  src="https://tools.sgraph.ai/components/vault-embed/sg-vault-trace/v0/v0.1/v0.1.0/sg-vault-trace.js"></script>

<!-- Optional content renderers for the inspector views (§5.7) -->
<script type="module"
  src="https://tools.sgraph.ai/components/content/sg-content-markdown/v0/v0.1/v0.1.0/sg-content-markdown.js"></script>
<script type="module"
  src="https://tools.sgraph.ai/components/content/sg-content-json/v0/v0.1/v0.1.0/sg-content-json.js"></script>
```

Do **not** pull in `<sg-vault-key>` or `<sg-vault-fetch>` to replace `SGVault`'s read path. They are read-only and only handle object fetches by id — the harness needs the full state machine.

### 10.2 Script load order

```html

<script src="../../../_common/js/lib/sg-vault/sg-vault-commit.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--file-ops.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--folder-ops.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--sync.js"></script>

<script type="module" src="./vault-sgit-harness.js"></script>
```

### 10.3 Shared-vault coordination

Both baseline and optimised clients write to the same server-side vault. This means:

- Scenarios that mutate state (`single-save`, `burst-save-10`) must run **sequentially** between the two clients, not in parallel
- After the baseline runs, the optimised client must `pull()` (or re-open) before its own run so it sees the baseline's state
- Document this clearly in the run-history rows: "ran sequentially: baseline → pull → optimised"
- For read-only scenarios (`status-check`, `cold-open`, `pull-up-to-date`) the order does not matter

### 10.4 Test vault — use a dedicated one

Strongly recommend developers create a **dedicated test vault** for this page (via `/en-gb/vault` or `/en-gb/vault/peek`). The harness writes test files and creates fake commits. Running it against a production vault is fine but adds noise to the user's data — surface a warning in the loader: "Recommended: use a dedicated test vault for clean measurements."

### 10.5 Variance

Wall-clock timings vary with network conditions. Each scenario should record **at least 3 runs** before declaring a result; the metrics card shows median, the run history shows individual runs. Request counts and bytes are deterministic — they don't vary.
