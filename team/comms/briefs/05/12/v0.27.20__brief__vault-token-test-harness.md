## 5. Custom Elements to Build

All elements live in `vault-token-harness.js` (or dedicated files per element, your call). All are prefixed `vt-` to avoid collisions with existing `vault-*` elements.

### 5.1 `<vt-vault-loader>` — credential entry

Renders a form with a single text field: "Vault key or read-only token".

**Accepted inputs:**
- `word-word-NNNN` → full vault key (owner mode)
- `passphrase:vault_id` → full vault key (owner mode)
- `#ro-word-word-NNNN` or `ro-word-word-NNNN` → read-only token

**On submit:**
1. Parse input via `vault-credentials.js:parseCredential(input)`.
2. For `ro-` tokens: call `GET /api/transfers/check-token/{token}` to verify it exists (no use consumed).
3. Store result in sessionStorage (see §6 credentials schema).
4. Dispatch a CustomEvent `vt:credentials-loaded` on `document` with the parsed credentials.
5. Display status: "Owner mode — vault `coral-…` loaded" or "RO mode — vault `coral-…`".
6. Buttons: **Clear** (wipes sessionStorage + clears frames) | **Open in main vault →** (navigates `/en-gb/vault/#[key]` in a new tab).

### 5.2 `<vt-vault-frame>` — iframe vault panel

Hosts an `<iframe>` that loads `/en-gb/vault/` with the correct hash.

**On `vt:credentials-loaded` event:**
- `mode: 'owner'` — load `iframe.src = '/en-gb/vault/#[vault-key]'`
- `mode: 'ro'` — for RO tab only: the iframe needs the vault URL with the ro-token hash. But the existing vault page does NOT yet understand `#ro-[token]` — that is Phase 2 work. **For Phase 1:** show a placeholder ("RO simulation pending Phase 2 integration") or simulate by using the read key directly if the credentials object contains `readKey`. Document this limitation prominently in the panel header.
- Provide a **Reload** button and a **Pop-out** button (opens the iframe URL in a new tab).
- Apply a colored border to distinguish Owner (teal) vs RO (orange) frames.

> **Note:** The full RO vault experience requires Phase 2. The RO frame in Phase 1 primarily proves credential resolution and URL generation are correct.

### 5.3 `<vt-token-manager>` — create / list / revoke tokens

This is the main new-code panel. It uses `vault-credentials.js` and calls the transfer API directly.

**Requires:** Owner credentials loaded (show "Load a vault with a write key first" when not).

**Create Token section:**
```
Label:       [My dev token____________________]
Expires:     [7 days ▾]   Use limit: [unlimited ▾]
             [+ Create read-only token]
```

**On create:**
1. Derive `vault_secret_key` via `vault-hkdf.js:deriveVaultSecretKey(vaultKey, vaultId)`.
2. Load current `.vault/owner/readonly-tokens.json` (decrypt outer + inner layers). If file missing, start with `[]`.
3. Generate friendly token: `crypto.getRandomValues` → encode as `word-word-NNNN` pattern (see `vault-loader-format.js` for the pattern, or generate `[adjective]-[noun]-[0000-9999]`).
4. Encrypt payload `{ vault_id, read_key }` with the token as passphrase (AES-256-GCM using the token-derived key).
5. POST encrypted payload to `/api/transfers/create`, then upload ciphertext. **Capture `delete_key` from response.**
6. Append entry to tokens array: `{ token, delete_key, label, created_at, expires_at, max_uses, uses: 0, revoked: false, revoked_at: null }`.
7. Inner-encrypt the updated array with `vault_secret_key`, outer-encrypt with read key, write back to `.vault/owner/readonly-tokens.json`.
8. Show the shareable link: `https://[origin]/en-gb/vault/#ro-[token]` with copy button.

**Token List section:**
- Render one row per token: label, status badge (active / expired / revoked), "uses / max_uses", "expires in Nd", copy-link button, revoke button, **Load in RO frame** button.
- **Revoke flow:**
  1. Call `DELETE /api/transfers/delete/{transfer_id}` with `Authorization: {delete_key}` header.
  2. Mark entry `revoked: true`, `revoked_at: now`.
  3. Update `.vault/owner/readonly-tokens.json` (write back encrypted).
  4. If DELETE fails → show warning "Server-side delete failed — try again". Still mark revoked locally.

### 5.4 `<vt-crypto-lab>` — HKDF & encryption inspector

A debug panel for verifying the crypto primitives:

**HKDF Derivation:**
- Input: vault key (from loaded credentials or manual paste)
- Shows computed `vault_id` (SHA-256[:12])
- Button: **Derive vault_secret_key** → shows first 8 hex chars of result + "256-bit key derived"
- Shows the HKDF call parameters: `input`, `salt=vault_id`, `info="sgraph-vault-secret-v1"`, `length=32`

**Owner-namespace file inspector:**
- Input: file path (default `.vault/owner/readonly-tokens.json`)
- Buttons: **Fetch as owner** (inner+outer decrypt), **Fetch as RO reader** (outer decrypt only → shows "encrypted blob, cannot read")
- Output: either JSON pretty-printed or `{ encrypted: true, lockedToOwner: true }` sentinel

**Transfer API tester:**
- Manual `check-token` input to test resolution of an `ro-` token without consuming a use

### 5.5 `<vt-api-log>` — transfer API call log

A scrolling log of every call made during the session:
- `[timestamp] POST /api/transfers/create → 201`
- `[timestamp] GET /api/transfers/check-token/coral-stamp-1234 → 200 valid`
- `[timestamp] DELETE /api/transfers/delete/abc123 → 200`

Intercepts by wrapping `fetch` in a minimal proxy. **Critical:** the log must NEVER display actual token values or keys in the URL column — mask them as `***` after the slash.

### 5.6 `<vt-storage-inspector>` — localStorage/sessionStorage viewer

Adapted from the peek page's LS/SS rendering code. Shows vault-related keys in the same style as peek, but also shows the new `vt-credentials` sessionStorage key.

## 9. Transfer API — Exact Endpoints to Use

All calls go to the same origin. Base URL from sessionStorage `sg-vault-endpoint` (fallback: `https://dev.send.sgraph.ai`).

| Purpose | Method | Path | Auth |
|---|---|---|---|
| Create transfer slot | POST | `/api/transfers/create` | `X-SGraph-Send-Access-Token: {access_token}` |
| Upload ciphertext | POST | `/api/transfers/upload/{transfer_id}` | same header |
| Mark complete | POST | `/api/transfers/complete/{transfer_id}` | same header |
| Check token (no use consumed) | GET | `/api/transfers/check-token/{token_name}` | same header |
| Delete (revoke) | DELETE | `/api/transfers/delete/{transfer_id}` | `X-Transfer-Delete-Auth: {delete_key}` |

`transfer_id` comes from the create response. `delete_key` also comes from the create response — store it in the token entry.

**Access token:** read from `sessionStorage['sg-vault-access-key']` or `localStorage['sg-vault-access-key-saved']`. If neither is set, show a warning in the Token Manager panel ("Backend access token not set — token creation will fail. Set it in the Storage panel.").

## 14. Vault File Ops — How to Read/Write `.vault/owner/readonly-tokens.json`

The Token Manager needs to persist token metadata to the actual vault. **Reuse the existing vault library** — do not reinvent encryption, commits, or pushes.

### 14.1 Allowed reuse boundary

You may **import (as `<script>` tags)** any file under `_common/js/lib/` and `_common/js/services/`. You may NOT **modify** them. Importing for read-only consumption does not count as "touching" existing code.

### 14.2 Script load order

These classes are global (no ES modules, no `export`). Load order matters because `--file-ops.js`, `--folder-ops.js`, `--sync.js`, `--branches.js` extend `SGVault.prototype` via IIFE.

```html
<!-- Required order -->
<script src="../../../_common/js/lib/sg-send/sg-send-crypto.js"></script>
<script src="../../../_common/js/lib/sg-send/sg-send.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault-crypto.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault-object-store.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault-ref-manager.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault-commit.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--file-ops.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--folder-ops.js"></script>
<script src="../../../_common/js/lib/sg-vault/sg-vault--sync.js"></script>
```

### 14.3 Open a vault from a vault key

```js
const sgSend = new SGSend({
    endpoint: sessionStorage.getItem('sg-vault-endpoint') || 'https://dev.send.sgraph.ai',
    token:    localStorage.getItem('sg-vault-access-key-saved') || sessionStorage.getItem('sg-vault-access-key') || ''
});

// vaultKey can be:
//   - 'word-word-NNNN'        (simple token)
//   - 'passphrase:vault_id'   (full key)
const vault = await SGVault.open(sgSend, vaultKey);

console.log(vault.vaultId);   // string — 8-char alphanumeric or 12-hex
console.log(vault.writable);  // true if we have the passphrase / write key
```

### 14.4 Read `.vault/owner/readonly-tokens.json`

```js
// Ensure the folder exists in the tree (load on demand)
const ownerFolder = vault.listFolder('/.vault/owner');
//   → null if folder doesn't exist
//   → array of { name, type, size, content_hash } if it does

if (ownerFolder && ownerFolder.some(e => e.name === 'readonly-tokens.json')) {
    const plaintext = await vault.getFile('/.vault/owner', 'readonly-tokens.json');
    // plaintext is an ArrayBuffer of the OUTER-decrypted bytes
    // For Phase 1, we INNER-encrypt before passing to addFile/updateFile, so
    // these bytes are still ciphertext from our HKDF layer. Decrypt with vault-hkdf.js:
    const tokensJson = await ownerDecrypt(vault._passphrase, vault.vaultId, plaintext);
    const tokens     = JSON.parse(new TextDecoder().decode(tokensJson));
}
```

> Note: `vault._passphrase` is private but reachable. If you want a public accessor, add a method to `vault-credentials.js` that holds the passphrase separately. Do NOT add a method to `SGVault` — that breaks the zero-touch rule.

### 14.5 Write `.vault/owner/readonly-tokens.json`

```js
const tokensJson  = JSON.stringify(tokens, null, 2);
const plainBytes  = new TextEncoder().encode(tokensJson);

// Inner encryption layer (HKDF-derived key)
const innerCipher = await ownerEncrypt(vault._passphrase, vault.vaultId, plainBytes);
// innerCipher is base64; convert to Uint8Array for the vault
const innerBytes  = Uint8Array.from(atob(innerCipher), c => c.charCodeAt(0));

// Ensure parent folders exist
if (!vault.listFolder('/.vault'))       await vault.createFolder('/.vault');
if (!vault.listFolder('/.vault/owner')) await vault.createFolder('/.vault/owner');

// Write the file (this also commits)
const existing = vault.listFolder('/.vault/owner')?.find(e => e.name === 'readonly-tokens.json');
if (existing) {
    await vault.updateFile('/.vault/owner', 'readonly-tokens.json', innerBytes);
} else {
    await vault.addFile('/.vault/owner', 'readonly-tokens.json', innerBytes);
}

// Publish: fast-forward named ref to our clone HEAD
await vault.push();
```

`addFile`/`updateFile` both call `_commit()` internally — you do NOT need a separate commit step. `push()` is what makes the change visible to other clients.

### 14.6 Important — outer encryption is automatic

The vault library **already** encrypts every file with the vault read key before storing it on the server. Our HKDF inner layer is the **second** encryption. So `addFile(..., innerBytes)` results in:

```
server stores: encrypt(read_key, innerBytes)
where innerBytes = encrypt(vault_secret_key, plaintext)
```

A read-only viewer (read key only) decrypts the outer layer and gets `innerBytes` — they cannot decrypt the inner layer because they don't have `vault_secret_key`.

### 14.7 Read for ro-viewer verification (Crypto Lab "Fetch as RO reader")

To simulate what a RO viewer sees in the Crypto Lab inspector, do exactly the same `getFile` call but **skip the inner decrypt step** — surface the raw `innerBytes` as `{ encrypted: true, lockedToOwner: true, byteLength: N }`.

### 14.8 What you must NOT do

- Do NOT call `vault._objectStore` or `vault._commitManager` directly — use the public-ish methods above
- Do NOT modify any file under `_common/js/lib/`
- Do NOT add new methods to `SGVault.prototype` from your code (even via IIFE) — that is Phase 2's job
- Do NOT cache the vault instance across credentials changes — `Clear` in the Vault Loader must dispose the vault instance and create a fresh one on next load
