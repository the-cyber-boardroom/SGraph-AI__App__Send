## 1. Goal (One Sentence)

## 3. Decisions Already Made (Do Not Re-Open)

| Question | Answer |
|---|---|
| ro-token URL format | `#ro-[friendly-token]` (e.g. `#ro-coral-stamp-1234`) |
| ro-token storage | Existing SG/Send transfer API. Token = decryption key. Payload = `{ vault_id, read_key }`. NO new endpoints. |
| Owner namespace | `.vault/owner/*` — double-encrypted with `vault_secret_key` |
| Inner key derivation | `vault_secret_key = HKDF-SHA256(input=vault_key, salt=vault_id, info="sgraph-vault-secret-v1", length=32)` |
| Token list location | `.vault/owner/readonly-tokens.json` |
| **Access key scope** (app `auth.required`) | **Per-vault in localStorage, key = `accessKey:[vaultId]`** |
| **Token revoke behaviour (vault side)** | **Mark as revoked, keep entry** (audit trail). Do NOT delete the entry from `.vault/owner/readonly-tokens.json`. |
| **Token revoke behaviour (server side)** | **DELETE the encrypted blob on the server** via the existing transfer-delete endpoint, using the `delete_key` captured at token-issue time. This makes revoke effective server-side, not just client-side. Store `delete_key` in the token entry. |
| **Owner namespace visibility for RO viewers** | **Show with lock badge, list filenames only.** RO viewers can SEE `.vault/owner/readonly-tokens.json` exists but cannot decrypt it. |
| Credentials store | `sessionStorage` (tab-scoped). Hash cleared from URL immediately after parse. |
| Vault-credentials module | Shared module `vault-credentials.js` — single source of truth for `#[key]` vs `#ro-[token]` parsing. (Used by both `/en-gb/vault` and the future `/en-gb/app`.) |

## 6. Implementation Order

Eight phases. Each phase has a **stop-and-verify** gate. Do not jump phases.

### Phase 1 — Shared `vault-credentials.js` module

**Location:** alongside existing vault utils (find during §5).

**API:**

```js
// Parses location.hash, clears it from URL, stores in sessionStorage.
// Returns { mode: 'full'|'readonly', vaultId, key, readKey } once resolved.
// For ro- tokens: calls GET /api/transfers/{token}, decrypts payload with token, extracts { vault_id, read_key }.
async function loadVaultCredentials() { ... }

// Returns current credentials from sessionStorage, or null.
function getVaultCredentials() { ... }

// Clears credentials (logout).
function clearVaultCredentials() { ... }
```

**Hash formats handled:**

- `#[vault-key]` → mode: 'full'
- `#ro-[token]` → mode: 'readonly' (resolves via SG/Send transfer GET)
- empty → null (show entry screen)

**Stop-and-verify:**
- [ ] Unit test: full-key hash parses and stores correctly
- [ ] Unit test: `ro-` token hash triggers transfer API call and stores `{ vaultId, readKey }`
- [ ] Hash is cleared from `window.location` after parse
- [ ] `sessionStorage` is scoped per-tab (verify by opening two tabs)

### Phase 2 — Wire `vault-shell` to use `vault-credentials.js`

Replace existing hash-parse logic in `vault-shell.js` with a call to `loadVaultCredentials()`. Behaviour must be identical for existing `#[vault-key]` URLs — this is a refactor, not a behaviour change.

**Stop-and-verify:**
- [ ] Existing vault loads still work with `#[key]` URLs
- [ ] No regression in auto-push / merge flow

### Phase 3 — `.vault/` namespace consolidation (new vaults only)

For **newly created** vaults:
- `.vault/settings.json` (was `.vault-settings.json` at root)
- `.vault/owner/` directory reserved

Existing vaults: do nothing (see §8). Read code paths that read `.vault-settings.json` and add a fallback that prefers `.vault/settings.json` when present.

**Stop-and-verify:**
- [ ] New vault created via UI has `.vault/settings.json`, not root-level `.vault-settings.json`
- [ ] Loading an existing vault with old-style `.vault-settings.json` still works

### Phase 4 — HKDF helper + `vault_secret_key` derivation

Add a small crypto helper:

```js
// HKDF-SHA256(input=vault_key, salt=vault_id, info="sgraph-vault-secret-v1", length=32)
async function deriveVaultSecretKey(vaultKey, vaultId) { ... }
```

Use `crypto.subtle.deriveBits` with HKDF. Confirm whether an existing helper covers this before adding (see §4 Q1).

**Stop-and-verify:**
- [ ] Unit test: same `vault_key` + `vault_id` → same 32-byte output every time
- [ ] Different `vault_id` → different output
- [ ] Output is reachable only by callers who have the full vault key

### Phase 5 — Inner-encryption layer for `.vault/owner/*`

In the commit/push pipeline, files under `.vault/owner/` get an **extra** encryption pass with `vault_secret_key` before the existing outer encryption with the vault read key.

On read: detect `.vault/owner/` path → outer-decrypt as normal → inner-decrypt with `vault_secret_key` → return plaintext. If caller has only the read key (RO viewer), inner-decrypt fails → return `{ encrypted: true, lockedToOwner: true }` sentinel.

**Stop-and-verify:**
- [ ] Owner can write+read files under `.vault/owner/`
- [ ] Same vault loaded with RO key: file LIST shows `.vault/owner/readonly-tokens.json` with a lock badge (decision in §3)
- [ ] RO viewer attempting to open it sees a "locked to owner" placeholder, not plaintext, not a crash

### Phase 6 — RO token issue/manage UI (vault settings page)

In the vault settings UI (find during §5), add a "Read-only sharing" section:

- "Create new read-only link" button → opens modal with TTL + use-count + label fields
- On submit: generate friendly token (e.g. `coral-stamp-1234`), encrypt `{ vault_id, read_key }` with token as key, POST to existing `/api/transfers` endpoint (**capture the `delete_key` returned by the server**), append entry to `.vault/owner/readonly-tokens.json` with `{ token, delete_key, label, created_at, expires_at, max_uses, revoked: false, revoked_at: null }`, commit + push
- List view: show all tokens with status (active / expired / **revoked**), copy-link button, revoke button
- **Revoke = two-step:**
  1. Call existing transfer-delete endpoint with `delete_key` → server removes the encrypted blob (so the link stops working even on fresh loads on any device)
  2. Mark entry `revoked: true`, set `revoked_at` to now, **keep the entry** (audit trail). Do NOT delete from JSON.
- If server-delete fails (network/404): still mark `revoked: true` locally, surface a warning to the user, allow retry. Revoke is best-effort server-side but always definitive vault-side.

**Stop-and-verify:**
- [ ] Owner can create a token, copy `https://.../vault/#ro-coral-stamp-1234`
- [ ] Opening that link in another browser → RO mode, vault visible, no write affordances
- [ ] Revoking the token: server-side blob is deleted (verify via direct GET on the transfer URL → 404), future loads via that link fail on any device, existing loaded sessions are NOT killed (browser-side enforcement is sufficient for Phase 1)
- [ ] Revoked entry persists in `.vault/owner/readonly-tokens.json` with `revoked: true` and a "revoked" badge in the list
- [ ] `delete_key` is stored alongside the token at issue-time so revoke can call the transfer-delete endpoint

### Phase 7 — Visual cues (per architect review §"Visual Cues")

Three surfaces:

1. **Header badge** (`vault-header.js`) — `🔑 Owner` (full key) or `👁 Read-only` (ro-token). Persistent, always visible.
2. **Per-file list badge** — `🌐 Visible to all` (anywhere outside `.vault/owner/`) or `🔒 Owner-only` (inside `.vault/owner/`). Shown in the file tree.
3. **File-open banner** — when a file is opened, a 1-line banner above the content states scope: "🌐 This file is visible to anyone with a read-only link" or "🔒 This file is owner-only — RO viewers cannot see its contents".
4. **Issue-time preview** in the token-create modal — "Recipients will see: [count] files. Will NOT see: `.vault/owner/*` ([N] files)."

**Stop-and-verify:**
- [ ] All three surfaces visible in both owner mode and RO mode
- [ ] Badge updates correctly when toggling between vaults

### Phase 8 — Per-vault access key persistence

Where the app shell (future `/en-gb/app` work) will need `accessKey:[vaultId]` in `localStorage`: add the helper now in `vault-credentials.js` so the future work can call it:

```js
function getAccessKey(vaultId) { return localStorage.getItem(`accessKey:${vaultId}`); }
function setAccessKey(vaultId, value) { localStorage.setItem(`accessKey:${vaultId}`, value); }
function clearAccessKey(vaultId) { localStorage.removeItem(`accessKey:${vaultId}`); }
```

No UI in this brief — just the helper. The `/en-gb/app` brief will consume it.

**Stop-and-verify:**
- [ ] Unit tests for the three helpers
- [ ] No call sites yet (intentional)

## 8. Existing-Vault Migration

**Default: do nothing.** Old vaults keep `.vault-settings.json` at root. New vaults use `.vault/settings.json`. Code reads `.vault/settings.json` first, falls back to `.vault-settings.json`.

If you think automated migration is needed, **stop and ask** before writing it. A migration touches every vault and is a one-shot, high-blast-radius change.
