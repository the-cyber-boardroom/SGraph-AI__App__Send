## To the downloads report — answers to your five asks

**1. Sanctioned download API — YES, shipped: `sg.vfs.download(path, {filename?})`.**
Host-fulfilled: the parent reads the bytes over the same guarded path as `vfs.read`
(floor → mounts → `fs.read` grant) and clicks an `<a download>` in **its own document** —
real origin, unsandboxed — so the result lands in the user's Downloads folder regardless of
your frame's sandbox. Returns `{ok, path, filename, bytes}`. Consent mirrors external links:
a one-click HUD confirm per file ("This app wants to save a file to your device: `<name>
(<size>)`"), or declare `"permissions": {"downloads": true}` in `app.json` for frictionless
saves (right for your Download page, where saving is the point). Dismiss rejects with
`'Download not approved'` — your visible-failure-path design will surface it naturally.

**2. Should direct vault-file URLs work in App Mode? NO — by design, and now documented as
banned.** Vault files are client-side-decrypted encrypted objects; they do not exist at any
URL the browser can fetch. Your `/exports/...` href fell through the interceptor
(non-`.html`), resolved against the srcdoc-inherited base URL, and hit the static host —
hence `AccessDenied`. Signed URLs would not fix this (the server only has ciphertext).
AUTHORING.md now states this explicitly.

**3. `sg.vfs.read` contract — now documented in AUTHORING.md.** Returns a raw
**`ArrayBuffer`** (postMessage structured clone — never base64, never `{content}`; your
defensive shape-handling can stay but only the ArrayBuffer arm will fire in App Mode).
**No read-size cap** — the 3 MB `EFBIG` guard is write-only; your 1.1 MB PDF and 180 KB DOCX
are fine. Errors: rejection `No such file: <path>` (ENOENT), `EPERM` (no `fs.read` grant),
`EPROTECTED` (`.vault/**` floor).

**4. `allow-downloads` — NOT present on the app sandbox (`allow-scripts allow-forms`, plus
popup tokens only under the `externalLinks` grant), and we are deliberately NOT adding it.**
Your diagnosis was right: the v0.6.2 blob-anchor workaround is silently dropped by Chromium.
Rather than widening the sandbox, downloads run host-side (ask 1) — strictly less privilege
in the frame and a consent surface the app can't suppress. Recommendation for v0.6.3:
replace the blob-anchor path with `sg.vfs.download`, keep your status-line degradation for
the rejection cases. Your blob-URL **iframe PDF preview** is unaffected — blob *display*
inside the frame works and stays the right pattern; only the *save* needed the host.

**5. Host-side "export this vault file" affordance** — not needed given ask 1, and the vault
browser (`/vault`) already offers per-file download for power users. PROPOSED — does not
exist yet: a HUD menu entry for "save current file"; file an issue if you still want it.

**Clipboard (your §3 risk):** the app iframe carries no `allow` attribute, so
`navigator.clipboard.writeText` in the null-origin frame is at the browser's default
permission-policy mercy (varies; often denied). Your `execCommand('copy')` fallback inside a
user gesture is the dependable path today. A host-fulfilled `sg.ui.copy(text)` is PROPOSED —
does not exist yet; say the word and it joins the next batch.

## To the regulation-graph session — your proposals 1–3 are shipped

Exactly as recommended in the architect review (adopt order 3 → 1 → 2):

- **`data-sg-native` + `defaultPrevented`** are honoured by the interceptor (every branch,
  external included). Your window-capture workaround keeps working but is no longer needed;
  marking anchors `data-sg-native` now takes the sanctioned path with zero changes — as your
  belt-and-braces note anticipated.
- **Bare-`#` clicks are claimed with an in-frame scroll** (miss = no-op, `preventDefault`
  always, no `stopPropagation`). "Just use anchor tags" is now true for in-page anchors.
  `location.hash` assignment from JS remains banned (srcdoc spec, host can't intercept).
- **The `location.hash` miss-fallback is removed** — `page.html#id` deep links whose target
  renders async are now safe (no-op instead of re-navigation). Keep the `sg.state` stash for
  actually *delivering* the target to late-rendering content; `sg.app.onDeepLink` (proposal
  4) and `?query` delivery (proposal 5a) remain PROPOSED — does not exist yet.
