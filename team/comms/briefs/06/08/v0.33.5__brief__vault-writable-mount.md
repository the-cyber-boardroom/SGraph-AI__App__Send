---

## Why this is separate

The `sg.vault.create` return-key plan ([`v0.33.5__dev-plan__vault-create-return-key.md`](https://github.com/the-cyber-boardroom/sgraph-ai__app__send/blob/claude/zealous-thompson-yDjFX/team/roles/dev/reviews/06/08/v0.33.5__dev-plan__vault-create-return-key.md)) proposed, then deferred, a writable cross-vault mount. It is the **highest-risk** piece and **orthogonal** to returning the key, so it ships on its own track.

The doctor/patient management MVP does **not** need it: that flow uses `returnKey` + the owner-secret store + `openApp`. Writable mount is for the *different* use case of an app writing into another vault **in place** (e.g. seeding a template by live copy, or ongoing cross-vault writes) without opening it as a separate app.

---

## Current state (verified)

`_mountChildVault` (`app-shell.js:2331–2344`, ViV Phase 2) is **read-through only**:
- Mounts a child vault for cross-vault **reads** via the parent kernel.
- Uses the child's **read key** from the read-tier ro-record.
- There is no path that threads a **write key** into a mount's data source.

`sg.vault.mount(opts)` reads `{ prefix, ref, label }` — no `key`, no `mode`.

---

## Requested behaviour

```js
sg.vault.mount({ key|ref, prefix, mode:'ro'|'rw', label }) → { mountId }
```

- `mode:'ro'` — today's behaviour (read-through).
- `mode:'rw'` — open the child **writable** and expose a writable mount data source so the app can write across the mount boundary.
- The write capability comes from a **key** (a full vault key the app holds, or a `ref` the owner-secret store can resolve to a key). No new grant beyond `vault.mount` for the prefix — the key *is* the write authority.

---

## Why it's risky (the design problems to solve)

1. **Write-capability threading.** The mount data source must carry the child's `write_key` (hex) so writes authorize against the server. Today the mount carries only a read key. This touches the composite-data-source / kernel-mount plumbing (`composite-data-source.js`, `kernel-mounts.js`, `_mountChildVault`).
2. **Commit semantics across the boundary.** Writing into a mounted child means committing to the child's tree, not the parent's. The mount needs its own `SGVault` instance (opened writable) and its own commit/push lifecycle, surfaced through the bridge.
3. **Broker / custody gates.** ViV already has a credential-tier gate (`viv-credential-tiers.js`) and custody gate (`viv-custody.js`) for cross-vault writes. A rw mount must pass through these — a writable mount is exactly the elevated-tier case those gates were built for.
4. **AppSec surface.** A writable mount is the most powerful cross-vault primitive. It needs explicit sign-off, especially around: which keys an app may mount rw, whether consent is required per-mount, and how the writable mount appears in the audit/broker log.

---

## Acceptance criteria (when implemented)

1. `mount({ key, prefix, mode:'rw' })` yields a mount the app can write to; writes land in the child vault's tree and survive a re-open of the child.
2. `mount({ ref, prefix, mode:'rw' })` resolves the key from the owner-secret store (kernel-side) — the key never crosses the iframe boundary.
3. `mode:'ro'` is unchanged from today.
4. rw mounts pass the existing ViV credential-tier + custody gates and appear in the broker/audit log.
5. AppSec sign-off on the writable cross-vault path.

---

## Dependencies

- The **owner-secret store** (from the return-key plan, §3) — needed to resolve `ref → key` kernel-side.
- The ViV credential-tier (`viv-credential-tiers.js`) and custody (`viv-custody.js`) gates — already exist; rw-mount must route through them.
- AppSec review.

---

## Recommendation

Implement **after** the return-key plan's owner-secret store lands (it's a hard dependency for the `ref → key` resolution), and behind an AppSec review. Until then, apps needing to populate another vault use `seedFrom` at create time or `openApp` + in-app writes.
