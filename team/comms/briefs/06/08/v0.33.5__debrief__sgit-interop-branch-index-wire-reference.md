## 2. The exact wire format (what `writeBranchIndex` now emits)

Plaintext JSON (before encryption):

```json
{
  "schema": "branch_index_v1",
  "branches": [
    {
      "branch_id":   "branch-named-<12 hex>",
      "branch_type": "named",
      "head_ref_id": "ref-pid-muw-<12 hex>",
      "name":        "current"
    }
  ]
}
```

- Single named branch. No `created_at` (deliberately omitted — the plaintext is stable per vault so re-pushes don't churn the JSON; the AES-GCM IV still rotates per write, so the *ciphertext* differs each push).
- No clone branch is ever advertised (`head_ref_id` is the named ref only) — you keep cloning the canonical published branch.
- `schema`, `branch_type:"named"` match `Schema__Branch_Index` / `Enum__Branch_Type.NAMED`.

## 3. `branch_id` derivation — fully reproducible from `read_key` + `vault_id`

`branch_id` is **not random** — it's derived from the index file id's hex tail, which is itself HMAC-derived. So you can compute and verify it independently:

```
hmac_key          = HMAC-SHA256 key imported from read_key (raw bits)
branchIndexFileId = "idx-pid-muw-" + HMAC-SHA256(hmac_key, "sg-vault-v1:file-id:branch-index:" + vault_id).hex()[:12]
branch_id         = "branch-named-" + <that same 12-hex tail>
```

Properties:
- **Conformant** — `branch-named-[0-9a-f]{12}` ⊂ your `^branch-(named|clone)-[0-9a-f]{8,64}$`.
- **Deterministic** — same vault → same `branch_id` across every push.
- **Per-vault unique** — collision needs an HMAC collision on `(read_key, vault_id)`, the same property your ref file ids rely on.
- **Opaque** — pure hex, no human label (the display name lives elsewhere; see §7).

This is also the answer to "the index deserves an explicit byte-vector test like the ref vectors": **`branch_id` is a pure function of `read_key` + `vault_id`**, identical web↔CLI because the file-id domain (`sg-vault-v1:file-id:branch-index:{vault_id}`) is the one you already cited.

## 4. Crypto envelope — identical to the ref envelope

The index ciphertext at `bare/indexes/{branchIndexFileId}` uses the **same envelope as refs** (which you confirmed already interop):

```
stored_bytes = IV(12 bytes) || AES-256-GCM(read_key, IV, plaintext_json)
                                └── ciphertext includes the 16-byte GCM tag (WebCrypto appends it)
```

- Key: `read_key` (the AES-256-GCM key), **not** `structure_key` (the structure-key split is still inert — see the reality doc).
- IV: 12 random bytes, prepended. Decrypt = `slice(0,12)` IV, `slice(12)` ciphertext+tag.
- So a branch-index byte-vector test is structurally the **same** as your ref vectors — only the plaintext differs (`branch_index_v1` JSON vs `{"commit_id": "..."}`). If your ref vectors pass, an index vector with the §2 plaintext will too.

## 6. What we pinned on our side (so this can't drift again)

`tests/unit/vault_ui/loader/test__branch_index.js` (now 15 assertions) encodes **your** contract directly — a CI failure here blocks the merge:

```
branch_id matches /^branch-(named|clone)-[0-9a-f]{8,64}$/      ← your Safe_Str__Branch_Id regex
branch_id !== "branch-named-main"                              ← regression guard, bug A
name === "current"                                            ← your hardcode
name !== "main"                                               ← regression guard, bug B
same branchIndexFileId → same branch_id                        ← deterministic
different branchIndexFileId → different branch_id              ← per-vault unique
```

The tests source the real `sg-vault-ref-manager.js` via `runInThisContext` and use Node's Web Crypto, so they exercise the actual encrypt/decrypt round-trip, not a mock.

## 7. Architect interop contract (Option A) — proposed structure

You'll draft v0 from the CLI side citing `Schema__Branch_Index` + the `derive_*` code; here's the field list I'd want pinned, with two additions:

| Field | Rule | Source of truth |
|---|---|---|
| `schema` | `"branch_index_v1"` | both |
| `branch_id` | `^branch-(named|clone)-[0-9a-f]{8,64}$`; opaque; web derives from index file-id hex tail | CLI `Safe_Str__Branch_Id` |
| `branch_type` | `"named" | "clone"` | CLI `Enum__Branch_Type` |
| `name` (wire) | named branch MUST be `"current"` | CLI hardcode |
| **`display_name` (NEW, optional)** | human label the UI shows (e.g. `"main"`); never used for lookup | web request |
| `head_ref_id` | the **named** ref (`ref-pid-muw-*`) only — never the clone ref | rule we both follow |
| `created_at` | ISO-8601 string **or** int-ms, both accepted; web omits it | CLI (you verified both) |
| index file id | `"idx-pid-muw-" + HMAC-SHA256(read_key, "sg-vault-v1:file-id:branch-index:{vault_id}")[:12]` | both (identical) |
| crypto envelope | `IV(12) || AES-256-GCM(read_key, IV, plaintext)` — same as refs | both |
| path | `bare/indexes/{index_file_id}` | both |

**Two additions I'm requesting:**
1. **`display_name`** — so the web can show "main" without ever touching the wire `name`. This pre-empts the *next* "I want a friendly label" patch from re-breaking the wire (exactly how round 2 happened).
2. **A "reference payloads" appendix** — the §2 single-named-branch plaintext (and the multi-branch shape if you have a CLI reference) as literal JSON, so both sides paste it into a fixture. The whole reason round 2 happened is that the documented shape diverged from the live shape; a shared literal fixture eliminates that class of drift.

If we both sign it (citing `Schema__Branch_Index` + the live web `writeBranchIndex` + a shared fixture), future drift becomes a failing test, not a user-facing crash.

## 8. CLI hardening (your item 1) — endorsed, and here's why it's worth it regardless

You offered to make `Step__Clone__Download_Index` degrade a malformed/foreign index to the absent-index fallback. **Please ship it.** The principle — *a malformed index should degrade, not crash* — is correct independent of who shipped which payload first, and it protects against drift in *either* direction (a future CLI schema bump, a web field we add, a partial write). It turns "interop bug = user-facing crash" into "interop bug = graceful fallback + a log line." That's the right resilience posture for a two-implementation protocol. With it + our wire fix + our pinned tests, we have belt **and** braces.
