## Verdict: agreed — you're right, and it's fixed

**The blocking issue is real and I've fixed it.** Thank you for pulling the actual branch and tracing the failure path rather than reviewing the prose — this was a genuine regression I introduced, and your diagnosis was precise.

### The bug, confirmed

`_commit` advances `this._headCommitId = commitId` (and clears `_settingsDirty`, sets `_currentSettingsEntry`) **inside** the batched `fn()`, but the writes only land at `flushBatch()` which runs *after* `fn()` returns. So:

```
stage tree+commit+ref  →  _headCommitId = commitId  →  flushBatch()   ← throws (the 9.77s write you cited)
                                                        discardBatch() drops the staged writes
                                                        …but head already moved → phantom parent next commit
```

Pre-batch, head advanced **after** the PUTs succeeded, so a failed write left head untouched and a retry self-healed. My batched version broke that invariant. Your "the spec's atomicity section oversells it" is correct — the batch was fail-safe against *server-side* dangling refs (ordering), but left the *client* ahead of the server on flush failure.

### The fix (your option 1 — snapshot/restore)

`_withBatch` now snapshots `{_headCommitId, _namedHeadId, _settingsDirty, _currentSettingsEntry}` before `fn`, and **restores them in the catch** before rethrowing. This reinstates the pre-batch semantics: head only advances on a durable write, so a retry re-stages from the correct parent and self-heals. I chose snapshot/restore over "defer head mutation" because it composes cleanly with the re-entrant nested case (`addFile → _commit`) — the outermost scope owns the rollback, so a failed `addFile` rolls back to its true pre-call state without threading return values through the nested `_commit`.

Two details from the analysis:
- **`push` was already correct** — it sets `_namedHeadId` *after* `_withBatch` returns, so a failed push never advances it. I included `_namedHeadId` in the snapshot anyway (covers `create`, which sets it inside its batch; harmless for the rest).
- **The in-memory tree mutation is intentionally NOT rolled back.** That pre-dates this change (pre-batch `addFile` also left the tree ahead on a write failure) and self-corrects: once head is restored, the next commit re-stages blob+tree+commit with the *correct* (old) parent and advances head on success. Deep-cloning the tree per commit would be a much bigger hammer for no consistency gain.

### The missing test (added)

You flagged the suite covered staging/ordering/discard but not a failed flush. Added to `test__write_batch.js`: a failing `flushBatch` → asserts head/namedHead/settingsDirty/settingsEntry all roll back to their pre-batch values, the batch is discarded, and the error propagates; plus a success-path assertion that the advanced head survives. **22 assertions, green.**

## On your smaller notes

- **`>50` ops.** Agreed and now documented in the spec. A normal commit is ~5 ops so the message-send case is one POST; `addFiles` bulk-add can exceed 50 → `vaultBatch` chunks sequentially (>1 POST). Ordering still protects the server (refs in the last chunk; a throwing chunk stops the rest and the new rollback restores the client head), so it stays consistent — just not a single atomic request for bulk-add. Caveat added.
- **Read-backs (#15/#16/#19).** Agreed it's a separate follow-up. The batch-write response already returns per-op `status:'ok'`, so trusting it to skip the reconcile read is the right next step — but it needs care against reconcile-on-open (the recent `SGVault.open` clean-behind work), so I'd rather land it deliberately than fold it in here.
- **`Access-Control-Max-Age` on `/batch`.** Please do verify this from the backend/CloudFront side — the client change makes the cacheable-preflight win *possible*, but if the header isn't actually sent (or CF strips it), the "~0 preflights after the first send" projection won't materialise. That's the one external dependency for the full win. **Yes, please check it.**
