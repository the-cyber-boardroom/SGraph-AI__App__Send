# Migration Guide: Vault Inbox → Append API (Breaking Change)

**date** 10 June 2026
**from** Explorer team (SG/API)
**to** Vault web team, sgit CLI team, comms-MVP agent, any app hitting `/api/vault/inbox/*`
**type** Breaking-change migration guide
**urgency** Immediate — merged to `dev`, deploying to prod
**full API reference** `team/comms/briefs/06/07/v0.32.7__api-to-vault-team__inbox-implementation-guide.md`

---

## What Changed

The vault inbox API has been renamed to **vault append**. All six endpoints moved
from `/api/vault/inbox/*` to `/api/vault/append/*`, and the write endpoint
changed from `/append/` to `/write/`. The old URLs **no longer exist** and will
return 404.

**This is a clean rename plus one enum value change.** The request/response body
shapes, headers, gate model, and storage semantics are all unchanged — only the
URL paths and one body value need updating.

---

## 1. URL Changes (All Six Endpoints)

| Old URL | New URL |
|---------|---------|
| `POST /api/vault/inbox/configure/{vault_id}` | `POST /api/vault/append/configure/{vault_id}` |
| `POST /api/vault/inbox/append/{vault_id}` | `POST /api/vault/append/write/{vault_id}` |
| `POST /api/vault/inbox/list/{vault_id}` | `POST /api/vault/append/list/{vault_id}` |
| `POST /api/vault/inbox/fetch/{vault_id}` | `POST /api/vault/append/fetch/{vault_id}` |
| `POST /api/vault/inbox/mark-processed/{vault_id}` | `POST /api/vault/append/mark-processed/{vault_id}` |
| `POST /api/vault/inbox/purge/{vault_id}` | `POST /api/vault/append/purge/{vault_id}` |

**Note the write endpoint:** the old path was `/inbox/append/` (verb "append"
inside noun "inbox"). The new path is `/append/write/` (verb "write" inside noun
"append"). This avoids the confusing `/append/append/` path.

## 2. Body Field Change (Purge Only)

The purge endpoint's `folder` field changed one accepted value:

| Old value | New value |
|-----------|-----------|
| `"inbox"` | `"pending"` |

`"processed"` is unchanged. Sending `"inbox"` now returns HTTP 400.

**Example fix:**
```diff
- { "folder": "inbox",     "inbox": "<token>" }
+ { "folder": "pending",   "inbox": "<token>" }
```

## 3. What Did NOT Change

Everything else is identical:

- **Headers:** `x-sgraph-vault-enum-key`, `x-sgraph-vault-write-key`, `x-sgraph-access-token` — same names, same positions
- **Body field names:** `inbox`, `append_token`, `payload`, `file_ids`, `after_file_id`, `limit`, `include_content`, `enum_key_hash`, `append_anchors` — all unchanged
- **Response shapes:** same fields, same status codes
- **Gate model:** four tiers (append_token, enum_key, write_key, private_key) — unchanged
- **Token formats:** `Safe_Str__Vault__Append_Token` (`^[0-9a-f]{16,128}$`), `Safe_Str__Vault__Append__File_Id` (`^\d{13}_[0-9a-f]{24}\.enc$`) — unchanged
- **Wire-compat:** The `inbox` field name in list/fetch/mark/purge bodies is **intentionally retained**. It identifies the token folder. No rename needed in request bodies.

## 4. Find-and-Replace Checklist

For most codebases the migration is mechanical. Run these replacements in order:

```
1.  /api/vault/inbox/append/    →  /api/vault/append/write/
2.  /api/vault/inbox/           →  /api/vault/append/
3.  "folder": "inbox"           →  "folder": "pending"
    (or folder:"inbox"          →  folder:"pending"        for JS without spaces)
4.  folder: 'inbox'             →  folder: 'pending'
    folder: "inbox"             →  folder: "pending"
```

**Step 1 must come before step 2** — otherwise you'd get `/api/vault/append/append/`.

After replacing, grep for any remaining `/vault/inbox` to catch edge cases
(comments, tests, documentation, config files).

## 6. Server-Side Limits Reference

These are the hard limits enforced by the SG/API backend. Client apps should
design within them.

### Append API limits

| Limit | Value | HTTP error | Notes |
|-------|-------|-----------|-------|
| **Max payload per write** | 5 MB | 413 | Single `payload` field (base64-decoded bytes) |
| **Max files per token** | 1,000 | 507 | Pending files for one append_token |
| **Max entries per list page** | 200 | — | Clamped silently; default 50 |
| **Inline content ceiling** | 3 MB cumulative | 413 | `include_content:true` bails early when sum exceeds 3 MB |
| **Batch cap (fetch/mark/purge)** | 100 file_ids | 400 | Client must page larger batches |

### Vault pointer API limits

| Limit | Value | Notes |
|-------|-------|-------|
| **Read-base64 response** | ~3.75 MB | Lambda 5 MB response limit minus base64 overhead |
| **Read (binary)** | ~5.5 MB | Lambda response body limit |
| **Write (single PUT)** | ~5.5 MB | Lambda request body limit |
| **Write (presigned multipart)** | Unlimited | S3 multipart via presigned URLs, 5 GB per part |
| **Batch operations** | 100 per request | `POST /api/vault/batch/{vault_id}` |
| **Immutable block caching** | `Cache-Control: public, max-age=31536000, immutable` | For `-imm-` file_ids only; refs/indexes are `no-store` |

### VFS bridge limits (client-side — NOT SG/API)

| Limit | Value | Notes |
|-------|-------|-------|
| **`sg.vfs.write` (SecureChannel path)** | No known size limit | Raw `Uint8Array` via structured clone; no base64 on wire |
| **`sg.vfs.write` (legacy `__sgVfsWriteReq` path)** | **~8 KB** | Bug: base64 encoding truncates above ~8 KB; surfaces as `"Bad encoding"`. See `team/comms/briefs/06/10/v0.32.7__debrief__api-to-vault-team__append-status-and-vfs-write-cap.md` for full root-cause analysis. |
| **No chunked/streaming write** | — | No `vfs.append` or offset-write exists. A file must fit in one `sg.vfs.write` call. |
| **No chunked/streaming append** | — | No server-side streaming endpoint. A message must fit in one 5 MB `payload`. |

## 7. Storage Path Change

The on-disk/S3 storage paths also moved. This matters if you read storage
directly (e.g. sgit managing `bare/append/` during clone/push):

| Old path | New path |
|----------|----------|
| `{root}/vault/{id[:2]}/{id}/inbox/{token}/...` | `{root}/vault/{id[:2]}/{id}/bare/append/{token}/pending/...` |
| `{root}/vault/{id[:2]}/{id}/inbox/{token}/processed/...` | `{root}/vault/{id[:2]}/{id}/bare/append/{token}/processed/...` |
| (config in manifest) | `{root}/vault/{id[:2]}/{id}/bare/append/config.json` |

**Key architectural change:** Append config (`append_anchors`, `enum_key_hash`)
is now stored in `config.json`, NOT in the vault manifest. The manifest is no
longer co-owned — `Service__Vault__Pointer` owns the manifest exclusively.
The gates (`_check_append_token`, `_check_enum_key`) read from `config.json`
only. If you build tooling that writes `config.json`, the gates will honour it.

---

## 8. Why the Rename

"Inbox" baked in a single use case (messaging) when the same infrastructure
serves logs, signals, control messages, state flows, and email workflows.
"Append" describes what the server does — the client decides the semantics.

Moving into `bare/` makes append data a first-class sgit namespace
(managed-but-unversioned), so the CLI can manage it alongside `data/`, `refs/`,
`keys/`, and `indexes/`.

## 9. Testing the Migration

After updating URLs, run this minimal smoke test against `send.sgraph.ai`:

```bash
# 1. Configure (need existing vault with write_key)
curl -X POST https://send.sgraph.ai/api/vault/append/configure/$VAULT_ID \
  -H "x-sgraph-vault-write-key: $WRITE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"append_anchors":["'$ANCHOR_HASH'"],"enum_key_hash":"'$ENUM_HASH'"}'
# Expect: {"vault_id":"...","status":"configured"}

# 2. Write (no access token needed)
curl -X POST https://send.sgraph.ai/api/vault/append/write/$VAULT_ID \
  -H "Content-Type: application/json" \
  -d '{"append_token":"'$TOKEN'","payload":"'$(echo -n "test" | base64)'"}'
# Expect: {"ok":true}

# 3. List
curl -X POST https://send.sgraph.ai/api/vault/append/list/$VAULT_ID \
  -H "x-sgraph-vault-enum-key: $ENUM_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
# Expect: {"status":"ok","entries":[...],"truncated":false}
```

If you get 404 on any endpoint, you're still hitting the old `/inbox/` URL.
If purge returns 400, check that `folder` is `"pending"` or `"processed"` (not `"inbox"`).
