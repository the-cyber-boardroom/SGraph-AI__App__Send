## 1. VFS Write-Cap (~8 KB "Bad encoding") — Not an SG/API Issue

We investigated the reported `sg.vfs.write` failure above ~8 KB. **The issue is
entirely client-side JavaScript in the vault UI bridge code, not in any SG/API
endpoint or service.**

### Root cause

There are **two** VFS write paths in the codebase. The bug is in the legacy one:

| Path | Transport | Size limit | Status |
|------|-----------|-----------|--------|
| **Legacy** `__sgVfsWriteReq` (`app-shell.js:2482`) | `window.postMessage` with base64 in `e.data.data` | **~8 KB** — `atob()` throws on truncated/corrupt data | **BUG** |
| **New** SecureChannel (`kernel-app-handlers.js:108`) | `MessageChannel` port, structured clone — `Uint8Array` round-trips natively | **No base64 size limit** | OK |

**Legacy path** (`app-shell.js:2491-2494`):
```js
var bin = atob(e.data.data || '');         // receiver: base64 → binary string
wBytes  = new Uint8Array(bin.length);
for (var i = 0; i < bin.length; i++) wBytes[i] = bin.charCodeAt(i);
// catch (_) { wReply(false, { err: 'Bad encoding' }); return; }
```
Above ~8 KB of raw content, `e.data.data` arrives truncated and `atob` throws.
The likely sender-side cause is `String.fromCharCode.apply(null, bytes)` without
chunking — the JS engine's `apply` argument limit is ~8192 on some runtimes.

**New SecureChannel path** (`kernel-app-handlers.js:108`):
```js
channel.handle('vfs.write', async function (p) {
    const data = p.data instanceof Uint8Array ? p.data : new Uint8Array(p.data || []);
    await ds.saveFile(dir, name, data);    // raw bytes, no base64 on the wire
```
Data travels as a raw `Uint8Array` over the `MessageChannel` port via structured
clone. The Envelope module's `_bytesToB64` (used only for signature computation)
properly chunks at 8192 bytes (`secure-channel-envelope.js:76-83`). No size issue.

### SG/API backend limits (for reference)

These are the actual server-side limits — none are ~8 KB:

| Limit | Value | Where |
|-------|-------|-------|
| Append payload per message | **5 MB** | `APPEND_MAX_PAYLOAD` in `Service__Vault__Append.py` |
| Append files per token | **1000** | `APPEND_MAX_FILES` |
| Append batch cap (fetch/mark/purge) | **100 file_ids** | `APPEND_BATCH_MAX_FILE_IDS` |
| Inline content ceiling (list with content) | **3 MB** cumulative | `INLINE_CONTENT_CEILING` |
| Vault pointer write | **No explicit limit** | Lambda payload (~6 MB) is the ceiling |

### Recommendations for the vault team

1. **Fix the legacy `__sgVfsWriteReq` handler** — chunk the sender-side base64
   encoding (same pattern as `_bytesToB64` in `secure-channel-envelope.js`), or
   switch to `Uint8Array` transport via structured clone.
2. **Or deprecate the legacy path** — if all apps should use `sg.vfs.write()` via
   `sg-app-stub.js` / SecureChannel, emit a console warning on the legacy handler
   and guide apps to the new API.
3. **Fix the error message** — return `{ err: 'Payload too large', code: 'EFBIG' }`
   with the actual vs allowed size, not the misleading `'Bad encoding'`.
4. **Confirm which apps still use the legacy path** — any app calling
   `window.parent.postMessage({ __sgVfsWriteReq: ... })` directly (instead of
   `sg.vfs.write()`) will hit this.

The `send-browse--v0.3.2.js` (`sgraph_ai_app_send__ui__user`) and
`send-browse--v0.3.3.js` (`sgraph_ai_app_send__ui__open`) both carry the same
legacy `atob` handler at their respective line ~1103/~888. These may also need
the fix if they serve writable vault contexts.

## 2. Vault Append Backend — Current State

### What shipped (all code-verified, 133 tests, no mocks)

The inbox-to-append rename is complete. All six endpoints, the four-tier gate
model, storage paths, typed validation, and blind-write contract are implemented
and tested.

**Endpoints** (all `POST`, under `/api/vault/append/`):

| Endpoint | Auth | HTTP errors |
|----------|------|-------------|
| `/write/{vault_id}` | `append_token` (body) | 400, 403, 413, 507 |
| `/list/{vault_id}` | `enum_key` (header) | 400, 403, 413 |
| `/fetch/{vault_id}` | `enum_key` (header) | 400, 403 |
| `/mark-processed/{vault_id}` | `enum_key` (header) | 400, 403 |
| `/purge/{vault_id}` | `write_key` (header) | 400, 403 |
| `/configure/{vault_id}` | `write_key` (header) | 403 |

**Account-less write surface:** No SGraph access token required for
write/list/fetch/mark-processed. The append_token is the sole gate for writes;
enum_key for reads. Deliberate — enables cross-vault communication without
requiring both parties to have SGraph accounts.

**Storage paths** (inside `bare/append/`, managed-but-unversioned by sgit):
```
{_ROOT}/vault/{vault_id[:2]}/{vault_id}/bare/append/
    config.json                                          ← append gate config (authoritative)
    {token}/pending/{epoch_ms}_{random_hex}.enc          ← new entries
    {token}/processed/{filename}                         ← after mark-processed
```

**Gate model:**

| Tier | Can do | Gate check |
|------|--------|-----------|
| `append_token` | write (blind) | `H(token) in config.append_anchors` |
| `enum_key` | list, fetch, mark-processed | `H(key) == config.enum_key_hash` |
| `write_key` | configure, purge | `H(key) == manifest.write_key_hash` |
| `private_key` | decrypt content | Client-side only, never on server |

### L-2 fix: config.json is authoritative (10 June 2026)

The original L-2 finding (QA review, 8 June) flagged that `configure()` wrote
append fields (`append_anchors`, `enum_key_hash`) to **both** `config.json` and
the manifest — but the gates only read from the manifest, making `config.json`
dead data and leaving the manifest co-owned between pointer and append services.

**Now fixed (Option A):**
- Gates (`_check_append_token`, `_check_enum_key`) read **exclusively from
  `config.json`** via a cached `_load_append_config()` reader.
- `configure()` **no longer writes** append fields into the manifest. Only
  `config.json` is written and cached.
- The `_check_write_key` gate stays reading from the manifest — `write_key_hash`
  is owned by `Service__Vault__Pointer` and shared intentionally.
- Test: `test__configure__does_not_write_append_fields_to_manifest` verifies
  the separation.

**Impact for vault team:** If you ever build tooling that reads or writes
`config.json` directly (e.g. sgit managing `bare/append/` during clone/push),
the gates will honour it. The manifest no longer carries append state.

### Wire-contract change: purge folder value

The purge endpoint's `folder` body field changed from `"inbox"` to `"pending"`.
Accepted values are now `"pending"` or `"processed"`. Sending `"inbox"` will
return HTTP 400.

The `inbox` **field name** (e.g. `{"inbox": "<token>"}` in list/fetch/mark/purge
bodies) is retained for wire compatibility. This is the token-folder identifier,
not a folder enum.

### Input validation (security)

All path-component inputs are validated via `Type_Safe` strict validators:
- `Safe_Str__Vault__Append_Token`: `^[0-9a-f]{16,128}$` (hex only)
- `Safe_Str__Vault__Append__File_Id`: `^\d{13}_[0-9a-f]{24}\.enc$`

These block path traversal at the type level — `../../etc` fails validation
before it reaches any storage call. 8 traversal negative tests + 3 batch-cap
tests exercise this.
