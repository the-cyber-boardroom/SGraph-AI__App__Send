# Brief — Presigned-PUT large-write path for `sg.vfs.write` (lift the ~3 MB ceiling)

**Version:** v0.33.21
**Date:** 2026-06-11
**For:** SG/API team (server) + Vault UI team (client) + sgit CLI team (informational)
**Status:** Proposed, scoped, not yet built.

## Why

Today an app-facing `sg.vfs.write` is capped at ~3 MB plaintext. One write becomes one
`POST /api/vault/batch` carrying the new blob + tree + commit + ref + index, each
base64-encoded inside JSON. AWS Lambda URL Functions cap the request payload at 6 MB;
base64 inflates ~1.33×; the rest of the batch eats ~10–50 KB. So 3 MB is the
conservative ceiling the host now enforces with `EFBIG`. (For context: the
historical "Bad encoding" at 8 KB was a separate base64 chunking bug, fixed at
v0.33.21.)

Reads already scale further — anything > 4 MB uses a **presigned-S3 URL** via
`GET /api/vault/presigned/read-url/{vaultId}/{filePath}`, fetched directly from
S3 by the browser. **Writes have no equivalent.** Result: an app can read multi-MB
blobs (videos, PDFs, datasets, ML weights) but can't store them in one call.

This brief proposes the mirror endpoint and the client switch.

## What

### Server: `POST /api/vault/presigned/write-url/{vaultId}/{filePath}`

Same shape and access policy as the read counterpart, just write-scoped:

- **Auth:** requires the `x-sgraph-vault-write-key` header (existing write gate).
- **Scope:** path MUST start with `bare/data/obj-cas-imm-` (only content-addressed
  immutable blobs use this path — refs/indexes/commits stay on the small-write batch
  endpoint, because they're tiny and mutating).
- **Response:** `{ "url": "<presigned PUT url>", "expires_in": 300, "max_bytes": 6291456 }`.
- **S3 conditions on the presigned URL:**
  - `Content-Length` between 1 and ~6 MB (or whatever the deployment's S3/object
    quota allows — likely the real ceiling will be 5 GB once we lift past Lambda).
  - `Content-Type: application/octet-stream`.
  - Key path matches exactly what the client requested (no key substitution).
- **Memory-FS mode:** return 400 with `presigned_unavailable` so the client can
  fall back to the existing batch write (matches the read fallback).

### Client (`sg-send.js` + `sg-vault-object-store.js`)

A `vaultWriteLarge(vaultId, filePath, writeKey, bytes)` that mirrors
`vaultReadLarge`:

```js
async vaultWriteLarge(vaultId, filePath, writeKey, bytes) {
    const presign = await this._fetch('POST',
        `/api/vault/presigned/write-url/${vaultId}/${filePath}`,
        { headers: { 'x-sgraph-vault-write-key': writeKey } }
    );
    if (presign.status === 400) return null;   // memory mode → fall back
    const { url } = await presign.json();
    const put = await fetch(url, {
        method: 'PUT',
        headers: { 'Content-Type': 'application/octet-stream' },
        body: bytes
    });
    if (!put.ok) throw new Error(`Large-write PUT failed: ${put.status}`);
    return { filePath };
}
```

Object-store `store()` picks the path by size, mirroring `getFile`/`loadLarge`:

```js
async store(ciphertext) {
    const objectId = await this.computeObjectId(ciphertext);
    const filePath = `bare/data/${objectId}`;
    const bytes    = new Uint8Array(ciphertext);

    const LARGE_WRITE_THRESHOLD = 4 * 1024 * 1024;   // same threshold as reads
    if (bytes.byteLength > LARGE_WRITE_THRESHOLD && !this.batching) {
        const result = await this._sgSend.vaultWriteLarge(this._vaultId, filePath, this._writeKey, bytes);
        if (result) { await this._cachePut(objectId, filePath, ciphertext); return objectId; }
        // null → presigned unavailable → fall through to legacy path
    }

    if (this.batching) { this._stage(filePath, bytes); return objectId; }
    await this._sgSend.vaultWrite(this._vaultId, filePath, this._writeKey, bytes);
    await this._cachePut(objectId, filePath, ciphertext);
    return objectId;
}
```

Notes:
- **Inside a batch (commit flush)**, the large blob goes via the presigned PUT
  **before** the batch POST — and the batch then only references the blob's
  content-addressed id (which is tiny). This keeps the batch under 6 MB even when
  a commit includes a multi-MB blob.
- **Encryption stays client-side.** What gets PUT is the AES-GCM ciphertext —
  the server never sees plaintext, identical to the small-write path.
- **Content-addressing is preserved.** The objectId is `SHA-256(ciphertext)`; the
  PUT URL is keyed by that same id, so the server can verify on receipt.

### Lift the host `EFBIG` ceiling

Once the path lands, `app-shell.js`'s 3 MB guard becomes:

```js
var MAX_WRITE_BYTES = 32 * 1024 * 1024;   // app-facing ceiling — picked by policy, not by Lambda
```

The real maximum becomes S3's `Content-Length` limit (5 GB), but we'll cap at
something sensible for the app surface (32 MB is plenty for any sane in-iframe app;
power-user CLI writes via `sgit` aren't gated by this).

## CLI implications (informational)

`sgit push` already PUTs object bytes directly, so it doesn't hit the batch
ceiling — no CLI change required. The presigned write would actually let
the CLI offload S3 uploads from the Lambda too, which is a nice side win
(currently every CLI PUT round-trips through Lambda).

## Test plan

**Server:**
- New positive: presigned URL is returned, has correct expiry, restricts path.
- Negative: missing write key → 401; non-`bare/data/obj-cas-imm-*` path → 400;
  memory mode → 400 with `presigned_unavailable`.
- Round-trip: client gets URL, PUTs ciphertext, then reads via the existing
  presigned READ → byte-identical.

**Client:**
- Unit: `vaultWriteLarge` routes by size; falls back on 400.
- Unit: `store()` picks the right path based on `bytes.byteLength`.
- Integration: write 8 MB → verify it landed in S3 + read back via `getFile` →
  bytes match.

**Host (app-shell):**
- Raise `MAX_WRITE_BYTES` to 32 MB.
- Adjust `test__sg_app_stub` / `test__vfs_write` to cover the new ceiling.

## What we are NOT changing

- The write API surface (`sg.vfs.write(path, content)` — no new verb, no
  `{offset}`, no streaming handle). The point of presigned-PUT is precisely
  that we don't need any of that to get multi-MB writes — a single call still
  carries the whole blob.
- The batch endpoint for refs/indexes/commits — those are tiny, and batching
  is exactly what keeps a commit consistent.
- The base64 encoding for the small-write path — only the *large* path PUTs
  raw bytes (`application/octet-stream`).
