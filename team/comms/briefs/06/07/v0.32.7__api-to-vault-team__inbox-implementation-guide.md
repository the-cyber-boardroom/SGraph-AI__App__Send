## What This Is

The SG API team has shipped the server-side inbox (6 endpoints, 957 tests green,
deployed to `send.sgraph.ai` and `main.send.sgraph.ai`). This brief tells the
vault web and CLI teams exactly how to call it — request shapes, header
conventions, token formats, the polling loop, and the gotchas we hit so the vault
team doesn't repeat them.

A working reference exists: the **Vault⇔Vault Comms Harness**
(`harp-make-6182`) exercises the full protocol end-to-end in three sandboxed
iframes. Its mock transport mirrors `Service__Vault__Inbox` faithfully; its live
transport hits the real endpoints.

## The Six Endpoints

Base: `https://send.sgraph.ai/api/vault/inbox`

All endpoints are **POST**. All request/response bodies are JSON.

### 1. Configure — establish inbox hashes on an existing vault

```
POST /api/vault/inbox/configure/{vault_id}

Headers:
  x-sgraph-access-token:    <access-token>
  x-sgraph-vault-write-key: <write_key_hex>
  Content-Type:             application/json

Body:
{
  "append_anchors": ["<sha256_hex_of_append_token_1>", ...],
  "enum_key_hash":  "<sha256_hex_of_enum_key>"
}

Response 200:
{ "vault_id": "...", "status": "configured" }

Errors:
  403  Write key mismatch (or vault does not exist)
```

**Important:** The vault MUST already exist (created via
`PUT /vault/write/{vault_id}/{file_id}` with the same write_key). Configure
patches the existing manifest — it does not create the vault.

The `append_anchors` array holds `SHA256(append_token)` for each accepted
sender. The `enum_key_hash` is `SHA256(enum_key)`. The server stores hashes
only — it never sees the raw keys.

### 2. Append — blind, write-only message delivery

```
POST /api/vault/inbox/append/{vault_id}

Headers:
  Content-Type: application/json

Body:
{
  "append_token": "<hex_token>",
  "payload":      "<base64_encoded_ciphertext>"
}

Response 200:
{ "ok": true }

Errors:
  400  Invalid append_token (format validation failed)
  403  Forbidden (token hash not in append_anchors)
  413  Payload too large (>5 MB)
  507  Insufficient Storage (>1000 files in this inbox)
```

**No access token required.** The append_token IS the auth. The response is
deliberately blind — no file_id, no count, no metadata. The sender learns
nothing about the inbox state.

### 3. List — paginated inbox scan

```
POST /api/vault/inbox/list/{vault_id}

Headers:
  x-sgraph-vault-enum-key: <enum_key_hex>
  Content-Type:            application/json

Body:
{
  "inbox":           "<append_token_hex>" | null,
  "after_file_id":   "<cursor>" | null,
  "limit":           50,
  "include_content": false
}

Response 200:
{
  "status":    "ok",
  "entries":   [
    { "inbox": "<token>", "file_id": "<timestamp>_<random>.enc", "received": 1717720000000 },
    ...
  ],
  "truncated": false
}

With include_content: true, each entry also has:
  "size":    <bytes>,
  "content": "<base64_ciphertext>"

Errors:
  403  Forbidden (enum_key hash mismatch)
  400  Invalid inbox or limit
  413  Content exceeds inline ceiling (3 MB summed)
```

**Pagination:** set `after_file_id` to the last `file_id` from the previous
page. Entries are sorted by `file_id` (which is `{epoch_ms}_{random}.enc`),
so pagination is stable and cursor-based.

**Metadata-only mode** (`include_content: false`) reads zero payloads from
storage. Use this for the inbox count / refresh check. Fetch content separately
with the fetch endpoint or via `include_content: true` for small batches.

**Scan all inboxes:** omit `inbox` (or set to `null`) to scan all sender
folders. Set `inbox` to a specific append_token to scope to one sender.

### 4. Fetch — retrieve specific messages by file_id

```
POST /api/vault/inbox/fetch/{vault_id}

Headers:
  x-sgraph-vault-enum-key: <enum_key_hex>
  Content-Type:            application/json

Body:
{
  "inbox":    "<append_token_hex>",
  "file_ids": ["<file_id_1>", "<file_id_2>", ...]
}

Response 200:
{
  "status":  "ok",
  "files":   [{ "file_id": "...", "size": 1234, "content": "<base64>" }, ...],
  "missing": ["<file_id_not_found>", ...]
}

Errors:
  400  Missing inbox or file_ids; batch >100; invalid format
  403  Forbidden
```

### 5. Mark-processed — move messages out of the inbox

```
POST /api/vault/inbox/mark-processed/{vault_id}

Headers:
  x-sgraph-vault-enum-key: <enum_key_hex>
  Content-Type:            application/json

Body:
{
  "inbox":    "<append_token_hex>",
  "file_ids": ["<file_id_1>", ...]
}

Response 200:
{
  "status":  "ok",
  "moved":   ["<file_id_1>", ...],
  "missing": []
}

Errors:
  400  Missing inbox or file_ids; batch >100
  403  Forbidden
```

**Idempotent:** if a file was already moved (or never existed), it appears in
`missing` — no error. This is intentional; the brief's seq-number layer handles
crash-between duplicates.

### 6. Purge — delete processed messages

```
POST /api/vault/inbox/purge/{vault_id}

Headers:
  x-sgraph-access-token:    <access-token>
  x-sgraph-vault-write-key: <write_key_hex>
  Content-Type:             application/json

Body:
{
  "folder":   "processed",
  "inbox":    "<append_token_hex>",
  "file_ids": ["<file_id>", ...] | null
}

Response 200:
{
  "status":  "ok",
  "purged":  ["<file_id_1>", ...],
  "missing": []
}

Errors:
  400  Missing inbox; invalid folder; batch >100
  403  Write key mismatch
```

**Bulk purge:** set `folder` to `"processed"` and omit `file_ids` to delete
all processed files for that inbox in one call.

## The Four-Tier Capability Model

Each tier has exactly one job. Tiers do not overlap.

| Tier | Token / Key | Who Holds It | What It Can Do |
|------|-------------|-------------|----------------|
| **append_token** | Hex, 16–128 chars | The sender (one per accepted pubkey) | Append only. Cannot list, fetch, or read. |
| **enum_key** | Any string | The vault owner | List, fetch, mark-processed. Cannot append or purge. |
| **write_key** | Any string | The vault owner | Configure, purge. Must match the vault's write_key_hash. |
| **private_key** | X25519 | The vault owner (never leaves client) | Decrypt ciphertext. Never sent to server. |

**The server never holds raw keys.** It stores `SHA256(write_key)`,
`SHA256(enum_key)`, and `SHA256(append_token)`. Gate checks are
`SHA256(presented) == stored_hash`.

---

## Token Format Requirements (Critical)

The server validates path-component inputs via `Safe_Str` typed primitives.
Tokens that fail validation return `400`, not `403`.

| Input | Validation | Regex | Example |
|-------|-----------|-------|---------|
| `append_token` | `Safe_Str__Vault__Append_Token` | `^[0-9a-f]{16,128}$` | `a3f8...9b2c` (hex, 16–128 chars) |
| `file_id` | `Safe_Str__Vault__Inbox__File_Id` | `^\d{13}_[0-9a-f]{24}\.enc$` | `1717720000000_a3f89b2c4d5e6f708192.enc` |
| `inbox` (in fetch/mark/purge body) | Same as append_token | `^[0-9a-f]{16,128}$` | Must be hex |
| `vault_id` | `VAULT_ID_PATTERN` | Lowercase alphanumeric, 8–24 chars | `mfw2be95xcftxpyl` |
| `enum_key` | Not path-validated | Any string | Can be any format |

**Do NOT use prefixed tokens** like `tok_abc...` or `enum_xyz...` — the `tok_`
and `enum_` prefixes fail the hex-only regex. Use raw hex values.

**Recommended derivation:**
```
append_token = SHA256(recipient_public_key).hex()    // 64 hex chars
enum_key     = SHA256(enum_key_seed).hex()           // any derivation
```

## Provisioning Flow (Vault Web / CLI)

```
Step 1: Create the vault (if it doesn't exist)
  PUT /vault/write/{vault_id}/init  →  establishes write_key_hash

Step 2: Generate inbox credentials (client-side)
  append_token  = sha256(recipient_pubkey).hex()    // per accepted sender
  enum_key      = sha256(enum_key_seed).hex()       // owner secret
  write_key     = (same write_key used in step 1)

Step 3: Configure the inbox
  POST /api/vault/inbox/configure/{vault_id}
    x-sgraph-vault-write-key: <write_key>
    body: {
      append_anchors: [sha256(append_token_1).hex(), ...],
      enum_key_hash:  sha256(enum_key).hex()
    }

Step 4: Distribute append_tokens to senders
  Each sender gets: { vault_id, append_token, recipient_pubkey }
  They use append_token to post, recipient_pubkey to encrypt.
  They NEVER get the enum_key or write_key.
```

## Polling / Drain Loop (Vault Web UI)

The inbox section should poll on the same refresh cadence as the rest of the
vault. The efficient pattern:

```
1. Metadata scan (cheap — zero payload reads):
   POST /list/{vault_id}
     enum_key in header
     body: { include_content: false }
   → entries[] with inbox, file_id, received
   → show count per sender (group by inbox field)

2. When user opens a sender's inbox (or on auto-expand):
   POST /list/{vault_id}
     body: { inbox: "<sender_token>", include_content: true, limit: 50 }
   → entries[] with content (base64 ciphertext)
   → decrypt client-side with private_key

3. After processing:
   POST /mark-processed/{vault_id}
     body: { inbox: "<sender_token>", file_ids: [...] }

4. Periodically (owner action):
   POST /purge/{vault_id}
     body: { folder: "processed", inbox: "<sender_token>" }
   → bulk-deletes all processed files for that sender
```

## Encryption Contract (Client-Side Only)

The server is write-blind. It stores ciphertext and never decrypts.

| Step | Who | What |
|------|-----|------|
| Encrypt | Sender (in browser / CLI) | Seal plaintext with recipient's public key (X25519 + AES-256-GCM) |
| Base64-encode | Sender | `btoa(ciphertext)` → POST as `payload` |
| Store | Server | Stores raw bytes at `inbox/{token}/{timestamp}_{random}.enc` |
| Fetch | Recipient | GET via list or fetch → base64 ciphertext |
| Base64-decode | Recipient | `atob(content)` → raw ciphertext |
| Decrypt | Recipient (in browser / CLI) | Open with own private key (X25519 + AES-256-GCM) |

The server never sees plaintext, never holds private keys, and the append
response is deliberately blind (`{ok: true}` — no file_id, no count).

## CORS Notes

- **Null-origin iframes work.** The server returns `Access-Control-Allow-Origin: *`
  with `allow_credentials: false`. Sandboxed iframes (`sandbox="allow-scripts"`)
  get `null` origin, which is accepted.
- **Custom headers allowed:** `x-sgraph-vault-enum-key`, `x-sgraph-vault-write-key`,
  `x-sgraph-access-token` are all in the CORS `allow_headers` list.
- **CloudFront:** If using a CF distribution with a response headers policy,
  either remove the `CORS-With-Preflight` managed policy (let the Lambda handle
  CORS) or create a custom policy that includes the custom headers. The managed
  policy overrides the Lambda's headers and strips custom ones.

## Gotchas We Hit (So You Don't)

| Gotcha | What Happened | Fix |
|--------|--------------|-----|
| **Vault must pre-exist** | Configure returns 403 if the vault doesn't have a manifest with `write_key_hash`. You must create the vault via the pointer API first. | Call `PUT /vault/write/{vault_id}/...` before configure. |
| **Token prefix breaks validation** | `tok_abc...` fails the hex-only regex → 400 not 403. | Use raw hex: `sha256(pubkey).hex()`. |
| **CF CORS-With-Preflight policy** | CF's managed policy strips custom headers from the Lambda response → preflight fails. | Remove the CF response headers policy; let Lambda handle CORS. |
| **`allow_credentials: true` + null origin** | Starlette reflects `null` as `Access-Control-Allow-Origin: null` → browsers reject it. | Set `allow_credentials: false` (already done on prod). |
| **Metadata-only is free; content is expensive** | `include_content: false` reads zero payloads. `include_content: true` reads every file in the page window. | Always scan metadata-only first; fetch content per-sender on demand. |
| **Batch cap is 100** | fetch/mark-processed/purge reject >100 file_ids → 400. | Page large batches client-side. |

## UI Section Specification

Per the companion dev brief, the inbox is a **main left-hand section** in the
vault UI, checked on every refresh:

| Element | Source | Display |
|---------|--------|---------|
| Message count (total) | `list` with `include_content: false`, count `entries.length` | Badge on the inbox section |
| Per-sender count | Group entries by `inbox` field | Sub-list: one row per accepted pubkey |
| Sender identity | Map `inbox` (append_token) to the pubkey it was derived from | Show pubkey fingerprint or agent name |
| Configuration | The list of accepted pubkeys (from vault's PKI registry) | Settings sub-panel |
| Message content | `list` with `include_content: true` per sender, decrypt client-side | Message list with plaintext after decryption |

## What's Server-Side vs Client-Side

| Concern | Where | Notes |
|---------|-------|-------|
| Store hashes, check gates | Server (SG API) | Done — shipped in v0.29.1 |
| Store/serve ciphertext | Server (SG API) | Done |
| Derive append_token from pubkey | Client (vault web / sgit CLI) | `SHA256(pubkey).hex()` |
| Derive enum_key | Client | Owner's secret, any derivation |
| X25519 keypair generation | Client | Web Crypto API or libsodium |
| Seal (encrypt for recipient) | Client | X25519 ECDH + AES-256-GCM |
| Open (decrypt with own privkey) | Client | X25519 ECDH + AES-256-GCM |
| PKI key registry | Client (vault web / sgit CLI) | Accepted pubkeys stored in vault's PKI layer |

**The server's P0 is complete. Everything remaining is client-side work in the
vault web and sgit CLI repos.**
