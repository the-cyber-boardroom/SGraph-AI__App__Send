## TL;DR

The comms-MVP agent verified that the v0.2.3 vault embed is **two iframes deep**: the outer `?embed=1` loader and the inner null-origin `srcdoc` where the app actually runs. The loader forwards only the handshake (`vault-embed-ready` / `vault-open` / `vault-ready`); any app-level message posted to the loader is silently dropped.

**This does not block the inbox plan.** Our `sg.vault.notify(mountId, eventName)` rides the **ViV SecureChannel** between sibling kernels, not embed `postMessage`. The two are different paths.

**But:** any future "parent vault embeds child vault as iframe + parent wants to nudge child" topology will need either §2a (loader pass-through relay) or §3.3 (SecureChannel reaches through the embed boundary). Filing this brief so the gap is visible and assigned, not forgotten.

---

## 1. What the comms-MVP agent found

The embed structure today:

```
   embedder page                        SG/App loader                  mounted app
   (e.g. harp-make-6182)                (?embed=1 wrapper)              (srcdoc, null-origin)
   ────────────────────                 ─────────────────                ────────────────────
        │                                     │                                │
        │ ◀── vault-embed-ready ──────────────┤                                │
        │                                     │                                │
        │ ─── vault-open {key,mode} ─────────▶│                                │
        │                                     │                                │
        │                                     │ mounts app via srcdoc          │
        │                                     │ in nested iframe ─────────────▶│
        │                                     │                                │
        │                                     │ ◀── __sgVfs* / __sgPrint* ────┤
        │                                     │     __sgUiMsg / sg-app-ready  │
        │                                     │     (kernel↔app bridge —      │
        │                                     │      request/response only)   │
        │                                     │                                │
        │ ◀── vault-ready {...} ──────────────┤                                │
```

**The handshake works** because each step is loader-addressed: the loader knows about `vault-embed-ready`, `vault-open`, `vault-ready`. **App-level messages do not work** because the loader treats unknown shapes as garbage and drops them. There is no general pass-through.

The agent's exact wording:
> Posting `{type:'sg:inbox-notify'}` to the loader is silently dropped. So **caveat #2 ("passthrough") is exactly the thing that fails.** The handshake works only because it is *loader-addressed*; an app poke is not.

## 2. Two paths to fix it (their §2a vs §3.3)

The notification spec offers two paths. Both are valid; they have different costs.

### 2a — Loader pass-through relay (minimal)

The loader gains exactly **two new wrapper message types**, one in each direction, that it relays opaquely:

```
   embedder ──{ sg:'vault-app-msg',  data }──▶ loader
                                       loader ──{ type:'sg-host-msg',   data }──▶ mounted app

   mounted app ──{ type:'sg-app-msg', data }──▶ loader
                                        loader ──{ sg:'vault-app-event', data }──▶ embedder
```

**Loader rules:**
- Validate `e.source` (only accept embedder above and mounted frame below).
- Allowlist only these two wrapper types.
- Cap `data` at ≤4 KB.
- Treat `data` as opaque — never read, never rewrite.
- No secret rides this channel (wake signals only).

**Surface for apps** (so apps don't write raw postMessage):

```js
// embedder (parent app)
mount.post({ kind: 'inbox-notify' });
mount.onEvent((data) => { /* {kind:'inbox-read',count} from child */ });

// mounted app (child app)
sg.host.onMessage((data) => { if (data.kind === 'inbox-notify') checkInbox(); });
sg.host.post({ kind: 'inbox-read', count: newCount });
```

**Cost:** small — ~80 LOC in the loader + ~40 LOC each in `sg-app-stub.js` (`sg.host.*`) and a new `mount.post/onEvent` API on the embedder side.
**Crypto:** none — raw `postMessage`, content-free wake signals.

### 3.3 — SecureChannel reaches through the embed boundary (cleaner, bigger)

The kernel↔kernel SecureChannel already exists for ViV sibling kernels (`secure-channel.js`, authenticated, replay-guarded, P-256 envelope). Extend it so it also spans the embedder↔loader↔app boundary. Then `sg.vault.notify(mountId, 'inbox.new-messages')` works **identically** for both topologies (sibling ViV mount and embed-loader child).

**Cost:** larger — the SecureChannel was designed for same-origin kernel-spawn scenarios. Adapting it for the embed-loader path requires handshake initiation across the loader and key exchange through a relay it doesn't currently mediate. ~300–500 LOC plus a security review (any new path that carries an authenticated channel is a SEC-VIV-class concern).
**Crypto:** reuses existing — but the threat model needs re-examination.

---

## 3. Why this isn't blocking the inbox v1 plan

The inbox plan's cross-vault wake (`sg.vault.notify(mountId, eventName)`) targets **sibling kernels under the same shell** — the ViV mount topology (`sg.vault.mount()` / app-perms Phase 4B). That path uses the existing SecureChannel between sibling kernels and **does not traverse an embed loader**.

```
   inbox v1 (this plan) — works without loader relay
   ─────────────────────────────────────────────────
   sg.vault.mount → KernelParent spawns child kernel as nested iframe of the
                    SAME app-shell. Both kernels live in the same parent
                    document. SecureChannel between them is direct.

   future "parent vault embeds child vault" — NEEDS loader relay
   ────────────────────────────────────────────────────────────────
   embedder is a separate vault UI (different document, different origin
   stack). The embed loader sits between embedder and the mounted app.
   SecureChannel does not reach across this boundary today.
```

So the inbox v1 ships and demos work with sibling ViV kernels. **The embed harness in the comms-MVP agent's screenshot** (`harp-make-6182` ⇄ `down-hunt-9564`, the Embed Handshake Test page) — that *is* the embed-loader path and **will need this fix** to support real-time `sg.vault.notify` instead of 9-second auto-poll.

## 5. Why we recommend §2a over §3.3 for the first ship

| Dimension | §2a (loader relay) | §3.3 (SecureChannel through embed) |
|---|---|---|
| LOC | ~120 | ~300–500 |
| New crypto surface | None (raw postMessage) | Yes (handshake across embed boundary) |
| AppSec review depth | Schema + size cap | Full security review (SEC-VIV-class) |
| Unblocks comms-MVP demo | ✓ same week | ✗ weeks of review |
| Threat model | Loader is content-blind; size-capped opaque relay; harmless wake signals only | Same threat model as ViV SecureChannel, applied across a new boundary — needs proving |
| Future-compat | Can coexist with §3.3 later (different message types) | Cleaner end-state |

**§2a is the unblock; §3.3 is the upgrade.** Ship §2a now; queue §3.3 behind a security review.
