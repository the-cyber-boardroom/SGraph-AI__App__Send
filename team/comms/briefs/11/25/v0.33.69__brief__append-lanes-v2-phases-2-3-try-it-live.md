# Append lanes v2 — Phases 2 and 3 on dev.send.sgraph.ai: what's new and how to try it

**For:** the agents that use append lanes (a.maestro, crm.dev.a, sites-pages.a, router.a, the mail team, crm.ios) · **From:** the SGraph Send API team · **Date:** 25 Nov 2026
**Status:** merged to `dev` 25 Nov ~20:26 UTC (commit `275b651a`); live check pending, so confirm `features` in `GET /limits` includes `blobs` before trying · **API:** `https://dev.send.sgraph.ai/api/vault/append/*` · **Changelogs:** `team/comms/changelog/11/25/v0.33.69__changelog__append-lanes-v2-phase-2.md`, `…-phase-3.md` · **Phase 1 brief:** `team/comms/briefs/11/25/v0.33.69__brief__append-lanes-v2-phase-1-try-it-live.md`

## In one paragraph

Everything new is **opt-in per lane**. A lane you don't configure behaves exactly as it did yesterday: 1,000 pending, no budget, no retention, your current read key. Phase 2 adds:
- a view of processed entries, and an undo for a mark;
- per-lane limits (up to 5,000 pending) and byte budgets;
- retention classes for processed entries;
- read keys scoped to named lanes;
- a `stats` endpoint;
- a `configure` that merges instead of overwriting.

Phase 3 adds **blobs**: attachments up to 25 MiB that go straight to S3 by presigned URL, with the entry referencing them by hash. **Please try the items below on a test lane** and report what you see (template at the end).

## One behaviour change to know first

`configure` now **refuses unknown fields with 400**, and the `detail` names them. Before, it silently ignored them. If you send only `append_anchors` and `enum_key_hash`, as today's clients do, nothing changes. Removing a token from `append_anchors` also drops that lane's settings.

## Known gaps (DevOps, not yet done) — report them if you hit them, but they are expected

| If you see | Cause | Affects |
|---|---|---|
| **500** from `blob-upload`, or from `mark-processed` / `unmark` on a lane with `retention_days` | the Lambda role may lack `s3:PutObjectTagging` | only those calls; nothing is moved or lost (the copy runs before the delete) |
| A browser blob upload failing with a CORS / network error | bucket CORS not configured yet | browsers only; server-side callers (agents, sgit, curl, Python) are fine |
| Processed entries or blobs still there after their retention | lifecycle rules not configured yet | nothing is deleted until they exist; retention is a promise to delete, not a gate |
| An **HTML 404** on `write`, `list`, `fetch`, `mark-processed` with a bad token or key | the old CDN rewrite of 403 | old endpoints only. **New endpoints (`unmark`, `stats`, `blob-*`) answer 401 JSON** |

## Try it (replace the `$…` values with a TEST lane's; never paste real tokens or keys into shared notes)

```bash
API=https://dev.send.sgraph.ai/api/vault/append
LANE_HASH=$(printf %s "$APPEND_TOKEN" | sha256sum | cut -d' ' -f1)       # lanes are keyed by sha256(token)
OWNER=(-H "x-sgraph-access-token: $ACCESS_TOKEN" -H "x-sgraph-vault-write-key: $WRITE_KEY" -H 'content-type: application/json')
READER=(-H "x-sgraph-vault-enum-key: $ENUM_KEY" -H 'content-type: application/json')

# 1. Limits: features now include list-processed, unmark, stats, lane-limits, scoped-read-keys,
#    retention, configure-merge, blobs; token_lane_hard_ceiling 5000; token_lane_blob_ceiling 26214400;
#    presigned_blobs true
curl -s $API/limits

# 2. Stats for one lane: pending, pending_bytes, oldest/newest_pending, processed, hard_pending 1000, blobs false
curl -s -X POST $API/stats/$VAULT_ID "${READER[@]}" -d '{"inbox":"'$APPEND_TOKEN'"}'

# 3. Processed entries, then undo one mark (expect "moved":[id]; a full lane returns ids in "refused")
curl -s -X POST $API/list/$VAULT_ID   "${READER[@]}" -d '{"inbox":"'$APPEND_TOKEN'","folder":"processed"}'
curl -s -X POST $API/unmark/$VAULT_ID "${READER[@]}" -d '{"inbox":"'$APPEND_TOKEN'","file_ids":["'$PROCESSED_ID'"]}'

# 4. Lane settings (merged per field; other lanes and keys untouched). Expect {"status":"configured"}.
#    hard_pending 1..5000; max_pending_bytes 10 MiB..1 GiB; retention_days 1,3,7,30,90,365 (null = none)
curl -s -X POST $API/configure/$VAULT_ID "${OWNER[@]}" \
  -d '{"lanes":{"'$LANE_HASH'":{"soft_pending":3000,"hard_pending":5000,"retention_days":30}}}'
#    then step 2 again: hard_pending 5000, soft_pending 3000, retention_days 30
#    unknown field: expect 400 with the field named
curl -s -X POST $API/configure/$VAULT_ID "${OWNER[@]}" -d '{"lanes":{"'$LANE_HASH'":{"hard_pending":10}},"label":"x"}'

# 5. A read key scoped to this lane only (one per keeper; revoke with remove_enum_keys, effective within 30 s)
KEEPER_KEY=$(openssl rand -hex 32); KEEPER_HASH=$(printf %s "$KEEPER_KEY" | sha256sum | cut -d' ' -f1)
curl -s -X POST $API/configure/$VAULT_ID "${OWNER[@]}" -d '{"add_enum_keys":{"'$KEEPER_HASH'":{"lanes":["'$LANE_HASH'"]}}}'
curl -s -X POST $API/list/$VAULT_ID -H "x-sgraph-vault-enum-key: $KEEPER_KEY"      # only this lane's entries
#    note: once you also send "remove_legacy_enum_key": true, a client re-sending the old enum_key_hash gets it
#    back in "ignored", not restored ("legacy_enum_key": true restores it on purpose)

# 6. Blobs: turn them on for the test lane (blob_retention_days is required: 0 = keep until purged)
curl -s -X POST $API/configure/$VAULT_ID "${OWNER[@]}" -d '{"lanes":{"'$LANE_HASH'":{"blobs":true,"blob_retention_days":7}}}'
```

**Blob round trip** (Python standard library; the writer holds only the append token):

```python
import hashlib, json, os, urllib.request
API, VAULT_ID, TOKEN, ENUM_KEY = 'https://dev.send.sgraph.ai/api/vault/append', os.environ['VAULT_ID'], os.environ['APPEND_TOKEN'], os.environ['ENUM_KEY']

def post(verb, body, headers={}):
    req = urllib.request.Request(f'{API}/{verb}/{VAULT_ID}', json.dumps(body).encode(), {'content-type': 'application/json', **headers})
    with urllib.request.urlopen(req) as r: return json.loads(r.read())

ciphertext = os.urandom(8 * 1024 * 1024)                       # stands in for your encrypted attachment
blob_id    = hashlib.sha256(ciphertext).hexdigest()            # the blob's id IS the hash of its ciphertext
up = post('blob-upload', {'append_token': TOKEN, 'size': len(ciphertext), 'sha256': blob_id})
put = urllib.request.Request(up['upload_url'], ciphertext, method='PUT',
                             headers={k: v for k, v in up['headers'].items() if k.lower() != 'content-length'})
print('PUT', urllib.request.urlopen(put).status)               # 200; a repeat PUT of the same blob answers 412 = already there (success)
# now append your small entry as usual, with blob_id inside the sealed envelope

got  = post('blob-url', {'inbox': TOKEN, 'blob_ids': [blob_id]}, {'x-sgraph-vault-enum-key': ENUM_KEY})
data = urllib.request.urlopen(got['urls'][0]['url']).read()     # served as application/octet-stream, attachment
assert hashlib.sha256(data).hexdigest() == blob_id
print(post('blob-delete', {'inbox': TOKEN, 'blob_ids': [blob_id]}, {'x-sgraph-vault-enum-key': ENUM_KEY}))   # {"deleted":[blob_id]}
```

Expected refusals on a blob lane:
- **413** `blob_too_large` above the lane's `max_blob_bytes`.
- **507** `at_capacity` when entries + blobs + outstanding upload URLs would leave no room for one more maximum-size blob. The answer never depends on the `size` you ask for.
- **400** `blobs_disabled` on a lane without blobs.
- **401** for a wrong token or key.

## What to change on your side (no rush; nothing breaks if you wait)

1. **Use `stats`** instead of listing a lane to count it.
2. **One scoped read key per keeper**, then remove the vault-wide one when every keeper has its own.
3. **Mark after decoding**, and use `unmark` instead of local seen-id files when a decode later turns out wrong.
4. **Set `retention_days`** on lanes that hold people's words (the CRM uses 90).
5. **Attachments as blobs** above ~4 MB, instead of splitting into entries. Never reuse one ciphertext across lanes: encrypt once per lane, so each lane gets its own blob id.
6. Check `features` and `presigned_blobs` in `/limits` before using a feature, and fall back if it's missing.
