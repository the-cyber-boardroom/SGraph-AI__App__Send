# Append lanes v2 — Phase 1 is live on dev.send.sgraph.ai: what changed and how to try it

**For:** the agents that use append lanes (a.maestro, crm.dev.a, sites-pages.a, router.a, the mail team, crm.ios) · **From:** the SGraph Send API team · **Date:** 25 Nov 2026
**Status:** deployed 25 Nov ~03:30 UTC and checked live (`GET /limits` returns the values below with `Cache-Control: no-store`; non-object and `NaN` bodies return 400 JSON) · **API:** `https://dev.send.sgraph.ai/api/vault/append/*` (the same API the vault web UI and sgit use) · **Plan:** `team/roles/dev/reviews/11/25/v0.33.69__dev-plan__append-lanes-v2-implementation.md` · **Changelog:** `team/comms/changelog/11/25/v0.33.69__changelog__append-lanes-v2-phase-1.md`

## In one paragraph

Phase 1 is server-only and backwards compatible: every request that worked before works the same way. It fixes the three defects you reported and two the security review found. It adds `GET /limits` and keeps every `fetch` under Lambda's response limit. Nothing in your lane layout, tokens or keys changes. **Please try the items below on a test lane and report what you see** (template at the end).

## What changed for you

| What | Before | Now |
|---|---|---|
| `configure` on a vault with no commit yet | 403 "Write key mismatch", shown by the CDN as an HTML 404 | **200 `configured`**: the call claims the vault id, as the first vault write would. A deleted vault still refuses |
| `list` with no body | 500 | **200**: an empty body means `{}` |
| A malformed body (not JSON, not an object, `NaN`, `Infinity`) or a badly typed field (`after_file_id: 123`, `limit: true`, `file_ids: 5` …) | often 500 | **400 with a JSON reason**, on all six append routes |
| A `fetch` of several large entries | could exceed Lambda's 6 MB response and fail | stops at **5.5 MB encoded**; the ids it skipped come back in a new **`deferred`** list. **Fetch those in your next call.** The first entry is always returned |
| Revoking a token or rotating the read key with `configure` | took effect only on the Lambda instance that served the call; others kept accepting the old value until recycled | takes effect everywhere within **30 s** (`config_ttl_seconds` in `/limits`) |
| Limits | undocumented; the advertised 5 MB was not reachable | **`GET /api/vault/append/limits`**: public, no input, never cached |
| Payload too large (above 5 MiB) | 413 "Payload too large" | 413 with `{"detail": {"error":"payload_too_large","limit":…,"received":…}}` |
| `inbox` in `list` results | unclear | documented: it is the lane's **raw append token** (its folder name), not a hash. Use **random** tokens |

Still true: an auth failure (403) is still shown by the CDN as an **HTML 404** (open DevOps item). An HTML body on a 404 means "gate failed", not "route missing".

## Try it (replace the `$…` values with your test lane's; never paste real tokens or keys into shared notes)

```bash
API=https://dev.send.sgraph.ai/api/vault/append

# 1. Limits, server time, features: expect max_inline_payload 4400000, max_pending 1000,
#    config_ttl_seconds 30, now_ms close to your clock, features incl. "fetch-deferred"
curl -s $API/limits

# 2. configure a NEW vault id before any commit: expect 200 {"status":"configured"} (was 403 / HTML 404)
curl -s -X POST $API/configure/$NEW_VAULT_ID \
  -H "x-sgraph-access-token: $ACCESS_TOKEN" -H "x-sgraph-vault-write-key: $WRITE_KEY" \
  -H 'content-type: application/json' \
  -d '{"append_anchors":["'$ANCHOR_HASH'"],"enum_key_hash":"'$ENUM_KEY_HASH'"}'

# 3. list with no body (real enum key): expect 200 (was 500)
curl -s -X POST $API/list/$VAULT_ID -H "x-sgraph-vault-enum-key: $ENUM_KEY"

# 4. malformed input: expect 400 with a JSON detail, never 500. Use your lane's REAL enum key: the read-key check
#    runs before field checks, so with a wrong key you get the gate failure (HTML 404) instead — by design.
curl -s -X POST $API/list/$VAULT_ID -H "x-sgraph-vault-enum-key: $ENUM_KEY" -H 'content-type: application/json' -d '[]'
curl -s -X POST $API/list/$VAULT_ID -H "x-sgraph-vault-enum-key: $ENUM_KEY" -H 'content-type: application/json' -d '{"after_file_id":123}'

# 5. fetch: the response now always has "deferred" (usually []). Write 3 entries of ~2 MB
#    to a test lane, fetch all 3 ids in one call: expect 2 in "files" and 1 in "deferred".
curl -s -X POST $API/fetch/$VAULT_ID -H "x-sgraph-vault-enum-key: $ENUM_KEY" -H 'content-type: application/json' \
  -d '{"inbox":"'$APPEND_TOKEN'","file_ids":["'$ID1'","'$ID2'","'$ID3'"]}'

# 6. revocation: remove a test token with configure (append_anchors without it), then retry a
#    write with that token every 5 s: expect it refused (HTML 404 at the edge) within 30 s
```

## What to change on your side (no rush; nothing breaks if you wait)

1. **Handle `deferred`** in your drain: loop until `deferred` is empty.
2. **Read `/limits`** instead of hard-coding sizes. Keep inline payloads at or under `max_inline_payload` (4.4 MB on this API; one base64 layer, not two).
3. **Mark entries only after they decode**; leave failures pending. A dedicated "processed" view and an undo arrive in Phase 2.
4. **Random append tokens.** A token derived from a public key would be an identifier stored on the server.

## Coming next (Phase 2, in progress)

- List `processed/` entries, and an `unmark` (undo).
- Retention classes (1, 3, 7, 30, 90, 365 days, or none).
- Soft and hard per-lane limits within server ceilings.

- A `stats` endpoint.

Phases 3 (blobs for attachments) and 4 (signed lanes with grants) follow. All of it is opt-in per lane.
