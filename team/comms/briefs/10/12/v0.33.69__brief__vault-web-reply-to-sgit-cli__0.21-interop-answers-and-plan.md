## 2. Answers

| Your point | Answer |
|---|---|
| **Q1** 44-char `file_id` on write / read / batch / list / presigned | Yes on all. The route is `{file_id:path}` and `Service__Vault__Pointer` never looks at id length. Your live run on `th8bfzj1` matches what the code says. No change needed or planned. |
| **`write-if-match` conflict shape** | Stable: HTTP 200, `results[i].status == "conflict"`, `results[i].current` (base64 of stored bytes). One more fact you should have: **the batch stops at the first conflict** (`Service__Vault__Pointer.batch`, "Stop on conflict"), so ops after a conflicting CAS op in the same batch are not executed. Put a CAS op last, or alone. We handle the same shape in `SGVaultRefManager.writeRefIfMatch` today. |
| **`list` continuation token** | Does not exist: `list_files` returns the whole prefix in one response. When we add it the response field will be `next_token` and the request parameter `token`. Not scheduled; we will tell you before it ships. |
| **`commit_v2` ↔ `commit_v1`** | We will write **`commit_v1`** for signed commits (same shape; our reader already accepts both). You can keep reading `commit_v2` for the unsigned history we have written so far. |
| **`branch_id` for web commits** | `branch-clone-<16 hex>` per device, as you proposed. Our current `branch_id: null` stays for unsigned commits. We noted that your `load_commit` rewrites a non-matching `branch_id` to `''` before re-serialising, so a signed web commit with a malformed id would read as `bad`; our writer will refuse to sign such a commit rather than produce one. |
| **Tree plaintext (your §2 question: JCS or Python bytes?)** | Our preference: **match your bytes now** (Python default separators, your 7-field entry order, `content_type_enc` + `large` populated), and propose JCS-for-trees as a format-3 item if the native-PKI mode goes ahead, since that bump rewrites every id anyway. Please confirm. |
| **`min_client` and the web** | The field carries CLI versions, so the web cannot compare it against its own version (`v0.2.3` vs `0.21.0` is meaningless). The web will refuse by name on a `format` it does not know and on a **write** it cannot make policy-compliant (`signatures-required` before we sign); reads are never refused on `min_client`. If you ever need to lock old web releases out, a `min-web-<version>` feature string would do it; we do not think it is needed. |
| **Index overwrite** | Acknowledged as our bug, not yours. The fix (read → merge by `branch_id` → `write-if-match` → retry; `tags`, gate and unknown fields carried back unchanged) is item 2 of our plan and ships with the format gate. |

## 3. What we will build, in order

1. Format gate read + format-aware `computeObjectId` (32-hex on format 2).
2. Branch index as a shared document (above); our clone entry registered with its `public_key_id`.
3. Per-device P-256 signing key (non-extractable, IndexedDB), public key at `bare/keys/key-rnd-imm-<id>` as `{"type":"public","pem":…}` under the read key, ten-member `commit_v1` signed over JCS, verification with your status vocabulary (verified / bad / unsigned / no-key) in the SGit view, and refusal to publish unsigned under `signatures-required`.
4. Ref monotonicity (last accepted named head per device) and compare-and-swap publish in every shell; a rewind banner with your wording.
5. Deterministic trees, after your answer on the plaintext rule.

Sequencing on your side that we rely on: nothing. Everything above is additive and fails open against today's web until it ships. We will send a second note with a vault id on dev once items 1–3 are on `dev.vault.sgraph.ai`, so you can run `sgit check verify` against web-signed commits.

## 4. One request

Your `Vault__Index_Sync.merge` keeps the server's gate unless the server copy has **no** gate fields at all. Once our index write carries the gate back unchanged (item 2), that fallback will stop firing for web pushes. Until then, a web push still erases it and your next pull restores it; please keep that repair path until you hear from us that item 2 is live.
