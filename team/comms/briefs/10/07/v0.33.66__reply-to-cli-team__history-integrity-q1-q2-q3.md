## Q1: 44-character `file_id` under `bare/data/`

Ids used: `obj-cas-imm-1abfd21f1430` and `obj-cas-imm-1abfd21f14308c611fe591dc4d6de285`.

| Surface | 44-char id | Notes |
|---|---|---|
| `PUT /api/vault/write/{vault_id}/{file_id}` | **yes** | `{file_id:path}`, plain `str`, no length or pattern check |
| `DELETE /api/vault/delete/{vault_id}/{file_id}` | **yes** | |
| `GET /api/vault/read/{vault_id}/{file_id}` (and `read-base64`) | **yes** | the immutable `Cache-Control` still applies; it keys on the `-imm-` substring |
| `POST /api/vault/batch/{vault_id}`: `read`, `write`, `write-if-match`, `delete` | **yes** | all four return `ok` |
| `GET /api/vault/list/{vault_id}?prefix=bare/data/` | **yes, with a size limit** | both ids come back byte-exact. See the limit below |
| presigned `initiate` / `complete` / `cancel` | **yes** | `file_id: str`, stored as given |
| presigned `read-url` | **yes** (code-read) | the route matches; the S3 call runs only in S3 mode, so it was not executed. The key comes from the same builder |
| S3 key length / charset | **yes** | 121 bytes for a 44-char id (S3 limit: 1024); hex and `-` only |
| cache / CDN keyed on id | **no issue** | no rule keys on id length; the immutable header keys on `-imm-`, which both formats carry. (Unrelated, for your error handling: the CDN in front of the API turns a `403` into the static 404 page; we hit this in September.) |

**The limit:** `list` returns every key in one JSON body, and Lambda caps a response at 6 MB.
That is about **165k objects at format 1 and about 108k at format 2** (38 vs 58 bytes per entry;
your +400 KB at 19,780 objects matches). Today's largest vault has about 5× headroom. We will add
a continuation token to `list` before any vault nears 80k objects. That is independent of
format 2. Your clone sweep should then follow the token.

**Host:** both clients write to `https://dev.send.sgraph.ai/api/vault/*` (your
`DEFAULT_BASE_URL` and every fallback in the web UI). `vault.sgraph.ai` serves the web UI only.
Any server work for this plan lands on that Lambda.

## Q2: can the web UI read and write both id lengths?

**Read: yes, today.** Ids are opaque strings on the read path (`load`, `batchLoad`, tree walks).
There is no regex, no fixed-width parsing, and no column width tied to id length.

**Write: no, not yet.** There is one place where ids are computed, and it is shared code you can
give a vector to:

```js
// sg-vault-object-store.js — SGVaultObjectStore.computeObjectId(ciphertext)
return 'obj-cas-imm-' + hex.slice(0, 12)
```

On `b'sgit test vector 0001'` it returns `obj-cas-imm-1abfd21f1430`, which matches your
format-1 vector. We will make it format-aware and add both of your vectors as JS fixtures. The
kernel bundle (the copy that child kernels run) is regenerated from the same source.

**Where id length is assumed:**

| Location | What | Affected? |
|---|---|---|
| `sg-vault-object-store.js` `computeObjectId` | `hex.slice(0, 12)` | **yes**, the one change |
| `kernel-shell-bundle.js` | generated copy of the above | regenerated |
| `sg-vault.js` open | reads the branch index for the named ref | **yes**: it must read and honour the gate |
| `sg-vault-commit.js` `computeContentHash` | `sha256(plaintext)[:12]`, the tree-entry dedupe hash, **not an object id** | no. Please confirm you are not widening `content_hash` either |
| `vault-loader-format.js` `RE_HEX_ID_PART` | the 12-hex **vault id** in a pasted key, not an object id | no |
| `sg-vault-ref-manager.js` | `ref-pid-…`, `branch-(named\|clone)-…` | no; refs and branch ids are unchanged per your brief |

**The format gate: yes.** On open we will read `format` / `min_client` / `features` and refuse
by name. We will match your refusal wording once you publish it.

**The side effect you need to know about before 0.19:** the web UI's `writeBranchIndex`
**replaces** the branch index with one entry,
`{ schema: 'branch_index_v1', branches: [{ branch_id, branch_type: 'named', head_ref_id, name: 'current' }] }`,
on create, on **every push**, and in child kernels (declared mounts). It does not read or merge
first. Against your `Schema__Branch_Meta` this means:

- the next web push **erases `format` / `min_client` / `features`**, so clones made afterwards
  see format 1 and are never refused;
- it **erases every other branch entry and its `public_key_id`**, so clones made afterwards
  cannot map commits to signing keys (under `warn` everything is unverifiable; under `required`
  the vault is unusable);
- CLI and web index writes race (last writer wins).

Existing clones are not affected today, because your `pull` reads the local index. This is a
latent bug now, and it becomes active the day the gate ships. **Our fix:** read-modify-write that
keeps unknown top-level fields and every other branch entry, written with `write-if-match` and
retried on conflict. A single-entry write is used only on create. **We will ship it before your
0.19.** Please also move your own index uploads to `write-if-match`, so neither side can clobber
the other.

**Size:** S for ids, gate, fixtures and the bundle (about a day). S–M for the index fix.

## Q3: can the web UI sign its commits, and under which key?

**Not today. Feasible. Size L.** What already lines up: WebCrypto ECDSA P-256 sign/verify is in
the web codebase, and your raw `r‖s` encoding (`PKI__Crypto`, "for Web Crypto interop") is what
WebCrypto produces. The signature format is not a problem. Three things block it:

1. **The signing input is not canonical (your side).** `Vault__Commit` signs
   `json.dumps(commit.json()).encode()`. Those bytes depend on Python's default separators
   (`", "`, `": "`), Type_Safe field order and defaults (`branch_id: ''`, `author_key_id: null`,
   `attestations: []`). `JSON.stringify` cannot reproduce them reliably. **Ask:** please specify
   the signing input exactly, either RFC 8785 (JCS) or a fixed field list with compact
   separators, and ship test vectors (commit JSON → signing bytes → signature with a fixed
   test key), as you did for ids. This has to be settled before any second implementation
   exists, or it is a migration later.
2. **No per-writer identity in the browser (our side).** Every browser session commits on one
   shared clone branch per vault (`web-ui`; child kernels use `viv:<parent id>`). Your model is
   one key per branch, so we need per-device clone branches, a non-extractable P-256 key in
   IndexedDB on the top-level origin, and the public key written to `bare/keys/key-rnd-imm-<id>`
   and **registered in the index**. That last step depends on the Q2 index fix.
3. **Schema alignment (both sides).** The web writes `schema: 'commit_v2'`, `branch_id: null`,
   and no `author_key_id`. You call the same shape `commit_v1`, and your `Safe_Str__Branch_Id`
   requires `branch-(named|clone)-<hex>`. Parsing works today because you fill in defaults. We
   should agree on one schema name and on the `branch_id` a web commit carries, before
   `required`.

**Server attestation ("unsigned but made under an authenticated session"): not recommended.**
The server would need a signing key, a secret on a host designed to hold none. Access tokens are
also often shared, so the attestation would not identify a person. Per-device web keys are the
better route.

**So:** `warn` by default is right. `required` waits for (1) a canonical signing input from you
and (2) per-device keys on our side.

## Anything else that assumes 12-hex ids or unsigned commits

**Web and server (we will fix):**

- **Random-IV trees.** Your brief says trees use `IV = HMAC-SHA256(key, plaintext)[:12]` "in both
  clients". The web UI encrypts trees with a **random** IV (`SGSendCrypto.encrypt`). Ids are
  still correct content addresses. But identical folders get different tree ids in the two
  clients, your `tree-iv-determinism` migration reports "needs migration" forever after any web
  commit, and applying it rewrites history (it reads as a rollback, and the signatures no longer
  match). We will move the web UI to your deterministic IV (`Vault__Crypto.encrypt_deterministic`).
  **Please send a tree test vector** (key, plaintext, IV, ciphertext).
- **Unconditional web push.** The web shells call `push()`, which re-points the named ref with
  no compare and can drop another writer's commits. `pushIfMatch()` (compare-and-swap) exists,
  but only child kernels use it. Your 0.20 monotonicity check would report these lost updates as
  rollbacks, and it would be right. We will move the shells to `pushIfMatch()` with a reconcile
  step **before your 0.20**.
- **Old web-UI releases stay reachable** (release folders are kept for rollback). They do not
  know about the gate, and the server cannot block them because the gate is encrypted. We will
  retire them when the gate-aware build ships.
- **Our own backlog:** a planned server path-validation fix will use a safe-charset rule, not an
  object-id regex, so it cannot reject 44-char ids.

**Found on your side while reading both codebases:**

- **The gate will not reach existing clones.** `pull` never re-reads the remote branch index
  (`Step__Pull__Load_Branch_Info` uses the local copy). Raising a vault to format 2 affects only
  new clones. Existing clones keep writing 12-hex ids and are never refused. If the gate should
  apply to them, `pull` has to refresh it.
- **Pre-gate CLIs crash instead of refusing.** `Safe_Str__Object_Id` is
  `^obj-cas-imm-[0-9a-f]{12}$`, max 24. Any CLI up to 0.18 that reads a 32-hex id raises a
  validation error instead of "needs sgit ≥ X". Worth a release note.
- **Migration × integrity.** Once signatures and monotonicity ship, `sgit migrate apply`
  rewrites signed history. It should either refuse on signed vaults, or re-sign and record
  intent the way `push --force` will.
- **Naming.** The web UI already calls a *vault-key* shape "Format 2" (`passphrase:vault-id`).
  We will label yours "id format v2" in the UI. Use whatever name you like on your side.
