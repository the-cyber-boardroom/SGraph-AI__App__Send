# Brief: sgit.ai Documentation Gap Analysis — the API Reference Is Missing and PKI Is Contradicted

**version** v0.33.59 · **date** 16 August 2026
**from** Architect / DevOps (Explorer)
**to** Journalist, Ambassador, whoever owns sgit.ai content
**trigger** An agent was asked how to send messages between vaults and could not find the answer on sgit.ai.
**method** Site audited against the code (`Routes__Vault__Pointer`, `Routes__Vault__Append`, `user__config.py`) at v0.33.54.

---

## 1. Why The Agent Failed — the discoverability chain is broken in three places

The capability **exists and is documented** — but no path leads from the question to the answer.

| Where the answer lives | What it says | Why the agent missed it |
|---|---|---|
| `/vault/sg-bridge.md` | `sg.append` — `configure`, `write`, `list`, `fetch`, `markProcessed`, `purge` | Framed as *"append-only transport… outside the commit tree"*. Never uses the words **message**, **send**, **recipient**, or **inbox**. Nobody searching for messaging finds it. |
| `/skills/use_sgit-and-vaults__SKILL.md` | `sgit pki keygen / sign / verify / encrypt / decrypt` | Documented as file signing/encryption. **No link to append**, so the two halves of the mechanism never meet. |
| Nowhere | The actual composition: `append_token = H(recipient_public_key)`, seal to the recipient's X25519 key, they poll and open | **This page does not exist.** It is the missing keystone. |

**The failure is not missing capability — it is missing composition.** The site documents the
transport and the crypto separately and never says they combine into vault-to-vault messaging.

## 2. The Correction That Matters Most — `/security/index.md` actively denies PKI

The security page describes sgit as symmetric-only and, per audit, contains
*"no discussion of asymmetric cryptography, key pairs, digital signatures, or per-recipient
encryption schemes"* — concluding users *"hold a single master key rather than using public-key
infrastructure."*

**That is wrong.** The CLI ships `sgit pki keygen/export/import/sign/verify/encrypt/decrypt`,
vaults store public PKI keys at `bare/keys/key-rnd-imm-*`, and the append model is built on
X25519 sealing to a recipient's public key.

This is worse than an omission: **an agent that reads the security page concludes PKI does not
exist and stops looking.** That is very likely what happened here. Fix this page first.

Suggested framing — both are true and the page should say so:
> The **vault key** is symmetric and is the root of the storage hierarchy. **PKI is layered on
> top** for identity and recipient-addressed operations: signing content, encrypting to a
> specific recipient, and addressing append lanes by `H(public key)`.

## 3. The Structural Gap — there is no HTTP API reference anywhere on the site

Confirmed across `/docs/index.md` (CLI-only), `/vault/`, and `/deploy/`. No endpoint list, no
auth headers, no status codes, no limits.

This matters immediately: **sgit.ai is becoming the home of `sgit-api`** (extraction in
progress). A protocol server whose site has no protocol reference cannot support the claim that
the API is the whole surface — which is exactly the claim the thin-interface argument rests on.

### 3.1 Raw material — the actual surface (code-verified, v0.33.54)

**Vault Pointer** — `/api/vault/*` (13 registered paths):

| Method | Path | Auth |
|---|---|---|
| PUT | `/api/vault/write/{vault_id}/{file_id:path}` | access token + `x-sgraph-vault-write-key` |
| GET | `/api/vault/read/{vault_id}/{file_id:path}` | none (public read) |
| GET | `/api/vault/read-base64/{vault_id}/{file_id:path}` | none — MCP-safe, ~3.75 MB cap |
| DELETE | `/api/vault/delete/{vault_id}/{file_id:path}` | access token + write_key |
| POST | `/api/vault/batch/{vault_id}` | mixed ops, **max 100 per request** |
| POST | `/api/vault/list/{vault_id}` | — |
| GET | `/api/vault/health/{vault_id}` | — |
| GET | `/api/vault/zip/{vault_id}` | — (**note:** reality doc lists this as PROPOSED — reconcile) |
| DELETE | `/api/vault/destroy/{vault_id}` | write_key; `purge:true` skips the tombstone |
| GET | `/api/vault/public-info/{vault_id}` | — |

Plus vault presigned (`initiate` / `complete` / `cancel` / `read-url`) for large blobs.

**Vault Append** — `/api/vault/append/*`, all POST — **this is vault-to-vault messaging**:

| Path | Gate | Notes |
|---|---|---|
| `/configure/{vault_id}` | `x-sgraph-vault-write-key` | registers `append_anchors` (hashes of accepted senders) + `enum_key_hash` |
| `/write/{vault_id}` | `append_token` in body | **account-less** — no access token; blind response `{ok:true}` |
| `/list/{vault_id}` | `x-sgraph-vault-enum-key` | paginated (`after_file_id`), optional inline content |
| `/fetch/{vault_id}` | enum_key | batch, max 100 file_ids |
| `/mark-processed/{vault_id}` | enum_key | pending → processed, idempotent |
| `/purge/{vault_id}` | write_key | `folder: "pending" \| "processed"` |

**Four-tier capability model** (the thing worth a diagram): `append_token` → write only ·
`enum_key` → list/fetch/mark · `write_key` → configure/purge · `private_key` → decrypt,
**client-side only, never sent to the server**. Server stores SHA-256 hashes only.

**Limits:** 5 MB per payload (413) · 1000 files per token (507) · 100 file_ids per batch (400)
· 3 MB inline content ceiling (413) · list page max 200.

**Auth headers** (code-verified): `x-sgraph-access-token`, `x-sgraph-vault-write-key`,
`x-sgraph-vault-enum-key`, `x-vault-public`, `x-vault-read-key`,
`x-sgraph-transfer-delete-auth`.

**Caching contract:** `-imm-` objects → `Cache-Control: public, max-age=31536000, immutable`;
refs/indexes → `no-store`. Consumers building clients need this.

## 4. Proposed Additions

| Priority | Page | Content |
|---|---|---|
| **P0** | `/security/index.md` — **correct** | Add the PKI layer per §2. Stop implying symmetric-only. |
| **P0** | `/docs/vault-messaging.md` — **new** | The missing keystone: sender derives `append_token = H(recipient_pubkey)`, seals with X25519, POSTs to `/append/write`; recipient polls `/append/list`, fetches, opens locally, marks processed. End-to-end worked example, both CLI and `sg.append`. Link it from `/docs/index.md`, `/vault/sg-bridge.md`, and the security page. |
| **P0** | `/api/index.md` — **new section** | The HTTP reference: §3.1 as real pages — vault pointer, append, presigned, auth headers, status codes, limits, caching. This is the `sgit-api` home. |
| **P1** | `/docs/pki.md` — **new** | Keypair lifecycle, `sgit pki *`, where public keys live (`bare/keys/`), what Mode 1 covers and what is still proposed. |
| **P1** | `/vault/sg-bridge.md` — **reframe** | Retitle `sg.append` as *"append lanes — the vault-to-vault message transport"* and cross-link the new messaging page. One sentence fixes most of the discoverability failure. |
| **P1** | `/skills/*` — **update** | Add append + messaging to the agent-facing skill. Agents read these first; today they list PKI with no transport and no messaging at all. |
| **P2** | `/docs/limitations.md` | Note what PKI does *not* yet do (Modes 2–4 proposed), so agents do not over-claim. |
| **P2** | Everywhere | Search for stale **"inbox"** naming. The API renamed inbox→append in v0.32.7 and `purge` now takes `folder:"pending"`, not `"inbox"`. |

## 5. Two Things To Verify Before Publishing

1. **`/api/vault/zip/{vault_id}` is registered in code but marked PROPOSED in the reality doc.**
   Confirm whether it is implemented before documenting it either way.
2. **`Routes__Join` (`/join/*`) is not registered in the User Lambda app** (found during the
   extraction work) while the reality doc lists 3 live endpoints. Do not document `/join/*` on
   the site until that is resolved.

## 6. The Test For Whether This Worked

Same standard the corpus uses elsewhere — reproducible rather than asserted:

> Give a fresh agent only `sgit.ai/llms.txt` and ask: *"How do I send an encrypted message from
> vault A to vault B?"* It should reach a working answer — including that the recipient's public
> key hash is the lane address — without reading source code or asking a human.

That test fails today. It is the acceptance criterion for the P0 items.
