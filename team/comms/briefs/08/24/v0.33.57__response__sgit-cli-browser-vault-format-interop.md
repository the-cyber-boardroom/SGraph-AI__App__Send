## The bug we did have: a stale key-prefix list

sgit's self-identifying prefixes were renamed on **08/17** (sgit `Vault__Crypto`, "design
contract 08/14, naming revised 08/17"). We had implemented only the 08/14 generation:

| Prefix | Meaning | Was handled here? |
|---|---|---|
| `sgit_private_vault_` | vault key (read + write) | ❌ → ✅ |
| `sgit_private_read_` | read key, keep secret | ❌ → ✅ |
| `sgit_public_read_` | read key, deliberately published | ❌ → ✅ |
| `sgit_vk1_` / `sgit_rk1_` | legacy (v0.15.5), input-only | ✅ (unchanged) |

The prefix must be stripped **whole**: `sgit_private_vault_` and `sgit_private_read_` share the
`sgit_private_` stem, and stripping only the stem leaves a residual passphrase that derives a
*different, non-existent vault* — verified (`vault_5or4…` → read_key `8c99ae4d…` vs the correct
`ad173882…`). Our fix mirrors sgit's `strip_key_prefix` list-and-order exactly, and we also
added `SGVaultCrypto.classifyKey` (sgit's `classify_key`) so a read-only surface can refuse
write capability **by declaration rather than by shape**.

## On the brief's asks 2 and 3 — we agree, and here is our half

- **Ask 2 (format-version marker + named error).** Strongly seconded. Note that in *this*
  incident a version marker would **not** have helped: nothing was version-divergent, the
  passphrase was simply wrong-by-one-prefix, and any client would have reported the same
  "HEAD ref missing". The more valuable primitive is the one sgit already shipped and we have
  now adopted — a *self-identifying credential* — plus an error that distinguishes
  "credential did not derive a vault that exists" from "vault exists, format unreadable".
- **Ask 3 (interop test in CI).** Yes please, and we have now built our half: the round trip
  above runs against this repo's own in-process server with no credentials and no network.
  We would take your KV store + Playwright scripts happily. In the meantime our
  known-answer test pins our derivation against literal `sgit vault derive-keys` output, so
  the next prefix or derivation change fails in our CI rather than in a user's browser.
- **Ask 4 (document what `deriveWriteKeys` accepts).** For our stack the answer is now
  explicit and enumerated in code: `SGVaultCrypto.KEY_PREFIXES`.

## What consumers should do

If you are opening vaults with **this repo's** vault UI or its modules
(`dev.vault.sgraph.ai`): current CLI keys work as printed once this lands — no manual prefix
stripping, no key rewriting. Both the vault UI (`/en-gb/vault/`) and the App UI
(`/en-gb/app/`) accept every current and legacy prefix on every key-input path.

If you are pinning the **npm** `vault-client` / `vault-write` / `vault-session` modules, this
response does not fix your case; deltas 1–3 need the publisher of those packages.
