## 1 · Gap 1's premise is now VERIFIED (was the brief's one unproven claim)

The 07/24 code review (F6) recorded that CLI-side support for
`sgit clone <64-hex>:<vault-id>` was unconfirmed. The CLI team has now verified it
**empirically** — real `sgit` binary against a real in-process SG/Send server:

- `sgit clone {64-hex}:{vault_id}` → read-only clone, correct content. The 64-hex head is
  **explicit routing** in `CLI__Vault.cmd_clone` (detected before passphrase parsing), not
  accidental parsing — the "treated as an ordinary passphrase" failure mode cannot occur.
- `sgit clone {vault_id} --read-key {hex}` and `sgit clone sgit_rk1_{hex}:{vault_id}` also pass.
- `sgit commit` on the read-only clone is refused.
- The shorthand shipped 2026-06-04 (CLI commit `2b9f4f5`, first release v0.14.26); F6 flagged a
  verification gap, not an absence.

**Consequence for the brief's §7 Decisions 1–2:** take them exactly as recommended. Bare
`{64-hex}:{vault_id}` as web format 6 creates **CLI parity**, and the 64-hex-passphrase edge
case is accepted with the *same semantics the CLI already chose* (a 64-hex head always routes
read-only).

## 2 · Correction: drop the invented `rk:` prefix — adopt `sgit_rk1_`

The brief's §3.2 proposed an `rk:` prefix for published links. The CLI shipped canonical
prefixes this week (SGit-AI__CLI design contract
`team/explorer/architect/contracts/08/14/v0__design__key-prefixes-and-leak-detection.md`):

| Credential | Canonical prefixed form |
|---|---|
| Vault key | `sgit_vk1_{passphrase}:{vault_id}` |
| Read key | `sgit_rk1_{64-hex}` — and `sgit_rk1_{64-hex}:{vault_id}` clones directly |

The value after the prefix is byte-identical to the legacy key; nothing cryptographic changed.
Web requirements that follow:

1. Format 6 detection accepts **bare** `{64-hex}:{vault_id}` **and** `sgit_rk1_{64-hex}:{vault_id}`.
2. Every web key-**input** path strips a leading `sgit_vk1_` / `sgit_rk1_` before format
   detection (users will paste prefixed keys from new CLI output). Two `startsWith` checks.
3. Ordering note carries over unchanged: the prefixed form also contains a colon, so without
   an explicit check before formats 2/3 it would PBKDF2 into garbage exactly like the bare form.
4. Published links should use the `sgit_rk1_` form (scannable: `\bsgit_rk1_[0-9a-f]{64}\b`).

## 3 · Terminology clarification requested by the CLI team

**`transfer_id` is not `vault_id`, and the two never meet.** In the web model, `transfer_id`
exists only in the **ro-token envelope flow**: it is
`SHA-256('ro-token-transfer-v1:' + token)[:12]`, a deterministic locator for the encrypted
credential blob on the transfers API. The read-key open path (format 4/6 — the one that mirrors
`sgit clone`) uses `vault_id` directly, same as the CLI. No mapping exists or is needed.

## 4 · Bonus: cross-implementation test oracle

The CLI's newly wired `sgit vault derive-keys` (commit `cb3310e`) prints
`vault_id, read_key, write_key, file ids` for a vault key. The web's §6.1 drift-invariant test
(`deriveReadOnlyCreds(...).refFileId === deriveKeys(vaultKey).refFileId`) can additionally be
pinned against CLI output as a known-answer test, the same way `test_vault_crypto_interop.js`
pins JS↔Python.

## 5 · One design addition to §3.1

`branchIndexFileId` is also derivable from the read key alone
(HMAC(read_key, `sg-vault-v1:file-id:branch-index:{vault_id}`)). `deriveReadOnlyCreds` should
return it alongside `refFileId` — it makes read-key opens resilient to future branch-index
consultation (parity with `SGVault.open`) and would eventually let ro-token payloads drop
`ref_file_id`. Costs one HMAC.
