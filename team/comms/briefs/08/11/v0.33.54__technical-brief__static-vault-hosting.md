# Technical Brief: Deploying a Vault to a Static Location

**version** v0.33.54
**date** 11 August 2026
**from** DevOps + Architect (Explorer team)
**status** DRAFT / PROPOSED — scoped and substantially specified; per-target recipes to be completed as each target is implemented
**relationship** Split out of the multi-target deployment plan (`v0.33.54__technical-brief__deployment-phases-a-d.md`) — static hosting is a different *kind* of deployment (no server runtime) and deserves its own architecture. Netlify moved here from that plan.

---

## 1. The Concept

A vault can be published as a **pile of static files**: the vault UI (plain HTML/JS, no
framework) plus a mirror of the vault's encrypted object tree (`bare/…` — ciphertext only).
Any static file host can then serve a **read-only vault**: the browser fetches ciphertext by
deterministic paths and decrypts locally. No API server, no compute, no per-request cost.

This works because of two things that **EXIST** today:

1. **`SGSend.staticMode`** (shipped 2026-06-30) — the vault client's static-host mode: reads
   become deterministic GETs (file IDs are content-hash/HMAC-derived, so no list/discovery
   call is needed), batch reads fan out to parallel GETs with identical response shapes, and
   writes reject with `EREADONLY`. Guide: `library/guides/vault-html/HOSTING-ON-STATIC-STORAGE.md`.
2. **`scripts/build-vault-static.sh`** — builds the flattened, self-contained vault UI tree
   (same script the Docker image uses).

The deployment model: **the source-of-truth vault lives on a live SG/Send server** (Lambda,
container, wherever). Publishing to a static location is an *export*: UI tree + object
mirror + access material. The live server is the write path; the static host is a read-only
projection, refreshed by re-publishing.

```
   live SG/Send server  ──(publish/export)──▶  static host
   (writes, sgit push)                          (read-only projection)
        │                                        GitHub Pages / S3 / Netlify /
        └── remains the source of truth          GCS / Cloudflare Pages / Heroku-static
```

## 2. Access Models — what "publishing the read token" means

Everything on the static host is ciphertext + UI code. Decryption is always client-side.
Two publication modes, chosen at publish time:

| Mode | What is published | Who can read | Use case |
|---|---|---|---|
| **M1 — Public projection** | files + the **read-only token embedded** in the page (or URL fragment pattern) | anyone with the URL | public docs, published reports, "website served from a vault" |
| **M2 — Locked projection** | files only; token shared out-of-band | anyone with URL **and** token | team snapshots, client deliverables, air-gapped review |

The "read-only token" is the existing **share-token / read-key material** (e.g. `sgit share`
snapshot tokens — read-only by construction; never the write key). Publishing a write key is
never valid in this model — rule 33 (never commit keys) extends naturally: **M1 embeds only
read-only material, and the brief's publish tooling must refuse anything stronger.**

## 3. Target Matrix

All targets serve the same exported tree; they differ in publish mechanism, domain/TLS
story, and gotchas. HTTPS matters everywhere: Web Crypto requires a secure context.

| Target | Publish mechanism | HTTPS / custom domain | CI automation | Gotchas |
|---|---|---|---|---|
| **GitHub Pages** | commit the exported tree to a `gh-pages` branch / `docs/`; or Actions `upload-pages-artifact` | HTTPS default; custom domain + enforced HTTPS | trivial (Actions) | 1 GB soft repo limit → large vaults need LFS or belong on S3; case-sensitive paths; no custom headers (cache-control fixed ~10 min — fine for imm objects, suboptimal) |
| **S3 (+ CloudFront)** | `aws s3 sync` the export; CF distribution for TLS+domain | via CloudFront (cert us-east-1) | trivial (already our pattern — `deploy_static_site.py` EXISTS for UIs) | our native target; per-object `cache-control` settable (imm objects → `immutable`); the CF imm-bypass pattern already deployed for the live API is the same idea |
| **Netlify** | `netlify deploy --prod --dir=…`, drag-and-drop, or git-linked build running the export | HTTPS default; custom domains | trivial (CLI/token) | `_headers` file gives per-path cache-control (better than GH Pages); free-tier bandwidth caps |
| **GCP Cloud Storage (+ optional Firebase Hosting)** | `gsutil rsync`; bucket website mode is HTTP-only → front with Cloud CDN/LB or use Firebase Hosting for free TLS | via LB/CDN or Firebase | small | bucket-website alone fails the secure-context requirement — must pair with CDN/Firebase |
| **Cloudflare Pages** | `wrangler pages deploy` | HTTPS default; domains trivial | trivial | generous free tier; `_headers` supported; good default recommendation alongside S3 |
| **Heroku (static)** | static buildpack (nginx) serving the exported dir from a git push | platform TLS | small | a dyno serving flat files — works, but is the least natural fit; only when Heroku is the org's only allowed platform |

(Cloudflare Pages added on Architect's initiative — it is the strongest free static host for
this shape and costs one row to keep.)

## 4. The Publisher — the missing piece (PROPOSED)

What does not exist yet is the **exporter**: one command that produces the deployable tree.
This aligns with the already-registered proposals `sgit publish-static` (doc 375 — "offline
static HTML bundle from vault; host anywhere") and the serverless static vault projection
(same doc). This brief adopts them as the engine:

```
sgit publish-static <vault-key-or-share-token> \
     --out ./_static_vault \
     --mode m1|m2                 # embed read token, or files-only
     --ui latest                  # bundle the static vault UI tree
     [--target github-pages|s3|netlify|gcs|cloudflare|dir]   # optional direct push
```

Produces: `index.html` + UI `_common/` tree + `api/vault/read/{vault_id}/…` **path-mirrored**
object files (the literal read-path layout `staticMode` expects today) + `_headers`/metadata
files where the target supports them (imm objects → long-cache immutable).

**Follow-on it depends on** (already noted in the staticMode guide): a configurable read-path
template on `SGSend`, so exports don't have to mirror the literal `/api/vault/read/…` prefix
forever.

Re-publish = re-run; content-addressed imm objects make syncs cheap (only refs/indexes and
new objects change). Cache invalidation only matters for the small mutable set (refs,
indexes, `index.html`).

## 6. Open Questions (to resolve before implementation)

1. **Large blobs** — presigned/large-file reads have no static equivalent; static export
   either inlines everything or documents a size ceiling per target (GH Pages 1 GB, etc.).
2. **M1 token placement** — embedded in `index.html` vs URL-fragment convention (`#<token>`
   keeps it out of server logs even on the static host; fragment never hits the wire).
3. **Multi-vault sites** — one export per vault, or a site hosting several projections
   (sub-vault links already exist in the UI model).
4. **Refresh cadence** — manual re-publish vs a CI job watching the source vault (ties into
   the `sgit publish --slug` subdomain proposals, doc 376).
