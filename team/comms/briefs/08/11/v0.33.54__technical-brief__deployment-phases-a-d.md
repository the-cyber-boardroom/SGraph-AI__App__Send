## Phase A — Lambda Web Adapter in the Docker Image

**Goal:** the existing `sg-send-vault` image runs unmodified on AWS Lambda (container image),
Cloud Run, and Heroku — while remaining byte-identical in behaviour on Docker/EC2.

### A.1 Dockerfile changes (`sgraph_ai_app_send__docker/Dockerfile`)

```dockerfile
# after FROM python:3.12-slim …
# Lambda Web Adapter — inert unless AWS_LAMBDA_RUNTIME_API is present (ADR-1)
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:0.9.1 /lambda-adapter /opt/extensions/lambda-adapter
ENV AWS_LWA_READINESS_CHECK_PATH=/api/info/health
# (pin the newest LWA release at implementation time; 0.9.1 = latest verified Aug 2026)

# hardening (marketplace + enterprise scans)
RUN useradd --create-home --uid 10001 app && chown -R app:app /data
USER app
HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request,os; urllib.request.urlopen(f'http://127.0.0.1:{os.environ.get(\"PORT\",8080)}/api/info/health')"
LABEL org.opencontainers.image.source="https://github.com/the-cyber-boardroom/SGraph-AI__App__Send" \
      org.opencontainers.image.title="sg-send-vault" \
      org.opencontainers.image.description="SG/Send zero-knowledge vault appliance"
```

Notes: `USER app` requires `/data` chown (above) and — if TLS mode binds :443 — either
`ENV FAST_API__TLS__PORT=8443` as the new non-root default or `cap_add NET_BIND_SERVICE`
documented in the README. Decide during implementation; document in the container README.

### A.2 `serve.py` — the `$PORT` contract (ADR-2)

```python
APP__HTTP_PORT = int(os.environ.get('PORT', 8080))   # Cloud Run / Heroku inject PORT
```

(Keep the constant's name; one-line change + a unit test in `tests/unit/docker/`.)

### A.3 ECR publishing

Lambda container images must be pulled from **ECR in the same account**. Add an ECR repo
(created by the Phase B template or CLI once) and a push step next to the existing Docker Hub
job — same digests, extra tag destination: `{account}.dkr.ecr.eu-west-2.amazonaws.com/sg-send-vault:{version}`.

### A.4 Friendly login page (ADR-12)

The existing `/auth/set-cookie-form` (EXISTS, unfriendly) becomes a proper front door,
shipped **in the image** so every target gets it: an SG-branded page — enter access key →
cookie set (+ header instructions for API clients) → redirect into the vault UI; wrong key
stays on the page with a clean error. In single-key mode this page IS the login screen for
the whole deployment (caddy on EC2/Fargate just proxies — the app's gate + this page do the
work; no caddy auth plugin). Small UI task, IFD-versioned like the rest of the vault UI.

### A.5 Self-contained invariant (ADR-14)

New smoke variant run on every image build: `docker run --network=none -e
SEND__STORAGE_MODE=memory …` + in-container health/UI/write-read checks. Proves zero runtime
external calls — no dependency loading, no CDN, no phone-home. (Already believed true —
this makes it enforced.)

### A.6 Acceptance criteria

1. `docker run -p 8080:8080 sg-send-vault:local` — health + vault UI checks pass (existing smoke).
2. `PORT=9999 python -m sgraph_ai_app_send__docker.serve` binds 9999.
3. A **manually created** dev Lambda from the ECR image (Function URL) returns
   `{"status":"ok"}` on `/api/info/health` and serves the vault UI root. Record cold-start ms
   vs the zip function (ADR §4.4 — measured, not assumed).
4. Existing container unit tests (31) still green; image still runs as root-free user.
5. **Network-isolated memory-mode run passes** (A.5) — the self-contained invariant is green.
6. With `SGRAPH_SEND__ACCESS_TOKEN` set: browser flow = login page → key → vault UI works
   end-to-end; all routes (including reads) 401 without the key.

**Effort:** small-medium (1–2 sessions; login page is the added half). **Risk:** low —
additive; LWA inert outside Lambda.

## Phase B — CloudFormation: Lambda Target + EC2 Target

**Goal:** `deploy/aws/lambda.cfn.yml` and `deploy/aws/ec2.cfn.yml`, parameterised (DNS,
memory/instance size, storage, auth), deployable with one CLI command into any account/region.
These templates are also the direct precursor of the P-398 Marketplace deliverable.

### B.1 Repo layout (new)

```
deploy/aws/
  lambda.cfn.yml        # container-image Lambda + Function URL (+ optional CloudFront/DNS)
  ec2.cfn.yml           # single-instance appliance (from AMI — ADR-15; user-data fallback)
  ecs-fargate.cfn.yml   # cluster + service + ALB — full lifecycle in one stack (ADR-13)
  ami-pipeline.cfn.yml  # EC2 Image Builder pipeline that bakes the AMI (Phase B3)
  README.md             # parameters, examples, teardown, data-recovery (EBS snapshots)
```

**Shared parameter semantics (all templates, ADR-12/ADR-8):**
- `AccessToken` (NoEcho) — **the licensing key, provided at startup** (ADR-6 as amended:
  no SSM/Secrets Manager — the deployment never stores it). Sources: GitHub Actions Secrets
  (our pipelines), an SG/Vault (team secret home, dogfooding), or the customer's own value at
  the Launch Stack screen. Empty = explicitly open instance. In single-key mode the key gates
  **all** routes — boot, API, and reads.
- `StorageMode` — every template accepts **`memory`** (nothing provisioned, zero external
  calls, data dies with compute — the agentic/ephemeral mode) alongside its target's other
  modes. Mode selects the IAM policy: memory mode gets no storage permissions at all.

### B.2 `lambda.cfn.yml` — parameters and resources

| Parameter | Default | Notes |
|---|---|---|
| `ImageUri` | — (required) | ECR image from Phase A |
| `Stage` | `dev` | suffixes names |
| `MemorySize` | `1024` | 128–10240 |
| `Timeout` | `30` | seconds |
| `AccessToken` | `""` (open) | sets `SGRAPH_SEND__ACCESS_TOKEN` (NoEcho) |
| `DomainName` / `HostedZoneId` / `CertificateArn` | `""` | all three ⇒ CloudFront + Route53 ALIAS; cert **must be us-east-1** (ADR §4.1); empty ⇒ bare Function URL |

Resources: `AWS::Lambda::Function` (`PackageType: Image`, arm64 or x86_64 — pick x86_64 to
match today, note arm64 works since the image is multi-arch), Function URL (`AuthType: NONE`),
execution role with least-privilege S3 (scoped to the two stack-created buckets:
transfers + public, names by the existing `{account}--sgraph-send-*--{region}` convention),
conditional CloudFront distribution (Function URL origin, forward all, no caching on `/api/*`)
+ Route53 record. Outputs: `FunctionUrl`, `PublicUrl`.

### B.3 `ec2.cfn.yml` — parameters and resources

| Parameter | Default | Notes |
|---|---|---|
| `ImageRef` | `diniscruz/sg-send-vault:latest` | Docker Hub or ECR |
| `InstanceType` | `t4g.small` | arm64 (image is multi-arch); param allows x86 types |
| `VolumeSize` | `20` | GiB, data volume |
| `StorageMode` | `disk` | `disk` \| `s3` — swaps the instance-role policy (P-398 least-privilege-per-mode) |
| `DomainName` / `HostedZoneId` | `""` | set ⇒ Route53 A record + caddy auto-TLS for the domain |
| `AllowedCidr` | `0.0.0.0/0` | security-group ingress 80/443 |
| `KeyName` | `""` | optional; SSM Session Manager is the default access path |

**AMI-first (ADR-15):** the template takes `AmiId` — default from a **pipeline-maintained
per-region mapping** in the template (the bake pipeline updates it; no SSM lookup); the AMI
already contains docker + the pre-pulled image + compose (app :8080 + caddy :80/:443, ADR-5)
+ an enabled systemd unit, so first boot only: receives `AccessToken` as a stack parameter →
instance env (ADR-6 — never stored anywhere), mounts the data volume at `/var/lib/sg-send`,
and passes `DomainName` to caddy. A **generic fallback path** (plain AL2023 + user-data that
installs docker and does all of the above) remains in the same template for regions with no
published AMI.

Other resources: security group (80/443 in, nothing else), IAM instance profile
(`AmazonSSMManagedInstanceCore` + storage policy selected by `StorageMode` — memory mode
gets none), data volume `DeletionPolicy: Snapshot` (ADR-7), EIP + optional Route53 A
record. Outputs: `PublicUrl`, `AccessTokenParameter`.

### B.3b `ecs-fargate.cfn.yml` — parameters and resources (ADR-13)

| Parameter | Default | Notes |
|---|---|---|
| `ImageRef` | ECR image | same image as everything else |
| `Cpu` / `TaskMemory` | `512` / `1024` | Fargate size classes |
| `DesiredCount` | `1` | >1 requires `StorageMode=s3` (memory replicas don't share state) |
| `StorageMode` | `s3` | `s3` \| `memory` |
| `AccessToken` | per shared semantics | licensing key |
| `DomainName` / `HostedZoneId` / `CertificateArn` | `""` | set ⇒ ALB HTTPS listener + Route53 ALIAS (cert in-region — no us-east-1 constraint, unlike CloudFront) |

Resources — **one stack owns the entire footprint**: ECS cluster, task definition, service,
ALB + target group (+ HTTPS listener when cert given), security groups, CloudWatch log group,
conditional S3 buckets + task-role policy, optional Route53 record. **Lifecycle contract:
stack delete removes everything including the cluster and ALB** — verified by the full-cycle
pipeline (C1); an orphaned resource is a pipeline failure, not a cleanup ticket. This is the
long-running multi-replica pattern (N tasks behind the ALB, `s3` mode).

### B.4 Deploy commands (documented in `deploy/aws/README.md`)

```bash
aws cloudformation deploy --template-file deploy/aws/lambda.cfn.yml \
  --stack-name sg-send-lambda-dev --capabilities CAPABILITY_IAM \
  --parameter-overrides ImageUri=$ECR_IMAGE MemorySize=1024

aws cloudformation deploy --template-file deploy/aws/ec2.cfn.yml \
  --stack-name sg-send-ec2-dev --capabilities CAPABILITY_IAM \
  --parameter-overrides DomainName=box.sgraph.ai HostedZoneId=Z...
```

### B.5 Acceptance criteria

1. `cfn-lint` clean on both templates.
2. Lambda stack: fresh dev account/region, no console → `PublicUrl/api/info/health` = ok;
   vault create/push/clone round-trip via `sgit --endpoint`.
3. EC2 stack with domain: `https://{DomainName}/` serves the vault UI with a valid cert;
   Web Crypto works (secure context); the token was supplied at launch and is stored
   nowhere server-side.
4. EC2 stack **teardown**: stack delete leaves an EBS snapshot; README documents restore.
5. Both stacks deploy into a *second* region unchanged (convention naming holds).

**Effort:** medium (2–3 sessions; EC2 user-data is the fiddly half). **Risk:** medium —
first IaC in the repo; mitigated by cfn-lint + the pytest smoke files in Phase C.

### B2 — Terraform modules (ADR-3 amended / ADR-10)

**Goal:** `deploy/terraform/modules/{aws-lambda,aws-ec2,aws-ecs-fargate,gcp-cloud-run,heroku}`
+ `examples/`. For AWS the CFN templates are authoritative and the modules mirror them; for
GCP/Heroku the Terraform module **is** the implementation that Phase D's CI jobs call
(`terraform apply` instead of bespoke `gcloud`/`heroku` CLI sequences).

| Module | Mirrors / implements | Providers used |
|---|---|---|
| `aws-lambda` | `lambda.cfn.yml` | `hashicorp/aws` |
| `aws-ec2` | `ec2.cfn.yml` (AMI consumption + user-data fallback via `templatefile()`) | `hashicorp/aws` |
| `aws-ecs-fargate` | `ecs-fargate.cfn.yml` (full cluster lifecycle) | `hashicorp/aws` |
| `gcp-cloud-run` | Phase D1 | `hashicorp/google` (+ Secret Manager) |
| `heroku` | Phase D2 | `heroku/heroku` |

(A `netlify-static` module, if ever wanted, belongs to the static-vault-hosting brief.)

Variables mirror the CFN parameter tables one-for-one (memory, instance type, DNS, storage
mode, token). Gates in CI: `terraform fmt -check`, `terraform validate`, `tflint`.
**Equivalence check:** the shared pytest smoke suite must pass against a module-deployed
stack exactly as against a CFN-deployed one — that suite, not code inspection, is the
drift alarm. Registry publication (`terraform-aws-sgsend` one-module-per-repo naming) is a
registered follow-on; git-source consumption works from day one.

**Effort:** medium (AWS modules ~1 session each since they mirror finished CFN; provider
modules land inside their Phase D sessions). **Risk:** low-medium — the deliberate CFN/TF
duplication for AWS is the cost of serving both consumer bases; the smoke suite bounds it.

### B3 — AMI baking pipeline (ADR-15)

**Goal:** the AMI as the **master server-side artifact** — every EC2-shaped deployment
(customer appliance, Marketplace, our own instances) boots from a pre-baked, versioned,
scannable AMI rather than installing docker at first boot.

- `deploy/aws/ami-pipeline.cfn.yml` defines an **EC2 Image Builder** pipeline: AL2023 base +
  docker + the versioned `sg-send-vault` image **pre-pulled** + compose file (app + caddy) +
  systemd unit enabled + first-boot script (token from startup env, caddy TLS for `DomainName`).
  (Image Builder over Packer: AWS-native, CFN-definable, no HashiCorp BSL question — Packer
  documented as the alternative.)
- Output: `sg-send-vault-{version}` AMIs, copied to the offered regions, tagged; the bake
  pipeline updates the per-region AMI **mapping in `ec2.cfn.yml`** and the deploy pages
  (no SSM dependency — ADR-6 amendment's spirit applied here too).
- `ec2.cfn.yml` consumes `AmiId` (default = the mapped latest baked AMI; the generic
  AL2023+user-data path remains as fallback for regions without a published AMI).
- Bake job runs in the full-cycle pipeline (C1) when the image version changes; the baked AMI
  is smoke-tested by launching the EC2 stack from it.
- **This AMI is the Marketplace artifact** (P-398): no baked credentials (ADR-6), no default
  passwords, SSH-less (SSM), scan-clean — the marketplace requirements are acceptance
  criteria here, long before any listing is filed.

**Effort:** medium (1–2 sessions). **Risk:** medium — Image Builder pipelines are fiddly to
debug; mitigated by the fallback user-data path staying alive.

## Phase C — The Pipelines (ADR-16)

Two **new** workflows — the existing `ci-pipeline*.yml` family is untouched until the
cutover is earned. Both run on **GitHub OIDC** (assume-role; no long-lived AWS keys in any
new workflow). New secrets: `GCP_WORKLOAD_IDENTITY_PROVIDER`+`GCP_SERVICE_ACCOUNT`,
`HEROKU_API_KEY`. Shared smoke = pytest (`tests/deploy/targets/test_smoke__*.py`),
parametrised over a base-URL env var: health, versions, auth-gate (all routes 401 without
key when token set), CORS preflight, sgit round-trip, and — where storage is `memory` —
a write-read-restart-gone check.

### C1 — `deploy-full-cycle.yml`: deploy everything → test everything → destroy everything

The proof-of-lifecycle pipeline. **Sequential by design** (dispatch + nightly):

```
build image → publish templates to the S3 template bucket → [bake AMI if image changed]
  → deploy lambda.cfn      → smoke → keep
  → deploy ecs-fargate.cfn → smoke
  → deploy ec2.cfn (from AMI) → smoke
  → deploy gcp-cloud-run (TF) → smoke        (once D1 lands)
  → deploy heroku (TF)        → smoke        (once D2 lands)
  → DESTROY in reverse order — every stack, cluster, ALB, instance
  → orphan sweep: assert the account/projects contain nothing tagged sg-send-fullcycle
  → report: per-target timings, cold starts, smoke results
```

A run that cannot fully tear down **fails loudly** — orphan detection is a pipeline step,
not an ops afterthought. Every resource carries a `sg-send-fullcycle` tag so the sweep is
mechanical. This is also where ADR-13's "stack delete leaves nothing" contract and ADR-14's
network-isolated invariant are continuously verified.

### C2 — `deploy-publish.yml`: the dogfood pipeline

Once the artifacts mature: publishes the **live** API to the several locations we already
want live — driven **exclusively by CFN/Terraform at pinned versions**, no pytest-deployer.
A config file (`deploy/publish-targets.yml`) lists the destinations (account/region/target/
params); the pipeline iterates it. This is us deploying with the customer artifacts —
if it hurts, the product hurts, and we feel it first.

**Productization direction (stated in ADR-16):** the osbot pytest-deploy mechanism was right
for the development era; once C2 has run production through a bedding-in period, it replaces
the incumbent and we converge on **one deployment mode — CFN/Terraform across the board**.

### C3 — Acceptance criteria

1. C1 dispatch from a clean checkout: full sequence green, account empty afterwards
   (orphan sweep passes), report artifact produced.
2. C1 nightly catches a deliberately-broken teardown (test the tester once).
3. C2 deploys one real location end-to-end from `publish-targets.yml` with a pinned version.
4. No job in either workflow uses `AWS_ACCESS_KEY_ID` (OIDC only).

**Effort:** medium-large (2–3 sessions; C1's sequencing/teardown discipline is the work).
**Risk:** medium — teardown edge cases; that's precisely why the pipeline exists.

## Phase D — Other Providers: GCP, then Heroku

Accounts exist for both. Order: Cloud Run first (closest to Lambda semantics), Heroku second
(trivial once `$PORT` works). Both are driven via their B2 Terraform modules from the
pipelines. (Netlify moved to the static-vault-hosting brief — see D3 note below.)

### D1 — GCP Cloud Run

```bash
gcloud run deploy sg-send-vault \
  --image docker.io/diniscruz/sg-send-vault:${VERSION} \
  --region europe-west2 --allow-unauthenticated \
  --memory 1Gi --set-env-vars SEND__STORAGE_MODE=s3 \
  --set-secrets AWS_ACCESS_KEY_ID=sg-send-aws-key:latest,AWS_SECRET_ACCESS_KEY=sg-send-aws-secret:latest,SEND__S3_BUCKET=sg-send-bucket:latest
```

- **Storage (ADR-8):** D1 ships with S3 cross-cloud (creds in GCP Secret Manager — dedicated
  low-privilege AWS IAM user scoped to the one bucket). `Storage_FS__GCS` is the registered
  follow-on (clean Memory-FS backend task), NOT part of D1.
- CI: Workload Identity Federation (no SA keys in GitHub).
- Custom domain: Cloud Run domain mapping (managed cert) — optional parameter of the CI job.
- Acceptance: health + smoke suite + sgit round-trip against the run.app URL; UI loads
  (secure context ⇒ Web Crypto fine).

### D2 — Heroku

```bash
heroku container:login
docker tag diniscruz/sg-send-vault:${VERSION} registry.heroku.com/${HEROKU_APP}/web
docker push registry.heroku.com/${HEROKU_APP}/web
heroku container:release web -a ${HEROKU_APP}
heroku config:set SEND__STORAGE_MODE=s3 SEND__S3_BUCKET=... -a ${HEROKU_APP}
```

- **Hard constraint:** Heroku's filesystem is ephemeral — `disk` mode is demo-only;
  production config is `s3` (or memory for throwaways). Document loudly.
- amd64 image from the manifest; platform TLS at the router; `$PORT` honored (Phase A).
- Acceptance: same smoke suite against `https://{app}.herokuapp.com`.

### D3 — ~~Netlify~~ moved (08/11): static hosting is its own brief

Netlify was removed from this plan (ADR-9 amended). It — together with GitHub Pages, S3,
GCS, Cloudflare Pages, and Heroku-static — belongs to a different deployment *kind*:
publishing a **read-only vault projection** (static UI + ciphertext mirror + read-only
token) to any static file host. See
**`v0.33.54__technical-brief__static-vault-hosting.md`** (same folder), which covers the
target matrix, the two access models (public projection vs locked projection), and the
`sgit publish-static` exporter it adopts from doc 375.

**Effort D1–D2:** small each (1 session per provider once C exists).

## Phase E — One-Click Deploy Web Pages (`sgraph_ai__website/en-gb/deploy/`)

**Goal:** a public "Run SG/Send anywhere" section on sgraph.ai where each target is one

/deploy/                      HUB — one card per target: button, "time to running",

├── /deploy/aws-lambda/       ★ the "one click to install the Lambda function" page

### E.2 `/deploy/aws-lambda/` — the Lambda one-click page, in detail

1. **Launch Stack buttons** — one per offered region (eu-west-2, us-east-1, …), each a CFN
   console deep-link with `templateURL` (public template bucket, `latest/lambda.cfn.yml`),
   `stackName=sg-send`, and prefilled `param_MemorySize`/`param_Stage`. The AWS console
   review screen is the actual "click" — the user sees every parameter and IAM capability
   before creating. We never ask for their credentials; everything runs in *their* console.
2. **"What this creates"** — plain-language resource list + architecture mini-diagram
   (function, Function URL, two S3 buckets, IAM role; optional CloudFront+DNS variant).
3. **Parameter guide** — the CFN parameter table rendered human: memory, token (leave empty =
   open instance), custom-domain trio with the us-east-1 cert caveat.
4. **After it's green** — copy the `PublicUrl` output → open the vault UI → `sgit clone …
   --endpoint {PublicUrl}` → optional: set the access token.
5. **Teardown** — delete the stack; what persists (S3 buckets keep vaults unless emptied).
6. **Trust block** — link to the template source file on GitHub at the pinned version, its
   sha256, and the security-model page (zero-knowledge: the instance never sees keys).

`/deploy/aws-ec2/` mirrors this with: instance-type/cost table, DNS+HostedZone walkthrough,
"your access token is the one you set at launch — keep it in a password manager or an
SG/Vault" guidance, EBS snapshot-on-delete promise.

### E.5 Acceptance criteria

1. A logged-in AWS user reaches a running SG/Send (health ok, vault UI opens) from
   `/deploy/aws-lambda/` in **under 5 minutes** without leaving the browser.

**Effort:** medium (pages are static site work; the S3 template publishing + 3 repo artifacts
