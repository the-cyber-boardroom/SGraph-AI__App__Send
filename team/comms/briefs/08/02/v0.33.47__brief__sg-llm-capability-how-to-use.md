# Brief — `sg.llm.*`: how to use AI inside a vault (and inside a vault app)

**Date:** 2026-08-02 · **Version:** v0.33.47 · **Audience:** anyone building on SG/Vault —
humans and agents · **Status:** code-verified against `v0/v0.2/v0.2.3`

There are now **two** ways to use an LLM in SG/Vault, sharing one engine, one key and one bill:

| Surface | Who uses it | Setup |
|---|---|---|
| **AI Chat panel** in the vault UI | Anyone opening a vault | Configure a key once, then it is just there |
| **`sg.llm.*`** from a vault HTML app | App authors | Declare `permissions.llm` in `app.json` |

The organising idea: **the key belongs to the vault, not to the app and not to the page.** It
lives in `.vault/llm/config.json`, inside the permission floor, sealed to the vault owner. Apps
send messages and get text back; they never hold a credential.

---

## Part 1 — Turning AI on for a vault (once)

1. Open the vault with its **full key** (an owner-sealed key cannot be unsealed in a read-only
   session — that is cryptographic, not a policy check).
2. **Settings → AI models (OpenRouter)** → paste an OpenRouter key → **Test** → **Save**.
3. Optional, under *advanced*: default model, allowed-models list (globs, e.g. `anthropic/*`),
   and spend caps (`maxCostPerSession`, `maxCallsPerSession`, `maxTokensPerCall`).

**Key tiers.** `owner` (default) seals the key with the vault's write key — a read-only opener
gets `EREADONLY` and cannot use it. `shared` stores it readable by anyone who can open the vault.
Prefer `owner` unless you deliberately want every opener to be able to spend.

> **Know what you are storing.** With a key configured, the vault contains a credential. Sharing
> the vault key shares the ability to spend it. Short-lived minted credentials are planned
> (Phase 4) and would remove this; until then, treat such a vault as carrying a secret.

## Part 2 — The AI Chat panel (no code)

Open it from **✨ AI Chat** in the vault header, or by clicking **➕ Add to chat** on any file.

- **Attach several files.** Each attached file shows as a chip with a `×`. Re-adding a file
  replaces its contents, so it refreshes after an edit. Chat with **no** files attached is fine —
  it is then a plain chat.
- **Files share one 24 000-char budget** (not one each), so attaching a second file cannot
  silently double your prompt or your bill. Trimmed files say `TRUNCATED` in the text the model
  sees, so it cannot pretend to have read the whole thing.
- **⚙ request params** — temperature, top-p, max tokens. Blank means the provider's own default.
  Max tokens is clamped to the vault policy, and says so when it clamps.
- **🧾 AI Requests** — every call with its OpenRouter **generation id**, tokens, cost, latency and
  the files it referenced; running totals; CSV/JSON export. Billed and estimated costs are shown
  **separately** — an estimate is never rendered as a bill.
- Both panels are ordinary `sg-layout` panes: drag, resize, close.

## Part 3 — `sg.llm.*` from a vault app

Full reference: `library/guides/vault-html/AUTHORING.md` → **"Calling an LLM"**.
Agent-facing how-to: `library/skills/create-vault-apps/SKILL.md`.

### Declare the grants (deny-by-default)

```json
{ "entry": "index.html",
  "permissions": { "llm": { "chat": true, "models": true, "usage": true } } }
```

### Always check availability first

```js
const a = await sg.llm.available();
if (!a.ok) return degrade(a.reason);   // ENOKEY | EPERM | EREADONLY | EBUDGET
```

`available()` is deliberately ungated — an app must be able to discover it *cannot* use the LLM
in order to degrade honestly, rather than rendering a chat box that fails on first use.

### Chat, streaming

```js
const res = await sg.llm.chat(
    { messages: [{ role: 'user', content: 'Summarise report.md' }] },
    (delta, acc) => { out.textContent = acc; }
);
// res: { content, model, finishReason, usage, cost:{value,source,estimated}, id, aborted }
```

The **terminal reply is authoritative** — an app that ignores `onToken` still gets the full
`content`. Deltas carry only the increment and are coalesced by the host (~50 ms), so you never
get a postMessage per token.

### Cancel

```js
const p = sg.llm.chat({ messages }, onToken);
stopBtn.onclick = () => sg.llm.cancel(p.requestId);
```

An aborted call keeps its partial text **and is still recorded and costed** — stop must not feel
like data loss, and must not hide spend.

### What the host enforces (so you don't, and can't bypass)

| Host does | Consequence for the app |
|---|---|
| Holds the key | Never in your frame, bundle, or any message you receive |
| Filters `models()` by the vault allow-list | A picker you build from it is automatically correct |
| Clamps `maxTokens` to policy | Asking for more is capped, not an error |
| Enforces `maxCost/maxCalls` per session | `EBUDGET` — and the cap counts spend from **all** surfaces, including the vault's own chat panel |
| Raises the consent prompt on first `chat()` | `ECONSENT` if the user declines |
| Reconciles cost two-source | `cost.estimated` tells you whether it is a guess |

**Errors** arrive as `err.code`: `EPERM`, `ECONSENT`, `ENOKEY`, `EREADONLY`, `EBUDGET`, `EMODEL`,
`EABORT`, `EPROTO`. Branch on the code, never on message text.

### This is not an agent

`sg.llm.chat` takes messages and returns text. There is no tool-calling loop and the model gets
no ambient authority over the vault: if you want the reply to cause a write, *your app* calls
`sg.vfs.*` / `sg.fs.*` itself, under grants it already declared. Keeping the model's output and
the vault's authority separate is the point.

## Should this be a skill?

**No — and deliberately.** It belongs in the two homes that already exist:

- `library/guides/vault-html/AUTHORING.md` — the canonical `window.sg.*` contract. Adding a
  competing document would create a second source of truth that drifts.
- `library/skills/create-vault-apps/SKILL.md` (`vault-html-app`) — already the skill that fires
  when someone builds a vault app, which is exactly when `sg.llm.*` is relevant. Both are updated.

A separate `sg.llm` skill would compete for triggering with `vault-html-app` on the same
intent ("build me a vault app that…") and split the authoring contract across two files. Skills
earn their keep when they cover a *distinct task*; this is one capability inside an existing one.
This brief exists for humans deciding whether/how to use it, not as a third API reference.

## Status — what is and is not built

**Shipped:** the shared engine (`SGLlm`), vault key/policy resolution (`SGLlmVault`), the admin
settings panel, the host-native chat panel (multi-file, params, ledger), and the `sg.llm.*` bridge
with permission + consent + budget + streaming + cancel.

**Not built:**

- **CSP egress lockdown.** App frames are not yet served with a `connect-src` that blocks direct
  network access, so a malicious app could still call an LLM provider itself with its *own* key.
  The bridge protects *your* key; it is not yet a boundary that prevents all egress. This is the
  gap that turns the current design from a convenience into a guarantee.
- **Phase 4 minted credentials** — short-lived, budget-capped tokens from SG-API so the vault holds
  a *reference*, not a key. This is what would make vault-sharing safe with AI configured, and it
  is the commercially load-bearing piece.
- **ViV kernel parity** — `sg.llm.*` is served by the `/en-gb/app/` host. Nested vault-in-vault
  kernels (`kernel-app-handlers.js`) do not relay it yet.
- Ledger persistence across reloads (session-only by design), and real per-file token counts
  (character counts are a proxy).
