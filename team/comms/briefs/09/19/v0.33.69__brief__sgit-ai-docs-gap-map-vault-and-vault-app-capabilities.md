> Version prefix from the latest git tag (`v0.33.69`).

**Objective (from the human owner):** help agents and humans who are building vaults know *in detail* how the platform works and *the art of the possible*. This brief is organised for that: what will actively mislead a builder today (fix first), what exists and is not written down anywhere on the site (the possible), and a page plan.

**One-paragraph verdict.** The site is unusually honest and well-structured — the surfaces page, the messaging page, the API reference and the "what not to build" brief are the best guidance in the estate, and the `.md`-twin + `llms.txt` design works. But it documents the platform **as of roughly 15 August**, and the vault UI has shipped its two largest capability jumps since: **declared mounts** (an app reads and writes another vault through a plain path, with receipts and a sync discipline) and the **read-key open forms** (`sgit_private_read_…:<id>`, `/en-gb/#<key>`, format 6). Neither has a single mention. Four things on the site would break an agent that follows them verbatim.

## 2 · The art of the possible — shipped, code-verified, and absent from the site

Counted across all 253 `.md` pages on the site. "0" means not one mention.

### 2.1 Declared mounts — one app, many vaults, no key in the app (0 mentions)

The owner drops `<name>.link.json` in the parent; the top kernel mounts the child **before the app iframe exists**. The app writes `sg.vfs.write('data/x.json')` and has no idea `data/` is another vault. Shipped 7–8 Sep; in production use by the games/telemetry pipeline; e2e with screenshots in `library/guides/vault-html/DECLARED-MOUNTS-E2E.md`.

What a builder needs to know, none of which is on the site:

- **Credential resolution order** and what tier each yields: `.vault/owner/secrets/<ref>.json` (sealed under the parent **write** key → **rw**) → `.vault/owner/ro-links.json` (read key → **ro**) → device-saved key → legacy stub. A read-only parent session mounts read-only, never rw. (`owner/secrets`: 0 mentions; `ro-links`: 1.)
- **Two gates on every relayed op**: the parent app's grant on the parent path (`"write": ["data/"]`) **and** the child's own `.vault/app.json` — the child's manifest is the real bound; grant `"write": ["events/"]` there, not `true`.
- **Receipts** (8 Sep): every `sg.vfs.write` / `sg.fs.mkdir` / `sg.fs.move` resolves `{ …, commit_id, published }`; local writes return `published:false` plus a `vfs.published` host event when auto-push lands. `published:true` witnesses the child's compare-and-swap publish at that instant — **not** survival against a later blind push by another clone. (`commit_id`: 0 mentions.)
- **What is refused and why**: cross-boundary `move` → `EXDEV`; `delete` across a mount → `EUNDERPRIVILEGED` (destructive verbs across a vault boundary need per-request elevation — the credential-tier model); `sg.history` never crosses a mount (parent-only). (`EXDEV`, `EUNDERPRIVILEGED`, `EMOUNT_RO`, `EDIVERGED`: 0 each.)
- **Sync discipline** in the child kernel: reconcile-before-write (FF or three-way merge), CAS push with one reconcile-and-retry then `EDIVERGED` (never force-publishes), throttled refresh-before-read; `sg.vault.mounts()` → `[{ prefix, access, declared, state: idle|unknown|clean|ahead|behind|diverged, at }]`, where `state` is as of the last tab-focus check, **not** updated by a write.
- **Provenance**: every commit a child kernel makes carries `Via-Mount: <label> (declared|runtime) parent=<parent vault id>` — visible in `sgit history log` on the child. This is the only durable artefact that distinguishes a mount write from any other writer. (`Via-Mount`: 0.)
- **The two lanes are different things**: the composite `.link.json` adapter the vault *browser* uses is read-only by design (`EMOUNT_RO` on all 8 verbs; a real folder cannot shadow a mount); the kernel lane the *app* uses is read-write. `sub-vaults.md` describes them as one mechanism.
- **One mount per child per parent** (`EEXIST` on a second link to the same child); many parents may share a child (each on its own `viv:<parent id>` clone branch).
- **Rollback is one file**: delete the `.link.json`; the child is untouched.

### 2.2 Credentials and URL forms — what the UI accepts (partially covered, never as a table)

The site explains read keys well but never lists the forms the deployed UI actually accepts. From `vault-loader-format.js` and the routing module:

| Form | Example | Opens as |
|---|---|---|
| Vault key | `passphrase:vault_id` | rw (with an access token or an embedded one) |
| Simple token | `word-word-1234` | rw |
| **Read credential (format 6)** | `<64-hex read_key>:<vault_id>` | ro — sgit CLI parity, verified byte-identical against sgit-ai 0.16.0 |
| **sgit-prefixed** any of the above | `sgit_private_read_<hex>:<id>`, `sgit_private_vault_…`, `sgit_public_read_…` | prefix stripped, then as above |
| ro-token | `ro-word-word-1234` | ro via the transfers API |
| Share token | `word-word-1234` on `send.sgraph.ai/en-gb/browse/#` | read-only snapshot |

And the URL inboxes: `/#<key>`, **`/<locale>/#<key>`** (since 9 Sep — what `sgit` prints; before that the landing silently dropped the key and showed the home page), deep links `#<key>|path`, `#<key>|app:path`, and **release pins** `#<key>|@<release>` (`@release`: 0 mentions on the site). `/en-gb/app#path` carries a file path, never a key.

### 2.3 Writable key-only links and owner custody (0 mentions)

`.vault/access-token.json` — created by `sg.vault.create({ accessToken: 'inherit' | '<token>' })`, rotated by `sg.vault.setAccessToken(ref, value)` — makes a **key-only link open writable** in both shells with no token in the URL. Together with the owner-secret store (child keys sealed under the parent write key, `custody: true`) and `sg.vault.getKey(ref)`, this is the whole "an app manages a fleet of child vaults" story, and the site has none of it. Security note to carry with it: the embedded token is floored (`.vault/**`) and read-key-encrypted — it upgrades the account tier only; a read credential can never write regardless.

### 2.4 Manifest semantics that cost another agent days (1 mention, incomplete)

`.vault/app.json` **replaces** the root `app.json`; a folder-level `app.json` replaces both — **nothing merges** (`_readAppJson` returns the first candidate). Adding `fs` grants in the new location silently drops `append.*`, `network`, `llm.*` unless copied forward. `vault-apps.md` says "preferred location … a legacy root `app.json` is still read" — true, and exactly the sentence that leads to the trap. Same page should carry: `permissions.network: true` reopens *all* egress from a frame holding decrypted content (7 mentions, good), `permissions.consent[verb]` (`always|once|auto`, never widens), and the 3 MB `EFBIG` cap (1 mention — good).

### 2.5 The vault browser itself — the art of the possible without writing an app

`docs/vault/index.md` covers the browser in one clause ("history, branches, editing"). Code-verified features with no page anywhere:

- **SGit view**: commit list, commit detail, per-commit diff, refs/tree inspector — the "look inside the encrypted store" your embed brief wanted to frame (`SGit view`: 8 mentions, mostly the version log).
- **Sync pill**: `● Synced` / `↑N to push` / `↓N to pull` / `⇅ Diverged`, auto-push (debounced) and auto-pull on tab focus, one shared `sg-vault-autosync` switch for `/vault` and `/app`; reconcile-on-open prefers the named head when the clone is cleanly behind (this is how a browser tab and `sgit push` coexist). (`auto-sync`, `auto-push`: 0.)
- **Editing**: markdown/text/HTML split editor with live preview (HTML preview sandboxed), upload, new file, rename/move/delete, `.vault-settings.json` visible and editable in the tree (1 mention), app-title fallback for unnamed vaults.
- **"Ask about this file" / vault chat** at `/en-gb/vault/chat/` — the vault's own LLM key (OpenRouter, configured in Settings), injection-floor fencing, context inspector, tools panel; and in `/app` the ✨ AI panel that never lets the app see the key. (`ask about this file`: 0; `vault chat`: 2.)
- **Settings**: AI config, read-only share block, credential display that hides write-key fields in read-only sessions, embedded-token status.
- **Sub-vault UI**: "🔗 Add link" (writes the pointer **and** the portable ro-record), link cards with public-info-before-key, the subvaults panel, click-to-load external embeds (the site covers the last one well).
- **Releases**: pin a version (`.vault/releases.json`, release picker, "not the latest" pill, `sg.app.pinned` / `sg.app.release`) — the site cites the AIUC-1 vault's version convention but never the platform feature it could use.
- **Per-tab vault identity** (sessionStorage-first key) so "open in new window" is an independent session; recent-vaults list; the peek page; public previews (OG cards).
- **The `/app` debug pane**: Vault trace, Bridge log, **Mounts**, **Audit** (cross-kernel), **REPL** over `sg.*`, State, Network — the first thing a builder should open when a call misbehaves, and unknown to the site.

### 2.7 Why a mount can be trusted — the kernel security model (3 mentions of "kernel", 0 of `SecureChannel`)

Null-origin `srcdoc` app frames; a PKI-authenticated `SecureChannel` per child kernel; the custody gate (parent-held credentials never inside a same-origin frame), the credential-tier gate (destructive verbs need per-request elevation), the broker with a per-op audit log and consent, the sovereignty rail. A builder deciding whether to put real data behind a mount has no page that explains what protects it. The 05/28 architect pack and `viv-*.js` tests are the source.
