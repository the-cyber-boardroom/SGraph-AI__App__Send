## 2 · Not shipped — and the reason each time

| Ask | Status | Why |
|---|---|---|
| `sg.fs.delete` through the mount | **refused as a standing request**; you get `EUNDERPRIVILEGED` with a message instead of `EMOUNT_RO` | destructive verbs across a vault boundary require **per-request elevation** in the credential-tier model; the issuance path does not exist yet, and we will not lower the tier to make it "work". |
| `sg.fs.move` across a mount boundary | **refused** — `EXDEV` | a move between two vaults is a copy plus a delete on two stores; a failure between the two leaves the file in both or neither. |
| make `sg.history` across a mount "live" | **not built** | it was never a snapshot: `sg.history.*` is always served by the **parent** (`logCommits` has no path option). Your 25 was the parent's own chain, not the child's 27. Building it is a new kernel verb and a policy call (it would hand the parent app the child's decrypted commit messages, other writers' included). The receipt covers your use case. |
| `vault_id` in the mount row | **not added** | it is in the owner's `data.link.json`, which your app can read — by the owner's choice. The row is the app contract; the child's identity is not part of it. |
| 403 JSON on a bad append token | **nothing to change in the gate** | the route already returns **403 whether or not the vault exists** (since July) — a deliberate absence of an existence oracle, which we will not trade for a 404. The HTML 404 you see is generated **above** the route. Please send us the response headers of one; if they are CloudFront's, the request never reached the Lambda. |
| derive the enum key in `sg.append.configure` | **already the behaviour** when you configure through the bridge — it publishes the hash of `SHA256("sg-inbox-enum:" ‖ read_key)`. Documented now. | your lanes were configured outside the bridge with random keys. Rule (documented, not enforced — the platform has no public-read flag): never host a lane whose enumeration is sensitive on a vault whose read key is public; the enum key *is* the read key. |
| validate before fetch on the append verbs | **handed to the append-lanes owner** | different code owner; recorded as S9. |
| `sgit pull` over a dirty working tree | **forwarded to the SGit-AI CLI team** as a data-loss shape | not this repository. |
| your `declare-mount.mjs` as the worked example | **accepted, pending a review** | it handles the child's full key and the parent's write key. Review gate: never prints a key (incl. `--dry-run`), never writes a plaintext key to disk, seals with the parent write key only. Then it goes in the guide. |

## 3 · The one caveat you must carry into the drain

`published: true` witnesses the child's compare-and-swap publish **at that instant**. It does not protect the commit against a later *blind* push by another clone that was behind — the browser shells push blind, and we have not verified `sgit push`. So for the irreversible step:

1. mark-processed on the receipt (recoverable);
2. **purge on the next drain**, after the read-back through the mount still finds the rows (reads reconcile against the server before they are served);
3. we are asking the CLI team for compare-and-swap push, which removes the blind writer.

Your recoverable/irreversible split is the right pattern and is going into the guide with this caveat attached.

## 4 · How to check the deployment carries this

**Level 1 — read-only probe, no token, ~2 s.** It now checks two marker groups: the 7 Sep change and this one.

```bash
npm run probe:vault-ui -- https://dev.vault.sgraph.ai https://dev.send.sgraph.ai
```

Read the exit code: **0** live (both groups) · **1** files fetched but markers missing (older build, or CloudFront has not caught up — wait a few minutes) · **2** the UI could not be reached — a **network** result, never evidence of a failed deploy. It also prints the deployed `build-info.js` app + UI version and the API health.

**Level 2 — from your own dashboard, four probes** (your `mount.*` harness, same session, same grants — remember to add `mkdir` and `move` to both manifests first):

| Probe | Expect |
|---|---|
| `sg.vfs.write('data/probe.json', bytes)` | resolves with `commit_id: 'obj-cas-imm-…'` and `published: true` |
| `sg.fs.mkdir('data/poc')` | `{ created: true, commit_id, published: true }` — your `mount.mkdir` flips from `EMOUNT_RO` to pass |
| `sg.fs.move('data/poc/x', 'data/events/x')` then `sg.fs.move('data/events/x', 'x')` | first `{ moved: true }`; second rejects with `code === 'EXDEV'` |
| `sg.fs.delete('data/events/x')` | rejects with `code === 'EUNDERPRIVILEGED'` (was `EMOUNT_RO`) |
| `sg.vault.mounts()[0]` | exactly the keys `access, at, declared, prefix, state` |

If the first probe still returns only `{ path, size }`, the UI you are on predates this change: check the probe's build line against the merge.

**Level 3 — the full browser e2e against dev** (needs a token; leaves throw-away vaults):

```bash
SG_UI_BASE=https://dev.vault.sgraph.ai SG_API_URL=https://dev.send.sgraph.ai \
SG_ACCESS_TOKEN=<token> SG_REQUIRE_API=1 npm run test:vault-e2e-declared-mounts
```

Test 1 now asserts the receipt, `mkdir`, same-mount `move`, `EXDEV`, `EUNDERPRIVILEGED` and the projection in a real browser. Green here is the confirmation.
