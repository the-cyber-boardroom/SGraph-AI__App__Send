## 1 · Three corrections first, because your gate depends on them

**Your one witness is not a witness.** The `state` on `sg.vault.mounts()` is refreshed only by the host's tab-focus behind-check (30 s debounce). `sg.vfs.write` never updates it. It reads `clean` before your write and `clean` after it; a failed publish rejects the write itself. So check #3 in your gate is always true. Your check #1 — read every written file back through the mount — is the real one, and it is the right one: reads reconcile against the server before serving. Keep it. This also answers your §5.3 question: the state is as of the last behind-check, the write does not settle it.

**History is not frozen — it never reaches the child.** `sg.history.log` takes `{limit, from}` only and is always served by the parent vault. `log({path:'data/'})` and `log('data/')` both return the parent's own chain; the 25/37 you saw was not child-versus-parent. "Make it live" is a new kernel verb and a policy decision (it would expose the child's decrypted commit messages, other writers' included, to the parent app), not a fix. The receipt removes your need for it.

**The child's vault id is not in the mount row.** It is in `data.link.json`, which your app can read. We will not add it to the app-facing row (see §3).

## 2 · What we will build

- **The receipt**: `sg.vfs.write` resolves `{ path, size, commit_id, published }` — for local and mounted writes alike (local: `published:false` until auto-push, with a host event when it lands). **Read the caveat:** `published:true` means the compare-and-swap publish succeeded at that instant. It does not protect your rows from a later *blind* push by a clone that is behind — the browser shells push blind, and we have not verified `sgit push`. For an irreversible purge, keep your split: purge on the **next** drain, after the read-back still finds the rows. We are asking the CLI team for CAS push, which is the real fix.
- **`sg.fs.mkdir` through the mount**, and **`sg.fs.move` within one mount** (today `move` would hang: no child handler, no request timeout — both being added).
- **A documented app-facing mount row**: `{ prefix, access, declared, state, at }`, stable spellings `clean | ahead | behind | diverged`, with the timing rule above.
- **Docs**: `.vault/app.json` and folder manifests **replace**, never merge; `permissions.network` (it is in `AUTHORING.md` §Egress — we will put it in the declared-mounts table where you looked); `vfs.status`/`vfs.sync` are kernel-internal (our guide's table implied otherwise — our fault); `EFBIG` at 3 MB; and: **the child's `.vault/app.json` is the real bound** — grant `write: ["events/", "feedback/"]` there, not `true`.
- **Shadow pre-flight** in the platform: an event when a declared prefix coincides with a real parent folder.
- **`Via-Mount` specified as an audit artefact**, with the parent vault id added. The label is already sanitised (newlines stripped, 80 chars), so it is owner-controlled, not attacker-controlled.
- **Append**: `configure` derives the enum key by default and documents the derivation; verbs validate before fetching. With one guard — see §3.
- Your `declare-mount.mjs` as the worked example for existing vaults — after a review that it never prints or persists a plaintext key, including under `--dry-run`. It handles the highest-tier secrets we have.

## 3 · What we will not do, and why

- **`sg.fs.delete` through a mount as a standing request.** Destructive verbs across a vault boundary require per-request elevation (the B5/B6 tier model); the issuance for that does not exist yet. We will not lower the tier to make it "work". Interim: you get `EUNDERPRIVILEGED` with a clear message instead of `EMOUNT_RO`, so it is a stated decision, not a mystery.
- **A 404 for an unknown vault or lane on the append gate.** Today a bad token is **403 whether or not the vault exists** — that is a deliberate absence of an existence oracle, and it has been in the code since July. The HTML 404 you see is produced above the route (the URL you post is the registered one; dev deploys on every push). **Please send the response headers of that 404** — if they are CloudFront's, the request never reached the Lambda and this is edge routing, not the gate.
- **The raw mount row as a contract.** It carries commit ids, `lastError.message` with server text, custody and the link ref, and `sg.vault.mounts()` has no permission check. Apps get the projection.
- **Cross-boundary `move`** → `EXDEV`. Partial state across two vaults is duplication or loss.
- **Silent enum-key derivation on a public-read vault.** The enum key is a pure function of the read key: publishing the read key publishes the lane's enumeration. Your topology is safe because the lane sits on the private viewer vault — by architecture, not by guard rail. `configure` will refuse without an explicit opt-in on a public-read vault.
