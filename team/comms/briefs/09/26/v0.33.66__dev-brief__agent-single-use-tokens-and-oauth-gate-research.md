# Dev brief — agent-created single-use password tokens, and an OAuth-gate research sprint

**date** 26 September 2026
**from** Dev (Explorer), from a voice memo by Dinis Cruz (26 Sep)
**status of the features described** Part 1 composes primitives that **EXIST**. Part 2 is **PROPOSED — does not exist yet** (no OAuth/OIDC code is in the codebase; the reality doc lists Google OAuth as proposed only). Nothing here is shipped until it is on the reality document.
**source** voice memo (transcribed): *"add support for the agents to easily create single-use password tokens, where we can basically use the shared functionality, which I believe already is working… and also have a sprint where we do research: can we add to SG/Send the feature of using OAuth as a protection mechanism… only if you've been authenticated in OAuth… we already have a version of that… we need to think about what would be the way to implement that on the server side, especially because we don't have secrets… the logic would be to use OAuth authentication before you even see the secret."*

This is two pieces of work with very different maturity. Part 1 is "expose and document something that already works." Part 2 is "research a genuinely hard design question." They should be separate sprints.

## Part 1 — Single-use password tokens for agents

### 1.1 What this is

An agent (VoiceDebrief, an n8n flow, a Claude session) should be able to create, in one operation, a share that:

- is protected by a **human-typable password** (the friendly token, e.g. `apple-mango-5623`);
- **self-destructs after one use** (one download, then the ciphertext is wiped);
- optionally **expires** on a clock as well.

The memo's own read is correct: *"I believe [the shared functionality] already is working."* It does. The primitives are shipped and tested; what is missing is a single clean way for an agent to ask for exactly this, and a page that says so.

### 1.2 The primitives that already exist (code-verified)

| Requirement | Shipped primitive | Where |
|-------------|-------------------|-------|
| Human-typable password that IS the key | **Friendly token** — `word-word-NNNN` derives both `transfer_id = SHA-256(token)[:12]` and the AES-256 key via `PBKDF2(token, 'sgraph-send-v1', 600000)`. No server-side token→id map; the token is all the recipient needs. | `friendly-crypto.js` (UI); the server just stores ciphertext under the derived id |
| One-time use | **`max_downloads: 1` + `auto_delete: true`** on `/api/transfers/create`. After the first download the payload is deleted and the transfer goes `exhausted` (further downloads → 410). | `Transfer__Service.get_download_payload` / `create_transfer` |
| Time limit | **`expires_at`** (ms since epoch) on create → 410 after expiry. | same |
| Revocation before use | **`delete_auth_hash`** on create + `x-sgraph-transfer-delete-auth` on delete → sender can burn it early. | `Transfer__Service.delete_transfer` |

So a single-use password token **is** a friendly-token transfer created with `max_downloads:1, auto_delete:true`. Every piece is live.

> **Terminology to fix (this is a real source of confusion).** "Token" means three different things in this system and the memo's phrasing touches all three:
> - **Access token** (`x-sgraph-access-token`) — authorises an *agent to create* transfers/vault writes. Admin-issued, `usage_limit`/`usage_count`/`status`. NOT a per-share secret.
> - **Share token / friendly token** — the per-share *password* the recipient types; derives the decryption key client-side.
> - **Delete-auth** — the sender's revocation secret for one transfer.
> The brief below only adds convenience around the **share/friendly token**. The access token model is untouched.

### 1.3 What is actually missing (the work)

1. **No single agent operation composes it.** Today an agent must: generate a friendly token → derive id+key client-side → `create(transfer_id=derived, max_downloads=1, auto_delete=true)` → upload ciphertext → complete → hand back the token. That is the VoiceDebrief guide's flow with three parameters flipped. It works, but every agent re-implements it. **Ask:** a documented recipe (and optionally a thin helper/MCP tool) — "create a single-use password share" — that sets those parameters and returns the friendly token + link.

2. **The friendly-token derivation is browser-only.** `friendly-crypto.js` runs in the UI. An agent in n8n/Python has to re-implement `SHA-256(token)[:12]` + `PBKDF2(token,'sgraph-send-v1',600000)`. **Ask:** publish the friendly-token derivation as a documented, language-neutral spec (like the SGMETA/AES layout already in the VoiceDebrief guide), plus a reference snippet in JS and Python, so any agent can mint one without the browser.

3. **No first-class "burn on read" acknowledgement.** `max_downloads:1 + auto_delete:true` deletes the payload *after* serving it, which is correct, but there is a race: if the download connection drops after the server wiped the payload, the recipient got nothing and the share is gone. **Decision to make:** is single-use "wiped after the bytes leave the server" (current) acceptable, or do we want "wiped after the client confirms receipt"? The former is simpler and matches the threat model (a one-time secret should fail closed); recommend keeping it and documenting the behaviour, not building an ack protocol.

### 1.4 Scope of Part 1

**In scope:** a documented agent recipe for single-use password shares; a language-neutral friendly-token spec + JS/Python reference; the terminology page above; an optional convenience wrapper (helper function or MCP tool `create_single_use_share`) that sets the three parameters. **Out of scope:** any server change to the transfer model (none is needed), any new storage.

**This is a "document and expose" sprint, not a build sprint.** The estimate is small precisely because the memo is right that it already works.

## Part 2 — OAuth as a protection mechanism (research sprint) — PROPOSED

### 2.1 The ask, precisely

From the memo: *"only if you've been authenticated in OAuth… before you even see the secret… on the server side, especially because we don't have secrets."* The desired property:

> A recipient can obtain the protected content **only after** completing an OAuth sign-in with an identity the sender allowed — and this gate is enforced **server-side, before the content is released**, without the zero-knowledge server ever holding the decryption key.

The memo notes *"we already have a version of that"* — the reality doc lists **Google OAuth as PROPOSED** (social login → vault key persisted; open decisions #15, #22). There is **no OAuth/OIDC code in the application today** (verified). So this is genuinely new server-side work, and the hard part the memo identifies is real: **the server has no secrets, so an OAuth gate cannot "release the key" — the server never had the key.** The research is about what an OAuth gate *can* do given that constraint.

### 2.2 The design space (three options, honestly compared)

The whole difficulty is that "decrypt" happens in the recipient's browser with a key the server never sees. OAuth can gate different things:

**Option A — Gate the ciphertext, keep the key out-of-band (recommended MVP).**
The server requires a verified OAuth identity (an OIDC `id_token`, validated against the IdP's JWKS, subject/email matching a sender-supplied allowlist) **before it serves the ciphertext** from `/download/{id}`. The decryption key still travels in the fragment / friendly token as today.

- *Preserves zero-knowledge fully* — the server verifies an identity and serves ciphertext; it never sees the key.
- *Delivers exactly what the memo describes* — "authenticate in OAuth before you even see the secret" (the secret being the encrypted bytes; the key is a second, independent factor).
- *Implementable server-side without holding any secret* — JWKS verification is stateless public-key crypto; the allowlist is non-sensitive metadata stored beside the transfer.
- *Honest limitation:* it is a **two-factor** gate (must be OAuth'd **and** hold the link/key). It does not make the key itself OAuth-derived. That is fine, and arguably better — it composes with the existing key model rather than replacing it.

**Option B — Envelope-encrypt the key to the recipient's identity via PKI (stronger, more work).**
The sender encrypts the decryption key to the recipient's **public key** (PKI exists — RSA-OAEP-4096 is shipped in `sgit pki`). OAuth is how the recipient proves which key is theirs and retrieves/unlocks their private key.

- *Ties the key to identity*, not just gating the ciphertext.
- *Requires solving key custody* — where does the recipient's private key live, and how does OAuth unlock it? This is the "vault key in Google app:data" open decision (#15/#22) and is unresolved. High value, high effort, depends on the identity-envelope work (P-313/P-314, all proposed).

**Option C — An OAuth-gated key-release microservice (compromises the model).**
A separate component holds a wrapping key and releases it only after OAuth. This reintroduces a secret-holding service and breaks the "no secrets" property the memo is proud of. **Recommend against** for the ZK product; note it only for completeness.

### 2.3 Recommended sprint shape

A time-boxed research sprint that produces a **decision**, not a build:

1. **Prototype Option A end to end** against one IdP. The memo says "Amazon authentication" — treat the IdP as pluggable and prototype with whichever is cheapest to stand up (Cognito / Sign-in-with-Amazon, or Google since it is already the proposed path). The server-side piece is: an OIDC `id_token` verification middleware (fetch JWKS, verify signature/`aud`/`iss`/`exp`, extract `sub`/`email`), plus an allowlist stored with the transfer (`oauth_gate: {provider, allowed_subjects|allowed_emails|allowed_domain}`), checked before `/download/{id}` serves bytes.
2. **Prove the zero-knowledge property is intact** — the server verifies an identity and serves ciphertext; write the test that asserts the key never reaches the server on any path.
3. **Document the threat model honestly** — what OAuth-gating does (stops anyone not signed in as an allowed identity from *fetching the ciphertext*) and does not do (it is not a substitute for the key; a leaked key + a compromised allowed account still opens it).
4. **Decision gate:** is Option A enough for the near-term product, with Option B recorded as the future PKI-identity path? Recommend **yes** — A is a real, shippable second factor that preserves the model; B waits on the identity-envelope decisions.

### 2.4 Open questions (must be answered in the sprint)

- **Which IdP(s) first?** Cognito vs Sign-in-with-Amazon vs Google. The reality doc's proposed path is Google (open decisions #15, #22 — client ID across `send.sgraph.ai` and `tools.sgraph.ai`). Amazon/Cognito may be simpler for the "before you see it" gate. Pick one for the prototype.
- **Where is the OAuth flow hosted?** The download page is static + a null-origin app frame. The OIDC redirect/callback needs a real origin. Likely a small authenticated route on the API host that sets a short-lived session and then serves (or 302s to) the gated download.
- **What is the allowlist granularity?** Specific `sub`/email, an email domain, or "any authenticated identity from provider X." All three are useful; the prototype should support at least domain + explicit list.
- **Session vs per-request?** After OAuth, do we mint a short session (cookie/bearer) so a multi-part or retried download does not re-auth each time? Recommend a short signed session bound to the transfer id.
- **Does this compose with single-use (Part 1)?** Yes, and it should: an OAuth-gated single-use password share is the strongest combination — recommend the prototype demonstrate exactly that as the flagship example.

### 2.5 Relationship to existing proposals

This sits directly on the identity roadmap already in the reality document: Google OAuth (proposed), the `sg1.` credential-prefix decision (#15), the multi-domain OAuth client-ID decision (#22), and the broader PKI-identity-envelope line (P-313/P-314, all proposed). Option A is the **smallest** step on that road that ships a real gate; Option B is where it meets the identity-envelope work. The sprint should update the identity reality doc's "Open Decisions" with whatever it resolves.

## 3 · Honest risks

- **Part 1** risk is near-zero (documenting shipped behaviour) except the single-use race in §1.3.3 — recommend "fail closed, document it," not a new ack protocol.
- **Part 2, Option A** risk: OIDC verification done wrong (accepting an unverified token, wrong `aud`, no `exp` check) turns a security feature into a bypass. The prototype must use a vetted JWKS-verification library and be security-reviewed by AppSec before any deploy. This is the one place where "we built an auth gate" can go badly if rushed.
- **Scope creep from B into A.** The temptation will be to solve key-custody (B) while building the gate (A). Resist — ship A as a ciphertext gate first; B is a separate, later decision that depends on unresolved identity work.

## 4 · Acceptance criteria

**Part 1 (this sprint):**
- A documented recipe + language-neutral friendly-token spec (JS + Python reference) for a single-use password share; the terminology page distinguishing access token / share token / delete-auth.
- Optionally, one convenience surface (`create_single_use_share`) that composes `max_downloads:1 + auto_delete:true + friendly token` and returns the token + link.
- No change to the transfer model; existing tests stay green.

**Part 2 (research sprint — produces a decision + prototype, not a prod deploy):**
- A working Option-A prototype against one IdP, behind a flag, with the zero-knowledge-intact test.
- A written decision: A ships / A+B roadmap, recorded on the identity reality doc.
- AppSec sign-off on the OIDC verification before any of it touches a real download path.
