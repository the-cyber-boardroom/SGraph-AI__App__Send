# Brief — sgit.ai docs vs the shipped API: what to fix, what to add, what to move from sgraph.ai

**date** 26 September 2026
**from** Dev / Librarian (Explorer)
**to** the sgit.ai content team + SG/API team
**builds on** [`08/16 — sgit.ai docs gap analysis`](../../08/16/v0.33.59__brief__sgit-ai-docs-gap-analysis.md) (that brief added the HTTP API reference section; this one reviews it against the code six weeks later and looks at the transfers surface, which that brief did not cover)

**How this was produced:** I read every `/api/*` page on sgit.ai and compared it line-by-line against the live route code in `lambda__user/`. sgit.ai has come a long way since August — there is now a real API reference (`/api/authentication`, `/vault-objects`, `/append-lanes`, `/transfers`, `/errors`). The findings below are (a) corrections where a page and the code disagree, (b) pages that should exist and do not, and (c) sgraph.ai library pages that belong on sgit.ai now that it is the canonical API site.

---

## 1 · Corrections — where a live page disagrees with the code

These are small but they are the ones that cost an integrator a debugging session (as the wrong auth-header name did for the VoiceDebrief work).

| # | Page | What it says / omits | What the code does | Fix |
|---|------|----------------------|--------------------|-----|
| C1 | `/api/vault-objects` | Lists `GET /api/vault/zip/{vault_id}` as "proposed, undocumented" | **Zip is live** — requires `x-sgraph-access-token` **and** `x-sgraph-vault-write-key`, returns `application/zip` of the vault's ciphertext. Verified live in the 08/16 brief and again here. | Document it as EXISTS with both required headers. The "proposed" label traces to a stale reality-doc line that was already corrected on 2026-08-25. |
| C2 | `/api/vault-objects` | "the immutable header is not currently being sent (as of Sep 21)" | The route **does** send `Cache-Control: public, max-age=31536000, immutable` for `-imm-` file_ids and `no-store` otherwise (`Routes__Vault__Pointer.read__vault_id__file_id`). | If a CDN in front is stripping it, that is an edge-config fix, not a code gap — but the page should not imply the API omits it. Re-verify against the deployed edge and correct the note. |
| C3 | `/api/vault-objects` | Batch ops: "reads, writes, deletes" — write-if-match not mentioned | The batch supports **`read`, `write`, `write-if-match` (CAS), `delete`**, stops on first conflict, stops on unknown op. There is also a compare-and-swap `write_if_match` on the single-object path. | Add `write-if-match` with its conflict semantics (returns `status:"conflict"` + current value, and halts the batch). This is the primitive agents need for optimistic concurrency and it is undocumented. |
| C4 | `/api/authentication` | Header list is correct (all six) | — | No change — this page is now accurate, including `x-sgraph-transfer-delete-auth`. Good. Worth adding a one-line "prefer the header; `?access_token=` works but leaks into logs." |
| C5 | `/api/transfers` | Friendly-token format not documented | `FriendlyCrypto` (word-word-NNNN) derives both the transfer id (`SHA-256(token)[:12]`) and the AES key (`PBKDF2(token, 'sgraph-send-v1', 600000)`) client-side, so the token is all a recipient needs and no server mapping exists. | Add a "Friendly tokens" subsection: it is the human-shareable alternative to the `#id/key` fragment, and it is already shipped in the UI. |
| C6 | `/api/index` + `/api/errors` | `/join/*` shown as endpoints "unresolved routing" | `/join/*` routes are defined in code but **not registered** in the live user-Lambda route set (confirmed in the 08/16 brief — absent from the live route paths; the reality doc's "3 live endpoints" was wrong). | Remove `/join/*` from the API index until it is actually mounted, or label it clearly PROPOSED. Listing an unmounted route in an API reference is worse than omitting it. |
| C7 | `/api/transfers` | `download_url` from `complete` shown without caveat | The `download_url` field (`/d/{id}`) is a **dead route** (404). | Note that integrators must build the link themselves (`/en-gb/download/#{id}/{key}`), or — better — track the code-side fix (Q1 in the API review) to return the real link-only URL, then update the page. |

## 2 · New pages sgit.ai should add

Ranked by how often an agent or integrator hits the wall today.

### P0 — `/api/transfers` needs the full send-and-share lifecycle, end to end

The transfers page documents the endpoints but not the **thing you actually have to do**: wrap in SGMETA → encrypt AES-256-GCM → create/upload/complete → build the fragment link. This is exactly the guide we just wrote for the VoiceDebrief integration (`library/guides/integrations/SG-SEND-FOR-VOICEDEBRIEF-AND-N8N.md`), and it is the highest-value page missing from the API site. **Action:** port that guide to `/api/transfers/sending-a-file.html` (or a `/docs/how-to/send-a-file.html`), generalised past VoiceDebrief. It already contains verified request/response/byte-layout, drop-in JS + Python, and the cross-language KAT. It is the missing keystone for the transfers half of the API the way `vault-messaging` was for the append half.

### P0 — `/api/agents.html` — the account-less agent quickstart

There is `agents.html` under `/docs/guides/` for the CLI, but nothing that says to an **API** consumer: "here is how an agent, with one access key, sends a file or writes to a vault in three calls, and hands back a link." The MCP surface (`transfers`, `presigned`, `vault`, `vault/presigned` tags are MCP-exposed) is also undocumented on the site. **Action:** one page: get an access key → the three transfer calls → the vault write calls → the MCP endpoint (`/mcp`) and which tools it exposes.

### P1 — `/api/limits-and-caching.html` (or fold into `/api/errors`)

`/api/errors` covers status codes and the append/batch caps well. It is missing: the **transfers** size ceilings (5 MB direct, 3.75 MB base64, then presigned/multipart), the **immutable vs no-store** caching contract (C2), and the **token cache TTL** (positives cached ~60 s in-Lambda; revocation takes effect within the TTL). Agents that retry need the TTL to reason about "I just created a token, why 401" and "I just revoked, why still 200." **Action:** add these three; they are all code-verified constants.

### P1 — `/api/write-if-match.html` — optimistic concurrency for vault refs

The CAS primitive (C3) is how two agents writing to the same vault ref avoid clobbering each other. It is shipped, tested, and undocumented. One short page with the request shape, the `conflict` response, and the retry loop. This is the primitive that makes multi-agent vaults safe and it is invisible today.

### P2 — `/api/public-preview.html`

The deliberately-public OG-preview derivation (`transfer_id = SHA-256('pvp-transfer-v1:'+id)[:12]`, `read_key = PBKDF2(id, 'sgraph-public-preview-v1', 600000)`) is what makes a vault link render a rich card in WhatsApp/LinkedIn. It is a genuine, shipped feature with a clean crypto story and it is undocumented externally. Good "look how the transparency model works in the open" page.

### P2 — `/api/self-hosting.html`

The API index mentions "self-hosted alternative" but nothing explains the storage-mode story: MEMORY (dev), DISK (container/EC2), S3 (prod), auto-detected via `SEND__STORAGE_MODE` / AWS creds. A self-hoster needs this, and it is the natural place to state the **disk-mode `file_id` hardening** note (S1 in the API review) once fixed — "on disk mode, ensure you run the version with file_id validation."

## 3 · sgraph.ai library pages that should move (or mirror) to sgit.ai

sgit.ai is now the canonical home for the API and vault platform. Several sgraph.ai `/library/` pages are really API/vault-platform docs that were written there first. Recommendation: **move the platform-mechanism pages, mirror the "how sgraph.ai itself is built" pages** (they are a legitimate case study, but they belong as a case study, not as the canonical reference).

| sgraph.ai library page | Recommendation | Why |
|------------------------|----------------|-----|
| `library/reference/vault-read-keys.md` | **Move** → `/docs/credentials` (merge) | Key-format spec is canonical API/credentials content. sgit.ai `/docs/credentials` already covers prefixes; the read-key format detail should live there, not on the content site. |
| `library/reference/per-article-vault-credentials.md` | **Move** → `/docs/guidance/` | Granular per-artefact read credentials is a vault-platform pattern, not sgraph.ai-specific. |
| `library/reference/sgit-skill.md` | **Move** → `/skills/` | sgit.ai already has `/skills/`; the CLI skill reference belongs with it. Keep one canonical copy. |
| `library/how-it-works/machine-readable-content/*` (resolution, three-layer, agent-access) | **Move** → `/docs/` | The `.md`-suffix machine-readable-endpoint pattern and agent-access guide are platform capabilities agents need from the API site. This is high-value and currently only discoverable on sgraph.ai. |
| `library/guides/sg-playwright.md` | **Mirror** → `/docs/how-to/` | Driving sg-playwright is cross-cutting (used against both sites). Mirror it; keep sgraph.ai's copy for its own audience. |
| `library/building-on-sgraph/*` (7 pages) | **Keep on sgraph.ai, link from sgit.ai `/case-studies/`** | This is genuinely "how we built sgraph.ai." It is a strong case study for sgit.ai's `/case-studies/` (which already has "live-vault-docs") but should not become the canonical platform reference — it is one implementation. |
| `library/how-it-works/email-fs-lite/*` (6 pages) | **Mirror** → `/docs/` or `/use-cases/` | Email-FS-lite is the vault-to-vault coordination protocol — a platform pattern that sits naturally beside `/docs/vault-messaging` and `/docs/append-lane-messaging`. Currently only on sgraph.ai. |
| `library/use-cases/agentic-js-api/*` and `js-tool-api-infographic-generation/*` | **Keep on sgraph.ai** | These are product/tooling showcases (infographic generator, JS tool API). Link from sgit.ai `/use-cases/` but they are sgraph.ai's own product surface. |
| `library/sg-teams/*`, `library/agentic-teams/*` | **Keep on sgraph.ai** | Team/governance content. sgit.ai has its own `/team/`; these are sgraph.ai's operating model. Cross-link, don't move. |

**Principle for the split:** *mechanism* (how a credential/endpoint/protocol works) → sgit.ai canonical. *implementation and showcase* (how sgraph.ai or a specific product uses it) → stays on its own site, linked from sgit.ai as a case study. The test: "would a self-hoster who never uses sgraph.ai need this?" If yes, it is API/platform docs and belongs on sgit.ai.

## 4 · Cross-check against the site's own open asks

sgit.ai `/docs/briefs/` already lists two API-team asks that this review corroborates:

- **"Fix `list` to return anchor not raw token"** — confirmed still true: the append `list` returns the raw append token as `inbox`. This is the finding from the 06/09 and 09/06 reviews. It remains the one append change worth doing (it is a breaking change needing a migration; keep it on the briefs board, don't drive-by it).
- **"Add `x-api-key` to CORS allow-list; test presigned-S3 fallback under browser CORS"** — the CORS allow-list in `Fast_API__SGraph__App__Send__User.setup_middleware__cors` currently lists `x-sgraph-access-token` and the vault headers but **not** `x-api-key`. If a browser transport needs it, it is a one-line add to `allow_headers`. Worth confirming whether the presigned browser path actually needs it before adding surface.
