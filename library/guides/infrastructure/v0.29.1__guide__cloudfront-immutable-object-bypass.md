# CloudFront Immutable Object Bypass — Deployment Guide

**Version:** v0.29.1 | **Date:** 2026-06-04 | **Status:** DEPLOYED to send.sgraph.ai

Skip Lambda for content-addressed immutable vault objects (`obj-cas-imm-*`)
by routing them directly from CloudFront to S3. No client changes required.

---

## What It Does

Immutable vault objects are encrypted ciphertext blobs whose ID is derived
from their content hash: `obj-cas-imm-{hex(SHA256(ciphertext))[:12]}`. They
never change. Previously, every read went through Lambda (cold-start 500ms+,
warm ~100ms) even though Lambda has no business logic to run — it just fetches
the blob from S3 and returns it.

After this change, CloudFront matches these requests by path pattern, a CF
Function rewrites the API-style URI to the S3 key, and CloudFront serves
the blob directly from S3 (or from its edge cache on repeat requests).

| Scenario | Before | After |
|----------|--------|-------|
| First request (this edge PoP) | Lambda + S3 (~100-600ms) | S3 direct (~50ms) |
| Repeat request (CF cache hit) | Lambda + S3 (~100-600ms) | Edge cache (~1ms) |
| Repeat request (browser cache) | Lambda + S3 (~100-600ms) | No network (~0ms) |

---

## Architecture: Three Changes

The bypass requires exactly three changes to the `send.sgraph.ai` CloudFront
distribution. No Lambda or client code changes.

### 1. CloudFront Function (`imm-object-rewrite`)

**Source:** `sgraph_ai_app_send/cloudfront/imm-object-rewrite.js`

A Viewer Request function that validates the URI with a strict regex and
rewrites it to the S3 key path. Anything that doesn't match returns 403.

**Input:**
```
/api/vault/read/{vault_id}/bare/data/obj-cas-imm-{hash}
```

**Output (rewritten URI):**
```
/sg-send__data/sg-send-api__v1.0/shared/vault/{vault_id[:2]}/{vault_id}/bare/data/obj-cas-imm-{hash}/payload
```

The rewrite mirrors `Storage__Paths.path__vault_payload()` in
`sgraph_ai_app_send/lambda__user/storage/Storage__Paths.py`.

**Strict regex:**
```
/^\/api\/vault\/read\/([a-z0-9]{8,24})\/bare\/data\/(obj-cas-imm-[a-f0-9]{12})$/
```

- `vault_id`: lowercase alphanumeric, 8-24 chars (matches `VAULT_ID_PATTERN`)
- `hash`: exactly 12 lowercase hex chars (matches `computeObjectId`)
- No path traversal: character classes reject `.`, `/`, `..`

### 2. S3 Origin (transfers bucket)

The transfers bucket added as a new origin with OAC (Origin Access Control):

| Setting | Value |
|---------|-------|
| Origin domain | `745506449035--sgraph-send-transfers--eu-west-2.s3.eu-west-2.amazonaws.com` |
| Origin path | *(empty)* |
| Origin access | OAC with SigV4 signing |

The S3 bucket policy restricts CloudFront to `GetObject` on
`*/obj-cas-imm-*/payload` paths only.

### 3. CloudFront Behavior (highest precedence)

| Setting | Value |
|---------|-------|
| Path pattern | `/api/vault/read/*/bare/data/obj-cas-imm-*` |
| Origin | S3 transfers bucket |
| CF Function | `imm-object-rewrite` (Viewer Request) |
| Cache policy | 1-year TTL (immutable content) |
| Allowed methods | GET, HEAD |
| Compress | Yes (gzip + brotli) |

## Request Flow

```
Browser
  GET /api/vault/read/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7

CloudFront behavior match (original URI, top-to-bottom):
  /api/vault/read/*/bare/data/obj-cas-imm-*  -> Prec 0 (S3 origin)

CF Function (Viewer Request):
  regex validates vault_id + hash
  rewrites URI -> /sg-send__data/.../vault/0j/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7/payload

CloudFront cache lookup (rewritten URI is the cache key):
  HIT  -> return cached response (~1ms)
  MISS -> S3 GetObject via OAC (~50ms) -> cache 1 year -> return
```

## Behavior Table (send.sgraph.ai)

| Prec | Path pattern | Origin | CF Function |
|------|-------------|--------|-------------|
| 0 | `/api/vault/read/*/bare/data/obj-cas-imm-*` | S3 transfers | `imm-object-rewrite` |
| 1 | `/api/*` | Lambda URL | -- |
| 2 | `/mcp` | Lambda URL | -- |
| 3 | Default `(*)` | S3 static | -- |

**Key insight:** CloudFront matches behaviors on the **original** request URI,
before any CF Function runs. The CF Function rewrites the URI for S3 key
resolution, but CloudFront does NOT re-match behaviors. The origin was
selected at match time and is locked in.

---

## Security Model (Three Independent Gates)

### Gate 1: Behavior path pattern

Only `/api/vault/read/*/bare/data/obj-cas-imm-*` routes to the S3 transfers
origin. Direct S3 key paths (e.g. `/sg-send__data/...`) hit the Default
behavior -> static S3 bucket -> 404.

### Gate 2: CF Function regex

The function rejects anything outside `[a-z0-9]{8,24}` for vault_id and
`obj-cas-imm-[a-f0-9]{12}` for the object. It is structurally impossible
to reach manifests, refs, tombstones, or non-immutable objects.

### Gate 3: S3 bucket policy

The OAC is restricted to `GetObject` on `*/obj-cas-imm-*/payload`. Even if
both CF gates failed, S3 would reject the request.

### Content is encrypted

Even bypassing all three gates yields encrypted ciphertext. The object ID is
a truncated SHA-256 of the ciphertext (unguessable). The decryption key is
never stored server-side.

## Deployment Commands

### Create and deploy the CF Function

```bash
# Create the function
aws cloudfront create-function \
  --name imm-object-rewrite \
  --function-config '{"Comment":"Rewrite immutable vault object reads to S3 key","Runtime":"cloudfront-js-2.0"}' \
  --function-code fileb://sgraph_ai_app_send/cloudfront/imm-object-rewrite.js

# Publish (use ETag from create output)
aws cloudfront publish-function \
  --name imm-object-rewrite \
  --if-match <ETag>
```

### Update an existing function

```bash
# Get current ETag
aws cloudfront describe-function --name imm-object-rewrite

# Update code
aws cloudfront update-function \
  --name imm-object-rewrite \
  --if-match <ETag> \
  --function-config '{"Comment":"Rewrite immutable vault object reads to S3 key","Runtime":"cloudfront-js-2.0"}' \
  --function-code fileb://sgraph_ai_app_send/cloudfront/imm-object-rewrite.js

# Publish (use NEW ETag from update output)
aws cloudfront publish-function \
  --name imm-object-rewrite \
  --if-match <new-ETag>
```

## Testing

### Test the CF Function in isolation

```bash
EVENT_JSON='{
  "version": "1.0",
  "context": { "eventType": "viewer-request" },
  "viewer": { "ip": "1.2.3.4" },
  "request": {
    "method": "GET",
    "uri": "/api/vault/read/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7",
    "headers": {},
    "querystring": {}
  }
}'

aws cloudfront test-function \
  --name imm-object-rewrite \
  --if-match <ETag> \
  --event-object "$(printf '%s' "$EVENT_JSON" | base64 | tr -d '\n')" \
  --stage LIVE
```

**Expected output:** `FunctionOutput` contains a `request` object (not
`response`) with the rewritten URI. If you see a `response` object, the
deployed code is wrong — see the Troubleshooting section.

### Verify end-to-end

```bash
# Literal slashes — should return ciphertext from S3
curl -D - -o /dev/null -s \
  'https://send.sgraph.ai/api/vault/read/<vault_id>/bare/data/obj-cas-imm-<hash>'
# Look for: server: AmazonS3, content-length > 0

# Repeat — should be a cache hit
curl -D - -o /dev/null -s \
  'https://send.sgraph.ai/api/vault/read/<vault_id>/bare/data/obj-cas-imm-<hash>'
# Look for: x-cache: Hit from cloudfront

# URL-encoded slashes — should return 403 (correct, our regex rejects %2F)
curl -D - -o /dev/null -s \
  'https://send.sgraph.ai/api/vault/read/<vault_id>/bare%2Fdata%2Fobj-cas-imm-<hash>'
# Look for: 403, content-length: 15 ("Invalid request")

# Non-immutable reads — should still go through Lambda
curl -D - -o /dev/null -s \
  'https://send.sgraph.ai/api/vault/read/<vault_id>/bare/refs/ref-pid-muw-abc123'
# Look for: server NOT AmazonS3 (goes to Lambda)

# Direct S3 path — should 404 (hits default behavior, wrong bucket)
curl -D - -o /dev/null -s \
  'https://send.sgraph.ai/sg-send__data/sg-send-api__v1.0/shared/vault/0j/0js1r0uj/bare/data/obj-cas-imm-00184ac7e9d7/payload'
# Look for: 403 or 404
```

## Troubleshooting

### Empty 200 response with `FunctionGeneratedResponse` header

```
HTTP/2 200
content-length: 0
x-cache: FunctionGeneratedResponse from cloudfront
cloudfront-functions: generated-by-CloudFront-Functions
```

**Cause:** The CF Function is returning a response object (not forwarding to
origin), but neither the expected 403 nor the expected forward-to-S3. This
means the **deployed function code does not match the source file.**

**How this happens:** `create-function` creates a DEVELOPMENT stage copy.
If you `publish-function` before uploading the code (or the
`--function-code` arg was wrong), the published function is empty/default.
CloudFront's default empty function returns `{statusCode: 200}` with no body.

**Diagnosis:** Run `test-function` and inspect `FunctionOutput`:
- `"response"` object with `statusCode: 200` and no body = **wrong code deployed**
- `"response"` object with `statusCode: 403` = function is working, URI didn't match
- `"request"` object with rewritten URI = function is working correctly

**Fix:** Re-upload the code with `update-function`, then `publish-function`
using the new ETag from the update.

### `PreconditionFailed` on test-function

```
An error occurred (PreconditionFailed) when calling the TestFunction operation
```

**Cause:** The `--if-match` ETag is stale. Every create/update/publish changes
the ETag.

**Fix:** Get the current ETag:
```bash
aws cloudfront describe-function --name imm-object-rewrite
```
Use the `ETag` value from the response.

### 403 on requests with `%2F` encoded slashes

This is **correct behavior**, not a bug. The CF Function regex expects literal
`/` characters. CloudFront delivers the URI as-is to the function — if the
client sends `%2F`, the function sees `%2F` (not `/`), and the regex rejects it.

The vault web client (`sg-send.js`) constructs URLs with literal slashes, so
production traffic always takes the correct path. The `%2F` rejection is bonus
defense against malformed requests.

### S3 returns 403 (AccessDenied)

The OAC is not configured, or the S3 bucket policy doesn't allow
`s3:GetObject` from the CloudFront distribution. Check:

1. The behavior has OAC assigned (not public or OAI)
2. The S3 bucket policy includes a statement allowing `cloudfront.amazonaws.com`
   to `GetObject` with `AWS:SourceArn` matching the distribution ARN
3. The `Resource` pattern covers `*/obj-cas-imm-*/payload`

## Maintenance

### When `Storage__Paths` changes

The S3 prefix in the CF Function (`sg-send__data/sg-send-api__v1.0/shared`)
mirrors constants in `Storage__Paths.py` (lines 11-15). If these change, the
CF Function must be updated. This is rare — changing them makes prior data
unreadable.

### When object ID format changes

The 12-hex-char hash comes from `SGVaultObjectStore.computeObjectId`. If the
hash length changes, update the regex in the CF Function. The behavior path
pattern uses wildcards and doesn't need updating.

### When vault_id format changes

The `[a-z0-9]{8,24}` constraint comes from `VAULT_ID_PATTERN` in
`Service__Vault__Pointer.py`. If this changes, update the CF Function regex.

## Rollback

1. Delete the behavior — immutable requests fall back to `/api/*` -> Lambda
2. CloudFront invalidation is NOT needed — cached objects are correct
3. The S3 origin and CF Function can remain — unused origins/functions are inert
