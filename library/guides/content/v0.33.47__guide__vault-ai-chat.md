# Vault AI Chat — user & feature guide

**Audience:** anyone using a vault at `dev.vault.sgraph.ai` / the vault UI; vault admins setting
AI up for their team. App authors: your surface is `sg.llm.*` — see
`library/guides/vault-html/AUTHORING.md`, not this guide.
**Verified against:** the shipped code on this branch, 2026-08-16 (incl. the P4 fixes). (The older
`library/sgraph-send/dev_packs/v0.27.80__vault-chat/USER_GUIDE.md` describes a May prototype
that never shipped — treat it as design history.)

---

## 1. What it is

Every vault has a built-in AI chat: open a vault, press **✨ AI** (or **✨ Ask AI** on a file),
and talk to a model *about your vault's content* — files you attach, screenshots you paste,
questions you dictate. It runs in the vault's own chrome at the real origin, and it calls
OpenRouter **directly from your browser** with a key stored *inside the vault*. There is no
SGraph server in the path: the same zero-knowledge posture as the vault itself.

By default the chat is **not an agent**: it cannot write to the vault, and it reads only what
you explicitly attach. Vault-reading *tools* exist but are off until deliberately granted (§7).

## 2. One-time setup (vault admin)

You need an [OpenRouter](https://openrouter.ai) API key — **mint a budget-capped, rotatable key**;
that credit limit is the real spending ceiling, everything below is accident-prevention.

1. Open the vault **with its full vault key** (not a read-only link) and an access key set.
2. **Settings → AI models (OpenRouter)** → paste the key → **Test** (validates against
   OpenRouter and lists the models your key can reach) → **Save**.
3. Under **(advanced)**, optionally set:
   - **Who can use the key** — see §3, the most important choice on the page.
   - **Default model** — pick from the list Test populated. Leaving it empty is allowed
     (the chat auto-picks and tells you), but a default makes behaviour predictable.
   - **Allowed models** — `*`, `anthropic/*`, or exact ids. The chat's model picker only
     ever shows models on this list.
   - **Spend caps per session** — max cost (USD) and max calls.

Everything saves to `.vault/llm/config.json`. That file sits inside the vault's protected
`.vault/` floor: **no vault app can ever read it through the bridge, under any permission** —
the credential is invisible to app code by construction.

## 3. Who can use the key — the two tiers

| Tier | Where the key lives | Who can chat | Who could extract the key |
|---|---|---|---|
| **Owner** (default) | Sealed with a key derived from the vault's **write** key | Only sessions opened with the full vault key | Same — a read-only session *cannot* derive the seal |
| **Shared** (opt-in) | In the config file in clear (encrypted at rest like every vault file) | Anyone who can open the vault, read-only links included | Anyone who can open the vault |

This is a cryptographic boundary, not a policy checkbox: a read-only session has no write key,
so under the owner tier it *cannot* open the seal — the chat shows "owner-sealed and
unavailable in a read-only session". Choose **Shared** only when everyone you'd give the vault
key to should also be able to spend (and, inevitably, extract) the credential.

## 4. Using the chat

Open it with the **✨ AI** button in the header, or **✨ Ask AI** on any open file.

- **Attach files** — open a file and click **➕ Add to chat**. Attached files are chips with a
  char count and an ✕; they stay attached across the whole conversation ("clear all" empties
  the set). Re-adding a file you just edited refreshes the copy the model sees. Context is
  **explicit**: the chat never silently reads whatever is on screen. Up to 20 files sharing a
  ~24k-character budget, split evenly; anything beyond a file's slice is cut and the model is
  told **inside the prompt** that the file is truncated, so it cannot pretend it read it all.
  Binary files attach as a name only — their bytes are never sent.
- **Paste or drop a screenshot** — image chips show a thumbnail; images are downscaled
  (max 1568px / 4 MB, 4 per message). If your current model can't read images the chat warns
  *before* sending and suggests vision models from your allow-list. An image is sent with
  **that message only** — afterwards the conversation keeps a text note of what was attached,
  so follow-up turns are never silently re-billed for the pixels.
- **Ask by voice** — 🎤 records on the vault's own chrome (the browser's mic prompt applies),
  ■ stops; the transcript appears in the input and is sent, so a misheard word is visible.
  While recording, a persistent "● your microphone is on" status shows.
- **Pick the model** — the dropdown in the header lists your allow-list ∩ your key's models.
  If no default is configured, the chat auto-picks and *says so*.
- **⚙ parameters** — per-session temperature / top-p / max-tokens. Blank = the provider's own
  default. Max-tokens is **clamped to the vault policy** — a per-session control is never a way
  around the vault's ceiling.
- **Stop** — the Send button becomes Stop mid-stream; the partial answer is kept and its cost
  still recorded.

## 5. Costs — always visible, never invented

Every call lands in the **request ledger** (🧾): model, latency, tokens, cost, and *where the
cost figure came from*. Estimates render with a `~` prefix; shortly after each call the
authoritative cost is fetched from OpenRouter and replaces the estimate. The header shows the
session's running spend. Session caps from Settings stop new calls when reached — but the hard
ceiling is your OpenRouter key's own credit limit.

## 6. Read-only vaults

Reading the vault never requires AI setup. A read-only session can chat **only** if the admin
chose the *Shared* tier (§3); owner-sealed vaults show a clear "unavailable in a read-only
session" state instead of a broken button.

## 7. Vault tools (opt-in, committed, read-only)

The 🔧 bar can grant the model **read-tier tools**: `session` (its own cost ledger) and
`files.read` (`list_folder`, `read_file`, `stat`, `exists`). The defaults are all-off, and:

- Grants save to **`.vault/llm/tools.json`** as a real commit — that file's history is the
  privilege audit log — and the file lives under `.vault/`, which tools can never reach: the
  model cannot read, relax, or widen its own grants.
- `files.read` **requires an explicit allow-list**; enabling the group alone grants nothing
  (every call returns "no allowed paths"). This is deliberate: one checkbox must not mean
  "the entire vault". Set the scope in the 🔧 bar's **allowed-paths field** (comma-separated
  globs, e.g. `docs/**, *.md`) — saved with the grant as a commit. The same thing can be set
  by editing `.vault/llm/tools.json` directly:

  ```json
  { "schema": 1,
    "session":    { "enabled": true },
    "files.read": { "enabled": true, "allow": ["docs/**", "*.md"], "deny": ["private/**"] } }
  ```
  Globs: `*` stays within a folder, `**` spans folders, deny wins over allow.
- Tool results enter the conversation wrapped in an **UNTRUSTED DATA** fence and the model is
  instructed that fenced text is data, never instructions. Reads are capped (16k chars), the
  loop is bounded (8 rounds, then it must answer with what it has), every round is on the
  ledger, and each tool call renders as a live 🔧 chip in the transcript — no invisible actions.
- Understand the residual risk before enabling `files.read`: the model reads files you scoped,
  and the model call itself sends that content to OpenRouter. A poisoned document could try to
  steer what gets read. Scope narrowly.

## 8. When it says no — every state, explained

| Message | Meaning | Remedy |
|---|---|---|
| "No AI key configured" | `.vault/llm/config.json` absent or keyless | Settings → AI models (needs a writable open) |
| "owner-sealed and unavailable in a read-only session" | Owner tier + ro-link open | Open with the full vault key, or admin switches to Shared |
| "No model selected" / "no usable model" | No default and nothing on the allow-list matches your key | Set a default, or widen Allowed models |
| "…cannot read images" | Current model is text-only and an image is attached | Pick a suggested vision model |
| "Session … limit reached" | Vault policy cap hit | Raise the cap in Settings, or accept it |
| "no allowed paths" (tools) | `files.read` enabled without an allow-list | §7 — set `allow` in tools.json |
| Upstream errors (rate limits etc.) | Reported verbatim, mid-stream ones included | Usually transient; the ledger records the failure |

## 9. Security model, in five lines

1. The key lives in `.vault/` — unreachable by any vault app, under any grant.
2. Owner tier seals it against read-only sessions **cryptographically**, not by policy.
3. Vault apps never see the key: `sg.llm.*` calls are brokered by the host, and app frames are
   served a CSP that removes direct network egress (their bridge is the only way out).
4. App-side AI use is consent-gated (and apps cannot weaken that consent), budget-capped
   per app, and listed as a standing grant in the app HUD.
5. Everything spent is on the ledger, with its provenance.

## 10. For app authors

Vault **apps** get AI through `sg.llm.{available, models, chat, cancel, usage, listen, imagePart}` —
declared in `app.json` `permissions.llm`, consent-gated, streamed over the bridge. The contract,
error codes and examples live in `library/guides/vault-html/AUTHORING.md`. `available()` first,
always: AI is a runtime capability of the *vault*, not of your app.
