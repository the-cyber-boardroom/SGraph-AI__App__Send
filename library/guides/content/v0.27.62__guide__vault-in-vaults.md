# SG/Vault — Vaults-in-Vaults (Sub-Vaults) User Guide

**Version:** v0.27.62 | **Audience:** vault owners, human authors, Claude sessions

> **Status — in development (Phases 0–2 code-complete).** The behaviour below reflects the current
> code. It is **not yet browser-verified or deployed**. What works in code today: a `*.link.json`
> file renders as an inline sub-vault folder and opens **read-only** on expand (key from a saved
> record, this device, or a prompt); external-resource link files (video / link / image / app) load
> in a controlled, default-deny embed with click-to-load; the vault key is per-tab; and the owner
> **🔗 Add link** button creates link files for you. What is **not built yet**: editing inside a
> sub-vault, and granting an app access to a folder. See "Limitations" at the end.

---

## 1. What it is

A vault can point at **other vaults**. A pointed-to vault (a "sub-vault") shows up **inline in the
file tree, exactly like a folder** — you just expand it. The only visual difference from a normal
folder is a small vault glyph (`🗄`) and a read-only chip (`·ro`).

This is how, for example, a clinic's "parent" vault can hold many per-patient vaults, or you can
gather demo vaults under a `demos/` folder — without copying their contents. The sub-vault's files
stay in the sub-vault; the parent only holds a tiny pointer.

The mechanism is a **convention**, like Git submodules: a small pointer file on disk, plus UI
behaviour. Nothing is baked into the vault format.

---

## 2. The link file (`*.link.json`)

A sub-vault is declared by a small JSON file in the regular tree whose name ends in **`.link.json`**.

- The **prefix is a label you choose** (`acme-demo.link.json`, `patient-alice.link.json`).
- The **`.link.json` suffix is the signal** that tells the UI to treat the file as a sub-vault.
- **Rename it off the suffix** (e.g. `acme-demo.link-2.json`) and it becomes a plain `.json` file
  again — a quick way to "disable" a link. (This is also why **no secret may ever go in a link
  file** — it's just a normal file that could be read as raw JSON at any time.)

### Minimal contents

The link file is deliberately tiny and **carries no key**:

```json
{
  "vault_id": "abcd1234",
  "ref_id": "lk-a1b2c3d4"
}
```

- `vault_id` — the public id of the child vault (safe to store).
- `ref_id` — an id that cross-references the key/metadata record kept in the parent's
  `.vault/owner/ro-links.json` (see §4).

### Optional fields (per-location overrides)

You may override any metadata on a specific link file:

```json
{
  "vault_id": "abcd1234",
  "ref_id": "lk-a1b2c3d4",
  "label": "Patient: Alice (post-op)",
  "pin": { "mode": "latest" },
  "description": "Right health-score record",
  "public_id": "acme-demo-pp"
}
```

- `label` — display name (otherwise the filename prefix is used).
- `pin` — `{ "mode": "latest" }` (default) follows the child's latest state; `{ "mode": "commit",
  "commit": "<id>" }` pins to a specific commit (like a Git submodule).
- `public_id` — if the child vault has a **public preview** published, the open dialog will show
  its title/description **before** asking for a key (see §5).

**The same vault can appear in several places** — just drop a link file (with the same `ref_id`)
in each folder. Edit the shared record once and every pointer updates. **Moving a sub-vault** is
just moving the small link file, then refreshing.

### How to create one

In a **writable** vault, click the **🔗 Add link** button in the file browser toolbar. Choose a type:

- **Linked vault** — enter a label and the child vault's key (full key, simple token, or `ro-…`
  token). The key is **validated by opening the vault** (which also reads its real `vault_id`), then
  **saved on this device**; a `<label>.link.json` pointer is written into the vault. The sub-vault
  then appears as a folder and opens read-only on expand — no prompt on this device.
- **Web page / Video / Image / External app** — enter a label and a URL. The type is auto-detected
  from the URL; a `<label>.link.json` pointer is written and the resource appears as an embed leaf.

(You can also still hand-author a `*.link.json` with the **New File** button — the Add button just
fills it in for you.)

## 3. Opening a sub-vault

Expand the sub-vault node like any folder. The UI then:

1. **Opens the child read-only** and splices its files in under the node (loaded on demand — nothing
   is fetched until you expand it). You can browse and open files inside, just like the parent.
2. If no key is available yet, the node shows a lock; opening it shows a small **link card** that
   (optionally) displays the child's public info, then asks for the key.

> **Read-only, for now.** In this version you can **read** a sub-vault but not edit it — editing
> inside a nested vault needs commit/sync handling that isn't built yet. Whatever key you provide,
> the sub-vault opens read-only.

### Open in a new window

The link card also offers **"Open in new window ↗"**, which opens the sub-vault as a normal,
full vault in its own browser tab (where it may be writable). (Multi-tab behaviour — each tab
remembering its own vault — is being finalised; see Limitations.)

---

## 4. Where the key lives (three options)

A link file holds **no key**. When you open a sub-vault, the key is found in this order:

1. **An owner record** in the parent's `.vault/owner/ro-links.json` (keyed by `ref_id`). If present,
   the sub-vault opens **silently, with no prompt**. The record holds the child's read key +
   reference; it lives at the parent's read tier, so anyone who can read the parent can traverse
   into these read-only sub-vaults. (Writing these records via a button is the upcoming owner flow;
   today they can be created programmatically.)
2. **Saved on this device** — if you ticked "Save on this device" in the link card, the key is kept
   in this browser's local storage.
3. **Ask each time** — otherwise you're prompted on each open (nothing is stored).

> **Keys are secrets.** They live only inside the encrypted vault record, in your browser's local
> storage, or in the prompt — **never** in the `.link.json` file, never in Git, never in logs.

---

## 5. Public info before the key

If the child vault's owner has published a **public preview** (a small, deliberately-public
title/description/thumbnail), and the link file carries that child's `public_id`, the open dialog
shows it **before** asking for the key. This lets someone recognise "this is the ACME demo vault"
without first holding its key — and is the same public-preview mechanism used at
`send.sgraph.ai/en-gb/app/<public-id>`.

## 6. External resources (video / link / image / app)

The same `*.link.json` convention can point at **external resources** instead of a vault. Give the
link file a `url` (and optionally a `type`):

```json
{ "ref_id": "lk-intro", "type": "video", "url": "https://youtu.be/XXXX", "label": "Intro video" }
```

- `type` is one of `video` / `link` / `image` / `app`. If you omit it, it's **auto-detected from the
  URL** (YouTube/Vimeo → video, `.png`/`.jpg`/… → image, `.mp4`/… → video file, otherwise a web page).
- It shows in the tree as a resource leaf (`🌐`/`▶`/`🖼`/`🧩` + `↗`). Clicking it opens the resource
  **in a controlled embed in the preview pane**:
  - **images** render as `<img>`, **video files** as `<video>` (media elements — they can't read the page);
  - **web pages / apps / YouTube** render in a **sandboxed iframe with no access to your vault**
    (no bridge, no messaging) — a sticky banner says *"External window · …  · cannot read this vault"*.
- **Click-to-load (privacy):** an external resource shows a placeholder first and only contacts the
  third party when you click **Load** — so opening a vault (or a folder full of links) never phones
  home on its own.

> External resources are **default-deny**: an embedded page or app cannot read your vault. (Selectively
> granting an app narrow access to a folder is a future, opt-in capability — not in this version.)

---

## 7. Security model (in brief)

- **Sub-vaults are read-only in this version.** No editing inside a nested vault.
- **A link file never contains a key** — only a public id and a reference. The key is resolved
  separately (§4).
- **Read access flows by key.** You only see a sub-vault's contents if you (or the parent's owner
  record) hold its read key. There is no backdoor — the zero-knowledge boundary is the key.
- **External embeds (when they ship) are default-deny** — they cannot read your vault unless you
  explicitly, narrowly grant access.

## 8. Limitations (this version)

| Area | Status |
|------|--------|
| Read a sub-vault inline | ✅ code-complete (not yet browser-verified) |
| Open with a saved record / on-device key / prompt | ✅ code-complete |
| Same vault in many places; move by moving the file | ✅ supported |
| Recursive sub-vaults (a sub-vault with its own sub-vaults) | ⏳ structurally supported; expansion-state polish pending |
| Editing / writing inside a sub-vault | ❌ not in this version (read-only) |
| Owner **🔗 Add link** button (creates the `*.link.json`; saves the key on this device) | ✅ code-complete (not yet browser-verified) |
| Writing portable `ro-links` records from the UI (so a linked vault opens silently on *other* devices too) | ⏳ device-key today; in-vault record is a follow-on |
| External resources (video / link / image / app embeds, click-to-load, default-deny) | ✅ code-complete (not yet browser-verified) |
| Selectively granting an external app access to a vault folder | ❌ future, opt-in (Phase 3, AppSec-gated) |
| Per-tab "open in new window" (each tab remembers its own vault) | ✅ done (vault key per-tab; access token shared) |
