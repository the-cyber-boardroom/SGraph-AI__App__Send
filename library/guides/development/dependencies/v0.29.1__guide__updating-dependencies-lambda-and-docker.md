# Updating Dependencies — Lambda and Docker

**Version:** v0.29.1 | **Date:** 2026-06-03 | **Status:** Code-verified guide
**Audience:** Any agent or developer updating Python dependencies in SGraph Send

---

## The Two-Track Model

Lambda and Docker resolve dependencies through completely different mechanisms.
Understanding this is essential — it explains why one target can have fresh deps
while the other is months behind.

| Target | Resolution mechanism | Cache behaviour |
|--------|---------------------|-----------------|
| **Docker** | `pip install` from `pyproject.toml` wildcards at image build time | Always gets latest PyPI releases — no action needed |
| **Lambda** | Hardcoded `==` pins in `*__config.py` → content-addressable S3 zip | Frozen until you explicitly bump a pin |

### Why they diverge

Docker's `pyproject.toml` uses wildcard deps (`"*"`). Every `docker build`
runs a fresh `pip install` that resolves the latest compatible versions from
PyPI. Starlette, for instance, will be whatever FastAPI's latest release pulls
in.

Lambda uses a **content-addressable S3 cache**. The deploy chain computes
`sha256(sorted(pin_strings))[:12]` to produce a cache key. If the S3 object
exists, it skips `pip install` entirely and reuses the cached zip. Transitive
dependencies (like Starlette) are baked into that zip and never re-resolved
until the hash changes — and the hash only changes when you change a pin string.

**Result:** Docker gets automatic upgrades. Lambda stays frozen until you
manually bump a pin. This is by design — Lambda deployments must be
reproducible and auditable.

## When to Update

Update Lambda pins when:

- A **security vulnerability** (CVE) is found in a transitive dependency
- An **upstream package** (e.g. `osbot-fast-api-serverless`) publishes a new
  version with bug fixes or features you need
- The `/api/info/versions` endpoint on a deployed Lambda shows outdated
  versions compared to Docker

Docker deps update automatically. You only need to act on Docker when:

- You need to **pin** a minimum version (e.g. `starlette = ">=1.0.1"` in
  `pyproject.toml`) to prevent regression to a vulnerable release
- A dep introduces a breaking change and you need to **cap** it

## Step-by-Step: Updating Lambda Dependencies

### 1. Identify what needs bumping

Check the deployed Lambda versions:

```
GET https://dev.send.sgraph.ai/api/info/versions
```

Compare against Docker (if running) or PyPI latest.

### 2. If the fix is in a transitive dependency

When the target package isn't directly pinned (e.g. Starlette, which is pulled
in by `osbot-fast-api-serverless`), you need to bump the **upstream package**
first:

```bash
# Clone the upstream repo
git clone git@github.com:owasp-sbot/OSBot-Fast-API-Serverless.git
cd OSBot-Fast-API-Serverless

# IMPORTANT: use `poetry update`, not `poetry install`
# `poetry install` reads the (possibly stale) lock file
# `poetry update` re-resolves all transitives from PyPI
poetry update

# Verify the target transitive was bumped
grep starlette poetry.lock

# Commit and push — CI will publish to PyPI
git commit -a -m 'updated poetry.lock'
git push
```

Wait for the upstream CI to publish the new version to PyPI before proceeding.

### 3. Bump the pins in SGraph Send

The pins live in two files — **both must be updated identically**:

| Lambda | Config file |
|--------|------------|
| User | `sgraph_ai_app_send/lambda__user/user__config.py` |
| Admin | `sgraph_ai_app_send/lambda__admin/admin__config.py` |

Edit the version strings:

```python
# Before
APP__SEND__USER__LAMBDA_DEPENDENCIES = ['fastapi-mcp==0.4.0'                     ,
                                        ...
                                        'memory-fs==v0.40.0'                     ,
                                        ...
                                        'osbot-fast-api-serverless==v1.33.0'     ]

# After
APP__SEND__USER__LAMBDA_DEPENDENCIES = ['fastapi-mcp==0.4.0'                     ,
                                        ...
                                        'memory-fs==v0.41.0'                     ,
                                        ...
                                        'osbot-fast-api-serverless==v1.35.0'     ]
```

**Rules:**
- Pin every version with `==` — floating versions would silently reuse a stale
  zip (the hash is computed from the literal pin strings)
- Update **both** config files identically
- Only bump packages that have new versions on PyPI

### 4. Run tests

```bash
python -m pytest tests/unit/ -x -q
```

The pin values are string constants — tests pass locally even before a deploy.
The real verification happens after deploy.

### 5. Deploy and verify

After the CI deploys the Lambda with the new pins:

```
GET https://dev.send.sgraph.ai/api/info/versions
```

Confirm the transitive dependencies (e.g. `starlette`) now show the expected
version. The first cold start after a pin change is slower (full S3 GET +
unzip), but subsequent invocations reuse the `/tmp` cache.

## The S3 Cache Mechanism (How It Works)

For full architecture details, see:
`team/comms/briefs/05/20/v0.27.38__architect-to-dev__lambda-dependency-packaging.md`

Summary of the flow:

```
Pin strings in *__config.py
        │
        ▼
sha256(sorted(pins))[:12]  →  S3 key: lambdas-deps/{base_name}/{hash}.zip
        │
        ├─ S3 object exists?  →  Skip upload (reuse cached zip)
        │
        └─ S3 object missing? →  pip install → strip → zip → upload to S3
```

At Lambda cold start:

```
Handler imports  →  load_combined_dependency()
        │
        ├─ /tmp/{hash}/ exists?  →  sys.path.insert (warm container)
        │
        └─ /tmp/{hash}/ missing? →  S3 GET → unzip to /tmp → sys.path.insert
```

**Key insight:** changing ANY pin string changes the hash, which busts the S3
cache and forces a complete re-resolution of all dependencies including
transitives.

## Checking Available Versions

```bash
# For packages with v-prefix versioning (osbot-*, memory-fs)
pip install "memory-fs>=0" 2>&1 | grep "Ignored"

# For standard PyPI packages
pip index versions fastapi-mcp
pip index versions httpx
```

## Common Mistakes

| Mistake | Why it's wrong | Fix |
|---------|---------------|-----|
| Only update one config file | User and Admin Lambda diverge | Always update both `user__config.py` and `admin__config.py` |
| Using `poetry install` upstream | Reads the stale lock file | Use `poetry update` to re-resolve transitives |
| Adding a pin to `pyproject.toml` to fix Lambda | `pyproject.toml` only affects Docker | Bump the pin in `*__config.py` |
| Expecting Docker to need action | Docker always gets latest via `pip install` | Docker self-heals on every build |
| Floating versions in Lambda pins | Hash stays the same, zip never rebuilt | Always use `==` pins |

## Quick Reference

```
Docker deps stale?  →  Shouldn't happen. Check pyproject.toml for caps.
Lambda deps stale?  →  Bump pins in user__config.py + admin__config.py.
Transitive stale?   →  Bump the direct dep that pulls it in.
                        May require `poetry update` on the upstream repo first.
Verify after deploy →  GET /api/info/versions
```
