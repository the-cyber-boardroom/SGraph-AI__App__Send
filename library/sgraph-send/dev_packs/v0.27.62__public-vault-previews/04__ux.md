# 04 — UX: Two Access Modes and the Settings Edit Flow

**version** v0.27.62
**date** 25 May 2026
**from** Developer (lead) + Designer
**to** implementing agent, Product
**source** `01__brief` (+ 3 corrections) · `02__architecture` · `03__derivation-and-storage` · `09__security-review`

These flows are the contract for the public page and the settings editor. Every state below is a first-class screen (mockups in `05__mockups`). Quoted copy is normative.

---

## 1. Anchor principles → UX rules

| Principle (source) | UX rule |
|---|---|
| Controlled, opt-in exposure (brief, R1) | A vault has **no** public preview by default. Nothing is published until the owner explicitly publishes. |
| Default to nothing public (R2) | The editor opens **empty and disabled**. Publishing requires an explicit "THIS WILL BE PUBLIC" confirmation that echoes the rendered card. |
| The public-id is genuinely public (R-leak) | The editor and share affordance state plainly that the public-id appears in URLs and logs. Never imply secrecy. |
| The real vault key rides in `#` only (architecture §3.1) | The key prompt writes the key to `location.hash`, never to the path or a query string. "Copy full-access link" warns it grants full access. |
| Expiry is real but be precise (doc 02 §7, R-expiry) | Expiry copy says what is enforced: "After this, the link stops working (server-enforced)." Both time and open-count are available. |

## 2. Access Mode A — preview-then-ask-key (no `#` fragment)

URL: `/en-gb/app/<public-id>` (production) — or `?p=<public-id>` in the dev/interim build (doc 02 §4.3). `<public-id>` is the public-vault-about-key.

### 2.0 Key-prompt prominence, "key on this device", and the correct-vault rule (lead refinements)

- **The key prompt is the primary call-to-action** — a separated, prominent box (heading + large input + button), not a small field, so it's obvious the viewer must enter the vault key.
- **A public-id URL ALWAYS shows the preview**, even for a logged-in owner with a saved key. The generic last-opened key (`sg-vault-key`) is **never auto-used** for `/en-gb/app/<public-id>`, because that key is for whatever vault was last opened — **not necessarily the vault this public-id is about** (the public-id carries no vault id, by design). Auto-opening it would silently open the *wrong* vault.
- **"Key saved on this device":** the only key we auto-offer is one we stored **for this specific public-id** (`localStorage` `sg-pvp-key:<public-id>`), written when the owner publishes it or when anyone successfully opens it here. When present, the card shows a one-click **"🔓 Open this vault — key saved on this device"** button above the manual prompt; a stale stored key (vault rekeyed) is dropped and the prompt shown. This IS the correct vault (stored by construction). *(Verifying a manually-typed key matches "the right vault" would require putting the vault id in the public preview — deferred; noted in doc 08.)*

### 2.1 Happy path

1. **Shell loads instantly** — header + a centred card slot showing a **loading skeleton**; no network for the shell.
2. **Derive + fetch** — `derivePublicPreviewKeys(publicId)` → `{ transferId, readKeyRO }`; `fetchPreview` GETs `download-base64/<transferId>`, unwraps SGMETA, AES-GCM-decrypts, validates.
3. **Preview rendered** — `sg-public-preview-card` shows title, description, thumbnail, disclaimer (if any), support (if any), expiry note (if any).
4. **Key prompt** — below the card: "Enter the vault key to open the contents" + `[Open vault]`. Always shown in Mode A.
5. **Open vault** — on submit, parse the key, set `location.hash = <key>` (so reload re-opens), run the normal open flow (`SGVaultCrypto.deriveKeys` → `SGVault.open` → tree). The card stays as the header while contents fill in.

### 2.2 Every state in Mode A

| State | Trigger | Copy |
|---|---|---|
| **Loading skeleton** | shell loaded, fetch in flight | (no text) |
| **Preview rendered** | fetch + validate OK | "Enter the vault key to open the contents" |
| **Wrong-key error** | open flow throws after the prompt | "That key didn't open this vault. Check it and try again." |
| **Expired preview** | `410` on fetch, or `now > expires_at_ms` | "This preview has expired. {support.label}" (or generic) |
| **Exhausted (open-count reached)** | `410 exhausted` on fetch | "This preview has reached its view limit. {support.label}" |
| **Preview-not-found (404)** | transfer absent / not complete | "No preview here yet. If you have the vault key you can still open the vault below." + key prompt |
| **No-preview-set** | owner never published | identical to not-found (indistinguishable by design) |
| **Malformed/invalid** | `validatePreview()` rejects | same not-found copy (don't leak validation internals to the public page) |

**Wrong-key vs not-found are deliberately different surfaces.** Not-found never reveals whether a vault exists; wrong-key only appears after a preview rendered (so the public-id is already known-good).

## 3. Access Mode B — hash-key auto-load (`#` fragment present)

URL: `/en-gb/app/<public-id>#<vault-key>`. The `#` fragment is the **real vault key** and never reaches the server.

1. **Shell loads** — same instant shell.
2. **Preview fetch + render fire immediately** — the card paints as fast as Mode A.
3. **In parallel**, the app reads `location.hash`, parses the vault key, and starts the normal open flow **without** a prompt. No key field shown.
4. **Contents fill in behind the card.** Preview is the fast skeleton-with-content; the tree renders below / replaces the card body once the vault opens.

The two fetches are independent and concurrent. If the preview 404s but the key is valid, the vault still opens.

| State | Copy |
|---|---|
| Preview painting + vault loading | "Opening vault…" |
| Both ready | (none) |
| Preview OK, key in `#` is wrong | fall back to the Mode A prompt: "The key in this link didn't work. Enter the correct vault key." |
| Preview 404, key valid | "No preview set for this vault." (small, above contents) |
| Expired preview, key valid | "This preview has expired." + contents still load (the key is independent of expiry) |

## 4. The corporate no-key state (first-class screen)

When a viewer has the link but no key, the page must be a useful destination, not a dead end. Rendered by `sg-public-preview-card` from the convention JSON:

- **Disclaimer** (`disclaimer`) in a bordered callout: "Confidential. Do not use unless authorised."
- **Support link** (`support.label` + `support.href`) as a button: "No key? Contact Dinis" → `mailto:`/`https:`.
- The key prompt remains below, so an authorised viewer who *does* have the key can still proceed.

If neither is set, the card shows title/description/thumbnail + the key prompt. Disclaimer and support text are owner-authored and **treated as public**.

## 5. The settings edit flow (`sg-public-preview-editor`)

Lives on the vault settings surface (doc 08 Q5). Calls the `sg-public-preview` write path.

### 5.1 Enabling a preview (default OFF — R2)

- Opens with a single toggle **"Public preview: OFF"** and an empty, disabled form.
- Turning it ON reveals the form but **publishes nothing** — publish is a separate explicit step (§5.4). "ON" means "I am authoring," not "it is live."
- Copy: "A public preview lets anyone with the link see the title, description, and thumbnail you choose — even without the vault key. It is deliberately public."

**Defaults from the vault (owner confirms at publish).** When the editor opens the vault, it seeds empty fields from the vault name: the **Title** defaults to the vault name, and the **Custom public-id** to a slug of it (e.g. "PoC | Wardley Maps in MD" → `poc-wardley-maps-in-md`). Both fill only when empty (never overwrite the owner's input), and the "THIS WILL BE PUBLIC" confirmation (§5.4) is the explicit approval step. This avoids the empty-id publish error.

### 5.2 Choosing the public-id (custom vs random)

- **Random id** — generates a 16-char ~80-bit id (`[a-z0-9-]`). Shown read-only with "regenerate". On the astronomically rare `409` at publish, regenerate and retry.
- **Custom id** — text field, validated live: charset `[a-z0-9-]`, 4–63 chars, no leading/trailing/double hyphen, **rejected if it matches `^[a-z]+-[a-z]+-\d{4}$`** (keeps it distinct from Simple Tokens). Copy: "Use lowercase letters, numbers, and hyphens (4–63 chars)."
- **"Id is taken" path:** on publish, `create` returns `409`. If the owner holds the `delete_auth` for that id in their vault bookkeeping → this is an **update** (§5.5). Otherwise: "That public id is already taken. Choose another."

### 5.3 Authoring the fields

| Field | Control | Notes / copy |
|---|---|---|
| Title (required) | text | "Shown as the page title and the social-share headline." |
| Description | textarea | "One or two lines. Shown on the page and in link previews." |
| Thumbnail | **two sources:** (a) upload an image (drag-drop), (b) **pick a file already in the vault** | Both paths converge on the same **fully native** pipeline — *no external libraries, no wasm*: `createImageBitmap(blob)` → draw onto a `<canvas>` downscaled to fit the cap → `canvas.toBlob(…, 'image/webp', q)` (or `OffscreenCanvas.convertToBlob`). The re-encode **drops EXIF automatically** (R-thumb). Check the result against the inline cap (~64 KB); over cap → second transfer (`<public-id>:thumb`) or downscale further. **Vault-file path:** the editor reads + decrypts the chosen vault file via the owner's open vault (`SGVault` file read), then runs the same encode — so the public thumbnail is derived from vault content the owner already holds, never the encrypted bytes. |
| Disclaimer | textarea | "Optional. Shown to anyone who opens the link without the key." |
| Support label + href | text + text | "Optional. A way for people without the key to reach you." href must be `mailto:`/`https:`. |
| Expiry — by time | toggle + number "in N days" | **OFF by default — confirmed no-expiry default (doc 08 Q3).** Writes `expires_at` at create when ON. "After N days the link stops working (server-enforced)." |
| Expiry — by opens | toggle + number "N opens" | **OFF by default.** Writes `max_downloads` (+ `auto_delete`) when ON. "After N opens the link stops working (server-enforced)." |

The editor **validates that no field is literally named `write_key` / `read_key` / `passphrase`** anywhere in the assembled JSON (R2); publish is blocked with a hard error if found.

### 5.4 The "THIS WILL BE PUBLIC" confirmation + publish

Before any network write, a confirmation that:
- Echoes the **exact rendered card** the public will see.
- States plainly: "This will be publicly readable by anyone with the link `…/app/<public-id>`. The id appears in URLs and server logs. The vault's contents stay encrypted."
- Requires an explicit `[Publish — make this public]`; `[Cancel]` returns to the form, publishing nothing. `[Publish]` is **never** the default-focused button (no accidental Enter-to-publish).

On publish: generate a random `delete_auth`, encrypt + 3-step upload (`create` carries `delete_auth_hash` + any expiry), then write bookkeeping to the owner vault at `.vault/owner/public-previews/<public-id>.json`. Success → the share affordance (§7).

### 5.5 Edit-after-publish — delete-then-recreate (ships day one)

Because DELETE exists (doc 03 §3), the edit flow is **seamless and in-place from the start** — same public-id, edited content, **same share link**:

- Owner edits fields → `[Update]`.
- `updatePreview` reads the bookkeeping, `DELETE`s the existing transfer with the persisted `delete_auth`, then recreates at the **same transfer-id**.
- UX: "Updating preview…" → "Updated. Your share link is unchanged."

(No versioned-id workaround is needed — that was an upstream `__Tools`-pack fallback for a missing DELETE that this repo does not have.)

### 5.6 Unpublish

`[Unpublish]` → `unpublishPreview`: `DELETE`s the transfer with the persisted `delete_auth` and marks bookkeeping inactive. Copy: "Unpublished. The preview link will stop working."

## 6. Share affordance + key-inclusion warning

After publish (and on the settings page for a live preview):

| Button | Copies | Warning |
|---|---|---|
| **Copy preview link** | `…/app/<public-id>` (no fragment) | "Anyone with this link sees the preview and is asked for the key." |
| **Copy full-access link** | `…/app/<public-id>#<vault-key>` | **"Includes the vault key — anyone with this link can open the full vault. Share only with trusted people."** (high-contrast; behind a "show full-access link" disclosure) |

The safe default (preview-only) is the obvious one. The `#key` is assembled client-side from the current session's key and is **never** logged or sent to the server.

## 6a. "How this works" transparency — on the tester/debug surface, NOT the public card

**Decision (lead):** the "How this works" disclosure is **removed from the public preview card** — for an end-user who just wants to open a vault, the transfer-id / read-key detail is noise that confuses. The transparency info now lives only on the **`/en-gb/preview/<id>` tester page debug strip** (doc 05 §6) and the OG-route `/info` JSON, where a curious developer can inspect it. The public card (`sg-public-preview-card`) shows only: title / description / thumbnail / disclaimer / support / footer + the key prompt.

The tester debug strip still shows the underlying SG/Send file, so a curious user can open it on `send.sgraph.ai` and learn the mechanism (doc 02 §9):

```
▾ How this works
   This preview is an ordinary SG/Send file, addressed deterministically by
   the public id in this URL. Nothing extra is stored on the server.
   Transfer id   a1b2c3d4e5f6                                   [copy]
   Read-only key UklGRkq…(base64url, decrypt-only, public)      [copy]
   Open the raw file ↗  send.sgraph.ai/en-gb/open/view#a1b2c3d4e5f6/UklGRkq…
```

All three values are derivable by anyone from the public id (which is public), the key is read-only, and the owner's delete key is **never** shown. This is opt-in to view (collapsed by default) and safe to expose (doc 09 R-transparency).

## 7. Where the editor mounts (surface)

- The `/en-gb/app/` route already exists (`…/v0.2.3/en-gb/app/index.html`) — extend it to read the public-id path segment (or `?p=` interim). The card + key-prompt shell go here.
- The **editor** is a standalone `VaultComponent` mounted on the vault settings surface (the vault browser's settings/manage area). It can be proven first in the dev tool / a settings panel; mounting it on the production settings page is in-repo wiring (no cross-repo dependency — the whole vault UI is here).

---

## 8. Accessibility & copy notes

- Key prompt has a visible label and `aria-describedby` for the wrong-key error.
- The "THIS WILL BE PUBLIC" confirmation is keyboard-reachable; `[Publish]` is never default-focused.
- Disclaimer callout uses a text label ("Confidential"), not colour alone.
- Expired / not-found / exhausted states announced via a polite live region.
- All public-ness warnings are text, high-contrast, never the sole job of an icon.

---

## 9. What this UX does NOT do (v0.1.0)

- No PKI auto-access (doc 02 §8) — the key prompt is the acquisition step.
- No crawler-card preview *inside* the editor beyond the rendered-card echo (the real crawler card is the Lambda OG route, doc 02 §6 / Phase 5).
